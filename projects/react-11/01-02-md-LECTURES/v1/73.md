# Lecture 73: Hiding a Tab Without Losing Its State with Activity

*(How can a tab leave the screen and come back exactly as the user left it?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do you hide a subtree without losing its state with <Activity>?

---

## VS | Removing a tab with `&&` vs. hiding it with `<Activity>`: one throws the state away, the other keeps it

> On your computer, you can close a window or minimize it: both take it off the screen, but only the minimized window comes back with your work still in it. **In React, `<Activity>` does the same for a part of the page: with `mode="hidden"`, React hides it and keeps its state until you show it again.** The usual `&&` closes it instead: React removes the component, and everything the user typed in it is gone.

In React, a page often shows **one part at a time**: the tabs of a settings page, the steps of a checkout, a chat and a contact list. Until now, we did this with `&&`: show the Chat tab only while `tab` is `'chat'`. When the condition is false, React removes `ChatTab` from the page, and its state goes with it. **This is why React gives us `<Activity>`.** It takes the tab off the screen without removing it, so the tab comes back exactly as the user left it.

Take a chat app with two tabs at the top, Chat and Contacts. The user starts a message, `Hello John`, then clicks Contacts to check a name, then clicks Chat to finish the message. Ask yourself: what should the message field show now? `Hello John`, of course. The user only looked away for two seconds.

**Why:** With `&&`, React does not know that the user only looked away. For React, `false && <ChatTab />` is `false`, and React draws nothing for `false`. So `ChatTab` is not hidden, it is gone, and the draft lived inside it. With `<Activity mode="hidden">`, React keeps `ChatTab`, hides it, and the draft waits.

The message field is empty. The user has to type `Hello John` again. Two reminders and one new word explain what happened:

> [!DEFINITION]
> **Unmount.** [REVIEW] Unmount is React's word for removing a component from the page. React runs the cleanup of its Effects, takes its elements out of the DOM, and throws away its state. When the same tag appears again, React mounts a brand-new component that starts from its initial state (Lesson 32).

> [!DEFINITION]
> **State lives at its place in the tree.** [REVIEW] React keeps a component's state only while the component is rendered at its place in the tree. The React docs say it plainly: "unmounting a component destroys its internal state, which is not always what you want" (Lesson 25).

> [!DEFINITION]
> **Activity.** [NEW] `<Activity>` is a component React provides, like `<Suspense>`. You import it from `react` and wrap it around the part of the page you want to hide and show. Its prop `mode` is `'visible'` or `'hidden'`. The React docs say it in one line: "`<Activity>` lets you hide and restore the UI and internal state of its children." It shipped in React 19.2 (Lesson 73).

### `<Activity>` in Two Lines

Here are the two ways to take the Chat tab off the screen, side by side:

```jsx title="Removing the Chat tab with && vs. hiding it with Activity"
{~tab === 'chat' &&~ <ChatTab />} {/* The user comes back to an empty field */}
<Activity ~mode={tab === 'chat' ? 'visible' : 'hidden'}~><ChatTab /></Activity> {/* The user comes back to Hello John */}
```

While the user looks at Contacts, both lines show no Chat tab. **It looks the same, but it is NOT the same thing!** With `&&`, React unmounts `ChatTab`, and the draft goes with it. With `<Activity>`, React keeps `ChatTab` in the tree and only hides it, so the draft waits for the user.

```tree caption="Two ways to take the Chat tab off the screen: remove it with && or hide it with Activity."
Two ways to take the Chat tab off the screen
- !Remove it with `&&` [`tab === 'chat' && <ChatTab />`] | React **unmounts `ChatTab`** | The user comes back to an **empty field**
- +Hide it with `<Activity>` [`<Activity mode="hidden">`] | React **keeps `ChatTab`** in the tree and hides it | The user comes back to **`Hello John`**
```

### Hidden Is More Than `display: none`

Remember `display: none` from CSS? An element with it takes no space and shows nothing, but it is still in the DOM. A hidden Activity does exactly that to your tab: React writes `display: none` on it for you.

But React did the hiding itself, so React knows the tab is not on the screen. That lets React do two things your own CSS never could:
1. **It stops the tab's Effects.** React runs their cleanup, as if the tab were unmounted. A chat connection disconnects while nobody sees the tab.
2. **It gives the tab's updates a lower priority.** The tab the user is looking at always goes first.

The React docs give the picture to keep in mind: "conceptually you should think of 'hidden' Activities as being unmounted", with one difference: "React saves their state for later."

Keep this one sentence in mind for the whole lesson: **a hidden Activity keeps the state and the DOM of the tab, and stops its Effects.**

### The Rule of Thumb: should the tab come back as the user left it?

**Ask one question about every tab: when the user comes back, should it be exactly as they left it? If yes, hide it with `<Activity>`. If it should start fresh, remove it with `&&`.**

`<Activity>` is not the only way to keep a draft. Developers use four ways, and all four keep it. They differ in where the draft lives while the user is away:
1. **Render every tab, and hide the others with your own CSS.** The tab is never removed, so the draft stays in it. The docs: "This solution works great for simple UIs. But it can get very slow if the hidden trees are large and contain a lot of DOM nodes."
2. **Lift the draft up into the parent, `App`.** The draft lives in `App`, so removing the tab no longer matters (Lesson 24). The docs call this "the most common solution."
3. **Save the draft in `localStorage`.** The browser keeps it, even after the user closes the page.
4. **Wrap each tab in `<Activity>`.** The draft stays in the tab, and the tab itself needs no change. The docs say the state comes back "without any changes to its implementation."

`<Activity>` fits when the tab's own state and its DOM should come back untouched, and the tab should stop its work while nobody sees it. This lesson is about that fourth way.

A senior developer also knows the three classic mistakes:
1. **Expecting React to remember a tab that `&&` removed.** It cannot: the tab is gone.
2. **Thinking `mode="hidden"` is only CSS.** The tab's Effects, such as its connection to the chat server, stop while it is hidden.
3. **Forgetting that a hidden `<audio>` or `<video>` is still in the DOM.** It keeps playing.

The rest of the lesson shows each one on a real chat app.

## SECTION | A Chat App with Two Tabs

Our page is one chat app with two buttons at the top, Chat and Contacts. One state variable in `App`, `tab`, holds `'chat'` or `'contacts'`. The Chat tab holds the message field, and it stays connected to the chat server while it is open. The Contacts tab lists two names, John and Mia.

`App` keeps the open tab in `tab`. Each button sets it, and each `&&` line shows one tab:

```jsx title="src/App.jsx"
import { useState } from 'react';
import ChatTab from './ChatTab.jsx';
import ContactsTab from './ContactsTab.jsx';

export default function App() {
  const [tab, setTab] = useState('chat');

  return (
    <main>
      <button onClick={() => setTab('chat')}>Chat</button>
      <button onClick={() => setTab('contacts')}>Contacts</button>
      {~tab === 'chat' &&~ <ChatTab />} {/* Shows ChatTab only while tab is 'chat' */}
      {~tab === 'contacts' &&~ <ContactsTab />} {/* Shows ContactsTab only while tab is 'contacts' */}
    </main>
  );
}
```

The draft does not live in `App`. It lives inside `ChatTab`, in its own state. The `<textarea>` is a controlled field (Lesson 20): it shows `draft`, and every letter calls `setDraft`:

```jsx title="src/ChatTab.jsx"
import { useState, useEffect } from 'react';
import { createConnection } from './chat.js';

export default function ChatTab() {
  const [~draft~, setDraft] = useState(''); // The draft lives inside ChatTab

  useEffect(() => {
    const connection = createConnection();
    connection.connect();
    return () => connection.disconnect();
  }, []);

  return (
    <section>
      <label>
        Message
        <textarea value={draft} onChange={e => setDraft(e.target.value)} />
      </label>
    </section>
  );
}
```

The Effect connects the Chat tab to the chat server, and its cleanup disconnects it (Lesson 32). The chat server is the fake one from React's docs. It only prints to the Console:

```js title="src/chat.js"
export function createConnection() {
  return {
    connect() {
      console.log('✅ Connecting...');
    },
    disconnect() {
      console.log('❌ Disconnected.');
    },
  };
}
```

The Contacts tab is a plain list:

```jsx title="src/ContactsTab.jsx"
export default function ContactsTab() {
  return (
    <ul>
      <li>John</li>
      <li>Mia</li>
    </ul>
  );
}
```

Each principle changes one file, or only watches the page:

**PRINCIPLES:** `<Activity>` hides a tab instead of removing it. Six principles follow:
1. **`&&` throws the draft away.** Leaving the tab unmounts it, so React throws away its state.
2. **A hidden Activity keeps the draft.** The tab stays in the tree, so its state comes back.
3. **A hidden Activity is more than your own `display: none`.** React writes the style, and also stops the Effects and lowers the priority.
4. **A hidden Activity disconnects the chat server.** React runs every Effect cleanup on hiding, and every Effect again on showing.
5. **A hidden `<audio>` keeps playing.** It is still in the DOM, so a cleanup must pause it.
6. **A hidden Activity loads the contacts before the click.** React renders a hidden tab in the background, so data read with `use` is ready.

## PRINCIPLE | `&&` on a tab: leaving the tab unmounts it, so its state is thrown away

> [!PRINCIPLE]
> **Principle 1: Removing a Tab: A Removed Component Loses Its State**
>
> *When `&&` stops rendering a tab, React unmounts it and throws away its state; coming back mounts a new tab with its initial state.*
>
> The user only looks away from the Chat tab for a moment, but React does not know that. When `tab === 'chat'` becomes false, `ChatTab` leaves the tree: its Effect is cleaned up, its `<textarea>` leaves the DOM, and `draft` is gone. The next `<ChatTab />` is a brand-new component, and its `useState('')` starts empty.
>
> **DO THIS:**
> ```jsx
> {~tab === 'contacts' &&~ <ContactsTab />} {/* The list holds nothing the user typed, so removing it loses nothing */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {~tab === 'chat' &&~ <ChatTab />} {/* **WRONG:** the draft the user typed is thrown away on every switch */}
> ```

The user types `Hello John`, clicks Contacts, and clicks Chat again. **The message field comes back empty.** Here is what happens, in order:
1. The user types `Hello John`. `setDraft` stores it in the state of `ChatTab`.
2. The user clicks Contacts. `tab` becomes `'contacts'`.
3. `tab === 'chat'` is now false, so `App` no longer returns `<ChatTab />`.
4. React unmounts `ChatTab`: it runs the Effect cleanup, takes the `<textarea>` out of the DOM, and throws away `draft`.
5. The user clicks Chat. React mounts a brand-new `ChatTab`, and `useState('')` starts again from an empty string.
6. The message field is empty.

The Console tells the same story. The chat server connects when the tab appears, disconnects when the user leaves, and connects again for the new tab:

```page caption="The page after the user types Hello John, clicks Contacts, and clicks Chat again, with the Console."

form:
  textarea: Message | | bad
log: ✅ Connecting... | chat.js:4
log: ❌ Disconnected. | chat.js:7
log: ✅ Connecting... | chat.js:4
```

The Console previews in this lesson show the order of a production build. In development, StrictMode adds extra pairs of `❌ Disconnected.` and `✅ Connecting...` to catch a missing cleanup (Lesson 47).

While the user is on Contacts, open the Elements panel. The Chat tab is really gone. There is no `<textarea>` anywhere in the DOM:

  <button>Chat</button>

### How developers meet this bug

A developer builds the tabs with `&&`, as Lesson 10 taught. They test each tab on its own, and each tab works. Then a real user types a long message, opens Contacts to copy a name, and comes back. The message is gone. The Console shows no error, and the user types the whole message again.

Something that can be tricky: sometimes a fresh tab is exactly what the product wants. When the user opens a chat with a different person, the old draft must not appear in the new chat. For that case, the docs give the chat a `key` based on the person, so React starts fresh on purpose (Lesson 25).

## PRINCIPLE | `<Activity mode="hidden">`: the tab stays in the tree, so its state comes back

> [!PRINCIPLE]
> **Principle 2: Hiding a Tab: A Hidden Child Stays in the Tree**
>
> *Wrap the tab in `<Activity>` and switch `mode` between `'visible'` and `'hidden'` instead of removing the tab; React keeps its state while it is hidden.*
>
> With `&&`, the tab leaves the tree, and React throws away its state. With a hidden Activity, the tab stays in the tree, and React saves its state for later. When `mode` becomes `'visible'` again, the tab comes back exactly as the user left it, and the tab itself needs no change.
>
> **DO THIS:**
> ```jsx
> <Activity ~mode={tab === 'chat' ? 'visible' : 'hidden'}~> {/* ChatTab stays in the tree; the draft waits */}
>   <ChatTab />
> </Activity>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Activity mode={tab === 'chat' ? 'visible' : 'hidden'}>
>   {~tab === 'chat' &&~ <ChatTab />} {/* **WRONG:** && still removes ChatTab, so the draft is lost */}
> </Activity>
> ```

### The smallest Activity boundary

You import `Activity` from `react`, next to `useState`, and wrap it around the tab:

```jsx title="The smallest Activity boundary"
import { ~Activity~ } from 'react'; // React provides Activity, as it provides useState

<Activity ~mode="hidden"~> {/* Hides ChatTab and keeps its state */}
  <ChatTab />
</Activity>
```

Besides its children, `<Activity>` takes one prop, `mode`, with two values:
- **`'visible'`** shows the children. It is also the default, so an `<Activity>` without `mode` shows them.
- **`'hidden'`** hides the children and keeps their state for later.

The children are what you put between the opening and the closing tag (Lesson 9). The docs describe them as "The UI you intend to show and hide." Here, the child is `<ChatTab />`. The docs call the `<Activity>` tag together with its children an **Activity boundary**. When this lesson says "the boundary becomes hidden", it means its `mode` switches to `'hidden'`.

### Replacing both `&&` lines in `App`

Only `App` changes. Each `&&` line becomes an Activity boundary, and the condition moves into `mode` as a ternary (Lesson 10):

```jsx title="src/App.jsx"
import { ~Activity~, useState } from 'react'; // The only new import
import ChatTab from './ChatTab.jsx';
import ContactsTab from './ContactsTab.jsx';

export default function App() {
  const [tab, setTab] = useState('chat');

  return (
    <main>
      <button onClick={() => setTab('chat')}>Chat</button>
      <button onClick={() => setTab('contacts')}>Contacts</button>
      <Activity ~mode={tab === 'chat' ? 'visible' : 'hidden'}~> {/* ChatTab stays in the tree on every switch */}
        <ChatTab />
      </Activity>
      <Activity ~mode={tab === 'contacts' ? 'visible' : 'hidden'}~> {/* ContactsTab stays in the tree too */}
        <ContactsTab />
      </Activity>
    </main>
  );
}
```

`ChatTab` does not change at all. The user types `Hello John`, clicks Contacts, and clicks Chat again:

The docs give the reason: "When you hide a component using an Activity boundary instead, React will 'save' its state for later." And when the boundary becomes visible again, "React will reveal the children with their previous state restored."

### VS | A draft in state vs. a draft kept by the `<textarea>`: both come back

What if the `<textarea>` keeps its own text, with no `value`, no `onChange`, and no state?

```jsx title="A draft kept in state vs. a draft kept by the textarea itself"
<textarea ~value={draft} onChange={e => setDraft(e.target.value)}~ /> {/* The draft lives in React state */}
<textarea /> {/* The draft lives in the textarea, kept by the browser */}
```

Under `<Activity>`, both come back with `Hello John`, for two different reasons:
- **The `<textarea>` with `value` and `onChange`** keeps the draft because React saves the state of the hidden tab.
- **The `<textarea>` with no state** keeps the draft because React does not remove it from the DOM. React only hides it, as Principle 3 shows.

Under `&&`, both lose the draft, because React removes both.

### Keeping `&&` inside the boundary

A common slip: a developer moves to `<Activity>` but keeps the old condition inside it:

```jsx title="src/App.jsx"
<Activity mode={tab === 'chat' ? 'visible' : 'hidden'}>
  {~tab === 'chat' &&~ <ChatTab />} {/* **WRONG:** && still removes ChatTab, so the draft is still lost */}
</Activity>
```

The draft is still lost. When the user clicks Contacts, `&&` still removes `ChatTab`, so `<Activity>` has nothing left to hide. Activity can only keep a child that is still rendered inside it.

## PRINCIPLE | `mode="hidden"`: React hides the tab with `display: none`, and also stops its Effects

> [!PRINCIPLE]
> **Principle 3: Hidden Is More Than CSS: React Writes display: none and Knows the Tab Is Hidden**
>
> *A hidden Activity keeps its children in the DOM with `display: none`; unlike your own CSS, it also cleans up their Effects and renders them at a lower priority.*
>
> React hides the top element of each hidden child with `display: none`, so the `<textarea>` and its text stay in the DOM. Your own `display: none` keeps them too, but React never learns that the tab is hidden, so the tab's Effects keep running and its updates keep full priority.
>
> **DO THIS:**
> ```jsx
> <Activity ~mode={tab === 'chat' ? 'visible' : 'hidden'}~> {/* React hides the tab and cleans up its Effects */}
>   <ChatTab />
> </Activity>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <div ~style={{ display: tab === 'chat' ? 'block' : 'none' }}~> {/* **WRONG:** hidden on the screen, but the chat server stays connected */}
>   <ChatTab />
> </div>
> ```

### What React writes on the hidden tab

**A hidden Activity does not remove its children from the DOM. React hides them with the CSS `display: none`.** The docs: "React will visually hide its children using the `display: "none"` CSS property."

Open the Elements panel while the user is on Contacts. The Chat tab is still there, with its `<textarea>`:

```dom caption="The Elements panel while the user is on Contacts: React put display none on the Chat tab, and the textarea is still inside it."

  <button>Chat</button>
  <button>Contacts</button>

      Message
      <textarea>Hello John</textarea>
    </label>
  </section>
  <ul style=""> | note: Emptied by React when the Contacts tab became visible
    <li>John</li>
    <li>Mia</li>
  </ul>

```

Our code never wrote that `style`. React wrote it on the top element of the hidden child: the `<section>` that `ChatTab` returns. The `!important` flag makes this rule win over any other `display` the page sets on that element. Nothing of the Chat tab shows on the page, but `Hello John` is still inside the `<textarea>`.

The `<ul>` of the Contacts tab carries an empty `style`. Why? The Contacts boundary was hidden when the page loaded, so React wrote `display: none` on it then. When the user clicked Contacts, React emptied that `style`.

### VS | Your own `display: none` vs. a hidden Activity: the same DOM, but only Activity stops the Effects

Developers already know another way to hide a tab: write `display: none` themselves.

```jsx title="Hiding the Chat tab with your own CSS vs. with Activity"
<div ~style={{ display: tab === 'chat' ? 'block' : 'none' }}~><ChatTab /></div> {/* Your own CSS hides the tab */}
<Activity ~mode={tab === 'chat' ? 'visible' : 'hidden'}~><ChatTab /></Activity> {/* React hides the tab */}
```

Both keep the tab in the DOM with `display: none`. Both keep the draft. **It looks the same, but it is NOT the same thing!** With your own CSS, React has no idea that the tab is hidden. With `<Activity>`, React knows, and it does two more things:
1. **React cleans up the Effects of the hidden tab.** The docs: "It will also destroy their Effects, cleaning up any active subscriptions." Principle 4 shows this in the Console.
2. **React gives the hidden tab a lower priority** (Lesson 66). The docs: "While hidden, children still re-render in response to new props, albeit at a lower priority than the rest of the content." React finishes the work of the visible tab first, so the hidden tab does not slow down the tab the user is using.

### Replacing Activity with a plain `<div>`

A developer reads that Activity uses `display: none`. To keep things simple, they replace `<Activity>` with a `<div>` and their own inline style. The draft is still kept, so nothing looks wrong on the screen. But every hidden tab now keeps its Effects running. The hidden Chat tab stays connected to the chat server for a screen nobody sees, and every update inside it competes with the visible tab at full priority.

## PRINCIPLE | `useEffect` cleanup in a hidden tab: React disconnects on hiding and connects again on showing

> [!PRINCIPLE]
> **Principle 4: Hidden Effects: React Runs Every Cleanup When the Boundary Is Hidden**
>
> *When a boundary becomes hidden, React runs the cleanup of every Effect inside it; when it becomes visible, React runs the Effects again.*
>
> A hidden Activity keeps the state and the DOM, and it stops the Effects. The chat server disconnects when the user leaves the tab and connects again when the user comes back, while the draft waits in the `<textarea>`. So every Effect must do its stopping work in its cleanup function.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection();
>   connection.connect();
>   ~return () => connection.disconnect();~ // Disconnects when the tab is hidden, connects again when it is visible
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection();
>   ~connection.connect();~ // **WRONG:** no cleanup, so the hidden tab stays connected and coming back opens a second connection
> }, []);
> ```

Here is the Effect of `ChatTab` again:

```jsx title="src/ChatTab.jsx" startLine="7"
useEffect(() => {
  const connection = createConnection();
  connection.connect(); // Runs when the tab appears
  ~return () => connection.disconnect();~ // Runs when the boundary becomes hidden
}, []);
```

**When a boundary becomes hidden, React runs the cleanup of every Effect inside it. When the boundary becomes visible again, React runs the Effects again.** For the Effects, hidden means unmounted. For the state and the DOM, hidden means kept.

### The draft survives, and the connection does not

The draft came back, so you might expect the whole tab to stay alive, the connection included. It does not. Here is what happens, in order:
1. The page loads on the Chat tab. React runs the Effect, and the Console shows `✅ Connecting...`.
2. The user types `Hello John`.
3. The user clicks Contacts. The Chat boundary becomes hidden.
4. React runs the cleanup, and the Console shows `❌ Disconnected.`
5. The draft `Hello John` is still in the hidden `<textarea>`.
6. The user clicks Chat. The boundary becomes visible.
7. React runs the Effect again. The Console shows `✅ Connecting...`, and the field shows `Hello John`.

```page caption="The page after the user types Hello John, clicks Contacts, and clicks Chat again, with Activity."
line: [Chat] [Contacts]
form:
  textarea: Message | Hello John | good
log: ✅ Connecting... | chat.js:4
log: ❌ Disconnected. | chat.js:7
log: ✅ Connecting... | chat.js:4
```

Compare it with the Console of Principle 1. With `&&`, the Console printed the same three lines, and the field came back empty. With `<Activity>`, the Effects run as if the tab left and came back, but the state stays.

```tree dir=right caption="What a hidden Activity keeps and what it stops while the user is on Contacts."
The Chat tab inside a hidden Activity
- +Kept [`draft` and the `<textarea>`] | React **saves the state** and **keeps the DOM** | The user comes back to **`Hello John`**
- !Stopped [`useEffect` and its cleanup] | React **runs the cleanup** on hiding | The chat server is **disconnected** until the tab is visible again
```

The docs call this a feature: "subscriptions won't be active for hidden parts of the UI, reducing the amount of work needed for hidden content." Only the Effects wait. The hidden tab still re-renders when its props change, at a lower priority, as Principle 3 showed.

### Two mistakes with Effects in a hidden tab

1. **Expecting the hidden tab to keep working.** A developer wants a notice when John sends a new message while the user is on Contacts. The connection lives in `ChatTab`, so they listen for new messages inside its Effect. With `<Activity>`, the tab is kept, so the developer expects this to work. It does not: the hidden Chat tab is disconnected, and no notice appears. Work that must go on while the tab is hidden belongs in a component that stays visible, such as `App`.
2. **Leaving the cleanup out.** Without a cleanup, React has nothing to run when the boundary becomes hidden, so the hidden tab stays connected. When the user comes back, React runs the Effect again and opens a second connection, while the first one is still open.

Here is the Console of the second mistake, after the user leaves the Chat tab and comes back:

```page caption="The page after the user leaves the Chat tab and comes back, when the Effect has no cleanup."
line: [Chat] [Contacts]
form:
  textarea: Message | Hello John
log: ✅ Connecting... | chat.js:4
log: ✅ Connecting... | chat.js:4
```

Two connections, and not one disconnect. The docs give the rule: "If you're relying on an Effect mounting to clean up a component's side effects, refactor the Effect to do the work in the returned cleanup function instead." StrictMode helps you find an Effect without a proper cleanup: in development, it "will eagerly perform Activity unmounts and mounts to catch any unexpected side-effects" (Lesson 47).

## PRINCIPLE | `<audio>` in a hidden tab: the element stays in the DOM, so a cleanup must pause it

> [!PRINCIPLE]
> **Principle 5: Hidden Media: Stop DOM Side Effects in a Cleanup**
>
> *A hidden Activity keeps its DOM, so a playing `<audio>`, `<video>`, or `<iframe>` keeps going; stop it in an Effect cleanup, such as `audio.pause()`.*
>
> `display: none` changes how an element looks, not what it does. With `&&`, removing the `<audio>` stopped the sound for free. With a hidden Activity, the `<audio>` stays in the DOM, so a cleanup in `useLayoutEffect` must pause it at the moment the tab is hidden.
>
> **DO THIS:**
> ```jsx
> useLayoutEffect(() => {
>   const audio = audioRef.current;
>   ~return () => audio.pause();~ // The sound stops when the user leaves the tab
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<audio ref={audioRef} src="/john-voice.mp3" />~ {/* **WRONG:** no cleanup, so John keeps talking on the Contacts tab */}
> ```

### A voice message under `display: none`

The Chat tab now gets one voice message from John, with a Play button:

```page caption="The Chat tab with John's voice message and the message field."
line: [Chat] [Contacts]
line: John sent a voice message [Play]
form:
  textarea: Message |
```

```jsx title="src/ChatTab.jsx"
const ~audioRef~ = useRef(null); // Holds the <audio> element after the first render

<p>
  John sent a voice message
  <button onClick={() => audioRef.current.play()}>Play</button>
</p>
~<audio ref={audioRef} src="/john-voice.mp3" />~ {/* Plays John's voice message, and shows nothing on the page */}
```

`audioRef` is a ref on the `<audio>` element (Lesson 31). React puts the real element into `audioRef.current`. It is the same element you would get with `document.getElementById` in plain JavaScript. `play()` is a method the browser provides on every `<audio>` and `<video>` element.

**The user plays the voice message and clicks Contacts, and John's voice keeps playing.** The Chat tab is gone from the screen, and the user still hears it. Here is why:
1. The user clicks Play. The browser starts playing the `<audio>` element.
2. The user clicks Contacts. The Chat boundary becomes hidden, and React puts `display: none` on the `<section>` around the `<audio>`.
3. The `<audio>` element is still in the DOM. `display: none` changes how an element looks. It does not stop its sound.
4. The user hears John while looking at the contact list.

The docs name this case: "since a hidden component's DOM is not destroyed, any side effects from that DOM will persist, even after the component is hidden." They also list the most common tags with such a side effect: "`<video>`, `<audio>`, `<iframe>`."

With `&&`, you never had to think about it. React removed the `<audio>` from the DOM, and the browser stopped playing it. With `<Activity>`, nothing removes it.

### Pausing the audio in the cleanup

The docs' fix: "If a component renders DOM that has a side effect, and you want to prevent that side effect when an Activity boundary hides it, add an Effect with a return function to clean it up." The browser provides `pause()` on every `<audio>` and `<video>`. We call it in the cleanup:

```jsx title="src/ChatTab.jsx"
useLayoutEffect(() => {
  const audio = audioRef.current;
  ~return () => audio.pause();~ // Stops John's voice when the boundary becomes hidden
}, []);
```

The Effect copies `audioRef.current` into `audio` when it runs, so the cleanup pauses the same element the Effect saw. The docs do the same with their video.

Now the sound stops the moment the user leaves the tab. When the user comes back, the same `<audio>` element is there, stopped where it was paused. The docs say the same of a video: "the timecode is preserved, and the video itself doesn't need to be initialized or downloaded again."

### VS | `useLayoutEffect` vs. `useEffect` for the pause: only one pauses at the moment the tab is hidden

The docs' example uses `useLayoutEffect` (Lesson 49), not `useEffect`:

```jsx title="Pausing in a useLayoutEffect cleanup vs. in a useEffect cleanup"
~useLayoutEffect~(() => { const audio = audioRef.current; return () => audio.pause(); }, []); // Pauses at the moment the tab is hidden
~useEffect~(() => { const audio = audioRef.current; return () => audio.pause(); }, []); // Also pauses, but React may run this cleanup later
```

In a simple page, both pause the audio. **It looks the same, but it is NOT the same thing!** The docs: "We call `useLayoutEffect` instead of `useEffect` because conceptually the clean-up code is tied to the component's UI being visually hidden."

Why does that matter? React can delay the cleanup of a regular Effect. The docs name two cases: a Suspense boundary around the tab that suspends again, and a View Transition, the subject of the next lesson. In those cases, the user would keep hearing John for a moment after the tab is hidden.

The pause belongs to the moment the tab disappears, and `useLayoutEffect` keeps it there.

```tree dir=right caption="What happens to John's voice message when the user leaves the Chat tab."
The user plays John's voice message and clicks Contacts
- !Hidden Activity, no cleanup [`<audio>` with `display: none`] | The `<audio>` is **still in the DOM** | The user **still hears John** on the Contacts tab
- +Hidden Activity, pause in the cleanup [`useLayoutEffect` with `audio.pause`] | React runs the cleanup **as the tab is hidden** | The sound **stops**, and resumes **where it stopped**
```

Don't worry, this is rare. The docs: "Typically, though, most of your React components should already be robust to being hidden by an Activity boundary." Only elements that play sound, play video, or show another page inside the tab need this care.

## PRINCIPLE | `use` in a hidden tab: React renders the tab before the click, so its data is ready

> [!PRINCIPLE]
> **Principle 6: Pre-rendering: A Hidden Boundary Renders Its Children in the Background**
>
> *A boundary hidden on the first render still renders its children at a lower priority, so data read with `use` loads before the user opens the tab; data fetched in an Effect does not.*
>
> `&&` renders nothing until the user opens the tab, so the request starts on the click and the user waits. A hidden Activity renders the tab in the background when the page loads, without running its Effects. A list read with `use` is ready by the time the user clicks.
>
> **DO THIS:**
> ```jsx
> const contacts = ~use(fetchData('/contacts'))~; // Starts loading while the tab is still hidden
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~fetchData('/contacts').then(setContacts);~ // **WRONG:** hidden Effects do not run, so loading starts on the click
> }, []);
> ```

### A hidden boundary still renders

So far, every hidden tab was a tab the user had already opened. Now look at a tab that starts hidden, such as Contacts when the page loads:

```jsx title="A boundary that is hidden on the first render"
<Activity ~mode="hidden"~> {/* Not on the screen, but React still renders ContactsTab in the background */}
  <ContactsTab />
</Activity>
```

**Hidden does not mean "not rendered yet". React still calls the components of a hidden boundary, in the background, at a lower priority.** The docs: "its children won't be visible on the page, but they will still be rendered."

> [!DEFINITION]
> **Pre-rendering.** [NEW] Pre-rendering means rendering a part of the page before the user asks for it. A boundary that is hidden when the page loads pre-renders its children: React calls them in the background, at a lower priority, and runs none of their Effects. The docs describe Activity as a way to render this kind of "background activity" (Lesson 73).

### The Contacts tab reads its list with `use`

In a real chat app, the contact list comes from the server. `ContactsTab` now reads it with `use` (Lesson 71):

```jsx title="src/ContactsTab.jsx"
import { use } from 'react';
import { fetchData } from './data.js';

export default function ContactsTab() {
  const contacts = ~use(fetchData('/contacts'))~; // Waits for the list; Suspense shows the fallback meanwhile
  return (
    <ul>
      {contacts.map(name => <li key={name}>{name}</li>)}
    </ul>
  );
}
```

`fetchData` is a small helper adapted from React's docs. It keeps one Promise for each address, so every render reads the same request. The Promise resolves after one second, as a slow server would:

```js title="src/data.js"
const cache = new Map();

export function fetchData(url) {
  if (!cache.has(url)) {
    cache.set(url, getContacts());
  }
  return cache.get(url);
}

async function getContacts() {
  await new Promise(resolve => setTimeout(resolve, 1000));
  return ['John', 'Mia'];
}
```

The docs add that "the way you would do data fetching depends on the framework that you use together with Suspense." In `App`, a `<Suspense>` boundary shows `Loading contacts...` while the list is on its way (Lesson 69).

### VS | `&&` vs. a hidden Activity on the first click: one starts loading on the click, the other is already done

The page loads on the Chat tab. The user types for a few seconds, then clicks Contacts for the first time:

::: row caption="What the user sees right after the first click on Contacts, with && and with a hidden Activity."
::: col title="With &&" tag="waits after the click" tone=bad
```page size=mini
line: [Chat] [Contacts]
line: Loading contacts... | bad
```
```jsx title="src/App.jsx" bad="1"
{tab === 'contacts' && (
  <Suspense fallback={<p>Loading contacts...</p>}>
    <ContactsTab />
  </Suspense>
)}
```
`ContactsTab` first renders on the click, so the request starts on the click.
:::
::: col title="With a hidden Activity" tag="ready before the click" tone=good
```page size=mini
line: [Chat] [Contacts]
line: John | good
line: Mia | good
```
```jsx title="src/App.jsx" good="1"
<Activity mode={tab === 'contacts' ? 'visible' : 'hidden'}>
  <Suspense fallback={<p>Loading contacts...</p>}>
    <ContactsTab />
  </Suspense>
</Activity>
```
`ContactsTab` rendered when the page loaded, so the list was already there.
:::
:::

Before the click, both Contacts tabs are off the screen, so you might expect both to start loading on the click. Here is what happens with the hidden Activity instead, in order:
1. The page loads on the Chat tab. The Contacts boundary is hidden.
2. React still renders `ContactsTab` in the background, and `fetchData('/contacts')` starts the request.
3. The list arrives one second later, while the user types in the Chat tab.
4. The user clicks Contacts and sees John and Mia at once, with no loading line.

With `&&`, `App` does not render `ContactsTab` at all until the user opens the tab, so nothing can load early. With the hidden boundary, the docs say the tab "was able to prepare itself for a faster render, thanks to the hidden Activity boundary."

### Fetching in an Effect is not pre-rendered

A developer wraps a tab that fetches its list in `useEffect` in a hidden Activity, to make it faster. The first click still shows the loading line. Why? A hidden boundary renders its children, but it does not run their Effects, as Principle 4 showed. So the fetch inside `useEffect` waits for the click. The docs name this limit: "Only data read from a source that activates a Suspense boundary, such as a Promise read with `use`, is fetched during pre-rendering. Activity does not detect data fetched inside an Effect."

```tree dir=right caption="Which Contacts tabs load their list before the first click."
The first click on Contacts
- !With `&&` [`tab === 'contacts' && <ContactsTab />`] | `ContactsTab` **first renders on the click** | The user sees **`Loading contacts...`** for one second
- !Hidden Activity, fetch in `useEffect` | React renders the tab but **runs no Effects** | The request **starts on the click**, and the user waits
- +Hidden Activity, list read with `use` | React **renders the tab when the page loads** | The list is **ready** when the user clicks
```

## All 6 Principles Together

### The complete files

Here is the finished `App`. Each tab sits in its own Activity boundary, and the Contacts tab has its own `<Suspense>`:

```jsx title="src/App.jsx"
import { Activity, Suspense, useState } from 'react';
import ChatTab from './ChatTab.jsx';
import ContactsTab from './ContactsTab.jsx';

export default function App() {
  const [tab, setTab] = useState('chat');

  return (
    <main>
      <button onClick={() => setTab('chat')}>Chat</button>
      <button onClick={() => setTab('contacts')}>Contacts</button>
      <Activity ~mode={tab === 'chat' ? 'visible' : 'hidden'}~> {/* Principle 2: the draft survives every switch */}
        <ChatTab />
      </Activity>
      <Activity ~mode={tab === 'contacts' ? 'visible' : 'hidden'}~> {/* Principle 6: hidden on load, so the list loads early */}
        <Suspense fallback={<p>Loading contacts...</p>}>
          <ContactsTab />
        </Suspense>
      </Activity>
    </main>
  );
}
```

The finished `ChatTab` has two Effects, one for the chat server and one for the voice message:

```jsx title="src/ChatTab.jsx"
import { useState, useEffect, useLayoutEffect, useRef } from 'react';
import { createConnection } from './chat.js';

export default function ChatTab() {
  const [draft, setDraft] = useState('');
  const audioRef = useRef(null);

  useEffect(() => {
    const connection = createConnection();
    connection.connect();
    ~return () => connection.disconnect();~ // Principle 4: disconnects when the tab is hidden
  }, []);

  useLayoutEffect(() => {
    const audio = audioRef.current;
    ~return () => audio.pause();~ // Principle 5: stops John's voice when the tab is hidden
  }, []);

  return (
    <section>
      <p>
        John sent a voice message
        <button onClick={() => audioRef.current.play()}>Play</button>
      </p>
      <audio ref={audioRef} src="/john-voice.mp3" />
      <label>
        Message
        <textarea value={draft} onChange={e => setDraft(e.target.value)} />
      </label>
    </section>
  );
}
```

`ContactsTab.jsx` and `data.js` stay as Principle 6 showed them, and `chat.js` stays as the example page showed it.

1. React calls `App` | Holds `tab`, which starts as `'chat'`
- +Visible Activity [`mode="visible"`] | Shows its child **on the screen**
  - +2. `ChatTab` at normal priority | Its Effects run: it **connects** to the chat server
- +Hidden Activity [`mode="hidden"`] | Hides its child with **`display: none`**

| Aspect | Removing the tab with `&&` | Hiding the tab with `<Activity>` |
| :--- | :--- | :--- |
| **State** | Thrown away; the tab comes back with its initial state | Saved; the tab comes back as the user left it |
| **DOM** | Removed | Kept, with `display: none` written by React |
| **Effects** | Cleaned up when the tab is removed | Cleaned up when the tab is hidden, run again when it is visible |
| **Media such as `<audio>`** | Stops, because the element leaves the DOM | Keeps playing unless a cleanup pauses it |
| **Updates while away** | None; the tab does not exist | Rendered at a lower priority |
| **A tab hidden on page load** | Not rendered until the first click | Pre-rendered, so data read with `use` loads early |

Remember the one sentence of this lesson. **`&&` removes a tab and throws its state away. `<Activity mode="hidden">` hides the tab, keeps its state and its DOM, and stops its Effects until the user comes back.**

## For the Interview

> **The Interview Question:** How do you hide a subtree without losing its state with <Activity>?

### How to Answer Clearly in 30 Seconds

"When a tab is shown with `&&`, leaving it unmounts it, so React throws away its state and its DOM. To keep them, I wrap the tab in `<Activity>`, imported from `react`, and switch `mode` between `'visible'` and `'hidden'` instead of removing the tab. `mode="hidden"` means four things:
1. **State is kept.** React saves the children's state and restores it when `mode` is `'visible'` again.
2. **The DOM is kept.** React hides the children with `display: none`, so even the text in an uncontrolled `<textarea>` survives.
3. **Effects are cleaned up.** For their Effects, the children are unmounted; the Effects run again when they become visible.
4. **Updates get a lower priority.** Hidden children still re-render in the background, so a boundary hidden on the first render can pre-render and load data read with `use` before the user opens it.

So I make sure every Effect does its stopping work in its cleanup, and I pause media such as `<audio>` or `<video>` in a `useLayoutEffect` cleanup."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Isn't `<Activity mode="hidden">` just `display: none`?"**
   **No.** `display: none` is only how Activity hides the DOM. If you write `display: none` yourself, React does not know the tab is hidden: its Effects keep running, such as a chat server connection, and its updates keep full priority. A hidden Activity tells React that the tab is hidden, so React cleans up its Effects and renders its updates at a lower priority. The React team first called this component Offscreen, and renamed it because "it's possible for parts of the app to be visible and inactive, such as content behind a modal." It shipped in React 19.2.
2. **"What happens to Effects, timers, and media inside a hidden Activity?"**
   React runs the cleanup of every Effect when the boundary becomes hidden, and runs the Effects again when it becomes visible. A timer stops only if it is set in an Effect and cleared in that Effect's cleanup. Media is different: the DOM is not destroyed, so a playing `<video>`, `<audio>`, or `<iframe>` keeps going. The docs' fix is an Effect whose cleanup pauses it, written with `useLayoutEffect` because the cleanup belongs to the moment the UI is hidden. In development, StrictMode eagerly performs Activity unmounts and mounts to find Effects without a proper cleanup.
3. **"When would you not use Activity to keep a tab's state?"**
   When the tab should start fresh, as a chat with a different person should, I let it unmount, or give it a `key`. When the state must be shared with other parts of the page, I lift it up into the parent, which the docs call the most common solution. When it must survive closing the page, I save it in `localStorage`. And if a hidden tab fetches its data in `useEffect`, Activity will not load it early: only data read through Suspense, such as a Promise read with `use`, is fetched during pre-rendering.

```tree dir=right caption="Interview comparison: removing a tab, hiding it with your own CSS, and hiding it with Activity."
Three ways to take a tab off the screen
- !Remove it with `&&` | State and DOM are **thrown away** | The user comes back to an **empty tab**
- !Hide it with your own `display: none` | State and DOM are kept | Effects **keep running** at **full priority**
- +Hide it with `<Activity mode="hidden">` | State and DOM are kept | Effects are **cleaned up**; updates at a **lower priority**; data read with `use` **loads early**
```
