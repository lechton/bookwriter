# Lecture 71: How use Reads a Promise, Even Inside an if

*(How can a component show comments that have not arrived yet?)*

> INTERVIEW QUESTION | ❱❱ MORE | What is the use() API, and how does it read promises and context conditionally?

---

## VS | An Effect with `isLoading` vs. `use(commentsPromise)`: the component shows its own loading line, or `<Suspense>` shows it

> A server takes time to answer, so `fetch` gives back a Promise at once, and the data arrives later. **`use` reads a Promise during render, and React shows the closest `<Suspense>` fallback until the value arrives.** So the component needs no loading variable of its own, and because `use` is not a Hook, it may even sit inside an `if`.

Data from a server never arrives on the same line that asks for it. You ask now, and the answer comes one second later. So every page that shows server data has the same three moments: while the data is on its way, when it has arrived, and when the request failed.

Until now, the component handled all three moments itself. We wrote an Effect and three state variables: the comments, `isLoading`, and `error` (Lesson 33). React 19 gives a shorter way. The component reads the data in one line:

```jsx title="src/Comments.jsx"
const comments = ~use~(commentsPromise); // Gives the comments once they have arrived
```

There is no `isLoading` and no `error` in this line. The component reads the comments as if they were already there. Two components above it handle the waiting and the failure.

### The Idea Behind It: `await` in Plain JavaScript

Remember `await`? In plain JavaScript, you wait for a Promise yourself. The function pauses on the line with `await`, and when the data arrives, it goes on with the next line:

```js title="Plain JavaScript: you wait for the Promise yourself"
async function showComments() {
  const comments = ~await~ fetchComments(); // The function pauses here until the comments arrive
  console.log(comments); // Runs one second later, with the comments
}
```

In React, you cannot pause a component like this. React calls your component, and the component must return its JSX right away. React does not support an `async` component in the browser.

`use` is how you ask React: "I need the value of this Promise. If it is not there yet, stop me, show the loading line, and call me again when it arrives."

```jsx title="React: you hand the wait to React"
const comments = ~use~(commentsPromise); // Not there yet: React stops Comments here and calls it again later
```

So `use` does not pause on its line the way `await` does. The React documentation draws the line between the two: "`async` and `await` pick up rendering from the point where `await` was invoked, whereas `use` re-renders the component after the data is resolved."

Keep one sentence in mind for the whole lesson. **`use` reads a value that is not ready yet. While it is not ready, React shows the closest `<Suspense>` fallback. When it is ready, React renders the component again, and this time `use` returns the value.**

### The Words This Lesson Stands On

> [!DEFINITION]
> **A Promise.** [REVIEW] A Promise is a JavaScript object that stands for a value that arrives later, such as comments the server is still sending. `fetch` gives back one at once, and the data comes later (Lesson 33).

> [!DEFINITION]
> **A `<Suspense>` fallback.** [REVIEW] A component suspends when it is not ready to render yet. React then goes up to the closest `<Suspense>` above it and shows its `fallback`, such as `<p>Loading comments...</p>`, until the component is ready. Everything outside that `<Suspense>` stays on the screen (Lesson 69).

> [!DEFINITION]
> **The Rules of Hooks.** [REVIEW] A Hook, such as `useState` or `useContext`, must be called at the top level of the component: never inside an `if`, never inside a loop, and never after an early `return`. React finds the saved value of each Hook by the order of the calls, so every render must call the same Hooks in the same order (Lesson 38).

### `use` Looks Like a Hook, but It Is NOT One

Its name starts with use, like `useState` and `useContext`. So a developer reads it as a Hook, and applies the Rules of Hooks to it.

The React documentation says the opposite: "Despite its name, `use` is not a Hook. Unlike Hooks, it can be called inside loops and conditional statements like `if`."

It may look the same as a Hook, but it is NOT the same thing! On our page, this matters before the click. There is no Promise yet, so the comments section returns nothing and never calls `use`. A Hook may not be skipped like this. Principle 4 shows why `use` may.

### Who Shows the Loading Line and the Error Line

Three components share the comments section, and each one shows one of its three moments:
1. **While the comments are on their way**, the component with `use` suspends. The closest `<Suspense>` shows its fallback, `Loading comments...`.
2. **When the comments have arrived**, React renders the component again, and `use` returns them. The component shows the list.
3. **When the request fails**, the closest Error Boundary shows its own fallback, `Could not load comments.` Principle 5 adds one to our page.

```tree caption="Three components share the comments section, and each one shows one of its three moments."
Who shows what in the comments section
- +`<Suspense>` above `Comments` [`fallback`] | While the comments are **on their way** | Shows **`Loading comments...`**
- +`Comments` with `use` [`use`] | When the comments **have arrived** | Shows **the two comments**
- +Error Boundary above `<Suspense>` [`ErrorBoundary`] | When the request **fails** | Shows **`Could not load comments.`**
```

### What Is at Stake

Two mistakes cost the reader the comments, or the whole article:
1. **The component creates the Promise itself, on every render.** `Loading comments...` stays on the page, and the comments never appear. The React documentation says this "prevents content from appearing".
2. **The request fails, and no Error Boundary sits above the comments.** The React documentation says: "By default, if your application throws an error during rendering, React will remove its UI from the screen." The reader loses the title and the whole article, not only the comments.

Developers usually go wrong in one of three ways:
1. **They call `fetchComments()` right inside `use`, in the component body.** It saves a click handler and a state variable. It is the first mistake above: the comments never appear.
2. **They wrap `use` in `try` and `catch` to show an error line.** That is how they handle errors everywhere else in JavaScript. React does not allow it.
3. **They keep their old loading check inside the component, below `use`.** That check never runs, because `use` returns only once the comments are there.

### The Rule of Thumb: was the Promise created before this render?

**Ask one question about every Promise you pass to `use`: was it created before this render, such as in a click handler? If yes, pass it to `use`. If it is created in the component body, React gets a new Promise on every render, and the loading line never goes away.**

### Four Ways to Show Data That Arrives Later

At work, developers pick one of four ways:
1. **An Effect with loading and error state** (Lesson 33). It fits a page that already works this way. The React documentation warns that it "requires managing loading and error states manually".
2. **A Promise read with `use`, under a `<Suspense>` and an Error Boundary.** This is the way of this lesson. It fits when our code creates the Promise before render, such as in a click handler, and keeps it in state.
3. **A Suspense-enabled framework or library.** It creates the Promises, keeps them, and reads them for us. The React documentation prefers it in real apps: "in practice prefer your framework's data fetching solution". Its lint pages name TanStack Query, useSWR, and React Router.
4. **`await` in a Server Component.** This code runs on the server, not in the browser. Part Two of this book covers it.

```tree caption="Four ways to show data that arrives after the page renders, and when each one fits."
Four ways to show data that arrives later
- +An Effect with loading and error state [`useEffect`] | The component **keeps the wait in its own state** | Fits a page that **already works this way**
- +`use` under `<Suspense>` [`use` `Suspense`] | Our code **creates the Promise before render** | Fits data needed **only after a click**, as on our page
- +A Suspense-enabled library [TanStack Query, useSWR] | The library **keeps the Promises** for us | The documentation's choice **for real apps**
- +`await` in a Server Component | Runs **on the server** | Covered in **Part Two**
```

**PRINCIPLES:** `use` reads a value that is not ready yet. React shows the closest fallback until the value is there. Five principles follow:
1. **Principle 1: The Click Creates the Promise and Keeps It in State.** The click handler starts the request and stores the Promise. The click does not wait for the comments.
2. **Principle 2: `use` Stops the Component Until the Comments Arrive.** While the Promise is pending, `<Suspense>` shows `Loading comments...`. When the comments arrive, React renders `Comments` again, and `use` returns them.
3. **Principle 3: A Promise Created in the Component Body Keeps the Loading Line Forever.** It is a new Promise on every render, so `use` keeps waiting.
4. **Principle 4: `use` May Sit Inside an `if`.** It is not a Hook, so it may sit inside an `if` or after an early return, both for a Promise and for a context.
5. **Principle 5: A Failed Request Goes to the Closest Error Boundary.** It shows its fallback in place of the list. `try` and `catch` around `use` are not allowed.

## PRINCIPLE | `setCommentsPromise(fetchComments())` in the click handler: one Promise per click, kept in state

> [!PRINCIPLE]
> **Principle 1: Promise in State: The Click Starts the Request and Keeps One Promise**
>
> *Create the Promise in the event handler that needs the data, and store it in state, so every render of the page reads the same Promise.*
>
> A reader who never clicks `Show comments` never sends a request. The click calls `fetchComments()`, which returns a pending Promise at once, and the setter keeps that one Promise in state. The click does not wait for the comments. Reading them is the job of the render that follows.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => ~setCommentsPromise(fetchComments())~}> {/* One Promise per click, kept in state */}
>   Show comments
> </button>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> async function handleClick() {
>   const comments = ~await~ fetchComments(); // **WRONG:** for one second the page does not react, because nothing in state says the comments are coming
>   setComments(comments);
> }
> ```

Start with the smallest code:

```js title="Calling fetchComments"
const promise = ~fetchComments()~; // Comes back at once: the comments are not there yet
```

`fetchComments()` does not give back the comments. It gives back a Promise right away, and the comments arrive one second later.

The word comes from everyday life. A promise is given now and kept later. A JavaScript Promise works the same way: your code gets the object now, and the value later.

> [!DEFINITION]
> **The three states of a Promise.** [NEW] A Promise is always in one of three states, and MDN names them. It is pending while the value has not arrived yet. It is fulfilled once the value has arrived, and then it holds that value. It is rejected when the work failed, and then it holds an error instead of a value (Lesson 71).

```tree dir=right caption="The three states of a Promise, and what our comments Promise holds in each one."
The three states of the comments Promise
- +pending | The comments are **on their way** | For **one second** after the click
- +fulfilled | The comments **have arrived** | Holds **the comments of John and Mia**
- !rejected | The request **failed** | Holds **an error** instead of the comments
```

### A stand-in for the server

Our page has no real server, so the request file stands in for one. It waits one second, then hands over two comments:

```js title="src/fetchComments.js"
const comments = [
  { id: 1, author: 'John', text: 'Great news!' },
  { id: 2, author: 'Mia', text: 'See you there.' },
];

export function fetchComments() {
  return new Promise(~resolve~ => { // JavaScript hands resolve to this function
    ~setTimeout~(resolve, 1000, comments); // After one second, calls resolve with the comments
  });
}
```

Your code never defines `resolve`. JavaScript provides it. When you write `new Promise`, JavaScript calls the function you pass to it, and hands it `resolve`. Calling `resolve` with a value makes the Promise fulfilled with that value.

The comments reach `resolve` through `setTimeout`. Every argument written after the delay, here `comments`, is passed on to the function that `setTimeout` calls. So after 1000 milliseconds, `setTimeout` calls `resolve` with the comments, and the Promise is fulfilled.

### The click starts the request, and the render reads it

Starting the request and reading its value happen at two separate moments:
1. **When the reader clicks `Show comments`**, the handler calls `fetchComments()` and stores the Promise in state. The click is over at once.
2. **During the render that follows**, a component reads the Promise with `use`. That is Principle 2.

Here is the page file. A state variable, `commentsPromise`, starts as `null`, and the click puts the Promise in it:

```jsx title="src/App.jsx"
import { useState } from 'react';
import { fetchComments } from './fetchComments.js';

export default function App() {
  const [~commentsPromise~, setCommentsPromise] = useState(null); // null until the click, then the Promise
  return (
    <article>
      <h1>City park opens on Saturday</h1>
      {commentsPromise === null && (
        <button onClick={() => ~setCommentsPromise(fetchComments())~}> {/* Starts the request and keeps its Promise */}
          Show comments
        </button>
      )}
    </article>
  );
}
```

The button shows only while `commentsPromise` is `null`. After the click, it has done its job, so it disappears. Nothing else appears yet, because no component reads the Promise so far:

```page caption="The page right after the click in Principle 1: the button is gone, and no component reads the Promise yet."
heading: City park opens on Saturday
```

### Why the click does not wait with `await`

The click could also wait for the comments with `await`, and store the comments instead of the Promise. Then, for a whole second, the page would not react to the click. Nothing in state says the comments are on their way.

To show a loading line, we would need an `isLoading` variable again. That is the very thing `use` lets us drop. With the Promise in state, React knows at once that something is coming, and Principle 2 turns that into `Loading comments...`.

### Why the Promise lives in state

State keeps the same instance of the Promise across renders. Same instance means the exact same Promise object, not a new Promise that will hold the same comments. Every render of `App` reads `commentsPromise` from state and gets that one object. `use` needs exactly this, as Principle 3 shows.

The React documentation names the event handler as the right place: "Ideally, Promises are created before rendering, such as in an event handler, a route loader, or a Server Component, and passed to the component that calls `use`."

Remember: the click creates the Promise. The render reads it.

## PRINCIPLE | `use(commentsPromise)`: the component stops until the comments arrive, then React renders it again

> [!PRINCIPLE]
> **Principle 2: Suspend: use Stops the Component Until the Promise Is Fulfilled**
>
> *Read the Promise with `use` during render, and put a `<Suspense>` with a `fallback` above the component; while the Promise is pending, React shows the fallback.*
>
> The component that reads the comments has no loading variable. While the Promise is pending, the component suspends, and the closest `<Suspense>` shows `Loading comments...`. When the Promise is fulfilled, React renders the component again from its first line, and `use` returns the comments. The loading line on the page belongs to `<Suspense>`, so a loading check below `use` never runs.
>
> **DO THIS:**
> ```jsx
> <~Suspense fallback={<p>Loading comments...</p>}~> {/* Shown while Comments waits at use */}
>   <Comments commentsPromise={commentsPromise} />
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const comments = use(commentsPromise);
> if (~!comments~) { // **WRONG:** never runs, because use returns only once the comments are there
>   return <p>Fetching the latest comments...</p>;
> }
> ```

### VS | With `useEffect` vs. with `use`: the same page, NOT the same thing

Both versions show the reader the same thing: `Loading comments...` for one second, then the two comments. The one difference is who shows the loading line.

First, the comments section with `useEffect`, the way we wrote it before (Lesson 33). That lesson also adds an `error` variable and a cleanup function. They are left out here to keep the code short:

```jsx title="With useEffect: the component keeps the wait in its own state"
function Comments() {
  const [comments, setComments] = useState([]);
  const [~isLoading~, setIsLoading] = useState(true); // The component tracks the wait itself
  useEffect(() => {
    fetchComments().then(data => {
      setComments(data);
      setIsLoading(false);
    });
  }, []);
  if (isLoading) {
    return ~<p>Loading comments...</p>~; // The component returns its own loading line
  }
  return <ul>{comments.map(comment => <li key={comment.id}>{comment.text}</li>)}</ul>;
}
```

Now the comments section with `use`. It receives the Promise from `App` as a prop:

```jsx title="With use: the component reads the comments in one line"
function Comments({ commentsPromise }) {
  const comments = ~use~(commentsPromise); // Returns the comments once the Promise is fulfilled
  return <ul>{comments.map(comment => <li key={comment.id}>{comment.text}</li>)}</ul>;
}
```

With `use`, the loading line moves out of the component, into the `<Suspense>` above it in the page file:

```jsx title="src/App.jsx: the Suspense boundary around Comments"
<~Suspense fallback={<p>Loading comments...</p>}~> {/* Shows the loading line while Comments waits */}
  <Comments commentsPromise={commentsPromise} />
</Suspense>
```

It may look the same on the page, but it is NOT the same thing!
1. **With `useEffect`**, the component keeps the wait in its own state. While `isLoading` is `true`, it returns the loading line itself.
2. **With `use`**, the component has no loading variable. It stops at `use`, and the `<Suspense>` above it shows the loading line.

`<Suspense>` notices only the second version. The React documentation says: "Suspense does not detect when data is fetched inside an Effect or event handler." Only a component that reads the Promise with `use` makes the closest `<Suspense>` show its fallback.

```tree caption="The same loading line on the page, shown by the component itself with useEffect, or by Suspense with use."
Who shows `Loading comments...`?
- +With `useEffect` [`isLoading`] | The component **keeps the wait in its own state** | The component **returns the loading line itself**
- +With `use` [`use` `Suspense`] | The component **has no loading variable** | The **`<Suspense>` above it** shows the loading line
```

### Adding `Comments` and the Suspense boundary to the page

`use` is a function that React provides, and we import it by name from `'react'`. Here is the comments section in its own file:

```jsx title="src/Comments.jsx"
import { ~use~ } from 'react'; // use comes from React

export default function Comments({ commentsPromise }) {
  const comments = ~use~(commentsPromise); // Returns the two comments once the Promise is fulfilled
  return (
    <ul>
      {comments.map(comment => (
        <li key={comment.id}>{comment.author}: {comment.text}</li>
      ))}
    </ul>
  );
}
```

The page file gains two imports at the top and a `<Suspense>` under the title. In this step, the page renders `Comments` only after the click, once state holds a Promise:

```jsx title="src/App.jsx"
import { useState, ~Suspense~ } from 'react'; // Suspense comes from React
import { fetchComments } from './fetchComments.js';
import Comments from './Comments.jsx';

export default function App() {
  const [commentsPromise, setCommentsPromise] = useState(null);
  return (
    <article>
      <h1>City park opens on Saturday</h1>
      {commentsPromise === null && (
        <button onClick={() => setCommentsPromise(fetchComments())}>
          Show comments
        </button>
      )}
      {commentsPromise !== null && (
        <~Suspense fallback={<p>Loading comments...</p>}~> {/* Shows the loading line while Comments waits */}
          <Comments commentsPromise={commentsPromise} />
        </Suspense>
      )}
    </article>
  );
}
```

### What happens after the click

**Beware! `use` does not wait inside its line the way `await` does. The component stops at `use`, and later React runs it again from its first line.** Here is the click in order:
1. The reader clicks `Show comments`. The handler stores a new Promise in `commentsPromise`.
2. React renders `App` again. The Promise is there now, so the page renders the `<Suspense>` with `Comments` inside it.
3. React renders `Comments`. It reaches `use`, and the Promise is still pending.
4. `Comments` suspends. React stops rendering it and shows the fallback of the closest `<Suspense>`:

```page caption="The page while the Promise is pending: the Suspense boundary shows its fallback."
heading: City park opens on Saturday
line: Loading comments...
```

5. One second later, the Promise is fulfilled with the two comments.
6. React renders `Comments` again, from its first line. The React documentation says: "After each suspension, React retries rendering from scratch".
7. This time `use` returns the array of comments, and the list takes the place of the loading line:

```page caption="The page after the Promise is fulfilled: use returns the comments, and the list replaces the fallback."
heading: City park opens on Saturday
line: John: Great news!
line: Mia: See you there.
```

So React runs the line with `use` twice. The first time, no line after it runs. The second time, `use` returns the array that the request file passed to `resolve`.

```tree dir=right caption="React renders Comments twice: once to find the Promise pending, once to read the comments."
After the click on Show comments
- +1. First render of `Comments` | `use` finds the Promise **pending** | `Comments` **suspends**; the page shows **`Loading comments...`**
- +2. One second later | The Promise is **fulfilled** | React **renders `Comments` again from its first line**
- +3. Second render of `Comments` | `use` **returns the two comments** | The list **replaces the loading line**
```

### Real mistake: a loading check below `use`

Here is how this happens at work:
1. A developer moves the comments section from the Effect version to `use`, and adds the `<Suspense>` in the page file. Out of habit, they also keep a loading check in `Comments`, below `use`.
2. Months later, the team asks for a new loading text, `Fetching the latest comments...`. A teammate opens the comments file, finds the old check, and changes its text there:

```jsx title="src/Comments.jsx"
const comments = use(commentsPromise);
if (~!comments~) { // **WRONG:** never true: use returns only once the comments are there
  return <p>Fetching the latest comments...</p>;
}
```

3. The teammate reloads the page and clicks `Show comments`. The page still says `Loading comments...`.

The check in `Comments` never runs. While the Promise is pending, `Comments` stops at `use` and never reaches the check. When `use` returns, the comments are already there.

The line on the page comes from the `fallback` of the `<Suspense>` in the page file. That is the place to change the loading text. The check below `use` can go.

Remember: the component shows only the data. `<Suspense>` shows the wait.

## PRINCIPLE | `use(fetchComments())` in the component body: a new Promise on every render, so the comments never appear

> [!PRINCIPLE]
> **Principle 3: Same Instance: Never Create the Promise in the Component Body**
>
> *Pass `use` a Promise created before render or taken from a cache; a Promise created in the component body is a new one on every render, and the fallback never goes away.*
>
> React renders a suspended component again from scratch, and that render runs every line of the component again. A call to `fetchComments()` in the body creates a new pending Promise each time, so `use` keeps waiting, the page keeps showing `Loading comments...`, and the Console stays empty. Create the Promise in the click handler and keep it in state, or let a Suspense-enabled library keep it.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => ~setCommentsPromise(fetchComments())~}> {/* Created once, on click, and kept in App state */}
>   Show comments
> </button>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Comments() {
>   const comments = use(~fetchComments()~); // **WRONG:** a new Promise on every render, so the comments never appear
> }
> ```

### VS | `use(fetchComments())` vs. `use(commentsPromise)`: a new Promise every time, or the same one

Both lines below hand `use` a Promise of the same two comments. The one difference is where the Promise is created:

```jsx title="A Promise created during render vs. a Promise created on click"
const comments = use(~fetchComments()~); // 1. Created during render: a new Promise every time Comments renders
const comments = use(~commentsPromise~); // 2. Created on click: the one Promise kept in App state
```

The first line looks like the second one with work saved: no state, no prop, no click handler. It may look the same, but it is NOT the same thing!

Each call to `fetchComments()` returns a brand-new Promise, even though every one of them will hold the same two comments. The React documentation says what that does: "Promises created during render are recreated on every render, which causes React to show the Suspense fallback repeatedly and prevents content from appearing."

### Why the comments never appear

**Beware! With the Promise created in render, every new render of `Comments` starts a new request. So `use` never finds a Promise that has had time to arrive.** Here is what happens when `Comments` creates the Promise inside its own body:
1. React renders `Comments`. The line calls `fetchComments()` and gets a new pending Promise.
2. `use` suspends, and the page shows `Loading comments...`.
3. React keeps nothing from this render. The React documentation says: "React does not preserve any state for renders that got suspended before they were able to mount for the first time."
4. One second later, that first Promise is fulfilled, and React renders `Comments` again from scratch.
5. The new render runs the whole function again. It calls `fetchComments()` again and gets a second new Promise, pending again.
6. `use` suspends on the new Promise. The page keeps showing `Loading comments...`, and the comments never appear.

No line of our code asks for a second request. The call to `fetchComments()` sits in the component body, so it runs every time React runs `Comments`.

The Console stays empty. React prints no warning for this mistake, so nothing on the screen points at the line that causes it:

```page caption="With use and fetchComments in the component body: the loading line stays, the comments never appear, and the Console is empty."
heading: City park opens on Saturday
line: Loading comments... | bad
console: quiet
```

Step 3 also explains why `Comments` cannot keep the Promise in its own `useState`. `Comments` suspends before it first appears on the page, so React keeps none of its state. The Promise has to live above it, in `App`, or in a cache.

```tree caption="A Promise created during render vs. a Promise created on click, and what use does with each one."
Where the Promise passed to `use` is created
- !In the component body [`fetchComments` inside `Comments`] | A **new Promise on every render** | `Loading comments...` **stays**; the comments **never appear**
- +In the click handler [`commentsPromise` in `App` state] | The **same Promise on every render** | `Loading comments...` for one second, **then the comments**
```

### Where the Promise may come from

Two places give `use` the same Promise on every render:
1. **Created before render, and kept in state.** Our click handler does this.
2. **Taken from a cache.** A cache is code that keeps the Promise of each request, and hands back the same Promise when asked again. The React documentation says: "The Promise must be cached so that the same instance is reused across re-renders". Suspense-enabled libraries such as TanStack Query and useSWR keep this cache for us.

### Real mistake: two more ways to create a new Promise in render

A developer who knows the rule can still break it, without a single call to `fetchComments()` in the body. The React documentation names two more forms of the same mistake:

```jsx title="Two more ways to create a new Promise during render"
const comments = use(~loadComments()~); // **WRONG:** loadComments is an async function, so every call returns a new Promise
const comments = use(~cachedPromise.then(list => list.slice(0, 1))~); // **WRONG:** .then returns a new Promise on every render
```

1. **Calling an `async` function during render.** An `async` function always returns a Promise, and a new one on every call. The page shows the same result as before: `Loading comments...` stays, the comments never appear, and the Console stays empty.
2. **Adding `.then` to a cached Promise during render.** The cache hands back the same Promise, but `.then` "returns a new Promise on every render, even if `fetchData` is cached". Here the page behaves differently. Once the cached Promise is fulfilled, the first comment appears, and React prints an error in the Console:

```devconsole width=full caption="The Console when Comments adds .then to a cached Promise during render."
x A component was suspended by an uncached promise. Creating promises inside a Client Component or hook is not yet supported, except via a Suspense-compatible library or framework.
```

The page works, so this error is easy to miss. The fix is the same for both forms: create the Promise once, outside render, and pass that one Promise to `use`.

Remember: the click creates the Promise. The render only reads it.

## PRINCIPLE | `use` inside an `if`: allowed, because `use` is not a Hook

> [!PRINCIPLE]
> **Principle 4: Not a Hook: use May Sit Inside an if or After an Early Return**
>
> *Call `use` inside an `if`, a loop, or after an early return when the component needs it only sometimes; it must still be called inside a component or a Hook.*
>
> A Hook finds its saved value by its place in the order of calls, so skipping it on one render breaks every Hook after it. `use` finds its value on the Promise itself, or in the closest provider above, so a render that skips it loses nothing. Before the click, `Comments` returns `null` and never calls `use`. Do not skip `use` by reading the Promise's own `status`.
>
> **DO THIS:**
> ```jsx
> if (commentsPromise === null) {
>   return null;
> }
> const comments = ~use~(commentsPromise); // After an early return: allowed for use
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> if (commentsPromise === null) {
>   return null;
> }
> const theme = ~useContext~(ThemeContext); // **WRONG:** a Hook after an early return breaks the Rules of Hooks
> ```

### VS | `useContext` inside an `if` vs. `use` inside an `if`: the same theme, only one is allowed

`use` reads a context too, not only a Promise. The React documentation shows the `if` case with a context, the way we passed a theme deep into a page (Lesson 28). A horizontal line reads the theme only when its `show` prop is `true`. First with `useContext`:

```jsx title="useContext inside an if"
function HorizontalRule({ show }) {
  if (show) {
    const theme = ~useContext~(ThemeContext); // **WRONG:** a Hook inside an if breaks the Rules of Hooks
    return <hr className={theme} />;
  }
  return false;
}
```

Now the same component with `use`:

```jsx title="use inside an if"
function HorizontalRule({ show }) {
  if (show) {
    const theme = ~use~(ThemeContext); // Allowed: use may be called inside an if
    return <hr className={theme} />;
  }
  return false;
}
```

Both read the same theme from the same provider. It may look the same, but it is NOT the same thing! The Rules of Hooks forbid the first one, and the React documentation allows the second: "Despite its name, `use` is not a Hook."

### Why `use` may be skipped and a Hook may not

The answer lies in how each one finds its value. The React documentation gives three facts, on three different pages:
1. **A Hook finds its value by its place in the order of calls.** The docs say: "Internally, React holds an array of state pairs for every component." React hands out those saved values in the order the Hooks are called (Lesson 38). The lint docs say: "React relies on the order in which hooks are called to correctly preserve state between renders". If one render skips a Hook, every Hook after it gets the wrong value.
2. **`use` with a Promise finds its value on the Promise itself.** React reads fields such as `status` and `value` on the Promise object. The docs say: "React checks these fields when `use` is called".
3. **`use` with a context finds its value in the tree of components.** The docs say: "React searches the component tree and finds the closest context provider above".

The documentation does not join these facts in one sentence, but together they explain the rule. `use` never asks React for a saved value by its place in the order of calls. So a render that skips `use` moves nothing out of place.

```tree caption="Where a Hook and use each find their value, and why only use may sit inside an if."
Where each one finds its value
- !A Hook [`useState` `useContext`] | By its **place in the order of calls** | Skipping it on one render gives **every later Hook the wrong value**
- +`use` with a Promise [`use`] | On **the Promise itself** | Skipping it **moves nothing out of place**
- +`use` with a context [`use`] | In **the closest provider above** | Skipping it **moves nothing out of place**
```

### Moving the `if` into `Comments`

On our page, `Comments` can now decide for itself what to show before the click. It returns `null` while there is no Promise, and calls `use` only after that early return:

```jsx title="src/Comments.jsx"
import { use } from 'react';

export default function Comments({ commentsPromise }) {
  if (commentsPromise === null) {
    return ~null~; // Before the click: no Promise yet, so nothing on the page
  }
  const comments = ~use~(commentsPromise); // After an early return: allowed for use
  return (
    <ul>
      {comments.map(comment => (
        <li key={comment.id}>{comment.author}: {comment.text}</li>
      ))}
    </ul>
  );
}
```

The page no longer checks the Promise around the `<Suspense>`. It always renders `Comments`, and only the button still depends on the click:

```jsx title="src/App.jsx" startLine="10"
      {commentsPromise === null && (
        <button onClick={() => setCommentsPromise(fetchComments())}>
          Show comments
        </button>
      )}
      <Suspense fallback={<p>Loading comments...</p>}>
        ~<Comments commentsPromise={commentsPromise} />~ {/* Rendered always: Comments decides what to show */}
      </Suspense>
```

The reader sees no change. Before the click, the page shows the title and the button. `Comments` returns `null` and never calls `use`:

```page caption="The page before the click: Comments returns null, and use is not called at all."
heading: City park opens on Saturday
line: [Show comments]
```

After the click, the page shows `Loading comments...` and then the comments, exactly as in Principle 2.

The linter agrees. The lint documentation of the Rules of Hooks shows `use` inside an `if` as valid code:

```jsx title="Valid code in the lint documentation"
if (shouldFetch) {
  const data = ~use~(fetchPromise); // Valid: the linter accepts use inside an if
}
```

`use` still has two limits:
1. **It must be called inside a component or a Hook.** The docs say: "`use` must be called inside a Component or a Hook".
2. **It cannot sit inside `try` and `catch`.** Principle 5 shows why.

### Real mistake: skipping `use` when the Promise is already fulfilled

Here is how this happens at work:
1. A developer learns that `use` may sit in an `if`.
2. They read the Promise's own `status` field, to skip `use` when the comments are already there:

```jsx title="src/Comments.jsx"
let comments;
if (~commentsPromise.status === 'fulfilled'~) { // **WRONG:** skips use based on the Promise itself
  comments = commentsPromise.value;
} else {
  comments = use(commentsPromise);
}
```

3. The page works, so the developer ships it.
4. The React documentation warns that this "can break React Suspense optimizations and Suspense features for React DevTools".

The docs give the rule in one sentence: "You can `use(promise)` conditionally, but don't conditionally `use(promise)` based on the promise itself." Our early return passes this test. It checks whether there is a Promise at all, not what state the Promise is in.

Remember: a Hook is found by its place in the order of calls. `use` is found by its Promise or its provider.

## PRINCIPLE | `<ErrorBoundary>` above `<Suspense>`: a failed request shows an error line, and the title stays

> [!PRINCIPLE]
> **Principle 5: Error Boundary: A Rejected Promise Goes to the Closest Error Boundary**
>
> *Wrap the `<Suspense>` in an Error Boundary to show a fallback when the Promise is rejected, and never wrap `use` in `try` and `catch`.*
>
> When the Promise is rejected, React renders the component again, and `use` throws the error. The closest Error Boundary above catches it and shows its fallback in place of the comments, while the title stays. Without an Error Boundary, React removes the whole page from the screen. `use` cannot sit inside `try` and `catch`, so the failure is handled above the component, just like the waiting.
>
> **DO THIS:**
> ```jsx
> <~ErrorBoundary fallback={<p>Could not load comments.</p>}~> {/* Catches the rejected Promise of the comments */}
>   <Suspense fallback={<p>Loading comments...</p>}>
>     <Comments commentsPromise={commentsPromise} />
>   </Suspense>
> </ErrorBoundary>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> try {
>   comments = ~use~(commentsPromise); // **WRONG:** use cannot be called inside try and catch
> } catch (error) {
>   return <p>Could not load comments.</p>;
> }
> ```

### A request that fails

Every request can fail: the server is down, or the reader's phone loses its connection. To see this case on our page, we add a second function to the request file. It fails after one second:

```js title="src/fetchComments.js"
export function fetchCommentsWithError() {
  return new Promise((resolve, ~reject~) => { // JavaScript hands reject to this function as its second argument
    setTimeout(reject, 1000, ~new Error('Could not load comments')~); // After one second, the Promise is rejected
  });
}
```

`reject` comes from the same place as `resolve`: JavaScript hands it to the function you pass to `new Promise`. Calling `reject` with an error makes the Promise rejected, and that error becomes the reason it failed.

### VS | `try` and `catch` vs. an Error Boundary: the error line inside the component, or above it

Everywhere else in JavaScript, you catch a failure with `try` and `catch` around the line that fails. So a developer writes this inside `Comments`:

```jsx title="try and catch around use"
let comments;
try {
  comments = ~use~(commentsPromise); // **WRONG:** use cannot be called inside try and catch
} catch (error) {
  return <p>Could not load comments.</p>;
}
```

React handles the failure above the component instead, the same way `<Suspense>` handles the waiting above it. An Error Boundary wraps the `<Suspense>`:

```jsx title="An Error Boundary around the Suspense boundary"
<~ErrorBoundary fallback={<p>Could not load comments.</p>}~> {/* Shown when the Promise is rejected */}
  <Suspense fallback={<p>Loading comments...</p>}>
    <Comments commentsPromise={commentsPromise} />
  </Suspense>
</ErrorBoundary>
```

> [!DEFINITION]
> **An Error Boundary.** [NEW] An Error Boundary is a component that catches an error thrown while React renders the components inside it. It then shows its own `fallback` in place of that part of the page, and everything outside it stays on the screen. It works for errors the way `<Suspense>` works for waiting: the closest one above the component takes over (Lesson 72).

Both aim to show `Could not load comments.` in place of the list. It may look the same as handling any error in JavaScript, but it is NOT the same thing! The React documentation says: "`use` throws internally to integrate with Suspense, so it cannot be wrapped in try-catch." So the failure is handled where the waiting is handled: above the component.

```tree caption="Two ways to show an error line when the comments fail, and which one React allows."
Where the failure of the comments is handled
- !Inside `Comments` [`try` `catch`] | Wraps the line with `use` | **Not allowed**: `use` cannot sit inside `try` and `catch`
- +Above `Comments` [`ErrorBoundary`] | Wraps the `<Suspense>` around `Comments` | Shows **`Could not load comments.`** in place of the list
```

### Adding the Error Boundary to the page

React has no ready-made Error Boundary, and we cannot write one as a function component. The React documentation says: "There is currently no way to write an Error Boundary as a function component." Its own example uses the `react-error-boundary` package, and so do we. Lesson 72 shows how to write one ourselves.

We add the package to the project from the terminal:

```bash title="Terminal"
npm install react-error-boundary
```

Then the page file imports `ErrorBoundary` and wraps the `<Suspense>` in it. For this principle only, the click handler calls the failing function:

```jsx title="src/App.jsx"
import { useState, Suspense } from 'react';
import { ~ErrorBoundary~ } from 'react-error-boundary'; // Comes from the react-error-boundary package
import { fetchCommentsWithError } from './fetchComments.js';
import Comments from './Comments.jsx';

export default function App() {
  const [commentsPromise, setCommentsPromise] = useState(null);
  return (
    <article>
      <h1>City park opens on Saturday</h1>
      {commentsPromise === null && (
        <button onClick={() => setCommentsPromise(~fetchCommentsWithError()~)}> {/* For this principle only: a request that fails */}
          Show comments
        </button>
      )}
      <~ErrorBoundary fallback={<p>Could not load comments.</p>}~> {/* Wraps only the comments section */}
        <Suspense fallback={<p>Loading comments...</p>}>
          <Comments commentsPromise={commentsPromise} />
        </Suspense>
      </ErrorBoundary>
    </article>
  );
}
```

### What the reader sees when the comments fail

**The title stays, and only the comments section shows the error.** Here is the click in order:
1. The reader clicks `Show comments`. The handler stores the failing Promise in `commentsPromise`.
2. `Comments` suspends, and the page shows `Loading comments...`.
3. One second later, the Promise is rejected.
4. React renders `Comments` again. This time `use` throws the error the Promise was rejected with.
5. The closest Error Boundary catches the error and shows `Could not load comments.` in place of the loading line.
6. The title stays on the page, because the Error Boundary wraps only the comments section.

React still reports the error in the Console, and names the Error Boundary that took over by the name of its class. The package ships minified code, where that class is named `C`. So the message ends with `C` instead of `ErrorBoundary`:

```page caption="The page after the Promise is rejected: the Error Boundary shows its fallback, and the title stays."
heading: City park opens on Saturday
line: Could not load comments.
console: Error: Could not load comments
  error: The above error occurred in the <Comments> component. React will try to recreate this component tree from scratch using the error boundary you provided, C.
```

### Without the Error Boundary, the whole article disappears

Now remove the `<ErrorBoundary>` and keep only the `<Suspense>`. Steps 1 to 4 stay the same. Step 5 changes: no Error Boundary catches the error, so React removes the page from the screen. The React documentation says: "By default, if your application throws an error during rendering, React will remove its UI from the screen."

The reader loses the title too, not only the comments:

```page caption="The page after the Promise is rejected, with no Error Boundary: React removed everything."
blank
```

```devconsole width=full caption="The Console after the Promise is rejected, with no Error Boundary."
x Uncaught Error: Could not load comments
x An error occurred in the <Comments> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

```tree caption="The same rejected Promise, with and without an Error Boundary around the comments."
What the reader sees after the comments fail
- +With an Error Boundary around the comments [`ErrorBoundary`] | The boundary **catches the error** | The title stays, and the page shows **`Could not load comments.`**
- !Without an Error Boundary | **No component catches the error** | React **removes the whole page**, title included
```

### Real mistake: `try` and `catch` around `use`

Here is how this happens at work:
1. A developer wraps the line with `use` in `try` and `catch` to show an error line, as in the code above.
2. The reader clicks `Show comments`. The page shows `Could not load comments.` at once, even with `fetchComments`, the request that does not fail. While the Promise is pending, `use` throws to stop the component, and the `catch` takes that for a failure.
3. The error line stays on the page after the comments arrive, and React prints an error in the Console:

```page caption="With try and catch around use: the error line appears right after the click, while the request is still on its way."
heading: City park opens on Saturday
line: Could not load comments. | bad
console: `use` was called from inside a try/catch block. This is not allowed and can lead to unexpected behavior. To handle errors triggered by `use`, wrap your component in a error boundary.
```

4. The lint rule `error-boundaries` also flags the `try` around `use`.

The React documentation lists this mistake under Troubleshooting, with the heading "Suspense Exception: This is not a real error!" Its fix is to remove the `try` and `catch`, and wrap the component in an Error Boundary instead, as our page does.

Remember: `<Suspense>` shows the wait. The Error Boundary shows the failure. Both sit above the component.

### How React renders the page from the first visit to the comments

When the page loads, React renders `App` and `Comments`. `Comments` returns `null`. The click stores the Promise. From then on, React renders `Comments` once to find the Promise pending, and once more to read its value:

```tree dir=right caption="The order in which React renders App and Comments, from the first visit to the comments on the page."
From the first visit to the comments on the page
- +1. The page loads | React renders `App` and `Comments` | `commentsPromise` is `null`: `Comments` **returns null**
- +2. The reader clicks Show comments | The handler **stores a new Promise** | React renders `App` again
- +3. React renders `Comments` | `use` finds the Promise **pending** | `Comments` suspends: **`Loading comments...`**
- +4. The Promise is fulfilled | React renders `Comments` **again from its first line** | `use` returns the comments: **John and Mia**
- !If the Promise is rejected | `use` **throws the error** | The Error Boundary shows **`Could not load comments.`**
```

### The habit that hurts, and the rule

| Principle | The habit that hurts | The React rule |
| :--- | :--- | :--- |
| **1. Promise in state** | Make the click wait for the comments with `await`, so the page does not react for a second | Create the Promise in the event handler and keep it in state |
| **2. Suspend** | Keep a loading check below `use`, and edit a line the reader never sees | Read the Promise with `use`, and let a `<Suspense>` above show the `fallback` |
| **3. Same instance** | Write `use(fetchComments())` in the component body to save a line | Pass a Promise created before render or taken from a cache |
| **4. Not a Hook** | Skip `use` by reading the Promise's own `status` | Call `use` inside an `if` or after an early return when the component needs it only sometimes |
| **5. Error Boundary** | Wrap `use` in `try` and `catch` | Wrap the `<Suspense>` in an Error Boundary that shows the error line |

Remember the one sentence of this lesson. **`use` reads a value that is not ready yet. While it is not ready, React shows the closest `<Suspense>` fallback. When it is ready, React renders the component again, and this time `use` returns the value.**

## For the Interview

> **The Interview Question:** What is the use() API, and how does it read promises and context conditionally?

### How to Answer Clearly in 30 Seconds

"`use` is a React API that reads a value during render, either from a Promise or from a context. With a Promise, `const comments = use(commentsPromise)` returns the value once the Promise is fulfilled. While the Promise is pending, the component suspends and the closest `<Suspense>` shows its fallback. When the Promise is rejected, the closest Error Boundary shows its fallback. Despite its name, `use` is not a Hook, so it can be called inside an `if`, a loop, or after an early return. Three rules keep it working:
1. **The same Promise on every render**: I create the Promise before render, such as in a click handler, and keep it in state, or I take it from a cache. A Promise created in the component body is new on every render, and the fallback never goes away.
2. **No `try` and `catch`**: `use` cannot sit inside them, so an Error Boundary handles the failure.
3. **Inside a component or a Hook**: `use` may be conditional, but it must still be called from a component or a Hook."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why can `use` sit inside an `if` when `useContext` cannot?"**
   A Hook finds its saved value by its place in the order of calls: React "holds an array of state pairs for every component", and it hands them out in call order. Skipping a Hook on one render gives every later Hook the wrong value. `use` does not depend on that order. With a Promise, React reads the result on the Promise itself, through fields such as `status` and `value`. With a context, React searches up the tree for the closest provider. So a render that skips `use` moves nothing out of place.
2. **"What does `use` do with a Promise that is already fulfilled?"**
   It returns the value at once, without suspending, when React has already read this Promise. The React documentation says that when `use` receives the same Promise again after it is fulfilled, it "reads the already-resolved value synchronously without suspending". React remembers the result on the Promise object: "React will set the `status` field itself on Promises that don't have it". A Promise that React has never read works differently. Say the page starts the request when the reader's pointer moves over the `Show comments` button, and the comments arrive before the click. The first `use` still suspends, and `Loading comments...` shows for a moment before the comments appear.
3. **"How do you let the reader try again after `Could not load comments.`?"**
   The retry creates a new Promise and clears the error. The React documentation's example uses a `Try again` button that calls `startTransition` with a setter that stores a new Promise (Lesson 67). It also passes `resetKeys` with the Promise to `ErrorBoundary`, so the boundary clears its error when the Promise changes. Lesson 72 shows how an Error Boundary works inside.
