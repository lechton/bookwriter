*(How can the small image the user tapped grow into the large image of the article?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do you animate between two screens with ViewTransition?

## VS | A plain setter vs. a setter inside `startTransition`: one cuts to the new screen, the other animates it

> Tap an article in a good news app, and the small image you tapped grows into the large image at the top of the article page. **In React, `<ViewTransition>` marks the parts of the page that may animate, and `startTransition` marks the change of screen that animates**. With a plain setter instead, React changes the screen at once, and the image simply jumps.

In React, apps often **open an item from a list**: an article in a news app, a product in a shop, a photo in a gallery. Until now, a click called a setter, and React replaced the list with the item page at once. The image the user tapped vanished from its row and appeared somewhere else, bigger. The user's eye has to search the new screen for it. **This is why React gives us `<ViewTransition>`.** It lets the browser animate the change of screen, so the user sees where they went.

Take a news app with two articles in a list, `New Park Opens` and `Library Opens Late`. Each row shows a small image and a title. The user taps `New Park Opens`, and the article page shows a large park image at the top. Ask yourself: what should the user see between the two screens? The small park image should leave its row, move up, and grow into the large one.

**Why:** In React, a click changes the screen in one step. The setter asks React to render, and React puts the new screen on the page. The browser can animate a change of the page, but only if someone warns it right before the change. Only React knows that moment, because React is the one that changes the page. So we tell React two things: which parts may animate, with `<ViewTransition>`, and which change should animate, with `startTransition`.

Nothing moved from one screen to the other. The small park image did not travel anywhere. It vanished, and a large one appeared in a different place.

One reminder and one new word explain how to fix it:

> [!DEFINITION]
> **A Transition.** [REVIEW] A Transition is a state update that you mark as not urgent, by calling the setter inside `startTransition`: `startTransition(() => setArticle(park))`. React provides `startTransition`, and you import it from `react`. A plain setter is urgent, so React shows its result at once. A Transition lets React prepare the new screen before it shows it (Lesson 66).

> [!DEFINITION]
> **ViewTransition.** [NEW] `<ViewTransition>` is a component React provides, like `<Suspense>`. You import it from `react` and wrap it around the part of the page that may animate. The React docs say it in one line: "`<ViewTransition>` lets you animate a component tree with Transitions and Suspense." On its own, it never starts an animation. It waits for a Transition to change what is inside it (Lesson 74).

### `<ViewTransition>` in Two Lines

Here are the two pieces, side by side:

```jsx title="What may animate, and when it animates"
~<ViewTransition>~ {/* What: the screens inside may animate */}
  {article ? <ArticlePage /> : <Home />}
</ViewTransition>

~startTransition~(() => setArticle(park)); // When: this change of screen animates
```

Here, `park` is the park article. With these two pieces, the list fades out while the article page fades in. Principle 3 then makes the park image itself move and grow.

**Keep this one sentence in mind for the whole lesson: `<ViewTransition>` says what may animate. A Transition says when.**

React's blog puts it the same way. The component lets you "declaratively define 'what' to animate". Then `startTransition`, `useDeferredValue`, and Suspense decide "when".

```tree caption="The two pieces of every View Transition in React: what may animate, and when it animates."
Two pieces make a change of screen animate
- +What may animate [`<ViewTransition>`] | Wraps the **parts of the page** that may animate | On its own, it **never starts** an animation
- +When it animates [`startTransition` `<Suspense>` `useDeferredValue`] | Marks **this change** as one that animates | Without it, the screen **cuts at once**
```

### The Browser Does the Animation, React Picks the Moment

Remember how you change a page in plain JavaScript? You grab an element and change it yourself. Modern browsers give you one method that animates such a change: `document.startViewTransition`.

```js title="Plain JavaScript: the browser's View Transition API, from MDN"
document.~startViewTransition~(() => { // The browser animates from the page before this function to the page after it
  updateColor();
});
```

You hand the browser a function that changes the page. The browser takes a still image of the page, like a screenshot. Then it runs your function, and animates from the screenshot to the new page.

In React, you never change the page yourself. React changes it for you, from your JSX, at a moment only React knows. So React makes this browser call for you, at exactly that moment. Your job is only to say what may animate and when.

The React docs are clear: "React automatically calls `startViewTransition` itself behind the scenes so you should never do that yourself."

### The Rule of Thumb: does the user move from one screen to another?

**Ask one question about every animation: does the user move from one view to another? If yes, use `<ViewTransition>` with a Transition. If one element only reacts to a click, use a CSS animation.**

There are three ways to animate something on the page:
1. **Call `document.startViewTransition` in plain JavaScript.** This fits a page without React.
2. **Wrap the parts in `<ViewTransition>`, and change state in a Transition.** React makes the browser call for us. This lesson is about this way.
3. **Write a CSS or JavaScript animation on one element**, such as a heart that pops when the user likes a post.

React's blog says View Transitions "are not meant to replace all the animations in your app". They are for moving between screens, opening, expanding, and reordering.

A senior developer also knows the three classic mistakes:
1. **Adding `<ViewTransition>` and keeping a plain setter.** Nothing animates, and the Console stays empty.
2. **Calling `document.startViewTransition` by hand inside a React app.** React's own animation never takes part.
3. **Giving every row of the list the same `name`.** React logs two errors.

One more fact before you use it at work. In React 19.3.1, the version this lesson runs, both `<ViewTransition>` and `addTransitionType` are named exports of the stable React package. Before that, they were only in the Canary and Experimental channels of React. So check the React version of your project first.

`App` comes in Principle 1. Each principle after it changes one or two files, or only watches the page:

**PRINCIPLES:** `<ViewTransition>` marks what may animate, and a Transition says when. React prepares the page, and the browser runs the animation. Six principles follow:
1. **A plain setter cuts, and `startTransition` cross-fades.** Only a Transition, a `<Suspense>` reveal, or a deferred value makes a `<ViewTransition>` animate.
2. **React calls the browser for us.** React writes `view-transition-name` and calls `startViewTransition`, and the browser fades the old screen into the new one.
3. **A shared `name` grows the small image into the large one.** The same name on both images makes them one image. Each name may be on the page only once at a time.
4. **A View Transition Class styles the animation.** Our CSS styles a class we name on the prop, and turns it down for users who asked for less motion.
5. **`addTransitionType` lets going back slide the other way.** Naming why the Transition happened lets each direction pick its own class.
6. **The loading line cross-fades into the article text.** A `<Suspense>` reveal is a trigger too, and the shared image must stay outside the boundary.

## PRINCIPLE | `startTransition` around the setter: the change of screen animates, a plain setter cuts

> [!PRINCIPLE]
> **Principle 1: A Plain setArticle Cuts, startTransition Cross-Fades: Only a Trigger Starts the Animation**
>
> *A `<ViewTransition>` animates only when the change inside it comes from a Transition, a `<Suspense>` reveal, or `useDeferredValue`; a plain setter changes the screen at once.*
>
> Wrapping the screens in `<ViewTransition>` only says what may animate. If the click handler calls the setter directly, React updates the screen at once, as it always has. There is no error, because nothing is wrong in React's eyes. Put the setter inside `startTransition`, and the same tap cross-fades the two screens.
>
> **DO THIS:**
> ```jsx
> function handleOpen(next) {
>   ~startTransition(() => setArticle(next))~; // A Transition: the list fades into the article page
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleOpen(next) {
>   ~setArticle(next)~; // **WRONG:** a plain setter is not a trigger, so the screen cuts with no error
> }
> ```

### Two buttons under the same `<ViewTransition>`

The smallest version holds one boolean, `open`. Compare two buttons that open the article:

```jsx title="A plain setter vs. a setter inside startTransition, under the same ViewTransition"
import { ViewTransition, startTransition, useState } from 'react';

const [open, setOpen] = useState(false);

<ViewTransition>
  {open ? <ArticlePage /> : <Home />}
</ViewTransition>

<button onClick={() => ~setOpen(true)~}>Open</button> {/* A plain setter: the screen cuts */}
<button onClick={() => ~startTransition(() => setOpen(true))~}>Open</button> {/* A Transition: the two screens cross-fade */}
```

You import `ViewTransition` from `react`, in the same line as the other names.

Both buttons open the article, and both sit under the same `<ViewTransition>`. So you expect both to animate. **It looks the same, but it is NOT the same thing!** With the plain setter, the article page replaces the list at once. With `startTransition`, the list fades out while the article page fades in.

The docs say it plainly: "By default, `setState` updates immediately and does not activate `<ViewTransition>`."

React's docs call the thing that starts an animation a **trigger**. A `<ViewTransition>` has three triggers:
1. **A Transition**, such as a setter inside `startTransition`.
2. **A deferred value** from `useDeferredValue` (Lesson 68).
3. **A `<Suspense>` boundary that switches from its fallback to its content** (Lesson 69).

The docs: "only updates wrapped in a Transition, `<Suspense>`, or `useDeferredValue` activate ViewTransition." A plain setter in a click handler is none of the three.

### What a cross-fade is

The default animation is a **cross-fade**. The old screen fades out while the new screen fades in, at the same moment, until only the new screen is left. The docs: "By default, `<ViewTransition>` animates with a smooth cross-fade."

Our code wrote no animation at all. The cross-fade is the browser's own default view transition, and the browser runs it.

```tree caption="The same ViewTransition with a plain setter and with a setter inside startTransition."
Two ways to open the article under one `<ViewTransition>`
- !A plain setter [`setOpen`] | Not a trigger: React **updates the screen at once** | The list **cuts** to the article page
- +A setter inside `startTransition` [`startTransition`] | A Transition is a **trigger**: the `<ViewTransition>` takes part | The list **fades out** while the article page **fades in**
```

### The first `App` cuts, with no error

Here is the first `App`. It wraps both screens in `<ViewTransition>`, but its handlers call the setter directly:

```jsx title="src/App.jsx" bad="11,15"
import { ViewTransition, useState } from 'react';
import Home from './Home.jsx';
import ArticlePage from './ArticlePage.jsx';
import { articles } from './articles.js';
import './App.css';

export default function App() {
  const [article, setArticle] = useState(null);

  function handleOpen(next) {
    ~setArticle(next)~; // **WRONG:** a plain setter is not a trigger, so the screen cuts
  }

  function handleBack() {
    ~setArticle(null)~; // **WRONG:** going back cuts too
  }

  return (
    <ViewTransition>
      {article ? (
        <ArticlePage article={article} onBack={handleBack} />
      ) : (
        <Home articles={articles} onOpen={handleOpen} />
      )}
    </ViewTransition>
  );
}
```

**The user taps `New Park Opens`, and the screen cuts exactly as it did before `<ViewTransition>` was added.** Here is what happens, in order:
1. The user taps the row, and `Home` calls `onOpen`. That is `handleOpen` in our App, and it calls `setArticle` with the park article.
2. No Transition is running, so React treats this as an urgent update.
3. React renders `ArticlePage` and puts it on the page at once, as in every earlier lesson.
4. The `<ViewTransition>` never takes part, because no trigger reached it.

The Console stays empty. Nothing tells the developer why the animation is missing:

```page width=full caption="The article page right after the tap, with the plain setter: the same cut, and an empty Console."
line: [Back]
line: 🌳
heading: New Park Opens
line: The park on Main Street opens at noon.
console: quiet
```

### Putting the change of screen inside `startTransition`

The fix is one wrapper in each handler. `startTransition` marks the update as a Transition, and the Transition is the trigger:

```jsx title="src/App.jsx" startLine="1" good="1,11,12,13,17,18,19"
import { ViewTransition, startTransition, useState } from 'react';
import Home from './Home.jsx';
import ArticlePage from './ArticlePage.jsx';
import { articles } from './articles.js';
import './App.css';

export default function App() {
  const [article, setArticle] = useState(null);

  function handleOpen(next) {
    ~startTransition~(() => { // The change of screen is now a Transition
      setArticle(next);
    });
  }

  function handleBack() {
    ~startTransition~(() => { // Going back is a Transition too
      setArticle(null);
    });
  }

  return (
    <ViewTransition>
      {article ? (
        <ArticlePage article={article} onBack={handleBack} />
      ) : (
        <Home articles={articles} onOpen={handleOpen} />
      )}
    </ViewTransition>
  );
}
```

Now the user taps `New Park Opens`, and the list fades out while the article page fades in. The user taps `Back`, and the article page fades out while the list fades in. The first screen and the last screen are the same as before. Only the moment in between changed.

### How developers meet this bug

A developer reads that `<ViewTransition>` animates a component tree, and wraps the whole app in it. Their click handlers, or their router, call a plain setter. Nothing animates, and the Console is empty. So the developer guesses that the browser does not support the feature.

The fix is in the handler, not in the browser. React's blog shows the other side. When a router already changes the page inside `startTransition`, "this one line change to add `<ViewTransition>` activates with the default cross-fade animation."

Remember: `<ViewTransition>` says what. `startTransition` says when.

## PRINCIPLE | `startViewTransition`: React calls the browser at the moment it changes the page, so we never call it

> [!PRINCIPLE]
> **Principle 2: The Browser Captures the Old Screen Before React Changes It: React Calls startViewTransition for Us**
>
> *On every Transition that activates a `<ViewTransition>`, React writes `view-transition-name` on its nearest DOM node and calls the browser's `startViewTransition`; the browser takes a still image of the old screen, React changes the DOM, and the browser fades the old snapshot into the live new one.*
>
> The animation belongs to the browser, and the timing belongs to React. React knows the exact moment it changes the page, so React makes the browser call at that moment and removes the names afterwards. A call from our own code cannot know that moment. Its function ends before React changes the page, and when React starts its own view transition, React interrupts ours.
>
> **DO THIS:**
> ```jsx
> function handleOpen(next) {
>   ~startTransition(() => setArticle(next))~; // React calls startViewTransition when it changes the page
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleOpen(next) {
>   document.~startViewTransition~(() => setArticle(next)); // **WRONG:** the function ends before React changes the page
> }
> ```

### Our own call to the browser vs. letting React make it

Browsers provide the **View Transition API**. MDN describes it as a way "for easily creating animated transitions between different website and element views". Its main method is `document.startViewTransition`, as the intro showed.

In React, we never write that call. Compare:

```jsx title="Our own call to the browser vs. letting React make it"
document.~startViewTransition~(() => setArticle(park)); // Our code calls the browser: the ViewTransition never takes part
~startTransition~(() => setArticle(park)); // Under a ViewTransition, React calls startViewTransition itself
```

**It looks the same, but it is NOT the same thing inside a React app!** React calls `startViewTransition` at the exact moment it is ready to change the page. A call from our own code does not know when that moment is.

The docs: "React automatically calls `startViewTransition` itself behind the scenes so you should never do that yourself. In fact, if you have something else on the page running a ViewTransition React will interrupt it."

### What happens during one tap

**In short: the browser takes a still image of the list. React swaps the list for the article page under it. Then the browser fades the image into the live new page.**

> [!DEFINITION]
> **Snapshot.** [NEW] A snapshot is the image of a part of the screen that the browser takes for a view transition. The old snapshot is a still image, like a screenshot: MDN says it is "a static image, so that the user can't interact with it as it animates 'out'". The new snapshot is the live page: MDN calls it "an interactive DOM region". While the animation runs, the user sees the old snapshot fade out and the new one fade in (Lesson 74).

Here is the whole tap, in order:
1. The user taps `New Park Opens`. `handleOpen` starts a Transition.
2. React renders `ArticlePage`, but does not change the page yet.
3. React writes a `view-transition-name` into the inline style of the nearest DOM node inside the `<ViewTransition>`. Here, that is the `<section>` of the list.
4. React calls the browser's `startViewTransition`.
5. The browser takes the old snapshot: a still image of the list.
6. Inside the function React gave the browser, React changes the DOM. The `<section>` leaves, and the `<article>` of the article page arrives.
7. The new `<article>` gets the same `view-transition-name`. React also waits for new fonts, runs `useLayoutEffect` (Lesson 49), and attaches refs.
8. The browser takes the new snapshot: the live article page.
9. The browser fades the old snapshot out and the new one in.
10. When the animation has finished, React removes the `view-transition-name` again and runs `useEffect` (Lesson 32).

Why does `useEffect` wait until the end? The docs: "This prevents those from interfering with the performance of the animation."

`view-transition-name` is a CSS property. MDN says it lets an element "participate in a separate snapshot". Our code never wrote it. React writes it, and only for the length of the animation. The docs: "React doesn't apply these eagerly but only at the time that boundary should participate in an animation."

When a `<ViewTransition>` has no `name` prop, React makes a unique name for it. Principle 3 gives one a name of our own.

```tree dir=right caption="Who does what during one tap: React prepares the page, and the browser takes the snapshots and runs the animation."
One tap on `New Park Opens`
- +1. React prepares [`view-transition-name`] | Renders `ArticlePage` | Names the list's `<section>` and calls **`startViewTransition`**
- +2. The browser takes the list | Takes the **old snapshot**: a **still image** the user cannot click
- +3. React changes the DOM | Swaps the `<section>` for the `<article>` | Runs `useLayoutEffect` and refs
- +4. The browser animates | Takes the **new snapshot**, which is **live** | Fades the old one **out** and the new one **in**
- +5. React cleans up | Removes the names | Runs **`useEffect` last**
```

### The pseudo-elements the browser draws

For the animation, the browser draws a small tree of **pseudo-elements** on top of the page. A pseudo-element is a part of the page that CSS can style, but that no tag in our code creates. You know `::before` from CSS: it works the same way.

Two of them matter here:
- **`::view-transition-old()`** holds the old snapshot.
- **`::view-transition-new()`** holds the new snapshot.

Principle 4 styles them.

### Calling `document.startViewTransition` inside a React app

A developer who used the View Transition API without React reaches for it again in a React app. They call it in the click handler, and change state inside it:

```jsx title="src/App.jsx" startLine="10"
function handleOpen(next) {
  document.~startViewTransition~(() => { // **WRONG:** our own view transition competes with React's
    setArticle(next);
  });
}
```

The page still changes, but React's `<ViewTransition>` never takes part. Here is why:
1. `setArticle` is a plain setter, so it only asks React to render.
2. The browser's function returns before React changes the page.
3. React writes no `view-transition-name` and starts no view transition of its own.
4. The browser fades a still image of the whole page into the live page. That page switches to the article a moment later.

A shared `name`, as in Principle 3, could never move the park image in this call.

Putting the setter inside `startTransition` within our call does not help either. React then starts its own view transition a few milliseconds later, and ours ends at once. The docs warn about exactly this: when something else runs a view transition, "React will interrupt it."

Their advice: "If you had other ways to trigger ViewTransitions in the past, we recommend that you migrate to the built-in way." In a React app, the built-in way is `startTransition` under a `<ViewTransition>`.

## PRINCIPLE | `name` on `<ViewTransition>`: the same name on both screens makes one image move and grow

> [!PRINCIPLE]
> **Principle 3: A Shared name Grows the Small Image into the Large One: One Name Leaves and the Same Name Arrives**
>
> *When a Transition removes a `<ViewTransition>` with a `name` and adds another `<ViewTransition>` with the same `name`, React animates from the removed one to the added one; only one `<ViewTransition>` with a given `name` may be mounted at a time.*
>
> The small image and the large image are two different elements on two different screens. The user should see one image travel, not two images fade. The same `name` on both tells React they are one, and the browser moves and grows the snapshot. Build the name from the item's `id`, so each row has its own name.
>
> **DO THIS:**
> ```jsx
> <ViewTransition ~name={`article-${article.id}`}~> {/* One name per article: article-1 pairs only with article-1 */}
>   <img className={size} src={article.image} alt="" />
> </ViewTransition>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ViewTransition ~name="article-image"~> {/* **WRONG:** every row mounts the same name, and React logs two errors */}
>   <img className={size} src={article.image} alt="" />
> </ViewTransition>
> ```

### The cross-fade still loses the user's place

The cross-fade from Principle 1 is better than a cut, but the eye still jumps. The small park image fades out with the list. The large park image fades in with the article page. For the browser, they are two separate images.

To make one image travel, give both images the same `name`:

```jsx title="The same name on the small image and on the large image"
<ViewTransition ~name="park-image"~><img className="small" src="/park.jpg" alt="" /></ViewTransition> {/* In the list row */}
<ViewTransition ~name="park-image"~><img className="large" src="/park.jpg" alt="" /></ViewTransition> {/* On the article page */}
```

`name` is a prop of `<ViewTransition>`. The docs: "The name of the View Transition used for shared element transitions."

When the user taps the row, the Transition removes the first `<ViewTransition name="park-image">` and adds the second one. React sees one name leaving and the same name arriving. So React treats them as one image.

> [!DEFINITION]
> **Shared element transition.** [NEW] A shared element transition is an animation of one element that two screens share, such as the park image in the list and on the article page. You make one by giving the two `<ViewTransition>` the same `name`. The docs: "It animates from the unmounting side to the mounting side." The browser takes the snapshot of the small image, then moves it, scales it, and cross-fades it until it sits where the large image is (Lesson 74).

In the words of the docs, `<ViewTransition>` "creates an image that can be moved around, scaled and cross-faded".

Compare the same tap without a `name` and with one:
- **Without `name`**, React gives each `<ViewTransition>` its own unique name, "to prevent unexpected animations". No two names match, so the small image fades out and the large image fades in somewhere else.
- **With the same `name` on both images**, the two form a pair. The park image moves from its row to the top of the article page and grows, while the rest of the screen cross-fades.

The code differs by one prop, and the screen changes completely.

```tree caption="The same tap without a name and with the same name on both images."
The park image during the tap
- !Without `name` | React gives **each image its own name** | The small image **fades out**; the large one **fades in** somewhere else
- +With the same `name` on both images [`name`] | One name **leaves**, the same name **arrives** | The park image **moves and grows** from the row to the top of the page
```

### One `ArticleImage` for both screens

Both screens now need the image inside a named `<ViewTransition>`. We write that once, in a new component. The name comes from the article's `id`. The park article gets `article-1`, and the library article gets `article-2`:

```jsx title="src/ArticleImage.jsx"
import { ViewTransition } from 'react';

export default function ArticleImage({ article, size }) {
  return (
    <ViewTransition ~name={`article-${article.id}`}~> {/* article-1 for the park, article-2 for the library */}
      <img className={size} src={article.image} alt="" />
    </ViewTransition>
  );
}
```

The `id` is the same field that `Home` already uses as the key of each row. Both screens now replace their `<img>` with `<ArticleImage />`:

```jsx title="src/Home.jsx" startLine="10"
<button onClick={() => onOpen(article)}>
  ~<ArticleImage article={article} size="small" />~ {/* The small image, named article-1 or article-2 */}
  {article.title}
</button>
```

```jsx title="src/ArticlePage.jsx" startLine="6"
<button onClick={onBack}>Back</button>
~<ArticleImage article={article} size="large" />~ {/* The large image, with the same name as its row */}
<h1>{article.title}</h1>
```

Both files also import the new component:

```jsx title="The new import in Home.jsx and in ArticlePage.jsx"
import ~ArticleImage~ from './ArticleImage.jsx'; // The same component on both screens
```

Now the user taps `New Park Opens`. The list screen and the article screen look exactly as before. In between, the park image leaves its row, moves up, and grows until it fills the top of the article page. The title and the rest of the screen cross-fade around it. The user taps `Back`, and the park image shrinks back into its row.

```tree dir=right caption="What the user sees during one tap when both park images share the name article-1."
The park image from the list to the article
- +In the list | The **small** park image sits in the first row
- +During the animation | The browser **moves and grows** one snapshot | The rest of the screen **cross-fades**
- +On the article page | The **large** park image sits at the top | `Back` makes it **shrink back** into its row
```

Our code wrote no position and no size for the movement. The browser reads where the image was and where it ends up, and animates between them.

### One fixed name for every row

There are two ways to write the name inside `ArticleImage`:

```jsx title="One fixed name vs. a name built from the id"
<ViewTransition ~name="article-image"~> {/* Every row gets the same name: article-image */}
<ViewTransition ~name={`article-${article.id}`}~> {/* Each row gets its own name: article-1, article-2 */}
```

**It looks the same, but it is NOT the same thing!** `ArticleImage` runs once for every row. With the fixed name, both rows mount a `<ViewTransition name="article-image">` at the same time.

The docs' rule: only one `<ViewTransition>` with a given name may be mounted at a time. Breaking it "will cause the View Transition to error."

This is easy to miss. A developer tests with one article, the image grows into the article page, and it works. Then the list gets its second article. In development, React logs two errors as soon as the list appears:

```page width=full caption="The list screen with one fixed name in ArticleImage: two rows, two errors in the Console."
heading: News
line: [🌳 New Park Opens]
line: [📚 Library Opens Late]
console: There are two <ViewTransition name="article-image"> components with the same name mounted at the same time. This is not supported and will cause View Transitions to error. Try to use a more unique name e.g. by using a namespace prefix and adding the id of an item to the name.
console: The existing <ViewTransition name="article-image"> duplicate has this stack trace.
```

Each message comes with a stack trace, so the developer can find both places where the name is mounted. The fix is the one the error itself suggests: "adding the id of an item to the name". Our `ArticleImage` already does that.

Remember: one name leaves, the same name arrives, and only one of each name is on the page at a time.

## PRINCIPLE | A View Transition Class on `default`: our CSS styles the animation, and turns it down for reduced motion

> [!PRINCIPLE]
> **Principle 4: A View Transition Class Slows the Cross-Fade: The Prop Names the Class, and CSS Styles It**
>
> *To change how a `<ViewTransition>` animates, give `enter`, `exit`, `update`, `share`, or `default` a class name, style it with `::view-transition-old` and `::view-transition-new`, and turn it down inside `@media (prefers-reduced-motion)`.*
>
> The browser's cross-fade is only the starting point. A class name on the right prop gives our CSS a stable handle, because React makes the names and writes them only during the animation. `"none"` turns an animation off, and `"auto"` keeps the browser's own. React plays every animation, even for users who asked for less motion, so the media query is our job.
>
> **DO THIS:**
> ```jsx
> <ViewTransition ~default="slow-fade"~> {/* App.css styles .slow-fade on the old and new snapshots */}
>   {article ? <ArticlePage /> : <Home />}
> </ViewTransition>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ViewTransition ~name="screens"~> {/* **WRONG:** a name added only so CSS can select it; name is for shared element transitions */}
>   {article ? <ArticlePage /> : <Home />}
> </ViewTransition>
> ```

### The smallest View Transition Class

Say the cross-fade between the two screens feels too quick, and we want a slower fade of half a second. We change two places: a prop on the `<ViewTransition>`, and two rules in CSS.

```jsx title="A class name on the default prop"
<ViewTransition ~default="slow-fade"~> {/* React adds the class slow-fade when this ViewTransition animates */}
```

```css title="Two CSS rules for the class slow-fade"
::view-transition-old(.slow-fade) {
  animation-duration: 500ms;
}
::view-transition-new(.slow-fade) {
  animation-duration: 500ms;
}
```

The prop names the class, and the CSS styles that class. We choose the name.

> [!DEFINITION]
> **View Transition Class.** [NEW] A View Transition Class is a class name that you write on a prop of `<ViewTransition>`, such as `default="slow-fade"`. The docs: it is "a CSS class name that React applies to the child elements when the ViewTransition activates". Your CSS then reaches the two snapshots through it: `::view-transition-old(.slow-fade)` is the old screen fading out, and `::view-transition-new(.slow-fade)` is the new screen fading in (Lesson 74).

### Five props, one for each kind of animation

`default` is one of five props that take a View Transition Class. Each one matches one kind of animation, and React picks the kind by itself:
1. **`enter`**: the Transition adds this `<ViewTransition>` to the page.
2. **`exit`**: the Transition removes this `<ViewTransition>` from the page.
3. **`update`**: React changes the DOM inside this `<ViewTransition>`.
4. **`share`**: a named pair, as in Principle 3.
5. **`default`**: every kind that has no prop of its own.

Our change of screen is an `update`. The `<ViewTransition>` around the screens stays on the page, and only its content changes, from the list to the article.

Each prop takes one of three values:
- **`"auto"`** keeps the browser's cross-fade. Leaving the prop out means the same.
- **`"none"`** turns that kind of animation off.
- **Any other text** is a class name, such as `"slow-fade"`.

In our app, the `<ViewTransition>` in `App` gets the new prop:

```jsx title="src/App.jsx" startLine="23"
<ViewTransition ~default="slow-fade"~> {/* The change of screen now fades in half a second */}
  {article ? (
    <ArticlePage article={article} onBack={handleBack} />
  ) : (
    <Home articles={articles} onOpen={handleOpen} />
  )}
</ViewTransition>
```

`App.css` gets the two `.slow-fade` rules from above, right after the two image sizes.

The shared park image from Principle 3 keeps its own animation. Its `<ViewTransition>` in `ArticleImage` has no class, so its move still uses the browser's default.

### VS | A selector on a name vs. a selector on a class: only the class is ours

Many early examples on the web style the animation through the name instead of a class:

```css title="A selector on a name vs. a selector on a class"
::view-transition-old(article-1) {
  animation-duration: 500ms;
}
::view-transition-old(.slow-fade) {
  animation-duration: 500ms;
}
```

**It looks the same, but it is NOT the same thing!** A name is something React manages. Without a `name` prop, React makes a unique name that our CSS cannot know in advance. And React writes it only during the animation.

A class is something we choose once and write in the prop. The docs: "We don't recommend that for styling. Instead, we normally recommend using a View Transition Class instead." And: "Only use `name` for shared element transitions."

### Users who asked for less motion

Some users turn on a system setting that reduces motion on the screen, often because movement makes them dizzy. The browser reports that setting to CSS through the media query `prefers-reduced-motion`.

React does not read it for us. The docs: "React doesn't automatically disable animations for this case." Their advice: "We recommend always using the `@media (prefers-reduced-motion)` media query to disable animations or tone them down based on user preference."

**Therefore, every time you add a View Transition Class, you need to pay attention and add the rule for reduced motion right next to it.** So `App.css` gains one more rule:

```css title="src/App.css" startLine="16"
@media (prefers-reduced-motion: reduce) {
  ::view-transition-old(.slow-fade),
  ::view-transition-new(.slow-fade) {
    animation: none;
  }
}
```

For these users, the list and the article page now swap at once, with no fade. Everyone else gets the half-second fade.

Something that can be tricky: the park image from Principle 3 still moves and grows for these users. Its `<ViewTransition>` has no class, so this rule does not reach it. Adding `::view-transition-group(*)` to the same rule stops that move too.

### Turning one part off with `"none"`

The `<ViewTransition>` in `App` wraps everything. That has a cost. Any later Transition that changes the DOM inside the article page would fade the whole screen too. React's blog warns that a `<ViewTransition>` at the top of an app "can lead to unexpected animations".

The docs' answer is an inner `<ViewTransition update="none">` around the part that should stay still. A change inside it then belongs to the inner boundary, and `"none"` turns its animation off. For example, around the text of the article:

```jsx title="An inner ViewTransition that keeps the text still"
<ViewTransition ~update="none"~> {/* A Transition that changes only this text no longer fades the whole screen */}
  <p>{article.text}</p>
</ViewTransition>
```

Our app does not need it yet, because no Transition in our app changes only the text.

## PRINCIPLE | `addTransitionType`: opening and going back each pick their own slide

> [!PRINCIPLE]
> **Principle 5: addTransitionType Slides Back the Other Way: The Type Picks the Class**
>
> *Call `addTransitionType` inside `startTransition` to name the cause of the Transition, and give the prop an object with one class for each type, so opening and going back can slide in opposite directions.*
>
> Opening an article and going back are the same kind of update to the same `<ViewTransition>`. Only the cause differs, and the cause is something only our code knows. `addTransitionType` hands that cause to React, and React picks the class whose key matches it.
>
> **DO THIS:**
> ```jsx
> startTransition(() => {
>   ~addTransitionType('nav-back')~; // The nav-back key picks slide-back
>   setArticle(null);
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ViewTransition ~default="slide"~> {/* **WRONG:** Back slides the list in from the same side, like a new screen */}
>   {article ? <ArticlePage /> : <Home />}
> </ViewTransition>
> ```

### Opening and going back slide the same way

Many apps slide screens instead of fading them. Opening an article slides the new screen in from the right. Going back slides the list in from the left, so the user feels they moved back to where they were.

Say the `<ViewTransition>` in our app gets one slide class, `default="slide"`. Opening an article slides the article page in from the right. Pressing `Back` also slides the list in from the right. To the user, going back now looks like going forward to yet another screen.

The two handlers run the same kind of update. One prop cannot tell them apart. What differs is why the Transition happened: the user opened an article, or the user went back.

### Naming why the Transition happened

React provides a function for this: `addTransitionType`. The docs: "`addTransitionType` lets you specify the cause of a transition." We call it inside `startTransition`, with any text we choose. It returns nothing.

Here are the two handlers from React's blog, side by side:

```jsx title="The same Transition with two different types"
startTransition(() => { ~addTransitionType('nav-forward')~; go(url); }); // Named as moving forward
startTransition(() => { ~addTransitionType('nav-back')~; go(url); }); // Named as moving back
```

In the blog, `go` is the router function that changes the page to `url`.

> [!DEFINITION]
> **Transition Type.** [NEW] A Transition Type is the text you pass to `addTransitionType` inside `startTransition`, such as `'nav-back'`. It names why the Transition happened. A prop of `<ViewTransition>` can then take an object instead of one class name, with one class for each type. The docs describe the object: "`{[type]: value}`: applies `value` if the animation matches the Transition Type" (Lesson 74).

```jsx title="One class for each Transition Type"
<ViewTransition ~default={{ 'nav-forward': 'slide-forward', 'nav-back': 'slide-back' }}~> {/* The type picks the class */}
```

Each key is a type, and each value is the class for it.

Compare the two props:
- **With `default="slide"`**, opening and going back use the same slide.
- **With an object of two types**, each direction gets its own class, so each can slide its own way.

**It works the same on the first tap, but it is NOT the same thing!** The difference shows on the first `Back`. With one class, the list arrives from the same side the article did. With the object, React reads the type of the Transition and picks the class that matches it.

```tree caption="One slide class for both directions vs. one class for each Transition Type."
How the `Back` button slides the list in
- !One class for both [`default="slide"`] | Opening and `Back` get the **same slide** | Going back **looks like going forward**
- +One class per Transition Type [`addTransitionType`] | `nav-forward` picks `slide-forward`; `nav-back` picks `slide-back` | `Back` slides the list in **from the other side**
```

### The two handlers in our app

`App` imports `addTransitionType` and names the cause of each handler's Transition:

```jsx title="src/App.jsx" startLine="1" good="12,19,25"
import { ViewTransition, startTransition, addTransitionType, useState } from 'react';
import Home from './Home.jsx';
import ArticlePage from './ArticlePage.jsx';
import { articles } from './articles.js';
import './App.css';

export default function App() {
  const [article, setArticle] = useState(null);

  function handleOpen(next) {
    startTransition(() => {
      ~addTransitionType('nav-forward')~; // The user opened an article
      setArticle(next);
    });
  }

  function handleBack() {
    startTransition(() => {
      ~addTransitionType('nav-back')~; // The user went back to the list
      setArticle(null);
    });
  }

  return (
    <ViewTransition ~default={{ 'nav-forward': 'slide-forward', 'nav-back': 'slide-back' }}~> {/* Replaces slow-fade */}
      {article ? (
        <ArticlePage article={article} onBack={handleBack} />
      ) : (
        <Home articles={articles} onOpen={handleOpen} />
      )}
    </ViewTransition>
  );
}
```

The strings `'nav-forward'` and `'nav-back'` are our own, the same ones the blog uses. React does not know what they mean. It only matches them against the keys of the object.

`App.css` replaces the slow fade with the two slides. Each slide moves the old snapshot out on one side and the new snapshot in from the other. It uses `@keyframes`, the CSS way to describe an animation:

```css title="src/App.css" startLine="9"
::view-transition-old(.slide-forward) {
  animation: slide-out-left 300ms ease-out;
}
::view-transition-new(.slide-forward) {
  animation: slide-in-right 300ms ease-out;
}
::view-transition-old(.slide-back) {
  animation: slide-out-right 300ms ease-out;
}
::view-transition-new(.slide-back) {
  animation: slide-in-left 300ms ease-out;
}

@keyframes slide-in-right { from { transform: translateX(100%); } }
@keyframes slide-out-left { to { transform: translateX(-100%); } }
@keyframes slide-in-left { from { transform: translateX(-100%); } }
@keyframes slide-out-right { to { transform: translateX(100%); } }

@media (prefers-reduced-motion: reduce) {
  ::view-transition-old(.slide-forward),
  ::view-transition-new(.slide-forward),
  ::view-transition-old(.slide-back),
  ::view-transition-new(.slide-back) {
    animation: none;
  }
}
```

Now the user taps `New Park Opens`. The list slides out to the left, and the article page slides in from the right. The user taps `Back`. The article page slides out to the right, and the list slides in from the left.

The park image still moves and grows between the two screens. Its own `<ViewTransition>` in `ArticleImage` has its own name and no class.

## PRINCIPLE | `<ViewTransition>` around `<Suspense>`: the loading line cross-fades into the text, and the shared image stays outside

> [!PRINCIPLE]
> **Principle 6: The Loading Line Cross-Fades into the Article Text: Where the Boundary Sits Decides the Animation**
>
> *A `<ViewTransition>` around a `<Suspense>` boundary cross-fades the fallback into the content as one update; a `<ViewTransition>` inside each animates them as an exit and an enter; a boundary that holds the shared image stops the shared element transition.*
>
> The reveal of a `<Suspense>` boundary is a trigger of its own, so the loading line can fade into the text after the change of screen is over. The place of the boundary matters. When the named image sits inside a new boundary, it arrives only after the fallback, too late to pair with the image that left. Keep everything that must travel outside the boundary.
>
> **DO THIS:**
> ```jsx
> <ArticleImage article={article} size="large" />
> ~<ViewTransition>~ {/* Only the text waits: the image still grows from the list */}
>   <Suspense fallback={<p>Loading article...</p>}><ArticleText article={article} /></Suspense>
> </ViewTransition>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<Suspense fallback={<p>Loading article...</p>}>~ {/* **WRONG:** the named image arrives after the fallback, so no pair forms */}
>   <ArticlePage article={article} onBack={handleBack} />
> </Suspense>
> ```

### The article text now loads from the server

In a real news app, the list knows only the titles and the images. The text of an article arrives from the server after the user opens it. So `ArticlePage` now shows a loading line under the large image, and then the text.

> [!DEFINITION]
> **Suspense and use.** [REVIEW] `use` reads the value of a Promise inside a component. While the Promise is still waiting, the component suspends: React stops rendering it and shows the `fallback` of the nearest `<Suspense>` boundary above it, such as a loading line. When the Promise resolves, React replaces the fallback with the content. This replacement is called the reveal (Lesson 71).

The text moves out of `articles.js` and into a small helper, `data.js`. Its `fetchText` keeps one Promise per article in a cache, and resolves it after one second. The `fetchVideo` helper in React's docs works the same way:

```js title="src/data.js"
const texts = {
  1: 'The park on Main Street opens at noon.',
  2: 'The library stays open until nine tonight.',
};

const cache = new Map();

export function fetchText(id) {
  if (!cache.has(id)) {
    cache.set(id, new Promise(resolve => {
      setTimeout(() => resolve(texts[id]), 1000);
    }));
  }
  return ~cache.get(id)~; // The same Promise every time for the same article
}
```

A new component reads the text with `use`:

```jsx title="src/ArticleText.jsx"
import { use } from 'react';
import { fetchText } from './data.js';

export default function ArticleText({ article }) {
  const text = ~use(fetchText(article.id))~; // Suspends until the text arrives
  return <p>{text}</p>;
}
```

`ArticlePage` wraps the text in `<Suspense>`. Around that boundary, it puts its own `<ViewTransition>`:

```jsx title="src/ArticlePage.jsx" good="11,15"
import { ViewTransition, Suspense } from 'react';
import ArticleImage from './ArticleImage.jsx';
import ArticleText from './ArticleText.jsx';

export default function ArticlePage({ article, onBack }) {
  return (
    <article>
      <button onClick={onBack}>Back</button>
      <ArticleImage article={article} size="large" />
      <h1>{article.title}</h1>
      ~<ViewTransition>~ {/* Cross-fades the loading line into the text */}
        <Suspense fallback={<p>Loading article...</p>}>
          <ArticleText article={article} />
        </Suspense>
      </ViewTransition>
    </article>
  );
}
```

The user taps `New Park Opens`. The article page slides in, and the park image grows into place, with the loading line under the title:

```page width=full caption="The article page right after the tap, while the article text is still loading."
line: [Back]
line: 🌳
heading: New Park Opens
line: Loading article...
```

A second later, the loading line fades out and the text fades in:

```page width=full caption="The same page after the text arrives and cross-fades in."
line: [Back]
line: 🌳
heading: New Park Opens
line: The park on Main Street opens at noon. | good
```

This is the third trigger from Principle 1: a `<Suspense>` boundary that switches from its fallback to its content. The docs: "If it's inside a new Suspense boundary instance, then the fallback is shown first. After the Suspense boundary fully loads, it triggers the `<ViewTransition>` to animate the reveal to the content."

### The type of the tap does not reach the reveal

The docs: "Transition Types are reset after each commit. This means a `<Suspense>` fallback will associate the types after a `startTransition`, but revealing the content does not."

The reveal is a later commit with no type. So a class picked by `nav-forward` cannot style it. The text simply cross-fades, with the browser's default animation.

React also waits for what the new screen needs before it starts an animation. The docs: "ViewTransitions also wait up to 500ms for new fonts to load before starting the animation". And "an image wrapped in ViewTransition will wait for the image to load". So the large park image does not appear in pieces while it grows.

### VS | Around the boundary vs. inside the fallback and the content: one update, or an exit and an enter

There are two places to put `<ViewTransition>` near a `<Suspense>` boundary. Both versions hold the same loading line and the same text. The one difference is how many `<ViewTransition>` there are.

```jsx title="ViewTransition around the Suspense boundary"
~<ViewTransition>~ {/* One ViewTransition holds the loading line first and the text after */}
  <Suspense fallback={<p>Loading article...</p>}>
    <ArticleText article={article} />
  </Suspense>
</ViewTransition>
```

```jsx title="ViewTransition inside the fallback and inside the content"
<Suspense fallback={<ViewTransition><p>Loading article...</p></ViewTransition>}>
  ~<ViewTransition>~ {/* A second ViewTransition, with its own name, holds only the text */}
    <ArticleText article={article} />
  </ViewTransition>
</Suspense>
```

Both versions animate the swap from the loading line to the text, but they are NOT the same thing!
- **With one `<ViewTransition>` around `<Suspense>`**, it holds the loading line first and the text after. The docs: "it'll be treated as an 'update'". The two "will get the same view-transition-name and therefore they're acting as a cross-fade by default."
- **With `<ViewTransition>` inside the fallback and inside the content**, there are two `<ViewTransition>`, each with its own name. The docs treat this as an "exit" of the fallback and an "enter" of the content.

The second way is useful when the two should move differently, such as the loading line sliding down and the text sliding up. React's blog does this with `exit="slide-down"` on the fallback's `<ViewTransition>`. The content's `<ViewTransition>` gets `enter="slide-up"`.

### One `<Suspense>` around the whole article page

**Beware! If the `<Suspense>` boundary also holds the large image, the park image no longer grows from the list. It simply appears with the text.**

A developer has learned to wrap a whole slow part of the page in one `<Suspense>` (Lesson 69). So they move the boundary up into `App`, around the whole `ArticlePage`:

```jsx title="src/App.jsx" startLine="26"
{article ? (
  ~<Suspense fallback={<p>Loading article...</p>}>~ {/* **WRONG:** the large named image now waits behind the fallback */}
    <ArticlePage article={article} onBack={handleBack} />
  </Suspense>
) : (
  <Home articles={articles} onOpen={handleOpen} />
)}
```

Here is what happens when the user taps `New Park Opens`:
1. The Transition removes the list, and the small image named `article-1` with it.
2. The new boundary in `App` shows its fallback first, because `ArticleText` inside the page is still waiting.
3. The large image named `article-1` is inside the boundary, so it is not on the page yet.
4. The name `article-1` left, but no `article-1` arrived in the same Transition. No pair forms.
5. The text arrives later. The large image and the text appear together, and no image moves from the list.

This is exactly the case the docs describe. "If Transition first unmounts one side and then leads to a `<Suspense>` fallback being shown before eventually the new name being mounted, then no shared element transition happens."

The Console shows no error. The only sign is that the animation from Principle 3 is gone. The fix is the version we already built: keep `<ArticleImage>` outside the boundary, and put `<Suspense>` only around the text.

Remember: what must travel stays outside the boundary. Only what waits goes inside.

## All 6 Principles Together

### The complete files

Here is the finished `App`. Both handlers start a Transition and name its cause, and one `<ViewTransition>` wraps both screens:

```jsx title="src/App.jsx"
import { ViewTransition, startTransition, addTransitionType, useState } from 'react';
import Home from './Home.jsx';
import ArticlePage from './ArticlePage.jsx';
import { articles } from './articles.js';
import './App.css';

export default function App() {
  const [article, setArticle] = useState(null);

  function handleOpen(next) {
    ~startTransition~(() => { // Principles 1 and 2: a Transition, so React calls the browser
      addTransitionType('nav-forward');
      setArticle(next);
    });
  }

  function handleBack() {
    startTransition(() => {
      ~addTransitionType('nav-back')~; // Principle 5: going back slides the other way
      setArticle(null);
    });
  }

  return (
    <ViewTransition ~default={{ 'nav-forward': 'slide-forward', 'nav-back': 'slide-back' }}~> {/* Principles 4 and 5: one class per type */}
      {article ? (
        <ArticlePage article={article} onBack={handleBack} />
      ) : (
        <Home articles={articles} onOpen={handleOpen} />
      )}
    </ViewTransition>
  );
}
```

The list screen:

```jsx title="src/Home.jsx"
import ArticleImage from './ArticleImage.jsx';

export default function Home({ articles, onOpen }) {
  return (
    <section>
      <h1>News</h1>
      <ul>
        {articles.map(article => (
          <li key={article.id}>
```

When the page loads, `article` is `null`. React calls `App` and then `Home`. `Home` renders one `ArticleImage` for each row. When the user taps a row, React calls `ArticlePage` and its `ArticleImage`. Then it calls `ArticleText`, which waits behind its `<Suspense>`:

| Aspect | Without the rule | With the rule |
| :--- | :--- | :--- |
| **The trigger** | A plain setter: the screen cuts, with no error | A setter inside `startTransition`: the screens animate |
| **Who animates** | Our own `document.startViewTransition`: the `<ViewTransition>` never takes part | React calls `startViewTransition`, and the browser runs the animation |
| **The image** | No `name`, or one fixed `name` for every row and two Console errors | The same `name` from the `id` on both images: the image moves and grows |
| **The style** | CSS on generated names, and full motion for every user | A View Transition Class on the prop, and `prefers-reduced-motion` |
| **The direction** | One slide class, so going back looks like going forward | `addTransitionType` and one class per type |
| **The loading text** | One `<Suspense>` around the whole page: the image no longer travels | `<ViewTransition>` around a `<Suspense>` that holds only the text |

Remember the one sentence of this lesson. **`<ViewTransition>` says what may animate, and `startTransition` says when. React calls the browser at the right moment, and the browser animates the change of screen.**

## For the Interview

> **The Interview Question:** How do you animate between two screens with ViewTransition?

### How to Answer Clearly in 30 Seconds

"I wrap the part that changes in `<ViewTransition>`, imported from `react`, and I make the change of screen inside `startTransition`. `<ViewTransition>` says what may animate, and a trigger says when. There are three triggers:
1. **A Transition**, such as `startTransition` or a router that navigates inside one.
2. **A `<Suspense>` reveal**, when the fallback switches to the content.
3. **`useDeferredValue`**, when the deferred value catches up.

A plain `setState` is none of these, so the screen just cuts. Behind the scenes, React writes `view-transition-name` on the DOM nodes taking part and calls the browser's `startViewTransition`. So I never call it myself. By default, the browser cross-fades the two screens.

To make an item grow from a list into its detail page, I give both sides the same `name`, built from the item's id. I style animations with View Transition Classes, with a `prefers-reduced-motion` media query."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"I wrapped my app in `<ViewTransition>`, and nothing animates. Why?"**
   Because the update is not a trigger. The docs: "By default, `setState` updates immediately and does not activate `<ViewTransition>`." Only a Transition, a `<Suspense>` reveal, or `useDeferredValue` activates it. Put the setter, or the router's navigation, inside `startTransition`. A related trap is the browser's own Back button: the docs say "React will skip animations from popstate". The fix is a router that uses the Navigation API.
2. **"How do you make a thumbnail in a list grow into the large image on the detail page?"**
   I wrap both images in a `<ViewTransition>` with the same `name`. One Transition removes the named one in the list and adds the named one on the page. React then runs a shared element transition, and the browser moves and scales the snapshot. Three things break it:
   1. **The same name mounted twice.** Every row needs its own name, such as one built from the item's id, or React logs two errors.
   2. **One side outside the viewport.** The docs: "If either the mounted or unmounted side of a pair is outside the viewport, then no pair is formed."
   3. **A `<Suspense>` fallback in between.** If the named side mounts only after a fallback, "no shared element transition happens."
3. **"How do you make going back animate differently from going forward?"**
   Inside `startTransition`, I call `addTransitionType` with a string such as `'nav-back'`. On the `<ViewTransition>`, a prop such as `default` takes an object with one View Transition Class for each type. React applies the class that matches. Types are reset after each commit, so a later `<Suspense>` reveal does not carry them. For animations that CSS cannot express, `<ViewTransition>` also has `onEnter`, `onExit`, `onUpdate`, and `onShare`. They drive the animation from JavaScript with the Web Animations API.

```tree dir=right caption="Interview comparison: a plain setter, the browser API called by hand, and ViewTransition with a Transition."
Three ways to change the screen in a React app
- !A plain setter | Not a trigger | The screen **cuts**, with **no error**
- !`document.startViewTransition` by hand | Runs **outside React's timing** | The `<ViewTransition>` **never takes part**
- +`<ViewTransition>` with `startTransition` | React calls **`startViewTransition`** at the right moment | The browser **cross-fades**, and a shared `name` makes the image **move and grow**
```
