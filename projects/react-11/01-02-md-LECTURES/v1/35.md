# Lecture 35: The Lifecycle of an Effect as Its Dependencies Change

*(What happens to an Effect when a prop changes, but the component stays on the page?)*

> INTERVIEW QUESTION | ❱ CORE | What is the lifecycle of a reactive effect as its dependencies change?

---

## VS | A Component's Lifecycle vs. an Effect's Lifecycle: the component mounts once, the Effect starts and stops for every room

> **An Effect stops and starts again every time a value in its dependency array changes, even while the component stays on the screen.**

In React, a component often stays on the screen while one of its values changes, like a chat box when the user picks another room, a map when the user types another city, or a product page when the user picks another size. We usually picture an Effect in two moments: it starts when the component appears, and it stops when the component leaves. But the component is not the only thing with a lifecycle. **An Effect has its own: whenever a value in its dependency array changes, React stops the old Effect and starts a new one with the new value.**

Take a chat app with rooms, like Slack: general, travel, and music. While the user reads a room, the browser stays connected to the chat server for that room. The user reads the general room, then picks music from the menu at the top. The chat box never leaves the screen. Ask yourself: who closes the general room and opens the music room, if the component never appears or leaves again? Let's follow what React does, step by step:

> music picked → handler calls `setRoomId('music')` → component renders again → React compares `roomId`, `'general'` before and `'music'` now → cleanup disconnects from general → Effect connects to music

**Why:** If the Effect ran only when the chat box appeared, picking a new room would do nothing, and the user would keep talking in the general room. If it opened the music room without closing the general room first, messages from both rooms would pour into the same screen. **Therefore, you need to keep in mind that the connection follows the room, not the chat box.** That is why React stops and starts the Effect each time `roomId` changes.

### The Room Switch in Plain JavaScript

In plain JavaScript, you would write the room switch yourself. You keep the connection in a variable. When the user picks another room, you close the old connection, and then you open a new one:

```js title="Plain JavaScript: you switch the room by hand"
let connection = createConnection(serverUrl, 'general');
connection.connect();

roomMenu.addEventListener('change', () => {
  ~connection.disconnect()~; // First, close the old room
  connection = createConnection(serverUrl, roomMenu.value);
  ~connection.connect()~; // Then, open the new room
});
```

Notice the order: close the old room first, then open the new one. Forget the first line, and the user stays connected to both rooms.

In React, you do not write the switch. You write two things inside one Effect: how to connect, and how to disconnect. React calls them in the right order, every time the room changes:

```jsx title="React: you write the start and the stop, React does the switch"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  ~connection.connect()~; // How to start: connect to this room
  return () => {
    ~connection.disconnect()~; // How to stop: disconnect from this room
  };
}, ~[roomId]~); // When roomId changes, React runs the stop for the old room, then the start for the new one
```

The React docs say it in two sentences: "Your Effect's body specifies how to start synchronizing, and your cleanup function specifies how to stop synchronizing. All that React needs to do now is to call them in the correct order and with the correct props and state."

> [!DEFINITION]
> **What is an Effect, and what is its cleanup?** [REVIEW] An Effect is code that React runs because the component is on the screen, not because the user clicked.
> You write it with `useEffect`. React runs it last: first it calls your component, then it puts the result into the DOM, and only then does it run the Effect.
> The function you pass to `useEffect` is the setup. It starts something outside React, such as a connection to a chat server.
> The function that the setup returns is the cleanup. It stops that same thing: it disconnects the exact connection that the setup opened (Lesson 32).

> [!DEFINITION]
> **What is the dependency array?** [REVIEW] It is the array at the end of `useEffect`, such as `[roomId]`. It lists the values the Effect reads.
> After every render, React compares each value with the one from the last render, using `Object.is`.
> If every value is the same, React skips the Effect. If even one value changed, React runs the Effect again.
> With `[]`, nothing can ever change, so the Effect runs once, when the component appears. With no array at all, the Effect runs after every render (Lesson 32).

### A component mounts, updates, and unmounts. An Effect only starts and stops.

A lifecycle is the list of stages something goes through over time. The docs put the rule of this lesson in three sentences: "Effects have a different lifecycle from components. Components may mount, update, or unmount. An Effect can only do two things: to start synchronizing something, and later to stop synchronizing it."

So there are two lifecycles on the same page:
- **The component's lifecycle** has three stages. It mounts when React adds it to the screen (Lesson 13). It updates when it renders again with new props or state. It unmounts when React removes it from the screen (Lesson 32).
- **The Effect's lifecycle** has two steps. The setup starts: it connects. The cleanup stops: it disconnects. This pair can repeat many times while the component stays on the page.

On the first visit, the two look the same. The component mounts, and the Effect connects to `general`.

The moment the user picks `travel`, they split. The component does not unmount. It only updates: the heading changes from general to travel. But the Effect must stop and start again: disconnect from `general`, then connect to `travel`.

> [!DEFINITION]
> **What does re-synchronizing mean?** [NEW] Re-synchronizing is the docs' word for one stop followed by one start.
> When `roomId` changes from `general` to `travel`, the open connection no longer matches the screen. So React runs the old cleanup, which disconnects from `general`, and then the new setup, which connects to `travel`.
> The component stays on the page the whole time. Only the Effect stops and starts.
> Every change of a dependency re-synchronizes the Effect once (Lesson 35).

```tree caption="A component mounts, updates, and unmounts; an Effect repeats one stop and one start for every new room."
Two lifecycles on the same chat page
- +The component's lifecycle [`mount` `update` `unmount`] | **Mounts** once, **updates** when `roomId` changes, **unmounts** when the chat closes | Stays **on the page** while the user switches rooms
- +The Effect's lifecycle [`useEffect`] | The setup **connects**, the cleanup **disconnects** | Repeats one **stop and start** every time `roomId` changes
```

### The Rule of Thumb: one start, one stop, and every value the Effect reads in the array

**Write the setup as "connect to this room". Write the cleanup as "disconnect from this room". Put every value the Effect reads in the array. React does the rest.**

The goal is simple: the heading on the screen and the connection behind it must always agree on which room the user is in. A senior developer knows the five classic mistakes that break this:
1. **"The cleanup is the unmount code."** Then the cleanup that runs on every room switch comes as a surprise. The docs even have a troubleshooting entry for it: "My cleanup logic runs even though my component didn't unmount".
2. **"The cleanup sees the new `roomId`."** It does not. It still holds the old room, and that is exactly what it needs to disconnect.
3. **"The Effect needs no cleanup."** Then every switch leaves the old room connected, and the user ends up in two rooms at once.
4. **"Leave `roomId` out of the array, so the Effect runs only once."** The heading says travel, and the connection stays on general. The docs: "You will remain connected to the initial `roomId` and `serverUrl` even after the user picks different values in the UI."
5. **"Put the visit log inside the connection Effect, since both run when the user enters a room."** Then an edit of the server address logs a visit to a room the user never left.

The rest of the lesson shows each mistake on a real chat page.

`ChatRoom` holds the Effect. The server address never changes, so it is a constant above the component:

```jsx title="src/components/ChatRoom.jsx"
import { useEffect } from 'react';
import { createConnection } from '../chat.js';

const ~serverUrl~ = 'https://localhost:1234'; // A fixed address, outside the component

export default function ChatRoom({ ~roomId~ }) { // general, travel, or music, from App
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    ~connection.connect()~; // Start: connect to this room
    return () => {
      ~connection.disconnect()~; // Stop: disconnect from this room
    };
  }, ~[roomId]~); // A new room means one stop and one start
  return <h1>Welcome to the {roomId} room!</h1>;
}
```

**PRINCIPLES:** An Effect does only two things: it starts, and it stops. Every time a dependency changes, React stops the old Effect and starts a new one. Five principles follow:
1. **Principle 1: An Effect Starts and Stops, It Does Not Mount.** The component mounts once, yet the Effect connects three times. Think about one connect and one disconnect at a time.
2. **Principle 2: The Old Cleanup Runs Before the New Setup.** On a switch to travel, React first disconnects from general, with the old `roomId`. Without a cleanup, the old room stays connected.
3. **Principle 3: Every Value the Effect Reads Goes in the Array.** With `[]` and a silenced linter, the heading says travel, and the chat stays on general.
4. **Principle 4: Values from the Component Body Are Reactive.** A `serverUrl` in state joins the array. A constant outside the component does not, and `ref.current` cannot.
5. **Principle 5: One Effect for Each Job.** The visit log gets its own Effect, so an edit of the server address does not log a false visit.

## PRINCIPLE | `useEffect`: one connect and one disconnect for each room, while the component stays mounted

> [!PRINCIPLE]
> **Principle 1: An Effect Starts and Stops, It Does Not Mount**
>
> *Think about one start and one stop at a time. The setup connects to this room, and the cleanup disconnects from it, no matter whether the component is mounting, updating, or unmounting.*
>
> For the component, opening the chat, picking two rooms, and closing the chat is one mount, two updates, and one unmount. For the Effect, it is three connections in a row: general, travel, and music. Write the Effect as "connect, then disconnect", and React can repeat it every time the room changes.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   ~return () => connection.disconnect();~ // Stops exactly what this setup started
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** written as "connect on mount", so a new room never reconnects
> ```

### VS | The component's view vs. the Effect's view: four moments vs. three connections

The docs take the same four clicks and describe them twice: once as the component sees them, and once as the Effect sees them.

The component sees four moments:
1. `ChatRoom` mounted with `roomId` set to general.
2. `ChatRoom` updated with `roomId` set to travel.
3. `ChatRoom` updated with `roomId` set to music.
4. `ChatRoom` unmounted.

The Effect sees three connections:
1. It connected to the general room, until it disconnected.
2. It connected to the travel room, until it disconnected.
3. It connected to the music room, until it disconnected.

Count them: four moments for the component, three connections for the Effect. Mount, update, and unmount are useful words for a component. The docs warn: "It's a good way to think about components, but _not_ about Effects."

If you think of an Effect as "code after mount" and "code before unmount", the docs say it "gets complicated very fast." Their simpler rule: "always focus on a single start/stop cycle at a time. It shouldn't matter whether a component is mounting, updating, or unmounting."

```tree caption="The same four clicks seen by the component vs. seen by the Effect: four moments vs. three connections."
Four clicks across three rooms
- !The component's view [`ChatRoom`] | 1. Mounted with `general` | 2. Updated with `travel` | 3. Updated with `music` | 4. Unmounted
- +The Effect's view [`useEffect`] | 1. Connected to `general`, until it disconnected | 2. Connected to `travel`, until it disconnected | 3. Connected to `music`, until it disconnected
```

### One mount, three connections

**`ChatRoom` mounts only once, yet the Effect connects three times.** Here is what React does for each click:
1. **Open chat.** `App` renders `ChatRoom` for the first time, with the general room. `ChatRoom` mounts, shows the general heading, and the setup connects to `general`.
2. **Pick `travel`.** `App` passes travel to the same `ChatRoom`. It does not mount again. It only changes its heading text. Then React runs the old cleanup, which disconnects from `general`, and the new setup, which connects to `travel`.
3. **Pick `music`.** The heading text changes again. React runs the cleanup of the travel render, then the setup of the music render.
4. **Close chat.** `App` stops rendering `ChatRoom`, so it unmounts. React runs the last cleanup one final time, which disconnects from `music`.

You can check that the component never mounted again. Open the Elements panel and switch rooms: the `<h1>` element stays in the DOM, and only its text changes.

What if an Effect returns no cleanup at all? The docs: "React will behave as if you returned an empty cleanup function." So for React, it is the same thing: there is still a stop step, and that step does nothing. For our chat, it means nobody ever calls `disconnect`, and every room stays connected. Principle 2 shows this bug.

### The bug: "connect on mount, disconnect on unmount"

Thinking in component lifecycles leads straight to a broken chat:
1. A developer looks at `ChatRoom` and thinks: connect when the component mounts, disconnect when it unmounts.
2. Mount and unmount happen once each, so the developer writes `[]` as the dependency array (Lesson 32).
3. The user clicks Open chat. `ChatRoom` mounts with general, and the Effect connects to general.
4. The user picks `travel`. `ChatRoom` does not unmount and does not mount again. It only updates. So the Effect never disconnects from `general` and never connects to `travel`. Principle 3 fixes this array.

The fix is a change of mindset. When you write JSX, you never ask "is this the first render or an update?" You describe what the screen should show, and React figures out the rest. An Effect works the same way. The docs: "The Effect is *also* a part of the rendering output."

So you describe only how to start and how to stop. The docs: "If you do it well, your Effect will be resilient to being started and stopped as many times as it's needed." The key: "When your cleanup logic correctly "mirrors" the setup logic, your Effect is resilient to running setup and cleanup as often as needed."

## PRINCIPLE | The cleanup function: the old room disconnects before the new room connects

> [!PRINCIPLE]
> **Principle 2: The Old Cleanup Runs Before the New Setup**
>
> *When a dependency changes, React first runs the old cleanup with the old values, then the new setup with the new values.*
>
> Every render keeps its own `roomId`. On a switch to travel, the cleanup that React calls was created by the general render, so it disconnects from general. Only then does the travel setup connect to travel. Without a cleanup, nothing disconnects, and every switch adds one more open connection.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   ~return () => connection.disconnect();~ // Closes the old room before the new setup runs
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   ~connection.connect();~ // **WRONG:** no cleanup, so every new room leaves the old one connected
> }, [roomId]);
> ```

### When React calls the setup and the cleanup

The `useEffect` reference gives the exact timing, in three moments:
1. **When the component mounts:** "Your setup code runs when your component is added to the page."
2. **After every render with a changed dependency:** "First, your cleanup code runs with the old props and state. Then, your setup code runs with the new props and state."
3. **When the component unmounts:** "Your cleanup code runs one final time after your component is removed from the page."

Moment 2 is the one this lesson is about. It is also where the cleanup surprises people. The docs' troubleshooting entry says it plainly: "The cleanup function runs not only during unmount, but before every re-render with changed dependencies."

### VS | The new setup vs. the old cleanup: the same name `roomId`, two different rooms

Look at the two functions again:

```jsx title="The setup and the cleanup inside ChatRoom.jsx"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // The roomId of the render that ran this setup
  connection.connect();
  return () => {
    ~connection.disconnect()~; // Disconnects the connection made with that same roomId
  };
}, [roomId]);
```

Both functions sit in the same `useEffect`. When the user picks travel, it is easy to think that both now see `travel`. They do not.

**The heading already says travel, and then the Console prints a disconnect line for general.** Here is the order:
1. The user picks `travel`, and `setRoomId` asks React for a new render.
2. `App` renders and passes travel to `ChatRoom`. React puts the travel heading into the DOM.
3. React compares the new array `['travel']` with the old `['general']`. They differ. So in the docs' words, "The Effect can't be skipped."
4. React calls the cleanup that the general setup returned. It disconnects the general connection.
5. React calls the setup of the travel render. It connects to `travel`.

The docs put the rule in bold: "**React always cleans up the previous render's Effect before the next render's Effect.**"

```tree dir=right caption="What React runs after a render where roomId changed from general to travel."
React re-synchronizes when `roomId` changes from `general` to `travel`
- +1. Update the screen [`Welcome to the travel room!`] | React puts the new heading text **into the DOM first**
- +2. Run the OLD cleanup [`roomId` is `general`] | Calls `disconnect` from the **general render**
- +3. Run the NEW setup [`roomId` is `travel`] | Calls `connect` from the **travel render**
```

### Why the cleanup still holds general

> [!DEFINITION]
> **What is a render's snapshot?** [REVIEW] Every render is one call of your component function.
> In that call, props and state have fixed values. Every function created during that call, including an Effect and its cleanup, sees those values forever.
> A later render is a new call, with new values, and new functions.
> So a function from an old render still sees the old values, even after the screen shows new ones (Lesson 15).

In the first render, `roomId` was `general`. So the Effect of the first render, and the cleanup it returned, captured `general`. In the docs' words, each Effect "captures" the value "from its corresponding render." If you could look inside that first Effect, you would see this:

```jsx title="The first render's Effect, with general captured"
() => {
  const connection = createConnection(serverUrl, ~'general'~); // Captured in the first render
  connection.connect();
  return () => ~connection.disconnect()~; // Always disconnects the general connection
}
```

That is exactly what you want. The cleanup must close the connection that its own setup opened, and that connection belongs to general.

The same holds at the end. When the user clicks Close chat in the music room, `ChatRoom` unmounts. React calls the cleanup of the music render one final time, and it disconnects from `music`.

1. React runs the setup for `general`. The first connect line appears.
2. React calls its cleanup right away. The disconnect line appears.
3. React runs the setup for `general` once more. The second connect line appears.

### A render with the same room skips the Effect

Suppose `ChatRoom` renders again while `roomId` is still general. Nothing reconnects. React compares the second render's `['general']` with the first render's `['general']`, and they are equal. The docs: "**Because all dependencies are the same, React *ignores* the Effect from the second render.** It never gets called."

Now a third render changes `roomId` to travel. Which cleanup runs? The second render's Effect never ran, so it has no cleanup. In the docs' words, React "needs to clean up the last Effect that _did_ run." That is the first render's Effect, so its cleanup disconnects from general.

### The bug: no cleanup function

**Without a cleanup, a switch from general to travel never closes general. The user is connected to both rooms at once.** Here is what happens when the `return` is missing:
1. The setup connects to the room and returns nothing.
2. The user picks `travel`. The page shows the travel heading. React has no cleanup to call for general.
3. React runs the travel setup. The Console shows a connect line for travel, with no disconnect line before it.
4. The general connection stays open in the background. Every new room adds one more open connection.

## PRINCIPLE | `[roomId]` in the dependency array: the Effect follows every room change

> [!PRINCIPLE]
> **Principle 3: Every Value the Effect Reads Goes in the Array**
>
> *List every reactive value the Effect reads in its dependency array, and never silence the `exhaustive-deps` linter to make the array shorter.*
>
> React runs the Effect again only when an item in the array changes, compared with `Object.is`. With `[]`, nothing can change, so the first render's Effect stays alive forever. The app stays connected to the first room, while the heading shows the new one.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId]~); // Lists roomId, so a new room reconnects
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** tells React the Effect reads nothing that can change
> ```

### VS | `[roomId]` vs. `[]`: the same connection code, only one follows the menu

Both Effects below run the same setup and the same cleanup. Only the last line differs:

```jsx title="roomId in the dependency array"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // Tells React: this Effect depends on roomId
```

```jsx title="roomId left out of the dependency array"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
  connection.connect();

}, ~[]~); // **WRONG:** tells React: this Effect depends on nothing
```

When the user clicks Open chat, both connect to general. Same screen, same Console. The difference appears on the first switch. With `[roomId]`, React disconnects from general and connects to travel. With `[]`, React does nothing, and the app stays on general.

How did React know to reconnect in the first version? It knew because you told it. The docs: "It's because *you told React* that its code depends on `roomId` by including it in the list of dependencies." They give your reasons in three steps:
1. "You knew `roomId` is a prop, which means it can change over time."
2. "You knew that your Effect reads `roomId`."
3. "This is why you specified it as your Effect's dependency."

So the array is not a setting you pick. It is a list of facts about your code. The docs put it in bold: "**You can't "choose" your dependencies.**" The `exhaustive-deps` lint rule reads your Effect and checks the list for you. Here is its own example:

```jsx title="The exhaustive-deps example: a missing userId vs. a complete array"
useEffect(() => {
  fetchUser(~userId~); // Reads userId
}, ~[]~); // **WRONG:** Missing 'userId' in the dependency array

useEffect(() => {
  fetchUser(~userId~); // Reads userId
}, ~[userId]~); // Runs again when userId changes
```

And `[roomId]` is not the same as no array at all. With no array, the Effect runs after every render of the component (Lesson 32). The docs' first challenge shows the cost. `ChatRoom` gets an `<input>` field for a chat message. With no array, every letter the user types renders the component, and "*also* reconnects to the chat".

```tree caption="Three ways to end the useEffect call when the Effect reads roomId."
Three endings for an Effect that reads `roomId`
- +With `[roomId]` | Lists the value the Effect reads | Reconnects **only when `roomId` changes**
- !With `[]` | ~Leaves `roomId` out | Never reconnects, **stuck on general**
- !With no array | ~No dependency array at all | Reconnects **after every render**, even on every typed letter
```

### The name for this bug: a stale closure

> [!DEFINITION]
> **What is a stale closure?** [NEW] A closure is a function that remembers the variables of the place where it was created. Every function in JavaScript does this.
> A stale closure is a function from an old render that still holds the old values. "Stale" means out of date.
> The `exhaustive-deps` docs name it: a missing dependency "causes stale closures where the hook uses outdated values."
> In the docs' challenge, a pointer listener inside an Effect reads `canMove`, and the linter is silenced. With an empty array, the listener "from the initial render will forever see" `canMove` as true, even after the user unticks the checkbox (Lesson 35).

### What to do when an Effect runs too often

Why does an Effect run again at all? The docs: "Effects are reactive blocks of code." And they compare them with event handlers: "Unlike event handlers, which only run once per interaction, Effects run whenever synchronization is necessary."

If you want the Effect to act only in some cases, put the condition inside the Effect. Never wrap the `useEffect` call itself in an `if`. The docs: "You can't declare an Effect conditionally. However, the code inside the Effect can use conditions!" That keeps the Hook at the top level of the component, as the rules of Hooks require (Lesson 38).

And if the linter asks for a value that makes the Effect run too often? Do not silence it. Change the code, so the Effect no longer needs that value. The docs: "The linter only knows when the dependencies are *wrong*. It doesn't know *the best* way to solve each case." But "All errors flagged by the linter are legitimate." Two ways to change the code come in the next lessons:
1. Read the latest value inside an Effect Event, without a reconnect (Lesson 36).
2. Stop depending on an object or a function that is created again on every render (Lesson 37).

## PRINCIPLE | `[roomId, serverUrl]`: every prop, state, and body variable the Effect reads goes in the array

> [!PRINCIPLE]
> **Principle 4: Values from the Component Body Are Reactive**
>
> *Props, state, and variables calculated in the component body can change on a re-render, so they go in the array. Constants outside rendering stay out, and values that change without a render, such as `ref.current`, cannot be dependencies.*
>
> A value is reactive when React calculates it during rendering. Move `serverUrl` from the top of the file into state, and it can change on a re-render, so the array becomes `[roomId, serverUrl]`. A change to `ref.current` or `location.pathname` never renders the component, so React never even looks at the array.
>
> **DO THIS:**
> ```jsx
> function ChatRoom({ roomId }) {
>   const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // State: reactive
>   useEffect(() => {
>     const connection = createConnection(serverUrl, roomId);
>     connection.connect();
>     return () => connection.disconnect();
>   }, ~[roomId, serverUrl]~); // Both reactive values the Effect reads
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ChatRoom({ roomId }) {
>   const [serverUrl, setServerUrl] = useState('https://localhost:1234');
>   useEffect(() => {
>     const connection = createConnection(serverUrl, roomId);
>     connection.connect();
>     return () => connection.disconnect();
>   }, ~[roomId]~); // **WRONG:** serverUrl is state now, so a new address never reconnects
> }
> ```

### VS | `serverUrl` above the component vs. `serverUrl` in state: the same call, only one is reactive

So far, `serverUrl` was a constant above the component. Now we want the user to edit the server address. So we move it into state:

```jsx title="serverUrl above the component: not reactive"
const ~serverUrl~ = 'https://localhost:1234'; // Outside the component: no render can change it

function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId]~); // Only roomId can change
}
```

```jsx title="serverUrl in state: reactive"
function ChatRoom({ roomId }) {
  const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // Inside the component: can change

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId, serverUrl]~); // Both can change, so both are listed
}
```

The call to `createConnection` is the same, letter for letter. Both start with the same address. The difference is where `serverUrl` lives.

Above the component, the address "never changes due to a re-render", so the array is `[roomId]`. In state, the address "may change over time", so it joins the array. The docs sum it up: "dependencies only do something when they change over time!"

> [!DEFINITION]
> **What is a reactive value?** [NEW] A reactive value is a value that can change from one render to the next. The docs, in bold: "Props, state, and other values declared inside the component are _reactive_".
> Why? Because React calculates them during rendering. On each render, React passes in the props, reads the state, and runs your component body from top to bottom. The docs call this the rendering data flow.
> Every value that comes out of that flow can be different next time, so an Effect that reads it must list it.
> A constant at the top of the file is outside that flow, so it is not reactive (Lesson 35).

### Which values go in the array, and which do not

The docs sort every value an Effect can read into four kinds:
1. **Reactive values: they go in the array.** Props, state, and every variable calculated in the component body.
2. **Constants outside rendering: they stay out.** A constant above the component, or declared inside the Effect, is never calculated during rendering.
3. **Stable values: you may leave them out.** React guarantees that some values do not change "on a re-render": the setter from `useState` and the ref object from `useRef` (Lesson 30). The docs: "Stable values aren't reactive, so you may omit them from the list. Including them is allowed." That is why the linter never asks for `setServerUrl`.
4. **Mutable values: they cannot be dependencies.** Values such as `location.pathname` or `ref.current` "can change at any time completely outside of the React rendering data flow." A change to them does not render the component.

```tree caption="Which values an Effect reads go in the dependency array, and which do not."
Four kinds of values an Effect can read
- +Props, state, and body variables [`roomId` `serverUrl`] | Calculated **during rendering** | **Reactive**: they go in `[roomId, serverUrl]`
- +Constants outside rendering [`const serverUrl` at the top of the file] | No render **can change** them | **Not reactive**: they stay out
- +Stable values from React [`setServerUrl` `ref` object] | Guaranteed **not to change** on a re-render | **Stable**: listed or not, both are allowed
- !Mutable values [`location.pathname` `ref.current`] | ~Change **outside the rendering data flow** | **Cannot be dependencies**: a change never renders the component
```

### A variable calculated in the body is reactive too

A value does not have to be a prop or state to be reactive. A plain `const` in the component body counts too. Here is the docs' example: `serverUrl` comes from a prop, or, when the prop is empty, from a context value read with `useContext` (Lesson 28). The `??` operator picks the context value when the prop is empty, that is, null or undefined:

```jsx title="A variable calculated in the body is reactive"
function ChatRoom({ roomId, selectedServerUrl }) {
  const settings = useContext(SettingsContext);
  const ~serverUrl~ = selectedServerUrl ?? settings.defaultServerUrl; // Calculated during rendering, so reactive

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, [roomId, ~serverUrl~]); // Listed, because the next render can calculate a new address
}
```

The docs explain why it is reactive: "It's a regular variable that you calculate during rendering". The next render can calculate a different address, just like a new prop.

### `[]` means "this Effect reads no reactive values"

When neither the address nor the room depends on props or state, you can declare both as constants, either above the component or inside the Effect:

```jsx title="Constants above the component"
const ~serverUrl~ = 'https://localhost:1234'; // Outside the component: not calculated during rendering
const roomId = 'general';

function ChatRoom() {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // Reads no reactive values
}
```

```jsx title="Constants inside the Effect"
function ChatRoom() {
  useEffect(() => {
    const ~serverUrl~ = 'https://localhost:1234'; // Inside the Effect: not calculated during rendering
    const roomId = 'general';
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // The same empty array
}
```

For the array, both are exactly the same thing. The docs: "They aren't calculated during rendering, so they're not reactive." This is the honest way to remove a dependency: move the value out of the component, or into the Effect. In the words of the `useEffect` reference, "you need to "prove" to the linter that it *doesn't need* to be a dependency."

It also shows what `[]` really means. It does not mean "run only on mount". It means "your Effect's code does not use *any* reactive values." And if the room or the address later moves into state, "your Effect's code won't change. You will only need to add them to the dependencies."

### Four ways to handle a value an Effect reads

Put together, the docs give four ways to handle any value an Effect reads:
1. **List it in the array.** It fits a reactive value, such as `roomId`. React re-synchronizes the Effect whenever it changes.
2. **Move it above the component.** It fits a fixed constant, such as a fixed `serverUrl`. It leaves the array.
3. **Move it inside the Effect.** It fits a helper value that only the Effect uses and that does not depend on props or state. It leaves the array.
4. **Read it in an Effect Event.** It fits a prop or state value whose latest value the Effect needs without a reconnect. Lesson 36 covers `useEffectEvent`.

```tree caption="The four places a value read by an Effect can live, and what each one means for the array."
Four ways to handle a value an Effect reads
- +1. Keep it in the body and list it [`[roomId]`] | Can change on a **re-render** | React **re-synchronizes** when it changes
- +2. Move a fixed constant above the component [`const serverUrl` at the top of the file] | No render **can change** it | It **leaves the array**
- +3. Move a helper value inside the Effect [declared inside `useEffect`] | Created **when the Effect runs**, not during rendering | It **leaves the array**
- +4. Read it in an Effect Event [`useEffectEvent`] | Reads the **latest value** without a reconnect | Covered in **Lesson 36**
```

### The Server URL field: every letter reconnects

Now `ChatRoom` keeps the address in state, with a controlled `<input>` field (Lesson 20). And `serverUrl` joins the array:

```jsx title="src/components/ChatRoom.jsx"
import { useState, useEffect } from 'react';
import { createConnection } from '../chat.js';

export default function ChatRoom({ roomId }) {
  const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // Reactive state

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => {
      connection.disconnect();
    };
  }, ~[roomId, serverUrl]~); // A new room or a new address means one stop and one start

  return (
    <section>
      <label>
        Server URL:{' '}
        <input
          ~value={serverUrl}~ // The field shows the address in state
          ~onChange={e => setServerUrl(e.target.value)}~ // Every typed letter stores a new address
        />
      </label>
      <h1>Welcome to the {roomId} room!</h1>
    </section>
  );
}
```

**Now every letter the user types in the Server URL field disconnects from the old address and connects to the new one.** Here is what happens when the user types `5` at the end of the address:
1. The user types `5`. The field now shows `https://localhost:12345`.
2. `setServerUrl` stores the new address, and React renders `ChatRoom` again.
3. React compares the new array with the old one, using `Object.is`. `serverUrl` changed.
4. React runs the old cleanup. It disconnects from `https://localhost:1234`.
5. React runs the new setup. It connects to `https://localhost:12345`.

### Why `ref.current` and `location.pathname` cannot be dependencies

**A mutable value in the array never makes the Effect run again when it changes.** The docs' deep dive "Can global or mutable values be dependencies?" explains it in four steps:
1. A developer wants the Effect to re-synchronize when `location.pathname` or `ref.current` changes (Lesson 30). So they put that value in the array.
2. Later, some code changes `location.pathname`, or writes a new value into `ref.current`.
3. That change happens outside the rendering data flow. It does not render the component.
4. No render means React never compares the array, and the Effect stays on the old value. The docs: "even if you specified it in the dependencies, React *wouldn't know* to re-synchronize the Effect when it changes."

To follow an outside value such as `location.pathname`, the docs recommend `useSyncExternalStore` (Lesson 53).

An object or a function created in the component body has the opposite problem. It is a brand-new object on every render, so `Object.is` says it changed every time, and the Effect re-synchronizes on every render. In the docs' challenge, a component creates a new `createConnection` function during rendering, and the chat reconnects too often. Passing a simple boolean prop such as `isEncrypted` instead keeps the dependency equal from render to render (Lesson 37).

## PRINCIPLE | Two `useEffect` calls: the visit log and the connection each run again only for their own values

> [!PRINCIPLE]
> **Principle 5: One Effect for Each Job**
>
> *Each Effect should be one separate synchronization process, with its own dependency array.*
>
> Two unrelated jobs in one Effect share one array. So both jobs run again whenever a value of either job changes. To check, ask: if I delete one Effect, does the other still work? If yes, give each job its own `useEffect`.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   ~logVisit(roomId);~ // Job 1: runs again only for a new room
> }, [roomId]);
>
> useEffect(() => {
>   const connection = ~createConnection(serverUrl, roomId)~; // Job 2: runs again for a new room or a new address
>   connection.connect();
>   return () => connection.disconnect();
> }, [roomId, serverUrl]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~logVisit(roomId);~ // **WRONG:** shares [roomId, serverUrl], so a new address logs a false visit
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, [roomId, serverUrl]);
> ```

### VS | One Effect for both jobs vs. two Effects: the same on a room switch, different on an address edit

Now we want to log a visit for analytics every time the user enters a room, with `logVisit` (Lesson 34). Here are two ways to write it:

```jsx title="logVisit inside the connection Effect"
useEffect(() => {
  ~logVisit(roomId);~ // **WRONG:** also runs every time serverUrl changes
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId, serverUrl]~); // Runs again when roomId OR serverUrl changes
```

```jsx title="logVisit in its own Effect"
useEffect(() => {
  ~logVisit(roomId);~ // Job 1: logs a visit
}, ~[roomId]~); // Runs again only when roomId changes

useEffect(() => {
  const connection = ~createConnection(serverUrl, roomId)~; // Job 2: connects
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId, serverUrl]~); // Runs again when roomId or serverUrl changes
```

On a room switch, both versions log one visit and reconnect once. The difference appears when the user types one letter in the Server URL field. With one Effect, React runs the whole Effect again, so `logVisit` logs a visit again. With two Effects, React reconnects to the new address and skips the visit Effect, because `roomId` did not change.

The docs give the rule: each Effect should be "**a separate and independent synchronization process**". For our chat, logging the visit "**is a separate process** from connecting." One Effect keeps the analytics in sync with `roomId`. The other keeps the connection in sync with `roomId` and `serverUrl`.

### The test: delete one Effect, does the other still work?

The docs give a simple test: two Effects are separate when "deleting one Effect wouldn't break the other Effect's logic."
- Delete the visit Effect, and the chat still connects.
- Delete the connection Effect, and the visit is still logged.

Neither breaks the other, so they are two processes, and they get two Effects.

The test also works the other way. Do not split one process into two Effects just to make each block look shorter. If deleting one part breaks the other, they are one process. The docs: "if you split up a cohesive piece of logic into separate Effects, the code may look "cleaner" but will be more difficult to maintain." And: "you should think whether the processes are same or separate, not whether the code looks cleaner."

```tree caption="One Effect or two Effects: ask whether the jobs are separate processes."
One Effect or two? Ask whether the processes are separate
- !Two processes in one Effect [`logVisit` and `createConnection` in one `useEffect`] | ~Both jobs share `[roomId, serverUrl]` | A new address **logs a false visit** for the same room
- +One Effect per process [`[roomId]` for the visit, `[roomId, serverUrl]` for the connection] | +Deleting one **does not break** the other | Each runs again **only for its own values**
- !One process split in two for looks | ~One setup cut across two blocks | **Harder to maintain**, with no real gain
```

### Two related cases: two fetches, and a value read without a reconnect

The same principle decides the docs' challenge with planets and places. One menu loads the list of planets at mount. A second menu loads the places of the selected planet. The two fetches are separate processes, so they get two Effects. In one Effect, "changing the planet ... refetch the list of all planets."

The docs also warn: "Effects are not a tool for code reuse." When two Effects share similar fetch code, you move that code into a custom Hook, such as `useSelectOptions` (Lesson 39).

Sometimes the visit log also needs a value, such as the number of items in the cart. But a new number must not log a new visit. Reading the latest value without re-synchronizing is the job of an Effect Event, with `useEffectEvent` (Lesson 36).

The chat helper returns an object with `connect` and `disconnect`:

`ChatRoom` has two Effects, one for each job:

```jsx title="src/components/ChatRoom.jsx"
import { useState, useEffect } from 'react';
import { createConnection } from '../chat.js';
import { logVisit } from '../analytics.js';

export default function ChatRoom({ roomId }) {
  const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // Principle 4: reactive state

  useEffect(() => {
    ~logVisit(roomId);~ // Principle 5: its own Effect for the visit
  }, ~[roomId]~); // Principle 3: the one reactive value this Effect reads

  useEffect(() => {
    const connection = ~createConnection(serverUrl, roomId)~; // Principle 1: start
    connection.connect();
    return () => {
      ~connection.disconnect()~; // Principle 2: stop, with this render's room and address
    };
  }, ~[roomId, serverUrl]~); // Principles 3 and 4: every reactive value this Effect reads

  return (
    <section>
      <label>
        Server URL:{' '}
        <input
          value={serverUrl}
          onChange={e => setServerUrl(e.target.value)}
        />
      </label>
      <h1>Welcome to the {roomId} room!</h1>
    </section>
  );
}
```

### How React runs the two Effects across a session

```tree dir=right caption="How React runs the visit Effect and the connection Effect across four clicks and edits."
From Open chat to Close chat
- +1. Click Open chat [`roomId: 'general'`] | `ChatRoom` **mounts** | The visit Effect logs **general** · The connection Effect **connects** to general
- +2. Pick `travel` [`roomId: 'travel'`] | `roomId` changed, so **both Effects** run again | The old cleanup **disconnects from general** · The visit Effect logs **travel** · The new setup **connects to travel**
- +3. Edit the Server URL field [`serverUrl: 'https://localhost:12345'`] | `roomId` is still travel, `serverUrl` changed | The visit Effect is **skipped** · The old cleanup **disconnects** from the old address · The new setup **connects** to the new address
- +4. Click Close chat [`show: false`] | `ChatRoom` **unmounts** | The last cleanup **disconnects** from travel at the new address
```

### The mistake, and what the user sees

| The mistake | What the user sees | The rule |
| :--- | :--- | :--- |
| **Thinking in mount and unmount** | A new room never connects | One start and one stop for each value of the dependencies |
| **No cleanup function** | Every old room stays connected | The cleanup undoes exactly what the setup did |
| **Expecting the new `roomId` in the cleanup** | A confusing Console, read the wrong way | The cleanup holds the values of its own render |
| **`[]` with a silenced linter** | The heading says travel, the chat stays on general | Every reactive value the Effect reads goes in the array |
| **`serverUrl` in state, left out of the array** | A new address never connects | Props, state, and body variables are reactive |
| **`ref.current` in the array** | The Effect never runs again when it changes | A value that changes without a render cannot be a dependency |
| **Two jobs in one Effect** | An address edit logs a false visit | One Effect for each separate process |

One last time, the sentence of this lesson: **An Effect does only two things: it starts, and it stops. Every time a dependency changes, React stops the old Effect and starts a new one.**

## For the Interview

> **The Interview Question:** What is the lifecycle of a reactive effect as its dependencies change?

### How to Answer Clearly in 30 Seconds

"A component mounts, updates, and unmounts. An Effect only does two things: the setup starts synchronizing, and the cleanup stops it. While the component stays mounted, that pair can repeat many times. The classic example is a chat room: the setup connects to `roomId`, and the cleanup disconnects. Three rules:
1. **How React decides**: after each render, React compares every item of the dependency array with the previous render, using `Object.is`. If all are the same, it skips the Effect.
2. **The order on a change**: React first updates the DOM. Then it runs the **previous render's cleanup**, which still holds the old props and state, and then the **new setup** with the new ones. On unmount, the last cleanup runs one final time.
3. **What goes in the array**: you do not choose it. Every prop, state variable, and body variable the Effect reads is reactive and must be listed. A fixed constant moves outside the component. And two jobs that should not run again together get two separate Effects."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"When `roomId` changes from general to travel, why does the cleanup disconnect from general and not from travel?"**
   Each render creates its own setup and its own cleanup, and both capture that render's props and state. When `roomId` was general, React ran that setup and kept the cleanup it returned. On the switch to travel, React calls that saved cleanup before the new setup. Its closure still holds general, so it disconnects exactly the room it connected to. That is the point: a cleanup must undo its own setup.
2. **"What counts as a reactive value? Can I put `ref.current` or `location.pathname` in the array?"**
   Reactive values are props, state, and every variable or function declared in the component body, because React calculates them during rendering. Values like `ref.current` or `location.pathname` change outside the rendering data flow, and the change does not render the component. Without a render, React never compares the array, so listing them does nothing. For an outside value like the pathname, use `useSyncExternalStore`. Setters and ref objects are stable, so you may leave them out.
3. **"What happens if I silence `exhaustive-deps` and pass `[]` so my Effect runs only once?"**
   The Effect's closure stays frozen on the first render's props and state. When a prop changes, React compares `[]` with `[]`, sees no change, and never re-synchronizes. The chat stays on the first room, and any timer or listener inside keeps reading old values: a stale closure. The docs say you "lie" to React this way. The fix is to change the code so the Effect does not need the value, for example with an Effect Event, never to silence the linter.

```tree dir=right caption="Interview summary: the lifecycle of a reactive Effect from mount to unmount."
The lifecycle of a reactive Effect
- +1. Mount [`useEffect` `[roomId, serverUrl]`] | React puts the component into the DOM | React runs **the first setup**, and in development Strict Mode runs **setup, cleanup, setup** to test the cleanup
- +2. Render with the same dependencies [`Object.is` is `true`] | Every item matches the previous render | React **skips the Effect**, and the connection stays open
- +3. Render with a changed dependency [`Object.is` is `false`] | At least one item changed | React runs **the old cleanup** with the old values, then **the new setup** with the new values
- +4. Unmount [`cleanup`] | The component leaves the screen | React runs **the last cleanup** one final time, so nothing stays open
```
