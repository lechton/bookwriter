# Lecture 89: Letting the Page Decide What Shared Tabs Show

*(How can one shared Tabs component look different on every page without a new prop for every request?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do Render Props, Compound Components, and Slot patterns structure flexible UI?

---

## VS | One New Prop per Request vs. Markup Written by the Page: both show the count, only the second leaves `Tabs` unchanged

> A shared component, such as the tabs on every product page of a store, is written once and used by many pages, and every page wants it to look a little different. **Instead of adding one more prop to the shared component for every request, let the page write the markup, and let the shared component only place it.** Then a request from one page no longer changes the shared file, so a change made for the headphones page can no longer break the shoes page.

You already pass values to functions all the time. `greet('John')` passes a string. `setCount(12)` passes a number. In React, JSX is a value too, just like `'John'` or `12` (Lesson 76). So a prop can hold a number, `count={12}`, and a prop can hold a piece of markup, `countLabel={<b>12</b>}`. Keep that one fact in mind, because the whole lesson is built on it.

Now the problem. Open a product page on any online store, for example a pair of headphones. Under the photo sit two tabs, `Description` and `Reviews`. The tabs are one shared component, `Tabs`, and the store uses it on many pages: headphones, shoes, books.

Then the store asks for three changes on the headphones page, one at a time:
1. The `Reviews` tab should show the number of reviews, `12`.
2. The open tab should be bold, so the user sees which one is open.
3. The line `Free returns for 30 days.` should sit between the tabs and the text.

The first habit is to put every change inside `Tabs`, as one more prop: `showCount` and `count`, then `boldSelected`, then one more prop for the returns line. After three requests, the shared file knows about reviews, counts, and returns. Every other page that uses `Tabs` carries this code too, even though only the headphones page asked for it.

**Why:** every request from one page changes the one file that every page shares. A mistake made for the headphones page can break the shoes page, which nobody touched. And a developer who reads `<Tabs showCount={true} />` on the shoes page cannot tell what it draws without opening `Tabs`.

A senior developer asks one question instead: **who writes the markup?** The answer of this lesson is always the same. **The page writes the markup. `Tabs` only places it.** There are three ways to do that, and you already know each one from plain JavaScript or HTML:
1. **The page hands `Tabs` finished JSX, in a prop.** Like `greet('John')`, except the value is markup.
2. **The page hands `Tabs` a function that returns JSX.** You know this from `array.map`. In `names.map(name => <li>{name}</li>)`, `map` runs the loop and decides when to call your function. Your function decides what each item becomes. Here, `Tabs` runs the loop and knows which tab is open. The page's function decides how each tab looks.
3. **The page gets the parts of the tabs, and places them itself.** You know this from HTML: `<select>` and `<option>`. You write the `<option>` tags yourself, in your own order, and the `<select>` still knows which option is chosen. `Tabs`, `Tab`, and `TabPanel` work the same way.

> [!DEFINITION]
> **What is children?** [REVIEW] `children` is a prop. React fills it with the JSX you write between a component's opening and closing tags.
> In `<Card><p>Hello</p></Card>`, `Card` receives `<p>Hello</p>` as `props.children`.
> Something that can be tricky: `children` is only a name. JSX is a value, like a number or a string, so any other prop can hold JSX too (Lesson 09).

### Two ways to ask `Tabs` for the review count

Here is the whole idea in two lines:

```jsx title="Telling Tabs what to draw, and handing Tabs what to draw"
<Tabs ~showCount={true} count={12}~ /> {/* Tabs must already hold the markup for the count */}
<Tabs ~countLabel={<b>12</b>}~ /> {/* The page wrote the markup; Tabs only places it */}
```

Both lines pass props, and `Tabs` reads both from `props`. It may look the same, but it is NOT the same thing! The one difference is who writes the markup:
- **With `showCount` and `count`**, `Tabs` must contain the code that draws a count. So the shared file changes for this one request.
- **With `countLabel`**, the page has already written `<b>12</b>`. `Tabs` only decides where it goes.

A prop that holds `<b>12</b>` is a prop just like one that holds `12`. **Yes, it is the exact same thing!**

```tree caption="Two ways to ask a shared Tabs component for the review count: describe it with props, or hand over the markup."
Two ways to ask `Tabs` for the review count
- !Describe it with props [`showCount={true}` `count={12}`] | `Tabs` holds the **markup for the count** | Every new request **changes the shared file**
- +Hand over the markup [`countLabel={<b>12</b>}`] | The page **writes the markup** | `Tabs` only decides **where it goes**
```

### The Rule of Thumb: who knows the markup, and when?

**The page writes the markup, and `Tabs` only places it. If the page knows the markup before `Tabs` runs, pass JSX. If the markup needs something only `Tabs` knows, such as which tab is open, pass a function. If the page must decide the order of the parts, give the page the parts.**

A senior developer also knows the three classic mistakes:
1. **Believing only `children` can hold JSX.** Any prop can, because JSX is a value.
2. **Believing a render prop is a special React feature.** It is not. In the words of react.dev, "there is nothing special about it: it is a regular prop which happens to be a function."
3. **Reaching for `Children.map` and `cloneElement`** to pass the open tab into each part. react.dev calls both "uncommon" and warns that they "can lead to fragile code". Lesson 100 covers them.

At work, you will meet four ways to let a page decide what a shared component shows. This lesson covers the first three:

```tree caption="Four ways to let a page decide what a shared component shows, and when each one fits."
Four ways to let the page decide what `Tabs` shows
- +1. JSX in a prop [`children` `header` `tabs`] | The page **writes the whole markup** before `Tabs` runs | Fits **visual wrappers** such as panels and grids, and lists of tabs
- +2. A render prop [`renderTab`] | `Tabs` **calls the page's function** and passes what only `Tabs` knows | Fits when the markup **depends on the open tab**
- +3. Several components exported together [`Tabs` `Tab` `TabPanel`] | The page **places each part itself**; the parts share state through **context** | Fits when the page decides **the order** of the parts
- +4. A custom Hook | Shares **only the logic**; the page writes **all the markup** | Fits when **no markup** should be shared, as Lesson 39 shows
```

Our first `Tabs` follows the shape react.dev uses for its own tab example. The page passes a `tabs` prop: an array with one object per tab. Each object has an `id`, a `header` for the button, and a `content` for the text under the buttons:

```jsx title="src/ProductPage.jsx"

const tabs = [
  { id: 'description', header: 'Description', content: <p>Light and loud.</p> },
  { id: 'reviews', header: 'Reviews', ~content: <p>John: Great sound.</p>~ }, // content already holds JSX
];

export default function ProductPage() {
  return (
    <main>
      <h1>Wireless Headphones</h1>
      <Tabs tabs={tabs} />
    </main>
  );
}
```

`Tabs` keeps the `id` of the open tab in state. It draws one button per tab, and under the buttons it shows the content of the open tab:

```jsx title="src/Tabs.jsx"
import { useState } from 'react';

export default function Tabs({ tabs }) {
  const [selectedId, setSelectedId] = useState(tabs[0].id);
  const selectedTab = tabs.find(tab => tab.id === selectedId); // The tab whose id matches selectedId

  return (
    <div>
      {tabs.map(tab => (
        <button key={tab.id} onClick={() => setSelectedId(tab.id)}>
          ~{tab.header}~ {/* The page wrote this header */}
        </button>
      ))}
      ~{selectedTab.content}~ {/* The page wrote this content */}
    </div>
  );
}
```

Look closely at `content`. It already holds JSX: a whole paragraph, written by the page. `Tabs` never knows what is inside it. It only places it under the buttons. That is the idea of the whole lesson, already at work.

Now the store sends its three requests. Each principle answers one of them, on the same headphones page:

**PRINCIPLES:** The page writes the markup. `Tabs` only places it. Three principles follow:
1. **Principle 1: A prop holding JSX puts the review count in the tab.** Any prop, not only `children`, can hold JSX. The page writes `Reviews` with a bold `12`, and `Tabs` places it inside the button without a `showCount` prop.
2. **Principle 2: `renderTab` lets the page bold the open tab.** Only `Tabs` knows which tab is open. So the page passes a function, and `Tabs` calls it for each tab with `true` or `false`. The page decides the look, and `Tabs` decides when to ask.
3. **Principle 3: `Tab` and `TabPanel` read the open tab from context.** To place the returns line between the tabs and the text, the page needs the parts themselves. `Tabs` keeps the open tab in state and provides it through context. Every `Tab` and `TabPanel` reads it, wherever the page puts them.

## PRINCIPLE | JSX in `header` or `children`: the page writes the markup, and `Tabs` only places it

> [!PRINCIPLE]
> **Principle 1: JSX in Props: The Page Writes the Markup, the Component Places It**
>
> *When a page knows the markup before the shared component runs, it passes that markup as JSX, in `children` or in any named prop, and the component places it.*
>
> A shared component that grows a prop for every request, such as `showCount` and `count`, holds markup that belongs to one page, and every other page carries it. Any prop can hold JSX, not only `children`, because JSX is a value. The page writes the markup, and the component only decides where it goes. This is React's equivalent of slots.
>
> **DO THIS:**
> ```jsx
> const tabs = [
>   { id: 'description', header: 'Description', content: <p>Light and loud.</p> },
>   { id: 'reviews', ~header: <>Reviews <b>12</b></>~, content: <p>John: Great sound.</p> }, // The page writes the count
> ];
> <Tabs tabs={tabs} />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Tabs tabs={tabs} ~showCount={true} count={12}~ /> // **WRONG:** Tabs must hold markup for one page's count
> ```

### VS | `children` between the tags vs. `header` on the opening tag: both are props that hold JSX

You already know that the JSX between a component's tags arrives as `children` (Lesson 09). Now look at a `Card` that takes JSX in two props, `header` and `children`:

```jsx title="A Card that places two pieces of JSX from the page"
function Card({ header, children }) {
  return (
    <div>
      ~{header}~ {/* The JSX from the header prop goes here */}
      ~{children}~ {/* The JSX between the Card tags goes here */}
    </div>
  );
}

<Card ~header={<b>John</b>}~> {/* header is written on the opening tag, with a name */}
  <p>Hello</p>
</Card>
```

`header` and `children` are both props that hold JSX. **Yes, it is the exact same thing!** The only difference is where the page writes them:
- **`header`** is written on the opening tag, with a name.
- **`children`** is written between the tags, with no name.

Inside `Card`, both are values on `props`, and `Card` places each one where it wants. `Card` does not know what the page wrote, and it does not need to. In the words of react.dev, a component with a `children` prop has a "hole" that its parent can fill "with arbitrary JSX", and it "doesn't need to 'know' what's being rendered inside of it." react.dev says `children` fits best for **visual wrappers**: components that only draw a frame around their content, such as "panels, grids".

> [!DEFINITION]
> **What is a slot?** [NEW] The interview question uses this word. It comes from web components: custom HTML tags that a page builds with the browser's own tools, without React.
> MDN says: "A slot is a placeholder inside a web component that users can fill with their own markup."
> React has no special slot feature. A prop that holds JSX does the same job. react.dev says that in React "an equivalent pattern is typically achieved by passing JSX as props" (Lesson 89).

Here is react.dev's own example, a `Layout` with two slots:

```jsx title="React's equivalent of two slots: two props that hold JSX"
<Layout ~left={<Sidebar />}~ ~right={<Content />}~ /> {/* Two props, both filled by the page */}
```

```tree caption="Every prop that holds JSX is one place the parent fills, whether it has a name or sits between the tags."
Where the page puts JSX for `Card`
- +On the opening tag, with a name [`header={<b>John</b>}`] | Arrives as **`props.header`** | `Card` places it **where it writes `{header}`**
- +Between the tags, with no name [`<p>Hello</p>`] | Arrives as **`props.children`** | `Card` places it **where it writes `{children}`**
- +Several named props [`left={<Sidebar />}` `right={<Content />}`] | React's equivalent of **slots** | One component, **several places to fill**
```

### Mistake: adding `showCount` and `count` to the shared `Tabs`

Back to the headphones page. The store asks for the review count on the `Reviews` tab. The first habit is to teach `Tabs` how to draw a count:

```jsx title="src/Tabs.jsx" startLine="3"
export default function Tabs({ tabs, ~showCount~, count }) { // **WRONG:** a new prop for one page's request
  const [selectedId, setSelectedId] = useState(tabs[0].id);
  const selectedTab = tabs.find(tab => tab.id === selectedId);

  return (
    <div>
      {tabs.map(tab => (
        <button key={tab.id} onClick={() => setSelectedId(tab.id)}>
          {tab.header}
          {showCount && ~tab.id === 'reviews'~ && <b> {count}</b>} {/* **WRONG:** Tabs now knows the word reviews */}
        </button>
      ))}
      {selectedTab.content}
```

And the page passes the two new props:


The tab now reads `Reviews 12`, so the request is met. But look at what `Tabs` has become. The shared file now contains the word `reviews`, which belongs to one kind of page.

Next week, the shoes page wants a small icon on its `Sizes` tab, and someone adds `showIcon` and `icon`. Now every page carries props meant for other pages, and every request changes the shared file.

### Why an array of tabs, and not `children`?

An array of objects like `tabs` is one form of JSX in a prop. react.dev says it fits "when you want to be able to pass more information as structured data together with children": here, an `id` and a `header` for each tab.

`Tabs` can run `.map` and `.find` on this array, because it is a plain JavaScript array. It should not do that on `children`: react.dev calls the structure of `children` "opaque", which means your code should not look inside it.

Remember: the page writes the markup. `Tabs` only places it.

## PRINCIPLE | `renderTab`: `Tabs` calls the page's function and tells it which tab is open

> [!PRINCIPLE]
> **Principle 2: Render Props: The Component Calls the Page's Function During Its Render**
>
> *When the markup needs information that only the shared component has, such as which tab is open, the page passes a function that returns JSX; the component calls it during its render and passes that information as arguments.*
>
> JSX written by the page is made before the shared component runs, so it cannot know which tab is open. A render prop is a regular prop that happens to be a function. `Tabs` calls it for each tab with `true` or `false`, and the page's function returns the look for that tab. The page decides the look, and `Tabs` decides when to ask.
>
> **DO THIS:**
> ```jsx
> <button key={tab.id} onClick={() => setSelectedId(tab.id)}>
>   {~renderTab(tab, tab.id === selectedId)~} {/* Tabs asks the page how this tab should look */}
> </button>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> { id: 'description', ~header: <b>Description</b>~ }, // **WRONG:** made before Tabs runs, so it stays bold when Reviews is open
> ```

### The request: the open tab should be bold

The store asks for the open tab to be bold. The page already writes the headers, so the first idea is to write the bold in `header`:

```jsx title="src/ProductPage.jsx" startLine="3"
const tabs = [
  { id: 'description', ~header: <b>Description</b>~, content: <p>Light and loud.</p> }, // **WRONG:** stays bold when Reviews is open
  { id: 'reviews', header: <>Reviews <b>12</b></>, content: <p>John: Great sound.</p> },
];
```

That does not work. `Description` stays bold even after the user clicks `Reviews`. Why? The page writes this JSX once, before `Tabs` runs. And `selectedId` lives inside `Tabs`, in its state. So the page cannot know which tab will be open.

The second habit is to go back to the shared file and add `boldSelected` to `Tabs`. Then the shoes page wants the open tab underlined, and someone adds another prop for that. We are back to one prop per request.

What the page needs is a way to say: "`Tabs`, when you draw a tab, tell me whether it is open, and I will give you its look." In JavaScript, that is a function.

### VS | A function prop called in a click vs. a function prop called during render: both are regular props

You already pass functions as props. In the cart of Lesson 23, the parent passed `onRemove`, and the row called it when the user clicked Remove. A **render prop** is also a function passed as a prop. Here it is in its smallest code:

```jsx title="A List that asks the page how each row should look"
function List({ items, renderItem }) {
  return items.map((item, index) => ~renderItem(item, index === 0)~); // List calls the page's function for each row
}

<List
  items={['John', 'Mia']}
  ~renderItem~={(name, isFirst) => ( // The page decides how a row looks
    <p key={name}>{isFirst ? <b>{name}</b> : name}</p>
  )}
/>
```

The page shows two lines: `John` in bold, then `Mia`. It is the deal of `array.map` again:
- **`List` knows which row is first.** It runs the loop, and it calls `renderItem` with `true` or `false`.
- **The page knows how the first row should look.** Its function gives back the JSX for that row.

`renderItem` and `onRemove` are the same kind of prop: a function written by the parent and called by the child. **Yes, it is the exact same thing!** The one difference is when the child calls it, and what it gives back:
- **`onRemove`** is called in a click handler, after the user clicks. It tells the parent that something happened, and it gives back nothing to show.
- **`renderItem`** is called while `List` renders. It gives back JSX, and `List` puts that JSX on the page.

> [!DEFINITION]
> **What is a render prop?** [NEW] A render prop is a prop that holds a function, and the function returns JSX.
> The child calls it while it renders, and puts the returned JSX on the page. That is where the name comes from. react.dev says "A prop like `renderContent` is called a *render prop*."
> Because it is a function, the child can pass it information that only the child has. In react.dev's words, "Render props are functions, so you can pass information to them."
> Something that can be tricky: it is not a React feature. It is "a regular prop which happens to be a function" (Lesson 89).

```tree caption="A render prop is a regular function prop; the difference from onRemove is when the child calls it and what it gives back."
Two function props from the parent
- +`onRemove` from Lesson 23 [`onRemove`] | The child calls it **in a click handler** | Tells the parent **something happened**; gives back **nothing to show**
- +A render prop [`renderItem`] | The child calls it **while it renders** | Gives back **JSX** that the child places on the page
```

### VS | `header` holding JSX vs. `renderTab` returning JSX: only the function can know which tab is open

Back to the bold tab. Here are the two ways the page can give `Tabs` the look of a tab:

```jsx title="Handing Tabs finished JSX, and handing Tabs a function it calls"
{ id: 'description', ~header: <b>Description</b>~ }, // Made once by the page: bold on every render
<Tabs tabs={tabs} ~renderTab~={(tab, isSelected) => (isSelected ? <b>{tab.header}</b> : tab.header)} /> // Called by Tabs: bold only while open
```

Both give `Tabs` markup written by the page. It may look the same, but it is NOT the same thing!
- **The JSX in `header`** is made by the page before `Tabs` runs. It is the same on every render, so it cannot depend on `selectedId`.
- **`renderTab`** is a function. `Tabs` calls it on every render and tells it whether this tab is open.

The page decides the look, and `Tabs` decides when to ask.

### `Tabs` calls `renderTab` for each tab

`Tabs` takes a new prop, `renderTab`, and calls it inside each button:

```jsx title="src/Tabs.jsx" startLine="3"
export default function Tabs({ tabs, ~renderTab~ }) { // A function from the page that returns JSX
  const [selectedId, setSelectedId] = useState(tabs[0].id);
  const selectedTab = tabs.find(tab => tab.id === selectedId);

  return (
    <div>
      {tabs.map(tab => (
        <button key={tab.id} onClick={() => setSelectedId(tab.id)}>
          {~renderTab(tab, tab.id === selectedId)~} {/* Tabs asks the page how this tab should look */}
        </button>
      ))}
      {selectedTab.content}
    </div>
  );
}
```

The page keeps the headers of Principle 1, `'Description'` and `<>Reviews <b>12</b></>`, and passes the function:

```jsx title="src/ProductPage.jsx" startLine="8"
export default function ProductPage() {
  return (
    <main>
      <h1>Wireless Headphones</h1>
      <Tabs
        tabs={tabs}
        ~renderTab~={(tab, isSelected) => (isSelected ? <b>{tab.header}</b> : tab.header)} // The open tab is bold
      />
    </main>
  );
}
```

`tab` and `isSelected` are names the page wrote, but the page never gives them values. `Tabs` does, when it calls `renderTab`:
1. The page writes `renderTab` as an arrow function and names its two parameters, `tab` and `isSelected`.
2. `Tabs` runs `tabs.map`. For each tab, it calls `renderTab` with two arguments: the tab object, and whether its `id` matches `selectedId`.
3. JavaScript gives the tab object to `tab`, and `true` or `false` to `isSelected`.
4. The arrow function returns the bold header or the plain header, and `Tabs` places it in the button.

The `key` stays on the `<button>` that `Tabs` makes around the call, because `Tabs` runs the `.map`. The page's function returns only what goes inside the button.

When the page opens, `Description` is bold. After the user clicks `Reviews`, `Reviews 12` is bold and `Description` is plain:

```dom
<div>
```

`Tabs` still contains no bold, no underline, and no word `reviews`. The shoes page can pass its own `renderTab` that underlines the open tab, and `Tabs` does not change. The page writes the markup. `Tabs` only places it, and now also decides when to ask for it.

### Mistake: writing `{renderTab}` without calling it

A render prop is a function, so it does nothing until someone calls it. Suppose a developer places it inside the button like any other value:

```jsx title="src/Tabs.jsx" startLine="10"
        <button key={tab.id} onClick={() => setSelectedId(tab.id)}>
          ~{renderTab}~ {/* **WRONG:** places the function itself, not the JSX it returns */}
        </button>
```

The two buttons appear with no text, and React prints an error in the Console. React expects something it can show, such as text or JSX. It gets a function instead, and it cannot show a function:

```devconsole width=full
x Functions are not valid as a React child. This may happen if you return renderTab instead of <renderTab /> from render. Or maybe you meant to call this function rather than return it.
  <button>{renderTab}</button>
```

The last sentence of the message names the fix: call the function. Write `renderTab(tab, tab.id === selectedId)`, with the tab and whether it is open, as in the code above.

## PRINCIPLE | `Tab` and `TabPanel` with `useContext`: every part reads the open tab, wherever the page puts it

> [!PRINCIPLE]
> **Principle 3: Several Components Exported Together: The Parent Provides, Every Part Reads**
>
> *When the page must also decide the order and place of the parts, export them together; the parent part keeps the state and provides it through context, and every part reads it with `useContext`, wherever the page puts it.*
>
> With an array of tabs, the shared component writes the order of the markup, so any new element in between needs one more prop. With the parts, the page writes the order. `Tabs` never looks at its children: each `Tab` and `TabPanel` finds the closest `Tabs` above it, even inside the page's own components. A part placed outside `Tabs` gets the default value `null` and blanks the page, so a `useTabs` Hook should throw an error that names the fix.
>
> **DO THIS:**
> ```jsx
> <Tabs defaultId="description">
>   <Tab id="description">Description</Tab>
>   ~<p>Free returns for 30 days.</p>~ {/* The page decides where each part goes */}
>   <TabPanel id="description"><p>Light and loud.</p></TabPanel>
> </Tabs>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Tabs defaultId="description"><Tab id="description">Description</Tab></Tabs>
> ~<Tab id="shipping">Shipping</Tab>~ {/* **WRONG:** no Tabs above it, so useContext returns null */}
> ```

### The request: a line between the tabs and the text

The store has one more request: the line `Free returns for 30 days.` must sit between the tab buttons and the text.

With the array of Principles 1 and 2, `Tabs` decides the order of everything: first the buttons, then the content. The page cannot put anything in between. So the line needs one more prop, and we are back to the first habit.

This time the page needs more than markup. It needs to decide where each part goes. Think of `<select>` and `<option>` in HTML again. You write every `<option>` yourself, in your own order, and the `<select>` still knows which one is chosen. So we give the page the parts of the tabs, as three components exported from one file: `Tabs`, `Tab`, and `TabPanel`. Here is how the page uses them:

```jsx title="The page places every part of the tabs itself"
<Tabs defaultId="description">
  <Tab id="description">Description</Tab>
  <Tab id="reviews">Reviews <b>12</b></Tab>
  ~<p>Free returns for 30 days.</p>~ {/* The page puts the line exactly where it wants */}
  <TabPanel id="description"><p>Light and loud.</p></TabPanel>
  <TabPanel id="reviews"><p>John: Great sound.</p></TabPanel>
</Tabs>
```

`defaultId` is our own prop for the tab that is open when the page loads. `Tabs` needs it because it no longer gets a list of tabs to pick the first one from.

Notice what is missing: the page never passes `selectedId` to a `Tab`. So how does each `Tab` know whether it is open? Through context (Lesson 28). Nothing here is new:
1. `Tabs` takes `children` and keeps `selectedId` in state.
2. `Tabs` wraps its children in a context provider.
3. `Tab` and `TabPanel` read that state with `useContext`.

> [!DEFINITION]
> **What are compound components?** [NEW] Compound components are several components exported from one file and written together by the page, such as `Tabs`, `Tab`, and `TabPanel`.
> The parent part keeps the state and provides it through context. Every other part reads it with `useContext`, so the parts work together wherever the page puts them.
> react.dev calls this **exposing multiple components**, as in `<RowList><Row>...</Row></RowList>`, and says the parts "coordinate" through context.
> react.dev does not use the name compound components, but it is the name you will hear in interviews (Lesson 89).

### VS | An array of tabs vs. the parts exported together: only the parts let the page write the order

The screen looks like the one in Principle 2, plus the returns line. But it is NOT the same thing!
- **With the array**, `Tabs` writes the order of every element.
- **With the parts**, the page writes the order. `Tabs` writes no visible markup at all. It only provides `selectedId` and `setSelectedId`.

```tree caption="With the array, Tabs writes the order of the markup; with the parts, the page writes it and Tabs only provides the open tab."
Who writes the order of the tabs
- !An array of tabs [`tabs` `renderTab`] | `Tabs` writes **buttons first, then content** | A line between them **needs one more prop**
- +Parts exported together [`Tabs` `Tab` `TabPanel`] | The page writes **every part in its own order** | `Tabs` only **provides the open tab** through context
```

### The full `Tabs.jsx` with three exports

Here is the shared file. The array, `renderTab`, and `.find` are gone:

```jsx title="src/Tabs.jsx"
import { createContext, useContext, useState } from 'react';

const TabsContext = createContext(null);

export function Tabs({ defaultId, children }) {
  const [selectedId, setSelectedId] = useState(defaultId);
  return (
    <TabsContext ~value={{ selectedId, setSelectedId }}~> {/* Provides the open tab to every part inside */}
      {children}
    </TabsContext>
  );
}

export function Tab({ id, children }) {
  const { selectedId, setSelectedId } = ~useContext(TabsContext)~; // Reads both from the closest Tabs above
  return (
    <button onClick={() => setSelectedId(id)}>
      {id === selectedId ? <b>{children}</b> : children}
    </button>
  );
}

export function TabPanel({ id, children }) {
  const { selectedId } = ~useContext(TabsContext)~; // Reads the same selectedId
  return id === selectedId ? children : null;
}
```

`selectedId` and `setSelectedId` reach each `Tab` without a single prop:
1. `Tabs` calls `useState` with `defaultId` and gets both.
2. `Tabs` puts them in one object and gives it to the provider around `children`.
3. Each `Tab` calls `useContext` and gets that object from the closest provider above it.
4. `Tab` takes the two names out of the object.

Inside `Tab`, `children` is the JSX the page wrote between the tags, such as `Reviews <b>12</b>`.

Notice that the bold for the open tab now lives in the shared `Tab`. The page still writes the text of every tab, but this store marks the open tab the same way on every page. If one page needed its own look, `Tab` could take a render prop as well. The three tools of this lesson can be combined.

`TabsContext` is not exported, so only `Tab` and `TabPanel` can read it. That is a choice of this file, not a rule.

The page imports the three parts by name (Lesson 05) and writes them in its own order:

```jsx title="src/ProductPage.jsx"
import { ~Tabs, Tab, TabPanel~ } from './Tabs.jsx'; // Three named exports from one file

export default function ProductPage() {
  return (
    <main>
      <h1>Wireless Headphones</h1>
      <Tabs defaultId="description">
        <Tab id="description">Description</Tab>
        <Tab id="reviews">Reviews <b>12</b></Tab>
        ~<p>Free returns for 30 days.</p>~ {/* The page puts the line between the tabs and the text */}
        <TabPanel id="description"><p>Light and loud.</p></TabPanel>
        <TabPanel id="reviews"><p>John: Great sound.</p></TabPanel>
      </Tabs>
    </main>
  );
}
```

```page width=text caption="The headphones page with the parts: the returns line now sits between the tabs and the text."
heading: Wireless Headphones
line: [Description] [Reviews 12]
line: Free returns for 30 days. | good
line: Light and loud.
```

`Tabs` and the provider add no element of their own to the page. The Elements panel shows only what the parts and the page wrote:

```dom caption="The Elements panel: Tabs and its provider add no element; the closed TabPanel returns null and adds nothing."
<main>
  <h1>Wireless Headphones</h1>
+ <button><b>Description</b></button> | note: The open tab
  <button>Reviews <b>12</b></button>
+ <p>Free returns for 30 days.</p> | note: Placed by the page
  <p>Light and loud.</p>
</main>
```

### Surprise: a `Tab` inside the page's own component still works

Suppose the page moves the two `Tab` tags into its own component, `ProductTabs`, and writes `<ProductTabs />` inside `<Tabs>`:

```jsx title="src/ProductPage.jsx"
import { Tabs, Tab, TabPanel } from './Tabs.jsx';

function ~ProductTabs~() { // The page's own component around the two Tab tags
  return (
    <>
      <Tab id="description">Description</Tab>
      <Tab id="reviews">Reviews <b>12</b></Tab>
    </>
  );
}

export default function ProductPage() {
  return (
    <main>
      <h1>Wireless Headphones</h1>
      <Tabs defaultId="description">
        ~<ProductTabs />~ {/* Tabs sees one child here, not two Tab tags */}
        <p>Free returns for 30 days.</p>
        <TabPanel id="description"><p>Light and loud.</p></TabPanel>
        <TabPanel id="reviews"><p>John: Great sound.</p></TabPanel>
      </Tabs>
    </main>
  );
}
```

Both buttons still work. That surprises developers who think `Tabs` must find its `Tab` children and hand each one `isSelected`. In fact, `Tabs` never looks at its children. Here is what happens:
1. `Tabs` gets one child where the tabs were, `<ProductTabs />`, and does not look inside it.
2. React renders `ProductTabs`, which returns the two `Tab` tags.
3. Each `Tab` calls `useContext` and finds the closest provider above it: the one `Tabs` renders, even though `ProductTabs` sits in between.
4. Each `Tab` gets `selectedId` and `setSelectedId`, and both buttons work.

react.dev shows the same case with a `MoreRows` component, and says this approach "works even if you keep extracting more components". The older way, `Children.map` with `cloneElement`, "wouldn't work" here, because it "would 'see' `<MoreRows />` as a single child".

Both ways try to get the open tab into each part. It may look the same, but it is NOT the same thing!
- **Cloning** searches the children and adds props to them. react.dev warns that it "makes it hard to tell how the data flows through your app".
- **With context**, each part asks for what it needs, wherever it sits.

### Surprise: a `Tab` outside `Tabs` blanks the whole page

Now suppose a teammate adds a third tab and places it below the closing `</Tabs>` tag:

```jsx title="src/ProductPage.jsx" startLine="7"
      <Tabs defaultId="description">
        <Tab id="description">Description</Tab>
        <Tab id="reviews">Reviews <b>12</b></Tab>
        <p>Free returns for 30 days.</p>
        <TabPanel id="description"><p>Light and loud.</p></TabPanel>
        <TabPanel id="reviews"><p>John: Great sound.</p></TabPanel>
      </Tabs>
      ~<Tab id="shipping">Shipping</Tab>~ {/* **WRONG:** outside Tabs, so there is no provider above it */}
```

The whole page goes blank. Not just the `Shipping` button: the heading, the tabs, and the text all disappear. Here is why:
1. The `Shipping` tab calls `useContext`, and there is no `TabsContext` provider above it.
2. React returns the default value of the context, `null`, which we passed to `createContext` (Lesson 28).
3. `Tab` tries to take `selectedId` and `setSelectedId` out of `null`. JavaScript cannot read a name from `null`, so it throws a `TypeError` during the render. A `TypeError` is JavaScript's error for a value of the wrong kind.
4. When an error is thrown during rendering, react.dev says "React will remove its UI from the screen", unless an Error Boundary catches it (Lesson 72).

```page width=full caption="The page after a Tab is placed outside Tabs: React removes the whole page."
empty: nothing on the page
console: Uncaught TypeError: Cannot destructure property 'selectedId' of 'useContext(...)' as it is null.
  warn: An error occurred in the <Tab> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The Console says that `Tab` failed and that something was `null`. It says nothing about the missing `Tabs`. The teammate has to open `Tabs.jsx` to find out what is wrong.

### The fix: a `useTabs` Hook that throws a clear error

react.dev shows the fix for a context whose default is `null`: a custom Hook (Lesson 39) that reads the context and throws a clear error when the value is missing. We write `useTabs`, and `Tab` and `TabPanel` call it instead of `useContext`:

```jsx title="src/Tabs.jsx" startLine="14"
function useTabs() {
  const value = useContext(TabsContext);
  if (~value === null~) { // No Tabs above this part
    throw new Error('Tab and TabPanel must be used inside Tabs');
  }
  return value;
}

export function Tab({ id, children }) {
  const { selectedId, setSelectedId } = ~useTabs()~; // Reads the context, or throws a clear message
  return (
    <button onClick={() => setSelectedId(id)}>
      {id === selectedId ? <b>{children}</b> : children}
    </button>
  );
}

export function TabPanel({ id, children }) {
  const { selectedId } = ~useTabs()~; // The same check for every panel
  return id === selectedId ? children : null;
}
```

The page still goes blank when a `Tab` sits outside `Tabs`, because `useTabs` also throws during the render. But now the Console names the fix:

```page width=full caption="The same mistake with useTabs: the page is still blank, but the Console says what is missing."
empty: nothing on the page
console: Uncaught Error: Tab and TabPanel must be used inside Tabs
  warn: An error occurred in the <Tab> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The teammate reads the message, moves the `Shipping` tab inside `<Tabs>`, and the page comes back.

## All 3 Principles Together

### The complete code

Here is the finished headphones page. The page writes all the markup and its order. The shared file keeps only the state of the open tab, the provider, the check, and the two parts that read it:

```jsx title="src/Tabs.jsx"
import { createContext, useContext, useState } from 'react';

const TabsContext = createContext(null);

export function ~Tabs~({ defaultId, children }) { // 2. Keeps the open tab and provides it
  const [selectedId, setSelectedId] = useState(defaultId);
  return (
    <TabsContext value={{ selectedId, setSelectedId }}>
      {children}
    </TabsContext>
  );
}

function useTabs() {
  const value = useContext(TabsContext);
  if (value === null) {
    throw new Error('Tab and TabPanel must be used inside Tabs');
  }
  return value;
}

export function ~Tab~({ id, children }) { // 3. Called once for each Tab tag
  const { selectedId, setSelectedId } = useTabs();
  return (
    <button onClick={() => setSelectedId(id)}>
      {id === selectedId ? <b>{children}</b> : children}
    </button>
  );
}

export function ~TabPanel~({ id, children }) { // 4. Called once for each TabPanel tag
  const { selectedId } = useTabs();
  return id === selectedId ? children : null;
}
```

```jsx title="src/ProductPage.jsx"
import { Tabs, Tab, TabPanel } from './Tabs.jsx';

export default function ~ProductPage~() { // 1. Called first when the page loads
  return (
    <main>
      <h1>Wireless Headphones</h1>
      <Tabs defaultId="description">
        <Tab id="description">Description</Tab>
        <Tab id="reviews">Reviews <b>12</b></Tab>
        <p>Free returns for 30 days.</p>
        <TabPanel id="description"><p>Light and loud.</p></TabPanel>
        <TabPanel id="reviews"><p>John: Great sound.</p></TabPanel>
      </Tabs>
    </main>
  );
}
```

A real `Tabs` also adds the ARIA roles `tablist`, `tab`, and `tabpanel`, and `aria-selected` on the open tab, so screen readers can announce the tabs. They are left out here to keep the code short.

### The order in which React calls the components

When the page loads, React calls `ProductPage` first. Inside it, React calls `Tabs`, which returns the provider with its children. Then React calls each `Tab` and each `TabPanel`, in the order the page wrote them:

```tree caption="The order in which React calls the components of the headphones page, and what each one returns."
1. `ProductPage` is called first | Returns the heading and **`<Tabs>`** with its parts
- +2. `Tabs` | Keeps **`selectedId`** in state | Returns the **provider** around its children and adds **no element**
  - +3. `Tab` for Description | The open tab | Returns a **bold** button
  - +4. `Tab` for Reviews | A closed tab | Returns a **plain** button
  - +5. `TabPanel` for Description | The open tab | Returns **`<p>Light and loud.</p>`**
  - !6. `TabPanel` for Reviews | A closed tab | Returns **`null`**, so nothing appears
```

When the user clicks `Reviews`, that `Tab` calls `setSelectedId('reviews')`. `Tabs` renders again with the new value, every part reads it, and the bold and the text move to `Reviews`.

| The store's request | The tool | Who writes the markup | Who decides when or where |
| :--- | :--- | :--- | :--- |
| **Show the count `12` on the Reviews tab** | JSX in a prop: `header` holds `<>Reviews <b>12</b></>` | The page | `Tabs` places it in the button |
| **Make the open tab bold** | A render prop: `renderTab` returns the look for each tab | The page | `Tabs` calls it with `isSelected` on each render |
| **Put the returns line between the tabs and the text** | Several components exported together: `Tabs`, `Tab`, `TabPanel` | The page | The page writes the order; the parts read the open tab from context |

Remember the one sentence of this lesson. **The page writes the markup, and the shared component only places it: as JSX in a prop, as a function it calls, or as parts the page arranges itself.**

## For the Interview

> **The Interview Question:** How do Render Props, Compound Components, and Slot patterns structure flexible UI?

### How to Answer Clearly in 30 Seconds

"All three solve the same problem: a shared component that grows one boolean or string prop for every request from a page. Instead, the page decides the markup.
1. **Slots**: in React, a slot is just a prop that holds JSX. `children` is one, and named props like `left` and `right` give more. Use it when the page knows the whole markup up front.
2. **Render props**: a render prop is a regular prop that happens to be a function returning JSX. The component calls it during its render and passes information only it has, such as which tab is open.
3. **Compound components**: several components exported together, like `Tabs`, `Tab`, and `TabPanel`. The parent keeps the state and provides it through context, and each part reads it with `useContext`, wherever the page places it. Use it when the page must also decide the order of the parts."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does React have slots, like web components?"**
   Not as a separate feature. MDN describes a slot as a placeholder in a web component that users fill with their own markup. react.dev says React reaches the same result by passing JSX as props, for example `<Layout left={<Sidebar />} right={<Content />} />`. Any prop can hold JSX, because JSX is a value. `children` is only the prop React fills from the JSX between the tags. react.dev also suggests this as the first step before context: pass JSX as `children`, so the components in the middle do not carry data they never use.
2. **"Why use a render prop or context instead of `Children.map` and `cloneElement`?"**
   react.dev calls `Children` and `cloneElement` uncommon and fragile. Cloning adds props to children the component did not write, so it is hard to see where a value comes from. A render prop is "more explicit": in react.dev's words, "you can clearly trace where the `isHighlighted` value is coming from." Context also works when the page wraps the parts in its own components, where `Children.map` sees only one child. A render prop can also save work: react.dev's own tab example calls its render prop only for the selected tab.
3. **"What happens if someone uses a compound component part outside its parent?"**
   The part calls `useContext`, finds no provider above it, and gets the default value, usually `null`. Taking a value out of `null` throws a `TypeError` during render, and React removes the whole page unless an Error Boundary catches it. The error says nothing about the missing parent. The fix is a small custom Hook, such as `useTabs`, that checks for `null` and throws a clear error like "Tab and TabPanel must be used inside Tabs".

```tree caption="The three tools side by side: what the page passes and when each one fits."
Three ways the page decides what a shared component shows
- +Slots: JSX in a prop [`children` `header` `left` `right`] | The page passes **finished markup** | Fits when the page **knows the markup up front**
- +Render prop [`renderTab`] | The page passes **a function that returns markup** | Fits when the markup **needs what only the component knows**
- +Compound components [`Tabs` `Tab` `TabPanel`] | The page gets **the parts** and places them | Fits when the page **decides the order**; the parts share state through **context**
```
