## How a Chat Room Switches Rooms Without Leaving the Page

### One component that stays on the page, and a connection that must stop and start

When you open a chat app with rooms, such as Slack or Discord, a menu at the top lets you pick which room to read. The page shows the heading for the general room, and your browser stays connected to the chat server for that room (as seen in Lesson 32).

Now the user opens the menu and picks the travel room. The heading on the screen changes at once to welcome the user to the travel room.

Here is the question that screen raises for the developer. The `ChatRoom` component never left the page. It did not unmount, and it did not mount again. It only received a new `roomId` prop from its parent. So who disconnects from the general room and connects to the travel room?

React's docs answer that question in two sentences: "Your Effect's body specifies how to start synchronizing, and your cleanup function specifies how to stop synchronizing. All that React needs to do now is to call them in the correct order and with the correct props and state."

Here is the docs' own Effect that keeps the chat connection in sync with `roomId` in eight lines:

```jsx title="An Effect that starts and stops synchronizing with roomId"
useEffect(() => {
  const connection = ~createConnection(serverUrl, roomId)~; // 1. Start synchronizing with this render's roomId
  connection.connect();
  return () => {
    ~connection.disconnect()~; // 2. Stop synchronizing when this Effect is cleaned up
  };
}, ~[roomId]~); // 3. Re-synchronize whenever roomId changes on a re-render
```

Look at the words that unlock how React runs this code:
- **What is a component's "lifecycle"?** React's docs use the word **lifecycle** for the three stages every React component goes through over time. It **mounts** when it is added to the screen (as seen in Lesson 13). It **updates** when it receives new props or state in response to an interaction. Finally, it **unmounts** when it is removed from the screen (as seen in Lesson 32).
- **What is an Effect's lifecycle?** React's docs state the core rule of this lesson directly: "Effects have a different lifecycle from components. Components may mount, update, or unmount. An Effect can only do two things: to start synchronizing something, and later to stop synchronizing it."
- **What do "start synchronizing" and "stop synchronizing" mean?** The body of your setup function specifies how to **start synchronizing** with the external system, here by opening the chat connection. The cleanup function returned by your Effect specifies how to **stop synchronizing**, here by closing that exact connection.

**It may look the same, or work the same at first, but it is NOT the same thing!**
1. **On the first visit**, the user opens the chat. Here the component's lifecycle and the Effect's lifecycle look identical: the component mounts, and the Effect starts synchronizing with the general room.
2. **When the user picks `travel` in the menu**, the two lifecycles split apart. The component only updates in place without unmounting, while the Effect stops synchronizing with the general room and starts synchronizing with the travel room.

```tree caption="A component's lifecycle has mount, update, and unmount; an Effect's lifecycle is a repeatable cycle of start synchronizing and stop synchronizing."
Two different lifecycles on the same chat page
- +The component's lifecycle [`ChatRoom`] | **Mounts** once, **updates** when `roomId` changes, **unmounts** when closed | Stays **on the page** while the user switches rooms
- +The Effect's lifecycle [`useEffect`] | **Starts synchronizing** in the setup and **stops synchronizing** in the cleanup | Repeats one **stop and start** every time `roomId` changes
```

### What is at stake

What is at stake is that the heading on the screen and the live chat connection behind it must always agree on which room the user is in. When the user switches the menu from `general` to `travel`, the heading on the page welcomes the user to the travel room. Two common mistakes break the connection behind that heading in opposite ways:
1. **Without a cleanup function**, the Effect opens a new connection to the travel room while leaving the old connection to the general room open. You now have two connections active at the same time.
2. **With `roomId` left out of the dependency array**, the Effect never runs again when the user picks `travel`. As React's docs warn: "You will remain connected to the initial `roomId` and `serverUrl` even after the user picks different values in the UI."
3. **In both broken cases**, the page and the server connection give two different answers to the question "which room am I in?". As the docs put it, what your Effect did back then, connecting to the `"general"` room, no longer matches the UI.

Readers usually go wrong in four places:
1. They read the cleanup function as "the unmount code". Then they hit the exact surprise named in the docs' Troubleshooting section: "My cleanup logic runs even though my component didn't unmount".
2. They expect the cleanup function to see the new `roomId` after a switch, when in fact it still holds the old `roomId` from the render that created it.
3. They leave `roomId` out of the dependency array to stop the Effect from re-running, which leaves the chat stuck on the first room.
4. They put unrelated work, such as logging a page visit, inside the connection Effect simply because both happen to run when the user enters a room.

### Four ways to handle a value that an Effect reads

Whenever an Effect reads a value, where that value is declared decides whether it can change during rendering and whether it belongs in the dependency array. React's docs give four ways to handle a value that an Effect reads:
1. **List it in the dependency array**: fits when the value is a prop, state variable, or value calculated in the component body that can change on a re-render. Listing `roomId` tells React to stop and start the Effect whenever `roomId` changes.
2. **Move it outside the component**: fits when the value is a fixed constant that never changes, such as a fixed `serverUrl`. Above the component, it cannot change on a re-render, so it does not belong in the array.
3. **Move it inside the Effect**: fits when only the Effect uses the value and it does not depend on props or state. Inside the Effect, it is not calculated during rendering, so it does not belong in the array.
4. **Read it in an Effect Event**: fits when the Effect needs to read the latest value of a prop or state variable without re-synchronizing the connection, which Lesson 36 covers with `useEffectEvent`.

```tree caption="The four places a value read by an Effect can live, and what each one means for the dependency array."
Four ways to handle a value that an Effect reads
- +1. Keep it in the component body and list it [`[roomId]`] | The value can change on a **re-render** | React **re-synchronizes** the Effect whenever it changes
- +2. Move a fixed constant outside the component [`const serverUrl` at top of file] | Never changes on a **re-render** | Not reactive, so it **leaves the dependency array**
- +3. Move a helper value inside the Effect [Declared inside `useEffect`] | Created **when the Effect runs**, not during rendering | Not reactive, so it **leaves the dependency array**
- +4. Read it inside an Effect Event [`useEffectEvent` in Lesson 36] | Reads the **latest prop or state** without reconnecting | Covered in **Lesson 36**
```

### Our example page: a chat room picker

To see every step of an Effect's lifecycle in the browser and the Console, we will build the chat room picker from the React docs. The page has four parts:
1. A room menu with three options: the general room, the travel room, and the music room.
2. A button beside it that reads `Open chat` while the chat is closed, and `Close chat` while the chat is open.
3. Under them, while the chat is open, a horizontal rule and the room heading.
4. The browser Console, where our helper in `chat.js` prints a connect line whenever a connection opens and a disconnect line whenever a connection closes.

Here is what the user does on this page, and what each action should change:
1. The user clicks the Open chat button: the general room heading appears, and the app connects to `general`.
2. The user picks `travel` in the menu: the heading changes to the travel room, and the app disconnects from the old room and connects to `travel`.
3. The user picks `music` in the menu: the heading changes to the music room, and the app disconnects from the old room and connects to `music`.
4. The user clicks the Close chat button: the heading disappears, and the app disconnects from `music`.

When the page first opens, `show` is `false`, so the chat is closed and the Console is quiet:

```page width=text caption="The chat room picker when the page first opens: the menu is on general, the button reads Open chat, and the Console is quiet."

```

Our server helper lives in `chat.js`, taken straight from the React docs. As the docs note in their code, "A real implementation would actually connect to the server". Here `createConnection` returns an object whose two methods print to the Console whenever the connection starts or stops:

```js title="src/chat.js"
export function ~createConnection~(serverUrl, roomId) { // Stand-in for a real chat server connection
  return {
    ~connect~() { // Prints the connect line with roomId and serverUrl
      console.log('✅ Connecting to "' + roomId + '" room at ' + serverUrl + '...');
    },
    ~disconnect~() { // Prints the disconnect line with roomId and serverUrl
      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);
    }
  };
}
```

In `App.jsx`, the parent component keeps the selected room and `show` in state (as seen in Lesson 12) and controls the room menu (as seen in Lesson 20). Clicking the button flips `show` (as seen in Lesson 11), and when the chat is open, React renders `ChatRoom` (as seen in Lesson 10):

```jsx title="src/App.jsx"
      </button>
```


### Five Principles of the Effect Lifecycle

**PRINCIPLES:** An Effect does not mount, update, and unmount like a component; instead, it starts synchronizing and stops synchronizing once for each value of its dependencies. Walking through how React re-synchronizes our chat room as its dependencies change gives us five practical rules:
1. **Principle 1: The Effect Connects to One Room Until It Disconnects**: A component's lifecycle has mount, update, and unmount, while an Effect's lifecycle has only one start and one stop. You write the setup to start synchronizing and the cleanup to stop synchronizing, and React repeats that pair as often as needed.
2. **Principle 2: Picking travel Runs the Cleanup for general First**: When a dependency changes, React first runs the cleanup function from the previous render with that render's old values. Then React runs the new setup function with the new render's values. Without a cleanup function, every room switch leaves an old connection open.
3. **Principle 3: Leaving roomId Out Keeps the Chat on general**: You cannot choose your dependencies. Every reactive value that the Effect reads must go in the dependency array. Suppressing the linter with `[]` leaves the Effect stuck on the first render's stale value.
4. **Principle 4: A serverUrl in State Joins the Array**: Props, state, and all variables calculated in the component body are reactive values that participate in the React data flow and must go in the dependency array. Constants outside the component, values inside the Effect, and stable values from React are not reactive, while mutable values such as `location.pathname` and `ref.current` cannot be dependencies.
5. **Principle 5: Logging the Visit Gets Its Own Effect**: Each Effect in a component must represent one separate synchronization process. Putting `logVisit` inside the connection Effect logs a false room visit every time `serverUrl` changes.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The Effect Connects to One Room Until It Disconnects** | Thinking of an Effect as "mount code" and "unmount code" breaks the moment a prop changes while the component stays on the page. | Write every Effect as a single start and stop cycle: the setup starts synchronizing and the cleanup stops synchronizing. |
| **Principle 2** | **Picking travel Runs the Cleanup for general First** | Expecting the cleanup to read the new prop, or forgetting the cleanup altogether, either misreads the Console or leaks a new connection on every room switch. | After a commit with changed dependencies, React runs the previous render's cleanup with the old values first, then the new render's setup with the new values, and runs the last cleanup once more on unmount. |
| **Principle 3** | **Leaving roomId Out Keeps the Chat on general** | Shortening the dependency array to `[]` and suppressing the linter leaves the chat connected to `general` after the heading changes to `travel`. | Include every reactive value the Effect reads in its dependency array so React compares each spot with `Object.is` and re-synchronizes when a value changes. |
| **Principle 4** | **A serverUrl in State Joins the Array** | Moving `serverUrl` into state or calculating it in the component body makes it reactive; conversely, putting `ref.current` or `location.pathname` in the array never triggers a re-run. | Put all props, state, and component-body variables read by the Effect into the array; keep constants outside the component or inside the Effect, and never use mutable values as dependencies. |
| **Principle 5** | **Logging the Visit Gets Its Own Effect** | Combining `logVisit` and the server connection in one Effect logs a new room visit for every letter the user types into the `Server URL:` box. | Give each independent synchronization process its own `useEffect` with its own dependency array, so deleting one Effect would never break the other. |

## 1. Principle 1: The Effect Connects to One Room Until It Disconnects

### The component's perspective vs. the Effect's perspective

Suppose the user clicks the Open chat button, picks `travel`, picks `music`, and then clicks the Close chat button. How should we describe what just happened?

React's docs write out that exact four-step user journey twice: first from **the component's perspective**, and second from **the Effect's perspective**.

From **the component's perspective**, you see four lifecycle moments of `ChatRoom`:
1. `ChatRoom` mounted with `roomId` set to the general room.
2. `ChatRoom` updated with `roomId` set to the travel room.
3. `ChatRoom` updated with `roomId` set to the music room.
4. `ChatRoom` unmounted.

Now read the exact same user journey from **the Effect's perspective**:
1. Your Effect connected to the `"general"` room, until it disconnected.
2. Your Effect connected to the `"travel"` room, until it disconnected.
3. Your Effect connected to the `"music"` room, until it disconnected.

**It may look the same, or work the same at first, but it is NOT the same thing!** From the component's perspective, there is one mount, two updates, and one unmount. From the Effect's perspective, mounting, updating, and unmounting do not matter at all. There are simply three separate connections, one after another, and each one starts synchronizing and later stops synchronizing. React's docs put the warning in bold: "**It's a good way to think about components, but _not_ about Effects.**"

Why do the docs insist on **the Effect's perspective**? Because thinking of Effects as callbacks or lifecycle events that fire at a specific time such as after a render or before unmount "gets complicated very fast". Instead, as the docs advise: "always focus on a single start/stop cycle at a time. It shouldn't matter whether a component is mounting, updating, or unmounting."

```tree caption="The same four user actions seen from the component's perspective versus from the Effect's perspective."
One user journey seen from two perspectives
- !The component's perspective [`mount -> update -> update -> unmount`] | Counts **4 component moments**: 1 mount, 2 updates, 1 unmount | Tempts you to write separate code for mount and unmount
- +The Effect's perspective [`3 start/stop cycles`] | Counts **3 independent connections**: `general`, then `travel`, then `music` | Every cycle uses the **exact same setup and cleanup**
```

### Writing the Effect in `ChatRoom.jsx`

When we write `ChatRoom.jsx` from the Effect's perspective, we only describe how to start one connection and how to stop that connection:

```jsx title="src/components/ChatRoom.jsx"
import { useEffect } from 'react';
import { createConnection } from '../chat.js';

const ~serverUrl~ = 'https://localhost:1234'; // Fixed constant declared above the component

export default function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = ~createConnection(serverUrl, roomId)~; // Start synchronizing with roomId
    connection.connect();
    return () => {
      ~connection.disconnect()~; // Stop synchronizing with roomId
    };
  }, ~[roomId]~); // Re-run this start/stop cycle whenever roomId changes

  return <h1>Welcome to the {roomId} room!</h1>;
}
```

Look at where the names inside `ChatRoom.jsx` come from:
- **`createConnection`, `connect`, and `disconnect`** come from our `chat.js` file, which stands in for a real chat server.
- **`serverUrl`** is a constant declared at the top level of `ChatRoom.jsx` above the component, holding `'https://localhost:1234'`.
- **What if an Effect returns no cleanup function at all?** As the docs' Note explains, "React will behave as if you returned an empty cleanup function." For React's start and stop cycle, an Effect without a `return` and an Effect returning an empty function are **the exact same thing**. For our chat page, however, returning no cleanup means nothing ever calls `disconnect`.

### One component mount produces three connections

**Beware! During this journey, the `ChatRoom` component mounts only once, yet the Effect connects three separate times.** Follow the four user actions in a production build to see why one mount produces three connect lines in the Console:
1. **The user clicks the Open chat button**: `ChatRoom` mounts on the page for the general room, and the Effect runs its first setup, printing the connect line for `general`.
2. **The user picks `travel` in the menu**: `ChatRoom` stays on the page and updates its heading text in the DOM, while the Effect stops the old connection and starts the `travel` connection.
3. **The user picks `music` in the menu**: `ChatRoom` updates its heading text again, while the Effect stops the old connection and starts the `music` connection.
4. **The user clicks the Close chat button**: `ChatRoom` unmounts from the page, and the Effect stops the `music` connection.

```page width=text caption="The chat page in a production build after the user opens the chat, switches to travel, and switches to music."
form:
  select: Choose the chat room: | music | good
  button: Close chat
heading: Welcome to the music room!
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:5
log: ❌ Disconnected from "general" room at https://localhost:1234 | chat.js:8
log: ✅ Connecting to "travel" room at https://localhost:1234... | chat.js:5
log: ❌ Disconnected from "travel" room at https://localhost:1234 | chat.js:8
log: ✅ Connecting to "music" room at https://localhost:1234... | chat.js:5
```

If you inspect the browser's Elements panel while switching rooms, the heading element is never destroyed and recreated. Only the text inside the heading changes from one room name to the next. In development, Strict Mode adds one extra setup and cleanup cycle when the component first mounts, which Principle 2 traces line by line.

### Why thinking from the component's lifecycle leads to a bug

When a developer thinks from the component's perspective instead of the Effect's perspective, four things happen in order:
1. The developer thinks of the setup as "the code that runs on mount" and the cleanup as "the code that runs on unmount".
2. The developer writes the connect code with `[]` so it runs on mount, and writes the disconnect code thinking it will wait until unmount.
3. When the user clicks the Open chat button, the first room works.
4. As soon as the user picks `travel` in the menu, nothing reconnects because the component did not unmount or mount again. Principle 3 shows how to fix that array.

As the docs explain: "If you do it well, your Effect will be resilient to being started and stopped as many times as it's needed." They compare writing an Effect to writing JSX: "you don't think whether a component is mounting or updating when you write the rendering logic that creates JSX." In the docs' Deep Dive words, "The Effect is *also* a part of the rendering output." And as the `useEffect` reference summarizes: "When your cleanup logic correctly "mirrors" the setup logic, your Effect is resilient to running setup and cleanup as often as needed."

> [!PRINCIPLE]
> **Principle 1: Effect Lifecycle: Write One Start and Stop Cycle at a Time**
>
> *Write the setup to start synchronizing and the cleanup to stop synchronizing, and let React repeat that cycle whenever dependencies change.*
>
> A component can stay mounted on the screen while its props and state change across many renders. An Effect only knows how to start synchronizing in its setup function and stop synchronizing in its cleanup function. Focusing on a single setup and cleanup cycle makes the Effect resilient to starting and stopping as many times as React needs.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = ~createConnection(serverUrl, roomId)~; // Starts synchronizing for this roomId
>   connection.connect();
>   return () => ~connection.disconnect()~; // Stops synchronizing when roomId changes or ChatRoom unmounts
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   ~connection.connect()~; // **WRONG:** treats the Effect as mount-only code with no cleanup to stop it!
> }, []);
> ```

## 2. Principle 2: Picking travel Runs the Cleanup for general First

### Both functions read `roomId`, but not from the same render

Look again at the setup and cleanup inside `ChatRoom`:

```jsx title="The setup and cleanup inside ChatRoom.jsx"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId from the render that starts this Effect
  connection.connect();
  return () => {
    ~connection.disconnect()~; // Disconnects the connection created with that same render's roomId
  };
}, [roomId]);
```

The `useEffect` reference states the exact three-step timing for when React calls your setup and cleanup functions:
1. **On mount**: "Your setup code runs when your component is added to the page", when it mounts.
2. **On a commit with changed dependencies**: "After every commit of your component where the dependencies have changed: First, your cleanup code runs with the old props and state. Then, your setup code runs with the new props and state."
3. **On unmount**: "Your cleanup code runs one final time after your component is removed from the page", when it unmounts.

**It may look the same, or work the same at first, but it is NOT the same thing!** The cleanup function and the setup function sit inside the same `useEffect` call and use the same variable name `roomId`. Yet when the user switches the menu from `general` to `travel`, the cleanup and the setup do not see the same room. First, the cleanup disconnects from `"general"` using the previous render's value. Only then does the new setup connect to `"travel"` using the new render's value. As React's docs state in bold: "**React always cleans up the previous render's Effect before the next render's Effect.**"

When React stops the old Effect and starts the new Effect because a dependency changed, the docs call that step **re-synchronizing**. In the docs' words: "React needs to re-synchronize your Effect to re-connect you to a different room."

```tree dir=right caption="What React runs after a commit where roomId changed from general to travel."
How React re-synchronizes when `roomId` changes from `'general'` to `'travel'`
- +1. Commit the new UI [`Welcome to the travel room!`] | React updates the heading text in the DOM first
- +2. Run the OLD render's cleanup [`roomId` is `'general'`] | Calls `disconnect` from the **`'general'` render**
- +3. Run the NEW render's setup [`roomId` is `'travel'`] | Calls `connect` from the **`'travel'` render**
```

### Why the cleanup still holds `'general'` after the heading says `travel`

**Beware! When the user picks `travel`, the Console prints a disconnect line for `general` after the heading on the page already welcomes the user to the travel room.** Here is what happens in order when the user picks `travel`:
1. The user picks `travel` in the room menu, and `setRoomId` asks React for a re-render.
2. `App` renders and passes the new `roomId` down to the child component, and React commits the travel room heading to the DOM.
3. React compares the new dependency array `['travel']` with the previous array using `Object.is` (as seen in Lesson 32). Because `'travel'` and `'general'` are not equal, the docs explain: "The Effect can't be skipped."
4. React calls the cleanup function that the `general` render's setup returned. That cleanup disconnects the connection created for the general room, printing the disconnect line for `general`.
5. React calls the `travel` render's setup function, which creates a new connection and prints the connect line for `travel`.

Where did `"general"` inside that cleanup come from when the current prop is already `"travel"`? Every render of a component keeps its own snapshot of props and state (as seen in Lesson 15). As the docs explain in their Deep Dive: "Each Effect "captures" the `text` value from its corresponding render." During the first render, `roomId` was `'general'`, so the first render's Effect and its cleanup function captured that string:

```jsx title="The first render's Effect with 'general' captured in its snapshot"
() => {
  const connection = createConnection(serverUrl, ~'general'~); // Captured 'general' during the 1st render
  connection.connect();
  return () => ~connection.disconnect()~; // Always disconnects the 1st render's 'general' connection
}
```

Later, the user clicks the Close chat button while in the `music` room. `ChatRoom` unmounts from the page, and React calls the active render's cleanup one final time, printing the disconnect line for `music`.

### Why clicking Open chat in development prints three lines

**Beware! In development with Strict Mode, clicking the Open chat button prints three lines in the Console for a single mount: connect, disconnect, and connect again.** Here is what React runs on mount in development:
1. React runs the first render's setup for `general`, which prints the first connect line for `general`.
2. React immediately calls that setup's cleanup function, which prints the disconnect line for `general`.
3. React runs the setup for `general` once more, which prints the second connect line for `general`.

```page width=text caption="After the user clicks Open chat in development: Strict Mode runs setup, cleanup, and setup to verify that the Effect can re-synchronize."
form:
  select: Choose the chat room: | general
  button: Close chat
heading: Welcome to the general room!
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:5
log: ❌ Disconnected from "general" room at https://localhost:1234 | chat.js:8
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:5
```

As the docs explain: "In development, React always remounts each component once." They compare this check to "opening a door and closing it an extra time to check if the door lock works" (as seen in Lesson 32). Lesson 47 covers this development check in full, along with how saving a file in development also re-synchronizes your Effect.

What if `ChatRoom` re-renders while the room is still `'general'`? React compares the second render's `['general']` array with the first render's array using `Object.is`. As the docs state: "**Because all dependencies are the same, React *ignores* the Effect from the second render.** It never gets called." What if the third render later changes `roomId` to `'travel'`? The docs' Deep Dive notes that before applying the third render's Effect, React "needs to clean up the last Effect that _did_ run." So React cleans up the first render's Effect before running the third render's Effect.

### What happens when you forget the cleanup function

**Beware! Without a cleanup function, switching from `general` to `travel` never closes the connection to `general`, so the user ends up connected to both rooms at the same time.** Look at what happens when a developer leaves the `return` out of `ChatRoom.jsx`:
1. The setup function opens a connection to `roomId` and returns nothing.
2. When the user switches the menu from `general` to `travel`, React has no cleanup function to call for the previous room.
3. React immediately runs the new setup for `travel` and prints the connect line with no disconnect line for `general` before it.

>

> Each render captures its own snapshot of props and state. ## 3. Principle 3: Leaving roomId Out Keeps the Chat on general

### `[roomId]` vs. `[]` when the Effect body reads `roomId`

Compare two dependency arrays at the bottom of the exact same Effect body that reads `roomId`:

```jsx title="Listing roomId in the dependency array: [roomId]"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // Tells React this Effect depends on roomId
```

```jsx title="Leaving roomId out of the dependency array: []"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
  connection.connect();
  return () => connection.disconnect();
}, ~[]~); // **WRONG:** tells React this Effect depends on nothing, so it never reconnects!
```

**It may look the same, or work the same at first, but it is NOT the same thing!** When the user clicks the Open chat button, both versions connect to the `general` room and show the exact same screen and Console lines. The moment the user picks `travel` in the menu, the first version disconnects from the old room and connects to `travel`. The version with `[]` does nothing at all and stays connected to `general`.

How did React know that the first Effect needed to re-synchronize when `roomId` changed? In the docs' words: "It's because *you told React* that its code depends on `roomId` by including it in the list of dependencies". The docs break that down into three steps:
1. "You knew `roomId` is a prop, which means it can change over time."
2. "You knew that your Effect reads `roomId`".
3. "This is why you specified it as your Effect's dependency".

That leads to the rule the docs put in bold: "**You can't "choose" your dependencies.**" Every reactive value your Effect reads must be listed in its dependency array. The `exhaustive-deps` linter rule checks this automatically, as in its reference example:

```jsx title="The exhaustive-deps reference example: missing userId vs. complete array"
useEffect(() => {
  fetchUser(~userId~); // Reads userId inside the Effect
}, ~[]~); // **WRONG:** Missing 'userId' in the dependency array!

useEffect(() => {
  fetchUser(~userId~); // Reads userId inside the Effect
}, ~[userId]~); // Lists userId so the Effect runs again when userId changes
```

```tree caption="What happens with [roomId], with [], and with no dependency array at all when the Effect reads roomId."
Three ways to write the end of `useEffect` when the body reads `roomId`
- +With `[roomId]` [`[roomId]`] | Lists the reactive value the Effect reads | Re-synchronizes **only when `roomId` changes**
- !With `[]` [`[]`] | ~Leaves `roomId` out of the array | Never re-synchronizes when `roomId` changes; **stays stuck on `'general'`**
- !With no array at all [no array] | ~Omits the dependency array completely | Re-synchronizes **after every single commit**, even when typing in a message box
```

Notice the third box above: passing `[roomId]` and passing **no dependency array at all** are **NOT the same thing** either. Without a dependency array, the Effect re-synchronizes after every single commit of the component (as seen in Lesson 32). Suppose `ChatRoom` also has a text input for typing a chat message, as in the docs' first Challenge. Omitting the array makes typing every letter in the message box "*also* reconnects to the chat".

Sometimes a developer silences that warning by writing a comment to **suppress the linter** on the next line. React's docs warn against this directly: "Don't fix these problems by suppressing the linter!"

5. No disconnect line and no new connect line appear in the Console. The Effect is still holding the **stale value** `'general'` from the first render (as seen in Lesson 34).

### Stale closures and what to do when an Effect runs too often

In interviews, you will hear the `exhaustive-deps` documentation's name for this bug: leaving out a dependency "causes stale closures where the hook uses outdated values." In JavaScript, a **closure** is a function that remembers the variables from the scope where it was created. A **stale closure** is one from an earlier render that still holds outdated props or state. In the docs' Challenge on investigating a stale value bug, a pointer listener `handleMove` inside an Effect reads `canMove` while the linter is suppressed. Because the dependency array is empty, that listener "from the initial render will forever see" `canMove` as `true`, even after the user unticks the checkbox.

Why do Effects work this way? In the docs' words: "Effects are reactive blocks of code." "Unlike event handlers, which only run once per interaction, Effects run whenever synchronization is necessary." What if you want an Effect to connect only when a condition holds? As the docs' Hint states: "You can't declare an Effect conditionally. However, the code inside the Effect can use conditions!" That keeps your Hook at the top level of the component, following the rules of Hooks covered in Lesson 38.

And what if the linter flags a dependency that makes your Effect re-run too often? The docs' Pitfall explains: "The linter only knows when the dependencies are *wrong*. It doesn't know *the best* way to solve each case." Still, "All errors flagged by the linter are legitimate." Instead of suppressing the linter, you change the code so it no longer needs that reactive dependency. Lesson 36 does this with an Effect Event, and Lesson 37 removes object and function dependencies.

> [!PRINCIPLE]
> **Principle 3: Complete Dependencies: Never Suppress the Linter to Hide a Reactive Value**
>
> *List every reactive value that the Effect reads inside its dependency array, and never suppress the `exhaustive-deps` linter to shorten the array.*
>
> React only knows to re-synchronize an Effect when an item in the dependency array changes between renders according to `Object.is`. Leaving `roomId` out and silencing the linter keeps the first render's setup alive forever, leaving the app connected to a stale `roomId`.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId]~); // Includes roomId so React reconnects when roomId changes
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** suppressing exhaustive-deps lies to React about roomId!
> ```

## 4. Principle 4: A serverUrl in State Joins the Array

### `serverUrl` above the component vs. `serverUrl` in state

In Principle 1, `serverUrl` sat above the component as a constant, and our dependency array was `[roomId]`. Now suppose we let the user edit `serverUrl` in a text box by moving that URL into state inside `ChatRoom`. Compare the two places where `serverUrl` can live:

```jsx title="serverUrl declared above the component: not reactive"
const ~serverUrl~ = 'https://localhost:1234'; // Outside the component: never changes on a re-render

function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId]~); // Only roomId is reactive here
}
```

```jsx title="serverUrl declared in state inside the component: reactive"
function ChatRoom({ roomId }) {
  const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // Inside the component: can change on a re-render

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId, serverUrl]~); // Both roomId and serverUrl are reactive and belong in the array
}
```

**It may look the same, or work the same at first, but it is NOT the same thing!** Inside the Effect, the call to `createConnection` is character-for-character identical in both versions, and both start with `'https://localhost:1234'`. Yet the first `serverUrl` sits outside the component and "never changes due to a re-render", while the second `serverUrl` sits inside the component and "may change over time". As the docs explain, "dependencies only do something when they change over time!"

Look at the four terms React's docs use to draw this boundary:
- **What is a "reactive value"?** React's docs define it in bold: "**Props, state, and other values declared inside the component are _reactive_**". They are calculated during rendering and participate in the React data flow.
- **What is the "data flow"?** During rendering, React passes props and context into your component, reads your state snapshots, and runs the variables in your component body from top to bottom. That calculation during rendering is the React **rendering data flow**, and every value calculated in it is reactive.
- **What is a "stable" value?** Some values returned by React are guaranteed "to not change on a re-render". Two examples are the state setter from `useState` and the ref object from `useRef` (as seen in Lesson 30). As the docs' Note explains: "Stable values aren't reactive, so you may omit them from the list. Including them is allowed". That is why the linter never asks you to put `setServerUrl` or `setRoomId` in the dependency array.
- **What is a "mutable value" or "global variable"?** A value such as `location.pathname` or `ref.current` that "can change at any time completely outside of the React rendering data flow" is a **mutable value**.

What if `serverUrl` is neither a prop nor a state variable, and is instead a regular variable calculated in the component body? Look at the docs' example where `serverUrl` is calculated from a prop and a context value from `useContext` (as seen in Lesson 28). The nullish coalescing operator `??` falls back to the default URL when the prop is null or undefined:

```jsx title="A regular variable calculated in the component body is also reactive"
function ChatRoom({ roomId, selectedServerUrl }) {
  const settings = useContext(SettingsContext);
  const ~serverUrl~ = selectedServerUrl ?? settings.defaultServerUrl; // Calculated during rendering -> reactive!

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, [roomId, ~serverUrl~]); // Must list serverUrl because it can change on a re-render
}
```

As the docs explain: "It's a regular variable that you calculate during rendering". All values inside the component, including props, state, and variables in your component's body, are reactive.

What if neither `serverUrl` nor `roomId` ever comes from props or state? Compare declaring both constants above the component with declaring both constants inside the Effect:

```jsx title="Declaring fixed constants above the component vs. inside the Effect"
const ~serverUrl~ = 'https://localhost:1234'; // 1. Outside the component: not calculated during rendering
const roomId = 'general';

function ChatRoomOutside() {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // Empty array: uses zero reactive values
}

function ChatRoomInside() {
  useEffect(() => {
    const ~serverUrl~ = 'https://localhost:1234'; // 2. Inside the Effect: not calculated during rendering
    const roomId = 'general';
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // Exact same empty array: uses zero reactive values!
}
```

**Yes, it is the exact same thing** for the dependency array! As the docs explain: "They aren't calculated during rendering, so they're not reactive". To remove a dependency honestly, you move it outside the component or inside the Effect. As the `useEffect` reference puts it, "you need to "prove" to the linter that it *doesn't need* to be a dependency". That also shows what `[]` truly means from the Effect's perspective: not "run only on mount", but "your Effect's code does not use *any* reactive values". If `roomId` or `serverUrl` later moves into state, "your Effect's code won't change. You will only need to add them to the dependencies."

```tree caption="Which values read by an Effect are reactive and belong in the dependency array, and which do not."
Does a value read by an Effect belong in the dependency array?
- +Props, state, and variables in the component body [`roomId` `serverUrl`] | Calculated **during rendering** in the React data flow | **Reactive**: must be listed in `[roomId, serverUrl]`
- +Constants outside the component or inside the Effect [`const serverUrl` at top of file] | Never change due to a **re-render** | **Not reactive**: can be omitted, leaving `[]` when none remain
- +Stable values from React [`setServerUrl` `ref` object] | Guaranteed **not to change** on a re-render | **Stable**: omitting or including them is allowed
- !Mutable values outside rendering [`location.pathname` `ref.current`] | ~Change **outside React's rendering data flow** | **Cannot be dependencies** because changing them never triggers a re-render
```

### Adding the `Server URL:` input box to `ChatRoom.jsx`

Now we update `ChatRoom.jsx` so the server URL lives in state with a controlled input box (as seen in Lesson 20). We also add `serverUrl` to the dependency array:

```jsx title="src/components/ChatRoom.jsx"
import { useState, useEffect } from 'react';
import { createConnection } from '../chat.js';

export default function ChatRoom({ roomId }) {
  const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // Reactive state variable

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => {
      connection.disconnect();
    };
  }, ~[roomId, serverUrl]~); // Re-synchronizes whenever either roomId or serverUrl changes

  return (
    <section>
      <label>
        Server URL:{' '}
        <input
          ~value={serverUrl}~ // Shows the current serverUrl in the input box
          ~onChange={e => setServerUrl(e.target.value)}~ // Updates serverUrl on every keystroke by the user
        />
      </label>
      <h1>Welcome to the {roomId} room!</h1>
    </section>
  );
}
```

**Beware! Because `serverUrl` is now a reactive dependency in `[roomId, serverUrl]`, every single keystroke by the user in the URL box disconnects from the old URL and connects to the new URL.** Here is what happens when the user types `5` at the end of `https://localhost:1234`:
1. The user types `5` at the end of the `Server URL:` box.
2. `setServerUrl` updates state with the new URL and asks React to re-render `ChatRoom`.
3. React compares the new dependency array with the previous render's array using `Object.is`.
4. Because `serverUrl` changed, React calls the previous render's cleanup function, which prints the disconnect line for `https://localhost:1234`.
5. React runs the new render's setup function, which prints the connect line for `https://localhost:12345`.

### Why mutable values like `location.pathname` and `ref.current` cannot be dependencies

**Beware! Putting a mutable value such as `location.pathname` or `ref.current` in the dependency array will not make your Effect re-run when that value mutates.** Walk through the four steps from the docs' Deep Dive "Can global or mutable values be dependencies?":
1. A developer wants an Effect to re-synchronize when `location.pathname` or `ref.current` changes (as seen in Lesson 30). So the developer puts that value in the dependency array.
2. Later, some code outside React mutates `location.pathname` or assigns a new value to `ref.current`.
3. Because mutating an external object or `ref.current` happens completely outside of the React rendering data flow, it does not trigger a re-render of the component.
4. Because the component never re-renders, React never checks the dependency array. As the docs explain: "even if you specified it in the dependencies, React *wouldn't know* to re-synchronize the Effect when it changes."

To subscribe to an external mutable value such as `location.pathname`, the docs recommend `useSyncExternalStore`, a Hook covered in Lesson 53. What if a prop or variable in the component body is an object or a function created during rendering? The docs' Challenge on fixing a connection switch shows this with `createConnection`. A function created during rendering is a brand-new function on every render, so listing it re-synchronizes the Effect on every render. Passing a simple boolean prop such as `isEncrypted` instead keeps the dependency stable across renders, which Lesson 37 covers in full.

> [!PRINCIPLE]
> **Principle 4: Reactive Values: Everything Calculated in the Component Body Belongs in the Array**
>
> *Props, state, and variables in the component body are reactive and belong in the dependency array; constants outside rendering are not reactive, and mutable values cannot be dependencies.*
>
> A value is reactive when it is calculated during rendering as part of the React data flow. Moving `serverUrl` from a top-level file constant into state or calculating it inside the component means it can change on a re-render, so it must join `[roomId, serverUrl]`. Conversely, mutating `ref.current` or `location.pathname` never triggers a re-render, so listing them in the array will never re-synchronize the Effect.
>
> **DO THIS:**
> ```jsx
> function ChatRoom({ roomId }) {
>   const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // Reactive state inside the component
>   useEffect(() => {
>     const connection = createConnection(serverUrl, roomId);
>     connection.connect();
>     return () => connection.disconnect();
>   }, ~[roomId, serverUrl]~); // Lists both reactive values read by the Effect
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ChatRoom({ roomId }) {
>   useEffect(() => {
>     const connection = createConnection(serverUrl, roomId);
>     connection.connect();
>     return () => connection.disconnect();
>   }, [roomId, ~ref.current~]); // **WRONG:** mutating ref.current never triggers a re-render, so it cannot be a dependency!
> }
> ```

## 5. Principle 5: Logging the Visit Gets Its Own Effect

### One Effect for both jobs vs. two separate Effects

Now we want our app to send an analytics visit log calling `logVisit` whenever the user visits a chat room (as seen in Lesson 34). Compare two ways to add `logVisit` to `ChatRoom`:

```jsx title="Putting logVisit inside the connection Effect"
useEffect(() => {
  ~logVisit(roomId);~ // **WRONG:** also runs every time serverUrl changes!
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId, serverUrl]~); // Re-runs when either roomId OR serverUrl changes
```

```jsx title="Giving logVisit its own Effect with [roomId]"
useEffect(() => {
  ~logVisit(roomId);~ // 1st process: logs a visit only when roomId changes
}, ~[roomId]~); // Re-runs only when roomId changes

useEffect(() => {
  const connection = ~createConnection(serverUrl, roomId)~; // 2nd process: reconnects when roomId or serverUrl changes
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId, serverUrl]~); // Re-runs when roomId or serverUrl changes
```

**It may look the same, or work the same at first, but it is NOT the same thing!** When the user first opens the chat or switches rooms, both versions call `logVisit` once per room change. The difference appears the moment the user types a character into the URL box. The single combined Effect calls `logVisit` again on every keystroke in the URL box. The two separate Effects reconnect to the new URL without logging a new room visit.

Why must those two jobs live in two separate Effects? React's docs state that each Effect in your code should represent "**a separate and independent synchronization process**". For our chat room, the docs explain that logging the visit "**is a separate process** from connecting".

What is the docs' test for whether two pieces of logic belong in two separate Effects or one? Ask whether "deleting one Effect wouldn't break the other Effect's logic." If you delete the visit Effect, the chat connection still works. If you delete the chat connection Effect, the visit log still works. Therefore, they are two separate synchronization processes and belong in two separate Effects.

What about the opposite case, splitting one cohesive synchronization process into two separate Effects just to make each block shorter? That is **NOT the same thing**! As the docs warn: "if you split up a cohesive piece of logic into separate Effects, the code may look "cleaner" but will be more difficult to maintain." And: "you should think whether the processes are same or separate, not whether the code looks cleaner."

```tree caption="How to decide whether code belongs in one Effect or two separate Effects."
One Effect or two Effects? Ask whether the synchronization processes are separate
- !Two separate processes in one Effect [`logVisit` + `createConnection` in one `useEffect`] | Shares `[roomId, serverUrl]` between **both jobs** | Changing `serverUrl` **falsely logs a new visit** for the same room
- +One Effect per synchronization process [`[roomId]` for visit, `[roomId, serverUrl]` for connection] | Deleting one Effect **does not break** the other | Each Effect re-synchronizes **only when its own dependencies change**
- !One cohesive process split into two Effects for looks | Splits one setup across two blocks | Makes the code **harder to maintain** without separating dependencies
```

### Adding `analytics.js` and testing both versions

First, we create `analytics.js`, which exports `logVisit` and prints a line in the Console whenever a visit is recorded:

```js title="src/analytics.js"
export function ~logVisit~(roomId) { // Sends an analytics event when the user visits roomId
  console.log('Visited "' + roomId + '" room');
}
```

**Beware! When `logVisit` sits inside the connection Effect, typing a single character in the `Server URL:` box logs a brand-new visit for the room the user never left.** Here is how that bug unfolds in practice:
1. A developer already has an Effect that runs when `roomId` changes, and drops `logVisit` onto its first line because both happen when the user enters a room.
2. Later, `serverUrl` becomes state and joins the dependency array `[roomId, serverUrl]`.
3. The user types `5` at the end of the URL box while staying inside the `general` room.
4. Because `serverUrl` changed, React re-synchronizes the Effect and runs its setup again.
5. As the docs explain, the Effect now calls `logVisit` "for the same room, which you did not intend." Your analytics now count a fresh visit for every character the user typed into the URL box.

Giving `logVisit` its own Effect with `[roomId]` fixes the bug immediately:

In development with Strict Mode, the visit Effect also runs twice on mount (as seen in Lesson 34). The docs keep analytics code as is rather than blocking the second run. On mount, React runs the two Effects in the exact order they appear in the component: `logVisit` runs first, and the connection setup runs second.

### Two independent fetches, custom Hooks, and Effect Events

This same principle decides the docs' Challenge with planets and places in two dropdown menus. One menu loads the list of planets, and the second menu loads the list of places on the selected `planetId`. Because those are two independent synchronization processes, they belong in two separate Effects. Combining them into one Effect would make "changing the planet ... refetch the list of all planets". As the docs state: "Effects are not a tool for code reuse." When two separate Effects share similar data-fetching code, you extract a custom Hook such as `useSelectOptions` to reuse the logic cleanly, which Lesson 39 covers.

What if `logVisit` inside a visit Effect needs to include the current shopping cart count without logging a new page visit every time the user adds an item? That is where one synchronization process needs to read the latest value without re-synchronizing, which Lesson 36 solves with an Effect Event and `useEffectEvent`.

> [!PRINCIPLE]
> **Principle 5: Independent Processes: Give Each Synchronization Process Its Own Effect**
>
> *Each Effect in your component should represent one separate and independent synchronization process, with its own dependency array.*
>
> Putting two unrelated jobs in one Effect forces both jobs to re-run whenever any dependency of either job changes. Test whether two pieces of logic belong in separate Effects by asking whether deleting one Effect would break the other. If each works on its own, give each its own `useEffect`.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   ~logVisit(roomId);~ // 1st independent process: runs only when roomId changes
> }, ~[roomId]~); // Re-runs only when roomId changes
>
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId); // 2nd independent process
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId, serverUrl]~); // Re-runs when roomId or serverUrl changes
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~logVisit(roomId);~ // **WRONG:** shares [roomId, serverUrl], so editing serverUrl logs a false room visit!
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, [roomId, serverUrl]);
> ```

| Aspect | The Common Mistake | The React Rule |
| :--- | :--- | :--- |
| **Mental model** | Think of the Effect as mount code and unmount code tied to the component's lifecycle | Think from the Effect's perspective: one repeatable cycle of start synchronizing in setup and stop synchronizing in cleanup |
| **Cleanup timing and values** | Assume cleanup runs only on unmount or reads the new render's props | Cleanup runs before every re-render with changed dependencies and once on unmount, reading the old render's snapshot |
| **Choosing dependencies** | Pass `[]` and suppress `exhaustive-deps` so the Effect runs only once | Include every reactive value the Effect reads so React compares each spot with `Object.is` and never holds a stale value |
| **Which values are reactive** | Forget component-body variables, or put `ref.current` and `location.pathname` in the array | Props, state, and component-body variables are reactive; constants outside rendering are not; mutable values cannot be dependencies |
| **Multiple processes** | Put `logVisit` inside the connection Effect because both run when entering a room | Give each independent synchronization process its own `useEffect` with its own dependency array |

## For the Interview

> **The Interview Question:** What is the lifecycle of a reactive effect as its dependencies change?

### How to Answer Clearly in 30 Seconds

"An Effect has a different lifecycle from a component. A component mounts, updates, and unmounts, whereas an Effect only does two things: its setup function starts synchronizing with an external system, and its cleanup function stops synchronizing. While a component stays mounted on the screen, React can repeat that start and stop cycle many times:
1. **How React knows to re-synchronize**: on every render, React compares each value in the Effect's dependency array with the value at the same spot from the previous render using `Object.is`. When all values are the same, React skips the Effect.
2. **Exact order when a dependency changes**: after React commits the new UI, it first runs the previous render's cleanup function with the old props and state. Then it runs the new render's setup function with the new props and state. When the component finally unmounts, React runs the last cleanup one final time.
3. **Reactive values and independent Effects**: every prop, state variable, and variable calculated in the component body that the Effect reads is reactive and must be in the dependency array. Omitting a reactive value and suppressing the linter creates a stale closure where the Effect stays connected to the initial render's value. Omitting the cleanup leaks open connections. Finally, each Effect should represent one independent synchronization process."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"When `roomId` changes from `'general'` to `'travel'`, why does the cleanup function disconnect from `'general'` instead of `'travel'`?"**
   Because each render in React has its own snapshot of props and state, and its own Effect function that closes over that snapshot. The cleanup function that React runs after the `'travel'` commit is not created during the `'travel'` render; it is the function returned by the `'general'` render's setup. Because that cleanup function was created inside the `'general'` render, `roomId` inside its closure is forever `'general'`, and `connection` is the exact connection opened for `'general'`. React cleans up that previous render's Effect first, and only then calls the `'travel'` render's setup.
2. **"What counts as a reactive value, and can `ref.current` or `location.pathname` be placed in the dependency array?"**
   Every value declared or calculated inside the component body is a reactive value because it participates in the React rendering data flow. That includes props, state, and regular `const` variables calculated from them during rendering. Constants declared outside the component or inside the Effect never change due to a re-render and are not reactive. React also guarantees that `useState` setters and the `useRef` object itself are stable. By contrast, mutable values such as `ref.current` and `location.pathname` change outside of React's rendering data flow without triggering a re-render. Even if you list them in the dependency array, React will not know to re-run the component or compare the array when they mutate. For external mutable stores, you use `useSyncExternalStore` instead.
3. **"What happens if I suppress the `exhaustive-deps` linter and pass `[]` so my Effect only runs once?"**
   From the Effect's perspective, `[]` does not mean "run on mount"; it means "this Effect reads zero reactive values." If the Effect actually reads a reactive value such as `roomId` and you suppress the linter with `[]`, you lie to React about what the Effect depends on. When `roomId` changes from `'general'` to `'travel'`, React compares `[]` with `[]`, sees no change, and skips re-synchronizing. The Effect stays stuck on a stale closure holding `'general'` while the UI shows `'travel'`. When an Effect re-synchronizes too often because of a dependency, never suppress the linter. Instead, move fixed constants outside the component or inside the Effect, split unrelated processes into separate Effects, or use `useEffectEvent` when reading a value should not trigger re-synchronization.

```tree dir=right caption="Interview summary: how React runs an Effect across mount, dependency change, unchanged re-render, and unmount."
The complete lifecycle of a reactive Effect
- +Mount [`1st commit`] | Runs the **1st render's setup** | In development, `<StrictMode>` runs **setup -> cleanup -> setup** to verify cleanup
- +Re-render with same dependencies [`Object.is` is `true` for all] | React **skips the Effect** | Existing synchronization **keeps running** untouched
- +Re-render with changed dependency [`Object.is` is `false`] | **1st**: old render's **cleanup** with old values; **2nd**: new render's **setup** with new values | Re-synchronizes cleanly without leaking connections or holding stale values
- +Unmount [`Removed from page`] | Runs the **last active cleanup** one final time | Stops synchronizing when the component leaves the screen
```
