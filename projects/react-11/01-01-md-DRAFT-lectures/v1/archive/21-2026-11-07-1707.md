# Lecture 21: Reacting to Input with State Instead of Touching the Page
> INTERVIEW QUESTION | ❱ CORE | How do you design a component that reacts to input with state instead of touching the DOM?

## Why a Page Needs One State for Each Look

### The smallest version: one button with two looks

Here is a tiny page with one button. When the page opens, the button says Send:

```page width=text caption="A page with one Send button, when the page opens."
form:
  button: Send
```

This is all the code behind it:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [status, setStatus] = useState('ready');

  return (
    <button onClick={() => setStatus('sending')}>
      {~status === 'sending'~ ? 'Sending...' : 'Send'} {/* The text of the button for each value of status */}
    </button>
  );
}
```

The user clicks the button, and its text changes:

```page width=text caption="The same page after the user clicks the button."
form:
  button: Sending... | good
```

Look at the click handler once more. It only puts the word sending into `status`. No line of our code writes Sending... onto the button. So who changes the text?

React does. Here is what happens, in order:
1. The user clicks, and React calls our arrow.
2. `setStatus` saves `'sending'` in state, as you saw in Lesson 12.
3. React calls `App` again.
4. This time the check `status === 'sending'` is true, so the JSX gives Sending... as the text of the button.
5. React sees that the text is different from the last render, and changes it on the page.

`status` is our own name, and React does not care what we call it. It is a normal state variable that holds one word from a short list, here `'ready'` or `'sending'`. Each word stands for one look of the button.

So the work is split in two. The handler says which look comes next. The JSX says what each look shows. This split is the whole lesson.

### One look at a time, like a parcel tracker

Think of the parcel tracker on a shop website. It has four steps: Ordered, Shipped, Out for delivery, and Delivered. Exactly one step is lit at any moment. Nobody ever sees Out for delivery and Delivered lit together.

Our button works the same way. It is ready or it is sending, never both. A real form has more than two looks, and it should still show exactly one of them at a time.

### The real page: a newsletter box that shows two answers

Now think of the newsletter box at the bottom of a news site. It asks for an email, and it has a Sign up button. After the click, it shows Sending... and turns the button off. A moment later, the answer comes back. The page shows either an error or a thank-you line. After an error, the user can fix the email and try again.

Every one of these events changes several parts of the box. In plain JavaScript, you write a command for each part, in each event. Forget one command, and an old part stays on the screen next to a new one. In Principle 1, our box ends up showing the error line right above the thank-you line.

This lecture shows how React avoids that bug. You describe each look once, and you keep the current look in state.

### Our example page: the newsletter sign-up box

Our page is the newsletter sign-up box of a news site. Here is the finished box when the page opens. The Sign up button is off, because the box is still empty:

```page width=text caption="The finished newsletter box when the page opens, with the Sign up button off."
heading: Get our weekly newsletter
form:
  field: Email |
  submit: Sign up
```

There is no real server in this lesson. A timer waits 1500 milliseconds and then plays the answer. The email john@mail.com is already on the list, so it gets the error. Any other email gets the thank-you line.

The project has a small plain page for Principle 1, and a React app for the rest of the lesson:

```files title="newsletter-page: File Explorer" caption="The plain page in plain/ and the React app in src/."
plain/

  signup.js | plain script | Changes each part of the plain box with commands
index.html | entry | The HTML page with the empty root div where React mounts

```

A few ideas from earlier lessons come back here:
- Plain JavaScript finds an element with `document.getElementById` and changes its text with `textContent`, from Lesson 01. That lesson also showed that one forgotten command leaves part of the screen out of date.
- `addEventListener` hands a function to the browser to call later, from Lesson 04.
- `disabled={true}` turns a button off, and `disabled={false}` turns it on, from Lesson 03.
- An early `if` with `return`, the `? :` choice, and `&&` decide which JSX to show, from Lesson 10.
- A prop can have a default value, written with `=` in the parameter list, from Lesson 09.
- A submit handler calls `e.preventDefault` so the browser does not reload the page, from Lesson 11.
- Our code must not change the parts of the page that React draws, from Lesson 13.
- `setTimeout` runs a function later, and that function still sees the state of the render that made it, from Lesson 15.
- `map` with a `key` draws one element for each item of an array, from Lesson 18.
- A controlled box gets `value` from state and saves each key with `onChange`, from Lesson 20.

### Five Principles of Reacting to Input with State

**PRINCIPLES:**
1. **Commands must cover every change.** In plain JavaScript, every event needs a command for every part of the page. One forgotten command leaves an old part on the screen.
2. **List every look and draw it first.** Before any handler, write down every look of the box, and draw each one from a hand-set `status`.
3. **Find what moves the page.** For every change between two looks, name its cause. The user causes some changes, and the computer causes others. Both must set state.
4. **Keep the look in one `status` string.** Separate true or false values allow mixes that no look matches. Anything that can be worked out from other state is not stored at all.
5. **Handlers only set the next state.** A handler names the next look. React makes the page match the JSX.

Here is the map of the five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Commands Must Cover Every Change** | A form that shows an error and a thank-you line together is the classic bug of plain JavaScript pages. Interviewers ask why React avoids it. | Describe each look once in JSX, instead of writing commands for every change. |
| **Principle 2** | **List Every Look and Draw It First** | A look that nobody drew, such as an error with the box still off, reaches the user broken. | List every visual state, and draw each one from a `status` prop before writing any handler. |
| **Principle 3** | **Find What Moves the Page** | A page stuck on Sending... forever means one cause never set state. | Name the cause of every change. Clicks, typing, and answers from the computer all set state. |
| **Principle 4** | **One `status` String, Not Many True or False Values** | Separate true or false values can show Sending... and an error at the same time. | Keep the current look in one `status` string, and work out everything else from state. |
| **Principle 5** | **Handlers Only Set the Next State** | Changing the page by hand next to React leaves parts of the page stuck. | A handler calls the setter with the next look, and React updates the page. |

## 1. Principle 1: Commands Must Cover Every Change, So One Forgotten Command Breaks the Page

### The smallest version: a button that changes its own text

Here is the same Send button in plain JavaScript, with no React. The script must change the button itself, once for each event:

```js title="plain/send.js"
const button = document.getElementById('send');

button.addEventListener('click', () => {
  ~button.textContent = 'Sending...'~; // Command 1: runs when the user clicks
  setTimeout(() => {
    ~button.textContent = 'Send'~; // Command 2: runs when the timer ends
  }, 1500);
});
```

Compare it with the React button at the start of the lecture. There, our handler changed only `status`. Here, our code changes the text of the button directly, and it needs one command for every change. Lesson 01 called this style imperative: the code gives the page one order after another.

Think of giving a friend directions to your house. Turn left at the bakery. Go two blocks. Turn right at the school. Your friend follows every order. If you forget one turn, they end up on the wrong street. Commands work the same way. The browser does exactly what each command says, and a missing command leaves the page in the wrong place.

### The plain newsletter page

Now we build the whole newsletter box in plain JavaScript. The page has a form with a box, a button, and three empty lines. Each line waits for its own message:

```html title="plain/index.html"
<form id="form">
  <h2>Get our weekly newsletter</h2>
  <label>Email <input id="email" /></label>
  <button id="signup">Sign up</button>
  <p id="sending"></p>
  <p id="error"></p>
  <p id="thanks"></p>
</form>
<script src="signup.js"></script>
```

The script finds every part. Then it says what happens after a click, and what happens when the answer comes:

```js title="plain/signup.js"
const form = document.getElementById('form');
const box = document.getElementById('email');
const button = document.getElementById('signup');
const sending = document.getElementById('sending');
const errorText = document.getElementById('error');
const thanks = document.getElementById('thanks');

form.addEventListener('submit', e => {
  e.preventDefault();
  button.disabled = true;
  sending.textContent = 'Sending...';

  setTimeout(() => {
    sending.textContent = '';
    button.disabled = false;
    if (box.value === 'john@mail.com') {
      errorText.textContent = 'This email is already signed up.';
    } else {
      ~thanks.textContent = 'Thanks! You are signed up.'~; // Writes the thank-you line, and nothing else
    }
  }, 1500);
});
```

Two small helpers appear here. `button.disabled` is the browser's own switch behind the `disabled` attribute of Lesson 03. `box.value` is the text in the box at that moment. To keep the script short, the button stays on even when the box is empty.

The user types john@mail.com and clicks Sign up. The button turns off, and the sending line appears:

```page width=text caption="The plain page right after the user types john@mail.com and clicks Sign up. The button is off."
heading: Get our weekly newsletter
form:
  field: Email | john@mail.com
  submit: Sign up
line: Sending...
```

After 1500 milliseconds, the timer runs. The sending line goes away, the button turns on, and the error line appears:

```page width=text caption="The plain page 1500 milliseconds later: the email is already on the list."
heading: Get our weekly newsletter
form:
  field: Email | john@mail.com
  submit: Sign up
line: This email is already signed up.
```

So far, everything is right. The user now changes the email to mary@mail.com and clicks Sign up again. After 1500 milliseconds, the page looks like this:

```page width=text caption="The plain page after the second try with mary@mail.com: both answers are on the page."
heading: Get our weekly newsletter
form:
  field: Email | mary@mail.com
  submit: Sign up
line: This email is already signed up. | bad
line: Thanks! You are signed up. | good
```

The second try worked. So why does the page still say that the email is already signed up? Here is what happened, in order:
1. The user typed john@mail.com and clicked Sign up.
2. The listener turned the button off and wrote Sending...
3. After 1500 milliseconds, the timer cleared Sending..., turned the button on, and wrote the error into the error line.
4. The user changed the email to mary@mail.com and clicked Sign up again.
5. The listener turned the button off and wrote Sending... No line cleared the error.
6. The timer wrote the thank-you line. Again, no line cleared the error.
7. Both lines now stand on the page together.

### Two looks on the screen at once

The box is now showing two answers that can never both be true. Each answer belongs to a different look of the box. One look is the error, and the other is the success. React's documentation calls each look a **visual state**: one look of the component that the user can see, such as empty, sending, error, or success.

Think back to the parcel tracker. Our page has lit two steps at once, Out for delivery and Delivered. A real tracker never does that, and our box should not either.

### Where did the old error line come from?

The success branch never writes the error. So where does the error line on the last screen come from? The browser kept it. Open the Elements panel, and the error paragraph still holds its text:

```dom caption="The Elements panel of the plain page after the second try: the error paragraph still holds the text from the first try."
<form id="form">
  <h2>Get our weekly newsletter</h2>
  <label>Email <input id="email"></label>
  <button id="signup">Sign up</button>
  <p id="sending"></p>
! <p id="error">This email is already signed up.</p> | note: Written by the first try, never cleared
+ <p id="thanks">Thanks! You are signed up.</p> | note: Written by the second try
</form>
```

Here is why the text is still there:
1. The first try wrote the error text into the error paragraph.
2. The browser keeps that text until a command changes it.
3. No command in the success branch changes it.

The fix in plain JavaScript is one more command. The developer adds `errorText.textContent = ''` to the success branch. From now on, they must remember the same line in every new branch they write.

### Why this is not a one-off slip

A forgotten line looks like a small mistake. It is not, because the page asks for many commands:
1. Every event must say what happens to every part: the box, the button, the sending line, the error line, and the thank-you line.
2. The box has five parts and three events: the click, the error answer, and the success answer. That is fifteen places where a command may be needed, and most of those commands only undo what an earlier event did.
3. A new part, such as a second error message, needs new commands in every event.

React's documentation says it plainly: adding a new part or a new interaction "would require carefully checking all existing code to make sure you haven't introduced a bug." A forgotten line that should show or hide something is exactly that bug.

This is the same cause as the cart bug of Lesson 01, a forgotten command. In Lesson 01, one number was shown in two places. Here, one box has several looks, and the forgotten command belongs to a move from one look to another.

### `button.disabled = true` and `disabled={...}` are NOT the same

In the React version of this box, you will soon write the button like this:

```jsx title="src/components/NewsletterForm.jsx"
<button ~disabled={status === 'submitting'}~>Sign up</button> {/* React reads this again on every render */}
```

The plain script turns its button off like this:

```js title="plain/signup.js"
~button.disabled = true~; // Runs once, at the moment of the click
```

Both end with a button that is off, but they are NOT the same thing. Here is what each one does when a new event arrives:
- **The plain command** runs once, at the moment of the click. The button stays off until another command turns it on. If that command is missing, the button stays off forever.
- **The JSX attribute** is a description. React reads it again on every render. When `status` changes, React works out the new answer and makes the button match.

So the command must be undone by another command. The description is simply read again.

> [!PRINCIPLE]
> **Principle 1: Commands: Every Change Needs a Command for Every Part**
>
> *When a page has several looks, plain JavaScript must change every part of the page after every event; React instead describes each look once.*
>
> This is a trap that waits for the second try. The first answer writes the error line, and the browser keeps it there until a command clears it. If the success branch forgets that one command, the user sees the error line and the thank-you line together. Every new part of the page adds new commands to every event, so the trap grows with the page. In React, the JSX says what each look shows, and React works out which parts to change.
>
> **DO THIS:**
> ```jsx
> function SignupButton({ status }) {
>   return <button ~disabled={status === 'submitting'}~>Sign up</button>; // A description React reads on every render
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> setTimeout(() => {
>   ~thanks.textContent = 'Thanks! You are signed up.'~; // **WRONG:** the old error line is never cleared, so both answers show
> }, 1500);
> ```

## 2. Principle 2: List Every Visual State and Draw Each One Before Writing Logic

### The smallest version: a button drawn from a prop

Before a designer's work reaches the developers, the designer draws a picture of every screen. There is one drawing for the empty form, one for the sending form, one for the error, and so on. Nobody writes any logic until every drawing is ready.

React lets us do the same with a component. Here, the Send button gets its look from a prop called `status`, not from state:

```jsx title="src/App.jsx"
function SendButton({ ~status = 'ready'~ }) { // Uses ready when the tag passes no status
  return <button>{status === 'sending' ? 'Sending...' : 'Send'}</button>;
}

export default function App() {
  return <SendButton ~status="sending"~ />; // Draws the sending look, with no click at all
}
```

The page opens, and the button already shows the sending look:

```page width=text caption="The SendButton page, drawn with status set to sending by hand."
form:
  button: Sending...
```

Change `"sending"` to `"ready"` in the tag, save, and the button says Send. Each look can be checked by changing one word by hand. A component drawn like this, from a hand-set value and with no logic yet, is called a **mock**.

### The five looks of the newsletter box

React's documentation lists five looks for a form like ours. Here they are for our newsletter box:
1. **Empty**: the box has no text, and the Sign up button is off.
2. **Typing**: the box has some text, and the button is on.
3. **Submitting**: the box and the button are both off, and Sending... shows.
4. **Success**: the thank-you line shows instead of the whole form.
5. **Error**: the same as typing, plus the error line.

This list is a design decision, not a coding one. Ask what the user must see, not what the code must do.

### Drawing each look with a `status` prop

Now we turn the list into a mock. `NewsletterForm` takes `status` as a prop, and draws the look that matches it:

```jsx title="src/components/NewsletterForm.jsx"
export default function NewsletterForm({ status = 'empty' }) {
  if (~status === 'success'~) { // The success look replaces the whole form
    return <p>Thanks! You are signed up.</p>;
  }

  return (
    <form>
      <h2>Get our weekly newsletter</h2>
      <label>
        Email
        <input disabled={status === 'submitting'} />
      </label>
      <button disabled={status === 'empty' || status === 'submitting'}>Sign up</button>
      {status === 'submitting' && <p>Sending...</p>}
      {~status === 'error'~ && <p>This email is already signed up.</p>} {/* Drawn only in the error look */}
    </form>
  );
}
```

The success look is different from the other four. It returns a different piece of JSX, so it gets an early `return` at the top. The other four looks share one form. The button is off in two of them, empty or submitting.

Now `App` draws the error look:

```jsx title="src/App.jsx"
import NewsletterForm from './components/NewsletterForm.jsx';

export default function App() {
  return <NewsletterForm ~status="error"~ />; // Asks for the error look by hand
}
```

The page opens, and the error line is already there:

```page width=text caption="The newsletter mock drawn with status set to error. Nobody has clicked anything."
heading: Get our weekly newsletter
form:
  field: Email |
  submit: Sign up
line: This email is already signed up.
```

No click happened. So how does the page already show the error line? Here is what happens when the page opens:
1. `App` renders `<NewsletterForm status="error" />`.
2. React calls `NewsletterForm` with `status` set to `'error'`.
3. The early `if` for success does not match, so the form is drawn.
4. The check `status === 'error'` is true, so the `&&` draws the error line.

The box is empty, because the mock has no text in it. Only the button and the lines change from one look to the next.

If `App` writes `<NewsletterForm />` with no `status` at all, the prop is `undefined`. The default value `'empty'` in the parameter list takes its place, so the empty look is drawn.

### All five looks on one page

Changing one word by hand works, but there is a faster way. `App` can draw all five looks at once, one copy of the box for each:

```jsx title="src/App.jsx"
import NewsletterForm from './components/NewsletterForm.jsx';

const statuses = ['empty', 'typing', 'submitting', 'success', 'error'];

export default function App() {
  return (
    <main>
      {statuses.map(status => (
        <section ~key={status}~> {/* One copy of the box for each look */}
          <h4>{status}</h4>
          <NewsletterForm status={status} />
        </section>
      ))}
    </main>
  );
}
```

Each copy of `NewsletterForm` gets its own `status`, and draws its own look:

```page width=text caption="All five looks of the newsletter mock on one page. The button is off in empty and submitting, and the box is off in submitting."
section: empty
heading: Get our weekly newsletter
form:
  field: Email |
  submit: Sign up
section: typing
heading: Get our weekly newsletter
form:
  field: Email |
  submit: Sign up
section: submitting
heading: Get our weekly newsletter
form:
  field: Email |
  submit: Sign up
line: Sending...
section: success
line: Thanks! You are signed up.
section: error
heading: Get our weekly newsletter
form:
  field: Email |
  submit: Sign up
line: This email is already signed up.
```

A page like this is often called a **living styleguide** or a **storybook**. Teams keep one so that a designer can check every look in a few seconds.

### Mistake: the box that stays off under the error

Here is a look that a developer forgets to check. While the form is sending, the box should be off, so the user cannot change the email halfway. A developer writes the box like this:

```jsx title="src/components/NewsletterForm.jsx" startLine="11" bad="11"
        <input ~disabled={status !== 'typing'}~ /> {/* **WRONG:** also off in the error look */}
```

They test only the typing look and the submitting look. In both, the box behaves well. Then the first real error arrives:
1. The error line appears, so the user wants to fix the email.
2. The box reads `status !== 'typing'`, and `'error'` is not `'typing'`.
3. So the box is off, and the user cannot type a new email.

React's documentation warns about exactly this: "you never want to show an error message and disable the input at the same time, or the user won't be able to correct the error!" On the page with all five looks, the mistake is plain to see:

```page width=text caption="The error look with the wrong rule: the box is off right under the error line."
section: error
heading: Get our weekly newsletter
form:
  field: Email | | bad
  submit: Sign up
line: This email is already signed up.
```

The fix names the one look where the box must be off: `disabled={status === 'submitting'}`.

### The `status` prop and the `status` state are NOT the same

In Principle 4, `status` moves from a prop into state. The same JSX reads it in both cases, but they are NOT the same thing:
- **The prop** is set by the parent. Nothing inside `NewsletterForm` can change it, so the mock never changes its look by itself.
- **The state** is set by our own handlers. When the user clicks Sign up, the handler sets a new `status`, and the look changes.

So the mock is a set of drawings. The state version is the same drawings, with a way to move from one to the next.

> [!PRINCIPLE]
> **Principle 2: Visual States: Draw Every Look Before Writing Any Logic**
>
> *List every look the component can have, and draw each one from a single `status` value before you write any handler.*
>
> A look that nobody drew is a look that nobody checked. The error look with the box still off reaches the user, and the user cannot fix the email. When you draw each look from a hand-set `status`, every look is one word away. Put all five on one page, and a wrong look is plain to see before any handler exists.
>
> **DO THIS:**
> ```jsx
> function NewsletterForm({ status = 'empty' }) {
>   return <input ~disabled={status === 'submitting'}~ />; // Off only while sending
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function NewsletterForm({ status = 'empty' }) {
>   return <input ~disabled={status !== 'typing'}~ />; // **WRONG:** also off in the error look, so the user cannot fix the email
> }
> ```

## 3. Principle 3: Find What Moves the Page from One State to the Next

### The smallest version: who moves the parcel tracker?

Look at the parcel tracker once more. The light moves from Ordered to Shipped when a person at the shop clicks Shipped. It moves from Out for delivery to Delivered when the scanner in the van reports the parcel. Nobody at the shop clicks anything for that last step.

So there are two kinds of causes. A person causes some changes, and a machine causes others. Our newsletter box has both.

### Human inputs and computer inputs

React's documentation calls the cause of a change a **trigger**. It sorts triggers into two kinds:
- **Human inputs**, such as "clicking a button, typing in a field, navigating a link". They usually need an event handler, such as `onChange` from Lesson 20 or `onSubmit` from Lesson 11.
- **Computer inputs**, such as "a network response arriving, a timeout completing, an image loading". In our box, the timer that plays the answer is the computer input.

The two kinds start in different places, but they end the same way. In the words of React's documentation: "In both cases, **you must set state variables to update the UI.**"

### The arrows of the newsletter box

React's documentation suggests a simple drawing. Draw each look as a labeled circle, and each change as an arrow between two circles. A drawing like this is called a **state diagram**. Something that is always in exactly one of a few states, and moves between them only along arrows like these, is called a **state machine**. Our box is a small one. Here are its arrows, written as a table:

| From | To | Trigger | Kind |
| :--- | :--- | :--- | :--- |
| **empty** | **typing** | The user types the first letter | Human |
| **typing** | **empty** | The user deletes the last letter | Human |
| **typing** | **submitting** | The user clicks Sign up | Human |
| **submitting** | **success** | The answer says yes | Computer |
| **submitting** | **error** | The answer says no | Computer |
| **error** | **submitting** | The user clicks Sign up again | Human |

```tree dir=right caption="The state diagram of the newsletter box: each look and the triggers that leave it."
The looks of `NewsletterForm` and their way out
- +empty | Leaves when the user **types a letter**
- +typing | Leaves when the user **clears the box** or **clicks Sign up**
- +submitting | Leaves when the **answer arrives**, yes or no
- +success | **No way out**: the box is finished
- +error | Leaves when the user **clicks Sign up again**
```

React's documentation says you can "sort out bugs long before implementation" this way. An arrow that is not on the drawing should never happen. A look with no arrow out of it is a dead end. Success is a dead end on purpose. Any other dead end is a bug.

### Nobody clicks after Sign up. What moves the page?

After the click, the user just waits. Nobody types or clicks anything. Yet the page moves on to the thank-you line. Here is what happens, in order:
1. The click on Sign up is a human input. Its handler sets the state to submitting.
2. The same handler starts a timer for 1500 milliseconds.
3. The handler ends, and React draws the submitting look.
4. 1500 milliseconds later, the browser calls our timer function. This is the computer input.
5. The timer function sets the state to success or to error.
6. React draws that look.

Who calls our timer function, with no click? The browser does. `setTimeout` hands our function and the number 1500 to the browser. The browser waits, then calls the function.

Inside the timer, our code checks the email. Which email does it see, 1500 milliseconds after the click? It sees the email from the render that made the handler, as in Lesson 15. That is the email that was in the box at the moment of the click.

### Mistake: the page stuck on Sending...

Suppose a developer skips the diagram and wires the box right away. They keep `status` in state, which Principle 4 shows in full, and write the handler. They think only of the human arrows, and forget the answer:

```jsx title="src/components/NewsletterForm.jsx" startLine="7" bad="11"
  function handleSubmit(e) {
    e.preventDefault();
    setStatus('submitting');
    setTimeout(() => {
      ~console.log('signed up')~; // **WRONG:** the answer arrives, but no state changes
    }, 1500);
  }
```

The user types mary@mail.com and clicks Sign up. The page shows Sending..., and the box and the button turn off. After 1500 milliseconds, the Console shows the log. The page does not change:

```page width=text caption="The newsletter box long after the click: still sending, with the box and the button off."
heading: Get our weekly newsletter
form:
  field: Email | mary@mail.com
  submit: Sign up
line: Sending... | bad
log: signed up | NewsletterForm.jsx:11
```

The answer arrived, so why is the page still sending? Here is what happens:
1. The click sets `status` to `'submitting'`, and React draws Sending...
2. The timer runs, and it only writes to the Console.
3. No setter is called, so React has no reason to render again.
4. `status` stays `'submitting'`, and the page stays on Sending... forever.

On the diagram, the mistake is easy to find. The submitting look has no arrow out of it. The fix adds one setter call for each arrow: success when the answer says yes, error when it says no. Principle 5 writes that handler in full.

### A click and a timer are NOT the same, but React treats them the same

The click and the timer start in different places. The user starts the click. The browser starts the timer, by calling a function our code handed it earlier. The click needs a handler on an element. The timer needs none.

Once they run, React treats them exactly the same. Each one calls the setter, and each setter call asks React to render again. React's documentation says that human inputs *often* need event handlers, not always. The rule that never changes is that both must set state.

> [!PRINCIPLE]
> **Principle 3: Triggers: Every Arrow Between Two Looks Must Set State**
>
> *For every change between two looks, name what causes it, and make that cause set state, whether it is the user or the computer.*
>
> It is easy to think only of clicks and typing, because you can see them. The answer from a server or a timer arrives with nobody touching the page. If it only logs a message, React never renders again, and the page shows Sending... forever. Draw each look as a circle and each change as an arrow. A look with no arrow out of it is a bug waiting to happen.
>
> **DO THIS:**
> ```jsx
> setTimeout(() => {
>   ~setStatus('success')~; // The computer input sets state, so React draws the next look
> }, 1500);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> setTimeout(() => {
>   ~console.log('signed up')~; // **WRONG:** no state changes, so the page stays on Sending... forever
> }, 1500);
> ```

## 4. Principle 4: Keep the Current State in One `status` String, Not in Many True or False Values

### The smallest version: two switches or one dial

Here is the Send button again, now with two true or false values instead of one word:

```jsx title="src/App.jsx"
const [isSending, setIsSending] = useState(false);
const [isDone, setIsDone] = useState(false);
```

Two values that are each true or false can be mixed in four ways. Three of them match a look: ready, sending, and done. The fourth mix, sending and done at the same time, matches no look at all. Yet nothing in the code stops it.

Here is the same button with one word:

```jsx title="src/App.jsx"
const [status, setStatus] = useState(~'ready'~); // Holds 'ready', 'sending', or 'done', and nothing else
```

Three words, three looks, and no fourth mix.

Think of the parcel tracker built with one light switch for each step. If two switches are on, two steps are lit. Now build it with one dial instead. The dial points at exactly one step, so exactly one step is lit.

### Mistake: five true or false values

A developer who reads the five looks of Principle 2 may give each look its own true or false value. React's documentation says this is a fine first try: "start by adding enough state that you're *definitely* sure that all the possible visual states are covered." It also warns that the first try is rarely the best.

Here are the five values, next to the text of the box:

```jsx title="src/components/NewsletterForm.jsx" startLine="4"
  const [email, setEmail] = useState('');
  const [isEmpty, setIsEmpty] = useState(true);
  const [isTyping, setIsTyping] = useState(false);
  const [isSubmitting, setIsSubmitting] = useState(false);
  const [isSuccess, setIsSuccess] = useState(false);
  const [isError, setIsError] = useState(false);
```

Every handler must now set several of them. Here is the submit handler:

```jsx title="src/components/NewsletterForm.jsx" startLine="11" bad="14"
  function handleSubmit(e) {
    e.preventDefault();
    setIsTyping(false);
    ~setIsSubmitting(true)~; // **WRONG:** isError is still true from the last try
    setTimeout(() => {
      setIsSubmitting(false);
      if (email === 'john@mail.com') {
        setIsError(true);
      } else {
        setIsSuccess(true);
      }
    }, 1500);
  }
```

The JSX shows each line from its own value:

```jsx title="src/components/NewsletterForm.jsx"
      {isSubmitting && <p>Sending...</p>}
      {isError && <p>This email is already signed up.</p>}
```

The user tries john@mail.com and gets the error. Then they change it to mary@mail.com and click Sign up again. For 1500 milliseconds, the page shows this:

```page width=text caption="The five-value version during the second try: Sending... and the old error line together."
heading: Get our weekly newsletter
form:
  field: Email | mary@mail.com
  submit: Sign up
line: Sending...
line: This email is already signed up. | bad
```

How can the page show Sending... and the error at the same time? Here is what happens, in order:
1. The first try fails. The timer sets `isSubmitting` to false and `isError` to true.
2. The user clicks Sign up again. The handler sets `isSubmitting` to true, but nothing sets `isError` back to false.
3. React renders. `isSubmitting` is true, so Sending... shows.
4. `isError` is still true, so the error line shows too.

### Impossible states

The page is sending and showing an error at once. No look on our list matches that mix. React's documentation calls this a **paradox**, a mix of values that can never be a real look. This lesson calls it an **impossible state**.

Five true or false values can be mixed in 2 times 2 times 2 times 2 times 2 ways. That is 32 mixes, and only five of them match a look. The other 27 are impossible states, and the code must work hard to never reach them. Each handler is one forgotten setter call away from one of them.

React's documentation asks three questions about every piece of state:
1. Does this state cause a paradox?
2. Is the same information available in another state variable already?
3. Can you get the same information from the inverse of another state variable?

### The empty look needs no state of its own

Look at `isEmpty` with the second question in mind. The box already holds its text in `email`. When `email.length` is 0, the box is empty. So `isEmpty` says nothing that `email` does not already say.

A value like this is called a **computed value**: something the render works out from state, instead of keeping it in state. React's documentation does the same: "you can remove `isEmpty` and instead check `answer.length === 0`." The full rules for what to keep in state and what to compute come in Lesson 22.

The same happens to the other four values. Typing, submitting, success, and error can never be true together, so they become four words of one string. What is left is the **essential state**, the state that the page cannot lose without breaking:
- `email`, the text in the box.
- `status`, which holds `'typing'`, `'submitting'`, `'success'`, or `'error'`.

Notice that `status` has no `'empty'` word any more. Typing now means that the box is ready for the user, with or without text. The button checks the text itself.

### One `status` string for the newsletter box

Now `NewsletterForm` keeps both values in state. The `status` prop of the mock is gone, and the box becomes a controlled box, as in Lesson 20:

```jsx title="src/components/NewsletterForm.jsx"
import { useState } from 'react';

export default function NewsletterForm() {
  const [email, setEmail] = useState('');
  const [status, setStatus] = useState(~'typing'~); // One word for the current look

  if (status === 'success') {
    return <p>Thanks! You are signed up.</p>;
  }

  return (
    <form>
      <h2>Get our weekly newsletter</h2>
      <label>
        Email
        <input
          value={email}
          onChange={e => setEmail(e.target.value)}
          disabled={status === 'submitting'}
        />
      </label>
      <button ~disabled={email.length === 0 || status === 'submitting'}~>Sign up</button> {/* The empty look, worked out from email */}
      {status === 'submitting' && <p>Sending...</p>}
      {status === 'error' && <p>This email is already signed up.</p>}
    </form>
  );
}
```

`App` goes back to one box: it returns `<NewsletterForm />`. The page opens with an empty box, and the button is off:

```page width=text caption="The newsletter box with email and status in state, when the page opens. The Sign up button is off."
heading: Get our weekly newsletter
form:
  field: Email |
  submit: Sign up
```

The user types anna@mail.com, and the button turns on:

```page width=text caption="The same box after the user types anna@mail.com. The Sign up button is on."
heading: Get our weekly newsletter
form:
  field: Email | anna@mail.com | good
  submit: Sign up
```

The form has no submit handler yet, so a click would reload the page. Principle 5 connects the button.

The button turned on, but no handler set any look. Where did the empty look go? The render worked it out:
1. Each key calls `setEmail`, and React calls `NewsletterForm` again.
2. The render checks `email.length === 0` with the newest `email`.
3. The answer is false, so the button reads `disabled={false}` and turns on.

### With `status`, why can the old error never stay?

The five-value version needed a handler to clear `isError`. With one `status`, the next handler only needs to say the next look:
1. The handler calls `setStatus` with `'submitting'`.
2. `status` now holds `'submitting'`, and nothing else.
3. React renders. The check `status === 'error'` is false, so the error line is not drawn.
4. No line of code had to clear the error.

One word cannot be two looks at once. So the mix of sending and error can no longer exist.

### `isEmpty` and `email.length === 0` are NOT the same

Both tell us whether the box is empty, but they are NOT the same thing:
- **`isEmpty` as state** must be kept in step by every handler that changes the text. Forget one setter call, and it says the box is empty when it is not.
- **`email.length === 0`** is worked out again on every render, from the newest `email`. It cannot be out of step, because nothing stores it.

> [!PRINCIPLE]
> **Principle 4: One Status: Keep the Current Look in One String**
>
> *When a component shows one look at a time, store that look in one `status` string, and work out everything else from the state you already have.*
>
> Every true or false value is a moving piece, and every moving piece must be set by every handler. Five of them allow 32 mixes, and only five of them are real looks. Forget one setter call, and the user sees Sending... with an old error under it. One `status` string can hold only one word, so it can only be one look. React's documentation puts it simply: "you want as few 'moving pieces' as possible."
>
> **DO THIS:**
> ```jsx
> const [status, setStatus] = useState(~'typing'~); // One of 'typing', 'submitting', 'success', 'error'
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isSubmitting, setIsSubmitting] = useState(false);
> const [isError, setIsError] = useState(~false~); // **WRONG:** both can be true, so Sending... and the error show together
> ```

## 5. Principle 5: Handlers Only Set the Next State, and React Makes the Page Match

### The smallest version: the handler names the next look

Look one last time at the Send button from the start of the lecture, with its handler written out:

```jsx title="src/App.jsx"
function handleClick() {
  ~setStatus('sending')~; // Names the next look, and touches nothing on the page
}
```

The handler does not say Sending... anywhere. It does not find the button or change its text. It only names the next look. The JSX already says what that look shows.

Think of taking a taxi. You do not tell the driver every turn. You give the address, and the driver finds the way. React's documentation says it well: "It's the driver's job to get you there, and they might even know some shortcuts you haven't considered!" Our handlers give the address, the next look. React drives, and changes the page. Lesson 01 called this style declarative.

### Connecting the Sign up button

Now we add the last part of the box: the submit handler. It stops the page from reloading, names the submitting look, and starts the timer. The timer names the answer:

```jsx title="src/components/NewsletterForm.jsx" startLine="7"
  function handleSubmit(e) {
    e.preventDefault();
    ~setStatus('submitting')~; // Human input: the next look is submitting
    setTimeout(() => {
      if (email === 'john@mail.com') {
        ~setStatus('error')~; // Computer input: the answer says no
      } else {
        ~setStatus('success')~; // Computer input: the answer says yes
      }
    }, 1500);
  }
```

The form hands every submit to it:

```jsx title="src/components/NewsletterForm.jsx" startLine="24"
    <form ~onSubmit={handleSubmit}~> {/* React calls handleSubmit when the user clicks Sign up */}
```

Nothing in the handler touches the box, the button, or any line. Each setter call is one arrow of the diagram in Principle 3.

### Trying the finished box

The user types john@mail.com and clicks Sign up. The box and the button turn off, and Sending... appears:

```page width=text caption="The finished box right after the user clicks Sign up with john@mail.com. The box and the button are off."
heading: Get our weekly newsletter
form:
  field: Email | john@mail.com
  submit: Sign up
line: Sending...
```

After 1500 milliseconds, the error line appears, and the box and the button turn on again:

```page width=text caption="The finished box 1500 milliseconds later, with the error line."
heading: Get our weekly newsletter
form:
  field: Email | john@mail.com
  submit: Sign up
line: This email is already signed up.
```

The user changes the email to mary@mail.com. The error line stays while they type, because `status` is still `'error'`. Then they click Sign up, and the error line is gone at once:

```page width=text caption="The finished box right after the second click with mary@mail.com: Sending..., and no error line."
heading: Get our weekly newsletter
form:
  field: Email | mary@mail.com
```

After 1500 milliseconds, the whole form is replaced by one line:

```page width=text caption="The finished box after the answer for mary@mail.com: only the thank-you line."

```

### The success branch never clears the error. Why is it gone?

In Principle 1, the plain page needed a command to clear the error, and forgot it. Our handler has no such command. Yet the error is gone. Here is what happened, in order:
1. The first try ended with `setStatus` and `'error'`, so the error line showed.
2. The user typed mary@mail.com and clicked Sign up.
3. `handleSubmit` stopped the reload, called `setStatus` with `'submitting'`, and started the timer.
4. React rendered. The JSX for `'submitting'` has Sending... and no error line.
5. So React removed the error paragraph from the page.
6. 1500 milliseconds later, the timer called `setStatus` with `'success'`.
7. React rendered, and the early `return` gave only the thank-you line.

### So who writes the commands now?

The plain page had commands for every part. Our component has none. But the browser still needs commands to change the page. Somebody must write them. React does, every time a setter is called:
1. The setter call asks React to render again.
2. React calls `NewsletterForm` and gets the JSX for the new `status`.
3. React compares it with the JSX from the last render.
4. React changes only the parts that are different.

React's documentation shows this with a challenge. You rewrite a plain page with one `updateDOM` function that sets every part from the current state. Then it explains: "The `updateDOM` function you wrote shows what React does under the hood when you set the state." It adds that React "also avoids touching the DOM for properties that have not changed since the last time they were set."

### The plain listener and `handleSubmit` are NOT the same

Both run on submit, and both start the same timer. Put their timers side by side:

::: row caption="The plain timer changes every part by hand; the React timer names one next look."
::: col title="Plain JavaScript" tag="five parts by hand" tone=bad
```js title="plain/signup.js" bad="7"
setTimeout(() => {
  sending.textContent = '';
  button.disabled = false;
  if (box.value === 'john@mail.com') {
    errorText.textContent = 'This email is already signed up.';
  } else {
    thanks.textContent = 'Thanks! You are signed up.';
  }
}, 1500);
```
The success branch must clear the error itself. It does not, so the error stays.
:::
::: col title="React" tag="one next look" tone=good
```jsx title="NewsletterForm.jsx" good="3,5"
setTimeout(() => {
  if (email === 'john@mail.com') {
    setStatus('error');
  } else {
    setStatus('success');
  }
}, 1500);
```
Each branch only names the next look. React clears the old parts.
:::
:::

They are NOT the same thing. The plain timer changes the page. The React timer changes one value. So the plain branch must clear every old part itself, and the React branch only names where to go next.

The React version of the whole box is longer than the plain one. That is fine. React's documentation says: "Although this code is longer than the original imperative example, it is much less fragile."

### Mistake: turning the button off by hand

Lesson 13 said that our code must not change the parts of the page that React draws. Here is what happens when a developer mixes both ways. They turn the button off by hand, and they never set the submitting look:

```jsx title="src/components/NewsletterForm.jsx" startLine="7" bad="9"
  function handleSubmit(e) {
    e.preventDefault();
    ~e.target.querySelector('button').disabled = true~; // **WRONG:** changes React's button by hand, and sets no status
    setTimeout(() => {
      if (email === 'john@mail.com') {
        setStatus('error');
      } else {
        setStatus('success');
      }
    }, 1500);
  }
```

On a submit, `e.target` is the form, and `querySelector` finds the first button inside it. The user types john@mail.com and clicks Sign up. There is no Sending... line, because `status` never became `'submitting'`. After 1500 milliseconds, the error line appears, but the button stays off:

```page width=text caption="The box with the button turned off by hand, after the error: the Sign up button stays off."
heading: Get our weekly newsletter
form:
  field: Email | john@mail.com
  submit: Sign up | bad
line: This email is already signed up.
```

The JSX says the button should be on. Why does React leave it off? Here is what happens:
1. The handler turns the button off in the page. React does not know about it.
2. The timer calls `setStatus` with `'error'`, and React renders.
3. The button's JSX gives `disabled={false}`, the same as on the render before.
4. React compares the new JSX with the old JSX, not with the page. It sees no change in `disabled`.
5. So React does not touch the button, and the button stays off.
6. The user cannot click Sign up again.

The fix removes the hand-written line and calls `setStatus` with `'submitting'` instead. Then React turns the button off while the box is sending, and turns it on again when the answer arrives.

### Adding a new look adds one branch

Suppose the server gets a new answer: too many tries in a short time. In the plain page, that would mean new commands in every event, to show the new line and to clear it again. With `status`, it is one new word and one new branch:

```jsx title="src/components/NewsletterForm.jsx"
{~status === 'rate-limited'~ && <p>Too many tries. Please wait a minute.</p>} {/* One new branch for one new look */}
```

The timer calls `setStatus` with `'rate-limited'` for that answer. No other handler changes. React's documentation names this as the reward: expressing every interaction as a state change "lets you later introduce new visual states without breaking existing ones."

> [!PRINCIPLE]
> **Principle 5: Declarative Updates: Handlers Name the Next Look, React Changes the Page**
>
> *A handler only sets the next state; the JSX describes each look once, and React changes the parts of the page that differ.*
>
> In plain JavaScript, every handler had to clear what the last event left behind. With React, the handler says where to go next, and React works out how to get there. It compares the new JSX with the old JSX and changes only what is different. That is also why you must never change React's parts by hand. React compares its own JSX, not the page, so a change made by hand stays until the JSX itself changes.
>
> **DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   ~setStatus('submitting')~; // Names the next look; React turns the box and the button off
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   ~e.target.querySelector('button').disabled = true~; // **WRONG:** React does not know the button is off, so it does not turn it on again
> }
> ```

## Putting All Five Principles Together

### The complete `NewsletterForm.jsx` file

Here is the finished box. It keeps two pieces of state, describes each look once, and its handlers only name the next look:

```jsx title="src/components/NewsletterForm.jsx"
import { useState } from 'react';

export default function NewsletterForm() {
  const [email, setEmail] = useState('');
  const [status, setStatus] = useState(~'typing'~); // Principle 4: one word for the current look

  function handleSubmit(e) {
    e.preventDefault();
    ~setStatus('submitting')~; // Principle 5: the handler names the next look
    setTimeout(() => {
      if (email === 'john@mail.com') {
        ~setStatus('error')~; // Principle 3: the computer input sets state too
      } else {
        setStatus('success');
      }
    }, 1500);
  }

  if (~status === 'success'~) { // Principle 2: the success look replaces the whole form
    return <p>Thanks! You are signed up.</p>;
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Get our weekly newsletter</h2>
      <label>
        Email
        <input
          value={email}
          onChange={e => setEmail(e.target.value)}
          disabled={status === 'submitting'}
        />
      </label>
      <button ~disabled={email.length === 0 || status === 'submitting'}~>Sign up</button> {/* Principle 4: the empty look is worked out */}
      {status === 'submitting' && <p>Sending...</p>}
      {~status === 'error'~ && <p>This email is already signed up.</p>} {/* Principle 1: no command ever clears this line */}
    </form>
  );
}
```

The main component only places the box on the page:

```jsx title="src/App.jsx"
import NewsletterForm from './components/NewsletterForm.jsx';

export default function App() {
  return ~<NewsletterForm />~; // React calls NewsletterForm, which holds the whole box
}
```

### How React calls the components, and what one sign-up does

When the page loads, React starts at `App` and follows the tags. `App` has one tag, so React calls `NewsletterForm` next:

```tree caption="The component tree of the newsletter page and the order in which React calls each component."
`main.jsx` mounts `App` inside `<StrictMode>`
- +`App` [1. Called first] | **Root component** | Returns `<NewsletterForm />`
  - +`NewsletterForm` [2. Called second] | Holds **two states**, `email` and `status` | Called again after **every key**, every **click on Sign up**, and every **answer**
```

One sign-up goes around the same loop twice, once for the click and once for the answer:

```tree dir=right caption="What one sign-up does, from the click to the answer."
One sign-up in the finished box
- +1. The click | Human input: `handleSubmit` sets **submitting** and starts the timer
- +2. React renders | Draws **Sending...**, turns the box and the button off, removes any old error
- +3. The timer | Computer input: sets **success** or **error**
- +4. React renders again | Draws the **thank-you line** or the **error line**
```

### Summary

| Aspect | The Plain JavaScript Habit | The React Rule |
| :--- | :--- | :--- |
| **Changing the page** | Write a command for every part, in every event, and clear what the last event left | Describe each look once in JSX, and let React change the parts that differ |
| **Planning the looks** | Write the handlers first, and find the missing looks when users meet them | List every visual state, and draw each one from a `status` prop before any logic |
| **The causes of change** | Think only of clicks and typing | Name every trigger, human or computer, and make each one set state |
| **Storing the look** | One true or false value for each look, which allows impossible mixes | One `status` string, plus values worked out from state, such as an empty box from `email.length` |
| **Handlers** | Turn parts on and off by hand | Call the setter with the next look, and never change React's parts by hand |

## For the Interview

> **The Interview Question:** How do you design a component that reacts to input with state instead of touching the DOM?

### How to Answer Clearly in 30 Seconds

"I never change the page directly. I describe what each look shows, keep the current look in state, and let React change the page. In plain JavaScript, every event needs a command for every part, and one forgotten command leaves an old error next to a success message. I follow five steps:
1. **List every visual state.** For a sign-up form, that is empty, typing, submitting, success, and error. I draw each one from a `status` prop before any logic, often all on one page.
2. **Find the triggers.** Human inputs, such as typing and clicking, usually need event handlers. Computer inputs, such as a network answer or a timer, must also set state, or the page gets stuck.
3. **Store the state with `useState`,** with as few moving pieces as possible.
4. **Remove what is not essential.** I replace separate true or false values with one `status` string, so impossible mixes such as sending and error together cannot exist. I work out anything I can from other state, such as an empty box from `email.length`.
5. **Connect the handlers.** A handler only calls the setter with the next state. The JSX describes each state once, and React updates only what changed. A new look then adds one branch, not new commands in every handler."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Your instinct is to show and hide parts by toggling classes on DOM nodes. How does a state machine replace that?"**
   A state machine is something that is in exactly one of a few states at a time, and moves between them only along known arrows. Our `status` string is a small one. With classes, every event must add one class and remove the others, and a missing removal leaves two looks on screen. With a state machine, the class comes from the state, such as `className={status === 'error' ? 'box box-error' : 'box'}`, so it is always right. One detail matters when two looks share the same parts. If two looks draw the same box from two separate branches of JSX, and the branches do not line up, React may treat the box as new and reset its state. Lesson 25 covers how React decides that.

2. **"Why not just use `isLoading` and `isError` true or false values?"**
   Because they allow mixes that no screen should show. Two true or false values give four mixes, and only three are real. Five of them give 32 mixes for five real looks. Every handler must then set all of them in the right way, and one forgotten setter shows a spinner and an error together. React's documentation asks three questions about each piece of state. Does it cause a paradox? Is the same information already in another variable? Can I get it from the opposite of another variable? One `status` string passes all three. React's own final version still keeps the error text in a separate state, so an error text can sit next to a success status. To rule out mixes like that, `useReducer` from Lesson 27 can model the state more strictly, and libraries such as XState go further. In TypeScript, a type that lists the allowed words also catches a typo such as sucess. Plain JavaScript accepts that typo without a warning, and no branch matches it.

3. **"How does this change with a real server, and with React 19 forms?"**
   The design steps stay the same. A real request uses `fetch` instead of a timer. Then new problems appear, such as answers that arrive out of order, and Lesson 33 covers them. React 19 also adds form actions. With `useActionState` and `useFormStatus`, React keeps track of the submitting look for a form by itself, as Lessons 41 to 43 show. You still list the looks and their triggers first. The same habit of listing every look before writing code returns in Lesson 26, Thinking in React.
