# Lecture 34: When You Do Not Need an Effect
> INTERVIEW QUESTION | ❱ CORE | When do you not need an Effect, and what replaces it?

---

## Where the Code for Each Change Belongs

### One question decides it: why does this code need to run?

When you open the cart of an online shop, you see one row for each item, a total under the rows, and a button to place the order. Our cart holds two items, `Socks` at $5 and `Hat` at $20:

```page width=text caption="A cart with two items, a total line, and a Place order button."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $25
line: [Place order]
```

The user does two things on this screen, and each one changes the page:
1. **The user clicks Remove on `Hat`.** The row goes away, and the total line shows `Total: $5`.
2. **The user clicks `Place order`.** The button is replaced by the line `Thank you! Your order is placed.`, and the order goes to the server once.

Right after learning `useEffect` (as seen in Lesson 32), many developers write both changes as Effects. One Effect watches the items and sets the total. Another Effect sends the order when the thank-you line appears. Both run, and the page seems to work. Both are the wrong tool.

React's docs give one test for where code belongs: "ask yourself *why* this code needs to run." There are three answers, and each answer has its own place in the component:
1. **To show something calculated from state or props**, such as the total: calculate it during rendering, in the body of the component.
2. **Because the user did something**, such as clicking `Place order`: put it in the event handler of that click.
3. **Because the component is on the screen and must stay in sync with something outside React**, such as a server that counts visits: that is the job of an Effect.

```tree caption="The docs' test for code that runs when something on the page changes: why does this code need to run?"
Why does this code need to run?
- +To show a value calculated from state or props [`const total`] | Example: **the total line** | Calculate it **during rendering**, in the component body
- +Because the user did something [`onClick`] | Example: **the click on Place order** | Put it in **that event's handler**
- +Because the component is on the screen [`useEffect`] | Example: **a visit sent to a server** | Keep it in **an Effect**, which stays in sync with **something outside React**
```

The first two answers need no Effect at all. React's docs say it in one line: when there is no external system involved, "you shouldn't need an Effect."

### What is at stake

What is at stake is what the user gets from each of the two wrong Effects:
1. **With the total set by an Effect**, every change renders the cart once with the old total, and then a second time with the new one. On the first load, the first render returns `Total: $0`, because the Effect has not run yet.
2. **With the order sent by an Effect**, one click in development sends the order twice, and the Console shows it twice. React's docs say it plainly: "You wouldn't want to buy the product twice." In production, the order can go out again with no click at all, when the user goes to another page and then presses Back.

Readers usually go wrong in two places:
1. They read "the total depends on the items" as "watch the items with an Effect".
2. They read "after the click, show the thank-you line and send the order" as "send the order when the thank-you line appears".

### Both carts look right, but they are NOT the same cart

It may look the same, or work the same at first, but it is NOT the same thing! Once the page settles, the total set by an Effect and the total calculated during rendering both show `Total: $25`. In production, one click sends one order with either version. The difference hides in two places: in the extra render with the old total, and in what happens when the thank-you line appears on the screen a second time.

### Our example page: a cart with two items

Our cart starts with the code the developer wrote first, with both Effects. `App` keeps the items in state, keeps a copy of the total in state, and shows the thank-you line after the click:

```jsx title="src/App.jsx"
import { useState, useEffect } from 'react';
import OrderPlaced from './components/OrderPlaced.jsx';

const initialItems = [
  { id: 1, name: 'Socks', price: 5 },
  { id: 2, name: 'Hat', price: 20 },
];

export default function App() {
  const [items, setItems] = useState(initialItems);
  const [total, setTotal] = useState(0);
  const [isOrdered, setIsOrdered] = useState(false);

  useEffect(() => {
    ~setTotal~(items.reduce((sum, item) => sum + item.price, 0)); // Copies the total into state after the render
  }, [items]);

  function handleRemove(id) {
    setItems(items.filter(item => item.id !== id));
  }

  return (
    <main>
      <h1>Your cart</h1>
      <ul>
        {items.map(item => (
          <li key={item.id}>
            {item.name} ${item.price} <button onClick={() => handleRemove(item.id)}>Remove</button>
          </li>
        ))}
      </ul>
      <p>Total: $~{total}~</p> {/* Shows whatever total holds in state */}
      {isOrdered ? (
        ~<OrderPlaced items={items} />~ // Appears after the click on Place order
      ) : (
        <button onClick={() => setIsOrdered(true)}>Place order</button>
      )}
    </main>
  );
}
```

The dollar sign in `${item.price}` and in `${total}` is plain text on the page, and the curly braces after it show the number. The Remove button keeps every item except the one clicked, with `.filter` (as seen in Lesson 19).

The thank-you line lives in its own component. It holds the second Effect, the one that sends the order:

```jsx title="src/components/OrderPlaced.jsx"
import { useEffect } from 'react';
import { sendOrder } from '../api.js';

export default function OrderPlaced({ items }) {
  useEffect(() => {
    ~sendOrder(items);~ // Sends the order when the thank-you line appears
  }, [items]);

  return <p>Thank you! Your order is placed.</p>;
}
```

The two helper functions in `api.js` are our own. In a real shop, `sendOrder` would send a **POST request**, a request that sends data to the server, such as an order. `logVisit`, which Principle 3 uses, would send one visit to a server that counts visits. Here both only print a line in the Console, so we can count how many times each one runs:

```js title="src/api.js"
export function sendOrder(items) {
  console.log('Sending order: ' + items.length + ' items');
}

export function logVisit(page) {
  console.log('Visit: ' + page);
}
```

The entry file, `main.jsx`, mounts `App` inside `<StrictMode>` (as seen in Lesson 07). Here is how the files sit in the project:

```files title="cart-page: File Explorer" caption="How the cart project files sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  App.jsx | parent | Keeps `items` in state, shows the rows and the total, and renders `OrderPlaced` after the click
  api.js | helpers | Exports `sendOrder` and `logVisit`, which only print to the Console
  components/
    OrderPlaced.jsx | child | Shows the thank-you line, and at the start of the lesson sends the order in an Effect
```

### Three Principles of Code That Needs No Effect

**PRINCIPLES:** An Effect is for code that runs because the component is on the screen and must stay in sync with something outside React. A value calculated from state needs no Effect, and neither does code caused by a click. Three principles follow from that:
1. **Principle 1: The Total Line Is Calculated During Rendering**: The total can be calculated from `items`, so the component calculates it in its body. An Effect that copies it into state costs one render with the old total, and then a second render.
2. **Principle 2: The Place order Click Sends the Order**: The order goes out because the user clicked, so `sendOrder` goes in the click's event handler. An Effect in the thank-you line sends it on every mount of that line: twice in development, and again after Back in production.
3. **Principle 3: The Cart Visit Is Logged by an Effect**: A visit is logged because the cart is on the screen, and there is no click to put it in. That code stays in an Effect, even though it runs twice in development.

Here is the complete map of those three principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The Total Line Is Calculated During Rendering** | A total set by an Effect renders the cart with the old total first, adds a state variable and a setter, and the linter reports it; interviewers ask what replaces this Effect. | Calculate a value from props or state in the component body, such as `const total = items.reduce(...)`; never copy it into state from an Effect. |
| **Principle 2** | **The Place order Click Sends the Order** | An order sent by an Effect goes out twice in development and again after Back in production, with no click. | Put code caused by one interaction in that event's handler, such as `sendOrder` inside `handlePlaceOrder`. |
| **Principle 3** | **The Cart Visit Is Logged by an Effect** | Developers who learn that Effects run twice in development move every Effect, including the ones that belong there. | Keep code caused by the component being on the screen in an Effect, such as `logVisit('cart')`, and let it run twice in development. |

## 1. Principle 1: The Total Line Is Calculated During Rendering

### A full name copied by an Effect vs. calculated in the body

React's docs show this mistake in its smallest form: a first name, a last name, and a full name made from both. Here is the full name both ways:

```jsx title="fullName in state, set by an Effect"
const [firstName, setFirstName] = useState('Taylor');
const [lastName, setLastName] = useState('Swift');
const [fullName, setFullName] = useState('');

useEffect(() => {
  ~setFullName~(firstName + ' ' + lastName); // Runs after React has already rendered the empty fullName
}, [firstName, lastName]);
```

```jsx title="fullName calculated during rendering"
const [firstName, setFirstName] = useState('Taylor');
const [lastName, setLastName] = useState('Swift');
const ~fullName~ = firstName + ' ' + lastName; // Taylor Swift, calculated on every render
```

It may look the same, or work the same at first, but it is NOT the same thing! Both show `Taylor Swift` once the page settles. The difference is how many times React renders to get there:
- **With `fullName` in state, set by an Effect**, the docs say React "does an entire render pass with a stale value for `fullName`, then immediately re-renders with the updated value." A **render pass** is one round of React calling the component functions and then committing the result to the DOM. A **stale value** is an old value that no longer matches the state it is made from: on the first render, `fullName` is still the empty string.
- **With `fullName` calculated during rendering**, the line runs every time React calls the component, so `fullName` always matches the names of this render. The docs: "That code will automatically re-run whenever your props or state change."

The Effect costs a whole render because Effects run last. React's docs give the order: "When you update the state, React will first call your component functions to calculate what should be on the screen. Then React will "commit" these changes to the DOM, updating the screen. Then React will run your Effects. If your Effect *also* immediately updates the state, this restarts the whole process from scratch!"

```tree dir=right caption="Why a setter called in an Effect costs a second render: the Effect runs after the commit, so its update starts the whole process again."
One state update with a setter inside the Effect
- +1. Render [`App`] | React calls the component | The JSX holds **the stale value**
- +2. Commit | React puts **the stale value** into the DOM
- !3. Effect [`setFullName`] | The Effect **sets state** | React must **start again from step 1**
- +4. Render and commit again | The JSX holds **the new value** | The page is right **one render late**
```

This is the rule for redundant state (as seen in Lesson 22): a value you can calculate from state is a `const` in the body, not state. Yes, it is the exact same thing here! An Effect that copies the value into state is not a way around that rule. It is the same redundant state, with one more render on top.

### The cart's total set by an Effect renders twice

Our cart has the same shape as the full name. `total` is made from `items`, and an Effect copies it into state:

```jsx title="src/App.jsx" startLine="10"
  const [items, setItems] = useState(initialItems);
  const [total, setTotal] = useState(~0~); // The total before the Effect has run
  const [isOrdered, setIsOrdered] = useState(false);

  useEffect(() => {
    ~setTotal~(items.reduce((sum, item) => sum + item.price, 0)); // Runs after the render, then asks for another one
  }, [items]);
```

**Beware! On the first load, the cart renders twice, and the first render shows `Total: $0`.** Here is the order of events:
1. React calls `App`. `total` is still `0`, so the JSX returns `Total: $0`.
2. React commits `Total: $0` to the DOM.
3. React runs the Effect, which calls `setTotal(25)`.
4. React calls `App` again and commits `Total: $25`.

```page width=text caption="What the first render of the cart returns, before the Effect has set the total."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $0 | bad
line: [Place order]
```

Whether the user sees `Total: $0` depends on when the browser paints the screen. React's `useEffect` reference says that when an Effect was not caused by a click, React "will generally let the browser paint the updated screen first before running your Effect." So the user can see `Total: $0` for a moment before it turns into `Total: $25`.

**After a click on Remove, one render shows a single row with the old total.** Here is the order of events when the user removes `Hat`:
1. The click calls `setItems` with only `Socks`.
2. React calls `App`. The list shows only `Socks`, and `total` is still `25`, so the JSX returns `Total: $25` under one row of $5.
3. React commits that render, then runs the Effect, which calls `setTotal(5)`.
4. React calls `App` again and commits `Total: $5`.

Here the user may never see step 2. The same reference says that when an Effect is caused by a click, React "may run your Effect before the browser paints the updated screen." The cost is still there: one extra render after every change of `items`, and one more state variable, one more setter, and one more Effect in the code.

### Calculating the total in the body

The fix is to delete the `total` state and its Effect, and to calculate `total` in the body of `App`. `.reduce` walks the array and adds each `item.price` to `sum`, starting from `0` (as seen in Lesson 27). The names `sum` and `item` belong to the arrow function: `sum` is the running total so far, and `item` is the current element of `items`, such as `{ id: 1, name: 'Socks', price: 5 }`.

```jsx title="src/App.jsx" startLine="9"
export default function App() {
  const [items, setItems] = useState(initialItems);
  const [isOrdered, setIsOrdered] = useState(false);
  const ~total~ = items.reduce((sum, item) => sum + item.price, 0); // 25 for Socks and Hat, 5 after Hat is removed
```

The JSX keeps the same line, `<p>Total: ${total}</p>`, and the import line drops `useEffect`, since `App` has no Effect left. Now there is one render for each change:
- **On the first load**, the first render already shows `Total: $25`.
- **After a click on Remove**, the render that removes the `Hat` row also shows `Total: $5`.

```page width=text caption="The cart after the user clicks Remove on Hat: the row and the total change in the same render."
heading: Your cart
line: Socks $5 [Remove]
line: Total: $5 | good
line: [Place order]
```

React's docs give three reasons for this rule: it makes your code "faster", because you avoid the extra "cascading" updates, a state update from an Effect that starts another render; "simpler", because you remove code; and "less error-prone", because two state variables can no longer get out of sync with each other.

```tree caption="The cart's total set by an Effect vs. calculated during rendering: the same page once it settles, and NOT the same thing."
Two ways to show the cart's total
- !`total` in state, set by an Effect [`useState` `setTotal` `useEffect`] | First render shows **`Total: $0`** | Every change of `items` costs **a second render**
- +`total` calculated during rendering [`const total`] | First render shows **`Total: $25`** | Every change of `items` costs **one render**, and the total always matches the rows
```

### The linter reports a setter called in an Effect

React's team ships a lint plugin, `eslint-plugin-react-hooks`, and one of its rules finds these Effects for you. The rule `set-state-in-effect` reports a setter called directly inside an Effect, such as `setTotal` in the Effect that copied the total. Its docs page describes it as a rule that "Validates against calling setState synchronously in an effect, which can lead to re-renders that degrade performance."

> [!PRINCIPLE]
> **Principle 1: Calculate During Rendering: A Value Made from State Is a const in the Body**
>
> *When a value can be calculated from the props or state the component already has, calculate it in the component body during rendering; do not keep it in state and set it from an Effect.*
>
> The component body runs again every time `items` changes, so a total calculated there always matches the rows on the screen. An Effect runs only after React has rendered and committed the page. When it sets the total, React renders the whole cart again, so every change costs one render with the stale total and a second render with the right one.
>
> **DO THIS:**
> ```jsx
> const [items, setItems] = useState(initialItems);
> const ~total~ = items.reduce((sum, item) => sum + item.price, 0); // Matches items on every render
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [total, setTotal] = useState(0);
> useEffect(() => {
>   ~setTotal~(items.reduce((sum, item) => sum + item.price, 0)); // **WRONG:** one render with the old total, then a second render
> }, [items]);
> ```

## 2. Principle 2: The Place order Click Sends the Order

### The same line in two places: the click's handler vs. an Effect

The line that sends the order, `sendOrder(items)`, can sit in two places. It can sit in the function that runs when the user clicks `Place order`, or in an Effect of the thank-you line:

```jsx title="sendOrder in the click's event handler"
function handlePlaceOrder() {
  ~sendOrder(items);~ // Runs once for each click by the user
  setIsOrdered(true);
}
```

```jsx title="sendOrder in an Effect of OrderPlaced"
useEffect(() => {
  ~sendOrder(items);~ // Runs every time OrderPlaced mounts
}, [items]);
```

It may look the same, or work the same at first, but it is NOT the same thing! In production, one click prints one `Sending order: 2 items` with either version. But the event handler runs once for each click, and the Effect runs once for each time `OrderPlaced` mounts. A click happens once. The thank-you line can mount more than once.

The docs' test gives the answer: "ask yourself *why* this code needs to run. Use Effects only for code that should run *because* the component was displayed to the user." The order goes out because the user clicked, not because the thank-you line is on the screen. The docs make the same point about a shop's Buy button: "You don't want to buy the product when the user *visits* a page; you want to buy it when the user *clicks* the Buy button."

### In development, one click sends the order twice

**Beware! In development, one click on `Place order` sends the order twice.** Here is what the user sees after the click, with the Effect still in `OrderPlaced`:

```page width=text caption="The cart after one click on Place order, with the order sent by an Effect: in development, the Console shows the order twice."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $25
line: Thank you! Your order is placed.
log: Sending order: 2 items | api.js:2
log: Sending order: 2 items | api.js:2
```

Here is the order of events behind the two lines:
1. The click calls `setIsOrdered(true)`.
2. React renders `App`. The button is replaced by `<OrderPlaced items={items} />`.
3. React mounts `OrderPlaced` and runs its Effect. The Console prints `Sending order: 2 items`.
4. Strict Mode runs the cleanup, which is empty, and then the setup again (as seen in Lesson 32). The Console prints `Sending order: 2 items` a second time.

React's docs show this exact shape and label it: "This Effect fires twice in development, exposing a problem in the code." The second line is not the bug. It shows the bug: the order is tied to the thank-you line being on the screen, and that line can appear again.

### In production, Back sends the order again

In production, Strict Mode does not run the extra setup, and the Console shows one line. The order can still go out again with no click:
1. The user places the order and sees the thank-you line.
2. The user goes to another page, then presses Back.
3. `OrderPlaced` mounts again, and its Effect sends the order again.

The docs: "What if the user goes to another page and then presses Back? Your Effect would run again." An Effect cannot tell the first mount from this one. The docs explain why: "By the time an Effect runs, you don't know *what* the user did."

### An Effect that waits for isOrdered works on one click, and it is still not the same

Some developers keep the Effect and move it up into `App`, where it waits for the flag `isOrdered` to turn `true`:

```jsx title="sendOrder in an Effect of App that waits for isOrdered"
useEffect(() => {
  if (~isOrdered~) { // **WRONG:** the order now follows a state value, not the click
    sendOrder(items);
  }
}, [isOrdered, items]);
```

It may look the same, or work the same at first, but it is NOT the same thing! One click prints one `Sending order: 2 items`, because `App` was already on the screen. But the order now goes out whenever `isOrdered` is `true` and `items` changes. When the user clicks Remove on `Hat` after placing the order, the Effect runs again and sends a second order with one item.

React's docs label this shape "Event-specific logic inside an Effect". **Event-specific logic** is code that runs because of one interaction, such as one click on `Place order`. It belongs in the handler of that interaction.

### Moving the order into the click's handler

The fix is to call `sendOrder` in a handler of its own, `handlePlaceOrder`, and give that handler to the button:

```jsx title="src/App.jsx" startLine="19"
  function handlePlaceOrder() {
    ~sendOrder(items);~ // 1. Sends the order, once for this click
    setIsOrdered(true); // 2. Then shows the thank-you line
  }
```

```jsx title="src/App.jsx" startLine="35"
      {isOrdered ? (
        ~<OrderPlaced />~ // No props: the thank-you line only shows text now
      ) : (
        <button ~onClick={handlePlaceOrder}~>Place order</button> // The click runs handlePlaceOrder
      )}
```

`App` now imports `sendOrder` from `./api.js`. `items` in the handler is `App`'s own state, so `OrderPlaced` needs no props. It loses its Effect and keeps only its line:

```jsx title="src/components/OrderPlaced.jsx"
export default function OrderPlaced() {
  return ~<p>Thank you! Your order is placed.</p>~; // The page shows the same line as before
}
```

One click now sends one order, in development and in production:

```page width=text caption="The cart after one click on Place order, with the order sent by the click's handler: the Console shows the order once."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $25
line: Thank you! Your order is placed. | good
log: Sending order: 2 items | api.js:2
```

When the Console shows the order twice, some developers reach for another fix: a ref that blocks the second run of the Effect. The Console then shows one line, and in production the order still goes out again after Back. React's docs ask how to make an Effect work after it mounts again, not how to make it run once (as seen in Lesson 32). Here the answer is to delete the Effect.

```tree caption="Three places for sendOrder: an Effect of the thank-you line, an Effect that waits for isOrdered, and the click's handler."
Where `sendOrder` runs
- !In an Effect of `OrderPlaced` [`useEffect`] | Runs on **every mount** of the thank-you line | **Twice** in development, **again after Back** in production
- !In an Effect of `App` that waits for `isOrdered` [`isOrdered`] | Runs whenever **`isOrdered` is true and `items` changes** | A Remove after the order **sends a second order**
- +In the click's handler [`handlePlaceOrder`] | Runs **once for each click** by the user | **One order**, in development and in production
```

> [!PRINCIPLE]
> **Principle 2: Event Handler: Code Caused by a Click Runs in That Click's Handler**
>
> *When code runs because the user did one thing, such as clicking `Place order`, put it in that event's handler; do not put it in an Effect that runs when a component appears or when a state flag changes.*
>
> A click happens once, and its handler runs once. An Effect runs every time its component mounts or its dependencies change, and by then it does not know what the user did. So an order sent from an Effect goes out twice in development, again after the user presses Back in production, and again when a dependency changes.
>
> **DO THIS:**
> ```jsx
> function handlePlaceOrder() {
>   ~sendOrder(items);~ // Runs once for each click on Place order
>   setIsOrdered(true);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function OrderPlaced({ items }) {
>   useEffect(() => {
>     ~sendOrder(items);~ // **WRONG:** runs on every mount, twice in development and again after Back
>   }, [items]);
>   return <p>Thank you! Your order is placed.</p>;
> }
> ```

## 3. Principle 3: The Cart Visit Is Logged by an Effect

### An Effect that stays: logging a visit to the cart

Shops count how many users open the cart. Each time the cart is shown, the page sends an **analytics event** to a server that counts what users see and do. Here the event is one visit of the cart, and `logVisit` stands in for it.

No click causes this visit. The cart is on the screen, and that is the whole reason. React's docs say the same about a form: "the _reason_ to send the analytics event is that the form was displayed." So this code goes in an Effect, with an empty array so that it runs after the first mount (as seen in Lesson 32):

```jsx title="src/App.jsx" startLine="10"
export default function App() {
  const [items, setItems] = useState(initialItems);
  const [isOrdered, setIsOrdered] = useState(false);
  const total = items.reduce((sum, item) => sum + item.price, 0);

  useEffect(() => {
    ~logVisit('cart');~ // Runs because the cart is on the screen
  }, ~[]~); // Empty array: runs after the first mount only
```

The import lines now bring back `useEffect` from `react`, and add `logVisit` next to `sendOrder` from `./api.js`.

### Two Effects that print twice: the visit vs. the order

**Beware! In development, `Visit: cart` prints twice on the first load, just as the order did in Principle 2.**

```page width=text caption="The cart on the first load in development: the visit Effect prints twice."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $25
line: [Place order]
log: Visit: cart | api.js:6
log: Visit: cart | api.js:6
```

Here is the order of events:
1. React mounts `App` and runs the setup. The Console prints `Visit: cart`.
2. Strict Mode runs the cleanup, which is empty, and then the setup again. The Console prints `Visit: cart` a second time.
3. In production, the Console prints one line.

It may look the same, or work the same at first, but it is NOT the same thing! Both Effects print twice in development. But the visit is caused by the cart being on the screen, and the order is caused by a click. One extra visit changes nothing the user sees. One extra order charges the user twice.

React's docs keep this code as it is: "**We recommend keeping this code as is.** Like with earlier examples, there is no *user-visible* behavior difference between running it once and running it twice." And: "**In production, there will be no duplicate visit logs.**" The docs add why the extra visits do not matter: "you don't want the logs from the development machines to skew the production metrics." So there is nothing to fix with a ref, and no reason to move the call out of the Effect.

The docs put the whole lesson in two sentences: "If this logic is caused by a particular interaction, keep it in the event handler. If it's caused by the user _seeing_ the component on the screen, keep it in the Effect."

```tree caption="Two Effects that print twice in development: the visit stays in its Effect, and the order moves to the click's handler."
Two Effects that run twice in development
- +`logVisit` in an Effect [`logVisit`] | Runs because **the cart is on the screen** | An extra visit **changes nothing the user sees**: it stays
- !`sendOrder` in an Effect [`sendOrder`] | Runs, but it was caused by **a click** | An extra order **charges the user twice**: it moves to the handler
```

> [!PRINCIPLE]
> **Principle 3: Effect: Code Caused by the Component Being on the Screen Stays in an Effect**
>
> *When code runs because the component was shown, and it talks to something outside React, such as a server that counts visits, keep it in an Effect; running twice in development is not a reason to move it.*
>
> The visit happens because the cart is on the screen, so there is no click whose handler could hold it. In development, Strict Mode runs the setup a second time, and the Console shows two visits. That extra visit changes nothing the user sees, and in production there is one.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   ~logVisit('cart');~ // Runs because the cart is on the screen
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const didLog = useRef(false);
> useEffect(() => {
>   if (~didLog.current~) return; // **WRONG:** blocks the second run instead of letting it run twice in development
>   didLog.current = true;
>   logVisit('cart');
> }, []);
> ```

## Putting All Three Principles Together

### The complete cart project

Here are the four files of our finished cart. The entry file mounts `App` inside `<StrictMode>`:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

`App` calculates the total, sends the order from the click, and logs the visit in its one Effect:

```jsx title="src/App.jsx"
import { useState, useEffect } from 'react';
import OrderPlaced from './components/OrderPlaced.jsx';
import { sendOrder, logVisit } from './api.js';

const initialItems = [
  { id: 1, name: 'Socks', price: 5 },
  { id: 2, name: 'Hat', price: 20 },
];

export default function App() {
  const [items, setItems] = useState(initialItems);
  const [isOrdered, setIsOrdered] = useState(false);
  const ~total~ = items.reduce((sum, item) => sum + item.price, 0); // Principle 1: calculated during rendering

  useEffect(() => {
    ~logVisit('cart');~ // Principle 3: runs because the cart is on the screen
  }, []);

  function handleRemove(id) {
    setItems(items.filter(item => item.id !== id));
  }

  function handlePlaceOrder() {
    ~sendOrder(items);~ // Principle 2: runs once for each click on Place order
    setIsOrdered(true);
  }

  return (
    <main>
      <h1>Your cart</h1>
      <ul>
        {items.map(item => (
          <li key={item.id}>
            {item.name} ${item.price} <button onClick={() => handleRemove(item.id)}>Remove</button>
          </li>
        ))}
      </ul>
      <p>Total: ${total}</p>
      {isOrdered ? (
        <OrderPlaced />
      ) : (
        <button onClick={handlePlaceOrder}>Place order</button>
      )}
    </main>
  );
}
```

`OrderPlaced` only shows the thank-you line:

```jsx title="src/components/OrderPlaced.jsx"

  return <p>Thank you! Your order is placed.</p>;
}
```

`api.js` holds the two helpers that stand in for requests to a server:

  console.log('Visit: ' + page);

### How React renders the cart and runs its one Effect

On the first load, React calls `App` once, commits the cart with the right total, and runs the one Effect. On the click, the handler sends the order before React renders the thank-you line:

```tree dir=right caption="The order of events in the finished cart, from the first load to the thank-you line."
From the first load to the thank-you line
- +1. Render [`App`] | React calls `App`; **`total` is 25** | The JSX returns **`Total: $25`** at once
- +2. Commit | React puts the rows, the total, and the button **into the DOM**
- +3. Effect [`logVisit`] | React runs the setup | The Console prints **`Visit: cart`**, twice in development
- +4. Click [`handlePlaceOrder`] | The user clicks **Place order** | `sendOrder` prints **`Sending order: 2 items`** once, then `setIsOrdered` asks for a render
- +5. Render and commit [`OrderPlaced`] | React calls `App`, then `OrderPlaced` | The thank-you line **replaces the button**
```

| Where the code runs | What the user gets | Why |
| :--- | :--- | :--- |
| **`total` in state, set by an Effect** | The right total, one render late: `Total: $0` on the first render | The Effect runs after the commit, and its setter starts another render |
| **`total` calculated during rendering** | The right total in the same render as the rows | The body runs again on every change of `items` |
| **`sendOrder` in an Effect of `OrderPlaced`** | Two orders in development, another order after Back in production | The Effect runs on every mount of the thank-you line |
| **`sendOrder` in an Effect that waits for `isOrdered`** | A second order after a Remove that follows the order | The Effect runs whenever `items` changes while `isOrdered` is `true` |
| **`sendOrder` in `handlePlaceOrder`** | One order for each click | The handler runs once for each click by the user |
| **`logVisit` in an Effect** | Nothing different on the page; two visit lines in development only | The visit is caused by the cart being on the screen |

## For the Interview

> **The Interview Question:** When do you not need an Effect, and what replaces it?

### How to Answer Clearly in 30 Seconds

"Effects are an escape hatch for staying in sync with a system outside React. When there is no external system, I usually do not need one. I ask why the code needs to run:
1. **To show a value calculated from props or state**, such as a cart total: I calculate it in the component body during rendering. An Effect that copies it into state costs a render pass with a stale value, and then a second render.
2. **Because the user did something**, such as clicking Place order: I put it in that event's handler. By the time an Effect runs, it does not know what the user did, so an order sent from an Effect goes out twice in development and again when the component mounts again.
3. **Because the component is on the screen**, such as an analytics visit: that stays in an Effect, and running twice in development is fine.

The lint rule `set-state-in-effect` helps me find a setter called directly in an Effect."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What if the calculation is slow? Shouldn't it go in an Effect then?"**
   No. A slow calculation is cached with `useMemo`, not moved into an Effect. The docs: "To cache expensive calculations, add `useMemo` instead of `useEffect`." Most calculations are not slow: "unless you're creating or looping over thousands of objects, it's probably not expensive." Lesson 56 teaches `useMemo`, and the React Compiler, in Lesson 63, "can automatically memoize expensive calculations for you".
2. **"How do you reset a child's state when a prop changes, without an Effect?"**
   Give the child a different `key` (as seen in Lesson 25). The docs' example is a profile page that renders `<Profile userId={userId} key={userId} />`, so React starts the profile's state over for each user. An Effect that calls the setters when `userId` changes renders the old state first, and then again, just like the total. To change only part of the state, the docs prefer to store less, such as a `selectedId`, and calculate the rest during rendering.
3. **"Should a fetch move to an event handler too?"**
   Usually not. The docs: "You *don't* need to move this fetch to an event handler." The results must match the query while the component is visible, whatever caused the query to change, so a fetch is a job for an Effect, with a cleanup that drops late answers (as seen in Lesson 33). The same test decides it: the data is needed because the component is on the screen.

```tree dir=right caption="Interview comparison: what replaces an Effect in each case, and what stays an Effect."
What replaces an Effect
- +A value calculated from props or state [`const total`] | **Calculate it during rendering** | A slow one is cached with **`useMemo`**, not an Effect
- +Code caused by one interaction [`handlePlaceOrder`] | **Put it in the event handler** | It runs **once for each click**
- +A child's state that must start over [`key`] | **Give the child a different `key`** | React **starts its state over**
- +Code caused by the component being on the screen [`useEffect`] | **Keep the Effect** | A visit log or a fetch **stays**, and may run twice in development
```
