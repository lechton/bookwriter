# Lecture 23: How a Child Tells Its Parent to Change State
> INTERVIEW QUESTION | ❱ CORE | How does a child component notify its parent or trigger state updates using callback props?

## How a Child Asks Its Parent for a Change

### Changing the papers yourself vs. calling the owner back

Think of a doctor's office that keeps your file. You cannot walk behind the desk and change your file yourself, because the file belongs to the office. So the office gives you its phone number and says: call us back when something changes. One day you move to a new street. You call the number, you say what happened, and the person at the desk updates your file. You never touched the file. You only made a call.

This is where the word **callback** comes from. A callback is a function that one piece of code hands to another piece of code, so the other piece can call it back later, when something happens.

React components work the same way. A parent component keeps a list in its state, and it hands a function down to a child component as a prop. When the user clicks a button inside the child, the child calls that function and says what happened. The parent's own code then changes the list.

Both things the parent passes are props written on the child's tag. The one difference is what the prop carries:
- **A prop that holds a value**, such as `name="John"`, carries something for the child to show.
- **A prop that holds a function**, such as `onRemove={handleRemove}`, carries something for the child to call.

```tree caption="Two kinds of props on a child's tag: one carries a value to show, the other carries a function to call."
Two kinds of props on `<GuestRow>`
- +A prop that holds a value [`name="John"`] | The child **shows it** on the page | The value travels **down** from the parent
- +A prop that holds a function [`onRemove={handleRemove}`] | The child **calls it** when the user acts | The parent's own code **changes the state**
```

So here is the key idea of this lesson: the parent owns the state and the only code that changes it, and the child never changes that state itself. It only calls the function it was given.

### What is at stake

What is at stake is a button the user clicks that does nothing. The user clicks `Remove` next to a guest, and the guest stays on the list. Or the guest's row disappears, while the line above the list still says `3 guests`. Both happen when the child tries to do the parent's job.

Readers usually go wrong in one of two places. Some picture the child reaching up into the parent and changing the parent's list. Others think that once a child can change the parent's state, data flows both ways. Neither is true. Only a function call goes up. The new list still comes down as props.

### Four ways to let a child change its parent's state

When a child must change the parent's state, developers choose among four ways:
1. **Pass a handler the parent wrote**, such as `onRemove={handleRemove}`, and let the child call it with a value. This is the usual way in React's docs, and the way this lesson teaches.
2. **Pass the setter itself**, such as `onFilterTextChange={setFilterText}`. React's docs do this in their *Thinking in React* page. It fits when the child sends exactly the next value of the state.
3. **Pass an arrow function with a fixed value**, such as `onShow={() => setActiveIndex(0)}`. It fits when each child tag is written by hand, so each tag already knows its own value.
4. **Pass one `dispatch` function, or put the functions in context**, when many components deep in the tree need them. Lessons 27 to 29 teach these.

### Four Principles of Callback Props

**PRINCIPLES:** A child cannot change its parent's state, but it can call a function the parent gave it. Four practical principles follow from that:
1. **Principle 1: `GuestRow` Cannot Call `setGuests`**: State is private to the component that declares it. A row placed inside the guest list sees only the props written on its tag, so the list's setter is out of its reach.
2. **Principle 2: `onRemove` Carries `handleRemove` Down to the Row**: A prop can hold a function. The parent writes the handler next to its state and passes it on the child's tag, and the child gives it to a real `<button>`.
3. **Principle 3: `onRemove(guest.id)` Tells the Parent Which Guest**: The child calls the function inside its own arrow function, with the value the parent needs. The parent's handler calls its own setter, and the new list comes down as props.
4. **Principle 4: `AddGuest` Sends the Typed Name Up with `onAdd(name)`**: When the value exists only in the child, such as the text typed in its own box, the child sends it as the argument of the call.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`GuestRow` Cannot Call `setGuests`** | A row that calls the list's setter throws `ReferenceError` when the user clicks Remove, and a row that hides only itself leaves the line saying `3 guests`. | State is private to the component that declares it. A child sees only the props written on its tag. |
| **Principle 2** | **`onRemove` Carries `handleRemove` Down to the Row** | Interviewers ask whether props that start with `on` are special. On our own component they are ordinary props, and passing the handler straight to `onClick` removes nobody, with no error. | Write the handler next to the state in the parent, and pass it on the child's tag as a prop such as `onRemove`. |
| **Principle 3** | **`onRemove(guest.id)` Tells the Parent Which Guest** | Writing `onRemove={handleRemove(guest.id)}` on the tag ends in `Too many re-renders` and a blank page. Interviewers also ask whether data now flows both ways. | The child calls the prop inside its own arrow function with the value the parent needs. Data still flows down; only the call goes up. |
| **Principle 4** | **`AddGuest` Sends the Typed Name Up with `onAdd(name)`** | Passing `onAdd` straight to `onClick` sends the event object instead of the name and crashes the page. | When the value lives only in the child, the child passes it as the argument of the callback prop. |

## 1. Principle 1: `GuestRow` Cannot Call `setGuests`

### Sitting inside the parent on the page vs. seeing the parent's names

Here is the smallest page that shows the problem. A parent component keeps a number in state and shows it. Below the number, it places a child component with an `Add` button:

```page width=text caption="A parent shows the number 0, and its child shows an Add button."
line: 0
line: [Add]
console: quiet
```

```jsx title="src/Parent.jsx"
import { useState } from 'react';
import Child from './Child.jsx';

export default function Parent() {
  const [count, setCount] = ~useState(0)~; // count and setCount are created here, inside Parent
  return (
    <div>
      <p>{count}</p>
      <Child />
    </div>
  );
}
```

```jsx title="src/Child.jsx"
export default function Child() {
  return <button onClick={() => ~setCount(count + 1)~}>Add</button>; // **WRONG:** Child.jsx has no setCount
}
```

When the user clicks `Add`, the number stays on `0`, and the Console shows an error:

```page width=text caption="The same page after the user clicks Add: the number stays on 0, and the Console shows a ReferenceError."
line: 0 | bad
line: [Add]
console: Uncaught ReferenceError: setCount is not defined
```

Sitting inside the parent on the page may look the same as sitting inside the parent's code, **but it is NOT the same thing!** On the page, the button sits inside the parent. In the code, `Child` is a separate function in a separate file, and it cannot see the names created inside `Parent`. Lesson 06 taught the rule behind it: a name created inside one function cannot be seen inside another function.

React's docs say it in one line: state is fully private to the component that declares it. React keeps each state variable inside the component that called `useState`, and no other component can read it or change it. The component that holds a state variable is the one that **owns the state**. It is the only component that can call its setter.

```tree caption="Placing a child inside a parent passes only the props written on its tag; the parent's state and setter stay inside the parent."
What `Child` can see when `Parent` places `<Child />`
- +The props written on the tag [`<Child />`] | React passes them **into `props`** | Here there are **none**
- !The parent's state and setter [`count` `setCount`] | Created by `useState` **inside `Parent`** | **Private** to `Parent`, so `Child` **cannot reach them**
```

### The guest list with `setGuests` inside the row

Now we start our guest list. The guest list file keeps the three guests in state, shows the heading and the count line, and places one row for each guest:

```jsx title="src/components/GuestList.jsx"
import { useState } from 'react';
import GuestRow from './GuestRow.jsx';

const initialGuests = [
  { id: 0, name: 'John' },
  { id: 1, name: 'Mia' },
  { id: 2, name: 'Sara' },
];

export default function GuestList() {
  const [guests, setGuests] = ~useState(initialGuests)~; // GuestList owns the list of guests

  return (
    <section>
      <h1>Party Guests</h1>
      <p>{guests.length} guests</p>
      <ul>
        {guests.map(guest => (
          <GuestRow
            key={guest.id}
            ~guest={guest}~ // The only value each row receives
          />
        ))}
      </ul>
    </section>
  );
}
```

The row file shows one guest's name and a `Remove` button. Its developer wants the button to remove the guest, so the button calls `setGuests` with a list that leaves this guest out:

```jsx title="src/components/GuestRow.jsx" bad="5"
export default function GuestRow({ guest }) {
  return (
    <li>
      {guest.name}
      <button onClick={() => ~setGuests~(guests.filter(g => g.id !== guest.id))}>Remove</button> {/* **WRONG:** GuestRow.jsx has no setGuests */}
    </li>
  );
}
```

Our main file only renders the guest list:

```jsx title="src/App.jsx"
import ~GuestList~ from './components/GuestList.jsx'; // The default export of the guest list file

export default function App() {
  return <GuestList />;
}
```

When the page opens, everything looks right:

```page width=text caption="The guest list when it opens, with setGuests called inside the row."
heading: Party Guests
line: 3 guests
line: John [Remove]
line: Mia [Remove]
line: Sara [Remove]
console: quiet
```

Now the user clicks `Remove` on Mia. Mia stays on the list, and the Console shows an error:

```page width=text caption="The same page after the user clicks Remove on Mia: all three guests stay, and the Console shows a ReferenceError."
heading: Party Guests
line: 3 guests
line: John [Remove]
line: Mia [Remove] | bad
line: Sara [Remove]
console: Uncaught ReferenceError: setGuests is not defined
```

The row cannot remove Mia, because the row has no way to reach the list. Here is what happens after the user's click:
1. React runs the arrow function given to Mia's button.
2. The arrow asks for `setGuests`, and `GuestRow.jsx` has no such name.
3. JavaScript throws a `ReferenceError` inside the handler, and the handler stops right there.
4. Nothing asked React to render again, so the page keeps all three rows and the line `3 guests`.

`guest` works inside the row because it is written on the tag: the guest list writes `guest={guest}` on each row inside `map`, React puts it inside `props`, and the row unpacks it in its parameter list. `setGuests` does not work, because it is written on no tag. It was created by `useState` inside `GuestList`, and it stays there.

### A row that hides only itself

Next, the developer tries another way. If the row cannot change the list, maybe it can keep its own state and hide itself:

```jsx title="src/components/GuestRow.jsx" bad="4,5"
import { useState } from 'react';

export default function GuestRow({ guest }) {
  const [isRemoved, setIsRemoved] = ~useState(false)~; // **WRONG:** a second record of who is coming, kept outside guests
  if (isRemoved) return null;

  return (
    <li>
      {guest.name}
      <button onClick={() => ~setIsRemoved(true)~}>Remove</button> {/* Changes only this row's own state */}
    </li>
  );
}
```

This time, the click seems to work. The user clicks `Remove` on Mia, and Mia's row disappears. But the line above the list still says `3 guests`:

```page width=text caption="The same page after the user clicks Remove on Mia, with isRemoved in the row: two rows under a line that still says 3 guests."
heading: Party Guests
line: 3 guests | bad
line: John [Remove]
line: Sara [Remove]
console: quiet
```

The row disappeared, so it looks as if `Remove` worked. **It may look the same at first, but it is NOT the same as removing the guest!** Here is what happens after the user's click:
1. Mia's row calls its own `setIsRemoved` with `true`.
2. React renders Mia's `GuestRow` again, and it returns `null`, so her row disappears.
3. `guests` inside `GuestList` still holds three guests, because nothing changed it.
4. The count line reads `guests.length`, so it still says `3 guests`.

The row changed its own state, and the list never heard about it. The Console stays quiet, because nothing here breaks a rule of React. The page simply shows two answers that disagree. React's docs show the same mistake on a page with two panels: each panel keeps its own state to know whether it is open, so the parent cannot keep only one panel open at a time.

The real list lives in `GuestList`, so the change must happen in `GuestList`. React's docs say what a component must do when it needs different props: it has to ask its parent to pass it different props. The next principle shows how a row asks.

> [!PRINCIPLE]
> **Principle 1: Private State: `GuestRow` Cannot Call `setGuests`**
>
> *State is private to the component that declares it, so a child component cannot call its parent's setter; the child sees only the props written on its tag.*
>
> A row placed inside the guest list looks as if it sits inside the list's code. It does not. `GuestRow` is a separate function, and `setGuests` was created inside `GuestList`, so calling it from the row throws a `ReferenceError` when the user clicks. Giving the row its own state hides the row, but the list in `GuestList` never changes, and the count line keeps the old number.
>
> **DO THIS:**
> ```jsx
> export default function GuestList() {
>   const [guests, setGuests] = ~useState(initialGuests)~; // Only GuestList can call setGuests
>   return <ul>{guests.map(guest => <GuestRow key={guest.id} guest={guest} />)}</ul>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function GuestRow({ guest }) {
>   return <button onClick={() => ~setGuests~(guests.filter(g => g.id !== guest.id))}>Remove</button>; // **WRONG:** setGuests is not defined in GuestRow
> }
> ```

## 2. Principle 2: `onRemove` Carries `handleRemove` Down to the Row

### A prop that holds text vs. a prop that holds a function

A prop can hold any JavaScript value: a string, a number, an object, and also a function. Here is a small button component that receives a function as a prop and gives it to a real button:

```jsx title="Passing a function as a prop"
function MyButton({ ~onSmash~ }) { // onSmash arrives in props like any other prop
  return <button ~onClick={onSmash}~>Click me</button>; // The real button calls onSmash when the user clicks
}

<MyButton onSmash={() => console.log('Hello')} />
```

When the user clicks `Click me`, the Console shows `Hello`.

Now compare a prop that holds text with a prop that holds a function:

```jsx title="A prop that holds text, and a prop that holds a function"
<MyButton ~label="Click me"~ /> {/* label holds text for MyButton to show */}
<MyButton ~onSmash={() => console.log('Hello')}~ /> {/* onSmash holds a function for MyButton to call */}
```

**Yes, it is the exact same thing!** For React, both are props written on the tag, and both arrive inside the same `props` object. The one difference is the value: text to show, or a function to call. This is the phone number from the start of the lesson. The parent hands its number down, and the child keeps it until it needs to call.

React's docs call a prop like `onSmash` an **event handler prop**: a prop whose value is a function that the child calls when something happens. In interviews you will hear a second name for the same thing, a **callback prop**, because the function it holds is a **callback function**, the callback from the start of this lesson.

### `onClick` on `<button>` vs. `onSmash` on `<MyButton>`

Both lines below give `handleClick` to a tag through a name that starts with `on`:

```jsx title="onClick on a built-in button, and onSmash on our own component"
<button ~onClick={handleClick}~>Click me</button> {/* React calls handleClick when the user clicks */}
<MyButton ~onSmash={handleClick}~ /> {/* handleClick only arrives in props.onSmash */}
```

**It may look the same, but it is NOT the same thing!** `<button>` is a **built-in component**: a tag that React gives us, such as `<button>` or `<div>`. React's docs say that built-in components support only browser event names, such as `onClick`, and React attaches `onClick` to the click of a real button in the browser. `<MyButton>` is our own component. `onSmash` is just a prop that arrives inside `props`. Nothing happens on a click until `MyButton` gives that function to a real `<button>`, as its `onClick={onSmash}` line does.

So the name `onSmash` is not special. React's docs say that when you build your own components, you can name their event handler props any way you like. By habit, the prop name starts with `on` and a capital letter, such as `onRemove`, and the function that handles the event starts with `handle`, such as `handleRemove`.

```tree caption="A name that starts with on means a browser event on a built-in component, and only an ordinary prop on our own component."
Two places a name that starts with `on` can appear
- +On a built-in component [`<button onClick={handleClick}>`] | A **browser event** that React listens for | React calls `handleClick` when **the user clicks**
- +On our own component [`<MyButton onSmash={handleClick} />`] | An **ordinary prop**, named by us | Nothing runs until `MyButton` **gives it to a real `<button>`**
```

### Passing `handleRemove` down to each row

Now we give the guest list a handler. We write `handleRemove` inside `GuestList`, right next to the `useState` line, and we pass it to every row as the prop `onRemove`:

```jsx title="src/components/GuestList.jsx" startLine="10" good="13,26"
export default function GuestList() {
  const [guests, setGuests] = useState(initialGuests);

  function ~handleRemove(id)~ { // Written next to the state, so it can call setGuests
    setGuests(guests.filter(guest => guest.id !== id));
  }

  return (
    <section>
      <h1>Party Guests</h1>
      <p>{guests.length} guests</p>
      <ul>
        {guests.map(guest => (
          <GuestRow
            key={guest.id}
            guest={guest}
            ~onRemove={handleRemove}~ // Hands the function itself down to every row
          />
        ))}
      </ul>
    </section>
  );
}
```

The row drops its own state and its broken `setGuests` line. It unpacks `onRemove` next to `guest` and gives it to the button:

```jsx title="src/components/GuestRow.jsx" bad="5"
export default function GuestRow({ guest, ~onRemove~ }) { // onRemove arrives in props, next to guest
  return (
    <li>
      {guest.name}
      <button ~onClick={onRemove}~>Remove</button> {/* **WRONG:** React calls handleRemove with the event object */}
    </li>
  );
}
```

The user clicks `Remove` on Mia. Nobody is removed, and the Console stays quiet:

```page width=text caption="The guest list after the user clicks Remove on Mia, with onClick={onRemove}: all three guests stay, with no error."
heading: Party Guests
line: 3 guests
line: John [Remove]
line: Mia [Remove] | bad
line: Sara [Remove]
console: quiet
```

The click did reach `handleRemove`, but `handleRemove` did not receive Mia's id. Here is what happens after the user's click:
1. React calls the function given to the button's `onClick`, which is `handleRemove` itself.
2. React passes the event object as the only argument, as Lesson 11 taught.
3. Inside `handleRemove`, `id` holds the event object, not Mia's id `1`.
4. `filter` keeps every guest, because no guest's `id` equals the event object.
5. `setGuests` receives a new array that still holds all three guests, so nothing changes on the page.

The row now holds the parent's function, and the parent's function can change the list. What is missing is the one thing only the row knows: which guest the user clicked. Principle 3 adds it.

### A prop name that does not match

One more mistake is easy to make while wiring a callback prop. The guest list writes the prop under one name, and the row unpacks it under another:

```jsx title="The tag in GuestList.jsx writes onDelete, and the parameter list in GuestRow.jsx unpacks onRemove"
<GuestRow key={guest.id} guest={guest} ~onDelete={handleRemove}~ /> {/* In GuestList.jsx: the prop is named onDelete */}
function GuestRow({ guest, ~onRemove~ }) { // **WRONG:** props holds onDelete, so onRemove is undefined
```

`props` holds `onDelete`, so `onRemove` is `undefined`. The button gets `onClick={undefined}`, and React attaches no handler at all. The user clicks `Remove`, and nothing happens, with no message in the Console. When a click does nothing and the Console is quiet, compare the name on the tag with the name in the parameter list.

> [!PRINCIPLE]
> **Principle 2: Event Handler Props: `onRemove` Carries `handleRemove` Down to the Row**
>
> *A prop can hold a function; the parent writes the handler next to its state, passes it on the child's tag, and the child gives it to a built-in component such as `<button>` through `onClick`.*
>
> A row cannot reach `setGuests`, but the guest list can write a function that does, and hand that function down on the row's tag. On our own component, `onRemove` is an ordinary prop with a name we chose. Only `onClick` on the real `<button>` is a browser event. Name the prop with `on` and the handler with `handle`.
>
> **DO THIS:**
> ```jsx
> function handleRemove(id) {
>   setGuests(guests.filter(guest => guest.id !== id));
> }
> <GuestRow key={guest.id} guest={guest} ~onRemove={handleRemove}~ /> // The row receives the function itself
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <GuestRow key={guest.id} guest={guest} ~onDelete={handleRemove}~ /> // **WRONG:** GuestRow unpacks onRemove, which is undefined
> ```

## 3. Principle 3: `onRemove(guest.id)` Tells the Parent Which Guest

### The child calls the function, and the parent changes the list

Here is the smallest row that tells its parent which item to remove. It receives an `id` and the parent's function, and it calls the function with the id inside its own arrow function:

```jsx title="A row that calls the parent's function with its own id"
function Row({ id, onRemove }) {
  return <button onClick={() => ~onRemove(id)~}>Remove</button>; // Calls the parent's function with this row's id
}

<Row id={2} onRemove={handleRemove} />
```

In the parent, the handler does the real work:

```jsx title="The parent's handler"
function handleRemove(id) {
  ~setNames(names.filter(n => n.id !== id))~; // The parent's own code changes the parent's state
}
```

**It may look as if the row removes the item, but it is NOT the row that does it!** The row only calls a function and passes a number. The code that builds the new list and calls the setter is the parent's own code, written next to the parent's state.

Now compare the two ways the row can give `onRemove` to its button:

```jsx title="Passing onRemove to the button, and calling it inside an arrow"
<button ~onClick={onRemove}~>Remove</button> {/* React calls handleRemove with the event object */}
<button ~onClick={() => onRemove(guest.id)}~>Remove</button> {/* The arrow calls handleRemove with the guest's id */}
```

They are NOT the same thing. With `onClick={onRemove}`, React calls `handleRemove` and decides the argument, which is the event object. With the arrow, React calls the arrow, and the arrow calls `handleRemove` with the guest's `id`. This is the arrow from Lesson 11 that passes an argument, now calling a prop.

### The row sends Mia's id

We change one line in the row:

```jsx title="src/components/GuestRow.jsx" good="5"
export default function GuestRow({ guest, onRemove }) {
  return (
    <li>
      {guest.name}
      <button onClick={~() => onRemove(guest.id)~}>Remove</button> {/* Calls handleRemove with this guest's id */}
    </li>
  );
}
```

`GuestList.jsx` does not change. The user clicks `Remove` on Mia. Her row disappears, and the count line outside the row changes to `2 guests`:

```page width=text caption="The guest list after the user clicks Remove on Mia, with the arrow that calls onRemove with guest.id."
heading: Party Guests
line: 2 guests | good
line: John [Remove]
line: Sara [Remove]
console: quiet
```

The click happened inside Mia's row, but the change shows in a line the row does not even render. Here is what happens after the user's click:
1. React runs the arrow function given to Mia's button.
2. The arrow calls `onRemove` with `1`, Mia's `guest.id`. In this row, `onRemove` is `handleRemove` from `GuestList`.
3. `handleRemove` calls `setGuests` with a new array that holds John and Sara.
4. React renders `GuestList` again. `guests` holds two guests, so the count line shows `2 guests`.
5. `map` now gives only two `<GuestRow>` tags, so Mia's row is gone.

`GuestRow` changed nothing itself. It sent one number up, and the guest list did the rest. The `1` came from Mia's own row: the guest list wrote `guest={guest}` on her tag, and the row read `guest.id` from it. And the `guests` that `handleRemove` filters is the `guests` of the render in which the guest list passed the function down, the snapshot from Lesson 15.

### One-way data flow, and the call that goes up

React's docs describe the usual direction of data with the words **one-way data flow**: data goes from the parent to the child through props, from the top of the tree to the bottom, and never back up as props. Think of water running downhill. In our page, `guest` and `onRemove` run down from the guest list to each row.

A callback prop does not reverse that flow. The row did not send a new list up. It sent a call with an id. The parent decided the new list, and the new list came down again as props on the next render. React's docs call this way of working **inverse data flow**: the child changes the parent's state by calling a function the parent passed down. The docs add that React makes this flow explicit, and that it takes a little more typing than **two-way data binding**, which some other tools use to let a box change a variable by itself.

```tree dir=right caption="The whole trip of one click on Remove: a call goes up with an id, and the new list comes down as props."
One click on `Remove` next to Mia
- +1. The user clicks Remove [`GuestRow`] | The row's arrow calls **`onRemove` with `1`**
- +2. The parent's handler runs [`handleRemove`] | Calls **`setGuests`** with John and Sara
- +3. React renders the parent again [`GuestList`] | The count line reads **`2 guests`**
- +4. The new list comes down [`guest` `onRemove`] | Only **two rows** receive props
```

### Calling `handleRemove` on the tag

To pass Mia's id, a developer might try to add it right on the tag inside `map`, in the guest list:

```jsx title="src/components/GuestList.jsx" startLine="23" bad="26"
          <GuestRow
            key={guest.id}
            guest={guest}
            ~onRemove={handleRemove(guest.id)}~ // **WRONG:** the parentheses call handleRemove while GuestList renders
          />
```

The page never shows the list. It goes blank, and the Console shows an error:

```page width=text caption="The guest list when handleRemove is called on the tag: the page is blank, and the Console shows Too many re-renders."
blank
console: Uncaught Error: Too many re-renders. React limits the number of renders to prevent an infinite loop.
```

The user did not even click. Here is what happens as soon as the page opens:
1. React calls `GuestList`, and `map` reaches the first `<GuestRow>` tag.
2. The parentheses after `handleRemove` call it right now, during rendering.
3. `handleRemove` calls `setGuests`, which asks React to render `GuestList` again.
4. That new render reaches the same tag and calls `handleRemove` again, which asks for another render.
5. React stops the loop with the error, and an error during rendering makes React remove the page from the screen.

React's docs show the same mistake in their tic-tac-toe tutorial, with `handleClick(0)` written on a square's tag. The fix is to keep each job in its place. The parent passes the function itself, `onRemove={handleRemove}`. The child adds the id inside its own arrow, `() => onRemove(guest.id)`.

> [!PRINCIPLE]
> **Principle 3: Inverse Data Flow: `onRemove(guest.id)` Tells the Parent Which Guest**
>
> *The child wraps the call in an arrow function and passes the value the parent needs, `() => onRemove(guest.id)`; the parent's handler calls its own setter, React renders the parent again, and the new list comes down as props.*
>
> The row knows which guest the user clicked, and the guest list knows how to change the list. The arrow joins the two: the row calls `onRemove` with its own `guest.id`, and the guest list's `handleRemove` calls `setGuests`. Data still flows one way. Only the call with the id goes up, and the new list comes down on the next render.
>
> **DO THIS:**
> ```jsx
> <GuestRow key={guest.id} guest={guest} onRemove={handleRemove} />
> <button onClick={~() => onRemove(guest.id)~}>Remove</button> // In GuestRow: calls handleRemove with this guest's id
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <GuestRow key={guest.id} guest={guest} ~onRemove={handleRemove(guest.id)}~ /> // **WRONG:** calls handleRemove during rendering: Too many re-renders
> ```

## 4. Principle 4: `AddGuest` Sends the Typed Name Up with `onAdd(name)`

### A value that only the child has

So far, the row sent up a value it received from its parent, `guest.id`. Sometimes the value exists only in the child. Here is a small box component that keeps the text the user types in its own state, and sends that text to its parent when the user clicks `Add`:

```jsx title="A box that sends the typed name to its parent"
function NameBox({ onAdd }) {
  const [name, setName] = useState('');
  return (
    <>
      <input value={name} onChange={e => setName(e.target.value)} />
      <button onClick={() => ~onAdd(name)~}>Add</button> {/* Sends the text the user typed */}
    </>
  );
}

<NameBox onAdd={name => console.log(name)} />
```

The user types `Leo` and clicks `Add`, and the Console shows `Leo`.

This is the same tool as `onRemove`. The one difference is where the argument comes from. The row took `guest.id` from a prop it received. The box takes `name` from its own state, a value the parent never had. Each component keeps what it knows: the box keeps the typing, and the guest list keeps the guests. The finished name travels up as the argument of the call.

### Clearing the box before or after the call

The box should also empty itself after the click, so the user can type the next guest. The child can run its own code in the same handler as the call. There are two ways to order the two lines:

```jsx title="Clearing the box first, and sending the name first"
~setName(''); onAdd(name);~ // With setName('') first: onAdd still receives Leo
~onAdd(name); setName('');~ // With onAdd(name) first: onAdd receives Leo
```

Many readers expect the first order to send an empty name, because the box is cleared before the call. **Yes, it is the exact same thing!** Both orders send `Leo`. Here is what happens when the user types `Leo` and clicks `Add` with `setName('')` first:
1. In this render, `name` is `'Leo'`.
2. `setName('')` asks React for a new render with an empty box. It does not change `name` in this render, as Lesson 15 taught.
3. `onAdd(name)` runs with `'Leo'`.
4. After the click, React renders again, and the box is empty.

### The box that adds a guest

Now we add the box to our page. The new file keeps the typed name in its own state and calls `onAdd` with it:

```jsx title="src/components/AddGuest.jsx"
import { useState } from 'react';

export default function AddGuest({ ~onAdd~ }) { // GuestList passes handleAdd here
  const [name, setName] = useState('');

  return (
    <>
      <input
        placeholder="Guest name"
        value={name}
        onChange={e => setName(e.target.value)}
      />
      <button onClick={() => {
        setName('');
        ~onAdd(name);~ // Sends the typed name up; name still holds Leo in this click
      }}>Add</button>
    </>
  );
}
```

The guest list gets a second handler, `handleAdd`, written next to its state. A counter above the component gives each new guest the next free id, as in Lessons 18 and 19. The guest list imports the box at the top of the file and passes `handleAdd` to it under the heading:

```jsx title="src/components/GuestList.jsx" startLine="11" good="21,27"
let nextId = 3;

export default function GuestList() {
  const [guests, setGuests] = useState(initialGuests);

  function handleRemove(id) {
    setGuests(guests.filter(guest => guest.id !== id));
  }

  function handleAdd(name) {
    ~setGuests([...guests, { id: nextId++, name: name }])~; // A new array with the guest that AddGuest sent up
  }

  return (
    <section>
      <h1>Party Guests</h1>
      ~<AddGuest onAdd={handleAdd} />~ {/* Hands handleAdd down to the box */}
      <p>{guests.length} guests</p>
```

The user types `Leo` in the box and clicks `Add`. The box empties, a row for Leo appears, and the line says `4 guests`:

```page width=text caption="The guest list after the user types Leo and clicks Add: the box is empty again, and Leo has his own row."
heading: Party Guests
form:
  field: | Guest name
  button: Add
line: 4 guests | good
line: John [Remove]
line: Mia [Remove]
line: Sara [Remove]
line: Leo [Remove] | good
console: quiet
```

Leo's `id` is `3`, from `nextId`. The line `nextId++` sits in the event handler, so it runs once for each click by the user, even under `<StrictMode>`.

### Passing `onAdd` straight to the button

The mistake of Principle 2 comes back here with a louder result. Suppose the box gives `onAdd` straight to the button:

```jsx title="src/components/AddGuest.jsx" startLine="13" bad="13"
      <button ~onClick={onAdd}~>Add</button> {/* **WRONG:** React calls handleAdd with the event object */}
```

The user types `Leo` and clicks `Add`. The page goes blank, and the Console shows an error that starts with `Objects are not valid as a React child`. Here is what happens after the user's click:
1. React calls `handleAdd` with the event object, as Lesson 11 taught.
2. `handleAdd` adds a fourth guest whose `name` is that event object.
3. React renders the guest list again, and the new row tries to show `{guest.name}`, which is an object.
4. React cannot put an object on the page, so it throws an error during rendering and removes the page from the screen.

The fix is the same as in Principle 3: the child calls the prop inside its own arrow, with the value the parent needs.

> [!PRINCIPLE]
> **Principle 4: The Callback Argument: `AddGuest` Sends the Typed Name Up with `onAdd(name)`**
>
> *When the value exists only in the child, such as the text typed in its own box, the child passes it as the argument of the callback; the child may run its own code, such as clearing its box, in the same handler.*
>
> The guest list never sees the letters the user types. The box keeps them in its own `name` state, and when the user clicks `Add`, it calls `onAdd` with the finished name. Clearing the box with `setName('')` in the same click does not empty `name` for that call, because `name` is this render's snapshot.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => { setName(''); ~onAdd(name);~ }}>Add</button> // Sends the typed name, then the box shows empty
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button ~onClick={onAdd}~>Add</button> // **WRONG:** sends the event object as the new guest's name
> ```

## Putting All Four Principles Together

### The complete guest list

Here is our complete guest list. `GuestList` owns `guests` and writes both handlers. `GuestRow` and `AddGuest` only call the functions they receive:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  ~<StrictMode>~ {/* Mounts App inside StrictMode */}
    <App />
  </StrictMode>
);
```

```jsx title="src/App.jsx"
import GuestList from './components/GuestList.jsx';

export default function ~App~() { // 1. Called first when the page loads
  return <GuestList />;
}
```

```jsx title="src/components/GuestList.jsx"
import { useState } from 'react';
import AddGuest from './AddGuest.jsx';
import GuestRow from './GuestRow.jsx';

const initialGuests = [
  { id: 0, name: 'John' },
  { id: 1, name: 'Mia' },
  { id: 2, name: 'Sara' },
];

let nextId = 3;

export default function ~GuestList~() { // 2. Called second, from App
  const [guests, setGuests] = ~useState(initialGuests)~; // Principle 1: only GuestList can call setGuests

  function ~handleRemove(id)~ { // Principle 2: written next to the state
    setGuests(guests.filter(guest => guest.id !== id));
  }

  function ~handleAdd(name)~ { // Principle 4: receives the name typed in AddGuest
    setGuests([...guests, { id: nextId++, name: name }]);
  }

  return (
    <section>
      <h1>Party Guests</h1>
      <AddGuest ~onAdd={handleAdd}~ /> {/* Principle 4: the box gets handleAdd */}
      <p>{guests.length} guests</p>
      <ul>
        {guests.map(guest => (
          <GuestRow
            key={guest.id}
            guest={guest}
            ~onRemove={handleRemove}~ // Principle 2: each row gets the function itself
          />
        ))}
      </ul>
    </section>
  );
}
```

```jsx title="src/components/AddGuest.jsx"
import { useState } from 'react';

  const [name, setName] = useState('');

  return (
    <>
      <input
        placeholder="Guest name"
        value={name}
        onChange={e => setName(e.target.value)}
      />
      <button onClick={() => {
        setName('');
        ~onAdd(name);~ // Principle 4: sends the typed name up
      }}>Add</button>
    </>
  );
}
```

```jsx title="src/components/GuestRow.jsx"

  return (
    <li>
      {guest.name}
      <button onClick={~() => onRemove(guest.id)~}>Remove</button> {/* Principle 3: tells GuestList which guest */}
    </li>
  );
```

### How React calls the components in order

When the page opens, React starts at `App` and follows the tags from top to bottom. Inside `GuestList`, it calls the box first, because the box's tag comes first, and then one row for each guest. Props run down every line of this tree, and the calls to `onAdd` and `onRemove` run back up to `GuestList`:

```tree caption="The component tree of the guest list and the order in which React calls each component when the page opens."
`App` [1. Called first] | **Root component** | Returns `<GuestList />`
- +`GuestList` [2. Called second] | **Owns `guests`** and writes `handleRemove` and `handleAdd`
  - +`AddGuest` [3. Called third] | Owns `name` | Receives **`onAdd`**
  - +`GuestRow` for John, Mia, and Sara [4. Called once per guest] | Receives **`guest`** and **`onRemove`**
```

| Aspect | The Habit That Breaks the Page | The React Rule |
| :--- | :--- | :--- |
| **Who changes the list** | The row calls `setGuests`, which throws `ReferenceError`, or keeps its own `isRemoved`, which leaves the count wrong | Only `GuestList`, which owns `guests`, calls `setGuests` |
| **What goes down** | The row has no way to reach the parent's code | The parent passes `handleRemove` as the prop `onRemove`, next to `guest` |
| **What goes up** | `onClick={onRemove}` sends the event object, and `onRemove={handleRemove(guest.id)}` calls the handler during rendering | The child calls the prop in its own arrow: `() => onRemove(guest.id)` |
| **A value only the child has** | The parent tries to reach into the child's box | The child sends it as the argument: `onAdd(name)` |

## For the Interview

> **The Interview Question:** How does a child component notify its parent or trigger state updates using callback props?

### How to Answer Clearly in 30 Seconds

"A child cannot change its parent's state, because state is private to the component that declares it, and props are read-only. So the parent writes a handler next to its state, such as `handleRemove`, and passes it to the child as a prop, such as `onRemove`. When the user acts, the child calls that prop with the value the parent needs, such as `onRemove(guest.id)` or `onAdd(name)`. The parent's own handler calls its own setter, React renders the parent again, and the new data comes down as props. Three details matter:
1. **Data still flows one way**: only a function call goes up, and React's docs call this inverse data flow.
2. **`on` names are ordinary props on our own components**: only built-in components such as `<button>` turn `onClick` into a browser event. By habit, the prop starts with `on` and the handler with `handle`.
3. **Pass the function, do not call it**: `onRemove={handleRemove(guest.id)}` calls the handler during rendering and ends in Too many re-renders. The id goes into the child's arrow, `() => onRemove(guest.id)`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"If the child can change the parent's state, does data now flow both ways?"**
   **No.** Data still goes only from the parent to the child through props. The child sends up a call with a value, such as an id, and nothing else. The parent decides what the new state is, and the new state comes down as props on the next render. React's docs say this makes the flow explicit, at the cost of a little more typing than two-way data binding. The benefit is that you can follow every change: the button's `onClick` came from `GuestRow`, `GuestRow` got it as `onRemove` from `GuestList`, and `GuestList` defined it.
2. **"Why not pass `setGuests` itself to the child?"**
   **Sometimes you can.** React's docs pass a setter straight down in their *Thinking in React* page, as `onFilterTextChange={setFilterText}`, because the child sends exactly the next value. But a row should not decide what the whole new list is. With `onRemove`, the row says only which guest the user clicked, and the parent keeps the rule for building the new list. The parent can also check the value first, such as skipping an empty name, and the child never needs to know. A name that describes the action, such as `onRemove`, also leaves the parent free to change how it handles it.
3. **"Does a new arrow function on every render cause problems?"**
   **Usually not.** `() => onRemove(guest.id)` is a new function each time the row renders, and that is normal in React. It matters only when a child is skipped with `memo` and should receive the same function between renders. Then `useCallback` keeps one function, as Lessons 55 and 57 show. When many components deep in the tree need the same functions, passing one `dispatch` function or putting the functions in context saves passing them through every level, as Lessons 27 to 29 show. And when two siblings must share one changing value, the state moves up to their common parent and the same callback props connect them, as Lesson 24 shows.

```tree dir=right caption="Interview summary: how a child triggers a state change in its parent."
How a child triggers a state change in its parent
- +The parent owns the state [`useState`] | Writes the handler **next to the state**
- +The parent passes the handler down [`onRemove={handleRemove}`] | An **ordinary prop** that holds a function
- +The child calls it when the user acts [`onRemove`] | Sends **only the value the parent needs**
- +The new state comes down [`guest`] | **One-way data flow** stays intact
```
