> INTERVIEW QUESTION | ❱ CORE | Why does state sometimes vanish, or survive, when you did not expect it?

## Where React Keeps a Component's State

### Two tags with two names, and the count still stays

Here is a small page with one counter button for a person and a `Next` button. When the page opens, the counter belongs to Anna and shows 0:

```page width=text caption="The counter page when it opens: Anna's counter shows 0."
line: [Anna: 0] [Next]
console: quiet
```

Each click on the counter adds one. The `Next` button switches between Anna and Ben. The code writes two separate `Counter` tags, one for each person:

```jsx title="src/App.jsx"
import { useState } from 'react';

function Counter({ person }) {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      {person}: {count}
    </button>
  );
}

export default function App() {
  const [isAnna, setIsAnna] = useState(true);
  return (
    <div>
      {isAnna ? ~<Counter person="Anna" />~ : ~<Counter person="Ben" />~} {/* Two tags, one for each person */}
      <button onClick={() => setIsAnna(!isAnna)}>Next</button>
    </div>
  );
}
```

The user clicks Anna's counter three times:

```page width=text caption="After the user clicks Anna's counter three times."
line: [Anna: 3] [Next]
console: quiet
```

Then the user clicks `Next`:

```page width=text caption="After the user clicks Next, Ben's counter shows 3, the count the user gave Anna."
line: [Ben: 3] [Next] | bad
console: quiet
```

Ben's counter shows 3, and the user never clicked it.

To the reader, the two tags with two names look like two counters. To React, they are the exact same `Counter`. **Yes, it is the exact same thing!** In both branches of the `? :`, `App` returns a `Counter` as the first child of the `<div>`. The click on `Next` only gives that same `Counter` a new `person` prop. So React keeps its `count`.

React works this way because it does not keep state inside the JSX tag, and not inside the component function either. React holds the state itself, and it ties each piece of state to the place where the component sits in the UI tree. React's docs call that place the component's **position in the UI tree**.

Think of a letter and the address on its envelope. The post office delivers a letter to an address, not to a person. When a new family moves into the house, the old family's letters still arrive there, and the new family finds them in the box. React's docs use the same word: "To React, these two counters have the same 'address'." React gives state to a position, so when Ben takes Anna's position, Ben finds Anna's count:

```tree caption="To the reader, two tags with two names look like two counters; to React, they are one Counter at one position."
What the reader sees and what React sees in `{isAnna ? <Counter person="Anna" /> : <Counter person="Ben" />}`
- !What the reader sees [`<Counter person="Anna" />` `<Counter person="Ben" />`] | Two tags with **two names** | Expects **two counters**, so Ben should start at **0**
- +What React sees [`Counter` as the first child of the `<div>`] | The **same component** at the **same position** | Only the `person` prop changes, so React **keeps `count`**: Ben shows **3**
```

### What is at stake

The key idea of this lesson is one rule. React keeps a component's state while the same component stays at the same position. When React removes the component, or puts a different component at that position, the state is gone.

What is at stake is what the user writes. On the page of this lesson, the user writes "Happy birthday, Anna!" to a friend, then clicks the button for Ben. The same text now sits under the heading "Note to Ben", right above a button that says "Send to Ben". In another case, the user's whole note disappears the moment a tip appears above it. Nobody wrote a line of code that moves or clears the text.

Readers usually go wrong in three places:
- They think the state lives inside the component function, or inside the JSX tag. It lives in React, at a position.
- They think a new prop makes a new component. A new prop at the same position is the same component.
- They read the `if` and the `? :` in their code. React never sees those. It sees only the tree that the code returns.

### Four Principles of Keeping and Resetting State

**PRINCIPLES:** React holds every piece of state at a position in the UI tree. Each render, React compares the new tree with the old one, position by position. Four practical rules follow from that:
1. **Principle 1: Closing the Note Throws Away Its Text**: When React removes a component from the tree, it destroys the component's state. When the component comes back, its state starts from scratch.
2. **Principle 2: Switching to Ben Keeps Anna's Text**: The same component at the same position keeps its state, even when its props change, and even when the code writes two separate tags in two branches.
3. **Principle 3: The Tip Box Around the Note Erases It**: A different component type at a position, such as a `<div>` where `NoteBox` was, destroys the old component and the state of everything inside it. To keep state, the tree must match from one render to the next.
4. **Principle 4: `key={friend}` Gives Ben an Empty Note**: A `key` becomes part of the position. When the `key` changes, React creates a new component with new state and new DOM elements.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Removed From the Tree, the State Is Destroyed** | A part of the page that the user closes and opens again comes back empty, with zero Console errors and no line of code that clears it. | React keeps state while the component is rendered at its position. When React removes it, the state is destroyed, and a returning component starts from its initial value. |
| **Principle 2** | **Same Component, Same Position, Same State** | Text typed for one person stays on screen for the next person, next to that person's name and send button. | React matches the tree the code returns, not the code. A new prop at the same position is the same component, so its state stays. |
| **Principle 3** | **A Different Type at the Position Resets Everything Inside** | Adding a wrapper `<div>` around a component on a condition erases what the user typed inside it. | To keep state, keep the tree's structure the same between renders. Put a conditional line next to the component instead of wrapping the component in a different tag. |
| **Principle 4** | **A New `key` Makes a New Component** | Interviewers ask how to reset a form when the user switches to another person, and why an Effect is the wrong tool for it. | Give the component a `key` that changes when it should become a different one, such as `key={friend}`. `key` works outside lists too. |

## 1. Principle 1: Closing the Note Throws Away Its Text

### One tag written once, two counters

Start with the `Counter` from the opening. This time `App` writes one tag, keeps it in a variable, and places that variable twice:

```jsx title="src/App.jsx" startLine="12"
export default function App() {
  const ~counter~ = <Counter person="Anna" />; // One tag, written once
  return (
    <div>
      {counter}
      {counter}
    </div>
  );
}
```

The user clicks the first counter twice:

```page width=text caption="After the user clicks the first counter twice, the second counter still shows 0."
line: [Anna: 2] [Anna: 0]
console: quiet
```

It looks like one counter, because the code wrote one tag. **It may look the same, but it is NOT the same thing!** The tag sits at two positions, the first and the second child of the `<div>`, so React keeps two separate `count` values. React's docs put it this way: "the state is actually held inside React. React associates each piece of state it's holding with the correct component by where that component sits in the render tree."

### A counter that leaves the tree and comes back

Now give Ben's counter a button that removes it from the page and brings it back:

```jsx title="src/App.jsx" startLine="12"
export default function App() {
  const [showBen, setShowBen] = useState(true);
  return (
    <div>
      <Counter person="Anna" />
      {~showBen &&~ <Counter person="Ben" />} {/* Shows Ben's counter, or nothing */}
      <button onClick={() => setShowBen(!showBen)}>Show or hide Ben</button>
    </div>
  );
}
```

The user clicks Ben's counter three times, clicks `Show or hide Ben` to hide it, then clicks the same button again to show it:

```page width=text caption="After the user hides Ben's counter and shows it again, Ben's counter is back at 0."
line: [Anna: 0] [Ben: 0] [Show or hide Ben] | bad
console: quiet
```

Ben's counter is back at 0. When `showBen` became `false`, nothing was rendered at that position. React removed Ben's `Counter` from the tree and destroyed its `count`. When `showBen` became `true` again, React put a new `Counter` at that position, and `useState(0)` started it from scratch.

React's docs use two words for this. React **destroys** the state of a component it removes. The next time the component appears, its state is **reset**, which means "initialized from scratch" from the initial value in `useState`.

```tree dir=right caption="What happens to Ben's count when showBen goes from true to false and back to true."
Ben's `Counter` at its position
- +1. `showBen` is `true` [`<Counter person="Ben" />`] | React renders Ben's `Counter` | The user clicks it up to **3**
- !2. `showBen` is `false` [`false`] | **Nothing** is rendered at that position | React **removes** the `Counter` and **destroys** `count`
- +3. `showBen` is `true` again [`<Counter person="Ben" />`] | React renders a **new** `Counter` there | `useState` starts it again at **0**
```

### The note page: a box that forgets the note

Now the note page. `NoteBox` holds the text of the note in a controlled `<textarea>`, as Lesson 20 built:

```jsx title="src/components/NoteBox.jsx"
import { useState } from 'react';

export default function NoteBox({ friend }) {
  const [~text~, setText] = useState(''); // The note starts empty
  return (
    <section>
      <h2>Note to {friend}</h2>
      <textarea
        value={text}
        placeholder={'Write to ' + friend}
        onChange={e => setText(e.target.value)}
      />
      <button>Send to {friend}</button>
    </section>
  );
}
```

`App` shows the note while `isOpen` is `true`, and one button closes and opens it:

```jsx title="src/App.jsx"
import { useState } from 'react';
import NoteBox from './components/NoteBox.jsx';

export default function App() {
  const [isOpen, setIsOpen] = useState(true);
  return (
    <main>
      <h1>Write a Note</h1>
      <button onClick={() => setIsOpen(!isOpen)}>
        {isOpen ? 'Close note' : 'Write a note'}
      </button>
      {~isOpen &&~ <NoteBox friend="Anna" />} {/* The note, or nothing */}
    </main>
  );
}
```

The user types a note to Anna:

```page width=text caption="The user has typed a note to Anna."
heading: Write a Note
line: [Close note]
form: title=Note to Anna
  textarea: | Happy birthday, Anna!
  button: Send to Anna
console: quiet
```

The user clicks `Close note` for a moment, then clicks `Write a note` to go back to it:

```page width=text caption="After the user closes the note and opens it again, the box is empty."
heading: Write a Note
line: [Close note]
form: title=Note to Anna
  textarea: | | bad
  button: Send to Anna
console: quiet
```

The box is empty, and it shows only its grey placeholder, `Write to Anna`. React threw the note away. No line of our code sets `text` back to an empty string, and the Console shows nothing. Here is what happens, in order:
1. The page opens with `isOpen` set to `true`. React renders `NoteBox` at its position, with `text` set to an empty string.
2. The user types `Happy birthday, Anna!`, and `NoteBox` holds it in `text`.
3. The user clicks `Close note`, and `App` sets `isOpen` to `false`.
4. React renders `App` again. `isOpen && <NoteBox friend="Anna" />` gives `false`, so nothing is rendered at that position.
5. React removes `NoteBox` from the tree and destroys its `text`.
6. The user clicks `Write a note`, and `App` sets `isOpen` back to `true`.
7. React renders a `NoteBox` at that position again. It is a new one, so `useState('')` starts its `text` from scratch.

While the note is closed, the browser's Elements panel shows that the note is really gone. There is no heading, no text box, and no send button in the DOM:

```dom caption="The Elements panel while the note is closed: the h2, the textarea, and the send button are not in the DOM."
<main>
  <h1>Write a Note</h1>
  <button>Write a note</button>
* no section, no textarea, and no Send to Anna button
</main>
```

This is a common mistake on real pages. A developer shows a panel with `{isShowing && <Panel />}`. The user types into a box inside it, closes the panel to look at something else, and opens it again. The box is empty, and the user has to type everything again. React's docs say it plainly: "unmounting a component destroys its internal state, which is not always what you want." To **unmount** a component is React's word for removing it from the tree.

> [!PRINCIPLE]
> **Principle 1: Removed From the Tree: React Destroys the State**
>
> *React keeps a component's state while the component is rendered at its position in the UI tree; when React removes the component, it destroys the state, and when the component comes back, its state starts from scratch.*
>
> State is not kept in the JSX tag or in the component function. React holds it at the position where the component was rendered. When the user closes the note, nothing is rendered at that position, so React throws the text away. When the note opens again, React builds a new `NoteBox`, and `useState` gives it its initial value.
>
> **DO THIS:**
> ```jsx
> function App() {
>   const [isOpen, setIsOpen] = useState(true);
>   const [text, setText] = useState('');
>   return isOpen && <NoteBox ~text={text}~ onTextChange={setText} />; // The text lives in App, so closing the note keeps it
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function App() {
>   const [isOpen, setIsOpen] = useState(true);
>   return ~isOpen &&~ <NoteBox friend="Anna" />; // **WRONG:** expecting the text to come back after isOpen goes false and true; the new NoteBox starts empty!
> }
> ```

## 2. Principle 2: Switching to Ben Keeps Anna's Text

### Two `return` lines, one counter

The opening showed two `Counter` tags in a `? :` that React treats as one counter. The same holds when the code splits the two tags into two `return` lines, one inside an `if`:

```jsx title="src/App.jsx" startLine="12"
export default function App() {
  const [isAnna, setIsAnna] = useState(true);
  if (isAnna) {
    return (
      <div>
        ~<Counter person="Anna" />~ {/* First child of the div */}
        <button onClick={() => setIsAnna(false)}>Next</button>
      </div>
    );
  }
  return (
    <div>
      ~<Counter person="Ben" />~ {/* Also the first child of the div */}
      <button onClick={() => setIsAnna(true)}>Next</button>
    </div>
  );
}
```

The user clicks Anna's counter three times and clicks `Next`. Ben's counter shows 3 again. The two `return` lines look like two separate pages, but both return a `<div>` with a `Counter` as its first child. React's docs: "React doesn't know where you place the conditions in your function. All it 'sees' is the tree you return."

```tree caption="Three ways to write the counter for Anna and Ben, and the one tree React sees in all three."
The tree React sees: a `<div>` with a `Counter` as its first child
- +One tag with a prop [`<Counter person={person} />`] | One `Counter` at the first position | **Same component, same position**: `count` stays
- +Two tags in a `? :` [`isAnna ? <Counter person="Anna" /> : <Counter person="Ben" />`] | **Yes, it is the exact same thing!** | `count` stays
- +Two `return` lines [`if isAnna return ...` `return ...`] | **Yes, it is the exact same thing!** | `count` stays
```

This is the rule of this principle, in React's docs' own words: "It's the same component at the same position, so from React's perspective, it's the same counter." You already know the same fact for DOM nodes from Lesson 13: a re-render keeps the DOM nodes that sit in the same spot, with the text typed in them. State follows the same rule.

### The note page: Anna's text under Ben's name

Now the note page gets its two friend buttons. `App` holds the chosen friend in state and passes it to `NoteBox`. `NoteBox.jsx` does not change:

```jsx title="src/App.jsx"
import { useState } from 'react';
import NoteBox from './components/NoteBox.jsx';

export default function App() {
  const [isOpen, setIsOpen] = useState(true);
  const [friend, setFriend] = useState('Anna');
  return (
    <main>
      <h1>Write a Note</h1>
      <button onClick={() => setFriend('Anna')}>Anna</button>
      <button onClick={() => setFriend('Ben')}>Ben</button>
      <button onClick={() => setIsOpen(!isOpen)}>
        {isOpen ? 'Close note' : 'Write a note'}
      </button>
      {isOpen && <NoteBox ~friend={friend}~ />} {/* Only the prop changes when the user picks a friend */}
    </main>
  );
}
```

The user types a note to Anna:

```page width=text caption="The user has typed a note to Anna."
heading: Write a Note
line: [Anna] [Ben] [Close note]
form: title=Note to Anna
  textarea: | Happy birthday, Anna!
  button: Send to Anna
console: quiet
```

Then the user clicks `Ben`:

```page width=text caption="After the user clicks Ben, the note written for Anna sits under Note to Ben."
heading: Write a Note
line: [Anna] [Ben] [Close note]
form: title=Note to Ben
  textarea: | Happy birthday, Anna! | bad
  button: Send to Ben | bad
console: quiet
```

The heading and the button now name Ben, and the box still holds the note written for Anna. React kept the state, because `App` still returns a `NoteBox` at the same position. Here is what happens, in order:
1. The page opens with `friend` set to `'Anna'`, and the heading says `Note to Anna`.
2. The user types `Happy birthday, Anna!`, and `NoteBox` holds it in `text`.
3. The user clicks `Ben`, and `App` sets `friend` to `'Ben'`.
4. React renders `App` again. At the same position, `App` returns a `NoteBox` again, now with the prop `friend` set to `'Ben'`.
5. React sees the same component at the same position, so it keeps this `NoteBox` and its `text`.
6. `NoteBox` runs again with the new prop. The heading says `Note to Ben`, and the button says `Send to Ben`.
7. `text` still holds `Happy birthday, Anna!`, so the box still shows it.

In the Elements panel, the same `<textarea>` node stays in the DOM. Only the text of the `<h2>` and of the button changes.

The real cost is a note sent to the wrong person. React's docs describe the same page: "You don't want to let the user send a message they already typed to a wrong person due to an accidental click."

Writing two separate tags in the code does not fix it. Look at both side by side:

```jsx title="One NoteBox tag with a prop, and two NoteBox tags in a ? :"
{isOpen && <NoteBox ~friend={friend}~ />} {/* One tag: Anna's text stays for Ben */}
{isOpen && (friend === 'Anna' ? ~<NoteBox friend="Anna" />~ : <NoteBox friend="Ben" />)} {/* Two tags: Anna's text still stays for Ben */}
```

**Yes, it is the exact same thing!** For React, both lines put a `NoteBox` at the same position, so the text stays in both. A new prop never makes a new component. Only a different component at that position, or a new `key`, does. The next two principles show each one.

The same rule causes a well-known bug with forms that copy a prop into state, as Lesson 22 showed. A contact page shows an edit form for the chosen contact, and the form starts its state with `useState(initialData.name)`. The user picks Taylor, then picks Alice. The form stays at the same position, so React keeps its state, and `useState` reads `initialData.name` only on the first render. React's docs describe the result: "the state updates but the form keeps showing the previous contact's details."

> [!PRINCIPLE]
> **Principle 2: Same Position: A New Prop Keeps the Old State**
>
> *When the same component is rendered at the same position, React keeps its state, even when its props change and even when the code writes two separate tags in two branches, because React matches what the component returns, not how the code is written.*
>
> When the user clicks `Ben`, `NoteBox` gets a new `friend` prop, but it is still a `NoteBox` at the same position. React keeps it and its `text`, so the note typed for Anna now sits under Ben's name. React never sees the `if` or the `? :` in the code. It sees only the tree that the code returns.
>
> **DO THIS:**
> ```jsx
> <Counter ~person={person}~ /> {/* One Counter at one position: count stays when person changes */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {isAnna ? ~<Counter person="Anna" />~ : <Counter person="Ben" />} {/* **WRONG:** expecting Ben to start at 0; it is the same Counter, so Ben gets Anna's count */}
> ```

## 3. Principle 3: The Tip Box Around the Note Erases It

### A different component at the same position

Principle 2 kept a `Counter` at its position. Now put something else there. When the user takes a break, the code shows a line of text instead of the counter:

```jsx title="src/App.jsx" startLine="12"
export default function App() {
  const [isPaused, setIsPaused] = useState(false);
  return (
    <div>
      {isPaused ? ~<p>See you later!</p>~ : <Counter person="Anna" />} {/* A p, or a Counter, at the same position */}
      <button onClick={() => setIsPaused(!isPaused)}>Take a break</button>
    </div>
  );
}
```

The user clicks the counter up to 3, clicks `Take a break`, and clicks it again to come back. The counter shows 0. At that position, a `<p>` took the place of `Counter`. A `<p>` and a `Counter` are different **component types**, which is React's name for what sits at a position: a built-in tag such as `<p>` or `<div>`, or a component such as `Counter` or `NoteBox`. When the type at a position changes, React removes the old one and its state.

That case is easy to accept, because the counter really left the page. The next one is harder to accept. Here the `Counter` never leaves. Only the tag around it changes:

```jsx title="src/App.jsx" startLine="12"
export default function App() {
  const [isFancy, setIsFancy] = useState(false);
  return (
    <div>
      {isFancy ? (
        ~<div>~ {/* A div around the Counter */}
          <Counter person="Anna" />
        </div>
      ) : (
        ~<section>~ {/* A section around the same Counter */}
          <Counter person="Anna" />
        </section>
      )}
      <button onClick={() => setIsFancy(!isFancy)}>Fancy</button>
    </div>
  );
}
```

The user clicks the counter up to 3 and clicks `Fancy`. The counter shows 0 again. **It may look the same, but it is NOT the same thing!** The `Counter` looks untouched, because only the tag around it changed. But React compares the tree from the top. At the first position, a `<div>` now stands where a `<section>` was. That is a different type, so React removes the `<section>` together with everything inside it, including the `Counter` and its `count`. React's docs say that when the `section` was removed from the DOM, "the whole tree below it" was destroyed as well, including the `Counter` and its state.

A component together with everything rendered inside it is called a **subtree**. React's docs: "when you render a different component in the same position, it resets the state of its entire subtree." And the rule that follows: "if you want to preserve the state between re-renders, the structure of your tree needs to 'match up' from one render to another."

```tree caption="What React compares at the first position of the div when the user clicks Fancy."
The first position inside `<div>`
- +Before the click [`<section>`] | Holds `Counter` with **`count` at 3**
- !After the click [`<div>`] | A **different type** from `<section>` | React destroys the whole subtree: the new `Counter` starts at **0**
```

### The note page: a tip that erases the note

Now the note page gets a tip. A developer wants the tip to sit together with the note, so the code puts both inside one `<div>` when the tip is on. `NoteBox.jsx` does not change:

```jsx title="src/App.jsx" bad="10,11,12,13,14,15,16,17"
import { useState } from 'react';
import NoteBox from './components/NoteBox.jsx';

export default function App() {
  const [isOpen, setIsOpen] = useState(true);
  const [friend, setFriend] = useState('Anna');
  const [showTip, setShowTip] = useState(false);

  let note = <NoteBox friend={friend} />;
  if (showTip) {
    note = (
      ~<div>~ {/* **WRONG:** the note's position now holds a div instead of a NoteBox */}
        <p>Tip: say one thing you like about them.</p>
        {note}
      </div>
    );
  }

  return (
    <main>
      <h1>Write a Note</h1>
      <button onClick={() => setFriend('Anna')}>Anna</button>
      <button onClick={() => setFriend('Ben')}>Ben</button>
      <button onClick={() => setShowTip(!showTip)}>
        {showTip ? 'Hide tip' : 'Show tip'}
      </button>
      <button onClick={() => setIsOpen(!isOpen)}>
        {isOpen ? 'Close note' : 'Write a note'}
      </button>
      {isOpen && note}
    </main>
  );
}
```

`note` is a `let` variable that holds a JSX tag and is filled before the `return`, as Lesson 10 showed. Keeping a tag in a variable does not keep its state, as `const counter` showed in Principle 1.

The user types a note to Anna:

```page width=text caption="The user has typed a note to Anna, with the tip off."
heading: Write a Note
line: [Anna] [Ben] [Show tip] [Close note]
form: title=Note to Anna
  textarea: | Happy birthday, Anna!
  button: Send to Anna
console: quiet
```

Then the user clicks `Show tip`:

```page width=text caption="After the user clicks Show tip, the tip appears and the note is gone."
heading: Write a Note
line: [Anna] [Ben] [Hide tip] [Close note]
line: Tip: say one thing you like about them.
form: title=Note to Anna
  textarea: | | bad
  button: Send to Anna
console: quiet
```

The tip appears, and the box under it is empty. The tip line never touches the note, yet the note is gone. Here is what happens, in order:
1. The user types `Happy birthday, Anna!`, and `NoteBox` holds it in `text`.
2. The user clicks `Show tip`, and `App` sets `showTip` to `true`.
3. React renders `App` again. The `if` wraps `note` in a `<div>`, so the position that held a `NoteBox` now holds a `<div>`.
4. A `<div>` is a different type from `NoteBox`, so React removes the `NoteBox` and destroys its `text`.
5. React builds the `<div>`, the tip line, and a new `NoteBox` inside the `<div>`, with `text` set to an empty string.
6. The tip shows, and the box under it is empty.

The new `NoteBox` is the same `NoteBox` function, but it now sits one level deeper, inside a new branch of the tree. And it happens again the other way. When the user types a new note and clicks `Hide tip`, the `<div>` goes, a `NoteBox` takes the position again, and the note is lost a second time.

### The fix: keep the tree the same shape

The tip has to appear without changing what sits at the note's position. Compare two ways to show the same tip above the same note:

```jsx title="Wrapping the note in a div, and placing the tip line above the note"
{isOpen && note} {/* note is a div with the tip and the NoteBox when showTip is true: the text is gone */}
{~showTip && <p>Tip: say one thing you like about them.</p>~} {/* The tip line keeps its own position */}
{isOpen && <NoteBox friend={friend} />} {/* NoteBox keeps its position: the text stays */}
```

Both show the tip above the note. **It may look the same, but it is NOT the same thing!** With the wrapper, the note's position holds a `<div>` instead of a `NoteBox`, and the text is gone. With the tip line above, the `NoteBox` keeps its position, and the text stays.

The tip line does not push `NoteBox` to a new position when it appears. The line `{showTip && <p>...</p>}` always keeps its own place among the children of `<main>`. When `showTip` is `false`, that place holds `false`, which shows nothing, as Lesson 10 taught. So `NoteBox` is always the child right after it, whether the tip shows or not. React's docs give the same fix for a hint above a form, so that "`Form` always renders in the same position."

Here is the fixed `App.jsx`. The `let note` and the `if` are gone:

```jsx title="src/App.jsx" startLine="9" good="20,21"
  return (
    <main>
      <h1>Write a Note</h1>
      <button onClick={() => setFriend('Anna')}>Anna</button>
      <button onClick={() => setFriend('Ben')}>Ben</button>
      <button onClick={() => setShowTip(!showTip)}>
        {showTip ? 'Hide tip' : 'Show tip'}
      </button>
      <button onClick={() => setIsOpen(!isOpen)}>
        {isOpen ? 'Close note' : 'Write a note'}
      </button>
      {~showTip &&~ <p>Tip: say one thing you like about them.</p>} {/* Its own position, even when it shows nothing */}
      {isOpen && <NoteBox friend={friend} />}
    </main>
  );
```

Now the user types a note and clicks `Show tip`:

```page width=text caption="With the tip line above the note, the tip appears and the note stays."
heading: Write a Note
line: [Anna] [Ben] [Hide tip] [Close note]
line: Tip: say one thing you like about them.
form: title=Note to Anna
  textarea: | Happy birthday, Anna! | good
  button: Send to Anna
console: quiet
```

If the `<div>` really matters to the page, keep it there in every render and put only the tip inside it with `showTip &&`. The rule is the same: what sits at the note's position must not change.

The same rule explains a mistake from Lesson 04: a component defined inside another component wipes out the text in its input box on every update. Every render of the outer component creates a new inner function. React's docs: "You're rendering a *different* component in the same position, so React resets all state below." A new function is a different type, just like a `<div>` in place of a `<section>`.

> [!PRINCIPLE]
> **Principle 3: A Different Type at the Position: React Resets Everything Inside**
>
> *When a different component type appears at a position, React destroys the old component and the state of everything inside it; to keep state, the tree must match from one render to the next.*
>
> Wrapping the note in a `<div>` only when the tip is on puts a `<div>` where a `NoteBox` was. React removes the `NoteBox` with its whole subtree, and the user's text is gone. A conditional line placed next to the note, such as `{showTip && <p>...</p>}`, keeps its own place, so `NoteBox` stays where it was.
>
> **DO THIS:**
> ```jsx
> <main>
>   {~showTip && <p>Tip: say one thing you like about them.</p>~} {/* The tip has its own position */}
>   {isOpen && <NoteBox friend={friend} />}
> </main>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <main>
>   {showTip ? ~<div><p>Tip</p><NoteBox friend={friend} /></div>~ : <NoteBox friend={friend} />} {/* **WRONG:** a div replaces NoteBox at its position, so the text is erased */}
> </main>
> ```

## 4. Principle 4: `key={friend}` Gives Ben an Empty Note

### The same two counters, with a `key`

Go back to the counter from the opening, where Ben got Anna's count. Add one attribute to each tag, a `key` with the person's name:

```jsx title="Two Counter tags without a key, and two Counter tags with a key"
{isAnna ? <Counter person="Anna" /> : <Counter person="Ben" />} {/* Ben shows 3 */}
{isAnna ? <Counter ~key="Anna"~ person="Anna" /> : <Counter ~key="Ben"~ person="Ben" />} {/* Ben shows 0 */}
```

The user clicks Anna's counter three times and clicks `Next`. With the `key`, Ben's counter shows 0.

When the page opens, both lines show `Anna: 0`, and the code differs by one attribute. **It may look the same, or work the same at first, but it is NOT the same thing!** Without a `key`, React finds a component by its order inside the parent. With a `key`, React uses the `key` as part of the position. React's docs: "Specifying a `key` tells React to use the `key` itself as part of the position, instead of their order within the parent." The `key` changed from `'Anna'` to `'Ben'`, so for React this is a different position, and Ben's counter is a new one.

Think of a street again. By default, React finds a house by its number on the street: the first house, the second house. A `key` puts a name on the door. React's docs: "A `key` lets you specify a named position instead of relying on order." When the name on the door changes, it is a different house, even at the same number. The docs call this giving each component "an explicit identity with `key`".

This is not a new kind of `key`. **Yes, it is the exact same thing!** It is the same `key` you wrote on each item inside `.map` in Lesson 18. React's docs: "Keys aren't just for lists!" In a list and outside one, the `key` tells React which component is which.

```tree caption="How React finds a Counter at the first position, without a key and with a key."
How React finds the `Counter` at the first position
- !Without a `key` [`<Counter person="Ben" />`] | React finds it by its **order** in the parent | Same order as Anna's, so it is **Anna's `Counter`**: Ben shows **3**
- +With a `key` [`<Counter key="Ben" person="Ben" />`] | React uses the **`key` as part of the position** | A new `key`, so it is a **new `Counter`**: Ben shows **0**
```

### The note page: an empty note for Ben

Now the note page. One change in `App.jsx` gives every friend a fresh note. `NoteBox.jsx` does not change:

```jsx title="src/App.jsx" startLine="21"
      {isOpen && <NoteBox ~key={friend}~ friend={friend} />} {/* A new friend means a new NoteBox */}
```

Lesson 18 showed that `key` is not a prop: React reads it, and the component never receives it. So `NoteBox` still needs `friend={friend}` as its own prop to show the name.

Compare the tag without and with the `key`:

::: row caption="After the user types a note to Anna and clicks Ben: without a key, Anna's text stays; with key={friend}, Ben gets an empty note."
::: col title="NoteBox without a key" tag="Anna's text under Ben's name" tone=bad

```page size=mini
heading: Write a Note
line: [Anna] [Ben] [Show tip] [Close note]
form: title=Note to Ben
  textarea: | Happy birthday, Anna! | bad
  button: Send to Ben
console: quiet
```
```jsx title="src/App.jsx" bad="1"
{isOpen && <NoteBox friend={friend} />}
```
React keeps the same `NoteBox`, so the box still holds the note for Anna.
:::
::: col title="NoteBox with key={friend}" tag="a fresh note for Ben" tone=good

```page size=mini
line: [Anna] [Ben] [Show tip] [Close note]
form: title=Note to Ben
  textarea: | | good
  button: Send to Ben
console: quiet
```

The `key` changed from `'Anna'` to `'Ben'`, so React builds a new `NoteBox` with an empty box that shows `Write to Ben`.
:::

**It may look the same, or work the same at first, but it is NOT the same thing!** Both versions show an empty note for Anna when the page opens, and they differ only after the click on `Ben`. React's docs describe what the new `key` does: the component "will be recreated from scratch, including any state in the tree below it. React will also re-create the DOM elements instead of reusing them." So the Elements panel gets a new `<h2>`, a new `<textarea>`, and a new button.

### Coming back to Anna: her note is gone too

Now the user goes back to Anna. Her note is empty as well. Here is what happens, in order:
1. The page opens with `friend` set to `'Anna'`. React renders `NoteBox` with the `key` `'Anna'`.
2. The user types `Happy birthday, Anna!`.
3. The user clicks `Ben`, and `App` sets `friend` to `'Ben'`.
4. React renders `App` again. The `NoteBox` now has the `key` `'Ben'`, which is a different position for React.
5. React removes Anna's `NoteBox` and destroys its `text`. It builds a new `NoteBox` for Ben, with an empty `text` and new DOM elements.
6. The user clicks `Anna`. The `key` is `'Anna'` again, but Anna's old `NoteBox` was destroyed in step 5.
7. React builds a new `NoteBox` for Anna, with an empty `text`.

The `key` does not store anything. It only tells React whether this is the same component as before. React's docs: "Toggling between them resets their state over and over." Principle 1 already showed why: a removed component's state is destroyed. To keep each friend's note and still give the box a fresh start, the notes must live somewhere that stays, such as in `App`, as the interview section below shows.

### Two ways to reset the note, and one wrong way

React's docs give two ways to reset a component at the same position. The first is the `key`. The second renders each friend's note at its own position:

```jsx title="One NoteBox with key={friend}, and two NoteBox tags at two positions"
{isOpen && <NoteBox ~key={friend}~ friend={friend} />} {/* One tag: a new NoteBox for each friend */}
{isOpen && ~friend === 'Anna' &&~ <NoteBox friend="Anna" />} {/* Anna's note at its own position */}
{isOpen && ~friend === 'Ben' &&~ <NoteBox friend="Ben" />} {/* Ben's note at the next position */}
```

On this page, both give the same result: every switch gives the user a fresh note. The second way is "convenient when you only have a few independent components rendered in the same place," as the docs say. With two friends it works. With twenty friends it needs twenty lines. The `key` is "more generic", and it needs one tag for any number of friends. On real pages, the `key` is usually an id, such as `key={contact.id}`. Here the two friends have different names, so `key={friend}` is enough.

A common wrong way is to clear the state from an Effect whenever the prop changes. The Effect runs after the page has already shown the old text, so the page renders twice, once with the stale note and once with the empty one. React's docs: "This is inefficient because `ProfilePage` and its children will first render with the stale value, and then render again." Every nested component with its own state would need the same Effect. Effects come in Lessons 32 and 34. The `key` does the job in one place: "This and any other state below will reset on key change automatically."

> [!PRINCIPLE]
> **Principle 4: A New `key`: React Creates a New Component**
>
> *To reset a component at the same position on purpose, give it a `key` that changes when it should become a different one; React uses the `key` as part of the position, so a new `key` makes a new component with new state and new DOM elements.*
>
> A note to Anna and a note to Ben are two different notes. Without a `key`, React sees one `NoteBox` at one position and keeps the text. With `key={friend}`, each friend's note has its own position, so the click on `Ben` gives the user an empty box. `key` works outside lists exactly as it does inside `.map`.
>
> **DO THIS:**
> ```jsx
> {isOpen && <NoteBox ~key={friend}~ friend={friend} />} {/* A new friend gets a new, empty NoteBox */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {isOpen && <NoteBox ~friend={friend}~ />} {/* **WRONG:** the same NoteBox for both friends, so Anna's note stays under Ben's name */}
> ```

## Putting All Four Principles Together

### The complete project

Here is the finished note page. `main.jsx` mounts `App` inside `<StrictMode>`:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
```

`App` holds whether the note is open, the chosen friend, and whether the tip shows:

```jsx title="src/App.jsx"
import { useState } from 'react';
import NoteBox from './components/NoteBox.jsx';

export default function App() {
  const [isOpen, setIsOpen] = useState(true);
  const [friend, setFriend] = useState('Anna');
  const [showTip, setShowTip] = useState(false);

  return (
    <main>
      <h1>Write a Note</h1>
      <button onClick={() => setFriend('Anna')}>Anna</button>
      <button onClick={() => setFriend('Ben')}>Ben</button>
      <button onClick={() => setShowTip(!showTip)}>
        {showTip ? 'Hide tip' : 'Show tip'}
      </button>
      <button onClick={() => setIsOpen(!isOpen)}>
        {isOpen ? 'Close note' : 'Write a note'}
      </button>
      {~showTip &&~ <p>Tip: say one thing you like about them.</p>} {/* Principle 3: its own position, so NoteBox never moves */}
      {~isOpen &&~ <NoteBox ~key={friend}~ friend={friend} />} {/* Principles 1 and 4: closing destroys the note; a new friend gets a new note */}
    </main>
  );
}
```

`NoteBox` holds the text of the note:

```jsx title="src/components/NoteBox.jsx"
import { useState } from 'react';

export default function NoteBox({ friend }) {
  const [~text~, setText] = useState(''); // Kept by React at the position of this NoteBox
  return (
    <section>
      <h2>Note to {friend}</h2>
      <textarea
        value={text}
        placeholder={'Write to ' + friend}
        onChange={e => setText(e.target.value)}
      />
      <button>Send to {friend}</button>
    </section>
  );
}
```

### How React calls the components in order

When the page opens, React calls `App` first. Inside `App`, it reaches the `NoteBox` tag and calls `NoteBox`. The double render of `<StrictMode>` in development changes none of the results in this lesson. React keeps `App`'s three state values at the root, and the `text` of the note at the position of `NoteBox`, under the `key` of the chosen friend:

```tree caption="The component tree of the note page, the order in which React calls each component, and where React keeps each piece of state."
`App` [1. Called first] | **Root component** | React keeps `isOpen`, `friend`, and `showTip` here
- +`<p>` tip line [`showTip && ...`] | Its **own position**, even when it shows nothing | Holds no state
- +`NoteBox` [2. Called second] | The position right after the tip line, named by **`key={friend}`** | React keeps `text` here, until the note is closed or the friend changes
```

| What the user does | What sits at the note's position | What happens to `text` |
| :--- | :--- | :--- |
| Closes the note and opens it again | Nothing, then a new `NoteBox` | Destroyed, and the new note starts empty |
| Picks Ben without a `key` on `NoteBox` | The same `NoteBox`, with a new `friend` prop | Kept, so Anna's note sits under Ben's name |
| Shows the tip when the tip wraps the note in a `<div>` | A `<div>` where a `NoteBox` was | Destroyed with the whole subtree |
| Shows the tip when the tip line sits above the note | The same `NoteBox` | Kept |
| Picks Ben with `key={friend}` | A `NoteBox` with a new `key` | Destroyed, and Ben gets an empty note |

## For the Interview

> **The Interview Question:** Why does state sometimes vanish, or survive, when you did not expect it?

### How to Answer Clearly in 30 Seconds

"React does not keep state inside the component function or inside the JSX tag. React holds it, and ties each piece of state to the component's position in the UI tree. On every render, React compares the new tree with the old one, position by position:
1. **Same component at the same position**: React keeps the state, even when the props change, and even when the code writes two tags in two branches of an `if`. That is why a note typed for Anna can stay on screen when the user switches to Ben.
2. **Removed, or a different type at that position**: React destroys the state of the component and of everything inside it. That is why a note vanishes when it is closed, or when a condition wraps it in a new `<div>`.
3. **On purpose**: to give a component a fresh start, I give it a `key` that changes when it should become a different one, such as `key={friend}`. The `key` becomes part of the position, so React creates a new component with new state and new DOM elements."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does a component defined inside another component lose everything the user typed on every update?"**
   Every time the outer component renders, JavaScript creates a new inner function. React compares the type at that position with the type from the last render and finds a different function, so it treats it as a different component. React's docs: "You're rendering a *different* component in the same position, so React resets all state below." It is the same rule as a `<div>` that takes the place of a `<section>`. React's docs end with the advice: "Don't nest component definitions, or you'll reset state by accident."
2. **"Is `key` only for lists, and must every `key` be unique in the whole app?"**
   No to both. `key` works on any component: `<NoteBox key={friend} />` resets the note whenever `friend` changes, just as a `key` inside `.map` tells React which row is which. And a `key` only has to differ among the children of the same parent. React's docs: "keys are not globally unique. They only specify the position *within the parent*." To put a `key` on a group of tags, write `<Fragment key={...}>`, because the short `<>...</>` form cannot take a `key`.
3. **"With `key={friend}`, how would you keep each friend's draft when the user switches back and forth?"**
   The `key` destroys the old note, so the drafts must live in a component that stays. React's docs name three ways. The most common is to lift the drafts up into `App`, as Lesson 24 taught, keeping one draft per friend and passing it down, while the `key` still gives each friend their own `NoteBox`. The second is to render every note and hide the ones not in use with CSS, which "can get very slow if the hidden trees are large." The third is to save the draft in `localStorage`, so it survives even when the user closes the page. React also has `<Activity mode="hidden">`, which hides a part of the page and keeps its state, covered in Lesson 73.

```tree caption="Interview summary: when React keeps a component's state and when it destroys it."
What React does with the state at a position
- +Keeps the state | **Same component** at the **same position** | A new prop or two tags in two branches change **nothing**
- !Destroys the state | The component is **removed**, or a **different type** takes the position | The state of the **whole subtree** is gone
- +Resets on purpose | A **new `key`** on the tag, such as `key={friend}` | React creates a **new component** with new state and new DOM elements
```
