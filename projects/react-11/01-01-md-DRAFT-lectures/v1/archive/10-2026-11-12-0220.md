## Why a Component Must Choose What Markup to Return

### Not every card on a real news page shows the same pieces

Look at any real city news page. The story cards in the feed share the same outer card design, yet no two cards show the exact same pieces inside. An unfinished draft story should not appear on the public feed at all. A subscriber-only story hides its summary paragraph and shows a sign-in notice instead. A breaking news story wears a `Live` badge at the top, while a regular story leaves that badge off. And a popular story with four reader comments shows a comment counter at the bottom, while a brand-new story with zero comments hides that line.

In plain JavaScript without React, you would put every possible badge, notice, and counter into the HTML ahead of time. Then you would hunt through the page and toggle CSS classes to hide the pieces you do not want.

In React, you never hide and show DOM nodes by hand. Instead, your component checks the props it receives and returns only the markup that belongs on the screen for that data. Having a component return different markup depending on a condition is called **conditional rendering**.

```tree caption="Two ways to show or hide parts of a card: hiding DOM nodes by hand in plain JavaScript vs. conditional rendering in React."
How to show or hide parts of a news card
- !Hide DOM nodes by hand in plain JavaScript | Put every badge, notice, and counter into the HTML ahead of time | Hunt for DOM nodes and toggle hidden styles by hand
- +Conditional rendering in React | +**DO** let the component check its props and return only the markup that belongs on screen | Unwanted pieces are **never created** in the browser DOM
```

### Three plain JavaScript tools control what a component returns

React does not invent special HTML attributes for conditions. Because a React component is a JavaScript function, you choose what markup to return with three standard tools from plain JavaScript:
- **An `if` statement before `return`** decides whether the whole component returns its markup, returns a different markup tree, or returns `null` so nothing appears on the page at all.
- **The ternary operator, written `?` and `:`**, sits inside JSX curly braces `{ }` and switches between two pieces of markup in the middle of a tag.
- **The logical AND operator, written `&&`**, sits inside JSX curly braces `{ }` and shows one piece of markup only when a boolean condition is `true`.

First, look at how an `if` statement at the top of our card function can stop an unpublished draft before any markup is returned:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, isPublished = true }) {
  ~if (!isPublished) { return null; }~ // 1. Outside JSX: stops early and returns null when unpublished

  return (
    <article className="card">
      <h3>{title}</h3>
      <p>{summary}</p>
    </article>
  );
}
```

Next, look at how `? :` and `&&` sit inside curly braces `{ }` to switch a paragraph or include a badge inside the card:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import { LiveBadge } from './Badges.jsx';

export default function ArticleCard({ title, summary, isSubscriberOnly = false, isBreaking = false }) {
  return (
    <article className="card">
      ~{isBreaking && <LiveBadge />}~ {/* 2. Inside JSX {}: shows LiveBadge only when isBreaking is true */}
      <h3>{title}</h3>
      ~{isSubscriberOnly ? <p>Subscribers only: Sign in to read this story.</p> : <p>{summary}</p>}~ {/* 3. Inside JSX {}: switches between two paragraphs */}
    </article>
  );
}
```

Here is how those three JavaScript tools divide the work across our component:

```tree dir=right caption="The three plain JavaScript tools for conditional rendering and where each one lives in a component."
Three JavaScript tools for conditional rendering
- +1. `if` statement and `return null` [Outside JSX, before `return`] | Guards the whole component or prepares a `let` variable before returning
- +2. Ternary operator `? :` [Inside JSX `{ }` curly braces] | Switches between **two** pieces of markup in one spot
- +3. Logical AND operator `&&` [Inside JSX `{ }` curly braces] | Includes **one** piece of markup when a boolean condition is `true`
```

### Statements outside curly braces vs. expressions inside curly braces, and what React renders

Recall from earlier lessons that curly braces `{ }` inside JSX open a window for JavaScript. However, you cannot put every kind of JavaScript inside `{ }`. JavaScript divides its code into two groups:
- **A statement** is an instruction that performs an action, such as an `if` / `else` block or a `let` variable declaration. A statement does not evaluate to a single value, so it can only live **outside** JSX, above the `return` line.
- **An expression** is a piece of code that evaluates to a single value, such as `isSubscriberOnly ? <p>Sign in</p> : <p>{summary}</p>` or `isBreaking && <LiveBadge />`. Because JSX curly braces `{ }` must hand a value to React, only expressions can sit **inside** `{ }`.

When an expression inside `{ }` finishes running, it hands its resulting value to React. React divides those values into two groups when building the browser DOM:
- **Values that render visible text**: React turns **strings**, such as `"New Park Opens Today"`, and **numbers**, such as `4` or `0`, into visible text nodes on the page.
- **Values that render nothing at all**: React treats **`null`**, **`undefined`**, **`false`**, **`true`**, and an empty string **`""`** as empty holes in the markup and creates **zero DOM nodes** for them.

```tree caption="What React puts into the browser DOM for each kind of JavaScript value returned or placed inside JSX curly braces."
JavaScript values handed to React in JSX
- +Visible text values [Strings `"Live"` and numbers `4` or `0`] | !Numbers include **`0`** | React creates a **visible text node** in the browser DOM
- +Empty hole values [`null` `undefined` `false` `true` `""`] | Treated as **intentional empty spots** | React creates **0 DOM nodes** in the browser DOM
```

Recall two prop rules that work hand in hand with conditional rendering:
- In `ArticleList.jsx`, passing a boolean or a number requires curly braces, such as `isPublished={false}` or `commentCount={4}`, while quotation marks always pass a text string.
- In `ArticleCard.jsx`, we can give any optional prop a default value with `=` in the destructured parameter list, such as `isPublished = true` or `readTime = 3`, so the parent tag only needs to pass props that differ from the default.

### Four Principles of Conditional Rendering

**PRINCIPLES:** Every conditional rendering bug comes from mixing up where JavaScript statements and expressions belong, or forgetting what value JavaScript actually hands to React. Walking from the top of `ArticleCard` down into its JSX gives us four rules:
1. **Principle 1: Returning Early with `if` and `return null`**: An `if` statement before `return` can stop the function early and `return null` when a component should render nothing at all. Forgetting that guard lets an unpublished draft card appear right on the public page.
2. **Principle 2: Switching Between Two Branches Inside `{ }` with `? :`**: JSX curly braces `{ }` only accept expressions that produce a value. Writing `{if ...}` inside `{ }` stops the build with a syntax error; use the ternary operator `condition ? <BranchA /> : <BranchB />` inside `{ }`, or set a `let` variable in an `if` block before `return`.
3. **Principle 3: Showing One Element with `&&` and a Real Boolean**: Inside `{ }`, `isBreaking && <LiveBadge />` shows the badge when `isBreaking` is `true` and returns `false` when it is `false`, which React renders as nothing. However, passing `isBreaking="false"` in quotes passes a non-empty string that is truthy in JavaScript, so the `Live` badge appears anyway!
4. **Principle 4: Avoiding the `0` Trap on the Left Side of `&&`**: Never put a number directly on the left side of `&&`, such as `commentCount && <p>...</p>`. When `commentCount` is `0`, `0 && <p>...</p>` returns the number `0`, and React prints a literal `0` on the page! Always compare with `commentCount > 0 && <p>...</p>` so the left side is a real boolean.

Here is the complete overview of all four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Early Return: Use `if` Before `return` and `return null` to Hide a Component** | **Draft Leak & DOM Interview Question:** Forgetting an early `if` guard renders unpublished cards on screen; interviewers ask what `return null` puts into the browser DOM. | Check `if` conditions before the component's `return` statement, and `return null` when the component should create zero DOM nodes. |
| **Principle 2** | **Ternary `? :`: Switch Between Two JSX Branches Inside `{ }`** | **Build Crash & Readability Question:** Writing `{if ...}` inside JSX curly braces crashes the build with `Unexpected token`; interviewers ask why `{ }` rejects `if` and when to use a `let` variable instead. | Use `condition ? <BranchA /> : <BranchB />` inside JSX `{ }` for two-way switching, or assign JSX to a `let` variable in an `if` block before `return`. |
| **Principle 3** | **Logical `&&`: Include One JSX Element with a Boolean Condition** | **Quoted String Bug & Falsy Evaluation:** Passing `isBreaking="false"` in quotes makes `&&` render the badge because `"false"` is a truthy string; interviewers ask why `false && <Badge />` leaves the DOM empty. | Use `{condition && <Element />}` with a real boolean prop in curly braces so `false` short-circuits to `false` and renders zero DOM nodes. |
| **Principle 4** | **The Zero Trap: Write `count > 0 && ...` Instead of `count && ...`** | **#1 React Conditional Rendering Trap:** Writing `{commentCount && <p>...</p>}` prints a stray `"0"` in the DOM when `commentCount` is `0` with zero Console warnings. | Compare numbers explicitly with `commentCount > 0 && <p>...</p>` so a zero count evaluates to `false` instead of the number `0`. |

## 1. Principle 1: Return Early with `if` and Return `null` When a Component Should Render Nothing

### Hiding a component in React means returning `null` before `return`, not hiding DOM nodes with CSS

When a card should not appear on the page at all, beginners often think of two habits from outside React:
- **In daily coding**: A developer coming from plain HTML leaves the card in the DOM and tries to hide it with CSS, or forgets to check `isPublished` at the top of `ArticleCard` so an unfinished draft story leaks onto the public page.
- **In an interview**: Explain that a React component is a normal JavaScript function. When an `if` statement at the top of the function runs `return null`, the function stops before reaching the JSX markup, and React creates **zero DOM nodes** for that component.

```tree caption="Keeping a hidden card in the DOM vs. returning null early from the component function."
How to hide an unpublished card in React
- !Keep the `<article>` node in the DOM and hide it with CSS | The unpublished draft text **still sits inside the browser's Elements panel**
- +Check `if` at the top of the component and `return null` | +**DO** stop the function before the JSX `return` | React puts **0 DOM nodes** for the draft card into the browser DOM
```

### What happens when the list renders an unpublished draft and the card forgets the `if` check

On our city news page, the article list has two finished stories and a third story that is still an unpublished draft. In our list file, we mark that third card as unpublished:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList({ category }) {
  return (
    <section>
      <h2>Section: {category}</h2>
      <ArticleCard
        title="New Park Opens Today"
        summary="The park on Main Street opens at noon."
        readTime={5}
      />
      <ArticleCard
        title="Library Extends Hours"
        summary="The central library stays open until nine."
      />
      <ArticleCard
        title="Mayor Budget Draft"
        summary="Unfinished notes for next week."
        ~isPublished={false}~ // Marks the 3rd card as an unpublished draft
      />
    </section>
  );
}
```

Now look at what happens when our card file unpacks the story props and returns the card markup right away, without checking whether the story is published:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ~ArticleCard~({ title, summary, readTime = 3 }) { // **WRONG:** never checks isPublished before returning the card!
  const totalTime = readTime + 2;

  return (
    <article className="card">
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

When you **leave out the `if` check at the top of the card function**, the unfinished `'Mayor Budget Draft'` card appears right on the public page with zero warnings in the Console!

Look at what happened in order:
1. The list file rendered three card tags, passing `isPublished={false}` on the third tag.
2. React called `ArticleCard` once for each of the three tags.
3. Because the third call never checked `isPublished` or stopped early, it ran the `return` line at the bottom and handed the draft card's `<article>` markup to React.

### Guarding the component with `if` and `return null` before the main `return`

To keep unpublished drafts off the page, we make two small additions at the top of our card file. First, we give the published prop a default value of `true` so normal stories stay visible when the list leaves that prop out. Second, right before the main `return`, we check whether the story is unpublished and return `null`:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime = 3, ~isPublished = true~ }) { // 1. Defaults to true when omitted
  ~if (!isPublished) {~ // 2. Stops early and returns null when isPublished is false
    ~return null;~
  ~}~

  const totalTime = readTime + 2;

  return (
    <article className="card">
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

Save the file, and look at the browser's **Elements panel** below. In `ArticleList.jsx`, there are still three `<ArticleCard />` tags inside `<section>`. Yet in the Elements panel, `<section>` holds only **two** `<article class="card">` elements, and there is no empty wrapper or comment where the third card stood!

Why did the third card leave zero trace in the DOM? Follow what JavaScript and React do across the three calls:
1. **On the first and second cards**: The list file omits `isPublished`, so the default value `isPublished = true` takes over. Because `!isPublished` is `false`, JavaScript skips the `if` block and returns the `<article className="card">` element.
2. **On the third card**: The list file passes `isPublished={false}`. Now `!isPublished` is `true`, so the `if` block runs `return null;` right away and stops the function before the JSX below it ever runs.
3. **When React builds the DOM**: React receives `null` from that third call, treats `null` as an intentional empty spot, and inserts **zero DOM nodes** into `<section>`.

In an interview, you may also be asked two follow-up details about early returns:
- **Where should the condition live?** Putting an early `if` guard at the top of `ArticleCard` is a clean safety check so the card can never render an unpublished draft by mistake. In other cases, developers check the condition inside the parent `ArticleList` before rendering `<ArticleCard />` so anyone reading the parent file can see at a glance that a tag is conditional.
- **Does returning early create a different kind of React element than branching inline?** No. Remember that JSX tags compile to lightweight plain objects that describe what should appear on screen. Whether a component returns one JSX tree from an early `if` statement or picks between two JSX trees at the bottom of the function, React receives the exact same element description.

## 2. Principle 2: Switch Between Two JSX Branches Inside `{ }` with the Ternary Operator `? :`

### JSX curly braces accept only value expressions such as `? :`, never statements such as `if`

In Principle 1, we hid the entire card by putting an `if` statement above `return`. Now what if we want to keep the card's outer `<article className="card">` box, its `<h3>` title, and its reading-time footer, and swap **only the middle paragraph** inside the card?

- **In daily coding**: Beginners know that curly braces `{ }` run JavaScript inside JSX, so they try to write an `if / else` block right inside `{ }`. The moment they save the file, Vite stops the build with a syntax error! Or, to avoid that error, they copy and paste the entire `<article className="card">` block twice inside a top-level `if / else`, which means every future design change has to be edited in two places.
- **In an interview**: State why `{ }` rejects `if`: JSX curly braces sit inside a JavaScript function call where a **value expression** is required. An `if / else` block is a statement, not a value. To switch between two pieces of JSX inline inside `{ }`, use the **ternary conditional operator**, written `condition ? <BranchA /> : <BranchB />`, or assign JSX to a `let` variable before `return` when the branches get long.

### How the ternary expression `? :` differs from an `if / else` statement in plain JavaScript

In plain JavaScript, an `if / else` statement controls which block of lines runs, whereas the **ternary operator** `? :` is a compact expression that evaluates directly to a single value. It has three parts:
1. **Before the question mark `?`**: the condition to test.
2. **Between `?` and the colon `:`**: the value returned when the condition is `true`.
3. **After the colon `:`**: the value returned when the condition is `false`.

Look at how `? :` produces a value directly where an `if` statement cannot sit:

```js title="Plain JavaScript"
const isSubscriberOnly = true;

const message = ~isSubscriberOnly ? 'Subscribers only' : 'Open story'~; // Expression: evaluates to 'Subscribers only'
console.log(message);
```

Compare where `if / else` and `? :` can live inside a React component:

```tree caption="Why an if / else statement must stay outside JSX curly braces while a ? : ternary expression fits inside { }."
Two ways to branch in JavaScript
- !`if / else` statement [Outside JSX, before `return`] | ~Do **NOT** put `if / else` inside JSX `{ }` | Performs an action rather than evaluating to a value | Writing `{if ...}` inside JSX **crashes the build**
- +Ternary operator `condition ? a : b` [Inside JSX `{ }` curly braces] | +**DO** use `? :` inside `{ }` to switch between two JSX branches | Evaluates to **one winning value** and hands it to React
```

### What happens when you write an `if` statement inside JSX curly braces

On our city news page, the library story is for subscribers only. First, in our list file, we mark that second card as subscriber-only:

```jsx title="src/components/ArticleList.jsx" startLine="12"
      <ArticleCard
        title="Library Extends Hours"
        summary="The central library stays open until nine."
        ~isSubscriberOnly={true}~ // Marks the 2nd story as subscriber-only
      />
```

Now look at what happens when a developer opens curly braces `{ }` inside the card markup and writes an `if / else` statement inside them:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime = 3, isPublished = true, isSubscriberOnly = false }) {
  if (!isPublished) {
    return null;
  }
  const totalTime = readTime + 2;

  return (
    <article className="card">
      <h3>{title}</h3>
      ~{if (isSubscriberOnly) { <p>Subscribers only: Sign in to read this story.</p> } else { <p>{summary}</p> }}~ {/* **WRONG:** if statement inside JSX {} stops the build! */}
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

When you **write an `if` statement inside JSX curly braces**, Vite immediately stops the build and covers the browser with its error overlay:


Why did the build stop at `{if` on line 10? Remember that the build rewrites `<article>` and its children into a `_jsxDEV` function call whose `children` sit inside an array. Every slot inside that `children` array must be a JavaScript expression that produces a value. When the parser sees the statement keyword `if` inside an expression slot, it halts with `Unexpected token`.

### Switching between the two paragraphs with `? :` inside `{ }`

Now let us replace that `if / else` block inside `{ }` with the ternary operator `? :`. We keep the shared `<article className="card">`, the `<h3>{title}</h3>` heading, and the reading-time line in one place, and use `? :` to switch only the middle paragraph:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime = 3, isPublished = true, ~isSubscriberOnly = false~ }) { // 1. Defaults to false for open stories
  if (!isPublished) {
    return null;
  }
  const totalTime = readTime + 2;

  return (
    <article className="card">
      <h3>{title}</h3>
      {isSubscriberOnly
        ~? <p>Subscribers only: Sign in to read this story.</p>~ // 2. Returned when isSubscriberOnly is true
        ~: <p>{summary}</p>~} {/* 3. Returned when isSubscriberOnly is false */}
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

Look closely at the curly braces in `ArticleCard.jsx` above. There are **two** `<p>` tags inside those curly braces, yet when you inspect the page in the browser, each card has only **one** middle `<p>` tag!

Follow what JavaScript hands to React for each card:
1. **On the park story**: The list file omits `isSubscriberOnly`, so it defaults to `false`. JavaScript evaluates the condition before `?` as `false` and hands React only the expression after `:`, which is `<p>{summary}</p>`.
2. **On the library story**: The list file passes `isSubscriberOnly={true}`. JavaScript evaluates the condition before `?` as `true` and hands React only the expression between `?` and `:`, which is `<p>Subscribers only: Sign in to read this story.</p>`.
3. **In the browser DOM**: Each card receives only its winning `<p>` element, while the outer `<article className="card">` shell is written once instead of being duplicated.

### When the branches grow longer: assign JSX to a `let` variable before `return`

The ternary operator `? :` is ideal when switching between two short pieces of markup. What if each branch spans several lines, or you need `else if` for three different cases, and cramming all of that inside `{ }` makes the JSX hard to read?

You still do not need to duplicate the outer card wrapper. Because JSX elements are normal JavaScript values, you can store the default paragraph in a `let` variable before `return`, reassign that variable inside a normal `if` block, and place the variable inside curly braces in the card markup:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime = 3, isPublished = true, isSubscriberOnly = false }) {
  if (!isPublished) {
    return null;
  }
  const totalTime = readTime + 2;

  ~let bodyContent = <p>{summary}</p>;~ // 1. Start with the normal summary paragraph
  if (isSubscriberOnly) {
    ~bodyContent = <p>Subscribers only: Sign in to read this story.</p>;~ // 2. Swap in the subscriber notice when true
  }

  return (
    <article className="card">
      <h3>{title}</h3>
      ~{bodyContent}~ {/* 3. Embed the chosen JSX variable inside curly braces */}
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

That gives you the best of both worlds: the `if` statement stays above `return` where statements belong, the outer card wrapper is written only once, and `{bodyContent}` inside the JSX is a single, readable variable name.

> [!PRINCIPLE]
> **Principle 2: Ternary `? :`: Switch Between Two JSX Branches Inside `{ }`**
>
> *Use the ternary conditional operator `condition ? <BranchA /> : <BranchB />` inside JSX curly braces to switch between two pieces of markup, or use an `if` statement with a `let` variable before `return` when the branches get long.*
>
> It is tempting to open `{ }` inside JSX and write an `if / else` block, only to watch the build stop right away! You see, JSX curly braces sit inside a JavaScript function call where a value is required, and an `if` statement does not evaluate to a value. The ternary operator `? :` is an expression that picks the winning branch and hands that single React element to React.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> <article className="card">
>   <h3>{title}</h3>
>   ~{isSubscriberOnly ? <p>Subscribers only: Sign in to read this story.</p> : <p>{summary}</p>}~ {/* Evaluates to the chosen <p> */}
> </article>
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> <article className="card">
>   <h3>{title}</h3>
>   ~{if (isSubscriberOnly) { <p>Subscribers only</p> } else { <p>{summary}</p> }}~ {/* **WRONG:** if statement inside {} crashes the build! */}
> </article>
> ```

## 3. Principle 3: Show or Hide a Single Element with Logical AND `&&` and a Real Boolean

### JavaScript's `&&` returns its left value when falsy and its right value when truthy, and React renders `false` as nothing

In Principle 2, we had two branches: a subscriber notice or a story summary. Now what if there is **only one branch**? When a story is breaking news, we want to show `<LiveBadge />` at the top of the card; when it is not breaking news, we want to show nothing at all in that spot.

You could write `{isBreaking ? <LiveBadge /> : null}`, and that works. In everyday React code, however, developers write `{isBreaking && <LiveBadge />}` instead.

- **In daily coding**: A beginner often thinks `&&` inside JSX is a special React rule, and passes `isBreaking="false"` in quotation marks expecting the `Live` badge to disappear. Instead, the `Live` badge stays right on the card with zero Console warnings!
- **In an interview**: Explain the two steps that make `{isBreaking && <LiveBadge />}` work:
  1. In JavaScript, `&&` returns its **left-hand value** if the left side is falsy, and returns its **right-hand value** if the left side is truthy.
  2. When `isBreaking` is the boolean `false`, `false && <LiveBadge />` returns `false`, and React treats `false` as an empty hole that creates **zero DOM nodes**. When `isBreaking` is the quoted string `"false"`, any non-empty string is truthy in JavaScript, so `"false" && <LiveBadge />` returns and renders `<LiveBadge />`!

### How `&&` short-circuits in plain JavaScript

In plain JavaScript, the logical AND operator `&&` reads from left to right. This behavior is called **short-circuit evaluation**:
- If the **left side is falsy**, `&&` stops right there and returns that **exact left-hand value** without even looking at the right side.
- If the **left side is truthy**, `&&` keeps going and returns the **right-hand value**.

Look at what `&&` returns for a boolean `false`, a boolean `true`, and a non-empty string `'false'`:

```js title="Plain JavaScript"
console.log(~false && 'Live'~); // Left side is falsy -> stops and returns false
console.log(~true && 'Live'~); // Left side is truthy -> returns the right side: 'Live'
console.log(~'false' && 'Live'~); // Non-empty string 'false' is TRUTHY -> returns 'Live'!
```

Look carefully at the third line above. In JavaScript, only an empty string `""` is falsy. Any string with characters inside it, including the five-letter word `'false'`, is **truthy**!

```tree caption="What JavaScript's && operator returns and what React puts in the DOM for boolean false, boolean true, and quoted string 'false'."
How `isBreaking && <LiveBadge />` evaluates in JSX
- +Boolean `false` [`isBreaking={false}`] | Left side is **falsy** | `&&` returns **`false`**, and React creates **0 DOM nodes**
- +Boolean `true` [`isBreaking={true}`] | Left side is **truthy** | `&&` returns **`<LiveBadge />`**, and React renders `<span class="badge">Live</span>`
- !Quoted string `"false"` [`isBreaking="false"`] | ~Do **NOT** wrap boolean props in quotes | Non-empty string `'false'` is **truthy**, so `&&` returns **`<LiveBadge />`** and renders `Live` by mistake!
```

### Including `LiveBadge` and `NewBadge` with `&&` inside `ArticleCard.jsx`

Let us add conditional badges to our news cards. First, remember the two badge components exported by our badge file:

```jsx title="src/components/Badges.jsx" startLine="1"
export function ~LiveBadge~() { // Shown when isBreaking is true
  return <span className="badge">Live</span>;
}

export function ~NewBadge~() { // Shown when isNew is true
  return <span className="badge">New</span>;
}
```

Next, in our card file, we import both badges, default both badge props to `false` in the parameter list, and use `&&` at the top of the card markup so each badge appears only when its prop is `true`:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleCard({
  title,
  summary,
  readTime = 3,
  isPublished = true,
  isSubscriberOnly = false,
  ~isBreaking = false,~ // 1. Both badge props default to the boolean false
  ~isNew = false,~
}) {

    return null;
  }
  const totalTime = readTime + 2;

  return (
    <article className="card">
      ~{isBreaking && <LiveBadge />}~ {/* 2. Evaluates to <LiveBadge /> when true, or false when false */}
      ~{isNew && <NewBadge />}~ {/* 3. Evaluates to <NewBadge /> when true, or false when false */}
      <h3>{title}</h3>
      {isSubscriberOnly
        ? <p>Subscribers only: Sign in to read this story.</p>
        : <p>{summary}</p>}
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

Pause and check what happens when `isBreaking` is `false`. We just saw that `false && <LiveBadge />` evaluates to the boolean `false`. Why doesn't the word `"false"` appear at the top of the card in the browser?

Because of how React handles boolean values inside JSX:
1. When `isBreaking` is `false`, JavaScript stops at the left side of `&&` and hands the boolean `false` to React.
2. React ignores boolean values `false` and `true` inside JSX children, just like `null` and `undefined`, and creates **zero DOM nodes** for them.
3. When `isNew` is `true`, JavaScript moves to the right side of `&&` and hands the `<NewBadge />` element to React, which puts `<span class="badge">New</span>` into the DOM.

### What happens when you pass `"false"` in quotation marks on a card tag

Now suppose the developer edits the list file. The park story is breaking news and brand-new, while the library story is brand-new **but not breaking news**. Look at what happens when the developer passes `"false"` in quotation marks for the breaking-news prop on the library card:

When you **pass `"false"` in quotation marks to a prop used with `&&`**, the `Live` badge still appears on the library story with zero Console errors!

Look at what happened in order:
1. In JSX, quotation marks always pass a **string**, so `isBreaking` arrived inside `ArticleCard` as the five-letter string `'false'`.
2. Inside `{isBreaking && <LiveBadge />}`, JavaScript checked `'false' && <LiveBadge />`.
3. Because any non-empty string is truthy, `&&` returned `<LiveBadge />`, and React drew `<span class="badge">Live</span>` on the library card.

> **Principle 3: Logical `&&`: Include One JSX Element with a Boolean Condition**
>
> *Use `{condition && <Element />}` inside JSX curly braces to render an element when a boolean condition is `true` and render nothing when it is `false`. Always pass boolean props in curly braces, never in quotes.*
>
> When you only want to show or hide a single badge, `&&` feels effortless, until someone passes `"false"` in quotation marks and the badge refuses to disappear! You see, JavaScript's `&&` stops at the left side when it is falsy and hands that value to React, and React renders nothing for the boolean `false`. Quotation marks, however, pass the five-letter text string `'false'`. Because any non-empty string is truthy in JavaScript, `&&` marches right past `'false'` and renders the badge on screen!

## 4. Principle 4: Compare Numbers with `> 0` Before `&&` So Zero Never Prints on the Page

### In JavaScript, `0 && markup` returns the number `0`, and React renders numbers as visible text

In Principle 3, `isBreaking` was a boolean, so `false && <LiveBadge />` returned `false` and React rendered nothing. What happens when the value on the left side of `&&` is a **number**, such as a comment counter `commentCount` or an array's `.length`?

- **In daily coding**: In a normal `if` statement, `0` is falsy, so developers assume `{commentCount && <p>{commentCount} comments</p>}` will also render nothing when `commentCount` is `0`. Instead, a stray number **`0`** appears right on the card in the browser with zero Console warnings!
- **In an interview**: This is the most famous conditional rendering question in React interviews. Explain why `0` prints on screen: `&&` does **not** convert its left side to `false`. When the left side is falsy, `&&` returns that exact left-hand value. So `0 && <p>...</p>` returns the number `0`. And because `0` is a valid number to display in a user interface, React renders `0` as a text node in the DOM!

### What `&&` returns when a number sits on the left side

Look at what plain JavaScript returns when we put `4`, `0`, and the comparison `0 > 0` on the left side of `&&`:

```js title="Plain JavaScript"
console.log(~4 && '4 comments'~); // 4 is truthy -> returns '4 comments'
console.log(~0 && '0 comments'~); // 0 is falsy -> stops at 0 and returns the number 0!
console.log(~0 > 0 && '0 comments'~); // 0 > 0 is false -> stops at false and returns false
```

Compare the second and third lines:
- On the second line, `0` is falsy, so `&&` stops on the left side and gives back the number **`0`** itself, not `false`!
- On the third line, `0 > 0` runs first and produces the boolean **`false`**. Then `false && '0 comments'` stops on the left side and gives back **`false`**.

Why doesn't React ignore the number `0` the way it ignores `false`, `null`, and `undefined`? Think of a shopping cart that renders `<p>Items in cart: {count}</p>` or a scoreboard that renders `<td>{score}</td>`. When the cart is empty or the score is zero, the user **must** see `0` on the screen! If React ignored `0`, every zero price, zero score, and zero count across your app would turn blank.

Here is how React handles all six falsy values in JavaScript when one of them lands on the left side of `&&` inside JSX:

```tree caption="What JavaScript's six falsy values return on the left side of && and what React puts into the browser DOM for each one."
All six JavaScript falsy values on the left side of `&&` in JSX
- +`false`, `null`, `undefined`, and `""` [`false && <p>...</p>`] | `&&` returns `false`, `null`, `undefined`, or `""` | React creates **0 DOM nodes**
- !The number `0` [`0 && <p>...</p>`] | ~Do **NOT** put a raw number on the left of `&&` | `&&` returns the number **`0`**, and React prints **`"0"`** in the DOM with **0 Console warnings**!
- !`NaN` from a broken math calculation [`NaN && <p>...</p>`] | `&&` returns **`NaN`** | React prints **`"NaN"`** in the DOM and logs a red Console error!
```

### What happens when `commentCount` sits directly on the left side of `&&`

Let us add a comment counter at the bottom of our article cards. When a story has comments, we want to show the comment count line. When a story has `0` comments, we want that line to disappear completely.

First, in our list file, we pass four comments on the park story and zero comments on the library story:

```jsx title="src/components/ArticleList.jsx" startLine="6"

        title="New Park Opens Today"
        summary="The park on Main Street opens at noon."
        readTime={5}
        isBreaking={true}
        isNew={true}
        ~commentCount={4}~ // Park story has 4 comments
      />
      <ArticleCard
        title="Library Extends Hours"
        summary="The central library stays open until nine."
        isSubscriberOnly={true}
        isBreaking={false}
        isNew={true}
        ~commentCount={0}~ // Library story has 0 comments
      />
```

Now look at what happens when a developer puts the comment count variable directly on the left side of `&&` at the bottom of the card:

```jsx title="src/components/ArticleCard.jsx" startLine="22"
      <p>{totalTime} min total · {readTime} min read</p>
      ~{commentCount && <p>{commentCount} comments</p>}~ {/* **WRONG:** when commentCount is 0, 0 && <p>...</p> returns 0 and prints "0" on the card! */}

```

When you **put `commentCount` directly on the left side of `&&` and `commentCount` is `0`**, a lone character **`0`** prints at the bottom of the library card with zero Console warnings!

Look closely at our card code above. Nowhere in our JSX did we write a bare `0` by itself. Where did that `"0"` at the bottom of the library card come from?

Follow what JavaScript and React did step by step:
1. On the park card, `commentCount` is `4`. Because `4` is truthy, `4 && <p>4 comments</p>` returns `<p>4 comments</p>`, which looks fine.
2. On the library card, `commentCount` is `0`. Because `0` is falsy, `0 && <p>0 comments</p>` stops at the left side and returns the number **`0`**.
3. React receives the number `0` as the last child of `<article className="card">` and inserts a text node `"0"` right after `<p>5 min total · 3 min read</p>`.

### Comparing `commentCount > 0` turns the left side into a real boolean

To fix the bug, we compare the number with `> 0` on the left side of `&&`:


Now trace the library card again when `commentCount` is `0`:
1. JavaScript evaluates `0 > 0` first, which produces the boolean **`false`**.
2. Next, `false && <p>0 comments</p>` stops at `false` and hands **`false`** to React.
3. React ignores `false` and puts **zero DOM nodes** after the reading-time paragraph.

>
> *Never put a number directly on the left side of `&&` in JSX. Always write an explicit comparison such as `commentCount > 0 && <p>{commentCount} comments</p>` so the left side evaluates to `true` or `false`.*

> This is a classic trap. If you write `{commentCount && <p>{commentCount} comments</p>}`, the left side cannot be `0`, or else the number zero will appear right on your screen! You see, JavaScript stops at `0`, and instead of returning `false`, it hands the number `0` to React. And React happily renders `0` on the screen, because for React `0` is a valid number to show! Writing `commentCount > 0` turns the left side into `false` when the count is zero, so React renders nothing at all.

## For the Interview

> **The Interview Question:** How do you show, hide, or switch JSX based on a condition?

### How to Answer Clearly in 30 Seconds

"React handles conditional rendering with standard JavaScript rather than special template attributes:
1. **Early return with `if` and `return null` outside JSX**: Before the component's `return` statement, an `if` statement can return a different JSX tree early, or `return null` when the component should render nothing at all. When a component returns `null`, React creates zero DOM nodes for it.
2. **The ternary operator `condition ? <A /> : <B />` inside `{ }`**: JSX curly braces only accept JavaScript expressions that evaluate to a value, so writing `{if ...}` inside `{ }` fails at build time with a syntax error. To switch between two pieces of JSX inline, we use `? :`, or we assign JSX to a `let` variable inside an `if` block before `return` when the branches get long.
3. **The logical AND operator `condition && <Element />` inside `{ }`**: To show one piece of JSX when a boolean condition is `true` and nothing when it is `false`, we use `&&`. When the left side is `false`, `&&` short-circuits to `false`, and React treats `false`, `null`, and `undefined` as empty holes that produce zero DOM nodes.
4. **Never put a raw number on the left side of `&&`**: If we write `{commentCount && <p>{commentCount} comments</p>}` and `commentCount` is `0`, `0 && <p>...</p>` evaluates to the number `0` rather than `false`. Because React renders numbers as visible text nodes, a literal `0` appears on the screen! Always write `{commentCount > 0 && <p>{commentCount} comments</p>}` so the left side evaluates to a boolean."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does `{commentCount && <p>{commentCount} comments</p>}` print `0` on the screen when `commentCount` is `0`, and what does React render for all six falsy values in JavaScript?"**
   JavaScript's `&&` operator does not convert its left side into a boolean; when the left side is falsy, `&&` returns that exact left-hand value. So `0 && <p>...</p>` returns the number `0`. React ignores `false`, `null`, `undefined`, and the empty string `""`, creating zero DOM nodes for those four falsy values. However, `0` is a valid number to display in UIs such as prices and scores, so React renders `0` as a text node `"0"` in the DOM with zero Console warnings. And if a broken calculation produces `NaN`, `NaN && <p>...</p>` returns `NaN`, which React renders as `"NaN"` while logging a Console error. Comparing `commentCount > 0 && ...` converts the left side into the boolean `false` so nothing renders.

2. **"Why can't you write an `if` statement directly inside JSX curly braces `{ }`, and when should you use `let` with `if` instead of `? :`?"**
   During the build, JSX tags compile into `_jsxDEV` function calls whose `children` sit inside an object property or array. A JavaScript function argument or array slot can only hold an expression that evaluates to a value, such as `a ? b : c` or `a && b`. Because `if / else` is a statement rather than a value expression, `{if ...}` stops the parser at build time with `Unexpected token`. When a condition switches between two compact pieces of markup, inline `? :` is clean. When a branch spans many lines or requires `else if`, declaring a `let` variable before `return` and reassigning it in an `if / else` block keeps the shared wrapper in one place without nesting ternaries.

3. **"What happens if a parent component passes `isBreaking=\"false\"` in quotation marks to a child that renders `{isBreaking && <LiveBadge />}`?"**
   The `LiveBadge` still renders on the screen with zero Console errors! Quotation marks on a JSX attribute always create a JavaScript string literal. Inside the child component, `isBreaking` is the five-character string `'false'`, not the boolean `false`. In JavaScript, every non-empty string is truthy, so `'false' && <LiveBadge />` evaluates and returns the right-hand side, `<LiveBadge />`. Boolean props must be passed inside curly braces, such as `isBreaking={false}`.

Here is a quick-reference tree of all four conditional rendering patterns for your interview review:

```tree dir=right caption="Interview comparison of the four conditional rendering patterns in React."
Four conditional rendering patterns in React
- +Early `if` guard and `return null` [Before `return`] | Guards the whole component | Returns `null` so React creates **0 DOM nodes**
- +`isSubscriberOnly ? <A /> : <B />` [Inside `{ }` curly braces] | Expression that switches between **two** JSX branches | Keeps the outer `<article>` wrapper in one place
- +`isBreaking && <LiveBadge />` [Inside `{ }` curly braces] | Includes **one** JSX branch when a boolean is `true` | Short-circuits to `false` when `false`, creating **0 DOM nodes**
- +`commentCount > 0 && <p>...</p>` [Inside `{ }` curly braces] | Converts a number into a **boolean** before `&&` | Prevents `0 && <p>...</p>` from printing a stray **`"0"`** in the DOM
```
