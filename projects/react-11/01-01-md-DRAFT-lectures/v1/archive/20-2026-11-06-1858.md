## How React Controls a Form Field

### Three ways to put a starting name inside an input box

Before we build a project, strip away every form, button, and stylesheet. Look at one plain text input on the screen that shows the name **John** when the page opens.

Here is the first way to write that input using `defaultValue`:

```jsx title="Line A: Starting text with defaultValue"
~<input defaultValue="John" />~ // 1. Hands "John" to the box once when it first appears, then lets the browser own the text
```

Here is the second way to write that input using `value` alone:

```jsx title="Line B: Fixed text with value and no handler"
~<input value="John" />~ // 2. Locks the box to "John" on every render with no way for typing to change it
```

Here is the third way, pairing `value` with React state and an `onChange` handler:

```jsx title="Line C: Controlled text with state, value, and onChange"
const [name, setName] = useState('John');

~<input value={name} onChange={e => setName(e.target.value)} />~ // 3. Shows the state variable name and updates state on every keystroke
```

When the page first opens, all three boxes display the exact same letters: **`John`**.

Now watch what happens when a user clicks inside each box and types the two letters `ny` at the end of **John**:
- In **Line A**, the box changes to **`Johnny`**.
- In **Line B**, nothing changes at all. The box stays locked on **`John`**!
- In **Line C**, the box changes to **`Johnny`**, just like Line A.

Finally, imagine a button next to the input calls `setName` with an empty string `''` to clear the name:
- In **Line A**, the box ignores `setName` and still shows **`Johnny`**!
- In **Line C**, the box immediately becomes **empty**!

Four everyday terms explain what is happening inside those three boxes:
- **What does "default" mean?** Think of the default ringtone on a new phone. The factory sets that ringtone for the very first day. The moment you pick a new ringtone yourself, your phone plays your choice, and the factory starting setting is history. In React, `defaultValue="John"` works the exact same way. It gives the input box its starting text when the box is first created. From that moment on, the browser input box keeps and updates its own text by itself.
- **What does "controlled" mean?** Think of the departure board at a train station. The board on the wall never decides for itself which train to display. The station computer system sends the current text to the board, and the board simply shows whatever the system tells it to show. In React, an input is **controlled** when your component's state decides what the input displays on every single render through `value={name}`.
- **What is a "single source of truth"?** Imagine a kitchen with two wall clocks that say different times. You do not know which clock to trust. When a room has only one official clock, everyone reads that one clock. Keeping the field's text in one place, inside React state, makes React state the **single source of truth** for both the screen and your code.
- **How does typing work if the box cannot change itself?** If a controlled input only shows what state tells it to show, how do new letters ever appear when the user types? The `onChange` prop is the report slip. On every keystroke, the browser hands React an event object `e` carrying what the user just typed in `e.target.value`. Your `onChange` handler passes that string to `setName`. Then React re-renders with the new `name`, and the box displays the new state!

Look closely at the four silent confusions that trip developers up here:
- **First, Line A with `defaultValue="John"` and Line C with `value={name}` look the same when you type, and both show Johnny, but they are NOT the same thing!** In Line A, the browser input box owns the text inside the DOM, and React state has no idea what is in the box. In Line C, React state owns the text, and the input box only mirrors `name`.
- **Second, Line B with `value="John"` and Line C with `value={name}` both use the value prop, but they are NOT the same thing!** Line B passes a fixed string with no `onChange` handler to update it. Because nothing updates the string, React forces `'John'` back into the box after every keystroke. Line C pairs `value={name}` with `onChange`, so every keystroke updates state and renders the new text.
- **Third, writing `value="John"` and writing `value={name}` while the state variable holds John and there is no handler: YES, they are the exact same thing for the input box!** In both cases, React receives the string `'John'` for `value` and locks the box to **John**. What makes Line C editable is not the curly braces around `name`. Line C is editable because its `onChange` handler calls `setName` on each keystroke.
- **Fourth, React's `onChange` prop sounds like the plain browser `change` event, which waits until you click outside the box, but it is NOT the same thing!** In React, `onChange` fires immediately on every single keystroke, paste, or cut, just like the browser's native `input` event.

```tree caption="How Line A, Line B, and Line C behave when the page opens, when the user types ny, and when code calls setName with an empty string."
Three ways to wire an `<input>` that starts with `John`
- !Line A: `<input defaultValue="John" />` [Uncontrolled] | Typing `ny` shows **`Johnny`** in the browser box | Calling `setName` with `''` does **nothing** to the box: it stays **`Johnny`**
- !Line B: `<input value="John" />` [Read-only lock] | Typing `ny` is **reverted after every keystroke** | Box stays frozen on **`John`**, and React logs a **Console error**
- +Line C: `value={name}` + `onChange` [Controlled] | Typing `ny` updates `name` to **`'Johnny'`** on each keystroke | Calling `setName` with `''` **clears the box** right away
```

### Two ways to own a form field's value in React

In daily React work, there are two ways to handle form fields, and each one fits a clear job:
1. **Controlled fields**: You pass `value` or `checked` from React state. Then you update that state inside an `onChange` handler. Choose controlled fields whenever the page must react to every keystroke or click. Common examples include live character counts, custom input rules, conditional fields that appear when a checkbox is ticked, and buttons that clear the form from state.
2. **Uncontrolled fields**: You pass `defaultValue` or `defaultChecked` so the browser DOM owns the field while the user types. Then you read all the values once when the form is submitted, for example with `FormData` from `e.currentTarget`. Choose uncontrolled fields when the page does not need to react on every keystroke and only cares about the final values on submit. A later lesson compares controlled and uncontrolled forms side by side in full detail.

```tree caption="When to make a form field controlled vs. when to leave it uncontrolled."
Two ways to handle form inputs in React
- +1. Controlled field [`value` + `onChange` + state] | React state is the **single source of truth** on every keystroke | Best for **live counts**, **conditional fields**, **live rules**, and **resetting from state**
- +2. Uncontrolled field [`defaultValue` + read on submit] | The **browser DOM node** holds the value until the form submits | Best for **simple forms** that only read values **once on submit**
```

### What we already know and how our project files are organized

This lesson builds on three React tools from earlier lessons, plus four small browser and JavaScript facts:
- **State snapshots and setters**: Calling `useState` gives back the current render's state value and a setter function that stores the next value and triggers a re-render.
- **Event handlers and preventing reload**: Passing `onSubmit={handleSend}` to a `<form>` runs the submit handler when the user sends the form. Calling `e.preventDefault` inside `handleSend` stops the browser from reloading the page.
- **Conditional rendering with `&&`**: Writing `{sent && <p>...</p>}` renders the paragraph when the boolean `sent` is true. When `sent` is false, React renders nothing at all.
- **The four HTML form tags in this lesson**: A single-line text box or checkbox is `<input>`, and a multi-line message box is `<textarea>`. A dropdown menu is `<select>` containing `<option>` choices. Wrapping a `<label>` around the label text and its field links them together so clicking the label focuses or ticks the field.
- **How the browser stores a field's current value**: Every text input or textarea DOM node in the browser has a live `.value` property holding its current text as a string. A `<select>` DOM node also has `.value`, and every checkbox or radio node has a live checked property holding a boolean. Inside an `onChange` handler, `e.target` is that DOM node. So `e.target.value` reads the string and `e.target.checked` reads the boolean.
- **String `length` and `trim`**: Every JavaScript string has a `.length` property that counts its characters, including spaces. It also has a `.trim` method that returns a new string with spaces removed from the very start and very end while keeping spaces between words.
- **`undefined` and the fallback operator `??`**: Calling `useState` with no initial value sets state to `undefined`. The nullish coalescing operator `??` returns the left side when it is defined. It falls back to the right side only when the left side is `null` or `undefined`.

### Six Principles of Controlled Inputs

**PRINCIPLES:** A form field is controlled when React state is its single source of truth on every render, and its `onChange` handler writes every edit back into state. Six practical principles cover every field type on our **Contact Us** page:
1. **Principle 1: An Uncontrolled Box Keeps Its Own Text, So State Cannot Clear It**: Passing `defaultValue` sets only the starting text when the field first mounts. After that, the browser input box owns its own text and ignores your state variables.
2. **Principle 2: `value` Forces the Box to Show State, and `onChange` Lets Typing Reach State**: Passing `value={message}` locks the box to the state variable on every render. Pairing `value={message}` with an `onChange` handler completes the loop so typing updates state and re-renders the box.
3. **Principle 3: Whatever the Handler Writes Into State Is What the Box Shows**: On every keystroke, React renders the exact string stored in state. Calling `.trim` inside `onChange` eats spaces as the user types. Checking `e.target.value.length <= 200` before calling the setter caps the length cleanly.
4. **Principle 4: A Select Is Controlled by `value` on `<select>`, Never `selected` on an `<option>`**: Never put the HTML `selected` attribute on an option inside React. Instead, pass `value={topic}` and `onChange` directly on the select tag.
5. **Principle 5: A Checkbox Is Controlled by `checked`, and Reports Through `e.target.checked`**: A checkbox stores a boolean `true` or `false`, not text. Control it with `checked={wantsReply}` and update state from `e.target.checked`, never from the string value prop.
6. **Principle 6: The `value` Is a String From the First Render to the Last**: Passing `value={undefined}` makes an input uncontrolled. If state starts as `undefined` from an empty `useState` call and later receives a typed string, the input switches from uncontrolled to controlled and logs a Console error. Always initialize text state with the empty string `''`.

Here is the complete map of all six principles before we build each one on our **Contact Us** page:

| # | Principle | Symptom in the Browser or Console | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Uncontrolled `defaultValue` vs. State** | Resetting `message` to `''` on submit shows the thank-you notice, yet the customer's typed message stays inside the box with zero Console errors. | `defaultValue` only sets the initial DOM text on mount; to drive or clear a box from state, bind `value` to state. |
| **Principle 2** | **`value` Paired with `onChange`** | Passing `value={message}` without `onChange` freezes the box so typed letters never appear and logs a read-only field error in the Console. | Always pair `value={state}` with an `onChange` handler that reads `e.target.value` and calls the state setter. |
| **Principle 3** | **Handler Transformation and Validation** | Trimming `e.target.value` inside `onChange` deletes the space key as the user tries to type `Anna Lee`. | Keep raw text in state while typing, trim on submit, and check `e.target.value.length` in `onChange` when capping length. |

''}`, so `value` is a string on every render. |

## 1. Principle 1: An Uncontrolled Box Keeps Its Own Text, So State Cannot Clear It

### Why calling a state setter does nothing to an input that uses `defaultValue`

Before we open our shop files, look at a single input box and one state variable side by side:

```jsx title="An uncontrolled input next to a state variable"
const [name, setName] = useState('John');

~<input defaultValue="John" />~ // Sets the starting text in the browser box once, with no link to the state variable name
```

Watch what happens when the user types `ny` into that box to make **Johnny**, and then clicks a button whose handler calls `setName` with an empty string:
1. The variable `name` inside React state changes from `'John'` to an empty string.
2. React re-renders the component and sees `defaultValue="John"` on the `<input>`.
3. Because `defaultValue` only sets the starting value when the input first mounts, the browser input box keeps its own current text. It still says **`Johnny`** on screen!

Look at the two confusions that make this bug so sneaky:
- **First, writing `defaultValue="John"` and writing `defaultValue={name}` look as if the second one connects the box to the state variable, but it does NOT control the box!** Passing `{name}` to `defaultValue` still only hands the starting value to the browser when the input first appears. Once the user types into the box, the browser keeps the user's typed text inside the DOM node. Changing `name` in state later will not clear or replace what the user typed.
- **Second, in plain HTML you set starting text on `<textarea>` by placing text between its opening and closing tags, but in React you should NOT put children inside `<textarea>`!** In React, even a multi-line `<textarea>` uses the `defaultValue` attribute for uncontrolled starting text, just like a text input.

Where do the words **uncontrolled** and **controlled** come from in React? In component design, any component that manages its own data in its own private memory instead of being driven by props from its parent is called **uncontrolled**. When you render an `<input>` with `defaultValue=""`, the built-in browser input manages its own text inside the browser DOM without asking your component. When you pass `value={name}` from your component's state, your component takes control via props, so the input becomes **controlled**:

```tree caption="Who owns the text inside the input box when you use defaultValue vs. when you control the input from state."
Who owns the text shown inside `<input>`?
- !Uncontrolled [`defaultValue`] | The **browser DOM node** stores and updates its own text | Calling `setName` with `''` in React **cannot clear** what the user typed
- +Controlled [`value={name}` + `onChange`] | **React state** owns `name` and hands it to the box on every render | Calling `setName` with `''` in React **clears the box** on the very next render
```

### Mistake: Trying to clear an uncontrolled textarea with `setMessage`

Let us start building our online shop's **Contact Us** page and watch this exact bug happen.

First, our main file imports `ContactForm` from the components folder and renders it inside `<main>`:

```jsx title="src/App.jsx" startLine="1"
import ~ContactForm~ from './components/ContactForm.jsx'; // 1. Import ContactForm from the components folder

export default function App() {
  return (
    <main className="page">
      ~<ContactForm />~ {/* 2. Render the shop's Contact Us form */}
    </main>
  );
}
```

Next, inside the form file, the developer creates two state variables: `message` initialized to an empty string and `sent` initialized to false. Inside `handleSend`, they prevent the browser reload and set `sent` to true. Then they call `setMessage` with an empty string expecting to empty the message box, while rendering the textarea with `defaultValue=""`:

```jsx title="src/components/ContactForm.jsx" startLine="1"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');
  const [sent, setSent] = useState(false);

  function handleSend(e) {
    e.preventDefault();
    setSent(true);
    ~setMessage('');~ // Tries to clear the message box by setting message state to ''
  }

  return (
    <section className="card">
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Message
          ~<textarea defaultValue="" />~ {/* **WRONG:** uncontrolled box ignores the message state variable! */}
        </label>
        <button type="submit">Send</button>
      </form>
      {sent && <p>Thanks! Your message was sent.</p>}
    </section>
  );
}
```

Now trace what happens step by step when a customer uses this form in the browser:
1. The page opens with an empty **Message** box and a **Send** button.
2. The customer clicks inside the **Message** box and types **Where is my order?**. The browser stores that sentence inside the `<textarea>` DOM node's own memory. Meanwhile, the `message` state variable in React is still `''`.
3. The customer clicks **Send**.
4. Inside `handleSend`, the code prevents the page reload, marks the sent flag as true, and resets `message` to an empty string.
5. React re-renders `ContactForm`. The thank-you line **Thanks! Your message was sent.** appears below the form.
6. Look at the **Message** box above it: **Where is my order?** is still sitting inside the box, and the browser Console shows zero errors or warnings!

```page size=mini caption="After clicking Send on an uncontrolled textarea: the thank-you notice appears, yet Where is my order? stays stuck inside the Message box."
heading: Contact Us
form:
  textarea: Message | Where is my order? | bad
  submit: Send
line: Thanks! Your message was sent. | good
console: quiet
```

Why did `setMessage` fail to clear the box? Because an uncontrolled `<textarea>` with `defaultValue=""` never reads the state variable! The `defaultValue` prop only told the browser to start the box empty when the page first loaded. Once the customer typed **Where is my order?**, the browser DOM node kept that text to itself.

To let React state drive and clear the **Message** box, we need to replace `defaultValue` with `value={message}` and connect the box back to state. That brings us directly to Principle 2.

> [!PRINCIPLE]
> **Principle 1: Uncontrolled `defaultValue` vs. State: An Uncontrolled Box Keeps Its Own Text**
>
> *Passing `defaultValue` only sets a form field's initial text when it first mounts; after that, the browser DOM node owns the text and ignores React state updates.*
>
> In React, both text inputs and `<textarea>` tags accept the `defaultValue` prop to set their starting text as uncontrolled fields. An uncontrolled field stores and updates its own text inside the browser DOM node. Calling a state setter inside a submit handler has no effect on what the box displays on screen, and no Console warning is printed. Whenever your component needs to read the field's text during typing or clear the field from state, control the field with `value` instead of `defaultValue`.
>
> **DO THIS:**
> ```jsx
> <textarea
>   ~value={message}~ // Binds the box to message state on every render
>   ~onChange={e => setMessage(e.target.value)}~ // Updates message state on every keystroke
> />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<textarea defaultValue="" />~ // **WRONG:** browser DOM owns the text and ignores setMessage!
> ```

## 2. Principle 2: `value` Forces the Box to Show State, and `onChange` Lets Typing Reach State

### Why passing `value` alone locks the box, and how `onChange` unlocks it

Strip everything back to our single `<input>` box and compare Line B and Line C again.

First, look at passing `value` without an `onChange` handler:

```jsx title="Line B: Passing value without onChange"
const [name, setName] = useState('John');

~<input value={name} />~ // Locks the input to name ('John') with no handler to update name!
```

Now compare that with passing both `value` and `onChange`:

```jsx title="Line C: Pairing value with onChange"
const [name, setName] = useState('John');

~<input value={name} onChange={e => setName(e.target.value)} />~ // Updates name on every keystroke and renders the new string
```

What happens when the user tries to type a letter into **Line B**?
1. The user presses the `n` key on the keyboard.
2. No `onChange` handler exists, so `setName` is never called. The state variable stays `'John'`.
3. Because the input has `value={'John'}`, React sees that the box is only allowed to display **John** and immediately restores the box's text back to **`John`**! Every single keystroke is wiped out the instant you press the key.

Now trace the four-step loop that runs on every single keystroke in **Line C**:
1. **Render**: `name` starts as **John**, so passing `value={name}` to the input tells the browser box to show **John**.
2. **Keystroke**: The user presses `n` at the end of **John**. The browser fires the change event and passes the event object `e` to `onChange`. On that event object, `e.target` is the input DOM element, and `e.target.value` holds the new string **Johnn**.
3. **State update**: Your handler passes `e.target.value` to `setName`, storing the new string in React state.
4. **Re-render**: React re-renders the component with `name` equal to `'Johnn'`. It passes `value={'Johnn'}` to the input, and the browser box now shows **`Johnn`**!

Look at the two confusions to clear up right here:
- **First, writing `value={name}` without `onChange` looks as if it should let the user type into `name`, because `name` is a state variable, but it does NOT!** A state variable only changes when someone calls its setter function `setName`. Without `onChange` calling the setter, the state variable stays frozen at its initial value on every render, and `value={name}` forces the box to keep showing that frozen value.
- **Second, you may wonder what to do when you genuinely want a box that displays a value the user can copy but cannot edit: pass `readOnly` alongside `value`!** Adding the `readOnly` prop tells both the browser and React that the box is intentionally read-only, which silences React's Console error.

```tree dir=right caption="The four-step controlled input loop that runs on every keystroke when value is paired with onChange."
One keystroke inside a controlled `<input>` with `value={name}` and `onChange`
- +1. Render [`value={name}`] | React passes the current `name` snapshot **`'John'`** to the `<input>` | Box displays **`John`**
- +2. User presses `n` [`onChange`] | Browser puts **`'Johnn'`** on `e.target.value` and calls `onChange` | Handler reads `e.target.value`
- +3. Setter call [`setName` with `'Johnn'`] | Handler stores **`'Johnn'`** in React state | React schedules a re-render
- +4. Re-render [`value={'Johnn'}`] | Component runs again with `name = 'Johnn'` | Box displays **`Johnn`**
```

### Mistake: Replacing `defaultValue=""` with `value={message}` and forgetting `onChange`

In our **Contact Us** form, the developer wants `setMessage` to clear the **Message** box on submit. They also want to show a live character counter **0 / 200** right below the box.

Suppose the developer replaces `defaultValue=""` with `value={message}` on the textarea. They add the counter paragraph below it, and they stop there without adding `onChange`:

```jsx title="src/components/ContactForm.jsx" startLine="13"
  return (
    <section className="card">
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Message
          ~<textarea value={message} />~ {/* **WRONG:** value={message} without onChange locks the box to ''! */}
        </label>
        <p>{message.length} / 200</p>
        <button type="submit">Send</button>
      </form>
      {sent && <p>Thanks! Your message was sent.</p>}
    </section>
  );
```

Save the file and open the browser:
1. Before the customer even clicks inside the box, React prints a red error in the browser **Console**. It warns that you passed `value` without an `onChange` handler, which renders a read-only field.
2. Next, the customer clicks inside the **Message** box and tries to type **Where is my order?**.
3. Not a single letter appears! Because `message` in state is an empty string and nothing updates it, React forces the textarea back to `''` after every keystroke. The counter below stays frozen at **0 / 200**.

### Fix: Pairing `value={message}` with an `onChange` handler that updates `message`

Now let us complete the controlled loop by adding `onChange` to the `<textarea>` in our form file. On every keystroke, that handler passes `e.target.value` to `setMessage`:

```jsx title="src/components/ContactForm.jsx" startLine="1"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');
  const [sent, setSent] = useState(false);

  function handleSend(e) {
    e.preventDefault();
    setSent(true);
    ~setMessage('');~ // Resets message to '' when the form is submitted
  }

  return (
    <section className="card">
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Message
          <textarea
            ~value={message}~ // 1. Displays the current message state on every render
            ~onChange={e => setMessage(e.target.value)}~ // 2. Writes every typed character into message state
          />
        </label>
        <p>{message.length} / 200</p>
        <button type="submit">Send</button>
      </form>
      {sent && <p>Thanks! Your message was sent.</p>}
    </section>
  );
}
```

Save the file and test the exact same customer steps now:
1. The Console is completely clean with zero errors.
2. As the customer types **Where is my order?**, each keystroke updates `message` in state. Both the `<textarea>` and the counter paragraph read the exact same `message` variable. So the box shows **Where is my order?** and the counter underneath climbs live to **18 / 200**.

> ~<textarea value={message} />~ // **WRONG:** missing onChange locks the box and logs a Console error!

## 3. Principle 3: Whatever the Handler Writes Into State Is What the Box Shows

### Three `onChange` handlers on the same controlled input

Because a controlled input always displays the string stored in state, your `onChange` handler has the final say on every single keystroke. Whatever string your handler passes to `setName` is what appears in the box!

Compare three different `onChange` handlers on a controlled `name` input when a user tries to type the two-word name **Ann Lee** one key at a time.

First, look at Handler A, which stores `e.target.value` as-is:

```jsx title="Handler A: Storing e.target.value as-is"
~<input value={name} onChange={e => setName(e.target.value)} />~ // 1. Typing "Ann Lee" stores and shows "Ann Lee"
```

Second, look at Handler B, which calls `.trim` on every keystroke:

```jsx title="Handler B: Calling .trim on every keystroke"
~<input value={name} onChange={e => setName(e.target.value.trim())} />~ // 2. Eats the space after "Ann" -> box shows "AnnLee"!
```

Third, look at Handler C, which only updates state when the length is at most `5`:

```jsx title="Handler C: Ignoring keystrokes past 5 characters"
<input
  value={name}
  ~onChange={e => { if (e.target.value.length <= 5) setName(e.target.value); }}~ // 3. Stops updating after "Ann L" (5 chars)
/>
```

Trace what happens at the exact moment the user finishes typing **Ann** and presses the **Spacebar**:
- In **Handler A**, `e.target.value` is `'Ann '` with a trailing space. Passing that string to `setName` stores the space in state, so when the user next types **Lee**, the box shows **`Ann Lee`**.
- In **Handler B**, `e.target.value` is `'Ann '` with a trailing space. Calling `.trim` on `'Ann '` strips the trailing space right off and returns the three-letter string **Ann**! So `setName` stores `'Ann'` without the space. When the user next types **Lee**, the letters glue straight onto **Ann** and the box shows **`AnnLee`**!
- In **Handler C**, the first five keys build the string up to `'Ann L'`. When the user presses `e` for the sixth character, the length is `6`, so the condition is false. Because `setName` is not called, `name` stays **Ann L**, and React keeps the box at **Ann L**!

Look at the three insights this reveals about controlled inputs:
- **First, calling `.trim` inside `onChange` and calling `.trim` inside `onSubmit` look like two ways to clean up extra spaces, but they are NOT the same thing!** While a person types a two-word name like **Ann Lee**, the space between the two words sits at the end of the string right after **Ann**. Trimming on every keystroke destroys that space before the second word is typed. Trimming once inside `onSubmit` when the form is sent strips leading and trailing spaces cleanly while letting the user type spaces between words normally.
- **Second, why does transforming text on every keystroke, such as converting to uppercase, or calling `setName` inside a `setTimeout` timer, make the blinking text cursor jump to the very end of the box?** Suppose the box holds **ann** and the user clicks between **a** and **nn** to type a letter in the middle. When `onChange` writes a brand-new transformed string or updates the input later in a timer, the browser replaces the whole string inside the `<input>` DOM node. Replacing the DOM string drops the blinking cursor, called the **caret**, at the very end of the text! Storing `e.target.value` synchronously inside `onChange` preserves the user's cursor position.
- **Third, even when an input has `type="number"`, `e.target.value` is ALWAYS a string in JavaScript!** Typing **42** into a number input gives `'42'` on `e.target.value`. Clearing the box gives the empty string `''`.

```tree caption="What appears in the input box when the user types Ann Lee under Handler A, Handler B, and Handler C."
Typing `A`, `n`, `n`, `Space`, `L`, `e`, `e` into a controlled `<input>` with `value={name}`
- +Handler A: passes raw `e.target.value` to `setName` | Keeps `'Ann '` when the user presses Space | Box shows **`Ann Lee`**
- !Handler B: trims `e.target.value` on every keystroke | `.trim` strips the trailing space right back to `'Ann'` | Box glues the words into **`AnnLee`!**
- +Handler C: checks `e.target.value.length <= 5` | Skips `setName` once length passes `5` | Box stops cleanly at **`Ann L`**
```

```jsx title="src/components/ContactForm.jsx" startLine="1"
    setName('');
    setMessage('');
  }
```

Any accidental spaces at the very start or end are trimmed when **Send** is clicked, and the **Message** box refuses any character past `200`! ## 4. Principle 4: A Select Is Controlled by `value` on `<select>`, Never `selected` on an `<option>`

### HTML's `selected` attribute on `<option>` vs. React's `value` prop on `<select>`

Now strip away the rest of the page and look at one dropdown menu with two choices: **Tea** and **Coffee**.

In plain HTML, you mark the starting choice by placing the `selected` attribute on one `<option>` tag inside the menu:

```html title="Plain HTML habit: putting selected on an <option>"
<select>
  <option value="tea">Tea</option>
  ~<option value="coffee" selected>Coffee</option>~ <!-- Plain HTML attribute on one option -->
</select>
```

In React, you never put `selected` on an `<option>`. Instead, you control a select menu the exact same way you control an input or textarea, by placing `value` and `onChange` right on the select tag itself:

```jsx title="React: controlling <select> with value and onChange on the <select> tag"
const [drink, setDrink] = useState('coffee');

~<select value={drink} onChange={e => setDrink(e.target.value)}>~ {/* Controls the chosen option from state! */}
  <option value="tea">Tea</option>
  <option value="coffee">Coffee</option>
</select>
```

How does `<select value={drink}>` know which option to display?
1. Each `<option>` has a `value` attribute, such as **tea** or **coffee**, and visible label text between its tags, such as **Tea** or **Coffee**.
2. On every render, React compares the `value` prop on `<select>` against the value attributes of its option children. Because `drink` is `'coffee'`, React highlights the **Coffee** option row.
3. When the user opens the menu and picks **Tea**, the browser sets `e.target.value` on the select DOM node to the string **tea** and fires `onChange`. Your handler passes `'tea'` to `setDrink`, and React re-renders with **Tea** selected!

Look at the two confusions that catch developers here:
- **First, putting `selected` on the Coffee option and putting `value={drink}` on `<select>` both show Coffee when the page opens, but they are NOT the same thing!** Putting `selected` on an `<option>` triggers a React Console warning and leaves the dropdown disconnected from state. Because it is disconnected from state, resetting state on submit will never reset the dropdown.
- **Second, when the user picks the My order option whose `value` attribute is `"order"`, you might expect `e.target.value` to be `'My order'`, but it is NOT!** When an `<option>` has a value attribute, `e.target.value` is always that attribute's string, such as **order**. It only falls back to the inner text if you omit the `value` attribute on `<option>`.

```tree caption="How HTML's selected attribute on option compares with React's value and onChange props on select."
Two ways developers try to control a `<select>` dropdown
- !`selected` on `<option>` [HTML habit] | Logs a **React Console warning** | Dropdown is **disconnected from state** and ignores state resets
- +`value={drink}` + `onChange` on `<select>` [React rule] | Matches `drink` against each `<option value="...">` | Picking an option updates `drink`, and resetting `drink` **resets the menu**
```

## 5. Principle 5: A Checkbox Is Controlled by `checked`, and Reports Through `e.target.checked`

### Why a checkbox is a light switch that uses `checked` and `e.target.checked`

Strip away the form again and look at a single checkbox input with `type="checkbox"`.

A text box holds a string of words, like a notepad. A checkbox is a **light switch**: it is either **on** with `true` or **off** with `false`. Because a checkbox represents a boolean, React controls it with the `checked` prop and reads its new boolean state from `e.target.checked`.

Compare the broken way and the working way to wire a checkbox to a boolean `agree` state variable.

First, look at the broken way that reads `e.target.value` instead of `e.target.checked`:

```jsx title="Broken checkbox handler: reading e.target.value"
const [agree, setAgree] = useState(false);

~<input type="checkbox" checked={agree} onChange={e => setAgree(e.target.value)} />~ // **WRONG:** e.target.value is always the string "on"!
```

Now compare that with the working way that reads `e.target.checked`:

```jsx title="Working checkbox handler: reading e.target.checked"
const [agree, setAgree] = useState(false);

~<input type="checkbox" checked={agree} onChange={e => setAgree(e.target.checked)} />~ // Reads true when ticked and false when unticked!
```

Why does the first checkbox tick on the first click and then **refuse to ever untick** on the second click?
1. In the browser DOM, every checkbox input without an explicit `value` attribute has a default `.value` string of **on**! That string `'on'` simply identifies the checkbox for traditional HTML form submissions and **never changes** whether the box is ticked or unticked.
2. When the user clicks the unticked box the first time, `e.target.value` is `'on'`. Passing `'on'` to `setAgree` puts a non-empty string into state. Because `'on'` is truthy in JavaScript, the box ticks!
3. When the user clicks the ticked box a **second** time to untick it, `e.target.value` is **still `'on'`**! Passing `'on'` to `setAgree` keeps that same truthy string in state, so the checkbox stays ticked forever!
4. By contrast, `e.target.checked` is a real boolean on the DOM node. It is `true` when the user ticks the box and `false` when the user unticks it.

Look at two more checkbox rules to keep in mind:
- **First, passing `value={agree}` instead of `checked={agree}` on a checkbox does NOT control the tick mark!** On a checkbox, `value` only sets the HTML submission label, whereas `checked` controls whether the box is ticked on screen.
- **Second, just like `value` on a text input, passing `checked={agree}` without an `onChange` handler locks the checkbox and logs a Console error!** For an uncontrolled checkbox, the starting attribute is `defaultChecked`, not `defaultValue`. Radio buttons also use `checked` and `defaultChecked` for their boolean selection state.

```tree caption="What happens on the first click and the second click when a checkbox handler reads e.target.value vs. e.target.checked."
Clicking a checkbox twice: once to tick, once to untick
- !Handler reads `e.target.value` | Click 1 passes **`'on'`** [ticks]; Click 2 still passes **`'on'`** | Checkbox stays **stuck ticked forever** on every click!
- +Handler reads `e.target.checked` | Click 1 passes **`true`** [ticks]; Click 2 passes **`false`** [unticks] | Checkbox **toggles cleanly** between `true` and `false`
```

### Mistake: Reading `e.target.value` on the Email me a reply checkbox

On our **Contact Us** page, we now add an **Email me a reply** checkbox stored in a boolean `wantsReply` state variable initialized to `false`. Suppose the developer copies the `e.target.value` habit from the text inputs and passes that string to `setWantsReply`:

### Fix: Reading `e.target.checked` and resetting `wantsReply` to `false` on submit

Let us change `e.target.value` to `e.target.checked` on the checkbox. Inside `handleSend`, we also reset `wantsReply` back to false:

> [!PRINCIPLE]
> **Principle 5: Controlling a Checkbox: Bind `checked` to a Boolean and Read `e.target.checked`**
>
> *Control a checkbox with `checked={booleanState}` and update state in the change handler by reading `e.target.checked`, never the string value.*
>
> Unlike text inputs, a checkbox represents a boolean `true` or `false`. Its visual tick mark is controlled by the `checked` prop, and the browser reports the new boolean after each click on `e.target.checked`. Reading `e.target.value` on a checkbox reads the static HTML string `'on'`, which turns state truthy on the first click and prevents the user from ever unticking the box.
>
> **DO THIS:**
> ```jsx
> <input
>   type="checkbox"
>   ~checked={wantsReply}~ // Binds the tick mark to boolean state
>   ~onChange={e => setWantsReply(e.target.checked)}~ // Updates state with true or false
> />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input
>   type="checkbox"
>   checked={wantsReply}
>   ~onChange={e => setWantsReply(e.target.value)}~ // **WRONG:** passes 'on' on every click so it can never untick!
> />
> ```

## 6. Principle 6: The `value` Is a String From the First Render to the Last

### Why leaving `useState` empty switches an input from uncontrolled to controlled mid-flight

Strip everything back to one `<input>` one last time and compare two lines that initialize `city` state.

First, look at calling `useState` with no argument:

```jsx title="Broken initialization: empty useState starts city as undefined"
~const [city, setCity] = useState();~ // 1. On Render 1, city is undefined -> value={undefined} makes <input> UNCONTROLLED!

<input value={city} onChange={e => setCity(e.target.value)} />
```

Now compare that with passing the empty string `''` to `useState`:

```jsx title="Working initialization: passing an empty string starts city as ''"
~const [city, setCity] = useState('');~ // 2. On Render 1, city is '' -> value={''} makes <input> CONTROLLED from Render 1!

<input value={city} onChange={e => setCity(e.target.value)} />
```

When the page first opens, both input boxes look **completely empty** on screen. Why does the first one log a Console error the moment the user types a single letter, while the second one works with zero warnings?
1. In JavaScript, calling `useState` with no argument sets the initial state to **`undefined`**.
2. To React, passing `value={undefined}` to an `<input>` means the exact same thing as rendering an input with no value prop at all! So on the first render, React creates an **uncontrolled** input box.
3. Next, the user presses the `P` key to type **Paris**. The `onChange` handler passes `'P'` to the setter.
4. On the second render, `city` is now the string `'P'`. React sees `value={'P'}` and realizes that an input that started its life **uncontrolled** with `value={undefined}` has suddenly switched to **controlled**!
5. React immediately logs an error in the Console. It warns that a component is changing an uncontrolled input to be controlled because the value changed from `undefined` to a defined string.

Look at the two confusions that make this happen in real projects:
- **First, calling `useState` with no argument and calling `useState` with `''` both produce an empty-looking input box on the first render, so they look the same on screen, but they are NOT the same thing!** An empty `useState` call passes `undefined`, which makes the input uncontrolled on the first render. Passing `''` gives the input a real string from the very first render, so it stays controlled for its entire lifetime.
- **Second, what if a prop or loaded record comes from a server where a field might be `null` or `undefined`, such as `user.city`?** Passing `null` or `undefined` to the value prop causes the exact same error. In that case, use the fallback operator `??` and write `value={user.city ?? ''}`. That way, the input always receives an empty string whenever the data is `null` or `undefined`. The same lifetime law applies to checkboxes: `checked` must be a boolean on every render, never `undefined`.

```tree caption="What React sees on Render 1 and on the first keystroke when city starts as undefined vs. when city starts as an empty string."
First render vs. first keystroke on `<input>` with `value={city}` and `onChange`
- !`city` starts as `undefined` | Render 1 passes `value={undefined}` [**uncontrolled**] | First keystroke passes `'P'` [**controlled**] and logs a **Console error**
- +`city` starts as `''` | Render 1 passes `value={''}` [**controlled**] | First keystroke passes `'P'` [**controlled**] with **0 Console errors**
```

## For the Interview

### How to Answer Clearly in 30 Seconds

**The Interview Question:** *How do you make an input, textarea, or select fully controlled by React state?*

> "You make a form field controlled by making React state its **single source of truth** through a two-part loop. First, you store the field's value in state with `useState`, starting with an empty string `''` for text or `false` for a checkbox, never `undefined`. You pass that state variable into the element's `value` prop, or into `checked` for checkboxes and radio buttons. Second, you pass an `onChange` handler that reads `e.target.value`, or `e.target.checked` for a checkbox, on every keystroke or click and calls the state setter. In React, `<input>`, `<textarea>`, and `<select>` all use `value` and `onChange` directly on the tag itself. So on `<select>`, you set `value` on `<select>` rather than `selected` on `<option>`. Because the field always displays whatever is in state, you can show live counts, enforce input rules inside `onChange`, or clear the entire form by resetting state."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What happens if you pass `value={text}` to an `<input>` without an `onChange` handler, or if you initialize state with an empty `useState` call instead of `''`?"**
   - **Your Answer:** "Passing `value={text}` without `onChange` locks the input to the current `text` value on every render. Typing does nothing in the box, and React logs a Console error saying you rendered a read-only field unless you also pass `readOnly`. Calling `useState` with no argument sets the initial state to `undefined`, so on the first render `value={undefined}` mounts an **uncontrolled** input. The moment the user types and `onChange` stores a string, the input switches from uncontrolled to controlled and React logs the uncontrolled-to-controlled Console error. Initializing state with `''` or falling back with `value={text ?? ''}` prevents that."
2. **"Why does trimming `e.target.value` inside `onChange` break typing a full name, and why can transforming text in `onChange` jump the cursor to the end?"**
   - **Your Answer:** "React re-renders the input with the exact string stored in state after every keystroke. When a user types `'Anna'` and presses the Spacebar to type `'Anna Lee'`, the space sits at the end of `'Anna '` on that keystroke. Calling `.trim` inside `onChange` strips that space right away and glues the words into `'AnnaLee'`. Instead, keep raw `e.target.value` while typing and call `.trim` once inside `onSubmit`. Similarly, if `onChange` rewrites characters mid-word or updates state inside `setTimeout`, the browser replaces the DOM string and drops the blinking caret at the end."
3. **"When should you use controlled inputs versus uncontrolled inputs with `defaultValue` and `FormData`?"**
   - **Your Answer:** "Use **controlled inputs** whenever the UI must react on every keystroke or click. Common examples include showing a live character count, disabling a button until fields are valid, revealing conditional fields, or clearing inputs via state setters. Use **uncontrolled inputs** with `defaultValue` or `defaultChecked` when you only need the values once when the form is submitted. In that case, you read them from the `<form>` element via `FormData` inside `onSubmit` or a React 19 form action."

```tree dir=right caption="The six-point interview checklist for controlled inputs in React."
How to control every form field in React
- +1. Uncontrolled vs. controlled [`defaultValue` vs. `value`] | `defaultValue` only sets initial DOM text once; `value` binds the box to **React state** on every render
- +2. The two-part loop [`value={text}` + `onChange`] | `value` forces state onto the box; `onChange` writes **`e.target.value`** back into state
- +3. Handler rules [raw while typing, `.trim` on submit] | Store raw `e.target.value` while typing; cap length with an `if` check in `onChange` or `maxLength`
- +4. Dropdowns [`value` on `<select>`] | Put `value={topic}` and `onChange` on **`<select>`**, never `selected` on `<option>`
- +5. Checkboxes [`checked` + `e.target.checked`] | Bind **`checked={bool}`** and read **`e.target.checked`**, because `e.target.value` is `'on'`
- +6. Lifetime string rule [`''` or `value ?? ''`] | Start text state with **`''`**, never `undefined`, so the input never switches from uncontrolled to controlled
```
