# Lecture 32: Connecting a Component to an External System with useEffect
> INTERVIEW QUESTION | ❱ CORE | How do you connect a component to an external system, and how do you disconnect it?

---

## How a Component Starts Something When It Appears, and Stops It When It Leaves

### Code that runs because the component is on the screen

Think of a counter on a page that counts the seconds by itself. When the counter appears, it starts at zero and goes up by one every second. When the user hides it, it stops. No click inside the counter starts it. So where does the code that starts the timer go, and who stops it?

So far, a component has held two kinds of code:
1. **Rendering code**, at the top level of the component. It takes props and state and returns JSX. Since Lesson 14 we know it must be pure. The docs put it this way: "Like a math formula, it should only _calculate_ the result, but not do anything else."
2. **Event handlers**, such as the function in `onClick` from Lesson 11. In the docs' words, they "*do* things rather than just calculate them", and they run because of "a specific user action", such as a click on a button or typing in a box.

Our counter fits neither. Starting a timer is not a calculation, so it cannot sit in the rendering code. And no click causes it, so there is no event handler to put it in. The timer must start because the counter is on the screen, "no matter which interaction caused the component to appear". The docs give a chat page as their example: the chat must stay connected to the chat server for as long as it is visible.

React has a third place for exactly this case. It is called an **Effect**. The docs say: "Effects let you specify side effects that are caused by rendering itself, rather than by a particular event."

```tree caption="Three kinds of code in a component, and what causes each one to run."
Three kinds of code in a component
- +Rendering code [`return <h1>{count}</h1>`] | Runs on **every render** | Only **calculates** the JSX from props and state
- +Event handler [`onClick={handleStart}`] | Runs because **the user did something**, such as a click | **Does** things: changes state, sends a message
- +Effect [`useEffect`] | Runs because **the component is on the screen** | **Starts** something, such as a timer, and **stops it** when the component leaves
```

### Switching the light on, and switching it off

When we enter a dark room, we switch the light on. When we leave, we switch it off. Whoever switched the light on is the one who switches it off.

A component works the same way. When our counter appears, our code starts a timer. When the counter leaves the page, React removes the DOM nodes it created from our JSX, here the `<h1>` with the number. But React did not start the timer. Our code did, by calling the browser's `setInterval`, as in Lesson 30. So React does not stop it either. Our code has to stop it, with `clearInterval`.

The docs have a name for things like this timer: "These systems aren't controlled by React, so they are called external." An **external system** is any piece of code that React does not control. The docs list the usual ones: a timer started with `setInterval`, an event listener added with `window.addEventListener`, a connection to a chat server, and a widget from a library that is not written in React.

```tree caption="What React removes when a component leaves the page, and what our own code must stop."
When the counter leaves the page
- +What React created [`<h1>{count}</h1>`] | React built the `<h1>` from **our JSX** | React **removes it by itself**
- !What our code started [`setInterval`] | The **browser** runs the timer, **not React** | It keeps running until **our code** calls `clearInterval`
```

### The same timer, started for two different reasons

In Lesson 30, the stopwatch also called `setInterval`. There, the call sat in the handler of the Start button. In this lesson, the counter calls `setInterval` inside an Effect. It may look the same, or work the same at first, but it is NOT the same thing! Both start the same kind of browser timer. The stopwatch's timer starts because the user clicked Start. The counter's timer starts because the counter appeared on the page. Principle 5 puts the two side by side.

### What is at stake

What is at stake is a timer that keeps running after the user can no longer see it. On our example page, each mistake of this lesson shows up at once:
1. With the timer started in the body of the component, the number climbs faster and faster.
2. With the timer in an Effect and no code that stops it, the number goes up by two every second in development. The docs say it plainly: "instead of incrementing once per second, it increments twice."
3. In production, the number looks right. But after the user hides the counter, the timer keeps running. Each time the user shows the counter again, one more timer starts. The docs say the same of the chat: "the connections would keep piling up."

Readers usually go wrong in four ways. They start the timer or the connection in the body of the component. They read the empty array `[]` as "run once" and then fight React when it runs the Effect twice in development, often with a ref. They write the code that starts the timer and forget the code that stops it. And they put work that a click causes, such as buying a product, into an Effect.

### Our example page: a seconds counter the user can show and hide

Our page has one button and, under it, the counter. The button reads Show counter, and Hide counter while the counter is shown. In this lecture we call them the show button and the hide button. Here is what the user does, and what each click should change:
1. The user clicks the show button. The number `0` appears and goes up by one every second.
2. The user clicks the hide button. The number disappears, and the timer stops.
3. The user clicks the show button again. The counter starts again from `0`, with one timer only.

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
```

### Five Principles of Connecting a Component to an External System

**PRINCIPLES:** An Effect is code that React runs because the component is on the screen. Its setup starts the connection to the external system, and its cleanup ends it. Five principles follow from that:
1. **Principle 1: useEffect Starts the Timer After the Commit**: The body of the component runs during every render and must only calculate the JSX. Code that must run because the component is on the screen goes inside `useEffect`, and React runs it after the commit.
2. **Principle 2: [] Starts the Timer Only on Mount**: The second argument of `useEffect` lists the values the Effect reads. With no array, the Effect runs after every commit. With `[]`, it runs only when the component appears.
3. **Principle 3: The Cleanup Function Stops the Hidden Counter's Timer**: The function that the setup returns is the cleanup. React calls it before the Effect runs again, and one last time when the component leaves the page.
4. **Principle 4: A Ref Guard Leaves the Timer Running**: In development, React runs the setup and the cleanup one extra time to test the cleanup. The fix for what this test shows is a cleanup, not a ref that blocks the second run.
5. **Principle 5: The Buy Click Sends the Order, Not an Effect**: Work that a click causes, such as buying, goes in the handler of that click. An Effect is only for work that being on the screen causes.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **useEffect Starts the Timer After the Commit** | A timer or a subscription started in the body of the component starts again on every render, and the number on the page climbs faster and faster. | Put code that must run because the component is on the screen inside `useEffect`; React runs it after the commit, never during rendering. |
| **Principle 2** | **[] Starts the Timer Only on Mount** | With no array, the Effect runs after every commit, so a timer that changes state starts a new timer on every tick. | List in the array every value from the component that the Effect reads; when it reads none, the array is `[]`, and the Effect runs only on mount. |
| **Principle 3** | **The Cleanup Function Stops the Hidden Counter's Timer** | Without a cleanup, the timer keeps running after the user hides the counter, and each new mount adds one more timer. | Return a cleanup function from the setup that stops or undoes what the setup started, such as `clearInterval` for `setInterval`. |
| **Principle 4** | **A Ref Guard Leaves the Timer Running** | A ref that blocks the second run in development makes the Console look right while the timers still pile up for real users. | Treat the extra setup and cleanup in development as a test; fix what it shows with a cleanup, never with a ref guard or by turning Strict Mode off. |
| **Principle 5** | **The Buy Click Sends the Order, Not an Effect** | A purchase sent from an Effect goes out twice in development, and again each time the user comes back to the page. | Put work caused by a specific click in that click's event handler; keep Effects for work caused by the component being on the screen. |

## 1. Principle 1: useEffect Starts the Timer After the Commit

### The box that must get the cursor when it appears

Lesson 31 left one job open: putting the cursor in a box the moment the box appears. Here is the same line in two places. In the body of the component, it blanks the page:

```jsx title="The call to focus in the body of the component"
function MyComponent() {
  const inputRef = useRef(null);
  ~inputRef.current.focus();~ // **WRONG:** runs during rendering, while current is still null
  return <input ref={inputRef} />;
}
```

Inside `useEffect`, the box gets the cursor:

```jsx title="The same call to focus inside useEffect"
import { useEffect, useRef } from 'react';

function MyComponent() {
  const inputRef = useRef(null);
  ~useEffect~(() => { // React runs this function after the box is on the page
    inputRef.current.focus(); // The box gets the cursor
  });
  return <input ref={inputRef} />;
}
```

It may look the same, or work the same at first, but it is NOT the same thing! The line is the same. The moment it runs is not. In the body, the line runs while React renders `MyComponent`, before React has created the box, so `inputRef.current` is still `null`, as Lesson 31 showed. Inside `useEffect`, the line runs after the commit, when the box is already in the DOM. The docs sum it up: "**`useEffect` "delays" a piece of code from running until that render is reflected on the screen.**"

```page width=text caption="With the call to focus inside useEffect, the cursor is in the box when the page opens."
form:
  field:  |  | good
console: quiet
```

### What useEffect is

`useEffect` is a Hook, like `useState`, and we import it from `react`. Its first argument is a function. The docs call it the **setup function**: "The function with your Effect's logic". Our code creates this function during the render and hands it to React. React keeps it and calls it after the commit. Our code never calls it.

```tree dir=right caption="How the function inside useEffect gets from our component to the moment React runs it."
How React runs the setup function
- +1. Render [`useEffect`] | React calls the component; our code **hands React the setup function** | Nothing runs yet
- +2. Commit [`<input>`] | React puts the box **into the DOM** | `inputRef.current` now holds the box
- +3. After the commit [`inputRef.current.focus`] | React **calls the setup function** | The box gets the cursor
```

React's docs write Effect with a capital E for this React meaning: a side effect caused by rendering. The external system here is the browser's focus, which React does not control. The docs' word for what an Effect does with it is **synchronize**: the Effect keeps the external system in step with the component while the component is on the screen. For the box, that means one thing: when the box appears, it has the cursor.

### The timer in the body of Counter

Back to our counter. A developer starts the timer in the body of `Counter`, right above the `return`. `onTick` is the function the timer calls every second, and the updater `c => c + 1` from Lesson 16 adds one to the latest count:

```jsx title="src/components/Counter.jsx" bad="10"
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  function onTick() {
    console.log('Tick');
    setCount(c => c + 1);
  }
  ~setInterval(onTick, 1000);~ // **WRONG:** runs during every render, so every render starts one more timer

  return <h1>{count}</h1>;
}
```

The user clicks the show button. The number starts to climb, and then it climbs faster and faster, and the Console prints more `Tick` lines every second. Here is why:
1. React calls `Counter` for the first render. The body calls `setInterval`, and one timer starts.
2. In development, `<StrictMode>` calls the body twice, as Lesson 14 showed, so a second timer starts.
3. A second later, a timer calls `onTick`. The setter asks for a render, and React calls `Counter` again.
4. The body calls `setInterval` again, and more timers start.
5. Every render adds timers, and every timer asks for more renders.

Starting a timer is a side effect, so it does not belong in the rendering code. The docs say the same of a chat connection: connecting to a server is not a pure calculation, it is a side effect, so it cannot happen during rendering. And they state the rule in four words: "Rendering code must be pure."

The same mistake hits a live comments feed. A developer subscribes to the feed in the body of the component. Each change of state renders the component again, and each render opens one more subscription. After six renders, the page holds six subscriptions to the same feed.

### Moving the timer into useEffect

So we move the timer into `useEffect`, and add a line to the Console each time the Effect starts a timer:

```jsx title="src/components/Counter.jsx" startLine="1"
import { useState, ~useEffect~ } from 'react'; // useEffect comes from react, like useState

export default function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    function onTick() {
      console.log('Tick');
      setCount(c => c + 1);
    }
    console.log('Timer started');
    ~setInterval(onTick, 1000);~ // Runs after the commit, not during rendering
  });

  return <h1>{count}</h1>;
}
```

The user clicks the show button, and the number still climbs faster and faster. The Console now prints `Timer started` after every `Tick`. Moving the timer out of the body was right, but it was not enough:
1. React commits the first render and runs the Effect. `Timer started` appears, and a timer starts.
2. A second later, the timer calls `onTick`. `count` changes, and React renders and commits again.
3. With no second argument, React runs the Effect after every commit. The docs: "By default, your Effect will run after every commit."
4. So every tick starts one more timer, and the timers pile up as before.

```page width=text caption="The counter with useEffect and no second argument: the Console shows Timer started after the ticks."
line: [Hide counter]
heading: 2
log: Timer started | Counter.jsx:11
log: Timer started | Counter.jsx:11
log: Tick | Counter.jsx:8
log: Timer started | Counter.jsx:11
log: Tick | Counter.jsx:8
log: Timer started | Counter.jsx:11
```

The first two `Timer started` lines come from the extra run in development that Principle 3 explains. The second argument of `useEffect` decides when React runs the Effect again, and Principle 2 adds it.

> [!PRINCIPLE]
> **Principle 1: Effects: useEffect Starts the Timer After the Commit**
>
> *Code that must run because the component is on the screen goes inside `useEffect`; React runs it after the commit, while the body of the component runs during every render and must only calculate the JSX.*
>
> A timer, a subscription, or a call to `focus` written in the body runs during rendering. On the first render, the DOM is not there yet, and every later render starts the side effect again. Inside `useEffect`, our code hands React a setup function, and React calls it after the commit, when the page is already on the screen.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   ~setInterval(onTick, 1000);~ // After the commit: the counter is on the page
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Counter() {
>   ~setInterval(onTick, 1000);~ // **WRONG:** in the body, every render starts one more timer
>   return <h1>{count}</h1>;
> }
> ```

## 2. Principle 2: [] Starts the Timer Only on Mount

### Three ways to write the second argument

`useEffect` takes a second argument: an array. The docs show three ways to write it:

```jsx title="Three ways to write the second argument of useEffect"
useEffect(() => { /* ... */ }); // No array: "This runs after every render"
useEffect(() => { /* ... */ }, ~[]~); // Empty array: "This runs only on mount (when the component appears)"
useEffect(() => { /* ... */ }, ~[a, b]~); // "This runs on mount *and also* if either a or b have changed since the last render"
```

It may look the same, or work the same at first, but it is NOT the same thing! No array and an empty array differ by two characters. The docs say it directly: "The behaviors without the dependency array and with an *empty* `[]` dependency array are different." With no array, the Effect runs after every commit. With `[]`, it runs after the first commit only, when the component mounts.

```tree caption="When React runs the Effect, for each way of writing the second argument."
The second argument of `useEffect`
- !No array [`useEffect`] | Runs after **every commit** | Our counter starts **a new timer on every tick**
- +Empty array [`[]`] | Runs after the **first commit only**, on mount | Our counter starts **one timer** when it appears
- +Array with values [`[a, b]`] | Runs on mount, and after any commit where **`a` or `b` changed** | React compares each value with the one from the last render
```

### What the array lists

The array is called the **dependency array**, and the values in it are the **dependencies**. In the docs' words, it is "The list of all reactive values referenced inside of the `setup` code": every prop, state variable, or other value from the component that the Effect reads. Lesson 35 covers reactive values in full.

The key idea is that we do not pick these values. The docs: "you can't "choose" your dependencies." They are decided by the code inside the Effect. After each commit, React compares each dependency with its value from the last render, using `Object.is`, the same check React uses on a setter's value. React skips the Effect only if all the dependencies have exactly the same values.

The docs show this with a video player. Its Effect plays or pauses the video depending on the `isPlaying` prop:

```jsx title="The docs' VideoPlayer: the Effect reads isPlaying, so isPlaying is in the array"
useEffect(() => {
  if (isPlaying) {
    ref.current.play();
  } else {
    ref.current.pause();
  }
}, ~[isPlaying]~); // The Effect reads isPlaying, so it runs again whenever isPlaying changes
```

With `[]` instead, the Effect would never see a new `isPlaying`. A **linter**, a tool that reads our code before it runs, catches this. Its `exhaustive-deps` rule checks that every dependency is listed, and the docs show its message: `React Hook useEffect has a missing dependency: 'isPlaying'`.

### The counter with []

Our Effect reads no props and no state. The updater `c => c + 1` gets the latest count from React, as Lesson 16 showed, so the Effect never reads `count` itself. The docs: "The code inside the Effect does not use any props or state, so your dependency array is `[]`." So we add `[]`:

```jsx title="src/components/Counter.jsx" startLine="6"
  useEffect(() => {
    function onTick() {
      console.log('Tick');
      setCount(c => c + 1);
    }
    console.log('Timer started');
    setInterval(onTick, 1000);
  }, ~[]~); // Runs only after the first commit, when Counter mounts
```

The timers no longer pile up on every tick. But in development, the number goes up by two every second:
1. The user clicks the show button.
2. React mounts `Counter` and runs the Effect. `Timer started` appears, and one timer starts.
3. In development, React mounts the counter a second time at once and runs the Effect again. `Timer started` appears a second time, and a second timer starts.
4. No line of our code stopped the first timer, so two timers call `onTick` every second.

```page width=text caption="The counter with [] in development, three seconds after the user clicks Show counter: two timers, so the number goes up by two."
line: [Hide counter]
heading: 6
log: Timer started | Counter.jsx:11
log: Timer started | Counter.jsx:11
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
```

This is the docs' own Challenge: "instead of incrementing once per second, it increments twice." In production, the Effect runs once, and the number goes up by one. Principle 3 explains the second run, and the line that makes the page right in both.

### count + 1 and c => c + 1 inside the Effect

The updater is what makes `[]` honest here. Compare two ways to add one inside the Effect:

```jsx title="Adding one with count + 1, and with the updater c => c + 1"
setCount(~count + 1~); // Reads count, so count must be in the array
setCount(~c => c + 1~); // Reads no state, so [] is honest
```

It may look the same, or work the same at first, but it is NOT the same thing! Both add one on the first tick. With `count + 1`, the Effect reads `count`, so `count` is a dependency. With the updater, the Effect reads no state at all, and `[]` tells React the truth. The `useEffect` reference says: "Now that you're passing `c => c + 1` instead of `count + 1`, your Effect no longer needs to depend on `count`."

A common mistake starts from `count + 1` with `[]`:
1. A developer writes `count + 1` inside the setter, in an Effect with `[]`.
2. The linter reports that `count` is missing, in the same words the docs show for `isPlaying`.
3. The developer turns the lint rule off for that line.
4. The Effect keeps the `count` of the first render, `0`, because each render keeps its own values, as Lesson 15 showed. Every second, it sets `count` to `1`.
5. The page stops at `1`.

The docs: "By suppressing the linter, you "lie" to React about the values your Effect depends on." Putting `count` in the array also works, but then the Effect runs again on every change of `count`, and the reference warns that "specifying `count` as a dependency always resets the interval." The updater is the clean fix.

> [!PRINCIPLE]
> **Principle 2: Dependencies: [] Starts the Timer Only on Mount**
>
> *The second argument of `useEffect` lists every value from the component that the Effect reads; with no array the Effect runs after every commit, with `[]` only after the first commit, and with `[a, b]` also after any commit where `a` or `b` changed.*
>
> The code inside the Effect decides the dependencies, and the `exhaustive-deps` lint rule checks them. An Effect that reads no props and no state, such as a timer that adds one with the updater `c => c + 1`, has the empty array `[]` and runs only on mount. Turning the lint rule off hides a missing dependency, and the Effect keeps the values of an old render.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const intervalId = setInterval(() => setCount(c => c + 1), 1000);
>   return () => clearInterval(intervalId);
> }, ~[]~); // Reads no state, so the array is empty and the Effect runs on mount
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const intervalId = setInterval(() => setCount(count + 1), 1000);
>   return () => clearInterval(intervalId);
> }, ~[]~); // **WRONG:** reads count but leaves it out, so the page stops at 1
> ```

## 3. Principle 3: The Cleanup Function Stops the Hidden Counter's Timer

### The setup returns a function that stops the timer

`setInterval` returns an interval ID, and `clearInterval` with that ID stops the timer, as Lesson 30 showed. Inside an Effect, the setup function can return a second function. React calls it when the timer must stop:

```jsx title="The setup returns the function that stops its timer"
useEffect(() => {
  const intervalId = ~setInterval(onTick, 1000)~; // The setup starts the timer
  return ~() => clearInterval(intervalId)~; // The cleanup stops that same timer
}, []);
```

This returned function is the **cleanup function**. Our code writes it, and React calls it. The docs: "React will call your cleanup function each time before the Effect runs again, and one final time when the component unmounts". A component **unmounts** when it is removed from the page. Here, that happens when the user clicks the hide button: `show` becomes `false`, and `{show && <Counter />}` gives nothing.

It is the light in the room from the start of this lecture. Our setup started the timer, so our cleanup stops it. The docs list the usual pairs: ""connect" needs "disconnect", "subscribe" needs "unsubscribe", and "fetch" needs either "cancel" or "ignore"." On our page, `setInterval` needs `clearInterval`.

```tree caption="Each setup that starts something outside React, paired with the cleanup that stops it."
What the setup starts, and what the cleanup stops
- +A timer [`setInterval` `clearInterval`] | The setup **starts** the timer | The cleanup **stops** it with the same interval ID
- +An event listener [`addEventListener` `removeEventListener`] | The setup **adds** the listener to `window` | The cleanup **removes** the same listener
- +A chat connection [`connect` `disconnect`] | The setup **connects** to the chat server | The cleanup **disconnects**
```

### Hiding the counter does not stop its timer

The counter with `[]` from Principle 2 has no cleanup. When the user hides it, the number disappears, and it looks as if everything stopped. It may look the same, but it is NOT the same thing! The `<h1>` is gone, and the timer is still running:
1. The counter is on the page, and a timer calls `onTick` every second.
2. The user clicks the hide button. React removes the `<h1>`.
3. Nothing calls `clearInterval`, so the timer still calls `onTick`, and the Console still prints `Tick` every second.
4. The user clicks the show button. A new counter starts from `0`, because a component removed from the page loses its state, as Lesson 25 showed. A new timer starts too.
5. Now one more timer prints `Tick`, and each click on the show button adds another.

```page width=text caption="The counter with [] and no cleanup, after the user clicks Hide counter: no number on the page, and the Console still prints Tick."
line: [Show counter]
log: Timer started | Counter.jsx:11
log: Timer started | Counter.jsx:11
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
log: Tick | Counter.jsx:8
```

The docs tell the same story with a chat page. A `ChatRoom` connects to the chat server in an Effect with `[]` and no cleanup. The user opens the chat page, and the component connects. The user goes to the Settings page, the component unmounts, and the connection stays open. The user clicks Back, and the component opens a second connection. "As the user navigates across the app, the connections would keep piling up." The fix is one line in the Effect: a cleanup that calls `connection.disconnect`.

### The cleanup in Counter

We keep the interval ID and return a cleanup that stops the timer, with a line in the Console:

```jsx title="src/components/Counter.jsx" startLine="6" good="12,13,14,15,16"
  useEffect(() => {
    function onTick() {
      console.log('Tick');
      setCount(c => c + 1);
    }
    console.log('Timer started');
    const ~intervalId~ = setInterval(onTick, 1000); // Keeps the ID of the timer this setup started
    return () => {
      console.log('Timer stopped');
      ~clearInterval(intervalId);~ // Stops that same timer
    };
  }, []);
```

The user clicks the show button, and in development the number goes up by one every second, even though the setup runs twice. In development, React **remounts** every component once, right after it first mounts: it removes the component and mounts it again at once. The docs: React "remounts every component once immediately after its initial mount." Here is the order:
1. React mounts `Counter` and runs the setup. `Timer started` appears, and the first timer starts.
2. React remounts the counter. First, it calls the cleanup. `Timer stopped` appears, and the first timer stops.
3. Then it runs the setup again. `Timer started` appears, and one timer runs.

The docs' chat follows the same order in its Console: connecting, disconnected, connecting. And they give the result for the counter: "The user-visible behavior in both cases is the same: the counter increments once per second."

Then the user clicks the hide button. React unmounts `Counter` and calls the cleanup one final time. `Timer stopped` appears, and no `Tick` follows:


```dom caption="The Elements panel after the user clicks Hide counter: only the button is left inside main."
</main>
```

The cleanup knows which timer to stop because it is created inside the setup, so it sees the `intervalId` of that same run of the setup. Each run of the setup has its own `intervalId`, and its own cleanup that stops it.

When the Effect runs again because a dependency changed, React follows the same order: first the cleanup, with the old props and state, then the setup, with the new ones. Lesson 35 walks through that in full. Some Effects need no cleanup at all. The docs' example is a map widget whose zoom is set to the same value twice: calling it twice with the same value "does not do anything".

> [!PRINCIPLE]
> **Principle 3: Cleanup: The Cleanup Function Stops the Hidden Counter's Timer**
>
> *The function that the setup returns is the cleanup function; React calls it before the Effect runs again and one final time when the component unmounts, so it must stop or undo what the setup started.*
>
> When a component leaves the page, React removes the DOM nodes it created from our JSX. It does not stop a timer, a listener, or a connection that our setup started, because React did not start them. The cleanup stops them: `clearInterval` for `setInterval`, `removeEventListener` for `addEventListener`, and `disconnect` for `connect`.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const intervalId = setInterval(onTick, 1000);
>   ~return () => clearInterval(intervalId);~ // The cleanup stops the timer this setup started
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~setInterval(onTick, 1000);~ // **WRONG:** no cleanup, so the timer runs on after the counter is hidden
> }, []);
> ```

## 4. Principle 4: A Ref Guard Leaves the Timer Running

### Two ways to see Timer started only once

A developer sees `Timer started` twice in development and wants to see it once. There are two ways to get the counter going up by one. The first is a ref that remembers that the setup already ran, with `useRef` from Lesson 30. The docs call it a **ref guard**:

```jsx title="A ref guard that blocks the second run of the setup"
const startedRef = useRef(false);

useEffect(() => {
  ~if (startedRef.current) return;~ // The second run stops here
  startedRef.current = true;
  setInterval(onTick, 1000);
}, []);
```

The second is the cleanup from Principle 3:

```jsx title="A cleanup that stops the first timer before the second run"
useEffect(() => {
  const intervalId = setInterval(onTick, 1000);
  ~return () => clearInterval(intervalId);~ // Stops the timer before the next setup
}, []);
```

It may look the same, or work the same at first, but it is NOT the same thing! In development, both counters go up by one every second. With the ref guard, `Timer started` even appears only once. But the ref guard never stops a timer, so the bug that the extra run was meant to show is still there. The docs say of the same guard on the chat page that it makes the connecting line print only once in development, "but it doesn't fix the bug."

### The page looks fixed, and the timers still pile up

Here is `Counter` with the ref guard and no cleanup:

```jsx title="src/components/Counter.jsx" startLine="1" bad="8,9"
import { useState, useEffect, useRef } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);
  const startedRef = useRef(false);

  useEffect(() => {
    ~if (startedRef.current) return;~ // **WRONG:** blocks the second run instead of cleaning up the first
    startedRef.current = true;
    function onTick() {
      console.log('Tick');
      setCount(c => c + 1);
    }
    console.log('Timer started');
    setInterval(onTick, 1000);
  }, []);

  return <h1>{count}</h1>;
}
```

The page looks fixed, and the timers still pile up:
1. The user clicks the show button. The setup runs, `startedRef.current` becomes `true`, and one timer starts.
2. React remounts the counter in development. There is no cleanup to call. During this remount, React keeps the state and the refs: in the docs' words, "state and DOM are preserved". So the setup runs again, finds `startedRef.current` already `true`, and returns at once.
3. The number goes up by one every second, and `Timer started` appears once.
4. The user clicks the hide button. Nothing stops the timer, and `Tick` goes on in the Console.
5. The user clicks the show button again. This is a new `Counter`, with a new `startedRef` that starts at `false`, so a second timer starts.

```page width=text caption="The counter with a ref guard, after the user clicks Hide counter and then Show counter: two timers print Tick each second."
line: [Hide counter]
heading: 2
log: Timer started | Counter.jsx:14
log: Tick | Counter.jsx:11
log: Tick | Counter.jsx:11
log: Timer started | Counter.jsx:14
log: Tick | Counter.jsx:11
log: Tick | Counter.jsx:11
log: Tick | Counter.jsx:11
log: Tick | Counter.jsx:11
```

The docs: "the connections would keep piling up, the same as it would before the "fix"." In production there is no extra run, but users leave the page and come back, and each visit adds one more timer.

### The extra run is a test

The extra setup and cleanup in development is a test React does on purpose. The `useEffect` reference calls it a **stress-test**: "This is a stress-test that verifies your Effect's logic is implemented correctly." It shows, at once and on our own screen, the bug that users would meet later. The docs' Challenge on the interval says: "React's behavior is not the *cause* of the bug: the bug already exists in the code. React's behavior makes the bug more noticeable."

So the docs ask us to change the question: "**The right question isn't "how to run an Effect once", but "how to fix my Effect so that it works after remounting".**" The answer is a cleanup that makes setup, cleanup, setup look exactly like one setup to the user. With the cleanup from Principle 3, the user sees one step per second in development and in production.

Turning off `<StrictMode>` hides the test the same way the ref guard does. The docs: "You can turn off Strict Mode to opt out of the development behavior, but we recommend keeping it on." Lesson 47 covers Strict Mode in full.

> [!PRINCIPLE]
> **Principle 4: Strict Mode: A Ref Guard Leaves the Timer Running**
>
> *In development, Strict Mode runs one extra setup and cleanup before the real setup to test the cleanup; the fix for a problem it shows is a cleanup function, never a ref that stops the Effect from running twice.*
>
> A ref guard makes the Console show `Timer started` once and the counter go up by one, so the page looks fixed. But no code stops the timer, so it runs on after the user hides the counter, and each new mount adds one more. The cleanup fixes the Effect itself, so the user cannot tell one setup from setup, cleanup, setup.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const intervalId = setInterval(onTick, 1000);
>   ~return () => clearInterval(intervalId);~ // Works after the remount: the old timer is stopped
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~if (startedRef.current) return;~ // **WRONG:** hides the second run, and the timer never stops
>   startedRef.current = true;
>   setInterval(onTick, 1000);
> }, []);
> ```

## 5. Principle 5: The Buy Click Sends the Order, Not an Effect

### Two timers started for two different reasons

Here are the two timers from the start of this lecture, side by side. The stopwatch from Lesson 30 starts its timer in a click handler:

```jsx title="Lesson 30's stopwatch: the timer starts in the Start click handler"
function handleStart() {
  intervalRef.current = ~setInterval(tick, 10)~; // Starts because the user clicked Start
}

<button onClick={handleStart}>Start</button>
```

Our counter starts its timer in an Effect:

```jsx title="This lesson's counter: the timer starts in an Effect"
useEffect(() => {
  const intervalId = ~setInterval(onTick, 1000)~; // Starts because the counter appeared on the page
  return () => clearInterval(intervalId);
}, []);
```

It may look the same, or work the same at first, but it is NOT the same thing! Both are right, for different causes. The stopwatch starts because the user clicked Start, and the Stop click stops it. The counter starts because it appeared on the page, and its cleanup stops it. The docs draw the same line on the chat page: "Sending a message in the chat is an *event* because it is directly caused by the user clicking a specific button. However, setting up a server connection is an *Effect* because it should happen no matter which interaction caused the component to appear."

So the question to ask is what causes the work. A click causes a purchase. Being on the screen causes a connection.

### Buying a product in an Effect

The docs show what goes wrong when a click's work moves into an Effect. A developer sends the purchase from an Effect on the order page, with `fetch`, which Lesson 33 teaches:

```jsx title="Sending the purchase from an Effect"
useEffect(() => {
  ~fetch('/api/buy', { method: 'POST' });~ // **WRONG:** sends a purchase every time the page appears
}, []);
```

The purchase goes out twice in development:
1. The order page appears, and React runs the Effect. One purchase request goes out.
2. React remounts the page in development and runs the Effect again. A second purchase request goes out.
3. No cleanup can take back a purchase.

The docs: "This Effect fires twice in development, exposing a problem in the code." In production the same thing happens another way: "What if the user goes to another page and then presses Back? Your Effect would run again." A visit to a page is not a purchase.

The fix is to send the purchase from the Buy button's handler:

```jsx title="Sending the purchase from the Buy click handler"
function handleClick() {
  ~fetch('/api/buy', { method: 'POST' });~ // Sends one purchase, only when the user clicks Buy
}

<button onClick={handleClick}>Buy</button>
```

The docs: "**Delete the Effect and move your `/api/buy` request into the Buy button event handler**".

### Where each kind of code goes

Here is where code that does something goes, by what causes it:

| What causes the work | Where the code goes | Example |
| :--- | :--- | :--- |
| **A specific action by the user** | The event handler of that action | The stopwatch's Start click, the Buy click |
| **The component being on the screen** | `useEffect`, with a cleanup that stops what the setup started | Our counter's timer, a chat connection, a listener on `window` |
| **The app starting** | Code outside any component, which runs once | Logic that should only run once when the application starts |
| **Nothing outside React** | No Effect at all | Changing one state from another state, which Lesson 34 covers |

Starting the counter's timer in the handler of the show button would be fragile: the counter can leave the page in many ways, and each one would need its own call to `clearInterval`. The Effect ties the timer to the counter itself: it starts when the counter mounts, whatever made it appear, and stops when the counter unmounts.

> [!PRINCIPLE]
> **Principle 5: Events: The Buy Click Sends the Order, Not an Effect**
>
> *Work caused by a specific user action, such as buying, goes in the event handler of that action; an Effect is only for work caused by the component being on the screen.*
>
> An Effect runs every time the component appears: twice in development, and again whenever the user comes back to the page. That is right for a timer or a connection, which the cleanup stops. It is wrong for a purchase, which no cleanup can take back. Ask what causes the work: a click, or being on the screen.
>
> **DO THIS:**
> ```jsx
> function handleClick() {
>   ~fetch('/api/buy', { method: 'POST' });~ // One purchase, when the user clicks Buy
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~fetch('/api/buy', { method: 'POST' });~ // **WRONG:** sends a purchase each time the page appears
> }, []);
> ```

### The complete seconds counter project

Here are the three files of our finished counter. The entry file mounts `App` inside `<StrictMode>`:

```jsx title="src/main.jsx"

import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
```

`App` shows and hides the counter:

```jsx title="src/App.jsx"
import { useState } from 'react';
import Counter from './components/Counter.jsx';

export default function App() {
  const [show, setShow] = useState(false);

  return (
    <main>
      <button ~onClick={() => setShow(!show)}~> {/* Principle 5: a click changes state, it starts no timer */}
        {show ? 'Hide' : 'Show'} counter
      </button>
      ~{show && <Counter />}~ {/* Principle 3: Counter mounts and unmounts with show */}
    </main>
  );
}
```

`Counter` starts its timer in an Effect and stops it in the cleanup:

```jsx title="src/components/Counter.jsx"
import { useState, useEffect } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  ~useEffect~(() => { // Principle 1: React runs the setup after the commit
    function onTick() {
      console.log('Tick');
      setCount(c => c + 1);
    }
    console.log('Timer started');
    const intervalId = setInterval(onTick, 1000);
    return () => {
      console.log('Timer stopped');
      ~clearInterval(intervalId);~ // Principles 3 and 4: stops this timer on remount and on unmount
    };
  }, ~[]~); // Principle 2: reads no state, so the Effect runs only on mount

  return <h1>{count}</h1>;
}
```

### How React calls the components and runs the Effect

When the user clicks the show button, React calls `App`, then `Counter`, and commits the `<h1>`. Only then does it run the Effect. When the user hides the counter, React removes the `<h1>` and calls the cleanup:

```tree dir=right caption="The order in which React renders the components, commits the page, and runs the setup and the cleanup of the Effect."
From the click on Show counter to the click on Hide counter
- +1. Render [`App` `Counter`] | React calls `App`, then `Counter` | `Counter` **hands React the setup function**
- +2. Commit [`<h1>0</h1>`] | React puts the number **into the DOM** | The user sees `0`
- +3. Setup [`setInterval`] | React runs the setup **after the commit** | **One timer** starts; in development, after a cleanup and a second setup
- +4. Unmount [`clearInterval`] | The user hides the counter; React **removes the `<h1>`** | React calls **the cleanup**, and the timer stops
```

| Where the timer starts | What the user sees | Why |
| :--- | :--- | :--- |
| **In the body of `Counter`** | The number climbs faster and faster | Every render starts one more timer |
| **In `useEffect` with no array** | The number still climbs faster and faster | The Effect runs after every commit, so every tick starts a timer |
| **In `useEffect` with `[]` and no cleanup** | The number goes up by two in development, and the timer runs on after the user hides the counter | Nothing stops the first timer before the second setup, or when the counter unmounts |
| **With a ref guard and no cleanup** | The number goes up by one, and timers pile up after each hide and show | The guard blocks the second setup, and nothing ever stops a timer |
| **In `useEffect` with `[]` and a cleanup** | The number goes up by one, and stops when the user hides the counter | React calls the cleanup before each new setup and when the counter unmounts |

## For the Interview

> **The Interview Question:** How do you connect a component to an external system, and how do you disconnect it?

### How to Answer Clearly in 30 Seconds

"With an Effect. An external system is anything React does not control, such as a timer, a listener on `window`, or a chat server. I call `useEffect` at the top level of the component and pass it a setup function that connects, for example by calling `setInterval`. React runs it after the commit, never during rendering, because rendering must stay pure. The setup returns a cleanup function that disconnects, here `clearInterval` with the interval ID. Three rules keep it right:
1. **The dependency array lists what the Effect reads**: no array runs it after every commit, `[]` only on mount, and `[a, b]` also when `a` or `b` changed. The `exhaustive-deps` lint rule checks the list, and I never turn it off.
2. **The cleanup undoes the setup**: React calls it before the Effect runs again and one final time when the component unmounts. Without it, the timer runs on and connections pile up.
3. **Only work caused by being on the screen**: a purchase caused by a click goes in the click handler, not in an Effect."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does my Effect run twice in development, and how do I make it run once?"**
   In development, Strict Mode remounts every component once right after it first mounts, so React runs setup, cleanup, setup. The `useEffect` reference calls it "a stress-test that verifies your Effect's logic is implemented correctly." The docs say the right question is not how to run an Effect once, but how to fix the Effect so it works after remounting. The fix is a cleanup, so that the user cannot tell one setup from setup, cleanup, setup. A ref guard or turning off `<StrictMode>` only hides the test, and the bug stays for users who leave the page and come back. In production there is no extra run. Lesson 47 covers Strict Mode in full.
2. **"Can I leave a value out of the dependency array to stop the Effect from running again?"**
   No. The docs: "you can't "choose" your dependencies." The code inside the Effect decides them, and suppressing the linter means you "lie" to React, so the Effect keeps the values of an old render. For our counter, `count + 1` with `[]` stops the page at `1`. The fix is to change the code so it no longer reads the value, such as the updater `c => c + 1`. A `ref` from `useRef` and a setter from `useState` have a stable identity, so they can stay out: "If the linter lets you omit a dependency without errors, it is safe to do." Lesson 36 shows `useEffectEvent`, and Lesson 37 removes object and function dependencies.
3. **"Does an Effect run before or after the browser paints the screen?"**
   After the commit, and usually after the paint. The `useEffect` Caveats say that when the Effect was not caused by a click, "React will generally let the browser **paint the updated screen first before running your Effect.**" When it was caused by a click, "React may run your Effect before the browser paints the updated screen". When the work must happen before the paint, for example to measure a tooltip before the user sees it in the wrong place, the tool is `useLayoutEffect`, which Lesson 49 teaches. Effects also never run during server rendering, as Lesson 102 shows.

```tree dir=right caption="Interview comparison: where code that does something goes, by what causes it."
What causes the work in an interview
- +A click by the user [`onClick={handleClick}`] | The **event handler** runs once per click | A purchase, a message sent in the chat
- +The component being on the screen [`useEffect`] | The **setup** connects after the commit; the **cleanup** disconnects | A timer, a chat connection, a listener on `window`
- !Rendering code [the body of the component] | Runs on **every render** | Must only **calculate**; a timer here starts again on every render
```
