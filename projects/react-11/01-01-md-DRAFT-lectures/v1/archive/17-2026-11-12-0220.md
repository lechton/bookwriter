## How We Update an Object Held in State

### Changing a field inside the state object vs. passing a brand-new object to the setter

When state holds a number like zero, calling `setX` with `5` never changes the number zero from the inside. Numbers, strings, and true or false values cannot be changed from inside in JavaScript. Calling `setX` simply replaces the old number with `5`:

```jsx title="Replacing a number in state"
const [x, setX] = useState(0);

function handleClick() {
  ~setX(5);~ // Replaces 0 with 5: the number 0 itself never changed
}
```

Now suppose `useState` holds a JavaScript **object** instead of a number, with its `name` property set to John. When the user clicks a button to change that name to `'Alice'`, compare two ways you might write the click handler:

```jsx title="Way 1: Changing user.name inside the existing object"
const [user, setUser] = useState({ name: 'John' });

function handleClick() {
  ~user.name = 'Alice';~ // 1. Changes the name property inside the existing user object
  ~setUser(user);~ // 2. Hands that exact same user object back to React -> page stays on "John"!
}
```

Now compare Way 1 with building a brand-new object and handing that new object to `setUser`:

```jsx title="Way 2: Passing a brand-new object to setUser"
const [user, setUser] = useState({ name: 'John' });

function handleClick() {
  ~setUser({ name: 'Alice' });~ // Creates a brand-new object and hands it to React -> page shows "Alice"!
}
```

When you click the button in Way 1, the screen stays stuck on **`John`**. When you click the button in Way 2, the screen updates to **`Alice`**!

Look at the three silent confusions that trip developers up here:
- **First, changing `user.name` and passing `user` back to the setter looks like passing a new object, and both objects hold `'Alice'`, but they are NOT the same thing!** Way 1 hands React the exact same object it already holds in state. Way 2 hands React a brand-new object.
- **Second, because `setUser` runs without any error in the Console, it looks as if the update worked, but it did NOT reach the screen!** React compared the object you passed with the object already in state, saw that both were the very same object, and skipped the render.
- **Third, when an object has several fields, spreading the old object with `...user` and typing every unchanged field by hand into a new object are the exact same thing!** Both build a brand-new object with every old field kept and one field changed.

Look at the three words you will hear in every React team and interview:
- **What is a "mutation"?** In everyday life, a **mutation** means a living thing changes from the inside while staying the same creature, like a caterpillar that becomes a butterfly. In JavaScript, changing a property inside an existing object, such as changing `user.name` in place, is a **mutation**. Its contents changed, yet it is still the exact same object.
- **Why does React ignore a mutated object?** Imagine returning a library book after rewriting one page inside it. The librarian scans the barcode on the cover, sees the exact same book that was already checked in, and files nothing new. React checks the box with `Object.is`, scanning the barcode on the outside rather than reading the fields inside. Handing React a brand-new object gives it a new barcode, so React renders the page again.
- **What does "read-only" mean?** Think of a printed store receipt. You can read every line on the receipt, and you never scribble over the ink to change the total. When the order changes, the cashier prints a brand-new receipt. Treating state as **read-only** means we read from the object in state and replace it with a new object whenever a field changes:

```tree caption="What happens when you mutate the existing state object vs. when you pass a brand-new object to the setter."
Two ways to update `user` in state
- !Way 1: Mutate `user.name` and pass `user` back | Changes the field inside the **same object** | `Object.is` sees the **same object** and **skips the render**
- +Way 2: Pass a brand-new object `{ name: 'Alice' }` | Creates a **new object** with the updated field | `Object.is` sees a **different object** and **re-renders the page**
```

### Four ways to pass a new object to a state setter

Whenever you update an object in state, your goal is always to hand the setter a brand-new object. Depending on the shape of your object and how your handler runs, there are four ways to build that new object:

```jsx title="Four ways to build a new object for a state setter"
function OrderWays() {
  const [order, setOrder] = useState({ item: 'Coffee mug', quantity: 1, giftWrap: false });

  function handleByHand() {
    ~setOrder({ item: order.item, quantity: order.quantity + 1, giftWrap: order.giftWrap });~ // 1. Every field written by hand
  }

  function handleSpread() {
    ~setOrder({ ...order, quantity: order.quantity + 1 });~ // 2. Object spread ... copies all fields, then updates quantity
  }

  function handleQueued() {
    ~setOrder(o => ({ ...o, quantity: o.quantity + 1 }));~ // 3. Spread inside an updater when queueing multiple updates
  }
}
```

Here is when each of the four ways fits in daily coding:
1. **Way 1, writing every field of the new object by hand**: Fits when the object only has one or two fields, or when every field is built fresh on the spot, such as pointer coordinates from a mouse event.
2. **Way 2, spreading the old object with `...` and writing the changed field after it**: The normal everyday tool once an object has several fields. When a field sits inside a nested object, you spread once at each level on the path to the change.
3. **Way 3, placing that same spread inside an updater function**: Fits when a single event queues several updates to the same state object before the next render. Notice the parentheses around the new object after the arrow `=>`. In JavaScript, curly braces right after `=>` normally start a function body, so wrapping them in parentheses returns an object literal instead.
4. **Way 4, using the optional library Immer**: When state is deeply nested across many levels, a helper library called **Immer** can simplify the code. It lets you write mutating-looking code on a temporary `draft` object while Immer builds the new copies behind the scenes. Another common choice for deep objects is flattening the state structure itself, which a later lesson covers.

```tree caption="The four ways to produce a new state object in React and when each way fits."
Four ways to give `setOrder` a new object
- +1. Write every field by hand | Best when the object has **only 1 or 2 fields** or is built fresh | Every field is typed out explicitly
- +2. Object spread `{ ...order, field: value }` | Best for **most state objects** in daily coding | Copies top-level fields automatically; spread **once per level** if nested
- +3. Spread inside an updater function | Best when **several updates to `order`** are queued in one event | Wrap the object in **parentheses** after `=>`
- +4. Immer helper library | Optional tool for **deeply nested state** | Records draft changes and builds the nested copies for you
```

### What we bring from earlier lessons and how our project files are organized

This lesson builds on six facts from earlier lessons, along with three small plain JavaScript ideas:
- **State variables and setters**: Calling `useState` stores a value inside React, uses the initial value only on the first render, and returns the current render's **snapshot** along with a setter function.
- **How React skips unchanged state**: When you pass a setter a value, React compares the new value with the current state using `Object.is`. When `Object.is` returns `true`, React skips re-rendering the component and its children.
- **Local mutation vs. mutating existing data**: Changing a brand-new object that you just created inside the running function is a **local mutation** and is completely safe, because no other code points at it yet. Changing an existing object that already lives in state or props is unsafe because other renders or components still share it.
- **Three dots `...` and left-to-right order**: On a JSX tag, `{...article}` opens the `article` object and copies its properties from left to right so the last attribute written wins. Inside an object literal `{ ...order }`, the exact same three dots copy properties into a new object in the exact same left-to-right order.
- **Objects pointing at other objects and shallow copies**: When one object appears inside another object, the outer object actually holds a pointer to a separate inner object. Because `...` copies only the top layer of properties, it is called a **shallow** copy, like shallow water at the surface of a pool.
- **Events, inputs, and computed property names**: React passes an event object `e` to every event handler, where `e.target` is the DOM element where the event started. Inside an object literal, putting square brackets around a variable name, such as `[key]: value`, tells JavaScript to read the property name from that variable.

Our shop project uses four files. In the entry file, React mounts `App` inside `<StrictMode>`. Then our main file renders the `OrderCard` component from the order card file inside the components folder:

```files title="order-card: File Explorer" caption="How the files of our online shop order card sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
```

### Four Principles of Updating Objects in State

**PRINCIPLES:** React never reaches inside your state object to check whether a property changed. Instead, React only checks whether the object you passed to the setter is a different object from the one it already holds. Four practical principles follow from that rule:
1. **Principle 1: Mutating Keeps the Same Object, Replacing Triggers a Render**: Changing a field inside the existing state object and passing that same object back to the setter leaves `Object.is` true, so React skips the render. To update the screen, pass a brand-new object to the setter.
2. **Principle 2: Copy Existing Fields with `...`, Then Write the Changed Field Last**: A state setter replaces the whole object rather than merging fields. Spread the old object first so no field is lost, and write the updated field after the spread so it wins from left to right.
3. **Principle 3: Spread Is Shallow, So Copy Every Level on the Path to a Nested Change**: An inner object is a separate object in memory that the outer object points to. Spreading only the outer object shares the inner object, so a nested change must copy every level from the changed field up to the top object.
4. **Principle 4: Use `[e.target.name]` So One Handler Can Update Several Inputs**: Give each input a `name` attribute that matches its state field. Then one shared handler can use `[e.target.name]` to update whichever field changed.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Same Object vs. New Object** | Mutating a state object and passing it to the setter leaves the screen frozen with zero Console errors, until an unrelated state update suddenly reveals the change. | Treat every object in state as read-only; create a new object with the updated value and pass that new object to the setter. |
| **Principle 2** | **Object Spread and Left-to-Right Order** | Omitting a field from a new state object erases that field on screen, and placing the spread after the changed field overwrites the new value with the old one. | Spread the existing object first and write the updated property after the spread so the new value wins. |
| **Principle 3** | **Shallow Spread vs. Nested Objects** | Spreading only the top object and mutating a nested field silently corrupts earlier snapshots and shared starting objects such as a reset state. | Because spread copies only one level deep, create a new copy of every nested object along the path to the changed field. |
| **Principle 4** | **Computed Property Names for Multiple Inputs** | Copy-pasting separate handlers for form fields leads to mismatched field bugs, and an input whose `name` attribute does not match state refuses to accept typing. | Give each input a `name` attribute matching its top-level state key and update state with `[e.target.name]: e.target.value`. |

## 1. Principle 1: A Mutated Object Is Still the Same Object, So React Skips the Render; a New Object Makes It Render

### Why changing a property inside an object is NOT the same thing as replacing a number

Before we touch our shop files, look at why objects behave differently from numbers in JavaScript.

When a variable holds the number `0`, you cannot open up the number `0` and change its insides. The only way to change a number state is to pass a different number, such as `5`, to the setter.

An object is different. In JavaScript, an object is a container whose properties can be changed from the inside. Compare these two ways of changing `user.name` to `'Alice'`:

```jsx title="Two ways a developer might try to change user.name to 'Alice'"
const [user, setUser] = useState({ name: 'John' });

function handleMutate() {
  ~user.name = 'Alice';~ // Way A: mutates the existing user object in place
  ~setUser(user);~ // Passes that SAME object back to setUser -> screen stays on "John"!
}

function handleReplace() {
  ~setUser({ name: 'Alice' });~ // Way B: passes a BRAND-NEW object to setUser -> screen shows "Alice"!
}
```

Look closely at the three confusions that make Way A such a common trap:
- **First, Way A and Way B look like the same update, and in both cases the object's `name` property holds `'Alice'`, but they are NOT the same thing!** Way A changes the inside of the existing object and hands that same object back to React. Way B builds a brand-new object in memory and hands the new object to React.
- **Second, because passing a new number like `5` to a setter always updates the screen, passing `user` to `setUser` after changing a property looks like it should work the same way, but it is NOT the same thing!** A new number is always a different value, whereas a mutated object is still the exact same object in memory.
- **Third, when `setUser` runs in Way A without throwing any error, it looks as if the setter worked, but it did NOT update the screen!**

To see why React ignores Way A, look at how JavaScript's `Object.is` compares two objects:

```js title="Plain JavaScript: how Object.is compares a mutated object vs. a new object"
const user = { name: 'John' };

user.name = 'Alice';
console.log(~Object.is(user, user)~); // 1. true: still the exact same object in memory!

const nextUser = { name: 'Alice' };
console.log(~Object.is(user, nextUser)~); // 2. false: two separate objects in memory!
```

For two objects, `Object.is` never looks inside the curly braces to compare their properties. It only asks whether both sides are **the very same object in memory**. When you mutate `user.name` and compare the object with itself, `Object.is` returns true. When you compare `user` with the brand-new `nextUser` object, that check returns false:

```tree caption="How Object.is compares a mutated object against itself vs. against a brand-new object."
What `Object.is` checks when you call `setUser`
- !Way A: Mutate `user.name` and pass `user` | Both old state and new value point at **the exact same box** | `Object.is` returns **`true`**, so React **skips the render**
- +Way B: Pass a new object `{ name: 'Alice' }` | Old state and new value are **two separate boxes** in memory | `Object.is` returns **`false`**, so React **renders the component**
```

### Mistake: Mutating the order object and passing the same object back to `setOrder`

Now let us build our online shop order card and watch this bug happen on stage.

First, our main application file imports `OrderCard` from the `components` folder and renders its tag:

```jsx title="src/App.jsx" startLine="1"
import ~OrderCard~ from './components/OrderCard.jsx'; // 1. Import OrderCard from the components folder

export default function App() {
  return <OrderCard />;
}
```

Next, inside the order card file, we store `order` in state with three fields: the item name, the quantity, and gift wrap. Below the state hook, the first handler mutates `order.quantity` in place and passes `order` back to the setter. Meanwhile, the gift wrap handler builds a brand-new object by hand:

```jsx title="src/components/OrderCard.jsx" startLine="1"
import { useState } from 'react';

export default function OrderCard() {
  const [order, setOrder] = useState({
    item: 'Coffee mug',
    quantity: 1,
    giftWrap: false,
  });

  function handleAddOne() {
    ~order.quantity = order.quantity + 1;~ // **WRONG:** mutates the existing order object in place!
    ~setOrder(order);~ // **WRONG:** passes the exact same order object back, so React skips the render!
  }

  function handleGiftWrap() {
    ~setOrder({ item: order.item, quantity: order.quantity, giftWrap: true });~ // Creates a new object
  }
```

Below the two handlers, the component returns the card heading, the three order lines, the `+1` button, and the `Add gift wrap` button:

```jsx title="src/components/OrderCard.jsx" startLine="18"
  return (
    <section className="card">
      <h1>Your Order</h1>
      <p>Item: {order.item}</p>
      <p>Quantity: {order.quantity}</p>
      <p>Gift wrap: {order.giftWrap ? 'Yes' : 'No'}</p>
      <button onClick={handleAddOne}>+1</button>
      <button onClick={handleGiftWrap}>Add gift wrap</button>
    </section>
  );
}
```

Watch what happens step by step when a shopper uses this page:
1. When the page loads, the card displays one coffee mug and `Gift wrap: No`.
2. The shopper clicks `+1`. The card on the screen still says `Quantity: 1`.
3. The shopper clicks `+1` a second time. The card still says `Quantity: 1`, and the Console panel shows zero warnings or errors.
4. Now the shopper clicks `Add gift wrap`.
5. The gift wrap line changes to `Gift wrap: Yes`, and at that exact moment the quantity jumps straight to `Quantity: 3`!

### Why `+1` stayed hidden and why `Add gift wrap` made the quantity jump to `3`

Look closely at `handleAddOne` and `handleGiftWrap` above. Two mysteries stand out right away.

**First, nothing in `handleAddOne` compares the old order with the new one.** Who compares them, and why did two clicks on `+1` leave the screen stuck on `1`?

React compares them inside `setOrder`. Follow what JavaScript and React do on each click of `+1`:
1. The first line of `handleAddOne` reaches inside the existing `order` object and changes its quantity property from one to two. Shorthand operators like `order.quantity++` or `order.quantity += 1` mutate the existing property in the exact same way. And if you mutate `order.quantity` without calling `setOrder` at all, React has no idea the object changed. The official React docs compare that to trying to change your meal order after you have already eaten the meal.
2. The next line calls `setOrder` and passes `order`, which is still that exact same object in memory.
3. React compares the object you passed with the current state using `Object.is`. Because both sides are the very same object, `Object.is` returns `true` and the setter does nothing.
4. React skips re-rendering the card and its children. Even though React may sometimes still call your component function once before skipping its children, it never commits an update to the screen. After two clicks on the plus-one button, the screen still shows `Quantity: 1` while `order.quantity` in memory is already three!

**Second, look at `handleGiftWrap`.** Nothing in `handleGiftWrap` adds anything to the quantity. It only copies `order.quantity` and sets `giftWrap: true`. Why did clicking `Add gift wrap` make the quantity on screen jump to `3`?

JavaScript reads `order.quantity` from the object that the two `+1` clicks already mutated! Follow what happens when the shopper clicks `Add gift wrap`:
1. After the two earlier clicks on the plus-one button, `order.quantity` inside the existing object in memory is already `3`.
2. Calling `handleGiftWrap` creates a brand-new object and copies `order.quantity`, which puts three into the new object.
3. When `setOrder` receives that brand-new object, `Object.is` compares the old object with the new one and returns false.
4. React renders the card again with the new object, putting both `Quantity: 3` and `Gift wrap: Yes` on the screen at once! That is also why mutating state is so treacherous: when another state update happens to run nearby, a mutation can appear to work while hiding a serious bug.

```tree dir=right caption="How two mutating clicks on +1 stay hidden inside the same object until Add gift wrap passes a brand-new object."
Why `Quantity` stayed at `1` and then jumped to `3`
- !1. First and second clicks on `+1` [`order.quantity` becomes `2`, then `3`] | Mutates the **same `order` object** and passes it to `setOrder` | `Object.is` is **`true`**: screen stays on **`Quantity: 1`**
- +2. Click on `Add gift wrap` [builds a **brand-new object**] | Copies `order.quantity`, which is already **`3`**, and sets `giftWrap: true` | `Object.is` is **`false`**: React renders **`Quantity: 3`** and **`Gift wrap: Yes`** together!
```

### Building a brand-new object in `handleAddOne` so React renders every click

Although objects in React state are technically mutable in JavaScript, you should always treat them as if they could not be changed, just like numbers, booleans, and strings. Instead of mutating an object in state, always replace it with a new object.

Passing a brand-new object to `setOrder` tells React two things:
1. Replace `order` with this new object.
2. Render this component again.

Let us fix `handleAddOne` in our order card file so it creates and passes a brand-new object on every click:

```jsx title="src/components/OrderCard.jsx" startLine="10"
  function handleAddOne() {
    ~setOrder({ item: order.item, quantity: order.quantity + 1, giftWrap: order.giftWrap });~ // Passes a brand-new object: React replaces order and re-renders!
  }
```

Save the file and reload the page. Now every click on `+1` passes a brand-new object to `setOrder`, and the quantity on the screen increases right away:

```page size=mini
row: +1; Add gift wrap
console: quiet
```
After two clicks on `+1`, the quantity in memory is three, yet `Object.is` saw the same object and skipped both renders.
:::

> [!PRINCIPLE]
> **Principle 1: Same Object vs. New Object: Treat State Objects as Read-Only and Always Replace Them**
>
> *Never mutate a property on an existing state object; always create a brand-new object with the updated property and pass that new object to the state setter.*
>
> When you call a state setter, React checks whether state changed by comparing the old value and the new value with `Object.is`. For objects, `Object.is` never inspects the properties inside the curly braces. It only checks whether both sides are the exact same object in memory. If you change a property inside the existing state object and pass that same object back to the setter, `Object.is` returns `true` and React skips the render. The changed property then sits hidden in memory until some unrelated state update triggers a render and makes it jump onto the screen all at once. Creating and passing a brand-new object makes `Object.is` return `false` so React replaces the state and re-renders immediately.
>
> **DO THIS:**
> ```jsx
> function handleAddOne() {
>   ~setOrder({ item: order.item, quantity: order.quantity + 1, giftWrap: order.giftWrap });~ // New object: Object.is is false, so React re-renders
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleAddOne() {
>   ~order.quantity = order.quantity + 1;~ // **WRONG:** mutates the existing state object in place!
>   ~setOrder(order);~ // **WRONG:** passes the same object back, so Object.is is true and React skips the render!
> }
> ```

## 2. Principle 2: Spread Copies the Other Fields, and the Change Is Written After the Spread

### Why `{ ...user, city: 'Paris' }` is the exact same thing as copying every field by hand

In Principle 1, our `order` object had only three properties, so typing each unchanged property by hand was manageable. What happens when an object in state has five, eight, or ten properties, and a button only needs to change **one** of them?

Look at a `user` object with three properties for the user's name, age, and city. To build a brand-new object where only `city` changes from Rome to Paris, compare writing every property by hand with using JavaScript's **object spread** syntax `...`:

```js title="Copying unchanged fields by hand vs. using object spread ...user"
const user = { name: 'John', age: 30, city: 'Rome' };

const nextByHand = ~{ name: user.name, age: user.age, city: 'Paris' }~; // Way A: copying name and age by hand
const nextBySpread = ~{ ...user, city: 'Paris' }~; // Way B: exact same new object using ...user!
```

Look at what is happening in those two lines:
- **First, Way A and Way B are the exact same thing!** Both lines create a brand-new object with the name and age preserved and `city` updated to `'Paris'`.
- **Second, the three dots inside `{ ...user }` are the exact same idea as `{...article}` on a JSX tag!** Think of `user` as a closed box holding its three properties. Instead of reaching in and copying each item by hand, the three dots `...` open the box and **spread** all of its fields into the new object.
- **Third, `{ ...user }` holds the same fields as `user`, so it may look like the old object at first, but it is NOT the same object in memory!** Because `{ ...user }` sits inside a fresh pair of curly braces, JavaScript creates a brand-new object in memory. When `Object.is` compares the two objects, it returns false and React knows to render:

```tree caption="Copying every unchanged property by hand vs. spreading the existing object with ...user."
Two ways to build a new object with one changed field
- +Way A: Copy each old field by hand [`{ name: user.name, age: user.age, city: 'Paris' }`] | You type **every unchanged field** yourself | Produces a **new object** with `city: 'Paris'`
- +Way B: Spread with three dots [`{ ...user, city: 'Paris' }`] | `...user` **copies all fields** into the new object automatically | **Exact same result** without typing every unchanged field
```

### Combining `...user` and a changed field in the same object: before vs. after

In that spread line above, the spread `...user` and the single property `city: 'Paris'` live together inside the same pair of curly braces.

Whenever you put a spread `...user` and a single property like `city: 'Paris'` inside the same object literal, there are **two ways to order them**:
- **Order 1**: `...user` comes **before** `city: 'Paris'`. That means `...user` is **first** on the left, and `city: 'Paris'` is **second** on the right.
- **Order 2**: `city: 'Paris'` comes **before** `...user`. That means `city: 'Paris'` is **first** on the left, and `...user` is **second** on the right.

Look at both orders side by side:

```js title="The two ways to order ...user and city: 'Paris' inside an object literal"
const user = { name: 'John', age: 30, city: 'Rome' };

const order1 = ~{ ...user, city: 'Paris' }~; // Order 1: ...user is first, city: 'Paris' is last -> city is 'Paris'!
const order2 = ~{ city: 'Paris', ...user }~; // Order 2: city: 'Paris' is first, ...user is last -> city is overwritten back to 'Rome'!
```

**Order 1 and Order 2 contain the exact same pieces, but they are NOT the same thing!**

Why do those two orders produce different cities? Because JavaScript builds an object literal **from left to right**, and when the same property name appears twice, whichever one comes **last** overwrites the earlier one:
1. **In Order 1**, `...user` runs first on the left and copies all three old properties, including `'Rome'`. Then `city: 'Paris'` runs second on the right and replaces Rome with `'Paris'`.
2. **In Order 2**, `city: 'Paris'` runs first on the left and sets the city to `'Paris'`. Then `...user` runs second on the right, pouring the old properties over it and overwriting `city` right back to Rome!

```tree caption="When ...user and an updated property share an object literal, JavaScript reads from left to right and the last one wins."
Two ways to order `...user` and `city: 'Paris'`
- +Order 1: `...user` before `city: 'Paris'` [`{ ...user, city: 'Paris' }`] | `...user` runs **first**; `city: 'Paris'` runs **last** | **`'Paris'` wins** because the change comes after the spread
- !Order 2: `city: 'Paris'` before `...user` [`{ city: 'Paris', ...user }`] | `city: 'Paris'` runs **first**; `...user` runs **last** | `...user` comes last and **overwrites `city` back to `'Rome'`!**
```

### Mistake 1: Leaving a new field out of a hand-written copy wipes it out

Why is copying every existing field so important in React? Because a `useState` setter **replaces** the state object with the exact object you pass to it. It **never merges** your new object into the old one! If you leave any field out of the new object, that field is gone from state on the next render.

Suppose we add a `customer` field for Anna Lee to our starting `order` object in the order card file. Meanwhile, the two button handlers still copy only the first three fields by hand:

```jsx title="src/components/OrderCard.jsx" startLine="3"
export default function OrderCard() {
  const [order, setOrder] = useState({
    item: 'Coffee mug',
    quantity: 1,
    giftWrap: false,
    ~customer: 'Anna Lee',~ // 1. New customer field added to the starting state
  });

  function handleAddOne() {
    setOrder({ item: order.item, quantity: order.quantity + 1, giftWrap: order.giftWrap });
  }

  function handleGiftWrap() {
    ~setOrder({ item: order.item, quantity: order.quantity, giftWrap: true });~ // **WRONG:** forgets to copy order.customer!
  }
```

In the card's markup, we add a paragraph showing who the order is for:

```jsx title="src/components/OrderCard.jsx" startLine="19"
  return (
    <section className="card">
      <h1>Your Order</h1>
      <p>Item: {order.item}</p>
      <p>Quantity: {order.quantity}</p>
      <p>Gift wrap: {order.giftWrap ? 'Yes' : 'No'}</p>
      ~<p>For: {order.customer}</p>~ {/* 2. Displays "For: Anna Lee" on first load */}
      <button onClick={handleAddOne}>+1</button>
      <button onClick={handleGiftWrap}>Add gift wrap</button>
    </section>
  );
}
```

When the page loads, the card shows `For: Anna Lee`. Then the shopper clicks `Add gift wrap`. The gift wrap line changes to `Gift wrap: Yes`. **However, the customer's name vanishes so the line reads `For:` with no name and zero Console warnings**. Because `handleGiftWrap` replaced the state object with one that had no customer field, `order.customer` became undefined.

### Using `...order` so every existing field is kept automatically

Instead of copying each unchanged property by hand, we rewrite both handlers with `...order` first and the changed field after it:

```jsx title="src/components/OrderCard.jsx" startLine="11"
  function handleAddOne() {
    ~setOrder({ ...order, quantity: order.quantity + 1 });~ // 1. Spreads all fields of order, then updates quantity
  }

  function handleGiftWrap() {
    ~setOrder({ ...order, giftWrap: true });~ // 2. Spreads all fields of order, then updates giftWrap to true
  }
```

Look closely at `handleGiftWrap` now. You will not find `item` or `customer` written anywhere inside that function! Where do those unchanged fields come from when React renders the updated card?

JavaScript's object spread `...order` supplies them automatically:
1. JavaScript creates an empty new object `{ }`.
2. `...order` copies all four existing fields of `order` into that new object from left to right.
3. Next, `giftWrap: true`, written after `...order`, replaces the copied false value with true.
4. Finally, `setOrder` receives this brand-new object, and `Object.is` returns false. React renders the card with `Gift wrap: Yes` and `For: Anna Lee` still intact!

### Mistake 2: Writing the changed field before `...order`

Now watch what happens if a teammate rearranges the gift wrap handler so `giftWrap: true` is written **before** `...order`:

```jsx title="src/components/OrderCard.jsx" startLine="15"
  function handleGiftWrap() {
    ~setOrder({ giftWrap: true, ...order });~ // **WRONG:** ...order comes last and overwrites giftWrap back to false!
  }
```

Look at that line. Nothing in `handleGiftWrap` writes `giftWrap: false`. Yet when the shopper clicks `Add gift wrap`, the card on the screen stays stuck on **`Gift wrap: No`**!

Why did the card keep `Gift wrap: No`? Follow JavaScript from left to right inside that new object:
1. First, `giftWrap: true` is written into the new object.
2. Second, `...order` copies every field from the current order object, including `giftWrap: false`, right over the new true value.
3. Even though the new object triggers a render, the card still displays the overwritten `false` as `Gift wrap: No`!

Move `giftWrap: true` back **after** `...order`, and the button works again:

### Wrapping the new object in parentheses inside an updater function

For forms and cards with several related fields, keeping all data grouped in one state object is very convenient. You only need to copy existing fields with `...` on every update.

What if a single click queues **several** updates to that same `order` object before the next render, such as a `+2` button that calls a helper twice? Just as we saw with updater functions for numbers, you pass an arrow function to `setOrder` and use `...` inside it:

```jsx title="Spreading the previous state object inside an updater function"
function handleAddOneQueued() {
  ~setOrder(o => ({ ...o, quantity: o.quantity + 1 }));~ // Parentheses around { ...o, ... } return the new object from =>
}
```

Notice the parentheses wrapped around the new object after the arrow `=>`. In JavaScript, curly braces right after an arrow `=>` normally mark the start of a multi-line function body rather than an object literal. Wrapping the curly braces in parentheses tells JavaScript to return that new object directly.

> [!PRINCIPLE]
> **Principle 2: Object Spread: Spread the Existing Object First, Then Write the Changed Property After It**
>
> *Spread `...order` first to copy all existing fields into a new object, and always write the updated field after `...order`.*
>
> A `useState` setter never merges the object you pass with the old state object. It replaces the old state object completely. If you build a new object by hand and forget a property, that property becomes `undefined` on the next render. Using object spread `...order` copies every top-level property of `order` into the new object automatically. Because JavaScript reads object properties from left to right and the last one wins, you must put `...order` first and write the changed property after it. If you place the changed field before `...order` so the spread comes last, `...order` overwrites your change with the old value.
>
> **DO THIS:**
> ```jsx
> function handleGiftWrap() {
>   ~setOrder({ ...order, giftWrap: true });~ // 1. ...order copies all fields first; 2. giftWrap: true wins last
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleGiftWrap() {
>   ~setOrder({ giftWrap: true, ...order });~ // **WRONG:** ...order comes last and overwrites giftWrap back to false!
> }
> ```

## 3. Principle 3: Spread Copies One Level, So a Nested Change Copies Every Object on the Path

### Why "nested" objects are really separate objects pointing at each other, and why spread is shallow

In code, we often write one object inside another object, such as an `address` object inside `user`:

```js title="An object written inside another object in code"
const user = {
  name: 'John',
  ~address: { city: 'Rome' }~, // Written inside user's curly braces in code
};
```

Look at two confusions that happen the moment developers see `{ ...user }` with a nested object:
- **First, writing an `address` object inside `user` looks like one big box holding a smaller box inside it, but it is NOT one object!** In JavaScript, there is no such thing as a truly nested object. Instead, JavaScript creates **two separate objects** in memory. The outer `user` object's `address` property simply holds a **pointer** to the separate inner object, like a street address written on a slip of paper.
- **Second, what does it mean that `...user` is "shallow"?** In everyday English, **shallow** water means only the top layer at the surface, not the deep water below. Object spread `{ ...user }` is a **shallow copy** because it copies only the top layer of properties. Think of photocopying the top sheet of a folder. If the top sheet says *"the address card is in drawer 3"*, the photocopy still says *"drawer 3"*. Both sheets point at the **exact same address card**!

Look at what `Object.is` reports when we spread `...user` into a shallow copy:

```js title="Plain JavaScript: what { ...user } copies vs. what it still shares"
const user = { name: 'John', address: { city: 'Rome' } };
const copy = { ...user };

console.log(~Object.is(copy, user)~); // 1. false: copy is a brand-new top-level object
console.log(~Object.is(copy.address, user.address)~); // 2. true: both point at the EXACT SAME address object!

~copy.address.city = 'Paris';~ // **WRONG:** mutates the shared address object, so user.address.city is now 'Paris' too!
```

Even though that copy is a brand-new top-level object, `copy.address` and `user.address` point at the **exact same inner object**. So changing `copy.address.city` to Paris mutates `user.address.city` at the exact same time!

What about mutating a brand-new object that you **just created** inside your function, such as creating a fresh `nextPosition` object and setting `nextPosition.x = 10`? That is called a **local mutation**, and it is **completely fine** because `nextPosition` is a fresh object that no other code points at yet. Reaching through `copy.address.city`, however, **looks like a local mutation on the copy, but it is NOT the same thing**, because `copy.address` is the old shared inner object!

To update `city` without mutating the shared inner object, we use `...` **twice**: once for the inner object and once for the outer object. You can write that in two steps with a variable or in one nested expression:

```js title="Two ways to copy every object on the path to city"
const nextAddress = ~{ ...user.address, city: 'Paris' }~; // Way 1, step 1: new inner address object
const nextUser1 = ~{ ...user, address: nextAddress }~; // Way 1, step 2: new outer user object pointing at nextAddress

const nextUser2 = ~{ ...user, address: { ...user.address, city: 'Paris' } }~; // Way 2: exact same thing in one step!
```

**Yes, Way 1 and Way 2 are the exact same thing!** Both create a brand-new inner address object and a brand-new outer user object, leaving the original `user.address` untouched at `'Rome'`:

```tree caption="Why a shallow copy { ...user } still shares the inner address object, while spreading both levels creates two fresh objects."
Updating `address.city` inside `user`
- !Shallow copy only [`const copy = { ...user }; copy.address.city = 'Paris'`] | `copy` is new, **but `copy.address` is the SAME inner object** | Mutates `user.address.city` and **corrupts earlier snapshots!**
- +Copy every level on the path [`{ ...user, address: { ...user.address, city: 'Paris' } }`] | Inner `...user.address` makes a **new `address` object**; outer `...user` makes a **new `user` object** | `user.address.city` stays **`'Rome'`** untouched
```

### Mistake: Spreading only the top level of `order` and mutating `next.delivery.time`

Now let us see how this shallow-copy trap breaks our online shop order card.

Suppose we move our starting order into a constant named `initialOrder` at the top of the order card file so we can wire a `Start over` button. Inside `initialOrder`, we add a nested `delivery` object for the street address and delivery time:

```jsx title="src/components/OrderCard.jsx" startLine="1"
import { useState } from 'react';

const ~initialOrder~ = { // 1. Starting order saved above OrderCard so Start over can reset to it
  item: 'Coffee mug',
  quantity: 1,
  giftWrap: false,
  customer: 'Anna Lee',
  ~delivery: { address: '12 Main Street', time: 'Morning' }~, // 2. Inner delivery object

```

Inside the card component, we pass `initialOrder` as the starting value of `useState`. If the evening button handler mutated `order.delivery.time` directly and passed that same object to `setOrder`, nothing on the screen would change.

Remembering to copy the outer object, the developer spreads `order` into `next`. Then the handler sets `next.delivery.time` to evening and passes `next` to the setter. Below that, the reset handler restores the card by passing `initialOrder` to `setOrder`:

```jsx title="src/components/OrderCard.jsx" startLine="11"
export default function OrderCard() {
  const [order, setOrder] = useState(initialOrder);

  function handleGiftWrap() {

    const next = ~{ ...order }~; // Shallow copy: next.delivery still points at the SAME delivery object!

```

In the card's markup, we display the delivery line and add the evening delivery button and the `Start over` button:

2. The shopper clicks the evening delivery button. The delivery line changes to `Evening`! **At first glance, the shallow copy looks as if it worked, but it is NOT working properly!**
3. Next, the shopper clicks `+1` twice so the card shows `Quantity: 3`.
4. Now the shopper decides to reset the order and clicks `Start over`.
5. The quantity goes back to one, **but the delivery line stays stuck on `Evening` instead of returning to `Morning`!**

### Why `Start over` failed to bring back `Morning`, and how copying both levels fixes it

Look at `handleEvening` and `handleStartOver` above. No line in our file ever wrote `initialOrder.delivery.time = 'Evening'`. How did `initialOrder` lose `'Morning'`?

Both `initialOrder.delivery` and `next.delivery` pointed at the **exact same inner delivery object** in memory! Follow what JavaScript and React did step by step:
1. On the first render, the state hook used `initialOrder` as the starting state, so `order` and that starting constant pointed at the same object.
2. When the shopper clicked the evening button, `{ ...order }` created a brand-new top-level `next` object. Its `delivery` property copied the pointer to the **existing** inner delivery object.
3. The line `next.delivery.time = 'Evening'` mutated that one shared delivery object in place. Because `initialOrder.delivery` points at that exact same inner object, its time silently became `'Evening'` too!
4. When the shopper clicked the reset button, the handler handed `initialOrder` back to `setOrder`. React rendered `initialOrder`, whose quantity was still one and whose mutated delivery object now held `'Evening'`!

Now let us fix `handleEvening` by spreading **every level** along the path down to `delivery.time`:

```jsx title="src/components/OrderCard.jsx" startLine="22"
  function handleEvening() {

```

Look closely at that single line. You will not see the word `address` written anywhere inside `handleEvening`. Where does the street address come from when the new card renders?

JavaScript's inner spread `...order.delivery` supplies it:
1. First, the inner spread `...order.delivery` creates a brand-new delivery object, copies the existing street address into it, and sets its time to `'Evening'`.
2. Next, the outer spread `...order` creates a brand-new order object, copies all top-level fields, and points `delivery` at the brand-new inner object.
3. Meanwhile, the original delivery object inside `initialOrder` is never touched and keeps `'Morning'`!

### Why mutating state breaks snapshots, debugging, and optimizations

Beyond breaking reset buttons like `Start over`, the official React documentation highlights five reasons why you should never mutate objects in state:
1. **Debugging**: When you replace state objects instead of mutating them, earlier `console.log` calls keep their exact historical values instead of getting overwritten by later mutations.
2. **Optimizations**: React components can skip unnecessary re-renders when their props have not changed. Checking `prevObj === obj` is instant when immutable updates guarantee that an unchanged reference means nothing inside changed.
3. **Render snapshots and new React features**: React's rendering model relies on every render having its own uncorrupted snapshot of state. Mutating an object changes the state inside previous render snapshots.
4. **Application features like Undo, Redo, and Reset**: Keeping earlier state objects untouched in memory makes features like `Start over`, Undo, and edit history straightforward to build.
5. **No hidden Proxies required**: Because you replace objects explicitly, React does not need to wrap every state object in hidden JavaScript Proxies or property traps just to detect changes.

What if your state object is nested three or four levels deep and spreading every level starts to look repetitive? Teams handle deep nesting in two ways. First, they can **flatten** the state structure into simpler pieces, which a later lesson covers. Second, they can use the optional library **Immer**, which gives you a temporary `draft` Proxy that records your changes and produces the nested copies automatically.

> [!PRINCIPLE]
> **Principle 3: Nested Objects: Spread Copies One Level, So Copy Every Object on the Path**
>
> *Because object spread `...` is shallow, update a nested property by creating a new copy of every object on the path from the change up to the root.*
>
> In JavaScript, an object written inside another object is actually a separate object in memory that the outer object points to. Spreading only the outer object with `{ ...order }` creates a new top-level object whose delivery property still points at the same inner object as `initialOrder.delivery`. If you mutate `next.delivery.time`, you corrupt that shared inner object inside earlier render snapshots and inside `initialOrder`, breaking the reset button. Instead, spread both levels with `...order` and `...order.delivery` so both the inner delivery object and the outer order object are brand-new copies.
>
> **DO THIS:**
> ```jsx
> function handleEvening() {
>   ~setOrder({ ...order, delivery: { ...order.delivery, time: 'Evening' } });~ // New delivery object inside a new order object
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleEvening() {
>   const next = { ...order };
>   ~next.delivery.time = 'Evening';~ // **WRONG:** next.delivery is still the shared inner object, corrupting initialOrder!
>   setOrder(next);
> }
> ```

## 4. Principle 4: One Handler for Many Fields: the Computed Property Name Reads the Input's `name`

### Why `{ [key]: 'Paris' }` is the exact same thing as `{ city: 'Paris' }`, and why leaving out `[ ]` is NOT the same thing

Suppose a variable named `key` holds the string `'city'`. Look at three small objects in plain JavaScript:

```js title="Plain JavaScript: a normal property name vs. a computed property name [key] vs. a literal key"
const key = 'city';

const obj1 = ~{ city: 'Paris' }~; // 1. Property name written directly as city -> { city: 'Paris' }
const obj2 = ~{ [key]: 'Paris' }~; // 2. Square brackets read the variable key ('city') -> { city: 'Paris' }!
const obj3 = ~{ key: 'Paris' }~; // 3. No square brackets: uses the literal word 'key' -> { key: 'Paris' }!
```

Look closely at the two nuances of confusion in those three lines:
- **First, when `key` holds `'city'`, writing `{ [key]: 'Paris' }` with square brackets and writing `{ city: 'Paris' }` are the exact same thing!** Both produce an object whose property is named `city` and holds `'Paris'`.
- **Second, `{ [key]: 'Paris' }` and `{ key: 'Paris' }` look almost identical, but they are NOT the same thing!** Without square brackets, JavaScript treats `key` as the literal name of the property and sets a property named `key`. With square brackets `[key]`, called a **computed property name**, JavaScript evaluates the expression inside the brackets first and uses its string result as the property name!

Think of a paper order form where each box has a printed label on it, such as `"customer"` or `"note"`. You do not need one clerk who only updates the customer line and a second clerk who only updates the note line. Instead, one clerk reads the printed label on whichever box you just filled in and updates that matching line on the order:

```tree caption="How JavaScript reads a direct property name, a computed property name inside [ ], and an unbracketed variable name."
Three ways to name a property when `const key = 'city'`
- +Direct property name [`{ city: 'Paris' }`] | You know the exact field name **`city`** ahead of time | Creates **`{ city: 'Paris' }`**
- +Computed property name [`{ [key]: 'Paris' }`] | Square brackets `[ ]` **look up the value of `key`** first | **Exact same result**: creates **`{ city: 'Paris' }`**
- !Forgot the square brackets [`{ key: 'Paris' }`] | ~Do **NOT** leave out `[ ]` when the name is in a variable | Creates a property literally named **`key`**: **`{ key: 'Paris' }`**!
```

### How an input carries its field name in `e.target.name`

Now suppose our order card has two text inputs: one for the customer's `Name` and one for the courier note.

In React, an input tag can display a state string with `value` and report every keystroke with `onChange`. Its `onChange` handler fires immediately on every keystroke as the user types. When an input displays `order.customer` as its value and its handler fails to update `order.customer`, React reverts the input box back to the old text after every keystroke! A later lesson covers the full rules of controlled inputs in detail.

You can also give each input tag a standard HTML `name` attribute that matches its field in `order`. For our two inputs, those attributes are `name="customer"` and `name="note"`. The browser then exposes that attribute on the event object as **`e.target.name`**, right beside the typed text in **`e.target.value`**:

```jsx title="Two separate handlers vs. one shared handler using [e.target.name]"
function handleCustomerChange(e) {
  ~setOrder({ ...order, customer: e.target.value });~ // Separate handler for customer only
}

function handleNoteChange(e) {
  ~setOrder({ ...order, note: e.target.value });~ // Separate handler for note only
}

function handleChange(e) {
  ~setOrder({ ...order, [e.target.name]: e.target.value });~ // Exact same result for BOTH inputs with one handler!
}
```

**Yes, wiring two separate handlers and wiring one shared `handleChange` with `[e.target.name]` work the exact same way on the screen!** You only need to make sure each input's `name` attribute matches its field in `order`.

### Mistake 1: Copy-pasting separate input handlers and forgetting to update the field name

Why do teams prefer one shared `handleChange` when a card or form has several text boxes? Because writing separate handlers by copy and paste makes it easy to update the wrong field!

Suppose we add `note: ''` to `initialOrder` in our order card file. The developer writes `handleNameChange` for the customer name, copies and pastes it to make `handleNoteChange`, and forgets to change the field name:

```jsx title="src/components/OrderCard.jsx" startLine="26"
  function handleNameChange(e) {
    setOrder({ ...order, customer: e.target.value });
  }

  function handleNoteChange(e) {
    ~setOrder({ ...order, customer: e.target.value });~ // **WRONG:** copy-pasted from handleNameChange and still updates customer!
  }
```

In the card's markup, we add the `Note: {order.note}` line and the two labeled `<input>` boxes:

```jsx title="src/components/OrderCard.jsx" startLine="41"
      <p>Delivery: {order.delivery.address}, {order.delivery.time}</p>
      <p>Note: {order.note}</p>
      <label>
        Name
        <input value={order.customer} onChange={handleNameChange} />
      </label>
      <label>
        Note for the courier
        ~<input value={order.note} onChange={handleNoteChange} />~ {/* Calls the copy-pasted handleNoteChange */}
      </label>
```

Watch what happens when the shopper clicks into the courier note box and tries to type a delivery note:
1. On the first keystroke, the note handler runs and writes the typed letter into `order.customer` instead of `order.note`!
2. The `For:` line and the `Name` input box get overwritten with the courier note.
3. Meanwhile, `order.note` is still the empty string `''`. Because the note box has `value={order.note}`, React reverts the note box back to empty after every keystroke!

### Replacing separate handlers with one `handleChange` using `[e.target.name]`

Let us replace both separate handlers with a single `handleChange` function that uses `[e.target.name]`:

```jsx title="src/components/OrderCard.jsx" startLine="26"
  function handleChange(e) {
    ~setOrder({ ...order, [e.target.name]: e.target.value });~ // 1. Reads the field name from e.target.name
  }
```

And on the two input tags, we add `name="customer"` and `name="note"` and wire both inputs to the shared handler:

```jsx title="src/components/OrderCard.jsx" startLine="39"
      <label>
        Name
        ~<input name="customer" value={order.customer} onChange={handleChange} />~ {/* 2. e.target.name is "customer" */}
      </label>
      <label>
        Note for the courier
        ~<input name="note" value={order.note} onChange={handleChange} />~ {/* 3. e.target.name is "note" */}
      </label>
```

Look closely at `handleChange` above. Neither `customer` nor `note` appears anywhere inside that function! How does `handleChange` know to update `order.note` when the shopper types in the second box?

The `<input name="note" />` tag supplies the field name through the browser's event object `e`:
1. The shopper types a courier note in the second input box.
2. React calls `handleChange` with the event object `e`.
3. Inside the handler, `e.target.name` is the string note, and `e.target.value` holds the typed note text.
4. After `...order` copies all top-level fields, JavaScript reads `[e.target.name]` and updates the note property. Notice that this single-level spread updates top-level fields on `order`; a nested field such as `delivery.time` still needs the two-level copy from Principle 3.

### Mistake 2: Giving an input a `name` attribute that does not match any field in state

Because `[e.target.name]` uses the input's `name` attribute as the exact property name on the state object, every input's name attribute must match its state property **character for character**.

Look at what happens if a teammate changes the first input's attribute from `name="customer"` to `name="customerName"` while the state field is still called customer:

1. On every keystroke, the handler uses `[e.target.name]` and writes a brand-new unused property named `customerName` onto the state object.
2. Meanwhile, `order.customer` is never updated and stays `'Anna Lee'`.
3. Because the input displays `value={order.customer}`, React reverts the input box back to `'Anna Lee'` after every keystroke! The shopper's typed letters refuse to stay in the box, `For: Anna Lee` never changes, and the Console shows zero warnings.

> [!PRINCIPLE]
> **Principle 4: Computed Property Names: Use `[e.target.name]` So One Handler Updates Multiple Inputs**
>
> *Give each input tag a `name` attribute matching its top-level state property, and update state in one handler with `[e.target.name]: e.target.value`.*
>
> Writing separate change handlers for every text box invites copy-paste bugs where a handler updates the wrong property. Inside an object literal, wrapping an expression in square brackets `[e.target.name]` creates a computed property name: JavaScript evaluates `e.target.name` first and uses that string as the property key. If you forget the square brackets, JavaScript creates a property literally named `key`. And if an input's `name` attribute does not match the state property in `value`, the handler writes to an unused property. React then reverts the input box on every keystroke.
>
> **DO THIS:**
> ```jsx
> function handleChange(e) {
>   ~setOrder({ ...order, [e.target.name]: e.target.value });~ // 1. Square brackets use e.target.name as the property key
> }
> ~<input name="note" value={order.note} onChange={handleChange} />~ {/* 2. name="note" matches order.note */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleChange(e) {
>   setOrder({ ...order, [e.target.name]: e.target.value });
> }
> ~<input name="courierNote" value={order.note} onChange={handleChange} />~ {/* **WRONG:** name="courierNote" does not match order.note, so typing is reverted! */}
> ```

And here is the complete order card file combining all four principles. Every update passes a brand-new object to `setOrder`, and top-level updates spread `...order` first. The nested delivery update spreads both levels so `initialOrder` stays untouched, and one `handleChange` updates both text inputs:

```jsx title="src/components/OrderCard.jsx"
import { useState } from 'react';

const ~initialOrder~ = { // 1. Saved above OrderCard; stays untouched because we never mutate nested objects
  item: 'Coffee mug',
  quantity: 1,
  giftWrap: false,
  customer: 'Anna Lee',
  delivery: { address: '12 Main Street', time: 'Morning' },
  note: '',

export default function OrderCard() {
  const [order, setOrder] = useState(initialOrder);

  function handleAddOne() {
    ~setOrder({ ...order, quantity: order.quantity + 1 });~ // 2. Principle 1 & 2: new object with ...order first and updated quantity last
  }

  function handleGiftWrap() {
    setOrder({ ...order, giftWrap: true });
  }

  function handleEvening() {
    ~setOrder({ ...order, delivery: { ...order.delivery, time: 'Evening' } });~ // 3. Principle 3: copies both order and order.delivery
  }

    setOrder(initialOrder);
  }

  function handleChange(e) {
    ~setOrder({ ...order, [e.target.name]: e.target.value });~ // 4. Principle 4: computed property name updates customer or note
  }

  return (
    <section className="card">
      <h1>Your Order</h1>
      <p>Item: {order.item}</p>
      <p>Quantity: {order.quantity}</p>
      <p>Gift wrap: {order.giftWrap ? 'Yes' : 'No'}</p>
      <p>For: {order.customer}</p>
      <p>Delivery: {order.delivery.address}, {order.delivery.time}</p>

      <label>
        Name

      </label>

        <input name="note" value={order.note} onChange={handleChange} />
```

| :--- | :--- | :--- |

## For the Interview

> **The Interview Question:** How do you update an object in state without mutating it?

### How to Answer Clearly in 30 Seconds

"We treat every object in React state as read-only. React never looks inside an object to check if a property changed; instead, the state setter compares the new value with the current state using `Object.is`. If we mutate `user.name = 'Alice'` on the existing object and pass `user` back to the setter, `Object.is` sees the exact same object reference. React then skips the re-render, leaving the change hidden until some unrelated render happens later.

To update an object properly, we create a brand-new object and pass it to the setter so React replaces the state and re-renders:
1. **Top-level fields with object spread**: we pass `{ ...order, quantity: order.quantity + 1 }` to `setOrder`. Because the setter replaces rather than merges, `...order` comes first to copy existing fields, and the changed property comes after it so the last property wins.
2. **Nested objects**: spread is shallow and only copies one level deep, so a nested object is a separate object the parent points to. We copy every level along the path, like `{ ...order, delivery: { ...order.delivery, time: 'Evening' } }`, which keeps earlier snapshots and reset objects intact. Mutating a brand-new local object we just created is fine, and for deep nesting we can either flatten state or use Immer.
3. **Multiple form inputs**: we give each input a `name` attribute matching its state key and share one handler using a computed property name, `{ ...order, [e.target.name]: e.target.value }`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why doesn't React re-render when I mutate `order.quantity = 2` and pass `order` to `setOrder`, and why does that change show up on a later render?"**
   When you call a `useState` setter, React compares the value you passed with the current state using `Object.is`. For objects, `Object.is` checks object identity in memory, not the properties inside. Mutating `order.quantity = 2` changes the contents of the existing object while keeping the exact same object reference, so `Object.is` returns `true` and React bails out without re-rendering. However, the object in memory really was mutated. The next time an unrelated state update triggers a re-render, React reads the mutated `order.quantity` and puts the delayed change onto the screen all at once.
2. **"Is `{ ...order }` a deep copy, and what goes wrong if you spread `order` into `next`, mutate `next.delivery.time = 'Evening'`, and pass `next` to `setOrder`?"**
   **No.** Object spread `{ ...order }` is a **shallow copy** that copies only the top-level properties. In JavaScript, a nested object like `order.delivery` is a separate object in memory that the outer object only points to. After `const next = { ...order }`, `next` is a new top-level object, so `setOrder` will trigger a render. However, `next.delivery` still points at the exact same inner object as the previous render's snapshot and any shared `initialOrder` constant. Mutating `next.delivery.time = 'Evening'` corrupts past snapshots and breaks features like a `Start over` reset button or `memo` optimizations. You must copy every level on the path to the change.
3. **"How can one `onChange` handler update multiple text inputs on a form object, and when is mutating an object actually safe in React?"**
   Give each `<input>` a `name` attribute matching its state key, and use a computed property name inside the spread: `{ ...order, [e.target.name]: e.target.value }`. The square brackets evaluate `e.target.name` from the input that fired and overwrite that matching property after `...order`. Mutating a **fresh local object** that you just created in the same function, like `const next = {}` and `next.x = 10`, is a local mutation. That is completely safe because no other component or earlier render snapshot points at that new object yet.

```tree dir=right caption="Interview comparison: mutating an existing state object vs. shallow-copying a nested object vs. copying every level on the path."
Updating objects in React state in an interview
- !Mutate existing state object [`order.quantity = 2` and pass `order` to `setOrder`] | Same object reference in memory | `Object.is` is **`true`**: React **skips the render**, and the change leaks out on a later render
- !Shallow copy + nested mutation [`const next = { ...order }; next.delivery.time = 'Evening'`] | Top object is new, **inner `delivery` object is shared** | Renders now, **but corrupts earlier snapshots and `initialOrder`**
- +Copy every level on the path [`{ ...order, delivery: { ...order.delivery, time: 'Evening' } }`] | Every modified level gets a **brand-new object** | React renders cleanly and **keeps all past snapshots intact**
```
