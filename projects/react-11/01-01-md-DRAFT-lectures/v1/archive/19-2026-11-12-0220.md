## How We Update an Array Held in State

### Pushing into the existing array vs. passing a brand-new array to the setter

Suppose a component holds a list of three names in state: Cara, Anna, and Ben. When the user clicks a button to add Dan at the end of the list, compare two ways you might write the click handler.

First, look at Way 1, which calls `push` on the existing state array and passes that array back to `setNames`:

```jsx title="Way 1: Pushing 'Dan' into the existing names array"
const [names, setNames] = useState(['Cara', 'Anna', 'Ben']);

function handleAdd() {
  ~names.push('Dan');~ // 1. Adds 'Dan' inside the existing names array
  ~setNames(names);~ // 2. Hands that exact same names array back to React -> page stays on 3 names!
}
```

Now compare Way 1 with Way 2, which uses three dots `...` inside square brackets to build a brand-new array with `'Dan'` at the end:

```jsx title="Way 2: Passing a brand-new array to setNames"
const [names, setNames] = useState(['Cara', 'Anna', 'Ben']);

function handleAdd() {
  ~setNames([...names, 'Dan']);~ // Creates a brand-new array with 'Dan' at the end -> page shows 4 names!
}
```

When you click the button in Way 1, the screen stays stuck on the original three names! When you click the button in Way 2, the fourth name appears right away.

Look at the four silent confusions that trip developers up whenever an array lives in state:
- **First, pushing Dan into `names` and calling `setNames` looks like passing an updated list, and both arrays hold four names, but they are NOT the same thing!** Way 1 changes the existing array from the inside and hands React the very same array it already holds. Way 2 builds a brand-new array in memory and hands that new array to React.
- **Second, arrays look different from objects because they use square brackets and numbered positions, but to JavaScript and React an array is a kind of object!** Just as with an object in state, React never opens an array to count or read its items. React checks only the outside box with `Object.is`, like a librarian scanning the barcode on the cover of a book. Writing a fourth name inside the same book leaves the same barcode on the cover, so React skips the render.
- **Third, the method names `slice` and `splice` differ by only one letter, so they look like the same word, but they are NOT the same thing!** In everyday life, to **splice** means to cut a movie film reel or a rope and tape a piece directly into the original reel. In JavaScript, `splice` cuts and changes the original array itself. By contrast, to **slice** means to take a slice of bread to keep. In JavaScript, `slice` copies a part of the array onto a new sheet while the original array stays untouched.
- **Fourth, calling `sort` or `reverse` on an array returns the reordered list, so it looks like it returns a brand-new array, but it is NOT a new array!** Both methods rearrange the original array in place and hand that same original array right back.

To keep the array methods straight, picture two tools sitting on an office desk: a **pen** and a **photocopier**:
- **The pen writes directly on the original sheet of paper**: Methods like `push` and `splice` change the original array in place. Calling `sort` or `reverse`, or assigning a slot by index, mutates the array in place too, so we avoid calling these directly on state.
- **The photocopier leaves the original sheet untouched and hands back a fresh sheet**: Tools like array spread `...` and `filter` build and return a brand-new array. Calling `slice`, `concat`, or `map` returns a brand-new array too. Even then, remember that a photocopy of a guest list is **shallow**. The sheet of paper is new, yet the guests named on that sheet are still the exact same people.

```tree caption="The two groups of JavaScript array operations: the pen that mutates the existing array vs. the photocopier that returns a brand-new array."
Two kinds of array tools in JavaScript
- !The Pen: Mutates the original array [`push` `splice` `sort` `reverse`] | ~Do **NOT** call directly on a state array | Rewrites the **same array box** in place | `Object.is` sees the **same array** and **skips the render**
- +The Photocopier: Returns a new array [`[...arr]` `filter` `slice` `map`] | +**DO** use to build the next state array | Leaves the old array untouched and returns a **new array box** | `Object.is` sees a **different array** and **re-renders the page**
```

Here is the complete table from the official React documentation showing which tool to avoid and which tool to prefer for every array job:

| Operation | Avoid: Mutates the Array | Prefer: Returns a New Array |
| :--- | :--- | :--- |
| **Adding** | `push`, `unshift` | `concat`, `[...arr]` spread syntax |
| **Removing** | `pop`, `shift`, `splice` | `filter`, `slice` |
| **Replacing** | `splice`, `arr[i] = ...` assignment | `map` |
| **Sorting** | `reverse`, `sort` | Copy the array first, then sort or reverse the copy |

### Why a music player queue ignores clicks and breaks Undo when mutated

To see every array operation in a real interface, we will build the **Up Next** queue of a music player. A music queue is an array that changes with every click:
1. The listener clicks **Add to queue** to put a suggested song at the bottom of the list.
2. The listener clicks **Remove** next to a song they want to skip, or clicks **Undo** if they removed the wrong song by mistake.
3. The listener clicks **Play next** to slip the suggested song right below the song playing now, at the second spot in the list.
4. The listener clicks **Move up** to bump a song one row higher in the queue.
5. The listener clicks **Like** on a favorite song to mark it as **Liked**.

When a developer writes those five buttons by mutating the `queue` array in place, the player breaks in ways that are frustrating to debug:
- Clicking **Add to queue**, **Remove**, **Play next**, or **Move up** changes the array in memory. Yet the list on the screen does not move at all, and the Console prints zero errors.
- Even trickier, if the developer copies the array before flipping `liked` in place, the **Liked** label appears on screen right away. Yet clicking **Undo** leaves the button stuck on **Liked**, because the saved array for **Undo** still points at the mutated song object!

```tree caption="What the listener expects in the Up Next music queue vs. what happens when handlers mutate the state array or its song objects."
Updating the `Up Next` music queue
- +What the listener expects | Every add, remove, insert, and move updates the queue **right away** | Clicking `Undo` after `Like` restores the song to **`Like`**
- !What happens when handlers mutate state | `push`, `splice`, and direct swaps leave the queue **frozen on screen** | Mutating a song inside a copied array makes `Undo` stay stuck on **`Liked`!**
```

### Six ways to give a state setter a new array

Whenever you update an array in state, you choose the recipe that builds a brand-new array for the job at hand. Here are the five core JavaScript recipes side by side:

```jsx title="Five recipes that hand setQueue a brand-new array"
function QueueRecipes({ queue, setQueue, newSong, id, index }) {
  const addedEnd = ~[...queue, newSong]~; // 1. Add at the end with spread
  const removed = ~queue.filter(s => s.id !== id)~; // 2. Remove by test with filter
  const inserted = ~[...queue.slice(0, 1), newSong, ...queue.slice(1)]~; // 3. Insert at index 1 with two slices
  const next = ~[...queue]~; // 4. Copy first before reordering or swapping slots
  const updated = ~queue.map(s => s.id === id ? { ...s, liked: !s.liked } : s)~; // 5. Replace one changed item with map
}
```

Across real React projects, six tools cover every array update:
1. **Array spread `[...queue, song]` or `[song, ...queue]`, or `concat`**: Best for adding a new item at the very end or the very start of the list.
2. **`filter`**: Best for removing one or more items by keeping every item that passes a test.
3. **Two `slice` calls with spread**: Best for inserting a new item at a specific position in the middle of the list.
4. **Copying first with `[...queue]`, then swapping, sorting, or reversing the copy**: Best for reordering items when the method itself mutates in place. Newer JavaScript methods like `toSorted` and `toReversed` copy and reorder in one call.
5. **`map` returning a new object for the changed item**: Best for updating a property on one item inside the array while leaving every other item untouched.
6. **Immer**: An optional helper library for deeply nested state that lets you write mutating-looking code on a temporary draft while it produces new copies behind the scenes.

```tree caption="How to choose the right non-mutating array recipe for each queue operation."
Which recipe builds the new array?
- +Add at the end or start [`[...queue, song]` `[song, ...queue]`] | Spreads the old items into a new array and places the new song after or before them
- +Remove an item [`queue.filter`] | Keeps every song where the test is `true` and leaves the old array untouched
- +Insert in the middle [two `queue.slice` calls + spread] | Places the new song between a slice of the items before `i` and a slice of the rest
- +Reorder items [`[...queue]` then swap or `sort`] | Copies the array first so mutating the copy never touches existing state
- +Change one item's field [`queue.map` with `{ ...s }`] | Returns a new song object for the changed row and keeps all other songs as they are
```

### What we bring from earlier lessons and how our project files are organized

This lesson stands on six ideas from earlier lessons, together with four plain JavaScript array tools:
- **State variables, snapshots, and `Object.is`**: Calling `useState` gives this render its own fixed **snapshot** of the array and a setter function. When you call the setter, React compares the new value with the current state using `Object.is` and skips the render when both are the exact same array.
- **Mutation vs. local mutation**: Changing an existing array that already lives in state is a **mutation** and breaks React's check. By contrast, changing a brand-new array that you just created inside your handler is a **local mutation**. Local mutation is completely safe because no other code points at that new array yet.
- **Arrow handlers and conditional rendering**: On a row button, an arrow function in `onClick` remembers which song row was clicked. Inside JSX, `&&` shows a badge or button only when a condition is true, and `? :` chooses between two labels.
- **Object spread and shallow copies**: Writing `{ ...song }` copies every property of `song` into a new object so you can overwrite one field. Because spread is **shallow**, copying an outer container only copies references to the inner objects.
- **Rendering lists with `map`, `index`, `key`, and `nextId`**: In JSX, `queue.map` turns each song into a list row and supplies the row's position as its second argument `index`. Each row uses `key={song.id}` so React tracks each song across reorders, and a counter `nextId` at the top of the file gives each added song a unique ID.
- **Plain JavaScript operators and methods for arrays**: The operator `!==` checks that two values are not equal and returns `true` when they differ. The method `slice` copies a range of items from a start index up to, and not including, an end index. Swapping two array slots uses a spare variable so neither item is lost. Newer JavaScript environments also offer `toSorted` and `toReversed`, along with `toSpliced`, which return a brand-new array in one step.

### Five Principles of Updating Arrays in State

**PRINCIPLES:** React decides whether a state array changed by checking whether you passed a different array box to the setter, never by reading the items inside it. Every operation on a state array must therefore build a new array and leave the old array untouched, down to the item objects inside it:
1. **Principle 1: A Changed Array Is the Same Array, So Adding Means a New Array**: Calling `push` or `unshift` changes the existing array in place, so the state check sees the same array and skips the render. Build a new array with spread, placing the new item at the end or the start.
2. **Principle 2: `filter` Removes a Song into a New Array and Leaves the Old Array Whole**: Calling `splice` or `pop` mutates the state array in place. Use `filter` to keep every item except the removed one in a brand-new array, leaving the old array whole so features like **Undo** can restore it.
3. **Principle 3: Inserting in the Middle Is Two Slices and the New Song Between Them**: Never use `splice` to insert into a state array. Build a new array that spreads a `slice` of the items before the insert position, writes the new item, and spreads a `slice` of the remaining items.
4. **Principle 4: Reordering Happens on a Copy: Copy First, Then Move, Sort, or Reverse the Copy**: Methods like `sort` and `reverse` and index swaps mutate the array they are called on. Make a copy with spread first, reorder that fresh copy through local mutation, and pass the copy to the setter.
5. **Principle 5: A Copied Array Still Holds the Same Songs, So Changing One Song Means a New Song Object**: Copying an array is shallow, so the copied array still points at the exact same song objects as the old array. Use `map` to return a brand-new object for the changed song while returning every other song as it is.

Here is the complete overview of all five principles before we build each step on stage:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Adding: Build a New Array with Spread** | Pushing into the state array and passing it to the setter leaves the screen unchanged with zero Console errors, until an unrelated update suddenly shows the pushed items. | Never call `push` or `unshift` on state; pass `[...queue, song]` to add at the end or `[song, ...queue]` to add at the start. |
| **Principle 2** | **Removing: Filter into a New Array** | Removing an item with `splice`, `pop`, or `shift` mutates the existing array so the deleted row stays on screen. | Call `queue.filter` with `s.id !== id` so React receives a new array and the old array stays whole for `Undo`. |
| **Principle 3** | **Inserting: Two `slice` Calls Around the New Item** | Confusing `splice` with `slice` either mutates the state array in place or throws away an unused copy. | Spread two `queue.slice` calls with the new song between them inside new square brackets and pass that array to the setter. |
| **Principle 4** | **Reordering: Copy First, Then Mutate the Copy** | Swapping items by index or calling `sort` or `reverse` directly on state mutates the original array and returns that same array. | Copy first with `[...queue]`, swap or sort inside that new copy, and pass the copy to the setter. |
| **Principle 5** | **Updating an Item: `map` with a New Item Object** | Mutating `next[i].liked` inside a copied array corrupts the shared song object still held by earlier snapshots and `Undo`. | Use `queue.map` to return a new `{ ...s }` object for the target song and `s` unchanged for every other song. |

## 1. Principle 1: A Changed Array Is the Same Array, So Adding Means a New Array

### Why pushing into `names` and spreading `names` are NOT the same thing

Before we open the music player files, look closely at what happens inside JavaScript memory when we add Dan to our three names in two different ways.

First, here is `push`, which writes Dan into the existing `names` array:

```js title="Way A: Mutating the existing names array with push"
const names = ['Cara', 'Anna', 'Ben'];
~names.push('Dan');~ // 1. Writes 'Dan' into the existing names array in place

console.log(~Object.is(names, names)~); // 2. true -> still the exact same array box!
```

Second, here is array spread `[...names, 'Dan']`, which lays out the old items inside a brand-new pair of square brackets and adds `'Dan'` at the end:

```js title="Way B: Creating a brand-new array with spread"
const names = ['Cara', 'Anna', 'Ben'];
const nextNames = ~[...names, 'Dan']~; // 1. Builds a brand-new array holding all 4 names

console.log(~Object.is(names, nextNames)~); // 2. false -> two different array boxes in memory!
```

Look at all three nuances here so nothing feels mysterious:
- **First, calling `push` and spreading `[...names, 'Dan']` both leave four names, so they look like they do the same job, but they are NOT the same thing!** In Way A, `names` is still the exact same array box it was before, so `Object.is` returns `true` and React ignores it. In Way B, `nextNames` is a brand-new array box, so the state check returns `false` and React re-renders the page.
- **Second, spreading an array with `[...names, 'Dan']` and spreading an object with `{ ...order }` use the exact same three dots!** When you write `...names` inside new square brackets, JavaScript opens the `names` box and lays out Cara, Anna, and Ben in order inside the new array.
- **Third, adding at the end with `[...names, 'Dan']` and adding at the start with `['Dan', ...names]` are the exact same recipe!** Look at both positions side by side:

```js title="Adding at the end vs. adding at the start with spread"
const names = ['Cara', 'Anna', 'Ben'];

const atEnd = ~[...names, 'Dan']~; // Order 1: ...names first, 'Dan' last -> ['Cara', 'Anna', 'Ben', 'Dan']
const atStart = ~['Dan', ...names]~; // Order 2: 'Dan' first, ...names last -> ['Dan', 'Cara', 'Anna', 'Ben']
```

JavaScript reads the items inside `[ ]` from left to right. Putting `...names` first places Dan at the end of the new array, replacing `push`. Putting `'Dan'` first places Dan at the very start of the new array, replacing `unshift`. Calling `concat` on `names` also returns a brand-new array with Dan at the end. Spread syntax is even handier because it adds at either end with the same three dots.

```tree caption="Why push is ignored by React's Object.is check, while spreading into new square brackets triggers a re-render."
How to add `'Dan'` to `names` in React state
- !Mutate with `push` or `unshift` [`names.push`] | Writes `'Dan'` inside the **existing array box** | `Object.is` returns **`true`** and React **skips the render**
- +Spread with `'Dan'` last [`[...names, 'Dan']`] | Lays out old items in a **new array**, then adds `'Dan'` at the **end** | `Object.is` returns **`false`** and React **re-renders**
- +Spread with `'Dan'` first [`['Dan', ...names]`] | Places `'Dan'` at the **start** of a **new array**, then lays out old items | `Object.is` returns **`false`** and React **re-renders**
```

### Mistake: Calling `push` on the `queue` array and passing `queue` to `setQueue`

Now we want to add a suggested song, Rainy Window, when the listener clicks **Add to queue**. Suppose a developer writes `handleAddToQueue` using the plain JavaScript habit of calling `queue.push` and passing the mutated array to the setter:

```jsx title="src/components/PlayQueue.jsx" startLine="11"
export default function PlayQueue() {
  const [queue, setQueue] = useState(initialQueue);

  function handleAddToQueue() {
    ~queue.push({ id: nextId++, title: 'Rainy Window', liked: false });~ // **WRONG:** mutates the existing queue array in place!
    ~setQueue(queue);~ // **WRONG:** hands React the exact same queue array, so React skips the render!
  }
```

Below the handler, the component returns the **Up Next** heading, the suggested song line, and an `<ol>` list where the first row shows **Now playing**:

```jsx title="src/components/PlayQueue.jsx" startLine="19"
  return (
    <section>
      <h1>Up Next</h1>
      <p>
        Suggested: Rainy Window{' '}
        <button ~onClick={handleAddToQueue}~>Add to queue</button> {/* Runs handleAddToQueue on click */}
      </p>
      <ol>
        {queue.map((song, index) => (
          <li key={song.id}>
            {song.title}

          </li>

      </ol>
    </section>
  );
}
```

Look at what happens when the listener clicks **Add to queue**:
1. The listener clicks **Add to queue** once. The list on the screen still shows only three songs: Sunny Road, Blue Bicycle, and Night Train.
2. The Console panel shows zero errors and zero warnings.
3. The listener clicks **Add to queue** a second time, and the screen still shows only three songs!

Why did the list stay stuck on three songs even though `setQueue` was called? Notice that no line in `handleAddToQueue` told React to skip the render. React decided that inside `setQueue` through four steps:
1. Calling `queue.push` wrote the fourth song object directly into the existing array that `queue` already points at.
2. Calling `setQueue` with `queue` handed that exact same array box back to React.
3. Inside `setQueue`, React compared the received array with the current state array using `Object.is`, which returned true.
4. Because `Object.is` returned true, React concluded nothing changed and skipped re-rendering `PlayQueue`!

Even worse, those pushed Rainy Window songs are now hiding inside the mutated `queue` array in memory. If an unrelated state variable in the same component updates later and triggers a render, all of the secretly pushed songs suddenly appear on screen at once! And if a developer puts `push` inside a state updater function, React calls updater functions twice in `<StrictMode>` during development, so the song gets pushed twice! Event handlers themselves are never called twice by `<StrictMode>`.

### Adding a song to a brand-new array with spread

To make **Add to queue** update the screen right away, we replace `queue.push` with array spread `[...queue, newSong]` inside the setter:

```jsx title="src/components/PlayQueue.jsx" startLine="14"
  function handleAddToQueue() {
    ~setQueue([...queue, { id: nextId++, title: 'Rainy Window', liked: false }]);~ // Builds a brand-new array with the new song at the end
  }
```

Look closely at that `[...queue, newSong]` line inside `handleAddToQueue`. You do not see Sunny Road, Blue Bicycle, or Night Train written anywhere on that line! Where did the three existing songs come from?
1. The outer square brackets `[ ]` create a brand-new, empty array in memory.
2. The three dots `...queue` copy the three existing song objects out of `queue` and lay them into the first three slots of the new array in order.
3. After the comma, the new Rainy Window object is placed in the fourth slot at the end, and `nextId++` gives it ID `4`.
4. Next, `setQueue` compares the brand-new array of four songs against the old array of three songs. Because they are two different array boxes in memory, `Object.is` returns `false`, React renders the queue again, and Rainy Window appears as the fourth row!

## 2. Principle 2: `filter` Removes a Song into a New Array and Leaves the Old Array Whole

### Why `filter` and `splice` are NOT the same thing when removing an item

Suppose our `names` array holds Cara, Anna, and Ben, and we want to remove Anna. Compare two ways of removing Anna in plain JavaScript.

First, look at `filter`, which tests each name with `name !== 'Anna'`:

```js title="Way A: Removing 'Anna' into a new array with filter"
const names = ['Cara', 'Anna', 'Ben'];
const fewer = ~names.filter(name => name !== 'Anna')~; // 1. Returns a new array ['Cara', 'Ben']

console.log(~fewer~); // 2. ['Cara', 'Ben'] -> new array of 2 names
console.log(~names~); // 3. ['Cara', 'Anna', 'Ben'] -> original array still has all 3 names!
```

Second, compare that with calling `splice` at index 1 to delete 1 item:

```js title="Way B: Deleting 'Anna' from the original array with splice"
const names = ['Cara', 'Anna', 'Ben'];
~names.splice(1, 1);~ // 1. Cuts 'Anna' directly out of the original names array!

console.log(~names~); // 2. ['Cara', 'Ben'] -> the original names array itself was changed!
```

Look at the two confusions that catch developers here:
- **First, calling `names.filter` and calling `names.splice` both leave Cara and Ben, so they look like two ways to do the same job, but they are NOT the same thing!** Calling `splice` cuts Anna out of the original `names` array in place. Calling `filter` never touches `names` at all: it returns a brand-new array holding Cara and Ben, while the original array still holds all three names.
- **Second, in everyday speech removing an item sounds like reaching into a box and taking something out, but with `filter` nothing is taken out of the old array!** Think of `filter` as pouring a bowl of items through a sieve into a clean second bowl. Every item where your test returns `true` passes into the new bowl, while any item where your test returns `false` is left out. The original list in state stays completely whole.

```tree caption="Removing an item with filter versus deleting it in place with splice, pop, or shift."
Two ways to remove `'Anna'` from `['Cara', 'Anna', 'Ben']`
- +`names.filter` with `name !== 'Anna'` [The Sieve] | +**DO** use for state arrays | Returns a **brand-new array** `['Cara', 'Ben']` | Leaves `names` **untouched** with all **3 names**
- !`names.splice` or `pop` or `shift` [The Knife] | ~Do **NOT** call on a state array | Cuts `'Anna'` out of **`names` in place** | Mutates the existing state array
```

### How `filter` tests each item with `!==`

In JavaScript, the operator `!==` means "is not equal to." It compares two values and returns `true` when they are different, or `false` when they are the same:

```js title="Plain JavaScript: how !== tests whether two IDs differ"
console.log(~1 !== 2~); // true -> 1 is different from 2, so filter keeps this item
console.log(~2 !== 2~); // false -> 2 equals 2, so filter leaves this item out
```

When you call `queue.filter` with `s.id !== id`, JavaScript runs your arrow function once for each song in the array. Every song whose `s.id` is different from the clicked `id` gets true and goes into the new array. The one song whose `s.id` matches the clicked `id` gets false and is left out of the new array.

What about `pop` and `shift`, or `splice`? All three mutate the original array in place, and none of them even return the remaining list. Instead, `pop` and `shift` return the single removed item, and `splice` returns an array of the removed items.

### Mistake: Removing a song with `splice` and passing `queue` back to `setQueue`

Now we want to add a **Remove** button next to every song row in our music queue. Suppose a developer writes `handleRemove` by finding the song's index with `findIndex`, cutting it out with `queue.splice`, and passing the array back to the setter:

## 3. Principle 3: Inserting in the Middle Is Two Slices and the New Song Between Them

### Why `slice` and `splice` look almost identical, but are NOT the same thing

Suppose our `names` array holds Cara, Anna, and Ben, and we want to insert Dan at index `1`, right between Cara and Anna.

Look at two ways to put Dan at index `1`:

```js title="Way A: Assembling two slices with 'Dan' between them"
const names = ['Cara', 'Anna', 'Ben'];
const nextNames = ~[...names.slice(0, 1), 'Dan', ...names.slice(1)]~; // 1. Two slices with 'Dan' in between

console.log(~nextNames~); // 2. ['Cara', 'Dan', 'Anna', 'Ben'] -> brand-new array of 4 names
console.log(~names~); // 3. ['Cara', 'Anna', 'Ben'] -> original names array is untouched!
```

Now compare Way A with calling `names.splice` at index `1`:

```js title="Way B: Splicing 'Dan' directly into the original names array"
const names = ['Cara', 'Anna', 'Ben'];
~names.splice(1, 0, 'Dan');~ // 1. Cuts open names at index 1 and inserts 'Dan' in place!

console.log(~names~); // 2. ['Cara', 'Dan', 'Anna', 'Ben'] -> the original names array was mutated!
```

Look closely at the three nuances here:
- **First, `slice` and `splice` differ by only one letter, and both take an index number, so they look like the same method, but they are NOT the same thing!** Remember the physical image inside each word: `splice` has a **`p`** and cuts the original film reel in place, mutating the array. By contrast, `slice` has **no `p`** and copies a slice of items into a new array, leaving the original array whole.
- **Second, spreading two `names.slice` calls and calling `names.splice` produce the exact same four names in order, but only the first one builds a new array for React!**
- **Third, inserting in the middle is the exact same spread recipe as adding at the start or end in Principle 1!** In Principle 1, we placed the new song before all old items or after all old items. Here, we use `slice` to copy the items before the insert spot and the items from that spot onward, and place the new song between them.

```tree caption="Why React state uses slice with no p to copy two halves around the new item, and never splice."
`slice` vs. `splice` when inserting `'Dan'` at index `1`
- +`slice` with no `p` [two `names.slice` calls + spread] | +**DO** use to copy parts of a state array | Copies `['Cara']` and `['Anna', 'Ben']` into a **brand-new array** with `'Dan'` between them | Leaves `names` **untouched**
- !`splice` with a `p` [`names.splice` at index `1`] | ~Do **NOT** call on a state array | Cuts open `names` at index `1` and **mutates it in place** | Passing `names` to the setter **skips the render**
```

### How `slice` copies a range of items without changing the array

Look at how `slice` works when you pass two numbers versus one number:

```js title="Plain JavaScript: how slice copies before and after insertAt"
const names = ['Cara', 'Anna', 'Ben'];
const insertAt = 1;

const before = ~names.slice(0, insertAt)~; // 1. From index 0 up to, not including, index 1 -> ['Cara']
const after = ~names.slice(insertAt)~; // 2. From index 1 to the end of the array -> ['Anna', 'Ben']
```

- **First, passing `0` and `insertAt` to the method** copies items starting at index 0 and stops **right before** `insertAt`. When `insertAt` is 1, it copies only index 0, which is `['Cara']`.
- **Second, passing only `insertAt` to `names.slice`** copies every item from index 1 all the way to the end of the array, which is `['Anna', 'Ben']`.

Newer JavaScript environments also include `toSpliced`, which works like `splice` on a copy and returns a brand-new array. However, two `slice` calls with spread is the standard React recipe you will read in codebases and interviews everywhere.

### Mistake 1: Using `splice` to insert the next song into `queue`

In a music player, the first row at index `0` is the song playing right now: Sunny Road. When the listener clicks **Play next** for Rainy Window, the new song should not replace Sunny Road at index `0`, and it should not go to the bottom. It belongs at index `1`, right after the song playing now!

### Mistake 2: Replacing `splice` with `slice` without building a new array

After reading a warning about `splice`, developers often make a second mistake. They delete the letter `p` so `queue.splice` becomes `queue.slice`, and keep the rest of the function the same:

## 4. Principle 4: Reordering Happens on a Copy: Copy First, Then Move, Sort, or Reverse the Copy

### Why sorting or swapping directly vs. copying first are NOT the same thing

Suppose we want to sort `names` alphabetically, or swap two items by their index. Look at what happens when you call `sort` directly on the array versus when you copy the array first with `[...names]`:

```js title="Way A: Calling sort directly on names"
const names = ['Cara', 'Anna', 'Ben'];
const sorted = ~names.sort()~; // 1. Sorts names in place AND returns that same names array!

console.log(~Object.is(names, sorted)~); // 2. true -> sorted and names are the exact same array box!
```

Now compare Way A with copying `names` into a brand-new array first with `[...names]` and then sorting that copy:

```js title="Way B: Copying with [...names] first, then sorting the copy"
const names = ['Cara', 'Anna', 'Ben'];
const sorted = ~[...names].sort()~; // 1. Copies names into a new array first, then sorts the new copy!

console.log(~names~); // 2. ['Cara', 'Anna', 'Ben'] -> original names array stays in its old order!
console.log(~Object.is(names, sorted)~); // 3. false -> sorted is a brand-new array box!
```

Look at the three confusions that catch developers when reordering an array:
- **First, calling `sort` directly on the array and calling it on `[...names]` both evaluate to Anna, Ben, and Cara, but `names.sort` is NOT a new array!** Both `sort` and `reverse` rearrange the original array in place and then return that exact same original array. If you pass `names.sort` directly to `setNames`, you are still passing the original array box back to React, so the state check returns true and skips the render!
- **Second, assigning `next = queue` and spreading `next = [...queue]` look like two ways to make a copy, but they are NOT the same thing!** Look at both lines side by side:

```js title="Assigning the same array variable vs. copying with spread"
const nextSame = ~queue~; // 1. NOT a copy: nextSame and queue point at the exact same array box!
const nextCopy = ~[...queue]~; // 2. Real copy: builds a brand-new array box holding the same items!
```

Assigning `queue` to `nextSame` only creates a second variable name pointing at the exact same array in memory. Spreading `[...queue]` into `nextCopy` builds a brand-new array box.
- **Third, once you make a fresh copy with `[...queue]`, changing slots inside `next` by index or sorting or reversing it is completely safe!** Think of a seating plan pinned to a classroom wall. You must never scribble on the plan pinned to the wall. Yet once you walk to the photocopier and make your own fresh photocopy, nobody else has seen that photocopy yet. Rearranging rows on your fresh photocopy before handing it to React is a **local mutation**, which is completely safe. Newer JavaScript environments also offer `toSorted` and `toReversed`, which make the copy and reorder it in a single call.

```tree caption="Why reordering directly on state fails, while mutating a freshly created spread copy is safe."
Three ways developers try to reorder or swap items in `queue`
- !Mutate `queue` directly [`queue.sort` or `queue[i] = ...`] | ~Do **NOT** reorder the state array in place | Changes the existing array and returns that **same array** | `Object.is` returns **`true`** and **skips the render**
- !Assign without spread [`next = queue` then swap] | ~Do **NOT** copy the variable without `[...queue]` | `next` still points at the **exact same `queue` array** | `Object.is` returns **`true`** and **skips the render**
- +Copy with spread first [`next = [...queue]` then swap or `sort`] | +**DO** make a fresh copy first | Local mutation on `next` touches **only the new copy** | `Object.is` returns **`false`** and **re-renders**
```

### How swapping two items in a copied array works in plain JavaScript

In our music queue, the first row at index `0` is playing now, and the second row at index `1` is already sitting right below it. Any song from the third row down, where `index > 1`, can move one spot higher when the listener clicks **Move up**.

To swap the song at `index` with the song right above it inside a fresh copy `next`, we use a spare variable named `above`:

```js title="Plain JavaScript: swapping two adjacent items through a spare variable"
const next = ~[...queue]~; // 1. Make a brand-new copy of the array first
const above = ~next[index - 1]~; // 2. Save the song above in a spare variable so it is not lost
~next[index - 1] = next[index];~ // 3. Move the clicked song up into index - 1
~next[index] = above;~ // 4. Put the saved song down into index
```

If we overwrote `next[index - 1]` without saving its song in `above` first, the song in that upper slot would be lost forever. Holding it in `above` lets the two songs trade places cleanly.

### Mistake 1: Swapping two songs directly inside `queue`

Suppose a developer adds a **Move up** button to every row after the second row and swaps the two slots directly inside `queue`:

```jsx title="src/components/PlayQueue.jsx" startLine="34"

    const above = queue[index - 1];
    ~queue[index - 1] = queue[index];~ // **WRONG:** mutates the existing queue array in place!
    ~queue[index] = above;~ // **WRONG:** mutates the existing queue array in place!
    ~setQueue(queue);~ // **WRONG:** passes the same queue array back to React!
  }
```

When the listener clicks **Move up** on the third song, Night Train, nothing moves on the screen! The swap mutated `queue` in place, and passing that same array to `setQueue` caused React to skip the render.

### Mistake 2: Assigning `next = queue` before swapping

Next, suppose the developer tries to fix the bug by creating a variable `next` and assigning `queue` to it without spread before swapping:

```jsx title="src/components/PlayQueue.jsx" startLine="34"
  function handleMoveUp(index) {
    ~const next = queue;~ // **WRONG:** does NOT copy the array; next and queue are the exact same array!
    const above = next[index - 1];
    next[index - 1] = next[index];
    next[index] = above;
    ~setQueue(next);~ // **WRONG:** next is still the same array box that React already holds!
  }
```

When the listener clicks **Move up** on Night Train, the screen still does not change! Why didn't assigning `queue` to `next` make a second array?
1. In JavaScript, assigning an array variable without `[...queue]` copies only the reference link to the existing array.
2. Both `next` and `queue` point at the exact same array box in memory, so swapping inside the variable still mutates the state array.
3. When `setQueue` runs with `next`, the state check compares the two references, returns true, and skips the render again.

### Copying the queue with spread before swapping the two songs

Now we change that first line so `next` is built with `[...queue]` as a brand-new array copy, and then swap the two slots inside that copy:

```jsx title="src/components/PlayQueue.jsx" startLine="34"

    ~const next = [...queue];~ // 1. Creates a brand-new array copy with the same songs
    const above = next[index - 1];
    ~next[index - 1] = next[index];~ // 2. Safe local mutation on the brand-new next array
    next[index] = above;
    setPrevious(queue);
    ~setQueue(next);~ // 3. Hands the brand-new reordered array to React
  }
```

In our `<ol>` list, we show the **Move up** button on every row where `index > 1`:

> [!PRINCIPLE]
> **Principle 4: Reordering Happens on a Copy: Copy First, Then Move, Sort, or Reverse the Copy**
>
> *Before swapping items by index or calling `sort`, copy the state array first with `[...queue]`, reorder that copy, and pass the copy to the setter.*
>
> Array methods that reorder items, such as `sort` and `reverse`, and index assignments mutate the array they are called on. Even though `queue.sort` returns the sorted list, it returns the exact same `queue` array it just mutated, so React skips the render. Copying the array first with `[...queue]` gives you a brand-new array that no other code points at yet. You can then freely swap, sort, or reverse that copy before passing it to `setQueue`.
>
> **DO THIS:**
> ```jsx
> function handleMoveUp(index) {
>   ~const next = [...queue];~ // 1. Copy the array into a brand-new box first
>   const above = next[index - 1];
>   ~next[index - 1] = next[index];~ // 2. Mutating the fresh copy is a safe local mutation
>   next[index] = above;
>   setQueue(next);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleMoveUp(index) {
>   const above = queue[index - 1];
>   ~queue[index - 1] = queue[index];~ // **WRONG:** mutates the existing state array in place!
>   queue[index] = above;
>   ~setQueue(queue);~ // **WRONG:** passes the same array back, so React skips the render!
> }
> ```

## 5. Principle 5: A Copied Array Still Holds the Same Songs, So Changing One Song Means a New Song Object

### Why mutating an item inside a copied array and replacing it with `map` are NOT the same thing

In Principle 4, we learned that `[...people]` makes a brand-new array so we can swap or reorder slots inside `copy`. That leads to one of the most common questions in React interviews. **Once I copy the array with `[...people]`, can I also change a property inside one of its objects, like `copy[0].seen = true`?**

Look at both ways of marking Anna as seen side by side. First, look at Way A, which copies the array with `[...people]` and then sets `copy[0].seen` to true:

```js title="Way A: Copying the array, then mutating copy[0].seen in place"
const people = [{ id: 1, name: 'Anna', seen: false }];
const copy = ~[...people]~; // 1. New outer array, but copy[0] still points at the exact same Anna object!
~copy[0].seen = true;~ // 2. Mutates that shared Anna object in place!

console.log(~people[0].seen~); // 3. true -> the original people[0] object was secretly changed too!
```

Now compare Way A with Way B, which uses `map` and object spread `{ ...p }` to create a brand-new object for Anna:

```js title="Way B: Using map and object spread to replace only the changed object"
const people = [{ id: 1, name: 'Anna', seen: false }];
const next = ~people.map(p => p.id === 1 ? { ...p, seen: true } : p)~; // Builds a new array AND a new Anna object!

console.log(~next[0].seen~); // true -> the new Anna object in next has seen: true
console.log(~people[0].seen~); // false -> the original Anna object in people is still untouched!
```

Read this distinction carefully, because it is the #1 subtle bug in React state arrays:
- **When you click the button on the page, Way A and Way B both produce a brand-new outer array, so BOTH ways re-render the screen right away! It looks the same on the first click, and it seems to work the same at first, but it is NOT the same thing!**
- **Why does Way A corrupt the original `people` array even though we wrote `[...people]`?** Because copying an array with `[...people]` is **shallow**! In JavaScript, objects do not really sit inside an array. Instead, each slot of the array holds a reference link pointing at an object in memory. Think of a photocopy of a party guest list. Spreading `[...people]` gives you a brand-new sheet of paper, yet every line on that new sheet still points at the exact same real person in the room. Both `copy[0]` and `people[0]` are that exact same object! When you set `copy[0].seen` to `true`, you reach through the new sheet and put a hat on the real person. As a result, the original guest list in `people` now sees that hat too!
- **Why does Way B keep the original `people` array clean?** It applies the exact same nested-state rule we learned for objects: copy every level on the path to the change. Here, `map` builds a brand-new outer array, and `{ ...p }` builds a brand-new inner object for the one person who changed. Every unchanged person is returned as is.

```tree caption="Why copying an array is shallow: copy[0] and people[0] point at the exact same object until map builds a new object for the changed item."
What happens when you update an object inside a state array
- !Shallow array copy + mutate item [`copy = [...people]`, then `copy[0].seen = true`] | ~Re-renders on click, **but is NOT the same thing!** | `copy[0]` and `people[0]` point at the **exact same object** | Secretly mutates `people[0]`, **breaking `Undo` and earlier snapshots!**
- +`map` + object spread [`people.map` with `{ ...p, seen: true }`] | +**DO** copy both the array and the changed item | Creates a **new array** AND a **new object** for the changed item | Leaves `people[0]` **untouched** with `seen: false`
```

### Mistake: Flipping `song.liked` inside a copied array breaks `Undo`

Let us watch this shallow-copy trap break our music player's **Undo** button on stage. We want to add a **Like** button to every song row that switches to **Liked** when clicked.

Suppose a developer writes `handleLike` by copying `[...queue]` into a variable, flipping the song's `liked` field in place, saving the old array, and updating state:

```jsx title="src/components/PlayQueue.jsx" startLine="43"
  function handleLike(index) {
    const next = [...queue];
    ~next[index].liked = !next[index].liked;~ // **WRONG:** mutates the shared song object that queue also points to!
    setPrevious(queue);
    ~setQueue(next);~ // Re-renders because next is a new array, hiding the bug on the first click!
  }
```

Watch what happens when the listener clicks **Like** on Blue Bicycle and then clicks **Undo**:
1. The listener clicks **Like** on Blue Bicycle. Because `next` is a new outer array, React re-renders and the button changes to **Liked** right away. Everything looks as if it worked!
2. Next, the listener decides to take the like back and clicks **Undo**.
3. The **Undo** button disappears, yet the button on Blue Bicycle stays stuck on **Liked**!

Why did **Undo** fail to bring back **Like** when no line ever wrote to `previous`?
1. When `[...queue]` ran, slot 1 of `next` and slot 1 of the old array both pointed at the **exact same Blue Bicycle object** in memory.
2. When `next[1].liked` flipped to `true`, it mutated that single shared Blue Bicycle object in place.
3. When `setPrevious` saved the old `queue` array for **Undo**, slot 1 of that old array was pointing at that **same, already-liked Blue Bicycle object**!
4. When **Undo** restored `previous`, React read `song.liked` from that corrupted object and rendered **Liked** again! In the official React docs, the exact same bug happens when two bucket lists start from one shared array. Checking an item in one list checks it in the other list too, because both arrays point at the same item objects.

### Replacing only the liked song with `map` and object spread

To fix `handleLike` so `previous` keeps the unliked song intact, we call `queue.map` and return a new spread object only for the matching song:

```jsx title="src/components/PlayQueue.jsx" startLine="43"
  function handleLike(id) {
    setPrevious(queue);
    ~setQueue(queue.map(s => s.id === id ? { ...s, liked: !s.liked } : s));~ // New array + new song object for the liked song
  }
```

In our `<ol>` list, we add the **Like** button to every row:


Look at `{ ...s }` inside `queue.map`. You do not see `id` or `title` written inside those curly braces! Where do they come from, and why does **Undo** work now?
1. Calling `queue.map` runs the arrow function once for each song `s`.
2. For Sunny Road and Night Train, `s.id === 2` is false, so the ternary returns the existing song object `s` unchanged. We do not waste work copying songs that did not change.
3. For Blue Bicycle, `s.id === 2` is true, so `{ ...s }` creates a **brand-new object**, copies its existing properties, and sets the liked flag to true.
4. The old `queue` array in `previous` still points at the original Blue Bicycle object with its unliked flag. Meanwhile, the new queue on screen points at the new Blue Bicycle object with `liked: true`.
5. When the listener clicks **Undo**, `setQueue` restores `previous`, whose Blue Bicycle object still has its unliked flag, and the button flips right back to **Like**!

What if a component needs to transform several items at once, such as unliking every song or moving every shape down on a canvas? Calling `map` handles that too by returning a new `{ ...s }` object for every item that needs the update. And when state arrays hold deeply nested objects, teams sometimes use the **Immer** library so `draft` updates build these nested copies automatically.

## Putting All Five Principles Together

### The complete project files

Here are the complete files of our **Up Next** music player queue, bringing all five array principles together in one component.

First, our main application file imports and renders `PlayQueue`:

```jsx title="src/App.jsx"
import ~PlayQueue~ from './components/PlayQueue.jsx'; // Renders the Up Next music queue component

export default function App() {
  return <PlayQueue />;
}
```

Second, our queue file implements adding with spread, removing with `filter`, inserting with `slice`, moving up on a copy, toggling likes, and restoring the previous queue:

```jsx title="src/components/PlayQueue.jsx"
import { useState } from 'react';

let nextId = 4;

const initialQueue = [
  { id: 1, title: 'Sunny Road', liked: false },
  { id: 2, title: 'Blue Bicycle', liked: false },
  { id: 3, title: 'Night Train', liked: false },
];

export default function PlayQueue() {
  const [queue, setQueue] = useState(initialQueue);
  const [previous, setPrevious] = useState(null);

  function handleAddToQueue() {
    setPrevious(queue);
    ~setQueue([...queue, { id: nextId++, title: 'Rainy Window', liked: false }]);~ // Principle 1: Spread to add at end
  }

  function handleRemove(id) {
    setPrevious(queue);
    ~setQueue(queue.filter(s => s.id !== id));~ // Principle 2: Filter to remove into a new array
  }

  function handlePlayNext() {
    const insertAt = 1;
    const newSong = { id: nextId++, title: 'Rainy Window', liked: false };
    setPrevious(queue);
    ~setQueue([...queue.slice(0, insertAt), newSong, ...queue.slice(insertAt)]);~ // Principle 3: Two slices to insert at index 1
  }

  function handleMoveUp(index) {
    const next = [...queue];
    const above = next[index - 1];
    next[index - 1] = next[index];
    next[index] = above;
    setPrevious(queue);
    ~setQueue(next);~ // Principle 4: Copy first, then swap on the copy
  }

  function handleLike(id) {
    setPrevious(queue);
    ~setQueue(queue.map(s => s.id === id ? { ...s, liked: !s.liked } : s));~ // Principle 5: Map + object spread to update one item
  }

  function handleUndo() {
    setQueue(previous);
    setPrevious(null);
  }

  return (
    <section>
      <h1>Up Next</h1>
      <p>
        Suggested: Rainy Window{' '}
        <button onClick={handleAddToQueue}>Add to queue</button>{' '}
        <button onClick={handlePlayNext}>Play next</button>{' '}
        {previous && <button onClick={handleUndo}>Undo</button>}
      </p>
      <ol>
        {queue.map((song, index) => (
          <li key={song.id}>
            {song.title}
            {index === 0 && ' · Now playing'}{' '}
            <button onClick={() => handleLike(song.id)}>
              {song.liked ? 'Liked' : 'Like'}
            </button>{' '}
            {index > 1 && <button onClick={() => handleMoveUp(index)}>Move up</button>}{' '}
            <button onClick={() => handleRemove(song.id)}>Remove</button>
          </li>
        ))}
      </ol>
    </section>
  );
}
```

| :--- | :--- | :--- |
| **Adding an item** | Call `queue.push` or `queue.unshift` in place | Pass `[...queue, song]` for the end or `[song, ...queue]` for the start |
| **Removing an item** | Call `queue.splice`, `pop`, or `shift` in place | Call `queue.filter` with `s.id !== id` so the old array stays whole |
| **Inserting in the middle** | Call `queue.splice` at `insertAt` in place | Spread two `queue.slice` calls with the new song between them |
| **Reordering or sorting** | Call `queue.sort`, `queue.reverse`, or swap `queue[i]` directly | Copy first with `const next = [...queue]`, then swap, sort, or reverse `next` |
| **Changing one item's field** | Copy the array and mutate `next[i].liked = true` on the shared object | Call `queue.map` and return `{ ...s, liked: !s.liked }` for the target song |

## For the Interview

> **The Interview Question:** How do you add, remove, insert, and reorder items in a state array?

### How to Answer Clearly in 30 Seconds

"In React, every array stored in state must be treated as read-only. In JavaScript, an array is a kind of object, and a state setter checks whether the state changed using `Object.is`. Mutating the existing array in place with `push`, `splice`, `sort`, or `reverse` and passing that same array back makes `Object.is` return `true` and skips the re-render. Instead, we always pass a brand-new array to the setter using non-mutating recipes:
1. **To add**: spread the old items into a new array, using `[...arr, newItem]` to append at the end or `[newItem, ...arr]` to prepend at the start.
2. **To remove**: call `arr.filter` with a test like `item.id !== id`, which returns a new array without that item and leaves the old array untouched.
3. **To insert in the middle**: spread two `slice` calls with the new item between them inside new square brackets, never `splice`.
4. **To reorder**: copy the array first with `const next = [...arr]`, swap or call `sort` or `reverse` on `next`, or use `toSorted` and `toReversed`.
5. **To update an object inside the array**: because array copying is shallow, both the old array and the copied array point at the same item objects. We call `arr.map` and return a brand-new `{ ...item }` object for the changed item so the old item object stays untouched."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does calling `push`, `splice`, or `sort` on a state array leave the screen unchanged, and when might the mutated items suddenly show up?"**
   - Because `push`, `splice`, and `sort` modify the existing array in place rather than creating a new array. Passing that mutated array back to `setQueue` makes `Object.is` compare the array with itself, return `true`, and skip re-rendering. However, the new items were already written into that array in memory. If an unrelated state variable in the component triggers a re-render later, the component reads the mutated array and all the hidden changes jump onto the screen.
2. **"If I copy the array first with `const next = [...queue]`, why is `next[0].liked = true` still a bug even though the screen re-renders?"**
   - Because `[...queue]` only makes a **shallow copy**. The outer `next` array is new, which is why `Object.is` returns `false` and the screen re-renders on the first click. However, `next[0]` and `queue[0]` still point at the exact same song object in memory. Mutating `next[0].liked = true` corrupts the song object inside earlier snapshots and inside any saved `previous` array for Undo, and it breaks child components using `memo`. We must copy every level on the path to the change using `queue.map` and object spread `{ ...s, liked: true }`.
3. **"What is the difference between `slice` and `splice`, and how do newer methods like `toSorted`, `toReversed`, and `toSpliced` help?"**
   - `slice` has no `p` and is non-mutating: it returns a shallow copy of a portion of the array and leaves the original array untouched. `splice` has a `p` and mutates the original array in place by inserting or deleting items. Newer JavaScript methods like `toSorted`, `toReversed`, and `toSpliced` are the non-mutating counterparts of `sort`, `reverse`, and `splice`. They copy the array and apply the change in a single call, returning a brand-new array ready for `setQueue`.

```tree dir=right caption="Quick interview reference: mutating array methods to avoid vs. non-mutating React state recipes."
Updating an array in React state
- +Add [`[...arr, item]` `[item, ...arr]`] | Replaces `push` and `unshift` | Returns a **new array** with the item at the end or start
- +Remove [`arr.filter` with `x.id !== id`] | Replaces `pop`, `shift`, and `splice` | Returns a **new array** without the item and keeps the old array intact
- +Insert [two `arr.slice` calls + spread] | Replaces `splice` at index `i` | Assembles two non-mutating **`slice` copies** around the new item
- +Reorder [`const next = [...arr]` then `sort` or swap] | Replaces direct `arr.sort` or `arr[i] = ...` | Applies safe **local mutation** to a fresh copy, or uses `toSorted`
- +Update item [`arr.map` with `{ ...x }`] | Replaces `next[i].field = ...` on a shallow copy | Builds both a **new array** and a **new item object**
```
