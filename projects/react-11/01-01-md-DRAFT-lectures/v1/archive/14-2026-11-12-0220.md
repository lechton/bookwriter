## Why React Components Must Be Pure

### A pure function vs. an impure function in four lines

Before we open a project, compare two tiny JavaScript functions that both take a number and return a number.

First, look at a function that multiplies its input by `2`:

```js title="A pure function: same input always gives the same output"
function ~double~(number) { // 1. Uses only its input and changes nothing outside
  return 2 * number;
}

console.log(~double(3)~); // First call with 3 -> returns 6
console.log(~double(3)~); // Second call with 3 -> still returns 6!
```

Now compare that with a function that adds its input to a `total` variable sitting outside the function:

```js title="An impure function: changes an outside variable on every call"
let total = 0;

function ~addToTotal~(number) { // 2. Reaches outside and changes total on every call!
  ~total = total + number~; // Changes a variable that existed before the call
  return total;
}

console.log(~addToTotal(3)~); // First call with 3 -> returns 3
console.log(~addToTotal(3)~); // Second call with 3 -> returns 6!
```

**At first glance, `double` and `addToTotal` both take a number and return a number, so they look like the same kind of function, but they are NOT the same thing!**

When you call `double` with `3`, you get `6` every single time, whether you call it once or a hundred times. When you call `addToTotal` with `3`, the first call gives `3` and the second call with the exact same input gives `6`, because `addToTotal` changes `total`, a variable that existed before the function was called.

In React, every component you write is supposed to work like `double`:

```jsx title="A pure React component: same props always return the same JSX"
function ~Greeting~({ name }) { // Uses only its name prop and changes nothing outside
  return <h1>Hello, ~{name}~</h1>;
}
```

Pass `name="John"` into `Greeting`, and it returns `<h1>Hello, John</h1>` every time React calls it.

Look at the three everyday words that unlock this whole chapter:
- **What does "pure" mean?** In everyday English, **pure** means nothing extra is mixed in from outside, like pure water. Think of the math formula `y = 2x`: when `x` is `3`, `y` is always `6`, no matter the time of day. Or think of a kitchen recipe: follow the same recipe with the same ingredients and you get the same dish every time, whereas a cook who secretly tosses in leftover ingredients from the counter gets a different dish on every batch. In JavaScript and React, a **pure function** follows two simple rules:
  1. **It minds its own business**: it does not change any variable or object that existed before it was called.
  2. **Same inputs, same output**: given the same inputs, it always returns the exact same result.
- **What is a "side effect"?** In everyday life, as with medicine, a **side effect** is an extra result you did not ask for that happens on the side of the main job. A component's main job during rendering is to calculate and return JSX from its props and state. Changing anything outside the component, such as changing an outside variable, adding to an outside array, or changing the browser page directly, is a side effect.
- **What does "mutation" mean?** In everyday English, a **mutation** is a change to the thing itself. In JavaScript, **mutation** means changing an existing variable, array, or object in place instead of leaving it alone or working on a fresh copy:

```tree caption="The difference between a pure function or component and an impure one."
Pure vs. impure functions and components
- +Pure [`double` and `Greeting`] | **Minds its own business** and leaves outside values untouched | **Same inputs, same output**: calling it with `3` or `name="John"` returns the **exact same result** every time
- !Impure [`addToTotal`] | Reaches outside and **mutates a variable or object** that existed before the call | **Same input, different output**: calling it twice with `3` returns **`3` first and `6` second**
```

### The three places where code can live in a component file

If a component must not cause side effects while rendering, where do we put code that actually needs to change things? Inside a React component file, a line of code can sit in one of **three places**:

```jsx title="The three places where code can live inside a component"
function MyPage() {
  const label = ~'Dark mode'~; // Place 1: In the component body -> runs during render, must stay PURE

  function handleToggle() {
    ~console.log('User clicked')~; // Place 2: Inside an event handler -> runs on user click, side effects belong here!
  }

  return <button onClick={handleToggle}>{label}</button>;
}
```

Each place runs at a different moment and has its own rule:
1. **Place 1 is the component body**: Lines written directly at the top level of the component run **during render**, every time React calls the component. Only pure calculations that turn props and state into JSX belong here, along with changes to brand-new variables created inside that very same render.
2. **Place 2 is an event handler**, such as `handleToggle`: Lines written inside an event handler run **only when the user acts**, such as clicking a button, and **never during render**. Side effects such as updating an outside counter, logging a user action, or calling a state setter belong here.
3. **Place 3 is an Effect**, written with `useEffect`: Lines inside an Effect run **after React commits the screen update**, as a last resort when a side effect is not caused by a user event.

```tree caption="The three places where code can live in a component and when each one runs."
Where code lives inside a React component
- +1. Component body [top-level lines before `return`] | Runs **during render** every time React calls the component | +**DO** keep this **100% pure**: calculate JSX from props and state only
- +2. Event handler [`function handleToggle` on `onClick`] | Runs **only when the user clicks**, never during render | +**DO** put **side effects** here: update state, count clicks, or log actions
- +3. Effect [`useEffect` after commit] | Runs **after** React updates the DOM on screen | Use only as a **last resort** when no user event caused the side effect
```

### Why purity matters on a real shopping list page

To see how an impure component breaks a real page, we will build `My Shopping List`. The page shows the heading `My Shopping List`, three numbered grocery items `1. Milk`, `2. Bread`, and `3. Eggs`, a summary line reminding the shopper to bring `Shopping bags`, and a `Dark mode` button that switches the page between light mode and dark mode.

Why is a `Dark mode` button on a shopping list the clearest test of component purity? Because clicking `Dark mode` only flips a theme state in `App`. It changes **nothing** about the grocery items. Yet when `App` re-renders for the new theme, React calls every child component inside `App` again.

When a component is impure, it often looks completely fine on the very first load. Both the pure shopping list and the impure shopping list display `1. Milk`, `2. Bread`, and `3. Eggs` when the page first opens. **It may look the same, and it may seem to work the same at first, but it is NOT the same thing!** On the very first click of the `Dark mode` button, the pure list stays at `1. Milk`, `2. Bread`, and `3. Eggs`, while the impure list jumps to `4. Milk`, `5. Bread`, and `6. Eggs`, and its summary line repeats `Shopping bags` over and over!

### What we need from plain JavaScript and earlier lessons

Before Principle 1, let us quickly recall a few building blocks and meet three small array helpers:
- **Props and state are read-only inputs**: A parent passes data to a child through attributes on a JSX tag, and the child reads those `props` without changing them. Inside `App`, `useState` keeps the `dark` theme state between renders, and calling `setDark` triggers a re-render of `App` and every child component it returns.
- **A variable outside every function keeps its value between calls**: When you write `let number = 0` at the very top of a `.jsx` file, outside all functions, JavaScript creates that variable once when the file loads. Every call to a function in that file reads and changes that same shared variable.
- **Three small array helpers**: In plain JavaScript, an array such as `['Milk', 'Bread', 'Eggs']` holds a list of items in order. Look at the three array methods we will use in Principle 3:

```js title="Plain JavaScript: .push, .slice, and .join on an array"
const groceries = ['Milk', 'Bread', 'Eggs'];

const copy = ~groceries.slice()~; // 1. .slice() with no arguments makes a brand-new copy of the array
~copy.push('Shopping bags')~; // 2. .push() adds an item to the end of that array in place
const text = ~copy.join(', ')~; // 3. .join(', ') turns the items into one string separated by commas
```

Here is what each of those three methods does:
1. **`.slice`** with nothing between its parentheses makes a **brand-new array copy** with the same items, leaving the original `groceries` array untouched.
2. **`.push`** mutates the array it is called on by adding a new item to the end of that array in place.
3. **`.join`** glues every item of the array into a single text string with a comma and a space between items, such as `'Milk, Bread, Eggs, Shopping bags'`.

### Four Principles of Pure Components

**PRINCIPLES:** React may call your component functions at any time and any number of times. Because of that, every component must act like a pure formula during render, which gives us four practical rules for daily debugging and interviews:
1. **Principle 1: Pure Components Return the Same JSX for the Same Inputs**: A component must use only its inputs and never change a variable that existed before it ran. If a component increments an outside variable during render, its numbers climb on every re-render even when its own props never change.
2. **Principle 2: StrictMode Calls Every Component Twice in Development**: Wrapping your app in `StrictMode` makes React call each component function twice in development. A pure component shows the exact same page, while an impure component exposes its bug on the very first load instead of hiding until a later re-render.
3. **Principle 3: Never Mutate an Outside Array During Render, Use Local Mutation Instead**: Pushing into an array that arrived from outside, such as a prop, mutates the parent's array and repeats items on every render. Creating a brand-new array or copy inside the same render and pushing into that local array is completely safe.
4. **Principle 4: Put Side Effects in Event Handlers, Never in the Component Body**: Code written directly in the component body runs on every render, whereas code inside an event handler runs only when the user acts. Side effects such as counting clicks or logging user actions belong in event handlers, with `useEffect` kept as a last resort.

Here is the complete map of all four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Same Inputs, Same JSX: Never Change Outside Variables in Render** | Changing a module-level counter during render looks right on first load, then shows wrong numbers after every state re-render. | Pass changing data in through props or state, and never modify variables created outside the component during render. |
| **Principle 2** | **StrictMode Double Rendering in Development** | Developers see doubled numbers in development and remove `StrictMode`, which only hides an impurity bug that still breaks in production on re-render. | Keep `StrictMode` enabled in `main.jsx` so double rendering catches impure components on the first load in development. |
| **Principle 3** | **Outside Mutation vs. Local Mutation of Arrays** | Calling `.push` on a prop array during render adds duplicate items on every render, while interviews test when `.push` is allowed. | Never mutate a prop or outside array during render; copy it first with `.slice` or create a new local array inside the same render. |
| **Principle 4** | **Side Effects Belong in Event Handlers** | Putting a click counter or log in the component body counts renders instead of user clicks and runs twice in `StrictMode`. | Place side effects inside event handlers like `onClick`, which run only on user actions and never during render. |

## 1. Principle 1: A Pure Component Returns the Same JSX for the Same Inputs and Changes Nothing That Existed Before It Ran

### Why an impure component looks right on first load, but is NOT the same thing as a pure component

Before we touch our shopping list files, compare two small components that both display a numbered item on the screen.

First, look at a component that receives both `number` and `name` through its `props`:

```jsx title="Option A: A pure component that reads number from props"
function ~PureItem~({ number, name }) { // 1. Uses only its props and changes nothing outside
  return <li>{number}. {name}</li>;
}
```

Now compare that with a component that keeps `let number = 0` outside the function and adds `1` to it every time the component runs:

```jsx title="Option B: An impure component that changes an outside variable during render"
let number = 0;

function ~ImpureItem~({ name }) {
  ~number = number + 1~; // **WRONG:** mutates an outside variable while rendering!
  return <li>{number}. {name}</li>;
}
```

When you render three items on the page for the first time without `StrictMode`, **both components show the exact same list on the screen: `1. Milk`, `2. Bread`, `3. Eggs`, with zero Console errors!** **It may look the same, and it may seem to work the same at first, but it is NOT the same thing!**

Why do the two components behave completely differently as soon as the page re-renders?
- **In Option A**, `PureItem` minds its own business. Whenever React calls `<PureItem number={1} name="Milk" />`, it reads `1` and `'Milk'` from its props and returns `<li>1. Milk</li>` every single time.
- **In Option B**, `ImpureItem` changes the outside `number` variable every time React calls it. On the first render, `number` climbs from `0` to `1`, `2`, and `3`. On the next render, `number` is already `3`, so calling the exact same three tags with the exact same `name` props returns `4. Milk`, `5. Bread`, and `6. Eggs`!

```tree caption="Why a pure component and an impure component look identical on first load, then split apart on re-render."
How `PureItem` and `ImpureItem` behave across renders
- +`PureItem` [reads `{ number, name }` from `props`] | Leaves everything outside the component **untouched** | Returns **`1. Milk`, `2. Bread`, `3. Eggs`** on first load **and on every re-render**
- !`ImpureItem` [runs `number = number + 1` on an outside `let`] | Looks right on first load, **but is NOT the same thing!** | Every re-render adds to the old `number`, jumping to **`4, 5, 6`** and then **`7, 8, 9`!**
```

### What happens when a component changes an outside variable during render

Let us watch this mistake happen step by step in our shopping list project. First, our startup file mounts the main component on the page without any extra check wrapper:

```jsx title="src/main.jsx" startLine="1"
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

const root = createRoot(document.getElementById('root'));
~root.render(<App />)~; // Mounts App once on startup
```

Next, a developer wants each grocery item to number itself automatically without typing the numbers on the tags. So in the item file, the developer creates a counter variable at the top of the file and adds one to it inside the item component:

```jsx title="src/components/Item.jsx" startLine="1"
~let number = 0~; // 1. Created once outside Item when Item.jsx loads

export default function Item({ name }) {
  ~number = number + 1~; // **WRONG:** changes the outside number variable during render!
  return <li>{number}. {name}</li>;
}
```

Then, in the main file, we keep a state variable for the page theme and render three item tags above a button that switches between light mode and dark mode:

```jsx title="src/App.jsx" startLine="1"
import { useState } from 'react';
import Item from './components/Item.jsx';

export default function App() {
  const [dark, setDark] = ~useState(false)~; // 1. Keeps the light or dark theme state

  function handleToggle() {
    ~setDark(!dark)~; // 2. Flips dark state and triggers a re-render of App
  }

  return (
    <main className={dark ? 'page dark' : 'page'}>
      <h1>My Shopping List</h1>
      <ul>
        ~<Item name="Milk" />~ {/* 3. Three Item tags with only the name prop */}
        <Item name="Bread" />
        <Item name="Eggs" />
      </ul>
      <button className="theme-btn" onClick={handleToggle}>
        {dark ? 'Light mode' : 'Dark mode'}
      </button>
    </main>
  );
}
```

Look at what happens in the browser when you open the page and click the theme button:
1. **On the first load**: The page shows `1. Milk`, `2. Bread`, and `3. Eggs` with the button `Dark mode`. Everything looks right!
2. **After clicking `Dark mode` once**: The background switches to dark, the button label switches to `Light mode`, and the three grocery items suddenly change to **`4. Milk`**, **`5. Bread`**, and **`6. Eggs`**!
3. **After clicking `Light mode` a second time**: The list jumps again to **`7. Milk`**, **`8. Bread`**, and **`9. Eggs`**, with zero warnings or errors in the Console!

### Why clicking the theme button made the item numbers climb

Look closely at `App.jsx` and `Item.jsx` above. In `App.jsx`, clicking the button only calls `setDark` with `!dark`. Nothing in `handleToggle` mentions `Item` or `number`, and the three `<Item />` tags still pass the exact same `name="Milk"`, `name="Bread"`, and `name="Eggs"` props. Why did `Item` run again, and why did its numbers climb to `4`, `5`, and `6`?

Here is what JavaScript and React do in order:
1. When `src/components/Item.jsx` loads for the first time, JavaScript creates `let number = 0` once at the top of the module file.
2. On the first render, React calls `App`, and then calls `Item` three times for `Milk`, `Bread`, and `Eggs`. Each call adds `1` to that shared `number`, so `number` becomes `1`, then `2`, then `3`.
3. When the shopper clicks `Dark mode`, `setDark` updates the state in `App` to `true`. As we learned in the render lifecycle, updating state in a parent component makes React call `App` again and then call every child component that `App` returns.
4. React calls `Item` three more times with the exact same `name` props. Because `number` sits outside `Item`, it was never reset to `0`. It still holds `3` from the first render, so the three new calls push `number` to `4`, `5`, and `6`!

```tree dir=right caption="How the outside number variable in Item.jsx keeps climbing every time App re-renders."
What happens to `let number = 0` across renders
- +1. File loads once [`src/components/Item.jsx`] | JavaScript creates **`number` = `0`** at the top of the file
- +2. First render [3 `<Item />` tags run] | `Item` adds `1` three times | Page shows **`1. Milk`, `2. Bread`, `3. Eggs`** and `number` stays at **`3`**
- !3. Click `Dark mode` [`setDark` re-renders `App` and its children] | `Item` runs 3 more times starting from **`3`** | Page jumps to **`4. Milk`, `5. Bread`, `6. Eggs`** and `number` stays at **`6`!**
```

### Passing the item number as a prop so the component stays pure

To make `Item` pure, we remove the outside counter from the item file and pass each item's number in through its `props`.

First, in the item file, we read both the number and the name from the component's props and return the list item without changing anything outside:

```jsx title="src/components/Item.jsx" startLine="1"
export default function Item({ ~number, name~ }) { // 1. Reads number and name from props; changes nothing outside
  return <li>~{number}~. {name}</li>; // 2. Always returns the exact same JSX for the same props
}
```

Second, in the main file, we pass each item's number as a prop on its tag:

```jsx title="src/App.jsx" startLine="10"
  return (
    <main className={dark ? 'page dark' : 'page'}>
      <h1>My Shopping List</h1>
      <ul>
        ~<Item number={1} name="Milk" />~ {/* 1. Passes number=1 and name="Milk" via props */}
        ~<Item number={2} name="Bread" />~ {/* 2. Passes number=2 and name="Bread" via props */}
        ~<Item number={3} name="Eggs" />~ {/* 3. Passes number=3 and name="Eggs" via props */}
      </ul>
      <button className="theme-btn" onClick={handleToggle}>
        {dark ? 'Light mode' : 'Dark mode'}
      </button>
    </main>
  );
```

Where does `number` inside `Item` come from now? Each `<Item />` tag in `App.jsx` passes its own `number` attribute, which React places into that component's `props` object. Now, when the shopper clicks `Dark mode` and React calls `Item` again, the first `<Item />` still receives `{ number: 1, name: 'Milk' }` and still returns `<li>1. Milk</li>` every single time:

Two more interview rules follow directly from Principle 1:
- **Never pass data between components through a shared outside variable**: Because React does not promise the order in which components render, one component must never write to an outside variable like `currentPerson` expecting another component like `Header` to read it. Components always share data through **props**, **state**, or **context**, and all three inputs are strictly read-only during render.

In technical interviews, a function that always returns the exact same output for the same inputs is called **idempotent**.

## 2. Principle 2: `<StrictMode>` Calls Every Component Twice in Development So Impure Code Shows on the First Load

### Why calling a function twice is the simplest test of purity

Look back at our two plain JavaScript functions from the start of the lecture: `double` and `addToTotal`. Suppose you want an automatic test that catches an impure function right away, before anyone clicks a button on the page. How can you test whether a function is pure?

**Call the function twice in a row with the same input and check whether the second answer changes!**

```js title="Calling a function twice to test whether it is pure"
console.log(double(3)); // 1st call -> 6
console.log(~double(3)~); // 2nd call -> still 6! Pure!

console.log(addToTotal(3)); // 1st call -> 3
console.log(~addToTotal(3)~); // 2nd call -> changes to 6! Impure!
```

That is the entire idea behind React's **`<StrictMode>`**:

```jsx title="Wrapping <App /> in <StrictMode> inside src/main.jsx"
import { ~StrictMode~ } from 'react'; // 1. Imported as a named export from react

root.render(
  ~<StrictMode>~ {/* 2. Calls every component inside it TWICE in development */}
    <App />
  </StrictMode>
);
```

- **Why is it called `StrictMode`?** Think of a **strict** math teacher who checks your work by asking you to calculate the same formula a second time. If you solved `y = 2x` purely from `x = 3`, your second calculation still gives `6`. If you secretly added to a running total on scrap paper, your second calculation gives `6` instead of `3`, and the teacher catches the mistake immediately!
- **Why do developers get confused when they see `2. Milk`, `4. Bread`, `6. Eggs` inside `<StrictMode>`?** Two things look confusing at first glance:
  1. When an impure component shows `2. Milk`, `4. Bread`, `6. Eggs` on the first load, **it looks as if `<StrictMode>` broke your numbers, but it did NOT!** The bug was already inside `Item.jsx`. Without `<StrictMode>`, that bug hid on the first load and waited until the user clicked `Dark mode`. With `<StrictMode>`, React calls `Item` twice right away so the bug shows up on the very first load!
  2. When you run the development server with `npm run dev`, the impure list shows `2. Milk`, `4. Bread`, `6. Eggs`, whereas when you build for production with `npm run build`, the first load shows `1. Milk`, `2. Bread`, `3. Eggs`. **The code is the exact same thing!** Only the development build calls each component twice; in the production build, `<StrictMode>` does nothing at all and calls each component once:

```tree caption="What happens when <StrictMode> calls a component twice in development."
How `<StrictMode>` tests your components in development
- +Pure component [`Item` reading `{ number, name }`] | 1st call returns `1. Milk`; 2nd call returns `1. Milk` | **Looks the exact same** with or without `<StrictMode>`
- !Impure component [`Item` changing outside `number`] | 1st call makes `number` `1`; 2nd call makes `number` `2` | Shows **`2. Milk`, `4. Bread`, `6. Eggs` on the very first load** so you spot the bug immediately!
```

### What happens when an impure component runs inside `<StrictMode>`

When you create a new React project with Vite, the startup file wraps the main component in `<StrictMode>` by default. First, we wrap our main component inside `<StrictMode>` in the startup file:

```jsx title="src/main.jsx" startLine="1"
import { ~StrictMode~ } from 'react'; // 1. Import StrictMode from react
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

const root = createRoot(document.getElementById('root'));
root.render(
  ~<StrictMode>~ {/* 2. Wraps <App /> so React double-calls components in development */}
    <App />
  </StrictMode>
);
```

Inside the item file, suppose the developer still keeps the counter variable at the top of the file:

```jsx title="src/components/Item.jsx" startLine="1"
let number = 0;

export default function Item({ name }) {
  ~number = number + 1~; // **WRONG:** runs twice per item in StrictMode!
  return <li>{number}. {name}</li>;
}
```

When the developer saves and looks at the browser in development, before anyone clicks a single button, the page on the very first load already shows **`2. Milk`**, **`4. Bread`**, and **`6. Eggs`**! And if the shopper clicks `Dark mode` once, the numbers jump straight to **`8. Milk`**, **`10. Bread`**, and **`12. Eggs`**!

### How `<StrictMode>` turns 1, 2, 3 into 2, 4, 6 on the first load

Look at `App.jsx` and `main.jsx`. Nowhere in our files did we write six `<Item />` tags, and nowhere did we write `number = number + 2`. Where did the second call for each item come from, and why did the odd numbers `1`, `3`, and `5` disappear?

In development, wrapping `<App />` in `<StrictMode>` tells React to call every component function **twice** per render and keep the second call's result:
1. For `<Item name="Milk" />`, React calls `Item` a first time, which changes `number` from `0` to `1`. React immediately calls `Item` a **second time** for `Milk`, which changes `number` from `1` to `2`, and puts **`2. Milk`** on the page.
2. For `<Item name="Bread" />`, React calls `Item` once, changing `number` to `3`, and then a second time, changing `number` to `4`, and puts **`4. Bread`** on the page.
3. For `<Item name="Eggs" />`, React calls `Item` once, changing `number` to `5`, and then a second time, changing `number` to `6`, and puts **`6. Eggs`** on the page.
4. When the shopper clicks `Dark mode`, React renders the list again and calls each of the three items twice more, pushing `number` to `8`, `10`, and `12`!

```tree dir=right caption="How <StrictMode> calls each <Item /> twice on the first load in development."
First load of impure `Item` inside `<StrictMode>`
- +1. `<Item name="Milk" />` [called twice] | Call 1 sets `number` to `1`; Call 2 sets `number` to **`2`** | Page shows **`2. Milk`**
- +2. `<Item name="Bread" />` [called twice] | Call 1 sets `number` to `3`; Call 2 sets `number` to **`4`** | Page shows **`4. Bread`**
- +3. `<Item name="Eggs" />` [called twice] | Call 1 sets `number` to `5`; Call 2 sets `number` to **`6`** | Page shows **`6. Eggs`**
```

### Why removing `<StrictMode>` from `main.jsx` only hides the bug

When beginners see `2. Milk`, `4. Bread`, and `6. Eggs` on their screen, they often search online, find out that `<StrictMode>` calls components twice, and delete `<StrictMode>` from `src/main.jsx`. Or they build the app for production with `npm run build`, see `1. Milk`, `2. Bread`, and `3. Eggs` on the first load, and assume the problem was only a development quirk.

Deleting `<StrictMode>` is a classic mistake! Removing `<StrictMode>` does not fix `Item.jsx`. It only turns off the alarm bell so the bug hides on the first load and breaks as soon as a real user clicks `Dark mode`.

### Keeping `<StrictMode>` enabled with our pure `Item` component

Now we keep `<StrictMode>` in the startup file and use our pure item component that reads its number and name from props:

export default function Item({ ~number, name~ }) { // Pure: calling this twice with number=1 returns "1. Milk" both times!
  return <li>{number}. {name}</li>;

Eggs` on the first load and after every click!

And if you inspect the browser's **Elements panel**, you will see that `<StrictMode>` adds **zero HTML elements** to the DOM:

- **Which functions does `<StrictMode>` call twice in development?** It calls your component function bodies twice, and it also calls functions you pass to `useState` and state setter functions twice. It **never** calls event handlers twice.
- **Zero cost in production**: `<StrictMode>` is completely inactive in a production build created by `npm run build`, so leaving it in `src/main.jsx` never slows down your live site.
- **Wrapping part of the tree**: You can wrap the entire `<App />` in `<StrictMode>`, or wrap only one branch of a large application tree while migrating older code. Inside a branch wrapped by `<StrictMode>`, there is no way for a child component to opt out.

> [!PRINCIPLE]
> **Principle 2: `<StrictMode>`: Double Rendering in Development Catches Impure Components on Load**
>
> *Keep `<StrictMode>` around `<App />` in `src/main.jsx`; when a component looks wrong in `<StrictMode>`, fix the impure code inside the component instead of removing `<StrictMode>`.*
>
> In development only, `<StrictMode>` calls every component function twice on each render. If a component is pure, calling it twice with the same inputs produces the exact same JSX, so you never notice the second call. >

> ```jsx title="src/main.jsx"

>     <App />
>   </StrictMode>
> );
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/main.jsx"
> root.render(
>   ~<App />~ // **WRONG:** removing StrictMode to "fix" doubled numbers only hides an impurity bug!
> );
> ```

## 3. Principle 3: Changing an Array That Came From Outside Breaks the Page, but Changing an Array Made in the Same Render Is Fine

### Why pushing into an outside array and pushing into a local array are NOT the same thing

In Principle 1, our impure component changed a **number** that lived outside the function. The exact same purity rule applies when a component works with an **array** or an **object**.

Before we add a summary line to our shopping list, look closely at these two plain JavaScript functions that both end by calling `.push` with `'Shopping bags'`.

First, look at a function that pushes directly into the `groceries` array created outside it:

```js title="Way 1: Pushing into an array that existed BEFORE the function ran"
const groceries = ['Milk', 'Bread', 'Eggs'];

function addBagsOutside() {
  ~groceries.push('Shopping bags')~; // **WRONG:** mutates the outside groceries array in place!
  return groceries.join(', ');
}
```

Second, look at a function that makes a fresh copy with `.slice` inside the function and pushes into that local copy:

```js title="Way 2: Pushing into a fresh array created INSIDE the function"
const groceries = ['Milk', 'Bread', 'Eggs'];

function addBagsLocal(items) {
  const ~list = items.slice()~; // 1. Creates a brand-new array copy inside this call
  ~list.push('Shopping bags')~; // 2. Local mutation: changes only the brand-new copy!
  return list.join(', ');
}
```

**Look at `groceries.push` in Way 1 and `list.push` in Way 2. Both lines call `.push`, and on the very first call both functions return `'Milk, Bread, Eggs, Shopping bags'`. It may look the same, and it may work the same on the first call, but it is NOT the same thing!**

Two nuances here clear up one of the most common points of confusion in React interviews:
1. **Why does Way 1 break on the second call while Way 2 stays clean?**
   - **In Way 1**, `groceries` existed **before** `addBagsOutside` was called. Think of `groceries` as a shared family shopping list taped to the refrigerator door. Every time `addBagsOutside` runs, it writes `'Shopping bags'` in marker right onto the fridge list. Call it a second time, and the fridge list now ends with `'Shopping bags, Shopping bags'`!
   - **In Way 2**, `items.slice` makes a **brand-new photocopy** of the list inside `addBagsLocal` and names it `list`. Pushing `'Shopping bags'` into `list` only writes on that fresh photocopy. When the function finishes, the photocopy is thrown away, and the original `groceries` list on the fridge still has only `'Milk'`, `'Bread'`, and `'Eggs'`!
2. **Is calling `.push` during render always forbidden in React?**
   **No!** Developers often hear the word **mutation** and think `.push` is completely banned inside a component. What React forbids is changing an array or object that **already existed before the render started**, such as a prop or a module-level array. Creating a brand-new array inside the component and calling `.push` on it during that same render is called **local mutation**, and React allows it completely because no code outside that single render can ever see the new array!

```tree caption="Mutating an array that came from outside the render vs. mutating a brand-new array created inside the same render."
Two kinds of array mutation during render
- !Outside mutation [`items.push` on a prop or outside array] | Writes onto the **shared fridge list** that existed **before** the render | Every render adds another `'Shopping bags'` to the same array!
- +Local mutation [`list.push` on `items.slice` or `[]` made in this render] | Writes onto a **fresh photocopy** created **inside** this render | Original array stays **3 items long**, and every render outputs `'Shopping bags'` **once**
```

### What happens when a child component pushes into a prop array during render

Let us see how outside array mutation breaks our shopping list page. We want to add a summary component below the list that joins the grocery items into one sentence and always adds `'Shopping bags'` at the end as a reminder.

First, in the main file, we place a three-item grocery array at the top of the file and pass it as a prop to the summary component below the list:

```jsx title="src/App.jsx" startLine="1"
import { useState } from 'react';
import Item from './components/Item.jsx';
import ListSummary from './components/ListSummary.jsx';

~const groceries = ['Milk', 'Bread', 'Eggs']~; // 1. Array of 3 items created outside App

export default function App() {
  const [dark, setDark] = useState(false);

  function handleToggle() {
    setDark(!dark);
  }

  return (
    <main className={dark ? 'page dark' : 'page'}>
      <h1>My Shopping List</h1>
      <ul>
        <Item number={1} name="Milk" />
        <Item number={2} name="Bread" />
        <Item number={3} name="Eggs" />
      </ul>
      ~<ListSummary items={groceries} />~ {/* 2. Passes groceries into ListSummary as the items prop */}
      <button className="theme-btn" onClick={handleToggle}>
        {dark ? 'Light mode' : 'Dark mode'}
      </button>
    </main>
  );
}
```

Next, in the summary file, a developer pushes the reminder item directly into the incoming prop array and joins the items into one line:

```jsx title="src/components/ListSummary.jsx" startLine="1"
export default function ListSummary({ ~items~ }) {
  ~items.push('Shopping bags')~; // **WRONG:** mutates the items prop array that came from App!
  return <p className="summary">You need: {items.join(', ')}</p>;
}
```

Look at what happens in the browser when you save the file with `<StrictMode>` active in development:
1. **On the very first load**: The summary line already says **`You need: Milk, Bread, Eggs, Shopping bags, Shopping bags`**, with `Shopping bags` repeated twice!
2. **After clicking `Dark mode` once**: The summary line grows to **four** `Shopping bags` at the end!
3. **After clicking `Light mode` a second time**: The summary line grows to **six** `Shopping bags`, with zero Console warnings!

### Why pushing into the `items` prop changed the `groceries` array in `App.jsx`

Look closely at `App.jsx` and `ListSummary.jsx`. Nowhere in `App.jsx` did we add `'Shopping bags'` to `groceries`. Inside `ListSummary.jsx`, the developer only called `.push` on its own parameter named `items`. Why did `groceries` keep growing across every render?

In JavaScript, passing an array as a prop does **not** make a copy of the array. Both `groceries` in `App.jsx` and `items` in `ListSummary.jsx` point to the **exact same array in memory**:
1. When `App.jsx` loads, JavaScript creates one three-item array `['Milk', 'Bread', 'Eggs']` in memory and names it `groceries`.
2. When `App` renders `<ListSummary items={groceries} />`, React passes that same array into `ListSummary` as `props.items`.
3. On the first `<StrictMode>` call in development, `items.push` adds a fourth item directly into that shared array. Now `groceries.length` is `4`.
4. On the second `<StrictMode>` call during that same initial load, `ListSummary` receives the same `groceries` array, which already has four items, and pushes a fifth item into it! Now `groceries.length` is `5`, and the screen shows `Shopping bags, Shopping bags`.
5. Even in a production build where `<StrictMode>` does not double-call, the first load pushes `groceries.length` to `4` and the first click on `Dark mode` pushes it to `5`, showing `Shopping bags, Shopping bags` to real shoppers!

```tree dir=right caption="Because props.items points to the same array as groceries, items.push mutates groceries in place."
How `items.push` inside `ListSummary` corrupts `groceries` in `App`
- +1. `App.jsx` loads [`const groceries = ['Milk', 'Bread', 'Eggs']`] | Creates **one array** in memory with **length `3`**
- !2. 1st call to `ListSummary` [`items.push` on shared array] | `items` points to `groceries`; mutates it to **length `4`**
- !3. 2nd `<StrictMode>` call [`items.push` on same array] | Mutates `groceries` to **length `5`** | Page shows **`Shopping bags, Shopping bags`** on first load!
```

### Copying the array with `.slice` before pushing so the mutation stays local

To fix the summary component, we leave the incoming prop array untouched. Inside the function, we copy the array first with `.slice` and push the extra item into that new local copy:

```jsx title="src/components/ListSummary.jsx" startLine="1"
export default function ListSummary({ items }) {
  const ~list = items.slice()~; // 1. Makes a brand-new copy of items inside this render
  ~list.push('Shopping bags')~; // 2. Local mutation: adds 'Shopping bags' only to the new copy
  return <p className="summary">You need: {~list.join(', ')~}</p>; // 3. Joins the 4-item local copy
}
```

Why does the screen now show `You need: Milk, Bread, Eggs, Shopping bags` while `groceries` in `App.jsx` never has `'Shopping bags'` inside it?
1. Each time React calls `ListSummary`, `items.slice` creates a brand-new array in memory containing `'Milk'`, `'Bread'`, and `'Eggs'`, and names that copy `list`.
2. `list.push` adds `'Shopping bags'` only to `list`, so `list` has four items while `groceries` in `App.jsx` stays untouched at three items.
3. `list.join` turns `list` into the sentence `Milk, Bread, Eggs, Shopping bags` for the `<p>` tag.
4. On the second `<StrictMode>` call and on every `Dark mode` click, `items.slice` copies the untouched three-item `groceries` array again, so `Shopping bags` appears **once** every single time!

You could also write `, Shopping bags` directly inside the `<p>` tag right after the `.join` result without calling `.push` at all. Both approaches follow the same rule: **never mutate the incoming `items` prop array**.

`items` is the parent's `groceries` array, so every render pushes another `'Shopping bags'` into it.

`items.slice` creates a fresh array inside this render, leaving `groceries` at 3 items.

> [!PRINCIPLE]
> **Principle 3: Outside vs. Local Mutation: Never Mutate an Array That Existed Before the Render**
>
> *Never call `.push` or mutate an array or object that came from outside the component, such as a prop; if you need to add items during render, copy the array first with `.slice` or create a new local array inside the same render.*
>
> Passing an array through `props` hands the child component the exact same array in memory that the parent holds. Calling `.push` on that prop mutates the parent's array in place, so every re-render and every `<StrictMode>` check adds duplicate items to the page. Calling `.push` on a brand-new array created inside the same render is a local mutation and is completely safe, because that array did not exist before the render began and nothing outside the component sees it.
>
> **DO THIS:**
> ```jsx title="src/components/ListSummary.jsx"
> export default function ListSummary({ items }) {
>   const ~list = items.slice()~; // 1. Copy the prop array into a new local array first
>   ~list.push('Shopping bags')~; // 2. Safe local mutation on the new copy
>   return <p className="summary">You need: {list.join(', ')}</p>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ListSummary.jsx"
> export default function ListSummary({ items }) {
>   ~items.push('Shopping bags')~; // **WRONG:** mutates the parent's array in place on every render!
>   return <p className="summary">You need: {items.join(', ')}</p>;
> }
> ```

## 4. Principle 4: Side Effects Belong in Event Handlers, Which Never Run During Render

### Why a line in the component body and a line inside an event handler are NOT the same thing

Principles 1, 2, and 3 showed what a component must **never** do while rendering. That raises the big practical question of this chapter: **a real app eventually has to change things, such as counting user clicks, logging analytics, or updating state, so where do side effects belong?**

Look at two places where you can write the exact same two lines, `switches = switches + 1` and `console.log`, inside `App`.

First, look at those two lines placed directly at the top level of the component body, above `return`:

```jsx title="Place A: Side effect written directly in the component body"
let switches = 0;

function App() {
  ~switches = switches + 1~; // **WRONG:** sits in the component body -> runs on EVERY render!
  ~console.log('Theme switches counted:', switches)~; // Logs twice on load in StrictMode before any click!

  return <button>Dark mode</button>;
}
```

Now compare that with putting the exact same two lines inside `function handleToggle`, which is passed to `onClick={handleToggle}`:

```jsx title="Place B: Side effect written inside the handleToggle event handler"
let switches = 0;

function App() {
  function handleToggle() {
    ~switches = switches + 1~; // Sits inside handleToggle -> runs ONLY when the user clicks!
    ~console.log('Theme switches counted:', switches)~; // Logs 0 times on load, and once per click!
  }

  return <button ~onClick={handleToggle}~>Dark mode</button>; // Hands handleToggle to React for clicks
}
```

**Look closely at `function handleToggle` in Place B. It is written right inside `function App`! Because both snippets sit between the opening and closing curly braces of `App`, it looks as if both run whenever `App` renders, but they are NOT the same thing!**

Here is the exact rule that tells you whether a line of code inside a component runs during render:
- **Lines at the top level of the component body**, as in Place A, run **during render**, every single time React calls `App`. That includes the initial page load, the second `<StrictMode>` check call in development, and every state re-render!
- **Lines inside an event handler function**, as in Place B, do **not** run during render. During render, JavaScript only creates the `handleToggle` function definition and passes it to `onClick={handleToggle}`. React calls `handleToggle` **only when the shopper clicks the button**. Because event handlers do not run during render, **event handlers do not need to be pure**, and **`<StrictMode>` never calls event handlers twice**!

```tree caption="How to tell whether code inside a component runs during render or only when the user acts."
Two places inside `function App`
- !Top-level component body [lines outside any inner function] | Runs **during render** on startup, in `<StrictMode>`, and on every re-render | ~Do **NOT** put side effects here: counts **renders**, not user clicks!
- +Inside an event handler [`function handleToggle` passed to `onClick`] | Defined during render, **but runs ONLY when the user clicks** | +**DO** put side effects here: `<StrictMode>` calls it **once per click**
```

### What happens when you count user actions in the component body instead of the click handler

Suppose our product team asks us to count how many times shoppers switch the page theme between light and dark, and print `Theme switches counted:` with the current number in the Console.

First, look at what happens when a developer creates a counter variable at the top of the main file and adds one to it directly inside the component body:

```jsx title="src/App.jsx" startLine="1"
import { useState } from 'react';
import Item from './components/Item.jsx';
import ListSummary from './components/ListSummary.jsx';

const groceries = ['Milk', 'Bread', 'Eggs'];
~let switches = 0~; // 1. Counter outside App

export default function App() {
  const [dark, setDark] = useState(false);

  ~switches = switches + 1~; // **WRONG:** top-level body runs on every render, not on click!
  ~console.log('Theme switches counted:', switches)~; // **WRONG:** logs during render!

  function handleToggle() {
    setDark(!dark);
  }
```

Below `handleToggle`, `App` returns the same shopping list markup as before:

```jsx title="src/App.jsx" startLine="18"
  return (
    <main className={dark ? 'page dark' : 'page'}>
      <h1>My Shopping List</h1>
      <ul>
        <Item number={1} name="Milk" />
        <Item number={2} name="Bread" />
        <Item number={3} name="Eggs" />
      </ul>
      <ListSummary items={groceries} />
      <button className="theme-btn" onClick={handleToggle}>
        {dark ? 'Light mode' : 'Dark mode'}
      </button>
    </main>
  );
}
```

Look at Chrome's **Console panel** when the page loads in development with `<StrictMode>` and the shopper clicks the theme button twice:
1. **On the first load, before anyone clicks the button**: The Console already logs `Theme switches counted: 1` and `Theme switches counted: 2`!
2. **After the 1st click on `Dark mode`**: The Console logs `Theme switches counted: 3` and `Theme switches counted: 4`.
3. **After the 2nd click on `Light mode`**: The Console reaches `Theme switches counted: 5` and `Theme switches counted: 6` for just two clicks!

Even if you build for production where `<StrictMode>` does not double-call `App`, loading the page still logs `Theme switches counted: 1` when the shopper has clicked **zero** times, and two clicks log `3`, because code in the component body counts **renders of `App`**, not **clicks on the button**!

### Moving the side effect into the `handleToggle` event handler

To count real theme switches, we move the counter and the log out of the component body and place them inside the click handler, right before the state update:

```jsx title="src/App.jsx" startLine="1"
import { useState } from 'react';
import Item from './components/Item.jsx';
import ListSummary from './components/ListSummary.jsx';

const groceries = ['Milk', 'Bread', 'Eggs'];
let switches = 0;

export default function App() {
  const [dark, setDark] = useState(false);

  function handleToggle() {
    ~switches = switches + 1~; // 1. Runs ONLY when the shopper clicks the button
    ~console.log('Theme switches counted:', switches)~; // 2. Logs 1 on the 1st click and 2 on the 2nd click
    setDark(!dark);
  }
```

### Why `<StrictMode>` calls `App` twice on load, yet `handleToggle` runs zero times until you click

Look closely at `App.jsx` above. Nowhere in `App.jsx` did we call `handleToggle` with parentheses. We only wrote `onClick={handleToggle}` on the `<button>` tag. Why didn't `<StrictMode>` run `handleToggle` when it called `App` twice on startup?

Follow what JavaScript and React do in order:
1. **On initial load**: `<StrictMode>` calls `App` twice. Each call creates the `handleToggle` function and returns the JSX, without ever running the lines inside `handleToggle`. The Console stays completely empty on load!
2. **On the 1st click of `Dark mode`**: The browser reports the click, and React calls `handleToggle` **once**. `switches` changes from `0` to `1`, the Console logs `Theme switches counted: 1`, and `setDark` triggers a re-render.
3. **During the re-render**: `<StrictMode>` calls `App` twice again to compute the dark-mode JSX. Again, `handleToggle` is only defined, not called, so `switches` stays at `1`.
4. **On the 2nd click of `Light mode`**: React calls `handleToggle` once more, `switches` becomes `2`, and the Console logs `Theme switches counted: 2`!

### Two more questions interviewers ask about side effects and purity

1. **What if a developer changes the DOM directly during render, such as writing `document.title = ...` or setting `document.body.className = 'dark'` in the body of `App`?**
   Directly changing the DOM inside the component body is also a side effect during render! Whenever a change can be expressed as JSX, return it in your JSX instead, just as our `App` writes `<main className={dark ? 'page dark' : 'page'}>` so React updates the class during the commit step. And when a side effect truly cannot be expressed in JSX and is not caused by a user event, React provides **`useEffect`** as a last resort that runs **after** the render commits to the screen.
2. **Why does React care so much that rendering stays pure?**
   Because when calling a component has zero side effects, React can safely do three powerful optimizations across your application:
   - **Render on the server**: React can run the exact same component on a server for thousands of visitors without one visitor's render changing variables seen by another visitor.
   - **Skip unnecessary renders**: When a component's inputs have not changed, React can skip calling it again with `memo`, because a pure component is guaranteed to return the exact same JSX for the same inputs.
   - **Stop and restart a render at any time**: If new user input arrives while React is rendering a deep component tree, React can safely throw away the half-finished calculation and start fresh without leaving half-applied side effects on the page.

```tree caption="Why React requires every component function to stay pure during render."
Three reasons React insists on pure rendering
- +1. Server rendering | The same component can run for **many requests** without leaking outside variables between users
- +2. Skipping renders [`memo`] | When inputs stay the same, React can **skip calling the component** because its output cannot change
- +3. Restarting renders | React can **stop a render mid-way** when new data arrives and start over with **zero side effects** left behind
```

> [!PRINCIPLE]
> **Principle 4: Where Side Effects Belong: Put Side Effects in Event Handlers, Never in the Component Body**
>
> *Keep the component body strictly for pure JSX calculations; place side effects such as counting actions, mutating outside values, or logging into event handlers like `onClick`, with `useEffect` kept as a last resort.*
>
> Any line written at the top level of a component body runs during every render, including initial load and `<StrictMode>` double checks. Even though an event handler function is defined inside the component, its body does not run during render. React calls the handler only when the user performs the action, so handlers do not need to be pure and `<StrictMode>` never calls them twice.
>
> **DO THIS:**
> ```jsx title="src/App.jsx"
> function handleToggle() {
>   ~switches = switches + 1~; // Runs only when the button is clicked, never during render
>   console.log('Theme switches counted:', switches);
>   setDark(!dark);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/App.jsx"
> export default function App() {
>   ~switches = switches + 1~; // **WRONG:** sits in the component body and runs on every render!
>   console.log('Theme switches counted:', switches);
>   return <main>...</main>;
> }
> ```

## Putting All Four Principles Together

### The complete project files

Here are all four source files of our `My Shopping List` project working together with every principle in place.

First, `src/main.jsx` wraps `<App />` in `<StrictMode>` so React checks every component for purity in development:

```jsx title="src/main.jsx"
import { ~StrictMode~ } from 'react'; // Principle 2: Calls every component twice in development
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

const root = createRoot(document.getElementById('root'));
root.render(
  ~<StrictMode>~ {/* Keeps double-render purity checks active in development */}
    <App />
  </StrictMode>
);
```

Second, `src/components/Item.jsx` is a pure component that reads `number` and `name` from its `props` and changes nothing outside itself:

```jsx title="src/components/Item.jsx"
export default function Item({ ~number, name~ }) { // Principle 1: Pure component -> same props always return the same JSX
  return <li>~{number}~. {name}</li>; // No outside counter mutated during render
}
```

Third, `src/components/ListSummary.jsx` copies the incoming `items` prop with `.slice` before calling `.push`, keeping the array mutation local to this render:

```jsx title="src/components/ListSummary.jsx"
export default function ListSummary({ items }) {
  const ~list = items.slice()~; // Principle 3: Copies the prop array into a fresh local array
  ~list.push('Shopping bags')~; // Local mutation on the copy leaves the parent's groceries array untouched
  return <p className="summary">You need: {list.join(', ')}</p>;
}
```

Fourth, `src/App.jsx` keeps its component body pure and places the `switches` side effect inside the `handleToggle` event handler:

```jsx title="src/App.jsx"
import { useState } from 'react';
import Item from './components/Item.jsx';
import ListSummary from './components/ListSummary.jsx';

const groceries = ['Milk', 'Bread', 'Eggs'];
let switches = 0;

export default function App() {
  const [dark, setDark] = useState(false);

  function handleToggle() {
    ~switches = switches + 1~; // Principle 4: Side effect lives inside the click handler, not in render
    ~console.log('Theme switches counted:', switches)~; // Logs once per click
    setDark(!dark);
  }

  return (
    <main className={dark ? 'page dark' : 'page'}>
      <h1>My Shopping List</h1>
      <ul>
        ~<Item number={1} name="Milk" />~ {/* Principle 1: Passes each item number via props */}
        <Item number={2} name="Bread" />
        <Item number={3} name="Eggs" />
      </ul>
      ~<ListSummary items={groceries} />~ {/* Principle 3: groceries stays 3 items long across every render */}
      <button className="theme-btn" onClick={handleToggle}>
        {dark ? 'Light mode' : 'Dark mode'}
      </button>
    </main>
  );
}
```

| Aspect | The Impure Habit | The React Rule |
| :--- | :--- | :--- |
| **Numbering or configuring items** | Increment an outside `let number = 0` variable inside the component body during render | Pass `number` in as a prop so the same inputs always return the same JSX |
| **When `<StrictMode>` shows doubled output** | Delete `<StrictMode>` from `main.jsx` so the first load looks right | Keep `<StrictMode>` enabled and fix the outside mutation that its double render exposed |
| **Adding an item to an array for display** | Call `items.push` directly on the incoming prop array during render | Copy the array first with `items.slice` or create a brand-new local array inside the same render |
| **Counting clicks or running side effects** | Put the counter or `console.log` at the top level of the component body | Put side effects inside an event handler like `handleToggle`, which never runs during render |

## For the Interview

> **The Interview Question:** What does it mean for a component to be pure, and what breaks across renders when it is not?

### How to Answer Clearly in 30 Seconds

"In React, a component is pure when it follows the two rules of a pure function:
1. **It minds its own business**: it does not mutate any variable, array, or object that existed before React called it.
2. **Same inputs, same output**: given the same `props`, `state`, and `context`, it always returns the exact same JSX.

When a component breaks purity during render, such as incrementing an outside `let` variable or calling `.push` on a prop array, it may look right on the first load, but its output changes on every re-render even when its props never changed. Item numbers climb on every state update, and pushed array items repeat over and over.

To catch these bugs early, `<StrictMode>` calls every component function twice in development. A pure component is unaffected, while an impure component shows its bug on the first load. Note that **local mutation**, changing a brand-new array or object created inside the same render, is completely fine because nothing outside the render sees it. Finally, **side effects** belong in **event handlers** like `onClick`, which run only when the user acts and never during render, or in `useEffect` as a last resort. React insists on pure rendering so it can safely render components on the server, skip unchanged renders with `memo`, and stop or restart renders at any time."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does my component run twice in development, and should I remove `<StrictMode>` to stop it?"**
   **No, never remove `<StrictMode>` to fix a bug.** In development, `<StrictMode>` intentionally calls every component function twice on each render to test whether it is pure. If calling your component a second time changes what appears on the screen, your component is mutating something that existed before the render. Removing `<StrictMode>` or building for production with `npm run build` makes the component run once on load, which only hides the bug until the next state update triggers a re-render.
2. **"If React forbids mutating arrays during render, why is it okay to call `.push` on an array created inside the component?"**
   Purity only requires that a component not change anything that existed **before** the render started. A prop array or a module-level array existed before the render and is shared across renders, so calling `.push` on it changes the input for future renders. An array created inside the component during the current render, such as `const list = items.slice` or `const cups = []`, is brand-new on every call. React calls changing that new array **local mutation**, and it is safe because no code outside that render can observe it.
3. **"How can you tell whether code inside a component runs during render, and why don't event handlers need to be pure?"**
   Any code written at the top level of the component function body runs during render, every time React calls the component. Code written inside an event handler like `function handleToggle` is only defined during render; React runs it only when the user triggers the event. Because event handlers do not run during render, they do not need to be pure and `<StrictMode>` does not call them twice, making event handlers the primary place for side effects.

```tree dir=right caption="Interview comparison: code in the component body vs. code inside an event handler."
Component body vs. Event handler in an interview
- +Component body [runs during render] | Must be **pure** and **idempotent** | Called **twice** by `<StrictMode>` in development; allows **local mutation** only
- +Event handler [runs on user action] | Does **not** run during render and **need not be pure** | Called **once per event**; the right place for **side effects**
```
