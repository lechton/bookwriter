Updating Objects in State

Interview Question · ❱ CORE

How do you update an object in state without mutating it?

OverviewHow We Update an Object Held in State

Changing a field inside the state object vs. passing a brand-new object to the setter

When state holds a number like 0, calling the setter with 5 never changes that old number from the inside. Numbers, strings, and booleans cannot be changed from the inside in JavaScript. Calling setX simply replaces the old number with 5:

Replacing a number in state
1const [x, setX] = useState(0);
2
3function handleClick() {
4 setX(5);
Replaces 0 with 5: the number 0 itself never changed
5}

Now suppose state holds a JavaScript object with a user's name instead of a number. Compare two ways you might try to change that name when a button is clicked.

First, look at changing user.name inside the existing object and passing that same object back to the setter:

Way 1: Changing user.name inside the existing object
1const [user, setUser] = useState({ name: 'John' });
2
3function handleClick() {
4 user.name = 'Alice';
1. Changes the name property inside the existing user object
5 setUser(user);
2. Hands that exact same user object back to React -> page stays on "John"!
6}

Now compare that with building a brand-new object and passing the new object to the setter:

Way 2: Passing a brand-new object to setUser
1const [user, setUser] = useState({ name: 'John' });
2
3function handleClick() {
4 setUser({ name: 'Alice' });
Creates a brand-new object and hands it to React -> page shows "Alice"!
5}

In Way 1, clicking the button leaves the screen stuck on John. In Way 2, clicking the button updates the screen to Alice!

Look at the three silent confusions that trip developers up here:

  • First, changing user.name and passing user to the setter looks like passing a new object, and both objects hold 'Alice', but they are NOT the same thing! Way 1 hands React the exact same object it already holds in state. Way 2 hands React a brand-new object.
  • Second, calling the setter runs with zero errors in the Console, so it looks as if the update worked, but it did NOT reach the screen! React compares the object you passed with the object already in state. Because both are the very same object, React skips the render.
  • Third, when an object has several fields, spreading the old object with ...user and typing every unchanged field by hand into a new object are the exact same thing! Both build a brand-new object that keeps every old field and updates the changed field.

Look at the three words you will hear in every React team and interview:

  • What is a "mutation"? In everyday life, a mutation means a living thing changes from the inside while staying the same creature, like a caterpillar that turns into a butterfly. In JavaScript, changing a property inside an existing object is a mutation. Its contents change, yet it is still the exact same object.
  • Why does React ignore a mutated object? Imagine returning a library book after rewriting one page inside it. The librarian scans the barcode on the cover and sees the exact same book that is already checked in, so nothing new is filed. React checks the state object with Object.is, which checks the box on the outside rather than reading the fields inside. Handing React a brand-new object gives it a new box, so React renders the page again.
  • What does "read-only" mean? Think of a printed store receipt. You read every line on the receipt, and you never scribble over the ink to change the total. When the order changes, the cashier prints a brand-new receipt. Treating state as read-only means we read from the state object and replace it with a new object whenever a field changes:

Four ways to pass a new object to a state setter

Whenever you update an object in state, your goal is always to hand the setter a brand-new object. Depending on the shape of your object and how your handler runs, there are four ways to build that new object:

5 setOrder({ item: order.item, quantity: order.quantity + 1, giftWrap: order.giftWrap });

9 setOrder({ ...order, quantity: order.quantity + 1 });

Here is when each of the four ways fits in daily coding:

  1. Way 1, writing every field of the new object by hand: Fits when the object only has one or two fields, or when every field is built fresh on the spot, such as pointer coordinates from a mouse event.
  2. Way 2, spreading the old object with ... and writing the changed field after it: The normal everyday tool once an object has several fields. When a field sits inside a nested object, you spread once at each level on the path to the change.
  3. Way 3, placing that same spread inside an updater function: Fits when a single event queues several updates to the same state object before the next render. Notice the parentheses around the new object after the arrow =>. In JavaScript, curly braces right after => normally start a function body. Wrapping them in parentheses tells JavaScript to return an object literal instead.
  4. Way 4, using the optional library Immer: When state is deeply nested across many levels, a helper library called Immer can simplify the code. It lets you write mutating-looking code on a temporary draft object while Immer builds the new copies behind the scenes. Another common choice for deep objects is flattening the state structure itself, which a later lesson covers.

How our project files are organized

This lesson builds on six facts from earlier lessons, along with three small plain JavaScript ideas:

  • State variables and setters: Calling useState stores a value inside React and uses the initial value only on the first render. On every render, it gives back that render's snapshot along with a setter function.
  • How React skips unchanged state: When you pass a value to a setter, React compares it with the current state using Object.is. When Object.is returns true, React skips re-rendering the component and its children.
  • Local mutation vs. mutating existing data: Changing a brand-new object that you just created inside the running function is a local mutation. That is completely safe because no other code points at the new object yet. Changing an object that already lives in state or props is unsafe because other renders or components still share it.
  • Three dots ... and left-to-right order: On a JSX tag, {...article} opens the article object and copies its properties from left to right, so the last attribute written wins. Inside an object literal { ...order }, the exact same three dots copy properties into a new object in the same left-to-right order.
  • Objects pointing at other objects and shallow copies: When one object appears inside another object, the outer object actually holds a pointer to a separate inner object. Because ... copies only the top layer of properties, it is called a shallow copy, like shallow water at the surface of a pool.
  • Events, inputs, and computed property names: React passes an event object e to every event handler, where e.target is the DOM element where the event started. Inside an object literal, putting square brackets around a variable name, such as [key]: value, tells JavaScript to read the property name from that variable.

Four Principles of Updating Objects in State

PRINCIPLES

React never reaches inside your state object to check whether a property changed. Instead, React only checks whether the object you passed to the setter is a different object from the one it already holds. Four practical principles follow from that rule:

  1. Principle 1: Mutating Keeps the Same Object, Replacing Triggers a Render: Changing a field inside the existing state object and passing that same object back to the setter gives React the exact same object, so React skips the render. To update the screen, pass a brand-new object to the setter.
  2. Principle 2: Copy Existing Fields with Spread, Then Write the Changed Field Last: A state setter replaces the whole object rather than merging fields. Spread the old object first so no field is lost, and write the updated field after the spread so it wins from left to right.
  3. Principle 3: Spread Is Shallow, So Copy Every Level on the Path to a Nested Change: An inner object is a separate object in memory that the outer object points to. Spreading only the outer object shares the inner object, so a nested change must copy every level from the changed field up to the top object.
  4. Principle 4: Let One Handler Update Several Inputs by Reading the Input's Name: Give each input a name attribute that matches its field in the state object. Then one shared handler can read that name from the event and update whichever field changed.

Here is the complete map of those four principles before we walk through each one:

Why changing a property inside an object is NOT the same thing as replacing a number

Before we touch our shop files, look at why objects behave differently from numbers in JavaScript.

When a variable holds the number 0, you cannot open up the number 0 and change its insides. The only way to change a number state is to pass a different number, such as 5, to the setter.

An object is different. In JavaScript, an object is a container whose properties can be changed from the inside. Compare these two ways a developer might try to change a user's name in state:

Two ways a developer might try to change user.name to 'Alice'

6}

9 setUser({ name: 'Alice' });
Way B: passes a BRAND-NEW object to setUser -> screen shows "Alice"!
10}

Look closely at the three confusions that make Way A such a common trap:

  • First, Way A and Way B look like the same update, and in both cases the object's name property holds 'Alice', but they are NOT the same thing! Way A changes the inside of the existing object and hands that same object back to React. Way B builds a brand-new object in memory and hands the new object to React.
  • Second, because passing a new number like 5 to a setter always updates the screen, passing user to setUser after changing a property looks like it should work the same way, but it is NOT the same thing! A new number is always a different value, whereas a mutated object is still the exact same object in memory.
  • Third, when setUser runs in Way A without throwing any error, it looks as if the setter worked, but it did NOT update the screen!

To see why React ignores Way A, look at how JavaScript's Object.is compares two objects:

Why +1 stayed hidden and why Add gift wrap made the quantity jump to 3

Look closely at the two handlers above. Two mysteries stand out right away.

First, nothing in handleAddOne compares the old order with the new one. Who compares them, and why did two clicks on +1 leave the screen stuck on 1?

React compares them inside setOrder. Follow what JavaScript and React do on each click of +1:

  1. The first line of handleAddOne reaches inside the existing order object and raises its quantity from one to two.
  2. The second line passes order to setOrder, which is still that exact same object in memory.
  3. React compares the object you passed with the current state using Object.is. Because both sides are the very same object, Object.is returns true and the setter does nothing.
  4. React skips re-rendering the card and its children. Even though React may sometimes still call your component function once before skipping its children, it never updates the screen. After two clicks on the plus-one button, the screen still shows Quantity: 1 while order.quantity in memory is already three!

Shorthand operators like order.quantity++ and order.quantity += 1 mutate the existing property in the exact same way. And if you mutate order.quantity without calling setOrder at all, React has no idea the object changed. The official React docs compare that to trying to change your meal order after you have already eaten the meal.

Second, look at handleGiftWrap. Nothing in handleGiftWrap adds anything to the quantity. It only copies order.quantity and sets giftWrap: true. Why did clicking Add gift wrap make the quantity on screen jump to 3?

JavaScript reads order.quantity from the object that the two +1 clicks already mutated! Follow what happens when the shopper clicks Add gift wrap:

  1. After the two earlier clicks on the plus-one button, order.quantity inside the existing object in memory is already 3.
  2. Calling handleGiftWrap creates a brand-new object and copies order.quantity, which puts three into the new object.
  3. When setOrder receives that brand-new object, Object.is compares the old object with the new one and returns false.
  4. React renders the card again with the new object, putting both Quantity: 3 and Gift wrap: Yes on the screen at once! That is also why mutating state is so treacherous: when another state update happens to run nearby, a mutation can appear to work while hiding a serious bug.

Combining ...user and a changed field in the same object: before vs. after

In that spread line above, the spread ...user and the single property city: 'Paris' live together inside the same pair of curly braces.

Whenever you put a spread ...user and a single property like city: 'Paris' inside the same object literal, there are two ways to order them:

  • Order 1: ...user comes before city: 'Paris'. That means ...user is first on the left, and city: 'Paris' is second on the right.
  • Order 2: city: 'Paris' comes before ...user. That means city: 'Paris' is first on the left, and ...user is second on the right.

Look at both orders side by side:

1const user = { name: 'John', age: 30, city: 'Rome' };
2

4const order2 = { city: 'Paris', ...user };
Order 2: city: 'Paris' is first, ...user is last -> city is overwritten back to 'Rome'!

Order 1 and Order 2 contain the exact same pieces, but they are NOT the same thing!

Why do those two orders produce different cities? Because JavaScript builds an object literal from left to right, and when the same property name appears twice, whichever one comes last overwrites the earlier one:

  1. In Order 1, ...user runs first on the left and copies all three old properties, including 'Rome'. Then city: 'Paris' runs second on the right and replaces the old city with 'Paris'.
  2. In Order 2, city: 'Paris' runs first on the left and sets the city to 'Paris'. Then ...user runs second on the right and copies the old properties over it, overwriting the city back to 'Rome'!

Why mutating state breaks snapshots, debugging, and optimizations

Beyond breaking reset buttons like Start over, the official React documentation highlights five reasons why you should never mutate objects in state:

  1. Debugging: When you replace state objects instead of mutating them, earlier console.log lines keep the exact values from when they ran instead of getting overwritten by later mutations.
  2. Optimizations: React components can skip unnecessary re-renders when their props have not changed. Checking prevObj === obj is instant when replacing objects guarantees that the same object reference means nothing inside changed.
  3. Render snapshots and new React features: React's rendering model relies on every render having its own uncorrupted snapshot of state. Mutating an object changes the state inside previous render snapshots.
  4. Application features like Undo, Redo, and Reset: Keeping earlier state objects untouched in memory makes features like Start over, Undo, and edit history straightforward to build.
  5. No hidden Proxies required: Because you replace objects explicitly, React does not need to wrap every state object in hidden JavaScript Proxies just to detect changes.

What if your state object is nested three or four levels deep and spreading every level starts to look repetitive? Teams handle deep nesting in two ways. First, they can flatten the state structure into simpler pieces, which a later lesson covers. Second, they can use the optional library Immer, which gives you a temporary draft Proxy that records your changes and produces the nested copies automatically.

Principle 3

Nested Objects: Spread Copies One Level, So Copy Every Object on the Path

Because object spread ... is shallow, update a nested property by creating a new copy of every object on the path from the change up to the root.

In JavaScript, an object written inside another object is actually a separate object in memory that the outer object points to. Interview PrepFor the Interview

The Interview Question: How do you update an object in state without mutating it?

How to Answer Clearly in 30 Seconds

"We treat every object in React state as read-only. React never looks inside an object to check if a property changed; instead, the state setter compares the new value with the current state using Object.is. If we mutate user.name = 'Alice' on the existing object and pass user back to the setter, Object.is sees the exact same object reference. React then skips the re-render, leaving the change hidden until some unrelated render happens later.

To update an object properly, we create a brand-new object and pass it to the setter so React replaces the state and re-renders:

  1. Top-level fields with object spread: we pass { ...order, quantity: order.quantity + 1 } to setOrder. Because the setter replaces rather than merges, ...order comes first to copy existing fields, and the changed property comes after it so the last property wins.
  2. Nested objects: spread is shallow and only copies one level deep, so a nested object is a separate object the parent points to. We copy every level along the path, like { ...order, delivery: { ...order.delivery, time: 'Evening' } }, which keeps earlier snapshots and reset objects intact. Mutating a brand-new local object we just created is fine, and for deep nesting we can either flatten state or use Immer.
  3. Multiple form inputs: we give each input a name attribute matching its state key and share one handler using a computed property name, { ...order, [e.target.name]: e.target.value }."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why doesn't React re-render when I mutate order.quantity = 2 and pass order to setOrder, and why does that change show up on a later render?"
    When you call a useState setter, React compares the value you passed with the current state using Object.is. For objects, Object.is checks object identity in memory, not the properties inside. Mutating order.quantity = 2 changes the contents of the existing object while keeping the exact same object reference, so Object.is returns true and React bails out without re-rendering. However, the object in memory really was mutated. The next time an unrelated state update triggers a re-render, React reads the mutated order.quantity and puts the delayed change onto the screen all at once.
  2. "Is { ...order } a deep copy, and what goes wrong if you spread order into next, mutate next.delivery.time = 'Evening', and pass next to setOrder?"
    No. Object spread { ...order } is a shallow copy that copies only the top-level properties. In JavaScript, a nested object like order.delivery is a separate object in memory that the outer object only points to. After const next = { ...order }, next is a new top-level object, so setOrder will trigger a render. However, next.delivery still points at the exact same inner object as the previous render's snapshot and any shared initialOrder constant. Mutating next.delivery.time = 'Evening' corrupts past snapshots and breaks features like a Start over reset button or memo optimizations. You must copy every level on the path to the change.
  3. "How can one onChange handler update multiple text inputs on a form object, and when is mutating an object actually safe in React?"
    Give each <input> a name attribute matching its state key, and use a computed property name inside the spread: { ...order, [e.target.name]: e.target.value }. The square brackets evaluate e.target.name from the input that fired and overwrite that matching property after ...order. Mutating a fresh local object that you just created in the same function, like const next = {} and next.x = 10, is a local mutation. That is completely safe because no other component or earlier render snapshot points at that new object yet.
