Consolidating State Logic with useReducer

Interview Question · ❱ CORE

When does state logic outgrow useState, and how does a reducer consolidate it?

OverviewHow a Reducer Gathers All the Update Logic in One Place

Working out the next state in the handler vs. saying what the user did

So far, every state change has worked the same way: an event handler works out the next value and hands it to the setter. React's docs call that code the state update logic. While a component has one or two buttons, the update logic is easy to read. But when four buttons change the same state, each in its own way, the update logic is scattered across four handlers. That is the moment state logic outgrows useState. React gives us a second way to write the same component: the handlers only say what the user did, and one function holds all the update logic. That function is called a reducer, and the Hook that uses it is useReducer.

Here is one counter written both ways. First with useState, as in Lesson 12:

A counter with useState
1const [count, setCount] = useState(0);
2
3<button onClick={() => setCount(count + 1)}>Count: {count}</button>
The handler works out count + 1 itself

Now the same counter with useReducer:

The same counter with useReducer
1function reducer(count, action) {
2 if (action.type === 'incremented') {
3 return count + 1;
Count + 1 is worked out here, outside the handler
4 }
5}
6
7const [count, dispatch] = useReducer(reducer, 0);
8
9<button onClick={() => dispatch({ type: 'incremented' })}>Count: {count}</button>
The handler only says what happened

On the page, nobody can tell the two counters apart. Each button shows Count: 0 when the page opens and Count: 1 after one click by the user. Yes, it is the exact same thing! React's docs say it plainly: "You can always convert between useState and useReducer back and forth: they are equivalent!"

What the two share is everything the user sees: one state variable that React keeps between renders, and a function that React gives back to change it. The one difference is where the update logic lives. With useState, the handler works out the next value and passes it to setCount. With useReducer, the handler only reports what happened, and the function reducer works out the next value.

React's docs describe the second way like this: "Instead of telling React 'what to do' by setting state, you specify 'what the user just did' by dispatching 'actions' from your event handlers."

Think of a waiter in a restaurant. The waiter writes down what the customer ordered and hands the order to the kitchen. The waiter never cooks, and only the kitchen knows how each dish is made. An event handler that calls dispatch works the same way: it passes on what the user did, and only the reducer knows how the state changes because of it.

What is at stake

The key idea to remember is this: event handlers say what happened, the reducer says how the state changes in response, and React connects the two through dispatch.

What is at stake is what the user sees when one piece of update logic is wrong. Picture a cart where the Milk row suddenly shows minus one. If four handlers each hold their own update logic for the cart, the developer must read all four to find the one that let the quantity drop below zero. React's docs put it this way: "When you have a bug with useState, it can be difficult to tell _where_ the state was set incorrectly, and _why_." With a reducer, all the update logic sits in one function, and one log line inside it shows every action the user caused, in order.

Readers usually go wrong in four places:

  1. They think useReducer is a new kind of state, or state that the whole app shares. It is the state of one component, exactly as with useState. Sharing it with other components is Lesson 29.
  2. They think dispatch changes the state at once. It asks React for the next render, exactly as a setter does in Lesson 15.
  3. They put a side effect, such as an alert, inside the reducer, and the user sees it twice in development.
  4. They think every component should now use a reducer. The docs answer: "You don't have to use reducers for everything: feel free to mix and match!"

Five Principles of useReducer

PRINCIPLES

React's docs move a component from useState to useReducer in three steps: the handlers dispatch actions, a reducer function holds the update logic, and the component uses that reducer. The first three principles are those three steps. The last two say how to write a reducer well:

  1. Principle 1: dispatch Sends What the User Did: Each handler stops working out the next cart. It calls dispatch with an object that says what the user just did.
  2. Principle 2: cartReducer Holds All the Update Logic for the Cart: One function, written outside the component, takes the current cart and that object and returns the next cart.
  3. Principle 3: useReducer Hands Back the Cart and dispatch: One line replaces the useState line. React calls the reducer during the next render and gives the component the cart it returned.
  4. Principle 4: An alert Inside cartReducer Pops Up Twice: React calls the reducer during rendering, and twice in development, so the reducer may only work out the next cart.
  5. Principle 5: One emptied Action Clears the Whole Cart: Each action is one thing the user did, even when it changes many things in the cart. Then a log in the reducer reads as the list of the user's clicks.

Here is the complete map of the five principles before we walk through each one:

Section 1 · Principle 1dispatch Sends What the User Did

Two handlers for the same button that look alike

Here are two handlers for the Add one button. Each one makes a single call:

The handler with setCart
1function handleIncrease(id) {
2 setCart(cart.map(item => item.id === id ? { ...item, quantity: item.quantity + 1 } : item));

3}
The handler with dispatch
1function handleIncrease(id) {
2 dispatch({ type: 'increased', id: id });

It may look the same, but it is NOT the same thing! Both handlers make one call. The handler with setCart passes the next cart itself, so the update logic lives in the handler. The handler with dispatch passes a description of the click, and the next cart is worked out somewhere else, in Principle 2.

The word dispatch means to send something off to the place where it is handled, as a shop dispatches a parcel to the post office. The handler sends the description off. It does not handle it.

The action: a plain object that says what happened

The object passed to dispatch is called an action. Our code writes it, right inside the handler. React's docs say: "It is a regular JavaScript object. You decide what to put in it, but generally it should contain the minimal information about _what happened_."

By convention, the action has a type field, a string that names what happened. Any other information goes in other fields. In our cart, type: 'increased' names the click, and id: 1 says which row the user clicked:

The action for a click on Add one in the Bread row
1dispatch({ type: 'increased', ~id: 1~ });
Type names what happened; id is the one extra fact the reducer needs

The id comes from the button, exactly as before. The arrow function on the button of each row passes that row's id to handleIncrease, as Lesson 11 showed.

Nothing we have written creates dispatch yet. React's docs also write the handlers first and add dispatch "in a later step". Here that step is Principle 3, where useReducer gives dispatch to the component. Until then, a click on any button stops with an error that says dispatch is not defined.

Name the action after what the user did

Two action names can lead to the same cart and still not be the same thing. Compare these two actions for the Add one button:

An action named after the click, and one named after the change
1dispatch({ type: 'increased', id: 1 });
Says what the user did
2dispatch({ type: 'set_quantity', id: 1, quantity: 3 });
Says how the state should change

Both can leave Bread: 3 on the page. It may look the same, but it is NOT the same thing! With set_quantity, the handler had to work out the 3 itself, so the update logic is back in the handler. React's docs advise: "action types should ideally describe 'what the user did' rather than 'how you want the state to change'. This makes it easier to later add more features."

How long the name is does not matter. The docs: "The type is specific to a component, so in this example either 'added' or 'added_task' would be fine. Choose a name that says what happened!" In our cart, 'increased' and 'increased_item' would be the exact same thing.

The docs' own exercise shows a mistake that a wrong name hides. A chat page has a message box and a Send button. After every keystroke by the user, the box already dispatches edited_message with the new text. To clear the box when the user clicks Send, a developer reuses that action with an empty text:

Clearing a chat box when the user clicks Send
1dispatch({ type: 'edited_message', message: '' });
WRONG says the user typed an empty message
2dispatch({ type: 'sent_message' });
Says the user clicked Send; the reducer empties the box

The box empties either way, so the first line seems right. But the action now says the user typed an empty message, when the user really clicked Send. As the docs say: "From the user's perspective, sending a message is a different action than editing the field."

Principle 1

Actions: dispatch Sends What the User Did

In a component with a reducer, an event handler does not work out the next state; it calls dispatch with an action object that says what the user just did, with only the information the reducer needs.

When every handler holds its own update logic, a wrong number on the page can come from any of them. With actions, the handler only reports the click: a type that names it, such as 'increased', and the id of the row. The update logic moves out of the handler.

✓ DO THIS

2 dispatch({ type: 'increased', id: id });
Says what the user did
3}
✗ DO NOT DO THIS
1function handleIncrease(id) {
2 dispatch({ type: 'set_quantity', id: id, quantity: 3 });
WRONG the handler worked out the next quantity itself
3}

Section 2 · Principle 2cartReducer Holds All the Update Logic for the Cart

A reducer is a plain function you can call by hand

A reducer is a function that takes two inputs, the current state and an action, and returns the next state. It is plain JavaScript. It does not touch the page, and React is not involved yet. We can call one by hand:

A reducer called by hand, with no React at all
1function counterReducer(count, action) {
2 if (action.type === 'incremented') {
3 return count + 1;
4 }
5}
6
7counterReducer(0, { type: 'incremented' });
Returns 1
8counterReducer(5, { type: 'incremented' });
Returns 6

The state we pass in is called the current state, and the value the reducer returns is the next state. React's docs: "React will set the state to what you return from the reducer." That part comes in Principle 3.

The name comes from the array method reduce, which walks through a list and folds it into one value. Here it adds five numbers:

The array method reduce adds five numbers
1[1, 2, 3, 4, 5].reduce((result, number) => result + number);
Returns 15

The function passed to reduce "takes the _result so far_ and the _current item,_ then it returns the _next result._" A React reducer does the same with the state so far and the next action. As the docs put it: "In this way, they accumulate actions over time into state." So the name does not mean that a reducer makes the code shorter. The docs say that reducers can "reduce" the amount of code inside your component, but that they are named after the array operation reduce.

if and switch give the same reducer

A reducer usually handles several action types, so it needs one branch for each. Here is a counter with two types, written first with if:

counterReducer with if
1function counterReducer(count, action) {
2 if (action.type === 'incremented') {
3 return count + 1;
4 }
5 if (action.type === 'reset') {
6 return 0;
7 }
8}

React's docs write the same branches with switch, a plain JavaScript statement:

counterReducer with switch
1function counterReducer(count, action) {
2 switch (action.type) {
Compares action.type with each case below
3 case 'incremented': {
4 return count + 1;
5 }
6 case 'reset': {
7 return 0;
8 }
9 }
10}

Yes, it is the exact same thing! switch takes one value, here action.type, compares it with each case from top to bottom, and runs the first one that matches. The docs: "The result is the same, but it can be easier to read switch statements at a glance." And: "If you're not yet comfortable with switch statements, using if/else is completely fine."

The docs give two small habits for each case. First, wrap it in curly braces, so that variables declared in different cases do not clash. Second, end it with return, because the docs warn: "If you forget to return, the code will 'fall through' to the next case, which can lead to mistakes!" To fall through means that JavaScript keeps running the lines of the next case too.

The reducer of our cart

Our reducer takes the current cart as its first argument and the action as its second. It is named after its state, as the docs name theirs tasksReducer. The update logic that left the handlers in Principle 1 comes back here, one case for each action type. We write it below Cart, in the same file:

src/components/Cart.jsx

48 switch (action.type) {
49 case 'increased': {
50 return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity + 1 } : item);
51 }
52 case 'decreased': {
53 return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity - 1 } : item).filter(item => item.quantity > 0);
54 }
55 case 'deleted': {
56 return cart.filter(item => item.id !== action.id);
57 }
58 case 'emptied': {
59 return [];
60 }
61 default: {
Runs when no case matches the type
62 throw Error('Unknown action: ' + action.type);

64 }

The last branch is new. default runs when no case matches. throw is plain JavaScript: it stops the function at once and reports an error in the Console. The docs end every reducer with this line, so a type that no case knows never passes silently.

action.id is the id that the handler wrote into the action in Principle 1. In Principle 3, React passes the current cart into cart, and the action that the handler gave to dispatch into action.

Why the reducer sits outside the component

We wrote cartReducer below Cart, not inside it. The reducer gets the cart as an argument, so it needs nothing from inside the component. The docs: "Because the reducer function takes state as an argument, you can declare it outside of your component. This decreases the indentation level and can make your code easier to read." A reducer inside Cart would return the exact same carts. Outside, it can later move to its own file, which Principle 5 does.

The filter in decreased takes the row out at zero

The decreased branch ends with a filter that keeps only the items whose quantity is above zero. Compare the branch with it and without it:

  2. initialCart still holds three items. The reducer built a new array and changed nothing it was given.

Principle 2

The Reducer: cartReducer Holds All the Update Logic for the Cart

A reducer is a function, declared outside the component, that takes the current state and an action and returns the next state, with one case for each action type and a default that throws for a type it does not know.

With all the update logic of the cart in one function, a wrong quantity has only one place to come from. The reducer is plain JavaScript: it gets everything it needs as arguments, so it lives outside the component, and calling it by hand changes nothing on the page. Each branch returns a whole new cart, with every old field copied.

✓ DO THIS

2 switch (action.type) {

4 return [];

8 }
9 }

Section 3 · Principle 3useReducer Hands Back the Cart and dispatch

One line in place of one line

The third step changes a single line. Compare the line we had with the line that replaces it:

The state line with useState, and with useReducer
1const [cart, setCart] = useState(initialCart);
The current cart and a setter
2const [cart, dispatch] = useReducer(cartReducer, initialCart);
The current cart and dispatch

Yes, the cart is the exact same thing! Both lines take the initial cart, and both give back the current cart on the left and a function made by React on the right. The docs: "The useReducer Hook is similar to useState: you must pass it an initial state and it returns a stateful value and a way to set state". The one difference is the reducer: useReducer also takes it, and the function it gives back takes an action instead of the next cart.

useReducer is a React Hook, imported from 'react' like useState. It takes two arguments:

  1. The reducer, here cartReducer.
  2. The initial state, here initialCart. React saves it on the first render and ignores it on the next renders.

It returns two values: the current state, here cart, and the dispatch function. This is the dispatch that the handlers of Principle 1 have been calling. The reference says: "The dispatch function returned by useReducer lets you update the state to a different value and trigger a re-render. You need to pass the action as the only argument to the dispatch function."

What happens after one click on Add one

Our code never calls cartReducer. React calls it, during the next render. Here is the click in the order things happen:

  1. The user clicks Add one in the Bread row. React runs the arrow function on the button, which calls handleIncrease with the Bread id, which is 1.

Interview PrepFor the Interview

The Interview Question: When does state logic outgrow useState, and how does a reducer consolidate it?

How to Answer Clearly in 30 Seconds

"State logic outgrows useState when many event handlers change the same state in different ways, so the update logic is scattered and a wrong value can come from any handler. A reducer gathers that logic into one function outside the component. Each handler calls dispatch with an action, a plain object whose type says what the user did. The reducer takes the current state and the action and returns the next state. useReducer takes the reducer and the initial state, replaces useState, and returns the state and dispatch. React calls the reducer during the next render, so it must be pure. The two Hooks are equivalent: only the place of the update logic changes, which makes it easier to log and to test."

Three Classic Follow-Up Questions Interviewers Ask

  1. "When would you pick useReducer over useState?"
    When many handlers change the same state, or when bugs from wrong state updates keep coming back. React's docs: "We recommend using a reducer if you often encounter bugs due to incorrect state updates in some component, and want to introduce more structure to its code." They compare the two on five points. On code size, useState needs less code at first, while useReducer "can help cut down on the code if many event handlers modify state in a similar way." On readability, useState "is very easy to read when the state updates are simple", and useReducer "lets you cleanly separate the _how_ of update logic from the _what happened_ of event handlers." On debugging, one log line in the reducer shows every update and its action, though "you have to step through more code than with useState." On testing, the reducer is a pure function, so you can check that it "returns a particular state for a particular initial state and action." And on taste: "Some people like reducers, others don't. That's okay." Both Hooks can live in the same component. The state behind a reducer still belongs to one component; to share it with components further down, you pass dispatch down as a prop, or through context, which Lessons 28 and 29 cover.
  1. "Does dispatch change the state right away?"
    No. "Calling the dispatch function does not change state in the running code." It puts the action in a queue, and React calls the reducer with the current state and that action during the next render, the same way it processes updater functions. A log of the state right after dispatch shows the old value, because the handler belongs to the render that is already on the screen. When you need the next value in the handler, call the reducer yourself, with the current cart and the same action. If the reducer returns the same object, as Object.is decides, React skips the re-render. Three more facts often come up. React gives back the very same dispatch function on every render, so you will often see it left out of Effect dependencies, which later lessons cover. Like every Hook, useReducer must be called at the top level of the component. And it takes an optional third argument, an initializer function such as createInitialState, which React calls once to build the initial state; you pass the function itself, not the result of calling it.
  1. "Why must a reducer be pure, and why is it called a reducer?"
    It must be pure because React calls it during rendering, not during the click. The docs: reducers "should not send requests, schedule timeouts, or perform any side effects", and they "should update objects and arrays without mutations." In Strict Mode, React calls the reducer twice in development and keeps one result, so an alert inside it appears twice, and a mutation changes the same object twice. That double call happens only in development. Purity is also what lets you test the reducer on its own, with no component and no browser. The name comes from the array method reduce: its function takes the result so far and the next item and returns the next result, and a React reducer takes the state so far and the next action and returns the next state. When a reducer works on deeply nested objects, the Immer library offers useImmerReducer, which lets the reducer write changes on a draft while Immer builds the new copies.
