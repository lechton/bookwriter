Pure Components and Where Side Effects Belong

Interview Question · ❱ CORE

What does it mean for a component to be pure, and what breaks across renders when it is not?

Why React Components Must Be Pure

A pure function vs. an impure function in four lines

Before we open a project, compare two tiny JavaScript functions that both take a number and return a number.

First, look at a function that multiplies its input by two:

A pure function: same input always gives the same output
1function double(number) {
1. Uses only its input and changes nothing outside
2 return 2 * number;
3}
4
5console.log(double(3));
First call with 3 -> returns 6
6console.log(double(3));
Second call with 3 -> still returns 6!

Now compare that with a function that adds its input to a variable sitting outside the function:

An impure function: changes an outside variable on every call
1let total = 0;
2
3function addToTotal(number) {
2. Reaches outside and changes total on every call!
4 total = total + number;
Changes a variable that existed before the call
5 return total;
6}
7
8console.log(addToTotal(3));
First call with 3 -> returns 3
9console.log(addToTotal(3));
Second call with 3 -> returns 6!

At first glance, double and addToTotal both take a number and return a number. They look like the same kind of function, but they are NOT the same thing!

When you call double with three, you get six every single time. When you call addToTotal with three, the first call gives three and the second call gives six. The second answer changed because addToTotal modified total, a variable that existed before the function ran.

In React, every component you write is supposed to work like double:

A pure React component: same props always return the same JSX
1function Greeting({ name }) {
Uses only its name prop and changes nothing outside
2 return <h1>Hello, {name}</h1>;
3}

Pass the same name prop into Greeting, and it returns the exact same heading every time React calls it.

Look at the three everyday words that unlock this whole chapter:

  • What does "pure" mean? In everyday English, pure means nothing extra is mixed in from outside, like pure water. Think of the math formula y = 2x: when x is three, y is always six, no matter the time of day. Or think of a kitchen recipe. Follow the same recipe with the same ingredients, and you get the same dish every time. If a cook secretly tosses in leftover ingredients from the counter, every batch comes out different. In JavaScript and React, a pure function follows two simple rules:

1. It minds its own business: it does not change any variable or object that existed before it was called.

2. Same inputs, same output: given the same inputs, it always returns the exact same result.

  • What is a "side effect"? In everyday life, as with medicine, a side effect is an extra result on the side of the main job. A component's main job during rendering is to calculate and return JSX from its props and state. Changing anything outside the component, such as modifying an outside variable, pushing into an outside array, or changing the DOM directly, is a side effect.
  • What does "mutation" mean? In everyday English, a mutation is a change to the thing itself. In JavaScript, mutation means changing an existing variable, array, or object in place instead of leaving it alone or working on a fresh copy:

The three places where code can live in a component file

If a component must not cause side effects while rendering, where do we put code that actually needs to change things? Inside a React component file, a line of code can sit in one of three places:

Where code can sit inside a component
1function MyPage() {
2 const label = 'Dark mode';
Place 1: In the component body -> runs during render, must stay PURE
3
4 function handleToggle() {
5 console.log('User clicked');
Place 2: Inside an event handler -> runs on user click, side effects belong here!
6 }
7
8 return <button onClick={handleToggle}>{label}</button>;
9}

Each place runs at a different moment and has its own rule:

  1. Place 1 is the component body: Lines written directly at the top level of the component run during render, every time React calls the component. Only pure calculations that turn props and state into JSX belong here, along with changes to brand-new variables created inside that same render.
  2. Place 2 is an event handler, such as handleToggle: Lines inside an event handler run only when the user clicks, and never during render. Side effects such as updating an outside counter, logging a user action, or calling a state setter belong here.
  3. Place 3 is an Effect, written with useEffect: Lines inside an Effect run after React commits the screen update. Keep Effects as a last resort when a side effect is not caused by a user event.

Why purity matters on a real shopping list page

To see how an impure component breaks a real page, we will build a small shopping list page. The page shows a heading, three numbered grocery items, and a theme button that switches the page between light mode and dark mode.

Why is a Dark mode button on a shopping list the clearest test of component purity? Because clicking the button only flips the theme state in App. It changes nothing about the grocery items. Yet when App re-renders for the new theme, React calls every child component inside App again.

When a component is impure, it often looks fine on the very first load. Both a pure shopping list and an impure shopping list display the grocery items numbered 1, 2, and 3 when the page first opens. It may look the same, and it may seem to work the same at first, but it is NOT the same thing. On the very first click of the theme button, the pure list keeps its numbers at 1, 2, and 3. Meanwhile, the impure list suddenly jumps to 4. Milk, 5. Bread, and 6. Eggs!

What we need from plain JavaScript and earlier lessons

Before Principle 1, let us recall two building blocks from earlier lessons and meet three small array helpers:

  • Props and state are read-only inputs: A parent passes data to a child through attributes on a JSX tag, and the child reads those props without changing them. Inside a component, useState keeps state between renders, and calling the state setter triggers a re-render of that component and every child it returns.
  • A variable outside every function keeps its value between calls: When you declare a let variable at the very top of a file, outside all functions, JavaScript creates that variable once when the file loads. Every function call in that file reads and changes that same shared variable.
  • Three small array helpers: In plain JavaScript, an array holds a list of items in order. Look at the three array methods we will use in Principle 3:

Four Principles of Pure Components

PRINCIPLES

React may call your component functions at any time and any number of times. Because of that, every component must act like a pure formula during render, which gives us four practical rules for daily debugging and interviews:

  1. Principle 1: Pure Components Return the Same JSX for the Same Inputs: A component must use only its inputs and never change a variable that existed before it ran. If a component increments an outside variable during render, its numbers climb on every re-render even when its own props never change.
  2. Principle 2: StrictMode Calls Every Component Twice in Development: Wrapping your app in StrictMode makes React call each component function twice in development. A pure component shows the exact same page, while an impure component exposes its bug on the very first load instead of hiding until a later re-render.
  3. Principle 3: Never Mutate an Outside Array During Render; Use Local Mutation Instead: Pushing into an array that arrived from outside, such as a prop, mutates the parent's array and repeats items on every render. Creating a brand-new array or copy inside the same render and pushing into that local array is completely safe.
  4. Principle 4: Put Side Effects in Event Handlers, Never in the Component Body: Code written directly in the component body runs on every render, whereas code inside an event handler runs only when the user acts. Side effects such as counting clicks or logging user actions belong in event handlers, with useEffect kept as a last resort.

Two more interview rules follow directly from Principle 1:

  • Never pass data between components through a shared outside variable: React does not promise the order in which components render. One component must never write to an outside variable like currentPerson expecting another component like Header to read it. Components always share data through props, state, or context, and all three inputs are strictly read-only during render.
  • Same inputs must give the same output, which interviewers call "idempotent": Calling Math.random or new Date directly inside the component body during render also makes a component impure. Two renders with the exact same props will produce two different numbers or timestamps. In technical interviews, a function that always returns the exact same output for the same inputs is called idempotent.
Principle 1

Pure Components: Same Inputs Return the Same JSX and Leave Outside Variables Alone

Keep every component pure during render: read only its props and state, return the same JSX, and never change an outside variable.

This is an easy trap when a page first loads. If your component adds to a variable sitting outside the function, the first render looks completely fine on the screen. The trouble starts as soon as any parent updates its state and React calls your component again. That outside variable kept its old value from the first render. So the numbers on the screen climb higher on every click even though the items themselves never changed! Pass each item's number in as a prop so the component always returns the exact same result for the same inputs.

  • Why is it called StrictMode? Think of a strict math teacher who checks your work by asking you to calculate the same formula a second time. Why removing <StrictMode> only hides the bug

When beginners see 2. Milk, 4. Bread, and 6. Eggs on their screen, they often search online and learn that <StrictMode> calls components twice. So they delete <StrictMode> from the startup file. Or they build the app for production with npm run build and see 1, 2, and 3 on the first load. Then they assume the problem was only a development quirk.

Deleting <StrictMode> is a classic mistake! Removing <StrictMode> does not fix the item component. It only turns off the alarm bell so the bug hides on the first load and breaks as soon as a real user clicks Dark mode.

Two more questions interviewers ask about side effects and purity

  1. What if a developer changes the DOM directly during render, such as setting document.title or changing document.body.className inside the component body?
    Directly changing the DOM inside the component body is also a side effect during render! Whenever a change can be expressed as JSX, return it in your JSX instead. That is why our main component sets className on the <main> tag in JSX so React updates the class during the commit step. When a side effect cannot be expressed in JSX and is not caused by a user event, React provides useEffect. Keep useEffect as a last resort that runs after the render commits to the screen.
  2. Why does React care so much that rendering stays pure?
    Because when calling a component has zero side effects, React can safely do three powerful optimizations across your application:
    - Render on the server: React can run the exact same component on a server for thousands of visitors without one visitor's render changing variables seen by another visitor.
    - Skip unnecessary renders: When a component's inputs have not changed, React can skip calling it again with memo. A pure component is guaranteed to return the exact same JSX for the same inputs.
    - Stop and restart a render at any time: New user input may arrive while React is rendering a deep component tree. Because rendering is pure, React can safely throw away the half-finished calculation and start fresh with zero side effects left on the page.

For the Interview

The Interview Question: What does it mean for a component to be pure, and what breaks across renders when it is not?

How to Answer Clearly in 30 Seconds

"In React, a component is pure when it follows the two rules of a pure function:

  1. It minds its own business: it does not mutate any variable, array, or object that existed before React called it.
  2. Same inputs, same output: given the same props and state inputs, it always returns the exact same JSX.

When a component breaks purity during render, such as incrementing an outside let variable or calling .push on a prop array, the first load may look fine. However, its output changes on every re-render even when its props never changed. Item numbers climb on every state update, and pushed array items repeat over and over.

To catch these bugs early, <StrictMode> calls every component function twice in development. A pure component is unaffected, while an impure component shows its bug on the first load. Changing a brand-new array or object created inside the same render is called local mutation, and it is completely fine because nothing outside the render sees it. Finally, side effects belong in event handlers like onClick, which run only when the user acts and never during render, or in useEffect as a last resort. React insists on pure rendering so it can safely render components on the server, skip unchanged renders with memo, and stop or restart renders at any time."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why does my component run twice in development, and should I remove <StrictMode> to stop it?"
    No, never remove <StrictMode> to fix a bug. In development, <StrictMode> intentionally calls every component function twice on each render to test whether it is pure. If calling your component a second time changes what appears on the screen, your component is mutating something that existed before the render. Removing <StrictMode> or building for production with npm run build makes the component run once on load. That only hides the bug until the next state update triggers a re-render.
  2. "If React forbids mutating arrays during render, why is it okay to call .push on an array created inside the component?"
    Purity only requires that a component not change anything that existed before the render started. A prop array or a module-level array existed before the render and is shared across renders, so calling .push on it changes the input for future renders. An array created inside the component during the current render, such as items.slice or [], is brand-new on every call. React calls changing that new array local mutation, and it is safe because no code outside that render can observe it.
  3. "How can you tell whether code inside a component runs during render, and why don't event handlers need to be pure?"
    Any code written at the top level of the component function body runs during render, every time React calls the component. Code written inside an event handler like handleToggle is only defined during render; React runs it only when the user triggers the event. Because event handlers do not run during render, they do not need to be pure and <StrictMode> does not call them twice. That makes event handlers the primary place for side effects.
