Passing Data Deeply with Context and use

Interview Question · ❱ CORE

How do you pass data many levels deep without prop drilling, and how does the use() API read it?

How a Value Chosen at the Top Reaches a Component Far Below

Passing a prop through every component vs. letting the far component ask for it

A value chosen at the top of the tree often has to reach a component far below. Suppose App decides that the theme is dark, and a Share button two components further down must show it. How does the value get there?

The way we already know is props. App gives theme to Page, and Page gives it to ShareButton:

Both trees put the same Share button on the page, with the class dark. For the user, yes, it is the exact same thing! The page cannot tell how the value arrived.

What the two share is the start and the end: App decides the value, and ShareButton uses it. The one difference is the middle. With props, every component on the way receives the value and passes it on. With context, Page does not mention theme at all.

Lesson 24 gave the first way its name: prop drilling. Think of a note passed hand to hand along a row of people. Everyone in the middle must hold the note and pass it on, though only the last person reads it. Page is in the middle: it receives theme only to hand it to ShareButton. Our tree has one such component. A real page often has three or four.

The second way takes its name from everyday speech. The context of something is its surroundings: one word can mean two different things in two sentences, and the words around it decide which. In React, a component reads a value from its surroundings, from the components above it in the tree. React's docs say it like this: "Context lets the parent component make some information available to any component in the tree below it, no matter how deep, without passing it explicitly through props."

Three names in the second tree carry the idea. createContext creates the context, outside any component. The tag around Page in App is a provider: to provide is to supply, and this tag supplies the value dark to every component inside it, at any depth. useContext in ShareButton asks for the value, and React finds it by searching the tree above ShareButton. The 'light' given to createContext is the default value: a component gets it only when React finds no provider above it.

What is at stake

The key idea to remember is this: context does not pass the value through the components in the middle. The component that reads it asks for it, and React finds the closest provider above that component.

What is at stake is whether the user sees the change. On our page, the user clicks Toggle theme, and the Share button must turn dark. With props, a middle component that forgets to pass theme on leaves the button with no class at all, so it never turns dark. With context, a tree that has no provider above the button leaves it light, because the button reads the default value.

Readers usually go wrong in four places:

  1. They think context is one global variable for the whole app. It is not. Each component that reads it gets the value of the closest provider above it. A provider lower in the tree can give one part of the page another value.
  2. They think the value given to createContext is the value to change later. React's docs answer: "This value never changes. React only uses this value as a fallback if it can't find a matching provider above."
  3. They read the context in the same component that provides it, and get the default value.
  4. They reach for context whenever a prop goes two levels down. React's docs warn: "Just because you need to pass some props several levels deep doesn't mean you should put that information into context."

Six Principles of Context

PRINCIPLES

React's docs give context three steps: create it, use it from the component that needs the data, and provide it from the component that specifies the data. Each step has its own place where the page goes wrong. Two more questions follow: which provider a component finds, and when context is the wrong tool. Six principles come from that:

  1. Principle 1: createContext Makes ThemeContext: createContext with the default 'light', called outside any component, returns a context object. The object holds no value of its own. 'light' is only the default, used when no provider is above.
  2. Principle 2: useContext Leaves the Share Button Light: useContext with ThemeContext returns the value of the closest provider above the component. With no provider above, it returns the default, so the button stays light after every click by the user.
  3. Principle 3: The ThemeContext Provider Turns the Share Button Dark: Wrapping components in the ThemeContext provider with value={theme} gives theme to every component inside that reads it, no matter how deep. When theme changes, React re-renders the components that read it.
  4. Principle 4: use Reads the Same Theme: use with ThemeContext returns the same value as useContext. The one difference is that use may also be called inside if and loops.
  5. Principle 5: The Closest ThemeContext Above Wins: React searches upward from the component that reads, starting above it. A provider returned by the same component does not count, and a provider lower in the tree overrides the value for its part of the page.
  6. Principle 6: Passing JSX as children Skips the Middle Layers: Before reaching for context, pass props or pass JSX as children. Context fits information that many distant components need, such as a theme.

Section 1 · Principle 1createContext Makes ThemeContext

Two lines create a context, and nothing appears on the page

The first of React's three steps is to create the context. It takes two lines in a new file:

src/ThemeContext.js
1import { createContext } from 'react';
A function that React provides
2export const ThemeContext = createContext('light');
'light' is the default value

Nothing changes on the page. No component reads ThemeContext yet, and the other files still pass theme as a prop.

createContext is a function from React. Its only argument is the default value, here 'light'. It returns a context object, which we name ThemeContext. React's docs say where to call it: "Call createContext outside of any components to create a context."

ThemeContext does not hold the theme. React's docs are direct about it: "The context object itself does not hold any information. It represents _which_ context other components read or provide." ThemeContext is the name that a provider and a reading component share, so React can match them. The value itself lives in the provider, which Principle 3 adds.

It looks like a variable that holds 'light' and can later be set to 'dark', but it is NOT the same thing! A component that reads ThemeContext gets 'light' only when no provider sits above it in the tree. React's docs say: "The default value is meant as a 'last resort' fallback. It is static and never changes over time." A fallback is what you fall back on when nothing better is there: here, the value a component gets when React finds no provider above it.

The default value: 'light' vs. null

The default matters only for a component that reads ThemeContext with no provider above it. Two common defaults give that component two different values:

Two defaults for the same context
1export const ThemeContext = createContext('light');
A component with no provider above it gets 'light'
2export const ThemeContext = createContext(null);
A component with no provider above it gets null

These two lines are NOT the same thing for that component. With 'light', the button still gets a real class and still looks right. React's docs recommend a default that makes sense, because "if you accidentally render some component without a corresponding provider, it won't break. This also helps your components work well in a test environment without setting up a lot of providers in the tests." When there is no default that makes sense, React's docs use null, for example as the default of a context for the current user.

A theme has an obvious default, so our page uses 'light'.

The context lives in its own file

Our context sits in ThemeContext.js, not inside a component file. React's docs say: "it's common to declare contexts in a separate file", and "This works similar to importing and exporting components." Keeping it in a component file would work the exact same way. A file of its own simply lets every file import the same object.

Because ThemeContext is a named export, every file that needs it imports it with curly braces:

src/components/ShareButton.jsx
1import { ThemeContext } from '../ThemeContext.js';
A named export, so curly braces

One file can create several contexts. React's docs show a Contexts.js file that exports ThemeContext and AuthContext side by side. Each one is a separate context.

There is no way to change the default value

React's docs list this as a common question: "I can't find a way to change the context value". A developer writes createContext with 'light', reads ThemeContext in a component, and then wants the page to turn dark after a click by the user. So the developer looks for a way to change the 'light' given to createContext.

There is none. React's docs say: "This value never changes. React only uses this value as a fallback if it can't find a matching provider above." Their fix is to "add state and wrap components in a context provider." That is Principle 3.

Two ways for ShareButton to get theme

The second step is to use the context from the component that needs the data. Here are two ways for ShareButton to get theme:

It may look the same, or work the same at first, but it is NOT the same thing! Both create a variable named theme, and both show a light button when the page opens. The first gets theme from the tag its parent writes. The second asks React for the value of the closest ThemeContext provider above ShareButton.

useContext is a React Hook. React's docs say: "useContext is a React Hook that lets you read and subscribe to context from your component." To read the context is to get its value now. To subscribe is to ask React to run the component again whenever that value changes later. We pass it the context object, and it returns the context value. React's docs say which value comes back: the value "passed to the closest SomeContext above the calling component in the tree." With no provider above, useContext returns the default value.

React's docs describe what was missing before: "some way for a child to 'ask' for data from somewhere above in the tree." useContext is that question. As with useState, the call sits at the top level of the component. React's docs say: "you can only call a Hook immediately inside a React component", not inside loops or conditions. Lesson 38 covers that rule.

Why? Well, no ThemeContext provider exists anywhere in the tree, so useContext returns the default 'light' on every render. App's state changes, but nothing connects it to ThemeContext. Here is what happens, in order:

  1. When the page opens, React renders ShareButton, and useContext looks for a ThemeContext provider above it. There is none, so it returns the default, 'light'.
  2. The button gets the class light. App's state is also 'light', so the page looks right by chance.
  3. The user clicks Toggle theme. App sets theme to 'dark', and React renders App again, with Page and everything below it.
  4. ShareButton runs again. It still finds no provider above it, so it gets 'light' again.

React prints nothing in the Console. Reading a context with no provider above is not an error, because the default value exists exactly for that case.

React's docs show the same moment in their own example, a page of headings: "Notice this example doesn't quite work, yet! All the headings have the same size because *even though you're using the context, you have not provided it yet.* React doesn't know where to get it!"

Reading a context and providing it are two separate steps. App holds theme and ShareButton reads ThemeContext, but a state variable reaches no reading component until some component provides it. React's docs name this case in their troubleshooting list: "You may have forgotten to wrap your component with <SomeContext>, or you might have put it in a different part of the tree than you thought." That tag is a context provider. React's docs say: "Wrap your components into a context provider to specify the value of this context for all components inside." In plain words, the tag tells React: if any component inside asks for ThemeContext, give it this value.

What happens after one click on Toggle theme

The Share button turns dark, although no component in the middle mentions theme. Why? Well, when the value of a provider changes, React re-renders the components inside it that read that context. Here is the click, in order:

  1. The user clicks Toggle theme, and the handler sets theme to 'dark'.
  2. React renders App again. The provider now has the value 'dark'.
  3. React compares the old value with the new one, using Object.is from Lesson 17. 'light' and 'dark' are different.
  4. React re-renders the components inside the provider that read ThemeContext. ShareButton calls useContext again, and this time it gets 'dark'.
  5. The button gets the class dark.

Page, ArticleCard, and ActionBar also run again, because their parent App rendered again, as Lesson 13 showed. But they pass nothing on. ShareButton gets 'dark' from the provider, not from them.

This is what "subscribe" means in React's description of useContext. React's docs say: "The returned value is always up-to-date. React automatically re-renders components that read some context if it changes." And: "Context is not limited to static values. If you pass a different value on the next render, React will update all the components reading it below! This is why context is often used in combination with state."

That is why context is NOT one global variable for the whole app. The value a component gets depends on where it sits in the tree. React's docs say context lets you write components that "adapt to their surroundings". That is the everyday meaning of the word context from the start of this lesson: the surroundings. The same ShareButton is light in one place and dark in another, because of where it is rendered.

React's docs compare it with CSS. When a div sets color: blue, every element inside it, no matter how deep, inherits blue, unless an element in the middle overrides it with color: green. React's docs say: "Similarly, in React, the only way to override some context coming from above is to wrap children into a context provider with a different value."

The comparison goes one step further. In CSS, color and background-color do not override each other. React's docs say: "Similarly, different React contexts don't override each other." A provider of ThemeContext never changes what a component reading AuthContext gets. Each context made with createContext is completely separate from the others.

Two ways to take a prop out of a layout component

Context is not the only way to stop prop drilling. React's docs warn: "Context is very tempting to use! However, this also means it's too easy to overuse it." Their own example is a Layout component that receives posts only to pass them on to Posts. Here are two ways to write it:

Passing posts through Layout, and passing Posts as children
1<Layout posts={posts} />
Layout receives posts only to pass them on to Posts
2<Layout><Posts posts={posts} /></Layout>
Layout receives the finished Posts tag as children

Both lines put the same posts on the page. The one difference is who writes the Posts tag. With posts={posts} on Layout, the Posts tag sits inside Layout's own code, so Layout needs posts. With Posts as children, the top component writes the Posts tag between the Layout tags, and Layout only places its children, as Lesson 09 showed. Layout never touches posts.

React's docs say that when data passes through components that only pass it on, "this often means that you forgot to extract some components along the way." Here, to extract Posts is to take its tag out of Layout's code and write it in the top component instead.

Passing children takes the data prop out of the middle, as context does. It may look the same, but it is NOT the same thing as context! With children, the top component still passes posts by hand, as a prop on the Posts tag, so anyone reading the code sees which component gets the data. For the Interview

The Interview Question: How do you pass data many levels deep without prop drilling, and how does the use() API read it?

How to Answer Clearly in 30 Seconds

"Prop drilling is passing a prop through components that never use it, only pass it on. Context removes it in three steps:

  1. Create: createContext with a default value, called outside any component, returns a context object. The object holds no value. The default is used only when there is no provider above at all.
  2. Provide: wrap the tree in <MyContext value={...}>. In React 19, the context object itself is the provider, and MyContext.Provider is the legacy way. With state as the value, a change re-renders every component that reads the context.
  3. Read: useContext or use, given the context object, returns the value of the closest provider above the component. use reads the same value, but unlike useContext it may sit inside if and loops, and it can also read Promises.

A provider in the same component does not count, and a nested provider overrides the value for its part of the tree. Before reaching for context, I try props, or passing JSX as children."

Three Classic Follow-Up Questions Interviewers Ask

  1. "A component reads a context and gets the default value, or undefined. Why?"
    The default value comes back when there is no provider above the reading component at all. The provider may be missing or sit in another part of the tree. Or it sits in the same component that reads the context, and React starts its search above that component. undefined comes back when a provider exists but has no value prop, for example when the prop is misspelled as theme. React's docs say: "If you forget to specify value, it's like passing value={undefined}." In that case React prints the warning that the value prop is required. The default never changes while the app runs: to change the value, put state in a provider.
  2. "What is the difference between use and useContext for reading context?"
    They return the same value from the same closest provider, and both re-render the component when that value changes. useContext is a Hook, so it must sit at the top level of the component. use is a React API, and "Despite its name, use is not a Hook", so it may be called inside if and loops. It must still be called inside a component or a Hook, and it does not see a provider in the same component. Reading context with use is not supported in Server Components. use can also read a Promise, which useContext cannot.
  3. "When a context value changes, which components re-render, and does memo stop it?"
    React re-renders every component that reads that context, starting from the provider that receives a different value. It compares the old and new values with Object.is. React's docs say: "Skipping re-renders with memo does not prevent the children receiving fresh context values." So a component that reads the context still updates, even deep inside a component wrapped in memo, Lesson 55. One trap follows from Object.is. An object written right inside value, such as an object holding a state and its setter, is a new object on every render of the provider. So every component that reads the context re-renders. Lesson 59 shows how useMemo and useCallback fix that.
