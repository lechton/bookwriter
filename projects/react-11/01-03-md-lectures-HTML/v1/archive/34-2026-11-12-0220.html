When You Do Not Need an Effect

Interview Question · ❱ CORE

When do you not need an Effect, and what replaces it?

OverviewWhere the Code for Each Change Belongs

One question decides it: why does this code need to run?

When you open the cart of an online shop, you see one row for each item, a total under the rows, and a button to place the order. Our cart holds two items, Socks at $5 and Hat at $20:

Figure 1 — A cart with two items, a total line, and a Place order button.

The user does two things on this screen, and each one changes the page:

  1. The user clicks Remove on Hat. The row goes away, and the total line shows Total: $5.
  2. The user clicks Place order. The button is replaced by the line Thank you! Your order is placed., and the order goes to the server once.

Right after learning useEffect (as seen in Lesson 32), many developers write both changes as Effects:

  1. One Effect watches the items and sets the total.
  2. Another Effect sends the order when the thank-you line appears.

Both Effects run, and the page seems to work. But neither change needs an Effect, and each of the two Effects costs the user something.

React's docs give one test for where code belongs: "ask yourself why this code needs to run." It is the same question that separated the Buy click from the timer (as seen in Lesson 32), now asked of every change on the page. There are three answers, and each answer has its own place in the component:

  1. To show something calculated from state or props, such as the total: calculate it during rendering, in the body of the component.
  2. Because the user did something, such as clicking Place order: put it in the event handler of that click.
  3. Because the component is on the screen and must stay in sync with something outside React, such as a server that counts visits: that is the job of an Effect.

The first two answers need no Effect at all. React's docs say it in one line: when there is no external system involved, "you shouldn't need an Effect."

What is at stake

What is at stake is what the user gets from each of the two Effects:

  1. With the total set by an Effect, every change of the items renders the cart twice: once with the old total, and once more with the new one. On the first load, the first render shows Total: $0, because the Effect has not run yet.
  2. With the order sent by an Effect, one click in development sends the order twice, and the Console shows it twice. In production, the order can go out again with no click on Place order, for example when the user clicks Remove on a row after placing the order. React's docs say it plainly: "You wouldn't want to buy the product twice."

It may look the same, or work the same at first, but it is NOT the same thing! Once the page settles, the total set by an Effect and the total calculated during rendering both show Total: $25. In production, the first click sends one order with either version. The difference hides in two places: in the extra render with the old total, and in what happens when the Effect that sends the order runs a second time.

Readers usually go wrong in two places:

  1. They read "the total depends on the items" as "watch the items with an Effect".
  2. They read "after the click, show the thank-you line and send the order" as "send the order when the thank-you line appears".

Three Principles of Code That Needs No Effect

PRINCIPLES

An Effect is for code that runs because the component is on the screen and must stay in sync with something outside React. A value calculated from state needs no Effect, and neither does code caused by a click. Three principles follow from that:

  1. Principle 1: The Total Line Is Calculated During Rendering: The total can be calculated from items, so the component calculates it in its body. An Effect that copies it into state costs one render with the old total, and then a second render.
  2. Principle 2: The Place order Click Sends the Order: The order goes out because the user clicked, so sendOrder goes in the click's event handler. An Effect in the thank-you line sends it again on every mount of that line and on every change of items: twice in development, and again after a Remove in production.
  3. Principle 3: The Cart Visit Is Logged by an Effect: A visit is logged because the cart is on the screen, and there is no click to put it in. That code stays in an Effect, even though it runs twice in development.

Here is the complete map of those three principles before we walk through each one:

Section 1 · Principle 1The Total Line Is Calculated During Rendering

A full name copied by an Effect vs. calculated in the body

React's docs show this mistake in its smallest form: a first name, a last name, and a full name made from both. Here is the full name both ways:

fullName in state, set by an Effect
1const [firstName, setFirstName] = useState('Taylor');
2const [lastName, setLastName] = useState('Swift');
3const [fullName, setFullName] = useState('');
4
5useEffect(() => {
6 setFullName(firstName + ' ' + lastName);
Runs after React has already rendered the empty fullName
7}, [firstName, lastName]);
fullName calculated during rendering
1const [firstName, setFirstName] = useState('Taylor');
2const [lastName, setLastName] = useState('Swift');
3const fullName = firstName + ' ' + lastName;
Taylor Swift, calculated on every render

It may look the same, or work the same at first, but it is NOT the same thing! Both show Taylor Swift once the page settles. The difference is how many times React renders to get there:

  • With fullName in state, set by an Effect, the docs say React "does an entire render pass with a stale value for fullName, then immediately re-renders with the updated value." A render pass is one round of React calling the component functions and then committing the result to the DOM. A stale value is an old value that no longer matches the state it is made from: on the first render, fullName is still the empty string.
  • With fullName calculated during rendering, the line runs every time React calls the component, so fullName always matches the names of this render. The docs: "That code will automatically re-run whenever your props or state change."

The Effect costs a whole render because Effects run last. React's docs give the order: "When you update the state, React will first call your component functions to calculate what should be on the screen. Then React will "commit" these changes to the DOM, updating the screen. Then React will run your Effects. If your Effect also immediately updates the state, this restarts the whole process from scratch!"

The fix is a rule you already know: a value you can calculate from state is a const in the body, not state. An Effect that copies the value into state does not get around that rule. Yes, it is the exact same redundant state you met before (as seen in Lesson 22), with one more render on top.

Whether the user sees Total: $0 depends on when the browser paints the screen. React's useEffect reference says that when an Effect was not caused by a click, React "will generally let the browser paint the updated screen first before running your Effect." React gives the browser that chance, but the browser paints only when its next frame is due. On a fast page load, both commits often come before the first paint, and the screen goes straight to Total: $25. When the paint falls between the two commits, the user sees Total: $0 for a moment.

After a click on Remove, one render shows a single row with the old total. Here is the order of events when the user removes Hat:

  1. The click calls setItems with only Socks.
  2. React calls App. The list shows only Socks, and total is still 25, so the JSX returns Total: $25 under one row of $5.
  3. React commits that render, then runs the Effect, which calls setTotal with 5.
  4. React calls App again and commits Total: $5.

Here the user may never see step 2. The same reference says that when an Effect is caused by a click, React "may run your Effect before the browser paints the updated screen." The cost is still there: one extra render after every change of items, plus one more state variable, one more setter, and one more Effect in the code.

Calculating the total in the body

The fix is to delete the total state and its Effect, and to calculate total in the body of App. .reduce walks the array and adds each item.price to sum, starting from 0 (as seen in Lesson 27). The names sum and item belong to the arrow function: sum is the running total so far, and item is the current element of items, such as the item for Socks.

React's docs give three reasons for this rule. Calculating during rendering is:

  1. "faster", because there is no extra update from an Effect. The docs call these extra updates "cascading": a state update from an Effect that starts another render.
  2. "simpler", because you remove a state variable, a setter, and an Effect.
  3. "less error-prone", because two state variables can no longer get out of sync with each other.

The linter reports a setter called in an Effect

The React team ships a lint plugin, eslint-plugin-react-hooks, and one of its rules finds these Effects for you. The rule set-state-in-effect reports a setter called directly inside an Effect, such as setTotal in the Effect that copied the total. Its docs page describes it as a rule that "Validates against calling setState synchronously in an effect, which can lead to re-renders that degrade performance."

Principle 1

Calculate During Rendering: A Value Made from State Is a const in the Body

When a value can be calculated from the props or state the component already has, calculate it in the component body during rendering; do not keep it in state and set it from an Effect.

The component body runs again every time items changes, so a total calculated there always matches the rows on the screen. An Effect runs only after React has rendered and committed the page. When it sets the total, React renders the whole cart again, so every change costs one render with the stale total and a second render with the right one.

The same line in two places: the click's handler vs. an Effect

The line that sends the order can sit in two places. It can sit in the function that runs when the user clicks Place order, or in an Effect of the thank-you line:

It may look the same, or work the same at first, but it is NOT the same thing! In production, the first click prints one Sending order: 2 items with either version. But the event handler runs once for each click by the user, and the Effect runs every time OrderPlaced mounts and every time its items change. A click happens once. The Effect can run many times.

This Effect is easy to write by mistake, because it looks tied to the click: the thank-you line only appears after the click. But the Effect knows nothing about the click. It only knows that the thank-you line is on the screen. React's docs: "By the time an Effect runs, you don't know what the user did." The order goes out because the user clicked, so the docs' test puts it in the click's handler. The docs say the same of a shop's Buy button: "You don't want to buy the product when the user visits a page; you want to buy it when the user clicks the Buy button."

Principle 2

Event Handler: Code Caused by a Click Runs in That Click's Handler

When code runs because the user did one thing, such as clicking Place order, put it in that event's handler; do not put it in an Effect that runs when a component appears or when a state flag changes.

A click happens once, and its handler runs once. An Effect runs every time its component mounts or its dependencies change, and by then it does not know what the user did. So an order sent from an Effect goes out twice in development, and again in production when a dependency changes, such as after the user removes an item.

Section 3 · Principle 3The Cart Visit Is Logged by an Effect

An Effect that stays: logging a visit to the cart

Shops count how many users open the cart. Each time the cart is shown, the page sends an analytics event: a message to a server that counts what users see and do. Here the event is one visit of the cart, and logVisit stands in for it.

No click causes this visit. The cart is on the screen, and that is the whole reason. React's docs say the same about a form: "the _reason_ to send the analytics event is that the form was displayed." So this code goes in an Effect, with an empty array so that it runs after the first mount (as seen in Lesson 32):

13 const total = items.reduce((sum, item) => sum + item.price, 0);

Empty array: runs after the first mount only

React's docs keep this code as it is: "We recommend keeping this code as is. Like with earlier examples, there is no user-visible behavior difference between running it once and running it twice." The docs put the whole lesson in two sentences: "If this logic is caused by a particular interaction, keep it in the event handler. If it's caused by the user _seeing_ the component on the screen, keep it in the Effect."

Principle 3

Effect: Code Caused by the Component Being on the Screen Stays in an Effect

When code runs because the component was shown, and it talks to something outside React, such as a server that counts visits, keep it in an Effect; running twice in development is not a reason to move it.

The visit happens because the cart is on the screen, so there is no click whose handler could hold it. In development, Strict Mode runs the setup a second time, and the Console shows two visits. That extra visit changes nothing the user sees, and in production there is one.

Interview PrepFor the Interview

The Interview Question: When do you not need an Effect, and what replaces it?

How to Answer Clearly in 30 Seconds

"Effects are an escape hatch for staying in sync with a system outside React. When there is no external system, I usually do not need one. I ask why the code needs to run:

  1. To show a value calculated from props or state, such as a cart total: I calculate it in the component body during rendering. An Effect that copies it into state costs a render pass with a stale value, and then a second render.
  2. Because the user did something, such as clicking Place order: I put it in that event's handler. By the time an Effect runs, it does not know what the user did, so an order sent from an Effect goes out twice in development, and again whenever the component mounts again.
  3. Because the component is on the screen, such as an analytics visit: that stays in an Effect, and running twice in development is fine.

The lint rule set-state-in-effect helps me find a setter called directly in an Effect."

Three Classic Follow-Up Questions Interviewers Ask

  1. "What if the calculation is slow? Shouldn't it go in an Effect then?"
    No. A slow calculation is cached with useMemo, not moved into an Effect. The docs: "To cache expensive calculations, add useMemo instead of useEffect." Most calculations are not slow: "unless you're creating or looping over thousands of objects, it's probably not expensive." Lesson 56 teaches useMemo. The React Compiler, which Lesson 63 teaches, "can automatically memoize expensive calculations for you".
  2. "How do you reset a child's state when a prop changes, without an Effect?"
    Give the child a different key (as seen in Lesson 25). The docs' example is a profile page that renders <Profile userId={userId} key={userId} />, so React starts the profile's state over for each user. An Effect that calls the setters when userId changes renders the old state first, and then renders again, just like the total. To change only part of the state, the docs prefer to store less, such as a selectedId, and to calculate the rest during rendering.
  3. "Should a fetch move to an event handler too?"
    Usually not. The docs: "You don't need to move this fetch to an event handler." The results must match the query while the component is visible, whatever caused the query to change, so a fetch is a job for an Effect, with a cleanup that drops late answers (as seen in Lesson 33). The same test decides it: the data is needed because the component is on the screen.
