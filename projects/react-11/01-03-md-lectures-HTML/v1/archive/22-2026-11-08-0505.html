Calculating Values During Rendering vs. Storing Them in State

Interview Question · ❱ CORE

How do you decide which values belong in state and which are derived?

OverviewBefore We Begin

To follow this lesson comfortably, you should already know a few tools from earlier lessons:

  • From Lesson 12, how useState stores a value for a component, how calling its setter asks React to call the component again, and why the initial value passed to useState is used only on the first render.
  • From Lesson 06 and Lesson 09, how a parent passes props to a child and how expressions such as ? : and && pick what JSX to return.
  • From Lesson 15, Lesson 17, and Lesson 18, how map turns an array into rows with a key on each row, how filter returns a new array without the removed item, and how { ...obj, key: newValue } copies an object with one changed field.
  • From Lesson 20, how a controlled <input> reads its text from value={query} and updates state in onChange through e.target.value.

Think of a shopping list on paper. You write one item per line: bread, milk, eggs. How many items are on the list? You could write the number 3 at the bottom of the page. Or you could count the lines whenever someone asks.

If you write 3 at the bottom and then cross out milk, the list now has two items, and the bottom of the page still says 3. Your two notes on the same page disagree. If instead you count the lines whenever someone asks, the answer is always 2, because it comes straight from the lines that are there right now.

A React component faces the same choice every time it shows a number, a filtered list, or a chosen item:

The values a component shows on the page
├── 1. Stored in state with useState
│ └── React keeps it between renders, and it changes only when a handler calls its setter
└── 2. Calculated during rendering with const
└── A plain variable in the component body, computed fresh from state and props on every render
Figure 1 — Two ways a component can get a value to show on the page

Both produce a variable that the JSX can put on the page. The one difference is who keeps it up to date. A state variable stays on its old value until your code calls its setter. A const in the component body runs again every time React calls the component, so it cannot lag behind the state and props it reads:

  • A state value is stored with useState. React keeps it between renders, and it changes only when an event handler calls its setter.
  • A calculated value is a plain const inside the component function, computed from state and props while the component runs. React's docs call this calculating during rendering.

Interviewers also call a value calculated during rendering derived, or sometimes derived state. In everyday English, one thing derives from another when it comes out of it, the way a river comes out of its spring. The count of items comes out of the list of items, so the count is derived from the list. Remember that "a derived value" and "a value calculated during rendering" are the exact same thing. It is not a special kind of useState. It is a plain const computed during rendering, with no useState at all:

Inside one render of a component
├── State from useState: the raw changing facts
│ ├── Kept by React between renders
│ └── Updated only when an event handler calls a setter
└── Derived values with const: calculated during rendering
├── Computed fresh from state and props each time the component function runs
└── Never stored in useState, so they never need their own setter call
Figure 2 — What React keeps between renders, and what the component computes on each render

What is at stake is a page that shows two answers that disagree. A line says 5 players above a list of four players. A line says Captain: Mia after Mia has left the team. React's docs say that two parts of a page like this have fallen out of sync: they should agree, and they do not. Each time, the component kept the same fact in two places: once in the list, and once in a second state variable. Then one click by the user updated only one of them. The Console prints no error, even though the two parts of the page disagree.

Readers usually go wrong in one place: they give every value the page shows its own useState. Then every event handler must remember to call every setter. The first handler that forgets leaves the page out of sync.

Both show 3 names when the page opens. It may look the same, or work the same at first, but it is NOT the same thing! They part ways as soon as a handler changes names:

  • With count in its own state, React keeps two separate values in memory: names and count. Calling setNames updates names and leaves count at 3 unless the handler also calls setCount.
  • With names.length, there is no second state variable to update. Because React calls the component again after every change to names, the const line runs again and reads the length of the new array.

React's docs have a name for a state variable that holds count in its own useState: redundant state. In everyday English, something is redundant when it is more than you need because it repeats what is already there, like a second copy of the same note. The number of names is already inside the names array as its .length. Keeping that number a second time in useState is redundant state. The docs' name for reading names.length in a const is to calculate during rendering: writing a const in the component body that runs again every time React calls the component.

  1. On the first render, players has 5 items and count is 5. The page shows 5 players above five rows.

One small fix could be to add a setCount call inside handleRemove. That would patch this one button, and it would leave the trap in place. Later, when we add a button that adds a player or a button that clears the team, every new handler must also remember setCount. The first handler that forgets puts the bug right back on the page.

The real fix is to remove count from state altogether, because players already knows how many items it has. Before we edit TeamList.jsx, compare what happens in both orders when Remove runs first and then React calls TeamList to render:

  • Order 1, Remove runs and count is in useState: handleRemove updates players to 4 items. Then React calls TeamList. useState returns the old count of 5, so the page says 5 players.
  • Order 2, Remove runs and count is a const in TeamList: handleRemove updates players to 4 items. Then React calls TeamList. The const line reads players.length from the new 4-item array, so count is 4 and the page says 4 players.

The same rule applies to text and booleans, not only to array counts. In the React docs' check-in form, storing fullName in state alongside firstName and lastName is redundant: const fullName = firstName + ' ' + lastName; calculates the full name fresh whenever either setter triggers a re-render. In the tic-tac-toe tutorial, xIsNext is removed from state because it can be calculated from currentMove % 2 === 0. Principle 1: Calculate from State During Rendering

When a value can be computed from existing state, calculate it with a const during rendering instead of storing it in its own useState.

A count kept in its own state is redundant state: it stores a second time what the list already knows. Because it changes only when a handler remembers to call its setter, one handler that updates the list without calling setCount leaves the page out of sync. A const that reads players.length runs again on every render, so it always agrees with the list.

DO THIS:

```jsx

const [players, setPlayers] = useState(initialPlayers);

const count = ~players.length~; // Recalculated on every render when players changes

```

DO NOT DO THIS:

```jsx

const [players, setPlayers] = useState(initialPlayers);

const [count, setCount] = ~useState(initialPlayers.length)~; // WRONG: changes only when every handler remembers setCount

```

OverviewPrinciple 2: visiblePlayers Comes from players and query

In Principle 1, the count came from one state variable, players. What when a value on the page depends on two state variables at once? Look at the smallest version of a searchable list:

Two state variables and one calculated list
1const [names, setNames] = useState(['John', 'Mia', 'Sara']);
2const [query, setQuery] = useState('');
3const visibleNames = names.filter(name => name.includes(query));
With query 'a', holds ['Mia', 'Sara']

Only names and query are in useState. visibleNames is a const calculated from both on every render.

How do we know for sure which values belong in state and which should be calculated? In the page Thinking in React, React's docs call this the DRY principle, short for Don't Repeat Yourself. They say: "Figure out the absolute minimal representation of the state your application needs and compute everything else on-demand." They describe state as the minimal set of changing data that your app needs to remember, meaning the fewest values, and only the ones that change, and they give three questions to test any piece of data:

  1. Does it remain unchanged over time? If so, it is not state.
  2. Is it passed in from a parent via props? If so, it is not state.
  3. Can you compute it based on existing state or props in your component? If so, it is definitely not state.

Let us run the values of our team page through those three questions:

Look at the two values that pass all three questions: players and query. You cannot compute the current list of players from the search text, and you cannot compute what the user typed from the list of players. React's docs call values like these essential state: "Notice that these two state variables are essential, because you can't calculate either of them from the other." If you remove either one, the page can no longer do its job. Everything else in that tree is derived: it comes out of players and query.

Readers usually go wrong here by putting the filtered rows into a third state variable, filteredPlayers, and filtering inside onChange, because typing in the search box is the first moment they think about filtering. Compare the two ways:

  • With filteredPlayers in useState, updated inside onChange: the rows on screen come from filteredPlayers, which is rebuilt only when the user types in the search box.
  • With visiblePlayers in a const, calculated during rendering: the rows on screen are rebuilt from players and query on every render, whether the render was caused by typing or by clicking Remove.

While the user is only typing in the search box, both ways show the same filtered rows. It may look the same, or work the same at first, but it is NOT the same thing! Watch what happens in TeamList.jsx when filteredPlayers is kept in state and updated inside onChange:

Principle 2: Calculate from Multiple State Values

Keep only the essential state variables that cannot be computed from each other, and derive every filtered list or combined count from them during rendering.

players and query are essential state: neither can be calculated from the other. visiblePlayers can be calculated from players and query, so storing it in a third useState is redundant state that updates only when the handler that calculates it runs. Computing visiblePlayers in the component body ensures it updates whether setPlayers or setQuery triggered the render.

DO THIS:

```jsx

const [players, setPlayers] = useState(initialPlayers);

const [query, setQuery] = useState('');

const visiblePlayers = ~players.filter(player => player.name.includes(query))~; // Updates when either players or query changes

```

DO NOT DO THIS:

```jsx

const [players, setPlayers] = useState(initialPlayers);

const [query, setQuery] = useState('');

const [filteredPlayers, setFilteredPlayers] = ~useState(initialPlayers)~; // WRONG: stays stale when setPlayers runs without setFilteredPlayers
```

OverviewPrinciple 3: Keep captainId in State, Not the captain Object

Look at two ways a component can remember which item in a list is chosen:

With the chosen object in state
1const names = [{ id: 0, name: 'John' }, { id: 1, name: 'Mia' }];
2const [chosen, setChosen] = useState(names[1]);

3
4<p>{chosen.name}</p>

1const names = [{ id: 0, name: 'John' }, { id: 1, name: 'Mia' }];
2const [chosenId, setChosenId] = useState(1);
Stores only Mia's id, 1
3const chosen = names.find(item => item.id === chosenId);

4

The version with chosenId in state uses a new helper: JavaScript's array method find. Like filter, find calls the arrow function we pass it once for each item in the array, in order. Instead of returning an array of matches, find stops at the first item for which the function returns true and returns that single item. When no item in the array matches, find returns undefined.

On the first render, both paragraphs print Mia. It may look the same, or work the same at first, but it is NOT the same thing! Look at what lives in state in each version:

  • With the chosen object in state, Mia's object { id: 1, name: 'Mia' } is held in two state variables at once: inside the list, and again in chosen. React's docs call this duplication in state: keeping the same information in two places in state.
  • With the chosen id in state, state holds the list and one number, 1. Mia's object lives in one place only, inside the list, and names.find looks it up on each render.

Think of a book of team recipes. If you photocopy page 12 and tape the photocopy to the fridge, and then someone crosses out an ingredient on page 12 in the book or tears page 12 out, the photocopy on the fridge still shows the old page 12. If instead you put a bookmark at "page 12" and open the book to page 12 whenever you cook, you always see page 12 as it is right now, or you see at once that page 12 is no longer in the book. Storing captain as an object is the photocopy. Storing captainId is the bookmark.

  2. Avoid contradictions in state: replace booleans that can disagree with one status variable, as in Lesson 21.

Now compare that nested object with the flat shape from React's docs. Every place sits at the top level of one object under its own numeric id, and instead of holding full child objects, each place holds an array of numbers called childIds:

React's docs call the shape where every place sits at the top level under its id flat state, also known as normalized state. Think of how a database engineer organizes a database table so each record lives in one row under its id, and rows point to other rows by id instead of stuffing whole tables inside other tables. In computer science, organizing data that way so nothing is nested or duplicated is called database normalization. React's docs say this state structure "might remind you of seeing a database table," and they call the outer object keyed by 0, 1, and 2 the "table" object.

Now compare the two shapes on two questions. First, for the information they hold: yes, it is the exact same thing! Both say that Earth has child 1, Africa, and Africa has child 2, Kenya. Second, for the work of removing a deeply nested place like Kenya: it is NOT the same thing!

  • In the nested plan, Lesson 17's rule of copying every level means that removing Kenya from Africa's childPlaces requires making a new Africa object with its new childPlaces array, and then making a new Earth object with its new childPlaces array, and in a deeper tree every parent level above it as well.
  • In the flat plan, Africa is not stored inside Earth. Africa sits at plan[1] at the top of the table object. Removing Kenya 2 from Africa 1 touches only two objects: a new Africa without 2 in its childIds, and a new top-level plan table object with key 1 pointing to that new Africa.

When updating deeply nested objects becomes repetitive because every parent level must be copied, flatten the state into a table object keyed by id where each item holds an array of childIds.

In a deeply nested tree, changing one item near the bottom requires copying every parent object on the path back to the root. In a flat table object where each item stores childIds, removing or reordering a child updates only that one parent item and the top-level table object.

OverviewSummary & Interview

The Interview Question: How do you decide which values belong in state and which are derived?

Model Answer

I test every piece of data with the three questions from React's Thinking in React guide: does it stay unchanged over time, is it passed in from a parent via props, or can it be computed from existing state or props in the component? If the answer to any of the three is yes, it does not belong in useState. Only the minimal set of changing data that cannot be computed from anything else is essential state, such as players, query, and captainId. Everything else is derived, meaning calculated during rendering with a plain const, such as visiblePlayers from players.filter, count from players.length, and captain from players.find.

Keeping derived values out of useState prevents three classic synchronization bugs:

  1. Redundant state: storing count or filteredPlayers in state leaves the UI out of sync whenever one handler updates players and forgets to call the second setter.
  2. Duplication in state: storing a full selectedItem or captain object in state duplicates the object inside the array, so editing or removing that item in the array leaves the selected state holding stale data. Storing only selectedId avoids the duplicate.
  3. Mirroring props in state: passing a prop to useState reads that prop only on the first render. If I intentionally want to ignore later prop updates, I prefix the prop name with initial or default, such as initialColor.

Finally, for values that do belong in state, I group related state into one object when two variables always change together, and I flatten deeply nested state into a normalized table object keyed by id with childIds arrays so updates do not have to copy every parent level.

Common Follow-Up Questions

  1. "Is it not slow to recalculate a filtered list on every render?"
    Usually not. Unless you are creating or looping over thousands of objects, recalculating a derived array during rendering is fast, and React's docs recommend measuring with console.time before optimizing. When a measured calculation is genuinely slow, you still do not move the value into useState: you wrap the calculation in useMemo so React reuses the previous result when players and query have not changed, which Lesson 56 covers. Even then, useMemo does not make the first render faster. In projects that use the React Compiler, covered in Lesson 63, expensive calculations during rendering can be cached automatically.
  2. "Why not store the derived count or filtered list in state and synchronize it inside a useEffect?"
    Because an Effect runs after React has already rendered the component and put the result on the page. When players changes, React first renders the component with the new players list and the stale count, and then the Effect calls setCount and forces a second render right after. React's docs say this is more complicated than necessary, and inefficient too. Calculating const count = players.length; during rendering produces the right value in a single render pass. Lesson 34 covers how to replace such Effects with values calculated during rendering.
  3. "When the user can select multiple items in a list, what belongs in state?"
    An array of selected ids, such as [0, 2], or a JavaScript Set of ids, which is a built-in collection of unique values. Just as with a single captainId, you never copy the selected item objects into a second array in state. Whether a row is selected and how many rows are selected are derived during rendering from those ids, and when you keep a Set in state, you copy it into a new Set before adding or deleting an id and passing the new Set to the setter.
