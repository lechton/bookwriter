How a Server Function's Answer Reaches the Line Under the Email Field

Interview Question❱ CORE

How do a Server Function's return values and errors reach the UI?

How does the server's "already subscribed" get onto the page, right under the email field?

Overview · Two Ways Side by SideAA Formaction={subscribe}vsBuseActionState(subscribe)Both run the Server Function, only useActionState keeps its answer

A function answers with return, and only the code that called it receives that answer. When a form calls a Server Function, pass the Server Function through useActionState: React keeps whatever it returns as state, and your component shows it. Without it, the form is the caller, so a refusal such as "already subscribed" reaches the browser, nothing shows it, and the user believes the signup worked.

Remember how return works in plain JavaScript. The value goes back to the line that called the function. If that line stores it in a variable, you have it. If not, the value is lost:

Plain JavaScript: the caller receives the returned value
1const total = add(2, 3);
The caller keeps the answer: total is 5
2add(2, 3);
The function still returns 5, but no variable receives it

A Server Function works exactly the same way. In Lesson 110, our own click handler called it, so our code kept the answer:

Our handler is the caller, so our code receives the answer
1const answer = await subscribe(email);
Answer holds what subscribe returned

In Lesson 112, we gave the Server Function to the form instead: <form action={subscribe}>. Now the form is the caller. React collects the fields, calls subscribe on the server, and gets the answer back. But no variable of ours receives it. It is the second line of the plain JavaScript example: the function answers, and nobody keeps the answer.

This is why we pass the Server Function to useActionState. It is the same Hook you know from Lesson 42. React calls the action for us, and keeps whatever it returns as state:

useActionState keeps the answer of the Server Function
1const [state, formAction] = useActionState(subscribe, { error: null });
State holds what subscribe returned last
2<form action={formAction}>
The form calls formAction, and React calls subscribe

Take a newsletter form at the bottom of a blog post. A user types john@example.com and clicks Subscribe. A week later, the same user forgets, and subscribes again with the same email. The server looks in the database, finds the email, and refuses. Ask yourself: how does the server's sentence get onto the page, right under the email field?

Why: Only the server can decide this refusal, because only the server can look in the database. But the line under the email field is drawn in the browser. So the answer must travel back over the network, and something in the browser must keep it. It takes three steps:

  1. subscribe returns the answer as a plain object, with the refusal in its error field.
  2. React sends a serialized copy of that object back to the browser (as seen in Lesson 110).
  3. useActionState keeps the copy as state, and the component shows state.error under the email field.

One more rule decides where an answer lands. A refusal the user can fix, like an email that is already saved, is returned. A failure nobody expected, like a database that does not answer, is thrown. A returned value becomes state. A thrown error skips state, and goes to the nearest Error Boundary.

Here is the one sentence to keep in mind for this whole lesson:

A Server Function answers by returning a value, and useActionState keeps that value as state. Return the refusals the user can fix. Throw only the failures nobody expected.

KEY DEFINITION

Server Function. REVIEW A Server Function is an async function that runs on the server, and that code in the browser can call like a normal function. It lives in a file that starts with 'use server'. The browser gets only a reference to it, and a call sends a request to the server (Lesson 110).

KEY DEFINITION

useActionState. REVIEW useActionState is a Hook that takes an action function and a starting value, and returns two things: state and formAction. When the form calls formAction, React calls your action with the previous state and the form data. Whatever the action returns becomes the new state, and React renders the component again (Lesson 42).

KEY DEFINITION

Serializable value. REVIEW A serializable value is a value React can turn into text, send over the network, and rebuild on the other side: strings, numbers, booleans, null, plain objects and arrays of those, and a few built-ins that React's docs list. An instance of a class you wrote is not one of them (Lesson 107).

KEY DEFINITION

Error Boundary. REVIEW An Error Boundary is a class component that catches an error thrown by any component inside it, and shows its fallback prop in place of that part of the page. It works like catch for components: the part that failed is replaced, and the rest of the page stays (Lesson 72).

KEY DEFINITION

Hydration. REVIEW The server sends the HTML of the page first, and the JavaScript bundle arrives later. Hydration is the step where React, once the bundle has loaded, takes the HTML already on the screen and attaches your event handlers to it. Before hydration, no handler of yours runs (Lesson 104).

Where Readers Usually Go Wrong

  1. They return an error and keep action={subscribe}. They expect the error to show up by itself. But the form is the caller, and the form keeps nothing.
  2. They keep the one parameter of Lesson 112. With useActionState, React passes the previous state first. So the parameter named formData receives the previous state, not the form data.
  3. They throw for the refusal, or they return the Error object itself. A thrown refusal replaces the whole form with a fallback. An Error object is not text, so React cannot draw it inside a paragraph.

The Two Questions to Ask

For every answer of a Server Function, ask: who receives the returned value? If the form receives it, nothing shows it, so pass the Server Function through useActionState.

Then ask: can the user fix the problem? If yes, return the message. If no, throw, and let an Error Boundary catch it.

PRINCIPLES

A Server Function's answer is its returned value, and the form needs useActionState to keep it. Five principles follow:

  1. action={subscribe}: the form is the caller, so the returned refusal reaches no code of ours. The answer comes back to the browser, React empties the email field as after a success, and nothing shows the refusal.
  2. useActionState: whatever the Server Function returns becomes state. The Server Function receives the previous state first and the form data second.
  3. state.error: the refusal appears exactly where the component writes it. Under the email field, the user knows at once which field is wrong.
  4. throw in a Server Function: the error skips state and reaches the nearest Error Boundary. The fallback replaces the whole form, so throw only failures the user cannot fix.
  5. useActionState with a Server Function: the refusal appears even before JavaScript loads. The server renders the page again with the answer already under the email field.

The Mistake: Returning an Answer That Nothing Reads

A developer adds the duplicate check, returns the refusal exactly as above, and tests the form:

  1. The developer subscribes with a new email. The field empties, which looks right.
  2. A tester subscribes twice with the same email. The field empties again, and no message appears.
  3. The developer looks for an error in the browser's Console and finds none. subscribe threw nothing. It returned an answer that nobody read.

The fix is to give the returned value a place to land. That place is the state of useActionState.

Remember: a returned value goes back to whoever called the function. With action={subscribe}, the caller is the form, and the form keeps nothing.

The Mistake: Keeping the One Parameter of Lesson 112

  3. A plain object has no get method. So the call throws a TypeError on the server: formData.get is not a function.
  4. subscribe stops there, before it saves anything.

PRINCIPLE4throw in a Server Function: the error skips state and reaches the nearest Error Boundary

Principle 4

Return or Throw: Only a Returned Refusal Becomes state

Summary: Return a refusal the user can fix as plain data; throw only an unexpected failure, and wrap the form in an Error Boundary to catch it.

Description: A returned value becomes state, and appears where the component writes it. A thrown error never becomes state. React throws it again from useActionState, cancels the queued submits, and the nearest Error Boundary shows its fallback in place of the form. Whatever you return must be serializable, so return the text of an error, never the Error object.

throw in Plain JavaScript Jumps to the Nearest catch

Remember what throw does in plain JavaScript. It skips every line after it, and jumps straight to the nearest catch:

1try {
2 throw new Error('The database is not answering');

Components have no try around them. In React, the nearest Error Boundary plays the part of catch. It catches the error, and shows its fallback in place of the part that failed (as seen in Lesson 72).

So far, the server refused an email for a reason the user can fix. Now picture a failure nobody expected: the database does not answer. There are two ways for subscribe to say no:

Returning the refusal and throwing it
1return { error: `${email} is already subscribed.` };

2throw new Error('The database is not answering');

Both lines stop subscribe, and both mean "it did not work". It may look the same, but it is NOT the same thing! They land in two different places:

  • With return { error }, the value travels back and becomes state. The line appears under the email field.
  • With throw, nothing becomes state. React throws the error again from useActionState, inside SubscribeBox. The nearest Error Boundary above it catches the error, and shows its fallback in place of the form.

React's docs draw the same line: return known errors as part of the state, and throw only unknown errors. For an unknown error, "React will cancel all queued Actions and shows the nearest Error Boundary by rethrowing the error from the useActionState hook."

Mistake 1: Returning the Error Object Itself

Sometimes a developer wants the database failure under the email field too, as a line instead of a fallback. So the developer wraps the database call in try and catch, and returns what the catch receives:

src/actions.js
1try {
2 await db.subscribers.add(email);
3} catch (err) {
4 return { error: err };
WRONG err is an Error object, not the text of the error
5}

An Error is an instance of a class. React's docs list the values a Server Function may return. Instances of a class are not on that list, apart from a few built-ins, and Error is not one of them.

React 19 still carries the Error back to the browser, but as an Error object, not as text. Two things go wrong:

  1. state.error now holds an object, and React cannot draw an object inside a paragraph. When the component renders again, React throws an error: objects are not valid as a React child. The Error Boundary replaces the form with its fallback, and the line the developer wanted never appears.
  2. In a production build, React leaves the message out on the way to the browser. The Error that arrives no longer says The database is not answering. Its message only points to React error 441.

The fix is to return plain text. The message field of the error is a string:

src/actions.js
1} catch (err) {
2 return { error: err.message };
A string: the line under the email field reads The database is not answering
3}

Mistake 2: Throwing for the Known Refusal

The opposite mistake is to throw for the refusal the user can fix:

src/actions.js
1if (await db.subscribers.has(email)) {
2 throw new Error(`${email} is already subscribed.`);
WRONG the fallback replaces the form, and queued submits are cancelled
3}

The user never sees the line under the email field. The fallback replaces the whole form, so the user cannot even type another email. React's docs give the fix for this case: "catch errors within your reducerAction and return an error state instead of throwing."

Remember: a returned value becomes state. A thrown error skips state, and lands in the nearest Error Boundary.

Old-School Forms: the Server Sends Back a Page With the Error in It

Remember how forms worked before JavaScript did everything. The browser posted the form, and the server answered with a whole new page. If the email was wrong, the server wrote the error into that page. No JavaScript ran in the browser.

useActionState with a Server Function gives you exactly this, and you write no extra code for it.

The Same Tap on the Slow Phone

We go back to the user of Lesson 112, on a phone with a slow connection. The server has sent the HTML of the post and the form. The JavaScript bundle is still downloading. The user types john@example.com, already saved, and taps Subscribe.

The refusal appears under the email field, even though useActionState is a Hook, and no JavaScript has run on the phone yet. React's docs say it directly: with a Server Function, useActionState "allows the server's response to be shown before hydration" completes.

React's docs list three conditions for a form error shown without JavaScript:

  1. The <form> is rendered by a Client Component.
  2. The function passed to the form's action is a Server Function.
  3. useActionState displays the error message.

Our SubscribeBox already meets all three. This principle adds no code. Only the moment of the tap changes.

The Mistake: Showing the Answer With Our Own Click Handler

A developer shows the refusal the way of Lesson 110: a button with onClick, a call to subscribe, and setError with the answer.

  1. Everything works on the developer's fast laptop, where the bundle loads at once.
  2. A user on a slow phone taps Subscribe before the bundle loads. No handler is attached yet, so nothing is sent, and no line appears (as seen in Lesson 112).

useActionState does two more things for a form sent before hydration finishes. React replays the submits the user made before hydration finished. And its third argument, permalink, picks the page the browser goes to when the form is sent without JavaScript. Both come later (Lesson 137).

Interview PrepFor the Interview

The Interview Question: How do a Server Function's return values and errors reach the UI?

How to Answer Clearly in 30 Seconds

"A Server Function answers by returning a value. React serializes that value on the server and sends it back to the browser. But a value only reaches the UI if some code receives it. If the form calls the Server Function directly with action={subscribe}, nothing keeps the answer. So we pass the Server Function to useActionState in a Client Component, and give its formAction to the form. Then:

  1. The Server Function receives previousState first and formData second, and whatever it returns becomes state.
  2. Known errors are returned, such as { error: 'john@example.com is already subscribed.' }, and the component renders state.error right under the field it is about.
  3. Unknown errors are thrown. React throws them again from useActionState, cancels queued submits, and the nearest Error Boundary shows its fallback.

Everything that crosses the network must be serializable, so we return text, never an Error object. And with this setup, the server can render the error into the page even before the JavaScript bundle loads."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why not throw an error for every failure and catch it in an Error Boundary?"
    Because an Error Boundary replaces the part that failed with its fallback. For a refusal the user can fix, such as an email already subscribed, the user loses the whole form and cannot even type another email. React also cancels every submit still waiting in the queue. React's docs advise to catch errors inside the action and "return an error state instead of throwing." Throw only for failures nobody expected, such as a database that does not answer.
  1. "What can a Server Function return?"
    Only serializable values: strings, numbers, booleans, null, plain objects and arrays of those, and a few built-ins that React's docs list. An instance of a class is not supported, and an Error is one. So return err.message, not err. The starting value of useActionState follows the same rule: "When using Server Functions, initialState needs to be serializable." The returned value can be a single string, or a plain object with one key per message, such as { error }.
  1. "Can the browser check the email instead, with required on the email field?"
    It can help the user, but it cannot replace the server's check, for two reasons. First, "already subscribed" is a fact only the database knows. Second, anyone can send the request without our page at all. React's docs say it plainly: "Arguments to Server Functions are fully client-controlled. For security, always treat them as untrusted input." So the Server Function validates every argument on the server (Lessons 130 and 162).
