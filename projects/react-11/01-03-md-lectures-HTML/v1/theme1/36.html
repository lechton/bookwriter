Separating Events from Effects with useEffectEvent

(How can an Effect read a value without running again every time that value changes?)

Interview Question · ❱ CORE

How do you keep non-reactive values from re-running an effect?

Overview · Two Ways Side by SideAuseEffectvsBuseEffectEventThe Effect runs again when a value changes, the Effect Event only reads it

useEffectEvent lets an Effect read the latest value without running again when that value changes.

In React, an Effect often needs to read a value that has nothing to do with why it runs, like a Mute checkbox, the color theme, or the number of items in a cart when a page visit is logged. Normally, every value an Effect reads goes into its dependency array, and every change of that value runs the Effect again. That is right for the value the Effect is about, but wrong for a value it only glances at. useEffectEvent lets an Effect read the latest value without running again when that value changes.

Take a chat room with a Mute notifications checkbox at the top. When a message arrives, the app plays a sound, unless Mute is ticked. Ask yourself: when the user ticks Mute, should the app leave the room and connect again? No. Only the sound should stop. The connection depends on the room, and the sound depends on the checkbox.

Why: If you read the checkbox state directly inside useEffect, the linter asks you to put it in the dependency array. Then every tick or untick of Mute disconnects from the chat server and connects again from scratch, just to turn a sound on or off. See the problem? The Effect runs again for a value it only reads at the moment a message arrives. Reading the checkbox inside a function made with useEffectEvent lets the Effect see its latest value and depend only on the room.

Now let's see why you need the second one.

Think of a chat app with rooms, like Slack. A menu lets the user pick a room. Next to it sits a checkbox: Mute notifications. The user does two everyday things, and expects two different results:

  1. The user picks another room. The app leaves the old room and connects to the new one.
  2. The user ticks Mute notifications. The notifications stop. Nothing else changes: same room, same connection.

In plain JavaScript, this is easy. You connect once. The message handler reads the muted variable each time a message arrives:

1let muted = false;
2const connection = createConnection(serverUrl, 'general');

Changing muted never touches the connection. The handler simply reads the current value when it runs.

In React, the connection lives in an Effect (Lesson 35). The messages arrive through that connection, so the check of muted must sit inside the same Effect. And here is the problem: every prop and every state variable the Effect reads must go in its dependency array.

React, first try: muted goes in the array

The user only wanted silence, and the chat disconnects and connects again. React's docs describe this exact case: "every time isMuted changes ... the Effect will re-synchronize, and reconnect to the chat. This is not the desired user experience!"

React's answer is a Hook called useEffectEvent. You move the one check that reads muted out of the Effect, into a function React calls an Effect Event. The Effect calls it when a message arrives:

React with an Effect Event: muted leaves the array
1const onMessage = useEffectEvent(msg => {
An Effect Event: reads the latest muted each time it runs
2 if (!muted) showNotification('New message: ' + msg);
3});
4
5useEffect(() => {
6 const connection = createConnection(serverUrl, roomId);
7 connection.connect();
8 connection.on('message', msg => onMessage(msg));
9 return () => connection.disconnect();
10}, [roomId]);
Only roomId: picking a room reconnects, ticking the checkbox does not

So you get the plain JavaScript behavior back. A function reads the current value when it runs, and the connection stays.

KEY DEFINITION

What is a reactive value? REVIEW A reactive value is a value that a render can change: a prop, a state variable, or a variable calculated from them inside the component.

When an Effect reads a reactive value, the linter asks you to put it in the dependency array.

After every render, React compares the array with the last one. If one value changed, React runs the old cleanup, then the setup again. For a chat, that means disconnect, then connect.

roomId and muted are both props. So for the linter, they are the same kind of value (Lesson 35).

KEY DEFINITION

What is an Effect Event? NEW An Effect Event is a function you get back from useEffectEvent, a Hook React added in version 19.2. You give it a function, and it gives you back a new function.

You call it from inside your Effect, like any function. Each time it runs, it reads the latest props and state.

It is not reactive: a change of the values it reads never makes the Effect run again. So neither the Effect Event nor the values it reads go in the dependency array.

React's docs: "You can think of Effect Events as being very similar to event handlers. The main difference is that event handlers run in response to user interactions, whereas Effect Events are triggered by you from Effects."

So, once more: the Effect runs again when a value changes. The Effect Event only reads it (Lesson 36).

The Rule of Thumb: does the user want the Effect to run again?

Ask one question about every value the Effect reads: when it changes, does the user want the Effect to run again? If yes, keep it in the array. If no, read it in an Effect Event.

  • roomId: yes. React's docs: "From the user's perspective, a change to the roomId does mean that they want to connect to a different room."
  • muted: no. Ticking the checkbox means the user wants silence, not a new connection.

There are four ways to handle a value that an Effect reads (Lesson 35). This lesson teaches the second one:

  1. Keep it in the dependency array when a change means the Effect must run again, such as roomId.
  2. Read it in an Effect Event when you only need it at the moment something happens, such as muted when a message arrives.
  3. Change the code so the value is no longer a dependency, for example by moving it outside the component (Lesson 37).
  4. Suppress the linter. React's docs: "We recommend never suppressing the linter." Principle 3 shows why.

A senior developer also knows the four classic mistakes:

  1. Silencing the linter to stop the reconnect. The React blog notes that "most users just disable the lint rule and exclude the dependency." The checkbox then stops working.
  2. Putting the Effect Event in the dependency array. The chat then reconnects after every render.
  3. Wrapping the whole connection in an Effect Event, only to make the array shorter. The chat then never leaves the first room.
  4. Calling the Effect Event from a click handler, or passing it to a child, as if it were an ordinary function.

The rest of the lesson shows each mistake on a real chat room.

Now let's break it. Each principle puts the check of muted in another place and shows what the user sees:

PRINCIPLES

An Effect runs again when a value it reads changes. An Effect Event reads the latest value and does NOT make the Effect run again. Five principles follow:

  1. Principle 1: Every Value the Effect Reads Goes in Its Array. With the check of muted inside the Effect, every tick of the checkbox reconnects the chat.
  2. Principle 2: An Effect Event Reads the Latest Value Without Reconnecting. onMessage reads muted for each message, and neither of them goes in the array.
  3. Principle 3: A Suppressed Linter Leaves the Effect With an Old Value. The reconnect stops, but the checkbox stops working too.
  4. Principle 4: Move Only the Lines That Should Not Run Again. The connection must follow roomId, so it stays in the Effect.
  5. Principle 5: Call an Effect Event Only From Its Own Effect. Never during rendering, never from a click handler, never from a child.

React's docs give the two kinds of code a name:

  • Code in an event handler is not reactive. It runs again only when the user clicks again. handleSendClick reads message, yet typing does not send anything. The docs: "a change to the message does not mean that they want to send a message. It only means that the user is typing."
  • Code in an Effect is reactive. It runs again whenever a value it reads changes. A new roomId means disconnect, then connect.

Then the docs add: "Things get more tricky when you want to mix reactive logic with non-reactive logic." Our notification is exactly that mix. It must live inside the Effect, because the message comes from the connection. But the check of muted should behave like an event handler: read the value when the message arrives, and ignore its changes.

useEffectEvent in its smallest form

useEffectEvent comes from React, like useEffect. You give it a function, and you get back a new function, the Effect Event:

The smallest useEffectEvent
1import { useEffect, useEffectEvent } from 'react';

React's docs: "It's a part of your Effect logic, but it behaves a lot more like an event handler. The logic inside it is not reactive, and it always 'sees' the latest values of your props and state."

So an Effect Event and an event handler share one thing. Both read the current values at the moment they run, and neither runs again when those values change. The one difference is who calls them. React calls an event handler when the user clicks. Your Effect calls an Effect Event, here when a message arrives.

Where does onMessage get the latest muted?

From React. The function the connection holds was created in the first render. Yet onMessage reads muted as it is now. The docs promise exactly that. Their words: "When you call the returned Effect Event function, the callback always accesses the latest committed values from render at the time of the call."

In plain words, onMessage reads the props and state of the latest render that reached the screen. The docs do not say how React does this inside, and you do not need to know it to use the Hook.

msg comes from somewhere else: the Effect. The connection hands the message text to the arrow function, and the arrow function passes it on to onMessage as an argument.

onMessage in the array reconnects on every render

Beware! An Effect Event in the array brings the reconnect back, and makes it worse: the chat reconnects after every render. Out of habit, developers add every function the Effect calls to its array:

src/components/ChatRoom.jsx
1useEffect(() => {
2 const connection = createConnection(serverUrl, roomId);
3 connection.connect();
4 connection.on('message', msg => onMessage(msg));
5 return () => connection.disconnect();
6}, [roomId, onMessage]);
WRONG onMessage is new on every render, so the chat reconnects on every render

Here is what goes wrong:

  1. The linter reports it: "Functions returned from useEffectEvent must not be included in the dependency array".
  2. If the code runs anyway, the Effect runs after every render, because "Effect Event functions do not have a stable identity".
  3. The identity of a function is which function object it is. React gives onMessage a brand-new function object on every render, on purpose.
  4. So the comparison of the array always sees a change. The chat disconnects and connects again on every render, including every tick of Mute.

Remember: the Effect runs again when a value in its array changes. The Effect Event never goes in the array.

Name the Effect Event after what the user thinks happened

The name onMount was the first warning sign. It says when the code runs, not what happened for the user. The docs ask you to "name your Effect Events after what the user thinks has happened, not when some code happened to run."

They warn about onMount and onUpdate. The same goes for onUnmount and onAfterRender. These names are "so generic that it's easy to accidentally put code that should be reactive into them." Good names describe an event the user would recognize, such as onMessage or onVisit. Two more from the docs are onTick and onConnected.

To decide what moves, ask the Rule of Thumb question for each piece of code. When this value changes, does the user want this code to run again?

  1. The connection: yes. A new roomId means a new room. The connection stays in the Effect, with roomId in the array.
  2. The notification check: no. A new muted does not mean a new connection. The check moves into onMessage.

Principle 5

Summary: Call an Effect Event only from its own Effect or from another Effect Event. Never call it during rendering or from an event handler, never pass it to another component or Hook, and declare it next to the Effect that uses it.

A click handler and a child get the linter's warning

Each has its own reason:

  2. A child would get a function that changes on every render. An Effect Event is a new function object after every render. If the child lists it in the array of its own Effect, that Effect runs after every render.

The docs show the second case with a timer. A component passes its Effect Event to a custom Hook, useTimer, and the timer restarts on every render. Their advice: "If you need a callback for event handlers or to pass to children, use a regular function or useCallback instead." useCallback gets its own lesson (Lesson 57), and so do custom Hooks that take a function (Lesson 39).

Interview PrepFor the Interview

The Interview Question: How do you keep non-reactive values from re-running an effect?

How to Answer Clearly in 30 Seconds

"Every reactive value an Effect reads must be in its dependency array. So a value I only need at the moment something happens, such as a Mute setting checked when a chat message arrives, still re-runs the whole synchronization. The fix is useEffectEvent, which React 19.2 added:

  1. Extract the non-reactive logic: I move the lines that read that value into an Effect Event, declared with useEffectEvent at the top level of the component. I call it from inside the Effect.
  2. Leave it out of the array: the Effect Event always reads the latest props and state when it is called, and neither it nor the values it reads go in the dependency array. The Effect keeps only the values that should re-synchronize it, such as roomId.
  3. Respect its limits: I move only logic that should not be reactive, and I never suppress the linter instead. I call the Effect Event only from its own Effect, never during rendering, from a click handler, or from a child."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why not just suppress the linter and leave the value out of the array?"
    Because the value gets stuck. The function the Effect hands to the connection belongs to the render that ran the setup, and each render keeps its own props and state. If the Effect does not run again, that function keeps checking the old value. In our chat, the user mutes the room and still gets notifications until the room changes. Worse, the linter stays silent for every new value the Effect reads later. An Effect Event avoids the reconnect without hiding anything from the linter.
  2. "When should a value be passed to the Effect Event as an argument instead of read inside it?"
    When the value belongs to the event itself. The message text exists only when the connection hands it over, so the Effect passes it to onMessage. React's docs give a second case: a log of page visits. For each new url, the Effect calls onVisit and passes the url as an argument, so the log records the page that caused this visit. If onVisit read url from the component instead, it would get the latest url, which may already be a different page. Asking for the value as an argument also keeps url in the Effect's array, so nobody can remove it by accident.
  3. "Why does an Effect Event get a new identity on every render, unlike a setter or a ref?"
    React does it on purpose. The docs say its identity "intentionally changes on every render", and that "the non-stable identity acts as a runtime assertion", which means a built-in check that fails loudly. If someone lists the Effect Event in a dependency array, the Effect runs again after every render, so the mistake shows up at once instead of hiding. It also makes clear that an Effect Event is not a function to pass around. For a function to give a child, you write a regular function, or wrap it in useCallback when the child needs the same function between renders.
