Connecting a Component to an External System with useEffect

(How does a component start a timer when it appears, and stop it when it leaves?)

Interview Question · ❱ CORE

How do you connect a component to an external system, and how do you disconnect it?

Overview · Two Ways Side by SideAEvent HandleronClickvsBEffectuseEffectOne runs because the user clicked, the other because the component is on the screen

useEffect lets a component start a task by itself, automatically, when it appears on the screen, and stop it when it leaves.

In React, a component often needs to start a background task automatically the moment it appears on the screen, like connecting to a live chat server, starting a ticking timer, or listening for window scroll events. Until now, our code only had two places to run:

  • inside an event handler like onClick when the user clicks something,
  • or right inside the component body while React renders.

Neither place works when a task must start simply because a component showed up on the page. This is why we have useEffect. It gives your code a third place to run: right after React puts the component on the screen, with a built-in way to clean that work up when the component leaves.

Take a live chat window on a customer support page. The moment the chat window appears on the screen, it needs to connect to the chat server all by itself, without waiting for the user to click a Connect button. Later, when the user closes the chat window, it must disconnect so it stops receiving messages in the background. Ask yourself: where do we put the code that opens and closes this server connection? The connection belongs to the chat window component itself, inside a useEffect: it must start automatically the moment React puts that component on the screen, and end the moment React removes it.

Why: Putting the server connection right inside the component body does not work here, because React runs the component function from the top on every single render. The component body is not a safe place for background tasks, because its code runs again on every render. This means that every time the user types a single letter into the message field of the chat window, the component re-renders and opens a brand-new connection to the server all over again. On the other hand, we cannot put the connection inside an onClick handler either, because the user never clicked a button to connect. The process needs to be automatic. See the problem? We need the code to run automatically without a click, but we cannot let it run on every render either. useEffect solves this by running your connection code after the component appears on the screen, and disconnecting cleanly when the component disappears.

In plain JavaScript, a script file runs once, when the page loads. Start a timer at the top of the file, and you get one timer. It runs until the user closes the tab:

Plain JavaScript: the file runs once, so one timer starts
1setInterval(tick, 1000);
Runs once, when the page loads

A component is different. React does not call it once. React calls your component function on every render (Lesson 13). So a line at the top of a component runs again and again.

Until now, a component had two places for code:

  1. The body. It returns the JSX, it runs on every render, and it must only calculate (Lesson 14).
  2. Event handlers. They run when the user does something, such as a click (Lesson 11).

Now take a counter that counts the seconds by itself. It appears, it shows 0, and it goes up by one every second. Nobody clicks anything.

So where does setInterval go? Starting a timer is not a calculation, so it cannot sit in the body. No click starts it, so there is no handler to put it in.

React has a third place for exactly this case, useEffect:

React: start the timer when Counter appears, stop it when Counter leaves

2 const intervalId = setInterval(tick, 1000);

4}, []);
KEY DEFINITION

What is an Effect? NEW An Effect is code that React runs because the component is on the screen, not because the user did something.

You write it with useEffect, a Hook you import from react, like useState. You hand it a function, and React calls that function after it has put the component on the page.

The docs: "Effects let you specify side effects that are caused by rendering itself, rather than by a particular event."

React's docs write Effect with a capital E for this meaning (Lesson 32).

KEY DEFINITION

What is an external system? NEW An external system is any code that React does not control. React controls the elements it builds from your JSX. It does not control the rest.

The usual ones: a timer from setInterval, a listener from window.addEventListener, a connection to a chat server, and a widget from a library that is not written in React.

The docs: "These systems aren't controlled by React, so they are called external."

An Effect connects the component to one of them and keeps it connected for as long as the component is on the screen. The docs' word for this is synchronizing (Lesson 32).

KEY DEFINITION

Rendering code must be pure. REVIEW The body of a component takes props and state and returns JSX. Nothing else.

The docs: "Like a math formula, it should only _calculate_ the result, but not do anything else."

Event handlers are the opposite. In the docs' words, they "do things rather than just calculate them", and they run because of "a specific user action".

An Effect is a third kind of code. It also does things, but no click causes it (Lesson 14).

React removes what it built, not what your code started

Our counter shows its number in an <h1>. When the counter leaves the page, React removes that <h1>, because React built it from your JSX.

The timer is different. React did not start it. Your code did, by calling the browser's setInterval (Lesson 30). So React does not stop it either. Your code has to call clearInterval.

Think of the light in a room. Whoever switched it on switches it off. Your Effect switched the timer on, so your Effect switches it off.

The Rule of Thumb: what causes the work?

Ask what causes the work. A click? Put it in the click handler. The component being on the screen? Put it in useEffect, and stop it in the function your Effect returns.

The docs give a chat page as their example. The chat must stay connected to the chat server for as long as the user can see it, "no matter which interaction caused the component to appear."

A senior developer also knows the four classic mistakes:

  1. The timer in the body. Every render starts one more timer, and the number climbs faster and faster.
  2. No code that stops the timer. The timer runs on after the counter is hidden, and every show adds one more.
  3. A ref so the Effect "runs once". The Console looks right in development, and the timers still pile up for real users.
  4. A purchase in an Effect. It goes out twice in development, and again every time the user comes back to the page.

The rest of the lesson shows each mistake on a real counter.

PRINCIPLES

useEffect runs your code after the component appears on the screen. Whatever that code starts, it must also stop when the component leaves. Five principles follow:

  1. Principle 1: useEffect Runs the Code After the Commit. The commit is the moment React puts the elements on the page. A timer in the body starts again on every render.
  2. Principle 2: The Empty Array Runs the Effect Only on Mount. With no array, the Effect runs after every render and starts one more timer each time.
  3. Principle 3: The Cleanup Function Stops What the Setup Started. Without it, the timer runs on after the user hides the counter.
  4. Principle 4: Fix the Extra Run in Development with a Cleanup, Never a Ref. A ref guard makes the Console look right, and the timers still pile up.
  5. Principle 5: A Click Causes a Purchase, So It Goes in the Click Handler. A purchase in an Effect goes out twice.

The user clicks Show counter. The number climbs, then climbs faster and faster, and the Console prints more Tick lines every second. Here is why:

  1. React calls Counter for the first render. The body calls setInterval, and one timer starts.
  2. In development, <StrictMode> calls the body twice, as Lesson 14 showed. A second timer starts.
  3. A second later, a timer calls onTick. The setter asks for a render, and React calls Counter again.
  4. The body calls setInterval again, and more timers start.
  5. Every render adds timers, and every timer asks for more renders.

Starting a timer is a side effect, not a calculation. The docs state the rule in four words: "Rendering code must be pure." They say the same of a chat connection: connecting to a server cannot happen during rendering.

The same mistake hits a live comments feed. A developer subscribes to the feed in the body. Each change of state renders the component again, and each render opens one more subscription. After six renders, the page holds six subscriptions to the same feed.

PRINCIPLE2The empty array []: the Effect runs only when the component appears

Principle 2

The Empty Array Runs the Effect Only on Mount

Summary: The second argument of useEffect lists every value from the component that the Effect reads. With no array, the Effect runs after every commit. With [], only after the first one. With [a, b], also after any commit where a or b changed.

Description: The code inside the Effect decides what goes in the array, and the exhaustive-deps lint rule checks it. A timer that adds one with the updater c => c + 1 reads no props and no state, so its array is [], and it runs only when the counter appears. Turning the lint rule off hides a missing value, and the Effect keeps the values of an old render. The return line in both blocks below stops the timer, as Principle 3 shows.

What goes in the array

KEY DEFINITION

What is the dependency array? NEW The array is called the dependency array, and the values in it are the dependencies. In the docs' words, it is "The list of all reactive values referenced inside of the setup code".

In plain words: every prop, state variable, or other value from the component that the Effect reads.

You do not pick them. The docs: "you can't "choose" your dependencies." The code inside the Effect decides them.

After each commit, React compares each dependency with its value from the last render, using Object.is, the same check it uses for a setter. React skips the Effect only if every dependency is the same as before. Lesson 35 covers reactive values in full (Lesson 32).

The docs show this with a video player. Its Effect plays or pauses the video, depending on the isPlaying prop:

The docs' VideoPlayer: the Effect reads isPlaying, so isPlaying is in the array
1useEffect(() => {
2 if (isPlaying) {
3 ref.current.play();
4 } else {
5 ref.current.pause();
6 }
7}, [isPlaying]);
The Effect reads isPlaying, so it runs again whenever isPlaying changes

With [] instead, the Effect would never see a new value of isPlaying. A linter catches this. A linter is a tool that reads your code before it runs, in your editor or in the terminal. Its exhaustive-deps rule checks that every dependency is listed. The docs show its message: "React Hook useEffect has a missing dependency: 'isPlaying'."

The updater is what makes [] honest here. Compare two ways to add one:

Adding one with count + 1, and with the updater c => c + 1
1setCount(count + 1);

2setCount(c => c + 1);

Both add one on the first tick. But count + 1 reads the state variable, so count is a dependency. With the updater, the Effect reads no state at all, and [] tells React the truth.

The useEffect reference says: "Now that you're passing c => c + 1 instead of count + 1, your Effect no longer needs to depend on count."

Here is the common mistake. A developer writes count + 1 with [], and the page stops at 1:

  1. The linter reports that count is missing, with a message like the one for isPlaying.
  2. The developer turns the lint rule off for that line.
  3. The Effect keeps the count of the first render, which is 0, because each render keeps its own values (Lesson 15).
  4. So every second, it sets count to 0 plus 1, which is 1.

The docs: "By suppressing the linter, you "lie" to React about the values your Effect depends on."

Putting count in the array also works. But then the Effect runs again on every change of count, and the reference warns that "specifying count as a dependency always resets the interval." The updater is the clean fix.

PRINCIPLE3The cleanup function: what the setup started stops when the component leaves

Principle 3

The Cleanup Function Stops What the Setup Started

Summary: The function that the setup returns is the cleanup function. React calls it before the Effect runs again, and one final time when the component unmounts, so it must stop or undo what the setup started.

Description: When a component leaves the page, React removes the elements it built from your JSX. It does not stop a timer, a listener, or a connection that your setup started, because React did not start them. The cleanup stops them: clearInterval for setInterval, removeEventListener for addEventListener, disconnect for connect.

KEY DEFINITION

What is setInterval? REVIEW setInterval is a browser function. setInterval(tick, 1000) calls tick every second.

It returns a number, the interval ID. To stop the timer, you pass that number to clearInterval. Lose the number, and you can never stop that timer (Lesson 30).

KEY DEFINITION

What is the cleanup function? NEW The cleanup function is the function that your setup returns. Your code writes it, and React calls it.

The docs: "React will call your cleanup function each time before the Effect runs again, and one final time when the component unmounts".

A component unmounts when React removes it from the page. On our page, that happens when the user clicks Hide counter: show becomes false, and Counter is no longer in the JSX.

Remember the light in the room: your setup switched the timer on, so your cleanup switches it off (Lesson 32).

The docs list the usual pairs: ""connect" needs "disconnect", "subscribe" needs "unsubscribe", and "fetch" needs either "cancel" or "ignore"." On our page, setInterval needs clearInterval.

Principle 4

The extra run is a test

React runs the extra setup and cleanup on purpose. The useEffect reference calls it a stress-test: "This is a stress-test that verifies your Effect's logic is implemented correctly."

It shows you the bug at once, on your own screen, before users meet it later. The docs' challenge on the interval says: "React's behavior is not the cause of the bug: the bug already exists in the code. React's behavior makes the bug more noticeable."

So the docs ask a different question: "The right question isn't "how to run an Effect once", but "how to fix my Effect so that it works after remounting"."

The answer is a cleanup. With it, setup, cleanup, setup looks to the user exactly like one setup. The counter goes up by one per second in development and in production.

Turning off <StrictMode> hides the test, just as the ref guard does. The docs: "You can turn off Strict Mode to opt out of the development behavior, but we recommend keeping it on." Lesson 47 covers Strict Mode in full.

PRINCIPLE5onClick: work caused by a click runs once per click, never in an Effect

Principle 5

A Click Causes a Purchase, So It Goes in the Click Handler

Summary: Work caused by a specific user action, such as buying, goes in the event handler of that action. An Effect is only for work caused by the component being on the screen.

Description: An Effect runs every time the component appears: twice in development, and again whenever the user comes back to the page. That is right for a timer or a connection, which the cleanup stops. It is wrong for a purchase, which no cleanup can take back. Ask what causes the work: a click, or being on the screen.

Interview PrepFor the Interview

The Interview Question: How do you connect a component to an external system, and how do you disconnect it?

How to Answer Clearly in 30 Seconds

"With an Effect. An external system is anything React does not control, such as a timer, a listener on window, or a chat server. I call useEffect at the top level of the component and pass it a setup function that connects, for example by calling setInterval. React runs it after the commit, never during rendering, because rendering must stay pure. The setup returns a cleanup function that disconnects, here clearInterval with the interval ID. Three rules keep it right:

  1. The dependency array lists what the Effect reads: no array runs it after every commit, [] only on mount, and [a, b] also when a or b changed. The exhaustive-deps lint rule checks the list, and I never turn it off.
  2. The cleanup undoes the setup: React calls it before the Effect runs again and one final time when the component unmounts. Without it, the timer runs on and connections pile up.
  3. Only work caused by being on the screen: a purchase caused by a click goes in the click handler, not in an Effect."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why does my Effect run twice in development, and how do I make it run once?"
    In development, Strict Mode remounts every component once right after it first mounts, so React runs setup, cleanup, setup. The useEffect reference calls it "a stress-test that verifies your Effect's logic is implemented correctly." The docs say the right question is not how to run an Effect once, but how to fix the Effect so it works after remounting. The fix is a cleanup, so that the user cannot tell one setup from setup, cleanup, setup. A ref guard or turning off <StrictMode> only hides the test, and the bug stays for users who leave the page and come back. In production there is no extra run. Lesson 47 covers Strict Mode in full.
  2. "Can I leave a value out of the dependency array to stop the Effect from running again?"
    No. The docs: "you can't "choose" your dependencies." The code inside the Effect decides them, and suppressing the linter means you "lie" to React, so the Effect keeps the values of an old render. For our counter, count + 1 with [] stops the page at 1. The fix is to change the code so that it no longer reads the value, such as the updater c => c + 1. A ref from useRef and a setter from useState keep the same identity on every render. So they can stay out: "If the linter lets you omit a dependency without errors, it is safe to do." Lesson 36 shows useEffectEvent, and Lesson 37 removes object and function dependencies.
  3. "Does an Effect run before or after the browser paints the screen?"
    After the commit, and usually after the paint. The useEffect caveats explain both cases. When the Effect was not caused by a click, "React will generally let the browser paint the updated screen first before running your Effect." When it was caused by a click, "React may run your Effect before the browser paints the updated screen". When the work must happen before the paint, the tool is useLayoutEffect, which Lesson 49 teaches. One example is measuring a tooltip before the user sees it in the wrong place. Effects also never run during server rendering, as Lesson 102 shows.
