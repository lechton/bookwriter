How a Delete Dialog Escapes Its Row with createPortal

Interview Question❱❱ MORE

How do you render a modal that escapes its parent's overflow and stacking context?

How does a dialog that opens from one small inbox row show over the whole page?

Overview · Two Ways Side by SideADialog inside the rowvsBcreatePortalThe row's CSS cuts the dialog off, or the dialog lands in <body>

In plain JavaScript, you choose where a new element lands, and a dialog usually goes at the very end of <body>, outside everything else on the page. In React, every element lands inside the element of the JSX around it, and createPortal lets a component send part of its JSX to document.body instead. A dialog needs this, because a row's CSS reaches everything inside the row, and it can cut the dialog off or hide it under the next row.

Remember how you add a dialog in plain JavaScript? You create the element yourself, so you also decide where it goes. Usually you put it at the end of <body>, outside every other element of the page:

Plain JavaScript: you choose where the dialog lands
1const dialog = document.createElement('div');
2dialog.textContent = 'Delete this email?';
3document.body.appendChild(dialog);
The dialog lands at the end of <body>, outside every row

In React, you never create elements by hand. React creates them from your JSX, and it puts each element inside the element of the JSX around it. So when a row component renders a dialog, React puts the dialog's <div> inside the row's <div>. Most of the time, that is exactly what you want. For a dialog, it is a problem.

createPortal is how you tell React: "Create this dialog from my JSX, but put its element at the end of <body>, not inside my row."

React: createPortal chooses where the dialog's div lands
1{showDialog && createPortal(<ConfirmDialog />, document.body)}
The dialog's div lands at the end of <body>, outside every row

React's docs call this a modal dialog: a dialog that floats above the rest of the page and waits for the user's answer.

The natural place for the dialog's code is the row component, EmailRow. The row holds the Delete button. It also holds the state that says whether the dialog is open.

Here is the catch. The three dots work only because the row hides everything that does not fit inside it. The browser applies that rule to every element inside the row. Without a portal, the dialog's <div> is one of them. So the row cuts the dialog off, and the user sees only a thin slice of it.

Two trees: the DOM tree and the React tree

Every part of our page sits in two trees at once:

  1. The DOM tree is what the Elements panel of the browser shows: the real elements, such as <div> and <button>, each inside its parent element. The browser applies CSS along this tree.
  2. The React tree is the tree of components that React builds from our JSX, as in Lesson 06: App, then each EmailRow, then the dialog that a row renders. React passes props and sends events along this tree.

Without a portal, both trees put the dialog inside the row. With createPortal, they disagree. In the DOM tree, the dialog's <div> sits directly inside <body>. In the React tree, ConfirmDialog is still a child of EmailRow, exactly where its JSX is written.

It may look as if the dialog has left the row completely, but it has NOT! Only its place in the DOM changes. Its place in React stays where it was. React's docs say it in one sentence: "A portal only changes the physical placement of the DOM node. In every other way, the JSX you render into a portal acts as a child node of the React component that renders it."

Why: Each tree causes one problem for the user of our inbox:

  1. Without a portal, the user clicks Delete and sees only a thin slice of the dialog. The row cuts off the rest, so the user cannot reach Cancel or Delete.
  2. With a portal, but with no care for clicks, the user clicks Cancel, and the email opens behind the dialog. The click still reaches the row's onClick, because in the React tree the dialog is still inside the row.

Remember the one sentence of this lesson. CSS follows the DOM tree. React follows the React tree. A portal changes only the DOM tree.

The Rule of Thumb: fix the dialog's place in the DOM, not its CSS

When a dialog is cut off or covered, look at where its <div> lands in the DOM, not at its own CSS. Render it through createPortal into document.body, and remember that its clicks still travel up through its parent components.

Developers choose between three ways to show a dialog from inside a row that cuts it off:

  1. Change only the dialog's CSS, with a bigger z-index or with position: fixed. This works only when no parent element cuts the dialog off or keeps it under its neighbors. Principle 2 shows how it breaks in our inbox.
  2. Render the dialog through createPortal into document.body. React's docs give this tool for a modal dialog or a tooltip that must appear "above and outside of the rest of the page". This lesson teaches this way.
  3. Use the browser's own <dialog> element, and open it with its showModal method. The browser then draws it in a layer above the whole page. React's docs list <dialog> among the built-in tags, but they do not compare it with portals, so this lesson only names it.

A senior developer also knows the three classic mistakes:

  1. Raising the dialog's z-index to 9999, and expecting the dialog to come out of the row. It stays cut off.
  2. Thinking a portal moves the whole component, so that the dialog loses the row's props and state. It keeps them.
  3. Thinking a click inside the portal can no longer reach the row, because the Elements panel shows the dialog outside the row. The click still reaches it.

The rest of the lesson shows each mistake on a real page.

PRINCIPLES

A dialog written inside a row lands inside the row's <div> in the DOM, so the row's CSS reaches it. Four principles follow:

  1. Principle 1: overflow: hidden on the row cuts the dialog off. The browser hides every part of the dialog that falls outside the row.
  2. Principle 2: z-index: 9999 on the dialog does not free it. The number counts only inside the row's stacking context, and with position: fixed the next row covers the dialog.
  3. Principle 3: createPortal puts the dialog's <div> in <body>. The JSX stays in EmailRow, and the row's CSS no longer reaches the dialog.
  4. Principle 4: A click inside the portal still reaches the row. Events travel up the React tree, so the dialog stops them with e.stopPropagation().

PRINCIPLE1overflow: hidden on the row: the browser hides every part of the dialog that falls outside the row

Principle 1

overflow: hidden: The Row Cuts Off the Delete Dialog

Summary: When an element has overflow: hidden, the browser hides every part of its children that falls outside the element, a dialog written inside it included.

Description: The browser cuts along the DOM tree. A dialog written next to the button that opens it lands inside that button's parent elements in the DOM. If the element it is placed against has overflow: hidden, as an inbox row needs for its three dots, the user sees only the part of the dialog that fits inside the row and cannot reach its buttons.

Something that can be tricky: the browser decides what to cut by looking at the DOM tree, not at your components. You wrote the dialog in JSX, so you expect the user to see it. But JSX only decides that the dialog exists. The CSS of the elements around it in the DOM decides how much of it the user sees.

PRINCIPLE2z-index: 9999 on the dialog: the number counts only inside the row's stacking context

Principle 2

Stacking Context: z-index: 9999 Leaves the Dialog Under the Next Row

Summary: A z-index orders elements only inside their own stacking context and never undoes overflow: hidden, so no CSS on the dialog alone lifts it out of a row that cuts it off or groups it.

Description: A row with position: relative and z-index: 1 starts a stacking context. Every element inside it, the dialog included, is layered only against the row's other children. The next row has the same z-index and a later place in the DOM, so it covers the first row together with its dialog. Raising the dialog's number cannot change where its parent's group lands.

z-index is a CSS number that the browser provides. When two positioned elements overlap, the browser draws the one with the bigger z-index on top. But the browser compares the numbers only inside one group of elements.

KEY DEFINITION

A stacking context. NEW It is a group of elements that the browser layers as one unit: an element with a position such as relative and a z-index other than auto starts one, and every element inside it is layered only against the other elements inside it, never against the rest of the page (Lesson 51).

So the browser works in two steps:

  1. First, it layers the groups. The first <div> sits at level 1, with everything inside it. The second <div> also sits at level 1, and it comes later in the DOM. When two elements have the same z-index, the later one is drawn on top. So the second <div> covers the whole first <div>, John included.
  2. Then, it layers each group inside. John's 9999 decides only the order inside the first <div>, where John is alone.

You might think a bigger z-index always wins. It does not. A z-index is compared only inside its own stacking context, and the parent's level decides where the child's whole group lands. Put the two cases side by side:

  1. With z-index: 9999 on an element in no smaller group, the element is compared with every other element of the page, and the browser draws it on top.
  2. With z-index: 9999 on an element inside a parent with z-index: 1, the element is compared only with the parent's other children. The parent itself sits at 1.

It looks the same, but it is NOT the same thing! The same 9999 is written on the same element. Where the element sits in the DOM decides what that number is compared with.

A dialog with z-index: 9999 sits under a row with z-index: 1. Here is why, in order:

  1. With position: fixed, the browser places the dialog 100 pixels below the top of the window, where it overlaps the second row. The first row no longer decides where the dialog sits, so its overflow: hidden no longer cuts the dialog off.
  2. The first row has position: relative and z-index: 1, so the browser makes it a stacking context. Nobody wrote the words "stacking context" anywhere. The browser starts one because of those two rules.
  3. In the DOM, the dialog is still inside the first row. So its 9999 counts only inside the first row.
  4. The second row also has z-index: 1, and it comes later in the DOM. So the browser draws the second row on top of the first row and of everything inside the first row.
  5. Where the two overlap, the user sees the row Lunch at noon? and not the dialog. The question is hidden under that row, and only Cancel and Delete show below it.

Every change went into the dialog's CSS. The cause is somewhere else: the dialog's place in the DOM, inside the first row.

This is how developers really lose an afternoon. They raise the z-index to 999999, and nothing changes. Then they start changing the parents' CSS. They remove overflow: hidden from the row, and every long subject loses its three dots. The fix is not more CSS on the dialog. The fix is a different place in the DOM, and that is what a portal gives. Both changes to .dialog were only tries, so the styles file goes back to the version of Principle 1.

KEY DEFINITION

A portal. NEW It is the part of a component's JSX that React puts somewhere else in the DOM, and in the words of React's docs, "Portals let your components render some of their children into a different place in the DOM. This lets a part of your component 'escape' from whatever containers it may be in" (Lesson 51).

createPortal is a function that React provides. You import it from react-dom, not from react. It takes two arguments:

  1. children is what to render: anything React can render, such as a piece of JSX. In our row, it will be <ConfirmDialog />.
  2. domNode is where to put its DOM nodes: an element that already exists on the page. In our row, it will be document.body.

document.body is provided by the browser. It is the <body> element of the page, the one written in the HTML file, and it exists for as long as our app runs.

This is the React version of appendChild from the start of the lesson. Where you write the JSX still decides the place in the React tree. createPortal lets you choose a different place in the DOM for part of it.

It may look the same, but it is NOT the same thing! Outside the row in the Elements panel looks like outside the row for clicks too. It is not. In the DOM tree, the dialog's parent is <body>. In the React tree, its parent is still EmailRow, and React sends the click there.

So remember the sentence of this lesson once more. CSS follows the DOM tree. React follows the React tree. React's events, props, state, and context all follow the React tree, and a portal does not change it.

Here is what happens, in order:

  2. The user clicks Cancel. React runs the click handler of Cancel, which calls onCancel and sets showDialog back to false.
  3. React sends the click on up the React tree: from Cancel, to the dialog's <div>, and then to the row's <div>. The row has an onClick.
  4. The row's onClick runs setIsOpen(true).
  5. React renders the row again. The dialog is gone, and the line Your offer ends Friday. appears under the subject.

The user only wanted to close the dialog, and the email opened. In the browser's own DOM tree, the click goes from Cancel to the dialog's <div> and then to <body>. It never passes the row. It is React that sends the click up the React tree, where the row is the dialog's parent.

The Delete button inside the dialog sends its click up the same way, so the row's onClick runs there too. But App removes that email in the same render, so the user sees only the row disappear.

This is the mistake developers really meet. They move a dialog into a portal so that a row stops cutting it off. The row, or an element around the row, has an onClick, as inbox rows do. Now every click inside the dialog also runs that onClick. The Elements panel cannot explain why, because the dialog is not inside the row there.

AInside the portale.stopPropagation()vsBThe portal moved up toAppThe same page, the dialog's code in a different place

React's docs give two fixes: "either stop the event propagation from inside the portal, or move the portal itself up in the React tree." Both keep the row's onClick from running for a click inside the dialog:

  1. Stop the click inside the portal. The dialog's outer <div> calls e.stopPropagation() for every click that happens inside it. The dialog's code stays in EmailRow, next to the button and the state that open it.
  2. Move the portal up the React tree. A component with no row's onClick above it renders the dialog, such as App. Then showDialog has to move up to App too, together with the id of the email to delete, as in Lesson 24.

The user sees the same page with both fixes: Cancel closes the dialog, and the email stays closed. The difference is where the dialog's code and state live. Stopping the click adds one prop and keeps the dialog in the row. Moving the portal up moves the state, the dialog, and its props out of the row.

Interview PrepFor the Interview

The Interview Question: How do you render a modal that escapes its parent's overflow and stacking context?

How to Answer Clearly in 30 Seconds

"CSS follows the DOM tree. A modal written inside an element with overflow: hidden is cut off. A modal inside a parent with a z-index is layered only inside that parent's stacking context. A bigger z-index on the modal fixes neither. So I render the modal with createPortal from react-dom, and pass it the modal's JSX and document.body. React keeps the JSX in my component and puts its DOM nodes directly inside <body>, outside every element that cuts it off. A portal changes only the physical placement of the DOM nodes, so two things stay the same:

  1. Props, state, and context: the modal still reads them from the component that renders it.
  2. Events: a click inside the modal still travels up the React tree, so a parent's onClick runs. I stop it with e.stopPropagation() inside the portal, or I render the portal higher up the React tree."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why doesn't z-index: 9999 bring the modal to the front?"
    For two reasons. First, overflow: hidden on a parent hides everything outside that parent, whatever the z-index. Second, a parent with a position and a z-index other than auto starts its own stacking context. The modal's number is then compared only with the parent's other children. A later sibling of the parent with the same z-index covers the whole group. Other CSS properties start a stacking context too, such as an opacity below 1 or a transform. A transform or a filter on a parent even makes position: fixed measure from that parent, so the parent's overflow: hidden cuts off a fixed modal again. The fix is a different place in the DOM, not more CSS on the modal.
  2. "Does a component inside a portal lose its parent's props, state, or context?"
    No. React's docs say: "In every other way, the JSX you render into a portal acts as a child node of the React component that renders it." The modal in <body> reads the props and state of the component that renders it, and it reads the context provided above that component. Only its DOM parent changes. React does need the target element to exist already. Passing null, for example from getElementById with a missing id, makes React throw. Passing a different DOM node during an update makes React create the portal's content again.
  3. "A click inside your portal runs a parent's onClick. Why, and how do you stop it?"
    Because "events from portals propagate according to the React tree rather than the DOM tree." In the DOM, the modal sits in <body>. In React, it is still a child of the row, so React sends the click up to the row's handler. React's docs give two fixes: "either stop the event propagation from inside the portal, or move the portal itself up in the React tree." Stopping the click inside the portal keeps the modal's code next to the state that opens it. Moving the portal up means lifting that state to a higher component. In both cases, a modal in a portal still needs its keyboard focus handled. The user must be able to move focus into it and back out, as the WAI-ARIA modal dialog pattern describes.
