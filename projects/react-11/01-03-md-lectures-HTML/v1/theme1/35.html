The Lifecycle of an Effect as Its Dependencies Change

(What happens to an Effect when a prop changes, but the component stays on the page?)

Interview Question · ❱ CORE

What is the lifecycle of a reactive effect as its dependencies change?

Overview · Two Ways Side by SideAA Component's LifecyclevsBAn Effect's LifecycleThe component mounts once, the Effect starts and stops for every room

An Effect stops and starts again every time a value in its dependency array changes, even while the component stays on the screen.

In React, a component often stays on the screen while one of its values changes, like a chat box when the user picks another room, a map when the user types another city, or a product page when the user picks another size. We usually picture an Effect in two moments: it starts when the component appears, and it stops when the component leaves. But the component is not the only thing with a lifecycle. An Effect has its own: whenever a value in its dependency array changes, React stops the old Effect and starts a new one with the new value.

Take a chat app with rooms, like Slack: general, travel, and music. While the user reads a room, the browser stays connected to the chat server for that room. The user reads the general room, then picks music from the menu at the top. The chat box never leaves the screen. Ask yourself: who closes the general room and opens the music room, if the component never appears or leaves again? Let's follow what React does, step by step:

music picked → handler calls setRoomId('music') → component renders again → React compares roomId, 'general' before and 'music' now → cleanup disconnects from general → Effect connects to music

Why: If the Effect ran only when the chat box appeared, picking a new room would do nothing, and the user would keep talking in the general room. If it opened the music room without closing the general room first, messages from both rooms would pour into the same screen. Therefore, you need to keep in mind that the connection follows the room, not the chat box. That is why React stops and starts the Effect each time roomId changes.

The Room Switch in Plain JavaScript

In plain JavaScript, you would write the room switch yourself. You keep the connection in a variable. When the user picks another room, you close the old connection, and then you open a new one:

Plain JavaScript: you switch the room by hand
1let connection = createConnection(serverUrl, 'general');
2connection.connect();
3
4roomMenu.addEventListener('change', () => {
5 connection.disconnect();
First, close the old room
6 connection = createConnection(serverUrl, roomMenu.value);
7 connection.connect();
Then, open the new room
8});

Notice the order: close the old room first, then open the new one. Forget the first line, and the user stays connected to both rooms.

In React, you do not write the switch. You write two things inside one Effect: how to connect, and how to disconnect. React calls them in the right order, every time the room changes:

React: you write the start and the stop, React does the switch
1useEffect(() => {
2 const connection = createConnection(serverUrl, roomId);
3 connection.connect();
How to start: connect to this room
4 return () => {
5 connection.disconnect();
How to stop: disconnect from this room
6 };
7}, [roomId]);
When roomId changes, React runs the stop for the old room, then the start for the new one

The React docs say it in two sentences: "Your Effect's body specifies how to start synchronizing, and your cleanup function specifies how to stop synchronizing. All that React needs to do now is to call them in the correct order and with the correct props and state."

KEY DEFINITION

What is an Effect, and what is its cleanup? REVIEW An Effect is code that React runs because the component is on the screen, not because the user clicked.

You write it with useEffect. React runs it last: first it calls your component, then it puts the result into the DOM, and only then does it run the Effect.

The function you pass to useEffect is the setup. It starts something outside React, such as a connection to a chat server.

The function that the setup returns is the cleanup. It stops that same thing: it disconnects the exact connection that the setup opened (Lesson 32).

KEY DEFINITION

What is the dependency array? REVIEW It is the array at the end of useEffect, such as [roomId]. It lists the values the Effect reads.

After every render, React compares each value with the one from the last render, using Object.is.

If every value is the same, React skips the Effect. If even one value changed, React runs the Effect again.

With [], nothing can ever change, so the Effect runs once, when the component appears. With no array at all, the Effect runs after every render (Lesson 32).

A component mounts, updates, and unmounts. An Effect only starts and stops.

A lifecycle is the list of stages something goes through over time. The docs put the rule of this lesson in three sentences: "Effects have a different lifecycle from components. Components may mount, update, or unmount. An Effect can only do two things: to start synchronizing something, and later to stop synchronizing it."

So there are two lifecycles on the same page:

  • The component's lifecycle has three stages. It mounts when React adds it to the screen (Lesson 13). It updates when it renders again with new props or state. It unmounts when React removes it from the screen (Lesson 32).
  • The Effect's lifecycle has two steps. The setup starts: it connects. The cleanup stops: it disconnects. This pair can repeat many times while the component stays on the page.

On the first visit, the two look the same. The component mounts, and the Effect connects to general.

The moment the user picks travel, they split. The component does not unmount. It only updates: the heading changes from general to travel. But the Effect must stop and start again: disconnect from general, then connect to travel.

KEY DEFINITION

What does re-synchronizing mean? NEW Re-synchronizing is the docs' word for one stop followed by one start.

When roomId changes from general to travel, the open connection no longer matches the screen. So React runs the old cleanup, which disconnects from general, and then the new setup, which connects to travel.

The component stays on the page the whole time. Only the Effect stops and starts.

Every change of a dependency re-synchronizes the Effect once (Lesson 35).

The Rule of Thumb: one start, one stop, and every value the Effect reads in the array

Write the setup as "connect to this room". Write the cleanup as "disconnect from this room". Put every value the Effect reads in the array. React does the rest.

The goal is simple: the heading on the screen and the connection behind it must always agree on which room the user is in. A senior developer knows the five classic mistakes that break this:

  1. "The cleanup is the unmount code." Then the cleanup that runs on every room switch comes as a surprise. The docs even have a troubleshooting entry for it: "My cleanup logic runs even though my component didn't unmount".
  2. "The cleanup sees the new roomId." It does not. It still holds the old room, and that is exactly what it needs to disconnect.
  3. "The Effect needs no cleanup." Then every switch leaves the old room connected, and the user ends up in two rooms at once.
  4. "Leave roomId out of the array, so the Effect runs only once." The heading says travel, and the connection stays on general. The docs: "You will remain connected to the initial roomId and serverUrl even after the user picks different values in the UI."
  5. "Put the visit log inside the connection Effect, since both run when the user enters a room." Then an edit of the server address logs a visit to a room the user never left.

The rest of the lesson shows each mistake on a real chat page.

PRINCIPLES

An Effect does only two things: it starts, and it stops. Every time a dependency changes, React stops the old Effect and starts a new one. Five principles follow:

  1. Principle 1: An Effect Starts and Stops, It Does Not Mount. The component mounts once, yet the Effect connects three times. Think about one connect and one disconnect at a time.
  2. Principle 2: The Old Cleanup Runs Before the New Setup. On a switch to travel, React first disconnects from general, with the old roomId. Without a cleanup, the old room stays connected.
  3. Principle 3: Every Value the Effect Reads Goes in the Array. With [] and a silenced linter, the heading says travel, and the chat stays on general.
  4. Principle 4: Values from the Component Body Are Reactive. A serverUrl in state joins the array. A constant outside the component does not, and ref.current cannot.
  5. Principle 5: One Effect for Each Job. The visit log gets its own Effect, so an edit of the server address does not log a false visit.

Principle 1

An Effect Starts and Stops, It Does Not Mount

Summary: Think about one start and one stop at a time. The setup connects to this room, and the cleanup disconnects from it, no matter whether the component is mounting, updating, or unmounting.

Description: For the component, opening the chat, picking two rooms, and closing the chat is one mount, two updates, and one unmount. For the Effect, it is three connections in a row: general, travel, and music. Write the Effect as "connect, then disconnect", and React can repeat it every time the room changes.

The docs take the same four clicks and describe them twice: once as the component sees them, and once as the Effect sees them.

The component sees four moments:

  1. ChatRoom mounted with roomId set to general.
  2. ChatRoom updated with roomId set to travel.
  3. ChatRoom updated with roomId set to music.
  4. ChatRoom unmounted.

The Effect sees three connections:

  1. It connected to the general room, until it disconnected.
  2. It connected to the travel room, until it disconnected.
  3. It connected to the music room, until it disconnected.

Count them: four moments for the component, three connections for the Effect. Mount, update, and unmount are useful words for a component. The docs warn: "It's a good way to think about components, but _not_ about Effects."

If you think of an Effect as "code after mount" and "code before unmount", the docs say it "gets complicated very fast." Their simpler rule: "always focus on a single start/stop cycle at a time. It shouldn't matter whether a component is mounting, updating, or unmounting."

One mount, three connections

ChatRoom mounts only once, yet the Effect connects three times. Here is what React does for each click:

  1. Open chat. App renders ChatRoom for the first time, with the general room. ChatRoom mounts, shows the general heading, and the setup connects to general.
  2. Pick travel. App passes travel to the same ChatRoom. It does not mount again. It only changes its heading text. Then React runs the old cleanup, which disconnects from general, and the new setup, which connects to travel.
  3. Pick music. The heading text changes again. React runs the cleanup of the travel render, then the setup of the music render.
  4. Close chat. App stops rendering ChatRoom, so it unmounts. React runs the last cleanup one final time, which disconnects from music.

You can check that the component never mounted again. Open the Elements panel and switch rooms: the <h1> element stays in the DOM, and only its text changes.

What if an Effect returns no cleanup at all? The docs: "React will behave as if you returned an empty cleanup function." So for React, it is the same thing: there is still a stop step, and that step does nothing. For our chat, it means nobody ever calls disconnect, and every room stays connected. Principle 2 shows this bug.

The bug: "connect on mount, disconnect on unmount"

Thinking in component lifecycles leads straight to a broken chat:

  1. A developer looks at ChatRoom and thinks: connect when the component mounts, disconnect when it unmounts.
  2. Mount and unmount happen once each, so the developer writes [] as the dependency array (Lesson 32).
  3. The user clicks Open chat. ChatRoom mounts with general, and the Effect connects to general.
  4. The user picks travel. ChatRoom does not unmount and does not mount again. It only updates. So the Effect never disconnects from general and never connects to travel. Principle 3 fixes this array.

The fix is a change of mindset. When you write JSX, you never ask "is this the first render or an update?" You describe what the screen should show, and React figures out the rest. An Effect works the same way. The docs: "The Effect is also a part of the rendering output."

So you describe only how to start and how to stop. The docs: "If you do it well, your Effect will be resilient to being started and stopped as many times as it's needed." The key: "When your cleanup logic correctly "mirrors" the setup logic, your Effect is resilient to running setup and cleanup as often as needed."

When React calls the setup and the cleanup

The useEffect reference gives the exact timing, in three moments:

  1. When the component mounts: "Your setup code runs when your component is added to the page."
  2. After every render with a changed dependency: "First, your cleanup code runs with the old props and state. Then, your setup code runs with the new props and state."
  3. When the component unmounts: "Your cleanup code runs one final time after your component is removed from the page."

Moment 2 is the one this lesson is about. It is also where the cleanup surprises people. The docs' troubleshooting entry says it plainly: "The cleanup function runs not only during unmount, but before every re-render with changed dependencies."

The heading already says travel, and then the Console prints a disconnect line for general. Here is the order:

Why the cleanup still holds general

KEY DEFINITION

What is a render's snapshot? REVIEW Every render is one call of your component function.

In that call, props and state have fixed values. Every function created during that call, including an Effect and its cleanup, sees those values forever.

A later render is a new call, with new values, and new functions.

So a function from an old render still sees the old values, even after the screen shows new ones (Lesson 15).

In the first render, roomId was general. So the Effect of the first render, and the cleanup it returned, captured general. In the docs' words, each Effect "captures" the value "from its corresponding render." If you could look inside that first Effect, you would see this:

The first render's Effect, with general captured
1() => {
2 const connection = createConnection(serverUrl, 'general');
Captured in the first render
3 connection.connect();
4 return () => connection.disconnect();
Always disconnects the general connection
5}

That is exactly what you want. The cleanup must close the connection that its own setup opened, and that connection belongs to general.

The same holds at the end. When the user clicks Close chat in the music room, ChatRoom unmounts. React calls the cleanup of the music render one final time, and it disconnects from music.

A render with the same room skips the Effect

The docs: "*Because all dependencies are the same, React ignores the Effect from the second render.* It never gets called."

Now a third render changes roomId to travel. Which cleanup runs? The second render's Effect never ran, so it has no cleanup. In the docs' words, React "needs to clean up the last Effect that _did_ run." That is the first render's Effect, so its cleanup disconnects from general.

  4. The general connection stays open in the background. Every new room adds one more open connection.

  2. "You knew that your Effect reads roomId."
  3. "This is why you specified it as your Effect's dependency."

The name for this bug: a stale closure

KEY DEFINITION

What is a stale closure? NEW A closure is a function that remembers the variables of the place where it was created. Every function in JavaScript does this.

A stale closure is a function from an old render that still holds the old values. "Stale" means out of date.

The exhaustive-deps docs name it: a missing dependency "causes stale closures where the hook uses outdated values."

In the docs' challenge, a pointer listener inside an Effect reads canMove, and the linter is silenced. With an empty array, the listener "from the initial render will forever see" canMove as true, even after the user unticks the checkbox (Lesson 35).

What to do when an Effect runs too often

Why does an Effect run again at all? The docs: "Effects are reactive blocks of code." And they compare them with event handlers: "Unlike event handlers, which only run once per interaction, Effects run whenever synchronization is necessary."

If you want the Effect to act only in some cases, put the condition inside the Effect. Never wrap the useEffect call itself in an if. The docs: "You can't declare an Effect conditionally. However, the code inside the Effect can use conditions!" That keeps the Hook at the top level of the component, as the rules of Hooks require (Lesson 38).

And if the linter asks for a value that makes the Effect run too often? Do not silence it. Change the code, so the Effect no longer needs that value. The docs: "The linter only knows when the dependencies are wrong. It doesn't know the best way to solve each case." But "All errors flagged by the linter are legitimate." Two ways to change the code come in the next lessons:

  1. Read the latest value inside an Effect Event, without a reconnect (Lesson 36).
  2. Stop depending on an object or a function that is created again on every render (Lesson 37).

KEY DEFINITION

What is a reactive value? NEW A reactive value is a value that can change from one render to the next. The docs, in bold: "Props, state, and other values declared inside the component are _reactive_".

Why? Because React calculates them during rendering. On each render, React passes in the props, reads the state, and runs your component body from top to bottom. The docs call this the rendering data flow.

Every value that comes out of that flow can be different next time, so an Effect that reads it must list it.

A constant at the top of the file is outside that flow, so it is not reactive (Lesson 35).

Which values go in the array, and which do not

The docs sort every value an Effect can read into four kinds:

  1. Reactive values: they go in the array. Props, state, and every variable calculated in the component body.
  2. Constants outside rendering: they stay out. A constant above the component, or declared inside the Effect, is never calculated during rendering.
  3. Stable values: you may leave them out. React guarantees that some values do not change "on a re-render": the setter from useState and the ref object from useRef (Lesson 30). The docs: "Stable values aren't reactive, so you may omit them from the list. Including them is allowed." That is why the linter never asks for setServerUrl.
  4. Mutable values: they cannot be dependencies. Values such as location.pathname or ref.current "can change at any time completely outside of the React rendering data flow." A change to them does not render the component.

The Interview Question: What is the lifecycle of a reactive effect as its dependencies change?

How to Answer Clearly in 30 Seconds

"A component mounts, updates, and unmounts. An Effect only does two things: the setup starts synchronizing, and the cleanup stops it. While the component stays mounted, that pair can repeat many times. The classic example is a chat room: the setup connects to roomId, and the cleanup disconnects. Three rules:

  1. How React decides: after each render, React compares every item of the dependency array with the previous render, using Object.is. If all are the same, it skips the Effect.
  2. The order on a change: React first updates the DOM. Then it runs the previous render's cleanup, which still holds the old props and state, and then the new setup with the new ones. On unmount, the last cleanup runs one final time.
  3. What goes in the array: you do not choose it. Every prop, state variable, and body variable the Effect reads is reactive and must be listed. A fixed constant moves outside the component. And two jobs that should not run again together get two separate Effects."

Three Classic Follow-Up Questions Interviewers Ask

  1. "When roomId changes from general to travel, why does the cleanup disconnect from general and not from travel?"
    Each render creates its own setup and its own cleanup, and both capture that render's props and state. When roomId was general, React ran that setup and kept the cleanup it returned. On the switch to travel, React calls that saved cleanup before the new setup. Its closure still holds general, so it disconnects exactly the room it connected to. That is the point: a cleanup must undo its own setup.
  2. "What counts as a reactive value? Can I put ref.current or location.pathname in the array?"
    Reactive values are props, state, and every variable or function declared in the component body, because React calculates them during rendering. Values like ref.current or location.pathname change outside the rendering data flow, and the change does not render the component. Without a render, React never compares the array, so listing them does nothing. For an outside value like the pathname, use useSyncExternalStore. Setters and ref objects are stable, so you may leave them out.
  3. "What happens if I silence exhaustive-deps and pass [] so my Effect runs only once?"
    The Effect's closure stays frozen on the first render's props and state. When a prop changes, React compares [] with [], sees no change, and never re-synchronizes. The chat stays on the first room, and any timer or listener inside keeps reading old values: a stale closure. The docs say you "lie" to React this way. The fix is to change the code so the Effect does not need the value, for example with an Effect Event, never to silence the linter.
