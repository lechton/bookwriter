Form Resets, requestFormReset, and Progressive Enhancement

(Why does a form forget what the user typed after the server says no, and how do you keep it?)

Interview Question · ❱❱ MORE

How do React 19 form actions manage automatic form resets, manual requestFormReset, and progressive enhancement?

Overview · Two Ways Side by SideAA Refusal for the UservsBA Success for ReactReact resets the form after every action that does not throw

React automatically resets every uncontrolled <form> after its action finishes, so when the server rejects a submission you must pass back the typed values in defaultValue.

Say a user types a username and an email into a Create Account form and clicks Submit. The server replies that the username is already taken, so the user wants to fix the username without retyping the whole form.

Why: Whenever a form action finishes without throwing, React assumes the submit succeeded and resets every field to its starting defaultValue. Unless your action returns the submitted text so your JSX can pass it into defaultValue, a server refusal wipes out everything the user just typed.

Remember form.reset()? The browser gives this method to every <form> element. Call it, and every field of the form goes back to the text it started with:

Resetting a form in plain JavaScript
1const form = document.getElementById('signup');
2form.reset();
Every field goes back to the text it started with

In Lesson 41, your onSubmit handler called reset() by hand. With a function in the action of a form, you never write that line. React resets the form for you, right after your function ends:

The same reset in React
1<form action={save}>
React calls save, then resets the form when save ends
KEY DEFINITION

The action of a form. REVIEW In plain HTML, the action of a form holds a URL. The browser sends the fields there and loads a new page.

In React 19, action can also hold a function: <form action={save}>.

When the user clicks the submit button, React stops the browser from sending the form, reads every field that has a name, and calls save with that form data. The page does not reload (Lesson 41).

That sounds like a gift. Now watch what it does when the server says no.

So what does the reset put back? The default value of each field.

KEY DEFINITION

The default value of a field. NEW Every <input> field holds two texts. The first is the text it shows right now, the one the user types. The second is its default value, the text it started with.

In plain HTML you set the default value with the value attribute: <input value="John">. In React you set it with the defaultValue prop: <input defaultValue="John" /> (Lesson 20). The user can type over it freely.

A reset throws away what the user typed and puts the default value back. A field with no default value goes back to empty (Lesson 45).

Our two fields have no default value, so the reset empties them.

That gives us the key idea of this lesson. You cannot switch the reset off. But you decide what it goes back to. Make what the user typed the new default value, and the reset puts that text back.

The Rule of Thumb: what is the default value of this field?

Ask one question about every field: what is its default value? After the action, that is what the user sees.

Developers often think React resets the form only when the account was created. It does not. React resets it after every action that does not throw.

Two things are at stake for the user:

  1. After every refusal, the user types the whole form again, including the parts that were right.
  2. On a slow phone, the user may click Create account before the JavaScript of the page has loaded. Whether that click sends anything depends on how the form is built.

There are three ways to keep the text after a refusal:

  1. defaultValue from the state the action returned. This is the React 19 way, for forms built on <form action> and useActionState. The form stays plain HTML, so it can work before JavaScript loads.
  2. A controlled field, with value and onChange (Lesson 20). React does not reset a controlled field at all. It fits a form that must change the page on every keystroke anyway, such as a live hint under the field.
  3. onSubmit with e.preventDefault() (Lessons 11 and 41). React does no reset here, so the text stays after a refusal. After a success, your code asks for the reset itself, with requestFormReset. It fits an older form that a team moves to Actions step by step.

PRINCIPLES

When the action ends without throwing, React resets the form. The reset puts every field back to its default value. Five principles follow:

  1. Principle 1: A Successful Action Empties the Form. React resets every uncontrolled field after the function in <form action> returns. No line of your code does it.
  2. Principle 2: A Returned Error Is a Success for React. The refusal line appears, and the fields empty at the same moment.
  3. Principle 3: defaultValue From State Brings the Text Back. The action returns what the user typed, and the reset puts it back.
  4. Principle 4: requestFormReset Resets a Form Submitted Through onSubmit. React never resets that form by itself, so your code asks for the reset.
  5. Principle 5: name and a Submit Button Let the Browser Send the Form Alone. A form works before its JavaScript loads only when it is real HTML.

Summary: When the function passed to <form action> ends without throwing, React resets every uncontrolled field of that form.

Description: No line of your code empties the fields, and the page does not reload. React calls the function with the form data. When the function returns, React puts every uncontrolled field back to its default value. A controlled field is not reset, because it shows what its state holds.

Something that can be tricky: the word uncontrolled. A plain <input name="username" /> is uncontrolled: the browser keeps its text (Lesson 40). Remember: the action ends without throwing, so React resets the form.

PRINCIPLE2return error: the refusal line appears, and React still resets the form

Principle 2

A Returned Error Is a Success for React

Summary: An action that returns an error message has succeeded for React, so React empties the fields while the error line appears.

Description: React does not read the message an action returns. It only knows whether the action threw. A known error, such as a taken username, is returned as state, as React's docs recommend. So React resets the form, and the user loses every field at the moment the refusal appears. Throwing the error instead does not save the text: it hands the whole form to the nearest Error Boundary.

PRINCIPLE3defaultValue from state: the reset puts back what the user typed

Principle 3

defaultValue From State Brings the Text Back

Summary: To keep the user's text after a refusal, return it in the state of the action and give each field defaultValue from that state.

Description: The reset cannot be stopped, but it only puts each field back to its default value. When the action returns what the user typed and each field reads it through defaultValue, the reset puts that text back. After a success, the action returns empty texts, and the same reset empties the form.

✓ DO THIS
1<input name="email" defaultValue={state.email} />

✗ DO NOT DO THIS
1<input name="email" value={state.email} />
WRONG value without onChange freezes the field, and the user cannot type

React gives no option to switch the reset off for a form with a function in action. But remember what the reset does: it puts each field back to its default value. And you decide the default value.

A field with no default value vs. a field whose default value comes from state
1<input name="email" />

2<input name="email" defaultValue={state.email} />

It is the exact same reset for both fields. Only the default value differs. So the fix has two parts:

  1. The action returns the text the user typed, together with the message.
  2. Each field reads that text through defaultValue.

Then the reset itself puts the user's text back.

PRINCIPLE4requestFormReset(form): a form submitted through onSubmit resets when the action ends

Principle 4

Summary: When a form is submitted without the action prop, call requestFormReset(form) from 'react-dom' inside the Transition, so the fields reset when the action ends.

Description: React resets a form for us only after a function passed to <form action>. A form submitted through onSubmit keeps its old text after a success. requestFormReset asks React for the same reset, and React waits for the Transition. The browser's form.reset() empties the fields at once, before the server has answered.

You know form.reset() from plain JavaScript. React DOM adds a function with the same job, requestFormReset:

Both put every field back to its default value. They differ only in when the fields change:

  • With form.reset(), the browser resets the fields at once, even while the action still waits for the server.
  • With requestFormReset(form), React waits for the Transition the call was made in. So the fields change in the same update as the new state.

This is the reset React already does for us after a function in <form action>. You ask for it by hand only when the form is submitted another way.

React never resets a form submitted through onSubmit

Some forms do not pass the action to <form action>. A team moving an older form to Actions often keeps its onSubmit handler (Lessons 11 and 41), and calls formAction from it.

React's docs say formAction must then be called inside a Transition. So the handler wraps the call in startTransition, which comes from 'react'. A later lesson covers Transitions in full (Lesson 67). For now, one fact is enough: React knows when the Transition ends, and that is when signUp has finished.

form.reset() empties the fields too early

form.reset() is the method developers already know, so it is tempting to call it right after starting the action. But the browser runs it at once.

The fields empty the moment the user clicks, a full second before the server answers. If the answer is Username john is taken., the user has already watched the form clear, as if the account was created. One second later, the refusal appears, and the fields fill again with the default values from the new state.

React's docs do call reset() at once in one example: a chat that shows each new message right away with useOptimistic. There, the user always wants the field empty right after sending, whatever the server answers. A sign-up form is the opposite case: the user wants the text kept until the server says yes.

PRINCIPLE5name and type="submit": the browser can send the form before JavaScript loads

Principle 5

name and a Submit Button Let the Browser Send the Form Alone

Summary: A form works before its JavaScript loads only when it is a real <form> with a name on every field and a real submit button, and its action is one the browser can send by itself.

Description: Progressive enhancement gives every user a basic version that works, and adds the richer version of React when the JavaScript runs. The browser can send a form alone only from HTML: the <form>, the named fields, the submit button, and a URL or a Server Function in action. A function from our own code needs React running, and a click on a <div> needs a handler that has not loaded yet.

Picture the same Create account form on a phone with a slow connection. The page has appeared, but the JavaScript of the app is still downloading. React's docs call this file the JavaScript bundle. The user clicks Create account.

Does that click send anything? It depends on what the action of the form holds.

Aaction="/signup"vsBaction={formAction}The browser understands a URL, only React can call a function

The two forms look the same on the screen. But the browser understands a URL without any JavaScript. It reads every field that has a name, and sends the values to /signup with the POST method.

A function is different. It exists only inside our JavaScript. Until React runs, nobody can call it.

KEY DEFINITION

Progressive enhancement. NEW A page built with progressive enhancement starts from a basic version that works with plain HTML, and adds the richer version when the browser can run more. MDN describes it as giving a baseline of essential content and functionality to as many users as possible, then adding the richer version for browsers that can run it.

For a form, the basic version is HTML the browser can send by itself. The richer version is what React adds: the refusal line without a reload, the reset, and the rest of our JavaScript (Lesson 45).

A form needs four parts so the browser can send it alone:

  1. A real <form> element.
  2. A name on every field. The browser sends only fields that have a name, and the name becomes the key in the form data.
  3. A real submit button, a <button type="submit">. A click on it submits the form with no handler at all.
  4. An action the browser can send without JavaScript: a URL, or a Server Function in a framework that renders the page on the server.

Our form already has the first three parts, and they cost nothing extra. The name that formData.get('username') reads is the same name the browser would send (Lesson 40).

What our Vite app shows before its JavaScript runs

Our Vite app shows the user nothing at all before its JavaScript runs. It is not a broken form. It is an empty page. Here is why, in order:

  1. The browser receives index.html, which holds only an empty root div (Lesson 7).
  2. main.jsx has not run yet, so React has not rendered App.
  3. There is no form on the page to click.

The mistake that breaks it

The classic mistake is building the button or the fields in a way only JavaScript understands:

  1. A developer builds the Create account button as a <div onClick>, because a click handler does the job.
  2. Another field has no name, because the React code reads its value from state.
  3. Everything works while the JavaScript runs.
  4. Later, the team renders the page on the server, so it appears fast on slow phones.
  5. A user clicks before the bundle loads. A <div> is not a submit button, so the browser sends nothing. And a field without a name is never part of the form data.

Interview PrepFor the Interview

The Interview Question: How do React 19 form actions manage automatic form resets, manual requestFormReset, and progressive enhancement?

How to Answer Clearly in 30 Seconds

"When a function is passed to <form action>, React calls it with the form data. After it succeeds, React resets every uncontrolled field of the form. Succeeds means it did not throw, so a returned validation error also clears the fields. Three points follow:

  1. Keeping the text after a refusal: the reset puts each field back to its default value. So the action returns the submitted values in the useActionState state, and each field reads them through defaultValue.
  2. requestFormReset: when a form is submitted without the action prop, for example through onSubmit, I call requestFormReset(form) from react-dom inside a Transition. It gives the same reset, when the action ends.
  3. Progressive enhancement: a basic version that works for everyone, made richer when JavaScript runs. A form needs a real <form>, a name on every field, and a real submit button. Its action must be one the browser can send without JavaScript, such as a URL or a Server Function in a server-rendered page."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Our sign-up form clears the email after the server says the username is taken. Why, and how do you fix it?"
    React resets a form after every action that does not throw, and a returned error message is a normal return value. The reset puts each field back to its default value. So the action returns the submitted values together with the message, and each field gets defaultValue from that state. After a refusal, the reset puts the text back. After a success, the action returns empty values, and the same reset empties the form. Writing value instead freezes the field.
  2. "What is the difference between form.reset() and requestFormReset(form)?"
    Both put every field back to its default value. form.reset() is the browser's method and runs at once, so the fields empty before the server has answered. requestFormReset comes from React DOM and is called inside a Transition, so the reset happens when the action ends, together with the new state. React does this same reset for us after a function in <form action>, so we call it by hand only for a form submitted another way.
  3. "Does a form with a function in action work before JavaScript loads?"
    Not by itself. A function from our own code exists only after React runs. And a Vite app that renders only in the browser has no form on the page at all before main.jsx runs. The browser sends a form with a URL in action by itself. In a framework that renders the page on the server, a Server Function in action makes the form progressively enhanced. The user can submit it before the bundle loads, and useActionState can replay that submit once React takes over.
