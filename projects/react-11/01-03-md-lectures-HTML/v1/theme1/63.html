What the React Compiler Writes into Your Components, and How to Turn It On Safely

Interview Question❱❱ MORE

What does the React Compiler do, and when should you adopt it?

How do the rows of a list stop rendering on every keystroke when nobody writes memo or useCallback?

Overview · Two Ways Side by SideAThe File We WritevsBThe Code the Browser RunsThe same ChatRoom.jsx, only the compiled version keeps a cache

Every letter the user types into a chat renders the chat room again, and every message row with it, even though no message changed. The React Compiler rewrites each of your components while Vite builds the app, and adds a cache that hands back the same JSX as long as nothing it depends on has changed. The reason: memo and useCallback written by hand are easy to get wrong, and the compiler does the same job on plain code, as long as that code follows the Rules of React.

You already use a compiler every day, and you probably never think about it. The browser cannot read JSX. When you write <div>Hello World</div> in a .jsx file, Vite turns it into a plain JavaScript function call before the browser ever sees it:

What we write in MyApp.jsx
1export default function MyApp() {
2 return <div>Hello World</div>;
JSX: the browser cannot read this line
3}
What Vite sends to the browser
1import { jsx as _jsx } from "react/jsx-runtime";
2export default function MyApp() {
3 return _jsx("div", { children: "Hello World" });
Plain JavaScript: a call to a function that React provides
4}

So the file in your editor and the code the browser runs are already two different things. The React Compiler adds one more step to that same build. It reads each component and each Hook, and it writes a new version of it that remembers the JSX it returned last time. When nothing that JSX depends on has changed, the new version hands back the same JSX instead of creating it again.

Remember what Lessons 55 to 57 did by hand: memo on the row, useCallback on the handler, and a dependency list to keep right. The compiler writes the same kind of memoization into the component for you. React's docs call it "the equivalent of manual memoization".

Keep one sentence in mind for the whole lesson: the file you write and the code the browser runs are two different things. The compiler changes only the second one.

Three Words for This Lesson

KEY DEFINITION

What is a compiler? NEW A compiler is a program that reads the code we write and writes new code from it. Vite already compiles every JSX tag into a plain function call. The React Compiler is a second compiler in the same build: it reads our components and Hooks, and writes a version of each one that keeps a cache and reuses JSX and values whose inputs did not change. It comes in the package babel-plugin-react-compiler (Lesson 63).

KEY DEFINITION

What is build time? NEW Build time is the moment Vite prepares our files for the browser, before any of our code runs in the browser. What happens at build time, such as JSX turning into function calls, never shows up in the Console or the Elements panel. React's docs call the compiler "a new build-time tool that automatically optimizes your React app" (Lesson 63).

KEY DEFINITION

What is memoization? REVIEW Memoization means keeping a result and handing it back while its inputs stay the same, instead of producing it again. memo skips a component whose props did not change, useMemo keeps a calculated value, and useCallback keeps the same function between renders (Lessons 55 to 57).

What Is at Stake

Two things are at stake: how fast the letters appear in the message field, and how much code we must keep right by hand.

  1. Speed. In a chat with a long history, each keystroke renders every message row again. When the rows are many or slow, the letters appear late in the field.
  2. Code kept right by hand. Lessons 55 to 57 fixed it with memo, useCallback, and a dependency list, and one arrow function on the tag broke it again. React's docs say that manual memoization "is tedious, easy to get wrong, and adds extra code to maintain."
  3. The gain. With the compiler on, the same rows skip the keystrokes, and the code stays plain.
  4. The condition. The compiler relies on our components following the Rules of React. A component that breaks them can show old information once its output is reused, such as a "min ago" label under a message that stops changing.

Developers usually go wrong in five places:

  1. They think the compiler is a library or a Hook that runs in the browser. It runs when the app is built.
  2. They think that once the compiler is on, they should delete every memo, useMemo, and useCallback in the app. React's docs advise leaving existing memoization in place, or testing carefully before removing it.
  3. They think the compiler fixes code that breaks the Rules of React. It skips the code it sees breaking them, and it can still compile code that breaks them in ways it cannot see.
  4. They think the compiler makes the first load of the page faster. React's docs say its memoization is mainly for update performance: rendering again the components that are already on the page.
  5. They turn it on for a large existing app in one step, with no lint and no tests.

PRINCIPLES

The file you write and the code the browser runs are two different things. The React Compiler writes the second one at build time, with a cache that reuses JSX and values whose inputs did not change, and it can do this safely only for code that follows the Rules of React. Four principles follow:

  1. Principle 1: reactCompilerPreset Adds a Cache to Each Component at Build Time. We turn the compiler on in vite.config.js and call nothing in our components. The browser runs a version of each component that stores its JSX and reuses it while its inputs stay the same.
  2. Principle 2: A Plain ChatRoom Keeps the Rows Still Without memo or useCallback. With the compiler on, plain files keep the rows still while the user types. The memo, useMemo, and useCallback already in an app stay in place until tests show they can go.
  3. Principle 3: Date.now() in Message Freezes the "min ago" Label. When the compiler sees a break of the Rules of React, it leaves that component as written. When it cannot see the break, reused output can show old information.
  4. Principle 4: "use memo" Lets a Team Compile One Component at a Time. A new app turns the compiler on from the first day. An existing app runs the lint first, then compiles one component, one folder, or one group of users at a time, and pins the compiler to an exact version.

A Cache in Plain JavaScript

How do you skip repeated work in plain JavaScript? You store the result in a variable. Next time, you check the variable first, and you build the result only if nothing is stored yet:

Plain JavaScript: build the result once, then hand back the stored one
1let cached;
2
3function getGreeting() {
4 if (cached === undefined) {
Nothing stored yet: build it now
5 cached = buildGreeting();
6 }
7 return cached;
Every later call: the stored result
8}

That variable is a cache, and that if is the check. The compiler writes this same pattern into every component, around every piece of JSX.

It is the plain JavaScript cache from above, with different names. Here it is in the order it runs:

  1. The first line calls _c and gets back $, the cache that belongs to this component on the page. $ is an array with one place, $[0].
  2. On the first render, $[0] still holds a special value made with Symbol.for. Read from the code, that value means "nothing stored yet", the same job undefined did in our plain cache. So the if is true: the code creates the <div> and stores it in $[0].
  3. On every later render, $[0] holds the stored <div>. The if is false, so the code creates nothing and returns the same <div> as last time.

It may look the same, but it is NOT the same thing! The page shows Hello World either way. The function we wrote creates a new <div> on every render. The function the browser runs creates it once, and after that it hands React the stored one. React's docs call that if a cache check: before the compiled code creates a piece of JSX, it asks the cache whether it already holds one with the same inputs.

Three names in the build output appear nowhere in our file. The compiler wrote all three:

  1. _c is the function c, imported from react/compiler-runtime. React 19 provides it, just as it provides jsx from react/jsx-runtime. The compiler adds that import line at the top of every file it compiles.
  2. $ is the cache that _c returns. Each compiled component on the page gets its own.
  3. t0 is a variable the compiler creates to hold the JSX. Our code never names it.

So nothing in our code calls the compiler. There is no Hook to call and no import to add. The compiler writes the one new import by itself. That is why a developer who does not know the compiler is on cannot explain why a component skips a render: the reason is not in the source.

Mistake: The Compiler Turned On in a React 18 App

The import of react/compiler-runtime trips up teams that are still on React 18:

  1. A team on React 18 installs babel-plugin-react-compiler and keeps the compiler's default target, which is '19'. The target option tells the compiler which version of React the app uses.
  2. The compiled files import react/compiler-runtime, which React 18 does not have.
  3. The app does not load. Vite shows an error that "./compiler-runtime" is not exported from the react package.

The fix has two parts. First, install react-compiler-runtime as a normal dependency, not a devDependency, because the browser needs it while the app runs:

Terminal
1npm install react-compiler-runtime@latest

Then set target to the version of React the app uses:

vite.config.js
1babel({
2 presets: [reactCompilerPreset({ target: '18' })],
Compiled files import from react-compiler-runtime
3}),

Remember: the file you write and the code the browser runs are two different things. With the compiler on, the code the browser runs imports something your files never import.

Why Plain Rows Skip a Keystroke

Here is the arrow function that broke memo in Lesson 57, now on a plain Message with no memo at all:

A plain row, and a new arrow function on its tag
1export default function Message({ text, onDelete }) {
2 return <li>{text} <button onClick={onDelete}>Delete</button></li>;
3}
4
5<Message key={m.id} text={m.text} onDelete={() => handleDelete(m.id)} />
A new function on every render of ChatRoom

Many developers expect that without memo and useCallback, every row renders again on every keystroke. Without the compiler, it does. With the compiler, it does not, as the opening of this lesson showed.

The rows stay still because the compiled ChatRoom hands React the same three <Message> elements as last time. Here is what happens after one keystroke:

  1. The user types O in the message field. The setter changes text, so React renders the chat room again. The Console prints ChatRoom rendered.
  2. The compiled ChatRoom reaches the list. The compiler wrote a cache check around it, and the check asks one question: is messages the same array as on the last render? It is, because typing changes only text.
  3. So the compiled ChatRoom returns the three <Message> elements it stored last time, with the same arrow functions inside them.
  4. React finds the very same elements in the same places, and skips the three rows. No Message rendered: line appears.

No line of our code stores those elements. The compiler wrote the cache check around the map at build time, the same way React's docs show it wrapping a child tag in a cache check. The arrow function on the tag no longer matters, because the whole element is reused, arrow function and all. React's docs say it of the same case: "React Compiler is able to optimize this correctly with or without the arrow function".

The Memo Badge: Which Components Were Compiled

The source looks the same whether a component was compiled or not. So how do you check? When the app runs in development, React Developer Tools shows a badge next to each component the compiler optimized. It reads Memo, followed by a sparkle sign, and we call it the Memo badge.

With the plain files, both ChatRoom and Message show it, even though the code has no memo call. React Developer Tools adds the badge, and Lesson 64 covers the tool in full. Check the badge instead of guessing from the source.

What the Compiler Speeds Up

React's docs say the compiler's memoization is mainly about update performance: rendering again the components that are already on the page, such as our rows after a keystroke. It does not mainly speed up the first load of the page. It covers two cases:

  1. It skips rendering child components whose inputs did not change, as with our rows.
  2. It skips expensive calculations inside a component or Hook, the job of useMemo (Lesson 56).

It has two limits:

  1. It memoizes only components and Hooks, not every function in the app.
  2. Its memoization is not shared between components. Each component keeps its own cache, so a heavy function called in ten components still runs once in each of them.

The memo, useMemo, and useCallback Already in the Code

The compiler works with the memoization it finds:

  1. It leaves memo in place.
  2. It replaces each useMemo and useCallback with a cache check of its own.
  3. When its own cache cannot keep a value as stable as the hand-written one, it skips the component.

For new code, React's docs say: rely on the compiler, and use useMemo or useCallback only where you need precise control over which values are memoized. The docs call these two Hooks an escape hatch: a way out of the automatic behavior, for the few places that need it. The common case is a value used as an Effect dependency (Lesson 37), which must stay the same object between renders.

For existing code, the docs advise one of two things:

  1. Leave the existing memoization in place, because removing it can change what the compiler writes.
  2. Or test carefully before removing it.

For memo itself, the docs say you can safely remove it from components when the compiler is on.

Mistake: Every useMemo Deleted on the First Day

Here is what goes wrong when a team removes everything at once:

  1. A team turns on the compiler in an app that already uses useMemo and useCallback.
  2. The same day, they delete every useMemo and useCallback, because "the compiler does it now".
  3. One of the deleted useMemo calls produced an object that sat in an Effect's dependency list.
  4. The compiler now memoizes that object in its own way, so the Effect starts to run at other moments than before. React's docs name the symptoms: Effects that fire too often, infinite loops, or missing updates.

Nobody changed the Effect, so nobody looks at it. The fix is the docs' advice: leave existing memoization in place, or remove it one piece at a time, with tests.

What the Compiler Trusts: the Rules of React

Think about the cache check again. It hands back the stored JSX when the inputs are the same. That is safe only if the same inputs always give the same JSX. If a component can give different JSX for the same props and state, the stored JSX can be wrong.

React's docs collect what every component must follow under one name, the Rules of React:

  1. Components and Hooks must be pure. The same props and state give the same JSX, and side effects run outside render (Lesson 14). Props and state are never changed in place (Lessons 17 and 19).
  2. React calls components and Hooks. We write <Message /> and let React call it. We never call Message() ourselves (Lesson 04).
  3. The Rules of Hooks. Hooks are called at the top level, never inside a condition or a loop (Lesson 38).

When the compiler finds code that might break these rules, React's docs say it "safely skips optimization": it leaves that component or Hook exactly as written, and keeps compiling the rest of the app. The page shows no error.

A Compiler Error vs. a Runtime Issue

React's docs name two kinds of trouble with the compiler, and they are not equally likely:

  1. A compiler error stops the build. It is rare. With the default settings, the compiler skips a component it cannot handle, and the build goes on.
  2. A runtime issue is compiled code that behaves differently from the code we wrote. It usually comes from a break of the Rules of React that the compiler could not see, so it compiled a component it should have skipped. Code that relies on memoization to work correctly can break the same way.

Mistake: A Form Library That Changes Values in Place

Some libraries break the rules in a way the compiler cannot always see:

  1. A form component reads a field with watch('name') from the react-hook-form library.
  2. The value lives inside an object that stays the same object while its contents change. React's docs call this interior mutability: from the outside, it is the same object, so a cache check sees nothing new.
  3. The incompatible-library lint rule knows this library, so the compiler skips the component, and the component keeps working.
  4. For some libraries, such as MobX with its observer, the docs say "the linter does not yet detect them". The compiler can compile such a component.
  5. The reused output does not follow the hidden change. React's docs show a useMemo over watch where the value "will never update" and the screen appears frozen. They add: "If something breaks with manual useMemo, it will also break the compiler's automatic optimization."

The docs' fix is the library's own API that follows the rules, such as useWatch, or "use no memo" on that component while the team fixes it.

Remember: the code the browser runs reuses JSX because it trusts your component. Keep render pure, and that trust is safe.

Mistake: A Directive the Compiler Ignores

A directive is easy to write in a way the compiler ignores:

  1. It is not the first line. A developer writes const data = getData(); and then "use no memo"; on the next line. The compiler still compiles the component, because a directive must be at the very beginning of the function body. React's docs label this example "Too late!".
  2. It uses backticks. A directive must use double or single quotes, not backticks.
  3. The new component has none. In 'annotation' mode, a new component without "use memo" is not compiled. The docs remind us to add it to new components.

In 'infer' mode, a Hook named without the use prefix, or a function that neither creates JSX nor calls Hooks, is not compiled. The docs advise fixing the name rather than forcing compilation with "use memo".

New Apps and Existing Apps

For a new app, the answer is simple: start with the compiler on. create-vite and create-next-app offer templates with the compiler turned on, and Expo turns it on by default from SDK 54.

For an existing app, go step by step:

  1. Install eslint-plugin-react-hooks with the recommended preset. It needs no compiler, so the team can fix what it reports at its own pace.
  2. Compile one part: one folder, one component with "use memo", or one group of users with gating.
  3. Check the Memo badges in React Developer Tools, run the tests, and measure the screens that felt slow.
  4. Widen the part, one step at a time, until the whole app is compiled.

React's docs say that how fast a team can roll it out depends on how well the code has followed the Rules of React.

Mistake: A Version Range on the Compiler

The last trap needs no change to the app's code at all. In package.json, a version such as ^1.0.0 is a version range: the caret lets npm install newer 1.x versions by itself. Here is how that goes wrong:

  1. A team installs the compiler with the range ^1.0.0, in an app with few tests.
  2. Later, npm installs a newer compiler version by itself, and that version memoizes some values differently.
  3. An Effect somewhere depended on one of those values, and it now fires more or less often.
  4. Nobody changed the app's code, so nobody looks at the compiler.

React's docs advise pinning the compiler to an exact version when tests are few, such as 1.0.0 instead of ^1.0.0, and upgrading it by hand. The --save-exact flag saves the exact version:

Terminal
1npm install --save-dev --save-exact babel-plugin-react-compiler@latest

Remember: the code the browser runs comes from the compiler. A new compiler version writes new code, even when your files stay the same.

Interview PrepFor the Interview

The Interview Question: What does the React Compiler do, and when should you adopt it?

How to Answer Clearly in 30 Seconds

"The React Compiler is a build-time tool. When the app is built, it reads every component and Hook and writes a new version that keeps a cache and reuses JSX and values whose inputs did not change. That gives the effect of memo, useMemo, and useCallback without writing them, and an arrow function on a tag no longer breaks it. It relies on the Rules of React: pure render, props and state never changed in place, Hooks at the top level. When it sees a break, it skips that component. When it cannot see one, reused output can show old information. So:

  1. New apps should start with it on.
  2. Existing apps run eslint-plugin-react-hooks first, then compile one folder, one component with "use memo", or one group of users, and widen step by step.
  3. Existing memoization stays in place unless tests show it can go, and the compiler version is pinned when tests are few."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Once the compiler is on, can we delete all our useMemo and useCallback calls?"
    Not all at once. For new code, React's docs say to rely on the compiler and use useMemo or useCallback only where precise control is needed, such as a value used as an Effect dependency. For existing code, they advise leaving the memoization in place, because removing it can change what the compiler writes, or testing carefully before removing it. The compiler replaces those calls with cache checks of its own, and it compiles a component only if its own memoization matches or exceeds the existing one. memo on a component can be removed safely.
  2. "What happens when a component breaks the Rules of React?"
    It depends on whether the compiler can see the break. When it sees one, such as a Hook called inside a condition, it skips that component, leaves it exactly as written, and keeps compiling the rest of the app. eslint-plugin-react-hooks shows the same finding in the editor, and the component has no Memo badge in React Developer Tools.

When it cannot see the break, it compiles the component, and the reused output can stop updating. Date.now() during render is such a break: only the lint reports it. A library value that changes inside the same object is another. Adding "use no memo" to the component is the quick test: if the bug disappears, the cause is likely a rule break.

  1. "Does the compiler make the app faster on the first load?"
    That is not its main goal. React's docs say its memoization is mainly about update performance: skipping the rendering of components whose inputs did not change, and skipping expensive calculations inside components and Hooks. It memoizes only components and Hooks, and the cache is not shared between them.

At the Meta Quest Store, React's team reports that some interactions became more than two and a half times faster, while initial loads and page changes improved by up to 12 percent, with memory use unchanged. It can also memoize after an early return, which useMemo cannot, because a Hook cannot be called after a return (Lesson 38).
