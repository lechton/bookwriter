React's Built-in Components vs. Raw HTML

Interview Question❱❱❱ ADVANCED

How do React's built-in HTML components differ from raw HTML?

If a tag in JSX looks like HTML, why does React ask for className, a style object, and one string inside a title?

Overview · Two Ways Side by SideARaw HTMLvsBA Built-in Component in JSXThe tag looks the same, but React reads it, not the browser

In an HTML file, the browser reads your tags and builds the page from them. In React, the browser never reads the tags you write in JSX: React reads them, and React creates every DOM node itself. That is why each name on a tag is the name the DOM uses in JavaScript, such as className, and why React can move a <title> into the document head.

Remember document.createElement? In plain JavaScript, you create the element yourself, and then you set its features one by one:

Plain JavaScript: you create the input and set its class
1const input = document.createElement('input');
Your code creates the DOM node
2input.className = 'search';
The DOM calls the class className, not class

In React, you never call createElement yourself. You write a tag in JSX, and React creates the DOM node for you:

React: you write the tag, and React creates the input
1<input className="search" />
React creates the input and sets its className

Look at the name on the tag. It is not HTML's class. It is className, the exact name you typed on the DOM node in plain JavaScript. And the result is the same: open the Elements panel, and both versions show <input class="search">.

So here is the one idea of this lesson: a tag in JSX is not HTML. It is a description that React turns into a DOM node, so it speaks the language of the DOM.

KEY DEFINITION

What is a built-in browser component? NEW React's docs call every tag of the browser, such as <div>, <input>, <li>, or <title>, a built-in browser component. It starts with a lowercase letter, while your own components start with a capital letter, such as <Inbox>. React supports every built-in HTML and SVG tag, and it creates the real DOM node from each one (Lesson 83).

Three Ways to Put a Count in the Browser Tab

A mail app shows its unread count in the browser tab, such as Inbox (2). The count lives in the state of a component. But the text of the tab lives in a <title> tag, inside the document head, far away from the root <div> where React renders your app.

Developers choose between three ways to bring the count to the tab:

  1. Render a <title> from the component. This is new in React 19, and this lesson uses it.
  2. Set document.title inside an Effect. This was the way before React 19 (Lesson 32).
  3. Use a metadata library such as react-helmet. A library still helps when every route of an app must replace the title and the other metadata (Lesson 121).

The Rule of Thumb: type the DOM's name, and let React place the head tags

On a tag in JSX, type the name the DOM uses in plain JavaScript, such as className instead of class. Give style an object, not a string. Render a <title> from the component that knows the data, and give it one string.

Here is what the user sees when a developer treats these tags as HTML:

  1. A row with a string of CSS in style, pasted from an HTML page, is not bold. The whole page goes blank.
  2. A title written as text and a value in curly braces side by side does not show the count in the tab.
  3. Two components on the same screen that each render a <title> give undefined behavior in browsers and search engines.

Developers usually go wrong by treating JSX as HTML with a few spelling changes. They paste HTML from a mockup and expect every HTML habit to work. And they never expect a tag to leave the place where they wrote it.

PRINCIPLES

Every tag in the inbox is a description that React turns into a DOM node. Five principles follow from that one fact:

  1. Principle 1: className and htmlFor Are the DOM's Names. On a built-in tag, a prop takes the name the DOM uses in JavaScript. Only aria-* and data-* keep their dashes.
  2. Principle 2: style Takes an Object. It works like the DOM's style property, with camelCase names. A string of CSS pasted from HTML blanks the whole page.
  3. Principle 3: React Places a title in the Head. In React 19, a <title> rendered from any component lands in the document head. Render only one at a time.
  4. Principle 4: A title Takes One String. Text and a value in curly braces side by side make several children. Build the text with a template literal instead.
  5. Principle 5: precedence Gives One Stylesheet Link for Every Row. With precedence, React puts one copy in the head and waits for it to load. Without it, nothing special happens.

KEY DEFINITION

What is a DOM property? NEW A DOM property is the name the browser gives to a feature of a DOM node when your JavaScript reads or changes it, such as input.className or label.htmlFor. It is often the same as the HTML attribute, such as id, but not always: HTML's class is the DOM's className (Lesson 83).

So the rule is simple. On a tag in JSX, type what you would type on the DOM node in plain JavaScript. React's docs give two reasons for this choice.

The first reason: JSX turns into JavaScript (Lesson 02). Every attribute on the tag becomes a key of a JavaScript object:

What the JSX compiler makes of the input tag
1<input id="search" className="search" />
Becomes _jsx('input', { id: 'search', className: 'search' })

Your own components often read those keys into variables. A JavaScript variable name cannot contain a dash, and it cannot be a reserved word such as class. A component that tried to read a prop named class would not even run:

Why class cannot be a variable name
1function SearchField({ class }) {
WRONG class is a reserved word, so JavaScript reports a syntax error and the file never runs
2 return <input className={class} />;
3}

The second reason: consistency. The names cannot all match HTML anyway, so React uses the DOM's names everywhere. That is why for becomes htmlFor. And a name made of several words is written in camelCase, such as tabIndex.

PRINCIPLE2style={{ fontWeight: 'bold' }}: style takes an object, like the DOM's style property

Principle 2

Style Object: style Takes an Object with camelCase Names

Summary: Pass style an object with camelCase CSS names, such as { fontWeight: 'bold' }, and use it for styles that depend on data.

Description: React's style works like the DOM's style property, so it takes an object, not a string of CSS. A number gets px, unless the property is unitless. A string of CSS pasted from HTML makes React stop with an error, and the whole page disappears. For styles that never change, a CSS class with className works better.

An unread email must be bold. Here is a bold row in HTML, and then in JSX:

A bold row in HTML, and the same row in JSX
1<li style="font-weight: bold">Your order has shipped</li>
HTML: a string of CSS
2<li style={{ fontWeight: 'bold' }}>Your order has shipped</li>
JSX: an object with a camelCase name

Both lines ask for the same CSS rule. But they are not the same thing. In HTML, style holds a string of CSS. In JSX, style holds a JavaScript object, and a string does not work there.

Why an object? Once again, React follows the DOM. In plain JavaScript, the DOM's style property is an object, and its CSS names are in camelCase:

Plain JavaScript: the DOM's style property is an object
1const row = document.querySelector('li');
2row.style.fontWeight = 'bold';
The DOM writes font-weight as fontWeight

So the style you pass in JSX follows the same two rules as the DOM's style property:

  1. The names are in camelCase. font-weight becomes fontWeight. And background-color becomes backgroundColor.
  2. The values are strings or numbers. When you pass a number, React adds px, so margin: 20 means 20 pixels.
KEY DEFINITION

What is a unitless property? NEW A unitless property is a CSS property where pixels make no sense, such as opacity. React leaves a number alone there, so opacity: 0.5 stays 0.5 and does not become 0.5px (Lesson 83).

The double curly braces are nothing new (Lesson 03). The outer pair steps into JavaScript. The inner pair is an ordinary object.

Here is what happens:

  1. React renders Inbox, which returns the title and the heading inside the same <div>.
  2. React places the <h1> inside that div, inside the root <div>.
  3. React sees a <title>, and places its DOM node in the document <head> instead.
  4. The browser reads the <title> in the head, and the tab shows Inbox.

Why? React's docs say that the <head> is the only valid place for a <title> in the DOM. So React puts it there for you, wherever the component writes it.

KEY DEFINITION

What does it mean that React hoists a tag? NEW To hoist means to lift, the way a crane lifts a load from the ground to the top floor. The React 19 announcement uses this word for a <title>, <meta>, or <link> that a component renders deep in the tree: React lifts its DOM node out of the component's place and puts it in the document head (Lesson 83).

Which Tags React Moves to the Head

The <title> belongs to the third group, the resource and metadata components. This group has five tags: title, meta, link, script, and style. They describe the whole document, not one part of the screen. React's docs say you can render a <title> from any component, and React will always place its DOM node in the head.

This is the point of the feature: the component that knows the data owns the tag. Only Inbox knows how many emails are unread, so Inbox renders the title.

A <meta> tag works the same way: React places it in the head too. It must have exactly one of four props, such as name or charset. The other two are httpEquiv and itemProp. Lesson 121 covers the metadata for each page of a site.

React leaves a tag where it is written in two cases:

  1. A <title> inside an <svg>. There it is a label for the graphic, which screen readers read.
  2. A tag with an itemProp prop. There it describes one part of the page, not the whole document.

Keep One Title at a Time

React's docs warn: render only one <title> at a time. Suppose a settings panel on the same screen also renders a <title>. React places both in the head. Then, in the words of React's docs, "the behavior of browsers and search engines is undefined".

The same holds for the <title> that index.html already has. A new Vite project starts with one in its head. Once Inbox renders its own title, delete the one in index.html, so the head holds only one.

PRINCIPLE4<title> children: one string, built with a template literal, or the tab loses its count

Principle 4

One String: A <title> Takes Exactly One String as Its Child

Summary: Give <title> one string as its only child, and build it with a template literal.

Description: Text and a value in curly braces between two tags become separate children, so Inbox ({unreadCount}) gives an array of three. An <h1> shows that array as one text, but a <title> must receive one string, so the tab does not get the count. A template literal builds the whole text first, so the title receives one string.

✓ DO THIS
1<title>{`Inbox (${unreadCount})`}</title>
One string: the tab reads Inbox (2)
✗ DO NOT DO THIS
1<title>Inbox ({unreadCount})</title>
WRONG three children, so the tab does not show the count

The tab must read Inbox (2). The natural way is to write the count in curly braces between the text, as in any other tag:

The same text and count in an h1 and in a title
1<h1>Inbox ({unreadCount})</h1>
Shows Inbox (2) on the page
2<title>Inbox ({unreadCount})</title>
WRONG the title does not get one string

Both tags hold the same text and the same curly braces. But only one works. The <h1> shows Inbox (2) on the page without a problem. The <title> does not show the count in the tab, and React's docs say plainly that this shape causes an error.

The reason is a rule from React's docs: the children of a <title> must be one single string of text. An <h1> accepts any number of children. A <title> accepts one.

Why the Text Between the Tags Is Not One String

To your eyes, Inbox ({unreadCount}) is one piece of text. To JSX, it is three pieces:

  1. The text Inbox ( before the curly braces.
  2. The value of unreadCount, which is 2.
  3. The text ) after the curly braces.

Each piece becomes its own child, and several children arrive as an array in props.children (Lesson 09). So the <title> receives an array of three pieces: two strings, with the number 2 between them.

The <h1> puts the three pieces side by side on the page, so they look like one text. A <title> cannot do that. It must receive one string, and an array is not a string.

Principle 5

Stylesheet Links: precedence Puts One Copy of the Link in the Head for Every Row

Summary: Write precedence on a stylesheet <link> rendered from a component, so React places one copy in the head, ranks it, and waits for it to load.

Description: With precedence, React de-duplicates the links by href, so three rows give one <link> in the head, and it waits for the stylesheet before it shows the rows. Without precedence, the link is an ordinary tag: each row keeps its own copy, and React neither ranks it nor waits for it. The props onLoad, onError, and disabled turn the special treatment off.

✓ DO THIS

✗ DO NOT DO THIS

Each email row needs a thin border below it. That rule lives in a stylesheet, email-row.css, in the public folder. React's docs leave it to you how a CSS file reaches the page. Developers choose between two ways:

  1. Import the CSS file in JavaScript. The build tool, here Vite, puts it in the page. This is the usual way in a Vite app.
  2. Render a <link> inside the component that needs the stylesheet. This is new in React 19. It keeps each stylesheet next to the component that depends on it, so a reader of EmailRow sees its styles right there.

This principle is about the second way: EmailRow renders the <link> itself.

KEY DEFINITION

What is precedence? NEW precedence is a prop on a stylesheet <link> that tells React where to rank it among the other stylesheets in the head. The rank matters, because when two stylesheets set the same rule, the one that comes later in the head wins. The value is a name you choose, such as "default" or "high", and React treats the names it finds first as lower and the names it finds later as higher (Lesson 83).

With precedence, React does three things for the stylesheet:

  1. It places the link in the head, ranked among the other stylesheets.
  2. It keeps one copy. When several components render a link with the same href, React puts a single <link> in the DOM. React's docs call this de-duplication: removing the extra copies of the same thing.
  3. It waits for the stylesheet to load before it shows the component that rendered it. So the user never sees the rows without their border. React waits by suspending the component (Lesson 69).

Without precedence, React's docs say there is no special behavior. The <link> is an ordinary tag, and React leaves it where the component wrote it.

Four More Facts About Managed Links

A few more facts come up in interviews:

  1. React ignores changes to the props of the link after it has been rendered, and the Console says nothing about it.
  2. React may leave the link in the head even after every row that rendered it is gone.
  3. Two more tags get the same treatment. A <style> tag with an href and a precedence is managed like the link. A <script> tag with async and a source address is de-duplicated by that address.
  4. React's preinit starts loading a stylesheet even before its first render. Lesson 84 covers it.

Interview PrepFor the Interview

The Interview Question: How do React's built-in HTML components differ from raw HTML?

How to Answer Clearly in 30 Seconds

"In JSX, a tag like <input> or <title> is not HTML for the browser. It is a description that React reads, and React creates the DOM node. React's docs call these built-in browser components, and they differ from raw HTML in three ways:

  1. Names follow the DOM. JSX attributes become keys of a JavaScript object, and class is a reserved word in JavaScript. So React uses the DOM property names: className, htmlFor, and camelCase such as tabIndex. Only aria-* and data-* keep their dashes.
  2. style takes an object, like the DOM style property, with camelCase names. A number gets px unless the property is unitless.
  3. Some tags gained new powers in React 19. A <title>, <meta>, or <link> rendered from any component lands in the document head. A stylesheet <link> with precedence is de-duplicated, ranked, and waited for. And the form components become controlled when you pass value."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why did React rename class to className at all?"
    Because JSX turns into JavaScript. Every attribute becomes a key of the props object, and components read those keys into variables. JavaScript names cannot contain dashes or be reserved words, and class is a reserved word. So React uses the names the DOM already uses in JavaScript, such as element.className and label.htmlFor. React still writes the usual HTML attribute on the node, so the Elements panel shows class="search". When you paste class into JSX, the Console asks: "Did you mean className?"
  2. "Why does <title>Inbox ({unreadCount})</title> fail in the tab, when the same shape works in an <h1>?"
    Because text and curly braces side by side become separate children. Here they become an array of three: 'Inbox (', the count, and ')'. An <h1> shows the three pieces as one text. A <title> must receive one single string, and React's docs say this array causes an error. The fix is a template literal inside the curly braces, which builds the whole text as one string before it reaches the <title>.
  3. "Several components render the same stylesheet <link>. How many links end up in the DOM?"
    With precedence, one. React de-duplicates the links by href, places that one copy in the head, and ranks it by its precedence. Then it waits for the stylesheet to load before it shows the components that depend on it. Without precedence, React gives the link no special treatment, so each component keeps its own copy where it wrote it. The props onLoad, onError, and disabled also turn the special treatment off.
