How the Search Box Stays Fast While a Slow List Renders

Interview Question❱❱ MORE

How do you keep typing responsive while a big re-render runs with useTransition?

Why does typing stutter when the same text also filters a long list?

Overview · Two Ways Side by SideAOne for the Field and the ListqueryvsBA Second in a TransitionsearchQueryOne freezes the typing, two let every letter in at once

In a search field over a long list, every letter the user types must appear at once, and the results can follow a moment later. useTransition splits one keystroke into two updates: an urgent one for the <input> field, and a Transition for the list. The list renders no faster, but React renders it in the background, so the next letter never waits for it.

Think of the search field on any shop or blog. You type 1, then 2, and the list of results under it gets shorter with every letter. Nobody minds if the results take a moment. Everybody minds if the letters show up late.

Remember Lesson 66? The browser has one main thread. It runs your JavaScript, handles every keystroke, and paints the screen, one thing after the other. While React renders a slow list, the browser can do nothing else.

Now the part that surprises most developers. In a controlled <input> field, the letter on the screen is state. React writes query into the value of the field. So the new letter appears only when React renders again with the new query and commits it.

If the same query also filters a slow list, the letter and the list come in the same render. The letter waits for the list.

The Words This Lesson Stands On

KEY DEFINITION

A controlled <input> field. REVIEW A controlled field shows what your state holds: <input value={query} onChange={e => setQuery(e.target.value)} />. When the user types a letter, React calls onChange, and your code calls setQuery with the new text. The field shows only what query holds, so the new letter reaches the screen when React renders again with the new query and commits it to the DOM (Lesson 20).

KEY DEFINITION

An urgent update and a Transition. REVIEW A normal call to a set function in an event handler, such as setQuery('1'), is an urgent update: React renders it to the end without a break, and nothing can interrupt it. A set function called inside startTransition makes a Transition: React renders it in the background, gives the main thread back to the browser between pieces of its work, and drops that render when an urgent update comes in. Nothing of a Transition reaches the screen before its commit (Lesson 66).

KEY DEFINITION

memo. REVIEW memo is a function from React that wraps a component: const PostList = memo(function PostList({ query }) { ... }). When the parent renders again, React compares each new prop with the old one, using Object.is. If every prop is the same, React skips the component and reuses its last result (Lesson 55).

AqueryvsBsearchQueryThe same text at two speeds

Both state variables get the same text from the same keystroke. When the user stops typing, both hold the same value, such as 12. It looks the same, but it is NOT the same thing!

  • query follows every keystroke at once, because the field must show what the user typed.
  • searchQuery lags behind, and it may even skip a value. When the user types the next letter before the list for 1 is ready, that list never reaches the screen.

The whole recipe of this lesson takes six steps:

  1. We keep two state variables: query for the field, and searchQuery for the list.
  2. On every keystroke, query changes at once, as an urgent update.
  3. searchQuery changes inside a Transition, so React renders the new list in the background.
  4. We wrap the list in memo, so the render for the urgent update can skip the slow list.
  5. When the user types the next letter before the new list is ready, React throws the unfinished list away. It renders the list for the latest text.
  6. A flag named isPending tells us that the list is behind, so we can fade the old list while the new one renders.

Steps 1 to 3 and step 5 are what Lesson 66 did for a tab click, now driven by a keystroke. Steps 4 and 6 are new in this lesson.

What Is at Stake

What is at stake is the field itself. It must answer every keystroke at once. React's docs explain why: "Urgent updates like typing, clicking, or pressing, need immediate response to match our intuitions about how physical objects behave. Otherwise they feel "wrong"."

When the field waits for the list, the letters appear late and in jumps. The user does not know that React is busy. The user sees a field that ignores the keyboard, and stops trusting the page.

Developers make three classic mistakes here:

  1. They wrap the field's own setQuery in startTransition. React's docs say it plainly: "You can't use a Transition for a state variable that controls an input". Principle 2 shows what goes wrong.
  2. They add the second state variable but forget memo on the list. The typing stays slow, and they conclude that useTransition does nothing. Principle 3 shows why.
  3. They think the Transition makes the list render faster. It does not. The list takes exactly as long as before. The Transition only lets the keystroke go first.

The Rule of Thumb: does the user type into it?

Ask one question about the text that drives a slow list: does the user type into it? If yes, keep the state of the <input> field urgent, and give the list its own state variable, set inside startTransition.

Five Ways to Handle Typing over a Slow List

A search field over a slow list is a common job at work. A senior developer picks one of five ways:

  1. Leave it as it is. This fits when the list renders fast enough. React's docs warn: "Don't optimize prematurely!"
  2. Render fewer rows with a virtualized list, as seen in Lesson 62. This fits when the list is long but each row is cheap.
  3. Two state variables and useTransition. This is the way of this lesson. It fits when our own component holds both set functions, and we want isPending. React's docs: "You can declare two separate state variables", one for the field and one "that you will update in a Transition."
  4. One state variable and useDeferredValue. Lesson 68 teaches it, and it is also the way when the text comes from a prop. React's docs: "Alternatively, you can have one state variable, and add useDeferredValue which will "lag behind" the real value."
  5. Debouncing or throttling. To debounce is to wait until the user stops typing for a moment. To throttle is to update at most once in a set time. React's docs say they "still produce a janky experience because they're blocking: they merely postpone the moment when rendering blocks the keystroke."

PRINCIPLES

The <input> field must answer at once. The list can follow a moment later. Five principles follow:

  1. Principle 1: One query Freezes the Field. When one state variable drives both the field and a slow list, the typed letter waits until React has rendered the whole list.
  2. Principle 2: useTransition Makes Two Updates from One Keystroke. The field's query stays urgent. A second state variable, searchQuery, changes inside startTransition and drives the list.
  3. Principle 3: memo Lets the Urgent Render Skip PostList. The urgent update renders SearchPage again, and with it every child. Only a list wrapped in memo skips that render, because its prop still holds the old text.
  4. Principle 4: A New Keystroke Throws Away the Unfinished List. When the user types 2 before the list for 1 is ready, React drops that list. It renders only the latest text.
  5. Principle 5: isPending Fades the Old List from Outside. isPending is true while the list is behind. We fade the old list on a wrapper <div>, so the props of PostList stay the same.

Why the Letter Waits for the List

The 1 cannot appear before the list for 1 is finished. Filtering 500 short titles is fast. Rendering 176 slow posts is slow: at least 176 milliseconds, because each post waits 1 millisecond. In development, Strict Mode calls each component twice, so it takes about twice that.

Here is what happens when the user types 1 and then 2:

  1. The page shows an empty field and all 500 posts.
  2. The user types 1. setQuery('1') is an urgent update.
  3. React renders SearchPage, then PostList, which renders 176 slow posts. The Console prints PostList rendered: 1.
  4. While React renders, the user types 2. Nothing changes on the page, and the field still looks empty. The browser cannot handle the keystroke, because React keeps the main thread busy, and an urgent render cannot be interrupted.
  5. React commits: the field shows 1, and the list shows 176 posts, at the same moment.
  6. Now the browser handles the 2. setQuery('12') starts another full render, this time of 15 slow posts. Then 12 appears.

The Real Mistake: Blaming the Filter

A developer sees the field freeze over a long list and makes a natural guess:

  1. The developer thinks the filter call is the slow part, and wraps it in useMemo, as seen in Lesson 56.
  2. The typing is still slow. query changes on every keystroke, so useMemo must work out the list again, and the rows must render again.
  3. The slow part was never the filter. It is rendering the rows.

React's docs describe exactly this case: "Sometimes, you can't skip re-rendering because the screen actually needs to update." The list must change. What we can change is when it changes.

Remember: one query for the field and the list means the letter waits for the whole list.

useTransition: the startTransition of Lesson 66, plus isPending

Remember the startTransition of Lesson 66? You imported it from react and wrapped a set function in it. React then rendered that update as a Transition. useTransition is the Hook that gives you the same function, plus one extra value.

KEY DEFINITION

useTransition. NEW useTransition is a Hook from React. React's docs: "useTransition is a React Hook that lets you render a part of the UI in the background." You call it at the top level of a component, with no arguments, like every Hook (Lesson 38). It returns an array with exactly two items, in this order: isPending, a boolean that "tells you whether there is a pending Transition", and startTransition, which marks every state update made while its function runs as a Transition (Lesson 67).

We name isPending here, and we use it in Principle 5.

The startTransition from the Hook does the same job as the one we imported from react in Lesson 66. React's docs say the imported one "is very similar to useTransition, except that it does not provide the isPending flag." So the difference that matters is isPending, and only the Hook gives it.

Why the State of the Field Must Stay Outside the Transition

Here is the tempting mistake. A developer reads that startTransition keeps typing smooth, and wraps the update of the field itself:

The state of the field inside startTransition
1startTransition(() => {
2 setQuery(e.target.value);
WRONG the state that controls the field is now a Transition
3});

React's docs mark this same code with the comment "Can't use Transitions for controlled input state". They give the reason: "Transitions are non-blocking, but updating an input in response to the change event should happen synchronously."

Think about what the field shows. It shows query, and the user expects the letter the moment they type it. A Transition is allowed to wait, so the field can no longer answer the keystroke at once. The typed 1 vanishes from the field until the list is ready. When the user types two letters quickly, the field can end with 2 alone, and the 1 is lost.

That is why one keystroke needs two state variables. The field and the list need the same text at two different speeds. The field needs it at once, and the list can wait.

The Real Mistake: Concluding That useTransition Does Nothing

This is the mistake that Principle 2 ended on, and it is common:

  1. A developer adds useTransition and the second state variable, as React's docs show.
  2. The developer leaves PostList as a plain function.
  3. The typing is still janky, and the developer concludes that useTransition does nothing.
  4. The Console tells the truth. On every keystroke, it prints PostList rendered: with the old text, because the render for the urgent update still renders the list.

In React's own example for this Hook, the slow tab PostsTab is wrapped in memo the same way. React's docs give the reason for the same pattern with useDeferredValue: "Without memo, it would have to re-render anyway, defeating the point of the optimization."

Remember: the Transition moves the slow list to the background only when memo keeps it out of the urgent render.

When the user types fast, React never shows the list for 1. The field shows 1, then 12, each at once. The list goes from 500 posts straight to 15. The list of 176 posts for 1 never reaches the screen.

React's docs describe the case of several characters typed in a row. React "will throw out the stale rendering work that wasn't finished and render only the latest update."

The code does not change. The page of Principle 3 already does this. What we watch is the order of events when the user types 1, and then types 2 while the 176 posts render in the background:

  2. React starts the Transition: it renders the 176 posts for 1 in the background.

  5. React throws away the unfinished list for 1 and renders the Transition for 12: 15 posts.

AA TransitionvsBA DebounceBoth keep typing smooth, only the Transition can be interrupted

Many developers reach for a debounce here: wait 300 milliseconds after the last keystroke, then update the list. In their mind, both do the same job, because both keep the typing smooth. It looks the same, but it is NOT the same thing!

  • With a debounce, the list waits a fixed time, and then its render blocks the main thread, as in Principle 1. When the user types again during that render, the new letter waits. React's docs: debouncing and throttling "merely postpone the moment when rendering blocks the keystroke."
  • With a Transition, the list starts rendering at once, and the next keystroke interrupts it. React's docs: "Unlike debouncing or throttling, it doesn't require choosing any fixed delay."

A debounce is still the right tool when the slow work is not rendering, such as a request to a server. React's docs: "If the work you're optimizing doesn't happen during rendering, debouncing and throttling are still useful."

The Real Mistake: Mixing a Delay into the Transition

A developer wants both a short delay and a Transition. So the developer puts a setTimeout inside startTransition, to set the text of the list 300 milliseconds later.

But startTransition marks only the updates made while our function runs. The update now runs later, after the call has ended. React's docs are clear: "If you try to perform state updates in a setTimeout, for example, they won't be marked as Transitions."

So the render of the list is no longer a Transition. The next keystroke cannot interrupt it, and the letter waits for the list again.

Remember: the next letter always goes first, and React keeps only the list for the latest text.

isPending and a pending visual state. NEW isPending is the first item that useTransition returns, a boolean that React sets for you: your code never calls a set function for it. A pending visual state is what the page shows during that time: a sign, such as a faded list, that the new results are on their way (Lesson 67).

Interview PrepFor the Interview

The Interview Question: How do you keep typing responsive while a big re-render runs with useTransition?

How to Answer Clearly in 30 Seconds

"When one state variable drives both a text field and a big list, every keystroke is an urgent update. The field cannot show the letter until React has rendered the whole list. With useTransition, one keystroke makes two updates. The field's own state stays urgent, because a Transition cannot control a text input. A second state variable for the list is set inside startTransition, so React renders the new list in the background. Three details make it work:

  1. memo on the list: the parent renders again for the urgent update, so the list must be memoized to skip that render.
  2. Interruption: when the user types again, React throws away the unfinished list and renders only the latest text.
  3. isPending: it is true while the list is behind, so we can fade the old list, on an element outside the memoized list."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why can't you put the input's own state inside startTransition?"
    Because the field must answer every keystroke at once. React's docs: "Transitions are non-blocking, but updating an input in response to the change event should happen synchronously." That is why we keep two state variables: query stays urgent for the field, and searchQuery is set inside the Transition for the list. When the text comes from a prop, we have no set function to wrap. Then useDeferredValue is the tool (as seen in Lesson 68).
  2. "Does useTransition make the list render faster? How is it different from debouncing?"
    No, the list takes exactly as long as before. The Transition only lets the keystroke go first, and it lets React drop a list nobody needs anymore. A debounce waits a fixed time, and then its render blocks the next keystroke all the same. A Transition needs no fixed delay and never blocks the keystroke. Debouncing is still right for slow work outside rendering, such as a request to a server.
  3. "Which updates count as a Transition?"
    Only the state updates made during the startTransition call. React calls our function at once, not later. An update inside a setTimeout runs after the call has ended, so it is not marked as a Transition. An update after an await also needs its own startTransition. React's docs explain: "This is a JavaScript limitation due to React losing the scope of the async context." Form actions and useActionState handle this for forms (as seen in Lessons 41 and 42).
