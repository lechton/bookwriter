How a Server Page Hands the Signed-In User to Client Context

Interview Question❱ CORE

How does context behave across the server/client boundary?

How do Client Components read the signed-in user when only the server can read the database?

Overview · Two Ways Side by SideAIn a Server ComponentcreateContextvsBIn a Provider'use client'Context lives only in the browser

Who is signed in is stored in the database, so only the server can read it, yet the components that show the name run in the browser. Context lives only in the browser, so the server reads the user and passes it as a prop to a small Client Component that provides it. The reason: context exists to re-render the components that read it, and a Server Component runs once and is gone.

Remember how a site greeted John before React. The server read John from the database and printed him into the page, inside a <script> tag. Every script in the browser then read him from that one place:

The page the server sends: the server printed the user into a script tag

The server reads the user once and hands it over. The browser keeps the value in one place, and every script reads it from there. No script in the browser ever touches the database.

React with Server Components keeps the same split. The server reads the user. The hand-over is a prop. The one place where the browser keeps the value is context.

These are the lines that worked in Lesson 28, letter for letter. It may look the same, but it is NOT the same thing! In Lesson 28, the file ran in the browser. Here, it runs on the server, and the copy of React on the server has no createContext at all. The server stops at this file, and the reader gets no article.

Why does React leave context out of the server? React's docs give two facts, and they fit together:

  1. Context exists to re-render. React's docs: "React automatically re-renders components that read some context if it changes."
  2. A Server Component does not stay around after it renders. React's docs: "Server Components do not persist in memory after render and cannot have their own state."

So a Server Component runs once, hands over its output, and is gone. On the server, no component is left for context to update. Context belongs where components stay alive: in the browser.

Three Ideas From Earlier Lessons

KEY DEFINITION

Server Component and Client Component. REVIEW A file with no directive holds Server Components. They run on the server, they can be async and await the database, and they send only their output to the browser. A file that starts with 'use client' holds Client Components. Their code goes into the bundle the browser downloads, so they can use state, Hooks, and click handlers. Hooks do not work in a Server Component (Lesson 108).

KEY DEFINITION

Context. REVIEW Context lets a component deep in the page read a value that a component far above it holds, with no prop passed through every layer in between. You make it once with createContext(null), where null is the default value. The provider, <UserContext value={user}>, wraps a part of the page. Any component inside it reads the value with useContext(UserContext), and React re-renders that component when the value changes (Lesson 28).

KEY DEFINITION

What can travel from the server to the browser. REVIEW When a Server Component renders a Client Component, React writes the props down on the server and rebuilds them in the browser. Strings, numbers, arrays, plain objects, and JSX can make this trip. A plain function cannot, because it is code, not data, and an instance of a class cannot either (Lesson 107).

What the Reader of the Page Sees

What is at stake is what the reader of the news page sees:

  1. With the context made in the server file, the reader sees no article at all. The server stops before it sends any part of the page.
  2. With the provider set up right, both places show John in the first page the server sends. The browser makes no extra request to learn who is signed in.

Where Readers Usually Go Wrong

Readers usually go wrong in three ways:

  1. They write createContext in the server file, because that is where the data is.
  2. They import the context into the server file and read it there, because a server page that already knows the user seems the right place to read it.
  3. They believe a provider around the whole page turns the whole page into client code, so they pass the user as a prop through every layer instead.

Four Ways to Bring a Server Value to Client Components

When Client Components need a value that only the server can read, you choose between four ways:

  1. Pass the value as a prop through every layer. React's docs: "Start by passing props." This fits one or two layers. On our page, every layer between App and the comment form would carry user without using it.
  2. Pass JSX as children, so the layers in the middle disappear (as seen in Lesson 115). This fits when the layers in the middle only wrap their content.
  3. A client provider that receives the value as a prop, and useContext in each component that reads it. This fits when many Client Components at different depths read the same value. This lesson builds this way.
  4. A Promise passed into the provider and read with use. This fits a value that is slow to read, when the page should not wait for it. Lesson 165 builds it.

The client provider and the Promise both work only for Client Components, because a Server Component cannot read context. A Server Component that needs the user takes it as a prop, or reads it from the database itself.

PRINCIPLES

Context lives only in the browser. The server can read a value and pass it on, but it can neither make context nor read it. Five principles follow:

  1. createContext in a Server Component: the server stops before it sends the page. The copy of React on the server has no createContext.
  2. UserProvider with 'use client': the server passes user as a prop, and the provider makes the context. The value must be plain data.
  3. <UserContext> in a Server Component: the server can pass the context on, but never read it. The server holds only a placeholder for the real context.
  4. useContext under the provider: every Client Component reads the same user, at any depth. It works exactly as in Lesson 28, even inside a Server Component.
  5. children of the provider: a Server Component inside UserProvider stays on the server. The imports decide where code runs, not the place on the screen.

The Data Is Here, So the Context Goes Here

A team moves its news site to Server Components. App.jsx now awaits the user from the database. A developer adds the context to that same file, as the team always did in client code:

src/App.jsx
1import { createContext } from 'react';
2import db from './db';
3
4const UserContext = createContext(null);
WRONG App.jsx runs on the server, where React has no createContext

The reasoning looks sound: the data is in this file, so the context goes in this file.

Why the Page Never Arrives

The reader gets no article and no Hello, John. The server stops at the first line of App.jsx, before it renders anything. Here is what happens when the reader opens the page, in order:

  1. App.jsx has no directive, so it is a Server Component. Server Components are the default, and they need no marker. React's docs: "there is no directive for Server Components."
  2. The server loads App.jsx with its own copy of React, the one made for Server Components.
  3. That copy of React has no createContext, and no useContext either. React's docs list createContext first among the APIs that "must run on the client".
  4. The import line asks react for createContext and finds nothing. The server stops with an error that names createContext. Each framework words that message its own way.
  5. The server sends no page, so the reader sees no article.

The error shows up on the server side: in the terminal, or on the framework's error page. It does not come from the browser, because the browser never receives this page.

What Happens When the Reader Opens the Page

Nothing stops now. Here is the trip of John, in order:

  1. On the server, App awaits db.users.get(1) and gets the user object, with the id 1 and the name John.
  2. App renders <UserProvider user={user}>. The provider file starts with 'use client', so UserProvider is a Client Component. The user object must cross to it as a prop.
  3. user is a plain object with a number and a string, so it can cross (as seen in Lesson 107). React's docs list "Plain objects" with serializable properties among the values a Client Component may receive.
  4. UserProvider runs with user in its props. Its file made UserContext in the browser, where context exists, so it provides John to everything between its tags.

The provider adds no element of its own to the page. In the Elements panel, <header> and <article> sit directly where the provider was.

What the Server Holds When It Imports From a 'use client' File

KEY DEFINITION

A Client Reference. NEW When a server file imports something from a 'use client' file, it does not get the real export. It gets a placeholder object that records only two things: which file, and which export. React's error message calls this placeholder a Client Reference. The server can put it into what it sends to the browser, and there React swaps it for the real export. The server cannot look inside it, because the real export exists only in the browser (Lesson 116).

So App.jsx holds a placeholder, not the real UserContext. Here is what each line does with it:

  1. Writing <UserContext value={user}> puts the placeholder in what the server sends to the browser, together with the value prop. The server sends <UserProvider user={user}> the same way. In the browser, React finds the real UserContext and renders the provider.
  2. Reading with use(UserContext) asks the server to look inside the context and find the provider above. The server holds only the placeholder, so React stops with the error above. React's docs: "Reading context with use is not supported in Server Components."
  3. Reading with useContext(UserContext) fails even earlier. The copy of React on the server has no useContext, as Principle 1 showed.

So a server file can pass a client file's export on to the browser, but it can never look inside it.

Why We Still Write UserProvider

With the context tag written in App.jsx, the page in React 19 looks exactly as it does with <UserProvider user={user}>. Our page still keeps UserProvider, for two reasons:

  1. It is the shape React's docs promise. React's docs say a server file may take from a 'use client' file only "a React component or supported serializable prop values". UserProvider is a component, so it follows that rule. The context object is neither a component nor a plain value, so writing its tag in a server file is outside what the docs promise.
  2. It is the place to grow. Later the browser may need to change the value, such as a theme the reader switches. Then the provider must keep state. Only a component can hold state, and UserProvider is that component.

Remember: the server passes the context on, and only Client Components read it.

A Page With No Provider Above the Comment Form

A component that reads the context with no provider above it gets null, and the page stops. A developer adds the comment form to a second page, a photo gallery, and App does not wrap that page in UserProvider. The reader opens the gallery and sees no gallery. Here is why, in order:

  1. With no provider above it, useContext returns the default value of the context. Our file gave createContext the default value null. React's docs: "If there is no such provider, then the returned value will be the defaultValue".
  2. The comment form then reads user.name, which asks for a property of null.
  3. JavaScript stops with a TypeError, and React shows no gallery.

The fix is to render UserProvider above every page that holds a component that reads the user. A custom Hook that gives a clearer error message for this case is the topic of Lesson 165.

PRINCIPLE5children of the provider: a Server Component inside UserProvider stays on the server

Principle 5

The Imports Decide: Article Inside UserProvider Stays a Server Component

Summary: Wrap the page in the client provider from a Server Component, and pass the page as children; those components stay on the server, and they read server data themselves, never the context.

Description: A provider at the top of the page does not move the page to the browser. Only the files that a 'use client' file imports become client code. Article is imported by App, so it runs on the server, and UserProvider receives only its output. Because Article runs on the server, it cannot read the context around it.

On the screen, both put the article inside the provider. But where Article runs depends on which file imports it, not on where its tag sits (as seen in Lesson 115):

  1. When App.jsx writes <Article /> between the provider tags, the provider file never imports Article. App.jsx imports it, so Article runs on the server. The provider receives only its output in children. React's docs, on their own example: "the InspirationGenerator module never directly imports the Copyright module nor calls the component, all of that is done by App."
  2. When UserProvider.jsx imports Article, Article becomes client code, together with everything it imports. React's docs: "Add 'use client' at the top of a file to mark the module and its transitive dependencies as client code."

Our page writes <Article /> in App.jsx. So only three files go to the browser: the provider, the account button, and the comment form. The article, the page file, and the database stand-in stay on the server.

A Server Component Inside the Provider Still Cannot Read It

Staying on the server has a second side: Article still cannot read the context around it. Suppose the editors want the heading to greet the reader with Hello, John. A developer reaches for the context in Article, because the article sits inside the provider:

src/Article.jsx
1import { useContext } from 'react';
2import { UserContext } from './UserProvider';
3
4export default function Article() {
5 const user = useContext(UserContext);
WRONG Article is a Server Component, and the copy of React on the server has no useContext
6 return <h1>Hello, {user.name}</h1>;
7}

The page stops, exactly as in Principle 1. Article sits inside the provider on the screen, yet it is a Server Component, and Server Components cannot read context. A Server Component that needs the user reads it on the server, from the database:

src/Article.jsx
1import db from './db';
2
3export default async function Article() {
4 const user = await db.users.get(1);
A Server Component reads the user itself, not from context
5 return <h1>Hello, {user.name}</h1>;
6}

Now App and Article each read the user. To make both reads share one call to the database in one request, React gives cache(), the topic of Lesson 123.

Teams that believe the provider turns the page into client code make the opposite mistake. They keep the provider away from the top of the page, and pass user as a prop through every Server Component down to the comment form. That brings back the passing through every layer that context exists to remove.

Remember: the imports decide where code runs, so the page inside the provider stays on the server.

Interview PrepFor the Interview

The Interview Question: How does context behave across the server/client boundary?

How to Answer Clearly in 30 Seconds

"Context is a client feature. A Server Component runs once and does not stay in memory, so there is nothing on the server for context to re-render. The copy of React on the server leaves out createContext and useContext, and reading context with use is not supported there.

So the work splits in three:

  1. The server reads the value. A Server Component awaits the user from the database.
  2. A Client Component provides it. A small 'use client' file makes the context and renders the provider. The Server Component renders it with the value as a prop, which must be serializable, and the page as children.
  3. Client Components read it. Any Client Component under the provider reads the value with plain useContext, at any depth, even inside a Server Component.

The page passed as children stays on the server, because the imports decide where code runs, not the place on the screen. Those Server Components cannot read the context; they read the data themselves."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why does a provider rendered from a Server Component throw?"
    It throws when the server must make the context or read it. A server file that calls createContext stops at once, because the copy of React on the server has no createContext. A server file that reads the context with use stops with the error Cannot use() an already resolved Client Reference. When the context comes from a 'use client' file, the server holds only a Client Reference. It is a placeholder the server can pass on to the browser, but never look inside. The safe shape is a Client Component, such as UserProvider, that makes the context, renders the provider, and receives the server value as a prop.
  2. "Does a client provider at the root make the whole app client-rendered?"
    No. The components a Server Component passes as children stay Server Components. React's docs explain this with Copyright inside InspirationGenerator: the client file never imports Copyright, so Copyright stays on the server. Only the files a 'use client' file imports become client code, so the bundle holds the provider and the components that read it, not the page.
  3. "What if the browser must change the value, such as a theme the user switches?"
    The provider keeps state that starts from the server prop. UserProvider becomes a ThemeProvider with useState(initialTheme), the same shape as the Counter with initialValue in React's docs. A click changes the state, and React re-renders every component that reads the context. That is exactly why the provider must be a Client Component. Keeping those re-renders fast is the topic of Lesson 59.
