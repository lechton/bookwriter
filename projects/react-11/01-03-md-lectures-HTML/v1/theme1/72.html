Catching a Rendering Error with an Error Boundary

Interview Question❱❱ MORE

How do you catch a rendering error before it unmounts the whole app?

How do you keep one broken comment from turning the whole page white?

Overview · Two Ways Side by SideAAndcatchvsBAn Error BoundaryOne catches the code that runs inside it, the other catches the components React renders inside it

In plain JavaScript, when one line throws an error, you wrap it in try and catch, and the rest of the script keeps running. In React, an error thrown while React renders one component removes the whole page from the screen, and a try around the JSX cannot stop it. An Error Boundary can: it catches that error and shows one short message in place of the broken part, so the rest of the page stays.

In React, the data on a page often comes from a server, and you do not control what is inside it. A list of comments can hold one comment without its author, because that person deleted their account. The line that reads the author's name then throws a TypeError. In plain JavaScript, you would expect one broken line, maybe one missing comment. React does something much harsher: it removes everything it drew, and the user sees a white page.

This is why we have Error Boundaries. An Error Boundary is a component you wrap around a part of the page, and it catches the errors thrown while React renders that part.

Take a news article with a title and two comments under it. Ask yourself: should one broken comment take the whole article with it? No. The title and the first comment have nothing wrong with them. At worst, the comments should be replaced by one short line, such as Comments are unavailable., and the article should stay.

Why: You could fix this one bug with a check, such as comment.author?.name, which gives undefined instead of throwing. That is a good fix for a bug you know about. But nobody knows every bug in advance. Tomorrow another field arrives broken, in another component. An Error Boundary keeps the page on the screen for the errors nobody foresaw.

One Missing Field, One White Page

Here is the smallest code that breaks a page:

Comment.jsx
1function Comment({ comment }) {
2 return <li>{comment.author.name}: {comment.text}</li>;
For a comment with no author, this line throws
3}

For a comment with no author, comment.author is undefined. JavaScript gives that value for any field the object does not have. Reading a field of undefined throws a TypeError. That is the JavaScript error for using a value in a way its type does not allow.

This line runs while React renders Comment. Two reminders and two new words carry the whole lesson:

KEY DEFINITION

Rendering. REVIEW Rendering is the moment React calls your component function to find out what to show. The lines of the body and the JSX it returns run during rendering. An event handler is different: you write it inside the component, but its code runs later, when the user clicks (Lesson 13).

KEY DEFINITION

Unmount. REVIEW Unmount is React's word for removing what a component drew from the screen. It is the word in the interview question: one error during rendering unmounts the whole app (Lesson 32).

KEY DEFINITION

Error Boundary. NEW An Error Boundary is a component you wrap around a part of the page, such as the comments. The React docs call it "a special component that lets you display some fallback UI instead of the part that crashed." Without one, the docs warn: "By default, if your application throws an error during rendering, React will remove its UI from the screen" (Lesson 72).

KEY DEFINITION

Fallback. REVIEW The fallback, or fallback UI, is what React shows in place of a part of the page that cannot show its real content. You met the word with <Suspense>, which shows a fallback while data is on its way. An Error Boundary shows a fallback when a part has crashed, such as the line Comments are unavailable. (Lesson 69).

Why try and catch Do Not Help

Remember try and catch? Around a function call, they work, because the function runs inside the try block:

Plain JavaScript: the function runs inside the try
1try {
2 readName(comment);
ReadName runs right here, so its error lands in the catch
3} catch (error) {
4 console.log('Caught it');
5}

So the first idea every developer has is to do the same around the JSX:

React: the tag inside the try only describes Comment
1try {
2 return <ul>{comments.map(c => <Comment key={c.id} comment={c} />)}</ul>;
Comment does not run here
3} catch (error) {
4 return <p>Comments are unavailable.</p>;
5}

It looks the same, but it is NOT the same thing! The tag <Comment /> is not a call to Comment. It is a description that tells React: "call Comment later" (Lesson 4). React calls it after the parent has returned, and by then the try block is over. Principle 2 shows it step by step.

The Error Bubbles Up to the Closest Boundary

So where does the error go? Remember how a click on a <button> bubbles up to the <div> around it, and then to the body? A rendering error travels the same way, but through your components. It goes from Comment to its parent, then to that parent's parent, one level at a time, until it meets an Error Boundary. With no boundary on the way, it reaches the top, and React removes the whole page.

The React docs use the same word: "Errors thrown in rendering methods or hooks bubble up through the component tree. Only Error Boundaries can catch these errors."

Keep this one sentence in mind for the whole lesson: an error during rendering travels up to the closest Error Boundary above it. That boundary shows its fallback, and everything outside it stays on the screen.

The Rule of Thumb: when did the error happen?

Ask one question about every error: did it happen while React renders, or later, in your own code? While React renders, only an Error Boundary catches it. In a click handler or a timer, try and catch catch it.

A senior developer also knows the three classic mistakes:

  1. try and catch around the JSX. The child runs after the parent returns, so the catch never runs.
  2. An Error Boundary written as a function component. React has no Hook for catching a child's error, so it must be a class.
  3. An Error Boundary that should catch a click. A click handler runs after rendering, so the boundary never sees its error.

The rest of the lesson shows each mistake on a real news article.

PRINCIPLES

An error during rendering travels up to the closest Error Boundary. Six principles follow:

  1. No boundary removes the whole page. One broken comment, and React removes the title and John's comment too.
  2. try and catch around the JSX catch nothing. React calls the child after the parent has returned.
  3. getDerivedStateFromError switches the boundary to its fallback. An Error Boundary is a class, because no Hook can catch a child's error.
  4. The place of the boundary decides what the user keeps. Around the comments, the article stays. Around each comment, John's comment stays too.
  5. componentDidCatch tells the team. The fallback hides the error from the user, and this method reports it.
  6. A click handler error skips the boundary. In a handler, try and catch is the tool.

PRINCIPLE2try and catch around the JSX: the catch is already over when the child throws

Principle 2

Bubbling: try and catch Cannot Catch a Child's Rendering Error

Summary: A try and catch inside a parent component cannot catch an error thrown while React renders a child component, because the parent only returns the child's tag and React calls the child later.

Description: The error bubbles up the component tree from the component that threw it, one parent at a time. Only an Error Boundary on that path can catch it. A catch block in the parent was already finished when the child threw.

Why the catch is already over when Comment throws

The catch is not broken. It is simply over before the error happens. Writing <Comment /> never calls Comment (Lesson 4). React renders a child only after its parent has returned (Lesson 13). Here is the order:

  1. React calls CommentList.
  2. The try block runs the return line. It builds a description of two <Comment> tags, and nothing throws.
  3. CommentList returns. Its try and its catch are finished.
  4. React calls Comment for each tag. The second one throws.
  5. No catch is waiting anymore, and no Error Boundary sits above, so React removes the page.

Compare it with plain JavaScript. Around readName(comment), the function runs inside the try. So the catch block sees its error. Around <Comment />, nothing runs inside the try. The tag only describes the child.

So does try and catch never work in a component? It does, for code that runs inside that same try block. If Comment itself wrapped the line that reads the author's name in a try block, that catch block would run. What a try misses are the errors of child components.

The linter can save you here (Lesson 38). The error-boundaries rule of the React Hooks ESLint plugin flags this code. The docs describe the rule in one line: "Validates usage of Error Boundaries instead of try/catch for errors in child components."

PRINCIPLE3getDerivedStateFromError: React switches the boundary from its children to its fallback

Principle 3

Class Boundary: getDerivedStateFromError Switches render to the Fallback

Summary: An Error Boundary is a class component with static getDerivedStateFromError, which returns new state when a child throws during rendering, and a render method that returns the fallback when that state says so and the children otherwise.

Description: No Hook tells a function component that a child threw, so the boundary must be a class. When a child throws, React calls getDerivedStateFromError, puts the state it returns into the boundary, and renders the boundary again. This time render returns the fallback.

✓ DO THIS
1class ErrorBoundary extends Component {
2 state = { hasError: false };
3 static getDerivedStateFromError() {
React calls it when a child throws, and the fallback shows
4 return { hasError: true };
5 }
6 render() {
7 return this.state.hasError ? this.props.fallback : this.props.children;
8 }
9}
✗ DO NOT DO THIS
1function ErrorBoundary({ children, fallback }) {
2 const [hasError] = useState(false);
WRONG nothing sets it when a child throws, so the page still goes white
3 return hasError ? fallback : children;
4}

Every component you wrote so far is a function. Before Hooks existed, React components were also written as JavaScript classes. Today you almost never need one, with one exception: the Error Boundary. React tells a component that a child threw only through a class method, and no Hook does the same job.

KEY DEFINITION

Class component. NEW A class component is a React component written as a JavaScript class instead of a function. It extends Component from React, keeps its state in a field named state, and returns its JSX from a method named render. Today its main use is the Error Boundary, because "there is currently no way to write an Error Boundary as a function component" (Lesson 72).

The smallest Error Boundary

An Error Boundary has two answers: its children, or its fallback. One state field, hasError, picks between them. Here is the smallest boundary, the same shape the React docs use:

The class words, one at a time

The file uses five words the earlier lessons never needed. Each one does one job:

  1. class and extends Component. A class is a JavaScript template for objects, and JavaScript provides both words. Component comes from React, and extending it makes our class a React component.
  2. state = { hasError: false }. This is the first state of the class, before any error. The docs: "The state field must be an object."
  3. render. This method returns what appears on the screen. The docs: "The render method is the only required method in a class component."
  4. static. A static method belongs to the class itself, not to one object made from it. React calls getDerivedStateFromError on the class, so the method must be static.
  5. getDerivedStateFromError. React calls it when a child throws during rendering, "including distant children", so a child of a child counts too. It "should return the state telling the component to display the error message."

The error it receives is the value that was thrown. The docs say it "will usually be an instance of Error but this is not guaranteed because JavaScript allows to throw any value."

Athis.statevsBState in a functionThe same thing, read through this

this.state and this.props look new. They are not:

Reading state and props in a class and in a function component
1if (this.state.hasError) return ~this.props.fallback~;
In a class: read through this
2if (hasError) return ~fallback~;
In a function: hasError from useState, fallback from the props

Yes, it is the exact same thing! A class reads its own state and props through the word this, which means "this boundary". The docs: "The props passed to a class component are available as this.props", and "The state of a class component is available as this.state."

Why a function component cannot be a boundary

So can we write the boundary as a function with useState? Reading state is the same, but catching is not:

A function component that tries to be an Error Boundary
1function ErrorBoundary({ children, fallback }) {
2 const [hasError, setHasError] = useState(false);
WRONG no Hook tells this function that a child threw
3 return hasError ? fallback : children;
4}

It looks the same, but it is NOT the same thing! Nothing ever calls setHasError, because React calls getDerivedStateFromError only on a class. The page still goes white.

So in practice there are two ways to add an Error Boundary:

  1. Write one class, and use it everywhere. The docs: "write a single ErrorBoundary component like above and use it throughout your app." It fits a team that wants no extra package.
  2. Use the react-error-boundary package. The docs: "you don't have to write the Error Boundary class yourself. For example, you can use react-error-boundary instead." It fits most apps.

A framework can also do it for you. In Next.js, an error.js file wraps a page in a boundary (Lesson 46). In this lesson we write the class ourselves, because it shows what every boundary does, including the one inside the package.

What React does when the second comment throws

React renders the boundary first with its children, and then again with its fallback. No line of our code calls a setter, yet the boundary's state changes. Here is the order:

  1. React renders ErrorBoundary. Its hasError is false, so it returns the children.
  2. React renders the children, and the second Comment throws.
  3. The error bubbles up to ErrorBoundary, and React calls getDerivedStateFromError with the error.
  4. It returns { hasError: true }, and React puts that into the boundary's state. The docs: "Update state so the next render will show the fallback UI."
  5. React calls render again. Now it returns the fallback, and the broken children never reach the screen.

One more rule: getDerivedStateFromError must stay a pure function (Lesson 14). It only returns new state. Reporting the error is the job of another method, in Principle 5.

How to choose the place

The docs call this choice "the granularity of Error Boundaries". They ask you to "consider where it makes sense to display an error message." Their own example fits our page: "in a messaging app, it makes sense to place an Error Boundary around the list of conversations. It also makes sense to place one around every individual message. However, it wouldn't make sense to place a boundary around every avatar."

Our comments list and each comment are the same two choices. A boundary around the author's name alone would make no sense: the user cannot read half a comment.

A boundary around the whole app still has a use, as the last safety net: one line of text is better than a white page. It only must not be the only boundary.

PRINCIPLE5componentDidCatch: the team gets the error, the user gets the fallback

Principle 5

Reporting: componentDidCatch Tells the Team, the Fallback Tells the User

Summary: componentDidCatch is the optional method React calls after a child throws during rendering, so the boundary can send the error and info.componentStack to an error reporting service; showing the fallback stays the job of getDerivedStateFromError.

AgetDerivedStateFromErrorvsBcomponentDidCatchOne changes the screen, the other reports

They look alike, but they are NOT the same thing! Both receive the same error. One changes what the user sees. The other tells the developer:

  • getDerivedStateFromError is static, receives the error, and returns new state. It must stay pure, and a boundary needs it.
  • componentDidCatch is not static, receives the error and an info object, and returns nothing. It may do side effects, such as a call to a server, and it is optional.

The docs draw the line between them: "static getDerivedStateFromError should be a pure function." For a side effect, such as a call to an analytics service, "you need to also implement componentDidCatch."

What the team receives

React calls componentDidCatch when a child, even a distant one, throws during rendering. The docs give its purpose: "This lets you log that error to an error reporting service in production."

An error reporting service is an outside service that collects the errors that happen in your users' browsers, so the team can see them. logErrorToMyService is the docs' placeholder name for the call to that service.

The second argument, info, holds componentStack. The docs describe it as "a stack trace with the component that threw, as well as the names and source locations of all its parent components." For our page, it says that Comment threw, inside the boundary, inside App. So the team knows exactly which part of the page broke.

Something that can be tricky: "In production, the component names will be minified." The build shortens the names, often to one or two letters, so a production report is harder to read.

Two mistakes with the two methods

Reporting errors for the whole app

For the interview, know one more place to report errors. createRoot accepts three options for this (Lesson 7):

  1. onCaughtError is "called when React catches an error in an Error Boundary."
  2. onUncaughtError is "called when an error is thrown and not caught by an Error Boundary."
  3. onRecoverableError is "called when React automatically recovers from errors."

Each one receives the error and an errorInfo object with componentStack. They report errors for the whole app, but they do not keep the page on the screen. Only an Error Boundary shows a fallback.

Without these options, React 19 sends the errors no boundary caught to window.reportError. That is the browser function that printed the "Uncaught" line in Principle 1.

Principle 6

Event Handlers: A Click Error Never Reaches the Boundary

Summary: An Error Boundary catches only errors thrown while React renders its children; errors in event handlers, in asynchronous code such as setTimeout, in the boundary itself, and during server side rendering are not caught; an error thrown inside startTransition from useTransition is caught.

Description: A click handler runs when the user clicks, not while React renders. So when it throws, React never calls getDerivedStateFromError, and the page stays as it was, with the error only in the Console. Inside a handler, try and catch work, because the handler's own code runs inside the try.

What an Error Boundary does not catch

The docs list four places where an Error Boundary catches nothing:

  1. Event handlers, such as our Reply button.
  2. Asynchronous code, such as callbacks of setTimeout or requestAnimationFrame. They run later, outside rendering, just like a click handler.
  3. Server side rendering, which belongs to Part Two.
  4. Errors thrown in the boundary itself, rather than in its children. Those go past it, to the next boundary above.

Interview PrepFor the Interview

The Interview Question: How do you catch a rendering error before it unmounts the whole app?

How to Answer Clearly in 30 Seconds

"By default, when a component throws during rendering, React removes the whole UI of the root, so one broken item of data turns the page white. A try and catch around the JSX cannot help. The parent only describes the child, and React calls the child after the parent has returned. The error bubbles up the component tree, and only an Error Boundary can catch it. An Error Boundary is a class component with static getDerivedStateFromError, which returns state that tells render to show a fallback instead of the children. Three rules:

  1. Place boundaries where a fallback makes sense to the user, such as around a list of comments or around each comment, not only around the whole app.
  2. Add componentDidCatch to send the error and its component stack to an error reporting service.
  3. Errors in event handlers and timers skip the boundary, so I catch those with try and catch.

In most apps, I use the react-error-boundary package instead of writing the class myself."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why can't you write an Error Boundary as a function component?"
    Because there is no Hook for it. React calls getDerivedStateFromError and componentDidCatch only on a class. The docs say: "There is no direct equivalent for static getDerivedStateFromError in function components yet." So a team writes one ErrorBoundary class and uses it everywhere, or uses the react-error-boundary package. The package also adds fallbackRender and resetKeys, which let the boundary try its children again, for example after the user presses a "Try again" button.
  2. "Does an Error Boundary catch an error thrown in a click handler?"
    No. A boundary catches only errors thrown while React renders its children. A click handler runs later, when the user clicks, so its error goes past the boundary, and the page does not change. The same goes for asynchronous code such as setTimeout, for errors in the boundary itself, and for server side rendering. Inside a handler, we use try and catch. The exception is startTransition from useTransition: an error thrown inside the transition function goes to the closest Error Boundary. So does the error of a Form Action.
  3. "What is the difference between getDerivedStateFromError and componentDidCatch?"
    Both receive the same error, but they do different jobs. getDerivedStateFromError is static and pure: it returns new state, such as hasError: true, so the next render shows the fallback. componentDidCatch receives the error and info.componentStack, and it may do side effects, such as sending a report to an error reporting service. Calling an analytics service inside getDerivedStateFromError breaks its purity. Calling setState inside componentDidCatch to show the fallback is deprecated.
