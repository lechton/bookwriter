What useMemo Caches, and When It Is Wasted Work

Interview Question❱❱ MORE

What does useMemo cache, and when is it wasted work?

How do you make React keep the result of a slow calculation between renders, and when does that only add code?

Overview · Two Ways Side by SideAA Filter in the BodyvsBThe Same Filter inuseMemoThe plain line runs on every render, the useMemo line reuses the last result

React runs every line of a component again on every re-render, so a filter over a long list of messages runs again on every letter the user types, even in a field that has nothing to do with the search. Wrap the calculation in useMemo, and React keeps its last result and hands it back while every dependency is the same as last time. It is worth it only for a calculation that a measurement shows is slow, or for an array you pass to a component wrapped in memo, and around a cheap line it only adds code.

Remember Lesson 55? The user types O in the chat, setText changes the state, and React calls ChatRoom again. React does not pick the lines that need to run. It runs the whole body of the component, every line, whatever state changed (as seen in Lesson 13). For most lines, that costs nothing.

But picture a chat that keeps 5,000 messages, with a Search messages field at the top and a Message field at the bottom. The line that filters the messages sits in the body of ChatRoom. So every letter the user types in the Message field filters all 5,000 messages again. The search did not change, and the list stays exactly the same. You want to tell React: "Keep the result of this filter. Run it again only when the messages or the search change."

That is exactly what useMemo does. useMemo hands back the last result while every dependency is the same as last time. A dependency is a value the calculation reads, here the messages and the search. Keep this sentence in mind. As in Lesson 55, the whole lesson is about the word "same".

KEY DEFINITION

A re-render. REVIEW A re-render is React calling a component function again to get its new JSX. It happens for three reasons: the component's own state changed, its parent re-rendered, or a context it reads changed. Every line in the body of the component runs again, so a calculation written there runs again too. A re-render is only a function call: React then changes only the DOM nodes that differ (Lesson 54).

KEY DEFINITION

Object.is. REVIEW Object.is(a, b) is the JavaScript check React uses to ask "is this the same value as before?". For strings and numbers, it compares the value: Object.is('l', 'l') is true. For objects, arrays, and functions, it asks whether both are the very same one: two arrays with the same messages give false (Lesson 37).

KEY DEFINITION

memo. REVIEW memo is a function React provides. It wraps a component and returns a memoized component. When the parent re-renders, React compares each prop with its old value by Object.is, and skips the memoized component while every prop is the same. A new array on every render counts as a changed prop (Lesson 55).

KEY DEFINITION

StrictMode calls every component twice. REVIEW Our project mounts <App /> inside <StrictMode>. In development, StrictMode calls every component function twice on purpose, so every console.log inside a component prints two lines. In production, each component is called once (Lesson 47).

Why It Is Called useMemo

You met the word in Lesson 55. memo comes from memoization, which React's docs explain as "in other words, cache". A cache keeps the last result and reuses it while the inputs stay the same. The docs say it outright: "Caching return values like this is also known as memoization, which is why this Hook is called useMemo." Like every Hook, its name starts with use.

In plain JavaScript, you would write such a cache yourself. You keep the last inputs and the last result, and you compare before you do the work:

Plain JavaScript: a cache for the filter, written by hand
1let lastMessages = null;
2let lastQuery = null;
3let lastResult = null;
4
5function cachedFilter(messages, query) {
6 if (Object.is(messages, lastMessages) && Object.is(query, lastQuery)) return lastResult;
The same inputs as last time: reuse the old result
7 lastMessages = messages;
8 lastQuery = query;
9 lastResult = filterMessages(messages, query);
10 return lastResult;
11}

useMemo writes this cache for you, inside the component. The list [messages, query] does the job of lastMessages and lastQuery. The value useMemo returns does the job of lastResult. And React keeps a separate cache for each copy of the component, the same way each copy has its own state (as seen in Lesson 12).

So the two names do two different jobs. memo caches what a whole component rendered. useMemo caches the result of one calculation inside a component.

KEY DEFINITION

useMemo. NEW useMemo is a Hook React provides. You give it a calculation function and a list of dependencies, the values the calculation reads: useMemo(() => filterMessages(messages, query), [messages, query]). On the first render, React calls the function and stores the result. On every later render, React compares each dependency with its value from the last render by Object.is. When all of them are the same, React hands back the stored result and does not call the function. When one changed, React calls it again and stores the new result (Lesson 56).

What the User Feels

The user feels this in the Message field. A real chat keeps a long history in memory, and filters it right in the browser while the user types a reply. When a slow filter runs on every letter, the letters appear late in the field. React's docs say this kind of work "makes the typing feel janky".

  1. With useMemo around the slow filter, letters in the Message field skip it. Only a change to the search, or a new message, runs it.
  2. With useMemo around a cheap line, such as the check that the Message field is not empty, the user sees nothing change. The docs: "There is no benefit to wrapping a calculation in useMemo in other cases." The code only gets longer and harder to read.

The Rule of Thumb: measure first, and keep every dependency the same

useMemo hands back the last result while every dependency is the same as last time. Add it only where a measurement shows a slow calculation, and make sure no dependency is a new object on every render.

A senior developer knows the four classic mistakes with useMemo:

  1. Wrapping every calculation because someone said it is faster. Nobody measured, and the user sees no difference.
  2. Thinking it makes the page load faster. It does not. The docs: "useMemo won't make the first render faster. It only helps you skip unnecessary work on updates."
  3. Letting the app depend on the stored result. React may throw it away. The docs: "You should only rely on useMemo as a performance optimization. If your code doesn't work without it, find the underlying problem and fix it first."
  4. Listing a dependency that is new on every render, such as an object made in the component body. Then React never reuses the stored result.

When a calculation in a component seems slow, there are four ways to handle it:

  1. Calculate it during rendering, with no cache. This is the default (as seen in Lessons 22 and 34). React's docs say it plainly: "Usually, this code is fine!"
  2. Cache it with useMemo. This fits when "The calculation you're putting in useMemo is noticeably slow, and its dependencies rarely change." This lesson covers it.
  3. Keep the fast-changing state lower, or pass JSX as children, so the slow part does not re-render at all. The docs put this first among the habits that "make a lot of memoization unnecessary". Lesson 58 covers it.
  4. Turn on React Compiler. It "can automatically memoize expensive calculations for you, eliminating the need for manual useMemo in many cases". Lesson 63 covers it.

PRINCIPLES

useMemo hands back the last result while every dependency is the same as last time. It is not a speed switch you can put on any line. Four principles follow:

  1. Principle 1: useMemo Skips the Filter While the User Types a Message. React calls the calculation on the first render and stores the result. On later renders, it hands back the stored result while every dependency is the same, and calls the calculation again when one changed.
  2. Principle 2: Measure First with console.time. Wrap a calculation only when a measurement shows it is slow. Around a cheap line, useMemo gains nothing and makes the code harder to read. It never makes the first render faster.
  3. Principle 3: useMemo Gives the Memoized MessageList the Same Array. filter builds a new array on every call, so a child wrapped in memo re-renders anyway. useMemo hands the child the same array until a dependency changes.
  4. Principle 4: An Object Made in the Body Breaks the Cache. An object written in the component body is new on every render, so a dependency list that holds it changes every time. Create the object inside the calculation function.

The Three Parts of a useMemo Line

A useMemo line has two arguments and one result, and React's docs give each one a name:

The three parts of a useMemo line
1const visibleMessages = useMemo(
2 () => filterMessages(messages, query),
1. The calculation function: React calls it, not our code
3 [messages, query]
2. The dependencies: every value the calculation reads
4);
  1. The calculation function is the first argument, our arrow function. React's docs say it "should be pure, should take no arguments, and should return a value of any type". Our code writes it, and React decides when to call it.
  2. The dependencies are the second argument. The docs call them "The list of all reactive values referenced inside of the calculateValue code." Our calculation reads messages and query, so both go in the list. On each render, React compares each one with its value from the last render by Object.is. It is the same check React uses for the dependency array of an Effect (as seen in Lesson 35). Write the list right inside the call, and keep the same number of items in it on every render.
  3. The cached value is what useMemo returns, here visibleMessages. On the first render, it is the result of our calculation function. On later renders, it is either the result React stored last time, or a fresh result when a dependency changed.

Why do we pass a function, and not the result? Because JavaScript first runs whatever you write between the parentheses of a call. If you passed the filter call itself, JavaScript would filter before useMemo even starts, and there would be nothing left to skip. So you hand React the function, and React decides whether to call it.

The messages and query inside the arrow function are the state variables of this render. The arrow function is written inside ChatRoom, so it reads them from the body around it (as seen in Lesson 15).

The Real Mistake: No Dependency List

React's docs list this mistake in their troubleshooting section. A developer adds useMemo and forgets the second argument:

useMemo without its dependency list
1const visibleMessages = useMemo(() => filterMessages(messages, query));
WRONG no dependency list, so React calls the filter on every render
  1. The page works, and the list is right.
  2. The user types in the Message field, and Filtering messages for: appears at every letter.
  3. The developer decides that useMemo does not work.

useMemo works. It just has nothing to compare. The docs: "If you forget the dependency array, useMemo will re-run the calculation every time." Add [messages, query], and the letters in the Message field stop printing the line.

Five Facts About the Calculation Function

  1. It runs during rendering, so it must be pure. React's docs say caching "only works for pure calculations". Suppose the calculation pushed a welcome message into messages, the array it received from state. StrictMode would then show that message twice. Changing a new array that the calculation made itself is fine. The React Hooks linter has a rule for this, use-memo: "useMemo is for computing and caching expensive values, not for side effects."
  2. StrictMode calls it twice in development. The docs: "React will call your calculation function twice in order to help you find accidental impurities. This is development-only behavior". React keeps one of the two results (as seen in Lesson 47).
  3. React may throw the cached value away. The docs: "React will not throw away the cached value unless there is a specific reason to do that." One reason is editing the component's file during development. Another is a component that pauses its first render to wait for data, which React calls suspending. Lesson 69 covers it. When a value must be kept, "a state variable or a ref may be more appropriate" (as seen in Lessons 12 and 30).
  4. It is a Hook, so you call it only at the top level of the component. The docs: "You can't call it inside loops or conditions." To cache one calculation for each item of a list, extract a component for the item, and call useMemo inside that component (as seen in Lesson 38).
  5. It replaces an Effect that copies a result into state. The docs: "To cache expensive calculations, add useMemo instead of useEffect." An Effect that stores the filtered list in state first renders the page with the old list (as seen in Lesson 34).

For the user, yes, it is the exact same thing! The Send button turns grey and turns active at the very same moments in both versions. Why is the useMemo useless here? For two reasons:

  1. There is nothing worth skipping. The check reads one short string.
  2. It would not skip anyway. text changes at every letter the user types in the Message field, so this useMemo runs the check on those letters too.

The second line only adds an arrow function and a dependency list for the next developer to read.

A developer new to this thinks: "useMemo makes any calculation faster, so wrap them all." But useMemo only skips work on renders where the dependencies did not change. When the work is tiny, there is nothing to skip. React's docs give a rule of thumb: "In general, unless you're creating or looping over thousands of objects, it's probably not expensive." Our filter loops over 5,000 messages, so it may be expensive. Only a measurement can tell.

Two things can mislead us here:

  1. Our machine is faster than the user's phone. The docs: "Your machine is probably faster than your users' so it's a good idea to test the performance with an artificial slowdown." Chrome's CPU Throttling gives that slowdown (as seen in Lesson 54).
  2. Development mode is slower, and StrictMode doubles every render. The docs: "To get the most accurate timings, build your app for production and test it on a device like your users have."

So the number decides, not the look of the code. If the filter over 5,000 messages stays far under 1ms on a throttled CPU, it is not expensive at this size, and the plain line is fine. If it reaches 1ms or more, it is worth caching. It runs at every letter, and its dependencies, the history and the search, rarely change.

Now we keep the timer and wrap the line in useMemo:

src/components/ChatRoom.jsx
1console.time('filter messages');
2const visibleMessages = useMemo(() => filterMessages(messages, query), [messages, query]);
Skipped on letters in the Message field
3console.timeEnd('filter messages');

The user types in the Message field again. The logged time drops close to zero, because React hands back the stored array and never calls the filter.

What useMemo Never Speeds Up: the First Render

Now we reload the page. On the first render, the timer shows the full cost of the filter again. Nothing is stored yet, so React has to call the calculation. The docs: "useMemo won't make the first render faster. It only helps you skip unnecessary work on updates."

The Real Mistake: Wrapping Every Calculation

Wrapping everything in useMemo brings the user nothing and costs the team readable code. Here is how it usually goes:

  1. A team agrees to wrap every calculation in useMemo, because someone said it is faster.
  2. A developer wraps canSend, the count of messages, and the line that joins a first name and a last name.
  3. Each wrapped line gains an arrow function and a dependency list. Some lists miss a value, and the linter starts to complain.
  4. Nothing the user sees changes.

React's docs describe exactly this: "There is no significant harm to doing that either, so some teams choose to not think about individual cases, and memoize as much as possible. The downside of this approach is that code becomes less readable. Also, not all memoization is effective: a single value that's 'always new' is enough to break memoization for an entire component."

When useMemo Is Worth Adding

React's docs name three cases where useMemo is valuable:

  1. The calculation is noticeably slow, and its dependencies rarely change. This is our filter, once a measurement shows it is slow.
  2. You pass the result as a prop to a component wrapped in memo. Principle 3 covers this case.
  3. The result is later used as a dependency of another Hook, such as another useMemo or a useEffect. Principle 4 shows how such a dependency breaks, and an Effect follows the same rule (as seen in Lesson 37).

The kind of app matters too. When most interactions are coarse, such as replacing a page or a whole section, the docs say "memoization is usually unnecessary." When most interactions are granular, as in a drawing editor where the user moves shapes, "you might find memoization very helpful."

React Compiler changes the habit for new code. The docs: "For new code, we recommend relying on the compiler for memoization and using useMemo/useCallback where needed to achieve precise control." For existing code, they recommend leaving the memoization in place, because removing it can change what the compiler produces. The other way is to test carefully before removing it. Lesson 63 covers the compiler.

The developer adds memo, the typing still lags, and they blame memo. Here is how it happens:

  2. They wrap MessageList in memo (as seen in Lesson 55).
  3. They pass the filter result without useMemo.
  4. The letters still lag. The docs explain why: the filtered list "is always a different array", and the slow list "can't skip re-rendering".
  5. The developer removes memo, believing it does nothing.

Three Facts for the Interview

  1. The rows often cost more than the filter. The docs: "if the number of todos grows significantly, most of the overhead will be in re-rendering rather than in the filtering." The same can hold in our chat: rendering 5,000 rows may take longer than filtering them. Lesson 62 covers very long lists.
  2. useMemo can also cache a JSX node. A JSX node is an object too, so useMemo can return the <MessageList> tag itself, with [visibleMessages] as its list. That gives the same result as memo. The docs: "if React sees the same exact JSX as during the previous render, it won't try to re-render your component." The docs still prefer memo: "Manually wrapping JSX nodes into useMemo is not convenient. For example, you can't do this conditionally."
  3. useMemo caches a result, and useCallback caches a function. The docs: "useMemo caches the result of calling your function" and "useCallback caches the function itself." A function passed to a memoized child needs useCallback, which Lesson 57 covers. An object passed as the value of a context provider needs useMemo for the same reason as our array, and Lesson 59 covers it.

Finding the Dependency That Breaks the Cache

When a useMemo runs on every render and the reason is not obvious, React's docs give a way to find the dependency that changes:

  1. Log the dependency list right above the useMemo line, such as console.log([messages, searchOptions]).
  2. In the Console, right-click two of the logged arrays from different renders, and store each one as a global variable. The browser names them temp1 and temp2.
  3. Compare each item in the Console. Start with Object.is(temp1[0], temp2[0]) for messages, then Object.is(temp1[1], temp2[1]) for searchOptions.
  4. The item that gives false is the one that breaks the cache. The docs: "When you find which dependency breaks memoization, either find a way to remove it, or memoize it as well."

The Real Mistake: Returning an Object from an Arrow Function

When the cached value is itself an object, the curly braces can trick us:

Caching an options object with useMemo

WRONG these braces start a function body, so it returns undefined
2const searchOptions = useMemo(() => {
3 return { text: query };

Right after an arrow, curly braces start the body of the function, not an object. The first line has no return, so useMemo gives back undefined. Wrapping the object in parentheses also works, but the docs say that form "is easy for someone to break again", and they recommend the explicit return.

The Same Rule in Effects

An object made in the body and listed in an Effect's dependency array makes the Effect run again on every render. The docs fix it the same way, by moving the object inside the Effect, because "useMemo is performance optimization, not a semantic guarantee" (as seen in Lesson 37).

Even with React Compiler, a hand-written useMemo still has a place here. The compiler docs: "A common use-case for this is if a memoized value is used as an effect dependency." Lesson 63 covers the compiler.

Interview PrepFor the Interview

The Interview Question: What does useMemo cache, and when is it wasted work?

How to Answer Clearly in 30 Seconds

"useMemo caches the result of a calculation between re-renders. On the first render, React calls the calculation function and stores the result. On later renders, React compares each dependency with its old value using Object.is. If all of them are the same, React returns the stored result. If one changed, React calls the calculation again. It is worth it in three cases:

  1. A slow calculation: about 1ms or more, measured with console.time on a throttled CPU, whose dependencies rarely change.
  2. A value passed to a component wrapped in memo: so the child gets the same array or object and can skip.
  3. A value used as a dependency of another Hook.

Around a cheap calculation it is wasted work: it brings no benefit, it never speeds up the first render, and it makes the code harder to read. And it is only a performance optimization: if the code breaks without it, there is a bug to fix."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Should we wrap every calculation in useMemo to be safe?"
    No. useMemo skips work only on renders where its dependencies did not change, and a cheap calculation has nothing worth skipping. React's docs say there is "no benefit" in other cases and "no significant harm" either, but the code "becomes less readable", and a single dependency that is always new breaks the cache anyway. Measure first with console.time, and wrap only what is slow. For new code, React Compiler can memoize calculations automatically.
  2. "Your useMemo recalculates on every render. Why?"
    There are two usual causes. First, the dependency array is missing, so React has nothing to compare and runs the calculation every time. Second, one dependency is new on every render, such as an object made in the component body. Object.is compares objects by identity, so the new object always looks changed. To find it, log the dependency list, store two of the logged arrays as global variables in the Console, and compare each item with Object.is. The fix is to create the object inside the calculation function and list the plain values it is made from.
  3. "Can your code rely on useMemo to keep a value between renders?"
    No. React may throw the cached value away, for example when you edit the component's file in development, or when a component pauses its first render to wait for data. The docs say to rely on useMemo only as a performance optimization: "If your code doesn't work without it, find the underlying problem and fix it first." A value that must be kept belongs in state or in a ref. The calculation must also be pure, because React calls it during rendering, and StrictMode calls it twice in development to find impurities.
