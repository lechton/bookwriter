How a Contact Form Keeps Up When the Contact Changes

Interview Question❱❱❱ ADVANCED

How do you derive values during render, and when is adjusting state during render legal?

Why does a form keep showing the old contact after the user picks another one?

Overview · Two Ways Side by SideAconst name = contact.namevsBuseState(contact.name)Both start with Taylor, only the const follows the new contact

When the user picks another contact, the parent passes the new contact down as a prop, and the component body runs again with it. But React reads the value inside useState(contact.name) only on the first render, so a copy of a prop in state stays on the first contact. That is why you read the prop directly when you can, and give the form a key when the user types in it.

Remember useState('John') from Lesson 12? The 'John' in the parentheses is the starting value. React uses it once, when the component first appears on the page. From then on, React keeps the value in its own memory, and only the setter can change it. With a fixed string like 'John', that is exactly what you want.

The trouble starts when the starting value is a prop. Here are two ways to get a name from a contact prop:

Two ways to get name from the contact prop
1const name = contact.name;
1. Plain JavaScript: our code reads the prop again on every render
2const [name, setName] = useState(contact.name);
2. React reads the prop on the first render only

When the page opens with Taylor's contact, both lines give name the value 'Taylor'. The page looks the same with either line.

It may look the same, or work the same at first, but it is NOT the same thing!

  1. With the const, the line is plain JavaScript. It runs on every render. When the parent passes Alice's contact, name is 'Alice' on the very next render.
  2. With useState, React uses the value in the parentheses on the first render only. The React docs say it plainly: this argument "is ignored after the initial render". When the parent passes Alice's contact, React ignores 'Alice' and hands back the stored 'Taylor'.

So the const is the one that follows the prop. A value that our code calculates during render from props or state is called a derived value. And putting a prop into state, as the second line does, has a name in the React docs too: mirroring props in state.

Why: Picture a contacts app with two buttons, Taylor and Alice, and a form under them that edits the selected contact. If the form mirrors the contact's name in state, the user clicks Alice, and the form still shows Taylor. The user trusts the form and clicks Save. Now Alice's contact holds the name Taylor, and the Console never said a word.

The Words of This Lesson

Here are the words this lesson builds on. Three are reminders, and one is new:

KEY DEFINITION

The starting value of useState. REVIEW useState('John') gives the state variable its first value, 'John'; React uses that value once, when the component first appears, and on every later render it returns the value it stored, which only the setter can change (Lesson 12).

KEY DEFINITION

State at a place in the tree. REVIEW React keeps the state of a component as long as the same component renders at the same place in the tree; when a different key appears at that place, React throws the old component and its state away and builds a new one (Lesson 25).

KEY DEFINITION

A derived value. REVIEW A derived value is a value your code calculates during render from data the component already has, such as the full name John Smith built from the first name John and the last name Smith; it needs no state, because the component body calculates it again on every render (Lesson 22).

KEY DEFINITION

Mirroring props in state. NEW Mirroring props in state means copying a prop into a state variable, as in useState(contact.name); the copy holds the value of the first render, so when the parent passes a new value, the state variable keeps the old one (Lesson 80).

Where Readers Usually Go Wrong

Readers read useState(contact.name) as "a state variable that follows contact.name". React reads it as "the first value of this state variable". React uses that first value once, when the form first appears, and never again.

Three Ways to Make the Form Follow the Contact

The React docs give three ways to fix this. Each one fits a different kind of value:

  1. Derive it during render. Read contact.name directly, with no state. This fits every value the user does not edit, such as the heading.
  2. Reset the form with a key. Write key={contact.id} on the form's tag. Each contact then gets a new form, with state that starts from that contact. This fits a form whose whole state belongs to one contact, such as the text the user types in the Name field. It is the docs' first choice for a reset.
  3. Adjust state during render. Keep the previous contact.id in state, and call the setters during render when it differs from the new one. This fits the rare case where part of the state must start over and the rest must stay. The docs say that "most components shouldn't need it".

Developers often reach for a fourth way, and it is not a good one: an Effect that calls setName(contact.name) whenever contact changes (Lesson 34). This lesson shows it next to the other three, so you recognize it and know what it costs.

The Rule of Thumb: calculate it, or reset it with a key

Ask one question about every value that comes from a prop: can my code calculate it from the prop? If yes, read the prop during render, with no state. If the user types it, it is state, and a key makes it start over for each contact.

PRINCIPLES

React uses the value inside useState only on the first render, so a copy of a prop stops following the prop. Five principles follow:

  1. Principle 1: A copy in state keeps the first value. useState(contact.name) stores 'Taylor'. After the click on Alice, React ignores 'Alice'.
  2. Principle 2: Derive what you can calculate. The heading reads contact.name during render, with no state, so it shows Alice right after the click.
  3. Principle 3: An Effect fixes the copy one render late. The Effect runs only after React has already rendered the form with Taylor's name.
  4. Principle 4: A key gives each contact a new form. React treats Alice's form as a different component, so its useState reads Alice's name for the first time.
  5. Principle 5: A setter during render is legal inside an if. The form remembers the previous ID and resets the Name field only when the ID changes.

PRINCIPLE1useState(contact.name): the copy keeps the value of the first render

Principle 1

Mirroring Props in State: The Copy Keeps the First Value

Summary: When a component copies a prop into state with useState(prop), the state holds the prop's value from the first render only; when the parent passes a new value, the state variable does not change.

Description: React uses the value inside useState only when the component first appears. On every later render, React returns the value it stored. So a heading built from a copied prop keeps showing the first contact after the user picks another one. If you really want to ignore later values, say so in the prop's name: initialName or defaultName.

When a copy in state is what you want

Sometimes ignoring later values is the goal. The React docs say: "Don't put props into state unless you specifically want to prevent updates." When you do want that, name the prop so every reader knows it. The docs' convention is to start its name with initial or default:

Our heading only shows the contact's name, so it has no reason to ignore updates. The docs' page Thinking in React gives the rule: data passed in from a parent through props is not state.

The React docs list three gains when you calculate during render: the code is faster, simpler, and less error-prone. There is one state variable fewer, and no second copy that can disagree with the first.

What if the calculation is really slow? Then you cache it with useMemo instead of copying its result into state (Lesson 56). But the docs add that "unless you're creating or looping over thousands of objects, it's probably not expensive."

App already follows the same rule. It keeps selectedId in state and finds the contact during render (Lesson 22). It does not keep the whole selected contact object in state. A stored object would be one more copy: after Save renames a contact in contacts, the stored object would still hold the old name.

PRINCIPLE3useEffect that copies the prop: the form renders once with the old name, then again

Principle 3

Copying in an Effect: The Copy Arrives One Render Late

Summary: When an Effect calls setName(contact.name) after contact changes, the component and its children first render and commit with the stale name, then React runs the Effect and renders everything again.

Description: Effects run after the commit. By the time the Effect runs, React has already rendered the whole form with Taylor's name and put it in the DOM. The Effect then starts a second render. Each new piece of state needs its own setter call in the Effect, and a forgotten one leaves that field on the old contact.

Why the form renders with Taylor first

The render right after the click still uses Taylor's name. The Effect runs only after React has put that render on the page. Here is what happens:

  1. App renders with Alice's contact.
  2. EditContact renders. The name in state is still 'Taylor', so the Console shows render Taylor.
  3. React commits that render to the DOM: the heading says Editing Alice, and the field still holds Taylor.
  4. React runs the Effect, because contact changed. The Effect calls setName('Alice').
  5. EditContact renders again with Alice's name, and the Console shows render Alice. React commits the field with Alice.

No click caused the second render. The setName call inside the Effect caused it.

Can the user see Taylor for a moment? Sometimes. After a click, React runs the Effect before the browser paints the screen. But the React docs say that even then, React "may allow the browser to repaint the screen before processing the state updates inside your Effect." So for one frame, the field can show Taylor under the heading Editing Alice.

And even when the user never notices that frame, the cost is real. The form, and everything inside it, rendered once with a value that was already wrong. Then React did all of that work again. The React docs describe it this way: the component "and its children will first render with the stale value, and then render again."

The mistake: a second field that the Effect forgets

The Effect has to copy every piece of state by hand. Suppose the form later gets an Email field, with its own email state that starts from contact.email. The developer forgets to add setEmail(contact.email) to the Effect. After the click on Alice, the Name field holds Alice's name, and the Email field still holds Taylor's email.

The React docs warn about exactly this: "you'd need to do this in every component that has some state inside" the form. The lint rule set-state-in-effect reports a setter called directly inside an Effect. Its docs list deriving state from props in an Effect as the mistake (Lesson 34).

PRINCIPLE4key={contact.id}: every contact gets a new form with new state

Principle 4

Reset with a Key: A New ID Means a New Form

Summary: When the whole state of a component belongs to one item, give the component a key from that item; when the key changes, React treats it as a different component, builds new state from the new props, and re-creates its DOM.

Description: The form never has to notice that the contact changed. A new form runs useState(contact.name) for the first time, so the field starts from the selected contact in one render. Unsaved text in the old form is thrown away with it. This is the docs' first choice when state must start over for a new item.

✓ DO THIS
1<EditContact key={contact.id} contact={contact} onSave={handleSave} />
Alice gets a new form
✗ DO NOT DO THIS
1<EditContact contact={contact} onSave={handleSave} />
WRONG Alice gets Taylor's form, with Taylor in the field

Remember the key on list rows (Lesson 18)? It tells React which row is which. A key works on any component, not only in a list. Compare the form's tag with and without one:

The form's tag without a key and with key={contact.id}
1<EditContact contact={contact} />

2<EditContact key={contact.id} contact={contact} />

It may look the same, or work the same at first, but it is NOT the same thing! When the page opens, both show Taylor in the field. After the click on Alice, only the tag with the key shows Alice.

Why? Taylor's form now has the key 0, and Alice's form has the key 1. To React, those are two different forms (Lesson 25). The React docs say that a different key asks React "to treat two Profile components with different userId as two different components that should not share any state." On our page, those two components are Taylor's EditContact and Alice's EditContact.

So the form itself never has to notice that the contact changed. A new form runs useState(contact.name) for the first time, so it reads the new name. The very thing that broke Principle 1, "React reads the starting value only once", now works for us.

The key throws away unsaved text, and that surprises developers. Here is why, in order:

  1. The user types Tay in the field. That text lives in the state of Taylor's form, the one with the key 0.
  2. The user clicks Alice. At the same place in the tree, App now renders the form with the key 1.
  3. React sees a different key at the same place. It removes the old form together with its state, and builds a new one.
  4. The new form runs useState(contact.name) for the first time, with 'Alice'. The field holds Alice.
  5. The user clicks Taylor. React sees the key 0 where the key 1 was, removes Alice's form, and builds a new form for Taylor.
  6. That new form reads contact.name for the first time: the saved 'Taylor'. The Tay lived in the form that React removed in step 3.

The mistake: expecting the key to keep a draft for each contact

A developer adds key={contact.id} and expects each contact to keep its own unsaved text. It does not: when the user switches away from a contact, React throws that contact's form away.   1. Lift the drafts up into the parent, which the docs call "the most common solution" (Lesson 24).
  2. Render every form, and hide all the others with CSS.

Principle 5

Adjust State During Render: Only Inside a Condition, Only Your Own State

Summary: When only part of a component's state must change after a prop changes, keep the previous prop value in state and, during render, inside a condition that compares it with the new prop, call that component's own setters; React throws away that render's JSX and renders the component again at once, before its children.

KEY DEFINITION

Adjusting state during render. NEW Adjusting state during render means calling a component's own setter in its body, while it renders, inside an if that compares a stored previous value with the new prop; the React docs call it storing information from previous renders, and their page on Effects calls it adjusting the state directly during rendering (Lesson 80).

A set call during render: alone vs. inside an if

A setter called in the component body is usually a bug. Compare a set call alone and the same call inside an if:

A set call alone during render, and inside a condition
1setName(contact.name);
Alone: every render sets state, and every set starts another render
2if (contact.id !== prevId) { setPrevId(contact.id); setName(contact.name); }
Inside a condition: runs once per new contact

It may look the same, or work the same at first, but it is NOT the same thing!

  1. With the setter alone in the body, every render calls it. Every setter call during render makes React render the component again. That is an infinite loop: it never ends on its own. React stops it and throws an error.
  2. With the setter inside the if, the same block also calls setPrevId(contact.id). On the next render, prevId equals contact.id, the condition is false, and nothing is set.

The React docs give both rules at once. The set call "must be inside a condition like prevCount !== count". And "there must be a call like setPrevCount(count) inside of the condition. Otherwise, your component would re-render in a loop until it crashes."

Developers call such a condition a guard: it lets the set call run only when it must. The lint docs say the same thing next to their valid example: "This condition makes it valid."

Why render Taylor shows up, and costs nothing on the page

React throws away the render with Taylor's name before any child renders and before any change to the DOM. Here is what happens after the user clicks Alice:

  1. EditContact renders with Alice's contact. prevId is still 0.
  2. The condition is true, so setPrevId(1) and setName('Alice') run.
  3. The rest of the component body still runs. In this pass, the name in state is still 'Taylor', so the Console shows render Taylor. The docs say it directly: "The rest of your component function will still execute", and its result is thrown away.
  4. React throws that JSX away and runs EditContact again at once, before rendering any child and before touching the DOM.
  5. Now prevId is 1, so the condition is false. The name in state is 'Alice', and the Console shows render Alice.
  6. React renders the children and commits. The field holds Alice.

No click and no Effect caused the second pass. The setter calls during render caused it, and React ran it before the children.

Compare this with the Effect of Principle 3. There, React rendered the children with Taylor's name and committed them, then rendered everything again. Here, the children never see Taylor's name. The React docs explain why, with their own example of a list. At this point, React "has not rendered the List children or updated the DOM yet". So the children "skip rendering the stale selection value." The same holds for our form.

The docs also allow an early return; right after the set calls, when the condition sits below all the Hook calls. React then restarts the render sooner.

The React docs agree: "This pattern can be hard to understand and is usually best avoided. However, it's better than updating state in an effect." Two more limits

A set call during render has two more limits:

  1. Only the component's own state. The component that is rendering may set only its own state. The React docs: "If you update another component's state during a render, you'll see an error." React limits it to the same component "to avoid very slow cascading retries".
  2. No other side effects. Changing the DOM or setting a timeout stays in an event handler or an Effect, to keep components pure (Lesson 14).

Interview PrepFor the Interview

The Interview Question: How do you derive values during render, and when is adjusting state during render legal?

How to Answer Clearly in 30 Seconds

"React uses the value I give to useState only on the first render. The docs say it is ignored after that. So if I copy a prop into state, the copy goes stale when the parent passes a new value. That is mirroring props in state. The React docs give two main fixes, and a rare third:

  1. Derive during render: if a value can be calculated from props or state, I calculate it in the component body as a const. It is right on every render, and nothing can get out of sync.
  2. Reset with a key: if the state is a draft that belongs to one item, such as a form, I write key={item.id} on the component. A new ID makes React build a new component with fresh state.
  3. Adjust during render: in the rare case where only part of the state must reset, I keep the previous prop value in state. During render, inside a condition that compares it with the new prop, I call my own setters. That is legal only inside the condition, with the previous value updated in the same block, and only for the component's own state. React throws away that render and retries before rendering the children.

I avoid an Effect that copies the prop into state, because the component and its children first render with the stale value."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Is it ever right to copy a prop into state?"
    Yes, when you want to ignore later values on purpose. React's docs: "Don't put props into state unless you specifically want to prevent updates." Then name the prop initialName or defaultName, so the caller knows that only the first value counts. A form draft is the common case: it starts from the saved value, and the key makes each item start its own draft.
  2. "Why not just sync the state with useEffect?"
    Because Effects run after the commit. The render that received the new prop has already used the old state, and React has already put it in the DOM. The Effect then sets state and starts a second render, so the component and all its children render twice for each change. Every piece of state needs its own line in the Effect, and a forgotten one stays stale. The lint rule set-state-in-effect reports a setter called directly in an Effect.
  3. "Why does React allow a set call during render, and why only for the component's own state?"
    Because React can retry that one component cheaply. When a component sets its own state during render, React throws away the JSX it returned and runs it again at once. That happens before any child renders and before any DOM change, so the children never render the stale value. If a component set another component's state during render, React would have to go back and render other parts of the tree again. The docs say React limits it "to avoid very slow cascading retries", and you see an error instead. Without a condition, even the component's own set call loops. React stops it with the error Too many re-renders.
