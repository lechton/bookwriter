What the React Lints Catch, and Why a Silenced Lint Still Ships the Bug

Interview Question❱❱❱ ADVANCED

What do the React Hooks and Compiler lint rules catch, and why should they never be disabled?

What does a React lint warn you about, and what happens when someone turns it off?

Overview · Two Ways Side by SideAChanging the codevsBA suppression commentBoth clear the warning, only the change removes the bug

Your editor can underline a line of code before you ever open the page, the way a spell checker underlines a typo. The React lints underline every line that breaks a rule of React, and each underline names a bug the user will meet later. A comment that turns a lint off removes the underline, not the bug, and it keeps the lint off for every later change to that line.

Start with plain JavaScript. You declare a variable and never use it:

Plain JavaScript: a variable nobody reads
1let total = 0;
ESLint underlines total: it is declared and never read

The program that underlines it is ESLint. It reads your files in the editor, without running them, and checks every line against a list of rules. This rule is called no-unused-vars. Each rule is one check, and React's docs call each check a lint.

Now the shortcut every developer finds sooner or later. You can tell ESLint to skip one rule on one line, with a comment:

Plain JavaScript: the same line with a suppression comment
1let total = 0;
Eslint-disable-line no-unused-vars

The underline is gone. But look at the code: nothing changed. total is still declared, and still never read. The comment did not fix the problem. It only told ESLint to stop talking about it.

React adds its own rules to ESLint, in one package named eslint-plugin-react-hooks. They work exactly like no-unused-vars, with one big difference: the cost. An unused variable costs nothing on the page. A line that breaks a rule of React always ends as a bug on the page. Think of a chat stuck in the wrong room, a time that moves by itself, or a page that never loads.

KEY DEFINITION

What is ESLint, and what is a lint? REVIEW ESLint is a tool that reads your code in the editor and in the terminal, without running it, and marks each line that fails one of its checks. React's docs call each check a lint. The report arrives before the page runs, so it arrives before any user meets the bug (Lesson 82).

KEY DEFINITION

What is a suppression comment? REVIEW A suppression comment is a comment such as // eslint-disable-line react-hooks/exhaustive-deps at the end of a line. It tells ESLint to skip that one rule on that one line. Developers often write the same thing as an eslint-disable-next-line comment on the line above. The comment changes no code, so whatever the lint reported is still in the file (Lesson 36).

The Same Comment in a Chat, a Month Later

Picture a chat app such as Slack. On the day it ships, it has one room, general, and a heading that reads Welcome to the general room!. The chat connects to the server for that room in an Effect.

The linter asked the developer to list roomId in the dependency array of that Effect. The developer thought the lint was wrong, because the room never changed, and wrote a suppression comment on that line.

A month later, a teammate adds a room picker above the heading. The user picks travel, and the heading changes. But the chat is still connected to general:

So the page lies. The heading names one room, and the connection belongs to another. In a real chat, every message the user reads would still come from general.

No line of the teammate's code is wrong, and the editor showed no warning anywhere. The bug came from one comment, written a month earlier. That comment still sat on the dependency line, so the lint stayed off, and nobody was told that roomId now changes.

Remember the one idea of this lesson: each React lint names a bug the page will show later. A suppression comment removes the message, not the bug, and it keeps removing the message for every later change on that line.

Five Lints, Five Bugs on the Page

Every React lint that a team turns off leaves its own bug behind, and the user sees each one:

  1. With exhaustive-deps off, the heading says travel, and the chat stays connected to general. Principle 2 builds this case.
  2. With rules-of-hooks off, the page goes blank after the user's click, and React reports "Rendered fewer hooks than expected" (Lesson 38).
  3. With set-state-in-render off, the page never loads, and React reports "Too many re-renders" (Lesson 80).
  4. With purity off, a time on the page moves each time the user types, or, with the React Compiler on, it stops moving (Lesson 63).
  5. With refs off, a count on the page stays on an old number (Lesson 30).

The Rule of Thumb: to silence a lint, change the code

When a React lint marks a line, the only fix is to change the code until the lint passes. Never change the lint.

React's docs say it twice. In general: "We recommend never suppressing the linter." And for the dependency array: "To change the dependency list, change the code."

That takes four steps:

  1. Read the report. It names the value or the line that breaks a rule, such as roomId.
  2. Ask what the page will do because of it. A chat stays in the wrong room, a time moves, or a page never loads.
  3. Change the code so the rule holds. Add the value to the array, move a setter into the event handler, or read the clock once.
  4. Leave no suppression comment behind. The lint then stays free to warn the next person who edits that line.

At work, developers really choose between four answers to a lint report. Only the first one fits every report:

  1. Change the code until the lint passes. This fits every report.
  2. Leave the report visible, and fix it later. This fits a compiler-powered report in code that already exists. React's docs say the compiler skips a component it can see breaking a rule, and that "you don't need to fix all violations immediately".
  3. Take one component out of the compiler with "use no memo", for a while. This fits a component that breaks after the team turns the compiler on (Lesson 63). React's docs say: "You should fix the underlying issue and remove the directive once resolved."
  4. Suppress the lint with a comment. This fits nothing.

A senior developer also knows the five classic mistakes:

  1. Thinking a lint is about style, like spaces or quotes. React's docs say the opposite about these rules: "They are essential and catch the most severe bugs early."
  2. Thinking a suppression covers only today's bug. It also covers every later edit to that line, often written by someone else.
  3. Thinking [] means "run once". Then a lint that asks for a prop looks wrong (Lesson 35).
  4. Thinking the compiler-powered lints matter only with the React Compiler. The linter works without the compiler.
  5. Thinking a compiler-powered report must be fixed at once, or else the rule must go. React's docs say the report can wait: "Address them at your own pace." The rule stays on.

PRINCIPLES

The React lints read the code before it runs and name the bug the page will show. One preset turns them all on, and each lint guards a different rule of React. Four principles follow:

  1. Principle 1: One line in the config turns on every React lint. The recommended preset turns on the Hook lints and the render lints, with or without the React Compiler.
  2. Principle 2: A suppression comment keeps the lint off for good. When a later change makes roomId change, nobody is told, and the Effect keeps the old room.
  3. Principle 3: purity, refs, and set-state-in-render check render code. A clock read, a ref read, and a setter call during render each show a different bug.
  4. Principle 4: A compiler-powered report can wait, but the rule stays on. Turning the rule off hides today's report and every later one.

KEY DEFINITION

What is a preset? NEW A preset is a ready-made list of rules that a package turns on together, so the team does not have to name each rule by hand. reactHooks.configs.flat.recommended is the preset of eslint-plugin-react-hooks: one object in the config, and every React lint is on (Lesson 95).

Two kinds of lints in one preset

The preset holds two kinds of lints. Both report breaks of the rules of React, and both look the same in the editor: a mark on the line and a message. The one difference is what each kind reads:

  • The fundamental lints, rules-of-hooks and exhaustive-deps, read where Hooks are called and which values go in a dependency array. React's docs call them the lints for "fundamental React patterns". They have guarded React code for years (Lessons 35 and 38).
  • The compiler-powered lints, such as purity, refs, set-state-in-render, and immutability, read all the code that runs while React renders the component, such as a clock read in the JSX or a setter called in the body. They come from the checks of the React Compiler. The React Compiler 1.0 post on React's blog calls them "compiler-powered lint rules", and they now ship inside the same package.

KEY DEFINITION

What is the React Compiler? REVIEW The React Compiler is a build tool that rewrites your components so React can reuse their earlier output instead of running the same work again. Before it rewrites a component, it checks that the component follows the rules of React. When it reuses an output that should have changed, a value on the page can freeze. "use no memo" as the first line of a component tells the compiler to skip that one component (Lesson 63).

The compiler-powered lints work without the compiler

The compiler-powered lints report breaks even in an app that never installs the React Compiler. The name suggests the opposite, so here is a team that shows it:

  1. The team installs eslint-plugin-react-hooks and adds the recommended preset.
  2. The team never installs the React Compiler.
  3. A developer writes Date.now() inside the JSX of a component, and the purity lint still marks the line.

The lints take their checks from the compiler, but they do not need the compiler to run. The React Compiler 1.0 post says it directly: "The linter does not require the compiler to be installed, so there's no risk in upgrading eslint-plugin-react-hooks." So every React app gets these reports, with or without the compiler.

When the team runs ESLint in the terminal, the report for that Date.now() call looks like this (Lesson 63):

ESLint in the terminal
1error Error: Cannot call impure function during render ... react-hooks/purity

The page and the Console do not change at all. The linter runs in the editor and in the terminal, never in the browser.

Where react-hooks/ in front of each rule comes from

Every report ends with a name such as react-hooks/purity. ESLint builds that name in two steps:

  1. The package is named eslint-plugin-react-hooks, so the short name of the plugin is react-hooks.
  2. ESLint writes the short name, then a slash, then the name of the rule.

The name reactHooks in the config file is a different thing. It is only the local name that our config file gives the package in its import line. We could call it anything.

A team that keeps two packages

Some teams still carry an older second package. The compiler lints first came in a package of their own, eslint-plugin-react-compiler. Here is what often happens:

  1. In 2024, the team set up the compiler lints with that second package.
  2. Later, a developer upgrades eslint-plugin-react-hooks and keeps both packages in the config.
  3. The React Compiler 1.0 post says the second package is no longer needed: "If you have already installed eslint-plugin-react-compiler, you can now remove it and use eslint-plugin-react-hooks@latest."

So the config needs one package, as in the file above.

In an interview, say where these lints run and which presets hold them. React's docs say the plugin "helps you catch violations of React's rules at build time", and the editor setup page says linters find problems "as you write". The compiler-powered rules ship in two presets of the same package, recommended and recommended-latest.

KEY DEFINITION

What is a dependency array? REVIEW The dependency array is the second argument of useEffect, the list of values the Effect reads. After every render, React compares each value in the list with its value from the render before. If one changed, React runs the cleanup of the old Effect and then runs the Effect again. If nothing changed, React does nothing. With [], the list is empty, so nothing can ever change, and the Effect runs only after the first render (Lesson 35).

Why the heading moves and the connection does not

The heading and the connection read the same roomId, and yet they disagree. The reason is when each one runs. The heading is JSX, so React makes it again on every render. The connection is made in the Effect, so React makes it only when the Effect runs.

Here is what React does after the user picks travel:

  1. React renders ChatRoom again with the new room, so the heading reads travel.
  2. React compares the new array [] with the old array []. There is nothing to compare, so nothing changed, and React does not run the Effect again (Lesson 35).
  3. The connection made on the first render, with 'general', stays open.

And why did the editor stay quiet on day 30? The suppression comment sits on the line with []. The teammate's change did not touch that line, so the comment still applies to it. ESLint has no idea that roomId became a state variable in another file. It just obeys the comment.

React's docs name this exact cost: "You will no longer get such reminders for any future edits to that Effect if you disable the linter. This leads to bugs."

PRINCIPLE3purity, refs, and set-state-in-render: the editor marks impure render code before the page runs

Principle 3

Pure Render: purity, refs, and set-state-in-render Flag Render Code Before It Runs

Summary: Keep render pure: read a changing value such as the clock once with an initializer function, keep what the page shows in state instead of in a ref, and call setters in event handlers instead of in the component body.

Description: The three newer lints check the code that runs while React renders the component. A clock read in the JSX shows a new time on every render. A ref read in the JSX shows the number of the last render. A setter called in the body asks for another render forever. Each line looks harmless on the first load, and the lint marks it before any user meets the bug.

WRONG set-state-in-render: asks for another render during this one

They look like three unrelated habits. They are three forms of one mistake. Remember what a render is: React calls your component function, from the first line to the return. It does that on the first load, and again every time state changes, for example on every letter the user types in a field. Every line in the body runs again each time.

KEY DEFINITION

What is a pure render? REVIEW A render is pure when the same props and state always give the same JSX, the way 2 + 3 always gives 5. React may call your component as often as it needs, so the component body must not read anything that changes by itself, such as the clock, and must not change anything while it runs, such as state (Lesson 14).

Each of the three lines breaks that rule in its own way, and each one shows a different bug to the user:

  1. Date.now() in the JSX reads the clock, so the time on the page moves each time the user types.
  2. sentRef.current in the JSX reads a ref, so the count on the page stays on an old number.
  3. setUnread(0) in the body changes state, so the page never loads.

Developers usually go wrong by trusting the first load. A line that shows no error on the first load looks fine. React's docs warn about exactly this for refs: "your component might still work".

The three lints, and what each one reports

All three lints come from the recommended preset of Principle 1:

  • purity reports a call during render to a function that returns a different value each time, such as Date.now(), Math.random(), or performance.now(). It knows these calls by name. In version 7.1.1 of the package, it does not report new Date() or crypto.randomUUID(), although each one also gives a new value on every call. That is why our chat reads the clock with Date.now().
  • refs reports a read or a write of ref.current during render. It finds refs made with useRef, refs passed to a JSX ref, and any name that ends in Ref.
  • set-state-in-render reports a setter called during render with no condition. React's docs say such a call "creates an infinite loop that crashes your app".

Why a report can wait

A report can wait because the compiler checks the same rules before it compiles. React's docs say that when the compiler finds a break, "it automatically skips over those components and hooks, while keeping the rest of your app compiled". The compiler installation page says the same about the lint: "When the ESLint rule reports an error, it means the compiler will skip optimizing that specific component or hook. This is safe".

So a skipped component runs exactly as the team wrote it, the way it ran before the compiler. The team can fix the reports one by one, and each fix lets the compiler compile one more component.

A report is not always a skip

Beware! The lint can see a break that the compiler lets through. Here is one such case (Lesson 63):

  1. The purity lint reported Date.now() in a Message component.
  2. The compiler, in version 1.0.0, still compiled Message. Its own check for impure functions, validateNoImpureFunctionsInRender, is off by default.
  3. The compiled component reused its output, and its "min ago" label stopped moving.

So a report is not a promise that the compiler skipped the component. With the lint on, the team still sees the line and can fix it. With the lint off, the team sees neither the report nor the frozen label, until a user does. React's debugging page names this case: "the compiler mistakenly compiled a component it should have skipped."

Turning the rules off to clean the editor

Here is what a team often does when it turns the compiler on in an existing app:

  1. The editor shows many compiler-powered reports.
  2. To clean the editor, a developer turns a compiler-powered rule off in the ESLint config.
  3. The purity report on the Opened at line is gone, and so is the report for every new line written after that day.
  4. With the compiler on, a time label that reads the clock during render can stop moving (Lesson 63).
  5. React's debugging page sends the team back to the lint, "Check with ESLint", and the lint is off.

Second, runtime problems with the compiler come from breaks "that the compiler couldn't detect", and the lint is how the team sees the breaks it can detect. Interview PrepFor the Interview

The Interview Question: What do the React Hooks and Compiler lint rules catch, and why should they never be disabled?

How to Answer Clearly in 30 Seconds

"Every React lint lives in one package, eslint-plugin-react-hooks, and its recommended preset turns them all on. They work even when the app does not use the React Compiler. Two kinds of lints catch two kinds of bugs:

  1. The fundamental lints read Hook calls and dependency arrays. rules-of-hooks keeps the Hooks in the same order on every render, and exhaustive-deps keeps the dependency array equal to what the Effect reads.
  2. The compiler-powered lints read the code that runs during render. purity catches values that change on every call, such as Date.now(). refs catches ref.current read during render. set-state-in-render catches a setter that loops forever. All three guard one rule: render must be pure.

They should never be disabled, because a suppression removes the message, not the bug. It also hides every later change on that line. A chat that suppressed exhaustive-deps on day 1 stays in the old room on day 30, after a teammate adds a room picker in another file. A compiler-powered report in old code may wait, but the rule stays on."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Our team silences the exhaustive-deps warning to ship faster. What classes of bugs does that invite?"
    Three classes. First, a stale value today: the Effect reads an old prop or state, such as a muted setting that never updates (Lesson 36). Second, a stale value later: when a teammate makes a value change, such as roomId with a room picker, the Effect keeps the old one, and the editor says nothing because the comment still covers that line. Third, a bug that hides in the wrong file: the developer who meets it searches the file that changed, not the file with the comment. React's docs say to treat this lint "as a compilation error", and to "start by searching for linter suppressions" when an Effect misbehaves. To change the dependencies, change the code.
  2. "What do the newer lints, purity, set-state-in-render, and refs, guard against?"
    They guard the rule that render must be pure. purity reports calls such as Date.now(), Math.random(), or performance.now() during render. Without the compiler, the page shows a new value on every render. With the compiler, the value can freeze. refs reports a read or a write of ref.current during render: a ref change renders nothing, so the page shows the number of the last render. set-state-in-render reports a setter called during render with no condition: every render asks for another one, and React stops with "Too many re-renders". Each fix moves the work out of render: an initializer function for the clock, state for what the page shows, and the event handler for the setter.
  3. "The React docs say compiler reports can be fixed at our own pace. Why not just turn those rules off until we are ready?"
    Because "at your own pace" is about fixing, not about turning the rule off. While the rule is on, the team sees every old report, and every new break as someone writes it. The compiler skips the components it sees breaking a rule, so the old code keeps working as written. When the rule is off, the editor is clean and the team sees no new break. Meanwhile, the compiler can still compile a component whose break it cannot see, and a "min ago" label freezes (Lesson 63). For one component that breaks under the compiler, "use no memo" is the temporary answer, removed once the code is fixed.
