Keeping Context Fast When Its Value Changes

Interview Question❱❱ MORE

How does context propagation cause re-renders, and how do you keep it fast?

Why does a message that uses only the user re-render when the theme changes?

Overview · Two Ways Side by SideAOne for Every ValueAppContextvsBOne Context per ValueReact compares the whole value, never the part a component uses

A context hands one value from a provider to every component below it that calls useContext, so the theme and the signed-in user reach the whole page without props. When the provider gets a different value, React re-renders every component that reads that context, even a component whose part of the value did not change. So one theme click can re-render every message row, until you give each value its own context and keep an object value the same object with useMemo.

In React, some values are needed all over the page: the theme, the signed-in user, the language. Passing them through every component as props is prop drilling, so we put them into a context instead (Lesson 28). A provider at the top holds the value, and any component below it reads the value with useContext. You know that part. This lesson is about what happens when the value changes.

Here is the one sentence to keep in mind for the whole lesson: React compares the whole value of the provider, never the part a component takes out of it. When the provider gets a different value, every component that reads that context runs again.

Take a chat app. Every message row reads the signed-in user, so it can show You next to your own messages. The same app has a Toggle theme button that switches the page between light and dark. A developer puts both values into one context, because one provider is less code. Ask yourself: when the user clicks Toggle theme, which message rows re-render? All of them, though no row uses the theme.

Why: The provider's value is one object that holds the theme and the user. A theme click builds a new object with the new theme in it. React sees a different object, so it re-renders every component that reads the context, every message row included. The rows show the same text as before, so nothing changes on the screen. The cost is time: on a chat with hundreds of messages, React calls hundreds of components that have nothing new to show, and the page turns dark only after a delay.

The Smallest Page That Shows It

Two reminders first, because this lesson stands on them.

KEY DEFINITION

What is a context? REVIEW A context lets a component far down the page read a value without props carrying it through every component in between.

You create it with createContext. A provider, such as <AppContext value={...}>, holds the value. Any component below the provider reads it with useContext(AppContext).

Something that can be tricky: useContext always returns the whole value of the closest provider above the component (Lesson 28).

KEY DEFINITION

What does Object.is say about objects? REVIEW Object.is is the check React uses to ask: "Is this the same value I already have?"

For a string or a number, it compares the values. Object.is('Taylor', 'Taylor') is true.

For an object, it never looks at the fields. It asks only: "Is this the very same object?" Two objects built on two renders are two different objects, even with the same fields inside. Object.is({ a: 1 }, { a: 1 }) is false, exactly like { a: 1 } === { a: 1 } in plain JavaScript (Lesson 56).

What useContext Really Hands Over

Message never uses the theme, and React re-rendered it anyway. Here is why:

  1. useContext does not hand Message only currentUser. It hands over the whole value of the provider, the object with theme and currentUser inside.
  2. The curly braces in const { currentUser } take one property out of that object, but only after React has handed the whole object over.
  3. After the click, AppProviders runs again and builds a new object, now with theme: 'dark' in it.
  4. React compares the old object with the new one using Object.is. They are two different objects.
  5. So React re-renders every component that reads AppContext, and Message is one of them.

React's docs say it in two sentences: "React automatically re-renders all the children that use a particular context starting from the provider that receives a different value. The previous and the next values are compared with the Object.is comparison."

Now compare two ways to read the same context. The first takes only the user out of it. The second takes both values:

Taking one property out of AppContext, and taking both
1const { currentUser } = useContext(AppContext);
Re-renders when the theme changes
2const { theme, currentUser } = useContext(AppContext);
Re-renders when the theme changes

For re-renders, yes, these two lines are the exact same thing! Both read the same whole value, so both re-render on every click on Toggle theme.

This is where developers usually go wrong. Taking only currentUser out of the context looks like depending only on currentUser. It may look the same, but it is NOT the same thing! Two separate things happen:

  1. What the component takes out. Only the properties it names, here currentUser.
  2. What React compares. The whole value, the old object against the new one.

React's docs give this its name: useContext lets a component "read and subscribe to context". To subscribe means that React notes the component as a reader of that context, and calls it again every time the provider gets a different value. The component subscribes to the whole value, not to the property it takes out.

What It Costs on a Real Chat

On a real chat, the list holds hundreds of messages, and each row reads the signed-in user to show You. With the theme and the user in one context, every click on Toggle theme re-renders every row.

The user sees no wrong text. The rows return the same JSX, so React changes nothing on the screen (Lesson 54). The cost is time. React calls hundreds of components that have nothing new to show, and with many or slow rows, the page turns dark only after a delay. React's docs are honest about the size of this: "In smaller apps, this is not a problem." On a long chat, it is.

Developers usually go wrong in four places, and the principles of this lesson fix them one by one:

  1. They think a component that takes one property out of a context re-renders only when that property changes.
  2. They split the context in two, and every row still re-renders, because the new context's value is an object written inside the providing component.
  3. They wrap that object in useMemo, while the providing component writes the rows' tags itself, so the rows re-render anyway as its children.
  4. They wrap the rows in memo and expect it to stop the context.

The Rule of Thumb: is the provider's value the same value?

Ask one question about every click: does the provider get the same value as last time, by Object.is? If not, every component that reads that context re-renders.

When a context change re-renders many components, you choose between four ways:

  1. Leave it, and measure first. This fits a small app where the user feels no lag (Lesson 54).
  2. Separate contexts for values that change at different times. This fits values that different components read, such as the theme and the current user. Principle 2 shows it.
  3. useMemo on an object value. This fits a context that must carry a value and a function together, such as the user and the setter that changes it. Principles 3 and 4 show it.
  4. Split the component in two. An outer component reads the context and passes the part it needs to an inner component wrapped in memo. This fits a component that needs only one part of a context that changes for other reasons. Principle 5 shows it.

PRINCIPLES

React compares the whole value of the provider, never the part a component takes out. Five principles follow:

  1. Principle 1: A Context Change Re-renders Every Component That Reads It. A theme click re-renders every message, while ChatRoom in the middle is skipped.
  2. Principle 2: Two Contexts Keep the Theme Away from the Messages. With the theme and the user in separate contexts, a theme click re-renders only the components that read the theme.
  3. Principle 3: An Object Written in the Provider Is New on Every Render. Putting the user and its setter into one object makes every message re-render on a theme click again.
  4. Principle 4: useMemo Keeps the Object the Same. The provider then gets the same object until currentUser really changes.
  5. Principle 5: Split the Component in Two So memo Can Work. An outer component reads the context and passes a prop to an inner component wrapped in memo.

Here is what React does after the click, in order:

  1. The user clicks Toggle theme, and setTheme('dark') asks React to re-render AppProviders.
  2. React calls AppProviders, which writes { theme, currentUser } again. This is a new object, with theme: 'dark'.
  3. React compares the old value with the new one using Object.is. They are different objects.
  4. children is the same as last time, because App did not run again. So React does not call ChatRoom as a child, and the Console has no ChatRoom rendered line (Lesson 58).
  5. React goes down from the provider and re-renders every component that reads AppContext: TopBar and the three messages.

You already split a reducer's state and its dispatch into two contexts the same way (Lesson 29). What is new here is the reason: the two values change at different times.

The messages came back because of the object, not because of the theme. Here is what React does after the click:

  2. AppProviders writes { currentUser, setCurrentUser } again. That builds a new object, though currentUser is still 'Taylor' and setCurrentUser is the same function.

A developer new to this thinks: "The object holds the same user and the same setter, so it is the same value." It may look the same, but it is NOT the same thing! Same contents and same object are two separate things. You know this from plain JavaScript:

Interview PrepFor the Interview

The Interview Question: How does context propagation cause re-renders, and how do you keep it fast?

How to Answer Clearly in 30 Seconds

"A component that calls useContext subscribes to the whole value of the closest provider above it. When that provider gets a different value, compared with Object.is, React re-renders every component below it that reads the context, even when the part a component uses did not change. That is what propagation means here: the change travels down from the provider to every component that reads it, and it passes through the components in the middle without re-rendering them. To keep it fast, I first measure that it matters, and then I use four tools:

  1. Separate contexts: values that change at different times, such as the theme and the current user, go into different contexts.
  2. A stable value: an object written in the provider is new on every render, so I wrap it in useMemo, and I wrap any function I write inside it in useCallback.
  3. children in the provider: the provider takes the page as children, so its own state change does not re-render the whole page as its children.
  4. Split in two: when a component needs only a part of a context, an outer component reads the context and passes that part as a prop to an inner component wrapped in memo."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Does memo stop a component from re-rendering when a context it reads changes?"
    No. memo compares only the props a component gets from its parent, and a context read inside the component is not a prop. React's docs say: "Even with memo, your component will re-render if its own state changes or if a context that it's using changes." To get the effect people expect, I split the component in two. The outer component reads the context, and the inner component, wrapped in memo, gets the part it needs as a prop.
  2. "I split my context in two, and every row still re-renders on a theme click. Why?"
    Most often, the second context carries an object written inside the providing component, such as value={{ currentUser, setCurrentUser }}. Every render of the provider builds a new object, and Object.is compares objects by identity, so the rows re-render as they did before the split. Wrapping the object in useMemo with [currentUser] fixes it. Another fix is to keep the value and the function that changes it in two separate contexts, as React's docs do with TasksContext and TasksDispatchContext.
  3. "I wrapped the context value in useMemo, and nothing changed. What went wrong?"
    The providing component probably writes the rest of the page in its own code. Then a state change in it re-renders every component it writes, as its children, whatever the context does. The stable value pays off only when the components in the middle are skipped, either because the provider takes them as children or because they are wrapped in memo. And in a small app, none of this is a problem. React's docs say so, and <Profiler> shows whether it matters in your app (Lesson 54).
