Why Every Row in a List Needs a key from the Data

Interview Question❱ CORE

How do you render a list from an array, and why does React demand a stable key on every item?

When a new email arrives at the top of the list, how does React know which row is which?

Overview · Two Ways Side by SideAThe IndexvsBAn ID from the Data as the keyThe index follows the position, the ID follows the email

First, let's set the two building blocks this lesson stands on:

KEY DEFINITION

State and its setter. REVIEW In plain JavaScript, you just write emails.unshift(newEmail), and the job is done. Not in React. A value that must survive between renders lives in state, and state always comes as a pair: the state variable and its twin setter, born together in one line. So far, the state variable held a number, such as score in const [score, setScore] = useState(0), or an object, such as item (Lesson 17). In this lesson it holds an array, a whole list of emails: const [emails, setEmails] = useState(initialEmails). Here emails is the state variable, and setEmails is its twin setter. React holds this array for your component between renders. When a new email arrives, you do not push it into emails. You call the matching setter with a NEW array, setEmails([newEmail, ...emails]). The three dots you used on objects in Lesson 17 do the same job inside square brackets: they copy every old email into the new array, right after newEmail. So the new email comes first, and every old email follows in its old order. Lesson 19 covers every recipe for arrays in state. Here is the catch: emails does NOT change on that line. Believe it or not, React first calls your component AGAIN, and only in that new render does emails hold the new list, with the new email at the top (Lesson 12).

KEY DEFINITION

A commit. REVIEW OK, we have seen that after a setter call, React calls your component AGAIN and gets back the new JSX. Then comes the commit: React puts the result into the real page. Pay attention here: React does NOT throw the old page away and build a new one. It compares the new JSX with the JSX of the last render, position by position, and when the same tag sits in the same position, it keeps the very same DOM node and changes only what is different, such as one line of text. Why does that matter? Because some things live inside the DOM node itself, and React never wrote them there. When the user ticks a checkbox that has no checked prop, the browser stores the tick in that checkbox's DOM node, just as a text box stores what the user types. Here is the good news: since React keeps the node, the tick survives every render. Here is the catch: the tick stays with the node, and React decides which node goes where. Keep this in mind, because in a list that changes, that decision is exactly where things go wrong (Lesson 13).

KEY DEFINITION

Rows from an array with map. NEW So far, every list on our pages was written by hand: <li>Dentist</li>, <li>Mom</li>, <li>Bank</li>, one tag per line. Cool for three rows... but a real inbox shows whatever the server sends: three emails today, two hundred tomorrow. Nobody writes those tags by hand. You keep the data in an array, and you let JavaScript build the rows. That is the job of map. Look: const senders = ['Dentist', 'Mom', 'Bank'], then senders.map(sender => <li>{sender}</li>). map takes the array, calls your arrow function once for EVERY item, from the first to the last, and collects what the function returns into a NEW array: [<li>Dentist</li>, <li>Mom</li>, <li>Bank</li>]. Same length, same order. And senders itself? Untouched. Who fills sender? map does: 'Dentist' on the first call, 'Mom' on the second, 'Bank' on the third. Now put that call inside the curly braces of the list: <ul>{senders.map(sender => <li>{sender}</li>)}</ul>. React receives an array of JSX and renders every element in it, in order. Yes, it is the exact same page as the three tags written by hand! Here is the catch: as soon as the list appears, React prints an error in the Console, Each child in a list should have a unique "key" prop. The rows are on the screen, and yet React is not satisfied. Why React asks for a key, and what to put in it, is what this whole lesson is about (Lesson 18).

In plain JavaScript, when a new email arrives, you insert one new row at the top with list.prepend(row). Every old row, with its tick, stays where it is. The job is done.

React breaks this habit.

In React, you never insert a row. You hand React the whole new list, and React must work out by itself which old row is which.

KEY DEFINITION

A key. NEW OK, we have seen that map hands React a whole array of rows, and that during the commit React keeps a DOM node when the same tag sits in the same position. But a list changes: a new email arrives at the top, one is deleted, the list is sorted. After the change, React gets a whole new array, and it must answer one question for every row: "Which row of the last render is this one?" By default, React answers with the position: the first row of the new list is the first row of the old list, the second is the second, and so on. A key replaces the position with a name. You write it on the tag that map returns: <li key={email.id}>. Now the row is not "the first row" anymore. If the Dentist email carries the ID 101 in the data, its row is "email 101", wherever it sits. A key is a string or a number, and it must be unique among siblings: two rows of the same list never share a key, but two different lists may use the same keys. Pay attention here: the key is NOT on the screen. The user never sees 101, and the Elements panel shows no key attribute on the <li>. React's docs say that the key is "only used as a hint by React itself": React uses it to match each row of this render with a row of the last render. Here is the catch: when React finds a key it already knows, it keeps that row's DOM node, with everything inside it, such as a tick, and only updates what changed. So the key decides where the tick goes. Moral of the story: the key must name the email, not its place in the list (Lesson 18).

React's docs put the job of the key in one sentence: "Keys tell React which array item each component corresponds to, so that it can match them up later."

Why does React need this rule? There are two reasons:

  1. React keeps DOM nodes. During the commit, React reuses the nodes it already has and changes only what differs. To keep the right node with the right email, it must first match the rows. In the docs' words, "A well-chosen key helps React infer what exactly has happened, and make the correct updates to the DOM tree."
  2. Whatever lives inside a row goes with the match. A tick, typed text, or the state of a component stays with the row React matched. In the docs' words, "Even if the _position_ changes due to reordering, the key lets React identify the item throughout its lifetime."

React's docs give the rules of keys in two parts:

  1. Unique among siblings. In the docs' words, "Keys must be unique among siblings. However, it's okay to use the same keys for JSX nodes in _different_ arrays." In plain actions: two rows of the same list never share a key.
  2. Never changing. In the docs' words, "Keys must not change or that defeats their purpose! Don't generate them while rendering." In plain actions: the Dentist row has the same key on every render.

Beware! A key taken from the position follows the position, not the email: when a new email arrives at the top, every tick stays on its row number.

  6. With names, "delete the dentist letter" stays right, wherever the file moves. That is a key from the data.

Names by place are completely fine when files never move, arrive, or leave. React's docs give the example of a poem: "This is a rare case where index as a key is acceptable because a poem's lines will never reorder."

One new idea explains why:

KEY DEFINITION

The index vs. an ID from the data. NEW So, we have seen that every row needs a key, and that React matches rows by their key. Now the tricky part: what do you put in the key? map hands your arrow function a second argument, the position of the item in the array, which we name index: 0 for the first email, 1 for the second, 2 for the third. So many developers write emails.map((email, index) => <li key={index}>...</li>), and the Console error disappears. Cool... but is the list fixed? NO. React's docs say that the index is exactly "what React will use if you don't specify a key at all". key={index} only silences the error: the rows are still matched by position. Now compare key={email.id}: the key is 101 for Dentist, 102 for Mom, 103 for Bank, numbers stored in the data, and each number travels with its email. On the first load, both lists look exactly the same, and both Consoles are quiet. They are NOT the same thing! Let's catch it in action. The user ticks Dentist, the first row, and the browser stores that tick in the checkbox node of the first row. Then the user clicks Check mail, and Shop arrives at the top: Shop, Dentist, Mom, Bank. With key={index}, Shop now has key 0. Will Dentist keep its tick? NO! Why? Because React looks at key 0, finds the row it already had under key 0, keeps that DOM node, tick included, and only changes its text from Dentist to Shop. Dentist, now key 1, gets Mom's old unticked node. Mom, now key 2, gets Bank's old node. Bank, now key 3, gets a brand-new node. The tick stayed on the first row, and the first row now says Shop. Here is the good news: with key={email.id}, Shop arrives with a key React has never seen, 104. So React builds one new, unticked row at the top. Dentist still has key 101, so React keeps Dentist's node, tick included, and moves it down to the second row. Did you notice the detail? The index names a position, and a position belongs to whoever sits there. The ID names the email, and the email takes its tick along. So, do not confuse a key that silences the error with a key that names the email. Moral of the story: take the key from the data, an ID that never changes (Lesson 18).

This bug hides well. The Console stays quiet, and the first load is perfect. The bug needs two events in a row, a tick and then a new email, and a quick test on your own computer rarely does both. For real users, the cost is real. If the inbox had a Delete selected button, the next click would delete the Shop email, which the user never chose. The Dentist email would stay, with no error anywhere.

The Rule of Thumb: name each row by its ID, and put the key where map returns

Give every row a key that names the item, not its position: an ID from the data that never changes. React's docs say it directly: "Instead, use a stable ID based on the data."

At the end of the day, a senior developer follows three rules:

  1. Need a key? Take the ID from the data. key={index} and key={email.id} seem to do the same job: both make the Console error go away. They are NOT the same! The index follows the position, so a new email at the top takes the first row's tick. Skip this rule, and the tick lands on the wrong email with no error.
  2. No ID in the data? Make one once, when the item is created. Write id: nextId++ or crypto.randomUUID() in the handler that builds the email. Never write key={Math.random()}: it makes a new key on every render, so React rebuilds every row and every tick is lost.
  3. Moved the row into its own component? Put the key on the component tag inside map. And if the child needs the ID, pass it again as a normal prop. Skip this rule, and the Console keeps asking for a key, or the child reads undefined.

PRINCIPLES

React matches the rows of a list by their key, and it keeps the DOM node of every row it matches. Four practical principles follow from that:

  1. Principle 1: Always Return the Row from map. Curly braces right after => open a block body that returns nothing, so the list renders empty. Write the row in parentheses, or write return.
  2. Principle 2: Always Take the key from the Data, Never from the Index. The index follows the position, so a new email at the top takes the first row's tick. Use key={email.id}, and never make a key during the render.
  3. Principle 3: Put the key Where map Returns. Once the row is its own component, the key goes on <EmailRow /> inside map, not on the <li> inside EmailRow.
  4. Principle 4: Never Read key Inside the Child. React keeps the key for itself, so the child reads undefined. Pass the same value again as id.

PRINCIPLE1I Mapped Three Emails, So Why Is My Inbox Empty?

Principle 1

Always Return the Row from map: a Curly Brace After => Needs return

Summary: Do not just open curly braces after => to make room for a long row. You cannot simply write email => { <li>...</li> }: this does not work. You need to wrap the row in parentheses, email => ( <li>...</li> ), or write return inside the curly braces. What if you open curly braces and forget return? The arrow function returns undefined for every email, and the inbox shows an empty list with a quiet Console.

Description: When you map three emails, you expect three rows on the page. Yet when the row grows to a checkbox, a sender, and a subject, and you open curly braces after => to give it more room, the list on the page is empty. Why? Because curly braces right after => do not group the JSX. They open a block body, a function body like any other. And a function body returns nothing unless you write return. So the arrow function builds the <li>, throws it away, and returns undefined. map collects whatever the arrow function returns, so it hands React [undefined, undefined, undefined]. And guess what: React draws nothing for undefined, and it does not complain either. No error, no warning, just a heading over an empty list. The solution is simple: make the arrow function return the row. Wrap the row in parentheses, which only group the JSX, so the arrow still returns it. Or keep the curly braces and write return in front of the row. Both fixes do the exact same thing: three emails, three rows.

PRINCIPLE2I Ticked Dentist, So Why Is Shop Ticked Now?

Principle 2

Always Take the key from the Data, Never from the Index: the ID Follows the Email

Summary: Do not just silence the missing key error with the position of the row. You cannot simply write key={index}: the error goes away, but the bug stays. You need a key from the data that never changes, key={email.id}. What if you use the index and a new email arrives at the top? The tick the user put on Dentist jumps to the new email, Shop, with a quiet Console.

Description: When the user ticks Dentist and then clicks Check mail, you expect Shop to arrive at the top, unticked, and Dentist to keep its tick. Yet with key={index}, the tick sits on Shop, and Dentist is unticked. Why? First, remember where the tick lives: the browser stores it in the checkbox's DOM node, and React keeps the DOM node of every key it finds again. How does React find a row? By its key, and by nothing else. With key={index}, the key is a position: 0, 1, 2. After the click, Shop sits first, so Shop gets key 0. React looks at key 0 and finds the node it already had under key 0, the one with the tick. It keeps that node, and only changes its text from Dentist to Shop. React does not care which email used to sit there. It only cares about the key. And guess what: a list with no key at all does exactly the same, because the index is what React uses by default. So key={index} only silences the error. A key made during the render, such as Math.random(), is even worse. It is new on every render, so React finds none of the old keys, throws away every row, and builds new ones, without a single tick. The solution is simple: take the key from the data. With key={email.id}, Dentist is 101 on every render, wherever it sits. Shop arrives with a key React has never seen, 104, so React builds one new, unticked row for it. Dentist's node, tick included, moves down to the second row.

OverviewWhere to Get Your key

Principle 2 leaves one practical question: where does the key come from? React's docs list the sources in a section called "Where to get your key". Developers really choose between three:

  1. An ID from the database. In the docs' words, "If your data is coming from a database, you can use the database keys/IDs, which are unique by nature." Emails from a server already carry an ID, so key={email.id} is the everyday case.
  2. An ID made once, when the item is created. In the docs' words, "use an incrementing counter, crypto.randomUUID() or a package like uuid when creating items." It fits data made in the browser, such as a note the user writes. In our inbox, it is nextId++ inside handleCheckMail.
  3. The index, only for a list that never changes. It works when the list never changes order, never gets an item inserted or removed, and holds nothing the user marks or types. The docs' poem is that case: "This is a rare case where index as a key is acceptable because a poem's lines will never reorder."

Interview PrepFor the Interview

The Interview Question: How do you render a list from an array, and why does React demand a stable key on every item?

How to Answer Clearly in 30 Seconds

"I turn the array into an array of JSX with map, inside the curly braces of the list. React needs a key on every element map returns, because after each render it must match each new row with a row of the last render, and it keeps the DOM node of every row it matches. Three rules follow:

  1. A key from the data: I use a stable ID such as email.id. The index follows the position, so when a new item arrives at the top, the first row's tick or typed text lands on the new item. A key made during the render, such as Math.random(), matches nothing, so React rebuilds every row and the user's input is lost.
  2. On the element map returns: once the row is its own component, the key goes on <EmailRow key={email.id} />, not inside the component. For several siblings per item, it goes on <Fragment key>.
  3. Not a prop: React keeps key for itself, so the child reads undefined. If the child needs the ID, I pass it again as a normal prop, such as id."

Three Classic Follow-Up Questions Interviewers Ask

  1. "When is the index fine as a key?"
    When the list never changes order, never gets an item inserted or removed, and holds nothing the user marks or types, such as the lines of a poem. React's docs: "This is a rare case where index as a key is acceptable because a poem's lines will never reorder." Without a key, React uses the index anyway, so key={index} only silences the error. It does not change the matching.
  2. "Is crypto.randomUUID() a good key?"
    Yes, when it runs once, in the handler that creates the item, and the ID is stored in the item. No, when it runs inside the JSX: then it makes a new key on every render, exactly like Math.random(), and React recreates every row. Keys must be unique only among siblings, so two different lists on one page may use the same IDs.
  3. "What happens with <EmailRow {...email} />?"
    The spread passes id, sender, and subject as props, but no key, because the key is never a prop. The Console keeps the missing key error, so the key is still written by hand: <EmailRow key={email.id} {...email} />. And if the object you spread holds a field named key, React prints A props object containing a "key" prop is being spread into JSX. The reason behind all of this, in the docs' words: "it's important to separate app logic from hints to React."
