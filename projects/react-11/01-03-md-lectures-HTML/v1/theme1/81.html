How an Error Report Names the Component That Wrote the Tag

Interview Question❱❱❱ ADVANCED

How does captureOwnerStack pinpoint which component caused a render or error?

When the error names a component that has no bug, how do you find the component that does?

Overview · Two Ways Side by SideAThe Component StackvsBThe Owner StackBoth list the components above the error, only the Owner Stack names who wrote the tag

In plain JavaScript, when a function crashes, the error also names the function that called it, so you can see where the bad value came from. In React, a component never calls the components it shows: it only writes their tags, so the error names the crashing component and then only React's own functions. captureOwnerStack() gives you the missing name: the component that wrote the tag and passed the bad props.

Remember the red error in the Console? Under the message, the browser prints a list of lines that start with at. The function that crashed is on top. One line down is the function that called it, then the function that called that one, and so on. This list is the stack trace, and each at line is a frame.

Here is a plain function that formats a price, and a function that calls it with no amount:

The component that wrote the tag: the owner

So the name we need is the component that wrote the <Price /> tag. React's docs call it the owner of this Price. In development, React keeps a record of which component wrote each tag, and one function reads it:

captureOwnerStack() returns a short text with one at line per step. The first line is the owner. Then comes the owner's owner, and so on, up to the top of the app. React's docs call this list the Owner Stack.

Both lists start with at, both come from React, and both describe the same failing Price. It may look the same, or work the same at first, but it is NOT the same thing!

  • The Component Stack follows where Price sits on the page. It lists Price, then every component and every HTML tag around it, up to App.
  • The Owner Stack follows who wrote the tags. Its first line points into the file of ProductList, at the exact line of the <Price /> tag. Then come ProductList and App. No layout and no HTML tag is in it.

Why does that first line have no name? The <Price /> tag sits inside an arrow function, the one that the product list passes to products.map. An arrow function has no name, so React prints its file and its line. Array.map on the next line is the method that calls that arrow function.

So the Owner Stack points at the file of ProductList, the file to open.

Where Readers Usually Go Wrong

Readers take the component right above the failing one in the tree as the one that created it. Often it is not. A layout that renders children only holds what another component wrote. The HTML tags around it, such as <main> and <li>, only hold it too.

Three Lists of Names for One Error

So for one error, the browser and React give us three lists of names. Each one fits a different job:

  1. The error's own stack, error.stack. The browser puts it on every JavaScript error. It names the component that threw, then React's functions. It fits a bug inside the component that threw.
  2. The Component Stack, errorInfo.componentStack. React gives it to the error handlers of the root and to componentDidCatch. It lists every parent in the tree. It fits production, because it is the only React list that exists there.
  3. The Owner Stack, captureOwnerStack(). It lists only the owners. It fits development, while React runs your code: during render, in Effects, in React event handlers, and in React's error handlers.

The Rule of Thumb: who wrote the tag?

Ask one question about every error: which component wrote the tag of the component that crashed? In development, captureOwnerStack() names it first. In production, there is no Owner Stack, so your error report sends the Component Stack.

PRINCIPLES

An error names the component that threw, but the code to fix is usually in the component that wrote its tag. Five principles follow that path, from the tag to the production report:

  1. Principle 1: The owner wrote the tag; the parent only holds it. App writes the <ProductList /> tag, so it is the owner. Layout receives that element as children, so it is only the parent.
  2. Principle 2: The error's own stack names Price, then React. ProductList never calls Price. React does, so ProductList is not in the error's stack.
  3. Principle 3: The Component Stack lists every parent; the Owner Stack lists only the owners. In the root's error handler, errorInfo.componentStack lists everything around the failing price. captureOwnerStack() lists only the product list and the app.
  4. Principle 4: captureOwnerStack() answers only while React runs your code. It gives a list during render, in Effects, in React event handlers, and in React's error handlers. It gives null in a timer callback, or in a listener added with addEventListener.
  5. Principle 5: In production, there is no Owner Stack. captureOwnerStack exists only in the development build. Production reports send errorInfo.componentStack instead.

PRINCIPLE1<ProductList /> inside App: the component that writes the tag is the owner, not the layout that holds it

Principle 1

Owner and Parent: The Owner Is the Component Whose JSX Wrote the Tag

Summary: The owner of an element is the component that wrote its tag; a component that only renders children, and every HTML tag, is a parent but not the owner.

Description: A layout sits right above the content of almost every page, so it looks like the component that created that content. It did not. It received the content in children and placed it. When you look for the component that wrote a tag, you look for the owner, and the owner can sit several levels higher in the tree.

On the page, the list sits inside the <main> that Layout returns. So Layout looks like the component that created ProductList (Lesson 06).

ALayoutvsBAppBoth sit above ProductList, only App wrote its tag

It may look the same, but it is NOT the same thing!

  • Layout is the parent of ProductList. The list sits inside it. But no line of Layout writes the <ProductList /> tag. Layout only places the children it received (Lesson 09).
  • App is the owner of ProductList. The <ProductList /> tag is written inside the JSX of App.

Remember the word from the start: React's docs define the owner of an element as the component whose JSX wrote its tag. They also say it in plain words: ProductList is "created by" App. The parent and the owner can be two different components, as they are here.

React's docs also have a word for what Layout does with an element it did not write: it forwards it. Layout holds the <ProductList /> element and places it, but it did not write a single character of it. The HTML tags around ProductList, such as <main>, forward it in the same way. React's docs call these tags DOM components, and a DOM component is never an owner.

Why ProductList sits under Layout but belongs to App

This is surprising, because the tree puts ProductList under Layout. The order in which React runs the two components explains it:

  1. React calls App. App returns <Layout><ProductList /></Layout>.
  2. The <ProductList /> element is created right there, inside App, before the layout runs.
  3. React calls Layout and passes that finished element in its props, under the name children.
  4. Layout returns the element inside <main>.
  5. In the tree, the product list now sits under Layout and its <main>. Its owner is still App, the component that wrote the tag in step 1.

PRINCIPLE2error.stack: names the component that threw, then only React's functions

Principle 2

The Error's Stack: React Calls the Component, So the Tag's Author Is Not on the Stack

Summary: When a component throws during render, the error's stack names that component and then React's functions; the component that wrote its tag is not on it.

Description: A component never calls the components it shows. It returns their tags and finishes, and React calls them later. So the error's own stack tells you which component threw, but not which component passed it the bad props. The file the error names is where the crash happened, and often not where the bug is.

✓ DO THIS
1<li key={product.id}>
2 {product.name} <Price amount={product.price} />
Fix it here: ProductList passed undefined for Cap
3</li>
✗ DO NOT DO THIS
1export default function Price({ amount }) {
2 return <span>${(amount || 0).toFixed(2)}</span>;
WRONG Cap now shows $0.00, and the missing price stays hidden
3}

In plain JavaScript, while a function runs, JavaScript keeps a list of the functions that are running right now. Each function sits on top of the function that called it. This list is the call stack. When an error is thrown, the browser copies it into the error as error.stack: the stack trace you met at the start.

So the stack trace can only name functions that really called each other. That is the whole story of this principle.

APrice()vsB<Price />Both mention Price, only the call puts ProductList on the stack

Many developers read the <Price /> tag as if the product list called Price(). It may look the same, but it is NOT the same thing!

  • A call such as Price() would run the price component right now, inside ProductList, and put ProductList on the stack. React's docs forbid it: never call a component function yourself.
  • A tag such as <Price /> only describes what to show. ProductList returns it and finishes. React calls Price later (Lesson 13).

So when Price throws, the function under it on the stack is React's own code, such as renderWithHooks. These are the "library frames" that the interview question talks about.

The fix that hides the bug

The Console points at Price, so the developer fixes Price, and the real bug stays hidden. Here is how it usually goes:

  1. The page goes blank, and the Console names Price.
  2. The developer opens the file of Price and makes it safe for a missing amount, so it shows 0.
  3. The page comes back, and the Cap row now says $0.00.
  4. The real bug, a product that arrived without a price, is still in the data of ProductList. Nothing points to it anymore, and the user sees a wrong price.

The stack named Price because it threw, not because it is wrong. To find the line that passed no amount, we need the component that wrote the <Price /> tag. The next principle shows where React gives us that name.

Reading the Component Stack from the top

On our small page, ProductList is the fourth line of the Component Stack. On a real page, many more lines stand between the failing component and its owner: layouts, cards, wrappers, and HTML tags. Here is what happens when a developer reads that list from the top:

  1. The first line is the component that threw, which has no bug.
  2. The next lines are HTML tags.
  3. The first component name after them is often a layout that only forwards children. The developer opens it, and the bug is not there.
  4. The component that wrote the tag is further down the list.

The Owner Stack skips steps 1 to 3. Its first line points into the owner.

The same two lists in an Error Boundary

An Error Boundary gets the same Component Stack. Its componentDidCatch method receives it in info.componentStack (Lesson 72). React's docs log it next to captureOwnerStack(). logErrorToMyService is the docs' name for the function that sends both to a server:

Logging both lists from an Error Boundary
1componentDidCatch(error, info) {
2 logErrorToMyService(error, info.componentStack, ~captureOwnerStack()~);
Both lists, in development
3}

Careful: the Owner Stack here belongs to a different component. While React runs componentDidCatch, the component it is running is the Error Boundary, not Price. So captureOwnerStack() names the owners of the Error Boundary.

In our shop, with the boundary written in App around the product list, it logs only at App. The root's onCaughtError handler, in contrast, gets the Owner Stack of Price. That is why the entry file logs it there in Principle 5.

Where the root options go

The root options go to createRoot, not to render. When a developer passes them to root.render, React ignores them and never calls the handler. It logs an error in the Console instead. The shop still crashes, and React's own handler logs the crash as before:

PRINCIPLE4captureOwnerStack(): returns the list only while React runs your code, and null after

Principle 4

When It Answers: captureOwnerStack Gives a List Only While React Runs Your Code

Summary: Call captureOwnerStack() during render, in an Effect, in a React event handler, or in a React error handler; in a setTimeout callback, after fetch, or in an addEventListener listener, it returns null.

Description: The Owner Stack belongs to the component that React is running right now. When the browser runs our code later, React is not running any component, so there is no Owner Stack to read. A log that prints null does not mean the tool is broken. It means the call ran outside React. Capture the string earlier, while React runs the code, and keep it.

Interview PrepFor the Interview

The Interview Question: How does captureOwnerStack pinpoint which component caused a render or error?

How to Answer Clearly in 30 Seconds

"captureOwnerStack() returns the Owner Stack: the list of components that wrote the tags leading to the component React is running. The owner of an element is the component whose JSX wrote its tag. That is different from the parent: a layout that renders children is a parent, but not the owner. Three facts make it useful:

  1. The error's own stack cannot name the owner. React calls components, so the stack shows the component that threw and then React's functions, the 'library frames'.
  2. The Component Stack is longer. errorInfo.componentStack lists every parent, including layouts and HTML tags. The Owner Stack lists only the owners, so its first name is the component that passed the bad props.
  3. It is a development tool. It works during render, in Effects, in React event handlers, and in the root's error handlers, and it returns null in a setTimeout callback or an addEventListener listener. In production it is not exported, so I reach it through import * as React behind a process.env.NODE_ENV check, and my production reports send errorInfo.componentStack, decoded with sourcemaps."

Three Classic Follow-Up Questions Interviewers Ask

  1. "What is the difference between the owner and the parent of a component?"
    The parent is where the element sits in the tree. The owner is the component whose JSX wrote its tag. In our shop, App writes the ProductList tag between the Layout tags. Layout is the parent of ProductList, because it places it inside <main>. App is the owner, because it wrote the tag. React's docs say that a component that only renders children, and every DOM component such as <main> or <li>, only forwards the element.
  2. "An error was thrown inside a tree of two hundred components, and the stack shows only library frames. What does the Owner Stack reveal?"
    It reveals who wrote the tag of the component that threw. The error's own stack shows the component that threw and then React's functions, because React called that component, not its owner. The Owner Stack starts with the owner, then the owner's owner. It leaves out every layout and HTML tag that only forwarded the element, every sibling, and the component that threw. Its first name is usually the file to open.
  3. "How do you log the Owner Stack in production?"
    You do not, because there is none. React's docs say that Owner Stacks are only available in development, and the production build of React does not export captureOwnerStack at all, so it is undefined there. In production, I pass onUncaughtError, onCaughtError, and onRecoverableError to createRoot, and send the error with errorInfo.componentStack to the error reporting service. Its component names are minified, so I decode them with sourcemaps, the same way as a normal JavaScript stack trace.
