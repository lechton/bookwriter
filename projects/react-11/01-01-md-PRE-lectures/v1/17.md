# Q17 Prelecture: Why React Sees a New Object but Not a Changed Field

- Bank row: 17, `❱ CORE`, `#state_objects`.
- Interview question: How do you update an object in state without mutating it?
- Bank scenario: You write user.name = 'Alice' on your state object and nothing re-renders. The object changed, but React did not see it. Why does React require a new object reference?
- Lecture title: Why React Sees a New Object but Not a Changed Field
- Short question under the title: *(When you change a field inside the object in state, why does the screen stay the same?)*
- Interview line: `> INTERVIEW QUESTION | ❱ CORE | How do you update an object in state without mutating it?`

## Scope

This lesson covers:
- An object held in state, read-only: a mutation such as `item.quantity = 2` does not reach the screen, and a new object passed to the setter does.
- Why: `Object.is` compares the object React holds with the object you pass, and a mutated object is still the same object.
- A setter replaces the whole object and never merges, so the new object must copy every field the click does not change.
- Object spread `{ ...item, giftWrap: true }`, and the left-to-right order inside it: the changed field goes after the spread.
- A shallow copy: spread copies one level, so a nested change copies every object on the path from the changed field up to `item`.
- Local mutation of a fresh copy, as a reminder from Lesson 14, and where it stops being local.
- One change handler for several text boxes with a computed property name, `[e.target.name]: e.target.value`.
- The ways to build the new object: by hand, with spread, with spread inside an updater function, and Immer named as an optional helper.

## Intro

- Section title, a central contrast title: Mutation `item.quantity = 2` vs. a New Object for `setItem`: the mutation keeps the same object, the new object brings a render.
- Terms to remind, at the top: **State and its setter** (Lesson 12), **A setter call with the same value** (Lesson 13). Other reminders sit in the text, where the Order part places them.
- What the reader knows: in plain JavaScript, `item.quantity = 2` changes the field, and every line after it reads `2`. The job is done.
- The one line where React breaks it: In React, the screen does not change, because React never looks inside the object.
- The new word at this moment: **A mutation** [NEW], right after the line where React breaks the habit.
- The mental model, in the docs' words, as what your code tells React when it passes a new object: "Replace `item` with this new object, and render this component again." (from "With `setPosition`, you're telling React: Replace `position` with this new object, and render this component again.")
- Why React needs the rule:
  1. React checks for a change by asking one fast question, "is this the same object?", and never walks through the fields. The docs: "If `prevObj === obj`, you can be sure that nothing could have changed inside of it."
  2. Old objects stay untouched, so every earlier render keeps a correct snapshot, and a reset to the starting values keeps working. The docs list "letting the user reset a form to earlier values" among the features that are easier when nothing is mutated.
- The rules from React's docs, quoted:
  1. "Treat any JavaScript object that you put into state as read-only." (learn/updating-objects-in-state)
  2. "React will ignore your update if the next state is equal to the previous state, as determined by an `Object.is` comparison. This usually happens when you change an object or an array in state directly." (reference/react/useState, troubleshooting)
  3. Hard word in plain actions: "read-only" means you read `item.quantity` to build a new object, and you never write `item.quantity = ...`.
- The "Beware!" line before the image: **Beware! Changing a field inside the object in state does not change the screen, and no error tells you.**
- The everyday object: a parcel at a shop counter. The clerk scans the label on the box and never opens it. A box with the same label is a box already checked in.
  1. The label stands for the object itself, the thing `Object.is` checks.
  2. The contents stand for the fields, such as `quantity: 1`.
  3. The scanner stands for `setItem`, which compares with `Object.is`.
  4. Opening the box and adding two mugs stands for `item.quantity = 3`: the scanner reads the same label, so the shop's screen still says 1 mug. What breaks: the screen and the box disagree until the box is opened for another reason, the next render, and then 3 appears at once.
  5. A new box with a new label stands for a new object: the scanner sees a new parcel and records it, so React renders.
  6. "This is fine": filling a new box before you hand it to the clerk is fine, because nobody has scanned it yet. That is local mutation (Lesson 14).
- The image is named as an image the first time it appears: "Think of a parcel at a shop counter."
- The "Beware!" line before the scenario: **Beware! A mutated object hides its change until some other click renders the component, and then the change jumps onto the screen.**
- The scenario:
  1. Grounding: shoppers change a cart item all the time: one more mug, gift wrap, a later delivery.
  2. The place of the mistake: inside the click handler of the `+1` button.
  3. The setup: `item` starts as `{ quantity: 1, giftWrap: false }`. `handleAddOne` runs `item.quantity = item.quantity + 1` and then `setItem(item)`. `handleGiftWrap` runs `setItem({ quantity: item.quantity, giftWrap: true })`, a new object.
  4. The wrong screen first: after two clicks on `+1`, the card says `Quantity: 1`. Then one click on `Add gift wrap`, and the card says `Quantity: 3` and `Gift wrap: Yes` at the same moment.
  5. The steps, with **The same object vs. a new object** [NEW] placed here:
     1. The first click on `+1`: `item.quantity` becomes `2` inside the object React holds.
     2. `setItem(item)` hands React that same object. `Object.is` is `true`, so React skips the render. The card stays on `Quantity: 1`.
     3. The second click: the quantity inside becomes `3`. Same object again, no render.
     4. The click on `Add gift wrap`: the handler builds a new object and copies `item.quantity`, which is already `3`.
     5. `Object.is` is `false`, React renders, and both lines change together.
  6. How the bug hides: the Console stays empty, and `console.log(item.quantity)` inside the handler prints `2`, then `3` (lab case `p1-wrong-probe`: `handleAddOne: item.quantity is 2`, then `handleAddOne: item.quantity is 3`), so the developer thinks state did update and blames the screen. For real users: if a Checkout button sends `item` to the server, the server receives 3 mugs while the card shows 1.
- The Rule of Thumb, the bold rule: **Treat every object in state as read-only: to change a field, hand the setter a new object.**
  1. **Need to change a field? Build a new object.** `item.quantity = 2` followed by `setItem(item)` and `setItem({ quantity: 2, giftWrap: item.giftWrap })` seem to do the same job: both hold `quantity: 2`. They are NOT the same! The first hands React the same object, and React skips the render. Skip this rule, and the screen stays behind with no error.
  2. **Building the new object? Spread first, write the change last.** The setter replaces the whole object and never merges. Leave a field out, and it disappears from the screen. Put `...item` after the change, and the old value wins.
  3. **Changing a nested field? Copy every level on the path.** `{ ...item }` copies the top level only, and `item.delivery` is still shared. Skip this rule, and `Start over` shows `Evening` because the starting object was changed too.
- Ways: developers really choose between four ways to build the new object. In the lecture they sit in their own section after Principle 3, as the Order part says, because Ways 2 to 4 need spread and nesting.
  1. **Every field by hand**, `setItem({ quantity: item.quantity + 1, giftWrap: item.giftWrap })`: fits an object with one or two fields, or an object built fresh from the event, such as the docs' pointer position `{ x: e.clientX, y: e.clientY }`.
  2. **Object spread**, `setItem({ ...item, quantity: item.quantity + 1 })`: the everyday way, once an object has several fields. A local copy changed before the call, `const nextItem = { ...item }; nextItem.quantity = 2; setItem(nextItem)`, is the exact same thing.
  3. **Spread inside an updater function**, `setItem(prevItem => ({ ...prevItem, quantity: prevItem.quantity + 1 }))`: fits when one click queues several updates to the same object (Lesson 16). The parentheses around the object are needed: right after `=>`, a curly brace starts a function body, so `prevItem => { ...prevItem, quantity: prevItem.quantity + 1 }` does not compile: Vite shows `[PARSE_ERROR] Unexpected token` at the three dots (lab case `ways-no-parens`). Three updater calls in one click move the quantity from 1 to 4 and keep `giftWrap`; three plain spreads of the same `item` reach only 2 (lab case `ways-updater`).
  4. **Immer**, an optional library for deeply nested state: it lets you write `draft.delivery.time = 'Evening'` and builds the copies for you. Named only. The other choice for deep nesting is to flatten the state, which Lesson 22 covers.

## Definitions

### Reminders

> [!DEFINITION]
> **State and its setter.** [REVIEW] In vanilla JavaScript, you just write `quantity = 2`, and the job is done. Not in React. A value that must survive between renders lives in state, and state always comes as a pair: the state variable and its twin setter, born together in one line. EVERY. SINGLE. TIME. Until now, the state variable held a number, such as `score` in `const [score, setScore] = useState(0)`. But state can hold any JavaScript value, including an object that groups several values together: `const [item, setItem] = useState({ quantity: 1, giftWrap: false })`. Here `item` is the state variable, and `setItem` is its twin setter. The object inside holds two fields: `item.quantity` (e.g. 1 mug) and `item.giftWrap` (e.g. no gift wrap). React holds this object for your component between renders, and each time you want a change, you call the matching setter, `setItem(...)`. Here is the catch: whatever you pass to `setItem`, `item` does NOT change on that line, and not on any line after it in the same handler. Believe it or not, React first calls your component AGAIN, and only in that new render does `item` hold the new object (Lesson 12).

> [!DEFINITION]
> **A setter call with the same value.** [REVIEW] OK, we have seen that a setter call asks React to render the component again. Well... not always. React first compares the value you pass with the value it already holds, using a JavaScript check called `Object.is`. Suppose `score` is 2, and a click handler calls `setScore(2)`. `Object.is(2, 2)` is true: it is the same value. So React skips re-rendering the component and its children, and the screen stays exactly as it was. Here is the good news: React does no useless work, and for a number this is exactly what you want, since the screen already shows 2. Now keep this check in mind, because in this lesson it decides everything: React never asks "did something change inside?". It only asks "is this the same value?" (Lesson 13).

### New definitions

> [!DEFINITION]
> **A mutation.** [NEW] So far, every state variable held a number, a string, or a boolean. You cannot change the number 0 from the inside: `setScore(5)` REPLACES 0 with 5, and the number 0 itself is still 0. An object is different. An object is a container, and JavaScript lets you change what is inside it: `item.quantity = 2`. This is called a mutation: the object stays the very same object, but its contents change. Shorthands such as `item.quantity++` and `item.quantity += 1` are mutations too. Here is the catch: JavaScript does not stop you, and neither does React. `item.quantity = 2` runs on the object React holds in state with zero errors and zero warnings. But no setter was told, so React has no idea that anything changed, and the screen stays as it was. React's docs compare it to "trying to change the order after you've already eaten the meal." Moral of the story: objects in state can technically be mutated, but you treat every object you put in state as read-only, just like a number. You read it. You never write into it. You replace it (Lesson 17).

> [!DEFINITION]
> **The same object vs. a new object.** [NEW] So, we have seen two things. First, `item` holds an object, born with its twin setter in `const [item, setItem] = useState({ quantity: 1, giftWrap: false })`. Second, React checks the value you pass to `setItem` with `Object.is`, and skips the render when it gets the same value. Now pay attention here, because this is where objects trick everyone. For two objects, `Object.is` does NOT open the curly braces to compare the fields. It asks one question only: "Is this the very same object in memory?" Let's catch it in action. The handler of the `+1` button writes `item.quantity = item.quantity + 1`, and then calls `setItem(item)`. The first line mutates the object: inside it, the quantity is now 2. The second line hands that object to React. Will the card show `Quantity: 2`? NO, it stays on `Quantity: 1`! Why? Because React compares the object it holds with the object you passed, and they are the SAME object. `Object.is(item, item)` is true, so React skips the render. Did you notice the detail? The quantity really changed, but the object did not: it is the same object with new contents, and React never reads the contents. Now compare: `setItem({ quantity: item.quantity + 1, giftWrap: item.giftWrap })`. Those curly braces build a NEW object in memory. `Object.is` compares the old object with the new one, the answer is false, and React does what you wanted: it replaces `item` with the new object and renders `Quantity: 2`. So, do not confuse a changed object with a new object: both hold `quantity: 2`, but only the new object reaches the screen. Now the tricky part: the mutation does not go away. It waits. Click `+1` twice: the card still says `Quantity: 1`, while the object in memory already holds 3. Then click `Add gift wrap`, whose handler builds a new object and copies `item.quantity` into it. That new object holds 3, React renders it, and the quantity jumps from 1 straight to 3, at the very moment the gift wrap line turns to `Yes`! Moral of the story: never edit the object React holds. To change a field, hand the setter a new object (Lesson 17).

> [!DEFINITION]
> **Object spread.** [NEW] OK, we have seen that the setter needs a new object. But writing every field by hand, `{ quantity: item.quantity, giftWrap: true }`, gets long when the object has five or ten fields. Remember the three dots on a JSX tag? `<ArticleCard {...article} />` opens the `article` object and copies all of its properties onto the tag (Lesson 9). Inside the curly braces of an object, the same three dots do the same job: `{ ...item, giftWrap: true }` builds a NEW object, copies every field of `item` into it, and then writes `giftWrap: true`. That is object spread. But why copy the old fields at all? Because a setter REPLACES the state with the exact object you pass. Notice that word: REPLACE, not merge. `setItem({ giftWrap: true })` does not add gift wrap to the old object. It replaces the whole object with one that holds only `giftWrap`. And the quantity? Gone! The card shows `Quantity:` with nothing after it. Here is the catch: order matters. JavaScript builds the object from left to right, and when the same field appears twice, the last one wins. In `{ ...item, giftWrap: true }`, the spread copies `giftWrap: false` first, and then `giftWrap: true` overwrites it: the gift wrap is on. In `{ giftWrap: true, ...item }`, `giftWrap: true` comes first, and then the spread copies the old `false` over it: the gift wrap stays off, with no error. Moral of the story: spread first, the changed field last (Lesson 17).

> [!DEFINITION]
> **Local mutation.** [REVIEW] OK, we have seen that changing an object that already lives in state is a mutation, and React never sees it. So is every `=` on an object forbidden? NO. Remember local mutation? Changing a brand-new object or array that you just created, inside the same function, is completely fine, because no other code points at it yet. So inside a click handler, `const nextItem = { ...item }` builds a fresh object, and `nextItem.quantity = 2` changes only that fresh copy. Then `setItem(nextItem)` hands React a new object, `Object.is` is false, and React renders. That is the exact same thing as writing `setItem({ ...item, quantity: 2 })`. Here is the catch: "brand-new" must be true for every object you change. `nextItem` is new. But is everything INSIDE `nextItem` new as well? Keep that question in mind (Lesson 14).

> [!DEFINITION]
> **A shallow copy.** [NEW] OK, we have seen how object spread `{ ...item, quantity: 2 }` builds a brand-new object so React can render. But what happens when the object in state holds another object inside it, such as `delivery: { address: '12 Main Street', time: 'Morning' }`? That brings us to a shallow copy. Pay attention here: object spread looks like it copies everything, but it only copies the top level! React's docs say that when the code runs, there is no such thing as a nested object: there are two different objects, and the outer one only points at the inner one. Think of the outer `item` box holding a card with the address of a second box, the `delivery` box, somewhere else in memory. When you write `const nextItem = { ...item }`, JavaScript builds a new outer box, but for `delivery` it copies only the card: `item.delivery` and `nextItem.delivery` point at the exact same inner box. That is why it is called a shallow copy, and not a deep copy! As long as you only read `delivery`, that is cool... but the moment you write `nextItem.delivery.time = 'Evening'`, you mutate the shared inner box that `item` still points at. Here is the catch, caught in action: the shopper clicks `Deliver in the evening`, and the handler runs `const nextItem = { ...item }`, then `nextItem.delivery.time = 'Evening'`, then `setItem(nextItem)`. `nextItem` is a new outer box, so React renders, and the card shows `Evening`. It looks like it worked, right? Now the tricky part: the shopper clicks `Start over`, whose handler runs `setItem(initialItem)` to bring back `Morning`. Does the card go back to `Morning`? NO, it stays on `Evening`! Why? Because `initialItem.delivery` points at that same inner box too, and `nextItem.delivery.time = 'Evening'` wrote into it. No line of the reset handler wrote `Evening`, but the starting object was changed through the shared inner box. Moral of the story: spread is shallow. To change a nested field, copy every object on the path from the changed field up to the top: `setItem({ ...item, delivery: { ...item.delivery, time: 'Evening' } })` (Lesson 17).

> [!DEFINITION]
> **The event object.** [REVIEW] OK, we have seen that when the user clicks a button, React calls your event handler. React also hands that handler one argument, the event object, which we name `e`. You never pass `e` yourself: React does, as the first argument, in `function handleChange(e)`. And `e.target` is the element where the event started (Lesson 11). Until now, that element was a clicked button. Now it is a text box. When the user types in `<input name="message" onChange={handleChange} />`, React calls `handleChange` on EVERY keystroke, and `e.target` is that very box. So `e.target.value` holds the text in the box right now (e.g. `Hi`), and `e.target.name` holds the `name` attribute written on the tag (e.g. `message`). Here is the catch: `e.target.name` is NOT a field of `item`. It is only the string you wrote in `name="..."` on the tag, nothing more (Lesson 11).

> [!DEFINITION]
> **A computed property name.** [NEW] So, we have seen how object spread writes one changed field after the copy: `{ ...item, message: 'Hi' }`. There, the field name `message` is written right in the code. But what if the field name sits in a variable, and you only know it when the code runs? Suppose `const field = 'message'`. Then `{ [field]: 'Hi' }`, with square brackets, tells JavaScript: "read the variable `field` first, and use its value as the field name". The result is `{ message: 'Hi' }`. That is a computed property name. Now pay attention here: `{ field: 'Hi' }`, without the brackets, is NOT the same thing! Without brackets, JavaScript reads no variable at all. It uses the word `field` itself as the name, and builds `{ field: 'Hi' }`. Here is the good news: put the brackets around `e.target.name`, and one handler can update every box: `setItem({ ...item, [e.target.name]: e.target.value })`. The user types in the box with `name="message"`, and `item.message` changes. The user types in the box with `name="recipient"`, and `item.recipient` changes. Here is the catch: the `name` on the tag must match the field in state, letter for letter. Write `name="msg"`, and the handler adds a new field, `msg`, that nothing on the card reads, so `Message:` stays empty, with no error (Lesson 17).

## Principles

### Principle 1: I Clicked +1 Twice, So Why Does the Card Still Say Quantity: 1?

- **Rule**: When a click must change a field of an object in state, pass the setter a new object. Do not change the field inside `item` and pass `item` back.
- **Real beginner mistake**:
  1. In plain JavaScript, the developer changes objects in place every day.
  2. In the `+1` handler, the developer writes `item.quantity = item.quantity + 1`.
  3. To tell React, the developer adds `setItem(item)` on the next line.
  4. The shopper clicks `+1`, and the card still says `Quantity: 1`.
  5. The developer clicks again, sees no error, and thinks the click missed.
  6. Later, the shopper clicks `Add gift wrap`, and the quantity jumps to `3`.
- **Wrong code**:
  ```jsx
  const [item, setItem] = useState({ quantity: 1, giftWrap: false });

  function handleAddOne() {
    item.quantity = item.quantity + 1;
    setItem(item);
  }

  function handleGiftWrap() {
    setItem({ quantity: item.quantity, giftWrap: true });
  }
  ```
- **Right code**:
  ```jsx
  function handleAddOne() {
    setItem({ quantity: item.quantity + 1, giftWrap: item.giftWrap });
  }
  ```
- **Proof on the screen**:
  - With the wrong code: two clicks on `+1` show `Quantity: 1`; then `Add gift wrap` shows `Quantity: 3` and `Gift wrap: Yes`.
  - The steps:
    1. Each click on `+1` mutates `item.quantity` inside the object React holds: 2, then 3.
    2. Each `setItem(item)` hands React the same object.
    3. `Object.is` is `true`, and React skips the render.
    4. `Add gift wrap` builds a new object that copies the quantity, already 3.
    5. `Object.is` is `false`, and React renders 3 and `Yes` together.
  - With the right code: two clicks on `+1` show `Quantity: 2`, then `Quantity: 3`, and `Gift wrap: No` stays.
- **Definitions it uses**: **State and its setter**, **A setter call with the same value**, **A mutation**, **The same object vs. a new object**.
- **Side by side**:
  1. "with `item.quantity = 2` and `setItem(item)`" vs. "with `setItem({ quantity: 2, giftWrap: item.giftWrap })`": NOT the same thing. Both objects hold `quantity: 2`, but the first is the same object, so React skips the render.
  2. "a new number, `setScore(5)`" vs. "a mutated object, `setItem(item)`": NOT the same thing. A new number is always a different value; a mutated object is still the same object.
- **Where did that come from?**:
  - `item` and `setItem` inside `handleAddOne`: they come from the `useState` line at the top of `CartItem`. Each render creates the handlers again, and each handler reads the `item` of that render.
  - The `3` inside the new object of `handleGiftWrap`: no line wrote 3 there. JavaScript reads `item.quantity`, and the two mutations already left 3 in that object.
- **Move**: Steps for a surprise. The jump from 1 to 3 on a click that never touches the quantity is something the reader would not expect.
- **React does**: the screen as above; the Console shows nothing; the Elements panel shows `<p>Quantity: 1</p>` after both clicks on `+1`, then `<p>Quantity: 3</p><p>Gift wrap: Yes</p>` (lab case `p1-wrong`). Without `StrictMode`, a render log in the component body prints `CartItem renders, Quantity on screen: 1` on load and `CartItem renders, Quantity on screen: 3` after `Add gift wrap`, and nothing after either `+1` (lab case `p1-wrong-probe`).
- **Interview depth**:
  - Why does the change appear later? The object in memory was really changed; the next render for any reason reads it.
  - The docs' hedge: "in some cases React may still need to call your component before skipping the children, it shouldn't affect your code."
  - `Object.is` on objects checks identity, not contents; for numbers and strings it checks the value.
  - Mutating without calling the setter at all: React has no idea the object changed, the docs' "change the order after you've already eaten the meal".
  - Why React chose this: a fast `prevObj === obj` check, and no hidden Proxies around your objects, from the docs' Deep Dive.
- **Example step**: `src/App.jsx` returns `<CartItem />`; `src/components/CartItem.jsx` holds `item` with `quantity` and `giftWrap`, the heading `Coffee mug`, two lines, and the buttons `+1` and `Add gift wrap`. The step ends with `handleAddOne` fixed.

### Principle 2: I Added Gift Wrap, So Where Did the Quantity Go?

- **Rule**: When only some fields change, copy the rest with `...item` first and write the changed field after it. Do not pass only the changed field, and do not put the spread after the change.
- **Real beginner mistake**:
  1. The developer finds the by-hand object `{ quantity: item.quantity, giftWrap: true }` long.
  2. The developer expects the setter to merge the new field into the old object.
  3. The developer writes `setItem({ giftWrap: true })`.
  4. The shopper clicks `Add gift wrap`. The gift wrap line says `Yes`, and the quantity line goes empty.
- **Wrong code**:
  ```jsx
  function handleGiftWrap() {
    setItem({ giftWrap: true });
  }
  ```
- **Right code**:
  ```jsx
  function handleGiftWrap() {
    setItem({ ...item, giftWrap: true });
  }
  ```
- **Proof on the screen**:
  - With the wrong code: one click on `Add gift wrap` shows `Quantity:` with nothing after it, and `Gift wrap: Yes`.
  - The steps:
    1. `setItem({ giftWrap: true })` hands React a new object with one field.
    2. `Object.is` is `false`, so React renders.
    3. The setter replaced `item` with that object, so `item.quantity` is `undefined`.
    4. JSX shows nothing for `undefined`, so the line reads `Quantity:`.
  - With the right code: one click shows `Quantity: 1` and `Gift wrap: Yes`.
  - With the spread last, `{ giftWrap: true, ...item }`: one click leaves `Gift wrap: No`, with no error, because the spread copies the old `false` over the new `true`. React still renders, because the object is new.
- **Definitions it uses**: **Object spread**, **The same object vs. a new object**.
- **Side by side**:
  1. "by hand, `{ quantity: item.quantity, giftWrap: true }`" vs. "with spread, `{ ...item, giftWrap: true }`": the exact same thing for this object. Both build a new object with the old quantity and the new gift wrap.
  2. "with the change last, `{ ...item, giftWrap: true }`" vs. "with the spread last, `{ giftWrap: true, ...item }`": NOT the same thing. The last field written wins.
  3. "the new object `{ ...item }`" vs. "`item`": NOT the same object. Same fields, new curly braces, so `Object.is` is `false`.
- **Where did that come from?**:
  - `quantity` in the new object of `{ ...item, giftWrap: true }`: no line writes it. The spread `...item` copies it from the old object, from left to right, before `giftWrap: true`.
- **Move**: Both orders first, for `...item` and `giftWrap: true` inside one object, as Lesson 9 did for `{...article}` on a tag. Side by side for the by-hand object and the spread.
- **React does**: the screen as above; the Console shows nothing; the Elements panel shows `<p>Quantity: </p>` after the click (lab case `p2-missing`). With the spread last, a render log prints a second time after the click, so React rendered, and the card still says `Gift wrap: No` (lab case `p2-spread-last`).
- **Interview depth**:
  - `useState` replaces; the old class component `this.setState` merged, which is where many developers learned the habit. Mark as background only; the lecture may leave it out.
  - Spread copies own enumerable properties into a new object, from left to right (MDN).
  - Which one is faster, spread or a deep copy? Spread copies one level, which "makes it fast" (the docs).
- **Example step**: `handleAddOne` and `handleGiftWrap` both use `{ ...item, ... }`. No new part on the screen.

### Principle 3: I Clicked Start Over, So Why Does the Delivery Still Say Evening?

- **Rule**: To change a nested field, copy every object on the path, `{ ...item, delivery: { ...item.delivery, time: 'Evening' } }`. Do not spread only `item` and then change `nextItem.delivery.time`.
- **Real beginner mistake**:
  1. The developer has learned the rule: copy before you change.
  2. The developer writes `const nextItem = { ...item }`, a fresh copy.
  3. The developer changes `nextItem.delivery.time = 'Evening'`, believing it is local mutation.
  4. `setItem(nextItem)` renders `Evening`, so the code looks right.
  5. The shopper clicks `Start over`, and the delivery stays on `Evening`.
- **Wrong code**:
  ```jsx
  const initialItem = {
    quantity: 1,
    giftWrap: false,
    delivery: { address: '12 Main Street', time: 'Morning' },
  };

  export default function CartItem() {
    const [item, setItem] = useState(initialItem);

    function handleEvening() {
      const nextItem = { ...item };
      nextItem.delivery.time = 'Evening';
      setItem(nextItem);
    }

    function handleStartOver() {
      setItem(initialItem);
    }
  ```
- **Right code**:
  ```jsx
  function handleEvening() {
    setItem({ ...item, delivery: { ...item.delivery, time: 'Evening' } });
  }
  ```
- **Proof on the screen**:
  - With the wrong code: `Deliver in the evening` shows `Delivery: 12 Main Street, Evening`; two clicks on `+1` show `Quantity: 3`; `Start over` shows `Quantity: 1` and `Delivery: 12 Main Street, Evening`.
  - The steps:
    1. On the first render, `item` and `initialItem` are the same object, and so `item.delivery` and `initialItem.delivery` are the same inner object.
    2. `{ ...item }` builds a new outer object, `nextItem`, and copies only the pointer to the inner `delivery` object.
    3. `nextItem.delivery.time = 'Evening'` writes into that shared inner object, which `initialItem.delivery` also points at.
    4. `nextItem` is a new outer object, so React renders `Evening`.
    5. `Start over` hands React `initialItem`, whose quantity is still 1 and whose shared delivery object now says `Evening`.
  - With the right code: the same clicks end on `Quantity: 1` and `Delivery: 12 Main Street, Morning`.
- **Definitions it uses**: **Local mutation**, **A shallow copy**, **Object spread**.
- **Side by side**:
  1. "with one spread, `{ ...item }`, and `nextItem.delivery.time = 'Evening'`" vs. "with two spreads, `{ ...item, delivery: { ...item.delivery, time: 'Evening' } }`": NOT the same thing. The first changes the shared inner object; the second builds a new inner object.
  2. "in two steps, `const nextDelivery = { ...item.delivery, time: 'Evening' }` and then `setItem({ ...item, delivery: nextDelivery })`" vs. "in one call": the exact same thing, as the docs show with `nextArtwork` and `nextPerson`. The lecture may use only the one-call form; then `nextDelivery` is not needed.
  3. "`nextItem.quantity = 2` on a fresh copy" vs. "`nextItem.delivery.time = 'Evening'` on the same fresh copy": NOT the same thing. The first is local mutation; the second reaches an object that was not created in this handler.
- **Where did that come from?**:
  - `initialItem`: a new constant above the component, so `Start over` can hand it back to the setter.
  - `address` in the right code: no line writes `address`. The inner spread `...item.delivery` copies it into the new inner object.
  - `Evening` after `Start over`: no line of `handleStartOver` writes it. It sits in the inner object that `initialItem.delivery` points at.
- **Move**: Steps for a surprise. A reset button that does not reset is the surprise.
- **React does**: the screen as above; the Console shows nothing (lab cases `p3-wrong` and `p3-right`).
- **Interview depth**:
  - "Spread syntax is shallow: it only copies one level deep." (docs Recap)
  - "To update a nested object, you need to create copies all the way up from the place you're updating." (docs Recap)
  - Mutation also changes the state "in previous render snapshots" (docs Recap), and earlier `console.log` lines of an object get clobbered (docs Deep Dive, Debugging).
  - The docs' Challenge: a shared `initialPosition` makes the background jump, the same bug as `Start over`.
  - Deep nesting: flatten the state (Lesson 22), or use Immer.
  - `structuredClone` as a deep copy is not in the React docs; leave it out of the lecture.
- **Example step**: `CartItem.jsx` gains `initialItem` above the component, the line `Delivery: ...`, and the buttons `Deliver in the evening` and `Start over`.

### Principle 4: I Typed Hi in Message, So Why Does the Card Say To: Hi?

- **Rule**: When several text boxes each update one field, give each box a `name` equal to its field and use one handler, `setItem({ ...item, [e.target.name]: e.target.value })`. Do not copy-paste one handler per box, and do not give a box a `name` that matches no field.
- **Real beginner mistake 1**:
  1. The developer writes `handleRecipientChange` for the `To` box.
  2. The developer copies it for the `Message` box, renames it `handleMessageChange`, and forgets to change `recipient` inside.
  3. The shopper types `Hi` in the `Message` box.
  4. The card says `To: Hi`, and `Message:` stays empty.
- **Real beginner mistake 2**:
  1. The developer uses the shared `handleChange`.
  2. On the `Message` box, the developer writes `name="msg"`, a short form of the field name.
  3. The shopper types `Hi` in the `Message` box.
  4. The card still says `Message:` with nothing after it. The Console stays quiet.
- **Wrong code 1**:
  ```jsx
  function handleRecipientChange(e) {
    setItem({ ...item, recipient: e.target.value });
  }

  function handleMessageChange(e) {
    setItem({ ...item, recipient: e.target.value });
  }

  <label>To <input onChange={handleRecipientChange} /></label>
  <label>Message <input onChange={handleMessageChange} /></label>
  ```
- **Wrong code 2**:
  ```jsx
  <label>Message <input name="msg" onChange={handleChange} /></label>
  ```
- **Right code**:
  ```jsx
  function handleChange(e) {
    setItem({ ...item, [e.target.name]: e.target.value });
  }

  <label>To <input name="recipient" onChange={handleChange} /></label>
  <label>Message <input name="message" onChange={handleChange} /></label>
  ```
- **Proof on the screen**:
  - With wrong code 1: typing `Hi` in `Message` shows `To: Hi` and `Message:`. The `Message` box shows `Hi`, and the `To` box stays empty.
  - The steps of wrong code 1:
    1. Each keystroke in the `Message` box calls `handleMessageChange`.
    2. That handler writes `e.target.value` into `recipient`.
    3. The card reads `item.recipient` on the `To:` line, so it shows `Hi` there.
    4. The box keeps its own text, as Lesson 13 showed, so the boxes and the card disagree.
  - With wrong code 2: typing `Hi` in `Message` leaves `Message:` empty; the state object gains a field `msg`, which holds `H` after the first keystroke and `Hi` after the second (lab case `p4-mismatch`: `CartItem renders with {"recipient":"","message":"","msg":"Hi"}`).
  - With the right code: typing `Mia` in `To` and `Hi` in `Message` shows `To: Mia` and `Message: Hi`.
- **Definitions it uses**: **The event object**, **A computed property name**, **Object spread**.
- **Side by side**:
  1. "with brackets, `{ [field]: 'Hi' }`, when `field` holds `'message'`" vs. "with the name written, `{ message: 'Hi' }`": the exact same thing.
  2. "with brackets, `{ [field]: 'Hi' }`" vs. "without brackets, `{ field: 'Hi' }`": NOT the same thing. Without brackets, the field is named `field`.
  3. "two handlers, one per box" vs. "one `handleChange` with `[e.target.name]`": the exact same thing on the screen when both are written right; the one handler cannot write the wrong field by a copy-paste slip.
- **Where did that come from?**:
  - `e`: React passes it to `handleChange` on every keystroke; no tag writes it.
  - `e.target.name`: the browser reads it from the `name` attribute on the tag that fired, `name="message"`.
  - `recipient` and `message` inside `handleChange`: neither word is written there. `[e.target.name]` turns the string from the tag into the field name.
- **Move**: Side by side, for `[field]` and `field`, and for two handlers and one handler.
- **React does**: the screen as above; the Console shows nothing for every version, and React does not warn about a `name` that matches no field (lab cases `p4-copy-paste`, `p4-mismatch`, `p4-right`). One render per keystroke: the render log of `p4-mismatch` prints once after `H` and once after `Hi`.
- **Interview depth**:
  - This handler works for top-level fields only. A nested field such as `delivery.time` still needs the two-level copy of Principle 3.
  - A `<select>` with a `name` works with the same handler, because `e.target.value` holds the chosen option. A checkbox needs `e.target.checked`.
  - The boxes here keep their own text, so `Start over` does not clear them; making a box show state with `value` is Lesson 20.
- **Example step**: `CartItem.jsx` gains `recipient: ''` and `message: ''` in `initialItem`, the lines `To:` and `Message:`, and the two labelled boxes.

## Interview Points

- Treat every object in state as read-only; to change a field, create a new object and pass it to the setter.
- The setter compares the next state with the current one using `Object.is`; for objects that is identity, not contents.
- A mutated object is still the same object, so React skips the render; the change shows up on a later render, and no error appears.
- A setter replaces the state and never merges; copy the other fields with spread.
- In an object literal, the later field wins, so the spread goes first and the change last.
- Spread is shallow; a nested change copies every object from the change up to the top.
- A shallow copy plus a nested mutation changes shared objects, such as a starting object used for reset, and earlier snapshots.
- Changing a fresh object you just created is local mutation and is fine; it stops being local at a shared inner object.
- One change handler for several boxes: `{ ...item, [e.target.name]: e.target.value }`, with each `name` matching its field.
- For queued updates to the same object, use an updater function with a spread, `prevItem => ({ ...prevItem, ... })`.
- For deep nesting: flatten the state, or use Immer.
- Why React works this way: fast change checks, correct snapshots, easy undo and reset, and no Proxies around your objects.
