## Scope

This lesson covers:
- `map`: turning an array of data into an array of JSX rows inside the curly braces of a list.
- The arrow function in `map`: a row written right after `=>` is returned; curly braces right after `=>` open a block body that needs `return`.
- The key: why React needs it, what it is, and the Console error React prints without it.
- Where the key comes from: an ID from the data, or an ID made once when the item is created; why the index and `Math.random()` fail.
- Where the key sits: on the element directly inside `map`, which becomes the component tag once the row moves into its own component; a `<Fragment key>` when one item returns several siblings.
- Why `key` is not a prop, and passing the same value again as a normal prop.
- Where to get a key: the three ways in the React docs.

## Intro

- Section title, a central contrast title: `## VS | The Index vs. an ID from the Data as the key: the index follows the position, the ID follows the email`.
- Terms to remind, at the top: **State and its setter** (Lesson 12), **A commit** (Lesson 13). The other reminders sit in the text, where the Order part places them.
- What the reader knows: three `<li>` tags written by hand (Lesson 2). A real inbox gets its emails as data, so the new word **Rows from an array with `map`** [NEW] comes here, before React breaks anything.
- What the reader knows about lists that change: in plain JavaScript, when a new email arrives, you insert one new row at the top with `list.prepend(row)`. Every old row, with its tick, stays where it is. The job is done.
- The one line where React breaks it: In React, you never insert a row. You hand React the whole new list, and React must work out by itself which old row is which.
- The new word at this moment: **A key** [NEW], right after that line.
- The mental model, as the question React asks of every row: "Which row of the last render is this one?" From the docs: "Keys tell React which array item each component corresponds to, so that it can match them up later."
- Why React needs the rule:
  1. React keeps DOM nodes between renders and changes only what differs (Lesson 13). To keep the right node with the right email, it must match the rows. The docs: "A well-chosen `key` helps React infer what exactly has happened, and make the correct updates to the DOM tree."
  2. Whatever lives inside a row, a tick, typed text, or a component's state, stays with the row React matched. The docs: "Even if the _position_ changes due to reordering, the `key` lets React identify the item throughout its lifetime."
- The rules from React's docs, quoted:
  1. "Keys must be unique among siblings. However, it's okay to use the same keys for JSX nodes in _different_ arrays."
  2. "Keys must not change or that defeats their purpose! Don't generate them while rendering."
  3. Hard word in plain actions: "unique among siblings" means two rows of the same list never share a key. "Must not change" means the Dentist row has the same key on every render.
- The "Beware!" line before the image: **Beware! A key taken from the position follows the position, not the email: when a new email arrives at the top, every tick stays on its row number.**
- The everyday image, from React's docs, "Why does React need keys?": files on a desktop with no names, only "the first file, the second file". It is named as an image the first time it appears.
  1. The folder is the list, `<ul>`.
  2. Each file is one row, one `<li>`.
  3. "The first file, the second file" is the index.
  4. The file name is the key, `email.id`.
  5. You ask a colleague to delete "the first file", meaning the dentist letter. Before the colleague acts, a new file lands at the top. Now "the first file" is the new file, and the colleague deletes it. What breaks: the instruction is tied to a position, not to the file. A tick tied to key `0` does the same.
  6. With names, "delete dentist.pdf" stays right wherever the file moves. That is a key from the data.
  7. "This is fine": names by position work when files never move, arrive, or leave. The docs: "This is a rare case where index as a key is acceptable because a poem's lines will never reorder."
- The "Beware!" line before the scenario: **Beware! `key={index}` silences the Console error and leaves the bug in place.**
- The scenario:
  1. Grounding: people tick emails all the time, to delete them, archive them, or mark them as read. And new mail arrives at the top while they work.
  2. The place of the mistake: inside `map`, on the row tag, in `Inbox`.
  3. The setup: `emails` starts as Dentist, Mom, Bank. `handleCheckMail` adds Shop at the top with `setEmails([newEmail, ...emails])`. The developer saw the missing key error and wrote `emails.map((email, index) => <li key={index}>...</li>)`. The Console went quiet.
  4. The wrong screen first: the user ticks Dentist, then clicks `Check mail`. The list reads Shop, Dentist, Mom, Bank, and the tick sits on Shop. Dentist is unticked.
  5. The right code, alone, as a strange line: `<li key={email.id}>`. What the eye sees: a number from the data, `101`, that no user ever sees, written on a tag. The first load looks exactly the same as before, and the Console was already quiet. Then the right screen: tick Dentist, click `Check mail`, and Shop arrives unticked while Dentist keeps its tick on the second row.
  6. Then **The index vs. an ID from the data** [NEW], and the steps:
     1. First render: keys `0`, `1`, `2` for Dentist, Mom, Bank.
     2. The user ticks Dentist. The browser stores the tick in the checkbox node of the row with key `0`.
     3. `Check mail`: the new list is Shop, Dentist, Mom, Bank, with keys `0`, `1`, `2`, `3`.
     4. React finds key `0` again, keeps its DOM node with the tick, and changes its text to Shop. Key `1` keeps Mom's old node and gets Dentist's text. Key `2` keeps Bank's old node and gets Mom's text. Key `3` is new, so Bank gets a new node (lab `p4-index-nodes`: "Shop: old node of Dentist, checked=true", "Dentist: old node of Mom", "Mom: old node of Bank", "Bank: new node").
     5. The screen: Shop ticked, Dentist unticked.
  7. How the bug hides: the Console is quiet (lab `p4-index`: Console nothing), the first load is perfect, and the bug needs two events in a row, a tick and then a new email, which a quick test on your own computer rarely does. For real users: if the inbox had a Delete button, the next click would delete the Shop email and keep the Dentist email, with no error anywhere.
- The Rule of Thumb, the bold rule: **Give every row a key that names the item, not its position: an ID from the data that never changes.** The docs: "Instead, use a stable ID based on the data."
  1. **Need a key? Take the ID from the data.** `key={index}` and `key={email.id}` seem to do the same job: both make the Console error go away. They are NOT the same! The index follows the position, so a new email at the top takes the first row's tick. Skip this rule, and the tick lands on the wrong email with no error.
  2. **No ID in the data? Make one once, when the item is created.** Write `id: nextId++` or `crypto.randomUUID()` in the handler that builds the email. Never write `key={Math.random()}`: it makes a new key on every render, so React rebuilds every row and every tick is lost.
  3. **Moved the row into its own component? Put the key on the component tag inside `map`.** And if the child needs the ID, pass it again as a normal prop. Skip this rule, and the Console keeps asking for a key, or the child reads `undefined`.
- Ways: developers really choose where the key comes from. The docs list them in "Where to get your `key`". In the lecture they sit in their own section after Principle 2, as the Order part says, because they need the index and `Math.random()` from Principle 2.
  1. **An ID from the database**: "If your data is coming from a database, you can use the database keys/IDs, which are unique by nature." The everyday case: emails from a server already carry an ID.
  2. **An ID made once when the item is created**: "use an incrementing counter, `crypto.randomUUID()` or a package like `uuid` when creating items." It fits data made in the browser, such as a note the user writes. In this lesson, `nextId++` inside `handleCheckMail`.
  3. **The index**, only for a list that never changes order, never gets an item inserted or removed, and holds nothing the user marks or types. The docs' poem: "This is a rare case where index as a key is acceptable because a poem's lines will never reorder."

## Definitions

### Reminders

> [!DEFINITION]
> **State and its setter.** [REVIEW] In vanilla JavaScript, you just write `emails.unshift(newEmail)`, and the job is done. Not in React. A value that must survive between renders lives in state, and state always comes as a pair: the state variable and its twin setter, born together in one line. EVERY. SINGLE. TIME. So far, the state variable held a number, such as `score` in `const [score, setScore] = useState(0)`, or an object, such as `item` (Lesson 17). In this lesson it holds an array, a whole list of emails: `const [emails, setEmails] = useState(initialEmails)`. Here `emails` is the state variable, and `setEmails` is its twin setter. React holds this array for your component between renders. When a new email arrives, you do not push it into `emails`. You call the matching setter with a NEW array, `setEmails([newEmail, ...emails])`. The three dots you used on objects in Lesson 17 do the same job inside square brackets: they copy every old email into the new array, right after `newEmail` (e.g. Shop first, then Dentist, Mom, and Bank). Lesson 19 covers every recipe for arrays in state. Here is the catch: `emails` does NOT change on that line. Believe it or not, React first calls your component AGAIN, and only in that new render does `emails` hold the new list, with the new email at the top (Lesson 12).

> [!DEFINITION]
> **A commit.** [REVIEW] OK, we have seen that after a setter call, React calls your component AGAIN and gets back the new JSX. Then comes the commit: React puts the result into the real page. Pay attention here: React does NOT throw the old page away and build a new one. It compares the new JSX with the JSX of the last render, position by position, and when the same tag sits in the same position, it keeps the very same DOM node and changes only what is different, such as one line of text. Why does that matter? Because some things live inside the DOM node itself, and React never wrote them there. When the user ticks a checkbox that has no `checked` prop, the browser stores the tick in that checkbox's DOM node, just as a text box stores what the user types. Here is the good news: since React keeps the node, the tick survives every render. Here is the catch: the tick stays with the node, and React decides which node goes where. Keep this in mind, because in a list that changes, that decision is exactly where things go wrong (Lesson 13).

### New definitions

> [!DEFINITION]
> **Rows from an array with `map`.** [NEW] So far, every list on our pages was written by hand: `<li>Dentist</li>`, `<li>Mom</li>`, `<li>Bank</li>`, one tag per line. Cool for three rows... but a real inbox shows whatever the server sends: three emails today, two hundred tomorrow. Nobody writes those tags by hand. You keep the data in an array, and you let JavaScript build the rows. That is the job of `map`. Look: `const senders = ['Dentist', 'Mom', 'Bank']`, then `senders.map(sender => <li>{sender}</li>)`. `map` takes the array, calls your arrow function once for EVERY item, from the first to the last, and collects what the function returns into a NEW array: `[<li>Dentist</li>, <li>Mom</li>, <li>Bank</li>]`. Same length, same order. And `senders` itself? Untouched. Who fills `sender`? `map` does: `'Dentist'` on the first call, `'Mom'` on the second, `'Bank'` on the third. Now put that call inside the curly braces of the list: `<ul>{senders.map(sender => <li>{sender}</li>)}</ul>`. React receives an array of JSX and renders every element in it, in order. Yes, it is the exact same page as the three tags written by hand! Here is the catch: as soon as the list appears, React prints an error in the Console, `Each child in a list should have a unique "key" prop.` The rows are on the screen, and yet React is not satisfied. Why React asks for a key is the whole lesson (Lesson 18).

> [!DEFINITION]
> **A key.** [NEW] OK, we have seen that `map` hands React a whole array of rows, and that during the commit React keeps a DOM node when the same tag sits in the same position. But a list changes: a new email arrives at the top, one is deleted, the list is sorted. After the change, React gets a whole new array, and it must answer one question for every row: "Which row of the last render is this one?" By default, React answers with the position: the first row of the new list is the first row of the old list, the second is the second, and so on. A key replaces the position with a name. You write it on the tag that `map` returns: `<li key={email.id}>`. Now the row is not "the first row" anymore. It is "email 101", wherever it sits. A key is a string or a number, and it must be unique among siblings: two rows of the same list never share a key, but two different lists may use the same keys. Pay attention here: the key is NOT on the screen. The user never sees 101, and the Elements panel shows no `key` attribute on the `<li>`. React's docs say that the key is "only used as a hint by React itself": React uses it to match each row of this render with a row of the last render. Here is the catch: when React finds a key it already knows, it keeps that row's DOM node, with everything inside it, such as a tick, and only updates what changed. So the key decides where the tick goes. Moral of the story: the key must name the email, not its place in the list (Lesson 18).

> [!DEFINITION]
> **The index vs. an ID from the data.** [NEW] So, we have seen that every row needs a key, and that React matches rows by their key. Now the tricky part: what do you put in the key? `map` hands your arrow function a second argument, the position of the item in the array, which we name `index`: 0 for the first email, 1 for the second, 2 for the third. So many developers write `emails.map((email, index) => <li key={index}>...</li>)`, and the Console error disappears. Cool... but is the list fixed? NO. React's docs say that the index is exactly "what React will use if you don't specify a `key` at all". `key={index}` only silences the error: the rows are still matched by position. Now compare `key={email.id}`: the key is 101 for Dentist, 102 for Mom, 103 for Bank, numbers stored in the data, and each number travels with its email. On the first load, both lists look exactly the same, and both Consoles are quiet. They are NOT the same thing! Let's catch it in action. The user ticks Dentist, the first row, and the browser stores that tick in the checkbox node of the first row. Then the user clicks `Check mail`, and Shop arrives at the top: Shop, Dentist, Mom, Bank. With `key={index}`, Shop now has key 0. Will Dentist keep its tick? NO! Why? Because React looks at key 0, finds the row it already had under key 0, keeps that DOM node, tick included, and only changes its text from Dentist to Shop. Dentist, now key 1, gets Mom's old unticked node, and Bank, now key 3, gets a brand-new node. The tick stayed on the first row, and the first row now says Shop. Here is the good news: with `key={email.id}`, Shop arrives with a key React has never seen, 104. So React builds one new, unticked row at the top. Dentist still has key 101, so React keeps Dentist's node, tick included, and moves it down to the second row. Did you notice the detail? The index names a position, and a position belongs to whoever sits there. The ID names the email, and the email takes its tick along. So, do not confuse a key that silences the error with a key that names the email. Moral of the story: take the key from the data, an ID that never changes (Lesson 18).

> [!DEFINITION]
> **A block body.** [NEW] Remember the short arrow function `s => s + 1` (Lesson 16)? It returns what comes right after `=>`, with no `return` written. React's docs call this an implicit return. `map` works perfectly with it: `email => <li>{email.sender}</li>` returns one `<li>` for every email. But a row with a checkbox, a sender, and a subject does not fit on one line, so developers want more room, and they open curly braces right after the arrow: `email => { ... }`. Pay attention here: curly braces right after `=>` do NOT group the JSX. They open a block body, a function body like any other, and a function body returns nothing unless you write `return`. So `email => { <li>{email.sender}</li> }` builds the `<li>`, throws it away, and returns `undefined`. Let's catch it in action: three emails, three calls, and `map` hands React `[undefined, undefined, undefined]`. Will React complain? NO. React draws nothing at all for `undefined` (Lesson 3), so the inbox shows its heading and an empty list, with zero errors and zero warnings in the Console. Here is the good news: two fixes work, and they are the exact same thing. Keep the curly braces and write `return`: `email => { return <li>...</li>; }`. Or replace the curly braces with parentheses: `email => ( <li>...</li> )`. Parentheses only group the JSX, so the arrow still returns it. Moral of the story: after `=>`, a parenthesis returns the row, and a curly brace needs `return` (Lesson 18).

### Reminders placed in the text

> [!DEFINITION]
> **Props.** [REVIEW] OK, we have seen how a component returns the JSX of its own part of the page. When a parent renders a child, it passes information down as attributes on the child's tag: `<EmailRow sender="Dentist" subject="Appointment on Friday" />`. These attributes are the props. React packs them into one object and hands that object to the child as its first argument, and the child unpacks the names it needs with curly braces: `function EmailRow({ sender, subject })`. Here is the catch: the child sees ONLY what the parent wrote on its tag. Inside `EmailRow`, there is no `email` and no `emails`. So when a row moves out of `map` and into its own file, every value it reads must arrive on its tag (Lesson 8).

> [!DEFINITION]
> **`key` is not a prop.** [REVIEW] OK, we have seen that every attribute on a component tag becomes a prop. Well... almost every attribute. `key` is the famous exception. React reads `key` for itself, to match the rows, and removes it before it builds the props object. So `<EmailRow key={email.id} sender="Dentist" />` gives `EmailRow` one prop only: `sender`. Will `EmailRow` find 101 if it unpacks `{ key }`? NO, it gets `undefined`, and React prints an error in the Console that starts with `EmailRow:` and says that `key` is not a prop. Why does React keep it? Because a key is a hint for React, not data for your component. React's docs say it is important "to separate app logic from hints to React". Here is the good news: if the child needs the same value, you pass it again, under a normal name: `<EmailRow key={email.id} id={email.id} />`. It looks redundant, but the two do different jobs: `key` tells React which row this is, and `id` hands the number to `EmailRow` (Lesson 8).

## Principles

### Principle 1: I Mapped Three Emails, So Why Is My Inbox Empty?

- **Rule**: In `map`, return the row: write it right after `=>`, wrapped in parentheses when it takes several lines, or write `return` inside the curly braces. Do not open curly braces after `=>` and forget `return`.
- **Real beginner mistake**:
  1. The row needs a checkbox, a sender, and a subject, so the developer wants several lines.
  2. The developer opens curly braces right after `=>` to make room.
  3. The developer writes the `<li>` inside, and no `return`.
  4. The page shows the heading `Inbox` and an empty list.
  5. The Console is quiet, so the developer suspects the data.
- **Wrong code**:
  ```jsx
  {emails.map(email => {
    <li>
      <input type="checkbox" /> <b>{email.sender}</b>: {email.subject}
    </li>;
  })}
  ```
- **Right code**:
  ```jsx
  {emails.map(email => (
    <li>
      <input type="checkbox" /> <b>{email.sender}</b>: {email.subject}
    </li>
  ))}
  ```
- **Proof on the screen**:
  - With the wrong code: the heading `Inbox`, then nothing. The Elements panel shows an empty `<ul></ul>`. The Console is quiet (lab `p1-wrong`).
  - The steps:
    1. `map` calls the arrow function three times, once per email.
    2. Each call opens a block body, builds the `<li>`, and reaches the closing brace with no `return`.
    3. Each call returns `undefined`, so `map` returns `[undefined, undefined, undefined]`.
    4. React draws nothing for `undefined`, with no message.
  - With the right code: the three rows appear, and the Console shows the error `Each child in a list should have a unique "key" prop.` with `Check the render method of `Inbox`.` (lab `p1-right`).
- **Definitions it uses**: **Rows from an array with `map`**, **A block body**.
- **Side by side**:
  1. "with parentheses, `email => ( <li>...</li> )`" vs. "with curly braces and no `return`, `email => { <li>...</li> }`": NOT the same thing. Parentheses group the JSX; curly braces open a body that returns `undefined`.
  2. "with parentheses" vs. "with curly braces and `return`": the exact same thing.
  3. "`emails.map(...)`" vs. "`emails.forEach(...)`": NOT the same thing. `forEach` runs the function for each email and returns `undefined`, so the list is empty the same way (lab `p1-foreach`).
- **Where did that come from?**:
  - `email` inside the arrow function: no line declares it. `map` passes the first email on the first call, the second on the second, the third on the third.
  - `undefined` in the array: no line writes it. A function body that ends without `return` gives `undefined`.
- **Move**: Side by side, for the parenthesis and the curly brace after `=>`, which differ by two characters.
- **React does**: the empty `<ul></ul>` and a quiet Console with the block body (lab `p1-wrong`); three rows and the missing key error with the parentheses (lab `p1-right`). React 19 prints the error without the `Warning:` prefix the docs show.
- **Interview depth**:
  - `map` builds a new array and leaves `emails` unchanged (MDN; lab `c0-plain`: `names after map ["Anna","Ben","Cara"]`).
  - `filter` then `map` shows only some items, as the docs do with chemists.
  - The `map` call can sit inside the JSX or in a variable above `return`; React only needs an array of JSX in the end. The docs: "all that matters is that you give it an array of JSX nodes in the end."
- **Example step**: `src/components/Inbox.jsx` holds the constant `emails` above the component, the heading, and the list. The step ends with the parentheses fix and the missing key error in the Console.

### Principle 2: I Ticked Dentist, So Why Is Shop Ticked Now?

- **Rule**: Give each row a key from the data that never changes, `key={email.id}`. Do not use the index on a list that gets items inserted, removed, or reordered, and never make the key during the render, as with `key={Math.random()}`.
- **Real beginner mistake 1**:
  1. The developer sees the missing key error.
  2. `map` already offers a second argument, `index`, so the developer writes `key={index}`.
  3. The Console goes quiet.
  4. The user ticks Dentist and clicks `Check mail`.
  5. Shop is ticked, and Dentist is not.
- **Real beginner mistake 2**:
  1. A teammate sees that the index moves to another email.
  2. The teammate wants a key that is always unique and writes `key={Math.random()}`.
  3. The user ticks Dentist and clicks `Check mail`.
  4. Every checkbox is unticked.
- **Wrong code 1**:
  ```jsx
  {emails.map((email, index) => (
    <li key={index}>
      <input type="checkbox" /> <b>{email.sender}</b>: {email.subject}
    </li>
  ))}
  ```
- **Wrong code 2**:
  ```jsx
  <li key={Math.random()}>
  ```
- **Right code**:
  ```jsx
  {emails.map(email => (
    <li key={email.id}>
      <input type="checkbox" /> <b>{email.sender}</b>: {email.subject}
    </li>
  ))}
  ```
  with the data and handler:
  ```jsx
  const initialEmails = [
    { id: 101, sender: 'Dentist', subject: 'Appointment on Friday' },
    { id: 102, sender: 'Mom', subject: 'Dinner on Sunday?' },
    { id: 103, sender: 'Bank', subject: 'Your statement is ready' },
  ];

  let nextId = 104;

  export default function Inbox() {
    const [emails, setEmails] = useState(initialEmails);

    function handleCheckMail() {
      const newEmail = { id: nextId++, sender: 'Shop', subject: 'Your parcel has shipped' };
      setEmails([newEmail, ...emails]);
    }
    ...
  }
  ```
- **Proof on the screen**:
  - With `key={index}`: tick Dentist, click `Check mail`: `Shop` ticked at the top, `Dentist` unticked on the second row. The steps are the five steps of the intro scenario. Console quiet (lab `p4-index`, `p4-index-nodes`, run with the row inside `EmailRow`; the same files with the `<li>` directly in `map` are `unconfirmed` until the lab run of the lecture).
  - With `key={Math.random()}`: the same clicks leave every checkbox unticked. The steps:
    1. The first render gives each row a random key.
    2. `Check mail` renders `Inbox` again, and `Math.random()` gives four new numbers.
    3. React finds none of the old keys, so it removes the three old rows with their DOM nodes, tick included.
    4. React builds four new rows, all unticked.
    Console quiet (lab `p4-random`, `p4-random-nodes`: "new node" for all four rows). The docs: "This will cause keys to never match up between renders, leading to all your components and DOM being recreated every time. Not only is this slow, but it will also lose any user input inside the list items."
  - With `key={email.id}`: Shop arrives unticked at the top, Dentist keeps its tick on the second row; React builds one new node, for key 104, and keeps the others (lab `p4-id`, `p4-id-nodes`).
- **Definitions it uses**: **A commit**, **A key**, **The index vs. an ID from the data**, **State and its setter**.
- **Side by side**:
  1. "with `key={index}`" vs. "with `key={email.id}`": the exact same screen on the first load, NOT the same thing after a new email at the top.
  2. "with no key" vs. "with `key={index}`": the exact same matching, by position. Only the Console differs: no key prints the error, `key={index}` prints nothing.
  3. "`id: nextId++` in the handler" vs. "`key={Math.random()}` in the JSX": NOT the same thing. The first runs once, when the email is created, and the number stays with the email. The second runs on every render and gives a new number every time.
- **Where did that come from?**:
  - `index`: no line declares it. `map` passes the position as the second argument of the arrow function.
  - `104` for Shop: no line writes 104. `nextId++` reads `nextId`, which starts at 104, puts it in `newEmail`, and then adds 1, so the next new email gets 105.
  - The old emails in the new array: `...emails` copies them in after `newEmail` (Lesson 17 for the three dots, Lesson 19 for arrays).
  - The tick: no line of our code writes it. The browser stores it in the checkbox's DOM node.
- **Move**: Steps for a surprise. A tick that jumps to an email the user never touched is something the reader would not expect.
- **React does**: the screens above; the Console is quiet for all three versions; the Elements panel shows `<input type="checkbox">` with no `checked` attribute on the ticked box, because a user's tick changes only the checkbox's checked property (lab `p4-index`).
- **Interview depth**:
  - The index is fine only for a list that never changes order and holds nothing the user marks or types; the docs' poem.
  - Keys must be unique among siblings, not across the whole page.
  - A key that changes on purpose resets a component, the docs' "Resetting state with a key": Lesson 25.
  - The docs' Challenge "Fix misplaced state in the list": the expanded email moves to another contact because the list used the index.
  - `crypto.randomUUID()` is right when the item is created, and wrong inside the JSX for the same reason as `Math.random()`.
- **Example step**: `Inbox.jsx` gains `useState`, `initialEmails`, `nextId`, `handleCheckMail`, and the `Check mail` button. The step ends with `key={email.id}`.

### Principle 3: I Gave the li a key, So Why Does the Console Still Ask for One?

- **Rule**: Put the key on the element directly inside `map`. When the row moves into its own component, the key goes on `<EmailRow key={email.id} />` in `Inbox`, not on the `<li>` inside `EmailRow`.
- **Real beginner mistake**:
  1. The row grows, so the team moves it into `EmailRow.jsx`.
  2. The developer cuts the `<li key={email.id}>...</li>` out of `map` and pastes it into `EmailRow`.
  3. Inside `EmailRow` there is no `email`, so the developer passes `id`, `sender`, and `subject` as props and writes `<li key={id}>`.
  4. In `Inbox`, `map` now returns `<EmailRow id={email.id} sender={email.sender} subject={email.subject} />`, with no key.
  5. The Console shows the missing key error again.
- **Wrong code**:
  ```jsx
  export default function EmailRow({ id, sender, subject }) {
    return (
      <li key={id}>
        <input type="checkbox" /> <b>{sender}</b>: {subject}
      </li>
    );
  }
  ```
  ```jsx
  {emails.map(email => (
    <EmailRow id={email.id} sender={email.sender} subject={email.subject} />
  ))}
  ```
- **Right code**:
  ```jsx
  export default function EmailRow({ sender, subject }) {
    return (
      <li>
        <input type="checkbox" /> <b>{sender}</b>: {subject}
      </li>
    );
  }
  ```
  ```jsx
  {emails.map(email => (
    <EmailRow key={email.id} sender={email.sender} subject={email.subject} />
  ))}
  ```
- **Proof on the screen**:
  - With the wrong code: the three rows look right, and the Console shows `Each child in a list should have a unique "key" prop.` with `Check the render method of `Inbox`.` (lab `p2-mistake2-id`).
  - The steps:
    1. `map` in `Inbox` returns three `<EmailRow />` elements.
    2. React looks for a key on those three elements, the siblings of the list, and finds none.
    3. The `key` on the `<li>` inside `EmailRow` sits inside a component that returns one `<li>`, not a list, so it does not help.
    4. React names `Inbox` in the error, the component whose `map` lacks the key.
  - With no key on `<EmailRow />`, React matches the rows by position again, so the tick bug of Principle 2 is back (from the docs: the index is "what React will use if you don't specify a `key` at all"; the screen is `unconfirmed` until the lab run).
  - With the right code: three rows, a quiet Console, and the Elements panel shows `<li><input type="checkbox"> <b>Dentist</b>: Appointment on Friday</li>`, with no `key` attribute (lab `p2-right`).
- **Definitions it uses**: **Props**, **A key**.
- **Side by side**:
  1. "the key on the `<li>` inside `EmailRow`" vs. "the key on `<EmailRow />` inside `map`": NOT the same thing. Only the element `map` returns is a sibling in the list.
  2. "`<li key={email.id}>` directly in `map`" vs. "`<EmailRow key={email.id} />` in `map`": the exact same rule. The key goes on whatever `map` returns.
  3. "`<Fragment key={email.id}>`" vs. "`<>...</>`": NOT the same thing. When one item returns two siblings, only `Fragment` can take the key; the short form takes no attributes (Lesson 2; docs Fragment Caveats).
- **Where did that come from?**:
  - `sender` and `subject` inside `EmailRow`: they come from the attributes on `<EmailRow ... />` in `Inbox`, packed by React into the props object (Lesson 8).
  - `EmailRow` in `Inbox`: from `import EmailRow from './EmailRow.jsx'` at the top of `Inbox.jsx`.
- **Move**: Side by side, for the two places the key can sit.
- **React does**: the error naming `Inbox` with the key on the inner `<li>` (lab `p2-mistake2-id`); a quiet Console and no `key` in the Elements panel with the key on `<EmailRow />` (lab `p2-right`).
- **Interview depth**:
  - The docs' Challenge "Extracting a list item component": "when you extract a component, don't forget to leave the `key` outside the JSX you copy and paste."
  - `<EmailRow {...email} />` passes `id`, `sender`, and `subject`, but no key, because the object has no `key` field: the missing key error stays (lab `p2-spread`). `<EmailRow key={email.id} {...email} />` is clean (lab `p2-spread-key`). A spread object that holds a `key` field prints `A props object containing a "key" prop is being spread into JSX` (lab `p2-spread-keyfield`).
  - The same keys may appear in two different lists on one page.
- **Example step**: the new file `src/components/EmailRow.jsx`; `Inbox.jsx` imports it and returns `<EmailRow key={email.id} ... />` from `map`. Nothing changes on the screen.

### Principle 4: I Gave Every Row a key, So Why Does the Child Get undefined?

- **Rule**: When the child needs the ID, pass it again as a normal prop, `id={email.id}`, next to `key={email.id}`. Do not read `key` inside the child.
- **Real beginner mistake**:
  1. The team wants a click on the sender or the subject to tick the box, so the text goes inside a `<label>` linked to the checkbox with `htmlFor`.
  2. `htmlFor` needs an id that is different on every row, such as `mail-101`.
  3. The row already has `key={email.id}`, so the developer unpacks `{ key }` in `EmailRow` and builds `'mail-' + key`.
  4. The Console shows an error about `key`, and every row gets `mail-undefined`.
  5. The user clicks Mom's text, and Dentist's box is ticked.
- **Wrong code**:
  ```jsx
  export default function EmailRow({ key, sender, subject }) {
    const inputId = 'mail-' + key;
    return (
      <li>
        <input type="checkbox" id={inputId} />
        <label htmlFor={inputId}><b>{sender}</b>: {subject}</label>
      </li>
    );
  }
  ```
- **Right code**:
  ```jsx
  <EmailRow key={email.id} id={email.id} sender={email.sender} subject={email.subject} />
  ```
  ```jsx
  export default function EmailRow({ id, sender, subject }) {
    const inputId = 'mail-' + id;
    return (
      <li>
        <input type="checkbox" id={inputId} />
  ```

- **Proof on the screen**:
  - With the wrong code: on load, the Console shows `EmailRow: `key` is not a prop. Trying to access it will result in `undefined` being returned. A click on `Mom: Dinner on Sunday?` ticks Dentist's box, and Mom's stays empty (lab `p3-wrong`).
  - The steps:
    1. `Inbox` writes `key={email.id}` on each `<EmailRow />`.

  - `id` inside `EmailRow`: the attribute `id={email.id}` on the tag in `Inbox`.

## Interview Points

- Render a list by turning the data array into an array of JSX with `map`, inside the curly braces of the list.
- The arrow function must return the row: a row right after `=>` or in parentheses is returned; curly braces need `return`, or the list renders empty with no message.
- React needs a key on every element `map` returns, to match each row of this render with a row of the last render.
- Without a key, React matches by position and prints `Each child in a list should have a unique "key" prop.`
- React keeps the DOM node of a matched row, so a tick, typed text, or state inside the row stays with the matched key.
- The key must be unique among siblings and must not change; take it from the data.
- The index as a key silences the error but keeps matching by position: insert at the top, and the first row's tick lands on the new item.
- `Math.random()` as a key makes new keys on every render: React rebuilds every row, slowly, and loses every tick and typed text.
- No ID in the data: make one once, when the item is created, with a counter or `crypto.randomUUID()`.
- The key goes on the element directly inside `map`: on the component tag once the row is its own component, or on `<Fragment key>` for several siblings per item.
- `key` is not a prop: React keeps it and the child gets `undefined`; pass the value again as a normal prop, such as `id`.
- Why: keys are hints for React, kept apart from the data your component uses.
