Lecture 31: Watching Reactive Values with $inspect

Interview Question

CORE

How do you inspect reactive values while developing?

Imagine this scenario:

  1. A journalist in the National Times newsroom types a headline.
  2. The character counter under the field reads zero and stays there.
  3. Why is the number stuck?
  4. You print the headline value to the console, a panel inside the browser's developer tools.
  5. The value appears once, when the page loads, then never again.
  6. The console stays silent.
  7. You need a tool that follows every single change.

The Log That Prints Once

Svelte runs the code inside a component's <script> block exactly once, at the moment the component is created. That code is initialization code, the setup phase of the component's life. A plain console.log sitting in the script executes during that single pass and then never again, no matter how many times your state changes afterwards. The log is frozen at the first value while the screen keeps moving, which is exactly why the headline prints once and then goes silent.

The newsroom layout system rejects headlines longer than ninety characters, and the counter on the screen insists the field is empty while the deadline approaches. You open the developer tools and print the value, and you get one line of output. You need a print statement that re-executes every time the value changes, and Svelte ships exactly that tool for development. Look first at the component that owns the value.

The plain call prints the empty string exactly once and stays silent. The second line keeps printing as the journalist types, one line per keystroke. The reason the second line works at all is that it is not a normal function call but a rune, a Svelte function whose name starts with a dollar sign and that carries special powers. This particular rune is called $inspect, and its power is that it re-runs whenever its argument changes. The traces prove the input binding works and point at the frozen count line, computed once with a plain assignment. The screen is wrong, the value is right, and now you know which half of the connection broke.

A Log That Follows the Value

$inspect is roughly a console.log that re-runs whenever its argument changes. You can pass several values at once, and the rune re-fires when any one of them changes. It also tracks state deeply: update something inside an object or an array and it re-fires, because Svelte 5 watches the individual pieces of a value, not just the top-level variable.

Every update also prints a stack trace, the list of function calls that led to the change. The trace names the file and line where the change happened, so when the counter is wrong you can see exactly which click handler or binding touched the value. The console does not just tell you that the value moved, it tells you who moved it.

Here is the same rune watching two values at once, a headline and its publication state.

HeadlineForm.svelte
1<script>
2 let headline = $state('');
3 let published = $state(false);
4
5 $inspect(headline, published);
RIGHT: Re-fires when either value changes.
6</script>
7
8<input bind:value={headline} placeholder="Type the headline" />
9<button onclick={() => published = !published}>{published ? 'Unpublish' : 'Publish'}</button>

Type in the field and one line appears; click the button and another line appears, each with a stack trace pointing at the exact handler or binding.

Taking Control of the Output

Sometimes the default output is not enough. You may want to pause the browser only when the headline crosses the ninety-character limit, instead of on every keystroke. $inspect returns an object with a with method, and that method accepts your own callback in place of the default print.

The callback receives a type as its first argument, either "init" when the rune first runs or "update" on every later change, followed by the watched values in order. That type string lets you write a breakpoint that only fires when the value actually changes.

HeadlineForm.svelte
1<script>
2 let headline = $state('');
3
4 $inspect(headline).with((type, value) => {
5 if (type === 'update' && value.length > 90) {
6 debugger;
RIGHT: Pauses the browser exactly when the headline gets too long.
7 }
8 });
9</script>
10
11<input bind:value={headline} placeholder="Type the headline" />
12<p>Characters: {headline.length}</p>

The debugger statement freezes the browser's JavaScript at that exact moment, so you can inspect the variables, the call stack, and the state of the page while the limit is being crossed.

Free in Production

$inspect only works during development. In a production build it becomes a noop, an operation that does nothing, because the compiler removes it entirely from the output. The rune costs nothing to ship, prints nothing to your readers' consoles, and leaks no internal state. You can leave every $inspect line in your code permanently and forget about them, which is something you can never say about a stray console.log.

Interview Tip

To impress the interviewer: Stress that $inspect is a development-only rune: a production build compiles it away to a noop, so unlike console.log it adds zero bytes and zero noise. Then add that .with hands you the change type, letting you drop a debugger breakpoint that fires only when a value crosses a threshold.

Key Takeaway

When the value moves but the screen does not, the change never reached the variable the markup reads. $inspect shows you which half of that connection is broken.

Summary

Svelte runs component scripts once, so a plain console.log freezes at the first value. The $inspect rune is a development-only print that re-runs on every change, tracks values deeply, and prints a stack trace naming the origin of each change.

  • console.log executes once at component creation and never re-runs.
  • $inspect re-runs whenever any watched value changes, and tracks nested values too.
  • Each update prints a stack trace that names the file and line that caused the change.
  • .with replaces the default print with your own callback, receiving "init" or "update" plus the values.
  • In production the rune compiles away to a noop, so it is free to leave in your code.
