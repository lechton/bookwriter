Lecture 1: What is Svelte?

Interview Question

CORE

What is Svelte, and how does it differ from frameworks like React and Vue?

You've heard Svelte "has no virtual DOM" — but what does that actually mean, and why does it matter for performance?

When building web applications, developers want to write declarative code (saying what the UI should look like based on state) instead of imperative code (writing out the exact steps to update the DOM). Frameworks like React and Vue achieve this by doing heavy work in the browser while the user is using the app. They load a large "runtime" engine, keep a memory representation of the entire UI (the Virtual DOM), and constantly compare the old state to the new state to figure out what changed.

Svelte takes a fundamentally different approach. It is not just a library you include in your webpage; it is a compiler.

The Compiler Advantage

Instead of doing the work in the browser, Svelte does the heavy lifting on your computer during the build step. It analyzes your .svelte files (which contain HTML, CSS, and JavaScript) and compiles them into highly optimized, standard JavaScript before the code is ever sent to the user.

Key Takeaway

What the DOM is to HTML, the AST is to code.

Just as the browser parses a flat HTML string into a Document Object Model (DOM) tree so it can manipulate the web page, a compiler parses a flat string of code into an Abstract Syntax Tree (AST) so it can analyze and manipulate the program. Svelte reads your declarative components, builds an AST, and figures out exactly how the state connects to the DOM.

Because Svelte knows exactly what can change at compile time, it generates vanilla JavaScript that directly targets those specific DOM nodes.

App.svelte
1<script>
2 let count = $state(0);
3
4 function increment() {
5 count += 1;
Directly updates the TEXT node, no diffing required
6 }
7</script>
8
9<button onclick={increment}>
10 Clicks: {count}
11</button>

No Virtual DOM

Interview Tip

To impress the interviewer: During an interview, most candidates will simply state that "Svelte doesn't use a Virtual DOM." If you want to show deep technical background, explain why it doesn't need one — this proves you understand the mechanics, not just the marketing.

React and Vue need a Virtual DOM because their runtime doesn't know what changed until it diffs the old virtual tree against the new one. Svelte doesn't need a Virtual DOM because its compiler has already wired the variable count directly to the specific text node inside the <button>. When count changes, Svelte's generated code surgically updates that exact spot.

By compiling away the framework, Svelte delivers smaller bundle sizes, faster initial load times, and eliminates the runtime overhead of diffing trees in memory.

Summary

Svelte shifts the heavy lifting of building user interfaces from the browser (runtime) to your local machine (compile time). It takes declarative components and compiles them into highly optimized JavaScript that updates the DOM surgically, without needing an intermediate Virtual DOM.

Lecture 2: Setting up a Svelte Project

Interview Question

CORE

How do you create and run a new Svelte project?

You want to start a Svelte app today. What command do you run, what does it give you, and how do you see it in the browser?

Starting a new project in modern Svelte is done entirely through a dedicated command-line tool. Unlike the early days where you might have manually wired up a bundler, the Svelte team now provides an official, zero-configuration pathway.

The Modern Standard: sv create

The easiest and official way to create a Svelte project is to use the sv CLI. This tool generates a complete, ready-to-run skeleton for your application.

Terminal
1npx sv create myapp
1. generate a new SKELETON project
2cd myapp
2. enter the directory
3npm install
3. fetch all required DEPENDENCIES
4npm run dev
4. start the local DEVELOPMENT server

When starting a new project, you need a place to put all your files, your settings, and your codebase. Should we manually create every single folder? Should we create an index.html, then a styles.css, and manually link them together one by one? This is a decision about how we build the foundation of our app. We need a way to instantly generate the correct folders and baseline files so we don't make mistakes setting up the architecture. This automated generation of the foundation is called scaffolding an application. When you run npx sv create, you are scaffolding a SvelteKit application.

Key Takeaway

SvelteKit is not an optional add-on; it is the official operating system for Svelte.

SvelteKit is the official framework built on top of Svelte (powered by Vite under the hood). To understand why it exists, we must look at what a full app needs.

When you create a full app, you need to make some decisions on how to present new pages. Should we name new pages automatically with "p", for example, /p/1 is page 1, and /p/2 is page 2? Or maybe we should write /page-1 for page 1? This is a decision about the architecture of our app. We have to make sure that when a specific path is visited by the user in the browser (e.g., mywebsite.com/page/1), a specific part of our app is activated. This matching mechanism is called the router of the app. The router makes sure to match all the paths with the proper components.

SvelteKit provides this router for you. Just as an operating system provides the file system and networking for software, SvelteKit provides the architecture for your Svelte components to live in.

Furthermore, when a user clicks a link to go to a new page, the browser usually talks to a server, downloads a brand new HTML document, and the screen flashes white while loading. Do we always want that flash? What if we just download the entire website's structure once, and then use JavaScript to swap out the content instantly when the user clicks a link? This is a decision about how our app behaves. We need a way for the app to feel as fast as a desktop program without constantly asking the server for new pages. An app that loads once and swaps content dynamically without refreshing is called a Single-Page Application (SPA).

Even if you only want to build a simple SPA and don't know the rest of SvelteKit yet, the team recommends using the npx sv create command. You can safely ignore the advanced features until you need them.

Interview Tip

To impress the interviewer: Mention that npx sv create scaffolds a SvelteKit project by default. Point out that the ecosystem has shifted away from standalone Svelte templates, and that SvelteKit is now the recommended baseline even for simple client-side apps.

The Development Server

After running npm run dev, Vite spins up a local web server (usually at http://localhost:5173). This server watches your files for changes. When you edit a component, Vite leverages Hot Module Replacement (HMR) to instantly push the updated compiled code to your browser without requiring a full page refresh.

The Standalone Alternative

If you absolutely must avoid SvelteKit (perhaps you are integrating Svelte into a legacy backend that serves its own HTML), you can use Vite directly:

Terminal
1npm create vite@latest myapp -- --template svelte
Creates a STANDALONE Svelte setup

This bypasses SvelteKit entirely, giving you a bare-bones Svelte project. However, you will have to handle routing and server-side rendering yourself.

Summary

To start a new Svelte project, run npx sv create myapp. This command scaffolds a complete application structure powered by SvelteKit and Vite. After installing dependencies with npm install, you use npm run dev to start a local development server that instantly reflects your code changes in the browser.

Lecture 3: The Anatomy of a Svelte Component

Interview Question

CORE

What are the three parts of a .svelte file, and what is each one for?

You open a .svelte file for the first time and see script, markup, and style all in one place. How do these three pieces fit together?

A Svelte component is a self-contained building block for your user interface. It is written in a .svelte file that uses a superset of HTML. Inside this single file, you can define three distinct sections. All three sections are entirely optional—you only include what you need.

1. The <script> Block (Logic)

The <script> block contains the JavaScript (or TypeScript) that controls how your component behaves.

When we define a user profile card in our code, we usually want to show more than one user on the screen at once. Should we copy and paste the profile card code three times? Or do we write it once as a blueprint, and then tell the framework "build me three of these"? This is a decision about how we reuse code. We need a way to stamp out multiple independent copies of the same UI blueprint, where each copy holds its own independent state (like its own name or counter variable). Each independent copy built from the blueprint is called a component instance.

The code inside the <script> block runs every time a new component instance is created. Any variable you declare here becomes the private, local state for that specific copy.

Profile.svelte
1<script>
2 let name = 'Alice';
Creates local state for this specific INSTANCE
3</script>

The <script module> Alternative

We know each copy of a component keeps its own private data. But what if all the copies need to talk to each other?

Imagine you are building a webpage with five audio players on it (like a podcast list). When a user clicks "Play" on Player #3, Player #1 needs to pause. You don't want two podcasts playing over each other. But if we build an AudioPlayer.svelte component and stamp out 5 copies, we have 5 independent "islands." Player #1 has no idea that Player #3 even exists.

So how do we make the 5 islands talk to each other? Do we pass messages all the way up to the main webpage, and then back down to all the other players telling them to stop? That’s exhausting. Do we create a completely separate JavaScript file just to hold one variable called currentlyPlaying? That feels like overkill.

This is a decision about data architecture. We need a way for these 5 component instances to share a single, communal brain. We want exactly one variable that all 5 players can look at and update. We need a place inside our .svelte file to run code exactly once, when the file is first loaded, rather than every time a new player is stamped out.

Visual Target: Five Independent Audio Players

The page we want contains five independent instances of one AudioPlayer.svelte definition. Each player keeps its own audio source, while all five can see and update one shared currently-playing value. Because the module script only runs once, any variable you put inside it is shared across every single copy of that component on the screen.

2. The Markup (Structure)

The markup is the HTML structure of your component. It sits outside of any tag, directly in the body of the .svelte file. You can freely reference any variable declared in your <script> block inside your markup.

Key Takeaway

A Svelte file is just HTML with superpowers, not JavaScript with HTML crammed inside it.

If you look at a React component, you are fundamentally writing a JavaScript function that happens to return HTML (via JSX). In Svelte, you are fundamentally writing an HTML file that happens to include logic. This inversion means that any valid HTML file is already a valid Svelte component.

3. The <style> Block (Aesthetics)

The <style> block contains the CSS for your component.

When we write CSS for our components, we need a way to style elements like a <p> tag. Should we just put p { color: red; } in our CSS? But what if another component also has a <p> tag? Will they all turn red, leaking styles everywhere? Do we need to invent complex class names like class="my-unique-component-p-tag" for every single element?

This is a decision about the architecture of our CSS. We need a way to guarantee that the styles written inside a file only affect the elements in that exact file, and nowhere else in the app. This guaranteed isolation is called scoped styling. Scoped styling ensures that your CSS cannot accidentally leak out and break other parts of your application.

Profile.svelte
1<style>
2 p {
3 color: burlywood; /* ✔️ safely **SCOPED** to this component only */
4 }
5</style>

Interview Tip

To impress the interviewer: When asked about .svelte files, emphasize that scoping is handled automatically by the compiler. You don't need external tooling like CSS Modules or BEM naming conventions; Svelte simply hashes the classes for you.

Summary

A .svelte file consists of three optional parts. The <script> block holds the JavaScript logic that runs when a component instance is created, managing its local state. The HTML markup defines the structure of the component and can reference variables from the script. Finally, the <style> block contains CSS that is automatically scoped to affect only the markup within that specific file, preventing global style leaks.

Lecture 4: Creating Reactive Variables

Interview Question

CORE

How do you create reactive variables in Svelte?

You change a variable in your script, but the screen doesn't update. Why, and how do you make it update?

When building an application, you often have data that changes over time, like a user's score, a toggled dark mode setting, or text typed into an input field.

The Problem with Plain Variables

Imagine you have a button that increases a counter. You write let count = 0; in your script, and in your click function you do count = count + 1.

In regular JavaScript, if you change count = 1, does the <h1> tag displaying that number on the screen automatically update? No. You would have to manually find the HTML element (e.g., document.getElementById) and forcefully update its text every single time the number changes. This is exhausting and error-prone.

We need a system where the HTML "listens" to our variables. When the variable changes in the script, the HTML should update itself automatically without us writing manual DOM manipulation code. This automatic synchronization between your variables and your screen is called reactivity. Reactivity ensures that your user interface always perfectly reflects the current state of your data.

How to Tell Svelte About Reactivity

If regular JavaScript doesn't have reactivity, how does Svelte know which variables should trigger screen updates?

Should we wrap every single variable in a heavy, complex JavaScript object like new ReactiveVariable(0) and call special methods like count.set(1) to change them? Other frameworks do this, but it makes writing simple math and logic very tedious.

We want to write normal JavaScript, like count++, but we need a way to tell the Svelte compiler, "Hey, this specific variable is special. Please add the secret reactivity code to it when you build my app." In Svelte 5, these special compiler symbols are called runes. Runes are just visual flags that tell the compiler to upgrade a normal variable into a reactive one.

Key Takeaway

Runes are not JavaScript functions; they are instructions for the Svelte compiler.

Because runes are compiler instructions rather than runtime library functions, you don't even need to import $state. It acts as a built-in keyword in the Svelte language.

The $state Rune

To make a variable reactive, you initialize it with the $state rune.

Counter.svelte
1<script>
2 let count = $state(0);
The compiler sees $state and wires up the REACTIVITY
3
4 function increment() {
5 count++;
Updates exactly like a normal VARIABLE
6 }
7</script>
8
9<button onclick={increment}>
10 Clicks: {count}
11</button>

When the increment function runs and count increases, Svelte automatically detects the assignment (=, ++, +=) and precisely updates only the part of the HTML where {count} is rendered.

Deep Reactivity

If you pass an array or an object into $state, Svelte makes it deeply reactive.

Todos.svelte
1<script>
2 let todos = $state([{ text: 'Buy milk', done: false }]);
3
4 function completeFirst() {
5 todos[0].done = true;
Triggers an update deep inside the OBJECT
6 }
7</script>

Modifying a property deep inside the object, or calling methods like todos.push(), will automatically trigger the UI to update. Svelte wraps the object in a JavaScript Proxy behind the scenes, watching for any changes to its properties.

Interview Tip

To impress the interviewer: Contrast Svelte 5's $state with React's useState. Point out that Svelte's approach allows you to update variables directly (count++) rather than requiring a setter function (setCount(count + 1)), resulting in much cleaner, more natural JavaScript.

Summary

To create reactive variables in Svelte, you use the $state rune. This tells the compiler to automatically update the user interface whenever the variable is reassigned or modified. Because it's a compiler feature, you interact with the reactive data just like normal JavaScript variables, without needing special setter functions.

Lecture 5: Handling User Events

Interview Question

CORE

How do you handle user events like clicks in Svelte?

You want a counter that goes up every time the user clicks a button. Where does the click handler go, and how does it connect to your state?

Interactive web applications rely on responding to user actions: clicking buttons, submitting forms, moving the mouse, or pressing keys.

The Problem with Manual Event Listeners

Imagine building a checkout page where a user clicks a "Buy Now" button to complete their purchase.

In vanilla JavaScript, to make that button do something, you have to query the DOM: document.getElementById('buy-btn').addEventListener('click', buyItems). This is fragile. If you accidentally rename the ID in your HTML but forget to update the JavaScript, the connection is severed. Your user clicks "Buy Now", nothing happens, and you lose the sale. Furthermore, if you dynamically create and destroy buttons, you have to manually detach those event listeners to prevent catastrophic memory leaks. The sheer disconnect between the HTML element and its JavaScript behavior creates a massive surface area for bugs.

We need a way to bind the behavior directly to the HTML element where it is defined, so they are impossible to separate.

Event Attributes

To solve this, Svelte 5 allows you to pass JavaScript functions directly into standard HTML attributes like onclick, oninput, or onkeydown. This is known as using event attributes. By wiring the event listener directly in the template, Svelte guarantees it is safely attached when the element is created and perfectly cleaned up when the element is destroyed.

Key Takeaway

In Svelte 5, event listeners are just regular properties. They don't require special framework syntax.

Wiring a Click Handler

To handle a click event, you simply define a function in your <script> and assign it to the onclick attribute of your HTML element.

Notice the syntax: onclick={buyItem}. We pass the function reference directly inside the curly braces. We do not invoke the function like onclick={buyItem()}—doing so would run the function immediately when the page loads, instead of waiting for the user to click.

Accessing the Event Object

Sometimes you need details about the user's interaction, such as where they clicked on the screen or what key they pressed. When the browser triggers an event, it automatically passes an event object to your handler.

This change aligns Svelte closer to native browser standards and allows for much easier passing (spreading) of event handlers as props.

Summary

You handle user events in Svelte by assigning functions directly to HTML attributes like onclick. The function lives in your <script> block and can freely modify your $state variables. Svelte automatically manages attaching the native event listeners, ensuring your code remains tightly coupled to the UI without the fragility of manual DOM queries.

Lecture 6: Outputting Dynamic Values

Interview Question

CORE

How do you output dynamic values and set attributes in Svelte markup?

You have a variable in your script and want its value to appear inside a heading, or drive an element's class. How does markup read your script?

In modern web development, hardcoding static values into HTML is rarely enough. Your user interface needs to reflect the live data flowing through your application in real-time.

The Problem with Manual DOM Updates

Imagine you are building a shopping cart, and you need to display the current number of items. In vanilla JavaScript, you would define an empty placeholder in your HTML: <span id="cart-count"></span>. Then, in your JavaScript code, you write document.getElementById('cart-count').innerText = count. If the cart is empty, you might want to disable the checkout button by writing document.getElementById('checkout-btn').disabled = true.

You are constantly writing imperative code to reach across the boundary between HTML and JavaScript, manually gluing data into place. This is tedious to write, fragile to maintain, and easy to break if the DOM structure changes.

The Curly Braces Portal

Svelte solves this by allowing your markup to read directly from your script. By wrapping any JavaScript expression in curly braces ({}), you open a portal into your <script> block right in the middle of your HTML.

Whenever the reactive value inside the braces changes, Svelte automatically updates the exact DOM node that relies on it.

Interpolating Text

To output a variable as text, just place the curly braces inside an HTML element. Svelte will evaluate the expression, convert the result to a string, and safely inject it as text (automatically escaping it to protect you from XSS injection attacks).

Cart.svelte
1<script>
2 let username = "Alice";
3 let count = $state(3);
4</script>
5
6<h1>Welcome back, {username}!</h1>
The markup reads directly from the script variables
7<p>You have {count} items in your cart.</p>

You can put any valid JavaScript expression inside the braces, not just variable names: {count * 2}, {username.toUpperCase()}, or {count > 0 ? 'Full' : 'Empty'}.

Dynamic Attributes

You can use the exact same curly brace syntax to set HTML attributes dynamically. Instead of a hardcoded string like class="active", you pass the dynamic variable.

Button.svelte
1<script>
2 let isSubmitting = $state(false);
3 let themeColor = "blue";
4</script>
5
6<button disabled={isSubmitting} class={themeColor}>
The disabled attribute and class are driven by variables
7 Checkout
8</button>

Key Takeaway

If a boolean attribute (like disabled or checked) receives a truthy value, Svelte includes it. If it receives a falsy value, Svelte removes it completely from the DOM.

The Attribute Shorthand

Developers frequently name their variables identically to the attributes they want to control. For example, controlling an id with a variable named id, or disabled with a variable named disabled.

When the attribute name and the variable name match perfectly, Svelte provides a convenient shorthand: you can just write {name} instead of name={name}.

Input.svelte
1<script>

3 let value = "Hello";
4</script>
5

The shorthand {disabled} is identical to disabled={disabled}

To impress the interviewer: Mention that unlike some frameworks that require special prefixes to bind attributes (like v-bind:class or :class), Svelte's curly braces work exactly the same way whether you are outputting text content or setting attribute values. It’s a single, unified mental model.

Summary

To bridge the gap between your script and your markup, Svelte uses curly braces {}. This syntax evaluates JavaScript expressions and automatically updates the DOM when the underlying state changes. You can use curly braces to output text between HTML tags, or to dynamically set the values of HTML attributes. When an attribute and its controlling variable share the exact same name, Svelte offers a clean {attribute} shorthand.

Lecture 7: Derived State

Interview Question

CORE

How do you compute a value that updates automatically when its inputs change?

You have a cart total that should recalculate whenever a price or quantity changes. Writing a function to recompute it by hand feels wrong.

State is the source of truth for your application. But often, the values you display in the UI aren't the raw state itself, but rather a computation based on that state.

The Problem with Manual Recalculation

Imagine you are building a checkout page with a list of items, and you need to display the grand total. If you create a standalone $state(0) variable for the total, you must manually update it every single time the cart changes.

When a user adds an item, you must call updateTotal(). When they remove an item, you must call updateTotal(). When they apply a 10 percent discount code, you must call updateTotal(). If another developer joins the team and adds a feature to change an item's quantity but forgets to call updateTotal(), the cart goes out of sync. Your user gets charged the wrong amount, resulting in a severe customer service nightmare.

The underlying problem is that the cart data and the total are fundamentally disconnected. The total depends on the cart, but your imperative code treats them as independent variables.

The $derived Rune

To fix this, Svelte 5 introduces the $derived rune. It allows you to declare a variable that is automatically calculated from other reactive variables.

Checkout.svelte
1<script>
2 let price = $state(20);
3 let quantity = $state(2);
4
5 let total = $derived(price * quantity);
Automatically stays in SYNC
6</script>
7
8<button onclick={() => quantity++}>
9 Add Item (Total: ${total})
10</button>

When you declare let total = $derived(price * quantity), you are telling the Svelte compiler to treat this value as entirely dependent on price and quantity.

You never have to manually update total. Whenever price or quantity changes, Svelte knows it needs to recalculate total before updating the DOM.

Key Takeaway

If $state is the source of truth, $derived is the automatic reflection of that truth.

Complex Derivations with $derived.by

Sometimes your computation is too complex to fit on a single line, like iterating over an array to sum up prices. For these cases, you can use $derived.by, which accepts a function block.

Cart.svelte
1<script>
2 let cart = $state([10, 20, 30]);
3
4 let grandTotal = $derived.by(() => {
5 let sum = 0;
6 for (const item of cart) {
7 sum += item;
Iterates and sums up the REACTIVE array
8 }
9 return sum;
10 });
11</script>

Push-Pull Reactivity

Svelte uses a highly optimized system called push-pull reactivity. When a $state variable changes, Svelte immediately pushes a notification to everything that depends on it, marking those derived values as dirty. However, it doesn't actually do the mathematical recalculation yet. It waits until the exact moment the UI tries to pull or read the value. This ensures Svelte never wastes CPU cycles calculating values that are never displayed on screen.

Furthermore, if the newly calculated value happens to be identical to the old value, Svelte halts the update right there, preventing unnecessary DOM updates.

Interview Tip

To impress the interviewer: Mention that $derived replaces Svelte 4's reactive statements (the $: label). While the old syntax felt like magic, the new $derived rune behaves like a standard JavaScript variable declaration, making it much easier to reason about scope and refactor into separate .svelte.js files.

Summary

When a value in your UI depends on other reactive data, never update it manually. Instead, use the $derived rune (or $derived.by for complex logic). Svelte's compiler automatically tracks the dependencies and ensures the derived value is recalculated exactly when needed. This guarantees your UI is never out of sync with your underlying state, completely eliminating a massive class of bugs.

Lecture 8: Child Components

Interview Question

CORE

How do you use one component inside another?

Your App.svelte is getting crowded. How do you split it into smaller pieces and reference them?

As your web application grows, putting everything into a single file quickly becomes impossible to manage.

The Problem with Monolithic Files

Imagine you are building a dashboard application, and your App.svelte file has grown to 1,500 lines of code. It contains the logic for a top navigation bar, a massive collapsible sidebar, a complex interactive data grid, and a footer.

Whenever you need to fix a tiny bug in the sidebar, you have to scroll past hundreds of lines of unrelated data grid logic, desperately searching for the exact <div> you need to change. Worse, because all the variables and styles are trapped in the same global scope of that file, a teammate might accidentally change a variable meant for the header and inadvertently break the footer. Your codebase has become a tangled, fragile monolith.

Splitting into Child Components

To solve this, Svelte allows you to break your user interface into smaller, entirely self-contained building blocks called components.

Instead of one giant file, you cut the sidebar logic out and paste it into its own file named Sidebar.svelte. You do the same for the header in Header.svelte. Each component encapsulates its own HTML markup, its own CSS styling, and its own JavaScript logic.

Lecture 13: Iterating with Each Blocks

Interview Question

CORE

How do you render a list of items from an array, and why does each need a key?

You have ten users and want a row for each. When you sort the list, the rows lose their state and input values jump around. What went wrong?

Most web applications display lists of data: a feed of social media posts, a grid of products, or a table of users.

The Identity Crisis

Imagine you are building a banking dashboard with a list of "Pending Transactions". Each transaction row has a text input where the user can type a memo before approving it. The user types "Rent" into the first input, then clicks a button to sort the transactions by date.

Suddenly, the "Rent" note jumps to a completely different transaction, attaching itself to a $5 coffee bill! What went wrong?

Without strict instructions, a rendering engine takes the path of least resistance. When the array sorted, it didn't actually move the HTML rows around. Instead, it left the HTML elements exactly where they were, and just updated the text inside them to match the new array order. But the text you typed into the <input> wasn't part of the array data; it was internal DOM state. Because the row itself never moved, the input text stayed at the top of the list, while the transaction data shifted beneath it.

The {#each} Block

To render a list of items in Svelte, you use the {#each} block. It takes an array and loops through it, rendering a block of HTML for every item.

To prevent the catastrophic identity crisis described above, Svelte allows you to define a key by providing a unique identifier in parentheses at the end of the declaration.

Transactions.svelte
1<script>
2 let transactions = $state([
3 { id: 'tx_1', amount: 50, merchant: 'Coffee Shop' },
4 { id: 'tx_2', amount: 1200, merchant: 'Landlord' }
5 ]);
6</script>
7
8{#each transactions as tx (tx.id)}
The (tx.id) is the unique key mapping data to the DOM
9 <div class="row">
10 <p>{tx.merchant}: ${tx.amount}</p>
11 <input placeholder="Add memo..." />
12 </div>
13{/each}

Why Keys are Mandatory

When you provide (tx.id) as the key, you are making a binding contract with the Svelte compiler. You are telling it: "This specific piece of data is permanently married to this specific HTML <div>."

Now, when the array is sorted, Svelte will not cheat by just updating the text. It will grab the exact DOM node tied to tx_2 and physically move it down the page. Because the entire HTML element moves, any internal state (like the text the user typed into the memo input, or CSS animations currently playing on that node) moves perfectly with it.

Key Takeaway

Always use a unique, stable database ID for your key. Never use the array index ((index)) as a key if the list can be reordered, because the index of an item changes when it moves, defeating the entire purpose of the key.

Summary

To render arrays of data, wrap your markup in an {#each array as item} logic block. To ensure the DOM updates safely and predictably when the array changes, you must provide a unique identifier for every item using the (key) syntax. This key locks the data to a specific DOM node, ensuring that sorting, filtering, or deleting items physically moves the correct HTML elements, preserving any internal DOM state like focus or user input.

Lecture 15: Side Effects

Interview Question

CORE

How do you run a side effect when something reactive changes, and how do you clean it up?

You need to save a value to localStorage every time it changes, and remove an event listener when the effect re-runs or the component dies. Where does that logic live?

While $derived is used to calculate new data for your UI, sometimes you need to step outside of the UI and interact with the external world. These external interactions are called side effects.

The Problem with Unmanaged Effects

Imagine you are building a document editor that automatically saves the user's progress to the browser's localStorage every time they type. If you just put localStorage.setItem('doc', text) floating loose in your <script> block, it will only run exactly once when the component is first created. When the user types, the text variable updates, but the loose code never runs again.

Conversely, if you manually add a window.addEventListener('resize', updateLayout) inside a component but forget to remove it when the user navigates away, you have created a memory leak. Every time the user visits that page, another permanent event listener is added, eventually grinding the browser to a halt. You need a safe, reactive wrapper for external code.

The $effect Rune

To solve this, Svelte 5 provides the $effect rune. It runs a block of code after the component has mounted to the DOM, and automatically re-runs that code whenever any reactive state inside it changes.

Editor.svelte
1<script>
2 let text = $state("Initial content");
3
4 $effect(() => {
5 localStorage.setItem("autosave", text);
Runs once on mount, and re-runs whenever 'text' changes
6 });
7</script>
8
9<textarea bind:value={text}></textarea>

When you use the $effect rune, you do not need to explicitly declare your dependencies. Svelte's compiler automatically tracks that text was read inside the function, and wires up the reactivity under the hood.

Key Takeaway

Never use $effect to synchronize internal state (e.g., updating variable B when variable A changes). That is what $derived is for. Only use $effect when you are explicitly stepping outside the Svelte reactivity system, like writing to the DOM, calling an API, or using localStorage.

Cleanup Functions

Many side effects create ongoing processes that need to be dismantled, such as setting intervals or attaching event listeners to the window.

To clean these up, your $effect function simply returns another function. This returned function is the cleanup phase. Svelte will automatically execute this cleanup function right before the effect runs again, and right before the component is destroyed.

Timer.svelte
1<script>
2 let count = $state(0);
3
4 $effect(() => {
5 const interval = setInterval(() => {
6 count++;
7 }, 1000);
8
9 return () => {
10 clearInterval(interval);
Cleans up the previous interval to prevent memory leaks
11 };
12 });
13</script>

Without the cleanup function, the component would spawn a brand new permanent interval timer every time the effect re-ran, immediately crashing the app.

Summary

When you need to interact with external systems outside of Svelte's reactivity model, you use the $effect rune. It runs its code block automatically on mount and whenever its internal reactive dependencies change. To prevent memory leaks when managing ongoing processes like timers or event listeners, the effect should return a cleanup function, which Svelte automatically executes before the next run and upon component destruction.

Interview Question

CORE

You've written an App.svelte file. How does it actually get onto the page?

Svelte compiles your component to JavaScript, but how does that JavaScript end up rendering on the screen? What actually puts your component into the DOM?

Writing a Svelte component is only half the battle. Once your .svelte file is compiled into highly optimized JavaScript, you still need a way to take that code and inject it into the browser's Document Object Model (DOM) so the user can actually see it.

The Blank Canvas Problem

Imagine you have just finished writing the most beautiful App.svelte file ever created. You open up your project's index.html file in the browser, expecting to see your application, but you are greeted with a completely blank white screen.

If you inspect the HTML file, you'll see a single empty <div> with an id of app. Your component exists, but the browser has no idea what an App.svelte file is. Browsers only understand raw HTML, CSS, and JavaScript. You need a dedicated bridge to take the compiled JavaScript output of your Svelte component and physically append it to that empty <div>. If you skip this step, your app remains trapped as raw code in memory forever.

The mount Function

In Svelte 5, the bridge between your compiled components and the browser's DOM is the mount function.

This function takes two arguments: the root component you want to render (usually App.svelte), and the physical DOM element on the page where it should be injected (the target). This code typically lives in a single entry-point file, usually named main.js or main.ts.

main.js

3

5

When you call mount, Svelte executes the <script> block of your App.svelte component for the very first time. It evaluates the initial values of your $state variables, computes any $derived values, and constructs the initial DOM nodes. It then grabs that newly constructed HTML and physically appends it as a child into your target element.

From that moment onward, the application is alive. The Svelte reactivity system takes over, and any further changes to the state will surgically update the DOM without ever needing to call mount again.

Lecture 17: Scoped CSS

Interview Question

CORE

How does Svelte keep one component's CSS from affecting other components?

You add .button { color: red } to one component, and you're terrified it'll turn every button in the app red. Does it? Why or why not?

CSS is notoriously difficult to manage at scale. Because traditional CSS is inherently global, a tiny styling change in one file can inadvertently destroy the layout of a completely unrelated page.

The Global Scope Nightmare

Imagine you are hired to fix a bug in a massive e-commerce application. You open the Header.svelte component and notice a login button that is supposed to be red. You add a simple <style> block at the bottom of the file with the rule .btn { color: red; }.

In a traditional global CSS architecture, this is a ticking time bomb. The moment that header loads, the browser applies that .btn rule globally across the entire DOM. Suddenly, the "Add to Cart" button in the product grid turns red. The "Delete Account" button in the settings panel turns red. You tried to fix one button, and in the process, you accidentally broke the design system for the entire application, infuriating the design team and causing massive visual confusion for users.

Automatic CSS Scoping

Svelte completely eliminates this nightmare by scoping your CSS to the component by default. When you write a <style> block inside a .svelte file, those styles only apply to the HTML elements directly inside that exact same file.

Header.svelte
1<button class="btn">Login</button>
2
3<style>
4 .btn { /* ✔️ This rule only affects the button in this specific file */
5 color: red;
6 }
7</style>

When you render this component, Svelte guarantees that no other .btn on the page will turn red. You can safely reuse class names like .container, .card, or .btn in dozens of different components without ever worrying about them colliding.

How the Magic Works

Svelte achieves this encapsulation during the compilation step. It doesn't rely on complex JavaScript runtime libraries like CSS-in-JS. Instead, it alters your code before it ever reaches the browser.

When the Svelte compiler sees your component, it generates a unique hash string (like svelte-1xyz5). It then quietly attaches that hash as an extra class to your HTML element, and rewrites your CSS rule to specifically target that exact hash.

Your source code: <button class="btn"> + .btn { color: red }

What the browser actually receives: <button class="btn svelte-1xyz5"> + .btn.svelte-1xyz5 { color: red }

Because Svelte mathematically guarantees that no other component will ever receive the svelte-1xyz5 hash, it is physically impossible for the styles to leak out and infect other elements on the page.

Interview Tip

To impress the interviewer: If you ever explicitly want a style to break out of the component and apply globally (like setting a universal font family on the <body>), you can use the :global() modifier. E.g., :global(body) { margin: 0; }.

Summary

To solve the fragility of global stylesheets, Svelte scopes CSS to the component level by default. The CSS you write inside a .svelte file will only ever affect the HTML elements inside that exact file. Behind the scenes, the Svelte compiler enforces this by generating a unique hash class and injecting it into both your HTML tags and your CSS selectors, ensuring your styles are permanently isolated and completely immune to global collisions.

Lecture 21: Reusable Markup with Snippets

Interview Question

CORE

How do you write a reusable chunk of markup you can use in several places?

The same three lines of markup appear in five spots in your component. Copy-paste feels wrong. Can you name a block of markup and reuse it?

The Five-Copy Disaster

You are building a product page. The same <figure> block, an image with a caption and a price badge, has to appear in five spots: the hero gallery, the "Customers also bought" strip, the search preview, the "Recently viewed" shelf, and a share dialog. You copy the five lines into all five places and ship. Three weeks later the designer asks for a loading spinner on every image. You edit the copies, but one was hiding inside an {#if} branch you forgot existed, so the "Recently viewed" shelf still renders the old markup. There is no error and no red squiggle. The page just looks broken in one corner, and the only way to catch it is for a human to notice.

That is the failure mode of duplicated markup: the copies drift apart silently, and the cost grows with every copy. The fix is not more discipline. The fix is making sure there is only one copy that has a name.

Naming the Block

Notice what the five copies actually are. They are not five features. They are one block of HTML stamped into the page five times, each time with different data. So the job is this: take a block of markup, give it a name, and call that name wherever the block should appear, passing in the data for that spot.

This is exactly what a function does for JavaScript: name a block of statements once, call it by name with arguments. Svelte gives you the same move for markup. That named, callable block of template is called a snippet. You define it with {#snippet ...} and stamp it into the page with {@render ...}.

Key Takeaway

A snippet is to markup what a function is to logic: name it once, call it anywhere.

Just as a function lets you write a block of JavaScript once and invoke it with different arguments, a snippet lets you write a block of HTML once and render it with different data. The markup lives in exactly one place, so a change to the snippet updates every spot that renders it, with zero copies to hunt down.

Interview Question

CORE

How do you use TypeScript inside a .svelte component and type its props?

You want type safety in a component. Typed props, typed state. What do you add to the script tag, and how do you declare a prop interface?

The Bug Nobody Could Find

You are building a <PriceBlock> component for a shop. It takes a price prop, and the parent grid is supposed to hand it a number. One afternoon a teammate wires it up from a different page and, without noticing, passes the price as a string: price="29.99" instead of price={29.99}.

Nothing errors. The app builds. The page renders. But the little "add insurance" upsell that runs price + 1 now performs string concatenation instead of addition, so the cart quietly shows 29.991 dollars instead of 30.99, and a customer screenshots the broken store before anyone on the team notices. The editor never warned you, because plain JavaScript has no idea that price was supposed to be a number; the mistake sailed straight through the build and detonated in front of a shopper.

That is the failure mode of untyped props: the contract between a parent and a child lives only in the author's head, and a typo or a wrong type becomes a silent runtime bug. The fix is to write that contract down in a form the editor can enforce, so the mistake is caught while you are typing, not after you ship.

To bring TypeScript into a Svelte component, you add a single attribute to the script tag: lang="ts".

Types are scaffolding, not structure: they guide the build, then vanish without leaving a single byte in the bundle.

State: Deep Proxying

When you pass an object or an array into the state rune, Svelte does not just monitor the top level variable for complete replacements. While deep mutation works perfectly for incremental changes, there are times when an external API gives you a completely fresh array or a brand new object. The Trap of Prop Drilling

When you declare reactive state inside a component, that data is strictly local. If the header component owns the user profile, it must pass it up to a common ancestor, like the root application layout, using a callback. Then the application layout must pass it down through the page, into the sidebar, and finally into the specific widget that actually displays the user's name. This technique, called prop drilling, forces you to wire data through every single layer of your application. It turns all of your intermediate components into useless middlemen that do not care about the user data, but are forced to declare properties and pass them along just to keep the plumbing connected. If the shape of the user profile changes, you have to update a dozen different files. When disconnected components need to read and write the exact same data, the solution is to move that data entirely out of the component hierarchy.

This module pattern completely decouples your application state from your user interface. The Primitive Reassignment Trap

There is one structural hazard to watch out for when sharing state through a module. You must export a container, such as an object or an array, and your components must mutate the properties inside that container. You cannot export a primitive variable and attempt to reassign it.

By exporting a constant container object like our session, you guarantee that the top level reference never changes. Lecture 32: Complex Derivations with $derived.by

Interview Question

CORE

How do you write a derived value that needs multiple statements, loops, or try/catch?

Imagine this scenario:

  1. A journalist files one more story at the end of the night at the National Times. The paper pays by the word.
  2. The page shows one payout total under the story list. That total counts the words of every story, because the paper pays by the word.
  3. The new story lands on the list.
  4. But the payout total still shows the old number. Why does it not move?

  6. One line cannot hold those steps.
  7. Svelte has a second form of the same tool, one that takes a whole function. Inside it, loops and safety checks are just normal JavaScript.

The Payment That Does Not Fit on One Line

The National Times pays its freelance writers per story: the number of words in the piece times a rate per word. One story is a one line calculation, and the tool you already know handles it. The $derived rune, a Svelte function whose name starts with a dollar sign, wraps an expression and recalculates the value automatically whenever the inputs inside that expression change.

3 let rate = $state(0.5);

The total needs a loop that walks the list of stories, a running sum held in a temporary variable, and a guard so that one broken record, a story filed without a word count, cannot turn the whole board into garbage. You could force it all into one crowded chain of array methods, but the moment a guard becomes necessary that chain breaks. An expression is exactly one computation; it has no room for steps.

The second form is written $derived.by, and instead of an expression it accepts a function. Between the braces you write a normal JavaScript function body: statements, loops, and temporary variables, in any order, as many as you need. The function must end by returning the value, and that returned value is what the board displays.

8 let subtotal = 0;

10 subtotal += story.words * story.rate;
11 }

13 });

The dependency rule from the one line form carries over unchanged. Anything the function reads synchronously, meaning any value read while the function is actually running, counts as a dependency of the derived value. Here the body reads the stories array, so stories is the dependency. When a writer files a new story and the array changes, Svelte marks totalPayout as dirty, a stale value that needs a fresh run, and re-executes the function the next time the board reads the total. This is push-pull reactivity: the change is pushed as a notification to everything that depends on the array, and the actual calculation is pulled only when the value is read. Nothing runs for values nobody looks at.

A Safety Net for Broken Records

Every newsroom has a damaged record: a story filed in a rush without a word count. Multiplying a missing count by a rate produces NaN, the JavaScript value for "not a number", and that NaN then poisons the whole sum. The board shows a payout of NaN and the accounting desk panics. In the one line form you have no room for a guard. Inside a function body you have the full JavaScript toolkit for errors: throw to flag a bad record and try/catch to catch the problem and substitute a safe value.

1<script>
2 let stories = $state([
3 { title: 'Harbor strike', words: 800, rate: 0.5 },
4 { title: 'Election night', rate: 0.5 }
5 ]);
6 let totalPayout = $derived.by(() => {
7 try {
8 let subtotal = 0;
9 for (const story of stories) {
10 if (!story.words || !story.rate) {
11 throw new Error('Damaged story record');
RIGHT: FLAG the bad record instead of computing garbage.
12 }
13 subtotal += story.words * story.rate;
14 }
15 return subtotal;
16 } catch {
17 return 0;

18 }

The damaged record throws, the catch block catches it, and the board shows zero instead of NaN. The editors fix the record in the morning; tonight the page stays alive. Note that this is still a pure calculation: the function reads the list and returns a number, and it never writes to any state.

Two Forms, One Machine

The two forms are not two different tools. $derived(expression) is shorthand for $derived.by(() => expression): the one line form wraps your expression in a function under the hood. Both share one dependency tracker, one dirtiness system, and one rule set. Pick the expression form for a single computation, and reach for the function form the moment the calculation needs more than one step.

That shared rule set includes one hard limit. Svelte disallows state changes inside a derived value, in both forms. A derived function must be a pure calculation: read inputs, return a value, touch nothing else. If you find yourself wanting to update state from inside the function, that work belongs in an event handler or an effect, not in the derived value, because a calculation that secretly writes state can loop forever and the board would never settle on a number.

Interview Tip

Then note that try/catch, loops, and temporary variables are only reachable through the function form.

When the calculation needs more than one expression, swap $derived(expr) for $derived.by(() => { ... }). Everything between the braces is a plain JavaScript function, loops and safety nets included.

Summary

The $derived rune computes a value from one expression and keeps it in sync with its inputs. When the calculation needs multiple statements, a loop, a temporary variable, or error handling, use the $derived.by form, which accepts a whole function. The function body is ordinary JavaScript: anything it reads synchronously becomes a dependency, and Svelte re-runs it when a dependency changes and the value is next read. The two forms are one machine, so the expression form is simply shorthand for the function form, and both must stay free of side effects.

  • $derived(expr) handles one expression; $derived.by(() => { ... }) handles a whole function body.
  • Inside the body you can declare temporary variables, run loops, and use try/catch.
  • Anything read synchronously in the body becomes a dependency; the body re-runs only when a dependency changes and the value is read.
  • Svelte disallows state changes inside a derived, in both forms, so the function stays a pure calculation.
  • $derived(expression) is shorthand for $derived.by(() => expression).

What is the difference between <script> and <script module>?

Imagine this scenario:

  1. A website visitor listens to audio dispatches from field reporters on the National Times website.
  2. The page shows three audio player boxes, and the first box is currently playing City Hall audio.
  3. The visitor clicks the play button on the second box to hear Harbor Strike news.

  5. Two reporters speak at once through the speakers, creating painful noise that drives the visitor away.
  6. Each player box runs its own isolated setup, so no box knows another box started playing.

Your Component File Grows a Second Script

Your .svelte component file grows a new part today. Up to now, every .svelte file you have built in this course contained at most one <script> block. That block is the instance script, meaning its code executes from scratch every single time the browser creates a new copy of your component. If your page places three audio player components on the screen, that instance script runs three separate times, creating three completely independent worlds. Any variable declared inside it belongs exclusively to that single copy.

The National Times homepage displays audio dispatches recorded by field reporters across the city. The editorial desk wants a clean listening experience: clicking play on one dispatch must immediately pause whichever dispatch was already playing. But when each component copy lives on its own isolated island, the first player cannot know that the second player just started. You get two reporters talking over each other at full volume. What the page needs is a shared coordinator, a single place in the component definition that runs once when JavaScript first loads the file, before any individual components are rendered.

In standard HTML or earlier component tutorials, putting two script tags in one component looks like a syntax error. Svelte explicitly allows a second script block when you add the module attribute, written as <script module>. We met this block briefly when exploring the anatomy of a component (see Lecture 3). The standard <script> tag is the instance script, running once per component copy. The <script module> tag is the module script, running exactly once when the file is imported. Why Not Pass Props or Use a Shared Module File?

Whenever developers first encounter <script module>, two natural alternatives come to mind from earlier lessons. The first alternative is lifting state up to DispatchBoard.svelte and passing down callback functions as props (see Lecture 11). But in a real newsroom application, an audio dispatch might appear in the top breaking news banner, another in the main article body, and a third inside a floating sidebar drawer. Lifting state across unrelated branches of the component tree forces you to pass props and callbacks through dozens of intermediate components that have nothing to do with audio playback.

The second alternative is creating a separate shared state file, like audio.svelte.js (see Lecture 25). Standalone .svelte.js modules are the gold standard for global application data like logged-in user profiles or shopping carts. But when the shared coordinator, play logic, and markup belong exclusively to the audio player itself, creating an external module fractures the component. A developer moving AudioDispatch.svelte to another project would have to remember to copy the auxiliary .svelte.js file and rewire the import paths. With <script module>, the component remains completely self-contained. Anyone who imports AudioDispatch.svelte gets the coordinator and the playback rules bundled in one single file.

The boundary between the two scripts follows strict one-way visibility rules. Code inside the instance <script> can freely read and update variables declared in <script module>. The module script runs only once when JavaScript first loads the file, a moment when zero component instances exist. Attempting to read an instance variable from inside the module block will trigger a compiler error. Furthermore, Svelte forbids export default inside <script module>, because the component itself is always the default export of a .svelte file.

The Accidental Execution at Render Time

In Lecture 5, we learned how to attach user interactions to HTML elements using standard event attributes like onclick (see Lecture 5). In those initial examples, we assigned a bare function name: onclick={handleClick}. Notice what was absent from that attribute: there were no parentheses trailing the function name. We passed the function itself as a reference, leaving it dormant so the browser could invoke it only when a reader clicked the element.

Problems begin the moment your event handler requires specific data. On the National Times news site, writers manage pending draft articles on a dashboard. Each draft has its own numeric identifier. When a writer clicks a button to delete a draft, the handler must know exactly which article to remove from the list. A developer new to Svelte naturally tries to pass that identifier between parentheses: onclick={deleteArticle(draft.id)}.

The result is an immediate disaster. In JavaScript, writing parentheses after a function name tells the engine to execute the function right now. When Svelte creates the component and evaluates the template markup, it encounters deleteArticle(draft.id) and executes it during the initial rendering phase. Every article in the list is deleted before the writer even touches the mouse. Even worse, because deleteArticle does not return a new function, the onclick attribute receives undefined. When the writer actually clicks the button later, nothing happens.

Deferring Calls with Arrow Functions

To pass custom arguments without triggering instant execution, you must wrap the function call in an arrow function: onclick={() => deleteArticle(id)}.

An arrow function is a compact JavaScript function expression. By writing () => deleteArticle(id), you create an anonymous function wrapper that sits in memory. Svelte assigns this wrapper function to the button's onclick attribute. During the initial render pass, JavaScript creates the wrapper but does not execute the code inside it. When the writer finally clicks the button, the browser invokes the wrapper, and the wrapper executes deleteArticle(id) with the correct article number.

This mechanism relies on a closure, meaning a JavaScript function that retains access to variables declared in its surrounding lexical scope even after that outer scope has finished executing. The inner arrow function captures the current id value, ensuring that clicking article 12 deletes article 12. You can pass as many custom arguments as your handler needs, including status strings or configuration flags: onclick={() => updateStatus(id, 'archived', true)}.

Understanding the Native Event Object

Now examine what happens when you do not need custom arguments, but instead need technical details about the user's interaction. Whenever a user interacts with a web page, the browser constructs an Event object, a native data structure packed with information about the physical event that just occurred.

If you attach a direct function reference without an arrow wrapper, such as onclick={handleClick}, the browser automatically supplies this Event object as the first argument to your function. Depending on the interaction, this object may be a MouseEvent, KeyboardEvent, or SubmitEvent.

The Event object exposes several critical properties and methods:

  • event.target: the exact DOM element where the event originated.
  • event.currentTarget: the element that owns the active event listener.
  • event.clientX and event.clientY: the horizontal and vertical screen coordinates of the cursor when clicked.
  • event.key: the specific keyboard character pressed during a typing event.
  • event.preventDefault(): a method that halts default browser behavior, such as preventing a form from submitting and reloading the page.
  • event.stopPropagation(): a method that halts event bubbling, meaning the browser process where an event triggers listeners on parent elements up the DOM tree.

In earlier versions of Svelte, developers used proprietary framework modifiers like on:click|preventDefault={handler}. Svelte 5 retired all custom event modifiers in favor of standard web APIs. You simply call event.preventDefault() or event.stopPropagation() directly inside your JavaScript handler function, matching the way plain browser code operates.

Deep State Proxies and Property Traps

When you pass an object or array to $state, Svelte does not modify the source object in place. Instead, it creates and returns a native JavaScript Proxy. A proxy is a built-in browser object that wraps around a target data structure, using internal functions called traps to intercept read and write operations. When your template reads a property, the proxy's get trap intercepts the access to record a dependency. When your script assigns a new value, the proxy's set trap catches the assignment, records the change, and schedules a DOM update.

Svelte applies this wrapping recursively. When your application accesses journalist.location, Svelte's proxy intercepts that access and returns a nested proxy for the location object. When you subsequently mutate journalist.location.city = 'Geneva', you are writing through that nested proxy's set trap. The nested proxy catches the new string and triggers a targeted update for any DOM element reading that exact city property.

The Non-Plain Object Boundary: Classes and Built-Ins

The second major boundary where nested reactivity stops is non-plain objects. Svelte's recursive proxying is deliberate and selective: it only recurses into plain objects, meaning objects created with curly braces {} or Object.prototype, and standard arrays created with brackets [].

Svelte deliberately stops recursive proxification whenever it encounters:

  • Class instances created with new MyClass(), such as SDK models or ORM records.
  • Built-in complex JavaScript objects such as Date, RegExp, Map, or Set.
  • Prototype-less objects created with Object.create(null) or objects frozen with Object.freeze().

Svelte halts at class instances to protect your code. Wrapping arbitrary third-party class instances in proxies can break private fields (declared with #field), disrupt prototype inheritance chains, and cause runtime crashes in third-party libraries. If journalist.location is an instance of a LocationRecord class, Svelte stores that instance as an opaque, unproxied reference. To make class instances reactive, you have two clear paths: either keep your data as plain object literals, or define reactive class fields using $state inside the class constructor itself (which we will explore in Lecture 39). The choice between $state and $state.raw comes down to the frequency of property-level mutations versus the cost of proxy allocation. Choose $state.raw in three primary scenarios:

  • Complex third-party library instances: Modern web applications integrate specialized client-side libraries: Chart.js visualization instances, Leaflet map objects, Three.js 3D scenes, WebGL renderers, or Monaco code editors. Wrapping external instances in Svelte's $state proxies frequently triggers runtime errors or degrades performance. Wrapping them in $state.raw preserves the exact original instance while still letting your component react when the instance is swapped or reset.
  • High-frequency immutable streaming feeds: In financial dashboards, telemetry viewers, or multiplayer canvases, state updates frequently arrive as complete immutable snapshots over a WebSocket. Because each update replaces the entire payload, deep proxy tracking on every incoming message is discarded seconds later. Reassigning raw immutable snapshots avoids continuous proxy creation and keeps the garbage collector idle.

In JavaScript, primitive types are immutable and passed by value; Svelte never proxies primitives under any circumstances. $state.raw is specifically designed for reference types: objects, arrays, and class instances.

The Proxy Barrier in the Outside World

In Lecture 36, we discovered how Svelte 5 achieves deep reactivity by wrapping plain objects and arrays in recursive JavaScript Proxies (see Lecture 36). Whenever code accesses or mutates a property, Svelte's proxy traps intercept the operation to track dependencies and trigger surgical DOM updates. In interactive forms and dynamic newsroom editors, this property-level reactivity makes UI state feel effortless and responsive.

Inside Svelte's component tree, reactive proxies are invisible and delightful. Your templates read properties directly, event handlers modify nested fields, and derived values recompute automatically when inputs change (see Lecture 7). But web applications do not exist in isolation. Modern frontend applications constantly exchange structured data with systems that live outside Svelte: external browser APIs, third-party libraries, network protocols, and developer debugging tools.

On the National Times website, journalists write investigative reports inside an editorial workspace. As the journalist types, the workspace tracks draft content, headline text, word counts, and section outlines. To prevent accidental data loss during breaking news coverage, the editor includes a backup manager. Whenever the journalist clicks the backup button, the application attempts to clone the current draft using the browser's native structuredClone function, saving an isolated duplicate record to browser storage.

This is where the application hits a sudden wall. When the code hands an article draft stored in $state directly to structuredClone, the browser immediately throws an uncaught DataCloneError exception. The backup operation aborts, an error message appears across the screen, and the journalist cannot save their work. The draft data itself consists of ordinary strings, numbers, and arrays, yet the browser flatly refuses to duplicate it.

The cause of this crash lies in the boundary between Svelte and the wider JavaScript runtime. To the browser's native cloning algorithm, a reactive Svelte object is not a plain object: it is a Proxy instance equipped with internal trap handlers and signal bindings. The native structuredClone algorithm explicitly forbids cloning Proxy instances, throwing an error whenever it encounters one. Similar friction occurs across the entire frontend ecosystem: web worker communication through postMessage fails on proxies, external charting libraries like Chart.js or D3 can produce unpredictable rendering loops when caching proxied objects, and calling console.log prints confusing internal proxy targets rather than readable data.

Peeling Off the Proxy with $state.snapshot

To safely pass reactive state across framework boundaries, Svelte 5 introduces the $state.snapshot rune function.

The $state.snapshot rune takes a reactive $state proxy, or any data structure containing reactive proxies, and returns a plain, non-reactive deep copy with every proxy wrapper completely stripped away. You can think of it as taking an instant static photograph of your data. Inside Svelte, your reactive state continues running normally, maintaining its proxy traps and driving the user interface. But the value returned by $state.snapshot is an inert, ordinary JavaScript object residing in standard computer memory, entirely disconnected from Svelte's signal graph.

Consider the contrast in memory between a live reactive state variable and its snapshot:

  • With live state: The object is wrapped in a JavaScript Proxy with get and set traps. Reading properties registers dependencies in active effects, and mutating properties notifies Svelte to update the DOM.
  • With $state.snapshot: The returned object is a plain JavaScript clone. Reading properties performs zero dependency tracking, and mutating properties has zero effect on Svelte or the rendered screen.

Because $state.snapshot returns native unproxied data, browser APIs like structuredClone and postMessage accept it without hesitation. Third-party charting libraries receive pure data without proxy interference, and debugging tools display clean, transparent object structures.

Snapshots Versus JSON Serialization and Shallow State

When developers first encounter the proxy barrier, a common naive question arises: why not simply use JSON.parse(JSON.stringify(article)) to strip proxies? We have used JSON serialization for years to clone objects in JavaScript; why does Svelte need a dedicated rune function?

While JSON serialization appears to produce plain objects, it suffers from severe limitations that corrupt application data:

  • Loss of data types: JSON serialization converts Date instances into plain strings, permanently destroying their date methods. It converts NaN and Infinity into null, strips undefined object properties entirely, and converts Map and Set instances into empty objects.
  • Crash on circular references: If your application data contains circular object references, JSON.stringify throws a fatal TypeError: Converting circular structure to JSON.
  • Performance overhead: Converting an entire memory structure into an intermediate text string and parsing that string back into memory is significantly slower and generates unnecessary garbage collector pressure.

By contrast, $state.snapshot is built directly into Svelte's runtime. It traverses object graphs natively, cloning data structures without text serialization. Furthermore, if an object in your state tree defines a custom toJSON method, $state.snapshot respects it by cloning the value returned by toJSON rather than the raw instance. If an object cannot be cloned, such as a browser DOM node or a window reference, $state.snapshot retains the original reference and warns you in development, ensuring your application never crashes unexpectedly.

It is equally important to distinguish $state.snapshot from $state.raw (see Lecture 37). While both tools deal with unproxied data, they serve opposite directions:

  • $state.raw: An input strategy. It creates a shallow reactive signal for large datasets at creation time, preventing Svelte from ever creating nested proxies.
  • $state.snapshot: An output strategy. It takes an existing deeply reactive $state proxy and extracts an inert, plain copy so you can export it to external systems.

Key Takeaway

$state.snapshot extracts a plain, static, non-reactive deep copy of reactive state, stripping all JavaScript Proxies so the data can safely pass to outside libraries, browser APIs, and developer tools.
