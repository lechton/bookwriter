The Stale Screen and the Mystery of Nested State

In Lecture 24, we discovered that Svelte 5 introduces deep reactivity for objects and arrays (see Lecture 24). When you store structured data in $state, Svelte wraps the container in a native JavaScript Proxy, an internal wrapper that intercepts operations like property reads and assignments. In standard examples, changing an item's property or pushing a new record into an array causes the screen to update immediately and surgically.

Yet developers frequently encounter an unsettling mystery in production applications. A developer writes journalist.location.city = 'Geneva', or updates a nested property inside profile data, and the user interface refuses to budge. The browser console confirms that the property holds the new string in memory. No runtime error appears in the terminal. But the HTML element rendered on the screen stays stuck on the old value.

To understand why this happens, you must look closely at the boundary where Svelte's reactive wrapping begins and ends. Deep reactivity is not magic; it relies on precise runtime mechanics governed by object references, JavaScript data types, and signal subscriptions. On the National Times website, journalists maintain a public profile page showing their assigned bureau city. The page displays the journalist's name and current location, allowing them to switch cities when moving between assignments.

Before inspecting how nested reactivity works in code, examine the component hierarchy. ProfileView.svelte serves as the container shell managing the journalist profile data, while LocationBadge.svelte renders the location badge on screen.

Deep State Proxies and Property Traps

When you pass an object or array to $state, Svelte does not modify the source object in place. Instead, it creates and returns a native JavaScript Proxy. A proxy is a built-in browser object that wraps around a target data structure, using internal functions called traps to intercept read and write operations. When your template reads a property, the proxy's get trap intercepts the access to record a dependency. When your script assigns a new value, the proxy's set trap catches the assignment, records the change, and schedules a DOM update.

Svelte applies this wrapping recursively. When your application accesses journalist.location, Svelte's proxy intercepts that access and returns a nested proxy for the location object. When you subsequently mutate journalist.location.city = 'Geneva', you are writing through that nested proxy's set trap. The nested proxy catches the new string and triggers a targeted update for any DOM element reading that exact city property.

Here is LocationBadge.svelte. It receives the journalist object through $props() (see Lecture 9) and renders the nested location properties directly into the template.

LocationBadge.svelte
1<script>
2 let { journalist, onRelocate } = $props();
3</script>
4
5<article class="location-badge">
6 <h3>Journalist: {journalist.name}</h3>
7 <p class="city-tag">Location: {journalist.location.city}, {journalist.location.country}</p>
8 <button onclick={() => onRelocate('Geneva')}>Relocate to Geneva</button>
9</article>

When the journalist clicks the relocation button, the component invokes the onRelocate callback. As long as that callback mutates the property through Svelte's proxy, the location badge updates immediately without requiring any full-page reload or parent component re-render.

The Raw Reference Trap: Mutating Unwrapped Data

Now we can answer the opening mystery: why does mutating journalist.location.city fail to update the screen in real-world code? The most frequent culprit is the raw reference trap, meaning your code accidentally mutates the original unproxied object rather than the proxy wrapper created by $state.

Consider how data enters a real frontend application. Data rarely starts as an inline object literal; it typically arrives from an external API payload, a network request, or an imported default dataset:

App.js
1const rawProfile = {
2 name: 'Elena Rostova',
3 location: { city: 'London', country: 'UK' }
4};
5
6let journalist = $state(rawProfile);

A common misconception is that passing rawProfile into $state alters rawProfile itself. It does not. JavaScript proxies never mutate their underlying targets. In memory, rawProfile remains a plain, inert JavaScript object. Svelte creates an entirely separate proxy instance and binds it to journalist. This means journalist !== rawProfile, and journalist.location !== rawProfile.location.

If an asynchronous data fetch, an external event listener, or a helper function retains a reference to rawProfile and mutates rawProfile.location.city = 'Geneva', the write occurs strictly in raw memory. Because rawProfile has no proxy traps, Svelte receives zero notification. The signal never fires, and the badge on screen stays stuck on London.

Always ensure your mutation logic targets the reactive variable returned by $state, never the raw data payload used to initialize it.

The Non-Plain Object Boundary: Classes and Built-Ins

The second major boundary where nested reactivity stops is non-plain objects. Svelte's recursive proxying is deliberate and selective: it only recurses into plain objects, meaning objects created with curly braces {} or Object.prototype, and standard arrays created with brackets [].

Svelte deliberately stops recursive proxification whenever it encounters:

  • Class instances created with new MyClass(), such as SDK models or ORM records.
  • Built-in complex JavaScript objects such as Date, RegExp, Map, or Set.
  • Prototype-less objects created with Object.create(null) or objects frozen with Object.freeze().

Svelte halts at class instances to protect your code. Wrapping arbitrary third-party class instances in proxies can break private fields (declared with #field), disrupt prototype inheritance chains, and cause runtime crashes in third-party libraries. If journalist.location is an instance of a LocationRecord class, Svelte stores that instance as an opaque, unproxied reference. Writing journalist.location.city = 'Geneva' mutates the class property in memory, but no proxy trap exists on that class instance, so Svelte never detects the change.

To make class instances reactive, you have two clear paths: either keep your data as plain object literals, or define reactive class fields using $state inside the class constructor itself (which we will explore in Lecture 39). For built-in collections like Map and Set, import Svelte's specialized reactive equivalents from svelte/reactivity (which we will cover in Lecture 40).

The Destructuring Fallacy with Primitive Leaf Values

A third frequent reason for stuck screens is destructuring primitive values. In JavaScript, primitive data types including strings, numbers, and booleans are passed and assigned strictly by value, not by reference.

When you destructure a primitive property from a reactive object, you sever the connection to the proxy:

LocationBadge.svelte
1<script>
2 let { journalist } = $props();
3
4 function renameCityBroken(newCity) {
5 let { city } = journalist.location;
WRONG: Copies a disconnected PRIMITIVE string value.
6 city = newCity;
Modifies only local variable; proxy is completely untouched.
7 }
8
9 function renameCityWorking(newCity) {
10 journalist.location.city = newCity;
RIGHT: Writes to property on the PROXY to trigger updates.
11 }
12</script>

Notice the vital distinction between destructuring an object versus destructuring a primitive. If you write let { location } = journalist, the variable location holds a reference to the nested proxy returned by Svelte. Mutating location.city = 'Geneva' successfully triggers the proxy's set trap and updates the DOM. But if you destructure let { city } = journalist.location, city is merely a plain string copy. Reassigning city = 'Geneva' alters only that temporary local variable, leaving the proxy and the screen completely unaffected.

Granular Dependency Signals and Tree Replacement

Why does Svelte invest in recursive proxies instead of re-rendering the whole component on any change? The answer lies in granular dependency tracking.

In Svelte 5, reactivity is powered by fine-grained signals. When LocationBadge.svelte renders <p class="city-tag">Location: {journalist.location.city}</p>, Svelte tracks a dependency specifically on the signal representing the city property. It does not subscribe the paragraph to the parent journalist object or to sibling properties like journalist.name. If another profile process updates journalist.name = 'Elena Rostova-Vance', the DOM element displaying the city is completely bypassed during the update cycle.

Furthermore, Svelte handles complete branch replacements effortlessly. If you replace the entire location object at once:

App.js
1journalist.location = { city: 'Berlin', country: 'Germany' };

Svelte's top-level proxy catches the assignment to the location property. It automatically wraps the new object in a fresh nested proxy, links its internal signals, and immediately updates the DOM expressions that depend on location and its children. You never need to call special cloning methods or manual notification hooks.

Key Takeaway

Passing an object to $state recursively proxies plain objects and arrays; mutating raw unproxied source references or class instances without runes bypasses reactivity completely.

Interview Tip

To impress the interviewer: Explain that Svelte 5 achieves deep reactivity through recursive JavaScript Proxies, wrapping nested plain objects and arrays on access. Emphasize three distinct failure modes where mutating a nested property fails to update the screen: first, mutating a retained reference to the raw, unproxied input object rather than the proxy returned by $state; second, attempting to mutate properties on non-plain objects like class instances or Object.create() records, which Svelte deliberately excludes from proxying to protect internal prototypes; and third, destructuring primitive leaf values, which severs reactivity due to JavaScript pass-by-value semantics. Finally, highlight that Svelte's fine-grained tracking attaches dependencies to individual property signals rather than whole objects, ensuring surgical DOM updates without virtual DOM overhead.

Summary

Svelte 5 handles nested objects and arrays through recursive JavaScript Proxies, intercepting property reads and writes to trigger surgical DOM updates. While standard mutations update the screen automatically, failures occur when developers mutate retained references to the original raw input object, mutate unproxied non-plain objects like class instances, or reassign destructured primitive variables. Mutating directly on the proxy ensures granular signals update only the exact elements bound to the modified properties.

  • Passing plain objects and arrays to $state creates deeply reactive JavaScript Proxies.
  • Mutating the original unproxied object in memory bypasses proxy traps and leaves the screen stale.
  • Svelte stops deep proxying at non-plain objects such as class instances, Dates, and Maps.
  • Destructuring primitive properties copies values and severs the connection to the reactive proxy.
  • Reassigning an entire nested object branch automatically wraps the new structure in a fresh proxy.
  • Svelte tracks dependencies at the property signal level, updating only the exact DOM nodes reading that path.
