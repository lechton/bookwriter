# Lecture 23: Reaching the Real DOM with bind:this
> INTERVIEW QUESTION | ❱ CORE | How do you get a direct reference to a DOM element from your script?

Imagine you run the live support chat for a checkout that processes thousands of orders an hour. A customer's payment fails, the chat panel pops open, and every second they spend hunting for the message box with their mouse costs you a ticket. The requirement is brutal and precise: the moment the chat appears, the typing cursor must already sit in the input, and after every sent message the input must grab focus again so the customer can keep typing without touching anything. To do any of this you need the real input element, the actual DOM node, so you can call its focus method from your script. The script and the markup live in the same `.svelte` file, yet reaching from one to the other is not obvious, because the script runs before the markup has become a real element.

```components title="support-chat — Component Explorer"
SupportChat.svelte | composerInput receives the mounted input node | form | chat log: empty;; typing box: cursor starts inside
```

Read the panel as the ownership map for this lesson: one component, `SupportChat.svelte`, owns one rendered input, and one component-local variable, `composerInput`, will receive that exact node. There is no second component and no global registry, just one file holding one door to one element.

### The tempting shortcut and the wall

The instinct is to reach for the browser's global toolbox: tag the element with an id and ask the document to find it.

```svelte title="SupportChat.svelte"
<script>
  let draft = $state('');
  function openChat() {
    const input = document.getElementById('composer'); // **WRONG:** couples the component to a page-wide global id
    if (input) input.focus(); // the guard hides a silent **NULL** instead of fixing the timing
  }
</script>

<input id="composer" bind:value={draft} /> <!-- the id is a promise to the whole page that this node is unique -->
```

This compiles, this runs, and this fails in two quiet ways. First, an id must be unique across the entire page, not inside your component. Render `SupportChat` twice, once for the customer and once on the agent console screen, and both copies carry an input called `composer`; the lookup returns whichever the browser saw first, and focus lands in the wrong window while the other one stays dead. Nothing crashes, nothing logs, the customer just experiences a chat that ignores them. Second, timing: the element might not exist yet when your code runs, and `getElementById` answers that with `null`, not with an error.

### The mechanism: bind:this

Svelte gives every component a private, typed wire to its own markup. You declare a plain variable, attach `bind:this` to the element, and when the component mounts, Svelte assigns the real node into your variable.

```svelte title="SupportChat.svelte"
<script>
  let draft = $state('');
  let composerInput; // declared, but **UNDEFINED** until the component mounts
  $effect(() => {
    composerInput?.focus(); // **RIGHT:** effects run after mount, when the node is guaranteed to exist
  });
</script>

<input bind:value={draft} bind:this={composerInput} /> <!-- Svelte assigns the real node into the local variable -->
```

Notice what disappeared: no id, no global lookup, no null guard. The variable is component-local, so a second `SupportChat` gets its own `composerInput` holding its own input, and the two never collide. The question mark in `composerInput?.focus()` is still worth keeping, because it states the timing rule out loud: the reference exists only after mount.

### Two references, one conversation

The same wire solves the second half of the support chat: the scrolling log. As messages arrive, the newest one must stay in view, which means measuring the log container and pushing its scroll position down. That needs a second reference, and a reactive re-run whenever the messages change.

```svelte title="SupportChat.svelte"
<script>
  let chatLog = $state([]);
  let logElement; // the messages **CONTAINER** node, captured the same way
  $effect(() => {
    if (chatLog.length === 0) return; // nothing to scroll on a fresh mount
    logElement?.scrollTo(0, logElement.scrollHeight); // reads the fresh **HEIGHT** on every new message
  });
  async function send() {
    chatLog = [...chatLog, draft]; // **REASSIGN** the array so the effect re-runs
    draft = '';
    composerInput?.focus(); // **RIGHT:** refocus with zero global lookups
  }
</script>

<div class="log" bind:this={logElement}> ... </div> <!-- the container that gets measured -->
```

Here the effect depends on `chatLog`, so it re-runs every time a message reassigns it, and each run reads the container's current height through the reference. Focus, measurement, scrolling: three real DOM jobs, all done through variables the component owns.

### The timing rule, and the server caveat

One rule carries all of this: the reference is undefined until the component mounts. Reading it at the top level of the script gives you `undefined`, because the element does not exist yet. During server rendering the element never exists at all, so keep every use inside effects and event handlers, where the component is safely mounted in the browser. And if you attach something with real cleanup duty, say a `ResizeObserver` watching the log container, disconnect it by returning the cleanup from the same effect that created it.

> [!KEY]
> `getElementById` is a shout into the whole building; `bind:this` is a private door from the component to its own DOM.

The allegory maps exactly. A shout depends on a name being unique across every room in the building, and it reaches whoever answers first. A private door exists only between your component and the node it rendered, and nobody else can walk through it.

> [!TIP]
> **To impress the interviewer:** Name the three properties in one breath: the reference is component-scoped, it is assigned exactly on mount, and it stays undefined during server rendering. Then show you own the consequences: anything you attach through the reference, such as an observer, is yours to detach in the effect's cleanup.

### Summary

When your script needs the real DOM node, declare a local variable and attach it to the element with `bind:this`. Svelte fills the variable when the component mounts, which makes the reference private to that component instance, immune to duplicate-name collisions, and honest about timing: undefined before mount, safe to use inside effects and handlers afterward. The mechanism replaces global lookups like `document.getElementById`, which couple your component to a page-wide id and return null whenever the element is not there yet.

* `bind:this={variable}` assigns the rendered element into a component-local variable on mount.
* The reference is undefined before mounting and during server rendering; use it inside effects and event handlers.
* Each component instance gets its own reference, so duplicate instances never collide.
* Reading layout (heights, positions) through a reference inside an effect re-measures on every relevant state change.
* Anything you attach through the reference, such as an observer, must be detached in the same effect's cleanup.

| | **DOCUMENT.GETELEMENTBYID**<br>(global lookup) | **BIND:THIS**<br>(component wiring) |
| ---: | :--- | :--- |
| **Coupling** | Page-wide id string | Local variable in the same file |
| **Timing** | Returns `null` if the element is not mounted | Assigned exactly on mount |
| **Duplicate Instances** | Ids collide, the lookup grabs the first copy | Each copy receives its own node |
| **Server Rendering** | Runs and finds nothing | Stays `undefined`, safe inside effects |
