### The Proxy Barrier in the Outside World

In Lecture 36, we discovered how Svelte 5 achieves deep reactivity by wrapping plain objects and arrays in recursive JavaScript Proxies (see Lecture 36). Whenever code accesses or mutates a property, Svelte's proxy traps intercept the operation to track dependencies and trigger surgical DOM updates. In interactive forms and dynamic newsroom editors, this property-level reactivity makes UI state feel effortless and responsive.

Inside Svelte's component tree, reactive proxies are invisible and delightful. Your templates read properties directly, event handlers modify nested fields, and derived values recompute automatically when inputs change (see Lecture 7). But web applications do not exist in isolation. Modern frontend applications constantly exchange structured data with systems that live outside Svelte: external browser APIs, third-party libraries, network protocols, and developer debugging tools.

On the National Times website, journalists write investigative reports inside an editorial workspace. As the journalist types, the workspace tracks draft content, headline text, word counts, and section outlines. To prevent accidental data loss during breaking news coverage, the editor includes a backup manager. Whenever the journalist clicks the backup button, the application attempts to clone the current draft using the browser's native structuredClone function, saving an isolated duplicate record to browser storage.

This is where the application hits a sudden wall. When the code hands an article draft stored in $state directly to structuredClone, the browser immediately throws an uncaught DataCloneError exception. The backup operation aborts, an error message appears across the screen, and the journalist cannot save their work. The draft data itself consists of ordinary strings, numbers, and arrays, yet the browser flatly refuses to duplicate it.

The cause of this crash lies in the boundary between Svelte and the wider JavaScript runtime. To the browser's native cloning algorithm, a reactive Svelte object is not a plain object: it is a Proxy instance equipped with internal trap handlers and signal bindings. The native structuredClone algorithm explicitly forbids cloning Proxy instances, throwing an error whenever it encounters one. Similar friction occurs across the entire frontend ecosystem: web worker communication through postMessage fails on proxies, external charting libraries like Chart.js or D3 can produce unpredictable rendering loops when caching proxied objects, and calling console.log prints confusing internal proxy targets rather than readable data.

Before examining how to cross this boundary safely, examine the component hierarchy that powers the newsroom workspace. ArticleEditor.svelte serves as the container shell managing article state and input bindings, while BackupManager.svelte renders the backup controls and status card on screen.

```components title="national-times — Component Explorer"

  BackupManager.svelte | creates offline backups and exports plain article data | card | Draft: **Offshore Energy Crisis**;; Words: **1450**;; Status: **Ready to archive**
```

### Peeling Off the Proxy with $state.snapshot

To safely pass reactive state across framework boundaries, Svelte 5 introduces the $state.snapshot rune function.

The $state.snapshot rune takes a reactive $state proxy, or any data structure containing reactive proxies, and returns a plain, non-reactive deep copy with every proxy wrapper completely stripped away. You can think of it as taking an instant static photograph of your data. Inside Svelte, your reactive state continues running normally, maintaining its proxy traps and driving the user interface. But the value returned by $state.snapshot is an inert, ordinary JavaScript object residing in standard computer memory, entirely disconnected from Svelte's signal graph.

Consider the contrast in memory between a live reactive state variable and its snapshot:
- With live state: The object is wrapped in a JavaScript Proxy with get and set traps. Reading properties registers dependencies in active effects, and mutating properties notifies Svelte to update the DOM.
- With $state.snapshot: The returned object is a plain JavaScript clone. Reading properties performs zero dependency tracking, and mutating properties has zero effect on Svelte or the rendered screen.

Because $state.snapshot returns native unproxied data, browser APIs like structuredClone and postMessage accept it without hesitation. Third-party charting libraries receive pure data without proxy interference, and debugging tools display clean, transparent object structures.

Here is BackupManager.svelte. It receives the reactive article draft and an onSaveBackup callback through $props() (see Lecture 9), rendering the draft title, word count, and backup status card.

```svelte title="BackupManager.svelte"
<script>
  let { article, onSaveBackup } = $props();

  let statusMessage = $state('Ready to archive');

  function handleBackup() {
    onSaveBackup();
    statusMessage = 'Backup saved to disk';
  }
</script>

<aside class="backup-panel">
  <h3>Backup Manager</h3>
  <p>Draft: <strong>{article.title}</strong></p>
  <p>Words: <strong>{article.words}</strong></p>
  <p>Status: {statusMessage}</p>
  <button onclick={handleBackup}>Save Backup</button>
</aside>
```

### Crossing Boundaries: Structured Clone, Storage, and Logging

Now examine ArticleEditor.svelte, where the application manages the reactive article draft and executes backup operations. This example demonstrates the contrast between passing live proxies to external tools versus unwrapping them with $state.snapshot.

```svelte title="ArticleEditor.svelte"
<script>
  import BackupManager from './BackupManager.svelte';

  let article = $state({
    title: 'Offshore Energy Crisis',
    words: 1450,
    sections: ['Investigation', 'Public Records', 'Interviews']
  });

  let savedSnapshots = $state([]);

  function backupBroken() {
    const copy = structuredClone(article); // **WRONG:** Native clone throws an error on a Svelte **PROXY**.
    savedSnapshots = [...savedSnapshots, copy];
  }

  function backupWorking() {
    const rawCopy = $state.snapshot(article); // **RIGHT:** Strips all proxies and returns a plain **OBJECT**.
    const deepClone = structuredClone(rawCopy); // **RIGHT:** Native browser clone accepts plain **DATA**.
    savedSnapshots = [...savedSnapshots, deepClone];
  }

  function logDraft() {
    console.log($state.snapshot(article)); // **RIGHT:** Prints clean data without proxy **TRAPS**.
  }
</script>

<main class="editor-shell">
  <h2>Investigative Newsroom Editor</h2>
  <label>
    Headline:
    <input bind:value={article.title} />
  </label>
  <label>
    Word Count:
    <input type="number" bind:value={article.words} />
  </label>
  <BackupManager {article} onSaveBackup={backupWorking} />
</main>
```

In backupBroken, the function passes the reactive article proxy directly into structuredClone. The browser encounters Svelte's proxy traps and throws a DataCloneError, terminating execution before the record can be added to savedSnapshots. In backupWorking, calling $state.snapshot(article) traverses the draft structure, stripping every proxy wrapper and producing an inert deep clone. When structuredClone receives this clean clone, it duplicates the record smoothly and appends it to savedSnapshots.

Notice also the logDraft function. When developers log reactive state directly using console.log(article), browser developer tools display Proxy { <target>: Object, <handler>: Object }. To view actual values, developers must expand nested internal properties manually. In development mode, Svelte even displays a helpful console warning reminding developers to use $inspect (see Lecture 45) for tracking values over time or $state.snapshot for one-off logging. Wrapping the variable in $state.snapshot(article) logs a crisp, immediately readable JavaScript object.

### Snapshots Versus JSON Serialization and Shallow State

When developers first encounter the proxy barrier, a common naive question arises: why not simply use JSON.parse(JSON.stringify(article)) to strip proxies? We have used JSON serialization for years to clone objects in JavaScript; why does Svelte need a dedicated rune function?

While JSON serialization appears to produce plain objects, it suffers from severe limitations that corrupt application data:
- **Loss of data types:** JSON serialization converts Date instances into plain strings, permanently destroying their date methods. It converts NaN and Infinity into null, strips undefined object properties entirely, and converts Map and Set instances into empty objects.
- **Crash on circular references:** If your application data contains circular object references, JSON.stringify throws a fatal TypeError: Converting circular structure to JSON.
- **Performance overhead:** Converting an entire memory structure into an intermediate text string and parsing that string back into memory is significantly slower and generates unnecessary garbage collector pressure.

By contrast, $state.snapshot is built directly into Svelte's runtime. It traverses object graphs natively, cloning data structures without text serialization. Furthermore, if an object in your state tree defines a custom toJSON method, $state.snapshot respects it by cloning the value returned by toJSON rather than the raw instance. If an object cannot be cloned, such as a browser DOM node or a window reference, $state.snapshot retains the original reference and warns you in development, ensuring your application never crashes unexpectedly.

It is equally important to distinguish $state.snapshot from $state.raw (see Lecture 37). While both tools deal with unproxied data, they serve opposite directions:
- **$state.raw:** An input strategy. It creates a shallow reactive signal for large datasets at creation time, preventing Svelte from ever creating nested proxies.
- **$state.snapshot:** An output strategy. It takes an existing deeply reactive $state proxy and extracts an inert, plain copy so you can export it to external systems.

> [!KEY]
> $state.snapshot extracts a plain, static, non-reactive deep copy of reactive state, stripping all JavaScript Proxies so the data can safely pass to outside libraries, browser APIs, and developer tools.

### Summary

Svelte 5 wraps objects and arrays in JavaScript Proxies to deliver fine-grained reactivity, but external tools and native browser APIs require plain JavaScript data. The $state.snapshot rune bridges this divide by extracting an inert, non-reactive deep clone with all proxy wrappers removed. This allows your application to share data seamlessly with structuredClone, Web Workers, external libraries, and developer tools without sacrificing the benefits of deep reactivity inside your Svelte components.

- $state.snapshot returns a plain, static deep copy of reactive state with all Proxies removed.
- Native browser APIs like structuredClone and worker.postMessage throw errors when passed Proxies.
- External charting libraries and developer tools expect plain unproxied JavaScript data.
- Snapshots are completely detached from Svelte's signal graph; mutating them never updates the DOM.
- Unlike JSON serialization, $state.snapshot preserves data types and handles toJSON methods natively.
- Use $state.raw to avoid proxies at creation; use $state.snapshot to export plain data on demand.
