# Lecture 33: Instance Script Versus Module Script
> INTERVIEW QUESTION | ❱ CORE | What is the difference between <script> and <script module>?

1. A website visitor listens to audio dispatches from field reporters on the National Times website.
2. The page shows three audio player boxes, and the first box is currently playing City Hall audio.
3. The visitor clicks the play button on the second box to hear Harbor Strike news.
4. Why do both play?
5. Two reporters speak at once through the speakers, creating painful noise that drives the visitor away.
6. Each player box runs its own isolated setup, so no box knows another box started playing.
7. Today your component file grows a shared room where every copy coordinates through one shared value.

### Your Component File Grows a Second Script

Your `.svelte` component file grows a new part today. Up to now, every `.svelte` file you have built in this course contained at most one `<script>` block. That block is the instance script, meaning its code executes from scratch every single time the browser creates a new copy of your component. If your page places three audio player components on the screen, that instance script runs three separate times, creating three completely independent worlds. Any variable declared inside it belongs exclusively to that single copy.

The National Times homepage displays audio dispatches recorded by field reporters across the city. The editorial desk wants a clean listening experience: clicking play on one dispatch must immediately pause whichever dispatch was already playing. But when each component copy lives on its own isolated island, the first player cannot know that the second player just started. You get two reporters talking over each other at full volume. What the page needs is a shared coordinator, a single place in the component definition that runs once when JavaScript first loads the file, before any individual components are rendered.

In standard HTML or earlier component tutorials, putting two script tags in one component looks like a syntax error. Svelte explicitly allows a second script block when you add the `module` attribute, written as `<script module>`. We met this block briefly when exploring the anatomy of a component (see Lecture 3). The standard `<script>` tag is the instance script, running once per component copy. The `<script module>` tag is the module script, running exactly once when the file is imported. Look at the visual structure before we inspect the code: `DispatchBoard.svelte` stamps out three reporter dispatches, and all three share one coordinator.

```components title="national-times — Component Explorer"
DispatchBoard.svelte | stamps out reporter dispatches | shell
  AudioDispatch.svelte | 3 instances share one coordinator | instances | Dispatch #1 · City Hall · **PLAYING**;; Dispatch #2 · Harbor Strike · **STOPPED**;; Dispatch #3 · Courtroom · **STOPPED**
```

### The Communal Coordinator Across Instances

In `AudioDispatch.svelte`, the `<script module>` block sits right at the top of the file, directly above the regular `<script>` block. Inside the module block, we declare `activeId` using the `$state` rune, Svelte's built-in tool for creating reactive variables that update the screen when their value changes (see Lecture 4). Because `activeId` lives inside `<script module>`, only one copy of that variable exists in memory. All three dispatch instances read and update that exact same variable.

```svelte title="AudioDispatch.svelte"
<script module>
  let activeId = $state(null); // **RIGHT:** Evaluates **ONCE**; all copies share this single coordinator.
</script>

<script>
  let { id, title } = $props(); // **RIGHT:** Runs for **EACH** instance; receives unique properties.

  let isPlaying = $derived(activeId === id); // Reads module state; stays in **SYNC** across all instances.

  function toggle() {
    if (isPlaying) {
      activeId = null; // Pause the current dispatch.
    } else {
      activeId = id; // **RIGHT:** Playing this dispatch **AUTOMATICALLY** pauses any other dispatch.
    }
  }
</script>

<div class="dispatch">
  <p>{title}: {isPlaying ? 'Playing' : 'Stopped'}</p>
  <button onclick={toggle}>{isPlaying ? 'Pause' : 'Play'}</button>
</div>
```

Each copy of `AudioDispatch.svelte` receives its own `id` and `title` via `$props()`, Svelte's rune for receiving data from parent components (see Lecture 9). The regular `<script>` block runs separately for each dispatch, so each dispatch knows its own identity. But `isPlaying` is a derived value, created with `$derived` (see Lecture 7 and Lecture 32), that checks whether `activeId === id`. When a listener clicks play on dispatch number two, `toggle` sets `activeId` to two. Svelte's reactivity system immediately notifies all three instances. Dispatch number one sees that its id no longer matches and pauses itself. Dispatch number two sees a match and starts playing.

Here is the parent component, `DispatchBoard.svelte`, which stamps out three independent copies of `AudioDispatch.svelte` on the page.

```svelte title="DispatchBoard.svelte"
<script>
  import AudioDispatch from './AudioDispatch.svelte';
</script>

<div class="dispatch-board">
  <h2>Audio Dispatches</h2>
  <AudioDispatch id={1} title="City Hall" />
  <AudioDispatch id={2} title="Harbor Strike" />
  <AudioDispatch id={3} title="Courtroom" />
</div>
```

### Why Not Pass Props or Use a Shared Module File?

Whenever developers first encounter `<script module>`, two natural alternatives come to mind from earlier lessons. The first alternative is lifting state up to `DispatchBoard.svelte` and passing down callback functions as props (see Lecture 11). That works cleanly when all dispatches live in one tidy parent container. But in a real newsroom application, an audio dispatch might appear in the top breaking news banner, another in the main article body, and a third inside a floating sidebar drawer. Lifting state across unrelated branches of the component tree forces you to pass props and callbacks through dozens of intermediate components that have nothing to do with audio playback.

The second alternative is creating a separate shared state file, like `audio.svelte.js` (see Lecture 25). Standalone `.svelte.js` modules are the gold standard for global application data like logged-in user profiles or shopping carts. But when the shared coordinator, play logic, and markup belong exclusively to the audio player itself, creating an external module fractures the component. A developer moving `AudioDispatch.svelte` to another project would have to remember to copy the auxiliary `.svelte.js` file and rewire the import paths. With `<script module>`, the component remains completely self-contained. Anyone who imports `AudioDispatch.svelte` gets the coordinator and the playback rules bundled in one single file.

### Exporting Utilities and Snippets to the Outside World

The module script has another distinct superpower: it can export functions, constants, types, and snippets to the rest of your application. The regular `<script>` block in Svelte 5 is reserved for instance logic and receives props via `$props()`. You cannot write standard module exports inside an instance script. But any export placed inside `<script module>` becomes a named export of the compiled component file.

```svelte title="AudioDispatch.svelte"
<script module>
  let activeId = $state(null);

  export function stopAllDispatches() { // **RIGHT:** Named **EXPORT** callable from outside the component.
    activeId = null;
  }
</script>
```

If the National Times homepage has an emergency broadcast banner that needs to silence all audio clips immediately, it does not need a reference to every player instance. It simply imports the named function: `import AudioDispatch, { stopAllDispatches } from './AudioDispatch.svelte'`. Calling `stopAllDispatches()` modifies the module-level `activeId`, immediately pausing every active dispatch across the page.

Starting in Svelte 5.5, top-level snippets can also be exported from `<script module>` (see Lecture 21). If `AudioDispatch.svelte` defines a reusable status badge snippet that does not depend on instance state, you can write `export { statusBadge }` inside the module block. Other components across the newsroom site can then import and render that snippet directly with `{@render statusBadge('live')}`.

The boundary between the two scripts follows strict one-way visibility rules. Code inside the instance `<script>` can freely read and update variables declared in `<script module>`. But the reverse is strictly impossible: code inside `<script module>` cannot access variables, props, or functions declared in `<script>`. The module script runs only once when JavaScript first loads the file, a moment when zero component instances exist. Attempting to read an instance variable from inside the module block will trigger a compiler error. Furthermore, Svelte forbids `export default` inside `<script module>`, because the component itself is always the default export of a `.svelte` file.

> [!TIP]
> **To impress the interviewer:** Explain that `<script module>` runs exactly once when the module file is first imported, while the standard `<script>` runs once per component instance. Mention that `<script module>` can export named functions, constants, and snippets (in Svelte 5.5+), but cannot use `export default` because the component itself is the default export. Emphasize that in Svelte 5, you can place `$state` inside `<script module>` to create shared reactive singletons across instances without needing an external `.svelte.js` file. Finally, note the one-way scope rule: instance scripts can access module declarations, but module scripts cannot access instance state.

> [!KEY]
> Use `<script>` for private data that every component copy owns independently, and use `<script module>` for shared state, exports, and heavy setup that should run only once.

### Where you will meet this

- Field reporter audio dispatches pause each other when a new clip plays, because all player boxes share one active playback identifier.
- An accordion FAQ list closes any open answer when a user clicks a new question, because every accordion item checks a shared active panel index.
- A photo gallery modal displays full-screen pictures from thumbnails scattered across multiple blog posts, because all thumbnail cards coordinate through one shared dialog controller.
- A stock ticker component shares a single WebSocket connection across ten header widgets, because the network subscription opens once inside the module script rather than ten separate times.

### Summary

The standard `<script>` block and the `<script module>` block divide component responsibilities between individual instances and the shared module. The instance script executes every time a new copy of the component is mounted, creating private state and receiving props. The module script executes only once when the file is first imported, providing a shared space for reactive singletons, expensive one-time setup, and exported helper functions or snippets. By keeping module-level coordination directly inside the `.svelte` file, components remain completely self-contained and easy to reuse.

- The `<script>` block runs once per component instance; `<script module>` runs once when the module first loads.
- Variables declared with `$state` inside `<script module>` are shared reactive singletons across every instance of the component.
- The instance script and markup can read module variables, but `<script module>` cannot access instance variables.
- You can export named functions, constants, and top-level snippets from `<script module>`, but `export default` is forbidden.
- Use `<script module>` when shared coordination belongs exclusively to the component, avoiding prop-drilling or external helper files.

| | **INSTANCE SCRIPT**<br>(instance) | **MODULE SCRIPT**<br>(module) |
| ---: | :--- | :--- |
| **Tag syntax** | `<script>` | `<script module>` |
| **Execution timing** | Runs every time an instance mounts | Runs once when the file is first imported |
| **Execution count** | Once per component copy on the page | Exactly once for the lifetime of the page |
| **State ownership** | Private to each individual instance | Shared across every instance of the component |
| **Scope visibility** | Can read variables from `<script module>` | Cannot access variables from `<script>` |
| **Module exports** | Cannot export named bindings | Can export functions, constants, and snippets |
| **Typical use cases** | Props, local UI state, element bindings | Shared coordinators, lookup caches, helpers |
