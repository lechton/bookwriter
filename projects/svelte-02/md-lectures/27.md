# Lecture 27: State in Effects
> INTERVIEW QUESTION | ❱ CORE | Why shouldn't you update state inside an `$effect`, and what should you do instead?

1. You are building an analytics tracker that logs user actions.
2. You write a reactive block that updates variables when a user clicks.
3. Why does it freeze?
4. A frozen app ruins the user experience instantly and forces a hard refresh.
5. The logic works flawlessly in testing but instantly crashes the browser in production.
6. We will learn to safely isolate external systems from internal data.

### The Infinite Loop Trap
You are trying to calculate a derived value based on a change to a variable. Your first instinct is to write a reactive block to watch the variable, and then overwrite the secondary value when the first one updates. If you try to synchronize Svelte state with other Svelte state inside an effect, you force the component into a dangerous cycle. The effect reads a value, updates a different state variable, and that update triggers the effect to run again, locking up the browser.

```components title="State in Effects — Component Explorer"
App.svelte | | shell
  BrokenLoop.svelte | | generic | Increment 0 (Double: **0**)
  DerivedFix.svelte | | generic | Increment 0 (Double: **0**)
  EventFix.svelte | | generic | typing box: empty;; warning: Username is too long
```

The two buttons paint exactly the same screen, and that is the trap: the broken version and the fixed version look identical until the user clicks.

In Svelte 5, updating state inside an effect is considered an anti-pattern. An effect is designed to run after the component has rendered. If that effect then modifies a piece of state that the component relies on, the component is immediately invalidated and must render a second time. 

```svelte title="BrokenLoop.svelte"
<script>
  let count = $state(0);
  let double = $state(0);

  $effect(() => {
    double = count * 2; // ✖️ updating state inside an effect causes a **double** render
  });
</script>

<button onclick={() => count++}>
  Increment {count} (Double: {double})
</button>
```

When you click the button, `count` increments and the component renders. Then the effect runs and updates `double`. Because `double` is reactive, the component must render a second time. You just paid for two renders to do the work of one. If `double` had triggered another effect that updated `count`, the browser would crash instantly in an endless loop.

### The Derived Fix
The correct way to compute a value based on another value is to use the dedicated derivation rune. This mechanism is pull-based, meaning it only computes the value when the template actually needs to read it. This completely eliminates the secondary render cycle.

```svelte title="DerivedFix.svelte"
<script>
  let count = $state(0);
  
  let double = $derived(count * 2); // ✔️ derive the value **synchronously** without an effect
</script>

<button onclick={() => count++}>
  Increment {count} (Double: {double})
</button>
```

With this approach, Svelte evaluates `double` exactly once during the initial render pass. There is no second render, no risk of an infinite loop, and the browser performs far less work. 

### The Event Handler Fix
Sometimes developers use an effect to watch state and trigger an action. For example, if a form input exceeds ten characters, you want to log a warning or adjust the layout. But updating state from an effect based on a user action separates the cause from the effect. The action was the user typing, so the logic belongs where the typing is handled.

```svelte title="EventFix.svelte"
<script>
  let username = $state('');
  let warning = $state('');

  function handleInput(e) {
    username = e.target.value; // ✔️ handle the state update directly inside the **user** event
    if (username.length > 10) {
      warning = 'Username is too long';
    } else {
      warning = '';
    }
  }
</script>

<input value={username} oninput={handleInput} />
<p>{warning}</p>
```

If the user typed the text, put the logic in the event handler. You only use effects to synchronize Svelte with systems outside of Svelte, like reading the DOM dimensions, setting a `localStorage` item, or connecting to a WebSocket.

> [!TIP]
> **To impress the interviewer:** Mention that updating state in an effect is a guaranteed double-render. The initial render completes, the effect fires and updates state, which invalidates the component and forces a second, completely avoidable render.

### Summary
Effects are a bridge to the outside world, not a tool for internal state synchronization. If you find yourself updating a `$state` variable inside an `$effect`, you are almost certainly introducing performance bugs and loop hazards.
- Never use an effect to compute one state value from another.
- Use `$derived` for computed values to guarantee single-pass rendering.
- Put logic triggered by a user action directly inside the event handler.
- Save effects strictly for external systems like `localStorage`, APIs, and DOM measuring.

| | **SYNC STATE**<br>(internal) | **SYNC SYSTEM**<br>(external) |
| ---: | :--- | :--- |
| **Tool** | `$derived` | `$effect` |
| **Trigger** | State changes | Render completes |
| **Risk** | None | Infinite loops |
