# Lecture 25: Shared Module State
> INTERVIEW QUESTION | ❱ CORE | How do you share reactive state across many components that aren't parent and child?

A user's login status is needed across the navbar, sidebar, and three deep pages. How do you share that reactive state without prop-drilling?

1. You are building the global navigation for the National Times.
2. The user signs in, and the header component fetches their subscriber profile.
3. How do components share?
4. Passing data through ten layers of intermediate components creates a brittle, unmaintainable mess.
5. The sidebar needs the profile but has no direct connection to the header.
6. You can lift this data completely outside the component tree.

### The Trap of Prop Drilling

When you declare reactive state inside a component, that data is strictly local. If the header component owns the user profile, it must pass it up to a common ancestor, like the root application layout, using a callback. Then the application layout must pass it down through the page, into the sidebar, and finally into the specific widget that actually displays the user's name. This technique, called prop drilling, forces you to wire data through every single layer of your application. It turns all of your intermediate components into useless middlemen that do not care about the user data, but are forced to declare properties and pass them along just to keep the plumbing connected. If the shape of the user profile changes, you have to update a dozen different files. When disconnected components need to read and write the exact same data, the solution is to move that data entirely out of the component hierarchy.

```components title="national-times — Component Explorer"
App.svelte | renders the header and sidebar | shell
  Header.svelte | mutates the shared session module | header | **Sign In**
  Sidebar.svelte | reads the shared session module | navigation | Welcome back, **Alice**!
  session.svelte.js | the shared login state both components import | generic
```

Read the two filled boxes as the shared state story: before sign in, the header shows its Sign In button and the sidebar shows nothing at all. The moment the header writes Alice into the shared session, the sidebar greeting appears, and the module between them never renders anything.

### Lifting State to a Module

The architectural fix is to completely abandon the component tree for this piece of data. Instead of letting any one component own the user profile, you create a neutral, independent JavaScript file to hold it as a universal source of truth. In Svelte 5, you achieve this by appending the `.svelte.js` extension to a standard JavaScript file. This unique file extension acts as a signal to the Svelte compiler, granting the file permission to use reactive framework features like the state rune outside of any component. Inside this new module, you declare a constant variable and assign it a reactive state object.

```javascript title="session.svelte.js"
export const session = $state({ user: null }); // **RIGHT:** export a reactive object from a module
```

By exporting an object wrapped in the state rune, you create a globally shared reactive proxy. A proxy is a special object that actively intercepts reads and writes to its properties. Because this proxy lives in a module rather than a component, it is instantiated exactly once when the application first loads. Every file that imports this session module receives the exact same reference to that single, persistent proxy in memory.

### Reading and Writing Shared State

Once the state is safely isolated in its own file, any component that needs it can bypass the component hierarchy entirely. The header component simply imports the session object and modifies it directly when the user completes the sign in process.

```svelte title="Header.svelte"
<script>
  import { session } from '../state/session.svelte.js';

  function login() {
    session.user = { name: 'Alice', tier: 'subscriber' }; // **RIGHT:** mutating the shared proxy updates all readers instantly
  }
</script>

<button onclick={login}>Sign In</button>
```

To the header, this operation feels exactly like mutating a local variable. However, because the session object is a reactive proxy, Svelte immediately detects the assignment. The framework then broadcasts this change to any other component that has imported the session and read the user property, triggering a targeted update.

```svelte title="Sidebar.svelte"
<script>
  import { session } from '../state/session.svelte.js';
</script>

{#if session.user}
  <p>Welcome back, {session.user.name}!</p> <!-- **RIGHT:** reads the shared property directly without props -->
{/if}
```

The sidebar requires no special subscription syntax, no context lookups, and no event listeners. It imports the data directly and renders it. When the header changes the user property, the sidebar updates automatically. The two components are communicating flawlessly without ever knowing that the other exists.

### Beyond Component Boundaries

This module pattern completely decouples your application state from your user interface. Because the session state is just standard JavaScript backed by a proxy, you are not restricted to reading it exclusively inside `.svelte` component files. You can import this exact same session object into other utility files, routing guards, or network clients. If your API client needs to attach an authentication token to every single outgoing request, it can import the session module and read the user's token directly. The reactivity travels with the proxy wherever it goes, making it a robust foundation for your entire application architecture.

### The Primitive Reassignment Trap

There is one structural hazard to watch out for when sharing state through a module. You must export a container, such as an object or an array, and your components must mutate the properties inside that container. You cannot export a primitive variable and attempt to reassign it.

```javascript title="session.svelte.js"
export let currentUser = $state(null); // **WRONG:** reassigning a primitive variable breaks module bindings
```

If you export a simple variable and a component attempts to update it by reassigning it to a new value, the reactive connection shatters. This failure happens because of how standard JavaScript modules work. When a component imports the current user, it receives the specific reference that existed at the moment of import. If another component reassigns the variable, it points the name to a brand new object, but all the other components are still holding onto the original, now stale reference. By exporting a constant container object like our session, you guarantee that the top level reference never changes. The components always hold the correct container, and Svelte can safely track all the mutations happening inside it.

> [!KEY]
> You can share reactive state across your entire application by exporting a state object from a standalone `.svelte.js` file.

> [!TIP]
> **To impress the interviewer:** Explain that in Svelte 5, the traditional readable and writable stores are no longer required for simple global state. You can achieve universal reactivity purely through JavaScript modules and the state rune, leading to cleaner code that does not require the auto subscription dollar sign prefix in your templates.

### Summary

Sharing state across disconnected components is achieved by lifting the data out of the component tree and into a standalone module. By appending the `.svelte.js` extension to a file, you gain the ability to use reactive runes directly in standard JavaScript. Exporting an object wrapped in state creates a shared reactive proxy that any component can import. Because all importing components share the exact same object reference, mutating a property on that object in one component will instantly trigger updates in every other component that reads it. You must always export a container object or array rather than a primitive variable, because reassigning a primitive value breaks standard JavaScript module bindings and leaves the user interface completely stale.

* A `.svelte.js` file allows you to use reactive runes entirely outside of a Svelte component.
* Exporting an object wrapped in state creates a globally shared reactive proxy.
* Components import the shared state exactly like they would import a regular JavaScript module.
* Mutating a property on the shared object in one place updates all readers instantly.
* You must export an object or array and mutate its properties instead of reassigning a primitive variable.

| | **LOCAL STATE**<br>(component) | **SHARED STATE**<br>(module) |
| ---: | :--- | :--- |
| **Location** | Declared inside a component script tag | Exported from a `.svelte.js` module file |
| **Visibility** | Private to the component unless passed down | Available to any file that imports it |
| **Update Mechanism** | Direct assignment or deep mutation | Deep mutation of the shared proxy properties |
| **Coupling** | Tightly coupled to the component tree | Decoupled and usable anywhere in the application |
