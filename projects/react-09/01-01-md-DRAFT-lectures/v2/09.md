## Why We Compose Props with children, Spread Attributes, and Default Values

### Hardcoded badges inside a card force every story to wear the same labels

Look at the story cards on any real news website. Every card shares the same outer box, heading, summary, and reading time line. Yet different stories carry different status badges at the top of the card. A breaking story about a new park carries both a `Live` badge and a `New` badge. A library announcement right below it carries only a `New` badge.

Suppose our card file imports both badges and places them directly inside the card markup:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleCard({ title, summary, readTime }) {
  const totalTime = readTime + 2;

  return (
    <article className="card">
      ~<LiveBadge />~ {/* **WRONG:** hardcoded inside ArticleCard, so every card gets LiveBadge! */}
      ~<NewBadge />~ {/* **WRONG:** hardcoded inside ArticleCard, so every card gets NewBadge! */}
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

Then our list file renders two card tags, one for the park story and one for the library story:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList() {
  return (
    <section>
      <ArticleCard
        title="New Park Opens Today"
        summary="The park on Main Street opens at noon."
        readTime={3}
      />
      <ArticleCard
        title="Library Extends Hours"
        summary="The downtown branch now stays open until 9 PM."
        readTime={5}
      />
    </section>
  );
}
```

Save both files, and look at the page in the browser. Both stories show their own headings and summaries, **but the library announcement also wears a `Live` badge that does not belong to it**:

```page caption="When LiveBadge and NewBadge are hardcoded inside ArticleCard.jsx, every card on the page is forced to show both badges."
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. · 5 min total · 3 min read | good
card: badge=Live | badge=New | title=Library Extends Hours | text=The downtown branch now stays open until 9 PM. · 7 min total · 5 min read | bad
```

Why did the library card get a `Live` badge? Because both badge tags sit directly inside the card function. Every time React calls the card function, it stamps out both badges at the top of the card. We want the card file to own the shared `<article>` box and text layout, while the list file decides which badge tags sit inside each card.

```tree caption="Two ways to put badges inside an ArticleCard: hardcoding them inside ArticleCard.jsx vs. passing them between opening and closing <ArticleCard> tags."
How to place different inner elements inside `ArticleCard`
- !Hardcode `<LiveBadge />` and `<NewBadge />` inside `ArticleCard.jsx` | Every card on the page is forced to show **the exact same badges** | You cannot give one card two badges and another card one badge
- +Nest badge tags between `<ArticleCard>` and `</ArticleCard>` in `ArticleList.jsx` | +**DO** let each card tag wrap **its own inner elements** | `ArticleCard` renders whatever inner content the parent hands it
```

### Passing inner markup between opening and closing tags with `children`

In plain HTML, when you want to place elements inside an `<article>` box, you write an opening `<article>` tag, put the inner elements inside it, and close it with `</article>`.

In React, you can wrap inner elements inside your own component tag the exact same way. Handing inner elements from a parent tag into a child component takes **two steps**.

First, in our list file, we give each card tag an opening tag and a closing tag, and we place each story's badges between them:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleList() {
  return (
    <section>
      <ArticleCard
        title="New Park Opens Today"
        summary="The park on Main Street opens at noon."
        readTime={3}
      >
        ~<LiveBadge />~ {/* 1st card wraps both LiveBadge and NewBadge */}
        ~<NewBadge />~ {/* 2nd badge inside the 1st card */}
      </ArticleCard>
      <ArticleCard
        title="Library Extends Hours"
        summary="The downtown branch now stays open until 9 PM."
        readTime={5}
      >
        ~<NewBadge />~ {/* 2nd card wraps only NewBadge */}
      </ArticleCard>
    </section>
  );
}
```

Whenever you place JSX between a component's opening and closing tags, React automatically packs that nested content into the `props` object under a reserved property name: **`children`**.

Second, in our card file, we unpack `children` in the parameter list and write `{children}` inside the `<article>` box right where the badges should appear:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime, ~children~ }) { // 1. Unpacks the reserved children prop
  const totalTime = readTime + 2;

  return (
    <article className="card">
      {~children~} {/* 2. Places the parent's nested badge tags right here */}
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

Save both files, and each card now displays only the badges placed inside its own tag:

```page caption="What the user sees when ArticleList nests badge tags inside each <ArticleCard> and ArticleCard renders {children}."
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. · 5 min total · 3 min read | good
card: badge=New | title=Library Extends Hours | text=The downtown branch now stays open until 9 PM. · 7 min total · 5 min read | good
```

```tree dir=right caption="The two steps that pass nested JSX between component tags and render it on the page."
How nested JSX flows from `<ArticleCard>...</ArticleCard>` to the screen
- +Step 1: Nest JSX between the tags [`ArticleList.jsx`] | Place `<LiveBadge />` and `<NewBadge />` between `<ArticleCard>` and `</ArticleCard>`
- +Step 2: Unpack and render `children` [`ArticleCard.jsx`] | Destructure `children` in the parameter list and place `{children}` inside `<article>`
```

### Built-in HTML tags insert their inner content automatically, while your component tags wait for `children`

Look closely at the two kinds of wrapper tags in our code: a built-in HTML `<article>` tag and our own `<ArticleCard>` component tag. Both can wrap inner tags between an opening tag and a closing tag.

Yet the browser and React handle their inner content in two very different ways:
- **On a built-in HTML tag**, such as `<article>` or `<section>`, the tag itself is a single box in the DOM. Any elements you place between `<article>` and `</article>` go straight inside that box automatically.
- **On your own React component tag**, such as `<ArticleCard>`, the component returns an entire tree of elements, with a heading and two paragraphs. React cannot guess whether your nested badges belong above the heading, between the heading and the summary, or at the bottom of the card! So React hands those nested elements to your function inside the `children` prop. Nothing appears on the page until your code writes `{children}` in the exact spot where they belong:

```tree caption="What happens to inner tags placed inside a built-in HTML tag vs. inside your own React component tag."
Inner tags placed between opening and closing tags
- +Built-in HTML tag [`<article><h3>...</h3></article>`] | The browser knows `<article>` is **one DOM box** | Inner tags appear inside `<article>` **automatically**
- +Your React component tag [`<ArticleCard><NewBadge /></ArticleCard>`] | React packs the inner tags into **`props.children`** | Inner tags appear **only where your function writes `{children}`**
```

### Three Principles of Props Composition

**PRINCIPLES:** Once a component accepts `props`, three tools let a parent compose it cleanly: nesting inner JSX, spreading an object's properties, and setting default values. Each tool prevents a silent bug in daily coding and answers a classic interview question:
1. **Principle 1: The `children` Prop**: Anything placed between a component's opening and closing tags is passed by React inside `props.children`. If you forget to render `{children}` inside the card file, or unpack a custom name like `badges`, every badge vanishes with zero Console errors.
2. **Principle 2: JSX Spread Attributes**: When a story's fields sit inside an object, writing `{...parkStory}` on the card tag copies every key directly into `props`. Passing `parkStory={parkStory}` without the three dots leaves the card's top-level props `undefined`. Writing `{...parkStory}` **after** an attribute you wanted to override overwrites your new value back to the object's old value!
3. **Principle 3: Default Prop Values**: Writing `readTime = 3` in the parameter list gives the reading time a fallback whenever a card tag omits it or passes `undefined`. Without that default, leaving out `readTime` turns the total time into `NaN` on the page. Passing `null` or `0` does **not** trigger a JavaScript default parameter. In addition, React 19 ignores `defaultProps` on function components.

Here is the complete overview of all three principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The `children` Prop: Nest JSX and Render `{children}`** | Forgetting `{children}` or unpacking `{ badges }` instead of `{ children }` makes nested tags vanish from the DOM with zero Console errors. | Nest inner JSX between `<ArticleCard>` and `</ArticleCard>` in the parent, unpack `children` in the child, and render `{children}` where that content belongs. |
| **Principle 2** | **Spread Attributes: Forward Object Keys with `{...obj}`** | Writing `parkStory={parkStory}` leaves top-level props `undefined`; placing `{...parkStory}` after `readTime={5}` overwrites `5`; spreading custom props onto `<article>` logs a DOM error. | Spread an object with `{...parkStory}`, place explicit overrides **after** the spread, and strip custom props before spreading onto HTML tags. |
| **Principle 3** | **Default Values: Set Fallbacks with `=` in Parameters** | Omitting `readTime` without a default prints `NaN min total`; passing `null` bypasses `= 3` and prints `2 min total`; `defaultProps` on function components is ignored in React 19. | Assign fallback values with `=` in destructured parameters, such as `{ readTime = 3 }`, which apply when the prop is omitted or `undefined`. |

## 1. Principle 1: The `children` Prop: Nest JSX Between Opening and Closing Tags and Render `{children}`

### A component function does not show nested tags until it renders `children`, and the prop name is fixed as `children`

When you wrap `<LiveBadge />` between `<ArticleCard>` and `</ArticleCard>`, it looks just like wrapping a tag inside an HTML `<article>`. That visual similarity causes two bugs when developers build their first wrapper component.

- **In daily coding**: First, if you nest badge tags inside a card tag **but forget to write `{children}` inside the card file**, the badges disappear with **zero Console errors**. Second, if you unpack a custom parameter name such as `badges` instead of `children`, the badges also disappear silently.
- **In an interview**: Explain why the parameter must be named `children` and why wrapper components use it. The JSX compiler always assigns content placed between opening and closing tags to the property `props.children`. Because the card component renders `{children}` without knowing what is inside it, any parent can fill that slot with badges, buttons, or nothing at all.

### How the build packs nested tags into `props.children`

Look back at our list file. We never wrote an attribute named `children=` on either card tag! Where did the property name `children` come from?

Before the browser runs our list file, the build rewrites each `<ArticleCard>...</ArticleCard>` tag into a `_jsxDEV` call. Whatever tags sit between the opening and closing card tags are placed into the second argument under the property key `children`:

```js title="How the build rewrites <ArticleCard>...</ArticleCard> in ArticleList.jsx"
_jsxDEV(ArticleCard, {
  title: 'New Park Opens Today',
  summary: 'The park on Main Street opens at noon.',
  readTime: 3,
  ~children: [_jsxDEV(LiveBadge, {}), _jsxDEV(NewBadge, {})]~ // 2 nested tags become an array in props.children
});

_jsxDEV(ArticleCard, {
  title: 'Library Extends Hours',
  summary: 'The downtown branch now stays open until 9 PM.',
  readTime: 5,
  ~children: _jsxDEV(NewBadge, {})~ // 1 nested tag becomes a single React element in props.children
});
```

Look at what the build put inside `props.children` for each card:
1. On the first card, we placed **two** badge tags inside `<ArticleCard>`, so `props.children` is an array holding those two React elements.
2. On the second card, we placed **one** badge tag inside `<ArticleCard>`, so `props.children` is that single React element.

```tree dir=right caption="How the build turns tags nested between <ArticleCard> and </ArticleCard> into props.children."
Nested JSX on its way from `ArticleList` into `ArticleCard`
- +1. Parent nests tags [`ArticleList.jsx`] | `<ArticleCard ...><LiveBadge /><NewBadge /></ArticleCard>`
- +2. Build sets `props.children` [JSX transform] | Packs the inner tags under the exact key `children` on `props`
- +3. Child renders `{children}` [`ArticleCard.jsx`] | `<article className="card">{children}...</article>` puts the badges in the DOM
```

### Mistake 1: Nesting tags inside `<ArticleCard>...</ArticleCard>` without placing `{children}` in the card file

In our list file, we import both badges and place them between the opening and closing `<ArticleCard>` tags:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleList() {
  return (
    <section>
      <ArticleCard
        title="New Park Opens Today"
        summary="The park on Main Street opens at noon."
        readTime={3}
      >
        ~<LiveBadge />~ {/* Passed into ArticleCard as props.children */}
        ~<NewBadge />~ {/* Also packed into props.children */}
      </ArticleCard>
    </section>
  );
}
```

Now look at what happens in the card file when we remove the old hardcoded badges **but forget to render the parent's inner content inside the card**:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ~ArticleCard({ title, summary, readTime })~ { // **WRONG:** never unpacks children!
  const totalTime = readTime + 2;

  return (
    <article className="card">
      ~<h3>{title}</h3>~ {/* **WRONG:** no {children} above <h3>, so the parent's badges are thrown away! */}
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

When you **nest tags inside a component tag without rendering `{children}` inside that component**, every nested tag vanishes from the screen with **zero Console errors**! Look at what happened in order:
1. React handed the two badge elements to `ArticleCard` inside `props.children`.
2. Inside `ArticleCard`, the function unpacked only the three story fields and returned only the heading and the two paragraphs.
3. Because a React component only puts into the DOM what it returns, `props.children` was silently discarded.

### Mistake 2: Unpacking a custom parameter name such as `badges` instead of `children`

What if a developer remembers to unpack a fourth parameter in the card file, **but names that parameter `badges` to describe what the slot holds**?

Look at the card file when the parameter is named `badges`:

```jsx title="src/components/ArticleCard.jsx" startLine="1"

  const totalTime = readTime + 2;

  return (
    <article className="card">
      {~badges~} {/* **WRONG:** badges is undefined, so React renders nothing here! */}
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

Save the file, and the badges still do not appear on the page, with zero Console errors!

Why did `{badges}` evaluate to `undefined` when the list file clearly placed both badge tags inside the card tag?
1. In the list file, we did not write an attribute named `badges=` on the `<ArticleCard>` tag. We placed the two badges **between** `<ArticleCard>` and `</ArticleCard>`.
2. Whenever content sits between opening and closing tags, the build **always** stores it under the property name `children`, never `badges`.
3. When the card function unpacks that custom name, JavaScript reads `props.badges`, which does not exist and returns `undefined`. React renders `undefined` as nothing at all.

### Unpacking `children` and placing `{children}` inside the card

To make the nested badges appear, we unpack the reserved `children` prop in our card file and render it at the top of the article box:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>

}
```

What if a card component needs **two separate holes** in different places, such as a badge slot at the top and an action button slot at the bottom? Because a JSX tag is just a JavaScript object, you can keep `children` for the main slot. Then you can pass JSX into a regular named prop for the second slot, such as `header={<LiveBadge />}`:

```tree caption="Two ways to pass JSX into a child wrapper component: between its tags as children or inside a named attribute."
How a parent passes JSX elements into a wrapper component
- +One main slot: between opening and closing tags [`<ArticleCard><NewBadge /></ArticleCard>`] | Packed automatically into **`props.children`** | Child unpacks **`children`** and renders **`{children}`**
- +Multiple separate slots: in a named prop attribute [`<ArticleCard header={<LiveBadge />}>`] | Packed into **`props.header`** alongside `props.children` | Child unpacks **`header`** and **`children`** and places each in its own spot
```

## 2. Principle 2: JSX Spread Attributes: Forward an Object's Keys with `{...object}` and Place Overrides After the Spread

### Passing an object as one prop nests it inside `props`, while spreading copies its keys to the top level

In our list file, we wrote the heading, the summary, and the reading time as three separate attributes on the first card tag. In a real news app, however, a story's fields already sit together inside a JavaScript object. Typing `title={parkStory.title}` and `summary={parkStory.summary}` by hand for every field on every card tag quickly clutters the file.

- **In daily coding**: Two silent bugs happen when forwarding an object onto a card tag. First, if you pass `parkStory={parkStory}` without the three dots, the card's top-level props arrive as `undefined`. Its heading goes blank and its total time displays `NaN` with **zero Console errors**. Second, if you write `{...parkStory}` **after** an attribute you wanted to override, the spread overwrites your new value back to the object's old value!
- **In an interview**: Explain how JSX spread attributes work and where their boundary lies. Writing `{...parkStory}` on a JSX tag copies each property from that object directly onto `props` from left to right. Never spread custom component props straight onto a built-in HTML tag such as `<article {...props}>`, or React will log an unknown DOM prop error.

### In plain JavaScript, `...` copies an object's keys, and the last key written wins

Before we use spread syntax on a JSX tag, look at how three dots `...` work inside a plain JavaScript object. When you write `...parkStory` inside a new object literal, JavaScript copies every property from `parkStory` into the new object from left to right. If the same property name appears twice, **whichever one is written later overwrites the earlier one**:

```js title="Plain JavaScript"
const parkStory = { title: 'New Park Opens Today', readTime: 3 };

const overrideAfter = { ~...parkStory, readTime: 5~ }; // 1. Spreads readTime: 3 first, then readTime: 5 overwrites it -> 5
const overrideBefore = { ~readTime: 5, ...parkStory~ }; // 2. Sets readTime: 5 first, then ...parkStory overwrites it back -> 3

console.log(overrideAfter.readTime); // Prints 5
console.log(overrideBefore.readTime); // Prints 3
```

Look at why those two objects ended up with different reading times:
1. In `overrideAfter`, JavaScript copied the three-minute reading time from the story object first. Then `readTime: 5` came after the spread and replaced three with five.
2. In `overrideBefore`, JavaScript set `readTime: 5` first. Then `...parkStory` came after it and overwrote five back to three.

```tree caption="What happens in JavaScript when you nest an object under a property name vs. when you copy its keys with spread syntax."
Ways to put `parkStory` into a `props` object
- !Nest under a property name [`{ parkStory: parkStory }`] | Creates **one nested `parkStory` key** | Top-level `props.title` and `props.readTime` are **`undefined`**
- +Spread first, override after [`{ ...parkStory, readTime: 5 }`] | Copies `title`, `summary`, and `readTime` to the **top level** | Later `readTime: 5` **wins**
- !Override first, spread after [`{ readTime: 5, ...parkStory }`] | Sets `readTime: 5` first, then copies `parkStory` over it | `parkStory.readTime` **overwrites `5` back to `3`!**
```

### Mistake 1: Passing `parkStory={parkStory}` when the card unpacks `{ title, summary, readTime }`

Suppose our list file stores the first story in an object named `parkStory`. Look at what happens if a developer passes that object as a regular named prop `parkStory={parkStory}` on the card tag:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleList() {
  const parkStory = {
    title: 'New Park Opens Today',
    summary: 'The park on Main Street opens at noon.',
    readTime: 3,
  };

  return (
    <section>
      <ArticleCard ~parkStory={parkStory}~> {/* **WRONG:** nests the object inside props.parkStory! */}
        <LiveBadge />
        <NewBadge />
      </ArticleCard>
    </section>
  );
}
```

Meanwhile, our card file still unpacks the story fields and `children` from the top level of `props`:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard(~{ title, summary, readTime, children }~) { // Looks for props.title, props.summary, and props.readTime at the top level
  const totalTime = readTime + 2;

  return (
    <article className="card">
      {children}
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

When you **pass `parkStory={parkStory}` to a component that unpacks individual fields from `props`**, the card breaks silently with **zero Console errors**! Look at what happened in order:
1. Writing `parkStory={parkStory}` placed the story object inside a nested property named `props.parkStory`.
2. Inside the card function, the destructured parameters looked for `props.title` and the other story fields at the top level, so all three evaluated to `undefined`.
3. Adding `undefined + 2` produced `NaN`, so the card rendered an empty heading, an empty summary, and Not-a-Number in the reading time line.

### Spreading `{...parkStory}` onto the card tag copies every key into `props`

To copy every field out of our story object and onto the top level of `props`, we spread `{...parkStory}` on the card tag:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleList() {
  const parkStory = {
    title: 'New Park Opens Today',
    summary: 'The park on Main Street opens at noon.',
    readTime: 3,
  };

  return (
    <section>
      <ArticleCard ~{...parkStory}~> {/* Copies title, summary, and readTime directly onto props */}
        <LiveBadge />
        <NewBadge />
      </ArticleCard>
    </section>
  );
}
```

Look closely at `<ArticleCard {...parkStory}>` in our list file. Nowhere on that card tag did we write `title=` or `readTime=` by hand! How did the card file still receive all three story fields?

1. Inside `parkStory`, the object's keys already match the parameter names that `ArticleCard` expects.
2. Writing `{...parkStory}` on the card tag tells the build to copy every key from that object directly into `props`.
3. When React calls `ArticleCard`, all three story fields and `children` sit at the top level, just as if we had written each attribute by hand.

What if you forget the three dots and write `<ArticleCard {parkStory}>`? On a JSX opening tag, curly braces only accept `...` spread syntax. Leaving out the three dots stops the build immediately with a `SyntaxError`.

### Mistake 2: Placing `{...parkStory}` after an explicit attribute override

Suppose `parkStory` has a reading time of three minutes, and for today's featured park opening we want to override `readTime` on the tag to five minutes.

Look at what happens if a developer writes `readTime={5}` **first** and `{...parkStory}` **after** it on the tag:

```jsx title="src/components/ArticleList.jsx" startLine="11"
  return (
    <section>
      <ArticleCard ~readTime={5} {...parkStory}~> {/* **WRONG:** {...parkStory} comes second and overwrites readTime back to 3! */}
        <LiveBadge />
        <NewBadge />
      </ArticleCard>
    </section>
  );
```

When you **place `{...parkStory}` after `readTime={5}`**, the card ignores your override and still shows a three-minute reading time with **zero Console warnings**! Because JSX merges attributes from left to right, `{...parkStory}` copies the object's three-minute value over your earlier `readTime={5}`.

To let your explicit attribute win, put `{...parkStory}` **first** and write the override attribute **after** it:

```jsx title="src/components/ArticleList.jsx" startLine="11"

        <NewBadge />
```

### Why you must not spread custom component props onto a built-in HTML tag

What happens if our card file takes the entire `props` object and spreads `{...props}` straight onto the built-in HTML article tag?

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard(props) {
  const totalTime = props.readTime + 2;

  return (
    <article className="card" ~{...props}~> {/* **WRONG:** forwards custom prop readTime onto a built-in HTML <article> tag! */}
      {props.children}
      <h3>{props.title}</h3>
      <p>{props.summary}</p>
      <p>{totalTime} min total · {props.readTime} min read</p>
    </article>
  );
}
```

Save the file, and Chrome's Console panel logs a red error:

```devconsole
x React does not recognize the `readTime` prop on a DOM element. If you intentionally want it to appear in the DOM as a custom attribute, spell it as lowercase `readtime` instead. If you accidentally passed it from a parent component, remove it from the DOM element.
```

Why did React complain? Because `<article>` is a built-in browser HTML tag, and `readTime` is our own custom component prop, not a real HTML attribute. What if your card needs to forward real HTML attributes, such as `id`, onto `<article>`? Unpack your component's own props first and collect the remaining HTML attributes with `...domProps`:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime, children, ~...domProps~ }) { // 1. Strips custom props and collects remaining HTML attributes
  const totalTime = readTime + 2;

  return (
    <article className="card" ~{...domProps}~> {/* 2. Forwards only valid HTML attributes onto <article> */}
      {children}
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

> [!PRINCIPLE]
> **Principle 2: JSX Spread Attributes: Forward Object Keys with `{...object}` and Place Overrides After**
>
> *Use `{...parkStory}` on a JSX tag to copy an object's properties onto `props`, and write any explicit attribute overrides after the spread.*
>
> When your story data already lives inside an object, passing `parkStory={parkStory}` without the three dots nests the whole object under `props.parkStory`. Then the child looks for the story fields at the top level of `props`, gets `undefined`, and leaves the card blank! Writing `{...parkStory}` unpacks the object's keys right onto `props` from left to right. Because JSX reads attributes from left to right, always put `{...parkStory}` first and any attribute you want to override after it.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleList.jsx"
> const parkStory = { title: 'New Park Opens Today', summary: 'The park on Main Street opens at noon.', readTime: 3 };
>
> <ArticleCard ~{...parkStory} readTime={5}~> {/* Spreads parkStory first, then overrides readTime to 5 */}

> </ArticleCard>

>

> ```jsx title="src/components/ArticleList.jsx"

## 3. Principle 3: Default Prop Values: Set Fallbacks with `=` in Destructured Parameters

### An omitted prop arrives as `undefined`, and a default parameter replaces only `undefined`

Now look at the second card in our article list, the short library announcement. Long feature stories carry a reading time, **but a short announcement often leaves the `readTime` attribute off the card tag**.

- **In daily coding**: If a card tag leaves out `readTime` and the card has no default value, that prop arrives as `undefined`. Adding two minutes to `undefined` produces `NaN` on the page with **zero Console errors**. A second bug happens when a database returns `null` for an empty field. Passing `readTime={null}` skips the default value because JavaScript parameter defaults only replace `undefined`!
- **In an interview**: State two rules clearly:
  1. In React 19, you set default prop values with `=` inside the destructured parameter list, such as `readTime = 3`. React 19 removed support for `defaultProps` on function components.
  2. A JavaScript default parameter triggers **only** when the prop is omitted or explicitly `undefined`. Passing `null` or `0` keeps that exact value instead of using the default.

### In plain JavaScript, `= 3` in destructuring runs only when a property is strictly `undefined`

Before we update our card component, look at how a default value `= 3` works when unpacking an object in plain JavaScript. JavaScript checks whether the property is strictly `undefined`. If it is `undefined`, JavaScript uses `3`. For any other value, including `0` and `null`, JavaScript keeps the value that was passed:

```js title="Plain JavaScript"
function showTime({ ~readTime = 3~ }) { // Uses 3 ONLY when readTime is undefined
  console.log(readTime);
}

showTime(~{}~); // Omitted -> readTime is undefined -> prints 3
showTime(~{ readTime: undefined }~); // Explicit undefined -> prints 3
showTime(~{ readTime: 0 }~); // Number 0 is NOT undefined -> prints 0
showTime(~{ readTime: null }~); // null is NOT undefined -> prints null
```

```tree caption="What JavaScript's destructuring default { readTime = 3 } produces for each of the four possible inputs."
How `{ readTime = 3 }` handles four inputs
- +Prop is omitted [`<ArticleCard />`] | `props.readTime` is **`undefined`** | Default fires: `readTime` becomes **`3`**
- +Explicit `undefined` [`readTime={undefined}`] | `props.readTime` is **`undefined`** | Default fires: `readTime` becomes **`3`**
- +Explicit `0` [`readTime={0}`] | `0` is a real number, **not `undefined`** | Default is skipped: `readTime` stays **`0`**
- !Explicit `null` [`readTime={null}`] | `null` is an empty object value, **not `undefined`** | Default is skipped: `readTime` stays **`null`!**
```

### Mistake 2: Expecting `readTime = 3` to replace `null`, or using removed `defaultProps` in React 19

Two classic interview traps sit right behind default prop values.

First, suppose a database record has an empty reading time column that returns `null`, and the parent passes `readTime={null}` to our card:

```jsx title="src/components/ArticleList.jsx" startLine="16"
      <ArticleCard
        title="Library Extends Hours"
        summary="The downtown branch now stays open until 9 PM."
        ~readTime={null}~ // **WRONG:** null is NOT undefined, so readTime = 3 will NOT run!
      >
        <NewBadge />
      </ArticleCard>
```

When you **pass `readTime={null}` to a component with `readTime = 3`**, the card prints two minutes total and a blank reading time on the page! Look at why:
1. JavaScript checks whether `props.readTime` is `undefined`. Because `null` is not `undefined`, JavaScript skips the default value and keeps the prop as null.
2. When JavaScript calculates `null + 2`, it treats null as zero and produces `2`.
3. Inside the paragraph, React renders `{readTime}` as nothing at all because `null` produces no text in JSX.

Second, in older React codebases before React 19, developers sometimes left `= 3` out of the function parameters and attached a `.defaultProps` object below the function:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, ~readTime~, children }) { // No = 3 in parameter list
  const totalTime = readTime + 2;
  return (
    <article className="card">
      {children}
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}

~ArticleCard.defaultProps = { readTime: 3 };~ // **WRONG:** React 19 removed defaultProps on function components, so it is silently ignored!
```

In React 19, **`defaultProps` on function components has been removed**. At runtime, React 19 ignores `ArticleCard.defaultProps` without a warning, leaving the omitted prop as `undefined` and printing NaN on the screen. Always use `= 3` in the destructured parameter list instead.

Here is how our card function behaves across all four possible inputs when its parameter list sets `readTime = 3`:

| What the Parent Tag Passes | Value of `props.readTime` | Does `readTime = 3` Run? | Final `readTime` | Rendered Paragraph in the DOM |
| :--- | :--- | :--- | :--- | :--- |
| **Omitted** `<ArticleCard title="..." />` | `undefined` | **Yes** | `3` | `<p>5 min total · 3 min read</p>` |
| **Explicit `undefined`** `readTime={undefined}` | `undefined` | **Yes** | `3` | `<p>5 min total · 3 min read</p>` |
| **Explicit `0`** `readTime={0}` | `0` | **No**, `0` is kept | `0` | `<p>2 min total · 0 min read</p>` |
| **Explicit `null`** `readTime={null}` | `null` | **No**, `null` is kept | `null` | `<p>2 min total ·  min read</p>` |

> [!PRINCIPLE]
> **Principle 3: Default Prop Values: Set Fallbacks with `=` in Destructured Parameters**
>
> *Define default prop values using `=` inside the component's destructured parameter list, such as `readTime = 3`.*
>
> When a parent tag leaves out an optional prop like `readTime`, JavaScript sets that parameter to `undefined`. Without a fallback value, adding two minutes turns `undefined + 2` into `NaN` right on the user's screen! Putting `readTime = 3` inside the parameter curly braces tells JavaScript to use three whenever the prop is omitted or `undefined`. Remember that JavaScript parameter defaults only replace `undefined`, never `null` or zero. In addition, React 19 completely ignores `defaultProps` on function components.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> export default function ArticleCard({ title, summary, ~readTime = 3~, children }) { // Falls back to 3 when readTime is omitted or undefined
>   const totalTime = readTime + 2;
>   return <article className="card">{children}<h3>{title}</h3><p>{totalTime} min total · {readTime} min read</p></article>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> export default function ArticleCard({ title, summary, ~readTime~, children }) { // **WRONG:** omitted readTime stays undefined and produces NaN!
>   const totalTime = readTime + 2;
>   return <article className="card">{children}<h3>{title}</h3><p>{totalTime} min total · {readTime} min read</p></article>;
> }
> ~ArticleCard.defaultProps = { readTime: 3 };~ // **WRONG:** ignored on function components in React 19!
> ```

| :--- | :--- | :--- |

## For the Interview

> **The Interview Question:** How do the children prop, spread attributes, and default values work?

### How to Answer Clearly in 30 Seconds

"These three mechanisms control how a parent composes a child component's `props`:
1. **The `children` prop**: Any JSX placed between a component's opening and closing tags, like `<ArticleCard><NewBadge /></ArticleCard>`, is packed by the JSX compiler into `props.children`. Unlike built-in HTML tags, a React component only displays that nested content where it explicitly evaluates `{children}` in its returned JSX. This enables slot composition, where a wrapper component provides the layout box without knowing its inner content ahead of time.
2. **JSX spread attributes with `{...object}`**: Writing `{...parkStory}` on a JSX tag copies every own enumerable property from `parkStory` into the component's `props` object. Attributes are evaluated from left to right, so whichever key comes last wins. Place `{...parkStory}` before an explicit attribute when you want that explicit attribute to override the object.
3. **Default prop values with `prop = defaultValue`**: In React 19, we define default prop values with `=` in the destructured parameter list, such as `{ title, readTime = 3, children }`. React 19 removed `defaultProps` on function components. Because parameter defaults use standard JavaScript rules, the fallback runs only when the prop is omitted or `undefined`, never when it is `null` or `0`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"When a component sets `{ readTime = 3 }`, what happens if the parent passes `undefined`, `null`, or `0`? And does `ArticleCard.defaultProps` still work in React 19?"**
   - JavaScript default parameters check strictly for `=== undefined`. If the parent omits `readTime` or passes `readTime={undefined}`, `readTime` falls back to `3`. If the parent passes `readTime={0}`, `0` is kept. If the parent passes `readTime={null}`, `null` is not `undefined`, so `readTime` stays `null`. In that case, `null + 2` evaluates to `2`, and `{null}` renders nothing in JSX.
   - As for `ArticleCard.defaultProps`, React 19 removed support for `defaultProps` on function components. Setting `ArticleCard.defaultProps = { readTime: 3 }` on a function component is silently ignored at runtime in React 19.

2. **"What is the difference between `<ArticleCard {...parkStory} readTime={5}>` and `<ArticleCard readTime={5} {...parkStory}>` when `parkStory.readTime` is `3`?"**
   - JSX attributes are merged from left to right into the `props` object.
   - In `<ArticleCard {...parkStory} readTime={5}>`, `parkStory` copies `readTime: 3` first, and then `readTime={5}` overwrites it to `5`.
   - In `<ArticleCard readTime={5} {...parkStory}>`, `readTime: 5` is set first, and then `{...parkStory}` copies `readTime: 3` over it, silently overwriting `5` back to `3`.

3. **"What happens if a component forwards `{...props}` directly onto a built-in DOM element like `<article {...props}>`, and how do you prevent it?"**
   - If `props` contains custom component props such as `readTime` or `isBreaking`, spreading `{...props}` onto `<article>` passes those custom names to a real HTML element. React logs a red Console error: `React does not recognize the \`readTime\` prop on a DOM element.`
   - To prevent that error, use rest destructuring in the parameter list, such as `{ title, summary, readTime, children, ...domProps }`, to strip your component's own props first. Then spread only `{...domProps}` onto `<article>`.
