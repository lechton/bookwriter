## Why Components Need Memory with useState

### Plain local variables with `let` vs. component memory with `useState`

Suppose we build a small counter component with a button that adds one to the count each time the user clicks it. Compare writing that counter with a plain local `let` variable against writing it with React's `useState`:

```jsx title="Option 1: A plain local let variable inside a component"
function Counter() {
  ~let count = 0;~ // 1. Starts at 0 every time Counter runs

  function handleClick() {
    ~count = count + 1;~ // 2. Changes the local variable, but never tells React to redraw!
  }

  return <button onClick={handleClick}>Count: {count}</button>;
}
```

Now look at the same counter written with `useState`:

```jsx title="Option 2: Component memory with useState"
import { ~useState~ } from 'react'; // 1. Import useState from React

function Counter() {
  const ~[count, setCount]~ = useState(0); // 2. React keeps count in memory outside Counter

  function handleClick() {
    ~setCount(count + 1);~ // 3. Saves the next number in React and redraws Counter!
  }

  return <button onClick={handleClick}>Count: {count}</button>;
}
```

**When the page first loads, both versions show `Count: 0` on the screen. They look like they work the same way at first, but they are NOT the same thing at all!**

In Option 1, clicking the button never changes the number on the screen. Every time React renders your component, it calls your function from top to bottom. Think of React walking into a room, reading the blueprint, and sweeping the room clean when it leaves. A plain `let` variable is like writing a tally on a disposable sticky note inside that room:
1. Changing `count` inside `handleClick` never rings React's bell to tell React that the screen needs to update.
2. Even if React enters the room again later, it starts from line 1 and writes a brand-new sticky note saying `0`, wiping out whatever you wrote before.

In Option 2, calling `useState` asks React to keep the number on a permanent clipboard **outside** the room. Even when `Counter` finishes running, React's clipboard keeps the number safe between renders.

Look at the three words you will hear in every React team and interview:
- **What is "state"?** In everyday English, **state** means the current condition of something that changes over time, like whether a lamp is on or how many likes a story has. In React, **state** is a component's own memory that React stores outside the function so it survives between renders.
- **What is a "Hook"?** In everyday English, a **hook** lets you attach onto a larger system. In React, a **Hook** is a special function whose name starts with `use`, such as `useState`, that lets your component hook into React features like state.
- **What are the two items `useState` gives back?** Calling `useState` hands you a pair of items in an array. The first item is the **state variable** `count`, which holds the current value on React's clipboard. The second item is the **setter function** `setCount`, which saves a new value on the clipboard and asks React to **re-render** the component:

```tree caption="Why a plain local let variable fails to update the screen, while useState remembers the value and triggers a re-render."
Two ways to store a changing value inside a component
- !Plain local variable [`let count = 0`] | Lives only during **one function call** and gets wiped on the next run | Changing `count` **never notifies React**, so the screen stays frozen
- +React state Hook [`[count, setCount]`] | Stored by React on a **permanent clipboard outside the function** | Calling `setCount` **saves the next value** and tells React to **re-render**
```

### Why `[count, setCount]` is the exact same thing as reading array items `0` and `1`

When you first see the square brackets around `[count, setCount]`, they can look like special React syntax.

In fact, `useState` simply returns a normal two-item JavaScript array. Item `0` is the current value, and item `1` is the setter function. You could read those two items out of the array one by one using `[0]` and `[1]`:

```jsx title="Reading the two array items by index 0 and 1"
const ~pair~ = useState(0); // 1. Returns a two-item array: [0, function]
const ~count = pair[0]~; // 2. First item at index 0 is the current value
const ~setCount = pair[1]~; // 3. Second item at index 1 is the setter function
```

Instead of writing three lines, JavaScript lets you unpack both items by position in one line using square brackets:

```jsx title="The shortcut: unpacking both array items with [count, setCount]"
const ~[count, setCount]~ = useState(0); // Exact same thing as reading pair[0] and pair[1]!
```

**Yes, it is the exact same thing!** Unpacking an array with square brackets on the left side of `=` is standard JavaScript **array destructuring**. Because arrays work by position rather than property names, you can choose any names that fit your component, following the `[something, setSomething]` naming habit:

```tree caption="Reading pair[0] and pair[1] by index is the exact same thing as array destructuring with [count, setCount]."
Two ways to unpack the two-item array returned by `useState`
- +1. Read by index one by one [`pair[0]` and `pair[1]`] | Reads item `0` into `count` and item `1` into `setCount` | Takes **three lines** of code
- +2. Unpack with array destructuring [`[count, setCount]`] | Unpacks item `0` and item `1` **in one line** | **Exact same result**; you choose any names like `[likes, setLikes]`
```

### Building a story card with its own interactive memory

Now look at where component memory matters on a real page. Suppose our reader page displays a story card with a `Like` button and a `Show summary` toggle button.

Each interaction on that card needs memory that survives between renders and redraws the screen:
1. When a reader clicks `Like`, the card must add one to its like count and show the new number on the screen right away.
2. When a reader clicks `Show summary`, the card must switch the button label to `Hide summary` and display the summary paragraph below the buttons.
3. Suppose two story cards sit side by side on the page. Clicking `Like` or `Show summary` on the first card must update **only** the first card, leaving the second card's count and summary untouched.

As our story card grows through this lesson, we will use `useState` in three ways depending on what the component needs:
- **Passing a simple starting value directly**: when the starting value is a simple number or boolean like `0` or `false`, we pass it directly to the Hook.
- **Passing an initializer function without parentheses**: sometimes finding the starting value requires running a helper function such as `loadSavedLikes`. We pass that function without parentheses so React runs it only on the first render.
- **Calling `useState` multiple times at the top level**: one component often tracks two independent pieces of data, such as `likes` and `showSummary`. We call `useState` once for each piece at the very top of the component:

```tree caption="The three ways we use useState as our story card grows across this chapter."
Three ways to set up state with `useState`
- +Simple starting value [`0` or `false`] | Best when the starting value is **already a simple literal** | React uses it on the **first render** and ignores it on re-renders
- +Initializer function [`loadSavedLikes` without parentheses] | Best when computing the starting value **calls a function** | React calls the function **only once** on the first render
- +Multiple `useState` calls [`likes` and `showSummary`] | Best when a component tracks **unrelated pieces of memory** | Called in the **exact same top-level order** on every render
```

### Four Principles of Component Memory with useState

**PRINCIPLES:** A component function runs from top to bottom every time it renders. Any ordinary local variable inside that function is created fresh when the function starts and forgotten when the function finishes. To give a component memory that lasts across renders and updates the screen, React provides the `useState` Hook, governed by four practical rules:
1. **Principle 1: Replace Local Variables with `useState`**: Storing changing screen data in a local `let` variable fails in two ways. Changing it never tells React to re-render, and the next render recreates the variable from scratch. Use `useState` so React stores the value outside the function and re-renders when you call the setter.
2. **Principle 2: Pass an Initializer Function Without Parentheses**: React uses the starting value passed to `useState` only on the first render. If computing that starting value requires calling a helper function, pass the function by name without parentheses so JavaScript does not run it again on every re-render.
3. **Principle 3: Call Multiple `useState` Hooks at the Top Level**: A component can call `useState` as many times as it needs. React tells multiple `useState` calls apart by their top-to-bottom call order rather than by variable names. Because of that, every Hook must sit unconditionally at the top level of the component, never inside `if` blocks, loops, or after an early return.
4. **Principle 4: State Is Isolated and Private to Each Component Instance**: State does not belong to the component function definition in the file. It belongs to each individual component tag rendered on the screen. Rendering two cards gives each card its own independent memory, and the parent component cannot read or change a child card's state.

Here is the complete overview of all four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Local Variables vs. `useState`** | Updating a local `let` variable logs the new value in the Console while the screen stays frozen on the old value. | Store changing UI data with `useState` and update it with the setter function so React remembers the value and re-renders. |
| **Principle 2** | **Initializer Function Without Parentheses** | Calling a setup function with parentheses inside `useState` re-runs that setup function on every single click, even though React throws away its result after the first render. | Pass the setup function reference without parentheses to `useState` so React calls it only once on the initial render. |
| **Principle 3** | **Top-Level Hook Call Order** | Placing a `useState` call inside an `if` block or below an early `return` shifts React's internal slot order and crashes the page on re-render. | Call every Hook unconditionally at the very top level of the component function so the call order stays identical on every render. |
| **Principle 4** | **Isolated Per-Instance State** | Developers often fear two `<StoryCard />` tags will share one counter, or they put a `let` variable at the top of the file and accidentally link all cards together. | Keep `useState` inside the component function; each rendered `<StoryCard />` on screen gets its own isolated, private state in memory. |

## 1. Principle 1: Replace Ephemeral Local Variables with `useState` So Changes Persist and Trigger a Re-Render

### Why a local `let` variable fails twice when clicked

Before we touch our story card files, look closely at what happens inside a plain JavaScript function when you declare a local variable with `let`:

```js title="Plain JavaScript: local variables start over on every call"
function countVisit() {
  ~let visits = 0;~ // 1. Recreated at 0 every single time countVisit runs!
  visits = visits + 1;
  return visits;
}

console.log(~countVisit()~); // 2. First call logs 1
console.log(~countVisit()~); // 3. Second call ALSO logs 1, because visits was reset to 0!
```

Every time `countVisit` runs, JavaScript creates a brand-new `visits` variable set to zero, adds one to it, and throws the variable away when the function finishes. Calling `countVisit` a second time does not continue from `1`. It starts all over again at `0`!

When you put a local `let` variable inside a React component, two separate problems stop your screen from updating:
1. **Local mutations do not trigger a re-render**: Changing a local variable inside a click handler happens in silence. React has no idea the variable changed, so React never calls your component function again to update the screen.
2. **Every re-render resets local variables from scratch**: Whenever React re-renders your component later, it calls your component function again from line 1. That sets `count` back to `0` and wipes out your earlier change:

```tree caption="The two separate reasons an ordinary local let variable fails to update a React component."
Why `let likes = 0` inside a component never updates the screen
- !1. Mutating `likes` never triggers a re-render [`likes = likes + 1`] | Changes the local number in memory, **but never notifies React** | React **never calls the component again**, so the screen stays frozen
- !2. Re-rendering resets `likes` from scratch [`let likes = 0` at line 1] | Every render calls your component function **again from the top** | Runs `let likes = 0` **all over again**, wiping out any earlier change
```

### Why `[likes, setLikes]` uses square brackets and `const`

When we replace a local variable with `useState`, we unpack `[likes, setLikes]` on the left side of the line. Notice two details in that line that interviewers love to ask about.

First, why did we unpack `props` with **curly braces** like `{ title }` in earlier chapters? And why do we unpack `useState` with **square brackets** like `[likes, setLikes]` here?

Look at the two shapes side by side in plain JavaScript:

```js title="Object destructuring with { } vs. array destructuring with [ ]"
const props = { ~title~: 'New Park Opens Today' }; // 1. An object: values are stored under fixed property names
const ~{ title }~ = props; // Curly braces { } match the exact property name "title"

const statePair = ~[0, setLikes]~; // 2. An array: values are stored by position 0 and position 1
const ~[likes, setLikes]~ = statePair; // Square brackets [ ] unpack position 0 and position 1 under any names you choose!
```

Second, if the like count climbs with every click, why do we declare `likes` with **`const`** instead of a mutable variable?

Because **you never reassign `likes` with `=` yourself**! During a single run of your component function, `likes` is a constant that never changes. When you call `setLikes`, React calls your component function **all over again** in a brand-new run. In that new run, React creates a fresh `const likes` holding the updated number:

```tree caption="Why props use curly braces { } while useState uses square brackets [ ] and const."
How `[likes, setLikes]` works in JavaScript
- +Square brackets `[ ]` [Array destructuring] | `useState` returns a **two-item array** by position `0` and `1` | Lets you give item `0` and item `1` **any names you want**
- +Declared with `const` [Never reassigned with `=`] | You **never** reassign `likes` with `=` | Each re-render runs the function anew with a **fresh `const likes`** holding the new value
```

### Mistake: Storing the like count in a local `let` variable inside `StoryCard`

Now let us start building our reader page and see the local variable bug in action. First, our main file imports the story card and places one card on the page with its title and summary props:

```jsx title="src/App.jsx" startLine="1"
import StoryCard from './components/StoryCard.jsx';

export default function App() {
  return (
    <main>
      <h1>Top Stories</h1>
      ~<StoryCard~ // Renders one story card with its title and summary props
        title="New Park Opens Today"
        summary="The park on Main Street opens at noon."
      />
    </main>
  );
}
```

Inside the card file, suppose a developer stores the like count in a local `let` variable at the top of the function. Inside the click handler, the developer adds one to that variable and prints the new value to the Console:

```jsx title="src/components/StoryCard.jsx" startLine="1"
export default function StoryCard({ title }) {
  ~let likes = 0;~ // **WRONG:** plain local variable forgets its value and never triggers a re-render!

  function handleLike() {
    ~likes = likes + 1;~ // **WRONG:** mutates local variable in silence without telling React!
    console.log('Local likes:', likes);
  }

  return (
    <article className="card">
      <h3>{title}</h3>
      <p className="likes-text">Likes: {likes}</p>
      <button className="like-btn" onClick={handleLike}>
        Like
      </button>
    </article>
  );
}
```

Save both files and open the browser. Look at what happens in order when the user clicks the `Like` button twice:
1. When the page first loads, React calls `StoryCard`, sets the count to zero, and draws `Likes: 0` on the card.
2. The user clicks `Like` a first time, and then a second time.
3. In Chrome's **Console panel**, two lines appear: `Local likes: 1` and `Local likes: 2`. That proves our click handler ran both times!
4. Yet on the page itself, the card is still stuck on `Likes: 0`! Because assigning to a local variable never tells React to re-render the card, the screen never updates.

### Storing `likes` in React state with `useState` and `setLikes`

To make the card remember its likes and redraw the screen on every click, we make two changes in the card file. First, we bring in React's state Hook at the top of the file and create a state slot for the like count starting at zero:

```jsx title="src/components/StoryCard.jsx" startLine="1"
import { ~useState~ } from 'react'; // 1. Import the useState Hook from React

export default function StoryCard({ title }) {
  const ~[likes, setLikes]~ = useState(0); // 2. Unpack current state (likes) and setter (setLikes)
```

Second, inside the click handler, we call our setter function with the next count so React saves the new number and redraws the card:

```jsx title="src/components/StoryCard.jsx" startLine="6"
  function handleLike() {
    ~setLikes(likes + 1);~ // 3. Save the next number in React and request a re-render!
  }

  return (
    <article className="card">
      <h3>{title}</h3>
      <p className="likes-text">Likes: ~{likes}~</p> {/* 4. Displays the latest likes count from React state */}
      <button className="like-btn" onClick={handleLike}>
        Like
      </button>
    </article>
  );
}
```

Look closely at the fixed card file above. Nowhere in our file did we declare a variable outside `StoryCard`, and nowhere in our file did we write a call to run `StoryCard` a second time! Who remembered the number one, and who called `StoryCard` again when the user clicked `Like`?

React did both jobs for us through `useState` and `setLikes`:
1. **On the first render**, `StoryCard` calls `useState` with zero. React creates a state slot in its own memory outside `StoryCard`, puts zero inside it, and returns that number along with `setLikes`. The card displays `Likes: 0`.
2. **When the user clicks the button**, `handleLike` calls `setLikes` with the next count, one.
3. **Inside React**, `setLikes` stores the number one in that state slot and schedules a new render of `StoryCard`.
4. **On the second render**, React calls `StoryCard` again. This time, `useState` ignores the starting zero, reads the stored one from React's memory slot, and hands it back with `setLikes`. React compares the new output with the page and updates the paragraph in the DOM to `Likes: 1`!

```tree dir=right caption="What happens step by step from the first render through clicking Like with useState."
How `useState` remembers `likes` across renders
- +1. First render [`useState` with `0`] | React stores `0` in its external memory slot and returns `[0, setLikes]` | Screen shows **`Likes: 0`**
- +2. User clicks `Like` [`setLikes` with `0 + 1`] | `setLikes` saves **`1`** into React's memory slot | Tells React to **re-render `StoryCard`**
- +3. Second render [`StoryCard` runs again] | `useState` ignores `0` and returns **`[1, setLikes]`** from React's memory | Screen updates to **`Likes: 1`**
```

When is a plain local variable still the right choice? Sometimes you only calculate a temporary value while rendering or inside a single click handler. When that value does not need to survive between renders or update the screen, a plain `const` variable works fine. Whenever a component must remember a changing value across renders and update the screen, use `useState`:

> [!PRINCIPLE]
> **Principle 1: Component Memory: Store Changing UI Data in `useState`, Never in a Local `let` Variable**
>
> *Store any changing value that updates the screen inside `useState`, and call its setter function to save the next value and trigger a re-render.*
>
> A plain local `let` variable inside a component fails in two ways when you try to update the screen. First, reassigning it in an event handler happens in silence and never tells React to re-render the page. Second, every time the component does re-render, React runs the function again from line 1 and recreates the `let` variable from scratch. Calling `useState` stores the value in React's memory outside the function and gives you a setter function that both saves the next value and triggers a re-render.
>
> **DO THIS:**
> ```jsx
> import { useState } from 'react';
>
> export default function StoryCard({ title }) {
>   const ~[likes, setLikes] = useState(0)~; // Stored in React memory across renders
>   return <button onClick={() => ~setLikes(likes + 1)~}>{title}: {likes}</button>; // Saves next value and re-renders
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function StoryCard({ title }) {
>   ~let likes = 0;~ // **WRONG:** resets to 0 on every render and never triggers a re-render!
>   return <button onClick={() => { ~likes = likes + 1;~ }}>{title}: {likes}</button>; // **WRONG:** screen stays frozen at 0!
> }
> ```

## 2. Principle 2: Pass an Initializer Function Without Parentheses So Setup Runs Only Once

### Why calling a function vs. passing a function inside `useState` looks the same on screen, but is NOT the same thing

In Principle 1, we started `likes` at a simple number, `0`. What if the starting like count is not zero, and instead comes from calling a helper function `loadSavedLikes` that returns `10`?

Look at the two ways you might write `loadSavedLikes` inside the parentheses of `useState`:

```jsx title="Two ways to write loadSavedLikes inside useState"
function loadSavedLikes() {
  console.log('Reading saved likes...');
  return 10;
}

const [likes, setLikes] = ~useState(loadSavedLikes())~; // 1. WITH parentheses (): calls loadSavedLikes() on EVERY render!
const [likes, setLikes] = ~useState(loadSavedLikes)~;   // 2. WITHOUT parentheses: hands the function to React to call ONCE!
```

**Whether you write parentheses after `loadSavedLikes` or leave them off, the card starts at `Likes: 10` and climbs higher with every click. On the screen both versions look like they work the exact same way, but under the hood they are NOT the same thing!**

Imagine `loadSavedLikes` is a clerk who walks down to a basement archive to look up the starting like count, `10`.
- **When does React actually need that starting number?** Only on opening day, during the very first render! On the second and third renders, React already has the updated count on its clipboard, such as `11` or `12`, and ignores the starting argument completely.
- **What happens in Way 1 when you write parentheses after `loadSavedLikes`?** In JavaScript, writing parentheses after a function name calls that function right away, **before** `useState` even starts! So on every single re-render, you send the clerk down to the basement again just so React can throw the returned `10` away.
- **What happens in Way 2 when you leave the parentheses off `loadSavedLikes`?** You do not call the function yourself. Instead, you hand the function itself to React, like handing over the clerk's phone number. React calls that function **only once** on the very first render, and never calls it again on any re-render! A function handed to `useState` like this is called an **initializer function**:

```tree caption="Calling loadSavedLikes with parentheses inside useState vs. passing the initializer function without parentheses."
Two ways to pass a function-computed starting value to `useState`
- !With parentheses [`loadSavedLikes` called inside `useState`] | JavaScript calls `loadSavedLikes` **before `useState` runs on every render** | Wastes work on **every re-render** even though React throws the result away
- +Without parentheses [`loadSavedLikes` passed by name] | Hands the **initializer function** to React | React calls `loadSavedLikes` **only once** on the first render
```

### Calling a function right now vs. handing the function to React

We saw this exact same JavaScript rule with event handlers such as `onClick={handleLike}`. In plain JavaScript, writing parentheses after a function name runs the function immediately and passes its returned value. Writing the function name without parentheses passes the function itself:

```js title="Plain JavaScript: calling a function right now vs. passing the function itself"
function loadSavedLikes() {
  return 10;
}

const result = ~loadSavedLikes()~; // 1. With (): runs loadSavedLikes RIGHT NOW and stores the number 10
const fn = ~loadSavedLikes~;       // 2. Without (): does NOT run it yet; stores the function itself
```

When you pass an initializer function to `useState` without parentheses, it must follow three simple rules:
1. It takes **no arguments**.
2. It calculates and **returns** the starting state value.
3. You only need an initializer function when computing the starting value runs a function, such as reading from storage or filtering a large list. When the starting value is already a simple number or boolean like `0` or `false`, pass that value directly.

### Mistake: Calling `loadSavedLikes` with parentheses inside `useState`

Look at what happens in the card file when a developer writes `loadSavedLikes` at the top and calls it **with parentheses** inside `useState`.

First, we add a helper function at the top of the card file that logs a message and returns the saved starting count:

```jsx title="src/components/StoryCard.jsx" startLine="1"
import { useState } from 'react';

function ~loadSavedLikes~() { // Helper that logs when it runs and returns the starting count 10
  console.log('Reading saved likes...');
  return 10;
}
```

Next, inside the card component, suppose the developer calls that helper function with parentheses when setting up state:

```jsx title="src/components/StoryCard.jsx" startLine="8"
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(~loadSavedLikes()~); // **WRONG:** parentheses call loadSavedLikes() on EVERY re-render!

  function handleLike() {
    setLikes(likes + 1);
  }

  return (
    <article className="card">
      <h3>{title}</h3>
      <p className="likes-text">Likes: {likes}</p>
      <button className="like-btn" onClick={handleLike}>
        Like
      </button>
    </article>
  );
}
```

Save the file and watch the page and Chrome's **Console panel** as the user clicks `Like` twice:
1. **On initial page load**, JavaScript calls `loadSavedLikes` and logs `'Reading saved likes...'` a **first time**. It passes the returned ten to `useState`, and the card shows `Likes: 10`.

3. **On the second click**, `StoryCard` re-renders for twelve, and JavaScript calls `loadSavedLikes` a **third time**! Because the numbers on the screen still climb from ten to eleven and twelve, this wasted work is invisible until you check the Console.

### Passing `loadSavedLikes` without parentheses so React calls it only once

```jsx title="src/components/StoryCard.jsx" startLine="8"
export default function StoryCard({ title }) {
```

Look closely at line 9 above. There are **no parentheses** after `loadSavedLikes`, yet on the screen `likes` still starts as the number ten, not as a function! If we did not write parentheses to call `loadSavedLikes`, who called it?

React called it for us on the very first render! Look at what JavaScript and React do on each render:
1. **On the first render**, the card hands the `loadSavedLikes` function itself to `useState`. React sees that the starting argument is a function and calls `loadSavedLikes` once. It stores the returned ten in memory and hands back `10` and `setLikes`.

## 3. Principle 3: Call Multiple `useState` Hooks Unconditionally at the Top Level

### Why React cannot see your variable names, and how it tells multiple `useState` calls apart

Now our story card needs a second independent piece of memory. In addition to `likes` for the like button, we want a boolean `showSummary` that remembers whether the summary paragraph is open.

To give one component two pieces of memory, we call `useState` twice at the top of the component:

```jsx title="Calling useState twice at the top of StoryCard"
export default function StoryCard({ title, summary }) {
  const [likes, setLikes] = ~useState(loadSavedLikes)~;     // 1. First useState call -> Slot 0 (number 10)
  const [showSummary, setShowSummary] = ~useState(false)~; // 2. Second useState call -> Slot 1 (boolean false)
```

Look closely at those two `useState` calls. **When you write `likes` on the first line and `showSummary` on the second line, it looks like React knows those two variable names. In fact, React CANNOT see your variable names at all!**

Why can't React see the names `likes` and `showSummary`? Because in JavaScript, the `useState` call on the right side of `=` finishes **before** the returned array is unpacked into your variable names on the left side! Neither call passes a string name like `'likes'` or `'showSummary'` into the Hook.

If React cannot see your variable names, how on earth does it know which `useState` call gets the number ten and which call gets the boolean `false`?

Picture React keeping a numbered row of lockers for `StoryCard`: **Slot 0** and **Slot 1**.
- Every time React starts rendering `StoryCard`, it points its finger at **Slot 0**.
- The **first** `useState` call that runs always opens **Slot 0** and gets the number `10`. Then React moves its finger to **Slot 1**.
- The **second** `useState` call that runs always opens **Slot 1** and gets the boolean `false`.

As long as every render calls the same Hooks in the exact same top-to-bottom order, **Slot 0** always lands in `likes` and **Slot 1** lands in `showSummary`. What happens if you put a `useState` call inside an `if` block or below an early return? When a Hook gets skipped on one render, the slot numbers no longer match and React crashes the page!

```tree caption="React cannot see your variable names; it matches each useState call to its memory slot by its top-to-bottom call order."
How React tells multiple `useState` calls apart inside one component
- +1st `useState` call at the top [`likes`] | Always opens **Slot 0** in React's internal array | Returns **`[10, setLikes]`** on every render
- +2nd `useState` call right below it [`showSummary`] | Always opens **Slot 1** in React's internal array | Returns **`[false, setShowSummary]`** on every render
- !A `useState` call inside `if` or after `return` [Skipped on some renders] | ~Changes how many Hooks run from one render to the next | **Crashes React** because the slot order no longer matches!
```

### How React tracks state slots in an internal array during render

Under the hood, React stores a plain array of state slots paired with a step counter that resets to `0` at the start of every render:

```js title="Mental model: how React tracks useState slots by call order"
let componentHooks = [ ~[10, setLikes]~, ~[false, setShowSummary]~ ]; // Slot 0 and Slot 1 stored by React
let ~currentHookIndex = 0~; // Resets to 0 at the start of every render, then steps 0 -> 1 as each useState runs!
```

React relies on `currentHookIndex` stepping through the slots in the exact same order on every render. Because of that, `useState` and every other function whose name starts with `use` must obey one strict rule:
- **Call every Hook unconditionally at the very top level of your component function.**
- **Never** call `useState` inside an `if` statement, a loop, or a nested function. And **never** place a Hook below an early `return`; always put early return checks **after** every `useState` call at the top of the function.

### Mistake 1: Placing a `useState` call after an early `return`

Suppose a developer declares the first state variable at the top of the card and adds an early return for popular stories right below it. Then the developer declares the second state variable underneath that early return:

```jsx title="src/components/StoryCard.jsx" startLine="8"
export default function StoryCard({ title, summary }) {
  const [likes, setLikes] = useState(loadSavedLikes); // 1. Slot 0: runs on every render

  if (likes > 10) {
    ~return <p>Popular story!</p>;~ // **WRONG:** early return sits ABOVE the second useState call!
  }

  const [showSummary, setShowSummary] = ~useState(false)~; // **WRONG:** Slot 1 runs on Render 1, but is skipped when likes > 10!
```

When you first load the page, `likes` is `10`. The `if` condition is `false`, so both Hook calls run for **Slot 0** and **Slot 1**, and the page looks completely fine!

Now click the `Like` button once. Look at what happens in order:
1. Calling `setLikes` changes the count from ten to eleven and triggers a re-render of `StoryCard`.
2. On this second render, `useState` for `likes` runs at **Slot 0**.
3. Next, because `likes` is now greater than ten, the condition is true and `StoryCard` returns early on line 12!
4. The second `useState` call on line 15 **never runs**! React expected two Hook calls just like on the first render, sees only one, and immediately crashes the page with a red error in the Console:

```devconsole
x Uncaught Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
```

### Mistake 2: Placing a `useState` call inside an `if` block

The opposite mistake crashes the page the exact same way. Suppose a developer only wants the summary toggle once a story passes ten likes, and wraps the second state Hook inside an `if` block:

```jsx title="src/components/StoryCard.jsx" startLine="8"
export default function StoryCard({ title, summary }) {
  const [likes, setLikes] = useState(loadSavedLikes);

  if (likes > 10) {
    const [showSummary, setShowSummary] = ~useState(false)~; // **WRONG:** Hook inside an if block only runs when likes > 10!
  }
```

On the first load, `likes` is `10`, so only **one** Hook runs. When the user clicks `Like`, the count becomes eleven and triggers a re-render. Now the `if` block runs and calls a **second** Hook that did not exist on the first render! React detects the changed Hook count and crashes the page:

```devconsole
x React has detected a change in the order of Hooks called by StoryCard.
x Uncaught Error: Rendered more hooks than during the previous render.
```

### Declaring both `useState` calls unconditionally at the top of `StoryCard`

To fix the card component, we place both `useState` calls unconditionally at the very top of the function, before any event handlers or return statements:

```jsx title="src/components/StoryCard.jsx" startLine="8"
export default function StoryCard({ title, summary }) {
  const [likes, setLikes] = ~useState(loadSavedLikes)~;     // 1. Slot 0: always runs 1st at the top of StoryCard
  const [showSummary, setShowSummary] = ~useState(false)~; // 2. Slot 1: always runs 2nd at the top of StoryCard

  function handleLike() {
    setLikes(likes + 1);
  }

  function handleToggleSummary() {
    ~setShowSummary(!showSummary);~ // 3. Flips Slot 1 between false and true
  }
```

Below the two event handlers, the card renders the like button, the summary toggle button, and the conditional summary paragraph:

```jsx title="src/components/StoryCard.jsx" startLine="20"
}
```

Now **Slot 0** for `likes` and **Slot 1** for `showSummary` run in the exact same order on every render. When the user clicks the toggle button, `setShowSummary` flips **Slot 1** from `false` to true while **Slot 0** stays at ten. The button label switches to `Hide summary`, and the summary paragraph appears right below the buttons:

> [!PRINCIPLE]
> **Principle 3: Top-Level Hooks: Call Every `useState` Unconditionally at the Top of the Component**
>
> *Give a component as many `useState` variables as it needs, and always call every Hook unconditionally at the very top level of the component function.*
>
> React cannot see the variable names you unpack on the left side of `useState`. Instead, React keeps an internal array of state slots for the component and matches each `useState` call by its top-to-bottom call order during render. Never place a `useState` call inside an `if` block, a loop, or below an early return. Changing how many Hooks run between renders shifts the slot order and crashes React.
>
> **DO THIS:**
> ```jsx
> export default function StoryCard({ title, summary }) {
>   const [likes, setLikes] = ~useState(loadSavedLikes)~;     // 1. Slot 0: always runs 1st
>   const [showSummary, setShowSummary] = ~useState(false)~; // 2. Slot 1: always runs 2nd

> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function StoryCard({ title, summary }) {

## 4. Principle 4: State Is Isolated and Private to Each Rendered Component Instance

### Why two `<StoryCard />` tags on the same page do NOT share the same state

Now let us place a **second** `<StoryCard />` tag inside `App.jsx` right below the first card:

```jsx title="Rendering two <StoryCard /> tags inside App"
export default function App() {
  return (
    <main>
      <h1>Top Stories</h1>
      ~<StoryCard~ // 1. First rendered StoryCard instance on screen
        title="New Park Opens Today"
        summary="The park on Main Street opens at noon."
      />
      ~<StoryCard~ // 2. Second rendered StoryCard instance on screen
        title="Library Extends Hours"
        summary="The central library stays open until 9 PM."
      />
    </main>
  );
}
```

**Both `<StoryCard />` tags on the page call the exact same `StoryCard` function. Because of that, it is easy to think both cards share the same `likes` and `showSummary` variables, but they do NOT share state at all!**

Think of `StoryCard` in the file as a cookie cutter, and the two `<StoryCard />` tags on the page as two separate cookies on a tray:
- React does **not** attach state to the `StoryCard` function definition in the file.
- Instead, React attaches a separate two-slot state clipboard to **each rendered component instance** at its spot on the screen.
- Putting frosting on the first cookie never frosts the second cookie. Clicking a button on the first `<StoryCard />` updates **only** the first card's state clipboard, leaving the second `<StoryCard />` completely untouched!

Unlike `props`, which `App` passes down into each card, state is completely **private** to the card that owns it. The parent component cannot read or change either card's `likes` or `showSummary` state.

```tree caption="Each rendered <StoryCard /> tag on screen gets its own isolated, private state slots in React memory."
Two `<StoryCard />` tags rendered inside `App`
- +First `<StoryCard />` [`"New Park Opens Today"`] | Owns its own **`[Slot 0, Slot 1]`** state array in memory | Clicking `Like` here updates **only this first card**
- +Second `<StoryCard />` [`"Library Extends Hours"`] | Owns a **completely separate `[Slot 0, Slot 1]`** state array | Stays untouched at **`Likes: 10`** and **`Show summary`**
```

### Mistake: Putting a variable outside the component function at the top of the file

When developers first see a local `let` variable reset on every render, they sometimes try a shortcut. They move that variable **outside** the component function to the very top of the card file:

```jsx title="src/components/StoryCard.jsx" startLine="1"
~let sharedLikes = 10;~ // **WRONG:** one module-level variable is shared across EVERY <StoryCard /> on the page!

export default function StoryCard({ title }) {
  return <article><h3>{title}</h3><p>Likes: {sharedLikes}</p></article>;
}
```

Why is a variable at the top of the file a trap when you render two `<StoryCard />` tags? Because `StoryCard.jsx` is loaded once as a module, there is only **one** `sharedLikes` variable in the entire file! Instead of each card having its own separate like count, both `<StoryCard />` tags read and overwrite that single shared variable.

When you keep `useState` **inside** `StoryCard`, you never have to duplicate the file to make a second card. Each `<StoryCard />` tag you place on the screen automatically gets its own isolated memory!

Look closely at `App.jsx` and `StoryCard.jsx`. Nowhere did we pass an `id` into `useState` to tell React which state belongs to the park story and which belongs to the library story! How does React keep the two cards separate?

React tracks each component by its **position in the rendered component tree** inside `<main>`:
1. When `App` renders the main container, React sees two `<StoryCard />` children at position 1 and position 2.

| :--- | :--- | :--- |
| **Where changing data lives** | Store a local `let` variable inside the function and reassign it with `=`, which never re-renders and resets on the next call | Unpack `[likes, setLikes]` from `useState` and call `setLikes` so React remembers the value and re-renders |

## For the Interview

> **The Interview Question:** Why do ordinary variables forget their values between renders, and how does useState remember?

### How to Answer Clearly in 30 Seconds

"Ordinary local variables declared inside a component function fail to update the UI across renders for two reasons. First, reassigning a local variable like `likes` with `=` happens in silence and never notifies React that data changed, so React never triggers a re-render. Second, whenever React does re-render the component, it calls the component function again from the very top and re-initializes every local variable from scratch.

`useState` solves both problems by storing the state value inside React's external memory outside the component function. Calling `useState` returns a two-element array that we unpack with JavaScript array destructuring:
1. **The current state value**, such as `likes`, which React reads from its stored memory slot and hands back on every render.
2. **The state setter function**, such as `setLikes`, which saves the next value into React's memory and requests a re-render of the component.

Three rules govern how `useState` works in practice:
- **Initial value and initializer function**: React uses the initial value only on the first render. When computing that starting value calls a helper like `loadSavedLikes`, we pass the function reference without parentheses to `useState`. React then calls it only once on mount rather than on every re-render.
- **Unconditional top-level call order**: React matches multiple `useState` calls to their stored slots by their sequential call index `0, 1, 2` during render rather than by variable names. Because of that, Hooks must always run at the top level of the component, never inside `if` blocks, loops, or after early returns.
- **Isolated per-instance state**: State is attached to each rendered component instance at its position on the screen. Rendering `<StoryCard />` twice gives each card its own independent, private state."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"If `likes` changes across renders, why do we declare `[likes, setLikes]` with `const` instead of `let`, and with square brackets instead of curly braces?"**
   We use `const` because we never reassign `likes` with `=` during a render. On each new render, React calls our component function again from scratch and creates a fresh `const likes` holding the latest value from memory. We use square brackets `[likes, setLikes]` because `useState` returns a two-item array unpacked by position `0` and `1`. By contrast, `props` is an object unpacked by property name with curly braces `{ title, summary }`.
2. **"What is the difference between calling `loadSavedLikes` with parentheses inside `useState` and passing `loadSavedLikes` without parentheses?"**
   In JavaScript, arguments inside parentheses are evaluated before the function is entered. If you call `loadSavedLikes` with parentheses inside `useState`, JavaScript runs `loadSavedLikes` on **every single render** and passes its return value to `useState`. React then throws that returned value away on every render after the first. If you pass `loadSavedLikes` **without parentheses**, you pass an initializer function reference to React, and React calls `loadSavedLikes` **only once** during the initial render.
3. **"Since you do not pass a variable name into `useState`, how does React know which state value belongs to `likes` and which belongs to `showSummary`?"**
   Inside React, each component instance holds an internal array of state slots and a call index counter that resets to `0` at the start of every render. The first `useState` call always reads slot `0`, the second `useState` call reads slot `1`, and so on. If you put a `useState` call inside an `if` block, a loop, or after an early `return`, the call order shifts between renders. React immediately throws a Hook order error such as `Rendered fewer hooks than expected`.
