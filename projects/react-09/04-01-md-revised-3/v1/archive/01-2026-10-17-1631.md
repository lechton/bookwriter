> INTERVIEW QUESTION | ❱ CORE | What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

## Example: updating reader details across a site header

The example for this whole lecture is the header of a news site, The National Times. At the top of every page, the header greets the signed-in reader by name ("Welcome back, Mary"), shows her account line ("Signed in as Mary"), and provides a search box. Here is the header as the signed-in reader sees it in the browser:

```page caption="The header of the news site. Outlined in green: the two places that show the signed-in reader's name."
heading: The National Times
card: title=Welcome back, Mary | text=Signed in as Mary | input=Search | good=title,text
```

Look closely at the header: the reader's name appears in two separate places. The greeting at the top shows "Welcome back, Mary", followed by the account line "Signed in as Mary". Below them sits a search box where the reader can type a query. When Mary updates her profile and adds her family name to become Mary Brooks, both places on screen must show the new name, and whatever she typed into the search box must stay intact. Each part of the header follows a rule about the data:

| on the page | the rule behind it |
| --- | --- |
| "Welcome back, Mary" in the greeting | IF a reader is signed in, THEN greet the reader by name |
| "Signed in as Mary" in the account line | IF a reader is signed in, THEN show the account line with that name |
| a search box with placeholder "Search" | always available for reader queries; IF reader data updates, THEN preserve typed query and active focus intact |

In plain JavaScript, updating the page means finding each element by its identifier and setting its text by hand. If a reader changes her name, a script that updates the greeting can easily forget the account line, leaving the old name on screen. And if a script rebuilds the header with `innerHTML` to refresh the text, the browser destroys the search box, wiping whatever the user typed. React replaces manual DOM commands with a different model: we describe what the page should look like for the current data, and React handles the DOM updates. Describing what to show instead of commanding how to change it is called **declarative programming**, and it is the foundation of React: how does React build and update the page from data, and why do you never change elements by hand?

## The components behind the page

In React, the page is built from modular pieces called **components**. A component is a JavaScript function whose name starts with a capital letter and which returns the markup for one piece of the page. The application is organized in a small component hierarchy:

```hierarchy layout=stack caption="The structure of the lesson's project, and who renders the header."
App | holds: the page
  SiteHeader | holds: `userName = 'Mary'` | here: describes greeting from data
notes:
index.html provides the empty root container `<div id="root"></div>`.
main.jsx is the entry JavaScript file that tells React to render the application into that container.
App is the root component that renders the header at the top of the page.
SiteHeader is the component we write: a function that holds userName and returns the header's markup.
We want: the header displayed on screen, built from component markup rather than written as static HTML nodes.
```

The header component lives in `src/SiteHeader.jsx`. It keeps the name in a local variable, `userName`, and returns the markup for the header:

```jsx title="SiteHeader.jsx" good="5"
export default function SiteHeader() {
  const userName = 'Mary';
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as Mary</span>
      <input placeholder="Search" />
    </header>
  );
}
```

The markup after `return` is **JSX**: it looks like HTML, but it is JavaScript. Inside JSX, **curly braces** `{ }` mark a place where a JavaScript value goes, so `{userName}` places "Mary" into the greeting. In this first draft, the corner line still carries the fixed text `"Signed in as Mary"` pasted from the old HTML. When Mary is the user, both places display "Mary". Section 2 shows what happens when the name changes, and why the corner must read the variable too. `export default` lets another file use this function. Our code never calls `SiteHeader`; React calls it, and React builds the DOM nodes from what the component returns.

## Two ways to update a page when data changes

The browser does not draw the HTML file directly. It reads the file and builds a tree of objects in memory called the **DOM** (Document Object Model), where each object is a **DOM node**. To change what the screen shows, something must change the DOM. When data changes, there are two opposing ways to update the DOM:

```tree caption="Two ways to update the DOM when data changes: command each step, or describe the result."
Update the DOM when data changes
- Imperative: command each step | plain JavaScript: find each element and set its text
- Declarative: describe the result | React: describe what the page shows, and React updates the DOM
```

> [!FACT] In plain JavaScript, document.getElementById finds a DOM node by its id attribute, and textContent replaces the text inside that node. In this lesson, saving an edited file in the development server triggers React to re-render the component with the new values.

When Mary updates her profile name to Mary Brooks, compare how plain JavaScript and React handle the greeting:

::: row caption="When Mary becomes Mary Brooks, how does the greeting update?"
::: col title="Imperative (plain JavaScript)" tone=plain
```js
const greeting = document.getElementById('greeting');
greeting.textContent = 'Welcome back, Mary Brooks';
```
Our code finds the element by its `id` and sets its text. The corner element is not named, so it stays on the old name, displaying 'Signed in as Mary'.
:::
::: col title="Declarative (React)" tone=good
```jsx
<p>Welcome back, {userName}</p>
```
In React, when userName changes to 'Mary Brooks', React re-renders the component and updates the greeting to 'Welcome back, Mary Brooks' automatically. Section 2 will show how to share userName with the account line.
:::
:::

Why does the difference matter? In plain JavaScript (**imperative programming**), our code gives the browser every step: find node, change text. In a header with ten places showing the user's name, our code needs ten manual commands. Miss one command, and the page shows stale data. And if code tries to rebuild the container with `innerHTML`, the browser destroys existing elements, wiping typed text and losing focus. In React (**declarative programming**), we declare what each element shows for the current data, and React calculates the minimal DOM changes needed.

## The path of one value: described, shared, changed

Everything in this lecture follows the path of one piece of data, `userName`, from its initial description to an update on screen:

```tree caption="The path of one value: from its first description to a change on screen."
The path of one value on the page
- 1. Describe what each element shows | declarative programming: no finding elements by hand
- 2. Read one variable in every place | a single source of truth: no typed copies of data
- 3. Compare descriptions on every change | the virtual DOM: update only the new text
```

These three principles follow the three moments in the life of `userName`. First, we describe what the header shows from `userName` rather than finding elements by hand. Second, we share that single variable across every place that displays the name so no place can drift. Third, when `userName` changes, React compares the new description with the previous one, updating only the text that changed while preserving existing input elements. We take them in this order because each step builds directly on the one before it.

## 1. Describe what each element shows: declarative programming

```tree size=mini here="1. Describe what each element shows"
The path of one value on the page
- 1. Describe what each element shows
- 2. Read one variable in every place
- 3. Compare descriptions on every change
```

> [!FACT] The DOM (Document Object Model) is the tree of objects the browser builds in memory for every HTML tag. The principle box below uses general stand-in names, Header and name, to show the rule for any component and variable. In our news site, the component is SiteHeader and the variable is userName.

> [!PRINCIPLE]
> **Principle 1: Describe what each element shows: declarative programming**
>
> We control the page by describing what each element shows for the current data.
>
> React calls the component and builds the DOM from what it returns.
>
> Our code has no line that finds or changes an element, so there is no element to forget.
>
> *We should do this:*
>
> ```jsx
> function Header() {
>   const name = 'John';
>   return <p>Hello, {name}</p>;
> }
> ```
>
> *We should not do this:*
>
> ```js
> function updateHeader(name) {
>   const el = document.getElementById('hello');
>   el.textContent = 'Hello, ' + name; // **PROBLEMATIC:** finds and sets the element by hand; if other elements display the name, they keep old data when the name updates
> }
> ```

The first choice decides who controls the DOM: our code, or React?

```hierarchy layout=stack caption="Describing the header from data in SiteHeader."
App | holds: the page
  SiteHeader | holds: `userName = 'Mary'` | here: describes greeting from data
notes:
App renders SiteHeader into the page container.
SiteHeader describes what the greeting shows from its userName variable, and returns the header markup.
We want: the greeting displayed from data, built by React from the component description with zero manual DOM calls.
```

In plain JavaScript, we write an update function that queries the element by its `id` and sets its text:

```js title="Plain JavaScript: updateHeaderUser" bad="3"
// In a plain HTML/JS page: <p id="greeting">Welcome back, Mary</p> and <span id="account">Signed in as Mary</span>
function updateHeaderUser(name) {
  const greeting = document.getElementById('greeting');
  greeting.textContent = 'Welcome back, ' + name;
}
updateHeaderUser('Mary Brooks');
```

Executed in the browser, this update function produces an inconsistent page:

```page size=mini caption="In plain JavaScript, updateHeaderUser('Mary Brooks') updates the greeting and forgets the corner."
heading: The National Times
card: title=Welcome back, Mary Brooks | text=Signed in as Mary | input=Search | bad=text
```

Look at the corner: `updateHeaderUser` named only `greeting`, so the corner still shows "Signed in as Mary". Every new place on the page that shows the name needs one more line in that function. One forgotten line leaves old data on screen.

> [!FACT] In the browser's Elements panel, you inspect the live DOM tree as it exists in memory right now. The live DOM can differ from the static index.html file whenever JavaScript creates or modifies nodes.

In React, we write no update function. We write `SiteHeader`, which returns JSX describing what each element shows for `userName`. React builds the elements from that description:

```jsx title="SiteHeader.jsx" good="5"
export default function SiteHeader() {
  const userName = 'Mary';
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as Mary</span>
      <input placeholder="Search" />
    </header>
  );
}
```

Compare the served `index.html` file with the browser's Elements panel:

```dom title="Elements panel: nodes built by React"
<div id="root">
*  <header>
*    <p>Welcome back, Mary</p>
*    <span>Signed in as Mary</span>
*    <input placeholder="Search">
*  </header>
</div>
```

In `index.html`, the file holds only `<div id="root"></div>`. In the live Elements panel, React built every node inside `<header>` from the JSX description. No line in our code called `getElementById` or `textContent`: React builds every element directly from the JSX description on render, so there are no manual DOM update commands to write or forget:

```chain caption="Top: imperative updates leave stale data if a command is missed. Bottom: React builds consistent DOM nodes directly from the component description."
!updateHeaderUser('Mary Brooks') -> sets greeting only -> forgets account node: page shows "Mary Brooks" beside "Mary"
+Initial render: SiteHeader returns JSX for userName = 'Mary' -> React builds all DOM nodes from description -> page shows consistent data ("Mary" in both places) with zero DOM calls
```

This settles how we control what appears on screen:

```tree dir=right
Who changes the DOM?
- !Imperative: find each element and set its text | our code commands every step; a forgotten element keeps old data
- +Declarative: describe what elements show from data | React builds and updates the DOM; no manual DOM commands to write or forget
```

## 2. Read one variable in every place: a single source of truth

```tree size=mini here="2. Read one variable in every place"
The path of one value on the page
- 1. Describe what each element shows
- 2. Read one variable in every place
- 3. Compare descriptions on every change
```

> [!FACT] In JSX, curly braces { } evaluate a JavaScript variable or expression and insert its value into markup. The principle box below uses Header and name to show the rule for any component and variable.

> [!PRINCIPLE]
> **Principle 2: Single source of truth: describing many places from one value**
>
> When one value appears in many places on the page, we describe every place from one variable.
>
> Inside JSX, curly braces `{ }` place the value of that variable into the markup.
>
> We never type a copy of the value into the markup as fixed text. Notice: a typed copy keeps the old value when the variable changes.
>
> *We should do this:*
>
> ```jsx
> function Header() {
>   const name = 'John Hall';
>   return (
>     <header>
>       <p>Hello, {name}</p>
>       <span>Signed in as {name}</span>
>     </header>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Header() {
>   const name = 'John Hall';
>   return (
>     <header>
>       <p>Hello, {name}</p>
>       <span>Signed in as John</span> {/* **PROBLEMATIC:** fixed text copy keeps old name when variable changes */}
>     </header>
>   );
> }
> ```

Section 1 showed that `SiteHeader` describes its elements from data instead of querying them by hand. But what happens when the same value appears in multiple places across that description?

```hierarchy layout=stack caption="Sharing one variable across multiple places in SiteHeader."
App | holds: the page
  SiteHeader | holds: `userName = 'Mary Brooks'` | here: greeting reads userName; corner still uses fixed text 'Mary'
notes:
userName holds the reader's name at the top of SiteHeader.
The greeting reads userName with `{userName}`, but the corner was pasted with fixed text 'Mary'.
When userName is updated to 'Mary Brooks', the corner fails to update.
We want: both the greeting and the corner described from userName, so changing userName updates both places.
```

Now Mary updates her profile and becomes Mary Brooks. Because we have not introduced interactive user forms yet, we simulate this data update by editing line 2 of `SiteHeader.jsx`, changing `'Mary'` to `'Mary Brooks'`, and saving. The development server detects the save and prompts React to re-render the component with the new value. The greeting reads `{userName}`, but the corner still has the text pasted from the old HTML page:

```jsx title="SiteHeader.jsx" bad="6"
export default function SiteHeader() {
  const userName = 'Mary Brooks'; // Changed from 'Mary' and saved
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as Mary</span>
      <input placeholder="Search" />
    </header>
  );
}
```

With the development server running, saving the file with `'Mary Brooks'` updates the page:

```page size=mini caption="With userName set to 'Mary Brooks', the greeting updates, but the corner still shows 'Mary'."
heading: The National Times
card: title=Welcome back, Mary Brooks | text=Signed in as Mary | input=Search | bad=text
```

Look at the corner: `userName` was updated to `'Mary Brooks'`, but the corner holds the fixed text `"Signed in as Mary"`, so it keeps the old name.

> [!FACT] In React, a component renders again when its data changes. In this lesson, saving SiteHeader.jsx in the dev server causes React to re-render SiteHeader and recalculate its JSX output.

React builds DOM nodes exactly as described in JSX:

| place | how it is described | what React builds | on screen after save |
| --- | --- | --- | --- |
| `<p>` (greeting) | `{userName}` | reads variable `'Mary Brooks'` | "Welcome back, Mary Brooks" |
| `<span>` (corner) | fixed text `"Signed in as Mary"` | uses string literal `"Signed in as Mary"` | "Signed in as Mary" |

React did nothing wrong: the JSX description asked for two different names. The fix is one line: line 6 reads the same variable as the greeting:

```jsx title="SiteHeader.jsx" good="6" startLine="3"
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as {userName}</span>
      <input placeholder="Search" />
    </header>
  );
```

Now both places read from `userName`. Keeping data in one variable that feeds every place on screen is called a **single source of truth**. With line 6 reading `{userName}`, both places now show 'Mary Brooks', and whenever `userName` changes in the future, both places update together. If you add an account menu or profile button later, each new spot adds `{userName}` and requires zero manual update code:

```tree dir=right
One value in many places?
- !Type a copy into markup as fixed text | the copy stays unchanged when the variable updates
- +Read one variable in curly braces { } | all places update together whenever the variable updates
```

## 3. Compare descriptions on every change: the virtual DOM

```tree size=mini here="3. Compare descriptions on every change"
The path of one value on the page
- 1. Describe what each element shows
- 2. Read one variable in every place
- 3. Compare descriptions on every change
```

> [!FACT] When an input element has focus, it receives keyboard typing and displays a blinking cursor. The principle box below uses Header and name to show the minimal component needed to illustrate input preservation.

> [!PRINCIPLE]
> **Principle 3: The virtual DOM: describing the page again when the value changes**
>
> When data changes, React calls the component again to get a new description.
>
> React compares the new description with the last one, element by element.
>
> It changes only the text and attributes that differ, leaving unchanged DOM nodes in place. Whatever the user typed into an input stays where it was.
>
> *We should do this:*
>
> ```jsx
> function Header() {
>   const name = 'Mary Brooks';
>   return (
>     <header>
>       <p>Hello, {name}</p>
>       <input placeholder="Search" />
>     </header>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```js
> function updateHeader(name) {
>   const header = document.getElementById('header');
>   header.innerHTML = '<p>Hello, ' + name + '</p><input placeholder="Search">'; // **PROBLEMATIC:** innerHTML rebuilds new nodes; typed text and focus are lost
> }
> ```

Section 2 ensured that every place reads the same `userName` variable. But when `userName` changes and React calls `SiteHeader` again, does it throw away the entire header DOM and recreate it from scratch?

```hierarchy layout=stack caption="Comparing descriptions when userName changes in SiteHeader."
App | holds: the page
  SiteHeader | holds: `userName = 'Mary Brooks'` | here: returns markup with search input
notes:
The user has typed "elections" into the search box, giving it active focus.
When userName changes to 'Mary Brooks', React calls SiteHeader again to receive a new description.
React compares the new description with the previous one, updating only the two changed text nodes.
We want: both names update to "Mary Brooks" while the search box keeps "elections" and its cursor.
```

In plain JavaScript, developers frequently update multiple elements by rebuilding the container with `innerHTML`:

```js title="Plain JavaScript: rebuilding the header with innerHTML" bad="3-6"
// In a plain HTML/JS page: <header id="header"><p id="greeting">...</p>...</header>
const name = 'Mary Brooks';
const header = document.getElementById('header'); // Finds <header id="header"> container
header.innerHTML =
  '<p>Welcome back, ' + name + '</p>' +
  '<span>Signed in as ' + name + '</span>' +
  '<input placeholder="Search">';
```

Compare what happens when Mary updates her name to Mary Brooks while "elections" is typed in the search box:

::: row caption="With 'elections' typed into the search box, userName changes from 'Mary' to 'Mary Brooks'. Both versions show the new name; only the search box differs."
::: col title="Plain JavaScript `innerHTML`" tone=bad
```page size=mini
card: title=Welcome back, Mary Brooks | text=Signed in as Mary Brooks | input=Search | bad=input
```
With `innerHTML`, the browser destroys all children of `<header>`. A brand new empty `<input>` is built; "elections" is gone, and focus is lost.
:::
::: col title="React (Virtual DOM)" tone=good
```page size=mini
card: title=Welcome back, Mary Brooks | text=Signed in as Mary Brooks | typed=elections | good=typed
```
React compares descriptions: it changes only the two text nodes. The `<input>` DOM node is preserved, keeping "elections" and active cursor focus.
:::
:::

> [!FACT] In React, the tree of description objects returned by components is commonly called the virtual DOM. React diffs (compares for differences) this description against the previous render to determine the minimal necessary operations on the real DOM.

When React re-runs `SiteHeader` with `'Mary Brooks'`, it compares the new description with the previous description, element by element:

| element | last description | new description | in the real DOM |
| --- | --- | --- | --- |
| `<p>` (greeting) | "Welcome back, Mary" | "Welcome back, Mary Brooks" | text node updated |
| `<span>` (corner) | "Signed in as Mary" | "Signed in as Mary Brooks" | text node updated |
| `<input>` (search box) | `<input placeholder="Search" />` | `<input placeholder="Search" />` | same DOM node kept in place |

The `<input>` node in the DOM was never removed or replaced. Because it is the exact same DOM node, whatever the user typed into it ("elections") and the blinking cursor remain intact:

```tree dir=right
On data change?
- !Rebuild container with innerHTML on data change | replaces all child DOM nodes: active focus and typed input text are wiped
- +Compare descriptions with the virtual DOM on data change | updates only changed text nodes: existing input nodes, typed text, and focus are preserved
```

## Putting the three together

The three principles in one header component, as the three sections built it: declarative programming describing the elements from data; a single source of truth reading `userName` in curly braces across both the greeting and the corner; and the virtual DOM comparing descriptions on every change so that the search box keeps what the user typed:

**DO THIS:**

```jsx right
export default function SiteHeader() {
  const userName = 'Mary Brooks';
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as {userName}</span>
      <input placeholder="Search" />
    </header>
  );
}
```

The same header with the three mistakes from this lesson, marked in red: in React, copying the user's name as fixed text into the corner leaves it on "Mary" when `userName` becomes "Mary Brooks" (line 6); in plain JavaScript, manual DOM commands update only the greeting while forgetting the corner, and rebuilding with `innerHTML` wipes typed search text:

**DO NOT DO THIS:**

```jsx wrong bad="6"

      <p>Welcome back, {userName}</p>
```

## For the interview

- **What is React, and how does its declarative model differ from plain JavaScript DOM scripting?** React is a JavaScript library for building user interfaces from components. In plain JavaScript (imperative programming), our code finds each DOM element and changes it step by step; any element forgotten by the script keeps stale data. In React (declarative programming), a component function describes what the UI should look like for the current data, and React makes the DOM match that description.
- **What is a single source of truth?** A single source of truth means storing a piece of data in one variable and reading it with JSX curly braces in every place that displays it. If a value is typed as fixed text into markup, it creates an independent copy that does not update when the data changes.
- **What is the virtual DOM, and does React rebuild the entire DOM on every render?** The virtual DOM is the tree of lightweight JavaScript description objects that components return. When data changes, React calls the component again, compares the new description tree with the previous one, and applies the minimal necessary operations to the real DOM. It does not rebuild the entire DOM: unchanged nodes like `<input>` stay in place, preserving typed text and active focus.
- **Does React make DOM updates faster than plain JavaScript?** No. React calls the exact same DOM methods (`appendChild`, `textContent`) that a browser script calls. A handwritten script targeting a single text node executes fewer operations than React's diffing algorithm. React's benefit is correctness and scalability, not raw speed: it frees developers from writing, synchronizing, or forgetting DOM update commands.
- **Why can you not call document.getElementById inside a React component?** During rendering, React executes the component function to calculate its description before any elements are inserted or updated in the browser's DOM. On initial render, `document.getElementById` returns `null`; on re-renders, querying or modifying DOM nodes directly bypasses React's diffing engine and desynchronizes the UI. Reaching a real DOM element for focus or measurement is handled after render through React-managed references known as refs (covered in Lecture 30).
