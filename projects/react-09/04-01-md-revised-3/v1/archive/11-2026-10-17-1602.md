# Lecture 11: Rendering Lists and Keys
> INTERVIEW QUESTION | ❱ CORE | How do you render a list from an array, and why does React demand a key on every item?

::: pagebreak

## Example: articles grouped by topic on a news site

The example for this whole lecture is the home page of a small news site. It groups its articles by topic: City, Weather, Food, and Sport. Each article appears as a card with its title, the author's name, and a box where a reader can write a comment. Here is the page, after a reader has typed a comment under the rain article:

```page caption="The home page of the news site. Outlined in green: the comment a reader typed under the rain article, and the message of the Sport section, which has no article."
heading: Latest Articles
section: City
card: title=New Park Opens Today | author=Mary Jones | input
section: Weather
card: title=Rain Expected This Weekend | author=Oliver Brooks | typed=Great news! | good=typed
section: Food
card: title=Five Soups for Cold Days | author=Samantha Robinson | input
section: Sport
line: None yet. | good
```

Look closely at the page. Every card has the same three parts, and only its data differs. Each section shows only the articles of its own topic. The Sport section has no article, so it shows a message instead. Each thing you see follows a rule about the data:

| on the page | the rule behind it |
| --- | --- |
| three cards with the same three parts | one card for each article in the data |
| City shows only the park card; Weather only the rain card | each section shows only the articles of its own topic |
| Sport says "None yet." | a section with no articles shows a message |
| "Great news!" under the rain card | a typed comment stays under its own article, even when a new article is added at the top (section 3 shows what makes this work) |

Written by hand, each card would be one tag in the code: thirty articles would mean thirty tags, and every new article a change to a component. Following these rules instead, the page is drawn from the data. Showing one element for each item of the data is called **rendering a list**, and it is the topic of this lecture: how does one array of articles become one card per article, and why does React ask for a key on every card?

## The components behind the page

Three components draw this page, and the articles live in a file of their own. The data flows down, from the file to each topic section, and from each section to its cards:

```hierarchy caption="The components of the news site, and what each one holds or receives."
App | holds: four topic sections
  ArticleList | gets: one `topic`, such as "City" | holds: the `articles`, imported | here: chooses which cards to draw
    ArticleCard | gets: one `article`
notes:
The articles live in `src/articles.js` as one array of objects. That file holds data, not a component.
`App` is the page: its heading, Latest Articles, and one `ArticleList` per topic: `<ArticleList topic="City" />`, and so on.
Each `ArticleList` imports the array, keeps the articles of its own topic, and draws one `ArticleCard` for each.
So the choice of how many cards to draw, and which ones, is made in `ArticleList`, from the array. Section 1 starts with a single `ArticleList` that shows every article; section 2 splits it by topic.
```

Each article is an object with an `id`, a number that belongs to that article and to no other, then its title, its author, and its topic:

```js title="articles.js"
export const articles = [
  { id: 1, title: 'New Park Opens Today', author: 'Mary Jones', topic: 'City' },
  { id: 2, title: 'Rain Expected This Weekend', author: 'Oliver Brooks', topic: 'Weather' },
  { id: 3, title: 'Five Soups for Cold Days', author: 'Samantha Robinson', topic: 'Food' },
];
```

Each card is one `ArticleCard`, which draws the article it receives, with a comment box at the bottom:

```jsx title="ArticleCard.jsx" good="6"
export default function ArticleCard({ article }) {
  return (
    <article className="card">
      <h2>{article.title}</h2>
      <p className="author">By {article.author}</p>
      <input placeholder="Write a comment" />
    </article>
  );
}
```

`ArticleList` and `ArticleCard` live in `src/components/`, so `ArticleList` reads the array with `import { articles } from '../articles.js';`, one folder up. An array counts its items from 0, so `articles[0]` is the park article, `articles[1]` the rain article, and `articles[2]` the soups article.

## Two ways to render one card per article

There are two ways to turn the articles into cards:

```tree caption="Two ways to get one card per article: write each card by hand, or draw them from the data."
Render one card per article
- Fixed: written by hand | one tag per article, typed into the JSX
- Dynamic: from an **array** of data | one tag, repeated for every article in the array
```

::: row caption="The same three cards on the page, written two ways inside ArticleList's return."
::: col title="Fixed: written by hand" tone=plain
```jsx
<main>
  <ArticleCard article={articles[0]} />
  <ArticleCard article={articles[1]} />
  <ArticleCard article={articles[2]} />
</main>
```
With three articles, three tags. A fourth article needs a fourth tag in the component.
:::
::: col title="Dynamic: from the array" tone=good
```jsx
<main>
  {articles.map(article => (
    <ArticleCard article={article} />
  ))}
</main>
```
With any number of articles, one tag. Section 1 shows how this line works.
:::
:::

Why does the difference matter? By hand, the component has to know how many articles exist and in what order, so every new article is a change to the code. From the data, a new article is one more object in `articles.js`, with no change to any component, and the same component can show whichever topic it is given, as section 2 does. So by hand fits only a few items that never change, such as two links in a footer; every list that comes from data is drawn from the data.

> [!FACT] Each JSX tag, such as `<ArticleCard />`, makes an **element**: React's description of what to show, not yet the box on the page. From each element, React builds the real card on the page.

That is rendering a list: an array of data becomes an array of elements, and later each element gets its own key.

## Rendering a list in four steps

Rendering a list takes four steps, in two pairs. The first pair creates the cards. The second keeps the cards right when the list is updated, so each card stays with its own article:

```tree caption="The four steps of rendering a list: first create the cards, then update them correctly when the list changes."
Render a list from an array of articles
- Create the cards | from the array to the page
  - Cards for every article | `map()`
  - Cards for only some articles | `filter()`, then `map()`
- Update the cards when the list changes | each card stays with its article
  - Key from the article's id | not from its position
  - Key on the tag `map()` returns | not inside the card
```

We take the steps in this order because each builds on the one before it; section 2 shows why, in the code, `filter()` runs before `map()`.

## 1. Cards for every article: map()

```tree size=mini here="Cards for every article"
Render a list from an array of articles
- Create the cards
  - Cards for every article
  - Cards for only some articles
- Update the cards when the list changes
  - Key from the article's id
  - Key on the tag `map()` returns
```

> [!FACT] An **arrow function** is a short way to write a function: the parameter, then `=>`, then what it gives back. `article => article.title` takes an article and gives back its title.

> [!FACT] **`forEach()`** calls a function once for each item of an array and gives back `undefined`. **`map()`** calls a function once for each item and collects what the function gives back into a new array, with one entry per item. It passes each item to the function as its parameter: in `article => ...`, the name `article`, which we choose, holds the park article on the first call, the rain article on the second, and so on.

> [!FACT] When a curly brace follows `=>`, the function has a **block body**: it gives back only what a `return` inside it names, and without `return` it gives back `undefined`. With parentheses, or nothing, after `=>`, the function gives back that expression by itself.

> [!FACT] In the box below, `items` stands for any array of data, `<Item />` for the component that draws one item, and the notes after `//` or inside `{/* */}` are labels for you, not code to copy. Each box shows a whole small component, so you can see where every line sits.

> [!PRINCIPLE]
> **Principle 1: Cards for every item: `map()`**
>
> To show one element per item, we call `map()` on the array inside the JSX.
>
> The arrow function can give back the element directly, inside parentheses `( )`. Or it can use curly braces `{ }`, and then it needs an explicit `return`. Notice: a missing `return` is easy to overlook.
>
> *We should do this:*
>
> ```jsx
> function ItemList({ items }) {
>   return (
>     <ul>
>       {items.map(item => ( // ( ): the element is given back
>         <Item item={item} />
>       ))}
>     </ul>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function ItemList({ items }) {
>   return (
>     <ul>
>       {items.map(item => { // **PROBLEMATIC:** { } with no return
>         <Item item={item} />; // gives back nothing: no element
>       })}
>     </ul>
>   );
> }
> ```

The first step turns every item of the array into one card. To start, a single `ArticleList` shows all three articles, with no topics yet:

```hierarchy
ArticleList | holds: `articles`, three objects | here: draws one card per article
  ArticleCard | gets: one `article`
notes:
`ArticleList` has the three articles in one array.
Inside its JSX, it must give back one `ArticleCard` for each article.
We want: three cards from one tag, and a fourth card, with no change to the code, when a fourth article is added to `articles.js`.
```

From plain JavaScript, the first idea is a loop that writes one card per article. A `for` loop cannot go inside JSX braces: it is a statement, and braces take only an expression, code that gives a value. So the loop becomes an array method that takes a function and calls it once for each article, `forEach()` or `map()`, as the facts above described.

With `map()` and no `return`, the one thing that decides whether cards appear is the bracket after the arrow. Here are the two versions, inside `ArticleList`'s `<main>`, with the three articles in the array:

::: row caption="With the three articles in the array: the same map(), once with curly braces after the arrow, once with parentheses. Compare the two pages."
::: col title="Curly braces `{ }`, no return" tone=bad
```jsx
{articles.map(article => {
  <ArticleCard article={article} />;
})}
```
```page size=mini
heading: Latest Articles
empty: no cards
quiet: Console: no messages
```
Each call gives back `undefined`: no cards, and no message to say why.
:::
::: col title="Parentheses `( )`" tone=good
```jsx
{articles.map(article => (
  <ArticleCard article={article} />
))}
```
```page size=mini
heading: Latest Articles
card: title=New Park Opens Today | author=Mary Jones | input
card: title=Rain Expected This Weekend | author=Oliver Brooks | input
card: title=Five Soups for Cold Days | author=Samantha Robinson | input
warn: Each child in a list should have a unique "key" prop.
```
Three cards, one per article. The console asks for a key; section 3 explains why.
:::
:::

`forEach()` fails too, for another reason: it gives back `undefined` whatever its function does. What each version gives back, and so what the page shows:

```chain caption="What each version gives back for the three articles, and so what the page shows."
!`articles.forEach(...)` -> `undefined` -> nothing to place: no cards
!`articles.map(article => { <ArticleCard />; })` -> `[undefined, undefined, undefined]` -> no cards
+`articles.map(article => <ArticleCard />)` -> `[<ArticleCard>, <ArticleCard>, <ArticleCard>]` -> three cards
```

React shows an array of elements in order, one after the other. To see that array, store it in a `const` above the `return`, as `const cards = articles.map(article => <ArticleCard article={article} />);`, and log it with `console.log(cards)`. With the three articles, the Console shows three elements:

```console title="Console: console.log(cards), with three articles, the first entry opened"
log: (3) [{…}, {…}, {…}]
log: 0: {type: ƒ ArticleCard, key: null, props: {article: {…}}, …}
```

Each of the three objects has the type `ArticleCard` and carries one article in its props. Its `key` is `null` for now, which is what the console's warning is about; section 3 deals with it. Here is the whole of `ArticleList.jsx` at this point; `App` renders `<ArticleList />` where the list goes:

```jsx title="ArticleList.jsx" good="7-9"
import { articles } from '../articles.js';
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList() {
  return (
    <main>
      {articles.map(article => (
        <ArticleCard article={article} />
      ))}
    </main>
  );
}
```

Writing `return <ArticleCard article={article} />;` inside curly braces works the same way. With a fourth article in `articles.js`, this same line gives four cards.

With all the ways tried inside the JSX braces side by side:

```tree dir=right caption="Every way tried inside JSX braces to turn an array into elements, and what each gives back."
What gives back one element per item?
- +map(), element right after => | the array of elements: one card per item
- +map(), => { return ... } | the same array: the return gives back each element
- !map(), => { ... } without return | undefined for every item: no cards, no message
- !forEach() | undefined: no cards, no message
- !a for loop inside JSX braces | a statement: it cannot go there
```

## 2. Cards for only some articles: filter(), then map()

```tree size=mini here="Cards for only some articles"
Render a list from an array of articles
- Create the cards
  - Cards for every article
  - Cards for only some articles
- Update the cards when the list changes
  - Key from the article's id
  - Key on the tag `map()` returns
```

> [!FACT] **`filter()`** calls a function for each item and gives back a new array of only the items for which the function gave back `true`. An array's **`length`** is its number of items; an empty array has a length of `0`. In the box below, `item.isOpen` stands for any true or false field of an item.

> [!FACT] `a && b` gives back `a` when `a` counts as false in a condition, as `0`, `false`, and `null` do, and `b` otherwise. In JSX, React shows nothing for `false` or `null`, but it shows a number as text. A comparison such as `shown.length > 0` always gives a real `true` or `false`, and the ternary `condition ? a : b` gives `a` when the condition is true and `b` otherwise.

> [!PRINCIPLE]
> **Principle 2: Cards for only some items: `filter()`, then `map()`**
>
> To show only some items, we call `filter()` before `map()`. It keeps only the items that pass a test.
>
> When no item passes, the array is empty, and its length is `0`. Then we show a message, with `length > 0` and the ternary. Notice: a bare `length` on the left of `&&` puts a `0` on the page instead.
>
> *We should do this:*
>
> ```jsx
> function OpenItems({ items }) {
>   const shown = items.filter(item => item.isOpen);
>   const cards = shown.map(item => <Item item={item} />);
>   return (
>     <section>
>       {shown.length > 0 ? cards : <p>None yet.</p>}
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function OpenItems({ items }) {
>   const shown = items.filter(item => item.isOpen);
>   const cards = shown.map(item => <Item item={item} />);
>   return (
>     <section>
>       {shown.length && cards} {/* **PROBLEMATIC:** a bare length shows 0 */}
>     </section>
>   );
> }
> ```

Section 1 turned every article into a card. Now the page gets one section per topic, and each section shows only the articles of its own topic. To keep the example small, `App` shows two sections, City and Sport, inside its `<main>`, and each `ArticleList` returns a `<section>` of its own:

```jsx title="App.jsx"
<main>
  <ArticleList topic="City" />
  <ArticleList topic="Sport" />
</main>
```

```hierarchy layout=stack
App | holds: two topic sections, City and Sport
  ArticleList | gets: `topic="City"` | holds: the park article | here: chooses City's cards
    ArticleCard | gets: the park `article`
  ArticleList | gets: `topic="Sport"` | holds: no Sport article | here: chooses a message
notes:
`App` renders one `ArticleList` per topic and passes the topic as a prop.
Each `ArticleList` keeps only the articles whose `topic` matches its own, and draws a card for each.
Of the three articles, only the park article is City; there is no Sport article at all.
We want: the City section shows the park card; the Sport section shows a message, not an empty space.
```

In `ArticleList`, above the `return`, `filter()` keeps the topic's articles, and `map()` turns them into cards. To keep the JSX short, the cards go into a variable, `cards`, as in section 1:

```jsx title="ArticleList.jsx" good="5-6"
import { articles } from '../articles.js';
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList({ topic }) {
  const shown = articles.filter(article => article.topic === topic);
  const cards = shown.map(article => <ArticleCard article={article} />);
  return (
    <section>
      <h2>{topic}</h2>
      {/* the choice goes here: the cards, or a message */}
    </section>
  );
}
```

For City, `shown` holds the park article. For Sport, `filter()` gives back an empty array, `map()` gives back an empty array too, and on its own `{cards}` would leave an empty space under the heading. So the section needs a check that tells "some articles" from "none". The first reflex is `&&`, the usual way to show a piece or nothing, as the facts above Principle 2 described:

::: row caption="With one City article and no Sport article: the line in the section, two ways. Compare the two Sport sections."
::: col title="A bare length left of `&&`" tone=bad
```jsx
{shown.length && cards}
```
```page size=mini
section: City
card: title=New Park Opens Today | author=Mary Jones | input
section: Sport
line: 0 | bad
```
For Sport, `shown.length` is `0`, so `&&` gives back the `0`, and a bare 0 appears under the heading. City, with a length of 1, shows its card.
:::
::: col title="`length > 0`, then the ternary" tone=good
```jsx
{shown.length > 0 ? cards : <p>None yet.</p>}
```
```page size=mini
section: City
card: title=New Park Opens Today | author=Mary Jones | input
section: Sport
line: None yet. | good
```
For Sport, `0 > 0` is `false`, so the ternary gives the message. City, with `1 > 0` true, shows its card.
:::
:::

With the `&&` version and the three articles, what each step gives back for each section:

| section | `filter()` gives back | `shown.length` | `shown.length && cards` gives back | the page shows |
| --- | --- | --- | --- | --- |
| City | `[park]` | `1` | `cards`, one card | the park card |
| !Sport | `[]` | `0` | `0` | a bare 0 |

So the line in the section is `{shown.length > 0 ? cards : <p>None yet.</p>}`. Three choices were possible for an empty topic: `{cards}` alone leaves an empty space, `{shown.length && cards}` shows a bare 0, and only the ternary shows the message. `filter()` runs before `map()`, so `map()` turns only the kept articles into cards.

## 3. Key from the article's id, not its position

```tree size=mini here="Key from the article's id"
Render a list from an array of articles
- Create the cards
  - Cards for every article
  - Cards for only some articles
- Update the cards when the list changes
  - Key from the article's id
  - Key on the tag `map()` returns
```

> [!FACT] A **key** is an attribute React reserves, written on each element of a list: `key={article.id}`. `map()` also passes each item's position to the function, as a second parameter: `items.map((item, index) => ...)`, where `index` is 0 for the first item; with two parameters, they go in parentheses. `Math.random()` gives a new random number each time it runs.

> [!PRINCIPLE]
> **Principle 3: Key from the item's id, not its position**
>
> We give each element a `key`, taken from the item's own id. With the key, React matches each item with the same card the next time the list is shown.
>
> The array index works only for a list whose positions never change: items are only added or removed at the end, and never sorted or moved. A key made while rendering, such as a random number, never works.
>
> *We should do this:*
>
> ```jsx
> function ItemList({ items }) {
>   return (
>     <ul>
>       {items.map(item => (
>         <Item key={item.id} item={item} /> // the key follows the item
>       ))}
>     </ul>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function ItemList({ items }) {
>   return (
>     <ul>
>       {items.map((item, index) => (
>         <Item key={index} item={item} /> // **PROBLEMATIC:** index = position
>       ))}
>     </ul>
>   );
> }
> ```

Since section 1, the console has asked for a key on every card. The cards show fine without one, so the key looks like a way to quiet the console. To see what it really does, we go back to section 1's single list of all three articles, and change the list while a reader is using it.

```hierarchy
ArticleList | holds: `articles`, each with its own `id` | here: names each card with a key
  ArticleCard | gets: one `article`
notes:
`ArticleList` draws one `ArticleCard` per article with `map()`.
From each element, React builds a card on the page, with a comment box; what a reader types stays inside that built card.
When the list is shown again, React must decide which built card goes with which article.
We want: a comment typed under the rain article stays under the rain article, even when a new article arrives at the top.
```

The experiment, with no key on the cards. A reader types "Great news!" into the comment box of the rain card, the second card. Then we add a new article, "Library Opens on Sundays", at the top of `articles.js`, and save the file. With `npm run dev` running, the dev server sends the change to the open page without reloading it, so the typed text is still there after the save, and we can see where it ends up. Saving the file stands in for any list that changes while someone uses the page: new articles from a server, a list sorted or filtered, an item deleted:

```js title="articles.js" good="2"
export const articles = [
  { id: 4, title: 'Library Opens on Sundays', author: 'James Smith', topic: 'City' },
  { id: 1, title: 'New Park Opens Today', author: 'Mary Jones', topic: 'City' },
  // the rain and soups articles follow, unchanged
];
```

::: row arrows caption="With no key on the cards: the comment typed under the rain article ends up under the park article."
::: col title="Before the save: three cards" tone=plain
```page size=mini
card: title=New Park Opens Today | input
card: title=Rain Expected This Weekend | typed=Great news!
card: title=Five Soups for Cold Days | input
```
:::
::: col title="After the save, with no key: four cards" tone=bad
```page size=mini
card: title=Library Opens on Sundays | input
card: title=New Park Opens Today | typed=Great news! | bad=typed
card: title=Rain Expected This Weekend | input
card: title=Five Soups for Cold Days | input
```
:::
:::

When a list is shown again, React matches each new element with a card it already built, keeps that built card, and changes only what differs, such as the title. With no key, it matches by position: the first element with the first built card, the second with the second. The new article pushed every article down one place, so the second built card now receives the park article's title, while the text typed into its box stays where it was. A mismatch is invisible when a card holds nothing of its own, which is why many lists seem fine without keys; it shows as soon as a card holds something, such as typed text or a checked box.

A key names each element, so React matches by name instead of by position. The key is written on the tag inside `map()`, from the article's own id:

```jsx title="ArticleList.jsx" good="2"
{articles.map(article => (
  <ArticleCard key={article.id} article={article} />
))}
```

With `key={article.id}`, the rain card is named 2, the rain article's id, and React finds the built card named 2 wherever it now sits:

```chain caption="After the new article arrives at the top: what React keeps for the built card that holds the typed text."
!by position: the 2nd card, holding "Great news!" -> now shows New Park Opens Today
+by key: the card named 2, the rain article's id, holding "Great news!" -> still shows Rain Expected This Weekend
```

So with `key={article.id}`, every article keeps its own built card, and only the new article gets a newly built one. Keys must differ among the items of one array; when two items share a key, React warns that it found two children with the same key, and it cannot tell them apart. With the same typing and the same save, the four possible keys give four results:

::: row caption="The same typing under the rain card and the same save, with four keys: the first three cards after the save."
::: col title="no key" tone=bad
```page size=mini
card: title=Library Opens on Sundays | input
card: title=New Park Opens Today | typed=Great news! | bad=typed
card: title=Rain Expected This Weekend | input
```
React matches by position: the text moves to the park card, and the console warns.
:::
::: col title="`key={index}`" tone=bad
```page size=mini
card: title=Library Opens on Sundays | input
card: title=New Park Opens Today | typed=Great news! | bad=typed
card: title=Rain Expected This Weekend | input
```
The warning goes, but the index is the position, and the new article shifted every index by one: the text still moves to the park card.
:::
::: col title="`key={Math.random()}`" tone=bad
```page size=mini
card: title=Library Opens on Sundays | input
card: title=New Park Opens Today | input
card: title=Rain Expected This Weekend | input | bad=input
```
A random key is new on every render: no key matches, every card is built again from scratch, and the text is gone.
:::
::: col title="`key={article.id}`" tone=good
```page size=mini
card: title=Library Opens on Sundays | input
card: title=New Park Opens Today | input
card: title=Rain Expected This Weekend | typed=Great news! | good=typed
```
The text stays with the rain article, now the third card.
:::
:::

The four keys side by side:

```tree dir=right caption="The four keys of the experiment, and what each does after a new article arrives at the top."
Which key?
- +key from the article's id | follows the article: the typed text stays with its article
- !key from the index | is the position: the text moves when an item is added, removed, or moved above it
- !key from Math.random() | new on every render: every card is rebuilt, the text is lost
- !no key | matches by position: the text moves the same way, and the console warns
```

The index fits a list like a fixed row of tabs built from an array that never changes. Adding an item at the end is safe too, since every position stays as it was; but removing an item anywhere else moves every later item up one place, just as adding one at the top moved them down.

## 4. Key on the tag map() returns, not inside the card

```tree size=mini here="Key on the tag map() returns"
Render a list from an array of articles
- Create the cards
  - Cards for every article
  - Cards for only some articles
- Update the cards when the list changes
  - Key from the article's id
  - Key on the tag `map()` returns
```

> [!PRINCIPLE]
> **Principle 4: Key on the tag `map()` returns, not inside the child**
>
> We write the `key` directly on the tag that `map()` gives back. That tag is the item of the list React matches.
>
> A key on a tag inside the child component is not an item of the list, so React does not use it, and the warning stays.
>
> *We should do this:*
>
> ```jsx
> function ItemList({ items }) {
>   return (
>     <ul>
>       {items.map(item => (
>         <Item key={item.id} item={item} /> // on the tag map() returns
>       ))}
>     </ul>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function ItemList({ items }) {
>   return <ul>{items.map(item => <Item item={item} />)}</ul>;
> }
> function Item({ item }) {
>   return <li key={item.id}>{item.name}</li>; // **PROBLEMATIC:** inside the child
> }
> ```

Section 3 showed what the key does, on section 1's single list inside `<main>`. Here `articles.js` is back to its first three articles, without the Library article. On which tag does the key go, and what does the card itself see of it?

```hierarchy
ArticleList | holds: the `map()` that gives back the `ArticleCard` elements | here: where the key goes
  ArticleCard | holds: its own markup, one `<article>`
notes:
`ArticleList`'s `map()` gives back an array of `<ArticleCard>` elements. Those are the items React matches.
Each `ArticleCard` returns one `<article>`: part of the card's own markup, not an item of any array.
We want: the key where React looks for it, so the warning goes and each article keeps its built card.
```

React looks for the key on the items of the array it receives, and that array holds `<ArticleCard>` elements; the `<article>` inside a card is not an item of any array, so a key there names nothing React matches. When `map()` gives back another tag around the card, the key moves to that outer tag. A list of articles is often marked up as a list, so each card sits in an `<li>` inside a `<ul>`, and the key goes on the `<li>`:

```jsx title="ArticleList.jsx" good="3"
<ul className="articles">
  {articles.map(article => (
    <li key={article.id}>
      <ArticleCard article={article} />
    </li>
  ))}
</ul>
```

React keeps the key for itself: the card never receives it as a prop. A card that tries to read it, as in `function ArticleCard({ key, article })`, gets `undefined`, and a warning:

```console title="Console, when ArticleCard reads its key as a prop"
warn: ArticleCard: `key` is not a prop. Trying to access it will result in `undefined` being returned.
```

Here the card can still read `article.id`, because it receives the whole article. A component that receives only some fields, and needs the id too, gets it as a prop of its own, under another name, such as `<ArticleCard key={article.id} articleId={article.id} title={article.title} />`.

> [!FACT] A **spread** `{...props}` on a tag passes every field of the object `props` as its own attribute.

A key can also end up hidden inside an object spread onto the tag, for example when a card's props are first gathered into one object, key included:

```jsx title="ArticleList.jsx" bad="2-3"
{articles.map(article => {
  const props = { key: article.id, article: article };
  return <ArticleCard {...props} />;
})}
```

React still reads the key from the spread object, but only as a fallback kept for older code, which a future version of React may drop; it warns, "A props object containing a "key" prop is being spread into JSX". So the key comes out of the object and is written directly on the tag, while the other props can still be spread: `const props = { article: article };` then `<ArticleCard key={article.id} {...props} />`.

> [!FACT] `<>` and `</>`, a Fragment, group several tags without adding a tag to the page, but take no attributes. The long form, `<Fragment>`, imported with `import { Fragment } from 'react';`, can take a key.

When each item is several tags with no single tag around them, the key goes on a `Fragment`. This is a different, simpler list, with no card component: with the three articles, it gives each title followed by its author, and no warning:

```jsx title="ArticleList.jsx" good="2"
{articles.map(article => (
  <Fragment key={article.id}>
    <h2>{article.title}</h2>
    <p>{article.author}</p>
  </Fragment>
))}
```

```tree dir=right caption="The places a key can be written, and what each gives."
Where does the key go?
- +key on the tag map() returns | <ArticleCard key>, or <li key> when the card sits in an <li>
- +key on <Fragment key>, the long form | when each item is several tags; <> takes no key
- !key inside the child | the warning stays: the child's <article> is not an array item
- !key inside a spread object | React still reads it for now, but warns: write key on the tag
```

## Putting the four together

The four steps in one topic section, as the sections built them. A list of articles is marked up as a list, so each card sits in an `<li>` inside a `<ul>`, and the key is on the `<li>`, the tag `map()` gives back. `App` renders `<ArticleList topic="City" />` and `<ArticleList topic="Sport" />`. With the three articles, City shows the park card, and Sport shows "None yet.":

**DO THIS:**

```jsx right
import { articles } from '../articles.js';
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList({ topic }) {
  const shown = articles.filter(article => article.topic === topic);
  const cards = shown.map(article => (
    <li key={article.id}>
      <ArticleCard article={article} />
    </li>
  ));
  return (
    <section>
      <h2>{topic}</h2>
      {shown.length > 0 ? <ul>{cards}</ul> : <p>None yet.</p>}
    </section>
  );
}
```

The same section with two mistakes, marked in red. It names each item by its index, so a comment typed under one article moves to another when a new article of that topic is added at the top (line 7). And it puts a bare length left of `&&`, so a topic with no articles shows a bare 0 instead of a message (line 14):

**DO NOT DO THIS:**

```jsx wrong bad="7,14"
import { articles } from '../articles.js';
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList({ topic }) {
  const shown = articles.filter(article => article.topic === topic);
  const cards = shown.map((article, index) => (
    <li key={index}>
      <ArticleCard article={article} />
    </li>
  ));
  return (
    <section>
      <h2>{topic}</h2>
      {shown.length && <ul>{cards}</ul>}
    </section>
  );
}
```

## For the interview

- **How do you render a list from an array?** Keep the data in an array of objects and call `map()` inside the JSX; its arrow function gives back one element per item, and React shows the array of elements in order. To show only some items, call `filter()` first; when the result can be empty, test its `length` with `> 0` in a ternary: the cards when it is true, a message when it is 0.
- **Why does React need a key?** To match each item with the card it built on the page last time, when the list is shown again. Without a key, React matches by position, so an item added at the top moves typed text to the wrong item.
- **Is `key={index}` fine?** Only for a list whose positions never change: no item is ever inserted or removed anywhere but the end, or moved. The index is the position, so it hides the warning; when a row holds typed text, the text moves to another row as soon as an item is inserted above it or the list is sorted. Lists whose rows hold nothing of their own hide this bug, which is why many tutorials get away with index keys.
- **Why not `key={Math.random()}`?** It changes on every render, so no key matches the last one: every card is built again from scratch, and typed text is lost.
- **Must keys be unique on the whole page?** No, only among the items of one array; two separate lists can use the same ids.
- **Can the child read its key?** No. React keeps the key, so `key` read as a prop is `undefined`, with a warning. When the child needs the id and does not receive the whole item, pass the id again under another name, such as `articleId`.
- **Where does the key go?** On the tag `map()` gives back: on `<ArticleCard key>` when `map()` returns the card, on the `<li>` when the card sits in one, on a `<Fragment key={...}>` when each item is several tags with no tag around them; never inside the child.
- **Why does an empty list with `length &&` show a 0?** For an empty array, `length` is `0`, and `0 && ...` gives back `0`, which React shows as text. Write `length > 0 ? cards : message`, so an empty list shows the message instead of a 0 or an empty space.

## Where you will meet this

- Every list built from data: comments, search results, cart items, messages. Each comes from an array, goes through `map()`, and takes its key from each item's id.
- Data from a server: each record usually arrives with its own id, ready to be its key. When the data has no id, give each item one once, when it is created, for example with `crypto.randomUUID()`, a browser function that gives back a new unique string, available on HTTPS pages and on localhost, and store it with the item; never while rendering.
- Rows that hold input, such as quantities in a cart or checkboxes in a to-do list: when the row itself holds what was typed or checked, as the comment box does, index keys or no keys move those entries to other rows when the list is sorted, or an item is added or deleted anywhere but the end.
- A console warning about keys: it names the component whose `map()` needs the key, so you know which file to open.
