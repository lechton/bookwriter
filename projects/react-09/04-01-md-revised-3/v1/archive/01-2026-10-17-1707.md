## Example: the cart count in a shop's header

An online shoe shop shows the same header at the top of every page. It has three parts: a search box, a line that says how many items are in the cart, and a button to check out. Here is the header while a shopper looks for running shoes, with 2 items already in the cart:

```page caption="The shop's header, with 2 items in the cart. Outlined in green: the two places that show the count."
card: search=running shoes | title=Your cart: 2 items | button=Check out 2 items | good=title,button
```

Look closely: the count, 2, appears twice, once in the cart line and once on the button. Now the shopper clicks "Add to cart" under one pair of shoes in the results, and the cart holds 3 items. Here is the header before and after that click:

::: row arrows caption="The shopper adds a third item to the cart. Outlined in green: the two places that must show the new count."
::: col title="Before the click: 2 items" tone=plain
```page size=mini
card: search=running shoes | title=Your cart: 2 items | button=Check out 2 items
```
With 2 items in the cart, both places show 2, and the search box holds "running shoes".
:::
::: col title="After the click: 3 items" tone=good
```page size=mini
card: search=running shoes | title=Your cart: 3 items | button=Check out 3 items | good=title,button
```
With 3 items in the cart, both places show 3, and the search box still holds "running shoes".
:::
:::

One click changes one piece of data, the count, and the three parts of the header must answer it in different ways:

| on the page | after the click |
| --- | --- |
| the cart line, "Your cart: 2 items" | shows 3 |
| the button, "Check out 2 items" | shows 3 too; otherwise it tells the shopper the cart holds fewer items than it does |
| the search box, with "running shoes" typed in it | still holds "running shoes", because the shopper typed it and is still reading its results |

Two places must follow the data, and one must stay exactly as the shopper left it. Every website meets this question in some form: when the data changes, how does the page change with it? React's answer is to describe the page from the data and let React change the page to match. That is the topic of this lecture: what is React, and how does its way of building a page differ from changing the page by hand with plain JavaScript?

## Two ways to change the page

> [!FACT] The browser does not draw the HTML file directly. It builds one object in memory for every tag, nested the way the tags are nested, and draws the screen from them. Together these objects are the **DOM**, the Document Object Model, and each one is a **DOM node**. So to change what the screen shows, something must change the DOM.

So when the cart gets a third item, something must change the two DOM nodes that show the count. There are two ways to do it:

```tree caption="Two ways to change the page when the cart count changes: give a command for each element, or describe the result."
Change the page when the cart count changes
- Imperative programming | our code finds each element that shows the count and sets its text, one command per element
- Declarative programming | our code describes what each element shows for the count, and React changes the DOM to match
```

> [!FACT] In plain JavaScript, `document.getElementById('cart-summary')` asks the browser for the DOM node whose `id` is `cart-summary`. Setting that node's `textContent` replaces the text inside it, and nothing else on the page changes.

In **imperative programming**, our code gives the browser each command itself: find this element, set its text. In plain JavaScript, the cart line gets its new count with a line such as this one:

```js title="Imperative: plain JavaScript"
document.getElementById('cart-summary').textContent = 'Your cart: 3 items';
```

In **declarative programming**, our code says what each element shows, and something else makes the DOM match. In React, the cart line is written once, with a place for the count, and when the count is 3, React makes the line show "Your cart: 3 items":

```jsx title="Declarative: React"
<p>Your cart: {cartCount} items</p>
```

**React** is a JavaScript library for building user interfaces out of components, and it is declarative.

Why does the difference matter? Imperative code is fine for one element that changes in one place, such as a clock in the corner of a page. But the count shows in two places, so imperative code needs two commands on every change, and a place with no command keeps the old count, as section 1 shows. And a script that rebuilds the whole header, to avoid writing one command per place, throws away what the shopper typed, as section 3 shows. Declarative code has no command to forget: each place says what it shows, and React works out the changes.

## The React project for this lesson

The rest of the lecture writes the header in React. In React, a page is built from **components**: a component is a JavaScript function whose name starts with a capital letter and which returns the markup for one piece of the page. Lecture 2 gives the rules for writing one. This lecture has one component, `ShopHeader`, inside a small project prepared for the lesson. Three files of that project matter:

| file | what it holds |
| --- | --- |
| `index.html` | the page the browser loads; its body holds one empty element, `<div id="root"></div>` |
| `src/main.jsx` | the code that tells React to show `ShopHeader` inside that empty element; Lecture 9 explains how |
| `src/ShopHeader.jsx` | the header component this lecture writes |

Here is `ShopHeader`, with the count written once, at its top:

```jsx title="ShopHeader.jsx"
export default function ShopHeader() {
  const cartCount = 2; // the count, written once
  return (
    <header>
      <input placeholder="Search products" />
      <p>Your cart: {cartCount} items</p>
      <button>Check out {cartCount} items</button>
    </header>
  );
}
```

Each piece of this code has a name:

| in the code | what it is |
| --- | --- |
| `const cartCount = 2` | a **local variable**: a name for a value, inside this function |
| the markup after `return` | **JSX**: it looks like HTML, but it is JavaScript, as Lecture 3 explains |
| `{cartCount}` | **curly braces** in JSX: a place where a JavaScript value goes, so the page shows 2 there |
| `export default` | lets another file, here `main.jsx`, use this function, as Lecture 8 explains |

What `ShopHeader` returns is a **description** of the header: it says what each element shows, and React builds the real DOM nodes from it. Our code never calls `ShopHeader`; React calls it. The search box reads no variable at all, because what it holds comes from the shopper, not from the data.

How does the count change in this lecture? A value that changes while the page is open, after a click, needs state, which Lecture 14 teaches. Until then, the count is written in the file, and we play the shopper's click ourselves: we change `2` to `3` in `ShopHeader.jsx` and save. The project runs with the command `npm run dev`, which starts a **dev server**: a small program on our computer that sends the project to the browser while we work. Each time we save a file, the dev server sends the new code to the open page, and React updates the page without reloading it.

## Three steps in the life of `cartCount`

The lecture follows the count through three steps, one section each:

```tree caption="The three steps of cartCount, and the idea each one teaches."
The life of one value, `cartCount`
- Declarative programming | `ShopHeader` describes what each element shows, and React builds the DOM from it
- A single source of truth | the cart line and the button both read `{cartCount}`
- Virtual DOM comparison | when `cartCount` changes, React changes only the new number
```

Each step needs the one before it. Two places can share the count only once the header is described from it. And the change can be shown whole only once both places read the same variable: then one save changes both, and the search box beside them shows what React leaves alone.

## 1. Declarative programming: ShopHeader describes the header, and React builds it

```tree size=mini here="Declarative programming"
The life of one value, `cartCount`
- Declarative programming
- A single source of truth
- Virtual DOM comparison
```

> [!PRINCIPLE]
> **Principle 1: Declarative programming: describing what the page shows, not how to change it**
>
> We control the page by describing what it shows from data.
>
> A component returns JSX that says what each element shows for the current data. React calls the component and builds the DOM from it.
>
> We never find and change the page's elements by hand. Notice: every element our code changes by hand is an element our code can forget.
>
> *We should do this:*
>
> ```jsx
> function ShopHeader() {
>   const cartCount = 3;
>   return <p>Your cart: {cartCount} items</p>; // React builds the <p> from this
> }
> ```
>
> *We should not do this:*
>
> ```js
> function updateCart(count) {
>   const summary = document.getElementById('cart-summary');
>   summary.textContent = 'Your cart: ' + count + ' items'; // **PROBLEMATIC:** names one element; the button keeps its old text
> }
> ```

Before the shop moved to React, its header was a plain HTML page, and a script changed it by hand. This section sets that page against `ShopHeader`:

```hierarchy caption="Section 1: the same header, changed by hand or described in ShopHeader."
ShopHeader | holds: `cartCount = 2` | here: describes the whole header from the count
notes:
On the old plain HTML page, the cart line and the button each have an `id`, and a script, `updateCart`, sets the text of each element it names.
In React, `ShopHeader` returns the header's markup, with `{cartCount}` in the cart line and on the button.
We want: the count right in both places, and no line of our code that finds or changes an element.
```

The old page writes the header in HTML, with an `id` on each place that shows the count:

```html title="old-header.html (the plain HTML page)"
<input placeholder="Search products">
<p id="cart-summary">Your cart: 2 items</p>
<button id="checkout">Check out 2 items</button>
```

When the shopper adds a third item, the old page calls `updateCart(3)`. The function finds the cart line by its `id` and sets its text:

```js title="Plain JavaScript: updateCart"
function updateCart(count) {
  const summary = document.getElementById('cart-summary');
  summary.textContent = 'Your cart: ' + count + ' items';
}

updateCart(3);
```

After the call, the old page shows this header:

```page caption="The old plain HTML page after updateCart(3). Look at the button."
card: search=running shoes | title=Your cart: 3 items | button=Check out 2 items | bad=button
```

The script changes exactly the nodes it names, and it names only the cart line. The button, never named, still says "Check out 2 items" while the cart holds 3. Every new place that shows the count needs one more line in `updateCart`, and one forgotten line is one place with an old count.

In React there is no `updateCart`. `ShopHeader` returns what each element shows, and React builds the DOM nodes from it. The proof is in the browser:

> [!FACT] To see the DOM, open the browser's developer tools and choose the **Elements panel**. It shows the DOM nodes the page has right now, which is not always what the HTML file holds.

::: row caption="With npm run dev running and ShopHeader returning the header: the file the browser loads, and the DOM it ends up with."
::: col title="The file `index.html`" tone=plain
```html
<body>
  <div id="root"></div>
</body>
```
In the file, the root is empty: no search box, no cart line, no button.
:::
::: col title="The Elements panel" tone=good
```dom title="Elements panel"
<div id="root">
*  <header>
*    <input placeholder="Search products">
*    <p>Your cart: 2 items</p>
*    <button>Check out 2 items</button>
*  </header>
</div>
```
In the page, the root holds the whole header. React built every marked node from what `ShopHeader` returned.
:::
:::

A search of our code finds no `getElementById` and no `textContent`. No line names an element, so no element can be forgotten. Section 2 changes the count and shows what that buys.

## 2. A single source of truth: every place reads `{cartCount}`

```tree size=mini here="A single source of truth"
The life of one value, `cartCount`
- Declarative programming
- A single source of truth
- Virtual DOM comparison
```

> [!FACT] Inside JSX, a comment is written in curly braces, `{/* like this */}`. It shows nothing on the page; the code below uses it to point at a line.

> [!PRINCIPLE]
> **Principle 2: Single source of truth: describing many places from one value**
>
> When one value appears in many places, we keep it in one variable.
>
> Every place reads that variable in curly braces, so every place is built from it.
>
> We never type a copy of the value into the markup. Notice: a typed copy is fixed text, so it keeps the old value when the variable changes.
>
> *We should do this:*
>
> ```jsx
> function ShopHeader() {
>   const cartCount = 3;
>   return (
>     <header>
>       <p>Your cart: {cartCount} items</p>
>       <button>Check out {cartCount} items</button> {/* reads cartCount, like the cart line */}
>     </header>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function ShopHeader() {
>   const cartCount = 3;
>   return (
>     <header>
>       <p>Your cart: {cartCount} items</p>
>       <button>Check out 2 items</button> {/* **PROBLEMATIC:** a 2 typed by hand never changes */}
>     </header>
>   );
> }
> ```

Section 1 described the header in `ShopHeader`. Now the shopper adds a third item, and the count must change in both places:

```hierarchy caption="Section 2: the count changes from 2 to 3, and two places show it."
ShopHeader | holds: `cartCount`, changed from `2` to `3` | here: describes the cart line and the button
notes:
We play the shopper's click: we change `cartCount` to `3` in the file and save.
In the version below, the cart line reads `{cartCount}`, but the button was pasted from the old HTML page with its 2 typed in.
We want: after the save, both places show 3.
```

When the header moved from the old HTML page into React, the cart line got its `{cartCount}`, but the button was pasted as it was, with "Check out 2 items" typed into it. It is an easy slip to miss: the page looks right for as long as the count is 2. Here is that version after we change line 2 to `3` and save:

```jsx title="ShopHeader.jsx" bad="7"
export default function ShopHeader() {
  const cartCount = 3; // changed from 2, then saved
  return (
    <header>
      <input placeholder="Search products" />
      <p>Your cart: {cartCount} items</p>
      <button>Check out 2 items</button> {/* pasted from the old HTML page */}
    </header>
  );
}
```

The save makes React call `ShopHeader` again, and the page shows this header:

```page caption="After the save, with cartCount set to 3. Look at the button."
card: search=running shoes | title=Your cart: 3 items | button=Check out 2 items | bad=button
```

React makes each element show exactly what the JSX describes, and the JSX describes two different counts:

| place | written in the JSX | what the page shows after the save |
| --- | --- | --- |
| the cart line | `Your cart: {cartCount} items` | "Your cart: 3 items", read from the variable |
| !the button | `Check out 2 items`, typed by hand | "Check out 2 items", the same text as before |

React did nothing wrong: the button never asked for the variable. The fix is line 7, where the button reads the same variable as the cart line:

```jsx title="ShopHeader.jsx" good="1" startLine="7"
      <button>Check out {cartCount} items</button>
```

Now both places are built from one variable, and after the save both show the new count:

```page caption="After the fix and the save, with cartCount set to 3. Both places show 3."
card: search=running shoes | title=Your cart: 3 items | button=Check out 3 items | good=title,button
```

Keeping each value in one place, which every part of the page reads, is called a **single source of truth**. A third place that shows the count, such as a small number on a cart icon, adds one more `{cartCount}` and no update code. Lecture 23 uses the same idea when two components share a value that changes.

## 3. Virtual DOM comparison: React changes only the new number

```tree size=mini here="Virtual DOM comparison"
The life of one value, `cartCount`
- Declarative programming
- A single source of truth
- Virtual DOM comparison
```

> [!FACT] In plain JavaScript, setting an element's `innerHTML` throws away every node inside it and builds new nodes from a string of HTML. `textContent` only replaces the text inside one node.

> [!PRINCIPLE]
> **Principle 3: The virtual DOM: describing the page again when the value changes**
>
> When the value changes, React calls the component again and gets a new description.
>
> React compares the new description with the last one, element by element. It changes only the text that is new.
>
> Every other node stays where it is, so a text box keeps what the user typed. Notice: rebuilding the elements with `innerHTML` makes new nodes, and the typed text is gone.
>
> *We should do this:*
>
> ```jsx
> function ShopHeader() {
>   const cartCount = 3; // changed from 2, then saved
>   return (
>     <header>
>       <input placeholder="Search products" /> {/* the same node: keeps what was typed */}
>       <p>Your cart: {cartCount} items</p> {/* only the number changes */}
>     </header>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```js
> function rebuildHeader(count) {
>   const header = document.getElementById('header');
>   const html = '<input placeholder="Search products"><p>Your cart: ' + count + ' items</p>';
>   header.innerHTML = html; // **PROBLEMATIC:** builds new nodes, so the typed text is gone
> }
> ```

Section 2 gave the count one variable, so one save changes both places. But on every save, `ShopHeader` returns a description of the whole header, the search box included. What happens to "running shoes", which the shopper typed into that box?

```hierarchy caption="Section 3: the count changes while 'running shoes' is typed in the search box."
ShopHeader | holds: `cartCount`, saved as `3` | here: returns a new description of the whole header
notes:
On the open page, "running shoes" is typed in the search box.
The file is saved with `cartCount = 3`, so React calls `ShopHeader` again, and it returns the whole header again, with 3 in it.
We want: both places show 3, and the search box still holds "running shoes".
```

A developer coming from plain JavaScript may expect React to do what many scripts do: rebuild the inside of the header from a string with the new count in it. Here is such a script, on the old page:

```js title="Plain JavaScript: rebuild the header with the new count" bad="3-6"
const count = 3;
const header = document.getElementById('header');
header.innerHTML =
  '<input placeholder="Search products">' +
  '<p>Your cart: ' + count + ' items</p>' +
  '<button>Check out ' + count + ' items</button>';
```

The script and React give two different headers. Compare the two search boxes:

::: row caption="With 'running shoes' typed in the search box, the count changes to 3. Both versions show 3 in both places; only the search box differs."
::: col title="Plain JavaScript: rebuilt with `innerHTML`" tone=bad
```page size=mini
card: search=placeholder:Search products | title=Your cart: 3 items | button=Check out 3 items | bad=search
```
With "running shoes" typed and the header rebuilt, both places show 3, but the search box is a new, empty `<input>`.
:::
::: col title="React: `ShopHeader` saved with `cartCount = 3`" tone=good
```page size=mini
card: search=running shoes | title=Your cart: 3 items | button=Check out 3 items | good=search
```
With "running shoes" typed and the file saved, both places show 3, and the search box still holds "running shoes".
:::
:::

After the save, React calls `ShopHeader` again and gets a whole new description of the header. It compares it with the last description, element by element:

| element | last description | new description | in the DOM |
| --- | --- | --- | --- |
| `<input>` | the search box | the search box | the same node stays, with "running shoes" in it |
| `<p>` | Your cart: 2 items | Your cart: 3 items | the text "2" becomes "3" |
| `<button>` | Check out 2 items | Check out 3 items | the text "2" becomes "3" |

So for this save, React makes two text changes, and nothing else on the page is rebuilt. Even "Your cart:" and "items" are left alone, because `{cartCount}` is its own piece of text inside the `<p>`. The `<input>` is the same DOM node it was before the save, so it still holds what the shopper typed. `innerHTML`, instead, throws away every node inside the header and builds new ones, and a new `<input>` starts empty.

The description is not the DOM: it is kept in memory as plain JavaScript objects that the browser never draws, as Lecture 3 shows. Because it has the shape of the DOM without being it, people often call it the **virtual DOM**. The React documentation describes what React does with it as "the minimal necessary operations": for this save, two text changes. When the new description is the same as the last one, React changes no text at all. Lecture 15 gives each step of an update its name.

## Putting the three together

The header as the three sections built it. `ShopHeader` describes every element, with no line that finds or changes one. The cart line and the button both read `{cartCount}`, the single source of truth. And when the file is saved with `cartCount = 3`, React compares the new description with the last one and changes only the two numbers, so the search box keeps "running shoes":

**DO THIS:**

```jsx right
export default function ShopHeader() {

  return (
    <header>
      <input placeholder="Search products" />
      <p>Your cart: {cartCount} items</p>
      <button>Check out {cartCount} items</button>
    </header>

    '<input placeholder="Search products">' +
    '<p>Your cart: ' + count + ' items</p>' +
    '<button>Check out ' + count + ' items</button>';
}
```

And the same mistake inside React: the button's count typed as fixed text, so with `cartCount` set to 3 the button still says "Check out 2 items" (line 7):

## For the interview

- **What is React?** A JavaScript library for building user interfaces out of components. It can run a whole page, or only one part of a page that already exists.
- **How does its model differ from plain JavaScript DOM scripting?** In plain JavaScript, our code finds each element and changes it by hand: that is imperative, and an element the code forgets keeps old data, as the button kept "2" while the cart held 3. In React, a component describes what the page shows for the current data, and React builds and changes the DOM to match: that is declarative. Each value lives in one variable that every place reads, a single source of truth, so no place keeps an old copy.
- **Does React rebuild the page each time the data changes?** No, that is the classic trap. React calls the component again and compares the new description with the last one. On our header it made two text changes, "2" to "3", and the search box, the same node as before, kept "running shoes". People call the compared description the virtual DOM.
- **Is React faster than changing the DOM by hand?** No, and that is not its job. React changes the DOM with the same browser methods a script uses, and a script that sets one piece of text does that work with less code to run. React's gain is that our code no longer writes, or forgets, the update steps.
- **Does React stop an old value from showing anywhere?** Only where the JSX reads the variable. A value typed into the markup as fixed text keeps the old value, even in React.
- **Can I still call `document.getElementById` inside a component?** On the component's first run, its own elements are not on the page yet, so the call returns `null`; Lecture 10 shows the error this causes. For the few jobs that need one particular element, such as moving the cursor into a search box, React gives a way to reach it without changing what it shows (Lecture 30).

## Where you will meet this

- The signed-in user's name: shown in the greeting at the top and again in the account menu. Both read one variable, so a name change reaches both at once.
- An order total: shown in the order summary and on the "Pay" button. Both read one total, so the button never asks for a different amount than the summary shows.
- A results page: "12 results for running shoes" changes above the list while the same words stay in the search box, because React changes the heading's text and leaves the box as the shopper left it.
- An unread count: shown in the browser tab and beside the inbox. One variable feeds both, so the tab and the inbox always agree.
