## Example: a site header that shows the user's name

The example for this whole lecture is the header at the top of a website. It greets the signed-in user by name, shows the name again in its corner, and holds a search box. Here is the header for a user named Mary:

```page caption="The site's header, for the signed-in user Mary. Outlined in green: the two places that show her name."
card: title=Welcome back, Mary | text=Signed in as Mary | input=Search | good=title,text
```

Look closely: the name appears twice, once in the greeting and once in the corner. Now Mary adds her family name in her profile and becomes Mary Brooks. At that moment she is using the page: she has typed "elections" into the search box, and the cursor blinks in it. Here is what the header must show before and after the change:

::: row arrows caption="Mary becomes Mary Brooks while 'elections' is typed in the search box. Outlined in green: the two places that must change."
::: col title="Before: the name is Mary" tone=plain
```page size=mini
card: title=Welcome back, Mary | text=Signed in as Mary | typed=elections
```
With the name Mary, both places show "Mary", and the box holds "elections".
:::
::: col title="After: the name is Mary Brooks" tone=good
```page size=mini
card: title=Welcome back, Mary Brooks | text=Signed in as Mary Brooks | typed=elections | good=title,text
```
With the name Mary Brooks, both places show the new name, and the box still holds "elections".
:::
:::

One change of data, three parts of the page, and they must not all do the same thing:

| on the page | when the name changes |
| --- | --- |
| "Welcome back, Mary" in the greeting | shows the new name |
| "Signed in as Mary" in the corner | shows the new name too |
| the search box, with "elections" typed in it | keeps "elections" and the cursor, because the user typed it, not the data |

Two places must follow the data, and one must be left exactly as the user left it. Every web page meets this question in some form: when the data changes, how does the page change with it? React's answer is to describe the page from the data and let React change the page to match. That is the topic of this lecture: what is React, and how does its way of building a page differ from changing the page by hand with plain JavaScript?

## The components behind the page

In React, a page is built from **components**. A component is a JavaScript function whose name starts with a capital letter and which returns the markup for one piece of the page; Lecture 2 gives the rules for writing one. This lecture has one component, `SiteHeader`, inside a small project prepared for the lesson. Three files of that project matter:

| file | what it holds |
| --- | --- |
| `index.html` | the page the browser loads; its body holds one empty element, `<div id="root"></div>` |
| `src/main.jsx` | the file that hands that empty element to React and tells React to show `SiteHeader` in it; Lecture 9 explains how |
| `src/SiteHeader.jsx` | the header component this lecture writes |

```hierarchy caption="The one component of this lecture, and what it holds."
SiteHeader | holds: the user's name, `userName` | here: returns the whole header's markup
notes:
`SiteHeader` lives in `src/SiteHeader.jsx`, and `main.jsx` shows it inside the empty `<div id="root">` of `index.html`.
It keeps the name once, in a variable, `userName`, and returns the markup of the greeting, the corner, and the search box.
Our code never calls `SiteHeader`: React calls it, and builds the page from what it returns.
`main.jsx` places it with its tag, `<SiteHeader />`, written like an HTML tag that closes itself; the diagrams in this lecture show each component by that tag.
```

Here is the component, with the name written once at its top:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const userName = 'Mary'; // the name, written once
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as {userName}</span>
      <input placeholder="Search" />
    </header>
  );
}
```

`const userName = 'Mary'` makes a **local variable**: a name for a value, inside this function. The markup after `return` is **JSX**: it looks like HTML, but it is JavaScript, as Lecture 3 explains. Inside JSX, **curly braces** mark a place where a JavaScript value goes, so `{userName}` shows "Mary" in the greeting and again in the corner. `export default` lets another file, here `main.jsx`, use this function, as Lecture 8 explains. What `SiteHeader` returns is a **description** of the header: it says what each element shows, and React builds the real elements from it.

So each part of the example has its line: the user's name is `userName`, the greeting is the `<p>`, the corner is the `<span>`, and the search box is the `<input>`, which reads no variable at all, because what it shows comes from the user.

The project runs with the command `npm run dev`, which starts a **dev server**: a small program on our computer that sends the project to the browser while we work. Each time we save a file, the dev server sends the new code to the open page, and the page shows the change without a reload. In this lecture the name changes only that way: Mary's profile change is played by us, editing `userName` in the file and saving. A value that changes while the page is open needs state, which Lecture 14 teaches.

## Two ways to change the page when the data changes

> [!FACT] The browser does not draw the HTML file directly. It builds one object in memory for every tag, nested the way the tags are nested, and draws the screen from them. Together these objects are the **DOM**, the Document Object Model, and each one is a **DOM node**. So to change what the screen shows, something must change the DOM.

> [!FACT] In plain JavaScript, `document.getElementById('greeting')` asks the browser for the DOM node whose `id` is `greeting`. Setting that node's `textContent` replaces the text inside it, and nothing else on the page changes.

There are two ways to change the DOM when the data changes:

```tree caption="Two ways to change the page when the data changes: command each element, or describe the result."
Change the page when the data changes
- Imperative programming | our code finds each element and sets its text, one command at a time
- Declarative programming | our code describes what each element shows; React changes the DOM to match
```

Here is the greeting, written each way, for the change from Mary to Mary Brooks. In plain JavaScript, on an older page where the greeting is written in HTML as `<p id="greeting">` (section 1 shows that page), our code names the greeting by its `id` and sets its text; the corner changes only if another line names it too:

```js title="Imperative: plain JavaScript"
const greeting = document.getElementById('greeting');
greeting.textContent = 'Welcome back, Mary Brooks';
```

In React, the greeting says what it shows. When `userName` holds "Mary Brooks", React makes the `<p>` show that name, and no line of our code names the element or sets its text:

```jsx title="Declarative: React"
<p>Welcome back, {userName}</p>
```

In **imperative programming**, our code gives the browser every command itself: find this element, set its text. In **declarative programming**, our code declares what each element shows for the current data, and React makes the DOM match. **React** is a JavaScript library for building user interfaces out of components, and it is declarative.

Why does the difference matter? Imperative code is fine for one element that changes in one place, such as a clock in the corner of a page. But when the same value shows in several places, imperative code needs one command per place on every change, and a place with no command keeps the old value. And code that rebuilds a part of the page to save writing commands throws away whatever the user typed inside it, as the last section of this lecture shows. Declarative code has no command to forget: each place says what it shows, and React works out the changes.

## Three moments in the life of one value

The whole lecture follows one value, `userName`, through three moments. First the header is described from it, then several places share it, then it changes:

```tree caption="The three moments of userName, and the idea each one teaches."
The life of one value, `userName`
- Described: declarative programming | `SiteHeader` returns what each element shows; React builds the DOM from it
- Shared: a single source of truth | the greeting and the corner both read `{userName}`, so neither keeps an old copy
- Changed: the virtual DOM | React compares the new description with the last one, and only the new text changes
```

The sections take the moments in this order because each one needs the one before it. The name can be shared only once the header is described from it. And the change can be shown whole only once every place reads the same variable: then one save changes both places, and the search box beside them shows what React leaves alone.

## 1. Declarative programming: the component describes the header, React builds it

```tree size=mini here="Described: declarative programming"
The life of one value, `userName`
- Described: declarative programming
- Shared: a single source of truth
- Changed: the virtual DOM
```

> [!FACT] The code in the principle boxes of this lecture uses general names, `Greeting` for a component and `name` for its value. In our header, they are `SiteHeader` and `userName`.

> [!PRINCIPLE]
> **Principle 1: Declarative programming: describing what the page shows, not how to change it**
>
> We control the page by describing what it shows from data.
>
> A component returns JSX that says what each element shows for the current data. React calls the component and builds the DOM from it.
>
> We never find and change the page's elements by hand. Notice: an element our code would have to change by hand is an element our code can forget.
>
> *We should do this:*
>
> ```jsx
> function Greeting() {
>   const name = 'John';
>   return <p>Hello, {name}</p>; // React builds the <p> from this
> }
> ```
>
> *We should not do this:*
>
> ```js
> function updateGreeting(name) {
>   const el = document.getElementById('hello');
>   el.textContent = 'Hello, ' + name; // **PROBLEMATIC:** sets one element; others keep old text
> }
> ```

The first moment: the header is described from `userName`. Before React, the same header was a plain HTML page, and a script changed it by hand. Here is what React asks of us instead:

```hierarchy caption="Section 1: the header described in SiteHeader."
SiteHeader | holds: `userName = 'Mary'` | here: describes the header from the name
notes:
In the old plain JavaScript page, the greeting and the corner each have an `id`, and a script sets the text of each element it names.
In React, `SiteHeader` returns the header's markup, with `{userName}` in the greeting and in the corner.
We want: the whole header on the page with "Mary" in both places, and no line of our code that finds or changes an element.
```

The old page has a greeting and a corner, each with its own `id`:

```html title="old-header.html (the plain JavaScript page)"
<p id="greeting">Welcome back, Mary</p>
<span id="account">Signed in as Mary</span>
```

When Mary becomes Mary Brooks, a script updates the header. It finds the greeting by its `id` and sets its text:

```js title="Plain JavaScript: updateHeaderUser" bad="3"
function updateHeaderUser(name) {
  const greeting = document.getElementById('greeting');
  greeting.textContent = 'Welcome back, ' + name;
}

updateHeaderUser('Mary Brooks');
```

After the call, the plain JavaScript page shows:

```page caption="The plain JavaScript page after updateHeaderUser('Mary Brooks'). Look at the corner."
card: title=Welcome back, Mary Brooks | text=Signed in as Mary | input=Search | bad=text
```

The script changes exactly the nodes it names, and it names only the greeting:

```chain caption="Why the corner keeps the old name after updateHeaderUser('Mary Brooks')."
!`updateHeaderUser('Mary Brooks')` -> names one element, the greeting, and sets its text -> the corner, never named, still shows "Signed in as Mary"
```

Every new place on the page that shows the name needs one more line in this function. One forgotten line is one place with the old name.

> [!FACT] To see the DOM, open the browser's developer tools and choose the **Elements panel**. It shows the DOM nodes the page has right now, which is not always what the HTML file holds.

In React, we write no update function at all. `SiteHeader`, shown in the components section, returns what each element shows, and React builds the DOM nodes from it. The served file and the Elements panel show the difference:

::: row caption="With npm run dev running and SiteHeader returning the header: the file the browser loads, and the DOM it ends up with."
::: col title="The file `index.html`" tone=plain
```html
<body>
  <div id="root"></div>
</body>
```
In the file, the root is empty: no greeting, no corner, no search box.
:::
::: col title="The Elements panel" tone=good
```dom title="Elements panel"
<div id="root">
*  <header>
*    <p>Welcome back, Mary</p>
*    <span>Signed in as Mary</span>
*    <input placeholder="Search">
*  </header>
</div>
```
In the page, the root holds the whole header. React built every marked node from what `SiteHeader` returned.
:::
:::

A search of our code finds no `getElementById` and no `textContent`, so there is no line that a new place on the page could be missing. Because the component only describes, the same data always gives the same page; Lecture 12 explains why React counts on that.

```tree dir=right caption="Who changes the DOM, and what each way risks."
Who changes the DOM?
- !Our code, one command per element | an element the code never names keeps its old text
- +React, from the JSX a component returns | our code names no element, so it forgets none
```

## 2. A single source of truth: every place reads one variable

```tree size=mini here="Shared: a single source of truth"
The life of one value, `userName`
- Described: declarative programming
- Shared: a single source of truth
- Changed: the virtual DOM
```

> [!FACT] Inside JSX markup, a comment is written in curly braces, `{/* like this */}`. It shows nothing on the page; the boxes use it to point at a line.

> [!PRINCIPLE]
> **Principle 2: Single source of truth: describing many places from one value**
>
> When one value appears in many places, we keep it in one variable.
>
> Every place reads that variable in curly braces, so every place is built from it.
>
> We never type a copy of the value into the markup. Notice: a typed copy is fixed text, so it keeps the old value when the variable changes.
>
> *We should do this:*
>
> ```jsx
> function Greeting() {
>   const name = 'John Hall';
>   return (
>     <header>
>       <p>Hello, {name}</p>
>       <span>Signed in as {name}</span> {/* reads name, like the greeting */}
>     </header>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Greeting() {
>   const name = 'John Hall';
>   return (
>     <header>
>       <p>Hello, {name}</p>
>       <span>Signed in as John Hall</span> {/* **PROBLEMATIC:** a typed copy never changes */}
>     </header>
>   );
> }
> ```

Section 1 built the header from `SiteHeader`'s description. Now the name changes, and it shows in two places:

```hierarchy caption="Section 2: the name changes, and two places show it."
SiteHeader | holds: `userName`, changed to `'Mary Brooks'` | here: describes the greeting and the corner
notes:
`userName` holds the name once, at the top of `SiteHeader`.
In the version below, the greeting reads `{userName}`, but the corner was pasted from the old HTML page, with the name typed into it.
We want: after `userName` changes to `'Mary Brooks'` and the file is saved, both places show "Mary Brooks".
```

`SiteHeader` in the components section reads `{userName}` in both places. Suppose instead that, when the header moved into React, the corner was pasted from the old page, letters and all. Here is that version, after we change line 2 to `'Mary Brooks'` and save, with the dev server running:

```jsx title="SiteHeader.jsx" bad="6"
export default function SiteHeader() {
  const userName = 'Mary Brooks'; // changed from 'Mary', then saved
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as Mary</span> {/* pasted from the HTML page */}
      <input placeholder="Search" />
    </header>
  );
}
```

The save makes React call `SiteHeader` again, and the page shows:

```page caption="After the save, with userName set to 'Mary Brooks'. Look at the corner."
card: title=Welcome back, Mary Brooks | text=Signed in as Mary | input=Search | bad=text
```

On every call, React makes each element show exactly what the JSX describes:

| place | written in the JSX | what the page shows after the save |
| --- | --- | --- |
| the greeting | `Welcome back, {userName}` | "Welcome back, Mary Brooks", read from the variable |
| !the corner | `Signed in as Mary`, typed letters | "Signed in as Mary", the same letters as before |

React did nothing wrong: the JSX asked for two different names. The fix is one line, line 6 of the file, where the corner reads the same variable as the greeting:

```jsx title="SiteHeader.jsx" good="1" startLine="6"
      <span>Signed in as {userName}</span>
```

Now both places are built from one variable, and after the save both show the new name:

```page caption="After the fix and the save, with userName set to 'Mary Brooks'. Both places show the new name."
card: title=Welcome back, Mary Brooks | text=Signed in as Mary Brooks | input=Search | good=title,text
```

Keeping each value in one place, which every part of the page reads, is called a **single source of truth**. A third place that shows the name, such as an account menu, adds one more `{userName}` and no update code. Lecture 23 uses the same idea when two components must share a value that changes.

```tree dir=right caption="How a place shows a value that appears in many places."
How does each place show the name?
- !A copy of the name, typed as fixed text | it keeps the old name when `userName` changes
- +`{userName}`, read in every place | every place shows the new name after the save
```

## 3. The virtual DOM: React changes only the new text

```tree size=mini here="Changed: the virtual DOM"
The life of one value, `userName`
- Described: declarative programming
- Shared: a single source of truth
- Changed: the virtual DOM
```

> [!FACT] In plain JavaScript, setting an element's `innerHTML` throws away every node inside it and builds new nodes from a string of HTML. `textContent` only replaces the text inside one node.

> [!FACT] When we click into a text box and type, that box has the **focus**: it receives the keys we press and shows a blinking cursor. Only one element has the focus at a time; when that element goes away, the focus goes back to the page itself.

> [!PRINCIPLE]
> **Principle 3: The virtual DOM: describing the page again when the value changes**
>
> When the value changes, React calls the component again and gets a new description.
>
> React compares the new description with the last one, element by element. It changes only the text that is new.
>
> Every other node stays where it is, so a text box keeps what the user typed, and its focus. Notice: rebuilding the elements with `innerHTML` makes new nodes, and the typed text is gone.
>
> *We should do this:*
>
> ```jsx
> function Greeting() {
>   const name = 'John Hall'; // changed from 'John', then saved
>   return (
>     <header>
>       <p>Hello, {name}</p> {/* only this text changes */}
>       <input placeholder="Search" /> {/* the same node: keeps what was typed */}
>     </header>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```js
> function updateGreeting(name) {
>   const header = document.getElementById('header');
>   const html = '<p>Hello, ' + name + '</p><input placeholder="Search">';
>   header.innerHTML = html; // **PROBLEMATIC:** new nodes: the typed text is gone
> }
> ```

Section 2 gave the name one variable, so a save changes it in every place. But `SiteHeader` returns a description of the whole header each time, and now the header is in use while the name changes:

```hierarchy caption="Section 3: the name changes while the search box is in use."
SiteHeader | holds: `userName`, saved as `'Mary Brooks'` | here: returns a new description of the whole header
notes:
We have typed "elections" into the search box of the open page, as Mary would, and the cursor blinks in it.
The file is saved with `userName = 'Mary Brooks'`, so React calls `SiteHeader` again, and it returns the whole header again, with the new name in it.
We want: both names change to "Mary Brooks", and the search box keeps "elections" and the cursor.
```

A developer coming from plain JavaScript may expect React to do what a script often does: rebuild the inside of the header from a string with the new name in it. Here is that script:

```js title="Plain JavaScript: rebuild the header with the new name" bad="3-6"
const name = 'Mary Brooks';
const header = document.getElementById('header');
header.innerHTML =
  '<p>Welcome back, ' + name + '</p>' +
  '<span>Signed in as ' + name + '</span>' +
  '<input placeholder="Search">';
```

The script and React give two different headers. Compare the two search boxes:

::: row caption="With 'elections' typed in the search box, the name changes to Mary Brooks. Both versions show the new name; only the search box differs."
::: col title="Plain JavaScript: rebuilt with `innerHTML`" tone=bad
```page size=mini
card: title=Welcome back, Mary Brooks | text=Signed in as Mary Brooks | input=Search | bad=input
```
With "elections" typed and the header rebuilt, both names change, but the search box is a new, empty `<input>`, and the focus is back on the page.
:::
::: col title="React: `SiteHeader` saved with `'Mary Brooks'`" tone=good
```page size=mini
card: title=Welcome back, Mary Brooks | text=Signed in as Mary Brooks | typed=elections | good=typed
```
With "elections" typed and the file saved, both names change, and the search box still holds "elections", with the cursor in it.
:::
:::

After the save, React calls `SiteHeader` again, and it returns a whole new description of the header. React compares it with the last description, element by element:

| element | last description | new description | in the DOM |
| --- | --- | --- | --- |
| `<p>` | Welcome back, Mary | Welcome back, Mary Brooks | the text changes |
| `<span>` | Signed in as Mary | Signed in as Mary Brooks | the text changes |
| `<input>` | the search box | the search box | the same node stays |

So for this save, React changes two texts in the DOM and leaves every other node where it is. The `<input>` is the same DOM node it was before the save, so it still holds "elections", and the cursor still blinks in it. `innerHTML`, instead, throws away every node inside the header:

```chain caption="Why the search box loses 'elections' in one version and keeps it in the other, when the name changes to Mary Brooks."
!`header.innerHTML = '...'` -> every node inside the header is thrown away, and new ones are built from the string -> the new `<input>` is empty, and the focus goes back to the page
+the file saved with `'Mary Brooks'` -> React compares the new description with the last one -> two texts change; the `<input>` stays, with "elections" and the focus
```

The description is not the DOM: it is kept in memory as plain JavaScript objects that the browser never draws, which Lecture 3 shows. Because it has the shape of the DOM without being it, people often call it the **virtual DOM**. The React documentation describes what React does with it as "the minimal necessary operations": for this save, exactly two text changes. When the new description is the same as the last one, React changes no text at all. Lecture 15 gives each step of an update its name.

```tree dir=right caption="What happens to the search box when the name changes."
When the name changes, what happens to the typed text?
- !Our code rebuilds the header with `innerHTML` | a new, empty search box, and the focus is lost
- +React compares the new description with the last one | the same search box, still holding "elections"
```

## Putting the three together

The header as the three sections built it: `SiteHeader` describes every element, with no line that finds or changes one; the greeting and the corner both read `{userName}`, the single source of truth; and when the file is saved with `'Mary Brooks'`, React compares the new description with the last one and changes only the two names, so the search box keeps what the user typed:

**DO THIS:**

```jsx right
export default function SiteHeader() {
  const userName = 'Mary Brooks';
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as {userName}</span>
      <input placeholder="Search" />
    </header>
  );
}
```

The two plain JavaScript habits of this lecture, marked in red: setting the greeting by hand and never naming the corner, so the corner keeps "Signed in as Mary" after the name changes (line 3); and rebuilding the header with `innerHTML`, so the search box is emptied of "elections" and loses the focus (lines 7 to 10):

**DO NOT DO THIS:**

```js wrong bad="3,7-10"
function updateHeaderUser(name) {
  const greeting = document.getElementById('greeting');
  greeting.textContent = 'Welcome back, ' + name;
}
function rebuildHeader(name) {
  const header = document.getElementById('header');
  header.innerHTML =
    '<p>Welcome back, ' + name + '</p>' +
    '<span>Signed in as ' + name + '</span>' +
    '<input placeholder="Search">';
}
```

And the same mistake inside React: the corner typed as fixed text, so it keeps "Signed in as Mary" while the greeting shows "Mary Brooks" (line 6):

**DO NOT DO THIS:**

```jsx wrong bad="6"
export default function SiteHeader() {
  const userName = 'Mary Brooks';
  return (
    <header>
      <p>Welcome back, {userName}</p>
```

## For the interview

- **What is React?** A JavaScript library for building user interfaces out of components. It can run a whole page, or only one part of a page that already exists.
- **How does its model differ from plain JavaScript DOM scripting?** In plain JavaScript, our code finds each element and changes it by hand: that is imperative, and an element the code forgets keeps old data, as the corner kept "Mary". In React, a component describes what the page shows for the current data, and React builds and changes the DOM to match: that is declarative. Each value lives in one variable that every place reads, a single source of truth, so no place keeps an old copy.
- **Does React rebuild the page each time the data changes?** No, that is the classic trap. React calls the component again and compares the new description with the last one; on our header it changed exactly two texts, and the search box, the same node as before, kept "elections" and the focus. People call the compared description the virtual DOM.
- **Is React faster than changing the DOM by hand?** No, and that is not its job. React changes the DOM with the same browser methods a script uses, and a script that sets one text node does that work with less code to run. React's gain is that our code no longer writes, or forgets, the update steps.
- **Does React stop an old name from showing anywhere?** Only where the JSX reads the variable. A name typed into the markup as fixed text keeps the old value, even in React.
- **Can I still call `document.getElementById` inside a component?** On the component's first run, its own elements are not on the page yet, so the call returns `null`; Lecture 10 shows the error this causes. For the few jobs that need one particular element, such as moving the cursor into a search box, React gives a way to reach it without changing what it shows (Lecture 30).

## Where you will meet this

- The signed-in name: shown in a greeting, in the account menu, and beside each comment the user wrote. Each place reads one variable, so a name change reaches all of them at once.
- A cart count: shown in the header and again on the checkout button. Both read the same count, so the button never promises more items than the cart holds.
- A search results page: "Results for elections" changes above the list while the same word stays in the search box, because React changes the heading and leaves the box, with its cursor, as the user left it.
- An unread count: shown in the browser tab and beside the inbox. One variable feeds both, so the tab and the inbox always agree.
