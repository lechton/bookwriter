# Lecture 1: What is React and the Declarative Model
> INTERVIEW QUESTION | ❱ CORE | What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

## Example: a shopping cart

An online shop shows a small cart on its pages. The cart says how many items it holds, and its button offers to buy them. Here is the cart with 2 items in it:

```page caption="The cart with 2 items. Outlined in green: the two places that show the count."
card: title=Items: 2 | button=Buy 2 items | good=title,button
```

Look closely: the count, 2, appears twice, once in the line "Items: 2" and once on the button. Now the shopper clicks "Add to cart" on another product, and the cart holds 3 items. Here is the cart before and after that click:

::: row arrows caption="The shopper adds a third item. Outlined in green: the two places that must show the new count."
::: col title="Before the click: 2 items" tone=plain
```page size=mini
card: title=Items: 2 | button=Buy 2 items
```
With 2 items in the cart, both places show 2.
:::
::: col title="After the click: 3 items" tone=good
```page size=mini
card: title=Items: 3 | button=Buy 3 items | good=title,button
```
With 3 items in the cart, both places show 3.
:::
:::

One click changes one piece of data, the count, and two places on the page must follow it. If the button kept "Buy 2 items" while the cart holds 3, it would offer the shopper the wrong purchase. Every website meets this question in some form: when the data changes, how does the page change with it? React's answer is to describe the page from the data and let React change the page to match. That is the topic of this lecture: what is React, and how does its way of building a page differ from changing the page by hand with plain JavaScript?

## Two ways to change the page

> [!FACT] The browser does not draw the HTML file directly. It builds one object in memory for every tag, nested the way the tags are nested, and draws the screen from them. Together these objects are the **DOM**, the Document Object Model, and each one is a **DOM node**. So to change what the screen shows, something must change the DOM.

So when the cart gets a third item, something must change the two DOM nodes that show the count. There are two ways to do it:

```tree caption="Two ways to change the page when the count changes: give a command for each element, or describe the result."
Change the page when the count changes
- Imperative programming | our code finds each element that shows the count and sets its text, one command per element
- Declarative programming | our code describes what each element shows for the count, and React changes the DOM to match
```

> [!FACT] In plain JavaScript, `document.getElementById('items')` asks the browser for the DOM node whose `id` is `items`. Setting that node's `textContent` replaces the text inside it, and nothing else on the page changes.

In **imperative programming**, our code gives the browser each command itself: find this element, set its text. In plain JavaScript, the line "Items: 2" gets its new count like this:

```js title="Imperative: plain JavaScript"
const items = document.getElementById('items');
items.textContent = 'Items: 3';
```

In **declarative programming**, our code says what each element shows, and something else makes the DOM match. In React, the line is written once, with a place for the count, and when the count is 3, React makes the line show "Items: 3":

```jsx title="Declarative: React"
<p>Items: {count}</p>
```

**React** is a JavaScript library for building user interfaces out of components, and it is declarative.

Why does the difference matter? Imperative code is fine for one element that changes in one place, such as a clock in the corner of a page. But the count shows in two places, so imperative code needs a command for each place on every change, and a place with no command keeps the old count, as section 1 shows. Declarative code has no command to forget: each place says what it shows, and React works out the changes.

## The React project for this lesson

The rest of the lecture builds the cart in React. In React, a page is built from **components**: a component is a JavaScript function whose name starts with a capital letter and which returns the markup for one piece of the page. Lecture 2 gives the rules for writing one. This lecture has one component, `Cart`, inside a small project prepared for the lesson. Three files of that project matter:

| file | what it holds |
| --- | --- |
| `index.html` | the page the browser loads; its body holds one empty element, `<div id="root"></div>` |
| `src/main.jsx` | the code that tells React to show `Cart` inside that empty element; Lecture 9 explains how |
| `src/Cart.jsx` | the cart component this lecture writes |

Here is `Cart`, with the count written once, at its top:

```jsx title="Cart.jsx"
export default function Cart() {
  const count = 2; // the count, written once
  return (
    <section>
      <p>Items: {count}</p>
      <button>Buy {count} items</button>
    </section>
  );
}
```

Each piece of this code has a name:

| in the code | what it is |
| --- | --- |
| `const count = 2` | a **local variable**: a name for a value, inside this function |
| the markup after `return` | **JSX**: it looks like HTML, but it is JavaScript, as Lecture 3 explains |
| `{count}` | **curly braces** in JSX: a place where a JavaScript value goes, so the page shows 2 there |
| `export default` | lets another file, here `main.jsx`, use this function, as Lecture 8 explains |

What `Cart` returns is a **description** of the cart: it says what each element shows, and React builds the real DOM nodes from it. Our code never calls `Cart`; React calls it.

How does the count change in this lecture? A value that changes after a click needs state, which Lecture 14 teaches. Until then, the count is written in the file, and we play the shopper's click ourselves: we change `2` to `3` in `Cart.jsx` and save. The project runs with the command `npm run dev`, which starts a **dev server**: a small program on our computer that sends the project to the browser while we work. Each time we save a file, the dev server sends the new code to the open page, and React updates the page without reloading it.

## Three steps in the life of `count`

The lecture follows the count through three steps, one section each:

```tree caption="The three steps of count, and the idea each one teaches."
The life of one value, `count`
- Declarative programming | `Cart` describes what each element shows, and React builds the DOM from it
- A single source of truth | the line and the button both read `{count}`
- Virtual DOM comparison | when `count` changes, React changes only the new number
```

Each step needs the one before it. Two places can share the count only once the cart is described from it. And the change can be shown whole only once both places read the same variable: then one save changes both, and section 3 adds a text box to show what React leaves alone.

## 1. Declarative programming: Cart describes the cart, and React builds it

```tree size=mini here="Declarative programming"
The life of one value, `count`
- Declarative programming
- A single source of truth
- Virtual DOM comparison
```

> [!PRINCIPLE]
> **Principle 1: Declarative programming: describing what the page shows, not how to change it**
>
> We control the page by describing what it shows from data.
>
> A component returns JSX that says what each element shows for the current data. React calls the component and builds the DOM from it.
>
> We never find and change the page's elements by hand. Notice: every element our code changes by hand is an element our code can forget.
>
> *We should do this:*
>
> ```jsx
> function Cart() {
>   const count = 3;
>   return <p>Items: {count}</p>; // React builds the <p> from this
> }
> ```
>
> *We should not do this:*
>
> ```js
> const items = document.getElementById('items');
> items.textContent = 'Items: 3'; // **PROBLEMATIC:** sets this one element; the button keeps "Buy 2 items"
> ```

Before the shop moved to React, its cart was plain HTML, and a script changed it by hand. This section sets that page against `Cart`:

```hierarchy caption="Section 1: the same cart, changed by hand or described in Cart."
Cart | holds: `count = 2` | here: describes the whole cart from the count
notes:
On the old plain HTML page, the line and the button each have an `id`, and a script sets the text of each element it names.
In React, `Cart` returns the cart's markup, with `{count}` in the line and on the button.
We want: the count right in both places, and no line of our code that finds or changes an element.
```

The old page writes the cart in HTML, with an `id` on each place that shows the count:

```html title="old-cart.html (the plain HTML page)"
<p id="items">Items: 2</p>
<button id="buy">Buy 2 items</button>
```

When the shopper adds a third item, the old page's script runs these two lines. They find the line "Items: 2" by its `id` and set its text:

```js title="Plain JavaScript, after the third item"
const items = document.getElementById('items');
items.textContent = 'Items: 3';
```

After the script runs, the old page shows this cart:

```page caption="The old plain HTML page after the script, with 3 items in the cart. Look at the button."
card: title=Items: 3 | button=Buy 2 items | bad=button
```

The script changes exactly the node it names, and it names only the line. The button, never named, still says "Buy 2 items" while the cart holds 3. Every new place that shows the count needs one more command in the script, and one forgotten command is one place with an old count.

In React there is no such script. `Cart` returns what each element shows, and React builds the DOM nodes from it. The proof is in the browser:

> [!FACT] To see the DOM, open the browser's developer tools and choose the **Elements panel**. It shows the DOM nodes the page has right now, which is not always what the HTML file holds.

::: row caption="With npm run dev running and Cart returning the cart: the file the browser loads, and the DOM it ends up with."
::: col title="The file `index.html`" tone=plain
```html
<body>
  <div id="root"></div>
</body>
```
In the file, the root is empty: no line and no button.
:::
::: col title="The Elements panel" tone=good
```dom title="Elements panel"
<div id="root">
*  <section>
*    <p>Items: 2</p>
*    <button>Buy 2 items</button>
*  </section>
</div>
```
In the page, the root holds the whole cart. React built every marked node from what `Cart` returned.
:::
:::

A search of our code finds no `getElementById` and no `textContent`. No line names an element, so no element can be forgotten. Section 2 changes the count and shows what that buys.

## 2. A single source of truth: every place reads `{count}`

```tree size=mini here="A single source of truth"
The life of one value, `count`
- Declarative programming
- A single source of truth
- Virtual DOM comparison
```

> [!FACT] Inside JSX, a comment is written in curly braces, `{/* like this */}`. It shows nothing on the page; the code below uses it to point at a line.

> [!PRINCIPLE]
> **Principle 2: Single source of truth: describing many places from one value**
>
> When one value appears in many places, we keep it in one variable.
>
> Every place reads that variable in curly braces, so every place is built from it.
>
> We never type a copy of the value into the markup. Notice: a typed copy is fixed text, so it keeps the old value when the variable changes.
>
> *We should do this:*
>
> ```jsx
> function Cart() {
>   const count = 3;
>   return (
>     <section>
>       <p>Items: {count}</p>
>       <button>Buy {count} items</button> {/* reads count, like the line */}
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Cart() {
>   const count = 3;
>   return (
>     <section>
>       <p>Items: {count}</p>
>       <button>Buy 2 items</button> {/* **PROBLEMATIC:** a 2 typed by hand never changes */}
>     </section>
>   );
> }
> ```

Section 1 described the cart in `Cart`. Now the shopper adds a third item, and the count must change in both places:

```hierarchy caption="Section 2: the count changes from 2 to 3, and two places show it."
Cart | holds: `count`, changed from `2` to `3` | here: describes the line and the button
notes:
We play the shopper's click: we change `count` to `3` in the file and save.
In the version below, the line reads `{count}`, but the button was copied from the old HTML page with its 2 typed in.
We want: after the save, both places show 3.
```

When the cart moved from the old HTML page into React, the line got its `{count}`, but the button was copied as it was, with "Buy 2 items" typed into it. The slip is easy to miss: the page looks right for as long as the count is 2. Here is that version after we change line 2 to `3` and save:

```jsx title="Cart.jsx" bad="6"
export default function Cart() {
  const count = 3; // changed from 2, then saved
  return (
    <section>
      <p>Items: {count}</p>
      <button>Buy 2 items</button> {/* copied from the old HTML page */}
    </section>
  );
}
```

The save makes React call `Cart` again, and the page shows this cart:

```page caption="After the save, with count set to 3. Look at the button."
card: title=Items: 3 | button=Buy 2 items | bad=button
```

React makes each element show exactly what the JSX describes, and the JSX describes two different counts:

| place | written in the JSX | what the page shows after the save |
| --- | --- | --- |
| the line | `Items: {count}` | "Items: 3", read from the variable |
| !the button | `Buy 2 items`, typed by hand | "Buy 2 items", the same text as before |

React did nothing wrong: the button never asked for the variable. The fix is line 6, where the button reads the same variable as the line:

```jsx title="Cart.jsx" good="1" startLine="6"
      <button>Buy {count} items</button>
```

Now both places are built from one variable, and after the save both show the new count:

```page caption="After the fix and the save, with count set to 3. Both places show 3."
card: title=Items: 3 | button=Buy 3 items | good=title,button
```

Keeping each value in one place, which every part of the page reads, is called a **single source of truth**. A third place that shows the count, such as a small number on a cart icon, adds one more `{count}` and no update code. Lecture 23 uses the same idea when two components share a value that changes.

## 3. Virtual DOM comparison: React changes only the new number

```tree size=mini here="Virtual DOM comparison"
The life of one value, `count`
- Declarative programming
- A single source of truth
- Virtual DOM comparison
```

> [!FACT] In plain JavaScript, setting an element's `innerHTML` throws away every node inside it and builds new nodes from a piece of HTML text. `textContent` only replaces the text inside one node.

> [!PRINCIPLE]
> **Principle 3: The virtual DOM: describing the page again when the value changes**
>
> When the value changes, React calls the component again and gets a new description.
>
> React compares the new description with the last one, element by element. It changes only the text that is new.
>
> Every other node stays where it is, so a text box keeps what the user typed. Notice: rebuilding the elements with `innerHTML` makes new nodes, and the typed text is gone.
>
> *We should do this:*
>
> ```jsx
> function Cart() {
>   const count = 3; // changed from 2, then saved
>   return (
>     <section>
>       <p>Items: {count}</p> {/* only the number changes */}
>       <input placeholder="Note to the shop" /> {/* the same node: keeps what was typed */}
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```js
> const cart = document.getElementById('cart');
> cart.innerHTML = `
>   <p>Items: 3</p>
>   <input placeholder="Note to the shop">
> `; // **PROBLEMATIC:** builds new nodes, so the typed note is gone
> ```

Section 2 gave the count one variable, so one save changes both places. Now the cart gets one more part: a text box where the shopper can write a note to the shop. Say the shopper has typed "Gift wrap, please" into it, and then adds a third item:

```page caption="The cart with its note box, before the third item. The shopper has typed a note."
card: title=Items: 2 | box=Gift wrap, please | button=Buy 2 items | good=box
```

On every save, `Cart` returns a description of the whole cart, the note box included. So what happens to the note?

```hierarchy caption="Section 3: the count changes while a note is typed in the box."
Cart | holds: `count`, saved as `3` | here: returns a new description of the whole cart
notes:
On the open page, "Gift wrap, please" is typed in the note box.
The file is saved with `count = 3`, so React calls `Cart` again, and it returns the whole cart again, with 3 in it.
We want: both places show 3, and the box still holds "Gift wrap, please".
```

Here is `Cart` with the note box, saved with the new count:

```jsx title="Cart.jsx" good="6"
export default function Cart() {
  const count = 3; // changed from 2, then saved
  return (
    <section>
      <p>Items: {count}</p>
      <input placeholder="Note to the shop" />
      <button>Buy {count} items</button>
    </section>
  );
}
```

A developer coming from plain JavaScript may expect React to do what many scripts do: rebuild the whole cart from a piece of HTML text with the new count in it. Here is such a script, on the old page:

```js title="Plain JavaScript: rebuild the cart with the new count" bad="2-6"
const cart = document.getElementById('cart');
cart.innerHTML = `
  <p>Items: 3</p>
  <input placeholder="Note to the shop">
  <button>Buy 3 items</button>
`;
```

The script and React give two different carts. Compare the two note boxes:

::: row caption="With 'Gift wrap, please' typed in the note box, the count changes to 3. Both versions show 3 in both places; only the note box differs."
::: col title="Plain JavaScript: rebuilt with `innerHTML`" tone=bad
```page size=mini
card: title=Items: 3 | box=placeholder:Note to the shop | button=Buy 3 items | bad=box
```
With the note typed and the cart rebuilt, both places show 3, but the note box is a new, empty `<input>`.
:::
::: col title="React: `Cart` saved with `count = 3`" tone=good
```page size=mini
card: title=Items: 3 | box=Gift wrap, please | button=Buy 3 items | good=box
```
With the note typed and the file saved, both places show 3, and the box still holds "Gift wrap, please".
:::
:::

After the save, React calls `Cart` again and gets a whole new description of the cart. It compares it with the last description, element by element:

| element | last description | new description | in the DOM |
| --- | --- | --- | --- |
| `<p>` | Items: 2 | Items: 3 | the text "2" becomes "3" |
| `<input>` | the note box | the note box | the same node stays, with the note in it |
| `<button>` | Buy 2 items | Buy 3 items | the text "2" becomes "3" |

So for this save, React makes two text changes, and nothing else is rebuilt. Even "Items:" and "items" are left alone, because `{count}` is its own piece of text. The `<input>` is the same DOM node it was before the save, so it still holds the note. `innerHTML`, instead, throws away every node inside the cart and builds new ones, and a new `<input>` starts empty.

The description is not the DOM: it is kept in memory as plain JavaScript objects that the browser never draws, as Lecture 3 shows. Because it has the shape of the DOM without being it, people often call it the **virtual DOM**. The React documentation describes what React does with it as "the minimal necessary operations": for this save, two text changes. When the new description is the same as the last one, React changes no text at all. Lecture 15 gives each step of an update its name.

## Putting the three together

The cart as the three sections built it. `Cart` describes every element, with no line that finds or changes one. The line and the button both read `{count}`, the single source of truth. And when the file is saved with `count = 3`, React compares the new description with the last one and changes only the two numbers, so the note box keeps what the shopper typed:

**DO THIS:**

```jsx right
export default function Cart() {
  const count = 3;
  return (
    <section>
      <p>Items: {count}</p>
      <input placeholder="Note to the shop" />
      <button>Buy {count} items</button>
    </section>
  );
}
```

The two plain JavaScript habits of this lecture, marked in red. The first script sets the line by hand and never names the button, so with 3 items in the cart the button still says "Buy 2 items" (line 2). The second rebuilds the cart with `innerHTML`, so the note box comes back empty (lines 4 to 8):

```js wrong bad="2,4-8"
const items = document.getElementById('items');
items.textContent = 'Items: 3';

cart.innerHTML = `
  <p>Items: 3</p>
  <input placeholder="Note to the shop">

```

And the same mistake inside React: the button's count typed as fixed text, so with `count` set to 3 the button still says "Buy 2 items" (line 7):

**DO NOT DO THIS:**


## For the interview

- **What is React?** A JavaScript library for building user interfaces out of components. It can run a whole page, or only one part of a page that already exists.
- **How does its model differ from plain JavaScript DOM scripting?** In plain JavaScript, our code finds each element and changes it by hand: that is imperative, and an element the code forgets keeps old data, as the button kept "Buy 2 items" while the cart held 3. In React, a component describes what the page shows for the current data, and React builds and changes the DOM to match: that is declarative. Each value lives in one variable that every place reads, a single source of truth, so no place keeps an old copy.
- **Does React rebuild the page each time the data changes?** No, that is the classic trap. React calls the component again and compares the new description with the last one. On our cart it made two text changes, "2" to "3", and the note box, the same node as before, kept the shopper's note. People call the compared description the virtual DOM.
- **Is React faster than changing the DOM by hand?** No, and that is not its job. React changes the DOM with the same browser methods a script uses, and a script that sets one piece of text does that work with less code to run. React's gain is that our code no longer writes, or forgets, the update steps.
- **Does React stop an old value from showing anywhere?** Only where the JSX reads the variable. A value typed into the markup as fixed text keeps the old value, even in React.
- **Can I still call `document.getElementById` inside a component?** On the component's first run, its own elements are not on the page yet, so the call returns `null`; Lecture 10 shows the error this causes. For the few jobs that need one particular element, such as moving the cursor into a text box, React gives a way to reach it without changing what it shows (Lecture 30).

## Where you will meet this

- The signed-in user's name: shown in the greeting at the top and again in the account menu. Both read one variable, so a name change reaches both at once.
- An order total: shown in the order summary and on the "Pay" button. Both read one total, so the button never asks for a different amount than the summary shows.
- A like count: shown under a post and again on the post's share card. One variable feeds both, so they always agree.
- A comment box under an article: the comment count above it changes while a half-written comment stays in the box, because React changes the count's text and leaves the box as the reader left it.
