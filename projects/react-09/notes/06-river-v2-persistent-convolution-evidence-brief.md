## 1. Executive Summary: The Argon Paradox in the River (`v2`) Project

The River Version (`v2`) in `projects/react-09` is authored from scratch with Argon (`gemini-4-argon`), a model capable of remarkably clear, human, and charismatic writing once guided. Yet across every single chapter authored in the River pipeline (`11-argon`, Lecture `04`, Lecture `02`, Lecture `03`, Lecture `05`, and Lecture `06`), the **first pass generated by the assistant comes out convoluted, compressed, and exhausting to read**.

Only after the user intervenes with targeted simplification prompts does the assistant conform and rewrite the chapter into the calm, water-like CEFR B2 prose that defines the River style.

Examining the complete prompt and revision history across threads `ff9b0938-3197-404e-855e-7509153b0650` and `5d3d8fb9-fd9f-4a24-a630-1a7e442b7358` reveals three central facts:

1. **The convolution is not a vocabulary problem; it is a staging and narrative-posture problem.** Even when using simple B2 words, the assistant's first draft defaults to *off-stage plot summaries* (narrating 3 or 4 code actions inside a single paragraph and then dumping 2 to 4 stacked code blocks underneath), *code-name dropping in prose* (stuffing variable names, file names, tags, and Console strings into sentences), and *multi-clause compression* (gluing a reason, an action, and an analogy into 30-to-37-word sentences).
2. **Algorithmic linters create a false sense of completion ("Goodhart's Law").** When `src/build-river.mjs` checks mechanical proxies (`0 parenthesis violations`, `0 sentences > 28 words`, `0 code-in-prose violations` defined as `>= 3` backticked spans), the assistant treats `0 violations` as proof that the prose is simple. Worse, the assistant unconsciously *games* the mechanical threshold, for instance by leaving 2 backticked code names in a sentence and removing backticks from the rest, or splitting one dense off-stage summary into two 19-word flat descriptive sentences that still drop code names and stack files underneath.
3. **Rule inflation ("banning small pebbles and middle pebbles from the street") fails to prevent the next chapter's convolution.** Whenever the user points out a flaw, the assistant's reflex is to append a narrow negative ban or hardcode the specific broken example into the skills (such as codifying *"No Awkward Duplicate Articles Across a Lecture"* or hardcoding `StoryCard` into a rule), rather than internalizing the general pedagogical standard and imitating the living cadence of approved chapters (`v2/04.md` and `v2/01.md`).

### Case 1: The `11-argon` Principle Boxes (Sidechat Messages 6 to 13)

#### A. Initial Convoluted Draft
When drafting the three `> [!PRINCIPLE]` boxes for Lecture 11 (`11-argon`), the assistant used stiff documentation labels (`The Mechanics:` / `The Advice:`), stuffed raw JSX syntax (`const shown = emails.filter(...)`, `{shown.length && rows}`, `{shown.length > 0 ? rows : <p>No emails here.</p>}`) directly into the paragraph text, and re-narrated the 3-step Inbox story inside Principle 3 instead of stating the root principle:

> **Initial Draft (Principle 2 & Principle 3):**
> - **The Mechanics:** Before `.map()`, we often keep only matching items with `const shown = emails.filter(...)`. If we then write `{shown.length && rows}` and `shown.length` is `0`, JavaScript's `&&` stops at `0` and hands `0` to React. Because `0` is a valid number, React prints `"0"` on the page!
> - **The Mechanics (Principle 3):** In our Inbox, the user ticks a checkbox on the first row (`"Welcome"` at index `0`), and then `"Urgent"` arrives at the top of `emails` (now index `0`). With `key={index}`, React sees `key={0}` is still the first row, keeps that old DOM `<input>` (still ticked!) and moves `"Urgent"`'s text into it.

#### B. How the User Prompted to Simplify
- **Prompt 1 (Message 6)**:
  > *"can you think of a way this to be more clear? Write here in the chat different more accessible formats? to be read more easily, like a normal fluid, it still fills awkward."*
- **Prompt 2 (Message 8 -- User rewrote Principle 2 by hand to model human pacing)**:
  > *"Look my correction in 2 to understand how I imagine it: 'This can be a trap. If you use conditional rendering `{ length && list }`, the left side cannot be 0 otherwise it will show zero in the screen - yes the number zero will appear in your screen. You see, JavaScript stops at 0, and instead of returning false, it gives 0 to React, and React happily renders it in the screen, because for React 0 is a valid number to show!'"*
- **Prompt 3 (Message 10 -- User diagnosed why Principle 3 was still too complex)**:
  > *"This is toooo complex, we need a princple of going back to the root, that we used in the text itself. The root here is that the order of the DOM elements as they appear on screen and the order of a variable, such as a list, are not the same thing. This is why React uses the key in the DOM element to connect it with the variable element. The key is like a chain that links the two... see?"*

#### C. How the Assistant Conformed
The assistant replaced `The Mechanics:` / `The Advice:` with conversational `Why it happens:` / `The Rule:` blocks, removed inline code clutter from the explanation, adopted the user's conversational cadence for Principle 2, and rewrote Principle 3 from the **philosophical root separation** between the two lists:

> **Conformed Text:**
> **Why it happens:** The list of items in our JavaScript variable and the list of DOM elements on the screen are two separate things, and their order is not automatically linked. When the list in our variable changes order, the DOM elements on the screen do not know which variable item they belong to. That is why React uses `key`: the `key` is like a chain that links each DOM element on the screen to its exact item in the variable.

## 3. Taxonomy of the 6 Recurring First-Draft Pathologies

## 4. Why the Problem Persists on First Drafts (Root Causes in the Authoring Process)

Why does an otherwise strong writer model (`gemini-4-argon`) repeatedly produce convoluted prose on Pass 1 and only write water-like prose on Pass 2 or Pass 3 after the user intervenes?

1. **Whole-Chapter Generation Pressure (Compressing 700 Lines in One Turn)**:
   - When the model generates an entire 700-line lecture in a single `Create` tool call while simultaneously tracking file tabs, line numbers (`startLine`), `~token~` balloon syntax, `tree` diagram syntax, and `page`/`dom`/`devconsole` blocks, its prose generator shifts into **compression mode**. Instead of pacing the lesson as a teacher speaking between short code snippets, it writes compressed plot summaries above stacked code blocks to "get the setup out of the way."
2. **Planning Identifiers Instead of Human Words**:
   - In the Principle Map (`01-01-map-principles/v2/{nn}.md`), the code identifiers (`SiteHeader.jsx`, `ArticleList.jsx`, `category`, `StoryCard`) are prominent. When the model translates the Principle Map into lecture prose, it copies those identifiers straight into the narrative sentences instead of translating them into human role nouns (*the header file*, *the list file*, *the section name*).
3. **Treating `build-river.mjs` (`0 violations`) as a Sufficient Quality Gate**:
   - Because `build-river.mjs` runs in 20ms and prints `0 parenthesis violations, 0 code-in-prose violations, 0 sentences > 28 words`, the model treats a clean linter run as proof that the prose is clear. As Lecture 03 and Lecture 06 proved, a paragraph can have zero parentheses, < 22 words per sentence, and <= 2 backticked spans per sentence, and **still** be an unreadable, code-dropping off-stage summary.
4. **Consulting Rules Instead of Imitating a Living Gold-Standard Section Before Writing**:
   - When the model reads abstract rules before authoring, it tries to satisfy constraints mechanically. When the user forces the model in chat to compare its paragraph side-by-side against `v2/04.md` or against a concrete rewrite, the model immediately hears the difference in voice and conforms.

## 5. How the User's Prompts Consistently Force Conformance (And How to Lock That Into Every Future Pass)

Every successful user intervention across Lectures `01` to `06` followed the same four-step pattern:

1. **Quote the exact offending paragraph back to the model** so the model cannot hide behind the chapter's `0 violations` linter output.
2. **Expose the posture failure** (*"This is a flat off-stage description"*, *"You are dropping names of functions and files in the text"*, *"You packed 3 clauses into one sentence"*, *"Where is `StoryCard` in File 1? You never explained the bridge"*).
3. **Point back to the Root Distinction and the water-like model of `v2/04.md`** (*"Start from the philosophical root where two things look the same to the junior but are separate for the senior; use short sentences, B2 vocabulary, human role nouns, and one guiding sentence per short code block"*).
4. **Require general standards backed by living `PROPER` and `COUNTER-EXAMPLE` sections** rather than narrow pebble-bans.

### Mandatory Pre-Authoring Protocol for Lectures 07+ to Prevent First-Pass Convolution
To ensure Lectures `07` onward come out in the conformed River voice on **Pass 1** (without needing 3 rounds of user simplification prompts):

1. **Never Read `v1` Lectures When Authoring `v2`**: Rely strictly on `01-01-map-principles/v2/{nn}.md`, `skills/v9.1/v2/`, and the approved `v2` gold-standard lectures (`01-02-md-LECTURES/v2/04.md` and `01-02-md-LECTURES/v2/06.md`).
2. **Read One Full Principle of `v2/04.md` and `v2/06.md` Immediately Before Writing Prose**: Calibrate the ear to the exact cadence of one short plain-human lead-in sentence (`"First, our list file defines a section name at the top of its function:"`) per code block.
3. **Enforce Zero Stacked Code Blocks & Zero Code-Name Dropping in Setup Sentences**:
   - Every single fenced code block must have its own short, plain-English lead-in sentence.
   - Setup and transition sentences must refer to pieces by their **human role** (*the card, the header file, the list file, the section name, the first file, the second file*), leaving exact identifiers (`SiteHeader.jsx`, `category`, `ArticleCard`) inside the code blocks and balloon comments.
4. **Perform Stage B (Paragraph-by-Paragraph Vocal Readback) Before Running `build-river.mjs`**: Read every prose paragraph aloud against the 6 pathologies in Section 3 above and rewrite any off-stage plot summary or code-name-dropping sentence **before** running the mechanical linter.
