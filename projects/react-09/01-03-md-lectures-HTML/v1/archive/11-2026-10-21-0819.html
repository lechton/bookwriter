Lecture 11: Rendering Lists and Keys

Interview Question

CORE

How do you render a list from an array, and why does React demand a key on every item?

  • Your article list writes one <ArticleCard /> tag by hand for every article on the site.
  • Thirty articles would mean thirty tags, and the console warns about a "key" as soon as you shorten them.
  • How does one array of articles become one card per article, and what is the key for?

A page shows many items of the same kind

A site shows the same kind of item many times: articles in a list, comments under an article, products in a shop. Every item has the same design, and only its data differs. So every React developer meets the same question: how does a component show one piece of markup for each item? Until now we have answered it by hand. ArticleList writes three <ArticleCard /> tags, one per article, and a fourth article would need a fourth tag.

This chapter turns the data itself into the cards. It follows one idea from the first question to the last: rendering a list, which means that an array of data becomes an array of elements, each with its own key. It goes in two stretches. First the items become elements: every item, then only some items. Then the elements get names: what a name does, and where it goes.

This lesson answers four questions:

  1. I have the articles in an array. How do I show a card for each without writing every tag?
  2. Each topic gets its own section with only its articles, and an empty section needs a message. How?
  3. The cards show fine. Why does React insist on a key?
  4. I put the key in, and the warning is still there. Where does it go?

  • Lecture 4: Curly braces in JSX: Braces hold an expression, code that gives back a value; a statement such as if or for cannot go inside them. An array of texts in braces shows its items one after another.

Three array methods take a function

An array has methods, functions that belong to it (Lecture 9), and three of them take a function and call it once for each item. forEach() only calls the function and gives back undefined. map() collects what the function gives back for each item into a new array of the same length. filter() keeps the items for which the function gives back true, in a new, often shorter array. length, a property with no parentheses, counts the items.

2articles.map(article => article.title);
3articles.filter(article => article.topic === 'Food');
One article
4articles.length;

map() turns every item into something new, filter() chooses which items stay, and forEach() gives back nothing at all.

Principles of React: Rendering Lists

Everything in this lesson comes down to one idea: rendering a list, which means that an array of data becomes an array of elements, each with its own key.

First, mapping, which means turning every item into an element: we call map on the array, and the arrow function gives back one element for each item.

Second, filtering, which means turning only some items into elements: we filter the array before we map it, and when nothing is left, we show a message instead of an empty space.

Third, keys, which means naming each element so React can tell the items apart: each key comes from the item's own id, so a new item at the top leaves every other item with its own element.

Fourth, the key's place, which means naming the element the map gives back: the key goes on the tag written inside the map, never inside the child component.

A map with curly braces shows no cards

When we open the page, the header and footer render, but no article cards appear on screen. The page shows an empty space where the catalog should be, and the browser Console panel reports no warnings or errors.

I have the articles in an array. How do I show a card for each without writing every tag?

ANSWER

The code does not do what we wanted. An arrow function with a curly brace creates a block body, requiring an explicit return statement to produce an element.

In plain JavaScript, developers often turn to loops when processing collections. But a standard JavaScript for loop is a statement, not an expression, so it cannot be placed inside JSX curly braces. The array method forEach() is an expression, but it always evaluates to undefined, so writing {articles.forEach(...)} inserts nothing into the JSX tree without any diagnostic message.

The array method map() solves this because it is an expression that returns a brand-new array. When JSX curly braces evaluate an array of React elements, React renders each element sequentially in order, matching how an array of text strings displays its values.

In the broken implementation, however, a curly brace immediately follows the arrow: article => { ... }. In JavaScript, this syntax defines a block body. A block body does not automatically return the expression inside it; it requires an explicit return keyword. Without return, the function body evaluates and returns undefined for each item. Consequently, articles.map() returns an array of three undefined values: [undefined, undefined, undefined] Because React renders undefined as empty visual output, the cards vanish completely.

The fix is to return the React element. We can wrap the returned element in parentheses directly after the arrow, or write an explicit return inside the block body:

ArticleList.jsx
7 {articles.map(article => (
8 <ArticleCard article={article} />
Given back for every article
9 ))}

With this change in place, all three cards appear on the page. Because the items lack keys, Chrome logs React's classic warning: Each child in a list should have a unique "key" prop which Question 3 addresses.

After =>, the expression is given back by itself; after => {, only return gives it back, and without it every item becomes undefined and nothing shows, with no message. Each topic gets its own section with only its articles, and an empty section needs a message. How?

ANSWER

The code does not do what we wanted. When the filtered array is empty, shown.length evaluates to 0, causing the logical AND operator to return 0 directly into the DOM.

The filtering strategy works correctly for the City topic. As introduced in our runway, filter() evaluates each item against a predicate test (article.topic === topic) and returns a new array containing only the items that pass. Calling map() afterwards transforms solely those retained items into React elements.

For the Sport category, however, zero articles match. The filter() method returns an empty array []. Calling shown.map() on an empty array would evaluate to another empty array, rendering an empty white gap below the heading without explaining the absence to the reader.

To avoid an empty gap, the code attempted to guard the list with {shown.length && shown.map(...)} But in JavaScript, the logical AND operator (&&) does not produce a boolean. When the left operand is falsy, && short-circuits and evaluates directly to the left operand. Because shown.length is the numeric value 0, the expression evaluates to 0. And as established in Lecture 10, React treats numbers as visible content, painting a literal 0 into the page markup.

The solution is to ask an explicit comparison question, shown.length > 0, and use a ternary expression to render an informative fallback message:

ArticleList.jsx
9 {shown.length > 0 ? (
10 shown.map(article => <ArticleCard article={article} />)
11 ) : (
12 <p>No {topic} articles yet.</p>
No Sport articles yet.
13 )}

With the ternary operator in place, the Sport section renders the heading "Sport" followed cleanly by the fallback paragraph: "No Sport articles yet."

QUESTION 3

A typed comment jumps to another article

We render ArticleList using articles.map() without specifying any key prop on <ArticleCard />. In the browser, Chrome logs a warning: Each child in a list should have a unique "key" prop Aside from this console message, the catalog appears to render properly.

With the dev server running, we type the phrase "Great news!" into the comment input box of "Rain Expected This Weekend", which currently sits as the second card on screen. We then open articles.js, prepend a brand-new breaking story, "Library Opens on Sundays" by James Smith with id: 4, to the very top of the array, and save the file:

articles.js
1export const articles = [
2 {
3 id: 4,
A new article, first in array
4 title: 'Library Opens on Sundays',
5 author: 'James Smith',
6 topic: 'City',
7 },

Vite pushes the update to the browser. The page re-renders to show four articles. But the comment "Great news!" has vanished from the weather card and now appears inside the comment box of "New Park Opens Today", which is now the second card on screen.

The cards show fine. Why does React insist on a key?

ANSWER

The code does not do what we wanted. Without unique keys, React matches elements across renders strictly by array position, mapping existing DOM nodes and their uncommitted input states to different items.

Developers frequently assume that React's key requirement exists merely to quiet compiler warnings. Because the initial visual layout looks identical with or without keys, the requirement can appear purely decorative. The bug reveals itself the instant the collection order changes.

When a component re-renders, React reconciles the newly returned element tree against the tree produced on the prior render pass. To avoid rebuilding the entire DOM from scratch, React attempts to preserve existing DOM nodes and updates only the attributes that changed.

Without keys, React relies on positional matching: it pairs the first new element with the first old element, the second with the second, and so on. When a new article is prepended at index 0, every existing article shifts down by one position. React inspects position 1. Previously, position 1 rendered "Rain Expected This Weekend". Now, position 1 holds "New Park Opens Today". React keeps the existing second DOM <article> container (along with the text "Great news!" typed into its <input> node), and merely overwrites its <h2> title and author paragraph to match the new park data. The user's typed comment is permanently attached to the wrong article.

A common junior impulse is using the array index as the key:

ArticleList.jsx
7 {articles.map((article, index) => (
8 <ArticleCard key={index} article={article} />
The position again
9 ))}

Passing key={index} silences the console warning, but the defect remains completely unchanged. Because the index is nothing more than the item's positional coordinate, React continues matching by array position, moving "Great news!" to the wrong article upon every prepend or reorder.

A key is a stable identifier that names each element across renders. By assigning key={article.id} using the item's unique database identifier, React tracks element identity regardless of layout position:

ArticleList.jsx
7 {articles.map(article => (
8 <ArticleCard key={article.id} article={article} />
Its own name
9 ))}

With key={article.id}, React recognizes that the card with key={2} has moved from position 1 to position 2. React moves the physical DOM node downward, preserving its internal input state, and constructs a fresh DOM node at position 0 for the new library story. The comment "Great news!" remains securely attached to "Rain Expected This Weekend".

Keys operate like file names inside a desktop directory: renaming or reordering files preserves each file's contents, whereas addressing files purely by their visual slot index causes contents to scramble whenever files are added. Generating dynamic keys on the fly using Math.random() breaks reconciliation completely: because the key changes on every render pass, React destroys and recreates every single DOM node on every update, wiping out all active focus and input values. Lecture 12 explores component purity, showing why generating values during a render breaks pure rendering.

The array index is acceptable as a key only for static collections that never insert, delete, or reorder, such as the fixed lines of a poem or hardcoded navigation links.

PRINCIPLE 3

Keys: naming each element so React can tell the items apart

We give each element a key from the item's own id, so React matches every item with the same element the next time the list is shown; the array index fits only a list that never changes order, and a key made while rendering fits nothing.

When a list is shown again, React matches each new element with one it already built, keeps it, and changes only what differs. Without a key, it matches by position: the first with the first. An item added at the top shifts every item down, so each old element receives the next item's data, and whatever the user typed stays behind under the wrong item. The index is the position again, so it fails the same way. A key taken from the item's own id names each element, and React matches by name: every item keeps its element, and only the new item gets a new one. A key made while rendering, such as a random number, matches nothing, so every element is built again.

The code does not do what we wanted. The key must be placed on the outermost JSX tag returned directly inside the map() call, not on elements nested inside the child component.

When developers inspect rendered HTML in developer tools, they see <article class="card"> repeating in the DOM tree, leading to the assumption that the <article> tag needs the key. But React reconciles element arrays where they are produced. In ArticleList, articles.map() returns an array of <ArticleCard> React elements. It is this array of child elements that React reconciles, and the console warning explicitly points to ArticleList as the culprit.

Inside ArticleCard, the <article> tag is simply a single root element returned by that component. It does not exist as an item within an array of siblings, so placing a key prop on it does not assist React's list reconciler.

The key belongs directly on the tag generated within the map() expression:

ArticleList.jsx
8 <ArticleCard key={article.id} article={article} />

Furthermore, React reserves key for internal reconciler identification. React never forwards the key attribute as a standard component prop. If a child component attempts to access props.key, JavaScript returns undefined, and React issues a console warning: key is not a prop. Trying to access it will result in undefined being returned If a child component requires the ID value for its own logic, pass it explicitly under a distinct prop name, such as <ArticleCard key={article.id} articleId={article.id} />

Similarly, hiding a key property inside an object and spreading it with {...props} triggers a compiler warning in modern React: A props object containing a "key" prop is being spread into JSX Always declare key directly and visibly on the JSX tag.

⚡ IN THE WILD

Why does the index work in so many tutorials?

In many online tutorials, you see lists rendered with key={index}, and nothing appears broken. The index fails only when an item is inserted, deleted, or reordered, and only when a DOM element holds uncommitted client-side state, such as text typed into an input or active focus. A fixed navigation menu with five static links never inserts items at the top and holds no user input, so its index keys never exhibit visible bugs. But on an article catalog where breaking news is saved at the top every day, index keys immediately scramble user comments. Lecture 61 returns to key strategies, examining sorting, deletion, and what makes a truly stable key.

If the key had remained on <ArticleCard>, React would log the list key warning because <li> elements are the direct children of the mapped array. With the key positioned on <li>, all four sections render clean semantic markup with zero console warnings.

A developer who comes from plain JavaScript expects a loop that writes the cards, && that hides an empty list, and a key that only quiets the console. In React 19, five articles became five cards from one tag, each topic section showed only its articles and a message when it had none, a new article at the top left every typed comment under its own article, and the key sat on the tag map() gave back. Each step applied one principle: every item became an element, only some items did, each element got its name, and the name sat on the right element.

Where you will meet this

  1. Every list on every site: Comments, search results, shopping cart items, and direct messages; each collection originates from an array, transforms via map(), and binds a key from each item's unique database identifier.
  2. Sections and categorized feeds: Pages that partition content by category or timestamp filter a single source array per category, displaying an empty state message when a partition contains zero items.
  3. Data fetched from servers: REST and GraphQL endpoints return database records containing immutable primary IDs, which map directly to React keys without client-side transformation.
  4. Lists holding active user input: Checkboxes, quantity inputs, and draft text fields; in these components, using index keys or omitting keys causes active user entries to jump to adjacent rows during sorting or deletion.
  5. Console key warnings in development: React's diagnostic key message points directly to the component whose map() call needs the key attribute, indicating exactly which file to inspect.

For the interview

The Interview Question: How do you render a list from an array, and why does React demand a key on every item?

1. The Hidden Signal

Interviewers ask this question to evaluate whether a candidate understands the fundamental connection between JavaScript expressions and React reconciliation. A junior developer views map() as boilerplate loop syntax and assumes keys exist merely to satisfy linter rules. A senior engineer explains that map() is an expression producing an array of React element descriptors, which React evaluates natively. More importantly, they demonstrate how React uses keys during the reconciliation phase to track component identity across renders, differentiating between node reuse, positional shifts, and structural destruction.

2. The Classic Trap

The classic interview trap is answering that "the array index is unique, so key={index} is always safe". The index is unique within a single render, but it reflects array position rather than data identity. When items are prepended, removed, or sorted, the index of every shifted item changes. Because React reconciles nodes by position when index keys are used, client-side input state (such as text typed into input fields, checkboxes, or focus) remains bound to the old DOM node and shifts to the wrong record. Another fatal trap is using key={Math.random()}, which generates a new key on every render, forcing React to destroy and rebuild every DOM node on every update pass.

3. What is Actually Going On

Writing articles.map(article => <ArticleCard key={article.id} article={article} />) provides React with an array of element objects, each stamped with an immutable identifier. When application data updates and triggers a re-render, React compares the new array of descriptors against the previous render tree.

By matching elements by key rather than array index, React recognizes when an existing element has merely changed its position. React moves the physical DOM node to its new slot in the tree, preserving its internal browser state and active input contents. Only genuinely new items trigger DOM node creation.

Without keys, React defaults to index-based reconciliation. When an item is added at index 0, React overwrites the properties of existing DOM nodes in place. The DOM node that held the second article receives the third article's text, while any text typed into its nested input elements lingers visibly on screen.

4. Where It Gets Tricky

Can a child component read its own key prop? No. React strips key during element creation. If a component reads props.key, JavaScript returns undefined and React logs a console warning. When a child needs its identifier, pass the value explicitly under a separate prop name, such as articleId={article.id}.

Where does the key go when a card is wrapped in a list tag? The key must sit on the outermost tag returned directly inside the map() callback. If you wrap <ArticleCard> in an <li>, the key moves to the <li>.

How do you key an item composed of multiple sibling elements without a container tag? Use a keyed Fragment: <Fragment key={article.id}>. The shorthand tag <> cannot receive attributes.

Must keys be globally unique across the whole page? No. Keys must be unique only among immediate sibling elements within the same array. Multiple independent lists may reuse the same IDs without collision.

When is the array index acceptable as a key? The index is safe only when the list is strictly static: it is never filtered, sorted, paginated, prepended, or deleted, and items contain zero internal state or form inputs.

Why does an empty list with length && render a zero? In JavaScript, 0 && <Component /> evaluates to the falsy left operand 0. React renders numbers into the DOM as visible text. Always write length > 0 to produce a clean boolean.

Glossary

  • Rendering a list: Transforming an array of data into an array of React element descriptors, typically via map(), so that React renders one element per item.
  • Arrow function: A concise function syntax (item => <Item item={item} />). An expression directly following the arrow returns automatically; a block body enclosed in curly braces requires an explicit return.
  • map(): A standard JavaScript array method that executes a callback on each item and returns a new array of transformed results of identical length.
  • filter(): A standard JavaScript array method that tests each item against a predicate and returns a new array containing only the items that returned true.
  • Key: A unique string or number attribute assigned to JSX tags returned in a list, used by React's reconciler to match element identity across render passes.
  • Index as key: Using an item's array position as its key. This defaults reconciliation to positional matching, causing form state and focus to attach to the wrong items upon reordering.

Summary

Rendering a list: an array of data becomes an array of elements, each with its own key

❒ Mapping: turning every item into an element
  • ALWAYS call map() inside the JSX, and give the element back right after =>, or with return after => {.
  • NEVER use forEach() or a for loop inside the braces; they give back nothing the page can show.
❒ Filtering: turning only some items into elements
  • ALWAYS call filter() before map() when only some items should show.
  • IF the filtered array can be empty THEN test length > 0 and show a message instead.
❒ Keys: naming each element so React can tell the items apart
  • ALWAYS take the key from the item's own id.
  • IF the list never inserts, deletes, or reorders THEN the index is a safe key; otherwise it moves typed text to the wrong item.
  • NEVER make a key while rendering, such as Math.random().
❒ The key's place: naming the element the map gives back
  • ALWAYS write the key on the tag written inside map(), directly, not inside a spread object.
  • IF the child needs the id THEN pass it again as a prop of its own; the child never receives key.
