Lecture 13: Responding to Events and Callback Props

Interview Question

CORE

How do you respond to user events like clicks and typing, and how do callback props communicate back to parents?

Imagine this scenario:

  1. You build an article feed where each card provides Read and Bookmark buttons.
  2. You write onClick={handleSelect()} on a button, but the function executes during page load and does nothing when clicked.
  3. How do you respond to user events like clicks and typing, and how do callback props communicate back to parents?

Interactive interfaces respond to user actions through event listeners

Every dynamic web application must respond when users interact with the screen. Readers click buttons to open stories, type search queries into input fields, select items from lists, and save articles for later reading. In traditional scripting and legacy HTML, developers wrote inline string handlers like onclick="handleClick()". In React, components are pure functions, and user interactions are handled declaratively by passing JavaScript function references to event props like onClick and onChange. React listens for browser events, wraps them in synthetic event objects, and executes the designated handler outside of the render cycle.

When developers begin adding interactivity to React components, they often bring imperative habits from classic JavaScript. In JSX, anything placed inside curly braces evaluates immediately while React calculates the component's output. Writing onClick={handleSelect()} with parentheses causes JavaScript to invoke handleSelect() right away during render. The function fires on initial page load before the user ever touches the mouse, and its return value (undefined) is passed to onClick, leaving the button unresponsive when clicked later. Furthermore, when nested components need to update application state, children cannot reassign parent variables directly; they must communicate upward through callback props.

This chapter answers five core questions. Why does calling a function inside JSX braces execute on page load instead of waiting for a click? How do we pass arguments to an event handler without invoking it during render? How does a child component notify its parent about an action without mutating props? Why does clicking a nested button also trigger parent click handlers, and how do stopPropagation and preventDefault differ? Why must interactive controls use native button tags instead of clickable divs?

Lecture 18 explores reading user input via e.target.value inside onChange handlers for complex objects. Lecture 40 explores React 19 <form action={...}>, which handles form submissions automatically without manual calls to e.preventDefault().

How React connects event props to handler functions

In Lecture 2 and Lecture 4, we saw that JSX curly braces evaluate JavaScript expressions immediately during the render phase. In standard HTML, event attributes like onclick expect a string of code to execute. In React, event listener props are written in camelCase, such as onClick, onChange, onKeyDown, and onSubmit. Instead of a string, React expects an actual JavaScript function value. When the user interacts with the rendered element, React receives the browser event and executes that function.

Function Reference Pattern
1function ActionButton() {
2 function handleClick() {
3 console.log('Button clicked');
Executes on user click
4 }
5 return <button onClick={handleClick}>Click</button>;
6}

The most critical distinction in React event wiring is passing a function reference versus calling a function. When you write onClick={handleClick}, you pass the function itself as an uncalled value; you tell React, "Hold this function reference and call it when the user clicks." If you add parentheses, onClick={handleClick()}, JavaScript executes handleClick right away while constructing the element tree.

Immediate Invocation Mistake
1function BrokenButton() {
2 return <button onClick={handleClick()}>Click</button>;
Fires during render
3}

The return value (typically undefined) is assigned to onClick, leaving the element with no click handler. Event handlers run outside of render, making them the safe and idiomatic home for side effects like logging, network requests, and future state updates.

How callback props pass actions upward without breaking unidirectional data flow

In Lecture 5 and Lecture 6, we established that React strictly enforces unidirectional data flow: data flows downward from parent to child through props, and props are strictly read-only. A child component cannot modify the parent's data or reassign variables in the parent's scope. If a child needs to report a user event to its parent, it cannot reach upward directly.

Callback Prop in Parent
1function Feed() {
2 function handleSelect(id) {
3 console.log('Selected article:', id);
Business logic in parent
4 }
5 return <ArticleCard id="art-1" onSelect={handleSelect} />;
6}

To allow children to communicate upward, React uses callback props. The parent component declares a handler function that knows what action to take (such as selecting a story). The parent passes that function downward to the child as a prop, conventionally prefixed with on (such as onSelect={handleSelect}).

Callback Wiring in Child
1function ArticleCard({ id, onSelect }) {
2 return <button onClick={() => onSelect(id)}>Read</button>;
Forwards id
3}

The child component receives the callback prop and attaches it to a native element's event prop, such as a <button onClick={...}>. When the user clicks the button, the child executes the callback, passing relevant data (like the story identifier) upward to the parent. In this way, data still flows down as props, but actions flow upward through function calls. Custom components (like <ArticleCard />) do not possess built-in DOM event listeners; placing onClick on a custom component merely passes a prop named onClick and does nothing unless the child explicitly attaches it to a native HTML element.

How browser events bubble and why stopPropagation differs from preventDefault

When a user interacts with a web page, the browser creates a native event object. React intercepts these native events at the root container and wraps them in a cross-browser SyntheticEvent object, conventionally passed to your handler as e. This event object provides standard properties such as e.target (the specific element that was clicked) and e.currentTarget (the element whose event handler is currently executing).

Event Propagation Control
1function CardActions({ onSave }) {
2 function handleSave(e) {
3 e.stopPropagation();
Stops click from bubbling to parent card
4 onSave();
5 }
6 function handleSubmit(e) {
7 e.preventDefault();
Prevents browser from reloading page
8 }
9 return <button onClick={handleSave}>Save</button>;
10}

In the browser DOM, events follow the bubbling mechanism: after an event fires on the innermost clicked element, it propagates upward through all parent elements in the document tree, triggering their event handlers in sequence. If a card contains a bookmark button, clicking the bookmark button fires the button's onClick, bubbles up to the card's onClick, and continues up to the container. To halt this cascade, call e.stopPropagation(). This tells the browser and React not to run event handlers on ancestor elements. In contrast, e.preventDefault() addresses browser default behaviors, such as preventing a <form> submission from reloading the page or preventing an <a> link from navigating. Calling e.stopPropagation() does not cancel default browser actions, and calling e.preventDefault() does not stop event bubbling; each call has a distinct, unrelated responsibility.

Why accessible interaction requires native button controls instead of generic tags

In the browser, interactive elements participate in keyboard navigation. Users navigating with a keyboard or assistive technology press the Tab key to cycle through interactive controls on the page. When an element receives keyboard focus, pressing Enter or Space activates it.

Semantic vs Generic Click Target
1function SafeAction({ onSelect }) {
Accessible: receives Tab focus and responds to Enter/Space
2 return <button type="button" onClick={onSelect}>Select</button>;
3}
4
5function UnsafeAction({ onSelect }) {
Inaccessible: skipped by Tab and ignores Enter/Space
6 return <div className="btn" onClick={onSelect}>Select</div>;
Skips keyboard
7}

React allows you to attach an onClick prop to any JSX tag, including generic tags like <div> or <span>. However, the browser does not treat generic tags as interactive. A <div> with onClick cannot receive keyboard focus via the Tab key, does not respond to Enter or Space key presses, and fails to announce an interactive role to screen readers. In contrast, a native <button> element is built into the browser with full keyboard focus support, standard key activation, and built-in accessibility roles. Developers should always use native <button> elements for clickable actions, using CSS to achieve any desired visual style.

QUESTION 1

Calling a handler in JSX braces executes on page load

A developer creates a publish button for an editorial workflow. They declare an event handler function inside the component and connect it to a native button element in the returned JSX:

Immediate Invocation Antipattern
1export default function PublishButton() {
2 function handlePublish() {
3 console.log('PUBLISH ran');
Runs during render
4 }
5 return (
6 <button onClick={handlePublish()}>
7 Publish Story
Parentheses invoke immediately
8 </button>
9 );
10}

When the page loads in the browser, the console immediately prints "PUBLISH ran" before the developer ever touches the mouse. When the developer clicks the button afterward, the console remains completely silent, and nothing happens.

Why did adding parentheses after handlePublish cause it to run during render instead of waiting for a user click?

ANSWER

The code does not do what we wanted. Adding parentheses invokes the function immediately while React calculates the component's output.

In React, JSX curly braces are an evaluation window into JavaScript. Any expression placed inside { ... } runs synchronously during the render phase. When JavaScript encounters handlePublish(), it executes the function right away while constructing the element tree. The function runs on page load, and its return value (undefined) is assigned to the onClick prop. When the user later clicks the button, React finds undefined and takes no action.

To fix this defect, remove the parentheses and pass the bare function name: <button onClick={handlePublish}> By passing the function reference without parentheses, React stores the function in memory and attaches it to the browser button element. The handler executes strictly when the user clicks the button.

Executing during render versus passing an uncalled function reference
Immediate invocation: onClick={handleClick()}

onClick receives: undefined
User clicks button: nothing happens (handler is undefined)

Function reference: onClick={handleClick}
Render: stores function reference without calling
onClick receives: function handleClick
User clicks button: React invokes handleClick() -> logs "PUBLISH ran"
PRINCIPLE 1

Pass the handler function to an event prop, not its result

function reference passing an uncalled function by name so React can run it later
immediate invocation calling a function during render by adding parentheses in JSX braces

An event prop like onClick takes a function to run later when the user acts. Curly braces evaluate their expression immediately during render. Writing parentheses like onClick={handleClick()} calls the function right away, and onClick receives what it returns, usually undefined. To run code on click, pass the function itself without parentheses: onClick={handleClick}.

How do I pass an item identifier to a handler without calling it during render?

ANSWER

The code does not do what we wanted. Writing openArticle(story.id) invokes the function during render for every item in the list.

Just as with handleClick(), writing openArticle(story.id) inside JSX braces causes JavaScript to execute the call immediately during the mapping loop. Each button's onClick prop receives undefined. When the user clicks the button, the handler is gone.

Wrapping the call in an arrow function creates a function that waits. React stores that function and calls it only when the user clicks, passing the arguments to your handler.

A developer splits their interface into modular components. The parent feed component NewsFeed tracks which story is selected, while an ArticleCard component renders each story's layout. The developer attaches an onClick prop directly to the custom component tag:

The Read button is in ArticleCard, but NewsFeed decides what opens. How does the card tell it?

ANSWER

The code does not do what we wanted. Custom components are JavaScript functions that do not attach DOM event listeners automatically.

Built-in HTML elements (like <button> or <input>) represent real browser DOM elements; React attaches native event listeners to them. In contrast, custom components (like <ArticleCard />) are JavaScript functions. Placing onClick on <ArticleCard /> does not attach an event listener to any DOM node. It merely passes a prop named onClick to ArticleCard. If ArticleCard never forwards that prop to a native element's event prop, the callback is completely ignored.

To communicate user actions from child to parent, use callback props. The parent defines the action logic in a handler function and passes it downward as a prop named after the application action, such as onSelect={handleSelect}. Inside ArticleCard, accept onSelect in props and wire it to a native element's event prop: <button onClick={() => onSelect(article.id)}>Read Story</button> When the user clicks the button, the child executes the callback, passing the article identifier upward to the parent.

QUESTION 4

Clicking a nested button triggers parent click handlers

An article card is designed so that clicking anywhere on the card opens the article view. Inside the card, the developer adds a secondary Bookmark button to save the story for later reading:

Nested Event Handlers
1export default function ArticleCard({ story, onOpen, onBookmark }) {
2 return (
3 <article className="card" onClick={() => onOpen(story.id)}>
4 <h3>{story.title}</h3>
5 <button onClick={() => onBookmark(story.id)}>
6 Bookmark
Bubbles to article click
7 </button>
8 </article>
9 );
10}

When the user clicks the Bookmark button, they expect the article to be saved. Instead, the console prints "button: bookmark" and immediately prints "card: open article". The article opens unexpectedly alongside the save action.

Why does clicking Save also open the article, and how do stopPropagation and preventDefault differ?

ANSWER

The code does not do what we wanted. Browser events bubble upward through the DOM hierarchy, triggering parent click listeners.

In the browser DOM, when an event occurs on a nested element, it executes that element's handler and then bubbles upward through each ancestor element in the tree. Clicking the Bookmark button runs its onClick, bubbles up to the <article> tag, and runs the card's onClick.

To prevent an event from triggering handlers on parent containers, call e.stopPropagation() on the event object inside the child's handler. This tells React and the browser to stop bubbling immediately. In contrast, e.preventDefault() stops default browser behaviors, such as preventing a link navigation or preventing a form submit from reloading the page. Calling e.stopPropagation() does not stop default actions, and calling e.preventDefault() does not stop event bubbling.

Event bubbling upward through ancestors versus stopping propagation
Default bubbling:
[Button] click -> fires button handler -> bubbles UP to [<article>]
Result: both button handler and card handler execute

Propagation stopped:
[Button] click -> calls e.stopPropagation() -> halts event
Result: button handler executes; ancestor card handler is silenced
PRINCIPLE 4

Use stopPropagation for parent handlers and preventDefault for browser actions

event bubbling the browser process where an event travels upward through ancestor elements
stopPropagation prevents an event from triggering handlers on ancestor elements
preventDefault cancels the browser default action without stopping event bubbling

When an element is clicked, the click bubbles upward through every parent element in the tree, running their onClick handlers too. Calling e.stopPropagation() stops the event from reaching parent elements. Browser default actions, like following a link or reloading on form submit, are separate: only e.preventDefault() stops them. Neither call does the other's job.

</button>

QUESTION 5

Using a div for click handling blocks keyboard users

A developer wants a custom visual design for an article selection control. To avoid browser default button styling, they attach an onClick handler to a generic <div> tag:

Clickable Div Antipattern
1export default function SelectControl({ onSelect }) {

The control works when clicked with a mouse. However, when an accessibility auditor navigates the page using the Tab key, the control is skipped completely. When the auditor places focus on an adjacent control and presses Enter or Space, the <div> does nothing.

Can I put onClick on a div and style it as I like?

ANSWER

The code does not do what we wanted. A div cannot receive keyboard focus or Enter and Space key activation.

React permits attaching an onClick listener to any HTML element, but the browser enforces interactive standards. A generic <div> has no semantic role: the browser does not include it in the Tab focus ring, and pressing Enter or Space while adjacent to it does not fire a click event. Screen readers do not announce it as a button, making it completely invisible to users relying on assistive technology.

To build accessible interfaces, always use a native <button> element for interactive click actions: <button type="button" onClick={handleSelect}>Select Story</button> Native buttons possess built-in keyboard focus support, automatically respond to Enter and Space keystrokes, and communicate an interactive role to screen readers. Developers can easily remove browser default styles using CSS resets while retaining complete accessibility.

Where you will meet this

  1. Design System Component Libraries: Component libraries build buttons, dialogs, and toggles that accept custom callback props (onPress, onToggle, onDismiss) and wire them internally to native elements while managing propagation.
  2. Data Tables and List Feeds: Rendering collections of items where row selection, deletion, or expansion requires passing row identifiers upward via inline arrow functions without running during render.
  3. Modal Dialogs and Dropdown Menus: Nested popup menus and overlay backdrops require e.stopPropagation() so clicking inside the modal content does not trigger the backdrop's dismissal click handler.
  4. Form Handling and Custom Inputs: Intercepting form submissions with e.preventDefault() to stop full-page browser reloads and handling onChange events across input fields.

For the interview

The Interview Question: How do you respond to user events like clicks and typing, and how do callback props communicate back to parents?

1. The Hidden Signal

The interviewer wants to know whether you understand React's declarative execution model and unidirectional data flow, or whether you still write React with imperative DOM habits. A junior developer states that you put onClick on elements. A senior engineer explains that event handlers are passed as function references, not invoked in JSX braces. They explain that children cannot mutate parent state, so parent components pass callback props downward, allowing children to invoke those functions with arguments. They clearly separate event bubbling (e.stopPropagation()) from browser default behavior (e.preventDefault()), and they emphasize that interactive controls must use native <button> tags for accessibility.

2. The Classic Trap

The classic trap is writing onClick={handleClick()} instead of onClick={handleClick}. Candidates frequently wonder why a function runs on page load and fails to respond to clicks. Another trap is passing an argument directly: onClick={openItem(id)}, which causes immediate invocation for every item in a list during render. A third trap is putting onClick directly on a custom component tag (like <UserCard onClick={...} />) and expecting React to attach a browser listener, unaware that custom components ignore unhandled props unless explicitly wired to native HTML tags.

3. What is Actually Going On

In React, JSX curly braces evaluate JavaScript synchronously during the render phase. Calling handleClick() inside braces runs the function right away, and its return value (undefined) is passed to onClick. When the user clicks, React finds no function to call. To defer execution, you must pass an uncalled function reference, or wrap calls that require arguments in an arrow function () => handleClick(id) Because props are strictly read-only, child-to-parent communication is achieved through callback props: the parent passes a function down, and the child calls it with arguments. Events bubble up the DOM tree unless stopped by e.stopPropagation(), while e.preventDefault() cancels browser actions like link navigation and form reloads.

4. Where It Gets Tricky

What happens if an onClickCapture handler is attached to a parent element? Capture handlers run during the downward capture phase before child handlers execute, so calling e.stopPropagation() inside a child button cannot prevent parent capture handlers from running. Do all React events bubble? No: all events bubble in React except onScroll. What happens if you attach onClick to a <div>? The click works for mouse users, but the <div> cannot receive keyboard focus via the Tab key and ignores Enter and Space key activation, creating an accessibility defect. Always use native <button> elements for actions.

Glossary

  • Event Handler: A JavaScript function passed to a React element's event prop that executes in response to user interaction outside of the render cycle.
  • Callback Prop: A function prop passed from a parent component to a child component allowing the child to report user actions upward.
  • Event Bubbling: The browser process where an event dispatches on an innermost target element and propagates upward through ancestor elements in the DOM tree.
  • stopPropagation: A method on the event object that halts event propagation, preventing ancestor element handlers from executing.
  • preventDefault: A method on the event object that cancels default browser behaviors (such as form submission reloads or link navigation) without affecting event bubbling.
  • Keyboard Focus: The browser state indicating which element currently receives keyboard input and keypress events.

➔ ALWAYS use callback props to let child components communicate actions upward to parents.

➔ NEVER place event props on custom components expecting automatic DOM binding; always wire callbacks to native HTML elements.
