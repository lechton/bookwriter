Lecture 15: Trigger, Render, and Commit

Interview Question

CORE

What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?

Imagine this scenario:

  1. You build a story card with a like counter, a comment input box, and an analytics tracker.
  2. You call a state setter and immediately read the text content of the counter paragraph from the DOM to send to a server, but it sends the old count.
  3. How do the trigger, render, and commit phases govern screen updates, and what runs in each?

Every screen update follows a three-step lifecycle

In modern web applications, the screen updates in response to user actions. Readers click buttons to like articles, submit feedback, or type comments into text inputs. In traditional browser scripting, developers updated the screen by selecting elements directly with document.querySelector. They changed properties like textContent by hand. In React, application code never mutates DOM nodes directly. Instead, React orchestrates every screen update through a structured three-step lifecycle: triggering a render, rendering components to produce element descriptions, and committing changes to the browser DOM.

When developers transition from classic scripting to React, they often bring imperative DOM habits with them. In plain JavaScript, assigning a new value to element.textContent modifies the page immediately on that exact line. In React, calling a state setter does not touch the DOM right away. It merely requests a future render. React waits until the current event handler finishes before it begins rendering components and committing changes to the document. A developer who attempts to read the DOM immediately after calling a setter finds the old value still sitting on the page. Furthermore, developers frequently worry that re-rendering a component will tear down the entire page. They fear wiping out user input from active form fields, unaware that React preserves identical DOM nodes across renders.

This chapter answers four core questions. How does calling a state setter turn into an updated number on the screen? When state changes, does React run the entire application again or only specific components? If a component re-renders on every interaction, will it wipe out text that the user is actively typing? Why does reading the page immediately after calling a setter return the old count, and where should application side effects read values from?

How a state change triggers an update that renders and commits

In Lecture 1, we saw that plain JavaScript uses imperative methods like document.getElementById and textContent to modify elements on the page. In standard browser programming, calling document.querySelector('.like-count').textContent = '1' changes the paragraph immediately.

Imperative DOM Mutation
1function BrokenButton() {
2 let likes = 0;
Local variable React does not track
3 function handleClick() {
4 likes = likes + 1;
Mutates variable without triggering render
5 document.querySelector('.count').textContent = likes;
Direct DOM write
6 }
7 return <button onClick={handleClick}>Like</button>;
8}

In Lecture 9, we learned that React applications mount by calling createRoot(container).render(<App />) That initial call is the very first trigger in a React application: it tells React to prepare the initial screen. Every interface update in React proceeds through three distinct steps. The first step is the trigger: a request that tells React to calculate a new screen. There are only two triggers: the initial root.render call, and calling a state setter like setLikes.

Declarative State Update
1function LikeButton() {
2 const [likes, setLikes] = useState(0);
State memory in React
3 function handleClick() {
4 setLikes(likes + 1);
Triggers a re-render
5 }
6 return <button onClick={handleClick}>Like ({likes})</button>;
7}

The second step is render: React calls your component functions to determine what JSX they return. During rendering, React does not touch the DOM or change any pixels on the screen; it simply collects the new virtual description of the user interface. The third step is commit: React compares the newly returned JSX with the previous render and applies the necessary changes to the real browser DOM. On initial render, React uses appendChild() to insert all created DOM nodes; on re-renders, it modifies only the specific attributes and text nodes that changed. After the commit, the browser performs a browser paint, recalculating geometry and drawing pixels on the physical screen.

How a state update re-renders its component subtree

In Lecture 5, we established that React components organize into a tree structure. A root component like App branches into child components like StoryTitle and LikeCounter, which in turn branch into leaves like LikeLabel.

When a state setter executes, React does not re-render the entire application from the root. Instead, React identifies the specific component that owns the state variable where the setter was called. React re-renders that component, and then recursively re-renders every component returned inside its JSX tree. Parent components higher up the tree do not re-render. Sibling components residing in adjacent branches do not re-render.

5}

If App renders StoryTitle and LikeCounter, and LikeCounter renders LikeLabel, calling setLikes inside LikeCounter causes React to call LikeCounter and LikeLabel. Neither App nor StoryTitle is called. Even if LikeLabel returns identical JSX output, React still executes its function to verify its returned elements.

How React preserves DOM nodes and form inputs across renders

A browser web page is constructed from persistent DOM nodes, including element nodes like <p> and <input>, and inner text nodes. When a user types text into an <input> element, the browser stores that typed text inside the input DOM node's internal state. In traditional web development, replacing a container with innerHTML destroys existing DOM nodes and replaces them with new ones, immediately erasing any text the user was typing and resetting keyboard focus.

DOM Node Preservation
1function InteractiveCard() {
2 const [likes, setLikes] = useState(0);
3 return (
4 <div>
5 <p>{likes}</p>
Text node updates in commit
6 <input placeholder="Type comment..." />
Preserved untouched
7 <button onClick={() => setLikes(likes + 1)}>Like</button>
8 </div>
9 );
10}

React does not replace the DOM tree when a component re-renders. During the render phase, React executes your component function and collects the new JSX element tree. In the commit phase, React compares this new JSX tree against the JSX tree from the previous render. React identifies the exact minimal differences. If a <p> element's text changed from "0" to "1", React updates only the specific text node inside that <p>. If an adjacent <input> element was rendered in the same position in the JSX tree with the same props, React leaves its underlying DOM node completely untouched. The input element retains its identity, its typed text, and its active cursor focus. After the commit phase applies these minimal DOM edits, the browser performs a browser paint, drawing the updated pixels onto the screen.

How handler completion governs DOM update timing

In Lecture 12 and Lecture 13, we learned that event handlers run in response to user actions outside the render cycle. Handlers are the designated home for side effects, such as sending analytics pings or making network requests.

Post-Setter DOM Read Defect
1function BrokenTracker() {
2 const [likes, setLikes] = useState(0);
3 function handleLike() {
4 setLikes(likes + 1);
Schedules render for later
5 const text = document.querySelector('.count').textContent;
6 console.log('Sending:', text);
Reads uncommitted DOM value
7 }
8 return <p className="count">{likes}</p>;
9}

When a user clicks a button, the browser dispatches an event, and React invokes your event handler. When your handler executes setLikes(likes + 1), React records the requested state update and schedules a re-render. However, React does not pause your handler or immediately render the component on that line. Your handler continues executing synchronously until it reaches the end of its function block.

Using Computed Variable
1function CorrectTracker() {
2 const [likes, setLikes] = useState(0);
3 function handleLike() {
4 const next = likes + 1;
Compute next value once
5 setLikes(next);
6 console.log('Sending:', next);
Sends fresh computed value
7 }
8 return <p className="count">{likes}</p>;
9}

Only after your handler has fully returned does React begin the render phase, followed by the commit phase. Consequently, if code on the line immediately following a setter call queries the DOM using document.querySelector, the commit phase has not yet occurred. The DOM still holds the old values from the previous render. To send the new value to an external service, you must use the value your code computed directly.

Principles of React: Trigger, Render, and Commit

QUESTION 1

Calling a setter starts an update that reaches the screen in three steps

A developer builds a like counter component. Having worked with plain JavaScript, they try updating the paragraph text directly inside the click handler:

Imperative DOM Mutation Mistake
1export default function LikeCounter() {
2 const [likes, setLikes] = useState(0);
3 function handleLike() {
4 const p = document.querySelector('.like-count');
5 p.textContent = likes + 1;
Mutates DOM directly
6 }
7 return <button onClick={handleLike}>Likes: {likes}</button>;
8}

On the first click, the text inside the button changes to 1. On the second and third clicks, the button still shows 1, and the component never updates past that first click.

I call setLikes(likes + 1). How does the new number get onto the screen?

ANSWER

The code does not do what we wanted. In plain JavaScript, assigning textContent modifies the page directly, but React updates the screen through trigger, render, and commit.

When you mutate the DOM by hand, React knows nothing about the change. The state variable likes remains at 0 because no setter was called. Every subsequent click evaluates likes + 1 as 0 + 1, repeatedly writing 1 to the paragraph. In React, application code never touches DOM elements directly. Instead, calling setLikes(likes + 1) initiates a three-step sequence.

First is the trigger: calling setLikes asks React to schedule a render for this component. Second is the render: React calls LikeCounter, which evaluates its JSX and returns the new virtual element tree where likes is 1. During rendering, the page remains unchanged. Third is the commit: React compares the returned JSX with the output from the previous render and updates the text node on the page from 0 to 1.

The Three Steps: Trigger, Render, and Commit
[1. TRIGGER] Click handler calls setLikes(1) -> React queues render
     |
     v
[2. RENDER]  React calls LikeCounter() -> returns JSX with likes = 1
     |       (Page remains completely unchanged during render)
     v
[3. COMMIT]  React updates real DOM text node from "0" to "1"
     |
     v
[4. PAINT]   Browser recalculates layout and draws updated pixels

On initial application mount, root.render(<App />) acts as the very first trigger, and its commit creates and inserts all initial DOM nodes.

PRINCIPLE 1

After a setter call, React runs the component and then changes the page

trigger a request that tells React to calculate an updated user interface
render React calling component functions to compute their latest JSX
commit React updating the browser DOM nodes to match the latest JSX

In plain JavaScript, code updates the screen by mutating DOM nodes directly: p.textContent = 1 changes the page on that line. In React, application code calls a state setter and leaves DOM manipulation to React. Every update proceeds through three steps. First, the setter asks React for an update: this is the trigger. Second, React calls the component function to calculate its latest JSX: this is the render, and the page has not changed yet. Third, React compares the new JSX with the previous output and modifies the DOM where they differ: this is the commit. Changing DOM nodes by hand bypasses these steps and leaves state variables out of sync.

We should do this:
function LikeCounter() {
const [likes, setLikes] = useState(0);
return (
<button onClick={() => setLikes(likes + 1)}>
Likes: {likes}
updates via render and commit
</button>
);
}
We should not do this:
function LikeCounter() {
const [likes, setLikes] = useState(0);
function handleLike() {
const p = document.querySelector('.like-count');
p.textContent = likes + 1;
bypasses render and commit
}
return <button onClick={handleLike}>Like</button>;
}
QUESTION 2

A state change re-renders its own component and the components inside it

A developer organizes an article header where App renders both a static headline and an interactive like counter:

Subtree Component Hierarchy
1export default function App() {
2 console.log('App runs');

4 <main>

The developer adds a console log to each component: App, StoryTitle, LikeCounter, and LikeLabel. When the page loads, all four logs print in sequence. When the developer clicks Like, the console prints only LikeCounter runs and LikeLabel runs.

When I click Like, does React run my whole app again, or only LikeCounter?

ANSWER

The code works as expected. React calls only the component whose state changed and any child components it returns in its JSX.

A state update does not trigger a full re-render of the entire application. When a state setter executes, React targets the specific component that declared the state variable. In our component tree, LikeCounter owns likes, so React calls LikeCounter. React then cascades downward, recursively rendering every child component that LikeCounter returns, calling LikeLabel.

Parent components located above the state owner in the tree do not re-render. Sibling components located in neighboring branches do not re-render. Because App sits above LikeCounter and owns no changing state, React leaves App untouched. Because StoryTitle is a sibling to LikeCounter, React bypasses StoryTitle completely.

Component Re-render Cascade Scope
[App] (Parent Shell) ------------------ Does NOT re-render
  |
  +--- [StoryTitle] (Sibling) --------- Does NOT re-render
  |
  +--- [LikeCounter] (State Owner) ---- RE-RENDERS on setter call
         |
         +--- [LikeLabel] (Child) ----- RE-RENDERS (descendant cascade)

Notice that child components like LikeLabel re-render even if their props have not changed. React executes the child function to verify what JSX elements it produces.

PRINCIPLE 2

A state change runs its own component and the components inside it

state update calling a state setter to request a new render of that component

Components in React form a hierarchical component tree. On initial mount, React renders from the root component downward through every branch. When a state update occurs, React does not re-render the entire application. It calls the specific component that owns the state variable, and then recursively renders the child components returned inside its JSX. Ancestor components above the state owner and sibling components in adjacent branches do not re-render. A child component re-renders even when its props have not changed.

The developer types "great post" into the comment box and then clicks Like. The count increments to 1. The typed comment "great post" remains in the input field, and the cursor position does not jump.

If React runs LikeCounter again on every like, will it wipe the comment the reader is typing?

ANSWER

The code works as expected. React compares the new JSX with the previous render and commits changes strictly to the DOM nodes that differ.

A re-render does not recreate the underlying page or reset existing DOM elements. During the render phase, React executes LikeCounter to compute the new JSX element tree. In the commit phase, React compares this new tree against the JSX tree from the previous render to determine minimal differences.

Because the <input> element occupies the exact same position in the JSX tree with identical props, React preserves the existing input DOM node completely untouched. React mutates only the specific text node inside <p className="like-count"> whose content changed from "Likes: 0" to "Likes: 1".

- Mutate inner text node of <p> from "Likes: 0" to "Likes: 1"

- Trigger browser paint to draw new characters on screen

The browser preserves the input DOM element's internal state, keeping any typed text intact. Once the commit finishes applying these minimal differences, the browser executes a browser paint to draw the updated text on the screen.

PRINCIPLE 3

The commit changes only what is different, so typed text stays

DOM node an individual HTML element or text object preserved in the browser page
browser paint the browser drawing calculated pixels and layout onto the visual display

Re-rendering a component does not destroy or recreate the underlying page. During the render phase, React calculates the new JSX element tree. In the commit phase, React compares the new tree with the previous one and modifies only the specific DOM node whose text or attributes changed. Elements that remain in the same position in JSX are preserved. An <input> field retains its active focus and any text the user typed. Once the commit completes, the browser performs a browser paint to draw the updated pixels.

A developer connects an analytics helper to track user engagement. They call the state setter and then read the count from the page to transmit:

Premature DOM Read Inside Handler

I call setLikes(likes + 1) and then read the number from the page to send it. Why does it send the old number?

ANSWER

The code does not do what we wanted. The setter asks for a future render, but the DOM does not update until after the current event handler finishes.

A state setter does not mutate the DOM synchronously. Calling setLikes(likes + 1) stores the requested value in React's memory and marks the component as needing a render. Your event handler continues executing synchronously until it reaches the end of its function block.

React waits until all active event handlers have finished before it starts rendering components. The commit phase, where React actually updates the DOM text, occurs only after rendering completes. On the line immediately following setLikes, the commit has not happened yet. The DOM still holds the old text from the previous render.

Where you will meet this

In production applications, understanding trigger, render, and commit is vital when integrating analytics trackers, logging user interactions, and handling form inputs. Teams frequently encounter bugs where telemetry payloads send stale counts because an engineer read element.textContent synchronously after calling a state setter. Understanding that handlers run to completion before React renders prevents these synchronization defects.

Another scenario involves complex form layouts. Junior engineers often worry that updating an inline validation message or character counter will re-render the form and wipe out user draft text. Knowing that React's commit phase updates only changed DOM nodes while preserving form elements builds confidence in creating responsive interfaces.

For the interview

The Interview Question: What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?

1. The Hidden Signal

The interviewer wants to know whether you understand React's declarative execution architecture or whether you still think in terms of imperative DOM mutation. Candidates who lack this foundation assume that calling a state setter directly edits the page. Senior engineers explain the three distinct phases: triggering requests an update, rendering invokes pure component functions to produce JSX descriptions, and committing applies minimal differences to the real DOM. They also distinguish React's render phase from the browser's paint phase.

2. The Classic Trap

The classic trap is believing that state setters mutate the DOM synchronously. Candidates often write handlers that call a setter and immediately query the DOM, expecting to see the new value. Another frequent trap is fearing that re-rendering destroys active form inputs, unaware that React reconciliation diffs output and preserves existing DOM nodes. A third trap is confusing React rendering (calling JavaScript functions) with browser painting (drawing pixels on screen).

3. What is Actually Going On

React batches state updates and delays rendering until all active event handlers have returned. During the render phase, React calls component functions from the state owner downward through its returned JSX tree. In the commit phase, React calculates minimal DOM differences and updates only changed text nodes or attributes. Once the commit finishes, the browser performs a paint phase, calculating layout geometry and drawing pixels on the display.

4. Where It Gets Tricky

What happens if a child component returns identical JSX? React still executes the child render function unless wrapped in optimization memoization, but the commit phase makes zero DOM modifications. What about form inputs? React preserves existing DOM nodes if their position in the JSX tree is unchanged, keeping typed text and focus intact. What if you must read the DOM after an update? You must wait for the commit phase to finish, which is why DOM measurements belong in effects or post-commit callbacks.

Glossary

  • Trigger: An event (initial root mounting or a state setter call) that requests React to calculate an updated user interface.
  • Render: The phase where React invokes component functions to calculate their latest JSX element descriptions without modifying the DOM.
  • Commit: The phase where React applies minimal calculated differences to the browser DOM nodes.
  • Browser Paint: The browser engine process of computing layout geometry and drawing pixels onto the visual display following the commit phase.
  • DOM Node: A persistent browser object representing an HTML element or text fragment in the document tree.
  • State Owner: The specific component declaring useState where re-rendering begins following a setter trigger.

Summary

Architectural Takeaways & Decision Matrix

❒ Declarative State Triggers

➔ ALWAYS trigger user interface updates using state setters or initial root render calls.

➔ NEVER mutate DOM nodes directly with imperative methods like textContent in React applications.

➔ IF you need to pass updated state to an external service THEN compute the next value in a local variable before updating state.

DO THIS: trigger updates through state setters

code.txt
1function LikeCounter() {
2 const [likes, setLikes] = useState(0);
3 return (
4 <button type="button" onClick={() => setLikes(likes + 1)}>
5 Likes: {likes}
6 </button>
7 );
8}

DO NOT DO THIS: mutate DOM nodes directly with querySelector

code.txt
1function LikeCounter() {
2 const [likes, setLikes] = useState(0);
3 function handleLike() {
4 document.querySelector('.count').textContent = likes + 1;
5 }
6 return <button type="button" onClick={handleLike}>Like</button>;
7}
❒ Subtree Render & Commit Boundaries

➔ ALWAYS expect state updates to re-render the state owner and its nested children.

➔ NEVER assume state updates re-render the whole application; parents and siblings remain untouched.

➔ IF a component re-renders THEN trust React to update only differing DOM nodes, preserving form input text.

➔ IF an event handler triggers a setter THEN wait for the handler to complete before expecting DOM updates.

DO THIS: compute next value once and pass to setter and tracker

code.txt
1function handleLike() {
2 const next = likes + 1;
3 setLikes(next);
4 sendAnalytics(next);
5}

DO NOT DO THIS: query the uncommitted DOM immediately after a setter call

code.txt
1function handleLike() {
2 setLikes(likes + 1);
3 const count = document.querySelector('.count').textContent;
4 sendAnalytics(count);
5}
