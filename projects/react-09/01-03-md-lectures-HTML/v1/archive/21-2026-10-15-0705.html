Lecture 21: Reacting to Input with State

Interview Question

CORE

How do you design a component that reacts to input with state instead of touching the DOM?

Imagine this scenario:

  1. You build a subscription paywall modal where users type a card number and click Subscribe.
  2. An imperative handler leaves "Payment failed" and "Welcome, subscriber" on screen together after a retry.
  3. How do you design a component that reacts to input with state instead of touching the DOM?

Imperative DOM commands leave conflicting messages on screen

Today we learn how React components react to user actions and network events using declarative state machines, why imperative DOM scripting leaves conflicting UI elements on screen, and how to model form lifecycles cleanly with a single status string.

In modern frontend web applications, user interfaces constantly react to user input and background network events. When a customer subscribes to a service, they type payment details, click a submit button, watch a loading indicator appear while the network request is in flight, and finally see either an error notification or a confirmation banner. In plain JavaScript, developers write imperative commands that modify the DOM element by element: disabling buttons, removing hidden classes, and toggling error styles. Each command changes the page step by step and stays there forever until another explicit command undoes it. If a single branch forgets to reset an element, contradictory elements remain visible simultaneously, displaying an error banner right alongside a welcome message. In React, we solve this synchronization breakdown by declaring visual states first, storing the active state in component memory, and letting JSX describe what each state displays. Event handlers never touch the DOM; they only set the next state.

When developers transition from vanilla JavaScript or jQuery to React, they often bring along imperative scripting habits. When an error occurs, an imperative handler queries the DOM to set errorText.style.display = 'block' When the user retries and the request succeeds, the success handler displays the welcome message, but forgets to hide the error container. The user ends up seeing "Payment failed" and "Welcome, subscriber" at the exact same time. The same defect appears when developers represent the form's lifecycle using three separate boolean state variables: isSubmitting, isSuccess, and isError. Three booleans allow eight distinct combinations, most of which represent impossible real-world states. When a retry succeeds and sets isSuccess to true without resetting isError back to false, the form renders both messages. React replaces both traps with a systematic design process: first, list every visual state; second, identify human and computer triggers; third, store the current state in a single status string.

This chapter investigates three core questions. Why does an imperative handler leave conflicting messages on screen after a retry, and how does JSX driven by status eliminate DOM commands? Where should component design begin: with the click handler, or by listing and mocking visual states before wiring triggers? Why do separate boolean flags create impossible states, and why does a single status string guarantee mutual exclusivity?

A component changes its screen across visual states

In Lecture 10, we learned how conditional rendering with early returns and logical AND operators controls what JSX appears on screen, and in Lecture 17, we learned how asynchronous event handlers use async and await to coordinate state changes during network operations. Today we combine those mechanics to model complete visual component states.

A visual state represents the complete visual appearance of a component at a specific moment in its lifecycle. A subscription form typically has four visual states: typing (the card input is editable and the Subscribe button is active), submitting (the input and button are disabled while a loading spinner spins), success (the form is replaced by a welcome message), and error (the button is active again and an error message is visible). The HTML disabled attribute prevents users from clicking buttons or typing into fields. In React, passing a boolean expression like <button disabled={status === 'submitting'}> binds button interactivity directly to state. When coordinating network requests, JavaScript provides try and catch blocks. An async handler runs code inside try, and if a network Promise rejects, execution immediately transfers to the catch block, allowing the component to transition cleanly from submitting to error.

The relationship between visual states, form buttons, and network handling involves three core concepts:

  1. visual state: the complete visual appearance of a component for a given state.
  2. disabled attribute: a boolean HTML attribute that prevents user interaction on buttons and inputs.
  3. try...catch: a JavaScript control structure that intercepts errors thrown during asynchronous operations.

Testing visual states with props before wiring triggers

In Lecture 6, we learned that components accept props with default values to configure their output, and in Lecture 11, we saw how array map() renders repeated items into an element list. In this section, we apply those mechanics to inspect every visual state before attaching interactive event handlers.

When developing a complex interactive component, writing event handlers first forces you to test screens by manually triggering every step in the browser. A more disciplined approach is to mock each visual state first. By accepting a status prop with a default value, such as function PaywallModal({ status = 'typing' }) an engineer can change the prop value by hand to verify how submitting, error, or success look without writing any network logic. In fact, rendering an array of statuses side by side with ['typing', 'submitting', 'error', 'success'].map(...) creates a living styleguide showing all four states simultaneously. Once the visual states are verified, you catalogue the triggers that move the component between them. Triggers divide into two categories: human inputs (such as typing into an input field or clicking a button) and computer inputs (such as an incoming network response or a timer firing). Each trigger becomes a single setStatus call in an event handler.

The process of mocking visual states and identifying transitions relies on four foundational concepts:

  1. mock: a visual preview rendered with static props to verify UI layout before attaching logic.
  2. living styleguide: rendering multiple visual states simultaneously side by side for visual auditing.
  3. human inputs: user interactions such as keystrokes, button clicks, and form submissions.
  4. computer inputs: system events such as network responses resolving, promises rejecting, and timeouts firing.

One status string prevents impossible states

In Lecture 14, we learned how useState stores component values across renders. Developers often create a boolean state variable for each piece of UI they need to toggle, which works well for independent flags but fails when states are mutually exclusive.

When a component can exist in only one visual mode at a time, representing those modes with separate boolean flags invites critical bugs. For example, using isSubmitting, isSuccess, and isError creates $2^3 = 8$ possible combinations. A state where isError === true and isSuccess === true is an impossible state: a screen cannot logically show a payment failure banner and a subscriber welcome message at the same time. If a retry handler sets setIsSuccess(true) but forgets to call setIsError(false), the component enters this impossible state. Using a single status string state variable with 'typing' | 'submitting' | 'success' | 'error' makes impossible states mathematically impossible, because a string variable can hold exactly one value at any moment. Values that change independently, such as user input (card) or dynamic error messages (error), remain separate state variables alongside status.

Representing form states cleanly without combinatorial errors centers on three core concepts:

  1. impossible state: a contradictory combination of state values that causes the UI to render broken or conflicting elements.
  2. single status string: a state variable holding a string enum that guarantees only one visual state is active at a time.
  3. independent state: state variables that change autonomously, such as input field values or error details, kept separate from status.

Principles of React: Reacting to Input with State

QUESTION 1

A successful retry shows the error and welcome messages together

A developer builds a subscription paywall modal where users type a card number and click Subscribe. To handle user interactions, the developer uses imperative DOM scripting, manually finding elements and modifying their styles and properties:

PaywallModal.jsx, imperative attempt
1function handleSubmit(e) {
2 e.preventDefault();
3 document.querySelector('#btn').disabled = true;
Disables button
4 submitPayment(card).then(() => {
5 document.querySelector('#welcome').style.display = 'block';
6 }).catch(() => {
7 document.querySelector('#error').style.display = 'block';
Shows error
8 });
9}

On the first attempt, the payment network request fails. The catch callback runs, and the browser displays "Payment failed". The user corrects their card number and clicks Subscribe a second time. This time the payment succeeds, and the then callback runs. On screen, the modal now displays "Payment failed" and "Welcome, subscriber" simultaneously.

My Subscribe handler disables the button, shows the spinner, and hides the error. Why does the form end up showing "Payment failed" and "Welcome, subscriber" together?

ANSWER

The code does not do what we wanted. Direct DOM edits stay on the page until another line manually undoes them.

In imperative programming, every command given to the browser changes the DOM directly, and each change remains in place indefinitely. On the first payment attempt, the request failed, so the catch handler executed document.querySelector('#error').style.display = 'block' That line made the error banner visible. On the second attempt, the request succeeded, so the then handler executed document.querySelector('#welcome').style.display = 'block' That line made the welcome message visible. However, because no line in the success path instructed the browser to hide the error banner, the error element remained visible.

React never sees these manual DOM mutations. React does not inspect element styles or query DOM nodes to decide what belongs on screen. When an imperative handler modifies the DOM behind React's back, state and the screen drift out of sync.

To fix this problem, you must remove all direct DOM commands from your event handlers. Instead of telling the browser how to change the page step by step, you describe what the screen displays for each visual state in JSX. You store the current state in a React state variable named status. Your event handlers only call setStatus('submitting'), setStatus('success'), or setStatus('error'). React re-renders the component and updates the DOM to match the JSX for that status. When status transitions to 'success', React unmounts the form and renders only the welcome message, making it physically impossible for the error message to remain visible.

Imperative DOM edits vs declarative status render
Attempt 1 (Fail):
  Imperative: error.style.display = 'block' -> [Payment failed] visible
  Declarative: setStatus('error')           -> renders error JSX

Attempt 2 (Retry Success):
  Imperative: welcome.style.display = 'block' (forgot to hide error!)
              Screen shows: [Payment failed] AND [Welcome, subscriber]
  Declarative: setStatus('success')
              Screen shows: ONLY [Welcome, subscriber]

When state changes, React re-renders the component and updates the DOM to match the JSX, so conflicting elements never share the screen.

Listing visual states comes before writing event handlers

A developer begins building the subscription modal by immediately writing the submission event handler, attempting to wire button clicks and network requests before establishing what screens the form can display:

8}

The developer is unsure how to handle loading spinners, error banners, and success confirmations, and must constantly click the button and trigger mock network errors to test UI layouts.

Where do I start? Do I write the Subscribe handler first?

ANSWER

The code works. However, starting from event handlers makes it hard to see every visual state before writing logic.

When you start building a component from its event handlers outward, you are forced to test your user interface by clicking buttons, filling fields, and triggering real or mocked network failures in the browser. This makes development slow and error-prone because edge-case visual states, such as a network timeout or a validation failure, are difficult to reproduce repeatedly on demand.

Idiomatic React development inverts this workflow by designing from the screen inward across four structured steps:

  1. List the visual states: Write down every distinct visual screen the user can encounter. For a subscription modal, these are typing (the initial editable form), submitting (disabled inputs with an active spinner), success (a confirmation message), and error (the editable form displaying an error banner).
  2. Mock each visual state with props: Implement the JSX for each state inside the component, accepting a status prop with a default value like status = 'typing'. By manually editing the prop or rendering all states side by side with statuses.map(...), you can audit and polish every screen before writing a single line of business logic.
  3. Catalogue human and computer triggers: Identify every event that causes the component to change state. Human triggers include typing in a text field, clicking a submit button, or pressing reset. Computer triggers include a network response arriving, an API call rejecting, or a timer completing.
  4. Connect event handlers: Finally, implement event handlers that call setStatus to transition the component from its current visual state to the next state when a trigger fires.

QUESTION 3

Separate boolean flags allow conflicting states to show together

A developer decides to manage the subscription modal's visual states using three boolean state variables:

PaywallModal.jsx, three booleans attempt
1function handleSubscribe() {
2 setIsSubmitting(true);
3 try {
4 fakePaymentApi();
5 setIsSuccess(true);
Sets success to true
6 } catch {
7 setIsError(true);
Leaves both booleans true after retry
8 }
9}

On the first submission, the request fails, setting isError to true. The user clicks Subscribe again. This time the payment succeeds, and setIsSuccess(true) executes. On screen, the component renders both the "Payment failed" banner and the "Welcome, subscriber" message.

Can I keep isSubmitting, isSuccess, and isError as three booleans instead?

ANSWER

The code does not do what we wanted. Multiple boolean flags allow conflicting states to be active simultaneously.

When you use three independent boolean state variables, JavaScript evaluates $2^3 = 8$ potential combinations. However, out of those eight combinations, only four correspond to real-world visual screens:

  1. isSubmitting: false, isSuccess: false, isError: false -> typing state.
  2. isSubmitting: true, isSuccess: false, isError: false -> submitting state.
  3. isSubmitting: false, isSuccess: true, isError: false -> success state.
  4. isSubmitting: false, isSuccess: false, isError: true -> error state.

The remaining four combinations represent impossible states. A component cannot be simultaneously submitting and successful, nor can it be simultaneously an error and a success. In the code above, when the first payment attempt failed, isError became true. When the second attempt succeeded, the handler set isSuccess to true, but forgot to call setIsError(false). As a result, both isSuccess and isError were true at the same time, causing the JSX conditional checks {isError && <p>Payment failed</p>} and {isSuccess && <p>Welcome, subscriber</p>} to render both messages together.

The solution is to model mutually exclusive visual states with a single status string state variable: const [status, setStatus] = useState('typing') Because a string variable can hold exactly one value at any given instant, impossible states become physically impossible. When the success handler calls setStatus('success'), the old status 'error' is automatically replaced without requiring any manual cleanup.

State variables that change independently, such as user input (card) or dynamic server error text (error), should remain in separate state variables alongside status.

Multiple boolean combinations versus single status string
Three Booleans (2^3 = 8 combinations):
  isSubmitting | isSuccess | isError | Result
  -------------+-----------+---------+-------------------------------
  false        | true      | true    | IMPOSSIBLE: two messages show!
  true         | true      | false   | IMPOSSIBLE: loading & success

Single Status String (1 of 4 mutually exclusive states):
  'typing' | 'submitting' | 'error' | 'success'
  Result: exactly one valid screen rendered at all times

Keep separate state only for values that change independently, such as typed text.

Where you will meet this

In production frontend applications, reacting to input with state is fundamental across authentication modals, payment checkouts, search bars, and multistep wizards. A frequent production bug occurs when teams implement a checkout flow with separate booleans: an intermittent network failure sets isError(true), and when the customer retries successfully, the success handler displays the confirmation receipt while leaving the failure alert visible on screen. Adopting a single status string eliminates this bug completely.

Another common production bug occurs when developers write imperative DOM queries inside React event handlers, such as document.querySelector('#submit-btn').disabled = true If the network request throws an unhandled exception before reaching the catch block, the button remains permanently disabled, locking the user out of the application until they reload the page. Deriving disabled={status === 'submitting'} guarantees that the button restores its interactivity whenever status changes.

In technical interviews, interviewers use this question to evaluate whether a candidate thinks in imperative DOM commands or declarative state machines. Strong candidates immediately recognize that mutually exclusive visual modes must be modeled with a single string enum, explain how to mock states with props before wiring handlers, and describe how React reconciliation guarantees clean UI transitions.

For the interview

The Interview Question: How do you design a component that reacts to input with state instead of touching the DOM?

A senior response deconstructs the problem across four battle-tested architectural beats:

1. The Hidden Signal

The interviewer is probing whether you have transitioned from the imperative DOM manipulation habits of vanilla JavaScript to React's declarative state machine paradigm. Juniors often recite syntax or attempt to fix conflicting UI by querying DOM elements. Seniors demonstrate that React components are state-driven projection functions: you define the visual states first, store the current state in component memory, and let JSX describe what each state displays.

2. The Classic Trap

The primary misconception is managing mutually exclusive visual states with multiple independent boolean flags, such as isSubmitting, isSuccess, and isError. Multiple booleans create $2^N$ possible combinations, allowing impossible states where contradictory flags are true simultaneously. Candidates who rely on booleans frequently write buggy retry handlers that display error alerts and success banners at the same time.

3. What is Actually Going On

Idiomatic React design follows five structured steps:

  1. Identify visual states (typing, submitting, success, error).
  2. Mock each visual state with a status prop to visually audit screens before adding logic.
  3. Catalogue human triggers (typing, clicking) and computer triggers (network responses, timeouts).
  4. Model the active mode using a single status string state variable, keeping independent data like input text in separate state.
  5. Wire event handlers that only call setStatus to transition the component between visual states.

4. Where It Gets Tricky

Edge cases arise during asynchronous network handling and rapid user interaction. An async submission handler must run inside try...catch to catch rejected promises cleanly. Submit buttons must bind disabled={status === 'submitting'} to prevent duplicate submissions during in-flight requests. Finally, user input fields must remain controlled and separate from status so typing remains responsive while the component transitions across states.

Glossary

  • Visual State: A distinct visual presentation of a component determined by its underlying data and lifecycle status.
  • Single Status String: A state variable containing a string enum that guarantees only one mutually exclusive visual mode is active at any time.
  • Impossible State: A contradictory combination of state values that causes the user interface to display invalid or conflicting elements.
  • Human Input: User-driven interactions such as typing into form inputs, clicking buttons, or submitting forms.
  • Computer Input: System-driven interactions such as network responses returning, promises rejecting, or timers completing.
  • Living Styleguide: Rendering all mocked visual states of a component simultaneously to audit and verify layout across all lifecycle phases.

➔ IF disabling form actions during submission THEN derive disabled={status === 'submitting'} directly from state.

➔ NEVER mutate DOM elements or styles directly with document.querySelector inside React handlers.
