Splitting repeated markup into a reusable component

Now look at why components matter on a real website. An online shop shows twenty product cards, and a news site shows twenty article cards. If you build that whole page inside one giant function, you end up copying and pasting the same card markup twenty times. Tomorrow, when you want to change the card's design, you have to hunt through hundreds of lines and edit all twenty copies by hand.

In React, you never copy and paste the same piece of markup over and over. Instead, you split the page into small, reusable components. Each component is a JavaScript function that returns the markup for one piece of the page.

How we inspect our components in the browser

Throughout this lesson, we keep all our components inside one file so you can see every function and every tag together at a glance. Whenever we want to check what happened on the page, we look in three places in the browser:

  • The page viewport shows what the user sees on screen.
  • The Elements panel shows the real HTML nodes inside the browser DOM.
  • The Console panel shows messages printed by console.log and any warnings from React.

Four Principles of Component Anatomy

PRINCIPLES

A React component is a JavaScript function that returns JSX. At first glance, it looks just like any normal JavaScript function. However, React uses your component through a tag to build and update the page. Because of that, four practical rules come up in daily debugging and React interviews:

  1. Principle 1: Declaring vs. Rendering a Component: Writing a component function and placing its tag on the page are two separate steps. If you write the function and forget to place its tag inside App, nothing appears. When you place the tag, React calls your function and puts only the returned HTML into the browser DOM.
  2. Principle 2: Capital First Letter in PascalCase: Normal JavaScript functions start with a small letter. If you start a component name with a small letter, JSX treats the tag as a built-in browser HTML tag and never calls your function.
  3. Principle 3: Open the Parenthesis on the return Line: If you move multi-line JSX to the line below return without opening a parenthesis on that same line, JavaScript ends the statement right there. It gives back undefined, and your component disappears with zero Console errors.
  4. Principle 4: Define Every Component at the Top Level: If you define one component function inside another component function, JavaScript creates a brand-new inner function in memory on every update. React then destroys the old DOM nodes and wipes out whatever the user was typing.

Here is the complete map of those four principles before we walk through each one:

Rendering: React Calls the Component Wherever a Tag Names It

Use a component by writing its name as a JSX tag, such as <ArticleCard />, inside another component's markup; React calls the function once for each tag.

Three ways programmers join words into one name

Because names in JavaScript cannot contain spaces, programmers use three common styles to join words together:

  • camelCase: Examples include myName and articleCard. The first word starts with a small letter, and each later word starts with a capital letter, like the humps of a camel. This is the usual style for variables and functions in JavaScript, but you must not use it for React components.
  • PascalCase: Examples include ArticleCard and CommentBox. Every word starts with a capital letter, including the very first word. You must use PascalCase for every React component.
  • snake_case: Examples include my_name and article_card. All words use small letters joined by an underscore _. Because its first letter is small, you must not use it for React components either.

For the Interview

The Interview Question: What is a React component, and how do you define and render one inside another component?

How to Answer Clearly in 30 Seconds

"A React component is a JavaScript function whose name starts with a capital letter and that returns JSX describing one piece of the UI. To render it inside another component, we never call the function ourselves. Instead, we write its name as a JSX tag, like <ArticleCard />, and React calls the function for each tag. That call is what 'rendering' means. Three rules keep components working properly:

  1. Capital first letter in PascalCase: a lowercase tag like <footer /> or <articleCard /> is treated as a built-in HTML tag, so our function never runs.
  2. Open the parenthesis on the return line: a bare return with JSX on the next line triggers Automatic Semicolon Insertion, turning return into return; and returning undefined.
  3. Top-level definition: we define every component at the top level of the file, never inside another component. A nested component creates a new function in memory on every render, which forces React to destroy and recreate its DOM nodes."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Is starting a component name with a capital letter in PascalCase just a naming convention?"
    No. In plain JavaScript, camelCase, such as let myName = 'John', is only a style convention for humans. In React, the first letter of a JSX tag is how the compiler tells built-in HTML tags apart from your components. A lowercase first letter, such as <articleCard /> or <footer />, is compiled as an HTML tag string. The browser creates an empty HTML element, and your function never runs. A capital first letter, such as <ArticleCard /> or <Footer />, passes your JavaScript function to React so React calls it.
  2. "What happens if you define a child component inside a parent component, such as CommentBox inside ArticleCard?"
    On the first render, it appears to work. On every re-render of the parent, however, JavaScript creates a brand-new function object in memory for the inner component, so oldFn !== newFn. When React compares the new render with the previous one, it sees a different function at that position and assumes it is a completely different component. React then unmounts the old DOM nodes and mounts new ones from scratch. Any typed input text or cursor focus inside that child component is wiped out on every update.
  3. "Does <ArticleCard> appear in the browser's DOM in the Elements panel, and is <ArticleCard /> the same as calling the function directly?"
    No to both. First, the browser DOM only holds real HTML tags such as <main>, <article>, and <h2>. <ArticleCard /> is for React, so <ArticleCard> never appears in the Elements panel. Second, writing <ArticleCard /> hands the function to React so React tracks ArticleCard as its own component in the tree. Calling the function directly only hands React the returned <article> HTML and hides the component from React.
