# Brief 2026-10-17-06: Examples Chosen Anew, Radically Simple

## Why

The owner, studying the revision 3 lessons: "They are very confusing. When we transform a normal lesson into a revision 3, we need to RADICALLY RECONSIDER ALL EXAMPLES, ALL OF THEM! ... for examples in the 01 lesson we see a weird example with elections, name becoming Mary Brooks, I do not get it." And, on what the reconsideration is for: "Radical change and reconsideration of examples to (a) better fit the story of the chapter and (c) to be radically simple and easy to comprehend, to avoid complex presentation of code in the code examples and clearly present the concepts. ALL UI elements and acts need to be simple and intuitive e.g. article, title, button, counter, colour etc."

The skills had led there. `summary-edition` Section 02 asked "Are the code, names, values, and error messages the lecture's own wherever the lecture has them?" and allowed a new story only "when the running example cannot host a proof"; `summary-figures` Section 02 asked for "the lecture's verified" values and names. Together they made keeping the lecture's example the default and changing it the exception. Nothing asked whether the example was simple.

## What was rejected on the way

A first proposal turned Lecture 1's symptoms into four tests (a real user action, values told apart at a glance, a reason for every detail, one set of names). The owner: "What on earth? As if every single chapter deals with the same minor idiosyncratic problems." The standard below replaced them. Its first wording listed "an article with a title, a button, a counter, a colour", which the owner read as a closed list; the list is now open, ends in "etc.", and comes after the test it illustrates: recognition, not the item.

## Group 1: Examples chosen anew, radically simple (#2026_10_17_06_group_1)

Pruned first: the three binding rules are reversed rather than overruled. `summary-edition` Section 02 now says the examples are chosen anew and each proof moves into them with its behaviour kept; its checks ask for the verified behaviours and for error texts word for word for the lesson's own code, and the report names the examples chosen. `summary-figures` Section 02 asks for values verified for the lesson's own example. Section 11's "the lecture's card or list" became "the lesson's".

Added: `summary-edition` Section 03B, the standard (every example reconsidered; it fits the chapter's story; it is radically simple, with parts and actions the reader recognises at once and code that holds only the concept; each part arrives where the lesson first needs it), with the owner's words, five checks, and a proper and counter example from Lecture 1. Casebook Case 21 records the three versions of Lecture 1. `summary-audit`: the cold-read prompt gains an EXAMPLE category, it joins the stopping rule, and the report check names the examples chosen.

The proper example describes the cart version of Lecture 1 now in `04-01-md-revised-3/v1/01.md`. That lesson was written before this batch, without the owner asking for it, and is not yet accepted; if the owner rejects it, the proper example in Section 03B and Case 21 changes with it.

Not in this batch: Lectures 3, 10, and 11, which were written before the standard; the `box=` and `button=` card fields of the build, not yet documented in `summary-figures/blocks.md`.
