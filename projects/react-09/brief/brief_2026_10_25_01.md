## The problem in one paragraph

River lectures are well organized, checked, and polished, yet they miss the elegance of simplicity. They bury an embarrassingly simple mechanism inside the multi-file City News app before the reader has seen it bare in two lines. Lecture 09 (`children`) is the clearest case: the reader first meets `children` already wrapped in `ArticleCard.jsx`, `ArticleList.jsx`, `Badges.jsx`, three attributes, and two imported badge components, and never sees the plain fact that everything between the tags becomes `children`.

## Argon's diagnosis of Lecture 09

Three layers of confusion:

1. The reader does not see the two physical places on a tag. A component tag has only two places to hand information in: on the opening tag, with a name you choose (`<MyComponent name="John" />`), and between the opening and closing tags, with no name at all (`<MyComponent>My name is John</MyComponent>`). Lecture 09 mixes both at once (`title`, `summary`, `readTime` plus `<LiveBadge /><NewBadge />`), so the two ways are never seen side by side in their purest form.
2. The reader wonders what kind of magical thing `children` is. With `name="John"` you typed the word `name`, so `props.name` is obvious. With text between the tags you typed no name, so how does the function grab it? That is why `props.children` exists: content between the tags has no attribute name, so React puts everything between the opening and closing tags into `props.children`.
3. Starting with `<LiveBadge />` hides that `children` is literally anything between the tags. The reader thinks `children` is a special slot architecture for nesting components. Starting with `<MyComponent>My name is John</MyComponent>` removes the mystery in five seconds: put text between the tags and `children` is that text; put an `<h1>` and it is that `<h1>`; put two badges and it is those two badges.

## Why it is missing across all chapters (Argon)

Every chapter opens inside the running City News app. The River structure has a step for "plain JavaScript first, when the principle rests on it", but no step for the bare two-line React essence before the multi-file app. So the reader learns the concept through the furniture of the example instead of grasping it on two lines and then watching it solve the project's problem.

Note added when this brief was written: `skills/v9.4` (commit `d199785c`) already makes the map choose a new example for every lesson instead of reusing City News. That removes the furniture carried over between lessons, but it does not add a bare two-line opening, so this brief's proposal is still open.

## The proposed rule: the five-second essence first

Before a chapter or principle touches the project files, open with the smallest self-contained contrast, two to six lines of code, no project baggage, no extra props, that makes the reader say "oh, that's all it is". Then step into the project, where the reader already knows what is happening.

## The two-line contrasts Argon proposed, chapter by chapter

These are Argon's suggestions in a discussion, not approved lecture text. Under the River rule that good examples come only from approved text, they can serve as content ideas for maps, not as PROPER passages in skills.

- Lecture 03 (curly braces): `<p>name</p>` prints the word "name"; `<p>{name}</p>` prints "John". On attributes, `age="10 + 5"` is the text "10 + 5", while `age={10 + 5}` runs JavaScript and gives the number 15. Quotes mean "these exact characters"; braces mean "run this as JavaScript and put the result here". This also explains `style={{ color: "red" }}`: there is no double-brace syntax; the outer braces switch to JavaScript, and the inner braces are an ordinary object.
- Lecture 04 (components): `sayHello()` is called by you; `<MyComponent />` is called by React.
- Lecture 05 (imports): `export default function Button() {}` pairs with `import Button from './Button.jsx'` (one default per file, so no braces and any name works); `export function LiveBadge() {}` pairs with `import { LiveBadge } from './Badges.jsx'` (many per file, so braces and the exact name).
- Lecture 08 (props): `sayHello("John", 30)` versus `<MyComponent name="John" age={30} />`. React collects every attribute into one object, `{ name: "John", age: 30 }`, and passes it as the first parameter. Writing `function MyComponent({ name, age })` unpacks that one object; React never passes separate arguments, which is why `function MyComponent(name, age)` fails.
- Lecture 09 (`children`, spread, defaults): `<MyComponent name="John" />` gives `props.name` as "John"; `<MyComponent>My name is John</MyComponent>` gives `props.children` as "My name is John", shown with `function MyComponent(props) { return <div>{props.children}</div>; }`. Spread: `const user = { name: "John", age: 30 }` and `<MyComponent {...user} />` puts the object's keys straight into `props`. Defaults: `<MyComponent />` with `function MyComponent({ name = "Guest" })` gives "Guest" instead of `undefined`.

## The pattern Argon named

Every time a reader feels confused, the lesson showed the application before the two-line contrast. Argon's closing question to the owner: should this two-line contrast become the required opening of every chapter and principle, before the project files appear?
