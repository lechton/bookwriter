# Brief 2026-10-17-05: Each Label Worded by the One Who Does It

## Why

Lecture 1's summary, drafted by another model from the skills, named its three principles "1. Describe what each element shows", "2. Read one variable in every place", and "3. Compare descriptions on every change", in the division tree, the "you are here" maps, the headings, and the Summary. The owner: "IT confuses what the React (it compares) with what the learner needs to learn how to do (he does not compare anything). The title should be Virtual DOM comparison or something like that. The language should be prescriptive only when explicit prescription is implied." And of the second label: "the junior or senior developer reading this is supposed to read something?"

The skills had led there. `summary-edition` Section 03 set every section heading as `## N. {{the section label}}: {{what to do}}`, which asks for a command even where React is the one acting, and the chart test's only examples of a box and a root were commands ("Give each card a key from its article's id", "Render one card per article"). Nothing said who acts.

## Group 1: Who acts (#2026_10_17_05_group_1)

Pruned first: the heading pattern now reads `{{the rule in a few words}}`, worded by who acts, with Lecture 3's "Each tag becomes a call that returns an object" beside Lecture 10's "return null at the top"; the chart test's root may be a question, a task the developer carries out, or a topic, and its box examples gain one with React as the subject. Added: `summary-edition` Section 06B, three checks with the owner's words and a proper and counter example from Lecture 1; `summary-figures` Section 02B, one check pointing to it; casebook Case 20. The map's Kind (Model or Decision) is named as a first hint only, because a Model principle can still ask the developer to do something.

Applied: `04-01-md-revised-3/v1/01.md`, archived first (stamp `2026-10-17-1624`). The three steps are now "1. Declarative programming", "2. A single source of truth", "3. Virtual DOM comparison", each with a note whose subject is the one who acts; the headings, maps, and Summary follow; the decision trees say "Our code finds each element ..." against "React builds and updates the DOM ...", "Our code rebuilds the header with `innerHTML`" against "React compares the new description with the last one", and keep commands where the developer chooses ("Type a copy of the value as fixed text" against "Write `{userName}` in every place"); Principle 1's title is the map's again.

## Group 2: A mark on the parts to compare (#2026_10_17_05_group_2)

The same draft opened with `good=title,text,input`: green rings on the greeting, the account line, and the search box, so the whole card looked like a form with heavy borders and nothing stood out. The skills explained the syntax of a mark but not what deserves one. Revised rather than added: `summary-figures` Section 02's check on marks now says a mark goes only on the parts the reader must compare or find, usually one or two, and in a row of pictures on the part that differs; a mark on every part marks nothing. Lecture 10's opening is the proper example, Lecture 1's first draft the counter-example.

Applied: Lecture 1's opening rings only the two names; in section 3's row, where both pictures show the new name, only the search box carries a ring, and the caption says so. In both builds' `base.css`, a ring on a page's title, author, or text line now keeps 4pt of room around the words, and a marked input shows one coloured border instead of a ring around its own border.
