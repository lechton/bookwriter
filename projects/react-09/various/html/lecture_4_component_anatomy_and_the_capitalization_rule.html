Component Anatomy and the Capitalization Rule

Interview Question · ❱ CORE

What is a React component, and how do you define and render one inside another component?

OverviewWhy We Split a Page into Components

A page is made of pieces, and each piece is a function

Look at any real website: an online shop shows twenty product cards, and a news site shows twenty article cards. If you build that whole page inside one giant function, you end up copying and pasting the same card markup twenty times. Tomorrow, when you want to change the card's design, you have to hunt through hundreds of lines and edit all twenty copies by hand.

In React, you never copy and paste the same piece of markup over and over. Instead, you split the page into small, reusable pieces called components. Each component is a JavaScript function that returns the markup for one piece of the page.

Split into a reusable ArticleCard component

Place <ArticleCard /> wherever you need a card
Figure 1 — Two ways to put twenty article cards on a page: copy-pasting markup by hand vs. splitting out a reusable component.

Two kinds of tags sit side by side in your markup

Four Principles of Component Anatomy

PRINCIPLES

A React component is a JavaScript function that returns JSX. At first glance, it looks just like any normal JavaScript function. However, React uses your component through a <Tag /> to build and update the page. Because of that, four real issues come up in daily debugging and code interviews:

  1. Principle 1 — Declaring vs. invoking a component: Declaring function ArticleCard and placing <ArticleCard /> are two separate steps. If you declare ArticleCard but forget to write <ArticleCard /> inside App, nothing appears. When you place <ArticleCard /> in App, React calls your function and puts only the returned <article> HTML into the browser DOM. That call by React is what "rendering" means.
  2. Principle 2 — Why a small first letter hides your component: Normal JavaScript functions start with a small letter in camelCase. If you name a component articleCard or footer with a small first letter, React treats <articleCard /> or <footer /> as a built-in HTML tag and never calls your function. With <footer />, it prints zero errors in the Console!
  3. Principle 3 — Why a line break after return erases your component: Suppose you move multi-line JSX to the line below return, but forget to open the parenthesis on the return line. JavaScript automatically turns return into return;, gives back undefined, and your component disappears with zero Console errors.
  4. Principle 4 — Why putting a component inside another component wipes out user input: If you define CommentBox inside ArticleCard, JavaScript creates a brand-new CommentBox function in memory on every update. React then destroys the old <input> box and erases whatever the user was typing.

Writing the component function and using its tag are two separate steps

Putting a component on the screen takes two separate steps: first you declare the function, and then you use its tag inside App.

  • In daily coding: If you write the card function, but forget to place its tag inside App, you see nothing on the screen. Declaring the function and using its tag are two separate steps.

Principle 1

Rendering: React Calls the Component Wherever a Tag Names It

Use a component by writing its name as a JSX tag, such as <ArticleCard />, inside another component's markup; React calls the function once for each tag.

Defining a component function does not put it on the page until a rendered component includes its <Tag />. During rendering, each <ArticleCard /> tag hands the function to React so React calls it and puts the returned <article> HTML into the browser DOM. Section 2 · Principle 2Start Component Names with a Capital Letter in PascalCase

Three ways programmers join words into one name

Because names in JavaScript cannot contain spaces, programmers use three common styles to join words together:

  • camelCase — such as myName, articleCard, and formatDate. The first word starts with a small letter, and each later word starts with a capital letter, like the humps of a camel. This is the usual style for variables and functions in JavaScript, but you must not use it for React components.
  • PascalCase — such as ArticleCard, CommentBox, and Footer. Every word starts with a capital letter, including the very first word. You must use PascalCase for every React component.
  • snake_case — such as my_name and article_card. All words use small letters joined by an underscore _. Because its first letter is small, you must not use it for React components either.

Every word starts with a capital letter

snake_case
my_name article_card
Do NOT use for React components
All words use small letters joined by _
JSX also treats <article_card /> as an HTML tag
Figure 8 — The three naming conventions in code: which ones we do NOT use for React components vs. the one we DO use.

In React, a capital first letter is a compiler rule, not a style habit

In plain JavaScript, choosing myName or MyName is only a matter of style for human readers; JavaScript runs both the same way. In React JSX, however, the first letter of a tag is a strict compiler rule:

  • In daily coding: If your component's name starts with a small letter, React treats the tag as a built-in browser HTML tag and never calls your function.
  • In an interview: If an interviewer asks whether PascalCase is just a naming convention, never say "Yes, it is best practice." State clearly: No, it is a compiler rule—a small first letter is read as an HTML tag name, so our function never runs.

  3. The moment the card runs again, everything the user typed is wiped out, and the blinking cursor disappears!

A new function tells React to destroy the old input box and build a new one

Remember from Lecture 1 what happens when a page updates. React keeps existing DOM nodes in place, so text boxes keep what the user typed and keep their cursor focus.

How does React decide whether to keep the old comment box or tear it down? It checks whether the component function in that spot is the very same function as on the last run:

  1. On the first run: The card creates the first comment box function and puts the text box on the page, where the user starts typing.
  2. On the second run: When the card updates, it runs again and makes a second, brand-new function in memory for the comment box.
  3. When React compares the two runs: React sees a different function in that spot. To React, a different function means a different component! So React removes the old text box and builds a brand-new, empty one. Everything the user typed is wiped out, and the cursor is lost.

Define every component at the top level of the file, outside all other functions, and never inside another component.

Interview PrepFor the Interview

The Interview Question: What is a React component, and how do you define and render one inside another component?

How to Answer Clearly in 30 Seconds

"A React component is a JavaScript function whose name starts with a capital letter and that returns JSX describing one piece of the UI. To render it inside another component, we never call the function ourselves. Instead, we write its name as a JSX tag, like <ArticleCard />, and React calls the function for each tag. That call is what 'rendering' means. Three rules keep components working properly:

  1. Capital first letter in PascalCase: a lowercase tag like <footer /> or <articleCard /> is treated as a built-in HTML tag, so our function never runs.
  2. Open the parenthesis on the return line: a bare return with JSX on the next line triggers Automatic Semicolon Insertion, turning return into return; and returning undefined.
  3. Top-level definition: we define every component at the top level of the file, never inside another component. A nested component creates a new function in memory on every render, which forces React to destroy and recreate its DOM nodes."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Is starting a component name with a capital letter in PascalCase just a naming convention?"
    No. In plain JavaScript, camelCase, such as let myName = 'John', is only a style convention for humans. In React, the first letter of a JSX tag is how the compiler tells built-in HTML tags apart from your components. A lowercase first letter, such as <articleCard /> or <footer />, is compiled as an HTML tag string. The browser creates an empty HTML element, and your function never runs. A capital first letter, such as <ArticleCard /> or <Footer />, passes your JavaScript function to React so React calls it.
  2. "What happens if you define a child component inside a parent component, such as CommentBox inside ArticleCard?"
    On the first render, it appears to work. On every re-render of the parent, however, JavaScript creates a brand-new function object in memory for the inner component, so oldFn !== newFn. When React compares the new render with the previous one, it sees a different function at that position and assumes it is a completely different component. React then unmounts the old DOM nodes and mounts new ones from scratch. Any typed input text or cursor focus inside that child component is wiped out on every update.
  3. "Does <ArticleCard> appear in the browser's DOM in the Elements panel, and is <ArticleCard /> the same as calling the function directly?"
    No to both. First, the browser DOM only holds real HTML tags such as <main>, <article>, and <h2>. <ArticleCard /> is for React, so <ArticleCard> never appears in the Elements panel. Second, writing <ArticleCard /> hands the function to React so React tracks ArticleCard as its own component in the tree. Calling the function directly only hands React the returned <article> HTML and hides the component from React.
