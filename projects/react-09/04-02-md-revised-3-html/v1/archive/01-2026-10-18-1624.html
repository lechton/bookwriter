What is React and the Declarative Model

Interview question❱ CORE
What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

Example: a site header that shows the user's name

The example for this whole lecture is the header at the top of a website. It greets the signed-in user by name, shows the name again in its corner, and holds a search box. Here is the header for a user named Mary:

Look closely: the name appears twice, once in the greeting and once in the corner. Now Mary adds her family name in her profile and becomes Mary Brooks. At that moment she is using the page: she has typed "elections" into the search box, and the cursor blinks in it. Here is what the header must show before and after the change:

One change of data, three parts of the page, and they must not all do the same thing:

"Signed in as Mary" in the cornershows the new name too

Two places must follow the data, and one must be left exactly as the user left it. Every web page meets this question in some form: when the data changes, how does the page change with it? React's answer is to describe the page from the data and let React change the page to match. That is the topic of this lecture: what is React, and how does its way of building a page differ from changing the page by hand with plain JavaScript?

The components behind the page

In React, a page is built from components. A component is a JavaScript function whose name starts with a capital letter and which returns the markup for one piece of the page; Lecture 2 gives the rules for writing one. This lecture has one component, SiteHeader, inside a small project prepared for the lesson. Three files of that project matter:

index.htmlthe page the browser loads; its body holds one empty element, <div id="root"></div>
src/main.jsxthe file that hands that empty element to React and tells React to show SiteHeader in it; Lecture 9 explains how
src/SiteHeader.jsxthe header component this lecture writes

Here is the component, with the name written once at its top:

const userName = 'Mary' makes a local variable: a name for a value, inside this function. The markup after return is JSX: it looks like HTML, but it is JavaScript, as Lecture 3 explains. Inside JSX, curly braces mark a place where a JavaScript value goes, so {userName} shows "Mary" in the greeting and again in the corner. export default lets another file, here main.jsx, use this function, as Lecture 8 explains. What SiteHeader returns is a description of the header: it says what each element shows, and React builds the real elements from it.

So each part of the example has its line: the user's name is userName, the greeting is the <p>, the corner is the <span>, and the search box is the <input>, which reads no variable at all, because what it shows comes from the user.

The project runs with the command npm run dev, which starts a dev server: a small program on our computer that sends the project to the browser while we work. Each time we save a file, the dev server sends the new code to the open page, and the page shows the change without a reload. In this lecture the name changes only that way: Mary's profile change is played by us, editing userName in the file and saving. A value that changes while the page is open needs state, which Lecture 14 teaches.

Two ways to change the page when the data changes

FactThe browser does not draw the HTML file directly. It builds one object in memory for every tag, nested the way the tags are nested, and draws the screen from them. Together these objects are the DOM, the Document Object Model, and each one is a DOM node. So to change what the screen shows, something must change the DOM.
FactIn plain JavaScript, document.getElementById('greeting') asks the browser for the DOM node whose id is greeting. Setting that node's textContent replaces the text inside it, and nothing else on the page changes.

There are two ways to change the DOM when the data changes:

Here is the greeting, written each way, for the change from Mary to Mary Brooks. In plain JavaScript, on an older page where the greeting is written in HTML as <p id="greeting"> (section 1 shows that page), our code names the greeting by its id and sets its text; the corner changes only if another line names it too:

Imperative: plain JavaScript
1const greeting = document.getElementById('greeting');
2greeting.textContent = 'Welcome back, Mary Brooks';

In React, the greeting says what it shows. When userName holds "Mary Brooks", React makes the <p> show that name, and no line of our code names the element or sets its text:

Declarative: React
1<p>Welcome back, {userName}</p>

In imperative programming, our code gives the browser every command itself: find this element, set its text. In declarative programming, our code declares what each element shows for the current data, and React makes the DOM match. React is a JavaScript library for building user interfaces out of components, and it is declarative.

Why does the difference matter? Imperative code is fine for one element that changes in one place, such as a clock in the corner of a page. But when the same value shows in several places, imperative code needs one command per place on every change, and a place with no command keeps the old value. And code that rebuilds a part of the page to save writing commands throws away whatever the user typed inside it, as the last section of this lecture shows. Declarative code has no command to forget: each place says what it shows, and React works out the changes.

Keeping each value in one place, which every part of the page reads, is called a single source of truth. A third place that shows the name, such as an account menu, adds one more {userName} and no update code. Lecture 23 uses the same idea when two components must share a value that changes.

FactIn plain JavaScript, setting an element's innerHTML throws away every node inside it and builds new nodes from a string of HTML. textContent only replaces the text inside one node.
FactWhen we click into a text box and type, that box has the focus: it receives the keys we press and shows a blinking cursor. Only one element has the focus at a time; when that element goes away, the focus goes back to the page itself.
Principle 3
The virtual DOM: describing the page again when the value changes

When the value changes, React calls the component again and gets a new description.

React compares the new description with the last one, element by element. It changes only the text that is new.

Every other node stays where it is, so a text box keeps what the user typed, and its focus. Notice: rebuilding the elements with innerHTML makes new nodes, and the typed text is gone.

The description is not the DOM: it is kept in memory as plain JavaScript objects that the browser never draws, which Lecture 3 shows. Because it has the shape of the DOM without being it, people often call it the virtual DOM. The React documentation describes what React does with it as "the minimal necessary operations": for this save, exactly two text changes. When the new description is the same as the last one, React changes no text at all. Lecture 15 gives each step of an update its name.

For the interview

  • What is React? A JavaScript library for building user interfaces out of components. It can run a whole page, or only one part of a page that already exists.
  • How does its model differ from plain JavaScript DOM scripting? In plain JavaScript, our code finds each element and changes it by hand: that is imperative, and an element the code forgets keeps old data, as the corner kept "Mary". In React, a component describes what the page shows for the current data, and React builds and changes the DOM to match: that is declarative. Each value lives in one variable that every place reads, a single source of truth, so no place keeps an old copy.
  • Does React rebuild the page each time the data changes? No, that is the classic trap. React calls the component again and compares the new description with the last one; on our header it changed exactly two texts, and the search box, the same node as before, kept "elections" and the focus. People call the compared description the virtual DOM.
  • Is React faster than changing the DOM by hand? No, and that is not its job. React changes the DOM with the same browser methods a script uses, and a script that sets one text node does that work with less code to run. React's gain is that our code no longer writes, or forgets, the update steps.
  • Does React stop an old name from showing anywhere? Only where the JSX reads the variable. A name typed into the markup as fixed text keeps the old value, even in React.
  • Can I still call document.getElementById inside a component? On the component's first run, its own elements are not on the page yet, so the call returns null; Lecture 10 shows the error this causes. For the few jobs that need one particular element, such as moving the cursor into a search box, React gives a way to reach it without changing what it shows (Lecture 30).

Where you will meet this

  • The signed-in name: shown in a greeting, in the account menu, and beside each comment the user wrote. Each place reads one variable, so a name change reaches all of them at once.
  • A cart count: shown in the header and again on the checkout button. Both read the same count, so the button never promises more items than the cart holds.
  • A search results page: "Results for elections" changes above the list while the same word stays in the search box, because React changes the heading and leaves the box, with its cursor, as the user left it.
  • An unread count: shown in the browser tab and beside the inbox. One variable feeds both, so the tab and the inbox always agree.

Summary

One description, one value, and the smallest change.
