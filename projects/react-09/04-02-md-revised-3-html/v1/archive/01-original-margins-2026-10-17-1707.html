Lecture 1

What is React and the Declarative Model

Interview question❱ CORE
What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

Example: the cart count in a shop's header

An online shoe shop shows the same header at the top of every page. It has three parts: a search box, a line that says how many items are in the cart, and a button to check out. Here is the header while a shopper looks for running shoes, with 2 items already in the cart:

Look closely: the count, 2, appears twice, once in the cart line and once on the button. Now the shopper clicks "Add to cart" under one pair of shoes in the results, and the cart holds 3 items. Here is the header before and after that click:

One click changes one piece of data, the count, and the three parts of the header must answer it in different ways:

on the pageafter the click
the cart line, "Your cart: 2 items"shows 3
the button, "Check out 2 items"shows 3 too; otherwise it tells the shopper the cart holds fewer items than it does
the search box, with "running shoes" typed in itstill holds "running shoes", because the shopper typed it and is still reading its results

Two places must follow the data, and one must stay exactly as the shopper left it. Every website meets this question in some form: when the data changes, how does the page change with it? React's answer is to describe the page from the data and let React change the page to match. That is the topic of this lecture: what is React, and how does its way of building a page differ from changing the page by hand with plain JavaScript?

Two ways to change the page

FactThe browser does not draw the HTML file directly. It builds one object in memory for every tag, nested the way the tags are nested, and draws the screen from them. Together these objects are the DOM, the Document Object Model, and each one is a DOM node. So to change what the screen shows, something must change the DOM.

So when the cart gets a third item, something must change the two DOM nodes that show the count. There are two ways to do it:

FactIn plain JavaScript, document.getElementById('cart-summary') asks the browser for the DOM node whose id is cart-summary. Setting that node's textContent replaces the text inside it, and nothing else on the page changes.

In imperative programming, our code gives the browser each command itself: find this element, set its text. In plain JavaScript, the cart line gets its new count with a line such as this one:

Imperative: plain JavaScript
1document.getElementById('cart-summary').textContent = 'Your cart: 3 items';

In declarative programming, our code says what each element shows, and something else makes the DOM match. In React, the cart line is written once, with a place for the count, and when the count is 3, React makes the line show "Your cart: 3 items":

Declarative: React
1<p>Your cart: {cartCount} items</p>

React is a JavaScript library for building user interfaces out of components, and it is declarative.

Why does the difference matter? Imperative code is fine for one element that changes in one place, such as a clock in the corner of a page. But the count shows in two places, so imperative code needs two commands on every change, and a place with no command keeps the old count, as section 1 shows. And a script that rebuilds the whole header, to avoid writing one command per place, throws away what the shopper typed, as section 3 shows. Declarative code has no command to forget: each place says what it shows, and React works out the changes.

The React project for this lesson

The rest of the lecture writes the header in React. In React, a page is built from components: a component is a JavaScript function whose name starts with a capital letter and which returns the markup for one piece of the page. Lecture 2 gives the rules for writing one. This lecture has one component, ShopHeader, inside a small project prepared for the lesson. Three files of that project matter:

Each piece of this code has a name:

in the codewhat it is
const cartCount = 2a local variable: a name for a value, inside this function
the markup after returnJSX: it looks like HTML, but it is JavaScript, as Lecture 3 explains

What ShopHeader returns is a description of the header: it says what each element shows, and React builds the real DOM nodes from it. Our code never calls ShopHeader; React calls it. The search box reads no variable at all, because what it holds comes from the shopper, not from the data.

How does the count change in this lecture? A value that changes while the page is open, after a click, needs state, which Lecture 14 teaches. Until then, the count is written in the file, and we play the shopper's click ourselves: we change 2 to 3 in ShopHeader.jsx and save. The project runs with the command npm run dev, which starts a dev server: a small program on our computer that sends the project to the browser while we work. Each time we save a file, the dev server sends the new code to the open page, and React updates the page without reloading it.

Three steps in the life of cartCount

The lecture follows the count through three steps, one section each:

Each step needs the one before it. Two places can share the count only once the header is described from it. And the change can be shown whole only once both places read the same variable: then one save changes both, and the search box beside them shows what React leaves alone.

Declarative programming: describing what the page shows, not how to change it

We control the page by describing what it shows from data.

A search of our code finds no getElementById and no textContent. No line names an element, so no element can be forgotten. Section 2 changes the count and shows what that buys.

Principle 2
Single source of truth: describing many places from one value

When one value appears in many places, we keep it in one variable.

We never type a copy of the value into the markup. Notice: a typed copy is fixed text, so it keeps the old value when the variable changes.

Keeping each value in one place, which every part of the page reads, is called a single source of truth. A third place that shows the count, such as a small number on a cart icon, adds one more {cartCount} and no update code. Lecture 23 uses the same idea when two components share a value that changes.

3Virtual DOM comparison: React changes only the new number

Virtual DOM comparison
FactIn plain JavaScript, setting an element's innerHTML throws away every node inside it and builds new nodes from a string of HTML. textContent only replaces the text inside one node.
Principle 3
The virtual DOM: describing the page again when the value changes

When the value changes, React calls the component again and gets a new description.

React compares the new description with the last one, element by element. It changes only the text that is new.

Every other node stays where it is, so a text box keeps what the user typed. Notice: rebuilding the elements with innerHTML makes new nodes, and the typed text is gone.

We should do this

7 </header>

2 const header = document.getElementById('header');

5}

Section 2 gave the count one variable, so one save changes both places. But on every save, ShopHeader returns a description of the whole header, the search box included. What happens to "running shoes", which the shopper typed into that box?

A developer coming from plain JavaScript may expect React to do what many scripts do: rebuild the inside of the header from a string with the new count in it. Here is such a script, on the old page:

Plain JavaScript: rebuild the header with the new count
1const count = 3;
2const header = document.getElementById('header');
3header.innerHTML =
4 '<input placeholder="Search products">' +
5 '<p>Your cart: ' + count + ' items</p>' +
6 '<button>Check out ' + count + ' items</button>';

The script and React give two different headers. Compare the two search boxes:

After the save, React calls ShopHeader again and gets a whole new description of the header. It compares it with the last description, element by element:

elementlast descriptionnew descriptionin the DOM
<input>the search boxthe search boxthe same node stays, with "running shoes" in it
<p>Your cart: 2 itemsYour cart: 3 itemsthe text "2" becomes "3"
<button>Check out 2 itemsCheck out 3 itemsthe text "2" becomes "3"

So for this save, React makes two text changes, and nothing else on the page is rebuilt. Even "Your cart:" and "items" are left alone, because {cartCount} is its own piece of text inside the <p>. The <input> is the same DOM node it was before the save, so it still holds what the shopper typed. innerHTML, instead, throws away every node inside the header and builds new ones, and a new <input> starts empty.

The description is not the DOM: it is kept in memory as plain JavaScript objects that the browser never draws, as Lecture 3 shows. Because it has the shape of the DOM without being it, people often call it the virtual DOM. The React documentation describes what React does with it as "the minimal necessary operations": for this save, two text changes. When the new description is the same as the last one, React changes no text at all. Lecture 15 gives each step of an update its name.

For the interview

  • What is React? A JavaScript library for building user interfaces out of components. It can run a whole page, or only one part of a page that already exists.
  • How does its model differ from plain JavaScript DOM scripting? In plain JavaScript, our code finds each element and changes it by hand: that is imperative, and an element the code forgets keeps old data, as the button kept "2" while the cart held 3. In React, a component describes what the page shows for the current data, and React builds and changes the DOM to match: that is declarative. Each value lives in one variable that every place reads, a single source of truth, so no place keeps an old copy.
  • Does React rebuild the page each time the data changes? No, that is the classic trap. React calls the component again and compares the new description with the last one. On our header it made two text changes, "2" to "3", and the search box, the same node as before, kept "running shoes". People call the compared description the virtual DOM.
  • Is React faster than changing the DOM by hand? No, and that is not its job. React changes the DOM with the same browser methods a script uses, and a script that sets one piece of text does that work with less code to run. React's gain is that our code no longer writes, or forgets, the update steps.
  • Does React stop an old value from showing anywhere? Only where the JSX reads the variable. A value typed into the markup as fixed text keeps the old value, even in React.
  • Can I still call document.getElementById inside a component? On the component's first run, its own elements are not on the page yet, so the call returns null; Lecture 10 shows the error this causes. For the few jobs that need one particular element, such as moving the cursor into a search box, React gives a way to reach it without changing what it shows (Lecture 30).

Where you will meet this

  • The signed-in user's name: shown in the greeting at the top and again in the account menu. Both read one variable, so a name change reaches both at once.
  • An order total: shown in the order summary and on the "Pay" button. Both read one total, so the button never asks for a different amount than the summary shows.
  • A results page: "12 results for running shoes" changes above the list while the same words stay in the search box, because React changes the heading's text and leaves the box as the shopper left it.
  • An unread count: shown in the browser tab and beside the inbox. One variable feeds both, so the tab and the inbox always agree.
