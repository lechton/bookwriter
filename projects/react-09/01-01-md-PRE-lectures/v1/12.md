### An array can be unpacked into names

- [runway] Array destructuring, used by Question 3 and every later question.

- [p] ◇ {array destructuring, named with code the reader knows} Lecture 6 unpacked an object by the names of its properties. An array has no names, only positions, so it is unpacked by position instead: the first name gets the first item, the second name the second item. This is called **array destructuring**: ◼ Educational objective: the refresher the map marks `yes`, set against the object destructuring the reader knows.

- [code] Two ways to unpack:

```js title="Unpacking an object and an array"
const { title } = { title: 'New Park Opens Today' }; // by name
const [first, second] = ['Mary Jones', 'Oliver Brooks']; // by position
// first is 'Mary Jones', second is 'Oliver Brooks'
```

◼ **The what-this-introduces list:** 1. `[first, second] = [...]`: array destructuring.

- [p] ◇ {the rule} The names in the square brackets are ours to choose; only their order matters. Array destructuring takes items by position, so the first name always gets the first item. ◼ Educational objective: the closing rule, which explains why `useState`'s pair can be named freely.

### useState asks React to keep a value

- [runway] `useState`, the Hook, the state variable, and the setter function, used by every question from Question 1's fix on.

- [p] ◇ {what it is for, then its name and its code} React offers a way to ask for a value it keeps between runs. The tool is a function named `useState`, imported from `react`. We call it once, at the top of the component, with the value to start from, and it gives back an array of exactly two things, which we unpack at once: ◼ Educational objective: say what the code is for before it appears; the form every fix of the lesson uses.

- [code] ArticleCard.jsx, lines 1 to 4, a value React keeps:

```jsx title="ArticleCard.jsx"
import { useState } from 'react';

export default function ArticleCard({ article }) {
  const [likes, setLikes] = useState(0); // starts at 0
```

◼ **The what-this-introduces list:** 1. `useState(0)`: asks React to keep a value that starts at 0. 2. `[likes, setLikes]`: the two things it gives back.

- [p] ◇ {the two names and the word Hook} `likes` is the **state variable**: the value for this run of the component. `setLikes` is the **setter function**: it stores a new value. By convention the pair is named `[something, setSomething]`. Functions whose names start with `use`, such as `useState`, are called **Hooks**: they let a component use something React offers, here a memory, and they work only while React runs the component. The questions below show what each half of the pair does. ◼ Educational objective: the four terms with their plain meaning and the naming convention (react.dev `<Note>`), named before the questions use them and explained by them.

### The browser can keep a value after a reload

- [runway] `localStorage` and `Number()`, used by Question 6 and Step 3.

- [p] ◇ {localStorage, named with code} Everything React keeps is lost when the page reloads. The browser itself can keep short texts for a site, even after a reload: this store is **`localStorage`**. `localStorage.setItem(name, value)` stores a text under a name, and `localStorage.getItem(name)` reads it back, or gives `null` when nothing is stored. Reading it takes the browser some work, which matters for Question 6. ◼ Educational objective: the refresher the map marks `yes`, with what each call gives back.

- [code] Storing and reading a count:

```js title="localStorage"
localStorage.setItem('likes-1', 3); // stored as the text '3'
Number(localStorage.getItem('likes-1')); // 3, a number again
Number(localStorage.getItem('likes-9')); // 0: nothing stored, Number(null)
```

◼ **The what-this-introduces list:** 1. `setItem` and `getItem`. 2. `Number(...)`: turns a text, or `null`, into a number.

### Principles of React: Component Memory

- [preview] Everything in this lesson comes down to one idea: component memory, which means a value React keeps for one component between its runs. The first stretch shows why a plain variable cannot be that memory. First, local variables, which means the value changes, but the screen keeps the old one: a value that must change on the screen never lives in a plain variable. Second, re-rendering, which means the value starts over on every run: a plain variable lasts only for one run of the component. The second stretch shows how React keeps the value. Third, state, which means the value React keeps, with a setter that changes it: we read the value, and we change it only through its setter. Fourth, multiple state variables, which means the values React tells apart by the order of the calls: we ask for each value at the top of the component, never inside a condition. Fifth, component instances, which means the value each copy keeps for itself: two copies of one component never share their state. The last stretch shows how the value starts and how it changes. Sixth, initializer functions, which means the starting value computed only once: an expensive start is passed as a function. Seventh, setters in event handlers, which means the value changes only when the user acts: a setter runs in a handler, never while the component runs. ◼ Educational objective: the map's Spoken Preview, word for word, one paragraph for the anchor and one per stretch and principle in the lecture, read aloud before Question 1.

> [!PRINCIPLE]
> **Principle 1: Local variables: the value changes, but the screen keeps the old one**
> *The screen keeps the value it got when the component ran, so a value that must change on the screen never lives in a plain variable: changing that variable changes nothing on the page.*
>
> When React runs a component, the `{count}` in its JSX puts the current value of `count` on the screen, for example 0. A click handler then changes `count` to 1, but nothing puts the new value on the screen. The screen changes only when React runs the component again, because only then is `{count}` read again. Changing a variable does not make React run the component. Calling a setter does, as Principle 3 shows.
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1); // React runs the component again`
>
> *We should not do this:*
> `let count = 0;`
> `count = count + 1; // the screen still shows 0`

> [!PRINCIPLE]
> **Principle 3: State: the value React keeps, with a setter that changes it**
> *`useState` gives a value that lasts and a function that changes it: we read the state variable and never assign to it, and every change goes through its setter.*
>
> A value on the screen needs two things. It must keep its value from one run of the component to the next. And changing it must make React run the component again, so the screen shows the new value. A plain variable does neither. `useState` gives both, in one line: `const [count, setCount] = useState(0)`.
>
> - `count` is the **state variable**, the current value: 0 on the first run. We read it, and we never assign to it.
> - `setCount` is the **setter function**. `setCount(1)` stores 1 and makes React run the component again. In that run, `count` is 1.
>
> >> state variable : a value that keeps its value from one run of the component to the next
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1); // the screen shows 1`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `count = count + 1; // TypeError, the screen stays at 0`

> [!PRINCIPLE]
> **Principle 4: Multiple state variables: the values React tells apart by the order of the calls**
> *React keeps state outside the component and matches it by order: we call `useState` once per value at the top of the component, never inside an `if`.*
>
> Each run calls the component's function from its first line, so `useState(0)` runs again on every run. We might expect it to set `count` back to 0, as `let count = 0` does. It does not. React keeps the value itself, outside our function. On the first run, `useState(0)` stores 0. On every later run, React ignores the 0 and returns the stored value.
>
> A component can call `useState` several times, once for each value. React never sees our names `count` or `isOn`. It matches each call to its stored value only by order: first call, second call. So the calls must come in the same order on every run, which means never inside an `if`.
>
> *We should do this:*
> `const [count, setCount] = useState(0); // first call`
> `const [isOn, setIsOn] = useState(false); // always the second call`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `if (count > 0) {`
> `  const [isOn, setIsOn] = useState(false); // React throws an error`
> `}`

> [!PRINCIPLE]
> **Principle 5: Component instances: the value each copy keeps for itself**
> *Each copy of a component on the screen keeps its own state: a value per copy lives in state inside the component, never in a variable outside it, and the parent cannot read or change it.*
>
> One component function can appear on the screen many times. A parent that returns `<Counter />` twice shows two counters. Both copies run the same function, with the same `useState(0)` line, so we might expect them to share one count. They do not. React keeps a separate set of stored values for each copy on the screen, called a **component instance**. A click on the first counter changes only the first count, and React runs only that copy again.
>
> >> component instance : one copy of a component on the screen, with its own stored values
>
> *We should do this:*
> `function Counter() {`
> `  const [count, setCount] = useState(0); // one count per copy`
> `  const add = () => setCount(count + 1);`
> `  return <button onClick={add}>{count}</button>;`
> `}`
>
> *We should not do this:*
> `let count = 0; // one variable shared by every copy`
> `function Counter() {`
> `  const add = () => { count = count + 1; }; // screen stays at 0`
> `  return <button onClick={add}>{count}</button>;`
> `}`

### Question 6: The saved count is read again on every click

- [question-cycle] Question 6: The saved count is read again on every click
    - Question: "My starting count is read from saved data. Why does that code run on every click?"
    - Code and result: `getSavedLikes(id)` above the component (lines 3 to 6) logs "reading saved likes" with the id and reads the count from `localStorage`; the card starts its state with it, `useState(getSavedLikes(article.id))` on line 9; on load the log appears twice for each card, and two Likes on the first card add two more pairs of "reading saved likes 1" (verified in React 19.3.1 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: the reader knows from Question 4 that React uses the starting value only once, so the code that makes it should run once; but React uses the argument of `useState` only on the first run and ignores it after that, while the whole line still runs on every run; in JavaScript, `f()` calls a function at once and passes its result, while `f` passes the function itself (Lecture 2); so `useState(getSavedLikes(article.id))` calls `getSavedLikes` on every run, reads `localStorage` each time, and React throws the result away; passing a function instead, an **initializer function**, lets React call it only on the first run: `useState(() => getSavedLikes(article.id))`, an arrow because `getSavedLikes` needs the id, while a function with no argument passes by name, `useState(createItems)`; with Strict Mode, React calls the initializer twice on the first run and keeps one result (Lecture 12), so the log appears twice on load and never after; a cheap value such as `0` needs no function; and because a function given to `useState` is always treated as an initializer, storing a function itself as state needs `useState(() => fn)`.
    - Fix: `useState(() => getSavedLikes(article.id))` on line 9; the log appears only on load, and the Likes add none (verified).
    - Rule: we pass an expensive starting value as a function, `useState(createItems)` or `useState(() => readSaved(id))`, so React computes it only on the first run; a cheap value such as `0` needs no function.
    - Needs: `localStorage` and `Number()` (runway "The browser can keep a value after a reload"); call against reference (recall Lecture 2); the arrow function (recall Lecture 11); Strict Mode's second call (recall Lecture 12); the argument ignored after the first run (Question 4).
    - Window plan: `ArticleCard.jsx`, lines 3 to 9 (`startLine="3"`); the fix, line 9 (`startLine="9"`).

> [!PRINCIPLE]
> **Principle 6: Initializer functions: the starting value computed only once**
> *We pass an expensive starting value as a function, `useState(createItems)` or `useState(() => readSaved(id))`, so React computes it only on the first run; a cheap value such as `0` needs no function.*
>
> React uses the starting value of `useState` only on the first run and ignores it after that. In JavaScript, `f()` calls a function at once and passes its result, while `f` passes the function itself. Each run of the component executes the whole `useState` line. So `useState(createItems())` calls `createItems` on every run, and React throws each later result away. When `createItems` does slow work, that work is wasted on every run. `useState(createItems)` passes the function itself, an **initializer function**, and React calls it only on the first run. A cheap starting value such as `0` needs no function.
>
> >> initializer function : a function passed to useState that React calls once to make the starting value
>
> *It is best practice to do this:*
> `const [items, setItems] = useState(createItems); // first run only`
>
> *Instead of doing this:*
> `const [items, setItems] = useState(createItems()); // every run`

### Question 7: A setter in the onClick crashes the page

- [question-cycle] Question 7: A setter in the onClick crashes the page
    - Question: "I wrote `onClick={setLikes(likes + 1)}`. Why does the page crash before I click?"
    - Code and result: the state card of Question 3 with the handler skipped: `<button onClick={setLikes(likes + 1)}>Like ({likes})</button>` on line 12; the page goes blank as it loads, and the console shows "Too many re-renders.     - Verdict: does not do what the reader wanted.
    - Answer: the reader expects the setter to be stored for the click, as `onclick="..."` stores code in HTML; in Lecture 13 the same mistake only ran a handler too early; with a setter it is worse: the braces run `setLikes(likes + 1)` while React runs the card, before anyone clicks; the setter makes React run the card again; that run calls the setter again, which asks for another run, and so on; React stops the loop with the error, and the page goes blank; `onClick={handleLike}`, with the setter inside `handleLike`, or `onClick={() => setLikes(likes + 1)}`, passes a function, and the setter runs only on the click.
    - Fix: `<button onClick={handleLike}>` with `setLikes(likes + 1)` inside `handleLike`; the cards show, and each click counts (verified).
    - Rule: we call a setter only when the user acts, inside an event handler, never in the component's body and never as a call written in an event prop.
    - Needs: pass, never call (recall Lecture 13); the setter runs the card again (Question 3).
    - Window plan: `ArticleCard.jsx`, line 12 (`startLine="12"`).
    - Diagram: the loop of runs and setter calls.

> [!PRINCIPLE]
> **Principle 7: Setters in event handlers: the value changes only when the user acts**
> *We call a setter only when the user acts, inside an event handler, never in the component's body and never as a call written in an event prop.*
>
> We give a button a function to run on click with `onClick={...}`.
> When does that function run? We expect it to run when the user clicks.
> But `onClick={setCount(count + 1)}` runs the setter already when the component appears on the screen, not when the user clicks.
> The setter makes React draw the component again. Drawing it again runs the setter again, and so on, until React stops with an error.
> Instead, write `onClick={() => setCount(count + 1)}`. Now the setter runs only when the user clicks.
>
> *We should do this:*
> `<button onClick={() => setCount(count + 1)}>Add</button> // on click`
>
> *We should not do this:*
> `<button onClick={setCount(count + 1)}>Add</button> // runs at once`

- [grounding] Where does a Like go when the page reloads? ◼ Friction target: the line between React's memory and the browser's storage, which the cycles touched in Question 6. Tactile scene: the reader likes an article three times and saves another, then presses the browser's reload button. Bold key terms: **state**, **localStorage**. Concrete operational resolution: state lives only as long as the page is open; a reload starts every component from its first run, so every `useState` starts again from its starting value; a count the user must find again is written to `localStorage` in the click handler, which is allowed to change the world outside (Lecture 13), and read back by the initializer function on the first run; Saved, which is never written anywhere, comes back as Save. ◼ Educational objective: one `> [!WILD]` card after the principles, adding a fact the cycles did not state (state does not survive a reload), verified in Step 3.

### For the interview

- [interview] > **The Interview Question:** Why do ordinary variables forget their values between renders, and how does useState remember?

- [interview] **1. The Hidden Signal** ◼ The interviewer wants two reasons a variable fails, and the mechanism that fixes both. A junior answer says "use useState because React says so". A strong answer says that changing a variable does not make React run the component, that each run starts the variable over, and that React keeps state outside the function, matched by the order of the calls, one set per copy.

- [interview] **2. The Classic Trap** ◼ The classic trap is "React reads the name, so `useState` can go anywhere". On the article card, a `useState` inside `if (likes > 0)` worked on the first run and crashed on the first Like with "Rendered more hooks than during the previous render.", because React matches values by the order of the calls, not by their names.

- [interview] **3. What is Actually Going On** ◼ With `let likes = 0`, three Likes logged 1, 2, 3 and the button stayed at "Like (0)": nothing ran the card again, and a later run set `likes` back to 0. With `const [likes, setLikes] = useState(0)`, `setLikes(likes + 1)` stored 1 and made React run the card again, and in that run `useState` returned 1. Each of the three cards kept its own count, and `isSaved` sat in the second call on every run.

- [interview] **4. Where It Gets Tricky** ◼ *Why can't I assign to the state variable?* It is a `const`, and even with `let`, assigning changes nothing on screen; only the setter stores the value and runs the component again. *Does `useState(0)` reset the value on every run?* No: React uses the argument only on the first run. *Why does my starting function run on every click?* `useState(f())` calls it on every run; pass `f`, or `() => f(id)`. *Why does Strict Mode call my initializer twice?* To check it is pure; it keeps one result (Lecture 12). *Why "Too many re-renders"?* A setter called while the component runs asks for another run, forever. *Why does a log right after the setter print the old value?* Lecture 16 answers it.

### Glossary

- [glossary] State ◼ A value React keeps for one component between its runs. Changing it through its setter makes React run the component again with the new value.
- [glossary] `useState` ◼ The Hook that asks React for one state value. It takes the starting value and gives back a pair: the value for this run and its setter.
- [glossary] Hook ◼ A function whose name starts with `use`, such as `useState`, that lets a component use something React offers. Hooks are called at the top of a component, in the same order on every run.
- [glossary] Setter function ◼ The second half of the pair, such as `setLikes`. It stores the next value and makes React run the component again; it is called in event handlers.
- [glossary] Component instance ◼ One copy of a component on the screen, with its own stored state values.
- [glossary] Initializer function ◼ A function passed to `useState`, such as `() => getSavedLikes(id)`, that React calls only on the first run to make the starting value.

### Summary

- [review-title] **Component memory: a value React keeps for one component between its runs**

- [review-subtitle] ❒ Local variables: the value changes, but the screen keeps the old one
- [never-rule] ➔ NEVER keep a value the screen shows and the user changes in a plain variable; changing it changes nothing on the page.

- [review-subtitle] ❒ Re-rendering: the value starts over on every run
- [if-then-rule] ➔ IF a later run needs the value THEN keep it in state; a plain variable starts over on every run.
- [if-then-rule] ➔ IF a value is computed from state on every run THEN a plain `const` is right for it.

- [review-subtitle] ❒ State: the value React keeps, with a setter that changes it
- [always-rule] ➔ ALWAYS change state through its setter, `setLikes(likes + 1)`.
- [never-rule] ➔ NEVER assign to the state variable; it throws with `const`, and changes nothing with `let`.

- [review-subtitle] ❒ Multiple state variables: the values React tells apart by the order of the calls
- [always-rule] ➔ ALWAYS call `useState` at the top of the component, once per value, in the same order on every run.
- [never-rule] ➔ NEVER call `useState` inside an `if`; decide what to show in the JSX instead.

- [review-subtitle] ❒ Component instances: the value each copy keeps for itself
- [always-rule] ➔ ALWAYS keep a value per copy in state inside the component.
- [never-rule] ➔ NEVER move a value outside the component to make it survive; every copy then shares it.

- [review-subtitle] ❒ Initializer functions: the starting value computed only once
- [if-then-rule] ➔ IF the starting value takes work to compute THEN pass a function: `useState(createItems)` or `useState(() => readSaved(id))`.
- [if-then-rule] ➔ IF the starting value is cheap, such as `0` THEN pass it as it is.

- [review-subtitle] ❒ Setters in event handlers: the value changes only when the user acts
- [always-rule] ➔ ALWAYS call a setter inside an event handler.
- [never-rule] ➔ NEVER write a setter call in an event prop or in the component's body; it loops until "Too many re-renders".

- [closing-line] Not a variable but state: kept by React, told apart by order, one per copy, started once, and changed on a click. ◼ Educational objective: the map's Closing Line, the last spoken sentence of the lesson.
