### An arrow function is a short way to write a function

- [runway] The arrow function, with its short body and its block body, used by Questions 1 to 4.

- [p] ◇ {the arrow function, named with code the reader knows} Every function so far began with the word `function`. JavaScript has a shorter way to write a small function, the **arrow function**: the parameters, then `=>`, then what the function gives back. When nothing but an expression follows the arrow, the function gives that expression back by itself, with no `return`. ◼ Educational objective: the refresher the map marks `yes` (Terms row `arrow function (() => ...)`), from the form the reader knows to the new one.

- [code] One function, written two ways:

```js title="Two ways to write one function"
function double(n) {
  return n * 2; // the classic form
}
const double = n => n * 2; // the arrow form: n in, n * 2 back
```

◼ **The what-this-introduces list:** 1. `n => n * 2`: an arrow function that gives back `n * 2`.

- [p] ◇ {the block body, then the rule} When a curly brace follows the arrow, the function has a **block body**: room for several lines, and a `return` is needed to give anything back. Without it, the function gives back `undefined`. An arrow function gives back the expression right after `=>`; after `=> {`, it gives back only what `return` names. ◼ Educational objective: the rule react.dev's arrow-function `<Pitfall>` states, taught before Question 1 breaks it.

- [code] A block body needs `return`:

```js title="The block body"
const half = n => {
  return n / 2; // with a curly brace, return is needed
};
const broken = n => { n / 2; }; // gives back undefined
```

◼ **The what-this-introduces list:** 1. `=> {`: a block body. 2. `broken`: the same function without `return`.

### Three array methods take a function

- [runway] `forEach()`, `map()`, `filter()`, and `length`, in plain JavaScript first, used by Questions 1 and 2 and Steps 1 and 2.

- [p] ◇ {three methods that take a function} An array has methods, functions that belong to it (Lecture 9), and three of them take a function and call it once for each item. **`forEach()`** only calls the function and gives back `undefined`. **`map()`** collects what the function gives back for each item into a new array of the same length. **`filter()`** keeps the items for which the function gives back `true`, in a new, often shorter array. **`length`**, a property with no parentheses, counts the items. ◼ Educational objective: plain JavaScript first (`principle-definition` Pass 3): what each method gives back, before React meets any of them.

- [code] The three methods on the articles:

```js title="Three array methods"
articles.forEach(article => article.title); // undefined
articles.map(article => article.title); // three titles, in order
articles.filter(article => article.topic === 'Food'); // one article
articles.length; // 3
```

◼ **The what-this-introduces list:** 1. `forEach`: calls, gives back nothing. 2. `map`: gives back a new array of results. 3. `filter`: gives back the items that pass. 4. `length`: the number of items.

- [p] ◇ {the rule} `map()` turns every item into something new, `filter()` chooses which items stay, and `forEach()` gives back nothing at all. ◼ Educational objective: the closing rule of the runway, the fact Questions 1 and 2 recall in a few words.

### Principles of React: Rendering Lists

- [preview] Everything in this lesson comes down to one idea: rendering a list, which means that an array of data becomes an array of elements, each with its own key. First, mapping, which means turning every item into an element: we call map on the array, and the arrow function gives back one element for each item. Second, filtering, which means turning only some items into elements: we filter the array before we map it, and when nothing is left, we show a message instead of an empty space. Third, keys, which means naming each element so React can tell the items apart: each key comes from the item's own id, so a new item at the top leaves every other item with its own element. Fourth, the key's place, which means naming the element the map gives back: the key goes on the tag written inside the map, never inside the child component. ◼ Educational objective: the map's Spoken Preview, word for word, one paragraph for the anchor and one per principle in the lecture, read aloud before Question 1.

>

> `{items.map(item => {`

> `})}`

> *To show only some items, we call `filter()` before `map()`; when the filtered array can be empty, we test its length with `> 0` and show a message instead.*

### Question 3: A typed comment jumps to another article

- [question-cycle] Question 3: A typed comment jumps to another article
    - Question: "The cards show fine. Why does React insist on a key?"
    - Code and result: `ArticleList` with the map of Question 1 and no key; the console shows "Each child in a list should have a unique "key" prop."; with the dev server running, "Great news!" is typed into the comment box of "Rain Expected This Weekend", the second card; then a new article, "Library Opens on Sundays" by James Smith, `id: 4`, is added at the top of `articles.js` and the file is saved; the page shows four cards, and "Great news!" now sits under "New Park Opens Today", the second card, while Rain's box is empty (verified in React 19.3.1, Vite 8.3.4, and Chrome).

    - Answer: the reader takes the key for something that only quiets the console, and the page looked fine, so the guess is fair until the list changes; when the saved file arrives, React shows the list again and matches each new element with one it already built, so that it can keep it and only change what differs; without a key, it matches by position: the first new element with the first old one, the second with the second; the new article at the top shifts every article down one position, so the old second element, the one whose box holds "Great news!", now receives "New Park Opens Today"; React changes its title and author and keeps its box as it is, typed text and all; the junior fix, `key={index}`, makes the warning go away, and the text moves all the same, because the index is the position (verified); a **`key`** names each element: with `key={article.id}`, React matches by id, keeps Rain's element with its box, moves it down, and builds one new element for the new article; react.dev compares keys to file names in a folder, which survive a reorder while positions do not; a key must be unique among the siblings of one list, or the console says "Encountered two children with the same key"; it must not change, so `key={Math.random()}` makes every element new on every save, and the typed text is lost (verified); keys come from the data: a database id, or an id made when the item is created; the index is fine only for a list that never inserts, deletes, or reorders, such as the lines of a poem; Lecture 61 returns to keys with sorting and deleting.

> [!PRINCIPLE]
> **Principle 3: Keys: naming each element so React can tell the items apart**
> *We give each element a `key` from the item's own id, so React matches every item with the same element the next time the list is shown; the array index fits only a list that never changes order, and a key made while rendering fits nothing.*
>
> When a list is shown again, React matches each new element with one it already built, keeps it, and changes only what differs. Without a key, it matches by position: the first with the first. An item added at the top shifts every item down, so each old element receives the next item's data, and whatever the user typed stays behind under the wrong item. The index is the position again, so it fails the same way. A **key** taken from the item's own id names each element, and React matches by name: every item keeps its element, and only the new item gets a new one. A key made while rendering, such as a random number, matches nothing, so every element is built again.
>
> *We should do this:*
> `{items.map(item => (`
> `  <Item key={item.id} item={item} /> // follows the item`
> `))}`
>
> *We should not do this:*
> `{items.map((item, index) => (`
> `  <Item key={index} item={item} /> // follows the position`
> `))}`

> [!PRINCIPLE]
> **Principle 4: The key's place: naming the element the map gives back**
> *We write the `key` directly on the tag the `map()` call gives back, never inside the child component and never inside a spread object, and when the child needs the id, we pass it again as a prop of its own.*
>
> React needs the key on the items of the array it receives, and that array holds the elements `map()` gave back. A key on an element inside the child component sits on the child's own markup, not on an array item, so the warning stays. React also keeps the key for itself: the child receives no `key` prop, and reading it gives `undefined`. So the key goes on the tag written inside `map()`, and a child that needs the id receives it again under another name. An item made of several elements uses `<Fragment key={...}>`, because `<>` takes no key.
>
> *We should do this:*
> `{items.map(item => (`
> `  <Item key={item.id} item={item} /> // on the array item`
> `))}`
>
> *We should not do this:*
> `function Item({ item }) {`
> `  return <li key={item.id}>{item.name}</li>; // warning stays`
> `}`

- [grounding] Why does the index work in so many tutorials? ◼ Friction target: the map's Merged row on the index for a list that never changes order, and the Preview of Lecture 61. Tactile scene: a tutorial maps a fixed array of five menu links with `key={index}`, and nothing ever goes wrong. Bold key terms: **key**, **index**. Concrete operational resolution: the index fails only when an item is added, removed, or moved, and only when an element holds something the data does not, such as text typed into a box; a fixed menu never changes and holds nothing typed, so its index keys never meet the bug; the article list gains a new article at the top every day, so it meets it at once; Lecture 61 shows the same bug with sorting and deleting, and what makes a good key. ◼ Educational objective: one `> [!WILD]` card after the principles, adding a fact the cycles did not state (when the index is harmless), with its owner lesson named in one sentence.

### For the interview

- [interview] > **The Interview Question:** How do you render a list from an array, and why does React demand a key on every item?

- [interview] **1. The Hidden Signal** ◼ The interviewer wants two things: that `map()` turns data into elements because React shows arrays of elements, and that the key is identity, not decoration. A junior answer says "keys stop the warning". A strong answer says what React does with the key on the next render, why the index fails when items are added at the top, and where the key goes.

- [interview] **2. The Classic Trap** ◼ The classic trap is "the index is unique, so it is a good key". On the article site, `key={index}` silenced the warning, and when a new article was saved at the top, the comment typed under "Rain Expected This Weekend" appeared under "New Park Opens Today". The index is unique, but it names the position, and positions shift.

- [interview] **3. What is Actually Going On** ◼ `articles.map(article => <ArticleCard key={article.id} article={article} />)` gives React an array of three elements, each named by its article's id. When the saved file adds "Library Opens on Sundays" at the top, React matches each new element with the old one of the same key, keeps Rain's element and its typed comment, moves it down, and builds one new element. Without a key, React matches by position, so the second old element, which holds the comment, receives the park article's data.

- [interview] **4. Where It Gets Tricky** ◼ *Can a child read its own key?* No: it gets `undefined`, and the console says "`key` is not a prop"; pass the id again under another name. *Where does the key go when the card is wrapped in an `<li>`?* On the `<li>`, the tag `map()` gives back. *What about an item made of two elements?* `<Fragment key={id}>`, because `<>` takes no key. *Must keys be unique across the whole page?* Only among the siblings of one list. *Is the index ever fine?* For a list that never inserts, deletes, or reorders. *Why not `key={Math.random()}`?* It changes on every render, so every element is built again and typed text is lost. *Why does an empty topic show `0`?* `length && ...` gives back the `0`, a number; ask `length > 0`.

### Glossary

- [glossary] Rendering a list ◼ Turning an array of data into an array of elements, usually with `map()`, so that React shows one element per item.
- [glossary] Arrow function ◼ A short way to write a function: `item => <Item item={item} />` gives back the expression after `=>`; after `=> {`, only `return` gives anything back.
- [glossary] `map()` ◼ An array method that calls a function for each item and gives back a new array of the results, the same length as the original.
- [glossary] `filter()` ◼ An array method that keeps the items for which a test gives back `true`, in a new array.
- [glossary] Key ◼ A name React gives each element of a list, written as `key={item.id}` on the tag inside `map()`. React matches elements by key from one render to the next; the component never receives it.
- [glossary] Index as key ◼ The item's position used as its key. It matches by position, so it moves typed text and focus when items are added, removed, or reordered.

### Summary

- [review-title] **Rendering a list: an array of data becomes an array of elements, each with its own key**

- [review-subtitle] ❒ Mapping: turning every item into an element
- [always-rule] ➔ ALWAYS call `map()` inside the JSX, and give the element back right after `=>`, or with `return` after `=> {`.
- [never-rule] ➔ NEVER use `forEach()` or a `for` loop inside the braces; they give back nothing the page can show.

- [review-subtitle] ❒ Filtering: turning only some items into elements
- [always-rule] ➔ ALWAYS call `filter()` before `map()` when only some items should show.
- [if-then-rule] ➔ IF the filtered array can be empty THEN test `length > 0` and show a message instead.

- [review-subtitle] ❒ Keys: naming each element so React can tell the items apart
- [always-rule] ➔ ALWAYS take the key from the item's own id.
- [if-then-rule] ➔ IF the list never inserts, deletes, or reorders THEN the index is a safe key; otherwise it moves typed text to the wrong item.
- [never-rule] ➔ NEVER make a key while rendering, such as `Math.random()`.

- [review-subtitle] ❒ The key's place: naming the element the map gives back
- [always-rule] ➔ ALWAYS write the key on the tag written inside `map()`, directly, not inside a spread object.
- [if-then-rule] ➔ IF the child needs the id THEN pass it again as a prop of its own; the child never receives `key`.

- [closing-line] Every item, only some items, one name each, and the name on the right element. ◼ Educational objective: the map's Closing Line, the last spoken sentence of the lesson.
