### Every web application calculates user interfaces from dynamic data

- [p] ◇ {theme: calculating user interfaces from data inputs} Every web application computes user interfaces from underlying data. An online store calculates cart summaries, a dashboard computes live metrics, and a content feed transforms arrays of articles into visual cards. In standard JavaScript scripting, developers frequently declare outside variables and write step-by-step instructions that modify those variables or reach into the browser document. In React, a component is a function that calculates what the interface should look like: `UI = f(props)`. To ensure that user interfaces render reliably without visual corruption or race conditions, React assumes that every component function you write is a pure function. ◼ Educational objective: introduce the universal architectural requirement of computing interfaces purely from input data.

- [p] ◇ {starting point: imperative mutation versus declarative pure formulas} In traditional imperative programming, functions freely read and write global variables, mutate shared lists, or modify the document with `document.getElementById()`. If a developer numbers list items by incrementing an outside counter variable inside a component, the application quickly breaks. In development mode, the counter increments twice per render, jumping from `#1` to `#2` and `#4`. In React, a component treats rendering as a mathematical formula: given the same inputs, it must return the exact same JSX, and it must never change any variable or system that existed before the function ran. ◼ Educational objective: contrast legacy mutable scripting habits with React's pure rendering contract.

### What makes a function pure: identical inputs, identical output, and zero side effects

- [runway] The definition of a pure function, mathematical formulas, and the render contract, used by Question 1 and Question 4.

- [p] ★ {preknowledge: functions returning values and JSX expressions} In Lecture 2 and Lecture 4, we saw that React components are JavaScript functions that accept props and return JSX element descriptions. In computer science and functional programming, a **pure function** is a function that satisfies two strict rules: first, it minds its own business, meaning it never modifies any variable, object, or system that existed before it was called; second, same inputs always produce the exact same output. A classic example is a math formula such as `y = 2x`. If `x` is 2, `y` is always 4. If `x` is 3, `y` is always 6. The answer never changes based on the time of day or what other formulas were calculated earlier. ◼ Educational objective: define a pure function using mathematical formulas and establish the two core laws of purity.

- [p] ★ {mechanism: components as mathematical formulas} React is built directly on this mathematical foundation. React assumes that every component function is a pure calculation. Given the same props, a component must always return the exact same JSX tree. When a component only calculates markup from its inputs without touching outside systems, React can run that component at any time, run sibling components in any order, or run the function multiple times without corrupting application data. ◼ Educational objective: establish the pure component model where JSX is a deterministic output of inputs.

- [code] Pure calculation versus external variable reading:

```jsx title="Pure Calculation"
// Pure: returns exact same JSX for given prop
function PureDouble({ number }) {
  const result = number * 2;
  return <p>Result: {result}</p>; // Deterministic
}

let outsideFactor = 2; // Outside variable
function ImpureDouble({ number }) {
  return <p>Result: {number * outsideFactor}</p>;
}
```

◼ **The what-this-introduces list:** 1. `PureDouble`: pure component returning predictable output. 2. `outsideFactor`: outside variable breaking formula independence. 3. `ImpureDouble`: impure component producing differing output if factor changes.

### How React runs components during render and why StrictMode double-calls in development

- [runway] The render phase, module-level variables, and StrictMode double-invocation in development, used by Question 1 and Question 2.

- [p] ★ {preknowledge: top-level component execution and StrictMode} In Lecture 4, we learned that development environments wrap the root application in `<StrictMode>`. To understand why StrictMode behaves the way it does, we must understand the **render phase**. Rendering refers to the process where React calls your component function to find out what the next screen description should look like. Code written at the top level of your component function body executes during this render phase. Because React may need to recalculate the interface when data changes, React does not promise to call your component exactly once per screen change. ◼ Educational objective: explain the render phase and top-level component execution.

- [p] ★ {mechanism: module-level variables survive across render calls} A **module-level variable** is a variable declared at the top of a file, outside of any component function. While local variables declared inside a component are recreated fresh on every call, a module-level variable lives in module scope and survives for the entire lifetime of the browser tab. If a component modifies a module-level variable during render, that mutation persists across calls. In development, `<StrictMode>` intentionally calls every component function twice during every render pass. If a component is pure, calling it twice produces identical JSX and causes zero harm. But if a component mutates an outside module variable, that mutation executes twice on page load, immediately exposing the bug. ◼ Educational objective: contrast module-level variables with local variables and explain why StrictMode double-rendering exposes impure mutations.

- [code] Module-level variable mutation under StrictMode:

```jsx title="Module Variable Mutation"
let renderPass = 0; // Module-level variable

export default function CounterCard() {
  renderPass = renderPass + 1; // Mutates outside variable
  return <div>Render pass #{renderPass}</div>;
}
```

◼ **The what-this-introduces list:** 1. `let renderPass = 0`: module-level variable persisting across calls. 2. `renderPass = renderPass + 1`: mutation executed in render body. 3. `StrictMode double call`: increments counter to 2 on first load.

### The difference between local mutation and external mutation

- [runway] Mutation boundaries, local arrays and objects, and immutable props, used by Question 2.

- [p] ★ {preknowledge: JavaScript objects, arrays, and props immutability} In Lecture 6, we established that props are strictly read-only. In JavaScript, **mutation** means modifying the contents or properties of an existing object or array in place without creating a new reference. Developers often wonder whether React forbids all JavaScript mutation. The answer is no: React explicitly allows **local mutation**. Local mutation means changing variables, arrays, or objects that were created inside that exact same render call. ◼ Educational objective: define mutation and distinguish between forbidden external mutation and valid local mutation.

- [p] ★ {mechanism: local mutation safety versus mutating inputs} If you create a brand-new array inside a component function body using `const items = [];` and call `items.push(...)` inside a loop to assemble list items, that code is 100% pure. Because the array was born inside that specific render call, no other component or function in the application can see it. When the component finishes executing, the local array is encapsulated in the returned JSX. However, calling `array.push()` on an array received as a prop or declared at the module level modifies data that existed before the render. Under StrictMode, that `push()` runs twice, duplicating items in memory. Furthermore, mutating a local object after passing it into a JSX element modifies the element because both share the same reference. ◼ Educational objective: derive why mutating newly created local data is safe while mutating preexisting objects or props corrupts application state.

- [code] Local mutation versus external mutation:

```jsx title="Local Array Mutation"
// Safe local mutation: array created in this render
function ItemList({ count }) {
  const items = []; // Fresh local array
  for (let i = 0; i < count; i++) {
    items.push(<li key={i}>Item {i + 1}</li>);
  }
  return <ul>{items}</ul>; // Pure return
}
```

◼ **The what-this-introduces list:** 1. `const items = []`: fresh local array created inside render. 2. `items.push(...)`: safe local mutation before JSX return. 3. `return <ul>{items}</ul>`: pure JSX constructed from local values.

### What belongs in render versus what belongs in event handlers

- [runway] Side effects, imperative DOM manipulation, non-idempotent calls, and declarative JSX expressions, used by Question 3 and Question 4.

- [p] ★ {preknowledge: browser DOM nodes, errors, and conditional expressions} In Lecture 1, we saw that scripts interact with the DOM using `document.getElementById()`. In Lecture 10, we saw that reading properties on `null` throws a `TypeError`. A **side effect** is any operation that modifies state outside the current function or interacts with outside systems during execution. Examples include writing to `document.getElementById()`, modifying `document.title`, starting a timer with `setInterval`, making a network request, or logging analytics. Top-level component execution must remain free of side effects because React calls components before their DOM elements exist. ◼ Educational objective: define side effects and explain why DOM writes fail during render.

- [p] ★ {mechanism: declarative JSX ternary expressions versus imperative DOM mutations} When a component runs for the first time, its HTML tags have not yet been created or mounted in the browser document. Calling `document.getElementById('badge').className = 'active'` during render fails immediately: `document.getElementById()` returns `null`, and assigning a property on `null` throws an unhandled `TypeError` that crashes the page. Even on later renders, directly mutating DOM nodes bypasses React's reconciliation engine. The pure React approach is declarative: calculate dynamic styles and text directly in the returned JSX using JavaScript expressions like ternary conditional operators (`condition ? 'active' : 'inactive'`). Changes caused by user actions (like button clicks) belong in event handlers, which run outside of render. ◼ Educational objective: contrast imperative DOM writes with declarative JSX expressions.

- [p] ★ {mechanism: non-idempotent functions like Math.random and new Date} A function is **idempotent** if running it multiple times with the same inputs always produces the exact same result. Functions like `Math.random()` and `new Date()` are non-idempotent: every single invocation returns a different number or timestamp. When a component calls `Math.random()` in its body, StrictMode runs the function twice and produces two disagreeing numbers. The screen shows the second number, while earlier logs or child components hold the first. To keep components pure, dynamic values and timestamps should be passed downward as props from data that already holds them. ◼ Educational objective: explain idempotence and why non-idempotent calls during render cause data drift.

- [code] Declarative JSX ternary versus imperative DOM write:

```jsx title="Declarative Ternary Expression"
// Declarative: evaluates ternary expression during render
function StatusIndicator({ isActive }) {
  const statusClass = isActive ? 'online' : 'offline';
  return <span className={statusClass}>Status</span>;
}

// Imperative mistake: attempts to query DOM during render
function BrokenIndicator() {
  document.getElementById('status').textContent = 'Live';
  return <span id="status">Ready</span>;
}
```

◼ **The what-this-introduces list:** 1. `isActive ? 'online' : 'offline'`: pure declarative ternary expression. 2. `span.statusClass`: class resolved cleanly in markup. 3. `document.getElementById`: forbidden imperative DOM write during render.

### Principles of React: Keeping Components Pure

- [question-cycle] Question 1: An outside counter variable doubles its numbers on page load
    - Question: "My cards show #2, #4, #6 on initial page load instead of #1, #2, #3. Why?"
    - Code and result: A developer declares `let count = 0;` at the top of the file outside the component. Inside `Card`, they write `count = count + 1;` and return `<li>#{count}: {title}</li>`. In React 19.3.0 under `<StrictMode>`, the three cards render on screen displaying `#2`, `#4`, and `#6` on initial load. When `root.render` runs again, the numbers climb to `#8`, `#10`, and `#12`.
    - Verdict: does not do what the reader wanted.
    - Answer: In development mode, React wraps components in `<StrictMode>`. StrictMode deliberately runs every component function twice during each render pass to catch unexpected side effects. Because `count` is a module-level variable that lives outside the function, the first card increments `count` to 1 on its first call and to 2 on its second call. The browser displays `#2` for the first item. The second card increments `count` to 3 and 4, displaying `#4`. On any subsequent render, `count` never resets; it keeps climbing without bound.
    - Fix: Remove the module-level variable and pass the item position downward as an explicit prop: `<Card position={index + 1} title={title} />`. Because `Card` calculates its markup strictly from props, React can call it once, twice, or ten times, and the output is always `#1`, `#2`, and `#3`. Taught in runway "What makes a function pure" and Lecture 6.
    - Rule with boundary: Always compute what a component shows from its props and local variables created in that render; never write to a variable outside the component function during render. Boundary: values that change over time through user interaction belong in component state (Lecture 14), not in module-scoped variables.
    - Needs: pure function (runway), module-level variable (runway), StrictMode double-call (runway, Lecture 4), props (recall, Lecture 6), re-render via root.render (recall, Lecture 9).
    - Diagram: ASCII diagram showing StrictMode double calls incrementing module variable vs pure prop calculation.

> [!PRINCIPLE]
> **Principle 1: A component must return the same JSX for the same props**
> React calls a component function to calculate what to show on screen. In development, **StrictMode double-rendering** calls every component twice to detect unexpected side effects. When a component reads or writes a variable outside itself, each run sees a different value and numbers drift. Treat every component as a **pure function**: compute output strictly from props and local variables so every run returns identical markup.
>
> >> pure function : a function that produces identical output for identical inputs and causes zero outside side effects
> >> StrictMode double-rendering : a development check where React calls component functions twice to catch side effects
>
> *We should do this:*
> `function Card({ title, position }) {`
> `  return <li>#{position}: {title}</li>; // pure prop calculation`
> `}`
>
> *We should not do this:*
> `let count = 0; // outside module variable`
> `function Card({ title }) {`
> `  count = count + 1; // mutates outside variable`
> `  return <li>#{count}: {title}</li>;`
> `}`

- [question-cycle] Question 2: Pushing into an outside array duplicates items across renders
    - Question: "Can I push an item into an array, or change an object, during render?"
    - Code and result: Inside `Feed`, the developer writes `headlines.push('Featured Item')` on an array declared at the module level or received as a prop. In React 19.3.0 under `<StrictMode>`, the feed displays two copies of "Featured Item" on the very first render. On every subsequent render, another copy is appended.
    - Verdict: does not do what the reader wanted.
    - Answer: Data that existed before the render—such as a module-level array or an array received as a prop—persists across render passes. Calling `push()` mutates that preexisting array in place. Because StrictMode executes the component function twice in development, `push()` runs twice on page load, appending duplicate items and triggering key warnings. Similarly, mutating an object after passing it into JSX (`styles.color = 'red'` after `<Header styles={styles} />`) alters the element because both share the same memory reference.
    - Fix: Use local mutation: create a brand-new array inside the component using spread syntax (`const list = [...headlines, 'Featured Item'];`) or push into an array created inside the function body. Because the array was born inside that specific render call, modifying it is safe, pure, and invisible to the rest of the application. Taught in runway "The difference between local mutation and external mutation".
    - Rule with boundary: Change only data that this render created; never mutate arrays, objects, or props that existed before the render started. Boundary: local mutation on fresh arrays or objects created inside the function body is completely valid, as long as mutation finishes before passing the value to JSX.
    - Needs: array mutation and push (runway), local mutation (runway), spread syntax for array copying (runway, Lecture 7), props immutability (recall, Lecture 6).
    - Diagram: ASCII diagram showing shared array mutation accumulating items vs fresh local array creation.

> [!PRINCIPLE]
> **Principle 2: Change only what this render created**
> Never mutate variables, objects, or arrays that existed before the component was called. Calling `push()` or reassigning properties on shared data changes memory that other components and later renders rely on. To modify data during render, use **local mutation**: create a brand-new array or object inside the function body and fill it before passing it to JSX.
>
> >> external mutation : changing a variable, array, or object that existed before the current render call
> >> local mutation : modifying a fresh variable or array created inside the current render call before passing it to JSX
>
> *We should do this:*
> `function Feed({ items, bonus }) {`
> `  const list = [...items, bonus]; // fresh local array`
> `  return <List items={list} />;`
> `}`
>
> *We should not do this:*
> `function Feed({ items, bonus }) {`
> `  items.push(bonus); // mutates incoming props array`
> `  return <List items={items} />;`
> `}`

- [question-cycle] Question 3: Modifying the document during render throws an error on initial load
    - Question: "Where do I set document properties, or add a CSS class to an element?"
    - Code and result: A developer writes `document.getElementById('clock').className = 'night'` directly inside the component function body. In React 19.3.0, the application crashes on initial page load with `TypeError: Cannot set properties of null (setting 'className')`, leaving a blank white screen.
    - Verdict: does not do what the reader wanted.
    - Answer: Component functions execute during the render phase, before React creates or mounts the browser DOM elements. When `document.getElementById('clock')` runs on initial render, the DOM node does not exist yet and evaluates to `null`. Setting a property on `null` crashes the application. Even if the element existed from an earlier render, directly modifying DOM nodes bypasses React's reconciliation engine and desynchronizes the interface. Similarly, writing `document.title = title` in the component body changes the browser window during the calculation phase, which is a side effect.
    - Fix: Calculate visual attributes declaratively directly in the returned JSX using JavaScript expressions like ternary conditional operators: `<span className={isNight ? 'night' : 'day'}>`. Side effects that interact with outside systems (such as setting document titles, starting timers, or logging analytics) belong in event handlers (Lecture 13), which execute in response to user actions outside the render path. Taught in runway "What belongs in render versus what belongs in event handlers".
    - Rule with boundary: Keep all DOM writes, timers, and outside changes out of the render; express what the user sees declaratively in JSX, and place side effects in event handlers. Boundary: actions triggered by user interactions belong in event handlers (Lecture 13); synchronizing with outside systems after render is handled by Effects (Lecture 31).
    - Needs: side effect (runway), DOM writes (runway, Lecture 1), TypeError on null (runway, Lecture 10), ternary operator (runway), event handlers (preview, Lecture 13).
    - Diagram: ASCII diagram showing render phase execution (before DOM exists) vs event handler execution (after DOM is mounted).

> [!PRINCIPLE]
> **Principle 3: Keep changes to the outside world out of the render**
> The component function body runs during the **render phase** strictly to calculate markup. Never modify DOM nodes, start timers, or trigger network requests directly in the component body. Modifying the DOM during render throws errors because elements do not exist yet. Express visual changes declaratively in JSX, and place outside changes into event handlers.
>
> >> side effect : an operation that changes an outside system or modifies data beyond returning JSX
> >> render phase : the synchronous execution where React calls a component function to calculate markup
>
> *We should do this:*
> `function Badge({ isUrgent }) {`
> `  const cls = isUrgent ? 'urgent' : 'normal'; // declarative JSX class`
> `  return <span className={cls}>Alert</span>;`
> `}`
>
> *We should not do this:*
> `function Badge({ isUrgent }) {`
> `  const el = document.getElementById('badge');`
> `  el.className = 'urgent'; // direct DOM mutation crashes`
> `  return <span id="badge">Alert</span>;`
> `}`

- [question-cycle] Question 4: Calling Math.random or new Date during render produces disagreeing values
    - Question: "Can I pick a random highlight, or show the current time, by calling Math.random or new Date inside the component?"
    - Code and result: Inside `ArticleCard`, a developer writes `const pick = Math.random();` to pick a random style or badge. In React 19.3.0 under `<StrictMode>`, console logs show two different numbers (such as `0.133` and `0.123`), and the screen displays `0.123`. For `new Date()`, the screen displays the timestamp when the component rendered and remains frozen on that exact millisecond.
    - Verdict: does not do what the reader wanted.
    - Answer: A pure component must be idempotent: executing it multiple times with identical inputs must always produce identical JSX output. Calling `Math.random()` or `new Date()` is non-idempotent because each invocation produces a different result. Under `<StrictMode>`, React calls the component twice; the two calls generate different numbers, and the screen displays the second value while earlier logs or child components hold the first. Furthermore, reading the clock during render freezes the timestamp at the render moment, failing to tick forward unless an update occurs.
    - Fix: Pass dynamic values and timestamps downward as explicit props from the parent component or data layer: `<ArticleCard pick={pick} timestamp={timestamp} />`. If a value must be generated when the user performs an action, generate it inside an event handler (Lecture 13) before passing it into state (Lecture 14). Taught in runway "What belongs in render versus what belongs in event handlers".
    - Rule with boundary: Do not call non-idempotent functions like `Math.random()` or `new Date()` during render to compute output; pass dynamic values and timestamps as props. Boundary: generating a random value in an event handler upon a user click is completely safe because event handlers run outside of render.
    - Needs: idempotent rendering (runway), Math.random non-idempotence (runway, Lecture 11), new Date timestamps (runway, Lecture 4), props (recall, Lecture 6), event handlers (preview, Lecture 13).
    - Diagram: ASCII diagram showing non-idempotent call drift under StrictMode double-rendering vs stable prop passing.

> [!PRINCIPLE]
> **Principle 4: Do not compute what you show from Math.random or new Date during render**
> A component must produce **idempotent rendering**: calling it with the same inputs must always return the exact same JSX. Calling a **non-idempotent call** like `Math.random()` or `new Date()` in the component body produces different values on every call, breaking predictability under StrictMode double-rendering. Pass random values and timestamps downward as props from outside the render.
>
> >> non-idempotent call : a function call that returns a different value each time it runs with the same arguments
> >> idempotent rendering : running a component with identical inputs produces identical output every time
>
> *We should do this:*
> `function Card({ title, pick }) {`
> `  return <h3>Pick {pick}: {title}</h3>; // deterministic prop`
> `}`
>
> *We should not do this:*
> `function Card({ title }) {`
> `  const pick = Math.random(); // different value on every call`
> `  return <h3>Pick {pick}: {title}</h3>;`
> `}`

### Where you will meet this

- [p] 1. **Server-Side Rendering and Static Generation**: Server frameworks render components on a web server to generate HTML for thousands of concurrent requests; because pure components never touch global variables or shared memory, concurrent visitor requests never contaminate each other's data.
- [p] 2. **Performance Optimization with Memoization**: When a component is pure, React can safely skip re-rendering it if its props have not changed, reusing the previous JSX calculation because a pure formula is guaranteed to return the exact same markup.
- [p] 3. **Concurrent and Interrupted Rendering**: When React prioritizes urgent user inputs over background updates, it can pause or discard a component render in memory and restart it later; pure components guarantee that discarded renders leave zero corrupted traces behind.
- [p] 4. **Automated Unit Testing**: Testing pure components is simple and reliable because you do not need to mock browser DOM globals, reset external counter variables, or clean up leaked side effects between test runs.

### For the interview

- [interview] The Interview Question: What does it mean for a component to be pure, and what breaks when it is not?
- [interview] 1. The Hidden Signal: The interviewer is probing whether you understand React's declarative execution loop and the contract of pure rendering, or whether you still write React like traditional imperative jQuery scripts. A junior developer mentions that functions should not change variables. A senior engineer explains that pure components act as mathematical formulas where `UI = f(props)`. They explain that React reserves the right to call components multiple times, in any order, and twice in development under StrictMode. They explain how external mutation causes state drift across renders and how imperative DOM queries during render crash because nodes do not exist yet.
- [interview] 2. The Classic Trap: The classic trap appears when an interviewer asks why a `console.log()` inside a component prints twice on page load. Candidates often assume React has an infinite render bug or a double-mount defect, and some admit to deleting `<StrictMode>` from their root file to silence the logs. In reality, StrictMode deliberately double-invokes components in development as an intentional stress test to expose hidden mutations. Another trap is assuming purity means you cannot use JavaScript arrays or objects; local mutation on fresh data created inside the current render call is 100% pure.
- [interview] 3. What is Actually Going On: In React, component execution is an on-demand calculation. React takes your props and calls your component function to obtain a tree of element descriptors. If your component is pure, calling it once, twice, or ten times produces identical JSX. If your component modifies a module-level variable during render, StrictMode double-rendering executes that mutation twice on the initial page load, causing numbers to double immediately. If a component writes to the DOM during render, the operation fails with a TypeError because React has not created the DOM nodes yet.
- [interview] 4. Where It Gets Tricky: What happens if you mutate a local object after passing it into a JSX element, such as `styles.color = 'red'` after writing `<Header styles={styles} />`? The element receives the modified value because both share the same reference in memory; values must be treated as immutable once passed to JSX. Why are `Math.random()` and `new Date()` forbidden in render output? Both are non-idempotent: they return different values on every call, causing the two StrictMode calls to disagree and freezing timestamps at render time. How do you handle real side effects like network requests or timers? Place them inside event handlers, which execute in response to user actions outside the render path.

### Glossary

- [glossary] Pure Function ◼ A function that always returns the exact same result given the same inputs and produces zero side effects on outside systems.
- [glossary] Side Effect ◼ Any operation that modifies state outside the current function or interacts with outside systems during execution.
- [glossary] StrictMode ◼ A React development-only wrapper component that deliberately calls component functions twice to expose unintended side effects.
- [glossary] Local Mutation ◼ Modifying variables, arrays, or objects created within the current render execution before they are passed into JSX.
- [glossary] Idempotence ◼ The property of a function where running it multiple times with identical inputs produces the exact same outcome without state drift.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Pure Render Calculations

➔ ALWAYS treat your component function as a pure mathematical formula: `UI = f(props)`.

➔ ALWAYS pass dynamic values like item positions, timestamps, and counters downward as explicit props rather than incrementing outside variables.

**DO THIS:** derive numbering directly from array mapping or props

```jsx right
function Feed({ stories }) {
  return (
    <div>
      {stories.map((story, i) => (
        <Card key={story.id} position={i + 1} title={story.title} />
      ))}
    </div>
  );
}
```

**DO NOT DO THIS:** increment outside variables inside the render body

```jsx wrong
let count = 0;
function Card({ title }) {
  count = count + 1;
  return <h3>#{count}: {title}</h3>;
}
```

❒ Managing Mutation and Data Flow

➔ NEVER mutate variables, arrays, or objects that existed before the component was called.

➔ IF you need to accumulate or format items during render THEN use local mutation on fresh arrays created within the same function call.

➔ NEVER mutate a local object after it has been passed into a JSX element.

**DO THIS:** copy arrays with spread syntax to avoid mutating props

```jsx right
function StoryTray({ stories, bonusStory }) {
  const allStories = [...stories, bonusStory];
  return <Feed list={allStories} />;
}
```

**DO NOT DO THIS:** call push directly on props arrays during render

```jsx wrong
function StoryTray({ stories, bonusStory }) {
  stories.push(bonusStory);
  return <Feed list={stories} />;
}
```

❒ Side Effects and Browser Interaction

➔ NEVER write to DOM nodes, start timers, or trigger network analytics directly inside the component body.

➔ IF you need visual class changes based on data THEN calculate them declaratively in JSX using ternary conditional operators.

➔ ALWAYS place interactive side effects inside event handlers that run outside of the render phase.

| | **IMPURE COMPONENT**<br>(Shared Outside State) | **PURE COMPONENT**<br>(Mathematical Formula) |
| ---: | :--- | :--- |
| **Formula contract** | Output changes based on outside variables and call counts | Same inputs always return identical JSX: `UI = f(props)` |
| **StrictMode behavior** | Corrupts data: counters double (`#2`, `#4`) and logs desynchronize | Fully resilient: calling twice produces identical output |
| **Mutation boundary** | Modifies external variables, props, or preexisting arrays | Mutates only fresh local variables created in current render |
| **Side effects handling** | Imperative DOM writes crash on initial load (`null` selector) | Declarative JSX ternary expressions resolve cleanly in markup |
| **Caching & Optimization** | Unsafe to cache: skipping renders leads to stale visual state | Safe to cache and optimize with `memo` or concurrent restarts |
