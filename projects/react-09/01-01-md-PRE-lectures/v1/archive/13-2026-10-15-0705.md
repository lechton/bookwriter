### Interactive interfaces respond to user actions through event listeners

- [p] ◇ {theme: responding to human interaction through declarative handlers} Every dynamic web application must respond when users interact with the screen. Readers click buttons to open stories, type search queries into input fields, select items from lists, and save articles for later reading. In traditional scripting and legacy HTML, developers wrote inline string handlers like `onclick="handleClick()"`. In React, components are pure functions, and user interactions are handled declaratively by passing JavaScript function references to event props like `onClick` and `onChange`. React listens for browser events, wraps them in synthetic event objects, and executes the designated handler outside of the render cycle. ◼ Educational objective: introduce the universal architectural requirement of responding to user actions via declarative event props.

- [p] ◇ {starting point: immediate JSX execution versus deferred event handling} When developers begin adding interactivity to React components, they often bring imperative habits from classic JavaScript. In JSX, anything placed inside curly braces evaluates immediately while React calculates the component's output. Writing `onClick={handleSelect()}` with parentheses causes JavaScript to invoke `handleSelect()` right away during render. The function fires on initial page load before the user ever touches the mouse, and its return value (`undefined`) is passed to `onClick`, leaving the button unresponsive when clicked later. Furthermore, when nested components need to update application state, children cannot reassign parent variables directly; they must communicate upward through callback props. ◼ Educational objective: contrast immediate JSX brace evaluation with deferred event handling and introduce inverse data flow.

### How React connects event props to handler functions

- [runway] Event handlers, JSX curly brace evaluation, function references vs function calls, and camelCase props (onClick), used by Question 1 and Question 2.

- [p] ★ {preknowledge: JSX curly braces and function references} In Lecture 2 and Lecture 4, we saw that JSX curly braces `{ ... }` evaluate JavaScript expressions immediately during the render phase. In standard HTML, event attributes like `onclick` expect a string of code to execute. In React, event listener props are written in camelCase, such as `onClick`, `onChange`, `onKeyDown`, and `onSubmit`. Instead of a string, React expects an actual JavaScript function value. When the user interacts with the rendered element, React receives the browser event and executes that function. ◼ Educational objective: establish the physical difference between HTML event strings and React camelCase function props.

- [p] ★ {mechanism: passing uncalled function values vs immediate invocation} The most critical distinction in React event wiring is passing a function reference versus calling a function. When you write `onClick={handleClick}`, you pass the function itself as an uncalled value; you tell React, "Hold this function reference and call it when the user clicks." If you add parentheses, `onClick={handleClick()}`, JavaScript executes `handleClick` right away while constructing the element tree. The return value (typically `undefined`) is assigned to `onClick`, leaving the element with no click handler. Event handlers run outside of render, making them the safe and idiomatic home for side effects like logging, network requests, and future state updates. ◼ Educational objective: derive the physical consequence of parentheses in JSX braces and identify handlers as the home for side effects.

- [code] Function reference pattern:

```jsx title="Function Reference Pattern"
function ActionButton() {
  function handleClick() {
    console.log('Button clicked'); // Executes on user click
  }
  return <button onClick={handleClick}>Click</button>;
}
```

- [code] Immediate invocation mistake:

```jsx title="Immediate Invocation Mistake"
function BrokenButton() {
  return <button onClick={handleClick()}>Click</button>; // Fires during render
}
```

◼ **The what-this-introduces list:** 1. `onClick={handleClick}`: uncalled function reference stored for user interaction. 2. `handleClick()` inside braces: immediate execution during render returning `undefined`. 3. `console.log`: side effect safely isolated inside event handler.

### How callback props pass actions upward without breaking unidirectional data flow

- [runway] Callback props, child-to-parent communication, and custom component prop boundaries, used by Question 3.

- [p] ★ {preknowledge: unidirectional data flow and props immutability} In Lecture 5 and Lecture 6, we established that React strictly enforces unidirectional data flow: data flows downward from parent to child through props, and props are strictly read-only. A child component cannot modify the parent's data or reassign variables in the parent's scope. If a child needs to report a user event to its parent, it cannot reach upward directly. ◼ Educational objective: recall unidirectional data flow and props immutability as the structural constraint for child-to-parent communication.

- [p] ★ {mechanism: passing function props downward so children can invoke them with data} To allow children to communicate upward, React uses **callback props**. The parent component declares a handler function that knows what action to take (such as selecting a story). The parent passes that function downward to the child as a prop, conventionally prefixed with `on` (such as `onSelect={handleSelect}`). The child component receives the callback prop and attaches it to a native element's event prop, such as a `<button onClick={...}>`. When the user clicks the button, the child executes the callback, passing relevant data (like the story identifier) upward to the parent. In this way, data still flows down as props, but actions flow upward through function calls. Custom components (like `<ArticleCard />`) do not possess built-in DOM event listeners; placing `onClick` on a custom component merely passes a prop named `onClick` and does nothing unless the child explicitly attaches it to a native HTML element. ◼ Educational objective: explain callback props, naming conventions (handle vs on), and the DOM boundary of custom components.

- [code] Callback prop in parent:

```jsx title="Callback Prop in Parent"
function Feed() {
  function handleSelect(id) {
    console.log('Selected article:', id); // Business logic in parent
  }
  return <ArticleCard id="art-1" onSelect={handleSelect} />;
}
```

- [code] Callback wiring in child:

```jsx title="Callback Wiring in Child"
function ArticleCard({ id, onSelect }) {
  return <button onClick={() => onSelect(id)}>Read</button>; // Forwards id
}
```

◼ **The what-this-introduces list:** 1. `onSelect={handleSelect}`: callback prop passed downward from parent. 2. `onSelect(id)`: child invoking parent function with identifier argument. 3. Native `<button>`: element boundary connecting JavaScript callback to browser click.

### How browser events bubble and why stopPropagation differs from preventDefault

- [runway] The SyntheticEvent object e, event bubbling (propagation), e.stopPropagation(), and e.preventDefault(), used by Question 4.

- [p] ★ {preknowledge: DOM tree nesting and native browser events} When a user interacts with a web page, the browser creates a native event object. React intercepts these native events at the root container and wraps them in a cross-browser **SyntheticEvent** object, conventionally passed to your handler as `e`. This event object provides standard properties such as `e.target` (the specific element that was clicked) and `e.currentTarget` (the element whose event handler is currently executing). ◼ Educational objective: introduce the SyntheticEvent object e and contrast e.target with e.currentTarget.

- [p] ★ {mechanism: event propagation bubbling upward through ancestors and browser default actions} In the browser DOM, events follow the bubbling mechanism: after an event fires on the innermost clicked element, it propagates upward through all parent elements in the document tree, triggering their event handlers in sequence. If a card contains a bookmark button, clicking the bookmark button fires the button's `onClick`, bubbles up to the card's `onClick`, and continues up to the container. To halt this cascade, call `e.stopPropagation()`. This tells the browser and React not to run event handlers on ancestor elements. In contrast, `e.preventDefault()` addresses browser default behaviors, such as preventing a `<form>` submission from reloading the page or preventing an `<a>` link from navigating. Calling `e.stopPropagation()` does not cancel default browser actions, and calling `e.preventDefault()` does not stop event bubbling; each call has a distinct, unrelated responsibility. ◼ Educational objective: derive event bubbling and contrast stopPropagation with preventDefault.

- [code] Stopping propagation versus preventing default behavior:

```jsx title="Event Propagation Control"
function CardActions({ onSave }) {
  function handleSave(e) {
    e.stopPropagation(); // Stops click from bubbling to parent card
    onSave();
  }
  function handleSubmit(e) {
    e.preventDefault(); // Prevents browser from reloading page
  }
  return <button onClick={handleSave}>Save</button>;
}
```

◼ **The what-this-introduces list:** 1. `e.stopPropagation()`: stops event from bubbling to ancestor elements. 2. `e.preventDefault()`: prevents default browser action without stopping bubbling. 3. `e`: synthetic event object provided to handler.

### Why accessible interaction requires native button controls instead of generic tags

- [runway] Keyboard focus, Tab navigation, Enter and Space key activation, and native button accessibility, used by Question 5.

- [p] ★ {preknowledge: browser focus management and keyboard accessibility} In the browser, interactive elements participate in keyboard navigation. Users navigating with a keyboard or assistive technology press the Tab key to cycle through interactive controls on the page. When an element receives keyboard focus, pressing Enter or Space activates it. ◼ Educational objective: explain browser focus management and keyboard navigation standards.

- [p] ★ {mechanism: native button semantics vs generic div tags} React allows you to attach an `onClick` prop to any JSX tag, including generic tags like `<div>` or `<span>`. However, the browser does not treat generic tags as interactive. A `<div>` with `onClick` cannot receive keyboard focus via the Tab key, does not respond to Enter or Space key presses, and fails to announce an interactive role to screen readers. In contrast, a native `<button>` element is built into the browser with full keyboard focus support, standard key activation, and built-in accessibility roles. Developers should always use native `<button>` elements for clickable actions, using CSS to achieve any desired visual style. ◼ Educational objective: derive why generic div click targets exclude keyboard users and enforce native button elements.

- [code] Semantic button versus non-semantic div:

```jsx title="Semantic vs Generic Click Target"
// Accessible: receives Tab focus and responds to Enter/Space
function SafeAction({ onSelect }) {
  return <button type="button" onClick={onSelect}>Select</button>;
}

// Inaccessible: skipped by Tab and ignores Enter/Space
function UnsafeAction({ onSelect }) {
  return <div className="btn" onClick={onSelect}>Select</div>;
}
```

◼ **The what-this-introduces list:** 1. `<button type="button">`: accessible interactive control with built-in keyboard support. 2. `<div onClick>`: inaccessible anti-pattern that fails keyboard navigation. 3. `type="button"`: explicit button type preventing accidental form submission.

### Principles of React: Responding to Events and Callback Props

- [question-cycle] Question 1: Calling a handler in JSX braces executes on page load
    - Question: "I wrote `onClick={handlePublish()}`. Why did it run on page load and not on click?"
    - Code and result: Inside `PublishButton`, a developer writes `<button onClick={handlePublish()}>Publish</button>`. In React 19.3.0, the console prints "PUBLISH ran" on initial page load during render, and clicking the button afterward prints nothing.
    - Verdict: does not do what the reader wanted.
    - Answer: Curly braces evaluate expressions immediately during the render phase. Writing `handlePublish()` invokes the function while React builds the element tree. The function runs on page load, and its return value (`undefined`) is assigned to `onClick`. When the user later clicks the button, React finds `undefined` and takes no action. Passing the bare function name `onClick={handlePublish}` passes an uncalled function reference that React executes strictly upon user interaction.
    - Fix: Remove the parentheses and pass the function reference directly: `<button onClick={handlePublish}>Publish</button>`. Taught in runway "How React connects event props to handler functions" and Lecture 2.
    - Rule with boundary: Pass the uncalled handler function reference to an event prop; never call it with parentheses in JSX. Boundary: when a handler requires arguments from the current element, wrap the call in an arrow function (Question 2).
    - Needs: event handler (runway), JSX curly brace evaluation (runway, Lecture 4), function reference vs call (runway, Lecture 2).
    - Diagram: ASCII diagram showing immediate invocation during render returning undefined vs passing function reference invoked on user click.

> [!PRINCIPLE]
> **Principle 1: Pass the handler function to an event prop, not its result**
> An event prop like `onClick` takes a function to run later when the user acts. Curly braces evaluate their expression immediately during render. Writing parentheses like `onClick={handleClick()}` calls the function right away, and `onClick` receives what it returns, usually `undefined`. To run code on click, pass the function itself without parentheses: `onClick={handleClick}`.
>
> >> function reference : passing an uncalled function by name so React can run it later
> >> immediate invocation : calling a function during render by adding parentheses in JSX braces
>
> *We should do this:*
> `<button onClick={handleClick}>`
> `  Save {/* runs on click */}`
> `</button>`
>
> *We should not do this:*
> `<button onClick={handleClick()}>`
> `  Save {/* runs in render */}`
> `</button>`

- [question-cycle] Question 2: Passing an argument directly calls the handler during render
    - Question: "`openArticle` needs the story's id. How do I pass it without calling it?"
    - Code and result: Inside an article list mapping over items, a developer writes `<button onClick={openArticle(story.id)}>Read</button>`. In React 19.3.0, the console prints "open a1" and "open a2" immediately during render, and clicking either button prints nothing.
    - Verdict: does not do what the reader wanted.
    - Answer: Writing `openArticle(story.id)` inside JSX braces executes the function during render for every item in the mapped array, assigning `undefined` to each button's `onClick`. To pass arguments without executing immediately, wrap the call in an arrow function: `onClick={() => openArticle(story.id)}`. The arrow function is an uncalled function value created during render. When the user clicks the button, React invokes the arrow function, which in turn calls `openArticle(story.id)` with the correct identifier.
    - Fix: Wrap the call in an inline arrow function: `<button onClick={() => openArticle(story.id)}>Read</button>`. Taught in runway "How React connects event props to handler functions" and Lecture 11.
    - Rule with boundary: When an event handler requires arguments, wrap the call in an arrow function. Boundary: if the handler takes no custom arguments, pass the bare function reference directly: `onClick={handleClick}`.
    - Needs: arrow function (runway, Lecture 11), array map (recall, Lecture 11), function reference (runway).
    - Diagram: ASCII diagram showing direct call in list render vs arrow function deferring execution until click.

> [!PRINCIPLE]
> **Principle 2: Wrap a handler call that needs arguments in an arrow function**
> When a handler needs arguments from the current item, writing `onClick={handleClick(id)}` calls the function during render for every item in the list. Wrapping the call in an arrow function creates a function that waits. React stores that function and calls it only when the user clicks, passing the arguments to your handler.
>
> >> arrow function wrapper : an inline function that defers execution until user interaction
>
> *We should do this:*
> `<button onClick={() => select(item.id)}>`
> `  Select {/* runs on click */}`
> `</button>`
>
> *We should not do this:*
> `<button onClick={select(item.id)}>`
> `  Select {/* runs in render */}`
> `</button>`

- [question-cycle] Question 3: Custom components ignore unwired event props
    - Question: "The Read button is in `ArticleCard`, but `NewsFeed` decides what opens. How does the card tell it?"
    - Code and result: A developer writes `<ArticleCard title="Budget" onClick={() => console.log('clicked')} />`, but `ArticleCard` does not accept or attach `onClick` to any DOM node. In React 19.3.0, clicking the card prints nothing to the console. If the child instead tries to reassign a parent variable (`selectedId = 'a2'`), it mutates only its local copy, and the parent still shows "Selected: none".
    - Verdict: does not do what the reader wanted.
    - Answer: Props flow downward; a child cannot modify parent variables directly. Furthermore, custom components are JavaScript functions, not browser DOM elements. React does not attach native event listeners to custom component tags. An `onClick` prop placed on `<ArticleCard />` is merely a custom prop and does nothing unless the component receives it and forwards it to a real HTML element. To enable communication, the parent passes a callback function prop downward (such as `onSelect={handleSelect}`). The child receives `onSelect` and attaches it to an inner native element, such as `<button onClick={() => onSelect(article.id)}>`.
    - Fix: Pass a callback prop from the parent named after the application action: `<ArticleCard onSelect={handleSelect} />`. Inside `ArticleCard`, accept `onSelect` and wire it to a native button: `<button onClick={() => onSelect(article.id)}>Read</button>`. Taught in runway "How callback props pass actions upward without breaking unidirectional data flow".
    - Rule with boundary: Use callback props to allow child components to report user actions upward to parents; wire the callback to a native element's event prop. Boundary: built-in DOM elements take native event names like `onClick`; custom components should name callback props after the application action (such as `onSelect` or `onSave`).
    - Needs: callback prop (runway), unidirectional data flow (recall, Lecture 5), props immutability (recall, Lecture 6), DOM element boundary (runway).
    - Diagram: ASCII diagram showing callback prop passed down from parent and invoked upward from child button click.

> [!PRINCIPLE]
> **Principle 3: Pass a callback prop to let a child report actions to its parent**
> Data in React flows downward through props, so a child cannot change parent variables directly. Putting `onClick` on a custom component does nothing unless the component attaches it to a real HTML element. To let a child report an action, the parent passes a **callback prop** such as `onSelect`. The child calls that function from its button, passing whatever data the parent needs.
>
> >> callback prop : a function prop passed from parent to child to report events upward
> >> custom component prop : an unhandled prop on a component that does not bind to the DOM
>
> *We should do this:*
> `function Card({ onSelect, id }) {`
> `  return (`
> `    <button onClick={() => onSelect(id)}>`
> `      Open {/* wires callback prop */}`
> `    </button>`
> `  );`
> `}`
>
> *We should not do this:*
> `function Card({ onClick, id }) {`
> `  return (`
> `    <div>`
> `      <h3>Card {id}</h3> {/* onClick prop is ignored */}`
> `    </div>`
> `  );`
> `}`

- [question-cycle] Question 4: Clicking a nested button triggers parent click handlers
    - Question: "Clicking Save also opened the article. Why?"
    - Code and result: An article card features an outer `<article onClick={openArticle}>` listener and an inner Bookmark `<button onClick={saveArticle}>`. In React 19.3.0, clicking the Bookmark button logs "button: bookmark" and immediately logs "card: open article".
    - Verdict: does not do what the reader wanted.
    - Answer: Browser events bubble upward through the DOM hierarchy from the clicked element through all ancestor elements. Clicking the inner button fires its handler, and the click event continues bubbling upward, triggering the article's `onClick`. Calling `e.stopPropagation()` stops the event from traveling further up the tree. In contrast, `e.preventDefault()` stops default browser behaviors (such as form reload or link navigation). Neither method does the other's job.
    - Fix: Call `e.stopPropagation()` inside the inner button's handler: `onClick={e => { e.stopPropagation(); onSave(article.id); }}`. Call `e.preventDefault()` when preventing browser default behaviors like page reloads on form submit. Taught in runway "How browser events bubble and why stopPropagation differs from preventDefault".
    - Rule with boundary: Call `e.stopPropagation()` to stop parent event handlers from firing when an inner control is clicked; call `e.preventDefault()` to stop browser default actions. Boundary: all React events bubble except `onScroll`; `onClickCapture` handlers on ancestors execute during the capture phase before bubbling and are unaffected by child `stopPropagation()`.
    - Needs: event object e (runway), event bubbling (runway), stopPropagation (runway), preventDefault (runway).
    - Diagram: ASCII diagram showing event bubbling upward from inner button to outer article card vs stopPropagation stopping the bubble.

> [!PRINCIPLE]
> **Principle 4: Use stopPropagation for parent handlers and preventDefault for browser actions**
> When an element is clicked, the click **bubbles** upward through every parent element in the tree, running their `onClick` handlers too. Calling `e.stopPropagation()` stops the event from reaching parent elements. Browser default actions, like following a link or reloading on form submit, are separate: only `e.preventDefault()` stops them. Neither call does the other's job.
>
> >> event bubbling : the browser process where an event travels upward through ancestor elements
> >> stopPropagation : prevents an event from triggering handlers on ancestor elements
> >> preventDefault : cancels the browser default action without stopping event bubbling
>
> *We should do this:*
> `<button onClick={e => { e.stopPropagation(); onSave(id); }}>`
> `  Save {/* stops parent bubbling */}`
> `</button>`
>
> *We should not do this:*
> `<button onClick={() => onSave(id)}>`
> `  Save {/* bubbles up to parent */}`
> `</button>`

- [question-cycle] Question 5: Using a div for click handling blocks keyboard users
    - Question: "Can I put `onClick` on a `<div>` and style it as I like?"
    - Code and result: A developer writes `<div className="read" onClick={handleRead}>Read story</div>`. In Google Chrome 154, pressing the Tab key skips the `<div>` entirely. When clicked with a mouse, the handler runs, but pressing Enter or Space while adjacent to the element does nothing.
    - Verdict: does not do what the reader wanted.
    - Answer: React attaches event listeners to any HTML tag, but the browser enforces interactive semantics. A native `<button>` automatically receives keyboard focus when pressing Tab, and the browser dispatches a click event when pressing Enter or Space. A generic `<div>` cannot receive focus, is ignored by keyboard navigation, and announces no interactive role to screen readers.
    - Fix: Use a native `<button type="button" onClick={handleRead}>Read story</button>` and style it with CSS to match any desired visual design. Taught in runway "Why accessible interaction requires native button controls instead of generic tags".
    - Rule with boundary: Always attach click handlers to interactive native elements like `<button>`; never use generic non-interactive tags like `<div>` or `<span>`. Boundary: if an element navigates to a new URL, use an `<a>` tag; for in-page actions, use `<button>`.
    - Needs: keyboard focus (runway), Tab navigation (runway), native button semantics (runway).
    - Diagram: ASCII diagram showing Tab focus and Enter/Space activation on native button vs complete omission on generic div.

> [!PRINCIPLE]
> **Principle 5: Handle user clicks on a button element, not on a div**
> React allows `onClick` on any element, but the browser gives keyboard focus only to interactive elements. A native `<button>` receives **keyboard focus** when pressing the Tab key, and pressing Enter or Space triggers its click handler. A `<div>` gets neither, so keyboard and screen reader users cannot use it. Always use a `<button>` for actions and style it with CSS.
>
> >> keyboard focus : the browser state indicating which element receives keyboard keystrokes
> >> semantic interactive element : a native HTML tag with built-in accessibility and keyboard support
>
> *We should do this:*
> `<button type="button" onClick={handleSelect}>`
> `  Select {/* accessible via Tab and Enter */}`
> `</button>`
>
> *We should not do this:*
> `<div className="btn" onClick={handleSelect}>`
> `  Select {/* inaccessible to keyboard */}`
> `</div>`

### Step 2: Next, we wire the interactive article card <src/components/ArticleCard.jsx>

- [p] ★ {mechanism: card boundary forwarding callbacks with arguments and scoping propagation} In `src/components/ArticleCard.jsx`, we construct the interactive card boundary. - [p] ★ {mechanism: terminal button control stopping propagation and ensuring keyboard accessibility} In `src/components/ActionButton.jsx`, we construct the reusable action button. ### For the interview

> **The Interview Question:** How do you respond to user events like clicks and typing, and how do callback props communicate back to parents?

**1. The Hidden Signal**

The interviewer wants to know whether you understand React's declarative execution model and unidirectional data flow, or whether you still write React with imperative DOM habits. A junior developer states that you put `onClick` on elements. A senior engineer explains that event handlers are passed as function references, not invoked in JSX braces. They explain that children cannot mutate parent state, so parent components pass callback props downward, allowing children to invoke those functions with arguments. They clearly separate event bubbling (`e.stopPropagation()`) from browser default behavior (`e.preventDefault()`), and they emphasize that interactive controls must use native `<button>` tags for accessibility.

**2. The Classic Trap**

The classic trap is writing `onClick={handleClick()}` instead of `onClick={handleClick}`. Candidates frequently wonder why a function runs on page load and fails to respond to clicks. Another trap is passing an argument directly: `onClick={openItem(id)}`, which causes immediate invocation for every item in a list during render. A third trap is putting `onClick` directly on a custom component tag (like `<UserCard onClick={...} />`) and expecting React to attach a browser listener, unaware that custom components ignore unhandled props unless explicitly wired to native HTML tags.

**3. What is Actually Going On**

In React, JSX curly braces evaluate JavaScript synchronously during the render phase. Calling `handleClick()` inside braces runs the function right away, and its return value (`undefined`) is passed to `onClick`. When the user clicks, React finds no function to call. To defer execution, you must pass an uncalled function reference, or wrap calls that require arguments in an arrow function `() => handleClick(id)`. Because props are strictly read-only, child-to-parent communication is achieved through callback props: the parent passes a function down, and the child calls it with arguments. Events bubble up the DOM tree unless stopped by `e.stopPropagation()`, while `e.preventDefault()` cancels browser actions like link navigation and form reloads.

**4. Where It Gets Tricky**

What happens if an `onClickCapture` handler is attached to a parent element? Capture handlers run during the downward capture phase before child handlers execute, so calling `e.stopPropagation()` inside a child button cannot prevent parent capture handlers from running. Do all React events bubble? No: all events bubble in React except `onScroll`. What happens if you attach `onClick` to a `<div>`? The click works for mouse users, but the `<div>` cannot receive keyboard focus via the Tab key and ignores Enter and Space key activation, creating an accessibility defect. Always use native `<button>` elements for actions.

### Glossary

- **Event Handler**: A JavaScript function passed to a React element's event prop that executes in response to user interaction outside of the render cycle.
- **Callback Prop**: A function prop passed from a parent component to a child component allowing the child to report user actions upward.
- **Event Bubbling**: The browser process where an event dispatches on an innermost target element and propagates upward through ancestor elements in the DOM tree.
- **stopPropagation**: A method on the event object that halts event propagation, preventing ancestor element handlers from executing.
- **preventDefault**: A method on the event object that cancels default browser behaviors (such as form submission reloads or link navigation) without affecting event bubbling.
- **Keyboard Focus**: The browser state indicating which element currently receives keyboard input and keypress events.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Declarative Event Wiring

➔ ALWAYS pass event handlers as uncalled function references: `onClick={handleClick}`.

➔ NEVER invoke handlers inside JSX braces: `onClick={handleClick()}` runs during render and returns `undefined`.

➔ IF a handler requires custom arguments THEN wrap the invocation in an inline arrow function: `onClick={() => handleClick(item.id)}`.

**DO THIS:** pass uncalled function reference or wrap in arrow function
```jsx right
function ItemList({ items, onSelect }) {
  return (
    <ul>
      {items.map(item => (
        <li key={item.id}>
          <button type="button" onClick={() => onSelect(item.id)}>
            Select {item.name}
          </button>
        </li>
      ))}
    </ul>
  );
}
```

**DO NOT DO THIS:** invoke handlers immediately inside JSX curly braces
```jsx wrong
function ItemList({ items, onSelect }) {
  return (
    <ul>
      {items.map(item => (
        <li key={item.id}>
          <button type="button" onClick={onSelect(item.id)}>
            Select {item.name}
          </button>
        </li>
      ))}
    </ul>
  );
}
```

❒ Inverse Data Flow & Propagation

➔ ALWAYS use callback props to let child components communicate actions upward to parents.

➔ NEVER place event props on custom components expecting automatic DOM binding; always wire callbacks to native HTML elements.

➔ IF an inner action button is nested inside a clickable card THEN call `e.stopPropagation()` to prevent triggering parent handlers.

➔ IF you need to cancel a browser default action like form reload THEN call `e.preventDefault()`.

**DO THIS:** stop bubbling on nested controls and wire callbacks to buttons
```jsx right
function StoryCard({ story, onSelect, onBookmark }) {
  function handleBookmark(e) {
    e.stopPropagation();
    onBookmark(story.id);
  }
  return (
    <div className="card" onClick={() => onSelect(story.id)}>
      <h3>{story.title}</h3>
      <button type="button" onClick={handleBookmark}>
        Bookmark
      </button>
    </div>
  );
}
```

**DO NOT DO THIS:** allow nested buttons to bubble into parent container handlers
```jsx wrong
function StoryCard({ story, onSelect, onBookmark }) {
  return (
    <div className="card" onClick={() => onSelect(story.id)}>
      <h3>{story.title}</h3>
      <button type="button" onClick={() => onBookmark(story.id)}>
        Bookmark
      </button>
    </div>
  );
}
```

❒ Accessible Interactive Semantics

➔ ALWAYS use native `<button>` elements for click actions to ensure universal keyboard navigation and focus management.

➔ NEVER attach click handlers to generic tags like `<div>` or `<span>` without native interactive semantics.

| | **BROKEN WIRING**<br>(Immediate Call / Generic Tag) | **IDIOMATIC ARCHITECTURE**<br>(Deferred Reference / Native Element) |
| ---: | :--- | :--- |
| **Execution timing** | Runs during render on page load (`handleClick()`); returns `undefined` | Defers execution until user interaction (`onClick=`<br>`{handleClick}`) |
| **Passing arguments** | Direct call `onClick={fn(id)}` fires during render for all items | Inline arrow `onClick={`<br>`() => fn(id)}` runs only when clicked |
| **Child-parent flow** | Attempts to mutate parent variables or puts `onClick` on custom tags | Parent passes callback prop; child wires to native button |
| **Event propagation** | Unstopped clicks bubble up and trigger ancestor card handlers | `e.stopPropagation()` isolates nested button clicks cleanly |
| **Browser defaults** | Form submissions execute full-page reloads, wiping memory | `e.preventDefault()` cancels browser actions without stopping bubbling |
| **Keyboard access** | Inaccessible `<div>` is skipped by Tab and ignores Enter/Space | Native `<button>` receives Tab focus and responds to Enter/Space |
