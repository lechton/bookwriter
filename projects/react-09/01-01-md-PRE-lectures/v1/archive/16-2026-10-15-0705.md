### Every render receives a fixed state snapshot

- [p] ◇ {theme: the snapshot nature of component state} In modern web applications, user interfaces update dynamically in response to user interactions. When a reader clicks a star rating, submits feedback, or confirms an order, the interface changes to reflect the new data. In plain JavaScript, developers modify memory by reassigning variables directly with `=`, expecting every subsequent line of code to see the new value immediately. In React, application state behaves differently: it acts as a snapshot. Calling a state setter does not mutate the variable in the running code; instead, it asks React to schedule a future render where `useState` returns the new value. Understanding that a state variable remains frozen as a constant for the entire duration of a render is essential for coordinating user events, network requests, and delayed callbacks without synchronization bugs. ◼ Educational objective: introduce the snapshot mental model and contrast declarative React state with imperative variable assignment.

- [p] ◇ {starting point: imperative assignment habits versus declarative snapshot timing} When developers transition from traditional scripting to React, they often assume that calling a state setter works like variable reassignment. In plain JavaScript, writing `rating = 5` changes the variable immediately, so logging `rating` on the very next line prints 5. In React, calling `setRating(5)` does not touch the local variable `rating` in the currently executing function. React keeps state memory outside the component and hands the current render a constant snapshot of that data. The running event handler continues executing using its existing snapshot value. Consequently, reading the state variable on the line immediately following a setter call prints the old value. Furthermore, developers often expect that calling `setRating(rating + 1)` three times in a row will increment the number by three, unaware that every call in that handler evaluates using the exact same snapshot number. ◼ Educational objective: expose the false mental model of immediate variable mutation and explain why state appears frozen.

- [p] ◇ {core questions: four governing laws of state snapshots} This chapter answers four core questions. **Why does reading a state variable immediately after calling its setter still return the old value?** **How should an event handler coordinate state updates with external API calls or network dispatches?** **Why does calling a state setter three times in a row only advance the count by one?** **If a delayed timer runs after the user selects a new rating, which value does its callback read?** ◼ Educational objective: frame the four roadmap questions the lecture investigates.

### How React captures state in a render snapshot

- [runway] The state snapshot concept, state variables as function constants, setter queuing requests, and the substitution method, used by Question 1 and Question 2.

- [p] ★ {preknowledge: useState memory and setter render requests} In Lecture 14, we learned that calling `useState` gives a component memory. React preserves state variables outside the component function, and calling a state setter tells React to schedule a re-render. In Lecture 15, we discovered that React runs event handlers to completion before initiating the render and commit phases. ◼ Educational objective: recall component memory from Lecture 14 and handler execution timing from Lecture 15.

- [p] ★ {mechanism: state variables as render constants and the substitution method} When React renders a component, it calls your component function. The `useState` call retrieves the current state value from React internal storage and returns it to your function. Inside that function execution, the state variable is a standard JavaScript `const`. It never changes while that function executes. The JSX, local variables, and event handlers are all computed using this fixed value. We call this fixed set of values a **snapshot**. Calling a setter function like `setRating(5)` does not mutate the variable `rating` in your running code; it only tells React what value to supply in the next render. You can visualize this behavior using the **substitution method**: if `rating` is `0` when the component runs, you can mentally substitute `0` for `rating` everywhere in that render code. Calling `setRating(rating + 1)` three times evaluates as `setRating(0 + 1)` three times, queuing a single update to 1. ◼ Educational objective: derive the physical snapshot model, define state as a render constant, and introduce the substitution method.

- [code] State variable as a render constant:

```jsx title="Declarative State Snapshot"
export default function FeedbackSnapshot() {
  const [rating, setRating] = useState(0); // rating is constant 0 in this run
  function handleRate() {
    setRating(5); // Requests next render with 5
    console.log(rating); // Still prints 0 in this run
  }
  return <button onClick={handleRate}>Rate ({rating})</button>;
}
```

- [code] Substitution method evaluation:

```jsx title="The Substitution Method"
function handleTripleBoost() {
  setRating(0 + 1); // Substituted: requests 1 for next render
  setRating(0 + 1);
  setRating(0 + 1); // Queues 1 again for the screen
}
```

◼ **The what-this-introduces list:** 1. `snapshot`: the fixed set of data and handlers React gives to one run of a component. 2. `substitution method`: mentally replacing state variables with their render constants. 3. `render constant`: a state variable behaving as an immutable local value inside that specific call.

### How functions capture state across time through closures

- [runway] JavaScript closure scope, setTimeout delay execution, and render-bound event handlers, used by Question 3.

- [p] ★ {preknowledge: event handlers and JavaScript functions} In Lecture 13, we saw that event handlers are JavaScript functions passed to JSX elements to handle user events. In standard JavaScript, functions declared inside an outer function have access to the outer function scope. ◼ Educational objective: recall event handler declarations from Lecture 13 and connect to JavaScript function scope.

- [p] ★ {mechanism: closures capturing render variables across timers and delays} Every time React renders a component, it executes the component function from top to bottom, creating fresh event handler functions for that specific render. In JavaScript, an inner function forms a **closure**: it permanently remembers the variables of the lexical scope where it was created. When an event handler schedules a delayed callback with `setTimeout`, that callback closes over the specific snapshot values of the render that created it. The browser native `setTimeout` method accepts a callback function and a delay in milliseconds, executing the callback after the timer expires. Even if subsequent user clicks trigger new renders that update the screen with fresh state, existing timer callbacks retain the snapshot values from the render where they were scheduled. This behavior prevents timing bugs and race conditions in asynchronous user workflows. ◼ Educational objective: derive closure capture over render snapshots and explain why delayed callbacks retain past state.

- [code] Delayed timer closure:

```jsx title="Delayed Timer Closure"
export default function DelayedConfirmation() {
  const [rating, setRating] = useState(0); // Snapshot constant for this render
  function handleSend() {
    setTimeout(() => {
      console.log(`Rating: ${rating}`); // Closure reads rating from this render
    }, 1000);
  }
  return <button onClick={handleSend}>Send ({rating})</button>;
}
```

◼ **The what-this-introduces list:** 1. `closure`: an inner JavaScript function that remembers the variables of the scope where it was created. 2. `setTimeout`: native browser method executing a callback after a millisecond delay. 3. `render-bound handlers`: fresh handler instances generated on every component render.

### Principles of React: State as a Snapshot

- [question-cycle] Question 1: Calling a setter leaves the variable unchanged until the next render
    - Question: "I call `setRating(5)` and log `rating` on the next line. Why does it still print 0?"
    - Code and result: Inside `StoryFeedback`, a developer attaches a click handler to a "5 Stars" button: `setRating(5); console.log('rating =', rating);`. In React 19.3.0, clicking the button logs `rating = 0` in the console, while the component body logs `render rating = 5` only during the subsequent render as the screen updates to 5 stars. In a "+3" handler calling `setRating(rating + 1)` three times, the screen moves from 0 to 1, not 3.
    - Verdict: does not do what the reader wanted.
    - Answer: In plain JavaScript, assigning a variable with `=` modifies the variable in place immediately. In React, `const [rating, setRating] = useState(0)` provides the running function with a constant value `0` for this execution. React stores state memory outside the component function. Calling `setRating(5)` does not mutate the variable in the running code; it stores `5` in React and schedules a new render. Every line in the current handler continues reading the constant `0`. Furthermore, when calling `setRating(rating + 1)` three times in one handler, the substitution method shows that each line evaluates `0 + 1` and asks React to replace the value with `1`. After the handler completes, React executes the new render, where `useState` returns `5` (or `1`), and the component calculates its new JSX.
    - Fix: When code in the handler needs the new value immediately, compute the next value once in a local variable: `const nextRating = 5; setRating(nextRating); console.log(nextRating);`. Taught in runway "How React captures state in a render snapshot" and Principle 2.
    - Rule with boundary: A state variable keeps one fixed value for the whole render; calling a setter requests a future render with the new value but leaves the variable in running code unchanged. Boundary: reading the new value inside the same handler requires computing it once in a variable or waiting for the next render.
    - Needs: snapshot (runway), substitution method (runway), setter queues render (recall, Lecture 14), handler completion (recall, Lecture 15).
    - Diagram: ASCII diagram showing handler execution with setter call -> line reading same constant value 0 -> handler completion -> React re-render returning 5.

> [!PRINCIPLE]
> **Principle 1: A state variable keeps one value for the whole render**
> React provides each component run with a fixed **snapshot** of its state. In that run, a state variable is a standard JavaScript constant. Calling a setter does not change that constant in your running code. The setter only tells React what value to return on the next run. So reading the state variable on the line after the setter still reads the value from the current run. The new value exists only when React calls the component again.
>
> >> snapshot : the fixed set of values React gives to one run of a component
>
> *We should do this:*
> `const nextCount = count + 1; // compute the value once`
> `setCount(nextCount);`
> `console.log(nextCount); // logs 1 in this handler`
>
> *We should not do this:*
> `setCount(count + 1);`
> `console.log(count); // prints the old count, 0`

- [question-cycle] Question 2: Calling an API after a setter sends the old value unless computed once
    - Question: "When the reader clicks 5 stars, I set the rating and send it to the server. Which value do I give `sendRating`?"
    - Code and result: Inside `handleFiveStars`, a developer writes `setRating(5); sendRating(rating);`. When clicked, the screen updates to 5 stars, but the network helper sends 0 to the server (React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: The developer expects `rating` to hold 5 because `setRating(5)` was just called. But `rating` is a constant `0` for the entire execution of this handler. Passing `rating` to `sendRating(rating)` passes `0`. The server receives a rating of 0 while the reader sees 5 stars on screen, creating a silent desynchronization defect. To ensure the server payload matches the requested UI state, the handler must compute the next value once in a local variable. Calling `const nextRating = 5; setRating(nextRating); sendRating(nextRating);` gives `5` to React for the next render and passes `5` to the network helper immediately.
    - Fix: Compute the next value once in a local variable: `const nextRating = 5; setRating(nextRating); sendRating(nextRating);`. Taught in runway "How React captures state in a render snapshot" and Principle 1.
    - Rule with boundary: Compute the next value once in a local variable and pass it to both the setter and any subsequent function calls. Boundary: when an event handler does not read the state value after setting it, passing a literal or inline calculation directly to the setter is completely safe.
    - Needs: local variable sharing (runway), side effects in handlers (recall, Lecture 13).
    - Diagram: ASCII diagram comparing passing `rating` (which sends 0 while screen updates to 5) versus computing `nextRating = 5` once (which sends 5 and updates screen to 5).

> [!PRINCIPLE]
> **Principle 2: Compute the next value once and use it after the setter**
> When an event handler must update state and notify an outside service or API, do not read the state variable right after calling the setter. The state variable still holds the value from the current run. Instead, calculate the new value once in a local variable. Pass that variable to the setter to schedule the screen update, and pass the same variable to the outside function.
>
> *We should do this:*
> `const nextCount = 5; // compute next value once`
> `setCount(nextCount);`
> `sendCount(nextCount); // sends 5 to the server`
>
> *We should not do this:*
> `setCount(5);`
> `sendCount(count); // sends old count 0 to server`

- [question-cycle] Question 3: A delayed timer callback keeps reading the rating from its own render
    - Question: "My Send button starts a `setTimeout` that thanks the reader for the rating. If the rating changes before the timer fires, which number does the message show?"
    - Code and result: Inside `StoryFeedback`, the Send button handler schedules a 100 ms timer: `setTimeout(() => console.log('Thanks for rating ' + rating), 100);`. The user rates 5, clicks Send, and quickly clicks 2 before the 100 ms timer fires. The screen updates to show 2 stars, but the timer callback prints "Thanks for rating 5" in the console (React 19.3.0).
    - Verdict: works as expected.
    - Answer: The user might expect the delayed timer to read the newest rating (2) because it executes after the screen has already re-rendered. In JavaScript, an inner function is a closure that captures the variables in scope when it was created. The render where `rating` was 5 created its own Send handler. Clicking Send created a timer callback that closed over that render constant `rating` value of 5. When the user later clicked 2, React re-rendered `StoryFeedback` with a new constant `rating = 2` and created new event handlers for the new screen. That second render does not mutate the variables held by the existing timer callback. When the timer fires, it reads the 5 from its own render snapshot. This snapshot model protects asynchronous and delayed code from race conditions: if a user sends a message to Alice and then switches to Bob before the delay completes, the message is sent to Alice as intended.
    - Fix: none (the code behaves as designed).
    - Rule with boundary: Event handlers and asynchronous callbacks retain the state values of the render that created them, even when executed after later re-renders. Boundary: if asynchronous code must read a mutable value across renders without triggering re-renders, React provides refs (deferred to Lecture 29).
    - Needs: closure (runway), setTimeout (runway), template literal (recall, Lecture 4).
    - Diagram: ASCII diagram showing Render 1 (rating=5, schedules timer) -> Render 2 (rating=2, screen updates to 2) -> Timer fires (reads captured rating=5 from Render 1).

> [!PRINCIPLE]
> **Principle 3: An event handler keeps the state of the render that created it**
> Every time React runs a component, that run creates its own fresh event handler functions. In JavaScript, an inner function is a **closure**: it remembers the variables of the function call where it was created. When a timer or delayed callback is scheduled, it closes over the state variables of that specific run. If a later click changes state and causes React to run the component again, the new run gets new state variables and new handlers. The earlier timer callback continues running with the values from the run that created it.
>
> >> closure : a JavaScript function that remembers variables from the scope where it was defined
>
> *We should do this:*
> `function handleSend() {`
> `  setTimeout(() => {`
> `    console.log(`Rating: ${count}`); // reads count from this render`
> `  }, 3000);`
> `}`

### Where you will meet this

- [p] In production applications, understanding state snapshots is vital when sending analytics telemetry, dispatching API requests, and managing delayed notifications. A frequent bug occurs when an engineer calls a state setter and immediately passes the state variable to an analytics helper on the next line, causing telemetry pipelines to record outdated values. Computing the value once in a local variable resolves this issue permanently.

- [p] Another universal scenario involves form submissions with delayed confirmation toasts or undo banners. When a user submits an item and quickly navigates or edits another record, delayed timer callbacks rely on closure capture to display the exact data submitted at that moment, rather than whatever record the user is currently editing.

### For the interview

- [interview] The Interview Question: Why does state appear frozen inside a render, even right after you set it?

- [p] **1. The Hidden Signal**: The interviewer is probing whether you understand React declarative execution lifecycle and closure mechanics, or whether you still hold an imperative mental model where setters mutate variables in place. Senior engineers explain that React keeps state outside the component and provides each render with an immutable snapshot. They clearly articulate that setters schedule future renders rather than altering variables in currently executing code.

- [p] **2. The Classic Trap**: The classic trap is claiming that "setState is asynchronous, so the variable has not updated yet." This answer confuses the timing of the next render with variable mutability. Even if JavaScript waited, the state variable inside the current function execution is a `const` primitive; no background process could mutate a local constant in running JavaScript. Another frequent trap is trying to fix the old value by adding a `setTimeout(..., 0)`, unaware that the callback still closes over the same render snapshot.

- [p] **3. What is Actually Going On**: React calls your component function to render the user interface. During that call, `useState` returns the state value for that specific render. Inside that function execution, the state variable is a constant. Calling a state setter queues a request for React to run the component again with a new value during the next render. The current function continues executing using its existing snapshot values. If code inside the handler needs the new value immediately, it must calculate that value once in a local variable and use it for both the setter and subsequent operations.

- [p] **4. Where It Gets Tricky**: What happens across an `await` pause in an asynchronous handler? If a handler awaits a network request and reads state after the promise settles, it still reads the snapshot value from the render that created it, even if user clicks in the meantime caused React to re-render. What happens with repeated setter calls? Calling `setCount(count + 1)` three times queues three requests to replace state with `0 + 1`, incrementing the counter by only one. What if code genuinely requires reading the latest mutable value across renders without triggering updates? That requirement calls for a ref (`useRef`), which React provides specifically for mutable storage outside the render snapshot.

### Glossary

- [glossary] Snapshot ◼ The immutable set of state values, props, and event handlers provided by React for a single execution of a component function.
- [glossary] State Variable ◼ A constant value returned by useState that reflects the component data for the current render.
- [glossary] Setter Function ◼ The update function returned by useState that records a requested value in React and schedules a future render.
- [glossary] Closure ◼ A JavaScript function that retains access to variables from its defining lexical scope, even when executed at a later time.
- [glossary] Substitution Method ◼ The mental debugging technique of replacing state variables with their concrete render values to predict handler behavior.
