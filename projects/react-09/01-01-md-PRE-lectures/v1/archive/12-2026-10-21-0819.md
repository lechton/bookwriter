### A pure function only calculates

- [runway] Pure function, idempotence, side effect, and `Math.random()`, used by Questions 1 and 2.

- [p] ◇ {the pure function, named with code the reader knows} A formula from school, `y = 2x`, gives 6 for 3, every time. A JavaScript function can work the same way: ◼ Educational objective: say what the code is for before it appears; react.dev's own starting point ("Components as formulas").

- [code] A pure function:

```js title="A pure function"
function double(number) {
  return 2 * number; // double(3) is 6, every time
}
```

◼ **The what-this-introduces list:** 1. `double`: a function that only calculates.

- [p] ◇ {two properties, named} `double` is a **pure function**, and it has two properties. It gives the same result for the same inputs, every time: this is called **idempotence**, from the Latin for "the same power". And it changes nothing that existed before it was called: no outside variable, no object it received, nothing on the page. A change of that kind is called a **side effect**, because it happens on the side of the result. ◼ Educational objective: the three terms, each with its plain meaning, before the questions use them.

- [code] Two functions that are not pure:

```js title="Two functions that are not pure"
let total = 0;
function addToTotal(number) {
  total = total + number; // a side effect: changes an outside variable
  return total; // and so a different result on every call
}
const pick = () => Math.random(); // a different result on every call
```

◼ **The what-this-introduces list:** 1. `addToTotal`: changes `total`, and gives 3, then 6, then 9 for the same 3. 2. `Math.random()`: a new number between 0 and 1 on every call.

- [p] ◇ {the rule} `addToTotal(3)` gives 3, then 6, then 9, because each call changes the variable the next call reads. `Math.random()` gives a new number every time, by design. A pure function only calculates: the same inputs give the same result, and nothing outside it changes. ◼ Educational objective: confirm both properties on a second example, then state the rule Questions 1 and 2 apply to components.

### Some array methods change the array they are called on

- [runway] Mutation and local mutation, array `push()`, `reverse()`, and `sort()`, used by Question 2 and Step 2.

- [p] ◇ {mutation, named with code} Changing an object or an array that already exists is called a **mutation**. Some array methods mutate: **`push()`** adds an item at the end of the array it is called on, **`reverse()`** turns it around in place, and **`sort()`** reorders it in place. Others, such as `map()` and `filter()` from Lecture 11, leave the array alone and give back a new one. ◼ Educational objective: the refreshers the map marks `yes`, sorted into the two groups Question 2 needs.

- [code] Methods that change the array, and a copy that protects it:

```js title="Changing an array, and changing a copy"
const titles = ['New Park', 'Rain'];
titles.push('Soups'); // titles itself now has three items
const copy = [...titles]; // a new array with the same items
copy.reverse(); // copy is turned around, titles is not
```

◼ **The what-this-introduces list:** 1. `push()` and `reverse()`: methods that change their array. 2. `[...titles]`: a copy (recall Lecture 7).

- [p] ◇ {local mutation, then the rule} The copy is new, so changing it changes nothing anyone else holds. Changing something created a moment ago, inside the same function, is called **local mutation**, and it is harmless. Mutation changes an array that already exists; a copy turns it into local mutation. ◼ Educational objective: the boundary of Principle 2 (react.dev "Local mutation: your component's little secret"), taught before the question that needs it.

### Principles of React: Pure Rendering

- [preview] Everything in this lesson comes down to one idea: pure rendering, which means that each call of a component only calculates its JSX from its inputs. First, idempotence, which means each call gives the same JSX for the same inputs: what the component shows depends on its props alone, never on how many times it was called. Second, no side effects, which means each call changes nothing that existed before it: the component may change only what it created during the same call. Third, Strict Mode, which means each component is called twice in development, to catch impure calls: we keep it on, because a pure component shows nothing different on the second call. ◼ Educational objective: the map's Spoken Preview, word for word, one paragraph for the anchor and one per principle in the lecture, read aloud before Question 1.

> [!PRINCIPLE]
> **Principle 1: Idempotence: each call gives the same JSX for the same inputs**
> *A component's JSX depends only on its props: we never read and change a variable outside the component while it runs, and never show a value that changes on every call, such as `Math.random()` or `new Date()`; a number that depends on an item's place comes in as a prop.*
>
> React calls a component whenever it needs its JSX, and it may call it more than once. A variable outside the component is shared by every call, so a component that adds one to it gives a different number on each call: the page then shows how many calls happened, not what the props say. A value that changes by itself, such as `Math.random()`, does the same. When every value the JSX shows comes from the props, every call gives the same JSX, however many calls there are.
>
> *We should do this:*
> `function Item({ number }) {`
> `  return <p>#{number}</p>; // the same on every call`
> `}`
>
> *We should not do this:*
> `let count = 0;`
> `function Item() {`
> `  count = count + 1; // a different number on every call`
> `  return <p>#{count}</p>;`
> `}`

> [!PRINCIPLE]
> **Principle 2: No side effects: each call changes nothing that existed before it**
> *While a component runs, we change only what that call created: a copy of an array or object is ours to change, while props, imported data, outside variables, and the page itself stay as they were; changes to the outside world belong in event handlers.*
>
> An array or object that existed before the call, such as a prop or imported data, is shared: every call receives the same one. > `const items = [...list]; // a new array on every call`

> `list.push(lastItem); // changes the shared array on every call`

> [!PRINCIPLE]
> **Principle 3: Strict Mode: each component is called twice in development, to catch impure calls**
> *We keep `<StrictMode>` around the app: in development it calls each component twice and keeps one result, so an impure component shows its mistake at once, and the doubled logs disappear in the production build.*
>
> A function that runs twice looks like a mistake, so removing Strict Mode seems to fix it. But in development, Strict Mode calls each component twice on purpose and keeps one result. A pure component gives the same JSX both times, so the page shows no difference, and only its logs appear twice. An impure component gives a different result on the second call, so its mistake shows on the first page instead of some render later. Removing Strict Mode removes the second call, not the mistake. The production build calls each component once, so the check costs users nothing.
>
> *We should do this:*
> `root.render(`
> `  <StrictMode>`
> `    <App /> {/* called twice in development only */}`
> `  </StrictMode>`
> `);`
>
> *We should not do this:*
> `root.render(<App />); // the mistake waits for the next render`

- [p] ★ This step applies the second principle, no side effects, which means each call changes nothing that existed before it. Decision: the articles in `articles.js` are in the order they were published, so the newest is last; the box needs them the other way round, but the main list reads the same array and must keep its order; so the box reverses a copy, `[...articles].reverse()`, never `articles.reverse()`. Prediction: what would `articles.reverse()` show here, with Strict Mode on? The box would list the oldest first, because its second call turns the shared array back (verified). Result: the box shows "Fresh Bread at Home" first and "New Park Opens Today" last, and the main list still starts with "New Park Opens Today" (verified). ◼ Meaningful pedagogical commentary: two components reading one array is normal; the copy is what lets one of them change the order for itself.

In React 19, the counter showed how many calls happened, the shared array grew and turned back with every call, and the second call was the check that showed both at once. ### Where you will meet this

- [p] 1. **Numbered rows and positions**: rankings, steps, and search results take their number from the list's position, passed as a prop, never from a counter.
- [p] 2. **Sorting and reversing data for one view**: "newest first", "most popular", and "A to Z" boxes sort a copy, `[...items].sort(...)`, because other parts of the page read the same data.
- [p] 3. **Doubled logs in development**: every new Vite project has Strict Mode on, and every log in a component body prints twice; the fix is never to remove it.
- [p] 4. **Code review**: a variable at the top of a component file that the component changes, or `push`, `sort`, and `reverse` on a prop, is flagged before anything else.
- [p] 5. **The tab title and other changes outside the page**: they happen in response to something, such as a click, in an event handler (Lecture 13), never while the component calculates its JSX.

### For the interview

- [interview] > **The Interview Question:** What does it mean for a component to be pure, and what breaks when it is not?

- [interview] **1. The Hidden Signal** ◼ The interviewer wants the two halves of purity and the reason React needs them. A junior answer says "a pure component has no side effects". A strong answer adds "the same inputs give the same JSX", explains that React may call a component many times, and connects this to Strict Mode calling it twice in development.

- [interview] **2. The Classic Trap** ◼ The classic trap is "React renders twice because of a bug, so I remove Strict Mode". On the article list, a counter outside the card showed #2, #4, #6 with Strict Mode. Removing it showed #1, #2, #3 until the next save, which gave #4, #5, #6. The mistake was in the card, and Strict Mode only made it visible earlier.

- [interview] **3. What is Actually Going On** ◼ `let cardNumber = 0` sat at the top of `ArticleCard.jsx`, outside every call, and each call added one, so the number grew with the calls, not with the cards. The fix passed `number={index + 1}` from the list. The list's `articles.push(...)` changed the array every call receives, so a second call pushed a second "See all articles"; pushing into `[...articles]`, a copy made in the call, showed it once.

- [interview] **4. Where It Gets Tricky** ◼ *Is it wrong to change any variable during render?* No: a variable or array created inside the same call is the component's own, and changing it is local mutation. *Why does `articles.reverse()` seem to do nothing in development?* Strict Mode's second call turns the shared array back. *Can a component show `new Date()` or `Math.random()`?* Not as a value computed while it renders: every call gives a different one. *Does Strict Mode run in production?* No; `npm run preview` called each card once. *Where do changes to the outside world go?* In an event handler (Lecture 13), or, as a last resort, an Effect (Lecture 31). *Why does React care?* So it can render on a server, skip unchanged components, and stop and restart a render (Lectures 102, 55, and 66).

### Glossary

- [glossary] Pure function ◼ A function that gives the same result for the same inputs and changes nothing that existed before it was called. React expects every component to be one.
- [glossary] Idempotence ◼ Giving the same result every time for the same inputs. A component is idempotent when the same props give the same JSX on every call.
- [glossary] Side effect ◼ A change a function makes outside its own result: an outside variable, an object it received, the page, the tab title.
- [glossary] Local mutation ◼ Changing a variable, array, or object created inside the same call. It is harmless, because nothing outside the call holds it.
- [glossary] Strict Mode ◼ A development check, `<StrictMode>` around `<App />`, that calls each component twice and keeps one result, so an impure component shows its mistake at once. It does nothing in production.

### Summary

- [review-title] **Pure rendering: each call of a component only calculates its JSX from its inputs**

- [review-subtitle] ❒ Idempotence: each call gives the same JSX for the same inputs
- [always-rule] ➔ ALWAYS build what a component shows from its props, and pass a number that depends on the place as a prop.
- [never-rule] ➔ NEVER read and change a variable outside the component while it runs.
- [never-rule] ➔ NEVER show a value that changes on every call, such as `Math.random()` or `new Date()`, computed while the component runs.

- [review-subtitle] ❒ No side effects: each call changes nothing that existed before it
- [always-rule] ➔ ALWAYS copy an array or object before you change it, `[...items]`.
- [never-rule] ➔ NEVER call `push`, `sort`, or `reverse` on props or imported data while a component runs.
- [if-then-rule] ➔ IF something outside the page's JSX must change THEN do it in an event handler, never while the component runs.

- [review-subtitle] ❒ Strict Mode: each component is called twice in development, to catch impure calls
- [always-rule] ➔ ALWAYS keep `<StrictMode>` around the app; the doubled logs are the check at work.
- [if-then-rule] ➔ IF the second call shows a different page THEN fix the component, not `main.jsx`.

- [closing-line] The same inputs, nothing changed, and a second call to prove it. ◼ Educational objective: the map's Closing Line, the last spoken sentence of the lesson.
