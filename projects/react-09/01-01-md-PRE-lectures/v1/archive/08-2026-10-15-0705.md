### Splitting components across files keeps each file easy to scan

- [p] ◇ {starting point: Lecture 5} Since Lecture 5, every component you write lives in one file, `App.jsx`. The card and the page that shows it sit side by side, so `App` uses `ArticleCard` simply by writing its tag. ◼ Educational objective: start from the code the reader already writes; the map's Theme and Options lists no options, so this is the starting point, not a rival way.

- [code] Starting point: the card and the page in App.jsx:

```jsx title="App.jsx"
function ArticleCard({ title }) {
  return <article className="card">{title}</article>; // declared in this file
}
export default function App() {
  return <ArticleCard title="New Park Opens" />; // used without an import
}
```

◼ **The what-this-introduces list:** 1. `ArticleCard`: the card declared in the same file as the page. 2. `App`: the root component using the card by its tag, with no import.

- [p] ◇ {theme} As the site grows, that one file grows with it. The card, the badge, the header, and the footer all end up in the same long `App.jsx`, and another page that needs the card cannot reach it without copying its code. So every React developer meets the same question: how does a component written in one file get used in another file? ◼ Educational objective: the theme from the map's Theme and Options, grounded in the file the reader knows.

- [p] ◇ {term: ES modules, module} JavaScript answers it with **ES modules**, the module system built into the language (ES stands for ECMAScript, the official name of JavaScript). Each file is a **module**: the names declared in it stay inside that file until the file exports them and another file imports them. ◼ Educational objective: name the exact terms with their plain meaning (lecture-voice Section 22).

- [p] ◇ {folders before file names} Your project's code lives in a folder named `src`, and `App.jsx` sits inside it. When a component moves out, it goes into a folder named `components` that sits inside `src`, next to `App.jsx`. ◼ Educational objective: the file-name evaluation; the folder structure comes before the file names.

◼ **The what-this-introduces list:** 1. `export default`: marks `ArticleCard` as the primary component of this file. 2. `ArticleCard`: the same component, now in its own file.

### A module keeps its names private until you export them

- [runway] The module boundary and relative paths, used by Question 1.

- [p] ★ {preknowledge: functions declared inside one file share scope} We know from Lecture 5 that when two functions are declared in the same file, one function can call the other directly because both exist in the same scope. In modern JavaScript and React, every separate file is an isolated **module**. Variables, functions, and components declared inside a module are private to that file. ◼ Educational objective: establish the module scope boundary before showing exports.

- [code] Module privacy: private helper in ArticleCard.jsx:

```jsx title="ArticleCard.jsx"
function formatDate(date) { // private helper function
  return `Published ${date}`;
}

export default function ArticleCard({ date }) {
  return <p>{formatDate(date)}</p>; // helper called inside file
}
```

◼ **The what-this-introduces list:** 1. `formatDate`: an unexported private function invisible outside this file. 2. `export default`: shares `ArticleCard` with the rest of the application.

- [p] ◇ {runway: relative paths} To import a component from a file in your project, you specify a **relative path** starting with `./`. The `./` tells the build tool to look for the file starting from the folder of the current file. In contrast, a **package import** like `import { useState } from 'react'` has no `./` because its name points into installed packages in `node_modules`. ◼ Educational objective: distinguish relative file paths from package imports.

- [code] Relative import path in App.jsx:

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // relative file path

export default function App() {
  return <ArticleCard date="Monday" />; // renders imported card
}
```

◼ **The what-this-introduces list:** 1. `./components/ArticleCard.jsx`: relative path navigating to the components directory. 2. `ArticleCard`: local identifier holding the imported component.

### Default exports share one main value, named exports share several

- [runway] Default and named exports, used by Questions 2 and 3.

- [p] ★ {preknowledge: export default from Lecture 2} In Lecture 2, we used `export default` to share the main component from `App.jsx`. JavaScript provides two primary ways to export values from a module: **default exports** and **named exports**. A default export represents the primary component of a file, declared with `export default`. A file can have at most one default export. In contrast, named exports allow a module to share multiple secondary helpers or utilities, declared with `export function Name()`. ◼ Educational objective: contrast default and named exports mechanically.

- [code] Combining default and named exports in one file:

```jsx title="ArticleCard.jsx"
export default function ArticleCard({ title }) { // primary default export
  return <article className="card">{title}</article>;
}

export function Badge({ text }) { // secondary named export
  return <span className="badge">{text}</span>;
}
```

◼ **The what-this-introduces list:** 1. `export default function ArticleCard`: default export for the primary component. 2. `export function Badge`: named export for the helper component.

- [p] ◇ {runway: matching import syntax} How you export a value dictates how you must import it. A **default import** is written without curly braces: `import ArticleCard from './ArticleCard.jsx'`. Because a file has only one default export, you can give it any local variable name. A **named import** is written with curly braces: `import { Badge } from './ArticleCard.jsx'`. The identifier inside the braces must match the exported name character for character. These curly braces are not JSX braces and not runtime destructuring; they are static module bindings checked at build time. ◼ Educational objective: teach the import syntax matching rule and contrast curly braces in imports with JSX braces.

- [code] Importing default and named exports together:

```jsx title="App.jsx"
import ArticleCard, { Badge } from './components/ArticleCard.jsx'; // combined

export default function App() {
  return (
    <ArticleCard title="News">
      <Badge text="LIVE" /> {/* uses named helper */}
    </ArticleCard>
  );
}
```

◼ **The what-this-introduces list:** 1. `ArticleCard`: default import without curly braces. 2. `{ Badge }`: named import inside curly braces. 3. Combined import statement: imports both in a single concise line.

### Principles of React: Splitting Components with Imports and Exports

- [question-cycle] Question 1: Moving a component to a new file leaves the screen blank
    - Question: "I moved ArticleCard into its own file under src/components/. Why does App say it is not defined?"
    - Code and result: `ArticleCard` is moved to `src/components/ArticleCard.jsx` and exported with `export default`. `App.jsx` renders `<ArticleCard />` without an import line. When the browser refreshes, the screen is blank, and the browser console prints `ReferenceError: ArticleCard is not defined`.
    - Verdict: does not do what the reader wanted.
    - Answer: Each JavaScript file is an isolated module with its own private scope. Functions and variables declared in one file are not visible to other files by default. Even though `ArticleCard.jsx` exists in the same project, `App.jsx` cannot see `ArticleCard` unless `App.jsx` explicitly imports it. When React renders `App`, JavaScript looks for `ArticleCard` in `App.jsx`'s scope, cannot find it, and throws a `ReferenceError`. The render crashes, and the screen goes blank.
    - Fix: Add `import ArticleCard from './components/ArticleCard.jsx'` at the top of `App.jsx`.
    - Rule with boundary: Each file is a module with private names; a name crosses into another file only through an export and an import. A helper used only inside its own file needs no export.
    - Needs: module (runway), relative path `./` (runway), ReferenceError (recall Lecture 5), export default (recall Lecture 2).
    - Diagram: ASCII diagram showing the module boundary between `ArticleCard.jsx` and `App.jsx`, with the import line bridging the gap.

> [!PRINCIPLE]
> **Principle 1: Each file is a module, and names cross files only by export and import**
> When React runs an application, each file is an isolated **module** with its own private scope. Functions, variables, and components declared in a file are not visible to other files by default. A component crosses into another file only when the source file exports it and the destination file imports it. Without an import statement, referencing a component from another file throws a `ReferenceError` during render, leaving the page blank.
>
> >> module : an isolated file with private scope that exposes values only through explicit exports and imports
>
> *We should do this:*
> `import ArticleCard from './components/ArticleCard.jsx';`
> `export default function App() {`
> `  return <ArticleCard />; // renders imported card`
> `}`
>
> *We should not do this:*
> `// App.jsx without import statement`
> `export default function App() {`
> `  return <ArticleCard />; // ReferenceError: not defined`
> `}`

- [question-cycle] Question 2: Importing a named export without braces stops the build
    - Question: "Do I write braces around the name or not?"
    - Code and result: `ArticleCard.jsx` exports `ArticleCard` as default and `Badge` as a named export. `App.jsx` writes `import Badge from './components/ArticleCard.jsx'` without braces. The development server stops with `The requested module '/src/components/ArticleCard.jsx' does not provide an export named 'default'`, the screen stays on its loading text, and `vite build` halts with `[MISSING_EXPORT] "default" is not exported`.
    - Verdict: does not do what the reader wanted.
    - Answer: JavaScript ES modules link imports to exports statically before any component runs. An import without braces requests the module's single default export. If the target file has only named exports, or if you write the helper name without braces, the engine looks for an export named `default`, fails to find it, and halts compilation immediately. Conversely, writing `import { ArticleCard }` with braces for a default export causes the engine to look for a named export called `ArticleCard` and fail with `does not provide an export named 'ArticleCard'`.
    - Fix: Match the import syntax to the export declaration: write `import ArticleCard from './components/ArticleCard.jsx'` for the default export, and `import { Badge } from './components/ArticleCard.jsx'` with curly braces for the named export.
    - Rule with boundary: Always import a component using the syntax that matches its export: no braces for default exports, and curly braces with the exact name for named exports.
    - Needs: named export (runway), default import (runway), named import (runway), curly braces in import (runway).
    - Diagram: ASCII diagram comparing default import linking without braces to named import linking with curly braces.

> [!PRINCIPLE]
> **Principle 2: Import with the same form the file used to export**
> JavaScript ES modules link imports to exports statically before any component executes. A **default export** must be imported without curly braces, and the importing file can assign it any local name. A **named export** must be imported with curly braces, and its name must match the exported identifier character for character. If the import syntax does not match the export declaration, the module fails to link, halting the development server and production build.
>
> >> default export : the primary value of a module, imported without curly braces under any local name
> >> named export : a specific value exported by name, imported inside curly braces matching its exact identifier
>
> *We should do this:*
> `import ArticleCard, { Badge } from './Card.jsx'; // imports both`
> `<ArticleCard><Badge text="LIVE" /></ArticleCard>; // renders both`
>
> *We should not do this:*
> `import { ArticleCard } from './Card.jsx'; // wrong for default`
> `import Badge from './Card.jsx'; // wrong for named export`

- [question-cycle] Question 3: Adding a second default export to a file halts compilation
    - Question: "Should Badge be a default or a named export?"
    - Code and result: Inside `ArticleCard.jsx`, `ArticleCard` is already exported with `export default`. A developer adds `export default function Badge()`. The build stops with `A module cannot have multiple default exports`.
    - Verdict: does not do what the reader wanted.
    - Answer: By definition in the ECMAScript standard, a module can have at most one default export. If a file contains two `export default` statements, the JavaScript compiler stops immediately with a syntax error. When a file contains one primary component and secondary helpers, export the primary component as the default export and secondary helpers as named exports. Furthermore, always write component functions with explicit names. An anonymous default export like `export default () => {}` displays as `<default>` in error callstacks and React DevTools, making bugs difficult to trace.
    - Fix: Keep `ArticleCard` as the single default export, and export `Badge` as a named export: `export function Badge({ text })`.
    - Rule with boundary: Export the primary component of a file as default, and secondary helpers as named exports. If a team keeps a convention of using only named exports across the project, follow that team convention.
    - Needs: one default export limit (runway), named functions in error stacks (runway), React DevTools (recall Lecture 5).
    - Diagram: ASCII diagram showing one default export slot alongside multiple named export slots in a module.

> [!PRINCIPLE]
> **Principle 3: One default export for the main component, named exports for the rest**
> An ES module allows at most one **default export** but any number of **named exports**. When a file provides one primary component, export that component as the default export so callers can import it cleanly. When that same file provides secondary helpers or sub-components that other files also use, export them as named exports. If a file contains two default exports, the compiler stops immediately. Always name your component functions, because an anonymous default export displays as `<default>` in error callstacks and React DevTools.
>
> >> anonymous component : a component function declared without a name identifier in its definition
>
> *We should do this:*
> `export default function ArticleCard() {} // primary component`
> `export function Badge({ text }) {} // secondary named helper`
>
> *We should not do this:*
> `export default function ArticleCard() {} // first default export`
> `export default function Badge({ text }) {} // duplicate default fails`

### For the interview

> **The Interview Question:** How do you split components across files, and how do default and named imports differ?

- [interview] The Hidden Signal ◼ Whether the candidate understands JavaScript module boundaries, static import resolution at build time, the difference between default and named bindings, and the debugging consequences of anonymous component exports.
- [interview] The Classic Trap ◼ Confusing import curly braces with JSX expression braces or runtime object destructuring. Forgetting that default imports link to the module's default export regardless of local naming, while named imports strictly enforce exact identifier matching.
- [interview] What is Actually Going On ◼ Each file is an ES module evaluated in its own scope. Build tools like Vite construct a module dependency tree by parsing import and export declarations statically before any component renders. Default exports bind to the module's `default` key, while named exports bind to explicit named export keys on the module record.
- [interview] Where It Gets Tricky ◼ Anonymous default exports (`export default () => {}`) print `<default>` in React callstacks. A module code line at the top level evaluates once on file import, whereas code inside the component function executes on every render.

### Glossary

- [glossary] module ◼ An isolated JavaScript file with private scope that shares values across file boundaries only through explicit exports and imports.
- [glossary] default export ◼ The single primary value or component exported by a module, declared with `export default` and imported without curly braces under any local name.
- [glossary] named export ◼ A specific value or component exported by name using `export function`, imported inside curly braces matching its exact identifier.
- [glossary] default import ◼ An import statement written without curly braces that loads the primary default export of a module.
- [glossary] named import ◼ An import statement written with curly braces that loads a specific named export from a module.
- [glossary] module dependency tree ◼ The hierarchical graph of file relationships formed by import and export statements, used by build tools to bundle application code.
