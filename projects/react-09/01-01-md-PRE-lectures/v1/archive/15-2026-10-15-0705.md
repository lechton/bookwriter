### Every screen update follows a three-step lifecycle

- [p] ◇ {theme: the three-step lifecycle of user interface updates} In modern web applications, the screen must continuously update in response to user actions. When a reader clicks a like button, submits a rating, or types into an input field, the interface changes to reflect new data. In traditional scripting and imperative JavaScript, developers updated the screen by selecting DOM nodes directly with `document.querySelector` and modifying properties like `textContent` by hand. In React, application code never mutates DOM nodes directly. Instead, React manages updates through a structured three-step lifecycle: triggering a render, rendering components to produce element descriptions, and committing changes to the browser DOM. Understanding what happens in each phase is essential for writing predictable code and avoiding timing defects. ◼ Educational objective: introduce the three-step lifecycle and contrast declarative React updates with imperative DOM mutation.

- [p] ◇ {starting point: imperative DOM habits versus declarative React timing} When developers transition from classic DOM manipulation to React, they often assume that calling a state setter immediately modifies the HTML on the page. In plain JavaScript, assigning `element.textContent = count + 1` updates the DOM synchronously on that exact line of code. In React, calling a state setter does not touch the DOM; it merely schedules a future render. React waits until the current event handler has completely finished executing before it begins rendering components and committing changes to the document. A developer who attempts to read the DOM immediately after calling a setter finds the old value still sitting on the page. Furthermore, developers frequently worry that re-rendering a component will tear down the entire page or wipe out user input from active form fields, unaware that React preserves identical DOM nodes across renders. ◼ Educational objective: expose the false mental model of immediate DOM mutation and introduce DOM preservation.

- [p] ◇ {core questions: four governing laws of the update cycle} This chapter answers four core questions. **How does calling a state setter turn into an updated number on the screen?** **When state changes, does React run the entire application again or only specific components?** **If a component re-renders on every interaction, will it wipe out text that the user is actively typing?** **Why does reading the page immediately after calling a setter return the old count, and where should application side effects read values from?** ◼ Educational objective: frame the four roadmap questions the lecture investigates.

### How a state change triggers an update that renders and commits

- [runway] The three lifecycle steps (trigger, render, commit), `document.querySelector`, manual DOM mutation vs declarative state setters, used by Question 1.

- [p] ★ {preknowledge: manual DOM mutation versus React root mounting} In Lecture 1, we saw that plain JavaScript uses imperative methods like `document.getElementById` and `textContent` to modify elements on the page. In standard browser programming, calling `document.querySelector('.like-count').textContent = '1'` changes the paragraph immediately. In Lecture 9, we learned that React applications mount by calling `createRoot(container).render(<App />)`. That initial call is the very first **trigger** in a React application: it tells React to prepare the initial screen. ◼ Educational objective: recall manual DOM mutation from Lecture 1, connect createRoot from Lecture 9, and introduce the concept of a trigger.

- [p] ★ {mechanism: the three steps of trigger, render, and commit} Every interface update in React proceeds through three distinct steps. The first step is the **trigger**: a request that tells React to calculate a new screen. There are only two triggers: the initial `root.render` call, and calling a state setter like `setLikes`. The second step is **render**: React calls your component functions to determine what JSX they return. During rendering, React does not touch the DOM or change any pixels on the screen; it simply collects the new virtual description of the user interface. The third step is **commit**: React compares the newly returned JSX with the previous render and applies the necessary changes to the real browser DOM. On initial render, React uses `appendChild()` to insert all created DOM nodes; on re-renders, it modifies only the specific attributes and text nodes that changed. After the commit, the browser performs a **browser paint**, recalculating geometry and drawing pixels on the physical screen. ◼ Educational objective: derive the physical distinction between trigger, render, and commit, and distinguish React render from browser paint.

- [code] Declarative state setter versus imperative DOM mutation:

```jsx title="Declarative State Update"
function LikeButton() {
  const [likes, setLikes] = useState(0); // State memory in React
  function handleClick() {
    setLikes(likes + 1); // Triggers a re-render
  }
  return <button onClick={handleClick}>Like ({likes})</button>;
}
```

- [code] Imperative DOM mutation mistake:

```jsx title="Imperative DOM Mutation"
function BrokenButton() {
  let likes = 0; // Local variable React does not track
  function handleClick() {
    likes = likes + 1; // Mutates variable without triggering render
    document.querySelector('.count').textContent = likes; // Mutates DOM directly
  }
  return <button onClick={handleClick}>Like</button>;
}
```

◼ **The what-this-introduces list:** 1. `trigger`: initiating an update via `root.render` or a state setter. 2. `render`: React invoking component functions to produce JSX. 3. `commit`: React applying calculated differences to the browser DOM. 4. `document.querySelector`: browser DOM query method contrasting with declarative state.

### How a state update re-renders its component subtree

- [runway] Component tree re-render scope, owner components, child component cascade, and sibling isolation, used by Question 2.

- [p] ★ {preknowledge: component hierarchies and tree structures} In Lecture 5, we established that React components organize into a tree structure. A root component like `App` branches into child components like `StoryTitle` and `LikeCounter`, which in turn branch into leaves like `LikeLabel`. ◼ Educational objective: recall the component tree structure as the layout for render cascading.

- [p] ★ {mechanism: localized state renders cascading to children} When a state setter executes, React does not re-render the entire application from the root. Instead, React identifies the specific component that owns the state variable where the setter was called. React re-renders that component, and then recursively re-renders every component returned inside its JSX tree. Parent components higher up the tree do not re-render. Sibling components residing in adjacent branches do not re-render. If `App` renders `StoryTitle` and `LikeCounter`, and `LikeCounter` renders `LikeLabel`, calling `setLikes` inside `LikeCounter` causes React to call `LikeCounter` and `LikeLabel`. Neither `App` nor `StoryTitle` is called. Even if `LikeLabel` returns identical JSX output, React still executes its function to verify its returned elements. ◼ Educational objective: derive the precise boundary of a re-render, showing that updates travel strictly downward from the state owner.

- [code] Component tree render scope:

```jsx title="Subtree Render Hierarchy"
function App() {
  console.log('App runs'); // Runs only on initial render
  return (
    <div>
      <StoryTitle /> {/* Sibling: does not re-render on like */}
      <LikeCounter /> {/* Owner: re-renders on state setter */}
    </div>
  );
}
```

- [code] Child component render cascade:

```jsx title="Child Component Execution"
function LikeCounter() {
  const [likes, setLikes] = useState(0);
  console.log('LikeCounter runs'); // Runs on every like
  return <LikeLabel count={likes} />; // Child runs when parent runs
}
```

◼ **The what-this-introduces list:** 1. State owner boundary: the component holding `useState` where execution begins. 2. Child render cascade: child components executing when their parent re-renders. 3. Sibling isolation: sibling branches remaining uncalled during localized state updates.

### How React preserves DOM nodes and form inputs across renders

- [runway] DOM node preservation, virtual DOM reconciliation diffing, input state retention, and browser paint, used by Question 3.

- [p] ★ {preknowledge: browser DOM nodes and user input} A browser web page is constructed from persistent **DOM nodes**, including element nodes like `<p>` and `<input>`, and inner text nodes. When a user types text into an `<input>` element, the browser stores that typed text inside the input DOM node's internal state. In traditional web development, replacing a container with `innerHTML` destroys existing DOM nodes and replaces them with new ones, immediately erasing any text the user was typing and resetting keyboard focus. ◼ Educational objective: recall persistent browser DOM nodes and contrast them with innerHTML destruction.

- [p] ★ {mechanism: diffing output and mutating only changed text nodes} React does not replace the DOM tree when a component re-renders. During the render phase, React executes your component function and collects the new JSX element tree. In the commit phase, React compares this new JSX tree against the JSX tree from the previous render. React identifies the exact minimal differences. If a `<p>` element's text changed from `"0"` to `"1"`, React updates only the specific text node inside that `<p>`. If an adjacent `<input>` element was rendered in the same position in the JSX tree with the same props, React leaves its underlying DOM node completely untouched. The input element retains its identity, its typed text, and its active cursor focus. After the commit phase applies these minimal DOM edits, the browser performs a **browser paint**, drawing the updated pixels onto the screen. ◼ Educational objective: derive why re-rendering does not reset form inputs and define browser paint.

- [code] DOM node preservation across renders:

```jsx title="DOM Node Preservation"
function InteractiveCard() {
  const [likes, setLikes] = useState(0);
  return (
    <div>
      <p>{likes}</p> {/* Text node updates in commit */}
      <input placeholder="Type comment..." /> {/* Preserved untouched */}
      <button onClick={() => setLikes(likes + 1)}>Like</button>
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `DOM node`: persistent browser object representing an HTML tag or text fragment. 2. Minimal diff commit: updating only changed attributes or text nodes. 3. `browser paint`: the browser rendering pixels to the screen following the React commit phase.

### How handler completion governs DOM update timing

- [runway] Event handler completion lifecycle, asynchronous commit scheduling, synchronous DOM read defects, used by Question 4.

- [p] ★ {preknowledge: event handlers and side effects} In Lecture 12 and Lecture 13, we learned that event handlers run in response to user actions outside the render cycle. Handlers are the designated home for side effects, such as sending analytics pings or making network requests. ◼ Educational objective: recall that event handlers execute side effects outside the render phase.

- [p] ★ {mechanism: React renders after the handler returns} When a user clicks a button, the browser dispatches an event, and React invokes your event handler. When your handler executes `setLikes(likes + 1)`, React records the requested state update and schedules a re-render. However, React does not pause your handler or immediately render the component on that line. Your handler continues executing synchronously until it reaches the end of its function block. Only after your handler (and any other handlers triggered by that browser event) has fully returned does React begin the render phase, followed by the commit phase. Consequently, if code on the line immediately following a setter call queries the DOM using `document.querySelector`, the commit phase has not yet occurred. The DOM still holds the old values from the previous render. To send the new value to an external service, you must use the value your code computed directly. ◼ Educational objective: derive why reading the DOM synchronously after a setter returns stale data and enforce using computed variables.

- [code] Post-setter DOM read defect:

```jsx title="Post-Setter DOM Read Defect"
function BrokenTracker() {
  const [likes, setLikes] = useState(0);
  function handleLike() {
    setLikes(likes + 1); // Schedules render for later
    const text = document.querySelector('.count').textContent; // Reads old DOM!
    console.log('Sending:', text); // Sends stale value "0"
  }
  return <p className="count">{likes}</p>;
}
```

- [code] Using computed value directly:

```jsx title="Using Computed Variable"
function CorrectTracker() {
  const [likes, setLikes] = useState(0);
  function handleLike() {
    const next = likes + 1; // Compute next value once
    setLikes(next); // Schedule render with next
    console.log('Sending:', next); // Sends fresh value 1
  }
  return <p className="count">{likes}</p>;
}
```

◼ **The what-this-introduces list:** 1. Handler completion boundary: render and commit occurring after the handler returns. 2. Synchronous DOM read defect: reading uncommitted DOM nodes inside an active handler. 3. Direct computed variable pattern: computing `next` and sharing it across state setters and side effect helpers.

### Principles of React: Trigger, Render, and Commit

- [question-cycle] Question 1: Calling a setter starts an update that reaches the screen in three steps
    - Question: "I call `setLikes(likes + 1)`. How does the new number get onto the screen?"
    - Code and result: Inside `LikeCounter`, a developer replaces the state setter with an imperative DOM mutation: `document.querySelector('.like-count').textContent = likes + 1`. In React 19.3.0, the first click changes the paragraph text to 1, but subsequent clicks keep displaying 1 because `likes` stays 0.
    - Verdict: does not do what the reader wanted.
    - Answer: In plain JavaScript, developers modify the page by mutating DOM nodes directly. In React, code never touches DOM nodes by hand. Calling `setLikes(likes + 1)` initiates a three-step sequence. First is the trigger: the setter stores the next value and tells React to schedule a render. Second is the render: React calls `LikeCounter`, which evaluates its JSX and returns `<p className="like-count">1</p>`, while the page remains unchanged. Third is the commit: React compares the returned JSX with the previous render and updates only the text node inside the paragraph from 0 to 1. On initial mount, `root.render(<App />)` serves as the first trigger, and its commit creates and inserts all initial DOM nodes.
    - Fix: Call the state setter `setLikes(likes + 1)` and allow React to execute the render and commit phases: `<button onClick={() => setLikes(likes + 1)}>Like</button>`. Taught in runway "How a state change triggers an update that renders and commits" and Lecture 14.
    - Rule with boundary: Trigger screen updates by calling state setters; allow React to render components and commit DOM changes. Boundary: application code should never mutate DOM nodes directly.
    - Needs: trigger (runway), render (runway, Lecture 2), commit (runway), document.querySelector (runway).
    - Diagram: ASCII diagram showing the three steps: Trigger (setter call) -> Render (calling component function) -> Commit (updating DOM text node) -> Browser Paint.

> [!PRINCIPLE]
> **Principle 1: After a setter call, React runs the component and then changes the page**
> In plain JavaScript, code updates the screen by mutating DOM nodes directly: `p.textContent = 1` changes the page on that line. In React, application code calls a state setter and leaves DOM manipulation to React. Every update proceeds through three steps. First, the setter asks React for an update: this is the **trigger**. Second, React calls the component function to calculate its latest JSX: this is the **render**, and the page has not changed yet. Third, React compares the new JSX with the previous output and modifies the DOM where they differ: this is the **commit**. Changing DOM nodes by hand bypasses these steps and leaves state variables out of sync.
>
> >> trigger : a request that tells React to calculate an updated user interface
> >> render : React calling component functions to compute their latest JSX
> >> commit : React updating the browser DOM nodes to match the latest JSX
>
> *We should do this:*
> `function LikeCounter() {`
> `  const [likes, setLikes] = useState(0);`
> `  return (`
> `    <button onClick={() => setLikes(likes + 1)}>`
> `      Likes: {likes} {/* updates via render and commit */}`
> `    </button>`
> `  );`
> `}`
>
> *We should not do this:*
> `function LikeCounter() {`
> `  const [likes, setLikes] = useState(0);`
> `  function handleLike() {`
> `    const p = document.querySelector('.like-count');`
> `    p.textContent = likes + 1; // bypasses render and commit`
> `  }`
> `  return <button onClick={handleLike}>Like</button>;`
> `}`

- [question-cycle] Question 2: A state change re-renders its own component and the components inside it
    - Question: "When I click Like, does React run my whole app again, or only `LikeCounter`?"
    - Code and result: An application mounts `App`, which renders a static `StoryTitle` and an interactive `LikeCounter`. `LikeCounter` in turn renders a `LikeLabel`. Adding console logs to all four components prints all four names on initial mount. Clicking the Like button logs `LikeCounter runs` and `LikeLabel runs`, while `App` and `StoryTitle` remain silent (React 19.3.0).
    - Verdict: works as expected.
    - Answer: A state update does not re-render the entire application tree. When `setLikes` is called, React begins rendering at the component that owns the state (`LikeCounter`). React then recursively renders every child component that `LikeCounter` returns in its JSX tree, calling `LikeLabel`. Parent components above `LikeCounter` (such as `App`) and sibling components in adjacent branches (such as `StoryTitle`) are completely bypassed. Furthermore, child components like `LikeLabel` execute their render functions even if their returned JSX output is identical to the previous render.
    - Fix: none (the code functions as designed).
    - Rule with boundary: Expect state updates to re-render the state owner and its nested children; parents and siblings do not re-render. Boundary: skipping child renders when props do not change requires optimization wrappers (deferred to Lecture 55).
    - Needs: component tree (recall, Lecture 5), state owner boundary (runway), child render cascade (runway).
    - Diagram: ASCII diagram showing component tree with re-rendering subtree highlighted (LikeCounter and LikeLabel) while parent (App) and sibling (StoryTitle) remain idle.

> [!PRINCIPLE]
> **Principle 2: A state change runs its own component and the components inside it**
> Components in React form a hierarchical **component tree**. On initial mount, React renders from the root component downward through every branch. When a **state update** occurs, React does not re-render the entire application. It calls the specific component that owns the state variable, and then recursively renders the child components returned inside its JSX. Ancestor components above the state owner and sibling components in adjacent branches do not re-render. A child component re-renders even when its props have not changed.
>
> >> state update : calling a state setter to request a new render of that component
>
> *We should do this:*
> `function Feed() {`
> `  return (`
> `    <main>`
> `      <Header /> {/* does not re-render on counter clicks */}`
> `      <Counter /> {/* owns state: re-renders itself and Label */}`
> `    </main>`
> `  );`
> `}`

- [question-cycle] Question 3: The commit updates only changed nodes, so typed text stays
    - Question: "If React runs `LikeCounter` again on every like, will it wipe the comment the reader is typing?"
    - Code and result: Inside `LikeCounter`, a reader types "great post" into an `<input>` element next to the like count. When the user clicks Like, the count increments from 0 to 1, while the text "great post" remains in the input field, and the input DOM element reference remains identical before and after the click (React 19.3.0).
    - Verdict: works as expected.
    - Answer: Re-rendering does not recreate or reload the browser DOM. During the render phase, React executes `LikeCounter` to compute a new JSX virtual description. During the commit phase, React compares this new description against the previous render. Because the `<input>` element occupies the same position in the JSX tree with identical props, React preserves the existing input DOM node completely untouched. React mutates only the specific text node inside `<p className="like-count">` whose value changed from 0 to 1. The input DOM node retains its identity, its typed text value, and its cursor focus. Once the commit finishes applying these minimal differences, the browser executes a browser paint to draw the updated text on the screen.
    - Fix: none (the code functions as designed).
    - Rule with boundary: Re-render components freely without fearing DOM destruction; React updates only differing DOM nodes during commit. Boundary: changing element keys or component positioning in JSX causes React to recreate DOM nodes (deferred to Lecture 24).
    - Needs: DOM node (runway), commit diffing (runway), browser paint (runway).
    - Diagram: ASCII diagram showing JSX virtual comparison resulting in text node mutation while input DOM node is preserved untouched.

> [!PRINCIPLE]
> **Principle 3: The commit changes only what is different, so typed text stays**
> Re-rendering a component does not destroy or recreate the underlying page. During the render phase, React calculates the new JSX element tree. In the commit phase, React compares the new tree with the previous one and modifies only the specific **DOM node** whose text or attributes changed. Elements that remain in the same position in JSX are preserved. An `<input>` field retains its active focus and any text the user typed. Once the commit completes, the browser performs a **browser paint** to draw the updated pixels.
>
> >> DOM node : an individual HTML element or text object preserved in the browser page
> >> browser paint : the browser drawing calculated pixels and layout onto the visual display
>
> *We should do this:*
> `function CommentBox() {`
> `  const [likes, setLikes] = useState(0);`
> `  return (`
> `    <div>`
> `      <p>Likes: {likes}</p> {/* commit updates only this text */}`
> `      <input placeholder="Type..." /> {/* preserved untouched */}`
> `      <button onClick={() => setLikes(likes + 1)}>Like</button>`
> `    </div>`
> `  );`
> `}`

- [question-cycle] Question 4: Reading the DOM right after a setter finds the old value
    - Question: "I call `setLikes(likes + 1)` and then read the number from the page to send it. Why does it send the old number?"
    - Code and result: Inside `handleLike`, a developer calls `setLikes(likes + 1)` and on the very next line executes `const text = document.querySelector('.like-count').textContent` to send to an analytics server. On the first click, the screen updates to 1, but the analytics server receives 0, and the console shows the send log printing before the render log (React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: A state setter does not update the DOM synchronously. Calling `setLikes(likes + 1)` stores the next value in React's internal queue and schedules a future render. Your event handler continues executing synchronously until it completes. React waits until all code in the event handler has returned before it initiates the render phase, and the commit phase occurs only after rendering completes. On the line immediately following `setLikes`, the commit has not happened yet, so querying the DOM finds the stale text from the previous render. To send the updated number to an external service, compute the next value once in a local variable (`const next = likes + 1`), pass it to `setLikes(next)`, and pass that same variable directly to your side effect helper.
    - Fix: Compute the next value in a local variable and use it for both the setter and the analytics call: `const next = likes + 1; setLikes(next); sendLikeEvent(next);`. Taught in runway "How handler completion governs DOM update timing".
    - Rule with boundary: Never read DOM nodes inside an event handler to inspect pending state updates; compute the next value once and pass it directly to setters and side effects. Boundary: reading actual DOM layout dimensions (like scroll position or element width) requires DOM refs after commit (deferred to Lecture 30).
    - Needs: event handler execution timing (runway, Lecture 13), synchronous DOM read defect (runway).
    - Diagram: ASCII timeline showing handler execution with setter call -> synchronous DOM read finding old value -> handler completion -> React render -> React commit -> DOM updated.

> [!PRINCIPLE]
> **Principle 4: The page changes only after the event handler finishes**
> Calling a state setter asks React to schedule a future render; it does not update the document on that line of code. Your active **event handler** runs to completion first. Only after the handler has completely returned does React execute the render phase and commit changes to the page. Reading the DOM immediately after calling a setter reads the stale value from the previous render. When an external service or analytics tracker needs the new value, compute the next value in a local variable and pass that variable to both the setter and the tracking call.
>
> >> event handler : the function executing in response to a user action before React renders

### Where you will meet this

- [p] In production applications, understanding trigger, render, and commit is vital when integrating analytics trackers, logging user interactions, and handling form inputs. Teams frequently encounter bugs where telemetry payloads send stale counts because an engineer read `element.textContent` synchronously after calling a state setter. Understanding that handlers run to completion before React renders prevents these synchronization defects.

### For the interview

- [p] > **The Interview Question:** What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?
- [p] **1. The Hidden Signal**: The interviewer is testing whether you understand React's declarative execution architecture or whether you still view React as an imperative DOM manipulation library. Strong candidates explain that triggering requests an update, rendering invokes pure component functions without touching the DOM, and committing updates only differing DOM nodes.
- [p] **2. The Classic Trap**: Believing that state setters mutate the DOM synchronously. Candidates often write code that reads the DOM right after a setter and wonder why it returns stale text. Another common trap is confusing React's render phase with the browser's paint phase.
- [p] **3. What is Actually Going On**: React batches state updates and delays rendering until all active event handlers have returned. During the render phase, React calls component functions from the state owner downward. In the commit phase, React calculates minimal DOM differences and updates only changed text nodes or attributes, followed by the browser painting pixels to the display.
- [p] **4. Where It Gets Tricky**: What happens if a child component returns identical JSX? React still executes the child render function unless optimized, but the commit phase makes zero DOM modifications. What about form inputs? React preserves existing DOM nodes if their position in the JSX tree is unchanged, keeping typed text and focus intact.

### Glossary

- [glossary-item] **Trigger**: An event (initial root mounting or a state setter call) that requests React to calculate an updated user interface.
- [glossary-item] **Render**: The phase where React invokes component functions to calculate their latest JSX element descriptions without modifying the DOM.
- [glossary-item] **Commit**: The phase where React applies minimal calculated differences to the browser DOM nodes.
- [glossary-item] **Browser Paint**: The browser engine process of computing layout geometry and drawing pixels onto the visual display following the commit phase.
- [glossary-item] **DOM Node**: A persistent browser object representing an HTML element or text fragment in the document tree.
- [glossary-item] **State Owner**: The specific component declaring `useState` where re-rendering begins following a setter trigger.

### Summary

- [summary-rule] ALWAYS trigger user interface updates using state setters or initial root render calls.
- [summary-rule] NEVER mutate DOM nodes directly with imperative methods like `textContent` in React applications.
- [summary-rule] IF state changes in a component THEN expect React to re-render that component and its children, leaving parents and siblings untouched.
- [summary-rule] IF an event handler triggers a state setter and sends data THEN compute the next value in a local variable instead of reading the uncommitted DOM.
