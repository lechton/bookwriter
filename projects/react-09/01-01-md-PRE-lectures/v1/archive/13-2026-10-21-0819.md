### A page must answer the user

- [p] ◇ {theme, where the reader stands} A page must answer the user: a click on Like says thank you, a comment box takes what the reader types, and a click on an article opens it. So every React developer meets the same question: how does a component run our code when the user acts? On a plain HTML page, the answer was an attribute such as `onclick="likeArticle()"`, or a script that found the element and called `addEventListener`. In a React component, neither is the tool: the component never finds its own elements (Lecture 1), and an attribute holds text, not a function. ◼ Educational objective: the map's theme with `Options: none`: the starting point named in one paragraph, then straight to the chapter's idea, with no list of ways (`lecture-structure` Section 12).

- [p] ◇ {the chapter's idea and its anchor} React lets a component hand a function to an element through a prop, and calls that function when the user acts. This chapter follows one idea from the first question to the last: **event handling**, which means that one click travels from the element to the functions we hand React. It follows the click along its path: the function we hand over, the event the click brings, the parents it climbs through, and the parent component it finally reaches. ◼ Educational objective: plant the anchor and the axis in the exact words of the map's `## Principle Thread`, so the spoken preview lands on phrases the reader has already heard.

### A function can wait for a click

- [runway] The event handler, the event prop, and `alert()`, used by every question and step.

- [p] ◇ {the event handler, named with code} To answer a click, we write a function inside the component and hand it to the element through a prop. The function is an **event handler**, and the prop that receives it, `onClick`, is an event prop. By convention the handler's name is `handle` plus the event, and an event prop's name is `on` plus the event, with a capital letter: ◼ Educational objective: the term with its code and the naming convention react.dev teaches, before any question breaks it.

- [code] A Like button with its handler:

```jsx title="ArticleCard.jsx"
export default function ArticleCard({ article }) {
  function handleLike() {
    alert('You liked "' + article.title + '"'); // shows a message box
  }
```

◼ **The what-this-introduces list:** 1. `handleLike`: an event handler, declared inside the component. 2. `alert(...)`: the browser's message box.

- [p] ◇ {who does what, then the rule} The handler is declared inside `ArticleCard`, so it can read the card's own props, such as `article.title`. `alert()` is the browser's message box, and in this lesson it is how a handler shows that it ran, because a component cannot yet change what the page shows: Lecture 14 adds that. A handler is not part of the JSX the component returns, so React does not run it while it calls the component; it runs it later, when the click happens. That makes handlers the place for side effects, which Lecture 12 kept out of rendering. ◼ Educational objective: who acts (we declare, React calls on the click), why `alert` stands in for state (map Supporting row), and the link to Lecture 12 (map Supporting row on side effects).

### Some events come with an action of their own

- [runway] The form submit and its page reload, the event object, and `e.target`, used by Question 2 and Step 2.

- [p] ◇ {the form submit, in plain HTML} The browser gives some events an action of its own. A `<form>` is the classic case: pressing its button, or Enter inside its box, makes the browser send the form, and on a plain page that means loading the page again with the form's data in the address. Whatever the reader typed disappears with the old page. ◼ Educational objective: the browser's default the reader must know before Question 2, in plain HTML first.

- [code] A form the browser sends on its own:

```html title="A plain HTML form"
<form>
  <input name="comment" />
  <button>Post</button> <!-- sends the form: the page loads again -->
</form>
```

◼ **The what-this-introduces list:** 1. `<form>`: a group of fields the browser can send. 2. A `<button>` inside it: sends the form.

- [p] ◇ {the event object, named with code} When React calls a handler, it passes one argument: the **event object**, called `e` by convention. It describes what happened and lets the handler answer the browser. **`e.preventDefault()`** tells the browser to skip its own action, and **`e.target`** is the element the event started on, so `e.target.value` is the text in a box the user is typing into. ◼ Educational objective: the refreshers the map marks `yes`, each with the line a question uses it in.

### Principles of React: Event Handling

- [preview] Everything in this lesson comes down to one idea: event handling, which means that one click travels from the element to the functions we hand React. First, event handlers, which means the click runs a function we pass, never one we call: we write the function's name, or an arrow around the call, so nothing runs before the user clicks. Second, the event object, which means the click brings the browser's own action, which we can cancel: a form's submit reloads the page unless the handler prevents it. Third, event propagation, which means the click travels up through every parent that listens: when an inner button must act alone, its handler stops the climb. Fourth, callback props, which means the click reaches the parent through a function it passed down: the child calls that function, and the parent decides what the click means. ◼ Educational objective: the map's Spoken Preview, word for word, one paragraph for the anchor and one per principle in the lecture, read aloud before Question 1.

### Question 1: A called handler runs when the page loads

- [question-cycle] Question 1: A called handler runs when the page loads
    - Question: "I wrote `onClick={handleLike()}`. Why do the alerts pop up when the page loads, and never when I click?"
    - Code and result: `ArticleCard` declares `handleLike` on lines 2 to 4 and writes `<button onClick={handleLike()}>Like</button>` on line 9; while the page loads, six alerts appear, "You liked "New Park Opens Today"" twice, then the same for the other two articles; a click on Like afterwards shows nothing (verified in React 19.3.1, Vite 8.3.4, and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: in HTML, `onclick="likeArticle()"` holds text that the browser runs on the click, parentheses and all, so the reader's line looks right; but in JSX the braces run their code at once, while React calls the component (Lecture 4); `handleLike()` is a call (Lecture 2), so the alert shows while React builds the card, and `onClick` receives the call's result, `undefined`; Strict Mode calls each card twice (Lecture 12), which makes six alerts for three cards; a click finds no function in `onClick`, so it does nothing; `onClick={handleLike}` passes the function itself, and React calls it when the user clicks; the HTML habits fail in other ways too: `onClick="handleLike()"`, a text, throws on the click with "Expected `onClick` listener to be a function, instead got a value of `string` type.", and the lowercase `onclick` prints "Invalid event handler property `onclick`. Did you mean `onClick`?" and does nothing (verified).
    - Fix: the junior fix, which removes the parentheses: `onClick={handleLike}`; no alert on load, and one alert on the click (verified). What it does not cover: a handler that needs an argument, such as a `handleShare(title)` helper several buttons share, brings the call back, `onClick={handleShare(article.title)}`, and it runs on load for every card again (verified). The senior fix wraps the call in an arrow function (Lecture 11): `onClick={() => handleShare(article.title)}` passes a new function, and the call inside it runs only on the click (verified). Both forms pass a function; that is the whole rule.
    - Rule: we pass a function to an event prop such as `onClick`: its name, `onClick={handleLike}`, or an arrow around a call that needs an argument, `onClick={() => handleShare(article.title)}`, never a call such as `onClick={handleLike()}`.
    - Needs: the event handler and `alert()` (runway "A function can wait for a click"); code in braces runs at once (recall Lecture 4); reference against call (recall Lecture 2); Strict Mode (recall Lecture 12); the arrow function (recall Lecture 11).
    - Window plan: `ArticleCard.jsx`, lines 1 to 9 (`startLine="1"`); the fix, line 9 (`startLine="9"`); the argument case as a short window of two lines, `title="Passing a handler that needs an argument"`.
    - Diagram: what `onClick` receives in each form, and when the alert runs.

- [code] ArticleCard.jsx, lines 1 to 9, a called handler:

```jsx title="ArticleCard.jsx"
export default function ArticleCard({ article }) {
  function handleLike() {
    alert('You liked "' + article.title + '"');
  }
  return (
    <article className="card">
      <h2>{article.title}</h2>
      <p className="author">{article.author}</p>
      <button onClick={handleLike()}>Like</button> {/* called right away */}
```

◼ **The what-this-introduces list:** 1. `onClick={handleLike()}`: a call inside the braces.

- [diagram] What `onClick` receives:

```ascii title="Three ways to write the prop"
written                              onClick receives   the alert runs
onClick={handleLike()}               undefined          while the page loads
onClick={handleLike}                 the function       on the click
onClick={() => handleShare(title)}   a new function     on the click
```

- [code] The fix, the function passed by its name:

```jsx title="ArticleCard.jsx" startLine="9"
      <button onClick={handleLike}>Like</button> {/* runs on the click */}
```

- [code] A handler that needs an argument:

```jsx title="Passing a handler that needs an argument"
<button onClick={handleShare(article.title)}>Share</button> // runs on load
<button onClick={() => handleShare(article.title)}>Share</button> // on click
```

◼ **The what-this-introduces list:** 1. `() => handleShare(...)`: an arrow that waits for the click.

> [!PRINCIPLE]
> **Principle 1: Event handlers: the click runs a function we pass, never one we call**
> *We pass a function to an event prop such as `onClick`: its name, `onClick={handleLike}`, or an arrow around a call that needs an argument, `onClick={() => handleShare(article.title)}`, never a call such as `onClick={handleLike()}`.*
>
> In HTML, `onclick="like()"` holds text the browser runs on a click. In JSX, the code inside braces runs at once, while React calls the component. So `onClick={like()}` calls the function before anyone clicks, and gives `onClick` its result, `undefined`. `onClick={like}` gives `onClick` the function itself, and React calls it when the user clicks. When the call needs an argument, an arrow function wraps it: the arrow is passed, and the call inside it waits for the click.
>
> *We should do this:*
> `<button onClick={like}>Like</button> // runs on the click`
> `<button onClick={() => share(title)}>Share</button>`
>
> *We should not do this:*
> `<button onClick={like()}>Like</button> // runs on load`

### Question 2: A posted comment reloads the page

- [question-cycle] Question 2: A posted comment reloads the page
    - Question: "Post reloads the page and my comment disappears. Why?"
    - Code and result: `ArticleCard` adds `handleSubmit` on lines 5 to 7, `alert('Thanks for your comment!')`, and a `<form onSubmit={handleSubmit}>` on lines 13 to 16 with a comment box and a Post button; "Great news!" is typed and Post is pressed; the alert shows, then the page loads again at `http://localhost:5173/?comment=Great+news%21`, and the comment box is empty (verified in React 19.3.1 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: the reader expects the handler to replace what the browser does, and remembers that `return false` stopped a form in old HTML; but the handler runs in addition to the browser's own action (runway): React calls `handleSubmit`, the alert shows, and when the handler ends, the browser sends the form as it always does, by loading the page again with the comment in the address, so the old page and the typed text are gone; `return false` does nothing in React, and the page reloads all the same (verified); the handler receives the event object as its argument, and `e.preventDefault()` as its first line tells the browser to skip the reload, so the alert shows and the comment stays in the box (verified); `onSubmit` sits on the form, not `onClick` on the button, so pressing Enter in the box submits too; the same object carries what the user typed: `onChange={e => console.log(e.target.value)}` on the box logs "H", then "Hi", one line per keystroke (verified); a box whose text React itself keeps is Lecture 20's, and Lecture 40 shows a React 19 form that needs no `preventDefault` at all.
    - Fix: `function handleSubmit(e) {`, `e.preventDefault();`, the alert, `}` on lines 5 to 8; the alert shows, the page stays, and "Great news!" stays in the box (verified).
    - Rule: every handler receives the event object as its first argument; when the browser's own action, such as reloading the page on a form's submit, is not wanted, the handler calls `e.preventDefault()` before anything else.
    - Needs: the form submit, the event object, `e.preventDefault()`, and `e.target` (runway "Some events come with an action of their own"); the event handler (Question 1).
    - Window plan: `ArticleCard.jsx` in two windows, one per place: lines 5 to 7, the handler (`startLine="5"`), and lines 13 to 16, the form (`startLine="13"`); the fix, lines 5 to 8 (`startLine="5"`); the typing log as a short window, `title="Reading what the user types"`.

> [!PRINCIPLE]
> **Principle 2: The event object: the click brings the browser's own action, which we can cancel**
> *Every handler receives the event object as its first argument; when the browser's own action, such as reloading the page on a form's submit, is not wanted, the handler calls `e.preventDefault()` before anything else.*
>
> Some events come with an action of the browser's own: a form's submit reloads the page with the form's data. A handler runs in addition to that action, not instead of it, and returning `false` changes nothing. React calls every handler with one argument, the event object, usually called `e`. Its method `e.preventDefault()` tells the browser to skip its own action, so the page stays and whatever the user typed stays with it.
>
> *We should do this:*
> `function handleSubmit(e) {`
> `  e.preventDefault(); // the page stays`
> `  alert('Sent');`
> `}`
>
> *We should not do this:*
> `function handleSubmit() {`
> `  alert('Sent'); // then the page reloads`
> `}`

### Question 3: Like opens the article as well

- [question-cycle] Question 3: Like opens the article as well
    - Question: "Clicking Like also opened the article. Why?"
    - Code and result: for this question the card keeps its title, author, and Like button, and leaves the comment form aside; the whole card opens the article on a click: `handleOpen` on lines 2 to 4 shows "Opening "New Park Opens Today"", and `<article className="card" onClick={handleOpen}>` on line 9 receives it; a click on Like shows "You liked "New Park Opens Today"" and then "Opening "New Park Opens Today"" (verified in React 19.3.1 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: the reader thinks a click belongs to the element under the mouse; but a click starts on the element the user clicked and then climbs to its parent, and to that parent's parent, running every `onClick` it meets; this is called **event propagation**, or bubbling; the button's handler runs first, then the `<article>`'s `handleOpen`; `e.stopPropagation()` as the first line of `handleLike(e)` ends the climb at the button, so only "You liked ..." shows, while a click on the title still climbs to the `<article>` and opens it (verified); the event object tells the two elements apart: `e.target` is the element the click started on, the `<h2>` for a title click, and `e.currentTarget` is the element whose handler runs, the `<article>` (verified); `stopPropagation` and `preventDefault` do unrelated jobs: the first stops the parents' handlers, the second stops the browser's own action; a parent can still see every click with `onClickCapture`, which runs before the climb even when a button stops it (verified); every event climbs except `onScroll`; a clickable `<article>` is a mouse shortcut: Tab skips it and lands on the buttons inside (verified), so a keyboard user needs a real button that opens the article, which Question 4 adds; React itself listens for the click once, at the root element, which Lecture 79 explains.
    - Fix: `function handleLike(e) {`, `e.stopPropagation();`, the alert, `}` on lines 5 to 8; one alert on Like, and the title still opens the article (verified).
    - Rule: a click runs the handler of the element it started on and then the handlers of every parent above it; when an inner button must act alone, its handler calls `e.stopPropagation()`, and a clickable parent always keeps a real button inside it for the keyboard.
    - Needs: the event object (Question 2); the event handler (Question 1); keyboard focus with Tab (taught in the answer, one sentence).
    - Window plan: `ArticleCard.jsx` as a chain of two windows, lines 1 to 7 (`continues="bottom"`) and lines 8 to 15 (`startLine="8"`, `continues="top"`); the fix, lines 5 to 8 (`startLine="5"`).
    - Diagram: the climb of one click on Like, with and without `stopPropagation`.

- [code] The fix, the climb stopped at the button:


◼ **The what-this-introduces list:** 1. `e.stopPropagation()`: ends the climb.

> [!PRINCIPLE]
> **Principle 3: Event propagation: the click travels up through every parent that listens**
> *A click runs the handler of the element it started on and then the handlers of every parent above it; when an inner button must act alone, its handler calls `e.stopPropagation()`, and a clickable parent always keeps a real button inside it for the keyboard.*
>
> A click does not stay on the element under the mouse. It starts there, runs that element's handler, and then climbs through every parent, running each parent's `onClick` on the way. So a button inside a clickable box runs the button's handler and then the box's. `e.stopPropagation()` in the button's handler ends the climb, while a click elsewhere in the box still reaches it. It does not cancel the browser's own action; that is `preventDefault`'s job. And since Tab skips a clickable box, a real button inside it does the same job for the keyboard.
>
> *We should do this:*
> `function handleLike(e) {`
> `  e.stopPropagation(); // only this button's handler runs`
> `  like();`
> `}`
>
> *We should not do this:*
> `function handleLike() {`
> `  like(); // then the box's handler runs too`
> `}`

### Question 4: An onClick on our own component does nothing

```jsx title="ArticleCard.jsx"
  return (
```

> [!PRINCIPLE]
> **Principle 4: Callback props: the click reaches the parent through a function it passed down**
> *A child reports a user's action to its parent by calling a function prop the parent passed down, named for the event, such as `onSelect`; an event prop on our own component does nothing until the component passes it to a browser element.*
>
> On a browser element, `onClick` is an event React listens for. On our own component it is only a prop, and a component that never reads it never hears the click. A child cannot reach its parent's variables either. So the parent passes a function down as a prop, and the child calls it from a real element's handler, with whatever the parent needs to know. The child reports what happened, and the parent decides what it means.
>
> *We should do this:*
> `function Item({ item, onSelect }) {`
> `  return <button onClick={() => onSelect(item.id)}>Open</button>;`
> `}`
>

> `<Item item={item} onClick={() => select(item.id)} /> // never read`

### Step 1: First, we hand every element its function <ArticleCard.jsx>

Decision: four elements in the card answer the user, so each gets a function: Like and Read get their handlers by name, `onClick={handleLike}` and `onClick={handleRead}`, and the card itself needs the article's id, so it gets an arrow around the call, `onClick={() => onSelect(article.id)}`; no line inside the braces calls anything. ### Step 2: Next, we let the form post without reloading <ArticleCard.jsx>

- [p] ★ This step applies the second principle, the event object, which means the click brings the browser's own action, which we can cancel. Decision: the comment is handled on the form's `onSubmit`, not on the Post button's `onClick`, so pressing Enter in the box posts too; the handler's first line cancels the browser's reload. ### Step 3: Then, we stop the climb where a click must act alone <ArticleCard.jsx>

- [p] ★ This step applies the third principle, event propagation, which means the click travels up through every parent that listens. Decision: the whole card opens the article, so every click inside it climbs to that handler; Like must act alone, Read already opens the article and must not open it twice, and a click into the comment box must not open anything; so `handleLike` and `handleRead` stop the climb, and the form stops it for everything inside it. Prediction: what would a click into the comment box do without the form's `stopPropagation`? Open the article, "Opening article 1" (verified). Result: Like shows one alert, Read and a click on the title each open the article once, and the comment box takes text in peace (verified). ◼ Meaningful pedagogical commentary: on a clickable card, every inner control must decide whether its click is also a click on the card.

- [code] ArticleCard.jsx, lines 2 to 9, two handlers that stop the climb:

```jsx title="ArticleCard.jsx" startLine="2"

    alert('You liked "' + article.title + '"');

  function handleRead(e) {
```

### For the interview

- [interview] > **The Interview Question:** How do you respond to user events like clicks and typing, and how do callback props communicate back to parents?

- [interview] **1. The Hidden Signal** ◼ The interviewer wants to hear that a handler is a function React calls later, that a click climbs through the parents, and that data flows down while calls flow up. A junior answer says "you use onClick". A strong answer separates passing from calling, names propagation, tells `stopPropagation` from `preventDefault`, and explains a callback prop as the child reporting and the parent deciding.

- [interview] **2. The Classic Trap** ◼ The classic trap is `onClick={handleLike()}`. On the article site it showed six alerts while the page loaded, two per card because of Strict Mode, and none when the reader clicked: the braces ran the call at once and gave `onClick` its result, `undefined`. A second trap is `onClick` on our own component: `<ArticleCard onClick={...} />` did nothing, because the card never passed it on.

- [interview] **3. What is Actually Going On** ◼ `onClick={handleLike}` hands React a function, and React calls it with an event object when the click arrives. The click then climbs: on the article card, a click on Like ran `handleLike`, then the card's own handler, until `e.stopPropagation()` ended the climb. A form's submit reloaded the page until `e.preventDefault()` cancelled it. To reach the parent, `ArticleList` passed `onSelect={handleSelect}`, and the card's Read button called `onSelect(article.id)`.

- [interview] **4. Where It Gets Tricky** ◼ *How do you pass an argument to a handler?* Wrap the call in an arrow, `onClick={() => onSelect(article.id)}`. *What is the difference between `stopPropagation` and `preventDefault`?* The first stops the parents' handlers, the second the browser's own action. *Can a parent see a click a child stopped?* Yes, with `onClickCapture`, which runs first. *Which event does not climb?* `onScroll`. *What are `e.target` and `e.currentTarget`?* The element the click started on, and the element whose handler runs. *Why a `<button>` and not a clickable `<div>`?* Tab skips the `<div>`, and Enter and Space do nothing on it. *Does React attach a listener to every button?* No: it listens once at the root element (Lecture 79).

### Glossary

- [glossary] Event handler ◼ A function we pass to an event prop such as `onClick`, which React calls when the event happens. By convention its name starts with `handle`.
- [glossary] Event object ◼ The one argument React passes to a handler, usually called `e`. It describes the event and offers `e.preventDefault()` and `e.stopPropagation()`.
- [glossary] Event propagation ◼ The climb of an event from the element it started on through every parent, running each parent's handler; also called bubbling.
- [glossary] `preventDefault` and `stopPropagation` ◼ `e.preventDefault()` cancels the browser's own action, such as a form's reload; `e.stopPropagation()` stops the climb to the parents' handlers.
- [glossary] Callback prop ◼ A function a parent passes to a child, such as `onSelect`, which the child calls to report what the user did. The parent decides what it means.

### Summary

- [review-title] **Event handling: one click travels from the element to the functions we hand React**

- [review-subtitle] ❒ Event handlers: the click runs a function we pass, never one we call
- [always-rule] ➔ ALWAYS pass a function: `onClick={handleLike}`, or an arrow around a call that needs an argument.
- [never-rule] ➔ NEVER write a call inside an event prop, `onClick={handleLike()}`; it runs while the page loads.

- [review-subtitle] ❒ The event object: the click brings the browser's own action, which we can cancel
- [if-then-rule] ➔ IF the browser's own action is not wanted, such as a form's reload, THEN call `e.preventDefault()` first.
- [never-rule] ➔ NEVER rely on `return false` in a React handler; it changes nothing.

- [review-subtitle] ❒ Event propagation: the click travels up through every parent that listens
- [if-then-rule] ➔ IF an inner control must act alone inside a clickable parent THEN call `e.stopPropagation()` in its handler.
- [always-rule] ➔ ALWAYS keep a real `<button>` inside a clickable box, so the keyboard can do what the mouse does.

- [review-subtitle] ❒ Callback props: the click reaches the parent through a function it passed down
- [always-rule] ➔ ALWAYS let the parent pass a function such as `onSelect`, and let the child call it with what the parent needs to know.
- [never-rule] ➔ NEVER expect `onClick` on your own component to work until the component passes it to a browser element.

- [closing-line] Pass the function, cancel the default, stop the climb, and call the parent. ◼ Educational objective: the map's Closing Line, the last spoken sentence of the lesson. The four subtitles above are the four thread labels word for word, so the summary repeats the structure the preview announced (`lecture-structure` Section 13).

**DO THIS:** pass functions, cancel the reload, stop the climb, and call the parent

```jsx right
function handleRead(e) {
  e.stopPropagation();
  onSelect(article.id);
}
function handleSubmit(e) {
  e.preventDefault();
  alert('Thanks for your comment!');
}
return (
  <article className="card" onClick={() => onSelect(article.id)}>
    <button onClick={handleRead}>Read</button>
    <form onSubmit={handleSubmit}>
      <input name="comment" />
    </form>
  </article>
);
```

**DO NOT DO THIS:** call the handler in the prop, and pass onClick to your own component

```jsx wrong
<button onClick={handleLike()}>Like</button>
<ArticleCard article={article} onClick={() => handleSelect(article.id)} />
```
