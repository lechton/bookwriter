### A function's parameters receive the values of a call

- [runway] Function parameter and argument, used by Questions 1 and 2 and Steps 1 and 2.

- [p] ◇ {parameters and arguments} A function lists names between its parentheses: its **parameters**. When we call it, the values we pass are its **arguments**, and each parameter takes the argument in its place. ◼ Educational objective: the plain JavaScript picture that props extend.

- [code] Plain JavaScript, one function, two calls:

```js title="Plain JavaScript: parameters and arguments"
function headline(title, readTime) {
  return title + ', ' + readTime + ' min read';
}
headline('Rail Strike Ends', 5); // 'Rail Strike Ends, 5 min read'
headline('New Park Opens Today', 2); // a different result
```

◼ **The what-this-introduces list:** 1. `title` and `readTime`: parameters. 2. `'Rail Strike Ends'` and `5`: arguments of the first call.

### Destructuring takes properties out of an object by name

- [runway] Destructuring and a default value in destructuring, used by Questions 2 and 3 and Steps 2 and 3.

- [p] ◇ {destructuring} Reading several properties of an object takes one line each: `const title = story.title;`. **Destructuring** does it in one line: names inside curly braces on the left of `=` take the properties with the same names. A name the object does not have gets `undefined`, unless a **default value** follows it after `=`. The same braces can stand in a function's parameter list, and then they unpack the object passed in. ◼ Educational objective: the form Questions 2 and 3 use, taught on a plain object first.

- [code] Plain JavaScript, destructuring with a default:

```js title="Plain JavaScript: destructuring"
const story = { title: 'Rail Strike Ends', readTime: 5 };
const { title, readTime, section = 'News' } = story;
console.log(title, readTime, section); // Rail Strike Ends 5 News
```

◼ **The what-this-introduces list:** 1. `{ title, readTime }` on the left of `=`: destructuring. 2. `section = 'News'`: a default for a property the object lacks.

### Two operators that fall back to a value

- [runway] Logical OR (`||`) and nullish coalescing (`??`), used by Question 3.

- [p] ◇ {or and nullish} `a || b` gives back `a` unless `a` counts as false, and then `b`; `0`, an empty text, `null`, and `undefined` all count as false. `a ?? b` gives back `b` only when `a` is `null` or `undefined`, so a real `0` stays. ◼ Educational objective: the two fallbacks Question 3 compares with a default value.

### Some objects cannot be changed

- [runway] `toUpperCase()`, the frozen object, `TypeError`, and the two builds, used by Question 4 and Step 4.

- [p] ◇ {a text in capitals} A text has methods: `'Rail Strike Ends'.toUpperCase()` gives back `'RAIL STRIKE ENDS'` and leaves the original text as it was. ◼ Educational objective: the method Question 4 and Step 4 use.

- [p] ◇ {frozen objects} JavaScript can **freeze** an object with `Object.freeze`: its properties can no longer be changed. In a module, which every file of our project is, an assignment to a frozen property throws a **`TypeError`**, the error JavaScript reports when a value cannot do what the code asks. The freeze covers only the object's own properties: an object stored inside it can still be changed. ◼ Educational objective: the mechanism behind Question 4's error, and its shallow limit.

- [p] ◇ {two builds} The dev server runs a **development build**, with extra checks that help us find mistakes. `npm run build` makes the **production build**, the one the published site runs, and leaves those checks out so the site is smaller and faster. ◼ Educational objective: why Question 4's mistake can pass in one build and fail in the other.

### Principles of React: Props Are a Component's Arguments

- [preview] Everything in this lesson comes down to one idea: props are a component's arguments, written by the parent and read by the component as one object. First, props, which means the attributes on a component's tag arrive as one object, its only argument: each card gets its own headline because each tag carries its own. Second, destructuring, which means the component names the props it reads, inside curly braces in its parameter list: without the braces, the whole object lands in the first name. Third, default values, which means the component names a fallback for a prop the tag leaves out: the fallback fills a missing prop, but not a null and not a zero. Fourth, read-only props, which means the component reads its props and never changes them: to show a value differently, it makes a new variable. ◼ Educational objective: the map's Spoken Preview, word for word, read aloud before Question 1.

### Question 1: Three tags carry three stories, and the card ignores them

- [question-cycle] Question 1: Three tags carry three stories, and the card ignores them
    - Question: "My three `ArticleCard`s show the same story. How do I give each its own headline?"
    - Code and result: `App` returns `<main>` with three `ArticleCard` tags, each with its own `title` ("City Library Extends Its Hours", "Rail Strike Ends", "New Park Opens Today") and `readTime` (`{3}`, `{5}`, `{2}`); `ArticleCard(props)` logs `props` and still returns `<h2>City Library Extends Its Hours</h2>`; the page shows that headline three times, with no warning, and the Console panel shows three different objects (verified in React 19.3.1, Vite 8.3.4, and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: React collects the attributes of each tag into one object, the **props**, and passes it as the first argument each time it calls the component: `{ title: 'City Library Extends Its Hours', readTime: 3 }` for the first tag, a different object for each of the others; that is all props are: the component's only argument; the card shows nothing of them until its code reads them, so the fix reads `props.title` and `props.readTime` in the markup; then each card shows its own story; the values follow Lecture 4: quotes pass text, so `readTime="5"` arrives as the text "5", and `{readTime + 1}` shows 51, while `readTime={5}` shows 6; braces pass any value, an object too: `writer={{ name: 'Samantha Robinson', city: 'Denver' }}`; this is the way down that Lecture 5 promised: the parent writes the value on the child's tag.
    - Fix: `ArticleCard` returns `<h2>{props.title}</h2>` and `<p>{props.readTime} min read</p>`; three headlines.
    - Rule: we give each copy of a component its own values by writing them as attributes on its tag; React collects them into one object, the props, and passes it as the component's only argument.
    - Needs: parameter and argument (runway "A function's parameters receive the values of a call"); object and property (recall Lecture 3); quotes and braces (recall Lecture 4); the tree (recall Lecture 5).
    - Window plan: the file's first appearance, with two of the three tags so it stays short, as a chain: lines 1 to 4, `ArticleCard` with the log and its fixed `<h2>` (`startLine="1" continues="bottom"`); lines 5 to 11, `App` up to the first tag (`continues="both"`); lines 12 to 18, the second tag and the end (`continues="top"`); each tag takes one attribute per line (`code-blocks` Section 03). The fix shows `ArticleCard` as lines 1 to 9.
    - Diagram: the three tags and the three objects, side by side.

> [!PRINCIPLE] Principle 1: Props: the attributes on a component's tag arrive as one object, its only argument. A model with a Real Mistake, so a pair: right, `ContactCard(props)` returning `<p>{props.name}, {props.city}</p>` for `<ContactCard name="John Hall" city="Austin" />` (shows "John Hall, Austin"); wrong, the same tag with a card that returns fixed text (shows its own text, whatever the tag says); verified.

### Question 2: Two names in the parentheses crash the page

- [question-cycle] Question 2: Two names in the parentheses crash the page
    - Question: "How do I get `title` out of the props?"
    - Code and result: `function ArticleCard(title, readTime)` returns `<h2>{title}</h2>` and `<p>{readTime} min read</p>`; the page goes empty, and the Console panel shows "Objects are not valid as a React child (found: object with keys {title, readTime})" (verified in React 19.3.1 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: the plain JavaScript habit lists one parameter per value, as in the runway's `headline(title, readTime)`; but React passes one argument, the props object, so `title` holds the whole object and `readTime` is `undefined`; `{title}` then puts an object into the text, which Lecture 4 showed React cannot show; the fix is destructuring in the parameter list, `({ title, readTime })`: the braces unpack the properties by name, exactly as `const title = props.title` would; the names must match the attributes: `({ headline })` for `title=` gives `undefined`, and the heading stays empty with no error; react.dev marks the missing braces as a Pitfall.
    - Fix: `function ArticleCard({ title, readTime })`; each card shows its story.
    - Rule: we read props by naming them inside curly braces in the parameter list, `({ title, readTime })`, with the same names the tag uses.
    - Needs: destructuring (runway "Destructuring takes properties out of an object by name"); an object in the text (recall Lecture 4); the props object (Question 1).
    - Diagram: none; the two parameter lists side by side carry the picture.

> [!PRINCIPLE] Principle 2: Destructuring: the component names the props it reads, inside curly braces in its parameter list. Right: `function ContactCard({ name, city })` (shows "John Hall, Austin"); wrong: `function ContactCard(name, city)` (the page goes empty, "found: object with keys {name, city}"); verified.

### Question 3: A prop the tag leaves out leaves a hole

- [question-cycle] Question 3: A prop the tag leaves out leaves a hole
    - Question: "What if a parent leaves out a prop?"
    - Code and result: `<ArticleCard title="Rail Strike Ends" />`, with no `readTime`, and `ArticleCard({ title, readTime })`; the card shows " min read", with no warning; `ArticleCard.defaultProps = { readTime: 3 }`, copied from an older tutorial, changes nothing (verified in React 19.3.1 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: a prop the tag leaves out is `undefined`, and Lecture 4 showed that `undefined` shows nothing; React 19 no longer reads `defaultProps` on a function component, so older tutorials mislead here; the fix is a default value in the destructuring, `readTime = 3`; it fills the prop when the tag leaves it out or passes `undefined`; four cards make the boundary visible: missing, `undefined`, `null`, and `0` show 3, 3, nothing, and 0, because `null` and `0` are values the parent chose; the older habit, `readTime || 3`, would turn a real 0 into 3; `readTime ?? 3` keeps 0 and fills `null`; a default fits when the component has a sensible fallback, and a prop with no fallback stays one the parent must pass.
    - Fix: `function ArticleCard({ title, readTime = 3 })`; "3 min read".
    - Rule: when a component has a sensible fallback, we write it beside the prop's name, `readTime = 3`, and we remember that it fills only a missing or `undefined` prop, never `null` or `0`.
    - Needs: a default value in destructuring (runway); `||` and `??` (runway "Two operators that fall back to a value"); `null` and `undefined` show nothing (recall Lecture 4).
    - Diagram: the four cards against what each shows, as a small table.

> [!PRINCIPLE] Principle 3: Default values: the component names a fallback for a prop the tag leaves out. Right: `function ContactCard({ name, phone = 'not listed' })` for `<ContactCard name="John Hall" />` (shows "John Hall, phone: not listed"); wrong: no default (shows "John Hall, phone: "); verified.

### Question 4: Changing a prop crashes in development and ships in production

- [question-cycle] Question 4: Changing a prop crashes in development and ships in production
    - Question: "Can the card change its own title, to show it in capitals?"
    - Code and result: `ArticleCard(props)` writes `props.title = props.title.toUpperCase()` and returns `<h2>{props.title}</h2>`; the page goes empty, and the Console panel shows "Cannot assign to read only property 'title' of object '#<Object>'"; in the production build, the same file shows the three headlines in capitals with no error (verified in React 19.3.1 and Chrome, in both builds).
    - Verdict: does not do what the reader wanted.
    - Answer: the props belong to the parent, which wrote them on the tag; in development, React freezes each props object, so the assignment throws a `TypeError`; the production build leaves the freeze out, so the line works there, and a mistake the dev server would have caught ships; the freeze covers only the top level: when `ArticleCard` writes `writer.name = writer.name.toUpperCase()` on an object prop, nothing stops it in either build, and `AuthorBox`, which shows the same `writer` object, turns to capitals too: one card's change reached a component that never asked for it; the fix makes a new variable, `const headline = title.toUpperCase()`, which shows the capitals and leaves the props as they were; reassigning a destructured name, `title = title.toUpperCase()`, changes only a local variable; when the value itself must change, the parent passes new props, or the component keeps it in state, which Lecture 14 teaches.
    - Fix: `const headline = title.toUpperCase();` and `<h2>{headline}</h2>`.
    - Rule: we never change a prop or an object inside one; to show a value differently, we make a new variable, `const headline = title.toUpperCase()`, and a value that must change comes from the parent.
    - Needs: `toUpperCase()`, the frozen object, `TypeError`, and the two builds (runway "Some objects cannot be changed"); destructuring (Question 2).
    - Diagram: the shared `writer` object with two arrows, from `ArticleCard` and from `AuthorBox`, both pointing at it.

> [!PRINCIPLE] Principle 4: Read-only props: the component reads its props and never changes them. Right: `const label = name.toUpperCase();` in `ContactCard({ name })` (shows "JOHN HALL"); wrong: `props.name = props.name.toUpperCase();` (the page goes empty, "Cannot assign to read only property 'name'"); verified.

- [grounding] Are props the same as HTML attributes? ◼ Friction target: the map's Merged row on familiar props. Tactile scene: `className` and `src` on an `<img>` look like `title` on an `ArticleCard`. Bold key terms: **built-in components**, **props**. Concrete operational resolution: on an HTML tag, React accepts the attributes HTML defines and sets them on the element; on our own component, any name works, because React only collects them into the props object and the component decides what each one means; a value can be any JavaScript value, a function too, which Lecture 13 uses for clicks. ◼ Educational objective: one `> [!WILD]` card after the principles, adding a fact the cycles did not state.
