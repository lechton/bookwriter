### A function runs only when something calls it

- [runway] Function call against function reference, `console.log`, and the Console panel, used by Questions 1, 2, and 4.

- [p] ◇ {the plain JavaScript pair} In plain JavaScript, a function's name can appear in two ways, and they do different things. With parentheses after it, the name is a **call**: the function runs now and gives back its result. Without parentheses, the name is a **reference**: it stands for the function itself, which has not run. ◼ Educational objective: the distinction the whole lesson stands on, from plain JavaScript the reader writes.

- [code] Plain JavaScript, a call and a reference:

```js title="Plain JavaScript: a call and a reference"
function sayHello() {
  console.log('sayHello runs'); // a line in the Console panel
  return 'Hello';
}
const text = sayHello(); // a call: it runs, text is 'Hello'
button.addEventListener('click', sayHello); // a reference: the browser calls it later
```

◼ **The what-this-introduces list:** 1. `console.log`: prints a message in the Console panel each time its line runs. 2. `sayHello()`: a call. 3. `sayHello` with no parentheses: a reference, handed to the browser.

- [p] ◇ {point into the code} `console.log('sayHello runs')` prints a message each time the line runs. The messages appear in the **Console panel**, next to the Elements panel in the browser's developer tools. `sayHello()` on the fifth line runs the function at once, so the Console panel shows "sayHello runs". On the last line, `addEventListener` gets `sayHello` with no parentheses: the function itself. Our code never calls it there. The browser calls it later, once for each click, and each click adds one more message. ◼ Educational objective: the Console panel as the place to see when a function runs; the reference handed to someone else who calls it, which is exactly what a tag does in Question 1.

### JavaScript names and HTML tags use different letters

- [runway] camelCase and PascalCase, used by Question 2 and Step 2.

- [p] ◇ {three ways of writing names} Plain JavaScript names functions and variables in **camelCase**: the first word starts with a small letter, and every later word with a capital, as in `sayHello` or `formatDate`. The bumps of capitals in the middle look like a camel's humps. **PascalCase** starts every word with a capital, the first one too, as in `ArticleCard`. The name comes from the Pascal programming language, which used it. HTML tags are written in small letters: `<article>`, `<footer>`, `<input>`. ◼ Educational objective: the three letter styles the reader must tell apart in Question 2, each with its everyday example; the term's origin in one clause.

### A return with nothing after it gives back undefined

- [runway] `undefined`, automatic semicolon insertion, and ESLint, used by Question 3 and Step 3.

- [p] ◇ {undefined} A function gives back what its `return` names. When `return` names nothing, the function gives back **`undefined`**, JavaScript's value for "no value here". ◼ Educational objective: the value Question 3's broken card returns.

- [code] Plain JavaScript, a return with nothing after it:

```js title="Plain JavaScript: return with nothing after it"
function getTitle() {
  return; // ends the function here
}
const title = getTitle(); // title is undefined
```

◼ **The what-this-introduces list:** 1. `return;`: a return that names no value. 2. `undefined`: what the call gives back.

- [p] ◇ {automatic semicolon insertion} JavaScript lets us leave out the semicolon at the end of a line, and `const city = 'Boston'` works with or without one. When a line could end a statement, JavaScript ends it there, as if we had typed the semicolon. This is called **automatic semicolon insertion**. Most of the time it does what we meant, and Question 3 shows the one place where it does not. ◼ Educational objective: name the behavior by its interview term on a line the reader already writes; its effect on `return` stays Question 3's to show.

- [p] ◇ {ESLint} Many code editors run a tool called **ESLint**. It reads the code as we type and underlines lines that are probably mistakes, each with a short message. It does not change the code and does not stop the page from running. ◼ Educational objective: the one tool that shows Question 3's mistake, named before the question needs it.

### A function defined inside another one is new on every call

- [runway] Nested function and the top level of a file, used by Question 4 and Step 4.

- [p] ◇ {two places for a function} A function written directly in the file, outside every other function, is at the **top level** of the file. JavaScript runs that line once, when the file loads, so the name stands for one function for as long as the page is open. A function can also be written inside another function. It is then a **nested function**, and its line runs each time the outer function runs. ◼ Educational objective: both terms, from where the line sits and when it runs.

- [code] Plain JavaScript, a nested function made twice:

```js title="Plain JavaScript: a nested function, made on every call"
function makeGreeter() {
  function greet() { // runs each time makeGreeter runs
    return 'Hello';
  }
  return greet;
}
makeGreeter() === makeGreeter(); // false: two different functions
```

◼ **The what-this-introduces list:** 1. `function greet()` inside `makeGreeter`: a nested function. 2. `===`: true only for the very same function.

- [p] ◇ {point into the code} Each call of `makeGreeter` runs the line `function greet()` again and makes a new function. The two `greet` functions do the same work, but they are two different functions, so `===` gives `false` (checked in Node 26). A function at the top level is made once, and its name gives the same function every time. ◼ Educational objective: the physical fact Question 4 stands on, shown in plain JavaScript before React enters.

### Principles of React: A Component Is a Function React Calls

- [preview] Everything in this lesson comes down to one idea: a component is a function that React calls, never our code. First, rendering, which means React calls the component wherever a tag names it: we write the component's name as a tag in another component's markup, and React runs the function and puts what it returns on the page. Second, PascalCase, which means React calls only the tags that start with a capital letter: a tag that starts with a small letter is read as an HTML tag, so our function never runs. Third, automatic semicolon insertion, which means React calls the function and gets back only what starts on the return line: markup that starts on the next line is never returned, so we open the parentheses on the return line. Fourth, top-level components, which means React calls the same function on every run: we define each component at the top level of the file, because a component defined inside another one is a new function every time, and React rebuilds everything it shows. ◼ Educational objective: the map's Spoken Preview, word for word, read aloud before Question 1 (`lecture-structure` Section 12C, `lecture-voice` Section 16B).


> [!PRINCIPLE]
> **Principle 1: Rendering: React calls the component wherever a tag names it**
> *We use a component by writing its name as a tag in another component's markup, and React calls the function once for each tag; our code never calls it.*
>
> A component is a function, and a function runs only when something calls it. The tag hands React the function itself. While React runs the component that holds the tag, it calls the function once for each tag and builds the DOM from what each call returns. A function that no tag names never runs. The DOM holds only the HTML tags the function returns, never a tag with the component's name.
>
> *We should do this:*
> `function Greeting() {`
> `  return <p>Hello, John Hall</p>;`
> `}`
> `function Page() {`
> `  return <Greeting />; // React calls Greeting`
> `}`

    - Fix: `function ArticleCard()` and `<ArticleCard />`, both with a capital first letter.

> [!PRINCIPLE]
> **Principle 2: PascalCase: React calls only the tags that start with a capital letter**
> *We start a component's name with a capital letter, in the function and in the tag, because a tag with a small first letter is read as an HTML tag and our function never runs.*
>
> React decides what a tag is by its first letter. A capital letter hands React our function, and React calls it. A small letter means an HTML tag, so the browser makes an element with that name. An unknown name gives an empty element, and our function never runs. Renaming the tag without the function leaves the name undefined, and the whole page fails.
>
> *We should do this:*
> `function ProfileCard() {`
> `  return <p>John Hall</p>;`
> `}`
> `<ProfileCard /> {/* React calls ProfileCard */}`
>
> *We should not do this:*
> `function profileCard() {`
> `  return <p>John Hall</p>;`
> `}`
> `<profileCard /> {/* an empty HTML tag; the function never runs */}`

### Question 3: A return alone on its line gives back nothing

- [question-cycle] Question 3: A return alone on its line gives back nothing
    - Question: "My markup is long. Can I start it on the line after `return`?"
    - Code and result: `ArticleCard` with `return` alone on its line and the `<article>` on the lines below it, ending in `</article>;`; `App` names `<ArticleCard />`; the page shows an empty `<main>`; the Console panel shows no error, and the dev server prints no warning, also in `vite build`; an editor that runs ESLint underlines the `<article>` line with "Unreachable code" (verified in React 19.3.1, Vite 8.3.4, Chrome, and ESLint 10.12.0).
    - Verdict: does not do what the reader wanted.
    - Answer: `return` alone on its line can end a statement, so automatic semicolon insertion ends it there, as if we had typed `return;`; the function gives back `undefined`, as `getTitle` did in the runway; the markup below is never reached; React called `ArticleCard` and got nothing back, so it shows nothing in the card's place; nothing is wrong in JavaScript's eyes, so no error appears anywhere, and only ESLint marks the lines below `return` as code that can never run; the fix is to open a parenthesis on the `return` line, `return (`, so the line cannot end there; markup that fits on the `return` line needs no parentheses.
    - Fix: `return (` on the `return` line, the markup inside, `);` after it.
    - Rule: when the markup does not fit on the return line, we open the parentheses on the return line, because a return alone on its line gives back nothing. Boundary: `return <footer>Town News, 2026</footer>;` fits on one line and needs no parentheses (Step 3).
    - Needs: `undefined`, automatic semicolon insertion, ESLint (runway "A return with nothing after it gives back undefined"); React calls `ArticleCard` and builds from what it returns (Question 1).
    - Diagram: none; the two versions of the `return` side by side carry the picture.

> [!PRINCIPLE]
> **Principle 3: Automatic semicolon insertion: React calls the function and gets back only what starts on the return line**
> *When the markup does not fit on the return line, we open the parentheses on the return line, because a return alone on its line gives back nothing.*
>
> JavaScript ends a return that stands alone on its line, as if a semicolon followed it. The function gives back undefined, and the markup below it never runs. React gets nothing, so it shows nothing, and no error appears. A parenthesis opened on the return line keeps the statement going until the markup is closed.
>
> *We should do this:*
> `function Greeting() {`
> `  return (`
> `    <section>`
> `      <h2>Hello, John Hall</h2>`
> `    </section>`
> `  );`
> `}`
>
> *We should not do this:*
> `function Greeting() {`
> `  return // gives back undefined`
> `    <section>`
> `      <h2>Hello, John Hall</h2>`
> `    </section>;`
> `}`

### Question 4: A card defined inside App loses the typed comment on every save

- [question-cycle] Question 4: A card defined inside App loses the typed comment on every save
    - Question: "`ArticleCard` is used only inside `App`. Can I define it inside `App`?"
    - Code and result: `ArticleCard` written inside `App`, returning an `<article>` with the title and a comment box, `<input placeholder="Write a comment" />`; `App` returns `<main>` with `<ArticleCard />`; the first run looks right; "Great news" is typed into the box, the title is changed to "New Park Opens on Saturday", and `App.jsx` is saved; the new title shows, the box is empty, and the cursor is gone (verified in React 19.3.1, Vite 8.3.4, and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: the save makes React call `App` again, as in Lecture 1; that run reaches the line `function ArticleCard()` and makes a new function, as `makeGreeter` did in the runway; React compares the new description with the last one and finds a different function in the card's place; to React, a different function is a different component, so it removes the old `<article>` with its `<input>` and builds new nodes; the new box was never typed into, and the focus had nowhere to stay; with `ArticleCard` moved to the top level, the same save keeps "Great news" and the cursor, and React changes only the title text; on a save, the dev server matches each top-level component of the file to its old version by name, and a nested one has no such match; Lecture 14 shows `App` running again while the page is open, when its data changes, and the nested card would empty there too; Lecture 24 explains how React matches components; a card that needs data from `App` gets it through props, which Lecture 6 teaches, not by living inside `App` (one sentence of preview each; message `02-24-02`).
    - Fix: `function ArticleCard()` beside `function App()`, at the top level of `App.jsx`.
    - Rule: we define every component at the top level of the file, beside the others, and never inside another component.
    - Needs: nested function and top level (runway "A function defined inside another one is new on every call"); the save, the comparison, and focus (recall Lecture 1); React calls each tag's function (Question 1).
    - Diagram: what React sees in the card's place on the save, nested against top level.

```ascii title="What React finds in the card's place on the save"
ArticleCard is   last run      this run      in the DOM
inside App       function #1   function #2   new <article>, empty box
at top level     ArticleCard   ArticleCard   same <input>, "Great news" kept
```

> [!PRINCIPLE]
> **Principle 4: Top-level components: React calls the same function on every run**
> *We define every component at the top level of the file, beside the others, and never inside another component.*
>
> React compares the new description with the last one, and it knows a component by its function. A component defined inside another one is made again on each run of the outer component, so React finds a different function in the same place. It removes the old elements and builds new ones, and a text box loses what the user typed and the focus. A component at the top level is made once, so React finds the same function and keeps its elements.
>
> *We should do this:*
> `function SearchBox() {`
> `  return <input placeholder="Search" />;`
> `}`
> `function Profile() {`
> `  return <SearchBox />; // the same SearchBox on every run`
> `}`
>
> *We should not do this:*
> `function Profile() {`
> `  function SearchBox() { // a new SearchBox on every run`
> `    return <input placeholder="Search" />;`
> `  }`
> `  return <SearchBox />;`
> `}`

### Step 2: Next, we name our footer with a capital letter <App.jsx>

- [p] ★ This step applies the second principle, PascalCase, which means React calls only the tags that start with a capital letter. Decision: the page needs a footer, and the best name for our component is the same word as the HTML tag it returns. The capital letter alone keeps them apart: `function Footer()` returns `<footer>`, and `App` names `<Footer />`. Result: "Footer runs" appears after the other three, and the Elements panel shows one `<footer>` with "Town News, 2026". Had `App` written `<footer />`, the browser would have made an empty HTML footer, our function would never have run, and React would have printed no error at all, because `<footer>` is a real HTML tag (verified in React 19.3.1 and Chrome). ◼ Meaningful pedagogical commentary: the decision a junior hesitates on (a component named like an HTML tag), the visible result, and the quieter form of Question 2's mistake (Principle 2).

- [code] `Footer` with its one-line return, written above `App` on lines 15 to 18 (`startLine="15"`); then `App`'s `<main>`, which moved down to lines 22 to 26, with `<Footer />` after `<ArticleCard />` (`startLine="22"`).

### Step 3: Then, we open the parentheses on the return line as the footer grows <App.jsx>

- [p] ★ This step applies the third principle, automatic semicolon insertion, which means React calls the function and gets back only what starts on the return line. Decision: the newsroom wants a contact link in the footer; the markup no longer fits on the `return` line, so it moves inside `return (`, opened on that line. Result: the footer shows "Town News, 2026" and the link "Contact the newsroom". Had the `<footer>` started on the line after a bare `return`, the footer would have vanished with no error, as in Question 3. ◼ Meaningful pedagogical commentary: the boundary of the rule (one line needs no parentheses, two lines need them), applied at the moment the markup grows (Principle 3).

- [code] `Footer` with `return (` and the two-line footer, lines 15 to 23 (`startLine="15"`).

### Step 4: Finally, we keep every component at the top level while the reader types <App.jsx>

- [p] ★ This step applies the fourth principle, top-level components, which means React calls the same function on every run, and it tests everything above. Decision: `CommentBox` is used only inside `ArticleCard`, which tempts us to write it there, but it stays at the top level beside the other three. Test: type "Great news" into the comment box and leave the cursor in it, change the title to "New Park Opens on Saturday", and save. Prediction: React calls the components again and finds the same `ArticleCard` and the same `CommentBox` functions in their places, so it changes the title text and keeps every other node. Result: the box still holds "Great news", and the cursor still blinks in it (verified in React 19.3.1, Vite 8.3.4, and Chrome). With `CommentBox` written inside `ArticleCard`, the same save empties the box and the cursor is gone (verified). ◼ Meaningful pedagogical commentary: the temptation, the test with the user's own text, the prediction the reader can now make alone, and the contrast with the nested version (Principle 4).

### Component Summary

- [component-code] Summary: The Logic of Nested Components: `main.jsx` names `<App />`; `App.jsx` holds four top-level components: `App` names `<ArticleCard />` and `<Footer />`, `ArticleCard` names `<CommentBox />`; React called them in the order of their tags; the save changed one text and kept the typed comment.

- [p] ★ A developer who comes from plain JavaScript expects to call each function where its markup should go, to name it like any other function, to start long markup on a fresh line, and to keep a helper inside the only function that uses it. Each habit breaks a component in a different way: a call hides the component from React, a small letter turns it into an empty HTML tag, a bare `return` gives back nothing, and a nested definition empties the comment box on every run. In React 19, the four steps avoided all four, and the page kept what the reader typed. ◼ Meaningful pedagogical commentary: the naive expectation against React 19's behavior, with the four principles in thread order.

### Where you will meet this

- [p] 1. **A list of cards**: a news site, a shop, or a feed writes one card component and names its tag once for each item. Lecture 6 shows how each card gets its own text.
- [p] 2. **Names that match HTML tags**: most apps have a `Header`, a `Footer`, a `Button`, or a `Form` component. The capital letter is the only thing that tells React to call ours instead of making the HTML tag.
- [p] 3. **A card that vanished after a reformat**: a teammate moves the markup to the line after `return` to make it easier to read, and the card is gone with no error. ESLint's "Unreachable code" points at the line.
- [p] 4. **A chat box that keeps emptying**: a message input defined inside the chat window component loses the half-typed message every time the window runs again. Moving it to the top level fixes it.
