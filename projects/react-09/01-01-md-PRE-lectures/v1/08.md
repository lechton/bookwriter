### A path names a file from where you stand

- [runway] Relative path (`./` and `../`) and package import, used by Question 4 and Step 4.

- [p] ◇ {relative paths} A file names another file by a **relative path**, a route that starts from its own folder. `./` means "this folder", so from `App.jsx`, `./components/ArticleCard.jsx` means the `components` folder beside it, then the card's file. `../` means "the folder above". Two files in different folders reach the same file by different paths. ◼ Educational objective: the rule Question 4's mistake breaks, taught before any import.

- [code] Two files, two routes to the same file:

```ascii title="Paths to src/components/Badge.jsx"
from src/App.jsx                    ./components/Badge.jsx
from src/components/ArticleCard.jsx ./Badge.jsx
```

◼ **The what-this-introduces list:** 1. `./`: the folder of the file that holds the path.

- [p] ◇ {package names} A name with no dot, such as `'react'`, is not a path at all: it names a **package**, code installed in the project, and the build finds it there. ◼ Educational objective: why `import { Fragment } from 'react'` has no `./` (map 03's deferred row).

### Principles of React: Each File Is a Module

- [preview] Everything in this lesson comes down to one idea: each file is a module, and its names cross to another file only by export and import. First, modules, which means each file keeps its names to itself until it exports them: a moved component is gone from the old file until the new file exports it and the old one imports it. Second, imports match exports, which means braces for a named export, none for the default: the wrong form stops the page before anything runs. Third, default and named exports, which means one default for the file's main component, named exports for the rest: a file has one default at most. Fourth, import paths, which means a path starts from the file that imports: a file in the components folder reaches its neighbor with a dot and a slash. ◼ Educational objective: the map's Spoken Preview, word for word, read aloud before Question 1.

### Question 1: A moved component is not defined in the old file

- [question-cycle] Question 1: A moved component is not defined in the old file
    - Question: "I moved `ArticleCard` into its own file. Why does `App` say it is not defined?"
    - Code and result: `function ArticleCard({ title })` cut from `App.jsx` and pasted into `components/ArticleCard.jsx`, with no `export`; `App` still returns `<ArticleCard title="Rail Strike Ends" />`; the page goes empty, and the Console panel shows "ArticleCard is not defined" (verified in React 19.3.1, Vite 8.3.4, and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: scripts on one HTML page share their names, but each file of a React project is a **module**: a file with its own scope, like the function scope of Lecture 5; `ArticleCard` now exists only inside `ArticleCard.jsx`, so `App.jsx` meets a name that does not exist there, the same `ReferenceError` as Lecture 5's `edition`; `export` in front of the function opens that one name to other files, and an `import` line at the top of `App.jsx` brings it in; both are needed: an import of a file that exports nothing stops the page with "The requested module '/src/components/ArticleCard.jsx' does not provide an export named 'default'"; a function only its own file uses, such as a `formatTitle` helper, stays unexported, and `App.jsx` cannot reach it; a module's top level runs once, however many files import it: a log at the top of a file prints once, while a log inside its component prints on every render; a new file with JSX needs the `.jsx` name, or Vite stops with "Unexpected JSX expression".
    - Fix: `export default function ArticleCard({ title })` in `components/ArticleCard.jsx`, and `import ArticleCard from './components/ArticleCard.jsx';` at the top of `App.jsx`.
    - Rule: we treat each file as a module: a component moved to its own file is exported there with `export`, and imported with `import` by every file that uses it; a function only its file uses stays unexported.
    - Needs: `ReferenceError` and scope (recall Lecture 5); the folders (runway "A project is a folder of files"); `export default` (recall Lecture 1).
    - Window plan: two files, two tabs: `ArticleCard.jsx` lines 1 to 3, and `App.jsx` lines 1 to 3; the fix shows line 1 of each, with the `import` line new at the top of `App.jsx`.
    - Diagram: two files with a wall between them, and the one name that crosses it.

> [!PRINCIPLE] Principle 1: Modules: each file keeps its names to itself until it exports them. A model with a Real Mistake, so a pair: right, `export default function ContactCard({ name })` in `ContactCard.jsx` and `import ContactCard from './components/ContactCard.jsx';` in `App.jsx` (shows "John Hall"); wrong, the same function with no `export` and no `import` ("ContactCard is not defined"); verified.

### Question 2: The braces of an import must match the export

- [question-cycle] Question 2: The braces of an import must match the export
    - Question: "Do I write braces around the name or not?"
    - Code and result: `components/ArticleCard.jsx` with `export function ArticleCard`; `App.jsx` with `import ArticleCard from './components/ArticleCard.jsx';`; the page stays empty, and the console shows "The requested module '/src/components/ArticleCard.jsx' does not provide an export named 'default'"; `npm run build` stops with `[MISSING_EXPORT] "default" is not exported by "src/components/ArticleCard.jsx"` (verified in Vite 8.3.4 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: a file has two kinds of export; `export default` marks its **default export**, and `export function` marks a **named export**; an import without braces asks for the default, and an import with braces asks for an export with that exact name; the browser links the files before any code runs, so a mismatch stops the page before React starts; the mirror mistake, `import { ArticleCard }` for a default export, fails with "does not provide an export named 'ArticleCard'", and a misspelled `{ Articlecard }` fails with its own spelling; a default import can take any name, so `import StoryBox from` still gets the card, while a named import must spell the name exactly; these braces list names, they are not the braces of Lecture 4; older tools let the mismatch through as `undefined`, which React reports as "Element type is invalid ... got: undefined. You likely forgot to export your component ... or you might have mixed up default and named imports", the message many tutorials show; under Vite it appears only through `import * as`.
    - Fix: `import { ArticleCard } from './components/ArticleCard.jsx';`.
    - Rule: we write each import in the form of its export: no braces for a default export, under any name we choose, and braces with the exact name for a named export.
    - Needs: modules, `export`, and `import` (Question 1); the two builds (recall Lecture 6).
    - Diagram: the two-row table of react.dev: the export statement and the import that matches it.

> [!PRINCIPLE] Principle 2: Imports match exports: braces for a named export, none for the default. Right: `export function ContactCard` with `import { ContactCard } from './components/ContactCard.jsx';` (shows "John Hall"); wrong: the same export with `import ContactCard from ...` ("does not provide an export named 'default'"); verified.

### Question 3: A file has one default export

- [question-cycle] Question 3: A file has one default export
    - Question: "Should the badges be default or named exports?"
    - Code and result: `components/ArticleCard.jsx` with `export default function ArticleCard` and, below it, `export default function Badge`; the page stays empty, and the overlay shows "[PARSE_ERROR] A module cannot have multiple default exports." (verified in Vite 8.3.4 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: every file so far ended with `export default`, so it feels like the only way; but a module has one default slot, so a second default stops the build; named exports have no limit; react.dev's convention: a file with one main component exports it as the default, and a file with several components exports each by name; the card keeps its default, the badge becomes `export function Badge`, and `App.jsx` imports both in one line, `import ArticleCard, { Badge } from './components/ArticleCard.jsx'`; some teams keep one style everywhere to avoid mixing, and both work; whichever the style, the exported function keeps a name: `export default ({ title }) => ...` gets the name "default", which is what an error message would then show.
    - Fix: `export function Badge`, and `import ArticleCard, { Badge } from './components/ArticleCard.jsx';`.
    - Rule: we give a file at most one default export, for its main component, and we export its other components with names; a file of several small components uses named exports only, and every exported function keeps a name.
    - Needs: default and named exports (Question 2).
    - Diagram: none; the file with its two exports and the one import line carry the picture.

> [!PRINCIPLE] Principle 3: Default and named exports: one default for the file's main component, named exports for the rest. Right: `export default function ContactCard` and `export function PhoneLine` in one file, imported as `import ContactCard, { PhoneLine } from ...` (shows the name and "555-0100"); wrong: two `export default` lines (the build stops); verified.

### Question 4: A path copied from App.jsx breaks inside components

- [question-cycle] Question 4: A path copied from App.jsx breaks inside components
    - Question: "I moved the feed into `components`. Why can't it find the card?"
    - Code and result: `components/ArticleCard.jsx` imports its badge with `import { Badge } from './components/Badge.jsx';`, the line that works in `App.jsx`; the page stays empty, and the overlay shows "Failed to resolve import "./components/Badge.jsx" from "src/components/ArticleCard.jsx". Does the file exist?" (verified in Vite 8.3.4 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: as the runway showed, a path starts from the folder of the file that holds it; from `App.jsx`, `./components/Badge.jsx` is right; from inside `components`, the same text means `src/components/components/Badge.jsx`, a folder that does not exist; the overlay names both the path and the file that holds it, which is the clue; the badge sits beside the card, so the path is `./Badge.jsx`; the `.jsx` ending may be left out, as many projects do; a package such as `'react'` has no dot at all.
    - Fix: `import { Badge } from './Badge.jsx';`.
    - Rule: we write each import path from the folder of the file that imports: `./` for a file beside it, `../` for the folder above, and no dot at all for a package such as `'react'`.
    - Needs: relative path and package import (runway "A path names a file from where you stand"); the overlay (recall Lecture 3).
    - Diagram: the folder tree with the two routes to `Badge.jsx`.

> [!PRINCIPLE] Principle 4: Import paths: a path starts from the file that imports. Right: `import { PhoneLine } from './PhoneLine.jsx';` inside `components/ContactCard.jsx` (shows "555-0100"); wrong: `'./components/PhoneLine.jsx'` there ("Failed to resolve import"); verified.

- [grounding] What is the tree of files? ◼ Friction target: the map's Supporting row on the module dependency tree. Tactile scene: Lecture 5 drew the render tree; now the files import each other. Bold key terms: **module dependency tree**, **bundler**. Concrete operational resolution: the imports form a second tree, starting from `main.jsx`; the build tool follows it to decide which files the site needs and packs them together; the two trees differ: `EditorialFeed` imports `CardContainer`, but the stories inside the frame are written by the feed, not imported by the frame. ◼ Educational objective: one `> [!WILD]` card after the principles, adding a fact the cycles did not state.

### Let's Design a Practical Example

- [p] ★ {framing, before the canvas} Each question moved one component. The page must look the same after every step, so each step ends on a page that still works, or on the message that says why not. Keep the dev server running and the Console panel open. ◼ Educational objective: what we build, why it is bigger, what each step proves, and what to keep open (`lecture-structure` Section 15).

### Step 1: First, we move the frame into its own file <CardContainer.jsx>

- [p] ★ Modules. Decision: `CardContainer` is used by every story and has one job, so it moves to `components/CardContainer.jsx`, exported as the file's default; `App.jsx` imports it on its first line. Prediction: what if the `import` line were missing? ("CardContainer is not defined", as in Question 1). Result: the page looks exactly as before (verified). ◼ Meaningful pedagogical commentary: the page does not change; only the place of the code does.

- [code] two windows: `CardContainer.jsx`, lines 1 to 8, the whole new file (`title="CardContainer.jsx"`, `startLine="1"`); `App.jsx`, line 1, the new import (`startLine="1"`).

### Step 2: Next, we import the first badge by its name <App.jsx>

- [p] ★ Imports match exports. Decision: the rail strike story gets a "Live" badge; `components/Badges.jsx` exports `LiveBadge` by name, so `App.jsx` imports it with braces, `import { LiveBadge } from './components/Badges.jsx';`. Prediction: without the braces? (verified: "does not provide an export named 'default'"). Result: "Live" appears in the second card (verified). ◼ Meaningful pedagogical commentary: the form of the import is read off the export, never guessed.

- [code] three windows: `Badges.jsx`, lines 1 to 3, the new file (`startLine="1"`); `App.jsx`, line 2, the named import (`startLine="2"`); `App.jsx`, line 10, `<LiveBadge />` in the rail strike card (`startLine="10"`).

### Step 3: Then, we give the badges file two named exports <Badges.jsx>

- [p] ★ Default and named exports. Decision: the library story gets a "New" badge; `NewBadge` is as small as `LiveBadge` and neither is the file's main component, so both stay named exports, and one import line brings both, `{ LiveBadge, NewBadge }`. Result: "New" appears in the first card (verified). ◼ Meaningful pedagogical commentary: a file of equals has no default.

- [code] three windows: `Badges.jsx`, lines 4 to 6, the new `NewBadge` (`startLine="4"`); `App.jsx`, line 2, the import with both names (`startLine="2"`); `App.jsx`, line 7, `<NewBadge />` in the library card (`startLine="7"`).

### Step 4: Finally, we move the feed and fix its paths <EditorialFeed.jsx>

- [p] ★ Import paths. Decision: `EditorialFeed` moves to `components/EditorialFeed.jsx` as that file's default export, and it takes its two imports with it; from inside `components`, the frame and the badges are neighbors, so the paths become `./CardContainer.jsx` and `./Badges.jsx`; `App.jsx` keeps one import, `./components/EditorialFeed.jsx`. Prediction: what if the two import lines were copied from `App.jsx` unchanged? (verified: "Failed to resolve import "./components/CardContainer.jsx" from "src/components/EditorialFeed.jsx""). Result: the page looks exactly as at the start, and `App.jsx` is four lines long (verified). ◼ Meaningful pedagogical commentary: the same file, reached by two different paths from two different folders.

- [code] two windows: `EditorialFeed.jsx`, lines 1 to 3, its two imports and its default export (`startLine="1"`); `App.jsx`, lines 1 to 4, the whole file (`startLine="1"`).

### Component Summary

- [component-code] Summary: Project Architecture & File Hierarchy: `App.jsx` (imports the feed and returns it); `components/EditorialFeed.jsx` (default export; imports the frame and both badges from its own folder); `components/CardContainer.jsx` (default export, the frame); `components/Badges.jsx` (named exports `LiveBadge` and `NewBadge`); `main.jsx` was prepared, and no step changed it.
