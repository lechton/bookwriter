### How do we keep a form's values in state?

- [p] ◇ {theme, where the reader stands} Lecture 14 kept a count of likes and a saved flag, two separate values, each with its own `useState`. A form is different. An article form edits a title, a summary, and the author's bio, and these values belong together: they arrive together when the article loads, and they leave together when it is saved. So every React developer meets the same question: when a form edits several values that belong together, how do we keep them in state, and how do we change one of them? ◼ Educational objective: the theme from the map's `## Theme and Options`, on a form every reader has filled in.

- [p] ◇ {option 1: one state variable per value} The first answer you know from Lecture 14: one `useState` for each value. ◼ Educational objective: say what the first code is for before it appears.

- [code] One state variable per value:

```jsx title="One state variable per value"
const [title, setTitle] = useState('New Park Opens Today');
const [summary, setSummary] = useState('The city opens a park by the river.');
```

◼ **The what-this-introduces list:** 1. Two separate values, each with its own setter.

The author's name and bio would need two more lines like these. This is **one state variable per value**: our code keeps each value apart, and React stores each one under its own `useState`. - [p] ◇ {option 2: one object in state} The second answer keeps the whole article in one `useState`, as one object. ◼ Educational objective: the chapter's option, introduced by its purpose before its code.

- [code] One object in state:

```jsx title="One object in state"

  title: 'New Park Opens Today',

```

◼ **The what-this-introduces list:** 1. `article`: one object with three properties, one of which, `author`, is an object too. 2. `setArticle`: one setter for the whole article.

There is one setter, `setArticle`, and it takes a whole article. This is **one object in state**: React stores one object, and our code reads its properties. It fits values that belong together, that arrive together as one object, or that are sent together, such as the fields of a form. Its cost is the subject of this chapter: to change one property, we must hand the setter a whole article. ◼ Educational objective: the term with its code, who acts, where it fits, and the cost that the lesson answers.

### A variable holds a reference to an object

- [runway] Object reference and `Object.is`, in plain JavaScript first, used by Question 1 and Step 1.

- [p] ◇ {a reference, named with code} When we write an object literal, JavaScript creates the object once, somewhere in the computer's memory, and the variable holds a way to reach it: a **reference**, the object's address. A second variable can hold the same address. Then there are two names, but only one object. ◼ Educational objective: the term the map marks `New` with refresher `yes`, from the code the reader knows.

- [code] Two names, one object:

```js title="Two names, one object"
const first = { title: 'New Park Opens Today' };
const second = first; // copies the address, not the object
second.title = 'Park Opens';
console.log(first.title); // Park Opens
```

◼ **The what-this-introduces list:** 1. `const second = first`: a second name for the same object. 2. The change through one name, seen through the other (verified in Node).

- [p] ◇ {the second example: Object.is} JavaScript has a check for exactly this: **`Object.is(a, b)`** is true when `a` and `b` are the same object, and false when they are two objects, even with the same contents. For numbers and strings it compares the values, so `Object.is(5, 5)` is true. ◼ Educational objective: the second term with a second, different snippet; who does what (JavaScript compares addresses).

- [code] Same contents, two objects:

```js title="Object.is compares the address"
const a = { title: 'Park Opens' };
const b = { title: 'Park Opens' };
console.log(Object.is(a, b)); // false: two objects
a.title = 'Park Closed';
console.log(Object.is(a, a)); // true: still the same object
```

◼ **The what-this-introduces list:** 1. `Object.is(a, b)`: true only for the same object. 2. A changed object is still the same object (verified in Node).

- [p] ◇ {the rule} A number cannot be changed in place: `setCount(5)` puts a new number in the place of the old one, and the 0 is still 0. An object can be changed in place, and after the change it is still the same object, at the same address. `Object.is` asks only "is this the same object?", never "is anything inside it different?". ◼ Educational objective: the closing rule, which Question 1's answer recalls in a few words (map Merged rows: "What's a mutation?" and the reference model).

### Three dots copy an object, one level deep

- [runway] Object spread, the last-one-wins order, the shallow copy and the nested object, and the arrow function that returns an object, in plain JavaScript first, used by Questions 1 to 4 and every step.

- [p] ◇ {object spread, named with code} Lecture 7 used the three dots to spread props onto a tag. Inside an object literal they do the same with properties: `{ ...article }` creates a new object and copies every property of `article` into it. This is **object spread**. ◼ Educational objective: the form the map marks `New` with refresher `yes`, recalled from the dots of Lecture 7 (handout `07-18-02`).

- [code] The dots make a new object:

```js title="Object spread"
const article = { title: 'New Park Opens Today', summary: 'A new park.' };
const copy = { ...article };
console.log(copy.title); // New Park Opens Today
console.log(Object.is(copy, article)); // false: a new object
```

◼ **The what-this-introduces list:** 1. `{ ...article }`: a new object with the same properties.

- [p] ◇ {the second example: one property changed} A property written after the dots replaces the copied one, because in an object literal the property written last wins, just as the attribute written last won in Lecture 7. Written before the dots, the copied property replaces it. ◼ Educational objective: confirm the idea with a second snippet: the order decides which value stays.

- [code] The property written last wins:

```js title="The property written last wins"
const after = { ...article, title: 'Park Opens' };
console.log(after.title); // Park Opens
console.log(after.summary); // A new park.
const before = { title: 'Park Opens', ...article };
console.log(before.title); // New Park Opens Today
```

◼ **The what-this-introduces list:** 1. The change after the dots: the new title. 2. The change before the dots: the old title wins (verified in Node).

- [p] ◇ {a shallow copy and a nested object, named with code} An object inside an object, such as the author inside the article, is a **nested object**. The outer object does not hold the author itself; its `author` property holds the author's address. So the dots copy that address, and the copy and the original share one author. A copy that copies only the first level is a **shallow copy**, and object spread always makes one. ◼ Educational objective: the two terms the map marks `New`, from the reference of the first runway section; the mechanism of Question 3.

- [code] The copy shares the author:

```js title="A shallow copy"
const withAuthor = { title: 'New Park Opens Today', author: { bio: 'Old' } };
const next = { ...withAuthor };
console.log(Object.is(next, withAuthor)); // false: a new article
console.log(Object.is(next.author, withAuthor.author)); // true: one author
next.author.bio = 'New';
console.log(withAuthor.author.bio); // New
```

◼ **The what-this-introduces list:** 1. `next.author` and `withAuthor.author`: one object reached from two articles (verified in Node).

- [diagram] Two articles, one author:

```ascii title="A shallow copy shares the objects inside"
withAuthor --> { title, author: --+ }
                                  |
                                  +--> { bio: 'New' }
                                  |
next ------> { title, author: ----+ }
```

- [p] ◇ {an arrow function that returns an object} An arrow function can return a new object too, but its object needs parentheses: `a => ({ ...a, title: 'Park Opens' })`. Without them, JavaScript reads the braces as the start of the function's body, and the file stops building: Vite shows "Unexpected token". This matters for the updater of Lecture 17 when the state is an object. ◼ Educational objective: the form the map marks `New` (map Supporting row on the updater with an object), with the build error verified in Vite 8.3.4.

- [p] ◇ {the rule} The three dots build a new object with the old properties, the property written after them wins, and anything the old object points to, the copy points to as well. ◼ Educational objective: the closing rule of the section, which Questions 2 and 3 recall in a few words.

### Principles of React: Updating Objects in State

- [preview] Everything in this lesson comes down to one idea: a new object for every change, which means that we never change the object React holds, and we build a new one and hand it to the setter. First, reference equality, which means a new object, because the setter compares objects, not their contents: a title changed inside the old object leaves the same object, so React skips the render, and the change appears later, when something else renders. Second, object spread, which means a new object that copies the old one and changes one property: the three dots copy every property first, the property written after them wins, and a property we leave out is gone. Third, nested objects, which means a new object at every level down to the change: the three dots copy only one level, so the author inside the article needs its own copy, or the old article changes too. Fourth, computed property names, which means a new object whose changed property comes from the field's name: one handler reads the name of the field that changed and uses it, in square brackets, as the property to replace. ◼ Educational objective: the map's Spoken Preview, word for word, read aloud before Question 1.

> [!PRINCIPLE]
> **Principle 1: Reference equality: a new object, because the setter compares objects, not their contents**
> *We never change a property of the object in state; we build a new object and pass it to the setter, because the setter skips the render when it gets the same object back; an object we have just built, which nothing else holds yet, is ours to change before we pass it.*
>
> A variable that holds an object holds a reference to it, not a copy. So the state variable and the value React keeps reach one object. Changing a property changes that object, and both still reach it. When we pass it to the setter, the setter compares the current value and the new one with `Object.is`, which is true only for the same object. For an object we changed and passed back, it is true, so React does not run the component again, and the screen keeps the old text. The change shows up later, on the next run for any other reason. A new object is a different object, so the setter runs the component again, and the screen shows the change at once.
>
> >> Object.is : a check that is true only when both values are the same object, or for numbers and strings, the same value
>
> *We should do this:*
> `const [user, setUser] = useState({ name: 'John Hall' });`
> `setUser({ ...user, name: 'John Hill' }); // shows John Hill`
>
> *We should not do this:*
> `const [user, setUser] = useState({ name: 'John Hall' });`
> `user.name = 'John Hill'; // changes the object React holds`
> `setUser(user); // the same object: the screen keeps John Hall`

> *We build the new object with the three dots first and the change after them: the dots copy every property, the property written after them replaces the copied one, and the setter stores exactly the object it gets, so a property we leave out is gone.*

- [p] ★ {the closing paragraph} A developer who comes from plain JavaScript expects to change an article by assigning to its properties, `article.title = ...`, and expects a copy of the article to be a copy of everything inside it. ### Where you will meet this

- [p] 1. **Profile and settings forms**: a user object with an address or preferences inside it; each field builds a new object, copying every level down to the field it changes.
- [p] 2. **Unsaved-changes warnings**: when nothing is ever changed in place, `current !== original` tells at once whether the user has edited anything.
- [p] 3. **Undo and reset buttons**: keeping the first object and handing it back to the setter works only while no handler changes it, including through a shallow copy.
- [p] 4. **Data from a server**: an article or an order arrives as one nested object, and an edit replaces it with a new one instead of changing it.
- [p] 5. **Code review**: `obj.x = value; setObj(obj)`, a spread written after the change, and a shallow copy with an assignment inside it are the three patterns reviewers flag; the linter catches only the first.

### For the interview

- [interview] > **The Interview Question:** How do you update an object in state without mutating it?

- [interview] **1. The Hidden Signal** ◼ The interviewer wants to hear why React needs a new object, not only the spread syntax. A junior answer says "use the spread operator, because state is immutable". A strong answer says that the setter compares the old and new value with `Object.is`, that a changed object is still the same object, so React skips the render, and that the spread makes a shallow copy, so a nested change needs a copy at every level.

- [interview] **2. The Classic Trap** ◼ The classic trap is `user.name = 'John Hill'; setUser(user)`. Candidates say the setter call makes React render. It does not: the setter gets the same object back, `Object.is` is true, and the screen keeps the old name until something else renders. A second trap is `const next = { ...user }; next.address.city = 'Denver'`: the screen updates, so it looks right, but the address is shared, and the old user changes too.

- [interview] **3. What is Actually Going On** ◼ A variable holds a reference to the object, so the state and the variable reach one article. `article.title = 'Park Opens'` changes that article, and `setArticle(article)` hands it back; `Object.is` says it is the same object, so React does not run the component again. `{ ...article, title: 'Park Opens' }` is a new object: the dots copy every property, and the title written after them wins. The dots copy the author's reference, not the author, so a new bio needs `author: { ...article.author, bio }` as well.

- [interview] **4. Where It Gets Tricky** ◼ *What happens to the change made in place?* It is not lost: the next render for any other reason shows it, which is why the bug looks random. *Is changing an object ever fine?* Yes, a fresh object we have just built, before we pass it to the setter. *Does the order of the dots matter?* Yes: `{ title, ...article }` lets the copied old title win. *Should I deep-copy the whole object to be safe?* No: copying only the objects on the path is enough, and objects nobody changes may stay shared. *How do I write an updater that returns an object?* `setArticle(a => ({ ...a, title }))`, with parentheses around the object. *What about deep nesting?* Immer writes the copies for us; arrays in state follow the same rule, and Lecture 19 shows their recipes.

### Glossary

- [glossary] Object reference ◼ The address of an object in memory, which a variable holds instead of the object itself; two variables can hold the same reference and reach one object.
- [glossary] `Object.is` ◼ The check a setter uses to compare the old and new value: true only for the same object, or for numbers and strings, the same value.
- [glossary] Object spread ◼ The three dots inside an object literal, `{ ...obj }`, which create a new object and copy every property of `obj` into it; a property written after them replaces the copied one.
- [glossary] Shallow copy ◼ A copy that copies only the first level: the objects inside it are shared with the original, so a nested change needs a copy at every level.
- [glossary] Computed property name ◼ A property name in square brackets, `{ [key]: value }`, taken from the value inside the brackets, such as `e.target.name`.
- [glossary] Controlled input ◼ A field that shows the value held in state through `value` and reports each change through `onChange`; Lecture 20 explains it in full.

### Summary

- [review-title] **A new object for every change: we never change the object React holds; we build a new one and hand it to the setter**

- [review-subtitle] ❒ Reference equality: a new object, because the setter compares objects, not their contents
- [never-rule] ➔ NEVER assign to a property of the object in state and pass the same object to the setter; React skips the render, and the change appears later.
- [if-then-rule] ➔ IF the object is one we have just built, before the setter call THEN it is ours to fill line by line.

- [review-subtitle] ❒ Object spread: a new object that copies the old one and changes one property
- [always-rule] ➔ ALWAYS write the dots first and the change after them: `{ ...user, name }`.
- [never-rule] ➔ NEVER pass only the changed property; the setter does not merge, and every other property is gone.

- [review-subtitle] ❒ Nested objects: a new object at every level down to the change
- [if-then-rule] ➔ IF the change sits inside an inner object THEN copy every object on the path, from the top to the change.
- [if-then-rule] ➔ IF an inner object is off the path THEN let it stay shared; no deep copy is needed.

- [review-subtitle] ❒ Computed property names: a new object whose changed property comes from the field's name
- [if-then-rule] ➔ IF several fields change the same object the same way THEN give them one handler with `[e.target.name]`, and give each field the `name` of its property.
- [if-then-rule] ➔ IF a field sits inside an inner object, or changes the object differently THEN give it its own handler, with its copy at every level.

- [closing-line] A new object, a copy with one change, a copy at every level, and the field that names the change. ◼ Educational objective: the map's Closing Line, the last spoken sentence of the lesson. The four subtitles above are the four thread labels word for word, so the summary repeats the structure the preview announced (`lecture-structure` Section 13).

**DO THIS:** build a new object, with a copy at every level down to the change

```jsx right
function handleCity(e) {
  setUser({
    ...user,
    address: { ...user.address, city: e.target.value },
  });
}
```

**DO NOT DO THIS:** change the object in state, or a shallow copy of it

```jsx wrong
function handleCity(e) {
  const next = { ...user };
  next.address.city = e.target.value;
  setUser(next);
}
```

| | **ONE STATE VARIABLE PER VALUE**<br>(`useState('New Park Opens Today')`) | **ONE OBJECT IN STATE**<br>(`useState(firstArticle)`) |
| ---: | :--- | :--- |
| **What React stores** | One value per `useState` | One object with every value |
| **Changing one value** | Its own setter replaces it | A new object: the dots first,<br>the change after them |
| **A value inside a value** | Not possible: each value<br>stands alone | A copy at every level<br>down to the change |
| **Many fields** | One handler per field | One handler with `[e.target.name]` |
| **When it fits** | A few values that change<br>one at a time | Values that belong together,<br>arrive together, or leave together |
