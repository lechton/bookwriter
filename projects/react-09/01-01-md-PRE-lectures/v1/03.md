### An object keeps values under names

- [runway] Object and property, used by Questions 1 and 5 and Steps 1 and 5.

- [p] ◇ {object and property} A JavaScript **object** keeps several values together, each under a name. Each name with its value is a **property**. We write an object with curly braces, and we read a property with a dot. ◼ Educational objective: the shape every tag becomes in Question 1, and the reason attribute names change in Question 5.

- [code] Plain JavaScript, an object with two properties:

```js title="Plain JavaScript: an object and its properties"
const story = {
  title: 'Rail strike ends', // a property named title
  section: 'City',
};
console.log(story.title); // Rail strike ends
```

◼ **The what-this-introduces list:** 1. `{ ... }`: an object. 2. `title: 'Rail strike ends'`: a property, a name and its value. 3. `story.title`: reading a property.

- [p] ◇ {point into the code} The object holds two properties, `title` and `section`. `story.title` reads the first one, so the Console panel shows "Rail strike ends". A property name is a JavaScript name, so it follows the same rules as the name of a variable. ◼ Educational objective: the property name as a JavaScript name, which Question 5 depends on.

### The dev server changes our files before the browser gets them

- [runway] Build, the Sources panel, and the Vite error overlay, used by Questions 1, 2, and 3 and every step.

- [p] ◇ {the build} The browser does not read `App.jsx` as we wrote it. When the page asks for the file, the dev server reads it, rewrites it into plain JavaScript, and sends the result. This rewriting is called the **build**. `npm run build` does the same for every file at once, when the site is ready to publish. ◼ Educational objective: the term the whole lesson rests on, from the dev server the reader already runs.

- [p] ◇ {the Sources panel} The **Sources panel** of the browser's developer tools, next to the Elements panel and the Console panel, shows each file the browser received. Opening `App.jsx` there shows the build's result, not our file. ◼ Educational objective: the place where Question 1 shows the calls.

- [p] ◇ {the overlay} When the build cannot read a file, nothing in that file runs. Vite then covers the page with a dark box, the **error overlay**, which shows the message, the file, and the line where the build stopped. The overlay goes away once we fix the file and save. ◼ Educational objective: the screen Questions 2 and 3 and Steps 1 to 3 end on, named before the first one appears.

### HTML lets some tags stay open

- [runway] Void element, used by Question 2 and Step 2.

- [p] ◇ {void elements} Some HTML tags can never hold anything inside them: `<img>`, `<br>`, and `<input>`. They are called **void elements**, and HTML lets us write them without a closing tag. HTML even lets us leave some other tags open, such as `<li>` and `<p>`, because the browser closes them when the next one starts. ◼ Educational objective: the habit pasted HTML brings, named with the elements the reader writes.

### CSS can style only the direct children of an element

- [runway] CSS child selector and flex layout, used by Question 4 and Step 4.

- [p] ◇ {the project's stylesheet} A new Vite project has a stylesheet, `index.css`, and `main.jsx` loads it with one line, so its rules apply to the whole page. ◼ Educational objective: where the CSS of Question 4 lives.

- [code] `index.css`, the stories list:

```css title="index.css"
.stories {
  display: flex; /* the items sit in a row */
  gap: 24px;
  padding: 0;
  list-style: none;
}
.stories > li { /* only the direct children */
  border: 1px solid #999;
  padding: 8px;
}
```

◼ **The what-this-introduces list:** 1. `display: flex`: puts the children of the element in a row. 2. `.stories > li`: the child selector, which matches only an `<li>` placed directly inside `.stories`.

- [p] ◇ {point into the code} `display: flex` turns the list into a **flex layout**: its children sit side by side in a row, with 24 pixels between them. The `>` in `.stories > li` makes it a **child selector**. It gives a border only to an `<li>` that sits directly inside the list, not to one that sits deeper. ◼ Educational objective: both CSS facts Question 4's broken layout depends on.

### Some words belong to JavaScript itself

- [runway] Reserved word, and `aria-*` and `data-*` attributes, used by Question 5 and Step 5.

- [p] ◇ {reserved words} JavaScript keeps some words for itself, such as `return`, `function`, `class`, and `for`. They are called **reserved words**. `class` starts a class definition, and `for` starts a loop, so neither can be the name of a variable. ◼ Educational objective: why `class` and `for` are the two attribute names that change most.

- [p] ◇ {aria and data attributes} HTML has two families of attributes whose names contain a dash. **`aria-*` attributes**, such as `aria-label`, describe an element to screen readers. **`data-*` attributes**, such as `data-edition`, store our own values on an element. ◼ Educational objective: the exception inside Question 5's rule, named before it.

### Principles of React: JSX Is JavaScript

- [preview] Everything in this lesson comes down to one idea: JSX looks like HTML, but it is JavaScript. First, the JSX transform, which means each tag becomes a JavaScript call that returns an object: the build rewrites every tag as a call, and React builds the page from the objects. Second, closed tags, which means JavaScript must know where each tag ends: every tag needs a closing tag or a slash, the image and the line break too. Third, a single root, which means a JavaScript function returns one value: a component gives back one element that holds the rest. Fourth, Fragments, which means one JavaScript value that adds no element to the page: when the page needs no extra box, an empty tag groups the elements instead. Fifth, camelCase attributes, which means each attribute becomes a JavaScript property name: class becomes className, and for becomes htmlFor. ◼ Educational objective: the map's Spoken Preview, word for word, read aloud before Question 1.

### Question 1: A tag in JSX becomes a call that returns an object

- [question-cycle] Question 1: A tag in JSX becomes a call that returns an object
    - Question: "My component returns something that looks like HTML. Is it HTML?"
    - Code and result: `ArticleCard` stores its `<article>` (an `<h2 className="headline">` with "City Library Extends Its Hours" and a `<p>` with "The library now stays open until nine.") in `const card`, logs it, and returns it; `App` returns `<main><ArticleCard /></main>`; the card appears, and the Console panel shows an object (verified in React 19.3.1, Vite 8.3.4, and Chrome).
    - Verdict: the code works as written (Real Mistake none): the card appears, and the Console panel shows an object.
    - Answer: the logged object has `type: 'article'` and `props`, whose `children` hold two more objects, the `h2` with `className: 'headline'` and its text, and the `p`; JSX is not HTML: the build rewrites each tag as a call of a React function, which the Sources panel shows as `_jsxDEV("article", ...)` with the `h2` and `p` calls inside, plus an import line the dev server added; `npm run build` writes `jsx(...)` instead; each call returns a plain object, a **React element**; this rewrite is the **JSX transform**; React reads the objects when it renders and builds the DOM, so the browser never receives a tag; Lecture 2's promise: `<ArticleCard />` becomes `_jsxDEV(ArticleCard, ...)`, a call that takes the function, and `<articleCard />` becomes `_jsxDEV("articleCard", ...)`, a call that takes a text; `className` is JSX's name for `class`, and Question 5 explains why; the other fields of the object wait for Lecture 76 (message `03-76-01`).
    - Fix: none needed.
    - Rule: we read JSX as JavaScript: the build turns each tag into a call, the call returns an object that describes the element, and React builds the DOM from those objects.
    - Needs: object and property (runway "An object keeps values under names"); build and Sources panel (runway "The dev server changes our files"); component tag and rendering (recall Lecture 2).
    - Diagram: three short blocks: the logged object (shortened), the Sources panel (shortened), and the two tags against their calls.

> [!PRINCIPLE] Principle 1: The JSX transform: each tag becomes a JavaScript call that returns an object. Rule word for word; a model card (Real Mistake none), so only the right example: `const greeting = <p className="note">Hello, John Hall</p>;` with the comment that it is an object, not text.

### Question 2: An open img tag stops the build

- [question-cycle] Question 2: An open img tag stops the build
    - Question: "My HTML has `<img>` with no closing tag. Why does the build stop?"
    - Code and result: `ArticleCard` pasted with `<article>`, `<img src="/library.jpg" alt="The city library">` and the `<h2>`; the page stays empty, and the overlay shows "Expected corresponding JSX closing tag for 'img'.", with "Opened here" under the `<img>` and "Expected `</img>`" under `</article>`, and a second message, "Unexpected token. Did you mean `{'}'}` or `&rbrace;`?", at the closing brace of the function (verified in Vite 8.3.4 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: each tag is a call, and the build must know where the call's content ends; after an open tag, it reads everything as its content until the closing tag; so the `<h2>` becomes the content of the `<img>`, and at `</article>` the build still waits for `</img>`; the second message comes from the same mistake: the build lost its place and reached the closing brace of the function as if it were text, so that line has no mistake of its own; the fix is a slash, `<img ... />`; then the photo and the headline appear; `<br>` and `<input>` fail the same way.
    - Fix: `<img src="/library.jpg" alt="The city library" />`.
    - Rule: we close every tag, with a closing tag or with a slash, `<img />` and `<br />` too, because JavaScript must know where each tag ends. Boundary: any tag may close itself, such as `<div className="spacer" />`.
    - Needs: void elements (runway "HTML lets some tags stay open"); the error overlay (runway); each tag a call (Question 1).
    - Diagram: the overlay's first message, shortened, as a text block.

> [!PRINCIPLE] Principle 2: Closed tags: JavaScript must know where each tag ends. Right: an `<img ... />` and a `<br />` in John Hall's profile; wrong: the same tags open.

### Question 3: Two tags side by side after return stop the build

- [question-cycle] Question 3: Two tags side by side after return stop the build
    - Question: "I pasted a heading and a paragraph after `return`. Why does the build fail?"
    - Code and result: `ArticleCard` returns `<h2>City Library Extends Its Hours</h2>` and `<p>The library now stays open until nine.</p>` inside `return (`; the page stays empty, and the overlay shows "Adjacent JSX elements must be wrapped in an enclosing tag." under the `<p>`, with "Help: Did you want a JSX fragment `<>...</>`?" (verified in Vite 8.3.4 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: each tag is one call, so one value; `return` gives back one value, as every JavaScript function does; two calls side by side are two values, so the build stops before anything runs; one element around both is one call, and the two inner calls become its content, its `children`, as in the object of Question 1; the fix wraps both in `<article>`; the Help line points at a second way, which Question 4 takes up.
    - Fix: `<article>` around the heading and the paragraph.
    - Rule: we return one root from every component, one element that holds the rest, because a JavaScript function returns one value.
    - Needs: the error overlay (runway); each tag a call and `children` (Question 1); `return (` (recall Lecture 2).
    - Diagram: none; the two versions side by side carry the picture.

> [!PRINCIPLE] Principle 3: Single root: a JavaScript function returns one value. Right: a `<section>` around a heading and a paragraph; wrong: the two side by side.

### Question 4: A div inside a list breaks the list's layout

- [question-cycle] Question 4: A div inside a list breaks the list's layout
    - Question: "So I wrap everything in a `<div>`?"
    - Code and result: `index.css` from the runway; `TopStories` returns two `<li>` ("Rail strike ends", "New park opens today") wrapped in a `<div>`; `App` returns `<main>` with `<ul className="stories">` around `<TopStories />`; the build passes and the console stays clean, but the two stories stack one above the other with no border; the Elements panel shows `<ul class="stories">`, then `<div>`, then the two `<li>` (verified in React 19.3.1 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: a `<div>` is a real element; React puts it between the `<ul>` and the `<li>`; the flex layout arranges the children of the list, and its only child is the `<div>`; the child selector `.stories > li` matches no item, so no border; the fix is a **Fragment**, written `<>` and `</>`: one call with React's `Fragment` type, so one value for `return`, and React puts its children straight into the parent; with it, the Elements panel shows the `<li>` directly in the `<ul>`, the two stories sit side by side, and both have their border; an element stays right when the page needs the box, such as Question 3's `<article>`; a Fragment cannot take a key, which Lecture 11 explains (message `03-11-01`).
    - Fix: `<>` and `</>` instead of `<div>` and `</div>`.
    - Rule: when the elements need one root but the page needs no extra box, we group them with a Fragment, `<>` and `</>`, and we keep an element only when the page needs the box.
    - Needs: flex layout and child selector (runway "CSS can style only the direct children"); one value for `return` (Question 3); Elements panel (recall Lecture 1).
    - Diagram: two Elements-panel blocks, with the `<div>` and with the Fragment.

> [!PRINCIPLE] Principle 4: Fragments: one JavaScript value that adds no element to the page. Right: a `NameCells` component returns `<>` around `<td>John</td>` and `<td>Hall</td>`, placed inside a `<tr>`; wrong: a `<div>` around them, which puts a `<div>` inside the `<tr>`, where HTML allows only cells.

### Question 5: class and for work, and the console fills with errors

- [question-cycle] Question 5: class and for work, and the console fills with errors
    - Question: "Can I keep `class` and `for` from my HTML?"
    - Code and result: `SignUp` returns a `<form>` with `<label class="label" for="email">Your email</label>` and `<input id="email" type="email" tabindex="0" />`; the page looks right, and a click on the label puts the cursor in the box; the Console panel shows three errors: "Invalid DOM property `class`. Did you mean `className`?" and the same for `for` and `tabindex` (verified in React 19.3.1 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: the attributes of a tag become the properties of the object, as `className` did in Question 1; a property name is a JavaScript name, and `class` and `for` are reserved words, so React uses the names the DOM itself gives these properties, `className` and `htmlFor`; other names of several words use camelCase, so `tabindex` becomes `tabIndex`; React 19 still sets the wrong names on the element, so the page looks right and only the console shows the mistake; `aria-*` and `data-*` keep their dashes and print no error; a console full of these errors hides the one that matters.
    - Fix: `className="label"`, `htmlFor="email"`, `tabIndex="0"`; adding `aria-label="Newsletter"` and `data-form-id="7"` to the form prints no error.
    - Rule: we write each attribute as a JavaScript property name: `className` for `class`, `htmlFor` for `for`, camelCase for names of several words, and dashes only in `aria-*` and `data-*`.
    - Needs: object and property (runway); reserved words and `aria-*` and `data-*` (runway "Some words belong to JavaScript itself"); the Console panel (recall Lecture 2).
    - Diagram: none; the three errors and the fixed form carry the picture.

> [!PRINCIPLE] Principle 5: camelCase attributes: each attribute becomes a JavaScript property name. Right: John Hall's contact form with `className`, `htmlFor`, `aria-label`; wrong: `class` and `for`.

- [grounding] Do I still need `import React from 'react'` at the top of every file? ◼ Friction target: the map's Merged row on the import the dev server adds. Tactile scene: older tutorials start every component file with that line; our files never had it, and the Sources panel of Question 1 shows an import line we did not write.
