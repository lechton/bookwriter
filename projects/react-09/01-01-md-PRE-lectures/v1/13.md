### Principles of React: One Update

- [preview] Everything in this lesson comes down to one idea: one update, which means a setter call travels through trigger, render, and commit to the screen. First, the trigger, which means the update starts with a setter, not with a change to the page: a handler asks for the new value, and React changes the page itself. Second, the handler first, which means the update reaches the page only after the handler ends: a line right after the setter still finds the old page, so we use the value we computed. Third, the render, which means the update runs the changed component and every component inside it: React calls them to work out the new page, and changes nothing yet. Fourth, the commit, which means the update changes only the DOM nodes that differ: whatever did not change, such as the text being typed, stays exactly as it was. ◼ Educational objective: the map's Spoken Preview, word for word, one paragraph for the anchor and one per principle in the lecture, read aloud before Question 1.

### Question 1: A count written by hand sticks at 1

- [question-cycle] Question 1: A count written by hand sticks at 1
    - Question: "I call `setLikes(likes + 1)`. How does the new number get onto the screen?"
    - Code and result: first the plain JavaScript habit: `handleLike` changes the page by hand, `document.querySelector('.likes').textContent = 'Likes: ' + (likes + 1);` on line 8, with no setter; every click shows "Likes: 1", never 2 (verified in React 19.3.1, Vite 8.3.4, and Chrome); with a Save button on the card, a click on Save after two Likes renders the card again, and the page still says "Likes: 1" while `likes` is 0 (verified).
    - Verdict: does not do what the reader wanted.
    - Answer: in plain JavaScript, changing a value on the page means writing to the element, and the reader expects the setter to do that writing; the hand-written version shows why it cannot be the reader's code that writes: `likes` is still 0 on every click, because nothing stored a new value, so the handler writes `0 + 1` each time; and React never learns of the change: when the card renders again for Save, React's new description says 0 and its last description also said 0, so React sees nothing to change and leaves the hand-written 1 in place, a page that no longer matches the state; the setter works the other way round, in three steps; the **trigger**: `setLikes(1)` stores 1 and asks React for an update, and touches no DOM; the **render**: React calls `ArticleCard` again, and it returns `<p className="likes">Likes: 1</p>`; the **commit**: React compares that with the page and changes the 0 to 1; the very first screen took the same steps, with `root.render(<App />)` as its trigger (Lecture 9).
    - Fix: `setLikes(likes + 1)` on line 8; the clicks show "Likes: 1", then "Likes: 2" (verified).
    - Rule: to change what the page shows, a handler calls a setter and never writes to the DOM itself; React then calls the component and changes the page to match.
    - Needs: `document.querySelector` and `textContent` (runway "Finding an element with a CSS selector"; recall Lecture 1); the setter (recall Lecture 14); `root.render` (recall Lecture 9); the three terms (named in the first section, defined in this answer).
    - Window plan: `ArticleCard.jsx`, lines 7 to 9, the hand-written version (`startLine="7"`); the fix, line 8 (`startLine="8"`).
    - Diagram: the three steps of one click, with what each one does.

> [!PRINCIPLE]
> **Principle 1: The trigger: the update starts with a setter, not with a change to the page**
> *To change what the page shows, a handler calls a setter and never writes to the DOM itself; React then calls the component and changes the page to match.*
>
> In plain JavaScript, we change the page by writing to an element. In React, the handler calls a setter instead, and the setter writes nothing to the page: it stores the new value and asks for an update, the **trigger**. React then calls the component, which returns the new JSX, the **render**. Last, React compares it with the page and changes what differs, the **commit**. A handler that writes to the page itself skips all three steps: the state keeps its old value, and React never learns of the change.
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1); // React renders, then changes the page`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `const el = document.querySelector('p');`
> `el.textContent = count + 1; // always 1: count stays 0`

### Question 2: A read right after the setter finds the old page

- [question-cycle] Question 2: A read right after the setter finds the old page
    - Question: "Why does a read of the page right after the setter send the old number?"
    - Code and result: an analytics call should report the new count, so `handleLike` reads it from the page right after the setter: `setLikes(likes + 1);` on line 8 and `console.log('the page says:', document.querySelector('.likes').textContent);` on line 9, standing for the analytics call; the first click logs "the page says: Likes: 0", and then the page shows "Likes: 1"; the second logs "Likes: 1" (verified in React 19.3.1 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: the reader expects the setter to change the page at once, so the next line reads the new number; but Question 1 showed that the setter only asks for an update; React lets the handler finish first, and only then renders and commits; so line 9 runs while the page is still the old page; the console shows the order: the handler's "the page says" line comes first, and the components' "ArticleCard runs" lines come after it (verified); the value the analytics call needs is the one the handler computed itself, so it keeps it in a constant and passes it both to the setter and to the call; React updates the screen after all the event handlers have run, and Lecture 17 shows what that means for several setters in one handler; the state variable, `likes`, also keeps its old value on the line after the setter, which Lecture 16 explains.

    - Rule: we never read the page right after a setter to learn the new value: the DOM still shows the old one until the handler ends, so we use the value we computed.

> [!PRINCIPLE]
> **Principle 2: The handler first: the update reaches the page only after the handler ends**
> *We never read the page right after a setter to learn the new value: the DOM still shows the old one until the handler ends, so we use the value we computed.*
>
> A setter only asks for an update. React lets the event handler finish first, and only then renders and commits. So every line after the setter, until the handler ends, sees the page as it was before the click. Reading the new value from the page there gives the old one. The handler already knows the new value, because it computed it, so it keeps that value in a constant and uses it for the setter and for anything else.
>
> *We should do this:*
> `const next = count + 1;`
> `setCount(next);`
> `report(next); // the new value`
>
> *We should not do this:*
> `setCount(count + 1);`
> `report(document.querySelector('p').textContent); // old value`

### Question 3: A Like runs one card, not the whole app

- [question-cycle] Question 3: A Like runs one card, not the whole app
    - Question: "Does a click run my whole app again?"
    - Code and result: every component logs when it runs: `App`, `ArticleList`, each `ArticleCard` with its title, and `CommentBox`; on load, all of them log; a click on the first card's Like logs "ArticleCard runs: New Park Opens Today" and "CommentBox runs", twice each, and nothing from `App`, `ArticleList`, or the other two cards (verified in React 19.3.1, Vite 8.3.4, and Chrome).
    - Verdict: works as React intends: the reader's guess, the whole app, is wrong in the reassuring direction.
    - Answer: the reader may expect the whole app to run again from `App`, or only the one paragraph that shows the number; React does neither; rendering is React calling our components (Lecture 2); on the first render, it calls the root component and every component down the tree; after a setter, it calls the component that owns the state, here the first `ArticleCard`, and then every component that component returns, here its `CommentBox`; `CommentBox` runs even though nothing it shows has changed, because React calls the whole tree below the changed component; it does not call the card's parent, `ArticleList`, or `App`, or the two sibling cards, whose state did not change (Lecture 5's tree); each call only returns JSX: while the components run, nothing on the page has changed yet; Strict Mode calls each one twice (Lecture 12), and the page still changes once; a component can also render again because its parent did, which Lecture 54 covers, and skipping renders on purpose is Lecture 55's.

    - Rule: when state changes, React calls the component that owns it and every component that component returns, and no other; those calls only work out the new page, because nothing on the page has changed yet.

> [!PRINCIPLE]
> **Principle 3: The render: the update runs the changed component and every component inside it**
> *When state changes, React calls the component that owns it and every component that component returns, and no other; those calls only work out the new page, because nothing on the page has changed yet.*
>
> After a setter, React calls the component whose state changed. That component returns other components, and React calls those too, and the ones they return, down to the bottom of that part of the tree. It calls a child even when the child's output stays the same. It does not call the component's parent or its siblings. Each call only returns JSX, so the page is still the old page while the components run.
>
> *We should do this:*
> `function Card() {`
> `  const [count, setCount] = useState(0); // a change runs Card`
> `  return <Box />; // and Box inside it, but not Card's parent`
> `}`

### Question 4: A new run leaves the typed comment alone

- [question-cycle] Question 4: A new run leaves the typed comment alone
    - Question: "Will the new run wipe what the reader is typing?"
    - Code and result: "Great news!" is typed into the first card's comment box; then Like is clicked; the card and its `CommentBox` run again, the count shows "Likes: 1", and the box still holds "Great news!"; the DOM changes recorded after the click: the text node "1" in the `<p>`, plus a `name` attribute react-dom sets and removes on the `<input>` (verified in React 19.3.1 and Chrome).
    - Verdict: works as the reader hoped.
    - Answer: Lecture 1 showed that `innerHTML` rebuilds every node it touches and empties a search box, so the reader fears that running the component again does the same; React does not: during the render it works out the new output, and in the **commit** it compares it with the output of the last render and changes only the DOM nodes that differ; here only the number differs, so React changes one text node and leaves the `<article>`, the `<h2>`, the button, and the `<input>` as they are, so the typed text stays; react-dom also sets and removes a `name` attribute on the input during the commit, so the Elements panel may flash the input as well, though nothing on it changes; `CommentBox` ran again, and its output was the same, so the commit changed nothing in it: running a component is not changing the page; on the very first render the commit adds every node with `appendChild()`; after the commit, the browser paints the new pixels, a step called the **browser paint**, which is what people outside React often call "rendering"; so a component with an input can have state, and the input survives every new run; when React keeps a node and when it replaces one is Lecture 24's.
    - Fix: none.
    - Rule: we let React render a component again whenever its state changes: the commit changes only the DOM nodes whose output changed, so typed text, focus, and every unchanged element stay as they are.
    - Needs: DOM node and the Elements panel (runway "Watching React work"); `innerHTML` and the virtual DOM (recall Lecture 1); the render (Question 3).
    - Window plan: no new code window: the card of the runway; the recorded changes as an ASCII block.
    - Diagram: the old and the new output of the card, line by line, with what the commit changes.

- [diagram] What the commit compares:

> [!PRINCIPLE]
> **Principle 4: The commit: the update changes only the DOM nodes that differ**
> *We let React render a component again whenever its state changes: the commit changes only the DOM nodes whose output changed, so typed text, focus, and every unchanged element stay as they are.*
>
> Running a component again does not rebuild the page. The render only works out the new JSX. In the commit, React compares it with the JSX of the last render and changes only the DOM nodes that differ, such as one number in a paragraph. Every other node stays the same node, so an input keeps the text being typed into it and the cursor inside it. A component whose output did not change causes no change at all. After the commit, the browser paints the screen.
>
> *We should do this:*
> `function Card() {`
> `  const [count, setCount] = useState(0);`
> `  return <><p>{count}</p><input /></>; // the input keeps its text`
> `}`

- [grounding] Is React's render the same as the browser's rendering? ◼ Friction target: the map's Merged row on the two meanings of "rendering". Tactile scene: a performance article says rendering is slow, and the reader wonders whether every `ArticleCard runs` log in the console costs a repaint. Bold key terms: **render**, **browser paint**. Concrete operational resolution: React's render is our JavaScript running, which returns JSX and draws nothing; only the commit changes the DOM, and only then does the browser paint; Strict Mode's second call of every component, and `CommentBox`'s run with the same output, produced logs but no DOM change and no new paint; so a log in a component counts renders, not repaints. ◼ Educational objective: one `> [!WILD]` card after the principles, adding a fact the cycles did not state, with the evidence from Questions 3 and 4.

Decision: the count and the Saved flag belong to one article, so they live in `ArticleCard`, not in `ArticleList`; a click then renders one card and its comment box. Prediction: which logs does a Save click print? "ArticleCard runs: New Park Opens Today" and "CommentBox runs", twice each, and nothing from the list or the other cards. Result: exactly those (verified). ◼ Meaningful pedagogical commentary: where state lives decides which part of the tree a click renders; Lecture 23 shows the case where two cards must share one value.

### Component Summary

- [component-code] Summary: The Logic of Nested Components:

```component-code title="Summary: The Logic of Nested Components"
ArticleList.jsx | none | parent | [role: The **list** maps the articles into cards and holds no state, so a click on a card never runs it. Its log appears on load and stays quiet after.]
  ArticleCard.jsx | article | card | [role: The **card** owns `likes` and `isSaved`. Its handler computes the new count, calls the setter, the **trigger**, and reports the value it computed. Each click renders this card and its comment box, and the **commit** changes one text node.]
    CommentBox.jsx | none | form | [role: The **comment box** runs with its card on every click and returns the same input, so the commit never touches it, and the typed comment stays.]
```

- [p] ★ {the closing paragraph} A developer who comes from plain JavaScript expects to write the new number onto the page, to read it back on the next line, to run the whole app on every click, and to lose what the user typed. In React 19, the setter asked for an update, the handler finished and reported the value it computed, React rendered one card and its comment box, and the commit changed one text node per click while "Great news!" stayed in the box. Each step applied one principle: every change went through a setter, the handler used its own value, the state lived in the card it changes, and the comment box stayed where it was. ◼ Educational objective: the example's one ending: the old habit, what React 19 did on the larger example, and each step's principle named once, in thread order (`lecture-structure` Section 19).

### Where you will meet this

- [p] 1. **Analytics and logging in click handlers**: the event reports the value the handler computed, never a value read back from the page.
- [p] 2. **A form inside a component that changes often**: a comment box, a search field, or a filter stays put while counts and labels around it change.
- [p] 3. **Debugging "why did this run?"**: a log at the top of each component shows which part of the tree a click renders.
- [p] 4. **React DevTools' highlight of renders**: it marks components that rendered, which is not the same as the DOM nodes the commit changed.
- [p] 5. **Interviews on rendering**: "render", "commit", and "paint" are three different moments, and candidates are expected to say which code runs in each.

### For the interview

- [interview] > **The Interview Question:** What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?

- [interview] **1. The Hidden Signal** ◼ The interviewer wants the three steps in order and the code that runs in each: our handler and setter in the trigger, our component bodies in the render, React's DOM changes in the commit, and the browser's paint after it. A junior answer says "React re-renders the page". A strong answer adds that rendering changes nothing on the page, that the commit changes only what differs, and that the page is still old while the handler runs.

- [interview] **2. The Classic Trap** ◼ The classic trap is "a re-render rebuilds the DOM". On the article card, a Like rendered the card and its comment box, and the commit changed one text node, the count; the comment box kept "Great news!". A second trap is reading the page right after the setter: the handler logged "Likes: 0", because the commit had not happened yet.

- [interview] **3. What is Actually Going On** ◼ The click runs `handleLike`, which computes `nextLikes` and calls `setLikes(nextLikes)`, the trigger. When the handler ends, React renders: it calls the first `ArticleCard` and its `CommentBox`, and nothing else; `App`, `ArticleList`, and the other cards do not run. The card returns `Likes: 1` where the last render said `Likes: 0`, so the commit changes that one text node. Then the browser paints.

- [interview] **4. Where It Gets Tricky** ◼ *What triggers the very first render?* `root.render(<App />)` in `main.jsx` (Lecture 9). *Does a child re-render when its output is the same?* Yes: `CommentBox` ran on every Like, and the commit changed nothing in it. *Why does Strict Mode's double render not flicker?* The render draws nothing; only the commit changes the DOM, once. *What if I change the DOM by hand?* React does not know: on the next render it compares its own two descriptions and may leave the stale text in place. *When can I read the new DOM?* After the commit; refs (Lecture 30) and Effects (Lecture 31) give code a place there. *Does the state variable change on the next line?* No, and Lecture 16 explains why.

### Glossary

- [glossary] Trigger ◼ The request that starts an update: the first `root.render()`, or a setter call. It stores the new value and changes nothing on the page.
- [glossary] Render ◼ React calling our components to work out what the page should show: the component that owns the changed state and every component inside it. It only returns JSX.
- [glossary] Commit ◼ React changing the DOM after a render, only where the new output differs from the last; on the first render, adding every node.
- [glossary] DOM node ◼ One object in the browser's DOM, for a tag or for the text inside it. The commit changes nodes one by one.
- [glossary] Browser paint ◼ The browser drawing the pixels on the screen after the commit; what people outside React often call "rendering".

### Summary

- [review-title] **One update: a setter call travels through trigger, render, and commit to the screen**

- [review-subtitle] ❒ The trigger: the update starts with a setter, not with a change to the page
- [always-rule] ➔ ALWAYS change what the page shows through a setter.
- [never-rule] ➔ NEVER write to the DOM by hand in a React handler; the state keeps its old value, and React may leave stale text in place.

- [review-subtitle] ❒ The handler first: the update reaches the page only after the handler ends
- [always-rule] ➔ ALWAYS keep the new value in a constant when the handler needs it after the setter.
- [never-rule] ➔ NEVER read the page right after a setter; it still shows the old value.

- [review-subtitle] ❒ The render: the update runs the changed component and every component inside it
- [if-then-rule] ➔ IF state changes in a component THEN React calls that component and everything inside it, and no parent or sibling.
- [always-rule] ➔ ALWAYS keep component bodies pure; they run without changing the page.

- [review-subtitle] ❒ The commit: the update changes only the DOM nodes that differ
- [if-then-rule] ➔ IF a component holds an input THEN let it re-render freely; the commit leaves the input and its text alone.
- [never-rule] ➔ NEVER avoid state for fear of rebuilding the page; a render changes only the nodes whose output changed.

- [closing-line] A setter asks, the handler ends, React renders, and the commit changes only what differs. ◼ Educational objective: the map's Closing Line, the last spoken sentence of the lesson. The four subtitles above are the four thread labels word for word, so the summary repeats the structure the preview announced (`lecture-structure` Section 13).

**DO THIS:** change state through the setter and use the value you computed

```jsx right
function handleLike() {
  const nextLikes = likes + 1;
  setLikes(nextLikes);
  console.log('analytics:', article.title, nextLikes);
}
```

**DO NOT DO THIS:** write the page by hand, or read it back after the setter

```jsx wrong
function handleLike() {
  document.querySelector('.likes').textContent = 'Likes: ' + (likes + 1);
  console.log('analytics:', document.querySelector('.likes').textContent);
}
```

| | **PLAIN JAVASCRIPT**<br>(change the page by hand) | **REACT**<br>(trigger, render, commit) |
| ---: | :--- | :--- |
| **Who changes the page** | Our handler, line by line | React, in the commit, after our handler |
| **The line after the change** | Reads the new page | Reads the old page; use the computed value |
| **What runs on a click** | Only the handler | The handler, then the changed component<br>and every component inside it |
