# Q13 Principle Map (River Version v2): The Trigger, Render, and Commit Lifecycle
- **Version**: River Version (`v2`)
- **Bank Row**: `questions/questions.md` row 13, Version 4
- **Topic Tag**: `#render_and_commit` | `❱ CORE`
- **Interview Question**: *What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?*

## Authorized Scope
- How every screen update in React passes through three ordered steps (`Trigger`, `Render`, and `Commit`), followed by the browser painting the updated screen (`Browser Paint`).
- Step 1 (`Trigger` a render): the two only reasons a component renders in React:
  1. The **initial render** when the application starts and `src/main.jsx` calls `createRoot(document.getElementById('root')).render(<App />)`.
  2. A **re-render** after the component is already mounted when an event handler or callback calls a `useState` setter function (`setCount(count + 1)`), which queues a render instead of mutating the DOM immediately.
- Why reading the live DOM on the line immediately after calling a state setter (`document.querySelector('.count-text').textContent` right after `setCount(count + 1)`) still returns the old DOM text (`'Tickets: 1'`), because calling `setCount` only triggers (queues) a render and the DOM is not updated until the `Commit` phase after the event handler finishes and React renders the component.
- Step 2 (`Render` your components): what "rendering" means in React (`React calling your component functions`), which components React calls on an initial render (starting at the root component `App` and calling every nested child component down the tree) versus on a state-triggered re-render (calling the component whose state updated, such as `TicketCounter`, and recursively calling the child components it returns, such as `OrderSummary`, without re-calling unaffected parent components above it like `App`), and why the `Render` phase is a pure calculation of JSX output that touches zero DOM nodes.
- Step 3 (`Commit` changes to the DOM) and `Browser Paint`: how React applies the result of the `Render` phase to the real browser DOM (`appendChild()` to insert all newly created DOM nodes on the initial render, and minimal targeted DOM updates on re-renders for only the nodes or attributes whose calculated output changed between renders), why an `<input className="note-input" placeholder="Seat note" />` inside a re-rendering component keeps its exact DOM node reference (`===`) and any text the user typed (`'Window seat'`) when sibling text updates, and how React's "rendering" (calling component functions) differs from the browser's "painting" (sometimes called "browser rendering", where the browser draws pixels on the screen after React commits DOM changes).
- Out of scope: why mutating external variables during render breaks component purity and how `<StrictMode>` calls components twice in development (`Q14 #purity`), why the state variable `count` itself still holds the old value inside the running event handler snapshot (`Q15 #state_snapshots`), batching multiple state setter calls in one event and updater functions `setCount(n => n + 1)` (`Q16 #state_updates`), synchronizing with external systems after commit using `useEffect` (`Q26 #effects`), skipping child re-renders with `React.memo` (`Q57 #react_memo`), and Fiber work loop priority lanes or concurrent rendering (`Q66 #concurrent_rendering`, `Q78 #fiber_architecture`).

## General Concepts Introduction (Runway Plan)
- **Opening Essence**:
  - **Furniture-free snippet**:
    - Initial trigger in `main.jsx`: `const root = createRoot(document.getElementById('root')); root.render(<App />);`
    - Re-render trigger, render, and commit in a small component:
      - `function TicketCounter() { const [count, setCount] = useState(1); function handleAdd() { setCount(count + 1); } return <p className="count-text">Tickets: {count}</p>; }`
  - **Human image**: The restaurant kitchen from `react.dev` where React is the waiter taking care of a guest's table (the browser screen):
    1. **Triggering a render** is the waiter taking the guest's order at the table and walking the order slip into the kitchen (either the opening-night order from `root.render(<App />)`, or a follow-up order when the guest clicks a button and calls `setCount(count + 1)`).
    2. **Rendering** is the chef in the kitchen calling your component function to prepare the dish and figure out what the plate should look like (`<p className="count-text">Tickets: 2</p>`), without touching the guest's table yet.
    3. **Committing** is the waiter bringing the finished dish out of the kitchen and updating only what changed on the guest's table (changing `1` to `2` in `<p class="count-text">` while leaving the guest's notepad `<input>` on the table untouched), after which the browser paints the screen.
  - **Exact nuance of confusion to state out loud**:
    1. Between calling `setCount(count + 1)` and updating the DOM on the very next line of `handleAdd`: ***"When you click `Add ticket`, the screen updates so fast that `setCount(count + 1)` looks like it changes the DOM right on that line, but it does NOT touch the DOM on that line!"*** Calling `setCount(count + 1)` only **triggers** (queues) a request for React to render; the DOM still holds `Tickets: 1` for the rest of `handleAdd`, and only changes to `Tickets: 2` later during the **Commit** step.
    2. Between React **rendering** a component and React **rebuilding the DOM** (or the browser **painting** the screen): ***"In everyday web talk, people say 'rendering' to mean the browser drawing pixels on the screen, or they assume re-rendering a component destroys and recreates all of its HTML elements, but in React they are NOT the same thing!"*** In React, **rendering** is simply React calling your component function in memory to calculate JSX; **committing** is React updating only the specific DOM nodes whose output changed; and **painting** is the browser drawing the updated DOM onto the screen afterward.
- **Theme**: On a ticket order box (`Concert Tickets`, `Tickets: 1`, a `Seat note` text input, and an `Add ticket` button), a developer needs to know why reading the DOM inside the click handler right after `setCount(count + 1)` sees the old number `Tickets: 1`, which component functions React actually calls during a re-render, and why re-rendering `TicketCounter` updates `Tickets: 1` to `Tickets: 2` without wiping out `'Window seat'` typed into the `<input>` right below it.
- **Ways**:
  - **Way 1 to trigger a render (Initial render)**: Calling `root.render(<App />)` on the root created by `createRoot(document.getElementById('root'))` when the app first starts up.
  - **Way 2 to trigger a render (Re-render on state update)**: Calling a `useState` setter function (`setCount(count + 1)`) after the component has already mounted.
- **Recall**:
  - React's virtual DOM compares previous and next element descriptions in memory and updates only changed DOM nodes instead of replacing container HTML with `innerHTML` (Lecture 01, `Q01 #what_is_react`).
  - JSX tags compile into plain JavaScript React element objects that describe what should appear on screen without creating DOM nodes by themselves (Lecture 02, `Q02 #jsx`).
  - `App` sits at the top of the Component Render Tree above its child components (Lecture 06, `Q06 #ui_tree`).
  - `createRoot(document.getElementById('root'))` and `root.render(<App />)` in `src/main.jsx` mount the root component into `<div id="root"></div>` in `index.html` (Lecture 07, `Q07 #create_root`).
  - Calling `const [count, setCount] = useState(1)` stores state in React outside the component function, and calling `setCount(count + 1)` requests a re-render with the new value (Lecture 12, `Q12 #use_state`).

## Principle Thread
- **Anchor**: How React separates scheduling an update (`Trigger`), calling component functions to compute the next UI description in memory (`Render`), and applying only the changed nodes to the browser DOM (`Commit`) before the browser paints (`Browser Paint`).
- **Axis**: Chronological execution order of a React update from start to finish:
  1. **Step 1: Triggering a Render** via `root.render(<App />)` on startup or `setCount(count + 1)` on a state update, which queues a render without changing the DOM inside the running handler (Principle 1).
  2. **Step 2: Rendering the Components** by calling `App` down the tree on initial mount, or calling the state-updated component (`TicketCounter`) and recursively calling its returned children (`OrderSummary`) on a re-render, as a pure calculation in memory before any DOM node is touched (Principle 2).
  3. **Step 3: Committing Changes to the DOM and Browser Painting** by inserting all created DOM nodes with `appendChild()` on initial mount, or mutating only the specific DOM nodes/text that changed between renders while leaving unchanged sibling DOM nodes (such as `<input className="note-input">` and its typed `'Window seat'` text) untouched, followed by the browser painting the screen (Principle 3).
- **Why This Axis**: Trigger, Render, and Commit form a strict causal timeline at runtime:
  1. Nothing renders until a **Trigger** (`root.render(<App />)` or `setCount(count + 1)`) requests work, and understanding that `setCount` only queues work explains why reading the DOM on the next line of the click handler sees the old text (Principle 1).
  2. Once the trigger queues work and the event handler finishes, React enters the **Render** phase and calls the component function (`TicketCounter`) and any child components it returns (`OrderSummary`) to compute the new JSX tree in memory while the live DOM still holds the previous output (Principle 2).
  3. Once React finishes computing the new JSX tree in the Render phase, it enters the **Commit** phase, compares the new output against the previous render's output, touches only the changed text node in the real DOM while preserving untouched nodes like `<input>`, and hands control to the browser to paint the pixels (Principle 3).

## Principles

### Principle 1: Step 1 (Trigger) Starts with `root.render` on Startup or a State Setter Queueing a Re-Render
- **Handle**: `trigger-phase-two-ways`
- **Rule**: A React component renders for only two reasons: the initial render triggered by `createRoot(...).render(<App />)` when the app starts, or a re-render triggered by calling a `useState` setter (`setCount(count + 1)`), which queues a render for after the event handler finishes rather than updating the DOM on that line.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - Trigger 1 (Initial render in `main.jsx`): `const root = createRoot(document.getElementById('root')); root.render(<App />);`
    - Trigger 2 (Re-render in `TicketCounter.jsx`): `function handleAdd() { setCount(count + 1); console.log(document.querySelector('.count-text').textContent); }`
  - **Human image**: In a restaurant, a dish never appears on a table by magic; someone has to **trigger** the order by walking a ticket into the kitchen. There are only two times an order ticket enters the kitchen: when the guests first sit down (`root.render(<App />)` on startup), or when a guest asks the waiter for another item (`setCount(count + 1)` inside an event handler). And when the guest hands the waiter that request (`setCount(count + 1)`), the new dish is **not** sitting on the table a millisecond later while the guest is still speaking! The waiter simply clips the order into the kitchen queue and finishes listening to the guest (`handleAdd` finishes running) before the kitchen cooks the dish and brings it to the table.
  - **Exact nuance of confusion to state out loud**: ***"When you click `Add ticket` and `setCount(count + 1)` runs, the number on the screen changes so fast to the human eye that it feels like `setCount(count + 1)` updated the DOM right on that line, but it does NOT update the DOM on that line!"*** Walk through what actually happens if you read `document.querySelector('.count-text').textContent` on the line right below `setCount(count + 1)`: the DOM still says `'Tickets: 1'`, because `setCount(count + 1)` only **queues** a render (Step 1: Trigger). The new number (`count + 1`) only reaches the DOM after `handleAdd` finishes, React runs the component in Step 2 (Render), and React updates the DOM in Step 3 (Commit).
- **Root Distinction**:
  - *Junior blurred view*: Calling `setCount(count + 1)` inside `handleAdd` immediately rewrites `<p class="count-text">` in the browser DOM before the next line of `handleAdd` executes.
  - *Senior grounding*: `setCount(count + 1)` is only the **Trigger** step that queues a render request in React; `handleAdd` finishes running against the existing DOM first, and only then does React run the **Render** and **Commit** steps to update the DOM.
- **Real Beginner Mistake (events, in order)**:
  1. A developer builds `TicketCounter.jsx` with `const [count, setCount] = useState(1)` and renders `<p className="count-text">Tickets: {count}</p>` and `<button className="add-btn" onClick={handleAdd}>Add ticket</button>`.
  2. Inside `handleAdd`, the developer calls `setCount(count + 1)` and on the very next line reads `document.querySelector('.count-text').textContent` to log or report the updated ticket text.
  3. On initial page load, `src/main.jsx` calls `root.render(<App />)` (the initial render trigger), and the browser displays `Tickets: 1`.
  4. The user clicks `Add ticket` once.
  5. Inside `handleAdd`, `setCount(1 + 1)` queues a re-render, and the next line `console.log(document.querySelector('.count-text').textContent)` executes immediately while the DOM still holds the old text, logging `'Tickets: 1'` instead of `'Tickets: 2'`.
  6. Only after `handleAdd` finishes does React render `TicketCounter` with `2` and commit `'Tickets: 2'` to `<p class="count-text">`, whereas computing `const nextCount = count + 1;` and passing `nextCount` to both `setCount(nextCount)` and the log reports `2` accurately inside the handler.
- **Interview Depth**:
  - Name the **only two ways** a render is ever triggered in React: (1) the initial render via `createRoot(...).render(<App />)`, and (2) a state update in a mounted component (or one of its ancestors) via a state setter (`setState` / `useState` setter).
  - What happens if you call `setCount(count)` with the exact same value that is already in state? React compares the new value with the current state using `Object.is(nextState, currentState)`. When they are identical, React bails out and skips re-rendering the component and its children (note that on the very first same-value call right after a state change from `1` to `2`, React may call `TicketCounter` once before bailing out without calling child components like `OrderSummary` or touching the DOM, and on subsequent same-value calls it does not even call `TicketCounter`).
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: Any direct DOM update call inside `setCount(nextCount)` that changes `<p class="count-text">` while `handleAdd` is still on the call stack.
    - **Who supplies it**: React's scheduler queues the state update during `handleAdd`, waits for `handleAdd` to return, and then drives the `Render` and `Commit` phases.

### Principle 2: Step 2 (Render) Is React Calling Your Component Functions Recursively to Compute JSX in Memory
- **Handle**: `render-phase-component-calls`
- **Rule**: "Rendering" is React calling your component functions to calculate the JSX they return: on the initial render React calls the root component (`App`) and every nested component down the tree, and on a re-render React calls the component whose state updated (`TicketCounter`) and recursively calls every child component it returns (`OrderSummary`) without calling unaffected parent components (`App`) or touching the DOM.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - `function App() { return <main><h1>City Box Office</h1><TicketCounter /></main>; }`
    - `function TicketCounter() { const [count, setCount] = useState(1); return <section><OrderSummary count={count} /><button onClick={() => setCount(count + 1)}>Add ticket</button></section>; }`
    - `function OrderSummary({ count }) { return <p className="count-text">Tickets: {count}</p>; }`
  - **Human image**: Once the waiter brings the order ticket into the kitchen (Step 1: Trigger), the chef prepares the order in the kitchen (Step 2: Render). On opening night (the initial render), the head chef starts at the very top of the menu (`App`), which calls the station chef (`TicketCounter`), which calls the plating assistant (`OrderSummary`). When a guest at the ticket counter asks for one more ticket (`setCount(count + 1)` inside `TicketCounter`), the head chef (`App`) does not need to redo the whole restaurant! React walks straight to the station whose state changed (`TicketCounter`), calls `TicketCounter()`, sees `<OrderSummary count={2} />` in its return value, and calls `OrderSummary({ count: 2 })`. All of this happens inside the kitchen in memory before anyone touches the guest's table (the DOM).
  - **Exact nuance of confusion to state out loud**:
    1. Between who gets called on initial render vs. on a state re-render: ***"When `TicketCounter` updates its state with `setCount(count + 1)`, you might think React re-runs the entire application from `App` down, or you might think React only calls `TicketCounter` and stops there, but it does NEITHER of those!"*** React starts at the component whose state changed (`TicketCounter` is called; `App` above it is **not** called) and then **recursively calls every child component that `TicketCounter` returns** (`OrderSummary` is called), continuing down the subtree until no more components are returned.
    2. Between the `Render` phase running and the DOM changing: ***"While `TicketCounter` and `OrderSummary` are running during a re-render with `count = 2`, if you inspect the live DOM on the page at that exact moment, `<p class="count-text">` STILL says `Tickets: 1`!"*** Rendering is strictly a pure JavaScript calculation that returns React element objects in memory; zero DOM nodes are created or modified during Step 2.
- **Root Distinction**:
  - *Junior blurred view*: "Rendering" means putting HTML onto the browser screen, and calling `setCount` inside `TicketCounter` either re-runs `App` at the top of the app or updates `<p class="count-text">` while `TicketCounter()` is executing.
  - *Senior grounding*: "Rendering" is React invoking component functions in memory to compute a tree of React elements; initial render starts at `App`, a state re-render starts at the component that owns that state (`TicketCounter`) and recursively invokes its returned children (`OrderSummary`), and the browser DOM remains untouched until Step 3 (`Commit`).
- **Real Beginner Mistake (events, in order)**:
  1. A developer extracts `<OrderSummary count={count} />` into `src/components/OrderSummary.jsx` and places `document.querySelector('.count-text').textContent` (or a DOM measurement) directly inside the body of `TicketCounter` during render, assuming that because `count` is now `2` during the re-render, the `<p class="count-text">` node in the DOM already shows `'Tickets: 2'`.
  2. On initial mount (`count = 1`), when `TicketCounter()` runs for the first time, `<p class="count-text">` does not even exist in the DOM yet (`document.querySelector('.count-text')` returns `null`), because React has not reached the Initial Commit step!
  3. When the user clicks `Add ticket` (`count` becomes `2`), React enters Step 2 (`Render`) and calls `TicketCounter()` and then `OrderSummary({ count: 2 })`.
  4. While `TicketCounter()` and `OrderSummary()` are executing with `count = 2`, the live DOM node `<p class="count-text">` still holds `'Tickets: 1'` from the previous render, because Step 3 (`Commit`) has not happened yet.
- **Interview Depth**:
  - Trace the exact recursive process in Step 2: if `TicketCounter` returns `<OrderSummary count={count} />`, React calls `OrderSummary({ count: 2 })`; if `OrderSummary` returned another component, React would call that component next, and so on until only built-in host tags (`<section>`, `<h2>`, `<p>`, `<button>`) remain.
  - Why rendering must always be a **pure calculation** (same inputs -> same JSX output, without modifying variables or DOM nodes outside the component during render): because Step 2 (`Render`) only calculates descriptions in memory, React can call component functions multiple times (as `<StrictMode>` does in development, covered in the next lesson `Q14 #purity`) without corrupting the screen.
  - From `react.dev`'s `<DeepDive>` ("Optimizing performance"): recursively calling child components inside the updated subtree is the default behavior because React cannot know whether `OrderSummary` depends on `TicketCounter`'s update without calling it; this pure function calculation is fast, and you only reach for optimizations (like `Q57 #react_memo`) if a large subtree is measurably slow.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: Any function call `OrderSummary({ count })` written with parentheses inside `TicketCounter.jsx`, or any code in `TicketCounter.jsx` that tells React to skip `App()` on a re-render.
    - **Who supplies it**: React tracks which component instance (`TicketCounter`) called `setCount`, starts the re-render at `TicketCounter`, reads the returned `<OrderSummary count={count} />` element object, and calls `OrderSummary({ count })` itself.
    - **What JavaScript and React do**:
      1. On initial mount (`root.render(<App />)`), React calls `App()`, sees `<TicketCounter />`, calls `TicketCounter()`, sees `<OrderSummary count={1} />`, and calls `OrderSummary({ count: 1 })`.
      2. When the user clicks `Add ticket`, `setCount(2)` marks `TicketCounter` as needing a re-render.
      3. In Step 2 (`Render`), React skips `App()` completely and calls `TicketCounter()`, where `useState(1)` returns `count = 2`.
      4. `TicketCounter()` returns its JSX tree containing `<OrderSummary count={2} />`, so React calls `OrderSummary({ count: 2 })`, which returns `<p className="count-text">Tickets: 2</p>`.
- **React Does**:
  - On initial mount (`root.render(<App />)`), the Console logs in exact order:
    1. `Render: App`
    2. `Render: TicketCounter count = 1 | DOM during render: null`
    3. `Render: OrderSummary count = 1`
  - On the first click of `Add ticket` (`1 -> 2`), `App` does **not** log at all, and the Console logs in exact order:
    1. `Trigger: handleAdd read DOM right after setCount: Tickets: 1`
    2. `Trigger: handleAdd nextCount variable: 2`
    3. `Render: TicketCounter count = 2 | DOM during render: Tickets: 1`
    4. `Render: OrderSummary count = 2`
- **Example Step**: Creates `src/components/OrderSummary.jsx` exporting `OrderSummary({ count })` that renders `<p className="count-text">Tickets: {count}</p>`, and updates `src/components/TicketCounter.jsx` to import `OrderSummary` and render `<OrderSummary count={count} />` inside `<section className="ticket-box">`.
- **Code names**: `src/App.jsx`, `src/components/TicketCounter.jsx`, `src/components/OrderSummary.jsx`, `App`, `TicketCounter`, `OrderSummary`, `count`, `Render: App`, `Render: TicketCounter count = 1 | DOM during render: null`, `Render: OrderSummary count = 1`, `Render: TicketCounter count = 2 | DOM during render: Tickets: 1`, `Render: OrderSummary count = 2`
- **Visual idea**: Side-by-side Component Render Tree diagram comparing **Initial Render** (`App` -> `TicketCounter` -> `OrderSummary` all highlighted and called) versus **Re-Render on `setCount`** (`App` unhighlighted and skipped; `TicketCounter` -> `OrderSummary` highlighted and called recursively).

### Principle 3: Step 3 (Commit) Applies Only Changed Nodes to the DOM, Preserving Untouched Elements Before Browser Paint
- **Handle**: `commit-phase-and-browser-paint`
- **Rule**: In the Commit phase, React inserts all created DOM nodes with `appendChild()` on the initial render, and on a re-render mutates only the specific DOM nodes or properties whose output changed from the previous render (leaving unchanged sibling elements like `<input>` and their user-typed text intact), after which the browser paints the updated screen.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - Inside `TicketCounter.jsx`:
      - `<h2>Concert Tickets</h2>`
      - `<OrderSummary count={count} />`
      - `<input className="note-input" placeholder="Seat note" />`
      - `<button className="add-btn" onClick={handleAdd}>Add ticket</button>`
  - **Human image**: When the waiter carries the newly prepared order out of the kitchen to the guest's table (Step 3: Commit), what does the waiter do? On opening night (the initial commit), the table is completely empty (`<div id="root"></div>`), so the waiter sets down every plate, glass, and notepad from scratch (`appendChild()`). On a re-render, when the guest only changed the ticket count from `1` to `2`, a clumsy waiter (`innerHTML`) would sweep the entire table onto the floor, throwing away the notepad (`<input>`) where the guest just wrote `'Window seat'`, and set a brand-new table from scratch. React's waiter compares the new order with what is already on the table, reaches in with tweezers to swap only the number `1` for `2` inside `<p class="count-text">`, and never touches the `<h2>`, the `<button>`, or the guest's `<input>` notepad with `'Window seat'`. Only after the waiter steps back does the dining room camera take the picture (**Browser Paint**).
  - **Exact nuance of confusion to state out loud**: ***"Because `TicketCounter` executes from top to bottom on every click and returns `<section>`, `<h2>`, `<OrderSummary />`, `<input />`, and `<button>` all over again, it is easy to fear that re-rendering `TicketCounter` destroys and recreates those DOM elements and wipes out what the user typed into `<input />`, but it does NOT!"*** Returning `<input className="note-input" placeholder="Seat note" />` during Step 2 (`Render`) only creates a lightweight JavaScript object description in memory. In Step 3 (`Commit`), React sees that `<input className="note-input" placeholder="Seat note" />` is at the same place with the same attributes as the previous render, so React leaves the live `<input>` DOM node and its typed `'Window seat'` value completely untouched, and updates only the text inside `<p class="count-text">` from `1` to `2` and `3`.
- **Root Distinction**:
  - *Junior blurred view*: Because `TicketCounter()` returns the entire `<section>` JSX block on every re-render, React rebuilds all the DOM elements inside `<section>` on every click, which would reset an uncontrolled `<input>` and force a full page rebuild.
  - *Senior grounding*: Step 2 (`Render`) produces lightweight React element descriptions in memory; Step 3 (`Commit`) diffs those descriptions against the previous render and applies the minimal DOM mutation (updating only the text node inside `<p class="count-text">`), preserving the exact DOM node instances (`===`) for `<main>`, `<h1>`, `<section>`, `<h2>`, `<p>`, `<input>`, and `<button>`, after which the browser paints.
- **Real Beginner Mistake (events, in order)**:
  1. A developer needs a `Seat note` input box (`<input className="note-input" placeholder="Seat note" />`) inside `TicketCounter.jsx` right below `<OrderSummary count={count} />`.
  2. The developer worries that clicking `Add ticket` and calling `setCount(count + 1)` will re-render `TicketCounter`, recreate the `<input>` DOM node, and erase whatever seat note (`'Window seat'`) the buyer already typed into the box.
  3. Because of that fear, the developer tries to avoid state updates in `TicketCounter` and mutates `<p class="count-text">` manually with `document.querySelector`, fighting React's declarative model.
  4. When written normally in React with `<input className="note-input" placeholder="Seat note" />` inside `TicketCounter.jsx`, the buyer types `'Window seat'` into the input and clicks `Add ticket` twice (`Tickets: 1` -> `Tickets: 2` -> `Tickets: 3`).
  5. On each click, `TicketCounter` and `OrderSummary` re-render in Step 2, and in Step 3 (`Commit`) React updates only the text inside `<p class="count-text">` while keeping the exact same `<input>` DOM node (`window.__nodes.input === document.querySelector('.note-input')` is `true`) and preserving `'Window seat'` inside the box.
- **Interview Depth**:
  - Contrast what happens in Step 3 (`Commit`) on **Initial Render** vs. **Re-Render**:
    1. **Initial Commit**: React creates all the DOM nodes for `<main>`, `<h1>`, `<section>`, `<h2>`, `<p>`, `<input>`, and `<button>`, and attaches them to `<div id="root"></div>` using the DOM `appendChild()` API.
    2. **Re-Render Commit**: React applies the minimal necessary DOM operations (calculated during rendering) to match the latest render output: here, updating only the changed text from `'1'` to `'2'` inside `<p class="count-text">` and touching zero other DOM nodes if their output did not change.
  - State the exact terminology distinction between **React rendering** and **Browser painting** ("browser rendering"):
    1. **React rendering** (Step 2) is React calling your component functions in JavaScript to calculate JSX element trees. A component can render without any DOM node changing (if its output is identical to the previous render).
    2. **Commit** (Step 3) is React mutating the real browser DOM nodes where the output differed.
    3. **Browser paint** (Epilogue, often called "browser rendering" in CSS/browser docs) happens **after** React finishes committing changes to the DOM, when the browser recalculates layout and repaints the pixels on the screen.

## Interview Points
1. Every UI update in React flows through three distinct phases (**Trigger**, **Render**, and **Commit**), followed by **Browser Paint** (often compared to a waiter taking an order in a restaurant, the kitchen preparing the dish, and the waiter placing the dish on the table).
2. **Step 1 (Trigger)**: There are only two ways to trigger a render in React: the **initial render** when the app starts via `createRoot(document.getElementById('root')).render(<App />)`, and a **re-render** when a mounted component calls a state setter function (`setCount(count + 1)`). Calling a state setter only queues a render request; it does not mutate the DOM immediately, which is why reading a DOM node (`document.querySelector(...).textContent`) on the next line of an event handler still returns the old text.
3. **Step 2 (Render)**: "Rendering" in React means React calling your component functions to calculate the JSX they return. On the initial render, React calls the root component (`App`) and every nested component down the tree; on a state-triggered re-render, React calls the component whose state updated (`TicketCounter`) and recursively calls all child components it returns (`OrderSummary`), skipping unaffected parent components (`App`). Rendering is a pure calculation in memory and touches zero DOM nodes.
4. **Step 3 (Commit)**: After rendering finishes, React commits the result to the real browser DOM. On the initial render, React inserts all created DOM nodes into the container using `appendChild()`. On a re-render, React compares the new render output with the previous render output and mutates only the specific DOM nodes or properties that actually changed, leaving unchanged sibling DOM nodes (such as an `<input>` element and any text typed into it) completely untouched.
5. **Epilogue (Browser Paint vs. React Rendering)**: Only after React finishes committing DOM changes does the browser recalculate layout and repaint the pixels on the screen (**Browser Paint**). In interviews, always distinguish **React rendering** (calling component functions in JavaScript to compute JSX descriptions) from **browser painting / browser rendering** (drawing pixels on the screen after the DOM changes).
