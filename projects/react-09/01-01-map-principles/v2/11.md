# Q11 Principle Map (River Version v2): Responding to Events with Handler References, Propagation Control, and preventDefault
- **Version**: River Version (`v2`)
- **Bank Row**: `questions/questions.md` row 11, Version 4 (syllabus card `01-01-map/11.md` does not exist; mapped directly from bank row 11 and the official React 19 documentation corpus)
- **Topic Tag**: `#event_handling` | `❱ CORE`
- **Interview Question**: *How do you respond to user events like clicks and form submissions, and how do you control propagation and default browser actions?*

## Authorized Scope
- How React attaches event handlers declaratively to built-in JSX tags using `camelCase` prop names (`onClick`, `onSubmit`) instead of imperative `element.addEventListener(...)` calls or lowercase HTML attributes (`onclick`), and why React warns in the Console (`Invalid event handler property \`onclick\`. Did you mean \`onClick\`?`) and ignores lowercase event attributes.
- How passing a function reference (`onClick={handleLike}`) differs from calling a function during render (`onClick={handleLike()}`), why `onClick={handleLike()}` executes immediately while React renders the component and passes its return value (`undefined`) to `onClick` so later clicks do nothing, and why passing a non-function value such as a string (`onClick="handleLike()"`) logs `Expected \`onClick\` listener to be a function, instead got a value of \`string\` type.`.
- How event handlers defined inside a component function body read the component's props directly through JavaScript lexical scope (`title`), and how wrapping a call inside an inline arrow function (`onClick={() => handleShare('Email')}`) passes custom arguments on click without calling the function during render.
- How React passes a `SyntheticEvent` object (`e`) as the first argument to every event handler (`e.target`, `e.currentTarget`, `e.nativeEvent`), how events bubble up the component tree from a child element (`<button>`) to parent elements (`<article>`), how `e.stopPropagation()` stops the event from reaching ancestor handlers, and how `onClickCapture` runs during the downward capture phase before target and bubbling handlers.
- How certain browser elements have built-in default actions (such as `<form>` submitting and reloading the page, or `<a href="...">` navigating to a new URL), why `e.stopPropagation()` does not cancel a browser default action, and how calling `e.preventDefault()` inside `onSubmit` keeps the page from reloading while executing your handler logic.
- Out of scope: storing or updating interactive component state across renders (`Q12 #use_state`), the Trigger-Render-Commit lifecycle (`Q13 #render_and_commit`), component purity rules (`Q14 #purity`), passing callback props from a parent component to a child component so the child can notify the parent (`Q23 #callback_props`), controlled inputs (`Q20 #controlled_inputs`), and React 19 form actions (`<form action={fn}>`, `Q41 #form_actions`).

## General Concepts Introduction (Runway Plan)
- **Opening Essence**:
  - **Furniture-free snippet**: A single `<button>` tag comparing three ways of writing an `onClick` attribute (`<button onClick={sayHello}>Say hello</button>`, `<button onClick={() => sayHello()}>Say hello</button>`, and `<button onClick={sayHello()}>Say hello</button>`) alongside `<form onSubmit={(e) => { e.preventDefault(); }}>`.
  - **Human image**: Writing a phone number on a sticky note and handing the note to a receptionist so they can call you when a visitor arrives (passing the function `sayHello`), versus dialing the phone yourself right at the front desk before any visitor walks in and handing the receptionist the dead receiver (calling `sayHello()` with parentheses during render). For bubbling (`e.stopPropagation()`), a button sitting physically inside a clickable card box so pressing the button also presses the card underneath it unless you tell the event to stop rising. For `e.preventDefault()`, telling the browser not to perform its built-in reflex (reloading the whole page when a form is submitted).
  - **Exact nuance of confusion to state out loud**:
    1. Between `onClick={sayHello}` and `onClick={() => sayHello()}` when no custom arguments are needed: ***"Yes, when the user clicks the button, they do the exact same thing!"*** (one hands React `sayHello` directly; the other hands React a tiny wrapper function that calls `sayHello()` when clicked).
    2. Between `onClick={sayHello}` (no parentheses) and `onClick={sayHello()}` (with parentheses): ***"It may look almost the same on the tag, but it is NOT the same thing at all!"*** Without parentheses, React saves the function and runs it only when the user clicks; with parentheses, JavaScript runs `sayHello()` immediately while building the page and hands `undefined` to `onClick`, so clicking the button later does nothing.
    3. Between `e.stopPropagation()` and `e.preventDefault()`: ***"They both sit on the event object `e` and both sound like 'stop this event', so they look like they do the same job, but they are NOT the same thing!"*** `e.stopPropagation()` stops the event from climbing up to parent tags in your tree; `e.preventDefault()` stops the browser's built-in default action (like reloading the page on `<form>` submit).
- **Theme**: On an interactive news page, clicking a `Like` or `Share` button inside a clickable story card and submitting a comment form below it must run the right handler at the right moment: the `Like` handler must wait for a click instead of firing on page load, clicking `Like` or `Share` inside the card must not accidentally open the card itself, and submitting the comment form must not reload the browser tab.
- **Ways**:
  - Passing a named function reference directly (`onClick={handleLike}`) when the handler takes no custom arguments (or only needs the event object `e`).
  - Passing an inline arrow function (`onClick={() => handleShare('Email')}` or `onClick={(e) => handleShare(e, 'Email')}`) when you need to pass a custom argument (such as `'Email'`) alongside the click.
  - Calling `e.stopPropagation()` inside a child element's handler when the event must not bubble up and trigger a parent element's handler.
  - Calling `e.preventDefault()` inside a `<form onSubmit={...}>` handler when the browser must not perform its default full-page reload on form submission.
- **Recall**:
  - Curly braces `{}` inside JSX evaluate the JavaScript expression inside them while React renders the component (Lecture 03, `Q03 #jsx_expressions`).
  - JSX attributes use `camelCase` names (`className`, `htmlFor`, `onClick`, `onSubmit`) because JSX compiles into JavaScript DOM and React element properties (Lecture 02, `Q02 #jsx`).
  - A child component receives data from its parent through `props` unpacked in its function parameter list (`function ArticleCard({ title, summary })`), and any function declared inside `ArticleCard` can read those props directly (Lecture 08, `Q08 #props`).
- **Runway topics**:
  - How referencing a function value in JavaScript (`const fn = handleLike`) differs from calling a function (`const result = handleLike()`), and what a function without a `return` statement returns (`undefined`).
  - How the browser's event object (`e`) is passed automatically as the first argument to an event handler, and how React wraps native browser events in a cross-browser `SyntheticEvent` object.
  - How DOM event bubbling works (an event on a nested `<button>` fires on the `<button>` first and then climbs up to its parent `<article>`, `<main>`, and `document`), and how a browser's built-in default action on `<form>` submission reloads the page if not cancelled.
  - How the project files (`src/main.jsx`, `src/App.jsx`, `src/components/ArticleCard.jsx`, and `src/components/CommentForm.jsx`) are organized on disk.
- **Example**:
  - **Chosen page**: A compact reader page with one clickable `<ArticleCard>` (`title="New Park Opens Today"`, `summary="The park on Main Street opens at noon."`) containing a `Like` button and a `Share by Email` button, followed by a `<CommentForm>` (`<input name="comment" placeholder="Write a comment" />` and `<button type="submit">Post comment</button>`) below the card.
  - **Why this concept is the reason this page exists**: Every part of this page exists only to exercise one of the four event mechanisms in Question 11: the `Like` button teaches passing a handler reference (`onClick={handleLike}`) vs. calling `handleLike()` during render (Principle 1); the `Share by Email` button inside `ArticleCard` teaches reading the `title` prop in scope and passing `'Email'` via an inline arrow function `onClick={() => handleShare('Email')}` (Principle 2); the clickable `<article onClick={handleOpenCard}>` box around the `Like` and `Share by Email` buttons makes event bubbling physical and visible at once because clicking `Like` inside the card also fires `handleOpenCard` on the card until `e.stopPropagation()` is added (Principle 3); and the `<CommentForm>` below the card has a `<form>` whose submit button triggers a real browser page reload (`?comment=...`) until `e.preventDefault()` is called inside `onSubmit` (Principle 4).
  - **Other candidate pages considered**:
    1. *A bare standalone counter page with a single `+1` button*: Considered and rejected because `Q11` comes before `Q12 #use_state` (so the count cannot update on screen yet), and a single button has no clickable parent container to demonstrate event bubbling (`e.stopPropagation()`) and no `<form>` to demonstrate default browser reload (`e.preventDefault()`).
    2. *A multi-card news feed with `SiteHeader`, `ArticleList`, `Badges`, and three `ArticleCard` items from Lecture 10*: Considered and rejected because `SiteHeader`, `Badges`, and multiple cards add file and prop clutter that has nothing to do with DOM events; trimming the page down to one `ArticleCard` and one `CommentForm` keeps the browser preview minimal while matching the bank row 11 hook directly.

## Principle Thread
- **Anchor**: How React attaches event handler functions to JSX elements, how JavaScript function references and inline arrow wrappers control when a handler runs and what arguments it receives, and how the `SyntheticEvent` object (`e`) controls upward DOM bubbling (`e.stopPropagation()`) and built-in browser default actions (`e.preventDefault()`).
- **Axis**: From attaching a single click handler reference, to passing arguments with an inline arrow wrapper, to stopping upward bubbling between nested elements, to stopping the browser's built-in page reload on form submission:
  1. Passing a function reference (`onClick={handleLike}`) to a `camelCase` event prop instead of calling `handleLike()` during render (Principle 1).
  2. Reading component props inside a handler and using an inline arrow function (`onClick={() => handleShare('Email')}`) to pass custom arguments on click (Principle 2).
  3. Stopping an event on a nested `<button>` from bubbling up and triggering a parent `<article>`'s click handler with `e.stopPropagation()` (Principle 3).
  4. Stopping the browser's built-in full-page reload when submitting a `<form>` with `e.preventDefault()` (Principle 4).
- **Why This Axis**: The sequence follows cause before effect and grows the page one element at a time:
  1. First, the reader wires a single `Like` button (`onClick={handleLike}`) and sees why writing `handleLike` without parentheses hands the function to React for later, whereas writing `handleLike()` runs it immediately during render (Principle 1).
  2. Second, once the reader knows that `onClick={fn()}` calls `fn` during render, a natural question arises: *"Then how do I pass an argument like `'Email'` to `handleShare('Email')` without calling it during render?"* Wrapping the call in an inline arrow function (`onClick={() => handleShare('Email')}`) solves that exact problem while also reading `title` from `ArticleCard`'s props (Principle 2).
  3. Third, making the `<article>` card itself clickable (`onClick={handleOpenCard}`) reveals that clicking `Like` or `Share by Email` inside the card fires both the button handler and the parent card handler because DOM events bubble upward, which introduces the event parameter `e` and `e.stopPropagation()` (Principle 3).
  4. Fourth, adding the `<CommentForm>` below the card introduces the second method on `e`, `e.preventDefault()`, and contrasts stopping upward tree propagation (`e.stopPropagation()`) against cancelling the browser's native form-reload behavior (`e.preventDefault()`) (Principle 4).

## Principles

### Principle 1: Pass a Function Reference to a `camelCase` Event Prop Instead of Calling It During Render
- **Handle**: `pass-handler-reference`
- **Rule**: Attach event handlers using `camelCase` JSX props (`onClick={handleLike}`) and pass the function reference without parentheses (`handleLike`), never a function call (`handleLike()`).
- **Opening Essence**:
  - **Furniture-free snippet**:
    - `<button onClick={sayHello}>Say hello</button>`
    - `<button onClick={sayHello()}>Say hello</button>`
  - **Human image**: Writing a phone number on a note (`sayHello`) and handing the note to React so React can call that number when the user clicks the button, versus dialing the phone yourself (`sayHello()`) while the page is still being built and handing React the finished call's empty result (`undefined`).
  - **Exact nuance of confusion to state out loud**: ***"Writing `onClick={sayHello}` and `onClick={sayHello()}` only differs by two tiny parentheses `()`, so they look almost the same on the tag, but it is NOT the same thing at all!"*** Without `()`, you pass the function itself to React so it waits for a click. With `()`, JavaScript calls `sayHello()` immediately inside `{}` while rendering the page, prints to the Console before anyone touches the mouse, and hands its return value (`undefined`) to `onClick`, leaving the button dead when clicked.
- **Root Distinction**:
  - *Junior blurred view*: Because HTML attributes write `onclick="handleLike()"` with parentheses, writing `onClick={handleLike()}` in JSX tells React what to run when the button is clicked.
  - *Senior grounding*: In JSX, `{}` is evaluated immediately during rendering; `onClick={handleLike}` passes the function object to React to call on a future click, whereas `onClick={handleLike()}` invokes `handleLike` during render and passes its return value (`undefined`) to `onClick`.
- **Real Beginner Mistake (events, in order)**:
  1. A developer declares `function handleLike() { console.log('Liked: New Park Opens Today'); }` inside `ArticleCard.jsx`.
  2. In the returned JSX, the developer writes `<button onClick={handleLike()}>Like</button>` with parentheses after `handleLike`, or writes `<button onclick={handleLike}>Like</button>` with a lowercase `c`.
  3. With `onClick={handleLike()}`, React calls `ArticleCard` on initial page load, evaluates `{handleLike()}` immediately, and logs `'Liked: New Park Opens Today'` in the Console before the user clicks anything.
  4. Because `handleLike` has no `return` statement, `handleLike()` evaluates to `undefined`, so the button receives `onClick={undefined}`.
  5. When the user clicks the `Like` button in the browser, nothing runs and zero new messages appear in the Console.
  6. With lowercase `onclick={handleLike}`, React logs a Console error (`Invalid event handler property \`onclick\`. Did you mean \`onClick\`?`) and ignores the handler completely.
- **Interview Depth**:
  - Why old HTML `onclick="handleLike()"` worked with parentheses while JSX `onClick={handleLike()}` does not: in HTML, the quotes `"handleLike()"` hold a string of code that the browser wraps into an anonymous function for later; in JSX, curly braces `{handleLike()}` execute JavaScript immediately during the component's render pass.
  - What happens if you pass a quoted string `onClick="handleLike()"` in JSX: React logs `Expected \`onClick\` listener to be a function, instead got a value of \`string\` type.` in the Console and never runs the code.
  - Naming convention from `react.dev`: by convention, event handler functions inside a component are named `handle` followed by the event or action name (`handleClick`, `handleLike`, `handleCommentSubmit`), while the JSX prop on a built-in element starts with `on` (`onClick`, `onSubmit`).
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: Any `onclick` attribute on `<button class="like-btn">Like</button>` in the browser's `Elements` panel even when `onClick={handleLike}` works properly.
    - **Who supplies it**: React attaches its own delegated event listener at the root DOM container (`#root`) created by `createRoot` instead of writing inline `onclick` HTML attributes onto individual DOM nodes.
    - **What JavaScript and React do**:
      1. During render, `ArticleCard` evaluates `{handleLike}` to the function reference in memory and stores it on the `<button>` React element's `props.onClick`.
      2. React commits `<button class="like-btn">Like</button>` to the DOM without an inline HTML `onclick` attribute and registers the click listener through its root delegation system on `#root`.
      3. When the user clicks the `<button>`, React catches the click at `#root`, looks up the `<button>`'s `onClick` handler (`handleLike`), and calls `handleLike(e)`.
- **React Does**:
  - When `ArticleCard` renders `<button className="like-btn" onClick={handleLike()}>Like</button>`, the Console immediately logs `Liked: New Park Opens Today` on initial page load; clicking `<button class="like-btn">Like</button>` afterward logs nothing (`[]`).
  - When `ArticleCard` renders `<button className="like-btn" onclick={handleLike}>Like</button>` with a lowercase `c`, the Console logs `Invalid event handler property \`onclick\`. Did you mean \`onClick\`?` on page load, and clicking the button logs nothing.
  - When `ArticleCard` renders `<button className="like-btn" onClick={handleLike}>Like</button>`, initial page load logs zero messages in the Console, the `Elements` panel shows `<article class="card"><h3>New Park Opens Today</h3><p>The park on Main Street opens at noon.</p><button class="like-btn">Like</button></article>`, and each click on the `Like` button logs `Liked: New Park Opens Today`.
- **Example Step**: Creates `src/App.jsx` and `src/components/ArticleCard.jsx` rendering the `'New Park Opens Today'` story card with its first interactive element: `<button className="like-btn" onClick={handleLike}>Like</button>`, where `handleLike` logs `'Liked: New Park Opens Today'`.
- **Code names**: `src/App.jsx`, `src/components/ArticleCard.jsx`, `ArticleCard`, `handleLike`, `onClick`, `onclick`, `onClick={handleLike}`, `onClick={handleLike()}`, `'Liked: New Park Opens Today'`, `undefined`, `Invalid event handler property \`onclick\`. Did you mean \`onClick\`?`, `Expected \`onClick\` listener to be a function, instead got a value of \`string\` type.`
- **Visual idea**: Side-by-side browser and Console comparison of `onClick={handleLike()}` (firing `'Liked: New Park Opens Today'` on page load and doing nothing when clicked) versus `onClick={handleLike}` (quiet Console on page load and logging `'Liked: New Park Opens Today'` when the user clicks `Like`).

### Principle 2: Wrap Calls in an Inline Arrow Function (`() => ...`) When Passing Custom Arguments
- **Handle**: `inline-arrow-for-arguments`
- **Rule**: Declare event handlers inside the component so they can read its props directly, and wrap a handler call in an inline arrow function (`onClick={() => handleShare('Email')}`) whenever you need to pass a custom argument on click.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - `<button onClick={sayHello}>Say hello</button>`
    - `<button onClick={() => sayHello()}>Say hello</button>`
    - `<button onClick={() => greet('John')}>Greet John</button>`
  - **Human image**: Putting a tiny envelope `() =>` around `greet('John')`. If you write `greet('John')` bare inside `{}`, JavaScript opens and runs it immediately while building the page; when you seal `greet('John')` inside the arrow wrapper `() => greet('John')`, you hand React the sealed envelope so React opens and runs `greet('John')` only when the user clicks.
  - **Exact nuance of confusion to state out loud**:
    1. First, compare `onClick={sayHello}` and `onClick={() => sayHello()}` with no arguments: ***"Yes, when clicked, these two do the exact same thing!"*** Both hand React a function to run later.
    2. Next, compare `onClick={greet('John')}` and `onClick={() => greet('John')}`: ***"Wait: in Principle 1 we saw that parentheses `()` call the function immediately during render! Why are parentheses `()` suddenly allowed inside `onClick={() => greet('John')}`? It may look like it breaks Principle 1, but it is NOT the same thing!"*** In `onClick={greet('John')}`, the call sits at the top level of `{}` so it runs during render. In `onClick={() => greet('John')}`, the `() =>` at the front creates a brand-new wrapper function and hands that wrapper function to React without running its body; `greet('John')` inside the wrapper runs only when the user clicks the button!
- **Root Distinction**:
  - *Junior blurred view*: Any parentheses `()` inside `onClick={...}` are either always fine or always forbidden, so passing `'Email'` to `handleShare('Email')` requires `onClick={handleShare('Email')}`.
  - *Senior grounding*: What sits directly inside `onClick={...}` must evaluate to a function value during render; `handleShare('Email')` evaluates to `undefined` during render, whereas `() => handleShare('Email')` evaluates to an uncalled arrow function during render whose body calls `handleShare('Email')` when clicked.
- **Real Beginner Mistake (events, in order)**:
  1. A developer adds a `Share by Email` button to `ArticleCard.jsx` and writes `function handleShare(platform) { console.log('Shared ' + title + ' by ' + platform); }`.
  2. Because `handleShare` needs the argument `'Email'`, the developer writes `<button onClick={handleShare('Email')}>Share by Email</button>` without an `() =>` arrow wrapper.
  3. While React renders `ArticleCard` on page load, JavaScript evaluates `{handleShare('Email')}` immediately and logs `'Shared New Park Opens Today by Email'` in the Console before the user clicks anything.
  4. `handleShare('Email')` returns `undefined`, so `onClick` receives `undefined`.
  5. When the user clicks `Share by Email` in the browser, nothing happens.
- **Interview Depth**:
  - How `handleLike` and `handleShare` read `title` without `title` being passed through `onClick`: because `handleLike` and `handleShare` are declared inside `function ArticleCard({ title, summary })`, JavaScript lexical scope (closure) gives both functions direct access to the `title` prop from that render.
  - When to use `onClick={handleLike}` vs. `onClick={() => handleShare('Email')}`: when no custom argument is needed, `onClick={handleLike}` is cleaner and avoids creating an extra wrapper function; when you must pass a custom argument like `'Email'` (or an item ID), `onClick={() => handleShare('Email')}` creates a function that remembers that argument and calls `handleShare('Email')` on click.
  - How to access both the React event object `e` and a custom argument inside an inline arrow function: accept `e` in the arrow function's parameter list and forward it (`onClick={(e) => handleShare(e, 'Email')}`).
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: `title` passed as an argument inside `onClick={handleLike}` or `onClick={() => handleShare('Email')}`, even though both handlers print `'New Park Opens Today'`.
    - **Who supplies it**: JavaScript lexical scope inside `function ArticleCard({ title, summary })` lets any function declared inside `ArticleCard` read `title` directly from the enclosing component parameters.
    - **What JavaScript and React do**:
      1. `App` renders `<ArticleCard title="New Park Opens Today" summary="The park on Main Street opens at noon." />`.
      2. Inside `ArticleCard`, `{ title, summary }` unpacks `title` as `'New Park Opens Today'`, and `handleLike` and `handleShare` are created inside that same function scope.
      3. When the user clicks `Share by Email`, React runs the arrow function `() => handleShare('Email')`, which calls `handleShare('Email')`, reads `title` (`'New Park Opens Today'`) from the surrounding `ArticleCard` scope, and logs `'Shared New Park Opens Today by Email'`.
- **React Does**:
  - When `ArticleCard` writes `<button className="share-btn" onClick={handleShare('Email')}>Share by Email</button>`, the Console immediately logs `Shared New Park Opens Today by Email` on page load, and clicking the button logs nothing.
  - When `ArticleCard` writes `<button className="share-btn" onClick={() => handleShare('Email')}>Share by Email</button>`, page load logs zero messages in the Console, and clicking `Share by Email` logs `Shared New Park Opens Today by Email`.
- **Example Step**: Updates `src/components/ArticleCard.jsx` so `handleLike` reads the `title` prop (`console.log('Liked: ' + title)`) and adds the second button `<button className="share-btn" onClick={() => handleShare('Email')}>Share by Email</button>` to `ArticleCard.jsx`.

### Principle 3: Use `e.stopPropagation()` When a Child Event Should Not Bubble Up to a Parent Handler
- **Handle**: `stop-propagation-bubbling`
- **Rule**: When an interactive child element (`<button>`) sits inside a clickable parent element (`<article onClick={...}>`), accept the `SyntheticEvent` parameter `e` in the child handler and call `e.stopPropagation()` so the event does not bubble up and fire the parent handler too.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - `<div onClick={openBox}><button onClick={likeItem}>Like</button></div>`
    - `<div onClick={openBox}><button onClick={(e) => { e.stopPropagation(); likeItem(); }}>Like</button></div>`
  - **Human image**: A button physically glued onto the front of a cardboard box. When you press the button on the box with your finger, your finger also pushes the box behind it. In the browser, an event starts on the innermost tag you clicked (`<button>`) and then rises upward like an air bubble through water (`<button>` -> `<article>` -> `<main>`), firing every `onClick` handler along the path unless you pop the bubble with `e.stopPropagation()`.
  - **Exact nuance of confusion to state out loud**: ***"In your code, `<button onClick={handleLike}>` and `<article onClick={handleOpenCard}>` are two separate `onClick` props on two separate tags, so it looks like clicking the button should only run the button's handler, but in the browser DOM it is NOT isolated like that!"*** Because `<button>` sits inside `<article>`, clicking `<button>` physically happens inside `<article>` too. First `<button>`'s `onClick` runs, and then the click bubbles up to `<article>` and runs `<article>`'s `onClick` right after it, unless the child calls `e.stopPropagation()`.
- **Root Distinction**:
  - *Junior blurred view*: Clicking `<button onClick={handleLike}>` only triggers `onClick` on `<button>`, because `<article onClick={handleOpenCard}>` is a different tag.
  - *Senior grounding*: All DOM events in React (except `onScroll`) bubble upward from the clicked target element through every ancestor in the tree; without `e.stopPropagation()` on the child handler, a single click on `<button>` executes the child handler first and the ancestor `<article>` handler second.
- **Real Beginner Mistake (events, in order)**:
  1. A developer makes the whole `<article className="card" onClick={handleOpenCard}>` clickable so clicking the card logs `'Opened: New Park Opens Today'`.
  2. Inside that `<article>`, the `Like` button has `onClick={handleLike}` and the `Share by Email` button has `onClick={() => handleShare('Email')}`, neither of which calls `e.stopPropagation()`.
  3. The user clicks the `Like` button intending only to like the story without opening the card.
  4. React runs `handleLike` on the `<button>` first, logging `'Liked: New Park Opens Today'`.
  5. The click event then bubbles up from `<button>` to its parent `<article>` and runs `handleOpenCard`, logging `'Opened: New Park Opens Today'` right after `'Liked: New Park Opens Today'`.
- **Interview Depth**:
  - What `e` is in React: a cross-browser `SyntheticEvent` wrapper that React passes as the first argument to every event handler, providing standard W3C properties and methods (`e.stopPropagation()`, `e.preventDefault()`, `e.target`, `e.currentTarget`) plus `e.nativeEvent` pointing to the underlying browser `MouseEvent` (`e.nativeEvent instanceof MouseEvent === true`).
  - The exact difference between `e.target` (*The Clicked Element*) and `e.currentTarget` (*The Listening Element*): when the user clicks `<button>` inside `<article onClick={handleOpenCard}>` without `e.stopPropagation()`, inside `handleOpenCard` on `<article>`, `e.target.tagName` is `'BUTTON'` (the inner element where the click originated) while `e.currentTarget.tagName` is `'ARTICLE'` (the outer element whose handler is currently running).
  - The three phases of DOM event dispatch and `onClickCapture`:
    1. **Capture phase (top-down)**: travels from the root down to the clicked child; in React, you opt into this phase by appending `Capture` to the prop name (`onClickCapture`), which runs before the child's `onClick` even if the child calls `e.stopPropagation()`.
    2. **Target phase**: reaches the clicked element itself.
    3. **Bubbling phase (bottom-up)**: rises from the clicked element back up to the root (`onClick` runs here by default).
  - Which event in React does not bubble: `onScroll` fires only on the specific DOM element being scrolled and never bubbles to parent elements.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: Any argument passed inside `<button onClick={handleLike}>` in the JSX markup, even though `function handleLike(e)` receives the event object `e` as its first parameter.
    - **Who supplies it**: React automatically creates the `SyntheticEvent` object `e` when the user clicks and passes `e` as the first argument when calling `handleLike(e)`.
    - **What JavaScript and React do**:
      1. When the user clicks `<button className="like-btn" onClick={handleLike}>`, React wraps the browser's native click event into a `SyntheticEvent` object `e`.
      2. React calls `handleLike(e)`, passing that `SyntheticEvent` as the first argument automatically; for an inline arrow function `onClick={(e) => handleShare(e, 'Email')}`, React passes `e` into `(e) => ...` which forwards `e` and `'Email'` to `handleShare(e, 'Email')`.
      3. When `handleLike(e)` or `handleShare(e, 'Email')` calls `e.stopPropagation()`, React marks the `SyntheticEvent` as stopped and skips calling `handleOpenCard` on the parent `<article>`.
- **React Does**:
  - When `<button className="like-btn" onClick={handleLike}>Like</button>` inside `<article className="card" onClick={handleOpenCard}>` does not call `e.stopPropagation()`, a single click on `Like` logs two messages in the Console in exact order: `Liked: New Park Opens Today` followed by `Opened: New Park Opens Today`.
  - When `handleLike(e)` and `handleShare(e, platform)` call `e.stopPropagation()`, clicking `Like` logs only `Liked: New Park Opens Today`, clicking `Share by Email` logs only `Shared New Park Opens Today by Email`, and clicking the card heading `<h3>New Park Opens Today</h3>` logs `Opened: New Park Opens Today`.
  - When `<article onClickCapture={handleCardCapture} onClick={handleOpenCard}>` wraps `<button onClick={handleLike}>` (where `handleLike` calls `e.stopPropagation()`), clicking `Like` logs `Capture: card` first and `Liked: New Park Opens Today` second, while `handleOpenCard` does not run.
- **Example Step**: Adds `onClick={handleOpenCard}` to `<article className="card">` in `src/components/ArticleCard.jsx`, updates `handleLike(e)` to accept `e` and call `e.stopPropagation()`, and updates `handleShare(e, platform)` and `onClick={(e) => handleShare(e, 'Email')}` to accept `e` and call `e.stopPropagation()`.
- **Code names**: `src/components/ArticleCard.jsx`, `handleOpenCard`, `handleLike`, `handleShare`, `e`, `e.stopPropagation()`, `e.target`, `e.currentTarget`, `e.nativeEvent`, `onClickCapture`, `onScroll`, `'Opened: New Park Opens Today'`, `'Liked: New Park Opens Today'`, `'Shared New Park Opens Today by Email'`
- **Visual idea**: A `tree` propagation flow diagram and side-by-side Console comparison showing a click on `<button>Like</button>` inside `<article>` without `e.stopPropagation()` (logging both `'Liked: New Park Opens Today'` and `'Opened: New Park Opens Today'`) versus with `e.stopPropagation()` (stopping at `<button>` and logging only `'Liked: New Park Opens Today'`).

### Principle 4: Use `e.preventDefault()` to Stop the Browser's Built-In Default Action on Form Submit
- **Handle**: `prevent-default-browser-action`
- **Rule**: Attach a submit handler to `<form onSubmit={handleCommentSubmit}>` and call `e.preventDefault()` inside it to stop the browser from reloading the page when the form is submitted.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - `<form onSubmit={handleSubmit}><button type="submit">Post</button></form>` without `e.preventDefault()`
    - `<form onSubmit={(e) => { e.preventDefault(); handleSubmit(); }}><button type="submit">Post</button></form>` with `e.preventDefault()`
  - **Human image**: A browser `<form>` has an old built-in reflex from the 1990s web: as soon as you press its submit button, the browser packs the inputs into the URL bar (`?comment=...`) and reloads the entire page from scratch, wiping out everything in JavaScript memory. Calling `e.preventDefault()` tells the browser: *"Cancel your built-in reload reflex; my JavaScript handler will take care of this submission."*
  - **Exact nuance of confusion to state out loud**: ***"Both `e.stopPropagation()` and `e.preventDefault()` are methods on `e` that sound like 'stop the event', so developers constantly mix them up, but they are NOT the same thing at all!"***
    - `e.stopPropagation()` stops an event from climbing up to **parent tags** in your component tree (it does **not** stop a `<form>` from reloading the page).
    - `e.preventDefault()` stops the **browser's built-in default action** for that HTML tag, such as a `<form>` reloading the page on submit or an `<a href="...">` link navigating away.
- **Root Distinction**:
  - *Junior blurred view*: Writing `onSubmit={handleCommentSubmit}` on a `<form>` automatically stops the browser from reloading the page, or calling `e.stopPropagation()` inside `onSubmit` prevents the reload.
  - *Senior grounding*: HTML `<form>` elements have a native browser default action that navigates and reloads the document on submit; only `e.preventDefault()` cancels that native browser behavior, whereas `e.stopPropagation()` only controls upward bubbling in the DOM tree.
- **Real Beginner Mistake (events, in order)**:
  1. A developer creates `src/components/CommentForm.jsx` with `<form className="comment-form" onSubmit={handleCommentSubmit}>`, an `<input name="comment" placeholder="Write a comment" />`, and `<button type="submit">Post comment</button>`.
  2. Inside `handleCommentSubmit`, the developer writes `console.log('Comment posted')` without calling `e.preventDefault()`.
  3. The user types `'See you at the park!'` into the comment input and clicks `Post comment` (or presses `Enter`).
  4. `handleCommentSubmit` runs briefly, and then the browser executes its built-in `<form>` submission action.
  5. The browser navigates to `http://localhost:5173/?comment=See+you+at+the+park%21`, reloads the entire page, clears the Console log and client memory, and resets the page from scratch.
- **Interview Depth**:
  - Why attaching `onSubmit={handleCommentSubmit}` to `<form>` is better than attaching `onClick` only to the submit `<button>`: `<form onSubmit={...}>` catches both clicking `<button type="submit">` with a mouse and pressing the `Enter` key inside any `<input>` field in the form.
  - Side-by-side contrast between `e.stopPropagation()` and `e.preventDefault()`:
    - `e.stopPropagation()`: stops the event from bubbling to parent event handlers in the tree; does not stop browser form reload or link navigation.
    - `e.preventDefault()`: stops the browser's built-in default behavior for the element (`<form>` page reload on submit, `<a href>` navigation on click); does not stop the event from bubbling to parent handlers.
  - Forward note on React 19: when using classic event handlers (`<form onSubmit={handleCommentSubmit}>`), you must call `e.preventDefault()` yourself; in Lesson 41 (`Q41 #form_actions`), React 19's `<form action={fn}>` calls `e.preventDefault()` automatically under the hood.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: Any `onClick` prop on `<button type="submit">Post comment</button>` inside `CommentForm.jsx`.
    - **Who supplies it**: The browser's native HTML form mechanism fires a `submit` event on the enclosing `<form>` whenever a `<button type="submit">` inside it is clicked or the user presses `Enter` in an `<input>`.
    - **What JavaScript and React do**:
      1. The user clicks `<button type="submit">Post comment</button>` (or presses `Enter` inside `<input name="comment" />`).
      2. The browser dispatches a `submit` event on `<form className="comment-form">`, which React catches and passes as `SyntheticEvent` `e` into `handleCommentSubmit(e)`.
      3. `handleCommentSubmit(e)` calls `e.preventDefault()`, cancelling the browser's native page reload, and then logs `'Comment posted'` while the URL stays at `http://localhost:5173/`.
- **React Does**:
  - When `handleCommentSubmit` omits `e.preventDefault()` and the user submits the form with `'See you at the park!'`, Chrome navigates from `http://localhost:5173/` to `http://localhost:5173/?comment=See+you+at+the+park%21` and reloads the document, clearing the previous Console output.
  - When `handleCommentSubmit(e)` calls `e.preventDefault()` and logs `console.log('Comment posted')`, submitting the form keeps the URL at `http://localhost:5173/`, does not reload the document, and logs `Comment posted` in the Console with zero errors.
- **Example Step**: Creates `src/components/CommentForm.jsx` with `<form className="comment-form" onSubmit={handleCommentSubmit}>`, `<input name="comment" placeholder="Write a comment" />`, and `<button type="submit">Post comment</button>`, and imports and renders `<CommentForm />` below `<ArticleCard />` inside `src/App.jsx`.
- **Code names**: `src/components/CommentForm.jsx`, `src/App.jsx`, `CommentForm`, `handleCommentSubmit`, `onSubmit`, `e`, `e.preventDefault()`, `e.stopPropagation()`, `<form className="comment-form" onSubmit={handleCommentSubmit}>`, `<input name="comment" placeholder="Write a comment" />`, `<button type="submit">Post comment</button>`, `'Comment posted'`, `'See you at the park!'`, `http://localhost:5173/?comment=See+you+at+the+park%21`
- **Visual idea**: Side-by-side browser comparison of submitting `<CommentForm />` without `e.preventDefault()` (URL changing to `localhost:5173/?comment=See+you+at+the+park%21` and reloading the page) versus with `e.preventDefault()` (URL staying at `localhost:5173` and Console logging `'Comment posted'`), plus a 2-branch `tree` contrasting `e.stopPropagation()` vs. `e.preventDefault()`.

## Interview Points
1. React attaches event handlers declaratively on JSX tags using `camelCase` props such as `onClick` and `onSubmit`, and you must pass a function reference (`onClick={handleLike}`) rather than calling the function with parentheses (`onClick={handleLike()}`), because calling it inside `{}` executes the function immediately during render and passes `undefined` to `onClick`.
2. Event handlers declared inside a component can read the component's props directly through JavaScript lexical scope, and when you need to pass a custom argument on click, you wrap the call in an inline arrow function (`onClick={() => handleShare('Email')}` or `onClick={(e) => handleShare(e, 'Email')}`) so React receives a function to call when the user clicks.
3. React passes a cross-browser `SyntheticEvent` object (`e`) as the first argument to every handler; because DOM events bubble upward from a child element (`<button>`) to its parent elements (`<article>`), calling `e.stopPropagation()` inside the child handler prevents the event from reaching and firing ancestor handlers (while `onClickCapture` lets a parent intercept an event during the downward capture phase).
4. Calling `e.preventDefault()` inside a handler such as `<form onSubmit={handleCommentSubmit}>` cancels the browser's built-in default action (stopping a form submission from reloading the page or an `<a>` link from navigating), which is distinct from `e.stopPropagation()` (which only stops upward bubbling in the component tree).
