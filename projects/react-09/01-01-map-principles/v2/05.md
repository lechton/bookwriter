## Authorized Scope
Lecture 05 teaches how to split React components into separate files using JavaScript `export` and `import` statements. Every `.jsx` file is an isolated module whose functions stay private to that file until exported, and another file can use them only by importing them. JavaScript offers two ways to export components from a file: a file can have at most one default export (`export default`) for its main component, and any number of named exports (`export function`) when one file holds multiple components or helpers. How a file exports a component determines how another file must import it: a default export is imported without curly braces under any local name the importing file chooses, while a named export is imported inside curly braces using its exact exported name, or renamed explicitly with `as`. Every relative import path (`./` or `../`) starts from the folder of the file that writes the `import`, while package names such as `'react'` have no dot and come from installed packages. Because Q05 comes before `props` (Q08) and `children` (Q09) in the Version 4 curriculum, every component in this lesson is a simple component with no props, continuing directly from Lecture 04.

## Principle Thread
- **Anchor**: Every file is a private module: its functions stay inside that file until exported, and another file can use them only by importing them.
- **Axis**: The four steps of splitting components into a `components/` folder in causal order: opening a file with `export` and `import` (Principle 1), choosing between one default export and multiple named exports in the exporting file (Principle 2), matching the `import` line and local name in the importing file (Principle 3), and starting every relative path from the importing file's folder (Principle 4).
- **Why This Axis**: Placing Principle 2 (why a file has one default export vs. many named exports) *before* Principle 3 (how the importing file uses curly braces and renames imports) teaches **cause before effect**. Once the reader has seen `ArticleCard.jsx` exporting one default component and `Badges.jsx` exporting two named components (`LiveBadge` and `NewBadge`), they immediately understand why importing from `ArticleCard.jsx` needs no curly braces and allows any name, whereas importing from `Badges.jsx` requires curly braces with the exact name (or `as` to rename).
- **Spoken Preview**: Everything in this lesson comes down to one idea: each file is a private module, and its functions cross to another file only through export and import. First, each file keeps its functions private until exported: a component moved to its own file is hidden from `App.jsx` until the new file exports it and `App.jsx` imports it, while helper functions that only one file needs stay unexported. Second, a file can have at most one default export for its main component and unlimited named exports when one file holds multiple smaller components. Third, how you export a component determines how you must import it: write no curly braces for a default export under any name you choose, and write curly braces with the exact exported name for a named export, or rename it with `as`. Fourth, every relative import path starts from the folder of the file that writes the import, using dot-slash for the same folder, dot-dot-slash for the folder above, and no dot for an installed package.
- **Closing Line**: One private module per file, one default or many named exports, an import that matches the export, and a path that starts from where you stand.

## Principles

### Principle 1: Modules: Each File Keeps Its Names Private Until Exported
- **Handle**: `file-is-module`
- **Thread Step**: Connecting a new component file to `App.jsx` with `export` and `import`
- **Rule**: Export a component from its own file with `export`, import it with `import` in every file that uses it, and leave internal helper functions unexported.
- **Root Distinction**:
  - **Junior Blurred View**: *"Both `App.jsx` and `ArticleCard.jsx` sit in the same project, so if I cut the card function out of `App.jsx` and paste it into `ArticleCard.jsx`, `App` will still find it."*
  - **Senior Root Grounding (`###` Heading)**: `### Old HTML script tags share one global space, but each module file keeps its names private`
- **Reader Question**: "I moved my card component into its own file. Why does `App.jsx` crash and say the card is not defined?"
- **Real Beginner Mistake (Daily Coding)**: Moving `ArticleCard` out of `App.jsx` into `src/components/ArticleCard.jsx` without adding `export` in the card file and `import` in `App.jsx`, which crashes the page with `ReferenceError: ArticleCard is not defined`.
- **Interview Depth (Nuance / Follow-Up)**: Why module privacy is helpful (a helper function like `getHeadline` used only inside the card file stays unexported so no other file can clash with it).
- **React Does**: Every `.jsx` file is a private module. Moving the card function into a new file hides its name from `App.jsx` until the card file exports it and `App.jsx` imports it.
- **River Progression**: Moves `ArticleCard` out of `src/App.jsx` into `src/components/ArticleCard.jsx` with an unexported `getHeadline` helper inside the card file.
- **Pertinent Division & Visual Comparison**:
  - `tree`: Old `<script>` tags sharing one global space (`!`) vs. module files keeping their functions private until exported (`+`).
  - `::: row` / `::: col` UI Browser & Console Preview: Moved without `export` and `import` (`page size=mini` blank + `devconsole` `ReferenceError: ArticleCard is not defined`) vs. Connected with `export default` and `import` (`page size=mini` showing `Latest Articles` and `New Park Opens Today`).
  - `tree dir=right`: Unexported private helper (`function getHeadline`) vs. Exported component (`export default function ArticleCard`).
- **Drafted Principle Box**:
  - **Title**: `Principle 1: Modules: Each File Keeps Its Names Private Until Exported`
  - **Rule**: *Export a component with `export` and import it with `import` in every file that uses it. Leave internal helper functions unexported.*

### Principle 2: Default vs. Named Exports: One Default for the Main Component, Named Exports for Multiple Components
- **Handle**: `default-or-named`
- **Thread Step**: Choosing between one default export and multiple named exports inside the exporting file
- **Rule**: Give a file at most one default export for its main component and use named exports when one file exports multiple components. Always give every component function a name.
- **Root Distinction**:
  - **Junior Blurred View**: *"`export default` just means 'export this function', so when I put two badges in the same file, I should write `export default` in front of both of them."*
  - **Senior Root Grounding (`###` Heading)**: `### A file can have only one default export, so a file with multiple components exports them by name`
- **Reader Question**: "Why does adding a second `export default` in my badge file stop the build, and why does JavaScript have two different ways to export?"
- **Real Beginner Mistake (Daily Coding)**: Putting `export default` on two functions (`LiveBadge` and `NewBadge`) in the same file, which stops the build with `A module cannot have multiple default exports`.
- **Interview Depth (Nuance / Follow-Up)**: When teams choose a default export (one main component per file) vs. named exports (multiple small components in one file), and why every component function needs a name so React DevTools does not display `"default"`.
- **React Does**: JavaScript allows at most one `export default` per file and any number of named `export function` declarations.
- **River Progression**: Creates `src/components/Badges.jsx` to hold two badges, `LiveBadge` and `NewBadge`, exporting both as named exports (`export function LiveBadge` and `export function NewBadge`).
- **Pertinent Division & Visual Comparison**:
  - `::: row` / `::: col` Overlay & Code Comparison: Two `export default` lines in `Badges.jsx` (`overlay` showing `A module cannot have multiple default exports`) vs. Two named exports (`export function LiveBadge` and `export function NewBadge`).
  - `tree`: One main component in its own file (`export default`) vs. Several small components in one file (`export function`) vs. Anonymous default export (`!`).
- **Drafted Principle Box**:
  - **Title**: `Principle 2: Default and Named Exports: One Default at Most, Named Exports for Multiple Components`
  - **Rule**: *Give a file at most one default export for its main component and use named exports when a file holds multiple components. Always give every component function a name.*

### Principle 3: Matching Imports to Exports: No Braces for Default, Curly Braces for Named
- **Handle**: `import-matches-export`
- **Thread Step**: Matching the import line and local name in the importing file to how the component was exported
- **Rule**: Import a default export without curly braces under any name you choose, and import a named export inside curly braces using its exact exported name, or rename it explicitly with `as`.
- **Root Distinction**:
  - **Junior Blurred View**: *"Sometimes I see an import with curly braces and sometimes without curly braces. Both lines import a component, so the curly braces and the imported name must be interchangeable."*
  - **Senior Root Grounding (`###` Heading)**: `### How a file exports a component determines whether the importing file uses curly braces and whether it can pick a new name`
- **Reader Question**: "When do I put curly braces around an imported component name, and why can I rename a default import freely while a named import requires the exact name or `as`?"
- **Real Beginner Mistake (Daily Coding)**: Importing a named export (`LiveBadge` from `Badges.jsx`) without curly braces (`import LiveBadge from './Badges.jsx'`), which asks `Badges.jsx` for a `default` export it does not have and stops the page before React runs.
- **Sub-Step 3B (Merged — Renaming an Imported Component Across Two Files)**:
  - **Reader Eye-Check ("I Do Not See `X` in the Other Code!")**:
    - When `ArticleCard.jsx` defines `export default function ArticleCard()` and `App.jsx` writes `import StoryCard from './components/ArticleCard.jsx'`, the reader's eye checks `ArticleCard.jsx` and asks: *"Wait—it says `import StoryCard`, and I do not see `StoryCard` anywhere in `ArticleCard.jsx`! Where did `StoryCard` come from?"*
    - Likewise, when `Badges.jsx` defines `LiveBadge` and `NewBadge`, `BreakingBadge` does not exist anywhere in `Badges.jsx`.
  - **Who Invents the Name & What JavaScript Actually Does Step-by-Step**:
    1. **For a default import (`import StoryCard`)**: `StoryCard` does not exist in `ArticleCard.jsx`—it is a **brand-new local nickname invented on the spot by `App.jsx`**. Because `import StoryCard` has **no curly braces**, JavaScript does **not** search `ArticleCard.jsx` for a function named `StoryCard`. Instead, leaving out the curly braces tells JavaScript: *"Go to `ArticleCard.jsx`, grab whatever single function is marked `export default` (which is `ArticleCard`), and give it the brand-new local nickname `StoryCard` inside `App.jsx` so it can be rendered as `<StoryCard />`."*
    2. **For a named import (`import { LiveBadge as BreakingBadge }`)**: Because curly braces `{ }` **do** search `Badges.jsx` by name (since `Badges.jsx` has multiple named exports), writing `import { BreakingBadge }` alone searches `Badges.jsx` for `BreakingBadge`, finds nothing, and crashes. Inside `{ }`, you must write the existing exported name first (`LiveBadge`) so JavaScript finds it in `Badges.jsx`, followed by `as BreakingBadge` to give it its new local nickname.
- **Interview Depth (Nuance / Follow-Up)**: Showing the complete two-file handshake and unwritten-bridge explanation for renaming both styles: why a default export (`ArticleCard.jsx`) has only one default component so `App.jsx` can invent any local name (`import StoryCard from './components/ArticleCard.jsx'` and render `<StoryCard />`), whereas `Badges.jsx` has multiple named exports (`LiveBadge` and `NewBadge`) so `ArticleCard.jsx` must name the exact export inside curly braces first and rename it with `as` (`import { LiveBadge as BreakingBadge, NewBadge } from './Badges.jsx'` and render `<BreakingBadge />`).
- **React Does**: An import without curly braces grabs the file's single `default` export under whatever local name you write. An import with curly braces looks up each named export by its exact spelling in the exporting file.
- **River Progression**: Imports `{ LiveBadge, NewBadge }` from `src/components/Badges.jsx` into `src/components/ArticleCard.jsx` and renders both badges on the card.
- **Pertinent Division & Visual Comparison**:
  - `::: row` / `::: col` UI Browser & Console Preview: Mismatched import without braces (`page size=mini` blank + `devconsole` showing the syntax error) vs. Matched import with `{ LiveBadge, NewBadge }` (`page size=mini` showing `Live · New` on the card).
  - `::: row` / `::: col` Two-File Renaming Comparison: Left column shows both files for **Renaming a Default Import** (`ArticleCard.jsx` + `App.jsx` rendering `<StoryCard />`); Right column shows both files for **Renaming a Named Import with `as`** (`Badges.jsx` + `ArticleCard.jsx` rendering `<BreakingBadge />`).
  - 4-column Markdown Summary Table (`| Export Style | In the Exporting File | Normal Import in the Importing File | Importing Under a New Name |`).
- **Drafted Principle Box**:
  - **Title**: `Principle 3: Matching Imports: No Braces for Default, Curly Braces for Named`
  - **Rule**: *Import a default export without curly braces under any name you choose, and import a named export inside curly braces with its exact exported name or rename it with `as`.*

### Principle 4: Import Paths: Every Relative Path Starts from the Importing File
- **Handle**: `import-paths`
- **Thread Step**: Writing the path after `from` when files sit in different folders
- **Rule**: Start every relative import path from the folder of the file that writes the import. Use `./` for the same folder, `../` for the parent folder, and no dot for an installed package.
- **Root Distinction**:
  - **Junior Blurred View**: *"`./components/ArticleCard.jsx` is the address of the card file in my project, so I can copy and paste that exact import line into any file."*
  - **Senior Root Grounding (`###` Heading)**: `### A relative path does not start from the project root, because it starts from the folder of the file you are editing`
- **Reader Question**: "I moved my article list into `src/components/ArticleList.jsx` and copied the import line from `App.jsx`. Why can't Vite find the card file?"
- **Real Beginner Mistake (Daily Coding)**: Copying `import ArticleCard from './components/ArticleCard.jsx'` from `src/App.jsx` into `src/components/ArticleList.jsx`. Because the list file is already inside `src/components/`, Vite looks for a second `components` folder inside `src/components/` and stops with `Failed to resolve import`.
- **Interview Depth (Nuance / Follow-Up)**: Whether `.jsx` at the end of an import path is required in Vite vs. native browser modules, and how `import` lines form a tree of files starting from `main.jsx`.
- **React Does**: Every `./` or `../` path resolves starting from the folder of the file that writes the `import`. Two files sitting side by side inside `src/components/` reach each other with `./FileName.jsx`.
- **River Progression**: Creates `src/components/ArticleList.jsx` importing `./ArticleCard.jsx`, while `src/App.jsx` imports `./components/ArticleList.jsx`.
- **Pertinent Division & Visual Comparison**:
  - `files`: Visual File Explorer showing `src/App.jsx` one folder above `src/components/ArticleList.jsx` and `src/components/ArticleCard.jsx`.
  - `::: row` / `::: col` Overlay & Browser Preview: Copied path `./components/ArticleCard.jsx` inside `ArticleList.jsx` (`overlay` showing `Failed to resolve import`) vs. Neighbor path `./ArticleCard.jsx` (`page size=mini` showing both article cards).
  - `tree dir=right`: Why `src/App.jsx` and `src/components/ArticleList.jsx` write two different paths to reach the same `ArticleCard.jsx` file.
- **Drafted Principle Box**:
  - **Title**: `Principle 4: Import Paths: Every Relative Path Starts from the Importing File`
  - **Rule**: *Start every relative import path from the folder of the file that writes the import. Use `./` for the same folder, `../` for the parent folder, and no dot for an installed package.*

## Senior Answer
In React, every `.jsx` file is an isolated ES module whose functions stay private until exported. To split a component into its own file, we export it from that file and import it at the top of the file that renders it. JavaScript modules have two kinds of exports: a default export and named exports. A file can have at most one `export default`, which we use for the file's main component, and unlimited named exports using `export function` when one file holds multiple smaller components or helpers. How you export a component determines how another file must import it: we import a default export without curly braces under any local name we choose, and we import named exports inside curly braces using their exact exported names, or rename them with `as`. Finally, every relative import path starting with `./` or `../` resolves starting from the folder of the file that writes the import.

## Reported Conflicts
- Card 05's Friction mentions React's classic error `Element type is invalid: expected a string or a class/function but got: undefined` when mixing up default and named imports. In modern ES modules and Vite, a direct `import ... from` mismatch stops earlier in the browser with `SyntaxError: The requested module ... does not provide an export named ...`, while React's `got: undefined` error appears when a component tag receives `undefined` (for example in older bundlers or when reading a missing property off a module object). This distinction is answered clearly in the interview follow-up questions at the end of the lecture so it does not clutter the beginner flow.
