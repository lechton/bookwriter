---

## Authorized Scope

- **Owns**:
  - What JSX is and how the JSX transform works: JSX looks like HTML, but it is a JavaScript syntax extension; the build rewrites each tag into a function call (`_jsxDEV` on the dev server, `jsx` in the production build) that returns a plain JavaScript object called a **React element** (`{ type, props }`), and React builds the browser DOM from those objects.
  - Why React 19 files do not need `import React from 'react'` for JSX: the new JSX transform automatically imports `_jsxDEV` / `jsx` from `react/jsx-dev-runtime` or `react/jsx-runtime`.
  - Why every tag must be closed (`<img />`, `<br />`, `<input />`): JavaScript must know where each tag's `children` end, so JSX makes no exception for HTML void elements, and an unclosed `<img>` stops the build with Vite's error overlay.
  - Why a component must return a single root element: each JSX tag compiles to one function call returning one value, and a JavaScript `return` statement can only return one value; two adjacent tags after `return (` stop the build.
  - How Fragments (`<>` and `</>`) group elements without adding a wrapper DOM node: when the page needs one root for `return` but no extra box in the DOM (for example, returning two `<li>` items inside a `<ul className="items">` styled with `display: flex` and `.items > li`), `<>...</>` groups them into one `Fragment` call while adding zero extra DOM nodes, whereas a `<div>` wrapper breaks the flex row and the direct-child border.
  - Why JSX attributes use JavaScript property names: attributes become keys on the `props` object, so `class` becomes `className`, `for` becomes `htmlFor`, multi-word attributes use camelCase (`tabIndex`, `strokeWidth`), and `aria-*` and `data-*` keep their dashes.
- **Excludes (Deferred to Later Lessons)**:
  - Embedding JavaScript variables and expressions inside JSX curly braces `{}` (`Q03 #jsx_expressions`).
  - Full custom component anatomy (`PascalCase` declaration, top-level vs. nested definition, `<Card />` vs. `{Card()}`) (`Q04 #component_anatomy`).
  - Splitting components across files with `import` and `export` (`Q05 #imports`).
  - Passing `props` to custom components (`Q08 #props`).
  - `<Fragment key={id}>` in rendered lists (`Q18 #rendering_lists`).

- **Anchor**: Pasted HTML markup (`ArticleCard`, `Items`, and `SignUp`) moving into React components and passing through the JSX build transform into the browser DOM.
- **Axis**: The chronological path of pasted HTML through the build to the live page: **What a tag becomes** (P1: JSX transform to function calls & element objects) $\rightarrow$ **Where each tag ends** (P2: closing every tag, including `<img />`) $\rightarrow$ **How many values `return` can give back** (P3: single root per return) $\rightarrow$ **How to return one root without adding a DOM box** (P4: Fragments `<>...</>` vs. `<div>`) $\rightarrow$ **How attributes become JavaScript object keys** (P5: `className`, `htmlFor`, camelCase).
- **Why This Axis**: Principles 1, 2, and 3 happen at build time in exact compiler order: once you know a tag is a function call (P1), you immediately see why the compiler needs every tag closed (P2) and why `return` accepts only one outer call (P3). Principle 4 (`<>...</>`) directly solves the extra-wrapper problem created by Principle 3. Principle 5 (`className`, `htmlFor`) comes last because wrong attribute names pass the build and appear in the Console only after the page renders.
- **Spoken Preview**: *"JSX looks like HTML, but the build compiles every tag into a JavaScript function call that returns a plain React element object. Because JSX is JavaScript, every tag must be closed including `<img />` and `<br />`, every component return must have a single root element, a Fragment `<>...</>` groups elements into one root without adding an extra DOM node that would break CSS flex or grid layouts, and attributes use JavaScript property names such as `className` and `htmlFor`."*
- **Closing Line**: *"One function call per tag, every tag closed, one root per return, a Fragment when the page needs no extra box, and JavaScript names for attributes."*

## Principles

### Principle 1: The JSX Transform — Each Tag Becomes a Function Call That Returns an Object
- **Handle**: The JSX Transform
- **Thread Step**: 1 of 5 — Understand what the build turns each JSX tag into before the browser ever sees the file.
- **Rule**: Read JSX as JavaScript: the build rewrites each tag into a React function call (`_jsxDEV` or `jsx`) that returns a plain React element object (`{ type, props }`), and React builds the DOM from those objects.
- **Root Distinction**:
  - *Junior Blurred View*: JSX inside a component looks like HTML text that the browser parses directly.
  - *Senior Root Grounding*: **HTML text parsed by the browser** vs. **JSX syntax that the build compiles into JavaScript function calls returning plain objects** (`### HTML text for the browser vs. JSX tags that compile into JavaScript objects`).
- **Reader Question**: *My component returns `<article>` and `<h2>` tags that look like HTML—is JSX actually HTML, and what does `console.log` print when I log a JSX tag?*
- **Real Beginner Mistake (Daily Coding)**: Expecting a JSX variable like `const card = <article>...</article>` to be an HTML string or a live DOM node, or wondering why React 19 files work without `import React from 'react'`.
- **Interview Depth (Nuance / Follow-Up)**: Why don't React 19 files need `import React from 'react'` at the top? Because React 19 uses the automatic JSX transform, which automatically injects the import for `_jsxDEV` / `jsx` from `react/jsx-dev-runtime` or `react/jsx-runtime`.
- **React Does**: Rewrites `<h2 className="title">Library Hours</h2>` into `_jsxDEV("h2", { className: "title", children: "Library Hours" })`, which returns `{ type: 'h2', props: { className: 'title', children: 'Library Hours' } }`.
- **River Progression**: Stores the 2-line `ArticleCard` markup (`<h2>Library Hours</h2>` and `<p>Open until nine.</p>` inside `<article>`) in `const card`, logs `card` to the Console, and inspects the returned object.

### Principle 2: Closed Tags — Close Every Tag Including `<img />` and `<br />`
- **Handle**: Close Every Tag
- **Thread Step**: 2 of 5 — Close every tag so the JSX compiler knows where each function call's `children` end.
- **Rule**: Close every JSX tag with a matching closing tag (`<h2>...</h2>`) or a self-closing slash (`<img />`, `<br />`, `<input />`).
- **Root Distinction**:
  - *Junior Blurred View*: Leaving `<img>`, `<br>`, or `<input>` open feels valid because HTML void elements never hold content.
  - *Senior Root Grounding*: **HTML's forgiving parser that auto-closes void elements** vs. **JavaScript's JSX compiler that reads everything after `<img ...>` as children of `<img>` until it finds `</img>` or `/>`** (`### HTML tags that close themselves vs. JSX calls that need an explicit end`).
- **Reader Question**: *Why does pasting `<img src="/library.jpg" alt="Library">` from an HTML file stop the Vite build with an error pointing at `</article>`?*
- **Real Beginner Mistake (Daily Coding)**: Pasting `<img src="/library.jpg" alt="Library">` or `<br>` without a trailing slash `/` and getting confused when the error overlay points to `</article>` (`Expected corresponding JSX closing tag for 'img'`).
- **Interview Depth (Nuance / Follow-Up)**: Why does an unclosed `<img>` on line 4 report `Expected </img>` down on line 6 at `</article>`? Because without `/>`, the parser treats line 5 (`<h2>...</h2>`) as children inside `<img>` and only realizes `<img>` was never closed when it hits `</article>`.
- **React Does**: Stops compilation at build time and displays Vite's error overlay until `<img ... />` is closed with `/>`.
- **River Progression**: Adds `<img src="/library.jpg" alt="Library" />` to `ArticleCard`.

### Principle 3: Single Root — Return One Outer Element From Every Component
- **Handle**: Single Root per Return
- **Thread Step**: 3 of 5 — Wrap adjacent tags returned by a component inside one outer root element.
- **Rule**: Return one outer root element (or Fragment) from every component, because a JavaScript `return` statement can only return one value.
- **Root Distinction**:
  - *Junior Blurred View*: Putting `<h2>` and `<p>` side by side after `return (` looks natural because HTML files allow sibling tags anywhere.
  - *Senior Root Grounding*: **Sibling tags in an HTML file** vs. **two separate `_jsxDEV(...)` function calls sitting side by side in a single JavaScript `return` statement** (`### Sibling tags in an HTML file vs. one return value in a JavaScript function`).
- **Reader Question**: *Why does returning `<h2>Library Hours</h2>` and `<p>Open until nine.</p>` side by side fail the build with `Adjacent JSX elements must be wrapped in an enclosing tag`?*
- **Real Beginner Mistake (Daily Coding)**: Returning two sibling tags directly inside `return (...)` without an enclosing `<article>`, `<section>`, or `<>...</>`.
- **Interview Depth (Nuance / Follow-Up)**: Why can't JSX return two tags side by side without a wrapper? Because each tag compiles to a `_jsxDEV(...)` call, and a JavaScript function cannot return two separate values at once without wrapping them in an outer call (or array).
- **React Does**: Stops the build with `Adjacent JSX elements must be wrapped in an enclosing tag` and suggests `Did you want a JSX fragment <>...</>?`.
- **River Progression**: Contrasts `ArticleCard` returning adjacent `<h2>` and `<p>` tags vs. wrapping both inside one `<article>` root.

### Principle 4: Fragments — Group Elements With `<>...</>` When No Extra DOM Box Is Wanted
- **Handle**: Fragments Without Wrapper Nodes
- **Thread Step**: 4 of 5 — Group sibling elements with `<>` and `</>` when adding a real `<div>` wrapper would pollute the DOM and break CSS layouts.
- **Rule**: Use a Fragment (`<>` and `</>`) when a component must return one root but the browser DOM needs no extra wrapper element; keep a real element such as `<article>` or `<section>` only when the page needs that box for meaning or styling.
- **Root Distinction**:
  - *Junior Blurred View*: Wrapping every multi-tag return in a `<div>` feels like a universal fix for the single-root rule.
  - *Senior Root Grounding*: **A real `<div>` tag that inserts an extra box into the browser DOM** vs. **a Fragment `<>...</>` that compiles to one `Fragment` call in JavaScript while adding zero nodes to the DOM** (`### Adding a real div box to the DOM vs. grouping tags with an invisible Fragment`).
- **Reader Question**: *What breaks on the page if I wrap two `<li>` items in a `<div>` inside `<ul className="items">`, and how does `<>...</>` fix it?*
- **Real Beginner Mistake (Daily Coding)**: Wrapping two `<li>` items (or `<td>` table cells, or flex/grid children) in a `<div>` to satisfy the single-root rule, which turns the `<div>` into the only child of `<ul class="items">` and breaks both `display: flex` and `.items > li` borders without any Console warning.
- **Interview Depth (Nuance / Follow-Up)**: Does a Fragment leave any trace in Chrome's Elements panel? No—`<>...</>` compiles to `_jsxDEV(Fragment, { children: [...] })`, and React mounts the children directly inside the parent DOM node.
- **React Does**: Unpacks the Fragment's children directly into `<ul class="items">` so both `<li>` elements remain direct children of `<ul>`.
- **River Progression**: Shows `Items` inside `<ul className="items">` comparing `<div>` (`stack: First ; Second`, no borders) vs. `<>...</>` (`row: First ; Second`, side by side with borders).

### Principle 5: camelCase Attributes — Write Attributes as JavaScript Property Names
- **Handle**: JavaScript Attribute Names
- **Thread Step**: 5 of 5 — Rename HTML attributes (`class`, `for`, `tabindex`) to their JavaScript property names (`className`, `htmlFor`, `tabIndex`).
- **Rule**: Write JSX attributes using their JavaScript property names: `className` instead of `class`, `htmlFor` instead of `for`, and camelCase for multi-word attributes (`tabIndex`, `strokeWidth`), while keeping dashes in `aria-*` and `data-*`.
- **Root Distinction**:
  - *Junior Blurred View*: Tag attributes in JSX look like verbatim HTML attributes copied to the page.
  - *Senior Root Grounding*: **HTML attribute names in markup** vs. **JavaScript property names on the `props` object and browser DOM nodes** (`### HTML attribute names vs. JavaScript property names on the props object`).
- **Reader Question**: *Why do `class="label"`, `for="name"`, and `tabindex="0"` pass the build and look right on screen, yet fill Chrome's Console with `Invalid DOM property` errors?*
- **Real Beginner Mistake (Daily Coding)**: Leaving `class`, `for`, or `tabindex` in pasted HTML so the dev Console fills with `Invalid DOM property` errors (or mistakenly camelCasing `aria-label` / `data-form-id`).
- **Interview Depth (Nuance / Follow-Up)**: Why did React choose `className` and `htmlFor` specifically? Because `class` and `for` are reserved words in JavaScript, and the browser DOM's own JavaScript properties on element objects are `element.className` and `label.htmlFor`.
- **React Does**: Logs `Invalid DOM property 'class'. Did you mean 'className'?` (and the same for `for` and `tabindex`) in development while writing clean HTML attributes when given `className`, `htmlFor`, and `tabIndex`.
- **River Progression**: Contrasts `SignUp` with `class`, `for`, and `tabindex` vs. `className`, `htmlFor`, `tabIndex`, `aria-label`, and `data-form-id`.

## Senior Answer

JSX is a syntax extension for JavaScript, not HTML inside JavaScript. During the build, the compiler rewrites every JSX tag into a function call (`_jsxDEV` in development or `jsx` in production) that returns a plain JavaScript object—a React element with `type` and `props`—and React builds the real browser DOM from those objects. Every JSX syntax rule follows directly from the fact that JSX compiles to JavaScript calls:
1. **Close every tag**: Void elements such as `<img />`, `<br />`, and `<input />` must close with a slash so the compiler knows where each call's `children` end.
2. **Return one root**: A JavaScript `return` statement returns one value, so a component cannot return two adjacent calls side by side without an outer wrapper call.
3. **Group with Fragments (`<>...</>`) when no extra DOM box is wanted**: Wrapping list items or flex/grid children in a real `<div>` inserts an extra DOM node between parent and children, breaking `display: flex` and direct-child CSS selectors like `.items > li`. A Fragment compiles to one `Fragment` call for `return` while adding zero nodes to the browser DOM.
4. **Use JavaScript property names for attributes**: Because attributes become properties on the `props` object and map to DOM properties, `class` becomes `className`, `for` becomes `htmlFor`, and multi-word attributes use camelCase (`tabIndex`, `strokeWidth`), while `aria-*` and `data-*` keep their dashes.
