## Authorized Scope
Lecture 04 teaches what a React component is and the four rules for defining and rendering one inside another component. A component is a JavaScript function that returns JSX describing one piece of the page. Our code never calls the component function directly. Instead, we write its name as a JSX tag, `<ArticleCard />`, inside another component's markup, and React calls the function once for each tag. The lesson builds one progressive example in a single file, `src/App.jsx`, starting with `ArticleCard` inside `App`, adding `Footer`, and adding `CommentBox` inside `ArticleCard`. Every component name must start with a capital letter in `PascalCase`, because JSX treats a tag with a small first letter as a built-in HTML tag. Multi-line JSX returned from a component must open its parenthesis on the same line as `return` so Automatic Semicolon Insertion does not turn `return` into `return;` and return `undefined`. Every component must be defined at the top level of the file, never inside another component, so JavaScript does not create a brand-new function on every render and force React to destroy and recreate DOM nodes such as `<input>`.

## Principle Thread
- **Anchor**: A component is a function that React calls, never our code: we define the function once and place its `<Tag />` wherever a piece of the page belongs.
- **Axis**: The path of a component tag from declaration to update: declaring vs. rendering the `<Tag />` (Principle 1), the capital first letter of its name in `PascalCase` (Principle 2), the `return (` line that hands its JSX back (Principle 3), and keeping the function at the top level of the file across updates (Principle 4).
- **Why This Axis**: The four principles follow the exact order a developer experiences when writing `ArticleCard`, `Footer`, and `CommentBox` in `App.jsx`. First you must understand that declaring `function ArticleCard()` does nothing until `<ArticleCard />` makes React call it. Second, once you know React calls the tag, you see why a small first letter (`<articleCard />` or `<footer />`) stops React from calling your function. Third, once React calls your function, a bare `return` with a line break makes the function return `undefined`. Fourth, once the page renders and updates, defining `CommentBox` inside `ArticleCard` recreates the function on every render and wipes out the user's `<input>`.
- **Spoken Preview**: Everything in this lesson comes down to one idea: a component is a function that React calls, never our code. First, rendering means React calls the component wherever a tag names it: declaring the function and placing its tag are two separate steps, and only the returned HTML appears in the browser DOM. Second, `PascalCase` means React calls only tags that start with a capital letter: a tag starting with a small letter is treated as a built-in HTML tag, and `<footer />` fails with zero Console warnings. Third, Automatic Semicolon Insertion means React gets back only what starts on the `return` line: when markup spans multiple lines, open the parenthesis on the `return` line so JavaScript does not return `undefined`. Fourth, top-level components mean React must find the same function on every render: define every component at the top level of the file, never inside another component, or React will destroy and rebuild its DOM nodes on every update.
- **Closing Line**: One tag to render it, one capital letter to name it, one opening parenthesis on the `return` line, and every component at the top level of the file.

## Principles

### Principle 1: Rendering Means React Calls Your Component for Each `<Tag />`
- **Handle**: `react-calls-it`
- **Thread Step**: Declaring the function vs. placing its `<Tag />` so React calls it
- **Rule**: Use a component by writing its name as a JSX tag, such as `<ArticleCard />`, inside another component's markup; React calls the function once for each tag.
- **Root Distinction**:
  - **Junior Blurred View**: *"I wrote `function ArticleCard()`, so my card should show up on the page."*
  - **Senior Root Grounding (`###` Heading)**: `### Writing the component function and using its tag are two separate steps`
- **Reader Question**: "I wrote the function `ArticleCard`. Why is nothing on the screen, who calls it, and why is `<ArticleCard>` not in the browser's Elements panel?"
- **Real Beginner Mistake (Daily Coding)**: Declaring `function ArticleCard()` at the top of `App.jsx` and forgetting to place `<ArticleCard />` inside `App`, resulting in 0 cards on screen and 0 messages in the Console.
- **Interview Depth (Nuance / Follow-Up)**: Explaining what "rendering" means (React calling your component function for each `<Tag />`), why `<ArticleCard>` never appears in the browser DOM (only the returned `<article>` HTML does), and why we write `<ArticleCard />` instead of calling `{ArticleCard()}` directly.
- **React Does**: When `App` returns two `<ArticleCard />` tags, each tag hands the `ArticleCard` function reference to React. React calls `ArticleCard` twice, logs `"ArticleCard runs"` twice in the Console, and inserts two `<article class="card">` elements into `<main>` in the browser DOM.
- **River Progression**: Starts `App.jsx` with `function ArticleCard()` and `export default function App()` rendering two `<ArticleCard />` tags inside `<main>`.
- **Pertinent Division & Visual Comparison**:
  - `tree dir=right`: Step 1 alone (declare `function ArticleCard` only -> 0 cards, 0 logs) vs. Step 1 + Step 2 (place `<ArticleCard />` in `App` -> React calls `ArticleCard` once per tag).
  - `::: row` / `::: col` UI Browser & Console Preview: Step 1 alone (`page size=mini` with `empty: no cards on the page` + `devconsole` `= No messages`) vs. Step 1 + Step 2 (`page size=mini` showing two `ArticleCard` cards + `devconsole` logging `ArticleCard runs` twice).
  - `tree`: How to invoke a component in JSX (`!Do NOT call the component yourself with parentheses` vs. `+DO hand the component to React as a tag`).
  - `tree`: First `<ArticleCard />` tag vs. Second `<ArticleCard />` tag inside `App`.
  - `dom` Elements Panel + `tree dir=right`: Built-in HTML tags kept in the Elements panel vs. React component tags replaced by their returned `<article class="card">` HTML.
- **Drafted Principle Box**:
  - **Title**: `Principle 1: Rendering: React Calls the Component Wherever a Tag Names It`
  - **Rule**: *Use a component by writing its name as a JSX tag, such as `<ArticleCard />`, inside another component's markup; React calls the function once for each tag.*

### Principle 2: Start Component Names with a Capital Letter in `PascalCase`
- **Handle**: `capital-name`
- **Thread Step**: The first letter of the tag decides whether JSX compiles an HTML tag string or passes your function
- **Rule**: Start every component's name with a capital letter in `PascalCase` in both the `function` declaration and the JSX `<Tag />`.
- **Root Distinction**:
  - **Junior Blurred View**: *"In JavaScript, `camelCase` vs. `PascalCase` is just a naming style for humans, so `function articleCard()` or `function footer()` should work fine."*
  - **Senior Root Grounding (`###` Heading)**: `### In React, a capital first letter is a compiler rule, not a style habit`
- **Reader Question**: "Does it matter whether I name my component `articleCard` / `footer` or `ArticleCard` / `Footer`?"
- **Real Beginner Mistake (Daily Coding)**: Naming a component with a small first letter (`function articleCard` + `<articleCard />`, or `function footer` + `<footer />`). `<articleCard />` renders an empty `<articlecard>` with 2 Console warnings; `<footer />` matches a real HTML tag and renders an empty `<footer></footer>` with **0 Console warnings**! And capitalizing only `<ArticleCard />` without capitalizing `function articleCard()` crashes with `ReferenceError: ArticleCard is not defined`.
- **Interview Depth (Nuance / Follow-Up)**: Why `PascalCase` is a compiler rule: the JSX compiler rewrites lowercase `<articleCard />` with quotes as `_jsx('articleCard', {})` (an HTML tag string) and uppercase `<ArticleCard />` without quotes as `_jsx(ArticleCard, {})` (your JavaScript function reference).
- **River Progression**: Adds `function Footer()` and `<Footer />` to `App.jsx` below `<ArticleCard />`.
- **Pertinent Division & Visual Comparison**:
  - `tree`: Three naming conventions (`!camelCase` Do NOT use, `+PascalCase` DO use, `!snake_case` Do NOT use).
  - `tree`: Plain JavaScript style habit vs. React JSX strict compiler rule.
  - `tree dir=right`: How JSX compiles `<Tag />` (small letter with quotes vs. capital letter without quotes).
  - `tree` + `overlay`: Capitalize BOTH function and tag vs. capitalizing only the tag (`ReferenceError: ArticleCard is not defined`).
  - `::: row` / `::: col` UI Browser, DOM, & Console Preview + `tree dir=right`: Three runtime outcomes of a tag's first letter (`<articleCard />` empty `<articlecard>` + 2 Console warnings, `<footer />` empty `<footer></footer>` + 0 Console warnings silent bug, `<ArticleCard />` and `<Footer />` rendered on the page).
- **Drafted Principle Box**:
  - **Title**: `Principle 2: PascalCase: React Calls Only the Tags That Start with a Capital Letter`
  - **Rule**: *Start every component's name with a capital letter in `PascalCase` in both the `function` declaration and the JSX `<Tag />`.*

### Principle 3: Open the Parenthesis on the Same Line as `return`
- **Handle**: `return-parentheses`
- **Thread Step**: What the component function hands back to React when JSX spans multiple lines
- **Rule**: When a component's markup spans multiple lines, always open the parenthesis on the same line as `return`.
- **Root Distinction**:
  - **Junior Blurred View**: *"In HTML and JavaScript, whitespace and line breaks don't matter, so I can press `Enter` right after `return` and put my multi-line JSX on the next line."*
  - **Senior Root Grounding (`###` Heading)**: `### Silent bugs are much harder to find than loud errors` / `### Why a line break right after return stops your component`
- **Reader Question**: "My `Footer` markup grew to several lines. Why did my footer vanish with zero errors when I moved `<footer>` to the line below `return`?"
- **Real Beginner Mistake (Daily Coding)**: Pressing `Enter` right after a bare `return` when expanding `Footer` to multiple lines. JavaScript's Automatic Semicolon Insertion turns `return` into `return;`, returning `undefined` so the component disappears with 0 Console errors and 0 Vite warnings.
- **Interview Depth (Nuance / Follow-Up)**: Explaining Automatic Semicolon Insertion (ASI), why returning `undefined` from a component produces no runtime error in React 19, and why opening `return (` on the same line prevents ASI from ending the statement early.
- **River Progression**: Expands `Footer` in `App.jsx` from a one-line `<footer>` to a multi-line `<footer>` with `<p>` and `<a href="/contact">` wrapped in `return ( ... );`.
- **Pertinent Division & Visual Comparison**:
  - `tree`: Loud crash (`ReferenceError`) vs. Silent bug (`<footer />`, `return` + `Enter`).
  - `::: row` / `::: col` UI Browser & Console Preview: Bare `return` + line break (`page size=mini` with `empty: footer is missing` and `devconsole` `= No messages`) vs. `return (` on the same line (`page size=mini` with `line: Latest Articles, 2026 · Contact us | good`).
  - `tree dir=right`: Where Automatic Semicolon Insertion helps (`const city = 'Boston'`) vs. where it sets a trap (bare `return` at the end of a line).
  - `tree dir=right`: The three ways to write `return` in a component (one-line return, multi-line with opening parenthesis on the `return` line, bare `return` + `Enter`).
- **Drafted Principle Box**:
  - **Title**: `Principle 3: Automatic Semicolon Insertion: Open the Parenthesis on the return Line`
  - **Rule**: *When a component's markup spans multiple lines, always open the parenthesis on the same line as `return`.*

### Principle 4: Define Every Component at the Top Level, Never Inside Another Component
- **Handle**: `top-level-components`
- **Thread Step**: Keeping the same component function in memory across re-renders so React preserves DOM nodes and user input
- **Rule**: Define every component at the top level of the file, outside all other functions, and never inside another component.
- **Root Distinction**:
  - **Junior Blurred View**: *"Only `ArticleCard` uses `CommentBox`, so I can tidy up my file by defining `function CommentBox()` inside `function ArticleCard()`."*
  - **Senior Root Grounding (`###` Heading)**: `### A component defined inside another component wipes out what the user typed`
- **Reader Question**: "Why does defining `CommentBox` inside `ArticleCard` wipe out what the user typed into the `<input>` box and lose cursor focus every time `ArticleCard` updates?"
- **Real Beginner Mistake (Daily Coding)**: Defining `function CommentBox()` inside `function ArticleCard()`. On the first render it looks fine, but on any update of `ArticleCard`, the `<input>` loses its typed text and cursor focus.
- **Interview Depth (Nuance / Follow-Up)**: Explaining JavaScript function allocation (`firstRun === secondRun` is `false` for nested functions because a brand-new function object is allocated on every call) and React's reconciliation check (`OldFn === NewFn`: when the function reference changes at the same tree position, React unmounts the old DOM subtree and mounts a brand-new `<input>`).
- **River Progression**: Adds `function CommentBox()` at the top level of `App.jsx` and places `<CommentBox />` inside `ArticleCard`, completing the 4-component `App.jsx` file (`CommentBox`, `ArticleCard`, `Footer`, `App`).
- **Pertinent Division & Visual Comparison**:
  - `tree`: Where to define a component function in React (`!Do NOT define inside another component` vs. `+DO define at the top level of the file`).
  - `::: row` / `::: col` UI Browser Preview: Nested `CommentBox` inside `ArticleCard` after update (`page size=mini` with `input=Write a comment | bad=input` where typed text and focus are wiped) vs. Top-level `CommentBox` after update (`page size=mini` with `typed=See you there | good=typed` where typed text and cursor focus stay untouched).
  - `tree`: Top-level function (`Created ONCE`, `CommentBox === CommentBox` is `true`) vs. Nested function (`Created BRAND-NEW every time`, `CommentBox #1 === CommentBox #2` is `false`).
  - `tree dir=right`: How React decides whether to keep or destroy an existing DOM node (`OldFn === NewFn`).
- **Drafted Principle Box**:
  - **Title**: `Principle 4: Top-Level Components: Define Every Component at the Top Level`
  - **Rule**: *Define every component at the top level of the file, outside all other functions, and never inside another component.*

## Senior Answer
A React component is a JavaScript function whose name starts with a capital letter and that returns JSX describing one piece of the UI. To render it inside another component, we never call the function ourselves. Instead, we write its name as a JSX tag, like `<ArticleCard />`, and React calls the function once for each tag. That call is what "rendering" means. Three rules keep components working properly: first, start every component name with a capital letter in `PascalCase`, because a lowercase tag like `<footer />` or `<articleCard />` is compiled as a built-in HTML tag string and our function never runs. Second, open the parenthesis on the `return` line whenever JSX spans multiple lines, because a bare `return` triggers Automatic Semicolon Insertion, turns into `return;`, and returns `undefined`. Third, define every component at the top level of the file, never inside another component, because a nested component creates a brand-new function in memory on every render, forcing React to destroy and recreate its DOM nodes and wiping out user input and focus.
