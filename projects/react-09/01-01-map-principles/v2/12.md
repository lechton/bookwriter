# Q12 Principle Map (River Version v2): Component Memory with useState
- **Version**: River Version (`v2`)
- **Bank Row**: `questions/questions.md` row 12, Version 4
- **Topic Tag**: `#use_state` | `❱ CORE`
- **Interview Question**: *Why do ordinary variables forget their values between renders, and how does useState remember?*

## Authorized Scope
- Why a regular local variable (`let likes = 0`) declared inside a component function fails to update the screen when modified in an event handler:
  1. Mutating a local variable (`likes = likes + 1`) does not notify React that data has changed, so React never triggers a re-render.
  2. Even when the component re-renders for another reason, React calls the component function again from the top and recreates `let likes = 0` from scratch, wiping out any previous local mutation.
- How importing `useState` from `'react'` and calling `const [likes, setLikes] = useState(0)` at the top level of a component solves both problems by returning a two-item array unpacked via JavaScript array destructuring:
  1. The current state value (`likes`), which React stores outside the component function and hands back on each render.
  2. The state setter function (`setLikes`), which stores the next value inside React and requests a re-render of the component with that new value.
- How `useState(initialValue)` uses its initial value only during the component's first render and ignores it on subsequent re-renders, why passing a direct function call (`useState(loadSavedLikes())`) still executes `loadSavedLikes()` on every single render even though React throws away its return value after the first render, and how passing an initializer function reference (`useState(loadSavedLikes)`) tells React to call `loadSavedLikes` only once during the initial render.
- How a single component can call `useState` multiple times to hold multiple independent pieces of state (such as `const [likes, setLikes] = useState(loadSavedLikes)` and `const [showSummary, setShowSummary] = useState(false)`), why Hooks (`use`, `useState`, and other `use*` functions) must be called unconditionally at the top level of a component function (never inside `if` blocks, loops, or nested functions), and how React matches each `useState` call to its stored state slot across renders using an internal array and a call-order index rather than variable names.
- How state is isolated and private to each rendered component instance on the screen: rendering two `<StoryCard />` tags side by side inside `App` gives each `<StoryCard />` its own independent `likes` and `showSummary` state in memory, so clicking `Like` or `Show summary` on the first card never affects the second card, and `App` can neither read nor change a card's internal state.
- Out of scope: the three-step Trigger-Render-Commit pipeline between calling `setLikes` and the DOM update (`Q13 #render_and_commit`), component purity and `<StrictMode>` double-rendering (`Q14 #purity`), why reading `likes` immediately after `setLikes(likes + 1)` still logs the old value in that render's snapshot (`Q15 #state_snapshots`), batching multiple updates in one click and updater functions `setLikes(n => n + 1)` (`Q16 #state_updates`), mutating objects or arrays in state (`Q17 #state_objects`), sharing state between sibling components by lifting state up to their parent (`Q24 #lifting_state`), how tree position and `key` preserve or reset state (`Q25 #component_identity`), and the comprehensive Rules of Hooks chapter (`Q38 #rules_of_hooks`).

## General Concepts Introduction (Runway Plan)
- **Opening Essence**:
  - **Furniture-free snippet**: Side-by-side comparison of a small component using a plain local variable (`let count = 0;` and `count = count + 1;`) versus a component using `const [count, setCount] = useState(0);` and `setCount(count + 1);`, plus the array destructuring equivalence (`const pair = useState(0); const count = pair[0]; const setCount = pair[1];` vs. `const [count, setCount] = useState(0);`) and initializer function comparison (`useState(loadInitialCount)` vs. `useState(loadInitialCount())`).
  - **Human image**: Writing a tally on a disposable sticky note (`let count = 0`) inside a room that gets swept clean and rebuilt from scratch every time the function runs, versus keeping the tally on a permanent clipboard held by React outside the room (`useState(0)`), where `count` is the current number React reads off the clipboard for you and `setCount` is the bell you ring to hand React the new number and ask it to redraw the room. For multiple `useState` calls, a numbered row of lockers (`Slot 0`, `Slot 1`) that React opens in exact top-to-bottom order on every visit.
  - **Exact nuance of confusion to state out loud**:
    1. Between `let count = 0` and `const [count, setCount] = useState(0)` on the very first render: ***"When the page first loads, both versions show `Count: 0` on the screen, so they look like they work the same way at first, but they are NOT the same thing at all!"*** A `let` variable lives only while the function is running once and vanishes as soon as the function finishes, and changing `count = count + 1` never tells React to redraw the page. `useState(0)` stores the number inside React outside your function and gives you `setCount` to both save the new number and trigger a fresh render.
    2. Between reading `pair[0]` / `pair[1]` by index and writing `const [count, setCount] = useState(0)`: ***"Yes, it is the exact same thing!"*** There is no special React syntax in `[count, setCount]`: `useState(0)` simply returns a two-item JavaScript array `[0, function]`, and `[count, setCount]` is standard JavaScript array destructuring that unpacks item `0` and item `1` into whatever names you choose.
    3. Between `useState(loadSavedLikes)` (no parentheses) and `useState(loadSavedLikes())` (with parentheses): ***"On the screen, both start at the exact same initial number, so they look like they do the same thing, but under the hood they are NOT the same thing!"*** With `useState(loadSavedLikes())`, JavaScript calls `loadSavedLikes()` on **every single re-render** before handing the result to `useState`, even though React ignores that result after the first render. With `useState(loadSavedLikes)`, you hand the function itself to React, and React calls it **only once** on the first render.
- **Theme**: On a story card with a `Like` button and a `Show summary` toggle button, clicking `Like` must increment the visible like count on screen and clicking `Show summary` must reveal or hide the summary paragraph, with each story card on the page keeping its own independent memory.
- **Ways**:
  - Passing a simple initial value directly (`useState(0)`, `useState(false)`) when the starting value is already a cheap literal or prop.
  - Passing an initializer function reference (`useState(loadSavedLikes)`) when computing the starting value requires calling a function (such as reading from storage or running a calculation) that should only run once on the initial render.
  - Calling `useState` multiple times at the top level of the same component when a component tracks multiple unrelated values (such as a numeric `likes` count and a boolean `showSummary` toggle).
- **Recall**:
  - Object destructuring (`const { title, summary } = props`) unpacks properties by name with curly braces `{}` (Lecture 08, `Q08 #props`), which contrasts with array destructuring (`const [likes, setLikes] = useState(0)`) that unpacks items by position with square brackets `[]`.
  - Conditional rendering with the ternary operator (`showSummary ? 'Hide' : 'Show'`) and logical AND (`{showSummary && <p>{summary}</p>}`) shows, hides, or switches JSX based on a boolean value (Lecture 10, `Q10 #conditional_rendering`).
  - Passing a function reference (`onClick={handleLike}`) vs. calling a function with parentheses (`onClick={handleLike()}`) determines whether a function is handed to React or executed immediately during render (Lecture 11, `Q11 #event_handling`).
- **Runway topics**:
  - How the lifetime of a plain JavaScript local variable inside a function works (created when the function starts, destroyed when the function returns, and recreated from scratch on the next call).
  - How JavaScript array destructuring (`const [first, second] = pair`) unpacks a two-element array by position (`pair[0]` and `pair[1]`), why square brackets `[]` let you pick any variable names (`[likes, setLikes]`), and the `[something, setSomething]` naming convention.
  - What a React **Hook** is (`import { useState } from 'react'`, a special function starting with `use` that lets your component hook into React features like state).
  - How the project files (`index.html`, `src/main.jsx`, `src/App.jsx`, and `src/components/StoryCard.jsx`) are organized on disk.
- **Example**:
  - **Chosen page**: A compact reader page (`src/App.jsx` and `src/components/StoryCard.jsx`) that starts with one `<StoryCard title="New Park Opens Today" summary="The park on Main Street opens at noon." />` showing `Likes: {likes}` and a `Like` button (Principle 1), initializes its starting like count through an initializer function `loadSavedLikes` (Principle 2), adds a second independent state variable `showSummary` with a `Show summary` / `Hide summary` toggle button that reveals or hides `<p className="summary-text">{summary}</p>` (Principle 3), and renders a second `<StoryCard title="Library Extends Hours" summary="The central library stays open until 9 PM." />` right below the first card in `App.jsx` so both cards keep independent `likes` and `showSummary` memories side by side (Principle 4).
  - **Why this concept is the reason this page exists**: Every piece of this page exists only to make one of Question 12's four principles visible at a glance:
    1. Clicking `Like` on `StoryCard` with `let likes = 0` leaves `Likes: 0` frozen on screen while logging `1`, `2` in the Console, and replacing `let likes = 0` with `const [likes, setLikes] = useState(0)` makes `Likes: 1`, `Likes: 2` update on screen immediately (Principle 1).
    2. Loading the starting like count (`10`) from `loadSavedLikes` shows why `useState(loadSavedLikes())` re-runs `loadSavedLikes` on every single click (`call #1`, `call #2`, `call #3`) while `useState(loadSavedLikes)` runs it only once on initial mount (Principle 2).
    3. Adding the `Show summary` / `Hide summary` button (`const [showSummary, setShowSummary] = useState(false)`) gives `StoryCard` two unrelated pieces of state (`likes` and `showSummary`) so the reader sees multiple `useState` calls in action and sees how React's internal `[slot 0, slot 1]` call-order array breaks if a Hook is placed inside `if (likes > 0)` (Principle 3).
    4. Placing a second `<StoryCard />` (`'Library Extends Hours'`) in `App.jsx` shows that clicking `Like` twice and opening the summary on `'New Park Opens Today'` (`Likes: 12`, summary visible) leaves `'Library Extends Hours'` untouched (`Likes: 10`, summary hidden), proving that state is attached to each component instance on screen rather than shared across the `StoryCard` function (Principle 4).

## Principle Thread
- **Anchor**: Why plain local variables neither persist across function calls nor trigger React re-renders, and how `useState` stores state outside the component function per rendered instance, matches state slots by top-level call order, and triggers re-renders through its setter function.
- **Axis**: From replacing a forgotten local variable with a single `useState` pair, to initializing state once with an initializer function, to tracking multiple state variables by top-level call order, to rendering multiple isolated component instances side by side:
  1. Replacing a plain local variable (`let likes = 0`) with `const [likes, setLikes] = useState(0)` and `setLikes(likes + 1)` so changes persist and trigger a re-render (Principle 1).
  2. Passing an initializer function reference (`useState(loadSavedLikes)`) instead of calling `useState(loadSavedLikes())` so setup logic runs only on the first render (Principle 2).
  3. Calling `useState` multiple times at the top level of a component (`likes` and `showSummary`) and keeping Hook call order identical across renders so React's internal state array matches every slot (Principle 3).
  4. Rendering multiple `<StoryCard />` instances side by side in `App` so each rendered instance keeps its own isolated, private state (Principle 4).
- **Why This Axis**: Each step answers the question raised by the step before it:
  1. First, the reader sees why `let likes = 0` inside `StoryCard` fails on click (no re-render, and re-running the function resets local variables) and fixes it with `const [likes, setLikes] = useState(0)` (Principle 1).
  2. Second, once the reader passes a starting value into `useState(...)`, the immediate question is how React treats that argument on later renders, and why calling `useState(loadSavedLikes())` wastes work on every re-render unless passed as `useState(loadSavedLikes)` (Principle 2).
  3. Third, once one state variable works, the card needs a second independent memory (`showSummary` for the summary toggle), which shows how to use multiple `useState` calls in one component and why React relies on unconditional top-level call order to tell them apart (Principle 3).
  4. Fourth, once a single `StoryCard` manages `likes` and `showSummary`, rendering two `<StoryCard />` tags in `App.jsx` proves that React stores that state array per rendered component instance on screen, not globally on the `StoryCard` function definition (Principle 4).

## Principles

### Principle 1: Replace Ephemeral Local Variables with `useState` So Changes Persist and Trigger a Re-Render
- **Handle**: `local-variables-vs-usestate`
- **Rule**: Never store data that changes on screen in a plain local variable (`let likes = 0`); call `const [likes, setLikes] = useState(0)` at the top of the component and call `setLikes(likes + 1)` in your event handler so React remembers the new value and re-renders the component.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - Option A (plain local variable): `let count = 0;` inside `Counter`, with `count = count + 1;` on click.
    - Option B (`useState`): `const [count, setCount] = useState(0);` inside `Counter`, with `setCount(count + 1);` on click.
    - Array destructuring equivalence:
      - `const pair = useState(0); const count = pair[0]; const setCount = pair[1];`
      - `const [count, setCount] = useState(0);`
  - **Human image**: Every time React renders your component, it calls your function from top to bottom like walking into a room, reading the blueprint, and sweeping the room clean when it leaves. A plain `let count = 0` variable is written on a scrap of paper inside the room: changing it in `handleClick` never rings React's bell to redraw the room, and the next time React enters the room, it starts at line 1 and writes a brand-new scrap of paper saying `let count = 0`. Calling `useState(0)` asks React to keep the number on a permanent clipboard outside the room and hands you two things in an array `[count, setCount]`: the current number on the clipboard (`count`) and a button (`setCount`) that updates the clipboard and tells React to re-render the component.
  - **Exact nuance of confusion to state out loud**:
    1. Between `let count = 0` and `const [count, setCount] = useState(0)` on initial load: ***"When the page first opens, both versions display `Count: 0` on the screen with zero errors, so they look like they work the same way at first, but they are NOT the same thing at all!"*** Explain the two separate reasons `let count = 0` fails when clicked: first, `count = count + 1` mutates a local variable in silence without telling React to re-render; second, even if the component re-renders later, `let count = 0` runs again from scratch and resets `count` to `0`.
    2. Between reading `pair[0]` / `pair[1]` and writing `const [count, setCount] = useState(0)`: ***"Yes, it is the exact same thing!"*** Show side by side that `useState(0)` simply returns a normal two-item JavaScript array `[0, function]`, and `[count, setCount]` is standard JavaScript array destructuring (using square brackets `[]` by position `0` and `1`, unlike object destructuring `{ title }` which uses curly braces `{}` by property name).
- **Root Distinction**:
  - *Junior blurred view*: Changing `likes = likes + 1` inside `handleLike` should automatically update `{likes}` on the screen because the JSX wrote `<p>Likes: {likes}</p>`.
  - *Senior grounding*: JSX is evaluated once per render call; a local `let` variable neither notifies React to re-run the component function nor survives between function calls, whereas `useState` stores the value in React's external memory and `setLikes(likes + 1)` schedules a new render call where `useState` returns the updated value.
- **Real Beginner Mistake (events, in order)**:
  1. A developer writes `let likes = 0;` at the top of `StoryCard.jsx` and renders `<p className="likes-text">Likes: {likes}</p>` and `<button className="like-btn" onClick={handleLike}>Like</button>`.
  2. Inside `handleLike`, the developer writes `likes = likes + 1;` and `console.log('Local likes:', likes);`.
  3. On initial page load, React calls `StoryCard()`, sets `likes` to `0`, and renders `Likes: 0` in the browser.
  4. The user clicks the `Like` button twice.
  5. The Console logs `Local likes: 1` and `Local likes: 2`, proving `handleLike` ran and incremented the local variable in memory, but the browser screen stays frozen at `Likes: 0` because assigning to `likes` never tells React to re-render `StoryCard`.
  6. Whenever `StoryCard` does re-render later, JavaScript runs `function StoryCard()` from the first line again and executes `let likes = 0;`, wiping out the local changes back to `0`.
- **Interview Depth**:
  - Always state **both** halves of why local variables fail in an interview: (1) local variable mutations do not trigger re-renders, and (2) local variables do not persist between renders because each render calls the component function from scratch.
  - Why `const [likes, setLikes] = useState(0)` uses `const` instead of `let` even though `likes` changes across renders: you never reassign `likes = ...` directly; on each new render, React calls `StoryCard()` as a brand-new function execution and creates a fresh `const likes` binding holding the latest value from `useState`.
  - Why array destructuring `const [likes, setLikes] = useState(0)` uses square brackets `[]` while props destructuring `function StoryCard({ title, summary })` uses curly braces `{}`: `props` is an object with fixed keys (`props.title`), whereas `useState` returns a two-element array `[currentValue, setterFunction]` so you can name the state variable and setter anything (`[likes, setLikes]`, `[count, setCount]`).
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: Any code inside `StoryCard.jsx` that calls `StoryCard()` a second time when the user clicks `Like`, or any variable declared outside `StoryCard` in the file.
    - **Who supplies it**: React's `useState` Hook stores the state value outside `StoryCard` inside React's internal fiber tree, and calling `setLikes(likes + 1)` tells React to call `StoryCard()` again and return `1` from `useState(0)`.
    - **What JavaScript and React do**:
      1. On the first render, `StoryCard()` calls `useState(0)`; React initializes its stored state slot to `0` and returns `[0, setLikes]`, so the DOM shows `<p class="likes-text">Likes: 0</p>`.
      2. When the user clicks `<button class="like-btn">Like</button>`, `handleLike` calls `setLikes(0 + 1)`.
      3. React saves `1` into the component's state slot and calls `StoryCard()` a second time.
      4. On that second render, `useState(0)` ignores the `0` argument, returns `[1, setLikes]`, and React updates `<p class="likes-text">` in the DOM to `Likes: 1`.
- **React Does**:
  - When `StoryCard` uses `let likes = 0;` and `handleLike` runs `likes = likes + 1; console.log('BrokenStoryCard local likes:', likes);`, clicking `Like` twice logs `BrokenStoryCard local likes: 1` and `BrokenStoryCard local likes: 2` in the Console, while `<p class="likes-text">` in the `Elements` panel remains `<p class="likes-text">Likes: 0</p>`.
  - When `StoryCard` imports `import { useState } from 'react';` and uses `const [likes, setLikes] = useState(0);` with `setLikes(likes + 1)`, initial load renders `<p class="likes-text">Likes: 0</p>`, the first click on `Like` updates the DOM to `<p class="likes-text">Likes: 1</p>`, and the second click updates the DOM to `<p class="likes-text">Likes: 2</p>` with zero Console errors.

### Principle 2: Pass an Initializer Function Reference (`useState(fn)`) Instead of Calling `useState(fn())` on Every Render
- **Handle**: `initial-value-and-initializer`
- **Rule**: React uses the initial value passed to `useState(initialValue)` only on the first render; when computing that initial value requires calling a function (`loadSavedLikes`), pass the function reference without parentheses (`useState(loadSavedLikes)`) instead of calling it (`useState(loadSavedLikes())`) so it runs only on the first render instead of every re-render.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - `const [likes, setLikes] = useState(loadSavedLikes());` (with parentheses `()`)
    - `const [likes, setLikes] = useState(loadSavedLikes);` (without parentheses)
  - **Human image**: Imagine `loadSavedLikes` is a clerk who walks down to the basement archive to look up the starting like count (`10`). Only on opening day (Render 1) does React actually need that starting number; on Render 2, Render 3, and Render 4, React already has the updated number (`11`, `12`, `13`) on its clipboard. If you write `useState(loadSavedLikes())` with parentheses, you send the clerk down to the basement on **every single click** just so React can throw the number in the trash! If you write `useState(loadSavedLikes)` without parentheses, you hand React the clerk's phone number, and React calls the clerk **only once** on opening day.
  - **Exact nuance of confusion to state out loud**: ***"Whether you write `useState(loadSavedLikes())` with parentheses or `useState(loadSavedLikes)` without parentheses, the screen starts at `Likes: 10` and increments to `Likes: 11` and `Likes: 12` when clicked, so on the screen they look like they work the exact same way, but under the hood they are NOT the same thing!"*** Explain why: in JavaScript, arguments inside parentheses `useState(...)` are evaluated **before** `useState` is called. So `useState(loadSavedLikes())` runs `loadSavedLikes()` on every re-render and hands the returned `10` to `useState`, which then ignores it on every render after the first. Passing `useState(loadSavedLikes)` hands the function reference to `useState`, and React only invokes it during the initial render.
- **Root Distinction**:
  - *Junior blurred view*: Because React ignores the initial state argument after the first render, writing `useState(loadSavedLikes())` will only call `loadSavedLikes()` on the first render.
  - *Senior grounding*: React cannot prevent JavaScript from evaluating the argument expression `loadSavedLikes()` before `useState` is entered; to defer execution so only the initial render runs the setup code, you must pass the initializer function reference `useState(loadSavedLikes)` without `()`.
- **Real Beginner Mistake (events, in order)**:
  1. A developer writes a helper function `function loadSavedLikes() { console.log('Reading saved likes...'); return 10; }` that computes the starting like count for `StoryCard`.
  2. Inside `StoryCard`, the developer writes `const [likes, setLikes] = useState(loadSavedLikes());` with parentheses after `loadSavedLikes`.
  3. On initial page load, JavaScript calls `loadSavedLikes()`, logs `'Reading saved likes...'` once, and passes `10` into `useState(10)`, rendering `Likes: 10`.
  4. The user clicks `Like` twice to increment the count to `11` and `12`.
  5. On each click, React re-runs `StoryCard()`, and before `useState` even runs, JavaScript evaluates `loadSavedLikes()` again, logging `'Reading saved likes...'` a second time and a third time even though React throws away the returned `10` on both re-renders.
- **Interview Depth**:
  - How this connects directly to Lecture 11 (`onClick={handleLike}` vs. `onClick={handleLike()}`): it is the exact same JavaScript rule: writing `fn()` calls the function immediately during render, whereas writing `fn` without parentheses passes the function reference so React can call it only when needed (on click for `onClick`, or on initial mount for `useState`).
  - What requirements an initializer function passed to `useState(fn)` must satisfy: it must take **no arguments**, must be **pure**, and must **return** the initial state value of any type.
  - When to pass a direct value (`useState(0)`, `useState(false)`) vs. an initializer function (`useState(loadSavedLikes)`): simple literals (`0`, `false`, `''`) cost nothing to evaluate so `useState(0)` is standard; use `useState(fn)` when creating the initial state reads `localStorage`, builds a large array, or performs an expensive calculation.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: Any parentheses `()` after `loadSavedLikes` inside `const [likes, setLikes] = useState(loadSavedLikes);`, even though `likes` starts as the number `10` (not as a function).
    - **Who supplies it**: On the initial render, React checks `typeof initialState === 'function'`, calls `loadSavedLikes()` itself internally, stores the returned number `10` as the state value, and returns `[10, setLikes]`.
    - **What JavaScript and React do**:
      1. On Render 1 (initial mount), `StoryCard` passes the function reference `loadSavedLikes` to `useState(loadSavedLikes)`.
      2. React sees that the initial state argument is a function, calls `loadSavedLikes()` once, stores its return value `10`, and returns `[10, setLikes]`.
      3. On Render 2 (after clicking `Like`), `StoryCard` again passes the function reference `loadSavedLikes` to `useState(loadSavedLikes)`.
      4. Because the component is already mounted, React ignores the argument completely, never calls `loadSavedLikes()`, and returns `[11, setLikes]`.
- **React Does**:
  - When `StoryCard` writes `const [likes, setLikes] = useState(loadSavedLikes());` and the user clicks `Like` twice, the screen updates from `Likes: 10` to `Likes: 11` and `Likes: 12`, and the Console logs `loadInitialLikesDirect ran, count: 1` on initial load, `loadInitialLikesDirect ran, count: 2` on the first click, and `loadInitialLikesDirect ran, count: 3` on the second click.
  - When `StoryCard` writes `const [likes, setLikes] = useState(loadSavedLikes);` without parentheses and the user clicks `Like` twice, the screen updates from `Likes: 10` to `Likes: 11` and `Likes: 12`, and the Console logs `loadInitialLikesRef ran, count: 1` on initial load and logs **zero** additional calls on the first and second clicks.
- **Example Step**: Adds `function loadSavedLikes()` (returning `10`) to `src/components/StoryCard.jsx` and updates `useState` in `StoryCard` to `const [likes, setLikes] = useState(loadSavedLikes);` so the card starts at `Likes: 10` and runs `loadSavedLikes` only once on mount.
- **Code names**: `src/components/StoryCard.jsx`, `loadSavedLikes`, `useState(loadSavedLikes())`, `useState(loadSavedLikes)`, `likes`, `setLikes`, `'Reading saved likes...'`, `'Likes: 10'`, `'Likes: 11'`, `'Likes: 12'`
- **Visual idea**: Side-by-side Console and render-step comparison of `useState(loadSavedLikes())` (running `loadSavedLikes` on Render 1, Render 2, and Render 3 and throwing away the result on Renders 2 and 3) versus `useState(loadSavedLikes)` (running `loadSavedLikes` on Render 1 only and skipping it on Renders 2 and 3).

### Principle 3: Call Multiple `useState` Hooks Unconditionally at the Top Level So Call Order Never Changes
- **Handle**: `multiple-states-and-call-order`
- **Rule**: Give a component as many independent `useState` variables as it needs, and always call every Hook unconditionally at the very top level of the component function (never inside `if`, loops, or nested functions, and never after an early `return`) because React matches each `useState` call to its stored state by its call order index.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - Valid top-level multiple Hooks:
      - `const [likes, setLikes] = useState(loadSavedLikes);` (Hook call #1 -> `Slot 0`)
      - `const [showSummary, setShowSummary] = useState(false);` (Hook call #2 -> `Slot 1`)
    - Broken conditional Hook:
      - Calling `const [showSummary, setShowSummary] = useState(false);` after `if (likes > 10) return ...` or inside `if (likes > 10) { ... }`.
  - **Human image**: Notice that when you call `useState(0)` and `useState(false)`, you never pass a variable name like `'likes'` or `'showSummary'` into `useState(...)`! How on earth does React know which value belongs to `likes` and which value belongs to `showSummary`? Picture React keeping a numbered row of lockers (`Locker 0`, `Locker 1`) for the component:
    - The **first** `useState` call that runs always opens **Locker 0** (`10`).
    - The **second** `useState` call that runs always opens **Locker 1** (`false`).
    As long as every render calls the exact same Hooks in the exact same order (`Locker 0` first, `Locker 1` second), every variable gets its own memory back. If you put a `useState` call inside an `if` block or after an early `return`, the locker numbers shift on the next render and React crashes!
  - **Exact nuance of confusion to state out loud**: ***"When you write `const [likes, setLikes] = useState(10)` and `const [showSummary, setShowSummary] = useState(false)`, it looks like React knows the names `likes` and `showSummary`, but React CANNOT see your variable names at all!"*** Explain clearly: JavaScript evaluates `useState(...)` on the right side of `=` **before** assigning the returned array to `[likes, setLikes]` on the left side. React only sees *"first `useState` call (`index 0`)"* and *"second `useState` call (`index 1`)"*. That is why calling `useState` inside an `if` statement or after an early `return` is forbidden even when it looks like ordinary JavaScript.
- **Root Distinction**:
  - *Junior blurred view*: `useState` magically inspects the left-hand variable name (`likes` vs. `showSummary`), so putting `useState` inside an `if` block or after an early `return` is harmless.
  - *Senior grounding*: React tracks a component's Hooks in an internal sequential list (`[slot 0, slot 1, ...]`) indexed by call counter during each render; every `useState` call must execute unconditionally at the top level in the exact same order on every render.
- **Real Beginner Mistake (events, in order)**:
  1. A developer wants `StoryCard` to track both `likes` and a boolean `showSummary` that toggles whether `<p className="summary-text">{summary}</p>` is visible.
  2. The developer places `const [likes, setLikes] = useState(loadSavedLikes);` at the top of `StoryCard`, adds an early return `if (likes > 10) { return <p>Popular story!</p>; }` (or wraps the second Hook in `if (likes > 10)`), and writes `const [showSummary, setShowSummary] = useState(false);` below the condition.
  3. On initial page load (`likes` is `10`), both `useState` calls run in order (`Slot 0` = `10`, `Slot 1` = `false`), and the card renders normally.
  4. The user clicks `Like`, updating `likes` to `11` and triggering a re-render.
  5. On the re-render, the conditional branch changes how many `useState` calls execute during `StoryCard()`.
  6. React detects that the Hook call count or order on this render does not match the previous render and throws a runtime error (`Rendered fewer hooks than expected. This may be caused by an accidental early return statement.` or `Rendered more hooks than during the previous render.`).
- **Interview Depth**:
  - Walk through the internal mental model from `react.dev`'s `<DeepDive>` ("How does React know which state to return?"): inside React, each component instance holds an array of state pairs (`componentHooks = []`) and a pointer (`currentHookIndex = 0`) that resets to `0` at the start of every render and increments (`currentHookIndex++`) each time `useState` is called.
  - When to use multiple `useState` calls vs. one state variable: when two values are unrelated and change independently (such as `likes` incremented by the `Like` button and `showSummary` toggled by the `Show summary` button), keep them as two separate `useState` calls at the top of the component.
  - Why any early `return` (such as `if (!isPublished) return null;` from Lecture 10) must be placed **after** all `useState` calls at the top of the component, never above them.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: Any key or string identifier passed into `useState(loadSavedLikes)` or `useState(false)` to tell React which state is `likes` and which state is `showSummary`.
    - **Who supplies it**: React's internal Hook call counter (`0`, `1`) during each render of `StoryCard` maps the first `useState` call to index `0` (`likes`) and the second `useState` call to index `1` (`showSummary`).
    - **What JavaScript and React do**:
      1. At the start of rendering `StoryCard`, React resets its internal Hook index for this component to `0`.
      2. The first line `const [likes, setLikes] = useState(loadSavedLikes)` runs at index `0` and reads/returns the number pair `[10, setLikes]`.
      3. The second line `const [showSummary, setShowSummary] = useState(false)` runs at index `1` and reads/returns the boolean pair `[false, setShowSummary]`.
      4. When the user clicks `Show summary`, `handleToggleSummary` calls `setShowSummary(!showSummary)`, updating slot `1` to `true` while slot `0` stays `10`.
- **React Does**:
  - When `StoryCard` places an early `return` before its second `useState` call and a state update triggers that early `return`, React throws the uncaught runtime error: `Rendered fewer hooks than expected. This may be caused by an accidental early return statement.`.
  - When `StoryCard` places a second `useState` call inside `if (likes > 0)` so the second Hook runs only on the re-render, React logs `React has detected a change in the order of Hooks called by ConditionalIfHookCard.` and throws the uncaught runtime error: `Rendered more hooks than during the previous render.`.
  - When `StoryCard` declares both `const [likes, setLikes] = useState(loadSavedLikes);` and `const [showSummary, setShowSummary] = useState(false);` unconditionally at the top of `StoryCard`, clicking `Show summary` changes the button text from `Show summary` to `Hide summary` and renders `<p class="summary-text">The park on Main Street opens at noon.</p>` while `<p class="likes-text">` keeps its current `Likes` count with zero Console errors.
- **Example Step**: Updates `src/components/StoryCard.jsx` by adding a second state variable `const [showSummary, setShowSummary] = useState(false);` at the top of `StoryCard`, adding `<button className="toggle-btn" onClick={handleToggleSummary}>{showSummary ? 'Hide' : 'Show'} summary</button>`, and conditionally rendering `{showSummary && <p className="summary-text">{summary}</p>}`.
- **Code names**: `src/components/StoryCard.jsx`, `showSummary`, `setShowSummary`, `const [showSummary, setShowSummary] = useState(false)`, `handleToggleSummary`, `setShowSummary(!showSummary)`, `{showSummary ? 'Hide' : 'Show'} summary`, `{showSummary && <p className="summary-text">{summary}</p>}`, `Rendered fewer hooks than expected. This may be caused by an accidental early return statement.`, `Rendered more hooks than during the previous render.`
- **Visual idea**: A `tree` diagram showing React's internal `Slot 0` (`likes`) and `Slot 1` (`showSummary`) array during a normal render versus what happens to the slot index when a Hook is skipped or added inside an `if` condition.

### Principle 4: State Is Isolated and Private to Each Rendered Component Instance
- **Handle**: `isolated-private-instance-state`
- **Rule**: State is attached to each individual rendered component instance on the screen, not to the component function definition itself: rendering `<StoryCard />` twice gives each card its own separate state in memory, and the parent `App` component cannot read or change a child's state.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - `function App() { return (<main><StoryCard title="New Park Opens Today" ... /><StoryCard title="Library Extends Hours" ... /></main>); }`
  - **Human image**: A cookie cutter (`function StoryCard`) versus two cookies stamped out onto a baking tray (the first `<StoryCard />` and the second `<StoryCard />` on screen). Both cards were stamped from the same `StoryCard` function, but once they sit in two separate spots on the page, React gives each card its own separate clipboard of state slots (`Card 1: [likes, showSummary]` and `Card 2: [likes, showSummary]`). Putting frosting on the first cookie never frosts the second cookie.
  - **Exact nuance of confusion to state out loud**: ***"Because both `<StoryCard />` tags in `App.jsx` call the exact same `function StoryCard` in `StoryCard.jsx`, it is easy to think they share the same `likes` and `showSummary` variables, but they do NOT share state at all!"*** State does not live inside the `StoryCard.jsx` file or on the `StoryCard` function; React attaches a separate state array to each `<StoryCard />` tag on the screen.
- **Root Distinction**:
  - *Junior blurred view*: Because `const [likes, setLikes] = useState(loadSavedLikes)` is written once inside `StoryCard.jsx`, rendering two `<StoryCard />` components on the page will make both cards share the same `likes` count.
  - *Senior grounding*: State is local and private to a specific component instance at its position in the render tree; each rendered `<StoryCard />` gets its own independent Hook array in React, and neither the sibling `<StoryCard />` nor the parent `App` has access to it.
- **Real Beginner Mistake (events, in order)**:
  1. A developer wants two `<StoryCard />` components to have separate counters and fears that reusing `<StoryCard />` twice in `App.jsx` will link their counts together, so the developer duplicates `StoryCard.jsx` into `StoryCardOne.jsx` and `StoryCardTwo.jsx` (or moves `let likes = 0` outside the component at the top of `StoryCard.jsx`, where both cards accidentally mutate the same module-level variable).
  2. When a variable is declared at module scope outside `function StoryCard`, both `<StoryCard />` instances read and mutate the same shared variable across the file instead of having isolated per-card memory.
  3. By contrast, when `const [likes, setLikes] = useState(loadSavedLikes)` and `const [showSummary, setShowSummary] = useState(false)` live inside `function StoryCard`, rendering `<StoryCard />` twice in `App.jsx` automatically gives each card its own private state without duplicating the component file.
- **Interview Depth**:
  - What "isolated and private" means in both directions:
    1. **Isolated between siblings**: rendering `<StoryCard />` twice creates two completely independent state memories (`Card 1` can have `Likes: 12` and `showSummary: true` while `Card 2` has `Likes: 10` and `showSummary: false`).
    2. **Private from the parent**: unlike `props` (which `App` passes down and controls), `App` cannot read or modify `StoryCard`'s `likes` or `showSummary` state.
  - Forward bridge to `Q24 #lifting_state`: what if you *do* want two components on screen to stay in sync and share the same state? You remove the state from the individual child components and move ("lift") it up into their closest shared parent component (`Q24 #lifting_state`).
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: Any `id` or instance key passed into `useState` inside `StoryCard.jsx` to keep the first `<StoryCard />`'s state separate from the second `<StoryCard />`'s state.
    - **Who supplies it**: React attaches a separate state list to each `<StoryCard />` node in the rendered component tree inside `<main>`.
    - **What JavaScript and React do**:
      1. `App` returns `<main>` containing two `<StoryCard />` children: the first for `'New Park Opens Today'` and the second for `'Library Extends Hours'`.
      2. React creates two separate component instances in its tree, each with its own `[Slot 0, Slot 1]` state array initialized to `[10, false]`.
      3. When the user clicks `Like` twice and clicks `Show summary` on the first card, React calls `setLikes` and `setShowSummary` bound to the **first** instance only, re-rendering the first `<StoryCard />` with `[12, true]` while the second `<StoryCard />` stays untouched at `[10, false]`.
- **React Does**:
  - When `App.jsx` renders `<StoryCard title="New Park Opens Today" summary="The park on Main Street opens at noon." />` and `<StoryCard title="Library Extends Hours" summary="The central library stays open until 9 PM." />`, and the user clicks `Like` twice and clicks `Show summary` on the first card:
    - The first card in the `Elements` panel renders `<h3>New Park Opens Today</h3><p class="likes-text">Likes: 12</p><button class="like-btn">Like</button><button class="toggle-btn">Hide summary</button><p class="summary-text">The park on Main Street opens at noon.</p>`.
    - The second card in the `Elements` panel renders `<h3>Library Extends Hours</h3><p class="likes-text">Likes: 10</p><button class="like-btn">Like</button><button class="toggle-btn">Show summary</button>` (with no `<p class="summary-text">` node).
- **Example Step**: Completes the 4-file application (`index.html`, `src/main.jsx`, `src/App.jsx`, and `src/components/StoryCard.jsx`) by rendering a second `<StoryCard title="Library Extends Hours" summary="The central library stays open until 9 PM." />` below the first card in `src/App.jsx`.
- **Code names**: `index.html`, `src/main.jsx`, `src/App.jsx`, `src/components/StoryCard.jsx`, `App`, `StoryCard`, `'New Park Opens Today'`, `'The park on Main Street opens at noon.'`, `'Library Extends Hours'`, `'The central library stays open until 9 PM.'`, `'Likes: 12'`, `'Likes: 10'`, `'Hide summary'`, `'Show summary'`
- **Visual idea**: Side-by-side view of the two `<StoryCard />` instances on the page and their two separate React state arrays in memory (`Card 1: [12, true]` with its summary open vs. `Card 2: [10, false]` with its summary hidden).

## Interview Points
1. Ordinary local variables (`let likes = 0`) fail to update the UI across renders for two reasons: mutating a local variable (`likes = likes + 1`) does not notify React to trigger a re-render, and every time React does re-render the component, it calls the function from scratch and re-initializes the local variable to its starting value.
2. Calling `const [likes, setLikes] = useState(0)` hooks into React's external state memory and returns a two-element array unpacked via JavaScript array destructuring: the current state value (`likes`) stored by React across renders, and a setter function (`setLikes`) that saves the next value and schedules a re-render of the component.
3. React uses the initial value passed to `useState(initialValue)` only on the first render and ignores it on subsequent renders; if computing the initial state requires calling a function (`loadSavedLikes`), pass the initializer function reference without parentheses (`useState(loadSavedLikes)`) rather than `useState(loadSavedLikes())` so JavaScript does not execute the function on every re-render.
4. A component can call `useState` multiple times to hold independent state values, and React matches each `useState` call to its stored state slot by its sequential call order index (`0, 1, 2...`) during render rather than by variable names, which is why Hooks must always be called unconditionally at the top level of the component function (never inside `if` blocks, loops, or after early returns).
5. State is isolated and private to each rendered component instance at its position on the screen: rendering `<StoryCard />` twice gives each instance its own independent state in memory, and a parent component cannot read or modify a child's internal state (unless you lift the state up into the parent).
