---

## Authorized Scope

- **Owns**:
  - What React is: a JavaScript library for building user interfaces from small, isolated pieces of code called components.
  - Declarative UI vs. imperative DOM manipulation: describing what the screen should look like for the current data (`<p>Items: {count}</p>` and `<button>Buy {count} items</button>`) instead of writing step-by-step DOM mutation instructions (`items.textContent = ...`, `buy.textContent = ...`) that go out of sync when one target is forgotten.
  - Component-based architecture: bundling a UI piece's markup and data into a reusable JavaScript function (`Cart` in `Cart.jsx`) placed as a JSX tag (`<Cart />` inside `App.jsx`), and keeping a single variable (`count`) as the source of truth for every place inside the component that displays it.
  - Virtual DOM (lightweight UI descriptions in memory): why replacing a container with `innerHTML` destroys the live `<input>` DOM node and wipes out the shopper's typed note (`"Please ring the bell"`) and cursor focus, whereas React compares the previous and next UI descriptions in memory and updates only the changed text nodes (`2` to `3`).
- **Excludes (Deferred to Later Lessons)**:
  - Component naming rules (`PascalCase` compiler rule), multi-line `return (` ASI trap, and top-level vs. nested component identity (`Q04 #components`).
  - Passing `props` from a parent component to a child component (`Q05 #props`).
  - `createRoot` and `main.jsx` bootstrap mechanics (`Q07 #rendering_and_commit`).
  - Deep reconciliation algorithm, Fiber tree internals, and list `key` matching (`Q08 #reconciliation`, `Q11 #lists_and_keys`).
  - `useState` hook and event handler wiring (`Q12 #state_basics`, `Q09 #events`).

- **Theme**: Keeping a shopping cart box on an online store page (`Items: 3` and `Buy 3 items`) in sync when the item count changes from `2` to `3`, without forgetting a place on the screen or wiping out what the shopper typed into the delivery note box (`"Please ring the bell"`).
- **Minimal, Video-Demo-Friendly Archetypical Example (`Cart.jsx`)**:

  - `Way 2 — Declarative UI in React`: You write a component function that returns JSX describing the cart for `count`, and React updates every place that uses `{count}`.

## Principle Thread

- **Anchor**: The `Cart` component (`Cart.jsx` placed inside `App.jsx`) displaying `count = 3` across `<p>Items: {count}</p>`, `<button>Buy {count} items</button>`, and (in Principle 3) `<input placeholder="Note to the shop" />`.
- **Axis**: How React turns data into a live webpage: **How you describe the UI** (Principle 1: Declarative UI) $\rightarrow$ **How you organize the UI into pieces** (Principle 2: Component-Based Architecture) $\rightarrow$ **How React updates the live DOM without destroying untouched elements** (Principle 3: Virtual DOM).
- **Why This Axis**: Each step answers the question raised by the previous one: once you declare the UI from `count` (P1) and package it into a reusable `<Cart />` component (P2), a thoughtful developer immediately asks whether returning the whole `<section>` on every update recreates the DOM from scratch like `innerHTML`—which P3 answers with the virtual DOM comparison.
- **Spoken Preview**: *"React is a JavaScript library for building user interfaces around three core ideas: declarative UI, where you describe what the screen should show for the current data; component-based architecture, where you build the page from self-contained functions that bundle markup and logic; and the virtual DOM, where React compares lightweight element descriptions in memory and updates only the exact DOM nodes that changed."*
- **Closing Line**: *"Describe the UI from data in a component, and let React's virtual DOM touch only the real DOM nodes that changed."*

## Principles

### Principle 1: Declarative UI — Describe What the Screen Should Look Like
- **Handle**: Declarative UI
- **Thread Step**: 1 of 3 — Describe the cart's markup from `count` so every place on screen stays in sync.
- **Rule**: Describe what the screen should look like for the current data using JSX curly braces `{count}`, and let React update the browser DOM.
- **Root Distinction**:
  - *Junior Blurred View*: Updating a variable and updating every DOM node that displays it feel like one manual chore (`textContent` line by line).
  - *Senior Root Grounding*: **Giving step-by-step DOM instructions** (imperative) and **describing the screen for the current data** (declarative) are two opposite ways to build a UI (`### Giving step-by-step DOM instructions vs. describing what the screen should show`).
- **Reader Question**: *Why do plain-JavaScript pages show `Items: 3` on one line and `Buy 2 items` on the button, and how does React prevent that mismatch?*
- **Real Beginner Mistake (Daily Coding)**: Updating `items.textContent = 'Items: ' + count` in plain JavaScript while forgetting `buy.textContent = 'Buy ' + count + ' items'`, leaving the line at `3` and the button stuck at `2`.
- **Interview Depth (Nuance / Follow-Up)**: Does declarative mean React has no DOM updates? No—React performs the imperative `textContent` DOM updates for you under the hood so your component code stays declarative.
- **React Does**: Evaluates `{count}` in `<p>Items: {count}</p>` and `<button>Buy {count} items</button>` and writes `3` into both DOM text nodes automatically.
- **River Progression**: Introduces the minimal two-element `Cart.jsx` component (`<p>Items: {count}</p>` and `<button>Buy {count} items</button>`).
- **Embedded UI Browser Preview & Visual Comparison**:
  - `::: row` comparing `Plain JavaScript` (`shop size=mini` with `text: Items: 3 | good` and `button: Buy 2 items | bad | old count`) vs. `React` (`shop size=mini` with `text: Items: 3 | good` and `button: Buy 3 items | good`).
  - `tree dir=right` Box-to-Boxes comparison of Imperative DOM steps (`!`) vs. Declarative JSX description (`+`).
- **Drafted Principle Box**:
  > [!PRINCIPLE]
  > **Principle 1: Declarative UI: Describe What the Screen Should Show for the Current Data**
  >
  > *Write JSX that plugs your data variable into every place that displays it, and let React update the browser DOM.*
  >
  > In plain JavaScript, you must find and update each DOM element by hand whenever a number changes, and forgetting even one element leaves the screen out of sync. In React, you declare what the markup looks like for the current value of your variable, and React updates every matching place on the page together.

### Principle 2: Component-Based Architecture — Build UIs from Reusable Pieces
- **Handle**: Component-Based Architecture
- **Thread Step**: 2 of 3 — Bundle the cart's data and markup into a self-contained `Cart` component placed inside `App` with `<Cart />`.
- **Rule**: Organize each piece of the user interface into its own component function that owns its data and markup, and place it on the page with a JSX tag such as `<Cart />`.
- **Root Distinction**:
  - *Junior Blurred View*: Splitting HTML into files and keeping JavaScript selectors in a separate script file feel normal, or copying a hardcoded number `2` into a second line inside JSX feels harmless.
  - *Senior Root Grounding*: **Splitting HTML and JavaScript across separate files by technology** vs. **bundling one UI piece's markup and data together in a component function** (`### Splitting files by technology vs. bundling each UI piece into a component`).
- **Reader Question**: *How do we package the shopping cart into its own reusable piece, and what happens if one line inside the component hardcodes `2` instead of reading `{count}`?*
- **Real Beginner Mistake (Daily Coding)**: Leaving a hardcoded number `<button>Buy 2 items</button>` inside `Cart.jsx` instead of `<button>Buy {count} items</button>`, so when `count` becomes `3`, the line says `Items: 3` while the button still says `Buy 2 items`.
- **Interview Depth (Nuance / Follow-Up)**: Why don't `<App>` and `<Cart>` appear in Chrome's Elements panel? Because components are JavaScript functions; the browser DOM only receives the HTML tags (`<main>`, `<section>`, `<p>`, `<button>`) those functions return.
- **React Does**: Calls `App`, sees `<Cart />`, calls `Cart`, and builds the browser DOM from the returned `<main>` and `<section>` HTML tags.
- **River Progression**: Places `<Cart />` inside `App.jsx` (`import Cart from './Cart.jsx'`) and inspects the resulting DOM in the Elements panel.
- **Embedded UI Browser Preview & Visual Comparison**:
  - `::: row` comparing hardcoded `Buy 2 items` (`shop size=mini` with `button: Buy 2 items | bad | hardcoded 2`) vs. `{count}` in both places (`shop size=mini` with `button: Buy 3 items | good`).
  - `dom` Elements panel showing `<main>`, `<section>`, `<p>Items: 3</p>`, `<button>Buy 3 items</button>` with no `<App>` or `<Cart>` tags.
- **Drafted Principle Box**:
  > [!PRINCIPLE]
  > **Principle 2: Component-Based Architecture: Bundle Markup and Data into Reusable Component Functions**
  >
  > *Package each piece of the interface into a component function that returns JSX, and read the component's variable in every line that shows that data.*
  >
  > A component keeps the data and the markup for one part of the page together in one function. Another component can place that piece anywhere with a single tag, and every line inside the component that reads the variable in curly braces stays in sync.

### Principle 3: Virtual DOM — Update Only What Changed So State Survives
- **Handle**: Virtual DOM
- **Thread Step**: 3 of 3 — Add `<input placeholder="Note to the shop" />` to `Cart.jsx` and prove why React's virtual DOM keeps the shopper's typed note `"Please ring the bell"` and cursor focus when `count` changes from `2` to `3`.
- **Rule**: Let React compare lightweight virtual DOM descriptions in memory and update only the changed DOM nodes; never replace a live container with `innerHTML`.
- **Root Distinction**:
  - *Junior Blurred View*: Returning `<section>...</section>` from `Cart` on every update looks like it replaces the whole `<section>` in the browser DOM, just like `cart.innerHTML = ...`.
  - *Senior Root Grounding*: **Replacing real DOM elements with `innerHTML`** and **comparing lightweight virtual DOM objects in memory before touching the real DOM** are two completely different operations (`### Replacing the whole DOM box with innerHTML vs. updating only the changed text with the virtual DOM`).
- **Reader Question**: *If `Cart` returns the whole `<section>` every time `count` changes, why doesn't React wipe out what the shopper typed into the `<input>` box the way `innerHTML` does?*
- **Real Beginner Mistake (Daily Coding)**: Rebuilding a container with `cart.innerHTML = ...` on update, which destroys the existing `<input>` DOM node and erases the shopper's typed note (`"Please ring the bell"`) and cursor focus.
- **Interview Depth (Nuance / Follow-Up)**: What is the virtual DOM physically? It is a tree of plain JavaScript objects in memory describing the tags and text; comparing two plain objects in memory and changing two text nodes is cheap and keeps untouched DOM nodes alive.
- **React Does**: Runs `Cart` to get the new virtual DOM description for `count = 3`, compares it against the previous description for `count = 2`, sees that only the two text nodes changed from `2` to `3`, updates those two text nodes in the real DOM, and leaves the `<input>` DOM element untouched.
- **River Progression**: Adds `<input placeholder="Note to the shop" />` between `<p>Items: {count}</p>` and `<button>Buy {count} items</button>` inside `Cart.jsx`.
- **Embedded UI Browser Preview & Visual Comparison**:
  - `::: row` comparing `Plain JavaScript (innerHTML)` (`shop size=mini` showing `input: Note to the shop | bad | empty again` + `dom` panel showing all 3 child nodes replaced with `!`) vs. `React (Virtual DOM)` (`shop size=mini` showing `typed: Please ring the bell | good | still here` + `dom` panel showing only `<p>` and `<button>` updated with `+` while `<input>` stays untouched with `*`).
- **Drafted Principle Box**:
  > [!PRINCIPLE]
  > **Principle 3: Virtual DOM: Compare in Memory and Update Only the Changed DOM Nodes**
  >
  > *Return the full JSX description from your component on every update; React compares the new virtual DOM tree against the previous one in memory and patches only the real DOM nodes that changed.*
  >
  > Replacing a container with `innerHTML` destroys every real DOM element inside it and builds new ones, which wipes out typed input text and cursor focus. React's virtual DOM compares lightweight JavaScript descriptions in memory first and updates only the changed text nodes, so untouched inputs keep their typed text and focus.

## Senior Answer

React is a JavaScript library for building user interfaces around three core characteristics. First, React is declarative: instead of writing step-by-step DOM instructions like `textContent` for every element and risking a mismatch when one line is forgotten, you describe what the UI should look like for the current data using JSX, and React updates every place on the screen that reads that data. Second, React is component-based: you split the page into self-contained JavaScript functions called components, such as `Cart` inside `App`, where each component bundles its own data and markup and can be placed with a tag like `<Cart />`. Third, React uses a virtual DOM: when data changes, your component returns a new lightweight JavaScript description of its UI in memory, and React compares it against the previous description so it updates only the exact real DOM nodes that changed, preserving live browser state like typed text and cursor focus inside an `<input>`.
