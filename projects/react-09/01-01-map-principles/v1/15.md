## Authorized Scope
Lesson 16 teaches why a state variable keeps its old value after its setter is called. Each render gets a snapshot of the state: one fixed value, held in a `const` of that render. The JSX and the event handlers of a render are all built from that value. A setter does not change the variable we already have. It asks for a new render, in which `useState` returns the new value. So every line of the handler after the setter still reads the old value. When the handler needs the new value, it computes it once into a constant and uses that constant twice. A function the handler creates keeps the same old value, even when it runs seconds later. One passed to `setTimeout` is the common case. That is a closure. The lesson builds on Q14, where the setter asked React to run the component again. It also builds on Q15, where the page changed only after the handler ended. The example is the article card's like count.

## Theme and Options
- **Theme**: We set state and read it on the next line, or a moment later. Which value does our code see, and why?
- **Options**: none (starting point: the state variable of Q14, read as if it were an ordinary variable that the setter changes)
- **This lesson teaches**: state as a snapshot

## Principle Thread
- **Anchor**: State as a snapshot: each render sees one fixed value of its state
- **Axis**: time after the setter call: right away, in the rest of the handler; and later, in code that runs after a delay
- **Why This Axis**: The two steps follow the clock, and the second needs the first. The reader first meets the old value on the very next line, where the snapshot can be seen and fixed. Only then does the same old value in a timer three seconds later make sense, because the timer's function was made by the same render. Two axes were rejected. "Reading the value, then sending it" splits one mistake into two places. "One click, then many clicks" hides the role of time, which is what the second principle is about.
- **Spoken Preview**: Everything in this lesson comes down to one idea: state as a snapshot, which means that each render sees one fixed value of its state. First, snapshots, which means the rest of the handler keeps the old value: a setter asks for a new render and changes nothing in the render we are in, so when the handler needs the new value, it computes it once and uses that. Second, stale closures, which means code that runs later keeps the old value too: a function made during a render remembers that render's values, even when it runs seconds afterwards.
- **Closing Line**: The old value right after the setter, and the same old value later.

## Principles

### Principle 1: Snapshots: the rest of the handler keeps the old value
- **Handle**: `fixed-in-render`
- **Thread Step**: right after the setter
- **Rule**: After a setter, every line of the same handler still reads the old value, so when a handler needs the new value, it computes it once into a constant and uses that constant for the setter and for everything else.
- **Kind**: Model
- **Reader Question**: "I call `setLikes(likes + 1)` and log `likes` on the next line. Why does it print the old number? Did the setter fail?"
- **Reader Expects**: the setter changes `likes`, as an assignment would, so the next line reads the new number; or the setter is slow and has not finished yet
- **React Does**: React calls the component with this render's value of the state, here 0, and `likes` is a `const` of that call; the JSX and the handler are built from it; `setLikes(1)` stores 1 in React and asks for a new render; it cannot reach the `const` of the render we are in, so the next line still reads 0, and the log says 0 while the screen soon says "Likes: 1"; no amount of waiting changes that `const`; in the new render, `useState` returns 1, and that render's handler reads 1; the setter did not fail; replacing `likes` with its value in the handler, the substitution method, shows the same: `setLikes(0 + 1); console.log(0);`; three `setLikes(likes + 1)` calls are three `setLikes(0 + 1)` calls, so the count moves by 1; when the handler needs the new value, it computes it once: `const nextLikes = likes + 1`, then `setLikes(nextLikes)` and the report with `nextLikes`
- **Placement**: `const nextLikes = likes + 1;` as the first line of `handleLike`; `setLikes(nextLikes)` and every later use read `nextLikes`
- **Real Mistake**: `setLikes(likes + 1);` followed by `console.log('likes after the setter:', likes);` in `handleLike`, standing for an analytics call; the first click logs 0 and the screen shows "Likes: 1"; `const nextLikes = likes + 1` logs 1, then 2; verified in React 19.3.1, Vite 8.3.4, and Chrome
- **Fix In**: this principle
- **Importance**: the bank question and its hook; the card's Friction; reviewers flag a state variable read after its setter
- **Prediction**: on the first click, a log right after the setter prints 0, and a log of `nextLikes` prints 1
- **Required Lesson Proof**: the log after the setter; the computed value; three calls against `likes + 3`.

### Principle 2: Stale closures: code that runs later keeps the old value too
- **Handle**: `handler-keeps-its-render`
- **Thread Step**: later, after a delay
- **Rule**: A function made during a render, such as the one we pass to `setTimeout`, keeps that render's values even when it runs later; we never wait for state to change, and when the delayed code needs the new value, we give it the value we computed.
- **Kind**: Model
- **Reader Question**: "I wait three seconds with `setTimeout`, so the state has surely changed by then. Why is it still the old number?"
- **Reader Expects**: waiting gives React time to update the state, so a function that runs after the new render reads the new value
- **React Does**: a function made inside the handler reads the variables of the place where it was made: that is a closure; the handler belongs to the render in which `likes` was 0, so the function passed to `setTimeout` reads that render's `likes`, 0, however late it runs; three seconds later, after the new render, it still logs 0 while the screen shows "Likes: 1"; three quick clicks make three functions from three renders, which log 0, 1, and 2 while the screen shows 3; the same holds after `await` (Q17); it is often what we want: a message scheduled at a click describes the moment of the click, even when the user changes the screen before it runs; when the delayed code needs the new value, it reads the constant the handler computed, `nextLikes`; reading the latest value at any moment belongs to Q17's updaters and Q29's refs
- **Placement**: `const nextLikes = likes + 1;` before the timer, and `nextLikes` inside the function passed to `setTimeout`
- **Real Mistake**: `setLikes(likes + 1);` then `setTimeout(() => { console.log(likes); }, 3000);` in `handleLike`, to read the count "once the state has updated"; three seconds later the log says 0 while the screen says "Likes: 1"; `nextLikes` in the timer logs 1; verified in React 19.3.1 and Chrome
- **Fix In**: this principle
- **Importance**: the bank question's "closures"; react.dev's "State over time"; interviewers ask what a stale closure is
- **Prediction**: three quick Likes, each with a three-second timer, log 0, 1, and 2 while the screen shows "Likes: 3"
- **Required Lesson Proof**: the timer that reads `likes`: 0 after three seconds; the timer that reads `nextLikes`: 1; three quick clicks: 0, 1, 2.

## Senior Answer
State is not an ordinary variable. When React renders a component, it gives that render a snapshot of the state. That is a fixed value, held in a `const`. The JSX and the event handlers of that render are built from it. Calling the setter does not change that `const`. It stores the new value in React and asks for a new render, in which `useState` returns it. So the rest of the handler still reads the old value. Calling the setter three times with `count + 1` adds only one. If the handler needs the new value, I compute it once. Then I use it for the setter and for the other code. The same holds for code that runs later. A function passed to `setTimeout` is a closure over its render's values. It still sees the old value seconds later. That protects a delayed message from timing mistakes. When I really need the latest value, I use an updater function or a ref, never a delay.
