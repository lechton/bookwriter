## Authorized Scope
Lesson 05 teaches the shape of a React page. Each component's markup names other components, and those become its children. So the components form a tree, the render tree, with `App` at its root. React calls them from the root down, one branch at a time, and only HTML tags reach the DOM. The lesson cuts Town News's front page into components by job: `NewsHeader`, `EditorialFeed`, `ArticleCard`, `EditorialByline`, and `MostRead`. It then shows why the tree decides how data moves. A component sees only its own variables, so a child cannot read its parent's variable, and a sibling cannot read its neighbor's. A value several components need must start above them and travel down. The lesson builds on Q02, where React calls each component a tag names, and on Q04, where curly braces show a value.

## Theme and Options
- **Theme**: A page grows from a few components into many. How do they fit together, and how does a value reach the part of the page that shows it?
- **Options**: none (starting point: components side by side in `App.jsx`, each named by a tag, Q02)
- **This lesson teaches**: the component tree

## Principle Thread
- **Anchor**: The page is a tree of components: each component's markup names its children, and React builds the page from the root down
- **Axis**: the tree from its shape to its use: how it grows (nesting), where it is cut (boundaries), and what travels along it (values, downward)
- **Why This Axis**: The reader must see the tree before deciding where to cut it, because a boundary is a branch, and a branch only makes sense once nesting makes the tree. Data flow comes last because it needs both: separate branches, and a parent above them; a value can only travel down a tree that has been cut into parts. One axis was rejected. "Root, branches, leaves" orders the parts of the tree, but it puts all three principles inside the first one and leaves no place for the question of data.
- **Spoken Preview**: Everything in this lesson comes down to one idea: the page is a tree of components, and React builds it from the root down. First, the render tree, which means each component's markup names its children: App is the root, every component is the parent of the components its markup names, and React calls them branch by branch. Second, component boundaries, which means one branch of the tree for each part of the page with its own job: the header, the feed, and the story each get a component, nested where they sit on the page. Third, data flow, which means a value travels down the tree, never across it: a component cannot read a variable of its parent or of its neighbor, so a value they share starts above them both.
- **Closing Line**: The tree grows by nesting, is cut by job, and carries values down.

## Principles

### Principle 1: The render tree: each component's markup names its children
- **Handle**: `render-tree`
- **Thread Step**: how it grows: nesting makes the tree
- **Rule**: We read the components a component's markup names as its children: `App` is the root, each component is the parent of the ones it names, and React calls them from the root down, finishing one branch before the next.
- **Kind**: Model
- **Reader Question**: "I have five components side by side in `App.jsx`. How does React know which goes where?"
- **Reader Expects**: by their order in the file, the way a script runs from top to bottom
- **React Does**: `main.jsx` names `App`, so React calls `App` first; `App` returns `<NewsHeader />` and `<EditorialFeed />`, so they are its children; React calls `NewsHeader`, then `EditorialFeed`, whose markup names `ArticleCard` and `MostRead`; it calls `ArticleCard` and its child `EditorialByline` before `MostRead`; the order of the functions in the file plays no part; React keeps this tree of components, and it builds the DOM tree from the tags they return, so the Elements panel shows no component names
- **Placement**: a child appears in its parent's markup as a tag; a component named twice is two nodes
- **Real Mistake**: none; the file-order picture breaks no code by itself, and `data-flows-down` shows where the flat picture misleads
- **Importance**: the interview question's first half; Q06 to Q27 draw this tree; the card's Under the Hood
- **Prediction**: with a `console.log` in each component, the Console panel shows "App runs", "NewsHeader runs", "EditorialFeed runs", "ArticleCard runs", "EditorialByline runs", "MostRead runs", the same when `App` is defined first and `NewsHeader` last; naming `<ArticleCard />` twice prints its message twice; the Elements panel shows `<header>`, `<main>`, `<article>`, `<p>`, and `<aside>`, and no `NewsHeader`
- **Required Lesson Proof**: the Town News front page with a log in each component: the order in the Console panel; the tree drawn from the markup; the Elements panel with only HTML tags.

### Principle 2: Component boundaries: one branch of the tree for each part of the page with its own job
- **Handle**: `component-boundaries`
- **Thread Step**: where it is cut: one branch per job
- **Rule**: We give each part of the page with its own job its own component, nested where the part sits on the page, and we keep a small piece inside its parent until it grows a job of its own.
- **Kind**: Decision
- **Reader Question**: "My `App` now holds the whole front page. Should I cut it up, and where?"
- **Reader Expects**: either keep one long `App`, because the page works, or make a component for every tag, the way HTML is a tag inside a tag
- **React Does**: React builds the same DOM from one long `App` or from many components, so the page alone cannot tell; the cut decides what each function is about: `NewsHeader` holds the masthead, `EditorialFeed` the list of stories, `ArticleCard` one story, `EditorialByline` the author line, and `MostRead` the side box; a part with a job of its own gets a component even when it is used once; the byline stays a component because it has its own job inside every card, while the story's `<h2>` stays inside `ArticleCard`
- **Placement**: a component per part of the page with one job (masthead, feed, story, byline, side box); a tag that is only part of a job stays in its parent
- **Real Mistake**: none; one long `App` shows the same page, so the cost appears later, when Q06 gives each part its own data
- **Importance**: the card's Code Experiment; reviewers flag a page in one function; every later lesson assumes components with one job each
- **Review Point**: Prefer
- **Required Lesson Proof**: the front page as one long `App` and as the tree of five components: the same Elements panel, and a file whose functions each fit in one window.

### Principle 3: Data flow: a value travels down the tree, never across it
- **Handle**: `data-flows-down`
- **Thread Step**: what travels along it: values, downward
- **Rule**: We start a value that several components need above all of them and let it travel down the tree; a component never reads a variable of its parent or of its neighbor, and never reads another component's text from the page.
- **Kind**: Decision
- **Reader Question**: "`ArticleCard` needs the edition that `App` declares. Can it just read it?"
- **Reader Expects**: yes; `<ArticleCard />` sits inside `App`'s markup, so the card should see `App`'s variables, the way a nested function does
- **React Does**: a tag inside `App`'s markup is not code inside `App`'s function; `ArticleCard` is defined at the top level of the file, so it sees only its own variables and the file's; `edition` lives only inside `App`, so React's call of `ArticleCard` throws "edition is not defined", and the page goes empty; a sibling fails the same way; reading the neighbor's text from the page fails too, because no part of the page exists yet while React calls the components; a value the whole file needs and that never changes can sit at the top level of the file; a value that belongs to the page starts in the closest common parent and travels down, which Lecture 6 does with props
- **Placement**: a fixed value for the whole file at its top level; any other shared value in the closest common parent, passed down (Q06); never a definition moved inside the parent to reach its variables (Q02)
- **Real Mistake**: `ArticleCard` returns `<h2>{edition} edition</h2>` while `const edition = 'Morning'` sits inside `App`; the page goes empty, and the Console panel shows "edition is not defined"; also `NewsHeader` reading `document.getElementById('edition').textContent`, which throws "Cannot read properties of null (reading 'textContent')"; `const edition = 'Morning'` at the top of the file shows "Town News, Morning edition" and "Stories for the Morning edition"; verified in React 19.3.1 and Chrome
- **Importance**: the interview question's second half ("why does hierarchy dictate data flow"); the card's Friction; the tempting fix, a definition inside `App`, brings back Q02's bug
- **Review Point**: Do not
- **Required Lesson Proof**: `ArticleCard` reading `App`'s `edition`: the empty page and the error; `EditorialFeed` reading `NewsHeader`'s: the same; the `getElementById` lookup: the `null` error; `edition` at the top level: both texts.

## Senior Answer
React sees a page as a tree of components. The root is `App`. Every component whose tag appears in another component's markup is that component's child. React calls the tree from the root down, one branch at a time, and it builds the DOM from the tags the components return, so the DOM holds no component names. I cut a page into components by job: a header, a feed, a story, a byline. A part with its own job gets a component even if it appears once. The tree also decides how data moves. A component sees only its own variables, so a child cannot read its parent's variable, and a sibling cannot read its neighbor's. A value that several components need starts above them, in their closest common parent, and travels down. That is why React's data flows one way, from the top down.
