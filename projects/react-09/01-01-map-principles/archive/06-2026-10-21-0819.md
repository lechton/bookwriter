## Authorized Scope
Lesson 06 teaches props, the way a parent hands values to a child. The parent writes them as attributes on the child's tag. React collects them into one object and passes it as the component's only argument. The component names the props it reads inside curly braces in its parameter list. A default written beside a name fills a prop the tag leaves out. The component reads its props and never changes them: it makes a new variable instead. The lesson works on Town News's feed of three `ArticleCard`s and sends the edition from `App` down the tree. It builds on Q04, where quotes pass text and braces pass a value, and on Q05, where a shared value starts above the components that need it.

## Theme and Options
- **Theme**: One component shows many stories. How does each copy get its own headline, author, and reading time?
- **Options**: none (starting point: values fixed inside the component or at the top of the file, Q04 and Q05)
- **This lesson teaches**: props

## Principle Thread
- **Anchor**: Props are a component's arguments: the parent writes them on the tag, and the component reads them as one object
- **Axis**: the life of one prop: written on the tag, read in the function, missing from the tag, and kept unchanged
- **Why This Axis**: A prop must be written before it can be read, so the tag comes first and the parameter list second. A missing prop only makes sense once the reader knows how a present one is read, because the default is written in the same braces. Keeping a prop unchanged comes last: the reader can only be tempted to change a prop once they hold one. One axis was rejected. "Parent side, child side" splits the lesson in two and leaves defaults and the read-only rule both on the child side, with no order between them.
- **Spoken Preview**: Everything in this lesson comes down to one idea: props are a component's arguments, written by the parent and read by the component as one object. First, props, which means the attributes on a component's tag arrive as one object, its only argument: each card gets its own headline because each tag carries its own. Second, destructuring, which means the component names the props it reads, inside curly braces in its parameter list: without the braces, the whole object lands in the first name. Third, default values, which means the component names a fallback for a prop the tag leaves out: the fallback fills a missing prop, but not a null and not a zero. Fourth, read-only props, which means the component reads its props and never changes them: to show a value differently, it makes a new variable.
- **Closing Line**: Written on the tag, read by name, filled when missing, and never changed.

## Principles

### Principle 1: Props: the attributes on a component's tag arrive as one object, its only argument
- **Handle**: `props-on-the-tag`
- **Thread Step**: written on the tag
- **Rule**: We give each copy of a component its own values by writing them as attributes on its tag; React collects them into one object, the props, and passes it as the component's only argument.
- **Kind**: Model
- **Reader Question**: "My three `ArticleCard`s show the same story. How do I give each its own headline?"
- **Reader Expects**: write the headline on the tag, as an HTML attribute; the card will somehow show it
- **React Does**: React collects the attributes of each tag into one object, `{ title: 'Rail Strike Ends', readTime: 5 }`, and passes it as the first argument each time it calls the component, one object per tag; the card shows nothing of it until its code reads it; quotes pass text, so `readTime="5"` arrives as the text "5", and braces pass any value: a number, an object, a variable such as `edition`
- **Placement**: `<ArticleCard title="Rail Strike Ends" readTime={5} />` on the parent's side; the props object as the component's first parameter
- **Real Mistake**: `title="..."` written on three tags while `ArticleCard` still returns `<h2>City Library Extends Its Hours</h2>`; all three cards show the same headline, with no warning; `console.log(props)` shows three different objects; verified in React 19.3.1 and Chrome
- **Fix In**: this principle
- **Importance**: the bank's hook and the card's Friction; Q07 to Q27 pass props; interviewers open with "what are props"
- **Prediction**: `console.log(props)` prints one object per card with that tag's `title` and `readTime`; `readTime="5"` with `{readTime + 1}` shows 51, and `readTime={5}` shows 6
- **Required Lesson Proof**: three `ArticleCard` tags with different `title` and `readTime`: the log of three objects; `{props.title}` in the card: three headlines; `readTime="5"` against `readTime={5}`: 51 against 6.

### Principle 2: Destructuring: the component names the props it reads, inside curly braces in its parameter list
- **Handle**: `destructure-props`
- **Thread Step**: read in the function
- **Rule**: We read props by naming them inside curly braces in the parameter list, `({ title, readTime })`, with the same names the tag uses.
- **Kind**: Decision
- **Reader Question**: "How do I get `title` out of the props?"
- **Reader Expects**: list the names as parameters, `function ArticleCard(title, readTime)`, the way a JavaScript function takes several arguments
- **React Does**: React passes one argument, the props object; without braces, `title` holds that whole object and `readTime` is `undefined`; `{title}` then puts an object into the text, and React stops the render; braces in the parameter list unpack the properties by name, the same as `const title = props.title`; a name that does not match the attribute is `undefined`, so its place stays empty
- **Placement**: `function ArticleCard({ title, readTime })`; or `function ArticleCard(props)` with `props.title`
- **Real Mistake**: `function ArticleCard(title, readTime)` with `<h2>{title}</h2>`; the page goes empty, and the console shows "Objects are not valid as a React child (found: object with keys {title, readTime})"; `({ title, readTime })` shows each headline; verified in React 19.3.1 and Chrome
- **Importance**: an official react.dev Pitfall; the first crash props bring; reviewers expect destructured props
- **Review Point**: Do not
- **Required Lesson Proof**: `ArticleCard(title, readTime)`: the empty page and the error; `({ title, readTime })`: three headlines; `({ headline })` for `title=`: an empty heading.

### Principle 3: Default values: the component names a fallback for a prop the tag leaves out
- **Handle**: `default-values`
- **Thread Step**: missing from the tag
- **Rule**: When a component has a sensible fallback, we write it beside the prop's name, `readTime = 3`, and we remember that it fills only a missing or `undefined` prop, never `null` or `0`.
- **Kind**: Decision
- **Reader Question**: "What if a parent leaves out a prop?"
- **Reader Expects**: React fills in something, or warns; or, from older tutorials, `ArticleCard.defaultProps` sets it
- **React Does**: a prop the tag leaves out is `undefined`, which shows nothing, so the card reads " min read" with no warning; React 19 ignores `defaultProps` on a function component; a default after `=` in the braces fills the prop when it is missing or `undefined`; `null` and `0` are values, so they stay: `null` shows nothing, and `0` shows 0; `readTime || 3` would replace a real 0, and `readTime ?? 3` fills `null` too
- **Placement**: `function ArticleCard({ title, readTime = 3 })`; `??` inside the braces when the data may hold `null`
- **Real Mistake**: `<ArticleCard title="Rail Strike Ends" />` with no `readTime`; the card shows " min read"; `readTime = 3` shows "3 min read"; `ArticleCard.defaultProps = { readTime: 3 }` leaves " min read"; verified in React 19.3.1 and Chrome
- **Importance**: the card's scope; a missing prop fails with no warning; old tutorials teach the API React 19 removed
- **Review Point**: Condition
- **Required Lesson Proof**: four cards, with `readTime` missing, `undefined`, `null`, and `0`, under `readTime = 3`: 3, 3, nothing, and 0.

### Principle 4: Read-only props: the component reads its props and never changes them
- **Handle**: `props-read-only`
- **Thread Step**: kept unchanged
- **Rule**: We never change a prop or an object inside one; to show a value differently, we make a new variable, `const headline = title.toUpperCase()`, and a value that must change comes from the parent.
- **Kind**: Decision
- **Reader Question**: "Can the card change its own title, to show it in capitals?"
- **Reader Expects**: yes; props are an object, and JavaScript lets us change an object's properties
- **React Does**: the props belong to the parent, which wrote them; in development React freezes the props object, so `props.title = ...` throws a `TypeError`, and the page goes empty; the production build does not freeze it, so the same line works there and the mistake ships; the freeze covers only the top level: a change inside an object prop, `writer.name = ...`, works in both builds and reaches every component that holds the same object; a new variable leaves the props as they were; a value that must change comes from the parent as new props, or from state, which Lecture 14 teaches
- **Placement**: `const headline = title.toUpperCase()` inside the component; the change on the parent's side, never on the child's
- **Real Mistake**: `props.title = props.title.toUpperCase()` inside `ArticleCard`; in development the page goes empty, and the console shows "Cannot assign to read only property 'title' of object '#<Object>'"; in the production build the headlines show in capitals with no error; also `writer.name = writer.name.toUpperCase()` in `ArticleCard`, after which `AuthorBox`, which shows the same `writer`, shows the capitals too; `const headline = title.toUpperCase()` shows the capitals and changes nothing else; verified in React 19.3.1 and Chrome, in both builds
- **Importance**: the interview question's second half; the card's Friction and Under the Hood; the shallow case corrupts data no error reports
- **Review Point**: Do not
- **Required Lesson Proof**: `props.title = ...`: the error in development and the capitals in the production build; the `writer` object changed in `ArticleCard` and seen in `AuthorBox`; `const headline`: the capitals, and `AuthorBox` unchanged.

## Senior Answer
Props are how a parent passes data to a child. The parent writes them as attributes on the child's tag. React collects them into one object and passes it as the component's only argument, so props are to a component what arguments are to a function. I read them by destructuring in the parameter list, as in `({ title, readTime })`. Quotes pass text, so a number goes in braces. A default such as `readTime = 3` fills a prop that is missing or `undefined`, but not `null` or `0`. A component never changes its props, because they belong to the parent. In development React freezes the props object, so an assignment throws. The production build does not, and the freeze is shallow, so changing an object inside a prop changes it for every component that shares it. When I need a different value, I make a new variable. When the value itself must change, the parent passes new props, or the component uses state.
