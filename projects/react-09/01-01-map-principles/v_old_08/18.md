## Authorized Scope
Lesson 18 teaches how to change an object that lives in state. It works on one component, `ProfileEditor`, from The National Times dashboard. It holds a `profile` object with a `title` and an `author` object inside it. Changing a property of that object in place is a mutation. React does not stop us from mutating. But the setter compares the new value with the current one using `Object.is`. A mutated object is still the same object, so React skips the render and the screen keeps the old text. So we treat every object in state as read-only. To change it, we create a new object with spread syntax and pass it to the setter. Spread copies only one level. A change inside `author` needs a new copy of each object on the way down. One change handler can serve many fields with a computed property name. The lesson builds on Q06, read-only props, Q14, `useState`, Q16, snapshots, and Q17, the updater function.

## Principles

### Principle 1: The setter skips the render when it gets the same object
- **Handle**: `same-object-no-render`
- **Kind**: Model
- **Reader Question**: "Can I just write `profile.author.bio = 'New bio'` and then call `setProfile(profile)`?"
- **Reader Expects**: yes; every setter call so far led to a render (Q14, Q15); a habit from plain JavaScript, where an object is changed in place, and from Vue, whose reactive objects notice every assignment
- **React Does**: the assignment changes the object React already holds; `setProfile(profile)` hands back that same object; `Object.is` compares current and next and finds the same object; React skips the render; no body log; the screen keeps "Old bio"; a click on the unrelated Views button renders, reads the changed object, and shows "New bio"; with no setter call at all, nothing renders either
- **Placement**: the setter looks only at which object it receives, not at what is inside it; a mutated object is still the current object
- **Real Mistake**: `profile.author.bio = 'New bio'; setProfile(profile)`, the card's Friction: no body log, the screen keeps "Old bio", and "New bio" appears only after a click on Views (React 19.3.0)
- **Fix In**: `copy-every-level`
- **Importance**: the interview question asks why React needs a new reference; the late, surprising update is a classic production bug
- **Prediction**: a mutation followed by `setProfile(profile)` produces no body log; the next render caused by any other state shows the mutated value.
- **Required Lesson Proof**: `ProfileEditor` with `useState(initialProfile)`, a body log, a Views counter, and a "Change bio" button whose handler assigns `profile.author.bio` and calls `setProfile(profile)`; the click logs nothing and the screen keeps "Old bio"; a click on Views logs a render and shows "New bio".

### Principle 2: Hand the setter a new object that copies the old fields first
- **Handle**: `new-object-with-spread`
- **Kind**: Decision
- **Reader Question**: "I only want to change the title. Can I call `setProfile({ title: 'Chief Editor' })`?"
- **Reader Expects**: yes; React merges the title into the old profile and keeps the author; a habit from class components' `this.setState`, which merges, seen in older tutorials
- **React Does**: the setter stores the object it receives as the whole new state, with no merge; `{ title: 'Chief Editor' }` has no `author`; the next render reads `profile.author.bio` and throws "Cannot read properties of undefined (reading 'bio')"; React removes the editor from the page; `{ ...profile, title: 'Chief Editor' }` copies every old field into a new object, then the later `title` overrides the copied one; the new object fails the `Object.is` check; React renders; the screen shows "Chief Editor" and keeps "Old bio"
- **Placement**: `setProfile({ ...profile, title: 'Chief Editor' })`, with the spread first and the change after it; not `profile.title = ...`, not `{ title }` alone, and not `{ title, ...profile }`
- **Real Mistake**: `setProfile({ title: 'Chief Editor' })`, the `this.setState` habit: the render throws "Cannot read properties of undefined (reading 'bio')" and the editor disappears; `setProfile({ title: 'Chief Editor', ...profile })`, the spread written after the change: a render runs and the screen keeps "Night Editor" (React 19.3.0)
- **Importance**: the card's main subject; reviewers flag both a mutation and a lost field
- **Review Point**: Do
- **Required Lesson Proof**: a "Promote" button on `ProfileEditor` written three ways: `{ ...profile, title: 'Chief Editor' }` shows "Chief Editor" and keeps the author; `{ title: 'Chief Editor' }` makes the editor disappear with the error above; `{ title: 'Chief Editor', ...profile }` still shows "Night Editor".

### Principle 3: For a nested change, copy every object on the way down
- **Handle**: `copy-every-level`
- **Kind**: Decision
- **Reader Question**: "I copied the profile first, `const next = { ...profile }`, then wrote `next.author.bio = 'New bio'`. The new bio shows. Is that fine?"
- **Reader Expects**: yes; spread made a full copy, so changing it is safe; a habit from copying a file or a folder, where the copy holds everything inside
- **React Does**: spread copies only the top-level fields into a new object; `next.author` is the same object as `profile.author` and `initialProfile.author`; the assignment changes that shared object; `next` is a new object, so React renders and the screen shows "New bio"; `initialProfile.author.bio` is now "New bio" too; Reset, `setProfile(initialProfile)`, shows "New bio"; `{ ...p, author: { ...p.author, bio: 'New bio' } }` makes a new `author` as well; `initialProfile` keeps "Old bio"; Reset shows "Old bio"
- **Placement**: `setProfile(p => ({ ...p, author: { ...p.author, bio: 'New bio' } }))`; not `{ ...profile }` followed by `next.author.bio = 'New bio'`
- **Real Mistake**: `const next = { ...profile }; next.author.bio = 'New bio'; setProfile(next)`, a shallow copy with a nested assignment: the screen shows "New bio", `initialProfile.author.bio` is also "New bio", and Reset shows "New bio" instead of "Old bio" (React 19.3.0)
- **Importance**: shallow copies pass a quick review and still corrupt old state; interviewers ask what "shallow" means
- **Review Point**: Do
- **Required Lesson Proof**: the "Change bio" button of `ProfileEditor` with a shallow copy and a nested assignment, then Reset: the screen shows "New bio" after Reset; the nested spread, then Reset: the screen shows "Old bio".

### Principle 4: Name each field after its key, and one handler updates them all
- **Handle**: `name-matches-key`
- **Kind**: Decision
- **Reader Question**: "My editor has a title input and a desk input. Do I write a separate change handler for each one?"
- **Reader Expects**: yes, one handler per input, the way each button got its own handler in Q13; that works, and it is right, only repetitive
- **React Does**: typing fires the input's `onChange` with the event object; `e.target` is the input typed in; `e.target.name` is its `name` attribute, "title" or "desk"; square brackets in the object literal use that string as the key; `{ ...profile, [e.target.name]: e.target.value }` is a new object with that one field changed; React renders; the screen shows the typed text in that field and keeps the other
- **Placement**: one `handleChange` with `setProfile({ ...profile, [e.target.name]: e.target.value })`, and each input's `name` equal to its key in `profile`; top-level fields only; `author.bio` still needs the nested copy of `copy-every-level`
- **Real Mistake**: none; a handler per input is valid code, and an input named differently from its key is a typo, not a habit
- **Importance**: named in the card's Mechanism; reviewers flag a handler copied once per field, and interviewers ask what the square brackets do
- **Review Point**: Prefer
- **Required Lesson Proof**: `initialProfile` gains `desk: 'Metro'`; `ProfileEditor` with a title input and a desk input, supplied ready-made with `name="title"` and `name="desk"`, `value` from `profile`, and `onChange={handleChange}`; typing "Chief" in the title and then "Sports" in the desk shows "Chief" and "Sports", from one handler.

## Senior Answer
I treat every object in state as read-only. React does not stop me from mutating it. But the setter compares the new value with the current one using `Object.is`. That checks whether it is the same object, not what is inside it. A mutated object is still the same object. So React skips the render, and the screen shows the old data until something else renders. To change a field, I create a new object with spread syntax. The spread comes first and copies the old fields. The changed field comes after it and wins. Spread copies only one level. Nested objects are separate objects that both copies point to. So for a nested change, I copy every level on the way down: the profile, and then its author. Otherwise I also change the old object that earlier renders still use. For a form, one handler with a computed key, `e.target.name`, can update every field. For deep nesting, Immer can write the copies for me.
