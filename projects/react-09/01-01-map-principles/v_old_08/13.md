## Authorized Scope
Lesson 13 wires the clicks of the homepage feed. `NewsFeed` shows an `ArticleCard` for each story, and each card has a Read button and a Save button. An event handler is a function passed to an element's event prop, such as `onClick` or `onChange`. React calls it when the reader acts, not while it renders. So the prop takes the function itself, `onClick={handleClick}`, never its result. When the handler needs an argument, an arrow function wraps the call. A child tells its parent about a click through a callback prop. The parent passes `onSelect`, and the child calls it from its own button. Events bubble up from the clicked element through its parents. `e.stopPropagation()` stops the parents' handlers, and `e.preventDefault()` stops the browser's own action. Only a real `<button>` can be reached and pressed with the keyboard. The lesson builds on Q02, where a function call differs from a function reference. It also builds on Q11, where arrow functions first appeared. And it builds on Q12, where side effects were kept out of the render.

## Principles

### Principle 1: Pass the handler to `onClick`, never its result
- **Handle**: `pass-not-call`
- **Kind**: Model
- **Reader Question**: "I wrote `onClick={handlePublish()}`. Why did it run on page load and not on click?"
- **Reader Expects**: `onClick` holds code to run later, as `onclick="handlePublish()"` does in HTML
- **React Does**: braces run their expression during render; `handlePublish()` calls the function right then, and `onClick` gets what it returned, `undefined`; React keeps the value of `onClick` and calls it on each click; given a function, `onClick={handlePublish}`, it calls that function on the click and not before
- **Placement**: declare `function handlePublish() { ... }` inside the component, and pass the name without parentheses: `<button onClick={handlePublish}>`
- **Real Mistake**: `<button onClick={handlePublish()}>Publish</button>`; "PUBLISH ran" prints while the page renders, and a click afterward prints nothing; verified in React 19.3.0
- **Fix In**: this principle
- **Importance**: the card's Friction and Recap bullet 2; maps 14, 16, and 17 recall it
- **Prediction**: with `onClick={handlePublish}`, nothing prints during render, and "PUBLISH ran" prints once per click.
- **Required Lesson Proof**: the Publish button with `handlePublish()`: the log at render and silence on click; with `handlePublish`: no log at render and one per click.

### Principle 2: Wrap a call that needs arguments in an arrow function
- **Handle**: `arrow-for-arguments`
- **Kind**: Decision
- **Reader Question**: "`openArticle` needs the story's id. How do I pass it without calling it?"
- **Reader Expects**: `onClick={openArticle(story.id)}`, since that is how a function gets an argument
- **React Does**: `openArticle(story.id)` runs during render for every card; `() => openArticle(story.id)` is a new function that React keeps and calls on the click, and it calls `openArticle` with that card's id
- **Placement**: `stories.map(story => <button key={story.id} onClick={() => openArticle(story.id)}>Read</button>)`; a handler with no arguments stays `onClick={handleClick}`
- **Real Mistake**: `onClick={openArticle(story.id)}` in the feed; "open a1" and "open a2" print during render, and clicking a card prints nothing; verified in React 19.3.0
- **Importance**: the card's Naive code; every list of buttons needs an argument
- **Review Point**: Do
- **Required Lesson Proof**: two cards with `openArticle(story.id)`: both logs at render, none on click; with the arrow: one log, for the clicked card only.

### Principle 3: A child reports to its parent by calling a callback prop
- **Handle**: `callback-props-up`
- **Kind**: Decision
- **Reader Question**: "The Read button is in `ArticleCard`, but `NewsFeed` decides what opens. How does the card tell it?"
- **Reader Expects**: the child changes a value it got from the parent, or `onClick` on `<ArticleCard>` catches the clicks inside it
- **React Does**: props flow down, and a child that assigns to a prop changes only its own copy; `onClick` on a component is just a prop, and nothing happens unless the component passes it to an element; a function passed as a prop lets the child call the parent's code, with the arguments it chooses
- **Placement**: in `NewsFeed`, `function handleSelect(id) { ... }` and `<ArticleCard article={story} onSelect={handleSelect} />`; in `ArticleCard`, `<button onClick={() => onSelect(article.id)}>Read</button>`; name the prop after the action, `onSelect`, not after the browser event
- **Real Mistake**: `<ArticleCard title="Budget" onClick={() => console.log('card clicked')} />`, where `ArticleCard` never uses `onClick`; clicking the card prints nothing; verified in React 19.3.0
- **Importance**: the second part of the interview question; the bank row's filter button
- **Review Point**: Do
- **Required Lesson Proof**: `onClick` on `<ArticleCard>` with no wiring: a silent click; the child assigning `selectedId = 'a2'`: the parent still shows "Selected: none"; `onSelect` wired to the Read button: "NewsFeed selected a2" for the second card.

### Principle 4: `stopPropagation` stops the parents, `preventDefault` stops the browser
- **Handle**: `stop-or-prevent`
- **Kind**: Decision
- **Reader Question**: "Clicking Save also opened the article. Why?"
- **Reader Expects**: a click belongs only to the element that was clicked
- **React Does**: the click runs the Save button's handler, then bubbles up and runs the `onClick` of every element around it; `e.stopPropagation()` in the button's handler stops the bubbling; the browser's own action, such as following a link or submitting a form, is separate, and only `e.preventDefault()` stops it; neither call does the other's job
- **Placement**: `onClick={e => { e.stopPropagation(); onSave(article.id); }}` on a button inside a clickable card; `e.preventDefault()` in a form's `onSubmit` or a link's `onClick` when the page must not reload or navigate; neither when nothing around the element listens and the browser has no action
- **Real Mistake**: a Save `<button>` inside an `<article onClick={openArticle}>`; one click logs "button: bookmark" and then "card: open article"; verified in React 19.3.0
- **Importance**: the card's Mechanism; interviewers ask for the difference between the two calls
- **Review Point**: Condition
- **Required Lesson Proof**: Save inside the clickable card: both logs, then only the button's with `e.stopPropagation()`; a link inside the card: `e.preventDefault()` keeps the card's log and cancels the link, `e.stopPropagation()` does the reverse; a search form: `defaultPrevented` false, then true.

### Principle 5: Handle clicks on a `<button>`, not a `<div>`
- **Handle**: `real-button`
- **Kind**: Decision
- **Reader Question**: "Can I put `onClick` on a `<div>` and style it as I like?"
- **Reader Expects**: any element with `onClick` works the same for everyone
- **React Does**: React attaches the handler to any element, but the browser decides who can reach it; Tab moves focus to a `<button>` and skips a `<div>`; Enter and Space click a focused `<button>`; a `<div>` gets neither, so keyboard and screen reader users cannot use it
- **Placement**: `<button onClick={handleRead}>Read story</button>`, styled with CSS, even to look like a link
- **Real Mistake**: `<div className="read" onClick={handleRead}>Read story</div>`; Tab skips it, and Enter and Space do nothing; verified in Chrome 154
- **Importance**: react.dev's `<Note>`; every accessibility review flags a clickable `<div>`
- **Review Point**: Do not
- **Required Lesson Proof**: the Read control as a `<div>` and as a `<button>`, tried with Tab, Enter, and Space: only the button gets focus and runs the handler.

## Senior Answer
I pass a function to an event prop such as `onClick` or `onChange`. React calls it when the user acts. I pass the function itself, `onClick={handleClick}`. If I write `handleClick()`, the braces call it during render, and the click does nothing. When the handler needs an argument, I wrap the call in an arrow function, like `() => openArticle(story.id)`. For child-to-parent communication, the parent passes a callback prop such as `onSelect`. The child calls it from its own button, with the data the parent needs. The data still flows down, and the parent decides what changes. Events bubble up through parent elements. `stopPropagation` stops the parents' handlers, and `preventDefault` stops the browser's own action, like a form reload. They are unrelated. And I put clicks on real buttons, because a `<div>` cannot be reached with the keyboard.
