## Authorized Scope
Lesson 15 teaches what happens between a setter call and the new screen. Every screen update takes three steps. The trigger asks for an update: the first `root.render()`, or a setter. The render is React calling our components to work out what the page should show. It changes nothing on the page. The commit is React changing the DOM nodes whose output differs, and no others. After the commit, the browser paints the screen. The page changes only after the event handler has finished. So a line right after the setter still finds the old page. A state change renders the component that owns the state and every component inside it, and no other. The lesson builds on Q01, where React changed only the new text. It also builds on Q14, where the setter asked React to run the component again. The example is the article card: a like count, a Like button, and a comment box.

## Theme and Options
- **Theme**: We call a setter, and a moment later the screen shows the new value. What happens in between, and which of our code runs at each moment?
- **Options**: none (starting point: the setter of Q14, which "runs the component again", with no word yet for the steps in between)
- **This lesson teaches**: the trigger, the render, and the commit

## Principle Thread
- **Anchor**: One update: a setter call travels through trigger, render, and commit to the screen
- **Axis**: time, along one click: the setter call, the end of the handler, the render, the commit
- **Why This Axis**: The steps happen in this order, and each needs the one before it. The setter must be understood as a request before the reader can see why the page does not change on the next line. The handler must end before the render begins, which explains the old page. The render works out the new output, and only then can the commit compare it with the old one and change what differs. Two axes were rejected. "One principle per piece of our code: handler, component body, DOM" splits the render and the commit across two places. "Initial render, then re-render" repeats every step twice and hides the order.
- **Spoken Preview**: Everything in this lesson comes down to one idea: one update, which means a setter call travels through trigger, render, and commit to the screen. First, the trigger, which means the update starts with a setter, not with a change to the page: a handler asks for the new value, and React changes the page itself. Second, the handler first, which means the update reaches the page only after the handler ends: a line right after the setter still finds the old page, so we use the value we computed. Third, the render, which means the update runs the changed component and every component inside it: React calls them to work out the new page, and changes nothing yet. Fourth, the commit, which means the update changes only the DOM nodes that differ: whatever did not change, such as the text being typed, stays exactly as it was.
- **Closing Line**: A setter asks, the handler ends, React renders, and the commit changes only what differs.

## Principles

### Principle 1: The trigger: the update starts with a setter, not with a change to the page
- **Handle**: `setter-to-screen`
- **Thread Step**: the setter call
- **Rule**: To change what the page shows, a handler calls a setter and never writes to the DOM itself; React then calls the component and changes the page to match.
- **Kind**: Model
- **Reader Question**: "I call `setLikes(likes + 1)`. How does the new number get onto the screen?"
- **Reader Expects**: the setter writes the new number onto the page, as `element.textContent = 1` does in plain JavaScript
- **React Does**: the setter stores 1 and asks for an update; that request is the trigger; React then calls `ArticleCard` again, the render, and the component returns `<p>Likes: 1</p>`; React compares it with the page and changes the 0 to 1, the commit; the setter itself touches no DOM; the plain JavaScript habit of writing the page by hand, with no setter, shows "Likes: 1" after every click, because `likes` stays 0 and the handler writes `0 + 1` each time; and when React renders the card again for another reason, its new output equals its last one, so it leaves the hand-written text in place: the page and the state no longer agree
- **Placement**: `setLikes(likes + 1)` in `handleLike`; `<p className="likes">Likes: {likes}</p>` in the JSX; no `document.querySelector` in the handler
- **Real Mistake**: `document.querySelector('.likes').textContent = 'Likes: ' + (likes + 1);` in `handleLike`, with no setter; every click shows "Likes: 1", never 2; `setLikes(likes + 1)` shows "Likes: 1", then "Likes: 2"; verified in React 19.3.1, Vite 8.3.4, and Chrome
- **Fix In**: this principle
- **Importance**: the bank question's three steps; the card's Core Truth; the plain JavaScript habit every reader brings
- **Prediction**: with the setter, the first click shows "Likes: 1" and the second "Likes: 2"; with the hand-written text, both show "Likes: 1"
- **Required Lesson Proof**: the hand-written text: "Likes: 1" on every click, and still after a Save; the setter: the count goes up.

### Principle 2: The handler first: the update reaches the page only after the handler ends
- **Handle**: `dom-after-handler`
- **Thread Step**: the end of the handler
- **Rule**: We never read the page right after a setter to learn the new value: the DOM still shows the old one until the handler ends, so we use the value we computed.
- **Kind**: Decision
- **Reader Question**: "Why does a read of the page right after the setter send the old number?"
- **Reader Expects**: the setter changes the page at once, so the next line of the handler reads the new number
- **React Does**: the setter only asks for an update; React lets the handler finish first, and only then renders and commits; so a line right after `setLikes` reads the page as it was: "Likes: 0" on the first click; the logs show the order: the handler's own log first, the components' logs after it; the value the handler needs is the one it computed, so `const nextLikes = likes + 1` is passed both to `setLikes` and to the analytics call
- **Placement**: `const nextLikes = likes + 1;` in `handleLike`, then `setLikes(nextLikes)` and the analytics call with `nextLikes`
- **Real Mistake**: `setLikes(likes + 1);` followed by `console.log('the page says:', document.querySelector('.likes').textContent);` in `handleLike`, standing for an analytics call; the first click logs "the page says: Likes: 0", and the page then shows "Likes: 1"; `nextLikes` logs 1, then 2; verified in React 19.3.1 and Chrome
- **Importance**: the card's Friction 1 and Code Experiment Naive; analytics and logs that report the old number
- **Review Point**: Do not
- **Required Lesson Proof**: the read after the setter: the old text in the log; the computed value: the new number; the order of the logs.

### Principle 3: The render: the update runs the changed component and every component inside it
- **Handle**: `update-renders-below`
- **Thread Step**: the render
- **Rule**: When state changes, React calls the component that owns it and every component that component returns, and no other; those calls only work out the new page, because nothing on the page has changed yet.
- **Kind**: Model
- **Reader Question**: "Does a click run my whole app again?"
- **Reader Expects**: either the whole app runs again from `App`, or only the one element that shows the number
- **React Does**: rendering is React calling our components (Q02); on the first render it calls the root component and every component down the tree; after a setter, it calls the component that owns the state, here one `ArticleCard`, and then every component that component returns, here its `CommentBox`, even though `CommentBox`'s output is the same; it does not call `App`, `ArticleList`, or the other cards; each call only returns JSX, so the page has not changed while the components run; with Strict Mode each runs twice, and the page still changes once
- **Placement**: a `console.log` at the top of each component to watch the render
- **Real Mistake**: none
- **Importance**: "what runs in each" is the bank question's second half; Q54 and Q55 build on it; interviewers ask which components re-render
- **Prediction**: a click on the first card's Like logs "ArticleCard runs: New Park Opens Today" and "CommentBox runs", twice each, and nothing from `App`, `ArticleList`, or the other two cards
- **Required Lesson Proof**: the logs of all components on load and after one Like.

### Principle 4: The commit: the update changes only the DOM nodes that differ
- **Handle**: `commit-only-differences`
- **Thread Step**: the commit
- **Rule**: We let React render a component again whenever its state changes: the commit changes only the DOM nodes whose output changed, so typed text, focus, and every unchanged element stay as they are.
- **Kind**: Model
- **Reader Question**: "Will the new run wipe what the reader is typing?"
- **Reader Expects**: running the component again rebuilds its part of the page, as `innerHTML` did in Lecture 1, so the comment box empties
- **React Does**: during the render React works out the new output; in the commit it compares it with the last one and changes only what differs; on the first render the commit adds every node with `appendChild()`; after a Like, the only difference is the number, so React changes one text node, "0" to "1", and leaves the `<article>`, the `<h2>`, the button, and the `<input>` as they are, with "Great news!" still in the box; react-dom also sets and removes a `name` attribute on the input, so the Elements panel may flash it; a component whose output is the same causes no DOM change at all; after the commit the browser paints the screen, which is the other thing people call "rendering"
- **Placement**: no fear of state in a component with an input; the Elements panel and a typed comment to watch the commit
- **Real Mistake**: none
- **Importance**: the card's Friction 2 and Under the Hood; interviewers ask what the commit changes and how it differs from the browser's paint
- **Prediction**: with "Great news!" typed into the first card's comment box, a Like changes only the number, and the box still holds "Great news!"
- **Required Lesson Proof**: the typed comment and a Like: the box keeps its text; the recorded DOM changes after a Like: one text node.

## Senior Answer
Every update has three steps. The trigger is the request: the first `root.render`, or a setter call. The setter stores the next value and asks for a render; it does not touch the page. React lets the event handler finish first, so a line right after the setter still sees the old page. Then React renders. It calls the component that owns the changed state and every component inside it, not its parent or its siblings. Rendering only calculates the new JSX, which is why it must be pure. Then React commits: it compares the new output with the last one and changes only the DOM nodes that differ. Text a user is typing into an input stays, because that input did not change. After the commit, the browser paints the pixels. So "rendering" in React means calling our components, not drawing the screen.
