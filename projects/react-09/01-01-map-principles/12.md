## Authorized Scope
Lesson 12 teaches what a component may do while React runs it. React may call a component any number of times. So each call must give the same JSX for the same props. It must also change nothing that existed before the call. A component that changes a variable outside itself shows numbers that grow with every call. A component that pushes into an array it did not create shows the same item twice. A copy made during the call is the component's own, and it may change the copy freely. `<StrictMode>`, in `main.jsx` since Q09, calls each component twice in development to show these mistakes at once. The production build calls each component once. The lesson builds on Q02, which promised this explanation for the doubled logs, and on Q06, where props were read-only. It changes the page by saving a file, as earlier lessons did, because state comes in Q14. The example is the article list of Q11: three article cards, each with a number.

## Theme and Options
- **Theme**: React runs our components, sometimes more often than we expect. What may a component do while it runs?
- **Options**: none (starting point: components that only return JSX from their props, Lectures 2 to 11, and a `main.jsx` with `<StrictMode>`, Lecture 9)
- **This lesson teaches**: pure rendering

## Principle Thread
- **Anchor**: Pure rendering: each call of a component only calculates its JSX from its inputs
- **Axis**: what each call may do, then how React checks it: the same output from the same inputs, nothing changed outside, and a second call in development to catch either mistake
- **Why This Axis**: Each step needs the one before it. The first principle shows why the number of calls matters: a component whose output depends on its calls gives a different page each time. The second widens the rule from the output to the outside world: a call that changes something outside breaks the next call too. The third explains the tool that makes both mistakes visible, and it can only be understood once the reader knows what it looks for. Two axes were rejected. "Inputs, body, output" splits the counter across all three parts and leaves Strict Mode with no place. "Development, then production" orders by where the code runs, and the first two rules are the same in both.
- **Spoken Preview**: Everything in this lesson comes down to one idea: pure rendering, which means that each call of a component only calculates its JSX from its inputs. First, idempotence, which means each call gives the same JSX for the same inputs: what the component shows depends on its props alone, never on how many times it was called. Second, no side effects, which means each call changes nothing that existed before it: the component may change only what it created during the same call. Third, Strict Mode, which means each component is called twice in development, to catch impure calls: we keep it on, because a pure component shows nothing different on the second call.
- **Closing Line**: The same inputs, nothing changed, and a second call to prove it.

## Principles

### Principle 1: Idempotence: each call gives the same JSX for the same inputs
- **Handle**: `idempotent-output`
- **Thread Step**: what each call may do: give the same output for the same inputs
- **Rule**: A component's JSX depends only on its props: we never read and change a variable outside the component while it runs, and never show a value that changes on every call, such as `Math.random()` or `new Date()`; a number that depends on an item's place comes in as a prop.
- **Kind**: Model
- **Reader Question**: "My cards number themselves with a counter outside the component. Why do they show #2, #4, #6?"
- **Reader Expects**: React calls each card once per tag, so a counter that grows by one per call counts the cards, as a loop counter does in plain JavaScript
- **React Does**: React calls a component whenever it needs its JSX, and it may call it more than once: Strict Mode calls it twice in development, and every saved change calls it again; the counter lives at the top of the file, outside every call, so each call adds one to the same variable; the first card is called twice and shows 2, the second shows 4, the third 6; after a save the numbers go on to 8, 10, 12; without Strict Mode the first page shows 1, 2, 3 and a save shows 4, 5, 6; the output depends on how many calls happened, not on the props; a value made by `Math.random()` or `new Date()` during the call changes the same way; the fix gives each card its number as a prop, `number={index + 1}` from the list's `map()`, and the cards show 1, 2, 3 on every call
- **Placement**: `{articles.map((article, index) => <ArticleCard key={article.id} article={article} number={index + 1} />)}` in `ArticleList`; `#{number}` in `ArticleCard`; no variable outside the component that the component changes
- **Real Mistake**: `let cardNumber = 0;` at the top of `ArticleCard.jsx` and `cardNumber = cardNumber + 1;` in its body, shown as `#{cardNumber}`; the three cards show #2, #4, #6, and #8, #10, #12 after a save; `number={index + 1}` shows #1, #2, #3 every time; verified in React 19.3.1, Vite 8.3.4, and Chrome
- **Fix In**: this principle
- **Importance**: the bank question's first half and its hook; the card's Code Experiment; every later lesson relies on components that can be called again
- **Prediction**: with the `number` prop, the cards show #1, #2, #3 with Strict Mode, without it, and after any number of saves
- **Required Lesson Proof**: the counter with Strict Mode, before and after a save; the same without Strict Mode; the `number` prop in both modes and after a save.

### Principle 2: No side effects: each call changes nothing that existed before it
- **Handle**: `no-side-effects`
- **Thread Step**: what each call may do: leave everything outside as it found it
- **Rule**: While a component runs, we change only what that call created: a copy of an array or object is ours to change, while props, imported data, outside variables, and the page itself stay as they were; changes to the outside world belong in event handlers.
- **Kind**: Decision
- **Reader Question**: "I want a 'See all articles' item at the end of the list. Can I push it into the articles array?"
- **Reader Expects**: `push()` adds one item, as it does in any script, and the list shows it once
- **React Does**: the `articles` array is created once, when `articles.js` first runs, and every call of `ArticleList` receives that same array; each call pushes one more item into it, so with Strict Mode the list shows "See all articles" twice, and React warns "Encountered two children with the same key, `all`"; without Strict Mode it shows once, and twice after a save; a copy made inside the call, `const items = [...articles]`, is new on every call, so pushing into it changes nothing outside, and the item shows once every time; `reverse()` and `sort()` change the array too: with Strict Mode, a list reversed during render keeps its order, because the second call reverses it back; changing the page from the body, such as `document.title = article.title`, is a side effect as well: each card overwrites the tab, and it shows the last card's title
- **Placement**: `const items = [...articles];` and `items.push(...)` in `ArticleList`, then `items.map(...)`; nothing in the body that changes props, imported data, outside variables, or the page
- **Real Mistake**: `articles.push({ id: 'all', title: 'See all articles', author: '' });` in the body of `ArticleList`; with Strict Mode the list ends with "See all articles" twice, and the console shows "Encountered two children with the same key, `all`"; the copy shows it once, also after a save; verified in React 19.3.1 and Chrome
- **Importance**: react.dev's story tray Challenge and Strict Mode example; reviewers flag `push`, `sort`, and `reverse` on props or imported data; map 06 and map 19 build on it
- **Review Point**: Do not
- **Required Lesson Proof**: the push into `articles` with Strict Mode and without it before and after a save; the copy in both modes; the reverse in both modes; `document.title` from three cards.

### Principle 3: Strict Mode: each component is called twice in development, to catch impure calls
- **Handle**: `strict-mode-twice`
- **Thread Step**: how React checks it: a second call in development
- **Rule**: We keep `<StrictMode>` around the app: in development it calls each component twice and keeps one result, so an impure component shows its mistake at once, and the doubled logs disappear in the production build.
- **Kind**: Model
- **Reader Question**: "Every `console.log` in my component prints twice. Should I remove Strict Mode?"
- **Reader Expects**: the second call is a bug or a waste, so removing `<StrictMode>` from `main.jsx` makes the app correct and faster
- **React Does**: in development, `<StrictMode>` calls each component's function twice and keeps one of the two results; a pure component gives the same JSX both times, so the page shows no difference, and only the logs come twice: six lines for three cards; an impure component gives a different result on the second call, so the mistake shows on the first page; React DevTools dims the second call's logs; removing `<StrictMode>` silences the logs and hides the counter's mistake: the first page shows #1, #2, #3, and the mistake comes back with the next render, #4, #5, #6 after a save; the production build never calls twice: `npm run preview` shows #1, #2, #3 and three logs
- **Placement**: `<StrictMode>` around `<App />` in `main.jsx`, as Vite writes it; the fix for a doubled result in the component, never in `main.jsx`
- **Real Mistake**: `<StrictMode>` removed from `main.jsx` because the logs print twice; the logs print once and the counter cards show #1, #2, #3, then #4, #5, #6 after a save; with `<StrictMode>` kept and the `number` prop, they show #1, #2, #3 every time; verified in React 19.3.1, Vite 8.3.4, and Chrome
- **Fix In**: this principle
- **Importance**: Lecture 2's promise; interviewers ask why React renders twice; developers remove Strict Mode and ship the bugs it was showing
- **Prediction**: with Strict Mode, a log in `ArticleCard` prints six times for three cards in development, and three times in `npm run preview`
- **Required Lesson Proof**: the logs with Strict Mode; the counter without Strict Mode, before and after a save; the production preview's cards and logs.

## Senior Answer
A pure component only calculates its JSX from its inputs. It gives the same JSX for the same props, and it changes nothing that existed before the call. React relies on this, because it may call a component many times. In development, Strict Mode calls each component twice on purpose. A component that writes to an outside variable then shows numbers that grow with each call. A component that pushes into an array it received shows the same item twice. The fix is to compute from props, and to change only a copy made during the call. Changes to the outside world belong in event handlers. Strict Mode does nothing in production. So the doubled logs are the check working, not a bug. Removing it only hides the mistake until the next render.
