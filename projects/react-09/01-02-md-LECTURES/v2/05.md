## Why We Split Components Across Files

### A real project quickly outgrows a single file

When you start learning React, keeping every component inside one file makes it easy to see your whole page at a glance. However, a real news website does not have only two or three components. It has a header, an article list, cards, status badges, a comment box, and a footer.

If a team keeps fifty components inside one giant file, two problems appear right away. Every small edit forces you to scroll past hundreds of lines that have nothing to do with your task. Worse still, when two developers edit different parts of the page on the same afternoon, their changes collide inside the same file.

To keep each piece easy to find and edit, we split components into separate files and connect them with JavaScript **exports** and **imports**.

```tree caption="Two ways to organize components in a growing React project: keeping everything inside one giant file vs. splitting components into dedicated module files."
How to organize components as a project grows
- !Keep every component inside one giant `App.jsx` | Every change means **scrolling past hundreds of unrelated lines** | Teammates editing different components **collide in the same file**
- +Split components into dedicated files inside `src/components/` | +**DO** give each main component its own `.jsx` file | Connect files cleanly with **`export`** and **`import`**
```

### Two steps to move a component into its own file

Suppose we want to move our article card out of the main application file and give it its own file inside a `components` folder. Connecting the two files takes **two steps**.

First, we create the card's own file and place `export default` at the front of the component function:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
~export default~ function ArticleCard() { // 1. Export the card so other files can use it
  return (
    <article className="card">
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

Second, at the very top of the main application file, we write an `import` line that brings the card in from its new file:

```jsx title="src/App.jsx" startLine="1"
~import ArticleCard from './components/ArticleCard.jsx';~ // 2. Import the card into App.jsx

export default function App() {
  return (
    <main>
      <h1>Latest Articles</h1>
      <ArticleCard />
    </main>
  );
}
```

When you save both files, the browser displays the exact same page as before, even though the two components now live in separate files:

```page caption="What the user sees in the browser when ArticleCard is exported from its own file and imported into App.jsx."
heading: Latest Articles
card: title=New Park Opens Today | text=The park on Main Street opens at noon.
```

```tree dir=right caption="The two steps that connect a component in one file to another file that renders it."
How a component crosses from one file to another
- +Step 1: Export from the card file [`src/components/ArticleCard.jsx`] | Write `export default` in front of the function to **open the name** to other files
- +Step 2: Import in the file that uses it [`src/App.jsx`] | Write `import` at the **top of the file** before using the tag
```

### How our project files sit in folders

Before we write more imports, look at where our files sit on disk. Every React source file lives inside the `src` folder. The main application file, `App.jsx`, sits directly inside `src`. Alongside it sits a subfolder named `components`, which holds the component files we split out:

```files title="article-site: File Explorer" caption="How our project files sit inside src/ and src/components/, and what each file exports or imports."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it on the page
  App.jsx | parent | Exports `App` as default and imports `ArticleList` from `./components/ArticleList.jsx`
  components/
    ArticleList.jsx | default export | Exports `ArticleList` as default and imports `ArticleCard` from `./ArticleCard.jsx`
    ArticleCard.jsx | default export | Exports `ArticleCard` as default and imports `{ LiveBadge, NewBadge }` from `./Badges.jsx`
    Badges.jsx | named exports | Exports `LiveBadge` and `NewBadge` as named exports
```

When one file imports another file, it writes a **path** after the word `from`. Every path starts with one of three prefixes:
- **A single dot and slash, `./`**, starts from **the current file's own folder**. From the main file, it steps into the `components` folder right beside it.
- **Two dots and a slash, `../`**, step **one folder up** into the parent folder.
- **A bare word with no dot, such as `'react'`**, is not a folder path at all. It names an **installed package** that the build tool finds automatically.

```tree caption="Every import path after the word from uses one of three prefixes."
Three kinds of paths after `from` in an import line
- +Same folder [`'./ArticleCard.jsx'` `'./components/ArticleCard.jsx'`] | Starts with **`./`** | Looks inside the **current file's own folder**
- +Parent folder [`'../App.jsx'`] | Starts with **`../`** | Steps **one folder up** before looking for the file
- +Installed package [`'react'` `'react-dom/client'`] | Starts with **no dot at all** | Looks inside the project's **installed packages**
```

### Four Principles of ES Module Imports and Exports

**PRINCIPLES:** In modern JavaScript, every file is an isolated **module**. Its functions stay locked inside that file unless you export them and another file imports them. Walking through how a file exports components and how another file imports them gives us four practical rules:
1. **Principle 1: Each File Is a Private Module**: Moving a component into a new file without exporting and importing it crashes the page because `App.jsx` can no longer see the function name. Any helper function that only one file needs should stay unexported.
2. **Principle 2: One Default Export for the Main Component, Named Exports for Multiple Components**: A file can have **at most one** `export default`. Writing a second `export default` in the same file stops the build immediately. When one file holds multiple components, such as two badges, export them by name with `export function`.
3. **Principle 3: Match Your Import to How the File Exported the Component**: How a file exports a component determines how another file must import it. You import a file's single **default export** **without curly braces** under any name you choose. You import a **named export** **inside curly braces** using its exact exported name, or rename it explicitly with `as`.
4. **Principle 4: Every Relative Path Starts from the Importing File's Folder**: A relative path starting with `./` always starts from the folder of the file you are editing, never from the project root. Copying an import line from the main file into a component file breaks the build because the two files sit in different folders.

Here is the complete overview of all four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Modules: Each File Keeps Its Names Private** | Moving a component to a new file without `export` and `import` blanks the page with `ReferenceError: ArticleCard is not defined`. | Export every shared component from its `.jsx` file with `export` and bring it in with `import`; leave internal helpers unexported. |
| **Principle 2** | **Default vs. Named Exports: One Default or Many Named** | Writing two `export default` statements in one file stops the build with `A module cannot have multiple default exports`. | Give a file at most one `export default` for its main component, use `export function` for multiple components, and always name every component function. |
| **Principle 3** | **Matching Imports: No Braces for Default, Braces for Named** | Leaving curly braces off a named import or putting curly braces on a default import stops the browser before React runs; interviewers ask how naming and renaming differ. | Import a default export without curly braces under any local name; import a named export inside `{ }` with its exact exported name or rename it with `as`. |
| **Principle 4** | **Import Paths: Start from the Importing File's Folder** | Copying `./components/ArticleCard.jsx` out of `src/App.jsx` into `src/components/ArticleList.jsx` breaks the build with `Failed to resolve import`. | Write every `./` or `../` path starting from the folder of the file that holds the `import` line. |

## 1. Principle 1: Modules: Each File Keeps Its Names Private Until Exported

### Old HTML script tags share one global space, but each module file keeps its names private

When developers first split a component into a new file, they often expect other files in the same project to see it automatically.

- **In daily coding**: Suppose you move the card function out of `App.jsx` and into its own file **without adding an export and an import**. The page goes blank and the Console reports that the card is not defined.
- **In an interview**: Explain why that happens. Old `<script>` tags on an HTML page dump every function into one shared global space. In React, every `.jsx` file is an **ES module** whose functions stay private to that file until exported.

```tree caption="Old browser script tags vs. modern JavaScript module files."
How files share function names in the browser
- !Old HTML `<script>` tags | Every file dumps its functions into **one shared global space** | Any file can accidentally **overwrite** a function with the same name in another file
- +Modern ES module files [`App.jsx` `ArticleCard.jsx`] | +**DO** treat every `.jsx` file as a private module | Functions stay **private inside their file** until connected by `export` and `import`
```

### What happens when you move a component without exporting and importing it

First, look at what happens when a developer moves the card function into a new file, **but forgets to write `export` in front of the function**:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
function ~ArticleCard~() { // **WRONG:** without export, ArticleCard stays private inside this file!
  return (
    <article className="card">
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

In `App.jsx`, the developer still uses the card tag without an `import` line at the top:

```jsx title="src/App.jsx" startLine="1"
export default function App() {
  return (
    <main>
      <h1>Latest Articles</h1>
      ~<ArticleCard />~ {/* **WRONG:** App.jsx cannot see ArticleCard without importing it! */}
    </main>
  );
}
```

When you save the files, the page goes blank and the Console shows an error:

```devconsole
x Uncaught ReferenceError: ArticleCard is not defined
```

Look at what happened in order:
1. Moving the card function into `ArticleCard.jsx` removed that function from `App.jsx`.
2. Without `export` in the card file and `import` in the main file, the card function stays locked inside its own file.
3. When `App` tries to render the card tag, JavaScript cannot find the card function and throws a `ReferenceError`.

### Connecting both files with `export default` and `import`

To connect the two files, we open both ends. First, we export the card function from `ArticleCard.jsx`, and second, we import it at the top of `App.jsx`:

### Why module privacy is helpful for internal helper functions

Keeping each file private is not an obstacle. It protects small helper functions that only one file needs.

Suppose the card file uses a small helper function to prepare its headline. Because no other file needs that helper, we leave `export` off the helper and only export the card component:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
function ~getHeadline~() { // No export: stays private inside ArticleCard.jsx
  return 'New Park Opens Today';
}

~export default~ function ArticleCard() { // Exported: shared with other files
  return (
    <article className="card">
      <h2>{getHeadline()}</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

Inside the card file, the card component can call `getHeadline` freely. Outside the card file, no other file can accidentally call or overwrite `getHeadline`.

```tree dir=right caption="Inside a module file, you export only the component other files need and keep internal helpers private."
Two functions inside `src/components/ArticleCard.jsx`
- +Private helper [`function getHeadline`] | **No `export`** keyword | Visible **only inside `ArticleCard.jsx`** so other files cannot clash with it
- +Shared component [`export default function ArticleCard`] | Marked with **`export default`** | Can be **imported and rendered** by `App.jsx` or any other file
```

> [!PRINCIPLE]
> **Principle 1: Modules: Each File Keeps Its Names Private Until Exported**
>
> *Export a component with `export` and import it with `import` in every file that uses it. Leave internal helper functions unexported.*
>
> Every `.jsx` file in React has its own private module scope. Moving a component into a new file hides its name from `App.jsx` until the new file exports it and `App.jsx` imports it. Any helper function that only one file needs should stay unexported so it remains private to that file.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> ~export default~ function ArticleCard() { // 1. Export the card from its own file
>   return <article>New Park Opens Today</article>;
> }
> ```
> ```jsx title="src/App.jsx"
> ~import ArticleCard from './components/ArticleCard.jsx';~ // 2. Import the card where it is rendered
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> function ~ArticleCard~() { // **WRONG:** missing export keeps ArticleCard private inside this file!
>   return <article>New Park Opens Today</article>;
> }
> ```

## 2. Principle 2: Default vs. Named Exports: One Default for the Main Component, Named Exports for Multiple Components

### A file can have only one default export, so a file with multiple components exports them by name

In Principle 1, `ArticleCard.jsx` had only one component, so we exported it with `export default`. What happens when we want one file to hold **two or three small components**, such as status badges?

- **In daily coding**: Beginners often think `export default` simply means *"export this function"*. When they put two badge components inside one file and write `export default` in front of both of them, Vite immediately stops the build with an error.
- **In an interview**: Explain why JavaScript has **two different ways to export**:
  1. **Default export**: Written with `export default function`. A file can have **at most one** default export. Teams use it when a file is dedicated to **one main component**, such as `ArticleCard.jsx`.
  2. **Named exports**: Written with `export function` and no `default` keyword. A file can have **as many named exports as you want**. Teams use named exports when one file groups **several small components or helpers**, such as `LiveBadge` and `NewBadge` in our badge file.

```tree caption="Why JavaScript has two ways to export components from a file."
Two ways to export components from a `.jsx` file
- +Default export [`export default function ArticleCard`] | **At most 1** per file | Use when the file exports **one main component**
- +Named exports [`export function LiveBadge` `export function NewBadge`] | **Unlimited** per file | Use when one file exports **several components or helpers**
```

### What happens when you write two `export default` lines in one file

Suppose we create a new badge file to hold two small badges for our news cards: `LiveBadge` and `NewBadge`. Look at what happens if a developer puts `export default` in front of both functions:

```jsx title="src/components/Badges.jsx" startLine="1"
export default function LiveBadge() {
  return <span className="badge">Live</span>;
}

~export default~ function NewBadge() { // **WRONG:** a file can only have ONE default export!
  return <span className="badge">New</span>;
}
```

The moment you save the file, Vite stops the build and shows its error overlay on the screen:

```overlay
message: [plugin:vite:oxc] [PARSE_ERROR] A module cannot have multiple default exports.
file: src/components/Badges.jsx:5:1
  3 | }
  4 |
> 5 | export default function NewBadge() {
    | ^^^^^^^^^^^^^^
```

Because `LiveBadge` already claimed the file's single default export, writing a second `export default` in the same file is a syntax error.

### Exporting multiple components by name with `export function`

To export both badges from the badge file, we remove the word `default` and write `export function` in front of each badge. That makes both of them **named exports**:

```jsx title="src/components/Badges.jsx" startLine="1"
~export function LiveBadge~() { // 1st named export: exported under the name "LiveBadge"
  return <span className="badge">Live</span>;
}

~export function NewBadge~() { // 2nd named export: exported under the name "NewBadge"
  return <span className="badge">New</span>;
}
```

### Always give every component function a name

Whether you use a default export or a named export, **always write a function name** such as `function ArticleCard`. Never write an anonymous default export like this:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
~export default () =>~ <article>New Park Opens Today</article>; // **WRONG:** component function has no name!
```

When a component function has no name, React DevTools and error stack traces cannot tell you which component failed. They only display the unhelpful label `default`.

```tree caption="How to choose between a default export and named exports when organizing component files."
Which export style should this file use?
- +One main component in its own file [`ArticleCard.jsx` `ArticleList.jsx`] | +**DO** use `export default function ArticleCard` | Gives the file's main component the single default export
- +Several small components in one file [`Badges.jsx`] | +**DO** use `export function LiveBadge` and `export function NewBadge` | Named exports have **no limit** in a single file
- !Anonymous default export [`export default function`] | ~Do **NOT** export a component without a function name | Shows up as **`"default"`** in React DevTools and error messages
```

> [!PRINCIPLE]
> **Principle 2: Default and Named Exports: One Default at Most, Named Exports for Multiple Components**
>
> *Give a file at most one default export for its main component and use named exports when a file holds multiple components. Always give every component function a name.*
>
> Every module file can have at most one default export, so writing a second `export default` stops the build with a parse error. Use `export default` when a file is dedicated to one main component, and use `export function` when one file exports several components or helper functions.
>
> **DO THIS:**
> ```jsx title="src/components/Badges.jsx"
> ~export function LiveBadge~() { // 1st named export in this file
>   return <span className="badge">Live</span>;
> }
> ~export function NewBadge~() { // 2nd named export in this file
>   return <span className="badge">New</span>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/Badges.jsx"
> export default function LiveBadge() {
>   return <span className="badge">Live</span>;
> }
> ~export default~ function NewBadge() { // **WRONG:** a module cannot have multiple default exports!
>   return <span className="badge">New</span>;
> }
> ```

## 3. Principle 3: Match Imports to Exports: No Braces for Default, Curly Braces for Named

### How a file exports a component determines whether the importing file uses curly braces and whether it can pick a new name

Now look at the two component files we have built so far:
1. **Our card file, `ArticleCard.jsx`**, exports **one default component** with `export default`.
2. **Our badge file, `Badges.jsx`**, exports **two named components** with `export function`.

How does another file import from each one?

- **In daily coding**: Beginners often think the curly braces `{ }` in an `import` line are optional formatting. If a file exported a component **by name**, and you import it **without curly braces**, the page goes blank before React even runs.
- **In an interview**: Explain how the export in the first file controls the import in the second file:
  1. **Importing a default export uses no curly braces**: Because the exporting file has **only one** default export, you write the import **without curly braces**. Because there is only one default export in that file, you can give it **any local name you want** when importing it.
  2. **Importing a named export uses curly braces `{ }`**: Because the exporting file can have **many** named exports, you must write **curly braces** around the **exact exported name** you want. If you want to give a named import a different local name, you rename it inside the braces with `as`.

### What happens when you import a named export without curly braces

Let us see what happens if our card file tries to import `LiveBadge` from the badge file **without curly braces**:

```jsx title="src/components/Badges.jsx" startLine="1"
~export function LiveBadge~() { // Exported BY NAME (no "default" keyword)
  return <span className="badge">Live</span>;
}

export function NewBadge() {
  return <span className="badge">New</span>;
}
```

```jsx title="src/components/ArticleCard.jsx" startLine="1"
~import LiveBadge from './Badges.jsx';~ // **WRONG:** no curly braces asks Badges.jsx for a default export!

export default function ArticleCard() {
  return (
    <article className="card">
      <LiveBadge />
      <h2>New Park Opens Today</h2>
    </article>
  );
}
```

When you save the file, the page goes blank and the Console shows an error:

```devconsole
x Uncaught SyntaxError: The requested module '/src/components/Badges.jsx' does not provide an export named 'default'
```

Look at what happened across the two files in order:
1. In the badge file, we exported both badges **by name**, without the word `default`. So the badge file has **no default export**.
2. In the card file, we wrote the `import` line **without curly braces**, which asks the badge file for its single `default` export.
3. Because the badge file has no `default` export, the browser stops before React runs.

The opposite mix-up fails the same way. If a file exports a component with `export default` and another file imports it **with** curly braces, the browser also stops with an error.

### Wrapping named imports in curly braces fixes the mismatch

Because the badge file exported `LiveBadge` and `NewBadge` by name, our card file imports them **inside curly braces** using their exact exported names:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import ~{ LiveBadge, NewBadge }~ from './Badges.jsx'; // Curly braces pick LiveBadge and NewBadge by name

export default function ArticleCard() {
  return (
    <article className="card">
      <LiveBadge />
      <NewBadge />
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

### Can the importing file give an imported component a different tag name?

Sometimes the file that imports a component wants to use a different local tag name on the page. For example, our main file might want to call the card `<StoryCard />`. Or our card file might want to call the live badge `<BreakingBadge />`.

Whether you can write that new name directly depends on **how many exports** the other file has.

#### 1. Renaming a default import: write any new name directly

Our card file has **only one** default export:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
~export default~ function ArticleCard() { // 1. The only default export in this file
  return <article className="card"><h2>New Park Opens Today</h2></article>;
}
```

When our main file imports from the card file **without curly braces**, it can invent a brand-new local name on the spot:

```jsx title="src/App.jsx" startLine="1"
import ~StoryCard~ from './components/ArticleCard.jsx'; // 2. StoryCard is a new local nickname invented here!

export default function App() {
  return (
    <main>
      <h1>Latest Articles</h1>
      ~<StoryCard />~ {/* 3. Renders ArticleCard under its new local nickname StoryCard */}
    </main>
  );
}
```

Look closely at those two files. The word `StoryCard` does not exist anywhere inside our card file! Inside the card file, the function is still named `ArticleCard`. Why doesn't JavaScript complain that `StoryCard` is missing?

Because the import line has **no curly braces**, JavaScript does **not** search the card file for a function named `StoryCard`. Instead, leaving out the curly braces tells JavaScript to do two simple steps:
1. Go to the card file and grab whatever single function is marked `export default`, which is `ArticleCard`.
2. Give that function the brand-new local nickname `StoryCard` inside our main file so we can render it as `<StoryCard />`.

#### 2. Renaming a named import: write the original name first, then `as` and the new name

Our badge file is different. It has **two** named exports in the same file:

```jsx title="src/components/Badges.jsx" startLine="1"
export function ~LiveBadge~() { // 1st named export
  return <span className="badge">Live</span>;
}

export function ~NewBadge~() { // 2nd named export
  return <span className="badge">New</span>;
}
```

When an import uses **curly braces**, JavaScript **does** search the badge file by name so it knows which of the two badges we want. If our card file writes the brand-new name `BreakingBadge` directly inside curly braces, JavaScript searches the badge file for `BreakingBadge`, finds nothing, and stops with an error:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import { ~BreakingBadge~ } from './Badges.jsx'; // **WRONG:** curly braces search Badges.jsx for BreakingBadge, which does not exist!
```

To rename a named import, we write **both names** inside the curly braces with the word **`as`** between them:
1. First write **`LiveBadge`**, the exact name exported by our badge file, so JavaScript finds the right badge.
2. Then write **`as BreakingBadge`**, the new local nickname we want to use as our JSX tag:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import { ~LiveBadge as BreakingBadge~, NewBadge } from './Badges.jsx'; // 1. Finds LiveBadge first, then renames it to BreakingBadge

export default function ArticleCard() {
  return (
    <article className="card">
      ~<BreakingBadge />~ {/* 2. Renders LiveBadge under its new local nickname BreakingBadge */}
      <NewBadge />
      <h2>New Park Opens Today</h2>
    </article>
  );
}
```

Look at both two-file handshakes side by side:

::: row caption="Why a default import can invent a new name directly, while a named import must write OriginalName as NewName inside curly braces."
::: col title="Renaming a Default Import" tag="no braces: any new name works" tone=good
```jsx title="src/components/ArticleCard.jsx"
~export default~ function ArticleCard() { // 1. Only ONE default export in this file
  return <article>New Park Opens Today</article>;
}
```
```jsx title="src/App.jsx" good="1,5"
import ~StoryCard~ from './components/ArticleCard.jsx'; // 2. No braces: grabs the default export and names it StoryCard

export default function App() {
  return (
    <StoryCard />
  );
}
```
`StoryCard` is not in the card file. Because there are no curly braces, JavaScript grabs the single `export default` and gives it the new nickname `StoryCard`.
:::
::: col title="Renaming a Named Import" tag="curly braces: OriginalName as NewName" tone=good
```jsx title="src/components/Badges.jsx"
export function ~LiveBadge~() { // 1. Exported by the exact name LiveBadge
  return <span>Live</span>;
}
export function NewBadge() {
  return <span>New</span>;
}
```
```jsx title="src/components/ArticleCard.jsx" good="1,5"
import { ~LiveBadge as BreakingBadge~ } from './Badges.jsx'; // 2. Finds LiveBadge first, then renames it to BreakingBadge

export default function ArticleCard() {
  return (
    <BreakingBadge />
  );
}
```
`BreakingBadge` is not in the badge file. Inside curly braces, you write `LiveBadge` first so JavaScript finds it, then `as BreakingBadge`.
:::
:::

Here is the complete picture of how default and named exports work across both files:

| Export Style | 1. In the Exporting File | 2. Normal Import in the Importing File | 3. Importing Under a Different Name |
| :--- | :--- | :--- | :--- |
| **Default Export: at most 1 per file** | `export default function ArticleCard` | `import ArticleCard from './ArticleCard.jsx'` | `import StoryCard from './ArticleCard.jsx'` |
| **Named Export: unlimited per file** | `export function LiveBadge` | `import { LiveBadge } from './Badges.jsx'` | `import { LiveBadge as BreakingBadge } from './Badges.jsx'` |

> [!PRINCIPLE]
> **Principle 3: Matching Imports: No Braces for Default, Curly Braces for Named**
>
> *Import a default export without curly braces under any name you choose. Import a named export inside curly braces with its exact exported name, or rename it with `as`.*
>
> How you export a component in one file dictates how you must import it in another file. Because a file has at most one default export, an import without curly braces grabs that single default export under whatever local name you write. Because a file can have many named exports, an import with curly braces must spell the exact exported name so JavaScript knows which export to grab. If you want a different local name for a named import, add `as` inside the curly braces.
>
> **DO THIS:**
> ```jsx title="src/components/Badges.jsx"
> ~export function LiveBadge~() { // 1. Exported by the exact name LiveBadge
>   return <span className="badge">Live</span>;
> }
> ```
> ```jsx title="src/components/ArticleCard.jsx"
> ~import { LiveBadge } from './Badges.jsx';~ // 2. Imported with matching curly braces
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> ~import LiveBadge from './Badges.jsx';~ // **WRONG:** missing curly braces asks Badges.jsx for a default export!
> ```

## 4. Principle 4: Import Paths: Every Relative Path Starts from the Importing File's Folder

### A relative path does not start from the project root, because it starts from the folder of the file you are editing

Now let us take the final step of organizing our project. We want to move the list of article cards into its own file, `ArticleList.jsx`, so `App.jsx` stays short and clean.

- **In daily coding**: When developers create a new component inside the `components` folder, they often **copy and paste an import line directly from `App.jsx`**. The build immediately stops because the two files sit in different folders.
- **In an interview**: State the rule clearly: every relative path starting with `./` or `../` starts from **the folder of the file that writes the import line**. It never starts from the project root.

### What happens when you copy an import path from `App.jsx` into `components/`

In `App.jsx`, the card was imported by stepping down into the `components` folder. Look at what happens when a developer creates `ArticleList.jsx` inside the `components` folder and pastes that exact same import line at the top:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from ~'./components/ArticleCard.jsx'~; // **WRONG:** ArticleList.jsx is ALREADY inside src/components/!

export default function ArticleList() {
  return (
    <section>
      <ArticleCard />
      <ArticleCard />
    </section>
  );
}
```

When you save the file, Vite stops the page with an import error. To see why the exact same path worked in `App.jsx` and failed in `ArticleList.jsx`, look at where the two files sit in the folder tree:

```files title="article-site: Import Paths by Folder Depth" caption="App.jsx sits in src/ and steps down into ./components/, whereas ArticleList.jsx and ArticleCard.jsx sit side by side in src/components/."
src/
  App.jsx | parent | Sits in `src/`, so it imports from `./components/ArticleList.jsx`
  components/
    ArticleList.jsx | default export | Sits inside `src/components/`, so it imports neighbor `./ArticleCard.jsx`
    ArticleCard.jsx | default export | Sits inside `src/components/`, so it imports neighbor `./Badges.jsx`
    Badges.jsx | named exports | Sits inside `src/components/` and exports `LiveBadge` and `NewBadge`
```

Look at where `./` starts in each file:
1. Our main file, `App.jsx`, sits inside the `src` folder. Starting there, its import path steps down into the `components` subfolder and finds the card file.
2. Our list file, `ArticleList.jsx`, is **already inside the `components` folder**. Starting there, that copied path looks for a second `components` subfolder inside the first one, which does not exist!

```tree dir=right caption="Why the same file, ArticleCard.jsx, has two different relative paths depending on which file imports it."
Reaching `src/components/ArticleCard.jsx` from two different folders
- +From `src/App.jsx` [sits in `src/`] | Write `'./components/ArticleCard.jsx'` | Steps down into `components/` and finds `ArticleCard.jsx`
- +From `src/components/ArticleList.jsx` [already in `src/components/`] | Write `'./ArticleCard.jsx'` | Finds its neighbor `ArticleCard.jsx` in the **same folder**
- !Copied `'./components/ArticleCard.jsx'` inside `ArticleList.jsx` | Looks for `src/components/components/ArticleCard.jsx` | **Fails to resolve import!**
```

### Fixing the neighbor path inside the `components` folder

Because the list file and the card file sit side by side in the `components` folder, the list file reaches its neighbor directly with `./`:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from ~'./ArticleCard.jsx'~; // Neighbor in the same src/components/ folder

export default function ArticleList() {
  return (
    <section>
      <ArticleCard />
      <ArticleCard />
    </section>
  );
}
```

Meanwhile, our main file sits one folder higher in `src`, so it steps into the `components` subfolder to import the list:

```jsx title="src/App.jsx" startLine="1"
import ArticleList from ~'./components/ArticleList.jsx'~; // Steps from src/ into src/components/

export default function App() {
  return (
    <main>
      <h1>Latest Articles</h1>
      <ArticleList />
    </main>
  );
}
```

Inside the `components` folder, the copied path looks for a second `components` subfolder.

Starting with `./` finds the neighbor file right inside the same `components` folder.

> [!PRINCIPLE]
> **Principle 4: Import Paths: Every Relative Path Starts from the Importing File**
>
> *Start every relative import path from the folder of the file that writes the import. Use `./` for the same folder, `../` for the parent folder, and no dot for an installed package.*
>
> Never copy and paste a relative import line from `App.jsx` into a file inside the `components` folder without adjusting the path. Two files sitting together inside the `components` folder reach each other directly with `./`.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleList.jsx"
> import ArticleCard from ~'./ArticleCard.jsx'~; // Neighbor in the same folder
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleList.jsx"
> import ArticleCard from ~'./components/ArticleCard.jsx'~; // **WRONG:** looks for src/components/components/ArticleCard.jsx!
> ```

## Putting All Four Principles Together Across Our Project Files

Here are all four files of our modular news project working together, applying every principle from this lesson:

```jsx title="src/components/Badges.jsx" startLine="1"
~export function LiveBadge~() { // Principle 2: 1st named export in Badges.jsx
  return <span className="badge">Live</span>;
}

~export function NewBadge~() { // Principle 2: 2nd named export in Badges.jsx
  return <span className="badge">New</span>;
}
```

```jsx title="src/components/ArticleCard.jsx" startLine="1"
~import { LiveBadge, NewBadge } from './Badges.jsx';~ // Principle 3 & 4: Named imports in { } from neighbor ./Badges.jsx

function ~getHeadline~() { // Principle 1: Unexported helper stays private to ArticleCard.jsx
  return 'New Park Opens Today';
}

~export default function ArticleCard~() { // Principle 1 & 2: Main component of this file uses export default
  return (
    <article className="card">
      <LiveBadge />
      <NewBadge />
      <h2>{getHeadline()}</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

```jsx title="src/components/ArticleList.jsx" startLine="1"
~import ArticleCard from './ArticleCard.jsx';~ // Principle 3 & 4: Default import without braces from neighbor ./ArticleCard.jsx

export default function ArticleList() {
  return (
    <section>
      <ArticleCard />
      <ArticleCard />
    </section>
  );
}
```

```jsx title="src/App.jsx" startLine="1"
~import ArticleList from './components/ArticleList.jsx';~ // Principle 4: From src/App.jsx, step into ./components/ArticleList.jsx

  return (
    <main>
      <h1>Latest Articles</h1>

    </main>
  );
}

```tree dir=right caption="How Vite follows import statements from src/App.jsx across all four module files."
How the four files connect starting at `src/App.jsx`
- +1. `src/App.jsx` [root component] | Imports default `ArticleList` from `'./components/ArticleList.jsx'`
- +2. `src/components/ArticleList.jsx` [default export] | Imports default `ArticleCard` from neighbor `'./ArticleCard.jsx'`
- +3. `src/components/ArticleCard.jsx` [default export + private `getHeadline`] | Imports named `{ LiveBadge, NewBadge }` from neighbor `'./Badges.jsx'`
- +4. `src/components/Badges.jsx` [two named exports] | Exports `LiveBadge` and `NewBadge` by name
```

| Aspect | The Single-File Habit | The ES Module Rule in React |
| :--- | :--- | :--- |
| **Visibility across files** | Expects every function in the project to be visible everywhere | Each `.jsx` file is a private module; names cross files only via `export` and `import` |
| **How many defaults per file** | Puts `export default` in front of every component in a file | At most **one** `export default` per file for the main component; unlimited named exports for multiple components |
| **Curly braces in `import`** | Treats `{ }` in `import` lines as optional formatting | No braces for `export default`; curly braces `{ Name }` for named `export function` |
| **Renaming on `import`** | Assumes any import can be renamed the same way | Default imports take any local name directly; named imports must match the exported name first and rename with `as` |
| **Relative paths starting with `./`** | Copies `./components/...` from `App.jsx` into every file | Every `./` or `../` path starts from the folder of the file that holds the `import` |

## For the Interview

> **The Interview Question:** How do you split components across files, and how do default and named imports differ?

### How to Answer Clearly in 30 Seconds

"In React, every `.jsx` file is an isolated ES module whose functions stay private until exported. To split a component into its own file, we export it from that file and import it at the top of the file that renders it. JavaScript modules have two kinds of exports: a **default export** and **named exports**. A file can have **at most one** `export default`, which we use for a file's single main component. A file can have **unlimited named exports** using `export function` when one file holds several smaller components or helpers. How a file exports a component dictates how another file must import it. We import a default export **without curly braces**, and because there is only one default export in that file, we can give it any local name we choose. We import named exports **inside curly braces** using their exact exported names so JavaScript knows which export to grab, or we rename them inside the braces with `as`. Finally, every relative import path starting with `./` or `../` resolves starting from the folder of the file that writes the import."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"How many `export default` statements can a single file have, and how many named exports?"**
   - A file can have **at most one** `export default` statement. Adding a second `export default` stops the build immediately with `A module cannot have multiple default exports`. Named exports have **no limit**.

2. **"Can I rename a component when I import it?"**
   - For a **default export**, yes, directly on the import line without curly braces. Leaving out the curly braces grabs the file's single `export default` and gives it whatever new local nickname you write, such as `StoryCard`.
   - For a **named export**, curly braces search the exporting file by name. You must write the existing exported name first so JavaScript finds it, followed by `as` and the new local nickname, such as `LiveBadge as BreakingBadge`.

3. **"What causes React's `Element type is invalid ... got: undefined` error when importing a component?"**
   - That error happens when the variable inside a JSX tag evaluates to `undefined`. In modern ES modules, mixing up default and named imports stops earlier with a browser `SyntaxError`. React's `got: undefined` error appears when code reads a missing property from an imported object or in older bundlers.

```tree dir=right caption="Quick comparison of Default Exports vs. Named Exports for interviews."
Default Export vs. Named Export
- +Default export [`export default function ArticleCard`] | **At most 1** per file | Import **without `{ }`**: `import ArticleCard from './ArticleCard.jsx'` | Rename directly: `import StoryCard from './ArticleCard.jsx'`
- +Named export [`export function LiveBadge`] | **Unlimited** per file | Import **inside `{ }`**: `import { LiveBadge } from './Badges.jsx'` | Rename with `as`: `import { LiveBadge as BreakingBadge } from './Badges.jsx'`
```
