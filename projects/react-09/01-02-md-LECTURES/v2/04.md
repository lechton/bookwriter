## Why We Split a Page into Components

### A page is made of pieces, and each piece is a function

Look at any real website: an online shop shows twenty product cards, and a news site shows twenty article cards. If you build that whole page inside one giant function, you end up copying and pasting the same card markup twenty times. Tomorrow, when you want to change the card's design, you have to hunt through hundreds of lines and edit all twenty copies by hand.

In React, you never copy and paste the same piece of markup over and over. Instead, you split the page into small, reusable pieces called **components**. Each component is a JavaScript function that returns the markup for one piece of the page.

```tree caption="Two ways to put twenty article cards on a page: copy-pasting markup by hand vs. splitting out a reusable component."
Two ways to put twenty article cards on a page
- !Copy and paste `<article>` 20 times inside `App` | Everything sits inside **one giant function** | Every design change means **editing all 20 copies** by hand
- +Split into a reusable `ArticleCard` component | Write the `<article>` markup **once** inside `function ArticleCard` | Place `<ArticleCard />` **wherever** you need a card
```

### One function for the card, and one tag wherever we need it

First, you write the markup for one card inside its own function:

```jsx title="App.jsx" startLine="1"
function ~ArticleCard~() { // 1. Define the component function once
  return (
    <article className="card">
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

Then, wherever you want that card to appear on the page, you write the function's name as a tag:

```jsx title="App.jsx" startLine="10"
export default function App() {
  return (
    <main>
      <h1>Latest Articles</h1>
      ~<ArticleCard />~ {/* 2. Each tag puts one card on the page */}
      <ArticleCard />
    </main>
  );
}
```

Write the tag twice, and two cards appear on the page. Write it ten times, and ten cards appear:

```page caption="What the user sees in the browser when App places two <ArticleCard /> tags on the page."
heading: Latest Articles
card: title=New Park Opens Today | text=The park on Main Street opens at noon.
card: title=New Park Opens Today | text=The park on Main Street opens at noon.
```

```tree dir=right caption="The two steps to create and use a React component."
How to create and use a component
- +1. Define the component function [`function ArticleCard`] | Write the `<article>` markup **once** inside its own function
- +2. Use it as a JSX tag [`<ArticleCard />`] | Place `<ArticleCard />` inside `App` **as many times** as you need
```

### Two kinds of tags sit side by side in your markup

Look at the tags inside `App` above. A page heading, a main wrapper, and our article card all use angle brackets, and they sit right next to each other.

Yet they are not all the same. **The browser only knows built-in HTML tags**, such as a main wrapper, a heading, an article, or a footer. It has no idea what our custom card tag is. Whenever you read JSX or check the browser's developer tools, every tag belongs to one of two groups:

```tree caption="Every angle-bracket tag in JSX belongs to one of two groups: built-in browser HTML tags or your own React component tags."
Tags side by side inside JSX [`<main>` `<h1>` `<ArticleCard />`]
- +Built-in HTML tags [`<main>` `<article>` `<footer>`] | !They start with a **small letter** | They are **known** to the browser | Created **directly** in the browser DOM
- +Your React component tags [`<ArticleCard />` `<Footer />`] | !They start with a **capital letter** | They are **known only** to React | React **calls your function** and puts its returned HTML into the DOM
```

### How we inspect our components in the browser

Throughout this lesson, we keep all our components inside one file, `src/App.jsx`, so you can see every function and every tag together at a glance. Whenever we want to check what happened on the page, we look in three places in the browser:
- **The page viewport** shows what the user sees on screen.
- **The Elements panel** shows the real HTML nodes inside the browser **DOM**.
- **The Console panel** shows messages printed by `console.log` and any warnings from React.

### Four Principles of Component Anatomy

**PRINCIPLES:** A React component is a JavaScript function that returns JSX. At first glance, it looks just like any normal JavaScript function. However, React uses your component through a `<Tag />` to build and update the page. Because of that, four real issues come up in daily debugging and code interviews:
1. **Principle 1 — Declaring vs. invoking a component**: Declaring `function ArticleCard` and placing `<ArticleCard />` are two separate steps. If you declare `ArticleCard` **but forget to write `<ArticleCard />` inside `App`**, nothing appears. When you place `<ArticleCard />` in `App`, **React calls your function** and puts only the returned `<article>` HTML into the browser DOM. That call by React is what **"rendering"** means.
2. **Principle 2 — Why a small first letter hides your component**: Normal JavaScript functions start with a small letter in `camelCase`. If you name a component `articleCard` or `footer` with a small first letter, React treats `<articleCard />` or `<footer />` as a built-in HTML tag and **never calls your function**. With `<footer />`, it prints zero errors in the Console!
3. **Principle 3 — Why a line break after `return` erases your component**: Suppose you move multi-line JSX to the line below `return`, **but forget to open the parenthesis on the `return` line**. JavaScript automatically turns `return` into `return;`, gives back `undefined`, and your component disappears with zero Console errors.
4. **Principle 4 — Why putting a component inside another component wipes out user input**: If you define `CommentBox` inside `ArticleCard`, JavaScript creates a brand-new `CommentBox` function in memory on every update. React then destroys the old `<input>` box and erases whatever the user was typing.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Rendering: React Calls the Component for Each Tag** | **Interview Core & Two-Step Rule:** Declaring `ArticleCard` without placing `<ArticleCard />` inside `App` shows nothing on screen; and interviewers ask what "rendering" means and why `<ArticleCard>` is not in the DOM. | Place `<ArticleCard />` as a JSX tag inside `App`. React calls `ArticleCard` once per tag and puts only the returned `<article>` HTML into the browser DOM. |
| **Principle 2** | **PascalCase: Start Component Names with a Capital Letter** | **Common Bug & #1 Interview Trap:** Naming a component `articleCard` or `footer` with a small first letter makes it disappear, and `<footer />` prints zero errors! | Start every component name with a capital letter, such as `ArticleCard` and `Footer`, in both the function and the tag so React calls your function instead of making an empty HTML tag. |
| **Principle 3** | **Multi-Line Return: Open the Parenthesis on the `return` Line** | **Silent Debugging Nightmare:** Moving JSX to the line below a bare `return` without opening a parenthesis on the `return` line makes the component vanish with zero Console or terminal errors. | When JSX spans multiple lines, open the parenthesis on the same line as `return` so JavaScript does not insert a semicolon and return `undefined`. |
| **Principle 4** | **Top-Level Components: Never Define a Component Inside Another** | **Severe Input-Wiping Bug & Senior Interview Question:** Defining `CommentBox` inside `ArticleCard` erases whatever the user typed and loses cursor focus on every update. | Define every component at the top level of the file, outside all other functions, so React sees the same function on every render and keeps the user's DOM nodes alive. |

## 1. Principle 1: Rendering Means React Calls Your Component for Each `<Tag />`

### Writing the component function and using its tag are two separate steps

Putting a component on the screen takes **two separate steps**: first you declare the function, and then you use its tag inside `App`.

- **In daily coding**: If you write the card function, **but forget to place its tag inside `App`**, you see nothing on the screen. Declaring the function and using its tag are two separate steps.
- **In an interview**: When an interviewer asks what a component is and how it runs, do not stop at *"It is a function that returns JSX."* State both steps: you write the function, and you place its tag in `App` so **React calls your function**. That call by React is what **rendering** means.

First, we write the function for the card:

```jsx title="App.jsx" startLine="1"
function ~ArticleCard~() { // Step 1 only: declared in memory, but never used below
  console.log('ArticleCard runs');
  return (
    <article className="card">
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

Below the card, `App` returns only the page heading and never names the card:

```jsx title="App.jsx" startLine="11"
export default function App() {
  return (
    <main>
      <h1>Latest Articles</h1>
    </main>
  );
}
```

**When you only write the function and forget to place its tag, the function never runs!** Writing the function only saves it in memory: no card appears on the screen, and nothing prints in the Console panel.

```tree dir=right caption="Declaring a component function in App.jsx vs. invoking its <Tag /> inside App so React renders it."
The two separate steps to make a component appear
- !Step 1 alone: Only declare the function [`function ArticleCard`] | Saves the function in memory, **but nothing calls it** | **0 cards** on screen and **0 messages** in the Console
- +Step 1 + Step 2: Also place the tag inside `App` [`<ArticleCard />`] | React **calls `ArticleCard` once per tag** during rendering | Puts the returned `<article>` **onto the page**
```

### A function runs when you call it, or when you hand it to someone else

In plain JavaScript, the name of a function can appear in two ways:

```js title="Plain JavaScript"
function sayHello() {
  console.log('Hello');
}

~sayHello()~; // 1. With (): YOU call the function right now
button.addEventListener('click', ~sayHello~); // 2. Without (): you hand the function to the browser to call later
```

**Where did the parentheses go?** Look at the last line above. With parentheses, our code calls the function right now. Without parentheses, we hand the function itself to the browser. Passing a function without calling it is called a **function reference**, and the browser calls it later whenever the user clicks.

**React works the same way!** To put two cards on the page, we never call the card function with parentheses. Instead, we write its tag twice. Each tag hands the function to React, and React calls it:

```tree caption="Why we do not call a component with parentheses in JSX, and instead hand it to React as a <Tag />."
How to invoke a component in JSX
- !Do NOT call the component yourself with parentheses | In plain JS you call a function right now with parentheses | In JSX we **never** call the component function ourselves
- +DO hand the component to React as a tag [`<ArticleCard />`] | Like `addEventListener` hands `sayHello` to the browser without parentheses | `<ArticleCard />` **hands `ArticleCard` to React** to call
```

### Each tag tells React to call your component once

Now we place two card tags inside the page:

```jsx title="App.jsx" startLine="11"
export default function App() {
  return (
    <main>
      <h1>Latest Articles</h1>
      ~<ArticleCard />~ {/* 1st tag: React calls ArticleCard a 1st time */}
      ~<ArticleCard />~ {/* 2nd tag: React calls ArticleCard a 2nd time */}
    </main>
  );
}
```

When you **place two tags for the component**, two things happen as soon as you save the file:
1. **On the page**: Two cards appear below the heading.
2. **In the Console panel**: The component prints **twice**, once for each tag.

**What does the word "rendering" mean?** When React calls your component function to ask what markup it returns, that call is called **rendering**.

### The browser's Elements panel shows only real HTML tags

Open the browser's **Elements panel** to inspect the page. You will see the real HTML elements on the page, **but the component tag itself is nowhere in the DOM**:

```dom caption="What the browser's Elements panel shows: only the returned <article> HTML tags appear in the DOM, never <ArticleCard>."

    <h2>New Park Opens Today</h2>
    <p>The park on Main Street opens at noon.</p>
  </article>
</main>
```

**Where did our component tag go?** The browser only understands built-in HTML tags. Our component tag was written for React: React called the function, took the HTML it returned, and placed only that real HTML into the DOM.

```tree dir=right caption="What happens to the two kinds of tags in App.jsx when React builds the browser DOM in the Elements panel."
Tags written in `App.jsx`
- +Built-in HTML tags [`<main>` `<h1>` `<article>` `<h2>` `<p>`] | **Kept** in the browser's Elements panel as **real DOM nodes**
- +React component tags [`<App />` `<ArticleCard />`] | **Called by React** and replaced by the HTML they return | `<ArticleCard>` **never appears** in the DOM
```

> [!PRINCIPLE]
> **Principle 1: Rendering: React Calls the Component Wherever a Tag Names It**
>
> *Use a component by writing its name as a JSX tag, such as `<ArticleCard />`, inside another component's markup; React calls the function once for each tag.*
>
> Defining a component function does not put it on the page until a rendered component includes its `<Tag />`. During rendering, each `<ArticleCard />` tag hands the function to React so React calls it and puts the returned `<article>` HTML into the browser DOM. The component tag `<ArticleCard>` itself never appears in the DOM.
>
> **DO THIS:**
> ```jsx
> function ArticleCard() {
>   return <article>New Park Opens Today</article>;
> }
> export default function App() {
>   return <main>~<ArticleCard />~</main>; // React calls ArticleCard() and puts <article> in the DOM
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ~ArticleCard~() { // **WRONG:** declared, but no <ArticleCard /> tag in App, so ArticleCard() never runs!
>   return <article>New Park Opens Today</article>;
> }
> export default function App() {
>   return <main></main>;
> }
> ```

## 2. Principle 2: Start Component Names with a Capital Letter in `PascalCase`

### Three ways programmers join words into one name

Because names in JavaScript cannot contain spaces, programmers use three common styles to join words together:

- **`camelCase`** — such as `myName`, `articleCard`, and `formatDate`. The first word starts with a small letter, and each later word starts with a capital letter, like the humps of a camel. This is the usual style for variables and functions in JavaScript, **but you must not use it for React components**.
- **`PascalCase`** — such as `ArticleCard`, `CommentBox`, and `Footer`. **Every** word starts with a capital letter, including the very first word. **You must use `PascalCase` for every React component.**
- **`snake_case`** — such as `my_name` and `article_card`. All words use small letters joined by an underscore `_`. Because its first letter is small, **you must not use it for React components** either.

```tree caption="The three naming conventions in code: which ones we do NOT use for React components vs. the one we DO use."
Variable and function naming conventions in code
- !`camelCase` [`myName` `articleCard`] | ~Do **NOT** use for React components | First word starts with a **small letter** | JSX treats `<articleCard />` as an **HTML tag**
- +`PascalCase` [`ArticleCard` `CommentBox`] | +**DO** use for every React component | Every word starts with a **capital letter** | JSX knows `<ArticleCard />` is **your component function**
- !`snake_case` [`my_name` `article_card`] | ~Do **NOT** use for React components | All words use **small letters** joined by `_` | JSX also treats `<article_card />` as an **HTML tag**
```

### In React, a capital first letter is a compiler rule, not a style habit

In plain JavaScript, choosing `myName` or `MyName` is only a matter of style for human readers; JavaScript runs both the same way. In React JSX, however, **the first letter of a tag is a strict compiler rule**:

- **In daily coding**: If your component's name starts with a small letter, React treats the tag as a built-in browser HTML tag and **never calls your function**.
- **In an interview**: If an interviewer asks whether `PascalCase` is just a naming convention, never say *"Yes, it is best practice."* State clearly: **No, it is a compiler rule—a small first letter is read as an HTML tag name, so our function never runs.**

```tree caption="Do not confuse plain JavaScript's style habit with React JSX's compiler rule."
Is a capital first letter in `PascalCase` just a style convention?
- !In Plain JavaScript [`let myName` `let MyName`] | ~Only a **style habit** for human readers | JavaScript runs both names the **exact same way** | Do **not** give this answer in a React interview
- +In React JSX [`<articleCard />` `<ArticleCard />`] | +A **strict compiler rule** | Small first letter becomes a **built-in HTML tag** string | Capital first letter makes React **call your function**
```

### A small first letter turns your component into an empty HTML tag

In plain JavaScript, we name functions with a small first letter. Suppose a developer does the same here and starts the card function with a small letter:

```jsx title="App.jsx" startLine="1"
function ~articleCard~() { // **WRONG:** small 'a'
  console.log('articleCard runs');
  return (
    <article className="card">
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

Then the tag is also written with a small first letter:

```jsx title="App.jsx" startLine="11"
export default function App() {
  return (
    <main>
      ~<articleCard />~ {/* **WRONG:** small 'a' — JSX treats this as an HTML tag, so articleCard() never runs! */}
    </main>
  );
}
```

Both names match, **but when you forget to start with a capital letter, the function never runs!** When you save the file:
1. **On the page**: No card appears.
2. **In the Console panel**: The component never prints, and React prints two red warnings.
3. **In the Elements panel**: The browser creates an empty, unknown HTML element in small letters.

### How the compiler tells an HTML tag apart from your component

Before the browser runs your file, the JSX compiler rewrites every tag into a JavaScript function call. To decide what to put inside that call, it looks only at **the first letter of the tag**:

```js title="How the JSX Compiler Rewrites Each Tag"
~<articleCard />~ // Small 'a' -> _jsx('articleCard', {}) — quoted HTML tag string; function never runs!
~<ArticleCard />~ // Capital 'A' -> _jsx(ArticleCard, {}) — passes your function so React calls it!
```

```tree dir=right caption="How the JSX compiler rewrites a tag based on its first letter."
How JSX compiles `<Tag />`
- !Starts with a small letter [`<articleCard />`] | Compiled **with quotes** around `'articleCard'` | Treated as an **HTML tag string**; your function **never runs**
- +Starts with a capital letter [`<ArticleCard />`] | Compiled **without quotes** as `ArticleCard` | Passes **your JavaScript function** so React calls it
```

**We need to capitalize the name in two places.** First, we write the component's name when we define the function, such as `function ArticleCard`. Second, we write the same name in the tag we use, such as `<ArticleCard />`. Both places need to start with a capital letter. What if we capitalize one and not the other? Then the two names no longer match, and the whole page fails with an error. You must start **both** the function and the tag with a capital letter:

```overlay caption="What happens if you capitalize the <ArticleCard /> tag while leaving function articleCard small."

```

```tree caption="Capitalizing both the function and the tag vs. the half-fix that causes a ReferenceError."
Where you must capitalize a component's name
- +Capitalize BOTH the function and the tag [`function ArticleCard` `<ArticleCard />`] | Both names **match** and start with a **capital letter** | React **calls `ArticleCard`**
- !Capitalize only the tag while leaving the function small [`function articleCard` `<ArticleCard />`] | The two names **no longer match** | Page crashes with **`ReferenceError: ArticleCard is not defined`**
```

### The bug that is even trickier: a component name that matches a real HTML tag

In the previous example, React printed a warning because the tag name was not a real HTML word. Now suppose your component has the same name as a **real HTML tag**, such as a footer, a header, or a button. What happens if you write it with a small first letter?

First, the developer writes the footer component with a small first letter:

```jsx title="App.jsx" startLine="1"
function ~footer~() { // **WRONG:** small 'f' matches the real HTML <footer> word
  console.log('footer runs');
  return <footer>Latest Articles, 2026</footer>;
}
```

Then the tag is also written with a small first letter:

```jsx title="App.jsx" startLine="6"
export default function App() {
  return (
    <main>
      <h1>Latest Articles</h1>
      <ArticleCard />
      ~<footer />~ {/* **WRONG:** creates an empty HTML <footer></footer> with 0 Console warnings! */}
    </main>
  );
}
```

When you **use a small first letter on a component name that matches a real HTML tag**, the Console stays completely silent! A footer with a small letter is a valid HTML tag. So React thinks you simply want an empty footer on the page, and it ignores your function with zero warnings. Change both the function and the tag to start with a capital letter, and the footer text appears right away:

## 3. Principle 3: Open the Parenthesis on the Same Line as `return`

### Silent bugs are much harder to find than loud errors

When code crashes with a red error box, it tells you the exact file and line number. The bugs that waste an afternoon are **silent bugs**: a component disappears from the screen, the Console panel shows **no error**, and the terminal shows **no warning**.

```tree caption="Two kinds of bugs when a component fails to appear: loud crashes vs. silent bugs."
Two kinds of bugs when a component fails
- +Loud crash [`ReferenceError: ArticleCard is not defined`] | +Easy to spot: shows a **red error box** | Tells you the **exact file and line number**
- !Silent bug [`<footer />` `return` + `Enter`] | ~Hard to spot: component **vanishes with 0 errors** | **Nothing** on screen, **0 Console errors**, and **0 terminal warnings**
```

Suppose our footer grows from one line to two lines. To make it look tidy, a developer presses `Enter` right after `return` and moves the markup to the next line:

```jsx title="App.jsx"
function Footer() {
  ~return~ // **WRONG:** bare return at the end of the line becomes return; and returns undefined!
    <footer>
      <p>Latest Articles, 2026</p>
      <a href="/contact">Contact us</a>
    </footer>;
}
```

When you **put a line break right after `return` without opening a parenthesis**, the entire footer vanishes from the page with zero errors in the Console.

### Why a line break right after return stops your component

**Why did a line break after `return` erase the footer?** In JavaScript, you can leave out the semicolon at the end of a line, and JavaScript adds it for you automatically. This rule is called **Automatic Semicolon Insertion**.

Most of the time it helps. However, when the word `return` sits alone at the end of a line with nothing after it, **JavaScript automatically ends the statement right there**:

```js title="Plain JavaScript"
function getTitle() {
  ~return~ // JavaScript automatically inserts a semicolon here: return;
    'New Park Opens Today'; // Never reached!
}

console.log(~getTitle()~); // Logs undefined
```

```tree dir=right caption="Where JavaScript's Automatic Semicolon Insertion helps vs. where it sets a trap."
Automatic Semicolon Insertion at the end of a line
- +Normal statement [`const city = 'Boston'`] | JavaScript turns it into `const city = 'Boston';` | **Works as expected**
- !Bare `return` at the end of a line [`return` + `Enter`] | JavaScript turns it into `return;` | **Stops the function** immediately and returns **`undefined`**
```

When React calls our footer function, the function stops on the `return` line and gives back `undefined`. The markup below it is never reached. Returning `undefined` is valid in JavaScript, so React shows nothing and prints no error. Only a code linter in your editor will warn you that the markup below is unreachable.

### Put the opening parenthesis on the same line as return

Whenever your markup spans more than one line, open the parenthesis **on the same line as `return`**:

```jsx title="App.jsx"
function Footer() {
  ~return (~ // Opening parenthesis on the return line keeps the statement open across lines
    <footer>
      <p>Latest Articles, 2026</p>
      <a href="/contact">Contact us</a>
    </footer>
  );
}
```

**Why does opening a parenthesis on the `return` line solve the problem?** A JavaScript statement cannot end while a parenthesis is open. Opening the parenthesis on the `return` line forces JavaScript to keep reading across the line breaks until the closing parenthesis:

```tree dir=right caption="The three ways to write return in a component and what JavaScript returns for each."
How you write `return` in a component
- +One-line return [`return <footer>...</footer>;`] | JSX starts on the **same line** as `return` | Returns the **`<footer>` markup**
- +Multi-line with opening parenthesis on the `return` line | Open parenthesis keeps the statement **alive across lines** | Returns the **`<footer>` markup**
- !Bare `return` + `Enter` [`return` on its own line] | JavaScript inserts a semicolon: `return;` | Returns **`undefined`** — blank on screen with **0 Console errors**
```

> [!PRINCIPLE]
> **Principle 3: Automatic Semicolon Insertion: Open the Parenthesis on the `return` Line**
>

>

React renders nothing for `undefined` and logs no error. Opening the parenthesis on the same line as `return` keeps the statement open until the closing parenthesis.

>     <footer>

>       <a href="/contact">Contact us</a>

## 4. Principle 4: Define Every Component at the Top Level, Never Inside Another Component

### A component defined inside another component wipes out what the user typed

Now we want to add a comment box under each article card. Only the card uses this comment box. In plain JavaScript, you sometimes put a small helper function inside the function that uses it. So you might try to write the comment box **inside** the card.

**In React, you must never define one component inside another component.** Always define every component at the **top level** of the file, outside all other functions:

```tree caption="What we must never do with a component in React vs. where every React component must be defined."
Where to define a component function in React
- !Do NOT define a component inside another component [`CommentBox` inside `ArticleCard`] | Recreates `CommentBox` on **every render** | **Destroys** its `<input>` DOM node and **wipes user text**
- +DO define every component at the top level of the file [Outside all other functions] | Created **once** when the file loads | React **keeps** its `<input>` DOM node and user text **alive**
```

Look at what happens when the comment box is defined inside the card:

```jsx title="App.jsx" startLine="1"
function ArticleCard() {
  function ~CommentBox~() { // **WRONG:** defined inside ArticleCard — recreated on every render!
    return <input placeholder="Write a comment" />;
  }
```

Below it, the card returns the heading, the text, and the comment box tag:

```jsx title="App.jsx" startLine="6"
  return (
    <article className="card">
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
      <CommentBox />
    </article>
  );
}
```

When you **define one component inside another component**, everything looks fine on the first load. That makes this bug very easy to miss! The problem appears as soon as the outer component updates:
1. The user clicks into the comment box and types a comment.
2. Now the card updates and runs again.
3. The moment the card runs again, **everything the user typed is wiped out, and the blinking cursor disappears!**

### A function inside another function is made again on every call

To see why the comment box was wiped out, look at how JavaScript handles functions in two different places:
- A function at the **top level** of a file, outside all other functions, is created **once**, when the file loads.
- A function **nested inside another function** is created **brand-new in memory each time the outer function runs**:

```js title="Plain JavaScript"
function makeGreeter() {
  function ~greet~() { // Created brand-new in memory every time makeGreeter() runs
    return 'Hello';
  }
  return greet;
}

const firstRun = makeGreeter();
const secondRun = makeGreeter();

console.log(~firstRun === secondRun~); // false — two different functions in memory!
```

Each call to the outer function runs the inner `function` line again and makes a brand-new function in memory. The two functions do the same job, but they are two different functions in memory, so comparing them gives `false`.

```tree caption="Two places to define a component function in App.jsx and how JavaScript creates each one in memory."
Where a component function is defined in `App.jsx` [`CommentBox`]
- +At the top level of the file [Outside all functions] | +Created **ONCE** when the file loads | **Same function** in memory on every render: `CommentBox === CommentBox` is **`true`**
- !Nested inside another component [Inside `ArticleCard`] | ~Created **BRAND-NEW** every time `ArticleCard` runs | **Different function** each time: `CommentBox #1 === CommentBox #2` is **`false`**
```

### A new function tells React to destroy the old input box and build a new one

When a page updates, React keeps unchanged DOM nodes in place so text boxes keep what the user typed and keep their cursor focus.

How does React decide whether to keep the old comment box or tear it down? It checks whether the component function in that spot is the **very same function** as on the last run:
1. **On the first run**: The card creates the first comment box function and puts the text box on the page, where the user starts typing.
2. **On the second run**: When the card updates, it runs again and makes a **second, brand-new function** in memory for the comment box.
3. **When React compares the two runs**: React sees a different function in that spot. To React, a different function means a different component! So React removes the old text box and builds a brand-new, empty one. Everything the user typed is wiped out, and the cursor is lost.

```tree dir=right caption="How React decides whether to keep or destroy an existing DOM node when a component updates."
React compares the component function at the same spot [`OldFn === NewFn`]
- +Same function in memory [`CommentBox === CommentBox` is `true`] | Top-level component | React **keeps** the existing `<input>` DOM node, `"See you there"`, and **cursor focus**
- !Different function in memory [`CommentBox #1 === CommentBox #2` is `false`] | Nested component | React **destroys** the old `<input>` and mounts a **brand-new empty `<input>`**
```

### Moving every component to the top level keeps the input box alive

The fix is to move the comment box out of the card so both functions sit at the **top level of the file**:

```jsx title="App.jsx" startLine="1"
function ~CommentBox~() { // 1. Top level of the file: created ONCE when the file loads
  return <input placeholder="Write a comment" />;
}
```

Inside the card, only the tag remains:

```jsx title="App.jsx" startLine="5"
function ArticleCard() {
  return (
    <article className="card">
      <h2>New Park Opens on Saturday</h2>
      <p>The park on Main Street opens at noon.</p>
      ~<CommentBox />~ {/* 2. ArticleCard only renders the <CommentBox /> tag */}
    </article>
  );
}
```

::: row
::: col title="CommentBox Nested Inside ArticleCard on Update" kind="bad"
```page size=mini
heading: Latest Articles
card: title=New Park Opens on Saturday | text=The park on Main Street opens at noon. | input=Write a comment | bad=input
```
:::
::: col title="CommentBox at the Top Level on Update" kind="good"
```page size=mini
heading: Latest Articles
card: title=New Park Opens on Saturday | text=The park on Main Street opens at noon. | typed=See you there | good=typed
```
:::
:::

| Where `CommentBox` is defined | First run | Next run on update | What happens to the `<input>` in the DOM |
| :--- | :--- | :--- | :--- |
| **Inside `ArticleCard`, nested** | `CommentBox #1` | `CommentBox #2` — new function | Old `<input>` is destroyed; `"See you there"` and cursor focus are lost |
| **At the top level, outside** | `CommentBox` | `CommentBox` — same function | Existing `<input>` is kept; `"See you there"` and cursor focus stay untouched |

When you **move the component to the top level of the file**, JavaScript creates that function once when the file loads. Every time the card updates, React sees the exact same function in that spot. It keeps the text box, the user's typed text, and the blinking cursor untouched. What if a child component needs data from its parent? You still keep both components at the top level and pass the data through props.

> [!PRINCIPLE]
> **Principle 4: Top-Level Components: Define Every Component at the Top Level**
>
> *Define every component at the top level of the file, outside all other functions, and never inside another component.*
>
> A component defined inside another component creates a brand-new function in memory on every render of the outer component, so `OldFn !== NewFn`. When React sees a different function in the same spot, it destroys the old DOM nodes and builds new ones from scratch. That wipes out any text the user typed and loses cursor focus.
>
> **DO THIS:**
> ```jsx
> function ~CommentBox~() { // Top level: same function in memory on every render
>   return <input placeholder="Write a comment" />;
> }
> function ArticleCard() {
>   return <article><CommentBox /></article>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ArticleCard() {
>   function ~CommentBox~() { // **WRONG:** nested inside ArticleCard — new function every render, wipes input!
>     return <input placeholder="Write a comment" />;
>   }
>   return <article><CommentBox /></article>;
> }
> ```

## Putting All Four Principles Together in `App.jsx`

### Four top-level components working together in one file

Here is our complete `App.jsx` file with all four pieces of the page: the comment box, the article card, the footer, and `App`. Every component sits at the top level and starts with a capital letter. Each one opens the parenthesis on the `return` line for multi-line markup and is used as a tag:

```jsx title="src/App.jsx"
function ~CommentBox~() { // 3. Called 3rd, inside ArticleCard
  console.log('CommentBox runs');
  return <input placeholder="Write a comment" />;
}

function ~ArticleCard~() { // 2. Called 2nd, 1st child tag inside App
  console.log('ArticleCard runs');
  return (
    <article className="card">
      <h2>New Park Opens on Saturday</h2>
      <p>The park on Main Street opens at noon.</p>
      <CommentBox />
    </article>
  );
}

function ~Footer~() { // 4. Called 4th, 2nd child tag inside App
  console.log('Footer runs');
  return (
    <footer>
      <p>Latest Articles, 2026</p>
      <a href="/contact">Contact us</a>
    </footer>
  );
}

export default function ~App~() { // 1. Called 1st when the page loads
  console.log('App runs');
  return (
    <main>
      <h1>Latest Articles</h1>
      <ArticleCard />
      <Footer />
    </main>
  );
}
```

### The order in which React calls the four components

When the page loads, React starts at `App` and follows the tags from top to bottom. In `App` it calls the card first, and inside the card it calls the comment box. After finishing the card, it calls the footer:

```page caption="The finished page in the browser with App, ArticleCard, CommentBox, and Footer all rendered."
heading: Latest Articles
card: title=New Park Opens on Saturday | text=The park on Main Street opens at noon. | typed=See you there | good=typed
line: Latest Articles, 2026 · Contact us | good
console: App runs -> ArticleCard runs -> CommentBox runs -> Footer runs | good
```

```tree caption="The component tree in App.jsx and the exact order from 1 to 4 in which React calls each component."
`App` [1. Logs `"App runs"`] | **Root component** | Returns `<main>` containing `<ArticleCard />` and `<Footer />`
- +`ArticleCard` [2. Logs `"ArticleCard runs"`] | **First child tag** in `App` | Returns `<article>` containing `<CommentBox />`
  - +`CommentBox` [3. Logs `"CommentBox runs"`] | **Child tag** inside `ArticleCard` | Returns `<input />`
- +`Footer` [4. Logs `"Footer runs"`] | **Second child tag** in `App` | Returns `<footer>`
```

| Aspect | The Plain JavaScript Habit | The React Rule |
| :--- | :--- | :--- |
| **The tag** | Call the function where its markup goes, or declare the function and forget the tag | Write its name as a tag, such as `<ArticleCard />`, and let React call it |
| **The name** | `camelCase`, like a normal function such as `articleCard` or `footer`, which creates an empty HTML tag | `PascalCase`, in both the function and the tag, such as `ArticleCard` and `Footer` |
| **The return** | Start long markup on the line after a bare `return`, which returns `undefined` with zero errors | Open the parenthesis on the `return` line whenever markup spans multiple lines |
| **The next run** | Put a helper inside the only function that uses it, which creates a new function on every run and wipes input | Keep every component at the top level of the file so React keeps existing DOM nodes alive |

## For the Interview

> **The Interview Question:** What is a React component, and how do you define and render one inside another component?

### How to Answer Clearly in 30 Seconds

"A React component is a JavaScript function whose name starts with a capital letter and that returns JSX describing one piece of the UI. To render it inside another component, we never call the function ourselves. Instead, we write its name as a JSX tag, like `<ArticleCard />`, and React calls the function for each tag. That call is what 'rendering' means. Three rules keep components working properly:
1. **Capital first letter in `PascalCase`**: a lowercase tag like `<footer />` or `<articleCard />` is treated as a built-in HTML tag, so our function never runs.
2. **Open the parenthesis on the `return` line**: a bare `return` with JSX on the next line triggers Automatic Semicolon Insertion, turning `return` into `return;` and returning `undefined`.
3. **Top-level definition**: we define every component at the top level of the file, never inside another component. A nested component creates a new function in memory on every render, which forces React to destroy and recreate its DOM nodes."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Is starting a component name with a capital letter in `PascalCase` just a naming convention?"**
   **No.** In plain JavaScript, `camelCase`, such as `let myName = 'John'`, is only a style convention for humans. In React, the first letter of a JSX tag is how the compiler tells built-in HTML tags apart from your components. A lowercase first letter, such as `<articleCard />` or `<footer />`, is compiled as an HTML tag string. The browser creates an empty HTML element, and your function never runs. A capital first letter, such as `<ArticleCard />` or `<Footer />`, passes your JavaScript function to React so React calls it.
2. **"What happens if you define a child component inside a parent component, such as `CommentBox` inside `ArticleCard`?"**
   On the first render, it appears to work. On every re-render of the parent, however, JavaScript creates a **brand-new function object in memory** for the inner component, so `oldFn !== newFn`. When React compares the new render with the previous one, it sees a different function at that position and assumes it is a completely different component. React then unmounts the old DOM nodes and mounts new ones from scratch. Any typed input text or cursor focus inside that child component is wiped out on every update.
3. **"Does `<ArticleCard>` appear in the browser's DOM in the Elements panel, and is `<ArticleCard />` the same as calling the function directly?"**
   No to both. First, the browser DOM only holds real HTML tags such as `<main>`, `<article>`, and `<h2>`. `<ArticleCard />` is for React, so `<ArticleCard>` never appears in the Elements panel. Second, writing `<ArticleCard />` hands the function to React so React tracks `ArticleCard` as its own component in the tree. Calling the function directly only hands React the returned `<article>` HTML and hides the component from React.

```tree dir=right caption="Interview comparison: rendering a component as a JSX tag vs. calling the function directly."
`<ArticleCard />` vs. calling the function directly in an interview
- +Render as a JSX tag [`<ArticleCard />`] | Hands the **`ArticleCard` function** to React | React tracks `ArticleCard` as **its own component** in the tree
- !Call the function directly | **You call** the function yourself | React only sees the returned `<article>` HTML; the component is **hidden from React**
```
