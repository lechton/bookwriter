## Why We Pass Data into Components with Props

### Hardcoded text inside a component stamps out identical copies

Look at any real news website: the article list shows several story cards one after another. Every card shares the same layout, with a heading and a short summary. Yet each card needs to show a different story.

Suppose we write the story's heading and summary directly inside our card file:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard() {
  return (
    <article className="card">
      <h3>~New Park Opens Today~</h3> {/* **WRONG:** hardcoded text inside the card */}
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

Then our list file places two card tags on the page:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList() {
  return (
    <section>
      ~<ArticleCard />~ {/* 1st card tag: shows New Park Opens Today */}
      ~<ArticleCard />~ {/* 2nd card tag: also shows New Park Opens Today! */}
    </section>
  );
}
```

Save both files, and the page shows the exact same park story twice:

```page caption="When the heading and summary are hardcoded inside ArticleCard.jsx, two <ArticleCard /> tags stamp out the exact same story twice."
card: title=New Park Opens Today | text=The park on Main Street opens at noon. | bad
card: title=New Park Opens Today | text=The park on Main Street opens at noon. | bad
```

Why did both tags draw the exact same story? Because those words are written directly inside the card function. Every time React calls that function, it returns the same hardcoded heading and summary. You would never create a separate component file for every news story on a website. Instead, you want **one** reusable card component that can display **any** story you hand to it.

```tree caption="Two ways to put different stories into article cards: hardcoding text inside the component vs. passing data into one reusable component."
How to show different stories with one `ArticleCard` component
- !Hardcode the story text inside `ArticleCard.jsx` | Every `<ArticleCard />` tag returns the **exact same words** | Two tags on the page look like a **copy-paste bug**
- +Pass each story's data into `<ArticleCard />` from `ArticleList.jsx` | +**DO** keep the `<article>` layout once inside `ArticleCard` | Each `<ArticleCard />` tag receives **its own heading and summary**
```

### Passing data on the tag and reading `props` inside the component

In plain JavaScript, when you want one function to work with different data on each call, you pass inputs inside the function's parentheses. In React, we never call a component function with parentheses ourselves. We write the component as a tag, and we pass data to it by writing attributes on that tag. React calls these inputs **props**, short for **properties**.

Passing props from a parent component to a child component takes **two steps**.

First, in our list file, we write each story's heading and summary as attributes on its card tag:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList() {
  return (
    <section>
      <ArticleCard
        ~title="New Park Opens Today"~ // 1st card's title prop
        summary="The park on Main Street opens at noon."
      />
      <ArticleCard
        ~title="Library Extends Hours"~ // 2nd card's title prop
        summary="The downtown branch now stays open until 9 PM."
      />
    </section>
  );
}
```

React collects all the attributes from one card tag into a single JavaScript object and passes it into the card function.

Second, in our card file, the function receives that `props` object and reads the heading and summary from it:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard(~props~) { // 1. React passes one props object for this card tag
  return (
    <article className="card">
      <h3>{~props.title~}</h3> {/* 2. Reads the title property from props */}
      <p>{~props.summary~}</p> {/* 3. Reads the summary property from props */}
    </article>
  );
}
```

Save both files, and the two card tags now display two different news stories from the same component:

```page caption="What the user sees when ArticleList passes each story's title and summary as props to ArticleCard."
card: title=New Park Opens Today | text=The park on Main Street opens at noon. | good
card: title=Library Extends Hours | text=The downtown branch now stays open until 9 PM. | good
```

```tree dir=right caption="The two steps that send data from a parent component tag into a child component function."
How data flows from `ArticleList` into `ArticleCard`
- +Step 1: Pass attributes on the child tag [`ArticleList.jsx`] | Write `title="..."` and `summary="..."` on each `<ArticleCard />` tag
- +Step 2: Read the `props` object [`ArticleCard.jsx`] | Receive `props` in the function parameter and read `{props.title}` and `{props.summary}`
```

### HTML attributes on browser tags vs. custom props on your component tags

Look at the two kinds of tags in those two files. Both built-in HTML tags and our own component tags carry attributes, and they sit right next to each other.

Yet their attributes follow two very different rules:
- **On a built-in HTML tag**, such as an article or an image, the attribute names are fixed by the HTML standard. You cannot invent a custom attribute named `summary` on an `<article>` tag and expect the browser to draw a paragraph for you.
- **On your own React component tag**, such as our article card, **you invent whatever prop names your component needs**. You can pass a title, a summary, or a reading time, and React packs all of those attributes into one `props` object for your function:

```tree caption="Attributes on built-in HTML tags vs. props on your own React component tags."
Attributes written on tags in JSX
- +Built-in HTML tags [`<article className="card">` `<img src="/park.jpg" />`] | Attribute names are **fixed by the HTML standard** | Passed to the **browser DOM element**
- +Your React component tags [`<ArticleCard title="..." summary="..." />`] | +**DO** choose any prop names your component needs | Packed by React into one **`props` object** and passed to your function
```

### Four Principles of Passing Props

**PRINCIPLES:** Props are how a parent component passes data down to a child component. React packs every attribute on a child tag into one read-only object and hands that object to the child function. Because of that, four rules come up constantly in daily debugging and interviews:
1. **Principle 1: Pass Attributes on the Tag and Read the `props` Object**: React packs every attribute on a child tag into one `props` object and passes it as the first argument to the child function. Leave the child's parentheses empty, and the page crashes with a `ReferenceError`. Spell an attribute `headline` in the parent while reading `props.title` in the child, and the heading goes blank with zero Console errors.
2. **Principle 2: Unpack the Single `props` Object with Curly Braces in the Parameter List**: Because React always passes **one object** as the first argument, you unpack its properties by putting curly braces around the parameter names. Leave out those curly braces, and the first parameter receives the **entire `props` object** instead of a string, crashing the page!
3. **Principle 3: Use Quotes for Strings and Curly Braces for Numbers, Booleans, and Objects**: Quotes on a JSX attribute always pass a text **string**, while curly braces pass any JavaScript value with its true type. Put quotes around a reading time of three minutes and add two minutes to it, and JavaScript glues the text together into `'32'` instead of `5`!
4. **Principle 4: Treat Props as Read-Only and Compute Derived Values in Local Variables**: A child component does not own its props. React freezes the `props` object in development mode, so overwriting any property on it crashes the page with a `TypeError`. Whenever you need a formatted or calculated value, store it in a new local `const` variable.

Here is the complete overview of all four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The `props` Object: Match Attribute Names to `props` Properties** | Leaving out the parameter crashes with `ReferenceError: title is not defined`; mismatching `headline` and `props.title` leaves the heading blank with zero Console errors. | Pass attributes on the child tag in the parent, receive `props` in the child function, and read the exact same property names. |
| **Principle 2** | **Parameter Destructuring: Put Curly Braces Around Prop Names** | Writing `title, summary` in the parameter list without curly braces puts the whole `props` object into `title` and crashes with `Objects are not valid as a React child`. | Unpack props from the first argument object with curly braces in the parameter list, such as `{ title, summary }`. |
| **Principle 3** | **Typed Props and Common Parents: Quotes for Strings, Braces for JS Values** | Writing `readTime="3"` in quotes passes the string `'3'`, turning `readTime + 2` into `'32'`; sibling components cannot pass data sideways. | Use quotes only for strings, use `{}` for numbers, booleans, and objects, and pass shared data down from a common parent component. |
| **Principle 4** | **The Read-Only Contract: Never Mutate Props; Derive Local Constants** | Assigning to `props.readTime` throws `TypeError: Cannot assign to read only property`, and mutating a prop object corrupts the parent's data across renders. | Treat `props` and every object inside `props` as read-only inputs, and compute formatted or calculated values in local `const` variables. |

## 1. Principle 1: Pass Attributes on the JSX Tag and Read the Matching Properties on `props`

### A child component cannot see its parent's attributes until it receives the `props` parameter

When you write attributes on a child tag in the parent file, those names do not automatically become variables inside the child file. Each file is separate, and the child function can only use what it receives through its parameter.

- **In daily coding**: Two mistakes happen when wiring up a new prop. First, if you write `{title}` inside the child component **without declaring a parameter in the function's parentheses**, the page crashes immediately with a `ReferenceError`. Second, if the parent passes an attribute named `headline` while the child reads `props.title`, the heading disappears from the card with **zero Console errors**.
- **In an interview**: Explain what happens under the hood. The build packs every attribute on the child tag into **one plain JavaScript object**. React then passes that object as the **first argument** when it calls the child component.

### How the build packs JSX attributes into one `props` object

Look closely at our list file and our card file from the introduction. Nowhere in the list file did we write a function call with an object inside parentheses! We only wrote attributes on the two card tags. Who turned those attributes into the `props` object?

Before the browser runs our list file, the build rewrites each card tag into a call to React's `_jsxDEV` helper. In that call, the build packs all of the tag's attributes into one plain JavaScript object:

```js title="How the build rewrites the two <ArticleCard /> tags in ArticleList.jsx"
_jsxDEV(ArticleCard, ~{ title: 'New Park Opens Today', summary: 'The park on Main Street opens at noon.' }~); // 1st card tag's props object
_jsxDEV(ArticleCard, ~{ title: 'Library Extends Hours', summary: 'The downtown branch now stays open until 9 PM.' }~); // 2nd card tag's props object
```

When React renders the list, it calls `ArticleCard` twice:
1. On the first call, React hands the first object to `ArticleCard` as its `props` parameter.
2. On the second call, React hands the second object to `ArticleCard` as its `props` parameter.

```tree dir=right caption="How Vite and React turn attributes on a JSX tag into the props object inside the child function."
One `<ArticleCard />` tag on its way into `ArticleCard`
- +1. Parent writes attributes [`ArticleList.jsx`] | `<ArticleCard title="New Park Opens Today" summary="..." />`
- +2. Build packs one object [JSX transform] | Creates `{ title: "New Park Opens Today", summary: "..." }`
- +3. React calls the child [`ArticleCard.jsx`] | Calls `ArticleCard` with that object as its first argument `props`
```

### Mistake 1: Using a prop name without declaring the parameter

In our list file, we pass `title` and `summary` on the card tag as before.

Now look at what happens in the card file if a developer leaves the function's parentheses empty and tries to use `title` directly:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ~ArticleCard()~ { // **WRONG:** empty parentheses do not receive the props object!
  return (
    <article className="card">
      <h3>{~title~}</h3> {/* **WRONG:** JavaScript looks for a variable named title and crashes! */}
    </article>
  );
}
```

When you save the file, the page goes blank and Chrome's Console panel logs a red error:

```devconsole
x Uncaught ReferenceError: title is not defined
```

React still passed the `props` object into the card function. However, because the function's parentheses are empty, our code never gave that object a parameter name. When JavaScript reaches `{title}`, no variable named `title` exists in the file, so execution stops right there.

### Mistake 2: Mismatching the attribute name in the parent and the property name in the child

Now suppose the developer adds `props` inside the parentheses of the card function, **but spells the attribute name differently across the two files**.

First, in the list file, the developer writes one attribute name for the story's heading:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList() {
  return (
    <section>
      <ArticleCard
        ~headline="New Park Opens Today"~ // **WRONG:** parent names the attribute "headline"
        summary="The park on Main Street opens at noon."
      />
    </section>
  );
}
```

Second, in the card file, the developer looks up a different property name on `props`:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard(props) {

    <article className="card">
      <h3>{~props.title~}</h3> {/* **WRONG:** props has .headline, so props.title is undefined! */}
      <p>{props.summary}</p>
    </article>
  );
}
```

When you **pass one attribute name in the parent and read a different property name in the child**, the heading vanishes with **zero Console errors**! Look at why this bug is completely silent:
1. The list file put the heading text inside `props.headline`.
2. In plain JavaScript, reading a property that does not exist on an object, such as `props.title`, does not throw an error. It quietly returns `undefined`.
3. When React receives `undefined` inside a heading tag, it renders an empty `<h3></h3>` element in the DOM and logs nothing in the Console.

## 2. Principle 2: Unpack the Single `props` Object with Curly Braces in the Parameter List

### React passes one object as the first argument, not separate positional arguments

In Principle 1, we wrote `props.title` and `props.summary` inside our card component. When a card uses five or six props, repeating `props.` in front of every name gets noisy. So in real React codebases, developers unpack the prop names right inside the function's parameter list.

- **In daily coding**: In plain JavaScript, a function that takes two inputs lists two names inside its parentheses. If you write `title` and `summary` inside a React component's parentheses without curly braces, the entire page crashes with an invalid-child error!
- **In an interview**: State the reason clearly: React **never** passes props as separate first, second, and third arguments. React **always** passes all props inside **one single object** as the first argument. Wrapping the parameter names in curly braces uses JavaScript **object destructuring** to unpack those properties from that single first argument.

### Plain JavaScript: Positional parameters vs. object destructuring in parameters

Before we touch our React component, look at two different ways a plain JavaScript function can receive data:

```js title="Plain JavaScript"
function showTwoArgs(~title, summary~) { // 1. No curly braces: 1st arg is title, 2nd arg is summary
  console.log(title);
}
showTwoArgs('New Park Opens Today', 'The park on Main Street opens at noon.');

function showOneObject(~{ title, summary }~) { // 2. Curly braces: unpacks .title and .summary from the 1st argument object
  console.log(title);
}
showOneObject({ title: 'New Park Opens Today', summary: 'The park on Main Street opens at noon.' });
```

Look at the difference between those two functions:
- `showTwoArgs` receives **two separate strings**, one in the first slot and one in the second slot.
- `showOneObject` receives **one object** in the first slot. Writing **curly braces** around the parameter names uses **object destructuring** to pull `title` and `summary` out of that object into two local variables.

```tree caption="Two ways to write function parameters in JavaScript: positional arguments vs. unpacking one object with curly braces."
How a function parameter list reads the first argument
- !Without curly braces [`title, summary`] | ~Do **NOT** use for React props | Expects **two separate arguments** | Puts the **entire `props` object** into `title` and sets `summary` to `undefined`
- +With curly braces [`{ title, summary }`] | +**DO** use for React component props | Unpacks properties from **the single first argument object** | Sets `title` and `summary` to their **string values**
```

### What happens when you forget the curly braces around prop names

React always calls our component the second way, passing **one `props` object** as the first argument.

Now look at what happens in our card file if a developer writes the two prop names inside the parentheses **without curly braces**:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard(~title, summary~) { // **WRONG:** missing { } puts the whole props object into title!
  return (
    <article className="card">
      <h3>{~title~}</h3> {/* **WRONG:** tries to render the whole props object inside <h3> and crashes! */}
      <p>{summary}</p>
    </article>
  );
}
```

When you **leave out the curly braces around destructured prop names**, the page goes completely blank and Chrome's Console panel logs a red crash:

```devconsole
x Uncaught Error: Objects are not valid as a React child
```

Walk through what happened inside that call step by step:
1. React called the card function with **one object** as the first argument, holding `title` and `summary`.
2. Because there were no curly braces in the parameter list, JavaScript put that **entire first argument object** into the first parameter, `title`. Since React passed no second argument, `summary` became `undefined`.
3. Inside the heading tag, `{title}` handed that whole plain JavaScript object to React to put on the screen.
4. React can render strings and numbers as text inside JSX, **but it cannot render a plain object**. So it stopped the page and threw the invalid-child error shown above.

### Wrapping the parameter names in curly braces unpacks the strings

Now wrap those two prop names in curly braces inside the function's parentheses:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard(~{ title, summary }~) { // 1. Curly braces unpack .title and .summary from React's props object
  return (
    <article className="card">
      <h3>{~title~}</h3> {/* 2. Now title is the string "New Park Opens Today" */}
      <p>{~summary~}</p> {/* 3. And summary is the string "The park on Main Street opens at noon." */}
    </article>
  );
}
```

Look closely at our card file now. The word `props` is completely gone! Yet React still passes that exact same `props` object as the first argument. Why does JavaScript know where `title` and `summary` come from?

Because the curly braces around the parameter names tell JavaScript to do two simple steps before the function body runs:
1. Take the single `props` object that React passed as the first argument.
2. Unpack its `title` and `summary` properties into two local variables with those exact names.

### Interview nuance: Does every attribute on a JSX tag go into `props`?

An interviewer will often ask a follow-up question here: *"Does every single attribute you write on a component tag become a property inside the `props` object?"*

Almost every attribute does, with one famous exception: **`key`**. React reserves the name `key` for its own internal list tracking. When a parent writes `key="park-1"` on a card tag, React reads that attribute itself and **strips it off before creating the `props` object**. If the child component tries to read `props.key`, it gets `undefined` and React logs a red error in the Console:

```devconsole
x ArticleCard: `key` is not a prop. Trying to access it will result in `undefined` being returned.
```

If a child component actually needs an article's ID for its own markup, pass it under a different prop name such as `id="park-1"`.

> [!PRINCIPLE]
> **Principle 2: Parameter Destructuring: Unpack the Single `props` Object with Curly Braces**
>
> *Always wrap destructured prop names in curly braces inside the component's parameter list.*
>
> React never passes props as separate first and second arguments. It always packs every prop into one object and passes that single object as the first argument. If you write two parameter names without curly braces, JavaScript puts the entire `props` object into your first parameter! When you render that first parameter inside a heading tag, you hand a whole JavaScript object to React. React cannot print a plain object on the screen, so it crashes. Putting curly braces inside the parentheses unpacks each named property out of React's object cleanly.
>
> **DO THIS:**
> ```jsx
> export default function ArticleCard(~{ title, summary }~) { // Curly braces unpack .title and .summary from the 1st argument object

>     <article className="card">

>     </article>
>   );
> }

## 3. Principle 3: Use Quotes for Strings and Curly Braces for Numbers, Booleans, and Objects

### Quotes on a JSX attribute always pass a string, whereas curly braces pass any JavaScript value

So far, both of our props, `title` and `summary`, have been text strings. Now we want to pass two new things down our component tree:
1. A reading time in minutes, `readTime`, so each card can add `2` minutes of discussion time and display the total.
2. The shared section name, `category`, from our top-level `App` component down to both the site header and the article list.

- **In daily coding**: In plain HTML, every attribute value is written in quotes, such as `width="100"`. If you follow that HTML habit in JSX and write `readTime="3"` in quotes, you pass the **text string `'3'`**, not a number! When the card adds two minutes to `readTime`, JavaScript glues the text together into **`'32'`** with zero Console errors.
- **In an interview**: State both rules clearly:
  1. **Quotes vs. curly braces on attributes**: Quotation marks around an attribute value always pass a string literal. Curly braces like `readTime={3}` open a JavaScript expression so you can pass numbers, booleans, arrays, objects, or variables with their true JavaScript types intact. Passing an inline object uses **double curly braces** `{{ ... }}`: the outer braces open a JSX expression, and the inner braces create the JavaScript object literal.
  2. **One-way data flow from a common parent**: Sibling components like our site header and article list cannot pass data sideways to each other. Instead, their common parent `App` owns the shared value and passes it down to both siblings through props.

```tree caption="How JSX attribute syntax decides the JavaScript data type of a prop."
What you write after `=` on a JSX attribute
- +Quotation marks [`title="New Park Opens Today"` `readTime="3"`] | Always passes a **JavaScript string** | `readTime="3"` arrives as `'3'`, so `readTime + 2` becomes **`'32'`**
- +Curly braces [`readTime={3}` `isFeatured={true}` `category={category}`] | Evaluates a **JavaScript expression** and keeps its true type | `readTime={3}` arrives as the number `3`, so `readTime + 2` becomes **`5`**
- +Double curly braces [`author={{ name: 'Maya Lin', role: 'Editor' }}`] | An **object literal `{ ... }`** inside JSX curly braces `{ ... }` | Passes a plain JavaScript object as a prop
```

### What happens when you pass a number inside quotation marks

Suppose we want each card to display the total time needed to read the story and discuss it, which is `readTime + 2` minutes.

First, in the list file, a developer adds the reading time to each card tag and wraps the numbers in quotation marks:

```jsx title="src/components/ArticleList.jsx" startLine="1"

      />
      <ArticleCard
        title="Library Extends Hours"
        summary="The downtown branch now stays open until 9 PM."
        ~readTime="5"~ // **WRONG:** quotes pass the string "5" instead of the number 5!
      />
    </section>
```

Second, in the card file, the component unpacks the reading time and adds two minutes to it inside the bottom paragraph:

When you **wrap a numeric prop in quotation marks and add a number to it**, the page renders with zero Console warnings. Look at the cards on the page, however, and they say **`32 min total`** and **`52 min total`**!

Why did `3 + 2` turn into `32`? In JavaScript, the `+` sign does two different jobs:
- When both sides are numbers, `3 + 2` adds them and gives `5`.
- When either side is a string, `'3' + 2` glues the two pieces of text together and gives `'32'`. Because the list file put quotes around `"3"`, `readTime` arrived as a string.

## 4. Principle 4: Treat Props as Read-Only and Compute Derived Values in Local Variables

### The parent owns the data, and the child receives a read-only snapshot

When `props` arrives inside a child component, it is a regular JavaScript parameter. In plain JavaScript, nothing stops a function from overwriting its own parameter. In React, however, **a component must never change its own props**.

- **In daily coding**: Suppose a developer wants the card to add two minutes of discussion time before returning its markup. If the developer overwrites `props.readTime` directly inside the card function, the page crashes immediately with a read-only `TypeError`!
- **In an interview**: Explain **both reasons** why props are **read-only**, also called **immutable**:
  1. **Direct assignment on `props` crashes immediately**: React locks the `props` object in development mode with `Object.freeze`. Overwriting any property on it immediately throws a `TypeError`.
  2. **Mutating a nested object prop corrupts shared data**: React only freezes the outer `props` object, not objects nested inside it. If a child changes a property on a passed object, it silently overwrites the parent's object in memory. Every other card using that object then renders corrupted text!

Whenever a child needs a modified or calculated value, it stores the result in a new local `const` variable inside the function body:

```tree caption="What a child component must never do with its props vs. how it computes a modified value safely."
When a child component needs to format or calculate a value from a prop
- !Do NOT mutate `props` or an object inside `props` [`props.readTime = ...` `article.title = ...`] | `props.readTime = ...` throws a **`TypeError`** | `article.title = ...` **corrupts the parent's object** across renders
- +DO compute a new local `const` variable inside the child [`const totalTime = readTime + 2`] | +Leaves the parent's `props` **completely untouched** | Safe to run as many times as React renders the component
```

### What happens when a child component tries to overwrite a property on `props`

Look at what happens if our card component receives `props` and tries to add two minutes by overwriting the reading-time property on `props` directly:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard(props) {
  ~props.readTime = props.readTime + 2;~ // **WRONG:** mutating a property on the frozen props object throws a TypeError!
  return (
    <article className="card">
      <h3>{props.title}</h3>
      <p>{props.summary}</p>
      <p>{props.readTime} min total</p>
    </article>
  );
}
```

When you save the file, the entire page goes blank and Chrome's Console panel logs a red `TypeError`:

```devconsole
x Uncaught TypeError: Cannot assign to read only property 'readTime' of object '#<Object>'
```

Look at that `TypeError` in the Console. Nowhere in our list file or our card file did we lock the `props` object! Who locked it?

Before React calls the card component in development mode, it locks the `props` object in memory using JavaScript's built-in `Object.freeze`. Every `.jsx` module file runs in JavaScript strict mode. In strict mode, any line that tries to overwrite a property on that frozen `props` object throws a `TypeError` and stops the render.

### Why mutating an object passed inside a prop is even more dangerous

What if the parent passes a **nested object** inside a prop? `Object.freeze` only freezes the outer `props` wrapper, not an object sitting inside it.

First, in our list file, suppose the parent stores a featured story inside an object and passes that same object to two card tags:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList() {
  const ~featuredArticle~ = { title: 'New Park Opens Today', readTime: 3 }; // 1. One shared story object in memory
  return (
    <section>
      <ArticleCard ~article={featuredArticle}~ /> {/* 2. Passes the shared object to the 1st card */}
      <ArticleCard ~article={featuredArticle}~ /> {/* 3. Passes the exact same object to the 2nd card */}
    </section>
  );
}
```

Second, in our card file, look at what happens if the card component modifies the title property on that object directly during render:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ article }) {
  ~article.title = 'BREAKING: ' + article.title;~ // **WRONG:** mutates the parent's shared object in memory!
  return (
    <article className="card">
      <h3>{article.title}</h3>
    </article>
  );
}
```

Because both card tags point to the **exact same `featuredArticle` object in memory**, watch what happens in order:
1. When React renders the **first card**, the card glues `'BREAKING: '` onto the front of `featuredArticle.title` in memory and displays the updated heading.
2. When React renders the **second card** right below it, `featuredArticle.title` already starts with `'BREAKING: '`! The second card glues a **second** `'BREAKING: '` onto that same object in memory, so the heading starts with `BREAKING: BREAKING:` on the screen:

```tree dir=right caption="How mutating an object prop inside a child component corrupts the parent's shared object across renders."
Parent passes `featuredArticle` to two `<ArticleCard article={featuredArticle} />` tags
- !1st `ArticleCard` mutates `article.title` | Overwrites `featuredArticle.title` in memory to `'BREAKING: New Park Opens Today'`
- !2nd `ArticleCard` mutates `article.title` again | Reads the already-mutated object and renders **`'BREAKING: BREAKING: New Park Opens Today'`**!
```

### Computing derived values safely in local `const` variables

Whenever a component needs to add to a number or format a string from its props, store the result in a new local `const` variable. React calls this a **derived value**.

In our card file, we calculate `totalTime` in a local constant and render the card with its two status badges:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleCard({ title, summary, readTime }) {
  ~const totalTime = readTime + 2;~ // 1. Computes a derived value in a new local const without touching props

  return (
    <article className="card">
      <LiveBadge />
      <NewBadge />
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{~totalTime~} min total · {readTime} min read</p> {/* 2. Renders the derived local constant */}
    </article>
  );
}
```

Storing the sum in `totalTime` leaves the incoming `props` object completely untouched. Both cards render cleanly. No matter how many times React re-renders the component, `totalTime` is always calculated fresh from the original `readTime` prop:

> [!PRINCIPLE]
> **Principle 4: The Read-Only Contract: Never Mutate Props; Compute Derived Local Variables Instead**
>
> *Treat `props` and every object inside `props` as read-only inputs during render. When you need a formatted or calculated value, store it in a new local `const` variable.*
>
> A component does not own its props. The parent component owns that data and hands the child a read-only snapshot for the current render. If you try to overwrite `props.readTime` directly, React stops the page with a `TypeError` because the props object is frozen. And if you mutate an object inside a prop, you silently corrupt the parent's data in memory so the next render gets garbled values! Always calculate what you need in a new local `const` variable inside your function.
>
> **DO THIS:**
> ```jsx
> export default function ArticleCard({ title, readTime }) {
>   ~const totalTime = readTime + 2;~ // Safe: computes a new local constant without touching props
>   return <article><h3>{title}</h3><p>{totalTime} min total</p></article>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function ArticleCard(props) {
>   ~props.readTime = props.readTime + 2;~ // **WRONG:** crashes with TypeError because props is read-only!
>   return <article><h3>{props.title}</h3><p>{props.readTime} min total</p></article>;
> }
> ```

## For the Interview

> **The Interview Question:** How do you pass data into a component, and why can a component never change its own props?

### How to Answer Clearly in 30 Seconds

"A parent component passes data to a child component by writing attributes on the child's JSX tag. The build packs those attributes into one plain JavaScript object, and React passes that single `props` object as the first argument to the child function. Inside the child, we unpack the properties we need with curly braces in the parameter list, such as `{ title, readTime }`. String literals use quotes, while numbers, booleans, arrays, and objects use curly braces so they keep their JavaScript types.

A component can never change its own props because React uses one-way data flow. The parent owns the data, and `props` is a read-only snapshot for the current render. In development mode, React freezes the `props` object, so assigning to a prop throws a `TypeError`. Mutating a nested object inside `props` is also forbidden because it silently corrupts the parent's shared data in memory across renders. When a child needs a formatted or calculated value, it computes a new local `const` variable. When the page needs to change after a user action, the parent updates its state and passes fresh props down on the next render."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What happens if you write `title, readTime` in the component's parameter list without curly braces?"**
   React always passes **one single `props` object** as the first argument to a component function, never separate positional arguments. Without curly braces, JavaScript assigns the entire `props` object to the first parameter `title`, and sets `readTime` to `undefined`. When the component tries to render `<h3>{title}</h3>`, React throws `Uncaught Error: Objects are not valid as a React child`. Adding curly braces `{ title, readTime }` unpacks the properties from that first argument object.

2. **"Does every attribute you write on a JSX component tag end up inside the `props` object?"**
   **No.** `key` is reserved by React itself so React can track which item is which across renders. React strips `key` before creating the `props` object. If a child tries to read `props.key`, it gets `undefined` and React logs a Console error saying that `key` is not a prop. If the child component needs that identifier, pass it as a separate prop such as `id={article.id}`.

3. **"If React freezes the `props` object, what happens if a child mutates an object inside a prop, such as `article.title = 'BREAKING: ' + article.title`?"**
   React only **shallow-freezes** the top-level `props` object with `Object.freeze`, not nested objects inside it. So `article.title = ...` does not throw a `TypeError`. Instead, it silently mutates the parent's object in memory! When another card renders that same `article` object, or when React re-renders the component, the already-mutated title gets modified a second time. That produces doubled text like `BREAKING: BREAKING: New Park Opens Today`. Always keep rendering pure by computing derived values in local `const` variables.

```tree dir=right caption="Interview comparison: mutating props or prop objects inside a child vs. computing derived local constants."
How a child component handles incoming `props`
- !Mutate `props` or nested prop objects [`props.readTime = ...` `article.title = ...`] | Top-level assignment throws **`TypeError` on frozen `props`** | Nested object mutation **corrupts parent data** across renders
- +Read `props` and derive local constants [`const totalTime = readTime + 2`] | Keeps the component **pure and predictable** | Parent's data stays **untouched** on every render
```
