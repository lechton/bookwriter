## What Conditional Rendering Is and Why We Need It

### Four ways to decide what a component shows on screen

Before we build our news feed, look at all four ways a React component decides what to show on the screen inside one tiny function:

```jsx title="Four ways to decide what a component shows on screen"
function MyComponent({ isVisible, isMember, isLive, count }) {
  ~if (!isVisible) { return null; }~ // 1. Early return: hides the whole component

  return (
    <div>
      ~{isMember ? <p>Welcome back!</p> : <p>Please sign in.</p>}~ {/* 2. Ternary ? : switches between two elements */}
      ~{isLive && <span>Live</span>}~ {/* 3. Boolean &&: shows one element when true */}
      ~{count > 0 && <p>{count} messages</p>}~ {/* 4. Number > 0 &&: compares first so 0 never prints */}
    </div>
  );
}
```

**React does not invent special HTML attributes for conditions! You use plain JavaScript right inside your component function. An `if` check at the top hides the whole component, the ternary operator switches between two elements, and `&&` includes one element when a condition is true.**

Look at the three words that unlock every rule in this lesson:
- **What does "conditional rendering" mean?** It simply means returning different markup depending on a condition, instead of creating every DOM node ahead of time and hiding elements with CSS.
- **What does "ternary" mean?** Just like **primary** means one and **secondary** means two, **ternary** means **three parts**: the condition before `?`, the true branch, and the false branch after `:`.
- **What does "short-circuit" with `&&` mean?** It works like an electrical switch that stops the current early. When the left side of `&&` is falsy, JavaScript stops right there and hands that left-hand value back without running the right side!

### What conditional rendering means in React

Look at any real city news page. Every story card shares the same outer box, yet different stories show different pieces inside. An unfinished draft story should not appear on the public feed at all. A subscriber-only story hides its summary and shows a sign-in notice instead. A breaking news story wears a `Live` badge at the top, while a regular story leaves that badge off. And a story with four reader comments shows a comment count at the bottom, while a story with zero comments hides that line.

In plain JavaScript without React, you would put every possible badge, notice, and counter into the HTML ahead of time. Then you would hunt through the page and toggle CSS classes to hide the pieces you do not want.

In React, you never hide and show DOM nodes by hand. Instead, your component checks its props and returns only the markup that belongs on the screen. Returning different markup depending on a condition is called **conditional rendering**.

```tree caption="Two ways to show or hide parts of a card: hiding DOM nodes by hand in plain JavaScript vs. conditional rendering in React."
How to show or hide parts of a news card
- !Hide DOM nodes by hand in plain JavaScript | Put every badge, notice, and counter into the HTML ahead of time | Hunt for DOM nodes and toggle hidden styles by hand
- +Conditional rendering in React | +**DO** let the component check its props and return only the markup that belongs on screen | Unwanted pieces are **never created** in the browser DOM
```

### Three ways to write conditions in React: `if`, `? :`, and `&&`

React does not invent special HTML attributes for conditions. Because a React component is a JavaScript function, you choose what markup to return with three standard tools from plain JavaScript:
- **An `if` statement before `return`** decides whether the whole component returns its markup or stops early and returns `null` so nothing appears on the page.
- **The ternary operator** sits inside JSX curly braces and switches between two pieces of markup in one spot, using `?` for the first branch and `:` for the second.
- **The logical AND operator `&&`** sits inside JSX curly braces and includes one piece of markup only when a boolean condition is `true`.

First, an `if` statement at the top of our card function can stop an unpublished draft before any markup is returned:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, isPublished = true }) {
  ~if (!isPublished) { return null; }~ // 1. Outside JSX: stops early and returns null when unpublished

  return (
    <article className="card">
      <h3>{title}</h3>
      <p>{summary}</p>
    </article>
  );
}
```

Second, inside JSX curly braces `{ }`, we use `&&` to include a badge and the ternary operator to switch between two paragraphs:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import { LiveBadge } from './Badges.jsx';

export default function ArticleCard({ title, summary, isSubscriberOnly = false, isBreaking = false }) {
  return (
    <article className="card">
      ~{isBreaking && <LiveBadge />}~ {/* 2. Inside JSX {}: shows LiveBadge only when isBreaking is true */}
      <h3>{title}</h3>
      {isSubscriberOnly
        ~? <p>Subscribers only: Sign in to read this story.</p>~ // 3. Inside JSX {}: shown when true
        ~: <p>{summary}</p>~} {/* 4. Inside JSX {}: shown when false */}
    </article>
  );
}
```

Here is how those three JavaScript tools divide the work inside a component:

```tree dir=right caption="The three plain JavaScript tools for conditional rendering and where each one lives in a component."
Three JavaScript tools for conditional rendering
- +1. `if` statement and `return null` [Outside JSX, before `return`] | Guards the whole component or prepares a `let` variable before returning
- +2. Ternary operator `? :` [Inside JSX `{ }` curly braces] | Switches between **two** pieces of markup in one spot
- +3. Logical AND operator `&&` [Inside JSX `{ }` curly braces] | Includes **one** piece of markup when a boolean condition is `true`
```

### Why `if` stays outside curly braces while `? :` and `&&` go inside

Recall from earlier lessons that curly braces `{ }` inside JSX open a window for JavaScript. However, you cannot put every kind of JavaScript inside `{ }`. JavaScript divides its code into two groups:
- **A statement** performs an action, such as an `if` block or a `let` variable declaration. A statement does not produce a value, so it can only live **outside** JSX, above `return`.
- **An expression** produces a single value, such as a ternary switch or an `&&` check. Because JSX curly braces `{ }` must hand a value to React, only expressions can sit **inside** `{ }`.

When an expression inside `{ }` finishes running, it hands its resulting value to React. React divides those values into two groups when building the browser DOM:
- **Values that render visible text**: React turns **strings** and **numbers**, including the number `0`, into visible text nodes on the page.
- **Values that render nothing at all**: React treats `null`, `undefined`, booleans, and an empty string as empty holes in the markup. It creates **zero DOM nodes** for them.

```tree caption="What React puts into the browser DOM for each kind of JavaScript value returned or placed inside JSX curly braces."
JavaScript values handed to React in JSX
- +Visible text values [Strings `"Live"` and numbers `4` or `0`] | !Numbers include **`0`** | React creates a **visible text node** in the browser DOM
- +Empty hole values [`null` `undefined` `false` `true` `""`] | Treated as **intentional empty spots** | React creates **0 DOM nodes** in the browser DOM
```

### Four Principles of Conditional Rendering

**PRINCIPLES:** Every conditional rendering bug comes from mixing up where statements and expressions belong, or forgetting what value JavaScript actually hands to React. Walking from the top of our card component down into its markup gives us four rules:
1. **Principle 1: Returning Early with `if` and `return null`**: An `if` statement at the top of a component can stop the function early when nothing should appear on screen. Returning `null` tells React to create zero DOM nodes, while forgetting that check lets an unpublished draft card leak onto the public page.
2. **Principle 2: Switching Between Two Branches with the Ternary Operator**: JSX curly braces only accept expressions that produce a value. Writing an `if` statement inside `{ }` stops the build with a syntax error. Instead, use the ternary operator inside curly braces, or set a `let` variable above `return` when the branches grow long.
3. **Principle 3: Showing One Element with `&&` and a Real Boolean**: Inside curly braces, the `&&` operator shows a badge when its condition is true and returns `false` when the condition is false. React renders nothing for the boolean `false`. However, passing `"false"` in quotation marks sends a non-empty text string that is truthy in JavaScript, so the badge appears anyway!
4. **Principle 4: Avoiding the Zero Trap on the Left Side of `&&`**: Never put a raw number directly on the left side of `&&`. When a comment count is zero, the `&&` operator returns the number `0` itself, and React prints a stray zero on the page! Always compare the number with `> 0` so the left side evaluates to a real boolean.

Here is the complete overview of all four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Early Return: Use `if` Before `return` and `return null` to Hide a Component** | **Draft Leak & DOM Interview Question:** Forgetting an early `if` guard renders unpublished cards on screen, and interviewers ask what `return null` puts into the browser DOM. | Check `if` conditions before the component's `return` statement, and `return null` when the component should create zero DOM nodes. |
| **Principle 2** | **Ternary `? :`: Switch Between Two JSX Branches Inside `{ }`** | **Build Crash & Readability Question:** Writing an `if` statement inside JSX curly braces crashes the build, and interviewers ask why `{ }` rejects `if` and when to use a `let` variable instead. | Use the ternary operator inside JSX curly braces for two-way switching, or assign JSX to a `let` variable in an `if` block before `return`. |
| **Principle 3** | **Logical `&&`: Include One JSX Element with a Boolean Condition** | **Quoted String Bug & Falsy Evaluation:** Passing `"false"` in quotes makes `&&` render the badge because `"false"` is a truthy string, and interviewers ask why `false` with `&&` leaves the DOM empty. | Use `&&` inside curly braces with a real boolean prop so `false` short-circuits to `false` and renders zero DOM nodes. |
| **Principle 4** | **The Zero Trap: Write `count > 0 && ...` Instead of `count && ...`** | **#1 React Conditional Rendering Trap:** Putting a raw number directly before `&&` prints a stray `"0"` in the DOM when the count is `0` with zero Console warnings. | Compare numbers explicitly with `> 0` before `&&` so a zero count evaluates to `false` instead of the number `0`. |

## 1. Principle 1: Use an Early `if` Statement and `return null` to Hide a Component

### Returning `null` from a component vs. hiding HTML with CSS

When a card should not appear on the page at all, you do not put the card into the DOM and hide it with CSS. Remember that a React component is a normal JavaScript function. An `if` statement at the top of the function can run `return null` and stop before reaching the JSX markup. React then creates **zero DOM nodes** for that component.

```tree caption="Keeping a hidden card in the DOM vs. returning null early from the component function."
How to hide an unpublished card in React
- !Keep the `<article>` node in the DOM and hide it with CSS | The unpublished draft text **still sits inside the browser's Elements panel**
- +Check `if` at the top of the component and `return null` | +**DO** stop the function before the JSX `return` | React puts **0 DOM nodes** for the draft card into the browser DOM
```

### What happens when a component forgets to check whether it should render

On our city news page, the article list has two finished stories and a third story that is still an unpublished draft. First, in our list file, we mark that third card as unpublished:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList({ category }) {
  return (
    <section>
      <h2>Section: {category}</h2>
      <ArticleCard
        title="New Park Opens Today"
        summary="The park on Main Street opens at noon."
        readTime={5}
      />
      <ArticleCard
        title="Library Extends Hours"
        summary="The central library stays open until nine."
      />
      <ArticleCard
        title="Mayor Budget Draft"
        summary="Unfinished notes for next week."
        ~isPublished={false}~ // Marks the 3rd card as an unpublished draft
      />
    </section>
  );
}
```

Now look at what happens when our card file unpacks the story props and returns the card markup right away, without checking whether the story is published:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ~ArticleCard~({ title, summary, readTime = 3 }) { // **WRONG:** never checks isPublished before returning the card!
  const totalTime = readTime + 2;

  return (
    <article className="card">
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

When you **leave out the `if` check at the top of the card**, the unfinished budget draft appears on the public page with zero Console warnings!

Look at what happened in order:
1. The list file rendered three card tags and passed `isPublished={false}` on the third tag.
2. React called `ArticleCard` once for each of the three tags.
3. Because the third call never checked whether the story was published, it ran the final `return` statement and handed the draft card's markup to React.

### Stopping early with `if` and `return null`

To keep unpublished drafts off the page, we make two small additions at the top of our card file. First, we give the published prop a default value of `true` so normal stories stay visible when a card tag leaves that prop out. Second, right before the main `return`, we check whether the story is unpublished and return `null`:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime = 3, ~isPublished = true~ }) { // 1. Defaults to true when omitted
  ~if (!isPublished) {~ // 2. Stops early and returns null when isPublished is false
    return null;
  }

  const totalTime = readTime + 2;

  return (
    <article className="card">
      <h3>{title}</h3>
      <p>{summary}</p>
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

Save the file, and look at the browser's **Elements panel** below. Our list file still renders three card tags inside `<section>`. Yet in the Elements panel, `<section>` holds only **two** `<article>` cards. There is no third card, no empty wrapper, and no placeholder comment where the draft stood!

Why did the third card leave zero trace in the DOM? Follow what JavaScript and React do across the three calls:
1. **On the first and second cards**: The list file leaves out `isPublished`, so its default value `true` takes over. The `if` block is skipped, and the function returns the card markup.
2. **On the third card**: The list file passes `isPublished={false}`. Now the `if` condition is true, so the function runs `return null` right away and stops before the markup below it ever runs.
3. **When React builds the DOM**: React receives `null` from that third call. React treats `null` as an intentional empty spot and puts **zero DOM nodes** into `<section>`.

In an interview, you may also be asked two follow-up questions about early returns:
- **Where should the condition live?** Putting an early `if` guard at the top of `ArticleCard` guarantees that the card never renders an unpublished draft by mistake. In other cases, developers check the condition inside the parent list before rendering the card tag. That way, anyone reading the parent file can see at a glance that the card is conditional.
- **Does returning early create a different kind of React element than branching inline?** No. Remember that JSX tags compile to lightweight plain objects that describe what should appear on screen. Whether a component returns early from an `if` statement or branches inline at the bottom, React receives the exact same element description.

## 2. Principle 2: Use the Ternary Operator `? :` to Switch Between Two Elements

### Why you cannot put an `if` statement inside JSX curly braces

In Principle 1, we hid the entire card by putting an `if` statement above `return`. Now what if we want to keep the card's outer box, heading, and reading-time line, and swap **only the middle paragraph**?

Beginners know that curly braces `{ }` run JavaScript inside JSX, so they often try to write an `if` block right inside the braces. However, JSX curly braces sit inside a JavaScript function call where a **value expression** is required, and an `if` block is a statement rather than a value. To switch between two pieces of markup inside curly braces, use the **ternary operator**. When the branches get long, assign the markup to a `let` variable before `return`.

### How the ternary operator `? :` works in plain JavaScript

In plain JavaScript, an `if` statement controls which block of lines runs. The **ternary operator** is a compact expression that evaluates directly to a single value. It has three parts:
1. **Before the question mark `?`**: the condition to test.
2. **Between `?` and the colon `:`**: the value returned when the condition is `true`.
3. **After the colon `:`**: the value returned when the condition is `false`.

Look at how the ternary operator produces a value directly inside a variable assignment, where an `if` statement cannot sit:

```js title="Plain JavaScript"
const isSubscriberOnly = true;

const message = ~isSubscriberOnly ? 'Subscribers only' : 'Open story'~; // Expression: evaluates to 'Subscribers only'
console.log(message);
```

Compare where an `if` statement and the ternary operator can live inside a React component:

```tree caption="Why an if / else statement must stay outside JSX curly braces while a ? : ternary expression fits inside { }."
Two ways to branch in JavaScript
- !`if / else` statement [Outside JSX, before `return`] | ~Do **NOT** put `if / else` inside JSX `{ }` | Performs an action rather than evaluating to a value | Writing `{if ...}` inside JSX **crashes the build**
- +Ternary operator `condition ? a : b` [Inside JSX `{ }` curly braces] | +**DO** use `? :` inside `{ }` to switch between two JSX branches | Evaluates to **one winning value** and hands it to React
```

### What happens when you write `if` inside JSX curly braces

On our city news page, the library story is for subscribers only. First, in our list file, we mark that second card as subscriber-only:

```jsx title="src/components/ArticleList.jsx" startLine="12"
      <ArticleCard
        title="Library Extends Hours"
        summary="The central library stays open until nine."
        ~isSubscriberOnly={true}~ // Marks the 2nd story as subscriber-only
      />
```

Now look at what happens when a developer opens curly braces `{ }` inside the card markup and writes an `if` statement inside them:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime = 3, isPublished = true, isSubscriberOnly = false }) {
  if (!isPublished) {
    return null;
  }
  const totalTime = readTime + 2;

  return (
    <article className="card">
      <h3>{title}</h3>
      ~{if (isSubscriberOnly) { <p>Subscribers only: Sign in to read this story.</p> } else { <p>{summary}</p> }}~ {/* **WRONG:** if statement inside JSX {} stops the build! */}
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

When you **write an `if` statement inside JSX curly braces**, Vite immediately stops the build and covers the browser with its error overlay:

```overlay caption="Vite's error overlay when an if statement is placed inside JSX curly braces in ArticleCard.jsx."

file: src/components/ArticleCard.jsx:10:7

```

Why did the build stop at `{if` on line 10? Remember that the build rewrites each JSX tag and its inner content into a `_jsxDEV` function call whose `children` sit inside an array. Every slot inside that array must be a JavaScript expression that produces a value. When the parser sees the statement keyword `if` inside an expression slot, it halts with `Unexpected token`.

### Switching between two elements with `? :` inside curly braces

Now let us replace that `if` block inside curly braces with the ternary operator. We keep the card wrapper, the heading, and the reading-time line in one place, and switch only the middle paragraph:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime = 3, isPublished = true, ~isSubscriberOnly = false~ }) { // 1. Defaults to false for open stories
  if (!isPublished) {
    return null;
  }
  const totalTime = readTime + 2;

  return (
    <article className="card">
      <h3>{title}</h3>
      {isSubscriberOnly
        ~? <p>Subscribers only: Sign in to read this story.</p>~ // 2. Returned when isSubscriberOnly is true
        ~: <p>{summary}</p>~} {/* 3. Returned when isSubscriberOnly is false */}
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

Look closely at the curly braces in our card file above. There are **two** `<p>` tags written inside those curly braces, yet when you inspect the page in the browser, each card has only **one** middle `<p>` tag!

Follow what JavaScript hands to React for each card:
1. **On the park story**: The list file leaves out `isSubscriberOnly`, so it defaults to `false`. Because the condition before `?` is false, JavaScript hands React only the summary paragraph after the colon.
2. **On the library story**: The list file passes `isSubscriberOnly={true}`. Because the condition before `?` is true, JavaScript hands React only the subscriber notice before the colon.
3. **In the browser DOM**: Each card receives only its winning `<p>` tag, and the outer card wrapper is written only once.

### Using a `let` variable with `if` when the branches get long

The ternary operator is clean when switching between two short pieces of markup. What if each branch spans several lines, or you need `else if` for three different cases? Cramming all of that inside `{ }` makes the markup hard to read.

You still do not need to duplicate the outer card wrapper. Because JSX elements are normal JavaScript values, we can store the default paragraph in a `let` variable before `return`. Then we reassign that variable inside a normal `if` block and place the variable inside curly braces in the markup:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary, readTime = 3, isPublished = true, isSubscriberOnly = false }) {
  if (!isPublished) {
    return null;
  }
  const totalTime = readTime + 2;

  ~let bodyContent = <p>{summary}</p>;~ // 1. Start with the normal summary paragraph
  if (isSubscriberOnly) {
    ~bodyContent = <p>Subscribers only: Sign in to read this story.</p>;~ // 2. Swap in the subscriber notice when true
  }

  return (
    <article className="card">
      <h3>{title}</h3>
      ~{bodyContent}~ {/* 3. Embed the chosen JSX variable inside curly braces */}
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

That gives you the best of both worlds. The `if` statement stays above `return` where statements belong. Meanwhile, the outer card wrapper is written only once, and `{bodyContent}` keeps the markup clean.

> [!PRINCIPLE]
> **Principle 2: The Ternary Operator: Switch Between Two JSX Branches Inside `{ }`**
>
> *Use a ternary expression inside JSX curly braces to switch between two pieces of markup. When the branches grow long, set a `let` variable inside an `if` block before returning.*
>
> It is tempting to open `{ }` inside JSX and write an `if / else` block, only to watch the build stop right away! You see, JSX curly braces sit inside a JavaScript function call where a value is required, and an `if` statement does not produce a value. The ternary operator is an expression that picks the winning branch and hands that single element to React.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> <article className="card">
>   <h3>{title}</h3>
>   ~{isSubscriberOnly ? <p>Subscribers only: Sign in to read this story.</p> : <p>{summary}</p>}~ {/* Evaluates to the chosen <p> */}
> </article>
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> <article className="card">
>   <h3>{title}</h3>
>   ~{if (isSubscriberOnly) { <p>Subscribers only</p> } else { <p>{summary}</p> }}~ {/* **WRONG:** if statement inside {} crashes the build! */}
> </article>
> ```

## 3. Principle 3: Use Logical AND `&&` with a Boolean to Show or Hide One Element

### Why `isBreaking ? <LiveBadge /> : null` and `isBreaking && <LiveBadge />` do the exact same thing

In Principle 2, we had two branches: a subscriber notice or a story summary. Now what if there is **only one branch**? When a story is breaking news, we want to show a `Live` badge at the top of the card. When it is not breaking news, we want to show nothing at all in that spot.

Look at two ways to write that one-branch check inside JSX curly braces side by side:

```jsx title="A ternary with : null vs. the && shortcut"
~{isBreaking ? <LiveBadge /> : null}~ // 1. Ternary with : null when false
~{isBreaking && <LiveBadge />}~       // 2. Logical && shortcut: returns false when isBreaking is false
```

**Yes, when `isBreaking` is a real boolean, both lines do the exact same thing! You do not need to write `: null` at the end when there is no second branch.**

However, look at what happens if the parent passes `"false"` in quotation marks instead of `{false}` in curly braces:
- **Boolean in curly braces**: Passes the real boolean `false`. The `&&` operator stops at the left side and returns `false`, which React renders as **zero DOM nodes**.
- **String in quotation marks**: It may look like false, **but it is NOT the same thing!** Quotation marks pass the five-letter text string `'false'`. Because every non-empty string is truthy in JavaScript, `&&` keeps going and renders the `Live` badge anyway!

### How the `&&` operator works in plain JavaScript

In plain JavaScript, the logical AND operator `&&` reads from left to right. This behavior is called **short-circuit evaluation**:
- If the **left side is falsy**, `&&` stops right there and returns that **exact left-hand value** without looking at the right side.
- If the **left side is truthy**, `&&` keeps going and returns the **right-hand value**.

Look at what `&&` returns for a boolean, and compare that with the non-empty string `'false'`:

```js title="Plain JavaScript"
console.log(~false && 'Live'~); // Left side is falsy -> stops and returns false
console.log(~true && 'Live'~); // Left side is truthy -> returns the right side: 'Live'
console.log(~'false' && 'Live'~); // Non-empty string 'false' is TRUTHY -> returns 'Live'!
```

Look closely at the third line above. In JavaScript, only an empty string `""` is falsy. Any string with characters inside it, including the five-letter word `'false'`, is **truthy**!

```tree caption="What JavaScript's && operator returns and what React puts in the DOM for boolean false, boolean true, and quoted string 'false'."
How `isBreaking && <LiveBadge />` evaluates in JSX
- +Boolean `false` [`isBreaking={false}`] | Left side is **falsy** | `&&` returns **`false`**, and React creates **0 DOM nodes**
- +Boolean `true` [`isBreaking={true}`] | Left side is **truthy** | `&&` returns **`<LiveBadge />`**, and React renders `<span class="badge">Live</span>`
- !Quoted string `"false"` [`isBreaking="false"`] | ~Do **NOT** wrap boolean props in quotes | Non-empty string `'false'` is **truthy**, so `&&` returns **`<LiveBadge />`** and renders `Live` by mistake!
```

### Showing an element conditionally with `&&`

Let us add conditional badges to our news cards. First, remember the two badge components exported by our badge file:

```jsx title="src/components/Badges.jsx" startLine="1"
export function ~LiveBadge~() { // Shown when isBreaking is true
  return <span className="badge">Live</span>;
}

export function ~NewBadge~() { // Shown when isNew is true
  return <span className="badge">New</span>;
}
```

Next, in our card file, we import both badges and give both badge props a default value of `false`. Then we use `&&` at the top of the card markup so each badge appears only when its prop is `true`:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleCard({
  title,
  summary,
  readTime = 3,
  isPublished = true,
  isSubscriberOnly = false,
  ~isBreaking = false,~ // 1. Defaults to the boolean false
  ~isNew = false,~ // 2. Also defaults to the boolean false
}) {
  if (!isPublished) {
    return null;
  }
  const totalTime = readTime + 2;

  return (
    <article className="card">
      ~{isBreaking && <LiveBadge />}~ {/* 3. Evaluates to <LiveBadge /> when true, or false when false */}
      ~{isNew && <NewBadge />}~ {/* 4. Evaluates to <NewBadge /> when true, or false when false */}
      <h3>{title}</h3>
      {isSubscriberOnly
        ? <p>Subscribers only: Sign in to read this story.</p>
        : <p>{summary}</p>}
      <p>{totalTime} min total · {readTime} min read</p>
    </article>
  );
}
```

Pause and check what happens when `isBreaking` is `false`. Our `&&` expression evaluates to the boolean `false`. Why doesn't the word `"false"` appear at the top of the card in the browser?

Because of how React handles boolean values inside JSX:
1. When `isBreaking` is `false`, JavaScript stops at the left side and hands that boolean value to React.
2. React ignores boolean values inside JSX children, just like `null` and `undefined`, and creates **zero DOM nodes** for them.
3. When `isNew` is true, JavaScript moves to the right side of `&&` and hands the badge element to React for the DOM.

### What happens when you pass `"false"` in quotes instead of `{false}`

Now suppose the developer edits the list file. The park story is breaking news and brand-new, while the library story is brand-new **but not breaking news**. Look at what happens when the developer passes `"false"` in quotation marks on the library card:

When you **pass `"false"` in quotation marks to a prop used with `&&`**, the breaking-news badge still appears on the library story with zero Console errors!

Look at what happened in order:
1. In JSX, quotation marks always pass a **string**, so `isBreaking` arrived inside our card component as the five-letter word `'false'`.
2. Inside the card's curly braces, JavaScript checked the left side of `&&` and saw that five-letter string.
3. Because any non-empty string is truthy, `&&` returned the right-hand side, and React drew the `Live` badge on the library card.

### Passing a boolean in curly braces so `&&` hides the element

To pass the real boolean `false`, we replace the quotation marks with curly braces on the library card. We can also leave the prop off so its default value takes over:

>

>
> When you only want to show or hide a single badge, `&&` feels effortless, until someone passes `"false"` in quotation marks and the badge refuses to disappear! You see, JavaScript's `&&` stops at the left side when it is falsy and hands that value to React, and React renders nothing for the boolean `false`. ## 4. Principle 4: Compare Numbers with `> 0` Before `&&` So `0` Never Prints on Screen

### Why `commentCount && <p>...</p>` and `commentCount > 0 && <p>...</p>` are NOT the same thing when the count is `0`

In Principle 3, our condition was a boolean, so when it was `false`, `&&` returned false and React rendered nothing. What happens when the value on the left side of `&&` is a **number**, such as `commentCount`?

Look at two ways to check `commentCount` before `&&` side by side:

```jsx title="Putting a raw number before && vs. comparing > 0 first"
~{commentCount && <p>{commentCount} comments</p>}~     // 1. WRONG: when commentCount is 0, returns 0 and prints "0" on screen!
~{commentCount > 0 && <p>{commentCount} comments</p>}~ // 2. RIGHT: 0 > 0 evaluates to false, so React renders nothing!
```

**When `commentCount` is `4`, both lines render the exact same paragraph, so they seem to work the same at first. When `commentCount` is `0`, however, they are NOT the same thing!**
- **Putting a raw number before `&&`**: When the count is zero, JavaScript's `&&` operator does not convert zero into `false`. It stops at the left side and hands the number **`0`** itself to React, and React prints a stray **`0`** on the card!
- **Comparing with `> 0` before `&&`**: Turns the left side into a real boolean first. When the count is zero, the comparison evaluates to `false`, so `&&` hands false to React and nothing appears on screen.

### What `&&` returns when a number is `0` in plain JavaScript

Look at what plain JavaScript returns when we put a positive number, zero, and a `> 0` comparison on the left side of `&&`:

```js title="Plain JavaScript"
console.log(~4 && '4 comments'~); // 4 is truthy -> returns '4 comments'
console.log(~0 && '0 comments'~); // 0 is falsy -> stops at 0 and returns the number 0!
console.log(~0 > 0 && '0 comments'~); // 0 > 0 is false -> stops at false and returns false
```

Compare the second and third lines:
- On the second line, zero is falsy, so `&&` stops on the left side and gives back the number **`0`** itself, not false!
- On the third line, `0 > 0` runs first and produces the boolean **`false`**. Then `&&` stops on the left side and gives back **`false`**.

Why doesn't React ignore the number `0` the way it ignores `false`? Think of a shopping cart with zero items or a game scoreboard where a player has zero points. When a count or a score is `0`, the user **must** see `0` on the screen! If React ignored `0`, every zero price, zero score, and zero count across your app would turn blank.

Here is how React handles all six falsy values in JavaScript when one of them lands on the left side of `&&` inside JSX:

```tree caption="What JavaScript's six falsy values return on the left side of && and what React puts into the browser DOM for each one."
All six JavaScript falsy values on the left side of `&&` in JSX
- +`false`, `null`, `undefined`, and `""` [`false && <p>...</p>`] | `&&` returns `false`, `null`, `undefined`, or `""` | React creates **0 DOM nodes**
- !The number `0` [`0 && <p>...</p>`] | ~Do **NOT** put a raw number on the left of `&&` | `&&` returns the number **`0`**, and React prints **`"0"`** in the DOM with **0 Console warnings**!
- !`NaN` from a broken math calculation [`NaN && <p>...</p>`] | `&&` returns **`NaN`** | React prints **`"NaN"`** in the DOM and logs a red Console error!
```

### What happens when you put a number directly before `&&`

Let us add a comment counter at the bottom of our article cards. When a story has comments, we want to show the comment count line. When a story has `0` comments, we want that line to disappear completely.

First, in our list file, we pass four comments on the park story and zero comments on the library story:

```jsx title="src/components/ArticleList.jsx" startLine="6"

        title="New Park Opens Today"
        summary="The park on Main Street opens at noon."
        readTime={5}
        isBreaking={true}
        isNew={true}
        ~commentCount={4}~ // Park story has 4 comments
      />
      <ArticleCard
        title="Library Extends Hours"
        summary="The central library stays open until nine."
        isSubscriberOnly={true}
        isBreaking={false}
        isNew={true}
        ~commentCount={0}~ // Library story has 0 comments
      />
```

Now look at what happens when a developer puts `commentCount` directly on the left side of `&&` at the bottom of the card:

```jsx title="src/components/ArticleCard.jsx" startLine="22"
      <p>{totalTime} min total · {readTime} min read</p>
      ~{commentCount && <p>{commentCount} comments</p>}~ {/* **WRONG:** when commentCount is 0, 0 && <p>...</p> returns 0 and prints "0" on the card! */}
    </article>
```

When you **put `commentCount` directly on the left side of `&&`**, a zero count prints a stray zero on the library card with no Console warnings!

Look closely at our card code above. Nowhere in our JSX did we write a bare `0` by itself. Where did that `"0"` at the bottom of the library card come from?

Follow what JavaScript and React did step by step:
1. On the park card, `commentCount` is `4`. Because four is truthy, `&&` returns the comment paragraph on its right side, which looks fine.
2. On the library card, `commentCount` is `0`. Because zero is falsy, `&&` stops on the left side and returns the number **`0`** itself.
3. React receives the number `0` as the last child of the card and prints `"0"` right below the reading-time line.

### Comparing `commentCount > 0` before `&&` to return a boolean

To fix the bug, we compare the number with `> 0` on the left side of `&&`:

```jsx title="src/components/ArticleCard.jsx" startLine="22"

    </article>
```

Now trace the library card again when `commentCount` is `0`:
1. JavaScript evaluates `0 > 0` first, which produces the boolean **`false`**.
2. Next, `&&` sees that false value on its left side, stops right there, and hands **`false`** to React.
3. React ignores `false` and puts **zero DOM nodes** after the reading-time paragraph.

| Aspect | The Plain JavaScript or Beginner Habit | The React Rule |

## For the Interview

> **The Interview Question:** How do you show, hide, or switch JSX based on a condition?

### How to Answer Clearly in 30 Seconds

"React handles conditional rendering with standard JavaScript rather than special template attributes:
1. **Early return with `if` and `return null` outside JSX**: Before the component's `return` statement, an `if` statement can return a different JSX tree early, or `return null` when the component should render nothing at all. When a component returns `null`, React creates zero DOM nodes for it.
2. **The ternary operator `condition ? <A /> : <B />` inside `{ }`**: JSX curly braces only accept JavaScript expressions that evaluate to a value, so writing `{if ...}` inside `{ }` fails at build time with a syntax error. To switch between two pieces of JSX inline, we use `? :`. When the branches get long, we assign JSX to a `let` variable inside an `if` block before `return`.
3. **The logical AND operator `condition && <Element />` inside `{ }`**: To show one piece of JSX when a boolean condition is `true` and nothing when it is `false`, we use `&&`. When the left side is `false`, `&&` short-circuits to `false`, and React treats `false`, `null`, and `undefined` as empty holes that produce zero DOM nodes.
4. **Never put a raw number on the left side of `&&`**: If we write `{commentCount && <p>{commentCount} comments</p>}` and `commentCount` is `0`, `0 && <p>...</p>` evaluates to the number `0` rather than `false`. Because React renders numbers as visible text nodes, a literal `0` appears on the screen! Always write `{commentCount > 0 && <p>{commentCount} comments</p>}` so the left side evaluates to a boolean."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does `{commentCount && <p>{commentCount} comments</p>}` print `0` on the screen when `commentCount` is `0`, and what does React render for all six falsy values in JavaScript?"**
   JavaScript's `&&` operator does not convert its left side into a boolean; when the left side is falsy, `&&` returns that exact left-hand value. So `0 && <p>...</p>` returns the number `0`. React ignores `false`, `null`, `undefined`, and the empty string `""`, creating zero DOM nodes for those four falsy values. However, `0` is a valid number to display in UIs such as prices and scores, so React renders `0` as a text node `"0"` in the DOM. And if a broken calculation produces `NaN`, `NaN && <p>...</p>` returns `NaN`, which React renders as `"NaN"` while logging a Console error. Comparing `commentCount > 0 && ...` converts the left side into the boolean `false` so nothing renders.

2. **"Why can't you write an `if` statement directly inside JSX curly braces `{ }`, and when should you use `let` with `if` instead of `? :`?"**
   During the build, JSX tags compile into `_jsxDEV` function calls whose `children` sit inside an object property or array. A JavaScript function argument or array slot can only hold an expression that evaluates to a value, such as `a ? b : c` or `a && b`. Because `if / else` is a statement rather than a value expression, `{if ...}` stops the parser at build time with `Unexpected token`. When a condition switches between two compact pieces of markup, inline `? :` is clean. When a branch spans many lines or needs `else if`, we declare a `let` variable before `return` and reassign it in an `if` block. That keeps the shared wrapper in one place without nesting ternaries.

3. **"What happens if a parent component passes `isBreaking=\"false\"` in quotation marks to a child that renders `{isBreaking && <LiveBadge />}`?"**
   The `LiveBadge` still renders on the screen with zero Console errors! Quotation marks on a JSX attribute always create a JavaScript string literal. Inside the child component, `isBreaking` is the five-character string `'false'`, not the boolean `false`. In JavaScript, every non-empty string is truthy, so `'false' && <LiveBadge />` evaluates and returns the right-hand side, `<LiveBadge />`. Boolean props must be passed inside curly braces, such as `isBreaking={false}`.

```tree dir=right caption="Interview comparison of the four conditional rendering patterns in React."

- +Early `if` guard and `return null` [Before `return`] | Guards the whole component | Returns `null` so React creates **0 DOM nodes**

- +`isBreaking && <LiveBadge />` [Inside `{ }` curly braces] | Includes **one** JSX branch when a boolean is `true` | Short-circuits to `false` when `false`, creating **0 DOM nodes**
```
