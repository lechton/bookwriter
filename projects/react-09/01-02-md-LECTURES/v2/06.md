## Why We Picture a React App as a Tree

### A flat folder of files on disk becomes a nested tree of components on screen

In Lecture 5, we split our news page across separate files and connected them with imports and exports. Each file holds one component, or a small pair of badge components, that returns its own markup.

Look at where our project files sit inside our folders on disk:

```files title="article-site: File Explorer" caption="How our project files sit inside src/ and src/components/, and what role each file plays in the component tree."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts the top of the tree
  App.jsx | root | Top root component that renders `SiteHeader` and `ArticleList` side by side
  components/
    SiteHeader.jsx | leaf | Renders the top `<header>` banner for the whole page
    ArticleList.jsx | parent | Renders the `<section>` container and `<ArticleCard />`
    ArticleCard.jsx | parent | Renders one `<article>` card and places `<LiveBadge />` and `<NewBadge />` inside it
    Badges.jsx | leaves | Exports the `LiveBadge` and `NewBadge` leaf components that return HTML `<span>` tags
```

Inside the `components` folder, all four component files sit side by side as neighbors. Looking only at the file list, every file appears equal. Nothing in the folder list tells you which component owns the whole page, which component holds the article section, or which component renders a single badge pill.

Yet when the browser loads our page, the screen is not a flat list of separate boxes. It is a nested page where large sections wrap smaller pieces:

```page caption="What the user sees in the browser: the page header at the top, followed by the article card holding a Live badge, a New badge, a title, and a paragraph."
heading: Latest Articles
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | good
```

One root component holds the page header and the article list. Inside the article list sits the article card. Inside the article card sit the live badge, the new badge, the card title, and the card text.

When you draw these parent-and-child relationships from top to bottom, they form an upside-down tree called the **Component Render Tree**:

```tree caption="The four structural roles inside a React Component Render Tree."
Four roles inside a React Component Render Tree
- +Root component [`<App />`] | Sits at the **very top** of the tree | Passed to `root.render` and wraps the entire page layout
- +Parent and child [`<ArticleList />` renders `<ArticleCard />`] | Connected **vertically** | The outer component is the **parent** and the inner tag is its **child**
- +Sibling components [`<SiteHeader />` and `<ArticleList />`] | Sit **side by side** | Share the **same parent** component
- +Leaf components [`<LiveBadge />` `<NewBadge />`] | Sit at the **bottom tips** | Render **only browser HTML tags** and zero other React components
```

### Four Principles of Component Hierarchy and Render Trees

**PRINCIPLES:** Designing a clean React page means giving every component a clear place in the tree so layout containers, cards, and small badges never get mixed up. Walking through our news page from top to bottom gives us four practical rules:
1. **Principle 1: Root, Parent, Child, and Leaf Roles**: A component's place in the tree is decided by which component renders its JSX tag. Placing a page-wide header inside a card traps the main site header inside the card box instead of at the top of the page.
2. **Principle 2: Module Dependency Graph vs. Component Render Tree**: A single file on disk is not the same as a single component node in memory. One badge file can export two leaf components, and importing a card file **once** on disk lets you render multiple card subtrees in memory.
3. **Principle 3: Sibling Components Cannot Read Each Other's Variables**: Two sibling components sitting side by side have separate function scopes. Trying to read a sibling's variable crashes the page, and copying the variable into both files lets the two siblings drift out of sync.
4. **Principle 4: A Child Must Never Render Its Own Parent**: Component imports and JSX tags must flow strictly downward from root to leaves. If a child imports and renders its own parent, React enters an endless render loop and crashes the browser tab.

Here is the complete overview of all four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Tree Roles: Root, Parent, Child, and Leaf** | Rendering `<SiteHeader />` inside `ArticleCard` traps the main page header inside the card box instead of at the top of the page. | Place page-wide sections under `App`, list containers in the middle, cards inside lists, and HTML-only badges at the leaves. |
| **Principle 2** | **Two Maps: Module Graph on Disk vs. Render Tree in Memory** | Developers often confuse 1 file import on disk with 1 component instance on screen. | Treat the file import graph as static wiring on disk and the Render Tree as the live component instances rendered in memory. |
| **Principle 3** | **Sibling Scope: No Sideways Variable Access** | Reading a sibling's local variable throws `ReferenceError: category is not defined`, and duplicating it causes stale UI drift. | Never read variables sideways across siblings or duplicate shared data; keep shared values in a single source of truth above both siblings. |
| **Principle 4** | **Tree Direction: Strictly Top-Down Without Loops** | Rendering `<ArticleList />` inside its own child `ArticleCard` crashes with `RangeError: Maximum call stack size exceeded`. | Keep all component imports and JSX tags flowing strictly downward from root to branches to leaves. |

## 1. Principle 1: Tree Roles: Root, Parent, Child, and Leaf

### Every component's role in the tree is decided by which component renders its JSX tag

Every component on a page has a specific size and job. The site header belongs at the top of the page. The article list belongs below the header. The article card belongs inside the list, and the small status badges belong inside the card.

- **In daily coding**: Placing a page-wide component tag inside a card renders the main page heading inside the card's border instead of at the top of the page.
- **In an interview**: Define the four tree roles clearly:
  1. **Root Component**: The top-level component mounted into the page root that wraps the entire application.
  2. **Parent Component**: Any component that renders another React component tag inside its JSX.
  3. **Child Component**: Any component whose JSX tag is rendered inside a parent component.
  4. **Leaf Component**: A component at the bottom tip of a branch that returns only built-in HTML tags and zero other React components.

```tree caption="What happens when you place the site header inside a card vs. placing it under the root App component."
Where should `<SiteHeader />` sit in the component tree?
- !Inside `ArticleCard.jsx` | `ArticleCard` renders `<SiteHeader />` inside `<article>` | Traps the **main site title inside the card box**
- +Inside `App.jsx` above `<ArticleList />` | +**DO** render `<SiteHeader />` once in the root component | Displays the **site title at the top of the page** above the article section
```

### What happens when you place a page-wide header inside a card component

Let us see what happens when we mix up those roles and place our page header inside the article card.

First, here is our header file, which returns the main title for the whole site:

```jsx title="src/components/SiteHeader.jsx" startLine="1"
export default function SiteHeader() {
  return (
    <header>
      ~<h1>Latest Articles</h1>~ // Main page heading meant to sit at the top of the page
    </header>
  );
}
```

Second, here is our badge file, which exports two small badge leaf components:

```jsx title="src/components/Badges.jsx" startLine="1"
export function LiveBadge() {
  return ~<span className="badge">Live</span>~; // 1st leaf badge pill
}

export function NewBadge() {
  return ~<span className="badge">New</span>~; // 2nd leaf badge pill
}
```

Now look at what happens if we accidentally import and render the site header inside the card file:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import ~SiteHeader~ from './SiteHeader.jsx'; // **WRONG:** importing the page header into a single card
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleCard() {
  return (
    <article className="card">
      ~<SiteHeader />~ // **WRONG:** traps the whole-page header inside the card box!
      <LiveBadge />
      <NewBadge />
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

Look at what appears in the browser when the card renders:

```page caption="When SiteHeader is placed inside ArticleCard, the top of the page has no header and Latest Articles is trapped inside the card border."
card: head=Latest Articles | badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | bad
```

Instead of sitting at the top of the page above the article section, the main site title is trapped inside the article card box! And if our list later renders five or ten cards, every single card will stamp out its own copy of the site header.

### Placing each component at its proper level from leaves to root

To fix our layout, we match each component's position in the tree to the area of the screen it controls.

First, at the bottom of the tree, our two badges in the badge file act as **leaf components** that return only HTML `<span>` tags:

```jsx title="src/components/Badges.jsx" startLine="1"
export function ~LiveBadge~() { // Leaf component: returns only an HTML <span>
  return <span className="badge">Live</span>;
}

export function ~NewBadge~() { // Leaf component: returns only an HTML <span>
  return <span className="badge">New</span>;
}
```

Second, one level up, our card file acts as the **parent** of the two badges, placing their tags inside the `<article>` card:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ~ArticleCard~() { // Parent of LiveBadge and NewBadge
  return (
    <article className="card">
      ~<LiveBadge />~ // 1st child leaf component inside the card
      ~<NewBadge />~ // 2nd child leaf component inside the card
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

Third, one level higher, our list file acts as the **parent** of the card, wrapping `<ArticleCard />` inside a `<section>`:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ~ArticleList~() { // Parent of ArticleCard
  return (
    <section>
      ~<ArticleCard />~ // Child card rendered inside the list section
    </section>
  );
}
```

Fourth, at the very top of the tree, our root file renders the page header above the article list:

```jsx title="src/App.jsx" startLine="1"
import SiteHeader from './components/SiteHeader.jsx';
import ArticleList from './components/ArticleList.jsx';

export default function ~App~() { // Root component at the top of the tree
  return (
    <main>
      ~<SiteHeader />~ // Rendered at the top of the page
      ~<ArticleList />~ // Rendered below the header
    </main>
  );
}
```

Compare the broken nesting against the clean parent-to-leaf hierarchy side by side:

::: row caption="Rendering SiteHeader inside ArticleCard vs. rendering SiteHeader inside the root App component."
::: col title="Header Inside ArticleCard" tag="header trapped inside card" tone=bad
```page size=mini
card: head=Latest Articles | badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | bad
```
Placing `<SiteHeader />` inside `ArticleCard` traps the site title inside the card box.
:::
::: col title="Header Inside Root App" tag="header at top of page" tone=good
```page size=mini
heading: Latest Articles
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | good
```
Placing `<SiteHeader />` inside `App` renders the header at the top of the page above the card.
:::
:::

> [!PRINCIPLE]
> **Principle 1: Tree Roles: Every Component Has a Root, Parent, Child, or Leaf Role**
>
> *Place page-wide layout components under the root component, container components in the middle, item components inside containers, and HTML-only leaf components at the bottom tips.*
>
> In React, a component's place in the hierarchy is decided by which component renders its JSX tag. When an outer component renders an inner component tag, the outer component is the parent and the inner component is its child. A leaf component at the bottom of a branch returns only standard HTML tags and zero other React components.
>
> **DO THIS:**
> ```jsx title="src/App.jsx"
> export default function App() {
>   return (
>     <main>
>       ~<SiteHeader />~ // Root renders page header at the top
>       ~<ArticleList />~ // Root renders article section below the header
>     </main>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> export default function ArticleCard() {
>   return (
>     <article className="card">
>       ~<SiteHeader />~ // **WRONG:** traps the site header inside the card box!
>       <LiveBadge />
>       <NewBadge />
>       <h2>New Park Opens Today</h2>
>       <p>The park on Main Street opens at noon.</p>
>     </article>
>   );
> }
> ```

## 2. Principle 2: Two Maps: The Module Graph on Disk vs. The Render Tree in Memory

### One file on disk can export multiple components or be rendered multiple times in memory

Look at our project folder: we have **5** component files on disk. Does having 5 files on disk mean React always builds 5 nodes in memory?

- **In daily coding**: Developers often confuse the **files on disk** with the **live components in memory**. First, our `Badges.jsx` file on disk exports two separate badge components. Second, you only write `import` once at the top of a file, but you can place that component's JSX tag multiple times inside `return`.
- **In an interview**: Distinguish the two maps clearly:
  1. **The Module Dependency Graph on Disk**: Shows which `.jsx` file imports which other `.jsx` file. Every file appears **once** in this graph no matter how many components it exports or how many times its tag is rendered.
  2. **The Component Render Tree in Memory**: Shows every live component instance that React renders onto the screen. Every JSX tag creates its own node and child subtree in memory.

### Seeing how 5 files on disk become 6 or 9 live nodes in memory

First, even when our page displays a single article card, count the files on disk versus the live component nodes in memory:
1. On disk, `Badges.jsx` is **1 file**, so the Module Dependency Graph has **5 component files**.
2. In memory, `ArticleCard` renders both badge tags, so the Component Render Tree already has **6 live component nodes**. Those six nodes are the root app, the site header, the article list, the article card, and the two badges.

Now suppose we want to test how our list layout looks when two `<ArticleCard />` tags are stacked inside `ArticleList.jsx`:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ~ArticleCard~ from './ArticleCard.jsx'; // Imported ONCE from the card file on disk

export default function ArticleList() {
  return (
    <section>
      ~<ArticleCard />~ // 1st live card subtree in the Render Tree
      ~<ArticleCard />~ // 2nd live card subtree in the Render Tree
    </section>
  );
}
```

Look closely at what stays the same on disk versus what multiplies in memory:
1. At the top of `ArticleList.jsx`, we still write the `import` line **only once**. On disk, the Module Dependency Graph still has the exact same **5 files**.
2. Inside `return`, writing `<ArticleCard />` twice tells React to build **two** card subtrees in memory. Because each card renders its own `LiveBadge` and `NewBadge`, the Component Render Tree now has **9 live component nodes**!

In Lecture 8, we will use **props** to pass a different headline and summary into each `<ArticleCard />` tag. Right now, before we add props, both card instances run the same function. That shows how **1 file import on disk** creates **2 card subtrees and 4 badge leaves in memory**:

```page caption="Testing two <ArticleCard /> tags in ArticleList: 5 files on disk produce 9 live component nodes in memory."
heading: Latest Articles
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | good
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | good
```

Compare the **5-file Module Dependency Graph on disk** with the **Component Render Tree in memory**:

```tree dir=right caption="The Module Dependency Graph on disk always has 5 component files, because each file is imported once."
Module Dependency Graph on Disk: 5 Component Files
- +`src/App.jsx` [1 file] | Imports `SiteHeader.jsx` once | Imports `ArticleList.jsx` once
- +`src/components/ArticleList.jsx` [1 file] | Imported once by `App.jsx` | Imports `ArticleCard.jsx` **once**
- +`src/components/ArticleCard.jsx` [1 file] | Imported once by `ArticleList.jsx` | Imports `Badges.jsx` **once**
- +`src/components/Badges.jsx` and `SiteHeader.jsx` [2 files] | Imported once on disk | Hold the leaf components
```

```tree caption="The Component Render Tree in memory creates a separate node for every rendered JSX tag."
Component Render Tree in Memory: Live Component Nodes
- +`<SiteHeader />` [1st child of `<App />`] | Renders 1 `<header>` banner at the top of the page
- +`<ArticleList />` [2nd child of `<App />`] | Every `<ArticleCard />` tag inside it creates a **full card subtree** | Each `<ArticleCard />` node spawns its own `<LiveBadge />` and `<NewBadge />` leaf nodes
```

Whenever you inspect your app in React DevTools, you are looking at the **Component Render Tree**, where every rendered JSX tag is its own live branch.

> [!PRINCIPLE]
> **Principle 2: Two Maps: The Module Graph on Disk Is Not the Render Tree in Memory**
>
> *Import a component file once at the top of a module. Then render its JSX tag as many times as needed to create multiple instances in memory.*
>
> The Module Dependency Graph tracks how files import one another on disk, so each file appears only once. The Component Render Tree tracks every live `<Component />` tag rendered in memory. Each `<ArticleCard />` tag creates its own card node and its own two badge leaf nodes.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleList.jsx"
> import ~ArticleCard~ from './ArticleCard.jsx'; // 1 file import on disk
>
> export default function ArticleList() {
>   return (
>     <section>
>       ~<ArticleCard />~ // 1st card subtree in memory
>       ~<ArticleCard />~ // 2nd card subtree in memory
>     </section>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleList.jsx"
> import ArticleCard from './ArticleCard.jsx';
> ~import ArticleCard2 from './ArticleCard.jsx';~ // **WRONG:** never import the same component twice to render two cards!
> ```

## 3. Principle 3: Sibling Scope: Why Sibling Components Cannot Read Each Other's Variables

### Two components side by side under the same parent cannot reach into each other's local variables

Now let us return `ArticleList.jsx` to rendering our single `<ArticleCard />` and look at the top of our Component Render Tree. Below the root component, the page header and the article list sit side by side:

```jsx title="src/App.jsx" startLine="1"
import SiteHeader from './components/SiteHeader.jsx';
import ArticleList from './components/ArticleList.jsx';

export default function App() {
  return (
    <main>
      ~<SiteHeader />~ // Left sibling inside <App />
      ~<ArticleList />~ // Right sibling inside <App />
    </main>
  );
}
```

Two components that share the same parent are called **siblings**. Here, the header and the article list are siblings because both are children of the root component.

- **In daily coding**: When two sibling components both need the same piece of text, such as the section name `'City News'`, beginners try two broken shortcuts:
  1. They declare a variable inside one sibling and try to read it directly inside the other sibling—which immediately crashes the page with a `ReferenceError`.
  2. Or they copy `const category` into **both** sibling files—which silently drifts out of sync as soon as someone updates one file and forgets the other.
- **In an interview**: State the law of sibling data flow: **sibling components cannot talk sideways**. Whenever two siblings need the same data, that value must live in a **single source of truth** above both siblings.

```tree caption="Why sibling components cannot share a local variable sideways or duplicate it in both files."
How should two sibling components share the section name `'City News'`?
- !Read a sibling's variable sideways [`SiteHeader` reads `{category}` from `ArticleList`] | Local variables are locked inside their own function | Crashes immediately with **`ReferenceError: category is not defined`**
- !Copy `const category` into both sibling files [`SiteHeader.jsx` and `ArticleList.jsx`] | Updating one file leaves the other file unchanged | Page shows **conflicting text** in the header and the list
- +Share one source of truth above both siblings [`src/siteData.js`] | +**DO** keep the shared value in one place | Both siblings **always display the exact same section name**
```

### What happens when one sibling tries to read another sibling's variable

Suppose we want to display the current news section name, `'City News'`, in **both** siblings:
1. In the header, we want the main heading to include `'City News'` after the site title.
2. In the article list right below it, we want a label line to show `'City News'` above the card.

First, let us create a `category` variable inside the list file and display it above the card:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList() {
  ~const category = 'City News';~ // Local variable created inside ArticleList
  return (
    <section>
      ~<p>Section: {category}</p>~ // Works here: category is inside this function
      <ArticleCard />
    </section>
  );
}
```

Now look at what happens if the sibling header file tries to read that same `category` variable inside its own heading:

```jsx title="src/components/SiteHeader.jsx" startLine="1"
export default function SiteHeader() {
  return (
    <header>
      <h1>Latest Articles — ~{category}~</h1> // **WRONG:** SiteHeader cannot see ArticleList's local variable!
    </header>
  );
}
```

As soon as the browser runs the header component, the page goes blank and the Console shows an error:

```devconsole
x Uncaught ReferenceError: category is not defined
```

Why did the page crash when `category` was already created inside the list component?

Because in JavaScript, a variable created inside one function is **locked inside that function's local scope**. Even though the header and the list sit right next to each other inside the root component, **sibling components cannot reach sideways into each other's local variables**.

### What happens when you copy the variable into both sibling files

What if a developer avoids the crash by typing `const category` inside **both** files?

First, the developer defines `category` as `'City News'` inside the header file:

```jsx title="src/components/SiteHeader.jsx" startLine="1"
export default function SiteHeader() {
  ~const category = 'City News';~ // Updated here to 'City News'
  return (
    <header>
      <h1>Latest Articles — {category}</h1>
    </header>
  );
}
```

Second, the list file still has its own separate `const category` variable from yesterday, when the section was called `'Local News'`:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList() {
  ~const category = 'Local News';~ // **WRONG:** forgot to update this second copy!
  return (
    <section>
      <p>Section: {category}</p>
      <ArticleCard />
    </section>
  );
}
```

Now the page loads without a Console error, but look at the browser screen:

```page caption="When both siblings keep their own copy of category, the header says City News while the list below it still says Local News."
heading: Latest Articles — City News
line: Section: Local News | bad
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | bad
```

The header at the top says **City News**, while the list right below it says **Local News**! Because each sibling owns a separate copy of the variable, updating one file leaves the other file showing stale text.

### Sharing one single source of truth above both siblings

Whenever two sibling components need the exact same value, that value must live **above** both siblings in a single shared place, known as a **single source of truth**.

Later in Lecture 8, we will learn **props** so a parent component can pass dynamic data down to both children. Before we even use props, we can already share a constant across files using the `export` and `import` statements from Lecture 5!

First, we create a shared data file that exports `category` from one place:

```js title="src/siteData.js" startLine="1"
~export const category = 'City News';~ // Single source of truth exported once
```

Second, our header file imports `category` from the shared data file and displays it in the main heading:

```jsx title="src/components/SiteHeader.jsx" startLine="1"
import ~{ category }~ from '../siteData.js'; // Imported into the left sibling

export default function SiteHeader() {
  return (
    <header>
      <h1>Latest Articles — ~{category}~</h1> // Reads 'City News' from siteData.js
    </header>
  );
}
```

Third, our list file imports that exact same `category` from the shared data file and displays it above the card:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ~{ category }~ from '../siteData.js'; // Imported into the right sibling
import ArticleCard from './ArticleCard.jsx';

export default function ArticleList() {
  return (
    <section>
      <p>Section: ~{category}~</p> // Reads the exact same 'City News' value
      <ArticleCard />
    </section>
  );
}
```

Compare the stale two-copy bug against the shared single source of truth side by side:

::: row caption="Keeping a separate copy of category in each sibling vs. importing a single shared constant into both siblings."
::: col title="Separate Copy in Each Sibling" tag="header and list disagree" tone=bad
```page size=mini
heading: Latest Articles — City News
line: Section: Local News | bad
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | bad
```
Updating the header file leaves the list file showing the old `'Local News'` label.
:::
::: col title="Single Source of Truth" tag="both siblings stay in sync" tone=good
```page size=mini
heading: Latest Articles — City News
line: Section: City News | good
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | good
```
Both siblings import `category` from the shared data file and display `'City News'`.
:::
:::

> [!PRINCIPLE]
> **Principle 3: Sibling Scope: Sibling Components Cannot Read Each Other's Variables**
>
> *Never read local variables sideways across sibling components or duplicate shared values in both files. Keep shared data in a single source of truth above both siblings.*
>
> A variable declared inside a component function is private to that function's local scope, so a sibling that tries to read it throws a `ReferenceError`. Copying the variable into both siblings removes the crash but creates two separate copies that easily drift out of sync.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleList.jsx"
> import ~{ category }~ from '../siteData.js'; // Both siblings import the same single source of truth
> import ArticleCard from './ArticleCard.jsx';
>
> export default function ArticleList() {
>   return (
>     <section>
>       <p>Section: {category}</p>
>       <ArticleCard />
>     </section>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleList.jsx"
> import ArticleCard from './ArticleCard.jsx';
>
> export default function ArticleList() {
>   ~const category = 'Local News';~ // **WRONG:** separate copy in a sibling drifts out of sync!
>   return (
>     <section>
>       <p>Section: {category}</p>
>       <ArticleCard />
>     </section>
>   );
> }
> ```

## 4. Principle 4: Tree Direction: Why a Child Component Must Never Render Its Own Parent

### Every branch in a component tree must point strictly downward from root to leaves

In a healthy component tree, every branch points strictly **downward** from larger containers to smaller pieces:
- The root component renders the list.
- The list renders the card.
- The card renders the badges.

- **In daily coding**: Suppose a child component accidentally imports its own parent and renders that parent's tag inside its JSX. The two components call each other back and forth forever until the browser tab crashes.
- **In an interview**: Explain that a React component tree must be a **directed acyclic graph**—meaning branches flow in one direction from top to bottom with **zero circular loops**.

```tree caption="One-way top-down component hierarchy vs. a circular parent-in-child loop."
How must component tags flow through the Render Tree?
- !Circular loop [`ArticleList` renders `<ArticleCard />` and `ArticleCard` renders `<ArticleList />`] | Parent and child call each other back and forth forever | Crashes with **`RangeError: Maximum call stack size exceeded`**
- +Strict top-down flow [`App` -> `ArticleList` -> `ArticleCard` -> `Badges`] | +**DO** point every import and JSX tag strictly downward | Rendering **stops cleanly** at the HTML leaf components
```

### What happens when a child component renders its own parent

Let us watch a circular render loop happen step by step.

First, remember that our list file imports and renders the card component:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ~ArticleCard~ from './ArticleCard.jsx'; // Parent imports child

export default function ArticleList() {
  return (
    <section>
      ~<ArticleCard />~ // ArticleList renders ArticleCard
    </section>
  );
}
```

Now suppose inside the card file, we make a mistake. We import the list component back into the card and place `<ArticleList />` at the bottom of the card:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import ~ArticleList~ from './ArticleList.jsx'; // **WRONG:** child imports its own parent!
import { LiveBadge, NewBadge } from './Badges.jsx';

export default function ArticleCard() {
  return (
    <article className="card">
      <LiveBadge />
      <NewBadge />
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
      ~<ArticleList />~ // **WRONG:** infinite loop: Card renders List -> List renders Card!
    </article>
  );
}
```

When you save the file, the page goes blank and the Console shows a `RangeError`:

```devconsole
x Uncaught RangeError: Maximum call stack size exceeded
```

Look at what React had to do when it tried to render this page:
1. React ran the list component, which returned `<ArticleCard />`.
2. To draw that card, React ran the card component, which returned `<ArticleList />` at the bottom.
3. To draw that inner list, React ran the list again, which returned another card and another list! Within a fraction of a second, the browser ran out of call-stack memory.

### Removing the upward import restores a clean top-down tree

To fix the crash, we remove `ArticleList` from the card file so the card only renders its own HTML and its smaller badge leaves:

::: row caption="Rendering parent ArticleList inside child ArticleCard vs. keeping all JSX tags flowing strictly downward to leaf components."
::: col title="Child Renders Its Own Parent" tag="infinite render loop + RangeError" tone=bad
```page size=mini
blank
```
```devconsole
x Uncaught RangeError: Maximum call stack size exceeded
```
The list renders the card, which renders the list again until the call stack overflows.
:::
::: col title="Strict Top-Down Hierarchy" tag="stops cleanly at HTML leaves" tone=good
```page size=mini
heading: Latest Articles — City News
line: Section: City News | good
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | good
```
```devconsole

```
The root renders the list, the list renders the card, and the card stops at the badge leaves.

> [!PRINCIPLE]
> **Principle 4: Tree Direction: A Child Component Must Never Render Its Own Parent**
>
> *Keep all component imports and JSX tags flowing strictly downward from the root component to container branches and down to leaf components.*
>
> Every branch in a React Render Tree must eventually end at leaf components that return only plain HTML tags. If a child component imports and renders its own parent or ancestor, React enters an infinite render loop and crashes with a `RangeError`.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> import ~{ LiveBadge, NewBadge }~ from './Badges.jsx'; // Imports only smaller leaf components below it
>
> export default function ArticleCard() {
>   return (
>     <article className="card">
>       ~<LiveBadge />~ // Leaf #1 stops at <span>
>       ~<NewBadge />~ // Leaf #2 stops at <span>
>       <h2>New Park Opens Today</h2>
>       <p>The park on Main Street opens at noon.</p>
>     </article>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> import ~ArticleList~ from './ArticleList.jsx'; // **WRONG:** child imports its own parent!
>
> export default function ArticleCard() {
>   return (
>     <article className="card">
>       <h2>New Park Opens Today</h2>
>       ~<ArticleList />~ // **WRONG:** endless List -> Card -> List loop!
>     </article>
>   );
> }
> ```

## Putting All Four Principles Together Across Our Project Files

Let us walk through all seven files of our complete news project from bottom to top, seeing how every file fits into the component hierarchy.

First, our shared data file exports the section name from one place so sibling components never drift out of sync:

```js title="src/siteData.js" startLine="1"
~export const category = 'City News';~ // Principle 3: Single source of truth shared by siblings
```

Second, at the bottom of the component tree, our badge file exports the two leaf components that return only HTML `<span>` tags:

```jsx title="src/components/Badges.jsx" startLine="1"
export function ~LiveBadge~() { // Principle 1 & 4: Leaf #1 returns only an HTML <span>
  return <span className="badge">Live</span>;
}

export function ~NewBadge~() { // Principle 1 & 4: Leaf #2 returns only an HTML <span>
  return <span className="badge">New</span>;
}
```

Third, one level up, our card file imports the two badges and places them inside an `<article>` card:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
import ~{ LiveBadge, NewBadge }~ from './Badges.jsx'; // Principle 4: Points strictly downward to leaf badges

export default function ArticleCard() {
  return (
    <article className="card">
      ~<LiveBadge />~ // 1st child leaf badge inside the card
      ~<NewBadge />~ // 2nd child leaf badge inside the card
      <h2>New Park Opens Today</h2>
      <p>The park on Main Street opens at noon.</p>
    </article>
  );
}
```

Fourth, our header file imports the shared `category` constant and returns the top `<header>` banner as a leaf component:

```jsx title="src/components/SiteHeader.jsx" startLine="1"
import ~{ category }~ from '../siteData.js'; // Principle 3: Left sibling reads shared category

export default function SiteHeader() {
  return (
    <header>
      <h1>Latest Articles — ~{category}~</h1> // Displays 'Latest Articles — City News'
    </header>
  );
}
```

Fifth, our list file imports the shared `category` constant and the card component, rendering the section line and the article card:

```jsx title="src/components/ArticleList.jsx" startLine="1"
import ~{ category }~ from '../siteData.js'; // Principle 3: Right sibling reads the same shared category
import ~ArticleCard~ from './ArticleCard.jsx'; // Principle 1 & 4: Imports child card component from below

export default function ArticleList() {
  return (
    <section>
      <p>Section: ~{category}~</p> // Matches the header's section name
      ~<ArticleCard />~ // Renders the child card inside the section
    </section>
  );
}
```

Sixth, at the top of the component tree, our root file imports the header and the list and renders them side by side as siblings:

```jsx title="src/App.jsx" startLine="1"
import ~SiteHeader~ from './components/SiteHeader.jsx'; // Principle 1: Page-wide header branch
import ~ArticleList~ from './components/ArticleList.jsx'; // Principle 1: Article list container branch

export default function App() {
  return (
    <main>
      ~<SiteHeader />~ // Left sibling rendered once at the top
      ~<ArticleList />~ // Right sibling rendered once below the header
    </main>
  );
}
```

Seventh, our entry file mounts the root component into the HTML page:

```jsx title="src/main.jsx" startLine="1"
import { createRoot } from 'react-dom/client';
import ~App~ from './App.jsx'; // Imports only the top root component

const rootElement = document.getElementById('root');
const root = createRoot(rootElement);
root.render(~<App />~); // Mounts the entire Component Render Tree!
```

When the browser runs our project, every component in the tree appears in its exact place:

```page caption="The complete Component Render Tree rendered in the browser."
heading: Latest Articles — City News
line: Section: City News | good
card: badge=Live | badge=New | title=New Park Opens Today | text=The park on Main Street opens at noon. | good
```

```tree dir=right caption="How the live component nodes in memory are organized from the root App component down to the leaf badges."
Complete Component Render Tree
- +1. Root [`<App />`] | Top of the tree | Renders sibling children `<SiteHeader />` and `<ArticleList />`
- +2. Left Branch [`<SiteHeader />`] | Leaf component | Renders `<header><h1>Latest Articles — City News</h1></header>`
- +3. Right Branch [`<ArticleList />`] | Parent container | Renders `<p>Section: City News</p>` and `<ArticleCard />`
- +4. Card Subtree [`<ArticleCard />`] | Card parent + 2 badge leaves | Renders `<LiveBadge />` and `<NewBadge />` leaf `<span>` tags inside `<article>`
```

| Aspect | The Flat-Folder Misconception | The React Component Tree Rule |
| :--- | :--- | :--- |
| **Where a component appears on screen** | Expects a component's folder location to decide where it sits on the page | Which component renders `<Component />` in its JSX decides its parent-child position and how often it repeats |
| **Files on disk vs. nodes on screen** | Assumes 5 `.jsx` files on disk always mean 5 component nodes in memory | 1 file can export multiple components, and 1 `import` on disk can render multiple `<Component />` subtrees in memory |
| **Sharing data between siblings** | Reads a sibling's local variable sideways or copies the variable into both files | Sibling scopes are isolated; shared values must live in a single source of truth above both siblings |
| **Direction of component imports** | Allows a child component to import and render its own parent container | Imports and JSX tags must flow strictly downward from root to leaves with zero circular loops |

## For the Interview

> **The Interview Question:** How do you model a React UI as a component tree, and how do you decide which components are parents, children, siblings, or leaves?

### How to Answer Clearly in 30 Seconds

"We model a React UI by breaking the visual page into nested boxes from the largest layout shell down to the smallest UI atoms. At the very top sits the **root component**, `App`, which we pass to `root.render`. Whenever one component renders another component's tag in its JSX, the outer component is the **parent** and the inner component is its **child**. Two components rendered side by side inside the same parent, such as `<SiteHeader />` and `<ArticleList />`, are **siblings**. At the bottom tips of the tree sit **leaf components**, such as `<LiveBadge />`, which return only built-in HTML tags and zero other React components. As we build this tree, we follow three architectural rules. First, the **Module Dependency Graph** on disk is different from the **Component Render Tree** in memory, because one imported file can be rendered multiple times. Second, **siblings cannot read each other's local variables**, so shared data must live above both siblings in a single source of truth. Third, the tree must flow **strictly top-down**, because a child rendering its own parent triggers an infinite loop and a `RangeError` crash."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What is the difference between the Module Dependency Graph and the Component Render Tree?"**
   - The **Module Dependency Graph** maps static `.jsx` files and their `import` statements on disk—where `ArticleList.jsx` imports `ArticleCard.jsx` only **once**. The **Component Render Tree** maps the live component instances rendered in memory at runtime—where rendering `<ArticleCard />` twice creates **two** card nodes and **four** badge leaf nodes.

2. **"Can two sibling components read variables directly from each other?"**
   - No. Each component is a JavaScript function with its own private local scope, so reading a sibling's local variable throws an `Uncaught ReferenceError`. Duplicating the variable in both siblings causes the UI to drift out of sync. Shared data must live in a single source of truth above both siblings. Static constants can be imported from a shared module, while dynamic data is lifted into their common parent component.

3. **"What happens if a child component imports and renders its own parent component?"**
   - React enters an infinite render cycle where the parent renders the child and the child renders a new instance of the parent. Within a fraction of a second, the JavaScript engine exhausts the call stack and crashes with `Uncaught RangeError: Maximum call stack size exceeded`.

```tree dir=right caption="Quick interview summary of Component Hierarchy & Render Trees."
Four Rules of the React Component Render Tree
- +1. Four Tree Roles [`Root` `Parent` `Child` `Leaf`] | Outer JSX tag = **Parent**; inner JSX tag = **Child** | Bottom HTML-only component = **Leaf**
- +2. Two Different Maps [`Module Graph` vs. `Render Tree`] | **1 import** on disk: `ArticleCard.jsx` | **Multiple instances** in memory: `<ArticleCard />` x 2
- +3. Sibling Isolation [`<SiteHeader />` + `<ArticleList />`] | No sideways variable access: throws `ReferenceError` | Keep shared values in a **single source of truth** above both siblings
- +4. Strict Top-Down Flow [`App -> List -> Card -> Badges`] | Branches point **downward only** | Child rendering parent crashes with **`Maximum call stack size exceeded`**
```
