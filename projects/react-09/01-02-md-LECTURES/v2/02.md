## Why Pasted HTML Breaks Inside a React Component

### Most React work starts from HTML that already exists

Most React work does not start from an empty file. It starts from markup that already exists: a page from an old site, a card from a designer, or a form from a CSS library.

Suppose our town news site is moving to React. On the old site, the pages are plain HTML files. A developer copies a five-line article card from `old-site/index.html` and pastes it into a React component named `ArticleCard`.

In `old-site/index.html`, those five lines worked without a single complaint. The browser read the file as it was and drew the card, with the library photo, the heading, and the text:

```html title="old-site/index.html"
<article>
  <img src="/library.jpg" ~alt="The city library">~ <!-- 1. No closing slash on img -->
  <h2 ~class~="title">Library Hours</h2> <!-- 2. HTML class attribute -->
  <p>The library stays open until nine.</p>
</article>
```

Now the developer pastes those exact same five lines into `ArticleCard` inside `App.jsx`:

```jsx title="App.jsx"
export default function ArticleCard() {
  return (
    <article>
      <img src="/library.jpg" ~alt="The city library">~ {/* **WRONG:** stops the build right here! */}
      <h2 ~class~="title">Library Hours</h2> {/* **PROBLEMATIC:** logs a Console error */}
      <p>The library stays open until nine.</p>
    </article>
  );
}
```

The developer saves `App.jsx`. Instead of drawing the card, our dev server, **Vite**, stops the build and covers the page with its **error overlay**, saying it expected a closing tag for `img`:

::: row caption="The same five lines of markup in a plain HTML file vs. pasted into a React component."
::: col title="In `old-site/index.html`" tone=plain
```page size=mini
url: old-site/index.html
card: img=Library | title=Library Hours | text=The library stays open until nine.
```
:::
::: col title="Pasted into `ArticleCard` in `App.jsx`" tone=bad
```overlay size=mini
message: [PARSE_ERROR] Expected corresponding JSX closing tag for 'img'.
file: src/App.jsx:4:8
```
:::
:::

Why did the same five lines draw a card in `old-site/index.html` and stop the page in `App.jsx`? Because markup can live in two very different places:
- **In a plain HTML file**: The browser reads the tags directly. A tag left open, or two tags placed side by side, still gives a working page.
- **In JSX inside a component**: The markup inside a React component is **JSX**. JSX looks like HTML, but it is JavaScript. Before the browser receives `App.jsx`, the **build** turns every tag into a JavaScript function call. Because each tag becomes a call, every tag must close, every `return` needs one root, and attributes take JavaScript names:

```tree caption="Two places markup can live: an HTML file read by the browser vs. JSX inside a React component."
Where markup lives
- !Plain HTML file [`old-site/index.html`] | The browser reads the tags **directly** | Forgives **open tags** and **tags side by side**
- +JSX inside a component [`App.jsx`] | The build turns each tag into a **JavaScript call** first | Every tag must **close**, every `return` needs **one root**, and attributes take **JavaScript names**
```

### An object keeps values under names

To see what JSX turns into, we need one small building block from plain JavaScript: an **object**.

A JavaScript object keeps several values together, each under a name. Each name with its value is called a **property**. We write an object with curly braces, and we read a property with a dot:

```js title="Plain JavaScript"
const article = {
  ~title~: 'Library Hours', // A property named title
  topic: 'City',
};

console.log(article.~title~); // Prints "Library Hours" in the Console
```

The `article` object holds two properties, `title` and `topic`. Reading `article.title` gives `'Library Hours'`. A property name is a JavaScript name, and an object can also hold other objects inside its properties.

### The dev server rewrites our files before the browser gets them

The browser does not read `App.jsx` as we wrote it. When the page asks for the file, our dev server, **Vite**, reads it, rewrites every JSX tag into plain JavaScript, and sends the result to the browser. This rewriting step is called the **build**. When the site is ready to publish, `npm run build` does the same rewrite for every file at once.

When a mistake in our JSX stops the build from reading a file, nothing in that file runs. Vite covers the page with a dark box called the **error overlay**. It shows what went wrong and which line stopped the build, and it goes away as soon as we fix the file and save.

Along with the page itself, we use two panels in Chrome's developer tools throughout this lesson:
- **The `Elements` panel** shows the live **DOM**, the tree of real page elements that React built.
- **The `Console` panel** shows values printed with `console.log` and any red runtime error messages from React.

### Five Principles of JSX Syntax

**PRINCIPLES:** Everything in this lecture comes down to one idea: JSX looks like HTML, but it is JavaScript. Five rules govern every JSX snippet we write:
1. **Principle 1 — The JSX Transform**: The build rewrites each JSX tag into a React function call that returns a plain object called a **React element**, and React builds the DOM from those objects.
2. **Principle 2 — Closed Tags**: Because the build must know where each tag's content ends, every tag needs a closing tag or a trailing slash, including `<img />`, `<br />`, and `<input />`.
3. **Principle 3 — Single Root**: Each tag becomes one call, and a JavaScript `return` gives back one value, so every component returns one outer root element that holds the rest.
4. **Principle 4 — Fragments**: When sibling tags need one root for `return` and the page needs no extra DOM box, group them with a **Fragment**, written `<>` and `</>`.
5. **Principle 5 — camelCase Attributes**: Tag attributes become properties on a JavaScript object. Write `className` for `class`, `htmlFor` for `for`, and camelCase for multi-word names, while `aria-*` and `data-*` keep their dashes.

| # | Principle | What Happens When Broken | The JSX Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The JSX Transform** | Treating JSX as an HTML text string instead of a JavaScript value fails to build elements. | Read every JSX tag as a call that returns a `{ type, props }` React element object. |
| **Principle 2** | **Closed Tags** | Leaving `<img>`, `<br>`, or `<input>` open without a slash stops the build with an error overlay. | Close every tag with a matching closing tag or a slash such as `<img />`. |
| **Principle 3** | **Single Root** | Placing two tags side by side after `return` stops the build because a function returns one value. | Return one outer root element or Fragment from every component. |
| **Principle 4** | **Fragments `<>...</>`** | Wrapping list or flex items in an extra `<div>` adds a real DOM box that breaks row layout and borders. | Group sibling tags with `<>...</>` when the page needs no extra DOM box. |
| **Principle 5** | **camelCase Attributes** | Keeping `class`, `for`, or `tabindex` from HTML fills the Console with red property errors. | Write `className`, `htmlFor`, and `tabIndex`; keep dashes in `aria-*` and `data-*`. |

## 1. Principle 1: The JSX Transform — Each Tag Becomes a Call That Returns an Object

### Is the markup inside a component really HTML?

When you look at `<article>`, `<h2>`, and `<p>` inside a React component, they look just like HTML. It is easy to think the component returns a piece of HTML text.

Let us test what that markup really is. In `ArticleCard`, we store the JSX in a variable named `card`, print `card` with `console.log`, and return it:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~card~ = ( // 1. Store the JSX markup in a variable
    <article>
      <h2 className="title">Library Hours</h2>
      <p>The library stays open until nine.</p>
    </article>
  );
  console.log(~card~); // 2. Log card in the Console panel
  return card; // 3. Return card so React draws it
}
```

Here `className` is how JSX writes the `class` attribute of HTML, and Principle 5 will explain why.

Save the file. The card appears on the page with its heading and its text. Now look at Chrome's **Console panel**. It does not show HTML text. It shows a plain JavaScript object!

When we click the small triangle in the Console to open that object, we see two main properties:
- **`type`** holds the tag's name, `'article'`.
- **`props`** holds an object with the tag's attributes and its inner content under **`children`**. Because `<article>` holds two tags inside it, `children` is a list of two more objects, one for the `<h2>` and one for the `<p>`:

::: row caption="Saving ArticleCard: the card appears on the page, and console.log shows a plain JavaScript object in the Console."
::: col title="On the Page" tone=plain
```page size=mini
card: title=Library Hours | text=The library stays open until nine.
```
:::
::: col title="In Chrome's Console Panel" tone=good
```devconsole source="App.jsx:8"
v {type: 'article', props: {…}}
  type: "article" | The outer tag's name
  v props: {children: Array[2]}
    v 0: {type: 'h2', props: {…}}
      type: "h2" | First inner tag
      props: {className: 'title', children: 'Library Hours'}
    v 1: {type: 'p', props: {…}}
      type: "p" | Second inner tag
      props: {children: 'The library stays open until nine.'}
```
:::
:::

### How the build turns every tag into a function call

Where did that object come from? We wrote `<article>`, `<h2>`, and `<p>`, not curly braces!

Before the browser received `App.jsx`, the build rewrote every tag into a JavaScript function call. In the rewritten file that the browser receives, every angle-bracket tag is gone. In its place is a call to a helper function from React named `_jsxDEV`:

```js title="App.jsx after the build, shortened"
const card = ~_jsxDEV~("article", { // <article> became a function call
  children: [
    _jsxDEV("h2", { className: "title", children: "Library Hours" }),
    _jsxDEV("p", { children: "The library stays open until nine." }),
  ],
});
```

Look at how simple that rewrite is:
- The tag's name became the first argument, such as `"article"` or `"h2"`.
- The tag's attributes and inner content became the properties of an object in the second argument.

This rewrite by the build is called the **JSX transform**. Each call returns the plain object we saw in the Console, and React calls that object a **React element**. When React renders the component, it reads those React elements and builds the real browser DOM from them.

The build also adds the `import` line for `_jsxDEV` at the top of the file automatically. Older versions of React rewrote tags into `React.createElement`, which required `import React from 'react'` at the top of every file. Because React 19 uses the automatic JSX transform, you never need to import `React` just to write JSX.

We can now follow a single tag, `<h2 className="title">Library Hours</h2>`, through all four stages from your file to the page:

```tree dir=right caption="The four stages of a JSX tag on its way from your file to the page."
One JSX tag on its way to the page
- +1. You write JSX [`App.jsx`] | `<h2 className="title">Library Hours</h2>`
- +2. The build writes a call [JSX transform] | Calls `_jsxDEV` with `"h2"` and `props`
- +3. The call returns an object [`Console` panel] | React element with `type: "h2"` and `props`
- +4. React builds the DOM [`Elements` panel] | `<h2 class="title">Library Hours</h2>` on the page
```

> [!PRINCIPLE]
> **Principle 1: The JSX Transform: Each Tag Becomes a Call That Returns an Object**
>
> *Read JSX as JavaScript: the build rewrites every tag into a function call that returns a plain React element object, and React builds the DOM from those objects.*
>
> The browser never reads raw JSX tags. Before the browser receives your file, the build turns every tag into a call to a function from React. That call returns a plain object called a React element, holding `type` and `props`. Because a JSX tag evaluates to a normal JavaScript object, you can return it from a function or store it in a variable.
>
> **DO THIS:**
> ```jsx
> export default function ArticleCard() {
>   const ~card~ = <article><h2>Library Hours</h2></article>; // Stores the React element object
>   return ~card~;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function ArticleCard() {
>   // **WRONG:** Quotes turn the markup into a plain text string instead of a React element!
>   const card = ~"<article><h2>Library Hours</h2></article>"~;
>   return card;
> }
> ```

## 2. Principle 2: Closed Tags — Close Every Tag Including `<img />` and `<br />`

### HTML lets void elements stay open, while JSX requires every tag to close

In HTML, some tags can never hold anything inside them, such as `<img>`, `<br>`, and `<input>`. They are called **void elements**, and HTML lets you write them without a closing tag or a slash:

```html title="Plain HTML"
<img src="/library.jpg" alt="The city library">
<br>
<input type="text">
```

Now we want our article card to show the library photo above the heading. A developer copies the `<img>` line from the old HTML site and pastes it into `ArticleCard` as it is, with no closing slash:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  return (
    <article>
      <img src="/library.jpg" ~alt="The city library">~ {/* **WRONG:** no closing slash on img! */}
      <h2 className="title">Library Hours</h2>
      <p>The library stays open until nine.</p>
    </article>
  );
}
```

When the developer saves, the build stops at the `<img>` tag, and nothing in the file runs. Vite covers the page with its error overlay. Look at the two lines the overlay points to: it marks `<img>` on line 4 as `Opened here`, and it marks `</article>` on line 7 as `Expected </img>`:

```overlay caption="Vite's error overlay when <img> on line 4 has no closing slash."
message: [PARSE_ERROR] Expected corresponding JSX closing tag for 'img'.
file: src/App.jsx:4:8
code: 4 | <img src="/library.jpg" alt="The city library">
bad: Opened here
code: 7 | </article>
bad: Expected </img>
```

### Why an open `<img>` tag makes the build complain at `</article>`

Why did a mistake on line 4 point to `</article>` down on line 7?

Each tag becomes a call, and the build must know where that call's `children` end. After an open tag, the build reads everything that follows as the content of that tag until it finds the closing tag. HTML knows that `<img>` is a void element that holds nothing, **but JSX makes no exception for void elements**.

So the build read `<h2>` and `<p>` as if they were children sitting inside `<img>`! When it reached `</article>` on line 7, it was still waiting for `</img>`, and the build stopped.

To tell the build that a tag holds nothing and ends right where it opens, put a slash `/` before the closing `>`:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  return (
    <article>
      <img src="/library.jpg" ~alt="The city library" />~ {/* Closed with a slash: ends right here */}
      <h2 className="title">Library Hours</h2>
      <p>The library stays open until nine.</p>
    </article>
  );
}
```

Save the file, and the error overlay disappears. The photo, the heading, and the text appear on the page. `<br />` and `<input />` follow the same rule, and any empty tag in JSX may close itself the same way, such as `<div className="spacer" />`.

> [!PRINCIPLE]
> **Principle 2: Closed Tags: Close Every Tag Including `<img />` and `<br />`**
>
> *Close every tag in JSX with a matching closing tag or with a trailing slash, including void elements such as `<img />`, `<br />`, and `<input />`.*
>
> The build reads everything after an open tag as its content until it finds the closing tag. JSX makes no exception for void elements, so an open image or input tag swallows the tags below it and stops the build at the next closing tag. A trailing slash closes a tag that holds nothing.
>
> **DO THIS:**
> ```jsx
> export default function ArticleCard() {
>   return (
>     <article>
>       <img src="/library.jpg" ~alt="The city library" />~ {/* Closed with a slash */}
>       <p>Library Hours<br />Open until nine.</p> {/* Line break closed with a slash too */}
>     </article>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function ArticleCard() {
>   return (
>     <article>
>       <img src="/library.jpg" ~alt="The city library">~ {/* **WRONG:** waits for </img> and stops the build */}
>       <p>Library Hours~<br>~Open until nine.</p> {/* **WRONG:** unclosed br stops the build */}
>     </article>
>   );
> }
> ```

## 3. Principle 3: Single Root — Return One Outer Element From Every Component

### Why two tags side by side after `return` stop the build

In an HTML file, you can place a heading `<h2>` and a paragraph `<p>` side by side with no outer tag around them. Suppose another card on the old site has only a heading and a paragraph, and a developer pastes both straight after `return`:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  return (
    ~<h2>Library Hours</h2>~
    ~<p>The library stays open until nine.</p>~ {/* **WRONG:** a second root tag after return! */}
  );
}
```

When the developer saves, the build stops before anything runs. Vite's error overlay points at the `<p>` tag on line 4 and says that adjacent JSX elements must be wrapped in an enclosing tag. Below the code, a help line asks whether we wanted a JSX fragment `<>...</>`:

```overlay caption="Vite's error overlay when a component returns two tags side by side."
message: Adjacent JSX elements must be wrapped in an enclosing tag.
file: src/App.jsx:4:4
code: 3 |     <h2>Library Hours</h2>
bad:  4 |     <p>The library stays open until nine.</p>
help: Did you want a JSX fragment <>...</>?
```

Why does HTML allow two tags side by side while a React component forbids them?

Remember Principle 1: each JSX tag becomes one function call, and one call produces one object. In JavaScript, a `return` statement can only give back **one value**. You cannot return two separate objects side by side from a JavaScript function:

```js title="Plain JavaScript"
function getCard() {
  return (
    { type: 'h2' }
    ~{ type: 'p' }~ // SyntaxError: a function cannot return two separate values!
  );
}
```

Because `<h2>` and `<p>` are two separate calls, the build cannot turn them into a single `return`.

### Wrapping both tags in one outer `<article>` gives `return` one value

To give `return` a single value, we put one outer `<article>` tag around both inner tags:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  return (
    ~<article>~ {/* One outer root element holds both tags as its children */}
      <h2>Library Hours</h2>
      <p>The library stays open until nine.</p>
    ~</article>~
  );
}
```

With `<article>` around both tags, `return` gives back **one** call for the `<article>`. The two inner calls become its `children`, just as we saw in the Console object in Principle 1.

Save the file, and the card appears. Notice the help line at the bottom of the overlay above: it mentioned a JSX fragment `<>...</>`. Wrapping `<h2>` and `<p>` in `<article>` was right here because our card needed an `<article>` box on the page. What if a component returns two tags, and an extra box on the page would break the layout? Principle 4 takes up that case next.

> [!PRINCIPLE]
> **Principle 3: Single Root: Return One Outer Element From Every Component**
>
> *Return one outer root element from every component, one tag that holds the rest as its children, because a JavaScript function returns one value.*
>
> Each JSX tag becomes one call that produces one value. Because a JavaScript function can only return one value, two tags side by side after `return` stop the build before any code runs. Wrapping them in one outer tag turns the inner tags into the `children` of a single returned object.
>
> **DO THIS:**
> ```jsx
> export default function ArticleCard() {
>   return (
>     ~<article>~ {/* One root element returned by the function */}
>       <h2>Library Hours</h2>
>       <p>The library stays open until nine.</p>
>     ~</article>~
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function ArticleCard() {
>   return (
>     <h2>Library Hours</h2>
>     ~<p>The library stays open until nine.</p>~ {/* **WRONG:** a second root value stops the build */}
>   );
> }
> ```

## 4. Principle 4: Fragments — Group Elements With `<>...</>` When No Extra DOM Box Is Wanted

### CSS flex layout and child selectors look for direct children

On our news site's home page, a list `<ul className="articles">` displays the featured articles side by side in a row. Our stylesheet, `index.css`, styles that list with two rules:

```css title="src/index.css"
.articles {
  ~display: flex~; /* 1. Places the direct children of .articles side by side in a row */
  gap: 24px;
}

.~articles > li~ { /* 2. Gives a border only to an <li> directly inside .articles */
  border: 1px solid #999;
}
```

Look at what those two CSS rules expect in the DOM:
- **`display: flex`** turns the `<ul class="articles">` list into a **flex layout** that places its **direct children** side by side in a row.
- **`.articles > li`** uses the `>` **child selector**. It gives a border only to an `<li>` that sits **directly** inside `.articles`, with no other element in between.

### Why a `<div>` inside a list breaks the layout

Now suppose `App` owns `<ul className="articles">`, and a child component named `FeaturedArticles` returns two `<li>` items for that list. Two `<li>` tags side by side would stop the build, so a developer wraps them in a `<div>`:

```jsx title="App.jsx" startLine="1"
function FeaturedArticles() {
  return (
    ~<div>~ {/* **PROBLEMATIC:** puts a real <div> box between <ul> and <li>! */}
      <li>Summer Recipes</li>
      <li>Park Opens Today</li>
    ~</div>~
  );
}

export default function App() {
  return (
    <ul className="articles">
      <FeaturedArticles />
    </ul>
  );
}
```

When the developer saves, the build passes and the Console stays clean. Yet on the page, the two articles stack one above the other, and neither one has a border!

Why did the layout break without a single warning? Because a `<div>` is a real HTML element, so React builds an extra `<div>` box in the DOM between `<ul class="articles">` and the two `<li>` items. Now the list has only one direct child: the `<div>`. As a result, `display: flex` cannot place the two items in a row, and `.articles > li` finds no direct `<li>` child to border.

### A Fragment `<>...</>` gives one root and adds no box to the DOM

What we need is one outer value for `return` and **no extra element in the DOM**. That is a **Fragment**, written as an empty opening tag `<>` and an empty closing tag `</>`:

```jsx title="App.jsx" startLine="1"
function FeaturedArticles() {
  return (
    ~<>~ {/* One root for return, and no element in the DOM */}
      <li>Summer Recipes</li>
      <li>Park Opens Today</li>
    ~</>~
  );
}
```

A Fragment compiles to one call with React's `Fragment` type, so `return` receives a single value. When React builds the DOM, it creates no element for the Fragment and places the two `<li>` items straight inside `<ul class="articles">` as direct children. Save the file, and the two articles sit side by side in a row with their borders back:

::: row caption="Wrapping the two <li> items in a <div> vs. grouping them with a Fragment <>...</>."
::: col title="Wrapped in a `<div>`" tag="breaks flex row & borders" tone=bad
```page size=mini
stack: Summer Recipes ; Park Opens Today
```
```dom
<ul class="articles">
!  <div> | note: Extra DOM box!
    <li>Summer Recipes</li>
    <li>Park Opens Today</li>
!  </div>
</ul>
```
:::
::: col title="Grouped with a Fragment `<>...</>`" tag="keeps flex row & borders" tone=good
```page size=mini
row: Summer Recipes ; Park Opens Today
```
```dom
<ul class="articles">
+  <li>Summer Recipes</li> | note: Direct child of <ul>
+  <li>Park Opens Today</li> | note: Direct child of <ul>
</ul>
```
:::
:::

How do you choose between a Fragment and a real HTML tag? Ask whether the page itself needs a box in the DOM:
- **When the page needs no extra box**, such as `<li>` items in a `<ul>` or `<td>` cells in a `<tr>`, group them with `<>...</>`. That gives `return` one value and adds zero nodes to the DOM.
- **When the page needs a real box** for meaning or styling, as our `<article>` card did in Principle 3, wrap them in a real HTML tag.
- **Never add a meaningless `<div>`** just to satisfy `return`, because that extra node breaks flex rows, grids, and `.parent > child` CSS:

```tree dir=right caption="Choosing between a Fragment and a real HTML tag when grouping elements for return."
Grouping sibling tags for `return`
- +Page needs no extra box [`<li>` in `<ul>` or `<td>` in `<tr>`] | +**DO** group with `<>...</>` | Gives `return` one value and adds **0 nodes** to the DOM
- +Page needs a real box [`<article>` or `<section>`] | +**DO** wrap in a real HTML tag | Builds the DOM element the page needs for meaning or styling
- !Meaningless `<div>` for `return` [`<ul><div><li>...`] | ~Do **NOT** add an unneeded `<div>` | Inserts an extra DOM box that breaks **flex rows** and **`.parent > child` CSS**
```

> [!PRINCIPLE]
> **Principle 4: Fragments: Group Elements With `<>...</>` When No Extra DOM Box Is Wanted**
>
> *Group sibling elements with a Fragment, `<>` and `</>`, when `return` needs one root and the page needs no extra box.*
>
> A wrapping `<div>` is a real node in the DOM between the parent and its children. Inside a list, a table row, or a flex layout, that extra box breaks the layout because CSS rules look for direct children. A Fragment is one call for `return`, and React puts its children straight into the parent with no extra DOM element.
>
> **DO THIS:**
> ```jsx
> function FeaturedArticles() {
>   return (
>     ~<>~ {/* One root for return, and no extra element in the DOM */}
>       <li>Summer Recipes</li>
>       <li>Park Opens Today</li>
>     ~</>~
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function FeaturedArticles() {
>   return (
>     ~<div>~ {/* **WRONG:** puts a real <div> inside <ul> and breaks the list layout! */}
>       <li>Summer Recipes</li>
>       <li>Park Opens Today</li>
>     ~</div>~
>   );
> }
> ```

## 5. Principle 5: camelCase Attributes — Write Attributes as JavaScript Property Names

### Some words belong to JavaScript itself

JavaScript keeps certain words for its own grammar, such as `return`, `function`, `class`, and `for`. They are called **reserved words**: `class` starts a class definition, and `for` starts a loop.

When the browser builds a DOM object in memory for an HTML element, that DOM object stores the element's attributes as JavaScript properties. Because `class` and `for` are reserved words in JavaScript, the DOM gives those two properties JavaScript names: **`className`** for `class`, and **`htmlFor`** for `for`. Other property names made of several words join them in **camelCase**, such as **`tabIndex`**.

### What happens when you keep `class`, `for`, and `tabindex` from HTML

Now suppose a developer pastes a newsletter form from the old HTML site into `SignUp`, keeping its original HTML attribute names:

```jsx title="App.jsx" startLine="1"
export default function SignUp() {
  return (
    <form>
      <label ~class~="label" ~for~="name">Name</label> {/* **PROBLEMATIC:** HTML attribute names class and for */}
      <input id="name" ~tabindex~="0" /> {/* **PROBLEMATIC:** lowercase tabindex */}
    </form>
  );
}
```

When the developer saves, the build passes without stopping, and the `Name` form looks and works fine on the page. Yet Chrome's **Console panel** fills with three red errors: one for `class` asking for `className`, one for `for` asking for `htmlFor`, and one for `tabindex` asking for `tabIndex`.

Why did the page work while the Console filled with errors?

Remember Principle 1: the attributes of a tag become the properties of the `props` object passed to React. React reads those properties by their JavaScript DOM names: `className`, `htmlFor`, and camelCase names such as `tabIndex` and `autoComplete`. In React 19, `class` and `for` still work on screen so the page does not break. However, React logs an `Invalid DOM property` error in the Console for each one, and a Console full of attribute errors hides real bugs!

### Renaming the attributes clears the Console

To clear all three Console errors, we write the attributes with their JavaScript names. The two families of attributes with a dash, **`aria-*`** for screen readers and **`data-*`** for custom values, are the one exception. They keep their dashes in JSX, just as in HTML:

```jsx title="App.jsx" startLine="1"
export default function SignUp() {
  return (
    <form ~aria-label~="Newsletter" ~data-form-id~="7"> {/* aria-* and data-* keep their dashes */}
      <label ~className~="label" ~htmlFor~="name">Name</label> {/* JavaScript property names */}
      <input id="name" ~tabIndex~="0" /> {/* camelCase for multi-word names */}
    </form>
  );
}
```

Save the file, and the Console panel is completely clean, with no messages at all:

| In Plain HTML | In React JSX | Why JSX Uses This Name |
| :--- | :--- | :--- |
| `class="label"` | `className="label"` | Matches the DOM property `className` because `class` is a reserved word. |
| `for="name"` | `htmlFor="name"` | Matches the DOM property `htmlFor` because `for` is a reserved word. |
| `tabindex="0"`, `autocomplete="off"` | `tabIndex="0"`, `autoComplete="off"` | Multi-word attributes use camelCase in JSX. |
| `aria-label="..."`, `data-form-id="7"` | `aria-label="..."`, `data-form-id="7"` | `aria-*` and `data-*` attributes keep their dashes. |

> [!PRINCIPLE]
> **Principle 5: camelCase Attributes: Write Attributes as JavaScript Property Names**
>
> *Write each attribute as a JavaScript property name: `className` for `class`, `htmlFor` for `for`, camelCase for multi-word names, and dashes only in `aria-*` and `data-*`.*
>
> The attributes of a tag become the properties of the object that the JSX call receives. Because `class` and `for` are reserved words in JavaScript, React uses `className` and `htmlFor`, the names the DOM gives those properties, and uses camelCase for multi-word names. React 19 still sets HTML attribute names on the element, so the page looks right while the Console fills with errors.
>

## Putting All Five Principles Together in `App.jsx`

### Moving our old news page into one clean React file

Now we bring all three parts of our old news page together inside `App.jsx`: `ArticleCard`, `FeaturedArticles`, and `SignUp`, all placed inside `App`:

```jsx title="src/App.jsx"
function ~ArticleCard~() { // Principles 1, 2, & 3: one <article> root and a closed <img /> tag
  return (
    <article>
      <img src="/library.jpg" alt="The city library" />
      <h2 className="title">Library Hours</h2>
      <p>The library stays open until nine.</p>
    </article>
  );
}

function ~FeaturedArticles~() { // Principle 4: Fragment groups two <li> items with no extra box
  return (
    <>
      <li>Summer Recipes</li>
      <li>Park Opens Today</li>
    </>
  );
}

function ~SignUp~() { // Principle 5: className, htmlFor, and tabIndex; aria-* and data-* keep dashes
  return (
    <form aria-label="Newsletter" data-form-id="7">
      <label className="label" htmlFor="name">Name</label>
      <input id="name" tabIndex="0" />
    </form>
  );
}

export default function ~App~() {
  return (
    <>
      <ArticleCard />
      <ul className="articles">
        <FeaturedArticles />
      </ul>
      <SignUp />
    </>
  );
}
```

Every piece of `App.jsx` above puts one of our five JSX principles to work:

```tree dir=right caption="How the five JSX principles work together in App.jsx."
The five JSX principles in `App.jsx`
- +1. The JSX Transform [`_jsxDEV`] | Every tag compiles to a call that returns a React element object
- +2. Closed Tags [`<img />` `<input />`] | Void elements close with a slash `/` so the build knows where each tag ends
- +3. Single Root [`<article>` `<form>` `<>...</>`] | Every component returns one outer root value
- +4. Fragments [`<>...</>`] | Keeps both `<li>` items as direct children of `<ul className="articles">`
- +5. camelCase Attributes [`className` `htmlFor` `tabIndex`] | Keeps the Console clean while `aria-*` and `data-*` keep their dashes
```

| Aspect | The HTML Habit | The JSX Rule |
| :--- | :--- | :--- |
| **The tag** | Markup text read directly by the browser | A JavaScript call that returns a `{ type, props }` React element object |
| **Its end** | Void elements stay open: `<img>`, `<br>`, `<input>` | Every tag is closed: `<img />`, `<br />`, `<input />` |
| **The return** | Any number of tags placed side by side | One outer root element or Fragment per `return` |
| **The group** | Wrap a group in an extra `<div>` box | Use a Fragment `<>...</>` when no extra DOM box is wanted |
| **Its attributes** | `class`, `for`, `tabindex` | `className`, `htmlFor`, `tabIndex`; `aria-*` and `data-*` keep dashes |

## For the Interview

> **The Interview Question:** What is JSX, what syntax rules must every snippet follow, and how do Fragments group elements without wrapper nodes?

### How to Answer Clearly in 30 Seconds

"JSX looks like HTML, but it is a syntax extension for JavaScript. During the build, each JSX tag is rewritten into a function call that returns a plain JavaScript object called a React element, with `type` and `props`. React reads those objects to build the browser DOM.

Every JSX syntax rule follows from the fact that tags become JavaScript calls:
1. **Close every tag**: every tag must close, including void elements like `<img />` and `<br />`, so the build knows where each call ends.
2. **Return a single root**: a component must return one outer root because a JavaScript function can only return one value.
3. **Use a Fragment `<>...</>` when no DOM box is wanted**: wrapping list items or flex children in a `<div>` inserts a real DOM box that breaks flex, grid, and direct-child CSS. A Fragment gives `return` one value and adds zero nodes to the DOM.
4. **Use JavaScript property names for attributes**: attributes become properties on `props`, so we write `className`, `htmlFor`, and camelCase like `tabIndex`, while `aria-*` and `data-*` keep their dashes."

### Four Follow-Up Questions Interviewers Ask

1. **"Does a Fragment `<>...</>` appear as an element in Chrome's Elements panel?"**
   **No.** An extra `<div>` wrapper inserts a real `<div>` node into the DOM, which breaks `display: flex`, `display: grid`, and `.parent > child` CSS rules. A Fragment `<>...</>` compiles to one `Fragment` call for `return` and adds **0 nodes** to the DOM, so its children sit directly inside the parent.
2. **"Why do `class` and `for` still work on screen in React 19, yet log an error in the Console?"**
   The build accepts any attribute name as a property on `props`, and React 19 still sets `class` and `for` on the DOM element. However, React expects the DOM's JavaScript property names, `className` and `htmlFor`, and logs an `Invalid DOM property` error in the Console for each HTML name.
3. **"Why don't React 19 files need `import React from 'react'` at the top to use JSX?"**
   Older transforms rewrote every tag into `React.createElement`, which needed `React` in scope. React 19 uses the automatic JSX transform, where the build adds its own import of React's JSX helper function automatically.
4. **"Can the short Fragment syntax `<>...</>` take a `key` attribute in a list?"**
   **No.** The empty tag `<>...</>` cannot take any attributes. When a Fragment in a list needs a `key`, import `Fragment` from `'react'` and write `<Fragment key={item.id}>...</Fragment>`.

```tree dir=right caption="Interview comparison: wrapping sibling elements in a <div> vs. grouping them with a Fragment <>...</>."
`<div>` wrapper vs. Fragment `<>...</>`
- !Extra `<div>` wrapper [`<div><li>...</li></div>`] | Inserts a **real `<div>` node** into the DOM | Breaks **`display: flex`**, **`display: grid`**, and **`.parent > child`** CSS
- +Fragment [`<><li>...</li></>`] | Compiles to **one `Fragment` call** for `return` | Adds **0 nodes** to the DOM; children sit **directly inside the parent**
```
