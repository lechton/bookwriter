# Lecture 8: Splitting Components with ES Module Imports and Exports
> INTERVIEW QUESTION | ❱ CORE | How do you split components across files, and how do default and named imports differ?

1. The article site keeps every component in one file, `App.jsx`, and the file keeps growing.
2. You move the article card into a file of its own, save, and the page goes blank with "ArticleCard is not defined".
3. How does a component written in one file get used in another?

### A project grows past one file

Since Lecture 2, every component we wrote has lived in one file, `App.jsx`. Each lesson said so, as a choice for learning: you could see every component at once. A real project does not stay that way. With a card, an article list, two badges, and a header in one file, every change means scrolling past code that has nothing to do with it, and two people who change the file at once get in each other's way. So every React developer meets the same question: how does a component written in one file get used in another?

The answer is one idea, and this chapter follows it from the first question to the last: each file is a module: its names stay inside until it exports them, and another file uses them only by importing them. The chapter follows one component's move to its own file: the file it lands in, the import that must match its export, the kind of export it gets, and the path that finds it.

This lesson answers four questions:

- **I moved `ArticleCard` into its own file. Why does `App` say it is not defined?**
- **Do I write braces around the name or not?**
- **Should the badges be default or named exports?**
- **I moved the feed into `components`. Why can't it find the card?**

The questions stand on what earlier lessons established:

- **Lecture 1 (What is React)**: `export default` in front of a component let another file use it; this chapter explains what that line does.
- **Lecture 5 (The render tree)**: A name used where it does not exist throws a **`ReferenceError`**, such as "topic is not defined": a function sees only its own names and those at the top of its file.
- **Lecture 7 (Children)**: `CardContainer({ title, children })` draws the frame, and each story writes its body between the frame's tags.

Later in this track, Lecture 9 demonstrates how `main.jsx` imports `App` and mounts it with `createRoot`, and Lecture 12 examines why variables declared at module scope run once and must remain pure across renders.

### A project is a folder of files

Two files need their names now, so the folders come first. Your project starts as one file, `App.jsx`, inside the `src` folder. When a component moves out, it goes into a folder named `components` that sits next to `App.jsx`.

```files title="Lesson 8 project: File Explorer"
index.html | parent | The page the browser loads, with one empty element for React
src/
  main.jsx | boundary | Imports App and shows it
  App.jsx | parent | The starter file, which imports the components it uses
  components/
    ArticleCard.jsx | child | The card component, moved into its own file
```

### A path names a file from where you stand

A file names another file by a **relative path**, a route that starts from its own folder. `./` means "this folder", so from `App.jsx`, `./components/ArticleCard.jsx` means the `components` folder beside it, then the card's file. `../` means "the folder above". Two files in different folders reach the same file by different paths.

```ascii title="Relative routes to the badge file"
from src/App.jsx                    ./components/Badges.jsx
from src/components/ArticleCard.jsx ./Badges.jsx
```

A name with no dot, such as `'react'`, is not a path at all: it names an installed **package**, and the build tool finds it in the project's dependencies.

### Principles of React: Each File Is a Module

Everything in this lesson comes down to one idea: each file is a module, and its names cross to another file only by export and import. First, modules, which means each file keeps its names to itself until it exports them: a moved component is gone from the old file until the new file exports it and the old one imports it. Second, imports match exports, which means braces for a named export, none for the default: the wrong form stops the page before anything runs. Third, default and named exports, which means one default for the file's main component, named exports for the rest: a file has one default at most. Fourth, import paths, which means a path starts from the file that imports: a file in the components folder reaches its neighbor with a dot and a slash.

### Question 1: A moved component is not defined in the old file

A developer cuts `ArticleCard` from `App.jsx` and pastes it into `src/components/ArticleCard.jsx`, but writes no `export` statement in front of the component function:

```jsx title="components/ArticleCard.jsx"
// **PROBLEMATIC:** missing export keyword
function ArticleCard({ title }) {
  return <article className="card">{title}</article>;
}
```

In `App.jsx`, `App` still attempts to render the card tag directly without an import statement:

```jsx title="App.jsx"
export default function App() {
  return <ArticleCard title="Rail Strike Ends" />; // **WRONG:** out of scope
}
```

Save the file. The browser screen turns completely blank. Open the Console panel: the browser reports an uncaught runtime error, `ReferenceError: ArticleCard is not defined`.

**I moved `ArticleCard` into its own file. Why does `App` say it is not defined?**

---

**ANSWER**

**The code does not do what we wanted.** `ArticleCard` is missing both an export in its new file and an import in `App.jsx`, so `App` cannot see it.

In traditional browser scripts loaded through separate `<script>` tags on an HTML page, all top-level functions share a single global scope. But in modern JavaScript applications, every file is an ES **module**. A module has its own local scope, just like the function scopes examined in Lecture 5.

When `ArticleCard` was moved into `components/ArticleCard.jsx`, its function name became private to that file. It no longer exists inside the module scope of `App.jsx`. When React attempts to evaluate `<ArticleCard />` inside `App`, JavaScript searches the local scope of `App.jsx`, fails to find any identifier named `ArticleCard`, and throws a **`ReferenceError`**.

Moving a component between files requires both sides of the bridge:
1. The source file must use an `export` statement to make the component available outside its own boundary.
2. The consuming file must use an `import` statement to bring that identifier into its local module scope.

If an import statement targets a file that exports nothing, the browser halts before running any code with `The requested module '/src/components/ArticleCard.jsx' does not provide an export named 'default'`.

Any helper function that only its own file needs, such as a title formatter `formatTitle`, stays unexported. Other files cannot reach it, keeping internal implementation details safe from accidental coupling.

Furthermore, a module's top level executes only once when the file is first imported, regardless of how many other files import it. A `console.log` placed at the top of a module file runs once during application startup. In contrast, a `console.log` placed inside a component body executes on every single render.

Under Vite, any module file containing JSX markup must end in `.jsx`. Naming the file `.js` stops the build immediately with `[PARSE_ERROR] Unexpected JSX expression` and `Help: JSX syntax is disabled`.

The fix is to export `ArticleCard` from its own file and import it at the top of `App.jsx`:

```jsx title="components/ArticleCard.jsx"
export default function ArticleCard({ title }) {
  return <article className="card">{title}</article>; // exported default
}
```

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // imported into scope

export default function App() {
  return <ArticleCard title="Rail Strike Ends" />; // renders card
}
```

> [!PRINCIPLE]
> **Principle 1: Modules: each file keeps its names to itself until it exports them**
>
> We treat each file as a module: a component moved to its own file is exported there with `export`, and imported with `import` by every file that uses it; a function only its file uses stays unexported.
>
> *We should do this:*
>
> ```jsx
> // src/components/ContactCard.jsx
> export default function ContactCard({ name }) { // exports component
>   return <p>{name}</p>;
> }
> // src/App.jsx
> import ContactCard from './components/ContactCard.jsx'; // imports card
> ```
>
> *We should not do this:*
>
> ```jsx
> // src/components/ContactCard.jsx
> function ContactCard({ name }) { // **PROBLEMATIC:** unexported
>   return <p>{name}</p>;
> }
> // src/App.jsx: **WRONG:** missing import throws ReferenceError
> ```

### Question 2: The braces of an import must match the export

A developer exports `ArticleCard` from `components/ArticleCard.jsx` using a named export:

```jsx title="components/ArticleCard.jsx"
export function ArticleCard({ title }) {
  return <article className="card">{title}</article>; // named export
}
```

In `App.jsx`, the developer attempts to import it without curly braces:

```jsx title="App.jsx"
// **WRONG:** missing braces for named export
import ArticleCard from './components/ArticleCard.jsx';

export default function App() {
  return <ArticleCard title="Rail Strike Ends" />;
}
```

Save the file. The browser page stays completely blank. The console displays a fatal module resolution error: `The requested module '/src/components/ArticleCard.jsx' does not provide an export named 'default'`. Running `npm run build` fails with `[MISSING_EXPORT] "default" is not exported by "src/components/ArticleCard.jsx"`.

**Do I write braces around the name or not?**

---

**ANSWER**

**The code does not do what we wanted.** The import syntax asks for a default export without braces, but the module provides only a named export.

JavaScript ES modules provide two distinct export mechanisms:
1. **Default export**: Declared with `export default`. A module has at most one default export, and importers consume it without curly braces: `import ArticleCard from ...`.
2. **Named export**: Declared with `export function Name` or `export const Name`. A module can have multiple named exports, and importers consume them inside curly braces: `import { ArticleCard } from ...`.

The browser links module imports and exports statically before any application code executes. When `App.jsx` writes `import ArticleCard from ...`, it explicitly requests the module's default export slot. Because `ArticleCard.jsx` used `export function ArticleCard`, it populated a named slot called `ArticleCard` and left the default slot completely empty. The runtime halts immediately.

The mirror mistake fails just as decisively: writing `import { ArticleCard } from ...` when the source file used `export default` fails with `does not provide an export named 'ArticleCard'`. Similarly, misspelling a named import, such as `import { Articlecard } from ...`, fails because named imports must match the exact case-sensitive identifier exported by the module.

Because a default import binds to the file's single default slot, the importing file can assign it any local name: `import StoryBox from './components/ArticleCard.jsx'` works cleanly. In contrast, named imports must match the exported name, or use the `as` keyword to rename them: `import { ArticleCard as StoryBox } from ...`.

Note that the curly braces in `import { ArticleCard }` are standard ES module syntax. They are not JSX expression curly braces from Lecture 4.

In older bundlers, an export and import mismatch was not caught at build time and evaluated to `undefined` at runtime. In React, passing `undefined` as a component type produces the classic error: `Element type is invalid: expected a string (for built-in components) or a class/function (for composite components) but got: undefined. You likely forgot to export your component from the file it's defined in, or you might have mixed up default and named imports.` Under Vite, this error appears if you import an entire module namespace with `import * as Cards` and render `<Cards.ArticleCard />` when `ArticleCard` was actually a default export.

The fix is to match the named export with curly braces:

```jsx title="App.jsx"
import { ArticleCard } from './components/ArticleCard.jsx'; // matches braces

export default function App() {
  return <ArticleCard title="Rail Strike Ends" />; // renders card
}
```

> [!PRINCIPLE]
> **Principle 2: Imports match exports: braces for a named export, none for the default**
>
> We write each import in the form of its export: no braces for a default export, under any name we choose, and braces with the exact name for a named export.
>
> *We should do this:*
>
> ```jsx
> // src/components/ContactCard.jsx
> export function ContactCard({ name }) { // named export
>   return <p>{name}</p>;
> }
> // src/App.jsx
> import { ContactCard } from './components/ContactCard.jsx'; // matched braces
> ```
>
> *We should not do this:*
>
> ```jsx
> // src/components/ContactCard.jsx: export function ContactCard
> // src/App.jsx
> import ContactCard from './components/ContactCard.jsx'; // **WRONG:** missing braces
> // **WRONG:** does not provide an export named 'default'
> ```

### Question 3: A file has one default export

A developer keeps `ArticleCard` and a small `Badge` helper in `components/ArticleCard.jsx`, adding an `export default` keyword in front of both functions:

```jsx title="components/ArticleCard.jsx"
export default function ArticleCard({ title }) {
  return <article className="card">{title}</article>; // first default
}

export default function Badge({ text }) {
  return <span className="badge">{text}</span>; // **WRONG:** second default
}
```

Save the file. The Vite error overlay immediately covers the browser window: `[PARSE_ERROR] A module cannot have multiple default exports.`

**Should the badges be default or named exports?**

---

**ANSWER**

**The code does not do what we wanted.** A JavaScript module has only one default export slot, so declaring a second default export is a syntax error.

Because `App.jsx` has had `export default` on its main function since Lecture 1, developers often assume every component should be exported as a default. But ECMAScript module specifications strictly limit each module file to a single default export.

In contrast, named exports have no numerical limit. A module can export tens or hundreds of functions, constants, or types by name.

The standard architectural convention across the React ecosystem is straightforward:
- A file whose primary responsibility is a single major component exports that component as its `export default`.
- A file containing several smaller components or utility helpers exports each helper using named exports: `export function LiveBadge()` and `export function NewBadge()`.

When a file exports both a primary default component and secondary named helpers, callers can import both in a single concise line: `import ArticleCard, { Badge } from './components/ArticleCard.jsx'`. The default name sits outside the braces, while the named helpers sit inside the braces.

Every exported function should retain an explicit identifier. Writing an anonymous default export like `export default ({ title }) => <article>{title}</article>` is discouraged. An anonymous component function has its runtime `name` property set to `"default"`, making stack traces and React DevTools component trees difficult to read.

The fix is to keep `ArticleCard` as the default export and export `Badge` as a named export:

```jsx title="components/ArticleCard.jsx"
export default function ArticleCard({ title }) {
  return <article className="card">{title}</article>; // single default
}

export function Badge({ text }) {
  return <span className="badge">{text}</span>; // named export
}
```

```jsx title="App.jsx"
import ArticleCard, { Badge } from './components/ArticleCard.jsx'; // both forms
```

> [!PRINCIPLE]
> **Principle 3: Default and named exports: one default for the file's main component, named exports for the rest**
>
> We give a file at most one default export, for its main component, and we export its other components with names; a file of several small components uses named exports only, and every exported function keeps a name.
>
> *We should do this:*
>
> ```jsx
> // src/components/ContactCard.jsx
> export default function ContactCard({ name }) { // one default export
>   return <p>{name}</p>;
> }
> export function PhoneLine({ number }) { // named export for helper
>   return <span>{number}</span>;
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> // src/components/ContactCard.jsx
> export default function ContactCard({ name }) { // first default
>   return <p>{name}</p>;
> }
> export default function PhoneLine({ number }) { // **WRONG:** second default
>   return <span>{number}</span>;
> }
> // **WRONG:** module cannot have multiple default exports
> ```

### Question 4: A path copied from App.jsx breaks inside components

A developer moves the article list feed into `src/components/ArticleList.jsx`. Inside this new file, the developer needs to render the card frame component `CardContainer.jsx`. The developer copies the import line directly from `App.jsx` without changing its text:

```jsx title="components/ArticleList.jsx"
// **WRONG:** copied path fails to resolve
import CardContainer from './components/CardContainer.jsx';

export default function ArticleList() {
  return <CardContainer title="Rail Strike Ends">Story body</CardContainer>;
}
```

Save the file. The Vite error overlay covers the page: `Failed to resolve import "./components/CardContainer.jsx" from "src/components/ArticleList.jsx". Does the file exist?`

**I moved the feed into `components`. Why can't it find the card?**

---

**ANSWER**

**The code does not do what we wanted.** The import path was copied from `App.jsx` and resolves to a nonexistent subfolder when evaluated from inside `components`.

Relative import paths in JavaScript always resolve relative to the folder containing the file that holds the import statement. They never resolve relative to the project root or relative to `App.jsx`.

When `App.jsx` (located in `src/`) writes `./components/CardContainer.jsx`, `./` represents `src/`. The build tool resolves the path to `src/components/CardContainer.jsx`, where the file exists.

However, when `ArticleList.jsx` (located in `src/components/`) writes `./components/CardContainer.jsx`, `./` represents `src/components/`. The build tool appends the relative segment, resulting in `src/components/components/CardContainer.jsx`. Because that directory does not exist, module resolution fails.

The Vite error message provides the diagnosis: it prints both the requested path (`"./components/CardContainer.jsx"`) and the originating file (`from "src/components/ArticleList.jsx"`).

Because `CardContainer.jsx` sits directly beside `ArticleList.jsx` in the same `components` directory, the relative route is simply `./CardContainer.jsx`:

```jsx title="components/ArticleList.jsx"
import CardContainer from './CardContainer.jsx'; // neighbor in same folder
```

If a file inside `components/` needs to reach a file in the parent `src/` directory, it uses `../` to move up one folder level: `import App from '../App.jsx'`.

The file extension `.jsx` may be omitted in modern projects (`./CardContainer`), though including it remains closest to native browser ES module standards. In contrast, package imports like `'react'` or `'react-dom/client'` contain no leading dot or slash, informing the bundler to look inside the project's installed package dependencies.

> [!PRINCIPLE]
> **Principle 4: Import paths: a path starts from the file that imports**
>
> We write each import path from the folder of the file that imports: `./` for a file beside it, `../` for the folder above, and no dot at all for a package such as `'react'`.
>
> *We should do this:*
>
> ```jsx
> // src/components/ArticleCard.jsx
> import { PhoneLine } from './PhoneLine.jsx'; // neighbor in same folder
> ```
>
> *We should not do this:*
>
> ```jsx
> // src/components/ArticleCard.jsx
> import { PhoneLine } from './components/PhoneLine.jsx'; // **WRONG:** wrong folder
> // **WRONG:** failed to resolve import from src/components/ArticleCard.jsx
> ```

### What is the tree of files?

In Lecture 5, we visualized how React builds a **render tree** by evaluating component tags: `App` called `ArticleList`, which called `CardContainer`, which rendered its child elements.

Now that our project spans multiple files, our import statements create a second tree: the **module dependency tree**. A **bundler** (such as Vite during development or Rolldown during production builds) starts at the root entry point, `main.jsx`. It inspects each `import` statement, loads the requested file, inspects that file's imports, and recursively maps every module our project needs.

```ascii title="The module dependency tree vs the render tree"
MODULE DEPENDENCY TREE (Static Files)     RENDER TREE (Runtime UI)
main.jsx                                  App
  └── App.jsx                               └── ArticleList
        └── components/ArticleList.jsx            ├── CardContainer
              ├── components/CardContainer.jsx    │     ├── NewBadge
              └── components/Badges.jsx           │     └── p (byline)
                                                  └── CardContainer
                                                        ├── LiveBadge
                                                        └── blockquote
```

Notice how the two trees differ: `ArticleList.jsx` imports `CardContainer.jsx` and `Badges.jsx` to assemble the UI. But `CardContainer.jsx` never imports `ArticleList.jsx` or `Badges.jsx`. The frame knows nothing about the badges placed inside it; it receives them at runtime through `children`.

### Let's Design a Practical Example

Each question moved one component. Now we split the whole article site feed of Lecture 7: the frame, two badges, and the article list itself leave `App.jsx` for the `components` folder, and `App.jsx` ends with four lines. ### Step 1: First, we move the frame into its own file <CardContainer.jsx>

This step applies Principle 1: Modules: each file keeps its names to itself until it exports them.

`CardContainer` is used by every article card and performs one clear visual role: rendering the card border, the title header, and the flexible children container. We cut `CardContainer` from `App.jsx` and place it in `src/components/CardContainer.jsx` as that file's default export.

What would happen if `App.jsx` forgot to import `CardContainer`? As shown in Question 1, the browser would throw `ReferenceError: CardContainer is not defined` and display a blank page. We add the default import line at the top of `App.jsx`.

In `CardContainer.jsx`, lines 1 to 8 declare the exported frame component:

```jsx title="CardContainer.jsx" startLine="1"
export default function CardContainer({ title, children }) {
  return (
    <article className="card">
      <h2>{title}</h2>
      {children} {/* wraps nested content */}
    </article>
  );
}
```

In `App.jsx`, line 1 imports the frame component from the components folder:

```jsx title="App.jsx" startLine="1"
import CardContainer from './components/CardContainer.jsx'; // imports frame
```

Save the file. The page renders identically to Lecture 7, proving that moving a component to an exported module preserves runtime behavior.

### Step 2: Next, we import the first badge by its name <App.jsx>

This step applies Principle 2: Imports match exports: braces for a named export, none for the default.

The second card ("Rail Strike Ends") requires a "Live" badge. We create a utility file `src/components/Badges.jsx` and export `LiveBadge` as a named export. In `App.jsx`, we import it using curly braces matching its exact function name.

What would happen if `App.jsx` wrote `import LiveBadge from './components/Badges.jsx'` without braces? The page would fail to load with `The requested module does not provide an export named 'default'`.

In `Badges.jsx`, lines 1 to 3 define and export the live status badge:

```jsx title="Badges.jsx" startLine="1"
export function LiveBadge() {
  return <span className="badge live">Live</span>; // named export
}
```

In `App.jsx`, line 2 imports `LiveBadge` with curly braces:

```jsx title="App.jsx" startLine="2"
import { LiveBadge } from './components/Badges.jsx'; // matches named export
```

In `App.jsx`, lines 14 to 17 render `<LiveBadge />` inside the second card:

```jsx title="App.jsx" startLine="14"
      <CardContainer title="Rail Strike Ends">
        <LiveBadge />
        <blockquote>We are back on Monday.</blockquote>
      </CardContainer> {/* renders badge in frame */}
```

Save the file. The "Live" badge appears cleanly inside the second article card.

### Step 3: Then, we give the badges file two named exports <Badges.jsx>

This step applies Principle 3: Default and named exports: one default for the file's main component, named exports for the rest.

The first card ("City Library Extends Its Hours") needs a "New" badge. Because `NewBadge` and `LiveBadge` are sibling utility widgets of equal standing, neither should be a default export. We add `NewBadge` to `Badges.jsx` as a second named export.

In `App.jsx`, we update the import statement on line 2 to request both named exports inside a single pair of curly braces: `import { LiveBadge, NewBadge } from './components/Badges.jsx'`.

In `Badges.jsx`, lines 4 to 6 add `NewBadge`:

```jsx title="Badges.jsx" startLine="4"
export function NewBadge() {
  return <span className="badge new">New</span>; // second named export
}
```

In `App.jsx`, line 2 imports both badges:

```jsx title="App.jsx" startLine="2"
import { LiveBadge, NewBadge } from './components/Badges.jsx'; // imports both
```

In `App.jsx`, lines 8 to 11 render `<NewBadge />` inside the first card:

```jsx title="App.jsx" startLine="8"
      <CardContainer title="City Library Extends Its Hours">
        <NewBadge />
        <p>New weekend opening times start this Saturday.</p>
      </CardContainer> {/* renders new badge */}
```

Save the file. Both cards now display their respective badges alongside their body content.

### Step 4: Finally, we move the feed and fix its paths <ArticleList.jsx>

This step applies Principle 4: Import paths: a path starts from the file that imports.

`App.jsx` still contains `ArticleList` with its markup and imports. We move `ArticleList` into its own file at `src/components/ArticleList.jsx` as the file's default export.

Inside `ArticleList.jsx`, we must import `CardContainer` and the badges. If we copied the import lines from `App.jsx` (`from './components/CardContainer.jsx'`), module resolution would fail with `Failed to resolve import`. Because `ArticleList.jsx`, `CardContainer.jsx`, and `Badges.jsx` are all located inside `src/components/`, their paths are `./CardContainer.jsx` and `./Badges.jsx`.

In `ArticleList.jsx`, lines 1 to 8 declare the imports and open the list:

```jsx title="ArticleList.jsx" startLine="1" continues="bottom"
import CardContainer from './CardContainer.jsx'; // neighbor in same folder
import { LiveBadge, NewBadge } from './Badges.jsx'; // neighbor in same folder

export default function ArticleList() {
  return (
    <main>
      <h1>Latest Articles</h1>
      <CardContainer title="City Library Extends Its Hours">
```

Lines 9 to 18 render both cards and close `ArticleList`:

```jsx title="ArticleList.jsx" startLine="9" continues="top"
        <NewBadge />
        <p>New weekend opening times start this Saturday.</p>
      </CardContainer>
      <CardContainer title="Rail Strike Ends">
        <LiveBadge />
        <blockquote>We are back on Monday.</blockquote>
      </CardContainer> {/* renders both cards */}
    </main>
  );
}
```

With `ArticleList` encapsulated in its own module, `App.jsx` becomes a clean four-line root file:

```jsx title="App.jsx" startLine="1"
import ArticleList from './components/ArticleList.jsx'; // imports article list

export default function App() {
  return <ArticleList />; // root renders list
}
```

Save the file. The rendered browser output remains completely unchanged, but our project architecture is now fully modularized across clean ES module files.

### Component Summary


A developer accustomed to older script tags expects every declared function to be globally available across all files, assumes curly braces in import statements are optional, uses `export default` indiscriminately, and copies import paths from file to file without inspecting directory depths. In React 19 with modern ES modules, each file forms an isolated module scope, import syntax strictly mirrors export form, files maintain at most one default export, and every relative path resolves from the directory of the file that writes it.

### Where you will meet this

1. A `components` directory where every primary UI component occupies its own dedicated `.jsx` file.
2. A `utils` or `helpers` file exporting multiple standalone calculation or formatting functions using named exports.
3. Third-party UI libraries like Lucide or Material UI imported by name, such as `import { Check, AlertCircle } from 'lucide-react'`.
4. Team git workflows where feature branches avoid merge conflicts because developers edit separate modular files rather than a monolithic `App.jsx`.
5. Debugging legacy codebases or third-party tutorials where mixing up default and named exports causes `Element type is invalid: expected a string or a class/function but got: undefined`.

### For the interview

- **Hidden Signal**: The interviewer is testing whether you understand JavaScript module scope and build-time static linking versus runtime execution. Candidates who guess whether to use curly braces reveal a weak foundation in modern ECMAScript fundamentals.
- **Classic Trap**: Claiming that default and named imports are interchangeable or that braces are merely an aesthetic preference. A mismatch halts execution before any component function runs.
- **What is Actually Going On**: ES modules use static analysis to resolve bindings at build time. Default exports map to an internal property named `default`, while named exports map to explicit property keys on the module's namespace object.
- **Where It Gets Tricky**: Can a file have multiple default exports? No, exactly one. Can a default import be renamed by the consumer? Yes, freely. Can a named import be renamed? Yes, but only with explicit `as` aliasing syntax (`import { Card as StoryCard }`). Where do relative paths start? Always from the directory of the importing file.

### Glossary

- **Module**: An isolated JavaScript file whose top-level functions and variables are private to that file until exported.
- **Default export**: An export declared with `export default` that can be imported without curly braces under any local name.
- **Named export**: An export declared with `export function` or `export const` that must be imported inside curly braces matching its exact identifier.
- **Relative path**: A file path starting with `./` or `../` that resolves relative to the folder containing the file that writes it.
- **Package import**: An import specifying a bare package name without dots or slashes that resolves to installed package dependencies in `node_modules`.
- **Module dependency tree**: The static tree of file relationships formed by `import` and `export` statements, followed by build tools to compile the application.

### Summary

**Each file is a module**

❒ Modules: each file keeps its names to itself until it exports them
- ALWAYS export a component with `export` if another file needs to render it.
- NEVER assume a function declared in another file is globally available.

❒ Imports match exports: braces for a named export, none for the default
- ALWAYS use curly braces when importing named exports: `import { LiveBadge } from './components/Badges.jsx'`.
- NEVER use curly braces when importing a default export: `import ArticleCard from './components/ArticleCard.jsx'`.

❒ Default and named exports: one default for the file's main component, named exports for the rest
- ALWAYS export the primary component of a dedicated file as `export default`.
- NEVER declare more than one `export default` in the same module file.

❒ Import paths: a path starts from the file that imports
- ALWAYS write relative paths starting from the importing file's directory: `./` for neighbors, `../` for parent folders.
- NEVER copy import paths between folders without adjusting their relative steps.

**One wall per file, an import that matches, one default, and a path from here.**

**DO THIS:** export the primary component as default and utility helpers as named

```jsx right
export default function ArticleCard({ title }) {
  return <article className="card">{title}</article>;
}
export function Badge({ text }) {
  return <span className="badge">{text}</span>;
}

import ArticleCard, { Badge } from './components/ArticleCard.jsx';
```

**DO NOT DO THIS:** declare multiple default exports or mix up default and named syntax

```jsx wrong
export default function ArticleCard({ title }) {
  return <article className="card">{title}</article>;
}
export default function Badge({ text }) {
  return <span className="badge">{text}</span>;
}

import { ArticleCard } from './components/ArticleCard.jsx';
```
