### A page grows from a few components into many

In Lecture 2, the Town News page had three components: `App`, an article card, and a comment box. A real front page has many more: a masthead with a menu, a feed of stories, a byline under each story, a box of the most-read stories, and a footer. In our project they all sit side by side in `App.jsx`, one function after another, like a flat list. But the page is not flat: the byline sits inside the story, and the story sits inside the feed. So every React developer meets the same question: how do the components fit together, and how does a value reach the part of the page that shows it?

The answer is one idea, and this chapter follows it from the first question to the last: the page is a tree of components: each component's markup names its children, and React builds the page from the root down. The chapter follows the tree from its shape to its use: how it grows, where it is cut, and what travels along it.

This lesson answers three questions:

- **I have five components side by side in `App.jsx`. How does React know which goes where?**
- **My `App` now holds the whole front page. Should I cut it up, and where?**
- **`ArticleCard` needs the edition that `App` declares. Can it just read it?**

The questions stand on what Lectures 1, 2, 3, and 4 established:

- **Lecture 1 (What is React)**: A **local variable** made with `const` holds a value inside the component. In plain JavaScript, `document.getElementById` finds an element on the page, and `textContent` reads its text.
- **Lecture 2 (Component anatomy)**: React calls a component wherever a tag names it, and `console.log` in its body shows each call in the **Console panel**, once per call in this course's projects. Every component is defined at the **top level of the file**; a component defined inside another one is made again on every run, and loses what the reader typed.
- **Lecture 3 (JSX syntax)**: A **Fragment**, `<>` and `</>`, groups elements without adding one to the page.
- **Lecture 4 (JavaScript expressions in JSX with curly braces)**: `{edition}` puts the value of a variable into the text, and the code inside the braces runs each time React calls the component.

### A variable lives inside the function that declares it

A variable declared with `const` inside a function exists only while that function runs, and only the code inside that function can see it. This part of the code where a name can be used is called the variable's **scope**. A variable declared at the top level of a file, outside every function, can be seen by every function of that file.

```js title="Plain JavaScript: a variable stays in its function"
const siteName = 'Town News'; // the whole file sees it
function header() {
  const edition = 'Morning'; // only header sees it
  return siteName + ', ' + edition;
}
function footer() {
  return siteName + ', ' + edition; // edition is not defined
}
```

`header()` gives back "Town News, Morning". `footer()` stops with "edition is not defined": `edition` exists only inside `header`. JavaScript calls this kind of error a **`ReferenceError`**: the code uses a name that does not exist where it is written. `siteName` works in both, because it sits at the top level.

### A tree has a root, branches, and leaves

Folders on a computer form a tree: one folder at the top holds others, and they hold more. The same words name any tree. The **root** is the one at the top. Each item is the **parent** of the items directly inside it, and those are its **children**. Children of the same parent are **siblings**. An item near the root is **top-level**, and an item that holds nothing is a **leaf**.

### One function, one job

A long function that does many things is hard to read and hard to change, because every change risks the other things it does. Programmers split it so that each function has one job, and this habit has a name: **separation of concerns**. A function with one job gets a name that says the job, such as `formatDate` or `sendEmail`.

### Principles of React: The Page Is a Tree of Components

Everything in this lesson comes down to one idea: the page is a tree of components, and React builds it from the root down.

First, the render tree, which means each component's markup names its children: App is the root, every component is the parent of the components its markup names, and React calls them branch by branch.

Second, component boundaries, which means one branch of the tree for each part of the page with its own job: the header, the feed, and the story each get a component, nested where they sit on the page.

Third, data flow, which means a value travels down the tree, never across it: a component cannot read a variable of its parent or of its neighbor, so a value they share starts above them both.

### Question 1: React calls the components in the order of the tree

A developer writes the Town News front page in `App.jsx` with six component functions. Each component logs its name to the Console panel so the execution order is visible:

```jsx title="App.jsx" startLine="1" continues="bottom"
function NewsHeader() {
  console.log('NewsHeader runs'); // leaf component
  return <header><h1>Town News</h1></header>;
}
function EditorialByline() {
  console.log('EditorialByline runs'); // leaf component
  return <p>By Samantha Robinson</p>;
}
```

`ArticleCard` logs its execution, renders the headline, and nests `<EditorialByline />`:

```jsx title="App.jsx" startLine="9" continues="both"
function ArticleCard() {
  console.log('ArticleCard runs'); // parent of byline
  return (
    <article>
      <h2>City Library Extends Its Hours</h2>
      <EditorialByline /> {/* child of card */}
    </article>
  );
}
```

`MostRead` renders the side box:

```jsx title="App.jsx" startLine="18" continues="both"
function MostRead() {
  console.log('MostRead runs'); // leaf component
  return <aside><h3>Most read</h3></aside>;
}
```

`EditorialFeed` groups `ArticleCard` and `MostRead` inside a `<main>` tag:

```jsx title="App.jsx" startLine="22" continues="both"
function EditorialFeed() {
  console.log('EditorialFeed runs'); // parent of card and most read
  return (
    <main>
      <ArticleCard /> {/* first child */}
      <MostRead /> {/* second child */}
    </main>
  );
}
```

Finally, `App` renders `NewsHeader` and `EditorialFeed` inside a Fragment:

```jsx title="App.jsx" startLine="31" continues="top"
export default function App() {
  console.log('App runs'); // root component
  return (
    <>
      <NewsHeader /> {/* first child */}
      <EditorialFeed /> {/* second child */}
    </>
  );
}
```

The developer saves. The page displays the masthead, the story with its byline, and the side box. In the Console panel, the messages appear in this order: "App runs", "NewsHeader runs", "EditorialFeed runs", "ArticleCard runs", "EditorialByline runs", "MostRead runs".

**I have five components side by side in `App.jsx`. How does React know which goes where?**

---

**ANSWER**

**The code works as written.** The page displays the complete layout, and the Console panel shows that React called the components in the order of the tree, not the order of the file.

The file starts with `NewsHeader` on line 1, but the first message in the console is "App runs". React starts at `App` because `main.jsx` names `<App />`. `App` is the **root** of the tree.

Inside `App`, the return markup names `<NewsHeader />` and `<EditorialFeed />`. Because `App` names them, they are `App`'s **children**, and `App` is their **parent**. `NewsHeader` and `EditorialFeed` share the same parent, so they are **siblings**.

React calls `NewsHeader` first. `NewsHeader` returns native HTML tags (`<header>` and `<h1>`), naming no further components. It is a **leaf** of the tree, so React finishes that branch. Next, React calls `EditorialFeed`. Its markup names `<ArticleCard />` and `<MostRead />`. Before calling `MostRead`, React dives into `ArticleCard`. Inside `ArticleCard`, the markup names `<EditorialByline />`. React calls `EditorialByline`, which is a leaf. Only after completing the entire `ArticleCard` branch does React call its sibling, `MostRead`.

This branching structure is the **render tree**. `App` sits at the root, top-level components branch below it, and leaf components sit at the tips. React keeps this tree as real data in memory, and React Developer Tools draws it in its Components tab, which Lecture 64 explores.

Notice that the render tree holds only React components. The Elements panel in the browser shows only the HTML tags they returned: `<header>`, `<main>`, `<article>`, `<p>`, and `<aside>`. No component names appear in the DOM.

Each component tag creates a distinct place in the tree. If `<ArticleCard />` were named twice inside `EditorialFeed`, React would create two nodes in the tree, and "ArticleCard runs" would print twice. When a component chooses different children based on state, the tree changes from one render to the next, which Lecture 10 teaches. And when components move into separate files that import each other, they form a module dependency tree, which Lecture 8 explores.

```ascii title="The render tree and the call order"
               1. App (root)
              /             \
    2. NewsHeader      3. EditorialFeed
                           /          \
                4. ArticleCard      6. MostRead
                      |
              5. EditorialByline
```

> [!PRINCIPLE]
> **Principle 1: The render tree: each component's markup names its children**
> *We read the components a component's markup names as its children: `App` is the root, each component is the parent of the ones it names, and React calls them from the root down, finishing one branch before the next.*
>
> We might expect React to call components from top to bottom as they appear in the file. But the file order plays no part. React begins at the **root component** named in `main.jsx` and builds the **render tree** by reading which component tags appear inside each component's markup. When a component returns other component tags, those become its **child components**. React calls each child and traverses down that entire branch to its **leaf components** before moving to the next sibling branch. The browser DOM receives only the native HTML tags the components return.
>
> >> root component : the top component in the tree that React mounts into the page
> >> render tree : the hierarchy of components created by nested tags in JSX
> >> child components : components named inside a parent component's markup
> >> leaf components : components at the ends of branches that name no other components
>
> *We should do this:*
> `function ProfilePage() {`
> `  return (`
> `    <>`
> `      <ProfileHeader /> {/* first child branch */}`
> `      <ContactList />   {/* second child branch */}`
> `    </>`
> `  );`
> `}`

### Question 2: One long App shows the same page

A developer considers writing the entire front page as one single `App` component that returns all the markup in a single function:

```jsx title="App.jsx" startLine="1" continues="bottom"
export default function App() {
  return (
    <>
      <header>
        <h1>Town News</h1> {/* masthead in App */}
      </header>
      <main>
        <article>
```

The rest of the markup follows, containing the headline, the byline, and the side box:

```jsx title="App.jsx" startLine="9" continues="top"
          <h2>City Library Extends Its Hours</h2>
          <p>By Samantha Robinson</p> {/* story and byline in App */}
        </article>
        <aside><h3>Most read</h3></aside>
      </main>
    </>
  );
}
```

The developer saves. The page displays the exact same layout as Question 1. Opening the Elements panel reveals the exact same DOM structure: `<header>`, `<main>`, `<article>`, `<p>`, `<aside>`.

**My `App` now holds the whole front page. Should I cut it up, and where?**

---

**ANSWER**

**The code works as written.** React builds the exact same page from one function or from six.

Looking only at the browser screen or the Elements panel, you cannot tell the two files apart. React creates identical DOM elements whether they come from one large component or a tree of smaller ones. So the reason to cut a page into components is for the code and the developers who maintain it, not for the browser.

In one long `App`, a single function handles five distinct jobs at once: the masthead, the list of stories, the individual article, the author line, and the side box. If you need to change how bylines look, you must read through the masthead and side box to find the right lines.

The official documentation in *Thinking in React* starts every app the same way: draw a box around each part of the design and give each box a name. The core rule behind this is **separation of concerns**: giving each piece of code one clear, focused job.

When breaking up a page, create one component for each part of the page that has its own distinct job, nested where that part sits on the page:

- `NewsHeader` holds the masthead.
- `EditorialFeed` organizes the list of stories.
- `ArticleCard` presents one story.
- `EditorialByline` displays the author line.
- `MostRead` handles the side box.

A part of the page deserves its own component whenever it has a distinct job, even if it is used only once. The byline stays a separate component because it represents an independent concern inside every card.

Conversely, do not create a component for every individual tag. An `<h2>` that serves only as the headline of `ArticleCard` stays inside `ArticleCard` until it grows a job of its own. Just as *Thinking in React* keeps a table header inside the table until it develops its own independent logic, keep minor tags inside their parent.

The real cost of keeping everything in one giant `App` becomes obvious in Lecture 6, when each part of the page needs its own data.

```ascii title="Component boundaries drawn around page jobs"
+---------------------------------------------------+
| NewsHeader: masthead ("Town News")                |
+---------------------------------------------------+
| EditorialFeed                                     |
|  +----------------------------+  +--------------+ |
|  | ArticleCard: story         |  | MostRead:    | |
|  |  +-----------------------+ |  | side box     | |
|  |  | EditorialByline       | |  +--------------+ |
|  +--+-----------------------+-+                   |
+---------------------------------------------------+
```

> [!PRINCIPLE]
> **Principle 2: Component boundaries: one branch of the tree for each part of the page with its own job**
> *We give each part of the page with its own job its own component, nested where the part sits on the page, and we keep a small piece inside its parent until it grows a job of its own.*
>
> React produces the identical DOM from one long component or from many small ones. We divide the UI into separate components to practice **separation of concerns**, ensuring each function has one understandable responsibility. Give each section with an independent role its own component, nested where it appears on the page. A component that performs a distinct job is worth creating even if it is rendered in only one place. Keep minor tags inside their parent until they develop independent logic or formatting needs.
>
> >> separation of concerns : organizing code so each component handles one distinct responsibility
>
> *We should do this:*
> `function ProfilePage() {`
> `  return (`
> `    <main>`
> `      <ProfileHeader /> {/* owns name and photo */}`
> `      <ContactList />   {/* owns email and phone */}`
> `    </main>`
> `  );`
> `}`

### Question 3: A child cannot read its parent's variable

Now that the page is cut into components, the developer wants `ArticleCard` to show the newspaper edition name, "Morning". `App` declares `edition` as a local variable:

```jsx title="App.jsx"
function ArticleCard() {
  return (
    <h2>{edition} edition</h2> {/* ReferenceError: edition not defined */}
  );
}
export default function App() {
  const edition = 'Morning'; // local variable inside App
  return <main><ArticleCard /></main>;
}
```

The developer saves. The page crashes and turns completely blank. Opening the Console panel reveals a red error message: `ReferenceError: edition is not defined`. React also logs a message suggesting adding an error boundary to handle rendering failures.

**`ArticleCard` needs the edition that `App` declares. Can it just read it?**

---

**ANSWER**

**The code does not do what we wanted.** `ArticleCard` cannot see a variable declared inside `App`.

Because `<ArticleCard />` appears inside `App`'s return markup, it is tempting to assume that `ArticleCard` can read `App`'s variables, the way a nested JavaScript function reads outer variables.

But a JSX tag is not code inside `App`'s function: it is only an instruction telling React to call `ArticleCard`. Both `ArticleCard` and `App` are defined as separate functions at the top level of the file. As shown in the runway, a variable declared with `const` inside a function exists only in that function's **scope**. When React calls `ArticleCard`, `edition` does not exist in its scope. JavaScript throws a **`ReferenceError`**, and because nothing catches it, the entire page unmounts and goes empty.

Reaching across horizontally to a sibling fails for the exact same reason: `EditorialFeed` cannot read a local variable declared inside its sibling `NewsHeader`.

Reaching across using traditional browser DOM methods fails too. If `NewsHeader` tries to read its neighbor's rendered text using `document.getElementById('edition').textContent`, JavaScript throws:

`TypeError: Cannot read properties of null (reading 'textContent')`

This happens because when React calls `NewsHeader`, the component tree is still being evaluated. No DOM elements exist on the page yet (as Lecture 15 explains in the render and commit lifecycle). Moreover, code that runs while React calls the components must not depend on other components having run, a requirement Lecture 12 explores with pure functions.

Another tempting fix is to declare `ArticleCard` directly inside `App`. While JavaScript function nesting would allow `ArticleCard` to read `edition`, this breaks the core rule from Lecture 2: defining a component inside another component recreates it on every run, resetting its state and destroying what the user typed.

Instead, data in React must flow in one direction: down the tree. A shared value must start above all components that need it.

For a fixed value that the entire file needs and that never changes, the immediate solution within this lesson's scope is to declare `const edition = 'Morning';` at the top level of the file, outside of every function:

```jsx title="App.jsx"
const edition = 'Morning'; // file-level scope
function ArticleCard() {
  return (
    <h2>{edition} edition</h2> {/* reads top-level constant */}
  );
}
```

Now `ArticleCard` displays "Morning edition". When data varies between cards or changes over time, it originates in the closest common parent and travels down through props, which Lecture 6 teaches.

```ascii title="Data flow: downward from above, never across"
[ const edition = 'Morning' ] (top-level file scope)
       |
       +-------------------------------+
       |                               |
       v (reads in scope)              v (reads in scope)
      App                         ArticleCard
       |                               ^
       +--- X (edition is private) ----+
         (cannot read parent variable)
```

> [!PRINCIPLE]
> **Principle 3: Data flow: a value travels down the tree, never across it**
> *We start a value that several components need above all of them and let it travel down the tree; a component never reads a variable of its parent or of its neighbor, and never reads another component's text from the page.*
>
> A component is a top-level function that sees only its own local variables and variables declared at the file level. Writing a component tag inside another component does not share JavaScript **scope**. A child cannot access variables declared inside its parent, and siblings cannot read from each other. DOM lookups like `document.getElementById` fail during rendering because HTML elements do not exist yet. Values that multiple components share must start above them in the hierarchy and travel down.
>
> >> scope : the area of code where a declared variable can be accessed
>
> *We should do this:*
> `const ownerName = 'John Hall'; // top-level file scope`
> `function ProfileHeader() {`
> `  return <h1>{ownerName}</h1>; // reads file scope`
> `}`
> `function ContactList() {`
> `  return <p>{ownerName}</p>; // reads file scope`
> `}`
>
> *We should not do this:*
> `function ProfilePage() {`
> `  const ownerName = 'John Hall'; // private to ProfilePage`
> `  return <ContactList />;`
> `}`
> `function ContactList() {`
> `  return <p>{ownerName}</p>; // ownerName not defined`
> `}`

> [!WILD]
> **Is the render tree the same as the tree of my files?**
> In Lecture 8, we will move each component into its own file, and those files will import one another. It is natural to expect the tree of files to look exactly like the render tree.
> However, these are two distinct trees. The files and their `import` statements form a **module dependency tree**. A build tool or **bundler** (such as Vite) reads the module dependency tree to determine which JavaScript files to bundle and send to the browser. In contrast, the render tree is created at runtime by React as it executes JSX tags and builds the component hierarchy.
> The two trees do not always match. A component can render children that it never imported directly, as Lecture 7 demonstrates when passing nested JSX via the `children` prop. Furthermore, conditional rendering can alter branches of the render tree dynamically while the module dependency tree remains fixed.

This step applies the first principle: The render tree: each component's markup names its children.

The masthead needs a navigation menu, and the page needs a footer. We decide where each sits in the tree: the navigation menu is part of the masthead, so `MainMenu` becomes a child of `NewsHeader`. The footer belongs to the whole page alongside the masthead and feed, so `SiteFooter` becomes a child of `App`, placed directly after `EditorialFeed`.

### Step 3: Finally, we send the edition down to both ends of the tree <App.jsx>

This step applies the third principle: Data flow: a value travels down the tree, never across it.

We want to show the edition name ("Morning") in two places: in the masthead ("Town News, Morning edition") and in the newsletter sign-up ("Get the Morning edition by email."). These two components (`NewsHeader` and `NewsletterBox`) sit at opposite ends of the render tree. If we declared `const edition = 'Morning';` inside `NewsHeader`, `NewsletterBox` could never access it because components cannot read across sibling branches.

What happens if `edition` stays inside `NewsHeader`? React tries to render `NewsletterBox`, finds that `edition` is not defined, attempts the render pass once more (logging each component message twice), throws `ReferenceError: edition is not defined`, and the page goes blank.

Because the edition name is a fixed value that the entire page needs and that does not change between instances, we declare it at the top level of `App.jsx`, on line 1, outside of every component. Adding line 1 pushes every subsequent line down by one, bringing the file to 72 lines.

Line 1 declares the edition constant:

```jsx title="App.jsx" startLine="1"
const edition = 'Morning'; // file-level constant
```

In `NewsHeader`, line 10 reads `{edition}` in the masthead:

```jsx title="App.jsx" startLine="10"
      <h1>Town News, {edition} edition</h1> {/* reads file scope */}
```

In `NewsletterBox`, line 52 reads `{edition}` in the sign-up paragraph:

```jsx title="App.jsx" startLine="52"
  return <p>Get the {edition} edition by email.</p>; // reads file scope
```

Save the file. The page displays "Town News, Morning edition" in the masthead and "Get the Morning edition by email." in the footer. Both ends of the tree successfully read the value. In Lecture 6, when the edition changes dynamically between pages, it will originate in `App` and travel downward as a prop.

### For the interview

> **The Interview Question:** How does React organize nested components into a tree, and why does hierarchy dictate data flow?

**1. The Hidden Signal**

The interviewer wants to hear that you distinguish between code file layout and the runtime render tree, and that you understand why React enforces unidirectional downward data flow. A junior candidate assumes components execute in file order or that functions in the same file can share local state. A senior engineer explains that JSX tags build a hierarchical render tree with `App` at the root, and that React traverses this tree depth-first.

**2. The Classic Trap**

The classic trap is believing that nesting a component tag inside JSX creates a lexical JavaScript closure. Writing `<ArticleCard />` inside `App` does not give `ArticleCard` access to `App`'s local variables; both functions sit at file scope. A second trap is reaching across sibling components using `document.getElementById` during render. Because React evaluates component functions before committing elements to the DOM, querying uncommitted elements returns `null` and crashes execution.

**3. What is Actually Going On**

React builds a tree of component instances based on JSX nesting. React calls the root component first and traverses down each branch, evaluating every child and descendant leaf before moving to the next sibling branch. Because each component is a separate top-level function, its scope is isolated. A component can only access its own local variables, file-level constants, or values passed explicitly from above. Therefore, any data needed by multiple components must originate in their closest common ancestor and flow downward.

**4. Where It Gets Tricky**

*Does the order of component definitions in a file affect the render order?*

No. The file order is completely irrelevant to the render sequence. React begins execution at the root component declared in `main.jsx` and calls child components strictly according to the JSX tree hierarchy.

*If a component tag is written twice in JSX, is it one node or two?*

It creates two distinct nodes in the render tree. React treats each JSX tag invocation as an independent component instance with its own execution and lifecycle, even though both share the same function definition.

*Why can a nested JavaScript function read outer variables, but a child component in JSX cannot?*

A nested function physically sits inside the outer function's body, creating a lexical closure. In contrast, React components are defined as separate top-level functions. Writing `<Child />` in JSX merely creates a React element descriptor; it does not place `Child`'s code inside the parent's function scope.

*Where must a value live if two sibling components need to display it?*

It must live above both of them: either as a file-level constant if it never changes, or in their closest common parent component, passed downward to each sibling via props (Lecture 6) or lifted state (Lecture 23).

### Glossary

- **Render tree**: The runtime hierarchy of React components created by nested component tags in JSX, starting from the root component.
- **Root component**: The top-level component in the render tree that React mounts directly into the browser page container.
- **Parent and child components**: A relationship where a parent component's return markup includes the tag of a child component.
- **Sibling components**: Components that share the same immediate parent component in the render tree.
- **Top-level and leaf components**: Top-level components sit near the root of the tree, while leaf components sit at the tips of branches and render only native HTML tags.
- **Separation of concerns**: The design principle of organizing code so that each component encapsulates exactly one distinct responsibility.
- **Scope**: The physical region of JavaScript code where a declared variable can be accessed.
- **`ReferenceError`**: A JavaScript runtime error thrown when code attempts to access a variable name that has not been declared in the current scope.

### Summary

**The page is a tree of components**

❒ The render tree: each component's markup names its children

➔ ALWAYS determine component hierarchy by reading JSX nesting rather than the order of functions in the file.

➔ NEVER assume components execute in file order; React calls them from the root down, completing one branch before the next.

❒ Component boundaries: one branch of the tree for each part of the page with its own job

➔ ALWAYS extract a separate component for each distinct responsibility, even if used only once.

➔ NEVER create components for every individual HTML tag; keep subordinate markup inside its parent until it develops its own job.

❒ Data flow: a value travels down the tree, never across it

➔ ALWAYS declare shared values above all components that need them and pass them downward.

➔ NEVER attempt to read a parent's local variable, reach across to a sibling, or query uncommitted DOM elements.

**The tree grows by nesting, is cut by job, and carries values down.**

**DO THIS:** compose components in a hierarchy with shared values defined above them

```jsx right
const edition = 'Morning';
function NewsHeader() {
  return <header><h1>Town News, {edition}</h1></header>;
}
function ArticleCard() {
  return <article><p>{edition} edition</p></article>;
}
export default function App() {
  return (
    <>
      <NewsHeader />
      <ArticleCard />
    </>
  );
}
```

**DO NOT DO THIS:** reach across components or declare variables inside parent functions

```jsx wrong
function ArticleCard() {
  return <article><p>{edition} edition</p></article>;
}
export default function App() {
  const edition = 'Morning';
  return (
    <>
      <header><h1>Town News</h1></header>
      <ArticleCard />
    </>
  );
}
```
