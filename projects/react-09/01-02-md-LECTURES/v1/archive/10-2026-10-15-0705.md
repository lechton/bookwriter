### Every web page needs to branch its markup

Every web page needs to adapt its markup to changing data. A shop shows an "Out of Stock" note when an item count reaches zero, an article shows an urgent alert when news breaks, and a discussion section hides comments when they are turned off. In static HTML, all content is permanent and unchanging. In modern applications, data changes constantly based on user actions and server responses. A developer needs a reliable way to show different elements, switch between two options, or render nothing at all.

In plain JavaScript, developers changed visibility by searching the page with `document.getElementById` and adding a CSS class like `hidden`, or setting `style.display = 'none'`. That approach tells the browser what commands to run step by step. In React, a component is a function that returns a description of what the user interface should look like for the current props. You never search the page or toggle classes on DOM nodes yourself. Instead, you write plain JavaScript control flow directly in your component to return the JSX for each case. React compares that description to the page and creates, updates, or removes real DOM nodes to match.

This chapter answers five core questions: **How does React show or hide elements without manual DOM queries?** **How do you protect a component from crashing when data is missing?** **When should you use a ternary operator instead of logical AND?** **Why does a count of zero print a stray zero on the screen?** **How do you organize complex branching without nesting ternaries inside JSX?**

Later in this track, Lecture 11 shows how to render lists of items from arrays, using `{tags.length > 0 && <ul>{tags.map(...)}</ul>}` to guard against empty collections.

- **Lecture 3 (JSX is JavaScript)**: JSX elements are plain JavaScript object descriptions that React turns into living browser DOM nodes.
- **Lecture 4 (JSX expressions)**: Braces inside JSX hold expressions, not statements. Inside braces, booleans, null, and undefined print nothing, while numbers and strings print directly to the screen.
- **Lecture 6 (Passing props)**: A parent passes values down to children as props. Quoted strings pass text, while curly braces pass numbers, booleans, and variables.

### How JavaScript evaluates conditions, operators, and falsy values

In Lecture 4, we learned that curly braces inside JSX open a window where JavaScript evaluates code. However, JavaScript strictly separates **statements** from **expressions**. An expression produces a single value that can be passed to a function or assigned to a variable, such as `2 + 2` or `user.name`. A statement performs an action or controls program flow, such as an `if` block, a `for` loop, or a variable declaration. Because JSX tags compile into function calls, you cannot place an `if` statement directly inside JSX curly braces. For inline branching inside JSX markup, you must use JavaScript expressions.

The **ternary operator** (`? :`) is an inline JavaScript expression that takes three operands. First comes a condition, followed by a question mark (`?`), an expression to evaluate if the condition is truthy, a colon (`:`), and an expression to evaluate if the condition is falsy. For example, `isLive ? <LiveBadge /> : <StaticDate />` checks `isLive`. If `isLive` is true, the expression evaluates to `<LiveBadge />`. If `isLive` is false, it evaluates to `<StaticDate />`. Because the whole ternary evaluates to a single value, it fits cleanly inside JSX curly braces.

The **logical AND operator** (`&&`) evaluates expressions from left to right using **short-circuit evaluation**. If the left side is falsy, JavaScript stops immediately and returns that exact left-hand value without evaluating the right side. If the left side is truthy, JavaScript evaluates and returns the right side. For example, in `isUrgent && <AlertBadge />`, if `isUrgent` is `true`, JavaScript evaluates and returns `<AlertBadge />`. If `isUrgent` is `false`, JavaScript stops and returns `false`.

In JavaScript, values are either **truthy** or **falsy** when tested in a boolean condition. There are six primary falsy values: `false`, `null`, `undefined`, `0`, `NaN`, and the empty string `""`. All other values are truthy, including non-empty strings like `"false"`, objects, and empty arrays `[]`. Because an empty array is truthy, testing `tags && <TagList />` evaluates to true even when `tags` has no items. Testing `tags.length > 0` produces an explicit boolean comparison using `>` that evaluates to `false` when the list is empty.

```jsx title="JavaScript Expressions"
const alert = isUrgent ? <Alert /> : <Normal />; // Ternary picks one of two
const badge = isLive && <LiveBadge />;
const hasTags = tags.length > 0;                 // Explicit boolean comparison
```

### Why React leaves omitted elements out of the browser DOM

When React runs a component function, the browser DOM has not been updated yet. The component executes in JavaScript memory to produce a tree of React elements. If a component attempts to find its own markup using `document.getElementById('comments')`, the browser method returns `null` because that element is not in the page yet. Attempting to call `.classList.add('hidden')` on `null` throws an unhandled `TypeError` that halts execution and causes the whole page to go blank.

In plain HTML, setting `style={{ display: 'none' }}` hides an element visually, but the physical HTML element remains in the browser DOM and accessibility tree, consuming memory and confusing screen readers. In React, conditional rendering uses **DOM omission**: when a condition is false, the component simply does not include that JSX element in its return value. React compares the returned tree against the real page and removes the corresponding node completely, or never creates it in the first place.

When a component receives data through props, that data may be uninitialized or missing. In JavaScript, reading a property on `undefined`, such as `article.title` when `article` is `undefined`, throws a fatal `TypeError: Cannot read properties of undefined (reading 'title')`. In React, an unhandled error during render unmounts the component tree, blanking the application. An **early return** checks for missing data at the very top of the function: `if (!article) return null;`. When a component returns `null`, React renders nothing for that component while leaving the rest of the application intact on screen.

```jsx title="Defensive Early Return"
export default function StoryHeader({ article }) {
  if (!article) {
    return null; // Exits early before reading missing data
  }
  return <h1>{article.title}</h1>; // Safe property access
}
```

### Principles of React: Conditional Rendering

### Question 1: Calling classList in render throws an error

We want to display an article header and hide reader comments when comments are turned off. A developer coming from vanilla JavaScript searches the document and attempts to toggle a CSS class directly:

```jsx title="Imperative Class Mutation"
export default function ArticleHeader({ commentsEnabled }) {
  if (!commentsEnabled) {
    const el = document.getElementById('comments');
    el.classList.add('hidden'); // Query during render
  }
  return (
    <div id="comments">Comments Section</div> {/* Target node */}
  );
}
```

When running this code, the browser halts with `TypeError: Cannot read properties of null (reading 'classList')`, and the whole page goes blank.

**Why does calling classList in the component throw an error?**

---

**ANSWER**

**The code does not work.** The element does not exist in the document while React runs the component function.

While a component runs, React executes the function in JavaScript memory to calculate a tree of element descriptions. The browser DOM has not been updated yet, so `document.getElementById('comments')` finds nothing and returns `null`. Attempting to read `.classList` on `null` throws a fatal `TypeError` that stops rendering and clears the page.

In React, components do not search or mutate DOM nodes directly. Instead, a component branches with plain JavaScript and returns the JSX descriptions for the current case. When the JSX includes an element, React creates the DOM node; when the JSX leaves it out, React creates no node at all.

```ascii title="Imperative DOM query vs declarative JSX branching"
Imperative lookup in render:
Component runs -> getElementById finds null -> classList throws -> blank screen

Declarative JSX branching:
commentsEnabled is false -> JSX omits comments -> React creates zero DOM nodes
```

The fix is to branch directly inside the JSX using logical AND or an early return, returning markup only when comments are enabled.

> [!PRINCIPLE]
> **Principle 1: Return the JSX for the case, and let React add or remove the DOM**
> When a component runs, its elements are not in the browser page yet. Searching the document with getElementById finds null, so calling classList throws an error and blanks the page. In React, a component is a function that returns the JSX for the current case. When the JSX includes an element, React creates the DOM node; when the JSX leaves it out, React performs **DOM omission** and creates no node at all.
>
> >> DOM omission : completely leaving an element out of the rendered DOM tree
>
> *We should do this:*
> `function Card({ showDetails }) {`
> `  return <div>{showDetails && <p>Details</p>}</div>; // adds or omits node`
> `}`
>
> *We should not do this:*
> `function Card({ showDetails }) {`
> `  const el = document.getElementById('details');`
> `  el.classList.add('hidden'); // throws on null`
> `  return <div id="details"><p>Details</p></div>;`
> `}`

### Question 2: Reading properties on missing data blanks the page

An article card component displays story details from an `article` prop. If the story data has not arrived yet from the server, the component receives `undefined` as its prop and attempts to read `article.title`:

```jsx title="Missing Prop Property Access"
export default function StoryCard({ article }) {
  return (
    <article className="card">
      <h2>{article.title}</h2> {/* article is undefined here */}
    </article>
  );
}
```

When this code runs without article data, the console logs `TypeError: Cannot read properties of undefined (reading 'title')`, and every element on the screen vanishes.

**Why does one missing property access clear the entire page?**

---

**ANSWER**

**The code does not work.** Reading a property on undefined throws a fatal JavaScript error that crashes the render pass.

In Lecture 4, we saw that rendering `{undefined}` directly in JSX produces nothing on the screen without crashing. But reading a property on `undefined`, such as `article.title`, is an unhandled JavaScript error. When an error throws during render, React unmounts the entire component tree, leaving the user with a completely blank screen.

The fix is a defensive **early return** placed at the very top of the component function. Checking `if (!article) return null;` intercepts the missing data before any property access occurs. When a component returns `null`, React renders an empty slot for that component, allowing the rest of the application to render safely.

```ascii title="Property read crash vs defensive early return"
Unguarded read:
article is undefined -> article.title throws TypeError -> whole page unmounts

Defensive early return:
article is undefined -> if (!article) return null -> rest of page stays visible
```

When the parent component already knows the data is missing, it can also choose to leave the child component out of its own JSX entirely.

> [!PRINCIPLE]
> **Principle 2: Guard missing data with an early return**
> When a component needs data from a prop, check that the data exists at the start of the function. Reading a property on undefined throws a TypeError that stops rendering and clears the page. Returning **null** or placeholder markup before reading any property lets React finish rendering the rest of the application. When the parent component knows the data is missing, it can omit the child in JSX instead.
>
> >> early return : returning from a component function before reaching the main JSX return
>
> *We should do this:*
> `function Header({ item }) {`
> `  if (!item) return null; // guards before reading property`
> `  return <h1>{item.title}</h1>;`
> `}`
>
> *We should not do this:*
> `function Header({ item }) {`
> `  return <h1>{item.title}</h1>; // throws TypeError on missing item`
> `}`

### Question 3: Choosing between a ternary and logical AND

An article header needs to show an urgent alert banner when a story is urgent, and display a live coverage badge or a published date for ongoing coverage. The developer writes:

```jsx title="Ternary and Logical AND"
export default function HeaderBadges({ isUrgent, isLive, date }) {
  return (
    <div className="badges">
      {isUrgent && <Alert />} {/* Shows badge or nothing */}
      {isLive ? <Live /> : <span>{date}</span>} {/* Picks one of two */}
    </div>
  );
}
```

The alert banner appears only for urgent stories, and the header switches cleanly between the live badge and the timestamp.

**When should you use a ternary operator instead of logical AND?**

---

**ANSWER**

**The code works.** Each operator matches the exact shape of its branch.

The **ternary operator** evaluates to one of two expressions: `condition ? <BranchA /> : <BranchB />`. This makes it the right choice when you must choose between two visible outcomes. The **logical AND** operator evaluates to its right-hand expression when the left side is truthy, and to `false` when the left side is falsy. Because React suppresses `false`, logical AND is the right choice when you want to show an element or render nothing at all.

A common mistake is writing two separate `&&` expressions with opposite conditions to simulate a choice: `{isLive && <LiveBadge />}` and `{!isLive && <StaticDate />}`. This duplicates the condition across two lines. If someone edits one condition and forgets the other, both elements or neither element may appear. When both branches share wrapper markup, branch only the piece that differs, such as `className={'card ' + (isUrgent ? 'urgent' : '')}`.

```ascii title="Branch shape decides the operator"
Binary Choice (Branch A or Branch B):
isLive ? <LiveBadge /> : <StaticDate />  -> exactly one element renders

Show-or-Nothing (Branch A or Nothing):
isUrgent && <AlertBadge />  -> badge when true, false suppressed when false
```

> [!PRINCIPLE]
> **Principle 3: A ternary picks one of two, and && shows one or nothing**
> Use the ternary operator to choose between two different elements, and use logical AND to show one element or nothing. In JSX, a **ternary operator** evaluates to one of its two branches. The **logical AND** operator evaluates to its right-hand element when true, and to false when false, which React leaves out of the page. When two branches share common markup, branch only the piece that changes.
>
> >> ternary operator : an inline operator that evaluates a condition and chooses between two values
> >> logical AND : an operator that evaluates to the right side when the left side is truthy
>
> *We should do this:*
> `{isLive ? <LiveBadge /> : <StaticDate />} // chooses one of two`
> `{isUrgent && <AlertBadge />} // shows badge or nothing`

### Question 4: An unread counter of 0 prints a raw 0 on screen

An article card component displays an unread comment badge using the logical AND operator:

```jsx title="Unread Counter Short Circuit"
export default function CommentCounter({ count }) {
  return (
    <div className="counter-box">
      {count && <p>{count} Comments</p>} {/* count is 0 here */}
    </div>
  );
}
```

When a story has 5 comments, the badge displays "5 Comments". But when a story has `0` comments, the screen displays a literal, stray `"0"` right where the badge should be.

**Why does a count of zero print a raw 0 onto the page?**

---

**ANSWER**

**The code does not work.** The logical AND operator returns 0, and React renders numbers as visible text.

In JavaScript, `&&` short-circuits and returns its left side whenever that side is falsy. When `count` is `0`, JavaScript evaluates `0 && <Badge />` to `0`, not to `false`. React suppresses booleans (`false`, `true`), `null`, and `undefined`, but it treats numbers as legitimate user content and renders them as real browser text nodes. Therefore, React creates a DOM text node containing `"0"` and paints it onto the screen.

The exact same issue occurs with `NaN`, which prints `"NaN"` on screen and triggers a console warning. Furthermore, non-empty strings like `"false"` and empty arrays `[]` are truthy in JavaScript, so `isUrgent="false"` and `tags && <TagList />` both display their elements.

```ascii title="Short-circuit evaluation of 0 vs comparison"
Raw number 0:
count is 0 -> 0 && <Badge /> returns 0 -> React renders text node "0"

Explicit boolean comparison:
count is 0 -> count > 0 is false -> false && <Badge /> returns false (omitted)
```

The fix is to convert the numeric check into an explicit boolean comparison by writing `{count > 0 && <p>{count} Comments</p>}`. Comparing `count > 0` produces `false` when count is zero, which React suppresses completely.

> [!PRINCIPLE]
> **Principle 4: Put a boolean on the left of &&, never a number**
> The logical AND operator returns its left side whenever that side is falsy. In JavaScript, 0 is falsy, so 0 on the left evaluates to the number 0. React leaves booleans, null, and undefined out of the page, but it renders numbers as visible text. A condition with 0 prints a **stray zero** on the screen. Compare numbers with zero using a comparison operator so the left side is always a real boolean.
>
> >> stray zero : an unwanted 0 displayed on screen when a numeric zero short-circuits in JSX
>
> *We should do this:*
> `function Card({ count }) {`
> `  return <div>{count > 0 && <Badge />}</div>; // prints nothing`
> `}`
>
> *We should not do this:*
> `function Card({ count }) {`
> `  return <div>{count && <Badge />}</div>; // 0 prints on page`
> `}`

### Question 5: Branching across multiple states nests ternaries

An article header needs to show an urgent alert badge, a live coverage badge, or nothing at all. The developer chains ternaries inside JSX:

```jsx title="Nested Ternaries in JSX"
export default function StatusHeader({ isUrgent, isLive, title }) {
  return (
    <header>
      {isUrgent ? <Alert /> : isLive ? <Live /> : null} {/* Nested ternaries */}
      <h1>{title}</h1>
    </header>
  );
}
```

The code runs and displays the correct badge, but code reviewers flag the nested ternaries as difficult to read and maintain.

**How do you branch across several conditions without nesting ternaries in JSX?**

---

**ANSWER**

**The code works.** The nested ternaries evaluate correctly, but they make the template difficult to read.

Curly braces inside JSX hold only a single expression, so handling three or more branches inline forces you to chain multiple ternary operators. Matching each question mark to its colon requires mental effort, and adding another branch requires editing a fragile expression.

Because JSX elements are plain JavaScript objects in memory, you can move branching above the `return` statement using standard `let` variables and `if/else` statements. You declare a variable such as `let badge = null;`, set it using plain JavaScript statements, and embed `{badge}` once inside your returned markup.

```ascii title="Nested inline ternaries vs extracted variable above return"
Nested inline ternaries:
{isUrgent ? <Alert /> : isLive ? <Live /> : null}  (hard to scan and edit)

Extracted variable above return:
let badge = null;
if (isUrgent) badge = <Alert />;
else if (isLive) badge = <Live />;
return <header>{badge}<h1>{title}</h1></header>;  (clean, readable, flat)
```

Simple binary choices and short show-or-nothing checks stay inline inside JSX. When branching logic outgrows a single clean expression, extract the logic above the `return` statement.

> [!PRINCIPLE]
> **Principle 5: Move complex branching above the return**
> Braces inside JSX hold a single expression, so handling several cases inline creates nested ternaries that are hard to read. Move multi-case branching above the return statement using standard if statements and a **local variable**. Assign the chosen JSX element to that variable, and place the variable inside your markup once. Simple binary choices and short show-or-nothing checks stay inline.
>
> >> local variable : a variable declared with let or const inside the component function
>
> *It is best practice to do this:*
> `let badge = null;`
> `if (isUrgent) badge = <AlertBadge />;`
> `else if (isLive) badge = <LiveBadge />;`
> `return <header>{badge}<h1>{title}</h1></header>; // clean placement`

### Step 1: First, we construct the parent container <src/App.jsx>

Step 1 constructs the parent container: `App.jsx` acts as the orchestrator for our feature. In production applications, data arrives with varying shapes and flags: some stories are urgent alerts, some have live updates, some have positive comment counts, and others have zero comments. To exercise our conditional branches, `App` defines two representative story objects: `urgentStory` (an urgent story with live status and 18 comments) and `standardStory` (a standard story with zero comments). Notice how `App` mounts two separate `<ArticleHeader />` components, passing different props to each without requiring state hooks.

```jsx title="App.jsx" startLine="1" continues="bottom"
import ArticleHeader from './components/ArticleHeader.jsx'; // Child header

export default function App() {
  const urgentStory = {
    title: 'City Opens New Central Library',
    isUrgent: true, // Urgent alert flag
    isLive: true,   // Active coverage flag
    commentCount: 18,
    date: '10:30 AM'
  };
```

The breaking story fixture sets `isUrgent` and `isLive` to true, and provides a positive comment count to trigger all active badges.

```jsx title="App.jsx" startLine="11" continues="both"
  const standardStory = {
    title: 'Downtown Farmers Market Expands',
    isUrgent: false,
    isLive: false,
    commentCount: 0, // Zero count verifies stray zero avoidance
```

The standard story fixture sets `commentCount` to 0, providing the critical test case that verifies whether our header avoids the stray zero bug.


Notice how `App` acts as the orchestrator. It holds the data fixtures and renders `ArticleHeader` twice with different inputs. By passing contrasting props down the tree, `App` exercises both sides of every conditional branch without requiring dynamic state hooks.

### Step 2: Next, we build the conditional header <src/components/ArticleHeader.jsx>

Step 2 builds the core conditional header: `ArticleHeader.jsx` unites all five principles in a single cohesive component. First, it places an early return at the top (`if (!article) return null;`) to guard against uninitialized data. Second, it extracts topic badge logic before the `return` statement using standard `if` statements and a `let topicBadge` variable, avoiding nested inline ternaries. Third, inside the JSX markup, it uses logical AND with an explicit boolean check (`isUrgent && ...`) to show an urgent banner. Fourth, it uses a ternary operator (`isLive ? <LiveIndicator /> : <span>{date}</span>`) to choose between live status and a static timestamp. Finally, it uses an explicit boolean comparison (`commentCount > 0 && ...`) to render comments only when the count exceeds zero, eliminating the stray zero bug.

```jsx title="ArticleHeader.jsx" startLine="1" continues="bottom"
import LiveIndicator from './LiveIndicator.jsx'; // Child badge

export default function ArticleHeader({ article }) {
  if (!article) {
    return null; // Principle 2: guards missing data
  }
  const { title, isUrgent, isLive, commentCount, date } = article;
```

The defensive guard intercepts uninitialized data on line 4, eliminating property access crashes before reading `title` or `date`.

```jsx title="ArticleHeader.jsx" startLine="8" continues="both"
  let topicBadge = null; // Principle 5: precomputes badge
  if (isUrgent) {
    topicBadge = <span className="badge urgent">URGENT ALERT</span>;
  }

  return (
    <header className="article-header">
      <div className="badge-row">
```

Preparing `topicBadge` before entering the return statement resolves the conditional alert in plain JavaScript, avoiding nested ternaries inside JSX.

```jsx title="ArticleHeader.jsx" startLine="17" continues="top"
        {topicBadge}
        {isLive ? <LiveIndicator /> : <span className="date">{date}</span>}
      </div>
      <h1 className="title">{title}</h1>
      {commentCount > 0 && ( // Principle 4: explicit boolean guard
        <span className="comments">{commentCount} Comments</span>
      )}
    </header>
  );
}
```

The ternary expression cleanly chooses between the live badge and the date. Below it, `commentCount > 0` evaluates to false when zero comments exist, suppressing the counter completely without displaying a stray zero.

Step 3 constructs the leaf presentation component: `LiveIndicator.jsx` encapsulates the visual markup and animated indicator for active live coverage. Declarative conditional rendering fundamentally changes how developers build dynamic interfaces. Instead of mutating the DOM after elements are created, React components describe exactly which elements should exist for any given combination of props. By using early returns for missing data, ternaries for binary choices, boolean-guarded logical AND operators for show-or-nothing branches, and variables for complex logic, you build user interfaces that are predictable, resilient to edge cases, and completely free of stray zeroes or layout flickering.

### Where you will meet this

1. **Authentication and Navigation Bars**: When building site headers, you conditionally render login buttons for guest visitors, user avatars for signed-in members, and administrative links for staff using ternary operators.
2. **Defensive API Data Consumption**: When fetching articles, profiles, or product records from a remote server, you protect components against uninitialized data during initial page load using early returns (`if (!data) return <p>Loading...</p>;`).
3. **Notification Badges and Cart Counters**: When displaying notification counters, message alerts, or shopping cart item totals, you guard numeric values with explicit comparisons (`unreadCount > 0 && <Badge />`) to eliminate the stray zero bug.

### For the interview

> **The Interview Question:** How do you show, hide, or switch JSX based on a condition?

**1. The Hidden Signal**

The interviewer is not asking whether you know the syntax of an if statement or a question mark. They are probing whether you understand how React manages the browser DOM declaratively. A junior candidate talks about toggling CSS classes with document queries. A senior engineer explains that components are pure functions of props and state: React renders what the returned JSX describes, and omits what the JSX leaves out. They immediately highlight the difference between expressions and statements inside JSX braces, explain how React treats falsy values, and address the stray zero trap.

**2. The Classic Trap**

The most famous trap is writing `{count && <Badge />}` with a numeric zero. Candidates assume that because 0 is falsy in JavaScript, React will render nothing. But in JavaScript, `0 && <Component />` returns `0`. React suppresses booleans, null, and undefined, but it treats numbers as visible user content and renders a literal "0" onto the physical screen. Another classic trap is using two separate inverted `&&` expressions (`{isLive && <A />}` and `{!isLive && <B />}`) to simulate an if/else branch, which duplicates the condition and causes visual desynchronization when conditions drift.

**3. What is Actually Going On**

In React, conditional rendering uses standard JavaScript control flow. Braces inside JSX open an expression window, so an `if` statement cannot live directly inside markup. For a binary choice between two elements, use a ternary: `{isLive ? <LiveBadge /> : <StaticDate />}`. For a show-or-nothing element, use logical AND: `{isUrgent && <AlertBadge />}`.
When a condition evaluates to false, React leaves that element out of the tree entirely; it produces zero DOM nodes, meaning the element is never created in the browser page. When data may be uninitialized, place an early return `if (!data) return null;` at the top of the component to prevent property read crashes. When logic has three or more cases, move branching above the `return` statement into standard `if` statements and a `let` variable.

**4. Where It Gets Tricky**

*What happens if you pass a quoted string like `isUrgent="false"` to a component?*
In JavaScript, all non-empty strings are truthy. Writing `isUrgent="false"` passes the literal string `"false"`, so `{isUrgent && <Alert />}` evaluates to true and shows the alert. To pass a real boolean, you must use curly braces: `isUrgent={false}`.

*What happens if an uninitialized calculation produces NaN?*
In JavaScript, `NaN` is falsy. But like `0`, `NaN && <Component />` returns `NaN`. React prints `"NaN"` directly onto the screen and logs a console warning. Always guard calculations with `!Number.isNaN(val) && val > 0`.

*What happens if you check an empty array with `tags && <TagList />`?*
In JavaScript, an empty array `[]` is an object, and all objects are truthy. Even with zero items, `tags && <TagList />` evaluates to true, mounting `<TagList />` with an empty collection. Always check length: `tags.length > 0 && <TagList />`.

### Glossary

- **Conditional Rendering**: The technique of displaying, hiding, or alternating user interface markup based on JavaScript conditions and props.
- **Early Return**: Exiting a component function early with null or fallback markup before executing the main JSX return.
- **Ternary Operator**: A JavaScript inline operator (`? :`) that evaluates a condition and chooses between two alternative expressions.
- **Short-Circuit Evaluation**: The evaluation model where logical AND (`&&`) stops and returns the left operand immediately if it is falsy.
- **Suppression Whitelist**: React's built-in rule that renders zero DOM nodes for booleans (`true`, `false`), `null`, and `undefined`.
- **Stray Zero**: An unwanted 0 displayed on the screen when a numeric zero short-circuits on the left side of logical AND.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Operator Selection & Branch Shape

➔ ALWAYS use logical AND (`&&`) for show-or-nothing branches, and use the ternary operator (`? :`) when choosing between two alternate elements.

➔ NEVER use two separate inverted `&&` expressions (`{isLive && ...}{!isLive && ...}`) to simulate an if/else choice.

❒ Numeric Guarding & Falsy Safety

➔ ALWAYS convert numbers to explicit booleans (`count > 0 && ...`) before using the `&&` operator to prevent the stray zero bug.

➔ NEVER place a raw numeric counter or unverified calculation on the left side of `&&`.

❒ Complexity Management & DOM Ownership

➔ IF branching logic exceeds one clean expression THEN move the calculation before the `return` statement using standard `if` statements and a variable.

➔ NEVER manipulate CSS classes or styles imperatively using `classList` on DOM elements managed by React.

**DO THIS:** guard numeric values with explicit boolean comparisons

```jsx right
{commentCount > 0 && (
  <span className="comments">{commentCount} Comments</span>
)}
```

**DO NOT DO THIS:** pass raw numeric counters to logical AND operators

```jsx wrong
{commentCount && (
  <span className="comments">{commentCount} Comments</span>
)}
```
