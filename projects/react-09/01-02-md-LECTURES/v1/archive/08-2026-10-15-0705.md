# Lecture 8: Splitting Components with ES Module Imports and Exports
> INTERVIEW QUESTION | ❱ CORE | How do you split components across files, and how do default and named imports differ?

1. You built an article card component and a badge helper inside App.jsx.
2. You move the card to its own file, but the screen is blank and the card is not defined.
3. How do we share components cleanly across files with default and named imports?

### Splitting components across files keeps each file easy to scan

Since Lecture 5, every component you write lives in one file, `App.jsx`. The card and the page that shows it sit side by side, so `App` uses `ArticleCard` simply by writing its tag:

```jsx title="App.jsx"
function ArticleCard({ title }) {
  return <article className="card">{title}</article>; // declared in this file
}
export default function App() {
  return <ArticleCard title="New Park Opens" />; // used without an import
}
```

As the site grows, that one file grows with it. The card, the badge, the header, and the footer all end up in the same long `App.jsx`, and another page that needs the card cannot reach it without copying its code. So every React developer meets the same question: how does a component written in one file get used in another file?

JavaScript answers it with **ES modules**, the module system built into the language (ES stands for ECMAScript, the official name of JavaScript). Each file is a **module**: the names declared in it stay inside that file until the file exports them and another file imports them.

Your project's code lives in a folder named `src`, and `App.jsx` sits inside it. When a component moves out, it goes into a folder named `components` that sits inside `src`, next to `App.jsx`:

```files title="Project folders: File Explorer"
src/
  App.jsx | parent | The starter file, which imports the card by its path
  components/
    ArticleCard.jsx | child | The card component, moved into its own file
```

You move the card into its own file, `ArticleCard.jsx`, and export it from there:

```jsx title="ArticleCard.jsx"
export default function ArticleCard({ title }) {
  return <article className="card">{title}</article>; // exported component
}
```

And `App.jsx` imports it by its path:

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // imported from file

export default function App() {
  return <ArticleCard title="New Park Opens" />; // rendered in page shell
}
```

The card is the same function as before; only its place changed. In one file, `App` could use it directly. Across two files, `ArticleCard.jsx` must export it and `App.jsx` must import it, because each module keeps its names private by default.

Later in this track, Lecture 9 shows how main.jsx imports App and hands it to createRoot to attach the React tree to the browser DOM, and Lecture 12 shows why variables declared at the top level of a module must never be mutated during render.

In this chapter, we move components out of `App.jsx` into their own module files so each component can be reused anywhere in the application. We will see why moving a component without importing it blanks the page, how default and named imports differ in syntax and behavior, and how to choose the right export style for primary components and helper utilities.

This lesson answers three questions:

- **How do you move a component into its own file and make it available to other files?**
- **How do default imports and named imports differ in syntax and behavior?**
- **When should a component be exported as a default export versus a named export?**

The questions stand on six earlier lessons:

- **Lecture 2 (Component anatomy)**: A React component is a JavaScript function that starts with a capital letter and returns markup. The `export default` syntax marks the main function of a file so another file can import and run it.
- **Lecture 3 (JSX)**: JSX tags compile into element descriptors. Attributes like `aria-label` keep their dashes, and the HTML `class` attribute is written as `className`.
- **Lecture 4 (Values in JSX)**: Curly braces evaluate JavaScript expressions inside markup. Values like `null`, `undefined`, and `false` render nothing on screen.
- **Lecture 5 (The component tree)**: Nesting component tags inside JSX builds the tree of elements on the page. A component nested in JSX must be in scope, or JavaScript halts with a `ReferenceError`.
- **Lecture 6 (Props)**: Attributes on a component tag arrive as a single props object, and curly braces in the parameter list unpack its keys. Props are read-only inputs.
- **Lecture 7 (Container composition)**: Content written between opening and closing tags arrives as the `children` prop. Prop spreading forwards remaining attributes with the rest syntax `...rest`.

### A module keeps its names private until you export them

We know from Lecture 5 that when two functions are declared in the same file, one function can call the other directly because both exist in the same scope. In modern JavaScript and React, every separate file is an isolated **module**. Variables, functions, and components declared inside a module are private to that file:

```jsx title="ArticleCard.jsx"
function formatDate(date) { // private helper function
  return `Published ${date}`;
}

export default function ArticleCard({ date }) {
  return <p>{formatDate(date)}</p>; // helper called inside file
}
```

Notice that `formatDate` has no `export` keyword in front of its declaration. That means `formatDate` is completely private to `ArticleCard.jsx`. External files cannot read, call, or modify it. Only `ArticleCard` is marked with `export default`, so only `ArticleCard` crosses the module boundary.

To import a component from a file in your project, you specify a **relative path** starting with `./`. The `./` tells the build tool to look for the file starting from the folder of the current file:

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // relative file path

export default function App() {
  return <ArticleCard date="Monday" />; // renders imported card
}
```

In contrast, a **package import** like `import { Fragment } from 'react'` has no `./` prefix. When a path has no `./` or `../`, the build tool looks inside the installed packages in the project's `node_modules` folder rather than your local source files.

### Default exports share one main value, named exports share several

In Lecture 2, we used `export default` to share the main component from `App.jsx`. JavaScript provides two primary ways to export values from a module: **default exports** and **named exports**. A default export represents the primary component of a file, declared with `export default`. A file can have at most one default export. In contrast, named exports allow a module to share multiple secondary helpers or utilities, declared with `export function Name()`:

```jsx title="ArticleCard.jsx"
export default function ArticleCard({ title }) { // primary default export
  return <article className="card">{title}</article>;
}

export function Badge({ text }) { // secondary named export
  return <span className="badge">{text}</span>;
}
```

How you export a value dictates how you must import it. A **default import** is written without curly braces: `import ArticleCard from './ArticleCard.jsx'`. Because a file has only one default export, you can give it any local variable name. A **named import** is written with curly braces: `import { Badge } from './ArticleCard.jsx'`. The identifier inside the braces must match the exported name character for character:

```jsx title="App.jsx"
import ArticleCard, { Badge } from './components/ArticleCard.jsx'; // combined

export default function App() {
  return (
    <ArticleCard title="News">
      <Badge text="LIVE" /> {/* uses named helper */}
    </ArticleCard>
  );
}
```

Notice the curly braces in `import { Badge }`. In JavaScript, these braces look similar to object destructuring, but they are a static module syntax. They tell the JavaScript engine to link directly to the specific named export binding declared in that module. Unlike runtime object destructuring, ES module import bindings are evaluated and linked statically before any component function executes.

### Principles of React: Splitting Components with Imports and Exports

### Question 1: Moving a component to a new file leaves the screen blank

You have a working article feed where `ArticleCard` is rendered inside `App.jsx`. To organize your code, you create a new file named `src/components/ArticleCard.jsx`, move the card function into it, and export it with `export default`. In `App.jsx`, you keep the card tag in your markup:

```jsx title="App.jsx"
export default function App() {
  return (
    <main>
      <ArticleCard title="Park Opens" /> {/* card tag in markup */}
    </main>
  );
}
```

You refresh the browser. The page is completely blank. When you open the browser development console, you see a red error message: `ReferenceError: ArticleCard is not defined`.

**Why does the screen go blank when the component exists in another file in the same project?**

---

**ANSWER**

**The code does not do what we wanted.** Files in a project do not share variables automatically.

In plain HTML scripts, any variable declared in one script tag often lands on the global window object, where other scripts can reach it. In modern JavaScript and React, each file is an isolated module. Variables and component functions declared inside a file stay private to that file. Even though `ArticleCard.jsx` sits in the same project folder, `App.jsx` has no access to it by default.

When React attempts to render the `App` component, JavaScript evaluates the identifier `ArticleCard`. Because there is no variable, parameter, or import named `ArticleCard` in `App.jsx`, JavaScript halts execution and throws a `ReferenceError`. As Lecture 5 showed, an unhandled error during component execution stops the render, causing React to render nothing and leaving the screen blank.

To fix this error, you add an explicit import statement at the top of `App.jsx`:

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // bridges the module

export default function App() {
  return <ArticleCard title="Park Opens" />; // in scope and renders
}
```

```ascii title="Module boundaries and the import bridge"
+-------------------------------+      +-------------------------------+
| src/components/ArticleCard.jsx|      | src/App.jsx                   |
|                               |      |                               |
| export default function       |      | import ArticleCard from       |
|   ArticleCard()               | ===> |   './components/ArticleCard'  |
|                               |      |                               |
| function formatDate()         |      | function App() {              |
|   (private to module)         |      |   return <ArticleCard />      |
+-------------------------------+      +-------------------------------+
```

Notice what happens to top-level code versus component code. Code written at the top level of a module evaluates once when the file is first imported, regardless of how many other files import it. In contrast, code inside the component function runs on every render for every card instance on screen.

> [!PRINCIPLE]
> **Principle 1: Each file is a module, and names cross files only by export and import**
> When React runs an application, each file is an isolated **module** with its own private scope. Functions, variables, and components declared in a file are not visible to other files by default. A component crosses into another file only when the source file exports it and the destination file imports it. Without an import statement, referencing a component from another file throws a `ReferenceError` during render, leaving the page blank.
>
> >> module : an isolated file with private scope that exposes values only through explicit exports and imports
>
> *We should do this:*
> `import ArticleCard from './components/ArticleCard.jsx';`
> `export default function App() {`
> `  return <ArticleCard />; // renders imported card`
> `}`
>
> *We should not do this:*
> `// App.jsx without import statement`
> `export default function App() {`
> `  return <ArticleCard />; // ReferenceError: not defined`
> `}`

In our runtime test with Vite 8.3.4, moving `ArticleCard` without an import produced a blank page with `ReferenceError: ArticleCard is not defined` in the browser console. Adding the import statement restored the rendered cards immediately.

### Question 2: Importing a named export without braces stops the build

You have extracted `ArticleCard.jsx`. The file provides two components: `ArticleCard` as its default export, and `Badge` as a named export: `export function Badge({ text })`. In `App.jsx`, a developer wants to use the badge. They write the import statement without curly braces:

```jsx title="App.jsx"
import Badge from './components/ArticleCard.jsx'; // wrote default import syntax

export default function App() {
  return <Badge text="Breaking" />; // attempts to render badge
}
```

When you save the file, the development server stops. The browser displays a build error overlay: `The requested module '/src/components/ArticleCard.jsx' does not provide an export named 'default'`. When you run `npm run build`, the production bundler halts with `[MISSING_EXPORT] "default" is not exported by "src/components/ArticleCard.jsx"`.

**Why does importing the badge without braces fail before any component runs?**

---

**ANSWER**

**The code does not do what we wanted.** A default import requests the module's default export, not a named export.

JavaScript ES modules resolve and verify import bindings statically before any component executes. When you write `import Badge from './components/ArticleCard.jsx'` without curly braces, you are writing a default import. You are asking the JavaScript engine for the single default export of `ArticleCard.jsx`, and asking it to bind that value to the local variable name `Badge`.

However, `ArticleCard.jsx` exported `ArticleCard` as its default export, and exported `Badge` as a named export. The file has no export named `default` that corresponds to `Badge`. Because static module verification happens before runtime, Vite detects that the requested default binding does not exist and halts immediately.

The mirror mistake fails the same way. If you write `import { ArticleCard } from './components/ArticleCard.jsx'` with curly braces, the JavaScript engine looks for a named export called `ArticleCard`. Because `ArticleCard` was exported as `default`, the engine reports: `The requested module '/src/components/ArticleCard.jsx' does not provide an export named 'ArticleCard'`.

```ascii title="Matching import syntax to export declaration"
EXPORT DECLARATION (ArticleCard.jsx):
  export default function ArticleCard()
  export function Badge()

MATCHING IMPORT STATEMENT (App.jsx):
  import ArticleCard from './ArticleCard.jsx'  (no braces: links to default)
  import { Badge } from './ArticleCard.jsx'    (braces: links to named)
```

The fix is to match the import syntax to the export declaration. Use a default import without curly braces for `ArticleCard`, and a named import with curly braces for `Badge`:

```jsx title="App.jsx"
import ArticleCard, { Badge } from './components/ArticleCard.jsx'; // matched

export default function App() {
  return (
    <ArticleCard title="News">
      <Badge text="Breaking" /> {/* renders correctly */}
    </ArticleCard>
  );
}
```

> [!PRINCIPLE]
> **Principle 2: Import with the same form the file used to export**
> JavaScript ES modules link imports to exports statically before any component executes. A **default export** must be imported without curly braces, and the importing file can assign it any local name. A **named export** must be imported with curly braces, and its name must match the exported identifier character for character. If the import syntax does not match the export declaration, the module fails to link, halting the development server and production build.
>
> >> default export : the primary value of a module, imported without curly braces under any local name
> >> named export : a specific value exported by name, imported inside curly braces matching its exact identifier
>
> *We should do this:*
> `import ArticleCard, { Badge } from './Card.jsx'; // imports both`
> `<ArticleCard><Badge text="LIVE" /></ArticleCard>; // renders both`
>
> *We should not do this:*
> `import { ArticleCard } from './Card.jsx'; // wrong for default`
> `import Badge from './Card.jsx'; // wrong for named export`

In our runtime test with Vite 8.3.4, importing a named export without braces halted the dev server with `does not provide an export named 'default'`, while `vite build` stopped with `[MISSING_EXPORT]`. Adding curly braces `{ Badge }` resolved both errors.

### Question 3: Adding a second default export to a file halts compilation

Inside `src/components/ArticleCard.jsx`, `ArticleCard` is already exported with `export default function ArticleCard`. Now you want other pages to use `Badge` as well. You write `export default` in front of `Badge`:

```jsx title="ArticleCard.jsx"
export default function ArticleCard({ title }) { // first default export
  return <article className="card">{title}</article>;
}

export default function Badge({ text }) { // second default export attempt
  return <span className="badge">{text}</span>;
}
```

When you save the file, the compiler halts immediately with a syntax error: `A module cannot have multiple default exports`.

**Why does adding a second default export stop the compiler?**

---

**ANSWER**

**The code does not do what we wanted.** A module can have at most one default export.

In the ECMAScript module specification, the default export is designed to represent the single fallback value of a module. When another file writes `import Anything from './components/ArticleCard.jsx'`, the runtime assigns the default export to the identifier `Anything`. If a file were allowed to have two default exports, the runtime would have no way to determine which of the two values to provide to the importing file. Therefore, JavaScript forbids multiple default exports at the syntax level.

When a file provides one main component alongside secondary helpers, the idiomatic convention is to export the main component as the default export, and export all secondary helpers as named exports:

```jsx title="ArticleCard.jsx"
export default function ArticleCard({ title }) { // primary default export
  return <article className="card">{title}</article>;
}

export function Badge({ text }) { // secondary named export
  return <span className="badge">{text}</span>;
}
```

```ascii title="Module export slots: one default, unlimited named"
+-------------------------------------------------------------+
| Module Export Table (ArticleCard.jsx)                       |
|                                                             |
| [default slot]  ======> ArticleCard                         |
|                         (at most one default per module)    |
|                                                             |
| [named slots]   ======> Badge                               |
|                 ======> formatDate (if exported)           |
|                         (unlimited named exports allowed)   |
+-------------------------------------------------------------+
```

Always give your component functions explicit names. If you write an anonymous default export like `export default () => {}`, the component has no name. When a runtime error occurs, React's error stack prints `The above error occurred in the <default> component:`, and React DevTools displays `<default>` instead of a recognizable component name, making debugging difficult.

> [!PRINCIPLE]
> **Principle 3: One default export for the main component, named exports for the rest**
> An ES module allows at most one **default export** but any number of **named exports**. When a file provides one primary component, export that component as the default export so callers can import it cleanly. When that same file provides secondary helpers or sub-components that other files also use, export them as named exports. If a file contains two default exports, the compiler stops immediately. Always name your component functions, because an anonymous default export displays as `<default>` in error callstacks and React DevTools.
>
> >> anonymous component : a component function declared without a name identifier in its definition
>
> *We should do this:*
> `export default function ArticleCard() {} // primary component`
> `export function Badge({ text }) {} // secondary named helper`
>
> *We should not do this:*
> `export default function ArticleCard() {} // first default export`
> `export default function Badge({ text }) {} // duplicate default fails`

In our runtime test, attempting to declare two default exports in one module stopped the build with `A module cannot have multiple default exports`. Exporting `Badge` as a named export allowed both components to compile and render cleanly.

### Step 1: First, we extract the primary card component <ArticleCard.jsx>

We begin by creating a new file on disk: `src/components/ArticleCard.jsx`. Instead of trapping the card inside `App.jsx`, we declare `ArticleCard` as a standalone component function. We place a top-level log at the head of the file to observe when the module evaluates. We also create a private helper function, `formatDate`, that formats publication dates. Because `formatDate` is only used inside this card, we keep it unexported, ensuring it remains an internal implementation detail:

```jsx title="ArticleCard.jsx" startLine="1" continues="bottom"
console.log('ArticleCard loaded'); // runs once on import

function formatDate(date) { // private helper unexported
  return `Published ${date}`;
}

export default function ArticleCard({ title, date, children }) {
  return (
    <article className="article-card"> {/* card container */}
      <p className="card-date">{formatDate(date)}</p>
```

Notice the architecture of this first step. The file opens with a top-level log that executes only once when the module is imported into memory. The `formatDate` helper function is declared without an `export` keyword, so it remains completely private to `ArticleCard.jsx`. External files cannot call or modify it. Finally, `ArticleCard` is declared as a named function declaration with `export default function ArticleCard`. This ensures that any React runtime error inside this component will clearly display `<ArticleCard>` in callstacks.

### Step 2: Next, we export the status badge as a named export <ArticleCard.jsx>

We complete `ArticleCard.jsx` by rendering the card title and nested content, and then adding a secondary component: `Badge`. Some pages in our application only need to display a status badge without rendering a full article card. When designing a module that contains related sub-components, developers face an architectural crossroad:

- **Option 1 (The Single-Export File Shredding Way)**: Extract every single two-line helper into its own file (`Badge.jsx`, `DateLabel.jsx`), creating dozens of tiny files and cluttered import lists.
- **Option 2 (The Multi-Export Module Way)**: Keep the primary component as the default export and export closely related sub-components as named exports from the same file.

First, examine Option 1 with excessive file shredding:

```jsx title="Option 1: Over-Shredded Helper Files"
export default function Badge({ text }) { // two-line component file
  return <span className="badge">{text}</span>;
}
```

In Option 1, every tiny tag requires a separate file on disk, bloating your folder hierarchy and forcing parent components to manage numerous separate import statements.

In Option 2, `ArticleCard.jsx` exports its primary card as default and provides `Badge` as a named export from that same module:

```jsx title="ArticleCard.jsx" startLine="10" continues="top"
      <h2 className="card-title">{title}</h2>
      <div className="card-body">{children}</div>
    </article>
  );
}

export function Badge({ text }) { // secondary utility as named export
  return <span className="status-badge">{text}</span>;
}
```

Notice what Option 2 accomplishes. The primary job of `ArticleCard.jsx` is still the article card, so it remains the default export. But by exporting `Badge` with `export function Badge`, the file allows other pages to import `{ Badge }` directly without creating an artificial new file on disk.

### Step 3: Finally, we import and compose the components inside <App.jsx>

Now that `src/components/ArticleCard.jsx` provides both a default card and a named badge, we open `src/App.jsx` and import them. We use default import syntax for `ArticleCard` and named import syntax with curly braces for `Badge`. We render two distinct cards: one with a "LATEST NEWS" badge and another with an "ARCHIVE" badge. Notice that both files now have clear, focused jobs: `ArticleCard.jsx` manages card structure and badge styling, while `App.jsx` orchestrates page layout:

```jsx title="App.jsx"
import ArticleCard, { Badge } from './components/ArticleCard.jsx'; // imports
export default function App() {
  return (
    <main className="feed-layout"> {/* orchestrates feed */}
      <ArticleCard title="Downtown Accord">
        <Badge text="NEWS" /> {/* named badge subcomponent */}
      </ArticleCard>
    </main>
  );
}
```

Notice how clean `App.jsx` has become. The single import statement `import ArticleCard, { Badge } from './components/ArticleCard.jsx'` imports both the default export and the named export in one concise line. The relative import path `./components/ArticleCard.jsx` matches the on-disk file casing exactly, ensuring the project compiles cleanly on both macOS development laptops and Linux CI build servers.

In legacy web applications, keeping all components in a single monolithic file resulted in severe maintenance friction, frequent git merge conflicts, and copy-paste duplication. In React, splitting components into standard ES modules establishes clean architectural boundaries. `ArticleCard.jsx` acts as a dedicated module, exporting its primary component as a default export and secondary utilities as named exports. Because import syntax strictly dictates how values are consumed, developers enjoy build-time verification, clear stack traces, and seamless code reuse across the entire application.

### Where you will meet this

1. **Design System Component Libraries**: Enterprise UI libraries export primary components (like `<Modal />`) as default exports, while exposing sub-components (like `{ ModalHeader, ModalFooter }`) as named exports.
2. **File-Based Routing Frameworks**: Modern frameworks like Next.js and Remix require each page route file to export a single default React component to represent the page view.
3. **Utility and Icon Packages**: Icon libraries package hundreds of SVG icons as individual named exports (`import { SearchIcon, CloseIcon }`), allowing bundlers to tree-shake unused icons from production bundles.

### For the interview

> **The Interview Question:** How do you split components across files, and how do default and named imports differ?

- **The Hidden Signal**: Interviewers ask this question to verify whether you understand the distinction between JavaScript module scope and the global window scope, how bundlers resolve static import bindings before runtime, and why team conventions favor one export pattern over another. Candidates who understand modules can explain that import statements form a static module dependency graph, whereas component execution builds the runtime UI tree.
- **The Classic Trap**: The most common mistake is confusing import curly braces with JSX expression braces or runtime object destructuring. Candidates often assume `import { ArticleCard } from './components/ArticleCard.jsx'` destructures a runtime object, unaware that ES module import specifiers are static language bindings checked by the bundler before any code executes. Another frequent trap is exporting anonymous arrow functions as default exports, which strips the component of its identifier and pollutes error stacks with `<default>`.
- **What is Actually Going On**: Each file is an ES module evaluated in its own isolated environment. Build tools like Vite construct a module dependency tree by parsing import and export declarations statically before any component renders. Default exports bind to the module's `default` key, allowing the importer to assign any local identifier. Named exports bind to explicit named export keys on the module record, enforcing character-for-character identifier matching between exporter and importer.
- **Where It Gets Tricky**: A tricky nuance arises with module evaluation timing. Code placed at the top level of a module executes exactly once when the file is first imported, and its exports are cached in memory. In contrast, code placed inside a component function executes on every render. If an engineer places shared mutable state at the top level of a module, that state becomes a global singleton shared across all instances of the component, breaking component isolation and causing severe concurrency bugs.

### Glossary

- **module**: An isolated JavaScript file with private scope that shares values across file boundaries only through explicit export and import statements.
- **default export**: The single primary value or component exported by a module, declared with `export default` and imported without curly braces under any local name.
- **named export**: A specific value or component exported by name using `export function`, imported inside curly braces matching its exact identifier.
- **default import**: An import statement written without curly braces that loads the primary default export of a module.
- **named import**: An import statement written with curly braces that loads a specific named export from a module.
- **module dependency tree**: The hierarchical graph of file relationships formed by import and export statements, used by build tools to bundle application code.

### Summary

**Architectural Takeaways and Module Resolution Rules**

❒ Module Organization and Export Choice

➔ ALWAYS give each component that other files use its own module under `src/components/`, and keep single-use helpers unexported in that file.

➔ NEVER export anonymous component functions like `export default () => {}`, because React prints `<default>` in error stacks and DevTools.

❒ Import Matching and Casing Discipline

➔ ALWAYS match import syntax to the export style, using default imports without braces for default exports and curly braces for named exports.

➔ IF a file provides one primary component, THEN export that component as the default export.

➔ IF a file provides multiple reusable helpers or sub-components, THEN export them as named exports.

**DO THIS:** match import syntax to export style and name exported functions

```jsx right
export default function ArticleCard({ title }) {
  return <article className="card">{title}</article>;
}
export function Badge({ text }) {
  return <span className="badge">{text}</span>;
}
```

**DO NOT DO THIS:** mix up default and named syntax or use anonymous components

```jsx wrong
export default () => <article className="card" />;
import { ArticleCard } from './ArticleCard.jsx';
```

| | **DEFAULT EXPORTS**<br>(Single Primary Component) | **NAMED EXPORTS**<br>(Multiple Distinct Utilities) |
| ---: | :--- | :--- |
| **Declaration Syntax** | `export default`<br>`function Card() {}` | `export function`<br>`Badge() {}` |
| **Import Syntax** | `import ArticleCard`<br>`from`<br>`'./ArticleCard.jsx'` | `import { Badge }`<br>`from`<br>`'./ArticleCard.jsx'` |
| **Exports Per File** | Exactly one default export per module | Unlimited named exports per module |
| **Import Naming** | Importer chooses any local variable name | Importer must match exported name |
| **Refactoring Safety** | Rename in source does not update importer | Rename in source breaks mismatched imports |
| **Debugging Callstack** | Uses function name; `<default>` if anonymous | Uses function name consistently |
| **Best Used For** | Primary component representing the file's job | Secondary helpers, badges, or utility functions |
