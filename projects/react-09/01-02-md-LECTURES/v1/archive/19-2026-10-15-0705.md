### The item list changes in memory, but the screen stays frozen

In modern web applications, user interfaces frequently manage collections of data. Applications display lists of tasks, shopping cart items, user messages, and incoming notifications. In plain JavaScript, developers modify arrays directly in memory using mutating methods like `push`, `splice`, and `sort`. When an array is stored in React state, this habit breaks application reactivity. In JavaScript, an array is an object, so React compares state values by memory reference using `Object.is`. When an event handler mutates an array in place and hands it back to the setter, React sees the exact same memory address and aborts rendering. To update the screen reliably, every array operation must construct a brand-new array and pass that new container to the setter function.

When engineers transition from plain JavaScript scripting to React, they naturally reach for standard array methods like `arr.splice()` to delete an element or `arr.push()` to append a record. In vanilla scripts, these methods modify memory in place, and the next line of code sees the modified array immediately. In React, application memory lives outside the component function, and state updates occur through declarative reconciliation. Calling `items.splice(1, 1)` deletes the element from computer memory, but calling `setItems(items)` hands React the exact same array reference it already holds. Because `Object.is(previousArray, nextArray)` evaluates to true, React assumes nothing changed and skips the render phase. Furthermore, developers who copy the array using spread syntax often mistakenly assign directly to properties of items inside the copy, unaware that shallow copying shares nested object references with previous render snapshots.

This chapter investigates five core questions:

1. **Why does calling a mutating method like splice or sort followed by the setter fail to update the screen?**
2. **How do you remove an item from a state array cleanly without modifying existing memory?**
3. **How do you add an item at the end, at the beginning, or between two existing items using spread syntax?**
4. **Why must sorting and reversing operate on a copy rather than the state array itself?**
5. **When updating properties on an item inside an array, why is copying the outer array container not enough?**

### How mutating array methods skip React re-renders

In Lecture 18, we discovered that JavaScript objects are compared by reference. When an event handler mutates an object's properties directly and calls the setter, `Object.is` finds identical references and React skips the render. Because JavaScript arrays are standard objects under the hood, array state operates under the exact same reference equality invariant.

```jsx title="Mutating Versus Copying Array Methods"
const items = [{ id: 1, title: 'First' }, { id: 2, title: 'Second' }];

// Mutating in place: modifies array in memory, returns removed elements
const removed = items.splice(1, 1); // items is still same array in memory

// Non-mutating copy: leaves original intact, returns new array
const filtered = items.filter(item => item.id !== 2); // brand-new array
```

In JavaScript, array methods divide into two distinct categories: mutating methods that alter the array in place, and non-mutating methods that return a fresh array. Mutating methods include `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, and `reverse`, as well as direct index assignment (`arr[0] = value`). When you execute any of these methods on a state array, JavaScript alters the existing array in memory. Passing that mutated array to the state setter gives React the same object reference it already holds. React detects zero reference difference and skips rendering. Conversely, copying methods like `slice`, `filter`, `map`, `concat`, `toSorted`, `toReversed`, and `toSpliced` generate a brand-new array in memory. Passing the new array to the setter allows `Object.is` to detect a distinct reference, scheduling a clean render pass.

### How array spread creates new arrays for additions and insertions

In Lecture 18, we used object spread syntax `{ ...obj }` to create a shallow copy of an object while updating selected properties. JavaScript provides identical spread syntax for arrays: writing `[...arr]` unpacks the elements of an existing array into a fresh array literal.

```jsx title="Array Spread Addition and Insertion"
const items = [{ id: 1, text: 'A' }, { id: 3, text: 'C' }];
const newItem = { id: 2, text: 'B' };

// Appending at the end
const appended = [...items, newItem]; // [A, C, B]

// Inserting at index 1 between A and C
const inserted = [...items.slice(0, 1), newItem, ...items.slice(1)];
```

When adding an item to state, developers often intuitively write `setItems(items.push(newItem))`. However, native `push()` mutates the array and returns the array's new length as an integer. Passing this call to the setter stores a number in state, causing the next render pass to crash when it attempts to call `items.map()`. To add items cleanly, use array spread. To append at the end, write `[...items, newItem]`. To prepend at the start, write `[newItem, ...items]`. To insert an item at index `i`, combine spread syntax with native `slice()`: write `[...items.slice(0, i), newItem, ...items.slice(i)]`. The `slice()` method returns a shallow copy of a portion of an array without modifying the original, creating a seamless insertion bridge.

### Why copying an array leaves its nested objects shared

In Lecture 18, we learned that copying an object with `{ ...user }` performs a shallow copy: top-level primitive properties are duplicated, but nested objects continue pointing to their original memory addresses. Mutating a nested property on a copied object damages earlier render snapshots and corrupts reset baselines.

```jsx title="Replacing Items with Map and Object Spread"
const items = [{ id: 1, title: 'Draft', done: false }];

// SAFE: returns a new array with a new object for item 1
const updated = items.map(item =>
  item.id === 1 ? { ...item, done: true } : item
); // original item in items remains completely unchanged
```

When an array contains objects, spreading that array with `[...items]` produces a new array container, but the elements inside that new container are identical object references. If a developer writes `const next = [...items]; next[0].done = true;`, the assignment mutates the shared object in memory. While `next` is a new array container that triggers a re-render, the underlying item object was mutated in place. Any earlier render snapshots, cached records, or baseline constants like `initialTasks` now reflect the mutation, permanently corrupting the Reset button. To update an item safely, use `map()`: iterate through the array, check if `item.id === targetId`, and return a new object using object spread `{ ...item, done: true }` for the target while returning unchanged items as they are.

### Principles of React: Updating Arrays in State

### Question 1: Calling splice on a state array leaves the screen unchanged

A developer builds a task queue manager called `TaskManager`. Three tasks appear on screen: "Fix navigation header", "Typo in footer link", and "Deploy production build". To delete the typo task, the developer attaches a click handler calling `items.splice(1, 1)` and immediately calls `setItems(items)`:

```jsx title="TaskManager.jsx, first attempt" startLine="8"
  function handleDeleteTypo() {
    items.splice(1, 1); // Mutates array in place
    setItems(items); // Passes same array reference back to React
  }
```

The developer clicks the "Delete typo" button. The console logs zero render passes, and the screen continues showing all three tasks. Moments later, the developer clicks an unrelated counter button, and the second task suddenly disappears from the screen.

**I call items.splice(1, 1) and setItems(items). Why does the deleted item stay on screen?**

---

**ANSWER**

**The code does not do what we wanted.** In plain JavaScript, calling `splice` alters the array in memory immediately, but React skips the render because the array reference is identical.

In plain JavaScript, calling `items.splice(1, 1)` deletes the element from memory in place. In React, `items` points to the exact array instance currently held in state. Calling `items.splice(1, 1)` mutates that array in place. When you pass `items` to `setItems(items)`, you pass the identical array reference back to React.

React checks whether state changed using `Object.is(previousState, nextState)`. Because both arguments point to the exact same memory address, `Object.is` returns `true`. React concludes that state has not changed and aborts the render pass. The screen remains stuck on the three original tasks. When an unrelated counter button triggers a re-render later, React reads the mutated array and finally displays two tasks, proving that the array mutated in memory while reactivity failed.

```ascii title="Array Reference Comparison During Mutation"
[Click Button] -> items.splice(1, 1) mutates array [0x101] in place
      |
      v
setItems(items) hands [0x101] back to React setter
      |
      v
Object.is(0x101, 0x101) === true: NO REFERENCE CHANGE
      |
      v
[React Skips Render] -> Screen keeps showing 3 items
```

To trigger a screen update, your code must provide a newly created array. Calling `setItems(items.filter(item => item.id !== 2))` generates a fresh array container, allowing `Object.is` to detect the update.

> [!PRINCIPLE]
> **Principle 1: The setter skips the render when it gets the same array**
> React checks whether state changed by comparing references with `Object.is`. Methods like `splice`, `push`, and `sort` modify an array in place, so passing the same array back to the setter gives React the exact reference it already holds. Because `Object.is` finds no difference, React skips running the component and the screen keeps showing the old list. To trigger a screen update, your code must provide a newly created array.
>
> >> Object.is : the JavaScript comparison method React uses to check if state changed
>
> *We should do this:*
> `const nextItems = items.filter(item => item.id !== 2); // new array`
> `setItems(nextItems); // React renders the new list`
>
> *We should not do this:*
> `items.splice(1, 1); // modifies array in place`
> `setItems(items); // same array, React skips render`

### Question 2: Calling slice instead of splice empties the list

The developer notices that `splice` mutated the array in place. Recalling that `slice` does not mutate arrays, the developer replaces `items.splice(1, 1)` with `items.slice(1, 1)` and passes the result to `setItems`:

```jsx title="TaskManager.jsx, slice attempt" startLine="8"
  function handleDeleteTypo() {
    const nextItems = items.slice(1, 1); // Slices from index 1 to index 1
    setItems(nextItems); // Passes slice result to setter
  }
```

The developer clicks the button. React executes a render pass, but the entire task list disappears from the screen, leaving an empty container.

**How do I delete an item without mutating the array in place?**

---

**ANSWER**

**The code does not do what we wanted.** Calling `slice(1, 1)` extracts zero elements from the array, passing an empty array to the setter.

The developer assumed `slice` is the non-mutating drop-in replacement for `splice`. However, the two methods accept completely different parameters. Native `splice(start, deleteCount)` takes a start index and the number of elements to remove. Native `slice(startIndex, endIndex)` extracts elements starting at `startIndex` up to, but not including, `endIndex`.

Calling `items.slice(1, 1)` asks JavaScript for all elements starting at index 1 up to index 1. Because the start and end boundaries are identical, `slice` extracts zero elements and returns an empty array `[]`. The setter receives `[]`, causing React to re-render an empty list on screen.

```ascii title="Removing Elements: Slice Pitfall Versus Filter"
[slice(1, 1) Pitfall]
  items = [Task 1, Task 2, Task 3]
  slice(1, 1) extracts index 1 up to 1 ---> Returns [] (EMPTY)
  setItems([]) renders ZERO items on screen!

[filter Solution]
  items.filter(item => item.id !== 2)
  Evaluates condition for each task     ---> Returns [Task 1, Task 3]
  setItems(...) renders TWO items safely
```

To remove an item cleanly, use `filter`. Calling `items.filter(item => item.id !== 2)` tests each item against the predicate. Every item whose id is not 2 is copied into a brand-new array. The setter receives the new 2-item array and updates the screen properly.

> [!PRINCIPLE]
> **Principle 2: Remove with filter, which returns a new array**
> Do not remove items with `splice`, which mutates the array in place, and do not confuse `splice` with `slice`, which extracts a range between two index boundaries. To remove an item from state, call `filter` on the array. The `filter` method evaluates a test function for each element and returns a brand-new array holding only the items that pass.
>
> >> filter : an array method that returns a new array with all elements that pass a test
>
> *We should do this:*
> `const nextItems = items.filter(item => item.id !== 2); // keeps all except id 2`
> `setItems(nextItems); // screen removes item 2`
>
> *We should not do this:*
> `const nextItems = items.slice(1, 1); // returns an empty array []`
> `setItems(nextItems); // empties the entire list on screen`

### Question 3: Calling push inside the setter crashes the next render

A new urgent task arrives. The developer wants to append it to the task queue. Accustomed to chaining method calls, the developer calls `items.push(newTask)` directly inside the setter argument:

```jsx title="TaskManager.jsx, push attempt" startLine="8"
  function handleAddTask() {
    const newTask = { id: 4, title: 'Emergency patch', time: 13 };
    setItems(items.push(newTask)); // Passes push result to setter
  }
```

The developer clicks the "Add Task" button. The screen turns white, and the development console reports an uncaught crash: `TypeError: items.map is not a function`.

**A new item arrives. How do I add it to the end, start, or middle of the list?**

---

**ANSWER**

**The code does not do what we wanted.** The `push` method modifies the array in place and returns its new length as an integer, causing the next render to throw a `TypeError`.

In JavaScript, `push()` appends an item to the array in place and returns the new length of the array as a number. In an array of three items, calling `items.push(newTask)` mutates the array and returns the number `4`. Calling `setItems(items.push(newTask))` stores the number `4` in React state.

When React initiates the next render pass, the component body attempts to render the task list using `items.map(...)`. Because the variable `items` now holds the number `4` rather than an array, JavaScript throws `TypeError: items.map is not a function`, crashing the application.

```ascii title="Adding Items: Push Return Value Versus Array Spread"
[items.push(newTask) Execution]
  items.push(...) mutates array in place
  push returns array length integer: 4
  setItems(4) stores NUMBER in state
  Next render: (4).map(...) ---> CRASH: TypeError!

[Array Spread Execution]
  [...items, newTask] creates a fresh array container
  setItems([...]) stores 4-item ARRAY in state
  Next render: [Task 1, Task 2, Task 3, Task 4].map(...) ---> SUCCESS!
```

To add an item cleanly, use array spread syntax `[...items, newTask]`. The spread operator unpacks all existing elements into a fresh array literal and places the new item at the end. To prepend an item at the beginning, place the item first: `[newTask, ...items]`. To insert an item at index `i`, combine spread syntax with two `slice` calls: `[...items.slice(0, i), newTask, ...items.slice(i)]`.

> [!PRINCIPLE]
> **Principle 3: Add and insert with spread**
> Calling `push` on an array modifies it in place and returns its new length as a number. Passing `items.push(newItem)` to a setter stores a number in state, crashing the next render when the code calls `items.map`. To add an item, spread the existing array into a new array literal with the new element at the end, at the start, or between two `slice` calls to insert at an index.
>
> >> spread syntax : the ... operator that copies elements from an existing array into a new array
>
> *We should do this:*
> `const nextItems = [...items, newItem]; // copies items and appends new item`
> `setItems(nextItems); // screen shows updated list`
>
> *We should not do this:*
> `setItems(items.push(newItem)); // returns array length number, not array`
> `// next render crashes: items.map is not a function`

### Question 4: Calling sort directly on state keeps the previous order

The developer wants to sort the task list chronologically by estimated completion time. Noting that `sort()` returns an array, the developer writes `setItems(items.sort(compareFn))`:

```jsx title="TaskManager.jsx, sort attempt" startLine="8"
  function handleSortByTime() {
    setItems(items.sort((a, b) => a.time - b.time)); // Passes sorted array
  }
```

The developer clicks the "Sort Tasks" button. The console logs zero render passes, and the task list remains in its original order on screen. When the developer clicks an unrelated counter, the list suddenly snaps into sorted order. Clicking Reset leaves the list sorted.

**I want to sort the list. Can I write setItems(items.sort(compareFn))?**

---

**ANSWER**

**The code does not do what we wanted.** The `sort` method reorders elements in place and returns that same array reference, so React skips the render.

Unlike `map` or `filter`, JavaScript native `sort()` and `reverse()` methods reorder the array in place and return the exact same array reference. Calling `items.sort(...)` mutates the array stored in state and passes that same array reference back to `setItems`.

React runs `Object.is(previousState, nextState)`. Because both arguments point to the identical array in memory, `Object.is` returns `true`. React assumes state did not change and skips the render pass. The screen keeps showing the old order. When an unrelated state setter triggers a render later, React finally renders the mutated array. Even worse, because `items` was sorted in place, the baseline array constant `initialTasks` was also sorted in place. Clicking the Reset button passes `initialTasks`, but `initialTasks` is already sorted, permanently breaking component reset behavior.

```ascii title="Reordering Items: In-Place Sort Versus ToSorted"
[items.sort() Mutation]
  items.sort(...) mutates array [0x202] in place
  setItems([0x202]) hands same reference to React
  Object.is(0x202, 0x202) is true ---> React skips render!
  initialTasks is also mutated ---> Reset button corrupted!

[items.toSorted() Copy]
  items.toSorted(...) creates brand-new array [0x303]
  setItems([0x303]) hands new reference to React
  Object.is(0x202, 0x303) is false ---> React renders new order!
  initialTasks remains untouched ---> Reset button works!
```

To sort correctly without mutating state, sort a fresh copy using spread `[...items].sort(compareFn)` or use the modern non-mutating method `items.toSorted(compareFn)`. Both approaches leave the existing state array and initial baseline constants untouched.

> [!PRINCIPLE]
> **Principle 4: Sort a copy, never the array in state**
> The JavaScript `sort` and `reverse` methods reorder elements in place and return the same array reference. Passing `items.sort()` to a setter hands React the array it already holds, so `Object.is` skips the render and the screen keeps the old order. To reorder items in state, sort a fresh copy using `[...items].sort()` or call the non-mutating method `items.toSorted()`.
>
> >> toSorted : a JavaScript method that returns a new array sorted by a comparison function
>
> *We should do this:*
> `const nextItems = items.toSorted((a, b) => a.time - b.time); // new sorted array`
> `setItems(nextItems); // React renders sorted items`
>
> *We should not do this:*
> `setItems(items.sort((a, b) => a.time - b.time)); // reorders in place`
> `// same array reference, React skips render`

### Question 5: Modifying an item in a copied array corrupts earlier renders

The developer wants to correct the title of task 2. Aware that mutating the array breaks re-renders, the developer copies the array first using spread, and then updates the item title directly:

```jsx title="TaskManager.jsx, item mutation in copy" startLine="8"
  function handleCorrectTypo() {
    const nextItems = [...items];
    nextItems[1].title = 'Fixed footer link'; // Mutates shared item in memory
    setItems(nextItems);
  }
```

The developer clicks the "Correct Typo" button. The screen updates immediately to show "Fixed footer link". Satisfied, the developer clicks the "Reset List" button to restore the original task list. The screen refuses to restore "Typo in footer link", stubbornly keeping the modified title.

**I copied the array first, then updated an item in the copy. Why does Reset fail?**

---

**ANSWER**

**The code does not do what we wanted.** Array spread creates a shallow copy where nested objects remain shared references, so mutating an item alters initial state constants and earlier snapshots.

When you copy an array with `[...items]`, JavaScript creates a brand-new array container. However, spreading an array copies references, not the objects themselves. In memory, `nextItems[1]` points to the exact same object reference as `items[1]` and `initialTasks[1]`.

Assigning `nextItems[1].title = 'Fixed footer link'` mutates that shared object directly in memory. Because `nextItems` is a new array container, `Object.is` detects a reference difference and triggers a re-render. The screen displays the updated title. But because the underlying object was mutated in place, `initialTasks[1].title` now holds "Fixed footer link". When the user clicks Reset, `setTasks(initialTasks)` passes the baseline array, but its second item was already permanently modified.

```ascii title="Nested Object Sharing Across Shallow Array Copies"
[Shallow Copy Mutation]
  nextItems = [...items] creates new array container
  items[1] and nextItems[1] point to SHARED OBJECT { id: 2, title: 'Typo...' }
  nextItems[1].title = 'Fixed' alters SHARED OBJECT!
  initialTasks[1] now also holds 'Fixed' ---> RESET BROKEN!

[Map with Object Spread Fix]
  items.map(t => t.id === 2 ? { ...t, title: 'Fixed' } : t)
  Creates NEW OBJECT for task 2 with { ...t, title: 'Fixed' }
  Unchanged tasks keep original object references
  initialTasks[1] remains completely untouched ---> RESET WORKS!
```

To update an item safely, use `map()`: iterate over the array, match the target item by `id`, and return a new object with object spread `{ ...item, title: 'Fixed footer link' }`. Return all non-matching items unchanged.

> [!PRINCIPLE]
> **Principle 5: To change one item, copy that item too**
> Spreading an array with `[...items]` creates a new array container, but the objects inside remain shared references in memory. Mutating a property on an item in a copied array changes the object that earlier snapshots and initial state still hold, breaking component resets. To update an item safely, call `map` to produce a new array, and return a new object using object spread for the item you want to change.
>
> >> shallow copy : an array copy where nested objects continue sharing the same memory references
>
> *We should do this:*
> `const nextItems = items.map(item =>`
> `  item.id === 2 ? { ...item, title: 'Fixed' } : item`
> `); // creates a new object for item 2`
> `setItems(nextItems); // screen updates and Reset works`
>
> *We should not do this:*
> `const nextItems = [...items]; // new array container`
> `nextItems[1].title = 'Fixed'; // mutates shared item object`
> `setItems(nextItems); // corrupts initialTasks and Reset`

### Step 1: First, we lay out the task manager application <src/App.jsx>

In `src/App.jsx`, we establish the top-level application container. The root component renders the main title and mounts the `TaskManager` widget.

Notice that `App` owns zero interactive state. Because `App` does not declare `useState`, array additions, removals, and reordering operations executed inside `TaskManager` remain completely encapsulated. React re-renders only `TaskManager` and its child subtree, keeping the outer layout stable.

```jsx title="App.jsx" startLine="1"
import TaskManager from './components/TaskManager.jsx';

export default function App() {
  return (
    <main className="task-app">
      <h1>Project Task Queue</h1>
      <TaskManager /> {/* State owner boundary */}
    </main>
  );
}
```

This structural separation guarantees that collection operations inside the task boundary never trigger unnecessary top-level re-renders.

### Step 2: Next, we build the stateful task array boundary <src/components/TaskManager.jsx>

In `src/components/TaskManager.jsx`, we construct the interactive state boundary. We declare the baseline constant `initialTasks` outside the component function and initialize state using `useState(initialTasks)`.

Keeping `initialTasks` at module scope guarantees that it acts as an immutable baseline benchmark for resetting state.

```jsx title="TaskManager.jsx" startLine="1" continues="bottom"
import { useState } from 'react';
import TaskControls from './TaskControls.jsx';

const initialTasks = [
  { id: 1, title: 'Fix navigation header', time: 9 }, // Task 1
  { id: 2, title: 'Typo in footer link', time: 11 }, // Typo task
  { id: 3, title: 'Deploy production build', time: 10 }
];

export default function TaskManager() {
```

Next, we implement the non-mutating handlers for deleting items, adding new tasks, and resetting the array.

We use `filter` in `handleDelete` to create a fresh array excluding the target id. In `handleAdd`, we use array spread to append a new task record. In `handleReset`, we pass `initialTasks` back to `setTasks`.

```jsx title="TaskManager.jsx" startLine="11" continues="both"
  const [tasks, setTasks] = useState(initialTasks);
  function handleDelete(id) {
    setTasks(tasks.filter(t => t.id !== id)); // Non-mutating remove
  }
  function handleAdd(title) {
    setTasks([...tasks, { id: 4, title, time: 12 }]); // Appends new task
  }
  function handleReset() {
    setTasks(initialTasks); // Restores initial state
  }
```

Next, we implement `handleSort` using `toSorted` and `handleCorrect` using `map` with object spread.

Using `toSorted` creates a new sorted array without mutating `tasks` or `initialTasks`. In `handleCorrect`, using `map` returns a brand-new object for the matching task while leaving unchanged tasks untouched.

```jsx title="TaskManager.jsx" startLine="21" continues="both"
  function handleSort() {
    setTasks(tasks.toSorted((a, b) => a.time - b.time)); // Sorted copy
  }
  function handleCorrect(id, title) {
    setTasks(tasks.map(t =>
      t.id === id ? { ...t, title } : t
    )); // Object copy in mapped array
  }
```

Finally, we render the task list and mount the child controls, passing action handlers downward.

```jsx title="TaskManager.jsx" startLine="29" continues="top"
  return (
    <section className="task-card">
      <ul className="task-list">
        {tasks.map(t => <li key={t.id}>{t.title}</li>)} {/* Task list */}
      </ul>
      <TaskControls onRemove={handleDelete} onAdd={handleAdd} />
    </section>
  );
}
```

The component passes its state and handler callbacks downward to `TaskControls`.

### Step 3: Finally, we build the task action controls <src/components/TaskControls.jsx>

In `src/components/TaskControls.jsx`, we create the action buttons that trigger user operations.

Notice that `TaskControls` owns zero local state. It receives callback functions from its parent and wires them directly to button click events. When a user clicks a button, the callback executes in `TaskManager` memory, demonstrating inverse data flow.

```jsx title="TaskControls.jsx" startLine="1"
export default function TaskControls({ onRemove, onAdd }) {
  return (
    <div className="task-actions">
      <button onClick={() => onRemove(2)}>Delete Typo</button> {/* Action */}
      <button onClick={() => onAdd('Write tests')}>Add Task</button>
    </div>
  );
}
```

The control buttons dispatch actions upward without holding local memory.

### Where you will meet this

In production frontend applications, updating arrays in state is universal across todo lists, shopping carts, notification feeds, and kanban boards. A frequent production bug arises when an engineer uses `splice` to delete an item from an active cart, causing the UI to freeze until an unrelated state change triggers a re-render. Adopting `filter` permanently prevents this defect.

Another universal scenario involves sorting tabular data or transaction histories. Developers who call `.sort()` directly on state arrays inadvertently mutate shared memory, scrambling cached datasets and preventing users from restoring original chronological sorting. Using `toSorted()` or `[...items].sort()` guarantees clean reordering without data pollution.

In technical interviews, engineering candidates are routinely asked how to update arrays in state without mutating them. Interviewers specifically probe whether candidates understand why `push` fails inside setters, why `slice` is not the copying equivalent of `splice`, and why copying an array still requires mapping objects inside it with `{ ...item }`.

### For the interview

> **The Interview Question:** How do you add, remove, insert, and reorder items in a state array?

**1. The Hidden Signal**

The interviewer is evaluating whether you understand JavaScript reference equality and React reconciliation mechanics. Junior developers view arrays as simple lists to be edited with imperative methods like `push` and `splice`. Senior engineers recognize that state arrays are immutable objects compared by reference using `Object.is`, requiring non-mutating operations that generate new array containers.

**2. The Classic Trap**

The most common trap is assuming that copying an array with spread syntax `const next = [...items]` makes it completely safe to mutate its elements. Candidates write `next[0].title = 'Updated'`, unaware that spreading creates a shallow copy where nested objects remain identical references. When asked why their Reset button no longer works, unprepared candidates cannot identify the shared reference leak.

**3. What is Actually Going On**

React checks whether state changed by comparing references with `Object.is`. Methods like `splice`, `push`, `sort`, and `reverse` modify the array in place, returning either the same array reference or an unintended value (such as the new length integer returned by `push`). Because the array reference never changes, React skips the render phase. To trigger a render, you must produce a new array container: `filter` for removal, array spread `[...items, newItem]` for additions, `slice` combined with spread for insertions, and `toSorted()` or `[...items].sort()` for reordering.

**4. Where It Gets Tricky**

What about updating one object inside an array? Because array spread is shallow, updating an item requires calling `items.map()`, checking for the target item identifier, and returning a new object using object spread `{ ...item, prop: value }` while returning untouched items as they are. When nested updates become complex or deeply nested, teams often introduce Immer to write update logic concisely while preserving structural immutability behind the scenes.

### Glossary

- **Immutable Array**: An array treated as read-only in state, updated exclusively by creating fresh array containers rather than altering memory in place.
- **`filter`**: A non-mutating JavaScript array method that returns a new array containing all elements that satisfy a predicate function.
- **Array Spread**: The JavaScript `...` syntax that unpacks elements of an existing array into a fresh array literal, enabling safe additions and shallow copies.
- **`toSorted`**: A modern non-mutating JavaScript array method that returns a brand-new sorted array without modifying the original array in place.
- **Shallow Copy**: A duplicated array container whose internal elements continue pointing to the identical memory references of the original collection.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Immutable Array Transitions

➔ ALWAYS treat state arrays as read-only collections by constructing fresh array containers for every state transition.

➔ NEVER call mutating array methods like `splice`, `push`, `sort`, or `reverse` directly on a state array.

➔ IF you need to remove an item from an array in state THEN use `filter` with the item identifier instead of `splice`.

➔ IF you need to add an item to an array in state THEN spread the existing array into a new literal with the new element.

➔ IF you need to reorder an array in state THEN sort a shallow copy or call `toSorted` to avoid in-place mutation.

➔ IF you need to update an item inside an array THEN use `map` and return a new object with object spread for the target item.

**DO THIS:**

```jsx right
function handleRemove(id) {
  setItems(items.filter(item => item.id !== id));
}
function handleAdd(newItem) {
  setItems([...items, newItem]);
}
```

**DO NOT DO THIS:**

```jsx wrong
function handleRemove(index) {
  items.splice(index, 1);
  setItems(items);
}
function handleAdd(newItem) {
  setItems(items.push(newItem));
}
```

| | **IN-PLACE ARRAY MUTATION**<br>(Plain JavaScript Habit) | **IMMUTABLE STATE ARRAY**<br>(React Declarative Architecture) |
| ---: | :--- | :--- |
| **Removal operation** | `splice` modifies array in place | `filter` returns a fresh array |
| **Addition operation** | `push` modifies array and returns length | `[...items, newItem]` unpacks into a brand-new array |
| **Insertion operation** | `splice` inserts elements in place | `slice` with spread creates a combined copy |
| **Reorder operation** | `sort` mutates order of original reference | `toSorted` or `[...items].sort()` on a fresh copy |
| **Item update** | Direct mutation alters shared object | `map` with `{ ...item }` copies changed item |
| **Reconciliation reaction** | `Object.is` finds identical reference; skips render | `Object.is` detects new array reference; triggers render |
| **Baseline data & Reset** | Mutates initial objects; corrupts Reset button | Leaves previous snapshots and initial constants intact |
