### Every render receives a fixed state snapshot

In modern web applications, user interfaces update dynamically in response to user interactions. When a reader clicks a star rating, submits feedback, or confirms an order, the interface changes to reflect the new data. In plain JavaScript, developers modify memory by reassigning variables directly with `=`, expecting every subsequent line of code to see the new value immediately. In React, application state behaves differently: it acts as a snapshot. Calling a state setter does not mutate the variable in the running code; instead, it asks React to schedule a future render where `useState` returns the new value. Understanding that a state variable remains frozen as a constant for the entire duration of a render is essential for coordinating user events, network requests, and delayed callbacks without synchronization bugs.

When developers transition from traditional scripting to React, they often assume that calling a state setter works like variable reassignment. In plain JavaScript, writing `rating = 5` changes the variable immediately, so logging `rating` on the very next line prints 5. In React, calling `setRating(5)` does not touch the local variable `rating` in the currently executing function. React keeps state memory outside the component and hands the current render a constant snapshot of that data. The running event handler continues executing using its existing snapshot value. Consequently, reading the state variable on the line immediately following a setter call prints the old value. Furthermore, developers often expect that calling `setRating(rating + 1)` three times in a row will increment the number by three, unaware that every call in that handler evaluates using the exact same snapshot number.

This chapter answers four core questions. **Why does reading a state variable immediately after calling its setter still return the old value?** **How should an event handler coordinate state updates with external API calls or network dispatches?** **Why does calling a state setter three times in a row only advance the count by one?** **If a delayed timer runs after the user selects a new rating, which value does its callback read?**

### How React captures state in a render snapshot

In Lecture 14, we learned that calling `useState` gives a component memory. React preserves state variables outside the component function, and calling a state setter tells React to schedule a re-render. In Lecture 15, we discovered that React runs event handlers to completion before initiating the render and commit phases.

```jsx title="Declarative State Snapshot"
export default function FeedbackSnapshot() {
  const [rating, setRating] = useState(0); // rating is constant 0 in this run
  function handleRate() {
    setRating(5); // Requests next render with 5
    console.log(rating); // Still prints 0 in this run
  }
  return <button onClick={handleRate}>Rate ({rating})</button>;
}
```

When React renders a component, it calls your component function. The `useState` call retrieves the current state value from React internal storage and returns it to your function. Inside that function execution, the state variable is a standard JavaScript `const`. It never changes while that function executes. The JSX, local variables, and event handlers are all computed using this fixed value. We call this fixed set of values a **snapshot**.

Calling a setter function like `setRating(5)` does not mutate the variable `rating` in your running code; it only tells React what value to supply in the next render. You can visualize this behavior using the **substitution method**: if `rating` is `0` when the component runs, you can mentally substitute `0` for `rating` everywhere in that render code.

```jsx title="The Substitution Method"
function handleTripleBoost() {
  setRating(0 + 1); // Substituted: requests 1 for next render
  setRating(0 + 1);
  setRating(0 + 1); // Queues 1 again for the screen
}
```

Calling `setRating(rating + 1)` three times in one handler evaluates as `setRating(0 + 1)` three times. Each call asks React for 1, not 3. The screen moves from 0 to 1, exactly as if you called `setRating(1)` three times.

### How functions capture state across time through closures

In Lecture 13, we saw that event handlers are JavaScript functions passed to JSX elements to handle user events. In standard JavaScript, functions declared inside an outer function have access to the outer function scope.

```jsx title="Delayed Timer Closure"
export default function DelayedConfirmation() {
  const [rating, setRating] = useState(0); // Snapshot constant for this render
  function handleSend() {
    setTimeout(() => {
      console.log(`Rating: ${rating}`); // Closure reads rating from this render
    }, 1000);
  }
  return <button onClick={handleSend}>Send ({rating})</button>;
}
```

Every time React renders a component, it executes the component function from top to bottom, creating fresh event handler functions for that specific render. In JavaScript, an inner function forms a **closure**: it permanently remembers the variables of the lexical scope where it was created.

When an event handler schedules a delayed callback with `setTimeout`, that callback closes over the specific snapshot values of the render that created it. The browser native `setTimeout` method accepts a callback function and a delay in milliseconds, executing the callback after the timer expires. Even if subsequent user clicks trigger new renders that update the screen with fresh state, existing timer callbacks retain the snapshot values from the render where they were scheduled. This behavior prevents timing bugs and race conditions in asynchronous user workflows.

### Principles of React: State as a Snapshot

### Question 1: Calling a setter leaves the variable unchanged until the next render

A developer builds a reader rating widget for stories. When a reader clicks five stars, the widget must update the screen to show 5 stars. The developer calls `setRating(5)` and logs `rating` on the very next line:

```jsx title="StoryFeedback.jsx, first attempt" startLine="6"
  function handleFiveStars() {
    setRating(5); // Requests next render with 5
    console.log('rating after setter:', rating); // Still prints 0 here
  }
```

The developer opens the browser and clicks the five-star button. The development console prints `rating after setter: 0`. A body log placed at the top of the component prints `render rating = 5` only after the click handler completes, when the button on screen changes to show 5 stars. In a boost button calling `setRating(rating + 1)` three times, the screen moves from 0 to 1 instead of 3.

**I call setRating(5) and log the rating on the next line. Why does it still print 0?**

---

**ANSWER**

**The code does not do what we wanted.** In plain JavaScript, assigning a variable with `=` changes it immediately, but React treats state as a snapshot fixed for an entire render.

In plain JavaScript, assigning a variable with `rating = 5` overwrites memory in place. In React, `const [rating, setRating] = useState(0)` provides the running function with a constant value `0` for this specific execution. React stores component state outside the function body. Calling `setRating(5)` does not mutate the variable in the running code; it stores `5` in React internal storage and queues a future render.

Every line inside the current handler continues reading the constant `0`. Furthermore, when calling `setRating(rating + 1)` three times in one handler, the substitution method shows that each line evaluates `0 + 1` and asks React to replace the value with `1`. After the handler returns, React executes the new render, where `useState` returns `5` (or `1`), and the component calculates its new JSX.

```ascii title="State as a Snapshot During Handler Execution"
[User Clicks "5 Stars"]
      |
      v
[handleFiveStars Execution: rating is constant 0]
  - setRating(5) queues 5 for next render
  - console.log(rating) reads constant: prints 0
      |
      v
[React Re-renders StoryFeedback with rating = 5]
```

When code inside the handler needs the new value immediately, compute the next value once in a local variable: `const nextRating = 5; setRating(nextRating); console.log('rating =', nextRating);`.

> [!PRINCIPLE]
> **Principle 1: A state variable keeps one value for the whole render**
> React provides each component run with a fixed **snapshot** of its state. In that run, a state variable is a standard JavaScript constant. Calling a setter does not change that constant in your running code. The setter only tells React what value to return on the next run. So reading the state variable on the line after the setter still reads the value from the current run. The new value exists only when React calls the component again.
>
> >> snapshot : the fixed set of values React gives to one run of a component
>
> *We should do this:*
> `const nextCount = count + 1; // compute the value once`
> `setCount(nextCount);`
> `console.log(nextCount); // logs 1 in this handler`
>
> *We should not do this:*
> `setCount(count + 1);`
> `console.log(count); // prints the old count, 0`

### Question 2: Calling an API after a setter sends the old value unless computed once

The developer now connects the rating widget to an analytics helper named `sendRating`. When a reader clicks five stars, the component must update the screen and notify the analytics server:

```jsx title="StoryFeedback.jsx, sending rating" startLine="6"
  function handleFiveStars() {
    setRating(5); // Schedules next render with 5
    sendRating(rating); // Sends stale snapshot value 0!
  }
```

The developer clicks the five-star button. The screen updates to show 5 stars. But the analytics server records a rating of 0 stars.

**When the reader clicks 5 stars, I set the rating and send it to the server. Which value do I give sendRating?**

---

**ANSWER**

**The code does not do what we wanted.** The function `sendRating` executes inside the running handler where `rating` is still 0.

The developer expects `rating` to hold 5 because `setRating(5)` was just called on the preceding line. But `rating` is a constant `0` for the entire execution of this handler. Passing `rating` to `sendRating(rating)` passes `0`. The server receives a rating of 0 while the reader sees 5 stars on screen, creating a silent telemetry defect.

To synchronize the server payload with the requested UI state, the handler must compute the next value once in a local variable before calling the setter. Calling `const nextRating = 5; setRating(nextRating); sendRating(nextRating);` gives `5` to React for the next render and passes `5` to the network helper immediately.

```ascii title="Sending Stale State Versus Computed Next Value"
[BROKEN APPROACH]
  setRating(5);
  sendRating(rating);      ---> Sends 0 (stale snapshot)
  Screen updates to 5      ---> Server has 0, UI shows 5 (MISMATCH)

[CORRECT APPROACH]
  const nextRating = 5;    ---> Computed once in local variable
  setRating(nextRating);   ---> Queues 5 for screen
  sendRating(nextRating);  ---> Sends 5 to server (IN SYNC)
```

By computing the next value once in a variable, both the state setter and the external helper receive the identical value.

> [!PRINCIPLE]
> **Principle 2: Compute the next value once and use it after the setter**
> When an event handler must update state and notify an outside service or API, do not read the state variable right after calling the setter. The state variable still holds the value from the current run. Instead, calculate the new value once in a local variable. Pass that variable to the setter to schedule the screen update, and pass the same variable to the outside function.
>
> *We should do this:*
> `const nextCount = 5; // compute next value once`
> `setCount(nextCount);`
> `sendCount(nextCount); // sends 5 to the server`
>
> *We should not do this:*
> `setCount(5);`
> `sendCount(count); // sends old count 0 to server`

### Question 3: A delayed timer callback keeps reading the rating from its own render

The developer adds a Send Confirmation button that schedules an alert using `setTimeout`. When clicked, the widget waits 100 milliseconds and prints a confirmation message:

```jsx title="StoryFeedback.jsx, delayed confirmation" startLine="10"
  function handleSend() {
    setTimeout(() => {
      console.log('Thanks for rating ' + rating); // Reads captured snapshot
    }, 100);
  }
```

The user rates 5 stars, clicks Send Confirmation, and quickly clicks 2 stars before the 100-millisecond timer expires. The screen updates to show 2 stars, but the timer callback prints "Thanks for rating 5" in the console.

**If the rating changes before the timer fires, which number does the message show?**

---

**ANSWER**

**The code works as expected.** The timer callback is a JavaScript closure that retains the state snapshot of the render that created it.

A developer might expect the delayed callback to read the newest rating (2) because it executes after the screen has already re-rendered. In JavaScript, an inner function forms a closure that captures the variables in scope when the function was created. The render where `rating` was 5 created its own Send handler. Clicking Send created a timer callback that closed over that render constant `rating` value of 5.

When the user later clicked 2, React re-rendered `StoryFeedback` with a new constant `rating = 2` and generated fresh event handlers for the new screen. That second render does not mutate the variables held by the existing timer callback. When the timer fires, it reads the 5 from its own render snapshot.

```ascii title="Closure Capture Across Component Re-renders"
[Render 1: rating = 5]
  |-- "Send" schedules timer (closure captures 5)
  |
  +--> [User clicks 2 Stars -> Render 2: rating = 2]
         |-- Screen updates to 2 Stars
         |
         +--> [Timer expires after 100ms]
                |-- Runs callback from Render 1
                |-- Prints "Thanks for rating 5"
```

This snapshot behavior is a protective feature. If a user sends a chat message to Alice and immediately switches the active recipient to Bob, a delayed network timeout or confirmation alert still sends the message to Alice, preventing race conditions.

> [!PRINCIPLE]
> **Principle 3: An event handler keeps the state of the render that created it**
> Every time React runs a component, that run creates its own fresh event handler functions. In JavaScript, an inner function is a **closure**: it remembers the variables of the function call where it was created. When a timer or delayed callback is scheduled, it closes over the state variables of that specific run. If a later click changes state and causes React to run the component again, the new run gets new state variables and new handlers. The earlier timer callback continues running with the values from the run that created it.
>
> >> closure : a JavaScript function that remembers variables from the scope where it was defined
>
> *We should do this:*
> `function handleSend() {`
> `  setTimeout(() => {`
> `    console.log(`Rating: ${count}`); // reads count from this render`
> `  }, 3000);`
> `}`

### Step 1: First, we lay out the feedback application <src/App.jsx>

In `src/App.jsx`, we establish the outer application shell. The root component renders the main title and mounts the `StoryFeedback` widget.

Notice that `App` owns zero interactive state. Because `App` does not declare `useState`, state changes triggered by user interactions inside `StoryFeedback` remain encapsulated within the child component. React re-renders only `StoryFeedback` and its subtree, keeping the outer layout stable.

```jsx title="App.jsx" startLine="1"
import StoryFeedback from './components/StoryFeedback.jsx';

export default function App() {
  return (
    <main className="feedback-app">
      <h1>Reader Ratings</h1>
      <StoryFeedback /> {/* State owner boundary */}
    </main>
  );
}
```

This structural separation ensures that user interactions do not trigger unnecessary top-level re-renders.

### Step 2: Next, we build the rating boundary <src/components/StoryFeedback.jsx>

In `src/components/StoryFeedback.jsx`, we construct the interactive rating boundary. This component owns the `rating` state variable using `useState(0)`.

We declare the `handleRate` action handler. When the user selects a score, `handleRate` computes `nextRating` in a local variable. It passes `nextRating` to `setRating` to schedule the next render, and synchronously logs the value to simulate sending it to an analytics server.

```jsx title="StoryFeedback.jsx" startLine="1" continues="bottom"
import { useState } from 'react';
import RatingControls from './RatingControls.jsx';

export default function StoryFeedback() {
  const [rating, setRating] = useState(0); // Snapshot constant for this render
  function handleRate(newScore) {
    const nextRating = newScore; // Compute next value once
    setRating(nextRating);
    console.log('Sending rating:', nextRating); // Sends fresh computed value
  }
```

Computing `nextRating` once guarantees that both the state update and the external side effect operate on the identical number.

Next, we implement `handleBoost` and `handleSend` to verify repeated updates and delayed closure capture.

Calling `setRating(rating + 1)` three times in `handleBoost` evaluates against the current snapshot value, demonstrating why one click increments the score by one. In `handleSend`, scheduling `setTimeout` creates a closure that permanently captures the rating of the render that created it.

```jsx title="StoryFeedback.jsx" startLine="10" continues="both"
  function handleBoost() {
    setRating(rating + 1); // Evaluates 0 + 1 against current snapshot
    setRating(rating + 1);
    setRating(rating + 1); // Queues 1 three times
  }
  function handleSend() {
    setTimeout(() => {
      console.log(`Confirmed rating: ${rating}`); // Closure captures snapshot
    }, 1500);
  }
```

Finally, we complete `StoryFeedback.jsx` by rendering the card container, displaying the score, and passing action handlers downward to `RatingControls`.

```jsx title="StoryFeedback.jsx" startLine="20" continues="top"
  return (
    <div className="feedback-card">
      <p className="score">Score: {rating}</p> {/* Shows render snapshot */}
      <RatingControls
        onRate={handleRate}
        onSend={handleSend}
      />
    </div>
  );
}
```

The component passes its state and handler functions downward to `RatingControls`.

### Step 3: Finally, we build the rating action controls <src/components/RatingControls.jsx>

In `src/components/RatingControls.jsx`, we create the button controls that trigger user actions.

Notice that `RatingControls` owns zero local state. It receives callback functions from its parent and wires them directly to button click events. When a user clicks a button, the callback executes in `StoryFeedback` memory, demonstrating inverse data flow.

```jsx title="RatingControls.jsx" startLine="1"
export default function RatingControls({ onRate, onSend }) {
  return (
    <div className="rating-actions">
      <button onClick={() => onRate(5)}>Rate</button> {/* Upward action */}
      <button onClick={onSend}>Send</button> {/* Upward timer trigger */}
    </div>
  );
}
```

This presentation leaf remains decoupled from state storage, delegating all state transitions upward to its parent boundary.

### Where you will meet this

In production applications, understanding state snapshots is vital when sending analytics telemetry, dispatching API requests, and managing delayed notifications. A frequent bug occurs when an engineer calls a state setter and immediately passes the state variable to an analytics helper on the next line, causing telemetry pipelines to record outdated values. Computing the value once in a local variable resolves this issue permanently.

Another universal scenario involves form submissions with delayed confirmation toasts or undo banners. When a user submits an item and quickly navigates or edits another record, delayed timer callbacks rely on closure capture to display the exact data submitted at that moment, rather than whatever record the user is currently editing.

Interviewers frequently probe candidate understanding of state snapshots by asking whether `setState` is asynchronous or by presenting code snippets that call a setter three times in a single handler. Candidates who explain that state variables are render constants and demonstrate the substitution method immediately distinguish themselves.

### For the interview

> **The Interview Question:** Why does state appear frozen inside a render, even right after you set it?

**1. The Hidden Signal**

The interviewer is probing whether you understand React declarative execution lifecycle and closure mechanics, or whether you still hold an imperative mental model where setters mutate variables in place. Senior engineers explain that React keeps state outside the component and provides each render with an immutable snapshot. They clearly articulate that setters schedule future renders rather than altering variables in currently executing code.

**2. The Classic Trap**

The classic trap is claiming that "setState is asynchronous, so the variable has not updated yet." This answer confuses the timing of the next render with variable mutability. Even if JavaScript waited, the state variable inside the current function execution is a `const` primitive; no background process could mutate a local constant in running JavaScript. Another frequent trap is trying to fix the old value by adding a `setTimeout(..., 0)`, unaware that the callback still closes over the same render snapshot.

**3. What is Actually Going On**

React calls your component function to render the user interface. During that call, `useState` returns the state value for that specific render. Inside that function execution, the state variable is a constant. Calling a state setter queues a request for React to run the component again with a new value during the next render. The current function continues executing using its existing snapshot values. If code inside the handler needs the new value immediately, it must calculate that value once in a local variable and use it for both the setter and subsequent operations.

**4. Where It Gets Tricky**

What happens across an `await` pause in an asynchronous handler? If a handler awaits a network request and reads state after the promise settles, it still reads the snapshot value from the render that created it, even if user clicks in the meantime caused React to re-render. What happens with repeated setter calls? Calling `setCount(count + 1)` three times queues three requests to replace state with `0 + 1`, incrementing the counter by only one. What if code genuinely requires reading the latest mutable value across renders without triggering updates? That requirement calls for a ref (`useRef`), which React provides specifically for mutable storage outside the render snapshot.

### Glossary

- **Snapshot**: The immutable set of state values, props, and event handlers provided by React for a single execution of a component function.
- **State Variable**: A constant value returned by useState that reflects the component data for the current render.
- **Setter Function**: The update function returned by useState that records a requested value in React and schedules a future render.
- **Closure**: A JavaScript function that retains access to variables from its defining lexical scope, even when executed at a later time.
- **Substitution Method**: The mental debugging technique of replacing state variables with their concrete render values to predict handler behavior.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Declarative State Snapshots

➔ ALWAYS treat state variables as immutable constants for the duration of a single render.

➔ NEVER expect a state setter call to modify the state variable in the currently executing code block.

➔ IF an event handler needs to use an updated value immediately THEN compute the next value once in a local variable before calling the setter.

**DO THIS:** compute next value once and pass to setter and tracker
```jsx right
function handleRate() {
  const nextRating = 5;
  setRating(nextRating);
  sendAnalytics(nextRating);
}
```

**DO NOT DO THIS:** read state variable immediately after calling setter
```jsx wrong
function handleRate() {
  setRating(5);
  sendAnalytics(rating);
}
```

❒ Event Handler Closures & Timing

➔ ALWAYS expect event handlers and timers to capture the state snapshot from the render that created them.

➔ NEVER assume delayed callbacks or code after `await` will automatically see future state values from subsequent renders.

➔ IF multiple updates must chain together in a single handler THEN use an updater function in Lecture 17.

| | **MUTABLE MEMORY HABIT**<br>(Plain JavaScript Variables) | **DECLARATIVE SNAPSHOT**<br>(React State Architecture) |
| ---: | :--- | :--- |
| **Variable mutability** | Reassigning with `=` modifies variable immediately on that line | State variable is a `const` for the duration of that render |
| **Setter execution** | Modifies memory in place synchronously before next statement | Records next value in React and schedules a future render |
| **Subsequent reads** | Code on next line reads the newly assigned value | Code on next line continues reading the current snapshot value |
| **Repeated updates** | Three increment statements produce three sequential mutations | Three calls evaluate against same snapshot, requesting one update |
| **Delayed callbacks** | Timer callback reads whatever value exists in memory at fire time | Closure captures snapshot from the render where timer was created |
| **Side effect sharing** | Reads variable directly after mutation to pass to network calls | Computes next value once in a local variable and passes to both |
