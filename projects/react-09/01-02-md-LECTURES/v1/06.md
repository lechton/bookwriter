### One component displays many different articles

An article list displays the same card frame again and again: the same layout, but a different title, a different author, and a different reading time. In Lecture 5, `ArticleCard` held its title inside its own markup, so every copy showed the same text. Declaring a constant at the top of the file does not solve this either: a file-level variable gives every copy the exact same value. In Lecture 5, we saw that a value that belongs to the page starts in a parent component and travels down the tree. So every React developer meets the same question: how does each copy of a component receive its own distinct values?

The answer is one idea, and this chapter follows it from the first question to the last: props are a component's arguments: the parent writes them on the tag, and the component reads them as one object. The chapter follows the life of one prop: written on the tag, read in the function, missing from the tag, and kept unchanged.

This lesson answers four questions:

- **My three `ArticleCard`s show the same story. How do I give each its own headline?**
- **How do I get `title` out of the props?**
- **What if a parent leaves out a prop?**
- **Can the card change its own title, to show it in capitals?**

The questions stand on what earlier lessons established:

- **Lecture 3 (JSX syntax)**: An **object** keeps values under names, called its **properties**. The build turns each JSX tag into a call, and `npm run build` makes the production files for the published site.
- **Lecture 4 (JavaScript expressions in JSX with curly braces)**: Quotes pass text strings, and **curly braces** pass a JavaScript value, such as a number or an object literal. In React rendering, `null` and `undefined` display nothing, while an object cannot be shown as text: React stops with "Objects are not valid as a React child".
- **Lecture 5 (UI as a tree and component hierarchy)**: Components form a render tree with `App` at the root. A component sees only its own variables, so a shared value needed by several components starts above them in the tree and travels downward.

### A function's parameters receive the values of a call

A JavaScript function lists variable names inside its parentheses: its **parameters**. When other code calls the function, the values supplied in that call are its **arguments**, and each parameter takes the argument provided in its matching position.

```js title="Plain JavaScript: parameters and arguments"
function headline(title, readTime) {
  return title + ', ' + readTime + ' min read'; // formats parameters
}
headline('Rail Strike Ends', 5); // arguments for first call
headline('New Park Opens Today', 2); // arguments for second call
```

In this function, `title` and `readTime` are parameters. In the first call, the string `'Rail Strike Ends'` and the number `5` are arguments. The second call passes different arguments to produce a different result.

### Destructuring takes properties out of an object by name

Reading several properties from an object often takes multiple lines of repetitive assignments, such as `const title = article.title;`. JavaScript **destructuring** extracts properties in a single statement: variable names placed inside curly braces on the left side of an assignment extract the matching property names from the object on the right side. If an extracted property does not exist on the object, it receives `undefined`, unless a **default value** follows the variable name after an equals sign.

```js title="Plain JavaScript: destructuring with a default"
const article = { title: 'Rail Strike Ends', readTime: 5 };
const { title, readTime, topic = 'News' } = article; // unpacks properties
console.log(title, readTime, topic); // logs unpacked values
```

The curly braces on the left extract `title` and `readTime` directly from the object. Because `topic` is absent on `article`, it takes the default value `'News'`. The exact same destructuring syntax works inside a function's parameter list, unpacking an incoming argument object directly.

### Two operators fall back to a default value

JavaScript provides two operators to supply fallback values when a variable might be empty: logical OR (`||`) and nullish coalescing (`??`).

```js title="Plain JavaScript: fallbacks with OR and nullish coalescing"
const missingTime = undefined;
const zeroTime = 0;
console.log(missingTime ?? 3); // 3: nullish coalescing fills fallback
console.log(zeroTime || 3);
console.log(zeroTime ?? 3); // 0: nullish coalescing preserves valid 0
```

The logical OR operator (`a || b`) returns `b` whenever `a` is falsy: `0`, an empty string `""`, `null`, `false`, and `undefined` all trigger the fallback. The nullish coalescing operator (`a ?? b`) returns `b` only when `a` is strictly `null` or `undefined`. Because `0` is a valid number of minutes for a short update, `0 ?? 3` preserves `0`, whereas `0 || 3` mistakenly replaces it with `3`.

### Some objects cannot be changed

JavaScript strings provide built-in methods to transform text. Calling `'Rail Strike Ends'.toUpperCase()` returns a brand-new uppercase string `'RAIL STRIKE ENDS'` while leaving the original string completely unchanged.

```js title="Plain JavaScript: frozen objects and string methods"
const text = 'Rail Strike Ends';
const upper = text.toUpperCase(); // returns new string without modifying text
const settings = Object.freeze({ readTime: 3 });
settings.readTime = 5; // throws TypeError in strict mode / modules
```

JavaScript can lock an object using `Object.freeze()`. Once an object is **frozen**, modifying or reassigning its properties is forbidden. In JavaScript ES modules, which all modern React files are, attempting to mutate a frozen property throws a **`TypeError`**. However, this freeze is shallow: if an object contains nested objects or arrays, those inner structures remain mutable.

The production command `npm run build` generates a **production build** that omits these extra checks so the application runs as fast and lean as possible in production.

### Principles of React: Props Are a Component's Arguments

Everything in this lesson comes down to one idea: props are a component's arguments, written by the parent and read by the component as one object.

First, props, which means the attributes on a component's tag arrive as one object, its only argument: each card gets its own headline because each tag carries its own.

Second, destructuring, which means the component names the props it reads, inside curly braces in its parameter list: without the braces, the whole object lands in the first name.

Third, default values, which means the component names a fallback for a prop the tag leaves out: the fallback fills a missing prop, but not a null and not a zero.

Fourth, read-only props, which means the component reads its props and never changes them: to show a value differently, it makes a new variable.

### Question 1: Three tags carry three stories, and the card ignores them

A developer wants to render three distinct article cards on the page. In `App.jsx`, `App` renders three `<ArticleCard />` tags, giving each tag its own `title` attribute and `readTime` attribute. In `ArticleCard`, the developer accepts `props`, logs it to the Console panel, but continues to return fixed markup:

```jsx title="App.jsx" startLine="1" continues="bottom"
function ArticleCard(props) {
  console.log('ArticleCard props:', props); // logs input props object
  return <h2>City Library Extends Its Hours</h2>;
}
```

In `App`, three tags specify three different headlines and reading times:

```jsx title="App.jsx" startLine="5" continues="both"
export default function App() {
  return (
    <main>
      <ArticleCard
        title="City Library Extends Its Hours"
        readTime={3}
      /> {/* first card attributes */}
```

The remaining two tags complete the list:

```jsx title="App.jsx" startLine="12" continues="top"
      <ArticleCard title="Rail Strike Ends" readTime={5} />
      <ArticleCard
        title="New Park Opens Today"
        readTime={2}
      /> {/* third card */}
    </main>
  );
}
```

The browser page displays the exact same heading "City Library Extends Its Hours" three times with zero errors or warnings. But when opening the Console panel, three different JavaScript objects appear: `{ title: 'City Library Extends Its Hours', readTime: 3 }`, `{ title: 'Rail Strike Ends', readTime: 5 }`, and `{ title: 'New Park Opens Today', readTime: 2 }`.

**My three `ArticleCard`s show the same story. How do I give each its own headline?**

---

**ANSWER**

**The code does not do what we wanted.** `ArticleCard` ignores its input argument and renders fixed markup.

React collects every attribute written on a component tag into a single JavaScript object, called **props**, and passes that object as the single argument to the component function. Writing attributes on a tag does not alter the DOM on its own; it merely delivers the data to the component. Because `ArticleCard` never read from its `props` argument, it rendered the same hardcoded text on every call.

The fix is to read the properties from the `props` object inside JSX curly braces: `props.title` and `props.readTime`. Once `ArticleCard` reads from `props`, each card displays its own title and reading time.

```jsx title="App.jsx" startLine="1"
function ArticleCard(props) {
  return (
    <article>
      <h2>{props.title}</h2>
      <p>{props.readTime} min read</p> {/* reads props object */}
    </article>
  );
}
```

Passing values follows the rules established in Lecture 4: quotes pass text strings, while curly braces pass dynamic JavaScript expressions. If you write `readTime="5"`, the value arrives as the string `"5"`, and `{props.readTime + 1}` produces `"51 min read"`. Writing `readTime={5}` delivers the actual number `5`, so `{props.readTime + 1}` calculates `6`. Props can carry any JavaScript value: numbers, booleans, arrays, or objects like `writer={{ name: 'Samantha Robinson', city: 'Denver' }}`. Content written between opening and closing tags arrives through a specialized prop named `children`, which Lecture 7 explores.

```ascii title="How React collects tag attributes into props objects"
TAG ON CALL SITE                       PROPS OBJECT PASSED TO COMPONENT
<ArticleCard title="News" readTime={3} />  -->  { title: 'News', readTime: 3 }
<ArticleCard title="Park" readTime={2} />  -->  { title: 'Park', readTime: 2 }
```

> [!PRINCIPLE]
> **Principle 1: Props: the attributes on a component's tag arrive as one object, its only argument**
> *We give each copy of a component its own values by writing them as attributes on its tag; React collects them into one object, the props, and passes it as the component's only argument.*
>
> We might expect attributes written on a component tag to appear automatically on the page. But a component tag is a function call descriptor, not an HTML element. React gathers every attribute written on the tag into a single **props** object and passes that object as the component function's only argument. A component displays nothing from its tag until its function body explicitly reads from that object. Quotes pass literal text strings, while curly braces pass evaluated JavaScript values such as numbers, arrays, and objects.
>
> >> props : the single object React passes to a component holding all tag attributes
>
> *We should do this:*
> `function ContactCard(props) {`
> `  return <p>{props.name}, {props.city}</p>; // reads props from tag`
> `}`
> `<ContactCard name="John Hall" city="Austin" />; // passes attributes`
>
> *We should not do this:*
> `function ContactCard(props) {`
> `  return <p>John Hall, Austin</p>; // hardcoded fixed values`
> `}`
> `<ContactCard name="Mary Jones" city="Denver" />; // tag values ignored`

### Question 2: Two names in the parentheses crash the page

Typing `props.` before every variable feels verbose. A developer with standard JavaScript habits decides to list parameters individually in the component definition:

```jsx title="App.jsx" startLine="1"
function ArticleCard(title, readTime) {
  return (
    <article>
      <h2>{title}</h2> {/* crashes: object is not valid child */}
      <p>{readTime} min read</p>
    </article>
  );
}
```

Save the file. The browser screen immediately goes blank, and the Console panel logs a fatal error: `Uncaught Error: Objects are not valid as a React child (found: object with keys {title, readTime})`.

**How do I get `title` out of the props?**

---

**ANSWER**

**The code does not do what we wanted.** React passes all props inside a single object rather than separate arguments.

In plain JavaScript, functions often accept multiple arguments. But React component functions always receive exactly one argument: the props object. When `ArticleCard(title, readTime)` declares two parameters, JavaScript assigns the first argument (the entire props object `{ title: '...', readTime: 5 }`) to `title`. The second parameter `readTime` receives `undefined`. When React attempts to render `{title}` inside `<h2>`, it encounters a plain JavaScript object. As Lecture 4 demonstrated, React forbids rendering objects directly as text children to prevent accidental data corruption, and the application crashes.

The fix is parameter **destructuring**: wrapping the parameter names in curly braces `function ArticleCard({ title, readTime })`. The curly braces instruct JavaScript to unpack the properties `title` and `readTime` directly from the single incoming props object into local variables.

```jsx title="App.jsx" startLine="1"
function ArticleCard({ title, readTime }) {
  return (
    <article>
      <h2>{title}</h2>
      <p>{readTime} min read</p> {/* unpacked from props */}
    </article>
  );
}
```

The destructured parameter names must match the attribute names written on the tag. If a tag writes `title="Rail Strike Ends"` but the component destructures `{ headline }`, the variable `headline` evaluates to `undefined`, and the heading renders completely blank without an error. Destructuring props in the parameter list is the standard idiom in modern React applications.

> [!PRINCIPLE]
> **Principle 2: Destructuring: the component names the props it reads, inside curly braces in its parameter list**
> *We read props by naming them inside curly braces in the parameter list, `({ title, readTime })`, with the same names the tag uses.*
>
> We might expect a component to accept several arguments like a standard JavaScript function. But React always passes exactly one argument: the props object. If we declare parameters without curly braces, the first parameter absorbs the entire object, and subsequent parameters become `undefined`. When the component attempts to render that first parameter, React crashes because objects cannot be rendered directly as text. We use **destructuring** by wrapping parameter names in curly braces `({ title, readTime })`, extracting values by name to match the tag attributes.
>
> >> destructuring : unpacking properties from an object directly into named variables
>
> *We should do this:*
> `function ContactCard({ name, city }) { // destructures props by name`
> `  return <p>{name}, {city}</p>; // displays each unpacked value`
> `}`
>
> *We should not do this:*
> `function ContactCard(name, city) { // receives entire object in name`
> `  return <p>{name}</p>; // crashes: object is not valid React child`
> `}`

### Question 3: A prop the tag leaves out leaves a hole

A developer renders `<ArticleCard title="Rail Strike Ends" />`, omitting the `readTime` attribute. Remembering an older tutorial, the developer attaches a `defaultProps` property to `ArticleCard` to provide a fallback:

```jsx title="App.jsx" startLine="1" continues="bottom"
function ArticleCard({ title, readTime }) {
  return <p>{title}: {readTime} min read</p>; // shows " min read"
}
ArticleCard.defaultProps = { readTime: 3 }; // ignored in React 19
```

`App` renders the card without a reading time:

```jsx title="App.jsx" startLine="5" continues="top"
export default function App() {
  return <ArticleCard title="Rail Strike Ends" />; // readTime omitted
}
```

The browser displays "Rail Strike Ends:  min read" with an empty hole where the number should be. React 19 displays no warning in the console, completely ignoring the `defaultProps` assignment.

**What if a parent leaves out a prop?**

---

**ANSWER**

**The code does not do what we wanted.** An omitted prop evaluates to `undefined`, which renders as empty space.

When a parent component omits an attribute from a JSX tag, that property is absent from the props object, so destructuring assigns it `undefined`. As Lecture 4 showed, React renders `undefined` as empty text. Furthermore, React 19 officially removed support for `defaultProps` on function components, rendering older tutorial patterns useless.

The fix is to assign a **default value** directly inside the destructuring braces using the equals sign: `function ArticleCard({ title, readTime = 3 })`. If the parent tag omits `readTime` or explicitly passes `readTime={undefined}`, JavaScript fills the fallback value `3`.

```jsx title="App.jsx" startLine="1"
function ArticleCard({ title, readTime = 3 }) {
  return (
    <article>
      <h2>{title}</h2>
      <p>{readTime} min read</p> {/* defaults to 3 when omitted */}
    </article>
  );
}
```

A default value activates only when the prop is `undefined` or omitted. If a parent passes `readTime={null}`, the value is explicitly defined as `null`, so the default `3` does not trigger, and the card renders empty text. If a parent passes `readTime={0}`, `0` is a valid number, so the card renders `"0 min read"`. Avoid using legacy logical OR fallbacks like `readTime || 3` in component bodies, because `0 || 3` mistakenly replaces a valid zero with `3`. Use default values whenever a prop has a natural, predictable fallback.

```ascii title="Fallback behavior for missing and defined props"
PROP WRITTEN ON TAG         VALUE OF readTime    readTime = 3 RENDERS
(omitted attribute)         undefined            3 min read (default used)
readTime={undefined}        undefined            3 min read (default used)
readTime={null}             null                   min read (null shows nothing)
readTime={0}                0                    0 min read (zero preserved)
```

> [!PRINCIPLE]
> **Principle 3: Default values: the component names a fallback for a prop the tag leaves out**
> *When a component has a sensible fallback, we write it beside the prop's name, `readTime = 3`, and we remember that it fills only a missing or `undefined` prop, never `null` or `0`.*
>
> When a tag omits an attribute, the destructured prop evaluates to `undefined`, producing empty gaps in the rendered text. React 19 ignores legacy `defaultProps` declarations on function components. When a prop has a sensible fallback, assign a **default value** directly inside the parameter destructuring braces using `=`. The fallback activates only when the prop is omitted or explicitly passed as `undefined`. Real values like `null` or `0` are preserved.
>
> >> default value : a fallback assigned when an attribute is missing or undefined
>
> *We should do this:*
> `function ContactCard({ name, phone = 'not listed' }) { // fallback`
> `  return <p>{name}: {phone}</p>; // shows fallback when omitted`
> `}`
>
> *We should not do this:*
> `function ContactCard({ name, phone }) { // no fallback provided`
> `  return <p>{name}: {phone}</p>; // leaves empty text when omitted`
> `}`

### Question 4: Changing a prop crashes in development and ships in production

A designer requests that every article title appear in capital letters. A developer decides to transform the title in place by assigning to `props.title`:

```jsx title="App.jsx" startLine="1"
function ArticleCard(props) {
  props.title = props.title.toUpperCase(); // throws TypeError in dev
  return <h2>{props.title}</h2>;
}
```

In the local development server, the page goes blank, and the Console panel throws `TypeError: Cannot assign to read only property 'title' of object '#<Object>'`. But when the developer runs `npm run build` and tests the production build with `npm run preview`, the error disappears, and the headlines display in uppercase letters.

**Can the card change its own title, to show it in capitals?**

---

**ANSWER**

**The code does not do what we wanted.** React freezes the props object in development, and mutating props violates component purity.

Props belong to the parent component that created them. A child component is a pure function that must treat its incoming arguments as **read-only**. To catch accidental mutations during development, React runs `Object.freeze()` on every props object. Modifying a frozen object in an ES module triggers a `TypeError`. However, to maximize speed in production, React omits `Object.freeze()`. The mutation silently succeeds in production, meaning an application that passed code review can ship with hidden state corruption.

The danger is worse with object props. Because React's development freeze is shallow, nested objects are never frozen. If `ArticleCard` receives a `writer` object and executes `writer.name = writer.name.toUpperCase()`, neither development nor production throws an error. But this mutates the shared object in browser memory, unexpectedly altering the author name across every other component on the page that references that same object, such as an `AuthorBox`.

```jsx title="App.jsx" startLine="1"
function ArticleCard({ writer }) {
  writer.name = writer.name.toUpperCase(); // shallow mutation succeeds
  return <h2>By {writer.name}</h2>;
}
```

The fix is to derive a new local variable during render: `const headline = title.toUpperCase()`.

```jsx title="App.jsx" startLine="1"
function ArticleCard({ title }) {
  const headline = title.toUpperCase(); // derives local uppercase value
  return <h2>{headline}</h2>; // leaves props object untouched
}
```

Deriving a local variable leaves the incoming props completely untouched. As Lecture 12 explains in detail, React components must remain pure, never mutating any inputs during rendering. If a displayed value must change dynamically over time in response to user actions, the parent component must pass new props, or the component must manage local state, which Lecture 14 introduces. Choosing which elements to render based on props using conditionals is covered in Lecture 10.

```ascii title="Shallow freeze leaves nested objects mutable"
props object (FROZEN by React in dev)
+------------------------------------+
| title: "New Park Opens Today"      |
| writer: [Ref: Object in memory] ---+--> writer object (NOT FROZEN)
+------------------------------------+    +----------------------------+
                                          | name: "Samantha Robinson"  |
                                          +----------------------------+
                                                    ^
                                          AuthorBox | also points here
```

> [!PRINCIPLE]
> **Principle 4: Read-only props: the component reads its props and never changes them**
> *We never change a prop or an object inside one; to show a value differently, we make a new variable, `const headline = title.toUpperCase()`, and a value that must change comes from the parent.*
>
> We might expect to modify a component's props like any ordinary JavaScript object. But props belong to the parent that declared them. In development, React freezes the props object, making it **read-only** and throwing a `TypeError` on assignment. Production builds skip this freeze for speed, allowing bugs to ship silently. The freeze is also shallow, so mutating an object inside a prop corrupts data across every component sharing that reference. To format a value differently, derive a new local variable.
>
> >> read-only : an object whose properties cannot be modified after creation
>
> *We should do this:*
> `function ContactCard({ name }) {`
> `  const upper = name.toUpperCase(); // derives new local variable`
> `  return <p>{upper}</p>; // leaves original props untouched`
> `}`
>
> *We should not do this:*
> `function ContactCard(props) {`
> `  props.name = props.name.toUpperCase(); // throws TypeError in dev`
> `  return <p>{props.name}</p>;`
> `}`

> [!WILD]
> **Are props the same as HTML attributes?**
> On a built-in HTML tag like `<img src="/photo.jpg" alt="Site logo" />`, the attributes look identical to props. We might wonder if React treats them the same way.
> However, there is a fundamental difference. On built-in HTML elements, React only accepts the specific attributes defined by the HTML standard and applies them directly to the browser DOM node. On our own custom components, we can invent any prop names we want. React does not send custom props to the DOM; it simply bundles all attributes into a single props object and hands it to our component function. Our component decides what to do with each value. Props can carry any JavaScript value: text strings, numbers, objects, arrays, and even functions, which Lecture 13 uses to handle user clicks.

### Step 2: Next, we read each prop by name <App.jsx>

This step applies Principle 2: Destructuring: the component names the props it reads, inside curly braces in its parameter list.

Now we connect the components to their props. `ArticleCard` destructures `{ title, readTime, author }` in its parameter list and forwards `author` down to `<AuthorName author={author} />`. `AuthorName` destructures `({ author })` to display the name. `SiteHeader` and `ArticleList` destructure `({ topic })`.

In `AuthorName`, lines 1 to 3 unpack and display the author prop:

```jsx title="App.jsx" startLine="1"
function AuthorName({ author }) {
  return <p className="author">By {author}</p>; // displays passed author
}
```

In `ArticleCard`, lines 4 to 12 unpack the card props and forward author downward:

```jsx title="App.jsx" startLine="4"
function ArticleCard({ title, readTime, author }) {
```

This step applies Principle 3: Default values: the component names a fallback for a prop the tag leaves out.

Every article card should display a section tag above its title, but only the third article card was passed `section="Sport"`. The first two cards omitted the section prop. Because most articles on the site cover general news, `'News'` is a natural default fallback.

### Step 4: Finally, we show the section in capitals without changing it <App.jsx>

This step applies Principle 4: Read-only props: the component reads its props and never changes them.

The design calls for the section badge to appear in uppercase letters: "NEWS", "NEWS", and "SPORTS". Because the section prop belongs to the parent list, `ArticleCard` must never mutate `section` directly.

What would happen if `ArticleCard` executed `section = section.toUpperCase()` or mutated `props.section`? In development, direct property mutation throws a fatal `TypeError`. In production, modifying shared objects causes unpredictable data corruption across other components. Instead, `ArticleCard` derives a new local variable `const label = section.toUpperCase();` and renders `{label}`.

### For the interview

> **The Interview Question:** How do you pass data into a component, and why can a component never change its own props?

**1. The Hidden Signal**

The interviewer is probing your understanding of unidirectional data flow and functional purity. A junior candidate treats props merely as HTML attributes and assumes a component can update its own props when its data changes. A senior engineer explains that props represent immutable input snapshots owned exclusively by the parent component. They articulate that maintaining props as read-only objects is essential for pure render contracts, predictable component re-rendering, and preventing cross-tree state corruption.

**2. The Classic Trap**

The classic trap is believing that props can be modified locally like ordinary JavaScript object arguments. Candidates often propose mutating a prop in place to format text or toggle a value. In development, React catches this by freezing the props object, triggering a fatal `TypeError`. However, because production builds omit `Object.freeze()` for performance, direct mutation appears to work in production while corrupting shared object references. Another trap is confusing missing props with `null`: a default value `= fallback` triggers only on `undefined`, leaving `null` values unchanged.

**3. What is Actually Going On**

When React evaluates JSX, it compiles element attributes into a plain JavaScript object and passes it as the first argument to the child component function. In development, React executes `Object.freeze()` on this props object. Because the freeze is shallow, nested objects remain technically mutable, but mutating them breaks component purity. When a component needs to display data differently, it derives a new local variable. When data must actually change over time, the change must be triggered in the parent via state, flowing downward as fresh props on the next render pass.

**4. Where It Gets Tricky**

*Why does `function Card(title, readTime)` fail to receive two arguments?*

React components always receive exactly one argument: the props object. In this definition, JavaScript binds the entire props object `{ title: '...', readTime: 5 }` to the parameter `title`, while `readTime` remains `undefined`. Attempting to render `{title}` inside JSX crashes because React cannot render objects as text children.

*Does a destructuring default value replace a `null` prop?*

No. JavaScript destructuring default values (`{ readTime = 3 }`) trigger strictly when the incoming property is `undefined` or omitted entirely. If a parent explicitly passes `readTime={null}`, `null` is a defined value, so the default does not activate and `readTime` remains `null`.

*Why does mutating `props.title` throw an error in development but succeed in production?*

In development, React calls `Object.freeze(props)` to catch impure side effects early. In production, React skips `Object.freeze()` to maximize rendering performance. In an ES module, modifying a frozen object throws a `TypeError`. In production, the assignment succeeds silently, masking bugs that corrupt application state.

*What happens when a child component mutates a nested object prop?*

Because `Object.freeze()` is shallow, nested objects are not frozen even in development. If a child modifies `user.name = 'New Name'`, the change mutates the underlying object in shared memory. Every other component in the tree that reads from that same `user` reference will display the mutated data, causing cross-tree state drift.

### Glossary

- **Props**: The single, read-only JavaScript object passed by React to a component function containing all attributes declared on its JSX tag.
- **Parameter and argument**: Parameters are variable names declared in a function signature; arguments are the concrete values passed during an invocation.
- **Destructuring**: A JavaScript syntax that unpacks properties from an object directly into distinct, named local variables.
- **Default value**: A fallback value assigned during destructuring that activates only when a property is omitted or equals `undefined`.
- **Nullish coalescing**: The JavaScript operator `??` that returns its right-hand operand only when its left-hand operand is `null` or `undefined`.
- **Frozen object**: A JavaScript object locked by `Object.freeze()` whose properties cannot be added, removed, or reassigned.
- **`TypeError`**: A standard JavaScript runtime error thrown when an operation cannot be performed, such as mutating a frozen property in strict mode.
- **Development and production builds**: Development builds include runtime sanity checks like object freezing; production builds omit them for speed.

### Summary

**Props are a component's arguments**

❒ Props: the attributes on a component's tag arrive as one object, its only argument

➔ ALWAYS pass data to child components by writing descriptive attributes on their JSX tags.

➔ NEVER assume writing attributes on a JSX tag updates the screen automatically; the child component must explicitly read and render those values.

❒ Destructuring: the component names the props it reads, inside curly braces in its parameter list

➔ ALWAYS wrap prop parameter names in curly braces `({ title, readTime })` to unpack the incoming props object directly.

➔ NEVER list multiple unbracketed parameters `(title, readTime)` in a component signature; the entire props object collapses into the first name.

❒ Default values: the component names a fallback for a prop the tag leaves out

➔ IF a prop has a natural fallback THEN assign a default value beside the prop name `({ readTime = 3 })` during destructuring.

➔ NEVER rely on legacy `defaultProps` in React 19, and never use `||` when zero is a valid numeric prop value.

❒ Read-only props: the component reads its props and never changes them

➔ ALWAYS compute derived values using new local variables `const headline = title.toUpperCase()` during rendering.

➔ NEVER assign to `props.title` or mutate nested object props; modifying props violates component purity and causes cross-tree corruption.

**Written on the tag, read by name, filled when missing, and never changed.**

**DO THIS:** read props by destructuring, assign defaults, and derive new values

```jsx right
function ArticleCard({ title, readTime = 3 }) {
```
