# Lecture 10: Conditional Rendering in React
> INTERVIEW QUESTION | ❱ CORE | How do you show, hide, or switch JSX based on a condition?

- Every article card on your site shows a title, an author, and a short summary.
- Some parts belong only to some articles: a "New" label, a comment count, a sign-in prompt for visitors.
- How does one component show a part in one case and leave it out in another?

### Some parts of a page appear only in some cases

Look at any website and count the parts that appear only sometimes. An online shop marks certain products "Sale". A messaging client shows a counter only when unread messages have arrived. A blog asks visitors to sign in, while greeting subscribers by name. The overall layout stays the same, while underlying data determines which parts appear. Every React developer meets the same question: how does a component show, hide, or switch a part of the page based on a condition?

The first answer comes from HTML and CSS. Every standard DOM element can carry the `hidden` boolean attribute, operating like the `disabled` attribute from Lecture 4:

```jsx title="Hiding with CSS"
<span className="new-label" hidden={!isNew}>New</span> {/* browser hides tag */}
```

When `isNew` evaluates to `false`, `!isNew` evaluates to `true`, causing the browser to apply the `hidden` attribute. The element remains in the live DOM tree: the Elements panel shows `<span class="new-label" hidden="">New</span>`, and the browser rendering engine skips painting it. Applying a CSS class with `display: none` behaves identically. This is **hiding with CSS**: the DOM node exists, and only visual presentation is turned off. It fits a user interface widget that must retain its exact position and internal state while hidden.

The second answer is React's approach: omit the element from the JSX tree entirely:

```jsx title="Conditional rendering"
{isNew && <span className="new-label">New</span>} {/* builds node if true */}
```

We read this as: if `isNew` is truthy, evaluate to the `<span>`; otherwise evaluate to false. When `isNew` is `false`, this expression hands React nothing to construct, so the Elements panel contains no `<span>` element. This mechanism is **conditional rendering**: each time a component executes, it decides which JSX elements to return, and React creates only those nodes in the DOM. React provides no proprietary template syntax for conditions; the choice relies entirely on standard JavaScript expressions and statements. Conditional rendering fits every dynamic element driven by data, and every element whose data might be missing, because unrendered JSX expressions never execute their children.

> [!WAYS]
> **Two ways to show a part of the page only in some cases**
>
> 1. Show a part only in some cases by **hiding with CSS** (HTML and Lecture 4): the element is always in the DOM, and an attribute such as `hidden` tells the browser not to draw it.
> 2. Show a part only in some cases with **conditional rendering** (this chapter): the component returns the element only when the condition holds, and otherwise React builds nothing.

This chapter focuses on conditional rendering. Everything follows one central anchor: **conditional rendering**, which means that each time it runs, a component chooses which JSX to return. The branching choices grow one piece at a time across our curriculum axis: none, one or nothing, one of two, and one of many. Lecture 73 returns to CSS-based hiding through React's `<Activity>` component, specifically for keeping user input and state alive while hidden.

This lesson answers four progressive architectural questions:
1. **Some days there is no featured article. How does the featured card show nothing instead of breaking the page?**
2. **The "New" label should show only on new articles, and the comment count only when there are comments. Do I need an `if` for that?**
3. **Signed-in readers see the summary, visitors see a sign-in prompt. Do I write two returns?**
4. **The comment line needs three wordings: no comments, one comment, many comments. Can I put one ternary inside another?**

### What we build on

- **Lecture 1: What is React**: `document.getElementById` locates an element by its `id`, and the **Elements panel** inspects the live DOM nodes currently constructed in the browser.
- **Lecture 2: Component anatomy**: React executes a component function whenever a JSX tag invokes it. `console.log` writes diagnostic output to the **Console panel**, and in Strict Mode, component function bodies execute twice in development. A function lacking an explicit return value returns **`undefined`**.
- **Lecture 3: JSX syntax**: An **object** stores key-value pairs as **properties**, accessed via dot notation: `article.title`. When a build fails to parse source code, Vite displays an **error overlay** covering the browser viewport.
- **Lecture 4: Curly braces in JSX**: Curly braces inside JSX embed an **expression** that computes a value. JavaScript **statements** like `if` belong above the `return` statement. The **ternary operator** selects between two values: `isLive ? 'Live now' : 'Recorded'`. Numbers render directly to the screen, whereas `true`, `false`, `null`, and `undefined` produce no visible output. The `+` operator concatenates strings.
- **Lecture 6: Props**: A component receives props as a single object and unpacks properties using destructuring: `function ArticleCard({ article })`. Quoted attributes pass raw strings, whereas curly braces pass live values. Logical OR (`||`) and nullish coalescing (`??`) supply fallback values. Reading a property on a non-object throws a runtime **`TypeError`**.
- **Lecture 7: Children**: The `children` prop receives elements passed between a component's opening and closing tags. An **array** stores multiple ordered values.
- **Lecture 8: Modules**: Components such as `ArticleCard` reside in separate modular files, requiring explicit imports in parent files.

### The card now receives one article object

Until now, `ArticleCard` received separate individual props: `title` and `author`. Because our article model now tracks summaries, publication status, and comment counts, each article travels as a single self-contained object passed via an `article` prop. These objects are defined at the top of `ArticleList.jsx`:

```jsx title="ArticleList.jsx" startLine="3"
const park = {
  title: 'New Park Opens Today',
  author: 'Mary Jones',
  summary: 'The park on Main Street opens at noon.',
  isNew: true, // a new article
  commentCount: 3, // three comments so far
};
```

Our second article, `rain`, is authored by Oliver Brooks. It is not new (`isNew: false`) and has no comments (`commentCount: 0`). `ArticleList` renders both cards by passing their respective article objects alongside an `isSignedIn` authentication boolean: `<ArticleCard article={park} isSignedIn={isSignedIn} />`. Inside `ArticleCard`, dot notation accesses properties from the prop:

```jsx title="ArticleCard.jsx" startLine="1"
export default function ArticleCard({ article }) {
  return (
    <article className="card">
      <h2>{article.title}</h2> {/* a property of the object */}
      <p className="author">{article.author}</p>
      <p>{article.summary}</p>
    </article>
  );
}
```

On days when no featured story is selected, the featured data slot is empty. JavaScript represents the intentional absence of an object using `null`. Attempting to read a property from `null` immediately throws a `TypeError: Cannot read properties of null`. The **optional chaining** operator (`?.`) allows safe navigation by evaluating to `undefined` instead of throwing when the target object is `null`:

```js title="Reading a property of null"
const article = null;
article?.title; // undefined, no error
article.title; // **WRONG:** TypeError: Cannot read properties of null
```

### JavaScript sorts every value into truthy or falsy

Conditional branching requires determining whether an expression evaluates to yes or no. When supplied with non-boolean values, JavaScript coerces them into a boolean. Exactly six values evaluate to false, known as **falsy** values: `false`, the number `0`, an empty string `''`, `null`, `undefined`, and `NaN`. All other values evaluate to true and are called **truthy**: `true`, every non-zero number, any non-empty string, all plain objects, and all arrays (including empty arrays `[]`).

```js title="Truthy and falsy"
if (0) { } // falsy: the block is skipped
if ('false') { }
if ([]) { } // truthy: an empty array is still an object
```

The **logical NOT** operator (`!`) inverts truthiness: `!null` evaluates to `true`, allowing `if (!article)` to read cleanly as "if there is no article". **Comparison operators** evaluate strictly to true or false: `count > 0` checks if a counter exceeds zero, and strict equality `count === 1` verifies that a value is identical in both type and value.

### && gives back one of its two sides

The **logical AND** operator (`&&`) evaluates expressions from left to right. When its left-hand operand is falsy, evaluation short-circuits and returns the left operand itself. When the left operand is truthy, evaluation continues and returns the right operand. It acts as the mirror of logical OR (`||`), which returns its left operand when truthy.

```js title="The logical AND"
true && 'New';
false && 'New'; // false: the left side itself
0 && 'New'; // 0: the left side itself, a number
```

Logical `&&` does not inherently produce a boolean. It returns one of its two operands verbatim.

### An if can end a function early

A `return` statement executed inside an `if` block immediately halts execution of the enclosing function, preventing any subsequent lines from running. This pattern is an **early return**.

```js title="An early return"
function firstLetter(name) {
  if (!name) {
    return ''; // ends here, the next line never runs
  }
  return name[0];
}
```

When handling multiple discrete outcomes, `if` statements can be chained with `else if` and a terminal `else`. JavaScript evaluates each condition sequentially from top to bottom, executing exclusively the first matching block:

```js title="if, else if, and else"
let size;
if (count === 0) {
  size = 'none';
} else if (count === 1) {
  size = 'one';
} else {
  size = 'many'; // every other count
}
```

### Principles of React: Conditional Rendering

Everything in this lesson comes down to one idea: conditional rendering, which means that each time it runs, a component chooses which JSX to return. First, returning null, which means choosing to show nothing: when there is nothing to show, the component returns null at its very top, before any line reads the missing data. Second, logical AND, which means choosing one piece or nothing: we put a true or false value on its left side, never a bare number, because a zero shows up on the page. Third, the ternary operator, which means choosing between two pieces: we write the choice inside the JSX, so the parts both cases share are written only once. Fourth, an if statement and a variable, which means choosing among many pieces: we make the choice above the return and place the result in the JSX, instead of putting one ternary inside another.

### Question 1: A missing featured article blanks the whole page

On our article site, `App.jsx` mounts a featured article slot above the main article catalog. On days without an active breaking story, `featured` is set to `null`:

```jsx title="App.jsx" startLine="6"
const featured = null; // no featured article today

export default function App() {
  return (
    <>
      <SiteHeader />
      <ArticleCard article={featured} /> {/* article is null */}
```

When this code runs, the entire browser window goes completely blank. The header and both standard articles vanish. In the Console panel, Chrome logs an uncaught runtime error: `TypeError: Cannot read properties of null (reading 'title')`, followed by React's diagnostic warning: `The above error occurred in the <ArticleCard> component`.

**Some days there is no featured article. How does the featured card show nothing instead of breaking the page?**

---

**ANSWER**

**The code does not do what we wanted.** An uncaught error during component rendering crashes React's entire component tree, wiping out all previously mounted UI.

Developers arriving from static HTML workflows often expect missing data to leave an empty placeholder box on the screen or assume that adding a CSS hiding class can suppress the element. In React, however, a component is an executable function. When `ArticleCard` runs with `article={null}`, execution reaches `{article.title}`, attempting to read the property `title` on `null`. This throws an unhandled JavaScript `TypeError`. Because the error occurs inside React's rendering pipeline without an error boundary (Lecture 72), React unmounts the entire application container to prevent displaying corrupted UI.

Attempting to hide the card using a CSS class name like `<article className={article ? 'card' : 'hidden'}>` fails completely. The function must still evaluate the nested `{article.title}` expression before producing the JSX element, triggering the exact same fatal crash. Similarly, attempting an imperative DOM query like `document.getElementById('featured-card').classList.add('hidden')` throws because the DOM node does not yet exist while the component function executes.

A common junior attempt uses optional chaining:

```jsx title="ArticleCard.jsx" startLine="4"
      <h2>{article?.title}</h2> {/* undefined, no crash */}
      <p className="author">{article?.author}</p>
      <p>{article?.summary}</p>
```

Optional chaining prevents the crash because `article?.title` evaluates safely to `undefined`. However, React still constructs the outer `<article className="card">` container. The Elements panel reveals a ghost card containing empty tags: `<article class="card"><h2></h2><p class="author"></p><p></p></article>`. A blank card border and empty margins linger visibly on the page.

The senior solution is an **early return** returning `null`:

```jsx title="ArticleCard.jsx" startLine="1"
export default function ArticleCard({ article }) {
  if (!article) {
    return null; // no article: no card at all
  }
  return (
```

Placing `if (!article) { return null; }` at the very top of the function intercepts execution before any property reads occur. Because `null` renders no DOM elements, React leaves the featured slot completely empty. The rest of the page (the header, article list, and footer) renders cleanly.

The component still executes: a `console.log` placed at the top of `ArticleCard` prints diagnostic lines for the featured card. If the parent instead guards the tag using `{featured && <ArticleCard article={featured} />}`, the component function never executes at all on days when `featured` is `null`.

```ascii title="The featured slot when article is null"
code                 page                     Elements panel
article.title        blank, all of it         nothing in #root
article?.title       an empty box             <article class="card"><h2></h2>...
if (!article) null   header and two articles  no <article> for the slot
```

> [!PRINCIPLE]
> **Principle 1: Returning null: choosing to show nothing**
>
> When a component has nothing to show for its props, it returns `null` from an `if` at its very top, before any line reads the missing data; when the parent decides whether the component appears at all, the parent leaves out its tag instead.
>
> *We should do this:*
>
> ```jsx
> function Profile({ user }) {
>   if (!user) {
>     return null; // nothing shows, the page stays
>   }
>   return <h2>{user.name}</h2>;
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Profile({ user }) {
>   return <h2>{user.name}</h2>; // **WRONG:** null user crashes render
> }
> ```

### Question 2: An article with no comments shows a bare 0

We enhance `ArticleCard` to display a "New" badge for recent stories and a comment counter for reader discussions:

```jsx title="ArticleCard.jsx" startLine="6"
    <article className="card">
      {article.isNew && <span className="new-label">New</span>} {/* label */}
      <h2>{article.title}</h2>
      <p className="author">{article.author}</p>
      <p>{article.summary}</p>
      {article.commentCount && <p>{article.commentCount} comments</p>}
    </article>
```

We load the page. The `park` article renders as expected: it displays the `New` badge and "3 comments". But the `rain` article exhibits an unexpected flaw: while the "New" badge is hidden, a standalone, unformatted number `0` appears right beneath the summary.

**The "New" label should show only on new articles, and the comment count only when there are comments. Do I need an `if` for that?**

---

**ANSWER**

**The code does not do what we wanted.** Placing a numeric expression on the left side of `&&` renders a literal `0` into the DOM whenever the count is zero.

Developers frequently conceptualize the logical AND operator (`&&`) as an inline `if` statement. But as demonstrated in our runway review, JavaScript's `&&` operator does not return a boolean; it short-circuits and returns the operand itself:

```ascii title="The left side decides what && gives back"
card   left side             && gives back   the page shows
park   isNew: true           <span>New</span>    New
rain   isNew: false          false               nothing
park   commentCount: 3       <p>3 comments</p>   3 comments
rain   commentCount: 0       0                   0
```

For the "New" label, `article.isNew` contains `true` or `false`. When `false`, `&&` evaluates to `false`. Because React treats boolean values (`false`, `true`), `null`, and `undefined` as non-rendering tokens, nothing is inserted into the DOM.

For the comment counter, however, `rain.commentCount` contains the number `0`. In JavaScript, `0` is falsy, causing `&&` to short-circuit and return `0`. But unlike `false` or `null`, numbers are legitimate render targets in React (as established in Lecture 4). React converts the number `0` to a text node and renders it directly to the browser DOM.

The fix is to ensure the left-hand side of `&&` evaluates strictly to a boolean by using a comparison operator:

```jsx title="ArticleCard.jsx" startLine="11"
      {article.commentCount > 0 && (
        <p>{article.commentCount} comments</p>
      )} {/* boolean comparison */}
```

Because `0 > 0` evaluates to `false`, the expression returns `false`, causing React to render nothing for stories without comments. Alternative conversions include `Boolean(article.commentCount)` or double negation `!!article.commentCount`.

Beware of other falsy traps: passing a string prop like `isNew="false"` passes a non-empty string, which is truthy and mistakenly displays the badge. Similarly, an empty array `[]` is truthy, meaning `tags && <ul>...</ul>` renders an empty list container; Lecture 11 guards `{tags.length > 0 && <ul>...</ul>}` around a list built with `map`.

> [!PRINCIPLE]
> **Principle 2: Logical AND: choosing one piece or nothing**
>
> To show a piece or nothing, we write `condition && <Piece />` with a true or false value on the left, such as `commentCount > 0`, never a bare number.
>
> *We should do this:*
>
> ```jsx
> const count = 0;
> {count > 0 && <p>{count} messages</p>} // shows nothing
> ```
>
> *We should not do this:*
>
> ```jsx
> const count = 0;
> {count && <p>{count} messages</p>} // **PROBLEMATIC:** renders a bare 0
> ```

### Question 3: Two returns drift apart when one of them changes

We need to differentiate content for registered members and unauthenticated guests. Signed-in readers should see the full article summary, while visitors should receive a sign-in callout. A developer implements this requirement using two full return statements inside `ArticleCard`:

```jsx title="ArticleCard.jsx" startLine="1" continues="bottom"
export default function ArticleCard({ article, isSignedIn }) {
  if (!article) {
    return null;
  }
  if (isSignedIn) {
    return (
      <article className="card">
        <h2>{article.title}</h2>
        <p className="author">{article.author}</p> {/* added later */}
        <p>{article.summary}</p>
```

```jsx title="ArticleCard.jsx" startLine="11" continues="top"
      </article>
    );
  }
  return (
    <article className="card">
      <h2>{article.title}</h2> {/* **PROBLEMATIC:** author omitted */}
      <p>Sign in to read this article.</p>
    </article>
  );
}
```

Later, an editor requests that author bylines appear on article cards. The developer updates the component by adding `<p className="author">{article.author}</p>` to the first return block. When testing with `isSignedIn = false`, visitors see the article title and sign-in prompt, but the author's byline is missing.

**Signed-in readers see the summary, visitors see a sign-in prompt. Do I write two returns?**

---

**ANSWER**

**The code does not do what we wanted.** Duplicating shared markup across multiple return statements leads to maintenance drift where changes in one branch fail to reach the other.

Using an `if` statement with two distinct returns seems intuitive: it produces the correct initial DOM output, and each branch reads as an isolated block of markup. However, duplicating the shared wrapper elements (`<article className="card">`) and common header elements (`<h2>{article.title}</h2>`) creates architectural fragility. Whenever layout requirements change, developers must remember to apply identical edits in multiple locations. In our code, adding the author byline to the signed-in branch left the guest branch out of date.

The only piece of the component that differs between states is a single paragraph. Therefore, the conditional choice belongs inline inside the JSX tree. While an `if` statement cannot sit inside JSX curly braces, the **ternary operator** (`? :`) evaluates as an expression and can seamlessly branch between two JSX nodes:

```jsx title="ArticleCard.jsx" startLine="5"
  return (
    <article className="card">
      <h2>{article.title}</h2>
      <p className="author">{article.author}</p> {/* written once */}
      {isSignedIn ? (
        <p>{article.summary}</p>
      ) : (
        <p>Sign in to read this article.</p>
      )}
    </article>
```

By consolidating the component into a single `return` block, the outer `<article>`, the heading, and the author byline are declared exactly once. The ternary operator targets strictly the dynamic paragraph. When JSX branches span multiple lines, wrapping each branch in parentheses preserves formatting and visual clarity.

A ternary expression always requires both branches. Omitting the colon clause triggers a compiler syntax error: `[PARSE_ERROR] Expected ':' but found '}'`. For cases requiring one branch or nothing, logical `&&` remains the appropriate pattern. Two separate return statements remain valid only when the two branches share zero common structure, such as returning `null` when data is missing.

> [!PRINCIPLE]
> **Principle 3: The ternary operator: choosing between two pieces**
>
> To show one of two pieces in the same place, we write `condition ? <A /> : <B />` inside the JSX and keep the markup both cases share written once; two whole returns fit only when the two cases share nothing.
>
> *We should do this:*
>
> ```jsx
> <h2>{name}</h2>
> {isSignedIn ? <Summary /> : <SignInPrompt />} // only this differs
> ```
>
> *We should not do this:*
>
> ```jsx
> if (isSignedIn) {
>   return <><h2>{name}</h2><Summary /></>;
> }
> return <><h2>{name}</h2><SignInPrompt /></>; // **PROBLEMATIC:** duplicate markup
> ```

### Question 4: Three comment wordings tangle into nested ternaries

Our design team updates the comment section specifications. The comment footer must now display one of three tailored messages depending on discussion activity: "No comments yet" when count is zero, "1 comment" when singular, and "5 comments" for plural counts. A developer writes nested ternaries inside the JSX:

```jsx title="ArticleCard.jsx" startLine="9"
      <p className="comments">
        {count === 0
          ? 'No comments yet'
          : count === 1
            ? '1 comment'
            : count + ' comments'} {/* **PROBLEMATIC:** nested ternaries */}
      </p>
```

Testing with articles containing 0, 1, and 5 comments reveals that the rendered output is visually accurate. However, during a team pull request review, senior engineers flag the construct as unmaintainable.

**The comment line needs three wordings: no comments, one comment, many comments. Can I put one ternary inside another?**

---

**ANSWER**

**The code does not do what we wanted.** Nesting ternary expressions creates convoluted syntax that obscures logic and increases cognitive overhead.

A single ternary operator cleanly models a binary choice. However, chaining multiple ternaries together requires the reader to mentally pair question marks with their respective colons. If a fourth condition is introduced (such as "Discussion closed"), the expression cascades into an impenetrable pyramid of conditions.

Because JavaScript statements are fully permitted above the `return` statement, multiple discrete branches are best handled using a standard `if...else if...else` chain that assigns its result to a local variable:

```jsx title="ArticleCard.jsx" startLine="5"
  const count = article.commentCount;
  let commentText;
  if (count === 0) {
    commentText = 'No comments yet';
  } else if (count === 1) {
    commentText = '1 comment';
  } else {
    commentText = count + ' comments'; // 5 comments
  }
```

```jsx title="ArticleCard.jsx" startLine="17"
      <p className="comments">{commentText}</p> {/* placed in JSX */}
```

Each branching case now occupies a single, easily readable line above the return block. The JSX return then embeds the resolved text or element via `{commentText}`. This local variable can store plain strings, numbers, or full JSX element trees.

If the number of conditions expands further (such as handling ten different status types), the logic can be factored into a dictionary lookup object or delegated to a dedicated helper component. Remember that syntax shortcuts like `&&` and the ternary operator are entirely optional conveniences; clean `if` statements remain a standard, robust architectural choice.

> [!PRINCIPLE]
> **Principle 4: An if statement and a variable: choosing among many pieces**
>
> When a choice has more than two cases, we pick the piece with `if`, `else if`, and `else` above the `return`, store it in a variable, and place the variable in the JSX, instead of nesting one ternary inside another.
>
> *We should do this:*
>
> ```jsx
> let label;
> if (count === 0) {
>   label = 'None';
> } else if (count === 1) {
>   label = 'One';
> } else {
>   label = 'Many';
> }
> return <p>{label}</p>; // one case per line above
> ```
>
> *We should not do this:*
>
> ```jsx
> return (
>   <p>{count === 0 ? 'None' : count === 1 ? 'One' : 'Many'}</p>
> ); // **PROBLEMATIC:** nested ternaries obscure logic
> ```

### Is hiding with display: none ever the better choice?

> [!WILD]
> **Hiding with CSS vs. Conditional Rendering**
>
> In Question 2, the rain article produced no `<span>` in the DOM, whereas the CSS `hidden` attribute retains `<span class="new-label" hidden="">New</span>`. When is CSS hiding preferable to conditional rendering?
>
> When an element is conditionally omitted from the JSX tree, React unmounts it completely. If that element is later re-introduced, React mounts a fresh DOM node, discarding any ephemeral DOM state (such as user-entered text, scroll position, or uncommitted form inputs).
>
> **Hiding with CSS** maintains the element in the DOM tree, preserving its internal state and avoiding the lifecycle cost of re-initialization. For dynamic visibility toggles, Lecture 14 introduces stateful user interactions, while Lecture 73 introduces React's built-in `<Activity>` component, which hides views while preserving cached state. For data-driven display rules and guarding against missing objects, conditional rendering remains the essential and correct standard.

### Step 1: First, we let the featured slot show nothing <App.jsx>

This step applies Principle 1: Returning null: choosing to show nothing.

Our featured slot includes an introductory heading: `<h2>Featured today</h2>`. If only `ArticleCard` guarded against missing data by returning `null`, this heading would remain orphaned on screen with empty space below it. Because the heading belongs to `App`, `App` owns the decision: it guards the entire `<section>` using `{featured && (...)}`. In parallel, `ArticleCard` retains its internal `return null` check as defensive protection against any caller.

In `App.jsx`, lines 12 to 17 render the featured section conditionally:

```jsx title="App.jsx" startLine="12"
      {featured && (
        <section className="featured">
          <h2>Featured today</h2> {/* only when there is an article */}
          <ArticleCard article={featured} />
        </section>
      )}
```

Because `featured` is either a valid article object or `null`, it acts as a safe boolean operand for `&&`. Today, the page renders the header, standard articles, and footer with zero orphan headings or empty card boxes.

### Step 2: Next, we show the "New" label only on new articles <ArticleCard.jsx>

This step applies Principle 2: Logical AND: choosing one piece or nothing.

The "New" badge sits directly above the article title and reads `article.isNew`. Because `isNew` is stored strictly as a boolean (`true` or `false`), it can safely occupy the left-hand position of the `&&` operator without danger of rendering zero tokens.

In `ArticleCard.jsx`, line 16 renders the label:


A developer accustomed to older static web paradigms expects to toggle element visibility with CSS classes, reads `&&` as a simple synonym for `if`, and copies markup across multiple return branches. In React 19, our featured slot rendered nothing without crashing the application, the "New" badge appeared exclusively on fresh content, the bare numeric `0` never leaked into the DOM, visitors and members shared a single robust card template, and three comment phrasings were evaluated cleanly as standard JavaScript lines. Each step fulfilled one foundational principle: returning `null` to show nothing, using boolean logical `&&` for one piece or nothing, using the ternary operator for binary choices, and using `if` with a local variable for multi-branch logic.

### Where you will meet this

1. **A notification badge with a count**: Displaying an unread message badge only when notifications exist. The count is numeric, requiring `count > 0 && <Badge />` rather than `count && <Badge />`.
2. **Visitor vs. member navigation bars**: Presenting a "Sign in" button to unauthenticated visitors while displaying an account avatar and username to logged-in subscribers.
3. **Asynchronous data loading states**: Rendering a loading spinner while data is fetching, returning `null` or a skeleton screen when data is empty, and rendering content once available.
4. **Multi-state workflow indicators**: Displaying order tracking statuses ("Placed", "Processing", "Shipped", "Delivered") computed via an `if...else if` chain into a local variable or status lookup dictionary.
5. **Preserving form state in tab panels**: Choosing between conditional rendering and CSS-based visibility toggles when hiding background panels without destroying user input (Lecture 73).

### For the interview

- **The Hidden Signal**: Interviewers assess whether a candidate understands how React interacts with JavaScript evaluation rules. Strong candidates immediately clarify that React has no special conditional syntax, explain how JSX unmounting affects the physical DOM versus CSS hiding, and proactively highlight the numeric zero trap.
- **The Classic Trap**: Stating that `{count && <Component />}` is equivalent to an inline `if`. In JavaScript, `0 && <Component />` returns `0`, causing React to render a literal text node `0` into the DOM. The solution is explicit boolean coercion: `{count > 0 && <Component />}` or `{Boolean(count) && <Component />}`. Another common trap is attempting to hide missing data with CSS, which fails because property access on `null` crashes during component execution.
- **What is Actually Going On**: React executes component functions to build virtual element trees. When a component returns `null`, React creates no physical DOM node for that component. Inside JSX, falsy values like `false`, `null`, and `undefined` produce no DOM nodes. The ternary operator evaluates strictly one expression, guaranteeing that shared surrounding markup remains deduplicated.
- **Where It Gets Tricky**: *What does a component return to render nothing?* It returns `null`; in React 19, returning `undefined` from a bare `return;` also renders nothing without throwing, but returning `null` remains the intentional idiomatic standard. *Is returning `null` identical to omitting the JSX tag in the parent?* No: returning `null` still executes the component function (invoking logs and hooks), whereas omitting the tag prevents the component from running at all. *Why does `isNew="false"` display the badge?* Quoting the attribute passes a string, and non-empty strings are truthy; passing `isNew={false}` in braces supplies a real boolean. *What happens to unmounted DOM nodes?* React completely destroys them; when re-rendered, they are re-created from scratch without preserved state.

### Glossary

- **Conditional rendering**: The process of choosing which JSX elements to return and mount in the DOM based on runtime conditions using standard JavaScript syntax.
- **Early return**: A pattern where a function terminates immediately via a `return` statement inside a top-level condition, preventing subsequent logic from running.
- **Truthy and falsy**: The inherent boolean classification of JavaScript values in conditional contexts. Falsy values include `false`, `0`, `''`, `null`, `undefined`, and `NaN`; all other values are truthy.
- **Logical AND (`&&`)**: An operator returning its left operand if falsy, and its right operand otherwise. Used in JSX to conditionally render an element when the left operand is a boolean.
- **Ternary operator**: An inline expression (`condition ? exprIfTrue : exprIfFalse`) that resolves to one of two values based on a condition.
- **Hiding with CSS**: Retaining an element in the browser DOM while toggling its visual visibility via attributes like `hidden` or CSS properties like `display: none`.

### Summary

**Conditional rendering: each time it runs, a component chooses which JSX to return**

❒ Returning null: choosing to show nothing
- IF a component has nothing to show for its props THEN return `null` from an `if` at its very top, before any line reads the missing data.
- IF the parent owns the markup around the component THEN the parent leaves out the tag instead.
- NEVER hide a part whose data may be missing with CSS alone; its JSX still runs and throws.

❒ Logical AND: choosing one piece or nothing
- ALWAYS put a true or false value on the left of `&&`, such as `count > 0`.
- NEVER put a bare number on the left of `&&`; a `0` shows up on the page.

❒ The ternary operator: choosing between two pieces
- IF two cases share markup THEN write the ternary inside the JSX, around the part that differs.
- IF the two cases share nothing THEN two whole returns are fine.

❒ An if statement and a variable: choosing among many pieces
- IF a choice has more than two cases THEN choose with `if`, `else if`, and `else` above the `return`, and place the variable in the JSX.
- NEVER put one ternary inside another; each new case adds a level to untangle.

**Nothing, one or nothing, one of two, and one of many.**

**DO THIS:**

```jsx right
function ArticleCard({ article, isSignedIn }) {
  if (!article) {
    return null;
  }
  return (
    <article className="card">
      <h2>{article.title}</h2>
      {isSignedIn ? <p>{article.summary}</p> : <p>Sign in to read.</p>}
      {article.commentCount > 0 && <p>{article.commentCount} comments</p>}
    </article>
  );
}
```

**DO NOT DO THIS:**

```jsx wrong
function ArticleCard({ article }) {
  return (
    <article className="card">
      <h2>{article.title}</h2>
      {article.commentCount && <p>{article.commentCount} comments</p>}
    </article>
  );
}
```
