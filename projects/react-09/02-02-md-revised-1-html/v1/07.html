Lecture 9: Mounting the Root Component with createRoot and Vite Tooling

Interview Question

CORE

How does your root component attach to the browser DOM with createRoot, and how do build tools assemble it?

Imagine this scenario:

  1. Your article site now lives in several files: App.jsx and a components folder beside it.
  2. You double-click index.html to see the site, and the browser shows a blank white page.
  3. How do the files you write become the page the browser shows?

Every React app starts from one HTML page

Every website reaches the browser as an HTML page. Since Lecture 2 we have written components, and since Lecture 8 each one lives in its own file. But a browser knows nothing about our files. It opens one HTML page and runs the scripts that page names. So every React developer meets the same question: how does React get onto a real web page?

React's own documentation lists three ways to start, and developers choose between them based on project architecture. The first way creates the project with a full-stack framework such as Next.js:

Terminal
1npx create-next-app@latest
Creates a framework project

With a full-stack framework, we write page components, and the framework handles the rest: a server sends each page's HTML already filled, and the framework calls React's start-up code for us. It fits a site whose pages should arrive ready from the server, with routing built in. Lecture 45 compares full-stack frameworks and standalone build tools.

The second way is the one this chapter teaches. A build tool turns our files into code the browser can run, and one file of our own, the entry file, starts React with an explicit mount call:

Entry file with a build tool
1createRoot(document.getElementById('root')).render(
2 <App />
Mounts root component into DOM
3);

Read the line from the inside out. document.getElementById('root') finds one element of the HTML page, as in Lecture 1. createRoot hands that element to React. .render(<App />) tells React to show App inside it. Here we decide where React starts and what it shows, and the build tool prepares our files. It fits an app built from scratch, where one page is loaded once and React draws everything on it.

The third way starts from a page that already exists. A legacy website built with other backend tools can hand over one designated container to React:

One area of an existing page
1createRoot(document.getElementById('comments')).render(
2 <Comments />
Mounts widget into page element
3);

The same two calls now take only the comments container. The rest of the page stays exactly as the backend server wrote it, and React never touches it. Lecture 1 explained that React can run an entire page or only a specific widget on an existing page. It fits a large legacy site that moves to React incrementally, one feature at a time.

Three ways to put React on a web page

(1) Start React with a full-stack framework (Lecture 45): the framework creates the project, renders HTML on a server, and calls React's start-up code for us.

(2) Start React with a build tool and an entry file (this chapter): the build tool prepares our modular files, and our own entry file hands one empty element to React.

(3) Add React to part of an existing page (this chapter): an existing page gives one area to React, and the rest stays as the server wrote it.

This chapter follows the second way, using Vite as the build tool, because it exposes every foundational step that frameworks hide. It follows one idea from the first question to the last: mounting, which means the browser loads one page, and React fills one element of it with our components. The steps follow the order of one page load: the page arrives, its code arrives, React takes one element, React fills it, and the app grows from there.

This lesson answers five questions:

  • index.html has only an empty <div id="root">. Where is the page I see, and where do I change it?
  • Why can't I just double-click index.html, like any HTML page I wrote before?
  • What does createRoot(document.getElementById('root')) do with the empty element?
  • My old tutorial writes ReactDOM.render(<App />, document.getElementById('root')) in one line. Why does our main.jsx use two steps?
  • I want a footer under the articles. Do I add a second createRoot for it in main.jsx?

The questions stand on what earlier lessons established:

  • Lecture 1 (What is React): index.html holds one empty element, <div id="root"></div>, which React fills. npm run dev starts the dev server, which serves the project during development. document.getElementById('root') queries the browser DOM for the element whose id is root, and the Elements panel inspects the live DOM tree.
  • Lecture 2 (Component anatomy): <App /> is a component tag: React calls the function App wherever JSX writes its tag. App without the tag is merely a function reference. A new Vite project wraps <App /> in <StrictMode>, a development-only verification tool.
  • Lecture 3 (JSX syntax): Browsers cannot parse JSX syntax natively. The build rewrites each JSX tag into a function call that returns a React element, a plain JavaScript object describing the UI. The Sources panel displays files as the browser received them, and main.jsx imports index.css. A Fragment, <> and </>, groups multiple sibling elements without introducing extra DOM nodes.
  • Lecture 4 (JavaScript expressions in JSX with curly braces): null represents the deliberate absence of any object value. Functions return null when a queried element is not found.
  • Lecture 5 (The render tree): App serves as the root component: every other component across the application descends from it in the render tree.
  • Lecture 6 (Props): npm run build compiles the production build, and npm run preview serves the compiled output locally.
  • Lecture 8 (Modules): Each file functions as an isolated module. import App from './App.jsx' is a default import with a relative path. In contrast, 'react-dom/client' is a bare package import pointing to an installed dependency.

The browser reads index.html first

When the browser requests our site, the first file it fetches is index.html. It parses the document from top to bottom. In a standard Vite project, the <body> of index.html holds only two items:

index.html
8 <body>
9 <div id="root"></div>
The one element React will fill
10 <script type="module" src="/src/main.jsx"></script>
Runs main
11 </body>

The <script> tag carries the attribute type="module". That attribute designates it as a module script: a script that can use standard import statements to load ES modules. Browsers defer execution of module scripts until the HTML document has finished parsing, guaranteeing that <div id="root"></div> already exists in the DOM when main.jsx runs.

The browser provides two distinct perspectives on a web page:

  1. View Page Source shows the raw HTML document sent across the network by the server.
  2. The Elements panel shows the live, active DOM tree inside browser memory after all scripts have executed.

On a static HTML site, both views look identical because no JavaScript modifies the DOM. On a React site, View Page Source displays an empty <div id="root"></div>, whereas the Elements panel reveals the full rendered component tree nested inside that same div.

The dev server sends the project from your computer

A web page can load in the browser through two distinct protocols. Opening an HTML file directly from the filesystem creates a file:// address, such as file:///Users/you/article-site/index.html In contrast, running npm run dev starts Vite's local HTTP server, delivering the page over a localhost address, such as http://localhost:5173/.

Terminal
1npm run dev
Prints local address http://localhost:5173/

Third-party dependencies installed via npm install reside in the node_modules folder. React divides its responsibilities across two core packages:

  • react contains platform-agnostic primitives: component definitions, JSX runtime helpers, and state hooks.
  • react-dom provides the browser rendering backend. Its submodule react-dom/client exposes client-side mounting APIs like createRoot. React Native pairs the same core react package with a mobile renderer instead of react-dom.

When running npm run build, the bundler compiles the entire application into a static distribution directory named dist. This folder contains the optimized production assets (index.html, minified JavaScript, and CSS bundles) that a production web server hosts.

A method is a function stored on an object

In JavaScript, a function stored as a property on an object is called a method. Methods are invoked using dot notation: the parent object, followed by a dot, the method name, and parentheses:

Lines 1 to 4 import dependencies. Line 6 performs two chained operations: createRoot(...) executes first and returns a React root object, and .render(...) immediately calls a method on that returned root. Principles of React: Mounting the Root Component

Everything in this lesson comes down to one idea: mounting, which means the browser loads one page, and React fills one element of it with our components. First, the root element, which means the page arrives with one empty element: we leave that element empty in the HTML file and write every part of the page in our components. Second, the build tool, which means the page's code arrives as plain JavaScript: we open the project through the dev server, because a browser cannot read JSX or a package name by itself. Third, the React root, which means the page hands that one element to React: we find the element by the same id the HTML file gives it, and we hand React the element itself. Fourth, the initial render, which means the page shows the root component in that element: we ask the root to render once, with the root component written as a tag. Fifth, one root per app, which means the page grows inside the root component: a new part of the page is a new tag inside the root component, never a second root on the same element.

QUESTION 1

A title typed into the root element disappears

A developer wants to add a header title above the article list. Remembering standard HTML, the developer opens index.html and types <h1>Latest Articles</h1> directly inside <div id="root">:

index.html
9 <div id="root"><h1>Latest Articles</h1></div>
Typed by hand

Save the file and refresh the browser. The page displays the article list, but the typed <h1> heading is missing entirely. Opening View Page Source shows <h1>Latest Articles</h1> nestled inside the div, but the browser Elements panel shows only <div id="root"><main>...</main></div>

index.html has only an empty <div id="root">. Where is the page I see, and where do I change it?

ANSWER

The code does not do what we wanted. React clears all existing children inside the container element on its initial render, destroying any manually typed HTML.

When the browser parses index.html, it initially constructs the DOM element <div id="root"><h1>Latest Articles</h1></div> Moments later, the module script executes main.jsx. When main.jsx calls root.render(<App />), React takes complete ownership of the DOM subtree inside that container.

As part of the initial mount contract, React wipes out all existing child nodes inside the container element before inserting its own virtual DOM tree. Any HTML markup typed inside <div id="root"> is removed from the live document.

View Page Source continues to display the typed <h1> because it inspects the unmodified network payload delivered from the disk. In contrast, the Elements panel reveals the live, active DOM tree after React's render pipeline has wiped the container.

In a modern client-side React application, the root element in index.html serves exclusively as an empty mounting hook. All user-facing content belongs inside React components. Elements outside the root container, such as the <head> tag or <title>, remain untouched by React.

The proper fix is to create a dedicated SiteHeader component, render the heading inside it, and assemble SiteHeader alongside ArticleList inside App:

SiteHeader.jsx
1export default function SiteHeader() {
2 return (
3 <header className="site-header">
4 <h1>Latest Articles</h1>
Title lives in component
5 </header>
6 );
7}
App.jsx
1import SiteHeader from './components/SiteHeader.jsx';
New import
2import ArticleList from './components/ArticleList.jsx';
3
4export default function App() {
5 return (

9 </>

QUESTION 2

A double-clicked index.html shows a blank page

A newcomer navigates to the project directory in their operating system file manager and double-clicks index.html to view the site. The browser launches with an address starting with file:///Users/you/article-site/index.html The browser viewport is blank.

Open the Console panel: Chrome prints a fatal error: Access to script at 'file:///src/main.jsx' from origin 'null' has been blocked by CORS policy: Cross origin requests are only supported for protocol schemes: http, data, chrome-extension, https, chrome-untrusted.

Why can't I just double-click index.html, like any HTML page I wrote before?

ANSWER

The code does not do what we wanted. Browsers block ES module scripts loaded over the file:// protocol, and native browser runtimes cannot interpret raw JSX or bare package names.

Standard HTML pages containing vanilla JavaScript can open directly from local disk storage. However, React source files cannot run directly in the browser for three distinct architectural reasons:

  1. CORS policy on local modules: Web security standards block <script type="module"> tags loaded over file:// because local file schemes have an origin of null. Furthermore, an absolute path like /src/main.jsx on a file:// URL resolves against the root directory of the hard drive rather than the project folder.
  2. Native lack of JSX parsing: Even if served over plain HTTP, the browser parser stops at the first JSX element (<App />) with SyntaxError: Unexpected token '<' JSX is a language extension, not valid standard JavaScript.
  3. Bare package specifiers: Standard browser module loaders require relative paths starting with ./, ../, or /. A bare package specifier like import { createRoot } from 'react-dom/client' halts browser resolution with TypeError: Failed to resolve module specifier "react-dom/client"

A build tool like Vite resolves all three obstacles. In development, running npm run dev launches a local dev server on http://localhost:5173/. On every file request, the server transforms JSX into _jsxDEV(...) function calls and maps bare package imports to concrete file paths inside .vite/deps/.

  from 'react-dom/client';          from '/node_modules/.vite/deps/...';

For production hosting, running npm run build executes a full compilation pass, generating bundled static assets inside the dist folder. Production files can then be tested locally with npm run preview or uploaded to a static web server.

QUESTION 3

A renamed id leaves the page blank

A developer decides to rename the container element in index.html to match another convention:

index.html
9 <div id="app"></div>
Renamed from root

However, main.jsx remains unchanged, continuing to query for the container using 'root':

main.jsx
6createRoot(document.getElementById('root')).render(
Still asks for root

Save both files. The browser displays an empty white screen. Opening the Console panel reveals an uncaught fatal exception: Uncaught Error: Target container is not a DOM element.

What does createRoot(document.getElementById('root')) do with the empty element?

ANSWER

The code does not do what we wanted. document.getElementById('root') found no matching element and returned null, which causes createRoot to throw an error.

The browser DOM method document.getElementById('root') queries the live document for an element matching the specified ID string. If no element in the HTML document possesses that ID attribute, the method returns null.

When createRoot receives null instead of a physical DOM element, it cannot initialize a mounting container. It halts execution immediately by throwing Target container is not a DOM element. Because execution crashes before .render() is called, nothing renders on screen.

When passed a valid DOM element, createRoot initializes and returns a React root object. This root object exposes two primary methods:

  • render(element): Mounts or updates the virtual DOM element tree inside the container.
  • unmount(): Teardowns the tree, cleans up event listeners, and empties the container.

Calling createRoot establishes the container boundary: React claims exclusive control over all DOM manipulation inside that designated element, while DOM nodes outside the container remain managed by traditional HTML and browser APIs. Note that passing a JSX tag directly into createRoot, such as createRoot(<App />), triggers the identical Target container is not a DOM element error because a React virtual element is not a real DOM node.

The fix is ensuring the query string in main.jsx matches the ID attribute declared in index.html letter for letter:

index.html
9 <div id="root"></div>
Matching ID attribute
main.jsx
6createRoot(document.getElementById('root')).render(
Matches index.html
PRINCIPLE 3

The React root: the page hands that one element to React

We call createRoot once in main.jsx with the element itself, found by the same id that index.html gives it; React then controls everything inside that element and nothing outside it.

We should do this:

QUESTION 4

ReactDOM.render from an old tutorial stops the page

Following a tutorial found on an older blog, a developer imports ReactDOM and writes the single-line mount call:

main.jsx
1import ReactDOM from 'react-dom';
2import './index.css';
3import App from './App.jsx';
4
5const container = document.getElementById('root');
6ReactDOM.render(<App />, container);
WRONG: not a function

Save the file. The browser viewport stays blank. In the console, a fatal TypeError appears: TypeError: ReactDOM.render is not a function

My old tutorial writes ReactDOM.render(<App />, document.getElementById('root')) in one line. Why does our main.jsx use two steps?

ANSWER

The code does not do what we wanted. ReactDOM.render was deprecated in React 18 and completely removed in React 19.

Older versions of React exposed a legacy API named ReactDOM.render(element, container) that combined container discovery and initial rendering into a single synchronous call.

React 19 removed ReactDOM.render entirely. Importing from react-dom no longer provides a render function, causing legacy invocation attempts to crash with ReactDOM.render is not a function

Modern React decouples container initialization from rendering into two explicit operations:

  1. createRoot(container): Registers the host DOM element once and initializes concurrent rendering internal queues.
  2. root.render(element): Schedules the virtual DOM element tree to be rendered into that root.

A common mistake when migrating legacy code is passing the DOM container a second time into root.render:

main.jsx
6const container = document.getElementById('root');
7const root = createRoot(container);
8root.render(<App />, container);
PROBLEMATIC: container warning

While the page renders, the console warns: Warning: You passed a container to the second argument of root.render(...). You don't need to pass it again since you already passed it to create the root.

Another common mistake is passing the component function without JSX brackets: root.render(App). Because App is a JavaScript function reference rather than an evaluated React element, React prints: Warning: Functions are not valid as a React child. The argument must be an element: <App />.

Under the hood, createRoot initializes concurrent rendering queues, which Lecture 66 investigates. The initial call to root.render initiates what Lecture 15 defines as the initial render. Furthermore, React attaches its top-level synthetic event listeners to this root DOM container, as Lecture 79 explores. In development, Vite wraps <App /> with <StrictMode> to perform safety audits, which Lecture 46 details.

The fix is importing createRoot from react-dom/client and passing only the root element to .render(...):

main.jsx
1import { StrictMode } from 'react';
2import { createRoot } from 'react-dom/client';
Client API
3import App from './App.jsx';
4
5createRoot(document.getElementById('root')).render(
6 <StrictMode>
7 <App />
Passes element, not container
8 </StrictMode>
9);

The initial render: the page shows the root component in that element

We call render on the root once, with the root component written as a tag, root.render(<App />), and nothing else; React 19 has no ReactDOM.render, and the element is never passed a second time.

We should do this:
import { createRoot } from 'react-dom/client';
const root = createRoot(document.getElementById('root'));
root.render(<App />);

import ReactDOM from 'react-dom';

QUESTION 5

A second root for the footer wipes out the page

A developer creates a Footer component and decides to mount it on the page by adding a second createRoot call directly underneath the first mount inside main.jsx:

main.jsx
5import Footer from './components/Footer.jsx';
Footer import
main.jsx
12const rootEl = document.getElementById('root');
13createRoot(rootEl).render(<Footer />);
PROBLEMATIC: overwrites root

Save the file. The browser renders only the footer text: "Latest Articles, 2026". The site header and article list have completely vanished. The console prints a warning: Warning: You are calling ReactDOMClient.createRoot() on a container that has already been passed to createRoot() before. Instead, call root.render() on the existing root instead if you want to update it.

I want a footer under the articles. Do I add a second createRoot for it in main.jsx?

ANSWER

The code does not do what we wanted. Creating a second root on the same DOM element destroys the existing component tree and replaces it with the footer.

In traditional jQuery or vanilla DOM manipulation, separate scripts find and populate distinct elements independently. In React, a root container maintains exclusive control over its target DOM node.

When createRoot is invoked a second time on <div id="root">, React takes over the container afresh, clears out all DOM nodes previously rendered by the first root (wiping out SiteHeader and ArticleList), and renders only Footer. Calling .render() twice on the same root instance produces the same result silently: each .render() replaces the entire contents of the root.

In an application built fully with React, the rule is absolute: one root per application. The entry file main.jsx initializes a single root container. Every new piece of user interface (a header, a feed, a modal, or a footer) is composed as a child component inside the component tree descending from App.

From then on, the page updates dynamically through state inside components (debuting in Lecture 14), never by calling createRoot or render again.

The only scenario where multiple roots belong in a single web application is when React is embedded into separate, independent sections of a legacy multi-page site. For example, if an existing server-rendered HTML page has <div id="header-widget"></div> and <div id="comments-widget"></div> each independent container receives its own dedicated createRoot call.

The fix is keeping a single createRoot in main.jsx and importing Footer inside App.jsx:

App.jsx
3import Footer from './components/Footer.jsx';
Imported where used
App.jsx
6 return (
7 <>
8 <SiteHeader />
9 <ArticleList />
10 <Footer />

11 </>
12 );
PRINCIPLE 5

One root per app: the page grows inside the root component

In an app built fully with React, we add each new part of the page as a tag inside App, never as a second createRoot or a second render; a page only partly built with React gives each separate React area its own element and its own root.

We should do this:
function App() {
return <><SiteHeader /><ArticleList /><Footer /></>;
App tree
}

We should not do this:
const container = document.getElementById('root');
createRoot(container).render(<App />);
createRoot(container).render(<Footer />);
PROBLEMATIC: overwrites first render

Why is the page blank for a moment on a slow phone?

When inspecting the built production files, dist/index.html contains only an empty <div id="root"></div> and a <script> tag referencing the compiled JavaScript bundle.

On a low-powered mobile device or an unreliable 3G network, the browser must finish downloading the JavaScript bundle (often hundreds of kilobytes) and execute the entire initialization pipeline before React can render a single pixel of article content. Until main.jsx runs, the screen remains completely white. Furthermore, search engine crawlers that do not execute client-side JavaScript perceive an empty page.

To overcome this blank initial state, full-stack architectures employ server-side rendering. With server-side rendering, a server executes React components beforehand and sends a fully populated HTML document on the very first network response. When HTML is pre-rendered on a server, React attaches using hydrateRoot rather than createRoot (Lecture 104).

A developer accustomed to older static web workflows expects HTML to live directly in index.html, opens files with a double-click, and assumes every distinct widget requires a separate mount call. In React 19 with modern build tooling, index.html provides only an empty container element, build tools translate modular code into browser-compatible JavaScript, main.jsx binds the container to React via createRoot, .render(<App />) displays the root component once, and all subsequent layout additions join the component tree descending from App.

Where you will meet this

  1. Every new Vite project: Running npm create vite@latest scaffoldings the identical index.html with an empty <div id="root"></div> and standard main.jsx entry file.
  2. Deploying static production builds: Uploading compiled assets to platforms like Cloudflare Pages or AWS S3 requires transferring the dist/ directory generated by npm run build.
  3. Embedding React into legacy systems: Adding an interactive component (such as a search autocomplete widget or interactive calculator) into an existing Rails or Django page uses createRoot targeted to that specific widget container.
  4. Upgrading legacy codebases: Modernizing older React 16 or 17 codebases requires replacing deprecated ReactDOM.render calls with createRoot.
  5. Architectural framework transitions: Migrating to full-stack frameworks like Next.js or Remix eliminates manual main.jsx files, as the framework manages mounting automatically.

For the interview

  • Hidden Signal: Interviewers use this question to assess whether a candidate understands the transition between physical browser DOM nodes and React's virtual component architecture. Strong candidates trace the complete path from network request to initial paint.
  • Classic Trap: Answering that React writes component HTML directly into index.html on disk. React builds the DOM dynamically in browser memory at runtime after scripts execute.
  • What is Actually Going On: The browser loads index.html, constructs an empty DOM container, and defers main.jsx via module script semantics. Vite transforms JSX into JavaScript function calls. createRoot initializes React's internal fiber root, and root.render initiates concurrent reconciliation to construct the physical DOM.
  • Where It Gets Tricky: How many roots does an application have? Exactly one for a pure React application; multiple roots only when embedding React widgets into separate areas of a legacy page. What happens if the query ID is misspelled? getElementById returns null, causing createRoot to throw an uncaught exception. Can code immediately following root.render inspect rendered DOM nodes? No, because render queues work asynchronously.

Glossary

  • Mounting: The process of initializing a React application and rendering its virtual component tree into a physical browser DOM container for the first time.
  • Build tool: A developer tool (such as Vite) that transforms modern JSX, TypeScript, and bare module imports into standard browser-executable JavaScript.
  • Module script: A <script type="module"> element that supports ES module imports and automatically defers execution until the HTML document has finished parsing.
  • createRoot: The mounting API provided by react-dom/client that initializes a concurrent React root container bound to a specific host DOM element.
  • React root: The controller object returned by createRoot that manages rendering and unmounting within a designated DOM container.
  • root.render: The method on a React root that schedules a virtual element tree to be rendered into the root container. Replaced legacy ReactDOM.render.

Summary

Mounting: the browser loads one page, and React fills one element of it with our components

❒ The root element: the page arrives with one empty element
  • ALWAYS leave <div id="root"> empty in index.html, and write everything the page shows in components.
  • NEVER type content inside the root element; React removes it on its first render.
❒ The build tool: the page's code arrives as plain JavaScript
  • ALWAYS open the project through npm run dev and its localhost address while you work.
  • IF the site goes to a server THEN send the dist folder from npm run build, checked first with npm run preview.
  • NEVER double-click index.html, in src or in dist; a file:// page stays blank.
❒ The React root: the page hands that one element to React
  • ALWAYS pass createRoot the element itself, found by the same id that index.html gives it.
  • NEVER call createRoot inside a component; it belongs in main.jsx, once.
❒ The initial render: the page shows the root component in that element
  • ALWAYS call render once, with one argument: the root component written as a tag.
  • NEVER copy ReactDOM.render from an old tutorial; React 19 removed it.
❒ One root per app: the page grows inside the root component
  • IF the app is built fully with React THEN add each new part of the page as a tag inside App, with one root and one render.
  • IF React runs only parts of an existing page THEN give each React area its own element and its own root.
