# Q172: Resuming State Snapshot Internals
* **Topic Tag**: #resume | ❱❱❱ ADVANCED (Server)
* **Interview Question**: *What must the saved state contain for resume to skip re-rendering?*
* **Core Truth**: Resuming skips re-executing server components because the prerender snapshot serializes both the prerendered HTML DOM tree and the Flight payload stream of unresolved promise holes, providing the client runtime with the exact Fiber slot map needed to stitch dynamic chunks in place without recalculating static components.
* **The Friction**: A long article on the site prerenders its static layout and article text at build time, but dynamically streams comments personalized for the signed-in user; a developer attempts to optimize TTFB with a custom cache, but breaks resuming because the cache strips the serialized Flight slot map, forcing the client to discard the prerendered DOM and re-fetch everything.
* **The Mechanism**: prerender() + resume(): `prerender` produces two streams: the static HTML shell and the postponement Flight state containing the tree of completed Fiber nodes alongside pending hole identifiers; the client or edge server passes this saved postponement state into `resume()` to continue rendering unresolved promises directly from the saved pause points.
* **Under the Hood**: Postponed Fiber serialization: when prerender encounters an unresolved promise or dynamic data access (`connection()`, cookies), it aborts that subtree, writes a postponement marker into the Flight payload with a slot ID, and serializes the surrounding completed Fiber tree into compact JSON-like chunks; `resume` mounts from this frozen snapshot, instantiating only the pending Fiber subtrees.
* **The Code Experiment**:
  * *Naive*: Re-rendering the entire component tree from root on the server for dynamic requests because static prerendering couldn't capture personalized dynamic subtrees.
  * *React*: Prerendering the static article shell into HTML and a postponement snapshot at build time, then using `resume()` at runtime to stream only the dynamic signed-in user payload into the pre-allocated Flight slots without re-rendering the static shell.
* **Scope Boundary**: Do not re-cover high-level differences between SSR, SSG, and resuming (covered in Q103/Q159); focus strictly on the internal contents of the prerender snapshot, postponed Fiber markers, slot ID mapping, and how the resume engine mounts directly at unresolved tree holes.
