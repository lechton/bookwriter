# Q60: When Built-In State Is Not Enough
* **Topic Tag**: `#state_libraries` | `❱❱ MORE`
* **Interview Question**: *When does an app outgrow useState and context, and what do external stores and server-cache libraries add?*
* **Core Truth**: Most "global state" in a React app is a copy of server data, and that copy belongs in a server-cache library (TanStack Query, SWR, or a framework's data loading) that shares one request per key, caches the result, and refetches it when it goes stale; the client-only state that remains is usually served by `useState`, `useReducer`, and context, and an external store (Zustand, Redux Toolkit) earns its place when many distant components read and write it often and each needs to subscribe to a small slice.
* **The Friction**: Three screens show three different like counts for the same article, because each one fetched its own copy in `useEffect` on mount and only one copy was updated after the reader liked it. The team moves the articles into one context provider, and now every like re-renders the entire list of articles because every consumer receives the new provider value.
* **The Mechanism**: Server cache: `useQuery({ queryKey: ['article', id], queryFn: () => fetchArticle(id) })`, where every component asking for the same key shares one request and one cached value, and a mutation invalidates the key so all three screens refetch the same fresh copy. Client store: `const saved = useReadingList((s) => s.saved.includes(id))` with Zustand, where a component re-renders only when its selected slice changes. Redux Toolkit adds one reducer-based store with strict update conventions and time-travel debugging for large teams.
* **Under the Hood**: External stores keep data outside React and notify subscribed components; their React bindings are built on `useSyncExternalStore` (Q53), so every component reads a consistent snapshot even during concurrent rendering. Each subscription compares its selected slice with `Object.is` and skips the re-render when the slice is unchanged, unlike a context provider, whose new value re-renders every consumer (Q59).
* **The Code Experiment**:
  * *Naive*: Article data fetched separately by three screens in `useEffect`, then copied into a single context object, with likes updated in one copy and the whole list of articles re-rendering on every change.
  * *React*: One `useQuery` key shared by the three screens and invalidated after the like mutation, plus a small Zustand store for the client-only reading-list panel.
* **Scope Boundary**: Focus on telling server cache from client state, what each library category adds, and the decision criteria for adopting one. Do not teach any library's full API, and do not re-teach `useSyncExternalStore` (Q53) or context splitting (Q59); server-side data fetching belongs to Q128.
