# Q13: Keeping Components Pure
* **Topic Tag**: `#purity` | `❱ CORE`
* **Interview Question**: *What does it mean for a component to be pure, and what breaks when it is not?*
* **Core Truth**: A pure React component acts as a mathematical formula: given the same inputs (props, state, context), it must always return the exact same JSX, producing zero mutations or observable side effects outside its render phase.
* **The Friction**: An engineer writes a `StoryByline` component that increments an external global counter `let guestCount = 0; guestCount++` or mutates an existing prop array during render. In production, concurrent renders, StrictMode double-rendering, or server rendering causes the counter to jump unpredictably, duplicating bylines and corrupting live article metadata.
* **The Mechanism**: The Purity Contract. Render logic must be pure: only calculate and return JSX, never mutate pre-existing variables, props, or external state during the render pass. Side effects are strictly quarantined to event handlers or effects.
* **Under the Hood**: Why React depends on idempotence: concurrent rendering can pause, abort, and restart component rendering multiple times before committing to the DOM. If rendering causes side effects, running a render twice produces corrupted application state.
* **The Code Experiment**:
  * *Naive*: A component mutating an external `let readCount = 0` variable or mutating `props.tags.push('Breaking')` directly inside its render function.
  * *React*: A pure `StoryByline` calculating display strings locally from incoming props without modifying any external bindings or input objects.
* **Scope Boundary**: Focus strictly on component render purity, the definition of side effects, and why render must be idempotent. Do not write `useEffect` (Q35) or custom hooks (Q39).
