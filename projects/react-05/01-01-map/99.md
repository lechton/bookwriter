# Q99: Legacy Ref Patterns: createRef, Callback Refs, and forwardRef
* **Topic Tag**: #legacy_refs | LEGACY
* **Interview Question**: *How did refs work before hooks: createRef, callback refs, and forwardRef?*
* **Core Truth**: Before React 19, refs evolved through string refs (deprecated), React.createRef() (for classes), callback refs, and forwardRef (for function components); React 19 simplifies this history by treating ref as a standard prop with cleanup callbacks.
* **The Friction**: While reviewing a 5-year-old codebase at The National Times, an engineer finds three conflicting ref patterns in search inputs: this.refs.input (string ref), this.myRef = React.createRef(), and const Input = forwardRef(...); unsure which is valid, the engineer struggles to modernize the component tree.
* **The Mechanism**: The evolution of refs: String refs (ref="input", abandoned due to performance and scoping bugs) -> createRef() (creates { current: null } on class instances) -> Callback refs (ref={el => this.input = el}) -> forwardRef (React 16.8–18 wrapper) -> React 19 ref as an ordinary prop.
* **Under the Hood**: Why string refs were removed: string refs required React to know the currently executing component ("owner"), had poor performance, prevented composability, and could not be statically typed; createRef worked well in classes but re-created a new ref object every render if called inside function components (necessitating useRef).
* **The Code Experiment**:
  * *Naive*: Calling React.createRef() inside a function component body, which creates a brand new { current: null } object on every render, losing the ref value.
  * *React*: Modernizing an old forwardRef and createRef class pattern into a React 19 function component with ref as a prop.
* **Scope Boundary**: Focus on the historical progression of refs and understanding legacy ref code. Do not write new code using string refs or createRef.
