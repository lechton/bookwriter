# Q89: Typing Components and Props in TypeScript
* **Topic Tag**: `#typescript_props` | `❱❱❱ ADVANCED`
* **Interview Question**: *How do you type React components, props, optional attributes, and children in TypeScript?*
* **Core Truth**: Typing React components in TypeScript requires defining explicit props interfaces with primitive types, optional fields (`?`), union literals, `React.ReactNode` for children, and extending native HTML attributes via `React.ComponentPropsWithRef`.
* **The Friction**: A team builds a design system in TypeScript. Developers type components as `const Button: React.FC<Props>`, which adds deprecated implicit children or breaks generic type inference; or they type `children: any` or forget optional prop flags, causing runtime crashes when optional callbacks are omitted.
* **The Mechanism**: Idiomatic React + TypeScript patterns: use standard function declarations with typed props interfaces (`interface ButtonProps { label: string; variant?: 'primary' | 'secondary'; children?: React.ReactNode; }`), avoiding `React.FC`, and extending native elements (`interface ButtonProps extends React.ComponentPropsWithRef<'button'>`).
* **Under the Hood**: TypeScript AST and JSX type checking: TypeScript uses `JSX.IntrinsicElements` to type built-in HTML tags and validates function component parameters against their defined prop interfaces; `ReactNode` encompasses all valid renderable JSX (elements, strings, numbers, fragments, null, undefined).
* **The Code Experiment**:
  * *Naive*: Using `React.FC` or `any` for props and children, losing type safety for native button attributes like `aria-label` or `disabled`.
  * *React*: A robust `StoryCard` component typed with a clean `interface StoryCardProps` including discriminated union variants and `React.ReactNode` slots.
* **Scope Boundary**: Focus strictly on typing components, prop interfaces, optional props, children, and extending HTML attributes. Do not cover generic components (Q92) or polymorphic `as` props (Q93).
