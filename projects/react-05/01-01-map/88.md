# Q88: Component Composition Patterns: Slots, Compound, and Render Props
* **Topic Tag**: `#component_composition_patterns` | `❱❱❱ ADVANCED`
* **Interview Question**: *How do Render Props, Compound Components, and Slot patterns structure flexible UI?*
* **Core Truth**: Advanced composition patterns—Slots (`children`, named JSX slots), Compound Components (shared context coordination), and Render Props (inverting rendering control)—solve configuration bloat by replacing dozens of rigid boolean props with flexible component collaboration.
* **The Friction**: An `ArticleCard` component grows to forty boolean and string props (`hasBadge`, `badgeColor`, `showAuthorBio`, `renderCustomFooter`, `onHeaderClick`). Every new newsroom layout request requires modifying the core card component, creating a bloated, unmaintainable monster.
* **The Mechanism**: The Three Core Composition Patterns: (1) Slots: passing JSX elements as props (`<Card header={<CustomHeader />} footer={<CustomFooter />} />`); (2) Compound Components: parent and child components sharing implicit context (`<Tabs><TabList><Tab /></TabList><TabPanels /></Tabs>`); (3) Render Props: functions returning JSX (`<List renderItem={item => <CustomRow item={item} />} />`).
* **Under the Hood**: Inversion of control: instead of the child component anticipating every possible visual layout permutation through props, the parent retains control over markup structure while the child manages state and behavioral logic.
* **The Code Experiment**:
  * *Naive*: A rigid `NewsCard` with 25 props trying to handle breaking badges, author avatars, social shares, and paywall banners through conditional prop flags.
  * *React*: A compound `ArticleCard` (`ArticleCard.Header`, `ArticleCard.Body`, `ArticleCard.Footer`) using shared context, allowing editorial pages to compose custom card layouts declaratively.
* **Scope Boundary**: Focus on architectural comparison and implementation of Slots, Compound Components, and Render Props. Do not introduce third-party UI component libraries.
