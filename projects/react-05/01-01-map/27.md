# Q27: Preserving and Resetting Component State
* **Topic Tag**: `#component_identity` | `❱ CORE`
* **Interview Question**: *Why does state sometimes vanish, or survive, when you did not expect it?*
* **Core Truth**: React ties component state to its position in the UI tree, not to the component function itself; rendering the same component at the same tree position preserves state, while rendering at a different position or with a different `key` destroys and resets state.
* **The Friction**: An editor switches between editing an "Opinion" piece and a "News" piece using the same form component. Because the component stays at the same tree position, the previous article's unsaved draft text unexpectedly persists into the second article. Conversely, toggling a wrapper `<div>` unexpectedly wipes out user input.
* **The Mechanism**: Component identity and the `key` reset trick. React preserves state as long as the component type and position in the tree match. Passing a unique `key={article.id}` forces React to unmount the old instance and reset state completely when switching articles.
* **Under the Hood**: Reconciliation tree diffing: React checks `element.type` and tree coordinates to identify component fibers. If type and position are identical, React reuses the existing Fiber and its `memoizedState`; changing the `key` or element type causes React to destroy the Fiber subtree and rebuild it from scratch.
* **The Code Experiment**:
  * *Naive*: Switching between two different records using the same form component without keys, causing text inputs to leak across records.
  * *React*: An `ArticleEditor` receiving `key={currentArticleId}`, cleanly resetting all local draft states whenever a different article is selected.
* **Scope Boundary**: Focus on tree position, component identity, and using `key` to intentionally reset state. Do not introduce `useRef` or external caching mechanisms.
