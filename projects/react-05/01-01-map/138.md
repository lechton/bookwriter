# Q138: Eliminating Server Waterfalls: Parallel Fetching with Promise.all
* **Topic Tag**: #server_resources | ❱❱ MORE (Server)
* **Interview Question**: *How do sequential awaits create waterfalls, and how do you fetch in parallel?*
* **Core Truth**: Sequential await statements inside an async Server Component create blocking execution waterfalls; initiating independent queries concurrently with Promise.all collapses the latency staircase into the duration of the single slowest query.
* **The Friction**: An article page at The National Times awaits getUser(), then awaits getArticle(), then awaits getRelatedStories(), and finally awaits getComments(); each query takes 150ms, causing the server render pass to take 600ms before sending a single byte of HTML.
* **The Mechanism**: Waterfall elimination: instead of const a = await fetchA(); const b = await fetchB();, start both promises before awaiting: const [a, b] = await Promise.all([fetchA(), fetchB()]); or pass unresolved promises to child components wrapped in <Suspense> using use().
* **Under the Hood**: Promise concurrency in V8: sequential await yields execution back to the event loop until the microtask resolves, delaying subsequent network calls; initiating promises concurrently dispatches network sockets in parallel, reducing total latency from the sum of durations to the max duration.
* **The Code Experiment**:
  * *Naive*: Writing four consecutive await statements in an async Server Component for independent database queries, multiplying total server render time.
  * *React*: Using Promise.all([getArticle(id), getTopStories(), getComments(id)]) to execute all three queries in parallel, cutting TTFB by 65%.
* **Scope Boundary**: Focus on identifying and eliminating sequential await waterfalls in Server Components. For streaming deferred promises with Suspense, see Q139.
