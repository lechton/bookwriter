# Q37: When You Don't Need an Effect
* **Topic Tag**: `#no_effect` | `❱ CORE`
* **Interview Question**: *When do you not need an Effect, and what replaces it?*
* **Core Truth**: Effects are only for synchronization with external systems; transforming data for rendering belongs directly in the render calculation, and handling user actions belongs directly in event handlers.
* **The Friction**: A developer wants to calculate the total reading time of filtered articles. They create `const [totalTime, setTotalTime] = useState(0)` and write a `useEffect` that listens to `[filteredArticles]` to call `setTotalTime`. This triggers an extra re-render cycle, flashes stale numbers on screen, and clutters the component with redundant effects.
* **The Mechanism**: Replacing unnecessary effects: calculate derived values directly in render (`const totalTime = calculateTime(articles)`), reset state using `key` props, and perform side effects (like sending an analytics POST or navigating) inside event handlers rather than effect listeners.
* **Under the Hood**: The "render-waterfall" penalty: an effect that sets state forces React to finish the current render, commit to the DOM, paint the screen, and immediately schedule a second render pass; in-render calculations execute in the exact same render pass with zero extra DOM operations.
* **The Code Experiment**:
  * *Naive*: Using `useEffect` to watch `firstName` and `lastName` state and set a `fullName` state, causing redundant renders and state drift.
  * *React*: Calculating `const fullName = `${firstName} ${lastName}`` directly during render, and placing a purchase confirmation POST inside `handleBuyClick`.
* **Scope Boundary**: Focus on identifying anti-pattern effects (derived state, prop-mirroring, event handling) and replacing them with pure in-render calculations or event handlers. Do not cover `useMemo` optimization (Q58).
