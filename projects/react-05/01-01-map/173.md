# Q173: Server Error Boundaries and Teardown Semantics
* **Topic Tag**: #server_errors | ❱❱❱ ADVANCED (Server)
* **Interview Question**: *What separates recoverable from unrecoverable errors in teardown and retry semantics?*
* **Core Truth**: React separates server errors into recoverable errors within Suspense boundaries—which emit client-retry fallback HTML while preserving the stream—and unrecoverable errors in the critical shell or root, which abort the stream, trigger immediate stream teardown, and fallback to full client-side rendering.
* **The Friction**: During a breaking disaster report at The National Times, a third-party weather widget throws an unhandled database exception; because the widget was placed outside a Suspense boundary in the page shell, it poisons the entire stream, aborting the HTTP response mid-flight and serving a blank white screen instead of rendering the critical news text.
* **The Mechanism**: onError vs onShellError: when a component throws inside a `<Suspense>` boundary, React marks it as a recoverable error, triggers `onError(error, errorInfo)`, emits the boundary's fallback HTML, and injects a client instruction to retry rendering the component in the browser; if an error occurs outside Suspense before `onShellReady`, React calls `onShellError` and tears down the entire server stream.
* **Under the Hood**: Reconciler stream abort protocol: within Suspense, an error cancels only the pending Fiber subtree, writing an error row (`E`) into the Flight stream and closing that boundary slot; in the shell, an uncaught error calls `stream.abort()`, destroys active writers, discards buffered chunks, and forces the server HTTP handler to return status 500 or fallback to pure client-side CSR.
* **The Code Experiment**:
  * *Naive*: Rendering unvetted third-party widgets directly in the server root layout, allowing a single widget failure to abort the entire Node.js stream and crash the page for all readers.
  * *React*: Isolating dynamic or risky widgets inside `<Suspense fallback={<WidgetSkeleton />}>` with an error boundary, allowing React to catch the server failure, stream the fallback HTML gracefully, and attempt client-side recovery without dropping the stream.
* **Scope Boundary**: Do not cover client-side Error Boundary class components (covered in Q51/Q101 of React Part One); focus strictly on server-side error classification, `onError` vs `onShellError`, stream teardown mechanics, Flight error rows, and server-to-client retry semantics.
