# Q109: Async Server Components: Direct Data Fetching and Replacing useEffect
* **Topic Tag**: #server_resources | ❱ CORE (Server)
* **Interview Question**: *How do Server Components read data with async/await, and what does that replace?*
* **Core Truth**: Server Components can be authored as native async JavaScript functions that directly await database queries, microservices, or filesystems, completely replacing the boilerplate of useEffect, useState, and loading spinners for server-fetched data.
* **The Friction**: A breaking news feed at The National Times previously required 30 lines of boilerplate: useState(data), useState(loading), useState(error), and a useEffect fetch call that caused layout shift and waterfalls; when migrating to RSC, a developer is shocked that an async function BreakingNews() can directly await db.articles.findMany().
* **The Mechanism**: async function ArticleList() { const articles = await fetchArticles(); return <ul>{articles.map(...)}</ul>; }: native JavaScript promises inside render without hooks; React pauses the server component until the promise resolves, then streams the rendered UI.
* **Under the Hood**: Suspense and promise resolution on the server: when an async Server Component awaits a promise, React uses its internal server scheduler to manage the pending promise; wrapped in <Suspense>, React streams the fallback shell immediately and flushes the resolved component chunk as soon as the promise fulfills.
* **The Code Experiment**:
  * *Naive*: Writing a client component with useState(null), useEffect(() => { fetch('/api/stories').then(...) }, []), and an annoying loading spinner.
  * *React*: Authoring an async function StoryFeed() Server Component that directly queries the database with await getTopStories() and renders plain markup.
* **Scope Boundary**: Focus on async/await syntax in Server Components, eliminating useEffect fetch boilerplate, and direct server resource access.
