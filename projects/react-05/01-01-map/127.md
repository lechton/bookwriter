# Q127: Shared Components: Authoring Directive-Free Isomorphic UI
* **Topic Tag**: #shared_components | ❱ CORE (Server)
* **Interview Question**: *What is a component with no directive: how does it run on both the server and the client?*
* **Core Truth**: Components authored without 'use client' or 'use server' are shared components that execute in whichever environment imports them—running on the server when imported by a Server Component, and on the client when imported by a Client Component.
* **The Friction**: An engineer at The National Times authors a Badge component without directives; another developer uses it inside an async Server Component, while a third uses it inside an interactive Client Component modal; a teammate argues that Badge must have 'use client' to work in the modal, causing unnecessary bundle bloat.
* **The Mechanism**: Shared components (directive-free): isomorphic by context; when imported by a Server Component, it renders to RSC payload and adds zero client JavaScript; when imported by a 'use client' component, it is compiled into the client bundle and runs in the browser.
* **Under the Hood**: Dual-environment constraints: a shared component must follow the strict intersection of both environments: it cannot use server-only features (direct database access, Node.js filesystem, secrets) and cannot use client-only features (useState, useEffect, window, browser DOM APIs).
* **The Code Experiment**:
  * *Naive*: Adding 'use client' to purely presentational UI components (like Typography, Badge, Icon), forcing them into the client bundle even when used on static server pages.
  * *React*: Keeping presentational components directive-free so they run on the server with zero client JS when used by Server Components, while remaining reusable in Client Components.
* **Scope Boundary**: Focus on shared components, environmental duality, and the rules of neutrality (no server secrets, no client hooks).
