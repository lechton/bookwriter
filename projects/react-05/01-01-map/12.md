# Q12: UI as a Tree
* **Topic Tag**: `#ui_tree` | `❱ CORE`
* **Interview Question**: *How does React see your UI as a tree, and why does that view matter?*
* **Core Truth**: React models applications as hierarchical tree structures—the module dependency tree, component tree, and render tree—which govern bundling, state scoping, top-down prop distribution, and the cascade of re-renders.
* **The Friction**: A developer sees their app as flat files and loose imports. When a header component re-renders, unexpected child components down the page re-render too; conversely, an imported heavy charting library balloons the bundle size even though it only appears in one nested tab. Without understanding tree representations, performance and architecture bugs remain invisible mysteries.
* **The Mechanism**: Mental models of the three React trees: the Module Dependency Tree (files and imports evaluated by bundlers), the Component Tree (parent-child JSX relationships describing UI structure), and the Render Tree (the live hierarchy of rendered React elements representing the current frame).
* **Under the Hood**: How React traverses the render tree during reconciliation from root to leaf, how tree position determines component lifecycle and state persistence, and how tree pruning (unmounting subtrees) cleans up associated DOM nodes.
* **The Code Experiment**:
  * *Naive*: Assuming components are isolated islands and placing heavy imports or global layout wrappers randomly without regard to tree hierarchy.
  * *React*: Structuring a clear newsroom hierarchy (`App` -> `PageLayout` -> `Header` / `ArticleGrid` / `Footer`) and tracing how props flow down the tree branches.
* **Scope Boundary**: Focus strictly on the structural mental models of trees (module, component, render tree) and top-down flow. Do not introduce Fiber node pointer internals (Q78) or virtual DOM diffing algorithms (Q77).
