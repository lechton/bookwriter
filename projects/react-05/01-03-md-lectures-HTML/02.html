Lecture 2: Project Scaffolding: Build Tools vs Full-Stack Frameworks

Interview Question

CORE

How do you create and run a new React project, and how do you choose between a framework and a build tool?

Imagine this scenario:

  1. Leo joins The National Times engineering team to build an internal dashboard for investigative reporters.
  2. The project requires an interactive screen to coordinate article edits, review news feeds, and verify fact checks.
  3. Leo opens the official documentation, which recommends installing a full-stack framework with server rendering.
  4. Why does a private newsroom tool behind an authentication login require a Node.js server runtime and edge infrastructure?
  5. Setting up a full-stack server creates ongoing server maintenance, edge deployment friction, and unnecessary hosting costs.
  6. The team only needs a fast client-side application compiled to static HTML, JavaScript, and CSS.
  7. Today, you will master project scaffolding with Vite and learn exactly when to choose a standalone build tool over a full-stack framework.

Monolithic Bundlers and Cold-Start Latency

In modern web development, you cannot run raw React code directly inside a browser without a build step. Browsers understand standard HTML, CSS, and vanilla JavaScript, but they cannot natively parse JSX tags like <App /> or unbundled module imports across hundreds of files. A build tool is a development program that compiles JSX into standard JavaScript functions, resolves package dependencies, and prepares files for the browser. Historically, developers relied on monolithic bundlers like Webpack, packaged inside tools like Create React App.

In legacy setups like Create React App, starting the local development server required crawling and bundling every single JavaScript module in the project into memory before serving a single page. Look at the monolithic bundling bottleneck below:

Legacy Monolithic Bundler

2const memoryBundle = compileAllModules(modules);

3server.listen(3000, () => {

4 console.log('Server ready');
5});

When a project grew to hundreds of components, running npm start meant waiting 30 to 60 seconds just to view a single text change. Every file save forced the bundler to reconstruct large module graphs in memory. This latency created a frustrating development loop. Modern development solves this by decoupling local development from production bundling.

⚡ IN THE WILD

Why did Create React App freeze large codebases? Legacy tools like Create React App were built around Webpack at a time when web browsers could not load JavaScript modules natively. The bundler had to crawl every import statement, convert every file into CommonJS or bundle chunks, and assemble a massive in-memory bundle before the local HTTP server could send its first response. If your newsroom dashboard imported 500 files, Webpack compiled all 500 files before you could preview a single button. Modern tools like Vite eliminate this by relying on browser-native ES Modules: the server starts instantly in milliseconds, and the browser requests only the exact files currently visible on your screen.

Interview Tip

To impress the interviewer: When asked how to start a new React project, do not recommend Create React App. Create React App is officially deprecated and unmaintained. Explain that for client-only single-page applications, the modern industry standard is Vite, while applications requiring search engine optimization or server-side rendering choose full-stack frameworks like Next.js or Remix.

Standalone Build Tools vs Full-Stack Frameworks

When starting a new React project today, your primary architectural decision is choosing between a standalone build tool and a full-stack framework. A standalone build tool, such as Vite, compiles client-side React code into static HTML, JavaScript, and CSS bundles that can be deployed to any static content delivery network (CDN) or cloud storage bucket. A full-stack framework, such as Next.js or Remix, combines React with a backend server runtime (such as Node.js or edge workers) to execute server rendering, server-side data fetching, and search engine optimization (SEO) pre-rendering.

If you are building a public-facing e-commerce storefront or a news publication where search engines must index HTML content immediately, a full-stack framework is essential. However, if you are building an internal newsroom dashboard behind a login wall, search engines never access the page. Choosing a full-stack framework for an internal tool adds unnecessary server hosting expenses, complex deployment pipelines, and server runtime maintenance.

To select the right toolchain, developers face a pedagogical crossroads between two architectural models:

  • Option 1 (The Standalone Client Model - Vite): Use Vite to build a fast Single-Page Application (SPA) executed entirely in the reader's browser, deployed as low-cost static files.
  • Option 2 (The Full-Stack Framework Model - Next.js / Remix): Use a full-stack framework to render React on a Node.js or edge server before sending HTML to the client.

The resulting files are pure static assets: an index.html file, compiled JavaScript bundles, and CSS stylesheets. You can host this application on low-cost static hosting like AWS S3, Cloudflare Pages, or GitHub Pages. There is zero server infrastructure to maintain, zero Node.js memory leaks, and zero server scaling headaches.

In Option 2, the framework renders HTML on the server before sending it over the network. This architecture is vital for public pages where search engine crawlers and social media preview bots demand pre-rendered markup. However, for our newsroom desk dashboard, this server overhead is unnecessary waste. The reporters log in, fetch data via client APIs, and interact with live controls. For this internal tool, Vite provides maximum speed with minimum operational overhead.

Key Takeaway

Choose a standalone build tool (Vite) when building client-only single-page apps, dashboards, or tools behind authentication. Choose a full-stack framework (Next.js/Remix) when search engine optimization, initial page load speed for public visitors, or server-side data mutations are core product requirements.

To build our newsroom desk dashboard, we will deconstruct the anatomy of a modern React project created with Vite. We will trace the project from initial CLI scaffolding through its build configuration, HTML entry point, JavaScript mounting bridge, and starter component.

Step 1
First, we scaffold the project with Vite
<terminal>

We begin by generating our project structure using the official Vite scaffolding command. In your terminal, run npm create vite@latest newsroom-desk -- --template react This command executes the create-vite CLI utility, which creates a new directory named newsroom-desk containing a pre-configured React template. Next, change into the directory, install the dependencies, and start the local development server:

Terminal
1npm create vite@latest newsroom-desk -- --template react
Scaffolds project DIRECTORY
2cd newsroom-desk
Enters workspace ROOT
3npm install
Downloads runtime DEPENDENCIES
4npm run dev
Launches local server on PORT 5173

Notice what happened when you ran npm run dev: the server started in less than 200 milliseconds. Unlike Create React App, which paused to compile every file into a bundle, Vite booted instantly. It started a native HTTP server and pre-bundled third-party dependencies using esbuild, a lightning-fast compiler written in Go. The server is immediately ready to accept incoming browser requests.

Step 2
Next, we inspect the manifest and build config
<package.json / vite.config.js>

Now we examine the two configuration files that govern our project: package.json and vite.config.js. First, open package.json. Notice how lean the dependencies are. Unlike legacy setups that pulled in hundreds of transitive packages via react-scripts, Vite separates runtime libraries (react and react-dom) from build-time developer tools (vite and @vitejs/plugin-react):

package.json
1{
2 "scripts": { "dev": "vite", "build": "vite build" },

4 "devDependencies": {
5 "@vitejs/plugin-react": "^4.3.0",

8}

Notice the role of @vitejs/plugin-react: during development, this plugin uses esbuild to transform JSX into browser-compatible JavaScript on the fly. In production, it coordinates with Vite's bundler to produce optimized, minified static files. Everything is declared in seven clean lines of code.

Step 3
Then, we connect the HTML host to React
<index.html / src/main.jsx>

Next, we explore the bridge between the physical HTML document and the React JavaScript runtime. In legacy bundlers, index.html was hidden inside a /public directory and treated as a passive template. In Vite, index.html is the first-class entry point of your application and lives directly in the project root:

index.html
1<!DOCTYPE html>
2<html lang="en">
3 <head><meta charset="UTF-8" /><title>Newsroom Desk</title></head>
4 <body>
5 <div id="root"></div>
Physical mount target for React DOM
6 <script type="module" src="/src/main.jsx"></script>
Native browser module ENTRY
7 </body>
8</html>

Notice the line <script type="module" src="/src/main.jsx"> This single tag unlocks Vite's speed. The browser reads type="module" and understands that it can request JavaScript modules natively over HTTP. When the browser requests /src/main.jsx, Vite intercepts the request, transforms the JSX into pure JavaScript, and returns it to the browser immediately.

Now open src/main.jsx. This file is the JavaScript entry point. It imports React's DOM renderer, locates the <div id="root"> element, and mounts our application component tree:

In main.jsx, notice the call createRoot(container). This is the single imperative bridge in your entire application. It connects the physical browser DOM to React's declarative world. Once root.render(<App />) executes, React takes full responsibility for computing and rendering the user interface inside <div id="root">.

When you save changes in src/App.jsx, observe what happens in your browser: the text updates instantly without a full page reload. This mechanism is called Hot Module Replacement (HMR). Because Vite knows the exact module dependency graph, it only invalidates and replaces the changed App.jsx module in the browser's memory, preserving all other page state intact.

Component Summary

App

The root application component provides the initial visual tree rendered by Vite. It owns the starter UI layout and demonstrates client-side JSX rendering in memory. Notice it imports zero global CSS side-effects directly, keeping its structure cleanly isolated. Why? To serve as the top-level boundary where feature containers mount.

main

The client entry point bridges the physical DOM and the React runtime. It executes createRoot against the native <div id="root"> element declared in index.html. Notice it passes zero props to App, serving strictly as an imperatively invoked mounting bridge. This architecture ensures React never controls global document markup outside its designated root container.

In our scaffolding experiment, we proved that modern React does not require opaque monolithic bundlers or complex server runtimes to build rich interactive applications. By using Vite, we gain instant development feedback through native browser modules and generate lean static bundles ready for global CDN deployment. Full-stack frameworks remain vital for public SEO pages, but standalone build tools provide the ideal foundation for client-rendered applications.

Where you will meet this

  1. Internal Operations Dashboards: Building private newsroom CMS editors, customer support portals, and analytics consoles that run entirely in the browser behind enterprise authentication.
  2. Single-Page Web Applications (SPAs): Creating client-heavy productivity tools, interactive audio/video editors, and diagramming canvas apps that require zero server-side rendering.
  3. Public E-Commerce & Media Publications: Evaluating when to migrate a marketing storefront from a client-only Vite SPA to Next.js or Remix to achieve sub-second SEO indexing and social media card previews.
  4. Micro-Frontend Architecture: Developing isolated client widgets and embeddable interactive calculators that bundle to static JavaScript assets and mount onto legacy host pages.

Glossary

  • Build Tool: A development program (such as Vite) that transforms JSX, resolves module dependencies, and bundles static assets for browser execution.
  • Full-Stack Framework: An integrated application framework (such as Next.js or Remix) that pairs React with a backend server runtime for server-side rendering, routing, and data mutations.
  • Native ES Modules: The ECMAScript standard for loading JavaScript files in web browsers using <script type="module"> and standard import / export syntax without upfront bundling.
  • Hot Module Replacement (HMR): A development server capability that swaps updated JavaScript modules in the browser memory in real time without triggering a full page refresh.
  • Single-Page Application (SPA): A web application architecture where the browser loads a single static HTML page and dynamically updates content via client-side JavaScript rendering.

Beyond the basics

  • Native ES modules and browser module graphs: Modern browsers natively parse import and export statements when loaded with <script type="module">, allowing Vite to serve unbundled source files directly during development and letting the browser handle dependency resolution (see react.dev/learn/start-a-new-react-project).
  • Dependency pre-bundling with esbuild: Vite uses esbuild written in Go to convert CommonJS dependencies into standard ES modules and bundle multi-file libraries into single cached files, preventing hundreds of simultaneous HTTP network requests on cold start (see react.dev/learn/start-a-new-react-project).
  • Client-side rendering vs server-side rendering: Client-side rendering (CSR) downloads an empty HTML container and executes JavaScript in the browser to construct DOM nodes, whereas server-side rendering (SSR) generates fully populated HTML strings on a Node.js server before delivery (see react.dev/learn/understanding-your-ui-as-a-tree).
  • The root HTML entry point convention: In Vite, index.html resides in the project root rather than a public subfolder because Vite treats the HTML file as the central source code entry point, discovering script tags and assets directly from the markup (see react.dev/learn/start-a-new-react-project).
  • Separation of runtime and dev dependencies: The package.json manifest strictly isolates packages executed in the user's browser (dependencies) from build tools, compilers, and linters executed exclusively in the developer's Node.js environment (devDependencies) (see react.dev/learn/start-a-new-react-project).
  • Strict mode in development: React's <StrictMode> component intentionally double-invokes component render functions in local development to help developers identify impure calculations, memory leaks, and unintended side effects before deploying to production (see react.dev/reference/react/StrictMode).

❒ Toolchain Selection

➔ ALWAYS choose a standalone build tool like Vite when building client-only single-page apps, dashboards, or tools behind authentication.

➔ ALWAYS choose a full-stack framework like Next.js or Remix when search engine optimization, public pre-rendering, or server-side data mutations are core requirements.

➔ NEVER use Create React App for new projects, as it is officially deprecated and frozen on unmaintained monolithic bundlers.

➔ ALWAYS place index.html at the project root when using Vite so the bundler can treat the HTML document as the primary entry point.

➔ ALWAYS separate runtime packages (dependencies) from build tools (devDependencies) in package.json to prevent bundle bloat.
