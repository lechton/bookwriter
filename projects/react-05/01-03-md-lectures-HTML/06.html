The Disconnected Component and the Blank Screen

In plain web development, HTML markup paints DOM nodes directly into the viewport. When you author a React component like App.jsx, you write a JavaScript function that returns an in-memory description of user interface elements. Sitting on disk, App.jsx is inert code. It has no physical connection to the browser's Document Object Model. Without an explicit bridge connecting your compiled JavaScript bundle to an existing HTML element, the browser parses index.html, encounters an empty <div id="root"></div>, and displays a completely blank page.

When developers first attempt to connect their component to the DOM, they often reach for legacy APIs or invoke mounting commands before the target container exists in memory.

Look at the naive attempt below:

Naive Mounting Attempt
1import ReactDOM from 'react-dom';
WRONG: legacy package import deprecated in REACT 19
2import App from './App.jsx';
3
4const container = document.getElementById('root');
FRAGILE: null if script executes before HTML PARSES
5ReactDOM.render(<App />, container);
WRONG: legacy synchronous mounting triggers DEPRECATION WARNING

The legacy ReactDOM.render API belonged to the pre-concurrent era of React. It forced synchronous rendering, meaning any slow render pass froze the browser main thread. In React 19, ReactDOM.render is deprecated. Calling it produces console warnings and disables concurrent features. Furthermore, if your script runs in the <head> before the browser parses <div id="root">, document.getElementById('root') evaluates to null. Passing null to mounting APIs crashes the application with a fatal TypeError: Target container is not a DOM element

⚡ IN THE WILD

Why does createRoot separate creation from rendering? When developers first learn createRoot, they wonder why React split one ReactDOM.render() call into two separate steps: createRoot(domNode) and root.render(<App />). Why not keep a single function? Because createRoot initializes the concurrent Fiber root container on the physical DOM node once, while .render() can be called repeatedly to update the tree. By separating container creation from element rendering, React coordinates concurrent priority levels, preserves event listeners across updates, and allows root unmounting via root.unmount() without tearing down the physical DOM node.

Interview Tip

To impress the interviewer: When asked how App.jsx gets onto the page, explain that createRoot is a two-step mounting bridge from react-dom/client. It first creates a concurrent Fiber root container attached to a physical DOM node, and then renders the virtual element tree into that container. Emphasize that legacy ReactDOM.render is deprecated in React 19 because it lacks concurrent rendering support.

The Two-Step Mounting Bridge: createRoot and root.render

To bridge the gap between static HTML and declarative React components, modern React introduces createRoot from the react-dom/client package. The mounting process consists of two distinct phases: establishing the root container in the DOM, and rendering the component tree into that root.

The mounting API follows a strict two-step execution pattern:

  1. Step 1: Container Creation: Calling const root = createRoot(domNode) creates a React root object attached to the physical DOM container.
  2. Step 2: Tree Rendering: Calling root.render(<App />) schedules and commits the initial render pass into the container.

When retrieving the container element from the DOM, you face an architectural crossroad between two implementation strategies:

  • Option 1 (The foundational way): Query the DOM directly without verification, risking null pointer exceptions if the element is missing.
  • Option 2 (The modern idiomatic way): Verify that the container element exists before calling createRoot, throwing a descriptive error if missing.

First, look at Option 1 using an unchecked DOM query:

Option 1: The Foundational Way (Unchecked Query)
1import { createRoot } from 'react-dom/client';
2import App from './App.jsx';
3
4const container = document.getElementById('root');
5createRoot(container).render(<App />);
Crashes if container is NULL

In Option 1, the code assumes document.getElementById('root') always returns a valid DOM element. If an engineer renames the element ID in index.html or loads the script before the DOM tree parses, container evaluates to null, causing an unhandled runtime crash.

Next, look at Option 2 using defensive null verification:

Option 2: The Modern Idiomatic Way (Guarded Mount)
1import { createRoot } from 'react-dom/client';
2import App from './App.jsx';
3
4const container = document.getElementById('root');
5if (!container) {
6 throw new Error('Failed to find the root element');
Halts with clear ERROR
7}
8createRoot(container).render(<App />);
Safely mounts into CONTAINER

In Option 2, the explicit guard halts execution immediately with an informative error message if the DOM node is absent. This prevents silent white-screen failures and pinpoints the exact misconfiguration during development.

Key Takeaway

Always verify that your target DOM container exists before calling createRoot. A defensive check prevents silent white screens and immediately alerts your team to missing HTML container elements.

To master createRoot and understand how App.jsx reaches the screen, we will construct the live broadcast desk for The National Times. We will progress across four sequential steps: inspecting the host HTML document in index.html, constructing the root component in src/App.jsx, declaring the child banner in src/components/BreakingBanner.jsx and establishing the concurrent mounting bridge in src/main.jsx.

Step 1
First, we inspect the host container
<index.html>

We begin by inspecting index.html at the project root. This file is the physical HTML document delivered to the browser. Inside the <body>, it provides a single empty <div> with id="root", followed by a module script tag that loads our JavaScript entry point:

index.html
1<!DOCTYPE html>
2<html lang="en">
3 <body>
4 <div id="root"></div>
Physical mounting TARGET
5 <script type="module" src="/src/main.jsx"></script>
Module entry POINT
6 </body>
7</html>

Notice the placement of <script type="module">: because it carries type="module", the browser defers execution until the HTML document is fully parsed. This ensures <div id="root"> exists in the DOM by the time src/main.jsx executes.

Next, we construct the root component
<src/App.jsx>

Now we author the top-level application component in src/App.jsx. This component acts as the root of our declarative React element tree. It imports BreakingBanner and returns the broadcast container layout:

src/App.jsx

2
3export default function App() {
4 return (
5 <main className="broadcast-shell">

9}

Notice that App.jsx contains pure JSX. It does not touch document.getElementById, query the DOM, or invoke any mounting methods. Component functions remain purely declarative, describing what to render rather than how to place it in the DOM.

The child component encapsulates its own markup and styles. It receives no direct knowledge of the root DOM node or how the application was mounted. Decoupling components from the mounting mechanism ensures they can be tested, reordered, or embedded anywhere in the tree.

Step 4
Finally, we initialize createRoot and mount the tree
<src/main.jsx>

Finally, we create src/main.jsx. This file is the dedicated client entry point that bridges our physical HTML document with our declarative React component tree. We import createRoot from react-dom/client, locate the container with a defensive guard, and call .render(<App />):

src/main.jsx
1import { createRoot } from 'react-dom/client';
2import App from './App.jsx';
3
4const container = document.getElementById('root');
5if (!container) {
6 throw new Error('Target container div#root was not found');
Diagnostic ERROR
7}
8
9const root = createRoot(container);
Initializes concurrent ROOT
10root.render(<App />);
Projects element tree into DOM

Notice what happens when root.render(<App />) executes: React calls the App component function, receives the element tree descriptor, and constructs the corresponding browser DOM nodes (<main>, <header>, <span>, <h1>) inside <div id="root">. Furthermore, React establishes event delegation on container, capturing all user events at the root boundary.

In our experiment, we saw how inert component files reach the browser screen. By pairing index.html with src/main.jsx, we established a robust mounting bridge using createRoot. The two-step initialization creates a concurrent Fiber root container and safely projects declarative JSX into physical DOM pixels.

Where you will meet this

  1. Single-Page Application Bootstrapping: Initializing the root component of a Vite or Webpack client-side application.
  2. Multi-Root Micro-Frontends: Mounting independent React widgets into separate DOM containers on the same legacy page.
  3. Modal and Portal Targets: Creating secondary mounting roots for floating dialogs and fullscreen overlays outside the primary tree.
  4. Testing Environments: Mounting component trees into isolated JSDOM containers during unit and integration test runs.

Glossary

  • createRoot: The official factory function from react-dom/client that initializes a concurrent React root container attached to a physical DOM node.
  • Concurrent Root: A React root instance that supports React 19 concurrent features, interruptible rendering, and priority scheduling.
  • Fiber Root: The internal React data structure that tracks the root container, reconciliation queue, and active element tree in memory.
  • Event Delegation: The architecture where React attaches a single event listener per event type to the root container rather than individual DOM nodes.
  • Root Container: The physical DOM element (typically <div id="root">) that houses the entire rendered React component tree.

Beyond the basics

  • The two-step createRoot lifecycle: Calling createRoot(container) creates a FiberRootNode in memory, while calling root.render(element) schedules the initial concurrent render pass (see react.dev/reference/react-dom/client/createRoot).
  • Root unmounting mechanics: Calling root.unmount() destroys the entire React tree, unbinds root event listeners, and clears the container element (see react.dev/reference/react-dom/client/createRoot#root-unmount).
  • Hydration with hydrateRoot: When server-rendered HTML exists in the container, applications use hydrateRoot(domNode, <App />) instead of createRoot to attach event listeners without destroying existing markup (see react.dev/reference/react-dom/client/hydrateRoot).
  • Multiple roots on a single page: A single HTML document can host multiple independent createRoot containers, enabling progressive migration of legacy server templates (see react.dev/reference/react-dom/client/createRoot#rendering-a-page-partially-built-with-react).
  • Strict Mode verification: Wrapping the root element in <StrictMode> causes React to double-invoke component render passes in development to catch impure side effects (see react.dev/reference/react/StrictMode).

Architectural Takeaways & Decision Matrix

❒ Root Initialization & Mounting

➔ ALWAYS import createRoot from react-dom/client when mounting React 19 applications into the browser DOM.

➔ NEVER use deprecated ReactDOM.render from react-dom because it disables concurrent rendering and triggers console warnings.

➔ IF querying the DOM container THEN verify that the element exists before calling createRoot to avoid null pointer crashes.

❒ Component Separation & Delegation

➔ ALWAYS keep component files purely declarative and free of direct DOM queries like document.getElementById.

➔ NEVER attach manual DOM event listeners inside components when React's root event delegation handles them automatically.
