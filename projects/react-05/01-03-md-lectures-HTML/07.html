Lecture 7: Splitting Components Across Files with ES Modules

Interview Question

CORE

How do you split components across files, and how do default and named imports differ?

Imagine this scenario:

  1. Maya manages the front-page editorial desk for The National Times.
  2. Her team writes five distinct layout components directly inside a single 1,200-line App.jsx file.
  3. When Maya tries to split them into separate files, she wraps a default export in curly braces during import.
  4. Why does the application crash with "Element type is invalid: expected a string or class/function but got undefined"?
  5. The build passes, but the newsroom homepage crashes immediately upon opening in the browser.
  6. Default exports attach to the module's default property, while curly braces instruct JavaScript to search for a named property that does not exist.
  7. Today, you will master ES module splitting, default exports, and named exports to organize React components cleanly across files.

The Monolithic File and the Import Trap

In early project stages, developers often place multiple components in a single file for convenience. As an application grows, a monolithic App.jsx becomes an unmaintainable bottleneck. Five developers editing different widgets inside the same file generate endless merge conflicts. Furthermore, locating bugs in a 1,200-line script slows down the entire engineering team. To build scalable React applications, you must extract each component into its own dedicated ES module file.

When splitting components into separate files, mistyping import syntax causes fatal runtime crashes.

Look at the naive attempt below:

Naive Import Mismatch
1import { ArticleCard } from './ArticleCard.jsx';
WRONG: curly braces search named property on DEFAULT EXPORT
2
3export default function App() {
4 return <ArticleCard />;
WRONG: crashes with undefined element type EXCEPTION
5}

When a file exports a component using export default the bundler places that function on the .default property of the module namespace object. If you write import { ArticleCard } from './ArticleCard.jsx' the JavaScript engine looks for an export literally named ArticleCard. Because none exists, ArticleCard is assigned undefined. When React attempts to render <ArticleCard />, it invokes _jsx(undefined, {}). React throws a fatal runtime exception: Error: Element type is invalid: expected a string or a class/function but got: undefined. You likely forgot to export your component or mixed up default and named imports.

⚡ IN THE WILD

Why does an undefined component crash during rendering instead of import? When developers mix up import syntax, they expect Vite or the browser to throw a syntax error immediately at the import statement. Why does the file load silently, only to explode when React renders? Because in JavaScript ES modules, importing a non-existent named export from a module is legally permitted at syntax level; it simply resolves to undefined. The failure only occurs when React's runtime attempts to evaluate <ArticleCard />. React inspects the first argument to _jsx() and finds undefined instead of a function or DOM string tag, halting with a fatal type error.

Interview Tip

To impress the interviewer: When asked how default and named imports differ, explain that a default export binds to the module's internal .default property and is imported without curly braces, while named exports represent specific properties and must be imported with curly braces matching their exact exported names.

Default vs. Named Exports: The Module Boundary

Organizing components across dedicated files is the cornerstone of scalable React architecture. In modern JavaScript, the ES module system provides two mechanisms for sharing code across files: default exports and named exports.

The two export mechanisms serve distinct architectural roles:

  1. Default Exports (export default): Each file can have at most one default export. It represents the primary component that defines the file (such as export default function ArticleCard). Consumers import it without curly braces: import ArticleCard from './ArticleCard.jsx'
  2. Named Exports (export function): A file can have multiple named exports. They represent secondary helper functions, constants, or companion components (such as export function formatRole). Consumers import them using curly braces: import { formatRole } from './ArticleCard.jsx'

When organizing component files, you face an architectural crossroad between two team conventions:

  • Option 1 (The foundational way): Use named exports for everything, forcing curly braces on every import across the codebase.
  • Option 2 (The modern idiomatic way): Use a default export for the primary component, and named exports for companion helpers and formatters.

First, look at Option 1 using named exports exclusively:

Option 1: The Foundational Way (Named-Only)
1export function ArticleCard() {
Named export for primary COMPONENT
2 return <article className="card">Headline</article>;
3}
4
5import { ArticleCard } from './ArticleCard.jsx';
Requires curly braces on IMPORT

In Option 1, every export is named. This guarantees that consumers cannot accidentally rename the component upon import, enforcing strict naming consistency across the team. However, it requires curly braces on every import, creating friction when a file clearly represents one single component.

Next, look at Option 2 using the modern idiomatic pattern:

Option 2: The Modern Idiomatic Way (Default Component + Named Helper)
1export function formatRole(role) {
Named export for utility HELPER
2 return `By ${role.toUpperCase()}`;
3}
4
5export default function ArticleCard() {
Default export for primary COMPONENT
6 return <article className="card">{formatRole('news')}</article>;
7}

In Option 2, the file has one unambiguous primary identity: the ArticleCard component. Any secondary utility or data transformer is exported alongside it as a named export. Consumers can import the primary component cleanly (import ArticleCard from './ArticleCard.jsx') or pull in helpers as needed (import ArticleCard, { formatRole } from './ArticleCard.jsx').

Key Takeaway

Use a default export for the single primary component of a file. Use named exports for secondary utility functions, constants, or companion components. Never wrap a default import in curly braces.

App

The parent component provides the outer newsroom page shell. It imports ArticleCard via a default import without curly braces. Notice it delegates all editorial presentation to the child files. Why? To keep the root layout clean, modular, and immune to merge conflicts.

ArticleCard

The boundary component encapsulates the article presentation. It exports itself as the default component while importing AuthorBadge and formatRole from a companion module. AuthorBadge

The terminal child component renders the reporter profile and exports a named utility helper. Notice it exports the badge component as default and formatRole as a named export. This structure allows consumers to import the visual widget alone or the helper alongside it.

In our experiment, we saw how a sprawling monolithic component was extracted into clean, focused ES module files. By leveraging default exports for primary components and named exports for companion helpers, we eliminated the danger of undefined element type crashes while establishing a scalable file architecture for the newsroom desk.

Where you will meet this

  1. Component Library Architectures: Organizing design system packages where each component resides in its own file alongside sub-components and icon assets.
  2. Utility Helper Co-location: Exporting validation functions, date formatters, and calculation helpers alongside the form components that consume them.
  3. Page Route Splitting: Separating Next.js or React Router page views into dedicated modules imported by top-level routing tables.
  4. Barrel File Aggregations: Re-exporting multiple component modules from a central index.js file using export { default as ArticleCard } from './ArticleCard.jsx'

Glossary

  • Default Export: The primary export of an ES module (export default), imported without curly braces and bound to .default on the module namespace.
  • Named Export: A specific exported member of an ES module (export function), imported with curly braces matching its exact identifier.
  • Module Specifier: The path string in an import statement (such as './components/ArticleCard.jsx') indicating the target file's location on disk.
  • Module Namespace Object: The internal JavaScript object containing all exports of a module, where default exports sit on .default and named exports sit on matching keys.
  • Component Extraction: The architectural process of refactoring a component from a monolithic file into its own dedicated ES module file.

Beyond the basics

  • Default vs named export specifications: In the ECMAScript module specification, default exports are syntactic sugar for a named export with the identifier default (see react.dev/learn/importing-and-exporting-components).
  • Import aliases with the as keyword: Both named and default imports can be renamed during import to resolve naming collisions via import { formatRole as formatTag } (see react.dev/learn/importing-and-exporting-components).
  • Re-exporting from barrel files: Modules can re-export components directly using export { default } from './ArticleCard.jsx' creating clean public entry points for component directories (see react.dev/learn/importing-and-exporting-components).
  • Dynamic imports and code splitting: React supports lazy loading components via React.lazy(() => import('./ArticleCard.jsx')) which requires the imported module to provide a default export (see react.dev/reference/react/lazy).
  • File extension resolution in bundlers: Modern bundlers like Vite resolve .jsx and .js extensions automatically, though explicit extensions improve module clarity and native ESM compatibility (see react.dev/learn/importing-and-exporting-components).

Architectural Takeaways & Decision Matrix

❒ Module Exports & File Structure

➔ ALWAYS dedicate each component file to a single primary component exported via export default

➔ NEVER place multiple major UI layout components in a single monolithic file once they exceed 50 lines.

➔ IF exporting secondary utility functions or constants alongside a component THEN use named exports (export function).

❒ Import Syntax & Braces

➔ ALWAYS import default exports without curly braces (import ArticleCard from './ArticleCard.jsx').

➔ NEVER wrap default imports in curly braces (import { ArticleCard }) because this resolves to undefined and crashes React during render.

➔ IF importing both a default component and named helpers THEN combine them in one statement (import ArticleCard, { formatRole } from './ArticleCard.jsx').
