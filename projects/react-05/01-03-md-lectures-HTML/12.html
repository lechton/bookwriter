Lecture 12: UI as a Tree

Interview Question

CORE

How does React see your UI as a tree, and why does that view matter?

Imagine this scenario:

  1. Marcus joins The National Times digital newsroom as a junior frontend engineer.
  2. Marcus views the codebase as a loose folder of JavaScript files and HTML fragments.
  3. When a ticker in the header updates, an unrelated video player in the footer restarts its playback buffer!
  4. Why did changing one corner of the page trigger an avalanche across unrelated components?
  5. React does not view your application as disconnected files; it sees a living, branching tree.
  6. Three distinct trees govern your app: the module dependency tree, the component tree, and the live render tree.
  7. Today, you will master React's three tree models, trace top-down prop distribution, and understand render tree lifecycles.

The Flat File Illusion and the Branching Reality

When developers look at their code editor, they see a flat list of files in a directory: HeaderBar.jsx, ArticleGrid.jsx, and NewsLayout.jsx. It is tempting to think of components as independent, disconnected islands that happen to share a page. In reality, React never sees a flat collection of files. React models user interfaces as hierarchical tree structures with strict parent, child, ancestor, and descendant relationships. Understanding this mental model is essential, because every major React mechanism—bundling, top-down prop flow, state scoping, and re-rendering—flows along the branches of these trees.

Treating components as isolated files leads to severe architectural defects.

Look at the naive attempt below, where a developer places a heavy third-party charting library and global state wrappers randomly inside a leaf component:

Naive Component Isolation and Scattered Imports
1import { HeavyAnalyticsChart } from 'heavy-chart-lib';
BLATANT: imported in every LEAF COMPONENT
2
3export default function ArticleCard({ story }) {
4 return (
5 <article className="card">
6 <h3>{story.title}</h3>
7 <HeavyAnalyticsChart data={story.metrics} />
Bloats bundle across ALL BRANCHES
8 </article>
9 );
10}

In the naive code, importing HeavyAnalyticsChart directly into ArticleCard pollutes the module dependency tree. Bundlers like Vite and Rollup crawl import statements starting from the entry point. Because ArticleCard imports the heavy library, that library is bundled into the primary critical chunk downloaded by every single mobile reader, even if the user never scrolls down to view analytics! Furthermore, when parent components re-render, all child components down the tree branch re-render too. Without a clear tree model, performance optimizations and bundle boundaries remain impossible to debug.

⚡ IN THE WILD

Why does unmounting a parent destroy child state? When a parent component unmounts or conditionally returns null, its entire branch vanishes from the render tree. Many developers are shocked when an input field or video player inside a child component resets its state completely when the parent momentarily unmounts. In React, component state does not live in your component file; it lives inside React's internal nodes attached to specific positions in the render tree. When a parent branch is pruned from the render tree, React destroys all associated DOM nodes and discards state for every child and grandchild on that branch!

Interview Tip

To impress the interviewer: When asked why React views UI as a tree, explain that three distinct trees govern an application: (1) the Module Dependency Tree evaluated by bundlers to split code and manage chunk sizes, (2) the Component Tree representing parent-child JSX relationships and top-down prop distribution, and (3) the Render Tree representing the live element hierarchy of the current frame that governs reconciliation and subtree pruning.

The Three Trees Governing Your Application

To build scalable applications, an engineer must distinguish between the three different trees that exist at different stages of your application's lifecycle: the Module Dependency Tree, the Component Tree, and the Render Tree.

The Module Dependency Tree represents the static relationship between files on disk. Every JavaScript module is a node, and every import statement is a directed edge. Bundlers like Vite and Rollup inspect this tree to determine which code to package, which unused exports to drop (tree shaking), and where to split bundles. This tree is evaluated at build time.

The Component Tree describes the logical hierarchy of your components based on JSX nesting: <NewsLayout> contains <HeaderBar> and <ArticleGrid>. This tree defines how props flow downward from ancestors to descendants. The Render Tree is the live, runtime hierarchy of React element objects evaluated during the current render pass. The render tree contains only the components that are currently rendered on screen (ignoring unrendered conditional branches) along with native host elements like <div> and <header>.

When structuring page layout, you face an architectural crossroad between two organizational patterns:

  • Option 1 (The foundational way): A monolithic page function declaring all markup in a single flat return block, obscuring structural branches.
  • Option 2 (The modern idiomatic way): A decomposed layout orchestrator composing clear branch components (HeaderBar, ArticleGrid) that receive curated props.

First, look at Option 1 using a monolithic layout:

Option 1: The Foundational Way (Monolithic Flat Layout)
1export default function NewsPage({ edition, stories }) {
2 return (
3 <div className="page-shell">
4 <header><h1>{edition.name}</h1><p>{edition.date}</p></header>
Inlined HEADER MARKUP
5 <main>{stories.map(s => <div key={s.id}>{s.title}</div>)}</main>
Inlined CONTENT GRID
6 </div>
7 );
8}

In Option 1, all layout concerns are compressed into a single flat function. While syntactically valid, it fails to establish clear tree branches, making it impossible to reuse the header or optimize the article grid independently.

Next, look at Option 2 using decomposed tree branches:

Option 2: The Modern Idiomatic Way (Decomposed Tree Branches)
1export default function NewsLayout({ edition, stories }) {
2 return (
3 <div className="page-shell">
4 <HeaderBar edition={edition} />
Branch 1: dedicated NAVIGATION TRUNK
5 <ArticleGrid stories={stories} />
Branch 2: dedicated CONTENT BRANCH
6 </div>
7 );
8}

In Option 2, NewsLayout acts as the trunk of the tree, branching cleanly into HeaderBar and ArticleGrid. Each branch encapsulates its own sub-elements, props flow deterministically downward, and each branch can be inspected, tested, or pruned without disturbing siblings.

Key Takeaway

Always think in trees: data flows strictly down the branches via props, component lifecycles are bound to tree position, and bundlers package code according to the module dependency tree.

To master React's tree architecture, we will construct the hierarchical newsroom layout for The National Times. We will progress across four sequential steps: constructing the layout orchestrator in src/components/NewsLayout.jsx, building the navigation branch in src/components/HeaderBar.jsx, declaring the content grid in src/components/ArticleGrid.jsx with nested StoryCard terminals, and mounting the tree inside src/App.jsx.

Step 1
First, we construct the parent layout container
<NewsLayout.jsx>

We begin by constructing src/components/NewsLayout.jsx. This component acts as the trunk of our feature tree. It receives top-level edition metadata and stories, and branches the UI into HeaderBar and ArticleGrid:

src/components/NewsLayout.jsx
1import HeaderBar from './HeaderBar.jsx';
2import ArticleGrid from './ArticleGrid.jsx';
3
4export default function NewsLayout({ edition, stories }) {
5 return (
6 <div className="layout-shell">
7 <HeaderBar edition={edition} />
Passes edition to NAVIGATION BRANCH
8 <ArticleGrid stories={stories} />
Passes stories to GRID BRANCH
9 </div>
10 );
11}

Notice how NewsLayout establishes two distinct branches. It does not mix masthead markup with article cards. Instead, it delegates responsibilities down to dedicated child components, ensuring that props flow cleanly along designated tree paths.

Step 2
Next, we build the navigation branch
<HeaderBar.jsx>

Now we construct src/components/HeaderBar.jsx. This component forms the first major branch of the tree, consuming the edition prop to display the newspaper masthead and publication date:

src/components/HeaderBar.jsx
1export default function HeaderBar({ edition }) {
2 const { masthead, issueDate } = edition;
3 return (
4 <header className="masthead-header">
5 <h1 className="masthead-title">{masthead}</h1>
6 <span className="edition-date">{issueDate}</span>

7 </header>
8 );
9}

Notice that HeaderBar knows nothing about stories or article cards. It is an isolated branch of the tree. If ArticleGrid updates or re-renders, HeaderBar remains completely unaffected in structure.

Step 3
Then, we declare the content grid branch
<ArticleGrid.jsx>

Next, we construct src/components/ArticleGrid.jsx and its terminal child StoryCard.jsx. ArticleGrid forms the second major branch, receiving the stories array and mapping each story to a StoryCard:

src/components/ArticleGrid.jsx
1import StoryCard from './StoryCard.jsx';
2export default function ArticleGrid({ stories }) {
3 return <main className="content-grid">
4 <h2 className="grid-heading">Top Dispatches</h2>
5 {stories.map((story) => (
6 <StoryCard key={story.id} story={story} />
Branches downward to TERMINAL CARDS
7 ))}
8 </main>;
9}

Now we create src/components/StoryCard.jsx. This component acts as the terminal UI control (leaf node) of the content branch:

src/components/StoryCard.jsx
1export default function StoryCard({ story }) {
2 return (
3 <article className="dispatch-card">
4 <span className="dispatch-category">{story.category}</span>
5 <h3 className="dispatch-title">{story.title}</h3>

6 </article>
7 );
8}

Notice the structural hierarchy: NewsLayout → ArticleGrid → StoryCard. Props flow strictly downward from parent to child to grandchild. If the parent unmounts ArticleGrid, React automatically prunes all StoryCard instances from the render tree.

Step 4
Finally, we mount the layout tree inside
<App.jsx>

Finally, we complete our application in src/App.jsx. We define the newsroom edition metadata and stories array, and mount the root of the tree:

src/App.jsx
1import NewsLayout from './components/NewsLayout.jsx';
2const EDITION = { masthead: 'The National Times', issueDate: 'Sep 22, 2026' };
3const STORIES = [
4 { id: 'disp-1', title: 'Diplomatic Accord Finalized', category: 'World' },
5 { id: 'disp-2', title: 'Tech Stocks Rebound in Asia', category: 'Markets' },
6];
7export default function App() {
8 return <NewsLayout edition={EDITION} stories={STORIES} />;
Mounts TREE TRUNK
9}

Look at the complete tree structure: App serves as the root container, mounting NewsLayout as the trunk, which branches into HeaderBar and ArticleGrid, with ArticleGrid terminating at StoryCard elements. Every component has a precise, deterministic address within the tree.

Component Summary

NewsLayoutedition={...} stories={...}

The layout orchestrator acts as the trunk of the feature tree. It receives top-level edition data and stories and branches them cleanly into HeaderBar and ArticleGrid. Notice it renders zero article cards directly. Why? To maintain structural separation between top-level layout coordination and branch-specific presentation.

HeaderBaredition={edition}

The navigation branch encapsulates the newspaper masthead and publication date. It consumes the edition prop from the layout trunk. Notice it knows nothing about the article collection. This guarantees that navigation styling and logic remain completely decoupled from content updates.

ArticleGridstories={stories}

The content branch manages the collection of dispatches. It receives stories from the layout and maps each record into a StoryCard. When does React unmount this branch? Whenever NewsLayout removes the grid, React automatically prunes all child cards from the live render tree.

In our experiment, we replaced the illusion of flat files with a disciplined tree architecture. By establishing NewsLayout as the trunk branching into HeaderBar and ArticleGrid, we demonstrated how props flow deterministically downward, how branches isolate concerns, and how React's render tree manages component lifecycles.

Where you will meet this

  1. Application Shell Layouts: Organizing top-level navigation, sidebar drawers, and main content areas into distinct branches that re-render independently.
  2. Modal Dialog Portals: Understanding that even when a modal renders into a different physical DOM container via portals, it remains an integral child in the React component tree for event bubbling.
  3. Bundle Optimization: Auditing the module dependency tree to identify heavy charting or animation libraries and moving them into dynamic import boundaries.
  4. Subtree Pruning & Tab Navigation: Recognizing that switching tabs unmounts the inactive tab's branch from the render tree, discarding its internal DOM and state unless hoisted.

Glossary

  • UI Tree: The hierarchical model React uses to represent component relationships, top-down prop distribution, and render lifecycles.
  • Module Dependency Tree: The static tree of JavaScript files and import statements evaluated at build time by bundlers like Vite and Rollup.
  • Component Tree: The logical hierarchy of components defined by parent-child JSX nesting in your source code.
  • Render Tree: The live runtime hierarchy of React element objects and DOM tags evaluated for the currently rendered frame.
  • Tree Pruning: The automatic cleanup process where React unmounts and destroys all child and grandchild DOM nodes when a parent branch is removed.

Summary

Architectural Takeaways & Decision Matrix

❒ Tree Architecture & Data Flow

➔ ALWAYS model your application as a hierarchical tree with clear parent, child, and sibling boundaries.

➔ ALWAYS pass data strictly downward from parent trunk to child branches via props.

➔ NEVER treat components as isolated flat files with random global dependencies.

❒ Bundling & Lifecycle Scoping

➔ ALWAYS audit your module dependency tree to keep heavy third-party imports confined to the branches that actually use them.

➔ IF a parent component unmounts THEN expect all child and grandchild state on that branch to be destroyed (tree pruning).

➔ IF state must survive branch unmounting THEN lift the state to an ancestor above the unmounting branch.
