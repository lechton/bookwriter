### The Identical Clones and the Mutation Trap

- [p] ◇ In plain HTML, tags take attributes like `src` or `href` to customize their behavior. When building reusable React components, hardcoding static text inside a function produces identical clones. If an editorial page renders three `<ArticleCard />` elements with hardcoded text, every card displays the exact same headline and author. To make components reusable across different stories, you must pass dynamic data into them from their parent. ◼ Educational objective: establish why components require dynamic input data to prevent identical clones.
- [p] ★ {preknowledge: JSX attributes, function parameters, object mutation} {bridging: developers assume props work like ordinary mutable JavaScript objects, but React strictly enforces immutability} When developers attempt to modify props inside a child component, JavaScript throws an unhandled runtime exception. Look at the naive attempt: ◼ Educational objective: demonstrate runtime failure caused by mutating the frozen props object.
- [code] Naive Prop Mutation:
```jsx title="Naive Prop Mutation"
export default function ArticleCard(props) {
  props.title = props.title.toUpperCase(); // **WRONG:** mutating frozen props object throws **TYPEERROR**
  return (
    <article className="card">
      <h2>{props.title}</h2>
    </article>
  );
}
```
◼ **The what-this-introduces list:** 1. `props`: incoming parameter object containing passed attributes. 2. `props.title = ...`: illegal direct property mutation. 3. `TypeError`: fatal runtime exception thrown by strict mode.
- [p] ★ {preknowledge: Object.freeze, pure functions, unidirectional data flow} {bridging: React freezes the props object in development, ensuring components remain pure functions of their inputs} In development mode, React invokes `Object.freeze()` on the `props` object before passing it into your component function. Attempting to assign `props.title = ...` in strict mode triggers `TypeError: Cannot assign to read only property 'title' of object '#<Object>'`. But why does React freeze props? Because React relies on **unidirectional data flow**. Data flows strictly downward from parent to child. If a child could mutate its own props, it would silently alter data shared with sibling components or cache layers, destroying deterministic rendering and breaking React's ability to know when components need updating. ◼ Educational objective: deconstruct Object.freeze and the architectural necessity of unidirectional data flow.
- [figure] ```html-figure src="figures/08-00-props-unidirectional-flow.html" caption="Unidirectional data flow: parent passes read-only props downward, and React's immutability shield prevents child mutations."```
- [grounding] [!WILD] **Why does React freeze props in development but not in production?** When developers see Object.freeze in development, they wonder why production builds omit the freeze. Is mutating props legal in production? No! Mutating props in production is still a catastrophic anti-pattern that causes desynchronized state and ghost renders. React skips Object.freeze in production purely for raw execution performance: deeply freezing thousands of prop objects on every render pass would slow down rendering on low-powered mobile devices. The development freeze is an automated safety net to catch mutation bugs before your code reaches production.
- [callout] > [!TIP]
> **To impress the interviewer:** When asked why a component cannot change its own props, explain that props are **read-only input snapshots** governed by unidirectional data flow. Mutating props violates component purity, breaks memoization and reconciliation assumptions, and corrupts shared state across siblings. Mention that React freezes props in development with Object.freeze to enforce this contract.

### Unidirectional Data Flow and Parameter Destructuring

- [p] ◇ Component props bridge the gap between static templates and dynamic, reusable building blocks. Props represent the inputs passed from a parent component downward into a child component. In React, data flows in a single direction: from top to bottom. ◼ Educational objective: define props and unidirectional data flow in component hierarchies.
- [p] ★ {preknowledge: JSX attribute syntax, function arguments, JavaScript object destructuring} {bridging: developers must learn the two sides of the props contract: passing attributes in JSX and receiving them in function parameters} Working with props involves two synchronized sides: ◼ Educational objective: categorize the two sides of the props contract.
- [p] 1. **Passing Props**: The parent declares custom attributes on the JSX tag: `<ArticleCard title="Crisis" author="Elena" />`. ◼ Educational objective: explain passing props in JSX.
- [p] 2. **Receiving Props**: The child receives all attributes combined into a single `props` object as its first function argument: `function ArticleCard(props)`. ◼ Educational objective: explain receiving props in component signatures.
- [p] ★ {preknowledge: object property access, ES6 parameter destructuring} {bridging: developers face an architectural crossroad between reading props via object dot notation or unpacking them via parameter destructuring} When receiving props inside the child component, you face an architectural crossroad between two syntax patterns: ◼ Educational objective: frame the pedagogical crossroad between props dot notation and parameter destructuring.
- [p] - **Option 1 (The foundational way)**: Accept `props` as a single parameter and access fields using dot notation (`props.title`). ◼ Educational objective: declare Option 1 with concrete syntax tokens.
- [p] - **Option 2 (The modern idiomatic way)**: Unpack fields directly in the function signature using parameter destructuring (`{ title, author }`). ◼ Educational objective: declare Option 2 with concrete syntax tokens.
- [p] First, look at Option 1 using dot notation: ◼ Educational objective: transition to Option 1 code.
- [code] Option 1:
```jsx title="Option 1: The Foundational Way (props.property)"
export default function ArticleCard(props) {
  return (
    <article className="card">
      <h2>{props.title}</h2> // Reads property from **PROPS** object
      <p>{props.author}</p>  // Repetitive object access in **JSX**
    </article>
  );
}
```
◼ **The what-this-introduces list:** 1. `props`: single object parameter. 2. `props.title`: dot notation access. 3. `props.author`: repeated object property lookup.
- [p] ★ In Option 1, the code receives `props` as a whole object. While this makes it immediately obvious where values come from, repeating `props.` across every variable clutters markup and obscures which specific props the component actually requires. ◼ Educational objective: analyze the verbosity of dot notation in JSX.
- [p] Next, look at Option 2 using parameter destructuring: ◼ Educational objective: transition to Option 2 code.
- [code] Option 2:
```jsx title="Option 2: The Modern Idiomatic Way ({ title, author })"
export default function ArticleCard({ title, author }) {
  return (
    <article className="card">
      <h2>{title}</h2>   // Unpacked prop used directly in **EXPRESSION**
      <p>{author}</p>    // Clean identifier without **PREFIX**
    </article>
  );
}
```
◼ **The what-this-introduces list:** 1. `{ title, author }`: parameter destructuring extracting props immediately. 2. Clean local variables in component scope. 3. Explicit prop contract declared in function header.
- [p] ★ In Option 2, destructuring unpacks `title` and `author` directly in the function signature. This serves as self-documenting code: any developer reading the function header instantly sees the exact props the component accepts. ◼ Educational objective: explain why parameter destructuring is the industry standard pattern for props.
- [callout] > [!KEY]
> Treat props as immutable inputs. Pass props from parent to child via JSX attributes, and unpack them in the child signature using parameter destructuring (`{ prop1, prop2 }`). Never mutate `props` directly.

### Glossary

- [glossary] Props ◼ The read-only inputs passed from a parent component downward to a child component via JSX attributes.
- [glossary] Unidirectional Data Flow ◼ The architectural rule in React where data flows strictly in one direction from parent to child.
- [glossary] Parameter Destructuring ◼ The JavaScript syntax (`{ title, author }`) that unpacks properties from the props object directly in the function signature.
- [glossary] Object.freeze ◼ The JavaScript runtime method React calls in development on the props object to prevent accidental property mutations.
- [glossary] Immutability Contract ◼ The non-negotiable rule that components must never alter their inputs, ensuring deterministic rendering.

## Beyond the basics

- **Props freezing in development vs production**: React freezes `props` with `Object.freeze()` in development to catch illegal mutations, but omits it in production for raw execution speed (see [react.dev/learn/passing-props-to-a-component](https://react.dev/learn/passing-props-to-a-component)).
- **Default prop values via destructuring**: You can assign fallback values during destructuring via `{ author = 'Staff Reporter' }`, which apply when the prop is `undefined` (see [react.dev/learn/passing-props-to-a-component#specifying-a-default-value-for-a-prop](https://react.dev/learn/passing-props-to-a-component#specifying-a-default-value-for-a-prop)).
- **JSX spread syntax for forwarding props**: Passing multiple props can be streamlined using the spread operator `<ArticleCard {...storyProps} />`, though explicit props are preferred for clarity (see [react.dev/learn/passing-props-to-a-component#forwarding-props-with-the-jsx-spread-syntax](https://react.dev/learn/passing-props-to-a-component#forwarding-props-with-the-jsx-spread-syntax)).
- **Props as function arguments**: JSX compiles `<ArticleCard title="News" />` directly to `_jsx(ArticleCard, { title: "News" })`, proving that props are simply the second argument to the element factory (see [react.dev/learn/passing-props-to-a-component](https://react.dev/learn/passing-props-to-a-component)).
- **Pure components and deterministic rendering**: A component that never mutates props behaves as a pure function: given the same props, it always renders the exact same output (see [react.dev/learn/keeping-components-pure](https://react.dev/learn/keeping-components-pure)).

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Downward Data Flow & Reusability

➔ ALWAYS pass data downward from parent to child via custom JSX attributes (`<Card title={title} />`).

➔ NEVER hardcode static text inside reusable components when multiple instances require distinct content.

➔ IF a component needs to adapt its display THEN pass configuration props rather than duplicating the component file.

❒ Immutability & Destructuring

➔ ALWAYS unpack props in the component function signature using parameter destructuring (`{ title, author }`).

➔ NEVER mutate `props` directly (`props.title = '...'`) because React freezes props to protect unidirectional data flow.

➔ IF you need to transform a prop value THEN compute a new local variable instead of reassigning the prop.

**DO THIS:** unpack props via destructuring and compute derived values

```jsx right
export default function ArticleCard({ title, category }) {
  const badge = category.toUpperCase();
  return <h2>{title} ({badge})</h2>;
}
```

**DO NOT DO THIS:** mutate props or reassign incoming parameters

```jsx wrong
export default function ArticleCard(props) {
  props.category = props.category.toUpperCase();
  return <h2>{props.title} ({props.category})</h2>;
}
```

| | **PROPS (DOWNWARD DATA)**<br>(read-only input) | **INTERNAL MUTATION**<br>(anti-pattern) |
| ---: | :--- | :--- |
| **Data Ownership** | Owned by the parent component | Attempted modification by child |
| **Immutability Status** | Frozen via `Object.freeze` in development | Throws `TypeError` in strict mode |
| **Data Direction** | Strictly downward (parent → child) | Violates unidirectional data flow |
| **Component Purity** | Preserves pure functional rendering | Corrupts shared data and sibling caches |
| **Idiomatic Syntax** | Unpacked via `{ prop1, prop2 }` destructuring | Forbidden direct property assignment |
