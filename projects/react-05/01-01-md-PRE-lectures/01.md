### Manual DOM Hunting and State Drift

- [p] ◇ In plain browser JavaScript, you build dynamic pages by manipulating the Document Object Model, commonly known as the **DOM**. The DOM is the browser's internal tree of live C++ objects that represents every HTML element painted on the screen. To change a word on the page, your script must locate the exact node using methods like `document.getElementById` or `document.querySelector`. Once the element is found, you manually overwrite its properties, such as setting `textContent` or `innerHTML`. ◼ Educational objective: establish the native baseline of imperative web development before introducing React's abstraction.
- [p] ★ {preknowledge: browser DOM nodes, getElementById queries, string properties like textContent} {bridging: manual DOM queries work for small scripts, but fail as the number of elements grows because developers must remember every element by hand} In a large application like The National Times, a single piece of information, such as the authenticated reader's name, appears in multiple places across the interface. Look at the naive imperative update function: ◼ Educational objective: demonstrate how imperative scripting requires manual element hunting and leads directly to state drift.
- [code] Naive DOM Update:
```js title="Naive DOM Update"
function updateHeaderUser(name) {
  const greeting = document.getElementById('header-greeting');
  greeting.textContent = 'Welcome, ' + name; // Updates header **GREETING**
  const profile = document.getElementById('nav-profile-name');
  profile.textContent = name;                // Updates navigation **PROFILE**
}
```
◼ **The what-this-introduces list:** 1. `updateHeaderUser`: an imperative script function. 2. `getElementById`: native browser API searching the physical DOM tree. 3. `textContent`: direct property assignment overwriting text on an existing node. 4. The missed selector: the silent failure where `#subscriber-badge` is omitted.
- [p] ★ {preknowledge: manual DOM mutations, DOM query omissions} {bridging: omitting an element causes parts of the UI to show old data while other parts show new data} When `updateHeaderUser` executes, the greeting and profile pill display Elena, but the subscriber badge remains unchanged. This condition is called **state drift**. State drift occurs when two pieces of the user interface that should reflect the exact same data fall out of synchronization. In imperative programming, you are responsible for both *what* to change and *how* to find and update every affected DOM node. As your application adds features, remembering every selector becomes impossible. ◼ Educational objective: formally define state drift and analyze why manual DOM updates are fragile.
- [figure] ```html-figure src="figures/01-00-manual-vs-declarative.html" caption="Imperative DOM queries fail as the interface grows: missing a single query creates state drift across the header."```
- [p] ★ {preknowledge: container elements, innerHTML assignment} {bridging: developers try to avoid missing elements by replacing entire HTML containers with innerHTML, but this wipes out browser state} To avoid hunting individual DOM nodes, developers often attempt to replace an entire section at once using `innerHTML`. While this guarantees all text is replaced, it creates severe side effects. Look at the innerHTML replacement attempt: ◼ Educational objective: expose the hidden cost of destructive innerHTML replacement.
- [code] Destructive innerHTML:
```js title="Destructive Replacement"
function replaceHeader(name) {
  const root = document.getElementById('header-root');
  const markup = `<header><h1>National Times</h1><p>${name}</p></header>`;
  root.innerHTML = markup; // **WRONG:** wipes container, losing input **FOCUS**
}
```
◼ **The what-this-introduces list:** 1. `container.innerHTML`: native browser property that parses HTML strings and replaces children. 2. Template literal `${name}`: string interpolation. 3. DOM node destruction: tearing down existing C++ objects and rebuilding them from scratch.
- [grounding] [!WILD] **Why does innerHTML destroy your active input focus?** When you assign a new string to `innerHTML`, the browser parser does not compare text. It destroys every existing DOM node inside that container and constructs brand-new C++ nodes in memory. If a reader is typing inside a search box when `innerHTML` runs, that `<input>` element is deleted from existence. The browser re-creates a new input that looks identical, but the active cursor focus is lost. Text selection disappears, and running CSS transitions abruptly reset to their initial frames. React avoids this by comparing changes in memory and surgically updating only the text nodes that changed.
- [callout] > [!TIP]
> **To impress the interviewer:** When asked why React was created, do not merely say "it makes building websites faster." Explain that React solves the fundamental problem of **state drift** inherent in imperative programming. In vanilla JavaScript, the developer must manually keep the DOM in sync with data across dozens of queries. React replaces this manual choreography with a declarative model. The user interface becomes a pure projection of application data: `UI = f(data)`.

### Components as Reusable Blueprints

- [p] ◇ To permanently eliminate manual DOM hunting and state drift, modern web development relies on a paradigm called **declarative UI**. In a declarative system, you do not write step-by-step instructions telling the browser how to locate, create, or mutate DOM elements. Instead, you declare what the user interface should look like for a given set of data. React takes on the mechanical burden of computing the differences and physically updating the browser DOM. ◼ Educational objective: define declarative programming and contrast it against imperative DOM mutation.
- [p] ◇ The fundamental building block of a React application is a **component**. A component is a self-contained, reusable JavaScript function that accepts inputs called **props** and returns a description of markup. React components are organized into hierarchical trees. In React, every component function name must begin with a capital letter. **Capitalization** is a strict compiler rule: it tells React that `<SiteHeader />` is a custom user component, whereas `<header>` is a native browser DOM element. Lowercase tags instruct React to produce built-in HTML elements, while capitalized tags instruct React to execute your custom function. ◼ Educational objective: define components, props, and the capitalization rule distinguishing custom components from native DOM tags.
- [p] ★ {preknowledge: JavaScript functions, function arguments, HTML element attributes} {bridging: developers often wonder how a component receives its incoming data, leading to a foundational crossroads between the full props object and parameter destructuring} When React executes a component function, it passes all attributes declared on the JSX tag inside a single JavaScript object called **props** (short for properties). To read this incoming data, you have two options: ◼ Educational objective: introduce the props mechanism across both educational dimensions.
- [p] - **Option 1 (The foundational way)**: Receive the full `props` object as an argument, then access variables with dot notation (`props.readerName`). ◼ Educational objective: declare Option 1 with concrete syntax tokens.
- [p] - **Option 2 (The modern idiomatic way)**: Unpack variables directly in the parameter list using JavaScript object destructuring (`{ readerName }`). ◼ Educational objective: declare Option 2 with concrete syntax tokens.
- [p] First, look at Option 1 using the explicit props object: ◼ Educational objective: transition to Option 1 code.
- [code] Option 1:
```jsx title="Option 1: The Foundational Way (props.readerName)"
export default function ReaderGreeting(props) { // Receives props **OBJECT**
  return <div className="greeting">Welcome back, {props.readerName}</div>;
}
```
◼ **The what-this-introduces list:** 1. `props`: the single argument object supplied by React. 2. `props.readerName`: dot notation accessing the specific property. 3. `{}` evaluation window: stepping out of static markup into live JavaScript expression execution.
- [p] ★ In Option 1, React calls the function with the complete props object. This reveals the raw mechanical truth of how React operates: attributes on JSX tags become key-value pairs on an object. However, repeating `props.` across larger components creates unnecessary visual noise. ◼ Educational objective: deconstruct the engine mechanics and maintenance trade-off of Option 1.
- [p] Next, look at Option 2 using parameter destructuring: ◼ Educational objective: transition to Option 2 code.
- [code] Option 2:
```jsx title="Option 2: The Modern Idiomatic Way ({ readerName })"
export default function ReaderGreeting({ readerName }) { // Unpacks **PROP**
  return <div className="greeting">Welcome back, {readerName}</div>;
}
```
◼ **The what-this-introduces list:** 1. `{ readerName }`: JavaScript object destructuring in the function signature. 2. `readerName`: local variable bound directly to the prop value. 3. Simplified evaluation window: `{readerName}` without object prefixes.
- [p] ★ In Option 2, the JavaScript engine unpacks `readerName` directly at the function parameter boundary. The component body remains concise, and the function signature clearly documents which props the component expects. This modern pattern is the standard across production React codebases. ◼ Educational objective: explain why modern teams standardize on parameter destructuring.
- [callout] > [!KEY]
> In React, the user interface is a pure reflection of data. You describe what the screen looks like for a given state, and React handles the physical DOM updates.

- [p] To eliminate state drift on The National Times, we will build a unified site header using four components assembled strictly top-down. ### Step 1: First, we construct the parent container <SiteHeader.jsx>

- [p] We begin by constructing the parent container `SiteHeader.jsx`. This component acts as the orchestrator of the site header. Inside this file, we declare our reader data once in a local constant `readerName = 'Elena Rostova'`. Notice that `SiteHeader.jsx` does not query any DOM elements. Instead, it renders JSX describing the header layout and passes `readerName` downward as an explicit prop to both child components: `<ReaderGreeting readerName={readerName} />` and `<SubscriberBadge readerName={readerName} tier="Premium" />`. ◼ Educational objective: demonstrate top-down data declaration and prop passing from a single source of truth.
- [code] SiteHeader.jsx:
```jsx title="SiteHeader.jsx"
import ReaderGreeting from './ReaderGreeting.jsx';
import SubscriberBadge from './SubscriberBadge.jsx';
export default function SiteHeader() {
  const readerName = 'Elena Rostova'; // Declares reader data **TRUTH**
  return (
    <header className="site-header">
      <ReaderGreeting readerName={readerName} /> // Passes name **PROP**
      <SubscriberBadge readerName={readerName} tier="Premium" />
    </header>);
}
```
◼ **The what-this-introduces list:** 1. `import ReaderGreeting`: importing child component. 2. `import SubscriberBadge`: importing second child component. 3. `const readerName`: the single source of data truth. 4. `readerName={readerName}`: passing prop downward. 5. `tier="Premium"`: passing static string prop. 6. `<header>`: native semantic HTML wrapper.
- [p] Notice what is physically absent from `SiteHeader.jsx`: there are zero `document.getElementById` calls, zero query selectors, and zero manual string concatenations. If the value of `readerName` changes, both child components receive the new prop simultaneously. Because both children derive their display from the exact same variable in the parent, state drift is mathematically impossible. ◼ Educational objective: underline the structural guarantee that prevents state drift.

### Step 2: Next, we build the child component <ReaderGreeting.jsx>

- [p] Now we build the first child component `ReaderGreeting.jsx`. This component has a single responsibility: display a personalized welcome greeting for the current subscriber. It declares a function parameter using object destructuring: `{ readerName }`. Inside its JSX markup, it renders a `<div>` element containing a `<span>`. It embeds the `readerName` variable directly inside the text using curly braces `{readerName}`. ◼ Educational objective: build the greeting child component and explain curly brace evaluation.
- [code] ReaderGreeting.jsx:
```jsx title="ReaderGreeting.jsx"
export default function ReaderGreeting({ readerName }) { // Unpacks **PROP**
  return (
    <div className="header-greeting">
      <span>Welcome back, {readerName}</span> // Evaluates in **JSX**
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `export default function ReaderGreeting`: exporting child component. 2. `{ readerName }`: destructuring expected prop. 3. `header-greeting`: CSS class name. 4. `{readerName}`: JSX evaluation window projecting variable into DOM text.
- [p] Inside `ReaderGreeting.jsx`, the curly braces around `{readerName}` act as an **evaluation window**. When the JavaScript engine reaches `{readerName}`, it evaluates the variable in memory and inserts its value into the rendered text. The component does not know where `readerName` came from. Nor does it care if other components display the same name. It simply takes its input prop and returns the corresponding markup description. ◼ Educational objective: explain the evaluation window and component isolation.

### Step 3: Then, we declare the child component <SubscriberBadge.jsx>

- [p] Next, we construct the second child component `SubscriberBadge.jsx`. In our plain JavaScript test, this widget fell victim to state drift. The script forgot to query its ID. In React, we define `SubscriberBadge` to accept two explicit props: `{ readerName, tier }`. It renders the subscriber's tier level alongside their name. ◼ Educational objective: build the second child component and contrast its reliability with the earlier manual failure.
- [code] SubscriberBadge.jsx:
```jsx title="SubscriberBadge.jsx"
export default function SubscriberBadge({ readerName, tier }) {
  return (
    <div className="subscriber-badge">
      <span className="tier-tag">{tier}</span>          // Shows tier **TAG**
      <span className="member-name">{readerName}</span> // Renders **NAME**
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `{ readerName, tier }`: destructuring multiple incoming props. 2. `tier-tag`: CSS class for subscriber tier. 3. `member-name`: CSS class for reader name. 4. Dual prop projection: rendering two dynamic variables in separate sibling spans.
- [p] What happens if `SubscriberBadge` manages its own reader lookup? If children query the DOM independently, timing differences cause desynchronized data. By requiring `SiteHeader` to pass `readerName` down to both children, we establish a **single source of truth**. Both widgets are guaranteed to display the exact same user identity on every render. ◼ Educational objective: apply the counterfactual circuit to justify centralized data passing.

### Step 4: Finally, we mount the feature inside <App.jsx>

- [p] Finally, we seal our feature by importing and mounting `SiteHeader` inside the top-level application component `App.jsx`. `App.jsx` acts as the root boundary of our application layout. It renders a containing `<div className="newsroom-layout">` and mounts `<SiteHeader />` at the top of the page. ◼ Educational objective: complete the top-down assembly by mounting the parent container inside the application shell.
- [code] App.jsx:
```jsx title="App.jsx"
import SiteHeader from './components/SiteHeader.jsx'; // Imports **ROOT**

export default function App() {
  return (
    <div className="newsroom-layout">
      <SiteHeader /> // Mounts at root **BOUNDARY**
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `import SiteHeader`: importing feature container. 2. `export default function App`: root application component. 3. `newsroom-layout`: outer application container. 4. `<SiteHeader />`: mounting custom component in JSX.
- [p] When React renders `<App />`, it does not touch the physical DOM immediately. First, it executes `App()`, which calls `SiteHeader()`, which in turn calls `ReaderGreeting()` and `SubscriberBadge()`. React constructs an in-memory tree of lightweight JavaScript objects representing the entire layout. This in-memory tree is called the **Virtual DOM**, or in official modern documentation, the **UI descriptor tree**. React then calculates the physical DOM operations required and mounts the nodes efficiently into the browser window. ◼ Educational objective: explain the complete mounting cycle and introduce Virtual DOM / UI descriptor tree terminology.

### Glossary

- [glossary] Declarative UI ◼ An architectural paradigm where code describes what the user interface should look like for a given state, leaving the runtime engine to compute and execute the necessary physical DOM mutations.
- [glossary] Component ◼ A self-contained, reusable JavaScript function that accepts input properties (props) and returns a tree of descriptors representing user interface markup.
- [glossary] Props ◼ A plain JavaScript dictionary of arguments passed downward from a parent component to a child component, configuring its behavior and appearance.
- [glossary] State Drift ◼ A synchronization bug where multiple UI elements that should reflect the exact same data display contradictory or outdated values due to missed imperative updates.
- [glossary] Virtual DOM / UI Descriptor Tree ◼ A lightweight in-memory tree of JavaScript objects representing the desired user interface structure, used by React to compute minimal physical DOM diffs.

## Beyond the basics

- **The UI descriptor tree and React elements**: When JSX executes, it produces plain, immutable JavaScript objects called React elements via `react/jsx-runtime`. React creates this UI tree from your components and uses it to compute minimal physical DOM mutations rather than traversing browser nodes directly (see [react.dev/learn/understanding-your-ui-as-a-tree](https://react.dev/learn/understanding-your-ui-as-a-tree)).
- **Purity in component rendering**: A React component function must be a pure calculation with respect to its inputs; given the same props, it must always return the same JSX without mutating preexisting variables or performing outside side effects during render (see [react.dev/learn/keeping-components-pure](https://react.dev/learn/keeping-components-pure)).
- **Module dependency trees vs render trees**: A React application possesses two distinct tree structures: the static module dependency tree evaluated by bundlers like Vite using `import` statements, and the dynamic runtime render tree constructed by React representing nested component instances on screen (see [react.dev/learn/understanding-your-ui-as-a-tree](https://react.dev/learn/understanding-your-ui-as-a-tree)).
- **Read-only immutable props**: Props received by a child component are strictly read-only snapshots in JavaScript memory; components must never reassign or mutate properties like `props.readerName` directly, requiring state setters or parent callbacks to request updates (see [react.dev/learn/passing-props-to-a-component](https://react.dev/learn/passing-props-to-a-component)).
- **Host elements vs custom component instances**: Lowercase JSX tags (`<header>`, `<span>`, `<div>`) map directly to native HTML host elements in the browser DOM, whereas capitalized tags (`<SiteHeader />`, `<ReaderGreeting />`) signal custom JavaScript functions that React invokes in memory (see [react.dev/learn/your-first-component](https://react.dev/learn/your-first-component)).
- **Fragments and single-root returns**: Every React component must return a single root JSX element because the markup compiles into a single JavaScript function call; when multiple adjacent sibling elements are needed without polluting the DOM with extra wrapper `<div>` nodes, developers wrap them in an empty fragment `<>...</>` (see [react.dev/learn/writing-markup-with-jsx](https://react.dev/learn/writing-markup-with-jsx)).

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Declarative Data Flow

➔ ALWAYS declare shared application data in a single parent container and pass it downward to children through explicit props.

➔ NEVER query or mutate the physical DOM directly with methods like `document.getElementById` or `container.innerHTML` inside React applications.

➔ IF multiple components display the same data THEN derive their output from a single source of truth to permanently prevent state drift.

❒ Component Naming & Syntax

➔ ALWAYS capitalize component function names (`SiteHeader`) so React can distinguish custom components from native HTML elements (`<header>`).

➔ ALWAYS use parameter destructuring (`{ readerName }`) in component signatures to explicitly document required props and eliminate repetitive `props.` prefixes.

**DO THIS:** derive all UI output declaratively from incoming props

```jsx right
export default function ReaderGreeting({ readerName }) {
  return <span>Welcome back, {readerName}</span>;
}
```

**DO NOT DO THIS:** hunt and mutate physical DOM nodes manually

```jsx wrong
export default function ReaderGreeting() {
  document.getElementById('greeting').textContent = 'Welcome back, Elena';
  return <span id="greeting" />;
}
```
