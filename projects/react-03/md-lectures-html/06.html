The Handshake Between React and the Browser DOM

When you build an application in React, your project begins with components like App.jsx. You write functions that return JSX describing headers, navigation bars, and article lists. However, a React component by itself is simply a JavaScript blueprint. It has no magical connection to the browser document, and it does not attach itself to the webpage on its own.

React is fundamentally a user interface library, not an invasive framework that takes over the entire browser window automatically. In traditional full-page frameworks, the framework boots on load and claims the entire document body. In contrast, React is designed to be as surgical as you need it to be. It requires an explicit handshake: you must designate an exact HTML element in your page, hand that container to React, and instruct React to manage the user interface strictly inside that boundary.

This handshake takes place across two files in your project root. In index.html, you define a host container: <div id="root"></div>. In your entry script /src/main.jsx, you import the mounting API from React and build the bridge between your declarative components and the physical DOM. This bridge is the createRoot container (known classically as the React Root / Mounting Point and in modern documentation as the createRoot Container / Root Renderer). In physical browser memory, it is a JavaScript controller object that holds references to both the physical DOM node and React's internal fiber tree.

⚡ IN THE WILD

Why does React need an entry bridge? In traditional web frameworks, the system boots automatically and controls the entire document. But React does not assume control of your page. You must hand it a specific HTML container. You tell React: here is your boundary, manage everything inside this container, and leave the rest of the webpage alone. This is the beauty of the entry bridge: you give React an explicit root container, granting it full control over that single DOM boundary without touching external scripts. Calling createRoot sets that boundary cleanly.

The Two-Step Mounting Protocol: Creation and Rendering

Connecting your root component to the physical browser DOM requires a two-step protocol: creating the root controller, and then rendering the component tree.

First, you query the browser document to locate the target HTML division: const domNode = document.getElementById('root') You pass this element to createRoot(domNode). This factory function creates a React root controller object. At this exact moment, React claims exclusive ownership of the container element. It initializes its internal scheduling engine, allocates its memory structures, and prepares to handle concurrent updates.

Second, you call root.render(<App />). This method accepts a React element (typically your top-level <App /> component). The first time root.render executes, React performs the initial mount: it clears any existing HTML markup sitting inside the container division, evaluates App and all its nested children, constructs the in-memory UI descriptor tree, and creates the physical browser DOM elements to paint the screen.

What does createRoot actually return? It returns a root controller object equipped with two primary methods:

  1. root.render(reactNode): mounts or updates a component tree inside the designated DOM container.
  2. root.unmount(): tears down the active React tree, destroys child components, unregisters event listeners, and completely empties the container division.

The entry script imports createRoot specifically from react-dom/client. React intentionally separates its platform-agnostic component model (react) from its browser DOM rendering engine (react-dom). Furthermore, client-side browser mounting lives strictly under the /client subpath, ensuring web applications load only the code required for browser DOM management.

Below the imports, root creation is cleanly decoupled from component rendering. Passing the queried DOM node to createRoot initializes the root controller once in memory. When the application needs to re-render the root with updated data or destroy it during route transitions, you call methods directly on the persistent root instance without repeating DOM queries.

Why React 18 Replaced ReactDOM.render

In older React tutorials and legacy codebases, you will frequently encounter a different mounting syntax: ReactDOM.render(<App />, document.getElementById('root')) This single-function pattern was the standard mounting API for nearly a decade, from early React versions through React 17.

In React 18, the core team deprecated ReactDOM.render and introduced createRoot. Understanding why this architectural change occurred is a frequent senior interview topic.

The legacy ReactDOM.render API was designed around a synchronous, blocking rendering model. It coupled container lookup with immediate tree execution in a single call. Because it executed synchronously, it could not pause rendering to handle urgent user input, nor could it coordinate updates across asynchronous boundaries.

The modern createRoot API was created to unlock concurrent features in React 18 and React 19. By separating root creation from tree rendering, createRoot initializes a modern fiber runtime that enables automatic batching by default. In legacy React, state updates were only batched together if they occurred inside native React event handlers; updates inside setTimeout, promises, or fetch callbacks each triggered separate re-renders. Under createRoot, React automatically batches all state updates regardless of where they originate, cutting re-renders and improving frame rates.

Furthermore, createRoot provides clean teardown ergonomics via root.unmount(). In modern micro-frontend platforms and multi-page hybrid apps, you frequently need to mount an interactive component on a page and destroy it when the user navigates away. Calling root.unmount() guarantees that all component cleanup effects run, timers stop, and event listeners detach, preventing memory leaks.

⚡ IN THE WILD

Why did React change how apps start? In older React versions, you passed your component and container into a single function. But that older method could not support modern performance features. It could not pause rendering or batch state updates across asynchronous timers. React 18 replaced it with createRoot. By separating container creation from rendering, React sets up a modern engine capable of prioritizing urgent updates. This is why createRoot replaced legacy mounting: it unlocks automatic batching and smooth concurrent features across your entire application.

Moving from legacy ReactDOM.render to createRoot decoupled root container initialization from rendering. This architectural shift enabled React's concurrent scheduler to activate automatic batching across async boundaries (promises, timeouts) and provided explicit lifecycle management via root.unmount().

Glossary

  • createRoot: The React 18+ client API that creates a root container to manage rendering inside a browser DOM element.
  • React Root: A controller object returned by createRoot that manages the lifecycle, rendering, and unmounting of a component tree.
  • Mounting: The initial process where React evaluates component blueprints and inserts physical DOM nodes into the browser document.
  • Automatic Batching: The performance optimization where React groups multiple state updates together into a single re-render cycle, enabled by default in createRoot.
  • root.unmount(): The method on a React root controller that tears down the component tree, cancels event listeners, and empties the container element.

Mounting the Root: The createRoot Bridge to the DOM

In daily production, understanding how createRoot connects your components to the browser document ensures that your application boots reliably with modern performance optimizations. While component blueprints describe visual layout in memory, the root controller establishes the physical bridge to the browser DOM. Here is your streetwise review.

❒ Root Controller Initialization and DOM Mounting
  1. Initialize the root controller once on the designated container element before rendering.
        (a) Query the target host element from index.html and pass it to createRoot from react-dom/client.
        (b) Invoke root.render() with your top-level component blueprint to initiate the recursive mounting process.
  2. Leverage modern concurrent features and clean lifecycle teardown.
        (a) Modern createRoot enables automatic batching across all promises, timeouts, and event callbacks.
        (b) Use root.unmount() to safely destroy component trees in micro-frontends and prevent memory leaks.

➔ NEVER use the legacy ReactDOM.render API in modern React applications.

➔ ALWAYS import createRoot from react-dom/client for client-side mounting.

➔ IF embedding independent interactive components THEN create separate roots for each container division.
