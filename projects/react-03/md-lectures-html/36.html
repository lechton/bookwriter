What is a Custom Hook: Sharing Logic, Not State

As applications grow, you often find multiple components that need the exact same stateful behavior. For example:

  • Checking whether the user is online or offline.
  • Listening to window resize dimensions.
  • Synchronizing a state variable with localStorage.
  • Tracking whether an element is hovering or focused.

In standard JavaScript, when two functions share logic, you extract that logic into a helper function. However, regular JavaScript functions cannot call React hooks like useState or useEffect.

To solve this, React allows you to build custom hooks. A custom hook is simply a JavaScript function whose name starts with use and that can call other React hooks internally.

Crucially, custom hooks share stateful logic, not state itself. Each time a component calls a custom hook, React allocates brand-new, completely independent state slots in that component's fiber node. Two components calling the same hook do not share data; they share the code that manages the data.

⚡ IN THE WILD

Do custom hooks share state between components? Imagine a blueprint for building an efficient brick fireplace. Two homeowners living on opposite sides of town hire a builder to build fireplaces using that exact same blueprint. Each house gets a working fireplace with an identical chimney and flue damper. When homeowner Alice lights a crackling fire in her living room, does smoke pour out of homeowner Bob's chimney across town? Of course not! They share the blueprint, but each house has its own physical fireplace and its own wood burning inside. That is a custom hook. The custom hook is the architectural blueprint. It defines how state and effects operate. When Component A and Component B both call useOnlineStatus(), each component builds its own private fireplace. They share the stateful logic, but their state instances are completely independent. Understanding custom hooks as an architectural blueprint clarifies why hooks share logic without sharing state.

The "use" Naming Convention and the Rules of Hooks

React enforces a mandatory naming convention for custom hooks: the function name must start with use followed by a capital letter (for example, useOnlineStatus, useWindowWidth, useLocalStorage).

This convention is not merely stylistic; it is an explicit signal to React's compiler and linter tools:

  1. Enforcing the Rules of Hooks: When the linter sees a function starting with use, it verifies that the function only calls hooks at the top level, never inside conditional branches, loops, or nested callbacks.
  2. Exhaustive dependency validation: The linter inspects dependency arrays inside your custom hook, catching missing reactive values before they turn into production bugs.
  3. Fiber tracking: React ensures that calls to custom hooks map cleanly to the component's internal hook linked list during render.

If you extract hook logic into a function named getOnlineStatus or checkConnectivity, the linter will disable its safety checks, leaving your application vulnerable to mysterious hook order corruption bugs.

⚡ IN THE WILD

Why must custom hooks begin with "use"? Imagine a municipal airport where air traffic controllers communicate with airplanes. Every commercial flight must use the official callsign prefix "Flight" before its number, such as "Flight 404." When the controller hears "Flight," the automated radar system immediately enforces strict flight separation rules and monitors fuel levels. If a pilot transmits without the prefix, the automated safety sensors fail to identify the aircraft, and automated collision warnings are disabled! That is why custom hooks must start with "use." React's compiler and linter scan function names for the "use" prefix. When React sees "use," it enables the Rules of Hooks: ensuring the hook is not called inside if statements or loops, verifying dependency arrays, and tracking hook slot indices in the fiber. Naming a hook getOnlineStatus turns off the compiler's safety radar, leading to mysterious runtime fiber corruption. Understanding the "use" prefix as an air traffic callsign clarifies why the naming convention enforces the Rules of Hooks.

Designing Clean Return Interfaces for Custom Hooks

When authoring custom hooks, consider how consumers will consume your return values:

  1. Single primitive value: When your hook tracks a single concept (like isOnline or windowWidth), return the primitive directly (return isOnline;).
  2. Tuple array ([value, setValue]): When your hook provides a value and an update function (like useState), return a 2-element tuple so consumers can name variables freely (const [text, setText] = useLocalStorage('draft', '');).
  3. Structured object ({ data, loading, error, refetch }): When your hook exposes multiple properties or helper actions, return an object so consumers can destructure only the properties they need and ignore the rest.

Where you will meet this

  • Device and browser capabilities: useMediaQuery, useWindowSize, useGeolocation, and useOrientation.
  • Asynchronous data abstractions: useFetch, usePolling, and useWebSocket.
  • Local browser persistence: useLocalStorage and useSessionStorage.
  • User interaction modifiers: useDebounce, useThrottle, useHover, and useClickOutside.
  • Complex form controllers: useForm managing validation, dirty tracking, and submission states.

Glossary

  • Custom Hook: A JavaScript function whose name starts with "use" that can call other React hooks to share stateful logic.
  • Stateful Logic Reuse: Extracting and sharing the mechanisms of state and effect management without duplicating code.
  • Independent State Instance: The guarantee that each invocation of a custom hook maintains its own isolated state variables in the fiber.
  • "use" Prefix Convention: The required React naming pattern allowing compiler tools to enforce the Rules of Hooks.
  • Reactive Return Interface: The primitive, tuple, or object returned by a custom hook to expose reactive values to consumers.
  • Hook Composition: The practice of combining multiple basic hooks (useState, useEffect, useRef) inside a custom hook to build higher-level abstractions.

Summary

Custom Hooks: Reusing Stateful Logic

Custom hooks extract stateful logic into reusable functions prefixed with use. They share stateful behavior and lifecycles without sharing state instances, allowing components to consume complex browser APIs declaratively in a single line.

❒ Core Takeaways of Custom Hook Architecture
  1. Share stateful logic, not state variables.
        (a) Each component calling a custom hook gets isolated state.
        (b) Custom hooks provide the blueprint, while components provide the state instances.
  2. Adhere strictly to the "use" prefix.
        (a) Always name custom hooks with use followed by a capital letter.
        (b) The prefix activates compiler and linter enforcement of the Rules of Hooks.
  3. Design clear return interfaces.
        (a) Return single values, tuples, or objects based on consumer ergonomic needs.
        (b) Encapsulate low-level event listeners and cleanup functions entirely inside the hook. ➔ ALWAYS prefix custom hooks with use to ensure React enforces the Rules of Hooks.
    ➔ NEVER assume calling the same custom hook in two components shares a single state variable between them.
