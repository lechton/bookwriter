Lecture 22: Choosing State Structure: Derived State versus Redundant State

Interview Question

CORE

How do you decide which values belong in state and which are derived?

Imagine this scenario:

  1. A developer named Liam builds an article search desk for The National Times.
  2. Liam stores the story list, search text, and result count in three separate state cells.
  3. When Liam types a query, the counter reports three results while the list shows five.
  4. Why does the result counter disagree with the articles displayed on the screen?
  5. Desynchronized counters confuse readers, display ghost results, and introduce subtle state duplication bugs.
  6. State setters schedule updates independently, leaving duplicated values out of sync across renders.
  7. Today you learn how to structure state, eliminate redundant variables, and derive values cleanly.

The Five Core Principles of State Architecture

When structuring state in React, the central engineering objective is to make state updates resilient and impossible to desynchronize. Inexperienced engineers often treat state as a passive storage bin, creating a new useState hook for every value displayed on the screen. This habit creates state redundancy, where multiple pieces of data in memory represent different views of the exact same underlying information.

To prevent bugs and race conditions, modern React architecture relies on five foundational principles:

  • Group related state: If two state variables always change together in response to the same event, unify them into a single state object.
  • Avoid contradictions in state: When multiple state booleans can disagree, such as isSending and isSent both evaluating to true, replace them with a single status string enum.
  • Avoid redundant state: If a value can be computed directly from component props or existing state variables during rendering, never store that value in state.
  • Avoid duplication in state: When the same data is duplicated across multiple state variables or mirrored from props, keeping them in sync becomes error-prone and brittle.
  • Avoid deeply nested state: Deeply hierarchical state objects require complex immutable copying logic; prefer flat, normalized state structures.

⚡ IN THE WILD

Why does duplicate state drift out of sync? Imagine an editorial room with two physical chalkboards on the wall. The first chalkboard lists the raw breaking news dispatches. The second chalkboard lists the stories matching today's search keyword. When a new dispatch arrives by telegraph, the junior assistant writes the story onto the first chalkboard, but forgets to walk over and update the second chalkboard. The two boards now disagree. That is what happens when you store filtered results in a separate state variable. You now have two sources of truth in memory. When raw state changes, you must remember to manually update the duplicate state variable every single time. If you miss one handler or an update runs out of order, the two boards drift apart. You do not need two chalkboards. You only need one master chalkboard, and you read it through magnifying glasses when looking for keywords. Understanding redundant state as chalkboard duplication clarifies why render-time calculation guarantees state synchronization.

Identifying and Eliminating Redundant State

To determine whether a piece of data belongs in React state, apply the three-question state audit to every variable in your component:

  1. Does this value remain unchanged over time? If so, it is not state; declare it as a module constant or a plain variable outside the component.
  2. Is this value passed into the component from a parent via props? If so, it is not state; use the prop directly.
  3. Can you compute this value from existing props or state variables? If the answer is yes, it is derived state and must never be stored in a useState hook.

React executes your component function from top to bottom on every single render pass. Any plain JavaScript variable declared inside the component body recalculates synchronously in memory:

During that re-render, JavaScript recalculates filteredStories and resultCount instantly before producing the new JSX descriptor tree. There is no second render cycle, no delayed state queue, and no chance of showing stale numbers.

The Prop-Mirroring Anti-Pattern and Cache Synchronization

Another frequent architectural mistake is prop mirroring, where a developer copies a prop directly into a local state variable:

Prop Mirroring Trap
1function StoryEditor({ initialTitle }) {
2 const [title, setTitle] = useState(initialTitle);
WRONG: ignores future prop changes from PARENT
3}

When you pass initialTitle to useState, React only reads that value on the initial mount. If the parent component later re-renders with a different initialTitle, the child component's title state variable will completely ignore the new prop and retain its old value. The local state variable acts as an accidental, stale cache.

Only mirror props into state when you explicitly intend for the child to fork the data into an independent, editable draft that deliberately ignores parent changes. In that scenario, rename the prop to initialTitle or defaultTitle to clearly communicate that incoming updates will not propagate.

Interview Tip

To impress the interviewer: When asked how to handle expensive calculations during render, explain the exact performance threshold for useMemo. Computing simple array filters, mappings, or sums over a few thousand items takes less than one millisecond in modern JavaScript engines. Adding useMemo incurs memory overhead and dependency array comparisons. Only wrap derived calculations in useMemo when profiling reveals measurable frame drops, or when the derived object reference is passed to an effect or memoized child component.

Where you will meet this

  • Newsroom article search: Filtering hundreds of breaking editorial dispatches by reporter name or topic tag without state desync.
  • E-commerce checkout totals: Calculating order subtotal, delivery fees, taxes, and item count from a single cart array during render.
  • Form validation indicators: Computing whether a submit button should be enabled without maintaining a separate isFormValid boolean.
  • Paginated data tables: Deriving current page slice, total page count, and active row index from raw server records and page state.
  • Filtered contact directories: Deriving active, archived, and flagged contact subsets from a single master contacts array.

Glossary

  • Derived State: Values computed dynamically from existing state or props during the component render phase without being stored in React memory cells.
  • Redundant State: Information stored in a state variable that could have been calculated directly from existing state or props during render, introducing the risk of state drift.
  • Single Source of Truth: The architectural practice of storing each piece of data in exactly one authoritative location in memory, deriving all secondary representations from it.
  • State Normalization: Structuring state data to be flat and free of duplicated records, mimicking relational database schemas to simplify updates.
  • Prop Mirroring: The anti-pattern of copying a prop into a local useState variable, causing the local state to ignore future prop updates from the parent.

Summary

State Structure Optimization: Derived Render Computations vs Redundant State Variables

Eliminating redundant state variables is the single most effective way to eliminate UI synchronization bugs in React applications. By auditing your state and keeping only raw, minimal inputs in memory, you guarantee that all derived UI representations remain synchronized automatically.

❒ The Core Takeaways of State Structure
  1. Never store in state what you can compute during render.
        (a) Formatted strings, filtered lists, and numeric aggregations belong in plain variables inside the component body.
        (b) Render-time computations execute synchronously on every render pass, eliminating asynchronous update lag.
  2. Establish a single source of truth for every piece of data.
        (a) When data exists in two state cells, one will eventually fail to update, causing visual contradictions.
        (b) Keep raw records in state; compute filtered and transformed views on the fly.
  3. Beware the prop-mirroring trap.
        (a) Initializing state with a prop freezes the value at mount time and ignores subsequent parent updates.
        (b) Only mirror props when intentionally forking an independent draft, and prefix the prop name with initial or default. ➔ ALWAYS derive lists and counts during the render pass instead of synchronizing multiple useState hooks.
    ➔ NEVER copy incoming props into local state unless intentionally creating an isolated, unlinked draft.

DO NOT DO THIS: Store redundant filtered lists and counters in separate state cells.
