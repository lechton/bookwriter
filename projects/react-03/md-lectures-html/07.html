The Thousand-Line Monolith: Why We Split Components

When you begin building a feature in React, keeping multiple components inside a single file feels quick and frictionless. You write your main parent component, and right beneath it in the same file, you add a navigation bar, a story card, and a footer. In small prototypes, this colocation seems harmless.

However, as an application expands into production, a single file holding multiple components quickly grows into a monolithic component file exceeding one thousand lines of code. Navigating such files becomes exhausting: developers spend more time scrolling through lines than writing features. More severely, when multiple engineers collaborate on the same repository, editing different components inside the same file triggers frequent git merge conflicts and unreadable diffs.

React solves this by adopting standard ES modules (known classically as Module Splitting / Component Files and in modern documentation as ES Module Component Imports). In physical project architecture, every component lives in its own file on disk. Splitting code into dedicated modules establishes clear visual boundaries, enables isolated unit testing, and allows modern build tools to perform dead-code elimination.

To maintain clean project ergonomics, the React community follows the one-component-per-file convention: each file typically exports one primary component whose name matches the filename on disk. For example, Navbar.jsx exports Navbar, and BrandLogo.jsx exports BrandLogo.

⚡ IN THE WILD

Why should components have separate files? In the beginning, keeping every component inside App.jsx seems fast. You write a header, a card, a sidebar, and a footer. But soon your file is a thousand lines long. You scroll endlessly trying to find one small function. When two teammates edit the file, git merge conflicts explode. This is the pain of the monolithic component file: it hides your components in a wall of code. Splitting each component into its own modular file creates clean boundaries, isolated tests, and instant readability. Giving each component its own file isolates changes and keeps your codebase healthy.

Default Exports: The Single Primary Component

JavaScript ES modules provide two mechanisms for sharing code across files: default exports and named exports. Understanding the operational difference between these two patterns is critical for writing clean imports.

A default export designates the single primary value exported by a module. You declare a default export by adding export default before your component function: export default function Navbar() { ... } Because a JavaScript file can have at most one default export, the exporting module makes a clear statement: this component is the main export of this file.

When consuming a default export in another file, you write an import statement without curly braces: import Navbar from './Navbar.jsx'

Because there is only one default export in the source file, you do not need curly braces to specify which member to import. Technically, JavaScript allows you to assign any local identifier to a default import (for example, writing import Nav from './Navbar.jsx'). However, in professional React development, you should always name the local import to match the exported component and file name exactly to preserve code searchability.

Named Exports: Multiple Utilities and Sub-Components

In contrast to default exports, a file can have as many named exports as needed. You declare a named export by adding the export keyword directly before any function, constant, or sub-component: export function NavLinks() { ... }

When consuming named exports in another file, you must wrap the imported identifiers in curly braces: import { NavLinks } from './NavLinks.jsx'

The curly braces signal that you are selecting specific members out of the module's export catalog. The name inside the curly braces must match the exported function name exactly. If you need to rename a named export to avoid naming collisions in the importing file, you must use the explicit as keyword: import { NavLinks as SectionLinks } from './NavLinks.jsx'

Key Takeaway

Default imports require no braces and represent the primary component; named imports require braces and pick specific members.

Mixing up these two syntax patterns is the exact reason Maya's application crashed. When a file uses export default Navbar importing it with curly braces as import { Navbar } from './Navbar.jsx' causes the browser to look for a named export called Navbar. Finding none, JavaScript assigns undefined to the variable. When React attempts to render <undefined />, the application crashes with a fatal runtime error: Element type is invalid: expected a string or a class/function but got: undefined

⚡ IN THE WILD

Why do named imports need curly braces? You import a component and suddenly your build crashes with an undefined error. Did you forget the curly braces, or did you add them by accident? Here is the secret: curly braces mean you are plucking a specific named item out of a collection. If a file exports several things, you use curly braces to select the exact name you need. But if a file has a default export, there is only one main item, so no curly braces are needed. This is the rule of named imports: curly braces pick a specific name from the file's export catalog. Knowing this distinction prevents undefined import crashes permanently.

Interview Tip

To impress the interviewer: When asked to contrast default and named exports, explain the refactoring trade-offs. While default exports are conventional for primary route components, named exports enforce strict identifier matching across large teams. If you rename a named export, TypeScript and IDE refactoring tools automatically update all consumer imports, whereas default exports can be imported under arbitrary names, increasing the risk of naming drift across files.

Where you will meet this

  • Design system component libraries: importing atomic controls such as Button, Input, and Modal using named exports from a central UI package.
  • Multi-page application routing: importing primary page components such as ArticlePage inside routing configuration files.
  • SVG icon collections: importing individual vector icons by name from icon packages such as SearchIcon and BellIcon.
  • Formatting utility modules: importing helper functions alongside components such as formatDate and truncateText from utility toolkits.

Glossary

  • ES Modules: The standard JavaScript module system using import and export statements to share code across independent files.
  • Default Export: A module export syntax (export default) allowing a file to designate one primary value that can be imported without curly braces.
  • Named Export: A module export syntax (export function) allowing a file to export multiple values that must be imported using matching names inside curly braces.
  • Barrel Export: The pattern of re-exporting multiple modular components from a central index.js file to simplify consumer import paths.
  • Export Catalog: The collection of named functions, objects, and types exported by a JavaScript module for external consumer selection.

Summary

Modular Component Architecture: Default versus Named Imports

In daily production, mastering ES module imports and exports ensures that your component codebase remains modular, maintainable, and free from runtime crashes. While default exports provide a clean interface for single primary components, named exports allow flexible sharing of multiple sub-components and utilities. Here is your streetwise review.

❒ Module Isolation and Export Contracts
  1. Designate a single primary component per file using default exports and import without curly braces.
        (a) A module can have at most one default export, establishing a clear primary export contract.
        (b) Match the imported identifier to the filename to maintain code searchability across the codebase.
  2. Export multiple sub-components or utilities using named exports and import with matching curly braces.
        (a) Named exports require consumer imports to wrap identifiers in curly braces matching the exact exported name.
        (b) Use the as keyword when importing named exports to resolve local naming collisions cleanly.

➔ NEVER use curly braces when importing a default export.

➔ ALWAYS match the exact exported identifier when importing named exports unless using as.

➔ IF a file exports a single primary component THEN designate it as the default export.
