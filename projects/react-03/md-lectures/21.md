### Imperative versus Declarative: The Passenger versus the Destination

In traditional web development without React, you implement user interactions imperatively. When an event occurs, your JavaScript code inspects the DOM and issues explicit, turn-by-turn commands to individual nodes: disable this button, hide that paragraph, toggle a CSS class on that container, and insert text into a spinner. In this classic paradigm (known classically as **Imperative DOM Scripting**), the programmer is responsible for orchestrating every DOM mutation manually.

As applications expand, imperative manipulation collapses under exponential complexity. A simple form with five visual states and three interactive elements requires dozens of conditional branches to ensure elements do not get stranded in contradictory states. If a single event handler forgets to hide a progress indicator or reset a disabled flag, the interface becomes corrupted.

React fundamentally departs from this approach through **Declarative UI / Finite State Machine** programming. In React, you never manipulate DOM nodes directly. You do not tell the browser *how* to change each element; you declare *what* the component should look like for each distinct state. The user interface is treated as a pure mathematical projection of state: $UI = f(state)$. React's reconciliation engine calculates the differences between the current and previous virtual representations, updating the real DOM with minimal operations.

> [!WILD]
> **Why does manual DOM scripting cause state drift?** Imagine sitting in a taxi and giving the driver rapid turn-by-turn commands: "Turn left here, accelerate, avoid that pothole, turn right at the red mailbox." If you forget one turn or issue commands out of order, you end up stranded in an alley. That is imperative DOM programming: you command every element individually, and if you forget to hide a spinner, it remains stuck on screen forever. Declarative programming is giving the driver your final destination: "Take me to Central Station." The driver navigates the roads while you relax. In React, your component states the final destination: "When status is submitting, show a spinner; when status is success, show a checkmark." React takes care of the driving. Understanding **declarative programming** as **destination declaration** clarifies why **state machines** prevent **visual desynchronization**.

### The Five-Step State Design Framework

To design components declaratively, React developers follow a structured five-step engineering framework:

1. **Identify visual states**: Before touching keyboard handlers or network APIs, enumerate every possible visual state the user can encounter. For a quiz poll, these states are: `'empty'` (input blank, submit disabled), `'typing'` (input has text, submit enabled), `'submitting'` (spinner shown, inputs disabled), `'success'` (thank-you message displayed), and `'error'` (error banner visible, input editable).
2. **Determine state triggers**: Map out what triggers transitions between these visual states. Triggers fall into two categories: human inputs (typing into a field, clicking submit) and computer events (network request resolving, response timing out).
3. **Represent state with useState**: Structure the component's state in memory. Always favor a single **status enum** (`const [status, setStatus] = useState('empty')`) over multiple disconnected booleans.
4. **Eliminate impossible states**: By representing mutual exclusions with a single status string, you make invalid states unrepresentable. You cannot accidentally have `isLoading === true` and `isSuccess === true` simultaneously when status can only be `'submitting'` or `'success'`.
5. **Connect event handlers**: Attach event listeners to update state variables, allowing React to trigger state transitions and re-render the view automatically.

> [!WILD]
> **Why are impossible states so dangerous in production?** Imagine an intersection where the traffic light has three separate switches: green, yellow, and red. If a faulty connection shorts out, the light can shine green and red simultaneously, causing a catastrophe. That is what happens when you use three independent booleans: isLoading, isSuccess, and isError. If a network retry fails to clear isLoading before setting isError, both evaluate to true, rendering a loading spinner inside a red error alert! By replacing three booleans with a single status enum that holds only 'submitting', 'success', or 'error', impossible states become physically impossible. The light can only shine one color at a time. Understanding **impossible states** versus a **status enum** prevents **boolean explosion** through a clean **state machine**.

To construct this declarative voting workflow cleanly, we decompose `PollStatusCard.jsx` and `QuizPoll.jsx` across five sequential implementation steps:

### Step 1: Status Card Presentation Layer

First, inspect the presentation card component, `PollStatusCard.jsx`:

```jsx title="PollStatusCard.jsx" startLine="1"
export default function PollStatusCard({ status, errorMessage }) {
  if (status === 'submitting') {
    return <p className="status-submitting">Submitting your response...</p>;
  }
  if (status === 'error') {
    return <p className="status-error">Error: {errorMessage}</p>;
  }
  if (status === 'success') {
    return <p className="status-success">Thank you for voting!</p>;
  }
  return null; // Renders nothing when in empty or typing **STATES**
}
```

In `PollStatusCard.jsx`, the presentation layer is purely declarative. It receives `status` and `errorMessage` as props, rendering the appropriate visual branch without touching DOM styles.

### Step 2: Setting Up the Form and Status State

We open the parent component `QuizPoll.jsx` and define the minimal state using an explicit status enum:

```jsx title="QuizPoll.jsx" startLine="1" continues="bottom"
import { useState } from 'react';
import PollStatusCard from './PollStatusCard.jsx';

export default function QuizPoll() {
  const [answer, setAnswer] = useState('');
  const [status, setStatus] = useState('empty'); // 'empty' | 'typing' | 'submitting' | 'success' | 'error'
  const [error, setError] = useState(null);
```

Using a single `status` string union eliminates impossible intermediate states like `isLoading && isError` being simultaneously true. State represents what the user can do next. Continuing inside the component, we handle typing changes:

### Step 3: Declarative Keystroke Handling

Next, we handle keystroke changes by transitioning between input states:

```jsx startLine="10" continues="both"
  function handleChange(e) {
    const nextText = e.target.value;
    setAnswer(nextText);
    setStatus(nextText.trim().length === 0 ? 'empty' : 'typing');
  }
```

When the user types, `handleChange` evaluates whether the trimmed text is empty. If characters exist, it flips to `'typing'`; if deleted, it returns to `'empty'`. With client input captured, we author the network submission routine:

### Step 4: Asynchronous Submission and State Transitions

Now we implement the submission routine that navigates network resolution:

```jsx startLine="17" continues="both"
  async function handleSubmit(e) {
    e.preventDefault();
    setStatus('submitting');
    try {
      await new Promise(res => setTimeout(res, 800)); // Simulated network request
      setStatus('success');
    } catch (err) {
      setError(err.message);
      setStatus('error');
    }
  }
```

Calling `setStatus('submitting')` triggers a re-render where the UI disables inputs immediately. Once the promise settles, state transitions definitively to either `'success'` or `'error'`. Moving to the visual output, we render the template:

### Step 5: Rendering the Form and Submit Button

Finally, we project the state machine into the JSX form markup and complete the parent form container:

```jsx startLine="29" continues="top"
  return (
    <form onSubmit={handleSubmit} className="poll-container">
      <PollStatusCard status={status} errorMessage={error} /> // Renders feedback card matching active **STATUS**
      {status !== 'success' && (
        <>
          <input value={answer} onChange={handleChange} disabled={status === 'submitting'} /> // Controlled input disabled during **TRANSITION**
          <button type="submit" disabled={status === 'empty' || status === 'submitting'}> // Submit button disabled until valid **ENTRY**
            Submit Vote
          </button>
        </>

  );
}
```

Inside `QuizPoll.jsx`, the form projects its interactive controls based purely on `status`. Buttons and inputs disable themselves automatically without imperative DOM queries.

### Deriving State: Why Fewer State Variables Mean Fewer Bugs

A common pitfall when transitioning to declarative programming is creating state variables for values that can easily be calculated. If a piece of data can be derived from existing props or state during rendering, never store it in state.

For instance, in `QuizPoll.jsx`, instead of creating a separate boolean `const [isEmpty, setIsEmpty] = useState(true)`, we derive it directly inline:

```jsx title="Derived State Pattern"
const isEmpty = answer.trim().length === 0; // Pure calculation during **RENDER**
```

Every redundant state variable increases the risk of state drift, where two variables tell conflicting stories about the current UI. Strive for the minimal amount of state necessary to represent what the user sees.

> [!KEY]
> Model UI as a finite state machine using explicit status enums, and derive everything else during render.

### Glossary

- **Declarative UI**: Programming model where you describe what the UI should look like for each state, leaving DOM updates to React.
- **Imperative UI**: Programming model where you manually command the computer with step-by-step instructions to alter individual DOM elements.
- **Finite State Machine**: A computational model that can exist in exactly one of a finite number of discrete states at any given moment.
- **Status Enum**: A string union representing mutually exclusive visual states (`'empty' | 'loading' | 'success' | 'error'`).
- **Derived State**: Values calculated directly from existing state or props during rendering without requiring their own `useState` storage.

❒ Declarative State, Status Enums, and Eliminating Impossible States

1. Treat the UI as a **pure projection of state**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Never query or mutate the DOM directly with `document.getElementById` or class manipulations.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Identify all visual states before writing logic: empty, typing, submitting, success, and error.

2. Consolidate modes with a **status enum**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Replace multiple independent booleans (`isLoading`, `isSuccess`) with a single string union (`'submitting' | 'success'`).<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Using a single status variable completely prevents impossible states where both a spinner and error banner display together.

3. Prune state by **deriving values during render**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) If a value can be computed from existing props or state, never store it in a separate `useState` call.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Fewer state variables mean fewer synchronization bugs and faster, more reliable component updates.

➔ NEVER manipulate DOM styles or attributes directly inside event handlers.

➔ ALWAYS model complex multi-step UI with an explicit status enum instead of multiple booleans.

➔ IF a value can be computed from existing state THEN **derive it inline during rendering**.

**DO THIS:** Model mutually exclusive states with a single status enum.

```jsx right title="QuizPoll.jsx"
const [status, setStatus] = useState('empty');

if (status === 'submitting') {
  return <Spinner />;
}
```

**DO NOT DO THIS:** Never toggle DOM node styles or classes imperatively.

```jsx wrong title="QuizPoll.jsx"

  document.getElementById('spinner').style.display = 'block';
  submitBtn.disabled = true;
}
```
