### What is a React Component?

In traditional web development, building an interface required juggling three separate technologies across different files. Developers wrote page structure in HTML, visual rules in CSS, and dynamic behavior in JavaScript. As web applications grew into rich interactive experiences, this separation created severe maintenance friction: changing a single button required opening three files and hoping the class names and DOM queries stayed synchronized.

React solves this fragmentation by uniting markup, design, and logic into cohesive, self-contained units called **components**. A **component** (known classically as a **React Component** and in modern documentation as a **Function Component**) is a regular JavaScript function that returns a user interface description written in JSX. Rather than writing an imperative sequence of browser commands, you author a function that defines what a piece of the screen should look like.

Under the hood, a component is not a heavy object-oriented class, nor is it a native browser Web Component. In computer memory, it is simply a **plain JavaScript function** that returns a lightweight object descriptor. When React renders your application, it invokes your component function, captures the returned **UI descriptor tree**, and coordinates with the browser engine to paint the real DOM nodes on the screen.

> [!WILD]
> **What is a React component under the hood?** You look at `<AuthorProfile />` on your screen and wonder what wizardry created it. Is it a complex browser extension or a heavy object class? In reality, it is nothing more than a plain JavaScript function. React executes that function and gets back a plain JavaScript object. It is a plain function returning a plain object, time and time again. This simplicity is the secret to React. Because every **component** is just a **plain JavaScript function**, React can run it, test it, and evaluate its **UI descriptor** in memory at lightning speed without touching the slow physical DOM until the exact moment of rendering.

### The Capitalization Law: Why Case Dictates DOM Identity

Because components are standard JavaScript functions, beginners often assume they can name them using standard camelCase conventions, such as `function authorProfile()`. However, React enforces an ironclad syntactic rule: **every component name must begin with a capital letter using PascalCase**.

This requirement exists because the JSX compiler needs a fast, unambiguous mechanism to differentiate between native HTML elements and custom user-defined components. When the compiler parses your JSX markup, it examines the first letter of each tag name. If the tag begins with a lowercase letter, such as `<header>`, `<p>`, or `<authorProfile />`, the compiler outputs a string literal: `_jsx('authorProfile', {})`. When React encounters a string tag name, it instructs the browser to create a native DOM node with that exact tag name.

When Leo named his component `authorProfile` with a lowercase `a`, the browser searched its internal HTML registry for a tag named `<authorprofile>`. Finding no standard element matching that name, the browser rendered an empty, inert custom HTML element. Leo's JavaScript function was never invoked, its internal JSX was never evaluated, and the author's name was completely omitted from the rendered page.

> [!KEY]
> In JSX, lowercase means a real browser tag; uppercase means a React component function.

If you capitalize the first letter and write `<AuthorProfile />`, the compiler behavior changes completely. Because the tag begins with an uppercase letter, the compiler treats `AuthorProfile` as a direct JavaScript identifier rather than a string: `_jsx(AuthorProfile, {})`. React receives the actual function reference and executes `AuthorProfile()` directly, evaluating its returned markup and mounting the author profile to the document.

To see this architectural contract in practice, examine how The National Times structures its article header. The parent container `ArticleHeader.jsx` imports and renders our presentation child component `AuthorProfile.jsx`:

```components title="national-times — Component Explorer"

  AuthorProfile.jsx | | profile | Written by **Elena Vance**;; Columnist, Metro Desk
```

The component explorer panel above demonstrates this structure. On the left, the file hierarchy shows `ArticleHeader.jsx` serving as the parent container, with `AuthorProfile.jsx` nested inside. On the right, the rendered canvas displays the completed output: "Written by Elena Vance" above her editorial role "Columnist, Metro Desk". The child component encapsulates the author's credentials into a reusable blueprint that can be embedded across any article template.

Here is the implementation of our child component, `AuthorProfile.jsx`:

```jsx title="AuthorProfile.jsx"
export default function AuthorProfile() {
  return (
    <div className="profile-box">
      <p className="profile-name">Written by Elena Vance</p> // Capitalized component returns author **NAME**
      <span className="profile-role">Columnist, Metro Desk</span> // Editorial role rendered in **SPAN**
    </div>
  );
}
```

The component function `AuthorProfile` begins with a capital `A`. Following **PascalCase** naming satisfies the compiler gate, allowing other files to import and render this function as a first-class component. Marking the declaration with `export default` establishes `AuthorProfile` as the primary export of the file, enabling parent components to bring it into scope cleanly.

Inside the return statement, `AuthorProfile` returns a `<div>` containing a `<p>` and a `<span>`. Because these tags are written entirely in lowercase, React translates them into standard browser DOM nodes (`HTMLDivElement`, `HTMLParagraphElement`, and `HTMLSpanElement`). The component packages both the structural layout and the static author text into a single reusable unit.

Now let us examine how the parent container, `ArticleHeader.jsx`, renders this child component:

```jsx title="ArticleHeader.jsx"
import AuthorProfile from './AuthorProfile.jsx';

export default function ArticleHeader() {
  return (
    <header className="article-header">
      <h1 className="story-title">Mayoral Election Special Report</h1> // Native lowercase h1 renders directly to **DOM**
      <div className="header-meta">
        <AuthorProfile /> // Capitalized tag invokes AuthorProfile component **FUNCTION**
      </div>
    </header>
  );
}
```

Notice the stark contrast between the tags rendered inside `ArticleHeader`. The `<header>`, `<h1>`, and `<div>` tags begin with lowercase letters, so React emits them directly as native browser elements. In contrast, `<AuthorProfile />` begins with an uppercase letter. React recognizes that `AuthorProfile` is a custom component, resolves the imported function identifier, and invokes `AuthorProfile()` to collect its rendered output.


> [!WILD]
> **Why does capitalization change how code runs?** In standard JavaScript, writing a lowercase function name works identically to an uppercase name. But in JSX, capitalization is an ironclad compiler law. If you type `<authorProfile />`, the compiler treats it as a built-in browser element. If you type `<AuthorProfile />`, the compiler treats it as your custom component function. This single capital letter decides whether React invokes your function or sends an unknown string to the browser. By enforcing **capitalization** through **PascalCase**, React separates native browser tags from your custom **component functions** cleanly.

### Return Rules: Parentheses and Automatic Semicolon Insertion

Every React component function must return something that React can render, such as JSX markup, a string, a number, or `null`. When returning JSX that spans multiple lines, you must follow an essential syntactic rule: **always wrap multi-line JSX markup in parentheses**.

To understand why parentheses are mandatory, you must understand how the JavaScript engine reads your code. JavaScript features a compiler mechanism called **Automatic Semicolon Insertion** (**ASI**). If you place a line break immediately after the `return` keyword without an opening parenthesis, JavaScript assumes you intended to write a standalone return statement and automatically inserts an invisible semicolon: `return;`.

When ASI triggers on an unparenthesized return statement, your component function terminates immediately after the return keyword, returning `undefined`. The JavaScript engine never reads the subsequent JSX markup. When React receives `undefined` from a component render, it throws a runtime crash: `Nothing was returned from render`. Wrapping the return statement in opening and closing parentheses `return (...)` prevents ASI by signaling to JavaScript that the expression continues across line breaks.

> [!WILD]
> **Why does returning on a newline fail?** You hit Enter after typing `return` to keep your code tidy and readable. On the next line, you start your JSX markup. You save the file, and your browser screen crashes with a blank error. Why? Because the JavaScript language inserts a hidden semicolon right after the word `return`. Your function ends immediately. It returns `undefined`, and your entire component is completely ignored. This is the silent trap of **Automatic Semicolon Insertion**: hitting Enter cuts off your **return statement** before it ever reaches your markup. Wrapping your code in **parentheses** keeps the statement open and safe.

### The Anti-Nesting Law: Never Define Components Inside Components

As your application grows, you will frequently assemble components out of smaller sub-components. However, there is a fundamental difference between **component composition** (rendering one component inside another) and **nested component definitions** (declaring the function body of a child component inside the function body of a parent component).

You must never define a component function inside another component function:

```jsx title="ArticleHeader.jsx"
export default function ArticleHeader() {
  function AuthorProfile() {
    return <p className="profile-name">Written by Elena Vance</p>; // **WRONG:** re-allocated on every parent **RENDER**
  }
  return (
    <header>
      <AuthorProfile />
    </header>
  );
}
```

The code above appears harmless to developers accustomed to nesting helper functions in plain JavaScript. In React, however, this pattern triggers severe performance degradation and catastrophic state bugs. Every time `ArticleHeader` renders, JavaScript allocates a brand new `AuthorProfile` function in memory with a completely new function reference.

When React reconciles the user interface, it compares the type of each component against the previous render. Because the nested `AuthorProfile` function has a fresh memory address on every render cycle, React assumes that the old component was deleted and a completely different component was inserted in its place. React destroys the entire existing DOM subtree, discards all internal state, wipes user form inputs, resets scroll positions, and mounts a brand new DOM element from scratch.

To preserve **component identity** across renders, always declare every component function at the top level of the file. When a child component requires data from its parent, pass that data downward through props rather than nesting function declarations.

> [!WILD]
> **When does nested code destroy your state?** You might think declaring a helper component inside your main component keeps your file organized. It looks harmless. But every time the parent component re-renders, the computer creates a brand new function in memory. React looks at that new function, assumes it is a completely new component type, and tears down the entire DOM tree. Any input you typed vanishes instantly. This is the danger of **nested component definitions**: you recreate the component blueprint on every render, resetting state over and over again. Declaring your component at the **top level** keeps **component identity** stable.

> [!TIP]
> **To impress the interviewer:** When asked why nesting component definitions is an anti-pattern, do not just say "it hurts performance." Frame your answer around component identity and DOM mounting. Explain that React identifies components by function reference. Defining a component inside another re-allocates that function on every parent render, destroying component identity, wiping child component state, and forcing the browser to recreate DOM nodes unnecessarily.

### Glossary

- **Component**: A self-contained, reusable JavaScript function that begins with a capital letter and returns a user interface description in JSX.
- **PascalCase**: The naming convention where the first letter of every word is capitalized, required for all React component function names.
- **Automatic Semicolon Insertion (ASI)**: The JavaScript parser mechanism that automatically inserts semicolons at line breaks, requiring parentheses around multi-line return statements.
- **Component Identity**: The persistent reference React uses to track a component across renders, preserved only when the component is declared at the top level.
- **UI Descriptor Tree**: An in-memory hierarchy of lightweight JavaScript objects generated by JSX that describes the intended DOM structure to React.

**DO THIS:** Declare component functions at the top level using PascalCase and wrap multi-line JSX in parentheses.

