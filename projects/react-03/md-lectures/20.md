### Standard HTML Inputs versus Synchronized State: Who Owns the Data?

In standard browser HTML, form elements like `<input>`, `<textarea>`, and `<select>` manage their own internal mutable state. When a reader types into an input field, the browser engine mutates the DOM node's `value` property directly. In this default DOM architecture, the DOM is the sole owner and source of truth for the field's data. React knows nothing about user typing until you manually query the DOM node through a ref or submit event.

React introduces an alternative architectural paradigm: the **Controlled Component / Single Source of Truth**. By passing the `value` prop to an `<input>`, you strip the DOM element of its state ownership and transfer total authority to React state.

When an input is controlled, React forces the DOM element to display whatever string is stored in React state. If state holds `"Port inquiry"`, the DOM input displays `"Port inquiry"`. If you attempt to type a new character without updating React state, React will overwrite the DOM node on the next render pass, resetting the field back to the current state string.

> [!WILD]
> **Why does typing freeze without an onChange handler?** Imagine a stenographer sitting in an editorial room. The chief editor gives the stenographer a sheet of paper that says "Headline typo". The editor orders: "Show only what is written on my master desk." A reporter walks up and whispers a new sentence into the stenographer's ear. The stenographer begins to pencil in the new words, but glances back at the editor's desk. Because the editor's master paper still says "Headline typo", the stenographer instantly erases the reporter's pencil marks and rewrites "Headline typo". That is what React does when you pass value without onChange. On every keystroke, the browser tries to insert a letter, but React immediately re-applies the unchanged state value back into the DOM element. The field is frozen in time. To allow typing, you must update the master state on every single stroke. Understanding **controlled state** as a **synchronization loop** clarifies why **onChange** is required for interactive **form fields**.

### The Two-Way Synchronization Loop: value and onChange

To make a controlled input interactive, you must establish a continuous two-way synchronization loop between the browser DOM and React state:

```jsx title="Synchronization Loop Pattern"
const [text, setText] = useState('');

<input
  type="text"
  value={text}
  onChange={e => setText(e.target.value)}
/>
```

During physical browser execution, every user keystroke executes a four-step choreography:

1. The reader types a character into the input field. The browser engine fires a native `input` event on the DOM node.
2. React intercepts this native event and synthesizes an `onChange` event, invoking your callback function.
3. Your callback reads `e.target.value` (the new string containing the typed character) and calls `setText(e.target.value)`.
4. React enqueues the state change, schedules a re-render, and passes the updated `text` back to the `<input value={text}>` prop. React reconciles the DOM, setting `element.value = text`.

Because this loop runs on every keystroke, React always possesses the latest user input. You can instantly validate the field, disable submit buttons, or format text in real time.

A frequent junior error is initializing state to `undefined` (`const [text, setText] = useState()`). When an `<input>` receives `value={undefined}`, React treats it as an uncontrolled input on initial render. If state later changes to a string, React suddenly treats it as controlled, throwing the warning: *"A component is changing an uncontrolled input to be controlled"*.

> [!WILD]
> **Why does an undefined initial state trigger a warning?** Imagine going through airport security. When you reach the agent, you declare: "I have no passport; I am traveling incognito." The agent classifies you as an unverified traveler. Five minutes later, halfway through inspection, you reach into your pocket, pull out a diplomat passport, and demand VIP entry. The security chief halts the line and sounds an alarm: "You cannot change identification categories mid-flight!" That is what happens when you initialize state with undefined and later pass a string to value. React classifies the input as uncontrolled on mount, but as controlled on the second render. Switching modes during a component's lifecycle is forbidden. Always declare your passport upfront by initializing state with an empty string. Understanding **uncontrolled mode** versus **controlled transition** ensures you always provide a valid **empty string** for **initial state**.

### Unifying Textareas, Selects, and Checkboxes

Standard HTML has notorious inconsistencies across form elements: `<textarea>` holds text between tags (`<textarea>my text</textarea>`), while `<select>` requires adding a `selected` attribute to specific `<option>` child elements.

React eliminates these inconsistencies by providing a **uniform form API**:

- Textareas: `<textarea value={text} onChange={e => setText(e.target.value)} />`. React ignores child text and drives `<textarea>` through the `value` prop.
- Dropdown selects: `<select value={selectedId} onChange={e => setSelectedId(e.target.value)}>`. React sets the active option by matching the `value` prop on `<select>` with the `value` attributes of `<option>` elements.
- Checkboxes and radios: `<input type="checkbox" checked={agreed} onChange={e => setAgreed(e.target.checked)} />`. Boolean controls use `checked` instead of `value` and read `e.target.checked` inside the change handler.

### The National Times Editorial Correction Architecture

To examine controlled inputs in production, inspect the article correction submission desk of The National Times. The parent component `CorrectionForm.jsx` renders `CorrectionField.jsx`:

```components title="national-times — Component Explorer"

  CorrectionField.jsx | value="Typo in paragraph two" | field | Correction: Typo in paragraph two
```

The component explorer panel above illustrates the architecture. On the left, `CorrectionForm.jsx` holds the correction state. On the right, the rendered view displays the current form field: "Correction: Typo in paragraph two".

Here is the implementation of our presentation input component, `CorrectionField.jsx`:

```jsx title="CorrectionField.jsx"
export default function CorrectionField({ label, value, onChange }) {
  return (
    <label className="field-group">
      <span className="field-label">{label}</span>
      <input
        type="text"
        value={value}
        onChange={e => onChange(e.target.value)} // Dispatches current input text to parent **COMPONENT**
      />
    </label>
  );
}
```

In `CorrectionField.jsx`, the component is completely stateless. It accepts `label`, `value`, and `onChange` as props, forwarding user edits directly to its parent component.

Now examine the parent component, `CorrectionForm.jsx`:

```jsx title="CorrectionForm.jsx"
import { useState } from 'react';
import CorrectionField from './CorrectionField.jsx';

export default function CorrectionForm() {
  const [correction, setCorrection] = useState(''); // Initialized to empty string

  function handleSubmit(e) {
    e.preventDefault();
    alert(`Submitted correction: ${correction}`); // Notifies user of processed **PAYLOAD**
  }

  return (
    <form onSubmit={handleSubmit} className="correction-form">
      <CorrectionField
        label="Article Correction"
        value={correction} // Drives field value from component **STATE**
        onChange={setCorrection} // Passes state setter to synchronize **INPUT**
      />
      <button type="submit">Submit Correction</button> // Triggers form submission **EVENT**
    </form>
  );
}
```

Inside `CorrectionForm.jsx`, `useState('')` guarantees that `correction` starts as an empty string rather than `undefined`, preventing the browser console from reporting an unmanaged-to-managed input transition warning. Passing `setCorrection` down to `CorrectionField` closes the two-way synchronization loop, ensuring that every keystroke updates state and re-renders the input with current data.

### When to Synchronize State versus Reading on Submit

Controlled components offer immense power, but they come with a performance trade-off: every single keystroke triggers a component re-render. Understanding when to synchronize inputs with state versus reading standard fields on submission is an essential architectural skill:

- Choose **Controlled Components** when you need:
  1. Real-time field validation (displaying errors while typing).
  2. Dynamic submit button disabling based on form validity.
  3. Enforcing specific text formatting (e.g. credit card number spacing, phone numbers).
  4. Conditionally displaying other fields based on the input's current content.

- Choose **Standard HTML Form Submission** (`defaultValue` + `FormData`) when:
  1. You have large, dense forms where re-rendering on every keystroke causes perceptible input latency.
  2. You only need form values upon submission and do not require live feedback.
  3. Integrating with third-party non-React libraries or native file uploads (`<input type="file" />`).

> [!KEY]
> Controlled inputs establish React as the single source of truth; always pair value with onChange and initialize with an empty string.

### Glossary

- **Controlled Component**: A form element whose value is driven by React state and updated via an explicit change callback.
- **Standard DOM Input**: A form element that maintains its own internal state within the browser DOM, queried upon submission using refs or FormData.
- **Single Source of Truth**: The architectural design where data exists in only one authoritative location, preventing synchronization drift.
- **Two-Way Synchronization**: The circular data loop where user keystrokes trigger state updates, and updated state drives the DOM element's value.
- **Uncontrolled-to-Controlled Warning**: A React console error triggered when an input is mounted with `undefined` or `null` and later receives a defined string.

In daily production, understanding **controlled components** ensures that form elements remain responsive, predictable, and tightly coupled to application state. By pairing `value` with `onChange`, you turn React into the single source of truth for all user input. Here is your streetwise review.

❒ Single Source of Truth, The Synchronization Loop, and Common Traps

1. Make React the **single source of truth**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Pass `value` to force the DOM input to reflect React state on every render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Always supply an `onChange` handler that updates state on every keystroke (`e.target.value`).

2. Avoid the **read-only freeze trap**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Passing `value` without `onChange` locks the input, preventing user typing.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) If you intend an input to be read-only, explicitly add the `readOnly` boolean attribute.

3. Prevent **mode-switching console warnings**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Never initialize input state to `undefined` or `null`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Always provide an initial empty string `''` to ensure controlled status throughout the component lifecycle.

➔ NEVER pass a `value` prop to an interactive input without an accompanying `onChange` handler.

➔ ALWAYS initialize text input state with an empty string `''` instead of `undefined`.

➔ IF creating checkboxes or radios THEN **use checked and read e.target.checked**.
