### The Mental Model Shift: Components Mount; Effects Synchronize

To master `useEffect`, you must abandon the mental model of class component lifecycles. In class components, code was organized around component events: `componentDidMount`, `componentDidUpdate`, and `componentWillUnmount`.

In modern React, components and Effects have completely separate lifecycles:

- **A component** mounts when it appears on the screen, updates when its props or state change, and unmounts when it leaves the screen.
- **An Effect**, by contrast, does not care about component lifecycles. An Effect has only two operations: it starts synchronizing, and later it stops synchronizing.

Whether synchronization starts because the component mounted or because a prop changed makes no difference. The Effect's job is simply to keep your component synchronized with whatever values are currently present in props and state.

> [!WILD]
> **Why should you stop thinking in component lifecycles?** Imagine a hotel room thermostat on a winter wall. When a guest walks into the room and sets the dial to 72 degrees, the thermostat starts the furnace to synchronize the room to 72 degrees. If two hours later the guest turns the dial to 75 degrees, does the thermostat tear down the hotel walls and build a brand new room? No! The thermostat simply stops synchronizing to 72 degrees and starts synchronizing to 75 degrees. The thermostat does not care about "the birth of the room" or "the death of the room." It cares only about synchronizing the temperature to whatever number is on the dial right now. That is useEffect. Stop thinking about when the component was born or updated. Think only about synchronizing your external connection to the current props and state. Understanding **component lifecycles** as **room construction** and **Effects** as a **temperature thermostat** clarifies why **Effects focus exclusively on starting and stopping synchronization**.

### The Chronological Re-synchronization Sequence

When a dependency changes, what is the exact sequence of events executed by React?

Consider an Effect that synchronizes a live document room:

```jsx
useEffect(() => {
  const connection = connectToRoom(roomId);
  connection.start();

  return () => {
    connection.stop();
  };
}, [roomId]);
```

When the user switches `roomId` from `'desk-general'` to `'desk-culture'`, React executes this sequence in strict order:

1. **Render phase**: React executes the component function with `roomId = 'desk-culture'`, computing the new JSX.
2. **Commit phase**: React updates the browser DOM with the new JSX markup.
3. **Preemptive teardown**: Before running the new effect, React runs the **cleanup function from the previous render**. This cleanup function still closes over the old value (`'desk-general'`), safely disconnecting the previous socket.
4. **Setup phase**: React runs the **setup function for the current render**. This setup function closes over the new value (`'desk-culture'`), establishing the new socket connection.
5. **Final unmount**: When the user eventually navigates away from the page, React runs the cleanup function for `'desk-culture'` one final time.

Notice step 3! Teardown **always precedes setup**. React clears the old connection before creating the new one, guaranteeing that two overlapping connections never exist simultaneously.

> [!WILD]
> **Why does cleanup run before the new setup?** Imagine a train conductor managing passenger tracks at a busy railway terminal. Train 101 from Chicago is parked on Track 4. Now, the station dispatcher announces that Train 202 from Boston needs Track 4. Does the conductor wave Train 202 onto the track while Train 101 is still parked there? If so, the two locomotives crash at full speed in a massive explosion! The conductor must first signal Train 101 to depart, clear the tracks completely, and only then wave Train 202 into the station. That is why React runs cleanup before re-setup. When dependencies change, React first clears the previous external connection before establishing the new one. If it ran setup first, both connections would exist simultaneously, causing catastrophic packet collisions. Understanding **cleanup** as **clearing the train track** clarifies why **teardown must always precede the next setup**.

First, inspect the mock collaboration client `collabServerClient.js`:

```js title="collabServerClient.js"
export function connectToRoom(roomId, serverUrl) {
  let timerId = null;

  return {
    start(onMessage) {
      console.log(`[SYS] Connected to ${roomId} on ${serverUrl}`);
      timerId = setInterval(() => {
        onMessage(`[SYNC] Pulse from ${roomId} at ${new Date().toLocaleTimeString()}`);
      }, 2500);
    },
    stop() {
      console.log(`[SYS] Disconnected from ${roomId}`);
      if (timerId) clearInterval(timerId);
    },
  };
}
```

Now examine the editor pane component `CollaborationEditorPane.jsx`:

```jsx title="CollaborationEditorPane.jsx"
import { useEffect, useState } from 'react';
import { connectToRoom } from './collabServerClient.js';

export default function CollaborationEditorPane({ roomId, serverUrl }) {
  const [pulse, setPulse] = useState('Connecting...');

  useEffect(() => {
    const connection = connectToRoom(roomId, serverUrl); // Setup phase connects to external room **HANDLE**
    connection.start(msg => setPulse(msg));

    return () => {
      connection.stop(); // Preemptive teardown terminates old socket before new **SETUP**
    };
  }, [roomId, serverUrl]); // Re-sync effect whenever either reactive dependency changes

  return (
    <div className="collab-pane">
      <h3>Desk Document: <strong>{roomId}</strong></h3>
      <p className="status-indicator">{pulse}</p>
    </div>
  );
}
```

Examine the dependencies array `[roomId, serverUrl]`:

1. Both `roomId` and `serverUrl` are props passed from the parent. Because they are read inside the effect, they are **reactive values**.
2. If `roomId` changes, React runs `connection.stop()` for the previous room, and then calls `connectToRoom` for the new room.
3. If `serverUrl` changes (such as failing over to a backup server), React stops the connection to the old server URL and reconnects to the new server URL.
4. Because all reactive values are listed in the dependency array, the effect is guaranteed to stay synchronized with the latest props.

Finally, examine the parent component `CollaborationRoomApp.jsx`:

```jsx title="CollaborationRoomApp.jsx"
import { useState } from 'react';
import CollaborationEditorPane from './CollaborationEditorPane.jsx';

export default function CollaborationRoomApp() {
  const [activeRoom, setActiveRoom] = useState('desk-general'); // Active editorial collaboration room **STATE**
  const [server, setServer] = useState('wss://primary'); // Selected WebSocket gateway endpoint **URL**

  return (
    <main className="collab-container">
      <select value={activeRoom} onChange={e => setActiveRoom(e.target.value)}>
        <option value="desk-general">General News Desk</option>
        <option value="desk-investigations">Investigative Bureau</option>
      </select>
      <button onClick={() => setServer(s => s === 'wss://primary' ? 'wss://backup' : 'wss://primary')}>
        Failover Server
      </button>
      <CollaborationEditorPane roomId={activeRoom} serverUrl={server} />
    </main>
  ); // Mounts editor pane, passing props that trigger synchronized effect **TEARDOWN**
}
```

In `CollaborationRoomApp`, changing the room or toggling the server URL triggers a re-render. React verifies that the editor pane cleanly tears down its previous connection before establishing the new one.

### The Stale Closure Trap and Reactive Dependencies

What happens if you read a reactive value inside `useEffect` but omit it from the dependency array?

```jsx title="Missing Dependency Anti-Pattern"
useEffect(() => {
  const connection = connectToRoom(roomId, serverUrl);
  connection.start(msg => setStatus(msg));
  return () => connection.stop();
}, [roomId]); // Omits reactive dependency serverUrl, causing stale **CLOSURE**
```

If the user clicks "Failover Server" and `serverUrl` changes from `primary` to `backup`, React checks `[roomId]`. Because `roomId` has not changed, React skips re-running the Effect!

The Effect remains trapped in a **stale closure**, continuing to communicate with the dead primary server using the initial `serverUrl` string it captured on mount.

The golden rule of effect dependencies is: **If a variable is declared inside the component (props, state, or derived variables) and read inside an Effect, it must be included in the dependency array.**

### Where you will meet this

- Collaborative document rooms: Switching between active document channels without leaking previous editor subscriptions.
- Audio and media streaming: Re-synchronizing audio buffers when changing bitrates or server hosts.

### Glossary

- **Reactive Effect Lifecycle**: The independent lifecycle of an Effect characterized by starting and stopping synchronization with external systems.
- **Synchronization Cycle**: The pairing of a setup function and its matching cleanup function executed when dependencies change.
- **Preemptive Teardown**: React's guarantee to execute the previous cleanup before starting the next setup function.
- **Stale Closure Trap**: A bug where an effect retains an outdated variable reference because the variable was omitted from dependencies.
- **Reactive Value**: Any prop, state, or variable derived from them declared inside the component function body.
- **Dependency Exhaustiveness**: The rule requiring every reactive value read inside an effect to be declared in its dependency array.

### Summary

**The Reactive Effect Lifecycle: Dependencies and Re-synchronization**

Effects do not follow component lifecycles; they follow an independent synchronization lifecycle. When reactive dependencies change, React executes preemptive teardown of the previous setup before initializing the new one, preventing connection collisions and stale closures.

❒ Core Takeaways of Reactive Effect Architecture
1. Abandon mount and update thinking.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Treat Effects as synchronization processes that start and stop.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Synchronization runs on mount and whenever dependencies change.
2. Rely on preemptive teardown.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) React executes the previous render's cleanup before executing the new setup.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Guarantees zero overlapping external connections at any point in time.
3. Obey exhaustive dependencies.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Include every prop and state variable used in the effect in the dependency array.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Omitting dependencies creates stale closures that ignore live data.
➔ ALWAYS include all reactive values read inside an effect in the dependency array.<br>
➔ NEVER assume cleanup only runs on unmount; cleanup runs before every re-synchronization.

**DO NOT DO THIS:** Omit reactive dependencies and assume cleanup only runs on unmount.
```jsx wrong title="BadEditor"
export function BadEditor({ roomId, serverUrl }) {
  useEffect(() => {
    const conn = connectToRoom(roomId, serverUrl);
    conn.start();
    return () => conn.stop();
  }, [roomId]);
}
```

**DO THIS:** Declare all reactive values in dependencies and embrace preemptive teardown.
```jsx right title="GoodEditor"
export function GoodEditor({ roomId, serverUrl }) {
  useEffect(() => {
    const conn = connectToRoom(roomId, serverUrl);
    conn.start();

    return () => {
      conn.stop();
    };
  }, [roomId, serverUrl]);
}
```
