### Why JSX Is Not HTML

When developers first encounter React, JSX appears identical to traditional HTML. You write opening and closing angle brackets, assign attributes, and nest tags inside one another. However, this visual resemblance is misleading. JSX is not HTML, nor is it a raw text template parsed by the browser.

JSX is a **syntax extension for JavaScript** (known classically as **JSX / React Elements** and in modern documentation as a **JSX Syntax Extension / UI Descriptors**). Under the hood, JSX provides a readable, declarative syntax that compilers like Vite, Babel, and SWC transform into standard JavaScript function calls. When you write `<p className="lead">Breaking News</p>`, the compiler transforms that markup into `_jsx('p', { className: 'lead', children: 'Breaking News' })`.

This transformation changes everything about how your code is evaluated. A web browser's HTML parser is intentionally permissive: if you forget to close an image tag or misplace an attribute, the browser forgives the error and renders whatever it can reconstruct. But JSX compiles directly into **JavaScript objects** and function arguments. JavaScript is a strict programming language that cannot tolerate missing commas, unclosed brackets, or invalid syntax. Because every JSX tag is a JavaScript function call in disguise, JSX enforces three strict syntax rules that every snippet must obey.

> [!WILD]
> **Why does valid HTML fail in JSX?** In plain HTML, browsers are extremely forgiving. If you forget to close an image tag or type a class attribute, the browser forgives you and renders the page anyway. But JSX is not HTML. JSX is JavaScript in disguise. Every tag you write turns into a real JavaScript function call. A JavaScript function cannot accept broken syntax. It cannot have missing brackets or unclosed arguments. This is why **JSX syntax** is so strict: it compiles directly to **JavaScript objects**, where every single token must be valid code. Conforming to **JSX syntax** guarantees that your declarative markup transforms into valid JavaScript without compiler crashes.

### Rule 1: The Single Root Rule and Fragment Architecture

The first universal rule of JSX is the **single root rule**: **a component return statement or JSX expression must return exactly one root element**. If you attempt to return two adjacent sibling elements side by side without an enclosing parent tag, the compiler throws an immediate syntax error.

To understand why this rule exists, look at the compiled JavaScript. When a function executes, JavaScript language grammar allows it to return exactly one value. Writing `return <p>...</p> <span>...</span>;` is equivalent to writing `return _jsx('p'), _jsx('span');`. In JavaScript, returning two separate objects from a single return statement is syntactically invalid. Every expression must resolve to a single value.

A common beginner reaction to this compiler constraint is wrapping everything in an extra `<div>`. While adding a wrapper div satisfies the compiler, it introduces a severe architectural defect known as **wrapper div bloat** (or "div soup"). Inserting unnecessary wrapper nodes pollutes the physical browser DOM, degrades accessibility tree navigation, and frequently breaks modern CSS layouts.

In CSS Grid and Flexbox, layout properties like `display: flex`, `gap: 12px`, and `grid-template-columns: repeat(2, 1fr)` apply strictly to the container's **direct children**. If you insert an unnecessary wrapper `<div>` between a grid parent and its child elements, the browser treats the wrapper div as a single grid column, squishing all inner elements into that one column and destroying your design. Furthermore, inside strict HTML structures like `<table>`, wrapping multiple `<td>` table cells inside a `<div>` violates the HTML specification, causing browsers to eject the div entirely.

To solve this problem cleanly, React provides the **Fragment** (`<>...</>` or `<React.Fragment>...</React.Fragment>`). A Fragment is a built-in React component that lets you group multiple sibling elements together without injecting any physical wrapper node into the browser DOM tree.

To see how Fragments prevent layout breakage on The National Times, examine our article summary card. The parent component `ArticleSummary.jsx` renders an article tag using `ArticleTag.jsx` alongside story metadata rendered by `StoryLead.jsx`:

```components title="national-times — Component Explorer"

  ArticleTag.jsx | | tag | Special Investigation
  StoryLead.jsx | | card | City council votes on zoning.;; 4 minute read
```

The component explorer panel above demonstrates this clean structure. On the left, `ArticleSummary.jsx` holds two child components. On the right, the rendered canvas displays the completed card: an urgent tag reading "Special Investigation", directly followed by the lead text "City council votes on zoning." and the reading time "4 minute read". Neither child introduces unwanted wrapper divs.

Let us inspect our first child component, `ArticleTag.jsx`:

```jsx title="ArticleTag.jsx"
export default function ArticleTag() {
  return (
    <span className="tag-urgent">Special Investigation</span> // Single span returns inline **TAG**
  );
}
```

The `ArticleTag` component returns a single `<span>` element, naturally satisfying the single root rule without requiring an extra container div. It exports a focused inline tag component ready for composition.

Now examine our second child component, `StoryLead.jsx`, which must return two distinct sibling elements:

```jsx title="StoryLead.jsx"
export default function StoryLead() {
  return (
    <>
      <p className="lead-text">City council votes on zoning.</p> // Fragment groups first sibling **ELEMENT**
      <span className="read-time">4 minute read</span> // Fragment groups second sibling **ELEMENT**
    </>
  );
}
```

Instead of wrapping the paragraph and span in an extra `<div>`, `StoryLead` encloses both siblings inside a **Fragment** (`<>...</>`). The JSX compiler recognizes the empty tags, groups both children into a single return expression, and attaches them directly to the parent layout without emitting an intermediate wrapper node into the DOM.

Now examine how the parent container, `ArticleSummary.jsx`, combines these components:

```jsx title="ArticleSummary.jsx"
import ArticleTag from './ArticleTag.jsx';
import StoryLead from './StoryLead.jsx';

export default function ArticleSummary() {
  return (
    <article className="summary-card">
      <ArticleTag /> // Renders article tag at top of **CARD**
      <StoryLead /> // Renders story lead without extra wrapper **NODES**
    </article>
  );
}
```

When React mounts `ArticleSummary`, it evaluates `StoryLead` and attaches its inner `<p>` and `<span>` elements directly to the parent `<article>`. The browser DOM tree contains zero intermediate wrapper nodes.


> [!WILD]
> **When do extra divs break your layout?** Imagine you configure a CSS grid with two equal columns. You place two elements inside a wrapper div to satisfy React's single root rule. Suddenly, your layout collapses. Why? Because CSS grid rules apply only to direct children. The browser sees your wrapper div as one single column instead of two independent items. This is the trap of **wrapper div bloat**: it inserts unwanted nodes into the **DOM tree**, breaking your grid and flexbox layouts. Using a **Fragment** (`<>...</>`) lets you return multiple sibling elements without rendering an extra node into the physical **DOM tree**, preserving your layout completely.

### Rule 2: Explicit Tag Closure

The second universal rule of JSX is **explicit tag closure**: **every single JSX tag must be closed explicitly**. In traditional HTML, elements known as "void tags" (such as `<img>`, `<input>`, `<br>`, and `<hr>`) never have closing tags. Writing `<img src="photo.jpg">` in standard HTML is completely valid.

In JSX, omitting the closing slash on any tag causes an immediate compiler crash. Void elements must be written as **self-closing tags** with a forward slash before the closing angle bracket: `<img src="photo.jpg" />`, `<input type="text" />`, and `<br />`. Wrapping tags that enclose children (such as `<p>` and `<li>`) must always include their corresponding closing tags (`</p>` and `</li>`).

This strictness is necessary because the JSX compiler processes your markup as an XML-like syntax tree. When the compiler encounters an unclosed tag, it cannot determine whether subsequent elements are children or siblings. Enforcing explicit closure ensures unambiguous syntax trees that translate cleanly into JavaScript objects.

> [!KEY]
> In JSX, every tag must close and every snippet must share a single root.

### Rule 3: camelCase Attributes and Reserved Words

The third universal rule of JSX governs attribute naming: **most HTML and SVG attributes must be written in camelCase**. Furthermore, certain standard HTML attribute names must be replaced to avoid collisions with JavaScript reserved words.

When the compiler transforms JSX into JavaScript, element attributes become property keys inside a plain JavaScript object. For example, `<div id="banner">` compiles to `_jsx('div', { id: 'banner' })`. In JavaScript, object keys must follow language syntax rules. Words like `class` and `for` are **reserved words** in JavaScript: `class` creates object classes, and `for` creates loops.

To prevent syntax conflicts and maintain consistency with the browser's native DOM API, JSX introduces two critical attribute replacements:

1. Use `className` instead of `class`. This matches the browser DOM property `element.className`.
2. Use `htmlFor` instead of `for`. This matches the browser DOM property `HTMLLabelElement.htmlFor`.

Similarly, multi-word HTML and SVG attributes that use hyphens in standard HTML must be converted to **camelCase attributes** in JSX: `stroke-width` becomes `strokeWidth`, `tabindex` becomes `tabIndex`, and `autocomplete` becomes `autoComplete`.

There is one intentional exception to this rule: **accessibility and custom data attributes remain hyphenated**. Attributes prefixed with `aria-` (such as `aria-label` and `aria-hidden`) and `data-` (such as `data-testid`) are written with hyphens in JSX exactly as they are in HTML. The React team preserved this hyphenation to align directly with W3C accessibility and HTML specifications.

> [!WILD]
> **Why do we write className instead of class?** When developers first write JSX, typing `className` feels unnatural and irritating. Why can't we just write `class`? Because in JavaScript, the word `class` is already taken. It is a reserved keyword used to create JavaScript classes. When the compiler turns your JSX attributes into a JavaScript object, using reserved words can cause confusion and syntax conflicts. To prevent this, React chose `className`, which matches the exact name of the browser's own DOM property. Writing `className` avoids collisions with the **reserved word** while aligning with the native **DOM property**.

> [!TIP]
> **To impress the interviewer:** When asked why JSX differs from HTML, do not just list the syntax rules. Explain that JSX attributes correspond to DOM object properties rather than HTML attribute strings. Mention that `className` and `htmlFor` reflect the underlying properties on DOM nodes, and explain that `aria-*` and `data-*` are the explicit standard-compliant exceptions to the camelCase rule.

### Where you will meet this

- HTML table row construction: grouping multiple `<td>` table cells inside `<><td>...</td><td>...</td></>` without inserting invalid wrapper `<div>` nodes inside `<tr>`.
- Flexbox navigation toolbars: grouping brand logos and navigation links with Fragments so `justify-content: space-between` distributes items cleanly without intermediate containers.
- Accessible form input groups: pairing `<label htmlFor="subscriber-email">` with `<input id="subscriber-email" />` to establish screen reader bindings without layout distortion.
- Editorial article typography: formatting breaking news stories with self-closing `<hr />` dividers and `<br />` line breaks.

### Glossary

- **JSX**: A syntax extension for JavaScript that allows developers to write declarative HTML-like markup that compiles into JavaScript object descriptors.
- **Fragment**: A built-in React component written as `<>...</>` that groups multiple sibling elements without rendering a physical wrapper node into the DOM tree.
- **Single Root Rule**: The syntactic constraint requiring every JSX return statement to have exactly one top-level enclosing element or Fragment.
- **Self-Closing Tag**: A JSX element syntax terminating in `/>` that is mandatory for void elements such as images, inputs, and horizontal rules.
- **Reserved Word**: A keyword reserved by the JavaScript language specification that cannot be used as an unquoted property name or variable identifier in standard code.
