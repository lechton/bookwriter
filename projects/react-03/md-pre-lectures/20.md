### Uncontrolled versus Controlled: Who Owns the Data?
- [p] The native DOM input model: Explains that in standard HTML, form inputs maintain their own internal state in the DOM. When a user types, the browser mutates `input.value` automatically. React knows nothing about these keystrokes unless queried via refs. ◼ Baptizes classic **Uncontrolled Component**, modern **Controlled Component / Single Source of Truth**, and concrete physical reality of *synchronizing React state with the DOM input property on every keystroke*.
- [p] The controlled contract: Details how passing `value` transfers state ownership from the DOM node to React. React takes exclusive control of the element's rendered text. ◼ Unpacks the controlled contract.
- [grounding] Leading Question: Why does typing freeze without an onChange handler?
  Confusion Point: Developers assume that HTML inputs naturally accept keyboard input regardless of props.
  Scene & Repetition: Imagine a stenographer sitting in an editorial room. The chief editor gives the stenographer a sheet of paper that says "Headline typo". The editor orders: "Show only what is written on my master desk." A reporter walks up and whispers a new sentence into the stenographer's ear. The stenographer begins to pencil in the new words, but glances back at the editor's desk. Because the editor's master paper still says "Headline typo", the stenographer instantly erases the reporter's pencil marks and rewrites "Headline typo". That is what React does when you pass value without onChange. On every keystroke, the browser tries to insert a letter, but React immediately re-applies the unchanged state value back into the DOM element. The field is frozen in time. To allow typing, you must update the master state on every single stroke. Understanding **controlled state** as a **synchronization loop** clarifies why **onChange** is required for interactive **form fields**.
  Key Terms (Bold): `**controlled state**`, `**synchronization loop**`, `**onChange**`, `**form fields**`.
  Resolution: Always supply an onChange handler alongside the value prop to keep state synchronized with user typing.

### The Two-Way Synchronization Loop: value and onChange
- [p] The four-step execution cycle: Deconstructs the exact sequence of events during a single keystroke: (1) User presses a key, triggering the browser's native `input` event; (2) React intercepts the event and invokes `onChange`; (3) The handler calls `setCorrection(e.target.value)`; (4) React schedules a re-render, computes the new virtual tree, and writes the updated string to the DOM node's `value` property. ◼ Unpacks the complete runtime loop.
- [p] Preventing the uncontrolled-to-controlled warning: Explains why passing `undefined` or `null` triggers React's runtime warning: React treats `undefined` as uncontrolled, and subsequent strings as controlled. Emphasizes always initializing input state with an empty string `''`. ◼ Baptizes **uncontrolled-to-controlled transition**.
- [grounding] Leading Question: Why does an undefined initial state trigger a warning?
  Confusion Point: Developers often write useState() without arguments, assuming React treats empty as a blank input.
  Scene & Repetition: Imagine going through airport security. When you reach the agent, you declare: "I have no passport; I am traveling incognito." The agent classifies you as an unverified traveler. Five minutes later, halfway through inspection, you reach into your pocket, pull out a diplomat passport, and demand VIP entry. The security chief halts the line and sounds an alarm: "You cannot change identification categories mid-flight!" That is what happens when you initialize state with undefined and later pass a string to value. React classifies the input as uncontrolled on mount, but as controlled on the second render. Switching modes during a component's lifecycle is forbidden. Always declare your passport upfront by initializing state with an empty string.
  Key Terms (Bold): `**uncontrolled mode**`, `**controlled transition**`, `**empty string**`, `**initial state**`.
  Resolution: Always initialize text input state with an empty string to keep the component controlled throughout its entire lifecycle.

- [code] CorrectionField.jsx snippet:
```jsx title="CorrectionField.jsx"
export default function CorrectionField({ label, value, onChange }) {
  return (
    <label className="field-group">
      <span className="field-label">{label}</span>
      <input
        type="text"
        value={value}
        onChange={e => onChange(e.target.value)} // Informs parent component of **KEYSTROKE**
      />
    </label>
  );
}
```
◼ **Code Self-Audit (What this snippet introduces):**
1. `{ label, value, onChange }`: Receiving controlled input properties.
2. `value={value}`: Binding the input's visual text to passed state.
3. `onChange={e => onChange(e.target.value)}`: Forwarding updated text string to parent.
- [p] Deconstructing CorrectionField.jsx: Explains that `CorrectionField` is fully controlled: it never manages internal state, relying exclusively on props received from its parent component. ◼ Sets up parent component role.
- [p] Introducing the parent component: Frames `CorrectionForm.jsx` as the component holding the correction state and validating submissions. ◼ Sets up parent component code.
- [code] CorrectionForm.jsx snippet:
```jsx title="CorrectionForm.jsx"
import { useState } from 'react';
import CorrectionField from './CorrectionField.jsx';

export default function CorrectionForm() {
  const [correction, setCorrection] = useState(''); // Initialized to empty string

  function handleSubmit(e) {
    e.preventDefault();
    alert(`Submitted correction: ${correction}`);
  }

  return (
    <form onSubmit={handleSubmit} className="correction-form">
      <CorrectionField
        label="Article Correction"
        value={correction}
        onChange={setCorrection}
      />
      <button type="submit">Submit Correction</button>
    </form>
  );
}
```
◼ **Code Self-Audit (What this snippet introduces):**
1. `useState('')`: Guaranteeing controlled status from initial mount.
2. `onChange={setCorrection}`: Closing the two-way synchronization loop.
- [p] Deconstructing CorrectionForm.jsx: Explains that by initializing `correction` with `''`, the input is controlled on initial render. Passing `setCorrection` directly to `onChange` completes the circular feedback loop. ◼ Completes the change detection cycle.

### Glossary
- **Controlled Component**: A form element whose value is driven by React state and updated via an explicit change callback.
- **Standard DOM Input**: A form element that maintains its own internal state within the browser DOM, queried upon submission using refs or FormData.
- **Single Source of Truth**: The architectural design where data exists in only one authoritative location, preventing synchronization drift.
- **Two-Way Synchronization**: The circular data loop where user keystrokes trigger state updates, and updated state drives the DOM element's value.
- **Uncontrolled-to-Controlled Warning**: A React console error triggered when an input is mounted with `undefined` or `null` and later receives a defined string.

### Summary
**Controlled Components: Two-Way Synchronization and Single Source of Truth**

In daily production, understanding **controlled components** ensures that form elements remain responsive, predictable, and tightly coupled to application state. By pairing `value` with `onChange`, you turn React into the single source of truth for all user input. Here is your streetwise review.

❒ Single Source of Truth, The Synchronization Loop, and Common Traps

1. Make React the **single source of truth**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Pass `value` to force the DOM input to reflect React state on every render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Always supply an `onChange` handler that updates state on every keystroke (`e.target.value`).

2. Avoid the **read-only freeze trap**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Passing `value` without `onChange` locks the input, preventing user typing.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) If you intend an input to be read-only, explicitly add the `readOnly` boolean attribute.

3. Prevent **mode-switching console warnings**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Never initialize input state to `undefined` or `null`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Always provide an initial empty string `''` to ensure controlled status throughout the component lifecycle.

➔ NEVER pass a `value` prop to an interactive input without an accompanying `onChange` handler.

➔ ALWAYS initialize text input state with an empty string `''` instead of `undefined`.

➔ IF creating checkboxes or radios THEN **use checked and read e.target.checked**.

**DO THIS:** Pair value with onChange and initialize with an empty string.

```jsx right title="CorrectionForm.jsx"
const [text, setText] = useState('');

<input
  value={text}
  onChange={e => setText(e.target.value)}
/>
```

**DO NOT DO THIS:** Never bind value without onChange or initialize state with undefined.

```jsx wrong title="CorrectionForm.jsx"
const [text, setText] = useState();

<input value={text} />
```
