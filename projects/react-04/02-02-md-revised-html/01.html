Lecture 01: What is React and the Declarative Component Model

Interview Question

CORE

What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

Imagine this scenario:

  1. Elena Vance logs into the newsroom portal of The National Times.
  2. Her name appears across the site header, the author byline, and the subscriber badge.
  3. She updates her account profile from Elena Vance to her pen name Elena Rostova.
  4. Why does the screen still show Elena Vance in three places?
  5. Readers see mismatched names across the page and distrust the publication.
  6. The JavaScript script updated two DOM nodes by hand, but missed the other eight.
  7. Today, we replace manual DOM hunting with React components that update the entire screen automatically.

The Imperative DOM Hunt vs Declarative React

In plain web development, a webpage is an HTML document loaded into browser memory. The browser parses that HTML into an object tree called the Document Object Model (DOM). When you write plain JavaScript, your code talks directly to this tree. You search for specific nodes, read their current contents, and overwrite their values.

As an application grows, user data rarely stays in a single location on screen. A subscriber's name appears in the top navigation bar, the article byline, the comments drawer, and the checkout receipt. In plain JavaScript, you must write manual search-and-replace instructions for every single appearance. If your script forgets even one element, the screen falls out of synchronization with memory. This failure is called state drift, and it leads to confusing bugs that erode user trust.

This manual hunting is the essence of imperative programming. What is imperative programming? In imperative code, you issue step-by-step commands instructing the browser how to mutate each individual node. You tell the engine: find this node, update its text, find that image, update its attribute. When you add a new checkout banner next week, you must remember to update this function. If you miss it, the new banner displays stale data forever.

What is declarative UI? React draws the line between two models of web development: imperative DOM scripting, controlled by manual step-by-step commands, and declarative UI, controlled by React from a single state description. In normal JavaScript, you command the browser: find this node, change its text, find that image, change its title. In declarative React, you describe what the user interface should look like for any given data: you write your component once, hand it the data, and React calculates which DOM nodes must change. The law of declarative UI: React updates the DOM to match your component description. You never touch physical DOM nodes by hand.

⚡ IN THE WILD

What is the problem with updating the physical DOM? Can you imagine a subscriber updating her account profile on The National Times? Elena Vance changes her name to Elena Rostova. Her name lives in ten separate places across the screen. In plain JavaScript, you must hunt down each and every element by hand. You write query after query. If you miss just one place, the old name remains on screen. This is the core problem of imperative programming: it is imperative to hunt down and update every DOM node manually, time and time again. This manual hunt leads to silent failures and broken screens. React solves this friction with declarative components: you declare your markup once, and React synchronizes the entire physical DOM automatically using its in-memory virtual DOM.

Components as Reusable Blueprints

In plain HTML, you structure documents using native tags like the <header>, <article>, and <button> elements. However, native HTML tags know nothing about your application logic or subscriber data. Traditionally, developers copied and pasted HTML markup across separate templates. Then, they attached external JavaScript scripts to add interactive behavior. This separation split structure from logic, producing fragile codebases where renaming a CSS class broke JavaScript event listeners.

To solve this fragmentation, React unifies markup, style, and logic into a single cohesive structure. This mechanism is called a component. What is a component? A component is a self-contained, reusable JavaScript function. It accepts input data called props (short for properties). It returns markup describing a piece of the user interface using JSX syntax. In React, every component function name must start with a capital letter. Capitalization is a strict compiler requirement: the component <SiteHeader /> tells React to invoke your custom JavaScript function, while the lowercase <header> element tells the browser to create a built-in DOM node.

ReaderGreeting.jsx
1export default function ReaderGreeting({ readerName }) {
2 return <h2>Welcome back, {readerName}</h2>;
Curly braces open live JavaScript execution
3}

The component ReaderGreeting receives its input data through a single parameter called props. Rather than writing props.readerName throughout the function body, the signature uses JavaScript object destructuring directly inside the parentheses. This unpacks the prop readerName straight into a local variable. Inside the markup, the curly braces around the prop readerName establish an evaluation window. This window steps out of static HTML structure and into live JavaScript execution. It projects the current value of the prop readerName directly into the heading text.

Key Takeaway

A component is a blueprint, not a building. When your component function executes, it does not construct physical DOM nodes; it returns a lightweight description of what the screen should look like, and React constructs the DOM nodes for you.

Components can be nested inside one another like building blocks. A top-level parent component coordinates layout and passes data downward, while focused child components render individual sections. To see this in action on The National Times, we organize our site header into three distinct files: (a) The parent component SiteHeader.jsx acts as the orchestrating container. (b) The child component ReaderGreeting.jsx renders the personalized welcome message. (c) The child component SubscriberInfo.jsx displays the subscriber tier details. Both child components receive the subscriber's name through the prop readerName passed directly from their parent.

Lessons from the Experiment: Naive Expectation vs Reality

Now that our site header is complete, let us review the architectural roles of each component in our hierarchy.

SiteHeader

The parent component coordinates the newsroom masthead layout. It owns the reader identity in a single variable. It actively passes that data downward to two child components: ReaderGreeting and SubscriberInfo. Notice that neither child queries the DOM. Why? Because the parent supplies their data through explicit props.

ReaderGreetingreaderName={currentReader}

This is a child component. It receives the readerName prop from the parent container. It unpacks the name using object destructuring and renders it inside an evaluation window {readerName}. Notice it owns zero DOM lookups and zero state. It is a pure presenter of greeting text.

SubscriberInforeaderName={currentReader}

This is a sibling child component. It receives the exact same readerName prop as ReaderGreeting. Notice that both siblings share the same data without communicating directly with each other. Why? Because React enforces one-way data flow downward from the common parent.

When developers transition from plain JavaScript to React, their naive expectation is to treat components as simple HTML templates with embedded DOM queries. They expect to write document.querySelector to update user greetings when account data changes. What the experiment showed is that React completely eliminates manual DOM queries: the parent holds data in memory, passes it downward through props, and React updates all matching elements on screen simultaneously.

What would happen if the component SiteHeader did not split greeting and subscriber details into child components, and instead hardcoded a monolithic HTML structure in one file? If you merged all markup and styling into one monolith, any design change to the subscriber badge would force you to re-test the greeting and navigation logic. Worse, you could never reuse the component ReaderGreeting on the mobile edition without copy-pasting markup. By separating concerns into child components, the component ReaderGreeting owns zero layout knowledge and zero subscriber logic.

This separation gives you two concrete superpowers:

  1. If tomorrow you replace the greeting styling with a localized banner, you touch zero lines of subscriber badge code.
  2. If you redesign the subscriber tier badges, you touch zero lines of greeting code.

Where you will meet this

  1. Newsroom mastheads and subscriber bars: updating user names, subscription badges, and access tokens across multi-column article pages without state drift.
  2. E-commerce cart counters and checkout summaries: reflecting item counts and totals simultaneously in the navigation bar, sticky sidebar, and checkout drawer.
  3. Social media profile headers: displaying author avatars, display names, and follower counts across profile headers, comment threads, and direct message lists.
  4. Banking and financial dashboards: synchronizing account balances and currency indicators across transaction feeds, transfer dialogs, and balance cards.

Glossary

  • Component: A self-contained, reusable JavaScript function that accepts props and returns a description of the user interface using JSX.
  • Declarative UI: A programming paradigm where developers describe what the UI should look like for any given data, and the framework automatically updates the DOM to match.
  • Imperative DOM Scripting: A programming approach where developers write manual step-by-step instructions to find, create, and mutate physical browser DOM elements.
  • Props: Short for properties; a single JavaScript object passed from a parent component to a child component to supply input data.
  • JSX Evaluation Window: The curly braces {} syntax inside JSX that steps out of static markup and evaluates a live JavaScript expression.

Summary

The Declarative Component Foundation

The transition from imperative DOM scripting to declarative React represents a fundamental shift in how user interfaces are built, synchronized, and maintained.

❒ Core Architectural Concepts
  1. Declarative Synchronization vs Manual DOM Hunting: In plain JavaScript, updating the screen requires finding and mutating physical DOM nodes by hand, which inevitably causes state drift as the app grows.
        (a) React inverts this model: you describe the interface as a function of data, and React calculates the required DOM updates.
        (b) You never touch physical DOM nodes with document.getElementById or document.querySelector in routine component code.
  2. Components as Reusable Blueprints: A component is a JavaScript function whose name starts with a capital letter and whose return value is JSX markup.
        (a) Capitalization is mandatory: the component <SiteHeader /> invokes a custom React component, while the <header> element creates a native browser DOM element.
        (b) Components compose together into a tree, allowing complex user interfaces to be assembled from small, focused building blocks.
  3. Unidirectional Props Flow: Data flows strictly downward from parent components to child components through props.
        (a) A child receives props as an immutable input object, commonly unpacked using parameter destructuring.
        (b) Sibling components share data by lifting that data into their nearest common parent, ensuring all siblings stay synchronized.

➔ NEVER query or mutate physical DOM nodes with document.querySelector or textContent to update component UI.

➔ ALWAYS capitalize component names so React distinguishes custom components from native HTML elements.

➔ IF two sibling components need the same piece of data, THEN pass that data downward as props from their common parent.
