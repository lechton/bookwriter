Lecture 01: What is React and the Declarative Component Model

Interview Question

CORE

What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

Imagine this scenario:

  1. Elena Vance logs into the newsroom portal of The National Times.
  2. Her name appears across the site header, the author byline, and the subscriber badge.
  3. She updates her account profile from Elena Vance to her pen name Elena Rostova.
  4. Why does the screen still show Elena Vance in three places?
  5. Readers see mismatched names across the page and distrust the publication.
  6. The JavaScript script updated two DOM nodes by hand, but missed the other eight.
  7. Today, we replace manual DOM hunting with React components that update the entire screen automatically.

The Imperative DOM Hunt vs Declarative React

In plain web development, a webpage is an HTML document loaded into browser memory. The browser parses that HTML into an object tree called the Document Object Model (DOM). When you write plain JavaScript, your code talks directly to this tree. You search for specific nodes, read their current contents, and overwrite their values.

As an application grows, user data rarely stays in a single location on screen. A subscriber's name appears in the top navigation bar, the article byline, the comments drawer, and the checkout receipt. In plain JavaScript, you must write manual search-and-replace instructions for every single appearance. If your script forgets even one element, the screen falls out of synchronization with memory. This failure is called state drift, and it leads to confusing bugs that erode user trust.

This manual hunting is the essence of imperative programming. What is imperative programming? In imperative code, you issue step-by-step commands instructing the browser how to mutate each individual node. You tell the engine: find this node, update its text, find that image, update its attribute. When you add a new checkout banner next week, you must remember to update this function. If you miss it, the new banner displays stale data forever.

What is declarative UI? React draws the line between two models of web development: imperative DOM scripting, controlled by manual step-by-step commands, and declarative UI, controlled by React from a single state description. In normal JavaScript, you command the browser: find this node, change its text, find that image, change its title. In declarative React, you describe what the user interface should look like for any given data: you write your component once, hand it the data, and React calculates which DOM nodes must change. The law of declarative UI: React updates the DOM to match your component description. You never touch physical DOM nodes by hand.

⚡ IN THE WILD

What is the problem with updating the physical DOM? Can you imagine a subscriber updating her account profile on The National Times? Elena Vance changes her name to Elena Rostova. Her name lives in ten separate places across the screen. In plain JavaScript, you must hunt down each and every element by hand. You write query after query. If you miss just one place, the old name remains on screen. This is the core problem of imperative programming: it is imperative to hunt down and update every DOM node manually, time and time again. This manual hunt leads to silent failures and broken screens. React solves this friction with declarative components: you declare your markup once, and React synchronizes the entire physical DOM automatically using its in-memory virtual DOM.

Components as Reusable Blueprints

In plain HTML, you structure documents using native tags like the <header>, <article>, and <button> elements. However, native HTML tags know nothing about your application logic or subscriber data. Traditionally, developers copied and pasted HTML markup across separate templates. Then, they attached external JavaScript scripts to add interactive behavior. This separation split structure from logic, producing fragile codebases where renaming a CSS class broke JavaScript event listeners.

To solve this fragmentation, React unifies markup, style, and logic into a single cohesive structure. This mechanism is called a component. What is a component? A component is a self-contained, reusable JavaScript function. It accepts input data called props (short for properties). It returns markup describing a piece of the user interface using JSX syntax. In React, every component function name must start with a capital letter. Capitalization is a strict compiler requirement: the component <SiteHeader /> tells React to invoke your custom JavaScript function, while the lowercase <header> element tells the browser to create a built-in DOM node.

ReaderGreeting.jsx
1export default function ReaderGreeting({ readerName }) {
2 return <h2>Welcome back, {readerName}</h2>;
Curly braces open live JavaScript execution
3}

The component ReaderGreeting receives its input data through a single parameter called props. Rather than writing props.readerName throughout the function body, the signature uses JavaScript object destructuring directly inside the parentheses. This unpacks the prop readerName straight into a local variable. Inside the markup, the curly braces around the prop readerName establish an evaluation window. This window steps out of static HTML structure and into live JavaScript execution. It projects the current value of the prop readerName directly into the heading text.

Key Takeaway

A component is a blueprint, not a building. When your component function executes, it does not construct physical DOM nodes; it returns a lightweight description of what the screen should look like, and React constructs the DOM nodes for you.

Components can be nested inside one another like building blocks. A top-level parent component coordinates layout and passes data downward, while focused child components render individual sections. To see this in action on The National Times, we organize our site header into three distinct files: (a) The parent component SiteHeader.jsx acts as the orchestrating container. (b) The child component ReaderGreeting.jsx renders the personalized welcome message. (c) The child component SubscriberInfo.jsx displays the subscriber tier details. Both child components receive the subscriber's name through the prop readerName passed directly from their parent.

Lessons from the Experiment: Naive Expectation vs Reality

Now that our site header is complete, let us review the architectural roles of each component in our hierarchy.

SiteHeader

The parent component coordinates the newsroom masthead layout. It owns the reader identity in a single variable. It actively passes that data downward to two child components: ReaderGreeting and SubscriberInfo. Notice that neither child queries the DOM. Why? Because the parent supplies their data through explicit props.

ReaderGreetingreaderName={currentReader}

This is a child component. It receives the readerName prop from the parent container. It unpacks the name using object destructuring and renders it inside an evaluation window {readerName}. Notice it owns zero DOM lookups and zero state. It is a pure presenter of greeting text.

SubscriberInforeaderName={currentReader}

This is a sibling child component. It receives the exact same readerName prop as ReaderGreeting. Notice that both siblings share the same data without communicating directly with each other. Why? Because React enforces one-way data flow downward from the common parent.

When developers transition from plain JavaScript to React, their naive expectation is to treat components as simple HTML templates with embedded DOM queries. They expect to write document.querySelector to update user greetings when account data changes. What the experiment showed is that React completely eliminates manual DOM queries: the parent holds data in memory, passes it downward through props, and React updates all matching elements on screen simultaneously.

What would happen if the component SiteHeader did not split greeting and subscriber details into child components, and instead hardcoded a monolithic HTML structure in one file? If you merged all markup and styling into one monolith, any design change to the subscriber badge would force you to re-test the greeting and navigation logic. Worse, you could never reuse the component ReaderGreeting on the mobile edition without copy-pasting markup. By separating concerns into child components, the component ReaderGreeting owns zero layout knowledge and zero subscriber logic.

This separation gives you two concrete superpowers:

  1. If tomorrow you replace the greeting styling with a localized banner, you touch zero lines of subscriber badge code.
  2. If you redesign the subscriber tier badges, you touch zero lines of greeting code.

Where you will meet this

  1. Newsroom mastheads and subscriber bars: updating user names, subscription badges, and access tokens across multi-column article pages without state drift.
  2. E-commerce cart counters and checkout summaries: reflecting item counts and totals simultaneously in the navigation bar, sticky sidebar, and checkout drawer.
  3. Social media profile headers: displaying author avatars, display names, and follower counts across profile headers, comment threads, and direct message lists.
  4. Banking and financial dashboards: synchronizing account balances and currency indicators across transaction feeds, transfer dialogs, and balance cards.

Glossary

  • Component: A self-contained, reusable JavaScript function that accepts props and returns a description of the user interface using JSX.
  • Declarative UI: A programming paradigm where developers describe what the UI should look like for any given data, and the framework automatically updates the DOM to match.
  • Imperative DOM Scripting: A programming approach where developers write manual step-by-step instructions to find, create, and mutate physical browser DOM elements.
  • Props: Short for properties; a single JavaScript object passed from a parent component to a child component to supply input data.
  • JSX Evaluation Window: The curly braces {} syntax inside JSX that steps out of static markup and evaluates a live JavaScript expression.

Summary

The Declarative Component Foundation

The transition from imperative DOM scripting to declarative React represents a fundamental shift in how user interfaces are built, synchronized, and maintained.

❒ Core Architectural Concepts
  1. Declarative Synchronization vs Manual DOM Hunting: In plain JavaScript, updating the screen requires finding and mutating physical DOM nodes by hand, which inevitably causes state drift as the app grows.
        (a) React inverts this model: you describe the interface as a function of data, and React calculates the required DOM updates.
        (b) You never touch physical DOM nodes with document.getElementById or document.querySelector in routine component code.
  2. Components as Reusable Blueprints: A component is a JavaScript function whose name starts with a capital letter and whose return value is JSX markup.
        (a) Capitalization is mandatory: the component <SiteHeader /> invokes a custom React component, while the <header> element creates a native browser DOM element.
        (b) Components compose together into a tree, allowing complex user interfaces to be assembled from small, focused building blocks.
  3. Unidirectional Props Flow: Data flows strictly downward from parent components to child components through props.
        (a) A child receives props as an immutable input object, commonly unpacked using parameter destructuring.
        (b) Sibling components share data by lifting that data into their nearest common parent, ensuring all siblings stay synchronized.

Interview Question

CORE

  2. She opens the official React documentation to find the terminal command that creates a modern application.
  3. The documentation presents two completely different paths: a full-stack framework like Next.js or a client build tool like Vite.
  4. Which command do you run in your terminal, and how do you choose between them?
  5. Choosing the wrong path traps the team: either wrestling complex server configurations for a simple widget, or delivering a blank white screen to mobile readers.
  6. Legacy scaffolding tools bundled the entire application into memory before serving a single line, while modern tools let the browser do the heavy lifting.
  7. Today, we scaffold a real project from the terminal, deconstruct every generated file, and master the framework versus build tool decision.

Scaffolding with Vite: From Terminal to Running Server

In earlier days of React, developers started projects using an official CLI tool called create-react-app. This tool hid the bundler Webpack behind an automated script. As applications grew, create-react-app became painfully slow. Every time you started the local server, Webpack had to crawl and bundle every single JavaScript file in your project before the browser could paint the first pixel. Changing one line forced a multi-second rebuild. Eventually, the tool became unmaintained.

Modern React development relies on Vite, a lightweight, high-performance build tool. Vite takes a radically different approach: it serves your source files directly to the browser as unbundled native ES modules (ESM) during development. Because the browser requests files on demand, the development server starts almost instantly.

To scaffold a new React project with Vite, you run a generator command in your terminal. The generic formula is npm create vite@latest <app_name> -- --template react Here, the parameter <app_name> is a required placeholder for your project folder name. In POSIX command conventions, angle brackets designate a required placeholder that you replace without typing literal brackets.

The command npm create automatically downloads and executes create-vite in memory without installing it globally on your machine. The double-dash -- tells npm to pass all following arguments directly to the generator, where the flag --template react selects the React template. For our newsroom weather widget, we run the concrete command below:

Terminal
1npm create vite@latest national-weather -- --template react
2cd national-weather
3npm install
4npm run dev

The command creates the directory national-weather, downloads packages into node_modules/, and starts the development server. When you open the local URL, you see Vite's starter screen:

⚡ IN THE WILD

Why did Create React App disappear? Can you imagine Elena Vance waiting at her desk at The National Times to update a single headline? She boots up the old development server and waits forty-five seconds while the bundler crawls through two thousand files in memory. Every single line edit triggers a sluggish re-bundle that freezes her terminal. This was the fatal flaw of early bundlers: they bundled every line of code before serving a single file. In modern web development, Vite permanently eliminates this delay. By serving source code as native ES modules, the browser only asks for the exact file Elena is editing. The server boots in milliseconds, and changes reflect on screen instantly through Hot Module Replacement.

Deconstructing the Scaffold: The Five Vital Files

Scaffolding a project generates a directory tree containing configuration files, package manifests, and source code. Beginners often view the generated files as intimidating boilerplate, but a Vite React project consists of five vital files with clear responsibilities:

(a) The project manifest (package.json) is the dependency blueprint, holding two separate lists: runtime dependencies (dependencies), which contains react and react-dom that ship to the browser, and development dependencies (devDependencies), which contains vite and @vitejs/plugin-react that remain strictly on your computer. The consequence: production downloads remain small because build tooling never leaves your machine.

(b) The entry document (index.html) is the physical HTML shell containing the container <div id="root"></div> and a module script tag. In Vite, index.html sits at the project root rather than in a hidden folder, making the document shell immediately accessible and customizable.

(c) The build configuration (vite.config.js) registers plugins like @vitejs/plugin-react. This plugin coordinates three systems: compiling JSX syntax into standard JavaScript, enabling Fast Refresh during editing, and configuring Rollup for production bundling.

(d) The application entry point (src/main.jsx) imports createRoot from react-dom/client and mounts your root component into the DOM container.

(e) The dependency tree (node_modules/ and package-lock.json) contains the downloaded packages and locks exact package versions, ensuring every team member runs identical code.

Look at index.html. It provides the physical anchor for the entire application:

The browser is the bundler in development.

Vite does not bundle your source code when you start the development server. Instead, it serves each file as a native ES module the instant your browser requests it. This architecture delivers instantaneous server startup times regardless of how many thousands of components your application contains.

Build Tools vs Full-Stack Frameworks: The Architectural Dilemma

React is formally defined as a library for building user interfaces, not an all-inclusive framework. When you build with React alone via a build tool like Vite, you get client-side rendering (CSR).

In client-side rendering, the web server delivers an empty HTML shell to the browser. The browser downloads the JavaScript bundle, parses it, executes it, and only then creates the DOM nodes. On slow mobile networks, the user stares at a blank white screen while the bundle loads. Furthermore, search engine crawlers may fail to index dynamic content properly.

To solve this initial loading delay, the React ecosystem provides full-stack frameworks like Next.js, Remix (now React Router v7), and Astro.

What is the difference between a build tool and a framework? React draws the line between two hosting architectures: the standalone build tool (like Vite), which produces a client-side Single Page Application (SPA), and the full-stack framework (like Next.js), which coordinates both server and client execution.

In normal web hosting with a build tool, the server is a passive file store: it sends an empty HTML shell and a JavaScript bundle, and React executes entirely in the user's browser. Leave your app in that architecture and React calls it a client-only SPA.

In a full-stack framework, the server is an active computing participant: it executes React components on the server, generates complete HTML filled with real text and images, and streams that HTML to the browser immediately.

The law of project setup: choose a build tool when your app lives behind a login or requires zero server infrastructure; choose a framework when your app demands instant initial page loads, search engine indexing, or integrated server endpoints.

To choose effectively, evaluate three concrete technical criteria:

  1. Routing and Navigation: Vite includes zero routing out of the box. You must install and configure client-side routing libraries like TanStack Router or React Router manually. Frameworks provide built-in file-based routing where creating a file in a routes/ or app/ folder automatically generates a URL route.
  2. Data Fetching and Server Integration: In Vite, data fetching occurs on the client using useEffect or React Query after the bundle executes in the browser. In a framework, data fetching can occur directly on the server before HTML is sent, eliminating client-side loading spinners.
  3. Deployment and Infrastructure: Vite builds to a folder of static .html, .js, and .css files that can be hosted on any static content delivery network (CDN) like AWS S3 or Cloudflare Pages. Frameworks that use server-side rendering require a running Node.js server or serverless compute environment.

Interview Tip

To impress the interviewer: Avoid claiming that frameworks are for large applications and build tools are for small ones. Enterprise internal dashboards with thousands of screens often run on Vite because they live behind corporate logins and require zero search engine optimization. Frame your decision around three architectural requirements: search engine indexing, initial page-load performance, and server-side data mutations.

In a full-stack framework with file-based routing, this file would live in a routes/ or app/ folder. In Vite, App.jsx serves as the root component mounted into the DOM by main.jsx. The root shell mounts the component <WeatherDashboard />, completing the client component hierarchy.

Lessons from the Experiment: Naive Expectation vs Reality

WeatherDashboard

The parent component orchestrates the weather station desk. It owns the weather station data. It actively passes that data downward to the child StationCard. Notice it does not fetch data inside child cards. Why? To maintain a single source of truth across the entire dashboard.

StationCardstation={currentStation}

This is the presentation child component. It receives the station object from the parent container. It unpacks the name and metrics using object destructuring and renders them inside JSX evaluation windows. Notice it owns zero network logic and zero DOM queries.

StationActions

This is the terminal action component. It renders an interactive button with a declarative onClick handler. Notice it contains zero DOM event listener bindings. When does it communicate? It dispatches actions cleanly without coupling to physical DOM element IDs.

When developers start a new React project, their naive expectation is that modern React demands a massive full-stack framework with complex server configurations just to render a simple dashboard. They expect that building a React app requires managing serverless functions, database adapters, and hydration protocols.

What the experiment showed is that Vite provides an instant, zero-config client development environment: you run one command, and within seconds you are writing pure, modular React components that compile into static assets ready for deployment anywhere.

What would happen if the component WeatherDashboard merged all weather markup, station data, and refresh actions into a single monolithic file?

If you kept all code in one monolith, any design change to the temperature display would force you to re-test the refresh button logic. Worse, you could never reuse the component StationCard to render multiple weather stations across The National Times homepage without copy-pasting code.

By separating concerns into focused child components, the component StationCard owns zero action logic and the component StationActions owns zero weather metrics. This separation gives you two concrete superpowers:

  1. If tomorrow you add five new weather stations from different cities, you reuse the component StationCard five times with zero code duplication.
  2. If you redesign the refresh button or add an automated polling timer, you touch zero lines of station display code.

Where you will meet this

  1. Newsroom editorial widgets: scaffolding standalone interactive graphics, live election maps, and weather widgets using Vite for instant client-side performance.
  2. Internal corporate dashboards: building authenticated employee portals and analytics workstations behind corporate firewalls where SEO is unnecessary and static hosting is preferred.
  3. Public media websites: choosing full-stack frameworks like Next.js or Astro for public article pages that demand instant server-rendered HTML for search engine indexing.
  4. E-commerce storefronts: leveraging full-stack frameworks with server-side rendering to ensure product pages load instantly on mobile networks and display rich social preview cards.

Glossary

  • Build Tool: A development utility like Vite that compiles source files, manages local development servers with Hot Module Replacement, and bundles code for production deployment.
  • Full-Stack Framework: An integrated application architecture like Next.js or Remix that executes React components on both the server and the client, providing built-in routing, data fetching, and HTML rendering.
  • Single Page Application (SPA): A web application architecture where the browser downloads a single HTML shell and a JavaScript bundle, using client-side JavaScript to render and update the user interface dynamically.
  • Hot Module Replacement (HMR): A development mechanism that swaps updated JavaScript modules in the running browser without performing a full page reload, preserving component state.
  • Server-Side Rendering (SSR): The process of executing React components on the web server to generate complete HTML markup before sending it to the client browser.

Summary

Project Setup: Build Tools vs Full-Stack Frameworks

❒ Core Architectural Concepts
  1. Vite as the Modern Standalone Build Tool: Vite replaces obsolete tools like create-react-app by serving unbundled native ES modules directly to the browser during development.
        (a) Development server cold starts are near-instantaneous because Vite does not crawl and bundle the entire codebase before serving.
        (b) In production, Vite uses Rollup to generate highly optimized, static .html, .js, and .css bundles.
  2. Anatomy of the Scaffolding: A standard Vite React project consists of five vital files that separate configuration from source code.
        (a) package.json separates runtime dependencies from build-time devDependencies, ensuring build tooling never ships to users.
        (b) index.html sits at the root as the entry document, hosting the container <div id="root"></div> and loading /src/main.jsx as a native module.
  3. Choosing Between Build Tools and Frameworks: The decision between a standalone build tool and a full-stack framework depends on SEO, performance, and infrastructure requirements.
        (a) Choose Vite for client-only SPAs, authenticated dashboards, prototypes, and applications where static hosting is preferred.
        (b) Choose a framework like Next.js or Remix when you need server-side rendering, instant Largest Contentful Paint (LCP), search engine indexing, or integrated server endpoints.

➔ NEVER use deprecated tools like create-react-app for new React projects when modern build tools like Vite provide instant development servers and active ecosystem support.

➔ ALWAYS separate runtime dependencies from development devDependencies in package.json to keep production bundle downloads minimal.

➔ IF your application requires public search engine indexing or fast initial page loads on mobile networks, THEN choose a full-stack framework with server-side rendering instead of a client-only SPA.
