### Component Architecture and the State Ownership Divide
- [p] ◇ {preknowledge:} In earlier lessons, we learned that React components maintain local reactive memory using the `useState` hook (see Lecture 1). When you build an interactive form, your immediate instinct is to store every character the user types inside a component state variable. {problem:} Developers often assume that controlling every input is the only way to manage form data in React. ◼ Pedagogical qualification: Ground the familiar controlled input pattern; introduce the concept of React as the single source of truth; terms introduced: **controlled input**, **single source of truth**, **onChange handler**.
- [p] ★ {preknowledge:} In a controlled input, you bind the `value` attribute to a state variable. You also attach an `onChange` listener to update that state on every keystroke. Now imagine typing the word hello into that field one letter at a time. Each keypress dispatches an event and updates state. React wakes the fiber reconciler. It re-runs the component function and recomputes the virtual DOM. Finally, it writes the updated string back into the DOM node. {problem:} The component re-renders on every keystroke. The CPU recalculates the entire component tree five times just to type a five-letter word. ◼ Pedagogical qualification: Execute the canonical h-e-l-l-o standard; unpack the per-keystroke reconciliation loop in plain CEFR B2 English.
- [grounding] the opening question: What does controlling an input really mean?
  the friction it clears: why React intercepting every keystroke differs from native paper writing.
  Scene & Repetition: Imagine you are typing your name into a guestbook. In plain HTML, the pen writes directly onto the paper, and the book holds the ink. In a **controlled input**, you do not write on the paper directly. Instead, you whisper each letter to an assistant named React. React writes the letter down in its private notebook (the **component state**), erases the paper, and copies the letter onto the paper for you. If you type five letters, you whisper five times, and React rewrites the paper five times. This gives React complete control over the paper. But whispering and rewriting on every keypress creates unnecessary work when you only care about the finished name on submit. An **uncontrolled input** lets the browser hold the ink until you hand in the book.
  Key Terms (Bold): **controlled input**, **component state**, **single source of truth**.
  Resolution: Controlled inputs make React the single source of truth by intercepting every keypress and pushing state back into the DOM.

### The Per-Keystroke Latency Bottleneck
- [p] ◇ {preknowledge:} On a high-performance desktop computer, running a small component function five times while typing a word takes less than a millisecond. On a budget smartphone with a busy CPU, re-rendering a large component tree on every keystroke causes frame drops and sluggish typing latency. {problem:} Controlling every input indiscriminately degrades user experience on low-end devices. ◼ Pedagogical qualification: Frame the hardware divide and why desktop developer machines mask mobile typing latency.
- [p] ★ {preknowledge:} When an input is controlled, typing a character triggers a state update. That schedules work on the React fiber work loop. Now imagine the component tree contains fifty child components, complex charts, or heavy layout elements. React must reconcile that entire tree before the browser paints the newly typed character. {problem:} If reconciliation takes more than 16 milliseconds, the frame drops. The user experiences input lag. Typed characters appear seconds after their fingers leave the glass. ◼ Pedagogical qualification: Execute the 16ms frame budget standard; explain how fiber work loop scheduling stalls native paint routines.
- [p] Uncontrolled inputs bypass the React work loop completely while typing. The native browser engine handles character insertion in compiled C++. Typing stays at a solid 60 frames per second, no matter how large the React application is. You pay zero rendering cost until the user clicks submit. ◼ Explains native C++ buffer performance.
- [grounding] the opening question: Why does typing lag on mobile devices?
  the friction it clears: why mobile devices stutter on controlled inputs while desktops do not.
  Scene & Repetition: Imagine typing a message on your smartphone. You tap five keys quickly, but the letters appear on screen with a sluggish delay. Why? Because every single keypress forced React to re-render the entire page. The computer was busy recalculating layout trees, re-rendering sidebars, and diffing virtual DOM trees instead of simply painting the letter you typed. This is the **input latency** bottleneck of over-controlled forms. **Uncontrolled inputs** eliminate this lag completely. The browser handles text entry in native C++, and React stays completely idle until the user taps submit.
  Key Terms (Bold): **input latency**, **uncontrolled inputs**, **fiber work loop**.
  Resolution: Uncontrolled inputs eliminate input latency by delegating text entry to compiled browser C++ routines.

### The Senior Engineering Decision Matrix
- [p] Senior engineers do not choose between controlled and uncontrolled inputs based on habit or dogma. They evaluate the concrete functional requirements of the specific form control. ◼ Introduces senior evaluation criteria.
- [p] When should you choose controlled inputs? Choose controlled inputs when you need immediate, synchronous access to the field's value while the user is actively typing. Specifically: ◼ Introduces controlled criteria.
- [bullet] Controlled criteria:
  - **Live Search Filtering**: Query strings that filter lists, tables, or autocomplete dropdowns on every keystroke.
  - **Input Masking and Formatting**: Fields requiring immediate character formatting, such as phone numbers, dates, or currency strings.
  - **Dynamic Field Dependencies**: Scenarios where typing in one field dynamically shows, hides, or disables another field.
  - **Instant Character Counters**: Live feedback widgets such as password strength meters or remaining character counters.
- [p] When should you choose uncontrolled inputs with FormData? Choose uncontrolled inputs when you only need the field values at the moment of submission. Specifically: ◼ Introduces uncontrolled criteria.
- [bullet] Uncontrolled criteria:
  - **Standard Data Collection Forms**: Contact forms, feedback submissions, user registration, and account profiles.
  - **Large Multi-Field Forms**: Forms with dozens of fields where per-keystroke re-rendering causes performance bottlenecks.
  - **Long-Form Text Editing**: Article authoring, commentary, and description fields where users type long paragraphs of text.
  - **React 19 Form Actions**: Workflows leveraging modern form actions, automatic resets, and progressive enhancement.
- [tip] To impress the interviewer: When asked whether forms should be controlled or uncontrolled, never say "always control everything." Explain the architectural trade-off. Controlled inputs provide instant real-time synchronization, but they cause per-keystroke re-renders and boilerplate state. Uncontrolled inputs with `FormData` isolate typing from the React work loop. They deliver maximum performance and clean code for standard submit-only workflows. ◼ Senior interview positioning.

### Glossary
- [definition] **Controlled Input**: An input element whose displayed value is bound to a React state variable and updated synchronously via an onChange handler on every keystroke.
- [definition] **Uncontrolled Input**: An input element that stores its value in the native browser buffer, accessed on demand via a ref or harvested on form submission through FormData.
- [definition] **FormData**: A native browser object providing a key-value representation of form fields, populated automatically from named inputs upon form submission.
- [definition] **Single Source of Truth**: The design principle where application state lives in exactly one place (React state for controlled inputs, or the DOM for uncontrolled inputs).
- [definition] **Input Latency**: The delay between a physical keystroke on the keyboard and the visual rendering of the corresponding character on screen, exacerbated by per-keystroke component re-renders.
- [definition] **DefaultValue**: The initial value supplied to an uncontrolled input at mount time, allowing the browser to manage subsequent edits without React state intervention.

### Summary
- [review-title] **Controlled State versus Uncontrolled FormData in React Forms**
- [p] In production applications, choosing between controlled state and uncontrolled `FormData` defines both developer ergonomics and runtime rendering performance. Here is your streetwise review.
- [review-subtitle] ❒ Core Principles of Form State Architecture
- [numbered-review-point] 1. Use **uncontrolled inputs with FormData** as your default strategy for standard submit-only forms.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Storing text in the native browser buffer eliminates per-keystroke re-renders and state boilerplate.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Named inputs are harvested automatically into a native `FormData` dictionary on submit.
- [numbered-review-point] 2. Reserve **controlled inputs** for fields that require real-time synchronization during typing.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Live search filters, character counters, and input formatting masks require immediate access to every keystroke.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Binding `value` and `onChange` forces React to re-render on every keypress, creating input latency on large trees.
- [numbered-review-point] 3. Protect mobile performance by avoiding **over-controlled forms**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Controlling dozens of fields in a single component causes cumulative layout recalculation and typing lag.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Keep inputs uncontrolled unless a specific real-time feature demands per-keystroke state.
- [never-rule] ➔ NEVER control an input if you only read its value when the user clicks submit.
- [always-rule] ➔ ALWAYS supply a `name` attribute to uncontrolled inputs so `FormData` can harvest them.
- [if-then-rule] ➔ IF you need real-time validation or live search filtering THEN **bind `value` and `onChange` with controlled state**.
- [do-this-header] **DO THIS:** Use uncontrolled inputs with `name` attributes and harvest values via `FormData` on submit.
