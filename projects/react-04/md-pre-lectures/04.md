### Why JSX Is Not HTML
- [p] ◇ {preknowledge:} In earlier lessons, we learned that a React component is a JavaScript function returning markup (see Lecture 3). When you write that markup, it looks nearly identical to HTML: you write angle brackets, tag names like `<h1>`, and attributes like `src`. {problem:} Developers naturally assume they are writing real HTML, but web browsers cannot understand JSX directly, and treating JSX as HTML causes sudden syntax errors. ◼ Pedagogical qualification: Establish that JSX is a syntax extension for JavaScript rather than HTML; terms introduced: **JSX**, **syntax extension**, **compiler**, **AST**.
- [p] ★ {preknowledge:} Under the hood, a compiler like Babel or Vite's SWC transforms every JSX element into a plain JavaScript function call: `jsx('h1', { children: 'Breaking' })`. Because JSX compiles into function calls, it must obey the strict grammar of JavaScript. In JavaScript, you cannot return two separate objects from a function without wrapping them, and you cannot leave syntax unclosed. {problem:} Loose HTML5 parsing rules allow unclosed void tags and arbitrary attributes, but the JSX compiler rejects any snippet that violates JavaScript syntactic integrity. ◼ Pedagogical qualification: Deconstruct the AST compilation from JSX tag to `jsx()` function call; explain why JavaScript grammar governs JSX.
- [p] {old solution:} Early web libraries used string templates or concatenated HTML strings, which bypassed the compiler but failed to catch syntax errors until runtime. ◼ Educational objective: Contrast compiled JSX with uncompiled string templates.
- [code] JSX compilation contrast:
```jsx title="Compilation Model"
// JSX Source:
<h1 className="headline">Breaking News</h1>
// Compiled JavaScript Output:
jsx('h1', { className: 'headline', children: 'Breaking News' });
```
◼ **Code Self-Audit (What this snippet introduces):** 1. `<h1 className="headline">`: Declarative JSX syntax written by the developer. 2. `jsx('h1', ...)`: Compiled JavaScript function call creating an in-memory UI descriptor object. 3. `className`: Attribute transformed directly into a property on the props dictionary.
- [grounding] Leading Question: Why can't browsers read JSX directly?
  Confusion Point: If JSX looks like HTML, why can't we simply load it into a browser with a standard script tag?
  Scene & Repetition: Imagine saving an ordinary `.jsx` file to your desktop and double-clicking it. The browser opens a blank white page. The developer console displays an unhandled SyntaxError: Unexpected token `<`. Why? Because web browsers are built to parse HTML and standard JavaScript, but JSX is neither. It is a syntax extension. If you do not run a **compiler** to transform every tag into a JavaScript function call, the browser chokes on the very first bracket. The compiler transforms your markup into plain JavaScript objects before the browser ever sees it.
  Key Terms (Bold): `**JSX**`, `**syntax extension**`, `**compiler**`.
  Resolution: Browsers cannot parse JSX natively because it is not standard JavaScript; a build tool compiler must transform every tag into function calls first.

### The Three Strict Syntax Rules of JSX
- [p] ◇ {preknowledge:} In plain HTML5, browsers are extremely forgiving: you can omit closing tags on `<img>` or `<input>`, you can write `class="card"`, and you can place multiple top-level elements side by side. In React, the compiler enforces three non-negotiable syntax rules. {problem:} Developers who paste HTML directly into JSX trigger immediate build failures if they violate any of these three invariants. ◼ Pedagogical qualification: Frame the three syntax invariants of JSX; terms introduced: **single root rule**, **self-closing tag**, **camelCase attributes**.
- [p] ★ Rule 1: Return a Single Root Element. A component function cannot return multiple adjacent elements without a single enclosing parent. Why? Under the hood, JSX compiles into JavaScript function calls. In JavaScript, a function cannot return two values at once: writing `return a, b;` returns only `b`. Returning `<header /><p />` is equivalent to returning `jsx('header'), jsx('p')`, which is invalid JavaScript grammar. Every returned JSX snippet must be wrapped in a single parent tag. ◼ Pedagogical qualification: Connect the single root rule directly to the return semantics of JavaScript functions.
- [p] ★ Rule 2: Close All Tags Explicitly. In HTML, certain tags known as void elements (such as `<img>`, `<input>`, `<br>`, and `<hr>`) never require a closing slash. In JSX, every tag must be explicitly closed. You must write `<img src="..." />`, `<input type="text" />`, or `<br />`. If you leave any tag unclosed, the compiler parser cannot determine where the element's children end, triggering a fatal syntax error. ◼ Pedagogical qualification: Explain the XML-strict closing requirement for void elements.
- [p] ★ Rule 3: camelCase Most Attributes. In HTML, attributes use lowercase or hyphenated names like `class`, `for`, `tabindex`, and `stroke-width`. In JSX, attributes become keys inside a JavaScript object: `jsx('div', { className: 'card' })`. Because words like `class` and `for` are reserved keywords in JavaScript (`class Component` and `for (;;)`), React uses `className` and `htmlFor` instead. All standard DOM properties use camelCase: `tabIndex`, `autoFocus`, `strokeWidth`. As an exception, `aria-*` and `data-*` attributes remain hyphenated to match web accessibility and data specifications. ◼ Pedagogical qualification: Explain why reserved JavaScript keywords necessitate `className` and `htmlFor`; establish camelCase naming across attributes.
- [code] Symmetrical syntax comparison:
```jsx title="JSX Rules Comparison"
<div className="card">
  <img src="news.jpg" alt="Harbor" /> // Self-closing tag satisfies **PARSER**
  <h2 className="title">Strike Enters Day 2</h2> // camelCase attribute avoids reserved **KEYWORD**
</div>
```
◼ **Code Self-Audit (What this comparison shows):** 1. Self-closing slash `/>`: Validated JSX tag closure. 2. `className`: Idiomatic JavaScript property name for DOM element class.

- [grounding] Leading Question: Why className instead of class in JSX?
  Confusion Point: Why did React invent `className` instead of letting developers write `class` like standard HTML?
  Scene & Repetition: Imagine you write `class="news-banner"` inside your component. In JavaScript, `class` is not just an attribute name: it is a sacred reserved keyword used to define object-oriented classes. Because JSX compiles directly into a JavaScript object (`{ class: "news-banner" }`), early JavaScript parsers threw fatal syntax errors when unquoted reserved words appeared as property keys. Even though modern JavaScript allows unquoted reserved keys, React standardized on **className** to match the browser's own DOM property (`element.className`). This is why you must write **className**: it prevents collisions with JavaScript keywords and matches the native DOM property directly.
  Key Terms (Bold): `**className**`, `**reserved keyword**`, `**DOM property**`.
  Resolution: `className` avoids collisions with the JavaScript `class` keyword and maps 1:1 to the browser's native `element.className` DOM property.

### Step 1: First, we construct the parent container ArticlePreview.jsx
- [p] ★ {preknowledge:} In React, the parent container defines the layout and dictates how children are grouped. {problem:} Wrapping children in a `<div>` breaks external CSS grid or flexbox rules. ◼ Pedagogical qualification: Construct parent using Fragment shorthand `<>...</>`.
- [code] Parent container ArticlePreview:
```jsx title="ArticlePreview.jsx"
import Headline from './Headline.jsx';
import StoryExcerpt from './StoryExcerpt.jsx';
export default function ArticlePreview({ title, text }) {
  return (
    <>
      <Headline title={title} /> // Mounts headline without extra wrapper **DIV**
      <StoryExcerpt text={text} /> // Mounts excerpt as direct sibling in **DOM**
    </>
  );
}
```
◼ **Code Self-Audit (What this snippet introduces):** 1. `<>`: Opening Fragment shorthand. 2. `</>`: Closing Fragment shorthand. 3. `<Headline />`: Contract for first child. 4. `<StoryExcerpt />`: Contract for second child.

### Step 2: Next, we build the heading child Headline.jsx
- [p] ★ {preknowledge:} Step 1 established the contract: `Headline` expects an incoming `title` prop. {problem:} The child component must render a semantic heading using valid JSX attributes. ◼ Pedagogical qualification: Fulfill child contract; enforce `className`.
- [code] Heading child component:
```jsx title="Headline.jsx"
export default function Headline({ title }) {
  return <h2 className="headline-text">{title}</h2>; // Renders heading with camelCase **CLASSNAME**
}
```
◼ **Code Self-Audit (What this snippet introduces):** 1. `Headline`: Functional component receiving title prop. 2. `className="headline-text"`: camelCase attribute. 3. `{title}`: Dynamic text expression.

### Step 3: Then, we declare the excerpt child StoryExcerpt.jsx
- [p] ★ {preknowledge:} Step 1 also established the contract for `StoryExcerpt`, which receives the `text` prop. {problem:} The child must render clean markup with self-closing void elements. ◼ Pedagogical qualification: Fulfill second child contract; enforce tag closure.
- [code] Excerpt child component:

}

◼ **Code Self-Audit (What this snippet introduces):** 1. `StoryExcerpt`: Functional component receiving text prop. 2. `className="story-excerpt"`: Standard JSX attribute.

- [grounding] Leading Question: Why does an extra div break flexbox and tables?
  Confusion Point: Why can't we just use a `<div>` every time the compiler asks for a single root?
  Scene & Repetition: Imagine you have a CSS flex container: `.feed { display: flex; gap: 20px; }`. Flexbox applies its spacing and alignment strictly to its immediate child elements. When your component returns a wrapper `<div>`, that wrapper becomes the flex child, while your headline and excerpt become grandchildren. The layout collapses. Worse, inside an HTML `<table>`, placing a `<div>` between `<tr>` and `<td>` violates the HTML specification, causing browsers to eject your content into a broken position outside the table. This is why you need a **Fragment**: it satisfies the single root rule while rendering zero wrapper nodes in the physical DOM.
  Key Terms (Bold): `**Fragment**`, `**single root rule**`, `**wrapper div**`.
  Resolution: Fragments satisfy React's single-root requirement while leaving the physical DOM tree completely free of extra container nodes.
- [callout] > [!TIP]
**To impress the interviewer:** When asked why JSX requires a single root element, explain the underlying JavaScript mechanism: JSX tags compile into `jsx()` function calls. In JavaScript, a function cannot return multiple expressions without wrapping them in an array or parent structure. A Fragment compiles into a call that tells React to render a list of children directly into the parent container without creating an unnecessary DOM wrapper.

### Where you will meet this
- News feed cards: grouping an article thumbnail and summary text inside a Fragment so they align cleanly as direct children of a CSS Grid layout.
- Table row components: rendering multiple `<td>` table cells from a single child component without inserting an illegal `<div>` inside a `<tr>`.
- Form field pairs: grouping a `<label>` and `<input>` together with a Fragment so custom form CSS can control their vertical rhythm without wrapper nodes.
- List rendering with keys: mapping an array of stories to adjacent title and excerpt tags using `<Fragment key={story.id}>` to maintain list identity.

### Glossary
- [glossary] JSX ◼ A syntax extension for JavaScript that allows developers to write HTML-like markup inside JavaScript component files.
- [glossary] Single Root Rule ◼ The syntactic requirement that every JSX expression must be enclosed in exactly one top-level element or Fragment.
- [glossary] Fragment ◼ A React component that groups a list of children without adding an extra node or wrapper to the physical browser DOM.
- [glossary] Self-Closing Tag ◼ A tag that closes itself with a trailing slash (`<tag />`), mandatory in JSX for elements without children.
- [glossary] camelCase Attributes ◼ The naming convention used for JSX properties to prevent collisions with reserved JavaScript keywords like class and for.
- [glossary] Keyed Fragment ◼ An explicit Fragment component imported from React that accepts a key prop during list rendering.

Treat JSX as strict JavaScript syntax rather than permissive browser HTML.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Every tag must be explicitly closed, including void elements like img and input.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use camelCase attribute names like className and htmlFor to avoid collisions with JavaScript reserved words.

- [always-rule] ➔ ALWAYS wrap adjacent sibling elements in a Fragment `<>...</>` to avoid unnecessary wrapper div soup.
- [if-then-rule] ➔ IF you need to pass a key to a group of sibling elements in a list THEN **import and use the explicit Fragment component**.
- [do-this-header] **DO THIS:** Wrap adjacent elements in a Fragment and use camelCase attributes with self-closing tags.
