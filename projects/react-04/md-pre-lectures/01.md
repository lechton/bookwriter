### The Imperative DOM Hunt vs Declarative React
- [p] ◇ In plain web development, a webpage is an HTML document loaded into browser memory. The browser parses that HTML into an object tree called the **Document Object Model (DOM)**. When you write plain JavaScript, your code talks directly to this tree: you search for specific nodes, read their current contents, and overwrite their values. ◼ Educational objective: introduce the physical DOM object tree; term introduced: **Document Object Model (DOM)**.
- [p] ★ {preknowledge:} We know that a browser provides querying methods like `document.getElementById` and `document.querySelector` to find elements in the DOM tree, and properties like `textContent` to overwrite their text. {problem:} As an application grows, user data rarely stays in a single location on screen. Elena's name appears across the top navigation bar, the article byline, the comments drawer, and the checkout receipt. In plain JavaScript, you must write manual search-and-replace instructions for every single appearance. If your script forgets even one element, the screen falls out of synchronization with memory. This failure is called **state drift**, and it leads to confusing bugs that erode user trust. ◼ Educational objective: establish the foundational pain of manual DOM scripting; terms introduced: **imperative programming**, **state drift**.
- [p] ★ {old solution:} Developers wrote manual update functions that executed long sequences of DOM lookups whenever data changed. ◼ Educational objective: deconstruct the imperative approach at the code level; term introduced: **imperative programming**.
- [code] Historical Pattern:
```js title="Historical Pattern"
function updateMastheadUser(newName) {
  document.getElementById('user-banner').textContent = newName; // Manual write to **BANNER** node
  document.getElementById('user-avatar').title = newName;       // Manual write to **AVATAR** attribute
  document.querySelector('.welcome-msg').textContent = newName; // Query by class misses second **WIDGET**
} // Unhandled '#subscriber-pill' causes **STATE DRIFT**
```
◼ **The what-this-introduces list:** 1. `document.getElementById`: manual retrieval of a specific DOM node by ID. 2. `textContent`: direct imperative mutation of node text content. 3. `document.querySelector`: CSS selector query requiring exact class naming. 4. Unhandled element: demonstrating how manual omission causes state drift.
- [p] ★ {preknowledge:} To update complex interfaces, developers frequently reached for container-level mutations using `innerHTML`. {problem:} When you assign a new HTML string to `innerHTML`, the browser engine destroys all existing child DOM nodes and constructs entirely new ones from scratch. This total teardown wipes active input cursor focus, resets text selection ranges, and cancels running CSS transitions. {new solution:} React solves this through lightweight in-memory tree comparisons called the **virtual DOM**. Instead of destroying physical nodes, React diffs your component's new description against the previous tree in memory. It calculates the exact difference and surgically patches only the changed text nodes, preserving active element focus and browser state. ◼ Educational objective: deconstruct the engine mechanics of innerHTML focus destruction vs virtual DOM diffing; terms introduced: **innerHTML**, **virtual DOM**, **reconciliation**.
- [p] ◇ {new solution:} React replaces manual hunting with **declarative UI**. What is **declarative UI**? React draws the line between two models of web development: **imperative DOM scripting**, controlled by manual step-by-step commands, and **declarative UI**, controlled by React from a single state description. In normal JavaScript, you command the browser: find this node, change its text, find that image, change its title. In declarative React, you describe what the user interface should look like for any given data: you write your component once, hand it the data, and React calculates which DOM nodes must change. The law of declarative UI: React updates the DOM to match your component description, and you never touch physical DOM nodes by hand. ◼ Educational objective: deliver the default and the law for declarative programming; terms introduced: **declarative UI**, **declarative programming**.
- [grounding] the opening question: **What is the problem with updating the physical DOM?** the friction it clears: why manual DOM querying inevitably causes state drift and broken user interfaces. Scene & Repetition: Elena Vance updates her account to Elena Rostova; her name appears in ten places across The National Times newsroom. In plain JavaScript, you must hunt down each and every element by hand. You write query after query. If you miss just one place, the old name remains on screen. This is the core problem of **imperative programming**: it is **imperative** to hunt down and update every DOM node manually, time and time again. This manual hunt leads to silent failures and broken screens. React solves this friction with **declarative** components: you declare your markup once, and React synchronizes the entire **physical DOM** automatically using its in-memory **virtual DOM**. ◼ Aha moment: permanently dissolve the illusion that manual DOM scripting is simpler by demonstrating catastrophic synchronization drift.

### Components as Reusable Blueprints
- [p] ◇ In plain HTML, you structure documents using native tags like `<header>`, `<article>`, and `<button>`. However, native HTML tags know nothing about your application logic, subscriber tiers, or live newsroom data. Traditionally, developers had to copy and paste chunks of HTML structure across separate templates and attach external JavaScript files to add behavior. This separation split structure from logic, producing fragile codebases where changing a CSS class broke JavaScript event listeners. ◼ Educational objective: explain the historical fragmentation of HTML and JavaScript; term introduced: **separation of concerns**.
- [p] ◇ To solve this fragmentation, React unifies markup, style, and logic into a single cohesive structure. This mechanism is called a **component**. What is a **component**? A component is a self-contained, reusable JavaScript function that accepts input data called **props** (short for properties) and returns a description of the user interface using JSX syntax. In React, every component function name must start with a capital letter. **Capitalization** is a strict compiler requirement: `<SiteHeader />` tells React to invoke your custom JavaScript function, while lowercase `<header>` tells the browser to create a built-in DOM element. ◼ Educational objective: unpack the component primitive across its educational dimensions; terms introduced: **component**, **props**, **capitalization**, **JSX**.
- [callout] > [!KEY] A component is a blueprint, not a building. When your component function executes, it does not construct physical DOM nodes; it returns a lightweight description of what the screen should look like, and React constructs the DOM nodes for you. ◼ Key takeaway: establish the blueprint mental model early.
- [p] ★ {preknowledge:} In JavaScript, functions receive arguments and return values. In React, a component function receives a single JavaScript object containing all its passed attributes, called `props`. Inside the component, curly braces `{}` act as an **evaluation window** that steps out of static markup and into live JavaScript execution. {problem:} When child components receive data, developers face two syntactic choices for reading incoming properties. ◼ Educational objective: decode JSX evaluation curlies and set up the pedagogical crossroad; terms introduced: **evaluation window**, **object destructuring**, **props passing**.
- [p] To read this data inside a component, you have two options: - **Option 1 (The foundational way)**: Receive the full `props` object as an argument, then access variables with dot notation (`props.readerName`). - **Option 2 (The modern idiomatic way)**: Unpack variables directly in the parameter list using JavaScript object destructuring (`{ readerName }`). ◼ Pedagogical crossroad declaration: Option 1 vs Option 2.
- [code] Option 1: The Foundational Way (props.readerName):
```jsx title="Option 1: The Foundational Way (props.readerName)"
export default function ReaderGreeting(props) { // Receives complete **PROPS** object
  return <h2>Welcome back, {props.readerName}</h2>; // Reads readerName via **DOT NOTATION**
}
```
◼ **The what-this-introduces list:** 1. `props`: single object holding all attributes passed from parent. 2. `props.readerName`: dot notation property access.
- [p] ★ In Option 1, React passes the full props object into the function. This is the mechanical reality of how React works under the hood. However, repeating `props.` across multiple elements adds visual clutter. ◼ Educational objective: unpack mechanical reality of Option 1.
- [code] Option 2: The Modern Idiomatic Way ({ readerName }):
```jsx title="Option 2: The Modern Idiomatic Way ({ readerName })"
export default function ReaderGreeting({ readerName }) { // Unpacks readerName via parameter **DESTRUCTURING**
  return <h2>Welcome back, {readerName}</h2>; // Reads readerName directly as **LOCAL VARIABLE**
}
```
◼ **The what-this-introduces list:** 1. `({ readerName })`: parameter destructuring extracting prop directly. 2. `{readerName}`: clean local variable access.
- [p] ★ In Option 2, JavaScript unpacks the variable directly at the function boundary. The component body stays clean, and the function signature explicitly documents which props it consumes. ◼ Educational objective: unpack ergonomic advantage of Option 2.
- [p] ◇ Components can be **nested** inside one another like building blocks. A top-level parent component coordinates layout and passes data downward, while focused child components render individual sections. To see this in action on The National Times, we organize our site header into three distinct files: (a) The parent component `SiteHeader.jsx` acts as the orchestrating container. (b) The child component `ReaderGreeting.jsx` renders the personalized welcome message. (c) The child component `SubscriberInfo.jsx` displays the subscriber tier details. Both child components receive the subscriber's name through the prop `readerName` passed directly from their parent. ◼ Educational objective: introduce component nesting and set up the practical example files; terms introduced: **component nesting**, **parent component**, **child component**.

### Step 1: First, we construct the parent container SiteHeader.jsx
- [p] Step 1 establishes the architectural layout: Notice how `SiteHeader` declares the single source of data in the variable `currentReader = 'Elena Rostova'`. Look at lines 6 and 7: `<ReaderGreeting readerName={currentReader} />` and `<SubscriberInfo readerName={currentReader} />`. We have not coded `ReaderGreeting` yet, but right here in the parent, we establish its contract: the parent passes the reader's name downward as an explicit prop named `readerName`. Mind you, hardcoding markup in a single file is tempting for small demos, but splitting into focused components allows greeting logic and subscriber badges to evolve independently; to recap this step: the parent owns the data and dictates child contracts before any child is implemented. ◼ Narration beats: notice-move on lines 6 and 7, props unpacked, warning against monoliths, recap of top-down data flow.
- [code] SiteHeader.jsx:
```jsx title="SiteHeader.jsx" startLine="1" continues="bottom"
import ReaderGreeting from './ReaderGreeting.jsx';
import SubscriberInfo from './SubscriberInfo.jsx';
export default function SiteHeader() {
  const currentReader = 'Elena Rostova'; // Single source of truth for **IDENTITY**
  return (
    <header className="site-header">
      <ReaderGreeting readerName={currentReader} /> {/* Passes reader identity as **PROP** */}
      <SubscriberInfo readerName={currentReader} /> {/* Shares same reader identity with **SIBLING** */}
```
◼ **The what-this-introduces list:** 1. `currentReader`: local constant acting as the single source of truth. 2. `readerName={currentReader}`: prop binding passing data from parent to child. 3. `<ReaderGreeting />` & `<SubscriberInfo />`: mounting child components with explicit contracts.

### Step 2: Next, we build the personalized child component ReaderGreeting.jsx
- [p] Step 2 fulfills the greeting contract: Notice how the function signature `ReaderGreeting({ readerName })` uses JavaScript object destructuring to unpack the exact prop name dictated by `SiteHeader.jsx` in Step 1. Inside the `<h2>` tag, the curly braces around `{readerName}` open an evaluation window that inserts the string straight into the heading. What would happen if `ReaderGreeting` tried to query the DOM directly? If you wrote `document.getElementById('user-name')` here, the component would crash if rendered before the element exists, or pick up stale text from another page. By receiving data strictly through props, `ReaderGreeting` owns zero DOM queries and zero side effects; to recap this step: data flows strictly downward from parent to child, and the child renders pure markup from props. ◼ Narration beats: notice-move on destructuring, evaluation window, Negative Counterfactual on DOM queries, recap of pure props rendering.
- [code] ReaderGreeting.jsx:
```jsx title="ReaderGreeting.jsx"
export default function ReaderGreeting({ readerName }) { // Destructures readerName from **PROPS**
  return (
    <div className="reader-greeting">
      <h2>Welcome back, <span className="reader-name">{readerName}</span></h2>
    </div> // Evaluates live readerName inside **JSX**
  );
}
```
◼ **The what-this-introduces list:** 1. `({ readerName })`: parameter destructuring extracting prop from props object. 2. `{readerName}`: JSX evaluation window projecting live JavaScript variable into markup. 3. `span.reader-name`: styled text wrapper for user identity.

### Step 3: Then, we declare the subscriber tier child component SubscriberInfo.jsx
- [p] Step 3 fulfills the subscriber tier contract: Notice that `SubscriberInfo` receives the exact same `readerName` prop from `SiteHeader.jsx`. Both children now read from the same single source of truth in the parent, making synchronization drift physically impossible. What would happen if `SubscriberInfo` maintained its own copy of the reader name? If Elena updated her profile, the greeting would update while the subscriber badge remained stale, reintroducing the exact bug that plagued our vanilla script. Because both siblings derive from the parent's data, changing `currentReader` in Step 1 updates both children in the exact same render; to recap this step: sibling components share data by receiving props from a common parent. ◼ Narration beats: notice-move on shared prop, Negative Counterfactual on duplicated state, recap of single source of truth.
- [code] SubscriberInfo.jsx:
```jsx title="SubscriberInfo.jsx"
export default function SubscriberInfo({ readerName }) { // Reads readerName to verify active **STATUS**
  return (
    <div className="subscriber-info">
      <span className="badge">Premium Member</span>
      <span className="reader-meta">Subscribed as {readerName}</span>
    </div> // Synchronizes badge label with parent **STATE**
  );
}
```
◼ **The what-this-introduces list:** 1. `SubscriberInfo({ readerName })`: child receiving shared parent prop. 2. `span.badge`: visual status pill indicating subscriber tier. 3. `Subscribed as {readerName}`: secondary visual element guaranteed to stay in sync with greeting.

### Step 4: Finally, we seal the header boundary with the live status indicator
- [p] Step 4 completes the parent container: We return to `SiteHeader.jsx` to seal the outer `<header>` boundary with a live edition status pill and an interactive account button. Notice how `startLine="7"` continues the file cleanly from Step 1. The button and badge are terminal UI controls that complete the editorial masthead. Mind you, adding interactive buttons in plain HTML requires attaching event listeners with `addEventListener`; in React, interactive controls remain declarative parts of the component hierarchy; to recap this step: the parent container closes its markup, sealing the component boundary. ◼ Narration beats: notice-move on continuation attributes, terminal UI controls, recap of complete component boundary.

- [p] ◇ When developers transition from plain JavaScript to React, their naive expectation is to treat components as simple HTML templates with embedded DOM selectors. They expect to write `document.querySelector` to update the greeting when a user changes their name. What the experiment showed is that React completely eliminates DOM queries: the parent holds data in memory, passes it downward through props, and React updates all matching elements on screen simultaneously. ◼ Educational objective: contrast naive imperative expectation against declarative reality.
- [p] ★ What would happen if `SiteHeader` did not split greeting and subscriber details into child components, and instead hardcoded a 100-line monolithic HTML string? ### Glossary
- [glossary] Component ◼ A self-contained, reusable JavaScript function that accepts props and returns a description of the user interface using JSX.
- [glossary] Declarative UI ◼ A programming paradigm where developers describe what the UI should look like for any given data, and the framework automatically updates the DOM to match.
- [glossary] Imperative DOM Scripting ◼ A programming approach where developers write manual step-by-step instructions to find, create, and mutate physical browser DOM elements.
- [glossary] Props ◼ Short for properties; a single JavaScript object passed from a parent component to a child component to supply input data.
- [glossary] JSX Evaluation Window ◼ The curly braces `{}` syntax inside JSX that steps out of static markup and evaluates a live JavaScript expression.

- [review-subtitle] ❒ Core Architectural Concepts
- [numbered-review-point] 1. **Declarative Synchronization vs Manual DOM Hunting**: In plain JavaScript, updating the screen requires finding and mutating physical DOM nodes by hand, which inevitably causes state drift as the app grows.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) React inverts this model: you describe the interface as a function of data, and React calculates the required DOM updates.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) You never touch physical DOM nodes with `document.getElementById` or `document.querySelector` in routine component code.
- [numbered-review-point] 2. **Components as Reusable Blueprints**: A component is a JavaScript function whose name starts with a capital letter and whose return value is JSX markup.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Capitalization is mandatory: `<SiteHeader />` invokes a custom React component, while `<header>` creates a native browser DOM element.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Components compose together into a tree, allowing complex user interfaces to be assembled from small, focused building blocks.
- [numbered-review-point] 3. **Unidirectional Props Flow**: Data flows strictly downward from parent components to child components through props.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) A child receives props as an immutable input object, commonly unpacked using parameter destructuring `({ readerName })`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Sibling components share data by lifting that data into their nearest common parent, ensuring all siblings stay synchronized.
- [never-rule] ➔ NEVER query or mutate physical DOM nodes with `document.querySelector` or `textContent` to update component UI.
- [always-rule] ➔ ALWAYS capitalize component names so React distinguishes custom components from native HTML elements.
- [if-then-rule] ➔ IF two sibling components need the same piece of data, THEN pass that data downward as props from their common parent.
- [do-this-header] **DO THIS:** pass data downward through props and render with JSX evaluation curlies
- [do-this-code]
```jsx right
export default function SiteHeader({ readerName }) {
  return <header><h1>The National Times</h1><span>{readerName}</span></header>;
}
```
- [do-not-do-this-header] **DO NOT DO THIS:** query physical DOM nodes by ID to update user interface text
- [do-not-do-this-code]
