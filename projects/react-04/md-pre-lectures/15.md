### The One-Way Data Flow Contract and the Upward Communication Problem
- [p] ◇ {preknowledge:} In earlier lessons, we learned that React components are JavaScript functions that receive props and return JSX markup (see Lecture 3). We also learned that props are strictly read-only: a component can never modify the props it receives from its parent (see Lecture 8). In plain HTML and vanilla JavaScript DOM scripting, any script on the page can query any element and overwrite its properties or change global variables at will (see Lecture 1). {problem:} Developers transitioning from plain JavaScript often expect a child component to directly update its parent's variables, only to find that modifying props throws errors or fails to update the user interface. ◼ Pedagogical qualification: Ground the foundational read-only props contract; introduce the need for upward communication; terms introduced: **one-way data flow**, **read-only props**.
- [p] ★ {preknowledge:} In React, data moves through the component tree like water flowing down a waterfall: an ancestor component passes props downward to its children, and those children pass props downward to their own children (see Lecture 12). Now imagine a user clicks a button at the very bottom of that component tree. The user wants the entire page layout or article list to update. But the child component does not own the article list, does not own the active filter, and cannot rewrite its parent's variables. {problem:} If the child attempts to reassign a prop or reach directly into parent memory, component purity is violated (see Lecture 13), React cannot detect the mutation, and the interface becomes completely broken. ◼ Pedagogical qualification: Unpack the physical waterfall model of one-way data flow; explain the conflict between downward data flow and upward interaction.
- [p] What is a **callback prop**? React resolves the tension between downward data flow and upward user events by drawing a line between two kinds of props. One is the **data prop**, which carries values like strings, numbers, and arrays downward from parent to child. The other is the **callback prop**, which carries a function reference downward so a child can request an action. In normal HTML, when you click a native button, the element handles its own inline event or triggers a global script, and no parent component coordinates the interaction. When you leave an element like that, code scatters across global scope. In React, you take that coordination into the parent: you write `<FilterButton onSelect={handleSelect} />`. The button receives a function reference. It can only notify the parent by invoking that function, and the parent dictates how state updates. The law of callback props states: a child component can never modify its parent's data directly; it can only invoke a callback prop passed down to it by the parent, ensuring that data flow remains strictly unidirectional. ◼ Pedagogical qualification: Deliver the full definition shape: reader's question as headline, both sides of contrast named, plain-world default sentence, React takeover, closing law sentence; terms introduced: **callback prop**, **data prop**.
- [code] MutatingPropsAntiPattern:
```jsx title="MutatingPropsAntiPattern"
function BrokenFilterButton({ activeCategory, category }) {
  function handleClick() {
    activeCategory = category; // **WRONG:** mutates local prop binding; parent never hears about it
  }
  return <button onClick={handleClick}>{category}</button>;
}
```
◼ **The what-this-introduces list:** 1. `BrokenFilterButton`: child component demonstrating the illegal prop mutation anti-pattern. 2. `activeCategory = category`: direct reassignment of a prop parameter that leaves the parent unchanged. 3. `onClick={handleClick}`: handler triggering an ineffective local mutation.
- [p] ★ {preknowledge:} In `BrokenFilterButton`, the child receives `activeCategory` as a prop. When the user clicks the button, `handleClick` executes and assigns `category` to `activeCategory`. However, props are local parameter bindings inside the child function. Reassigning `activeCategory` merely overwrites a local variable; it never touches the parent's memory, never triggers a re-render in the parent, and leaves the rest of the application completely unaware of the user's action. {bridging:} To allow the child to notify the parent, the parent must pass a function reference downward, which the child invokes when the event occurs. ◼ Pedagogical qualification: Explain the mechanical failure of prop reassignment; bridge to the callback prop solution.
- [code] CallbackPropPattern:
```jsx title="CallbackPropPattern"
function FilterButton({ category, onSelect }) {
  return <button onClick={() => onSelect(category)}>{category}</button>; // **RIGHT:** invokes callback prop with **PAYLOAD**
}
```
◼ **The what-this-introduces list:** 1. `FilterButton`: child component accepting a callback prop. 2. `onSelect`: callback prop carrying the parent's function reference. 3. `() => onSelect(category)`: inline arrow handler passing the category payload upward.
- [grounding] the opening question: How does a child talk back to a parent?
  the friction it clears: why a child invoking a parent function does not violate one-way data flow.
  Scene & Repetition: Imagine a newsroom telephone. The managing editor sits in the central office on the top floor, and a field reporter stands on the street corner. The editor cannot reach down through the window to tap the reporter's shoulder, and the reporter cannot climb up the fire escape to write directly on the editor's whiteboard. What does the editor do? The editor hands the reporter a telephone with a direct line to the office. When breaking news happens, the reporter dials that telephone line and speaks into it: "Category is politics!" The reporter does not write on the whiteboard. The reporter speaks into the line, and the editor writes on the whiteboard. In React, a **callback prop** is that telephone line: the parent passes a function reference down to the child, and the child calls that function to notify the parent, preserving **one-way data flow**.
  Key Terms (Bold): **callback prop**, **one-way data flow**, **inverse data flow**, **props**.
  Resolution: A child talks back by calling a function passed down from above, so data still flows downward while action messages travel upward.

### Inverse Data Flow: Passing Payloads and Naming Conventions
- [p] ◇ {preknowledge:} In JavaScript, functions are first-class values: you can assign functions to variables, pass them as arguments to other functions, and return them from functions. In earlier lessons, we saw that React event handlers like `onClick` and `onChange` accept function references (see Lecture 14). {problem:} Beginners often struggle to understand how a child can pass information back up to a parent if props only point downward. ◼ Pedagogical qualification: Ground first-class functions; introduce parameter passing through callbacks; terms introduced: **first-class functions**, **inverse data flow**.
- [p] ★ {preknowledge:} When a parent component passes a function to a child under a prop like `onSelect`, the function retains access to the parent's lexical scope and state setters. When the child executes `onSelect(category)`, it passes an argument into that function call. {bridging:} Even though the function was called from inside the child, it executes in the parent's environment. The data passed as an argument travels upward from child to parent. The React community calls this architectural pattern **inverse data flow** (or upward event flow): data flows down through props, and user actions flow up through callbacks. ◼ Pedagogical qualification: Trace the closure execution of callbacks; define inverse data flow with dual-canon terminology.
- [p] In professional codebases, developers follow a strict naming convention to keep data props and callback props instantly distinguishable: (a) The callback prop name on the child begins with `on` followed by the capitalized event name, such as `onSelect`, `onFilterChange`, or `onDeleteStory`. This prop name describes what event happened from the child's perspective. (b) The handler function in the parent begins with `handle` followed by the capitalized event name, such as `handleSelectFilter`, `handleFilterChange`, or `handleDeleteStory`. This function name describes the action the parent takes when notified. The split creates clarity: inside the parent, you write `<FilterButton onSelect={handleSelectFilter} />`, where `onSelect` is the prop contract and `handleSelectFilter` is the concrete implementation. ◼ Pedagogical qualification: Deliver the lettered four-part anchor for naming conventions: kind-name, short reminder, contents, consequence.
- [grounding] the opening question: Why does React forbid two-way data binding?
  the friction it clears: why two-way binding creates untraceable bugs while inverse data flow keeps state predictable.
  Scene & Repetition: Imagine a busy newspaper printing press where ten different journalists can walk up to the printing plate and carve changes directly into the metal type with their own chisels. One journalist changes a headline, another erases a paragraph, and a third rewrites a name. When the morning paper prints with a glaring typo, who made the mistake? Nobody knows, because everyone had direct write access! This is the chaos of **two-way data binding**: when any component can mutate state anywhere, bugs become impossible to trace. React stops this chaos with **one-way data flow**: only the parent component owns the printing plate, and children must submit change requests through **callback props**.
  Key Terms (Bold): **two-way data binding**, **one-way data flow**, **callback props**, **inverse data flow**.
  Resolution: React requires callback props so every state change flows through a single predictable owner, making state updates completely traceable.

### Lessons from the Experiment: Naive Expectation vs Reality
- [p] ◇ {preknowledge:} Developers new to React instinctively assume that child components should be able to directly modify their parents, or that sibling components should be able to pass data sideways to each other without parent intervention. {problem:} This naive expectation leads to tangled state architectures, hidden dependencies between distant components, and impossible-to-debug state mutation bugs. ◼ Pedagogical qualification: Contrast the naive expectation of direct component mutation with React's unidirectional architecture.
- [p] ★ {preknowledge:} In our experiment, `FilterButton` needed to change which category was selected. However, `FilterButton` does not render the articles; `ArticleFeed` renders the articles. If `FilterButton` held the active category in local state, `ArticleFeed` could never see it. If `FilterButton` directly mutated a variable in `NewsPage`, React's reconciler would never be notified to re-render the feed. {bridging:} By placing state in the closest common ancestor (`NewsPage`) and passing callback props downward, React keeps data flow strictly unidirectional while enabling dynamic user interactions across sibling components. ◼ Pedagogical qualification: Explain the architectural necessity of lifting state and using callback props to coordinate siblings.

### The Architectural Trade-offs of Callback Props and Prop Drilling
- [p] ◇ {preknowledge:} When a component tree is shallow, passing a callback prop from a parent to a child is simple and explicit. However, in large applications, components often sit five or six levels deep inside nested layouts, sidebars, and panels. {problem:} When an intermediate component does not care about a callback prop but must receive it and pass it down just so a deeply nested child can reach it, developers encounter **prop drilling**. ◼ Pedagogical qualification: Introduce the architectural trade-off of deep callback propagation; terms introduced: **prop drilling**.
- [p] ★ {preknowledge:} In our experiment, `CategoryNav` sat between `NewsPage` and `FilterButton`. It received `onSelectFilter` from `NewsPage` and passed it down to `FilterButton`. In a small layout with one intermediate layer, this explicit wiring is clean and self-documenting: anyone reading `CategoryNav` sees exactly what props flow through it. {bridging:} However, if a callback must pass through ten layers of containers that never use it, prop drilling creates boilerplate and makes refactoring cumbersome. In later lessons, we will learn how React Context solves deep propagation (see Lecture 30). But for adjacent components and shallow hierarchies, callback props remain the most performant, explicit, and reliable pattern in React. ◼ Pedagogical qualification: Frame the boundary between callback props and Context; establish when callback props are the right tool.
- [tip] To impress the interviewer: When asked how child components notify parents, explain that callback props are not an exception to one-way data flow; they are an application of it. In JavaScript, functions are first-class values. Passing a function down through a prop is still one-way data flow: the function reference flows down. When the child invokes the function, it triggers code in the parent's scope. This is called **inverse data flow**. ◼ Senior interview positioning.

### Glossary
- [definition] **Callback Prop**: A prop that accepts a function reference from a parent component, allowing a child component to notify the parent or send data upward when an event occurs.
- [definition] **Inverse Data Flow**: The pattern where data flows strictly downward through props, but user actions and notifications flow upward by invoking callback functions passed down from ancestors.
- [definition] **One-Way Data Flow**: The architectural principle in React where data travels strictly from parent to child through read-only props, preventing unintended mutations and ensuring state changes are predictable.
- [definition] **First-Class Functions**: The programming language feature in JavaScript where functions are treated like any other value, allowing them to be stored in variables, passed as arguments, and returned from functions.
- [definition] **Prop Drilling**: The practice of passing props through intermediate components that do not need them, solely to deliver those props to deeply nested children.

### Summary
- [review-title] **Child-to-Parent Communication with Callback Props in React**
- [p] In production applications, callback props establish the communication bridge between child components and their parent containers without violating React's fundamental one-way data flow. Here is your streetwise review.
- [review-subtitle] ❒ Core Principles of Callback Props and Inverse Data Flow
- [numbered-review-point] 1. Maintain **one-way data flow** by passing function references downward as props.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Props are strictly read-only; child components can never modify parent state or props directly.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Passing a function down allows the child to invoke parent logic while keeping state ownership in the parent.
- [numbered-review-point] 2. Follow the standard **naming convention** for callback props and handlers.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Use `on[Event]` for callback prop names on child components (such as `onSelect` or `onChange`).<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use `handle[Event]` for the corresponding handler functions defined in the parent (such as `handleSelect`).
- [numbered-review-point] 3. Pass payload data upward as **arguments to the callback**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) The child supplies event arguments (such as a selected category or input text) when invoking the callback.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) The parent handler receives those arguments and updates its state, initiating a re-render cycle.
- [never-rule] ➔ NEVER reassign or mutate a prop directly inside a child component.
- [always-rule] ➔ ALWAYS pass a function reference to callback props, using an inline arrow function if arguments are required.
- [if-then-rule] ➔ IF a child needs to trigger a parent state change THEN **pass a callback prop from the parent and invoke it in the child**.
- [do-this-header] **DO THIS:** Pass a callback prop downward and invoke it with an argument when the user interacts.
- [do-this-code] ProperCallbackPattern implementation:
```jsx right title="Proper Callback Pattern"

- [do-not-do-this-header] **DO NOT DO THIS:** Never attempt to mutate props directly or reassign parameters to change parent data.

```
