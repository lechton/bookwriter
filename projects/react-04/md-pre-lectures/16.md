### Why Ordinary Local Variables Fail: Retention and Triggering
- [p] ◇ {preknowledge:} In earlier lessons, we learned that React components are regular JavaScript functions that calculate and return JSX markup (see Lecture 3). We also learned that component rendering must remain completely pure and free of side effects (see Lecture 13). When you want a component to track changing numbers or text, your natural instinct as a JavaScript developer is to declare a local variable with `let`, such as `let count = 0`, and increment it inside an event handler (see Lecture 14). {problem:} Developers often expect that reassigning an ordinary local variable will automatically update what the user sees on screen. ◼ Pedagogical qualification: Ground the familiar local variable pattern; introduce the concept of component memory; terms introduced: **local variable**, **render pass**, **component function**.
- [p] ★ {preknowledge:} In plain JavaScript DOM scripting, you could mutate a global or module variable and manually write the updated value into the DOM with `element.textContent = count` (see Lecture 1). Now imagine clicking a button in React that executes `count = count + 1`. The variable in memory changes from 0 to 1. But two critical failures occur: first, changing a local variable never tells React to run the component function again. React never hears about your change, so no new JSX is computed and the screen remains frozen. Second, even if another interaction forces the component to re-render, the function executes again from line 1, wiping the local variable back to `let count = 0`. {problem:} Ordinary variables fail on both necessary requirements: they do not trigger renders, and they do not persist across renders. ◼ Pedagogical qualification: Unpack the dual failure modes of ordinary variables; contrast transient stack execution against reactive triggering.
- [p] The broken pattern using an ordinary local variable:
- [code] BrokenCounter implementation:
```jsx title="BrokenCounter"
export default function BrokenCounter() {
  let count = 0; // local variable declared on every execution
  function handleClick() {
    count = count + 1; // **WRONG:** mutates local variable; React never hears about it
  }
  return <button onClick={handleClick}>Bookmarks: {count}</button>;
}
```
◼ **The what-this-introduces list:** 1. `let count = 0`: ordinary local variable initialized on every render. 2. `count = count + 1`: mutation that fails to notify React. 3. `<button onClick={handleClick}>`: event handler modifying dead local memory.
- [p] What is `useState`? React resolves this failure by drawing a strict boundary between two kinds of variables: the **ordinary local variable**, which belongs to the transient JavaScript call stack, and **component state**, which belongs to React's persistent memory. In normal JavaScript, a local variable exists only while the function runs: when the function finishes, the engine pops its execution frame and the variable vanishes from memory. If you call that function a second time, the engine allocates a brand new variable initialized from scratch. In React, when you define data through `useState`, you hand ownership of that data to React: you write `const [count, setCount] = useState(0)`. React preserves that value outside the component function, in its internal fiber tree, across every single render pass. The law of useState states: a component can only preserve interactive data and trigger visual updates through the useState hook; reading the state variable returns the frozen value for the current render, and only calling the state setter requests React to schedule the next render with a new value. In web development, a variable that automatically drives the screen when it changes is called a **reactive variable**, and that reactivity is where React got its name; React's own documentation simply calls it **state**. ◼ Pedagogical qualification: Execute the default and the law standard; reader's question, both sides of contrast, default sentence, takeover, closing law sentence, dual-canon terminology.
- [p] The corrected pattern using the `useState` hook:
- [code] CorrectCounter implementation:
```jsx title="CorrectCounter"
import { useState } from 'react';
export default function CorrectCounter() {
  const [count, setCount] = useState(0); // **RIGHT:** retains data across **RENDERS**
  function handleClick() {
    setCount(count + 1); // **RIGHT:** schedules a **RE-RENDER** with new value
  }
  return <button onClick={handleClick}>Bookmarks: {count}</button>;
}
```
◼ **The what-this-introduces list:** 1. `import { useState }`: importing the state hook primitive. 2. `const [count, setCount] = useState(0)`: array destructuring yielding state variable and setter. 3. `setCount(count + 1)`: setter invocation queueing a state update and scheduling a render.

  Scene & Repetition: Imagine a newsroom whiteboard in The National Times office. A reporter walks up to the whiteboard, writes down the number 0, and starts writing an article. At the end of the day, the janitor walks in, wipes the whiteboard completely clean, and turns off the lights. The next morning, the reporter walks in, sees an empty whiteboard, and is forced to write 0 all over again. That whiteboard is an **ordinary local variable**: every time the function runs, the board is wiped clean, and any number written on it is discarded. Now imagine that instead of writing on the whiteboard, the reporter deposits the number into a secure vault in the building's basement (the **fiber memory**). Every morning, the reporter asks the vault manager for the latest number. The vault never forgets, no matter how many times the office lights turn off.   Resolution: Ordinary variables live on the temporary stack and vanish after execution, while useState stores data in React's persistent fiber tree.

### How useState Remembers: Hook Queues and Fiber Memory
- [p] ◇ {preknowledge:} When you look at the syntax `const [count, setCount] = useState(0)`, you notice something peculiar: you pass an initial value `0`, but you pass no variable name or string identifier like `"count"`. When the component re-renders, you call `useState(0)` again with the exact same initial argument `0`. {problem:} How does React know to return the updated value `1` instead of resetting back to `0`? Does React inspect variable names or parse your function code? ◼ Pedagogical qualification: Formulate the reader's live question; expose the mystery of identifier-free hook calls.
- [p] ★ {preknowledge:} React does not parse function code or use magic variable reflection. Instead, React stores component memory outside your function, on an internal JavaScript object called a **Fiber node** (see Lecture 12). For each component instance mounted in the UI, React maintains an internal linked list of hook records. Each time your component calls `useState`, React inspects the current hook cell in that list. During the initial mount render, React creates a new cell, stores `0` as the memoized value, and creates the setter function. On subsequent re-renders, React does not read the initial argument `0` again; it simply returns the current value stored in that existing cell and advances its internal pointer to the next hook. {problem:} If the order of hook calls changes between renders, React points to the wrong cell and scrambles your component's memory. ◼ Pedagogical qualification: Deconstruct the Fiber node hook linked list; explain the internal cursor index in plain CEFR B2 English; terms introduced: **Fiber node**, **hook cell**, **memoizedState**, **call order**.
- [p] This internal pointer mechanism is why the **Rules of Hooks** exist: you must only call Hooks at the top level of your component function. You can never call `useState` inside loops, conditions, or nested functions. Why? Because React relies strictly on a **stable call order** to match each hook call to its corresponding memory cell. If a hook call sits inside an `if` block that only runs on certain renders, the pointer index shifts out of alignment, and a state variable for a headline might receive the value intended for a bookmark count.
- [grounding] the opening question: How does React remember without variable names?
  the friction it clears: why hooks do not need names and why the call order must never change.
  Scene & Repetition: Imagine a row of numbered post office boxes in a newsroom mailroom: box 1, box 2, and box 3. When the reporter walks in, they do not ask for "the box named headline." They simply open box 1 first, box 2 second, and box 3 third. As long as the reporter visits the boxes in the exact same order every single day, they always find the right mail. Box 1 always holds the headline, box 2 always holds the author, and box 3 always holds the count. This is how **`useState`** works: React stores your values in an ordered row of **hook cells**, and every render reads those cells in sequence. But imagine if on Tuesday, the reporter skips box 1 and opens box 2 first! Suddenly, the reporter reads the author's mail thinking it is the headline! This is why the **Rules of Hooks** demand a **stable call order**: calling hooks conditionally scrambles the boxes, while calling them unconditionally keeps every value in its proper slot.
  Key Terms (Bold): **`useState`**, **hook cells**, **Rules of Hooks**, **stable call order**.
  Resolution: React tracks hook state by its sequential position in an internal array, requiring an unconditional call order on every render.

### State Memory Behind the Scenes: The Fiber Cell Lifecycle
- [p] ◇ {preknowledge:} Now that we have seen `useState` in action, we can examine exactly what happens inside the browser when state changes. When your application first loads, React mounts your component tree into the DOM (see Lecture 6). {problem:} How does React transition from the initial render to subsequent update renders without losing data? ◼ Pedagogical qualification: Introduce the runtime lifecycle of state; frame mount versus update phases.
- [p] ★ {preknowledge:} The lifecycle of component state moves through three distinct phases: (a) The mount phase (`mountState`) occurs when the component renders for the first time. React allocates a Fiber node, creates a new hook object, sets its `memoizedState` to the initial value `0`, and returns `[0, dispatch]`. (b) The dispatch phase occurs when the user clicks a button and your code calls `setCount(1)`. The setter dispatches an action that appends the update to the hook's update queue and requests the React scheduler to trigger a re-render. (c) The update phase (`updateState`) occurs when the component re-renders. React re-runs the component function. When it encounters `useState(0)`, it ignores the initial value `0`, evaluates the pending update queue, writes the new value `1` into `memoizedState`, and returns `[1, dispatch]`. {problem:} If you mutate state directly without calling the setter, React never enqueues the update and never schedules a render pass. ◼ Pedagogical qualification: Detail the three lifecycle phases of state; unpack mountState, dispatch, and updateState in CEFR B2 English.
- [tip] To impress the interviewer: When asked why ordinary variables forget and how `useState` remembers, do not just say "React re-renders." Give the senior two-part answer: First, ordinary variables live on the transient JavaScript execution stack, so they vanish when the function exits and cannot trigger renders. Second, `useState` stores data in the component's persistent Fiber node outside the function. Calling the setter queues an update and schedules a re-render, and on the next pass React uses stable hook call order to return the updated value from that fiber cell. ◼ Senior interview positioning.

### Glossary
- [definition] **useState**: A React Hook that declares a state variable, giving a function component private memory that persists across renders and triggers re-renders when updated.
- [definition] **State Variable**: The current value returned as the first element of the useState array, representing the state snapshot for the active render pass.
- [definition] **State Setter**: The updater function returned as the second element of the useState array, used to update the state value and schedule a re-render with React.
- [definition] **Fiber Node**: An internal React data structure that represents a component instance in memory and stores its persistent hook linked list outside the function stack.
- [definition] **Rule of Hooks**: The invariant requiring that Hooks be called only at the top level of function components, ensuring a stable, predictable call order on every render.

### Summary
- [review-title] **Persistent Component Memory with useState in React**
- [p] In production applications, understanding why ordinary variables forget and how `useState` remembers is the foundation of all interactive React engineering. Here is your streetwise review.
- [review-subtitle] ❒ Core Principles of Component State Memory
- [numbered-review-point] 1. Ordinary local variables fail because they cannot **retain** data or **trigger** renders.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) A function's local variables are discarded when execution finishes, resetting to their initial values on the next call.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Reassigning an ordinary variable never notifies React, leaving the on-screen user interface completely unchanged.
- [numbered-review-point] 2. The `useState` hook provides both **retention** and **triggering**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) React stores state variables in the component's persistent Fiber node, surviving across render cycles.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Calling the state setter function queues an update and schedules a re-render to paint new data on screen.
- [numbered-review-point] 3. React matches state to hook calls using a **stable call order**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Hooks have no string identifiers; React steps through an internal linked list of hook cells in sequential order.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Calling hooks conditionally or inside loops breaks the sequence, scrambling component memory.
- [never-rule] ➔ NEVER use ordinary local variables to track data that should update what appears on the screen.
- [always-rule] ➔ ALWAYS call `useState` at the top level of your component to preserve a stable hook call order.
- [if-then-rule] ➔ IF you need a component to remember changing values across user interactions THEN **declare them with `useState`**.
