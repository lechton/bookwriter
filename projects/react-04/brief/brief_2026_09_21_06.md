# Brief 2026-09-21 06: Universal Scenario De-Compounding, Reader Horizon, and Anti-Tautology Standard

## Group 1: Universal Scenario De-Compounding, Reader Horizon, and Anti-Tautology Standard (#2026_09_21_06_group_1)

### Philosophy and Defect Origin
During the refinement of Lecture 02 (`#project_setup`), three coupled pedagogical defects were identified in the `[!WILD]` friction card:
1. **Compound Scenario Jamming**: Staging two distinct applications with an appositive "or" (`"Imagine you are building an interactive subscriber widget or an offline-capable client dashboard"`). This crammed two separate products, audiences, and technical requirements into one breathless sentence.
2. **The Alien Concept Trap (Reader Horizon Violation)**: Attempting to explain a choice by creating a more complex mystery (`"Does your application need server-side rendering or database connections inside your view layer?"`). A Lecture 02 student has just learned JSX and has no concept of a "view layer" or full-stack database connections. Explaining early tools by dropping alien backend jargon causes severe cognitive dislocation.
3. **The Circular Tautology Fallacy**: Concluding an architectural trade-off with a tautology (`"If your application only needs to run in the browser, a web server is pure overhead"`). To a beginner, all web apps run in the browser; defining a client tool's purpose as "running in the browser" provides zero decision criteria.

### The Remediation & Standards
Under `#2026_09_21_06_group_1`:
1. **Universal Scenario De-Compounding**: All applications, use cases, and scenarios—whether hypothetical ("Imagine if...") or analytical ("Consider an internal tool...")—must be staged one by one with concrete human scale (`for thousands of daily readers`) and dedicated transitional framing (`Alternatively, what if you build...`).
2. **The Reader Horizon Law**: Authors are strictly forbidden from justifying or contrasting early tools by invoking alien downstream concepts outside the student's current curriculum stage. Contrasts must stay anchored to physical realities already understood (static files, browser execution, and local development machines vs continuous cloud web servers).
3. **The Anti-Tautology & Concrete Decision Criteria Law**: Trade-offs must never be explained by restating category definitions. Authors must provide concrete, observable operational decision criteria:
   - What requirement is absent? (e.g. public search engines never need to index private tools behind a login; users do not need pre-rendered HTML before an interactive widget loads).
   - What operational burden is eliminated? (e.g. no 24/7 cloud server hosting bills, no monitoring crashed Node processes, zero backend server maintenance).
