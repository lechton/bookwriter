Lecture 39: Extracting and Reusing Stateful Logic with Custom Hooks

Interview Question

CORE

How do you extract and reuse stateful logic between components?

Imagine this scenario:

  1. A developer named Marcus builds an editorial newsroom workspace for The National Times website.
  2. Two separate components need network status: a status bar displaying connection health, and a draft button that disables saving when offline.
  3. Marcus copy-pastes identical useState and useEffect blocks into both components, but updating event cleanup in one file leaves the other out of sync.
  4. How do you extract and reuse stateful logic between components?
  5. If you duplicate logic across components, bug fixes drift apart and maintenance costs multiply. If you assume custom hooks share state, you introduce severe data bugs.
  6. Both components call the exact same hook function, yet updating the state in one component never modifies the state of the other.
  7. Today you learn how to extract custom hooks, how React allocates hook memory to individual fiber nodes, and how to share logic cleanly without sharing state.

Component Architecture and the Logic Extraction Divide

In earlier lessons, we learned that React components maintain local state using useState and synchronize with external browser APIs using useEffect (see Lecture 1 and Lecture 28). In an editorial desk, components often need to observe the same external browser condition, such as whether the device is currently online or offline. Developers often assume that because two components need the exact same reactive behavior, they must either copy-paste the code or lift state to a distant parent container.

In plain JavaScript, when two functions need the same calculation, you extract a shared helper function. In React, however, a standard helper function cannot call useState or useEffect. If you copy-paste the hook calls directly into both NetworkStatusBar and SaveDraftButton, both files maintain identical lines of setup, subscription, and cleanup code. Duplicating stateful logic creates state drift: fixing a missing event listener or correcting an event type in one file leaves the second file broken.

Look at the code above: to give NetworkStatusBar access to the browser's online status, we had to declare a local state variable and write an effect with two event listeners and two cleanup calls. If another component, such as SaveDraftButton, needs that exact same network status, a developer following this pattern copy-pastes those exact nine lines into the second file. Now your project has eighteen lines of low-level subscription boilerplate across two files. If you ever update the event handler or add a reconnection ping, you must remember to edit both files by hand.

What is a custom hook? In standard JavaScript, an ordinary utility function can compute values, format dates, or transform arrays, but it has no memory and cannot participate in React's component lifecycle. When you write an ordinary function, it executes once and discards all local variables when it returns. A custom hook takes that standard JavaScript function and authorizes it to call other React hooks inside its body. You write a function whose name starts with use, such as function useOnlineStatus() and place useState and useEffect inside it. The custom hook encapsulates the stateful recipe: it tells React how to declare state, how to subscribe to external browser events, and what value to return to the caller. The law of custom hooks is absolute: a custom hook shares the stateful logic and lifecycle recipe, but it never shares state itself; each component calling the hook receives its own completely isolated state cell in memory.

⚡ IN THE WILD

Does a custom hook share state between components? Imagine two pastry chefs in two separate kitchens baking sourdough bread. They both open the exact same cookbook to page forty and follow the exact same recipe. Does that mean they share the same loaf of bread? Of course not. Chef Elena mixes her own flour, water, and yeast in her kitchen bowl. Chef Marcus mixes his own flour, water, and yeast in his kitchen bowl. If Marcus burns his loaf in the oven, Elena's loaf is completely unharmed. This is the difference between sharing a recipe and sharing the food. A custom hook is a recipe for stateful logic. When NetworkStatusBar calls useOnlineStatus(), it bakes its own private component state. When SaveDraftButton calls useOnlineStatus(), it bakes its own private component state. They share the recipe for subscribing to the browser, but their state remains completely independent.

Step 1
First, we construct the parent container EditorialDesk.jsx

We start our implementation at the top: the parent container EditorialDesk.jsx.

We begin here because the parent establishes the layout of the newsroom desk. Notice that it mounts both child components without passing any network-related state or callbacks:

Look at line 2: const handleSave = () => console.log('Draft saved') The parent declares the action handler that persists the reporter's article draft.

Now look at lines 5 and 6: <NetworkStatusBar /> and <SaveDraftButton onSave={handleSave} /> Notice what is deliberately absent: there is no isOnline state declared in this parent container, and zero network props passed downward.

We could have declared const [isOnline, setIsOnline] = useState(true) right here in EditorialDesk and passed isOnline down to both children. But lifting state to this parent would be a serious architectural flaw. Why? Because every time the device's internet connection flickered, this entire parent container and all its unrelated child views would re-render. By leaving the parent lean, we keep its rendering cost at zero. Each child will subscribe to the network on its own terms.

To recap this first step: the parent provides the structural layout, leaving network synchronization entirely to the child boundaries.

Step 2
Next, we extract the custom hook useOnlineStatus.js

In step 2, we extract the reusable stateful logic into our custom hook: useOnlineStatus.js.

Notice the function name begins with the mandatory lowercase prefix use. This prefix authorizes the function to call React's built-in hooks:

useOnlineStatus.js
1import { useState, useEffect } from 'react';
2export function useOnlineStatus() {
3 const [isOnline, setIsOnline] = useState(navigator.onLine);

5 function updateStatus() {
6 setIsOnline(navigator.onLine);

7 }
8 window.addEventListener('online', updateStatus);
9 window.addEventListener('offline', updateStatus);

Look at line 3: const [isOnline, setIsOnline] = useState(navigator.onLine) We read the browser's native navigator.onLine property to establish our starting state. If the device is connected when the component mounts, isOnline starts as true.

Now examine the useEffect call starting on line 4. Inside the effect, we define a small helper function updateStatus that reads navigator.onLine and passes the fresh boolean to setIsOnline. We attach this helper to two native window events: online and offline. Whenever the operating system detects a network change, the browser dispatches one of these events, and our helper synchronizes our state variable immediately.

Now let us complete the custom hook by adding its cleanup function and returning the boolean state:

11 return () => {

Look at lines 11 to 14: the effect returns a cleanup callback that removes both event listeners from the window object. This cleanup callback is essential. Without it, every time a component calling this hook unmounted, its event listeners would remain attached to the global window, leaking memory and executing stale setters in the background.

Finally, look at line 16: return isOnline Notice that we return only the boolean value, not the setter setIsOnline. The custom hook manages its own state updates internally in response to browser events. Components that consume this hook need to know whether the network is active, but they have no business manually overriding that status.

To recap this step: the custom hook encapsulates state declaration, event subscription, and cleanup into a single reusable function returning a clean boolean.

To recap this step: calling a custom hook lets a component consume complex stateful logic in a single, readable line of code.

Now look at line 5: disabled={!isOnline}. When isOnline is false, the browser natively disables the button, preventing click events and showing a dimmed visual style. The button text also switches dynamically from "Save Draft" to "Reconnecting...".

Look at the button click handler on line 5: onClick={onSave}.

Where does onSave come from? Look back at Step 1 in EditorialDesk.jsx. The parent declared const handleSave = () => console.log('Draft saved') and then rendered: <SaveDraftButton onSave={handleSave} />

Notice what happened: the parent handed its private handler function handleSave to the child under the prop name onSave. SaveDraftButton does not own the saving logic or article content, and it does not know where the draft is stored. It only holds a telephone line called onSave.

When the reporter clicks the button, the native browser onClick fires and calls onSave(). Because onSave points directly to handleSave, that call immediately executes handleSave() back in EditorialDesk.

This is standard inverse data flow: data flows down through props (disabled={!isOnline}), and user actions flow up through callbacks (onSave).

Here is the central lesson: even though SaveDraftButton and NetworkStatusBar call the exact same hook, their state is completely independent. Calling useOnlineStatus() twice creates two separate state variables in React's memory. If you unmount NetworkStatusBar, SaveDraftButton continues to function with zero disruption.

To recap this step: multiple components can call the same custom hook to reuse its logic, while each component retains its own isolated state.

Lessons from the Experiment: Naive Expectation vs Reality

When developers first encounter custom hooks, their naive expectation is that calling a custom hook acts like a global store or shared singleton, connecting all calling components to a single shared state variable. This naive expectation leads to deep confusion when an update in one component fails to trigger re-renders in other components calling the same hook.

In our newsroom experiment, both NetworkStatusBar and SaveDraftButton called useOnlineStatus(). When the browser fired an online event, both components updated simultaneously. However, they did not update because they shared state. They updated because each component had its own independent isOnline state variable, and both happened to receive the same external browser event at the exact same millisecond. Conflating shared logic with shared state causes developers to create buggy custom hooks when managing user-driven state like form inputs or modal toggles.

The Fiber Node Memory Model: Why Custom Hooks Do Not Share State

To truly understand why custom hooks do not share state, you must look at where React stores state in memory. In plain JavaScript, if two modules import a shared variable from a file, both modules read and write to that exact same variable in memory. Developers often assume that because a custom hook is declared in a single file (useOnlineStatus.js), the state inside that file behaves like a module-level variable.

In React, a custom hook owns zero memory of its own. A custom hook is not a component, not a class, and not an actor. It is simply a JavaScript function that executes inside the context of whichever component called it. When a component calls useOnlineStatus(), React looks at the fiber node currently being processed on the work loop. Calling useState inside a custom hook tells React: "allocate a new state cell on the currently executing fiber node." If two components call the hook, React creates two separate state cells on two separate fiber nodes.

⚡ IN THE WILD

Where does custom hook state actually live? Imagine a carpenter who owns a set of measuring tools. When the carpenter works on house number one, they use their ruler to measure a wooden door. When the carpenter works on house number two, they use the exact same ruler to measure a wooden window. Does house number two have a door because the carpenter used the same ruler? No. The ruler does not own the wood; the house owns the wood. The ruler is simply the tool used to shape it. A custom hook is like that ruler. The hook does not own any component state. When NetworkStatusBar calls the hook, React allocates the state inside NetworkStatusBar's fiber node. When SaveDraftButton calls the hook, React allocates the state inside SaveDraftButton's fiber node. The state lives inside the component, never inside the hook.

The use Prefix Convention and Linter Contract

In standard JavaScript, you can name a function anything you want: getOnlineStatus, calculateTotal, or syncNetwork. In React, however, any function that calls other React hooks must start with the lowercase prefix use, written in camelCase (such as useOnlineStatus or useWindowSize). Developers who name a custom hook with a standard prefix like getOnlineStatus encounter linter errors or mysterious runtime bugs.

React hooks rely on an internal invariant: hooks must be called in the exact same order on every single render. You cannot call hooks inside loops, conditions, or nested functions. Because React cannot inspect the internal body of every third-party function at compile time, it relies on the use prefix as an explicit syntactic contract. The use prefix signals to the React linter that this function contains hook calls and must obey the Rules of Hooks. If you name it getOnlineStatus, the linter assumes it is an ordinary function, allowing developers to call it inside an if statement and corrupting React's internal hook linked list.

When should a function be a custom hook versus an ordinary utility function? The rule is straightforward: (a) if the function calls at least one React hook (useState, useEffect, useContext, useRef), it must be named with the use prefix and treated as a custom hook; (b) if the function performs pure data transformation, string formatting, or mathematical calculation without calling any React hooks, it should be an ordinary utility function without the use prefix. Naming a pure function with use restricts it unnecessarily, preventing it from being called conditionally or inside loops.

Interview Tip

To impress the interviewer: When asked how custom hooks work under the hood, never say "they share state between components." State clearly that custom hooks share stateful logic, not state. Explain that hooks are pure syntactic composition: calling a custom hook executes its internal useState and useEffect calls directly against the calling component's current fiber node. Each component gets its own independent state cell in the fiber linked list. If you need to share state itself, you must either lift state to a common ancestor or use React Context.

Where you will meet this

  • Network connectivity monitoring (useOnlineStatus): Subscribing to browser online and offline events to display status banners and disable mutation buttons in offline-resilient applications.
  • Window dimensions and responsive breakpoints (useWindowSize): Listening to browser resize events to dynamically switch between mobile drawer navigation and desktop sidebar layouts.
  • Form input controllers and validation (useFormField): Encapsulating value state, change handlers, validation rules, and error messages across recurring input fields.
  • LocalStorage synchronization (useLocalStorage): Syncing a reactive state variable with browser storage so user preferences like dark mode or collapsed sidebars persist across page reloads.

Glossary

  • Custom Hook: A JavaScript function whose name starts with use that can call other React hooks, encapsulating reusable stateful logic and lifecycle synchronization for components.
  • Stateful Logic: The instructions, event subscriptions, and effect lifecycles that govern how state is declared, updated, and synchronized over time.
  • Fiber Hook Cell: An internal JavaScript object within a component fiber's linked list that stores the state value, memoized calculation, or effect cleanup for a specific hook call.
  • Rules of Hooks: The fundamental constraints governing hook execution: hooks must only be called at the top level of React function components or custom hooks, and never inside loops, conditions, or nested functions.
  • State Isolation: The core React guarantee that state declared by a hook belongs exclusively to the component instance that invoked it, remaining completely independent of other components calling the same hook.
  • Lifecycle Synchronization: The process of keeping React component state aligned with an external system, such as browser window events, network sockets, or hardware sensors, using effects.

Summary

Extracting and Reusing Stateful Logic with Custom Hooks

In production React applications, custom hooks allow developers to extract complex stateful logic and lifecycle subscriptions into clean, reusable modules without sharing state. Here is your streetwise review.

❒ Core Principles of Custom Hook Architecture
  1. Custom hooks share stateful logic, never state itself.
        (a) Each component that calls a custom hook receives its own independent state storage on its private fiber node.
        (b) Two components calling the same hook update independently unless both subscribe to the exact same external browser event.
  2. Hook names must always begin with the lowercase prefix use.
        (a) The use prefix informs React and linting tools that the function contains hook calls and must follow the Rules of Hooks.
        (b) Functions that do not call React hooks must not use the use prefix, allowing them to be called conditionally.
  3. Use custom hooks to eliminate copy-pasted effect boilerplate.
        (a) Encapsulate browser event subscriptions, timers, and storage listeners inside a single custom hook.
        (b) Keep component files focused on visual presentation rather than low-level event listener wiring.

➔ NEVER assume that calling a custom hook in two components shares a single state variable between them.

➔ ALWAYS name custom hooks starting with use so the linter can enforce the Rules of Hooks.

➔ IF a function does not call any React hooks THEN name it as a standard utility function without the use prefix.

DO THIS: Extract stateful logic into a custom hook and let each component call it independently.
