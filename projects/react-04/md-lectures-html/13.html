The Two Rules of Purity: Mind Your Own Business and Same Input, Same Output

In earlier lessons, we learned that a React component is a JavaScript function that receives props and returns JSX markup (see Lecture 3 and Lecture 8). In school mathematics, a formula like y = 2x is completely predictable: if x is 3, y is always 6, whether you calculate it today, tomorrow, or a thousand times in a row. In traditional JavaScript scripting, developers frequently write functions that reach outside their own bodies: they read global variables, mutate external objects, or rewrite DOM nodes while computing a value (see Lecture 1). When a function changes variables outside its own scope, executing that function multiple times produces completely different results, making user interfaces unpredictable and fragile.

What is a pure component? In computer science, React draws a strict boundary between a pure calculation and an impure routine. One is the pure component, governed by mathematical predictability; the other is the impure component, corrupted by side effects. In plain JavaScript, an ordinary function can modify any variable it can reach: it can increment a global counter, push an item into an array declared in another file, or write to the browser window object. When you write a React component that does this during render, React calls it an impure component. In a pure component, you give up external mutation entirely: you write a function that receives props, state, and context, and computes JSX without altering anything outside. The law of component purity states: a React component must always be a pure function; given the same inputs, it must always return the exact same JSX, and it must never change any object or variable that existed before rendering.

⚡ IN THE WILD

What does component purity really mean? Imagine ordering a cup of coffee at a newsroom cafe. Every time you ask for a black coffee, you expect a cup of black coffee. If the barista gives you black coffee on your first visit, but handing you the cup also secretly turns off the cafe lights, and on your second visit for the exact same order you get hot water because the beans were moved, the cafe is chaotic and broken. A pure function is like a reliable recipe: every single time you provide the exact same ingredients, you get the exact same dish, and preparing it never breaks a chair or rewrites the menu. In React, a pure component minds its own business: it uses its props to calculate JSX, and it never changes any outside variables during calculation.

Side Effects in Render: Global State Drift and StrictMode Double-Rendering

In earlier lessons, we saw that React applications re-render whenever state updates or parent components re-evaluate (see Lecture 12). In plain JavaScript scripts, running a script from top to bottom happens once when the page loads. In React, rendering is an ongoing rhythm: components execute again and again throughout the lifetime of the application. If a component performs a side effect during its calculation step, such as reading and writing a shared global variable, every re-render causes state drift, where values drift further away from reality on every screen refresh.

What is a side effect? A side effect is any observable change outside the current function call: modifying a global variable, rewriting a DOM node, starting a timer, or sending a network request. In React, there is a strict law about when side effects are permitted. The render phase of a component is strictly for calculation: it takes inputs and returns a tree of React elements (see Lecture 12). If you place side effects directly inside the body of your component function, you violate the render contract. React must be free to call your component function at any time, in any order, and as many times as necessary to keep the user interface synchronized. If calling your component changes the world around it, React cannot safely optimize, cache, or interrupt rendering.

To help developers detect accidental impurities before shipping code to production, React provides a built-in development audit tool called StrictMode. In development mode, whenever a component renders, StrictMode intentionally calls the component function twice in rapid succession with the exact same props. If your component is pure, calling it twice produces the exact same JSX, and the duplicate call is completely invisible to the user. But if your component mutates an external variable, like storyCount++, the first call increments the counter to 1 and the second call immediately increments it to 2! The screen shows double numbers instantly, exposing the hidden mutation bug on day one.

⚡ IN THE WILD

Why does React render components twice? Imagine a photographer taking a passport photo. To make sure the camera works properly, the photographer snaps two photos back to back. If you sit completely still, both photographs look identical. But imagine if taking the first photo accidentally knocked your glasses off your face! The second photograph now shows you without glasses. The two photos disagree! That disagreement proves that taking the photograph was not a neutral observation: it physically altered the subject. In React, StrictMode is that double snapshot: it renders your component twice in development to verify that rendering is a pure calculation. If your component has an accidental side effect, the two renders produce conflicting data, instantly catching the mutation bug before it reaches production.

Safe Local Mutation vs External Side Effects

In plain JavaScript, the word mutation means changing the properties of an object or the elements of an array after it has been created. When beginners hear that React components must be pure, they often believe that mutating any variable anywhere in their code is strictly forbidden. This misunderstanding leads developers to avoid simple local loops or array aggregations, writing overly complex code out of fear of mutation.

What is local mutation? React draws a clear line between two kinds of mutation: external mutation, which alters variables that existed before your component was called, and local mutation, which modifies variables created inside the same render call. Mutating an external variable is an illegal side effect: it changes the outside world and corrupts other components. In contrast, local mutation is completely safe and pure. When you write const items = []; inside your component function and then push items into that array using a for loop, no code outside that function can see or touch that array. When the component finishes running, the array is returned as part of JSX or discarded by garbage collection. The law of local mutation states: mutating objects, arrays, or variables created inside the current render is 100% pure; purity only forbids changing objects or variables that existed before the render started.

In React, local mutation inside your component body is completely pure, while external mutation corrupts shared memory across your entire application.

Where Side Effects Belong: Event Handlers and the Render Contract

In modern web applications, programs must eventually change things: save articles to a database, update user profiles, trigger animations, or show notifications. If components must be pure during render, where do these side effects actually belong? Beginners often place side effects like API requests, storage updates, or DOM changes directly in the component body because they want them to happen when the component appears on screen.

Where do side effects belong in React? Side effects belong in event handlers. An event handler is a function that runs in response to a user action: clicking a button, submitting a form, or typing into an input field (see Lecture 14 and Lecture 40). Unlike the component render function, event handlers do not run during rendering! They run after the render is finished, when the user physically clicks or types. Because event handlers do not participate in calculating JSX, they do not need to be pure. Inside an event handler, you can safely update state, send HTTP requests, write to local storage, or navigate to another page. The law of side effects states: rendering must remain a pure calculation with zero side effects; all mutations, network requests, and external modifications must be executed inside event handlers or dedicated effect escape hatches.

Interview Tip

To impress the interviewer: When asked why React demands purity, do not just recite "same inputs, same output." Explain the architectural benefits: purity allows React to safely re-render components without side-effect bugs, execute concurrent rendering by pausing and restarting renders without leaving corrupted state behind, skip rendering unchanged subtrees via memoization, and safely execute components on the server where shared globals would leak data between different users.

  • Breaking news alert banners: Deriving alert visibility and styling strictly from incoming alert data without modifying external window objects during render.

Glossary

  • Pure Component: A React component function that always returns the exact same JSX when given the same inputs and causes zero observable changes to the outside world during rendering.
  • Side Effect: Any observable change or mutation performed outside the scope of the current function call, such as modifying global variables, changing the DOM, or firing network requests.
  • StrictMode: A built-in React development tool that intentionally renders components twice to detect accidental impurities and side effects before code ships to production.
  • State Drift: The cumulative corruption of application state caused by components mutating external variables during repeated render passes.
  • Local Mutation: The modification of variables, arrays, or objects that were created inside the current render pass, which is completely pure because no external code can observe it.
  • Event Handler: A callback function executed in response to user interactions, which serves as the primary sanctioned location for performing side effects in React applications.

Summary

Component Purity and the Elimination of Side Effects in React

In production applications, component purity is the foundational contract that enables React's rendering engine, optimization algorithms, and concurrent features to function reliably. Here is your streetwise review.

❒ Core Principles of Component Purity
  1. Treat component rendering strictly as a pure calculation.
        (a) A component must always return the exact same JSX when provided with the same props, state, and context.
        (b) A component must never modify any object, array, or variable that existed before rendering started.
  2. Understand why StrictMode double-renders components in development.
        (a) Double-rendering exposes side effects by making accidental mutations visible as duplicated values on screen.
        (b) In production, React renders components once, but keeping them pure guarantees safe re-rendering.
  3. Distinguish between safe local mutation and dangerous external mutation.
        (a) Mutating arrays or objects created inside the current render pass is 100% pure because it has zero outside visibility.
        (b) Mutating variables in module scope or global scope causes state drift and unpredictable multi-user bugs.

➔ NEVER mutate an external variable, prop, or existing object during component render.

➔ ALWAYS derive display values strictly from incoming props, state, or freshly created local variables.

➔ IF you need to perform a mutation or network request THEN place that logic inside an event handler.
