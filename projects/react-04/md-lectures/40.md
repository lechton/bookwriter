### Component Architecture and the State Ownership Divide

In earlier lessons, we learned that React components maintain local reactive memory using the `useState` hook (see Lecture 1). When you build an interactive form, your immediate instinct is to store every character the user types inside a component state variable. Developers often assume that controlling every input is the only way to manage form data in React.

What is a **controlled input**? React draws a clear line between two kinds of inputs. One is the **controlled input**, governed by React. The other is the **uncontrolled input**, governed by the browser. In normal HTML, an input controls itself. When you type a letter, the browser stores that letter directly in its native C++ buffer and paints it on screen. No JavaScript is involved. When you leave an input like that, React calls it an **uncontrolled input**. In a controlled input, you take that power away from the browser. You write `<input value={query} onChange={(e) => setQuery(e.target.value)} />`. The input is now locked. It can only display whatever the state variable holds. React dictates every single character shown on screen.

Here is the minimal code comparison between the two approaches:

```jsx title="Controlled vs Uncontrolled"
<input value={query} onChange={(e) => setQuery(e.target.value)} /> // 1. Controlled: React dictates value via **STATE**
<input name="contributor" defaultValue="Elena Rostova" /> // 2. Uncontrolled: Browser holds text in native **DOM**
```

In a controlled input, you bind the `value` attribute to a state variable. You also attach an `onChange` listener to update that state on every keystroke. Now imagine typing the word hello into that field one letter at a time. Each keypress dispatches an event and updates state. React wakes the fiber reconciler. It re-runs the component function and recomputes the virtual DOM. Finally, it writes the updated string back into the DOM node. The component re-renders on every keystroke. The CPU recalculates the entire component tree five times just to type a five-letter word.

> [!WILD]
> **What does controlling an input really mean?** Imagine typing your name into a physical guestbook. In plain HTML, the pen writes directly onto paper, and the paper holds the ink. In a **controlled input**, you never write on the paper directly. Instead, you whisper each letter to an assistant named React. React writes the letter in its private notebook, erases the paper, and rewrites the letter for you. Type five letters, and React rewrites the paper five times. This gives React complete control over the paper. But whispering and rewriting on every keypress creates unnecessary overhead. In most forms, you only care about the finished name on submit. An **uncontrolled input** lets the browser hold the ink until you hand in the book.

### Step 1: First, we construct the parent container FeedbackPortal.jsx

We start our implementation at the top: the parent container `FeedbackPortal.jsx`.

We begin here because the parent defines the layout and dictates the data architecture for the entire view. It decides which piece of data needs reactive state and which piece stays completely uncontrolled:

```jsx title="FeedbackPortal.jsx"
import { useState } from 'react';
export default function FeedbackPortal() {
  const [query, setQuery] = useState(''); // **CODE LOGIC:**<br>Holds search state locally because filtering requires per-keystroke sync
  return (
    <main className="portal-layout">
      <LiveSearchInput query={query} onChange={setQuery} /> // **DATA FLOW:**<br>Passes state downward and setter callback for inverse flow
      <ArticleCorrectionForm /> // **DATA FLOW:**<br>Mounted with zero props; manages its own submission lifecycle
    </main>
  );
}
```

Look at line 3: `const [query, setQuery] = useState('')`. We declare state here because search filtering requires real-time synchronization on every keystroke.

Now look at line 6: `<LiveSearchInput query={query} onChange={setQuery} />`. We have not coded `LiveSearchInput` yet. But right here in the parent, we establish its contract. The parent owns the search text, and passes a callback so the child can report keypresses. We will build that child next in step 2.

Now look at line 7: `<ArticleCorrectionForm />`. Notice that it takes zero props, zero state, and zero callbacks. We could have declared state variables for the contributor name and commentary right here in `FeedbackPortal`. But that would be a serious design mistake. Why? Because every single letter typed into the commentary box would force this entire parent container and the child search input to re-render repeatedly. By giving it zero props, we isolate it completely. We will build that form in steps 3 and 4.

To recap this first step: the parent holds the shared state that child components need to coordinate, and leaves independent forms completely isolated.

### Step 2: Next, we build the controlled child LiveSearchInput.jsx

In step 2, we fulfill the contract established by the parent: we build `LiveSearchInput.jsx`.

This child component is responsible for the live search pill at the top of the portal:

```jsx title="LiveSearchInput.jsx"
export default function LiveSearchInput({ query, onChange }) { // **DATA FLOW:**<br>Receives active search query and updater callback from parent
  return (
    <input
      value={query} // **CODE LOGIC:**<br>Locks displayed text strictly to React state as single source of truth
      onChange={(e) => onChange(e.target.value)} // **DATA FLOW:**<br>Forwards typed character upward on every keystroke to update state
      placeholder="Filter by headline..."
      className="search-input"
    />
  );
}
```

Notice the function parameters: we destructure `{ query, onChange }` directly from props. That matches the contract we wrote in step 1. `LiveSearchInput` owns zero local state. It relies entirely on its parent to provide the search text and the function to update it.

Look at the input event handler on line 5: `onChange={(e) => onChange(e.target.value)}`.

Where does `onChange` come from? Look back at Step 1 in `FeedbackPortal.jsx`. The parent declared `const [query, setQuery] = useState('')`, and then rendered: `<LiveSearchInput query={query} onChange={setQuery} />`.

Notice what happened: the parent handed its private updater function `setQuery` to the child under the prop name `onChange`. `LiveSearchInput` does not own state, and it does not know what `query` is used for. It only holds a telephone line called `onChange`.

When the editor types a character, the native browser `onChange` event fires and calls `onChange(e.target.value)`. Because `onChange` points directly to `setQuery`, that call immediately executes `setQuery(e.target.value)` back in `FeedbackPortal`.

This is standard **inverse data flow**: data flows down through props (`query`), and user actions flow up through callbacks (`onChange`).

What would happen if `LiveSearchInput` declared its own local `useState` for the query?

If `LiveSearchInput` owned the query state locally, the parent `FeedbackPortal` and the headline news feed would have no way to access the query string without complex ref forwarding or state-lifting hacks. The search input would filter itself in isolation while the article feed remained completely unchanged.

By separating them, `LiveSearchInput` owns zero local state. It is a pure controlled presenter: given `query` and `onChange`, it displays the string and reports keystrokes.

This separation gives you two concrete superpowers:
1. If tomorrow you replace this text field with a voice-dictation search input, you touch zero lines of filtering logic in the parent.
2. If you change how the article feed filters stories (such as searching by author instead of headline), you touch zero lines of input code.

To recap this step: data flows down from the parent through `query`, and user events flow up through `onChange`.

### Step 3: Then, we declare the uncontrolled form ArticleCorrectionForm.jsx

In step 3, we build our second child component: `ArticleCorrectionForm.jsx`.

Remember how we mounted `ArticleCorrectionForm` in step 1 without any props? Here is why.

Think about how a reader uses this correction form.
They type their name. Then they write a few sentences of feedback.
While they are typing, React does not need to know a single letter.
We only need that text once: the moment they click submit:

```jsx title="ArticleCorrectionForm.jsx" startLine="1" continues="bottom"
export default function ArticleCorrectionForm() {
  async function handleSubmit(formData) { // **DATA FLOW:**<br>Receives native FormData dictionary containing all named inputs on submit
    const contributor = formData.get('contributor'); // **CODE LOGIC:**<br>Reads contributor name from native buffer with zero re-renders
    const commentary = formData.get('commentary'); // **CODE LOGIC:**<br>Harvests multi-line commentary only at submission time
    console.log('Correction submitted:', { contributor, commentary }); // **ACTION:**<br>Logs assembled payload with zero re-renders
  }
  return (
    <form action={handleSubmit} className="correction-form"> // **DATA FLOW:**<br>Action intercepts native submit and passes FormData package
      <input name="contributor" defaultValue="Elena Rostova" /> // **CODE LOGIC:**<br>Native input manages its own buffer with initial default value
      <textarea name="commentary" placeholder="Describe the correction..." />
```

Look closely at the markup inside the form. Notice what is missing: there is no `value` prop, no `onChange` listener, and not a single `useState` hook anywhere in this file.

Instead, notice `defaultValue="Elena Rostova"`. That sets an initial starting string when the input first mounts. From that moment on, the browser's native C++ engine takes over. It stores every typed character directly in its own buffer. When a reader types three paragraphs of feedback, React does not execute a single line of code. The component never re-renders.

Never forget to include the `name` attribute on every input. Notice we wrote `name="contributor"` and `name="commentary"`. Without a `name`, the browser has no key to associate with the value, and the data will be lost during submission.

Now look at `handleSubmit(formData)` at the top of the component. When submission happens, React 19 hands us a native `FormData` instance containing all named fields. We simply call `formData.get('contributor')` and `formData.get('commentary')` to extract the values.

Notice the contrast with step 2: in step 2, React synchronized every keystroke in real time. Here in step 3, React stays completely idle while the user types. It only harvests the data at the final moment of submission.

### Step 4: Finally, we seal the form with native action submission

In step 4, we complete `ArticleCorrectionForm.jsx` by adding the submit button and closing the form tag:

```jsx title="ArticleCorrectionForm.jsx" startLine="11" continues="top"
      <button type="submit">Submit Correction</button> // **DATA FLOW:**<br>Fires submit event to trigger native form action pipeline
    </form> // **CODE LOGIC:**<br>Form boundary isolates input typing from parent re-renders
  );
}
```

Notice the submit button on line 11. When the user clicks this button or presses Enter inside an input field, the browser fires a native submit event on the enclosing `<form>`.

In classic React, you had to attach an `onSubmit` handler to the form. You had to call `e.preventDefault()` to stop the page from reloading. Then you had to gather your form data manually.

Notice what we wrote on line 8 instead: `<form action={handleSubmit}>`. In React 19, passing an async function to `action` tells React to intercept the submission automatically. React prevents the page reload. It gathers the named inputs into `FormData`. Then it runs `handleSubmit` inside a background transition, so the rest of the page stays responsive.

The `<form>` boundary seals this entire workflow. It is completely self-contained. It collects its own data, triggers its own action, and never forces the parent container `FeedbackPortal` to re-render.

Let us recap the senior rule. Use controlled state when you need immediate, per-keystroke synchronization, such as live search filtering. Use uncontrolled `FormData` when you only care about the values at the moment of submission.

### The Per-Keystroke Latency Bottleneck

On a high-performance desktop computer, running a small component function five times while typing a word takes less than a millisecond. On a budget smartphone with a busy CPU, re-rendering a large component tree on every keystroke causes frame drops and sluggish typing latency. Controlling every input indiscriminately degrades user experience on low-end devices.

When an input is controlled, typing a character triggers a state update. That schedules work on the React fiber work loop. Now imagine the component tree contains fifty child components, complex charts, or heavy layout elements. React must reconcile that entire tree before the browser paints the newly typed character. If reconciliation takes more than 16 milliseconds, the frame drops. The user experiences input lag. Typed characters appear seconds after their fingers leave the glass.

Uncontrolled inputs bypass the React work loop completely while typing. The native browser engine handles character insertion in compiled C++. Typing stays at a solid 60 frames per second, no matter how large the React application is. You pay zero rendering cost until the user clicks submit.

> [!WILD]
> **Why does typing lag on mobile devices?** Imagine typing a message on your smartphone. You tap five keys quickly, but the letters appear on screen with a sluggish delay. Why? Because every single keypress forced React to re-render the entire page. The computer was busy recalculating layout trees, re-rendering sidebars, and diffing virtual DOM trees instead of simply painting the letter you typed. This is the **input latency** bottleneck of over-controlled forms. **Uncontrolled inputs** eliminate this lag completely. The browser handles text entry in native C++, and React stays completely idle until the user taps submit.

### The Senior Engineering Decision Matrix

Senior engineers do not choose between controlled and uncontrolled inputs based on habit or dogma. They evaluate the concrete functional requirements of the specific form control.

When should you choose controlled inputs? Choose controlled inputs when you need immediate, synchronous access to the field's value while the user is actively typing. Specifically:
- **Live Search Filtering**: Query strings that filter lists, tables, or autocomplete dropdowns on every keystroke.
- **Input Masking and Formatting**: Fields requiring immediate character formatting, such as phone numbers, dates, or currency strings.
- **Dynamic Field Dependencies**: Scenarios where typing in one field dynamically shows, hides, or disables another field.
- **Instant Character Counters**: Live feedback widgets such as password strength meters or remaining character counters.

When should you choose uncontrolled inputs with FormData? Choose uncontrolled inputs when you only need the field values at the moment of submission. Specifically:
- **Standard Data Collection Forms**: Contact forms, feedback submissions, user registration, and account profiles.
- **Large Multi-Field Forms**: Forms with dozens of fields where per-keystroke re-rendering causes performance bottlenecks.
- **Long-Form Text Editing**: Article authoring, commentary, and description fields where users type long paragraphs of text.
- **React 19 Form Actions**: Workflows leveraging modern form actions, automatic resets, and progressive enhancement.

> [!TIP]
> **To impress the interviewer:** When asked whether forms should be controlled or uncontrolled, never say "always control everything." Explain the architectural trade-off. Controlled inputs provide instant real-time synchronization, but they cause per-keystroke re-renders and boilerplate state. Uncontrolled inputs with `FormData` isolate typing from the React work loop. They deliver maximum performance and clean code for standard submit-only workflows.

### Where you will meet this

- Editorial correction forms: Collecting contributor names, emails, and multi-line correction notes using uncontrolled `FormData` for zero-lag text editing.
- Live article search filters: Synchronizing search query strings with controlled state to filter published headlines in real time as the editor types.

### Glossary

- **Controlled Input**: An input element whose displayed value is bound to a React state variable and updated synchronously via an onChange handler on every keystroke.
- **Uncontrolled Input**: An input element that stores its value in the native browser buffer, accessed on demand via a ref or harvested on form submission through FormData.
- **FormData**: A native browser object providing a key-value representation of form fields, populated automatically from named inputs upon form submission.
- **Single Source of Truth**: The design principle where application state lives in exactly one place (React state for controlled inputs, or the DOM for uncontrolled inputs).
- **Input Latency**: The delay between a physical keystroke on the keyboard and the visual rendering of the corresponding character on screen, exacerbated by per-keystroke component re-renders.
- **DefaultValue**: The initial value supplied to an uncontrolled input at mount time, allowing the browser to manage subsequent edits without React state intervention.

### Summary

**Controlled State versus Uncontrolled FormData in React Forms**

In production applications, choosing between controlled state and uncontrolled `FormData` defines both developer ergonomics and runtime rendering performance. Here is your streetwise review.

❒ Core Principles of Form State Architecture

1. Use **uncontrolled inputs with FormData** as your default strategy for standard submit-only forms.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Storing text in the native browser buffer eliminates per-keystroke re-renders and state boilerplate.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Named inputs are harvested automatically into a native `FormData` dictionary on submit.

2. Reserve **controlled inputs** for fields that require real-time synchronization during typing.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Live search filters, character counters, and input formatting masks require immediate access to every keystroke.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Binding `value` and `onChange` forces React to re-render on every keypress, creating input latency on large trees.

3. Protect mobile performance by avoiding **over-controlled forms**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Controlling dozens of fields in a single component causes cumulative layout recalculation and typing lag.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Keep inputs uncontrolled unless a specific real-time feature demands per-keystroke state.

➔ NEVER control an input if you only read its value when the user clicks submit.

➔ ALWAYS supply a `name` attribute to uncontrolled inputs so `FormData` can harvest them.

➔ IF you need real-time validation or live search filtering THEN **bind `value` and `onChange` with controlled state**.

**DO THIS:** Use uncontrolled inputs with `name` attributes and harvest values via `FormData` on submit.

```jsx right title="ArticleCorrectionForm.jsx"
export default function ArticleCorrectionForm() {
  async function handleSubmit(formData) {
    const contributor = formData.get('contributor');
    const commentary = formData.get('commentary');
    await saveCorrection({ contributor, commentary });
  }
  return (
    <form action={handleSubmit}>
      <input name="contributor" defaultValue="Elena" />
      <textarea name="commentary" />

    </form>
  );
}
```

**DO NOT DO THIS:** Never declare redundant state hooks and per-keystroke handlers for fields only read on submit.

```jsx wrong title="Over-Controlled Form Pattern"
export default function BadForm() {

  const [text, setText] = useState('');

    <form onSubmit={(e) => { e.preventDefault(); save({ name, text }); }}>
      <input value={name} onChange={(e) => setName(e.target.value)} />
      <textarea value={text} onChange={(e) => setText(e.target.value)} />

```
