### Why Hardcoded Components Fail: The Need for Dynamic Inputs

In earlier lessons, we learned that a React component is a JavaScript function that returns JSX markup describing what should appear on screen (see Lecture 3 and Lecture 4). When starting a new project, developers define component functions with hardcoded text and static HTML tags. If you build an action button with the text "Publish Story" hardcoded into its JSX return statement, every single copy of that button renders the exact same text. Creating separate component files like `PublishButton.jsx`, `DraftButton.jsx`, and `ArchiveButton.jsx` produces massive code duplication and maintenance friction.

What are **props**? In React, **props** (short for properties) are the configuration values that a parent component passes downward to a child component to customize its behavior and visual output. In plain HTML, native tags come with fixed, standardized attributes: an `<img>` tag accepts `src` and `width`, and an `<input>` tag accepts `type` and `value`. But native HTML tags cannot be taught new custom attributes, and plain JavaScript functions require manual invocation. In modern React, you declare custom parameters on your own component functions: you write `function ActionButton({ label, variant })` and mount it with `<ActionButton label="Publish Story" variant="primary" />`. React gathers every attribute into a single plain JavaScript object and passes it to your function. The law of props is absolute: props are strictly read-only inputs passed from parent to child, meaning a child can only read the props it receives and can never change them.

In plain JavaScript, calling a function with different arguments returns different results based on those inputs. When developers build static components, they hardcode text directly inside the function body, forcing them to copy and paste entire files just to change a word. In React, you turn hardcoded markup into an adaptable template by replacing static text with dynamic prop expressions inside curly braces (see Lecture 5).

```jsx title="ComponentReuseContrast"
export function HardcodedPublishButton() {
  return <button className="btn-primary">Publish Story</button>;
}
export function ActionButton(props) {
  return <button className={`btn-${props.variant}`}>{props.label}</button>;
}
```

Look at lines 1 to 3 in `HardcodedPublishButton`: the label "Publish Story" and the class name `btn-primary` are hardcoded into the markup. If you need a secondary button to save drafts, you are forced to copy and paste the entire function. Now look at lines 4 to 6 in `ActionButton(props)`: the component accepts a single argument called `props`. Instead of hardcoding words, it reads `props.variant` to construct the button styling and `props.label` to display the dynamic text.

When you pass data into a component, you choose between two input channels: (a) The string literal channel (`label="Publish Story"`) passes plain text directly inside double quotes, identical to traditional HTML attributes. (b) The dynamic expression channel (`count={42}`) wraps JavaScript numbers, booleans, variables, or objects inside JSX curly braces (see Lecture 5). The consequence of this distinction is complete flexibility: a single component blueprint can receive static text strings, computed numbers, or complex data structures without altering its internal markup.

> [!WILD]
> **What is the problem with copy-pasting components?** Imagine a printing press that stamps labels onto newspaper bundles. If the press could only print the word "Morning", you would need to build an entirely new steel machine just to print "Evening". You would need a third machine to print "Special Edition". That is what happens when you build hardcoded components: every tiny text variation forces you to copy and paste entire files. This copy-paste habit leads to fragile **code duplication** and maintenance chaos. **Props** turn your component into an adaptable stamp: the machine stays identical, but you supply the ink and wording dynamically.

### Passing and Reading Props: The Function Argument Pipeline

In earlier lessons, we learned that JSX is an extension to JavaScript that allows you to write HTML-like tags inside your scripts (see Lecture 4). When you write a tag like `<ActionButton label="Publish Story" />`, you are not writing native HTML elements; you are writing a declarative description that compiles to JavaScript.

What is the **props object**? Under the hood, JSX attributes compile directly into a single plain JavaScript object called **`props`**. In plain JavaScript functions, developers often pass multiple positional arguments like `createButton(text, color, size, icon)`. If a caller accidentally swaps the order of two strings, the button renders with the wrong color and label. In React, component functions always take exactly one argument: the `props` object. The law of the props object states: all attributes declared on a JSX tag become key-value properties on that single object, and React passes it directly as the first argument of the component function.

```jsx title="PropsSyntaxContract"
export function ActionButton(props) {
  return <button className={props.variant}>{props.label}</button>;
}
export function ModernButton({ label, variant = 'secondary' }) {
  return <button className={variant}>{label}</button>;
}
```

Look at line 1 in `ActionButton(props)`: the component accepts `props` as its single parameter, reading values with `props.label` and `props.variant`. Now look at line 4 in `ModernButton({ label, variant = 'secondary' })`: instead of typing `props.` repeatedly, modern React developers use JavaScript object destructuring directly inside the parameter parenthesis. Destructuring extracts the exact named properties you need into local variables in the function scope. Notice also `variant = 'secondary'`: JavaScript default parameter syntax ensures that if the parent omits the `variant` prop, the component falls back to a safe default styling.

Passing string values to props uses double quotes, exactly like HTML attributes. When beginners need to pass numbers, booleans, arrays, or objects, they frequently write `count="5"` or `isUrgent="true"`. Passing numbers inside quotes delivers a literal string to the component, which breaks mathematical operations like `count + 1` by producing `"51"` instead of `6`. Whenever you pass non-string values into a component, wrap them inside JSX curly braces (see Lecture 5): `<ActionButton count={5} isUrgent={true} />`.

> [!KEY]
> A component is a function, and props are its arguments.

When your component function runs, it does not invent its own incoming data. It receives a single object containing every attribute written by the parent, unpacks those properties, and returns JSX markup calculated strictly from those inputs. Just as a plain JavaScript function cannot choose what arguments its caller provides, a child component cannot dictate what props its parent passes downward.

> [!WILD]
> **Why does React bundle props into an object?** Imagine a restaurant kitchen. If the waiter shouted five different ingredients across the room in a specific order, one misheard word would ruin the dish. Instead, the waiter writes the entire customer order onto a single order ticket and clips it to the kitchen wheel. The ticket holds all instructions in one tidy package. In React, the **`props` object** is that order ticket. Instead of passing five positional parameters that could get mixed up, React packages every attribute into a single **`props` object**. The child component unclips the ticket and reads the exact instructions it needs.

> [!TIP]
> **To impress the interviewer:** When asked how props work in React, explain that JSX attributes are syntactic sugar for the single props argument passed to the component function. Highlight that props can carry any JavaScript value: primitives, arrays, objects, JSX elements, and functions. Emphasize that parameter destructuring with default values (`{ variant = 'secondary' }`) is the universal React standard because it makes component contracts self-documenting.

### Why Props Are Read-Only: Purity and Unidirectional Data Flow

In earlier lessons, we learned that React renders UI by calling component functions (see Lecture 3). When a component needs to change what appears on screen in response to user interaction, a beginner's instinctive reflex is to reassign its props: `props.label = "Saved"`.

What is **unidirectional data flow**? In React, **unidirectional data flow** (also called **one-way data flow**) is the architectural rule where data travels exclusively downward through the component tree, from parent to child. In traditional imperative scripting or two-way data-binding frameworks, a child can mutate variables shared with its parent, creating hidden side effects and state drift across unrelated screens. In modern React, the parent owns the data and passes read-only snapshots downward. The law of unidirectional data flow states: data flows strictly downward from parent to child through props, and a child component can never mutate the props it receives.

In JavaScript, plain objects are mutable by default: you can add, change, or delete properties on any ordinary object literal at any time. In React, components must behave like pure functions with respect to their inputs: given the same props, a component must always return the exact same JSX and produce zero side effects during rendering. If a child component were allowed to mutate `props.label = "Saved"`, it would silently modify the object stored in the parent's memory. To protect this boundary, React freezes the `props` object in development using `Object.freeze(props)`. When code tries to assign to a prop, JavaScript strict mode halts execution and throws a fatal TypeError: `Cannot assign to read-only property 'label' of object '#<Object>'`.

```jsx title="PropsImmutabilityContract"
function BrokenButton(props) {
  props.label = 'Saved'; // **WRONG:** Mutating frozen props throws fatal **TYPEERROR**
  return <button>{props.label}</button>;
}
function PureButton({ label }) {
  const display = label.toUpperCase(); // **RIGHT:** Computes **LOCAL** derived value
  return <button>{display}</button>;
}
```

Look at line 2 in `BrokenButton`: assigning directly to `props.label` attempts to mutate a frozen object. In modern React and JavaScript strict mode, this line crashes the application with a TypeError. Even in an environment without strict mode, mutating `props` does not tell React to re-render, creating silent **state drift** where the internal object changed but the screen never updated. Now look at lines 6 and 7 in `PureButton`: if you need a modified version of an incoming prop, calculate a new local variable during render. The incoming prop `label` remains completely untouched.

How do props change over time if they are immutable? Props are not static constants; a component may receive different props across different renders. Imagine an editorial clock or live story card: the parent component re-renders with new data from a timer or network request and passes a brand-new props object downward. The child component casts its old props object aside, and the JavaScript garbage collector reclaims that memory. The child then executes its function again with the new props snapshot, returning fresh JSX to match.

> [!WILD]
> **Why can a component never change its props?** Imagine a manager gives an accountant a signed financial budget on paper. The accountant's job is to calculate taxes based on that budget. What would happen if the accountant took an eraser, changed the budget numbers on the paper, and pretended the manager approved it? The company's financial records would be completely corrupted. In React, a child component is that accountant: the parent hands it a signed **read-only contract** in the form of **props**. If the child could mutate that paper, the parent's data and sibling components would silently corrupt. This is **component purity**: props are read-only inputs that guarantee predictable rendering across the entire application.

### Step 1: First, we construct the parent container EditorialDesk.jsx

We start our implementation at the top: the parent container `EditorialDesk.jsx`.

We begin here because the parent defines the layout and dictates the component contracts. It owns the story data dictionary and passes it downward as a prop to its child components:

```jsx title="EditorialDesk.jsx"
import StoryCard from './components/StoryCard.jsx';
export default function EditorialDesk() {
  const story = { id: 101, title: 'Metro Transit Strike Enters Day Three', author: 'Elena Vance', reads: 1420 }; // **CODE LOGIC:**<br>Declares immutable story data dictionary in parent memory
  return (
    <main className="desk-layout">
      <header className="desk-header">Editorial Workspace</header>
      <StoryCard story={story} /> // **DATA FLOW:**<br>Passes story data object downward as a read-only prop contract
    </main>);
}
```

Look at line 1: `import StoryCard from './components/StoryCard.jsx'`. We import `StoryCard` to mount it inside our layout.

Notice line 3: `const story = { id: 101, title: 'Metro Transit Strike Enters Day Three', author: 'Elena Vance', reads: 1420 }`. The parent container owns this data in local memory and acts as the single source of truth for the entire desk.

Now look at line 7: `<StoryCard story={story} />`. We have not authored `StoryCard.jsx` yet. But right here in the parent, we establish its contract: it receives the entire `story` object via props. We will build that child next in Step 2.

If you ever forget to pass the `story` prop when rendering `<StoryCard />`, React passes an empty object `{}` to the child. When the child attempts to read `story.title`, it encounters a fatal TypeError: "Cannot read properties of undefined". Always ensure required props match the child component contract.

To recap this first step: the parent container owns application data and establishes props contracts for child components in its returned markup.

### Step 2: Next, we build the card child StoryCard.jsx

In step 2, we fulfill the contract established by the parent: we build `StoryCard.jsx`.

This intermediate presenter component unpacks the story data and mounts two distinct copies of our reusable button:

```jsx title="components/StoryCard.jsx"
import ActionButton from './ActionButton.jsx';
export default function StoryCard({ story }) { // **DATA FLOW:**<br>Receives story prop downward fulfilling Step 1 contract
  return (
    <article className="story-card">
      <h2 className="story-title">{story.title}</h2> // **CODE LOGIC:**<br>Projects story headline into semantic heading markup
      <p className="story-meta">By {story.author}</p>
      <ActionButton label="Publish Story" variant="primary" /> // **DATA FLOW:**<br>Configures primary button instance with custom props
      <ActionButton label="Save Draft" variant="secondary" /> // **DATA FLOW:**<br>Configures secondary button instance using identical component
    </article>);
}
```

Look at line 2: `export default function StoryCard({ story })`. Notice the parameter destructuring `{ story }` matching the Step 1 contract.

Look at line 5: `<h2 className="story-title">{story.title}</h2>`. The component reads the story title directly from props and projects it into the heading.

Now look at lines 7 and 8: `<ActionButton label="Publish Story" variant="primary" />` and `<ActionButton label="Save Draft" variant="secondary" />`. Notice what happened: `StoryCard` uses the exact same `ActionButton` component twice. It gives the first copy `label="Publish Story"` with `variant="primary"`, and the second copy `label="Save Draft"` with `variant="secondary"`. We will build that button in Step 3.

What would happen if `StoryCard` mutated `story.title` directly?

If `StoryCard` executed `story.title = 'Breaking News'`, it would silently modify the object in the parent's memory without triggering a re-render. Other components reading that story object would display outdated text, causing state drift across the newsroom. By treating `story` as read-only, `StoryCard` owns zero global state and guarantees pure rendering.

This separation gives you two concrete superpowers:
1. If tomorrow you add a third action button to `StoryCard`, you touch zero lines of `EditorialDesk.jsx` code.
2. If you change how `EditorialDesk.jsx` acquires story data, you touch zero lines of button code.

To recap this step: intermediate presenter components unpack incoming props and configure nested child controls without mutating input data.

### Step 3: Then, we declare the button child ActionButton.jsx

In step 3, we build our reusable terminal control: `ActionButton.jsx`.

Rather than creating separate files for primary and secondary buttons, we define a single parameterized component:

```jsx title="components/ActionButton.jsx"
export default function ActionButton({ label, variant = 'secondary' }) { // **DATA FLOW:**<br>Destructures label and variant with fallback default
  return (
    <button className={`btn btn-${variant}`}> // **CODE LOGIC:**<br>Interpolates variant prop into dynamic CSS class name
      {label} // **DATA FLOW:**<br>Renders incoming label text inside native button node
    </button>
  );
}
```

Look at line 1: `export default function ActionButton({ label, variant = 'secondary' })`. Notice the parameter destructuring. We extract `label` and `variant` directly from the incoming props object.

Notice also `variant = 'secondary'`. That is a default prop fallback. If a parent renders `<ActionButton label="Preview" />` without specifying a variant, JavaScript automatically assigns `'secondary'` so the button always has a valid CSS class.

Look at line 3: `className={`btn btn-${variant}`}`. The component uses a template literal expression to construct the CSS class dynamically from the incoming prop (see Lecture 5).

Now look at line 4: `{label}`. The text displayed on screen is driven 100% by the `label` prop.

Never attempt to assign `label = 'Saved'` inside this function. In development, React freezes the props object via `Object.freeze`. Reassigning throws a fatal TypeError. When a button needs to show different text, its parent must pass a different label prop.

To recap this step: terminal UI controls receive read-only props and project them into native DOM elements with safe default fallbacks.

### Step 4: Finally, we seal the application entry point main.jsx

In step 4, we complete our application architecture by providing the client entry point `main.jsx`.

This file acts as the root consumer of our component hierarchy, connecting our top-level container component to the browser DOM:

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import EditorialDesk from './EditorialDesk.jsx';

```

Look at line 1: `import { createRoot } from 'react-dom/client'`. We import the concurrent root initializer from the DOM renderer (see Lecture 6).

Look at line 2: `import EditorialDesk from './EditorialDesk.jsx'`. We import our top-level desk container (see Lecture 7).

Look at lines 3 to 6: `main.jsx` acquires `#root`, initializes the concurrent root, and mounts `<EditorialDesk />` into the page. React invokes `EditorialDesk()`, passes the story props to `StoryCard()`, passes the button props to `ActionButton()`, and paints the complete UI onto the screen.

To recap this final step: main.jsx serves as the root consumer of the module graph, mounting the configured component hierarchy onto the page.

### Passing Objects, Numbers, and Functions as Props

In earlier sections, we passed strings and plain objects as props. In real production applications, props are not limited to text; you can pass numbers, booleans, arrays, nested objects, and callback functions.

What is a **prop contract**? A **prop contract** is the explicit specification of what props a component expects to receive from its parent, including property names, data types, and default values. In plain JavaScript, passing unexpected arguments causes silent errors or NaN calculations. In React, writing clear destructured signatures with default values establishes an explicit contract between parent and child. The law of prop contracts states: a child component specifies what props it can receive, and the parent must supply data matching that contract.

```jsx title="ComplexPropsContract"
export function MetricPill({ count, label, isLive = false }) {
  const badge = isLive ? ' [LIVE]' : ''; // **CODE LOGIC:**<br>Computes status modifier string from boolean prop
  return (
    <div className="metric-pill">
      <span className="count">{count.toLocaleString()}</span> // **CODE LOGIC:**<br>Formats number prop using toLocaleString
      <span className="label">{label}{badge}</span> // **DATA FLOW:**<br>Renders label and dynamic status badge
    </div>
  );
}
```

Look at line 1 in `MetricPill`: the component accepts three different data types: `count` (a number), `label` (a string), and `isLive` (a boolean with default `false`). When mounting this component, the parent writes `<MetricPill count={1420} label="Readers" isLive={true} />`. Look at line 5: `count.toLocaleString()` calls a number method directly because `count` was passed inside curly braces as a real number rather than a string.

> [!WILD]
> **Why can props carry any JavaScript value?** Imagine a postal courier that only accepted handwritten paper letters. If you needed to send a book, a set of keys, or a photograph, the courier would refuse the delivery. That is how traditional HTML attributes work: they only understand plain string text. In React, **props** are an unrestricted shipping container. You can load a string, a number, a complex data object, an array of stories, or even a callback function into that container. React delivers the package intact to the child component. This unrestricted delivery is what makes React components truly modular: they communicate using the full power of the JavaScript language.

> [!TIP]
> **To impress the interviewer:** When discussing props in an interview, mention that props are the foundation of component composition. Explain that passing functions as props (callback props) enables inverse data flow, allowing child components to notify parents of events without violating unidirectional data flow. This bridge will be explored in depth in upcoming lectures on events and state.

### Glossary

- **Props**: Plain JavaScript objects passed from parent to child components to configure their behavior and visual output.
- **Component Purity**: The design principle where component functions return JSX calculated strictly from their inputs (props and state) without causing observable side effects.
- **Unidirectional Data Flow**: The architectural model where data flows strictly downward from parent to child through the component tree.
- **Object Destructuring**: A JavaScript syntax that unpacks properties from an object into distinct local variables directly in function parameters.
- **Object.freeze**: A native JavaScript method used by React in development to make props objects strictly read-only, preventing runtime mutation.
- **Prop Contract**: The explicit specification of property names, data types, and default values that a component expects to receive from its parent.
