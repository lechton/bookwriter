### Why Single-File Monoliths Break Down

In earlier lessons, we learned that a React component is a JavaScript function that returns JSX markup describing what should appear on screen (see Lecture 3 and Lecture 4). When starting a new project or building a small prototype, developers often define multiple component functions in a single file like `App.jsx`. As features multiply, keeping the masthead, navigation, article cards, sidebar, and layout container in one file turns into an unwieldy thousand-line monolith.

What is a **module**? In modern JavaScript and React, a **module** is an isolated file whose top-level variables and functions remain private unless explicitly exported. In plain HTML scripts, any variable or function declared in a `<script>` tag pollutes the global `window` scope, creating silent name collisions and making code impossible to refactor safely. In modern React development, ES modules replace that global chaos with strict file-level isolation: a component defined in `SiteHeader.jsx` is completely invisible to `NewsPortal.jsx` until it is exported. The law of modular architecture is absolute: a file can only consume what another file explicitly exports, and only through the precise contract established by the author.

In a monolithic file, all functions share the same file scope, so one component can accidentally read helper variables or internal utilities belonging to a sibling component. Early web applications concatenated multiple scripts into a single global bundle or kept hundreds of lines in one file to avoid managing import paths. In modern React, you decompose the monolith by moving each component into its own dedicated `.jsx` file, exposing public components through exports and connecting them through imports.

When you split an application into separate files, the build system enforces module rules: (a) The project configuration (`package.json`) declares modern ES module support via Vite or standard bundlers (see Lecture 2), ensuring imports resolve asynchronously. (b) The local file imports (`./SiteHeader.jsx`) use relative paths starting with dot-slash to differentiate local components from external packages in `node_modules`. The consequence is complete isolation: each component manages its own dependencies, merge conflicts drop to zero, and components can be tested or reused independently across the newsroom.

> [!WILD]
> **Why can separate files not see each other?** Imagine a library filled with books on open shelves. If every book had its pages torn out and scattered across the tables, text from one story would mix into another. You would have no way to keep stories separate. Instead, every book has a thick cover that keeps its pages locked inside. A JavaScript file is a book with a locked cover. Variables declared inside that file stay strictly inside its covers. If you want another file to read a function, you must stamp that function with an **export** badge. If another file wants to use it, that file must submit an **import** request. This is **module encapsulation**: it ensures no file can accidentally overwrite or corrupt the code inside another file.

### Default Exports versus Named Exports: The Import Contract

Once you split a component into its own file, you must decide how to expose it to the rest of the application. JavaScript modules provide two distinct export mechanisms: **default exports** and **named exports**.

What is a **default export**? A **default export** is a module mechanism that designates one primary value or component per file using the `export default` declaration. In plain JavaScript, a file with no exports keeps everything private. When you add `export default function SiteHeader() { ... }`, you declare that `SiteHeader` is the official, primary export of that file. When another file imports it, you write `import SiteHeader from './SiteHeader.jsx'` without curly braces. The law of default exports states: a file may contain only one default export, and the importing file can assign any local variable name to it without curly braces.

What is a **named export**? A **named export** is a module mechanism that allows a file to export multiple distinct functions, components, or constants by placing the `export` keyword directly before their declarations. In plain JavaScript, you would have to bundle multiple functions into a single object literal to export them. With named exports, you write `export function ArticleCard() { ... }` and `export function ArticleList() { ... }` as individual declarations. The importing file must use curly braces `{ ArticleCard, ArticleList }`, matching the exact identifiers declared in the source file. The law of named exports states: a file may have as many named exports as needed, and the importing file must use curly braces with names matching the export record unless explicitly aliased.

```jsx title="Export Syntax Contract"
export default function SiteHeader() { // default export: single **PRIMARY** component
  return <header className="masthead">The National Times</header>;
}
export function ArticleCard({ title }) { // named export: individual **REUSABLE** card
  return <article className="story-card">{title}</article>;
}
export function ArticleList() { // named export: companion **FEED** component
  return <section><ArticleCard title="Breaking News" /></section>;
}
```

Look at line 1: `export default function SiteHeader()`. The keyword `default` tells the JavaScript module system that this component is the main export of the file. Now look at lines 4 and 7: `export function ArticleCard` and `export function ArticleList`. Here, the keyword `default` is absent. Each function is registered under its specific identifier in the module's export table. A file can have only one default export, but it can declare dozens of named exports.

When you import components into another file, the syntax you write must match the export contract of the source file. The most frequent bug encountered by React developers is wrapping a default export in curly braces, such as `import { SiteHeader } from './SiteHeader.jsx'`.

When JavaScript evaluates that import, it searches the module's named export dictionary for a key called `SiteHeader`. Because `SiteHeader` was exported as the default, no named key exists. The variable `SiteHeader` evaluates to `undefined`. When React attempts to render `<SiteHeader />`, it evaluates `<undefined />`, halts execution, and throws a fatal TypeError: "Element type is invalid: expected a string or a class/function but got: undefined."

```jsx title="Import Syntax Contrast"
import { SiteHeader } from './SiteHeader.jsx'; // **WRONG:** default with curlies evaluates to **UNDEFINED**
import SiteHeader from './SiteHeader.jsx'; // **RIGHT:** default export imported **WITHOUT** curlies
import { ArticleList } from './ArticleComponents.jsx'; // **RIGHT:** named export imported with matching **CURLIES**
```

Notice the contrast on line 1: wrapping `SiteHeader` in curly braces attempts a named property lookup on a module that only declared a default export. The lookup fails silently in JavaScript, assigning `undefined` to the local identifier. The error only detonates when React attempts to evaluate the element in JSX. On line 2, omitting the curly braces correctly accesses `module.default`. On line 3, the curly braces around `ArticleList` match the named export declared in `ArticleComponents.jsx`, successfully loading the component.

> [!WILD]
> **What is the curly brace import trap?** Imagine a postal mailroom. A **default export** places a package in the open mailbox right on your front porch. When you walk outside to pick it up, you pick it up directly: you do not need a special mailbox key. A **named export** places a package inside a numbered private locker at the post office. To retrieve it, you must present the exact locker key inside **curly braces** `{ ArticleList }`. If you bring a locker key `{ SiteHeader }` to a mailbox on the porch, you are trying to unlock a locker that does not exist. You open the locker door and find absolutely nothing inside: `undefined`. When you hand that empty `undefined` box to React to display on screen, the entire page goes blank with an element type error. To receive a default export, leave the curly braces off: `import SiteHeader from './SiteHeader.jsx'`.

> [!TIP]
> **To impress the interviewer:** When asked how default and named imports differ, do not just recite the syntax. Explain the module namespace object: default exports assign to `module.default`, whereas named exports assign to named properties on the module object. Point out that importing a default export with curly braces evaluates to `undefined`, which is the primary cause of React's notorious "Element type is invalid: expected a string or a class/function but got: undefined" runtime error.

### Let's Design a Practical Example NewsPortal SiteHeader

Let's build a practical example to experience how an application splits across files and coordinates both default and named imports. In the newsroom of The National Times, we are refactoring a monolithic layout into four modular files:
1. A top-level portal container (`NewsPortal.jsx`) that imports child components and coordinates the newsroom view.
2. A primary child branding component (`SiteHeader.jsx`) exported as the default module.
3. A shared component module (`ArticleComponents.jsx`) exporting `ArticleCard` and `ArticleList` as named exports.
4. An application entry point (`main.jsx`) that imports the root portal and mounts it into the DOM.

Before writing any code, examine the final rendered interface we are building. Notice that this visual panel represents the authentic rendered user interface on screen, without code distractions:

```components title="national-times - Rendered UI Canvas"
NewsPortal.jsx | none | shell
  SiteHeader.jsx | edition="Evening Edition" | header | [badge: The National Times] ;; [badge: Evening Edition]
  ArticleComponents.jsx | none | card | [badge: Politics] ;; Transit Union Agrees to Midnight Talks ;; [button: Read Full Story]
```

The rendered canvas displays the visual destination of our application. The parent container `NewsPortal.jsx` coordinates the page layout. At the top sits the publication header displaying the masthead and edition badge, and below it sits the article feed presenting the breaking news story card.

Here is the file layout on disk:

```files title="national-times: File Explorer"

  NewsPortal.jsx | parent | Top-level newsroom container importing modular header and feed

  ArticleComponents.jsx | child | Shared module providing ArticleCard and ArticleList named exports
```

To construct this architecture, we follow a top-down assembly pipeline: we start with the parent container `NewsPortal.jsx`, build the default export child `SiteHeader.jsx`, declare named exports in `ArticleComponents.jsx`, and seal the application entry point `main.jsx`:

### Step 1: First, we construct the parent container NewsPortal.jsx

We start our implementation at the top: the parent container `NewsPortal.jsx`.

We begin here because the parent defines the layout and dictates the component contracts. It coordinates the edition metadata and mounts the child components across module boundaries:

```jsx title="NewsPortal.jsx"
import SiteHeader from './SiteHeader.jsx';
import { ArticleList } from './ArticleComponents.jsx';
export default function NewsPortal() {
  const edition = 'Evening Edition'; // **CODE LOGIC:**<br>Holds edition metadata string in local parent memory
  return (
    <main className="portal-layout">
      <SiteHeader edition={edition} /> // **DATA FLOW:**<br>Mounts default export child passing edition prop downward
      <ArticleList /> // **DATA FLOW:**<br>Mounts named export child from shared component module
    </main>);
}
```

Look at line 1: `import SiteHeader from './SiteHeader.jsx'`. We import `SiteHeader` without curly braces because it will be exported as the single default export of that file.

Notice line 2: `import { ArticleList } from './ArticleComponents.jsx'`. The file name is `ArticleComponents.jsx` in the plural because it encodes two components, not one (`ArticleList` and `ArticleCard`). Because multiple components share this file, they cannot use a single default export and must be declared as named exports, which is why this import requires curly braces: `{ ArticleList }`. The parent imports only `ArticleList` as the feed container; `ArticleCard` is composed internally inside that file and does not need to be imported here.

Look at line 4: `const edition = 'Evening Edition'`. The parent container owns this metadata string and dictates it downward.

Now look at line 7: `<SiteHeader edition={edition} />`. We have not authored `SiteHeader.jsx` yet. But right here in the parent, we establish its contract: it receives the `edition` string through props. We will build that child next in Step 2.

Now look at line 8: `<ArticleList />`. Notice that it takes zero props. We isolate the feed component so it manages its own article rendering without cluttering the parent container.

If you ever write `import { SiteHeader } from './SiteHeader.jsx'`, React receives `undefined` instead of a component function. When the page mounts, execution crashes instantly with an invalid element type error. Always match the import syntax to the source export contract.

To recap this first step: the parent container coordinates child modules by establishing export contracts and mounting them into layout markup.

### Step 2: Next, we build the default export child SiteHeader.jsx

In step 2, we fulfill the contract established by the parent: we build `SiteHeader.jsx`.

This child component renders the publication masthead and displays the dynamic edition string received from props:

```jsx title="SiteHeader.jsx"
export default function SiteHeader({ edition }) { // **DATA FLOW:**<br>Receives edition prop downward fulfilling Step 1 contract
  return (
    <header className="masthead">
      <h1 className="brand-title">The National Times</h1> // **CODE LOGIC:**<br>Renders static brand masthead heading
      <span className="edition-badge">{edition}</span> // **CODE LOGIC:**<br>Displays dynamic edition string via JSX curly braces
    </header>
  );
}
```

Look at line 1: `export default function SiteHeader({ edition })`. Notice the destructured `{ edition }` matching the Step 1 contract.

Notice the declaration `export default`. This designates `SiteHeader` as the single primary export of this file.

What would happen if `SiteHeader` remained inside `NewsPortal.jsx`?

If `SiteHeader` were trapped inside `NewsPortal.jsx`, any other page in the newsroom (such as the archive search, opinion desk, or subscription portal) would be forced to duplicate the entire masthead markup or import the monolithic portal just to display the publication branding. Modifying the title or logo in one place would risk breaking layout across unrelated pages.

By separating them, `SiteHeader.jsx` owns zero portal layout state and zero article dependencies. It is a pure presenter: given an `edition` string, it will always render the exact same masthead.

This separation gives you two concrete superpowers:
1. If tomorrow you redesign the masthead branding with a new vector logo, you touch zero lines of `NewsPortal.jsx` or article feed code.
2. If you change the portal layout from a single column to a multi-column grid, you touch zero lines of `SiteHeader.jsx` code.

To recap this step: default exports establish a clean single-component contract that lets any file import the primary component without curly braces.

### Step 3: Then, we declare named exports in ArticleComponents.jsx

In step 3, we build our shared component module: `ArticleComponents.jsx`.

Rather than creating a separate file for every tiny presentation component, we group related article elements into a single module using named exports:

```jsx title="ArticleComponents.jsx" startLine="1" continues="bottom"
export function ArticleCard({ title, category }) { // **CODE LOGIC:**<br>Named export component rendering individual story card
  return (
    <article className="story-card">
      <span className="story-tag">{category}</span> // **CODE LOGIC:**<br>Renders category tag label
      <h2 className="story-title">{title}</h2> // **CODE LOGIC:**<br>Projects article title into heading markup
    </article>
  );
}
```

Look at line 1: `export function ArticleCard({ title, category })`. Notice that `default` is absent. By writing `export function`, we register `ArticleCard` as a named export.

This component accepts `title` and `category` props and returns semantic article markup. Because it is a named export, any file in the application can import it selectively using `{ ArticleCard }`.

Next, we declare our second companion component, `ArticleList`, inside the exact same file:

```jsx title="ArticleComponents.jsx" startLine="9" continues="top"
export function ArticleList() { // **DATA FLOW:**<br>Named export rendering collection of article cards
  return (
    <section className="story-feed">
      <ArticleCard category="Politics" title="Transit Union Agrees to Midnight Talks" /> // **DATA FLOW:**<br>Composes sibling card within same module boundary
    </section>
  );
}
```

Look at line 9: `export function ArticleList()`. This is our second named export from `ArticleComponents.jsx`.

Look at line 12: `<ArticleCard category="Politics" title="Transit Union Agrees to Midnight Talks" />`. Notice that `ArticleList` composes `ArticleCard` directly with zero imports. Because both components share the same file scope, they can reference each other natively.

What would happen if every small helper component were forced into its own separate file?

If you created a new file for every single two-line helper like `ArticleCard`, your project directory would quickly drown in dozens of tiny files. Developers would spend cognitive energy navigating deep folder hierarchies and writing verbose import statements for tightly coupled siblings.

Grouping cohesive, tightly coupled components in a single module via named exports preserves clean modularity while preventing file proliferation.

This separation gives you two concrete superpowers:
1. If tomorrow you add a new named export like `ArticleSummary` to `ArticleComponents.jsx`, you touch zero lines of `SiteHeader.jsx` or `NewsPortal.jsx` code.
2. If you change how `NewsPortal.jsx` arranges its layout, you touch zero lines of `ArticleComponents.jsx` code.

To recap this step: named exports allow a single file to expose multiple companion components under strict names, requiring curly braces on import.

### Step 4: Finally, we seal the application entry point main.jsx

In step 4, we complete our module architecture by providing the client entry point `main.jsx`.

This file acts as the root consumer of our module graph, connecting our top-level container component to the browser DOM:

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import NewsPortal from './NewsPortal.jsx';
const container = document.getElementById('root'); // **CODE LOGIC:**<br>Acquires physical root container from index.html
if (!container) throw new Error('Root container missing'); // **CODE LOGIC:**<br>Defensive guard prevents null pointer error
const root = createRoot(container); // **CODE LOGIC:**<br>Initializes concurrent ReactDOMRoot in memory
root.render(<NewsPortal />); // **DATA FLOW:**<br>Mounts root component tree into the browser document
```

Look at line 2: `import NewsPortal from './NewsPortal.jsx'`. Notice again: `NewsPortal` was exported as a default export in Step 1, so we import it without curly braces.

Look at lines 3 to 6: `main.jsx` acquires `#root`, initializes the concurrent root, and mounts `<NewsPortal />` into the DOM (see Lecture 6).

Modern bundlers like Vite (see Lecture 2) trace this entire dependency graph starting from `main.jsx`. Vite reads `main.jsx`, follows the import of `NewsPortal.jsx`, follows the imports of `SiteHeader.jsx` and `ArticleComponents.jsx`, and compiles the modular files into an optimized bundle for the browser.

To recap this final step: main.jsx serves as the root consumer of the module graph, importing the top-level container and mounting the application onto the page.

### Renaming Imports and Combining Export Types

What happens when two different files export a component with the same name? For example, both `ArticleComponents.jsx` and an administrative module might export a component called `Badge`. If you import both into `NewsPortal.jsx`, JavaScript encounters a syntax error because two variables share the same identifier in the same file scope.

To resolve naming collisions, JavaScript provides the `as` keyword to create an **import alias**. When importing a named export, you write `import { ArticleCard as FeedCard } from './ArticleComponents.jsx'`. From that line down, your file refers to the component as `FeedCard`. For default exports, you do not even need the `as` keyword: because a default export has no mandatory name, you can write `import Masthead from './SiteHeader.jsx'` directly.

A single file can also export both a default component and named helper components or constants. For example, a branding module might default-export a `SiteHeader` component while providing a named export for a `HeaderNotice` utility. To consume both in a single statement, write the default import first outside curly braces, followed by a comma, then the named imports inside curly braces: `import SiteHeader, { HeaderNotice } from './SiteHeader.jsx'`.

```jsx title="Aliasing and Combined Imports"
import { ArticleCard as FeedCard } from './ArticleComponents.jsx'; // **ALIAS:** renames import with **AS**
import SiteHeader, { HeaderNotice } from './SiteHeader.jsx'; // **COMBINED:** default and named in **ONE** line
export default function DeskView() {
  return (
    <section className="desk-view">
      <SiteHeader edition="Morning" />
      <FeedCard title="Mayor Approves Green Transit Fleet" />
    </section>
  );
}
```

> [!WILD]
> **When do import names collide across files?** Imagine two reporters both author a component named `Card`. One reporter builds a card for breaking news, and another reporter builds a card for weather updates. If you try to import both into the same file with `import { Card }`, JavaScript refuses to run. The two names crash into each other in the same room. Which card do you mean? To solve this collision, you use the **`as` keyword** to create an **import alias**: `import { Card as NewsCard } from 'news-module'` and `import { Card as WeatherCard } from 'weather-module'`. By giving each import an alias, you give each component its own clear, unambiguous name in your file.

> [!TIP]
> **To impress the interviewer:** When discussing code organization, explain the industry consensus on export strategy. Modern design systems and large enterprise codebases heavily favor named exports because they enforce consistent naming across thousands of files, prevent accidental renaming during imports, and integrate seamlessly with IDE automatic refactoring tools. Reserve default exports for route pages or single-purpose components where a dominant identity is universally understood.

### Where you will meet this

- Design system component libraries: Consuming common UI primitives like buttons, modals, and typography chips via named imports from a shared component package.
- Page routing in frameworks: Exporting top-level page views as default exports to satisfy convention-based routing in Next.js or dynamic imports with React.lazy.
- Feature folder architecture: Grouping complex newsroom widgets into dedicated folders where subcomponents are exported through an index barrel module.
- Icon and utility packages: Selectively importing specific icons from large icon libraries using named imports to enable bundler tree-shaking and keep bundle sizes small.

### Glossary

- **Default Export**: A module export declared with export default that designates a single primary value for the file, imported without curly braces.
- **Named Export**: A module export declared with export that exports a specific function or variable by name, imported using matching curly braces.
- **ES Modules**: The official ECMAScript standard for JavaScript code modularity, providing file-level scope with explicit import and export statements.
- **Tree Shaking**: An optimization performed by modern bundlers that analyzes ES module imports and eliminates unused named exports from the production bundle.
- **Module Encapsulation**: The boundary guarantee that variables, functions, and classes defined inside a module are private unless explicitly exported.
- **Import Alias**: The syntax using the as keyword that renames an imported named export to avoid naming collisions or clarify its local role.

In modern React, splitting monolithic files into focused, single-responsibility modules is fundamental for clean code architecture and team collaboration. Here is your streetwise review.

❒ Core Principles of File Splitting and Import Contracts

1. Use **default exports** for files that represent a single primary component.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Declared with `export default function Name()`, a default export establishes the main identity of the module.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Consuming files import default exports without curly braces, avoiding undefined lookup errors.

2. Use **named exports** for modules that expose multiple cohesive components or utilities.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Declared with `export function Name()`, each export is registered under its exact identifier in the module record.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Consuming files must import named exports using matching curly braces `{ Name }`, supporting tree-shaking.

3. Beware of the **curly brace import trap** when consuming modules.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Wrapping a default export in curly braces evaluates to `undefined`, crashing React at runtime on mount.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use the `as` keyword to alias named imports whenever two modules export components with identical names.

➔ NEVER wrap a default export in curly braces when importing it into another file.

➔ ALWAYS use exact matching names inside curly braces when importing named exports.

➔ IF two imported components share the same identifier THEN **rename one locally using the `as` keyword**.

**DO THIS:** Import default exports without curly braces and named exports with matching curly braces.
