### Adding Event Handlers: Passing Functions Versus Calling Functions

In earlier lessons, we learned that React components are JavaScript functions that return JSX markup (see Lecture 3). We also saw that component rendering must remain completely pure and free of side effects (see Lecture 13). In plain HTML, you attach interactivity by writing string attributes directly into your markup, such as `<button onclick="alert('clicked')">`. In that plain web world, the browser evaluates that string as global JavaScript code whenever a click occurs. When you move to React, writing a string attribute fails completely: JSX requires real JavaScript functions wrapped in curly braces (see Lecture 5). Developers transitioning from plain HTML often write parentheses after their function names inside JSX props, expecting the handler to wait for a user click, only to watch their function execute immediately during the render pass.

What is an **event handler**? React draws a strict boundary between two distinct parts of your component: the **render function**, which calculates JSX markup, and the **event handler**, which responds to user interactions. In normal HTML, an element handles its own inline events through string attributes: when you write `onclick="handleClick()"`, the browser's native engine waits until the user physically clicks before evaluating the script string, and no JavaScript framework is involved. Leave event handling in that plain world and functions sit in global browser scope. In React, you take that control into your component: you write `<button onClick={handleClick}>`. The button is now bound to a real function reference: it can only execute when the user physically clicks or types, and React guarantees that the handler never runs during rendering. The law of event handlers states: you must always pass an event handler function as a reference without parentheses; calling the function with parentheses executes it immediately during render, which violates component purity and can trigger infinite re-render loops.

In plain JavaScript DOM scripting, you query a button node and attach a listener with `addEventListener('click', handler)` (see Lecture 1). In React, you pass the handler directly as a prop using camelCase naming, such as `onClick`, `onChange`, or `onKeyDown`. Now consider the physical difference between passing a reference and calling a function. When you write `onClick={handleClick}`, you hand React a pointer to the function: React holds the reference in memory and invokes it only when the browser registers a physical click event. But if you write `onClick={handleClick()}`, the JavaScript engine evaluates `handleClick()` right at that moment, during the render pass, and assigns the return value (usually `undefined`) to `onClick`. The handler executes before the user ever touches the keyboard or mouse, and when the user actually clicks, nothing happens because `onClick` is `undefined`.

Here is the code showing the parenthesis mistake:

```jsx title="EventBindingMistakes"
export default function BrokenArticle({ headline }) {
  function openStory() {
    console.log('Story opened:', headline); // **WRONG:** executes during **RENDER**
  }
  return <button onClick={openStory()}>Read Headline</button>;
}
```

To fix this premature execution, you pass the function name bare: `onClick={openStory}`. If your handler needs arguments, such as an article identifier, you wrap the call inside an inline arrow function: `onClick={() => openStory(story.id)}`. The arrow function acts as a wrapper: React stores the arrow function in memory, and the inner call runs only when the user clicks.

Here is the correct code passing a function reference with arguments:

```jsx title="CorrectEventBinding"
export default function SafeArticle({ story }) {
  function openStory(id) {
    console.log('Story opened:', id); // **RIGHT:** executes only upon **CLICK**
  }
  return <button onClick={() => openStory(story.id)}>Read Story</button>;
}
```

> [!WILD]
> **Why do parentheses break your click handler?** Imagine hiring a messenger to deliver a letter whenever a newsroom bell rings. You give the messenger instructions: "Deliver this letter when the bell rings." That is passing a **function reference**: the messenger waits patiently until the bell sounds. Now imagine walking up to the messenger, handing them the letter, and immediately shouting "Deliver this letter now!" That is calling a **function with parentheses**. The messenger runs out the door instantly, before the bell ever rings! When the bell finally rings later, the messenger is already gone and nothing happens. In React, writing `onClick={handleClick}` gives React the instructions to wait for a user action. Writing `onClick={handleClick()}` executes the function during **render**, long before any user clicks.

### The SyntheticEvent Object: Reading Event Details and Input Values

In plain JavaScript, when an event listener fires, the browser passes an `Event` object containing details such as mouse coordinates, pressed keys, and the target element. However, different web browsers historically implemented event properties differently: Internet Explorer used `window.event`, older versions of Firefox handled mouse coordinates differently than Safari, and event propagation methods varied across operating systems. Developers historically spent countless hours writing defensive browser-sniffing code to ensure identical event behavior across platforms.

What is a **SyntheticEvent**? React distinguishes between two kinds of event objects: the **native browser event**, created directly by the browser engine, and the **SyntheticEvent**, the standardized cross-browser wrapper created by React. In normal DOM scripting, when a user clicks or types, the browser produces a native `MouseEvent` or `InputEvent` whose properties and behavior depend on the underlying browser engine. In React, your event handler never receives the raw browser event directly: React intercepts the event at the root and wraps it in a **SyntheticEvent**. The law of SyntheticEvent states: every React event handler receives a SyntheticEvent instance that exposes the exact same interface across Chrome, Safari, Firefox, and mobile browsers; you can read event properties like `e.target.value` and call methods like `e.stopPropagation()` and `e.preventDefault()`, and React guarantees identical behavior regardless of the user's browser or operating system.

When responding to user typing, an input element fires an event on every keystroke. In plain HTML, typing a letter dispatches an `input` event on the physical DOM node. In React, you listen to typing using the camelCase prop `onChange`. Inside the handler, React passes the SyntheticEvent object, conventionally named `e`. To read what the user typed, you inspect `e.target.value`. The property `e.target` refers to the physical DOM element that dispatched the event (the `<input>`), and `.value` holds the current string of text inside that input box. When listening to keyboard events like pressing Enter, you use `onKeyDown` and inspect `e.key`.

Here is a component reading input text and keyboard keys from the SyntheticEvent:

```jsx title="SyntheticEventDemo"
export default function SearchField() {
  function handleType(e) {
    console.log('Typed text:', e.target.value); // reads current **VALUE**
  }
  function handleKeyDown(e) {
    if (e.key === 'Enter') console.log('Submitted'); // reads pressed **KEY**
  }
  return <input onChange={handleType} onKeyDown={handleKeyDown} />;
}
```

> [!WILD]
> **What is inside that event object?** Imagine receiving news dispatches from reporters all over the world. One reporter writes in French on blue paper, another writes in Japanese on parchment, and a third sends a voice recording. If the editor had to translate every dialect and format before reading, the newsroom would grind to a halt. Instead, an editorial assistant intercepts every dispatch at the door, translates it into standard English, and places it into a clean white folder labeled **SyntheticEvent**. Every folder contains the exact same tabs: **`e.target`** for who sent it, **`e.key`** for what key was pressed, and **`e.preventDefault()`** to hold the presses. In React, the **SyntheticEvent** is that clean folder: it wraps the messy **native browser event** so your code works identically on every device and browser.

### Step 1: First, we construct the parent container NewsDesk.jsx

We start our implementation at the top: the parent container `NewsDesk.jsx`.

We begin here because the parent defines the layout and dictates the event handling contracts for the entire view. It declares the handler functions and passes them downward as props to its children:

```jsx title="NewsDesk.jsx" startLine="1" continues="bottom"
export default function NewsDesk({ stories }) {
  function handleSearch(query) { // **CODE LOGIC:**<br>Handles search submission triggered by child keyboard event
    console.log('Searching for:', query);
  }
  function handleSelectArticle(id) { // **CODE LOGIC:**<br>Opens full article view when user clicks article card
    console.log('Opening article:', id);
  }
```

Notice lines 2 to 7: the parent defines two handler functions, one for search queries and one for article selections. It then renders the layout and passes those handlers downward:

```jsx startLine="8" continues="top"
  return (
    <main className="desk-layout">
      <ArticleSearch onSearch={handleSearch} /> // **DATA FLOW:**<br>Passes search handler callback downward to search input child
      {stories.map((story) => (
        <ArticleItem key={story.id} story={story} onOpen={handleSelectArticle} /> // **DATA FLOW:**<br>Passes selection callback downward to each article card
      ))}
    </main>
  );
}
```

Now look at line 10: `<ArticleSearch onSearch={handleSearch} />`. We have not coded `ArticleSearch` yet. But right here in the parent, we establish its contract: it receives an `onSearch` callback prop.

Next look at line 12: `<ArticleItem key={story.id} story={story} onOpen={handleSelectArticle} />`. The parent maps over the stories collection and passes `handleSelectArticle` down under the prop name `onOpen`.

Mind you, the easiest shortcut in plain JavaScript is hardcoding alert dialogs or opening modals directly inside child buttons. But passing callbacks down keeps the parent in complete command of navigation and search workflows.

To recap this first step: the parent defines the event handlers and passes them downward as explicit callback props, establishing the contracts for all child components.

### Step 2: Next, we build the search filter ArticleSearch.jsx

In step 2, we fulfill the contract established by the parent: we build `ArticleSearch.jsx`.

This child component provides an interactive search box that listens to typing and keyboard events:

```jsx title="ArticleSearch.jsx"
export default function ArticleSearch({ onSearch }) {
  function handleChange(e) { // **CODE LOGIC:**<br>Reads typed character string from SyntheticEvent target on every keystroke
    console.log('Live query buffer:', e.target.value);
  }
  function handleKeyDown(e) { // **CODE LOGIC:**<br>Detects Enter key press and dispatches search callback to parent
    if (e.key === 'Enter') onSearch(e.target.value); // **DATA FLOW:**<br>Forwards search query upward to parent handler
  }
  return <input placeholder="Search newsroom..." onChange={handleChange} onKeyDown={handleKeyDown} />;
}
```

Look at the input element on line 8: notice the two event props `onChange={handleChange}` and `onKeyDown={handleKeyDown}`.

Where does `onSearch` come from? Look back at Step 1 in `NewsDesk.jsx`. The parent declared `handleSearch` and rendered: `<ArticleSearch onSearch={handleSearch} />`.

Notice what happened: the parent handed its private handler function `handleSearch` to the child under the prop name `onSearch`. `ArticleSearch` does not own story state, and it does not filter articles itself. It only holds a telephone line called `onSearch`.

When the editor presses Enter, `handleKeyDown` detects `e.key === 'Enter'` and calls `onSearch(e.target.value)`. Because `onSearch` points directly to `handleSearch`, that call immediately executes `handleSearch(e.target.value)` back in `NewsDesk`.

This is standard **inverse data flow**: data flows down through props, and user actions flow up through callbacks (`onSearch`).

What would happen if `ArticleSearch` filtered the stories array directly?

If you put story filtering inside `ArticleSearch`, the input would be trapped managing article arrays, sorting orders, and category filters. Worse, other components like the story feed or statistics bar would have no access to the filtered results without messy global hacks. You would have an input element and newsroom data models tangled in a single file.

By separating them, `ArticleSearch` owns zero story state and zero data store dependencies. It is a pure interactive input: given the `onSearch` callback, it will always render the exact same search box and report user keystrokes.

This separation gives you two concrete superpowers:
1. If tomorrow you replace the text input with voice dictation, you touch zero lines of story filtering code.
2. If you change how stories are filtered in the parent, you touch zero lines of search box code.

To recap this step: user typing and keypresses are captured via SyntheticEvent and forwarded upward through `onSearch` as standard inverse data flow.

### Step 3: Then, we declare the clickable article card ArticleItem.jsx

In step 3, we fulfill the parent's `onOpen` contract by building `ArticleItem.jsx`.

This component represents an individual article card that responds to user clicks:

```jsx title="ArticleItem.jsx"
export default function ArticleItem({ story, onOpen }) {
  return (
    <article className="story-card" onClick={() => onOpen(story.id)}> // **DATA FLOW:**<br>Passes story id upward to parent onOpen callback when card is clicked
      <h3>{story.title}</h3> // **CODE LOGIC:**<br>Renders headline text from incoming story prop
      <span className="badge">{story.category}</span>
      <BookmarkButton storyId={story.id} /> // **DATA FLOW:**<br>Renders nested interactive bookmark action
    </article>
  );
}
```

Look at line 5: `onClick={() => onOpen(story.id)}`. Notice the inline arrow function wrapping `onOpen(story.id)`.

If you ever write `onClick={onOpen(story.id)}` with parentheses, JavaScript evaluates that call immediately during render! The article opens before the user ever touches the mouse, and `onClick` receives `undefined`. By wrapping the call in an arrow function, execution is delayed until the user physically clicks the card.

Now notice line 8: `<BookmarkButton storyId={story.id} />`. `ArticleItem` hosts a child button inside its markup. If an editor clicks that bookmark button, the click physically occurs inside the card. Without intervention, that click will bubble up and open the article!

To recap this step: the card responds to clicks by passing the story identifier to the parent callback via an inline arrow function, while hosting a nested button that requires event isolation.

### Step 4: Finally, we seal the card with BookmarkButton.jsx

In step 4, we build `BookmarkButton.jsx` to solve the event bubbling challenge:

```jsx title="BookmarkButton.jsx"
export default function BookmarkButton({ storyId }) {
  function handleBookmark(e) {
    e.stopPropagation(); // **CODE LOGIC:**<br>Halts event bubbling to prevent parent card click from firing
    console.log('Bookmarked story:', storyId); // **ACTION:**<br>Executes bookmark save action independently
  }
  return <button onClick={handleBookmark}>Bookmark</button>; // **DATA FLOW:**<br>Binds isolated click handler
}
```

Look at line 3: `e.stopPropagation()`. Notice this critical method call on the SyntheticEvent object.

Where does `e` come from? React passes the SyntheticEvent automatically to every event handler function. By calling `e.stopPropagation()`, the bookmark button commands the browser and React: "Stop this event right here; do not let it bubble up to ancestor elements."

If you omit `e.stopPropagation()`, the click bubbles up the DOM tree to `ArticleItem`. The card's `onClick` fires immediately after the button's `onClick`, opening the full article view when the user only wanted to save a bookmark.

To recap this step: calling `e.stopPropagation()` on the SyntheticEvent isolates child button actions from parent container click handlers, preventing unwanted side effects across nested components.

### Lessons from the Experiment: Naive Expectation vs Reality

Developers often assume that attaching an event handler to a button inside a card only triggers that button. In the browser's Document Object Model, however, events do not stop at the element that was clicked: they bubble up through every parent container in the tree all the way to the document root. This naive expectation leads to frustrating bugs where clicking a nested action button accidentally fires the parent card's navigation handler.

### Stopping Event Propagation Versus Preventing Default Browser Behavior

Beginners frequently confuse two methods on the event object: `e.stopPropagation()` and `e.preventDefault()`. Because both methods contain words that suggest halting an action, developers often treat them as interchangeable or call both in every handler out of superstition. In web standards, however, these two methods solve completely different problems.

What is the difference between **event propagation** and **default behavior**? React follows the W3C DOM event specification, which defines two independent browser mechanisms: (a) **event propagation** (bubbling), where an event travels upward through the component tree, and (b) **default behavior**, where the browser executes a built-in action in response to an event (such as submitting a form, navigating to a link URL, or checking a checkbox). When you call `e.stopPropagation()`, you halt the upward travel of the event: parent components will not hear the event, but the browser will still execute any native default action. When you call `e.preventDefault()`, you cancel the browser's native default action (such as preventing a `<form>` from reloading the page or an `<a>` tag from navigating), but the event continues bubbling upward through the component tree! The law of event control states: `e.stopPropagation()` stops the event from traveling to parent components, while `e.preventDefault()` stops the browser from executing its native action; neither method performs the job of the other.

Here is a component demonstrating the difference between both methods:

```jsx title="PropagationVsDefault"
function NestedLink({ onCardClick }) {
  function handleLinkClick(e) {
    e.preventDefault(); // cancels browser navigation; click STILL BUBBLES to card
    e.stopPropagation(); // cancels bubbling; click DOES NOT REACH onCardClick
    console.log('Handled custom client navigation');
  }
  return <a href="/story/42" onClick={handleLinkClick}>Read Story</a>;
}
```

> [!WILD]
> **When does an event bubble out of control?** Imagine a large wooden table in a newsroom. On the table sits an article folder, and on the folder sits a red stamp button. If you slam your hand down on the red stamp button, the vibration travels through the stamp, through the folder, and rattles the entire table. That upward vibration is **event bubbling**: an action on a nested child vibrates upward through every parent container. If the table is wired with a sensor that archives the article whenever it vibrates, stamping the button accidentally archives the folder! Calling **`e.stopPropagation()`** is like placing a rubber shock absorber under the stamp: the stamp executes its action, but the vibration stops immediately. The folder and the table stay completely still.

> [!TIP]
> **To impress the interviewer:** Explain that in React 17 and later, React attaches event listeners to the root DOM container (`rootNode`) rather than the `document` object. This makes embedding multiple React roots inside a larger page safe, because stopping propagation at one React root will not break events in other roots.

### Glossary

- **Event Handler**: A JavaScript callback function passed as a prop to a JSX element to respond to user interactions such as clicks, typing, or keypresses.
- **SyntheticEvent**: React's cross-browser wrapper around the native browser DOM event, providing a standardized interface across all browsers.
- **Event Propagation (Bubbling)**: The natural process where a DOM event travels upward from the target element through all its ancestor components in the tree.
- **stopPropagation**: A method on the SyntheticEvent that halts event bubbling, preventing ancestor components from receiving the event.
- **preventDefault**: A method on the SyntheticEvent that cancels the browser's native default action, such as preventing form submission page reloads.
- **Inline Handler**: An event handler defined directly inside JSX using an arrow function, useful for passing custom arguments to callbacks.

### Summary

**Event Handling and SyntheticEvent Architecture in React**

In production applications, understanding how to bind event handlers, inspect SyntheticEvent properties, and manage event bubbling is essential for building robust interactive interfaces. Here is your streetwise review.

❒ Core Principles of React Event Handling

1. Pass **function references** to event props; never call functions during render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Writing `onClick={handleClick}` passes a reference that executes only when the user clicks.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Writing `onClick={handleClick()}` executes the function during render, corrupting state and leaving `onClick` undefined.

2. Use **SyntheticEvent** to inspect user interactions across all browsers.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Read input text with `e.target.value` inside `onChange` handlers for typing events.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Inspect pressed keys with `e.key` inside `onKeyDown` handlers for keyboard navigation.

3. Distinguish between **stopPropagation** and **preventDefault**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Use `e.stopPropagation()` to prevent nested child clicks from triggering parent container handlers.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use `e.preventDefault()` to cancel native browser actions like link navigation or form reloads.

➔ NEVER call an event handler with parentheses directly inside a JSX prop unless wrapped in an arrow function.

➔ ALWAYS call `e.stopPropagation()` on nested buttons inside clickable cards to prevent accidental parent actions.

➔ IF an event handler requires custom arguments THEN **wrap the invocation in an inline arrow function: `onClick={() => handleSelect(item.id)}`**.

**DO THIS:** Pass function references or wrap parameterized calls in inline arrow functions.

```jsx right title="Safe Event Handling Pattern"
export default function ArticleActions({ story, onSelect }) {
  function handleBookmark(e) {
    e.stopPropagation();
    saveBookmark(story.id);
  }
  return (
    <div onClick={() => onSelect(story.id)}>
      <h3>{story.title}</h3>
      <button onClick={handleBookmark}>Bookmark</button>
    </div>
  );
}
```

**DO NOT DO THIS:** Never call functions during render or omit stopPropagation on nested buttons.
