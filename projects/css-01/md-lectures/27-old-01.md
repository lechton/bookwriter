### Snap Container and Snap Targets: The Axis Contract

To understand how native CSS scroll interactions achieve the buttery smoothness of native mobile applications, one must examine the dual-actor architecture of the CSS Scroll Snap specification. Scroll snapping is not a single property applied to an element; it is an explicit geometric contract negotiated between two distinct entities in the DOM tree: the **Snap Container** (the scrollable parent viewport) and the **Snap Targets** (the children arranged inside that scroll container).

> "The scroll-snap-type CSS property sets how strictly snap points are enforced on the scroll container in case there is one. It specifies the axis on which snapping occurs (x, y, block, inline, or both) and the strictness of the snapping (mandatory or proximity)."<br><br>*MDN Web Docs, CSS scroll snap (`resources/web-performance/mdn/files/en-us/web/css/reference/properties/scroll-snap-type/index.md`)*


#### Actor 1: The Snap Container (`scroll-snap-type`)

The snap container establishes the coordinate physics for the entire scrollable area. By applying `scroll-snap-type: x mandatory;` to an element with `overflow-x: auto;`, you instruct the browser's compositor thread to monitor kinetic scrolling along the horizontal axis. The container defines an invisible reference line called the **snapport line**.

#### Actor 2: The Snap Target (`scroll-snap-align`)

The snap targets are the child elements resting inside the scroll track. Each child must explicitly declare where its bounding box should align relative to the parent's snapport line using `scroll-snap-align`. The property accepts three primary values:
- `start`: Aligns the leading edge of the child with the leading edge of the scroll container.
- `center`: Aligns the geometric center of the child with the center of the scroll container.
- `end`: Aligns the trailing edge of the child with the trailing edge of the scroll container.

```html title="photo-gallery.html"
<section class="gallery-viewport">
  <article class="gallery-slide">
    <img src="summit-01.jpg" alt="Delegates entering the assembly hall">
    <p class="slide-caption">Opening plenary in Geneva.</p>
  </article>
  <article class="gallery-slide">
    <img src="summit-02.jpg" alt="Protesters outside the conference center">
    <p class="slide-caption">Demonstrations along the riverbank.</p>
  </article>
</section>
```

```css title="photo-gallery.css"
.gallery-viewport {                  /* Actor 1: Snap Container */
  display: flex;
  overflow-x: auto;
  scroll-snap-type: x mandatory;     /* Enables horizontal snapping with mandatory strictness */
  overscroll-behavior-x: contain;    /* Prevents horizontal momentum from bubbling to parent */
  gap: 16px;
  padding: 16px;
}

.gallery-slide {                     /* Actor 2: Snap Target */
  flex: 0 0 85%;                     /* Each slide occupies 85% of viewport width */
  scroll-snap-align: center;         /* Centers each slide within the gallery container */
  scroll-snap-stop: always;          /* Prevents flick gestures from skipping multiple slides */
}
```

#### Why CSS Snapping Outperforms JavaScript Carousel Libraries

For more than a decade, web developers relied on heavyweight JavaScript touch carousels. These libraries attached `touchstart`, `touchmove`, and `touchend` listeners to DOM nodes, manually calculated finger velocity vectors, and updated element positions using `requestAnimationFrame` or CSS transforms.

This JavaScript approach introduces severe performance bottlenecks:
1. **Main Thread Contention**: If the browser is busy parsing JSON, hydrating a framework component, or executing analytics scripts, JavaScript touch listeners drop frames, causing visible stutter.
2. **Passive Listener Friction**: Touch event listeners can block native compositor scrolling unless explicitly marked as `{ passive: true }`, triggering browser warnings and touch latency.
3. **Hardware Mismatch**: A JavaScript script cannot replicate the exact native momentum physics, spring coefficients, and friction curves of iOS or Android devices.

In sharp contrast, CSS scroll snapping is implemented directly inside the browser's native C++ compositor pipeline. When a user swipes their finger on an iPhone or trackpad, the touch gesture is processed entirely on the GPU compositor thread. The main thread can be completely frozen by heavy JavaScript execution, and the photo carousel will still snap with flawless sixty or one hundred and twenty frames-per-second precision.

### Strictness Matters: mandatory vs proximity Snap Dynamics

When configuring `scroll-snap-type`, developers must choose between two fundamentally different behavioral keywords: `mandatory` and `proximity`. Selecting the wrong keyword destroys the intended user experience.

#### Mandatory Snapping: The Strict Carousel Contract

Under `scroll-snap-type: x mandatory`, the browser is under a strict legal obligation: whenever the user finishes a scroll interaction, the scroll container **must** come to rest precisely on a snap point.

If the user drags the photo gallery thirty pixels and releases their finger, the container will not stay there. The compositor engine evaluates the velocity and displacement, detects that the current position does not satisfy a snap target, and animates the scroll offset to lock onto the nearest item. `mandatory` is mandatory: it is mathematically impossible for the scroll view to come to rest at an arbitrary fractional offset between slides.

`mandatory` is the mandatory standard for:
- Full-bleed photo essays and carousels.
- Paginated onboarding card flows.
- Full-screen vertical story presentations (like TikTok or Instagram Reels interfaces).

#### Proximity Snapping: The Gentle Magnetic Guide

Under `scroll-snap-type: x proximity`, snapping is treated as an optional suggestion rather than an absolute rule. The browser's physics engine calculates where the scroll momentum would naturally decay. If that natural stopping position happens to land near a snap point (within an internal browser-defined threshold), the engine gently pulls the scroll position into alignment. However, if the user scrolls with moderate force and releases their finger far from any snap point, the view simply rests where momentum naturally stops.

`proximity` is the ideal standard for:
- Horizontal product catalogs where users want to scan dozens of items quickly.
- Multi-column tables or horizontal news category ribbons where items have varying widths and strict pagination would feel rigid and frustrating.

### Scroll Chaining and overscroll-behavior: Isolating Component Gestures

One of the most disruptive defects in modern responsive web design is **Scroll Chaining**. Scroll chaining occurs when a user scrolls inside a nested scrollable element (such as a horizontal photo gallery, an embedded code snippet, a comment drawer, or a modal dialog) and reaches the boundary of that container.

> "The overscroll-behavior CSS property sets what a browser does when reaching the boundary of a scrolling area. It's a shorthand for overscroll-behavior-x and overscroll-behavior-y. By default, mobile browsers tend to provide a bounce effect or even a page refresh when the top or bottom of a page is reached... overscroll-behavior allows you to override this behavior."<br><br>*MDN Web Docs, overscroll-behavior (`resources/web-performance/mdn/files/en-us/web/css/reference/properties/overscroll-behavior/index.md`)*


#### The Chaining Catastrophe

By default, every scroll container has `overscroll-behavior: auto`. Under this default setting, when a reader swipes to the final photo in a horizontal gallery and continues swiping, the horizontal container has exhausted its scrollable range. The browser does not discard the remaining kinetic momentum. Instead, it "chains" that momentum up the DOM tree to the nearest scrollable ancestor—typically `<body>` or `<html>`.

On mobile touch devices, this produces jarring defects:
- An aggressive horizontal swipe suddenly jerks the entire article vertically.
- Swiping down inside a comment drawer reaches the top and accidentally triggers a full-page reload via the browser's native pull-to-refresh mechanism.
- Scrolling a modal dialog reaches the bottom and starts scrolling the background webpage underneath the modal backdrop.

```css title="gesture-isolation.css"
.gallery-viewport {
  overflow-x: auto;
  scroll-snap-type: x mandatory;
  overscroll-behavior-x: contain;    /* Traps horizontal scroll momentum inside this gallery */
}

.modal-content-scroll {
  overflow-y: auto;
  overscroll-behavior-y: contain;    /* Prevents modal scrolling from scrolling background page */
}
```

Declaring contain traps momentum at the boundary, isolating component gestures."
```

#### The Power of contain vs none

The `overscroll-behavior` property provides three distinct keywords:
1. `auto`: The default behavior. Momentum chains upward to parent scroll containers, and native boundary effects (rubber-banding or pull-to-refresh) are triggered.
2. `contain`: **The recommended standard.** Eliminates scroll chaining to parent elements. When the boundary is reached, momentum terminates immediately. Local boundary effects (such as the subtle rubber-band stretch inside the container on iOS) are preserved, giving the user tactile feedback that the end was reached without affecting the rest of the page.
3. `none`: Eliminates both scroll chaining AND local rubber-band bounce effects entirely. The scroll view hits an absolute hard stop at the boundary.

By setting `overscroll-behavior-x: contain` on horizontal galleries and `overscroll-behavior-y: contain` on modal dialogs, you create self-contained interactive components that never disturb the reader's main page position.

### Single-Item Paging: scroll-snap-stop and High-Velocity Swipes

Even with `scroll-snap-type: x mandatory` active, developers testing mobile photo essays frequently encounter a secondary frustration: high-velocity flicks.

If a reader performs a fast, aggressive swipe gesture, the touch physics engine imparts significant kinetic energy to the scroll view. By default, the browser engine treats snap points like rumble strips on a highway: it acknowledges them, but if the momentum is high enough, it happily blows right past three, four, or five slides before friction brings it to rest on slide number six!

For a photo gallery where each slide contains critical editorial context or an interactive infographic, allowing users to accidentally skip four slides with a single swipe is unacceptable.

```css title="snap-stop.css"
.gallery-slide {
  scroll-snap-align: center;
  scroll-snap-stop: always;          /* Forces momentum to capture at the very next snap point */
}
```

```html-figure src="md-lectures/figures/27-03-scroll-snap-stop-carousel.html" caption="Flick Physics and Inertia Capture: Under scroll-snap-stop: normal, high-velocity flicks skip past multiple items. Declaring scroll-snap-stop: always forces the compositor to trap momentum at the very next item, creating a true single-item carousel."
```

#### The Mechanism of scroll-snap-stop: always

The `scroll-snap-stop` property is declared on the **child snap targets**, not the parent container. It accepts two values:
- `normal` (default): The scroll container is permitted to pass over this snap target if the velocity of the scroll gesture is sufficient.
- `always`: The scroll container is strictly forbidden from skipping this snap point. The engine must trap the scroll momentum at this exact element, regardless of how fast or violently the user flicked the screen.

When you pair `scroll-snap-type: x mandatory` on the parent with `scroll-snap-stop: always` on every slide, you transform a plain HTML `<div>` into a bulletproof, native-feeling pagination slider:
- A gentle swipe advances one slide.
- A furious, fast flick advances exactly one slide and locks into place.
- Zero lines of JavaScript are required.
- Memory consumption and CPU load remain virtually zero.

### Summary

**The Kinetic Scroll Physics**

Building horizontal photo galleries and interactive carousels with JavaScript touch libraries is a legacy anti-pattern that bloats bundles, blocks the main thread, and degrades mobile scrolling performance. Modern CSS provides native, hardware-accelerated scroll physics that run directly on the browser's compositor thread with zero JavaScript overhead.

By declaring `scroll-snap-type: x mandatory` on the container and `scroll-snap-align: center` on the children, developers guarantee that the scroll view always locks cleanly onto slide boundaries. Adding `scroll-snap-stop: always` prevents aggressive flicks from skipping multiple slides, while `overscroll-behavior-x: contain` eliminates scroll chaining to the parent document. Together, these four declarations deliver native mobile application smoothness using purely declarative web standards. Here is your streetwise review.
