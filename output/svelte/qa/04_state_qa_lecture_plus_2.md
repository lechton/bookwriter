# 04 | The Proxy: Where Reactivity Reaches, And Where It Stops

## 4.1 Where This Hour Sits (no booklet section; orientation)

This is the fourth lecture, and it covers the ground of the main state lecture, but it comes at that ground sideways, through the fifteen questions in your booklet. A word on what it rests on. It assumes the first lecture, where Svelte turned out to be a compiler, a tool that reads your code ahead of time and rewrites it, rather than a library that rides along in the browser while the page runs. And it assumes the third lecture, where we built the world this whole course lives in: a news organisation, The National Times, with its articles, its readers, and the small count of claps under each story. That count, and that newsroom, are where every example here will live.

You may have the booklet open, the one with the fifteen questions, the maps, and the code. I will not read code to you, because code is for the eye, and the eye's work is on that page. Each time we step into one of the fifteen questions, I will say which one, so you can look down and find it.

By the end, you should be able to look at any piece of state in a Svelte component and say, before you run anything, whether a change to it will reach the screen, and why. The whole answer rests on one idea, and on a handful of words that you will meet again in documentation and in error messages long after this hour. Those words are the point as much as the idea is, so I will say them often.

## 4.2 Why A Plain Variable Cannot Move The Screen (booklet: "Making a value react to change", question one)

The smallest possible thing is the clap count on a story. It is a number. A reader taps the button, and you want the number to climb.

In ordinary JavaScript you would keep that number in a variable, and when the tap comes, you would add one to it. And nothing would happen on the screen. That is the problem the entire chapter exists to solve. The variable and the thing the reader sees are two separate worlds. The variable is a value in memory. The number on the screen is text inside an element on the page. Changing the first does not touch the second. To make the screen agree, you would have to find that element yourself and rewrite its text by hand, every time the number changed.

So here is what you do instead. You write the variable with a small marker in front of its starting value, and that marker tells Svelte's compiler to wire the variable to the screen for you, ahead of time. That marker has a name worth keeping, because you will type it on nearly every component you ever build: it is called the state rune. Let me give you the name in full, the careful way, because it is the first of the names this lecture turns on. The state rune is the dollar sign, followed by the word state. So, the state rune, the dollar sign followed by the word state, is the marker that tells the compiler to make a variable reactive.

And there is the second word, reactive, so let me build it before I lean on it. A variable is reactive when Svelte is watching it, so that the screen moves when the variable moves. That is the whole meaning: reactive means Svelte watches the variable, so the screen moves when the variable moves. Wrap the clap count in the state rune, and the count is reactive: you change it the way you always would, you add one to it, with no special function to call, and every place on screen that shows it updates on its own. The booklet has the few lines under question one.

So, two names to carry out of this first minute. The state rune, the dollar sign followed by the word state, the marker that makes a variable reactive. And reactive, which means Svelte watches the variable so the screen moves when it moves. They are almost disappointingly small. The interest begins the moment the thing you wrap is not a single number, but an object, or a list. Because a clap count is rare. Most state is an article with a title and a body, or a list of articles, or a draft with a checklist. What happens to reactivity then?

## 4.3 The Proxy (booklet: "When state is an object or a list", question two)

Picture a draft article in the newsroom, with a small checklist on it: a list of tasks, each task a little object with a label and a flag for whether it is done. You wrap the whole list in the state rune, the marker that makes a variable reactive. Now you reach into it, past the list, into one task, and you flip that task's done flag, deep inside.

Here is the question the section turns on. Does the screen move? A reasonable first guess is that it cannot. Whatever is watching your state is watching the variable, from the outside, and you did not change the variable, the list is the same list; you changed something buried three layers down inside it. A watcher outside a box should not see a page turn deep inside the box. That guess is wrong, and the reason it is wrong is the idea this whole lecture is built on.

When you wrap an object or a list in the state rune, Svelte does not watch it from the outside. It puts a thin wrapper in front of the object, a wrapper that gets to run a little code every time anyone reads one of the object's fields or writes one of them. Reading goes through the wrapper. Writing goes through the wrapper. So the wrapper sees everything, and it is the wrapper, not a distant watcher, that knows the screen must change. That wrapper is the central name of this lecture, and you will meet it constantly in documentation and in error messages, so here it is, in full: it is called a proxy. Let me say what a proxy is, plainly, in the sentence I will come back to all hour. A proxy is a wrapper that stands in front of an object and intercepts every read and write of its fields. Reading goes through the proxy; writing goes through the proxy; that is how the proxy knows the screen must change.

And the proxy goes all the way down. If your object holds another object, that inner one gets its own proxy; if it holds a list, the list gets a proxy; a proxy inside a proxy, as deep as the data goes. This is why flipping the flag on one task, deep in the list, moves the screen: that task has its own proxy, and its own proxy saw the write. The booklet calls this deep reactivity, under question two. You get the same thing when you add to the list. Push a new task onto the end, the plain way you would push onto any array, and the screen updates, and the new task arrives already wrapped in its own proxy. Anyone coming from React will feel something here, because over there, changing an array in place is a known way to get a screen that silently refuses to update, and you are taught to replace the array instead. Here the proxy is watching the array itself, so the plain, direct change is the right one.

So the name to carry from this section is proxy: a wrapper that stands in front of an object and intercepts every read and write of its fields, reaching all the way down. Reactivity, Svelte watching so the screen moves, is the proxy doing its work. And that fact has a shadow, which is the next section. If reactivity is the proxy, then everything depends on whether you are still holding the proxy, or whether you have somehow stepped off it.

## 4.4 The Live Thing And Its Dead Copy (booklet: "When state is an object or a list", question three; and "Passing state around", question ten)

The booklet keeps the next two ideas far apart. One is question three, here under objects and lists. The other is question ten, much later, under passing state into functions. They are not two ideas. Question three's destructuring, the shorthand that copies a field out of an object into a loose variable, and question ten's pass-by-value, the rule that a function receives copies of its arguments, are the same fact about copies wearing two outfits. So I am taking them together, and pulling question ten forward, because together they are the most common way people break their own reactivity without seeing how.

The idea needs one piece of plain JavaScript groundwork, about a thing and a copy of its value. When you have an object in a variable, the variable does not hold the object; it holds a reference to it, a way of reaching the one object. Two variables can hold references to the same single object. But the moment you take a value out of the object and put it in its own plain variable, you have made a copy of that value, and the copy has no connection back to where it came from. That is true in any JavaScript program, with or without Svelte.

Now the proxy comes back, the wrapper that stands in front of the object and intercepts every read and write. Your reactivity lives in that proxy. As long as you reach through the proxy, your reads and writes are seen and the screen stays in step. So here is the trap. There is a tidy shorthand in JavaScript for lifting a field out of an object into its own variable; the booklet shows it under question three, pulling the title out of an article. That shorthand has a name, and the name is destructuring. Let me fix it: destructuring is the JavaScript shorthand that copies a field out of an object into its own loose variable. You reach for destructuring to save typing. And then you change the article's title later, and the heading on the screen does not move. What happened? It is tempting to think Svelte lost track, that something broke. Nothing broke. When you destructured the title into its own variable, plain JavaScript made a copy of the title's value, right then, a copy that was never behind the proxy, that the proxy has no knowledge of. The real title, behind the proxy, did change. Your copy, sitting outside the proxy, did not, because nothing connects it to anything. And now you can see the rule rather than memorise it: destructuring copies a field into a loose variable outside the proxy, so the proxy never sees it again. Do not destructure reactive values; reach in through the proxy each time.

That same fact, worn as a different outfit, is question ten. There you call a function with a piece of state, the way you would call a function to greet someone by their name. Does the function get a live connection to your state, or the value as it stood at the moment of the call? It gets the value, copied in at that moment, and that has a name too: pass-by-value. Let me fix this one as well, because it is a ledger word. Pass-by-value is the rule that a function receives copies of its arguments, not living links to your variables. So pass-by-value hands the function a copy, frozen, exactly like the destructured title; both are values that left the proxy. Store that copy in a variable off to the side, change the state afterwards, and the stored copy does not care.

There is a softening detail, and it matters, because without it pass-by-value sounds more dangerous than it is. Inside a component, when you call that function right in the markup, the part of the file that paints the screen, Svelte runs that markup again whenever the state changes, and so it calls the function again, with the current value, and the result on screen stays current on its own. Pass-by-value only catches you when you reach for the result and park it in a plain variable off to the side. And for the one case where you genuinely need to hand the live value to a function that will keep it and read it again later, there is a clean move: instead of passing the value, you pass a tiny function that, when called, fetches the current value. The booklet shows the frozen line and the current line side by side under question ten.

So this section gives you two names, and they are one idea. Destructuring, the shorthand that copies a field out into a loose variable. Pass-by-value, the rule that a function receives copies of its arguments. Both make a copy that lives outside the proxy, and a copy outside the proxy is dead, because reactivity is the proxy and the copy is not on it. Everything left in this chapter is about where the proxy reaches, and where it stops.

## 4.5 What The Proxy Cannot Wrap By Itself (booklet: "Modeling data as a class", questions four and five; "Reactive built-ins and the variants", question six)

So far the proxy, the wrapper that intercepts every read and write, has appeared on its own, the moment you wrap a plain object or a plain array in the state rune. But not everything is a plain object, and for the things that are not, the proxy does not appear by itself. Three of the booklet's questions are about that, and I am gathering them, even though the booklet files one of them elsewhere.

The first is the class. When your data grows past a loose bag of fields, you reach for a class, a blueprint you define once, the fields it holds and the actions it can take, and stamp objects out of. Two names ride in here that you will use forever, so let me build them. The object you stamp out of a class is called an instance; you make one with the keyword new. To fix it: an instance is the object you stamp out from a class with the keyword new. And a class has a special setup function that runs the moment a new instance is born, which is called the constructor. Again, plainly: the constructor is the setup function that runs once, the moment an instance is born. A draft article is a natural class: each instance has its data, and it knows how to reset or publish itself. So you would expect that wrapping a draft instance in the state rune gives it a proxy, the way a plain object gets one. It does not, and the reason is care. A class instance is a more delicate thing than a plain object: it has methods, it may have private fields, it carries internal machinery, and putting a proxy around the whole instance, intercepting every read and write, could disturb that machinery. So Svelte leaves the instance alone, and asks you to switch reactivity on field by field, by marking each field you want reactive with the state rune, either on the field itself or on its first assignment inside the constructor, that setup function that runs when the instance is born. The booklet has the draft class under question four.

Question five sits right beside it, and it is a footnote to the class, not a fact about reactivity. It is a pure JavaScript trap about the small word that means "the object this method belongs to." When you wire a button straight at a draft instance's method, its reset, and the button is tapped, that small word inside the method no longer points at the instance. It points at the button, because in JavaScript what the word refers to is decided by how the function is called, not where it was written, and you handed the bare method over with nothing to anchor it. The fixes are small and the booklet shows them. It catches people often, and when it does, it is JavaScript catching them, not Svelte.

The third case is a family of built-in types, and it is the same lesson as the class. Beyond plain objects and arrays, JavaScript ships some special containers: a set, which holds unique values with no duplicates, exactly right for the identifiers of the posts a reader has liked; a map, for looking a value up by a key; a date; a web address. These are not plain objects. Each keeps its contents in its own internal machinery, which the proxy cannot see through, so wrapping them gives you no reactivity. Put a plain set of liked identifiers in the state rune, add one, and the heart on the screen stays dark. Svelte's answer is to ship reactive versions of these four, with the same names and methods you already know, but built with the proxy's behaviour inside them from the start. You import the reactive set, written as the two words Svelte and Set joined into one, from a small package named svelte, slash, reactivity, and you use it as you would the plain one. The booklet has it under question six. I have moved that question back here, out of the variants where the booklet files it, because it is the class's lesson exactly: the proxy is automatic only for plain objects and arrays. For a class instance you switch reactivity on field by field. For these built-in types you reach for a version that has the proxy built in.

So the consolidation of this section is one rule with three names attached. The proxy wraps plain objects and arrays on its own, and nothing else on its own. A class instance, the object you stamped out with new, you make reactive field by field, marking each with the state rune in the constructor or on the field. The built-in set, map, date, and web address you replace with the reactive versions from svelte slash reactivity. The next section is about the proxy again, but from the other side: not where it fails to appear, but where you turn it down on purpose.

## 4.6 Turning The Proxy Down, Off, And Sideways: The Variants (booklet: "Reactive built-ins and the variants", questions seven, eight, and nine)

The proxy, the wrapper that intercepts every read and write reaching all the way down, is a fine default, and it is not free. Wrapping an object, and everything inside it, in proxies costs a little, and most of the time that little is nothing you would notice. But the state rune gives you three deliberate adjustments, and each is a knob on the proxy.

The first knob turns the depth off. Take a feed, the endless kind, that grows to thousands of posts, and that you only ever replace wholesale or add to at the end; you never reach in and edit one post in place. Giving every one of those thousands of posts, and every field inside them, its own proxy, only so the list can be shown, is real work for no return. For exactly that, there is a raw form of the state rune, written as the state rune followed by the word raw, which holds the value with no proxy inside at all. It comes with one firm condition, the other side of the same coin: with no proxy watching the parts, changing a part does nothing, and the only change the raw form notices is replacing the whole value with a new one. That fits a feed, because the natural way to grow a feed is to build a new list from the old one plus the next page and assign that, which is a replacement. The honest caution, which the Svelte team presses, is not to reach for the raw form out of a vague worry about speed. The ordinary proxy is fast enough for almost everything. Measure first, and use the raw form when you actually have thousands of things, or a value you only ever swap. The booklet has it under question seven.

The second knob strips the proxy off, on the way out. What you are holding, remember, is the proxy, not the bare object. That is right inside Svelte, but the moment you hand your data to something outside Svelte, a charting library, or the browser's own function for deep-copying a value, those outsiders were never built to understand the proxy, and they choke on it. So there is a snapshot form, the state rune followed by the word snapshot, which gives you back a plain, ordinary copy of the data with the proxy stripped off, safe to hand to anyone. The booklet has it under question eight.

The third knob changes when the proxy reports. Ordinarily Svelte is deliberate about timing, gathering changes and applying them together for a smooth result, and now and then a change waiting on something slow can lag by a beat. Almost always that is what you want. But once in a while you want an instant flicker of feedback to a tap, the section link the reader pressed a moment ago lighting up at once, before the next page has loaded. For that there is an eager form, the state rune followed by the word eager, which shows the change the instant it happens, skipping the usual coordination. It is a specialist's tool, for feedback to a direct action and nothing else. The booklet has it under question nine.

So three knobs on the one proxy. The raw form, no proxy inside, replace the whole value to update it. The snapshot form, the proxy stripped off, for handing data to the outside world. The eager form, the proxy reporting at once, for instant feedback. With those, the proxy is in your hands, except for one last thing about it: where it gets built.

## 4.7 The Proxy Is Wired One File At A Time (booklet: "Sharing state across files", questions eleven and twelve)

Everything so far has lived inside a single component. But some state belongs to no single component. The logged-in reader is the clearest case: the greeting at the top wants it, the comment box deep in an article wants it, a dozen far-apart corners want the same one. Handing it down through every component in between would be miserable. So you lift it out of the components entirely, into a file that other files import from. That kind of file has a name: a module. To fix it: a module is an ordinary file that other files import from. You keep the reader in a module, for everyone to share.

There is one catch, and it reaches back to the first idea of the course, that Svelte is a compiler. The state rune is not an ordinary function that runs in the browser; it is an instruction to the compiler, which rewrites your reads and writes of that state into the proxy machinery when it processes your file. For that to happen in a module, the file has to be marked so the compiler knows to process it, which you do by ending its name in dot svelte dot t s, rather than plain dot t s. So: a module whose name ends in dot svelte dot t s is one the compiler processes for runes. Now the state rune works there. But here is the consequence that catches people, and it follows from the compiler working on one file at a time. If you put state in that module, export it, and then reassign it inside the module, another file that imports it was compiled separately, and that other file never learned that the name it imported is secretly backed by a proxy and needs the special handling. So it would receive, not your value, but the raw machinery underneath, and the connection would break at the border between the two files.

The way around it falls out of naming the cause. The trouble is reassigning an exported name across a file boundary, so you arrange never to do that. The first way, under the booklet's question eleven, is to export an object and change a property on it, rather than reassigning the variable that holds the object. You never reassign the export; you set a field on the shared object; and because that object carries its proxy with it, the change reaches everyone who imported it. The second way, question twelve, is to not export the state at all: keep it private inside the module, and export instead a small handful of functions, one to read the state, others to change it. Every read and write then happens inside the one file the compiler controls, and the outside world only ever calls the functions. That second way has a quiet bonus: a single doorway, one place every change passes through, where you could check it, or record it, or send it to the server. The booklet has both, with the logged-in reader.

So the names from this section are module and the dot svelte dot t s file. A module is an ordinary file that other files import from; a module ending in dot svelte dot t s is one the compiler processes for runes. And the lesson under them is that even the proxy has a boundary, the boundary of a file, because the compiler lays the wiring one file at a time. The next section steps back from state entirely, to place it among its neighbours.

## 4.8 Choosing Among The Three, And Two Loose Ends (booklet: "Going further", questions thirteen, fourteen, and fifteen)

The booklet's last three are gathered under going further, and one of them is the right note to end the teaching on, because it steps back from the state rune and sets it beside its two siblings.

That is question fourteen, and it is a question of choosing. The clap count is a value you hold and change over time; that is state, and the state rune, the marker that makes a variable reactive, is its tool. But take the little label on a story that says it is a five minute read. That number is not held anywhere. It is worked out from the length of the article's body. A value computed from other values is not state at all, and forcing it into a state rune, recomputing it by hand whenever the body changes, is the surest way to get a label that quietly goes stale. It wants a different rune, the derived rune, which is the whole subject of the next lecture, and which recomputes itself whenever its ingredients change. I am naming it and leaving it there, a deferral, not a half-explanation. And there is a third kind of thing again: not a value you hold, and not a value you compute, but an action on the world outside your data, saving to a server, drawing to a canvas. That is the effect rune, with its own hour later, named here and left for then. So the question to ask of any piece of behaviour is which of the three it is. Holding a value is the state rune. Computing a value is the derived rune. Doing something in the world is the effect rune. Get that fork right, and most of the rest follows.

Two loose ends close the booklet, and they are quick. Question thirteen asks whether you can put two components in one file, the article card and the clap button together. You cannot; one file is one component, and to show two components, and how they talk, you write two files. Question fifteen is for anyone arriving from React or from Vue, and it is a translation. The state rune is, near enough, Vue's reactive value with the small ceremony around it taken away, and React's state hook without the separate setter and without the rule never to change the value directly. The deepest difference shows only later, in how the reusable pieces behave, and it can wait.

So the close of this section is the fork: the state rune for a value you hold, the derived rune for a value you compute, the effect rune for an action on the world. This lecture was the first of the three.

## 4.9 The One Mechanism (synthesis)

Step back, and the fifteen questions fall into one mechanism and a handful of names.

The mechanism is this. Reactivity in Svelte is the compiler, ahead of time, putting a proxy around your state. Let me run the names one last time, in their final, tightest form, because these are the words you will carry into the documentation and the error messages.

The state rune, the dollar sign followed by the word state, is the marker that tells the compiler to make a variable reactive. Reactive means Svelte watches the variable, so the screen moves when the variable moves. For an object or a list, the state rune installs a proxy: a wrapper that stands in front of the object and intercepts every read and write of its fields, reaching all the way down, so changing anything inside the object, or adding to it, moves the screen. Where you fall off the proxy, you get a dead copy, and there are two ways to fall off, which are one idea. Destructuring, the shorthand that copies a field out of an object into a loose variable. And pass-by-value, the rule that a function receives copies of its arguments. Both make a copy that lives outside the proxy, and a copy outside the proxy is dead. What the proxy cannot wrap on its own you handle by hand: a class instance, the object you stamp out with the keyword new, you make reactive field by field, in its constructor, the setup function that runs when the instance is born; and the built-in set, map, date, and web address you import already reactive from svelte slash reactivity. The proxy has three knobs: the raw form, no proxy inside, for great masses of data you only swap; the snapshot form, the proxy stripped off, for the outside world; the eager form, reporting at once, for instant feedback. And the proxy has a boundary, the file, because the compiler wires it one file at a time, which is why shared state lives in a module ending in dot svelte dot t s and is exported as an object you mutate, or behind functions, never as a name you reassign.

That accounts for every one of the booklet's fifteen. Question three and question ten, destructuring and pass-by-value, were the same idea, the live thing and its dead copy, taken together. Questions four and five were a class and a piece of plain JavaScript that travels with it. Question six I moved out of the variants to sit with the class, because the built-in types are the class's lesson. And the derived rune and the effect rune, the two tools that are not the state rune, I named but deferred, the derived rune to the very next lecture.

That next lecture is the derived rune, for values computed rather than held. It rests directly on the proxy you now know, which makes it the natural next step.
