# 04 Extra. JavaScript Foundations, Part One: From Objects To The Reactive Graph

## Orientation

This is a companion to the state chapter, and it stands on it. In that chapter you met the state rune, you saw the screen follow a variable, and you heard two words used as names without being fully opened: signal, and proxy. This lesson opens them, and everything underneath them. It is a foundations lesson, so it has no booklet of its own. The code you need already sits in the state booklet, and wherever one of these foundations holds up a particular entry there, I will say which entry, so a reader with that booklet open is never lost.

Here is what you will carry away. You will know the several different ways JavaScript builds an object, and how a function can hold private memory. You will know what interception is, the single idea every reactive framework is built on, and why being able to intercept a read or a write is what lets a framework wire itself into your plain code. You will know what a proxy actually is, what a signal actually is, and why they are not the same kind of thing even though one looks like the other. You will know the shape of the structure that holds a whole framework together, and whether it is a graph or a tree. And you will know, in exact terms, how React, how Vue, and how Svelte each solve the one shared problem, keeping the screen in step with the data, by very different means.

We will cross several fields on the way, and I will name each as we enter it: a little functional programming, a good deal of metaprogramming, three classic design patterns, and two data structures. We begin with the most ordinary thing in the language, the object, because every other idea is built on it.

## 1. Objects, And The Several Roads To One (groundwork; underlies the article object throughout the state booklet)

Let me bring back the world from the state chapter. We are building The National Times, a newsroom and its website, and the thing on screen we keep returning to is an article, which holds a headline, a body, and a count of claps. That article is an object, so let me lay down what an object is, plainly, before we use it for anything.

An object, in JavaScript, is a bag of named slots. Each slot has a name, called a key, and a value. The article object has a slot named headline holding a string, a slot named body holding a longer string, and a slot named claps holding a number. That is the whole idea: names pointing to values. If you know Python, the closest familiar thing is a dictionary, a dict, which is also names pointing to values. Hold that comparison lightly, though, because a JavaScript object does double duty: it is both the everyday key-value bag that a Python dict is, and the thing you build instances from, which in Python is a class instance. JavaScript blurs those two into one kind of thing, and that blur is worth knowing about.

Now the part that surprises people coming from other languages: there is not one way to make an object in JavaScript, there are several, and they are genuinely different roads to a similar destination. Let me walk the main ones, because each road gives you a different power, and one of them leads straight to the next section.

The first road is the object literal. You write the object out directly, its slots and their values, right there in the code, and you have an object. This is the article exactly as you have seen it: headline, body, claps, written down. No ceremony, no blueprint. When you want one object, this is the road. Python has the same move with a dict written out directly.

The second road is the constructor function, and it is mostly history now, but it explains the third road, so it is worth a sentence. Long before JavaScript had the word class, you made many similar objects by writing an ordinary function that set up the slots, and calling it with the keyword new. The keyword new makes a fresh empty object, runs your function with that new object as its subject, and hands it back. People wrote a function called something like Article, and called new Article, and got article objects.

The third road is the class, which you met in the state chapter when we built the draft. A class is a blueprint: you describe the shape once, the slots and the actions, called methods, and then stamp out instances with the keyword new. Here is the thing to know, the detail that pays off later: in JavaScript, the class keyword is what we call syntactic sugar. It is a clean, modern spelling on top of that older constructor-function machinery. Underneath, a class is still a function and an object it points to. Which brings in the one structural word you need from this section, the prototype.

A prototype is another object that your object falls back to for any slot it does not have of its own. When you ask an article for a slot, JavaScript looks on the article itself first, and if the slot is not there, it follows a link to the article's prototype and looks there, and up a chain if it must. Methods defined in a class do not sit on each instance; they sit once on a shared prototype object, and every instance falls back to it. So a thousand article instances share one copy of each method, through the prototype. If you know Python, this fallback-to-another-object is close to how Python looks up an attribute on the instance, then on its class, then up the chain of base classes. JavaScript does it object to object, through the prototype link, rather than instance to class, but the spirit, look here, then fall back to there, is the same.

The fourth road is the one that matters most for what comes next, and it is called the factory function. A factory function is plainly a function that builds an object and returns it. You call the function, it assembles an object, perhaps an article, and hands it back. No new, no class, no prototype, ordinarily a plain object literal built inside and returned. On its face this looks like a long way around to make an object you could have written directly. The reason it is powerful is not visible yet, because the power comes from what the function can hide inside itself while it builds the object. That is the whole of the next section.

And there is a fifth road I will only name, the built-in create method, which makes a new object with a prototype you choose directly. You will meet it occasionally; it is the bare-metal version of the prototype idea.

So, several roads: write it directly as a literal, stamp it from a class with new, or build and return it from a factory function. The last road handed an object back out of a function. A function that returns things, a function that holds things, a function that contains another function, is the next foundation, and it is where private data, the data nothing on the outside can touch, comes from.

## 2. Functions Are Values, And Closures Are Private Memory (groundwork; underlies state booklet Q12, the private-state module)

There is a move that looks strange at first sight: putting functions inside functions, and handing functions back out of functions. It is not strange at all; it is one of the deepest features of the language, and almost everything elegant in JavaScript rests on it. Let me build it from the bottom.

The first fact is that in JavaScript a function is a value. That phrase has a standard name: functions are first-class. A first-class function is one you can treat like any other value, a number or a string. You can store a function in a variable. You can put a function in a slot of an object. You can pass a function as an argument to another function. You can return a function as the result of another function. It is data that happens to be runnable. You have used this already without naming it: in the state chapter, when you handed a button the little function to run on a click, you were passing a function as a value. Python has this too; a Python function is also a value you can pass around and return, so the idea should feel familiar even if the name does not.

The second fact builds on the first. A function that takes another function as an argument, or returns a function as its result, has a name: it is a higher-order function. Higher-order, because it operates one level up, on functions themselves, rather than on plain data. A function that returns a function is the case to hold onto, because that is the literal form of a function defined inside another.

Now the third fact, which is the real prize, and the one genuinely subtle idea in this section, so I will go slowly. When you define a function inside another function, the inner function can see and use the variables of the outer function. That much might seem ordinary. The remarkable part is what happens when the inner function outlives the outer call. Here is the factory function from the last section again, building a clap counter for an article this time. The factory declares a private variable, the count, starting at zero. Inside it, it defines two small functions: one that raises the count by one, and one that reads the count back. Then the factory returns those two functions, bundled together, and ends. The factory call is over. Its local variables would, you might expect, be gone, swept away when the function returned.

The plausible expectation there is that the count is gone, because the function that declared it has finished, and finished functions usually take their local variables with them. That expectation is wrong, and the reason it is wrong is the idea called the closure. A closure is a function that remembers the variables that surrounded it when it was created, and keeps them alive for as long as the function itself is alive. The two little functions the factory returned were created inside the factory, surrounded by the count, so they closed over the count. They carry it with them. The factory call ended, but the count did not vanish, because two living functions still hold it. Call the raise function, and the very same count goes up. Call the read function, and you see the new value. The count survived its birthplace, held alive by the functions that close over it.

Here is why that is not a curiosity but a tool. Nothing outside those two returned functions can reach the count. There is no slot on any object holding it, no name in the outer program pointing at it. The only way to touch the count is through the two functions the factory chose to hand out. The count is private, truly private, hidden by the closure, reachable only through a controlled door. That is encapsulation, the idea from the state chapter, achieved with nothing but a function and the variables it closed over. No class required.

If you come from Python, you have seen this. A Python function defined inside another can use the outer function's variables, and if you return it, it remembers them; that is a Python closure. The one wrinkle Python adds is that to reassign such a captured variable from the inner function you must declare it nonlocal, a bookkeeping word JavaScript does not require. But the shape is identical: an inner function, returned, carrying private memory from where it was born.

And now I can connect this straight to the state booklet, to entry twelve, the encapsulated sharing pattern. There, you kept a piece of state private inside a module, did not export it, and exported functions instead, a reader to get it and actions to change it. That module is a closure. The private state is the count in our factory; the exported functions are the raise and read we handed out. The module file is the factory, and importing its functions is holding the door handles to memory you cannot otherwise reach. The pattern you learned as a Svelte rule is, underneath, the oldest trick in JavaScript: a closure guarding private state.

So functions are values you can pass and return, and a function returned from another carries that other's variables alive inside it as private memory. We hid data behind functions. The next question turns that around. What if you want the opposite surface: not a function the caller must call, but a plain-looking property the caller reads like any other, while a function secretly runs underneath? That is the first rung of interception, and it is called a getter.

## 3. Getters And Setters: When A Property Is Secretly A Function (groundwork; underlies the signal's get and set from the state chapter)

Stay with the article. It holds a headline and a body, plain stored slots: read the headline, you get the string that is sitting there. Now suppose you want a reading-time label, the small five-minute-read line, computed from the length of the body. You could store it in a slot, but then it would go stale the moment the body changed, which is the exact staleness the state booklet warned about in entry fourteen. What you want is a slot that looks like an ordinary property from the outside, you read article dot reading-time, but that secretly runs a calculation every time you read it. JavaScript lets you do exactly this, and the feature is the getter.

Let me define it carefully, because it is the seed of everything reactive. A getter is a property that is secretly a function, so that reading it runs code instead of fetching a stored value. Its twin, the setter, is a property that runs a function when you write to it instead of storing the value directly. From the caller's side, nothing looks unusual. They write article dot reading-time, the plain syntax of reading a property, with no parentheses, no sign that anything is being called. But underneath, your get function runs, counts the words in the body, and returns the label. Write to a property with a setter, and your set function runs with the new value and does whatever you decide, perhaps validating it, perhaps storing it somewhere else. The plain face of a property, the hidden body of a function.

You can attach a getter and setter three ways, and I will name them so you recognize them. You can write them directly in an object literal, marking a slot with the little words get and set in front of a function. You can write them in a class, the same way, and then every instance has them. Or you can attach them after the fact to an existing object with the built-in define-property method, which lets you say, in detail, this slot is not a plain value, it is this get function and this set function. That third way is worth filing away, because a famous framework used it as its whole reactivity engine, as we will see at the end.

For the comparison, this is precisely Python's property decorator. In Python you write a method that computes a value, put the at-sign property line above it, and from then on callers read it as a plain attribute, no parentheses, while your method runs underneath; a matching at-sign setter line gives you the write side. JavaScript's getter and Python's property decorator are the same feature with different spellings: a property whose read or write is secretly a function call. I am dwelling on the sameness because it tells you this is not a framework trick, it is a base capability of both languages.

Now the point that makes this the first rung of a ladder. A getter is interception. The read article dot reading-time looks like a plain fetch, but you have inserted yourself into it; code of yours runs in the gap between the request and the answer. Sit with how much that gives you. If, inside that get function, you did not only compute the label but also quietly wrote down who is asking, you would have the beginnings of dependency tracking, the bookkeeping that reactivity is made of. We are not there yet, but the door is now open: a read can run code, so a read can be made to do bookkeeping. Keep that sentence; it returns as the heart of the whole lesson.

But a getter has a hard limit, and the limit is what forces the next, bigger tool. A getter intercepts exactly one property, and one you named in advance. You decided, ahead of time, that reading-time would be an accessor. If a caller reads a slot you never declared, no getter runs. If code adds a brand-new slot to the object later, there is no getter on it. And operations that are not simple property reads, asking how many items are in a list, pushing a new item onto it, slip past entirely, because they are not reads of a named slot. To intercept everything, every property, including the ones you did not predeclare and the ones added in the future, and even method calls, you need a heavier instrument. JavaScript calls it the Proxy.

## 4. The Proxy: Intercepting Everything, And Why Interception Builds Frameworks (groundwork; underlies state booklet Q2, Q6, Q7, Q8)

Here is the instrument the state chapter named but did not open, and it deserves to be opened properly. Four questions frame it: what is it, why do we need it, when do we use it, and why is intercepting things a good thing at all. Let me answer all four, in order, on the article.

First, what it is. A proxy is an object that stands in front of another object, the target, and intercepts the basic operations performed on it, running your code in between the operation and its effect. You wrap the article in a proxy, hand the proxy out in the article's place, and from then on every read of a slot, every write to a slot, every check of whether a slot exists, every deletion, even every call if the target is a function, can be made to run code of yours first. The standard word for the function you supply for one kind of operation is a trap. A trap is the function a proxy runs for one kind of operation: a get trap for reads, a set trap for writes, and others for the rest. You give the proxy a get trap, and now reading any slot on the article, named or not, runs it.

Set this directly against the getter from the last section, because the contrast is the whole reason the proxy exists. A getter intercepts one property, chosen in advance. A proxy intercepts all of them, including properties you never declared and properties added long after the proxy was made, and operations that are not plain reads. This is exactly why, in the state booklet, putting an object in the state rune lets you reach in and flip a nested field, or push onto a list, and have the screen follow, that was entry two. The object was wrapped in a proxy, and the proxy's traps catch the field write and the push alike. And it is exactly why, in entry six, a plain Set did not react: a Set keeps its contents in private internal storage, reached only through its own methods, and those internal operations are not property reads or writes on the object, so no trap fires. The proxy is total over property access, and blind to a collection's private internals. Both facts now follow from one mechanism, instead of being two rules to memorize.

Second, why we need it, which is really the same as the fourth question, why interception is a good thing. Name the field first: this is metaprogramming. Metaprogramming is writing code whose job is to intercept or reshape what other code does, rather than to compute a result of its own. The proxy is a metaprogramming tool, and the design-patterns literature has a name for the shape of it too: the Proxy pattern, a stand-in object that controls access to the real one. Now, why is that good. Because interception is how a framework wires itself into your plain code without making you do the wiring. Think about what reactivity needs: every time you read a piece of state, something must record that this part of the screen now depends on it, and every time you change it, something must notify the parts that depended on it. If there were no interception, you would have to write those two steps by hand, every single time, a record-this call after every read and a notify-them call after every write, scattered through all your code. That is miserable and impossible to keep correct. Interception removes it. You write a plain read and a plain write, and the framework does the recording and the notifying for you, invisibly, in the gap the proxy opened. The principle is worth stating plainly: the moment you can intercept reads and writes before and after, you can build the wiring of a framework, because the framework can do all its bookkeeping in the space between the access and the value. That is the good thing interception buys.

Third, when you use it. You reach for a proxy when you need to intercept access broadly and dynamically, across all of an object's properties and the ones not yet born, which is precisely a reactivity system's need, and also the need of things like validation layers, logging wrappers, and lazy-loading stand-ins. You do not reach for it for a single known property; a getter is lighter and clearer for that.

Now the Python comparison, because Python draws the getter-versus-proxy line beautifully. Python's property decorator, which we met, intercepts one named attribute, exactly like a JavaScript getter. But Python also has catch-all hooks, the get-attribute and set-attribute methods written with leading and trailing double underscores, which run for any attribute access on an object, including ones you never defined. Those catch-all dunder hooks are Python's version of a proxy's traps: total interception over attribute access, not one named slot. So the mapping is clean. Python property decorator is JavaScript getter, one attribute. Python's double-underscore get-attribute hook is JavaScript's proxy get trap, all attributes. Same two rungs of the same ladder, in both languages.

And there is a further comparison worth drawing, the at-sign written above a Python function. That is a decorator, and it is worth pulling apart, because it is interception of a different operation: not reading a property, but calling a function. A Python decorator wraps a function so that calling the function runs extra code before and after the original. You write the at-sign and a name on the line above a function, and from then on the decorated function is really the wrapper, which can log the call, time it, check permissions, then run the real one, then do more after. The design-patterns name for this is the Decorator pattern, a wrapper that adds behavior around something without changing its inside. JavaScript does the same thing in two ways. A higher-order function from section two can take a function and return a wrapped version of it, before-and-after behavior around a call, which is a decorator by hand. And a proxy has a call trap, named apply, that intercepts calling the thing behind it, which is interception of a function call at the language level. JavaScript is in the middle of adding the at-sign decorator spelling as a built-in, and the typed dialect of it has had decorators for years, but the concept, wrap a function to run code around it, is already familiar from Python, and it is the same family as the proxy: interception, metaprogramming, code that operates on other code.

So the proxy is total interception over an object, the heavy instrument of metaprogramming, and interception is good because it lets a framework do its bookkeeping invisibly in the gap. But I have kept saying bookkeeping without saying what the books contain. The thing the framework records in the get trap, and acts on in the set trap, has a precise shape and a classic name. It is the observer pattern, and it is the true heart of reactivity, so it gets the most careful treatment of anything in this lesson.

## 5. The Observer Pattern: Track On Read, Trigger On Write (groundwork; the mechanism beneath all reactivity)

This is the center of the whole subject, so let me build it slowly and concretely, on the reader from the state chapter, the person logged into The National Times.

Two places on the page care about the logged-in reader. The masthead greets them by name across the top. The comment form signs a draft comment with their name as the byline. Both read the same one value, the reader's name. Now state the problem in its barest form: when the reader logs out, or changes their display name, both of those places must update, and nothing else should have to know about it in advance. The masthead should not have to be told, by hand, every place the name might change. The name itself should somehow know who is watching it, and tell them.

That is the observer pattern, and here is its definition. The observer pattern is an arrangement in which a value keeps a list of everyone who depends on it, and notifies every one of them the moment it changes. The value being watched is sometimes called the subject; the watchers are the observers. In the reactive version the framework uses, the same idea goes by the working name dependency tracking. Two motions make it run, and I want you to hold both as a pair, because they are the two halves of one machine.

The first motion is track on read. When some computation reads the value, the value writes that computation down on its list of dependents. Read the reader's name while drawing the masthead, and the reader's name now knows the masthead depends on it. This is where interception finally earns its keep: the recording happens inside the get, the getter or the proxy trap from the last two sections, so it costs you nothing to write. You read the name plainly; the read, intercepted, quietly adds the masthead to the list. The second motion is trigger on write. When the value changes, it walks its list of dependents and tells each one to run again. The reader logs out, the name is set to nothing, and in that set, intercepted, the name walks its list, masthead and comment byline, and tells both to redraw. The masthead reruns and the greeting clears; the byline reruns and falls back to guest. Two observers, one subject, notified by the subject itself.

Now the genuinely subtle part, the piece that is hardest to reconstruct unaided, so I will spend the most time here. How does the value, in its get, know which computation is reading it? The read is only a read; the name has no obvious way to know whether it is the masthead asking, or the byline, or something else. The answer is a small piece of shared bookkeeping the framework keeps off to the side: at any moment, the framework knows which computation is currently running. Before it runs the masthead's drawing code, it sets a marker, the current computation is the masthead, and then runs it. Any value read during that run looks at the marker, sees the masthead, and records the masthead. When the masthead's run ends, the marker is cleared or set back. So a read is never really anonymous during a tracked computation; the framework has quietly stamped the room with whose turn it is, and every value read takes that stamp. That is the trick that makes the dependency list build itself. It is invisible precisely because interception hides it inside the ordinary-looking read.

Let me make the contrast that proves the pattern is doing real work, the kind of contrast the state booklet's mechanisms always drew. Without this pattern, you would wire each connection by hand: after computing the greeting you would call something like subscribe, and in the logout code you would call notify, and you would have to remember every such pair, forever, with no help. That is, in fact, close to what older code made you do, and close to what React's setter still makes you signal explicitly. With the pattern, plus interception, the subscribe happens automatically inside every read and the notify automatically inside every write, and you wrote neither. The difference between those two worlds, hand-wired and self-wiring, is the difference between bookkeeping you maintain and bookkeeping the framework maintains, and it is the whole reason reactive frameworks feel like magic until you see this gear.

For the Python mind, this pattern is not a language feature in either language; it is something you build. In Python you would keep a list of callbacks on the subject, append to it when something starts watching, and loop over it to call them when the subject changes; that is the observer pattern by hand, and it is a standard exercise. JavaScript frameworks build the very same thing, then use interception, getters and proxies, to perform the appending and the looping for you. The pattern is universal; the automation is what the language tools provide.

So the observer pattern is a subject that holds a list of its dependents, adds to that list on every read, intercepted, and walks that list to notify on every write, intercepted, with a hidden marker telling each read whose dependency it is. A value bundled together with its list of dependents, handing its data out through a tracked get and notifying through a triggered set, that bundle is so useful that modern frameworks give it a name and make it the atom of everything. The name is the signal.

## 6. The Signal, And Why It Is Not A Proxy (groundwork; opens the word the state chapter only named)

There is a sharp and common intuition about the signal worth meeting head on, because it is right. The signal seems to look like a proxy, walk like a proxy, talk like a proxy, yet be something else entirely. That is precisely the situation, and now we have the parts to say what the something-else is.

Start with what a signal is, built from the last section. A signal is a single reactive value bundled with the list of computations that have read it, handing its value out through a get that records the reader, and, on a set, telling every recorded reader to run again. Read that against the observer pattern and you will see a signal is nothing more than the observer pattern packaged into one small reusable object, for one value. The reader's name, made a signal, is the name plus its watcher list, with track-on-read and trigger-on-write built in. That is all a signal is: one node of reactivity, the smallest possible unit, the subject of the observer pattern wearing a tidy wrapper.

Now the distinction itself, and I will make it sharp, because conflating these two is the central confusion and it is worth a minute of precision. A proxy and a signal are different kinds of thing, from different worlds.

A proxy is a feature of the JavaScript language itself. It is general-purpose interception. It wraps an object and catches operations on that object's many properties. It knows nothing about reactivity; you could use a proxy to log accesses, or guard them, or fake them, with no reactivity anywhere. It is a tool for intercepting, full stop. A signal is not a language feature at all. It is a userland construct, something a library author builds out of ordinary code, and it is purpose-built for one job, being a reactive value that tracks its dependents. The language has no signal keyword; signals are an invention of reactivity libraries.

So why does one look like the other? Because they share a surface, and the shared surface is interception of get and set. A proxy makes reading and writing a property run code. A signal makes reading and writing its value run code, the tracking and the triggering. Both are things you touch with a get and a set that secretly do work, so from a distance they rhyme. But a proxy is a generic interceptor spread across all of an object's properties, while a signal is a single reactive node holding one value and one watcher list. One is breadth, general interception over a whole object; the other is depth, the full reactivity machine for one value.

And here is how Svelte composes the two, which finally cashes the phrase the state chapter used, that a proxy is a bundle of signals. When you put a plain number in the state rune, there is no object to wrap, so Svelte makes a single signal, and that is the whole story for a primitive: one signal, no proxy. When you put an object in the state rune, Svelte wraps it in a proxy, and behind that proxy it creates one signal for each property you touch. The proxy's get trap, for a given property, reads from and subscribes to that property's signal; the proxy's set trap writes that signal and triggers it. So the proxy is the automation layer, the front desk that, for every property, quietly stands up a signal and routes access to it, deeply, all the way down through nested objects. The signal is the worker behind each slot, doing the actual tracking. A bundle of signals, fronted by a proxy: that is a deep reactive object, and now the phrase is a mechanism, not a slogan.

This even re-explains the raw variant from the state booklet, entry seven, cleanly. Raw state keeps the single top-level signal but skips the proxy. With no proxy, no per-property signals are ever created, so reaching into the value changes nothing, no inner signal exists to trigger. Only replacing the whole value fires, because that is a set on the one signal that does exist. Mutation ignored, reassignment tracked, and you could now derive that yourself from the architecture: no proxy means no inner signals means only the outer signal can fire, and the outer signal fires on assignment.

So a signal is one reactivity node, the observer pattern for a single value, a userland invention, not the language's proxy, though it shares the intercepted get and set that make it resemble one. The reader is one signal. The greeting computed from the reader is another kind of node. The masthead that displays the greeting is a third. They are connected, the greeting reads the reader, the masthead reads the greeting, so arrows run between them. Many such nodes and arrows form a structure, and that structure is the answer to your largest question: the thing that actually holds a whole framework together.

## 7. The Dependency Graph: The Structure That Holds It Together (groundwork; answers "is it a graph or a tree?")

Three questions press here: whether all the reactive values get traced into one huge structure, whether that structure is a graph, and whether a graph is merely an object shaped like a tree. The answers are yes, a graph, and no, a graph is more general than a tree. Let me build the structure and name its parts, because this is the abstraction that holds a reactive framework together, and it is a data structure with a precise identity.

There are three kinds of node in this structure, and you met two of them in the state booklet's triage, entry fourteen, hold, compute, or do. The first kind is the source, a piece of held state: a signal you write to directly, the reader, the clap count, the article's body. The second kind is the derived, a computed value: the greeting built from the reader, the reading-time built from the body. A derived reads other nodes and produces a value of its own, and it is itself a node others can read. The third kind is the effect, a leaf that does something in the world rather than producing a value: the code that writes the greeting into the masthead on the actual page. Sources at the top, deriveds in the middle reading sources, effects at the bottom reading deriveds and touching the screen. Hold, compute, do, arranged as a structure.

The arrows between the nodes are the dependencies, and they are built by the observer pattern from two sections ago. An arrow runs from a value to every computation that read it. The reader has an arrow to the greeting, because the greeting read the reader. The greeting has an arrow to the masthead effect, because the effect read the greeting. Every read you write becomes an arrow the framework records.

Now name the structure. A graph, in the data-structures sense, is a set of nodes with arrows between them. This one is directed, because the arrows have a direction, this depends on that, not the reverse. And it is acyclic, meaning it has no loops: a value cannot, in the end, depend on itself, because that would be a definition with no bottom. A directed graph with no cycles has a standard name, a directed acyclic graph. That is the formal identity of the thing holding a reactive framework together: the whole app's reactivity is one large directed acyclic graph of sources, deriveds, and effects, wired by the reads you wrote.

This is also where the graph-versus-tree question resolves precisely, because the difference matters here. A tree is a special, more restrictive graph: it has a single root, and exactly one path from the root to every node, which means no node has two parents and there are no loops. A family tree, a folder hierarchy, an outline. A general graph relaxes that: a node may have many parents, many arrows pointing into it. The dependency structure is a graph and not a tree, and the reason is concrete. One source can feed many dependents: the reader feeds both the greeting and, say, a permissions check, two arrows out. And one derived can read many sources: a derived might combine the reader and the article, two arrows in, so it has two parents, which a tree forbids. There is even a classic shape here worth knowing by name, the diamond: one source feeds two deriveds, and a single effect reads both of those deriveds, so paths split and rejoin. In a diamond, a careful reactive system must update in an order that respects all the arrows, computing both middle deriveds before the bottom effect, so the effect never runs on a half-updated mix. That ordering is a graph traversal in what is called topological order, and getting it right is what separates a serious signal library from a toy one, where the failure even has a name, a glitch, the brief showing of an inconsistent in-between state. It is worth naming because the diamond is where the graph stops being a tree and starts demanding real algorithms.

So, when a source changes, the framework does not blindly redo everything. It follows the arrows out of that source, recomputes the deriveds that depended on it, and reruns the effects that depended on those, in an order that respects the arrows, and it touches nothing the change could not reach. That selective, arrow-following propagation is the core algorithm of fine-grained reactivity, and it operates on the directed acyclic graph we have now built.

One more line, to prevent the confusion that would otherwise bite in the next section. This dependency graph is data depending on data. It is not the page. The reader, the greeting, the reading-time, these are values, and the graph is how their changes flow into one another. The page is a different structure entirely, a separate tree, and the effects at the bottom of our graph are the bridge: they reach out of the data world and edit the page. So to finish the picture we need to know what the page actually is, as a structure, and that is the DOM.

## 8. The DOM: Tag, Element, And Tree (groundwork; underlies all rendering, in every framework)

The difference between an HTML tag and a DOM element is one worth nailing, because the entire rendering story, and the differences between the three frameworks, ride on it. Let me build it from the source text up.

When you write a web page, you write HTML, and HTML is text. A tag, like the button on our article card, is characters in a file: an opening angle bracket, the word button, a closing bracket, some text, and a closing tag. That is all a tag is, markup, static text describing what should exist. By itself it does nothing and reacts to nothing; it is a description.

The browser reads that text and does something transformative with it: it parses the text and builds, in memory, a tree of live objects, one object for each tag. That in-memory tree of objects is the DOM. Let me define it. The DOM, the document object model, is the tree of live objects the browser builds from your HTML, one object per element, that JavaScript can read and change to alter the page. And now the distinction is exact. The tag is the text in the source. The element is the live object the browser made from that text. Your button tag, eight characters of markup, becomes a button element, a real object in memory with properties you can read and methods you can call, the thing JavaScript actually touches. Tag is text; element is object. When people say the DOM is an abstraction made of objects, this is what they mean: the browser has turned your flat text into a structured collection of objects you can manipulate at run time.

And the shape of that collection is a tree, in the strict sense from the last section. There is one root, the document. Every element sits inside exactly one parent element, the button inside the article, the article inside the body, the body inside the document, so each node has a single parent, and there are no loops. A tree, precisely. Each object in it is a node, most of them element nodes, some of them text nodes holding the words between tags. To change what the reader sees, JavaScript reaches into this tree and edits the objects: sets the text of an element, adds a child, changes a style, removes a node. Editing the UI is editing the DOM tree. There is no other way; everything any framework does, in the end, comes down to mutating objects in this tree.

For the Python reader, the nearest familiar thing is parsing an XML or HTML document into an element tree, where the document becomes a tree of node objects you walk and edit, parents and children, a root at the top. Same data structure, a tree of element objects, same operations, find a node and change it.

Here is the fact that drives every design decision in the next section: reaching into the real DOM and mutating it is comparatively slow, and working out by hand the smallest correct set of edits, given that some data changed, is error-prone. So a framework has a problem. When your data changes, which exact nodes in this tree must change, and how do you find them without redoing the whole page? Three frameworks, three answers, and now we have every word we need to state them exactly: a graph and a tree, interception and the observer pattern, signals and proxies, the compiler from the state chapter. Let me put them side by side.

## 9. Three Answers: React, Vue, And Svelte (groundwork; the synthesis; underlies state booklet Q15, the framework bridge)

The shared problem, stated once: keep the DOM tree, the page, in step with the application's data, automatically, and do it without rebuilding the whole page on every little change. React, Vue, and Svelte each answer with a different architecture. I will give each one in exact terms, name its data structures and its algorithm, and then lay the three on a common axis, so the comparison is precise and not a vibe. These three are often half-remembered, so the details are stated fully here, since half-memory tends to mislead.

Begin with React, because it leans hardest on the tree from the last section. React is a library that runs in the browser, at run time, no compiler in the picture. You hold state with a hook called use-state, which hands you the current value and a setter function, under the rule you met in the state booklet, never change the value in place, always call the setter. When you call the setter, React does something wholesale: it reruns your component, the whole component function, from top to bottom. Every hook in it runs again; this is why a React hook is said to run on every render, the exact contrast the state booklet drew in entry fifteen. Running the component produces not real DOM, but a new virtual DOM. Let me define that, since it is React's central object. A virtual DOM is a lightweight tree of plain JavaScript objects describing what the page should look like, a stand-in for the real DOM that is cheap to build and throw away. So each render makes a fresh virtual tree. React then compares this new virtual tree against the previous virtual tree, node by node, to find what actually differs, and this comparison has a name, reconciliation, or plainly, diffing. The diff yields the minimal list of real-DOM edits, and only those edits are applied to the actual tree the browser shows. React's modern engine for doing this incrementally is called Fiber, a name you will meet. So React's structures are two trees, the old and new virtual DOM, and its core algorithm is diffing them. Its granularity is coarse: a change reruns whole components and diffs their output, and if that is too much work you prune it by hand with memo helpers that tell React to skip rerunning a piece when its inputs have not changed. React does not, by default, track which individual value each piece of the screen read; it reruns and compares. Pull, rerun, diff, patch.

Now Vue, which sits in the middle and is the most instructive contrast, so I will give it the most detail. Vue runs at run time too, but its reactivity is built on the very machinery this lesson has been assembling: interception and the observer pattern. In current Vue, version three, you make an object reactive by wrapping it in a proxy, through a function called reactive, and you make a single value reactive by boxing it through a function called ref, which you then read and write through a property named value, dot value on every access. That dot value is not a tax for its own sake; it exists because a bare primitive, a lone number, cannot be wrapped in a proxy, there are no properties to intercept, so Vue puts the number inside an object with a value slot and intercepts that, which is exactly why the state booklet called dot value the price Vue charges and Svelte does not. With the proxy in place, Vue runs the observer pattern precisely as we built it: while a component renders, every reactive property it reads, through the proxy's get trap, subscribes that component's render to that property, dependency tracking, track on read. When a property later changes, through the set trap, Vue triggers only the renders that read it. So Vue is fine-grained about which components rerun, only the ones that actually depended on the changed value, which is a real difference from React's rerun-the-subtree default. But, and this is the part people forget, once Vue decides a component should rerun, that component still produces a virtual DOM, and Vue still diffs it against the previous one to patch the real tree, with compiler-assisted hints to make the diff cheaper. So Vue is a hybrid: the observer pattern, over proxies, decides which components update, and virtual-DOM diffing decides which DOM nodes within them change. One exact historical detail: Vue two, the previous major version, did not use proxies; it used the getter-and-setter approach from section three, the define-property method, attached to each known property. That is why Vue two could not detect a brand-new property added to an object, or certain changes to arrays, and needed special helper calls to work around it. Vue three moved to the proxy precisely to intercept everything, the new properties and the array operations included, the same total-interception advantage section four described. Vue two was per-property getters; Vue three is a whole-object proxy; the move was from the first rung of the ladder to the second.

Now Svelte five, which the state chapter already half-told, and which we can now place exactly against the other two. Svelte is a compiler, working at build time on your machine, not a library running in the browser; that whole first machine from the state chapter. Its reactivity is signals, the observer-pattern nodes from this lesson, plus proxies to give objects per-property signals deeply, the bundle from section six. And here is the move that sets it apart: because the compiler reads your component ahead of time, it knows, at build time, exactly which spots in the page depend on which signals. So it does not need a virtual DOM and it does not diff. It generates code that wires each signal straight to the specific DOM nodes that depend on it, and when a signal changes, that node updates directly, the leaf effect of the dependency graph touching one node of the DOM tree. No second tree, no comparison, only a pre-wired path from a value to the one piece of page it controls. That is the most fine-grained of the three: not which component, but which node. The state rune is a plain variable the compiler attaches to a signal; a deep object is a proxy over per-property signals; the dependency graph drives surgical edits to the DOM tree.

Now the three on one axis, so the comparison is structural and exact. First axis, where the reactivity is decided. React decides by rerunning your code in the browser and comparing the results. Vue decides by intercepting reads and writes in the browser, through a proxy, and tracking dependencies. Svelte decides ahead of time, in the compiler, before the browser runs anything. Run-time rerun, run-time interception, build-time wiring. Second axis, what structure mediates the change to the page. React and Vue both build a virtual DOM, a throwaway tree, and diff it to find the real edits. Svelte builds no virtual DOM; it wires signals to real nodes directly. Two trees and a diff, versus a direct wire. Third axis, how fine the granularity is. React is coarse, rerun a component and its children, diff their whole output, optimize by hand. Vue is medium, the observer pattern narrows it to the components that read the changed value, then diffs within them. Svelte is fine, the compiler narrows it to the exact nodes, no diff at all. And the three dialects from the state booklet now sit on solid ground: React's setter is the surface of rerun-and-diff, Vue's dot value is the box that lets a primitive be intercepted by a proxy, and Svelte's plain variable is what is left when a compiler does the wiring ahead of time instead of a library doing it as you go.

That is the full comparison, in the real terms: two trees and a diff against one observer-tracked proxy against a compiled signal graph with no diff at all. Three answers to one tree-keeping problem, separated by where they intercept and what structure they build.

## Closing: Interception, The Graph, And The Tree, Named Once More

Everything in this lesson hangs on one idea, and you named it yourself before we began. Reactivity is built on interception: making an ordinary-looking read or write secretly run code. That single hook is what lets a framework keep an observer-pattern ledger of who depends on what, and that ledger is a dependency graph, a directed acyclic graph of sources, deriveds, and effects, whose leaves reach out and edit the DOM, the tree of live objects the browser made from your tags. JavaScript hands you a ladder of interception, a getter for one property, a proxy for an entire object, and a signal is the userland reactivity node those tools wire into the graph. The three frameworks are three places to stand on that ladder: React reruns and diffs two virtual trees, Vue intercepts through a proxy and tracks dependencies before diffing, and Svelte wires signals to real nodes in a compiler and never diffs at all.

Let me gather the words you now own, each at its tightest, because these are the standard terms of these fields, and you will meet them in documentation, in talks, in source code, for the rest of your working life.

A first-class function is a function treated as a value, stored, passed, and returned like any other. A closure is a function that remembers and keeps alive the variables that surrounded it when it was created, which is how JavaScript hides private data. A prototype is the object your object falls back to for properties it lacks. A getter is a property that is secretly a function, so that reading it runs code, with a setter as its twin for writing, and that is the first rung of interception. A proxy is an object that stands in front of another and intercepts the basic operations on it through functions called traps, the second rung, total interception, the heart of metaprogramming, which is code that intercepts what other code does. Interception is good because it lets a framework do its bookkeeping invisibly, in the gap between an access and its value. The observer pattern is a value that keeps a list of its dependents, adds to that list on every intercepted read, and walks it to notify on every intercepted write, track on read and trigger on write. A signal is that pattern packaged for one value, a single reactivity node, a userland invention and not the language's proxy, though it shares the intercepted get and set that make it resemble one. A dependency graph is the whole network of sources, deriveds, and effects wired by your reads, a directed acyclic graph, which is more general than a tree because a node may have many parents. The DOM is the browser's tree of live element objects, one per tag, where a tag is the source text and an element is the live object, and editing the page means editing that tree. A virtual DOM is a throwaway copy of that tree that React and Vue build and diff, reconciliation, to find the minimal real edits, while Svelte's compiler skips it. And fine-grained reactivity updates the exact node that changed, where coarse-grained reactivity reruns a whole component and works out the change afterward.

This lesson built the floor under the state chapter, so it pointed back rather than forward: the closure under entry twelve, the proxy under entries two and six and seven, the getter under the signal, the whole comparison under entry fifteen. And it leaves two nodes of the dependency graph named but not yet built, the derived, the computed middle of the graph, and the effect, its world-touching leaf. Those two are the subject of the next lesson, lecture five, which builds the derived rune in full. We have built the graph; next we put real computations into its middle.
