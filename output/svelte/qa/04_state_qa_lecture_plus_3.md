# 04 | What The Box Holds: Reactivity Down To The Machine

## 4.1 Where This Hour Sits (no booklet section; orientation)

This is the fourth lecture, teaching the state chapter through the fifteen questions in your booklet. It rests on two earlier hours: the first, where Svelte turned out to be a compiler that rewrites your code ahead of time, and the third, where we built this course's running world, the news organisation The National Times, with its articles, its readers, and the count of claps under each story.

You may have the booklet open. I will not read code aloud, because code is for the eye, and the eye's work is on that page; each time we enter one of the fifteen questions I will say which one, so you can find it. By the end you should be able to look at any piece of state and predict, before running anything, whether a change to it reaches the screen, and why. The answer is a few machine-level facts, so we start one layer below the framework.

## 4.2 The Reactive Variable, And The Compiler That Wires It (booklet: "Making a value react to change", question one)

A reader taps the button under a story, and the clap count beside it should climb. You keep that count in a variable, and on the tap you add one to it, and the number on the screen does not move.

The reason it does not move is the gap this whole chapter is about. The variable is a value in the computer's memory. The count on the screen is text inside an element on the page. These are two separate things, and writing a new number into the variable does nothing to the text on the page. To keep them in agreement by hand, you would find the element each time and rewrite its text, which is the work a framework exists to take off you.

So you write the variable with a marker in front of its value, and that marker is an instruction to Svelte's compiler to wire the variable to the screen for you when it rewrites your code. The marker has a name you will type constantly, so here it is, spelled out: the state rune, which is the dollar sign followed by the word state. To fix the definition I will reuse all hour: the state rune, the dollar sign followed by the word state, is the marker that tells the compiler to make a variable reactive. And there is the second word, reactive, built before I lean on it. A variable is reactive when Svelte is watching it so that the screen moves when the variable moves. Once more, plainly: reactive means Svelte watches the variable, so the screen moves when the variable moves. Wrap the clap count in the state rune, and it is reactive; you add one to it the ordinary way, and every place on the screen showing it updates on its own. The booklet has it under question one.

Two names to carry forward, then. The state rune, the dollar sign followed by the word state, the marker that makes a variable reactive. And reactive, Svelte watching so the screen follows. These are small. The depth starts the moment the thing you wrap is not a lone number but an object, because most state is an article, or a list of them, or a draft with a checklist, and to see what reactivity does there, we have to look at how a variable holds an object at all.

## 4.3 The Proxy, And The Tag That Reaches It (booklet: "When state is an object or a list", question two)

Put a draft's checklist into the state rune, a list of tasks, each task a small object with a label and a done flag. Reach past the list, into one task, and flip its done flag, three layers deep. Does the screen move?

A reasonable first guess is that it cannot. Whatever watches your state watches the variable, from outside, and you did not touch the variable; the list is the same list. You changed something buried deep inside it, and a watcher outside a box should not see a page turn inside the box. That guess is wrong, and untangling why means seeing how the variable holds the list in the first place.

Here is the machine, and it is worth picturing literally, because we will compute with it for the rest of the hour. Think of a variable as a labeled box. A small, simple value, a number, a string, a true-or-false, fits inside the box and sits there directly. But an object, like one of those tasks, is too big for the box. So the object lives out in the computer's memory, at some location, and the box holds only a number that points to that location, the way a coat-check ticket points to a coat. That number in the box has a name worth keeping: it is a reference. A reference is a numbered tag, sitting in the variable's box, that points to where the object actually lives. Your variable does not contain the task; it contains a reference, a tag, say tag forty-one, and the task itself is out at location forty-one in memory.

Now reactivity. When you wrap an object in the state rune, Svelte does not watch your box from outside. It goes to where the object lives, at the location the tag points to, and it puts a wrapper around the object there, a wrapper that gets to run a little code on every read of a field and every write of a field. Reading a field goes through the wrapper; writing a field goes through the wrapper. That wrapper is the central name of this lecture, and you will meet it in documentation and in stack traces, so here it is in full: it is called a proxy. The canonical sentence, which returns many times: a proxy is a wrapper that stands in front of an object and intercepts every read and write of its fields. Reading goes through the proxy; writing goes through the proxy; that is how the proxy knows the screen must change. And notice where the proxy sits: at the object, at the location the tag points to. You reach the proxy only by following the tag. Hold that, because it is the hinge of the whole chapter.

The proxy goes all the way down. If a task holds another object, that inner object gets its own proxy where it lives; a proxy at every object, as deep as the data goes. So flipping the done flag deep in the list moves the screen because that task is itself an object with its own proxy, and its own proxy saw the write. The booklet calls this deep reactivity, under question two. You get the same when you grow the list: push a new task on the end, the plain way you push onto any array, and the array's proxy sees the push, the screen updates, and the new task arrives with its own proxy. Anyone from React will notice this, because there, changing an array in place is a known way to get a frozen screen, and you are taught to replace the array; here the proxy watches the array itself, so the direct change is correct.

So this section leaves you with the proxy, a wrapper that intercepts every read and write of an object's fields, reaching all the way down, and sitting at the object, reachable only through the reference, the numbered tag in the box. That last fact, the proxy is reached through the tag, is the one the next section turns on. Because if you ever hold something other than that tag, you are no longer reaching the proxy at all.

## 4.4 What Every Assignment Copies (booklet: "When state is an object or a list", question three; "Passing state around", question ten)

You destructure an article to save typing, lifting its title into its own variable, and then later the article's title changes and the heading on the screen does not. The booklet treats this as question three, and treats a separate puzzle, passing state into a function, as question ten, far away. They are one law, and I am taking them together, because question three's destructuring, the shorthand that copies a field out of an object into its own box, and question ten's pass-by-value, the rule that a function receives a copy of what each argument's box holds, are the same fact about copies, worn as two outfits. To see it, we finish the machine picture from the last section, and we finish it whole, both of its halves, because half of this model is exactly what makes the bug mysterious.

Recall the box. A small value, a number, a string, a true-or-false, sits directly inside the variable's box; that kind of value has a name, a primitive value. A primitive value is a value that sits directly inside the variable's box. An object does not fit, so it lives out in memory and the box holds a reference, the numbered tag pointing to it. One box, two possible contents: a primitive sitting in it, or a tag pointing out of it.

Now the one law that governs everything that follows, and it is worth stating as a law because every case is an instance of it: every assignment, every destructuring, and every function call copies what is in the box, and never the object itself. Only what is in the box. For a primitive, what is in the box is the value, so you copy the value. For an object, what is in the box is the tag, so you copy the tag, and both tags then point at the one object still sitting out in memory.

Watch both halves of that law, as a pair, because the pair is the whole idea. First half, copying a tag. Take a variable holding an article, that is a box with a tag, and assign it to a second variable. By the law, you copied what is in the box, the tag. Now two boxes hold the same tag, both pointing at the one article in memory. Change a property through the first variable, and you see it through the second, because there is only one article and both tags reach it. That is sharing. Second half, copying a primitive. Take that same article and destructure its title, a string, into its own variable. The title is a primitive, so what is in its slot is the string value itself, and the law copies the value into a fresh box. That new box holds a lone string, with no tag pointing back to the article. It is independent, connected to nothing. That is copying. Sharing when you copy a tag; an independent island when you copy a primitive. Same law, two outcomes, decided entirely by what was in the box.

And the function call is the same law a third and fourth time, which is question ten. Pass the article object into a function, and the function's parameter is a box that received a copy of the tag; so the function reaches the one shared article, and if it changes a property, you see it, because it changed the single object both tags point at. That is sharing across a function boundary. But pass the clap count, a primitive, and the parameter got a copy of the number; whatever the function does to its own copy stays in its own box. The rule that a function receives a copy of what each argument's box holds is what pass-by-value names. Pass-by-value is the rule that a function receives a copy of what each argument's box holds. It is the same law as assignment and as destructuring, applied at the call.

Only now does the reactivity land, as a consequence rather than a rule, and here the proxy returns, the wrapper that intercepts every read and write, sitting at the object and reachable only through the tag. Put the two facts together. Reactivity is the proxy, and the proxy is reached only through the tag. So copy the tag, by assignment, by passing the object to a function, and you still hold a tag to the one proxied object, and reads and writes still go through the proxy, and the screen still follows. But copy a primitive out, by destructuring a string field into its own box, and you are holding a lone value with no tag, no path to the proxy, nothing the proxy will ever touch again. That is why the destructured title goes stale: it was a primitive, copied out of the box, sitting outside the proxy. Nothing broke. The law did exactly what the law does.

This model predicts cases the booklet never poses, which is the sign it was taught whole. Destructure a field that is itself an object rather than a string, the article's author, and you copied a tag, so you are still holding that author object through its proxy, and reading the author's fields stays reactive. Store the result of a function that handed you back a number, and it is frozen, a copied primitive. There is one softening detail worth having, so this sounds no scarier than it is: when you call a function right in the markup that paints the screen, Svelte runs that markup again on every change and calls the function again with the current value, so the result on screen stays current; the frozen copy only bites when you park the returned value in a variable off to the side. And for the rare case where a function in another file must read your latest value over time, you hand it not the value but a tiny function that fetches the value when called. The booklet shows the frozen line and the live line under question ten.

So the names from the deepest section. Primitive value, a value that sits directly in the box. Reference, the numbered tag in the box pointing to where an object lives. The copy law, that every assignment, destructuring, and function call copies what is in the box, the value for a primitive, the tag for an object. Destructuring, the shorthand that copies a field out into its own box. Pass-by-value, the rule that a function receives a copy of what each box holds. And over all of them, the proxy reached only through the tag. Keep the tag, keep the proxy; copy a bare value out, and reactivity was left behind in the box you copied from. The next question is what happens when the thing you put in state is not a plain object at all, so the proxy cannot appear around it by itself.

## 4.5 What The Proxy Cannot Wrap, And How A Method Loses Itself (booklet: "Modeling data as a class", questions four and five; "Reactive built-ins and the variants", question six)

You build a draft as a class, give it a reset method, wire a button straight to that reset, tap it, and the draft does not reset. And separately, you put a draft instance into the state rune expecting the proxy to appear around it, and your fields are not reactive. Two surprises, both about things the proxy, the wrapper that intercepts every read and write, does not wrap on its own. Three of the booklet's questions live here, and I am gathering them, though the booklet files one elsewhere.

First the class itself, and two names that ride in with it. A class is a blueprint; the object you stamp out of it is an instance, made with the keyword new. An instance is the object you stamp out from a class with the keyword new. A class also has a setup function that runs once the moment an instance is born, called the constructor. The constructor is the setup function that runs once, the moment an instance is born. Now, why does wrapping a draft instance in the state rune not give it a proxy, the way a plain object gets one? Because an instance is not a plain bag of fields. It carries methods, it may carry private fields, it has machinery of its own, and a proxy intercepts every read and write, which could disturb that machinery in ways Svelte will not risk by default. So Svelte leaves the instance unwrapped and asks you to switch reactivity on field by field, marking each field you want reactive with the state rune, on the field or on its first assignment in the constructor, that setup function that runs when the instance is born. The fields you mark get the proxy's behavior; the others stay ordinary. The booklet has the draft class under question four.

The reset that did nothing is question five, and it is not about reactivity at all; it is a mechanism in the language itself, the rule for how the little word meaning "the object this method belongs to" gets its value. That word does not get its value from where the method was written. It gets it from how the method is called, at the moment of the call, from whatever is to the left of the dot when you invoke it. Teach it whole, as a pair. Call the method on the draft, with the draft to the left of the dot, and inside the method that word is the draft, and reset clears the draft. Hand the bare method to the button and let the button call it later, and now there is nothing to the left of any dot that you put there; the browser calls it as the button's own handler, so inside the method that word is the button, and reset clears fields on the button, and the draft is untouched. Same method, two call sites, two different objects bound, because binding follows the call, not the text. The fixes both restore a call on the draft: wrap the call so the draft is to the left of the dot again, or define the method in the form that fixes that word to the instance for good. The booklet shows both under question five. When this bites, it is the language biting, not Svelte.

The third case is a family of built-in types, and it is the class's lesson again. A set, which holds unique values with no duplicates and is exactly right for the identifiers of the posts a reader has liked; a map, for lookups by key; a date; a web address. These are not plain objects. Each keeps its contents in private internal machinery rather than in ordinary fields, and a proxy intercepts reads and writes of ordinary fields, so it has nothing to intercept on these, and wrapping one does nothing. Put a plain set of liked identifiers in the state rune, add one, and the heart on the screen stays dark, because the add went into internal machinery the proxy cannot see. Svelte ships reactive versions of these four, with the same methods you know but built to report their changes from the inside; you import the reactive set, written as the two words Svelte and Set joined into one, from a package named svelte, slash, reactivity, and use it as the plain one. The booklet files this with the variants, under question six, but I have moved it here because it is one lesson with the class: the proxy is automatic only for plain objects and arrays. A class instance you make reactive field by field. A set, map, date, or web address you replace with the reactive version.

So this section's consolidation. An instance, the object stamped from a class with new, gets no proxy by default, so you mark its fields with the state rune in the constructor. The little binding word inside a method is fixed by the call, not the text, which is why a bare method handed off loses the instance. And the built-in set, map, date, and web address keep their contents where a proxy cannot reach, so you import reactive versions. Next, the three deliberate adjustments you can make to the proxy when the default is not what you want.

## 4.6 Three Adjustments To The Proxy (booklet: "Reactive built-ins and the variants", questions seven, eight, nine)

You load a feed of thousands of posts that you only ever replace or append to, and giving every post and every field its own proxy is real work you will never use. The proxy, the wrapper intercepting every read and write reaching all the way down, is a fine default and it is not free, and the state rune gives you three deliberate adjustments to it, one per question here.

The first turns the depth off. There is a raw form, the state rune followed by the word raw, that holds the value with no proxy installed inside it at all. Its condition is the other side of that coin and follows from it directly: with no proxy watching the parts, changing a part is seen by nothing, so the only change the raw form notices is replacing the whole value with a new one. That suits the feed, because the natural way to grow a feed is to build a new list from the old one plus the next page and assign it, which is a replacement, not an inner edit. The honest caution the Svelte team presses is not to reach for the raw form out of a vague fear of slowness; the ordinary proxy is fast enough for almost everything, so measure first and use the raw form for genuine masses of data you only ever swap. The booklet has it under question seven.

The second strips the proxy off on the way out. What you hold is the proxy, not the bare object, and that is right inside Svelte, but hand your data to something outside Svelte, a charting library, or the browser's own function for deep-copying a value, and those outsiders were not built to understand a proxy and refuse it. The snapshot form, the state rune followed by the word snapshot, hands you back a plain ordinary copy of the data with the proxy stripped off, safe for any outsider. The booklet has it under question eight.

The third changes when the proxy reports. Svelte ordinarily gathers changes and applies them together for smoothness, and a change waiting on something slow can lag a beat, which is almost always fine; but for an instant flash of feedback to a tap, the section link the reader pressed a moment ago lighting at once before the next page loads, there is an eager form, the state rune followed by the word eager, which shows the change the instant it happens. It is for direct feedback and nothing else. The booklet has it under question nine.

So three adjustments to the one proxy: the raw form with no proxy inside, updated by full replacement; the snapshot form with the proxy stripped off, for the outside world; the eager form reporting at once, for instant feedback. One last fact about the proxy remains, which is where it gets built, and that is a fact about the compiler.

## 4.7 The Compiler Works One File At A Time (booklet: "Sharing state across files", questions eleven and twelve)

The logged-in reader is needed everywhere at once, the greeting at the top, the comment box deep in an article, a dozen scattered corners, and threading it down through every component between them is misery. So you lift it out of any component into a file that other files import from, which is called a module. A module is an ordinary file that other files import from. You keep the reader in a module, for everyone to import.

The catch reaches back to the first idea of the course, that Svelte is a compiler, and to one detail of how it works: it processes one file at a time. The state rune is not an ordinary function that runs in the browser; it is an instruction the compiler acts on while rewriting your file, turning your reads and writes into the proxy machinery. For that to happen in a module, the file must be marked so the compiler rewrites it, which you do by ending its name in dot svelte dot t s rather than plain dot t s. A module whose name ends in dot svelte dot t s is one the compiler processes for runes. Now the consequence, and it follows from one-file-at-a-time. If you export a piece of state from that module and then reassign the exported name inside it, another file that imports the name was compiled separately, on its own, and never learned that the name is backed by reactive machinery needing special handling; so it receives the raw machinery instead of your value, and the connection breaks at the border between the two files.

The cure falls out of naming the cause: the break is reassigning an exported name across a file boundary, so never do that. The first way, question eleven, is to export an object and change a property on it rather than reassigning the variable; you never reassign the export, you set a field on the shared object, and because that object carries its proxy, every importer that follows the tag to it sees the change. The second way, question twelve, is to not export the state at all, keeping it private in the module and exporting functions instead, one to read it, others to change it, so every read and write stays inside the one file the compiler controls, with a single doorway for changes where you could validate or record or persist them. The booklet has both under questions eleven and twelve.

So the names here are module, an ordinary file other files import from, and the dot svelte dot t s file, the module the compiler processes for runes. And the lesson beneath them is that the proxy has a boundary, the file, because the compiler lays its wiring one file at a time. The last section steps back from state entirely to set it beside its two siblings.

## 4.8 Three Tools, And Two Loose Ends (booklet: "Going further", questions thirteen, fourteen, fifteen)

A story carries a small label saying it is a five minute read, and you are tempted to keep that label in a state rune and update it whenever the body changes. That temptation is question fourteen, and resisting it is the right note to end the teaching on, because it places the state rune among its neighbours.

The label is not a value you hold and change; it is a value computed from another value, the length of the body. Forcing a computed value into a state rune means recomputing it by hand on every change, which is the surest way to get a label that quietly disagrees with the body. It wants a different rune, the derived rune, the whole subject of the next lecture, which recomputes itself whenever its inputs change. I name it and leave it, a deferral, not a half-explanation. And there is a third kind of thing again, neither a value you hold nor a value you compute, but an action reaching out of your data into the world, saving to a server, drawing to a canvas, which is the effect rune, with its own hour later. So of any piece of behavior, ask which of three it is. Holding a value is the state rune. Computing a value is the derived rune. Acting on the world is the effect rune. This lecture was the first of the three.

Two quick loose ends. Question thirteen asks whether the article card and the clap button can live in one file; they cannot, one file is one component, and to show two components and how they talk you write two files. Question fifteen translates for arrivals from React or Vue: the state rune is near enough Vue's reactive value with its ceremony removed, and React's state hook without the separate setter and without the rule never to change the value directly, with the deepest difference showing only later in how reusable pieces behave. So the close here is the fork among three runes: the state rune for a value held, the derived rune for a value computed, the effect rune for an action on the world.

## 4.9 From The Machine Up (synthesis)

Every one of the fifteen questions was a consequence of a few facts about the machine, so let me run those facts one last time, in their tightest form, and let the framework fall out of them.

A variable is a box. A primitive value, a number or a string or a boolean, sits directly in the box. An object is too big, so it lives in memory and the box holds a reference, a numbered tag pointing to it. One law governs everything: every assignment, every destructuring, and every function call copies what is in the box, the value for a primitive, the tag for an object, never the object itself. On top of that, the framework. The state rune, the dollar sign followed by the word state, is the marker that tells the compiler to make a variable reactive, where reactive means Svelte watches it so the screen moves when it moves. For an object, the compiler installs a proxy, a wrapper that stands in front of the object and intercepts every read and write of its fields, sitting at the object and reached only through the tag.

From those, all fifteen. Reactivity reaches all the way down because there is a proxy at every object. It survives sharing, because copying a tag, by assignment or by passing an object to a function, still reaches the proxy. It dies on a copy, because destructuring, the shorthand that copies a field into its own box, and pass-by-value, the rule that a function receives a copy of what each box holds, both copy a bare value out, leaving the proxy behind; question three and question ten were that one law in two outfits. The proxy is not installed on a class instance, the object stamped out with new, so you mark its fields in the constructor, the setup function that runs when the instance is born; and a method handed off bare loses its instance, because the binding word follows the call, not the text. The proxy cannot reach the internal machinery of a set, map, date, or web address, so you import reactive versions. You adjust the proxy three ways: raw, with none installed, updated by replacement; snapshot, stripped off, for outsiders; eager, reporting at once. And the proxy ends at a file's edge, because the compiler wires one file at a time, so shared state lives in a module ending in dot svelte dot t s and is exported as a mutated object or behind functions, never as a reassigned name.

That is the booklet's fifteen, in full. Question three and question ten I merged as the copy law in two outfits. Questions four and five I took together, a class and the language's binding rule beside it. Question six I moved from the variants to sit with the class. The derived rune and the effect rune I named and deferred, the derived rune to the very next lecture, which is exactly where this leads: derived values rest on the same proxy and the same copy law you now hold from the machine up.
