# 04 | Where Reactivity Lives: The Proxy, The Reference, And The Copy

## 4.1 What This Hour Stands On (no booklet section; orientation)

This is the fourth lecture, and it teaches the state chapter through the fifteen questions in your booklet. It rests on two earlier hours: the one where Svelte turned out to be a compiler that rewrites your code before it ever runs, and the one where we built the running world for this course, a news organisation called The National Times, with its articles, its readers, and the count of claps beneath each story.

You may have the booklet open beside you. I will not read code aloud, because code is made for the eye, and the eye's work is on that page; each time we step into one of the fifteen questions I will name it, so you can find it. By the end you should be able to look at any piece of state and say, before you run a thing, whether a change to it reaches the screen, and why. The answer turns out to be a handful of facts about the language underneath the framework, so that is where we begin.

## 4.2 The Reactive Variable, And The Compiler That Wires It (booklet: "Making a value react to change", question one)

A reader taps the button under a story, and the clap count beside it ought to climb. You hold that count in a variable, and on the tap you add one to it, and the number on the screen does not move.

It does not move because two separate things are involved, and you only changed one of them. The variable is a value held in the computer's memory. The count on the screen is text inside an element on the page. Writing a new number into the variable does nothing to that text; nothing connects them. To keep them in step by hand, you would find the element after every tap and rewrite its text yourself, which is precisely the labour a framework exists to take off you.

So you put a marker in front of the value when you declare the variable, and that marker is an instruction to Svelte's compiler: wire this variable to the screen for me when you rewrite the code. The marker has a name you will type all day, so here it is, spelled out in words: the state rune, the dollar sign followed by the word state. Let me fix the definition I will lean on all hour. The state rune, the dollar sign followed by the word state, is the marker that tells the compiler to make a variable reactive. And there is the second word I just used, reactive, which I will not leave undefined. A variable is reactive when Svelte is watching it, so that the screen changes when the variable changes. Once more, in plain words: reactive means Svelte watches the variable, and the screen follows it. Wrap the clap count in the state rune, and it is reactive; you add one to it in the ordinary way, with no setter and no special method, and every place on screen that shows it redraws on its own. The booklet has this as question one.

Two names to carry forward, then. The state rune, the dollar sign followed by the word state, the marker that makes a variable reactive. And reactive, which means Svelte watches the variable and the screen follows. These are easy while the thing you wrap is a lone number. The depth arrives the moment it is not, because most real state is an article, or a list of articles, or a draft with a checklist, and to see what reactivity does to those, we first have to see how a variable holds an object at all.

## 4.3 What A Variable Holds, And The Proxy It Reaches (booklet: "When state is an object or a list", question two)

Put a draft's checklist into the state rune: a list of tasks, each task a small object with a label and a done flag. Now reach past the list, into one task, and flip its done flag, three layers down from the variable you declared. Does the screen move?

A reasonable first answer is that it cannot. Whatever is watching your state is watching the variable, from the outside, and you never touched the variable; the list it holds is the same list. You changed something buried deep inside, and a watcher standing outside should not see a change made inside. That answer is wrong, and seeing why means seeing what the variable actually holds.

Here is the fact from the language, and it is the hinge of the whole chapter. A simple value, a number, a string, a true-or-false, is small, and the variable stores it directly. That kind of value has a standard name: a primitive value. A primitive value is a simple value, a number or a string or a true-or-false, that the variable stores directly. An object is different. The object lives somewhere in the computer's memory, and the variable does not hold the object itself; it holds a pointer to where the object lives. That pointer has a standard name too: a reference. A reference is what a variable holds when its value is an object, a pointer to where that object actually lives in memory. Picture it for a moment like a coat-check ticket, which is not the coat but tells you exactly where the coat is. I will retire that picture now and use the real word. Your variable holding the checklist does not contain the list; it contains a reference to it.

Now the reactivity. When you wrap an object in the state rune, Svelte does not watch your variable from outside. It follows the reference to where the object lives, and it installs a wrapper around the object there, a wrapper that gets to run a little of its own code on every read of a field and every write of a field. Read a field, and the read passes through the wrapper; write a field, and the write passes through the wrapper. That wrapper is the central object of this entire lecture, and it is a real thing in the language with a real name you will meet in documentation and in error messages, so here it is: it is a Proxy. The canonical sentence, which returns many times today: a Proxy is a wrapper that stands in front of an object and intercepts every read and every write of its fields. The reads go through the Proxy; the writes go through the Proxy; that is how the Proxy knows the screen must be updated. And mark where the Proxy sits. It sits at the object, where the object lives, at the far end of the reference. You reach the Proxy only by following the reference. Hold that, because the next section turns on it entirely.

The Proxy goes all the way down. If a task holds another object inside it, that inner object gets its own Proxy where it lives, and so on, a Proxy standing at every object as deep as the data runs. So flipping the done flag deep in the checklist moves the screen, because that task is itself an object with its own Proxy, and that Proxy saw the write. The booklet calls this deep reactivity, and files it under question two. You get the same when you grow the list rather than edit it: push a new task onto the end, the plain way you push onto any array, and the array's own Proxy intercepts the push, the screen updates, and the new task arrives wrapped in a Proxy of its own. Anyone arriving from React will feel the contrast here, because in React, changing an array in place is a classic way to freeze the screen, and you are trained to build a new array instead; here the Proxy is watching the array itself, so the direct, obvious change is the correct one.

So this section leaves you holding three names. The primitive value, stored directly in the variable. The reference, the pointer a variable holds when its value is an object. And the Proxy, the wrapper that intercepts every read and write of an object's fields, reaching all the way down, sitting at the object, reachable only by following the reference. That last clause, the Proxy reached only through the reference, is the fact the next question lives or dies on. Because the instant you are holding something other than that reference, you are no longer reaching the Proxy at all.

## 4.4 What Every Copy Carries, And What It Leaves Behind (booklet: "When state is an object or a list", question three; "Passing state around", question ten)

You destructure an article to save some typing, lifting its title out into a variable of its own, and later the article's title changes and the heading on the screen stays stuck on the old words. The booklet poses this as question three. Far away, under a different banner, it poses what looks like a separate puzzle: you pass a piece of state into a function, and the function seems to get a dead copy rather than the live value. That is question ten. I am teaching them together, in one section and the longest one, because they are a single law of the language wearing two costumes, and this law is the hardest thing in the chapter to reconstruct on your own. Destructuring, which is the shorthand that lifts a field out of an object into its own variable, and pass-by-value, which is how a function receives its arguments, are the same fact about copying. To see it, we finish the picture from the last section, and we finish both halves of it, because owning only one half is exactly what makes the bug feel like sorcery.

Recall what a variable can hold. A primitive value sits in the variable directly. A reference sits in the variable when the value is an object, pointing out to where the object lives. One variable, two possibilities: a primitive in it, or a reference out of it.

Now the law that governs everything that follows, and it earns the word law because every case today is an instance of it. Every assignment, every destructuring, and every function call copies what the variable holds, and never the object itself. Only what the variable holds. If the variable holds a primitive value, you copy that value. If the variable holds a reference, you copy that reference, and now two variables hold the same reference, both pointing at the one object still sitting where it always was in memory.

Watch the two halves of that law side by side, because the pair is the whole idea. First, copying a reference. Take a variable holding an article, which is a variable holding a reference, and assign it to a second variable. By the law, you copied what the first variable held, the reference. Two variables now hold the same reference, both pointing at the one article. Change a property through the first variable, and you can read that very change through the second, because there is one article and both references reach it. That is sharing. Second, copying a primitive value. Take that same article and destructure its title, which is a string, into a variable of its own. The title is a primitive value, so what gets copied is the string itself, dropped into a fresh, independent variable. That new variable holds a lone string with no reference pointing back to the article. It is connected to nothing. That is an island. Sharing when you copy a reference; an island when you copy a primitive value. One law, two outcomes, decided entirely by what the variable held.

And the function call is the same law, a third time and a fourth, which is question ten. Pass the article object into a function, and the function's parameter is a variable that received a copy of the reference; so the function reaches the one shared article, and if it changes a property, you see it, because there is a single object that both references point at. That is sharing across the boundary of a function. But pass the clap count, a primitive value, and the parameter received a copy of the number itself; whatever the function does to its copy stays with its copy. This rule, that a function receives a copy of what its argument's variable holds, has a standard name: pass-by-value. Pass-by-value means a function receives a copy of what its argument's variable holds, never the variable itself. It is the very same law as assignment and as destructuring, applied at the moment of the call.

Only now does the reactivity fall out, as a consequence rather than a rule, and here the Proxy comes back, the wrapper that intercepts every read and write, sitting at the object and reachable only by following the reference. Lay the two facts together. Reactivity is the Proxy, and the Proxy is reached only through the reference. So copy a reference, by assignment or by passing the object to a function, and you still hold a reference to the one Proxied object, your reads and writes still pass through the Proxy, and the screen still follows. But copy a primitive value out, by destructuring a string field into its own variable, and you hold a lone value with no reference, no path to the Proxy, nothing the Proxy will ever touch again. That is the whole reason the destructured title goes stale: it was a primitive value, copied out, sitting beyond the reach of the Proxy. Nothing broke. The law did exactly what the law always does.

Now the test of whether this was taught whole, which is whether it answers questions the booklet never asks. Take three. First, what if you destructure a field that is itself an object, say the article's author, rather than a string? Then you copied a reference, not a primitive value, so you still hold the author object through its Proxy, and reading the author's fields stays reactive. Second, what if you store the result of a function that handed you back a number? That is a copied primitive value, frozen at the moment of the call, and it will not update. Third, then why does the same call work when it sits right in the markup that paints the screen? Because Svelte re-runs that markup on every change, calling the function again with the current value, so what appears on screen stays fresh; the frozen copy only bites when you park the returned value in a variable off to one side. And for the genuine case where a function in another file must read your latest value over time, you hand it not the value but a small function that fetches the value when called, so each call reads the current one. The booklet shows the frozen line beside the fresh line under question ten.

So the names from the deepest section, gathered. The primitive value, stored directly in the variable. The reference, the pointer the variable holds when the value is an object. The copy law, that every assignment, destructuring, and function call copies what the variable holds, the value for a primitive, the reference for an object. Destructuring, the shorthand that copies a field out into its own variable. Pass-by-value, the rule that a function receives a copy of what the variable holds. And presiding over all of them, the Proxy, reached only through the reference. Keep the reference, keep the Proxy; copy a bare value out, and the reactivity stayed behind in the variable you copied from. The next question is what happens when the thing you put in state is not a plain object at all, so the Proxy cannot appear around it on its own.

## 4.5 What The Proxy Does Not Wrap On Its Own (booklet: "Modeling data as a class", questions four and five; "Reactive built-ins and the variants", question six)

You model a draft as a class, give it a reset method, wire a button straight to that reset, tap it, and the draft does not reset. Separately, you put a draft instance into the state rune expecting the Proxy to appear around it, and the fields turn out not to be reactive. Two surprises, and both are about things the Proxy, the wrapper that intercepts every read and write, does not wrap by itself. Three of the booklet's questions belong to this one idea, and I am taking them together, though the booklet files one of them elsewhere.

First the class, with two standard names that arrive alongside it. A class is a blueprint for objects; the object you stamp out of the blueprint is an instance, and you make one with the keyword new. An instance is the object you stamp out of a class with the keyword new. A class also carries a setup function that runs once, automatically, the moment an instance is created, and that function is called the constructor. The constructor is the setup function that runs once, the moment an instance is born. Now, why does wrapping a draft instance in the state rune not give it a Proxy, the way a plain object would get one? Because an instance is not a plain bag of fields. It carries methods, it may carry private fields, it has machinery of its own, and a Proxy intercepts every read and write, which could disturb that machinery in ways Svelte will not risk on your behalf. So Svelte leaves the instance unwrapped and asks you to turn reactivity on one field at a time, marking each field you want reactive with the state rune, either on the field itself or on its first assignment inside the constructor, that setup function that runs when the instance is born. The fields you mark behave reactively; the rest stay ordinary. The booklet has the draft class under question four.

The reset that did nothing is question five, and it is not about reactivity at all. It is a rule of the language itself, the rule that decides the value of the keyword this. Inside a method, the keyword this means the object the method was called on. Here is the standard, canonical statement, and the cruel part is in it: the keyword this is decided by how the method is called, not by where it was written. It is whatever stands to the left of the dot at the moment of the call. Teach it whole, as a pair of cases. Call the method on the draft, with the draft to the left of the dot, and inside the method the keyword this is the draft, and reset clears the draft. Hand the bare method to the button and let the button call it later, and now nothing of yours stands to the left of any dot; the browser calls that loose function as the button's own handler, so inside it the keyword this is the button, and reset clears fields on the button while the draft sits untouched. Same method, two call sites, two different objects bound, because the binding follows the call and not the text. Both fixes restore a real call on the draft: wrap the call so the draft is to the left of the dot again, or define the method in the arrow form, which fixes the keyword this to the instance once and for all, since an arrow function takes its this from where it was written rather than from how it is called. The booklet shows both fixes under question five. When this one bites, it is the language biting, not Svelte.

The third case is a family of built-in types, and it is the class's lesson told again. A set, which holds unique values with no duplicates and is exactly right for the identifiers of the posts a reader has liked; a map, for looking values up by key; a date; a web address. None of these is a plain object. Each keeps its contents in hidden internal storage rather than in ordinary fields, and that storage has a standard name: an internal slot. An internal slot is hidden storage inside a built-in type, holding its contents where ordinary field access cannot reach. A Proxy intercepts reads and writes of ordinary fields, and these types keep their contents in internal slots instead, so the Proxy has nothing to intercept and wrapping one accomplishes nothing. Put a plain set of liked identifiers in the state rune, add an identifier, and the heart on the screen stays dark, because the add went into an internal slot the Proxy cannot see. Svelte ships reactive versions of these four, with the same methods you already know but built to report their own changes from the inside. You import the reactive set, written as the two words Svelte and Set joined into one, from a package named svelte slash reactivity, and use it exactly as you would the plain one. The booklet files this with the variants, under question six, but I moved it next to the class on purpose, because it is one lesson with two faces: the Proxy is automatic only for plain objects and arrays. A class instance you make reactive field by field. A set, a map, a date, or a web address you replace with its reactive version.

So the consolidation for this section. An instance, the object stamped from a class with new, gets no Proxy by default, so you mark its fields with the state rune, often in the constructor, the setup function that runs when the instance is born. The keyword this inside a method is fixed by the call and not the text, which is why a method handed off bare loses its instance. And the built-in set, map, date, and web address keep their contents in internal slots the Proxy cannot reach, so you import the reactive versions from svelte slash reactivity. Next, the three deliberate adjustments you can make to the Proxy when its default is not what you want.

## 4.6 Three Adjustments To The Proxy (booklet: "Reactive built-ins and the variants", questions seven, eight, nine)

You load a feed of thousands of posts that you only ever replace or add to, and giving every post and every field inside it its own Proxy is real work you will never make use of. The Proxy, the wrapper intercepting every read and write all the way down, is the right default, and it is not free, and the state rune offers three deliberate adjustments to it, one for each question here.

The first adjustment switches the depth off. There is a raw form of the state rune, written as the state rune followed by dot raw, that holds your value with no Proxy installed inside it at all. The condition that comes with it is the other side of that fact: with no Proxy watching the parts, a change to a part is seen by nothing, so the only change the raw form notices is replacing the whole value with a new one. That suits the feed exactly, because the natural way to grow a feed is to build a new list from the old one plus the next page and assign it, which is a replacement, not an edit inside. The honest caution the Svelte team presses is not to reach for the raw form out of a vague worry about speed; the ordinary Proxy is fast enough for nearly everything, so measure first, and use the raw form for genuine masses of data that you only ever swap. The booklet has it under question seven.

The second adjustment strips the Proxy off on the way out. What you are holding is the Proxy, not the bare object, and that is right while you stay inside Svelte; but hand your data to something outside Svelte, a charting library, or the browser's own function for making a deep copy of a value, and those outsiders were never built to understand a Proxy, so they choke on it or refuse it. The snapshot form, written as the state rune followed by dot snapshot, hands you back a plain, ordinary, static copy of the data with the Proxy stripped away, safe to give to any outsider. The booklet has it under question eight.

The third adjustment changes when the Proxy reports a change. Svelte normally gathers changes and applies them together for smoothness, and a change that happens to be waiting on something slow can lag a beat, which is almost always what you want. But once in a while you want an instant flash of feedback to a tap, the section link the reader just pressed lighting up at once, before the next page has even loaded, so the click feels like it landed. For that there is an eager form, written as the state rune followed by dot eager, which shows the change the very instant it happens. It is for direct feedback to an action and nothing else; let Svelte time everything else. The booklet has it under question nine.

So, three adjustments to the one Proxy. The raw form, with no Proxy installed, updated only by full replacement. The snapshot form, with the Proxy stripped off, for the world outside Svelte. The eager form, reporting at once, for an instant flash of feedback. One last fact about the Proxy remains, and it is about where the Proxy gets built, which turns out to be a fact about the compiler.

## 4.7 The Proxy Stops At The File's Edge (booklet: "Sharing state across files", questions eleven and twelve)

The logged-in reader is wanted everywhere at once, in the greeting at the top of the page, in the comment box buried deep inside an article, in a dozen scattered corners, and threading that one value down through every component in between would be misery. So you lift it out of any single component and put it in a file that other files import from. A file other files import from has a standard name: a module. A module is a file that other files import from. You keep the reader in a module, for everyone to import.

The catch reaches all the way back to the first idea of the course, that Svelte is a compiler, and to one detail of how that compiler works: it processes one file at a time, on its own. The state rune is not an ordinary function that runs in the browser; it is an instruction the compiler acts on while it rewrites a file, turning your reads and writes into the small read-and-write machinery that backs a reactive variable. That machinery has a name worth having, because the bug here is a glimpse of it leaking out: a signal, the little read-and-write unit the compiler generates behind each reactive variable. For the compiler to build that machinery inside a module, the module has to be marked so the compiler rewrites it, which you do by ending the file's name in dot svelte dot t s rather than plain dot t s. A module whose name ends in dot svelte dot t s is one the compiler processes for runes. Now the consequence, and it follows straight from one-file-at-a-time. If you export a piece of state from such a module and then reassign the exported name inside it, another file that imports the name was compiled separately, on its own, and never learned that the name is backed by a signal needing special handling at the read; so it receives the raw signal object instead of your value, and the connection breaks at the border between the two files.

The cure falls out of naming the cause: the thing that breaks is reassigning an exported name across a file boundary, so do not do that. The first way, question eleven, is to export an object and change a property on it rather than reassigning the variable. You never reassign the export; you set a field on the shared object, and because that object carries its Proxy, every importer that follows the reference to it sees the change through that Proxy. The second way, question twelve, is to not export the state at all. You keep it private inside the module, declared with the state rune but never exported, and you export functions instead, one to read it and others to change it. Every read and write then happens inside the one file the compiler controls, and you have a single doorway for changes, the one place where you could validate them, or record them, or send them to a server. The booklet has both ways under questions eleven and twelve.

So the names here are the module, a file that other files import from, and the dot svelte dot t s module, the one the compiler processes for runes. And the lesson beneath them is that the Proxy has a boundary, and the boundary is the file, because the compiler lays its wiring one file at a time. The last section steps back from state entirely, to set it beside its two siblings.

## 4.8 Three Runes, And Two Loose Ends (booklet: "Going further", questions thirteen, fourteen, fifteen)

A story carries a small label saying it is a five minute read, and you are tempted to keep that label in the state rune and update it by hand whenever the body of the article changes. That temptation is question fourteen, and resisting it is the right note to close the teaching on, because it places the state rune among its neighbours.

The label is not a value you hold and change. It is a value computed from another value, the length of the body. Force a computed value into the state rune, and you are signing up to recompute it by hand on every change, which is the surest way to end up with a label that quietly disagrees with the article. It wants a different rune, the derived rune, which is the whole subject of the next lecture, and which recomputes itself whenever its inputs change. I name it and leave it there, a deferral and not a half-explanation. And there is a third kind of thing again, neither a value you hold nor a value you compute, but an action that reaches out of your data into the world, saving to a server, drawing onto a canvas, and that is the effect rune, with its own hour later on. So of any piece of behaviour, ask which of the three it is. Holding a value is the state rune. Computing a value from other values is the derived rune. Acting on the world is the effect rune. This lecture was the first of the three.

Two quick loose ends remain. Question thirteen asks whether the article card and the clap button can share a single file; they cannot, because one file is one component, and to show two components and the way they talk to each other you write two files. Question fifteen translates for anyone arriving from React or Vue: the state rune is close to Vue's reactive value with its ceremony stripped off, and close to React's state hook without the separate setter and without the rule never to change the value directly, with the deepest difference surfacing only later, in how a reusable piece of reactive logic behaves when it runs. So the close here is that fork between three runes: the state rune for a value you hold, the derived rune for a value you compute, the effect rune for an action on the world.

## 4.9 The Whole Chapter From A Few Facts (synthesis)

Every one of the fifteen questions turned out to be a consequence of a few facts about the language, so let me run those facts one last time, in their tightest form, and let the framework fall out of them.

A variable holds one of two things. A primitive value, a number or a string or a true-or-false, the variable stores directly. An object is too large, so it lives in memory and the variable holds a reference, a pointer to where it lives. One law governs all of it: every assignment, every destructuring, and every function call copies what the variable holds, the value for a primitive, the reference for an object, never the object itself. On top of that, the framework. The state rune, the dollar sign followed by the word state, is the marker that tells the compiler to make a variable reactive, where reactive means Svelte watches it and the screen follows. For an object, the compiler installs a Proxy, a wrapper that stands in front of the object and intercepts every read and write of its fields, sitting at the object and reached only by following the reference.

From those few facts, all fifteen questions. Reactivity reaches all the way down, because there is a Proxy at every object. It survives sharing, because copying a reference, by assignment or by passing an object to a function, still reaches the Proxy. It dies on a copy, because destructuring, the shorthand that copies a field into its own variable, and pass-by-value, the rule that a function receives a copy of what the variable holds, both copy a bare value out and leave the Proxy behind; question three and question ten were that one law in two costumes. The Proxy is not installed on a class instance, the object stamped out with new, so you mark its fields with the state rune in the constructor, the setup function that runs when the instance is born; and a method handed off bare loses its instance, because the keyword this follows the call and not the text. The Proxy cannot reach the internal slots of a set, a map, a date, or a web address, so you import the reactive versions from svelte slash reactivity. You adjust the Proxy three ways: the raw form, with none installed, updated by replacement; the snapshot form, stripped off, for the world outside Svelte; the eager form, reporting at once, for instant feedback. And the Proxy ends at the edge of a file, because the compiler wires one file at a time, so shared state lives in a module ending in dot svelte dot t s and is exported either as an object you mutate or behind functions, never as a name you reassign.

That is the booklet's fifteen, in full. Question three and question ten I merged, as the copy law in two costumes. Questions four and five I took together, the class and the language's binding rule beside it. Question six I moved out of the variants to sit with the class, because it is the same lesson about what the Proxy will not wrap. The derived rune and the effect rune I named and deferred, the derived rune to the very next lecture, which is exactly where this leads, because derived values rest on the same Proxy and the same copy law you now hold from the machine up.
