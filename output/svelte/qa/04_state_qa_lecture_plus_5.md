# 04 | What Really Happens To A Reactive Variable: State In Svelte Five

## Orientation

This lesson stands on one thing you have already met: a Svelte component, which is a single file holding a little script and some markup, and the idea that inside that script you can write a special word with a dollar sign in front of it. We are going to take one of those words, the one for holding state, and follow it all the way down, until nothing about it is mysterious.

You have a companion for this. It is the printed question-and-answer booklet for this chapter, fifteen entries, numbered from entry one to entry fifteen. The booklet carries every line of code; this lesson carries none, because code teaches through the eye and we are working through the ear. So each time we reach a place where the page shows something, I will name the entry, and you can look at it there.

Here is what you will be able to do at the end. You will declare reactive state of every shape there is, a single number, a whole object, a list, a class, even a set or a date. You will share one value across an entire website. And, this is the part I care about most today, you will understand the machinery underneath, so that none of it feels like magic: where the work happens, when it happens, and which piece does what. We start with the smallest possible piece of state, and the question that opens the whole machine.

## 1. The Variable That Will Not Update (Booklet Q1, reactivity basics)

Let me build the world first, because every problem in this lesson happens inside it.

We are working on The National Times, a digital newsroom and the website it publishes. The smallest thing on that website is an article card: a headline, and under it a little button a reader can tap to applaud the piece. The number on that button is a count of how many claps the article has received. It starts at zero. Each tap raises it by one. That number is the first piece of state we will hold, and I will call it the clap count throughout.

Now the problem, and it is the most basic problem there is. You write the clap count as an ordinary variable, a number set to zero. A reader taps the button. Your click handler raises the number by one. The number in memory is now one. And the screen still says zero.

Here is the question, and if React or Vue are a faint memory in the back of your mind, your instinct will answer one way. The instinct says the screen must update, because the button is showing that variable, the variable changed, so the text should change. That is the framework reflex talking, and it is worth pausing on, because the reflex hides the thing we need to see. Strip every framework away and look at plain JavaScript underneath, and the honest answer is the opposite: nothing happens. A variable is a value sitting in memory. The page on screen was drawn once, from whatever the value was at the time, and the page has no wire back to the variable. Change the number, and the already-drawn text on screen knows nothing about it. To update what the reader sees, you would have to find that exact piece of text in the page yourself and rewrite it by hand, every single time the number moved. That chore, keeping the screen in step with the data, is the one problem every user-interface framework exists to solve.

Svelte's way of removing that chore begins with a mark you put on the variable. The mark is a word with a dollar sign in front of it, and the family of these words has a name: they are called runes. Let me give you that word with full honors, because it is the vocabulary of this entire framework. A rune is a keyword, written with a dollar sign in front, that gives an instruction to the Svelte compiler. The official documentation even opens with the dictionary meaning of the word, a rune as a mark used as a magic symbol, which is a small joke, because our whole job today is to show that there is no magic in it, only a compiler doing ordinary work. You will see runes everywhere in Svelte five, the state one we want now, and later the derived one and the effect one and others.

The rune we want is spelled with a dollar sign and then the word state, and I will call it the state rune. Wrap the starting value of the clap count in the state rune, and you have changed what kind of variable it is. It is now reactive state. Let me fix that phrase, because it is the heart of the lesson and I will say it many times in the same words: reactive state is a value Svelte watches, so that the moment it changes, every part of the screen showing it redraws on its own. Reactive. The screen reacts. You raise the clap count by one, the way you would raise any number, with no setter and no special method, and every spot on screen showing that count redraws itself. The booklet's entry one shows the article card in full, the clap count and the button, and it is the smallest complete piece of state there is.

But naming the rune is not understanding it. The instinct earlier was wrong about plain variables, so what exactly did putting a rune in front change? Who watches the variable, and when did the watching get set up? That is not a detail. That is the machine, and almost everything strange about Svelte comes from one fact about that machine, which the next section is entirely about.

## 2. The Compiler You Never See: When It Runs, And What It Leaves Behind (groundwork; the foundation under Q1, no booklet code)

This section has no entry in your booklet, because there is no new code to look at. It answers the question the last section ended on, and it is the most important fifteen minutes in the chapter, because once this machine is clear, half the surprises later stop being surprises.

The word at the center of it is compiler, so let me build the idea before I lean on it. A compiler is a program that reads the code you wrote and rewrites it, ahead of time, into different code that will run later. The key words there are ahead of time. A compiler is not part of your running program. It runs first, finishes completely, and what it produces is a separate thing that runs afterward.

You already know one compiler, even if you have not called it that. If you have used TypeScript, you wrote files in TypeScript, and then a compiler turned them into plain JavaScript before a browser ever ran them. The browser never saw your TypeScript. Nobody ships TypeScript to a browser; browsers do not understand it. You compile it down to JavaScript on your own machine, and the JavaScript is what gets sent. Svelte works the same way, one step larger. You write files ending in dot svelte, holding markup and a script together, and the Svelte compiler turns each of them into plain JavaScript, ahead of time, on your machine. The documentation says it in one line: Svelte uses a compiler to turn your components into lean, optimized JavaScript.

Now I can answer the questions directly, because you asked the right ones, the ones that make the whole thing feel inconsistent until they are answered. When does the compiler run? Once, at what we call build time, the moment you build your project, on your own computer or on a build machine, before a single visitor has loaded the site. Where does it run? There, on that machine, never in the browser. A common setup runs a tool called Vite, and when you run the build command, it produces a folder of plain files, some HTML, some JavaScript, some CSS, the finished site. Those files are the output. The compiler that made them is finished and gone.

Then comes the second, completely separate time: run time. A visitor opens the site in a browser, somewhere else, later. The browser downloads those plain files and runs the JavaScript, exactly the way it runs the JavaScript of any website. And here is the line to hold onto: the browser never sees a rune, and never sees a dot-svelte file. By the time the browser is involved, the compiler has already run, on a different machine, at an earlier time, and every rune is gone. A rune was an instruction to the compiler, and once the compiler has obeyed it, the instruction has served its purpose and does not survive into the output. This is why, as the documentation stresses, you do not import a rune, you cannot pass it around or store it in a variable. It is not a function. It is a keyword the compiler reads and then removes, the way a recipe's instruction to preheat the oven does not appear in the finished cake.

This clears up a confusion you named directly, so let me meet it head on, because it is the sharpest way to feel the difference. You can add React to a plain web page with a single script link, the way you would drop in any ordinary script, no build step at all. Can you do that with Svelte? No. And the reason is exactly the compiler. React's reactivity is a library that lives and runs in the browser, so you can link the library and start calling it. A dot-svelte file is not a library and is not something a browser can run; it is raw material for the compiler. There is nothing to link, because there is something to compile first. That difference is not a limitation hiding in the corner. It is the entire design. Because the compiler does the work ahead of time, what reaches the browser is small and direct, with most of the framework already compiled away into plain instructions.

And one more worry, because it is a reasonable one: if there is a compiler, do you now need a server, does your code run on a back end? No. Build time and a back end are different things. The compiler runs once and produces plain static files, and plain static files can be served from anywhere, a simple file host, no server program running, no back end at all. Running code on a server for each visitor is a separate, optional choice, a different topic entirely. The compiler by itself implies none of it. It is a translator that runs once and then steps out of the way.

So, with all of that settled, here is the thing the compiler actually wrote for you when it saw the clap count marked with the state rune. It did not leave a plain number. It wrote out code that, when it runs in the browser, builds a small container around that value, and this container has a name in the field, a signal. Let me hand you that word carefully, because it is the true atom of everything reactive in Svelte. A signal is the cell the compiler makes for one reactive value, holding it behind a get to read it and a set to change it, and remembering every place it was read so it can notify those places when it changes. Read the clap count anywhere, and the compiled code is really calling get on the signal, and the signal quietly writes down that this spot depends on it. Change the clap count, and that is a call to set on the signal, and the signal tells every spot that read it to redraw. You can confirm this with your own eyes: the Svelte playground online has a tab labelled JS Output, and there you will find your read turned into a get and your write turned into a set on a thing the types call a Signal. That is not a picture I am painting. That is the compiled code.

That gives us the sentence the whole lesson turns on. Reactivity is a read that something is watching. For a single value, the watcher is the signal, and the watching was wired up by the compiler, ahead of time, before the browser ever opened. Keep reading through the signal, and the screen follows. We will return to that sentence again and again, because most of the traps in this chapter are nothing more than someone reading around the signal instead of through it. So far we have one signal for one number. But real state is rarely one number. What happens when the value you mark is a whole object?

## 3. When State Is A Whole Object: The Proxy, And How It Differs From The Signal (Booklet Q2, deep reactivity)

Let me widen the world. An article on The National Times is not only a clap count. It is an object, a bundle of labelled fields: a headline, which I will also call the title; a body, the text of the piece; and the clap count we already have. One variable, several fields inside it. And alongside it, the newsroom keeps a checklist for getting a story ready to publish, a list of small tasks. Each task has two fields: a text label, like add the photo, or legal check, and a done flag that starts false. So now we are holding richer shapes, an object with fields, and a list of objects.

A signal, as we built it last section, watches one value as a whole. That is fine for a number. But an article has many fields, and you want the screen to react when any one of them changes, the headline on its own, the clap count on its own. A single signal around the whole article cannot tell those apart. So what does the state rune do when the value is an object?

It does something different, and this is the exact place your two foundations need to be kept apart, so let me be very plain about it. When the value is a plain object or array, Svelte wraps it, while the app runs, in a proxy. Here is the word, and it is a standard JavaScript word with its own documentation page: a proxy is a wrapper Svelte puts around an object while the app runs, giving every one of the object's properties its own signal, automatically, and all the way down. Read that against the signal and hold the difference, because it is the answer to a question you might already be carrying: are a signal and a proxy the same thing? No. A signal watches one value. A proxy is a bundle of signals, one for each property of an object. The signal is the atom; the proxy is a machine built out of many atoms, one per field. When you marked a single number, you got one signal and no proxy. When you mark an object, you get a proxy, and behind it a signal for each property you touch.

Two things follow from the proxy being made of per-property signals, and both matter. The first is that it reaches all the way down. The field word for this is deeply reactive, and it means the proxy does not stop at the outer object: any object or array nested inside gets its own proxy, with its own per-property signals, and so does anything nested in that, to the bottom. So when an editor flips the done flag on the first task, that task deep in the list has its own proxy, the write goes through that field's signal, and the one checkbox bound to it redraws. Not the whole list. The one field of the one item.

The second thing is where React veterans exhale, so let me set it up the way the scar was made. In React, you are taught never to change state in place. If you reach into an array and push a new item on, React does not notice, and the screen sits frozen while your data has moved on. Mutating state is the classic React bug. So a React-trained reader, asked whether pushing a task onto our checklist updates the screen, will say no, that is the trap, it freezes. In Svelte it does not, and the reason is the proxy. The proxy intercepts the array's own methods, not only direct writes. Push a task onto the list, and the proxy sees the push, knows the list grew, and renders the one new row. The plain, obvious, change-it-in-place code, the very code React punished, is the code that works here. You flip a flag, you push, you splice, and the screen keeps up. The booklet's entry two shows the checklist in full, the toggle and the push.

One honest footnote, which the booklet also flags. When you change a property through the proxy, the original underlying object you first handed in is not itself changed; the proxy keeps the change in its own layer. You will go years without noticing, because you always read back through the proxy. It surfaces in one narrow case: if you bring your own proxy with its own handlers, wrap your object first and hand the result to the state rune, not the other way around.

So now you hold the two run-time pieces apart, and they are not the same piece. The signal watches one value. The proxy is a bundle of signals, one per property, deep all the way down, and it was placed around your object while the app runs. Both share one demand, though, and the next two sections are about what happens when you break it. Both the signal and the proxy only work while you read through them. So here is the uncomfortable question. What happens if you read a value out of the proxy once, and then keep using your copy instead of going back through the proxy? Does the copy still hear the changes?

## 4. Destructuring: The Copy That Stops Listening (Booklet Q3, destructuring)

Stay with the article, our reactive object with a headline, a body, and a clap count, wrapped in its proxy, which is a bundle of per-property signals. There is a piece of everyday JavaScript convenience that walks straight into the question I asked a moment ago, and it is called destructuring.

Let me define destructuring plainly, because the whole trap lives in one detail of how it works. Destructuring is a shorthand for lifting a field out of an object into its own standalone variable. Instead of writing a line that reads the headline off the article and puts it in a variable called title, you write a small pattern with braces that pulls the title out for you in one stroke. Convenient. And here is what it costs.

The instant you destructure, JavaScript reads the headline out of the article, once, right at that line, and copies it into your new standalone variable. Now follow it through the machine we built. Reading the headline did go through the proxy, through that field's signal, but only the one time, to make the copy. Your new title variable is now a loose, ordinary string. It has no proxy behind it and no signal, no wire of any kind back to the article. So later, when an editor renames the article, the new headline flows into the proxy, and the proxy faithfully updates everything still reading through it. But your copied variable was never reading through the proxy. It read once, took its copy, and walked away. So it stays frozen at whatever the headline was the moment you destructured, while the article's real headline has moved on without it.

The booklet's entry three puts both on screen at once, the frozen copy beside a fresh read straight off the article, so you can watch one sit still while the other updates. The fix is to not pull the field out into its own variable at all. Read it fresh each time, straight off the article, so every read goes through the proxy and its signal. And this is not a Svelte quirk you are learning to dodge. It is how copying works in plain JavaScript. Vue, the other framework some of you half remember, trips on this identical move with its own reactive objects, for the same underlying reason.

So the rule, stated as a consequence and not a decree: a destructured field is a value read once and copied out, therefore it has no link back to the signal, therefore it cannot hear later changes. It is the spine sentence again. Reactivity is a read that something is watching, and a copy taken once is a read that already happened and will not happen again. Now, the unsettling part. That exact mistake, a value read once and frozen, hides in a place you would never suspect, a place you use a hundred times a day. It hides inside an ordinary function call. That is the next section, and I am going to work it slowly, with real names and real values, because it is the single subtlest thing in the chapter.

## 5. Passing State Into A Function: The Same Trap, Worked Through (Booklet Q10, passing state into functions)

I want to start this one away from Svelte entirely, with a plain function, because the trap is plain JavaScript and you will see it more plainly with the framework set aside for a moment.

Here is a function. It is called greet. It takes one input, which I will call name. It returns a string: the word Hello, then a comma and a space, then whatever the name was. That is all it does. Hand greet the name John, and it returns the string Hello, John. Hand greet the name Mary, and it returns the string Hello, Mary. Nothing surprising lives in greet; it builds a greeting from whatever name you give it, and hands the finished greeting back.

Now let us use it with reactive state. On The National Times, the signed-in reader has a name, and that name is reactive state, a value Svelte watches. Right now the name holds the string John. You call greet, passing it the name, and greet returns Hello, John. You take that returned string and store it in a variable. I will call that variable the message. So the message now holds the string Hello, John. Good.

A moment later, the reader changes their display name from John to Mary. The name, the reactive state, now holds Mary. Here is the question. What does the message hold now?

The natural expectation, the one almost everyone reaches for, is Hello, Mary. The message was built from the name; the name changed to Mary; so surely the message followed and now says Hello, Mary. That expectation is wrong. The message still holds Hello, John. It never changed. It did not so much as flicker. And the reason has a proper name you will meet in the Svelte documentation itself: JavaScript is pass-by-value. Let me fix that term: pass-by-value means a function receives a copy of each argument's value as it stood at the moment of the call, never a live link to the variable it came from.

Walk it through with our names and it stops being abstract. At the moment you called greet, the name held John. So greet did not receive the name variable. It received a copy of the string John, the value as it stood right then. Inside greet, that input is now an ordinary string, John, with no thread back to the reader's name. Greet built Hello, John out of that string and handed it back. You stored the result in the message. That stored string is now a finished, frozen thing, sitting in the message, complete. Later the reader's name became Mary, but nothing went back and ran greet again, and the message has no way to know the name moved on, because it was never connected to the name in the first place. It only ever held a copy of an old greeting. It is precisely the frozen copy from the destructuring trap, wearing the disguise of a function call.

Now, the reassuring part, the reason your everyday components are not riddled with this bug, and it follows from the signal directly. The freeze only bites when you store the result. Suppose instead of storing the message, you call greet right there in your markup, in the spot on screen where the greeting shows. Reading the name in your markup goes through its signal, so that spot becomes a place that depends on the name. When the name changes from John to Mary, the signal redraws that spot, which re-runs the markup there, which calls greet again, this time with the name as it now stands, Mary, and the screen shows Hello, Mary. You did not store a stale copy; you re-read and re-called on every change. The booklet's entry ten shows both lines side by side, the stored one that freezes at Hello, John and the inline one that keeps up.

So storing the result freezes it; calling inline keeps it fresh. But there is a third case, and it is the one you must reach for when you genuinely need to hand the living value into a function that will keep it and read it again later, across some boundary. You cannot hand it the value, because the value is a copy frozen at the call, as we saw a moment ago. So instead you hand it a small function whose entire job is to read the name and give back whatever it holds right now, every time that function is called. Let me explain exactly what that little function looks like, in words, because it is a JavaScript shape you will use constantly and I do not want it to stay vague.

In JavaScript there is a compact way to write a tiny function. You write a pair of empty parentheses, which means the function takes no input. Then you write an arrow, a small arrow made of two characters. Then you write the single value the function gives back. So a function written as empty parentheses, an arrow, and then the word name, is a function that takes nothing in and hands back the current value of name. The empty parentheses say it needs no argument. The arrow says what follows is what it returns. And because the word name sits in the body of the function, it is read freshly every single time the function is called, not once when you wrote it. Call that little function now, while the name is John, and it returns John. Call the very same function later, after the name has become Mary, and it returns Mary. It re-reads each time.

That little function has a name in the field, a getter, a small function whose only job is to read and hand back a current value on demand. And now the contrast is exact, so hold the two side by side. Passing the name passes a copy of today's value, John, frozen forever. Passing the getter, the empty parentheses and the arrow and the name, passes the ability to ask for the value, so the receiving function can read the latest, John now, Mary later, as often as it likes. One hands over a frozen photograph; the other hands over a live phone line. Keep this getter in mind, because in a few sections it becomes the clean way to share one value across an entire application.

So three outcomes from one piece of plain JavaScript, all of them the spine sentence in different clothes. Store the result of a function called on state, and you froze a copy, the same death as the destructured field. Call it inline in the markup, and the signal re-runs it, so it stays fresh. Or pass a getter, empty parentheses and an arrow and the value, and you have handed over a live read instead of a dead copy. Next, a different container for state, one Svelte deliberately refuses to wrap for you.

## 6. State In A Class, And The This That Slips (Booklet Q4, reactive class fields; and Q5, method binding)

The newsroom needs a richer object than a loose bundle of fields. It needs a draft. A draft is an article in progress, and it should know how to act on itself: reset itself back to empty, mark itself ready to publish. When a thing carries both data and the actions that operate on that data, the natural tool is a class. Let me lay the word down. A class is a blueprint for making objects. You describe the shape once, the fields it holds and the actions it can perform, and the actions that live on it are called methods. Then you stamp out objects from the blueprint, each one called an instance, and you make one with the word new. So we write a Draft blueprint with a text field for the working headline and a done flag for ready-to-publish, and a reset method that clears them, and we make one draft for the editor with the word new. The booklet's entry four has the blueprint in full.

Here is the question, and it follows from the proxy we built two sections ago. You hand the screen an instance of your Draft class and start changing its fields. A class instance is an object. The state rune wraps objects in a proxy and gives every field its own signal. So the fields are reactive automatically, surely?

No, and this is a deliberate refusal, not an oversight, and the reason was already sitting in the proxy section. Remember that the proxy reaches deeply, wrapping nested objects, but only until it meets something that is not a plain object or array. A class instance is exactly that stopping point. The proxy reaches it and halts. Svelte will not clamp a proxy around a whole class instance, and holding back is wise: a class is a fussier creature than a loose object. It has methods. It can have private fields, its own internal machinery, the very things a class exists to protect. Wrapping the entire instance in a proxy that intercepts every property could quietly break that machinery. So Svelte declines, and asks you to switch on reactivity yourself, one field at a time.

You do it by marking the individual field with the state rune, the same rune from the clap count, so that this one field gets its own signal. You write the rune right on the field, or on the field's first assignment inside the constructor. And let me hand you that word, because it runs through every class you will write: the constructor is the setup function that runs once, automatically, the instant you make an instance with new. So either mark the done flag with the state rune where it is declared, or mark the text field with the state rune on its first assignment in the constructor, and that single field becomes reactive, backed by its own signal, while the instance around it stays an ordinary class. The booklet's entry four shows both spots, the field and the constructor.

There is a small surprise the compiler leaves behind, and the booklet notes it. To make a marked field reactive, the compiler turns it into a hidden get and set pair on the class, the signal again, wearing class clothing. A side effect is that those fields become non-enumerable, which means that if you loop over the instance's keys expecting to list its fields, the reactive ones do not show up. Rare to hit, but real, and now you can predict it rather than be baffled by it, because you know the field is secretly a get and a set, not a plain property.

Now the second half, entry five in your booklet, and I will flag honestly that we are leaving reactivity for a moment. This next trap is pure JavaScript, it has nothing to do with Svelte, and it bites people constantly. Our Draft has that reset method. You want a button to call it, so you wire the button straight to the draft's reset method, handing the method over by name. Reasonable. The reader clicks. And the draft does not reset.

The culprit is one of the genuinely subtle corners of JavaScript, the keyword this. Let me define it carefully, because the definition is the whole fix: inside a method, the keyword this means the object the method was called on, and which object that is gets decided by how the method is called, not where it was written. That second half is the crux: not where it was written, but how it is called. When you hand the button the draft's reset method by name, bare, you have torn the method loose from the draft. The button is now holding a free-floating function. Later the click fires, and the browser calls that function as the button's own handler, so at that moment the method was called on the button. Therefore this, inside reset, is the button. The method runs faithfully, trying to clear a text field and a done flag, but on the button, which has no such fields, while your draft sits untouched. The right action happened to the wrong object.

Both fixes keep this pointed at the draft, and both are about controlling how the method gets called. The first reuses the exact shape from the last section. Do not hand the method over bare. Hand over a small inline function instead, empty parentheses, an arrow, and then a call to the draft's reset. Now when the click fires, the thing that runs is your little function, and inside it the call is written as the draft's reset, so the draft is right there as the object it is called on, and this is the draft. The second fix reaches into the blueprint. Define reset not as an ordinary method but as an arrow function held in a field. Arrow functions have a special property worth keeping: they do not get their own this at all, they permanently borrow the this from the place they were created, which for a field is the instance being built. So an arrow-function reset is glued to its draft for life, and no matter who calls it, however bare, this stays the draft. The booklet's entry five shows the broken wiring and both fixes.

So a class is the first shape Svelte will not watch for you, and you switch on each field by hand with the state rune, one signal per field; and the keyword this, decided by how a method is called and not where it was written, is the JavaScript trap waiting in every class method. A class is one kind of object the proxy refuses. There is a whole family of others, and they hide their contents even more thoroughly than a class does.

## 7. The Collections The Proxy Cannot See Into (Booklet Q6, reactive built-ins)

Let me open a second surface in our world, because the next problem lives most naturally there. Alongside the formal news site, The National Times runs a social feed, the fast-scrolling kind you know from an X timeline, a stream of short posts from readers and reporters. On that feed, every post has a little heart, and the heart should fill in if the signed-in reader has already liked that post. So you need to track, across all the posts, which ones this reader has liked.

You could keep a list of the liked post identifiers, but there is a question you ask constantly: is this particular post liked? Asked against a plain list, that scans the whole list every time a post draws. The right structure for membership is a Set. A Set is a built-in JavaScript collection that holds unique values, no duplicates, and answers the question does it contain this one instantly. That fits exactly: a reader cannot like a post twice, and you want an instant yes or no per post. This membership shape is everywhere in real applications, the selected rows in a table, the comment threads currently expanded, the users shown as online. So you make a Set of liked post identifiers, hand it to the state rune, and when the reader taps a heart you add that post's identifier to the Set.

The heart does not fill. Nothing on screen moves. And by now you might predict it should work, since a Set is an object, and the state rune wraps objects in a proxy. That prediction is the trap, and the reason it fails is precise, and it comes straight from how the proxy works. The proxy watches an object by giving each of its properties a signal. But a Set does not keep its contents in properties. It keeps them in its own private internal storage, a hidden compartment the language gives it, reachable only through its methods, like add and has. When you call add, no property is written that the proxy could attach a signal to. The change happens entirely inside that private compartment, behind glass the proxy cannot reach. So no signal fires, and the screen never hears. The same is true of a Map, a Date, a URL: each keeps its real contents in internal machinery the proxy cannot see into, so the per-property trick has nothing to grip.

Svelte's answer is a small package, named svelte slash reactivity, that ships reactive versions of exactly these built-ins, written by hand to do the tracking the proxy cannot. There is a Svelte Set, a Svelte Map, a Svelte Date, a Svelte URL, and a Svelte version of the URL's query parameters. You import the Svelte Set from that package and use it precisely as you would a normal Set, the same add, the same has, the same size, the same iteration. The difference is that reading it, calling has inside your markup, or reading its size, registers a dependency, so a later add or delete redraws exactly the hearts that changed. You swap a normal Set for a Svelte Set and you are done; the booklet's entry six shows the swap and the heart that now fills.

The other three earn their keep in jobs you will recognize. A Svelte Map is for a key-to-value lookup that must drive the screen as it changes: a cache of fetched posts keyed by identifier, or a running like-count per post. A Svelte Date is for anything that shows live time, a ticking clock, or a two-minutes-ago label that keeps counting up. A Svelte URL, with its query-parameter companion, is for binding the feed's filters to the address bar, so the chosen filters, the visible feed, and the URL stay locked together, and a shared link reopens the same view. Same methods you know, made reactive.

So the rule falls out of the mechanism: a plain Set, Map, Date, or URL hides its contents from the proxy, therefore it cannot react under the state rune, therefore you reach for its reactive twin from the svelte reactivity package. That package is the patch for everything the proxy cannot see into. And our feed now raises the opposite worry. The proxy is thorough; it wraps everything deeply, giving every property of every post its own signal. On a handful of posts that is free. But a feed does not stay small. What happens when it grows to thousands of posts, and the proxy's thoroughness turns from a gift into a bill?

## 8. Raw State: Turning The Proxy Off (Booklet Q7, state dot raw)

Stay on the social feed, and let it grow the way feeds really grow. An infinite timeline, the kind that loads more as you scroll, an X feed or a long video watch list, climbs into the thousands of posts, each post an object with an author, some counts, maybe media. By default the state rune is deep: it wraps that whole array, and every post object inside it, each in its own proxy, each property given its own signal. For a handful of items that cost is nothing. At thousands, building a proxy and its signals around every single post, only so the list can draw, is real, measurable, wasted work, and the overhead starts to bite.

And you do not even use what you are paying for. Look at how this feed actually changes. You never reach into the array and edit post number eight hundred and forty-seven in place. You load the next page and append a fresh batch. You switch feeds and replace the array wholesale. Every change you make to this list is a replacement of the list, never an edit inside it. You are paying for deep, in-place watching of objects you never edit in place.

That is the exact situation the raw variant of the state rune is built for. You write the state rune followed by dot raw, and I will call the result raw state. Here is its definition, and it lands cleanly now that you hold the signal and the proxy as separate pieces: raw state is a reactive value kept as a single signal with no proxy around it, so it reacts when you replace the whole value, but not when you reach inside it. Read that against everything we built. The single top-level signal is still there, the same kind of cell as the clap count, so the variable itself is watched. But there is no proxy, which means no per-property signals, which means nothing is watching the insides. So thousands of posts sit there as plain objects, unwrapped, free.

And the one rule of raw state is now a consequence, not a decree, which is the whole point of building the machine first. There are two kinds of change, and you must hold both. To mutate means to reach inside, to push a post onto the array or set a field on one post. Raw state ignores mutation completely, because mutation needs a per-property signal to notice it, and raw state has none. To reassign means to hand the variable a whole new value, a brand-new array. Raw state tracks reassignment, because reassigning the variable is a set on that one top-level signal, which is the one watcher raw state kept. Mutation, ignored, no inner signals. Reassignment, tracked, the top signal fires. That is the entire behavior, and you could have derived it yourself from the definition.

It fits the feed like a key in a lock, because the idiomatic way to grow a feed was already to build a new array, the old posts followed by the next page, and assign that, rather than to push. You were going to reassign anyway; raw state drops the proxy you were not using. The booklet's entry seven shows the load-more function reassigning a new array, with the marks showing which moves are tracked and which are ignored. The per-post thing that genuinely does flip, which posts are liked, does not live in the raw array at all. It lives outside it, in a Svelte Set of liked identifiers, the very structure from the last section. The big cold list goes in raw state; the small hot membership goes in a reactive Set.

One caution, stated plainly by the Svelte team, so I will pass it on with the same weight. Do not reach for raw state by reflex, the moment you hear the word performance. Proxies are fast enough for the overwhelming majority of state you will ever write. Raw state is a specialist tool for the genuine case: thousands of items, or a value you only ever swap as a whole, a large response you replace on each fetch, a big dataset handed to a charting library that does not want Svelte poking at its insides. Measure first; reach for raw when the profile actually shows the cost. And note, raw state can still contain reactive state, a raw array holding ordinary reactive objects, and it works on class fields too.

So raw state is the deliberate opt-out: keep the one signal, drop the proxy, update by replacing the whole value. We turned the proxy off there for performance, to stop paying for watching we did not need. There is a second reason you might need the proxy out of the way, and it has nothing to do with speed. Sometimes you must hand your data to a tool that lives outside Svelte entirely, and that tool has never heard of a proxy.

## 9. Snapshot: Handing State To The Outside World (Booklet Q8, state dot snapshot)

Come back to the news site and to our article, the reactive object with its headline and its clap count, wrapped, like everything reactive of its kind, in a proxy. Inside Svelte that proxy is exactly what you want. The trouble starts the moment you hand your article to code that lives outside Svelte and was never taught what a proxy is.

There are three concrete cases you will actually hit. You want to deep-copy the article using the browser's own built-in copier, the one called structured clone, which duplicates a data structure for you. Or you want to hand the article to a charting library to draw it. Or, most ordinary of all, you want to print the article to the console while debugging. In each case the receiving tool meets your article and finds not a plain object but a proxy, Svelte's watchful wrapper, a strange thing it does not understand. The structured copier can choke on it and throw an error. The console prints something cryptic, the word Proxy and a tangle, instead of your clean fields. The outside tool was built for plain objects, and you handed it a watched one.

The fix is a third variant of the state rune, written as the rune followed by dot snapshot, and the word is the definition: a snapshot is a plain, static copy of reactive state with the proxy peeled away, safe to hand to code outside Svelte. You pass your reactive article to snapshot, and it walks the proxy and hands you back an ordinary, frozen copy of the data, every field present, no proxy anywhere, a photograph of the article as it stands right now. Give that to the structured copier and it copies happily. Give it to the chart and it draws. Print it and the console shows your clean fields. The booklet's entry eight shows the snapshot wrapped around the article on the way out, both into the console and into the structured copier.

One edge to remember, which the booklet flags. If the value you snapshot has a method named to-J-S-O-N, the method that controls how an object turns itself into J-S-O-N text, then the snapshot copies whatever that method returns, rather than the raw object. Usually what you want; occasionally a surprise if you forgot the object had one.

So a snapshot is how reactive state leaves home: the proxy peeled off, a plain static copy in its place, safe for any outside hand. Snapshot is about handing data across a boundary in space, out of Svelte to another tool. There is one more variant, and its concern is not space but time: not where the update goes, but the exact instant it lands on screen.

## 10. Eager: Forcing The Update To Land Now (Booklet Q9, state dot eager)

Back to the news site, to a small but specific part of it: the section navigation bar across the top, the row of links, World, Sports, and the rest, that takes the reader between sections. Whichever section the reader is in, that link should look active, highlighted, so the reader always knows where they are. The current path drives which link is lit.

Now a subtle thing about Svelte you have not had to think about yet. Svelte is careful about when it repaints. It does not rush to redraw on every tiny change. It gathers changes together and coordinates them, for smoothness, and, importantly, if a value happens to be waiting on something slow, an in-flight load of the next page for instance, Svelte may hold the visible update a beat so that everything lands together and consistent. Almost always that coordination is what you want; it is why Svelte applications feel composed rather than jittery.

But here is the case where it works against you. The reader clicks the Sports link. The next page has to load, and that load is not instant. With Svelte coordinating, the highlight on the Sports link might wait for the page rather than moving at the instant of the click. So the reader clicks and, for a beat, nothing visibly responds. The click feels dropped. What you want here is for the link to light up the moment it is pressed, immediate visual feedback, while the page is still on its way, so the click feels like it landed.

The tool is the last variant of the state rune, written as the rune followed by dot eager, and the word fits: eager state reflects a change on screen the instant it happens, skipping the coordination Svelte normally does to time updates. Wrap the path value in eager where the navigation decides which link is active, and the highlight flips the moment the reader clicks, ahead of the loading page, with no wait for the coordinator. The booklet's entry nine shows the nav links reading the path through eager.

Then the discipline, because this one comes with a rope around it. Use eager sparingly, and only for this: instant feedback in direct response to a user action, the click that needs to feel acknowledged at once. For everything else, let Svelte coordinate, because coordinated updates give the better experience across the application as a whole. Eager is the specialist you call when, and only when, a human action needs to feel instantly heard.

So eager is the override on timing: skip the coordinator, paint the change now, reserved for feedback to a user's action. That is the last of the variants that live inside one component. Everything so far, the clap count, the article, the checklist, the draft, the feed, has belonged to a single component. But the signed-in reader, that name we greeted back with John and Mary, belongs to no single component. The masthead wants to greet them, the comment form wants their name, a dozen corners of the site need the same one value. State has to grow up and be shared, and sharing is where the compiler's one habit, working a single file at a time, finally matters.

## 11. One Value The Whole Site Shares (Booklet Q11, sharing across files; and Q12, sharing, encapsulated)

I am taking entries eleven and twelve of your booklet together, because they are two answers to one question, how to share a single value across the whole application, and the second answer is the first one tightened. And to understand both cleanly, we finally collect on something I planted back in the compiler section.

The world first. The shared value is the signed-in reader, the person currently logged into The National Times, the same name we greeted earlier, now grown into a full reader with a name. It has to be readable everywhere: the masthead greets the reader by name, the comment form signs posts with it, more corners besides. Most state lives inside one component, like the clap count on its one card. But the reader belongs to no one component, and threading it down through every layer of the site by hand would be madness. So you lift it out of the components and put it in a module. Let me set that word: a module is a standalone file you import from, and giving its name the dot-svelte ending lets you use runes inside it. That ending matters, and the compiler section already told you why. Runes are instructions to the compiler, and the compiler only treats a file as component code if its name says so. A plain JavaScript file is left alone, runes and all, which would break. A file whose name ends in dot svelte dot t s, or dot svelte dot j s, tells the compiler to treat it like component code, runes allowed, so you can declare the state rune in it and share it.

Now the heart of it, and this is the most subtle move in the chapter, so I will build it on the machine rather than hand you a rule. Recall two facts from the compiler section, and watch them collide. First, the compiler turns every read of a reactive value into a get on a signal, and every write into a set. Second, the compiler works one file at a time, at build time; it rewrites each file looking only at that file. Now suppose you declare the reader in your module as a bare reactive variable and export it, and then, when someone logs in, you reassign that variable to the new reader. Inside the module, the compiler sees the reassignment and writes it correctly as a set on the signal. But another component imports that variable. The compiler, rewriting that other file all by itself, at build time, has no way to know the imported name came from a signal whose reads need wrapping in get. So the importing file never gets the get-and-set treatment for it. What it receives is the raw signal object, the cell itself, not the value inside. Ask it for the reader and you get back, if you check, an object, not a person. The reactivity has leaked out as bare plumbing. The booklet's entry eleven shows this broken export and names it.

So the rule falls out of the machine, and there are two safe shapes. The first, entry eleven: do not export a bare variable you reassign. Export an object, and change a property on it. Wrap the reader inside an object, export that object, and to log someone in, set the reader property on it rather than reassigning the whole thing. This works for two reasons standing together. The object is exported by reference, so every importing component holds the very same object. And the proxy, remember, is a run-time wrapper that travels with the value itself; it is not something the compiler had to add file by file. So changing the reader property goes through that object's proxy and its per-property signal in any file that holds the object, no per-file rewrite required. The instant you set the property, every component reading it updates. The line to carry: share app-wide state by exporting an object you mutate, never a bare variable you reassign.

The second shape, entry twelve, is the first with a guard rail, and it brings back the getter from the function section. The exported object works, but it is wide open: any component anywhere can write the reader, with nothing standing guard. Often you want the opposite, a single controlled doorway, so every change to who is logged in runs through one place where you could check it, log it, call the server. That discipline has a name, encapsulation: encapsulation means hiding a value away and exposing only chosen functions to read or change it. You get it by keeping the reader as a private variable inside the module, declared with the state rune but not exported, and exporting functions instead: a getter that returns the current reader, and actions, log-in and log-out, that change it. Because the variable never leaves the file, every read and write to it happens inside that one module, where the compiler rewrote it correctly, which sidesteps the leak from entry eleven entirely; outside files only ever call functions, they never touch the variable. And it stays reactive for the same reason the inline call stayed fresh in the function section. When a component calls the getter in its markup, the getter reads the private reactive variable right then, through its signal, so that spot re-runs whenever the reader changes. The getter is reading through the watcher on demand, which is exactly what a getter is for. The booklet's entries eleven and twelve put the two modules side by side, the open object and the guarded functions.

Choosing between them: reach for the exported object when you only want shared data with no ceremony; reach for the private-variable-and-functions when changes need a guard rail. And when this pattern grows heavy, the cleanest form is a reactive class, the Draft-style class from earlier, a Session class with its reader as a marked field, one signal, and log-in and log-out as methods, packaging the private state and its actions in one blueprint. Same idea, tidied into an object that owns itself.

So sharing is a module with the dot-svelte ending so runes are allowed, an object you mutate or functions you call, never a bare reassigned export, because the compiler worked one file at a time, at build time, and a signal does not survive that crossing on its own. We have leaned hard on the idea that one file is the unit the compiler works on. That raises a small, clean question worth answering outright. If a file is the unit, how many components can live in one file?

## 12. One File, One Component (Booklet Q13, one file, two components)

A short section, but a useful fence to know is there. Throughout this lesson, every component has been one file. The article card, the checklist, the draft editor, the post card, the navigation bar, each its own file. So when you want to show two components together, say the article card and a separate clap button it contains, and you wonder whether you can define both in a single file to keep them close, the honest answer is no. In Svelte, a component file, the kind ending in dot svelte, is exactly one component, and the compiler turns it into exactly one component. One file, one box. There is no syntax to declare a second, separate component inside it. To show two components and the relationship between them, you write two files, the card and the button, and have one bring in and place the other, and that parent-and-child conversation, how they pass data and events, is its own topic later in the series.

Two features get mistaken for a back door, and it is worth naming both so you are not fooled. The first is a snippet, which lets you reuse a chunk of markup inside one component. But a snippet is not a second component: it has no script and no state of its own, it borrows everything from the host it lives in. It is reuse within the one box, not a second box. The second is the self-reference feature, which lets a component render itself again, for genuine recursion, a comment that displays its own replies displaying theirs. That is the same one component calling itself, not a second component. Neither gives you two real components in one file, because that thing does not exist. The booklet's entry thirteen shows the two-file shape, the card importing the button.

So the dot-svelte file is the unit, one component per file, and relationships are always more than one file. That settles the shape of components. It leaves one last thing to settle, and it is the most practical question of all, the one you ask yourself every time you reach for a rune: which rune, for this value, right now?

## 13. Hold, Compute, Or Do; And The Bridge From React And Vue (Booklet Q14, the three runes; and Q15, the framework bridge)

We end where you will spend your days, choosing. Three runes sit near each other in Svelte five, and reaching for the wrong one is among the most common mistakes, so here is the deciding question, framed around a concrete case from our world. On the article card we want a small label, five minute read, the estimated reading time of the piece. It is computed from the length of the article's body. Which rune holds it?

The tempting answer is the state rune, the one you now know best, hold the label in reactive state. That is the trap, and seeing why draws the line between all three runes. The state rune is for a value you hold and change over time: the clap count, a menu's open-or-shut flag, the text a reader is typing into a box. But the reading-time label is not held. Nobody sets it. It is computed, every time, from the body. A value computed from other values is the job of a different rune, the derived rune, which I will only name today and hand to the next lesson, lecture five, where it gets built properly. The derived rune recalculates itself whenever its ingredients change. If instead you compute the reading time once by hand and store it in the state rune, it goes stale the instant the body changes, the body grew, the label still shows the old number, and that staleness is precisely the bug the derived rune exists to kill. It is, in fact, the very same freeze from the function section, a value computed once and stored, gone stale. And there is a third rune, the effect rune, also for lecture five, which is not for producing a value at all but for doing something out in the world when state changes, saving to the server, drawing to a canvas.

So carry the deciding question, asked of any piece of behavior: am I holding a value, which is the state rune; computing one from other values, which is the derived rune; or doing something in the world, which is the effect rune? Hold, compute, do. The reading-time label is a compute, so it is the derived rune, never the state rune. The booklet's entry fourteen lays the three side by side.

And now, since some of you carry React and Vue as fading memories, let me close the loop you have been half-holding, entry fifteen: is the state rune anything new, or the same thing as React's use-state or Vue's ref under a fresh name? The honest answer is almost, and the gaps are the whole point. In React, you made a reactive value with use-state, which handed you the value together with a setter function, under an iron rule: never change the value directly, always call the setter. The state rune is use-state with the setter and that rule removed; you change the variable directly, because the compiler wired the set on the signal for you. In Vue, you used ref, which wrapped your value in a little box you had to open with dot value on every read and write. The state rune is ref with the dot value removed; the compiler reads the box for you, so you touch the plain variable. Strip the ceremony from either, and you arrive at the state rune.

But there is a deeper difference, and it is the compiler one final time, so the lesson closes on the machine it opened with. When you move reactive logic into one of those dot-svelte modules, the function that sets it up runs once, and the reactivity lives on inside the value, in its signal. A React hook does the opposite: it re-runs top to bottom on every single render, the whole function body again and again. That is the real divide, and it is the build-time compiler against the run-time library, exactly the contrast from section two. React puts the reactivity in the repeated running of your code in the browser. Svelte's compiler put it, ahead of time, into a signal, so your code runs once and the signal does the watching from then on. The state rune is a plain variable that a compiler wired to a signal, doing ahead of time, on your machine, the work React and Vue do over and over in the browser. The booklet's entry fifteen shows the same counter in all three dialects, the setter, the dot value, and the plain variable.

## Closing: The Machine, Named Once More

Everything in this chapter was one claim. State in Svelte is a plain variable, and a small, knowable machine is what makes it react, with no magic in it anywhere. There are three pieces to that machine, and you now hold them apart. A compiler, which runs once on your computer, ahead of time, before any browser is involved, and rewrites your variable into working code. A signal, the cell that code builds for one value, which notices when it is read and tells the screen when it changes. And a proxy, which is a bundle of signals, one for every property of an object, deep all the way down. One sentence ties every rule to those pieces: reactivity is a read that something is watching, so keep reading through the watcher, the signal or the proxy, and the screen follows; copy the value out once and it freezes.

Let me gather the words you now own, each at its tightest, because these are the words the documentation, the error messages, and the next chapter will speak to you.

A compiler is a program that runs once on your machine, ahead of time, and rewrites your dot-svelte files into plain JavaScript, which is the only thing the browser ever runs; the rune disappears in that step. A rune is a keyword with a dollar sign that instructs that compiler, never a function you import. Reactive state is a value Svelte watches, so the moment it changes, every part of the screen showing it redraws on its own. A signal is the cell the compiler makes for one reactive value, read through a get and changed through a set, remembering everywhere it was read; you can find it under the playground's JS Output. A proxy is a wrapper placed around an object while the app runs, giving every property its own signal, deeply, all the way down, and it is built from signals, not a rival to them. The keyword this, inside a method, means the object the method was called on, decided by how it is called and not where it is written. Pass-by-value means a function receives a copy of each argument's value at the moment of the call, never a live link to the variable, which is why a stored result freezes; a getter, a small function of empty parentheses and an arrow that re-reads on each call, is how you hand over a live read instead. Raw state is a single signal with no proxy, so it reacts to replacing the whole value but not to reaching inside. A snapshot is a plain static copy with the proxy peeled away, safe for the outside world. Eager state reflects a change on screen the instant it happens, skipping Svelte's coordination, used sparingly for feedback to a user's action. A module is a standalone file you import from, and the dot-svelte ending lets runes work inside it. And encapsulation is hiding a value away and exposing only chosen functions to read or change it.

For the booklet: we took its fifteen entries and re-threaded them around that one machine. Entry one posed the first problem; the section after it, with no booklet code, built the compiler and the signal underneath that problem, because that foundation is what the rest depends on. Entry two built the proxy and set it firmly apart from the signal. Entries three and ten we taught one after the other, slowly, because a destructured field and a stored function result are the very same frozen copy, and the getter, empty parentheses and an arrow, is the cure for both. Entries four and five married the marked class field, each its own signal, with the slippery keyword this. Entries six through nine walked the variants in order, the reactive built-ins for what the proxy cannot see into, raw state for what is too big to wrap, snapshot for what must leave Svelte, eager for what must land now. Entries eleven and twelve, the shared object and the guarded functions, fell out of one fact from the compiler section, that it works a single file at a time. Entry thirteen fixed the one-file-one-component fence. And entries fourteen and fifteen, the hold-compute-do triage and the React-and-Vue bridge, pointed straight at the next lesson, which builds the derived rune in full, the rune for a value computed from other values, the one we named today and deferred. That is where we go next.
