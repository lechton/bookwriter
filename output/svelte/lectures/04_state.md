## 4.2 The One Question Every Framework Is Trying To Answer

Here is a question I want you to sit with for a few seconds. When the data inside your program changes, how does the screen find out?

That sounds almost too small to be worth asking. But I promise you it is the single hardest problem in all of front end development, and every framework you have ever heard of, React, Vue, Angular, and Svelte, every last one of them exists first and foremost to answer that one question. So let us feel the real weight of it before we let anybody hand us a solution. And let us feel it on a real thing from our running world, not an abstract toy.

Picture the clap count on an article card. Remember the family from lecture three: the clap button is a child box sitting inside the article card, and the count is a little number shown right there beside it. A reader taps the button, and the number goes up by one. A child could describe it. Now let us try to build just that, with nothing but plain JavaScript and the browser, the way people had to do it before any of these frameworks existed. Turn to the first code block in your booklet for this section, the naive counter, and follow along, because this bare counter is the skeleton of the clap count.

You would keep your number in a variable. Let us call it count, holding zero. Then you would reach into the page and grab the specific element where the number is shown, using something like document dot get element by id. Then you would set the text inside that element to the number. So far so good. Now you wire up the button so that when it is clicked, you add one to count. And here is the part that hurts. Adding one to count does absolutely nothing to the screen. The variable changed in memory, but the page has no idea. The card is still showing the old number. So you, the programmer, have to remember to reach back into the page and rewrite the text by hand, every single time the count changes. Look at the booklet: right after count plus plus, there is a second line that shoves the new value back into the page manually. That second line is the tax. The screen does not update itself. You update it, by hand, forever.

One clap count, that is annoying but survivable. Now scale it up, because scale is where every beginner habit gets exposed as a bad idea, and The National Times is built entirely at scale. Think back to the front page from lecture three, and remember what we discovered it really was, underneath the paint: not one mysterious whole, but four or five filtered lists of article objects, each fetched by its own little call. Now count the live numbers on that single page. Every article card in the latest-news block has its own clap count. Every card has a comment count. Up in the masthead there is a badge counting unread notifications. There is a most-read strip whose order shifts as the numbers move. There is a live breaking-news region. That is not one number on the screen. That is fifty numbers on the screen, easily, each living in some variable, and every one of them would have to be manually pushed back into the page by hand whenever it changes. And worse, many of those values depend on each other. A clap lands, and the raw count changes, and the nicely formatted label that says one point two thousand claps has to be recomputed, and maybe the most-read ordering shifts too. You end up writing a tangle of code whose only job is to keep the screen and the data in agreement, and that tangle grows faster than the actual features of your news site. This is the pain. This is the swamp that frameworks were invented to drain.

So now let us look at how the two frameworks you already have some faded memory of, React and Vue, each tried to drain that swamp. Because Svelte is going to drain it a third way, and you will appreciate the third way far more once you have felt the first two.

## 4.3 How React Drains The Swamp, And What It Costs You

Let us talk about React first, since for many of you that was the first framework you ever touched, even if it has gone a bit fuzzy with the years.

React made a bold bet. React said, I am not going to try to figure out which little piece of the screen changed. That is too fiddly. Instead, whenever anything changes, I will simply re run your entire component function from the top, build a fresh description of what the whole screen should look like, compare that fresh description against the previous one, and then quietly patch only the differences into the real page. That re run and compare strategy is what people mean when they say React uses a virtual copy of the page. It is a broad, sweeping approach. Re run everything, then diff.

But this creates an immediate problem for React. If your data is just a normal variable, and you change it with a normal assignment, React has no way to know that anything happened. Nothing told React to re run. So React needs you to announce your changes. And the way you announce them is a hook called useState. And notice, already, the word hook, the word that lecture three told you to drop the moment you cross into Svelte. Hold that thought; it pays off shortly.

Now, because we never drop a reference to another framework without explaining it, let me describe useState in plain words, and let us keep it on our clap count so the comparison is fair. Turn to the React block in your booklet. When you call useState in React, you write const, then an open square bracket, then two names separated by a comma, then a close square bracket, then an equals sign, then the word useState with a starting value in parentheses. For the clap count you might write const, open square bracket, count comma setCount, close square bracket, equals useState, with zero in parentheses. That square bracket pair on the left is pulling two separate things out of useState in one move. The first thing, count, is the current value, the number itself. The second thing, setCount, is a function, and that function is the only approved way to change the value.

So in React, you never, ever write count plus plus. If you try to just mutate the value directly, React will not notice, and your clap count will sit there frozen while the reader taps and taps. Instead you must call setCount and hand it the new value. And calling setCount is also the signal that tells React, hey, something changed, please re run this component and update the screen.

Feel the ceremony in that. You have a value, but you may not touch it directly. You have to go through its appointed setter function every single time. And you have to keep a rule in your head at all times: never mutate, always use the setter. That mental rule, never mutate, always call the setter, is the tax that React charges you in exchange for keeping your screen in sync. Many bugs in React apps come from someone forgetting that rule for a moment and changing a value directly, then staring at a screen that refuses to update.

So React drained the swamp, but it handed you a setter function for every piece of state and a strict rule you must never break. Hold that feeling. Now let us look at Vue.

## 4.4 How Vue Drains The Swamp, And What It Costs You

Vue took a more surgical approach than React. Vue said, I am not going to re run your whole component every time. Instead I am going to watch your individual values very closely, and when one of them changes, I will update only the precise spots on the screen that actually used that value. That precise, targeted style is what people mean when they say Vue has fine grained reactivity. Fine grained, as in, it gets right down to the exact dependency, not the whole component. And here is a pairing worth holding: Vue and Svelte are family in this respect, both fine grained, both updating exactly the spot that changed, where React is the broad re run everything and diff approach. So as we go, think of Svelte as taking Vue's precise idea and removing the ceremony around it.

To pull off that precise watching, Vue needs to wrap your values in something it can watch. And here, again explaining the other framework so we never leave you guessing, Vue gives you a tool called ref. Turn to the Vue block in your booklet. You write const, then a name, then equals, then ref, with a starting value in parentheses. So const count equals ref, with zero in parentheses, for our clap count. That looks clean enough. But here is the catch that everyone who has used Vue remembers with a small wince. Once a value is wrapped in a ref, you can no longer read or write it as a plain number. You have to go through a property called value. To add one to the count, you do not write count plus plus. You write count, then a dot, then the word value, then plus plus. That little dot value, sprinkled all over your script, on every read and every write, is the tax that Vue charges you. Forget it even once, and you are working with the wrapper object instead of the number inside, and things quietly go wrong.

And there is a second wrinkle. The ref tool is really aimed at single values, like one clap count or one headline string. When you have a whole object, say an entire article with its title and section and tags, Vue offers a separate tool called reactive, which wraps the whole object in a watchful layer so that changing any property inside it updates the screen. So now you are juggling two different tools. Ref for the simple values, reactive for the objects, and the dot value rule hanging over the ref side. Two tools, and a tax.

So let us tally up what we have seen. React drains the swamp but makes you call a setter function for every change and never mutate. Vue drains the swamp but makes you write dot value everywhere and remember which of two tools to use. Both of them work. Millions of apps run on both. But in both, the framework has left fingerprints all over your code. There is ceremony. There is an API standing between you and your own data.

Now, at last, we are ready to see what Svelte does. And the headline is going to sound almost suspiciously simple.

## 4.5 The Big Idea: State Is Just A Variable

Here is the whole philosophy of today's lecture in one sentence. In Svelte five, state is just a variable.

Let me say that again, slowly, because it is the heart of everything. In Svelte ... five ... state ... is ... just ... a ... variable. There is no setter function you must call. There is no dot value you must remember. There is no second tool for objects. You change your state the exact same way you would change any plain variable in ordinary JavaScript, and the screen simply follows along.

Open your booklet to the very first Svelte code block for this section, the little counter, marked as the headline block. This bare counter is the skeleton of our clap count, so picture the article card around it as I describe it. Inside the script zone of the component, there is one line. It reads: the word let, then a space, then the name count, then an equals sign, then the state rune, which is the dollar sign followed by the word state, then an open parenthesis, the number zero sitting inside, then a close parenthesis. So in spoken form: let count equals state, with zero in parentheses.

Let me repeat the key tokens with pauses. Let ... count ... equals ... state ... zero. That single line declares a piece of reactive state called count, and starts it at zero. On a real article card, this is the clap count, born at zero claps.

Now look just below, in the markup zone. There is a button. In the bare booklet example its text reads clicks, and then the count. On our article card, picture that same button as the clap button, with the count beside it. And inside the button there are two things worth seeing. First, the way it reacts to a click. There is an onclick attribute, and its value, wrapped in curly braces, is a tiny arrow function whose body is count plus plus. In plain words: when this button is clicked, run count plus plus. And count plus plus, two plus signs stuck together right after the name, is the most ordinary thing in all of JavaScript. It means take count and add one to it. Just bump it up by one. No setter. No dot value. Just count plus plus, exactly like you would write in a plain script with no framework at all. A reader taps the clap button, count plus plus, the applause is recorded.

And second, look at where the number is displayed. Inside the button text there is a single pair of curly braces with the word count inside. In Svelte markup, a pair of curly braces means: take the live value of whatever is inside me and drop it right here into the page. So the button literally shows the current value of count, and because count is reactive state, every time count changes, that spot on the screen quietly updates to match. The clap count climbs on the glass, instantly, with nobody pushing it there by hand.

That is the entire clap count. One line to declare the state. One ordinary plus plus to change it. One pair of curly braces to show it. And it all stays in sync, automatically. Compare that to the painful by-hand version from two sections ago, the one where you had to grab the element and rewrite its text manually after every change. All of that hand-pushing is simply gone.

Now I want you to really feel the contrast, because this is the moment the whole framework justifies itself. In React you would have needed a setter function and the iron rule never to mutate. In Vue you would have needed dot value on every touch. In Svelte, count is just a number. You read it like a number. You change it like a number. You can write count plus plus, or count equals count plus five, or count equals zero to reset it after a recount. All the plain, boring, normal ways of changing a variable simply work, and the screen comes along for the ride.

So the obvious question, the one a sharp programmer asks immediately, is: how? How on earth can a plain variable update the screen? Plain variables do not do that. If this were ordinary JavaScript, count plus plus would change a number in memory and the page would never know, exactly like our painful hand-wired clap count from the start of this lecture. So something has to be different. Let us answer that, because understanding the how is what separates someone who memorizes Svelte from someone who actually understands it.

## 4.6 How A Plain Variable Can Possibly Update The Screen

Cast your mind all the way back to lecture one, to the very first and deepest idea of this whole course: Svelte is a compiler. That single fact is the secret behind everything you just saw.

A library, like React, ships its code to the browser and runs there, alongside your app, watching and reacting at runtime. A compiler does something completely different. A compiler reads your code before your app ever ships, at build time, on your machine, and it rewrites that code into something else. With Svelte, you write friendly, readable code with runes in it, and the compiler transforms it, behind the scenes, into plain efficient JavaScript that does all the wiring for you.

So when you write count plus plus on the clap button, that is not actually the final code that runs in the browser. That is the code you wrote for your own comfort. The compiler reads it, sees that count was declared with the state rune, and quietly rewrites that simple plus plus into the real machinery that both updates the value and notifies every part of the screen that depends on it. You get to write count plus plus, plain and human. The compiler writes the tedious notify everyone code for you, invisibly. This is exactly the bargain lecture three closed on: you describe what you want, plainly, and the compiler, reading ahead of time, builds the machine. You are the architect drawing a clean plan. The compiler is the builder pouring the concrete.

Let me give you a more concrete picture of what the compiler turns your state into, because your booklet shows this near the end of the section and it explains a great deal of Svelte's behavior down the line. Under the hood, a piece of state becomes what the wider programming world calls a signal. Now let me name that word and explain it, the way lecture three taught us to, because a name with no explanation is just a noise. A signal is a small reactive container. Think of it as a little box that holds a value, and that also keeps a private list of everyone who has read from it. When you read the value, the box quietly notes, this part of the screen now depends on me. When you write a new value into the box, the box runs down its list and says to each dependent, wake up, I changed, update yourself. That is a signal. A value, plus a built in list of watchers, plus the duty to notify them. So when a clap lands and count changes, the signal behind count tells exactly the one spot on the card that shows the number, and only that spot, to refresh.

If you used Vue, by the way, that little box should feel familiar, because a Vue ref is essentially a signal too. The difference is purely cosmetic and it is exactly the difference we have been circling. In Vue you reach into that box yourself, by hand, through dot value, every time. In Svelte, the compiler reaches into the box for you. It rewrites your plain reads and your plain writes into the get and set operations on the signal, so you never see the box at all. You write count. The compiler writes get the value from count's signal. You write count plus plus. The compiler writes get the current value, add one, set it back, and notify the watchers.

If you ever want to see this with your own eyes, the booklet mentions a wonderful trick. In the Svelte online playground there is a tab labeled J S Output. Paste your component in, click that tab, and you will see the actual JavaScript the compiler produced, with the signal machinery laid bare. I encourage you to do that at least once. There is nothing like seeing the rewritten code to make the compiler mindset feel real rather than magical.

So, to plant this firmly, and to settle that word hook we flagged earlier: a rune like state is not a normal function you call at runtime, and it is certainly not a React hook. It is an instruction to the compiler. It is a marker that says, hey compiler, this variable is special, please wire it up for reactivity when you rewrite my code. That is why runes are not imported from anywhere. You do not bring them in at the top of your file the way you import a normal tool. They are part of the language that the Svelte compiler understands. They look like a function with a dollar sign in front, but they are really compile time signals to the machine that is rewriting your work. This is precisely what lecture three meant when it said, make the swap once: where React reaches for a hook, Svelte reaches for a rune, and then you let go of the word hook for good.

Let me pause and recap the core, because we have covered the most important ground in the whole lecture and I want it locked in. The problem: keeping the screen in sync with the data. React's answer: re run everything and force you through setter functions. Vue's answer: watch values closely but force you through dot value. Svelte's answer: let you write a completely plain variable, and let the compiler secretly rewrite it into the notify everyone machinery. State is just a variable, because the compiler does the dirty work you cannot see. Hold that, and let us go deeper, into what happens when your state is not a simple number like a clap count, but a whole object or a list.

## 4.7 Deep Reactivity: When Your State Is An Object Or A List

So far our state has been a single number, the clap count. But real apps are full of richer things. Lists of items. Objects with many properties. And The National Times is no exception. Think back to lecture three, to all the lists we found hiding under the front page, and to the rich article object with its title and section and tags. What happens when you wrap one of those in the state rune?

Let me ground this in a concrete newsroom thing so the code has a home. Picture a draft article being prepared for publication, and on that draft, a production checklist: the list of tasks that must be ticked off before the story can go live. Add the photo. Write the headline. Get the legal check. Each item on that checklist is a little object with two labels, a done flag that is true or false, and a text holding the task. So the checklist is a list of objects, exactly the shape lecture three taught you to see everywhere. That is what we are about to make reactive.

Here is where Svelte does something genuinely elegant. When you pass the state rune an array or a plain object, you do not just get a watched box around the whole thing. You get what is called a deeply reactive state proxy. Let me unpack both of those words, deeply and proxy, because together they describe a very pleasant behavior.

First, proxy. A proxy is a real feature built into JavaScript itself, not something Svelte invented. A proxy is an object that wraps another object and sits in front of it like a gatekeeper, able to run a little bit of its own code every single time you read a property or write a property. So when Svelte wraps your checklist in a proxy, it gains the power to notice every read and every write to that list, and to do its reactive bookkeeping at exactly those moments. If you used Vue's reactive tool, this is the very same idea, because Vue's reactive is also built on JavaScript proxies. So a Vue veteran already has the right instinct here.

Now, deeply. This is the lovely part. Svelte does not just wrap the outer list. It reaches all the way down. If your list contains objects, each of those objects gets wrapped in a proxy too. If one of those objects contains another list, that list gets wrapped. Svelte keeps wrapping recursively, layer after layer, until it hits something that is not a plain object and not a plain array, at which point it stops. So your entire nested structure, top to bottom, becomes reactive. That is what deeply reactive means: the reactivity goes all the way down, not just one level.

Turn to the to-do list code block in your booklet, and read it as our production checklist. There is a variable, declared with the state rune, and its starting value is a list containing one item. That item is an object with two properties: a property called done, set to false, and a property called text, holding a task, in the booklet the placeholder words add more todos. So in spoken form: the list equals state, and inside the parentheses, a list holding one item, and that item is an object with done equals false and text holding the task. One unfinished task on the checklist, to begin.

Now watch what deep reactivity buys you. Look at the next snippet, the one that flips the done flag, the moment an editor ticks a task as finished. It reads: the list, open square bracket, zero, close square bracket, then a dot, then done, then equals, then an exclamation mark in front of the same list, square bracket zero, dot done again. Let me translate. The list, square bracket zero, square bracket, means reach into the list and grab the very first item, the one at position zero, because lists in JavaScript start counting at zero. Then dot done reaches inside that item to its done property. The exclamation mark means the logical opposite, the flip, true becomes false and false becomes true. So the whole line reads: set the first task's done property to the opposite of what it currently is. In plain English: tick the task, or un-tick it.

And here is the magic of deep reactivity. Because every layer is a proxy, when you reach in and change that one nested property, that one specific done flag on that one specific task, Svelte knows precisely what changed, and it updates only the parts of the screen that depend on that exact property. Not the whole checklist. Not even the whole item. Just the little checkbox tied to that one flag. That is granular updating, and you got it for free, just by reaching in and assigning, the most natural way you could imagine.

It gets better. Look at the snippet where we add a new item, where the editor adds a task to the checklist. It reads: the list, then a dot, then push, then in parentheses a new object with done equals false and a text, in the booklet the words eat lunch, in our newsroom say, get the legal check. In plain JavaScript, dot push is the standard way to add an item to the end of a list. And in most reactive systems you would expect push to be a problem, because push mutates the list in place rather than creating a new one, and many systems cannot see a mutation like that. But because our list is wrapped in a proxy, the proxy notices the push, and the screen updates. Even better, the brand new task you just pushed in gets wrapped in its own proxy automatically, so it too is fully reactive from the moment it joins the list. You did not have to do anything special. You used plain old push, the way you would in any script, and reactivity simply held.

Let me hammer the contrast home one more time, because this is exactly where the never mutate, always use the setter rule of React makes Svelte look like a holiday. In React, calling push on a piece of state is a classic mistake that leaves your screen frozen, because you mutated instead of replacing. In Svelte, push just works, because the proxy is watching. You write the plainest, most obvious JavaScript, and it does the right thing.

Now, one careful note that the booklet flags, and that I want you to tuck away. When you change a property on one of these proxies, the original underlying object is not itself mutated. The proxy intercepts your write and records it in its own reactive layer. For almost everything you do day to day, you will never notice this. It only becomes relevant in rare advanced cases, for instance if you have your own custom proxy handling that you want to combine with Svelte's. In that situation the rule is to apply your own proxy first and then wrap the result in state. File that away as a footnote and move on. The everyday lesson is simply: read and write your nested state the normal way, and it all stays reactive.

## 4.8 The Trap That Catches Everyone: Destructuring

Now I have to warn you about a trap. It is the single most common way that people, especially people coming from React or Vue, accidentally break their reactivity. And once I name it, you will see why it happens, and you will never fall into it.

The trap is called destructuring. Let me first remind you what destructuring is, in plain JavaScript, with no Svelte involved. Destructuring is a shorthand for pulling values out of an object or a list into their own little variables. Instead of writing several lines to grab each property, you write one line with curly braces that names the properties you want, and JavaScript yanks them out for you. It is tidy and people love it.

Look at the destructuring snippet in your booklet, still on our checklist. It reads: let, then a pair of curly braces containing the names done and text, then equals, then the list, square bracket zero, square bracket. In plain words: pull the done property and the text property out of the first task, and put them into two new standalone variables, one called done and one called text. Right below, there is a line that toggles the original task, the list at zero, dot done, becoming its opposite, just like before.

Here is the painful part. After that toggle runs, the original task's done property has indeed flipped. But your little standalone done variable, the one you destructured out, does not change. It is still showing the old value. Your reactivity is broken for that variable. The checkbox on the screen that reads from your loose copy will not move, even though the real task did.

Why? Here is the clean explanation, and it is not really a Svelte quirk at all, it is just how JavaScript works. The moment you destructure, JavaScript reads the value out right then and there and copies it into your new variable. That new variable, done, is now just a frozen snapshot of whatever the property happened to be at the instant you destructured. It has no living connection back to the proxy. It is a plain copy. So when the real property changes later, your copy has no idea, because it was never wired to anything. It was a one time read.

And this, by the way, is the very same trap that bites people in Vue, where destructuring a reactive object also severs the connection to the proxy, and it is the same family of issue you hit if you pull a value out of a signal in other modern frameworks. Fine grained reactivity is precise and wonderful, but the price of that precision is that you have to keep your values connected to the system. Tear off a plain copy by destructuring, and you have cut the wire.

So the rule of thumb is simple. When you want something to stay reactive, keep reaching into the proxy each time. Keep saying the list at zero, dot done, rather than pulling done out into its own loose variable up front. Reach in fresh, every time, and the connection holds. The booklet line on this is worth a second read, because seeing the broken example in print really cements it. Let me restate the lesson once more, since it is a true gotcha: destructuring a piece of reactive state gives you a dead snapshot, not a live link. If you need the live link, do not destructure.

## 4.9 State Inside Classes

Let us turn now to a question that ambitious learners ask quickly. What if I want to use a class to model my data? Classes are a great way to bundle data together with the methods that operate on it. Can my class hold reactive state?

This is not an abstract question for us, because lecture three already hinted at exactly where we would want one. Remember the talk of reusable reactive logic, the small classes living in a reactive module, a counter class with a count field and an increment method. And think how naturally an article wants to be a class. Picture a Draft class for the newsroom: a draft article that carries its own data, its done-or-not flag, its text, its title, and also the methods that act on it, a method to reset it, a method to publish it. The booklet shows this idea in its simplest possible seed, a tiny Todo class, so picture that Todo as the seed of our Draft. Can such a class hold reactive state?

The answer is yes, but the rules shift a little, and there is a good reason for the shift. Remember, Svelte makes objects and arrays reactive by wrapping them in a proxy. But class instances are deliberately not wrapped in a proxy. Why hold back? Because a class is a much more particular thing than a plain object. It has methods on its prototype, it might have private fields, it carries its own internal expectations about how it works. Slapping a gatekeeper proxy around the whole instance could quietly break those mechanics in surprising ways. So Svelte draws a sensible line. Plain objects and arrays get wrapped automatically. For classes, you opt in, field by field, exactly where you want reactivity.

The way you opt in is to use the state rune directly on the class fields themselves. Open your booklet to the Todo class, our seed of a Draft. Let me walk you through it in spoken form. There is a class named Todo, capital T. Inside it, the first line declares a field: the word done, then equals, then the state rune with false in parentheses. So done equals state false. That is a reactive field, set up right on the class, starting at false. On a real Draft, this might be a published flag, or a ready-for-legal flag.

Then there is the constructor. Now let me make sure that word lands, since we lean on classes throughout programming. The constructor is the special setup function that runs automatically the instant a new instance of the class is created, the moment a journalist starts a new draft. Its whole job is to take the starting values for this particular instance and stamp them onto it. In this Todo class, the constructor receives a text value, and inside the constructor body there is a line that reads: this, then a dot, then text, then equals, then the state rune with text in parentheses. Let me unpack that. The word this, then a dot, means on this particular instance. So this dot text means the text property belonging to this very draft. And we are setting it equal to state, with the incoming text wrapped inside. So we are declaring, right here as the very first assignment to this property inside the constructor, that text is reactive state, starting from whatever text was handed in.

So you have two valid places to put the state rune in a class. Directly on a field, like done equals state false. Or as the first assignment to a property inside the constructor, like this dot text equals state of the incoming value. Either way, that property is now reactive, and reading or writing it from anywhere will keep your screen in sync.

There is also a small piece of behind the scenes behavior worth knowing, which the booklet notes. When the compiler sets up these reactive class fields, it quietly converts them into a pair of getter and setter methods on the class, backed by a hidden private field. The practical consequence is that these properties are not enumerable, meaning they will not show up if you try to loop over the plain keys of the object in the usual way. You will rarely bump into this, but if one day you loop over a draft's keys and your reactive fields seem to be missing, now you know why. They are living as getters and setters, not as plain visible properties.

## 4.10 The Other Class Trap: The Word This

Now, classes bring a second trap, and again it is not Svelte's fault, it is pure JavaScript. But it bites people constantly, so let us defuse it. And it ties straight back to lecture three, because it is really about events, about a button calling a function.

Suppose your Draft class, our Todo, has a method called reset, whose job is to clear the text and set done back to false, a discard-this-draft button in the newsroom. And suppose in your markup you have that reset button, and you want clicking it to call the method. Remember the family: the button is a child box, and the thing it needs to do lives on the draft. The tempting thing to write is an onclick attribute whose value is simply todo dot reset. Just point the click straight at the method. Look at the first button snippet in the booklet, the one that does exactly this. It looks perfectly reasonable. And it does not work.

Here is why, and you have to understand the word this to understand it. In JavaScript, inside a method, the word this refers to whatever object the method was called on. But here is the cruel detail: what this points to is decided at the moment the function is called, based on how it was called, not on where it was written. When you hand todo dot reset to an onclick attribute, you are handing over the bare function, detached from the draft. Later, when the button is clicked and the browser calls that function, the word this inside it no longer points at your draft. It points at the button element instead. So the method runs, tries to clear properties on the button rather than on the draft, and your draft never resets. The reactivity is fine. The problem is that this got hijacked.

There are two clean fixes, and the booklet shows both. The first fix is to wrap the call in an inline arrow function. Instead of pointing onclick straight at todo dot reset, you point it at a tiny arrow function whose body is todo dot reset, with parentheses, called right there. Look at the second button snippet to see this. Because you are now explicitly writing todo dot reset and calling it through the draft, the word this correctly points at the draft. The arrow function preserves the connection. And notice, this is exactly the shape lecture three taught for events: the markup holds a tiny function, and the click calls it through the right object.

The second fix lives in the class itself. Instead of writing reset as a normal method, you write it as a field that holds an arrow function. Look at the version of the Todo class where reset is declared with an equals sign and an arrow function. Arrow functions have a special property: they do not get their own this. They permanently borrow the this from the place where they were created, which in this case is the instance. So no matter how the function is later called, even detached and handed to a button, its this stays locked onto the draft. This is a popular pattern precisely because it makes the method safe to pass around without worrying about who calls it, which matters a great deal when, as lecture three showed, parents are constantly handing functions down to child buttons.

So, to summarize the two class traps together, because they often travel as a pair. Trap one: class instances are not auto wrapped, so you must put the state rune on the fields you want reactive. Trap two: passing a method by name can sever its this, so either call it through an inline arrow function in the markup, or define it as an arrow function field on the class. Neither trap is about reactivity itself. Both are about the deeper mechanics of JavaScript classes that the state rune happens to sit inside.

## 4.11 When You Need Reactive Versions Of Built In Tools

Here is a short but useful corner, and it connects directly to the article object we dissected in lecture three. Remember all the labels on an article: the id, the slug, the tags, the published date, the link. Some of those naturally want richer containers than a plain number or string. JavaScript ships with several handy built in containers beyond plain objects and arrays. There is a Set, which holds a collection of unique values, perfect for a set of tags where no tag should appear twice. There is a Map, which holds key and value pairs, perfect for looking something up by an article id. There is a Date, which holds a moment in time, exactly what the published label is. And there is a U R L, which holds a web address you can pick apart, exactly the article link built from the slug. These are not plain objects, and so, just like class instances, they are not automatically made reactive by the state rune.

So what do you do when you want, say, a reactive Set of tags that updates your screen the instant the journalist adds or removes a tag? Svelte hands you the answer in a built in package called svelte slash reactivity. From there you can import reactive versions of all four: a reactive Set, a reactive Map, a reactive Date, and a reactive U R L. They behave just like the originals you already know, with all the same methods, but they are wired into Svelte's reactivity so that changing them updates the screen. The lesson to carry away is simple: if you reach for one of these built in containers and find your screen is not reacting, do not fight it. Just import the reactive version from svelte slash reactivity, and carry on as normal. The booklet lists the import line for when you need it, and this little family of reactive built-ins gets its own proper treatment later in the course.

## 4.12 Opting Out On Purpose: The Raw Variant

Up to now we have been celebrating deep reactivity, the way Svelte reaches all the way down into your nested objects and wraps every layer in a proxy. But sometimes you do not want that. Sometimes deep reactivity is more than you need, and wrapping a huge structure in proxies, layer after layer, costs a little performance you would rather not pay. Think of a genuinely big object on The National Times: a fully loaded article fetched from your FastAPI server, body and metadata and a long thread of comments, that you only ever intend to swap out wholesale when the reader navigates to a different story, never to poke at piece by piece. For cases like that, Svelte gives you a way to opt out. It is the raw variant, written as the state rune, then a dot, then the word raw. So in spoken form, state dot raw.

When you declare a piece of state with state dot raw, you are telling Svelte, do not wrap this deeply, do not make its insides reactive. And that comes with one firm rule that you must absorb. Raw state cannot be mutated. It can only be reassigned wholesale. Let me make that distinction crisp, because mutate versus reassign is the entire idea here. To mutate is to reach inside and change a part, like setting one property on an object. To reassign is to throw away the old value entirely and point the variable at a brand new value. With state dot raw, reaching in to change a part does nothing. You have to replace the whole thing.

Open your booklet to the raw example. The docs make the point with a person, and they chose the name well: the person is Heraclitus, the philosopher who said you never step in the same river twice, that everything flows and nothing stays. It is a fitting mascot for raw state, because raw state is all about replacing the whole river rather than stirring the water you are standing in. There is a variable called person, declared with state dot raw, holding an object with a name and an age. The starting name is Heraclitus, and the starting age is forty nine. Now look at the two attempts to change it. The first attempt reaches in and tries to bump the age, writing person dot age plus equals one. The comment beside it tells you the truth: this will have no effect. Because the state is raw, reaching in to mutate a property is ignored. The screen does not update, and as far as Svelte is concerned, nothing happened. The second attempt does it the right way. It writes person equals a whole new object, with the name Heraclitus and the age now fifty. That is a reassignment. We threw away the old person and pointed the variable at a fresh one. And that works, because reassigning the whole variable is exactly what raw state listens for. A new river, not a stirred one.

So why would you ever choose this more restrictive tool? Performance, and honesty about your intentions. If you have a very large array or a very large object that you know you are never going to poke at piece by piece, that you will only ever swap out wholesale, like that fully loaded article, then wrapping the whole thing in deep proxies is wasted effort. The raw variant skips all that machinery and just watches for a full replacement. It is a deliberate choice that says, I will only ever replace this, never tinker with its insides, so do not bother making the insides reactive. And one neat detail the booklet mentions: raw state can still contain reactive state. You could have a raw array whose individual items are themselves ordinary reactive objects. The outer shell is raw and only listens for replacement, while the items inside keep their own reactivity. That gives you fine control over exactly where you pay the cost. And it works on class fields too, for the same reasons.

## 4.13 Getting A Plain Object Back Out: The Snapshot Variant

Here is a practical situation you will hit sooner than you think, and lecture three set it up for us. Your state is a reactive proxy. That is great inside Svelte. But now you want to hand that data to something outside Svelte. Maybe an external library, a charting library for the editors' analytics page, the kind of third-party tool lecture three said you wrap in an action. Maybe a browser function. Maybe you just want to log an article to the console and actually see the plain data rather than a confusing wrapper. The trouble is, those outside tools were not built to understand Svelte's proxy. If you hand them the proxy, they may get confused, or print something cryptic, or choke entirely.

For this, Svelte gives you the snapshot variant, written as the state rune, then a dot, then the word snapshot. So, state dot snapshot. You wrap your reactive value in a call to state dot snapshot, and what comes back is a plain, ordinary, static copy of the data, with all the reactive proxy machinery stripped away. A frozen photograph of the current state, in plain object form, safe to hand to anyone.

Look at the snapshot example in your booklet. There is a piece of state called counter, holding an object with a count inside, the same little shape we have used all along. And there is a function that logs it. Notice it does not log counter directly. It logs state dot snapshot of counter. The comment points out the payoff: this prints the plain object, the count and its value, rather than a baffling proxy wrapper. The booklet also names a perfect real use case, a built in browser function called structured clone, which makes a deep copy of data but will not accept a proxy. So if you ever need a deep copy of an article object to hand off elsewhere, snapshot first, then clone. Snapshot first, then hand the clean copy along, and everyone is happy.

There is one small advanced footnote on snapshot. If your value happens to have a method called to J S O N, the standard hook that controls how an object turns itself into J S O N, then the snapshot will use the result of that method rather than the raw object. You will not need that detail often, but it is there for the day you do. The everyday takeaway is plain: when an outside tool needs your state and gets confused by the proxy, wrap it in state dot snapshot to get a clean, plain copy it can understand.

## 4.14 A Brief Word On The Eager Variant

There is one more variant, and I will keep it brief, because it touches on timing, a feature we cover properly later, and it is something you will reach for only rarely. It is written as the state rune, then dot, then the word eager. So, state dot eager.

Here is the situation it exists for, in plain terms, and lecture three gave us the perfect home for it. Normally Svelte is smart about timing its screen updates, batching them up and coordinating them so the reader gets a smooth experience. But in certain cases, particularly when your screen is waiting on something slow, like a value that depends on an operation that has not finished yet, remember the asynchronous world from lecture three, where a fetch travels across the network and back, a change in your state might not show up on screen the very instant it happens. Usually that is fine and even desirable. But occasionally you want instant visual feedback the moment the reader acts. The classic example the booklet gives is a navigation bar, and we have one ready made: the section navigation along the top of The National Times, World, Politics, Sports, Culture. The reader clicks Sports, and you want the Sports link to look active right away, even while the Sports page is still loading, so the person gets that immediate sense of, yes, I clicked, it heard me.

Look at the eager example in your booklet, the navigation bar. Each link checks the current path and lights itself up if it matches, and it does that check through state dot eager. For that narrow purpose, you wrap a value in state dot eager, and it will be reflected on screen as soon as it changes, without waiting for the usual coordination. And the booklet gives you a wise instruction, which I will pass on directly: use this sparingly, and only to give feedback in response to a user action. In general, letting Svelte coordinate the timing of updates gives a better experience. So think of state dot eager as a small, specialized tool for instant feedback, not something you sprinkle around. We will understand the timing it relates to much better once we have covered effects in lecture six and the runtime in more depth. For now, just know it exists and what it is for.

## 4.15 Passing State Into Functions: The Pass By Value Catch

Now we arrive at a subtler topic, one that reveals something deep about how JavaScript itself works, and it explains a behavior that surprises people. What happens when you pass your state into a function? Let us keep it concrete: what happens when you hand your clap count to some helper function, one of those pure utility functions lecture three filed away in the utilities module, say a function that formats a raw count into the label one point two thousand?

To understand this, we need one fact about JavaScript, and the booklet states it plainly: JavaScript is a pass by value language. Let me explain what that phrase means, because it is the whole key. When you call a function and hand it some arguments, the function receives the current values of those arguments, copied in at that moment. It does not receive a living link back to your original variables. It gets a snapshot of their values, frozen at the instant of the call.

Look at the simple add example in your booklet. There is a plain function called add that takes two numbers and returns their sum. Outside it, there is a variable a holding one, and a variable b holding two. We call add with a and b, store the result in a variable called total, and log it. It prints three, exactly as you would expect, one plus two. But now look at what follows. We change a to three, and we change b to four. And then we log total again. And total still prints three. Not seven. Three.

Why? Because of pass by value. When we called add, the function received the values one and two, the values a and b held at that moment. It added them, got three, and returned three. That three got stored in total and is now just a frozen number. Later, changing a and b changes those variables, but it does not reach back in time to redo the addition. total was computed once, from the values as they were, and it stays put. The function never had a connection to the live variables. It only ever saw copies.

And here is the crucial point for us: state in Svelte is no different. The booklet shows it directly, with a and b now declared using the state rune instead of plain let, and the behavior is exactly the same. When you reference a piece of state, you are accessing its current value, the value right now. Hand that value to a plain function, and the function gets a copy of the value as it stood at that instant, with no live link. So if you were hoping that passing the clap count into a function would let that function track the latest count as readers keep clapping, plain value passing will not give you that. It captured the number once and froze it.

So how do you give a function access to the current, live value, the one that keeps changing? The booklet shows the technique, and it is a clever one rooted in the same logic. Instead of passing the value, you pass a function that returns the value. Look at the second add example. Here, add does not take two numbers. It takes two little functions, often called getters, each of which, when called, hands back the latest value. And add itself returns a function, which, when you call it, runs those getters fresh and adds up whatever they currently return. Then, when you change a and b and call the returned function again, it re runs the getters, sees the new values, and gives you seven.

Do you see the trick? A plain value is frozen at the moment you pass it. But a function is a live wire. Every time you call the function, it goes and fetches the value as it is right then. So by passing functions instead of values, you keep a living connection to the current state, even across a function boundary. The booklet broadens this idea too, in its fourth example: functions here means more than just obvious functions. It includes getter properties on objects, and the get and set properties that proxies expose. Anything that runs a fresh read each time you ask, rather than handing over a frozen copy. And the booklet adds a gentle nudge that lands perfectly given where we have been: if you find yourself writing a lot of this getter passing by hand, that is often a sign you would be happier using a class, where the live properties come more naturally. So keep our Draft class in your back pocket as the cleaner option when this pattern starts to pile up. This is the same instinct lecture three gave you: reusable, stateful things often want to be a small class in a reactive module.

## 4.16 Sharing State Across Files: The Export Catch

We come to our last big topic, and it is the one that completes a thread we opened in the keystone lecture. Cast your mind back to lecture three, to the third direction boxes talk: sideways. We said some things are needed everywhere, by boxes scattered all over the tree, with no tidy parent-child line connecting them, and the prime example was the logged-in reader, needed by the masthead greeting up top and by the comment form buried deep in the article page. And we said the cleanest way to hold something truly app-wide is to lift it clean out of the component tree and put it in a shared module, a file we said might be called session dot svelte dot t s. Today we learn exactly how that file works, and the one rule you must respect to build it.

First, the good news. You are not limited to declaring state inside dot svelte components. You can declare reactive state in a separate module, as long as its file name carries the special marker, ending in dot svelte dot j s, or, since you are deploying in TypeScript, the equivalent ending in dot svelte dot t s. That special naming is the flag that tells the compiler, this is not an ordinary script, this one contains runes, please process it for reactivity. So you can put the logged-in reader in session dot svelte dot t s and pull it into many components, exactly as lecture three promised. Wonderful.

But now the catch, and it is a catch that traces straight back to the compiler mindset we keep returning to. There is a thing you cannot do, and the booklet shows it clearly. You cannot declare a piece of state with the state rune, export it directly, and then also reassign it inside that same module with a plain assignment. Look at the first module example, the one with a count that is exported and then changed inside an increment function by writing count plus equals one. Picture that count as a number we want to share, and the pattern is not allowed. We have to understand why, because the why teaches you something true about Svelte.

Recall what the compiler does to your state. It rewrites every plain read and every plain write into get and set operations on the underlying signal. Inside one file, that is fine, because the compiler can see every reference and rewrite them all consistently. The booklet even shows you the rewritten version, the J S Output, where reading count becomes a get call and writing count becomes a set call. Here is the problem. The compiler works on only one file at a time. It cannot see across into other files. So when another file imports your count, the compiler over in that other file has no idea that count is secretly a signal that needs to be read through a get call. To that other file, count just looks like some imported thing, and it would be handled as a plain value, not as a live signal. The wiring breaks at the border between files. The booklet drives this home with a small demonstration: import a reassignable state value into another file, check its type, and you find it is not the number you expected at all, but an object, the raw signal wrapper, leaking through because the importing file never got the rewriting treatment.

So Svelte gives you two clean ways around this, and both are easy to remember once you see the principle behind them. The principle is: the trouble only happens when you reassign the variable itself. Reassigning is what triggers the set rewriting that cannot cross file boundaries. So both solutions simply avoid reassigning the exported variable.

The first solution: export an object, and change a property on it rather than reassigning the variable. Look at the example with a counter object. You export a constant called counter, declared with the state rune, holding an object with a count property. To increase the value, you do not reassign counter. You reach in and write counter dot count plus equals one. Because you are updating a property inside the object, not reassigning the variable counter itself, the compiler never has to rewrite a reassignment, and the whole thing travels across files perfectly. This is exactly how your session module wants to be built: export a session object, and when the reader logs in, set session dot reader to the new person, a property change, never a reassignment of session itself. And it works hand in hand with the deep reactivity we learned earlier: the object is a reactive proxy, so changing its property updates everyone who depends on it, the masthead greeting and the deep comment form alike, everywhere across the tree.

The second solution: do not export the state directly at all. Instead, keep the state private inside the module, and export functions that touch it. Look at the final example. There is a count declared with the state rune, but it is not exported. What is exported is a function called get count, which returns the current value, and a function called increment, which adds one to it. Because the state itself never leaves the module, and other files only ever talk to it through these exported functions, all the reading and writing happens inside the one file where the compiler can see and rewrite everything correctly. The functions are the safe doorway through the wall. For our session, that would be a get reader function and a log in function and a log out function, the state sealed inside, the doors the only way in.

Let me restate the whole lesson plainly, because it is a real source of confusion for newcomers. Inside a single file, do whatever you like with your state. But if you want to share state across files, the sideways sharing of lecture three, do not export a state value that you also reassign. Either export an object and mutate its properties, or keep the state private and expose functions that read and change it. Both work because both avoid the one thing that breaks across file boundaries, which is reassigning the exported variable. And underneath it all is the same truth we started with: Svelte is a compiler that rewrites your code one file at a time, and your sharing patterns simply have to respect that boundary. That is the real machinery behind the session module we sketched in the keystone hour.
