## 2.2 The Pain Of The Scattered Component, And The Idea Of One File

Here is the problem. Think about what a single piece of a user interface actually is. Take something simple, a button that counts how many times you have clicked it. What does that little thing need in order to exist? It needs three things. It needs some logic, the JavaScript that holds the count and adds one when you click. It needs some structure, the actual button element with its text. And it needs some appearance, the styling that makes it look like your button and not a bare grey default. Logic, structure, appearance. Those three are not three separate concerns that happen to be near each other. They are one thing. They are the button. The button is not complete without all three.

And yet, for most of the history of web development, those three pieces lived in three different places. Your logic sat in a JavaScript file. Your structure sat in an HTML file, or got generated somewhere else entirely. And your appearance sat in a separate CSS file, way off in another folder. So this single conceptual thing, your button, was smeared across three files that did not know about each other. To make them cooperate, you had to invent bridges. You gave the button a class name in your HTML, and then you wrote that exact same class name again over in your CSS file, hoping you spelled it the same, hoping nobody else in the entire app used that name for something else and quietly broke your button from a distance. The component was a concept with no home. It was an idea you had to reassemble in your head every time, by jumping between three files.

Now feel that at scale, because scale is where every small annoyance reveals itself as a real problem. One button across three files is survivable. But a real application is not one button. It is hundreds of components. So now you have hundreds of pieces of logic in one place, hundreds of pieces of markup in another, and a single giant tangle of styling in a third, where every class name is fighting every other class name for a globally shared namespace, and changing one rule over here silently restyles something three screens away. Developers built whole disciplines just to survive this. Naming systems with strict rules so class names would not collide. Tooling that rewrote your class names to be unique for you. It was a lot of machinery, and all of it existed to paper over one underlying wound: the pieces of a component did not live together.

So here is the idea that fixes it, and it is almost aggressively simple. What if one component lived in exactly one file? What if the logic, the structure, and the appearance of your button all sat together, in a single file, that you could open and understand and change as one unit, with no bridges to maintain and no class names to keep in sync across a folder you forgot existed? That single file is the dot svelte file. It is the whole reason this lecture exists, and it is the daily reality of working in Svelte. One component. One file. Everything it needs, right there, together.

Now, because we never name another framework without explaining it, let me place this idea in its history, because Svelte did not invent it alone. The framework that really popularized putting a component's pieces in one file was Vue, with what it calls the Single File Component, a file ending in dot vue that holds a template section, a script section, and a style section all together. If that rings a faint bell from your Vue days, good, because the dot svelte file is a close cousin of that idea. React, fascinatingly, made the opposite bet. React said, we will also colocate the pieces, but we will do it by pulling the markup down into the JavaScript, writing your structure right inside your logic using a syntax called J S X, which lets you write something that looks like HTML directly in your JavaScript code. So React puts everything in a JavaScript file. Vue and Svelte put everything in a dedicated component file with distinct zones. Same goal in all three, keep the pieces of a component together, but reached from different directions. Svelte's particular answer is the one we are about to take apart: a single file with three clearly marked zones.

## 2.3 The Three Zones: A Guided Tour Of The Skeleton

Turn in your booklet to the skeleton at the top of the dot svelte files page. It is a little component called MyComponent, and it shows you, in outline, every zone a dot svelte file can contain. I want you to look at the overall shape of it while I describe the zones, because this shape is going to be burned into your memory by the end of the course. You will see thousands of these.

There are, at most, three kinds of zone in a dot svelte file. At the top, there is a script zone, which is where your JavaScript lives, the logic of the component. In the middle, there is the markup, which is where your HTML lives, the structure of the component. And at the bottom, there is a style zone, wrapped in a style tag, where your C S S lives, the appearance of the component. Logic on top, structure in the middle, looks on the bottom. Script, markup, style. That is the canonical order, and it is the order you will see almost everywhere.

Now here is the first liberating fact, and the booklet states it plainly: all three sections are optional. Every single one. You can have a dot svelte file that is nothing but markup, a little chunk of pure HTML with no logic and no styling, and that is a perfectly valid, complete Svelte component. You can have one with just a script and some markup but no styles. You can have one with all three. The file does not demand any particular zone. It only asks that whatever zones you do include follow the shape. This matters because it means the simplest possible Svelte component is just... HTML. Which leads me to the second liberating fact.

A dot svelte file is written, in the documentation's own words, using a superset of HTML. Let me make sure that word superset really lands, because it is doing a lot of quiet work. A superset means: everything that HTML already is, plus more. It means that any valid, ordinary HTML you already know is also valid Svelte. You can take a plain paragraph, a plain heading, a plain image tag, paste it straight into a dot svelte file, and it simply works, untouched, because it was already legal. Svelte does not ask you to relearn HTML. It takes the HTML you know and adds powers on top of it, the curly braces for expressions, the special blocks for loops and conditions, the directives, all the things we will study in the template lectures. But the foundation is plain HTML.

This is, again, a real point of difference from React, and worth feeling. That J S X syntax I mentioned, the HTML-like thing you write inside React's JavaScript, looks like HTML but is not HTML. It is JavaScript wearing an HTML costume, and the costume has tells. In J S X you cannot write the plain word class for a C S S class, because class is a reserved word in JavaScript, so you have to write className instead, a thing that exists in no HTML document on earth. You have to close tags that HTML lets you leave open. You have to return one single root element. These are small frictions, but they are constant, and they come from J S X being JavaScript first. Svelte goes the other way. It is HTML first. The plain word class is just the word class. Your existing HTML instincts transfer directly. That HTML-first nature is one of the quietly pleasant things about living in Svelte, and it flows from this one design choice: the markup zone is a superset of HTML, not a reimagining of it.

So that is the map: three optional zones, script and markup and style, built on a foundation of real HTML. Now let us walk into each zone and see what makes it tick, starting with the one where the real action is, the script.

## 2.4 The Instance Script: A Setup That Runs Once For Every Copy

Look at the plain script zone in your booklet, the one labeled, in the comments, as instance level logic. This is where the JavaScript brain of your component lives. And there is one sentence in the documentation about it that looks innocent but contains a genuinely important idea, so we are going to slow all the way down on it. The sentence says: a script block contains JavaScript that runs when a component instance is created, and variables declared at the top level can be referenced in the component's markup.

Let me pull that apart, because there are two deep ideas hiding in it. The first idea is the relationship between the script and the markup. Any variable you declare at the top level of that script, a count, a name, a list, anything, automatically becomes visible to the markup below it. You do not pass it anywhere. You do not wire it up. You declare a variable named count in the script, and then down in the markup you can just refer to count, and Svelte knits them together. The script and the markup share a world. That is the deep cooperation that the single file buys you: the logic and the structure are not strangers passing data through a slot, they are two halves of one room, and a name spoken in one half is heard in the other.

But the second idea is the one I really want to carve into you, because it is one of the most important conceptual differences between Svelte and React, and getting it clear now will save you from a whole category of confusion later. Read the phrase again: the script runs when a component instance is created. When the instance is created. Once. When the component is born, its script runs, top to bottom, one time, setting up that instance's variables and logic. And then it is done. It does not run again.

Now contrast that with React, carefully, because this is where memory plays tricks. In React, a component is a function, and that function runs again, from the top, every single time anything changes. Click a button, the value updates, and React calls your entire component function over from the beginning to produce the new picture. Over and over, on every update, the whole function body re executes. That is simply how React works, and it has consequences that React developers spend real energy managing: because the function re runs constantly, any value you compute inside it is recomputed constantly, and React has to give you special tools to hold onto things between those re runs so they do not get rebuilt every time.

Svelte does not do this, and now you know exactly why, because you learned it in lecture one. Svelte is a compiler. It does not need to re run your whole script to find out what changed, because it already worked out, at build time, precisely which little piece of the screen depends on which piece of state, and it wired up a surgical update for exactly that piece. So your instance script runs once, sets up your reactive values, and then those values quietly update their specific spots on the screen for the rest of the component's life, without the script ever running again. Let me say that contrast as plainly as I can, because it is a keeper. In React, your component code runs again on every change. In Svelte, your component script runs once, when the instance is born, and the compiler handles every change after that surgically. One of these re runs everything and optimizes the re running. The other runs once and never needs to re run at all.

And if a flicker of Vue memory is stirring here, your instinct is right, so let me honor it. Modern Vue, with what it calls its script setup block, also runs a component's setup logic once per instance, much closer to Svelte's model than to React's. So on this particular axis, Svelte and modern Vue are cousins, and React is the odd one out. But Svelte reaches that once and done behavior through its compiler, which is the thread running through everything in this course. The script runs once because the compiler already did the work of figuring out what needs to change later.

So, the instance script in one breath: it is the JavaScript brain of one copy of your component, it runs a single time when that copy is created, and every top level variable in it is automatically visible to the markup. Hold that, because the next zone is a deliberate contrast to it.

## 2.5 The Module Script: One Brain Shared By Every Copy

Now look in your booklet at the other kind of script, the one with the word module written on the opening tag. This is a script block with a module attribute, and it is a different beast from the instance script in one precise and important way, which we are going to make crystal clear with the example right there on the page.

Here is the distinction. The plain instance script runs once for each instance, each copy, of your component. If you put your component on the screen fifty times, the instance script runs fifty times, once per copy, and each copy gets its own private set of variables. The module script is different. The module script runs once, total, the very first time the file is loaded by your app, no matter how many copies of the component you eventually create. It is shared. There is exactly one of it, and every instance of the component looks at the same one.

The booklet's little example makes this vivid, so let me narrate it. In the module script, there is a single variable declared, called total, starting at zero. Because it lives in the module script, there is only one total in the whole application, shared by every copy of this component. Then, down in the instance script, the one that runs once per copy, there are two lines. The first takes total and adds one to it, written as total plus equals one. The second logs a little message to the developer console saying, in effect, instantiated this many times, with the current value of total filled in. Now walk through what happens as your app runs. The first time you create this component, the module script has already run once and set total to zero. Then the instance script runs and bumps total to one, and logs, instantiated one time. Create a second copy. The module script does not run again, total is still sitting at one, but the instance script runs afresh for this second copy and bumps total to two, and logs, instantiated two times. A third copy makes it three. The module script gave us a single shared number, living above all the instances, and each instance reached up and touched that same shared thing. That is the whole point of the module script: a place for logic and values that belong to the component as a concept, shared across every copy, rather than to any one copy.

There are a couple of rules around it that the booklet flags, and they both make perfect sense once you hold the timing in your head. The first rule is about direction. Variables declared in the module script can be referenced down in the instance script, but not the other way around. The instance script cannot reach up and use a variable that only exists per instance from within the shared module code. And the reason is pure logic, not an arbitrary restriction: the module script runs first, once, before any instance exists at all, so at the moment the module code runs there are no instances yet, and therefore no per instance variables for it to possibly refer to. The shared thing is born before the individual things, so the shared thing cannot know about them, but the individual things, born later, can certainly know about the shared thing that came before them. Direction follows time.

The second rule is about sharing across files. You are allowed to mark a value in the module script with the word export, and when you do, that value becomes something other files in your app can import and use, exactly like exporting from any normal JavaScript module. But there is one specific thing you cannot do, and the booklet calls it out: you cannot write export default. And there is a beautifully Svelte reason for that. In a dot svelte file, the default export is already spoken for. It is the component itself. When another file imports your component, what it gets, the default thing, is the component. So that slot is taken, and Svelte will not let you override it. You can export other named things alongside the component, but the component keeps the default seat.

One last note, a small kindness for when you go reading older code. The booklet has a legacy flag here telling you that in Svelte four, this same module script was written differently, with an attribute reading context equals module, rather than just the word module. So if you open an older Svelte file and see context equals module on a script tag, do not be confused, that is simply the previous spelling of the exact same idea you just learned. We have a whole lecture late in this course on reading and updating older code, so you will become fluent in these little dialect differences. For now, just file it away. And one honest word of expectation, straight from the documentation, which says about the module script, in a gentle parenthesis, that you will rarely use this. That is true. The module script is a real and useful tool, but you will reach for it only occasionally, for genuinely shared component level concerns. The instance script is your daily home. The module script is a specialized room you visit now and then. Know it exists, understand what it does, and do not feel you must reach for it often.

## 2.6 The Style Zone: Scoped To Your Component Without You Asking

Now to the third zone, the style block at the bottom, and I am going to keep this one shorter than it deserves, because there is an entire lecture later in this course devoted to styling in Svelte, and I do not want to spend its inheritance early. But there is one idea here so central, and so different from what you may be used to, that you must meet it today.

The documentation states it in a single sentence: C S S inside a style block will be scoped to that component. Let me make sure the word scoped is fully clear, because it is the whole gift. Scoped means that the styles you write inside a component's style block apply only to that component, and to nothing else in your entire application, automatically, with no effort from you. Look at the little example in your booklet: a style rule that paints paragraphs a color called burlywood, a sort of soft tan. The comment beside it tells you the truth of it: this will only affect paragraph elements inside this one component. If you have paragraphs anywhere else in your app, in other components, they are completely untouched. The rule is sealed inside the component that wrote it.

Now feel why this is such a relief, by remembering the pain we opened the lecture with. Recall the nightmare of global C S S, where every class name shares one enormous namespace, where naming a style over here can silently reach across the whole app and break something over there, where developers invented elaborate naming disciplines and extra tooling just to keep styles from colliding. Svelte makes that entire category of problem simply vanish, by default, for free. You write your styles plainly, the way C S S was always meant to be written, and Svelte guarantees they stay home. The collision problem is not managed, or mitigated, or made easier. It is gone.

And, as ever, let me place this against the frameworks you remember, because the defaults tell a story. React, out of the box, has no opinion about styling at all, it hands you nothing, and you go and choose from a marketplace of approaches, C S S modules, or styling libraries that let you write C S S inside your JavaScript, or utility class systems. Vue is closer to Svelte here, but with a key difference: Vue can scope your styles too, but you have to opt in, you have to deliberately add the word scoped to your style block to ask for it. Svelte flips the default. In Svelte, scoping is simply what happens. You do not ask for it. You would have to go out of your way to make a style global, which, yes, you can absolutely do when you genuinely need to, and that is exactly the kind of thing the dedicated styling lecture will teach you. But the default, the thing that happens when you just write some C S S and move on, is the safe thing. Scoped to this component. That is a small design decision with a large effect on your daily peace of mind, and it is one of those places where Svelte quietly makes the right thing the easy thing.

That is all I will say on styling today. Just hold the headline: your component's styles belong to your component, automatically. We will return to the full richness of it later.

## 2.7 TypeScript In A Single Attribute

Before we leave the file and turn to the runes, one quick practical note that several of you will care about immediately, because you have tasted TypeScript and do not want to go back to writing JavaScript without types.

The good news is that turning on TypeScript in a Svelte component is almost insultingly easy. You take your script tag, and you add one attribute to it: the word lang, short for language, set equal to the letters t s, for TypeScript. That is it. The moment that attribute is on your script tag, the code inside that script is TypeScript, and you get all the type checking, all the autocompletion, all the safety you remember. The documentation mentions this right alongside the script block, almost in passing, because in Svelte it really is that small a thing. There is a whole lecture later in the course on the deeper TypeScript story in Svelte, the typing of props, generic components, all of it, so I will not go further now. I raise it only so you know, from day one, that the door to TypeScript is open and it is exactly one attribute wide. Write lang equals t s on your script, and you are typing.

So that completes our tour of the file itself. Three zones, script and markup and style, all optional, built on a superset of plain HTML, with an instance script that runs once per copy and a shared module script that runs once for all of them, styles scoped to the component by default, and TypeScript available for the cost of a single attribute. Now we arrive at the heart of the hour, and the heart of the whole language. We have kept mentioning a strange word. Runes. It is time to find out what on earth a rune actually is.

## 2.8 What Is A Rune, Really? Not A Function, Though It Dresses Like One

Open your booklet to the page titled what are runes, and look first at the little note at the very top, because it is charming and it is also a real clue. It gives you the dictionary definition of the ordinary English word rune. A rune, it says, is a letter or a mark used as a mystical or magic symbol. Hold that image, an ancient symbol with a kind of power in it, because the Svelte team chose this word on purpose, and by the end of this section you will see exactly why it fits, and also why, for us, the magic is not really magic at all.

Here is the formal definition, and we are going to unpack every piece of it. Runes are symbols that you use in your dot svelte and dot svelte dot j s files to control the Svelte compiler. And then the line that I want you to underline twice: if you think of Svelte as a language, runes are part of the syntax. They are keywords. Keywords. That single word is the key that unlocks everything strange about runes, so let us make sure we know what a keyword is.

In any programming language, there are special reserved words built into the grammar of the language itself. In JavaScript, words like return, and if, and for, and the word typeof, and the word await. These are not functions that somebody wrote and that you call. They are part of the very fabric of the language. You do not import them from anywhere. They do not come from a library. They are simply there, baked into the grammar, and the language treats them specially wherever they appear. That is a keyword. And the claim the documentation is making, the claim that explains every odd thing about runes, is that a rune is exactly that kind of thing. A rune is a keyword in the Svelte language. It just happens to be a keyword that the standard JavaScript grammar does not have, which Svelte adds on top, and which the Svelte compiler understands.

Now look at the one line of code on that page, and let me narrate it, because it shows you what a rune looks like. It reads: the word let, then a name, message, then an equals sign, then the state rune, which is a dollar sign followed immediately by the word state, and then, in parentheses, the word hello inside quotation marks. Spoken plainly: let message equal state, with hello in quotes. And here is the thing that confuses everyone at first, and that we are now going to permanently un confuse. That state rune, dollar sign state followed by parentheses with something inside, looks exactly like a function call. It has the shape of one. A name, then parentheses, then an argument inside. Your whole instinct, from every language you have ever used, screams that this is a function named state that you are calling with the argument hello. And that instinct is wrong. It is not a function. It only dresses like one.

How can something that looks so much like a function call not be a function? Let me give you the perfect anchor, because JavaScript itself already has examples of exactly this, and once you see them, runes will never feel strange again. Think about the word typeof in JavaScript. You write typeof, and then a value, and it tells you the type of that value. It takes something and operates on it, just like a function. But typeof is not a function, it is a keyword, part of the grammar. You cannot import it, you cannot store it in a variable, it is just part of the language. Or think about the word await, which some of you will remember from working with promises. You write await, then an expression, and it pauses until that expression resolves. It takes an operand and acts on it, exactly like a function would. But await is not a function. It is a keyword. It can only appear in certain positions, inside a special kind of function, and the language enforces that. Runes are precisely this kind of creature. The state rune is to Svelte what the keyword await is to JavaScript: a word built into the grammar that operates on what follows it, that looks a little like a function but is something more fundamental than a function. A piece of the language itself.

The documentation then lists three specific ways runes differ from ordinary functions, and now that you have the keyword idea, each of the three is going to feel obvious rather than arbitrary. Let us take them one at a time.

The first difference: you do not need to import them. They are part of the language. With a normal function from a library, you have to bring it in at the top of your file with an import line, naming where it comes from. Runes have no import. There is nowhere to import them from, because they do not live in a package. They live in the language, the way return and typeof live in JavaScript. You just write the state rune, anywhere it is allowed, and the compiler knows it. No import line, ever. In fact, if you tried to import a rune, that would be a mistake, because there is no package that exports it. It is grammar, not a tool.

The second difference: runes are not values. You cannot assign a rune to a variable, and you cannot pass one as an argument to a function. Let me make this concrete. You could not write something like, let my saved rune equal the state rune by itself, holding onto it for later, the way you can grab any normal function and store it in a variable. That is meaningless in Svelte, because a rune is not a thing that exists as a value floating in your program. It is a marker that has meaning only in the exact spot where you write it, the way the word return has meaning only where it sits and cannot be scooped up and stored in a box. A rune is an instruction at a location, not an object you can carry around.

The third difference: just like JavaScript keywords, runes are only valid in certain positions. You cannot sprinkle them just anywhere. There are specific, grammatical places where a rune is allowed, and places where it is not, and if you put one in the wrong spot, the compiler will catch it and, in the documentation's own reassuring words, will help you, telling you what went wrong. Again, lean on the analogy and it stops feeling like a rule to memorize: you cannot jam the word return into the middle of an arithmetic sum, because return has its proper grammatical positions and the middle of a sum is not one of them. Runes are the same. They have their proper places, and the compiler, which reads your whole file, gently keeps you honest about them.

So step back and look at the three differences together, because as a set they paint one clear picture. No import, because it is built into the language. Not a value, because it is an instruction at a spot, not an object. Position restricted, because it is grammar. Every one of the three is just a consequence of the single underlying truth: a rune is a keyword, a piece of the Svelte language, not a function from a library. Say that to yourself and the strangeness dissolves. Runes are keywords that look like functions.

## 2.9 So What Do Runes Actually Do, And Why Not Just Use Functions?

Let me answer the question that a sharp programmer is now asking. Fine, a rune is a keyword, not a function. But why? Why would the Svelte team build this whole unusual category? Why not just give me ordinary functions to call, the way React and Vue do? This is exactly the right question, and the answer ties this entire lecture back to lecture one.

Remember what a rune is for, from the definition: it is a symbol you use to control the Svelte compiler. That is the heart of it. When the compiler is reading your code, before your app ever ships, and it comes across the state rune, it does not call a function. There is no function to call. Instead, the rune is a signal, a marker, that tells the compiler something like: this variable here is special, please wire it up to be reactive, please generate the machinery that makes the screen follow it. The rune is a message from you to the compiler. It is the way you, the author, reach into the build process and direct it. And because it is a message to the compiler, a thing that happens at build time, it makes no sense for it to be a normal runtime function, a thing that happens later, in the browser. It is operating on a different plane entirely, the plane of compilation, which is the plane Svelte lives on.

This is also the answer to a question some of you have been holding since I mentioned the frameworks. In React, the tools for reactivity are functions you import and call, the hooks, with names like useState and useEffect. In Vue, they are functions you import and call too, with names like ref and computed. These are real runtime functions from real libraries. And because they are real functions tracked at runtime, they come with their own famous rules. React's hooks, for instance, must be called in the same order on every render, which means you are forbidden from calling them inside a condition or a loop, because that could change the order and break React's behind the scenes bookkeeping. React developers know this as the rules of hooks, and they are a genuine source of bugs and head scratching. Now here is something subtle and worth savoring. Runes also have rules about where you can put them, we just covered that, they are position restricted. So on the surface, both have placement rules. But the reason underneath is completely opposite, and the difference is illuminating. React's hooks have placement rules because they are runtime functions whose call order has to stay consistent for the framework to track them. Runes have placement rules because they are compile time grammar, like any keyword. One is a runtime bookkeeping constraint. The other is simply syntax. React is managing an order it watches as your code runs. Svelte is just reading grammar before your code ever runs. Same surface symptom, placement matters, but born from opposite worlds, the runtime world and the compile time world. That contrast, if you sit with it, tells you almost everything about the difference between these frameworks.

And there is one more piece worth knowing, because you may have heard a certain word in modern front end circles and wondered where Svelte stands on it. The word is signals. Under the hood, the reactivity that runes give you is built on a mechanism the industry calls signals, those smart little reactive containers we keep gesturing at and will fully open up in the state lecture. Some frameworks, the framework called Solid is the famous example, hand you those signals directly, as things you create and read and call yourself. Svelte made a deliberate, different choice. Svelte uses signals underneath, but treats them as plumbing, as an implementation detail you are not meant to touch directly. What you touch instead is the rune, the friendly keyword, and the compiler translates your runes into the signal machinery for you. So when someone tells you Svelte is powered by signals, they are right, and now you know the nuance: powered by signals underneath, but driven by runes on the surface, with the compiler bridging the two. You get the performance of signals without having to manage signals by hand. That is the trade Svelte chose, and it is very much in character. Let the compiler do the fiddly work. You just write the friendly marker.

## 2.10 When Runes Escape The Component: The .svelte.js File

Now we can close a loop I opened earlier, and it is a satisfying one. Cast your mind back to the start of the lecture, to the module script, and to a limitation that was lurking underneath all of this. Reactivity, the whole magic of state that updates the screen, traditionally only worked inside your component files. It was trapped there. If you wanted to take some reactive logic and reuse it across many components, or hold a piece of state that the whole application could share, you ran into a wall, because the moment you tried to move that logic out into an ordinary JavaScript file, the reactivity stopped working. Ordinary JavaScript files were not reactive. So you had to reach for a clumsier, older tool to share state, something we will meet much later called the store, with its own ceremony and its own API.

The Svelte team named this pain directly when they introduced runes. They pointed out that the old style of reactivity only worked for simple variable declarations at the very top level of a component, which, in their words, can cause confusion, and that having code behave one way inside a dot svelte file and a completely different way inside an ordinary dot j s file made it genuinely hard to refactor, hard to pull logic out into a shared place. Your reactivity was a prisoner of the component file.

And here is the line that I want you to hear as the triumphant resolution of that whole problem, straight from the announcement of runes: with runes, reactivity extends beyond the boundaries of your dot svelte files. That is the headline capability that runes unlocked, and it is delivered through a special kind of file, which is the third source for today's lecture. Besides dot svelte files, Svelte also works on files ending in dot svelte dot j s, and the TypeScript version, dot svelte dot t s. Look at how that name is built, because the name is the whole trick. It is an ordinary j s or t s file, but with the word svelte slipped in just before the extension. Dot svelte dot j s. And that little svelte in the middle of the filename is a flag, a signal to the compiler that says: this is not an ordinary JavaScript file, this one is allowed to use runes, please process it for reactivity.

So what is a dot svelte dot j s file? The documentation puts it perfectly: these behave like any other JavaScript or TypeScript module, except that you can use runes. That is the entire definition, and it is wonderful in its simplicity. It is just a normal module, the kind you have written a thousand of, with imports and exports and functions, with one superpower added: inside it, runes work. Which means reactivity works. Which means you can finally take a piece of reactive state, or a bundle of reactive logic, lift it clean out of any single component, put it in one of these files, and share it across your whole application, with the same runes you use everywhere else, behaving the same way everywhere. The thing that behaved one way in components and another way in plain files now behaves one consistent way in both. The prisoner is free.

The documentation names the two great uses for this, and they are exactly what you would hope. The first is creating reusable reactive logic, a bundle of reactive behavior you write once and use in many components. The second is sharing reactive state across your app, a single piece of state that lives above all your components and that any of them can read and update, the holy grail of application state, now achievable with nothing more exotic than a rune in a specially named file. There is one careful caveat the documentation flags, which is that there is a particular pattern, exporting a piece of state that you then reassign, that does not work across these module boundaries, for reasons that reach right back into the compiler and that we will understand fully when we study the state rune in depth, a few lectures along. So I am going to leave that caveat as a planted flag for now, name it, but not unpack it, because it genuinely belongs to the state lecture. For today, the headline is the liberation itself: runes, and therefore reactivity, are no longer trapped inside components. The dot svelte dot j s file is where they go to be free, and it is a capability that, as the booklet notes, simply did not exist before Svelte five. It is one of the signature gifts of the modern era of the framework.

## 2.11 Meeting The Family: A Wave At Every Rune From Across The Room

We have spent this whole second half understanding what kind of thing a rune is. Now let me do for you what lecture one's successor promised, and what the state lecture itself refers back to: let me walk you past the whole family of runes and introduce each one by name, with a single sentence about the job it does. We are not learning any of them today. We are at the gathering, shaking hands, catching names and faces, so that when we sit down to dinner with each one in the coming lectures, they are already familiar. I will name each rune, tell you the one problem it exists to solve, and, where it helps, point at the React or Vue tool it most resembles, so your old memories have something to grab.

First, and most important, the state rune. Dollar sign, state. This is the one you will type more than any other, and it is the entire subject of our next lecture. Its job is to declare a piece of reactive state, a variable that, when it changes, updates the screen. It is the foundation everything else stands on. If you remember React's useState or Vue's ref, this is the thing those were reaching for, but reached for the Svelte way, as a plain variable.

Second, the derived rune. Dollar sign, derived. Its job is to declare a value that is computed from other reactive values, and that automatically stays up to date as they change. A running total derived from a list of prices, a full name derived from a first and last name. If you recall React's useMemo or Vue's computed, the derived rune is that idea: a value calculated from other values, kept fresh for you.

Third, the effect rune. Dollar sign, effect. Its job is to run some side effect, some action that reaches outside the pure world of your data, whenever the reactive values it depends on change. Things like talking to a third party library, setting up a timer, logging. If your memory offers up React's useEffect or Vue's watch and watchEffect, the effect rune is the Svelte answer to that same need, and we will spend a whole lecture on why it should be a tool of last resort, not first instinct.

Those first three, state and derived and effect, are the core trio of reactivity, and they will take up the heart of the next part of the course. Now two more that deal with the edges of a component, where it meets its parent.

Fourth, the props rune. Dollar sign, props. Its job is to declare what a component receives from its parent, the inputs, the data handed down from above. If you remember React's props, the things you pass into a component as attributes, or Vue's defineProps, this is that, the Svelte way of saying, here is what I expect to be given.

Fifth, the bindable rune. Dollar sign, bindable. Its job is narrower and more specialized: it marks one of those props as something the parent is allowed to bind to two ways, so that data can flow not just down from parent to child but back up from child to parent through that same connection. It is the explicit opt in for two way binding on a prop, and it pairs with a directive we will study in the template lectures.

And finally, two small specialists that you will reach for rarely, which is exactly why, in our restructured course, they do not each get a whole hour to themselves but are folded in where they naturally belong. The inspect rune, dollar sign inspect, is a development time tool whose job is to watch a piece of reactive state and log every change it undergoes, a little debugging companion that vanishes completely from your production build. And the host rune, dollar sign host, is the most specialized of all, mattering only in the narrow case where you are packaging a Svelte component as a native web component to drop into a non Svelte page, where it gives you a handle on the host element. Do not worry about those two now. I name them only so the family is complete, so that when they appear later you greet them as acquaintances rather than strangers.

So there is the whole family, seen once, from across the room. State, the foundation. Derived, for computed values. Effect, for side effects. Props, for what a component receives. Bindable, for two way binding on a prop. Inspect, for debugging. And host, for web components. Seven symbols, each a keyword, each a message to the compiler, each solving one clear problem. You have now met them all. Over the coming lectures, one by one, you will come to know them deeply.

## 2.12 The Full Recap, And The Road Into Reactivity

We have covered the entire anatomy of the thing you will spend your career writing, so let us gather it all and tie it off, because the recap is where a tour turns into a map you actually own.

We began with a pain you had felt but maybe never named: that a single component, one conceptual thing like a button, traditionally had its three pieces, its logic, its structure, and its appearance, scattered across three separate files that did not know each other, bridged only by fragile shared class names, and that this scattering became a real swamp at the scale of a few hundred components. And we met Svelte's answer, the same answer Vue reached with its Single File Component and that React reached from the opposite direction by pulling markup into JavaScript: put one component in one file. The dot svelte file. Logic, structure, and appearance, together at last, with no bridges to maintain.

We toured the file's three zones, all of them optional, all of them built on a superset of plain HTML, which means your existing HTML knowledge transfers directly, unlike React's J S X which looks like HTML but is JavaScript in disguise. The script zone, the brain. The markup, the structure. The style zone, the looks.

We went deep on the two kinds of script, and the difference between them is one of timing. The instance script runs once for every copy of the component, when that copy is created, and its top level variables are automatically visible to the markup. And we drew the sharp and important contrast with React, where the component function re runs from the top on every single change, whereas the Svelte instance script runs exactly once and lets the compiler handle every later change surgically, a difference that flows straight from Svelte being a compiler, and that places Svelte alongside modern Vue's run once setup rather than React's re run everything. The module script, by contrast, runs once in total, shared by every copy, a home for component level shared values, with its sensible rules: shared code is born first so the instance can see it but not the reverse, and you can export named values from it but never a default, because the default export is forever reserved for the component itself.

We met the style zone and its single most important gift, scoping by default. Your component's styles belong to your component and reach nothing else, automatically, with no effort, dissolving the entire historical nightmare of global C S S collisions, a default that goes further than Vue's opt in scoping and stands in contrast to React shipping no styling opinion at all. And we noted that TypeScript is available for the price of a single attribute, the word lang set to t s on your script tag.

Then we arrived at the heart: what a rune actually is. Not a function, though it dresses like one. A rune is a keyword, a piece of the Svelte language itself, a symbol you use to control the compiler. We anchored it in JavaScript's own keywords that look function like but are not, the words typeof and await, and from that one insight, rune equals keyword, the three strange properties fell out as obvious consequences. You do not import runes, because they are built into the language, not shipped in a package. Runes are not values, you cannot store one in a variable or pass it around, because a rune is an instruction at a location, not an object. And runes are position restricted, valid only in certain grammatical spots, with the compiler helping you when you slip, because that is simply what grammar is. We saw why this is so different from React's hooks and Vue's composition functions, which are real imported runtime functions, and we savored the subtle point that while runes and React hooks both have placement rules, the reasons are opposite, React's from runtime call order bookkeeping, Svelte's from pure compile time grammar. And we placed Svelte on the signals question: powered by signals underneath, like the framework Solid, but unlike Solid keeping them as hidden plumbing while you drive with the friendly rune on top, the compiler bridging the two.

We closed the loop with the dot svelte dot j s file, and the liberation it represents. Reactivity used to be a prisoner of the component file, behaving one way inside a dot svelte file and not at all inside a plain script, forcing you toward clumsier tools to share state. Runes broke reactivity out of that prison. A file named with svelte tucked in before its extension is an ordinary module with one superpower, runes work inside it, which means you can lift reactive logic and shared state clean out of any component and use it across your whole app, consistently, a capability that simply did not exist before Svelte five.

And finally we shook hands with the whole family, from across the room. State for reactive variables, derived for computed values, effect for side effects, props for what a component receives, bindable for two way binding, inspect for debugging, and host for web components. Seven keywords, seven messages to the compiler, each solving one clean problem.

Through all of it, the thread from lecture one held: Svelte is a compiler, and almost everything peculiar and powerful about the dot svelte file and the runes inside it traces back to that one fact. The script runs once because the compiler handles the rest. The runes are keywords because they are instructions to the compiler. The styles scope themselves because the compiler rewrites them. You keep meeting the same idea wearing new clothes, and that is exactly as it should be, because a good mental model is one idea that explains a hundred details.

In the next lecture, before we pick up any single rune, we pull back and see the bigger picture: how components fit together into a whole app, how they pass data and talk to one another, and the entire toolbox laid out at a glance, so that nothing after it is a surprise. Then, in the lecture that follows, we sit down to dinner with the most important member of the family, the state rune, and see how a plain variable can possibly update a screen, how Svelte makes objects and lists deeply reactive, and why, in Svelte, state really is just a variable, with none of React's setter ceremony and none of Vue's dot value tax. Everything you learned today, the file, the script that runs once, the rune that is really a keyword, is the ground we needed to stand on before any of it. So take a short break, look back over the skeleton of the dot svelte file in your booklet while it is fresh, and when you are ready, I will see you in lecture three.
