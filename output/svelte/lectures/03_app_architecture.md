## 3.2 Every Website Is A Database You Can See: One Object, Or A List Of Objects

We have the first great picture, boxes inside boxes, the picture of how an app is put together. Now I want to give you the second great picture, the picture of what an app is actually for, what all those boxes exist to do. And it is, if anything, even simpler and even more powerful than the boxes, and the moment it clicks, a great deal of web development stops feeling like a thousand separate puzzles and collapses into one small, endlessly repeated idea. So let us build it from the ground up, from the smallest brick.

Start with the most important little thing in all of JavaScript: the object. A JavaScript object is just a bundle of labeled values. That is the entire definition. You take a handful of related facts, give each one a label, and wrap them together into one parcel. An article, as an object, is a bundle with a label called headline holding some text, a label called body holding more text, a label called author holding a name, a label called date holding when it was published, a label called section holding which part of the paper it belongs to. Labels and values, wrapped together into one parcel. That parcel is an object. If you ever touched Python, this is exactly the dictionary you knew there, a thing with labeled slots, and a list of them Python folks call a list of dictionaries. In JavaScript we say an object, and a list of them is an array of objects. Same idea, different word, and it is the brick that everything is built from. Because here is the thing about communication in an app: when two parts of your app talk to each other, when the server sends data to your page, when one box hands data to another box, what passes between them is almost always one of just two shapes. A single object, that one labeled parcel. Or a list of objects, a whole stack of those parcels. Everything is an object, or a list of objects. Hold that sentence, because it is about to organize the entire web for you.

Now, where do all these objects come from, and where do they rest when nobody is looking at them? They live in a database. And here is the sentence I want you to carve right next to boxes-inside-boxes, as the second pillar of this whole hour: every website is a visual representation of a database. Say it slowly. A website is a database that you can see and touch. The National Times, with all its pages and photographs and buttons, is, underneath the paint, a database, and every screen you will ever build is nothing more than a way of taking some piece of that database and showing it on the glass, arranged prettily, so a human can read it. The pixels are the paint. The database is the substance. The website is the database, made visible.

So what is a database? At its simplest, a database is a set of tables, and a table is just what it sounds like, a grid, like a spreadsheet, with rows and columns. One table holds the articles: each row is one article, and the columns are its fields, a column for the headline, a column for the body, a column for the date. So the articles table is a stack of article rows, one row per article. Another table holds the users: one row per person, with columns for the name, the email, the role, journalist or editor or reader. Another holds the comments, one row per comment. So the whole data of The National Times is a few tables, articles, users, comments, sections, tags, each one a grid of rows. And the word for a database whose tables are linked to each other is relational. Relational, because the tables relate: an article row points at a user row to say who wrote it, a comment row points at an article row to say what it sits under. The tables hold hands.

Now, your Svelte app, running out in the reader's browser, cannot reach into that database directly. It has to ask for what it needs, across the network, and the way it asks has a name you have heard ten thousand times without perhaps ever pinning it down: an API call. Let me pin it down, plainly. An API call is the communication between your app and your database. It is your app saying, across the network, please give me some data, and the server in front of the database sending data back. And what comes back, every single time, is one of our two shapes. Either one object, or a list of objects. You ask, give me the article with this identifier, and back comes one object, one article parcel. You ask, give me the latest articles, and back comes a list of objects, a stack of article parcels. That is all an API call is. It reaches across to the database and brings back one object, or a list of objects. There is genuinely nothing more mysterious to it, at the level we need today.

And here is the part that makes a relational database quietly powerful. When you ask for one article, the server does not have to hand you only the bare row from the articles table. It can follow the links between the tables and pack you a rich, combined object. It takes the article row, follows the link to the users table to pull in the author, counts how many other articles that author has published, gathers the article's tags from the tags table, and bundles all of it, fields drawn from several different tables, into one neat parcel, and hands that to you. So the single article object you receive might carry the headline and body from the articles table, the author's name and photo from the users table, a number saying this author has forty-two other pieces to their name, and the list of tags, all packed together and labeled, in one object. One object, woven from many tables. That weaving is what relational means in practice, and it is why a single object can be so wonderfully rich. And the same goes for a list: ask for the latest ten articles, and back comes a list of ten such combined objects, each already carrying its author and its tags, ready to display.

So now stand back, and see what the entire web framework is built around, because it is breathtakingly simple. Your app does two things with data. It presents one object. Or it presents a list of objects. That is the whole job. Show one parcel in full, or show a stack of parcels as a list. And when it comes to changing data, the very same two shapes return: you edit one object, or you edit a list of objects. Present one, present a list. Edit one, edit a list. Keep that sentence in your pocket for the rest of your life as a developer, because every screen you ever build is one of those four things. It really is that simple to always hold in mind.

We have a name for each, the four views, and I want them burned into your memory. Presenting one object is the detail view. Presenting a list of objects is the list view. Editing one object is the edit view. And editing a list of objects, many at once, is the batch view, with its lively cousin, editing in place. Four views, but truly just two ideas, one object or a list, doubled across showing and changing. The detail view, on The National Times, is one article opened to its full page, or one video playing. One object, shown completely. The list view is the front page of latest articles, or the Sports section, or one author's articles, or everything carrying a tag, always a filtered stack of article objects. The edit view is the newsroom form where a journalist writes or fixes one article. And the batch view is the editor's dashboard, a hundred articles each with a checkbox, five ticked and published together. A framework called Django taught this with those very names, detail and list, and they are perfect, so we keep them.

And once you truly believe this, that every screen is just one object or a list of objects, a wonderful clarity arrives about what your actual job is as the person writing the code. Your job is design. Specifically, your job is to decide how to arrange the screen real estate, the rectangle of pixels in front of the reader, to present the information of one object, or of a list of objects, beautifully and usefully. The data is fixed, one object or a list. The art is the arrangement. For one article, how do you lay out the headline, the byline, the body, the comments, in the space, so it reads well? For a list, how do you arrange the cards, how many across, what does each show? That is the whole creative act, and it lives entirely inside the simple frame of one object, or a list. The hard part was never what a website is. It is only ever how to arrange one object, or a list, on the glass.

Let me make this concrete with the very first screen any reader meets, the front page, and let us interrogate it the way I want you to interrogate every screen from now on. You open nationaltimes dot com. What do you see? The latest news. Now ask the question that unlocks everything: what did the API call do to put this here? Did it fetch one object, or a list of objects? A list, plainly, you are looking at many articles. Is it the whole, unfiltered list, every article ever published, all million of them in the archive? No, of course not, that would be madness. It is a filtered list, narrowed to the recent ones, perhaps just the five latest stories. So the front page's API call said to the database, in effect: give me a list of articles, newest first, just the top five. A filtered list of objects. And it is usually richer still, because a good front page is not one list, it is several. Look closely at a real news home page and you will see it carved into regions: a big block up top for the five latest breaking stories, a strip for the most-read pieces, a panel for the latest in Technology, another for Sports, another for Opinion. And every one of those regions is its own filtered list of objects, fetched by its own little API call. The Technology panel is a list of articles filtered to the technology section, newest first, top four. The Sports panel is the same query filtered to sports. So the single front page in front of you is, underneath, four or five separate filtered lists of objects, each fetched by its own call, each arranged in its own corner of the screen real estate. Four lists, in four parts of the page. And once you can look at any screen at all and instantly name what it is, this one object, or this filtered list, and guess the call that must have fetched it, you have gained an X-ray vision that makes the whole of web development legible. You will never again see a page as a mysterious whole. You will see the objects and the lists lying underneath the paint.

And here is the realization that seals it and ties the four views into one single craft: the very same object wears all the costumes. One article is a small card in a list, the same article opened into a full page in the detail view, the same article spread across a form in the edit view, the same article shrunk to a checkbox row in the batch view. One object, four costumes. You are never building a thousand different things. You are reaching into a database, pulling out one object or a list of objects, and dressing it, four ways, for the screen. That, from top to bottom, is what a website is: a database you can see, shown one object, or one list, at a time.

## 3.3 The Real Shape Of An Article: Its Id, Its Slug, Its Tags, And How You Filter The Stream

We just said, at a high level, that everything is an object or a list of objects, and that an object is a bundle of labeled values. That is true, but it is still a little abstract, and since every single lecture from here on is going to stand on top of exactly this thing, the article object, I want to make one utterly concrete, so real you could almost hold it in your hand. Let us look at one article on The National Times up close and name every label inside it, because these labels are the handles that the entire rest of the course will reach for.

Picture one article, a breaking news story. As an object, it is a parcel with these labels. There is a label called id, spelled i d, short for identifier, holding a unique number, let us say one thousand two hundred and three. There is a label called slug, holding a short, hyphenated piece of text, ceasefire talks collapse, all lowercase with hyphens between the words, and we will spend real time on what a slug is in a moment, because it matters far more than it looks. There is a label called title, holding the actual headline, the words Ceasefire Talks Collapse As Fighting Resumes. There is a label called section, sometimes called category, holding the word World, because this story lives in the World section of the paper. There is a label called tags, holding a small list of words, war, ceasefire, diplomacy. There is a label called author, and here is something important: it does not hold the writer's name. It holds a number, a user id, say forty-two, a pointer, a reference to one particular person who lives over in a different table. There is a label called published, holding the date and time the story went live. And there is a label called body, holding the long text of the article itself. So that is one article object: id, slug, title, section, tags, author, published, body. Eight labels, one parcel, one story. Hold that picture, because it is the atom of everything we build.

Let me pull out the very first label, the id, because it carries a principle that runs through all of databases and all of web development. Every article has an id, and every id is unique. No two articles share the number one thousand two hundred and three. Why does that matter so much? Because an id is how you point at exactly one thing, with zero ambiguity. Titles can repeat, two different papers can both run a story called Breaking News, but ids never repeat. So when you need to say to the server, fetch me that article, the one and only that one, you say it by id. And it is not only articles. Every user has a unique id. Every comment has a unique id. Every tag, every section, everything that lives in a table gets its own unique id, its true name inside the database. That is, in fact, the rule of a table: every row has a unique id, called its key, and the whole table is organized around those keys. One subtle thing worth holding: ids are unique within their own table, not across tables. Article number forty-two and user number forty-two are completely different things, because forty-two means a row in the articles table in the first case and a row in the users table in the second. An id only means something paired with the table it belongs to.

And here is where this becomes something you will feel directly, very soon, inside Svelte. When the server hands you a list of objects, a stack of article parcels, every parcel in that stack carries its own unique id. And that turns out to be essential, not merely tidy, because the instant you show a list on screen and that list can change, an article added at the top, one deleted from the middle, the order reshuffled, the framework needs a way to tell the items apart, to know that this card on screen is still the same article it was a moment ago and not a different one that slid into its place. The only reliable way to tell them apart is a stable, unique field on each one, and that is exactly what the id is for. So in Svelte, when you render a list, you will hand the framework that unique id as the key for each item. Every framework, React, Vue, Svelte, asks the very same thing of a list: give me something unique per item. The id is the answer. File that away; it comes back in full in the lecture on lists.

Now the tags label, because a tag is a small idea that does a great deal of work. A tag is just a short word you stick on an article to describe what it is about, so the article can be grouped and found. Our war story carries the tags war, ceasefire, and diplomacy. A sports story might carry the tags basketball, playoffs, lakers; a tech story the tags hardware, batteries, laptops. An article usually carries several tags. And the same tag is shared across many articles: the tag war sits on this story and on a hundred others. Tags are open-ended and informal, anyone in the newsroom can coin a new one, climate, election, royal-family. And what they buy you is a way to slice the stream: a tag page that gathers every article carrying war, pulled together from across all the sections of the paper. So a tag is a cross-cutting label, many per article, shared by many articles, and it powers those gather-everything-about-this pages.

It is worth one breath to separate a tag from a section, because beginners blur them constantly. A section, or category, is the big official bucket an article lives in, and there are only a handful: World, Politics, Sports, Technology, Business, Culture, Opinion. An article belongs to one section. A tag is a small informal label, and there are thousands of them, and an article wears many at once. The section is the grand division of the newspaper; the tags are the fine threads running sideways across it. A few fixed sections, a sea of open tags. Both are just labels on the object, and both, as we are about to see, become ways to filter.

Now back to that slug, because you asked about it directly, and it is genuinely important and genuinely practical. Look at the two labels our article carries for identifying itself: the id, one thousand two hundred and three, and the slug, ceasefire talks collapse. Both point at this one article, uniquely. So why have both? Here is the story. Every article needs a web address, a link, so people can visit it and share it. The simplest possible address would just use the id: nationaltimes dot com, then a slash, then one two zero three. That works. It is unique, it lands on the right article. But look at it. It tells a human absolutely nothing. It is an opaque number. You cannot tell, from that link alone, whether it leads to a war story or a cake recipe. Now look at the other option, built from the slug: nationaltimes dot com, then a slash, then ceasefire hyphen talks hyphen collapse. You can read it. The link itself now tells you what waits on the other end. The address has become a carrier of meaning, in plain visible words, right there in the link. That readable, hyphenated, lowercase version of the title is the slug, and the recipe for making one is simple: take the title, make it all lowercase, replace the spaces with hyphens, and strip out the punctuation, so Ceasefire Talks Collapse As Fighting Resumes turns into ceasefire-talks-collapse-as-fighting-resumes. Why go to this trouble? Two reasons, both worth real money in the real world. First, search engines. The readable words sitting in a web address are one of the signals a search engine uses to understand and rank a page, so an address full of the right words helps the article get found, and being found is the lifeblood of a news site. That whole concern, shaping your site so search engines favor it, has a name you will hear constantly, S E O, search engine optimization, and slugs are one basic piece of it. Second, plain human trust. People click a link they can read. A link that says ceasefire-talks-collapse looks relevant and safe; a link that says one two zero three looks like nothing, or like a trap. So the slug makes the link both findable by machines and clickable by humans. And, crucially, the slug is still unique, exactly like the id: each article gets its own, and if two articles would ever generate the same slug, the same headline running twice, you simply add something to keep them apart, a number on the end, or the date. So hold this clean distinction: the id is the article's private name, the one the database uses internally; the slug is its public name, the readable, unique handle the world uses out in the open, in the link. Modern sites lead with the slug in their addresses for exactly these reasons, and so will we, which is why, when you saw the article route earlier written with a bracketed name in the address, that bracket catches the slug.

Step back now to where all of this actually rests when nobody is looking at it: the database. Our article object, in storage, is one row in the articles table. The columns of that table are precisely the labels we named: a column for id, a column for slug, a column for title, a column for section, a column for author, a column for published, a column for body. One row is one article; the columns are its fields. The author column holds the user id, forty-two, the pointer, and over in the users table, row forty-two holds that person's name and photo and role. That pointer from one table to another is the relational link we talked about, and it is how an article knows who wrote it without copying the writer's whole identity into every single article. The tags, because they are many-per-article and shared across articles, get their own little table and a join that records which tags belong to which articles. So the neat single object you receive from the server is, underneath the surface, one article row, plus the joined author row, plus the joined tag rows, all gathered together for your convenience. The object is the convenient, combined parcel. The tables are where the pieces really live.

And now, at last, the labels pay off, because every label on the object is a handle you can filter the entire stream by, and this is where the lists on your pages actually come from. Want the recent list for the front page? You filter by the published label: give me articles, sorted by published date, newest first, just the top five. Want the Technology section page? You filter by the section label: give me articles where the section is Technology, newest first. Want a tag page gathering everything about the war? You filter by the tags label: give me every article that carries the tag war. Want one journalist's page, all of their work in one place? You filter by the author label: give me articles where the author id is forty-two. Do you see the single pattern under all four? Each of those pages, the recent page, the section page, the tag page, the author page, is the very same move: take the stream of article objects, and narrow it by one of the labels on the object. The fields are not just for display. Every field is a potential filter, a potential way to slice the million articles in the archive down to the handful this particular screen wants to show. That is exactly why the shape of the object matters so much, and why we just spent real time on it: the richer and more thoughtful the labels, the more ways you can slice and arrange the stream. An article that knows its date and its section and its tags and its author can be gathered into a recent list, a section list, a tag list, and an author list, four completely different pages, all from the same object, all just by filtering on a different label.

And when one of those objects, or one of those lists, finally arrives in your app, your boxes simply read its labels. The article card reads the title to print the headline, reads the section to show a little category badge, reads the tags to show the tag chips, reads the author, now filled in with the real person, to print the byline, and reads the slug to build the link that, when a reader clicks it, will fetch this one article by its slug and open its full detail page. The object is read, label by label, to paint the card and to wire up the link. That, concretely, is how communicating with objects works: data arrives as labeled parcels, and your interface reads off the labels.

So now you are standing on real ground, not the abstract idea of an object, but a particular article, with an id and a slug and a section and tags and an author pointer and a body, stored as a row among related rows, fetched as one object or filtered into a list, and read label by label to paint the screen. Every lecture after this one, when it teaches you state, or derived values, or props, or loading data, will be operating on exactly this article object. We are not going to invent fresh data each time. We are going to keep reaching for this same parcel, this article with its id and its slug and its tags and its author, and lay one more layer of skill on top of it. So let this object live in your mind as a real, specific, particular thing. It is the ground the whole course is built on.

## 3.4 The Tree Of Boxes, And The Family That Lives In It

We have the data, a stream of article objects, and the four ways to view it. Now the structure question: how do we actually arrange the boxes on the screen to show that data? The answer is a tree. A tree of components, boxes nested inside boxes. Open your booklet to the front-page diagram and follow along with your eyes while I build it in your ears, because we are about to name every box, and we are going to name the family relationships between them, and we are going to keep naming those relationships for the rest of the course.

Let us build the front page of The National Times, the list view. The outermost box, the whole page, is a component. We will call it the front page component. It is the biggest box, the one that holds everything else. Inside the front page box, there is a box whose job is to show one section's worth of articles in a stream. We will call it the section feed. So the front page box contains a section feed box. And inside the section feed box, there is one box for each article, a little card showing the headline and a snippet. We will call that box the article card. So now we have three levels: the front page holds the section feed, and the section feed holds many article cards. Boxes inside boxes inside boxes.

Now I am going to introduce the words we will use for the rest of the course to talk about who sits where in this tree, because without these words we will get hopelessly lost, and with them everything stays clear. The words are family words, and they work exactly the way you would guess.

When one box sits directly inside another, the outer one is the parent and the inner one is the child. So the front page is the parent of the section feed. And the section feed is the child of the front page. Simple. The front page holds the section feed, so front page is parent, section feed is child.

Now go one level deeper. The section feed holds the article cards. So the section feed is the parent of each article card, and each article card is a child of the section feed. But notice what that makes the front page. The front page is the parent of the section feed, and the section feed is the parent of the article card. So the front page is the parent of the parent of the article card. And we have a lovely short word for the parent of the parent: the grandparent. The front page is the grandparent of the article card. And running the other way, the article card is the child of the child of the front page, the grandchild. The article card is the grandchild of the front page. Let me say that whole chain once more, slowly, because this is the vocabulary of the entire course: the front page is the parent of the section feed, the section feed is the parent of the article card, so the front page is the grandparent of the article card, and the article card is its grandchild.

Let us fill in the article card itself, because it is full of smaller boxes, and they introduce one more family word. Inside one article card, there are several little boxes side by side: a headline box, a short excerpt box, an author badge box showing who wrote it, a publish date box showing when, a tag list box holding the article's tags, and a clap button box, the little reaction button readers tap to applaud an article. Now, all of those boxes, the headline, the excerpt, the author badge, the date, the tag list, the clap button, are all children of the same parent, the article card. And boxes that share the same parent have a name too: they are siblings. The headline and the clap button are siblings, because they have the same parent, the article card. Just like children in a family who share a parent are brothers and sisters. So inside one article card we have a little family of siblings.

And we can go deeper still, because the tag list box is itself a parent. The tag list holds one small box per tag, a tag box. So the tag list is the parent of each tag, which makes the article card the grandparent of each tag, and the section feed the great-grandparent of each tag, and the front page the great-great-grandparent. You see how the chain extends. Parent, child, sibling, grandparent, grandchild, and onward, as deep as the nesting goes.

The article page, the detail view, nests even deeper, and it is worth walking because it gives us the deepest family chain we will use. Open the article-page diagram in your booklet. The outer box is the article page. Inside it, an article header box, an article body box, a tag list, and a comment section box. Now follow the comment section down, because this is the deep one. The comment section holds a comment form, where you type your comment, and a comment list, which is the stream of existing comments. The comment list holds one comment box per comment. And each comment box holds a comment author box, a comment body box, and a comment date box. So count the levels from the top: the article page holds the comment section, which holds the comment list, which holds a comment, which holds the comment body. That is the article page as the parent of the comment section, the grandparent of the comment list, the great-grandparent of the comment, and the great-great-grandparent of the comment body. A deep chain of boxes inside boxes inside boxes, five levels down.

Why am I drilling these family words so hard? Because the entire second half of this lecture, and a great deal of the whole course, is about how these boxes talk to each other, and you cannot talk about talking without knowing who is the parent and who is the child and who is the distant grandchild. The relationships are the map of who can reach whom. And because you are listening, not looking, I am going to keep reminding you of these relationships every single time I name a component, on purpose, in repetition. When I say the clap button, I will often add, remember, the child of the article card. When I say the comment body, I will remind you it is a deep grandchild buried inside the comment, inside the comment list, inside the comment section. That repetition is not me padding the time. It is me drawing the diagram in your ear, over and over, because you have no diagram in front of you, only my voice. So let the repetition wash over you. By the end, this tree will live in your head without any picture at all. Boxes inside boxes, and a family living in the tree.

Before we move on to how the boxes talk, let me make sure you can picture how a box gets born in the first place, because it is wonderfully simple and it is the daily act of building in Svelte. Creating a component is two moves, and only two. Move one: you make a new file and write the box. Say you want the clap button. You create a file named clap button dot svelte, and inside it you write the three zones you learned in lecture two, a script zone for its logic, some markup for the button itself, and a style zone to make it look right. That file, those three zones, is the clap button box, complete, sitting on disk, ready to be used. Move two: you place the box inside another box, by writing its tag. Over in the article card, which, remember, is the parent that will hold this button, you go to the card's markup and, wherever you want the button to appear, you write a clap button tag. That is the entire act. Writing that tag is what puts the box on the screen, nested inside the article card, a child inside its parent. A box inside a box, which, say it with me, in code is a tag inside a tag.

And here is the economy that makes this powerful, the thing that pays off everywhere. If you want a hundred clap buttons across a hundred article cards, you do not write a hundred files. You wrote the one clap button file, once, the single design of the box, and then you place its tag a hundred times, or, far more usefully, you let a loop place it once per article. One file is the design of the box; many tags are the many places it appears. That split, one component definition and endless uses of it, is the whole logic of building with components, and it is the rubber stamp we will lean on the moment we talk about props. So hold this simple pair: to make a box, write its dot svelte file with the three zones; to use a box, write its tag inside a parent. Create the file, place the tag. That two-move rhythm, repeated a few hundred times, is how an entire news organisation gets built, one box at a time. Now, those boxes are placed but mute. Let us teach them to talk.

## 3.5 The First Way Boxes Talk: Data Flows Down, Through Props

Now the real heart of the hour. We have a tree of boxes. But a tree of boxes that cannot share anything is useless. The front page knows there are articles to show, but how does that knowledge get down into each individual article card so the card can display the right headline? The boxes have to talk. And it turns out there are exactly three directions in which boxes talk, and we are going to take them one at a time. Down, then up, then sideways. Master those three directions and you have mastered how an app communicates. Let us start with the most common and most important one: down.

Here is the problem, made concrete on The National Times. The front page component, the big outer box, is the one that has the array of articles, all the latest news, fresh from the server. The section feed, its child, loops over that array. And for each article in the array, the section feed creates one article card, its child. But a freshly created article card is an empty box. It does not know which article it is supposed to show. The section feed has to hand each card its particular article, this card gets the article about the election, that card gets the article about the football match. The parent has data, and it needs to give a specific piece of that data to each child. Parent to child. Down the tree.

The mechanism for this has a name, and it is the most important word in component communication: props. Short for properties. Let me name it and then immediately explain it, the way I promised I always would, because a name with no explanation is just a noise. A prop is a value that a parent component hands down to a child component, by writing it onto the child's tag. That is the whole idea. When the parent puts the child's box on the screen, it writes the child's tag, and right there on the tag, it attaches the values it wants to hand down.

Let me show you the shape of it in plain words, because the structure is simple and you should be able to picture it. Think back to lecture two, where you learned that putting a box inside a box means writing a tag. So when the section feed wants to place an article card, it writes an article card tag in its markup. Now, to hand that card an article, it writes the value right on the tag. In ordinary words, it is like writing an article card tag and adding, on the tag itself, article equals this particular article. You have seen this a thousand times in plain HTML without thinking about it: when you write an image tag, you add source equals some web address, right there on the tag. That source is, in spirit, a prop. You are handing the image element a value by writing it on its tag. Props are the same idea, for your own components.

And then, on the other side, the child has to be built to catch what is handed to it. Over in the file named article card dot svelte, the article card component is written to expect a value called article, and to receive it already filled in. So the parent decides the value and writes it on the tag, and the child file is written to catch that value and use it, to pull the headline and the date and the author out of the article it was handed, and display them. Let me say the whole shape once more, because it is the pattern you will use more than any other in your entire life as a Svelte developer: the parent writes the child's tag with the value attached, and the child file is built to catch the value. Parent writes the tag with the value. Child file catches it. That is props.

Notice the direction. The data flows down. From the parent, down to the child. From the front page, down through the section feed, down into each article card. Data always flows down through props, from a box to the boxes inside it. Down, down, down the tree, like water. Hold that image next to the boxes: the outer box pours data into the inner boxes through the values written on their tags.

Now let me make you feel why this matters, by showing you what breaks without it, because a feature only really lands once you have felt the hole it fills. Imagine props did not exist, and a child box could not be handed any values. Then every article card would be a sealed, identical box. The section feed could create a hundred article cards, but it could not tell any of them which article to show, because it would have no way to hand the article in. Every card would be blank, or every card would show the same hard-coded thing. The whole idea of a reusable card, one component design that displays a hundred different articles, would be impossible. Props are what let one component, written once, show endless different data. Without them, components could not be reused with different content, and the entire web would collapse into hand-writing every single card by hand. Props are the difference between a rubber stamp and writing every page out longhand. That is the size of what props do.

Now, props are wonderful for parent-to-child, one step down. But here is a wrinkle that you will hit, and it has its own name, so let us name it. What happens when a value has to reach a box that is not one step down, but many steps down, a deep grandchild? Suppose the logged-in reader's name needs to appear in the comment form, which, remember, is buried deep: inside the comment section, inside the article page. To get the reader's name from the top of the tree all the way down to that deep comment form using only props, you would have to pass it as a prop from the article page down to the comment section, and then the comment section, even though it does not care about the reader's name at all, would have to take it and pass it down again to the comment list or the comment form, and so on, hand to hand, down every single level, each box in the middle dutifully passing along a value it has no use for itself, just to get it to the deep box that actually needs it.

That tedious, hand-to-hand passing of a prop down through many levels, through parents and grandparents that do not care, just to reach a deep grandchild, has a name: prop drilling. You are drilling a value down through the layers, like drilling a hole straight down through floor after floor. And while it works, it is miserable at depth. Every box in the chain gets cluttered with a value it only passes along. And the day you insert a new box in the middle of the chain, you have to re-thread the whole drill, teaching the new box to pass the value too. Prop drilling is the pain that one of our later tools, called context, exists to cure, and we will meet that cure in just a few minutes, in the third direction. But first, we have only covered data going down. What about a box that needs to send something back up?

## 3.6 The Second Way Boxes Talk: Messages Flow Up, Through Events

Data flows down through props. That is settled. But now flip the problem around, because real apps need the reverse too. A reader taps the clap button to applaud an article. The clap button, remember, is a small box, a child of the article card. When it is tapped, something needs to happen up above it: the article card, its parent, needs to know, so it can bump the clap count and maybe send the new count off to the server. So here a child needs to tell its parent that something happened. Information needs to travel up the tree, from child to parent. The opposite direction from props.

Let me state the great rule of component communication, the one that organizes everything, because you now have both halves of it. Data flows down, through props. Messages flow up, through events. Down for data, up for messages. The parent pours data down into the child through props. The child sends signals back up to the parent through events. Two directions, two mechanisms, and they are not the same mechanism running backwards, they are genuinely different tools for the two genuinely different directions. Down is props. Up is events.

So how does a child send a message up? Here is the clever and slightly surprising part, and I want to name it carefully and then explain it, because newcomers often get this backwards. The child does not reach up and grab its parent. A box is never allowed to reach up out of itself and meddle with the box it lives inside. That would be chaos, a child reaching up and yanking on its parent. Instead, the trick is this: the parent hands the child a function. The parent, when it places the child and hands down its props, also hands down, as one of those props, a little function for the child to call. And then, when the event happens, the child simply calls that function. The function was written up in the parent, so calling it runs code up in the parent. The child does not reach up. The child just calls the function it was given, and that function, by its nature, does its work back home in the parent.

Let me make that concrete on the clap button, with its family relationship reminded, because this is exactly the kind of thing the family words are for. The clap button is a child of the article card. So the article card, the parent, when it places the clap button, hands it a function as a prop, a function we might think of as on clap. The function itself, the actual code that increases the count, lives up in the article card. The clap button just holds onto this function it was handed. Then, when the reader taps the clap button, the button calls the on clap function. And because that function lives in the article card, calling it runs the count-bumping code in the article card. The message has traveled up, from the child clap button to the parent article card, without the child ever reaching up. It just called the function it was given. The parent handed down a string, and the child pulled the string.

This is called passing a callback, or handling an event. A callback is just a function you hand to someone else so they can call it back to you when the moment comes, hence the name, call back. You hand the child a way to call back up to you. Name it, and explain it: a callback is a function the parent gives the child so the child can notify the parent that something happened.

And what breaks without it? Picture a clap button that has no way to message upward. The reader taps it, and the button could light up its own little self, but it could never tell anyone above it. The article card would never learn that a clap happened, so the count would never rise, and the new count would never reach the server. The button would be a doorbell with no wire, a button that clicks but rings nothing. Every interactive element that needs to affect anything beyond its own tiny box, which is almost all of them, depends on this upward channel. Without messages flowing up, a child could receive the world through props but could never answer back. Events are the answer-back.

Because we never name another framework without explaining it, let me quickly place this against the two you half remember, because they do the exact same dance with slightly different choreography. In React, it is identical in spirit: data flows down as props, and to send a message up, the parent hands the child a function as a prop, and the child calls it. If you ever wrote on click handlers in React and passed functions down, you were doing precisely this. In Vue, the down direction is also props, but the up direction has its own dedicated mechanism, where a child emits an event with a name and the parent listens for that named event. Different spelling, same sentence: down is props, up is messages. Svelte's way, handing the child a function to call, is the same family idea as React's, and you will see the full, comfortable details of it when we reach the lecture on markup and events. For today, hold the rule: data down through props, messages up through events, and the child never reaches up, it only calls the function it was handed.

## 3.7 The Third Way Boxes Talk: Shared Things Flow Sideways, Through Context

We have two directions: data down through props, messages up through events. And for a huge amount of an app, those two are all you need, a tidy parent-child conversation up and down the tree. But there is a third situation that the up-and-down conversation handles badly, and it is common enough to need its own tool. Let us feel the pain first, because the pain is exactly the prop-drilling misery I flagged earlier.

Some things in an app are needed everywhere, by boxes scattered all over the tree, with no tidy parent-child line connecting them. The logged-in reader: who is logged in matters to the comment form deep in the article page, to a little greeting up in the navigation bar, to the clap button which needs to know who is clapping, to a dozen boxes in completely different branches of the tree. The current theme, light mode or dark mode: every single box might need it, to color itself correctly. The current section the reader is browsing. These are not values that flow neatly from one parent to one child. They are ambient. They hang in the air of the whole app, and boxes everywhere reach for them.

If you tried to deliver the logged-in reader to every box that needs it using only props, you would be back to prop drilling, and at a brutal scale. You would thread the reader's identity down from the very top, through the section feed, through every article card, through the comment section, through the comment list, down to the comment form, with every box in the middle accepting it and passing it along though it does not use it. And you would do that drilling separately for the theme, and again for the current section, and again for anything else ambient. Your whole tree would clog with values passing through on their way to somewhere else. The grandparents and great-grandparents would be stuffed with props they are merely couriering. It is the wrong tool, painfully applied.

So there are two better tools for sideways sharing, and I will name and explain each.

The first is called context. Name it, explain it: context is a way for a parent to put a value into a shared space that any of its descendants, however deep, can reach into directly, without the value being drilled through every level in between. Picture it like this. Instead of passing the reader's identity hand to hand down the stairs, a high-up box, say the outermost app shell, places the reader's identity on a shared shelf, a shelf that the whole subtree below can see. Then the deep comment form grandchild, when it needs to know who is logged in, simply reaches over to the shared shelf and takes it. It does not receive it through ten layers of props. It reaches straight to the shelf. The boxes in between, the section feed, the article card, the comment section, none of them have to know or care or pass anything along. The value skipped them entirely and went straight from the high-up provider to the deep consumer. That is context: a value set high in the tree, readable by any descendant directly, no drilling.

Let me anchor it: the app shell, near the top of The National Times, sets the logged-in reader into context once. Then the comment form, buried deep, a great-grandchild several levels down, reads the reader straight out of context to stamp the comment with the right name. The whole long chain of boxes between them is bypassed. And what breaks without context? Without it, you are condemned to prop drilling for every ambient value, threading the reader and the theme and the section through every box in the tree, cluttering grandparents with couriered props, and re-threading the entire chain every time you nest one more box. Context is the relief valve for that pressure. We give it a full hour later in the course, in the lecture on the context API, and you will know it by then as an old friend, because you met its job here.

The second tool for sideways sharing is even more direct, and it ties back to something you already learned in lecture two. Sometimes a value is not just ambient within one subtree, it is truly global, belonging to the whole application and not to any particular place in the tree at all. The logged-in reader is often like this. The count of unread notifications. A shopping cart, on a shop. For these, you do not even need the tree. You can lift the value clean out of the component tree entirely and put it in a shared file, a module, that any component anywhere can simply import and use. And here is the lovely callback to lecture two: remember the dot svelte dot j s file, the ordinary module that is allowed to use runes? That is exactly where shared, app-wide reactive state lives. You make a file, perhaps called session dot svelte dot j s, you put the logged-in reader in it as reactive state, and then any component, in any branch of the tree, at any depth, imports that file and reads the reader, and when the reader changes, every component using it updates. The value does not live in the tree at all. It lives off to the side, in a shared module, and the whole tree reaches into it.

So now you have the full picture of how boxes talk, all three directions, and I want you to hold them together as one shape. Data flows down, through props, parent to child. Messages flow up, through events, child to parent, by calling a function the parent handed down. And shared, ambient, or global things flow sideways, reaching boxes all over the tree directly, through context for a subtree or a shared module for the whole app. Down, up, and sideways. Props, events, and context-or-modules. That is the entire grammar of component communication. Every conversation between any two boxes in any app you ever build is one of those three. When you are stuck, when two boxes need to share something and you do not know how, ask the one diagnostic question: which direction is this? Down to a child, up to a parent, or sideways to somewhere scattered? Answer that, and the tool chooses itself.

## 3.8 What Keeps The Screen Alive: The Reactivity Toolbox, Previewed

The boxes are arranged into a tree, and they can talk in three directions. But there is still a missing ingredient, the one that makes a website feel alive rather than dead. When something changes, when a clap count goes up, when a new comment arrives, when the reader switches to dark mode, the screen has to respond, instantly, without anyone manually rebuilding the page. That responsiveness is called reactivity, and it is delivered by the runes we waved at last lecture. Today I want to preview the three most important runes, the core trio, so that when each gets its own full hour, it arrives as a familiar face. I will use the same five-beat shape for each: name it, explain it in a sentence, show its shape, anchor it in The National Times, and tell you what breaks without it.

But first, one piece of housekeeping that will save a React veteran real confusion. Coming from React, your hand reaches for a thing called a hook. Use state, use effect, use memo, the hooks. I have to tell you plainly: Svelte has no hooks. The word does not apply here. There are no hooks to look for, and if you go hunting for them you will be lost. What Svelte has instead, in the place where React keeps its hooks, are the runes. So make this one mental translation, once, and then let go of the word hook for the rest of the course: the thing you would reach for a hook to do in React, you reach for a rune to do in Svelte. The reactive variable that React calls use state, Svelte calls the state rune. The side effect that React calls use effect, Svelte calls the effect rune. The computed value that React calls use memo, Svelte calls the derived rune. Hooks become runes. Make the swap and move on. Now, the trio.

First and most important, the state rune. Name and explanation: the state rune declares a reactive variable, which is simply a value that, when you change it, automatically updates the screen wherever it is shown. Its shape, which you will learn cold next lecture, is that you declare a normal-looking variable but mark it with the state rune, and then you change it like any plain variable, and the screen follows along. Anchor it in The National Times: the clap count on an article card is reactive state. So is a little true-or-false value tracking whether this article card's share menu is currently open. So is the text the reader is typing into the comment form. These are values that change while the page is open, and the screen must keep up with them. And what breaks without it? If the clap count were a plain, ordinary variable, then tapping the button would change the number in the computer's memory, but the number printed on the screen would never move. The reader would tap and tap, the count would silently climb in memory, and the screen would sit there frozen, lying, showing the old number forever. State is the rune that closes that gap, that ties the variable to the screen so they move together. We give it the whole next lecture, lecture four, because it is the foundation everything else stands on.

Second, the derived rune. Name and explanation: the derived rune declares a value that is computed from other reactive values, and that stays correct automatically, recomputing itself whenever its ingredients change. Its shape is that you write a little formula in terms of your state, and Svelte keeps the formula's result fresh forever. Anchor it in The National Times, and there are lovely examples. The phrase five minute read, shown on each article card, is not stored anywhere, it is derived, computed from the length of the article body, so many words, so many minutes. The clean label one point two thousand claps is derived from the raw clap count, a number formatted nicely for humans. A little Breaking badge that should appear only on articles published in the last hour is derived from the article's date. Each of these is a value calculated from other values. And what breaks without it? Suppose you computed five minute read once, by hand, when the card first appeared, into a plain variable. Then the moment the article body changed, or the moment you reused the card for a different article, your label would be stale, still claiming five minutes for an article that is now ten. Derived is the rune that keeps every computed value honest, recomputing exactly when its sources move and never otherwise. You have, in fact, already glimpsed this one, because it is lecture five, the very next deep dive after state, and its whole theme is computing values without the cache bugs that stale-by-hand computation causes.

Third, the effect rune. This one is different in kind, and I want you to feel the difference. State holds a value. Derived computes a value. But the effect rune does not produce a value at all. The effect rune reaches out and does something in the world when your reactive values change. Name and explanation: the effect rune runs a piece of action, a side effect, whenever the reactive values it watches change. Its shape is a block of code that re-runs automatically when its ingredients move. Anchor it in The National Times: imagine a live breaking-news ticker that needs to open a connection to the server and keep it open, receiving fresh headlines as they happen, and updating the page. Opening that connection and listening on it is an effect, an action out in the world, triggered by the page appearing. Or, in the newsroom, automatically saving the journalist's draft to the server every few seconds as they type, so nothing is ever lost. That autosave is an effect, watching the draft and acting when it changes. And here is the what-breaks, and it is the most important warning in the whole reactivity story, so listen closely: effects come with a duty to clean up after themselves, and forgetting that duty causes a specific, nasty bug called a memory leak. Picture the breaking-news ticker again. It opens a live connection to the server when the article appears. Now the reader navigates away to a different article. If the effect did not clean up, did not close that connection on the way out, the connection stays open forever, abandoned, consuming memory, listening to nobody. Now multiply: the reader browses fifty articles in a session, and you have opened and abandoned fifty live connections, fifty leaks, and the browser slowly chokes. A memory leak is exactly this, resources you opened but forgot to close, piling up invisibly until the app grinds. The effect rune gives you a clean way to say, when this box goes away, close the connection, and using it correctly is the difference between a smooth app and one that gets slower the longer it runs. Effects are powerful and a little dangerous, which is why, when we give them their full hour in lecture six, the whole theme is treating them as a tool of last resort, used carefully, cleaned up always.

So there is the core trio, previewed. State, the reactive value that keeps the screen in sync. Derived, the computed value that stays correct on its own. Effect, the action in the world that runs on change, and must be cleaned up. There is a fourth rune in this neighborhood that you will meet very soon too, the props rune, which is simply how a component formally declares the props it expects to catch, the catching side of the down-the-tree conversation we had earlier, and it gets its hour in lecture seven. But the trio, state and derived and effect, is the engine room. Every flicker of life on The National Times, every count that climbs, every label that updates, every ticker that streams, is one of these three doing its quiet work.

Let me give you the rule of thumb for which of the three you reach for, because the choice becomes obvious once you ask the right question, and learning to ask it is most of the craft. Ask, of any piece of behavior: what kind of thing is this? If it is a fact that can change, a value you hold and update over time, it is state. The clap count, the open-or-closed share menu, the text being typed into the comment box. You are holding a value, so reach for state. If it is a fact computed purely from other facts, something you could always recalculate from scratch and never actually need to store, it is derived. The read time from the body length, the formatted label from the raw count, the breaking badge from the date. You are not holding a value, you are expressing a relationship between values, so reach for derived, and never, ever compute it by hand into a plain variable, because that is precisely the stale-value cache bug we will spend the whole of lecture five killing. And if it is not a value at all, but an action, something that reaches out and touches the world beyond your data, opening a connection, starting a timer, saving to the server, writing to the page, only then is it an effect, and the instant you reach for an effect you must ask the second question right behind it: what do I have to clean up when this box goes away? Because the honest answer is almost never nothing, and forgetting it is the memory leak. So hold the three questions as one: am I holding a value, computing a value, or performing an action? Hold a value, reach for state. Compute a value, reach for derived. Perform an action, reach for effect, and clean up after it. When you can feel, instantly, which of those three a given behavior is, you will reach for the right rune without thinking, and a great deal of the rest of this course is simply sharpening that one instinct until it is automatic.

## 3.9 Why A Web App Is Not A Script: Reactivity, The Lifecycle, And The Asynchronous World

We need to pause now on the single biggest mental shift in all of this, because if you came to web development from ordinary programming, from writing a script that does a job, then a web app works in a way that will quietly confuse you until somebody names the difference out loud. So let me name it out loud.

Think about a normal program, the kind you may have written to learn to code. A script. It runs from top to bottom. Do this, then this, then this, read some input, do a calculation, print the answer, and then it ends. The program's whole life is that single run, that sprint from the first line to the last, and when it reaches the bottom, it is over. Two things are true of that script, and we take them so for granted that we never notice them. First, it is synchronous: each step waits for the one before it to finish, in order, and nothing happens until you tell it to, in the sequence you wrote. And second, it is one-shot: it runs once, start to finish, and dies. You, the programmer, are in charge of the order, and the program does exactly what you said, in the order you said it, and then it stops.

A web app is not like that, in two deep ways, and both of them are why reactivity exists at all.

The first way: a web app is long-lived and event-driven, not one-shot. When your page loads, it does not run top to bottom and exit. It loads, and then it sits there, alive, for minutes, for hours, doing nothing at all, waiting. And then something happens, the reader clicks the clap button, or types into the comment box, or navigates to a new article, or a fresh headline arrives from the server, and the app springs to life for an instant to respond, and then goes back to waiting. Your code is no longer a sequence of steps to run in order. Your code is a set of reactions, hung off events, waiting to be triggered. The clap handler waits for a tap. The derived read-time waits for the article body to change. The effect waits for the component to be born. You are not writing a recipe that runs once; you are wiring up a switchboard that answers calls for as long as the page is open. That is what event-driven means, and it is the opposite of the top-to-bottom script. The browser runs a never-ending loop, watching for events, and your job is to register what should happen when each one fires.

The second way: a web app is asynchronous, where a script is synchronous. Asynchronous is a long word for a simple, crucial idea: some things take time, and you must not freeze while you wait for them. When your app asks the server for the latest articles, that request travels across the network and back, and that takes time, maybe a tenth of a second, maybe two whole seconds on a train with bad signal. A synchronous script would simply stop and wait, frozen, until the answer came. A web app cannot do that, because a frozen page is a broken page, the reader cannot scroll, cannot click, cannot do anything, while you wait. So instead, the app fires the request and immediately moves on, keeping the page alive and responsive, and then later, whenever the answer finally arrives, a piece of code wakes up and continues the work, and the reactive system updates the screen with the new data. That pattern, fire it now, continue later when the result is ready, without ever freezing, is the whole meaning of asynchronous. The tools for it are called promises, a promise being a placeholder for a value that is not here yet but will be, and a keyword called await, which politely says, pause this particular piece of work until the promise arrives, but let everything else keep running. Every time your app talks to your FastAPI server for articles, or to Supabase to check who is logged in, or opens a live feed of breaking news, or runs an animation over time, it is doing something asynchronous, something that unfolds over time rather than instantly. A simple script almost never touches this. A web app swims in it.

Now, because the app is long-lived and full of boxes that come and go, the reader navigates from the front page to an article and back, articles scroll into the list and out of it, comments are added and removed, each component has a life of its own. It is born, it lives, and it dies. It is born when it is first created and placed on the screen. It lives, for a while, updating itself as its state changes. And it dies when it is removed, when the reader navigates away, or when it scrolls out of a list that no longer holds it. This birth, life, and death of a component is called its lifecycle, and it is the missing piece that ties reactivity to the real, moving app.

Here is why the lifecycle is not a side topic but the very thing reactivity needs. Remember the effect rune from a few minutes ago, the one that runs an action in the world and must be cleaned up. Why must it be cleaned up? Because of the lifecycle. When the breaking-news ticker box is born, the moment it appears on the article page, it opens a live connection to the server to receive headlines. That is an action taken at birth. Now the reader navigates away, and the ticker box dies, it is removed from the screen. If nothing happens at that death, the live connection it opened stays open forever, abandoned, listening to no one, holding memory, the very leak we talked about. So the effect must do something at the moment of death: close the connection. Reactive side effects have to be born and die with their component. They start when the box is born and stop when the box dies. Without that binding to the lifecycle, every effect would leak. So the lifecycle is the frame, the birth and death boundary, inside which reactivity safely lives. Reactivity says what reacts to what; the lifecycle says when those reactions begin and end.

Svelte gives you a small set of tools for the lifecycle, and I will name them so they are familiar when they get their full hour, which is lecture twenty. The effect rune you already met is the main one, and now you can see it whole: an effect runs its action after the box is born, re-runs that action whenever its reactive ingredients change, and runs its cleanup both before each re-run and at the box's death. So the effect rune is reactivity and lifecycle fused into one tool, which is exactly why it is the home of anything that touches the world and must be tidied up. Alongside it, there is a function called on mount, which runs once, right after a box first appears, for one-time setup that needs the box to actually exist on the page, focusing an input, say, or starting up a third-party library on an element. And there is on destroy, which runs once, at the box's death, for one-time cleanup. And there is a small tool called tick, for the rare moment you need to wait until the screen has finished updating before you do your next thing. You do not need to hold the details today. You need to hold the shape: a component has a life, it is born and it dies, and anything reactive that reaches out into the world, a connection, a timer, a subscription, a foreign library, must start at birth and be cleaned up at death, or it leaks.

So gather the whole shift in one image. A plain script is a sprint: it runs once, in order, waiting at each step, and then it is done. A web app is a long, living conversation: it loads and then stays alive for hours, doing nothing until an event calls it to react, with pieces being born and dying all the while, and with much of its work unfolding over time, fired now and finished later, without ever freezing. Reactivity is how Svelte manages the reacting, the keeping-in-sync as things change. The lifecycle is how Svelte manages the being-born-and-dying, the starting and stopping. And asynchrony is the over-time nature of the work that flows through both. Hold those three together, reactive, alive, and asynchronous, and you understand why a web framework looks so different from the scripts you may have written before. It is not more complicated for the sake of it. It is shaped exactly to the strange fact that a web app, unlike a script, has to stay alive and stay responsive while the world changes around it.

## 3.10 Beyond The Boxes: The Code That Is Not A Component, And The Reusable Logic People Call Hooks

So far, almost everything we have built is a component, a dot svelte file, a visible box. But a real app is full of code that is not a component at all, code with no markup, no box, that does its work behind the scenes. I want to give you the whole typology of that non-component code, the filing cabinet of it, because knowing where each kind of code belongs is precisely what makes a project feel organized rather than a junk drawer you are afraid to open. And since you are going to deploy this with TypeScript, I will talk in terms of dot t s files, TypeScript files, throughout.

There are three big kinds of file that are not components, and then a couple of special seams where your code meets the outside world. Let me take them in order.

The first kind is the plain TypeScript file, the dot t s file: an ordinary module with no reactivity at all, just plain code that takes input and gives output. And inside this plain-file world, there are several distinct jobs worth separating. One job is type definitions. Because you are using TypeScript, you get to describe the shape of your objects, once, in one place, and have the whole app agree on it. You write, in a types file, what an article actually is: a headline which is text, a body which is text, an author which is a user, a date, a section, a list of tags, a list of comments. You describe a user, you describe a comment, you describe a video. And from then on, every other file in your app imports those shapes, so that everywhere you touch an article, the compiler knows it has a headline and a body and an author, and will catch you the instant you misspell one or forget one. Those type files are the shared vocabulary of your whole app, the agreed-upon shape of every object in your streams, and in a TypeScript project they are some of the most valuable files you own. A second job for plain files is utilities, little pure helper functions: format this raw date into the words three hours ago, turn this headline into a web-address-friendly slug, count the words in this body and turn it into a read time, shorten this text to a preview. Pure input to output, no state, no surprises. They gather in a utilities file. A third job, and a crucial one, is the api module, the file that talks to your server, but that one deserves its own full section, the next one, so I will only flag it here: the functions that fetch articles and post comments live together in one plain TypeScript module. And a fourth, smaller job is configuration: the address of your server, settings, switches, gathered in a config file so they live in one place rather than scattered.

The second kind of non-component file is the reactive module, the dot svelte dot t s file, which you met back in lecture two: an ordinary module that has the one superpower of letting runes work inside it. This is where reactivity lives when it does not belong to any single box. And it has two great uses. The first you already met in our talk about sideways sharing: shared global state. The logged-in reader, held in a file called session dot svelte dot t s, reactive, so that when the reader logs in or out, every box in the app that shows their name updates at once. The current theme, light or dark. A shopping cart on a shop, a count of unread notifications. State that belongs to the whole app, not to one box, lives in a reactive module.

But the second use of the reactive module is the one I most want to give you today, because it is the thing you specifically asked to be reminded of, and it is genuinely important. It is reusable reactive logic. Let me build up to it through the idea you remember from React, the custom hook, because the principle carries straight over even though the machinery is cleaner.

In React, you would sometimes find yourself with a chunk of stateful logic that you needed in several different places. Tracking whether a dropdown is open, and closing it when the reader clicks outside it. Debouncing a search box, so it does not fire a request on every keystroke but waits until the reader pauses. Pagination, keeping track of which page you are on and how to step forward and back. Tracking whether the screen is currently narrow or wide. Each of these is a little bundle of state plus the logic that drives it, and the painful thing was that you might need the exact same bundle in five different components. So React gave you the custom hook: you would extract that logic into a function, named beginning with the word use, that held the state and returned it, and then any component could call that one function and get the same behavior without copying and pasting. And the wisdom you developed about them, the principle you remember, was exactly right and worth restating: keep them small and focused, agile little pieces, not giant monsters; and the test for when to make one is reuse. If you find yourself needing the same stateful logic in more than one place, several similar buttons that all talk the same way to do the same kind of job, a behavior repeated across the app, extract it into a small reusable unit. If you only need it once, leave it sitting in its one component. Reuse is the trigger. That principle is sound, and it is the same in Svelte.

Here is the Svelte version, and it is cleaner. Because runes work inside a dot svelte dot t s file, you extract reusable reactive logic into an ordinary function, or an ordinary class, that lives in such a file and uses runes inside itself, and returns reactive values. You might write a function called create pagination that holds the current page as reactive state inside itself and hands back a way to read the page and functions to step forward and back. You might write a class called counter with a reactive count field and an increment method, and then make as many independent counters as you like. You might write a function that watches whether a media query matches, narrow screen or wide, and gives back a reactive true-or-false that any component can read. You write the bundle once, in a dot svelte dot t s file, and any component imports it and gets the same live behavior, exactly the reuse you had with custom hooks. But here is the relief, and it is a big one, because you told me hooks were hard to grasp. In React, hooks came with a thicket of rules, the so-called rules of hooks: you could only call them at the top of a component, never inside a condition or a loop, always in the same order, and breaking those rules broke your app in baffling ways. Those rules are why hooks felt fiddly and fragile to learn. In Svelte, none of those rules exist, because these are not a special category called hooks at all. They are just ordinary functions and ordinary classes that happen to use runes inside them. You can call them anywhere, in any order, inside a condition if you like, because they are not hooks, they are functions. So the good instinct you built in React, extract reusable reactive logic into small agile units, transfers completely, and the awkward rules that made it hard to learn simply fall away. Reusable logic in Svelte is just well-named functions in a reactive module. Small, focused, reused when reused, and free of the old rules.

And now I have to clear up a genuine source of confusion, because the word hook means three completely different things in this world, and people mix them up constantly. Let me separate them once, cleanly. Meaning one: a React custom hook, reusable stateful logic. Svelte's answer to that, as we just said, is a function in a dot svelte dot t s file, and Svelte does not call it a hook. Meaning two: React's built-in hooks, use state and use effect, the reactivity primitives themselves. Svelte's answer to those is the runes, state and derived and effect, and again Svelte does not call them hooks. So in the two senses you know from React, Svelte has the capabilities but never uses the word hook. But, meaning three, and this is the trap, SvelteKit does have a feature it literally calls hooks, and it is a totally different animal: a special file, named hooks dot server dot t s, that runs on every single request that hits your server, like a guard at the door who inspects everyone coming in. It is middleware, a checkpoint, and the classic thing you do in it is check who is logged in, which is exactly where Supabase will come in shortly. So when you hear the word hook in the Svelte and SvelteKit world, it almost always means that server checkpoint file, the middleware, and almost never means a reusable piece of component logic. Reusable logic is a function in a reactive module. A hook, in SvelteKit, is the guard at the server's door. Keep those apart and a whole category of confusion evaporates.

There is one more seam I owe you, because you asked it directly: how do you bring in someone else's JavaScript library? Because you will, constantly. A charting library for an analytics page. A rich-text or markdown editor for the newsroom. A date picker, a map, a drag-and-drop reorderer, a syntax highlighter. There are two cases, and they are easy to tell apart. The first case is a library that is pure logic, with no need to touch the page itself: a date library that does calendar math, a library that validates email addresses, a money-formatting library. These you simply import into a plain TypeScript module or straight into a component and call, like any other function. Nothing special, it is just code. The second case is the interesting one: a library that needs to attach itself to a real element on the page, a chart that has to draw into a particular box, a tooltip that hangs off a particular button, a map that fills a particular container, an editor that takes over a particular text area. These libraries need a live element, and they need to be set up the moment that element appears and torn down the moment it leaves, which, you will notice, is exactly the birth-and-death lifecycle we just discussed, but for a single element rather than a whole component. Svelte has a tool made precisely for this seam, and it is called an action. An action is a small function that you attach to an element using a directive called use, and Svelte hands your function the real element the instant it appears on the page, lets your function set the foreign library up on it, and lets your function return a cleanup that Svelte will run when the element leaves. So wrapping a charting library is exactly this: you write a small action that takes the box and the data, draws the chart into the box, and cleans the chart up on the way out, and then in your markup you attach that action to a div with the use directive, and you are done. The action is the clean, tidy joint between Svelte's lifecycle and a foreign library's setup and teardown. We give actions their own full hour in lecture fourteen, but know today that they are the proper home for any third-party thing that lives on a real element.

So let me close this section by answering the question underneath all of it: apart from the components, which look so calm and static, what are the dynamic, code-demanding situations a real app actually throws at you, and where does each one's code live? Because the boxes are the calm surface, and underneath them is a great deal of moving machinery, and now you can place every piece of it. Fetching and paging through a million archived articles: the api module talks to the server, a load function pulls each page, and a reusable pagination function in a reactive module tracks where you are. Search as the reader types: a small reusable debounce in a reactive module, calling the api module, updating local state. The live breaking-news ticker: an effect that opens a subscription at birth and closes it at death. Logging in, and keeping ordinary readers out of the newsroom: Supabase auth, checked in the SvelteKit server hook and in load functions, the user shared through session dot svelte dot t s. Clapping with instant feedback: optimistic state updated now, the api module called, the server reconciled. The newsroom editor with its validation and its autosave: form state, a validation utility, an autosave effect, and a rich-text library wrapped in an action. Infinite scroll: an action wrapping the browser's own intersection observer. An analytics chart for the editors: a charting library wrapped in an action. Every one of those dynamic situations, every place the app actually moves and breathes, is a specific kind of code in a specific, nameable home: the api module for server talk, load and actions for page data, effects for things that happen over time and must be cleaned up, actions for foreign libraries on real elements, reusable functions in reactive modules for logic you repeat, and plain TypeScript files for pure helpers and the all-important type shapes. The static-looking boxes are the still surface of the pond. This is the life moving underneath.

## 3.11 Where Data Enters And Leaves: Reads, Writes, FastAPI, And Supabase

We have the last big piece to place: the data itself. The articles on The National Times do not appear by magic. They live out on a server, in a database, behind a backend, and you have told me exactly what yours will be, so let us be concrete. Your content, the articles and videos and comments, will live behind a backend written in Python with a tool called FastAPI. And your identities, who is logged in, who is an editor and who is just a reader, will be handled by a service called Supabase. So your app has two outside worlds to talk to: FastAPI for the content, Supabase for the people. Let us see exactly where each conversation happens, because the question every real app must answer, and the one you asked me directly, is: where do the calls to the server actually go? In the context? In a hook? Let me give you the clean, complete answer.

First the rule in one breath, and then the detail. Reads, the data a page needs to show, go in a load function. Writes, creating and changing things, go in a form action. On-demand fetches that happen while the page is already open go in an event handler. And every one of those, underneath, calls into the single api module. Reads in load, writes in actions, on-demand in handlers, all of them through the one api module. And explicitly, so you stop wondering: API calls do not go in the context, because context is only for handing shared values down the tree, it fetches nothing; and they do not go in a hook in the React sense, because there are no such hooks, the reusable version of fetch logic would simply be a function in a reactive module. So: load, actions, handlers, through the api module. That is the whole of where data calls live.

Let me walk the three, anchored on The National Times. Reading first, which serves the list and detail views. When the front page needs its array of latest articles, or the article page needs its one article and its comments, that fetching happens in a load function, a piece of code attached to the page that runs first, before the page is drawn, fetches what the page needs, and hands it to the page. The front page's load asks the api module for the latest articles; the article page's load, seeing in the address which article was requested, asks the api module for that one article and its comments. And then the load hands its fetched data to the page as a prop, and from there it pours on down the tree through props to every card, exactly the downward flow we have leaned on all hour. Reading is load, and load feeds the props. Writing next, which serves the edit view. When a journalist fills in the new-article form and hits publish, that submission is caught by a form action on the server, which takes the headline and body and tags and tells the api module to create the article. Editing an existing one is the same shape, an action that calls the api module to update it. And the third, the on-demand fetch, for things that happen after the page is already alive: the reader clicks load more comments, or types into a search box, or taps clap. Those are handled right there in an event handler in the component, which calls a function on the api module and updates local reactive state with what comes back. And if a fetch should re-run whenever some state changes, say, refetch the list whenever the chosen section changes, that can live inside an effect, carefully, with cleanup, because it is exactly the over-time, lifecycle-bound kind of work effects are for.

Now let us put FastAPI concretely in the picture, because it is your backend and you should see how the conversation actually works. FastAPI, on the Python side, exposes a set of addresses, called endpoints, each of which answers a particular request and replies with data in a plain, universal format called JSON, which is just text laid out as labeled bundles, the very streams of objects we started the hour with. So your FastAPI server offers an address for the list of articles, an address for one article by its identifier, an address that accepts a new article, and so on. Notice that those addresses are nothing but our two shapes turned into routes on the server: an address that gives back a list of objects, and an address that gives back one object, the very present-a-list and present-one we built the whole hour on. And when the one-article address replies, it sends the rich, combined object we talked about, the article woven together with its author and its tags from across the tables, so your card receives everything it needs in a single parcel. And your Svelte app, inside the api module, talks to those addresses using a built-in browser tool called fetch, which reaches out over the network to an address and brings back the reply. So a function in your api module called get articles does, in plain words, this: it fetches the articles address on your FastAPI server, it waits, asynchronously, without freezing, for the JSON to come back, and it returns that as an array of articles. And here is where your TypeScript types pay off beautifully: you tell the compiler that what get articles returns is an array of your article shape, and from that moment the whole app knows, with certainty, that every article has a headline and a body and an author, all the way down. The content flows from FastAPI, as JSON over fetch, into your api module, which hands it to a load, which feeds it as props into your boxes. That is the full pipe from the Python server to the screen. One more important detail: a load function can run on your own server rather than in the reader's browser, in that plus page dot server file, and that is where you make any call that needs a secret, a private key to your FastAPI backend, because code on your server is never shipped to the reader, so the secret stays safe. Server-side load for anything secret, the reader's browser never sees it.

And Supabase, for the people. Supabase is a hosted backend that bundles a few things, a database, file storage, live updates, and the part you are using it for, authentication, the machinery of who is logged in. The flow is worth holding in outline, because authentication touches several of the files we just typed out, and seeing it tie them together is satisfying. The reader signs in, with an email and password or through a provider like Google, and Supabase hands back a session, which is essentially a sealed token that proves who they are. You keep a small Supabase client in a module in your lib folder, the thing that knows how to talk to Supabase. Then, remember the third meaning of the word hook, the SvelteKit server hook, that guard at the door that runs on every request? That is exactly where you check the session: on every request to your app, the server hook reads the reader's token, asks Supabase who they are, and attaches the answer so the rest of the app can see it. The root layout's load function then takes that logged-in user and makes it available to the whole tree, and a session dot svelte dot t s reactive module holds it so any box, from the masthead greeting to the deep comment form, can read who am I and react when it changes. And protecting the newsroom is then simple and lives in the right place: in the write page's load function, you check the user; if they are not an editor, you turn them away before the page ever loads. So Supabase answers the question we raised long ago about the logged-in reader, the one we share sideways through context and modules; Supabase is where that reader's identity actually comes from. Two backends, two clean jobs: FastAPI serves the content through your api module and your load functions, and Supabase establishes identity through the server hook, the layout load, and the session module. Content on one wire, identity on the other, each landing in exactly the kind of file we built a typology for.

So let me give you the single sentence to carry, because it prevents the most common beginner mess, and then the picture of the whole circulation. The sentence: components receive their data through props from a load function, send their changes back through form actions, fetch on demand through event handlers, and every one of those goes through the one api module, never scattered ad hoc across the components, and never, ever in the context. And the circulation, end to end: a million articles sit in your database behind FastAPI; the reader arrives, the server hook establishes through Supabase who they are, the front page's load asks the api module for the latest articles, the api module fetches them as JSON from FastAPI, the load hands them down as props, and they pour into the cards; the reader opens one, its route loads the single article and its comments the same way; the reader, now known to be logged in, claps, and an instant optimistic update shows on screen while a write travels out through an action and the api module back to the server; an editor logs in, is recognized by Supabase as an editor, is let into the newsroom that a mere reader's load would have turned away from, writes a piece, and a form action sends it through the api module to FastAPI, where it joins the million. Content in through load, changes out through actions, identity through the hook and the session, all of it through clean, named, single-home pieces. That is the full circulation of a real app, and you now know where every drop of it flows.
