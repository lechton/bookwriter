# Derived Values

A derived value is a value that will not compute until somebody reads it, and will not recompute when its inputs change, only when it is read again after a change. Most values sit holding a number. A derived value sits holding a rule for producing a number, and the production happens on demand. Change the inputs a thousand times. The derived does not recompute. It records that its answer can no longer be trusted, and waits.

## What a derived is, technically

A derived is a kind of Signal. A Signal is a closure: a function that defines inner functions, and those inner functions keep access to the variables of the function that created them, even after the outer function has finished running. That private access is what lets a Signal hide its value and its list from the outside world, while still letting its inner read and write functions reach them.

A Signal holds two things. It holds a value, and it holds a list of something from each function that has read that value. The list exists because when the value changes, the Signal needs to know which functions to re-run. Something from each of those functions is on the list because the function was caught reading the value, from inside an Effect. An Effect is a wrapper that runs a function in a way that lets the Signals the function reads learn the function's name, so they can drop a piece of that function into their own list. The Effect's whole purpose is to make that learning possible. Without an Effect around the function, the Signal would never find out the function read it, and nothing from the function would ever end up on any list.

A derived is a Signal with two additions, and both additions exist for the same reason: to defer work. The first addition is a stored answer, the last value the derived's rule produced, kept around so later reads do not redo the work. The second addition is a dirty flag, a single boolean that says whether the stored answer can still be trusted. The dirty flag is true when the stored answer might be stale, and false when the stored answer is known to be correct.

The derived also has its own list, separate from any Signal's list, holding the functions that have read the derived itself. A derived is read by other code the same way a Signal is read by other code, and for the same reason: so that when the derived changes, the code that read it can be told. A derived is downstream of its inputs, the way a function is downstream of the values it reads. A derived is upstream of its readers, the way a Signal is upstream of the functions that read it. Both directions use the same list mechanism, because a derived plays both roles at once.

## The rule that governs a derived

A derived obeys one rule, and the rule has two halves that never swap.

When one of a derived's inputs changes, the derived does not recompute. The change travels to the derived through the input's list, which holds a small inner function of the derived called markDirty. markDirty is the inner function whose entire job is to flip the derived's dirty flag to true, and then pass the news along to whatever is on the derived's own list. No arithmetic happens. The stored answer is still there, still holding the old value, now flagged as untrustworthy.

When the derived is read, the derived checks its dirty flag. If the flag is false, the stored answer is handed back as-is, and no work is done. If the flag is true, the derived's rule runs, produces a fresh answer, the fresh answer replaces the stored answer, and the flag is cleared.

markDirty runs on every input change. The rule runs only on a read that finds the flag up. Those are the two halves, and they never swap.

## Why the deferral exists

A real screen does not have one derived value. It has a cart total, a discounted total, a taxed total, a shipping total, a currency-formatted string for each, a sorted item list, a filtered sale list, a flag for free-shipping eligibility. None of these are stored. All of them follow from a handful of values the user can change. If every one of them recomputed the instant any input changed, every keystroke in any input field would set off a cascade of arithmetic across the whole screen, including the parts in collapsed panels, scrolled out of view, or behind tabs.

The deferral stops the cascade. A derived recomputes only when read, and only if its flag is up. A derived in a collapsed panel is read by nothing while the panel is closed, so it recomputes nothing while the panel is closed, no matter how many times its inputs change. The moment the panel opens and the screen reads the derived, the flag is up, the rule runs once, and the answer is correct. The arithmetic is paid for exactly when the answer is needed, and not before.

## The laziness has two layers

The derived is lazy in two distinct senses, and confusing them is where most of the misunderstanding lives.

The first sense is lazy about work. The derived does not recompute when its inputs change. This is what markDirty guarantees: a change reaches the derived through the input's list, markDirty flips the flag, and nothing else happens. The arithmetic is deferred.

The second sense is lazy about wiring. The derived does not subscribe to its inputs until somebody reads it for the first time. Before that first read, the derived is connected to nothing. Its inputs do not know the derived exists, because markDirty has never been dropped into any input's list. Writes to the inputs have nobody to notify. The derived is structurally incapable of being told about changes, because it has not yet introduced itself to anything.

Both senses are lazy. The first is lazy about computation. The second is lazy about subscription. Together they make a derived free when nobody uses it: free of arithmetic, and free of the bookkeeping that would precede arithmetic.

## The first read is where the wiring happens

The derived is wired to its inputs during its first read. The first read is special because the derived's flag starts true, so the rule runs, and the rule reads the inputs. Reading an input means calling the input's read function. The input's read function, the moment it is called, looks at which Effect or derived is currently running, and drops that thing into the input's own list.

During the first read of a derived, the thing currently running is the derived, in the form of markDirty. The input's read function drops markDirty into the input's list. The wire is built. The input now holds a reference to markDirty, and through markDirty, to the derived. Future writes to that input will call markDirty, which will flip the derived's flag.

The wire is an entry in a list. The entry is markDirty. markDirty is an inner function of the derived, sealed in the derived's closure. That is the entire physical reality of the connection between an input and a derived.

## The proof, watched from inside the lists

Here is a derived whose rule increments a counter every time the rule runs, so the cost is visible. The input is a Signal called price.

```js
let runs = 0;
const price = makeSignal(3);

const total = makeDerived(() => {
  runs = runs + 1;
  return price.read() * 100;
});
```

Change the price twice, without ever reading total.

```js
console.log("before anything, runs:", runs);   // before anything, runs: 0
price.write(9);                                 // the input changes
price.write(12);                                // the input changes again
console.log("after two writes, runs:", runs);   // after two writes, runs: 0
```

Two writes. Zero computations. The derived ignored both, in the only sense that matters: no arithmetic happened. price's list holds markDirty, markDirty flipped the flag twice, and the flag is now true. The stored answer is stale, but the rule has not run.

Read total once.

```js
console.log("first read:", total.read(), "runs:", runs);   // first read: 1200 runs: 1
```

One read. The flag was up, so the rule ran. The rule read price, got 9, multiplied, returned 900, but wait: the stored value was updated to 12 by the second write, so the rule read 12, multiplied, returned 1200. The rule stored 1200 and cleared the flag. One computation.

Read total again, immediately, with no change in between.

```js
console.log("second read:", total.read(), "runs:", runs);  // second read: 1200 runs: 1
```

Second read. The flag is false. The stored answer, 1200, is handed back. Zero computation. The second read was free.

The two writes cost two flag flips. The first read paid for the arithmetic. The second read was free. A derived that nobody reads is free forever, no matter how many times its inputs change.

## The dirty flag, in plain words

The dirty flag is a single boolean attached to a derived. It means, exactly and only, that the stored answer might be stale and must be recomputed before being returned. The flag is flipped to true by markDirty, every time an input changes. The flag is flipped to false by the rule, every time the rule runs. The flag is checked by the read function, every time the derived is read.

The flag is the bridge between the write that did not recompute and the read that did. Without it, the read would have no way to know whether the stored answer was still good. With it, the read does not need to remember what the inputs were, or what values they held, or how many times they changed. The read checks one boolean. That is the whole bridge.

## When to use a derived, and when not to

The rule of thumb is one sentence. If the thing being written is an answer, use a derived. If the thing being written is an action, use an Effect.

A cart total is an answer. A filtered list is an answer. A formatted date is an answer. A flag that says whether a form is valid is an answer. Each follows from other values, each is read by something, none is set by hand. Each goes in a derived.

A logging statement is an action. A network fetch is an action. Focusing an input is an action. Calling a third-party library is an action. Each reaches into the world and does something, none produces a value that something else reads. Each goes in an Effect.

The sign that the choice was wrong is always the same. An Effect that needed a second piece of state to hold what it produced wanted to be a derived. A derived whose body reaches into the world instead of returning a value wanted to be an Effect.

## The whole mechanism, restated

A derived is a Signal with a stored answer, a dirty flag, and a rule. The stored answer is the last value the rule produced. The dirty flag says whether the stored answer can be trusted. The rule is a function of the derived's inputs.

A derived is wired to its inputs during its first read. The first read runs the rule, the rule reads the inputs, and the inputs drop markDirty into their own lists. markDirty is the derived's inner function that flips the dirty flag.

When an input changes, the input calls markDirty. markDirty flips the dirty flag to true. No arithmetic happens.

When the derived is read, the read function checks the dirty flag. If the flag is true, the rule runs, the stored answer is replaced, the flag is cleared. If the flag is false, the stored answer is returned. No arithmetic happens.

A derived is lazy about computation, and lazy about wiring. A derived that nobody reads costs nothing, no matter how many times its inputs change. A derived that is read by an Effect recomputes once per change, because the Effect reads it, the read finds the flag up, and the rule runs. The laziness is what stops a thousand derived values across a complex screen from recomputing on every keystroke.
