# Derived Values

A derived value is a value that will not get out of bed until somebody knocks on its door. Even then, it only gets dressed if it noticed its clothes changed overnight. If nobody knocks, it stays in bed forever, no matter how much the world outside moves on.

That is a strange thing for a value to do. Most values sit there, holding a number, waiting to be read. A derived value is not holding a number. It is holding a promise to produce a number on demand, and the demand has to actually arrive before the production happens. Change its inputs all you like. Write to them a thousand times. The derived does not recompute. It just makes a small private note that its answer can no longer be trusted, and goes back to waiting.

This is the whole intuition of a derived value, and like all good intuitions, it is wrong in every detail and right in every important way. The derived is not asleep. It does not have clothes. It does not make notes. All of that gets corrected later, or it never does, because by the time the real mechanism arrives the reader will not need the cartoon anymore. What the cartoon captures is the only thing a cold reader can actually hold at the start: a derived value is lazy about its own existence, and it is conditionally lazy at that.

## Why a value would behave this way

Picture the alternative. You have a shopping cart. There is a price, there is a quantity, and there is a total that is always price times quantity. You want that total available, because the screen shows it. The obvious thing to do is to recompute it the instant either input changes, so it is always correct and always ready.

That obvious thing works. It is also, in any real application, a disaster. The screen does not only have one total. It has a total for the cart, a total after discount, a total with tax, a total with shipping, a formatted currency string for each of those, a sorted list of items by price, a filtered list of items on sale, a flag that says whether the cart qualifies for free shipping. None of these are stored. All of them are derived from a handful of actual values the user can change. If every one of them recomputed the instant any input changed, then every keystroke in the quantity field would set off a cascade of arithmetic across the whole screen, including the parts the user cannot see because they are in a collapsed panel, or scrolled out of view, or hidden behind a tab.

The derived value exists to refuse that cascade. It says: I will not recompute when my inputs change. I will only recompute when somebody asks me for my value, and only if I have reason to believe my old answer is stale. If nobody asks, I do nothing. If somebody asks and my inputs have not changed since last time, I hand back the answer I already computed. The arithmetic happens once, on demand, and never again until it has to.

## What "lazy" actually means here, before any code

A value is lazy if it does not do its work until the moment its work is needed. That is the whole definition. The contrast is with a value that is eager, which does its work the moment its inputs change, whether or not anyone needs the result.

The derived is lazy in two distinct senses, and conflating them is where most of the confusion lives.

The first sense is the obvious one: the derived does not recompute when its inputs change. This is the part the cartoon captured. Write to a dependency, the derived ignores you, in the sense that no arithmetic happens.

The second sense is less obvious, and it is the one that makes the first sense survivable: the derived does not even subscribe to its dependencies until somebody reads it for the first time. Before the first read, the derived is connected to nothing. Its inputs do not know it exists. Writes to them have nobody to notify. The derived is not merely refusing to recompute. It is, at this stage, structurally incapable of being notified, because it has not yet introduced itself to anything.

Both senses are lazy. The first is lazy about work. The second is lazy about wiring. Together they are what make a derived free when nobody uses it: free of computation, and free of the bookkeeping that would precede computation.

## The two things that have to be true for this to work

If a derived does nothing when its inputs change, two questions immediately follow, and the entire mechanism exists to answer them.

The first question: how does the derived know it needs to recompute, when somebody finally reads it, if it did nothing when its inputs changed? Something must have happened on the write, even if that something was not arithmetic. The answer is a single boolean, flipped on every write, checked on every read. The boolean is called the dirty flag. When an input changes, the derived does not recompute. It flips the boolean to true. When somebody reads the derived, it checks the boolean. If true, it recomputes. If false, it hands back the stored answer. The write did one unit of the cheapest possible work. The read did the expensive work, but only if the boolean said it had to.

The second question: how does the derived know which values are its inputs in the first place, given that it has not subscribed to anything yet? The answer is that the very first read is special. On the first read, the derived runs its computation, and while that computation reads its inputs, those inputs notice the derived and add it to their private lists of dependents. From that moment on, the derived is wired in. Future writes to those inputs will flip its dirty flag. But the wiring itself only happens because the first read forced the computation to run, and the computation, by reading its inputs, introduced the derived to them.

So the full picture, before any code: a derived holds a stored answer, a dirty flag, and a function. The function defines how the answer is produced from inputs. The dirty flag says whether the stored answer can still be trusted. The stored answer is the last value the function produced. On the first read, the function runs, the inputs learn the derived exists, and the answer is stored. On every later write to an input, the dirty flag flips to true and nothing else happens. On every later read, if the flag is true the function runs again and the flag clears; if the flag is false the stored answer is handed back as-is.

## The proof, because the proof is the point

Here is a derived with a counter inside it, so we can watch how many times the computation actually runs. The dependency is a signal called price.

```js
let runs = 0;
const price = makeSignal(3);

const total = makeDerived(() => {
  runs = runs + 1;
  return price.read() * 100;
});
```

Now we change the price twice, without ever reading the total.

```js
console.log("before anything, runs:", runs);   // before anything, runs: 0
price.write(9);                                 // dependency changes
price.write(12);                                // dependency changes again
console.log("after two writes, runs:", runs);   // after two writes, runs: 0
```

Two writes. Zero computations. The derived did not lift a finger. The inputs changed, and the derived ignored them, in the only sense that matters: no arithmetic happened.

Now read it once.

```js
console.log("first read:", total.read(), "runs:", runs);   // first read: 1200 runs: 1
```

One read. One computation. The function ran, produced 1200, and stored it.

Now read it again, immediately, with no change in between.

```js
console.log("second read:", total.read(), "runs:", runs);  // second read: 1200 runs: 1
```

Second read. Same answer. Still only one computation. The second read did zero work. It read the stored answer and gave it back.

This is the laziness made visible. The two writes were ignored at the cost of two boolean flips. The first read paid for the arithmetic. The second read was free. A derived that nobody reads is free forever, no matter how many times its inputs change.

## Why the dirty flag exists, said without the jargon

The dirty flag is the bridge between the write that was ignored and the read that was not. Without it, the derived would have no way to know, at the moment of reading, whether its stored answer was still good or whether an input had changed underneath it. With it, the derived does not need to remember what its inputs were, or what values they held, or how many times they changed. It needs to remember exactly one thing: did anything happen since I last computed. That is a boolean. That is the whole bridge.

The word dirty is unfortunate, and it carries baggage from a different mechanism entirely. In some older frameworks, dirty meant a slow loop that compared every watched value to its previous value, over and over, until nothing changed. That is not this. Here, dirty is a single yes-or-no bit attached to one derived. It means, exactly and only: this stored answer might be stale, recompute before returning it. Nothing more. If the word were coined today it would be called stale. It was not coined today.

## When to use a derived, and when not to

The rule of thumb is one sentence. If the thing you are writing is an answer, use a derived. If the thing you are writing is an action, use an effect instead.

A computed total is an answer. A filtered list is an answer. A formatted date is an answer. A flag that says whether a form is valid is an answer. All of these follow from other values, all of them are read by something, none of them are set by hand. They go in a derived.

A logging statement is an action. A network fetch is an action. Focusing an input is an action. Calling a third-party library is an action. All of these reach out into the world and do something, none of them produce a value that something else reads. They go in an effect.

The smell that tells you the choice was wrong is always the same. If you wrote an effect and then had to invent a second piece of state just to hold what the effect produced, you wanted a derived. If you wrote a derived and its body reaches out into the world instead of returning a value, you wanted an effect.

## The cartoon, retired

The derived is not asleep, and it does not have clothes, and it does not make notes. It is a stored answer, a dirty flag, and a function, sealed inside a closure. On the first read, the function runs and the inputs learn the derived exists. On every later write to an input, the dirty flag flips and nothing else happens. On every later read, the function runs only if the flag is up, and the stored answer is returned either way.

That is the whole mechanism, and it is the mechanism underneath every computed value in modern web frameworks. The laziness is the point. The laziness is what stops a thousand derived values across a complex screen from recomputing on every keystroke. The laziness is what lets a derived in a collapsed panel cost nothing while the panel is closed, and snap to correctness the instant the panel opens and somebody reads it.

A derived is a value that will not get out of bed until somebody knocks. That was the cartoon. The mechanism is the reason the cartoon was true.
