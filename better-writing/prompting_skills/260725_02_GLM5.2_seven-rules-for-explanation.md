# The Seven Rules (for technical explanation that does not lose the reader)

**Date:** 2026-07-25
**Author:** GLM-5.2
**Origin:** distilled from the user's critique of `01_GLM5.2_explanation_derived.md`, where four failure modes appeared pervasively despite the prior skill's bans: meta-narration about the writing, missing technical scaffolding, hanging references that withheld key information, and false equivalences that asserted identities the mechanism does not have.
**Status:** standalone. Focused on seven rules, each with concrete bad/good pairs so the rule is operational. Does not reference the prior cartoon-first skill; the two can coexist, and the prior file is retained as fallback.
**When to use:** any technical explanation of a mechanism with named parts. Particularly load-bearing for hyper-complex interconnected concepts, where the failure modes below are most damaging.

---

## Rule 1. No meta-narration

Never announce a writer's decision, never narrate pacing, never tell the reader what you are about to do or have just done. The reader does not need to know the writer's editorial choices. Those choices are felt through the structure of the text, not stated by it. If a sentence is about the text itself, cut it.

**Bad.**
> That explanation left one thing out on purpose.
> We will build the wire between them one step at a time, and we will not introduce a third thing until the wire between these two is solid.
> Let us restate the structure we have built so far.
> We will slow down here, because this is where it gets tricky.
> Now we turn to the question of how the wire is built.

**Good.**
> One thing is still missing: how the derived finds out that an input changed.
> The wire is built during total's first read.
> Price's list holds markDirty. Total's list holds the effect.
> The first read is the moment total's inputs learn total exists.

The test: delete the sentence. If the subject loses nothing and only the writer's narration of their own process disappears, the sentence was meta-narration. Cut it.

---

## Rule 2. No register-labeling or self-apology

Never label the text's own register, quality, or difficulty. Never call the text cartoonish, simple, slow, technical, careful, or deliberate. Never apologize for or justify the pacing, the density, or the choice of framing. Discuss only the subject.

**Bad.**
> Like all good intuitions, it is wrong in every detail and right in every important way.
> This is the hardest part of the whole mechanism to hold in your head.
> That slowness is the point.
> The word dirty is unfortunate, and it carries baggage from a different mechanism entirely.
> This is a cartoon simplification, but it captures the essence.

**Good.**
> The derived is lazy about its own existence.
> The wire is an entry in a list.
> The dirty flag is a single boolean that means the stored answer might be stale.

The test: would the sentence survive a reader who did not know they were reading a lesson? If it would not, because it is commenting on the lesson's nature, cut it.

---

## Rule 3. Definitions are chained on demand, then settled

Technical terms are introduced as a chain, each defined as one step from the last, at the moment the reader would ask why for it. Once a term is defined, it is settled vocabulary. Never re-justify it, never re-explain what kind of thing it is, never remind the reader it is a function or a closure or a variable. Define once, use thereafter.

**Bad.**
> markDirty, which is a function inside the closure of the derived (remember, a closure is a function that can return inner functions which keep their scope), is the function that flips the flag.
> So when markDirty, this inner function we defined inside the closure, runs...
> The markDirty function, an inner function of the derived's closure, does two things.

**Good.**
> A derived is a kind of Signal. A Signal is a closure: a function that can define inner functions, and those inner functions keep access to the variables of the function that created them. The derived's markDirty is one such inner function. It flips the derived's dirty flag.
> When markDirty runs, two things happen.
> markDirty does two things.

The chain is delivered once, in the order the reader asks why. After that, the chain is settled and the prose uses the terms without re-introducing them.

---

## Rule 4. No hanging references

Every named thing gets its purpose and its reason for existing at the moment it is named. Never announce a thing's existence while deferring its meaning. Never say "we will discuss this later." If a thing cannot be explained now, it is not named yet.

**Bad.**
> A Signal has two properties: a value, and a list (we will discuss the list later).
> Both the derived and the price have an actual value and a list.
> This function has two parts: the reader (which we cover now) and the cache (which comes later).

**Good.**
> A Signal holds a value, and it holds a list of the functions that have read that value. The list exists because when the value changes, the Signal needs to know which functions to re-run. Those functions are on the list because they were caught reading the value, from inside an Effect. The Effect's purpose is to run a function in a way that lets the Signals it reads learn the function's name, so they can add it to their own list.
> A Signal holds a value and a list. The list records every function that has read the value, so the Signal knows who to notify when the value changes.

The test: read the sentence that names the thing. Does the reader now know what the thing is for and why it has to exist? If not, the reference is hanging. Either explain it now, or do not name it yet.

The one exception: a forward reference is allowed when the forward reference is itself the key idea. "markDirty, whose entire job is to flip the dirty flag" is fine, even though the mechanism of flipping is unpacked later, because the job is the key idea and it has been stated. What is banned is naming a thing and deferring both its purpose and its mechanism.

---

## Rule 5. Definitions singular, names redundant

This is the resolution to a real tension. Connection density requires naming both endpoints of a connection every time, because pronouns and elisions do not survive across a connection. But re-defining a term every time it appears is noise. The split: a term is defined once, and named many times. The name is the handle the reader grabs. The definition is what the handle refers to, stated once and then assumed.

**Bad.**
> So when markDirty, which is the inner function that flips the flag, runs... and then markDirty, this flag-flipping inner function, calls the entries in the list...

**Good.**
> markDirty runs. markDirty calls every entry in total's own list. The list is empty in this example.
> Price's write function calls markDirty. markDirty is the same function that was dropped into price's list during the first read.

The name appears many times. The definition appears once. Restating the name is redundancy in service of grip. Restating the definition is noise.

---

## Rule 6. Restate the subject, never narrate the restating

This is the resolution to a second tension. Connection density requires repeating the accumulated structure at checkpoints, because the structure has to survive in working memory as a unit. But announcing the restating is meta-narration. The split: restate the subject matter directly, never narrate the act of restating.

**Bad.**
> Let us restate what we have so far.
> Before moving on, let me summarize the chain we have built.
> To recap, we have three things and two wires.
> Now that we have established all of that, here is the whole picture.

**Good.**
> The three things are price, total, and the effect. The two wires are price's list holding markDirty, and total's list holding the effect.
> Price's list holds markDirty. Total's list holds the effect. The effect reads total.
> One rule built both wires: when a thing is read, the reader goes into the thing's list.

The subject is restated. The restating is not announced.

---

## Rule 7. No false equivalence; allow honest vagueness

When simplifying for a beginner, it is permitted to be vague. It is never permitted to be precise-sounding and wrong. The line is between honest vagueness, which names a thing loosely enough that the loose name does not assert a false identity, and false equivalence, which asserts that two unequal things are equal by giving them the same name. Honest vagueness survives the moment the reader learns the real mechanism. False equivalence collapses in that moment, and when it collapses the precise reader concludes the writer never understood the material.

A beginner cannot tell the difference between honest vagueness and false equivalence. A precise reader can, immediately. The temptation is to write the false-equivalence version because it scans cleaner and the beginner will not object. Refuse the temptation. The honest-vagueness version costs one or two extra words. The false-equivalence version costs the trust of every reader who already knows the mechanism.

The test: does the sentence assert an identity (A is B, or A holds B) where the mechanism actually has a part-whole, stand-in, or wrapper relationship? If it does, the sentence is false equivalence. Insert the vagueness marker: A holds something from B, A holds a stand-in for B, A holds a wrapper around B, A holds a piece of B.

**Bad.**
> A Signal holds a value, and it holds a list of the functions that have read that value.
> Total's list holds the Effect.
> The derived's subscriber list holds the functions that depend on it.
> When the effect runs, it adds itself to the signal's list.

Each of these asserts an identity the mechanism does not have. The list does not hold the functions. It holds markDirty for a derived reader, or the effect's run wrapper for an effect reader. Those are stand-ins, pieces, wrappers. The functions themselves are never in the list. To say the list holds the functions is to assert an equality between the function and its stand-in, and that equality is false.

**Good.**
> A Signal holds a value, and it holds a list of something from each function that has read that value.
> Total's list holds a piece of the Effect, the Effect's run wrapper.
> The derived's subscriber list holds a stand-in for each function that depends on it.
> When the effect runs, it drops a wrapper around itself into the signal's list.

The vagueness markers (something from, a piece of, a stand-in for, a wrapper around) signal to the precise reader that the writer knows the full story and is choosing to abbreviate. They signal nothing in particular to the beginner, who was not going to query the exact identity of the list entry anyway. Both readers are served. The false-equivalence version serves only the beginner, and only until the mechanism is revealed.

The deeper principle: a simplification may remove detail, but it may not assert a falsehood. Removing detail is honest vagueness. Asserting that the removed detail did not exist, or that the simplified thing is identical to the precise thing, is false equivalence. The first is permitted. The second is forbidden, always, no exceptions, because it is the one simplification that cannot survive the reader learning more.

## How the seven rules interact

Rules 1 and 2 clear the text of writer-commentary. Rules 3 and 5 govern technical vocabulary: define once, chain on demand, name freely, never re-justify. Rule 4 governs when a thing may be named: only when its purpose can be stated. Rule 6 governs how repetition is done: by restating subject matter, never by narrating the restating. Rule 7 governs the honesty of every simplification: vague is allowed, false is not.

The deepest tension, named so the writer does not trip on it: rules 5 and 6 both demand redundancy, while rules 1 and 2 demand the absence of commentary. The line is always the same. Redundancy in service of the subject (re-naming endpoints, restating structure) is required. Redundancy in service of the writer (re-justifying decisions, narrating pacing, labeling register) is forbidden. If the sentence is about price, total, markDirty, or the wire, it is probably fine. If the sentence is about the text, the writer, or the reader's experience of the text, cut it.

A second tension, between rules 2 and 7: rule 2 forbids labeling the text's register as cartoonish or simple, and rule 7 permits honest vagueness. These do not conflict. Rule 2 is about commentary on the text. Rule 7 is about the content of the text. A sentence may be honestly vague without announcing that it is vague, the same way a sentence may be a cartoon without labeling itself a cartoon.

## The one-sentence version

Discuss only the subject. Define each technical term once, in a chain, at the moment it is needed, and then use it freely without re-justifying it. Name every endpoint of every connection every time, but never re-define. Never announce a writer's decision, a pacing choice, or a register. Never name a thing without stating its purpose. Restate structure by restating the subject, never by narrating the restating. When simplifying, be vague rather than false: a simplification may remove detail, but it may never assert an identity the mechanism does not have.
