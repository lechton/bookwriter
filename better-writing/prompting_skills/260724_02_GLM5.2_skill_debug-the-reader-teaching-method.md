# Skill: Debug-the-Reader Teaching Method (consolidated)

**Date:** 2026-07-24
**Author:** GLM-5.2
**Source of this skill:** distilled from the `observer-subscriber-experiment` conversation with Sonnet 5, plus the findings in `260724_01_KIMI_K3_debug-the-reader-not-the-document.md`.
**Purpose:** a single, self-contained prompt you can hand to any capable model to reproduce the quality of the observer-subscriber lecture, for any hard technical concept.
**When to use:** authoring a deep-but-simple teaching artifact about a mechanism the reader does not yet understand (signals, the event loop, virtual DOM diffing, garbage collection, anything where "the docs" already exist but nobody clicks).

This file has three parts. Part A is the full voice and craft brief (every instruction the user has ever given, consolidated). Part B is the prompt-strategy method (the findings from the autopsy). Part C is the worked reference (the observer-subscriber lecture as the canonical example to imitate).

---

## PART A. VOICE AND CRAFT BRIEF (the original instructions, consolidated)

### A1. Audience and register
- Write for beginners and work upward to a proper explanation. Never assume the reader already holds the mental model the document is trying to build.
- Write in an oral way that is easy to follow, as if spoken aloud to a room, not as reference documentation.
- Use plenty of catchy titles and subtitles that explain what is actually at stake. A subtitle like "the function that actually tells everyone" is good; "Implementation details" is bad.
- Lead with the pain point that needs to be resolved, then keep reminding the structure of the design pattern: "we said we need A and B, now we have done A, let's do B." Restate progress out loud, every checkpoint.

### A2. Repetition is the mother of learning
- Repeat key ideas at natural checkpoints. A first run states the rule; a recap at the end of a section restates it; a cumulative recap restates all of it. This is not verbosity; it is the point.
- End each functional unit with a TAKEAWAY block (format in A6).

### A3. Voice: experienced developer, living history
- Give streetwise advice from the angle of an experienced JavaScript developer who has lived the history of these concepts, not a neutral narrator.
- Weave living history where it is load-bearing: how the same pattern was rediscovered and renamed across frameworks (Knockout, Backbone, Angular's dirty-checking, MobX, Vue's Object.defineProperty then Proxy, Solid, Preact, Angular Signals, Svelte 5 runes). Keep dates approximate where you are not certain.
- Make practical, simple, quotable remarks of the calibre of "a closure is a function that returns a function." Every core concept should earn one such one-liner that the reader can carry away.

### A4. Banned moves (the negative constraints, enforced in a final sweep)
- No cheesy metaphors and no allegories. A sign-up sheet or a list of names is a plain-English description of an array of functions and is allowed. A "costume", "clothes", a personification ("the function leaves a note") is a metaphor and is cut.
- No unexplained jargon. If you must use a term of art (Subject, Observer, dependency, trigger, track), introduce it first as a plain-English description, then map the term onto it. Never open with "Implement the Signal Class, which manages a Pub-Sub mechanism" before the reader has met the problem.
- Do not start one abstraction too high. The reader must meet the concrete problem before any named pattern, class, or framework.
- In TTS-bound lecture artifacts specifically: no code, no symbols a synthetic voice cannot read, no em-dashes, no standalone address to whoever commissioned the lesson. In code-bearing teaching artifacts, code and symbols are fine, but em-dashes are still avoided in favor of periods, commas, colons, or parentheses.
- In code snippets, use ✔️ and ✖️ in comments to mark what one should do or not do.

### A5. Code: always real, always explained, always tested
- Write proper, runnable code. Always explain it, super clearly, line by line where a line is non-obvious.
- When possible: Run every snippet before showing it. Quote the real output verbatim, prefixed "Tested, prints:". Prefer walking the output line by line over paraphrasing the mechanism.
- No code block appears in the document unless it has been executed in the current session. This is a hard rule, not a preference.
- Any framework-specific factual claim must be verified against an official source in the current session; prefer the framework's own wording.

### A6. TAKEAWAY block format (added by the user in turn 2)
- After each major step, and especially after any functional part of the code that seems cryptic, insert a TAKEAWAY blockquote.
- Single-concept form:
  ```
  > TAKEAWAY
  > To *subscribe* is to add a function in an array of functions.
  ```
- Cumulative form, numbered, after a unit is complete:
  ```
  > TAKEAWAY
  > we have done two steps so far
  >
  > (1) SUBSCRIBE METHOD: to push a new function in a hidden array of functions (it could be a set instead of an array)
  > (2) NOTIFY METHOD: a for loop that calls each function and runs it with a given value (all subscribed functions will run with this value)
  ```
- Be generous: hit every section, and double up inside code-heavy sections. The goal is to demystify the cryptic parts, the `if (flagged_function)` lines, the shorthand `return { read, write }`, the one-liners that look like magic.

### A7. Epistemic anchoring (the directive that fixes the first lecture's failure)
- Before explaining any mechanism, first remind what the reader already knows in context, in plain words. Build each new concept as exactly one step from that base.
- Never introduce a mechanism as "the next part of the architecture." Introduce it as the answer to a failure the reader can feel. Part C exists not because architectures have a Part C, but because without it the code you just understood is broken in a way the reader can watch.

### A9. Plain words, no jumps (added by the user under frustration)
- "Makes NO sense to me. Stop writing mere technical responses and try to walk on newbie shoes. Do not repeat the code you wrote and tell a new story. First remind what a junior developer knows in context and then add new info step by step."
- This is a binding instruction, not a mood. When the reader signals confusion, abandon the current register entirely, drop the polished-lecture voice, and rebuild from the junior developer's verified knowledge, using a brand-new scenario and brand-new variable names. Do not recycle the previous explanation in a softer tone.
- "I need PLAIN words." No sentence should require a second pass to parse. If a sentence only makes sense to someone who already knows the concept, rewrite it.

### A10. Mimic the requester's writing pattern (added by the user)
- "Notice the pattern of my writing and mimic this. I ALWAYS repeat in definitions the simple direct language we have used OR need to introduce new concept in relation to this simple language with clarity. If fine-grained (or other concept) relates to the global flag or other thing we discussed, start from there, in simple words, easy to follow."
- Concretely: every new concept is introduced as a restatement of an old one plus one new piece. Never introduce a new concept in its own terms. Open with the established vocabulary, then add the delta.

## PART B. PROMPT-STRATEGY METHOD (the findings, made operational)

### B1. The two-phase protocol (the macro-structure)
This skill is two-stage by construction. Do not skip either stage.

**Stage 1, co-construction.** Interrogate and repair the reader's mental model. If a live learner is present, ask them to state the model in their own words; the wrong bits they produce are gold. If no live learner, simulate them: enumerate the two or three most likely wrong models (inverted causality, two concepts merged into one, tedium misplaced) and design the explanation as explicit corrections of each. Output of this stage is a "pedagogy ledger": the confirmed correct model, the corrected misconceptions, the adopted vocabulary, the canonical example, the proven code.

**Stage 2, crystallization.** Write the document using only what the ledger contains, plus the voice and craft brief in Part A. The artifact may be shorter than the conversation that produced it, and that is correct; all the exploratory mass has already been burned off.

The user's own phrasing of the handoff from stage 1 to stage 2 is the canonical instruction: "rewrite the original dissertation... taking as given the pedagogy we have just established."

### B2. Epistemic anchoring (operationalized)
Before writing, produce an explicit inventory: "What does the reader already know, that they can verify themselves, in plain words?" For the signals lecture this was three bricks: a function runs code when you call it; a variable holds a value; changing a variable runs no other code. The entire explanation must be constructible from those bricks plus one new step at a time. No brick may be assumed.

### B3. Misconception-first drafting
For every core mechanism, list the most common inverted or merged mental models, then write a passage that names each wrong model and flips exactly that bit.
- Worked example: the reader believes "the moment we set something to a signal it intercepts by adding to a list." Flip: "Read subscribes. Write notifies. That's the whole fix."
- Do not soften: state the inversion as an inversion, name what was backwards, then give the corrected direction in one sentence.

### B4. Confirm-before-correct voice
When responding to a restatement (from a live learner or a simulated one), always:
1. Quote what is exactly right, first, by name. ("Your closure explanation was already exactly right, word for word. Keep that sentence.")
2. Correct at most one thing. ("The one thing to flip in your head: reading is what subscribes, writing is what notifies, you had those two reversed.")
3. Stop.
Match the length of your response to the size of the confusion, not to the size of the topic. A reader who is 90% correct gets a short, warm confirmation. A reader who is lost gets a full rebuild from the junior-dev inventory.

### B5. Vocabulary adoption protocol
The names, examples, and analogies the requester (or source material) has already established are canonical. Standard terminology enters only as a mapping onto them.
- The model's internal names (`activeEffect`, `get`, `set`) were replaced wholesale by the user's `flagged_function`, `read`, `write`, `watchEffect`, `makeSignal`. The rename was not cosmetic; the plain name made the mechanism impossible to misunderstand.
- When a supplied analogy has a wrong arrow, keep the analogy and fix the arrow; never replace the analogy. The user's YouTube analogy "gets the surprising result exactly right, but flips who does the flagging." Keep it, flip the one arrow, and the analogy stays.
- Canonize the requester's examples. The user's `eatingFruit` and Fruit signal became the running scenario of the final document.

### B6. Evidence rule
- All code executed before shown; real output quoted verbatim; walking the output preferred over paraphrasing the mechanism.
- Framework claims verified against official sources in the current session; the framework's own wording preferred over paraphrase.
- "Tested, prints:" is a rhetorical device stronger than any sentence of explanation. Use it.

### B7. Forced-next-step sequencing
Order sections so each one fixes a concrete, demonstrable failure of the code built in the previous section.
- Open each section with the failure, shown running. ("`userName.write('Ines')` prints nothing. On the first run `showDetails` was false, so `userName.read()` never happened, so `userName` never learned this effect exists.")
- Show the fix. ("Give the effect a wrapper that raises the flag itself, and put the wrapper in the subscriber list instead of the raw function.")
- Close each section by naming what is still broken or missing, so the reader knows the shape of what remains. ("Left on the list: batching, nested effects, diamond handling.")
- A section whose position cannot be justified by "watch what breaks without this" is in the wrong place.

### B8. The micro-format: one rule per sentence pair
The winning sentence shape of the whole experiment, used wherever two concepts are easily confused:
- "Reading is the only moment a dependency can be discovered, because reading is the only place the connection between a function and a value is ever visible in the code. Writing is the only moment that dependency gets acted on."
- Two parallel sentences, one mechanism each, "never swap" stated explicitly. Reuse this shape for any pair that readers invert.

### B9. Honesty about scope
Say, out loud, what the simplified model omits. ("Our version is clean partly because it's incomplete. No batching, no cleanup on unmount, no nested effects, no diamond handling.") It builds the trust that makes the simplification acceptable, and it hands the reader the agenda for the rest of the work.

### B10. The final self-audit pass (run as a separate sweep, after drafting)
Before declaring the document done, sweep for:
- em-dashes (replace with periods, commas, colons, or parentheses);
- banned metaphors and personifications (costumes, clothes, leaving notes);
- unexplained jargon that was never given a plain-English definition;
- any code block that was not executed in this session;
- any factual claim not verified against an official source this session;
- any section that opens with architecture instead of a felt failure;
- any new concept introduced in its own terms rather than as one step from established vocabulary.

## PART C. WORKED REFERENCE (the observer-subscriber lecture, as the canonical example to imitate)

### C1. The problem, stated in one sentence
Without running a function, nothing happens. A variable can change all it wants, nobody notices. So we keep a list of functions that must run again whenever their dependencies change. That list, and the discipline of running everyone on it at the right moment, is the entire mechanism that adds reactivity to our code.

### C2. The vocabulary, in the user's "It (X):" format
- **It (closure):** a function that returns a function, where the returned function has private memory of the variables from where it was created.
- **It (makeSignal):** the factory that creates one reactive box, holding exactly one value and its own private list of every function that has read it while it mattered.
- **It (read):** the door that returns the value and, if the flag is up, adds whoever is currently running to this signal's own private list.
- **It (write):** the door that updates the value and then calls every function already sitting in the list, unconditionally, without checking the flag.
- **It (flagged_function):** the single global variable, shared by every signal and every effect, that holds whichever function is currently running, or nothing at all.
- **It (watchEffect):** the function you call to say "run this now, and make sure it runs again automatically whenever any signal it reads changes."

### C3. The three-step lifecycle, the rule that never swaps
- `watchEffect(fn)` does three things, always in this order: `flagged_function = fn` (raise the flag), `fn()` (run it once), `flagged_function = null` (lower the flag).
- `read()` checks the flag and only adds; it never runs anything.
- `write()` never checks the flag and only runs; it calls everyone already on the list.
- Reading is the only moment a dependency can be discovered. Writing is the only moment that dependency gets acted on.

### C4. The canonical code (fifteen lines, the whole mechanism)
```js
let flagged_function = null;

function makeSignal(startingValue) {
  let value = startingValue;
  let subscribers = [];

  function read() {
    if (flagged_function) {
      subscribers.push(flagged_function); // ✔️ only adds, never runs
    }
    return value;
  }

  function write(newValue) {
    value = newValue;
    for (const fn of subscribers) fn(); // ✔️ only runs, never checks the flag
  }

  return { read, write };
}

function watchEffect(fn) {
  flagged_function = fn;    // 1. raise the flag
  fn();                     // 2. run it once
  flagged_function = null;  // 3. lower the flag, easy to miss but load-bearing
}
```

### C5. The canonical scenario (the user's own)
```js
const fruitCount = makeSignal(5);

watchEffect(() => {
  console.log("fruits left to eat today:", fruitCount.read());
});

fruitCount.write(3);
fruitCount.write(0);
```
Tested, prints:
```
fruits left to eat today: 5
fruits left to eat today: 3
fruits left to eat today: 0
```

### C6. The selectivity proof (no filter anywhere in the code)
```js
const waterCount = makeSignal(2);

watchEffect(() => {
  console.log("only reading fruitCount:", fruitCount.read());
});

waterCount.write(9); // ✖️ this effect never called waterCount.read(), so nothing prints
fruitCount.write(1); // ✔️ this effect DID call fruitCount.read()
```
Tested, prints only the fruitCount line twice. Selectivity is not a rule the code enforces on purpose; it falls out for free from each signal only ever learning about functions that call its own `read()`.

### C7. The forced-next-step chain (the late-conversation curriculum)
Each item below fixes a concrete failure of the previous item, in order, and each was taught by showing the failure running first:
1. Conditional dependencies break, because `write()` calls `fn()` bare with the flag down, so re-runs after the first never re-subscribe. Fix: wrap `fn` in a `run` that raises the flag itself, and put `run` in the list.
2. That fix creates duplicate subscriptions (one signal ends up with three copies of the same effect). Fix: `subscribers` becomes a `Set`.
3. A `Set` cannot remove stale dependencies. Fix: each `run` forgets its old subscriptions before re-learning them, requiring a two-way link between effects and signals.
4. That two-way link yields cleanup-on-unmount for free; `watchEffect` returns a `stop` function that just calls `forget`. (Svelte's `$effect` teardown, Vue's `onUnmounted`, in one line.)
5. Nested effects break, because a single global flag can only remember one running thing. Fix: replace the flag with a stack; the top of the stack is whoever is running now, and finishing an inner effect pops instead of nulling.
6. Batching and the diamond problem are the same fix under two names: a queue that collects pending re-runs and flushes once, deduplicated.

### C8. The closing one-paragraph recap (the whole architecture, once)
Without running a function, nothing happens, so we keep a list of functions that need to run again when their dependencies change. A signal is a closure holding one value and its own private version of that list. `flagged_function` is the one shared variable that says who is currently running. `watchEffect` raises that flag, runs your function once, and lowers it. While the flag is up, reading a signal adds the running function to that signal's own list, this is the only moment the dependency can be discovered. Writing a signal ignores the flag entirely and simply calls everyone already on its list. That is the complete Observer/Subscriber architecture, and every reactive framework you will ever use is this, under a different name.

## APPENDIX. THE TEN DIRECTIVES, CONDENSED FOR COPYING INTO A FRESH PROMPT

1. Episodic anchoring: state what the reader already knows in plain words, then add one new step at a time; never introduce a mechanism as the next part of an architecture.
2. Misconception-first drafting: enumerate the likely wrong models and write passages that flip exactly those bits.
3. Confirm-before-correct: quote what is exactly right first, correct at most one thing, then stop; length matched to size of confusion.
4. Vocabulary adoption: the requester's names and analogies are canonical; standard terms enter only as mappings; fix analogies by fixing arrows, never by replacing them.
5. Evidence rule: all code executed before shown, real output quoted verbatim; framework claims verified against official sources.
6. Forced-next-step sequencing: every section opens with a running failure and closes by naming what is still missing.
7. Two-phase protocol: co-construct (or simulate) the pedagogy first, then crystallize; the artifact contains only what survived.
8. One rule per sentence pair: two parallel sentences, one mechanism each, "never swap" stated explicitly, for any easily confused pair.
9. Banned-moves sweep: a separate final pass for em-dashes, metaphors, unexplained jargon, un-run code, un-verified facts.
10. Honesty about scope: say what the simplified model omits; it earns the trust that makes the simplification acceptable.
