# Lecture 49: Syncing Local Variables with Incoming Props

> INTERVIEW QUESTION | How do you initialize a reactive local variable that dynamically syncs with an incoming prop using Runes?


A common source of confusion when moving from legacy Svelte to Svelte 5 runes is how to handle a local variable that needs to initialize from an incoming prop, but also needs to stay in sync when that prop changes over time. 

If you pass a prop down to a child component and assign it to a **`$state`** rune — the rune used to declare reactive state — it will capture the *initial* value of that prop perfectly. However, if the parent later updates the prop, the child's `$state` variable will stubbornly hold onto the original value. The connection is severed the moment the child component is created.

To solve this, we rely on the **`$derived`** rune — a reactive declaration that automatically recalculates its value whenever its dependencies change.

### The problem with `$state`

When a component is instantiated, code inside the `<script>` block runs exactly once. 

```svelte
<script>
let { initialCount } = $props();
let count = $state(initialCount); // ✖️ reads initialCount **ONCE** during creation
</script>

<p>Count is: {count}</p>
```

In the example above, `count` is a completely independent variable. It took `initialCount` as its starting value, but it has no ongoing relationship with it. If the parent component changes `initialCount`, the child component will ignore the change, and `count` will not update.

### The solution: `$derived`

If you want a variable to dynamically sync with a prop, you declare it as derived state. Anything read synchronously inside a `$derived` expression is considered a **dependency** — a reactive value that Svelte watches for changes. When the dependency changes, the derived state is marked as **dirty** (meaning it's stale and needs recalculation) and will be updated automatically.

```svelte
<script>
let { post } = $props();
let likes = $derived(post.likes); // ✔️ creates a continuous, **REACTIVE** relationship
</script>

<p>Total likes: {likes}</p>
```

Because `$derived` expressions are re-evaluated when their inputs change, `likes` will always stay in sync with `post.likes`. Whenever the parent updates the `post` prop, `likes` recalculates.

### Overriding derived values for Optimistic UI

Historically, derived values were strictly read-only. You could not assign a new value to `likes = 5`. But starting in Svelte 5.25, you can temporarily override the value of a `$derived` variable by simply reassigning it (as long as you didn't declare it with `const`).

This is specifically designed for **optimistic UI** — a pattern where you update the user interface immediately before the server confirms the change, making the app feel lightning fast. 

Here is how it works in practice:

```svelte
<script>
let { post, like } = $props();
let likes = $derived(post.likes); // ✔️ derived from the **SOURCE** of truth (the prop)

async function onclick() {
	likes += 1; // 1. optimistic override: increment **LOCALLY** immediately

	try {
		await like(); // 2. tell the server to **SAVE** the change, re-deriving likes
	} catch {
		likes -= 1; // 3. rollback: if network request failed, **REVERT** the override
	}
}
</script>

<button {onclick}>🧡 {likes}</button>
```

When you write `likes += 1`, you are temporarily overriding the derived value. When the parent eventually passes down a new `post` object with updated likes, the `$derived` rune recalculates, and the override is washed away by the new source of truth.

### Summary

If you need a local variable that dynamically syncs with an incoming prop, do not use `$state`. Use `$derived`. And if you need to let the user temporarily update that value before the parent data catches up, you can safely reassign the derived variable.

## Beyond the basics

> **Frequency Rating System**
> ★★★ = Very common gotcha / pattern
> ★★☆ = Common gotcha / pattern
> ★☆☆ = Niche / Advanced pattern

### ★★★ Two-way prop sync uses `$bindable`

The `$derived` pattern above is one-way (parent → child). When the child must also push changes back up to the parent — a text input bound to a parent-owned string, a checkbox toggling parent state — declare the prop with `$bindable()` and use `bind:text` in the parent. The Svelte docs are explicit: *"don't mutate props. Either use callback props to communicate changes, or — if parent and child should share the same object — use the `$bindable` rune."*

```svelte
<script>
let { text = $bindable('') } = $props(); // ✔️ enables two-way data **FLOW**
</script>
```

### ★★☆ Multi-statement derived values use `$derived.by`

The `$derived(expr)` form takes a single expression. If your transform needs a loop, an intermediate `let`, or a `try/catch`, switch to `$derived.by()`. Under the hood `$derived(expr)` is exactly equivalent to `$derived.by(() => expr)`; `.by` exists only for multi-statement bodies.

```svelte
<script>
let formatted = $derived.by(() => {
	let str = text.trim(); // ✔️ allows complex **LOGIC** inside the derivation
	return str.toUpperCase();
});
</script>
```

### ★☆☆ Editable-and-syncing local drafts use `$effect`

When the child must own its own edits (a form draft the user is typing into) but also needs to re-sync when the parent hands down a new prop, the pattern is `$state(prop.value)` combined with `$effect()`. Use this sparingly — `$effect`-driven sync can create loops if you write back to the same signal you read (see Lecture 21). Default to `$derived` first; reach for this only when editability and continuous sync are both required.

```svelte
<script>
let { user } = $props();
let draft = $state(user.name);

$effect(() => {
	draft = user.name; // ✔️ carefully syncs **UPSTREAM** changes into local draft
});
</script>
```

### ★★★ Destructuring a prop is a one-shot snapshot

`let { title } = $props()` reads `title` once, at component setup. Later changes to the parent's prop do not flow into the destructured `title` variable. This is the same JavaScript-level gotcha as destructuring a `$state` proxy (see Lecture 50). If you need ongoing reactivity, read through the props object: `{title}` in the template, or `let p = $props()` and then `p.title`.

```svelte
<script>
let { title } = $props(); // ✖️ severs the **REACTIVE** connection to the prop
</script>
```

### ★★☆ Derived expressions must be side-effect-free

The `$derived` body may not mutate state. Svelte disallows this because derived values must be pure functions of their inputs — side effects belong in `$effect`, not `$derived`. If your "sync" needs to write to another signal as part of its work, you are writing an effect, not a derived.

```svelte
<script>
let count = $state(0);
let doubled = $derived.by(() => {
	count += 1; // ✖️ mutating state here is a **COMPILE ERROR**
	return count * 2;
});
</script>
```

### ★☆☆ Passing proxied data to external libraries

A `$derived` whose source is a `$state` proxy returns a proxied value. Some libraries (structured clone, certain chart libraries) trip over Proxy objects. Wrap the handoff with `$state.snapshot(derivedValue)` to pass a static deep clone instead.

```svelte
<script>
let data = $derived(post.metrics);

$effect(() => {
	new Chart($state.snapshot(data)); // ✔️ passes a raw, **CLONED** object
});
</script>
```

### ★★★ Don't conflate the three syncing runes

Picking the wrong one is the most common source of "why isn't my UI updating" bugs in Svelte 5 components that receive props.

```svelte
<script>
let { data } = $props();
let a = $state(data); // ✖️ initializes once, then goes **DEAF**
let b = $derived(data); // ✔️ listens forever, but is **READ-ONLY**
let { c = $bindable() } = $props(); // ✔️ listens forever AND is **WRITABLE**
</script>
```
