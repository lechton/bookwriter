3. She updates her account profile from Elena Vance to her pen name Elena Rostova.
4. Why does the screen still show Elena Vance in three places?

### The Imperative DOM Hunt vs Declarative React
In plain web development, a webpage is an HTML document loaded into browser memory. The browser parses that HTML into an object tree called the **Document Object Model (DOM)**. When you write plain JavaScript, your code talks directly to this tree. You search for specific nodes, read their current contents, and overwrite their values.

As an application grows, user data rarely stays in a single location on screen. A subscriber's name appears in the top navigation bar, the article byline, the comments drawer, and the checkout receipt. In plain JavaScript, you must write manual search-and-replace instructions for every single appearance. If your script forgets even one element, the screen falls out of synchronization with memory. This failure is called **state drift**, and it leads to confusing bugs that erode user trust.

```js title="Historical Pattern"
function updateReaderName(newName) {
  document.getElementById('user-banner').textContent = newName; // 1. manual lookup for banner
  document.getElementById('user-avatar').title = newName;       // 2. manual lookup for avatar
  document.querySelector('.welcome-msg').textContent = newName; // 3. manual query by class
} // 4. unhandled '#sticky-checkout' causes **STATE DRIFT**
```

This manual hunting is the essence of **imperative programming**. What is **imperative programming**? In imperative code, you issue step-by-step commands instructing the browser how to mutate each individual node. You tell the engine: find this node, update its text, find that image, update its attribute. When you add a new checkout banner next week, you must remember to update this function. If you miss it, the new banner displays stale data forever.

```html-figure src="figures/01-01-manual-vs-declarative.html" caption="Imperative DOM queries fail as the interface expands. Forgetting even one query creates state drift. In React, all components derive from shared data automatically."
```

What is **declarative UI**? React draws the line between two models of web development: **imperative DOM scripting**, controlled by manual step-by-step commands, and **declarative UI**, controlled by React from a single state description. In normal JavaScript, you command the browser: find this node, change its text, find that image, change its title. In declarative React, you describe what the user interface should look like for any given data: you write your component once, hand it the data, and React calculates which DOM nodes must change. The law of declarative UI: React updates the DOM to match your component description. You never touch physical DOM nodes by hand.

> [!WILD]
> **What is the problem with updating the physical DOM?**
> Can you imagine a subscriber updating her account profile on The National Times? Elena Vance changes her name to Elena Rostova. Her name lives in ten separate places across the screen. In plain JavaScript, you must hunt down each and every element by hand. You write query after query. If you miss just one place, the old name remains on screen. This is the core problem of **imperative programming**: it is **imperative** to hunt down and update every DOM node manually, time and time again. This manual hunt leads to silent failures and broken screens. React solves this friction with **declarative** components: you declare your markup once, and React synchronizes the entire **physical DOM** automatically using its in-memory **virtual DOM**.

### Components as Reusable Blueprints
In plain HTML, you structure documents using native tags like the `<header>`, `<article>`, and `<button>` elements. However, native HTML tags know nothing about your application logic or subscriber data. Traditionally, developers copied and pasted HTML markup across separate templates. Then, they attached external JavaScript scripts to add interactive behavior. This separation split structure from logic, producing fragile codebases where renaming a CSS class broke JavaScript event listeners.

To solve this fragmentation, React unifies markup, style, and logic into a single cohesive structure. This mechanism is called a **component**. What is a **component**? A component is a self-contained, reusable JavaScript function. It accepts input data called **props** (short for properties). It returns markup describing a piece of the user interface using JSX syntax. In React, every component function name must start with a capital letter. **Capitalization** is a strict compiler requirement: the component `<SiteHeader />` tells React to invoke your custom JavaScript function, while the lowercase `<header>` element tells the browser to create a built-in DOM node.

```jsx title="ReaderGreeting.jsx"
export default function ReaderGreeting({ readerName }) {
  return <h2>Welcome back, {readerName}</h2>; // curly braces open live JavaScript execution
}
```

The component `ReaderGreeting` receives its input data through a single parameter called **props**. Rather than writing `props.readerName` throughout the function body, the signature uses JavaScript **object destructuring** directly inside the parentheses. This unpacks the prop `readerName` straight into a local variable. Inside the markup, the curly braces around the prop `readerName` establish an **evaluation window**. This window steps out of static HTML structure and into live JavaScript execution. It projects the current value of the prop `readerName` directly into the heading text.

> [!KEY]
> A component is a blueprint, not a building. When your component function executes, it does not construct physical DOM nodes; it returns a lightweight description of what the screen should look like, and React constructs the DOM nodes for you.

Components can be **nested** inside one another like building blocks. A top-level parent component coordinates layout and passes data downward, while focused child components render individual sections. To see this in action on The National Times, we organize our site header into three distinct files: (a) The parent component `SiteHeader.jsx` acts as the orchestrating container. (b) The child component `ReaderGreeting.jsx` renders the personalized welcome message. (c) The child component `SubscriberInfo.jsx` displays the subscriber tier details. Both child components receive the subscriber's name through the prop `readerName` passed directly from their parent.

### Let's Design a Practical Example SiteHeader ReaderGreeting
Let us build the newsroom site header for The National Times. Our layout consists of a parent container `SiteHeader.jsx` and two child components: `ReaderGreeting.jsx` and `SubscriberInfo.jsx`. Both children must display the same logged-in reader identity without querying the DOM.

```components title="national-times - Rendered UI Canvas"
SiteHeader.jsx | none | header
  ReaderGreeting.jsx | readerName={currentReader} | card | [badge: Logged In]
  SubscriberInfo.jsx | readerName={currentReader} | badge | [badge: Premium Member] ;; [button: Account Settings]
```

```files title="national-times: File Explorer"
src/

  components/
    SiteHeader.jsx | boundary | Orchestrates header layout and passes reader identity downward
    ReaderGreeting.jsx | child | Renders personalized welcome heading using props
    SubscriberInfo.jsx | child | Renders subscriber tier badge synchronized with reader identity
```

### Step 1: First, we construct the parent container SiteHeader.jsx
In the component `SiteHeader`, we declare the logged-in reader's name in a single constant: `currentReader`. The parent component decides what data both child components need before we write their code. It mounts the component `<ReaderGreeting />` and the component `<SubscriberInfo />`.

```jsx title="SiteHeader.jsx" startLine="1" continues="bottom"
import ReaderGreeting from './ReaderGreeting.jsx';
import SubscriberInfo from './SubscriberInfo.jsx';
export default function SiteHeader() {
  const currentReader = 'Elena Rostova'; // **CODE LOGIC:**<br>Single source of truth for logged-in identity
  return (
    <header className="site-header">
      <ReaderGreeting readerName={currentReader} /> {/* **DATA FLOW:**<br>Passes reader name downward as prop */}
      <SubscriberInfo readerName={currentReader} /> {/* **DATA FLOW:**<br>Shares same reader identity with sibling */}
```

Notice the prop binding `readerName={currentReader}`. The left side names the prop expected by the child component, while the right side supplies the parent's live variable inside curly braces. Mind you, placing all header markup inside this single parent function is tempting for small demos. However, splitting greeting logic and subscriber status into focused child components allows each section to evolve independently. The parent owns the data and passes props downward to its children.

### Step 2: Next, we build the personalized child ReaderGreeting.jsx
We now create the child component `ReaderGreeting.jsx` to receive and display the reader's name. The function signature uses parameter destructuring to unpack the prop `readerName` passed by the component `SiteHeader` in Step 1.

```jsx title="ReaderGreeting.jsx"
export default function ReaderGreeting({ readerName }) { // **CODE LOGIC:**<br>Destructures readerName directly from props
  return (
    <div className="reader-greeting">
      <h2>Welcome back, <span className="reader-name">{readerName}</span></h2>
    </div> // **DATA FLOW:**<br>Renders live readerName inside JSX evaluation window
  );
}
```

Inside the markup, the curly braces around the prop `readerName` project the value straight into the `<span>` element. What would happen if the component `ReaderGreeting` queried the DOM directly using `getElementById`? The component would crash if rendered before the element exists in the DOM, or scrape stale text from an unrelated page. By receiving data strictly through props, the component `ReaderGreeting` owns zero DOM lookups and zero side effects. Data flows strictly downward from parent to child through props.

### Step 3: Then, we declare the subscriber tier child SubscriberInfo.jsx
We now create the second child component: `SubscriberInfo.jsx`. This component also receives the prop `readerName` from the parent container `SiteHeader.jsx`. Both child components now share the exact same source of truth in memory.

```jsx title="SubscriberInfo.jsx"
export default function SubscriberInfo({ readerName }) { // **CODE LOGIC:**<br>Reads readerName to verify active status
  return (
    <div className="subscriber-info">
      <span className="badge">Premium Member</span>
      <span className="reader-meta">Subscribed as {readerName}</span>
    </div> // **DATA FLOW:**<br>Synchronizes badge label with parent reader identity
  );
}
```

What would happen if the component `SubscriberInfo` maintained its own separate copy of the reader's name in a global variable? If Elena updated her profile, the greeting would display Elena Rostova while the badge displayed Elena Vance. Because both children derive their values from the parent variable `currentReader`, changing that string updates both components in the exact same render. Sibling components stay synchronized by receiving props from a common parent.

### Step 4: Finally, we seal the header boundary with the live status indicator
We resume the component `SiteHeader.jsx` where Step 1 paused. We add a newsroom edition pill and an account button.

```jsx title="SiteHeader.jsx" startLine="7" continues="top"
      <div className="header-actions">
        <span className="edition-pill">National Edition</span>
        <button className="account-btn" type="button">Account Settings</button>
      </div> {/* **CODE LOGIC:**<br>Terminal controls completing the masthead boundary */}
    </header>
  );
}
```

The `<button>` element and the `<span>` element are terminal UI controls that complete the masthead interface. In plain JavaScript, adding an interactive button requires attaching an event listener with `addEventListener`. In React, interactive elements remain declarative parts of the component hierarchy. The parent container closes its return statement and exports a complete, self-contained header.

### Lessons from the Experiment: Naive Expectation vs Reality
Now that our site header is complete, let us review the architectural roles of each component in our hierarchy.

```component-code title="Summary: The Logic of Nested Components"
SiteHeader.jsx | none | parent | [role: The **parent component** coordinates the newsroom masthead layout. It owns the **reader identity** in a single variable. It actively passes that data downward to two child components: **ReaderGreeting** and **SubscriberInfo**. Notice that neither child queries the DOM. Why? Because the parent supplies their data through explicit props.]
  ReaderGreeting.jsx | readerName={currentReader} | card | [role: This is a **child component**. It receives the **`readerName` prop** from the parent container. It unpacks the name using **object destructuring** and renders it inside an evaluation window `{readerName}`. Notice it owns **zero DOM lookups** and **zero state**. It is a pure presenter of greeting text.]
  SubscriberInfo.jsx | readerName={currentReader} | badge | [role: This is a **sibling child component**. It receives the exact same **`readerName` prop** as ReaderGreeting. Notice that both siblings share the same data without communicating directly with each other. Why? Because React enforces **one-way data flow** downward from the common parent.]
```

When developers transition from plain JavaScript to React, their naive expectation is to treat components as simple HTML templates with embedded DOM queries. They expect to write `document.querySelector` to update user greetings when account data changes. What the experiment showed is that React completely eliminates manual DOM queries: the parent holds data in memory, passes it downward through props, and React updates all matching elements on screen simultaneously.

What would happen if the component `SiteHeader` did not split greeting and subscriber details into child components, and instead hardcoded a monolithic HTML structure in one file? If you merged all markup and styling into one monolith, any design change to the subscriber badge would force you to re-test the greeting and navigation logic. Worse, you could never reuse the component `ReaderGreeting` on the mobile edition without copy-pasting markup. By separating concerns into child components, the component `ReaderGreeting` owns zero layout knowledge and zero subscriber logic.

This separation gives you two concrete superpowers:
1. If tomorrow you replace the greeting styling with a localized banner, you touch zero lines of subscriber badge code.
2. If you redesign the subscriber tier badges, you touch zero lines of greeting code.

### Glossary
- **Component**: A self-contained, reusable JavaScript function that accepts props and returns a description of the user interface using JSX.
- **Declarative UI**: A programming paradigm where developers describe what the UI should look like for any given data, and the framework automatically updates the DOM to match.
- **Imperative DOM Scripting**: A programming approach where developers write manual step-by-step instructions to find, create, and mutate physical browser DOM elements.
- **Props**: Short for properties; a single JavaScript object passed from a parent component to a child component to supply input data.
- **JSX Evaluation Window**: The curly braces `{}` syntax inside JSX that steps out of static markup and evaluates a live JavaScript expression.

### Summary

**The Declarative Component Foundation**

The transition from imperative DOM scripting to declarative React represents a fundamental shift in how user interfaces are built, synchronized, and maintained.

❒ Core Architectural Concepts

1. **Declarative Synchronization vs Manual DOM Hunting**: In plain JavaScript, updating the screen requires finding and mutating physical DOM nodes by hand, which inevitably causes state drift as the app grows.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) React inverts this model: you describe the interface as a function of data, and React calculates the required DOM updates.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) You never touch physical DOM nodes with `document.getElementById` or `document.querySelector` in routine component code.

2. **Components as Reusable Blueprints**: A component is a JavaScript function whose name starts with a capital letter and whose return value is JSX markup.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Capitalization is mandatory: the component `<SiteHeader />` invokes a custom React component, while the `<header>` element creates a native browser DOM element.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Components compose together into a tree, allowing complex user interfaces to be assembled from small, focused building blocks.

3. **Unidirectional Props Flow**: Data flows strictly downward from parent components to child components through props.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) A child receives props as an immutable input object, commonly unpacked using parameter destructuring.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Sibling components share data by lifting that data into their nearest common parent, ensuring all siblings stay synchronized.

➔ NEVER query or mutate physical DOM nodes with `document.querySelector` or `textContent` to update component UI.
➔ ALWAYS capitalize component names so React distinguishes custom components from native HTML elements.
➔ IF two sibling components need the same piece of data, THEN pass that data downward as props from their common parent.

**DO THIS:** pass data downward through props and render with JSX evaluation curlies

```jsx right
export default function SiteHeader({ readerName }) {
  return <header><h1>The National Times</h1><span>{readerName}</span></header>;
}
```

**DO NOT DO THIS:** query physical DOM nodes by ID to update user interface text

```jsx wrong
export default function SiteHeader() {
  const name = document.getElementById('user-name').textContent;
  return <header><h1>The National Times</h1><span>{name}</span></header>;
}
```
