### The Tree Position Rule

Developers often think of state as living inside the component function instance. Under this mental model, switching views or unmounting should destroy local state, while rendering the same component elsewhere should carry its state along. Why does React preserve state between two seemingly different renders at the same position, while resetting state when tree structure changes?

In React, **state is held in internal Fiber nodes, tied directly to the component's position in the UI tree**, not inside the function itself. When a re-render occurs, React compares the new tree to the old tree. If the **same component type** is rendered at the **exact same position**, React retains the existing Fiber node and preserves all of its state!

If the component type at that position changes (for example, replacing `<StaffReview />` with `<FreelanceReview />`), or if the tree hierarchy changes (such as wrapping a child inside a new `<div>`), React destroys the old Fiber node, unmounts the component, and discards all associated state.

```jsx title="Tree Position Rule in Action"
// PERSISTS: Same component type at same position; state is preserved!
{isStaff ? <ReviewScore isStaff={true} /> : <ReviewScore isStaff={false} />}
// RESETS: Different tree position/structure; state is destroyed!
{isStaff ? (
  <div><ReviewScore isStaff={true} /></div>
) : (
  <section><ReviewScore isStaff={false} /></section>
)}
```

Why does conditional rendering with ternary preserve state? To React, JSX produces a virtual tree. In `{isStaff ? <ReviewScore ... /> : <ReviewScore ... />}`, the parent element has a single child at position 0. In both branches, that child has the exact same component type: `ReviewScore`. Because the position and type are identical, React assumes it is the same logical component and preserves its state across toggles! Key terms: **virtual tree position**, **ternary position equivalence**, **fiber matching**, **branch reconciliation**.

### Resetting State with Keys and the Nested Definition Trap

We understand why React preserves state at the same position. How do you tell React that two components at the same position are logically distinct and must have completely separate state?

The standard React mechanism to distinguish components at the same tree position is the **`key` attribute**. When you assign different keys (`key="staff"` vs `key="freelance"`), React treats them as two completely distinct entities. Switching the key causes React to unmount the old component, discard its state, and mount a brand-new component with fresh state.

A catastrophic beginner mistake is **nesting a component definition inside another component function**: `function Parent() { function Child() { ... } }`. On every parent re-render, JavaScript re-creates `Child` as a brand-new function reference. React sees a completely different component type at that position, wiping out child state and DOM focus on every single keystroke! Component definitions must **always be declared at top-level module scope**.

```jsx title="Keys vs Nested Function Trap"
// RIGHT: Unique keys force React to reset state on switch:
{isStaff ? <ScoreCard key="staff" /> : <ScoreCard key="free" />}
// WRONG: Defining component inside parent wipes state on EVERY render!
function BrokenParent() {
  function NestedInput() { const [v, setV] = useState(''); return <input ... />; }
  return <NestedInput />;
}
```

Can keys also preserve state when list items reorder? Keys provide a persistent identity. In a list, assigning `key={item.id}` tells React: "This specific Fiber node belongs to item #42." If the array is sorted, filtered, or prepended, React moves the existing Fiber node and its state to the new position, instead of mistakenly rebinding item #42's state to item #99! Key terms: **list identity preservation**, **stable key**, **reorder tracking**, **fiber relocation**.

It embeds `ReviewToggle.jsx` to switch modes and `ReviewScore.jsx` (which holds a score counter). By providing distinct keys, it ensures switching modes cleanly resets the review score. ### Step 1: First, we construct the parent container ReviewSwitcher.jsx

The parent container tracks active `mode` and passes unique keys to `ReviewScore`. The parent must demonstrate that `key={mode}` forces state reset between modes.

```jsx title="ReviewSwitcher.jsx"
import { useState } from 'react';
import ReviewToggle from './components/ReviewToggle.jsx';
import ReviewScore from './components/ReviewScore.jsx';
export default function ReviewSwitcher() {
  const [mode, setMode] = useState('staff');
  return <div className="review-box"><ReviewToggle mode={mode} onToggle={setMode} /><ReviewScore key={mode} mode={mode} /></div>;
}
```

Step 1 establishes keyed identity: Look at line 6: `<ReviewScore key={mode} mode={mode} />`. When `mode` changes from `'staff'` to `'freelance'`, React sees a new key, tears down the old score card, and mounts a fresh one with initial score 0. We will build `ReviewToggle` next in step 2.

### Step 2: Next, we declare the toggle child ReviewToggle.jsx

Step 1 passed `mode` and `onToggle` to `ReviewToggle`. The child component must render buttons allowing the user to switch modes.

```jsx title="ReviewToggle.jsx"
export default function ReviewToggle({ mode, onToggle }) {
  return (
    <nav className="review-toggle">
      <button disabled={mode === 'staff'} onClick={() => onToggle('staff')}>Staff</button>
      <button disabled={mode === 'freelance'} onClick={() => onToggle('freelance')}>Freelance</button>
    </nav>
  );
}
```

Step 2 fulfills the toggle role: Look at lines 4 and 5: clicking either button calls `onToggle` with the new mode string, triggering a parent re-render.

### Step 3: Then, we declare the score child ReviewScore.jsx

`ReviewScore` holds internal `score` state. The child must show that state is preserved during normal updates but reset when the key changes.

```jsx title="ReviewScore.jsx"
import { useState } from 'react';
export default function ReviewScore({ mode }) {
  const [score, setScore] = useState(0);
  return (
    <div className="review-score">
      <h3>Tier: {mode}</h3><p>Score: {score}</p>
      <button onClick={() => setScore(s => s + 1)}>Increment</button>
    </div>
  );
}
```

Step 3 completes the stateful card: Look at line 3: `const [score, setScore] = useState(0)`. While interacting within the same mode, clicking "Increment" preserves state. But when `mode` switches, the key changes, and `score` resets cleanly back to 0.

What would happen if we omitted `key={mode}` from `<ReviewScore mode={mode} />`? If we omitted `key={mode}`, React would see the exact same component type (`ReviewScore`) at the exact same position in `ReviewSwitcher`. The `score` state would persist across mode switches, causing an editor's evaluation of a staff writer to erroneously bleed into a freelance evaluation!

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the identity switcher component tree. Now we inspect `main.jsx`, which mounts `ReviewSwitcher` to the DOM. The entry point must initialize the React root and render the switcher.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import ReviewSwitcher from './ReviewSwitcher.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<ReviewSwitcher />);
```

Step 4 seals the architecture: Look at line 6: `root.render(<ReviewSwitcher />)`. React mounts the application. Component identity is governed strictly by tree position and explicit keys, preventing accidental state contamination.

Why does changing CSS display: none preserve state while unmounting resets it? If a component remains rendered in JSX and in the DOM (e.g. `<div style={{ display: isVisible ? 'block' : 'none' }}>`), its Fiber node remains intact in the React tree, so its state is 100% preserved. Conditional rendering (`{isVisible && <Modal />}`) completely removes the Fiber node, resetting state. If state preservation is desired without keys or lifted state, CSS hiding is a valid technique. Key terms: **CSS visibility preservation**, **DOM retention**, **fiber permanence**, **conditional unmounting**.

### Glossary

- **Component Identity**: How React recognizes whether a component on the new render corresponds to a component from the previous render.
- **Tree Position Rule**: React's algorithm that matches state to a component based on its component type and position in the Fiber tree.
- **Key Attribute**: A special React prop that overrides tree position, giving a component a permanent, explicit identity.
- **State Preservation**: The retention of a component's internal state across renders when its tree position and key remain unchanged.
- **State Reset**: The complete destruction of a component's internal state when its type, key, or tree position changes.
- **Nested Component Definition Trap**: The severe defect of defining a component function inside another component, causing remounts on every render.

### Summary

**React 19 Component Identity Invariants**

In daily production, understanding how React tracks component identity prevents state bleeding, phantom data bugs, and accidental input resets. Here is your streetwise review.

❒ Component Identity Invariants

1. State is tied to position in the UI tree.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) The same component type at the same position preserves state across renders.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Changing component type or wrapping in new parent elements destroys state.

2. Keys force state reset at the same position.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Pass a unique `key` when switching between logically distinct views.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) React treats different keys as distinct components, unmounting the old state.

3. Never define a component inside another component.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) A nested function creates a new component type reference on every render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) React unmounts and remounts the child, wiping state and input focus.

➔ NEVER declare component functions inside another component's body.

➔ ALWAYS use distinct `key` props when you need state to reset between toggled views.

➔ IF you need state to survive while hidden THEN **use CSS display: none instead of unmounting**.

**DO THIS:** Use distinct keys to reset state when switching view modes.

```jsx right title="ReviewSwitcher.jsx"
export default function ReviewSwitcher() {
  const [mode, setMode] = useState('staff');
  return (
    <div>
      <button onClick={() => setMode('free')}>Switch</button>
      <ReviewScore key={mode} mode={mode} />
    </div>
  );
}
```

**DO NOT DO THIS:** Never omit keys when toggling distinct workflows at the same position.

```jsx wrong title="State-Bleed Anti-Pattern"
export default function BrokenSwitcher() {
  const [mode, setMode] = useState('staff');
  return (
    <div>
      <button onClick={() => setMode('free')}>Switch</button>
      <ReviewScore mode={mode} />
    </div>
  );
}
```
