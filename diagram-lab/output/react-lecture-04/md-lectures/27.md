### One-Way Data Flow and the Common Ancestor

In React, data flows strictly downwards through props from parent to child. In many application layouts, two sibling components need to coordinate around the same dynamic piece of data: such as a search box in a navbar filtering an article list in the main view. Why can't `ArticleGrid` simply import or reference the state of `HeaderSearch` directly?

React components are isolated functional units. A component's state is completely private to itself; neither parents nor siblings have direct access to it. Attempting to share state horizontally violates encapsulation and creates untraceable bugs. The standard React solution is **lifting state up**:
1. Identify every component that depends on that piece of state.
2. Locate their closest common parent component in the component tree.
3. Move the `useState` call out of the child and into that common parent.
4. Pass the current state value down to the components that need to read it.
5. Pass an event handler callback down to the component that needs to update it.

When state is lifted to the common parent, the parent becomes the **single source of truth**. When the user interacts with the input, an event triggers the callback, updating state in the parent. React then re-renders the parent and passes the fresh values down to both children simultaneously, guaranteeing perfect visual coordination.

```jsx title="Horizontal Isolation vs Lifted State"
// BROKEN: Sibling cannot read another sibling's state:
function Header() { const [q, setQ] = useState(''); return <input ... />; }
function Main() { /* Cannot see `q`! */ return <ArticleList />; }
// RIGHT: Lift state to common parent:
function Dashboard() {
  const [query, setQuery] = useState('');
  return <div><Header query={query} onQuery={setQuery} /><Main query={query} /></div>;
}
```

What if no existing parent component directly wraps both siblings? If the closest common ancestor is too far up the tree (e.g. `App`), or if no clean common parent exists, you can introduce a new intermediate component specifically to group the siblings and own their shared state. Lifting state up does NOT mean lifting everything to the root of the app; always lift only as high as necessary to encompass all dependent children! Key terms: **intermediate wrapper**, **minimal lift principle**, **tree proximity**, **state scoping**.

### Controlled Children and Inverse Data Flow

We moved state to the parent. How does the child component that accepts user input trigger state updates in the parent?

When state is lifted, the child component that renders the input (`HeaderSearch`) is transformed into a **controlled component**. It holds zero internal state; instead, it receives its current value as a prop (e.g. `query`) and receives an updater function as a callback prop (e.g. `onQueryChange`).

This pattern is called **inverse data flow**: data flows *down* through props (`query`), while actions and changes flow *up* through function callbacks (`onQueryChange(e.target.value)`). The child does not mutate anything; it simply announces: "The user typed this new value," allowing the parent to decide how to update state.

```jsx title="Controlled Child Pattern"
export default function HeaderSearch({ query, onQueryChange }) {
  return (
    <div className="header-search">
      <input value={query} onChange={e => onQueryChange(e.target.value)} placeholder="Search..." />
    </div>
  );
}
```

Does lifting state cause unnecessary re-renders in sibling components? Yes, updating state in the parent causes the parent and both children to re-render. In React, this is by design and extremely fast. Re-rendering is how `ArticleGrid` receives the updated search query! Unless profiling reveals a severe bottleneck in a huge table, this default re-render behavior is desired, predictable, and virtually free. Key terms: **render tree propagation**, **predictable coordination**, **virtual DOM diffing**, **premature memoization**.

### Step 1: First, we construct the parent container NewsroomLayout.jsx

The parent container owns `query` state and coordinates the two siblings. The parent must pass `query` and `setQuery` down to the appropriate children.

```jsx title="NewsroomLayout.jsx"
import { useState } from 'react';
import HeaderSearch from './components/HeaderSearch.jsx';
import ArticleGrid from './components/ArticleGrid.jsx';
export default function NewsroomLayout() {
  const [query, setQuery] = useState('');
  return <div className="layout-root"><HeaderSearch query={query} onQueryChange={setQuery} /><ArticleGrid query={query} /></div>;
}
```

Step 1 establishes the shared state: Look at line 5: `const [query, setQuery] = useState('')`. Look at line 6: `query` is passed to both siblings, while `setQuery` is passed to `HeaderSearch` as `onQueryChange`. We will build `HeaderSearch` next in step 2.

### Step 2: Next, we declare the input child HeaderSearch.jsx

Step 1 passed `query` and `onQueryChange` to `HeaderSearch`. The sibling component must render the input without maintaining local state.

```jsx title="HeaderSearch.jsx"
export default function HeaderSearch({ query, onQueryChange }) {
  return (
    <header className="header-search">
      <input value={query} onChange={e => onQueryChange(e.target.value)} placeholder="Search newsroom..." />
    </header>
  );
}
```

Step 2 fulfills the input role: Look at line 4: `onChange={e => onQueryChange(e.target.value)}`. When the user types, `HeaderSearch` notifies `NewsroomLayout` via the callback prop, keeping `HeaderSearch` completely stateless.

### Step 3: Then, we declare the display child ArticleGrid.jsx

`ArticleGrid` receives `query` from `NewsroomLayout`. The terminal sibling must filter its articles based on the query.

```jsx title="ArticleGrid.jsx"
const ARTICLES = [{ id: 1, title: 'Budget Approved' }, { id: 2, title: 'Port Strike' }];
export default function ArticleGrid({ query }) {
  const matches = ARTICLES.filter(a => a.title.toLowerCase().includes(query.toLowerCase()));
  return (
    <main className="article-grid">
      <h2>Active Dispatches ({matches.length})</h2>
      <ul>{matches.map(a => <li key={a.id}>{a.title}</li>)}</ul>
    </main>
  );
}
```

Step 3 completes the consumer sibling: Look at line 3: `ArticleGrid` computes `matches` directly from `query`. As the user types in `HeaderSearch`, `NewsroomLayout` re-renders, and `ArticleGrid` instantly reflects the filtered results.

What would happen if `HeaderSearch` kept its own internal state instead of lifting it? If `HeaderSearch` kept its own state, `ArticleGrid` would have no way to access the search string. The articles would remain static and unfiltered unless clumsy DOM hacks or leaky event emitters were introduced.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the lifted state component tree. Now we inspect `main.jsx`, which mounts `NewsroomLayout` to the DOM. The entry point must initialize the React root and render the layout.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import NewsroomLayout from './NewsroomLayout.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<NewsroomLayout />);
```

Step 4 seals the architecture: Look at line 6: `root.render(<NewsroomLayout />)`. React mounts the application. State lives cleanly at the common ancestor, guaranteeing synchronized interaction across navigation and content panels.

When should you NOT lift state up? Do not lift state if only one component cares about it! For example, whether a dropdown menu is open or whether an input has focus is private UI state. Keep state as local as possible. Only lift state when two or more distinct components need to access or modify the same information. Key terms: **local state boundary**, **over-lifting antipattern**, **state locality**, **co-location principle**.

### Glossary

- **Lifting State Up**: The practice of moving state from child components to their closest common ancestor so multiple siblings can share it.
- **Closest Common Ancestor**: The nearest parent component in the component tree that wraps all components needing access to shared state.
- **Controlled Component**: A child component that receives its current value and change handlers exclusively via props without local state.
- **Inverse Data Flow**: The flow of events upwards via callback props while state data flows downwards via props.
- **One-Way Data Flow**: The core React architectural model where data flows strictly in one direction from parent to child.
- **State Locality**: The design rule that state should live as close as possible to where it is used.

In daily production, lifting state up coordinates sibling components while preserving clean encapsulation and predictable one-way data flow. Here is your streetwise review.

❒ Lifting State Invariants

1. Siblings cannot communicate horizontally.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Data flows strictly down via props; events flow up via callbacks.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Sibling components are completely isolated from each other's state.

2. Lift state to the closest common ancestor.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Identify all components that depend on the value.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Place `useState` in the lowest parent component that encloses all of them.

3. Use controlled children with callback props.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Pass the value prop down to the consumer child.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Pass an updater function down to the input child to trigger inverse data flow.

➔ NEVER attempt to read or mutate a sibling component's state directly.

➔ ALWAYS find the closest common ancestor and lift shared state there.

➔ IF state is only needed by a single component THEN **keep it local to that component**.

**DO THIS:** Lift shared state to the closest common ancestor.
