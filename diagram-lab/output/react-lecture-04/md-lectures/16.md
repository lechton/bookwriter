### The Photographic Snapshot Mental Model

In Lecture 15, we learned that `useState` stores data in React's fiber tree and that calling a setter function schedules a re-render. Beginners naturally expect `setVotes(votes + 1)` to immediately change the value of `votes` on the next line of code, just like a regular variable assignment `x = x + 1`. Why does `console.log(votes)` immediately after `setVotes` still print the old value?

In React, **rendering means calling your component function**. The JSX returned by that function is like a snapshot of the UI in time. Its props, event handlers, and local variables were all calculated using the state values *at the time of that render*. When React calls `LivePoll`, it passes a snapshot of `votes` (e.g. `0`). Inside that function execution, `votes` is not a live data channel: it is a fixed JavaScript constant with the value `0`.

Calling `setVotes(1)` does NOT change the `votes` variable in the currently running execution frame. Instead, it tells React: "For the *next* render, prepare a snapshot where `votes` is `1`." React schedules a new render pass, calls the component function again, and in that *next* snapshot, `votes` will be `1`.

```jsx title="State Snapshot in Action"
export default function PollButton() {
  const [votes, setVotes] = useState(0);
  function handleVote() {
    setVotes(votes + 1); // Requests next snapshot: votes = 1
    console.log(votes); // STILL 0! Current snapshot is frozen
  }
  return <button onClick={handleVote}>{votes} Votes</button>;
}
```

Recognizing that each render execution receives an immutable snapshot constant is the core invariant that makes React's execution model predictable.

> [!WILD]
> **What happens if an event handler has a setTimeout?** If you set state and read it inside a `setTimeout` after five seconds, will it see the new state or the old state? Imagine Elena writes `setVotes(votes + 1); setTimeout(() => { alert(votes); }, 5000);`. The user clicks. The screen re-renders immediately to `1`. Five seconds later, the alert pops up. What number does it show? It shows `0`! Why? Because the alert was created inside the render execution where `votes` was `0`. That function formed a closure over the snapshot of `votes` at the moment the click happened. Even though the screen re-rendered to `1` in a new snapshot, the old timeout is still looking at its own captured snapshot of `0`. State does not change under the feet of running code.

### Event Handlers and Past Snapshots

In traditional programming, if a value changes in the system, any delayed task eventually sees that new value. Why does React deliberately freeze state inside past render closures rather than letting them read the live current value?

Imagine a user clicks "Send Dispatch" on a draft story, and then immediately edits the headline before the network request finishes. If the event handler read a "live" mutable state variable, the dispatch might send half of the old story and half of the new story. By freezing state in a snapshot per render, React guarantees **temporal consistency**: every handler sees the exact user interface state that the reader was looking at when they triggered the interaction.

If you ever truly need the calculated future value immediately inside the same handler, compute it locally: `const nextVotes = votes + 1; setVotes(nextVotes); log(nextVotes);`. You do not need to wait for state to update: you already know what you passed to the setter.

```jsx title="Local Value Calculation Idiom"
function handleVote() {
  const nextVotes = votes + 1; // Compute next value locally
  setVotes(nextVotes); // Update future React snapshot
  sendAnalytics(nextVotes); // Use fresh value immediately
}
```

By computing values into local constants, you decouple immediate operational logic from React's scheduled render lifecycle.

> [!WILD]
> **Why is state snapshot immutability a superpower?** Why does React make state a snapshot instead of giving us a reactive mutable proxy? In systems with mutable reactive proxies, one event can trigger a mutation that changes values while another part of the code is still running, causing bizarre synchronization bugs and race conditions. In React, a component render is a pure, immutable projection of a single moment in time. You can pass that snapshot to children, log it, or delay it with `setTimeout`: nothing can tamper with it. When a change happens, React renders a completely new snapshot, cleanly separating "the past" from "the future".

### Step 1: First, we construct the parent container LivePoll.jsx

The parent container owns the vote state snapshot. It passes `votes` to `VoteStatus` and the update callback to `PollOption`.

```jsx title="LivePoll.jsx"
import { useState } from 'react';
import PollOption from './components/PollOption.jsx';
import VoteStatus from './components/VoteStatus.jsx';
export default function LivePoll() {
  const [votes, setVotes] = useState(0);
  const handleVote = () => setVotes(votes + 1);
  return (
    <main><VoteStatus votes={votes} /><PollOption onVote={handleVote} /></main>
  );
}
```

Look at line 5: `const [votes, setVotes] = useState(0);`. During this render pass, `votes` is frozen at `0`. When `handleVote` runs, `setVotes(votes + 1)` tells React to prepare a new snapshot where `votes` is `1`. We will build `PollOption` next in step 2.

### Step 2: Next, we declare the option child PollOption.jsx

Step 1 passed `handleVote` to `PollOption` under `onVote`. The child component must trigger the callback on click.

```jsx title="PollOption.jsx"
export default function PollOption({ onVote }) {
  return (
    <button className="btn-poll" onClick={onVote} type="button">
      Approve Overhaul
    </button>
  );
}
```

Look at lines 1 through 7: `PollOption` renders the vote button and executes `onVote` when clicked, triggering the parent's state setter and initiating the next snapshot render pass.

What would happen if `PollOption` tried to read `votes` immediately after calling `onVote()`? If `PollOption` received `votes` as a prop, its `votes` prop would still be `0` during that click handler execution frame because the parent has not finished re-rendering yet. React never updates props or state mid-handler.

### Step 3: Then, we declare the status child VoteStatus.jsx

Step 1 passed `votes` to `VoteStatus`. The child component must display the current vote count from the snapshot.

```jsx title="VoteStatus.jsx"
export default function VoteStatus({ votes }) {
  return (
    <div className="vote-status">
      <h2>Harbor Transit Overhaul</h2>
      <p>Total verified votes: {votes}</p>
    </div>
  );
}
```

Look at lines 1 through 8: `VoteStatus` receives the current `votes` snapshot and renders the tally. When `LivePoll` re-renders with the next snapshot (`votes = 1`), `VoteStatus` receives the new snapshot prop and updates the DOM.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the snapshot-driven component tree. Now we inspect `main.jsx`, which mounts `LivePoll` to the DOM.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import LivePoll from './LivePoll.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<LivePoll />);
```

Look at line 6: `root.render(<LivePoll />)`. React mounts `LivePoll` with its initial snapshot of `votes = 0`. When clicked, the setter requests the next snapshot, React re-renders `LivePoll` with `votes = 1`, and commits the updated DOM into `<div id="root">`.

Now let us examine an architectural consideration when reasoning about state across running functions.

Does state ever change inside a running function? Can a state variable ever change its value while a function is executing? Never! Inside any single function execution, `const [count, setCount] = useState(0)` means `count` is a constant. No matter what setters you call, what promises resolve, or how many milliseconds pass, `count` remains `0` for the entire lifetime of that function call. Only when React calls the function again in a new render pass does `count` have a different value.

Calling `setState` does not mutate that local constant: it schedules a new render where the component will be called with a fresh snapshot. Conclude by mentioning that closures over snapshots guarantee temporal consistency for async operations like `setTimeout`.

### Where you will meet this
- Debugging state setters: understanding why `console.log` immediately after `setState` shows stale data.
- Asynchronous timers: handling `setTimeout` or `setInterval` where handlers retain the snapshot of the render they were created in.
- Optimistic UI updates: calculating next values locally (`const next = count + 1`) to pass to both `setState` and API fetch calls simultaneously.
- Form submissions: verifying that payload data sent to the backend matches what the user saw when clicking submit.

### Glossary
- **State Snapshot**: The concept that state inside a component render is an immutable constant captured at the moment of that specific render pass.
- **Render Phase**: The execution of the component function where React calculates the next UI snapshot based on current props and state.
- **Temporal Consistency**: The architectural guarantee that all handlers and child components in a render pass see a self-consistent slice of time.
- **Closure over Snapshot**: A JavaScript function retaining access to the specific state snapshot variables present when the function was created.
- **Local Calculation Idiom**: The practice of storing `const next = state + 1` in a local variable to use the fresh value immediately before the next render.
- **Stale State Illusion**: The false perception that React failed to update state, caused by reading the current frozen snapshot instead of waiting for the next render.

### Summary

**React 19 State Snapshot Invariants**

In daily production, understanding state snapshots eliminates the most common beginner source of confusion: why `setState` does not immediately update variables. Recognizing that each render is an immutable photograph of time guarantees predictable, race-condition-free code. Here is your streetwise review.

❒ State Snapshot Invariants

1. State is a fixed constant for the duration of a render pass.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Calling `setVotes(1)` does not alter `votes` in the currently executing code.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) It schedules a *future* render pass where `votes` will be `1`.

2. To use the next value immediately, compute it in a local constant.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Write `const next = votes + 1; setVotes(next); log(next);`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Never rely on reading `votes` immediately after `setVotes(votes + 1)`.

➔ NEVER expect state variables to update synchronously within the same event handler.

➔ ALWAYS compute next values locally if you need them immediately for logging or API calls.

➔ IF you encounter stale values in a `setTimeout` THEN **remember that closures capture the snapshot of the render they were created in**.

**DO THIS:** Compute next values locally to update state and use the value immediately.

```jsx right title="PollOption.jsx"
// Computes next value locally for immediate use
export default function PollOption({ votes, onVote }) {
  function handleClick() {
    const nextVotes = votes + 1;
    onVote(nextVotes);
    console.log('Next vote count:', nextVotes);
  }
  return <button onClick={handleClick}>Vote</button>;
}
```

**DO NOT DO THIS:** Never read state immediately after setting it expecting synchronous mutation.

```jsx wrong title="Synchronous State Anti-Pattern"
// FAILS: console.log prints stale snapshot value!
export default function BrokenOption({ votes, onVote }) {
  function handleClick() {
    onVote(votes + 1);
    console.log(votes); // Prints old votes, NOT votes + 1!
  }
  return <button onClick={handleClick}>Vote</button>;
}
```
