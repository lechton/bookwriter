### Anti-Pattern 1: Transforming Data for Rendering

In early React code, newcomers often use `useEffect` as an automatic watch-dog to update one state variable whenever another changes: such as updating `total` whenever `items` change. Why is updating state inside an Effect to compute derived data a major performance and architectural bug?

When you update state inside an Effect:
1. React runs the component and renders the DOM with old/stale state.
2. The browser paints the screen with stale values.
3. React executes `useEffect` and calls `setTotal(...)`.
4. React is forced to re-run the entire component a second time and repaint!
This creates an **extra render pass**, degrades performance, and causes visual flicker. Instead, **calculate derived values on the fly during render**. Because render code executes synchronously, the calculation is instant, perfectly synchronized, and causes zero extra renders. If the calculation is computationally heavy, cache it with `useMemo`.

```jsx title="Transforming Data: Effect vs Derivation"
// BAD: Extra render pass, flashes stale total:
const [total, setTotal] = useState(0);
useEffect(() => {
  setTotal(items.reduce((sum, i) => sum + i.fee, 0));
}, [items]);
// GOOD: Instant, synchronous, zero extra passes:
const total = items.reduce((sum, i) => sum + i.fee, 0);
```

What about caching expensive calculations? Moving an expensive calculation to `useEffect` still runs the calculation, but adds an extra render cycle on top! If a calculation is genuinely slow (e.g. searching thousands of rows), keep it in render and wrap it in `useMemo`: `const total = useMemo(() => computeSlowTotal(items), [items])`. It stays derived and avoids duplicate render passes. Key terms: **useMemo memoization**, **render efficiency**, **caching vs synchronization**, **pure computation**.

### Anti-Pattern 2: Handling User Actions in Effects

We know data transformations belong in render. Why is triggering user actions or mutations (like submitting forms or posting analytics) in `useEffect` dangerous?

Consider an editor clicking "Approve Payout". If you set `const [approved, setApproved] = useState(false)` in `onClick` and run `useEffect(() => { if (approved) api.post('/payout'); }, [approved])`, the mutation is detached from the user event. If the component remounts (or in StrictMode), the effect might re-run and **submit duplicate financial transactions**!

Code that runs because the user performed a specific action belongs directly in the **event handler**, not in `useEffect`. Event handlers know the exact user intent; Effects only know that state changed. Reserve Effects strictly for code that must run **regardless of which interaction caused the state change** (such as syncing a document title or keeping a socket connected).

```jsx title="User Events: Effect vs Handler"
// BAD: Detached effect risks duplicate network requests on remount:
function BadBtn() {
  const [sent, setSent] = useState(false);
  useEffect(() => { if (sent) api.post('/payout'); }, [sent]);
  return <button onClick={() => setSent(true)}>Approve</button>;
}
// GOOD: Event handler directly executes action:
function GoodBtn() {
  return <button onClick={() => api.post('/payout')}>Approve</button>;
}
```

How do you reset all component state when a prop changes? Instead of watching `userId` in an effect to imperatively reset fields, pass a `key` to the child component: `<PayoutForm key={userId} />`. When `userId` changes, React automatically unmounts the old instance and mounts a fresh one with initial state! Zero effect code, zero bugs, zero stale renders. Key terms: **key-driven reset**, **declarative unmounting**, **zero-effect reset**, **state re-initialization**.

### Step 1: First, we construct the container PayoutAuditor.jsx

The container manages accepted articles and computes total payout during render. The container must prove that total requires zero useState or useEffect.

```jsx title="PayoutAuditor.jsx"
import { useState } from 'react';
import PayoutSummary from './components/PayoutSummary.jsx';
import ApproveButton from './components/ApproveButton.jsx';
const ITEMS = [{ id: 1, fee: 350 }, { id: 2, fee: 400 }];
export default function PayoutAuditor() {
  const [articles] = useState(ITEMS);
  const total = articles.reduce((sum, a) => sum + a.fee, 0);
  return <div className="auditor-box"><PayoutSummary total={total} count={articles.length} /><ApproveButton total={total} /></div>;
}
```

Step 1 establishes render-time derivation: Look at line 7: `const total = articles.reduce(...)`. Notice there is NO `useEffect` or `setTotal`. The calculation runs synchronously during render. We will build `PayoutSummary` next in step 2.

### Step 2: Next, we declare the summary child PayoutSummary.jsx

Step 1 computed `total` and passed it to `PayoutSummary`. The child component must display the derived values.

```jsx title="PayoutSummary.jsx"
export default function PayoutSummary({ total, count }) {
  return (
    <section className="payout-summary">
      <h2>Pending Author Disbursements</h2>
      <p>Total Items: <strong>{count}</strong></p>
      <p>Calculated Total: <strong>${total}</strong></p>
    </section>
  );
}
```

Step 2 fulfills the summary role: Look at line 6: `PayoutSummary` displays `${total}`. Because the calculation happened in render, the displayed total is always fresh and never flashes stale data.

### Step 3: Then, we declare the button child ApproveButton.jsx

`ApproveButton` handles payment authorization. The button must perform the action in `onClick`, not in an effect.

```jsx title="ApproveButton.jsx"
import { useState } from 'react';
export default function ApproveButton({ total }) {
  const [msg, setMsg] = useState(null);
  const handleApprove = () => setMsg(`Disbursed $${total}`);
  return <div className="approve-action"><button onClick={handleApprove}>Authorize</button>{msg && <p>{msg}</p>}</div>;
}
```

Step 3 completes handler-driven execution: Look at line 4: `const handleApprove = ...`. The approval mutation runs in direct response to the click event. There is no `useEffect` watching state flags, eliminating duplicate submission risks.

What would happen if we used an effect to watch an approval flag instead? If we used `useEffect(() => { if (approved) submit(); }, [approved])`, the network call would fire asynchronously after commit. In StrictMode or upon remounting, the effect could execute again, submitting duplicate payouts and creating accounting discrepancies.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the effect-free architecture. Now we inspect `main.jsx`, which mounts `PayoutAuditor` to the DOM. The entry point must initialize the React root and render the auditor.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import PayoutAuditor from './PayoutAuditor.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<PayoutAuditor />);
```

Step 4 seals the architecture: Look at line 6: `root.render(<PayoutAuditor />)`. React mounts the application. Clean derivations and event handlers replace fragile effects, keeping rendering fast and deterministic.

When DO you genuinely need an Effect? You need an Effect if and only if you must synchronize your component with an **external system** that does not know about React: WebSockets, browser geolocation, window resize listeners, custom canvas rendering, or imperative third-party plugins. If code only involves React state and props, you do not need an Effect! Key terms: **genuine effect use cases**, **external system boundary**, **React-only logic**, **browser API synchronization**.

> [!TIP]
**To impress the interviewer:** Cite the three golden rules of "You Might Not Need an Effect":
1. **Transforming data for rendering?** Calculate it during render (derived state); do not put it in an effect.
2. **Handling user interaction?** Put the logic directly in the event handler; do not watch a state flag in an effect.
3. **Resetting state on prop change?** Pass a `key` to the component; do not write an effect that calls state setters.

### Where you will meet this

- Filtered lists and search tables: calculating filtered results during render instead of in an effect.
- Form submissions: firing API calls directly in `onSubmit` instead of setting `isSubmitting` and watching it in `useEffect`.
- Entity viewers: passing `key={articleId}` to reset editing state when switching articles.
- Shopping cart totals: calculating discounts and sales tax directly during render.

### Glossary

- **Derived Calculation**: A value computed synchronously during render from existing props and state without `useState` or `useEffect`.
- **Double-Render Waterfall**: The performance defect where an effect updates state immediately after render, forcing an unnecessary second render pass.
- **Event Handler Action**: Code executed directly in response to a user gesture (click, submit, change).
- **Key-Driven Reset**: Using React's `key` attribute to recreate a component tree and cleanly reset all state.
- **Redundant Effect**: An unnecessary `useEffect` call used for operations that should be handled during render or in event handlers.
- **Visual Tearing**: A momentary screen flash where the user sees outdated or contradictory state before an effect runs.

In daily production, pruning unnecessary effects eliminates double-render waterfalls and prevents duplicate mutations. Here is your streetwise review.

❒ No-Effect Invariants

1. Calculate derived data during render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) If a value can be computed from props or state, calculate it on the fly.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Storing it in state and updating it in an effect forces an unnecessary second render pass.

3. Reset state on prop changes with keys.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Pass `key={userId}` to reset a child component's internal state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) React unmounts the old instance and mounts a fresh one automatically.

➔ NEVER use `useEffect` to copy props into state or compute derived values.

➔ ALWAYS execute user-initiated actions directly inside event handlers.

➔ IF you need to reset all component state when an ID changes THEN **pass a key prop**.

**DO THIS:** Calculate derived values synchronously during render.

```jsx right title="PayoutAuditor.jsx"
export default function PayoutAuditor({ articles }) {
```
