### The Three State Tests and Redundant State

In earlier lectures we learned that `useState` preserves data across re-renders and triggers UI updates. When designing features, newcomers often declare a state variable for every dynamic value on screen: raw items, filter input, filtered output, and total count. Why does storing filtered items or item counts in state inevitably cause synchronization bugs?

React provides three definitive tests to determine if a value belongs in state:
1. Does it remain unchanged over time? If so, it is NOT state (use a plain constant).
2. Is it passed from a parent via props? If so, it is NOT state (it belongs to the parent).
3. Can you compute it from existing state or props? If so, it is **DEFINITELY NOT state**—it is **derived state**!
When you store derived values (like `filteredStories` or `count`) in separate state variables, every event handler that updates `stories` or `query` must remember to manually recalculate and set both dependent states. If even one handler forgets, the values drift apart and the UI lies to the reader.

Instead of storing derived values in state, compute them directly in the body of the component during render. Because React re-runs the component function on every state update, the derived values are always fresh, perfectly synchronized, and require zero synchronization code.

```jsx title="Redundant vs Derived State"
// WRONG: Redundant state variables drift out of sync!
const [stories, setStories] = useState(initialStories);
const [query, setQuery] = useState('');
const [filtered, setFiltered] = useState(initialStories);
// RIGHT: Calculate derived values on the fly during render:
const [stories, setStories] = useState(initialStories);
const [query, setQuery] = useState('');
const filtered = stories.filter(s => s.title.includes(query));
const count = filtered.length;
```

What about performance if the filter calculation is expensive? In 99% of cases, filtering an array of several hundred items takes less than 1 millisecond; computing it during render is virtually free. If and only if the calculation is genuinely expensive (e.g. searching 50,000 items), wrap the computation in `useMemo`: `const filtered = useMemo(() => stories.filter(...), [stories, query])`. Even then, it remains a **derived calculation**, never a separate state variable! Key terms: **useMemo memoization**, **expensive calculation**, **render-time cost**, **premature optimization**.

### Avoiding Duplicate and Contradictory State

We know not to store computed values in state. What other structural mistakes lead to state corruption in production apps?

A very common antipattern is storing a selected object in state: `const [selectedStory, setSelectedStory] = useState(stories[0])`. If the user edits the story title in `stories`, `selectedStory` still holds the old object copy! You now have two diverging copies of the same data. The solution is to store only the **selected ID** in state: `const [selectedId, setSelectedId] = useState(1)`. Then derive the selected object: `const selectedStory = stories.find(s => s.id === selectedId)`.

Another frequent trap is contradictory boolean flags: `const [isSending, setIsSending] = useState(false)` and `const [isSent, setIsSent] = useState(false)`. It is possible for a bug to leave both flags set to `true`, creating an impossible UI state. Instead, unify mutually exclusive states into a single status variable: `const [status, setStatus] = useState('idle')` where status can only be `'idle' | 'sending' | 'sent' | 'error'`.

```jsx title="Selected Object vs Selected ID"
// WRONG: Duplicated object; edits to stories leave selectedStory stale:
const [selectedStory, setSelectedStory] = useState(stories[0]);
// RIGHT: Store the ID, derive the object:
const [selectedId, setSelectedId] = useState(stories[0]?.id);
const selectedStory = stories.find(s => s.id === selectedId);
```

What should you do when props are passed as initial state? `useState(initialQuery)` only uses `initialQuery` on the very first mount; if the parent passes a new `initialQuery` prop later, React ignores it! Only use props in `useState` if the state is truly intended to be independent after initialization (prefixing the prop with `initial` or `default`). If the child should always reflect the parent prop, do not put it in state at all! Key terms: **prop mirroring**, **initial prop convention**, **stale initializer**, **controlled flow**.

### Step 1: First, we construct the parent container WireFilter.jsx

The parent container defines the minimal raw state (`stories` and `query`) and computes `filteredStories` and `matchCount` during render. The parent must demonstrate that filtered output and count require zero useState calls.

```jsx title="WireFilter.jsx"
import { useState } from 'react';
import SearchBox from './components/SearchBox.jsx';
import StoryFeed from './components/StoryFeed.jsx';
const INITIAL = [{ id: 1, title: 'Metro Transit' }, { id: 2, title: 'Federal Reserve' }];
export default function WireFilter() {
  const [stories, setStories] = useState(INITIAL);
  const [query, setQuery] = useState('');
  const filtered = stories.filter(s => s.title.toLowerCase().includes(query.toLowerCase()));
  return <div className="filter-panel"><SearchBox query={query} onQuery={setQuery} /><StoryFeed items={filtered} count={filtered.length} /></div>;
}
```

Step 1 establishes minimal state: Look at lines 6 and 7: only `stories` and `query` are in `useState`. Look at line 8: `filtered` is calculated on the fly. Look at line 9: `count` is derived directly as `filtered.length`. We will build `SearchBox` next in step 2.

### Step 2: Next, we declare the input child SearchBox.jsx

Step 1 passed `query` and `onQuery` to `SearchBox`. The child component must render a controlled text input.

```jsx title="SearchBox.jsx"
export default function SearchBox({ query, onQuery }) {
  return (
    <div className="search-box">
      <input value={query} onChange={e => onQuery(e.target.value)} placeholder="Filter wire..." />
    </div>
  );
}
```

Step 2 fulfills the input role: Look at line 4: `SearchBox` holds zero state of its own; it receives `query` as a prop and notifies the parent via `onQuery`.

### Step 3: Then, we declare the display child StoryFeed.jsx

`StoryFeed` receives `items` and `count` from `WireFilter`. The terminal child must render the story list and match count.

```jsx title="StoryFeed.jsx"
export default function StoryFeed({ items, count }) {
  return (
    <section className="story-feed">
      <header>Matching Dispatches: {count}</header>
      <ul>{items.map(s => <li key={s.id}>{s.title}</li>)}</ul>
    </section>
  );
}
```

Step 3 completes the display component: Look at line 4: `StoryFeed` renders the fresh count and filtered list passed down from `WireFilter`. Because `items` and `count` are derived in the parent on every render, the feed can never display a mismatch between item count and displayed rows.

What would happen if we stored `filtered` and `count` in separate state variables? If we stored `filtered` and `count` in separate state variables, every time `query` changed, `filtered` and `count` would only update if a handler explicitly called `setFiltered` and `setCount`. Any missing call or asynchronous delay would cause the count badge and story list to show conflicting data.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the state structure tree. Now we inspect `main.jsx`, which mounts `WireFilter` to the DOM. The entry point must initialize the React root and render the top-level feed.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import WireFilter from './WireFilter.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<WireFilter />);
```

Step 4 seals the architecture: Look at line 6: `root.render(<WireFilter />)`. React mounts the application. As Marcus types into the search box, `WireFilter` re-renders, recalculating `filtered` and `count` instantly with zero state drift.

Why is redundant state considered a major architectural defect? In large teams and complex applications, redundant state creates multiple sources of truth. As features evolve and multiple actions modify data, synchronizing dependent states requires sprawling boilerplate. Inevitably, edge cases arise where one state updates while another remains stale, creating phantom bugs and corrupted UI views. Key terms: **multiple sources of truth**, **phantom bugs**, **maintenance debt**, **defensive programming**.

> [!TIP]
**To impress the interviewer:** When asked how to structure state, quote the core rule: **State should be minimal, non-redundant, and non-contradictory**. State the three tests: (1) Does it stay constant? (2) Is it passed as props? (3) Can you compute it from existing state or props? If you can compute it, compute it on the fly during render! Mention that for selections, you should store the selected item's **ID**, never the whole object, to avoid stale duplicate data.

### Where you will meet this

- Filtered lists and tables: computing search results and row counts during render instead of syncing state.
- Form validation: computing `isValid` and error messages from field values during render.
- Shopping cart totals: calculating subtotals, taxes, and shipping from item quantities on the fly.
- Selected entity views: storing `selectedId` and looking up the active record in the master collection.

### Glossary

- **Derived State**: Any value that can be computed from existing props or state during render without `useState`.
- **Minimal State**: The principle of storing only the raw, irreducible data required to represent UI changes.
- **Redundant State**: Storing duplicate or computable values in separate state variables, risking desynchronization.
- **Selected ID Pattern**: Storing only the unique identifier of an active item in state and looking up the full object during render.
- **Status Enum**: Replacing multiple mutually exclusive boolean flags with a single union string (`'idle' | 'loading' | 'success' | 'error'`).
- **Single Source of Truth**: The architectural guarantee that each piece of data is owned and modified in exactly one place.

### Summary

**React 19 State Structure Invariants**

In daily production, keeping state minimal and computing derived values during render eliminates entire categories of synchronization bugs. Here is your streetwise review.

❒ State Structure Invariants

1. Never put derived values into state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) If a value can be computed from props or existing state, calculate it on the fly.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Render-time computations are fresh, immediate, and zero-maintenance.

2. Store IDs, not duplicate objects.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Storing a selected object creates a stale duplicate when the original updates.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Store `selectedId` in state and find the active object during render.

3. Replace contradictory booleans with a status string.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Multiple flags like `isLoading` and `isSuccess` can accidentally both be true.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use a single status string: `'idle' | 'loading' | 'success' | 'error'`.

➔ NEVER store filtered arrays, item counts, or validation flags in `useState`.

➔ ALWAYS calculate derived values during render from the single source of truth.

➔ IF you need an active item from a collection THEN **store its ID and derive the object**.

**DO THIS:** Compute derived values directly during render.

```jsx right title="WireFilter.jsx"
export default function WireFilter({ stories }) {
  const [query, setQuery] = useState('');
  const filtered = stories.filter(s => s.title.includes(query));
  const count = filtered.length;
  return <div>Found {count}: {filtered.map(s => s.title)}</div>;
}
```

**DO NOT DO THIS:** Never store redundant filtered arrays and counts in separate state.

```jsx wrong title="Redundant-State Anti-Pattern"
export default function BrokenFilter({ stories }) {

```
