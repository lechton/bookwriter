### The Bridge Between HTML and React

In earlier lessons, we learned how to write React components, JSX syntax rules, and dynamic expressions (see Lectures 3, 4, and 5). You wrote an `App.jsx` component that returns markup, but that component is just a JavaScript function sitting in a file. Web browsers do not know what `App.jsx` is: they only load `index.html`. You need an explicit bridge to connect that JavaScript function to a real DOM element on the page.

React is a modular library rather than an all-or-nothing framework. The core `react` package only knows about components, hooks, and virtual element descriptors: it knows nothing about browser DOM nodes, phone screens, or canvas elements. To render into a web browser, React provides a separate package called `react-dom/client`. In modern React 19, mounting is a two-step process rather than a single function call.

The two-step mounting sequence works in strict order. (a) First, you call `createRoot(domNode)`: this takes a physical DOM element (usually `document.getElementById('root')`) and creates a React root object in memory that takes over managing the DOM inside that container. (b) Second, you call `root.render(<App />)`: this takes your root component JSX, evaluates its component tree, and commits the resulting HTML into the DOM container. Calling `render` directly on `react-dom` without creating a root is the obsolete React 17 pattern that disables concurrent rendering features.

```jsx title="Mounting Contrast"
// Legacy React 17 Synchronous Mount:
ReactDOM.render(<App />, document.getElementById('root'));
// Modern React 19 Two-Step Root Architecture:
import { createRoot } from 'react-dom/client';
const domNode = document.getElementById('root');
const root = createRoot(domNode); // 1. Acquires container in **MEMORY**
root.render(<App />); // 2. Renders component tree into **DOM**
```

In legacy React 17 and earlier, developers called `ReactDOM.render(<App />, domNode)`. This legacy API attempted to configure the root and render the tree in a single blocking synchronous step, preventing concurrent rendering and background transitions. Modern `createRoot` initializes an internal FiberRoot with priority lanes, enabling interruptible rendering.

```html-figure src="figures/06-03-mounting-pipeline.html" caption="Fig 6.1: The two-step mounting pipeline from physical DOM container to React root memory and initial render commit."
```

> [!WILD]
> **Why does React need two steps to mount?** Imagine you are setting up an electrical sub-panel in an office building. You do not plug in a high-voltage appliance and simultaneously wire the breakers to the municipal grid in one motion. First, you install the sub-panel and verify the connection to the electrical main. Once the panel is securely anchored, you switch on the circuits. `createRoot` is that sub-panel. Step 1 (`createRoot`) anchors React's memory to a specific DOM node and initializes its concurrent scheduler. Step 2 (`root.render`) switches on the circuits, evaluating your components and rendering the interface. Splitting the process lets React manage the root's lifecycle independently from individual render updates.

### Root Lifecycle, DOM Clearing, and Unmounting

Once a root is created, React takes exclusive ownership of the DOM container. When `root.render(<App />)` executes for the very first time, React clears any existing HTML markup sitting inside the container before rendering your component tree. Developers often leave fallback text or loading spinners inside `<div id="root">Loading...</div>` in `index.html` and wonder what happens to that markup when React mounts. React wipes it clean and replaces it with the component tree.

If your application uses server-side rendering (SSR) or static site generation (SSG), using `createRoot` is a serious mistake. Calling `createRoot` on server-rendered HTML wipes the existing markup and recreates every DOM node from scratch, causing an ugly screen flicker. In server-rendered applications, you must call `hydrateRoot(domNode, <App />)` instead, which reuses the existing HTML nodes and attaches event listeners.

```jsx title="Root Lifecycle and Cleanup"
const root = createRoot(document.getElementById('ticker-root'));
root.render(<LiveTicker />); // Mounts live ticker widget
// When host page navigates away or removes widget:
root.unmount(); // Tears down tree and cleans up **SUBSCRIPTIONS**
```

Most applications have a single `createRoot` call that runs once at startup. However, in applications where React is embedded as a widget inside a legacy non-React host page (like a WordPress blog or jQuery dashboard), the widget may need to be removed. Calling `root.unmount()` tells React to stop managing the root DOM node. It unmounts all components in the tree, runs their cleanup functions, detaches event listeners, and frees internal memory.

> [!WILD]
> **When should you call root.unmount in production?** Imagine The National Times has a legacy article archive built with jQuery. An editor opens a tab containing an interactive breaking news ticker built with React. When the editor clicks away to another tab, jQuery deletes the tab's DOM container. But what happened to the React component that lived inside? If you did not call **root.unmount**, React still holds the component tree, its timer intervals, and its event listeners in memory. The DOM node is gone, but the code continues running in the background, leaking memory until the tab crashes. Calling **root.unmount** before removing the DOM container ensures every component cleans up and releases its resources.

To see how `createRoot` integrates an entire application into the browser, consider the newsroom workspace on The National Times. The entry point `main.jsx` acquires the root DOM node, creates the root, and renders `NewsApp.jsx`, which in turn mounts a live ticker child component `LiveTicker.jsx`.

The rendered canvas displays the visual destination of our app. The parent container `NewsApp.jsx` coordinates the workspace. Inside it sits the editorial masthead and the live ticker status child component.

### Step 1: First, we construct the entry point main.jsx

We start our implementation at the entry point: `main.jsx`.

The entry point is the first JavaScript file executed by the browser after loading `index.html`. It locates the target DOM container and initializes the React root:

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import NewsApp from './NewsApp.jsx';
const domNode = document.getElementById('root');
if (!domNode) throw new Error('Target container #root not found');
const root = createRoot(domNode); // Acquires container and sets up **SCHEDULER**
root.render(<NewsApp />); // Mounts root component into **DOM**
```

Look at lines 5 and 6: `createRoot(domNode)` creates the React root, and `root.render(<NewsApp />)` launches the component tree.

Notice the guard clause on line 4: if `document.getElementById('root')` evaluates to null because the HTML is missing the element, the script fails fast with a clear error rather than crashing silently.

To recap this first step: the entry point acquires the physical DOM container, creates the root instance, and initiates the initial render pass.

### Step 2: Next, we build the parent container NewsApp.jsx

In step 2, we build the top-level application layout: `NewsApp.jsx`.

This component coordinates the newsroom masthead and embeds the live ticker child component:

```jsx title="NewsApp.jsx"
import LiveTicker from './components/LiveTicker.jsx';
export default function NewsApp() {
  return (
    <main className="news-app">
      <h1 className="masthead-title">The National Times</h1>
      <LiveTicker channel="breaking" /> // Mounts child with channel **PROP**
    </main>
  );
}
```

Look at line 8: `<LiveTicker channel="breaking" />`. The parent dictates the layout and passes the `channel` prop downward to the child.

Notice what happened: `NewsApp` does not need to know anything about `createRoot` or DOM element IDs. It focuses purely on rendering declarative UI and coordinating children.

To recap this step: the root component defines the application layout and mounts child components without needing any DOM-specific code.

### Step 3: Then, we declare the ticker child LiveTicker.jsx

In step 3, we fulfill the contract established by the parent: we build `LiveTicker.jsx`.

This child component renders the breaking news status badge and headline text:

```jsx title="LiveTicker.jsx"
export default function LiveTicker({ channel }) {
  return (
    <div className="live-ticker">
      <span className="ticker-badge">Live Broadcast</span> // Status badge in **TICKER**
      <p className="ticker-text">Dockworkers Reach Tentative Agreement</p>
    </div>
  );
}
```

Look at lines 4 and 5. `LiveTicker` renders a status badge and paragraph.

When `main.jsx` executed `root.render(<NewsApp />)`, React reconciled this entire hierarchy and committed it into `<div id="root">`.

To recap this step: child components participate in the unified DOM tree mounted by `createRoot` without needing separate mount points.

### Step 4: Finally, we seal the host document index.html

In step 4, we examine the static HTML shell that hosts the entire application on disk:

```html title="index.html"
<!DOCTYPE html>
<html lang="en">
  <head><meta charset="UTF-8"><title>The National Times</title></head>
  <body>
    <div id="root"></div> <!-- Target DOM container for **CREATEROOT** -->
    <script type="module" src="/src/main.jsx"></script> <!-- Loads **ENTRY** -->
  </body>
</html>
```

Look at lines 5 and 6. `<div id="root"></div>` provides the physical mount point. The module script points to `/src/main.jsx`.

The browser loads the HTML, executes `main.jsx`, creates the root, and replaces the empty div content with our interactive React application.

To recap this final step: `index.html` provides the static DOM container and script tag that bootstraps React into the browser window.

### Lessons from the Experiment: Naive Expectation vs Reality

To review the architectural lessons from this implementation, examine the component hierarchy:

```component-code title="Summary: The Logic of Nested Components"
main.jsx | none | entry | [role: The **application entry point** retrieves the physical DOM element `#root` from the document. It invokes `createRoot(domNode)` and schedules the initial render pass via `root.render(<NewsApp />)`. Why? To establish React's concurrent scheduler and take exclusive ownership of DOM updates inside the container.]
  NewsApp.jsx | none | parent | [role: This is the **root application component**. It renders the editorial masthead and mounts the `<LiveTicker />` child component. Why? To define the top-level layout hierarchy that React reconciles on every render cycle.]
  LiveTicker.jsx | none | child | [role: This is the **terminal child component**. It displays the live broadcast status badge and headline text. Why? To demonstrate that child components participate in the unified DOM tree mounted by `createRoot` without needing separate mount points.]
```

In the naive approach, developers assume React components can mount themselves or append to existing HTML without an explicit container. Alternatively, they call legacy `ReactDOM.render`, disabling concurrent rendering and trapping the main thread.

In the React 19 reality, `createRoot` creates an explicit root instance with a concurrent scheduler, claims exclusive container ownership, and provides clean unmounting.

```html-figure src="figures/06-02-architecture-audit.html" caption="Architecture audit: evaluating createRoot mounting, DOM container ownership, and lifecycle cleanup against naive legacy expectations."
```

> [!WILD]
> **Why does createRoot wipe existing HTML inside the container?** Imagine you put a placeholder message `<div id="root">Connecting to news wire...</div>` inside your HTML file. When the JavaScript bundle finishes downloading, `root.render(<NewsApp />)` executes. That placeholder message vanishes instantly. Why? Because React does not append to the container: it takes complete, exclusive ownership of the container's interior. In client-side rendering with **createRoot**, React clears all existing children to guarantee that the physical DOM matches its in-memory virtual tree 100%. If you want that HTML preserved and made interactive, you cannot use **createRoot**: you must use **hydrateRoot**.

> [!TIP]
> **To impress the interviewer:** When asked how `createRoot` differs from legacy `ReactDOM.render`, explain that `createRoot` changes the fundamental execution model of React. In React 17, `ReactDOM.render` ran synchronously from top to bottom, blocking the main thread until the entire DOM tree was committed. In React 19, `createRoot` creates an internal FiberRoot with priority lanes, enabling concurrent rendering, interruptible work, and background transitions.

### Where you will meet this

- Single-page application entry points: initializing the root application container in `main.jsx` or `index.js` across all Vite and Webpack projects.
- Micro-frontends and multi-root architectures: calling `createRoot` multiple times on a single page to mount independent React widgets into different DOM sections.
- Embedded third-party widgets: mounting a live chat widget or feedback form into a customer's existing non-React website and unmounting on close.
- Unit and integration tests: testing libraries calling `createRoot` and `root.unmount` behind the scenes to mount components into headless JSDOM nodes.

### Glossary

- **createRoot**: The React DOM client API that creates a root container for displaying content inside a browser DOM element.
- **root.render**: The method on a React root that evaluates a component tree and commits it into the DOM container.
- **root.unmount**: The method on a React root that tears down the component tree, runs cleanups, and detaches React from the DOM.
- **Root Container**: The physical DOM element (typically `<div id="root">`) managed exclusively by a React root.
- **hydrateRoot**: The server-rendering counterpart to `createRoot` that attaches event handlers to existing server-rendered HTML without wiping it.
- **Concurrent Scheduler**: The internal React engine mechanism initialized by `createRoot` that coordinates priority-based, interruptible rendering.

❒ The Mounting Sequence and Container Governance

1. Mount applications using the two-step `createRoot` and `root.render` sequence.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Step 1 (`createRoot(domNode)`) anchors React to a physical DOM element and initializes its concurrent scheduler.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Step 2 (`root.render(<App />)`) evaluates the component hierarchy and commits the initial DOM nodes.

2. Manage container lifecycles and clean up embedded widgets.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `root.render()` completely clears any existing HTML inside the container on its initial run.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Call `root.unmount()` whenever a React root is removed from a non-React host page to prevent memory leaks.

➔ NEVER call the legacy `ReactDOM.render` API, which disables concurrent rendering in modern React.

➔ ALWAYS verify that `document.getElementById('root')` exists before passing it to `createRoot`.

➔ IF your HTML was rendered on a server THEN **call `hydrateRoot` instead of `createRoot` to prevent screen flickering**.

**DO THIS:** Separate root initialization from rendering and provide an explicit DOM container.

```jsx right title="main.jsx"
import { createRoot } from 'react-dom/client';
import NewsApp from './NewsApp.jsx';

const container = document.getElementById('root');
if (container) {
  const root = createRoot(container);
  root.render(<NewsApp />);
}
```

**DO NOT DO THIS:** Never use legacy ReactDOM.render or call createRoot without verifying the container.

```jsx wrong title="Legacy Synchronous Mount"
import ReactDOM from 'react-dom';
import NewsApp from './NewsApp.jsx';

// Fails in React 19: disables concurrent rendering
ReactDOM.render(<NewsApp />, document.getElementById('root'));
```
