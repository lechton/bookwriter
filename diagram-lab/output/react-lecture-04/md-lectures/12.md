### Mathematical Purity and the Render Phase

In computer science, a function is considered **pure** if it satisfies two strict criteria: (1) It minds its own business: it does not change any objects or variables that existed before the function was called. (2) Same inputs, same output: given the exact same arguments, the function always returns the exact same result. In React, component functions are executed repeatedly whenever state or props change. If a component modifies external variables during render, each execution produces unpredictable results.

React's rendering process must always be pure. Your component function should only calculate and return JSX: it should never mutate global variables, modify preexisting objects, or trigger network requests during the render phase. When a component is pure, React can pause rendering, discard work, re-order renders, or reuse cached results safely.

Local mutation is completely fine. If you create a variable or an array inside the component during render: `const items = []; items.push(1);`, that mutation is invisible to the outside world because the array was created within the same render pass. What is strictly forbidden is mutating variables declared outside the component or mutating objects passed in through props.

```jsx title="Pure Component Contrast"
// IMPURE: Mutates external variable during render!
let guestCount = 0;
function BadCounter() {
  guestCount = guestCount + 1; // Mutates outer variable!
  return <p>Guest #{guestCount}</p>;
}
// PURE: Computes output purely from incoming props:
function GoodCounter({ index }) {
  return <p>Guest #{index + 1}</p>;
}
```

By ensuring that components only compute output from their inputs, your UI becomes deterministic and predictable.

> [!WILD]
> **Why does React call components twice in development?** Imagine Elena runs her app and sees `storyCount` jump by 2 instead of 1 on the very first page load. She thinks React has a bug. In reality, React's `<StrictMode>` intentionally calls every component function twice in development mode. Why? React does this as an automated audit to expose accidental impurities. If a component is pure, calling it twice produces the identical JSX without changing external state: `f(x) = y`, and running it again still produces `y`. But if the component mutates an external variable (`count++`), running it twice causes the count to double immediately, alerting the developer to the bug before shipping to production.

### Quarantining Side Effects

Real-world applications cannot be 100% pure: they must fetch data, update the DOM, play sounds, and send analytics. If components must be pure during render, where do side effects belong?

In React, side effects are **quarantined**. They belong in two specific places: (1) **Event handlers**: functions that run in response to user actions like clicking a button or submitting a form. Event handlers run after the render phase is complete, so they are free to perform side effects. (2) **Effects (`useEffect`)**: an escape hatch hook for synchronizing with external systems, which runs after React has committed the DOM to the screen.

By keeping the render phase strictly pure, React guarantees that your user interface is a predictable projection of state and props. If something changes on screen, it changes because state changed, never because a component function happened to execute.

```jsx title="Quarantining Side Effects"
// WRONG: Side effect in render phase!
function BadStory({ id }) {
  fetch(`/api/track/${id}`); // Fires on every render!
  return <h2>Story {id}</h2>;
}
// RIGHT: Side effect quarantined in event handler:
function GoodStory({ id }) {
  const handleRead = () => fetch(`/api/track/${id}`);
  return <button onClick={handleRead}>Read Story</button>;
}
```

By strictly separating pure render calculations from post-render side effects, your application stays resilient against race conditions and unexpected re-renders.

> [!WILD]
> **Is mutating a prop object considered an impurity?** Imagine a parent passes `story = { title: 'Election Results' }` to `StoryCard`. Inside `StoryCard`, the author writes `story.viewed = true`. This mutates an object that existed before `StoryCard` was called. Because objects are passed by reference, the parent component and any sibling components sharing `story` now have their data altered without React knowing. This violates the first rule of purity: never modify objects that existed prior to render. React freezes props in development, but mutating nested object properties bypasses shallow freezes and corrupts app state.

### Step 1: First, we construct the parent container NewsroomDesk.jsx

The parent container coordinates the dashboard. It passes an array of stories to `StoryCounter` with explicit index props, avoiding any global counters.

```jsx title="NewsroomDesk.jsx"
import StoryCounter from './components/StoryCounter.jsx';
import EditionBadge from './components/EditionBadge.jsx';
export default function NewsroomDesk({ list = ['Deal', 'Transit'] }) {
  return (
    <main className="desk-shell">
      <EditionBadge edition="Morning" />
      {list.map((t, i) => <StoryCounter key={t} index={i} title={t} />)}
    </main>
  );
}
```

Look at line 7: `{list.map((t, i) => <StoryCounter key={t} index={i} title={t} />)}`. Notice that `NewsroomDesk` passes the index `i` explicitly as a prop. It does not increment a global variable. Every time `NewsroomDesk` renders, it passes the same inputs to each `StoryCounter`. We will build `StoryCounter` next in step 2.

### Step 2: Next, we declare the counter child StoryCounter.jsx

Step 1 passed `index` and `title` to `StoryCounter`. The child component must compute the display number (`index + 1`) purely without touching external variables.

```jsx title="StoryCounter.jsx"
export default function StoryCounter({ index, title }) {
  const displayNum = index + 1; // Pure **LOCAL** calculation
  return (
    <li className="story-item">
      <span className="story-num">#{displayNum}</span>
      <span className="story-title">{title}</span>
    </li>
  );
}
```

Look at line 2: `const displayNum = index + 1;`. This calculation is 100% pure: given `index = 0`, it will always produce `displayNum = 1`. If React renders this component twice under StrictMode, `displayNum` is calculated twice, but no external memory is modified. The output remains identical.

What would happen if `StoryCounter` used a global `let count = 0` outside the component and wrote `count++` inside the function? Under StrictMode, React would run the component function twice for each story. Story 1 would display `#2`, Story 2 would display `#4`, and the next re-render would inflate the numbers to `#6` and `#8`. By calculating from `index + 1`, the component is completely immune to render count variations.

### Step 3: Then, we declare the badge child EditionBadge.jsx

Step 1 embedded `<EditionBadge edition="Morning" />`. The terminal badge component derives its text purely from the `edition` prop.

```jsx title="EditionBadge.jsx"
export default function EditionBadge({ edition }) {
  const label = `${edition} Edition`; // Pure string derivation
  return (
    <span className="edition-badge">
      {label} // Rendered **DERIVED** label
    </span>
  );
}
```

Look at lines 1 through 7: `EditionBadge` derives its label purely from `edition`. It causes zero side effects, touches zero external variables, and always produces the same badge for the same prop value.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the pure component tree. Now we inspect `main.jsx`, which wraps `NewsroomDesk` in `<StrictMode>` and mounts to the DOM.

```jsx title="main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import NewsroomDesk from './NewsroomDesk.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container); // Acquires container in **MEMORY**
root.render(<StrictMode><NewsroomDesk /></StrictMode>); // Audits **PURITY**
```

Look at line 7: `root.render(<StrictMode><NewsroomDesk /></StrictMode>)`. React mounts `NewsroomDesk` under `StrictMode`. React executes each component function twice in development to audit purity. Because all our components are pure, the rendered DOM is identical on both passes, proving the architecture is robust and production-ready.

Now let us examine a subtle detail regarding local mutation.

Can pure components use local variables? Imagine an engineer wants to build an array of items during render: `const rows = []; for (let i = 0; i < 5; i++) { rows.push(<Row key={i} />); }`. Does this violate purity? No! The variable `rows` was created inside the function during this specific render call. No other component or function can see `rows`. When the function finishes, `rows` is returned as JSX. This is called **local mutation**. Purity only forbids mutating things that existed before the render started (like global variables, props, or parent state).

### Glossary
- **Pure Component**: A component function that produces identical JSX for the same props and state without causing observable side effects during render.
- **Side Effect**: Any modification of external state, network request, timer, or DOM mutation that occurs outside the pure calculation of JSX.
- **Render Phase**: The phase where React calls component functions to compute the next Virtual DOM tree; must be completely free of side effects.
- **Commit Phase**: The phase where React applies changes to the actual DOM and runs layout/passive effects.
- **StrictMode**: A React development-only tool that double-renders components to expose side effects and impurities in the render phase.
- **Local Mutation**: Modifying variables or objects created within the current component's render execution, which is completely safe and pure.

### Summary

**React 19 Pure Component Invariants**

In daily production, component purity is the bedrock of predictable, scalable React applications. Keeping the render phase free of side effects ensures components are resilient to re-renders and ready for concurrent React features. Here is your streetwise review.

❒ Pure Component Invariants

1. Same inputs must always return the same JSX output.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Compute all display values directly from props and state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Never read or modify mutable global variables during render.

2. Quarantine all side effects in event handlers or Effects.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Never initiate API calls, timers, or DOM mutations during render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Embrace StrictMode double-rendering in development to detect impurities early.

➔ NEVER mutate a variable declared outside the component function during render.

➔ ALWAYS compute derived values locally using incoming props and state.

➔ IF you need to perform an action that changes the outside world THEN **place it inside an event handler or a `useEffect` hook**.

**DO THIS:** Compute values locally from props and return deterministic JSX.

```jsx right title="StoryCounter.jsx"
// Pure calculation derived entirely from props
export default function StoryCounter({ index, title }) {
  const displayNum = index + 1;
  return <li>#{displayNum}: {title}</li>;
}
```

**DO NOT DO THIS:** Never mutate an external variable inside a component function.

```jsx wrong title="External Mutation Anti-Pattern"
// FAILS: Mutates global variable during render; doubles in StrictMode!
let globalCount = 0;
export default function BrokenCounter({ title }) {
  globalCount++; // Impure! Corrupts state on re-render
  return <li>#{globalCount}: {title}</li>;
}
```
