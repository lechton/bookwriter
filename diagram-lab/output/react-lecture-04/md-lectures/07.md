### Why We Split Components Across Files

In earlier lessons, we learned how to write React components as JavaScript functions that return JSX markup (see Lectures 3, 4, and 5). You can declare five or ten component functions in a single `App.jsx` file, and React will render them without complaint. As your application grows, keeping multiple components in one file creates an unmaintainable monolith where styling, logic, and markup tangle together.

In plain browser scripts without module loaders, any function declared in a script tag enters the global scope (`window`). If two scripts declare a function with the same name, the second silently overwrites the first. In modern web development, Vite and React rely on ECMAScript Modules (ES Modules). Every JavaScript or JSX file is an isolated module: nothing declared inside is accessible from the outside world unless you explicitly export it.

```jsx title="Module Organization Contrast"
// Legacy Global Namespace (Error-Prone):
window.NewsApp = { Header: function Header() { /* ... */ } };
// Modern ES Module Architecture (Isolated & Type-Safe):
// In SiteHeader.jsx:
export default function SiteHeader() { return <header>...</header>; }
// In NewsPortal.jsx:
import SiteHeader from './SiteHeader.jsx'; // Explicit dependency link
```

In legacy JavaScript applications, developers had to concatenate scripts in a specific order in `index.html` or attach components to a shared global namespace object like `window.App.Components = {}`. This pattern caused ordering bugs and naming collisions. Modern ES modules isolate each file into its own module scope, turning components into modular building blocks.

> [!WILD]
> **Why not keep all components in one file?** Imagine three journalists and two engineers are working on The National Times homepage at 4:00 PM before deadline. Elena is updating the breaking news banner, Marcus is redesigning the article card, and David is fixing a typo in the footer. If all three components live in `App.jsx`, every person is editing the exact same file. When they push their changes to Git, they hit massive merge conflicts, overwriting each other's code. By splitting each component into its own file ending in `.jsx`, each developer owns an isolated file. Git merges become effortless, components become reusable across pages, and the codebase stays clean.

### Default Exports versus Named Exports

When you split components into separate files, you need a mechanism to share them: you export a component from its home file and import it where it is needed. JavaScript provides two distinct ways to export code: default exports and named exports. Beginners often mix up the syntax, putting curly braces where they do not belong and triggering baffling runtime errors.

A **default export** designates the primary value or component that a file provides. A file can have at most one default export, declared with the keywords `export default`. When importing a default export, you do not use curly braces: `import SiteHeader from './SiteHeader.jsx'`. Because it is the default value of that module, the importing file can choose any local identifier for it (for example `import Header from './SiteHeader.jsx'`).

A **named export** allows a single file to export multiple functions, components, or constants, each identified by its specific name. You declare named exports by prefixing declarations with `export` (like `export function ArticleCard()`) or using an export list: `export { ArticleCard, ArticlePill }`. When importing named exports, you must wrap their identifiers in curly braces: `import { ArticleCard, ArticlePill } from './ArticleComponents.jsx'`. The imported names must match the exported names exactly, unless you rename them explicitly using the `as` keyword: `import { ArticleCard as Card } from './ArticleComponents.jsx'`.

```jsx title="Export and Import Patterns"
// 1. Default Export (One per file, imported without curly braces):
import SiteHeader from './SiteHeader.jsx'; // Local name can vary
// 2. Named Exports (Multiple per file, imported with curly braces):
import { ArticleCard, ArticlePill } from './ArticleComponents.jsx';
// 3. Named Export with Renaming Alias:
import { ArticleCard as FeaturedStory } from './ArticleComponents.jsx';
```

What is the **curly brace trap**? This is the single most common import bug in React development. If a component is exported with `export default function SiteHeader()`, and you import it with curly braces: `import { SiteHeader } from './SiteHeader.jsx'`, what happens? The browser or bundler looks inside the module's export dictionary for a named property called `SiteHeader`. Because `SiteHeader` was exported as the default, the named property does not exist: the import resolves to `undefined`. When React tries to render `<SiteHeader />`, it evaluates `<undefined />` and crashes with: `Element type is invalid: expected a string (for built-in components) or a class/function (for composite components) but got: undefined`.

> [!WILD]
> **Why does importing a component yield undefined?** Imagine you order a package from a delivery service addressed to "The Resident" (the default recipient). When the courier arrives, they ask: "Is there a package specifically labeled for SiteHeader?" The courier checks the manifest, sees only "The Resident", and declares: "Nothing found under that specific name: result is undefined." In JavaScript, `export default` puts the component in the box labeled `default`. Writing `import SiteHeader` (without curly braces) reaches into the box and grabs the default item. Writing `import { SiteHeader }` (with curly braces) tells JavaScript to look for a specific named slot called `SiteHeader`. That slot is empty, so JavaScript hands you `undefined`. When React attempts to render `undefined`, your app crashes immediately.

### Step 1: First, we construct the parent container NewsPortal.jsx

We start our implementation with the parent container: `NewsPortal.jsx`.

The parent coordinates the page layout and imports child components from separate files using both default and named import syntax:

```jsx title="NewsPortal.jsx"
import SiteHeader from './components/SiteHeader.jsx';
import { ArticleList } from './components/ArticleComponents.jsx';
export default function NewsPortal() {
  return (
    <div className="news-portal">
      <SiteHeader edition="Morning Print" /> // Default import child
      <ArticleList desk="International" /> // Named import child
    </div>
  );
}
```

Look at lines 1 and 2: notice that `SiteHeader` is imported without curly braces because it is a default export, while `ArticleList` is enclosed in `{ ArticleList }` because it is a named export.

Now look at lines 6 and 7: `<SiteHeader edition="Morning Print" />` and `<ArticleList desk="International" />`. We have not written either child component yet. But right here in the parent, we establish their contracts and layout relationship. We will build `SiteHeader` next in step 2.

To recap this step: the parent container establishes explicit import contracts with its child components before those children are built.

### Step 2: Next, we build the default export child SiteHeader.jsx

In step 2, we fulfill the contract established by the parent: we build `SiteHeader.jsx`.

This child component renders the editorial masthead title and edition badge:

```jsx title="SiteHeader.jsx"
export default function SiteHeader({ edition }) {
  return (
    <header className="site-header">
      <h1 className="masthead-title">The National Times</h1>
      <span className="edition-badge">{edition}</span> // Status badge in **HEADER**
    </header>
  );
}
```

Look at line 1: `export default function SiteHeader({ edition })`. The keyword `default` tells JavaScript that this function is the primary export of this file.

Notice that any consuming file can import this component using any name it wants. If you ever put curly braces around `SiteHeader` when importing from this file, the import will resolve to `undefined` and crash the render pass.

What would happen if `SiteHeader` also declared and exported article feed components directly?

If you put article rendering logic and data fetching inside `SiteHeader`, the header would be trapped managing article lists and layout feeds. The masthead would re-render whenever articles changed. By separating them into their own files, `SiteHeader` owns zero article state and zero list logic. If tomorrow you redesign the masthead, you touch zero lines of article code.

To recap this step: a default export represents the primary component of a dedicated file, isolating markup and preventing unnecessary re-renders.

### Step 3: Then, we declare the named exports in ArticleComponents.jsx

In step 3, we build `ArticleComponents.jsx`, which exports both `ArticleList` and `ArticleCard` as named exports from a single module:

```jsx title="ArticleComponents.jsx"
export function ArticleCard({ title, category }) {
  return <article className="article-card"><span className="pill">{category}</span><h3>{title}</h3></article>;
}
export function ArticleList({ desk }) {
  return (
    <section className="article-list">
      <ArticleCard title="Peace Treaty" category={desk} /> // Named component in **FEED**
    </section>
  );
}
```

Look at lines 1 and 4: `export function ArticleCard` and `export function ArticleList`. Neither declaration uses the `default` keyword.

Because both functions are named exports, consumers must use curly braces: `import { ArticleList } from './ArticleComponents.jsx'`. If a consuming file only needs `ArticleCard`, it can import `ArticleCard` alone without importing `ArticleList`, enabling bundlers to optimize the build.

To recap this step: named exports allow a single module to share multiple related components, and consumers import them using exact curly brace syntax.

### Step 4: Finally, we seal the application entry point main.jsx

In step 4, we inspect `main.jsx`, which imports `NewsPortal` as a default export and mounts it to the DOM using `createRoot` (as learned in Lecture 6):

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import NewsPortal from './NewsPortal.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container); // Initializes root in **MEMORY**
root.render(<NewsPortal />); // Mounts root component into **DOM**
```

Look at line 2: `import NewsPortal from './NewsPortal.jsx'`. `NewsPortal` is imported as a default export without curly braces.

When `root.render(<NewsPortal />)` executes on line 6, React mounts `NewsPortal`, which in turn evaluates `SiteHeader`, `ArticleList`, and `ArticleCard`. The browser bundles these separate files into an optimized module graph, keeping the source code clean and modular on disk.

To recap this final step: the entry point imports the root component as a default export and mounts the entire modular component tree into the DOM.

### Lessons from the Experiment: Naive Expectation vs Reality

To review the architectural lessons from this implementation, examine the component hierarchy:

```component-code title="Summary: The Logic of Nested Components"
NewsPortal.jsx | none | parent | [role: This is the **parent layout container**. It coordinates the page structure by importing `SiteHeader` via default import and `ArticleList` via named import. Why? To demonstrate how a container integrates components from different module boundaries into a single unified layout.]
  SiteHeader.jsx | edition="Morning Print" | child | [role: This is a **default export child component**. It encapsulates the masthead title and edition badge in its own isolated file. Why? To prove that primary components can be exported with `export default` and imported without curly braces under any local name.]
  ArticleComponents.jsx | desk="International" | bundle | [role: This is a **named export component module**. It exports both `ArticleList` and `ArticleCard` from a single file. Why? To prove that multiple related components can share a file and be selectively imported using curly braces `{ ArticleList }`.]
```

In the naive approach, developers keep all components inside a single thousand-line file to avoid learning import syntax. When they eventually split files, they mix up default and named exports, using curly braces everywhere and triggering mysterious `undefined` runtime errors.

In the React 19 reality, components are split into single-responsibility files using ES modules. Primary components use `export default` and import without braces, while utility collections use named exports with curly braces.

> [!WILD]
> **Can you mix default and named exports in one file?** Imagine you are writing a comprehensive UI kit file for buttons. You have a main `Button` component that almost every screen uses. But you also have small utility variations, like `IconButton` and `ButtonGroup`. Can you export `Button` as the default, and also export `IconButton` as a named export? Yes, absolutely. You write `export default function Button() { ... }` and on the next line `export function IconButton() { ... }`. In the consumer file, you can import both in a single line, placing the default export outside the curly braces and the named export inside: `import Button, { IconButton } from 'ui-library'`. Notice how the default export sits outside the curly braces, and the named export sits inside.

> [!TIP]
> **To impress the interviewer:** When asked how default and named exports differ under the hood, explain that an ES module produces a single namespace object. Named exports become keys on that object (`module.ArticleCard`). A default export is simply a named export stored under the special key `default` (`module.default`). When you write `import SiteHeader from './SiteHeader.jsx'`, the runtime assigns `module.default` to your local variable. When you write `import { SiteHeader }`, the runtime looks for `module.SiteHeader`. If the file used `export default`, `module.SiteHeader` is `undefined`, triggering React's infamous `Element type is invalid` runtime error.

### Where you will meet this

- Organizing component libraries: structuring UI directories with one component per file or grouping small related primitives into a single module.
- Importing third-party React libraries: importing default components from libraries (`import React from 'react'`) versus named hooks (`import { useState, useEffect } from 'react'`).
- Barrel files (index.js): re-exporting multiple components from a folder to provide a clean public entry point without deep path nesting.
- Fast Refresh and bundler optimization: keeping one component per file so Vite's Hot Module Replacement updates only the edited component without reloading the page.

### Glossary

- **ES Module**: The official ECMAScript standard for modular JavaScript files that use `import` and `export` statements with isolated module scope.
- **Default Export**: A module export declared with `export default` representing the primary value of the file; imported without curly braces.
- **Named Export**: A module export declared with `export` and identified by its variable or function name; imported using curly braces.
- **Curly Brace Trap**: The common runtime bug where a default export is imported with curly braces, resulting in `undefined` and crashing React.
- **Module Scope**: The isolated execution environment of a module where top-level variables and functions are private unless explicitly exported.
- **Tree Shaking**: The dead-code elimination process performed by bundlers like Rollup and Vite that removes unused named exports from the final bundle.

❒ Export Patterns and Import Syntax Rules

1. Choose the right export strategy for each file.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Use `export default` when a file has one primary component, like `export default function SiteHeader()`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use named exports when a file exports multiple related components or utility functions, like `export function ArticleCard()`.

2. Match your import syntax strictly to the export declaration.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Import default exports without curly braces: `import SiteHeader from './SiteHeader.jsx'`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Import named exports with curly braces: `import { ArticleCard } from './ArticleComponents.jsx'`.

➔ NEVER use curly braces when importing a default export, which evaluates to `undefined` and crashes React.

➔ ALWAYS name your component file to match its primary component, such as `SiteHeader.jsx` for `SiteHeader`.

➔ IF you need to rename a named export during import THEN **use the `as` keyword like `import { ArticleCard as Card }`**.

**DO THIS:** Match the import syntax to the export type and verify that default exports are imported without curly braces.

```jsx right title="NewsPortal.jsx"
// Default export: no curly braces
import SiteHeader from './SiteHeader.jsx';
// Named export: exact curly braces
import { ArticleCard } from './ArticleComponents.jsx';

export default function NewsPortal() {
  return (
    <div>
      <SiteHeader />
      <ArticleCard title="News" />
    </div>
  );
}
```

**DO NOT DO THIS:** Never import a default export using curly braces.

```jsx wrong title="Curly Brace Anti-Pattern"
// FAILS AT RUNTIME: SiteHeader evaluates to undefined!
import { SiteHeader } from './SiteHeader.jsx';

export default function BrokenPortal() {
  // Crashes: Element type is invalid: expected string or function but got undefined
  return <SiteHeader />;
}
```
