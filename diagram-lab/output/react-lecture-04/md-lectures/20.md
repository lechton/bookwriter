### The Controlled Input Contract

In HTML, form elements like `<input>` maintain their own internal state in the browser DOM. When a user types, the DOM node updates its own `value` property directly. Why does passing `value={text}` without an `onChange` handler freeze the input and prevent the user from typing?

In React, a **controlled input** transfers ownership of the input's value from the DOM to React state. The component's state becomes the **single source of truth**. This requires a two-way contract: (1) `value={state}` pushes the current state into the DOM on every render. (2) `onChange={e => setState(e.target.value)}` intercepts user keystrokes, reads the event value, and updates state. If you supply `value` without `onChange`, React re-renders on every keystroke and forces the input's DOM value back to the state snapshot, freezing the input completely.

If you only want to set the initial value and let the DOM handle user typing, use `defaultValue="Initial text"` instead of `value`. This creates an **uncontrolled input**, where React sets the initial DOM value on mount and never touches it again.

```jsx title="Controlled vs Uncontrolled Input"
// CONTROLLED: React state is the single source of truth:
<input value={text} onChange={e => setText(e.target.value)} />
// UNCONTROLLED: DOM owns the state after mount:
<input defaultValue="Initial text" />
```

By establishing React state as the sole authority, controlled inputs allow you to validate, format, and synchronize input values instantaneously.

> [!WILD]
> **What happens if state transforms or filters the value inside onChange?** Can you force an input to stay uppercase or strip special characters inside `onChange`? Yes! Because React controls the value, you can sanitize input in real time: `onChange={e => setText(e.target.value.toUpperCase())}`. When the user types lowercase 'a', `onChange` runs, converts it to 'A', and updates state. React re-renders and pushes 'A' into the DOM. The user physically cannot type a lowercase letter. Controlled inputs give you absolute authority over what appears in the field.

### Textareas, Selects, and Multi-Field State

In standard HTML, `<textarea>` uses child text (`<textarea>hello</textarea>`), and `<select>` uses `<option selected>`. How does React standardize textareas and selects into the controlled component model?

React eliminates HTML's syntax inconsistencies by standardizing `<textarea>` and `<select>` to use the exact same `value` and `onChange` props as `<input>`. In React, `<textarea value={text} onChange={e => setText(e.target.value)} />` takes `value` directly instead of children. Similarly, `<select value={choice} onChange={e => setChoice(e.target.value)}>` takes `value` on the `<select>` tag itself, automatically selecting the matching child `<option>`.

For forms with multiple fields, you can either declare individual `useState` calls (`const [name, setName] = useState('')`) or manage a single form object (`const [form, setForm] = useState({ name: '', email: '' })`) updated via `setForm(f => ({ ...f, [e.target.name]: e.target.value }))`.

```jsx title="Controlled Select and Textarea"
// Unified value and onChange across all form elements:
<select value={role} onChange={e => setRole(e.target.value)}>
  <option value="reporter">Reporter</option>
  <option value="editor">Editor</option>
</select>
<textarea value={bio} onChange={e => setBio(e.target.value)} />
```

Standardizing all form controls around `value` and `onChange` creates a coherent, predictable programming model across every input type.

> [!WILD]
> **What is the "uncontrolled to controlled" warning?** Why does React warn `A component is changing an uncontrolled input to be controlled`? If you initialize state to `undefined` or omit it (`useState()`), `value={text}` evaluates to `undefined`. React treats `value={undefined}` as an uncontrolled input! When the user types, state updates to a string (e.g. `'a'`), and `value` is suddenly a defined string. React sees the input switch from uncontrolled to controlled and throws a console warning. Always initialize form state with empty strings: `useState('')`.

### Step 1: First, we construct the parent container CorrectionDesk.jsx

The parent container owns the text state initialized to `''`. It passes `text` to both `CorrectionInput` and `CorrectionPreview`.

```jsx title="CorrectionDesk.jsx"
import { useState } from 'react';
import CorrectionInput from './components/CorrectionInput.jsx';
import CorrectionPreview from './components/CorrectionPreview.jsx';
export default function CorrectionDesk() {
  const [text, setText] = useState('');
  return (
    <main><CorrectionInput value={text} onChange={setText} /><CorrectionPreview text={text} /></main>
  );
}
```

Look at line 5: `useState('')`. Notice that we initialize `text` to an empty string rather than `undefined` to guarantee the input starts and remains controlled. We will build `CorrectionInput` next in step 2.

### Step 2: Next, we declare the input child CorrectionInput.jsx

Step 1 passed `value={text}` and `onChange={setText}` to `CorrectionInput`. The child component must bind both props to an HTML input.

```jsx title="CorrectionInput.jsx"
export default function CorrectionInput({ value, onChange }) {
  return (
    <input
      className="correction-field"
      onChange={e => onChange(e.target.value)}
      placeholder="Type correction..."
      value={value}
    />
  );
}
```

Look at lines 3 through 8: `value={value}` forces the DOM node to match React state, while `onChange={e => onChange(e.target.value)}` captures user typing and updates state.

### Step 3: Then, we declare the preview child CorrectionPreview.jsx

Step 1 passed `text` to `CorrectionPreview`. The child component must render the live note in real time.

```jsx title="CorrectionPreview.jsx"
export default function CorrectionPreview({ text }) {
  return (
    <div className="preview-card">
      <h2>Live Note</h2>
      <p>{text || 'No correction entered yet.'}</p>
    </div>
  );
}
```

Look at lines 1 through 8: `CorrectionPreview` receives `text` via props and displays it. Because `CorrectionDesk` updates state on every keystroke, the preview synchronizes with the user's typing in real time.

What would happen if `CorrectionInput` omitted the `onChange` prop? The `<input>` element would receive `value={text}` on every render. When the user pressed a key, the browser would attempt to insert the character, but React would immediately re-render and reset the DOM `value` back to `text`, rendering the input completely uneditable.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the controlled component tree. Now we inspect `main.jsx`, which mounts `CorrectionDesk` to the DOM.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import CorrectionDesk from './CorrectionDesk.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<CorrectionDesk />);
```

Look at line 6: `root.render(<CorrectionDesk />)`. React mounts `CorrectionDesk`. When the reader types, `onChange` triggers state updates, re-rendering `CorrectionDesk` and pushing the updated text simultaneously into both the `<input>` and the preview card.

Now let us examine an architectural consideration when evaluating typing performance with controlled inputs.

Does a controlled input cause performance problems on fast typing? In 99% of web applications, React's virtual DOM reconciliation takes less than a millisecond: typing remains buttery smooth. If a parent component has expensive computations (like filtering 10,000 items on every keystroke), the lag comes from the expensive calculation, not the controlled input itself. In those cases, keep the controlled input local to its own small component, or debounce/defer the expensive filtering operation using `useDeferredValue`.

### Glossary
- **Controlled Input**: A form element whose displayed value is driven by React state and updated via event handlers.
- **Uncontrolled Input**: A form element that maintains its own internal value in the DOM, optionally initialized via `defaultValue`.
- **Two-Way Contract**: The pair of `value={state}` and `onChange={handler}` props required to make an input controlled and editable.
- **Single Source of Truth**: The architectural design where one piece of state (React state) exclusively determines the value across the application.
- **defaultValue**: An HTML attribute in React used to set the initial value of an uncontrolled input on mount.
- **Event Target Value**: The `e.target.value` property extracted from the browser event representing the current text inside the input element.

### Summary

**React 19 Controlled Input Invariants**

In daily production, controlled inputs provide total authority over form data, validation, and real-time UI synchronization. Implementing the two-way contract properly guarantees editable, predictable form controls. Here is your streetwise review.

❒ Controlled Input Invariants

1. Controlled inputs require both `value` and `onChange`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `value={state}` pushes state into the DOM.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) `onChange={e => setState(e.target.value)}` pulls user edits into state.

2. Never supply `value` without `onChange` unless the input is explicitly read-only.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Omitting `onChange` freezes the input and triggers React warnings.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use `readOnly` if the input is meant to display uneditable text.

3. Always initialize controlled input state to an empty string `''`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Initializing to `undefined` or `null` makes the input start as uncontrolled.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Updating it later triggers the "uncontrolled to controlled" warning.

➔ NEVER initialize controlled form state to `undefined` or `null`.

➔ ALWAYS pair `value` with `onChange` on inputs, textareas, and selects.

➔ IF an input is completely independent and only read at submit THEN **consider an uncontrolled input with `defaultValue`**.

**DO THIS:** Pair value and onChange to maintain full control over the input.

```jsx right title="CorrectionInput.jsx"
// Fully controlled input with two-way synchronization
export default function CorrectionInput({ value, onChange }) {
  return (
    <input
      onChange={e => onChange(e.target.value)}
      value={value}
    />
  );
}
```

**DO NOT DO THIS:** Never supply value without onChange expecting the user to type freely.

```jsx wrong title="Frozen Input Anti-Pattern"
// FAILS: Value is supplied without onChange; input is frozen!
export default function BrokenInput({ value }) {
  return (
    <input
      value={value}
    />
  );
}
```
