### Imperative DOM Manipulation vs Declarative State

In traditional JavaScript (vanilla DOM scripting), when you want to change the screen in response to user input, you write imperative instructions: find an element (`document.querySelector`), disable it, find a spinner, show it, find an error banner, hide it. Why does imperative DOM manipulation quickly lead to bugs in complex user interfaces?

In imperative programming, you must manually orchestrate every DOM mutation for every possible transition. As the number of UI elements and states grows, the number of manual transitions explodes exponentially ($2^n$). If you forget to hide a spinner on error, or fail to re-enable a button on retry, the UI enters an **impossible state** (e.g. showing both a loading spinner and a success message simultaneously).

React inverts this model: you never manipulate DOM nodes directly. Instead, you declare **what the UI looks like for any given state**. The component function acts as a pure projection: $UI = f(state)$. When input occurs, your event handlers simply update the state, and React handles the DOM updates automatically.

```jsx title="Imperative vs Declarative UI"
// IMPERATIVE: Manually poking DOM nodes (Fragile):
// btn.disabled = true; spinner.classList.remove('hidden');
// DECLARATIVE: Driving UI purely from state (Robust):
<button disabled={status === 'submitting'}>
  {status === 'submitting' ? <Spinner /> : 'Submit'}
</button>
```

By expressing user interfaces as pure projections of state, React eliminates the fragile manual plumbing that characterizes imperative DOM programming.

> [!WILD]
> **What is an "impossible state"?** Why is `const [isSubmitting, setIsSubmitting] = useState(false)` and `const [isSuccess, setIsSuccess] = useState(false)` risky? If you use independent boolean flags for mutually exclusive states, you can accidentally set both to `true` at the same time: `isSubmitting === true` AND `isSuccess === true`. The UI tries to render both a spinner and a success banner! By replacing multiple booleans with a single status string: `const [status, setStatus] = useState('typing')` (where status is `'typing' | 'submitting' | 'success' | 'error'`), it becomes mathematically impossible to be in two states at once.

### The Five Steps of Declarative UI Design

We know React replaces imperative DOM manipulation with declarative state machines. What is the disciplined, step-by-step process for designing a component from scratch?

React's official methodology breaks component design into five steps: (1) **Identify visual states**: sketch all visual modes (empty, typing, submitting, success, error). (2) **Determine triggers**: identify human inputs (typing, clicking) and computer inputs (network responses, timeouts) that cause transitions. (3) **Represent state in memory**: declare minimal state with `useState`. (4) **Remove non-essential state**: eliminate redundant or derived state that can be calculated during render. (5) **Connect event handlers**: wire up user interactions to set state.

Following this five-step process prevents premature optimization and ensures your component state remains minimal, clean, and impossible to desynchronize.

```jsx title="State Machine Status Transitions"
// Valid states: 'typing' -> 'submitting' -> 'success' | 'error'
function handleSubmit() {
  setStatus('submitting');
  sendDispatch()
    .then(() => setStatus('success'))
    .catch(() => setStatus('error'));
}
```

Grounding every interaction in defined transitions ensures state changes remain predictable across the entire component lifecycle.

> [!WILD]
> **How do you know if a state variable is redundant?** Should you store `isEmpty` in state alongside `text`? Ask three questions: (1) Does it remain unchanged over time? If so, not state. (2) Is it passed in from a parent via props? If so, not state. (3) Can you compute it from existing state or props? If so, definitely not state! `const isEmpty = text.length === 0` can be calculated directly during render. Storing `isEmpty` in state creates two places to update, creating synchronization bugs.

### Step 1: First, we construct the parent container DispatchStatus.jsx

The parent container owns the state machine status. It passes `status` and `onSend` down to children.

```jsx title="DispatchStatus.jsx"
import { useState } from 'react';
import StatusForm from './components/StatusForm.jsx';
import StatusAlert from './components/StatusAlert.jsx';
export default function DispatchStatus() {
  const [status, setStatus] = useState('typing');
  return (
    <main><StatusForm status={status} onSend={() => setStatus('success')} /><StatusAlert status={status} /></main>
  );
}
```

Look at line 5: `const [status, setStatus] = useState('typing');`. The entire UI's appearance is governed by this single status variable. We will build `StatusForm` next in step 2.

### Step 2: Next, we declare the form child StatusForm.jsx

Step 1 passed `status` and `onSend` to `StatusForm`. The child component must declare its form controls to reflect the active status.

```jsx title="StatusForm.jsx"
export default function StatusForm({ status, onSend }) {
  const isSubmitting = status === 'submitting';
  return (
    <form onSubmit={e => { e.preventDefault(); onSend(); }}>
      <input disabled={isSubmitting} placeholder="Headline" />
      <button disabled={isSubmitting} type="submit">Submit</button>
    </form>
  );
}
```

Look at line 2: `const isSubmitting = status === 'submitting'`. Notice that `isSubmitting` is NOT a state variable: it is derived during render. The `disabled` attributes on the input and button are driven directly by this calculation.

### Step 3: Then, we declare the alert child StatusAlert.jsx

Step 1 passed `status` to `StatusAlert`. The child component must render feedback only when the dispatch succeeds.

```jsx title="StatusAlert.jsx"
export default function StatusAlert({ status }) {
  if (status !== 'success') return null;
  return (
    <div className="status-alert">
      <p>Dispatch broadcasted to newsroom.</p>
    </div>
  );
}
```

Look at line 2: `if (status !== 'success') return null;`. Rather than querying a DOM element and toggling `.hidden`, the component returns `null` when inactive, and JSX when active.

What would happen if `DispatchStatus` used direct DOM queries like `document.querySelector('.status-alert').classList.add('visible')`? Because React re-renders and manages DOM nodes dynamically, imperative class mutations would be wiped out or cause hydration mismatches on the next render pass. React's virtual DOM must remain the single source of truth.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the declarative component tree. Now we inspect `main.jsx`, which mounts `DispatchStatus` to the DOM.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import DispatchStatus from './DispatchStatus.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<DispatchStatus />);
```

Look at line 6: `root.render(<DispatchStatus />)`. React mounts the component tree. When the user submits, `setStatus('success')` transitions the state machine, triggering a clean re-render where the form and alert update in perfect harmony.

Now let us examine an architectural consideration when handling complex branching workflows.

How do you handle complex multi-step forms with state machines? For simple components with 3 to 5 states, a plain `useState('typing')` string is clean and lightweight. When a component has complex branching logic, timeouts, rollback transitions, or nested parallel states (like an airplane booking wizard), a formal state machine library like XState ensures that only valid transitions can occur, preventing edge-case bugs that scatter across dozens of event handlers.

### Glossary
- **Declarative UI**: A programming paradigm where you describe what the UI should look like for any given state, rather than how to change it imperatively.
- **State Machine**: A model consisting of a finite set of distinct states, where a system can only exist in exactly one state at any given time.
- **Impossible State**: A buggy UI condition where mutually exclusive visual elements (like a spinner and an error banner) are displayed simultaneously.
- **Derived State**: A value that is computed dynamically during rendering from existing props or state, rather than stored separately in `useState`.
- **Imperative DOM Scripting**: Directly querying and modifying DOM nodes using browser APIs (`querySelector`, `classList.add`).
- **Five-Step Design Process**: React's official methodology for architecting state-driven interactive user interfaces.

In daily production, abandoning imperative DOM manipulation in favor of declarative state machines is the hallmark of professional React engineering. Modeling UI as a pure projection of state eliminates impossible states and guarantees synchronization. Here is your streetwise review.

❒ Declarative State Invariants

1. Never query or manipulate DOM elements to change component UI.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Banning `querySelector` and `classList` prevents virtual DOM desynchronization.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Let JSX declare what renders based on the current state.

2. Model mutually exclusive visual states with a single status string.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Replace multiple boolean flags with `'typing' | 'submitting' | 'success'`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Single status strings make impossible states mathematically impossible.

3. Calculate derived values during render instead of storing them in state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) If a value can be computed from existing props or state, do not use `useState`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Eliminating redundant state prevents synchronization bugs.

➔ NEVER use `document.querySelector` or imperative DOM methods inside React components.

➔ ALWAYS model multi-state UI workflows with a single status state machine string.

➔ IF a value can be computed during render THEN **derive it locally without creating a new `useState` variable**.

**DO THIS:** Model visual states declaratively with a status state machine.

```jsx right title="StatusForm.jsx"
// Declarative state machine driving UI appearance
export default function StatusForm({ status, onSend }) {
  const isBusy = status === 'submitting';
  return (
    <button disabled={isBusy} onClick={onSend}>
      {isBusy ? 'Submitting...' : 'Submit'}
    </button>
  );
}
```

**DO NOT DO THIS:** Never query DOM elements to imperatively toggle classes and disabled states.

```jsx wrong title="Imperative DOM Anti-Pattern"
// FAILS: Imperatively manipulates DOM; desyncs with React!
export default function BrokenForm({ onSend }) {
  function handleClick() {
    document.querySelector('.btn-sub').disabled = true;
    onSend();
  }
  return <button className="btn-sub" onClick={handleClick}>Submit</button>;
}
```
