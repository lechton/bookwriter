### Batching and the Update Queue

In Lecture 16, we learned that state is a snapshot and `setTip(tip + 1)` requests a future render pass with the value `0 + 1`. Beginners often expect calling `setTip(tip + 1)` three times in a row to increment the value by three. Why does calling `setTip(tip + 1)` three times only increment the count by one?

React does not immediately re-render after every call to a state setter. Instead, React waits until all code in the event handler has finished running before processing any state updates. This behavior is called **automatic batching**. When you call `setTip(tip + 1)` three times in a handler where `tip` is `0`, you are passing `setTip(0 + 1)` three times. React's queue records: `[replace with 1, replace with 1, replace with 1]`. When the handler finishes, React processes the queue, takes the last instruction, and sets state to `1`.

Batching is a vital performance optimization. If React re-rendered the component and updated the DOM after every setter call, a handler with four updates would cause four separate render passes and layout reflows. Batching ensures your component only re-renders once after all event handler code completes.

```jsx title="Stale Snapshot Updates"
function handleTripleTip() {
  setTip(tip + 1); // Queue: replace with 0 + 1 = 1
  setTip(tip + 1); // Queue: replace with 0 + 1 = 1
  setTip(tip + 1); // Queue: replace with 0 + 1 = 1
  // Final queued result: 1!
}
```

By postponing queue resolution until the event handler finishes, React protects the browser from unnecessary re-renders.

> [!WILD]
> **Why does passing a function change how the queue processes updates?** What does `setTip(prev => prev + 1)` do differently than `setTip(tip + 1)`? When you pass a value like `setTip(1)`, you tell React: "Replace the state with 1." But when you pass a function like `setTip(prev => prev + 1)`, you tell React: "Take whatever state value was computed by the previous queued step, and calculate the next value from it." Instead of storing a fixed value in its queue, React stores the updater function. During the next render pass, React runs each queued function in sequence, feeding the return value of each step into the next one.

### Functional Updates and Queue Processing

We know updater functions chain calculations. How does React process an update queue that contains a mix of direct values and updater functions?

Consider what happens if Elena writes: `setTip(tip + 5); setTip(n => n + 1); setTip(42);`. React queues three actions: (1) `replace with 5`, (2) `n => n + 1`, and (3) `replace with 42`. When the handler ends, React iterates over the queue starting from current state `0`: first, `0` is replaced by `5`; second, the updater function runs with `5` and returns `6`; third, `6` is replaced by `42`. The final state is `42`.

In general, you do NOT need updater functions for simple one-off state changes like `setIsActive(!isActive)`. But you MUST use an updater function whenever: (1) you perform multiple updates on the same state within one handler, (2) you update state based on its previous value inside an asynchronous callback where the closure snapshot might be stale, or (3) you want to extract clean, reusable update actions.

```jsx title="Mixed Update Queue Processing"
function handleComplexUpdate() {
  setTip(tip + 5); // Queue: replace with 5
  setTip(n => n + 1); // Queue: (5) => 6
  setTip(42); // Queue: replace with 42
  // Next render receives tip = 42
}
```

Understanding how values and updater functions interleave ensures your state updates resolve deterministically.

> [!WILD]
> **Must updater functions be pure?** Can an updater function trigger side effects or mutate variables? Updater functions run during rendering! If React renders twice in StrictMode, it runs your updater functions twice to verify they are pure. If an updater function mutates an external variable or attempts to make a network request, it will corrupt your application. An updater function must be a pure calculation: given `pendingState`, it must return `nextState` without touching anything else.

### Step 1: First, we construct the parent container TipJar.jsx

The parent container owns the tip state. It defines `addTriple` using updater functions: `setTip(t => t + 1)` called three times.

```jsx title="TipJar.jsx"
import { useState } from 'react';
import TipDisplay from './components/TipDisplay.jsx';
import TipControls from './components/TipControls.jsx';
export default function TipJar() {
  const [tip, setTip] = useState(0);
  const addTriple = () => {
    setTip(t => t + 1); setTip(t => t + 1); setTip(t => t + 1);
  };
  return <main><TipDisplay tip={tip} /><TipControls onTriple={addTriple} /></main>;
}
```

Look at lines 6 through 8: `addTriple` calls `setTip(t => t + 1)` three times. Because each call passes an updater function, React queues three increment operations: `[t => t + 1, t => t + 1, t => t + 1]`. When React re-renders, it processes the queue sequentially, incrementing `tip` from `0` to `3`. We will build `TipDisplay` next in step 2.

### Step 2: Next, we declare the display child TipDisplay.jsx

Step 1 passed `tip` to `TipDisplay`. The child component must display the current tip total.

Look at lines 1 through 8: `TipDisplay` receives `tip` via props and renders the total. When `TipJar` re-renders after processing the update queue, `TipDisplay` receives the resolved value of `3` and updates the DOM.

### Step 3: Then, we declare the button child TipControls.jsx

Step 1 passed `addTriple` to `TipControls` under `onTriple`. The child component must provide the interactive button to trigger the triple-tip action.

```jsx title="TipControls.jsx"
export default function TipControls({ onTriple }) {
```

Look at lines 1 through 8: `TipControls` renders the button and invokes `onTriple` on click. This queues all three updater functions within a single event loop turn.

What would happen if `addTriple` used `setTip(tip + 1)` three times instead of `setTip(t => t + 1)`? Each call would pass `0 + 1 = 1` because `tip` is frozen at `0` for the duration of that render. The queue would contain `[replace with 1, replace with 1, replace with 1]`, and clicking the button would only increase the tip by 1 dollar instead of 3.

Now let us examine an architectural consideration when deciding whether an updater function is necessary.

When should you NOT use an updater function? Should developers write every state update as an updater function just in case? No! If you are setting state to a replacement value that does not depend on the previous state (like `setSelectedTab('news')` or `setName(e.target.value)`), an updater function adds unnecessary boilerplate: `setSelectedTab(() => 'news')` is redundant. Use updater functions specifically when the next state depends on the previous state and multiple updates may be queued.

> [!TIP]
> **To impress the interviewer:** When asked how React handles multiple `setState` calls in one handler, explain automatic batching and the update queue. State that direct values (`setCount(count + 1)`) queue replacement instructions that overwrite each other because they evaluate against the frozen render snapshot. By contrast, updater functions (`setCount(c => c + 1)`) queue pure reduction functions that React iterates over sequentially during the next render, passing the result of each step into the next.

### Where you will meet this
- Increment/decrement counters: building quantity pickers, pagination buttons, or like counters.
- Multi-step wizards: advancing steps or accumulating form sections where multiple updates fire in rapid succession.
- Asynchronous handlers: updating state after a network response where the enclosing snapshot may be stale.
- Toggling flags: flipping boolean flags (`setOpen(o => !o)`) without relying on current render closure values.

### Glossary
- **Update Queue**: React's internal list of pending state changes and updater functions waiting to be processed for the next render.
- **Automatic Batching**: React's mechanism of grouping multiple state updates into a single render pass to prevent unnecessary UI reflows.
- **Updater Function**: A function passed to a state setter (`prev => next`) that calculates the next state from the pending state in the queue.
- **Queue Reduction**: The sequential evaluation of queued values and updater functions to determine the final state for the next render.
- **Stale Replacement**: The bug where multiple `setState(value)` calls overwrite each other because all evaluated against the same frozen snapshot.
- **Pending State**: The intermediate state value during queue processing, passed as the argument to the next updater function.

### Summary

**React 19 State Update Queuing Invariants**

In daily production, understanding React's update queue and automatic batching prevents frustrating lost-update bugs. Using updater functions whenever the next state depends on the previous state guarantees mathematical accuracy across multiple updates. Here is your streetwise review.

❒ Update Queue Invariants

1. React batches all state updates in an event handler into a single render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Multiple setter calls do not trigger multiple re-renders.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) The component re-renders once after the entire event handler finishes.

2. Direct value setters queue replacement instructions.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `setCount(count + 1)` evaluates against the current frozen snapshot.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Calling it three times queues three identical replacements, incrementing by one.

3. Updater functions queue sequential calculations.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `setCount(c => c + 1)` queues a function that receives the pending state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Calling it three times chains three increments, incrementing by three.

➔ NEVER call direct value setters multiple times in one handler expecting cumulative additions.

➔ ALWAYS use an updater function `setVal(prev => prev + 1)` when the new state depends on the previous state.

➔ IF you set state to an independent value like a string or boolean THEN **use a direct value setter to avoid unnecessary boilerplate**.

**DO THIS:** Use an updater function to chain multiple consecutive state updates.

```jsx right title="TipControls.jsx"
// Chains updates sequentially using updater functions
export default function TipControls({ onTriple }) {
  function handleClick() {
    onTriple(prev => prev + 3);
  }
  return <button onClick={handleClick}>Triple Tip</button>;
}
```

**DO NOT DO THIS:** Never repeat direct snapshot setters expecting cumulative increments.

```jsx wrong title="Stale Setter Anti-Pattern"
// FAILS: Repeated calls overwrite each other; increments by only 1!
export default function BrokenControls({ tip, onTip }) {
  function handleClick() {
    onTip(tip + 1);
    onTip(tip + 1);
    onTip(tip + 1);
  }
  return <button onClick={handleClick}>Broken Triple</button>;
}
```

| **Queue action** | Queues a calculation function<br>for sequential reduction | Queues a static replacement<br>value for the next render |
