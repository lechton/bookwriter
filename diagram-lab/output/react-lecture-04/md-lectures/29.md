### When State Logic Outgrows useState

In simple components, `useState` is concise and sufficient. As features grow, components often accumulate 5 to 8 separate state variables that frequently change together in response to a single event. Why does coordinating multiple `useState` setters across many event handlers lead to brittle code?

When multiple state variables change in tandem, every event handler must remember to invoke every corresponding setter. If one handler updates `status` but forgets to clear `error` or increment `revisions`, the component enters an **impossible or corrupted state**. Furthermore, business rules are duplicated across handlers, making the logic difficult to audit or refactor.

You should migrate from `useState` to `useReducer` when:
1. Multiple state values change together in response to user actions.
2. The next state depends on multiple previous state values.
3. You want to extract and unit-test your state logic outside of React's rendering tree.
4. Complex state transitions benefit from an explicit audit log of dispatched actions.

```jsx title="Scattered useState vs useReducer"
// FRAGILE: Handlers must manually orchestrate 3 separate setters:
function handlePublish() { setStatus('published'); setError(null); setRev(r => r + 1); }
// CONSOLIDATED: Event handler simply dispatches what happened:
function handlePublish() { dispatch({ type: 'published' }); }
// Pure reducer outside component owns ALL transition rules:
function editorReducer(state, action) {
  if (action.type === 'published') return { ...state, status: 'published', error: null, rev: state.rev + 1 };
  return state;
}
```

Is useReducer only for large, complex enterprise applications? No! For independent state variables (like a text input string, a boolean toggle, or a counter), `useState` is simpler, cleaner, and less verbose. Only reach for `useReducer` when state variables are interdependent or when state transitions become difficult to follow across multiple handlers. Key terms: **independent state**, **co-located simplicity**, **state interdependence**, **boilerplate overhead**.

### Reducer Architecture: Actions and Pure Functions

We know `useReducer` centralizes state updates. How should actions and reducer functions be structured to maintain a clean architecture?

The reducer function follows a strict signature: `(state, action) => nextState`. It must be a **pure function**: given the same state and action, it must return the exact same next state without mutating arguments, making network calls, or generating random numbers. Reducers must perform **immutable updates**, returning a new object reference rather than modifying the existing state object.

Action objects should describe **what happened in user terms**, not how the state should be updated. For example, dispatch `{ type: 'headline_submitted' }` rather than `{ type: 'set_headline_and_clear_status' }`. This keeps event handlers declarative and concentrates all transition logic within the reducer.

```jsx title="Pure Reducer Pattern"
export function dispatchReducer(state, action) {
  switch (action.type) {
    case 'saved_draft':
      return { ...state, status: 'draft', revisions: state.revisions + 1 };
    case 'published':
      return { ...state, status: 'published', revisions: state.revisions + 1 };
    default:
      return state;
  }
}
```

Why should a reducer be defined outside the component? Always define the reducer outside the component body (or in a separate file)! Because a reducer is a pure function that does not depend on component props or hooks, defining it outside proves that it has no hidden dependencies. This allows you to export the reducer and unit-test all state transitions in standard Node or Jest tests without mounting React components! Key terms: **external definition**, **zero-dependency purity**, **isolated unit testing**, **module export**.

### Step 1: First, we construct the parent container DispatchEditor.jsx

The parent container declares the reducer function and invokes `useReducer`. The parent must demonstrate the reducer declaration and dispatch wiring.

```jsx title="DispatchEditor.jsx"
import { useReducer } from 'react';
import EditorControls from './components/EditorControls.jsx';
import StatusBanner from './components/StatusBanner.jsx';
const reducer = (s, a) => ({ ...s, status: a.type, rev: s.rev + 1 });
export default function DispatchEditor() {
  const [state, dispatch] = useReducer(reducer, { status: 'editing', rev: 0 });
  return <div className="editor-box"><EditorControls dispatch={dispatch} /><StatusBanner state={state} /></div>;
}
```

Step 1 establishes reducer consolidation: Look at line 4: `reducer` gathers all transition rules into one pure function. Look at line 6: `const [state, dispatch] = useReducer(reducer, { status: 'editing', rev: 0 });`. We will build `EditorControls` next in step 2.

### Step 2: Next, we declare the controls child EditorControls.jsx

Step 1 passed `dispatch` to `EditorControls`. The child component must dispatch semantic user actions.

```jsx title="EditorControls.jsx"
export default function EditorControls({ dispatch }) {
  return (
    <div className="editor-controls">
      <button onClick={() => dispatch({ type: 'draft' })}>Draft</button>
      <button onClick={() => dispatch({ type: 'published' })}>Publish</button>
    </div>
  );
}
```

Step 2 fulfills the dispatch role: Look at lines 4 and 5: buttons call `dispatch({ type: 'draft' })` and `dispatch({ type: 'published' })`. The buttons express *what happened*, leaving all state calculations to the reducer.

### Step 3: Then, we declare the banner child StatusBanner.jsx

`StatusBanner` receives `state` from `DispatchEditor`. The terminal child must display the current workflow status and revision count.

```jsx title="StatusBanner.jsx"
export default function StatusBanner({ state }) {
  return (
    <aside className="status-banner">
      <p>Workflow Status: <strong>{state.status}</strong></p>
      <p>Total Revisions: {state.rev}</p>
    </aside>
  );
}
```

Step 3 completes the display component: Look at lines 4 and 5: `StatusBanner` reads `state.status` and `state.rev`. Because the reducer updates both values atomically, the banner never displays contradictory data.

What would happen if a handler mutated the `state` object directly instead of returning a new copy? If a handler mutates `state.status = 'published'` directly, React's shallow comparison (`Object.is`) sees the exact same object reference and skips re-rendering. The UI remains frozen on the old view until an unrelated state change occurs.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the reducer-governed component tree. Now we inspect `main.jsx`, which mounts `DispatchEditor` to the DOM. The entry point must initialize the React root and render the editor.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import DispatchEditor from './DispatchEditor.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<DispatchEditor />);
```

Step 4 seals the architecture: Look at line 6: `root.render(<DispatchEditor />)`. React mounts the application. State transitions execute predictably through the pure reducer, guaranteeing clean workflow progression.

How do you initialize expensive state in useReducer? `useReducer` supports an optional third argument: an initializer function! You write `useReducer(reducer, initialArg, init)`. React runs `init(initialArg)` only once on the initial mount, preventing expensive setup logic from running on subsequent re-renders. Key terms: **initializer function**, **lazy initialization**, **initialArg parameter**, **render performance**.

**To impress the interviewer:** When asked to compare `useState` and `useReducer`, explain that **`useState` is best for simple, independent state values**, while **`useReducer` is best when multiple state values change together, or when the next state depends on complex rules**. Highlight that `useReducer` decouples *what happened* (actions) from *how state updates* (the reducer), and that the pure reducer can be tested outside React with zero component mocking.

### Glossary

- **useReducer**: A React hook that manages state through a pure reducer function and action dispatching.
- **Reducer Function**: A pure function with signature `(state, action) => nextState` calculating the new state snapshot.
- **Action Object**: A plain JavaScript object describing an event or user intent, typically containing a `type` property.
- **Dispatch Function**: The stable function returned by `useReducer` that sends an action to the reducer.
- **Pure Function**: A deterministic function with no side effects that always returns the same output for given inputs.
- **Atomic State Update**: Updating multiple related state fields simultaneously in a single immutable transition.

### Summary

**React 19 useReducer Invariants**

In daily production, consolidating state transitions with `useReducer` prevents state desynchronization and makes complex business logic easy to test. Here is your streetwise review.

❒ useReducer Invariants

1. Reducers must be pure functions.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Reducers take `(state, action)` and return the next immutable state object.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Never mutate state directly; always return a new object reference.

2. Actions describe what happened, not how to update.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Use descriptive names like `{ type: 'saved_draft' }`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Let the reducer decide how to compute the resulting state changes.

3. Declare reducers outside the component body.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Reducers have no dependencies on component props or hooks.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) External reducers can be directly imported and unit-tested in isolation.

➔ NEVER mutate state properties directly inside a reducer function.

➔ ALWAYS dispatch semantic action objects describing user intent.

➔ IF multiple state variables update together THEN **consolidate them into useReducer**.

**DO THIS:** Consolidate multiple interdependent states in a pure reducer.

```jsx right title="DispatchEditor.jsx"
function reducer(state, action) {
  if (action.type === 'publish') {
    return { ...state, status: 'published', rev: state.rev + 1 };
  }
  return state;
}
export default function DispatchEditor() {
  const [state, dispatch] = useReducer(reducer, { status: 'idle', rev: 0 });
  return <button onClick={() => dispatch({ type: 'publish' })}>Publish</button>;
}
```

**DO NOT DO THIS:** Never scatter interdependent setters across event handlers.

```jsx wrong title="Scattered-Setters Anti-Pattern"
export default function BrokenEditor() {
  const [status, setStatus] = useState('idle');
  const [rev, setRev] = useState(0);
  function handlePublish() {
    setStatus('published');
    // BUG: Forgot to increment rev; state becomes inconsistent!
  }
  return <button onClick={handlePublish}>Publish</button>;
}
```
