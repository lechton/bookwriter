### The Child Placement Rule

In Lecture 24, we learned how `useActionState` manages a form's action return value and `isPending` flag. However, in modern component libraries, the submit button is often a separate reusable component (`<SubmitButton />`) rendered deep inside complex layouts, cards, or dialog footers. Why does calling `useFormStatus()` in the same component that renders `<form>` always return `pending: false`?

The `useFormStatus` hook (exported from `'react-dom'`) returns status information about the **parent** `<form>` element. Under the hood, React provides form status using an internal Context Provider that wraps the form's children. Because a context consumer must be rendered *inside* its provider, `useFormStatus` **MUST be called from a component that is a child of the `<form>`**. If you call `useFormStatus` in the component that renders `<form action={...}>`, there is no parent form above it in the React tree, and `pending` will be permanently `false`.

This architectural rule enforces a clean separation of concerns: the parent component defines the `<form action={...}>`, while nested child components (like buttons, progress bars, or field indicators) can read the form's status independently without any props passed down.

```jsx title="The Child Placement Rule"
function BrokenForm() {
  const { pending } = useFormStatus();
  return <form action={act}><button disabled={pending}>Send</button></form>;
}
function GoodForm() {
  return <form action={act}><SubmitButton /></form>;
}
```

What other properties does useFormStatus return besides pending? `useFormStatus` returns four properties: `{ pending, data, method, action }`. While `pending` is a boolean, `data` is the actual `FormData` instance currently being submitted! This means a child component can inspect `data.get('title')` while pending to render optimistic feedback: "Publishing 'City Budget'..." before the server even responds! Key terms: **formData inspection**, **optimistic child feedback**, **method property**, **action property**.

### Eliminating Prop Drilling in Design Systems

We know `useFormStatus` must live in a child component. How does this hook transform how teams design reusable buttons and form inputs?

In design systems, a `<PrimaryButton>` previously required an `isPending` or `loading` prop passed from above. Every modal or card that hosted a form had to accept `isPending` and thread it down. With `useFormStatus`, a `<SubmitButton>` becomes completely **form-aware and self-contained**: it reads `pending` from the enclosing form automatically, disabling itself and rendering a spinner with zero props required.

If you render multiple forms on a page, each `useFormStatus` call automatically binds to its closest enclosing `<form>` ancestor, completely isolating their pending states from one another.

```jsx title="Self-Contained Submit Button"
import { useFormStatus } from 'react-dom';
export default function SubmitButton() {
  const { pending, data } = useFormStatus();
  return (
    <button disabled={pending} type="submit">
      {pending ? `Saving ${data?.get('title')}...` : 'Save'}
    </button>
  );
}
```

Does useFormStatus track nested formAction buttons? `useFormStatus` tracks the parent `<form>`'s action submission, regardless of whether it was triggered by the form's default action or a button's `formAction`. When the action runs, `pending` flips to true for the entire form subtree! Key terms: **formAction tracking**, **subtree synchronization**, **action trigger source**, **unified pending**.

### Step 1: First, we construct the parent container PublishModal.jsx

The parent container owns the action handler and renders `<form action={publish}>`. It embeds `ModalBody` without passing any pending props. The parent must demonstrate that pending state is not manually drilled down.

```jsx title="PublishModal.jsx"
import { useState } from 'react';
import ModalBody from './components/ModalBody.jsx';
export default function PublishModal() {
  const [msg, setMsg] = useState(null);
  const publish = async data => setMsg(data.get('headline'));
  return (
    <form action={publish}><ModalBody msg={msg} /></form>
  );
}
```

Step 1 establishes the enclosing form: Look at line 7: `<form action={publish}><ModalBody msg={msg} /></form>`. Notice that `PublishModal` does NOT track `isPending` or pass any pending props into `ModalBody`. We will build `ModalBody` next in step 2.

### Step 2: Next, we declare the layout child ModalBody.jsx

Step 1 passed `msg` to `ModalBody`. The child component must lay out the headline input and embed `SubmitButton`.

```jsx title="ModalBody.jsx"
import SubmitButton from './SubmitButton.jsx';
export default function ModalBody({ msg }) {
  return (
    <div className="modal-body">
      <input name="headline" placeholder="Headline" /><SubmitButton />
      {msg && <p>Published: {msg}</p>}
    </div>
  );
}
```

Step 2 fulfills the layout role: Look at lines 4 through 7: `ModalBody` renders an input and nests `SubmitButton`. Notice that `ModalBody` acts as a pure layout shell with zero knowledge of whether the form is currently submitting.

### Step 3: Then, we declare the button child SubmitButton.jsx

`SubmitButton` is nested inside `ModalBody`, which is nested inside `PublishModal`'s `<form>`. The terminal child must read the form's pending state using `useFormStatus`.

```jsx title="SubmitButton.jsx"
import { useFormStatus } from 'react-dom';
export default function SubmitButton() {
  const { pending } = useFormStatus();
  return (
    <button disabled={pending} type="submit">
      {pending ? 'Publishing...' : 'Publish Story'}
    </button>
  );
}
```

Step 3 completes the self-contained control: Look at line 3: `const { pending } = useFormStatus();`. `SubmitButton` reaches directly up the component tree to the enclosing `<form>` rendered by `PublishModal`, disabling the button and changing the label to "Publishing..." while the action runs.

What would happen if `SubmitButton` was rendered outside the `<form>` element? If `SubmitButton` is rendered outside the enclosing `<form>`, React's internal form status context has no provider above it. `useFormStatus()` evaluates to `{ pending: false, data: null, method: null, action: null }`, and the button will never reflect the form's pending state.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the form status component tree. Now we inspect `main.jsx`, which mounts `PublishModal` to the DOM. The entry point must initialize the React root and render the top-level modal.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import PublishModal from './PublishModal.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<PublishModal />);
```

Step 4 seals the architecture: Look at line 6: `root.render(<PublishModal />)`. React mounts the application. When the user clicks "Publish Story", React's form action runtime triggers, `useFormStatus` flips `pending` to true inside `SubmitButton`, the action resolves, and the form resets seamlessly.

Why is useFormStatus exported from react-dom rather than react? Forms and `<form>` elements are specific to the web DOM (React DOM), whereas core React is platform-agnostic (used in React Native, React 3D, etc.). Because `<form>` and its action behaviors are HTML DOM primitives, `useFormStatus` lives in `'react-dom'`. In contrast, `useActionState` is a general-purpose action transition hook that does not depend on the DOM, so it lives in `'react'`. Key terms: **react-dom package**, **DOM-specific hook**, **platform agnosticism**, **package boundary**.

### Glossary

- **useFormStatus**: A React DOM hook that returns the pending status and data of the nearest enclosing parent `<form>`.
- **Child Placement Rule**: The requirement that `useFormStatus` must be invoked inside a component rendered as a child of `<form>`, not in the form's parent.
- **Enclosing Form**: The closest `<form>` ancestor element in the React component tree providing status context.
- **Prop Drilling Elimination**: The architectural benefit of allowing deep components to read parent form status without intermediate prop threading.
- **Form-Aware Component**: A component (like a submit button) that self-manages its disabled and loading states by reading form context.
- **Form Data Inspection**: Using the `data` property returned by `useFormStatus` to access field values currently in flight.

### Summary

**React 19 useFormStatus Invariants**

In daily production, `useFormStatus` eliminates tedious prop drilling for nested form controls. Understanding the Child Placement Rule ensures that reusable buttons and banners reliably reflect form execution state. Here is your streetwise review.

❒ useFormStatus Invariants

1. `useFormStatus` must be called from a child inside `<form>`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Calling it in the component that renders `<form>` always returns `pending: false`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) It reads status via React context from the nearest enclosing `<form>` ancestor.

2. It returns `{ pending, data, method, action }`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `pending` is a boolean indicating whether the form is submitting.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) `data` is the `FormData` instance being submitted, enabling live previews.

3. Import `useFormStatus` from `'react-dom'`, not `'react'`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) It is a DOM-specific hook coupled to the HTML `<form>` element.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Multiple forms on a page isolate their status to their own subtrees.

➔ NEVER call `useFormStatus` inside the same component that renders `<form>`.

➔ ALWAYS extract submit buttons into child components when reading form status.

➔ IF you need to preview submitted fields during loading THEN **read them from `const { data } = useFormStatus()`**.

**DO THIS:** Call useFormStatus in a child component nested inside the form.

```jsx right title="SubmitButton.jsx"
import { useFormStatus } from 'react-dom';
export default function SubmitButton() {
  const { pending } = useFormStatus();
  return (
    <button disabled={pending} type="submit">
      {pending ? 'Publishing...' : 'Publish'}
    </button>
  );
}
```

**DO NOT DO THIS:** Never call useFormStatus in the parent component rendering the form.

```jsx wrong title="Same-Component Anti-Pattern"
import { useFormStatus } from 'react-dom';
export default function BrokenForm({ action }) {
  const { pending } = useFormStatus();
  return (
    <form action={action}>
      <button disabled={pending}>Publish</button>
    </form>
  );
}
```
