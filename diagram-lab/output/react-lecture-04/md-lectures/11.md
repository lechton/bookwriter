### Transforming Arrays into Elements with map()

In Lectures 6 and 8, we learned that JSX evaluates JavaScript expressions inside curly braces `{}` and that components receive data through props. In plain JavaScript, when you have an array of data objects and want to transform each into a new format, you call the `array.map()` method. How do you take an array of story objects and convert them into a collection of rendered JSX elements?

When you call `stories.map(story => <li key={story.id}>{story.title}</li>)`, JavaScript returns a new array of JSX element objects. Because React natively knows how to render arrays of elements, placing that expression inside JSX curly braces renders the entire collection in order. You can map arrays to native HTML elements or to custom components: `{stories.map(story => <StoryRow key={story.id} story={story} />)}`.

Whenever you render a list of elements from an array, React demands that every item have a special `key` prop: `<li key={story.id}>`. React uses the `key` internally to track which item is which. The `key` prop is not passed down to the child component: if the child needs the ID, you must pass it as a separate prop like `id={story.id}`.

```jsx title="Rendering Lists with Map and Keys"
const stories = [
  { id: 's-01', title: 'Dockworkers Deal' },
  { id: 's-02', title: 'Transit Approved' },
];
export default function StoryList() {
  return (
    <ul>{stories.map(s => <li key={s.id}>{s.title}</li>)}</ul>
  );
}
```

By mapping arrays into elements with keys, your markup stays declarative and directly synchronized with your data collections.

> [!WILD]
> **Why does React need keys if array items already have indexes?** Imagine an editor has a list of three stories: index 0 is "Transit", index 1 is "Economy", and index 2 is "Sports". The reader checks a checkbox on story 0 ("Transit"). Now a breaking news story arrives and gets prepended to the top of the array. The breaking story becomes index 0. "Transit" shifts to index 1. If React matched elements by their index, it would compare the old index 0 with the new index 0 and assume the breaking story is the same component as the old "Transit" story. The checkbox that the user checked on "Transit" would now be attached to the breaking story. By assigning a stable ID like `key="transit-101"`, React knows that "Transit" simply moved down, preserving its state.

### The Dangers of Index Keys and Rules of Stable Identity

When developers see the console warning about missing keys, many write `stories.map((story, index) => <li key={index}>)`. While this silences the warning, using array indexes as keys is an anti-pattern that creates subtle, catastrophic bugs when lists change.

An array index does not represent the item's identity: it represents the item's position in memory. If you sort the list, filter items, insert at the beginning, or delete a row, every item's index changes. React reuses existing DOM nodes and component state based on the matching key. When keys change because of reordering, inputs lose focus, animations break, and uncontrolled form state attaches to the wrong row.

Stable keys must satisfy three strict rules: (1) **Keys must be unique among siblings**: different lists can use the same keys, but within a single array, each key must be unique. (2) **Keys must never change**: do not generate keys on the fly using `Math.random()` or `crypto.randomUUID()` during render, which forces React to destroy and recreate every DOM node on every render. (3) **Keys should come from data**: use database IDs, permanent slugs, or unique business keys.

```jsx title="Key Identity Contrast"
// DANGEROUS: Math.random destroys and recreates DOM!
{stories.map(s => <StoryRow key={Math.random()} story={s} />)}
// DANGEROUS: Index keys cause state mismatch on reorder:
{stories.map((s, index) => <StoryRow key={index} story={s} />)}
// SAFE: Stable database IDs preserve component identity:
{stories.map(s => <StoryRow key={s.id} story={s} />)}
```

Treating keys as permanent identity tags ensures React's reconciliation engine can intelligently reorder, insert, and delete DOM elements without side effects.

> [!WILD]
> **Can you ever safely use an index as a key?** Imagine a static pagination bar with five fixed pages (1, 2, 3, 4, 5). The list is never reordered, never filtered, never inserted into, and the items have no internal state or inputs. In this rare scenario, using `key={index}` causes no visual harm. However, as a professional standard, you should avoid index keys entirely. Requirements evolve: tomorrow an editor adds drag-and-drop sorting or a delete button to that list, and the index key immediately turns into a bug. Always use stable, unique data IDs.

### Step 1: First, we construct the parent container NewsFeed.jsx

The parent container owns the story data array. It maps each story to `<StoryRow key={s.id} story={s} />`.

```jsx title="NewsFeed.jsx"
import StoryRow from './components/StoryRow.jsx';
export default function NewsFeed() {
  const stories = [
    { id: 'story-01', title: 'Dockworkers Deal', cat: 'Economy' },
    { id: 'story-02', title: 'Transit Approved', cat: 'Metro' },
  ];
  return (
    <ul>{stories.map(s => <StoryRow key={s.id} story={s} />)}</ul>
  );
}
```

Look at line 8: `{stories.map(s => <StoryRow key={s.id} story={s} />)}`. We have not written `StoryRow` yet. But right here, we establish its contract: it receives a `story` prop containing title and category. Notice that the `key` prop sits on `<StoryRow>`, which is the outermost element returned by the map callback. We will build `StoryRow` next in step 2.

### Step 2: Next, we declare the row child StoryRow.jsx

Step 1 mapped stories to `StoryRow` components. The row component destructures `story`, renders the title, and embeds `StoryBadge`.

```jsx title="StoryRow.jsx"
import StoryBadge from './StoryBadge.jsx';
export default function StoryRow({ story }) {
  return (
    <li className="story-row">
      <StoryBadge category={story.cat} />
      <span>{story.title}</span>
    </li>
  );
}
```

Look at line 2: `export default function StoryRow({ story })`. Notice that `StoryRow` does NOT receive `key` in its props object: React strips `key` from props for internal reconciliation. `StoryRow` reads only `story.title` and `story.cat`.

What would happen if `NewsFeed` placed the `key` inside `StoryRow` on the `<li>` tag instead of on `<StoryRow>`? React would throw a console warning: "Each child in a list should have a unique key prop." The key must ALWAYS be declared on the JSX element directly inside the `map()` call. If you wrap the item in a Fragment, the Fragment must take the key: `<Fragment key={story.id}>`.

### Step 3: Then, we declare the badge child StoryBadge.jsx

Step 2 embedded `<StoryBadge category={story.cat} />`. The terminal badge component renders the category text inside a styled pill.

```jsx title="StoryBadge.jsx"
export default function StoryBadge({ category }) {
  return (
    <span className={`badge badge-${category.toLowerCase()}`}>
      {category}
    </span>
  );
}
```

Look at lines 1 through 7: `StoryBadge` renders the category badge cleanly. It receives `category` as a prop and formats the class name and text.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the list hierarchy. Now we inspect `main.jsx`, which mounts `NewsFeed` to the DOM.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import NewsFeed from './NewsFeed.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container); // Acquires container in **MEMORY**
root.render(<NewsFeed />); // Mounts root component into **DOM**
```

Look at line 6: `root.render(<NewsFeed />)`. React mounts `NewsFeed`, evaluates the `map()` expression, uses the `key` to track each `StoryRow`, renders both rows with their `StoryBadge` children, and commits the resulting DOM into `<div id="root">`. React's reconciliation engine now has permanent identity tags to track list updates efficiently.

Now let us examine a subtle detail regarding key accessibility.

Why can't you access `props.key` in a child component? Imagine an engineer wants to display the item's key on the screen. They write `props.key` inside `StoryRow`. React prints a warning: `key is not a prop. Trying to access it will result in undefined being returned`. Why? React reserves `key` (and `ref`) for its own internal reconciliation engine. React extracts `key` before passing the remaining props to your component. If your component needs the ID value for display or logic, pass it explicitly under another name: `<StoryRow key={story.id} id={story.id} />`.

> [!TIP]
> **To impress the interviewer:** When asked about keys in React lists, explain that keys do not just silence console warnings: they define element identity for React's reconciliation algorithm. When a list changes, React uses keys to match previous Virtual DOM nodes with new ones (`reconciliation key matching`). Emphasize that using array indices as keys breaks when items are reordered, inserted, or deleted, because local state clings to the DOM node position rather than the data item.

### Glossary
- **List Rendering**: The technique of mapping an array of data items into an array of JSX elements using `array.map()`.
- **Key Prop**: A special string or number attribute assigned to elements in an array to give them a stable identity across renders.
- **Reconciliation**: The process by which React compares the new Virtual DOM tree with the previous one to determine the minimal set of DOM updates.
- **Index as Key**: The anti-pattern of using the second argument of `map((item, index) => ...)` as the key prop, causing state corruption during reordering.
- **Stable Identity**: A unique identifier (like a database ID) that remains permanently associated with an item throughout its entire lifecycle.
- **Prop Exclusion**: The architectural rule where React strips reserved attributes (`key` and `ref`) so they are not accessible on the `props` object.
