### Custom Hooks: Sharing Logic, Not State

Components frequently require identical stateful behaviors: listening to browser window events, managing input form state, or polling a server. In plain JavaScript, duplicate logic is extracted into helper functions. Why can't we extract stateful logic into a standard JavaScript utility function?

React hooks (`useState`, `useEffect`, `use`) can only be called from React component functions or from other hooks. To extract stateful logic, you write a **custom hook**: a JavaScript function whose name starts with **`use`** (e.g. `useOnlineStatus`). Because it follows the `use` prefix convention, React and ESLint enforce the Rules of Hooks within it.

The most vital mental model invariant is: **Custom hooks share stateful logic, NOT state itself!** When two components call `useOnlineStatus()`, each component gets its own completely separate, independent `isOnline` state variable. Custom hooks do not create global state; they simply reuse the blueprint of state and effects across different components.

```jsx title="Custom Hook Encapsulation"
export function useOnlineStatus() {
  const [on, setOn] = useState(true);
  useEffect(() => {
    const f = () => setOn(navigator.onLine);
    window.addEventListener('online', f);
    return () => window.removeEventListener('online', f);
  }, []);
  return on;
}
```

Why must custom hook names start with "use"? The "use" prefix is a mandatory React convention. React's linter uses this prefix to identify functions that may call hooks, ensuring that early returns, conditional calls, and loop violations are caught at build time. If you name a function `getOnlineStatus` and call `useState` inside it, React linters will flag a rule violation! Key terms: **use prefix mandate**, **linter verification**, **hook rule enforcement**, **build-time safety**.

### Composing Hooks and Passing Reactive Values

We know custom hooks package state and effects. How do custom hooks interact when one hook's output serves as another hook's input?

Custom hooks can take arguments and return values just like normal functions. If you pass an argument to a custom hook, and that argument is a state variable in the calling component, the custom hook re-runs whenever the argument changes!

This enables powerful **hook composition**: you can build high-level domain hooks (like `useArticleSubscription(articleId)`) by composing lower-level primitives (`useOnlineStatus()`, `useEffect`, `useState`). By hiding implementation details behind declarative hook signatures, components stay concise and focused on rendering markup.

```jsx title="Composing Custom Hooks"
export function useWireFeed(channel) {
  const isOnline = useOnlineStatus();
  const [data, setData] = useState(null);
  useEffect(() => {
    if (!isOnline) return;
    const socket = connect(channel, setData);
    return () => socket.disconnect();
  }, [channel, isOnline]);
  return { data, isOnline };
}
```

When should you NOT create a custom hook? Do not create a custom hook for trivial, one-off logic that only exists in a single component and is unlikely to be reused. Wrapping everything in custom hooks adds indirection without benefit. Extract a custom hook when the logic is reused across multiple components, or when complex effect orchestration clutters a component's core rendering role. Key terms: **indirection cost**, **pragmatic extraction**, **code clutter reduction**, **reusability threshold**.

### Step 1: First, we construct the custom hook useOnlineStatus.js

The custom hook encapsulates `useState` and `useEffect` with window event listeners, returning the boolean connection state.

```jsx title="useOnlineStatus.js"
import { useState, useEffect } from 'react';
export function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(true);
  useEffect(() => {
    const set = () => setIsOnline(navigator.onLine);
    window.addEventListener('online', set);
    return () => window.removeEventListener('online', set);
  }, []);
  return isOnline;
}
```

Step 1 establishes custom hook extraction: Look at line 2: `export function useOnlineStatus()`. The hook packages internal state and symmetrical window listeners. We will build `ReporterStatusBar` next in step 2.

### Step 2: Next, we declare the status child ReporterStatusBar.jsx

`ReporterStatusBar` needs to display network status. The child component invokes `useOnlineStatus`.

```jsx title="ReporterStatusBar.jsx"
import { useOnlineStatus } from '../useOnlineStatus.js';
export default function ReporterStatusBar() {
  const isOnline = useOnlineStatus();
  return (
    <header className="status-bar">
      <span>Field Connection: <strong>{isOnline ? 'Active' : 'Offline'}</strong></span>
    </header>
  );
}
```

Step 2 demonstrates clean consumption: Look at line 3: `const isOnline = useOnlineStatus()`. `ReporterStatusBar` gets fresh connectivity state without managing window event listeners directly.

### Step 3: Then, we declare the banner child OfflineWarningBanner.jsx

`OfflineWarningBanner` also needs connectivity status. The child shows that calling `useOnlineStatus` creates independent state.

```jsx title="OfflineWarningBanner.jsx"
import { useOnlineStatus } from '../useOnlineStatus.js';
export default function OfflineWarningBanner() {
  const isOnline = useOnlineStatus();
  if (isOnline) return <p className="banner ok">Dispatches syncing live.</p>;
  return <p className="banner warn">Disconnected. Changes queued locally.</p>;
}
```

Step 3 demonstrates independent state instances: Look at line 3: `OfflineWarningBanner` calls `useOnlineStatus()`. Even though both components call the same hook, each component owns its own private `isOnline` state variable in React's Fiber tree.

What would happen if a custom hook returned a mutable object without useState? If a custom hook mutates an external variable without `useState`, React has no trigger to schedule a re-render when the variable changes. The calling components will never update when network status shifts.

### Step 4: Finally, we seal the application entry point main.jsx

In Steps 1 through 3 we created the custom hook architecture. Now we inspect `main.jsx`, which mounts `NetworkMonitor` to the DOM. The entry point must initialize the React root and render the monitor.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import NetworkMonitor from './NetworkMonitor.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container);
root.render(<NetworkMonitor />);
```

Step 4 seals the architecture: Look at line 6: `root.render(<NetworkMonitor />)`. React mounts the application. Custom hooks cleanly decouple stateful mechanics from rendering, enabling reusable, bulletproof behaviors across the codebase.

Can custom hooks return functions and setters? Custom hooks can return anything! They can return a single value (`isOnline`), a tuple array (`[value, setValue]`), or an object with methods and flags (`{ data, isLoading, refetch }`). Match the return type to the consumer's needs: tuples are great when callers want to name their own variables; objects are great when returning multiple named properties. Key terms: **flexible return signature**, **tuple vs object returns**, **action method exposure**, **consumer flexibility**.

### Glossary

- **Custom Hook**: A JavaScript function whose name begins with `use` that calls other React hooks to extract and reuse stateful logic.
- **use Prefix**: The mandatory naming convention identifying custom hooks to React's compiler and ESLint plugin.
- **Stateful Logic**: The sequence of state declarations, effect synchronizations, and event callbacks that govern a dynamic behavior.
- **State Isolation**: The guarantee that each component calling a custom hook receives its own private, unshared state.
- **Hook Composition**: Calling one or more hooks inside another custom hook to build higher-level abstractions.
- **Declarative API**: Exposing clean values and actions from a hook while hiding complex browser event subscriptions.
