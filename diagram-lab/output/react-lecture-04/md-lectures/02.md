### The Modern Starting Point

When you start a modern React application today, you cannot simply link a JavaScript file inside an HTML document. React components rely on JSX syntax and modular imports across multiple files. Browsers cannot execute raw JSX directly. Your development environment requires specialized tooling to compile your code, resolve dependencies, and prepare your project for deployment.

Choosing how to start a project requires making an early architectural choice between a **build tool** and a **framework**. A **build tool** (a command-line development program that compiles, bundles, and serves application code for browser execution) packages your source files into optimized JavaScript. The modern standard for standalone client projects is Vite. In contrast, a **framework** (an integrated application architecture that manages routing, data loading, and server execution) runs your code across both the server and the browser. Prominent examples include Next.js and React Router v7.

This choice directly determines your application's rendering strategy. A standalone build tool uses **client-side rendering** (**CSR**), delivering an empty HTML shell and running all React logic inside the user's browser. A full-stack framework unlocks **server-side rendering** (**SSR**), where React runs on a server to generate full HTML on each request, as well as **static-site generation** (**SSG**), where HTML is pre-rendered at build time.

Historically, the default starting tool was Create React App. However, Create React App is officially deprecated and unmaintained. It relied on monolithic Webpack builds that grew painfully slow as applications scaled, and it offered no architecture for modern server-rendered React features. Today, every new project starts either with a dedicated build tool like Vite or an integrated framework.

```bash title="Terminal (Historical CRA)"
npx create-react-app national-weather // 1. historical tool scaffolds monolithic **WEBPACK** setup
cd national-weather                   // 2. navigates into the project **DIRECTORY**
npm start                             // 3. starts slow Webpack **DEVELOPMENT** server
```

> [!WILD]
> **Why did Create React App get retired?** In older React projects, saving a single file forced the computer to rebuild your entire application from scratch. Developers regularly waited twenty seconds for the local development server to recompile. As projects grew larger, the browser was forced to download massive files before displaying a single pixel on screen. This is the problem with older bundlers: they force the user to wait for giant bundles, time and time again. A modern **build tool** like Vite eliminates this delay by serving individual files over native browser modules. A modern **framework** eliminates the blank screen by pre-rendering HTML on the server.

### Generating a Project with Vite

When your application does not require a backend server or complex search engine optimization, the fastest path to production is a modern **build tool**. The standard choice recommended across the React ecosystem is Vite. Vite provides instant local startup and near-instant updates during development.

To create a new project, developers use a command-line **scaffolding** tool. In documentation, this command is described using a generic formula: `npm create vite@latest <app_name> -- --template react`. In this generic formula, the token `<app_name>` represents a placeholder for your chosen application name. In practice, this value determines the physical folder created on your hard drive, as well as the `"name"` property recorded inside your `package.json` manifest. You must follow standard package naming rules: use lowercase letters, numbers, and hyphens without spaces or uppercase characters, such as `national-weather`. Notice the angle brackets `<...>`: in command-line documentation, angle brackets denote a required parameter that you replace with your own value. You must never type the literal angle brackets into your terminal, because shells like bash and zsh treat `<` and `>` as file redirection operators, which trigger immediate syntax errors.

Notice also the tool invocation flags. The command `npm create vite@latest` is shorthand for `npm exec create-vite@latest`. It downloads the latest `create-vite` generator package into npm's execution cache, runs it once to scaffold the project, and discards it without leaving an unmaintained global program on your computer. The double-dash delimiter `--` is mandatory: npm consumes all arguments before the double-dash, while everything placed after `--` is forwarded directly to the underlying `create-vite` program. Without that delimiter, npm attempts to interpret `--template react` as an internal npm flag and aborts. The `--template react` argument instructs the generator to scaffold a React project pre-configured for standard JavaScript and JSX.

Here is the concrete runnable command sequence to generate and start your project:

```bash title="Terminal"
npm create vite@latest national-weather -- --template react // 1. scaffolds the **PROJECT** directory
cd national-weather                                         // 2. navigates into the project **DIRECTORY**
npm install                                                 // 3. installs the React **DEPENDENCIES**
npm run dev                                                 // 4. starts the local **DEVELOPMENT** server
```

After running the scaffolding command, Vite generates a clean, purposeful project structure on your hard drive. It is essential to understand the exact role of each generated file and folder:
`package.json` is the project manifest, and it holds two separate lists. (a) The runtime dependencies (`dependencies`) are the packages the application needs while it runs: `react` and `react-dom`. The browser loads these when a reader opens the page, so these are the only packages your readers ever download. (b) The development dependencies (`devDependencies`) are the packages your computer needs while you build and serve the project: `vite` and `@vitejs/plugin-react`. They run on your machine, and they never ship to the browser. The split is the point: the build tools stay on your machine, so what the browser loads stays small. The manifest also defines runnable scripts: `npm run dev` starts the development server, and `npm run build` produces the production files.
The file `index.html` sits at the project root, not buried in a public folder like older tools. It holds the empty `<div id="root"></div>` plus the `<script type="module" src="/src/main.jsx">` tag that starts the module chain.
The file `vite.config.js` registers the React plugin, and that plugin does three separate jobs. Job one: it compiles JSX into standard JavaScript function calls. Job two: **Fast Refresh** keeps a live connection to the browser and swaps a saved component without a full page reload and without wiping form input. Job three: at `npm run build`, **Rollup** bundles, shrinks, and optimizes the whole project into production files.
Inside the `src/` folder, the file `main.jsx` finds the root div with `document.getElementById('root')`, hands it to `createRoot`, and mounts `App.jsx`, which renders the visible interface.
The `node_modules/` folder is where `npm install` downloads the libraries. Next to it, `package-lock.json` records the exact resolved versions so every machine installs the identical set.

Navigating into the folder with `cd national-weather` establishes the execution context for all subsequent commands. Running `npm install` reads `package.json`, downloads `react` and `react-dom` into `node_modules/`, and writes the exact resolved dependency versions into `package-lock.json`. Running `npm run dev` starts the local Vite development server at `localhost:5173`, establishing a WebSocket connection that provides **Hot Module Replacement** (**HMR**), swapping updated component code in browser memory in milliseconds without losing active form inputs or scroll position.

To examine what Vite generates out of the box, we inspect the default project structure. Inside the `src/` directory, Vite creates `App.jsx`, which serves as the canonical starter component:

```components title="national-weather - Rendered UI Canvas"
App.jsx | none | counter | [button: count is 0]
```

The starter template generated by Vite centers on `App.jsx` as the root component. It encapsulates both the visual layout and the local counter state in a single file before any additional feature components are introduced.

Here is the exact code generated inside `App.jsx`:

```jsx title="App.jsx"
import { useState } from 'react';

export default function App() {
  const [count, setCount] = useState(0);
  return (
    <div className="card">
      <div className="starter-heading">Vite + React</div> // Brand headline declared in **STARTER**
      <button onClick={() => setCount((c) => c + 1)}>
        count is {count} // Button increments local component **STATE**
      </button>
      <p className="starter-caption">Click button to increment count</p> // Helper text guides **USER**
    </div>
  );
}
```

The line `const [count, setCount] = useState(0)` declares a piece of reactive memory called state. In plain JavaScript, ordinary local variables reset to zero every time a function executes, but React preserves this `count` variable across renders in internal memory.

When the user clicks the button, the inline arrow function invokes `setCount((c) => c + 1)`, dispatching an update request to React. React calls `App()` again with the updated count value, compares the new UI description against the previous one in memory, and surgically updates only the text node inside the button in the physical DOM.


> [!WILD]
> **What makes a modern build tool so fast?** In older bundlers, saving a single file forced the tool to repackage every file in the project into one gigantic bundle before the browser could see the change. A modern **build tool** like Vite works completely differently. When you edit a component, the development server transforms only that single file and sends it directly to the browser. Your browser requests only what changed, time and time again. Because the server never re-bundles the entire codebase, updates happen in milliseconds through **Hot Module Replacement**. In this mechanism, the development server keeps a live connection to your browser. When you save a file, the server sends the updated module directly over this connection. The browser swaps the new code into memory instantly and re-renders the component, so you see your changes immediately without losing your current form inputs or scroll position.

### Client-Side Rendering Mechanics

Understanding Vite requires understanding the physical network reality of **client-side rendering** (**CSR**). When a visitor opens your website in their browser, the web server does not send a completed HTML document. Instead, the server delivers an almost empty HTML file:

```html title="index.html"
<!doctype html>
<html lang="en">
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
```

Notice what is missing from this HTML: there are no headlines, no paragraphs, and no weather forecasts. The body contains only an empty root container `<div id="root"></div>` and a script tag. In the classic industry lexicon, this architecture is known as a **Single-Page Application** (**SPA**). In the modern React specification, this structure represents a **client-rendered UI descriptor tree**.

Once the browser downloads this HTML document, it encounters the script tag. The browser then makes a second network request to fetch the compiled JavaScript bundle. Only after that JavaScript bundle arrives does the browser execute React in local CPU memory. React evaluates your components, builds the in-memory tree, and inserts the resulting DOM nodes into the empty root container.

This sequence reveals the core architectural trade-off of client-side rendering:
- **Instant Client Transitions**: Once the application is loaded into browser memory, clicking between views or updating components is instantaneous. The browser never makes another full page request.
- **Cheap Static Hosting**: Because the server only delivers static HTML, JavaScript, and CSS files, you can host the application on any global Content Delivery Network without managing backend servers.
- **The Initial Blank Screen**: The browser cannot display anything until the full JavaScript bundle downloads and executes. On slow cellular connections, visitors stare at a blank white screen during initial loading.
- **Search Engine Limitations**: Search engine crawlers and social media preview bots may read the initial empty HTML before JavaScript executes, making search indexation unpredictable.

> [!WILD]
> **When does client-side rendering show a white screen?** Imagine a reader on a mobile phone opens The National Times. The screen stays completely blank for several seconds before anything appears. This delay happens because the server sends an empty HTML document with nothing more than an empty root container. The browser cannot display a single headline or button until it finishes downloading and executing the entire JavaScript bundle. On a slow mobile network, the reader stares at this blank screen while waiting for the code to arrive. This initial delay is the fundamental cost of **client-side rendering**: the user must download the full application engine before seeing any content.

### When to Choose a Full-Stack Framework

A **framework** expands beyond file compilation to provide a complete software architecture. While a build tool leaves page routing, data fetching patterns, and server deployment entirely to the developer, a framework integrates these responsibilities into a cohesive system.

To generate a project using a full-stack framework, you use the framework's official scaffolding CLI:

```bash title="Terminal"
npx create-next-app@latest national-times-web // Next.js full-stack framework
npx create-react-router@latest national-portal // React Router full-stack framework
```

Full-stack frameworks solve the initial white screen problem through **server-side rendering** (**SSR**). When a reader requests a web page, the server executes the React component functions immediately on its own CPU. The server outputs fully constructed HTML containing real text and markup. The server streams that HTML to the browser across the network.

The browser displays this HTML immediately. The reader sees headlines, articles, and weather forecasts without waiting for JavaScript. While the reader reads the content, the browser downloads the JavaScript bundle in the background. Once the JavaScript arrives, it attaches event listeners to the existing HTML in a process called **hydration** (the process where client-side React attaches event handlers to pre-rendered server HTML).

Frameworks also provide **static-site generation** (**SSG**). For pages that do not change on every incoming request, the framework runs your React components once during your deployment build. The framework exports pre-rendered HTML files that can be stored on edge servers worldwide.

Here is the senior engineering decision matrix for choosing your starting foundation:

1. **Choose a Build Tool (Vite) when:**
- You are building an internal company dashboard, admin portal, or authenticated account tool behind a login.
- Search engine optimization is unnecessary because the application is private.
- You want zero backend infrastructure, hosting purely on static file storage.
- You are learning core React fundamentals, testing an isolated component, or building a lightweight client tool.

2. **Choose a Full-Stack Framework (Next.js or React Router) when:**
- You are building a public-facing website, e-commerce catalog, or news publication where fast first-contentful paint and search engine visibility are critical.
- The application contains dozens of distinct pages requiring automatic code splitting and nested routing.
- You want to query databases directly from server components without writing separate REST API endpoints.

> [!WILD]
> **Does a full-stack framework require a backend server?** Many developers avoid frameworks because they fear the operational burden of managing backend servers. But modern frameworks support static exports. They can generate pre-rendered HTML files during the build and upload them straight to a static file host. You do not need a running server. This means you can use a **framework** purely for its routing and pre-rendering capabilities without maintaining any server infrastructure.

> [!TIP]
> **To impress the interviewer:** When asked whether to use Next.js or Vite, never offer an opinionated preference. Frame your answer around architectural constraints. Explain that Vite provides simplicity, complete architectural control, and zero server maintenance for client-focused applications. Explain that a framework provides built-in routing, server-rendered HTML for search engines, and integrated data loading at the cost of framework conventions and hosting requirements.

### Glossary

- **Build Tool**: A command-line program that compiles source files, bundles dependencies, and serves local development assets for browser execution.
- **Full-Stack Framework**: An integrated application architecture that manages routing, server-side data loading, and execution across both server and browser environments.
- **Client-Side Rendering (CSR)**: A rendering architecture where the server delivers a minimal HTML shell and the browser executes JavaScript to construct the user interface.
- **Server-Side Rendering (SSR)**: A rendering architecture where the web server runs React components on each HTTP request to generate and send fully constructed HTML to the browser.
- **Hydration**: The client-side process where React attaches event listeners to pre-rendered server HTML to make the static markup interactive.
- **Hot Module Replacement (HMR)**: A development mechanism that replaces updated component modules in browser memory over a live connection without reloading the full page.

### Summary

**Build Tools versus Full-Stack Frameworks**

In daily production, choosing between a **build tool** and a **full-stack framework** establishes the architectural foundation of your application. While a build tool focuses strictly on compiling client-side JavaScript, a framework provides an integrated platform managing the entire request lifecycle. Here is your streetwise review.

❒ Client Bundling versus Server-Integrated Platforms

1. Choose a **build tool** like Vite when building client-focused applications that do not require server execution.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Vite compiles JSX and bundles assets with near-instant local server startup.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Delivers an empty HTML shell that executes all React logic in browser memory via client-side rendering.

2. Choose a **full-stack framework** like Next.js or React Router when building public web applications requiring search visibility and fast initial loads.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Pre-renders HTML on the server or during build time to eliminate initial blank screens.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Provides built-in file-based routing, server data loaders, and automatic code splitting.

➔ NEVER deploy a public, content-heavy application using pure client-side rendering if search engine optimization matters.

➔ ALWAYS use a modern build tool like Vite for authenticated dashboards, prototypes, and isolated client components.

➔ IF your application requires fast initial paint and multi-route navigation THEN **choose an integrated full-stack framework**.

**DO THIS:** Pre-render public content on the server or at build time so search crawlers and readers receive full HTML immediately.
