### Component Architecture and the Effect Synchronization Cycle

In earlier lessons, we learned that React components maintain local state using `useState` and synchronize with external systems using `useEffect` (see Lecture 1 and Lecture 28). In an editorial desk, components often need to maintain an active connection to an external service, such as a websocket chat room. Developers often assume that effects follow the lifecycle of the host component, mounting once when added to the DOM and unmounting once when removed.

Every React component undergoes a standard three-phase lifecycle: it mounts when inserted into the DOM, updates when receiving new props or state, and unmounts when removed from the screen. An effect, however, lives by a different set of rules. An effect does not mount or update; it starts synchronizing and stops synchronizing. When a prop such as `roomId` changes from `"general"` to `"politics"`, the component updates, but the effect must stop synchronizing with the old room before starting to synchronize with the new room.

What is a **reactive effect**? In standard web development, when you open a connection to an external server with `connection.connect()`, the browser maintains that socket indefinitely. The browser does not know when your application has moved on to a different topic, and it never automatically closes the connection for you. That manual, open-ended connection is the default behavior of the plain web platform. A **reactive effect** changes this relationship completely. In React, you declare an effect by passing a function to `useEffect`, specifying the reactive values it reads in a dependency array. Inside that function, you write the setup code to start synchronizing, and return a cleanup function to stop synchronizing. The law of reactive effects is absolute: React will never run a new setup for changed dependencies without first running the cleanup from the previous render; every single setup is strictly paired with a prior cleanup.

Here is the naive connection pattern that treats effects as component mount events, omitting cleanup and causing connection leaks:

```jsx title="Zombie Connection Pattern"
function BadChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(roomId); // **SETUP:**<br>Connects to server on mount
    connection.connect(); // **LEAK:**<br>Never disconnects when roomId changes or component unmounts
  }, [roomId]);
  return <h2>Active Room: {roomId}</h2>;
}
```

In the naive snippet above, the component opens a socket connection whenever `roomId` changes. But notice what is missing: there is no cleanup return. When the reporter switches from `"general"` to `"politics"`, React re-runs the effect function. It opens a new connection to `"politics"`. But the socket to `"general"` was never closed. Both sockets remain alive in browser memory. Every message broadcast to either channel will now trigger duplicate event handlers on the same screen.

> [!WILD]
> **Why does an effect clean up before re-running?** Imagine checking into a hotel room. You enter room one hundred and unpack your clothes into the wardrobe. Later, the front desk calls and upgrades you to room two hundred. Do you leave your clothes scattered across room one hundred and start unpacking fresh clothes into room two hundred? Of course not. If you did, you would have your belongings split across two rooms at once. First, you pack your bags and check out of room one hundred. Only then do you enter room two hundred and unpack. In React, a **reactive effect** works the exact same way. When `roomId` changes, React checks out of the old room by running the **cleanup function**. Then it checks into the new room by running the new **setup function**. This strict sequence guarantees you never have two active connections open at the same time.

### Step 1: First, we construct the parent container ChatWorkspace.jsx

We start our implementation at the top: the parent container `ChatWorkspace.jsx`.

We begin here because the parent defines the layout and dictates the shared state for the entire workspace. It decides which room is currently active and coordinates the child components without touching websockets directly:

```jsx title="ChatWorkspace.jsx"
import { useState } from 'react';
export default function ChatWorkspace() {
  const [roomId, setRoomId] = useState('general'); // **STATE:**<br>Coordinates active channel across newsroom views
  return (
    <main className="chat-layout">
      <ChannelSelector activeRoom={roomId} onSelect={setRoomId} /> // **DATA FLOW:**<br>Passes current channel and setter callback
      <ChatRoom roomId={roomId} /> // **REACTIVE PROP:**<br>Triggers effect re-synchronization when value changes
    </main>
  );
}
```

Look at line 3: `const [roomId, setRoomId] = useState('general')`. We declare state here because multiple child components need to coordinate around the active channel.

Now look at line 6: `<ChannelSelector activeRoom={roomId} onSelect={setRoomId} />`. We have not coded `ChannelSelector` yet. But right here in the parent, we establish its contract. The parent passes down the active room string for styling, and passes `setRoomId` so the child can report user selections. We will build that child next in step 2.

Now look at line 7: `<ChatRoom roomId={roomId} />`. Notice that we pass `roomId` as a prop. Notice also that the parent contains zero effect code and zero socket logic. If we put the websocket connection in `ChatWorkspace`, switching channels would force the entire workspace layout to re-render and re-initialize. By delegating `roomId` downward as a prop, we turn `ChatRoom` into an isolated reactive boundary. We will build that component in steps 3 and 4.

To recap this first step: the parent holds the shared state that child components need to coordinate, and leaves external socket synchronization to the child boundary.

### Step 2: Next, we build the channel selector child ChannelSelector.jsx

In step 2, we fulfill the contract established by the parent: we build `ChannelSelector.jsx`.

This child component is responsible for the channel navigation pills at the top of the workspace:

```jsx title="ChannelSelector.jsx"
export default function ChannelSelector({ activeRoom, onSelect }) {
  const rooms = ['general', 'politics', 'breaking'];
  return (
    <nav className="channel-bar">
      {rooms.map((room) => (
        <button key={room} className={room === activeRoom ? 'active' : ''} onClick={() => onSelect(room)}>#{room}</button> // **ACTION:**<br>Notifies parent to update active channel
      ))}
    </nav>
  );
}
```

Notice the function parameters: we destructure `{ activeRoom, onSelect }` directly from props. That matches the contract we wrote in step 1. `ChannelSelector` owns zero local state. It relies entirely on its parent to provide the active channel name and the function to update it.

Look at the button click handler on line 6: `onClick={() => onSelect(room)}`.

Where does `onSelect` come from? Look back at Step 1 in `ChatWorkspace.jsx`. The parent declared `const [roomId, setRoomId] = useState('general')`, and then rendered: `<ChannelSelector activeRoom={roomId} onSelect={setRoomId} />`.

Notice what happened: the parent handed its private updater function `setRoomId` to the child under the prop name `onSelect`. `ChannelSelector` does not own state, and it does not know what `roomId` is used for. It only holds a telephone line called `onSelect`.

When the reporter clicks a button, the native browser `onClick` fires and calls `onSelect(room)`. Because `onSelect` points directly to `setRoomId`, that call immediately executes `setRoomId('politics')` back in `ChatWorkspace`.

This is standard **inverse data flow**: data flows down through props (`activeRoom`), and user actions flow up through callbacks (`onSelect`).

What would happen if `ChannelSelector` opened the websocket connection itself?

If you put the `useEffect` or socket connection inside `ChannelSelector`, the navigation buttons would be trapped managing network sockets, reconnection timers, and message buffers. Worse, the chat message area in `ChatRoom` would have no way to access that socket without messy prop-drilling or global state hacks. You would have buttons and network protocols tangled in a single file.

By separating them, `ChannelSelector` owns zero `useState` and zero `useEffect`. It is a pure presenter: given the same `activeRoom` string and `onSelect` callback, it will always render the exact same three buttons.

This separation gives you two concrete superpowers:
1. If tomorrow you replace the button pills with a dropdown `<select>` menu, you touch zero lines of websocket code.
2. If you swap the websocket protocol in `ChatRoom` for a mock test service, you touch zero lines of button code.

To recap this step: user interactions in `ChannelSelector` flow upward to `ChatWorkspace` through `onSelect`, changing the parent's `roomId` state.

### Step 3: Then, we declare the reactive effect in ChatRoom.jsx

In step 3, we build the core reactive boundary: slice 1 of `ChatRoom.jsx`.

Think about what must happen when `roomId` changes.
The component receives a new `roomId` prop.
It must terminate the previous websocket connection.
Then it must open a new connection to the new channel:

```jsx title="ChatRoom.jsx" startLine="1" continues="bottom"
export default function ChatRoom({ roomId }) {
  const [status, setStatus] = useState('disconnected');
  useEffect(() => {
    const connection = createConnection(roomId); // **SETUP:**<br>Instantiates socket for current roomId
    connection.connect(() => setStatus('connected'));
    return () => {
      connection.disconnect(); // **CLEANUP:**<br>Terminates socket before next setup or unmount
      setStatus('disconnected');
    };
  }, [roomId]); // **DEPENDENCY:**<br>Triggers cleanup and re-setup whenever roomId changes
```

Look closely at the `useEffect` call on lines 3 to 10. Notice the dependency array on line 10: `[roomId]`. This tells React that the effect depends on the value of `roomId`. Whenever `roomId` changes between renders, React must re-synchronize the effect.

Now look at the body of the effect on lines 4 and 5. That is your **setup function**. It calls `createConnection(roomId)` and initiates the connection with `connection.connect()`. When the socket opens, it updates local state to `'connected'`.

Now look at lines 6 to 9: `return () => { connection.disconnect(); setStatus('disconnected'); };`. That return statement is your **cleanup function**. It tells React how to stop synchronizing.

Here is the vital rule of effect execution. When `roomId` changes from `"general"` to `"politics"`, React does not just run the setup code with `"politics"`. First, React runs the cleanup function returned during the `"general"` render. That disconnects the old socket. Only after the old socket is closed does React run the setup code with `"politics"`.

To recap this step: the effect pairs every setup with a cleanup, ensuring that changing `roomId` cleanly shuts down the old channel before opening the new one.

### Step 4: Finally, we seal the chat interface and message composer

In step 4, we complete `ChatRoom.jsx` by adding the message composer interface and closing the component tag:

```jsx title="ChatRoom.jsx" startLine="11" continues="top"
  return (
    <section className="chat-card">
      <header className="chat-header">
        <h3>Channel: #{roomId}</h3>
        <span className={`status-badge ${status}`}>{status}</span> // **UI STATUS:**<br>Reflects live connection state
      </header>
      <input placeholder={`Broadcast to #${roomId}...`} />
      <button type="button">Send</button> // **CONTROL:**<br>Dispatches message to active connection
    </section>
  );
}
```

Notice the header on lines 13 to 16. It renders the current channel name `#{roomId}` and a status badge showing whether the socket is `'connected'` or `'disconnected'`.

Now look at the message area on lines 17 and 18. It provides an input and a Send button. When the reporter types a message and submits it, the message travels across the currently active websocket connection.

Notice what happens when the user switches channels: `ChatRoom` never unmounts from the DOM. The card stays in place. The input box stays in place. But behind the scenes, React executed the cleanup function to close the previous socket and executed the setup function to connect to the new socket.

The `<section>` boundary seals this entire workflow. It isolates connection management from the rest of the application. The parent container `ChatWorkspace` never has to know how websockets work, and `ChannelSelector` never has to know how connections are cleaned up.

Let us recap the senior rule. An effect does not represent component mounting or unmounting. An effect represents an ongoing synchronization cycle. When dependencies change, React always runs the cleanup from the previous render before running the setup for the next render.

### Lessons from the Experiment: Naive Expectation vs Reality

Developers familiar with traditional component lifecycles instinctively assume that an effect only runs its cleanup function when the component is removed from the screen. This naive expectation leads to severe bugs: when props or state change, developers expect the effect to update in place, leaving old subscriptions active and creating zombie listeners.

In our experiment, the `ChatRoom` component remained mounted continuously while the reporter switched channels from `"general"` to `"politics"`. However, React still ran the cleanup function for `"general"` before running the setup function for `"politics"`. If React waited until unmount to run cleanup, the application would maintain two open sockets simultaneously, receiving duplicate messages and wasting network bandwidth.

### The Exact Synchronization Sequence: Cleanup Before Re-Setup

To understand why React executes cleanup before re-setup, we must trace the exact sequence of events during a dependency transition. A dependency change is not a simple function call; it is an orchestrated three-step sequence. Without understanding this sequence, developers are baffled by console logs showing cleanup running with old prop values while the screen already displays new prop values.

Consider what happens when the user clicks the `# politics` button while currently connected to `# general`. First, React updates the `roomId` state in `ChatWorkspace` and re-renders the component tree. Second, React commits the changes to the DOM: the screen now paints the new title "Channel: #politics". Third, before running the new effect, React calls the cleanup function returned during the previous render. That cleanup function closed over `roomId = "general"`, so it disconnects cleanly from `# general`. Fourth, React runs the effect setup function for the current render. That setup function closes over `roomId = "politics"`, connecting to the new channel. If setup ran before cleanup, both connections would exist concurrently, causing race conditions and state corruption.

What happens in React 19 development with Strict Mode? When your component first mounts in development, React intentionally mounts the component, runs setup, runs cleanup immediately, and then runs setup a second time. Why? To prove that your cleanup function completely undoes whatever your setup function did. If your cleanup function is missing or incomplete, the second setup exposes the bug immediately during development before it reaches production users.

> [!WILD]
> **Why does cleanup see the old prop value?** Imagine you write a letter, place it inside an envelope, and seal it shut. Inside that envelope, you wrote: "Please lock door number ten." Ten minutes later, you move to room twenty. Does moving to room twenty magically rewrite the letter inside the sealed envelope? Of course not. The sealed envelope still says: "Please lock door number ten." In JavaScript, a **cleanup function** is like that sealed envelope: it is a **closure**. When React created the cleanup function during the first render, it captured the old prop value `roomId = "general"`. When React opens that envelope during the next render, it executes the instructions inside: it disconnects from `"general"`, not `"politics"`. This **closure capture** guarantees that cleanup always cleans up the exact resource that was opened.

### Where you will meet this

- Editorial websocket channels: Subscribing to live newsroom dispatches and disconnecting the old channel before opening the new one when reporters switch topics.
- Document title and event observers: Attaching window resize or scroll listeners that re-bind to new target containers when layout dimensions change.
- Real-time stock and score tickers: Subscribing to high-frequency market tickers where changing the selected asset requires terminating the previous data feed.
- Video and audio player instances: Initializing native media player instances that must destroy existing playback sessions before mounting a new media stream.

### Glossary

- **Reactive Effect**: An effect declared with `useEffect` that synchronizes an external system with current props and state, re-running whenever its declared dependencies change.
- **Effect Lifecycle**: The independent lifecycle of an effect, consisting solely of starting synchronization via setup and stopping synchronization via cleanup, distinct from component mounting.
- **Cleanup Function**: A callback returned by an effect setup function that releases resources, cancels subscriptions, and disconnects sockets created during that synchronization cycle.
- **Dependency Array**: The second argument to `useEffect`, listing all reactive values (props, state, and derived variables) read inside the effect to tell React when to re-synchronize.
- **Strict Mode Re-synchronization**: React development behavior that executes setup, cleanup, and setup on initial mount to verify that effect cleanup routines completely undo setup actions.

### Summary

**The Lifecycle of a Reactive Effect in React 19**

In production applications, understanding the independent lifecycle of reactive effects prevents zombie connections, memory leaks, and out-of-sync external systems. Here is your streetwise review.

❒ Core Principles of Effect Synchronization
1. Think of effects as **synchronization cycles**, not component lifecycles.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Components mount, update, and unmount; effects start synchronizing and stop synchronizing.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) An effect may start and stop synchronization dozens of times while its host component remains continuously mounted.
2. React **always runs cleanup before re-setup** when dependencies change.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Before connecting to the new dependency, React calls the cleanup function from the previous render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Closure capture ensures the cleanup function accesses the exact props and state from the render that created it.
3. Every setup must have a **mirror cleanup function** that completely reverses it.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) If setup connects, cleanup must disconnect; if setup subscribes, cleanup must unsubscribe.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Strict Mode in development tests this symmetry by running setup, cleanup, and setup immediately on mount.

➔ NEVER assume an effect only cleans up when the component leaves the screen.
➔ ALWAYS return a cleanup function from effects that open connections, subscriptions, or timers.
➔ IF an effect reads a reactive prop or state variable THEN **include it in the dependency array to trigger timely re-synchronization**.

**DO THIS:** Return a mirror cleanup function that reverses setup and cleanly releases external resources.
```jsx right title="Resilient Effect Pattern"
function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect();
    return () => {
      connection.disconnect(); // cleans up old channel before next setup
    };
  }, [roomId]);
  return <h2>Room: #{roomId}</h2>;
}
```

**DO NOT DO THIS:** Never omit cleanup or treat effects as mount-only routines when dependencies change.
```jsx wrong title="Leaky Effect Pattern"
function LeakyChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect(); // leaks old connection when roomId changes
  }, [roomId]); // missing cleanup leaves zombie sockets active
  return <h2>Room: #{roomId}</h2>;
}
```
