Lessons from the Code
The Modular Import Architecture

An architectural evaluation of component file splitting, default exports, named exports, and the curly brace trap across application layers.

Component Layer Naive Expectation (Legacy Approach) What Happened (React 19 Reality)
1. The Parent Container (NewsPortal.jsx) Monolithic Single File Developers keep all components in a single thousand-line file to avoid import syntax, causing massive merge conflicts and zero component reusability. Explicit Module Orchestration The parent imports SiteHeader as a default export and ArticleList as a named export, establishing clear architectural contracts across boundaries.
2. The Primary Child (SiteHeader.jsx) Ambiguous Named Lookup Developers wrap default exports in curly braces { SiteHeader }, assuming named property lookup resolves default module exports. Default Export Contract Exported via export default and imported without curly braces. Omitting curly braces grabs module.default, preventing undefined runtime crashes.
3. The Shared Module (ArticleComponents.jsx) Redundant File Proliferation Developers create separate files for every small two-line helper component, cluttering directory trees and complicating import paths. Multi-Component Named Bundle Groups related components (ArticleCard, ArticleList) in a single file via export function, imported selectively with tree-shaking support.
4. The Entry Point (main.jsx) Global Scope Pollution Attaching components to window or loading scripts sequentially in HTML leads to ordering bugs and silent naming collisions. Isolated Module Graph ES Modules establish strict file-level scope. createRoot mounts the root component, and modern bundlers construct an optimized dependency graph.
Final Verdict Fragile Coupling Monolithic files, global namespace collisions, and undefined runtime crashes from misplaced curly braces. Bulletproof Modularity Isolated ES module boundaries, explicit default and named contracts, and tree-shakeable component bundles.
