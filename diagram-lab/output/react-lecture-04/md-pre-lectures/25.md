### The Child Placement Rule
- [p] ◇ {preknowledge:} In Lecture 24, we learned how `useActionState` manages a form's action return value and `isPending` flag. However, in modern component libraries, the submit button is often a separate reusable component (`<SubmitButton />`) rendered deep inside complex layouts, cards, or dialog footers. {problem:} Why does calling `useFormStatus()` in the same component that renders `<form>` always return `pending: false`? ◼ Pedagogical qualification: Contrast parent form scope with deep child hook reads; terms introduced: **useFormStatus hook**, **child placement rule**, **context reach**.
- [p] ★ {preknowledge:} The `useFormStatus` hook (exported from `'react-dom'`) returns status information about the **parent** `<form>` element. Under the hood, React provides form status using an internal Context Provider that wraps the form's children. Because a context consumer must be rendered *inside* its provider, `useFormStatus` **MUST be called from a component that is a child of the `<form>`**. If you call `useFormStatus` in the component that renders `<form action={...}>`, there is no parent form above it in the React tree, and `pending` will be permanently `false`. ◼ Pedagogical qualification: Explain the context mechanism and the child placement mandate; terms introduced: **child placement rule**, **internal context provider**, **enclosing form**.
- [p] ★ {preknowledge:} This architectural rule enforces a clean separation of concerns: the parent component defines the `<form action={...}>`, while nested child components (like buttons, progress bars, or field indicators) can read the form's status independently without any props passed down. ◼ Pedagogical qualification: Explain decoupling of layout and form state; terms introduced: **separation of concerns**, **prop drilling elimination**, **self-contained controls**.
- [code] Child placement contrast:
```jsx title="The Child Placement Rule"
// FAILS: Called in same component rendering <form>; pending is ALWAYS false!
function BrokenForm() {
  const { pending } = useFormStatus();
  return <form action={act}><button disabled={pending}>Send</button></form>;
}
// WORKS: Called from a child component rendered inside <form>:
function GoodForm() {
  return <form action={act}><SubmitButton /></form>;
}
```
- [grounding] Leading Question: What other properties does useFormStatus return besides pending?
  Confusion Point: Does `useFormStatus` only give you a boolean `pending` flag?
  Scene & Repetition: `useFormStatus` returns four properties: `{ pending, data, method, action }`. While `pending` is a boolean, `data` is the actual `FormData` instance currently being submitted! This means a child component can inspect `data.get('title')` while pending to render optimistic feedback: "Publishing 'City Budget'..." before the server even responds!
  Key Terms (Bold): `**formData inspection**`, `**optimistic child feedback**`, `**method property**`, `**action property**`.
  Resolution: `useFormStatus` returns `data`, `method`, and `action` in addition to `pending`, enabling child components to render rich submission previews.

### Eliminating Prop Drilling in Design Systems
- [p] ◇ {preknowledge:} We know `useFormStatus` must live in a child component. {problem:} How does this hook transform how teams design reusable buttons and form inputs? ◼ Pedagogical qualification: Connect useFormStatus to design systems; terms introduced: **design system buttons**, **zero-prop controls**, **form awareness**.
- [p] ★ {preknowledge:} In design systems, a `<PrimaryButton>` previously required an `isPending` or `loading` prop passed from above. Every modal or card that hosted a form had to accept `isPending` and thread it down. With `useFormStatus`, a `<SubmitButton>` becomes completely **form-aware and self-contained**: it reads `pending` from the enclosing form automatically, disabling itself and rendering a spinner with zero props required. ◼ Pedagogical qualification: Explain self-contained design system button pattern; terms introduced: **self-contained button**, **zero-prop pattern**, **form awareness**.
- [p] ★ {preknowledge:} If you render multiple forms on a page, each `useFormStatus` call automatically binds to its closest enclosing `<form>` ancestor, completely isolating their pending states from one another. ◼ Pedagogical qualification: Explain multiple ancestor form isolation; terms introduced: **ancestor isolation**, **independent form status**, **lexical scoping**.
- [code] Self-contained submit button pattern:
```jsx title="Self-Contained Submit Button"
import { useFormStatus } from 'react-dom';
export default function SubmitButton() {
  const { pending, data } = useFormStatus();
  return (
    <button disabled={pending} type="submit">
      {pending ? `Saving ${data?.get('title')}...` : 'Save'}
    </button>
  );
}
```
- [grounding] Leading Question: Does useFormStatus track nested formAction buttons?
  Confusion Point: If a button uses `formAction` instead of the form's default action, what does `useFormStatus` show?
  Scene & Repetition: `useFormStatus` tracks the parent `<form>`'s action submission, regardless of whether it was triggered by the form's default action or a button's `formAction`. When the action runs, `pending` flips to true for the entire form subtree!
  Key Terms (Bold): `**formAction tracking**`, `**subtree synchronization**`, `**action trigger source**`, `**unified pending**`.
  Resolution: `useFormStatus` tracks form submissions regardless of whether the action was defined on the `<form>` tag or a specific button's `formAction`.

- [p] ★ {preknowledge:} The parent container owns the action handler and renders `<form action={publish}>`. - [p] ★ {preknowledge:} `SubmitButton` is nested inside `ModalBody`, which is nested inside `PublishModal`'s `<form>`. {problem:} The terminal child must read the form's pending state using `useFormStatus`. ◼ Pedagogical qualification: Build self-contained submit button using useFormStatus.
- [code] Button child SubmitButton.jsx:

```jsx title="SubmitButton.jsx"
export default function SubmitButton() {

```
- [p] ★ Step 3 completes the self-contained control: Look at line 3: `const { pending } = useFormStatus();`. `SubmitButton` reaches directly up the component tree to the enclosing `<form>` rendered by `PublishModal`, disabling the button and changing the label to "Publishing..." while the action runs. ◼ Pedagogical qualification: Deconstruct useFormStatus consumer mechanics.
- [p] What would happen if `SubmitButton` was rendered outside the `<form>` element? If `SubmitButton` is rendered outside the enclosing `<form>`, React's internal form status context has no provider above it. `useFormStatus()` evaluates to `{ pending: false, data: null, method: null, action: null }`, and the button will never reflect the form's pending state. ◼ Pedagogical qualification: Apply Negative Counterfactual Law to useFormStatus called outside form boundaries.

- [grounding] Leading Question: Why is useFormStatus exported from react-dom rather than react?
  Confusion Point: Why isn't `useFormStatus` in the main `'react'` package like `useActionState`?

### Glossary
- **useFormStatus**: A React DOM hook that returns the pending status and data of the nearest enclosing parent `<form>`.
- **Child Placement Rule**: The requirement that `useFormStatus` must be invoked inside a component rendered as a child of `<form>`, not in the form's parent.
- **Enclosing Form**: The closest `<form>` ancestor element in the React component tree providing status context.
- **Prop Drilling Elimination**: The architectural benefit of allowing deep components to read parent form status without intermediate prop threading.
- **Form-Aware Component**: A component (like a submit button) that self-manages its disabled and loading states by reading form context.
- **Form Data Inspection**: Using the `data` property returned by `useFormStatus` to access field values currently in flight.

### Summary

**React 19 useFormStatus Invariants**

In daily production, `useFormStatus` eliminates tedious prop drilling for nested form controls. Understanding the Child Placement Rule ensures that reusable buttons and banners reliably reflect form execution state. Here is your streetwise review.

❒ useFormStatus Invariants

1. `useFormStatus` must be called from a child inside `<form>`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Calling it in the component that renders `<form>` always returns `pending: false`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) It reads status via React context from the nearest enclosing `<form>` ancestor.

2. It returns `{ pending, data, method, action }`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `pending` is a boolean indicating whether the form is submitting.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) `data` is the `FormData` instance being submitted, enabling live previews.

3. Import `useFormStatus` from `'react-dom'`, not `'react'`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) It is a DOM-specific hook coupled to the HTML `<form>` element.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Multiple forms on a page isolate their status to their own subtrees.

➔ NEVER call `useFormStatus` inside the same component that renders `<form>`.

➔ ALWAYS extract submit buttons into child components when reading form status.

➔ IF you need to preview submitted fields during loading THEN **read them from `const { data } = useFormStatus()`**.

**DO THIS:** Call useFormStatus in a child component nested inside the form.

```jsx right title="SubmitButton.jsx"
// Clean child component reading parent form status
import { useFormStatus } from 'react-dom';
export default function SubmitButton() {
  const { pending } = useFormStatus();
  return (
    <button disabled={pending} type="submit">
      {pending ? 'Publishing...' : 'Publish'}
    </button>
  );
}
```

**DO NOT DO THIS:** Never call useFormStatus in the parent component rendering the form.

```jsx wrong title="Same-Component Anti-Pattern"
// FAILS: useFormStatus called in same component as <form>; pending is ALWAYS false!
import { useFormStatus } from 'react-dom';
export default function BrokenForm({ action }) {
  const { pending } = useFormStatus(); // BUG: Always false!
  return (
    <form action={action}>
      <button disabled={pending}>Publish</button>
    </form>
  );
}
```
