### The Modern Starting Point
- [p] ◇ {preknowledge:} In earlier lessons, we learned that a React component is a JavaScript function returning markup, and saving that function in a file gives us a reusable building block. Save an ordinary .jsx file to your desktop and double-click it in your file explorer, and the browser displays a blank white screen with a syntax error because web browsers natively understand only plain JavaScript, HTML, and CSS, and cannot parse raw JSX or unbundled import statements. {problem:} Browsers cannot execute raw JSX or modular imports directly without an upfront compilation and bundling step. ◼ Pedagogical qualification: Establish the physical browser execution boundary; ground why starting a React project requires a dedicated build environment; terms introduced: **build tool**, **framework**, **client-side rendering**, **CSR**, **server-side rendering**, **SSR**, **static-site generation**, **SSG**.
- [p] ★ {preknowledge:} For seven years, the official React documentation instructed every newcomer to open a terminal and run `npx create-react-app my-app`, which generated a ready-to-run project folder configured with Webpack and Babel. Run that command on a modern computer or expand the project to fifty components, and every file save forces Webpack to re-crawl the entire module graph from scratch, forcing the developer to wait twenty seconds for recompilation while the computer fans spin. {problem:} Create React App suffered from slow development reloads, produced monolithic client-side JavaScript bundles that delayed initial page rendering, and lacked any architecture for server-side pre-rendering. ◼ Pedagogical qualification: Trace the historical pain point that led to the deprecation of Create React App; underline the developer velocity bottleneck in legacy tooling.
- [p] {old solution:} Developers historically relied on Create React App and its underlying Webpack development server to compile JSX and bundle dependencies into a single monolithic script. ◼ Educational objective: Show the legacy starting point before introducing modern replacements.
- [code] Old Create React App CLI & script execution:
```bash title="Terminal (Historical CRA)"
npx create-react-app national-weather // 1. historical tool scaffolds monolithic **WEBPACK** setup
cd national-weather                   // 2. navigates into the project **DIRECTORY**
npm start                             // 3. starts slow Webpack **DEVELOPMENT** server
```
◼ **Code Self-Audit (What this legacy snippet shows):** 1. `npx create-react-app national-weather`: Legacy scaffolding command now deprecated by the React team. 2. `cd national-weather`: Directory navigation into the generated project folder. 3. `npm start`: Legacy script invoking `react-scripts start` and Webpack dev server.
- [p] ◇ {new solution:} Today, the React ecosystem separates project creation into two distinct architectural categories: lightweight build tools that package code for browser execution, and full-stack frameworks that execute code across both the web server and the browser. A build tool like Vite compiles JSX and serves files over native browser modules, whereas a full-stack framework like Next.js or React Router manages routing, server data loading, and HTML pre-rendering. ◼ Pedagogical qualification: Deliver the upfront architectural breakthrough; contrast browser-only compilation with full-stack server-client execution in plain CEFR B2 vocabulary.
- [grounding] Leading Question: Why did Create React App get retired?
  Confusion Point: Why did the official React documentation stop recommending the tool that everyone used for seven years?
  Scene & Repetition: In older projects, saving a single file forced the computer to rebuild the entire application bundle from scratch. Developers waited dozens of seconds for recompilation. As the application expanded, the browser had to download megabytes of JavaScript before displaying a single pixel. This is the problem with older bundlers: they force the user to wait for monolithic files, time and time again. Which, in turn, creates sluggish development and blank mobile screens. Modern tools eliminate this bottleneck. A modern **build tool** serves files instantly using native browser modules, while a modern **framework** pre-renders HTML on the server so readers see content immediately.
  Key Terms (Bold): `**Create React App**`, `**build tool**`, `**framework**`, `**client-side rendering**`.
  Resolution: Modern tools eliminate monolithic rebuilds by serving unbundled ES modules during development and pre-rendering HTML for production.

### Generating a Project with Vite
- [p] ◇ {preknowledge:} We know that modern browsers support native ECMAScript modules, allowing an HTML page to load modular JavaScript files using `<script type="module" src="...">`. When you save an edit to a single component file in a modern project, the browser can fetch only that single changed file without reloading the rest of the application. {problem:} Developers need a fast, lightweight command-line tool to scaffold this modern module structure without manual configuration. ◼ Pedagogical qualification: Introduce Vite as the modern standard build tool; explain the shift from monolithic bundling to native ES modules.
- [p] ★ {preknowledge:} When running a command-line generator, developers often see placeholder documentation like `npm create vite@latest <app_name>`. Type that command with literal angle brackets into a bash or zsh shell, and the shell throws a syntax error because angle brackets are interpreted as file redirection operators. {problem:} Generic scaffolding formulas must be translated into concrete, copy-pasteable terminal commands with valid project names. ◼ Pedagogical qualification: Explain the Dual-Form CLI pattern; unpack the anatomy of the scaffolding formula in plain B2 English.
- [p] ★ {preknowledge:} The scaffolding command `npm create vite@latest national-weather` is shorthand for running the `create-vite` generator package through npm's execution cache. npm downloads the generator, runs it once, and discards it. {problem:} Developers may assume the command installs a tool permanently, when in fact there is no global installation and nothing permanent left on the machine afterward. ◼ Pedagogical qualification: Narrate the download, run once, discard lifecycle of `npm create`; discharge the global-install assumption before the flag anatomy begins.
- [p] ★ {preknowledge:} The command carries a double dash `--` in its middle. The `--` is the standard **argument separator**: it tells npm to stop reading its own flags here, because everything after this marker belongs to the generator. {problem:} Without the separator, npm consumes `--template react` itself, the flag never reaches the generator, and the generator opens its interactive question prompt instead of scaffolding the project. ◼ Pedagogical qualification: Unpack the argument separator as its own concern; stage the broken-command failure as the concrete on-screen symptom of the interactive prompt appearing.
- [p] ★ {preknowledge:} Once the separator has passed the flags through, `--template react` reaches the generator. The flag tells the generator to skip its interactive questions and generate the official React preset. {problem:} Without the flag, the generator would ask its questions one by one and wait for keyboard answers before creating anything. ◼ Pedagogical qualification: Explain the preset flag as the non-interactive path; connect it to the silent, self-finishing scaffold the developer watches in the terminal.
- [p] ★ {preknowledge:} The `<app_name>` placeholder in documentation means a value you replace, not text you type. Valid names use lowercase letters, numbers, and hyphens; no spaces, no uppercase. {problem:} The name is not cosmetic: it becomes the folder name on disk and the "name" field in package.json, and typing literal angle brackets into bash or zsh triggers a redirection syntax error. ◼ Pedagogical qualification: Unpack the placeholder naming rules as a separate concern; anchor the two physical consequences of the chosen name, the folder on disk and the package.json name field.
- [code] Terminal scaffolding commands for creating and running the project:
```bash title="Terminal"
npm create vite@latest national-weather -- --template react // 1. scaffolds the **PROJECT** directory
cd national-weather                                         // 2. navigates into the project **DIRECTORY**
npm install                                                 // 3. installs the React **DEPENDENCIES**
npm run dev                                                 // 4. starts the local **DEVELOPMENT** server
```
◼ **Code Self-Audit (What this snippet introduces):** 1. `npm create vite@latest national-weather -- --template react`: Scaffolding command specifying concrete project name and official React starter preset. 2. `cd national-weather`: Shell command changing working directory into the newly created project folder. 3. `npm install`: Package manager command reading `package.json` and installing dependencies into `node_modules`. 4. `npm run dev`: NPM script invoking the local development server at `localhost:5173`.
- [p] ★ Physical File and Folder Anatomy: package.json: The first generated file is package.json, the project manifest, and it holds two separate lists. (a) The runtime dependencies (dependencies) are the packages the application needs while it runs: react and react-dom. The browser loads these when a reader opens the page, so these are the only packages your readers ever download. (b) The development dependencies (devDependencies) are the packages your computer needs while you build and serve the project: vite and @vitejs/plugin-react. They run on your machine, and they never ship to the browser. The split is the point: the build tools stay on your machine, so what the browser loads stays small. The file's scripts object maps npm run dev to vite, which starts the development server, and npm run build to vite build, which produces the production files. ◼ Pedagogical qualification: Build each list as a lettered anchor in the fixed four-part shape (kind-name, short reminder, contents, consequence); close on the meaning of the split, the browser loads less.
- [p] ★ Physical File and Folder Anatomy: index.html at the root: The file index.html sits at the project root, not buried in a public folder like older tools. It holds the empty `<div id="root"></div>` plus the `<script type="module" src="/src/main.jsx">` tag that starts the module chain. ◼ Pedagogical qualification: Ground the entry HTML shell physically; underline the root placement and the module script as the start of the whole module chain.
- [p] ★ Physical File and Folder Anatomy: vite.config.js and its three plugin jobs: The file vite.config.js registers the React plugin, and that plugin does three separate jobs. Job one: it compiles JSX into standard JavaScript function calls. Job two: Fast Refresh keeps a live connection to the browser and swaps a saved component without a full page reload and without wiping form input. Job three: at npm run build, Rollup bundles, shrinks, and optimizes the whole project into production files. ◼ Pedagogical qualification: Unpack the React plugin into three separate pieces instead of one chained clause; bold-baptize Fast Refresh and Rollup at their lecture debut.
- [p] ★ Physical File and Folder Anatomy: src/main.jsx mounting App.jsx: Inside the src folder, the file main.jsx finds the root div with document.getElementById('root'), hands it to createRoot, and mounts App.jsx, which renders the visible interface. ◼ Pedagogical qualification: Walk the mount chain from the root div to the visible interface; keep the mount point and the interface component as two named roles.
- [p] ★ Physical File and Folder Anatomy: node_modules with package-lock.json: The node_modules folder is where npm install downloads the libraries. Next to it, package-lock.json records the exact resolved versions so every machine installs the identical set. ◼ Pedagogical qualification: Pair the download folder with the lockfile; underline identical installs on every machine as the engineering benefit.
- [p] ★ Deconstructing Terminal Lines 2 to 4 (Navigation, Dependencies, and HMR): Navigating into the folder with cd national-weather establishes the execution context for all subsequent commands. Running npm install reads package.json, downloads react and react-dom into node_modules, and writes the exact resolved dependency versions into package-lock.json. Running npm run dev starts the local Vite development server at localhost:5173, establishing a WebSocket connection that provides Hot Module Replacement (HMR), swapping updated component code in browser memory in milliseconds without losing active form inputs or scroll position. ◼ Pedagogical qualification: Walk the developer through the four steps of project startup; define Hot Module Replacement and its browser-memory mechanics.

- [p] Introducing the canonical starter component file App.jsx: The default component generated by Vite demonstrates stateful interactivity using a simple counter card with a button. ◼ Pedagogical qualification: Frame the canonical starter component before displaying its syntax.
- [code] Canonical starter component:
```jsx title="App.jsx"
import { useState } from 'react';

export default function App() {
  const [count, setCount] = useState(0);
  return (
    <div className="card">
      <div className="starter-heading">Vite + React</div> // Brand headline declared in **STARTER**
      <button onClick={() => setCount((c) => c + 1)}>
        count is {count} // Button increments local component **STATE**
      </button>
      <p className="starter-caption">Click button to increment count</p> // Helper text guides **USER**
    </div>
  );
}
```
◼ **Code Self-Audit (What this snippet introduces):** 1. `import { useState } from 'react'`: Named import bringing the core React state hook into component scope. 2. `export default function App()`: Standard default export declaring the root component function. 3. `const [count, setCount] = useState(0)`: Array destructuring capturing the reactive state variable and its updater function with initial value zero. 4. `<button onClick={() => setCount((c) => c + 1)}>`: Inline click handler dispatching a state update with an updater arrow function. 5. `{count}`: JSX expression evaluating the active numerical value into the button label.
- [p] ★ State declaration and component memory: The line const [count, setCount] = useState(0) declares a piece of reactive memory called state. In plain JavaScript, ordinary local variables reset to zero every time a function executes, but React preserves this count variable across renders in internal memory. ◼ Pedagogical qualification: Deconstruct `useState` memory preservation; contrast local function scope with React fiber state retention.
- [p] ★ Event handling and reactive DOM updates: When the user clicks the button, the inline arrow function invokes setCount((c) => c + 1), dispatching an update request to React. React calls App() again with the updated count value, compares the new UI description against the previous one in memory, and surgically updates only the text node inside the button in the physical DOM. ◼ Pedagogical qualification: Connect the button click to the reconciliation loop; reinforce the declarative state projection model.

- [grounding] Leading Question: What makes a modern build tool so fast?
  Confusion Point: Why does editing a file in Vite update instantly, while older tools paused for several seconds?
  Scene & Repetition: In older bundlers, saving a file forced the bundler to rebuild every single file into one gigantic bundle before the browser could see the change. Vite reverses this. When you edit a file, the development server transforms only that single file and sends it directly over a live connection. The server never bundles the entire project again. This is the power of a modern **build tool**: it updates components in milliseconds through **Hot Module Replacement**, preserving your form inputs and scroll position.
  Key Terms (Bold): `**build tool**`, `**Hot Module Replacement**`, `**client-side rendering**`.
  Resolution: Vite keeps a live connection to the browser, sending only the changed module to be swapped in memory without full-page reloads.

### Client-Side Rendering Mechanics
- [p] ◇ {preknowledge:} In traditional websites, requesting a page sends an HTTP GET request to a web server, and the server returns a complete HTML document containing all the headlines, paragraphs, and images ready to read. In a Vite application, the web server returns an index.html file that contains no article text, no navigation links, and no buttons, containing only an empty <div id="root"></div> and a script tag. {problem:} The browser displays nothing until it downloads, parses, and executes the entire JavaScript bundle. ◼ Pedagogical qualification: Explain the empty shell delivery in client-side rendering; introduce the Single-Page Application (SPA) architecture.
- [p] ★ {preknowledge:} Once the browser downloads the JavaScript bundle, it executes the React library and invokes createRoot(document.getElementById('root')).render(<App />). React evaluates the App component function in memory, constructs a UI descriptor tree of lightweight objects, and creates physical DOM nodes to insert into the empty root container. {problem:} If the user is on a slow mobile network or an older smartphone, downloading and executing this bundle takes several seconds, during which the screen remains completely white. ◼ Pedagogical qualification: Trace the browser execution pipeline from empty container to mounted DOM; name the dual-canon: **Single-Page Application** and **client-rendered UI descriptor tree**.
- [p] ★ Practical trade-offs of CSR: Client-side rendering provides rapid, fluid page transitions once the initial bundle has loaded, because subsequent user actions do not require full-page reloads. However, this model carries two severe production limitations: slow initial load times that degrade Largest Contentful Paint (LCP) on mobile devices, and poor search engine visibility because web crawlers may index the empty HTML shell before client JavaScript finishes executing. ◼ Pedagogical qualification: Ground the engineering trade-offs of CSR in Core Web Vitals (LCP) and search engine optimization (SEO).
- [grounding] Leading Question: When does client-side rendering show a white screen?
  Confusion Point: When does a web page built with a client build tool stay completely blank for the first two seconds on a mobile phone?
  Scene & Repetition: Imagine a reader on a subway train opens The National Times on their smartphone. The screen displays a pure white window. When does this happen? It happens during the initial load because the server sent an empty HTML file containing nothing more than an empty root element. The browser cannot show a single word or button until it finishes downloading and executing the entire JavaScript file. On a slow mobile network, the reader stares at a blank screen while waiting. This delay is the fundamental cost of **client-side rendering**: you download the entire engine before seeing any content.
  Key Terms (Bold): `**client-side rendering**`, `**CSR**`, `**single-page application**`, `**build tool**`.
  Resolution: A white screen occurs when network or device delays postpone the initial download and execution of the client-side JavaScript bundle.

### When to Choose a Full-Stack Framework
- [p] ◇ {preknowledge:} We have seen that a build tool like Vite focuses strictly on compiling and serving client-side code for the browser. When an application grows to include multiple pages, secure database queries, and search-indexed public content, developers find that a build tool alone provides no built-in routing, no server data loading, and no HTML pre-rendering. {problem:} Teams are forced to assemble and maintain dozens of separate libraries for routing, data fetching, and bundling, creating configuration fatigue and fragile architectures. ◼ Pedagogical qualification: Define a full-stack framework; explain how frameworks combine client and server execution into a unified platform.
- [p] ★ {preknowledge:} When a user requests a page from a full-stack framework like Next.js or React Router, the framework executes the React components on the web server before sending any response. The server generates fully formed HTML containing the actual article text, headlines, and markup, and sends that HTML across the network. The browser renders this HTML immediately, so the reader sees the content on the very first paint. {problem:} Static HTML cannot respond to button clicks or user typing until the browser downloads the accompanying JavaScript bundle. ◼ Pedagogical qualification: Deconstruct Server-Side Rendering (SSR); explain the mechanics of server component execution and initial paint delivery.
- [p] ★ Hydration and interactive enablement: Once the server-rendered HTML is displayed, the browser downloads a compact client JavaScript bundle. React walks the existing physical DOM nodes and attaches event listeners to match the server markup through a process called hydration. After hydration completes, the static HTML becomes fully interactive without any visual flicker. ◼ Pedagogical qualification: Explain hydration mechanics; contrast static markup display with reactive event listener attachment.
- [p] ★ Static-Site Generation (SSG) in action: For content that does not change on every request, such as published news articles or documentation pages, modern frameworks pre-render the complete HTML at build time through Static-Site Generation (SSG). These static HTML files are deployed directly to a global Content Delivery Network (CDN), delivering pages to readers in milliseconds from servers located geographically close to them. ◼ Pedagogical qualification: Explain SSG and CDN distribution; ground the cost and latency benefits of static hosting.
- [p] The Architectural Decision Matrix: Choose a build tool like Vite when building authenticated internal dashboards, private tools behind a login wall, isolated component libraries, or when learning core React fundamentals where server infrastructure adds unnecessary complexity. Choose a full-stack framework like Next.js or React Router when building public web applications, e-commerce storefronts, content-driven news platforms requiring search engine optimization, or applications with complex multi-page routing and server data requirements. ◼ Pedagogical qualification: Provide decisive, actionable engineering criteria for choosing between build tools and frameworks in production.
- [grounding] Leading Question: Does a full-stack framework require a backend server?
  Confusion Point: Does choosing a framework force an engineering team to manage and pay for a fleet of Node.js servers?
  Scene & Repetition: Many developers avoid frameworks because they fear the operational burden of managing backend servers. But modern frameworks support static exports. They can generate pre-rendered HTML files during the build and upload them straight to a static file host. You do not need a running server. This means you can use a **framework** purely for its routing and pre-rendering capabilities without maintaining any server infrastructure.
  Key Terms (Bold): `**framework**`, `**server-side rendering**`, `**SSR**`, `**static-site generation**`, `**SSG**`.
  Resolution: Modern frameworks support static exports and client rendering, allowing teams to benefit from integrated routing and pre-rendering without running server infrastructure.

### Glossary
- [glossary] Build Tool ◼ A command-line program that compiles source files, bundles dependencies, and serves local development assets for browser execution.
- [glossary] Full-Stack Framework ◼ An integrated application architecture that manages routing, server-side data loading, and execution across both server and browser environments.
- [glossary] Client-Side Rendering (CSR) ◼ A rendering architecture where the server delivers a minimal HTML shell and the browser executes JavaScript to construct the user interface.
- [glossary] Server-Side Rendering (SSR) ◼ A rendering architecture where the web server runs React components on each HTTP request to generate and send fully constructed HTML to the browser.
- [glossary] Hydration ◼ The client-side process where React attaches event listeners to pre-rendered server HTML to make the static markup interactive.
- [glossary] Hot Module Replacement (HMR) ◼ A development mechanism that replaces updated component modules in browser memory over a live connection without reloading the full page.

### Summary
- [p] Streetwise architectural review: In modern web development, starting a project is not a matter of picking one universal tool, but of identifying where your application needs to execute. A client build tool like Vite gives you unmatched developer speed, near-instant server starts, and simple static deployments, which makes it the ideal choice for private dashboards and single-page applications. A full-stack framework like Next.js or React Router moves the first render to the server, delivering fully formed HTML to users on slow connections and search engine crawlers, but requires you to understand the boundary between server execution and client hydration. ◼ Emphasize developer velocity versus application delivery requirements.
- [p] Core mental model review: Keep two fundamental boundaries clear in your mind: compilation boundaries and execution boundaries. A build tool handles the compilation boundary, transforming JSX and modern syntax into browser-ready JavaScript. A full-stack framework handles both the compilation boundary and the execution boundary, deciding whether a component runs on the Node.js server, at build time, or in the user's browser. ◼ Underline browser-only execution versus unified server-client rendering.
- [p] Permanent operational directives: ➔ ALWAYS start with Vite when building internal tools, authenticated subscriber dashboards, or learning core React hooks where server complexity adds unnecessary friction. ➔ ALWAYS choose a full-stack framework when your project requires search engine optimization, fast initial page loads on mobile networks, or integrated server-side data fetching. ➔ NEVER use deprecated tools like Create React App for new projects, because slow Webpack reloads and unmaintained dependencies create technical debt from day one. ➔ IF your application is a public content site, THEN pre-render HTML on the server or at build time so readers never stare at an empty white screen. ◼ Solidifies permanent architectural habits for launching React projects.
