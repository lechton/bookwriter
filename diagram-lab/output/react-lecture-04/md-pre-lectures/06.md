### Why React Needs a Bridge to the DOM
- [p] ◇ {preknowledge:} In earlier lessons, we learned that a React component is a JavaScript function that returns JSX markup describing what should appear on screen (see Lecture 3 and Lecture 4). In your editor, you write tags like `<header>` and `<h1>` inside your component files. {problem:} Web browsers do not understand React component functions directly, and saving a component file to disk does not cause it to paint onto the screen. What is a **renderer**? In web development, React draws a strict boundary between two independent systems: the core **component library**, which designs virtual UI trees, and the platform **renderer**, which builds physical host elements. In plain HTML, markup controls its own presentation: you write `<div id="root"></div>` into an HTML file, open the file, and the browser parses the tags directly without any JavaScript running. When you write React components, that direct connection is severed: component functions produce lightweight JavaScript objects in memory, and the browser never sees them until an external renderer translates them. The law of React architecture is simple: React core cannot touch the DOM, and only a dedicated renderer like `react-dom` can translate components into physical browser nodes. ◼ Introduces the separation of concerns between React core and platform renderers; terms introduced: **renderer**, **react-dom**, **UI descriptor**, **host environment**.
- [p] ★ {preknowledge:} In plain JavaScript DOM scripting, you query an existing element and insert text or elements using imperative methods like `document.getElementById` and `element.appendChild` (see Lecture 1). In React, the bridge between component functions and browser DOM nodes lives inside a dedicated client package called `react-dom/client`. {problem:} Developers often look inside the `react` package for mounting functions, but `react` contains only component primitives, state hooks, and element factories. ◼ Pedagogical qualification: Clarifies the package boundary between react and react-dom/client.
- [p] ★ {preknowledge:} To bridge the gap, the package `react-dom/client` exports an entry function called `createRoot`. {old solution:} Developers historically relied on manual DOM insertion or legacy mounting APIs that tightly coupled component evaluation to physical DOM mutation. {new solution:} In modern React, you pass an existing HTML container node from the page to `createRoot`, which initializes an in-memory root instance. ◼ Pedagogical qualification: Prepares the code snippet demonstrating the two-step mounting bridge.
- [code] Minimal createRoot bridge:
```jsx title="Mounting Bridge"
import { createRoot } from 'react-dom/client';
import NewsApp from './NewsApp.jsx';
const domNode = document.getElementById('root'); // 1. Finds physical **CONTAINER** in index.html
const root = createRoot(domNode); // 2. Creates concurrent **ROOT** instance in memory
root.render(<NewsApp />); // 3. Mounts component tree into **DOM**
```
◼ **The what-this-introduces list:** 1. `import { createRoot } from 'react-dom/client'`: the official React 19 client renderer entry function. 2. `document.getElementById('root')`: standard browser DOM lookup retrieving the host container. 3. `createRoot(domNode)`: factory call creating the root instance. 4. `root.render(...)`: method executing initial component mounting.
- [p] Post-code deconstruction of the mounting bridge: The call `document.getElementById('root')` queries the physical browser document for a pre-existing container element. Line 4 calls `createRoot(domNode)`, which takes that physical DOM node and creates a specialized root manager object in memory called a `ReactDOMRoot`. Line 5 calls `root.render(<NewsApp />)`, passing the root component wrapped in JSX. This single line triggers the React engine: it evaluates `NewsApp()`, receives its returned JSX element tree, compares that virtual tree against the empty container, and creates and inserts the real HTML elements into the browser page. ◼ Educational objective: walk through the three distinct lines of mounting code in strict execution order; terms introduced: **createRoot**, **ReactDOMRoot**, **root.render**.

### The Two-Step API: createRoot versus Legacy ReactDOM.render
- [p] ◇ {preknowledge:} In older tutorials and legacy React codebases, developers mounted applications using a single function called `ReactDOM.render`. What is the **two-step mounting API**? In React 18 and 19, the React team replaced the single-step mounting function with a two-step sequence: first `createRoot(domNode)`, then `root.render(<App />)`. In plain JavaScript, you are used to single-action operations: you call `fetch(url)` or `element.appendChild(node)` in one step. Legacy React followed that same habit: `ReactDOM.render(<App />, domNode)` took the component and the container together in a single call. However, that single call suffered from a severe limitation: it was strictly synchronous, locking the browser main thread during large renders, and it offered no mechanism to update the root without re-checking the container. The law of the two-step API is clear: you cannot render a component tree without first creating a root instance, and once created, that root instance owns the container forever. ◼ Defines the two-step mounting API by contrasting legacy single-step execution with modern root management; terms introduced: **two-step mounting API**, **concurrent root**, **ReactDOM.render**.
- [p] ★ {preknowledge:} In legacy React 17, `ReactDOM.render` executed synchronously: when called, it traversed the entire component tree and pushed changes to the DOM in a single unbroken block of CPU time. {problem:} On complex web pages with thousands of elements, synchronous mounting froze user typing, blocked button clicks, and dropped animation frames during initial page load. ◼ Explains the synchronous blocking bottleneck of legacy ReactDOM.render.
- [p] ★ {preknowledge:} Modern React 19 relies on concurrent rendering, where the engine can pause low-priority background work to keep the browser responsive to immediate user interactions. {old solution:} Legacy code passed the component and DOM node together in `ReactDOM.render(<App />, container)`. {new solution:} Modern code splits this responsibility: `createRoot(domNode)` initializes the concurrent scheduler, priority lanes, and container-level event listeners in memory, and `root.render(<App />)` schedules the actual component rendering. ◼ Contrasts legacy and modern API mechanics.
- [code] Legacy vs Modern Mounting Contrast:
```jsx title="Mounting Paradigm Contrast"
ReactDOM.render(<NewsApp />, document.getElementById('root')); // **WRONG:** Legacy synchronous mount blocks **MAIN** thread
const root = createRoot(document.getElementById('root')); // **RIGHT:** 1. Modern root initializes **CONCURRENT** scheduler
root.render(<NewsApp />); // 2. Schedules interruptible **RENDER** pass
```
◼ **The what-this-introduces list:** 1. `ReactDOM.render`: legacy single-step API deprecated in modern React. 2. `createRoot`: modern root factory initializing concurrent capabilities. 3. `root.render`: instance method scheduling non-blocking render passes.

  the friction it clears: why calling createRoot once and then render is superior to a single function.
  Scene & Repetition: Imagine you are connecting your television to a streaming service.   Key Terms (Bold): **physical DOM**, **concurrent root**, **createRoot**, **root.render**.
  Resolution: The two-step API separates the one-time cost of container registration and event delegation from the recurring task of component tree rendering.

### What createRoot Actually Returns: Lifecycle and Memory Governance
- [p] ◇ {preknowledge:} When you call a factory function in JavaScript, you expect it to return an object with specific properties and methods. {problem:} Developers frequently treat `createRoot(container)` as a throwaway helper, chaining `.render()` immediately without understanding what object was created in memory. What is a **ReactDOMRoot**? A **ReactDOMRoot** is an in-memory controller object returned by `createRoot` that manages the lifecycle of a mounted React tree inside a specific DOM container. In plain JavaScript, if you create an object or insert an element, the browser leaves it in memory until the page unloads or you manually call `remove()`. The law of the root object is absolute: the `ReactDOMRoot` is the sole authority over the container's interior, and calling its methods is the only legitimate way to update or destroy the mounted tree. ◼ Introduces the ReactDOMRoot return object and its identity; terms introduced: **ReactDOMRoot**, **root.unmount**, **root.render**.
- [p] ★ {preknowledge:} The object returned by `createRoot` exposes two primary methods: `render` and `unmount`. Line 6 of our entry file invoked `root.render(<NewsApp />)`. The second method, `root.unmount()`, is responsible for destroying the mounted application. {problem:} In single-page applications where React is embedded inside a legacy site, a tab switcher, or a micro-frontend shell, simply deleting the container div leaves event listeners and fiber trees leaking in memory. ◼ Explains the necessity of root.unmount in dynamic environments.
- [p] ★ {preknowledge:} Calling `root.unmount()` triggers a complete, coordinated teardown of the application tree. React runs all cleanup effects, cancels pending transitions, removes root event listeners from the container, and clears the container's inner HTML. {old solution:} Developers previously removed DOM nodes manually with `container.innerHTML = ''`, which caused memory leaks because internal React references remained intact. {new solution:} Developers now call `root.unmount()` to release all internal references cleanly. ◼ Contrasts manual DOM clearing with root.unmount.
- [code] Lifecycle unmounting pattern:
```jsx title="Lifecycle Teardown"
const root = createRoot(document.getElementById('ticker-widget'));
root.render(<NewsApp />); // 1. Mounts breaking news widget into **DOM**
function teardownWidget() {
  root.unmount(); // 2. Cleans up fiber tree and removes all event **LISTENERS**
}
```
◼ **The what-this-introduces list:** 1. `root.unmount()`: lifecycle teardown method. 2. `teardownWidget`: cleanup handler executing graceful teardown.
- [grounding] the opening question: What happens if you remove a container without unmounting?
  the friction it clears: why deleting the container DOM node leaves silent memory leaks.
  Scene & Repetition: Imagine you build a live breaking news widget embedded inside a legacy newsroom management dashboard. When an editor clicks to close the widget, the legacy dashboard runs `container.remove()` to delete the HTML element from the screen. The widget disappears visually, so the developer assumes everything is cleaned up. But behind the scenes, a disaster is unfolding. React still holds the entire component tree, its active timers, and its root event listeners in computer memory. Every single time the editor opens and closes the widget, another ghost tree is abandoned in memory. This is a severe **memory leak**. To properly destroy a React application, you must never simply delete the container. You must call **root.unmount()**. This method destroys the **fiber tree**, executes all cleanup routines, detaches all event listeners, and releases memory completely.
  Key Terms (Bold): **memory leak**, **root.unmount**, **fiber tree**, **root container**.
  Resolution: Calling root.unmount destroys all internal references, runs effect cleanups, and detaches event listeners before the DOM node is removed.

Highlight that calling `unmount` is vital in micro-frontends, testing harnesses, and embedded widgets to prevent memory leaks and dangling event listeners. ◼ Senior interview positioning tip.

### Container Ownership, Clearing, and Server-Side Hydration
- [p] ◇ {preknowledge:} When you look at an HTML file like `index.html`, you might be tempted to put initial markup inside the root div, such as `<div id="root"><h1>Loading news...</h1></div>`. What is **container clearing**? In React client-side rendering, `createRoot` assumes exclusive, dictatorial governance over the target DOM element. In plain HTML, appending an element leaves existing children untouched: calling `container.appendChild(node)` places the new node at the bottom of the list. In React, the default behavior of `root.render` is completely different: during initial mount, React wipes all pre-existing HTML nodes inside the container before inserting the component tree. The law of container ownership states: `createRoot` never shares a DOM container with static HTML, and any pre-existing children inside the container will be cleared upon initial render. ◼ Defines container ownership and clearing; terms introduced: **container clearing**, **exclusive governance**, **hydrateRoot**.
- [p] ★ {preknowledge:} If your application uses server-side rendering (SSR), the web server sends fully constructed HTML markup inside `<div id="root">` so the reader sees text immediately (see Lecture 2). {problem:} If you invoke `createRoot` on a container that already contains server-rendered HTML, React wipes that HTML and rebuilds the entire DOM from scratch. This causes a jarring visual flicker and throws a hydration mismatch warning in the console. ◼ Identifies the pitfall of using createRoot on server-rendered HTML.
- [p] ★ {preknowledge:} To preserve server-rendered HTML and attach event listeners without destroying the DOM, React provides a specialized companion function in `react-dom/client` called `hydrateRoot`. {old solution:} Developers mistakenly used `createRoot` and suffered layout shifts and double-rendering. {new solution:} Developers use `hydrateRoot(domNode, <App />)` for server-rendered HTML, and reserve `createRoot` strictly for pure client-side applications. ◼ Contrasts createRoot and hydrateRoot.
- [code] Hydration vs Client Mount Contrast:
```jsx title="Client Mount vs Hydration"
const root = createRoot(document.getElementById('root'));
root.render(<NewsApp />); // 1. Client mount: clears container and builds **TREE**
import { hydrateRoot } from 'react-dom/client';
hydrateRoot(document.getElementById('root'), <NewsApp />); // 2. SSR: preserves server markup and **HYDRATES**
```
◼ **The what-this-introduces list:** 1. `createRoot`: pure client-side root creation that clears the container. 2. `hydrateRoot`: specialized entry point that preserves pre-rendered server HTML and attaches event handlers.

### Glossary
- [definition] **createRoot**: A factory method from react-dom/client that initializes a ReactDOMRoot instance managing a physical DOM container with concurrent rendering capabilities.
- [definition] **ReactDOMRoot**: The in-memory controller object returned by createRoot that provides render and unmount methods to manage the application lifecycle.
- [definition] **root.render**: The method on a ReactDOMRoot instance that evaluates a React element tree and commits the resulting HTML nodes into the DOM container.
- [definition] **root.unmount**: The method on a ReactDOMRoot instance that destroys the mounted component tree, runs cleanup effects, and detaches all container event listeners.
- [definition] **hydrateRoot**: The companion API to createRoot used in server-side rendered applications to attach event listeners to pre-rendered HTML without re-creating DOM nodes.
- [definition] **Entry Point**: The primary JavaScript module such as main.jsx where browser DOM access occurs and the application root is instantiated.

The **createRoot API** establishes a two-step bridge between React component blueprints and the physical browser DOM.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Step 1 acquires the HTML container and initializes the concurrent scheduler in memory.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Step 2 schedules component evaluation and commits real HTML nodes into the page.
- [numbered-review-point] 2. The **ReactDOMRoot instance** returned by `createRoot` provides full lifecycle control over the mounted application.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Calling `root.render()` updates the component tree without re-registering root event listeners.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Calling `root.unmount()` destroys the fiber tree, cleans up effects, and prevents memory leaks.
- [numbered-review-point] 3. Client mounting assumes **exclusive container governance** over the target DOM element.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Initial mounting clears all pre-existing HTML nodes inside the target container div.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Applications with pre-rendered server HTML must use `hydrateRoot` instead of `createRoot`.
- [never-rule] ➔ NEVER call `document.getElementById` or perform manual DOM queries inside ordinary React components.
- [always-rule] ➔ ALWAYS call `root.unmount()` when destroying a mounted React application in dynamic multi-page or micro-frontend architectures.
- [if-then-rule] ➔ IF the HTML container already contains server-rendered markup THEN **use `hydrateRoot` instead of `createRoot`**.
- [do-this-header] **DO THIS:** Isolate DOM access to main.jsx using createRoot and keep components purely declarative.
- [do-this-code] Proper mounting in main.jsx:
```jsx right title="main.jsx"
import { createRoot } from 'react-dom/client';
import NewsApp from './NewsApp.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Root element missing');
const root = createRoot(container);
root.render(<NewsApp />);
```
- [do-not-do-this-header] **DO NOT DO THIS:** Never invoke deprecated ReactDOM.render or perform manual DOM mutations inside components.
- [do-not-do-this-code] Bad mounting anti-pattern:
```jsx wrong title="Deprecated Mounting Pattern"
import ReactDOM from 'react-dom';
import NewsApp from './NewsApp.jsx';
ReactDOM.render(<NewsApp />, document.getElementById('root'));
```
- [comparison-table] Architectural comparison table:
| | **LEGACY REACTDOM.RENDER**<br>(React 17 and earlier) | **MODERN CREATEROOT**<br>(React 18 and 19) |
| ---: | :--- | :--- |
| **API Architecture** | Single-step call:<br>`ReactDOM.render`<br>`(el, node)` | Two-step sequence:<br>`createRoot(node)`<br>`root.render(el)` |
| **Rendering Mode** | Synchronous execution;<br>blocks browser main thread | Concurrent rendering;<br>interruptible background work |
| **Root Re-renders** | Must pass container node<br>again on every update | Call `root.render()` on<br>existing root instance |
| **Lifecycle Cleanup** | Imperative cleanup:<br>`unmountComponent`<br>`AtNode` | Native method on root:<br>`root.unmount()` |
| **Container Management** | Overwrites container without<br>concurrent priority lanes | Exclusive governance with<br>priority scheduling lanes |
