### Why Single-File Monoliths Break Down
- [p] ◇ {preknowledge:} In earlier lessons, we learned that a React component is a JavaScript function that returns JSX markup (see Lecture 3 and Lecture 4). When starting a new project or building a small prototype, developers often define multiple component functions in a single file like `App.jsx`. {problem:} As features multiply, keeping the masthead, navigation, article cards, sidebar, and layout container in one file turns into an unwieldy thousand-line monolith. What is a **module**? In modern JavaScript and React, a **module** is an isolated file whose top-level variables and functions remain private unless explicitly exported. In plain HTML scripts, any variable or function declared in a `<script>` tag pollutes the global `window` scope, creating silent name collisions and making code impossible to refactor safely. In modern React development, ES modules replace that global chaos with strict file-level isolation: a component defined in `SiteHeader.jsx` is completely invisible to `NewsPortal.jsx` until it is exported. The law of modular architecture is absolute: a file can only consume what another file explicitly exports, and only through the precise contract established by the author. ◼ Defines the module boundary and contrasts global script pollution with ES module encapsulation; terms introduced: **module**, **export**, **import**, **module encapsulation**.
- [p] ★ {preknowledge:} In a monolithic file, all functions share the same file scope, so one component can accidentally read helper variables or internal utilities belonging to a sibling component. {old solution:} Early web applications concatenated multiple scripts into a single global bundle or kept hundreds of lines in one file to avoid managing import paths. {new solution:} In modern React, you decompose the monolith by moving each component into its own dedicated `.jsx` file, exposing public components through exports and connecting them through imports. ◼ Clarifies the shift from monolithic files to decomposed component modules.
- [grounding] the opening question: Why can separate files not see each other?
  the friction it clears: why splitting files requires explicit exports instead of automatic sharing.
  Scene & Repetition: Imagine a library filled with books on open shelves. If every book had its pages torn out and scattered across the tables, text from one story would mix into another. You would have no way to keep stories separate. Instead, every book has a thick cover that keeps its pages locked inside. A JavaScript file is a book with a locked cover. Variables declared inside that file stay strictly inside its covers. If you want another file to read a function, you must stamp that function with an **export** badge. If another file wants to use it, that file must submit an **import** request. This is **module encapsulation**: it ensures no file can accidentally overwrite or corrupt the code inside another file.
  Key Terms (Bold): **module encapsulation**, **export**, **import**.
  Resolution: Explicit exports and imports create an isolated module boundary that prevents naming collisions and enables clear component contracts.

### Default Exports versus Named Exports: The Import Contract
- [p] ◇ {preknowledge:} Once you split a component into its own file, you must decide how to expose it to the rest of the application. JavaScript modules provide two distinct export mechanisms: **default exports** and **named exports**. What is a **default export**? A **default export** is a module mechanism that designates one primary value or component per file using the `export default` declaration. In plain JavaScript, a file with no exports keeps everything private. When you add `export default function SiteHeader() { ... }`, you declare that `SiteHeader` is the official, primary export of that file. When another file imports it, you write `import SiteHeader from './SiteHeader.jsx'` without curly braces. The law of default exports states: a file may contain only one default export, and the importing file can assign any local variable name to it without curly braces. ◼ Defines default export with its default sentence and law sentence; terms introduced: **default export**, **default import**.
- [p] ◇ {preknowledge:} In many cases, a single file naturally contains multiple related components or helper functions that belong together, such as an `ArticleCard` and an `ArticleList`. What is a **named export**? A **named export** is a module mechanism that allows a file to export multiple distinct functions, components, or constants by placing the `export` keyword directly before their declarations. In plain JavaScript, you would have to bundle multiple functions into a single object literal to export them. With named exports, you write `export function ArticleCard() { ... }` and `export function ArticleList() { ... }` as individual declarations. The importing file must use curly braces `{ ArticleCard, ArticleList }`, matching the exact identifiers declared in the source file. The law of named exports states: a file may have as many named exports as needed, and the importing file must use curly braces with names matching the export record unless explicitly aliased. ◼ Defines named export with its default sentence and law sentence; terms introduced: **named export**, **named import**, **curly braces**.
- [code] Default vs Named syntax contrast:
```jsx title="Export Syntax Contract"
// Default Export (One per file, primary component):
export default function SiteHeader() {
  return <header>The National Times</header>;
}
// Named Exports (Multiple per file, cohesive helpers):
export function ArticleCard({ title }) {
  return <article>{title}</article>;
}
export function ArticleList() {
  return <section><ArticleCard title="News" /></section>;
}
```
◼ **The what-this-introduces list:** 1. `export default function SiteHeader`: single primary export declaration. 2. `export function ArticleCard`: first named export declaration in shared module. 3. `export function ArticleList`: second named export declaration in shared module.
- [p] ★ Deconstruction of the export syntax contract: Look at line 2: `export default function SiteHeader()`. The keyword `default` tells the JavaScript module system that this component is the main export of the file. Now look at lines 6 and 9: `export function ArticleCard` and `export function ArticleList`. Here, the keyword `default` is absent. Each function is registered under its specific identifier in the module's export table. A file can have only one default export, but it can declare dozens of named exports. ◼ Explains syntax difference between export default and export function.
- [p] ★ {preknowledge:} When you import components into another file, the syntax you write must match the export contract of the source file. {problem:} The most frequent bug encountered by React developers is wrapping a default export in curly braces, such as `import { SiteHeader } from './SiteHeader.jsx'`. When JavaScript evaluates that import, it searches the module's named export dictionary for a key called `SiteHeader`. Because `SiteHeader` was exported as the default, no named key exists. The variable `SiteHeader` evaluates to `undefined`. When React attempts to render `<SiteHeader />`, it evaluates `<undefined />`, halts execution, and throws a fatal TypeError: "Element type is invalid: expected a string or a class/function but got: undefined." ◼ Explains the mechanics of the curly brace import trap and the resulting runtime undefined crash; terms introduced: **undefined import trap**, **runtime crash**.
- [code] Import Syntax Contrast:
```jsx title="Import Syntax Contrast"
// **WRONG:** Wrapping a default export in curly braces causes undefined:
import { SiteHeader } from './SiteHeader.jsx'; // Evaluates to **UNDEFINED** at runtime
// **RIGHT:** Default export imported without curly braces:
import SiteHeader from './SiteHeader.jsx'; // Grabs **DEFAULT** export cleanly
// **RIGHT:** Named exports imported with exact matching curly braces:
import { ArticleList } from './ArticleComponents.jsx'; // Matches **NAMED** export key
```
◼ **The what-this-introduces list:** 1. `import { SiteHeader }`: erroneous named lookup on a default export. 2. `import SiteHeader`: valid default import without curly braces. 3. `import { ArticleList }`: valid named import with matching curly braces.
- [p] ★ Post-code deconstruction of the import contrast: Notice the contrast in line 2: wrapping `SiteHeader` in curly braces attempts a named property lookup on a module that only declared a default export. The lookup fails silently in JavaScript, assigning `undefined` to the local identifier. The error only detonates when React attempts to evaluate the element in JSX. In line 4, omitting the curly braces correctly accesses `module.default`. In line 6, the curly braces around `ArticleList` match the named export declared in `ArticleComponents.jsx`, successfully loading the component. ◼ Deconstructs the import syntax comparison.
- [grounding] the opening question: What is the curly brace import trap?
  the friction it clears: why { SiteHeader } causes an undefined crash when SiteHeader is a default export.
  Scene & Repetition: Imagine a postal mailroom. A **default export** places a package in the open mailbox right on your front porch. When you walk outside to pick it up, you pick it up directly: you do not need a special mailbox key. A **named export** places a package inside a numbered private locker at the post office. To retrieve it, you must present the exact locker key inside **curly braces** `{ ArticleList }`. If you bring a locker key `{ SiteHeader }` to a mailbox on the porch, you are trying to unlock a locker that does not exist. You open the locker door and find absolutely nothing inside: `undefined`. When you hand that empty `undefined` box to React to display on screen, the entire page goes blank with an element type error. To receive a default export, leave the curly braces off: `import SiteHeader from './SiteHeader.jsx'`.
  Key Terms (Bold): **default export**, **named export**, **curly braces**, **undefined**.
  Resolution: Default exports map to the module's default property and require bare import syntax, while named exports map to named dictionary keys and require curly braces.
- [tip] To impress the interviewer: When asked how default and named imports differ, do not just recite the syntax. Explain the module namespace object: default exports assign to `module.default`, whereas named exports assign to named properties on the module object. Point out that importing a default export with curly braces evaluates to `undefined`, which is the primary cause of React's notorious "Element type is invalid: expected a string or a class/function but got: undefined" runtime error. ◼ Senior interview positioning on module namespace objects and runtime undefined crashes.

### Renaming Imports and Combining Export Types
- [p] ◇ What happens when two different files export a component with the same name? For example, both `ArticleComponents.jsx` and an administrative module might export a component called `Badge`. If you import both into `NewsPortal.jsx`, JavaScript encounters a syntax error because two variables share the same identifier in the same file scope. ◼ Frames the problem of module name collisions.
- [p] ★ To resolve naming collisions, JavaScript provides the `as` keyword to create an **import alias**. When importing a named export, you write `import { Badge as ArticleBadge } from './ArticleComponents.jsx'`. From that line down, your file refers to the component as `ArticleBadge`. For default exports, you do not even need the `as` keyword: because a default export has no mandatory name, you can write `import Masthead from './SiteHeader.jsx'` directly. ◼ Explains aliasing and renaming imports; terms introduced: **import alias**, **as keyword**.
- [p] ★ A single file can also export both a default component and named helper components or constants. For example, a design system file might default-export a `Button` component while providing named exports for `ButtonSizes` and `ButtonVariants`. To consume both in a single statement, write the default import first outside curly braces, followed by a comma, then the named imports inside curly braces: `import Button, { ButtonSizes } from './Button.jsx'`. ◼ Explains combined default and named imports.
- [code] Combined and aliased imports:
```jsx title="Aliasing and Combined Imports"
// Renaming a named export to avoid collision:
import { ArticleCard as FeedCard } from './ArticleComponents.jsx';
// Combining default and named imports in one statement:
import SiteHeader, { HeaderNotice } from './SiteHeader.jsx';
export default function DeskView() {
  return (
    <section>
      <SiteHeader edition="Morning" />
      <HeaderNotice text="Press release embargo lifted" />
      <FeedCard title="Mayor Approves Green Transit Fleet" />
    </section>
  );
}
```
◼ **The what-this-introduces list:** 1. `as FeedCard`: named import aliased to local identifier. 2. `SiteHeader, { HeaderNotice }`: combined default and named import syntax. 3. `<FeedCard ... />`: rendering the aliased component in JSX.
- [grounding] the opening question: When do import names collide across files?
  the friction it clears: how to handle two components from different files that share the exact same name.
  Scene & Repetition: Imagine two reporters both author a component named `Card`. One reporter builds a `Card` for breaking news, and another reporter builds a `Card` for weather updates. If you try to import both into the same file with `import { Card }`, JavaScript refuses to run. The two names crash into each other in the same room. Which `Card` do you mean? To solve this collision, you use the **`as` keyword** to create an **import alias**: `import { Card as NewsCard } from './News.jsx'` and `import { Card as WeatherCard } from './Weather.jsx'`. By giving each import an alias, you give each component its own clear, unambiguous name in your file.
  Key Terms (Bold): **as keyword**, **import alias**, **name collision**.
  Resolution: Import aliasing with as resolves name collisions by mapping external exports to unique local identifiers.

### Glossary
- [definition] **Default Export**: A module export declared with export default that designates a single primary value for the file, imported without curly braces.
- [definition] **Named Export**: A module export declared with export that exports a specific function or variable by name, imported using matching curly braces.
- [definition] **ES Modules**: The official ECMAScript standard for JavaScript code modularity, providing file-level scope with explicit import and export statements.
- [definition] **Tree Shaking**: An optimization performed by modern bundlers that analyzes ES module imports and eliminates unused named exports from the production bundle.
- [definition] **Module Encapsulation**: The boundary guarantee that variables, functions, and classes defined inside a module are private unless explicitly exported.
- [definition] **Import Alias**: The syntax using the as keyword that renames an imported named export to avoid naming collisions or clarify its local role.
