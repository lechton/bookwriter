### Why We Split Components Across Files
- [p] ◇ {preknowledge:} In earlier lessons, we learned how to write React components as JavaScript functions that return JSX markup (see Lectures 3, 4, and 5). You can declare five or ten component functions in a single `App.jsx` file, and React will render them without complaint. {problem:} As your application grows, keeping multiple components in one file creates an unmaintainable monolith where styling, logic, and markup tangle together. ◼ Pedagogical qualification: Establish the need for file splitting; terms introduced: **module boundaries**, **single responsibility**, **component file**.
- [p] ★ {preknowledge:} In plain browser scripts without module loaders, any function declared in a script tag enters the global scope (`window`). If two scripts declare a function with the same name, the second silently overwrites the first. In modern web development, Vite and React rely on ECMAScript Modules (ES Modules). Every JavaScript or JSX file is an isolated module: nothing declared inside is accessible from the outside world unless you explicitly export it. ◼ Pedagogical qualification: Connect plain global script behavior to ES Module isolation; terms introduced: **ES Modules**, **module scope**, **export**.
- [p] {old solution:} In legacy JavaScript applications, developers had to concatenate scripts in a specific order in `index.html` or attach components to a shared global namespace object like `window.App.Components = {}`. This pattern caused ordering bugs and naming collisions. ◼ Educational objective: Contrast ES Module exports with legacy global namespace patterns.
- [code] Legacy global namespace versus modern ES module exports:
```jsx title="Module Organization Contrast"
// Legacy Global Namespace (Error-Prone):
window.NewsApp = { Header: function Header() { /* ... */ } };
// Modern ES Module Architecture (Isolated & Type-Safe):
// In SiteHeader.jsx:
export default function SiteHeader() { return <header>...</header>; }
// In NewsPortal.jsx:
import SiteHeader from './SiteHeader.jsx'; // Explicit dependency link
```
- [grounding] Leading Question: Why not keep all components in one file?
  Confusion Point: Why should a developer spend time creating separate files for small components?
  Scene & Repetition: Imagine three journalists and two engineers are working on The National Times homepage at 4:00 PM before deadline. Elena is updating the breaking news banner, Marcus is redesigning the article card, and David is fixing a typo in the footer. If all three components live in `App.jsx`, every person is editing the exact same file. When they push their changes to Git, they hit massive merge conflicts, overwriting each other's code. By splitting each component into its own file ending in `.jsx`, each developer owns an isolated file. Git merges become effortless, components become reusable across pages, and the codebase stays clean.
  Key Terms (Bold): `**component file**`, `**module boundaries**`, `**merge conflicts**`, `**single responsibility**`.
  Resolution: Splitting components into dedicated files isolates changes, prevents merge conflicts, and makes components reusable across the application.

### Default Exports versus Named Exports
- [p] ◇ {preknowledge:} When you split components into separate files, you need a mechanism to share them: you export a component from its home file and import it where it is needed. JavaScript provides two distinct ways to export code: default exports and named exports. {problem:} Beginners often mix up the syntax, putting curly braces where they do not belong and triggering baffling runtime errors. ◼ Pedagogical qualification: Introduce the dual export mechanisms; terms introduced: **default export**, **named export**, **curly brace trap**.
- [p] ★ {preknowledge:} A **default export** designates the primary value or component that a file provides. A file can have at most one default export, declared with the keywords `export default`. When importing a default export, you do not use curly braces: `import SiteHeader from './SiteHeader.jsx'`. Because it is the default value of that module, the importing file can choose any local identifier for it (for example `import Header from './SiteHeader.jsx'`). {problem:} If you attempt to export two default values from the same file, the JavaScript compiler throws a syntax error. ◼ Pedagogical qualification: Deconstruct default export mechanics and naming flexibility.
- [p] ★ {preknowledge:} A **named export** allows a single file to export multiple functions, components, or constants, each identified by its specific name. You declare named exports by prefixing declarations with `export` (like `export function ArticleCard()`) or using an export list: `export { ArticleCard, ArticlePill }`. When importing named exports, you must wrap their identifiers in curly braces: `import { ArticleCard, ArticlePill } from './ArticleComponents.jsx'`. The imported names must match the exported names exactly, unless you rename them explicitly using the `as` keyword: `import { ArticleCard as Card } from './ArticleComponents.jsx'`. ◼ Pedagogical qualification: Deconstruct named export mechanics and the `as` alias keyword.
- [code] Default and named import syntax contrast:
```jsx title="Export and Import Patterns"
// 1. Default Export (One per file, imported without curly braces):
import SiteHeader from './SiteHeader.jsx'; // Local name can vary
// 2. Named Exports (Multiple per file, imported with curly braces):
import { ArticleCard, ArticlePill } from './ArticleComponents.jsx';
// 3. Named Export with Renaming Alias:
import { ArticleCard as FeaturedStory } from './ArticleComponents.jsx';
```
- [p] ★ {preknowledge:} What is the **curly brace trap**? This is the single most common import bug in React development. If a component is exported with `export default function SiteHeader()`, and you import it with curly braces: `import { SiteHeader } from './SiteHeader.jsx'`, what happens? The browser or bundler looks inside the module's export dictionary for a named property called `SiteHeader`. Because `SiteHeader` was exported as the default, the named property does not exist: the import resolves to `undefined`. When React tries to render `<SiteHeader />`, it evaluates `<undefined />` and crashes with: `Element type is invalid: expected a string (for built-in components) or a class/function (for composite components) but got: undefined`. ◼ Pedagogical qualification: Detail the exact runtime failure of the curly brace trap; terms introduced: **undefined component**, **element type invalid error**.
- [grounding] Leading Question: Why does importing a component yield undefined?
  Confusion Point: Why does `import { SiteHeader }` fail when `export default function SiteHeader` is right there in the file?
  Scene & Repetition: Imagine you order a package from a delivery service addressed to "The Resident" (the default recipient). When the courier arrives, they ask: "Is there a package specifically labeled for SiteHeader?" The courier checks the manifest, sees only "The Resident", and declares: "Nothing found under that specific name: result is undefined." In JavaScript, `export default` puts the component in the box labeled `default`. Writing `import SiteHeader` (without curly braces) reaches into the box and grabs the default item. Writing `import { SiteHeader }` (with curly braces) tells JavaScript to look for a specific named slot called `SiteHeader`. That slot is empty, so JavaScript hands you `undefined`. When React attempts to render `undefined`, your app crashes immediately.
  Key Terms (Bold): `**default export**`, `**named export**`, `**curly brace trap**`, `**undefined**`.
  Resolution: Curly braces specify a named property lookup; importing a default export with curly braces looks for a non-existent key, resulting in `undefined` and crashing React.

### Step 1: First, we construct the parent container NewsPortal.jsx
- [p] ★ {preknowledge:} The parent container coordinates the page layout and imports child components from separate files. {problem:} The file must use default import syntax for `SiteHeader` and named import syntax for `ArticleList`. ◼ Pedagogical qualification: Construct parent container demonstrating both import types.
- [code] Parent container NewsPortal.jsx:
```jsx title="NewsPortal.jsx"
import SiteHeader from './components/SiteHeader.jsx';
import { ArticleList } from './components/ArticleComponents.jsx';
export default function NewsPortal() {
  return (
    <div className="news-portal">
      <SiteHeader edition="Morning Print" /> // Default import child
      <ArticleList desk="International" /> // Named import child
    </div>
  );
}
```
- [p] ★ Step 1 establishes the contracts: Look at lines 1 and 2. Notice that `SiteHeader` is imported without curly braces because it is a default export, while `ArticleList` is enclosed in `{ ArticleList }` because it is a named export. Now look at lines 6 and 7: `<SiteHeader edition="Morning Print" />` and `<ArticleList desk="International" />`. We have not written either child component yet. But right here in the parent, we establish their contracts and layout relationship. We will build `SiteHeader` next in step 2. ◼ Pedagogical qualification: Deconstruct parent imports, contracts, and forward references.

### Step 2: Next, we build the default export child SiteHeader.jsx
- [p] ★ {preknowledge:} Step 1 established the contract: `SiteHeader` receives an `edition` prop and renders the masthead. {problem:} The file must provide a clean default export that matches the import in Step 1. ◼ Pedagogical qualification: Fulfill default export component contract.
- [code] Default export child SiteHeader.jsx:
```jsx title="SiteHeader.jsx"
export default function SiteHeader({ edition }) {
  return (
    <header className="site-header">
      <h1 className="masthead-title">The National Times</h1>
      <span className="edition-badge">{edition}</span> // Status badge in **HEADER**
    </header>
  );
}
```
- [p] ★ Step 2 fulfills the default export: Look at line 1: `export default function SiteHeader({ edition })`. The keyword `default` tells JavaScript that this function is the primary export of this file. Notice that any consuming file can import this component using any name it wants. If you ever put curly braces around `SiteHeader` when importing from this file, the import will resolve to `undefined` and crash the render pass. ◼ Pedagogical qualification: Deconstruct `export default` syntax and reiterate the curly brace trap consequence.
- [p] What would happen if `SiteHeader` also declared and exported article feed components directly? If you put article rendering logic and data fetching inside `SiteHeader`, the header would be trapped managing article lists and layout feeds. The masthead would re-render whenever articles changed. By separating them into their own files, `SiteHeader` owns zero article state and zero list logic. If tomorrow you redesign the masthead, you touch zero lines of article code. ◼ Pedagogical qualification: Apply the Negative Counterfactual Law to justify file separation.

### Step 3: Then, we declare the named exports in ArticleComponents.jsx
- [p] ★ {preknowledge:} Step 1 also established a contract for `ArticleList`. Now we build `ArticleComponents.jsx`, which provides both `ArticleList` and `ArticleCard` as named exports from a single module. {problem:} The file must demonstrate how multiple related components can be exported from a single file using named exports. ◼ Pedagogical qualification: Implement named exports for related components.
- [code] Named exports in ArticleComponents.jsx:
```jsx title="ArticleComponents.jsx"
export function ArticleCard({ title, category }) {
  return <article className="article-card"><span className="pill">{category}</span><h3>{title}</h3></article>;
}
export function ArticleList({ desk }) {
  return (
    <section className="article-list">
      <ArticleCard title="Peace Treaty" category={desk} /> // Named component in **FEED**
    </section>
  );
}
```
- [p] ★ Step 3 demonstrates named exports: Look at lines 1 and 4: `export function ArticleCard` and `export function ArticleList`. Neither declaration uses the `default` keyword. Because both functions are named exports, consumers must use curly braces: `import { ArticleList } from './ArticleComponents.jsx'`. If a consuming file only needs `ArticleCard`, it can import `ArticleCard` alone without importing `ArticleList`, enabling bundlers to optimize the build. ◼ Pedagogical qualification: Deconstruct named exports, selective importing, and tree shaking benefits.

### Step 4: Finally, we seal the application entry point main.jsx
- [p] ★ {preknowledge:} In Step 1 we built `NewsPortal.jsx`. In Steps 2 and 3 we built its children. Now we inspect `main.jsx`, which imports `NewsPortal` as a default export and mounts it to the DOM using `createRoot` (as learned in Lecture 6). {problem:} The entry point must connect the modular component tree to the physical browser page. ◼ Pedagogical qualification: Seal architecture at application entry point.
- [code] Entry point main.jsx:
```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import NewsPortal from './NewsPortal.jsx';
const container = document.getElementById('root');
if (!container) throw new Error('Target container #root not found');
const root = createRoot(container); // Initializes root in **MEMORY**
root.render(<NewsPortal />); // Mounts root component into **DOM**
```
- [p] ★ Step 4 seals the architecture: Look at line 2: `import NewsPortal from './NewsPortal.jsx'`. `NewsPortal` is imported as a default export without curly braces. When `root.render(<NewsPortal />)` executes on line 6, React mounts `NewsPortal`, which in turn evaluates `SiteHeader`, `ArticleList`, and `ArticleCard`. The browser bundles these separate files into an optimized module graph, keeping the source code clean and modular on disk. ◼ Pedagogical qualification: Trace complete application execution from entry point through module graph.

- [grounding] Leading Question: Can you mix default and named exports in one file?
  Confusion Point: Can a single `.jsx` file have both a default export and named exports at the same time?
  Scene & Repetition: Imagine you are writing a comprehensive UI kit file for buttons. You have a main `Button` component that almost every screen uses. But you also have small utility variations, like `IconButton` and `ButtonGroup`. Can you export `Button` as the default, and also export `IconButton` as a named export? Yes, absolutely. You write `export default function Button() { ... }` and on the next line `export function IconButton() { ... }`. In the consumer file, you can import both in a single line, placing the default export outside the curly braces and the named export inside: `import Button, { IconButton } from 'ui-library'`.   Resolution: A file can combine one default export with multiple named exports, and consumers can import both simultaneously using `import Default, { Named } from './file.jsx'`.
- [callout] > [!TIP]
**To impress the interviewer:** When asked how default and named exports differ under the hood, explain that an ES module produces a single namespace object. Named exports become keys on that object (`module.ArticleCard`). A default export is simply a named export stored under the special key `default` (`module.default`). When you write `import SiteHeader from './SiteHeader.jsx'`, the runtime assigns `module.default` to your local variable. When you write `import { SiteHeader }`, the runtime looks for `module.SiteHeader`. If the file used `export default`, `module.SiteHeader` is `undefined`, triggering React's infamous `Element type is invalid` runtime error.

### Where you will meet this
- Organizing component libraries: structuring UI directories with one component per file or grouping small related primitives into a single module.
- Importing third-party React libraries: importing default components from libraries (`import React from 'react'`) versus named hooks (`import { useState, useEffect } from 'react'`).
- Barrel files (index.js): re-exporting multiple components from a folder to provide a clean public entry point without deep path nesting.
- Fast Refresh and bundler optimization: keeping one component per file so Vite's Hot Module Replacement updates only the edited component without reloading the page.

### Glossary
- **ES Module**: The official ECMAScript standard for modular JavaScript files that use `import` and `export` statements with isolated module scope.
- **Default Export**: A module export declared with `export default` representing the primary value of the file; imported without curly braces.
- **Named Export**: A module export declared with `export` and identified by its variable or function name; imported using curly braces.
- **Curly Brace Trap**: The common runtime bug where a default export is imported with curly braces, resulting in `undefined` and crashing React.
- **Module Scope**: The isolated execution environment of a module where top-level variables and functions are private unless explicitly exported.
- **Tree Shaking**: The dead-code elimination process performed by bundlers like Rollup and Vite that removes unused named exports from the final bundle.

### Summary

**ES Module Component Architecture and Import Invariants**

In daily production, splitting components across files keeps codebases maintainable, prevents team merge conflicts, and enables fast module bundling. Understanding default and named exports ensures clean architecture and eliminates runtime import errors. Here is your streetwise review.

❒ Export Patterns and Import Syntax Rules

1. Choose the right export strategy for each file.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Use `export default` when a file has one primary component, like `export default function SiteHeader()`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use named exports when a file exports multiple related components or utility functions, like `export function ArticleCard()`.

2. Match your import syntax strictly to the export declaration.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Import default exports without curly braces: `import SiteHeader from './SiteHeader.jsx'`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Import named exports with curly braces: `import { ArticleCard } from './ArticleComponents.jsx'`.

➔ NEVER use curly braces when importing a default export, which evaluates to `undefined` and crashes React.

➔ ALWAYS name your component file to match its primary component, such as `SiteHeader.jsx` for `SiteHeader`.

➔ IF you need to rename a named export during import THEN **use the `as` keyword like `import { ArticleCard as Card }`**.

**DO THIS:** Match the import syntax to the export type and verify that default exports are imported without curly braces.

```jsx right title="NewsPortal.jsx"
// Default export: no curly braces
import SiteHeader from './SiteHeader.jsx';
// Named export: exact curly braces
import { ArticleCard } from './ArticleComponents.jsx';

export default function NewsPortal() {
  return (
    <div>
      <SiteHeader />
      <ArticleCard title="News" />
    </div>
  );
}
```

**DO NOT DO THIS:** Never import a default export using curly braces.

```jsx wrong title="Curly Brace Anti-Pattern"
// FAILS AT RUNTIME: SiteHeader evaluates to undefined!
import { SiteHeader } from './SiteHeader.jsx';

export default function BrokenPortal() {
  // Crashes: Element type is invalid: expected string or function but got undefined
  return <SiteHeader />;
}
```
