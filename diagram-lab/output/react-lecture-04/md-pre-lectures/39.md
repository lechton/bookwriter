### Component Architecture and the Logic Extraction Divide
- [p] ◇ {preknowledge:} In earlier lessons, we learned that React components maintain local state using `useState` and synchronize with external browser APIs using `useEffect` (see Lecture 1 and Lecture 28). In an editorial desk, components often need to observe the same external browser condition, such as whether the device is currently online or offline. {problem:} Developers often assume that because two components need the exact same reactive behavior, they must either copy-paste the code or lift state to a distant parent container. ◼ Pedagogical qualification: Ground familiar hook primitives; introduce the friction of logic duplication across independent components; terms introduced: **custom hook**, **stateful logic**, **lifecycle synchronization**.
- [p] ★ {preknowledge:} In plain JavaScript, when two functions need the same calculation, you extract a shared helper function. In React, however, a standard helper function cannot call `useState` or `useEffect`. If you copy-paste the hook calls directly into both `NetworkStatusBar` and `SaveDraftButton`, both files maintain identical lines of setup, subscription, and cleanup code. {problem:} Duplicating stateful logic creates state drift: fixing a missing event listener or correcting an event type in one file leaves the second file broken. ◼ Pedagogical qualification: Contrast plain utility extraction with stateful logic extraction; expose the maintenance hazard of copy-pasted hooks.
- [p] Here is the legacy copy-paste duplication pattern showing identical hook boilerplate repeated across components: ◼ Introduces the old copy-paste solution before presenting the custom hook extraction.
- [code] Legacy copy-paste duplication anti-pattern:
```jsx title="Copy-Paste Duplication Pattern"
const [isOnline, setIsOnline] = useState(true); // **STATE:**<br>Tracks connectivity locally in component 1
useEffect(() => {
  const handle = () => setIsOnline(navigator.onLine); // **EFFECT:**<br>Registers online/offline browser listeners
  window.addEventListener('online', handle);
  window.addEventListener('offline', handle);
  return () => {
    window.removeEventListener('online', handle);
    window.removeEventListener('offline', handle);
  };
}, []);
```
◼ **The what-this-introduces list:** 1. `const [isOnline, setIsOnline] = useState(true)`: Local state declaration inside the first component. 2. `useEffect(() => { ... }, [])`: Window event subscription with cleanup. 3. Identical block required in every other component needing online status.
- [p] What is a **custom hook**? In standard JavaScript, an ordinary utility function can compute values, format dates, or transform arrays, but it has no memory and cannot participate in React's component lifecycle. When you write an ordinary function, it executes once and discards all local variables when it returns. A **custom hook** takes that standard JavaScript function and authorizes it to call other React hooks inside its body. You write a function whose name starts with `use`, such as `function useOnlineStatus()`, and place `useState` and `useEffect` inside it. The custom hook encapsulates the stateful recipe: it tells React how to declare state, how to subscribe to external browser events, and what value to return to the caller. The law of custom hooks is absolute: a custom hook shares the stateful logic and lifecycle recipe, but it never shares state itself; each component calling the hook receives its own completely isolated state cell in memory. ◼ Pedagogical qualification: Execute the default and the law standard; define custom hooks through everyday programming habits and contrast with ordinary utility functions; terms introduced: **custom hook**, **stateful logic**, **Rules of Hooks**.
- [grounding] the opening question: Does a custom hook share state between components?
  the friction it clears: why two components calling the same custom hook do not share a single state variable.
  Scene & Repetition: Imagine two pastry chefs in two separate kitchens baking sourdough bread. They both open the exact same cookbook to page forty and follow the exact same recipe. Does that mean they share the same loaf of bread? Of course not. Chef Elena mixes her own flour, water, and yeast in her kitchen bowl. Chef Marcus mixes his own flour, water, and yeast in his kitchen bowl. If Marcus burns his loaf in the oven, Elena's loaf is completely unharmed. This is the difference between sharing a recipe and sharing the food. A **custom hook** is a recipe for **stateful logic**. When `NetworkStatusBar` calls `useOnlineStatus()`, it bakes its own private **component state**. When `SaveDraftButton` calls `useOnlineStatus()`, it bakes its own private **component state**. They share the recipe for subscribing to the browser, but their state remains completely independent.
  Key Terms (Bold): **custom hook**, **stateful logic**, **component state**, **fiber node**.
  Resolution: Custom hooks share the recipe for managing state and effects, while React allocates independent state storage for every component that calls the hook.

export function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(navigator.onLine); // **STATE:**<br>Local state initialized from browser navigator

### Lessons from the Experiment: Naive Expectation vs Reality

- [p] ★ {preknowledge:} In our newsroom experiment, both `NetworkStatusBar` and `SaveDraftButton` called `useOnlineStatus()`. When the browser fired an `online` event, both components updated simultaneously. However, they did not update because they shared state. They updated because each component had its own independent `isOnline` state variable, and both happened to receive the same external browser event at the exact same millisecond. {problem:} Conflating shared logic with shared state causes developers to create buggy custom hooks when managing user-driven state like form inputs or modal toggles. ◼ Pedagogical qualification: Dissect the simultaneity illusion; explain why simultaneous updates from external events mimic shared state while remaining strictly independent.

### The Fiber Node Memory Model: Why Custom Hooks Do Not Share State
- [p] ◇ {preknowledge:} To truly understand why custom hooks do not share state, you must look at where React stores state in memory. In plain JavaScript, if two modules import a shared variable from a file, both modules read and write to that exact same variable in memory. {problem:} Developers often assume that because a custom hook is declared in a single file (`useOnlineStatus.js`), the state inside that file behaves like a module-level variable. ◼ Pedagogical qualification: Contrast module-level state with React's fiber-allocated hook storage.
- [p] ★ {preknowledge:} In React, a custom hook owns zero memory of its own. A custom hook is not a component, not a class, and not an actor. It is simply a JavaScript function that executes inside the context of whichever component called it. When a component calls `useOnlineStatus()`, React looks at the fiber node currently being processed on the work loop. {problem:} Calling `useState` inside a custom hook tells React: "allocate a new state cell on the currently executing fiber node." If two components call the hook, React creates two separate state cells on two separate fiber nodes. ◼ Pedagogical qualification: Deconstruct the internal fiber linked list; explain how hook cells attach strictly to the caller's fiber node.
- [grounding] the opening question: Where does custom hook state actually live?
  the friction it clears: why custom hooks do not own the state they declare.
  Scene & Repetition: Imagine a carpenter who owns a set of measuring tools. When the carpenter works on house number one, they use their ruler to measure a wooden door. When the carpenter works on house number two, they use the exact same ruler to measure a wooden window. Does house number two have a door because the carpenter used the same ruler? No. The ruler does not own the wood; the house owns the wood. The ruler is simply the tool used to shape it. A **custom hook** is like that ruler. The hook does not own any **component state**. When `NetworkStatusBar` calls the hook, React allocates the state inside `NetworkStatusBar`'s **fiber node**. When `SaveDraftButton` calls the hook, React allocates the state inside `SaveDraftButton`'s **fiber node**. The state lives inside the component, never inside the hook.
  Key Terms (Bold): **custom hook**, **component state**, **fiber node**, **Rules of Hooks**.
  Resolution: Custom hooks do not hold state; they instruct React to allocate state on the calling component's internal fiber node.

### The use Prefix Convention and Linter Contract
- [p] ◇ {preknowledge:} In standard JavaScript, you can name a function anything you want: `getOnlineStatus`, `calculateTotal`, or `syncNetwork`. In React, however, any function that calls other React hooks must start with the lowercase prefix `use`, written in camelCase (such as `useOnlineStatus` or `useWindowSize`). {problem:} Developers who name a custom hook with a standard prefix like `getOnlineStatus` encounter linter errors or mysterious runtime bugs. ◼ Pedagogical qualification: Introduce the `use` prefix naming convention; connect naming rules to compiler and linter enforcement; terms introduced: **Rules of Hooks**, **eslint-plugin-react-hooks**, **camelCase**.
- [p] ★ {preknowledge:} React hooks rely on an internal invariant: hooks must be called in the exact same order on every single render. You cannot call hooks inside loops, conditions, or nested functions. Because React cannot inspect the internal body of every third-party function at compile time, it relies on the `use` prefix as an explicit syntactic contract. {problem:} The `use` prefix signals to the React linter that this function contains hook calls and must obey the Rules of Hooks. If you name it `getOnlineStatus`, the linter assumes it is an ordinary function, allowing developers to call it inside an `if` statement and corrupting React's internal hook linked list. ◼ Pedagogical qualification: Explain the Rules of Hooks enforcement mechanism; show why the `use` prefix enables static analysis of call-order stability.
- [p] When should a function be a custom hook versus an ordinary utility function? The rule is straightforward: (a) if the function calls at least one React hook (`useState`, `useEffect`, `useContext`, `useRef`), it must be named with the `use` prefix and treated as a custom hook; (b) if the function performs pure data transformation, string formatting, or mathematical calculation without calling any React hooks, it should be an ordinary utility function without the `use` prefix. Naming a pure function with `use` restricts it unnecessarily, preventing it from being called conditionally or inside loops. ◼ Pedagogical qualification: Deliver the senior decision rule distinguishing custom hooks from pure utility functions.
- [tip] To impress the interviewer: When asked how custom hooks work under the hood, never say "they share state between components." State clearly that custom hooks share stateful logic, not state. Explain that hooks are pure syntactic composition: calling a custom hook executes its internal `useState` and `useEffect` calls directly against the calling component's current fiber node. Each component gets its own independent state cell in the fiber linked list. If you need to share state itself, you must either lift state to a common ancestor or use React Context. ◼ Senior interview positioning.

### Glossary
- [definition] **Custom Hook**: A JavaScript function whose name starts with `use` that can call other React hooks, encapsulating reusable stateful logic and lifecycle synchronization for components.
- [definition] **Stateful Logic**: The instructions, event subscriptions, and effect lifecycles that govern how state is declared, updated, and synchronized over time.
- [definition] **Fiber Hook Cell**: An internal JavaScript object within a component fiber's linked list that stores the state value, memoized calculation, or effect cleanup for a specific hook call.
- [definition] **Rules of Hooks**: The fundamental constraints governing hook execution: hooks must only be called at the top level of React function components or custom hooks, and never inside loops, conditions, or nested functions.
- [definition] **State Isolation**: The core React guarantee that state declared by a hook belongs exclusively to the component instance that invoked it, remaining completely independent of other components calling the same hook.
- [definition] **Lifecycle Synchronization**: The process of keeping React component state aligned with an external system, such as browser window events, network sockets, or hardware sensors, using effects.
