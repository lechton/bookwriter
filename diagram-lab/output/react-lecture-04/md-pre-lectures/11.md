### Transforming Arrays into Elements with map()
- [p] ◇ {preknowledge:} In Lectures 6 and 8, we learned that JSX evaluates JavaScript expressions inside curly braces `{}` and that components receive data through props. In plain JavaScript, when you have an array of data objects and want to transform each into a new format, you call the `array.map()` method. {problem:} How do you take an array of story objects and convert them into a collection of rendered JSX elements? ◼ Pedagogical qualification: Connect plain JavaScript array transformation to JSX list rendering; terms introduced: **list rendering**, **array.map**, **collection transformation**.
- [p] ★ {preknowledge:} When you call `stories.map(story => <li key={story.id}>{story.title}</li>)`, JavaScript returns a new array of JSX element objects. Because React natively knows how to render arrays of elements, placing that expression inside JSX curly braces renders the entire collection in order. You can map arrays to native HTML elements or to custom components: `{stories.map(story => <StoryRow key={story.id} story={story} />)}`. ◼ Pedagogical qualification: Explain array of JSX elements and embedding inside JSX; terms introduced: **array of elements**, **JSX map**, **item component**.
- [p] ★ {preknowledge:} Whenever you render a list of elements from an array, React demands that every item have a special `key` prop: `<li key={story.id}>`. React uses the `key` internally to track which item is which. The `key` prop is not passed down to the child component: if the child needs the ID, you must pass it as a separate prop like `id={story.id}`. ◼ Pedagogical qualification: Introduce the `key` prop and clarify that keys are not accessible via `props.key`; terms introduced: **key prop**, **reconciliation tag**, **prop exclusion**.
- [code] Transforming arrays into elements with map and keys:
```jsx title="Rendering Lists with Map and Keys"
const stories = [
  { id: 's-01', title: 'Dockworkers Deal' },
  { id: 's-02', title: 'Transit Approved' },
];
export default function StoryList() {
  return (
    <ul>{stories.map(s => <li key={s.id}>{s.title}</li>)}</ul>
  );
}
```
- [grounding] Leading Question: Why does React need keys if array items already have indexes?
  Confusion Point: If an array already numbers items 0, 1, 2, why doesn't React just use those numbers automatically?
  Scene & Repetition: Imagine an editor has a list of three stories: index 0 is "Transit", index 1 is "Economy", and index 2 is "Sports". The reader checks a checkbox on story 0 ("Transit"). Now a breaking news story arrives and gets prepended to the top of the array. The breaking story becomes index 0. "Transit" shifts to index 1. If React matched elements by their index, it would compare the old index 0 with the new index 0 and assume the breaking story is the same component as the old "Transit" story. The checkbox that the user checked on "Transit" would now be attached to the breaking story. By assigning a stable ID like `key="transit-101"`, React knows that "Transit" simply moved down, preserving its state.
  Key Terms (Bold): `**key prop**`, `**array index**`, `**reconciliation**`, `**state corruption**`.
  Resolution: Keys provide permanent identity across renders so React can track item movement, insertion, and deletion without corrupting component state.

### The Dangers of Index Keys and Rules of Stable Identity
- [p] ◇ {preknowledge:} When developers see the console warning about missing keys, many write `stories.map((story, index) => <li key={index}>)`. {problem:} While this silences the warning, using array indexes as keys is an anti-pattern that creates subtle, catastrophic bugs when lists change. ◼ Pedagogical qualification: Expose index keys as a dangerous anti-pattern; terms introduced: **index as key**, **anti-pattern**, **order mutation**.
- [p] ★ {preknowledge:} An array index does not represent the item's identity: it represents the item's position in memory. If you sort the list, filter items, insert at the beginning, or delete a row, every item's index changes. React reuses existing DOM nodes and component state based on the matching key. When keys change because of reordering, inputs lose focus, animations break, and uncontrolled form state attaches to the wrong row. ◼ Pedagogical qualification: Deconstruct DOM reuse and state mismatch caused by shifting indexes; terms introduced: **positional identity**, **DOM node reuse**, **uncontrolled state mismatch**.
- [p] ★ {preknowledge:} Stable keys must satisfy three strict rules: (1) **Keys must be unique among siblings**: different lists can use the same keys, but within a single array, each key must be unique. (2) **Keys must never change**: do not generate keys on the fly using `Math.random()` or `crypto.randomUUID()` during render, which forces React to destroy and recreate every DOM node on every render. (3) **Keys should come from data**: use database IDs, permanent slugs, or unique business keys. ◼ Pedagogical qualification: State the three golden rules of React keys; terms introduced: **sibling uniqueness**, **stable keys**, **render generation ban**.
- [code] Safe versus dangerous key patterns:
```jsx title="Key Identity Contrast"
// DANGEROUS: Math.random destroys and recreates DOM on every render!
{stories.map(s => <StoryRow key={Math.random()} story={s} />)}
// DANGEROUS: Index keys cause state mismatch when reordering:
{stories.map((s, index) => <StoryRow key={index} story={s} />)}
// SAFE: Stable database IDs preserve component identity:
{stories.map(s => <StoryRow key={s.id} story={s} />)}
```
- [grounding] Leading Question: Can you ever safely use an index as a key?
  Confusion Point: Are index keys ever acceptable in production?
  Scene & Repetition: Imagine a static pagination bar with five fixed pages (1, 2, 3, 4, 5). The list is never reordered, never filtered, never inserted into, and the items have no internal state or inputs. In this rare scenario, using `key={index}` causes no visual harm. However, as a professional standard, you should avoid index keys entirely. Requirements evolve: tomorrow an editor adds drag-and-drop sorting or a delete button to that list, and the index key immediately turns into a bug. Always use stable, unique data IDs.
  Key Terms (Bold): `**index as key**`, `**static lists**`, `**stable ID**`, `**data identifiers**`.
  Resolution: Only use index keys when a list is completely static, never reordered or filtered, and has no state; otherwise, always use stable data IDs.

### Step 1: First, we construct the parent container NewsFeed.jsx
- [p] ★ {preknowledge:} The parent container owns the story data array. It maps each story to `<StoryRow key={story.id} story={story} />`. {problem:} The parent must demonstrate `array.map()` and place the `key` prop directly on the outermost JSX tag of the map. ◼ Pedagogical qualification: Construct parent container demonstrating list mapping with stable keys.
- [code] Parent container NewsFeed.jsx:
```jsx title="NewsFeed.jsx"
import StoryRow from './components/StoryRow.jsx';
export default function NewsFeed() {
  const stories = [
    { id: 'story-01', title: 'Dockworkers Deal', category: 'Economy' },
    { id: 'story-02', title: 'Transit Approved', category: 'Metro' },
  ];
  return (
    <ul className="news-feed">
      {stories.map(story => (
        <StoryRow key={story.id} story={story} /> // Key on **OUTERMOST** tag
      ))}
    </ul>
  );
}
```
- [p] ★ Step 1 establishes the contracts: Look at line 10: `<StoryRow key={story.id} story={story} />`. We have not written `StoryRow` yet. But right here, we establish its contract: it receives a `story` prop containing title and category. Notice that the `key` prop sits on `<StoryRow>`, which is the outermost element returned by the map callback. We will build `StoryRow` next in step 2. ◼ Pedagogical qualification: Deconstruct `key` placement on outermost mapped element.

### Glossary
- **List Rendering**: The technique of mapping an array of data items into an array of JSX elements using `array.map()`.
- **Key Prop**: A special string or number attribute assigned to elements in an array to give them a stable identity across renders.
- **Reconciliation**: The process by which React compares the new Virtual DOM tree with the previous one to determine the minimal set of DOM updates.
- **Index as Key**: The anti-pattern of using the second argument of `map((item, index) => ...)` as the key prop, causing state corruption during reordering.
- **Stable Identity**: A unique identifier (like a database ID) that remains permanently associated with an item throughout its entire lifecycle.
- **Prop Exclusion**: The architectural rule where React strips reserved attributes (`key` and `ref`) so they are not accessible on the `props` object.

### Summary

**React 19 List Rendering and Key Invariants**

In daily production, transforming collections into UI is one of the most common tasks in frontend development. Understanding `array.map()` and the reconciliation mechanics of keys prevents subtle state bugs and ensures optimal rendering performance. Here is your streetwise review.

❒ List Rendering and Key Invariants

1. Transform arrays using `array.map()` and assign a stable `key` to the outermost element.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Map data items into JSX: `{items.map(item => <Row key={item.id} item={item} />)}`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Place `key` directly on the root element returned by the callback.

2. Never use array indices as keys for dynamic or reorderable lists.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Indices represent position, not identity: reordering shifts indices and corrupts local state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Always use stable, unique data identifiers from your backend or database.

➔ NEVER generate keys during render using `Math.random()`, which causes React to destroy and recreate DOM nodes on every render.

➔ ALWAYS place the `key` prop on the outermost JSX element returned by the `map()` function.

➔ IF a child component needs to read the ID value THEN **pass it as a separate prop like `id={item.id}` because `key` is not accessible via `props`**.

**DO THIS:** Use stable data IDs and place the key on the outermost mapped component.

```jsx right title="NewsFeed.jsx"
// Stable keys on outermost mapped elements
export default function NewsFeed({ stories }) {
  return (
    <ul>
      {stories.map(story => (
        <StoryRow key={story.id} story={story} />
      ))}
    </ul>
  );
}
```

**DO NOT DO THIS:** Never use array indices as keys when items can be inserted or reordered.

```jsx wrong title="Index Key Anti-Pattern"
// FAILS: Index keys corrupt state when items are prepended!
export default function BrokenFeed({ stories }) {
  return (
    <ul>
      {stories.map((story, index) => (
        <StoryRow key={index} story={story} />
      ))}
    </ul>
  );
}
```
