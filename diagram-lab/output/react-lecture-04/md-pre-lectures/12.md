### Mathematical Purity and the Render Phase
- [p] ◇ {preknowledge:} In computer science, a function is considered **pure** if it satisfies two strict criteria: (1) It minds its own business: it does not change any objects or variables that existed before the function was called. (2) Same inputs, same output: given the exact same arguments, the function always returns the exact same result. {problem:} In React, component functions are executed repeatedly whenever state or props change. If a component modifies external variables during render, each execution produces unpredictable results. ◼ Pedagogical qualification: Establish the formal definition of pure functions in the context of React rendering; terms introduced: **pure component**, **mathematical purity**, **render phase**.
- [p] ★ {preknowledge:} React's rendering process must always be pure. Your component function should only calculate and return JSX: it should never mutate global variables, modify preexisting objects, or trigger network requests during the render phase. When a component is pure, React can pause rendering, discard work, re-order renders, or reuse cached results safely. ◼ Pedagogical qualification: Explain why React demands component purity; terms introduced: **side effects**, **concurrent rendering**, **deterministic rendering**.
- [p] ★ {preknowledge:} Local mutation is completely fine. If you create a variable or an array *inside* the component during render: `const items = []; items.push(1);`, that mutation is invisible to the outside world because the array was created within the same render pass. What is strictly forbidden is mutating variables declared *outside* the component or mutating objects passed in through props. ◼ Pedagogical qualification: Distinguish safe local mutation from dangerous external mutation; terms introduced: **local mutation**, **external mutation**, **scope boundary**.
- [code] Pure calculation versus external mutation:
```jsx title="Pure Component Contrast"
// IMPURE: Mutates external variable during render!
let guestCount = 0;
function BadCounter() {
  guestCount = guestCount + 1; // Mutates outer variable!
  return <p>Guest #{guestCount}</p>;
}
// PURE: Computes output purely from incoming props:
function GoodCounter({ index }) {
  return <p>Guest #{index + 1}</p>;
}
```
- [grounding] Leading Question: Why does React call components twice in development?
  Confusion Point: When running in development mode, why does `console.log` or an external counter run twice for every single render?
  Scene & Repetition: Imagine Elena runs her app and sees `storyCount` jump by 2 instead of 1 on the very first page load. She thinks React has a bug. In reality, React's `<StrictMode>` intentionally calls every component function twice in development mode. Why? React does this as an automated audit to expose accidental impurities. If a component is pure, calling it twice produces the identical JSX without changing external state: `f(x) = y`, and running it again still produces `y`. But if the component mutates an external variable (`count++`), running it twice causes the count to double immediately, alerting the developer to the bug before shipping to production.
  Key Terms (Bold): `**StrictMode**`, `**double render**`, `**impurity audit**`, `**pure function**`.
  Resolution: StrictMode double-renders components in development to aggressively catch external mutations and side effects during the render phase.

### Quarantining Side Effects
- [p] ◇ {preknowledge:} Real-world applications cannot be 100% pure: they must fetch data, update the DOM, play sounds, and send analytics. {problem:} If components must be pure during render, where do side effects belong? ◼ Pedagogical qualification: Introduce the need for side effects in real applications; terms introduced: **side effects**, **quarantine**, **event handlers**.
- [p] ★ {preknowledge:} In React, side effects are **quarantined**. They belong in two specific places: (1) **Event handlers**: functions that run in response to user actions like clicking a button or submitting a form. Event handlers run after the render phase is complete, so they are free to perform side effects. (2) **Effects (`useEffect`)**: an escape hatch hook for synchronizing with external systems, which runs after React has committed the DOM to the screen. ◼ Pedagogical qualification: Define the two legal zones for side effects in React; terms introduced: **event handlers**, **useEffect**, **commit phase**.
- [p] ★ {preknowledge:} By keeping the render phase strictly pure, React guarantees that your user interface is a predictable projection of state and props. If something changes on screen, it changes because state changed, never because a component function happened to execute. ◼ Pedagogical qualification: Summarize the architectural payoff of pure rendering.
- [code] Quarantining side effects in event handlers:
```jsx title="Quarantining Side Effects"
// WRONG: Side effect in render phase!
function BadStory({ id }) {
  fetch(`/api/track/${id}`); // Fires on every render!
  return <h2>Story {id}</h2>;
}
// RIGHT: Side effect quarantined in event handler:
function GoodStory({ id }) {
  const handleRead = () => fetch(`/api/track/${id}`);
  return <button onClick={handleRead}>Read Story</button>;
}
```
- [grounding] Leading Question: Is mutating a prop object considered an impurity?
  Confusion Point: If a parent passes an object as a prop, can a child add a property to it?
  Scene & Repetition: Imagine a parent passes `story = { title: 'Election Results' }` to `StoryCard`. Inside `StoryCard`, the author writes `story.viewed = true`. This mutates an object that existed before `StoryCard` was called. Because objects are passed by reference, the parent component and any sibling components sharing `story` now have their data altered without React knowing. This violates the first rule of purity: never modify objects that existed prior to render. React freezes props in development, but mutating nested object properties bypasses shallow freezes and corrupts app state.
  Key Terms (Bold): `**prop mutation**`, `**pure function**`, `**pass by reference**`, `**shallow freeze**`.
  Resolution: Mutating incoming props or existing objects violates component purity; treat all incoming data as immutable snapshots.

### Step 2: Next, we declare the counter child StoryCounter.jsx
- [p] ★ {preknowledge:} Step 1 passed `index` and `title` to `StoryCounter`. {problem:} The child component must compute the display number (`index + 1`) purely without touching external variables. ◼ Pedagogical qualification: Build pure component calculating output from props.
- [code] Counter child StoryCounter.jsx:
```jsx title="StoryCounter.jsx"
export default function StoryCounter({ index, title }) {
  const displayNum = index + 1; // Pure **LOCAL** calculation
  return (
    <li className="story-item">
      <span className="story-num">#{displayNum}</span>
      <span className="story-title">{title}</span>
    </li>
  );
}
```
- [p] ★ Step 2 fulfills the purity contract: Look at line 2: `const displayNum = index + 1;`. This calculation is 100% pure: given `index = 0`, it will always produce `displayNum = 1`. If React renders this component twice under StrictMode, `displayNum` is calculated twice, but no external memory is modified. The output remains identical. ◼ Pedagogical qualification: Deconstruct pure local calculation.
- [p] What would happen if `StoryCounter` used a global `let count = 0` outside the component and wrote `count++` inside the function? Under StrictMode, React would run the component function twice for each story. Story 1 would display `#2`, Story 2 would display `#4`, and the next re-render would inflate the numbers to `#6` and `#8`. By calculating from `index + 1`, the component is completely immune to render count variations. ◼ Pedagogical qualification: Apply Negative Counterfactual Law to shared-state mutation.

### Glossary
- **Pure Component**: A component function that produces identical JSX for the same props and state without causing observable side effects during render.
- **Side Effect**: Any modification of external state, network request, timer, or DOM mutation that occurs outside the pure calculation of JSX.
- **Render Phase**: The phase where React calls component functions to compute the next Virtual DOM tree; must be completely free of side effects.
- **Commit Phase**: The phase where React applies changes to the actual DOM and runs layout/passive effects.
- **StrictMode**: A React development-only tool that double-renders components to expose side effects and impurities in the render phase.
- **Local Mutation**: Modifying variables or objects created within the current component's render execution, which is completely safe and pure.

### Summary

**React 19 Pure Component Invariants**

In daily production, component purity is the bedrock of predictable, scalable React applications. Keeping the render phase free of side effects ensures components are resilient to re-renders and ready for concurrent React features. Here is your streetwise review.

❒ Pure Component Invariants

1. Same inputs must always return the same JSX output.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Compute all display values directly from props and state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Never read or modify mutable global variables during render.

2. Quarantine all side effects in event handlers or Effects.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Never initiate API calls, timers, or DOM mutations during render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Embrace StrictMode double-rendering in development to detect impurities early.

➔ NEVER mutate a variable declared outside the component function during render.

➔ ALWAYS compute derived values locally using incoming props and state.

➔ IF you need to perform an action that changes the outside world THEN **place it inside an event handler or a `useEffect` hook**.

**DO THIS:** Compute values locally from props and return deterministic JSX.

```jsx right title="StoryCounter.jsx"
// Pure calculation derived entirely from props
export default function StoryCounter({ index, title }) {
  const displayNum = index + 1;
  return <li>#{displayNum}: {title}</li>;
}
```

**DO NOT DO THIS:** Never mutate an external variable inside a component function.

```jsx wrong title="External Mutation Anti-Pattern"
// FAILS: Mutates global variable during render; doubles in StrictMode!
let globalCount = 0;
export default function BrokenCounter({ title }) {
  globalCount++; // Impure! Corrupts state on re-render
  return <li>#{globalCount}: {title}</li>;
}
```
