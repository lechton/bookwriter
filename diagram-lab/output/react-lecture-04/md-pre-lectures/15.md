### Why Ordinary Variables Forget
- [p] ◇ {preknowledge:} In Lectures 3 and 12, we learned that React components are JavaScript functions that execute during the render phase. In plain JavaScript, local variables declared inside a function exist only while that function is running. {problem:} When a user clicks a button to increment a count, why doesn't a local variable update the screen? ◼ Pedagogical qualification: Establish the lifecycle limitation of local variables in functional components; terms introduced: **component memory**, **render cycle**, **local variables**.
- [p] ★ {preknowledge:} Two distinct obstacles prevent local variables from working: (1) **Local variables do not persist between renders**: every time React re-renders a component, it calls the function from top to bottom. Any variable declared with `let` or `const` is re-initialized to its initial value. (2) **Changes to local variables do not trigger renders**: modifying a local variable (`likes++`) alters a value in memory, but React has no mechanism to observe this change, so it never updates the DOM. ◼ Pedagogical qualification: Deconstruct the two reasons local variables fail; terms introduced: **variable reset**, **render trigger**, **change detection**.
- [p] ★ {preknowledge:} To retain data across renders and trigger UI updates, React provides the **`useState` hook**. A hook is a special function that lets you "hook into" React features. When you call `const [likes, setLikes] = useState(0)`, React allocates memory for that variable in its internal fiber data structure. When you call `setLikes(likes + 1)`, React updates that memory and schedules a new render pass. ◼ Pedagogical qualification: Introduce `useState` and state setter mechanics; terms introduced: **useState**, **hook**, **state setter**, **fiber memory**.
- [code] Local variable versus useState contrast:
```jsx title="Local Variable vs useState"
// FAILS: Variable resets on render; does not trigger update:
function BrokenCounter() {
  let likes = 0;
  return <button onClick={() => likes++}>{likes}</button>;
}
// WORKS: useState retains value and triggers re-render:
function GoodCounter() {
  const [likes, setLikes] = useState(0);
  return <button onClick={() => setLikes(likes + 1)}>{likes}</button>;
}
```
- [grounding] Leading Question: Where does React store state if the function runs from scratch?
  Confusion Point: If a component function executes from scratch on every render, where does the state value actually live between renders?
  Scene & Repetition: Imagine Elena calls `useState(0)`. During render, the function finishes and its execution stack is cleared from memory. Where is the number 0 kept? Behind the scenes, React maintains a **fiber node** for every mounted component instance. That fiber node contains a linked list of hook records. When `useState` is called, React looks up the current hook record in the fiber node. On initial render, it initializes the value to `0`. On subsequent renders, React ignores the argument `0` and returns the current value stored in the fiber node. State lives in React's internal memory, completely outside the component function.
  Key Terms (Bold): `**fiber node**`, `**hook record**`, `**initial render**`, `**execution stack**`.
  Resolution: State lives inside React's internal fiber node memory, surviving the lifecycle of individual component function executions.

### The Anatomy of useState and the Rules of Hooks
- [p] ◇ {preknowledge:} The syntax `const [state, setState] = useState(initialState)` uses JavaScript array destructuring. {problem:} Why does `useState` return an array with two elements instead of an object with named properties? ◼ Pedagogical qualification: Explain the API design of `useState`; terms introduced: **array destructuring**, **state variable**, **setter function**.
- [p] ★ {preknowledge:} Returning an array allows you to name the state variable and setter whatever you want without awkward object renaming. The convention is `[something, setSomething]`. The first element is the **state variable** representing the current value for this render. The second element is the **setter function** used to update the value and trigger a re-render. ◼ Pedagogical qualification: Explain naming conventions and setter roles; terms introduced: **naming convention**, **re-render trigger**.
- [p] ★ {preknowledge:} Because React matches hook calls by their call order inside the fiber node's linked list, you must follow the **Rules of Hooks**: (1) Only call hooks at the top level of your component function: never inside loops, conditions, or nested functions. (2) Only call hooks from React function components or custom hooks. Calling hooks unconditionally guarantees that React pairs each hook with the exact same memory slot on every render. ◼ Pedagogical qualification: State the Rules of Hooks and ground them in linked list traversal; terms introduced: **Rules of Hooks**, **top-level call**, **hook order invariant**.
- [code] Hook call order and array destructuring:
```jsx title="Rules of Hooks in Practice"
import { useState } from 'react';
export default function Scoreboard() {
  // 1. First hook call: index 0 in fiber list
  const [likes, setLikes] = useState(0);
  // 2. Second hook call: index 1 in fiber list
  const [hasVoted, setHasVoted] = useState(false);
  return <p>{likes} likes</p>;
}
```
- [grounding] Leading Question: What happens if you call useState inside an if statement?
  Confusion Point: Why does React crash if a hook is placed inside a conditional block?
  Scene & Repetition: Imagine Elena writes `if (isSpecial) { useState(0); }` followed by `useState('news')`. On the first render, `isSpecial` is true: React records Hook 0 as the counter and Hook 1 as the category. On the second render, `isSpecial` is false: the `if` block is skipped. The category hook is now called first. React looks at Hook 0 in its internal list, expects a counter, and returns the counter data to the category variable. The hook order drifts out of alignment, corrupting state. React immediately detects this mismatch and throws a fatal error: `Rendered fewer hooks than expected. This may be caused by an accidental early return or conditional hook call`.
  Key Terms (Bold): `**hook order drift**`, `**conditional hook ban**`, `**Rules of Hooks**`, `**fiber linked list**`.
  Resolution: Calling hooks unconditionally at the top level ensures that hook call order perfectly matches React's internal linked list across every render pass.

### Step 1: First, we construct the parent container StoryScoreboard.jsx
- [p] ★ {preknowledge:} The parent container owns the like state. It declares `useState(0)` and passes `likes` and `handleVote` down to children. {problem:} The parent must initialize state and manage the update callback. ◼ Pedagogical qualification: Construct parent container demonstrating `useState` declaration and render trigger.
- [code] Parent container StoryScoreboard.jsx:
```jsx title="StoryScoreboard.jsx"
import { useState } from 'react';
import ScoreDisplay from './components/ScoreDisplay.jsx';
import VoteButton from './components/VoteButton.jsx';
export default function StoryScoreboard() {
  const [likes, setLikes] = useState(0); // Allocates **FIBER** memory
  const handleVote = () => setLikes(likes + 1); // Triggers re-render
  return (
    <main className="scoreboard">
      <ScoreDisplay likes={likes} />
      <VoteButton onVote={handleVote} />
    </main>
  );
}
```
- [p] ★ Step 1 establishes state ownership: Look at line 5: `const [likes, setLikes] = useState(0);`. This allocates a state slot in React's fiber tree. Now look at line 6: `const handleVote = () => setLikes(likes + 1);`. When `setLikes` is invoked, React updates the stored like count and schedules a re-render of `StoryScoreboard`. We will build `ScoreDisplay` next in step 2. ◼ Pedagogical qualification: Deconstruct `useState` allocation and re-render trigger.

- [grounding] Leading Question: Can you store multiple values in a single useState call?
  Confusion Point: Should you call `useState` multiple times for individual values, or use a single `useState` call with an object?
  Scene & Repetition: In React, you can do either: `const [x, setX] = useState(0); const [y, setY] = useState(0);` or `const [pos, setPos] = useState({ x: 0, y: 0 });`. **To impress the interviewer:** When asked how `useState` works under the hood, explain that React does not store state inside your component function. On render, React traverses this linked list in the exact order the hooks were called. Calling hooks conditionally disrupts this index alignment, which is why the Rules of Hooks are mathematically mandatory.

### Glossary
- **useState**: The foundational React hook that declares a state variable and provides a setter function to update it and trigger a re-render.
- **State Variable**: The first value returned by `useState`, representing the current value of the state for the current render pass.
- **State Setter**: The second value returned by `useState`, a function that schedules a state update and triggers a re-render.
- **Fiber Node**: React's internal data structure representing a component instance in memory, where hook values are persisted across renders.
- **Rules of Hooks**: The core constraints requiring hooks to be called only at the top level of React functions and never conditionally or inside loops.
- **Render Trigger**: The mechanism where calling a state setter alerts React to schedule a new render pass for the component.

### Summary

**React 19 useState and Component Memory Invariants**

In daily production, `useState` is the primary hook for adding interactivity and memory to functional components. Understanding that state lives in React's fiber tree and requires setter functions to trigger re-renders is essential for reliable frontend architecture. Here is your streetwise review.

❒ useState Invariants

1. State persists across renders because React stores it in fiber memory.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Local variables reset every render; `useState` values survive.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Always call state setters (`setLikes`) to schedule a re-render.

2. Follow the Rules of Hooks to protect hook call order in the fiber list.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Call hooks only at the top level of your component.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Never place `useState` inside `if` statements, loops, or nested functions.

➔ NEVER use ordinary local variables to hold data that should persist across user interactions.

➔ ALWAYS follow the naming convention `const [value, setValue] = useState(initial)`.

➔ IF you need to update what appears on the screen THEN **call the state setter function rather than mutating variables directly**.

**DO THIS:** Declare state at the top level with `useState` and update via setters.

```jsx right title="StoryScoreboard.jsx"
// Persists state across renders and triggers updates
export default function StoryScoreboard() {
  const [likes, setLikes] = useState(0);
  return <button onClick={() => setLikes(likes + 1)}>{likes} Likes</button>;
}
```

**DO NOT DO THIS:** Never rely on plain local variables for interactive component state.

```jsx wrong title="Local Variable Anti-Pattern"
// FAILS: Variable resets on every render; screen never updates!
export default function BrokenScoreboard() {
  let likes = 0;
  return <button onClick={() => likes++}>{likes} Likes</button>;
}
```

| | **REACT STATE (`useState`)**<br>(Fiber Memory) | **LOCAL VARIABLE (`let`)**<br>(Stack Memory) |
| ---: | :--- | :--- |
| **Lifecycle persistence** | Survives across multiple<br>render executions | Resets to initial value on<br>every function call |
| **Re-render trigger** | Calling setter schedules a<br>new UI render pass | Modifying variable never<br>alerts React to re-render |
| **Storage location** | Stored in React's internal<br>fiber node on heap | Stored in JavaScript call<br>stack execution frame |
| **Call constraint** | Strictly at top level via<br>the Rules of Hooks | Can be declared anywhere<br>in any scope or loop |
| **Destructuring syntax** | Returns `[value, setter]`<br>array pair | Declared directly: `let count`<br>`= 0;` |
