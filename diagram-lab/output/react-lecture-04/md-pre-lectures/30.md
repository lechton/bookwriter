### Prop Drilling vs Context Teleportation
- [p] ◇ {preknowledge:} Passing props is the standard way to send data down in React. When components are separated by many intermediate layers, threading props through components that have no interest in the data is known as **prop drilling**. {problem:} Why does prop drilling become a major architectural burden in large applications? ◼ Pedagogical qualification: Contrast prop drilling overhead with direct ancestor-descendant data delivery; terms introduced: **prop drilling**, **courier props**, **architectural friction**.
- [p] ★ {preknowledge:} Prop drilling forces intermediate components to accept and forward props they never use. If you rename a prop or add an extra configuration flag, you must modify every intermediate file in the chain. React **Context** solves this by creating a direct channel from a top-level provider to any deep descendant, effectively "teleporting" data across the tree without touching intermediate components. ◼ Pedagogical qualification: Establish context teleportation mechanism; terms introduced: **react context**, **context provider**, **context consumer**, **teleportation**.
- [p] ★ {preknowledge:} Context follows a simple three-step lifecycle:
  1. **Create:** Create the context outside components with `createContext(defaultValue)`.
  2. **Provide:** Wrap the subtree with `<ThemeContext value={currentValue}>`. In React 19, you write `<ThemeContext>` directly instead of `<ThemeContext.Provider>`.
  3. **Consume:** Read the value in any descendant component using `use(ThemeContext)`. ◼ Pedagogical qualification: Formalize the 3-step context lifecycle and React 19 provider syntax; terms introduced: **createContext**, **React 19 Context element**, **use hook**.
- [code] Prop drilling vs context contrast:
```jsx title="Prop Drilling vs Context"
// FRAGILE: Every intermediate layer must accept and forward `theme`:
function Feed({ theme }) { return <Card theme={theme} />; }
function Card({ theme }) { return <Badge theme={theme} />; }
// CONTEXT: Provider wraps tree, deep child reads directly:
function App() {
  return <ThemeContext value="dark"><Feed /></ThemeContext>;
}
function Badge() {
  const theme = use(ThemeContext); // Direct read with zero prop drilling!
  return <span className={theme}>Nightly Wire</span>;
}
```
- [grounding] Leading Question: What happens if a component calls use(ThemeContext) without a provider?
  Confusion Point: Does calling `use(ThemeContext)` throw an error if no `<ThemeContext>` wraps the component?
  Scene & Repetition: No! If no provider wraps the consumer, `use(ThemeContext)` returns the **default value** passed to `createContext(defaultValue)`. This is why setting a sensible default value is useful: it allows leaf components to be tested and rendered in isolation without wrapping them in fake providers!
  Key Terms (Bold): `**default value fallback**`, `**unwrapped consumer**`, `**isolated component testing**`, `**createContext fallback**`.
  Resolution: Unwrapped consumers gracefully receive the default value passed to `createContext`.

### Consuming Context with React 19's use() API
- [p] ◇ {preknowledge:} Prior to React 19, reading context required the `useContext` hook. {problem:} What limitations did `useContext` have, and how does the new `use()` API improve context consumption? ◼ Pedagogical qualification: Contrast legacy useContext with React 19 use() API; terms introduced: **useContext hook**, **use API**, **conditional hook execution**.
- [p] ★ {preknowledge:} Traditional hooks like `useContext` must obey the Rules of Hooks: they can never be called inside `if` statements, loops, or after early returns. In React 19, the new **`use(Context)`** API replaces `useContext` for reading context. Crucially, **`use()` can be called conditionally** inside conditional blocks and loops! ◼ Pedagogical qualification: Explain conditional superpowers of use(Context); terms introduced: **use function**, **conditional context read**, **early return safety**.
- [p] ★ {preknowledge:} While context is powerful, avoid using it for every piece of shared data. Context is ideal for **global or ambient data**: current user session, UI theme, localization, and navigation router. Do not use context just to avoid passing props between 2 or 3 adjacent components—props are more explicit and easier to trace. ◼ Pedagogical qualification: Formulate context usage boundaries; terms introduced: **ambient data**, **global state boundary**, **explicit props**.
- [code] Conditional use(Context) pattern:
```jsx title="Conditional Context Read"
import { use } from 'react';
import { ThemeContext } from './ThemeContext.js';
export default function DynamicBadge({ showTheme }) {
  if (!showTheme) return <span>Standard Dispatch</span>;
  // React 19 superpower: use() can be called inside an `if` block!
  const theme = use(ThemeContext);
  return <span className={theme}>Edition: {theme}</span>;
}
```
- [grounding] Leading Question: Does updating context re-render all intermediate components?
  Confusion Point: When a provider's value changes, does every component between provider and consumer re-render?
  Scene & Repetition: No! Only components that actually **consume** the context (via `use()`) re-render when the context value changes. Intermediate components that do not read the context can skip re-rendering if they are wrapped in `memo` or passed as `children` to the provider!
  Key Terms (Bold): `**consumer re-render**`, `**intermediate bypass**`, `**children prop optimization**`, `**targeted subscription**`.
  Resolution: Context changes specifically target components that consume the context; non-consuming intermediates do not need to re-render.

### Step 1: First, we construct the provider container ThemePortal.jsx
- [p] ★ {preknowledge:} The container defines `ThemeContext` and renders `<ThemeContext value={theme}>`. {problem:} The provider must wrap the tree and provide dynamic theme values. ◼ Pedagogical qualification: Construct React 19 context provider.
- [code] Provider container ThemePortal.jsx:
```jsx title="ThemePortal.jsx"
import { useState, createContext } from 'react';
import ArticleCard from './components/ArticleCard.jsx';
export const ThemeContext = createContext('light');
export default function ThemePortal() {
  const [theme, setTheme] = useState('dark');
  return (
    <ThemeContext value={theme}>
      <button onClick={() => setTheme(t => t === 'dark' ? 'light' : 'dark')}>Toggle</button>
      <ArticleCard />
    </ThemeContext>
  );
}
```
- [p] ★ Step 1 establishes the context provider: Look at line 3: `export const ThemeContext = createContext('light')`. Look at line 7: `<ThemeContext value={theme}>`. In React 19, we render `<ThemeContext>` directly. Notice `ArticleCard` receives zero theme props. We will build `ArticleCard` next in step 2. ◼ Pedagogical qualification: Deconstruct React 19 context provider syntax.

### Step 3: Then, we declare the consumer child EditionBadge.jsx
- [p] ★ {preknowledge:} `EditionBadge` is nested inside `ArticleCard`. {problem:} The leaf component must consume `ThemeContext` directly using React 19's `use()` function. ◼ Pedagogical qualification: Build consumer leaf using React 19 use(Context).
- [code] Consumer child EditionBadge.jsx:
```jsx title="EditionBadge.jsx"
import { use } from 'react';
import { ThemeContext } from '../ThemePortal.jsx';
export default function EditionBadge() {
  const theme = use(ThemeContext);
  return (
    <span className={`badge badge-${theme}`}>
      Current Edition: {theme.toUpperCase()}
    </span>
  );
}
```
- [p] ★ Step 3 completes direct consumption: Look at line 4: `const theme = use(ThemeContext)`. `EditionBadge` teleports the value directly from `ThemePortal`. When the user clicks "Toggle", `EditionBadge` immediately re-renders with the new theme while `ArticleCard` remains decoupled. ◼ Pedagogical qualification: Deconstruct use(Context) read mechanics.
- [p] What would happen if we read a context that was never provided? If a component calls `use(ThemeContext)` without an ancestor `<ThemeContext>` provider, React returns the default value passed into `createContext('light')`. The component continues to function smoothly using the fallback value instead of crashing. ◼ Pedagogical qualification: Apply Negative Counterfactual Law to missing context provider.

- [grounding] Leading Question: Can you have multiple providers for the same context?
  Confusion Point: What happens if an outer and inner component both render `<ThemeContext>`?
  Scene & Repetition: Yes! You can nest multiple providers for the same context. A consumer component will always read from the **closest matching provider above it in the tree**. This makes it easy to override ambient values for specific subtrees (e.g. rendering a dark-themed sidebar inside a light-themed application).
  Key Terms (Bold): `**provider nesting**`, `**closest provider resolution**`, `**subtree override**`, `**lexical context scoping**`.
  Resolution: Consumers always resolve values from the nearest matching ancestor provider.

### Glossary
- **React Context**: A mechanism for sharing values across the component tree without explicitly passing props through every layer.
- **use() API**: A React 19 function that consumes resources like Context and Promises, with the unique ability to be called conditionally.
- **Prop Drilling**: The maintenance antipattern of passing props through intermediate components that do not need them.
- **Context Provider**: A component (`<Context value={...}>`) that supplies a context value to its descendant subtree.
- **Default Context Value**: The fallback value passed into `createContext(defaultValue)` returned when no provider is found.
- **Ambient Data**: Broad, application-wide data (like themes or authentication) relevant to many components across the application.

### Summary

**React 19 Context Invariants**

In daily production, React Context teleports ambient data across deep component hierarchies, eliminating prop drilling while preserving clean component interfaces. Here is your streetwise review.

❒ React 19 Context Invariants

1. Use `<Context value={...}>` in React 19.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) You can render `<Context>` directly instead of `<Context.Provider>`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Consumers read from the nearest ancestor provider of that specific context.

2. Read context using `use(Context)`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `use(Context)` replaces `useContext` in React 19.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) `use()` can be invoked conditionally inside `if` statements and loops.

3. Reserve context for ambient, widely shared data.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Excellent for themes, authentication, locale, and routing.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Avoid context for localized props between adjacent parent-child components.

➔ NEVER drill props through more than two intermediate layout components.

➔ ALWAYS provide a sensible default value in `createContext(fallback)`.

➔ IF you need conditional context access THEN **call `use(Context)` inside the branch**.

**DO THIS:** Provide context via `<Context>` and read with `use()`.

```jsx right title="ThemePortal.jsx"
// Clean React 19 provider and consumer
export const Theme = createContext('light');
export default function ThemePortal() {
  return (
    <Theme value="dark">
      <DeepChild />
    </Theme>
  );
}
function DeepChild() {
  const theme = use(Theme);
  return <div className={theme}>Nightly Wire</div>;
}
```

**DO NOT DO THIS:** Never thread courier props through multiple intermediate layers.

```jsx wrong title="Prop-Drilling Anti-Pattern"
// FAILS: Courier props pollute intermediate components!
function Portal({ theme }) { return <Layout theme={theme} />; }
function Layout({ theme }) { return <Section theme={theme} />; }
function Section({ theme }) { return <Card theme={theme} />; }
function Card({ theme }) { return <Badge theme={theme} />; }
```

| ---: | :--- | :--- |
| **Coupling** | Decoupled; intermediates have<br>zero knowledge of data | Tightly coupled; every layer<br>must forward the prop |
| **Refactoring** | Edit provider and consumer;<br>intermediates untouched | Edit every file in the<br>entire component chain |
| **Consumption** | Direct read via `use(Ctx)`<br>with conditional support | Must be passed as arguments<br>down every invocation |
