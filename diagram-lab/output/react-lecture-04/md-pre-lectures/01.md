4. Why does that tenth tag on the screen still show her old name?

### The Fragility of Manual DOM Scripting

On any content website like The National Times, **reader data** appears across many independent sections at once. When a subscriber logs into the site, their name appears in the top navigation greeting, in the subscriber status profile, in the comment box, and in the account drawer. In traditional JavaScript development, keeping all ten locations accurate requires you to write **manual browser commands** for each spot. When the reader renames their account, your script must locate every single HTML element on the page and rewrite its text content by hand.

To understand why this approach fails at scale, consider what that manual script actually looks like in practice. You write selectors such as `document.getElementById('greeting-text')` and `document.querySelector('.header-user')`. You assign the new name directly to the `textContent` property of each element. If your page has ten places showing that name, you write **ten separate queries** and **ten separate property assignments**.

**DO NOT DO THIS:** Never write manual DOM queries, defensive null checks, and imperative property mutations across application scripts.

```javascript wrong title="Manual DOM Script"
function updateReaderName(newName) {
  const greeting = document.getElementById('greeting-text');
  if (greeting) greeting.textContent = `Welcome back, ${newName}`; // **WRONG:** manually queries and mutates each **NODE**
  const subscriber = document.getElementById('subscriber-user');
  if (subscriber) subscriber.textContent = `Subscriber: ${newName}`; // **WRONG:** breaks silently if an **ID** changes
}
```

Notice how fragile this pattern is in practice. The script relies entirely on hardcoded string identifiers like `'greeting-text'` and `'subscriber-user'`. If an HTML designer renames an element ID or moves the subscriber profile into a breaking news header, `document.getElementById` fails silently and returns `null`. Because of the defensive `if (subscriber)` guard clause, the browser does not throw a loud error: it simply skips the mutation. The tenth element is never updated, and no warning appears in the developer console to alert you.

This quiet failure triggers **state drift** (the divergence where computer memory holds the updated data, but the live webpage still renders stale text). The JavaScript variable holds the reader's new name, but the browser DOM remains frozen in the past. To prevent this drift, the programmer is forced to act as a human bookkeeping engine, manually memorizing every DOM node that displays the name and ensuring no update command is ever omitted.

This failure reveals the core problem of **imperative DOM scripting** (the programming style where you write explicit, step-by-step commands instructing the browser exactly how to find and mutate each individual document node). Imperative code acts like a passenger giving **turn-by-turn driving directions**: turn left, drive two hundred meters, turn right, and stop. If the passenger forgets one turn, the car ends up in the wrong neighborhood. In web applications, if your imperative script misses one DOM node, the screen shows incorrect data.

> [!WILD]
> **What does imperative vs declarative really mean?** Imagine a subscriber named Elena logs into The National Times. Her name appears in ten different places across the screen, from the sidebar to the navigation bar. But what happens when she updates her account to use a pen name? In plain JavaScript, you are forced to write manual commands to find and rewrite every single spot. You need to hunt down each and every "name" variable, manually. If you miss in one place, it does not update. This is the problem with **imperative programming**: it is **imperative** to hunt down and update all variables, time and time again. Which, in turn, can lead to many silent failures. This silent failure is exactly why you need the **declarative** component model of React: it eliminates manual DOM hunting to ensure your entire interface stays perfectly synchronized automatically.

### The Declarative Shift

React was created to eliminate this category of bugs entirely. Instead of forcing you to write imperative instructions that manually mutate individual browser elements, React introduces a **declarative programming model** (a design paradigm where you describe what the user interface should look like for a given state, rather than how to manipulate the screen step by step).

> [!KEY]
> In imperative programming you describe how to update; in React you describe what to show.

When you write plain JavaScript DOM code, your script is an instruction manual for the browser: find this node, verify that it exists, overwrite its text, and attach an event listener. React reverses this relationship. Instead of telling the browser how to modify the document over time, you write a function that receives data and returns a **declarative UI description** of the completed interface. You provide the **destination address**, and React handles the underlying browser navigation.

Because your code only describes the finished screen for any given value, there is no list of manual DOM queries to maintain. If the reader's name changes from Elena to her new pen name, you do not hunt down ten DOM elements. You simply supply the new name to React. React evaluates your description, calculates the difference, and updates every visible spot on the screen through **automated state synchronization**.

### Components as Reusable Blueprints

In plain HTML, you structure documents using **native HTML tags** like `<header>`, `<article>`, and `<button>`. However, native HTML tags do not know anything about your **application logic**, your subscriber tiers, or your reader data. Traditionally, developers had to copy and paste chunks of HTML structure across templates and attach separate JavaScript scripts to add behavior.

To solve this fragmentation, React combines markup, style, and logic into a single cohesive structure. This mechanism is called a **component** (a self-contained, reusable JavaScript function that accepts data inputs called **props** and returns markup describing a piece of the user interface).

In React, every component is a standard JavaScript function whose name starts with a capital letter. **Capitalization** is a strict requirement: it tells React that `<SiteHeader />` is your custom component, whereas `<header>` is a built-in browser DOM tag. Components can be **nested** inside one another, allowing you to assemble complex pages out of small, focused building blocks.

To see this in action on The National Times, we can organize our site header into three distinct files. The **parent component** `SiteHeader.jsx` acts as the container. Inside it, we place two specialized **child components**: `ReaderGreeting.jsx`, which renders the welcome message, and `SubscriberInfo.jsx`, which renders the subscriber profile details. Both child components receive `readerName` as an input **prop** from their parent.

```components title="national-times — Component Explorer"
SiteHeader.jsx | readerName="Morgan" | generic | [code: <header className="site-header">] ;; [code:   <ReaderGreeting readerName={readerName} />] ;; [code:   <SubscriberInfo readerName={readerName} />] ;; [code: </header>]
  ReaderGreeting.jsx | readerName="Morgan" | greeting | [code: return <span>Welcome back, {readerName}</span>] ;; Welcome back, **Morgan**
  SubscriberInfo.jsx | readerName="Morgan" | profile | [code: return <p>Subscriber: {readerName}</p>] ;; Subscriber: **Morgan**;; Plan: All-Access
```

The component explorer panel above illustrates this relationship. On the left, the file hierarchy shows `SiteHeader.jsx` containing both `ReaderGreeting.jsx` and `SubscriberInfo.jsx`. On the right, the **rendered canvas** displays the final visual output: the greeting box displays "Welcome back, Morgan", while the subscriber info displays "Subscriber: Morgan" alongside the subscription plan. The reader name "Morgan" flows directly from the parent container into both child components. Neither child queries the DOM; each merely returns a **declarative description** of its own HTML elements.

Let us look closely at how our first child component, `ReaderGreeting.jsx`, receives and projects this data:

```jsx title="ReaderGreeting.jsx"
export default function ReaderGreeting({ readerName }) {
  return (
    <div className="greeting-box">
      <span>Welcome back, {readerName}</span> // Projects reader name directly into **MARKUP**
    </div>
  );
}
```

The component function `ReaderGreeting` receives its input data through a single parameter called **props** (short for properties). Rather than writing `props.readerName` throughout the function body, the signature uses JavaScript **object destructuring** directly inside the parentheses: `({ readerName })`. This unpacks the `readerName` property straight into a local variable. Inside the markup, the curly braces around `{readerName}` establish an **evaluation window** that steps out of static HTML structure and into live JavaScript execution. When React evaluates this component, it reads the current value of `readerName` and projects it straight into the text content of the span, eliminating manual string concatenation and DOM lookups.

Our second child component, `SubscriberInfo.jsx`, follows the same pattern to assemble a subscriber card:

```jsx title="SubscriberInfo.jsx"
export default function SubscriberInfo({ readerName }) {
  return (
    <div className="subscriber-info">
      <p className="user-name">Subscriber: {readerName}</p> // Reflects the current prop **VALUE**
      <p className="user-status">Plan: All-Access</p> // Static metadata stays **UNCHANGED**
    </div>
  );
}
```

The implementation of `SubscriberInfo` demonstrates how dynamic expressions and static markup coexist harmoniously within a single component. The paragraph rendering `{readerName}` recalculates dynamically whenever incoming props change, whereas the adjacent paragraph displaying `Plan: All-Access` remains completely static. React compiles both elements into a single **declarative blueprint**, ensuring that styling and structural scaffolding remain untouched while only the dynamic tokens update in response to fresh data.

With both child components prepared, `SiteHeader.jsx` imports them and assembles the completed site header:

```jsx title="SiteHeader.jsx"
import ReaderGreeting from './ReaderGreeting.jsx';
import SubscriberInfo from './SubscriberInfo.jsx';

export default function SiteHeader({ readerName }) {
  return (
    <header className="site-header">
      <h1>The National Times</h1> // Brand heading declared **STATICALLY**
      <div className="header-actions">
        <ReaderGreeting readerName={readerName} /> // Passes reader name to **GREETING**
        <SubscriberInfo readerName={readerName} /> // Passes same reader name to **SUBSCRIBER**
      </div>
    </header>
  );
}
```

The container `SiteHeader` orchestrates child components through the contract of **prop passing**: `<ReaderGreeting readerName={readerName} />`. Notice the two distinct halves of this JSX attribute. The left side, `readerName=`, defines the property name expected by the child component, while the right side within curly braces, `={readerName}`, supplies the parent component's live variable. Through this downward flow, `SiteHeader` distributes its data cleanly to both child components without either child needing to know where that data originated.

This composition also exposes the foundational distinction between HTML elements and custom React components. When React encounters lowercase tags like `<header>`, `<h1>`, and `<div>`, it instructs the browser engine to instantiate native DOM elements. When it encounters capitalized tags like `<ReaderGreeting />` and `<SubscriberInfo />`, it recognizes custom component functions, invokes them in memory, and stitches their returned UI descriptors into the render tree.

> [!WILD]
> **Why do multi-component screens fall out of sync?** What happens when a shopper clicks "Add to Cart" on a flash sale product? The slide-out drawer pops open and shows 3 items. But what about the checkout counter in the top navigation bar? It still says 2. Why? Because the manual script forgot to update the header counter. One variable in memory, two different numbers on the screen. This is **split-brain state divergence**. React eliminates this headache entirely. Instead of updating elements one by one, you pass the data down from a **single source of truth**. Because every **component** reads from that same **single source of truth**, every section on the screen updates together. Instantly.

### How React Synchronizes the Screen

If our component functions never touch the browser DOM, how does the screen actually change when application data updates? A naive alternative approach would be to destroy the existing container markup and recreate the entire HTML subtree from scratch on every change. However, tearing down physical DOM elements produces catastrophic side effects: active input fields lose **keyboard focus**, ongoing CSS transitions cancel abruptly, and browser performance degrades under continuous layout recalculation.

React avoids this destruction through an intelligent comparison pipeline. When a component executes, React constructs an in-memory tree of lightweight JavaScript objects representing the intended user interface structure, known classically as the **virtual DOM** (and referred to in modern React documentation as a **UI descriptor tree**). When data updates, React runs the component again to produce a new **virtual DOM** tree. It then diffs the new tree against the previous tree through a process called **reconciliation** (the comparison algorithm React uses to compute the minimal set of physical DOM mutations required to bring the screen into alignment).

During reconciliation of our National Times header, React observes that the parent `<header>`, the brand `<h1>`, and the surrounding container elements have identical types and positions. React leaves those physical DOM nodes completely untouched. It surgically patches only the specific **text content nodes** inside `ReaderGreeting.jsx` and `SubscriberInfo.jsx` that reflect the updated `readerName`. Because the physical elements stay in place, your page remains stable, responsive, and free from flickering.

> [!WILD]
> **What is the problem with updating the physical DOM?** Can you imagine a routine update of the DOM while you are typing in a form? The container is destroyed and instantly rebuilt. Remember the blinking cursor that appears when completing a form? Well... it vanishes completely, and your next few keystrokes disappear into thin air. React prevents this frustrating wipeout entirely. Instead of destroying the **physical DOM**, it compares the new updates in memory (the **virtual DOM**) and only touches the real **physical DOM** when changes are absolutely necessary, leaving your active typing perfectly untouched.

> [!TIP]
> **To impress the interviewer:** When asked why declarative UI beats manual DOM scripting, do not just say "it is easier to write." Explain the predictability of state synchronization: manual DOM scripting distributes state across two places, namely your JavaScript variables and the live DOM nodes. React eliminates that split by making the DOM a pure projection of data, so your screen and your data can never drift apart.

### Glossary

- **Declarative Programming**: A programming model where you describe what the user interface should look like for a given state without writing manual step-by-step browser commands.
- **Imperative DOM Scripting**: A programming style where you write explicit, manual instructions commanding the browser how to locate and mutate individual DOM nodes.
- **State Drift**: The divergence where computer memory holds updated data, but the live webpage still renders stale or partial content.
- **Component**: A self-contained, reusable JavaScript function that accepts data inputs called props and returns markup describing a piece of the user interface.
- **Virtual DOM**: An in-memory tree of lightweight JavaScript objects representing the intended user interface structure used by React to calculate differences.
- **Reconciliation**: The comparison algorithm React uses to diff the virtual DOM against the previous render and compute the minimal set of physical DOM mutations.

In daily production, choosing between **imperative DOM manipulation** and **declarative React components** defines how you structure user interfaces.
