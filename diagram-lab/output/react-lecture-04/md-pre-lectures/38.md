### Component Architecture and the Effect Synchronization Cycle
- [p] ◇ {preknowledge:} In earlier lessons, we learned that React components maintain local state using `useState` and synchronize with external systems using `useEffect` (see Lecture 1 and Lecture 28). In an editorial desk, components often need to maintain an active connection to an external service, such as a websocket chat room. {problem:} Developers often assume that effects follow the lifecycle of the host component, mounting once when added to the DOM and unmounting once when removed. ◼ Pedagogical qualification: Ground familiar hook primitives; expose the friction of thinking about effects through component lifecycle categories; terms introduced: **reactive effect**, **external system**, **synchronization cycle**.
- [p] ★ {preknowledge:} Every React component undergoes a standard three-phase lifecycle: it mounts when inserted into the DOM, updates when receiving new props or state, and unmounts when removed from the screen. An effect, however, lives by a different set of rules. An effect does not mount or update; it starts synchronizing and stops synchronizing. {problem:} When a prop such as `roomId` changes from `"general"` to `"politics"`, the component updates, but the effect must stop synchronizing with the old room before starting to synchronize with the new room. ◼ Pedagogical qualification: Contrast component lifecycle phases with effect synchronization phases; introduce the need for paired setup and cleanup.
- [p] What is a **reactive effect**? In standard web development, when you open a connection to an external server with `connection.connect()`, the browser maintains that socket indefinitely. The browser does not know when your application has moved on to a different topic, and it never automatically closes the connection for you. That manual, open-ended connection is the default behavior of the plain web platform. A **reactive effect** changes this relationship completely. In React, you declare an effect by passing a function to `useEffect`, specifying the reactive values it reads in a dependency array. Inside that function, you write the setup code to start synchronizing, and return a cleanup function to stop synchronizing. The law of reactive effects is absolute: React will never run a new setup for changed dependencies without first running the cleanup from the previous render; every single setup is strictly paired with a prior cleanup. ◼ Pedagogical qualification: Execute the default and the law standard; define reactive effects through plain web socket behavior and contrast with React lifecycle guarantees; terms introduced: **reactive effect**, **setup function**, **cleanup function**, **dependency array**.
- [p] Here is the naive connection pattern that treats effects as component mount events, omitting cleanup and causing connection leaks: ◼ Introduces the broken pattern before presenting the correct paired lifecycle.
- [code] Naive connection pattern omitting cleanup:
```jsx title="Zombie Connection Pattern"
function BadChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(roomId); // **SETUP:**<br>Connects to server on mount
    connection.connect(); // **LEAK:**<br>Never disconnects when roomId changes or component unmounts
  }, [roomId]);
  return <h2>Active Room: {roomId}</h2>;
}
```
◼ **The what-this-introduces list:** 1. `createConnection(roomId)`: External socket factory. 2. `connection.connect()`: Imperative connection trigger. 3. Omission of cleanup callback: Causes zombie socket accumulation when `roomId` changes.
- [grounding] the opening question: Why does an effect clean up before re-running?
  the friction it clears: why React runs cleanup while the component is still visible on the screen.
  Scene & Repetition: Imagine checking into a hotel room. You enter room one hundred and unpack your clothes into the wardrobe. Later, the front desk calls and upgrades you to room two hundred. Do you leave your clothes scattered across room one hundred and start unpacking fresh clothes into room two hundred? Of course not. If you did, you would have your belongings split across two rooms at once. First, you pack your bags and check out of room one hundred. Only then do you enter room two hundred and unpack. In React, a **reactive effect** works the exact same way. When `roomId` changes, React checks out of the old room by running the **cleanup function**. Then it checks into the new room by running the new **setup function**. This strict sequence guarantees you never have two active connections open at the same time.
  Key Terms (Bold): **reactive effect**, **cleanup function**, **setup function**, **dependency array**.
  Resolution: React runs the cleanup function before every re-setup to ensure external resources are cleanly released before new ones are acquired.

### The Exact Synchronization Sequence: Cleanup Before Re-Setup
- [p] ◇ {preknowledge:} To understand why React executes cleanup before re-setup, we must trace the exact sequence of events during a dependency transition. A dependency change is not a simple function call; it is an orchestrated three-step sequence. {problem:} Without understanding this sequence, developers are baffled by console logs showing cleanup running with old prop values while the screen already displays new prop values. ◼ Pedagogical qualification: Frame the three-step sequence of effect re-synchronization; prepare the reader for closure mechanics.
- [p] ★ {preknowledge:} Consider what happens when the user clicks the `# politics` button while currently connected to `# general`. First, React updates the `roomId` state in `ChatWorkspace` and re-renders the component tree. Second, React commits the changes to the DOM: the screen now paints the new title "Channel: #politics". Third, before running the new effect, React calls the cleanup function returned during the *previous* render. That cleanup function closed over `roomId = "general"`, so it disconnects cleanly from `# general`. Fourth, React runs the effect setup function for the current render. That setup function closes over `roomId = "politics"`, connecting to the new channel. {problem:} If setup ran before cleanup, both connections would exist concurrently, causing race conditions and state corruption. ◼ Pedagogical qualification: Detail the exact four-beat re-synchronization timeline; highlight how closures preserve old values for cleanup.
- [p] What happens in React 19 development with Strict Mode? When your component first mounts in development, React intentionally mounts the component, runs setup, runs cleanup immediately, and then runs setup a second time. Why? To prove that your cleanup function completely undoes whatever your setup function did. If your cleanup function is missing or incomplete, the second setup exposes the bug immediately during development before it reaches production users. ◼ Explains Strict Mode double-invocation rationale in plain CEFR B2 English.
- [grounding] the opening question: Why does cleanup see the old prop value?
  the friction it clears: why the cleanup function still sees "general" when the component has already updated to "politics".
  Scene & Repetition: Imagine you write a letter, place it inside an envelope, and seal it shut. Inside that envelope, you wrote: "Please lock door number ten." Ten minutes later, you move to room twenty. Does moving to room twenty magically rewrite the letter inside the sealed envelope? Of course not. The sealed envelope still says: "Please lock door number ten." In JavaScript, a **cleanup function** is like that sealed envelope: it is a **closure**. When React created the cleanup function during the first render, it captured the old prop value `roomId = "general"`. When React opens that envelope during the next render, it executes the instructions inside: it disconnects from `"general"`, not `"politics"`. This **closure capture** guarantees that cleanup always cleans up the exact resource that was opened.
  Key Terms (Bold): **closure**, **cleanup function**, **reactive prop**, **lexical scope**.
  Resolution: Cleanup functions close over the props and state from the render in which they were defined, ensuring they always release the exact resource created by that render.

### Glossary
- [definition] **Reactive Effect**: An effect declared with `useEffect` that synchronizes an external system with current props and state, re-running whenever its declared dependencies change.
- [definition] **Effect Lifecycle**: The independent lifecycle of an effect, consisting solely of starting synchronization via setup and stopping synchronization via cleanup, distinct from component mounting.
- [definition] **Cleanup Function**: A callback returned by an effect setup function that releases resources, cancels subscriptions, and disconnects sockets created during that synchronization cycle.
- [definition] **Dependency Array**: The second argument to `useEffect`, listing all reactive values (props, state, and derived variables) read inside the effect to tell React when to re-synchronize.
- [definition] **Strict Mode Re-synchronization**: React development behavior that executes setup, cleanup, and setup on initial mount to verify that effect cleanup routines completely undo setup actions.

### Summary
- [review-title] **The Lifecycle of a Reactive Effect in React 19**
- [p] In production applications, understanding the independent lifecycle of reactive effects prevents zombie connections, memory leaks, and out-of-sync external systems. Here is your streetwise review.
- [review-subtitle] ❒ Core Principles of Effect Synchronization
- [numbered-review-point] 1. Think of effects as **synchronization cycles**, not component lifecycles.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Components mount, update, and unmount; effects start synchronizing and stop synchronizing.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) An effect may start and stop synchronization dozens of times while its host component remains continuously mounted.
- [numbered-review-point] 2. React **always runs cleanup before re-setup** when dependencies change.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Before connecting to the new dependency, React calls the cleanup function from the previous render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Closure capture ensures the cleanup function accesses the exact props and state from the render that created it.
- [numbered-review-point] 3. Every setup must have a **mirror cleanup function** that completely reverses it.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) If setup connects, cleanup must disconnect; if setup subscribes, cleanup must unsubscribe.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Strict Mode in development tests this symmetry by running setup, cleanup, and setup immediately on mount.
- [never-rule] ➔ NEVER assume an effect only cleans up when the component leaves the screen.
- [always-rule] ➔ ALWAYS return a cleanup function from effects that open connections, subscriptions, or timers.
- [if-then-rule] ➔ IF an effect reads a reactive prop or state variable THEN **include it in the dependency array to trigger timely re-synchronization**.
- [do-this-header] **DO THIS:** Return a mirror cleanup function that reverses setup and cleanly releases external resources.
- [do-this-code] Resilient effect lifecycle pattern:
```jsx right title="Resilient Effect Pattern"
function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect();
    return () => {
      connection.disconnect(); // cleans up old channel before next setup
    };
  }, [roomId]);
  return <h2>Room: #{roomId}</h2>;
}
```
- [do-not-do-this-header] **DO NOT DO THIS:** Never omit cleanup or treat effects as mount-only routines when dependencies change.
- [do-not-do-this-code] Leaky effect anti-pattern:
```jsx wrong title="Leaky Effect Pattern"
function LeakyChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect(); // leaks old connection when roomId changes
  }, [roomId]); // missing cleanup leaves zombie sockets active
  return <h2>Room: #{roomId}</h2>;
}
```
