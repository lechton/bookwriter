### Adding Event Handlers: Passing Functions Versus Calling Functions
- [p] ◇ {preknowledge:} In earlier lessons, we learned that React components are JavaScript functions that return JSX markup (see Lecture 3). We also saw that component rendering must remain completely pure and free of side effects (see Lecture 13). In plain HTML, you attach interactivity by writing string attributes directly into your markup, such as `<button onclick="alert('clicked')">`. In that plain web world, the browser evaluates that string as global JavaScript code whenever a click occurs. When you move to React, writing a string attribute fails completely: JSX requires real JavaScript functions wrapped in curly braces (see Lecture 5). {problem:} Developers transitioning from plain HTML often write parentheses after their function names inside JSX props, expecting the handler to wait for a user click, only to watch their function execute immediately during the render pass. ◼ Grounding the move from plain HTML string handlers to React function references; terms introduced: **event handler**, **render function**.
- [p] What is an **event handler**? React draws a strict boundary between two distinct parts of your component: the **render function**, which calculates JSX markup, and the **event handler**, which responds to user interactions. In normal HTML, an element handles its own inline events through string attributes: when you write `onclick="handleClick()"`, the browser's native engine waits until the user physically clicks before evaluating the script string, and no JavaScript framework is involved. Leave event handling in that plain world and functions sit in global browser scope. In React, you take that control into your component: you write `<button onClick={handleClick}>`. The button is now bound to a real function reference: it can only execute when the user physically clicks or types, and React guarantees that the handler never runs during rendering. The law of event handlers states: you must always pass an event handler function as a reference without parentheses; calling the function with parentheses executes it immediately during render, which violates component purity and can trigger infinite re-render loops. ◼ Full definition of event handler following the default and the law standard; establishes the distinction between passing a reference and calling during render.
- [p] ★ {preknowledge:} In plain JavaScript DOM scripting, you query a button node and attach a listener with `addEventListener('click', handler)` (see Lecture 1). In React, you pass the handler directly as a prop using camelCase naming, such as `onClick`, `onChange`, or `onKeyDown`. Now consider the physical difference between passing a reference and calling a function. When you write `onClick={handleClick}`, you hand React a pointer to the function: React holds the reference in memory and invokes it only when the browser registers a physical click event. But if you write `onClick={handleClick()}`, the JavaScript engine evaluates `handleClick()` right at that moment, during the render pass, and assigns the return value (usually `undefined`) to `onClick`. {problem:} The handler executes before the user ever touches the keyboard or mouse, and when the user actually clicks, nothing happens because `onClick` is `undefined`. ◼ Explains the physical execution consequence of the parenthesis trap under the h-e-l-l-o tactile standard.
- [code] Legacy string and parenthesis anti-patterns:
```jsx title="EventBindingMistakes"
// {old solution:} plain HTML string and parenthesis mistakes
// <button onclick="handleClick()">Read</button> (HTML string)
export default function BrokenArticle({ headline }) {
  function openStory() {
    console.log('Story opened:', headline);
  }
  // **WRONG:** calling openStory() executes during render
  return <button onClick={openStory()}>Read Headline</button>;
}
```
◼ **The what-this-introduces list:** 1. `BrokenArticle`: component demonstrating the parenthesis trap. 2. `openStory()`: function call invoked prematurely during render. 3. `onClick`: React event prop receiving the return value `undefined`.
- [p] ★ {preknowledge:} To fix this premature execution, you pass the function name bare: `onClick={openStory}`. If your handler needs arguments, such as an article identifier, you wrap the call inside an inline arrow function: `onClick={() => openStory(story.id)}`. The arrow function acts as a wrapper: React stores the arrow function in memory, and the inner call runs only when the user clicks. ◼ Explains how to pass parameters safely using inline arrow functions.
- [code] Correct function reference binding:
```jsx title="CorrectEventBinding"
export default function SafeArticle({ story }) {
  function openStory(id) {
    console.log('Story opened:', id);
  }
  // **RIGHT:** passing arrow function delays execution until click
  return <button onClick={() => openStory(story.id)}>Read Story</button>;
}
```
◼ **The what-this-introduces list:** 1. `SafeArticle`: component demonstrating safe parameter passing. 2. `() => openStory(story.id)`: inline arrow function holding execution until click. 3. `onClick`: event prop receiving a valid function reference.
- [grounding] the opening question: Why do parentheses break your click handler?
  the friction it clears: why adding parentheses executes code during render instead of waiting for a click.
  Scene & Repetition: Imagine hiring a messenger to deliver a letter whenever a newsroom bell rings. You give the messenger instructions: "Deliver this letter when the bell rings." That is passing a **function reference**: the messenger waits patiently until the bell sounds. Now imagine walking up to the messenger, handing them the letter, and immediately shouting "Deliver this letter now!" That is calling a **function with parentheses**. The messenger runs out the door instantly, before the bell ever rings! When the bell finally rings later, the messenger is already gone and nothing happens. In React, writing `onClick={handleClick}` gives React the instructions to wait for a user action. Writing `onClick={handleClick()}` executes the function during **render**, long before any user clicks.
  Key Terms (Bold): **function reference**, **event handler**, **render**.
  Resolution: Passing a bare function reference ensures that event handlers execute exclusively when the user interacts, keeping rendering pure and predictable.

### The SyntheticEvent Object: Reading Event Details and Input Values
- [p] ◇ {preknowledge:} In plain JavaScript, when an event listener fires, the browser passes an `Event` object containing details such as mouse coordinates, pressed keys, and the target element. However, different web browsers historically implemented event properties differently: Internet Explorer used `window.event`, older versions of Firefox handled mouse coordinates differently than Safari, and event propagation methods varied across operating systems. {problem:} Developers historically spent countless hours writing defensive browser-sniffing code to ensure identical event behavior across platforms. ◼ Grounding the historical browser fragmentation problem and introducing React's standardization solution; terms introduced: **SyntheticEvent**, **native browser event**.
- [p] What is a **SyntheticEvent**? React distinguishes between two kinds of event objects: the **native browser event**, created directly by the browser engine, and the **SyntheticEvent**, the standardized cross-browser wrapper created by React. In normal DOM scripting, when a user clicks or types, the browser produces a native `MouseEvent` or `InputEvent` whose properties and behavior depend on the underlying browser engine. In React, your event handler never receives the raw browser event directly: React intercepts the event at the root and wraps it in a **SyntheticEvent**. The law of SyntheticEvent states: every React event handler receives a SyntheticEvent instance that exposes the exact same interface across Chrome, Safari, Firefox, and mobile browsers; you can read event properties like `e.target.value` and call methods like `e.stopPropagation()` and `e.preventDefault()`, and React guarantees identical behavior regardless of the user's browser or operating system. ◼ Full definition of SyntheticEvent following the default and the law standard; establishes the cross-browser wrapper contract.
- [p] ★ {preknowledge:} When responding to user typing, an input element fires an event on every keystroke. In plain HTML, typing a letter dispatches an `input` event on the physical DOM node. In React, you listen to typing using the camelCase prop `onChange`. Inside the handler, React passes the SyntheticEvent object, conventionally named `e`. To read what the user typed, you inspect `e.target.value`. The property `e.target` refers to the physical DOM element that dispatched the event (the `<input>`), and `.value` holds the current string of text inside that input box. When listening to keyboard events like pressing Enter, you use `onKeyDown` and inspect `e.key`. ◼ Explains how to capture typing and keyboard events via SyntheticEvent properties.
- [code] Reading event details from SyntheticEvent:
```jsx title="SyntheticEventDemo"
export default function SearchField() {
  function handleType(e) {
    console.log('Typed text:', e.target.value); // reads input value
  }
  function handleKeyDown(e) {
    if (e.key === 'Enter') console.log('Submitted search'); // reads key
  }
  return <input onChange={handleType} onKeyDown={handleKeyDown} />;
}
```
◼ **The what-this-introduces list:** 1. `handleType`: change handler reading input text. 2. `e.target.value`: SyntheticEvent property pointing to typed content. 3. `handleKeyDown`: keydown handler checking `e.key === 'Enter'`. 4. `<input onChange=... />`: host element binding both handlers.

  Key Terms (Bold): **SyntheticEvent**, **native browser event**, **target**.
  Resolution: The SyntheticEvent provides a predictable, standardized interface that shields developers from cross-browser discrepancies.

### Stopping Event Propagation Versus Preventing Default Browser Behavior
- [p] ◇ {preknowledge:} Beginners frequently confuse two methods on the event object: `e.stopPropagation()` and `e.preventDefault()`. Because both methods contain the word "stop" or "prevent", developers often treat them as interchangeable or call both in every handler out of superstition. In web standards, however, these two methods solve completely different problems. {problem:} Calling the wrong method either fails to stop unwanted parent clicks or fails to prevent browser navigations, leaving applications buggy and vulnerable to page reloads. ◼ Introduces the confusion between propagation and default behavior; terms introduced: **event propagation**, **default behavior**.
- [p] What is the difference between **event propagation** and **default behavior**? React follows the W3C DOM event specification, which defines two independent browser mechanisms: (a) **event propagation** (bubbling), where an event travels upward through the component tree, and (b) **default behavior**, where the browser executes a built-in action in response to an event (such as submitting a form, navigating to a link URL, or checking a checkbox). When you call `e.stopPropagation()`, you halt the upward travel of the event: parent components will not hear the event, but the browser will still execute any native default action. When you call `e.preventDefault()`, you cancel the browser's native default action (such as preventing a `<form>` from reloading the page or an `<a>` tag from navigating), but the event continues bubbling upward through the component tree! The law of event control states: `e.stopPropagation()` stops the event from traveling to parent components, while `e.preventDefault()` stops the browser from executing its native action; neither method performs the job of the other. ◼ Full definition of both mechanisms following the default and the law standard.
- [code] Symmetrical comparison between stopPropagation and preventDefault:
```jsx title="PropagationVsDefault"
function NestedLink({ onCardClick }) {
  function handleLinkClick(e) {
    e.preventDefault(); // cancels browser navigation; click STILL BUBBLES to card
    e.stopPropagation(); // cancels bubbling; click DOES NOT REACH onCardClick
    console.log('Handled custom client navigation');
  }
  return <a href="/story/42" onClick={handleLinkClick}>Read Story</a>;
}
```
◼ **The what-this-introduces list:** 1. `handleLinkClick`: handler demonstrating both methods. 2. `e.preventDefault()`: cancels native link navigation. 3. `e.stopPropagation()`: halts upward bubbling to parent elements.

### Glossary
- [glossary] **Event Handler**: A JavaScript callback function passed as a prop to a JSX element to respond to user interactions such as clicks, typing, or keypresses.
- [glossary] **SyntheticEvent**: React's cross-browser wrapper around the native browser DOM event, providing a standardized interface across all browsers.
- [glossary] **Event Propagation (Bubbling)**: The natural process where a DOM event travels upward from the target element through all its ancestor components in the tree.
- [glossary] **stopPropagation**: A method on the SyntheticEvent that halts event bubbling, preventing ancestor components from receiving the event.
- [glossary] **preventDefault**: A method on the SyntheticEvent that cancels the browser's native default action, such as preventing form submission page reloads.
- [glossary] **Inline Handler**: An event handler defined directly inside JSX using an arrow function, useful for passing custom arguments to callbacks.

Use **SyntheticEvent** to inspect user interactions across all browsers.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Read input text with `e.target.value` inside `onChange` handlers for typing events.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Inspect pressed keys with `e.key` inside `onKeyDown` handlers for keyboard navigation.
- [numbered-review-point] 3. Distinguish between **stopPropagation** and **preventDefault**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Use `e.stopPropagation()` to prevent nested child clicks from triggering parent container handlers.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use `e.preventDefault()` to cancel native browser actions like link navigation or form reloads.
- [never-rule] ➔ NEVER call an event handler with parentheses directly inside a JSX prop unless wrapped in an arrow function.
- [always-rule] ➔ ALWAYS call `e.stopPropagation()` on nested buttons inside clickable cards to prevent accidental parent actions.
- [if-then-rule] ➔ IF an event handler requires custom arguments THEN **wrap the invocation in an inline arrow function: `onClick={() => handleSelect(item.id)}`**.
- [do-this-header] **DO THIS:** Pass function references or wrap parameterized calls in inline arrow functions.
- [do-this-code] Safe event binding patterns:
```jsx right title="Safe Event Handling Pattern"
export default function ArticleActions({ story, onSelect }) {
  function handleBookmark(e) {
    e.stopPropagation();
    saveBookmark(story.id);
  }
  return (
    <div onClick={() => onSelect(story.id)}>
      <h3>{story.title}</h3>
      <button onClick={handleBookmark}>Bookmark</button>
    </div>
  );
}
```
- [do-not-do-this-header] **DO NOT DO THIS:** Never call functions during render or omit stopPropagation on nested buttons.
- [do-not-do-this-code] Broken event binding anti-patterns:
```jsx wrong title="Broken Event Handling Pattern"
export default function BrokenActions({ story, onSelect }) {
  return (
    <div onClick={onSelect(story.id)}>
      <h3>{story.title}</h3>
      <button onClick={() => saveBookmark(story.id)}>Bookmark</button>
    </div>
  );
}
```
