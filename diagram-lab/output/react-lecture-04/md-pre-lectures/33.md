### Anti-Pattern 1: Transforming Data for Rendering
- [p] ◇ {preknowledge:} In early React code, newcomers often use `useEffect` as an automatic watch-dog to update one state variable whenever another changes—such as updating `total` whenever `items` change. {problem:} Why is updating state inside an Effect to compute derived data a major performance and architectural bug? ◼ Pedagogical qualification: Expose the cascading double-render penalty; terms introduced: **cascading render**, **redundant effect**, **render-time derivation**.
- [p] ★ {preknowledge:} When you update state inside an Effect:
  1. React runs the component and renders the DOM with old/stale state.
  2. The browser paints the screen with stale values.
  3. React executes `useEffect` and calls `setTotal(...)`.
  4. React is forced to re-run the entire component a second time and repaint!
  This creates an **extra render pass**, degrades performance, and causes visual flicker. Instead, **calculate derived values on the fly during render**. Because render code executes synchronously, the calculation is instant, perfectly synchronized, and causes zero extra renders. If the calculation is computationally heavy, cache it with `useMemo`. ◼ Pedagogical qualification: Deconstruct the double-render penalty and teach render-time calculation; terms introduced: **double-render waterfall**, **visual flicker**, **instant synchronization**, **useMemo**.
- [code] Redundant effect vs render-time derivation:
```jsx title="Transforming Data: Effect vs Derivation"
// BAD: Extra render pass, flashes stale total to the user:
const [total, setTotal] = useState(0);
useEffect(() => {
  setTotal(items.reduce((sum, i) => sum + i.fee, 0));
}, [items]);
// GOOD: Instant, synchronous, zero extra render passes:
const total = items.reduce((sum, i) => sum + i.fee, 0);
```
- [grounding] Leading Question: What about caching expensive calculations?
  Confusion Point: If a calculation takes noticeable time, should we move it to `useEffect`?
  Scene & Repetition: No! Moving an expensive calculation to `useEffect` still runs the calculation, but adds an extra render cycle on top! If a calculation is genuinely slow (e.g. searching thousands of rows), keep it in render and wrap it in `useMemo`: `const total = useMemo(() => computeSlowTotal(items), [items])`. It stays derived and avoids duplicate render passes.
  Key Terms (Bold): `**useMemo memoization**`, `**render efficiency**`, `**caching vs synchronization**`, `**pure computation**`.
  Resolution: Use `useMemo` for expensive computations; never declare separate state and sync it with `useEffect`.

### Anti-Pattern 2: Handling User Actions in Effects
- [p] ◇ {preknowledge:} We know data transformations belong in render. {problem:} Why is triggering user actions or mutations (like submitting forms or posting analytics) in `useEffect` dangerous? ◼ Pedagogical qualification: Contrast event handlers with effects for user intent; terms introduced: **user event handling**, **mutation in effect**, **duplicate execution risk**.
- [p] ★ {preknowledge:} Consider an editor clicking "Approve Payout". If you set `const [approved, setApproved] = useState(false)` in `onClick` and run `useEffect(() => { if (approved) api.post('/payout'); }, [approved])`, the mutation is detached from the user event. If the component remounts (or in StrictMode), the effect might re-run and **submit duplicate financial transactions**! ◼ Pedagogical qualification: Explain why mutations in effects cause duplicate requests; terms introduced: **detached mutation**, **duplicate transaction bug**, **accidental re-execution**.
- [p] ★ {preknowledge:} Code that runs because the user performed a specific action belongs directly in the **event handler**, not in `useEffect`. Event handlers know the exact user intent; Effects only know that state changed. Reserve Effects strictly for code that must run **regardless of which interaction caused the state change** (such as syncing a document title or keeping a socket connected). ◼ Pedagogical qualification: Formulate the Event Handler vs Effect rule; terms introduced: **event handler responsibility**, **user intent encapsulation**, **external system boundary**.
- [code] Event handler vs effect mutation:
```jsx title="User Events: Effect vs Handler"
// BAD: Detached effect risks duplicate network requests on remount:
function BadBtn() {
  const [sent, setSent] = useState(false);
  useEffect(() => { if (sent) api.post('/payout'); }, [sent]);
  return <button onClick={() => setSent(true)}>Approve</button>;
}
// GOOD: Event handler directly executes user-initiated action:
function GoodBtn() {
  function handleApprove() { api.post('/payout'); }
  return <button onClick={handleApprove}>Approve</button>;
}
```
- [grounding] Leading Question: How do you reset all component state when a prop changes?
  Confusion Point: Don't you need `useEffect(() => { resetForm(); }, [userId])` to clear form state?
  Scene & Repetition: No! Instead of watching `userId` in an effect to imperatively reset fields, pass a `key` to the child component: `<PayoutForm key={userId} />`. When `userId` changes, React automatically unmounts the old instance and mounts a fresh one with initial state! Zero effect code, zero bugs, zero stale renders.
  Key Terms (Bold): `**key-driven reset**`, `**declarative unmounting**`, `**zero-effect reset**`, `**state re-initialization**`.
  Resolution: Use the `key` attribute to reset state when an entity changes, eliminating imperative reset effects.

### Step 1: First, we construct the container PayoutAuditor.jsx
- [p] ★ {preknowledge:} The container manages accepted articles and computes total payout during render. {problem:} The container must prove that total requires zero useState or useEffect. ◼ Pedagogical qualification: Construct container computing derived state during render.
- [code] Container PayoutAuditor.jsx:
```jsx title="PayoutAuditor.jsx"
import { useState } from 'react';
import PayoutSummary from './components/PayoutSummary.jsx';
import ApproveButton from './components/ApproveButton.jsx';
const ITEMS = [{ id: 1, fee: 350 }, { id: 2, fee: 400 }];
export default function PayoutAuditor() {
  const [articles] = useState(ITEMS);
  const total = articles.reduce((sum, a) => sum + a.fee, 0);
  return (
    <div className="auditor-box">
      <PayoutSummary total={total} count={articles.length} />
      <ApproveButton total={total} />
    </div>
  );
}
```
- [p] ★ Step 1 establishes render-time derivation: Look at line 7: `const total = articles.reduce(...)`. Notice there is NO `useEffect` or `setTotal`. The calculation runs synchronously during render. We will build `PayoutSummary` next in step 2. ◼ Pedagogical qualification: Deconstruct render-time calculation without effects.

### Step 2: Next, we declare the summary child PayoutSummary.jsx
- [p] ★ {preknowledge:} Step 1 computed `total` and passed it to `PayoutSummary`. {problem:} The child component must display the derived values. ◼ Pedagogical qualification: Build display child receiving derived props.

- [p] ★ Step 2 fulfills the summary role: Look at line 6: `PayoutSummary` displays `${total}`. Because the calculation happened in render, the displayed total is always fresh and never flashes stale data. ◼ Pedagogical qualification: Deconstruct synchronized summary display.

### Step 3: Then, we declare the button child ApproveButton.jsx
- [p] ★ {preknowledge:} `ApproveButton` handles payment authorization. {problem:} The button must perform the action in `onClick`, not in an effect. ◼ Pedagogical qualification: Build action button executing mutation in event handler.
- [code] Button child ApproveButton.jsx:
```jsx title="ApproveButton.jsx"
import { useState } from 'react';
export default function ApproveButton({ total }) {
  const [msg, setMsg] = useState(null);
  function handleApprove() {
    setMsg(`Disbursed $${total}`);
  }
  return (
    <div className="approve-action">
      <button onClick={handleApprove}>Authorize Disbursement</button>
      {msg && <p className="success-banner">{msg}</p>}
    </div>
  );
}
```
- [p] ★ Step 3 completes handler-driven execution: Look at line 4: `function handleApprove()`. The approval mutation runs in direct response to the click event. There is no `useEffect` watching state flags, eliminating duplicate submission risks. ◼ Pedagogical qualification: Deconstruct direct event handler execution.
- [p] What would happen if we used an effect to watch an approval flag instead? If we used `useEffect(() => { if (approved) submit(); }, [approved])`, the network call would fire asynchronously after commit. In StrictMode or upon remounting, the effect could execute again, submitting duplicate payouts and creating accounting discrepancies. ◼ Pedagogical qualification: Apply Negative Counterfactual Law to effect-based mutations.

- [grounding] Leading Question: When DO you genuinely need an Effect?
  Confusion Point: If so many things don't need effects, what IS useEffect actually for?
  Scene & Repetition: You need an Effect if and only if you must synchronize your component with an **external system** that does not know about React: WebSockets, browser geolocation, window resize listeners, custom canvas rendering, or imperative third-party plugins. If code only involves React state and props, you do not need an Effect!
  Key Terms (Bold): `**genuine effect use cases**`, `**external system boundary**`, `**React-only logic**`, `**browser API synchronization**`.
  Resolution: An Effect is required only to synchronize with external systems; all internal React state logic belongs in render or event handlers.
- [callout] > [!TIP]
**To impress the interviewer:** Cite the three golden rules of "You Might Not Need an Effect":
1. **Transforming data for rendering?** Calculate it during render (derived state); do not put it in an effect.
2. **Handling user interaction?** Put the logic directly in the event handler; do not watch a state flag in an effect.
3. **Resetting state on prop change?** Pass a `key` to the component; do not write an effect that calls state setters.

### Where you will meet this
- Filtered lists and search tables: calculating filtered results during render instead of in an effect.
- Form submissions: firing API calls directly in `onSubmit` instead of setting `isSubmitting` and watching it in `useEffect`.
- Entity viewers: passing `key={articleId}` to reset editing state when switching articles.
- Shopping cart totals: calculating discounts and sales tax directly during render.

### Glossary
- **Derived Calculation**: A value computed synchronously during render from existing props and state without `useState` or `useEffect`.
- **Double-Render Waterfall**: The performance defect where an effect updates state immediately after render, forcing an unnecessary second render pass.
- **Event Handler Action**: Code executed directly in response to a user gesture (click, submit, change).
- **Key-Driven Reset**: Using React's `key` attribute to recreate a component tree and cleanly reset all state.
- **Redundant Effect**: An unnecessary `useEffect` call used for operations that should be handled during render or in event handlers.
- **Visual Tearing**: A momentary screen flash where the user sees outdated or contradictory state before an effect runs.

### Summary

**React 19 You Might Not Need an Effect Invariants**

In daily production, pruning unnecessary effects eliminates double-render waterfalls and prevents duplicate mutations. Here is your streetwise review.

❒ No-Effect Invariants

1. Calculate derived data during render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) If a value can be computed from props or state, calculate it on the fly.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Storing it in state and updating it in an effect forces an unnecessary second render pass.

2. Run user interaction logic in event handlers.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Form submissions, analytics, and mutations belong directly in `onClick` or `onSubmit`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Watching state flags in effects risks duplicate mutations when components remount.

3. Reset state on prop changes with keys.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Pass `key={userId}` to reset a child component's internal state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) React unmounts the old instance and mounts a fresh one automatically.

➔ NEVER use `useEffect` to copy props into state or compute derived values.

➔ ALWAYS execute user-initiated actions directly inside event handlers.

➔ IF you need to reset all component state when an ID changes THEN **pass a key prop**.

**DO THIS:** Calculate derived values synchronously during render.

```jsx right title="PayoutAuditor.jsx"
// Clean render-time derivation without useEffect
export default function PayoutAuditor({ articles }) {
  const total = articles.reduce((sum, a) => sum + a.fee, 0);
  return <div>Total Payout: ${total}</div>;
}
```

**DO NOT DO THIS:** Never synchronize derived data via state and useEffect.

```jsx wrong title="Redundant-Effect Anti-Pattern"
// FAILS: Forces an extra render pass and flashes stale numbers!
export default function BrokenAuditor({ articles }) {
  const [total, setTotal] = useState(0);
  useEffect(() => {
    setTotal(articles.reduce((sum, a) => sum + a.fee, 0));
  }, [articles]);
  return <div>Total Payout: ${total}</div>;
}
```

| ---: | :--- | :--- |
| **Render cycles** | Exactly 1 render pass;<br>synchronous and instant | 2 render passes; first render<br>paints stale state |
| **Visual stability** | Zero flicker; UI always matches<br>current props and state | Visual tearing; values flash<br>before effect executes |
| **Mutation safety** | Event handlers execute once<br>per user click | Effects risk re-running on<br>remounts and StrictMode |
