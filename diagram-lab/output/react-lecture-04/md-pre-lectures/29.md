### When State Logic Outgrows useState
- [p] ◇ {preknowledge:} In simple components, `useState` is concise and sufficient. As features grow, components often accumulate 5 to 8 separate state variables that frequently change together in response to a single event. {problem:} Why does coordinating multiple `useState` setters across many event handlers lead to brittle code? ◼ Pedagogical qualification: Contrast independent useState with multi-field state machines; terms introduced: **setter sprawl**, **partial state update**, **state machine**.
- [p] ★ {preknowledge:} When multiple state variables change in tandem, every event handler must remember to invoke every corresponding setter. If one handler updates `status` but forgets to clear `error` or increment `revisions`, the component enters an **impossible or corrupted state**. Furthermore, business rules are duplicated across handlers, making the logic difficult to audit or refactor. ◼ Pedagogical qualification: Diagnose the failure mode of scattered useState calls; terms introduced: **impossible state**, **setter duplication**, **business rule fragmentation**.
- [p] ★ {preknowledge:} You should migrate from `useState` to `useReducer` when:
  1. Multiple state values change together in response to user actions.
  2. The next state depends on multiple previous state values.
  3. You want to extract and unit-test your state logic outside of React's rendering tree.
  4. Complex state transitions benefit from an explicit audit log of dispatched actions. ◼ Pedagogical qualification: Establish the 4 criteria for choosing useReducer; terms introduced: **useReducer hook**, **state machine consolidation**, **external unit testing**, **transition auditability**.
- [code] Scattered useState vs useReducer:
```jsx title="Scattered useState vs useReducer"
// FRAGILE: Handlers must manually orchestrate 3 separate setters:
function handlePublish() { setStatus('published'); setError(null); setRev(r => r + 1); }
// CONSOLIDATED: Event handler simply dispatches what happened:
function handlePublish() { dispatch({ type: 'published' }); }
// Pure reducer outside component owns ALL transition rules:
function editorReducer(state, action) {
  if (action.type === 'published') return { ...state, status: 'published', error: null, rev: state.rev + 1 };
  return state;
}
```
- [grounding] Leading Question: Is useReducer only for large, complex enterprise applications?
  Confusion Point: Should you default to `useReducer` for all state to be safe?
  Scene & Repetition: No! For independent state variables (like a text input string, a boolean toggle, or a counter), `useState` is simpler, cleaner, and less verbose. Only reach for `useReducer` when state variables are interdependent or when state transitions become difficult to follow across multiple handlers.
  Key Terms (Bold): `**independent state**`, `**co-located simplicity**`, `**state interdependence**`, `**boilerplate overhead**`.
  Resolution: Use `useState` for independent values; use `useReducer` when state values change together or have complex transitions.

### Reducer Architecture: Actions and Pure Functions
- [p] ◇ {preknowledge:} We know `useReducer` centralizes state updates. {problem:} How should actions and reducer functions be structured to maintain a clean architecture? ◼ Pedagogical qualification: Teach action design and pure function constraints; terms introduced: **action object**, **pure reducer**, **dispatch**.
- [p] ★ {preknowledge:} The reducer function follows a strict signature: `(state, action) => nextState`. It must be a **pure function**: given the same state and action, it must return the exact same next state without mutating arguments, making network calls, or generating random numbers. Reducers must perform **immutable updates**, returning a new object reference rather than modifying the existing state object. ◼ Pedagogical qualification: Explain pure reducer function contracts; terms introduced: **pure function**, **immutable update**, **nextState signature**.
- [p] ★ {preknowledge:} Action objects should describe **what happened in user terms**, not how the state should be updated. For example, dispatch `{ type: 'headline_submitted' }` rather than `{ type: 'set_headline_and_clear_status' }`. This keeps event handlers declarative and concentrates all transition logic within the reducer. ◼ Pedagogical qualification: Formulate semantic action design principles; terms introduced: **semantic action**, **declarative event handling**, **intent-driven dispatch**.
- [code] Pure reducer with semantic actions:
```jsx title="Pure Reducer Pattern"
export function dispatchReducer(state, action) {
  switch (action.type) {
    case 'saved_draft':
      return { ...state, status: 'draft', revisions: state.revisions + 1 };
    case 'published':
      return { ...state, status: 'published', revisions: state.revisions + 1 };
    default:
      return state;
  }
}
```
- [grounding] Leading Question: Why should a reducer be defined outside the component?
  Confusion Point: Can you define the reducer function inside the component body?
  Scene & Repetition: Always define the reducer outside the component body (or in a separate file)! Because a reducer is a pure function that does not depend on component props or hooks, defining it outside proves that it has no hidden dependencies. This allows you to export the reducer and unit-test all state transitions in standard Node or Jest tests without mounting React components!
  Key Terms (Bold): `**external definition**`, `**zero-dependency purity**`, `**isolated unit testing**`, `**module export**`.
  Resolution: Define reducers outside the component to guarantee pure logic and enable direct unit testing without React.

### Step 1: First, we construct the parent container DispatchEditor.jsx
- [p] ★ {preknowledge:} The parent container declares the reducer function and invokes `useReducer`. {problem:} The parent must demonstrate the reducer declaration and dispatch wiring. ◼ Pedagogical qualification: Construct container hosting useReducer and pure reducer function.
- [code] Parent container DispatchEditor.jsx:
```jsx title="DispatchEditor.jsx"
import { useReducer } from 'react';
import EditorControls from './components/EditorControls.jsx';
import StatusBanner from './components/StatusBanner.jsx';
const INIT = { status: 'editing', rev: 0 };
function reducer(s, a) {
  if (a.type === 'draft') return { ...s, status: 'draft', rev: s.rev + 1 };
  if (a.type === 'publish') return { ...s, status: 'published', rev: s.rev + 1 };
  return s;
}
export default function DispatchEditor() {
  const [state, dispatch] = useReducer(reducer, INIT);
  return <div className="editor-box"><EditorControls dispatch={dispatch} /><StatusBanner state={state} /></div>;
}
```
- [p] ★ Step 1 establishes reducer consolidation: Look at lines 5 through 9: `reducer` gathers all transition rules into one pure function. Look at line 11: `const [state, dispatch] = useReducer(reducer, INIT);`. We will build `EditorControls` next in step 2. ◼ Pedagogical qualification: Deconstruct useReducer invocation and transition consolidation.

- [grounding] Leading Question: How do you initialize expensive state in useReducer?
  Confusion Point: What if initializing state in `useReducer` requires complex calculations?
  Scene & Repetition: `useReducer` supports an optional third argument: an initializer function! You write `useReducer(reducer, initialArg, init)`. React runs `init(initialArg)` only once on the initial mount, preventing expensive setup logic from running on subsequent re-renders.
  Key Terms (Bold): `**initializer function**`, `**lazy initialization**`, `**initialArg parameter**`, `**render performance**`.
  Resolution: Use the third `init` parameter of `useReducer` to lazily compute expensive initial state on mount.

### Glossary
- **useReducer**: A React hook that manages state through a pure reducer function and action dispatching.
- **Reducer Function**: A pure function with signature `(state, action) => nextState` calculating the new state snapshot.
- **Action Object**: A plain JavaScript object describing an event or user intent, typically containing a `type` property.
- **Dispatch Function**: The stable function returned by `useReducer` that sends an action to the reducer.
- **Pure Function**: A deterministic function with no side effects that always returns the same output for given inputs.
- **Atomic State Update**: Updating multiple related state fields simultaneously in a single immutable transition.

### Summary

**React 19 useReducer Invariants**

In daily production, consolidating state transitions with `useReducer` prevents state desynchronization and makes complex business logic easy to test. Here is your streetwise review.

❒ useReducer Invariants

1. Reducers must be pure functions.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Reducers take `(state, action)` and return the next immutable state object.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Never mutate state directly; always return a new object reference.

2. Actions describe what happened, not how to update.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Use descriptive names like `{ type: 'saved_draft' }`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Let the reducer decide how to compute the resulting state changes.

3. Declare reducers outside the component body.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Reducers have no dependencies on component props or hooks.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) External reducers can be directly imported and unit-tested in isolation.

➔ NEVER mutate state properties directly inside a reducer function.

➔ ALWAYS dispatch semantic action objects describing user intent.

➔ IF multiple state variables update together THEN **consolidate them into useReducer**.

**DO THIS:** Consolidate multiple interdependent states in a pure reducer.

```jsx right title="DispatchEditor.jsx"
// Pure reducer gathers all state transitions into one place
function reducer(state, action) {
  if (action.type === 'publish') {
    return { ...state, status: 'published', rev: state.rev + 1 };
  }
  return state;
}
export default function DispatchEditor() {
  const [state, dispatch] = useReducer(reducer, { status: 'idle', rev: 0 });
  return <button onClick={() => dispatch({ type: 'publish' })}>Publish</button>;
}
```

**DO NOT DO THIS:** Never scatter interdependent setters across event handlers.

```jsx wrong title="Scattered-Setters Anti-Pattern"
// FAILS: Scattered setters risk partial updates and missed transitions!
export default function BrokenEditor() {
  const [status, setStatus] = useState('idle');
  const [rev, setRev] = useState(0);
  function handlePublish() {
    setStatus('published');
    // BUG: Forgot to increment rev; state becomes inconsistent!
  }
  return <button onClick={handlePublish}>Publish</button>;
}
```
