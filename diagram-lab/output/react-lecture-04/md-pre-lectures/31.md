### The Two-Context Architecture
- [p] ◇ {preknowledge:} In Lecture 29 we learned that `useReducer` consolidates complex state transitions, and in Lecture 30 we learned that Context teleports values across deep trees. When building app-wide state (like a shopping cart or user session), combining `useReducer` with Context allows any component to read state or dispatch actions. {problem:} Why is bundling `{ state, dispatch }` into a single context value an architectural flaw? ◼ Pedagogical qualification: Contrast single combined context with split context architecture; terms introduced: **combined context**, **re-render cascade**, **dispatch stability**.
- [p] ★ {preknowledge:} If you provide `{ state, dispatch }` in a single context: `<CartContext value={{ state, dispatch }}>`, every time `state` changes, the context value is a brand-new object reference. React re-renders **every single component that subscribes to `CartContext`**, even if that component only uses `dispatch` (like an "Add to Cart" button)! Because buttons only need `dispatch`—and `dispatch` has a stable identity that never changes—buttons should never re-render when cart items change. ◼ Pedagogical qualification: Explain why combined context defeats dispatch stability; terms introduced: **dispatch stability**, **subscriber re-render**, **object reference invalidation**.
- [p] ★ {preknowledge:} The battle-tested production pattern is the **Two-Context Pattern**:
  1. Create `CartContext` for reading state: `createContext(null)`.
  2. Create `CartDispatchContext` for sending actions: `createContext(null)`.
  3. Nest the providers: `<CartContext value={state}><CartDispatchContext value={dispatch}>{children}</CartDispatchContext></CartContext>`.
  Now components that read state subscribe to `CartContext`, while components that only dispatch subscribe to `CartDispatchContext` and **never re-render when state updates**! ◼ Pedagogical qualification: Establish the 3-step Two-Context Pattern; terms introduced: **two-context pattern**, **CartContext**, **CartDispatchContext**, **selective subscription**.
- [code] Single context vs split two-context pattern:
```jsx title="Single vs Split Two-Context Pattern"
// FLAWED: Single context re-renders dispatch-only buttons on every state update:
<CartContext value={{ state, dispatch }}>{children}</CartContext>
// PRODUCTION STANDARD: Split state and dispatch into separate contexts:
export function CartProvider({ children }) {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });
  return (
    <CartContext value={state}>
      <CartDispatchContext value={dispatch}>{children}</CartDispatchContext>
    </CartContext>
  );
}
```
- [grounding] Leading Question: Why is React's dispatch function guaranteed to be stable?
  Confusion Point: Does `useReducer` create a new `dispatch` function on every render?
  Scene & Repetition: No! React guarantees that the `dispatch` identity returned by `useReducer` is 100% stable across the entire lifetime of the component. It never changes between re-renders. By isolating `dispatch` in its own context, components reading `useCartDispatch()` will literally NEVER re-render due to context updates!
  Key Terms (Bold): `**dispatch stability guarantee**`, `**identity permanence**`, `**zero-re-render dispatch**`, `**hook invariant**`.
  Resolution: The `dispatch` function is permanently stable; placing it in a dedicated context guarantees zero re-renders for action-dispatching controls.

### Encapsulating with Custom Providers and Hooks
- [p] ◇ {preknowledge:} We know why splitting contexts optimizes rendering. {problem:} How do we package this logic so consumers don't have to import multiple contexts and handle null checks? ◼ Pedagogical qualification: Teach custom provider encapsulation and ergonomic hook exports; terms introduced: **custom provider component**, **custom context hooks**, **invariant error check**.
- [p] ★ {preknowledge:} Raw context consumption forces every consumer to import the context object and call `use(CartContext)`. A professional architecture wraps this in a dedicated provider file exporting two custom hooks:
  - `useCart()`: returns `use(CartContext)`. Throws a helpful error if used outside `<CartProvider>`.
  - `useCartDispatch()`: returns `use(CartDispatchContext)`.
  This hides internal context details, prevents accidental out-of-bounds reads, and provides clean, auto-completable APIs across your engineering team. ◼ Pedagogical qualification: Explain custom hook encapsulation and guard assertions; terms introduced: **useCart hook**, **useCartDispatch hook**, **boundary guard assertion**.
- [p] ★ {preknowledge:} This pattern scales cleanly: you can place reducers, action type constants, and providers in a single `cartContext.jsx` module, turning complex app-wide state into a plug-and-play architectural layer. ◼ Pedagogical qualification: Establish modular state packaging; terms introduced: **modular state architecture**, **pluggable state layer**, **domain isolation**.
- [code] Custom provider and consumer hook exports:
```jsx title="Custom Hooks Pattern"
export function useCart() {
  const ctx = use(CartContext);
  if (!ctx) throw new Error('useCart must be used within CartProvider');
  return ctx;
}
export function useCartDispatch() {
  const ctx = use(CartDispatchContext);
  if (!ctx) throw new Error('useCartDispatch must be within CartProvider');
  return ctx;
}
```
- [grounding] Leading Question: Can you pass complex action creator functions instead of raw dispatch?
  Confusion Point: Should `CartDispatchContext` provide dispatch directly or helper functions?
  Scene & Repetition: You can do either, but providing `dispatch` directly keeps the context value permanently stable. If you wrap dispatch in helper functions (like `addItem(id)`), make sure they are wrapped in `useCallback` or pass raw `dispatch` and define action helpers in a separate utility module. Raw `dispatch` is universally preferred because it requires zero memoization.
  Key Terms (Bold): `**raw dispatch preference**`, `**action creators**`, `**useCallback memoization**`, `**boilerplate reduction**`.
  Resolution: Providing raw `dispatch` avoids unnecessary function allocations and ensures maximum stability.

### Step 1: First, we construct the provider container SyndicationCart.jsx
- [p] ★ {preknowledge:} The provider container manages `useReducer` and renders both contexts. {problem:} The parent must demonstrate the two-context provider nesting. ◼ Pedagogical qualification: Construct container nesting state and dispatch contexts.
- [code] Provider container SyndicationCart.jsx:
```jsx title="SyndicationCart.jsx"
import { useReducer, createContext } from 'react';
import CartBadge from './components/CartBadge.jsx';
import AddArticleBtn from './components/AddArticleBtn.jsx';
export const CartContext = createContext(null);
export const CartDispatchContext = createContext(null);
const reducer = (s, a) => (a.type === 'add' ? { count: s.count + 1 } : s);
export default function SyndicationCart() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <CartContext value={state}><CartDispatchContext value={dispatch}>
      <header><CartBadge /><AddArticleBtn /></header>
    </CartDispatchContext></CartContext>
  );
}
```
- [p] ★ Step 1 establishes dual context nesting: Look at lines 4 and 5: two distinct contexts are created. Look at lines 10 through 12: `CartContext` supplies `state` while `CartDispatchContext` supplies `dispatch`. We will build `CartBadge` next in step 2. ◼ Pedagogical qualification: Deconstruct split context provider nesting.

### Step 2: Next, we declare the state consumer CartBadge.jsx
- [p] ★ {preknowledge:} Step 1 provided `CartContext`. {problem:} The badge component must display the current item count using `CartContext`. ◼ Pedagogical qualification: Build state consumer reading CartContext.
- [code] State consumer CartBadge.jsx:
```jsx title="CartBadge.jsx"
import { use } from 'react';
import { CartContext } from '../SyndicationCart.jsx';
export default function CartBadge() {
  const cart = use(CartContext);
  return (
    <div className="cart-badge">
      <span>Active Licenses: <strong>{cart?.count ?? 0}</strong></span>
    </div>
  );
}
```
- [p] ★ Step 2 fulfills the state reading role: Look at line 4: `const cart = use(CartContext)`. `CartBadge` subscribes strictly to cart state. When an item is added, it re-renders to display the fresh count. ◼ Pedagogical qualification: Deconstruct state subscription mechanics.

### Step 3: Then, we declare the dispatch consumer AddArticleBtn.jsx
- [p] ★ {preknowledge:} `AddArticleBtn` only needs to trigger actions. {problem:} The button component must consume `CartDispatchContext` without subscribing to cart state. ◼ Pedagogical qualification: Build dispatch-only consumer reading CartDispatchContext.
- [code] Dispatch consumer AddArticleBtn.jsx:
```jsx title="AddArticleBtn.jsx"
import { use } from 'react';
import { CartDispatchContext } from '../SyndicationCart.jsx';
export default function AddArticleBtn() {
  const dispatch = use(CartDispatchContext);
  return (
    <button onClick={() => dispatch({ type: 'add' })}>
      Add Syndication License
    </button>
  );
}
```
- [p] ★ Step 3 completes dispatch isolation: Look at line 4: `const dispatch = use(CartDispatchContext)`. Because `dispatch` is stable and isolated from `CartContext`, `AddArticleBtn` **never re-renders when cart count updates**. ◼ Pedagogical qualification: Deconstruct dispatch-only isolation and re-render prevention.
- [p] What would happen if we bundled state and dispatch into a single context object? If state and dispatch are passed in one object (`value={{ state, dispatch }}`), a new object is created every time count increments. Every component consuming the context—including `AddArticleBtn`—is forced to re-render, degrading performance across large lists. ◼ Pedagogical qualification: Apply Negative Counterfactual Law to single bundled context objects.

### Step 4: Finally, we seal the application entry point main.jsx
- [p] ★ {preknowledge:} In Steps 1 through 3 we created the reducer-context tree. Now we inspect `main.jsx`, which mounts `SyndicationCart` to the DOM. {problem:} The entry point must initialize the React root and render the cart. ◼ Pedagogical qualification: Seal architecture at application entry point.

State flows cleanly through `CartContext` while actions dispatch through `CartDispatchContext`, guaranteeing modular, performant app-wide state. ◼ Pedagogical qualification: Trace complete reducer-context lifecycle.

### Glossary
- **Two-Context Pattern**: An architectural pattern that separates state values and dispatch functions into two distinct context providers.
- **CartDispatchContext**: A context providing only the stable `dispatch` function, ensuring zero re-renders for subscribers.
- **CartContext**: A context providing the current state snapshot to components that display data.
- **Dispatch Stability**: React's guarantee that `dispatch` retains the exact same function reference across all re-renders.
- **Custom Provider**: A component wrapping state setup, reducers, and context providers into a single reusable tag.
- **Selective Subscription**: Subscribing only to the specific context slice (state vs dispatch) required by a component.

### Summary

**React 19 Reducer + Context Invariants**

In daily production, combining reducers with the two-context pattern scales state across large applications while eliminating unnecessary re-renders. Here is your streetwise review.

❒ Reducer + Context Invariants

1. Split state and dispatch into two contexts.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `StateContext` provides the dynamic state object.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) `DispatchContext` provides the permanently stable `dispatch` function.

2. Dispatch-only components never re-render on state changes.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Buttons subscribing only to `DispatchContext` remain completely idle when state updates.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Bundling both into a single object destroys this optimization.

3. Wrap contexts in custom hooks with guard assertions.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Export `useCart()` and `useCartDispatch()` to encapsulate context reads.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Throw a clear descriptive error if a hook is used outside its Provider.

➔ NEVER bundle `{ state, dispatch }` into a single combined context value object.

➔ ALWAYS separate state and dispatch into two independent contexts.

➔ IF a component only dispatches actions THEN **subscribe it strictly to DispatchContext**.

**DO THIS:** Separate state and dispatch into two distinct contexts.

```jsx right title="SyndicationCart.jsx"
// Clean two-context pattern preserving dispatch stability
export const StateCtx = createContext(null);
export const DispatchCtx = createContext(null);
export function Provider({ children }) {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <StateCtx value={state}>
      <DispatchCtx value={dispatch}>{children}</DispatchCtx>
    </StateCtx>
  );
}
```

**DO NOT DO THIS:** Never combine state and dispatch into a single object value.

```jsx wrong title="Combined-Context Anti-Pattern"
// FAILS: Single context forces every dispatch-only button to re-render!
export const CartCtx = createContext(null);
export function BrokenProvider({ children }) {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <CartCtx value={{ state, dispatch }}>
      {children}
    </CartCtx>
  );
}
```
