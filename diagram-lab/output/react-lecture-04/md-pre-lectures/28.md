### The Tree Position Rule
- [p] ◇ {preknowledge:} Developers often think of state as living inside the component function instance. Under this mental model, switching views or unmounting should destroy local state, while rendering the same component elsewhere should carry its state along. {problem:} Why does React preserve state between two seemingly different renders at the same position, while resetting state when tree structure changes? ◼ Pedagogical qualification: Contrast intuitive mental model with React's Fiber tree position model; terms introduced: **tree position rule**, **fiber tree position**, **state persistence**.
- [p] ★ {preknowledge:} In React, **state is held in internal Fiber nodes, tied directly to the component's position in the UI tree**, not inside the function itself. When a re-render occurs, React compares the new tree to the old tree. If the **same component type** is rendered at the **exact same position**, React retains the existing Fiber node and preserves all of its state! ◼ Pedagogical qualification: Formulate the core Tree Position Rule; terms introduced: **tree position rule**, **same component type**, **fiber node retention**.
- [p] ★ {preknowledge:} If the component type at that position changes (for example, replacing `<StaffReview />` with `<FreelanceReview />`), or if the tree hierarchy changes (such as wrapping a child inside a new `<div>`), React destroys the old Fiber node, unmounts the component, and discards all associated state. ◼ Pedagogical qualification: Explain unmounting and destruction triggers; terms introduced: **type change destruction**, **hierarchy shift**, **fiber unmount**.
- [code] Tree position preservation contrast:
```jsx title="Tree Position Rule in Action"
// PERSISTS: Same component type at same position; state is preserved!
{isStaff ? <ReviewScore isStaff={true} /> : <ReviewScore isStaff={false} />}
// RESETS: Different tree position/structure; state is destroyed!
{isStaff ? (
  <div><ReviewScore isStaff={true} /></div>
) : (
  <section><ReviewScore isStaff={false} /></section>
)}
```
- [grounding] Leading Question: Why does conditional rendering with ternary preserve state?
  Confusion Point: If the condition switches between two branches of a ternary, shouldn't React treat them as separate components?
  Scene & Repetition: To React, JSX produces a virtual tree. In `{isStaff ? <ReviewScore ... /> : <ReviewScore ... />}`, the parent element has a single child at position 0. In both branches, that child has the exact same component type: `ReviewScore`. Because the position and type are identical, React assumes it is the same logical component and preserves its state across toggles!
  Key Terms (Bold): `**virtual tree position**`, `**ternary position equivalence**`, `**fiber matching**`, `**branch reconciliation**`.
  Resolution: React reconciles by tree position; identical component types at the same slot in the tree share the same state across conditional branches.

### Resetting State with Keys and the Nested Definition Trap
- [p] ◇ {preknowledge:} We understand why React preserves state at the same position. {problem:} How do you tell React that two components at the same position are logically distinct and must have completely separate state? ◼ Pedagogical qualification: Introduce the key attribute as identity reset mechanism; terms introduced: **key attribute**, **explicit identity**, **forced state reset**.
- [p] ★ {preknowledge:} The standard React mechanism to distinguish components at the same tree position is the **`key` attribute**. When you assign different keys (`key="staff"` vs `key="freelance"`), React treats them as two completely distinct entities. Switching the key causes React to unmount the old component, discard its state, and mount a brand-new component with fresh state. ◼ Pedagogical qualification: Explain keys as identity overrides; terms introduced: **key attribute**, **identity override**, **clean mount**.
- [p] ★ {preknowledge:} A catastrophic beginner mistake is **nesting a component definition inside another component function**: `function Parent() { function Child() { ... } }`. On every parent re-render, JavaScript re-creates `Child` as a brand-new function reference. React sees a completely different component type at that position, wiping out child state and DOM focus on every single keystroke! Component definitions must **always be declared at top-level module scope**. ◼ Pedagogical qualification: Deconstruct the nested component definition trap; terms introduced: **nested definition trap**, **top-level declaration**, **accidental remounting**.
- [code] Resetting state with keys vs nested trap:
```jsx title="Keys vs Nested Function Trap"
// RIGHT: Unique keys force React to reset state on switch:
{isStaff ? <ScoreCard key="staff" /> : <ScoreCard key="free" />}
// WRONG: Defining component inside parent wipes state on EVERY render!
function BrokenParent() {
  function NestedInput() { const [v, setV] = useState(''); return <input ... />; }
  return <NestedInput />;
}
```
- [grounding] Leading Question: Can keys also preserve state when list items reorder?
  Confusion Point: If keys reset state when switched, why do we use keys on lists?
  Scene & Repetition: Keys provide a persistent identity. In a list, assigning `key={item.id}` tells React: "This specific Fiber node belongs to item #42." If the array is sorted, filtered, or prepended, React moves the existing Fiber node and its state to the new position, instead of mistakenly rebinding item #42's state to item #99!
  Key Terms (Bold): `**list identity preservation**`, `**stable key**`, `**reorder tracking**`, `**fiber relocation**`.
  Resolution: Keys override tree position; they preserve identity when items move, and force state resets when items switch.

### Step 1: First, we construct the parent container ReviewSwitcher.jsx
- [p] ★ {preknowledge:} The parent container tracks active `mode` and passes unique keys to `ReviewScore`. {problem:} The parent must demonstrate that `key={mode}` forces state reset between modes. ◼ Pedagogical qualification: Construct container using keys to control component identity.
- [code] Parent container ReviewSwitcher.jsx:
```jsx title="ReviewSwitcher.jsx"
import { useState } from 'react';
import ReviewToggle from './components/ReviewToggle.jsx';
import ReviewScore from './components/ReviewScore.jsx';
export default function ReviewSwitcher() {
  const [mode, setMode] = useState('staff');
  return (
    <div className="review-box">
      <ReviewToggle mode={mode} onToggle={setMode} />
      <ReviewScore key={mode} mode={mode} />
    </div>
  );
}
```
- [p] ★ Step 1 establishes keyed identity: Look at line 9: `<ReviewScore key={mode} mode={mode} />`. When `mode` changes from `'staff'` to `'freelance'`, React sees a new key, tears down the old score card, and mounts a fresh one with initial score 0. We will build `ReviewToggle` next in step 2. ◼ Pedagogical qualification: Deconstruct key-driven identity switching.

### Step 2: Next, we declare the toggle child ReviewToggle.jsx
- [p] ★ {preknowledge:} Step 1 passed `mode` and `onToggle` to `ReviewToggle`. {problem:} The child component must render buttons allowing the user to switch modes. ◼ Pedagogical qualification: Build controlled toggle controls child.
- [code] Toggle child ReviewToggle.jsx:
```jsx title="ReviewToggle.jsx"
export default function ReviewToggle({ mode, onToggle }) {
  return (
    <nav className="review-toggle">
      <button disabled={mode === 'staff'} onClick={() => onToggle('staff')}>Staff</button>
      <button disabled={mode === 'freelance'} onClick={() => onToggle('freelance')}>Freelance</button>
    </nav>
  );
}
```
- [p] ★ Step 2 fulfills the toggle role: Look at lines 4 and 5: clicking either button calls `onToggle` with the new mode string, triggering a parent re-render. ◼ Pedagogical qualification: Deconstruct mode toggle mechanics.

### Step 3: Then, we declare the score child ReviewScore.jsx
- [p] ★ {preknowledge:} `ReviewScore` holds internal `score` state. {problem:} The child must show that state is preserved during normal updates but reset when the key changes. ◼ Pedagogical qualification: Build stateful child demonstrating key-governed lifecycle.
- [code] Score child ReviewScore.jsx:
```jsx title="ReviewScore.jsx"
import { useState } from 'react';
export default function ReviewScore({ mode }) {
  const [score, setScore] = useState(0);
  return (
    <div className="review-score">
      <h3>Review Tier: {mode}</h3>
      <p>Rating: {score}</p>
      <button onClick={() => setScore(s => s + 1)}>Increment Score</button>
    </div>
  );
}
```
- [p] ★ Step 3 completes the stateful card: Look at line 3: `const [score, setScore] = useState(0)`. While interacting within the same mode, clicking "Increment Score" preserves state. But when `mode` switches, the key changes, and `score` resets cleanly back to 0. ◼ Pedagogical qualification: Deconstruct state preservation vs key-driven reset.
- [p] What would happen if we omitted `key={mode}` from `<ReviewScore mode={mode} />`? If we omitted `key={mode}`, React would see the exact same component type (`ReviewScore`) at the exact same position in `ReviewSwitcher`. The `score` state would persist across mode switches, causing an editor's evaluation of a staff writer to erroneously bleed into a freelance evaluation! ◼ Pedagogical qualification: Apply Negative Counterfactual Law to missing key attribute.

- [grounding] Leading Question: Why does changing CSS display: none preserve state while unmounting resets it?
  Confusion Point: Can you hide a component with CSS instead of conditional rendering if you want to keep its state?
  Scene & Repetition: Yes! If a component remains rendered in JSX and in the DOM (e.g. `<div style={{ display: isVisible ? 'block' : 'none' }}>`), its Fiber node remains intact in the React tree, so its state is 100% preserved. Conditional rendering (`{isVisible && <Modal />}`) completely removes the Fiber node, resetting state. If state preservation is desired without keys or lifted state, CSS hiding is a valid technique.

### Glossary
- **Component Identity**: How React recognizes whether a component on the new render corresponds to a component from the previous render.
- **Tree Position Rule**: React's algorithm that matches state to a component based on its component type and position in the Fiber tree.
- **Key Attribute**: A special React prop that overrides tree position, giving a component a permanent, explicit identity.
- **State Preservation**: The retention of a component's internal state across renders when its tree position and key remain unchanged.
- **State Reset**: The complete destruction of a component's internal state when its type, key, or tree position changes.
- **Nested Component Definition Trap**: The severe defect of defining a component function inside another component, causing remounts on every render.

### Summary

**React 19 Component Identity Invariants**

In daily production, understanding how React tracks component identity prevents state bleeding, phantom data bugs, and accidental input resets. Here is your streetwise review.

❒ Component Identity Invariants

1. State is tied to position in the UI tree.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) The same component type at the same position preserves state across renders.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Changing component type or wrapping in new parent elements destroys state.

2. Keys force state reset at the same position.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Pass a unique `key` when switching between logically distinct views.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) React treats different keys as distinct components, unmounting the old state.

3. Never define a component inside another component.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) A nested function creates a new component type reference on every render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) React unmounts and remounts the child, wiping state and input focus.

➔ NEVER declare component functions inside another component's body.

➔ ALWAYS use distinct `key` props when you need state to reset between toggled views.

➔ IF you need state to survive while hidden THEN **use CSS display: none instead of unmounting**.

**DO THIS:** Use distinct keys to reset state when switching view modes.

```jsx right title="ReviewSwitcher.jsx"
// Clean key attribute forcing fresh state on mode change
export default function ReviewSwitcher() {
  const [mode, setMode] = useState('staff');
  return (
    <div>
      <button onClick={() => setMode('free')}>Switch</button>
      <ReviewScore key={mode} mode={mode} />
    </div>
  );
}
```

**DO NOT DO THIS:** Never omit keys when toggling distinct workflows at the same position.

```jsx wrong title="State-Bleed Anti-Pattern"
// FAILS: Omitted key causes state to bleed across workflows!
export default function BrokenSwitcher() {
  const [mode, setMode] = useState('staff');
  return (
    <div>
      <button onClick={() => setMode('free')}>Switch</button>
      <ReviewScore mode={mode} /> {/* BUG: State bleeds! */}
    </div>
  );
}
```
