### Passing Data from Parent to Child
- [p] ◇ {preknowledge:} In earlier lessons, we learned that React components are JavaScript functions that return JSX markup, and we can split them across separate files (see Lectures 3 and 7). When you mount a component using JSX syntax like `<ActionButton />`, React executes the function and renders its returned elements. {problem:} If you hardcode text and attributes inside the component function, every instance renders identical content, making component reuse impossible. ◼ Pedagogical qualification: Establish the need for dynamic component arguments; terms introduced: **props**, **component arguments**, **JSX attributes**.
- [p] ★ {preknowledge:} In ordinary JavaScript, when you want a function to produce different output, you pass arguments inside parentheses: `renderButton('Publish', 'primary')`. In React, you pass arguments as named attributes directly on the JSX tag: `<ActionButton label="Publish" variant="primary" />`. React collects all attributes declared on the tag and packages them into a single JavaScript object called **props** (short for properties). The component function receives this `props` object as its first argument: `function ActionButton(props)`. ◼ Pedagogical qualification: Connect plain function arguments to React JSX props; terms introduced: **props object**, **destructuring**.
- [p] ★ {preknowledge:} Most developers do not write `props.label` and `props.variant` throughout their components. Instead, they use modern JavaScript object destructuring in the function signature: `function ActionButton({ label, variant })`. Destructuring extracts the exact properties the component needs directly into local variables. You can also specify default values for props that might be omitted: `function ActionButton({ label, variant = 'secondary' })`. ◼ Pedagogical qualification: Explain destructuring and default prop values.
- [code] Props passing and destructuring patterns:
```jsx title="Props Passing and Destructuring"
// Parent passes props as JSX attributes:
<ActionButton label="Publish Story" variant="primary" />
// Child receives props as an object and destructures:
export default function ActionButton({ label, variant = 'secondary' }) {
  return <button className={`btn btn-${variant}`}>{label}</button>;
}
```
- [grounding] Leading Question: Why does React bundle props into an object?
  Confusion Point: Why does React pass a single `props` object instead of separate positional arguments like `function ActionButton(label, variant)`?
  Scene & Repetition: Imagine you are calling a function that takes five positional arguments: `createArticle("Title", "Author", true, 4, "World")`. Six months later, you want to omit the boolean flag or reorder the parameters. You have to remember the exact position of every argument, and passing `undefined` for unused slots creates ugly code. In HTML, tags never use positional arguments: an `<input type="text" name="title" required>` can list attributes in any order. By packaging all JSX attributes into a single **props object**, React lets parents pass props in any order, omit optional props cleanly, and add new props without breaking existing call sites.
  Key Terms (Bold): `**props object**`, `**JSX attributes**`, `**positional arguments**`, `**destructuring**`.
  Resolution: Packaging props into a single object allows order-independent arguments, optional properties, and seamless future expansion.

### Why Props Are Strictly Read-Only
- [p] ◇ {preknowledge:} When a component receives props from its parent, those props represent the current snapshot of data provided by the parent. What happens if the child component decides to modify that data? For example, what if a button tries to write `props.label = 'Saved'` after being clicked? {problem:} Beginners often assume props behave like ordinary mutable JavaScript objects, attempting to update values by reassigning prop properties. ◼ Pedagogical qualification: Introduce the immutability boundary; terms introduced: **prop immutability**, **read-only props**, **unidirectional data flow**.
- [p] ★ {preknowledge:} In plain JavaScript, objects are passed by reference. If function A passes an object to function B, and function B modifies a property on that object, function A sees that mutation immediately. In React, this behavior is strictly forbidden. React enforces **unidirectional data flow** (one-way data flow): data flows strictly downward from parent to child through props. In development mode, React freezes the props object using `Object.freeze(props)`. If a child attempts to assign to a prop (`props.label = 'New'`), JavaScript throws a `TypeError: Cannot assign to read only property` in strict mode. ◼ Pedagogical qualification: Deconstruct `Object.freeze` and unidirectional data flow; terms introduced: **Object.freeze**, **pure functions**, **TypeError**.
- [p] ★ {preknowledge:} Why does React insist that props are immutable? React components must be **pure functions** with respect to their props: given the same props, a component must always return the exact same JSX. If a child could mutate its props, it would mutate the parent's data behind the parent's back without calling a state setter. Sibling components sharing that same data would see corrupted values, and React's reconciliation engine would fail to detect what changed. ◼ Pedagogical qualification: Explain pure function invariants and state consistency.
- [code] Prop mutation error versus state setter pattern:
```jsx title="Prop Immutability Contrast"
// WRONG: Mutating props directly throws TypeError!
function BadButton(props) {
  props.label = 'Submitted'; // Fails: props is frozen!
  return <button>{props.label}</button>;
}
// RIGHT: Child treats props as read-only; parent owns state:
function GoodButton({ label, onClick }) {
  return <button onClick={onClick}>{label}</button>;
}
```
- [grounding] Leading Question: What happens if a child mutates props?
  Confusion Point: If JavaScript objects are mutable by default, why does React forbid modifying props?
  Scene & Repetition: Imagine an editor at The National Times opens an article draft. The parent `EditorialDesk` owns an article object `{ title: 'Dockworkers Strike', status: 'draft' }`. It passes this object as a prop to both `StoryPreview` (which renders the article text) and `StatusPill` (which displays the status badge). Now imagine `StatusPill` directly writes `props.article.status = 'published'` inside its body. `StoryPreview` still thinks the article is a draft. The parent never called a state setter, so React never triggers a re-render. The screen now displays contradictory information. By making props **read-only**, React guarantees that data only changes through explicit parent state updates, keeping the entire UI synchronized.
  Key Terms (Bold): `**read-only props**`, `**unidirectional data flow**`, `**pure functions**`, `**re-render**`.
  Resolution: Props are read-only to preserve pure function invariants and ensure that state changes flow predictably through parent updates.

### Step 1: First, we construct the parent container EditorialDesk.jsx
- [p] ★ {preknowledge:} The parent container owns the story data and passes it downward as props to child components. {problem:} The file must define the data contract and pass distinct props to each child instance. ◼ Pedagogical qualification: Construct parent container dictating props contracts.
- [code] Parent container EditorialDesk.jsx:
```jsx title="EditorialDesk.jsx"
import StoryCard from './components/StoryCard.jsx';
export default function EditorialDesk() {
  const story = { title: 'Dockworkers Reach Agreement', author: 'Marcus Vance', readTime: '4 min' };
  return (
    <main className="editorial-desk">
      <h1 className="desk-title">The National Times Editorial Desk</h1>
      <StoryCard title={story.title} author={story.author} readTime={story.readTime} /> // Passes props
    </main>
  );
}
```
- [p] ★ Step 1 establishes the contracts: Look at line 7: `<StoryCard title={story.title} author={story.author} readTime={story.readTime} />`. We have not written `StoryCard` yet. But right here in the parent, we establish its contract: it receives `title`, `author`, and `readTime` as props. Notice that the parent dictates what data is shown. We will build `StoryCard` next in step 2. ◼ Pedagogical qualification: Deconstruct parent props passing and forward contracts.

### Step 2: Next, we build the card child StoryCard.jsx
- [p] ★ {preknowledge:} Step 1 established the contract: `StoryCard` receives `title`, `author`, and `readTime`. {problem:} The child component must destructure these props and render the article card while mounting two `ActionButton` children with different props. ◼ Pedagogical qualification: Fulfill child contract with destructuring and forward child props.
- [code] Card child StoryCard.jsx:
```jsx title="StoryCard.jsx"
import ActionButton from './ActionButton.jsx';
export default function StoryCard({ title, author, readTime }) {
  return (
    <article className="story-card">
      <h2>{title} ({readTime})</h2> // Title and time from **PROP**
      <ActionButton label="Publish" variant="primary" /> // Primary action
      <ActionButton label="Archive" variant="secondary" /> // Secondary action
    </article>
  );
}
```
- [p] ★ Step 2 fulfills the contract: Look at line 2: `export default function StoryCard({ title, author, readTime })`. The component destructures the incoming `props` object directly in its signature. Now look at lines 6 and 7: `<ActionButton label="Publish" variant="primary" />` and `<ActionButton label="Archive" variant="secondary" />`. Notice what happened: `StoryCard` reuses the same `ActionButton` component twice, passing different `label` and `variant` props to each copy. ◼ Pedagogical qualification: Deconstruct props destructuring and component reuse.
- [p] What would happen if `StoryCard` tried to mutate `author` directly by writing `author = 'Anonymous'`? Inside `StoryCard`, `author` is a local constant created by destructuring. Reassigning `author` would change only the local variable inside this single render pass, leaving the parent's `story.author` untouched. Even worse, if `StoryCard` received `props` and wrote `props.author = 'Anonymous'`, React would throw a TypeError because the `props` object is frozen. If tomorrow you change the story data in `EditorialDesk`, `StoryCard` updates automatically without needing internal mutation. ◼ Pedagogical qualification: Apply Negative Counterfactual Law to prop mutation.

### Step 3: Then, we declare the button child ActionButton.jsx
- [p] ★ {preknowledge:} Step 2 mounted two `ActionButton` instances with `label` and `variant` props. {problem:} The terminal button component must accept these props and render the native `<button>` element. ◼ Pedagogical qualification: Build terminal UI control receiving props with default values.

- [p] ★ Step 3 completes the terminal control: Look at line 1: `export default function ActionButton({ label, variant = 'secondary' })`. Notice the default parameter `variant = 'secondary'`: if a parent renders `<ActionButton label="Preview" />` without specifying a variant, the button falls back to secondary styling automatically. The component reads `label` and `variant` to construct its class name and children, without modifying any incoming data. ◼ Pedagogical qualification: Deconstruct default prop fallback and read-only rendering.

### Step 4: Finally, we seal the application entry point main.jsx
- [p] ★ {preknowledge:} In Steps 1 through 3 we built the component tree. Now we inspect `main.jsx`, which mounts `EditorialDesk` to the DOM. {problem:} The entry point must initialize the React root and render the top-level container. ◼ Pedagogical qualification: Seal architecture at application entry point.
- [code] Entry point main.jsx:
```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import EditorialDesk from './EditorialDesk.jsx';
const container = document.getElementById('root');

const root = createRoot(container); // Acquires container in **MEMORY**
root.render(<EditorialDesk />); // Mounts root component into **DOM**
```
- [p] ★ Step 4 seals the architecture: Look at line 6: `root.render(<EditorialDesk />)`. React mounts `EditorialDesk`, evaluates its JSX, passes props to `StoryCard`, which passes props to both `ActionButton` instances, and commits the resulting DOM into `<div id="root">`. Data flows strictly downward at every level of the tree. Props remain pure, frozen inputs from start to finish. ◼ Pedagogical qualification: Trace complete props flow from root container to terminal buttons.

- [grounding] Leading Question: Can a child ever communicate back to a parent?
  Confusion Point: If props are strictly read-only and data only flows downward, how can a child button tell the parent that it was clicked?
  Scene & Repetition: Imagine a child component wants to notify the parent that the user clicked "Publish Story". If props only flow downward, how does the message travel upward? The parent passes a function as a prop: `<ActionButton onPublish={handlePublish} />`. The child receives this function under `props.onPublish` and executes it when clicked: `onClick={props.onPublish}`. The function runs in the parent's scope, updating the parent's state.   Resolution: Children communicate with parents by invoking callback functions passed down as props, preserving unidirectional data flow without mutating props.
- [callout] > [!TIP]
**To impress the interviewer:** When asked why React props are immutable, explain that React relies on pure component functions to enable features like concurrent rendering, time-travel debugging, and fast reconciliation. If props were mutable, React could not determine whether a component's inputs had changed without performing deep, expensive object comparisons. By guaranteeing that props are read-only snapshots, React can perform cheap shallow reference equality checks (`prevProps === nextProps`) to optimize rendering.

### Glossary
- **Props**: The inputs passed from a parent component to a child component via JSX attributes, bundled into a single object.
- **Unidirectional Data Flow**: The architectural principle where data flows strictly in one direction: downward from parent to child through props.
- **Destructuring**: The JavaScript syntax used to unpack properties from the `props` object directly into distinct local variables.
- **Prop Immutability**: The rule that props are strictly read-only and must never be modified by the receiving component.
- **Object.freeze**: The JavaScript method used by React in development mode to prevent mutation of the `props` object.
- **Pure Function**: A function that returns the same output whenever given the same inputs and produces zero observable side effects.

### Summary

**React 19 Props Architecture and Immutability Invariants**

In daily production, props are the primary mechanism for making components flexible and reusable. Understanding props passing, destructuring, and the immutability invariant guarantees reliable, bug-free component architecture. Here is your streetwise review.

❒ Props Invariants and Data Flow

1. Pass data downward using JSX attributes and destructure in the child.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Declare attributes on the JSX tag: `<StoryCard title="News" author="Marcus" />`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Destructure props directly in the component signature: `function StoryCard({ title, author })`.

2. Treat all props as strictly read-only snapshots.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Never reassign or mutate a prop: React freezes `props` in development mode.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) To change data over time, have the parent manage state and pass updated values downward.

➔ NEVER mutate a prop directly, which throws a TypeError and violates pure component invariants.

➔ ALWAYS provide default values for optional props using destructuring syntax: `{ variant = 'secondary' }`.

➔ IF a child needs to communicate a change to its parent THEN **invoke a callback function passed down as a prop**.

**DO THIS:** Pass dynamic values via props and destructure cleanly with default values.

```jsx right title="StoryCard.jsx"
// Destructures props with a safe default value
export default function StoryCard({ title, author, status = 'draft' }) {
  return (
    <article className="story-card">
      <h2>{title}</h2>
      <p>By {author} · Status: {status}</p>
    </article>
  );
}
```

**DO NOT DO THIS:** Never attempt to mutate props directly inside a component function.

```jsx wrong title="Prop Mutation Anti-Pattern"
// FAILS AT RUNTIME: props is frozen!
export default function BrokenCard(props) {
  if (!props.status) {
    props.status = 'draft'; // TypeError: Cannot assign to read only property
  }
  return <article>{props.title}</article>;
}
```

| ---: | :--- | :--- |
