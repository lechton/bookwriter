### Why Hardcoded Components Fail: The Need for Dynamic Inputs
- [p] ◇ {preknowledge:} In earlier lessons, we learned that a React component is a JavaScript function that returns JSX markup describing what should appear on screen (see Lecture 3 and Lecture 4). When starting a new project, developers define component functions with hardcoded text and static HTML tags. {problem:} If you build an action button with the text "Publish Story" hardcoded into its JSX return statement, every single copy of that button renders the exact same text. Creating separate component files like `PublishButton.jsx`, `DraftButton.jsx`, and `ArchiveButton.jsx` produces massive code duplication and maintenance friction. What are **props**? In React, **props** (short for properties) are the configuration values that a parent component passes downward to a child component to customize its behavior and visual output. In plain HTML, native tags come with fixed, standardized attributes: an `<img>` tag accepts `src` and `width`, and an `<input>` tag accepts `type` and `value`. But native HTML tags cannot be taught new custom attributes, and plain JavaScript functions require manual invocation. In modern React, you declare custom parameters on your own component functions: you write `function ActionButton({ label, variant })` and mount it with `<ActionButton label="Publish Story" variant="primary" />`. React gathers every attribute into a single plain JavaScript object and passes it to your function. The law of props is absolute: props are strictly read-only inputs passed from parent to child, meaning a child can only read the props it receives and can never change them. ◼ Defines props with its default sentence and law sentence; terms introduced: **props**, **component parameter**, **read-only contract**.
- [p] ★ {preknowledge:} In plain JavaScript, calling a function with different arguments returns different results based on those inputs. {old solution:} When developers build static components, they hardcode text directly inside the function body, forcing them to copy and paste entire files just to change a word. {new solution:} In React, you turn hardcoded markup into an adaptable template by replacing static text with dynamic prop expressions inside curly braces (see Lecture 5). ◼ Connects standard function arguments to React component props; terms introduced: **dynamic inputs**, **template reuse**.
- [code] Hardcoded vs Parameterized Button:
```jsx title="ComponentReuseContrast"
export function HardcodedPublishButton() {
  return <button className="btn-primary">Publish Story</button>;
}
export function ActionButton(props) {
  return <button className={`btn-${props.variant}`}>{props.label}</button>;
}
```
◼ **The what-this-introduces list:** 1. `HardcodedPublishButton`: static component with fixed markup and zero reuse. 2. `ActionButton(props)`: parameterized component accepting a single props argument. 3. `props.variant` and `props.label`: dynamic property reads driving attributes and text.
- [p] When you pass data into a component, you choose between two input channels: (a) The string literal channel (`label="Publish Story"`) passes plain text directly inside double quotes, identical to traditional HTML attributes. (b) The dynamic expression channel (`count={42}`) wraps JavaScript numbers, booleans, variables, or objects inside JSX curly braces (see Lecture 5). The consequence of this distinction is complete flexibility: a single component blueprint can receive static text strings, computed numbers, or complex data structures without altering its internal markup. ◼ Technical explanation of prop channels using the four-part lettered anchor standard.
- [grounding] the opening question: What is the problem with copy-pasting components?
  the friction it clears: why duplicating components for different text creates maintenance nightmares.
  Scene & Repetition: Imagine a printing press that stamps labels onto newspaper bundles. If the press could only print the word "Morning", you would need to build an entirely new steel machine just to print "Evening". You would need a third machine to print "Special Edition". That is what happens when you build hardcoded components: every tiny text variation forces you to copy and paste entire files. This copy-paste habit leads to fragile **code duplication** and maintenance chaos. **Props** turn your component into an adaptable stamp: the machine stays identical, but you supply the ink and wording dynamically.
  Key Terms (Bold): **props**, **component blueprint**, **code duplication**.
  Resolution: Props parameterize component functions so a single component blueprint renders infinite visual variations based on incoming data.

### Passing and Reading Props: The Function Argument Pipeline
- [p] ◇ {preknowledge:} In earlier lessons, we learned that JSX is an extension to JavaScript that allows you to write HTML-like tags inside your scripts (see Lecture 4). When you write a tag like `<ActionButton label="Publish Story" />`, you are not writing native HTML elements; you are writing a declarative description that compiles to JavaScript. What is the **props object**? Under the hood, JSX attributes compile directly into a single plain JavaScript object called **`props`**. In plain JavaScript functions, developers often pass multiple positional arguments like `createButton(text, color, size, icon)`. If a caller accidentally swaps the order of two strings, the button renders with the wrong color and label. In React, component functions always take exactly one argument: the `props` object. The law of the props object states: all attributes declared on a JSX tag become key-value properties on that single object, and React passes it directly as the first argument of the component function. ◼ Defines the props object with its default sentence and law sentence; terms introduced: **props object**, **positional arguments**, **destructuring**.
- [code] Props argument vs Parameter Destructuring:
```jsx title="PropsSyntaxContract"
export function ActionButton(props) {
  return <button className={props.variant}>{props.label}</button>;
}
export function ModernButton({ label, variant = 'secondary' }) {
  return <button className={variant}>{label}</button>;
}
```
◼ **The what-this-introduces list:** 1. `function ActionButton(props)`: standard single-argument component signature. 2. `props.variant` and `props.label`: direct property access on the incoming object. 3. `function ModernButton({ label, variant = 'secondary' })`: parameter destructuring with default fallback value.
- [p] ★ Deconstruction of the props syntax contract: Look at line 2 in `ActionButton(props)`: the component accepts `props` as its single parameter, reading values with `props.label` and `props.variant`. Now look at line 6 in `ModernButton({ label, variant = 'secondary' })`: instead of typing `props.` repeatedly, modern React developers use JavaScript object destructuring directly inside the parameter parenthesis. Destructuring extracts the exact named properties you need into local variables in the function scope. Notice also `variant = 'secondary'`: JavaScript default parameter syntax ensures that if the parent omits the `variant` prop, the component falls back to a safe default styling. ◼ Deconstructs property access vs parameter destructuring; explains default fallback values.
- [p] ★ {preknowledge:} Passing string values to props uses double quotes, exactly like HTML attributes. {problem:} When beginners need to pass numbers, booleans, arrays, or objects, they frequently write `count="5"` or `isUrgent="true"`. Passing numbers inside quotes delivers a literal string to the component, which breaks mathematical operations like `count + 1` by producing `"51"` instead of `6`. {new solution:} Whenever you pass non-string values into a component, wrap them inside JSX curly braces (see Lecture 5): `<ActionButton count={5} isUrgent={true} />`. ◼ Explains quotes for strings versus curly braces for JavaScript values; terms introduced: **prop types**, **curly brace expressions**.
- [callout] `> [!KEY]` `A component is a function, and props are its arguments.` ◼ Insider takeaway: links component execution directly to pure function invocation.
- [p] When your component function runs, it does not invent its own incoming data. It receives a single object containing every attribute written by the parent, unpacks those properties, and returns JSX markup calculated strictly from those inputs. Just as a plain JavaScript function cannot choose what arguments its caller provides, a child component cannot dictate what props its parent passes downward. ◼ Unpacks the KEY takeaway in narrative prose.
- [grounding] the opening question: Why does React bundle props into an object?
  the friction it clears: why components take one props object instead of multiple positional arguments.
  Scene & Repetition: Imagine a restaurant kitchen. If the waiter shouted five different ingredients across the room in a specific order, one misheard word would ruin the dish. Instead, the waiter writes the entire customer order onto a single order ticket and clips it to the kitchen wheel. The ticket holds all instructions in one tidy package. In React, the **`props` object** is that order ticket. Instead of passing five positional parameters that could get mixed up, React packages every attribute into a single **`props` object**. The child component unclips the ticket and reads the exact instructions it needs.
  Key Terms (Bold): **props object**, **destructuring**, **positional arguments**.
  Resolution: Bundling props into a single dictionary ensures arguments never depend on fragile parameter ordering and simplifies component signatures.
- [tip] To impress the interviewer: When asked how props work in React, explain that JSX attributes are syntactic sugar for the single props argument passed to the component function. Highlight that props can carry any JavaScript value: primitives, arrays, objects, JSX elements, and functions. Emphasize that parameter destructuring with default values (`{ variant = 'secondary' }`) is the universal React standard because it makes component contracts self-documenting. ◼ Senior interview positioning on props mechanics and syntactic sugar.

### Why Props Are Read-Only: Purity and Unidirectional Data Flow
- [p] ◇ {preknowledge:} In earlier lessons, we learned that React renders UI by calling component functions (see Lecture 3). When a component needs to change what appears on screen in response to user interaction, a beginner's instinctive reflex is to reassign its props: `props.label = "Saved"`. What is **unidirectional data flow**? In React, **unidirectional data flow** (also called **one-way data flow**) is the architectural rule where data travels exclusively downward through the component tree, from parent to child. In traditional imperative scripting or two-way data-binding frameworks, a child can mutate variables shared with its parent, creating hidden side effects and state drift across unrelated screens. In modern React, the parent owns the data and passes read-only snapshots downward. The law of unidirectional data flow states: data flows strictly downward from parent to child through props, and a child component can never mutate the props it receives. ◼ Defines unidirectional data flow with its default sentence and law sentence; terms introduced: **unidirectional data flow**, **one-way data flow**, **component purity**.
- [p] ★ {preknowledge:} In JavaScript, plain objects are mutable by default: you can add, change, or delete properties on any ordinary object literal at any time. {problem:} In React, components must behave like pure functions with respect to their inputs: given the same props, a component must always return the exact same JSX and produce zero side effects during rendering. If a child component were allowed to mutate `props.label = "Saved"`, it would silently modify the object stored in the parent's memory. To protect this boundary, React freezes the `props` object in development using `Object.freeze(props)`. When code tries to assign to a prop, JavaScript strict mode halts execution and throws a fatal TypeError: `Cannot assign to read-only property 'label' of object '#<Object>'`. ◼ Explains runtime freezing via Object.freeze and the resulting TypeError; terms introduced: **immutable props**, **Object.freeze**, **TypeError**.
- [code] Mutating props anti-pattern vs Pure derived calculation:
```jsx title="PropsImmutabilityContract"
function BrokenButton(props) {
  props.label = 'Saved'; // **WRONG:** Mutating frozen props throws fatal **TYPEERROR**
  return <button>{props.label}</button>;
}
function PureButton({ label }) {
  const display = label.toUpperCase(); // **RIGHT:** Computes **LOCAL** derived value
  return <button>{display}</button>;
}
```
◼ **The what-this-introduces list:** 1. `BrokenButton`: anti-pattern attempting direct mutation of incoming props. 2. `props.label = 'Saved'`: illegal assignment triggering TypeError at runtime. 3. `PureButton`: pure component deriving local formatted text without mutating inputs.
- [p] ★ Deconstruction of the immutability contrast: Look at line 2 in `BrokenButton`: assigning directly to `props.label` attempts to mutate a frozen object. In modern React and JavaScript strict mode, this line crashes the application with a TypeError. Even in an environment without strict mode, mutating `props` does not tell React to re-render, creating silent **state drift** where the internal object changed but the screen never updated. Now look at lines 6 and 7 in `PureButton`: if you need a modified version of an incoming prop, calculate a new local variable during render. The incoming prop `label` remains completely untouched. ◼ Explains why mutation fails both mechanically and architecturally.
- [p] ★ {preknowledge:} How do props change over time if they are immutable? Props are not static constants; a component may receive different props across different renders. Imagine an editorial clock or live story card: the parent component re-renders with new data from a timer or network request and passes a brand-new props object downward. The child component casts its old props object aside, and the JavaScript garbage collector reclaims that memory. The child then executes its function again with the new props snapshot, returning fresh JSX to match. ◼ Explains how props change across render cycles; terms introduced: **props snapshot**, **render cycle**.
- [grounding] the opening question: Why can a component never change its props?
  the friction it clears: why child components are forbidden from modifying their own input data.
  Scene & Repetition: Imagine a manager gives an accountant a signed financial budget on paper. The accountant's job is to calculate taxes based on that budget. What would happen if the accountant took an eraser, changed the budget numbers on the paper, and pretended the manager approved it? The company's financial records would be completely corrupted. In React, a child component is that accountant: the parent hands it a signed **read-only contract** in the form of **props**. If the child could mutate that paper, the parent's data and sibling components would silently corrupt. This is **component purity**: props are read-only inputs that guarantee predictable rendering across the entire application.
  Key Terms (Bold): **read-only contract**, **component purity**, **unidirectional data flow**, **state drift**.
  Resolution: Freezing props protects component purity and prevents silent state corruption across parent and sibling components.

### Passing Objects, Numbers, and Functions as Props
- [p] ◇ {preknowledge:} In earlier sections, we passed strings and plain objects as props. In real production applications, props are not limited to text; you can pass numbers, booleans, arrays, nested objects, and callback functions. What is a **prop contract**? A **prop contract** is the explicit specification of what props a component expects to receive from its parent, including property names, data types, and default values. In plain JavaScript, passing unexpected arguments causes silent errors or NaN calculations. In React, writing clear destructured signatures with default values establishes an explicit contract between parent and child. The law of prop contracts states: a child component specifies what props it can receive, and the parent must supply data matching that contract. ◼ Defines prop contract with its default sentence and law sentence; terms introduced: **prop contract**, **data types**, **callback props**.
- [code] Complex prop types in action:
```jsx title="ComplexPropsContract"
export function MetricPill({ count, label, isLive = false }) {
  const badge = isLive ? ' [LIVE]' : ''; // **CODE LOGIC:**<br>Computes status modifier string from boolean prop
  return (
    <div className="metric-pill">
      <span className="count">{count.toLocaleString()}</span> // **CODE LOGIC:**<br>Formats number prop using toLocaleString
      <span className="label">{label}{badge}</span> // **DATA FLOW:**<br>Renders label and dynamic status badge
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `count`: number prop formatted via toLocaleString. 2. `isLive = false`: boolean prop with default fallback. 3. `badge`: local derived string calculated during render.
- [p] ★ Deconstruction of complex prop types: Look at line 1 in `MetricPill`: the component accepts three different data types: `count` (a number), `label` (a string), and `isLive` (a boolean with default `false`). When mounting this component, the parent writes `<MetricPill count={1420} label="Readers" isLive={true} />`. Look at line 5: `count.toLocaleString()` calls a number method directly because `count` was passed inside curly braces as a real number rather than a string. ◼ Deconstructs diverse prop types; explains number formatting.
- [grounding] the opening question: Why can props carry any JavaScript value?
  the friction it clears: why props are not limited to string HTML attributes.
  Scene & Repetition: Imagine a postal courier that only accepted handwritten paper letters. If you needed to send a book, a set of keys, or a photograph, the courier would refuse the delivery. That is how traditional HTML attributes work: they only understand plain string text. In React, **props** are an unrestricted shipping container. You can load a string, a number, a complex data object, an array of stories, or even a callback function into that container. React delivers the package intact to the child component. This unrestricted delivery is what makes React components truly modular: they communicate using the full power of the JavaScript language.
  Key Terms (Bold): **props**, **unrestricted delivery**, **callback function**, **shipping container**.
  Resolution: Because React compiles JSX attributes to JavaScript object properties, props can carry any valid JavaScript data type without serialization.

### Glossary
- [definition] **Props**: Plain JavaScript objects passed from parent to child components to configure their behavior and visual output.
- [definition] **Component Purity**: The design principle where component functions return JSX calculated strictly from their inputs (props and state) without causing observable side effects.
- [definition] **Unidirectional Data Flow**: The architectural model where data flows strictly downward from parent to child through the component tree.
- [definition] **Object Destructuring**: A JavaScript syntax that unpacks properties from an object into distinct local variables directly in function parameters.
- [definition] **Object.freeze**: A native JavaScript method used by React in development to make props objects strictly read-only, preventing runtime mutation.
- [definition] **Prop Contract**: The explicit specification of property names, data types, and default values that a component expects to receive from its parent.

### Summary
- [review-title] **Passing Data with Props and the Immutability Contract in React 19**
- [p] In modern React, props are the primary mechanism for component communication and code reuse. Here is your streetwise review.
- [review-subtitle] ❒ Core Principles of Props and Component Architecture
- [numbered-review-point] 1. Pass data into components by declaring **custom JSX attributes**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) String literals use double quotes (`label="Publish"`), while numbers, booleans, and objects require curly braces (`count={5}`).<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) React bundles all attributes into a single plain JavaScript object called `props` and passes it as the function argument.
- [numbered-review-point] 2. Read props cleanly using **parameter destructuring with default fallbacks**.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Destructuring `{ label, variant = 'secondary' }` extracts named properties directly into local function scope.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Default parameters ensure safe fallback values when the parent component omits optional props.
- [numbered-review-point] 3. Respect the **immutable read-only contract** of props.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Mutating props violates component purity and throws a fatal TypeError in development because React freezes the object.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) To change on-screen data, the parent must render again and pass a brand-new props snapshot downward.
- [never-rule] ➔ NEVER reassign or mutate a prop inside a component function.
- [always-rule] ➔ ALWAYS use parameter destructuring with default fallbacks for clean component signatures.
- [if-then-rule] ➔ IF you need to pass numbers, booleans, objects, or variables THEN **wrap them in JSX curly braces `{}`**.
- [do-this-header] **DO THIS:** Parameterize components with destructured props and derive local values without mutation.
- [do-this-code] Proper props consumption in ActionButton.jsx:
```jsx right title="ActionButton.jsx"
export default function ActionButton({ label, variant = 'secondary' }) {
  return (
    <button className={`btn btn-${variant}`}>
      {label}
    </button>
  );
}
```
- [do-not-do-this-header] **DO NOT DO THIS:** Never hardcode text or mutate incoming props inside a component.
- [do-not-do-this-code] Broken button mutation anti-pattern:
```jsx wrong title="BrokenButtonMutation"
export default function BrokenButton(props) {
  props.label = 'Saved';
  return (
    <button className="btn-fixed">
      {props.label}
    </button>
  );
}
```
