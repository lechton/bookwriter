### The Push vs Pull Architecture
- [p] ◇ {preknowledge:} In Lecture 20, we learned how controlled inputs synchronize React state with DOM elements on every keystroke using `value` and `onChange`. {problem:} Why is controlling every single input field not always the best architectural choice? ◼ Pedagogical qualification: Establish the architectural overhead of controlled inputs; terms introduced: **push vs pull**, **keystroke re-renders**, **form architecture**.
- [p] ★ {preknowledge:} The choice between controlled and uncontrolled forms comes down to a fundamental architectural question: **Do you need the data *while* the user is typing (Push), or only *when* the user submits (Pull)?** Controlled inputs represent a **Push architecture**: every keystroke pushes data into React state and triggers a component re-render. Uncontrolled inputs represent a **Pull architecture**: the browser DOM holds the input values silently with zero re-renders, and your code pulls the values out only when the submit button is clicked. ◼ Pedagogical qualification: Define Push vs Pull mental model; terms introduced: **push architecture**, **pull architecture**, **submit extraction**.
- [p] ★ {preknowledge:} In modern web development, extracting values from an uncontrolled form at submit time is remarkably simple using the native browser `FormData` API. As long as each input has a `name` attribute, `new FormData(event.currentTarget)` collects all form fields in a single line of code without requiring any `useState` hooks or `useRef` bindings. ◼ Pedagogical qualification: Introduce native FormData extraction; terms introduced: **native FormData**, **name attribute**, **submit extraction**.
- [code] Controlled push vs uncontrolled pull extraction:
```jsx title="Controlled Push vs Uncontrolled Pull"
// PUSH: Controlled state re-renders on every keystroke:
<input value={name} onChange={e => setName(e.target.value)} />
// PULL: Uncontrolled DOM extracted at submit time:
<input defaultValue="Elena" name="readerName" />
const data = new FormData(event.currentTarget);
const name = data.get('readerName');
```
- [grounding] Leading Question: Can you mix controlled and uncontrolled inputs in the same form?
  Confusion Point: Does choosing uncontrolled mean the entire form must be uncontrolled?
  Scene & Repetition: Absolutely not! You can freely mix both strategies. For example, a search filter with autocomplete requires real-time suggestions: make that specific field controlled. The rest of the form (shipping address, phone number, delivery instructions) only matters at submit time: leave them uncontrolled. Choose the strategy that matches each field's specific interactive requirements.
  Key Terms (Bold): `**hybrid form architecture**`, `**field-level strategy**`, `**selective control**`, `**granular re-rendering**`.
  Resolution: Form architecture is not all-or-nothing; control only the specific fields that require real-time feedback and leave the rest uncontrolled.

### The Decision Matrix and Trade-Offs
- [p] ◇ {preknowledge:} We know controlled forms offer instant access while uncontrolled forms avoid typing re-renders. {problem:} What are the exact technical criteria that dictate when to choose controlled state over uncontrolled FormData? ◼ Pedagogical qualification: Establish the formal decision matrix; terms introduced: **decision criteria**, **instant validation**, **file uploads**.
- [p] ★ {preknowledge:} Choose **controlled inputs** when you need: (1) **Instant field validation**: showing error messages while typing before submit. (2) **Conditional form controls**: disabling the submit button until all required fields are valid. (3) **Dependent fields**: showing or hiding additional inputs based on a dropdown selection. (4) **Dynamic input formatting**: masking credit card numbers or phone numbers in real time. (5) **External state coordination**: populating inputs from external WebSocket feeds or URL query params. ◼ Pedagogical qualification: Enumerate controlled input winning scenarios; terms introduced: **instant validation**, **conditional controls**, **dependent fields**, **input masking**.
- [p] ★ {preknowledge:} Choose **uncontrolled inputs** when you need: (1) **Simple submit-only forms**: contact forms, login forms, or feedback submissions where data is only read at submit. (2) **High-performance forms**: massive tables or spreadsheets with hundreds of inputs where re-rendering on every keystroke causes lag. (3) **File inputs**: `<input type="file" />` is inherently read-only and *must always be uncontrolled* in React. (4) **Non-React integration**: integrating with legacy jQuery or vanilla DOM libraries that manage their own inputs. ◼ Pedagogical qualification: Enumerate uncontrolled input winning scenarios; terms introduced: **submit-only forms**, **high-density forms**, **file input constraint**, **legacy integration**.
- [code] Uncontrolled FormData extraction pattern:
```jsx title="FormData Extraction on Submit"
function handleSubmit(e) {
  e.preventDefault();
  const form = new FormData(e.currentTarget);
  const feedback = {
    author: form.get('author'),
    comment: form.get('comment')
  };
  sendFeedback(feedback);
}
```
- [grounding] Leading Question: Why is an input of type file always uncontrolled?
  Confusion Point: Can you write `<input type="file" value={file} />`?
  Scene & Repetition: Never! For browser security reasons, JavaScript cannot imperatively set the `value` of a file input (otherwise a malicious script could upload arbitrary files from the user's hard drive). The browser keeps file selection strictly in DOM memory. In React, `<input type="file" />` is always uncontrolled; you read selected files via `e.target.files` or `FormData`.
  Key Terms (Bold): `**file input security**`, `**inherently uncontrolled**`, `**browser security sandbox**`, `**files property**`.
  Resolution: File inputs are inherently uncontrolled in React because browser security prevents programmatic setting of file paths.

### Step 1: First, we construct the parent container ArticleFeedback.jsx
- [p] ★ {preknowledge:} The parent container manages the submitted author state. It passes `setAuthor` down to `FeedbackForm` and `author` down to `FeedbackReceipt`. {problem:} The parent must coordinate submission confirmation. ◼ Pedagogical qualification: Construct parent container coordinating submission receipt.
- [code] Parent container ArticleFeedback.jsx:
```jsx title="ArticleFeedback.jsx"
import { useState } from 'react';
import FeedbackForm from './components/FeedbackForm.jsx';
import FeedbackReceipt from './components/FeedbackReceipt.jsx';
export default function ArticleFeedback() {
  const [author, setAuthor] = useState(null);
  return (
    <main><FeedbackForm onSubmit={setAuthor} /><FeedbackReceipt author={author} /></main>
  );
}
```
- [p] ★ Step 1 establishes submission state: Look at line 5: `const [author, setAuthor] = useState(null);`. Notice that the parent does NOT track typing keystrokes: it only stores the finalized author once the form is submitted. We will build `FeedbackForm` next in step 2. ◼ Pedagogical qualification: Deconstruct submission-only parent state.

### Step 2: Next, we declare the form child FeedbackForm.jsx
- [p] ★ {preknowledge:} Step 1 passed `onSubmit` to `FeedbackForm`. {problem:} The child component must render an uncontrolled form and extract values via `FormData` on submit. ◼ Pedagogical qualification: Build uncontrolled form extracting values on submit.
- [code] Form child FeedbackForm.jsx:
```jsx title="FeedbackForm.jsx"
export default function FeedbackForm({ onSubmit }) {
  const handleSubmit = e => {
    e.preventDefault();
    onSubmit(new FormData(e.currentTarget).get('author'));
  };
  return (
    <form onSubmit={handleSubmit}>
      <input defaultValue="Elena Vance" name="author" /><button type="submit">Submit</button>
    </form>
  );
}
```
- [p] ★ Step 2 fulfills the uncontrolled form: Look at lines 2 through 5: `new FormData(e.currentTarget).get('author')` extracts the input value directly from the DOM on submit. The input uses `defaultValue="Elena Vance"` and `name="author"`, operating with zero keystroke re-renders. ◼ Pedagogical qualification: Deconstruct uncontrolled form submission.

### Step 3: Then, we declare the receipt child FeedbackReceipt.jsx
- [p] ★ {preknowledge:} Step 1 passed `author` to `FeedbackReceipt`. {problem:} The child component must render the confirmation receipt once feedback is received. ◼ Pedagogical qualification: Build receipt display component.
- [code] Receipt child FeedbackReceipt.jsx:
```jsx title="FeedbackReceipt.jsx"
export default function FeedbackReceipt({ author }) {
  if (!author) return null;
  return (
    <div className="receipt-card">
      <p>Feedback registered for {author}</p>
    </div>
  );
}
```
- [p] ★ Step 3 completes the confirmation receipt: Look at lines 1 through 8: `FeedbackReceipt` renders nothing while `author` is `null`, and displays the confirmation once the form submits. ◼ Pedagogical qualification: Deconstruct conditional receipt display.
- [p] What would happen if `FeedbackForm` omitted the `name` attribute on the input? `new FormData(e.currentTarget)` relies on the `name` attribute to map form fields. If `name` is omitted, the input's value will not be included in the `FormData` object, and `form.get('author')` will return `null`. ◼ Pedagogical qualification: Apply Negative Counterfactual Law to missing name attributes in FormData.

### Step 4: Finally, we seal the application entry point main.jsx
- [p] ★ {preknowledge:} In Steps 1 through 3 we created the uncontrolled form component tree. Now we inspect `main.jsx`, which mounts `ArticleFeedback` to the DOM. {problem:} The entry point must initialize the React root and render the top-level feedback manager. ◼ Pedagogical qualification: Seal architecture at application entry point.

- [grounding] Leading Question: When should you use a form library like React Hook Form?
  Confusion Point: If native uncontrolled forms are so simple, why do libraries like React Hook Form exist?
  Scene & Repetition: Native `FormData` is perfect for simple forms with straightforward submit actions. - [callout] > [!TIP]
**To impress the interviewer:** When asked whether forms should be controlled or uncontrolled, frame the answer around the **Push vs Pull decision model**. Use controlled state when you need *push* capabilities (real-time validation, character limits, dependent fields, dynamic disabling). Use uncontrolled inputs with `FormData` when you only need *pull at submit* values, high performance across dozens of fields, or file inputs. Conclude by noting that modern React allows hybrid architectures where only specific fields are controlled.

### Where you will meet this
- Login and authentication forms: extracting username and password at submit with `FormData`.
- Complex profile editors: controlling interactive photo croppers while leaving address fields uncontrolled.
- Checkout flows: controlling payment fields for real-time card validation while leaving shipping notes uncontrolled.
- Document uploaders: handling `<input type="file" />` with native uncontrolled extraction.

### Glossary
- **Push Architecture**: The controlled model where every user keystroke pushes updates into state and triggers re-renders.
- **Pull Architecture**: The uncontrolled model where values remain in the DOM until explicitly pulled at submit time.
- **FormData**: The native browser API that collects name-value pairs from an HTML form element.
- **Hybrid Form**: A form that mixes controlled inputs (for real-time needs) and uncontrolled inputs (for submit-only needs).
- **File Input**: A specialized `<input type="file" />` that is inherently read-only and must always be uncontrolled in React.
- **Keystroke Re-Render**: A component re-render triggered on every character typed into a controlled input.

### Summary

**React 19 Form Architecture Invariants**

In daily production, choosing between controlled and uncontrolled forms is an essential architectural decision. Selecting the right model based on whether data is needed during typing or only at submit time ensures optimal performance and maintainable code. Here is your streetwise review.

❒ Form Architecture Invariants

1. Controlled inputs push data to state on every keystroke.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Choose controlled when you need live validation, character counts, or dependent fields.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Controlled inputs re-render the component on every keystroke.

2. Uncontrolled inputs keep data in the DOM until submit.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Choose uncontrolled when data is only needed at submit time or for file inputs.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Extract values easily with `new FormData(event.currentTarget)`.

3. Always provide a `name` attribute on uncontrolled inputs.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `FormData` uses the `name` attribute as the key for extraction.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Missing `name` attributes cause values to be dropped from submission.

➔ NEVER control every input by default if the data is only read at submit time.

➔ ALWAYS provide `name` attributes on uncontrolled inputs for `FormData` extraction.

➔ IF handling file uploads THEN **use uncontrolled inputs because file paths cannot be set programmatically**.

**DO THIS:** Use uncontrolled inputs with FormData for clean submit-only forms.

```jsx right title="FeedbackForm.jsx"
// Clean uncontrolled form extracting values at submit
export default function FeedbackForm({ onSubmit }) {
  function handleSubmit(e) {
    e.preventDefault();
    onSubmit(new FormData(e.currentTarget).get('author'));
  }
  return (
    <form onSubmit={handleSubmit}>
      <input defaultValue="Elena" name="author" />
      <button type="submit">Submit</button>
    </form>
  );
}
```

**DO NOT DO THIS:** Never create unnecessary useState variables for submit-only forms.

```jsx wrong title="Over-Controlled Form Anti-Pattern"
// FAILS: Unnecessary keystroke re-renders for submit-only data!
export default function BrokenForm({ onSubmit }) {
  const [author, setAuthor] = useState('Elena');
  function handleSubmit(e) {
    e.preventDefault();
    onSubmit(author);
  }
  return <input onChange={e => setAuthor(e.target.value)} value={author} />;
}
```

| | **CONTROLLED FORM (`useState`)**<br>(Push Architecture) | **UNCONTROLLED FORM (`FormData`)**<br>(Pull Architecture) |
| ---: | :--- | :--- |
| **Data flow** | Pushes to React state on<br>every single keystroke | Stored in DOM; pulled only<br>upon form submission |
| **Component re-renders** | Re-renders component tree on<br>every character typed | Zero re-renders during typing;<br>fast performance |
| **Real-time validation** | Instant validation, error<br>banners, character limits | Validation occurs only at<br>submit time |
| **Dependent fields** | Easily hides/shows fields<br>based on other inputs | Requires manual DOM refs or<br>hybrid state |
| **File inputs** | Cannot control `<input`<br>`type="file" />` | Native support for all file<br>uploads via FormData |
