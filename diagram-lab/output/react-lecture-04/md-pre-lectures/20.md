### The Controlled Input Contract
- [p] ◇ {preknowledge:} In HTML, form elements like `<input>` maintain their own internal state in the browser DOM. When a user types, the DOM node updates its own `value` property directly. {problem:} Why does passing `value={text}` without an `onChange` handler freeze the input and prevent the user from typing? ◼ Pedagogical qualification: Contrast native DOM input behavior with React controlled inputs; terms introduced: **uncontrolled DOM state**, **controlled input contract**, **frozen input**.
- [p] ★ {preknowledge:} In React, a **controlled input** transfers ownership of the input's value from the DOM to React state. The component's state becomes the **single source of truth**. This requires a two-way contract: (1) `value={state}` pushes the current state into the DOM on every render. (2) `onChange={e => setState(e.target.value)}` intercepts user keystrokes, reads the event value, and updates state. If you supply `value` without `onChange`, React re-renders on every keystroke and forces the input's DOM value back to the state snapshot, freezing the input completely. ◼ Pedagogical qualification: Explain the two-way loop of value and onChange; terms introduced: **single source of truth**, **two-way contract**, **target value**.
- [p] ★ {preknowledge:} If you only want to set the initial value and let the DOM handle user typing, use `defaultValue="Initial text"` instead of `value`. This creates an **uncontrolled input**, where React sets the initial DOM value on mount and never touches it again. ◼ Pedagogical qualification: Contrast controlled value with uncontrolled defaultValue; terms introduced: **uncontrolled input**, **defaultValue**, **DOM autonomy**.
- [code] Controlled vs uncontrolled input declaration:
```jsx title="Controlled vs Uncontrolled Input"
// CONTROLLED: React state is the single source of truth:
<input value={text} onChange={e => setText(e.target.value)} />
// UNCONTROLLED: DOM owns the state after mount:
<input defaultValue="Initial text" />
```
- [grounding] Leading Question: What happens if state transforms or filters the value inside onChange?
  Confusion Point: Can you force an input to stay uppercase or strip special characters inside `onChange`?
  Scene & Repetition: Yes! Because React controls the value, you can sanitize input in real time: `onChange={e => setText(e.target.value.toUpperCase())}`. When the user types lowercase 'a', `onChange` runs, converts it to 'A', and updates state. React re-renders and pushes 'A' into the DOM. The user physically cannot type a lowercase letter. Controlled inputs give you absolute authority over what appears in the field.
  Key Terms (Bold): `**real-time sanitization**`, `**controlled transformation**`, `**input filtering**`, `**state authority**`.
  Resolution: Controlled inputs allow components to intercept, transform, or reject user keystrokes before they are committed to the screen.

### Textareas, Selects, and Multi-Field State
- [p] ◇ {preknowledge:} In standard HTML, `<textarea>` uses child text (`<textarea>hello</textarea>`), and `<select>` uses `<option selected>`. {problem:} How does React standardize textareas and selects into the controlled component model? ◼ Pedagogical qualification: Address HTML inconsistency vs React standardization; terms introduced: **React standardization**, **controlled textarea**, **controlled select**.
- [p] ★ {preknowledge:} React eliminates HTML's syntax inconsistencies by standardizing `<textarea>` and `<select>` to use the exact same `value` and `onChange` props as `<input>`. In React, `<textarea value={text} onChange={e => setText(e.target.value)} />` takes `value` directly instead of children. Similarly, `<select value={choice} onChange={e => setChoice(e.target.value)}>` takes `value` on the `<select>` tag itself, automatically selecting the matching child `<option>`. ◼ Pedagogical qualification: Explain unified value/onChange API across form elements; terms introduced: **unified form API**, **select value prop**, **textarea value prop**.
- [p] ★ {preknowledge:} For forms with multiple fields, you can either declare individual `useState` calls (`const [name, setName] = useState('')`) or manage a single form object (`const [form, setForm] = useState({ name: '', email: '' })`) updated via `setForm(f => ({ ...f, [e.target.name]: e.target.value }))`. ◼ Pedagogical qualification: Introduce multi-field form state management; terms introduced: **computed property names**, **form object state**, **field decoupling**.
- [code] Controlled select and textarea syntax:
```jsx title="Controlled Select and Textarea"
// Unified value and onChange across all form elements:
<select value={role} onChange={e => setRole(e.target.value)}>
  <option value="reporter">Reporter</option>
  <option value="editor">Editor</option>
</select>
<textarea value={bio} onChange={e => setBio(e.target.value)} />
```
- [grounding] Leading Question: What is the "uncontrolled to controlled" warning?
  Confusion Point: Why does React warn `A component is changing an uncontrolled input to be controlled`?
  Scene & Repetition: If you initialize state to `undefined` or omit it (`useState()`), `value={text}` evaluates to `undefined`. React treats `value={undefined}` as an uncontrolled input! When the user types, state updates to a string (e.g. `'a'`), and `value` is suddenly a defined string. React sees the input switch from uncontrolled to controlled and throws a console warning. Always initialize form state with empty strings: `useState('')`.
  Key Terms (Bold): `**uncontrolled to controlled warning**`, `**undefined initial state**`, `**empty string initialization**`, `**input stability**`.
  Resolution: Always initialize input state to an empty string `''` rather than `undefined` to prevent inputs from switching between uncontrolled and controlled modes.

### Glossary
- **Controlled Input**: A form element whose displayed value is driven by React state and updated via event handlers.
- **Uncontrolled Input**: A form element that maintains its own internal value in the DOM, optionally initialized via `defaultValue`.
- **Two-Way Contract**: The pair of `value={state}` and `onChange={handler}` props required to make an input controlled and editable.
- **Single Source of Truth**: The architectural design where one piece of state (React state) exclusively determines the value across the application.
- **defaultValue**: An HTML attribute in React used to set the initial value of an uncontrolled input on mount.
- **Event Target Value**: The `e.target.value` property extracted from the browser event representing the current text inside the input element.

### Summary

**React 19 Controlled Input Invariants**

In daily production, controlled inputs provide total authority over form data, validation, and real-time UI synchronization. Implementing the two-way contract properly guarantees editable, predictable form controls. Here is your streetwise review.

❒ Controlled Input Invariants

1. Controlled inputs require both `value` and `onChange`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) `value={state}` pushes state into the DOM.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) `onChange={e => setState(e.target.value)}` pulls user edits into state.

2. Never supply `value` without `onChange` unless the input is explicitly read-only.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Omitting `onChange` freezes the input and triggers React warnings.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use `readOnly` if the input is meant to display uneditable text.

3. Always initialize controlled input state to an empty string `''`.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Initializing to `undefined` or `null` makes the input start as uncontrolled.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Updating it later triggers the "uncontrolled to controlled" warning.

➔ NEVER initialize controlled form state to `undefined` or `null`.

➔ ALWAYS pair `value` with `onChange` on inputs, textareas, and selects.

➔ IF an input is completely independent and only read at submit THEN **consider an uncontrolled input with `defaultValue`**.

**DO THIS:** Pair value and onChange to maintain full control over the input.

```jsx right title="CorrectionInput.jsx"
// Fully controlled input with two-way synchronization
export default function CorrectionInput({ value, onChange }) {
  return (
    <input
      onChange={e => onChange(e.target.value)}
      value={value}
    />
  );
}
```

**DO NOT DO THIS:** Never supply value without onChange expecting the user to type freely.

```jsx wrong title="Frozen Input Anti-Pattern"
// FAILS: Value is supplied without onChange; input is frozen!
export default function BrokenInput({ value }) {
  return (
    <input
      value={value}
    />
  );
}
```
