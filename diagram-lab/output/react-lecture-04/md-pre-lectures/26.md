### The Three State Tests and Redundant State
- [p] ◇ {preknowledge:} In earlier lectures we learned that `useState` preserves data across re-renders and triggers UI updates. When designing features, newcomers often declare a state variable for every dynamic value on screen: raw items, filter input, filtered output, and total count. {problem:} Why does storing filtered items or item counts in state inevitably cause synchronization bugs? ◼ Pedagogical qualification: Contrast naive state proliferation with state drift; terms introduced: **state proliferation**, **synchronization drift**, **redundant state**.
- [p] ★ {preknowledge:} React provides three definitive tests to determine if a value belongs in state:
  1. Does it remain unchanged over time? If so, it is NOT state (use a plain constant).
  2. Is it passed from a parent via props? If so, it is NOT state (it belongs to the parent).
  3. Can you compute it from existing state or props? If so, it is **DEFINITELY NOT state**—it is **derived state**!
  When you store derived values (like `filteredStories` or `count`) in separate state variables, every event handler that updates `stories` or `query` must remember to manually recalculate and set both dependent states. If even one handler forgets, the values drift apart and the UI lies to the reader. ◼ Pedagogical qualification: Establish the three state tests and define derived state; terms introduced: **three state tests**, **derived state**, **single source of truth**.
- [p] ★ {preknowledge:} Instead of storing derived values in state, compute them directly in the body of the component during render. Because React re-runs the component function on every state update, the derived values are always fresh, perfectly synchronized, and require zero synchronization code. ◼ Pedagogical qualification: Teach calculation during render as primary pattern; terms introduced: **render-time computation**, **automatic synchronization**, **zero-drift guarantee**.
- [code] Redundant vs derived state contrast:
```jsx title="Redundant vs Derived State"
// WRONG: Redundant state variables drift out of sync!
const [stories, setStories] = useState(initialStories);
const [query, setQuery] = useState('');
const [filtered, setFiltered] = useState(initialStories); // BUG!
// RIGHT: Calculate derived values on the fly during render:
const [stories, setStories] = useState(initialStories);
const [query, setQuery] = useState('');
const filtered = stories.filter(s => s.title.includes(query));
const count = filtered.length;
```
- [grounding] Leading Question: What about performance if the filter calculation is expensive?
  Confusion Point: If a calculation is run on every render, won't it slow down the application?
  Scene & Repetition: In 99% of cases, filtering an array of several hundred items takes less than 1 millisecond; computing it during render is virtually free. If and only if the calculation is genuinely expensive (e.g. searching 50,000 items), wrap the computation in `useMemo`: `const filtered = useMemo(() => stories.filter(...), [stories, query])`. Even then, it remains a **derived calculation**, never a separate state variable!
  Key Terms (Bold): `**useMemo memoization**`, `**expensive calculation**`, `**render-time cost**`, `**premature optimization**`.
  Resolution: Derived state should be calculated on the fly; if profiling proves it is slow, use `useMemo` instead of declaring separate state.

### Avoiding Duplicate and Contradictory State
- [p] ◇ {preknowledge:} We know not to store computed values in state. {problem:} What other structural mistakes lead to state corruption in production apps? ◼ Pedagogical qualification: Transition to duplicate and contradictory state patterns; terms introduced: **duplicate state**, **contradictory state**, **state normalization**.
- [p] ★ {preknowledge:} A very common antipattern is storing a selected object in state: `const [selectedStory, setSelectedStory] = useState(stories[0])`. If the user edits the story title in `stories`, `selectedStory` still holds the old object copy! You now have two diverging copies of the same data. The solution is to store only the **selected ID** in state: `const [selectedId, setSelectedId] = useState(1)`. Then derive the selected object: `const selectedStory = stories.find(s => s.id === selectedId)`. ◼ Pedagogical qualification: Teach ID reference normalization over object cloning; terms introduced: **selected ID pattern**, **normalized state**, **object duplication trap**.
- [p] ★ {preknowledge:} Another frequent trap is contradictory boolean flags: `const [isSending, setIsSending] = useState(false)` and `const [isSent, setIsSent] = useState(false)`. It is possible for a bug to leave both flags set to `true`, creating an impossible UI state. Instead, unify mutually exclusive states into a single status variable: `const [status, setStatus] = useState('idle')` where status can only be `'idle' | 'sending' | 'sent' | 'error'`. ◼ Pedagogical qualification: Eliminate impossible states via status enum; terms introduced: **impossible states**, **status enum**, **mutually exclusive state**.
- [code] Selected object vs selected ID:
```jsx title="Selected Object vs Selected ID"
// WRONG: Duplicated object; edits to stories will not update selectedStory!
const [selectedStory, setSelectedStory] = useState(stories[0]);
// RIGHT: Store the ID, derive the object:
const [selectedId, setSelectedId] = useState(stories[0]?.id);
const selectedStory = stories.find(s => s.id === selectedId);
```
- [grounding] Leading Question: What should you do when props are passed as initial state?
  Confusion Point: If a component receives `initialQuery` as a prop, is it safe to do `useState(initialQuery)`?
  Scene & Repetition: `useState(initialQuery)` only uses `initialQuery` on the very first mount; if the parent passes a new `initialQuery` prop later, React ignores it! Only use props in `useState` if the state is truly intended to be independent after initialization (prefixing the prop with `initial` or `default`). If the child should always reflect the parent prop, do not put it in state at all!
  Key Terms (Bold): `**prop mirroring**`, `**initial prop convention**`, `**stale initializer**`, `**controlled flow**`.
  Resolution: Mirroring props in state creates stale duplicates; treat props as the single source of truth unless intentionally detached.

### Step 1: First, we construct the parent container WireFilter.jsx
- [p] ★ {preknowledge:} The parent container defines the minimal raw state (`stories` and `query`) and computes `filteredStories` and `matchCount` during render. {problem:} The parent must demonstrate that filtered output and count require zero useState calls. ◼ Pedagogical qualification: Construct parent container demonstrating render-time derived state.
- [code] Parent container WireFilter.jsx:
```jsx title="WireFilter.jsx"
import { useState } from 'react';
import SearchBox from './components/SearchBox.jsx';
import StoryFeed from './components/StoryFeed.jsx';
const INITIAL = [{ id: 1, title: 'Metro Transit Accord' }, { id: 2, title: 'Federal Reserve Meeting' }];
export default function WireFilter() {
  const [stories, setStories] = useState(INITIAL);
  const [query, setQuery] = useState('');
  const filtered = stories.filter(s => s.title.toLowerCase().includes(query.toLowerCase()));
  return (
    <div className="filter-panel"><SearchBox query={query} onQuery={setQuery} /><StoryFeed items={filtered} count={filtered.length} /></div>
  );
}
```
- [p] ★ Step 1 establishes minimal state: Look at lines 7 and 8: only `stories` and `query` are in `useState`. Look at line 9: `filtered` is calculated on the fly. Look at line 11: `count` is derived directly as `filtered.length`. We will build `SearchBox` next in step 2. ◼ Pedagogical qualification: Deconstruct minimal state and on-the-fly derivation.

- [callout] > [!TIP]
**To impress the interviewer:** When asked how to structure state, quote the core rule: **State should be minimal, non-redundant, and non-contradictory**. State the three tests: (1) Does it stay constant? (2) Is it passed as props? (3) Can you compute it from existing state or props? If you can compute it, compute it on the fly during render! Mention that for selections, you should store the selected item's **ID**, never the whole object, to avoid stale duplicate data.

### Where you will meet this
- Filtered lists and tables: computing search results and row counts during render instead of syncing state.
- Form validation: computing `isValid` and error messages from field values during render.
- Shopping cart totals: calculating subtotals, taxes, and shipping from item quantities on the fly.
- Selected entity views: storing `selectedId` and looking up the active record in the master collection.

### Glossary
- **Derived State**: Any value that can be computed from existing props or state during render without `useState`.
- **Minimal State**: The principle of storing only the raw, irreducible data required to represent UI changes.
- **Redundant State**: Storing duplicate or computable values in separate state variables, risking desynchronization.
- **Selected ID Pattern**: Storing only the unique identifier of an active item in state and looking up the full object during render.
- **Status Enum**: Replacing multiple mutually exclusive boolean flags with a single union string (`'idle' | 'loading' | 'success' | 'error'`).
- **Single Source of Truth**: The architectural guarantee that each piece of data is owned and modified in exactly one place.

### Summary

**React 19 State Structure Invariants**

In daily production, keeping state minimal and computing derived values during render eliminates entire categories of synchronization bugs. Here is your streetwise review.

❒ State Structure Invariants

1. Never put derived values into state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) If a value can be computed from props or existing state, calculate it on the fly.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Render-time computations are fresh, immediate, and zero-maintenance.

2. Store IDs, not duplicate objects.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Storing a selected object creates a stale duplicate when the original updates.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Store `selectedId` in state and find the active object during render.

3. Replace contradictory booleans with a status string.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Multiple flags like `isLoading` and `isSuccess` can accidentally both be true.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Use a single status string: `'idle' | 'loading' | 'success' | 'error'`.

➔ NEVER store filtered arrays, item counts, or validation flags in `useState`.

➔ ALWAYS calculate derived values during render from the single source of truth.

➔ IF you need an active item from a collection THEN **store its ID and derive the object**.

**DO THIS:** Compute derived values directly during render.

```jsx right title="WireFilter.jsx"
// Clean derived calculation during render
export default function WireFilter({ stories }) {
  const [query, setQuery] = useState('');
  const filtered = stories.filter(s => s.title.includes(query));
  const count = filtered.length;
  return <div>Found {count}: {filtered.map(s => s.title)}</div>;
}
```

**DO NOT DO THIS:** Never store redundant filtered arrays and counts in separate state.

```jsx wrong title="Redundant-State Anti-Pattern"
// FAILS: Multiple states drift out of sync when updates occur!
export default function BrokenFilter({ stories }) {
  const [query, setQuery] = useState('');
  const [filtered, setFiltered] = useState(stories); // BUG: Redundant!
  const [count, setCount] = useState(stories.length); // BUG: Redundant!
  return <div>Found {count}: {filtered.map(s => s.title)}</div>;
}
```
