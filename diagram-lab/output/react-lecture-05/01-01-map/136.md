# Q136: Actions vs Server Functions: Disentangling Client Actions from RPCs
* **Topic Tag**: #actions | ❱❱ MORE (Server)
* **Interview Question**: *What is the precise distinction between an action and a Server Function?*
* **Core Truth**: An action is any asynchronous transition function passed to <form action>, formAction, or startTransition to handle user submissions; a Server Function is specifically an action marked with 'use server' that executes on the server.
* **The Friction**: An engineer on the reader analytics team at The National Times needs to handle client-side form validation and localStorage caching; they write 'use server' because they believe <form action> requires a Server Function, inadvertently sending client-only state over the network to the backend.
* **The Mechanism**: Actions vs Server Functions: (1) Client Action: an async function running entirely in the browser, manipulating client state, localStorage, or calling third-party client APIs; (2) Server Function ('use server'): an async function executing on the server with database access; both can be passed to <form action={fn}> or useActionState.
* **Under the Hood**: Action dispatch mechanism: React's form handler treats any async function as an action, wrapping its execution in a transition to track pending state (useFormStatus, useActionState); whether the function executes locally in the browser or dispatches an RPC depends solely on the presence of the 'use server' reference.
* **The Code Experiment**:
  * *Naive*: Forcing a client-only form (e.g. local theme preferences or draft autosave to IndexedDB) to call a 'use server' function.
  * *React*: Writing a client-side action <form action={async (formData) => { localStorage.setItem('pref', formData.get('pref')); }}> to utilize transitions without server round-trips.
* **Scope Boundary**: Focus on the precise definition and distinction between actions (transitions/forms) and Server Functions (server RPCs).
