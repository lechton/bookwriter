# Q169: Concurrent Rendering Under Streaming SSR
* **Topic Tag**: #concurrent | ❱❱❱ ADVANCED (Server)
* **Interview Question**: *Why does streaming require concurrent rendering under the hood?*
* **Core Truth**: Streaming SSR fundamentally requires concurrent rendering machinery because pausing an in-progress tree upon encountering a pending promise, flushing ready sibling chunks to the network, and resuming subtree rendering out-of-order without blocking the server process is impossible with synchronous recursive renderers.
* **The Friction**: During breaking election coverage at The National Times, traffic surges cause server latency to spike catastrophically; the operations team discovers that legacy synchronous rendering (`renderToString`) blocked Node.js event loops for 250ms per request on slow database calls, whereas streaming SSR interleaves thousands of active requests without a single blocked thread.
* **The Mechanism**: Cooperative interruptible work loop: when an async component or Suspense boundary suspends on an unresolved promise, React's server renderer catches the suspension, saves the Fiber boundary's execution state, immediately emits fallback HTML or placeholder Flight rows, yields control back to the event loop, and registers a continuation callback that wakes up the reconciler when the promise resolves.
* **Under the Hood**: Fiber as a resumable coroutine: traditional synchronous renderers (`renderToString`) traverse virtual DOM trees via call stack recursion, where waiting for I/O freezes the entire call stack; React's concurrent Fiber architecture models every component as an individual unit of work on an interruptible work loop (`workLoopSync` vs `workLoopConcurrent`), enabling React to abandon, yield, or resume subtree traversal independently across concurrent reader streams.
* **The Code Experiment**:
  * *Naive*: Using synchronous `renderToString` on the server, forcing Node.js to block its single event-loop thread until every slow database query resolves before sending the very first byte of HTML.
  * *React*: Using `renderToPipeableStream` with concurrent Suspense boundaries, streaming the outer editorial shell instantly in milliseconds while background promises resolve and stream content chunks asynchronously without thread contention.
* **Scope Boundary**: Do not cover client-side concurrent lane priority scheduling, `useTransition`, or `useDeferredValue` (covered in Q35/Q36/Q74); focus strictly on why server streaming depends on concurrent Fiber interruptibility, cooperative yielding, and asynchronous continuation mechanics.
