# Q140: Server Stream Lifecycle: onShellReady, onShellError, and onAllReady
* **Topic Tag**: #stream_lifecycle | ❱❱ MORE (Server)
* **Interview Question**: *What do onShellReady, onShellError, and onAllReady each mean?*
* **Core Truth**: onShellReady signals that the critical HTML shell outside Suspense boundaries has finished rendering and can be piped to human readers, while onAllReady indicates all deferred Suspense boundaries have resolved, which is required for search crawlers and static file generation.
* **The Friction**: Search engine crawlers index The National Times homepage and index only skeleton loading spinners because the server piped the response on onShellReady; meanwhile, human readers on mobile devices experience 3-second delays when an engineer switches the entire server to onAllReady.
* **The Mechanism**: Lifecycle callbacks in renderToPipeableStream: (1) onShellReady: fires when the synchronous shell is ready; pipe immediately for human users; (2) onAllReady: fires when all suspended promises have resolved; pipe for SEO bots (isbot(userAgent)); (3) onShellError: fires if the shell throws; send a fallback 500 error page.
* **Under the Hood**: Stream state machine: React renders the component tree into internal chunks; if all components outside Suspense complete, onShellReady triggers; React continues rendering pending promises in the background; once the internal work queue empties with zero pending boundaries, onAllReady fires.
* **The Code Experiment**:
  * *Naive*: Using a single onShellReady callback for all incoming requests, causing search engines to index empty fallback spinners.
  * *React*: Inspecting the user-agent header with isbot: piping on onAllReady for search engine bots to ensure 100% indexed content, and piping on onShellReady for human readers for sub-second TTFB.
* **Scope Boundary**: Focus on the stream lifecycle callbacks (onShellReady, onAllReady, onShellError), crawler vs human strategies, and error handling.
