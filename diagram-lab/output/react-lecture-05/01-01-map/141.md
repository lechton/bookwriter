# Q141: Static Prerender APIs: prerender vs prerenderToNodeStream
* **Topic Tag**: #static_prerender | ❱❱ MORE (Server)
* **Interview Question**: *What do the static prerender APIs produce, and how do their variants differ?*
* **Core Truth**: React 19's static prerender APIs (prerender for Web Streams and prerenderToNodeStream for Node.js) block until all pending promises and Suspense boundaries resolve, producing a fully resolved HTML stream and client preload hints, but will hang indefinitely or reject if an unresolved promise never completes.
* **The Friction**: The build pipeline at The National Times hangs for 30 minutes during the nightly static archive export; an engineer used prerender on an article page containing an unresolving websocket subscription promise, not understanding that prerendering guarantees 100% completion before emitting output.
* **The Mechanism**: APIs: prerender(jsx, options) returns Promise<{ prelude }> (Web Stream); prerenderToNodeStream(jsx, options) returns Promise<{ prelude }> (Node.js stream); both guarantee zero pending Suspense fallbacks in the generated HTML.
* **Under the Hood**: Full tree resolution guarantee: unlike renderToPipeableStream which flushes fallbacks immediately, prerender creates an internal task queue and drains every suspended component until all promises resolve; if any promise rejects, the entire prerender call rejects, guaranteeing that broken partial pages are never written to disk.
* **The Code Experiment**:
  * *Naive*: Using renderToString or renderToPipeableStream for static build scripts, generating unfinished HTML containing <template id="B:1"> placeholders.
  * *React*: Using const { prelude } = await prerender(<ArticleArchive />) in a build script to generate self-contained, fully resolved static HTML for CDN deployment.
* **Scope Boundary**: Focus on the technical differences between prerender and prerenderToNodeStream, what { prelude } contains, and the completion guarantee.
