# Q72: Catching Rendering Errors with Error Boundaries
* **Topic Tag**: `#error_boundaries` | `❱❱ MORE`
* **Interview Question**: *How do you catch a rendering error before it unmounts the whole app?*
* **Core Truth**: Error boundaries are React components that catch JavaScript errors anywhere in their child component tree during rendering, lifecycle methods, and constructors, displaying a fallback UI instead of unmounting the entire application.
* **The Friction**: A single corrupt live blog entry has `entry.author.name` set to `undefined`, throwing `TypeError: Cannot read property 'name' of undefined` during render. Without an error boundary, React unmounts the entire root component, turning the whole website into a terrifying blank white screen.
* **The Mechanism**: Error Boundaries (implementing `static getDerivedStateFromError()` and `componentDidCatch()`). Wrap isolated widgets or route sections in error boundaries so failures remain localized to the broken widget while the rest of the application stays fully interactive.
* **Under the Hood**: Why `try/catch` cannot catch rendering errors: JSX is declarative markup executed by React's reconciler outside the component's lexical call stack; error boundaries catch errors thrown during the Fiber workLoop render pass and schedule an emergency fallback commit.
* **The Code Experiment**:
  * *Naive*: Wrapping JSX return statements in `try { return <Widget /> } catch (e) { ... }`, which fails to catch errors during actual child rendering.
  * *React*: An `EditorialErrorBoundary` wrapping a flaky third-party weather widget, rendering a localized "Widget Unavailable" card while the main news grid functions normally.
* **Scope Boundary**: Focus on Error Boundaries, `getDerivedStateFromError`, `componentDidCatch`, and error boundary placement strategies. Note that error boundaries do not catch errors in event handlers or async timers (use `try/catch` there).
