# Q24: Reacting to Input with State
* **Topic Tag**: `#reacting_to_input` | `❱ CORE`
* **Interview Question**: *How do you design a component that reacts to input with state instead of touching the DOM?*
* **Core Truth**: Declarative UI requires identifying visual states (empty, typing, submitting, success, error) and triggering state transitions rather than imperatively enabling, disabling, showing, or hiding individual DOM elements.
* **The Friction**: A developer builds a paywall subscription form. Instinctively, they write imperative code: `button.disabled = true`, `spinner.classList.remove('hidden')`, `errorText.style.display = 'block'`. As form requirements grow, impossible states emerge—such as showing both an error message and a success banner simultaneously.
* **The Mechanism**: Visual state modeling. Enumerate discrete UI states as explicit state variables or a status string (`'idle' | 'submitting' | 'success' | 'error'`), and write JSX that renders declaratively based on the current status.
* **Under the Hood**: Finite state machines vs imperative UI scripts: why declarative state modeling eliminates intermediate impossible states and ensures the DOM is always a pure projection of the active state machine state.
* **The Code Experiment**:
  * *Naive*: Imperative event handlers querying elements with `document.querySelector` and manually tweaking CSS classes and disabled properties.
  * *React*: A `PaywallModal` modeled with a discrete `status` state (`'editing' | 'submitting' | 'success'`) cleanly rendering appropriate loading indicators and error banners without touching the DOM.
* **Scope Boundary**: Focus on visual state modeling and declarative UI transitions using basic state. Do not introduce full state machine libraries (XState) or `useReducer` (reserved for Q29).
