# Q56: Re-Render Mechanics and the Fiber Tree
* **Topic Tag**: `#re-render_mechanics` | `❱❱ MORE`
* **Interview Question**: *When does a component re-render, and why is re-rendering children usually fast and harmless?*
* **Core Truth**: A component re-renders when its state changes, its parent re-renders, or context it consumes updates; re-rendering simply re-executes JavaScript component functions in memory and is usually fast and harmless unless heavy computations or physical DOM mutations are involved.
* **The Friction**: A developer notices in console logs that clicking a counter in `Header` causes twenty child navigation items to re-run their functions. Panicking about performance, the developer wraps every single component in `React.memo` and every handler in `useCallback`, introducing bloat and bugs for negligible microsecond gains.
* **The Mechanism**: Understanding the three re-render triggers: (1) state update, (2) parent re-render, (3) context change. Distinguish between *rendering* (calling the component function in JS to get virtual elements) and *committing/painting* (writing to the physical browser DOM).
* **Under the Hood**: Virtual DOM diffing efficiency: React calls child component functions and compares returned virtual elements; if the virtual elements have identical properties and types, React terminates the pass with zero physical DOM mutations, making most child re-renders virtually free.
* **The Code Experiment**:
  * *Naive*: Assuming every component re-render touches the physical DOM and prematurely optimizing every component with unnecessary memoization.
  * *React*: Measuring a `Newsfeed` page with console logs and DevTools, demonstrating that dozens of child re-renders complete in under a millisecond with zero DOM reflow.
* **Scope Boundary**: Focus on re-render causes, the difference between function execution and DOM repainting, and debunking re-render panic. Do not introduce `React.memo` syntax yet (reserved for Q57).
