# Q150: Recoverable Errors and Telemetry: onRecoverableError and Root Options
* **Topic Tag**: #server_errors | ❱❱ MORE (Server)
* **Interview Question**: *What is a recoverable error, and what do onRecoverableError and root options do with it?*
* **Core Truth**: A recoverable error is a non-fatal failure—such as a hydration mismatch or a suspended server chunk error—where React successfully falls back to client rendering, reporting the error via onRecoverableError without crashing the application.
* **The Friction**: The engineering team's Sentry dashboard at The National Times is spammed with hundreds of thousands of uncaught error alerts on every release; they cannot distinguish between fatal crashes that white-screen the app and minor hydration text mismatches that React recovered from automatically.
* **The Mechanism**: onRecoverableError option: passed to hydrateRoot(container, <App />, { onRecoverableError(error, errorInfo) { logToSentry(error, errorInfo); } }) or renderToPipeableStream; receives the error and component stack for non-fatal, self-healed anomalies.
* **Under the Hood**: Self-healing mechanisms: when hydration fails on a DOM node, React discards the server markup for that subtree, renders the client virtual DOM from scratch, and reports the discrepancy via onRecoverableError; the user sees the correct UI, but the developer receives telemetry to investigate the root cause.
* **The Code Experiment**:
  * *Naive*: Letting hydration mismatches log unmonitored to the browser console or treating them as fatal application-halting crashes.
  * *React*: Configuring onRecoverableError in hydrateRoot to route recoverable hydration diffs to an error logging service with component stacks for targeted developer remediation.
* **Scope Boundary**: Focus on onRecoverableError API, what constitutes a recoverable error, how React self-heals, and production telemetry logging.
