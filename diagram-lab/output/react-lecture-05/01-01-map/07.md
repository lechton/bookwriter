# Q07: Splitting Components Across Files with ES Modules
* **Topic Tag**: `#imports` | `❱ CORE`
* **Interview Question**: *How do you split components across files, and how do default and named imports differ?*
* **Core Truth**: React applications scale by organizing components into dedicated ES module files; default exports represent the single primary component of a file, while named exports allow exporting multiple utility helpers or companion components.
* **The Friction**: A newsroom project keeps five major layout components in a single 1,200-line `App.jsx`. Editing a headline badge forces git merge conflicts across the whole team, and mistyping curly braces on a default import crashes the bundler with `undefined is not a component`.
* **The Mechanism**: ES Module exports and imports. Using `export default function ArticleCard` for the main feature component, and `export function formatDate` for secondary helpers, imported cleanly via `import ArticleCard, { formatDate } from './ArticleCard.jsx'`.
* **Under the Hood**: How bundlers (Vite/Rollup) resolve file paths, how default exports bind to an internal `.default` property on the module namespace object, and why mixing up default vs named imports results in `undefined` element type errors.
* **The Code Experiment**:
  * *Naive*: Monolithic `App.jsx` with all components in one file, or attempting `import { ArticleCard }` from a default export causing runtime crashes.
  * *React*: Extracting `ArticleCard.jsx` and `AuthorBadge.jsx` into `src/components/`, cleanly importing and assembling them inside `App.jsx`.
* **Scope Boundary**: Focus strictly on file splitting, folder architecture, path resolution, and default vs named import syntax. Keep data static; do not introduce dynamic prop drilling or state.
