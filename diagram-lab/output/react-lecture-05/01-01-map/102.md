# Q102: Server-Side Rendering: Fast Initial Paint and TTI Trade-offs
* **Topic Tag**: #ssr | ❱ CORE (Server)
* **Interview Question**: *What is server-side rendering, and what does it solve?*
* **Core Truth**: SSR generates initial HTML on the server so users see content immediately (fast FCP/LCP), but interactive event listeners remain dead until client JavaScript downloads, parses, and hydrates the DOM (the Time to Interactive gap).
* **The Friction**: Breaking news strikes and readers rush to The National Times on mobile devices; under a pure Client-Side Rendering (CSR) architecture, readers stare at a blank white screen for three seconds while the app bundle downloads, causing high bounce rates before the headline even paints.
* **The Mechanism**: Traditional SSR (renderToString / renderToPipeableStream) vs CSR (createRoot): SSR outputs a full HTML document on the server that the browser paints instantly; client JavaScript then executes hydrateRoot to attach event listeners.
* **Under the Hood**: The "Uncanny Valley" of SSR: HTML renders visual DOM nodes with inline styles and markup, giving the illusion of a loaded page; however, until the JavaScript bundle arrives and executes hydrateRoot, buttons, links with custom handlers, and search inputs are completely unresponsive.
* **The Code Experiment**:
  * *Naive*: Relying on a pure CSR single-page app (<div id="root"></div>) that renders a blank screen until a 1MB JavaScript bundle executes an API fetch in useEffect.
  * *React*: Using SSR to render the article headline, byline, and paragraphs as raw HTML on the initial HTTP response, delivering instantaneous First Contentful Paint while background scripts load.
* **Scope Boundary**: Focus on traditional SSR vs CSR, the distinction between First Contentful Paint and Time to Interactive, and the hydration gap. Do not confuse traditional SSR with React Server Components (RSC).
