# Q122: Module Boundaries: Guarding Server Code with server-only
* **Topic Tag**: #server_only | ❱ CORE (Server)
* **Interview Question**: *How do you keep server-only code out of the client bundle?*
* **Core Truth**: The server-only package throws a compile-time build error if a module containing private server logic or secrets is accidentally imported into a Client Component module graph.
* **The Friction**: A developer building an article reaction widget at The National Times imports a shared utils/db.ts file to use a helper function; unbeknownst to them, db.ts exports private PostgreSQL connection strings and API keys, which get bundled into the client JavaScript and leaked publicly to the browser console.
* **The Mechanism**: import 'server-only': placed at the top of server modules; if a bundler encounters this import while tracing a 'use client' dependency graph, it halts the build with an error: "This module cannot be imported from a Client Component".
* **Under the Hood**: Bundler environment enforcement: the server-only package leverages Node/bundler package exports ("react-server" condition); in server environments it resolves to an empty file, but in client bundle compilation it resolves to a module that throws a fatal compilation error.
* **The Code Experiment**:
  * *Naive*: Relying on developer discipline or naming conventions (db.server.ts) without automated compiler guards, leading to leaked database secrets in the client bundle.
  * *React*: Adding import 'server-only' to the database client module, causing the bundler to fail immediately if any client component transitively imports it.
* **Scope Boundary**: Focus on server-only, secret leakage prevention, and build-time enforcement. Mention client-only symmetrically, but do not dive into Taint APIs.
