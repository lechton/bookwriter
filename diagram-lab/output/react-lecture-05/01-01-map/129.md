# Q129: Rendering Strategy Selection: Static Prerendering vs Streaming
* **Topic Tag**: #rendering_models | ❱ CORE (Server)
* **Interview Question**: *How do you choose between static prerendering and streaming for a page?*
* **Core Truth**: The decision between static prerendering and streaming SSR hinges on whether content is user-personalized and how frequently it updates: static prerendering maximizes CDN cacheability for evergreen content, while streaming SSR delivers real-time dynamic data without blocking TTFB.
* **The Friction**: The editorial team at The National Times launches three pages: an investigative archive (updated once a month), a breaking news dashboard (updated every 30 seconds), and a personalized "My Saved Stories" feed; using static prerendering for all three causes stale news feeds, while dynamic SSR for all three spikes cloud infrastructure costs.
* **The Mechanism**: Decision matrix: (1) Static Prerendering: for identical content across all users (About page, published articles, evergreen archives); (2) Streaming SSR: for per-request dynamic or user-personalized data (account settings, live breaking tickers, search results); (3) Hybrid: static shell with streamed dynamic slots.
* **Under the Hood**: Infrastructure and cache mechanics: Static prerendered pages are stored as static files on edge CDN nodes (sub-20ms TTFB, zero server compute per request); Streaming SSR invokes a Node.js/Edge function per request, streaming the initial shell and piping live database queries through Suspense.
* **The Code Experiment**:
  * *Naive*: Rendering a high-traffic static masthead page dynamically on every request, wasting database connections and cloud compute.
  * *React*: Configuring static prerendering for the published article archive and streaming SSR with Suspense for the personalized live reader dashboard.
* **Scope Boundary**: Focus on the decision criteria and trade-offs between static prerendering and streaming SSR. Do not duplicate the taxonomy from Q103.
