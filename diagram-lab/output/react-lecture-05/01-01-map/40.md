# Q40: Forms: Controlled State vs Uncontrolled FormData
* **Topic Tag**: `#forms` | `❱ MORE`
* **Interview Question**: *Should a form use controlled state or uncontrolled FormData, and how do you choose?*
* **Core Truth**: Controlled forms re-render on every keystroke to provide real-time validation and dynamic UI, whereas uncontrolled forms using native `FormData` avoid intermediate re-renders by reading values only at submission time.
* **The Friction**: A newsroom article submission form has forty input fields. Storing every field in controlled `useState` causes the entire form to re-render on every single keystroke, creating noticeable typing lag on low-end laptops and mobile devices.
* **The Mechanism**: Choosing between controlled and uncontrolled: use controlled inputs when you need instant inline feedback (e.g. password strength meters, autocomplete, live character limits); use uncontrolled forms with native `new FormData(e.currentTarget)` or `defaultValue` when fields are only inspected upon submit.
* **Under the Hood**: Browser DOM state vs React memory: uncontrolled inputs allow the browser to manage its own internal input buffers without dispatching React render passes; controlled inputs intercept every input event, update React state, and re-commit the value back to the DOM.
* **The Code Experiment**:
  * *Naive*: Making a 40-field form fully controlled with forty `useState` calls and experiencing lag on every character typed.
  * *React*: An `ArticleSubmissionForm` using uncontrolled inputs with `name` attributes, reading all values cleanly at submission using `const data = new FormData(e.currentTarget)`.
* **Scope Boundary**: Focus on the trade-offs between controlled state and uncontrolled `FormData` in standard React forms. Do not introduce React 19 form actions (Q41) or `useActionState` (Q42).
