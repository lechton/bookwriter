# Q98: Legacy Memoization: PureComponent and shouldComponentUpdate
* **Topic Tag**: #legacy_memoization | LEGACY
* **Interview Question**: *How did PureComponent and shouldComponentUpdate prevent re-renders, and what replaced them?*
* **Core Truth**: Class components optimized rendering using shouldComponentUpdate(nextProps, nextState) or extending React.PureComponent, which modern React replaces with React.memo and useMemo.
* **The Friction**: An inherited legacy dashboard at The National Times experiences severe performance lag; a developer sees class NewsGrid extends React.PureComponent, but notices the component re-renders on every parent tick anyway because the parent passes tags={['news', 'opinion']} as a new array literal on every render.
* **The Mechanism**: Legacy memoization: shouldComponentUpdate(nextProps, nextState) allowed manual boolean comparison; React.PureComponent implemented a shallow comparison of props and state. Today, React.memo(FunctionComponent) provides the exact functional equivalent of PureComponent.
* **Under the Hood**: Shallow comparison in class components: PureComponent runs shallowEqual(prevProps, nextProps) and shallowEqual(prevState, nextState); in-place object mutations (e.g. this.state.items.push()) evaluate to true (skipping legitimate re-renders), while new object literals evaluate to false (defeating memoization).
* **The Code Experiment**:
  * *Naive*: Mutating this.state.stories.push(newStory) in a PureComponent, which prevents shouldComponentUpdate from detecting the change and leaves the screen stale.
  * *React*: Refactoring a PureComponent with complex shouldComponentUpdate logic into a clean function component wrapped in React.memo.
* **Scope Boundary**: Focus on how shouldComponentUpdate and PureComponent worked, their shallow comparison pitfalls, and how they translate to React.memo. Do not write new class components.
