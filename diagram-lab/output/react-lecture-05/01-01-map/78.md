# Q78: Fiber Architecture and the Dual-Buffering workLoop
* **Topic Tag**: `#fiber_architecture` | `❱❱❱ ADVANCED`
* **Interview Question**: *What is a Fiber node, and how does the dual-buffering workLoop manage rendering?*
* **Core Truth**: A Fiber is a JavaScript object representing a unit of work with `child`, `sibling`, and `return` pointers; React uses a dual-buffering technique (`current` and `workInProgress` trees) to assemble updates in memory and swap pointers instantaneously during commit.
* **The Friction**: In legacy React, the call stack was bound to recursive function calls: once rendering started, it could not be paused or aborted without crashing. Long renders caused frame drops because the browser could not interrupt JavaScript to process user scroll or mouse events.
* **The Mechanism**: Fiber node architecture and the dual-buffering workLoop. Every component instance has a `current` fiber (representing what's on screen) and a `workInProgress` fiber (constructed during render). On commit, React swaps `fiberRoot.current = workInProgress` in a single pointer reassignment.
* **Under the Hood**: Singly linked-list tree traversal: Fibers replace recursive call stacks with explicit heap-allocated pointers (`child`, `sibling`, `return`). This enables the `workLoop` to pause at any fiber node, yield execution to the browser, and resume exactly where it left off without stack overflow.
* **The Code Experiment**:
  * *Naive*: Thinking React re-creates all internal nodes from scratch on every render, leading to misconceptions about memory churn.
  * *React*: Tracing the lifecycle of a Fiber node through `beginWork()` and `completeWork()`, showing how the `workInProgress` tree clones alternate fibers and swaps pointers on commit.
* **Scope Boundary**: Focus on the Fiber node data structure (`child`, `sibling`, `return`), the dual-buffering strategy, and the mechanics of the non-blocking `workLoop`. Do not cover scheduler priority lane bitmasks in detail.
