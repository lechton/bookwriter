# Q25: Structuring State and Avoiding Redundancy
* **Topic Tag**: `#state_structure` | `❱ CORE`
* **Interview Question**: *How do you decide which values belong in state and which are derived?*
* **Core Truth**: State should represent the minimal essential data needed to compute the UI; any value that can be calculated from existing props or state during render should never be stored in state.
* **The Friction**: A newsroom developer stores `articles`, `filterText`, `filteredArticles`, and `articleCount` as four separate `useState` variables. When an article is added, the developer forgets to update `articleCount` and `filteredArticles`, resulting in contradictory UI where the counter says "0 results" while five articles are displayed.
* **The Mechanism**: Derived state. Keep only the raw inputs in state (`articles` and `filterText`), and compute `filteredArticles = articles.filter(...)` and `articleCount = filteredArticles.length` directly in the component body during render.
* **Under the Hood**: State synchronization hazards: storing derived data creates redundant sources of truth that can fall out of sync; calculating values during render is fast, guarantees consistency, and eliminates synchronization effects.
* **The Code Experiment**:
  * *Naive*: Synchronizing `filteredList` and `totalCount` into separate states using state setters or effects whenever `search` changes.
  * *React*: A `StorySearch` component storing only `query` in state, calculating filtered stories and match counts on the fly during render.
* **Scope Boundary**: Focus on rules of state structuring: don't mirror props in state, don't store derived values, and avoid duplication. Do not introduce `useMemo` for optimization yet (reserved for Q58).
