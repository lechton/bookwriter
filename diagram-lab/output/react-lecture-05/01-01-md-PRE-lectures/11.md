### The Scrambled Input Trap and Index Diffing

- [p] ◇ In web applications, data almost always arrives as collections of records: lists of news articles, subscriber profiles, or live market tickers. In vanilla JavaScript, developers wrote imperative loops to create DOM nodes, append them to parent containers, and manually remove outdated elements. In React, rendering lists is completely declarative: you transform an array of raw JavaScript objects into an array of JSX elements using the standard array .map() method. React takes this array of element descriptors and reconciles it against the real DOM. ◼ Educational objective: establish the declarative foundation of list rendering via array mapping.
- [p] ★ {preknowledge: array iteration, DOM nodes, input focus} {bridging: developers assume array index is a natural key, but positional diffing scrambles state} When developers first render lists in React, they encounter a compiler warning demanding a "key" prop. To silence the warning, many developers hastily write `key={index}`. This creates one of the most notorious and insidious bugs in React. Look at the naive attempt below: ◼ Educational objective: demonstrate the common index-as-key bug.
- [code] Naive List Rendering with Index as Key:
```jsx title="Naive List Rendering and the Index Key Trap"
export default function BreakingFeed({ stories }) {
  return <ul>
    {stories.map((s, index) => (
      <li key={index}>
        <span>{s.headline}</span> <input placeholder="Note..." /> // **GLITCH:** state attaches to **INDEX**
      </li>
    ))}
  </ul>;
}
```
◼ **The what-this-introduces list:** 1. `stories.map((s, index) => ...)`: iterating arrays with index. 2. `key={index}`: the positional index trap. 3. `<input />`: local DOM state that glitches upon list reordering.
- [p] ★ {preknowledge: reconciliation, virtual DOM, element diffing} {bridging: React reuses DOM nodes when keys match, even if the underlying business record changed} When a new urgent headline arrives at index 0, every subsequent item shifts down by one position. The item previously at index 0 is now at index 1. Because the keys are indices, React compares the old tree's item at `key="0"` with the new tree's item at `key="0"`. React concludes that item 0 did not move; it simply changed its headline text! Therefore, React updates the text node inside the existing DOM node, but leaves the native `<input>` completely untouched. As a result, the note you typed for the old story is now visibly attached to the new breaking story! ◼ Educational objective: deconstruct why positional index diffing preserves local DOM state in the wrong items.
- [figure] ```html-figure src="figures/11-00-list-rendering-keys-reconciliation.html" caption="List reconciliation: contrasting positional index recycling against stable entity keys."```
- [grounding] [!WILD] **Why does prepending an item scramble form inputs?** When you prepend an item to an array using `key={index}`, the new item receives `key={0}`, the previous first item becomes `key={1}`, and so forth. React's reconciler assumes the element with `key={0}` is the exact same component instance as before, just with updated props. It reuses the physical DOM node in place. While React updates the text props it controls, the browser's native `<input>` state, text cursor, and focus live inside the unmanaged DOM node. Because the DOM node was recycled for the new record, your typed text remains stuck in the first input box while the headline above it changes completely!
- [callout] > [!TIP]
> **To impress the interviewer:** When asked why React requires keys, explain that keys do not exist for performance alone; they provide **identity**. Without stable keys, React falls back to positional diffing, mutating DOM nodes in place and corrupting internal component state or unmanaged DOM buffers. Always emphasize that keys must be unique among siblings and stable across renders, which is why database primary keys or unique entity IDs are mandatory.

### Key Mechanics and the Reconciliation Contract

- [p] ◇ A key is a special string attribute that you must pass when creating arrays of elements in JSX. Keys act as permanent identity badges: they tell React which array item corresponds to which component instance across consecutive renders. When the data changes, React uses these identity badges to deduce what physically happened: was an item inserted, was an item removed, or did items simply switch places? ◼ Educational objective: define the core purpose and architectural role of React keys.
- [p] ★ {preknowledge: database IDs, object identity, array mutation} {bridging: developers must choose between inline JSX mapping and variable extraction based on readability} When transforming an array of data into JSX, you encounter an architectural crossroad between two clean patterns: ◼ Educational objective: frame the crossroad between pre-computing list items and inline mapping.
- [p] - **Option 1 (The foundational way)**: Pre-compute the array of JSX elements in a local variable `const storyItems = stories.map(...)` outside the return statement, then project `{storyItems}` inside JSX. ◼ Educational objective: declare Option 1 with concrete syntax tokens.
- [p] - **Option 2 (The modern idiomatic way)**: Inline the array `.map()` expression directly inside the return statement within JSX curly braces `{stories.map(story => ...)}`. ◼ Educational objective: declare Option 2 with concrete syntax tokens.
- [p] First, look at Option 1 using a pre-computed variable: ◼ Educational objective: transition to Option 1 code.
- [code] Option 1:
```jsx title="Option 1: The Foundational Way (Pre-computed Variable)"
export default function NewsFeed({ stories }) {
  const storyItems = stories.map((story) => ( // Transforms data array into **ELEMENTS**
    <li key={story.id}>{story.headline}</li> // Assigns permanent database **KEY**
  ));
  return <ul className="feed-list">{storyItems}</ul>; // Projects pre-computed **JSX ARRAY**
}
```
◼ **The what-this-introduces list:** 1. `const storyItems = ...`: explicit array variable holding JSX elements. 2. `key={story.id}`: stable entity identifier. 3. `{storyItems}`: embedding pre-computed array in markup.
- [p] ★ In Option 1, storing the transformed array in `storyItems` makes the separation between data processing and markup projection explicit. This helps developers verify that the mapped output is a plain JavaScript array of React element objects. ◼ Educational objective: analyze the mechanics of pre-computing JSX arrays in local variables.
- [p] Next, look at Option 2 using the inline mapping idiom: ◼ Educational objective: transition to Option 2 code.
- [code] Option 2:
```jsx title="Option 2: The Modern Idiomatic Way (Inline JSX Mapping)"
export default function NewsFeed({ stories }) {
  return (
    <ul className="feed-list">
      {stories.map((story) => ( // Evaluates inline map within **EXPRESSION WINDOW**
        <li key={story.id}>{story.headline}</li> // Binds stable **ENTITY ID**
      ))}
    </ul>
  );
}
```
◼ **The what-this-introduces list:** 1. `{stories.map(...)}`: inline evaluation window directly inside parent tags. 2. Compact single-pass return structure. 3. Standard idiomatic React community convention.
- [p] ★ In Option 2, the `.map()` call sits directly within JSX curly braces. This keeps parent container markup and child element generation tightly co-located, reducing boilerplate while preserving full identity reconciliation via `story.id`. ◼ Educational objective: demonstrate clean inline list mapping.
- [callout] > [!KEY]
> Keys must satisfy two non-negotiable rules: they must be **unique among siblings** (different lists can use the same keys), and they must be **stable across renders** (never generate keys on the fly using `Math.random()` or `crypto.randomUUID()`).

### Step 1: First, we construct the parent container <NewsFeed.jsx>

- [p] We begin by constructing `src/components/NewsFeed.jsx`. This component acts as the orchestrating container. It accepts a `stories` array prop and transforms it into an array of `StoryItem` elements, passing each record's permanent `story.id` as the `key`: ◼ Educational objective: construct the parent container mapping records to child components with stable keys.
- [code] NewsFeed.jsx:
```jsx title="src/components/NewsFeed.jsx" startLine="1"
import StoryItem from './StoryItem.jsx';
export default function NewsFeed({ stories }) {
  return <section className="feed-container">
    <h2>Live Editorial Desk</h2>
    {stories.map((story) => (
      <StoryItem key={story.id} story={story} /> // Binds persistent **ENTITY KEY**
    ))}
  </section>;
}
```
◼ **The what-this-introduces list:** 1. `stories.map(...)`: array transformation pipeline. 2. `key={story.id}`: stable identity prop consumed by React's reconciler. 3. `<StoryItem story={story} />`: passing data downward to child.
- [p] Notice line 6: `key={story.id}`. The `key` prop is passed directly on the outermost JSX element returned inside the `.map()` callback. Notice that `key` is reserved for React: `StoryItem` does not receive `props.key` in its own parameter list; React absorbs the prop during element creation. ◼ Educational objective: explain that key is an engine reserved prop not accessible in child props.

### Glossary

- [glossary] List Rendering ◼ The pattern of transforming an array of raw JavaScript objects into an array of JSX elements using array .map().
- [glossary] Key Prop ◼ A special string attribute passed to elements in an array that gives them a permanent, stable identity across renders.
- [glossary] Reconciliation ◼ The algorithm React uses to diff one element tree against another to determine which DOM updates are necessary.
- [glossary] Index as Key Trap ◼ The bug where using array indices as keys causes React to recycle DOM nodes in place, scrambling unmanaged DOM state during reorders.
- [glossary] Stable Identity ◼ The guarantee that a component instance and its associated physical DOM node persist across renders regardless of array position.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Declarative List Transformation

➔ ALWAYS use standard array `.map()` to project arrays of data into arrays of JSX elements.

➔ NEVER use imperative loops or push methods to populate arrays of elements inside the render block.

➔ IF rendering a collection THEN place the `key` prop on the outermost JSX tag returned directly inside `.map()`.

❒ Key Stability & Identity Protection

➔ ALWAYS assign stable, unique entity identifiers (such as database primary keys `story.id`) as the `key` prop.

➔ NEVER use array indices (`key={index}`) when items in the list can be reordered, inserted, or deleted.

➔ NEVER generate keys on the fly using `Math.random()` or `crypto.randomUUID()` during render, as this forces complete DOM recreations on every render.

**DO THIS:** assign stable database IDs directly to mapped elements

```jsx right
export default function StoryFeed({ stories }) {
  return (
    <ul>
      {stories.map((story) => (
        <li key={story.id}>{story.title}</li>
      ))}
    </ul>
  );
}
```

**DO NOT DO THIS:** use array indices as keys on dynamic lists

```jsx wrong
export default function StoryFeed({ stories }) {
  return (
    <ul>
      {stories.map((story, index) => (
        <li key={index}>{story.title}</li>
      ))}
    </ul>
  );
}
```

| | **STABLE ENTITY KEYS**<br>(Database IDs) | **INDEX AS KEY**<br>(Positional Slot) |
| ---: | :--- | :--- |
| **Node Identity** | Tied permanently to business record | Tied to transient array index slot |
| **Prepending Items** | Inserts 1 new DOM node at top | Mutates all existing DOM nodes in place |
| **Unmanaged DOM State** | Inputs, focus, and audio buffers move cleanly | State stays glued to slot, scrambling data |
| **Diffing Efficiency** | Minimal targeted DOM insertions and moves | Expensive cascade of DOM attribute mutations |
| **Component Identity** | Component instance preserved across reorders | Instance recycled for completely different item |
