### The Bandwidth Illusion: Why More Megabits Do Not Fix Latency

Zoe reviews real-user telemetry to understand why rural subscribers abandon the National Times checkout flow. When engineering teams test web applications on gigabit corporate Wi-Fi, they mistake network bandwidth for network speed. While high bandwidth allows massive video files to download quickly, initial page delivery is constrained by round-trip latency (RTT), TCP handshakes, and slow-start congestion windows. On high-latency mobile networks, shipping hundreds of small external requests forces the radio to idle across sequential round trips:

```html title="resource-payload.html"
<link rel="stylesheet" href="/style-bundle-2mb.css" /> <!-- **WRONG:** 2MB blocking stylesheet stalls mobile radio -->

<link rel="stylesheet" href="/style-core-18kb.css" /> <!-- **RIGHT:** 18KB critical styles fit in initial TCP bursts -->
```

The contrast illustrates why bandwidth cannot overcome latency. Because the speed of light in optical fiber is limited to roughly 200 kilometers per millisecond, physical distance imposes an irreducible round-trip delay. When a browser initiates a new connection, it must perform DNS resolution, a TCP three-way handshake, and a TLS cryptographic negotiation before requesting the first byte. Under TCP slow-start, the server delivers the initial response in a small congestion window of approximately 14 kilobytes. On the left, downloading two megabytes requires dozens of round-trip network acknowledgments, stranding the mobile user on an empty screen. On the right, keeping critical styles under 18 kilobytes delivers the complete layout within the very first network burst.

### The Heavy Byte: Why JavaScript Costs More Than Images

In the cost model of the web, not all network bytes impose equal burdens on the client device. A one-megabyte JPEG photograph is streamed to the GPU, decoded off-thread, and painted without freezing the user interface. Conversely, a one-megabyte JavaScript bundle monopolizes the browser's single main thread as the V8 engine parses tokens, compiles abstract syntax trees, and executes initialization logic:

```javascript title="script-budget.js"
import { FullChartsSuite } from 'all-charts-3mb'; // **WRONG:** 3MB library monopolizes main thread compilation

import { renderSparkline } from './sparkline-4kb.js'; // **RIGHT:** 4KB micro-script compiles in under 5 milliseconds
```

A byte of code demands far more computing resources than a byte of media. After downloading, an image requires simple decompression and memory allocation. JavaScript, however, undergoes a grueling multi-stage compilation pipeline. The browser must parse the raw text into an Abstract Syntax Tree, compile bytecode, and execute instructions on the CPU's primary execution thread. On mid-tier and budget smartphones, compiling three megabytes of script locks the main thread for nearly two full seconds, causing buttons to ignore taps and gestures to stutter. Replacing bloated libraries with focused utility functions protects the main thread and keeps user interactions fluid.

Author and web performance engineer Ilya Grigorik defines this fundamental optimization principle:

> In any complex system, a large part of the performance optimization process is the untangling of the interactions between the many distinct and separate layers of the system, each with its own set of constraints and limitations.
*Ilya Grigorik, High Performance Browser Networking, resources/web-performance/hpbn/primer-on-web-performance/index.html*

> [!KEY]
> Performance is user retention; round-trip latency and main thread CPU execution cost far more than raw network bandwidth.

> [!TIP]
> **To impress the interviewer:** contrast byte economics across media types: an image costs network transfer and GPU rasterization, while JavaScript costs transfer, decompression, lexical parsing, bytecode compilation, and main thread execution. Cite the rule of thumb that 170KB of gzipped JavaScript equates to roughly 1MB of raw code, which can consume over a second of CPU time on a mobile device before the user can tap an interactive element.

### Glossary

- **Cost Model of the Web**: The analytical framework evaluating how network latency, bandwidth, CPU parsing, and battery power limit performance.
- **Round-Trip Time (RTT)**: The duration required for a network packet to travel from the browser to the server and return.
- **TCP Slow-Start**: A congestion control algorithm where the server begins transmission with a conservative burst (initcwnd) before scaling up.
- **Main Thread Contention**: The bottleneck that occurs when intensive JavaScript compilation blocks user taps and rendering updates.
- **Byte Inequality**: The reality that script bytes demand orders of magnitude more device computation than equivalent image bytes.

### Summary

**Network Physics and Client Execution Economics**

Web performance is governed by immutable physical laws and device constraints. Upgrading server bandwidth cannot eliminate round-trip latency, and downloading huge JavaScript payloads overtaxes budget mobile processors. Design for high-latency cellular connections, respect the initial TCP packet window, and minimize main thread execution debt. Here is your streetwise review.

❒ The Core Laws of the Web Cost Model

1. Network Transmission Laws
<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) RTT dominates mobile load times; latency cannot be resolved by raw bandwidth.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Keep initial critical payloads under 14KB to fit within TCP initcwnd.
