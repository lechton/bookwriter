### Visual Styling Versus Programmatic Error Association

Arthur reaches the checkout using a screen reader, but his card is rejected with a silent red outline. Because visual styling does not reach the accessibility tree, speech synthesizers announce only the bare field name without mentioning any error. Binding the invalid state and error description through ARIA ensures assistive devices vocalize the failure upon focus:

```html title="input-error.html"
<input type="text" class="border-red" /> <!-- **WRONG:** red border leaves screen reader unaware of **ERROR** -->

<input type="text" aria-invalid="true" /> <!-- **RIGHT:** aria-invalid speaks error state on **FOCUS** -->
```

```canvas title="Checkout Validation: CSS Border Only vs Programmatic Error" width="2/3" layout="compare"
input | 4111 | label="Card Number" | wrong="css border only" | sr="Card Number, edit text, 4111" | note="✕ Silent failure · No error state in a11y tree" | style="border-color:#e11d48;"
input | 4111 | label="Card Number" | right="aria error binding" | sr="Card Number, invalid entry, edit text, 4111. Enter a valid 16-digit card number." | note="✓ Error announced on focus · Passes WCAG 3.3.1"
```

The comparison reveals the fundamental disconnect between visual styling and accessibility tree semantics. For a sighted user, a red border, an exclamation icon, and a paragraph below an input box immediately signal an error. For assistive technology, visual CSS styling does not exist. A screen reader queries the browser accessibility tree for states and descriptions. If an engineer applies a red border class without setting programmatic attributes, the screen reader announces only the element name and value: "Card Number, edit text, 4111."

When validation fails, satisfying WCAG Criterion 3.3.1 (Error Identification, Level A) requires exposing the error state explicitly in text and code. Setting `aria-invalid="true"` alerts the browser that the control contains an invalid value, prompting screen readers to append "invalid entry" to the element announcement. Connecting the explanatory error message through `aria-describedby` ensures that the specific corrective guidance is vocalized immediately after the control's accessible name.

The W3C Understanding documentation establishes the core mandate of Criterion 3.3.1:

> The intent of this success criterion is to ensure that users are aware that an error has occurred and can determine what is wrong. In the case of an unsuccessful form submission, it is not sufficient to only re-display the form without providing any hint that the submission failed. The error must be indicated in text.
*W3C, Understanding WCAG 2.0: Error Identification, `resources/accessibility/wcag/understanding/20/error-identification.html`*

### Semantic Grouping: Bare Division Containers Versus Fieldset and Legend

Beyond individual error states, radio options and multi-part inputs lose their contextual meaning when grouped inside generic division containers. When a non-sighted subscriber tabs onto a radio choice labeled "Annual", hearing the label alone fails to communicate what product or frequency is being chosen. Wrapping related controls inside a fieldset with an explicit legend ensures screen readers speak the overarching category before each option:

```html title="grouping-controls.html"
<div class="options">...</div> <!-- **WRONG:** generic div drops group context for **OPTIONS** -->

<fieldset><legend>Billing</legend>...</fieldset> <!-- **RIGHT:** fieldset legend announces group **CONTEXT** -->
```

```canvas title="Radio Options: Generic Div vs Semantic Fieldset" width="2/3" layout="compare"
button | Annual All-Access ($120/yr) | wrong="generic div wrapper" | sr="Annual All-Access, radio button" | note="✕ Missing context · Fails WCAG 1.3.1"
button | Annual All-Access ($120/yr) | right="fieldset with legend" | sr="Billing Cadence, Annual All-Access, radio button" | note="✓ Category announced · Passes WCAG 1.3.1"
```

Grouping related form controls satisfies WCAG Criterion 1.3.1 (Info and Relationships, Level A). When individual options share an overarching prompt, placing them in generic containers like divs breaks reading flow because screen readers ignore surrounding paragraph tags during keyboard navigation.

The W3C Web Accessibility Initiative documentation highlights why semantic grouping is essential for cognitive clarity:

> Grouping related form controls makes forms more understandable for all users, as related controls are easier to identify. It also makes it easier for people to focus on smaller and more manageable groups rather than try to grasp the entire form at once.
*W3C WAI, Grouping Controls, `resources/accessibility/wai/pages/design-develop/tutorials/forms/grouping.md`*

### The Triad of Accessible Error Architecture

Production applications require a coordinated three-tier strategy for form error recovery:

1. **State Signaling with `aria-invalid`:** Informs the accessibility API that the control value violates validation constraints. Screen readers voice "invalid entry" upon focus.
2. **Inline Association with `aria-describedby`:** Points to the unique ID of the inline error message. When the user focuses the invalid field, the screen reader voices the corrective instruction directly after the field label.
3. **Top-Level Error Summary with `role="alert"`:** When a form submission fails, the application moves focus programmatically to an error summary container at the top of the form. The summary outlines the total number of errors and provides in-page jump links directly to each invalid field.

Here is an accessible Svelte 5 component implementing this validation lifecycle:

```svelte title="SubscriptionCheckout.svelte"
<script>
  let errors = $state({});
  let cardNumber = $state('');
  let summaryHeading = $state(null);

  function validateForm(event) {
    event.preventDefault();
    const newErrors = {};
    if (!/^\d{16}$/.test(cardNumber.replace(/\s+/g, ''))) {
      newErrors.cardNumber = 'Enter a valid 16-digit card number without spaces.';
    }
    errors = newErrors;
    if (Object.keys(newErrors).length > 0) {
      summaryHeading?.focus();
    }
  }
</script>

<form onsubmit={validateForm} novalidate>
  {#if Object.keys(errors).length > 0}
    <div class="error-summary" role="alert" tabindex="-1" bind:this={summaryHeading}>
      <h2>There are problems with your submission</h2>
      <ul>
        {#each Object.entries(errors) as [field, msg]}
          <li><a href="#{field}-input">{msg}</a></li>
        {/each}
      </ul>
    </div>
  {/if}

  <div class="input-block">
    <label for="cardNumber-input">Credit Card Number</label>
    <input
      id="cardNumber-input"
      type="text"
      bind:value={cardNumber}
      aria-invalid={errors.cardNumber ? 'true' : 'false'}
      aria-describedby={errors.cardNumber ? 'cardNumber-err' : undefined}
    />
    {#if errors.cardNumber}
      <span id="cardNumber-err" class="inline-error">{errors.cardNumber}</span>
    {/if}
  </div>

  <button type="submit">Complete Subscription</button>
</form>
```

> [!KEY]
> Visual error outlines convey nothing to screen readers. Expose error state through `aria-invalid="true"` and connect error text through `aria-describedby`.

### Glossary

- **Fieldset**: An HTML container element that groups related form controls and establishes a common context for assistive technologies.
- **Legend**: The first child element of a fieldset that supplies the accessible name and group title for all enclosed controls.
- **aria-invalid**: An ARIA state attribute that programmatically flags whether the current value of a form control passes validation rules.
- **aria-describedby**: An ARIA property taking a list of element IDs whose combined text acts as the accessible description for the target element.
- **Error Summary**: A prominent list placed at the top of a form after failed submission that outlines all errors and links to failing fields.
- **Accessible Description**: Supplementary text provided to assistive technologies after the element's accessible name and role are announced.

### Summary

**Form Grouping and Validation Error Architecture**

Handling forms cleanly requires separating visual decoration from programmatic accessibility semantics. Red border styles and floating error paragraphs convey zero information to non-sighted users unless they are anchored to inputs in the accessibility tree. Grouping controls with fieldset and legend preserves context for radio buttons and multi-part inputs, while aria-invalid and aria-describedby ensure error feedback is vocalized immediately upon focus. Here is your streetwise review.

❒ Semantic Grouping with Fieldset and Legend

1. Never group related controls with bare div and paragraph tags.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Radio buttons and multi-input dates lose their overarching question without semantic grouping.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) The legend element automatically prefixes every child control during screen reader tabbing.
2. Group controls when choices cannot stand alone.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Always wrap radio button groups inside a fieldset.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Always place the legend as the very first element inside the fieldset.

❒ Wiring Inline Validation Errors

1. Never rely on CSS classes alone to communicate errors.

**DO NOT DO THIS:** Add a red border class without updating ARIA state attributes.
```html wrong
<input type="text" id="email" class="input-error">
<p class="error-msg">Email format is invalid.</p>
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Signal the error state and bind the error description ID to the input.
```html right
<input type="text" id="email" aria-invalid="true" aria-describedby="email-error">
<p id="email-error" class="error-msg">Email format is invalid.</p>
```
2. Never hide error descriptions behind unassociated floating icons.

**DO NOT DO THIS:** Display an error tooltip that is not connected to the input element.
```html wrong
<input type="text" id="postal" class="border-red">
<span class="tooltip">Invalid zip code</span>
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Use aria-describedby so screen readers speak the error on focus.
```html right
<input type="text" id="postal" aria-invalid="true" aria-describedby="postal-desc">
<span id="postal-desc" class="tooltip">Invalid zip code</span>
```

➔ NEVER rely solely on color or CSS border styling to signal input error states.

➔ ALWAYS wrap radio button clusters inside a fieldset with a clear legend title.

➔ IF form submission fails THEN move focus to a top-level error summary and wire fields with aria-invalid.
