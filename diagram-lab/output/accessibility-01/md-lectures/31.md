### The Ghost Node: Visual Opacity Versus Tree Removal

Hannah navigates the editorial archives using speech synthesis on her desktop computer. When frontend engineers hide components using visual-only CSS techniques like `opacity: 0` or `transform: scale(0)`, the elements vanish from the visual display but remain fully active in the browser DOM. The browser's layout engine continues exposing these elements to the accessibility tree, allowing screen readers to focus, read, and interact with completely invisible controls. Truly hiding content requires CSS properties that strip nodes from accessibility mappings:

```css title="hiding-mechanisms.css"
.promo-card { opacity: 0; } /* **WRONG:** Visual fade leaves node in accessibility tree */

.promo-card { display: none; } /* **RIGHT:** Completely removes node from tree */
```

```canvas title="Promotional Banner: Visual Opacity vs True Tree Removal" width="2/3" layout="compare"

card | Special Offer ($1) | right="display: none" | note="✓ Removed from screen and accessibility tree"
```

The contrast illustrates the deep architectural separation between visual rasterization and the accessibility tree. Setting `opacity: 0` instructs the GPU compositor to render pixels with total transparency, yet the element remains in the geometry layout, retains focusability, and stays fully registered in the accessibility tree. When Hannah tabs through the article, her screen reader encounters the ghost node, speaking headlines and prices from an empty expanse of white space. Conversely, applying `display: none` or the HTML `hidden` attribute instructs the browser engine to prune the node from both visual rendering and the accessibility tree, ensuring total synchronization between eye and ear.

### The OS Bridge: From DOM Nodes to Platform Accessibility APIs

Assistive technologies do not scrape raw HTML documents or calculate pixel geometries directly from the viewport. Instead, the browser engine acts as a compiler, translating HTML elements, computed CSS styles, and ARIA attributes into a specialized data structure known as the accessibility tree. The browser projects this tree into the operating system's native accessibility API, which screen readers query to deliver spoken announcements:

```html title="tree-pipeline.html"
<div class="fake-btn" onclick="go()">Next</div> <!-- **WRONG:** Generic div maps to unknown text node -->

<button type="button">Next</button> <!-- **RIGHT:** Maps to native OS button role -->
```

```canvas title="Button Mapping: Unsemantic Div vs Native Accessibility Node" width="2/3" layout="compare"
button | Next Story | wrong="unsemantic div" | sr="Next Story, text" | note="✕ Generic node lacks OS button role"
button | Next Story | right="native button" | sr="Next Story, button" | note="✓ Exposed to OS API as push button"
```

The accessibility pipeline operates in three distinct phases. First, the browser parses the DOM and applies cascading styles to determine visibility and roles. Second, it synthesizes an internal tree of accessible objects, calculating each object's accessible name, role, states, and relations. Third, the browser bridges these objects to host operating system APIs, such as UI Automation on Windows or NSAccessibility on macOS. When developers use native elements like `<button>`, the browser automatically maps them to native OS button primitives. Using unsemantic elements like `<div>` maps to generic containers, leaving screen reader users without role feedback or activation hooks.

The W3C Core Accessibility API Mappings specification defines this translation layer between the web engine and the host environment:

> The Core Accessibility API Mappings specifies how WAI-ARIA roles, states, and properties are expected to be exposed by user agents via platform accessibility APIs.
*W3C WAI, Core Accessibility API Mappings 1.2, resources/accessibility/aria/core-aam/index.html*

### Glossary

- **Accessibility Tree**: A tree of accessible objects generated by the browser from the DOM, containing roles, names, and states for assistive tools.
- **Platform Accessibility API**: The operating system layer that exposes UI components to screen readers, such as UIA on Windows or AXAPI on macOS.
- **Ghost Node**: A DOM element visually hidden via opacity or sizing that erroneously remains active in the accessibility tree.
- **display: none**: A CSS declaration that completely removes an element from visual layout and the browser accessibility tree.
- **aria-hidden**: A boolean attribute that strips an element and all its children from the accessibility tree while leaving visual rendering intact.

❒ The Rules of Content Visibility and Tree Pruning

1. Dual-Surface Hiding (Screen and Tree)
<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Apply `display: none` or `visibility: hidden` in CSS.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Add the HTML boolean attribute `hidden` to the container.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(c) Prunes the element from both pixels and accessibility APIs.

2. Asymmetric Hiding Patterns
<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Screen reader only: use CSS clip-path or `.sr-only` margins.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Visual only: set `aria-hidden="true"` to strip decorative graphics.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(c) Never use `opacity: 0` to hide interactive controls.

**DO NOT DO THIS:** Hide content with opacity, leaving invisible ghost controls in the tree.
```html wrong
<div style="opacity: 0;">
  <button onclick="pay()">Confirm Payment ($50)</button>
</div>
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Prune inactive content using display none or the hidden attribute.
```html right
<div hidden>
  <button onclick="pay()">Confirm Payment ($50)</button>
</div>
```

➔ NEVER rely on `opacity: 0` or `transform: scale(0)` to hide accessible content.

➔ ALWAYS use `hidden` or `display: none` to strip inactive components from the tree.

➔ IF content is purely visual or decorative THEN apply `aria-hidden="true"`.
