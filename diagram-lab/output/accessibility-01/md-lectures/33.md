### The Unplugged Mouse: Verifying Focus Trails and Keyboard Traps

Marcus begins manual validation by disconnecting his mouse and relying exclusively on physical keystrokes. Sighted keyboard navigators follow a visual focus trail to identify active controls and verify sequential progress through the DOM. When third-party checkout frames or custom payment widgets capture focus without providing an escape key handler, keyboard users become permanently trapped. Conducting manual keyboard passes exposes focus containment flaws that automated DOM linters completely overlook:

```html title="checkout-trap.html"
<iframe src="/pay" tabindex="0"></iframe> <!-- **WRONG:** Traps Tab key with no keyboard exit -->

<iframe src="/pay" title="Secure Payment"
        aria-label="Payment Gateway"></iframe> <!-- **RIGHT:** Escaped via standard Tab sequence -->
```

On the right, manual keyboard verification proves that focus advances naturally through the payment fields and exits cleanly onto the primary purchase trigger.

### The Speech Audit: Testing Rotor Navigation and Acoustic Landmarks

Manual testing requires evaluating how assistive software interprets content through auditory output. Non-sighted users navigate web pages using specialized screen reader shortcut menus, such as the VoiceOver Rotor or the NVDA Elements List. When developers organize content using visual typography without semantic landmark tags or heading levels, screen reader navigation menus display blank screens. Auditing pages with a screen reader ensures structural elements appear cleanly in rotor dialogs:

```html title="rotor-landmarks.html"
<div class="header-band">Checkout</div> <!-- **WRONG:** Division invisible in screen reader rotor -->

<header><h1 class="page-title">Checkout</h1></header> <!-- **RIGHT:** Discovered via heading rotor menu -->
```

```canvas title="Checkout Header: Plain Div vs Semantic Heading Landmark" width="2/3" layout="compare"
heading | Checkout Summary | wrong="styled div heading" | sr="Checkout Summary, text" | note="✕ Missing from Screen Reader Rotor"
heading | Checkout Summary | right="semantic h1 heading" | sr="Checkout Summary, heading level 1" | note="✓ Navigable via H key and Rotor list"
```

Screen readers empower users to jump directly to primary regions using single-key shortcuts, pressing `H` to browse headings, `L` to browse lists, and `B` to locate buttons. On the left, relying on styled divisions forces the user to listen to every preceding paragraph and navigation item in linear sequence. On the right, semantic tags register in the screen reader's virtual rotor menu, allowing Marcus to jump directly to the checkout summary in a single keystroke.

### Glossary

- **Manual Accessibility Testing**: The systematic evaluation of a user interface using physical keyboards, screen readers, and zoom controls.
- **Keyboard Trap**: A defect where focus enters an interactive component but cannot be moved to another element using the keyboard.
- **Screen Reader Rotor**: A dialog menu in VoiceOver and assistive tools listing page landmarks, headings, links, and form controls.
- **Linear Tab Order**: The sequential flow of keyboard focus through interactive elements in matching visual reading order.
- **Rotor Menu Audit**: A manual testing technique verifying that all page sections are indexed properly in assistive shortcut lists.

### Summary

**Manual Verification Protocols and Assistive Tool Auditing**

Automated testing tools cannot experience an application the way a human does. ❒ The Core Manual Testing Protocol

1. Keyboard Operability Checks
<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Navigate forward with Tab and backward with Shift+Tab.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Verify that every interactive control displays an assertive focus ring.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(c) Ensure modals dismiss and restore focus upon pressing Escape.

2. Screen Reader Acoustic Checks
<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Open the rotor menu (`Caps Lock + U` or `VO + U`) to audit headings and landmarks.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Verify form inputs announce explicit accessible names and invalid states.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(c) Ensure dynamic status updates are announced without stealing active focus.

**DO NOT DO THIS:** Rely on mouse clicks during development and ship unverified keyboard traps.
```html wrong
<div class="custom-card" onclick="openOrder()">
  <span>View Order Details</span>
</div>
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Build native interactive controls and verify them with physical keystrokes.
```html right
<button type="button" class="custom-card"
        onclick="openOrder()">View Order Details</button>
```

➔ NEVER consider a user conversion funnel complete without an unplugged-mouse walkthrough.

➔ ALWAYS test modal dialogs and dropdown menus for Escape key dismissal and focus return.

➔ IF a component appears in visual reading order THEN verify it appears in the screen reader rotor.
