### The 80-Percent Core: How Metric Weights Determine the Score

Developers often assume that all suggestions listed in a Lighthouse audit report contribute equally to the final score. In reality, the overall Performance score is a strict weighted average derived from five specific lab metrics. Opportunities and Diagnostics listed further down the report have zero direct impact on your score; they serve purely as qualitative diagnostic advice:

```javascript title="lighthouse-weights.js"
const naiveModel = { allAuditsEqual: 0.20 }; // **WRONG:** Assumes opportunities directly move the score

const v10Weights = { TBT: 0.30, LCP: 0.25, CLS: 0.25, FCP: 0.10, SI: 0.10 }; // **RIGHT:** Official weights
```

The contrast exposes why micro-optimizations often produce disappointing score results. In modern Lighthouse (versions 10 and 11), three metrics dominate eighty percent of the overall calculation: Total Blocking Time accounts for thirty percent, Largest Contentful Paint contributes twenty-five percent, and Cumulative Layout Shift contributes twenty-five percent. The remaining twenty percent is split evenly between First Contentful Paint (ten percent) and Speed Index (ten percent). An engineering team that spends days minifying minor CSS bundles or compressing secondary icons without reducing LCP or clearing main thread blocking tasks will see negligible score movement.

### Log-Normal Curves: The Non-Linear Math of Point Distribution

Lighthouse does not score metrics on a flat linear scale. Instead, each raw metric value in milliseconds is mapped against log-normal distribution curves calibrated against real-world performance data from the HTTP Archive. Understanding this non-linear mathematical curve prevents teams from misallocating optimization hours:

```javascript title="score-targeting.js"
optimize('minify-css-3kb'); // **WRONG:** Minor diagnostic item yielding near-zero metric change

reduceMainThreadWork({ targetTBT: 150 }); // **RIGHT:** Directly shifts the 30% weighted blocking curve
```

```canvas title="Optimization Focus: Diagnostic List Ticking vs Core Metric Reduction" width="2/3" layout="compare"

```

Because log-normal scoring curves steepen around the boundary between "Needs Improvement" and "Good", the return on investment varies drastically across performance bands. Trimming five hundred milliseconds from an LCP that sits at four seconds delivers a dramatic point increase, lifting the score out of the red. Conversely, optimizing an already fast LCP from 1.5 seconds down to 1.2 seconds produces negligible point gains due to curve saturation. Performance engineering requires diagnosing which of the five core metrics sits furthest down its scoring curve and focusing effort where the mathematical leverage is highest.

Chrome Developers summarize the fundamental architecture of Lighthouse performance scoring in the official documentation:

> In general, only metrics contribute to your Lighthouse Performance score, not the results of Opportunities or Diagnostics. That said, improving the opportunities and diagnostics likely improve the metric values, so there is an indirect relationship. The Performance score is a weighted average of the metric scores. Naturally, more heavily weighted metrics have a bigger effect on your overall Performance score.

### Glossary

- **Lighthouse Performance Score**: A weighted composite score from 0 to 100 calculated from five standardized lab performance metrics.
- **Total Blocking Time (TBT)**: A lab metric measuring the total duration of CPU tasks exceeding 50ms between FCP and TTI (30% weight).
- **Speed Index (SI)**: A metric measuring how quickly visual content is visibly populated during page load (10% weight).
- **First Contentful Paint (FCP)**: The timestamp marking when the browser renders the first bit of text or visual content (10% weight).
- **Log-Normal Distribution**: A statistical probability distribution whose logarithm is normally distributed, used to map raw timings to scores.
