### The Thousand-Line Monolith: Why We Split Components
- [p] Cognitive overload and merge conflicts in monolithic files: Explains that while keeping multiple components in `App.jsx` seems convenient initially, large files create unreadable git diffs, frequent team merge conflicts, and unmaintainable codebases. ◼ Baptizes classic **Module Splitting / Component Files**, modern **ES Module Component Imports**, and concrete physical reality of *native ECMAScript module exports resolved by build bundlers*.
- [p] The one-component-per-file convention: Outlines the industry standard architecture of dedicating each file to a single primary component matching the filename (`Navbar.jsx` exports `Navbar`). ◼ Establishes clean directory organization and mental boundaries.
- [grounding] Leading Question: Why should components have separate files?
  Confusion Point: Keeping all components inside a single file feels convenient initially until team collaboration breaks down.
  Scene & Repetition: In the beginning, keeping every component inside App.jsx seems fast. You write a header, a card, a sidebar, and a footer. But soon your file is a thousand lines long. You scroll endlessly trying to find one small function. When two teammates edit the file, git merge conflicts explode. This is the pain of the **monolithic component file**: it hides your components in a wall of code. Splitting each **component** into its own **modular file** creates clean boundaries, isolated tests, and instant readability.
  Key Terms (Bold): `**monolithic component file**`, `**component**`, `**modular file**`, `**ES modules**`.
  Resolution: Giving each component its own file isolates changes, eliminates merge conflicts, and makes components easy to find and reuse.

### Default Exports: The Single Primary Component
- [p] Syntax and semantics of default exports: Explains `export default function Navbar() { ... }`. Details that a file can have at most one default export, designating the primary component of that module. ◼ Baptizes **default export** and **primary component designation**.
- [p] Importing default exports without curly braces: Demonstrates `import Navbar from './Navbar.jsx'`. Explains that because there is only one default export, no curly braces are needed. Highlights that while the importing file can technically choose any local name, keeping the local name identical to the filename and component is standard best practice. ◼ Grounds syntax rules for default imports.

### Named Exports: Multiple Utilities and Sub-Components
- [p] Syntax and semantics of named exports: Explains `export function NavLinks() { ... }`. Details that a file can have as many named exports as needed, making it ideal for utility collections, sub-components, and icon packs. ◼ Baptizes **named export** and **export catalog**.
- [p] Importing named exports with curly braces: Demonstrates `import { NavLinks } from './NavLinks.jsx'`. Explains that curly braces are mandatory because the consumer must explicitly pick which named export to bring into scope. Explains renaming via the `as` keyword: `import { NavLinks as Links } from './NavLinks.jsx'`. ◼ Unpacks exact identifier matching rules.
- [callout] One-line insider takeaway: Highlighting the definitive distinction between default and named imports. ◼ Reinforces that default imports require no braces and represent the primary component, while named imports require braces and pick specific items from a file.

- [components] Navigation component explorer: Finder-style panel showing `App.jsx` importing `Navbar.jsx`, which composes default export `BrandLogo.jsx` and named export `NavLinks.jsx`. ◼ Grounds component ownership and rendered UI strings before implementation syntax appears.

- [grounding] Leading Question: Why do named imports need curly braces?
  Confusion Point: Developers constantly forget whether to write curly braces when importing components.
  Scene & Repetition: You import a component and suddenly your build crashes with an undefined error. Did you forget the curly braces, or did you add them by accident? Here is the secret: curly braces mean you are plucking a specific named item out of a collection. If a file exports several things, you use curly braces to select the exact name you need. But if a file has a default export, there is only one main item, so no curly braces are needed. This is the rule of **named imports**: curly braces pick a specific name from the file's **export catalog**.
  Key Terms (Bold): `**named imports**`, `**curly braces**`, `**default export**`, `**export catalog**`.
  Resolution: Default exports represent the main export and require no braces, while named exports represent specific items from a file and require curly braces matching their export names.

### Glossary
- [glossary] ES Modules ◼ The standard JavaScript module system using import and export statements to share code across independent files.
- [glossary] Default Export ◼ A module export syntax (export default) allowing a file to designate one primary value that can be imported without curly braces.
- [glossary] Named Export ◼ A module export syntax (export function) allowing a file to export multiple values that must be imported using matching names inside curly braces.
- [glossary] Barrel Export ◼ The pattern of re-exporting multiple modular components from a central index.js file to simplify consumer import paths.
- [glossary] Export Catalog ◼ The collection of named functions, objects, and types exported by a JavaScript module for external consumer selection.

- [code] DO THIS: Use default exports for primary components and import them without curly braces.
```jsx right title="BrandLogo.jsx"
export default function BrandLogo() {
  return <div className="brand-logo">The National Times</div>;
}
```
◼ **Code Self-Audit (What makes the right code resilient):**
1. `export default function BrandLogo()`: Designates the primary component cleanly as the default export.
2. Consumers import without curly braces (`import BrandLogo from './BrandLogo.jsx'`), ensuring clean and predictable imports.
- [code] DO NOT DO THIS: Never mix default import syntax with named exports or use curly braces on default imports.
```jsx wrong title="Navbar.jsx"
import { BrandLogo } from './BrandLogo.jsx'; // **WRONG:** default export imported with **CURLY BRACES**
import NavLinks from './NavLinks.jsx'; // **WRONG:** named export imported without **CURLY BRACES**
```
◼ **Code Self-Audit (The runtime failure and import mismatch triggered by the wrong code):**
1. `import { BrandLogo }`: Attempts to pluck a named export called `BrandLogo` from a file that only has a default export, evaluating to `undefined`.
2. `import NavLinks`: Attempts to read the default export from a file that only has named exports, causing a runtime crash.
