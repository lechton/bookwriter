### Architectural Hierarchy and the Five-Step Framework

When building user interfaces in React, jumping straight into code and declaring state hooks is the most common path to architectural failure. React applications succeed when engineers follow a structured, step-by-step thinking process. The official React team established the canonical **Thinking in React** framework, decomposing the journey from visual mock to production application across five distinct phases:

- **1. Component Hierarchy**: Draw boxes around every element in the design mock, using the **Single Responsibility Principle** so each component ideally does only one thing.
- **2. Static Prototype**: Construct the complete visual layout using only JSX and props, completely devoid of `useState` hooks or event handlers.
- **3. Minimal State Representation**: Audit data with the three-question test to find the absolute minimum mutable state required, computing everything else on the fly.
- **4. State Placement**: Identify every component that relies on that state, find their **closest common ancestor**, and place the state in that shared owner.
- **5. Inverse Data Flow**: Pass updater callback functions down through props so user events in child controls trigger state updates in the parent.

The framework begins by enforcing a strict separation between visual structure and dynamic interactivity: building the static prototype first before touching state:

- **Decomposing the Hierarchy**: When breaking down a mock, look for natural visual boundaries. If a component grows too large or handles multiple concerns (such as an article table that formats rows, calculates filters, and coordinates pagination), decompose it into smaller child components.
- **Constructing the Static Prototype**: Building the visual interface using only JSX and props establishes the component tree skeleton without the mental overhead of state synchronization. You write lots of typing with very little thinking, creating a solid structural foundation.

> [!WILD]
> **Why should you build a static prototype first?** Imagine an architect constructing a skyscraper. Does the construction crew run electrical wiring and install plumbing before the steel frame and concrete floors are poured? Never. If you run wires before the walls exist, the framing crew tears through your cables. That is what happens when you write useState before your component tree is built. Writing state requires deep thinking about mutability and timing; building the layout requires thinking about visual composition. By building a static version first, you write lots of typing and zero thinking. You create a working visual skeleton using only props. Once the skeleton stands solid, adding state becomes effortless because you have clear homes for every variable. Understanding the **static prototype** as a **steel framework** clarifies why **decoupling layout from state** prevents **architectural chaos**.

### Auditing the Minimal State Representation

Once your static component tree renders correctly on screen, move to Step 3: find the **minimal state representation** of your UI.

The goal is to eliminate state redundancy. To determine whether a piece of data is genuine state, apply the three-question audit:

1. Does it remain unchanged over time? If so, it is not state.
2. Is it passed in from a parent via props? If so, it is not state.
3. Can you compute it from existing state or props? If so, it is **derived state** and must not be stored in React memory cells.

Consider a searchable editorial article desk that displays breaking news stories. The design displays an initial story list, search text, a breaking-news checkbox filter, and a matching story count. In this UI, the story list is passed down from the server (props), the filtered list is computed by running an array filter during render (derived), and the count is computed from the filtered array's length (derived). The only two genuine pieces of state are the search string and the checkbox toggle.

> [!WILD]
> **What is the minimal state representation?** Imagine packing a backpack for a mountain expedition. If you pack a heavy iron stove, three frying pans, and four extra blankets, your pack becomes so heavy you collapse before reaching base camp. You must practice strict minimalism: pack only what cannot be found on the mountain. In React, state is the weight in your backpack. Every state variable you add requires memory, re-renders, and synchronization. If you can gather firewood on the trail by computing a value during render, do not pack it in state! Keep only the bare essential inputs: the raw text typed by the reader and the checkbox toggle. Everything else is derived on the fly. Understanding **minimal state** as **expedition packing** clarifies why **eliminating redundant state** keeps applications **fast and lightweight**.

To construct this editorial article desk cleanly, we decompose `CategoryHeader.jsx`, `ArticleItem.jsx`, `ArticleTable.jsx`, `SearchBar.jsx`, and `ArticleSearch.jsx` across four sequential implementation steps:

### Step 1: Decomposing Presentation Components

Under Step 1 of Thinking in React, we divide the UI into atomic components using the Single Responsibility Principle. We isolate the presentation elements into two dedicated components. The header `CategoryHeader.jsx` formats the category title spanning both columns:

```jsx title="CategoryHeader.jsx"
export default function CategoryHeader({ category }) {
  return (
    <tr className="category-row">
      <th colSpan="2">{category}</th>
    </tr>
  ); // Category header spanning both table **COLUMNS**
}
```

Next, `ArticleItem.jsx` renders individual article entries with their breaking news indicator:

```jsx title="ArticleItem.jsx"
export default function ArticleItem({ story }) {
  return (
    <tr className="article-row">
      <td>{story.title}</td>
      <td>{story.isBreaking && <span className="breaking-tag">Breaking</span>}</td>
    </tr>
  ); // Atomic story row projecting title and breaking **INDICATOR**
}
```

Both `CategoryHeader` and `ArticleItem` are stateless display units driven entirely by props.

### Step 2: Assembling the Filtered Table Container

Under Step 2, we build the static container `ArticleTable.jsx` that accepts the full collection and active filters, grouping stories by category:

```jsx title="ArticleTable.jsx"
import CategoryHeader from './CategoryHeader.jsx';
import ArticleItem from './ArticleItem.jsx';

export default function ArticleTable({ stories, filterText, isBreakingOnly }) {
  const rows = [];
  let lastCategory = null;

  const filtered = stories.filter(story => {
    if (!story.title.toLowerCase().includes(filterText.toLowerCase())) return false;
    if (isBreakingOnly && !story.isBreaking) return false;
    return true;
  });

  filtered.forEach(story => {
    if (story.category !== lastCategory) {
      rows.push(<CategoryHeader key={story.category} category={story.category} />);
      lastCategory = story.category;
    }
    rows.push(<ArticleItem key={story.id} story={story} />);
  });

  return (
    <table className="article-table">
      <thead>
        <tr><th>Headline</th><th>Status</th></tr>
      </thead>
      <tbody>{rows}</tbody>
    </table>
  );
}
```

`ArticleTable` computes `filtered` synchronously on every render. Because the filtered list and category headers can be derived purely from `stories` and filter criteria, storing them in `useState` would be redundant and dangerous.

### Step 3: Authoring the Controlled Search Controls

The search form provides the interactive inputs. Following the controlled component pattern, it receives values and callback props without storing local state:

```jsx title="SearchBar.jsx"
export default function SearchBar({
  filterText,
  isBreakingOnly,
  onFilterTextChange,
  onIsBreakingOnlyChange
}) {
  return (
    <form className="search-bar" onSubmit={e => e.preventDefault()}>
      <input
        type="search"
        placeholder="Search articles..."
        value={filterText}
        onChange={e => onFilterTextChange(e.target.value)}
      />
      <label>
        <input
          type="checkbox"
          checked={isBreakingOnly}
          onChange={e => onIsBreakingOnlyChange(e.target.checked)}
        />
        Only show breaking dispatches
      </label>
    </form>
  ); // Controlled search controls forwarding events **UPWARD**
}
```

`SearchBar` forwards native input keystrokes and checkbox changes upward to its parent through `onFilterTextChange` and `onIsBreakingOnlyChange`. It holds zero state cells.

### Step 4: Lifting Search State into the Parent Component

In Steps 4 and 5 of Thinking in React, we identify the common ancestor and implement inverse data flow. Mock dataset `stories.js` supplies immutable article items:

```js title="stories.js"
export const sampleStories = [
  { id: '1', category: 'Metro', title: 'Port workers vote on harbor agreement', isBreaking: true },
  { id: '2', category: 'Metro', title: 'Transit council reviews underground budget', isBreaking: false },
  { id: '3', category: 'Culture', title: 'City library opens rare archive', isBreaking: false }
];
```

Then, the parent component `ArticleSearch.jsx` declares minimal state hooks and binds inverse data flow:

```jsx title="ArticleSearch.jsx"
import { useState } from 'react';
import SearchBar from './SearchBar.jsx';
import ArticleTable from './ArticleTable.jsx';
import { sampleStories } from './stories.js';

export default function ArticleSearch() {
  const [filterText, setFilterText] = useState('');
  const [isBreakingOnly, setIsBreakingOnly] = useState(false);

  return (
    <section className="search-container">
      <h2>National Times Article Desk</h2>
      <SearchBar filterText={filterText} isBreakingOnly={isBreakingOnly} onFilterTextChange={setFilterText} onIsBreakingOnlyChange={setIsBreakingOnly} /> // Passes state and updater callbacks to search **CONTROLS**
      <ArticleTable stories={sampleStories} filterText={filterText} isBreakingOnly={isBreakingOnly} /> // Forwards filter criteria to article table **VIEW**
    </section>
  );
}
```

In `ArticleSearch`, the two minimal state variables (`filterText` and `isBreakingOnly`) reside at the common apex. The component passes current values down to `ArticleTable` to drive the filtered view, and passes updater callbacks down to `SearchBar` to handle reader keystrokes.

### State Placement Rules and Inverse Data Flow

The final two steps of the framework complete the reactive circuit:

- **Step 4: Identify where your state should live**:
  1. Identify every component that renders something based on that state.
  2. Find their **closest common ancestor** component, meaning a single component above them all in the hierarchy.
  3. Either put the state directly into that common ancestor, or put it in a component higher up, or create a new wrapper component if none exists.
- **Step 5: Add inverse data flow**: Sibling components and deep children need to update state living high above them. Pass state updater functions (or custom action callbacks) down through props so that child events trigger re-renders in the state owner.

By following these five steps in strict sequence, you eliminate architectural guesswork. You never write a state setter without knowing exactly who owns it, and you never build a child component that accidentally duplicates data owned by its parent.

### Glossary

- **Thinking in React**: The official five-step methodology for breaking UI designs into component hierarchies, static prototypes, minimal state, state placement, and inverse data flow.
- **Single Responsibility Principle**: The software design principle stating that a component should ideally do only one thing; if it grows, it should be decomposed into smaller subcomponents.
- **Static Prototype**: A complete, working React component tree that renders UI using only props, completely devoid of state and interactivity.
- **Minimal State**: The smallest possible set of mutable variables required to represent the entire dynamic state of the user interface without redundancy.
- **Inverse Data Flow**: The architectural pattern of passing callback functions down through props so child components can trigger state updates in their common ancestor.

### Summary

**The Five-Step React Design Methodology: From Design Mock to Dynamic Component Architecture**

Thinking in React transforms UI development from an ad-hoc trial-and-error exercise into a systematic engineering discipline. By separating static layout composition from state identification and data flow, you create resilient component hierarchies that scale cleanly.

❒ The Canonical Five Steps
1. Deconstruct the mock into a component hierarchy.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Apply the single responsibility principle to draw component perimeters around distinct UI regions.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Identify parent-child and sibling relationships across the visual tree.
2. Build a static version using only props.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Create the full JSX layout with mock props and zero `useState` hooks.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Verify visual rendering without the cognitive overhead of state management.
3. Determine the minimal state representation.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Discard values that come from props, remain static, or can be computed during render.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Keep only the raw, irreducible inputs that change over time.
4. Position state in the closest common ancestor.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Find the lowest component that sits hierarchically above all consumers of that state.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Establish that common ancestor as the single authoritative source of truth.
5. Establish inverse data flow.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Pass setter callbacks down to interactive child controls.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Allow user events to trigger state transitions cleanly at the common apex.
➔ ALWAYS build a static version of the component tree with props before adding state hooks.<br>
➔ NEVER declare a state variable for information that can be derived during the render pass.
