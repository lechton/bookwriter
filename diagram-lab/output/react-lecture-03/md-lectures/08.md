### Props: The Component Configuration Channel

A React component without inputs is merely a static stamp. If you write a button component with hardcoded text inside its JSX, every single copy you place on the page renders the exact same word and executes the exact same behavior. To build flexible, reusable interfaces, components need a mechanism to receive external configuration data.

In JavaScript, when you want a function to perform calculations on different values, you pass it arguments: `calculateTotal(price, tax)`. React components operate on the exact same principle. The inputs you pass to a component are called **props** (known classically as **Component Props** and in modern documentation as the **Props Object / Data Contract**). In physical browser execution, props are represented as a frozen JavaScript object passed as the first argument into your component function.

Every JSX attribute you write on a component tag is gathered by React into this single props object. When you write `<SubscribeButton label="Annual Pass" price={49} isFeatured={true} />`, React constructs `{ label: "Annual Pass", price: 49, isFeatured: true }` and hands it to the `SubscribeButton` function. Through props, a single button component can serve as a monthly signup button, an annual pass banner, or a gift subscription trigger.

> [!WILD]
> **What are props in plain English?** In standard JavaScript, when you want a function to calculate different results, you pass it arguments. You call add(2, 3) or add(10, 20). React components work the exact same way. When you want a button to display a different label or color, you pass it inputs called props. React packs every attribute you write into a single object and hands it to your component function. It is just **function arguments** wrapped in an object, time and time again. Understanding **props** as plain **function arguments** clarifies how parents configure child **components**.

### Reading and Destructuring Props

Because React passes all incoming attributes inside a single object parameter, your component function reads that object directly: `export default function SubscribeButton(props)`. You can access individual properties using standard object dot notation, such as `props.label` and `props.price`.

However, writing `props.` before every variable quickly becomes repetitive and clutters your markup. In modern React development, the industry-standard idiom is **object destructuring** directly inside the function parameter parentheses:

```jsx title="SubscribeButton.jsx"
export default function SubscribeButton({ label, price, isFeatured = false }) {
  return <button className="sub-btn">{label}: ${price}</button>; // Binds props directly into local **VARIABLES**
}
```

Destructuring plucks specific properties from the incoming object and binds them as local variables in component scope. Furthermore, destructuring allows you to declare **default prop values**. If a parent component renders `<SubscribeButton label="Basic" price={5} />` without supplying `isFeatured`, the fallback `isFeatured = false` takes effect automatically.

> [!KEY]
> Props flow strictly downward from parent to child; components never modify their own props.

Here is the implementation of our reusable child component, `SubscribeButton.jsx`:

```jsx title="SubscribeButton.jsx"
export default function SubscribeButton({ label, price, isFeatured = false }) {
  return (
    <button className={`sub-btn ${isFeatured ? 'featured' : ''}`}>
      <span className="btn-label">{label}</span> // Projects dynamic label prop into **SPAN**
      <span className="btn-price">${price}</span> // Projects dynamic price prop into **SPAN**
      {isFeatured && <span className="featured-tag">Best Value</span>} // Conditionally renders featured **TAG**
    </button>
  );
}
```

The component signature destructures `{ label, price, isFeatured = false }` directly from the incoming props object, assigning a fallback value of `false` if `isFeatured` is omitted. Inside the button, the expressions `{label}` and `{price}` project incoming prop values directly into text spans. The trailing logical AND expression `{isFeatured && ...}` evaluates conditionally, mounting the "Best Value" tag only when `isFeatured` evaluates to `true`.

Now examine how the parent container, `PaywallSection.jsx`, passes different props to each button:

A single component definition effortlessly powers both subscription tiers without duplicated markup.

### The Immutability Law: Why Props Are Strictly Read-Only

When David attempted to modify a button's label by writing `props.label = "Discounted"`, React halted execution with a strict runtime error. Why does React prevent components from changing their own props?

This restriction is governed by the **immutability law**: **props are strictly read-only snapshots**. In React, component functions are designed to act as **pure functions**. A pure function is a mathematical ideal: given the exact same inputs, it must always return the exact same user interface description without causing external side effects or modifying incoming data.

Consider the severe bugs that would occur if child components could mutate their own props:

1. **State Corruption**: In React, data belongs to the parent component that instantiated it. If a child component could alter `props.price`, it would mutate the parent's memory from below, causing the parent and sibling components to fall out of sync.

2. **Broken Unidirectional Data Flow**: React architecture relies on **unidirectional data flow** (one-way data flow). Data flows strictly downward from parent to child. If children could mutate props backward up the tree, tracking which component altered a value would become impossible.

3. **Predictable Re-renders**: To protect against accidental mutations, React runs `Object.freeze()` on the props object in development. Attempting to assign a new value to any prop immediately throws a `TypeError: Cannot assign to read only property`.

If a value needs to change over time, the component should not mutate its props. Instead, the parent component must store that value in state. When the state changes, the parent re-renders and passes a fresh, updated prop snapshot downward to the child. The child receives the new value, re-evaluates its JSX, and updates the screen smoothly.

> [!WILD]
> **Why can a component never mutate props?** Imagine you hire a courier to deliver an official contract. The courier opens the envelope, crosses out the price with a pen, and writes a new number. The recipient and the sender are now completely out of sync. Chaos ensues. This is why React freezes props. Props are an official delivery from the parent component. If a child component could alter its own props, data would change secretly from behind, causing subtle bugs across your app. This is the **immutability law**: props are strictly **read-only snapshots**, preserving **unidirectional data flow**.

> [!TIP]
> **To impress the interviewer:** When asked why props are immutable, connect the concept to pure functions and reconciliation. Explain that React components must be pure with respect to their props: given identical props, they must return identical JSX. Mutating props breaks the purity guarantee, invalidates memoization optimizations, and prevents React's concurrent scheduler from safely pausing and resuming component renders.

### Glossary

- **Props**: The inputs passed to a React component via JSX attributes, assembled by React into a single read-only JavaScript object.
- **Object Destructuring**: The JavaScript syntax ({ label, price }) used in component parameters to extract properties from the props object directly into local variables.
- **Unidirectional Data Flow**: The architectural principle in React where data always flows in one single direction, downward from parent components to child components.
- **Immutability**: The rule stating that props cannot be modified, reassigned, or mutated by the receiving child component.
- **Default Prop Value**: A fallback value assigned during destructuring (such as isFeatured = false) used when the parent omits that prop.

➔ NEVER attempt to reassign or mutate props inside a child component.

➔ ALWAYS use object destructuring with sensible defaults in component parameter lists.

➔ IF a value needs to change over time THEN **manage it as state in the owning parent component**.

**DO THIS:** Extract props using object destructuring and treat them as immutable inputs.

```jsx right title="SubscribeButton.jsx"
export default function SubscribeButton({ label, price }) {
  return (
    <button className="sub-btn">
      <span>{label}</span>
      <span>${price}</span>
    </button>
  );
}
```

**DO NOT DO THIS:** Never attempt to mutate or reassign incoming props inside a child component.

```jsx wrong title="SubscribeButton.jsx"
export default function SubscribeButton(props) {
  props.price = props.price * 0.9;
  return <button>{props.label} - ${props.price}</button>;
}
```
