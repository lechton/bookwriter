# Q14: Responding to Events — Operational Principle Map
- **Source Map**: `01-01-map/14.md`
- **Topic Tag**: `#event_handling` | `❱ CORE`
- **Interview Question**: *How do you respond to user events like clicks and typing?*

## Authorized Scope
Q14 teaches what happens once a handler runs: handlers run on user interaction and never during render, which makes them the home for side effects, they receive a React event object whose `target` and `currentTarget` differ, React's `onChange` fires on every keystroke, events bubble from the clicked element up through its ancestors' handlers, `e.stopPropagation()` keeps an `ArticleActions` button from also opening its parent card, calling the parent's handler explicitly is an alternative to relying on bubbling, and `e.preventDefault()` stops browser defaults such as a form submit reloading the page; handlers only log, because state is not available yet; it builds on Q12 (side effects stay out of render) and Q13 (handler syntax and handler props), and it excludes state updates from handlers (Q16), controlled inputs (Q23), form actions, and root-level delegation internals (Q79).

## Principles

### Principle 1: Put side effects in handlers, which run on interaction, not during render
- **Kind**: Model
- **Rule**: React stores a handler during render but calls it only when the event happens, so a handler is not part of the render calculation and may do things (log analytics, write to storage, start a request, and later set state) that a component body must never do.
- **Importance**: Q12 removes side effects from render, and without this model a developer has nowhere to put them and slides back into the component body or into `useEffect` for work that a click should trigger.
- **Prediction**: With a `console.log` in `ArticleCard`'s body and another in `handleBookmark`, a page load under StrictMode prints the render log twice and the handler log never, and each click prints the handler log once without printing the render log.
- **Required Lesson Proof**: Add both logs, load the page, show the console, click Bookmark twice, and show two handler lines.
- **Sources**: Core Truth of `01-01-map/14.md`; responding-to-events "Can event handlers have side effects?"; rules Note on side effects; the merged logging candidate, verified in React 19.3.

### Principle 2: Read `currentTarget` for the handler's element and `target` for what was touched
- **Kind**: Model
- **Rule**: Every handler receives a React event object that follows the DOM `Event` standard: `e.currentTarget` is the element whose handler is running, and `e.target` is the innermost element the user actually touched, which can be a child such as an icon inside a button; `e.nativeEvent` holds the browser's own event.
- **Importance**: A handler on a card that reads `e.target.dataset.id` breaks as soon as the user clicks the icon or headline inside it, because `target` is then the icon, not the card.
- **Prediction**: Clicking the ★ icon inside the Bookmark button, with a handler on the surrounding `<article>`, logs `target` SPAN and `currentTarget` ARTICLE.
- **Required Lesson Proof**: Log `e.target.tagName` and `e.currentTarget.tagName` in the card's handler, click the icon, then click the headline, and show the two lines.
- **Sources**: Mechanism of `01-01-map/14.md`; common.md "React event object" Properties and Caveats; the merged candidates, verified in React 19.3.

### Principle 3: Expect `onChange` on every keystroke
- **Kind**: Model
- **Rule**: React's `onChange` on an `<input>` fires for every change of the value, as the browser's `input` event does, and not only when the field loses focus as the DOM `change` event does, so `e.target.value` in the handler holds the text typed so far.
- **Importance**: A developer who knows the DOM `change` event expects one call on blur and writes validation or search logic for that timing, then sees it run on every keystroke.
- **Prediction**: Typing "ab" into the search field logs `onChange value: a` and then `onChange value: ab`, and `e.nativeEvent.type` is `input`.
- **Required Lesson Proof**: Log `e.target.value` and `e.nativeEvent.type` in `onChange`, type two characters, and show the two lines before leaving the field.
- **Sources**: Interview Question and Core Truth of `01-01-map/14.md`; the merged typing candidate, verified in React 19.3; the Deferred row for controlled inputs (Q23).

### Principle 4: Expect clicks to bubble up through every ancestor's handler
- **Kind**: Model
- **Rule**: An event starts at the element the user touched, runs that element's handler, and then runs the handlers of each ancestor in turn up to the root; capture handlers (`onClickCapture`) run first on the way down, and `onScroll` is the one event that does not bubble.
- **Importance**: A developer who puts a Bookmark button inside a clickable `ArticleCard` is surprised when bookmarking also opens the article, and cannot fix it without this model.
- **Prediction**: Clicking Bookmark inside the card logs `card capture`, then `bookmark onClick`, then the card's `onClick`.
- **Required Lesson Proof**: Add handlers to the button, the card, and an `onClickCapture` on the card, click Bookmark, and show the order in the console.
- **Sources**: responding-to-events "Event propagation", its Pitfall on `onScroll`, and the Deep Dive "Capture phase events"; the order verified in React 19.3.

### Principle 5: Stop propagation where a child's action must stay local
- **Kind**: Decision
- **Rule**: When clicking a control inside a clickable container means something different from clicking the container, call `e.stopPropagation()` in the control's handler, and when the parent should still react, call its handler prop explicitly after stopping, so the chain of code for the event is visible in one place.
- **Importance**: Without it, the Share and Bookmark buttons in `ArticleActions` also trigger the card's navigation, and a colleague's parent handler seems to run "by itself" (the "Wire up the events" Challenge).
- **Review Point — Do**: Check that every action nested inside a clickable container stops propagation when its meaning differs from the container's, and calls the parent's handler prop explicitly when the parent must still act.
- **Required Lesson Proof**: Click Share without `stopPropagation` and show both handlers logging, add `e.stopPropagation()` and show only `share onClick (stopped)`, then add an explicit `onShare()` call and show the parent's log returning through the prop.
- **Sources**: Code Experiment of `01-01-map/14.md`; responding-to-events "Stopping propagation", "Passing handlers as alternative to propagation", Recap bullets 7 and 9, and Challenge "Wire up the events"; the Share output verified in React 19.3.

### Principle 6: Prevent the browser's default action when React handles the event
- **Kind**: Decision
- **Rule**: Some events carry a browser default, such as a form submit navigating to its action URL or a link opening its `href`, so a handler that handles the event in JavaScript calls `e.preventDefault()`; this is unrelated to `e.stopPropagation()`, which only stops ancestor handlers.
- **Importance**: A search form in the masthead reloads the whole page on submit, wiping what the reader typed, and developers reach for `stopPropagation()` to fix it, which does nothing for the default action.
- **Review Point — Do**: Check that every `onSubmit` handler, and every link handler that replaces navigation, calls `e.preventDefault()`, and that `stopPropagation()` is not used for that purpose.
- **Required Lesson Proof**: Submit the search form without `preventDefault()` and show the page navigate (the URL gains `?` and the console clears), then add `e.preventDefault()` and show the page stay, and show that `stopPropagation()` alone does not stop the reload.
- **Sources**: Mechanism of `01-01-map/14.md`; responding-to-events "Preventing default behavior" and Recap bullet 8; the submit behavior verified in Chrome with React 19.3.

## Senior Answer
I respond to clicks and typing with handlers passed to event props, and they run only when the event happens, never during render, which makes them the place for side effects such as analytics, storage, requests, and later state updates. Each handler receives a React event object that follows the DOM standard: `e.currentTarget` is the element whose handler runs, `e.target` is whatever the user actually touched, possibly an icon inside the button, and for typing, React's `onChange` fires on every keystroke with the text so far in `e.target.value`, unlike the DOM `change` event that waits for blur. Events bubble from the touched element up through every ancestor's handler (capture handlers run first, and `onScroll` does not bubble), so a Bookmark button inside a clickable card calls `e.stopPropagation()` to keep the card from opening, and if the parent must still react, the child calls the parent's handler prop explicitly. Browser defaults are a separate matter: a form's `onSubmit` calls `e.preventDefault()` so the page does not reload, and `stopPropagation()` does nothing for that.
