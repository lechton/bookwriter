## Operational Principles

### Principle 1: Split Files Along Cohesive Reuse and Ownership Boundaries
- **Operational Rule**: Move a component into its own module when the boundary makes the code easier to scan, reuse, test, or change independently. Keep small private helpers beside their owner when another file would add navigation without creating a useful public contract.
- **Review Point — Condition**: Split by stable responsibility and reuse, not by an automatic one-function-per-file rule or an arbitrary line count.
- **Required Lesson Proof**: Refactor one monolithic `App.jsx` into a primary component module and a locally retained helper, explaining why one boundary earns a file and the other does not.

### Principle 2: Export Only the Module Values Other Files Need
- **Operational Rule**: Treat each module's exports as its public API and leave implementation-only components or helpers unexported. A narrow export surface prevents other files from depending on details that the owning module should be free to change.
- **Review Point — Do**: Review every `export` by identifying its external consumer; keep a value private when no other module needs it.
- **Required Lesson Proof**: Show a private badge helper used inside `ArticleCard.jsx`, then export only the values that `App.jsx` legitimately consumes.

### Principle 3: Use the Default Export Contract for One Primary Module Value
- **Operational Rule**: A module can expose at most one default export, and consumers import that binding without braces. JavaScript permits the importing file to choose the local name, but a meaningful name aligned with the component and filename keeps searches and debugging clear.
- **Review Point — Prefer**: Prefer a default export when the module has one obvious primary component, while keeping the imported local name recognizable even though renaming is legal.
- **Required Lesson Proof**: Pair `export default function ArticleCard()` with an unbraced import, then demonstrate that a differently named default import still resolves to the same binding.

### Principle 4: Use Named Export Contracts for Multiple Public Values
- **Operational Rule**: Named exports let one module expose several public components or helpers, and consumers import the exact exported names inside braces. Use an explicit `as` alias when the receiving module needs a different local name.
- **Review Point — Do**: Match each named import to an exported name, including capitalization, or alias it explicitly rather than relying on an implicit rename.
- **Required Lesson Proof**: Export two named values, import both with braces, alias one deliberately, and show the module error produced by requesting a name that is not exported.

### Principle 5: Resolve the Exact Module Path Before React Rendering
- **Operational Rule**: Verify the relative path, directory, filename casing, and extension convention when a module cannot be found. ES Module resolution must locate the source file before React can receive any imported component value.
- **Review Point — Do not**: Do not debug JSX rendering until the module path resolves to the intended file; use Principles 3 and 4 separately when the file resolves but its export contract does not match.
- **Required Lesson Proof**: Trigger one relative-path error and one filename-case mismatch, then trace each build-time failure to the unresolved module boundary.
