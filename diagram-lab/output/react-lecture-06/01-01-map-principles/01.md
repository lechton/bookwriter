# Q01: What is React and the Declarative Model — Operational Principle Map
- **Source Map**: `01-01-map/01.md`
- **Topic Tag**: `#what_is_react` | `❱ CORE`
- **Interview Question**: *What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?*

## Authorized Scope
Q01 answers "What is React" with static data only: React is a JavaScript library for building user interfaces out of components, the screen is a projection of the data (you describe what each state should show, React calls your components and applies the result to the DOM), one source of truth feeds every visible copy of a fact, and the DOM inside React's root belongs to React rather than to hand-written queries and `innerHTML` rewrites. It builds on no earlier lesson, distributes the shared `readerName` through one module-level constant instead of props or state, and leaves the mounting pipeline to Q09, component authoring rules to Q02, JSX grammar to Q03, curly-brace expressions to Q04, the UI tree to Q05, props to Q06, purity to Q12, the trigger-render-commit pipeline to Q17, StrictMode to Q20, and every behavior that needs an event or a re-render to the state lessons, with one-sentence previews where the lesson's code already touches those topics.

## Principles

### Principle 1: Treat React as a component library you adopt one root at a time
- **Kind**: Model
- **Rule**: React is a JavaScript library for rendering user interfaces: you build the screen from components, plain functions that return markup descriptions, and you attach React to one DOM node per island, from a single widget inside a hand-written page up to the whole application, while frameworks add routing, builds, and server rendering on top.
- **Importance**: "What is React" is the interview question, and "a component-based library you can adopt incrementally" is its expected first sentence; a candidate who calls React a framework gets the follow-up about who owns routing and the build.
- **Prediction**: A plain HTML page with one empty `<div id="root">` shows nothing until JavaScript runs, and after `root.render` the DevTools tree shows React's markup inside that one div while the paragraphs outside it remain the original hand-written HTML.
- **Required Lesson Proof**: Render `SiteHeader` into the root div of an otherwise static National Times page; show view-source (the empty div) against DevTools (React's markup inside the div only); name `createRoot` as Q09's subject in one sentence without teaching it.
- **Sources**: describing-the-ui Intro; add-react-to-an-existing-project; your-first-component "Components all the way down"; the merged blank-page framework contrast from the createRoot Note.

### Principle 2: Treat the screen as a projection of your data
- **Kind**: Model
- **Rule**: A component describes what the UI should look like for the current data; React calls your components and applies the returned description to the DOM, calculating which properties changed and applying the minimal necessary operations, so the same data always produces the same screen and your code contains no DOM commands at all.
- **Importance**: This is the model every later mechanism deepens (the Q17 pipeline, Q56 re-renders, Q77 reconciliation), and it corrects the interview myth of a "virtual DOM" that exists to be fast: React's guarantee is correct, minimal updates, not universal speed.
- **Prediction**: A `console.log` inside a component that no JSX ever mentions never prints, because only React's render calls components, and the rendered DOM contains only plain HTML with no trace of the component names.
- **Required Lesson Proof**: Log inside `SiteHeader` and inside an unused component; show that only the used one prints on the initial render; inspect the DOM to show plain HTML where the component tags stood; preview in one sentence that the minimal patching of re-renders is demonstrated in Q17.
- **Sources**: card Core Truth and Under the Hood; render-and-commit Steps 2 and 3 with the merged initial-render and browser-sees-HTML candidates; react-compiler introduction ("UI as a function of their current state"); the purity preview (Q12) and pipeline preview (Q17).

### Principle 3: Declare the destination instead of commanding each step
- **Kind**: Decision
- **Rule**: Write the UI as the destination, the markup each state should show, and let React perform the updates, instead of writing step-by-step commands that query elements and patch them one by one, because every hand-written query is one more place an update can forget.
- **Importance**: The card's Friction is the review finding: hand-written update functions drift out of sync, and the one element a query missed keeps showing yesterday's name on screen with no error anywhere.
- **Review Point — Prefer**: Prefer describing the final markup for each state; avoid update functions that walk the DOM with `getElementById` and patch nodes individually.
- **Required Lesson Proof**: Run the plain-JavaScript `updateHeaderUser` that rewrites nine of the ten places where Elena's name appears and show the tenth widget still greeting the old name; then show the React version, where the markup simply reads `readerName` and no query exists to be forgotten.
- **Sources**: card Friction and Mechanism; reacting-to-input declarative-versus-imperative section and Challenge 3 Solution, both merged.

### Principle 4: Keep one source of truth per fact
- **Kind**: Decision
- **Rule**: Store each fact exactly once, one `readerName` constant, and let every widget that displays it read that same value, because two stored copies of one fact can disagree while two derivations of one source cannot.
- **Importance**: State drift is the bug this lesson exists to kill, and "single source of truth" is vocabulary a senior interviewer expects; reviewers delete derivable duplicates on sight.
- **Review Point — Do**: Keep each fact in one place and derive every visible copy from it; when a fact must change over time it will live in the closest common parent (Q26), never in two widgets at once.
- **Required Lesson Proof**: Show the naive page storing the name in two places disagreeing after the update; show `Greeting` and `SubscriberBadge` both reading the one `readerName` and agreeing by construction; edit the constant, reload, and show both widgets change together.
- **Sources**: card Code Experiment; sharing-state single-source-of-truth section; the merged derive-don't-duplicate candidate from thinking-in-react Step 3; the Q06 and Q26 previews.

### Principle 5: Leave React's DOM to React
- **Kind**: Decision
- **Rule**: Once a node lives inside React's root, never modify, move, or remove it with hand-written DOM code: an `innerHTML` rewrite destroys the real nodes and everything living in them, such as focus and typed text, and React's next update then meets a tree it no longer recognizes; change the data and let React patch the DOM instead.
- **Importance**: Mixing jQuery-style scripts with a React root is the classic integration bug: it corrupts the screen silently first and crashes later, when React patches nodes that no longer exist; reviewers flag any DOM mutation inside the root on sight.
- **Review Point — Do not**: Do not write to, move, or delete DOM nodes that React manages; if outside code truly owns a region, keep it outside the root or inside an element React always leaves empty (the escape hatches arrive with refs in Q34).
- **Required Lesson Proof**: With a plain script, focus an input on the page, rewrite a sibling region with `innerHTML`, and show that `document.activeElement` fell back to the body and the old node is disconnected; then show that the React version contains no such code at all, and preview in one sentence that Q17 demonstrates React's surgical patching with the Clock example.
- **Sources**: card Under the Hood; manipulating-the-dom-with-refs best practices and Recap bullets; the merged ownership, safe-region, and `remove()`-crash candidates; the supporting `innerHTML` node-identity fact.

## Senior Answer
React is a JavaScript library for building user interfaces out of components, plain functions that return a description of the UI, and I can adopt it for one corner of an existing page or for the whole app, one root at a time, while a framework would also supply routing, builds, and server rendering. The model is a projection: my components describe what the screen should show for the current data, React calls them and applies the result to the DOM with the minimal necessary operations, and the same data always produces the same screen, which is why the guarantee is correctness, not a promise that a so-called virtual DOM is always faster. In plain JavaScript I commanded the DOM step by step, query this ID, set that text, and any element I forgot went stale with no error; in React I declare the destination once. Each fact lives in exactly one place, `readerName` in `SiteHeader`, and every widget derives from that single truth, so copies can never disagree. And because the DOM inside React's root belongs to React, I never rewrite, move, or delete its nodes by hand: an `innerHTML` rewrite destroys the real nodes along with focus and typed text, and fights React's own updates, so I change the data and let React patch the DOM.
