# Architectural Decision Brief — 2026-09-26-11: Canonical Industry Vocabulary Standard and Anti-Circumlocution Law

## Executive Summary
This brief resolves an insidious regression where AI models, in an over-eager attempt to obey instructions to "avoid academic jargon," threw out standard, canonical industry terminology. In Lecture 01, instead of baptizing fundamental concepts like **Declarative UI vs. Imperative DOM Scripting**, **Unidirectional Data Flow**, **Single Source of Truth**, and **Virtual DOM Reconciliation**, the model invented 11-word conversational circumlocutions (e.g. *"Declare Complete Target End-States Rather Than Scripting Transition Steps"*).

Under `#2026_09_26_11_group_1`, we establish the **Canonical Industry Vocabulary Standard**:
*Every principle title and definition must front-load and explicitly name the canonical platform and industry terminology that senior engineers and technical interviewers expect, and immediately ground that vocabulary in physical machine mechanics.*

## 1. Root Cause Analysis

### 1.1 The Exclusionary Fallacy on "Academic Jargon"
In previous iterations, the instruction system warned against "academic jargon," targeting bloated, disembodied academic phrases like *"Monolithic entanglement"* or *"Horizontal cross-component coupling"*. 

However, AI models routinely succumb to **The Exclusionary Fallacy** (Rule `AGENTS.md`): interpreting a warning against bad jargon as a total prohibition against all technical terminology. The model began treating ubiquitous industry standards—like **"Declarative UI"**, **"Imperative Scripting"**, **"Unidirectional Data Flow"**, and **"Virtual DOM"**—as forbidden words. It replaced them with long-winded descriptive circumlocutions that danced around the terms without ever baptizing the actual concepts.

### 1.2 The Pedagogical Defect in Interview Preparation
When a student prepares for a senior technical interview, an interviewer will directly ask: *"Explain the difference between declarative UI in React and imperative DOM manipulation."*
If the lecture tip-toes around the words like a tongue-twister, the student fails to connect the physical mechanics they learned to the actual vocabulary used in the industry. The job of an authoritative guide is never to hide standard terms behind conversational evasions, but to **lead with the canonical term upfront and immediately ground its physical machine behavior**.

## 2. The New Standard (#2026_09_26_11_group_1)

### 2.1 Front-Load Canonical Terminology, Ground Physically
Every principle must marry two essential halves:
1. **The Canonical Industry Name**: The exact term recognized across the global React ecosystem (e.g. Declarative UI, Imperative DOM, Unidirectional Data Flow, Single Source of Truth, Virtual DOM Reconciliation, Component Functions: $UI = f(data)$).
2. **The Physical Machine Trace**: The concrete path through Developer JSX, Compiler AST, and Browser DOM, explaining the exact physical failure mode prevented.

### 2.2 Re-titling and Defining Principles in Lecture 01
- **Principle 1**: `Principle 1: Model UI as Component Functions of Data (UI = f(data)) Rather Than Querying the DOM`
  - Canonical Terms: Component Functions, $UI = f(data)$, Imperative DOM queries (`getElementById`).
- **Principle 2**: `Principle 2: Enforce Unidirectional Data Flow from a Single Source of Truth to Prevent State Drift`
  - Canonical Terms: Unidirectional Data Flow, Single Source of Truth, State Drift.
- **Principle 3**: `Principle 3: Write Declarative UI Descriptions Instead of Scripting Imperative DOM Transitions`
  - Canonical Terms: Declarative UI, Imperative DOM Scripting, Intermediate State.
- **Principle 4**: `Principle 4: Keep Application State in JavaScript Memory and Treat the DOM as a Write-Only Projection Screen`
  - Canonical Terms: State in Memory, Write-Only Projection Surface, DOM-Coupled Logic.
- **Principle 5**: `Principle 5: Use Virtual DOM Reconciliation to Surgically Patch the DOM Without Destroying Focus`
  - Canonical Terms: Virtual DOM, Reconciliation, Surgical Patching, Focus Preservation.
