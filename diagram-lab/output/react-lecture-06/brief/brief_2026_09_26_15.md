# Architectural Decision Brief — 2026-09-26-15: Editorial Division of Labor Between Principle Cards and Machine Trace Prose

## Executive Summary
This brief resolves the principle definition bloat defect where 5-sentence, 84-word procedural specs were crammed into callout boxes. Under `#2026_09_26_15_group_1`, we formalize the **Editorial Division of Labor** between principle definition cards and deep explanation prose: the principle box functions strictly as a concise architectural compass (2 to 3 calm, active sentences, ~35–50 words) stating the core rule, the canonical mechanism, and the operational failure mode without dumping internal compiler transformation code (`_jsx(...)`) or multi-step execution flows into the box. We reserve the full machine trace (AST branching, `_jsx()` emissions, W3C specifications, Fiber node records) for the deep prose explanation underneath the code cards, expand the Golden Exemplar Bank with Lesson 2 Component Anatomy models, and record "The Exhausted Spec Dump" counter-example.

## 1. Root Cause Analysis

### 1.1 The Machine Trace Leakage Trap
In `#2026_09_26_13_group_1`, we established the natural 3-step sequence: (1) physical screen consequence first, (2) named mechanism second, and (3) step-by-step physical trace in memory and DOM third. At the same time, rule `#2026_09_26_09_group_1` required deep physical machine tracing through compiler and runtime layers.
Because the boundary between the definition card and the explanation prose was not sharply delineated, AI models conflated the two: they attempted to execute the entire 3-layer machine trace (Developer JSX $\rightarrow$ AST $\rightarrow$ `_jsx()` emission $\rightarrow$ function pointer in memory $\rightarrow$ browser DOM paint) directly inside the callout box.

### 1.2 The Resulting Editorial Collapse
This leakage produced an unreadable 84-word, 5-sentence flowchart inside a 200px callout card:
> ❌ *"When you mount a component in JSX, starting its name with a capital letter tells the compiler to run your JavaScript function instead of creating an empty browser tag. If you write `<articleCard />` in lowercase, the browser creates an unknown HTML element and renders a blank screen without throwing an error. React enforces this distinction through the JSX compiler AST branch. When the compiler encounters an uppercase tag like `<ArticleCard />`, it emits an unquoted function identifier `_jsx(ArticleCard)`. React holds the function pointer in memory, runs `ArticleCard()`, and paints the returned markup to the page."*

This collapsed the publication's editorial hierarchy:
1. It stated everything upfront in a breathless, exhausted tone.
2. It forced raw compiler code (`_jsx(...)`) into what should be a memorable architectural law.
3. It made the comparative code card and the prose explanation underneath entirely redundant, as the prose immediately repeated the exact same AST walkthrough.

## 2. The Solution Architecture (#2026_09_26_15_group_1)

### 2.1 The Editorial Division of Labor
We clearly separate the editorial roles across the three visual zones of each principle:
1. **The Principle Definition Card (The Architectural Compass)**:
   - Length: Exactly 2 to 3 calm, human sentences (~35–50 words).
   - Content: Core rule or physical screen reality $\rightarrow$ canonical platform mechanism $\rightarrow$ operational consequence or silent failure mode.
   - Tone: A clear-headed mentor giving a memorable rule to a tired developer.
   - Prohibitions: Zero raw compiler transformation code (`_jsx(...)`), zero multi-step procedural flowcharts.
2. **The Comparative Code Cards**:
   - Symmetrical, full-width code snippets demonstrating the best practice vs the anti-pattern, labeled with visceral action-paired comments (`// PascalCase emits function reference` vs `// Lowercase emits string literal`).
3. **The Explanation Prose Below the Cards (The Machine Trace)**:
   - The dedicated home of the deep machine trace. Here, the text walks through the AST Unicode character category checks (`Ll` vs `Lu`), the transpiled `_jsx()` code block, W3C `HTMLUnknownElement` browser parsing, Fiber node allocation, and DevTools inspection.

### 2.2 Golden Exemplar Bank Expansion
We added canonical models for **Lesson 2 Component Anatomy** directly into `skills/v6.3/principled-theory/SKILL.md`:
- **Principle 1 (PascalCase vs Native HTML)**:
  > *"Always name custom components with a capital letter in **PascalCase** so React knows to run your function. When a tag starts with an uppercase letter, React invokes your component and renders its markup. Lowercase tags are treated as native HTML, causing the browser to render an empty unknown element and fail silently."* (3 sentences, 46 words)
- **Principle 2 (Return Descriptors vs DOM Mutation)**:
  > *"React components must return a description of what the screen should look like instead of modifying the DOM by hand. Your component function should be a pure calculation that returns JSX or `null`. If a component mutates the real page during render, it bypasses React's memory tracking and creates duplicate elements or broken UI."* (3 sentences, 56 words)
- **Principle 3 (JSX Tags vs Direct Function Calls)**:
  > *"Mount components using JSX tags like `<ArticleCard />` rather than calling them directly as JavaScript functions. A JSX tag tells React to create an independent record in memory to manage the component's lifecycle and hooks. Calling the function directly strips that identity and dumps raw markup into the parent, breaking state tracking."* (3 sentences, 53 words)
