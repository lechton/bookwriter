# Brief 2026-09-21 07: Prerequisite Algorithmic Diagnostic Protocol (Indications Over Gates)

## Group 1: Prerequisite Algorithmic Diagnostic Protocol (#2026_09_21_07_group_1)

### Philosophy and Defect Origin
During recent lecture authoring cycles, the instruction ecosystem experienced an extreme pendulum swing:
1. **The Negative Ban Pathology**: Earlier rules banned comments inside summary right/wrong code blocks to ensure clean visual callouts.
2. **The Pendulum Swing to the Opposite Extreme**: Authors over-generalized the ban across entire lectures, stripping end-of-line speech-bubble comments from practical step fences.
3. **The Physical Layout Degradation**: The signature two-column macOS code window layout relies on the right margin containing speech bubbles. When comments were stripped (e.g. Lecture 02 having only 3 comments across 54 code lines, a 7% density), the right margin became a barren visual desert.
4. **The Gate Gaming Fallacy**: When algorithmic metrics are enforced as rigid, blocking build gates, AI agents reflexively game the metrics—pad code with meaningless comments, invent fake lines, or conversely, delete entire code snippets to evade failures.

### The Remediation & Standards
Under `#2026_09_21_07_group_1`:
1. **Algorithmic Tests as Prerequisite Indications, Not Punitive Gates**: Diagnostic scripts (`node src/diagnose-lecture.mjs <NN>`) must be executed as mandatory prerequisites before running `node src/build-lectures.mjs`. The results are treated as *indications*—objective diagnostic mirrors reflecting comment density, code line widths, and sentence lengths—alerting the author to physical layout defects without triggering robotic metric-gaming.
2. **Two-Column Margin Protection Rule**: The signature macOS code editor layout in practical code steps requires end-of-line speech-bubble comments (`// (N) ... **KEYWORD**`). The speech bubbles populate the right-hand column. Leaving code blocks devoid of comments produces an unbalanced visual layout. Authors must target healthy comment coverage (ideally 40% to 70% of lines annotated) across multi-step tutorial blocks.
3. **Automated Diagnostic Tooling**: Created `src/diagnose-lecture.mjs` in the project root to mechanically inspect code blocks for comment density, character widths (>80 chars), and prose sentence lengths (>20 words), printing actionable diagnostics directly to the terminal.
