# Decision Brief 2026_09_25_04: Tangible Developer-at-the-Keyboard Grounding

## Context & Problem
During the production authoring of Lesson 01 (Declarative UI and the Component Model), the opening paragraph of Section 1 defaulted to a cold, academic textbook tone:
> "In standard browser scripting, we manipulate interface nodes with imperative queries. To update a user's name on The National Times, a script must locate every matching HTML tag..."

While technically accurate, this style fails the core pedagogical contract:
1. **Premature Abstraction**: It opens on textbook terminology (*"standard browser scripting"*, *"imperative queries"*, *"external mutable database"*) before showing any code or tangible screen elements.
2. **Disembodied Observer Voice**: It removes the human engineer from the screen, describing what *"a script must do"* rather than what the developer types, sees, and experiences.
3. **Missing Tangible Anchors**: It refers vaguely to *"every matching HTML tag"* instead of naming actual tags and attributes (`<span id="user-greeting">Guest</span>`).

## The Golden Rule of De-Prescription Applied
Rather than layering rigid prohibitions (*"never write about scripts"*, *"never use the word imperative in paragraph 1"*), we refined the existing core stance standard in `skills/v6.2/lecture-voice/SKILL.md` under `## Stance | 01 | The Developer-at-the-Keyboard Stance`:
- Added evaluative checklist questions verifying that Section 1 opens by anchoring in familiar developer muscle memory and concrete markup before introducing architectural terms.
- Added explicit evaluative checks requiring active second-person developer perspective (*"you reach into the browser using document.getElementById"*) rather than third-person passive descriptions (*"a script must locate/check"*).
- Enshrined the exact Counter-Example and Proper-Example with explanatory pedagogical notes into `lecture-voice/SKILL.md`.

## Quality Standard Established
All baseline problem sections must open by anchoring in familiar developer experience and concrete markup. The text must speak directly from the developer at the keyboard, naming specific elements and selectors before analyzing architectural trade-offs.
