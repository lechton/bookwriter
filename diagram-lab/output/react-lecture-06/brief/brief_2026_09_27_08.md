# Architectural Decision Brief — 2026-09-27-08: Lessons That Share Material

**Status**: Proposal. No skill, map, pre-lecture, or lecture has been changed yet. The edits in Section 5 will carry the tag `#2026_09_27_08_group_1`. The registry row in `skills/v6.3/RULE-TAGS.md` and an "Applied" section in this brief will be written together with the edits.

## Summary

Some syllabus cards cover the same or similar material. The principle maps already handle this well on paper. Every map says which lesson owns each piece of material. The other lessons only recall it or mention it in one sentence.

What is missing is follow-through. Nobody checks that the owner lesson actually picks up what it was sent. Nobody corrects an earlier map or lecture when a later map says "this was mine". And when two cards claim the same topic equally, the skill does not say who wins.

This brief proposes small edits to existing rules in `map-principles`, one shared list of overlaps, and a one-time cleanup of the overlaps already found.

## 1. The Problem in Plain Words

Each principle map has a candidate ledger. Rows marked `Prerequisite`, `Preview`, or `Deferred` are notes that say "this belongs to lesson X". The notes are good. A note only helps if someone reads it and acts on it.

Today three things can go wrong:

1. A note is sent to a later lesson, but that lesson never reads it. The material falls between two lessons.
2. A later map finds that an earlier lesson teaches its material. It writes this down and ticks the box. The earlier map and its lecture stay unchanged, so the material is taught twice.
3. Two cards both make the same topic their main subject. The routing rule assumes only one card does, so the author has to improvise.

## 2. What Already Works

- Routing by main subject (`skills/v6.3/map-principles/SKILL.md`, Section 03). A decision goes to the lesson whose card is about it, not to the first card that mentions it.
- The ledger dispositions give shared material a clear place. `Prerequisite` means recall it in one line. `Preview` means one sentence that names the owner. `Deferred` means leave it out.
- Each map's Authorized Scope names its neighbors, for example "excludes the event object, propagation, and default actions (Q14)". This is already the per-lesson plan for overlap.
- The downstream skills follow the ledger: `pre-lecture/SKILL.md:24`, `lecture-structure/SKILL.md:51`, `principled-theory/SKILL.md:126`, and `verification/SKILL.md:204-205`.

So the maps do not need new sections, and each lesson does not need its own overlap instructions.

## 3. Evidence From the Current Maps

### 3.1 A conflict that was reported but never fixed

The Q10 map says the numeric-zero `&&` trap belongs to Q10, because the Q10 card's Under the Hood and Code Experiment are about it. It says Q04 should keep only the fact that numbers render as text. Nothing changed afterwards:

- The Q04 map still numbers "Convert Numeric Guards to Booleans Before Using `&&`" as its Principle 6 (`01-01-map-principles/04.md:55`). It is also the only map still in the old format.
- The v6 Q04 pre-lecture teaches the "rogue zero" (`01-01-md-PRE-lectures/v6/04.md:145-160`).
- The v6 Q04 lecture teaches it in full (`01-02-md-LECTURES/v6/04.md:258-330`).
- The Q10 lecture, when it is written, will teach it again.

The Q10 map ticked its gate line "Ownership conflicts with earlier principle maps are reported". Writing the report was enough to pass.

### 3.2 Two cards that claim the same topic

- Q13 and Q14 are near-duplicate cards. They share the Topic Tag `#event_handling`, the Friction, and the Under the Hood.
- Q13's Code Experiment is a callback prop (`onSelect`). Callback props are Q15's Topic Tag (`#callback_props`).
- Q11 and Q61 both name the index-as-key mistake.
- Q12 and Q20 both explain StrictMode's double render.
- Q06 and Q07 both list default values.

The authors solved each case the same sensible way, without a written rule. When the two cards need different parts of the topic, they split it. Otherwise the earlier card owns it and the later card recalls it. For example, Q13 took handler syntax and handler props, Q14 took the event object and propagation, and Q15 was left the inverse-data-flow model.

The risk is that Q15, whose Topic Tag is callback props, ends up with little of its own. Section 03's own counter-example warns about exactly this outcome.

### 3.3 Notes sent forward with no check that they arrive

98 ledger rows point to lessons that have no map yet. Q16 alone is owed 7 of them, from Q06, Q07, Q09, Q10, Q12, Q13, and Q14.

Earlier map authors mostly collected their incoming notes on their own. For example, the Q09 gate lists every item that Q01 sent it. The skill does not ask for this step. Discovery stays map-blind on purpose, so without an explicit step after Discovery an author can miss these notes.

### 3.4 Defects in the syllabus cards themselves

- Q13's Scope Boundary reserves `useState` for "Q14". The useState card is Q16.
- The Q14 map suggests that Q14 needs its own Topic Tag, such as `#event_object_and_propagation`.
- The numbering in `01-01-map/` differs from `questions/questions.md`, where Q14 is `#use_state`.

Maps report these defects. No step decides who fixes the syllabus.

## 4. Options Considered

1. **Business as usual.** No cost now. The duplicates in 3.1 and 3.2 stay, and Q16 and later lessons may miss their notes.
2. **Add new information to every map.** Most of this information is already in the ledger. More notes would not fix the missing follow-through, and all 14 maps would need updating.
3. **Add follow-through steps.** Chosen. It edits a few existing bullets, adds a few short bullets, and creates one shared list. This follows the Golden Rule of De-Prescription: it adjusts rules that already exist instead of adding a new overlap section.

## 5. Proposed Changes

All edits are in `skills/v6.3/map-principles/SKILL.md` unless noted. The current text is quoted so the change can be reviewed and reverted.

### 5.1 A tie-break when two cards claim the same topic (Section 03)

Add after the first bullet (line 40):

> - [ ] When two cards both make a candidate their main subject, is it split by layer when their Code Experiments need different parts of it, and owned by the earlier card when they need the same part, with the later card recalling it as a `Prerequisite`? #2026_09_27_08_group_1
>
> - [ ] When a tie-break leaves a lesson with little of its own subject, is that entered in the overlap list as a syllabus defect, so the card gets revised rather than the map? #2026_09_27_08_group_1
>
> - [ ] PROPER EXAMPLE: Two cards share the topic tag for event handling. One card's Code Experiment wires a handler prop, and the other's stops propagation inside an action toolbar. Handler syntax and handler props go to the first card. The event object, propagation, and default actions go to the second.

Why: this writes down what the authors already do. It reuses the "earliest lesson" fallback that line 42 already applies to candidates no card claims.

### 5.2 Fix conflicts instead of only reporting them (Sections 01 and 03, Completion Gate)

Section 03, line 45. Current:

> When the syllabus routes a decision to this lesson but an earlier principle map already numbers it, is the conflict reported for correction in that earlier map?

Proposed:

> When the syllabus routes a decision to this lesson but an earlier principle map already numbers it, is that earlier map corrected in the same batch, or is the conflict entered as open in the overlap list together with the pre-lectures and lectures built from that map?

Section 01, line 16. Current: "is the conflict reported for correction rather than used to expand or shrink the principle set?" Proposed: "is the conflict entered in the overlap list rather than used to expand or shrink the principle set?"

Completion Gate, line 135. Current: "Ownership conflicts with earlier principle maps are reported." Proposed: "Every ownership conflict with an earlier principle map is corrected in that map or open in the overlap list."

Why: today a tick means "I wrote it down". After the change, a tick means "it is fixed, or it is on the list where someone will see it".

### 5.3 Collect the notes sent to this lesson (Sections 03 and 07, Completion Gate)

New Section 03 bullet:

> - [ ] After Discovery, are the `Preview` and `Deferred` rows that earlier maps address to this lesson collected, and does each one get a row in this ledger or go back to its sender with a reason? #2026_09_27_08_group_1

Section 07, line 149. Current: "does every `Prerequisite`, `Preview`, and `Deferred` row point to the owner lesson that the Section 03 routing rules select?" Proposed: add "and, where the owner lesson's map exists, does that map carry a row for it?"

New Completion Gate line: "Every `Preview` and `Deferred` row that an earlier map addresses to this lesson has a row in this ledger."

Why: the notes get read. Discovery stays map-blind, because the collection happens after Discovery ends.

### 5.4 One shared overlap list (new file)

Create `01-01-map-principles/overlaps.md` and add its format to the Output Contract (Section 06):

```markdown
# Overlap List
| lessons | shared material | decision | status | files to fix |
|---|---|---|---|---|
| {Q numbers} | {the shared decision or topic} | {which lesson owns what} | {open or fixed} | {maps, syllabus cards, pre-lectures, and lectures that must change} |
```

A row becomes `fixed` when every file in its last column matches the decision. Why: overlaps are now scattered across 14 gate lines. One list shows every open item in one place.

## 6. One Decision Needed

Who fixes a syllabus card in `01-01-map/` when a map finds a defect in it?

- **A.** The map author fixes the card in the same batch and notes the change in the overlap list.
- **B.** The map author enters the defect in the overlap list, and the user approves each syllabus change.

Recommendation: B. The syllabus decides ownership for every map, so one unreviewed change can move material across many lessons.
