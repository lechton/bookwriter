# Q90: Typing Events and SyntheticEvents in TypeScript
* **Topic Tag**: `#typescript_events` | `❱❱❱ ADVANCED`
* **Interview Question**: *How do you type event handlers and SyntheticEvents in TypeScript?*
* **Core Truth**: React provides generic SyntheticEvent types (`React.MouseEvent<HTMLButtonElement>`, `React.ChangeEvent<HTMLInputElement>`) that strictly enforce type safety on event targets, current targets, and event-specific properties.
* **The Friction**: An engineer writes a standalone `handleChange` function for a search input: `const handleChange = (e: any) => { console.log(e.target.value); }`. Using `any` silences TypeScript but loses autocomplete, misses misspelled properties, and risks runtime errors when accessing element-specific attributes like `e.currentTarget.checked`.
* **The Mechanism**: Typed event handlers: pass generic HTML element types to React event definitions (`React.ChangeEvent<HTMLInputElement>`, `React.FormEvent<HTMLFormElement>`, `React.KeyboardEvent<HTMLTextAreaElement>`), or type handler props directly using `React.ChangeEventHandler<HTMLInputElement>`.
* **Under the Hood**: `e.target` vs `e.currentTarget` typing in TypeScript: `e.target` is the DOM element that originally dispatched the event (typed as generic `EventTarget`), while `e.currentTarget` is the specific DOM element to which the React listener is attached (typed with the exact generic element type `HTMLInputElement`).
* **The Code Experiment**:
  * *Naive*: Typing event parameters as `e: any` or `e: Event` (native browser event), which causes TypeScript errors when accessing `e.target.value`.
  * *React*: An `ArticleSearchToolbar` with strictly typed `handleInput: (e: React.ChangeEvent<HTMLInputElement>) => void` and `handleSubmit: (e: React.FormEvent<HTMLFormElement>) => void`.
* **Scope Boundary**: Focus on typing event parameters, SyntheticEvent generics, and `target` vs `currentTarget`. Do not cover custom event emitter typing.
