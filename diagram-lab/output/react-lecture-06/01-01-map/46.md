# Q46: The Rules of Hooks
* **Topic Tag**: `#rules_of_hooks` | `❱❱ MORE`
* **Interview Question**: *Why must hooks be called at the top level, and only from React functions?*
* **Core Truth**: React relies on stable call order to associate hook calls with their corresponding internal fiber cells; calling hooks conditionally, in loops, or in nested functions corrupts the hook pointer index and crashes the component.
* **The Friction**: A developer writes `if (isSubscriber) { const [badge, setBadge] = useState('VIP'); }`. When `isSubscriber` changes from `true` to `false`, the second render executes one fewer hook. React mismatches subsequent hooks, assigning the badge setter to an unrelated state variable, causing catastrophic state corruption and the error "Rendered fewer hooks than expected".
* **The Mechanism**: The Two Rules of Hooks: (1) Only call hooks at the top level (never inside loops, conditions, or nested functions); (2) Only call hooks from React function components or custom hooks.
* **Under the Hood**: The Fiber hook linked list: React stores a component's hooks in a singly linked list on `fiber.memoizedState`; during re-render, React walks a pointer through this list in the exact order hooks are executed. Any deviation in call order causes the pointer to read the wrong hook data.
* **The Code Experiment**:
  * *Naive*: Putting `useState` or `useEffect` inside an `if` block, triggering runtime crashes when the condition flips between renders.
  * *React*: Refactoring conditional logic so hooks remain unconditionally at the top level, moving conditions *inside* the hook or splitting into conditional sub-components.
* **Scope Boundary**: Focus strictly on the two rules of hooks, the internal linked-list call-order mechanism, and how to refactor illegal hook calls. Do not cover the React Compiler's automatic rule validation yet (Q63).
