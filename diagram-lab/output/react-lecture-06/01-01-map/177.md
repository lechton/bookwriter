# Q177: Legacy renderToStaticMarkup vs renderToString
* **Topic Tag**: #legacy_static_markup | LEGACY (Server)
* **Interview Question**: *What did renderToStaticMarkup do, and how did it differ from renderToString?*
* **Core Truth**: renderToStaticMarkup generated clean, minimal HTML strings without React's hydration markers or checksums, making it lighter for non-interactive content like emails and blogs, but entirely un-hydratable by ReactDOM in the browser.
* **The Friction**: A developer at The National Times used `renderToStaticMarkup` to render an interactive news quiz page to save bytes; when the client tried to hydrate with `hydrateRoot`, React could not match the DOM nodes, throwing warnings and completely wiping and re-rendering the DOM from scratch.
* **The Mechanism**: ReactDOMServer.renderToStaticMarkup(element): synchronously renders a React element tree to pure HTML without `data-reactroot` attributes or internal hydration comment markers (like `<!-- -->` for text separators); in React 19, `prerender` and `renderToPipeableStream` replace it for modern static and streaming pipelines.
* **Under the Hood**: Omission of hydration metadata: historically, `renderToString` inserted `data-reactroot` and text-separator comments so `ReactDOM.hydrate` could align virtual DOM nodes with existing server DOM; `renderToStaticMarkup` deliberately stripped all metadata, producing raw HTML that saves bytes but makes DOM tree reconciliation impossible without a full client-side remount.
* **The Code Experiment**:
  * *Naive*: Generating the HTML for an interactive story page with `renderToStaticMarkup`, causing client-side hydration to fail completely and trigger a jarring full-page DOM wipe and re-render.
  * *React*: Using `renderToStaticMarkup` strictly for static RSS feeds, sitemaps, and email templates where no client JavaScript runs, while using `renderToPipeableStream` with `hydrateRoot` for interactive web pages.
* **Scope Boundary**: Do not cover modern `prerender` or `prerenderToNodeStream` APIs (covered in Q123); focus strictly on the historical mechanics of `renderToStaticMarkup`, how it differs from `renderToString` (absence of hydration metadata), and why it cannot be hydrated.
