# Q38: Lifecycle of Reactive Effects
* **Topic Tag**: `#effect_lifecycle` | `❱ CORE`
* **Interview Question**: *What is the lifecycle of a reactive effect as its dependencies change?*
* **Core Truth**: Unlike components which mount and unmount once, an effect represents a continuous cycle of starting synchronization (setup) and stopping synchronization (cleanup) whenever its reactive dependencies change.
* **The Friction**: A developer connects to a live chat room: `useEffect(() => { connectToRoom(roomId); }, [roomId])`. When the user switches from `roomId = 'news'` to `roomId = 'sports'`, the developer expects the component to keep running, but fails to provide a cleanup. The connection to `'news'` stays open in the background, cross-posting messages and leaking memory.
* **The Mechanism**: The reactive synchronization loop: when dependencies change, React first runs the previous render's cleanup function with the old values, then runs the setup function with the new values. On unmount, React runs the final cleanup.
* **Under the Hood**: Dependency tracking and closure values: why React insists that every reactive value (props, state, variables declared in the component body) used inside the effect must appear in the dependency array; omitting dependencies traps stale closures that reference outdated state snapshots.
* **The Code Experiment**:
  * *Naive*: Omitting `roomId` from the dependency array to "prevent re-running the effect", leaving the socket stuck on the initial room forever.
  * *React*: A `LiveRoomConnection` effect with `[roomId]` dependencies and a returned `disconnect()` cleanup, logging the exact setup-cleanup-setup execution rhythm as `roomId` changes.
* **Scope Boundary**: Focus on the setup-cleanup lifecycle, dependency array contracts, and the mental model of synchronization over time. Do not introduce `useEffectEvent` (Q48) or layout effects (Q49).
