# Q142: Resuming APIs: resume, resumeToPipeableStream, and resumeAndPrerender
* **Topic Tag**: #resume | ❱❱ MORE (Server)
* **Interview Question**: *When do you use resume, resumeToPipeableStream, and resumeAndPrerender?*
* **Core Truth**: React 19's resuming APIs allow servers to save the intermediate execution state of suspended component trees and resume rendering later—either streaming remaining chunks to Web/Node streams or completing static prerenders without restarting from the root.
* **The Friction**: The National Times operates a live election night blog that updates in sporadic bursts; re-rendering the 5,000-word historical timeline from scratch on every new incoming update strains server CPU; developers need a way to freeze the rendered shell and resume streaming only the new update chunks.
* **The Mechanism**: The 3 resume APIs: (1) resume(jsx, postponedState, options): resumes streaming to a Web ReadableStream; (2) resumeToPipeableStream(jsx, postponedState, options): resumes streaming to a Node.js writable stream; (3) resumeAndPrerender(...): completes a postponed static prerender once deferred data arrives.
* **Under the Hood**: Postponed state serialization: during an initial prerender, React can "postpone" dynamic holes (e.g. user session, live poll counts) and serialize the partially evaluated Fiber tree into an opaque postponedState blob; the resume APIs deserialize this state and pick up execution exactly at the suspended holes.
* **The Code Experiment**:
  * *Naive*: Re-rendering an entire massive editorial live-blog tree from root on every new breaking update, burning server CPU on static content.
  * *React*: Freezing the static shell into postponedState and using resumeToPipeableStream to stream only the dynamic election updates when polls close.
* **Scope Boundary**: Focus on when and how to use resume, resumeToPipeableStream, and resumeAndPrerender. Contrast with standard streaming.
