### The Purity Contract and the StrictMode Double-Render

- [p] ◇ In computer science, a pure function is a mathematical formula: given the same inputs, it always returns the exact same result, and it changes nothing outside of its own function body. React is designed entirely around this concept. Every React component you write must be a pure function. When React calls your component, the component should only calculate and return JSX describing what the screen should look like. It must never reach outside its own boundaries to mutate pre-existing variables, modify incoming props, or trigger side effects during the render pass. ◼ Educational objective: establish the mathematical purity contract of React components.
- [p] ★ {preknowledge: JavaScript scope, shared variables, render cycles} {bridging: developers mutate variables outside render, causing state drift and double-counting} When developers violate the purity contract by mutating external variables, silent bugs explode across their application. Look at the naive attempt: ◼ Educational objective: demonstrate the external variable mutation anti-pattern.
- [code] Naive Impure Component:
```jsx title="Naive Impure Component and External Mutation"
let guestViews = 0; // External variable

export default function StoryByline({ author }) {
  guestViews = guestViews + 1; // Mutates outside render
  return (
    <div>
      <span>By {author}</span>
      <small>Views: {guestViews}</small>
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `let guestViews`: shared external module state. 2. `guestViews + 1`: render-phase side effect. 3. Double-counting bug under StrictMode.
- [p] ★ {preknowledge: React StrictMode, concurrent rendering, idempotence} {bridging: StrictMode double-renders in development to catch impure render-time mutations} In development, React wraps your application in `<StrictMode>`. One of StrictMode's primary duties is to verify component purity by calling every component function twice! For a pure component, running the function twice produces the exact same JSX with zero side effects. But for our impure `StoryByline`, running the function twice increments `guestViews` from 0 to 1, and then immediately from 1 to 2. The counter doubles on every single page load! In production, concurrent rendering can pause, abort, and restart rendering at any moment. If your component is not pure, these restarts corrupt application data. ◼ Educational objective: explain how StrictMode double-rendering exposes render-phase mutations.
- [figure] ```html-figure src="figures/12-00-purity-contract-mutation-trap.html" caption="The Purity Contract: contrasting impure external mutations against pure mathematical functions."```
- [grounding] [!WILD] **Why does StrictMode render your component twice?** When developers first see `console.log()` or counters firing twice in development, they often assume React has a bug. In reality, React's `<StrictMode>` intentionally calls your component functions, initializers, and reducers twice in development. Why? Because React is testing your code for purity! If a component is pure, calling it twice produces no observable side effects; the output is identical. But if a component mutates an external variable or modifies a prop array, the second run produces different results, exposing the bug immediately in development before it causes corrupted state in production.
- [callout] > [!TIP]
> **To impress the interviewer:** When asked what component purity means, state that React components must be **idempotent**: given the same inputs (props, state, and context), they must always return the exact same JSX, producing zero mutations outside their render phase. Emphasize that StrictMode double-rendering exists specifically to detect side effects during the render phase, and explain that side effects belong exclusively in event handlers or lifecycle effects.

### Principles of React: The Core Laws of Component Purity and Idempotence

- [p] ◇ To prepare for senior technical interviews, we must separate imperative scripting habits from React's functional architecture and establish the five fundamental laws governing how components maintain purity, handle derivations, and isolate side effects. In React, component execution is governed by functional idempotence and immutability. We formalize these rules into five standalone principles. ◼ Educational objective: establish the necessity of principled component purity for senior interviews.
- [principle] Principle 1: Components Must Be Pure Functions with Deterministic Outputs
> [!PRINCIPLE]
> **Principle 1: Components Must Be Pure Functions with Deterministic Outputs**
> You must write every component as a **pure mathematical function**: given the exact same props and state, it must always return identical JSX without modifying external state.
> 
> >> mathematical purity : a function where the output is strictly determined by inputs with zero outside changes
> >> deterministic execution : running a component multiple times produces identical DOM descriptors every pass
> 
> *It is best practice to do this:*
> `export default function Card({ title }) {`
> `  return <h2>{title}</h2>;`
> `}`
> 
> *Instead of doing this:*
> `let counter = 0;`
> `export default function Card({ title }) {`
> `  counter++;`
> `  return <h2>{title} ({counter})</h2>;`
> `}`
- [p] ★ {preknowledge: pure functions, deterministic calculations} {bridging: pure components enable concurrent rendering, memoization, and safe pre-rendering} When a component is pure, React can invoke it at any time, cache its results with memoization, or execute it in parallel on server runtimes without risk of state corruption. ◼ Educational objective: deconstruct Principle 1.
- [principle] Principle 2: Never Mutate Variables Outside the Component Render Scope
> [!PRINCIPLE]
> **Principle 2: Never Mutate Variables Outside the Component Render Scope**
> You must never mutate variables, objects, or arrays that existed **before the render pass started**, including module-level variables and global objects.
> 
> >> external variable mutation : reassigning or pushing to variables defined outside the component function
> >> render scope isolation : confining all write operations strictly to variables declared within the current execution
> 
> *It is best practice to do this:*
> `export default function Byline({ author }) {`
> `  return <span>By {author}</span>;`
> `}`
> 
> *Instead of doing this:*
> `let globalViews = 0;`
> `export default function Byline({ author }) {`
> `  globalViews += 1;`
> `  return <span>Views: {globalViews}</span>;`
> `}`
- [p] ★ {preknowledge: JavaScript scope chains, shared state bugs} {bridging: external mutations leak across components and cause race conditions} Mutating variables outside the component creates hidden dependencies between unrelated parts of the application. In concurrent React, background renders can cause external counters to increment multiple times, corrupting shared data. ◼ Educational objective: deconstruct Principle 2.
- [principle] Principle 3: Treat All Incoming Props as Strictly Read-Only and Immutable
> [!PRINCIPLE]
> **Principle 3: Treat All Incoming Props as Strictly Read-Only and Immutable**
> You must treat props as **strictly read-only**, never invoking mutating methods like `.push()`, `.sort()`, or `.splice()` on incoming prop arrays or objects.
> 
> >> prop immutability : contract that component props must never be altered by the receiving component
> >> mutating array methods : JavaScript methods like sort and push that alter the underlying array in place
> 
> *It is best practice to do this:*
> `// Copy before sorting`
> `const sorted = [...tags].sort();`
> 
> *Instead of doing this:*
> `// Mutates parent array in place`
> `tags.sort();`
- [p] ★ {preknowledge: JavaScript object references, props contract} {bridging: in-place prop mutation corrupts data owned by parent components and siblings} Props are passed by reference in JavaScript. Calling `.sort()` or `.push()` directly on a prop array alters the parent's data store in place, causing unpredictable glitches across all sibling components that share the same data. ◼ Educational objective: deconstruct Principle 3.
- [principle] Principle 4: Local Mutation Created During the Current Render Is Fully Permitted
> [!PRINCIPLE]
> **Principle 4: Local Mutation Created During the Current Render Is Fully Permitted**
> You are completely permitted to mutate variables, arrays, and objects that you **created locally** within the component function during the current render pass.
> 
> >> local mutation : modifying newly instantiated objects that have no external references
> >> temporary rendering scratchpad : using local variables to assemble markup or calculate derived data cleanly
> 
> *It is best practice to do this:*
> `const localList = [];`
> `for (let i = 0; i < count; i++) {`
> `  localList.push(<span key={i} />);`
> `}`
> `return <div>{localList}</div>;`
> 
> *Instead of doing this:*
> `// Mutating shared external array`
> `sharedList.push(<span />);`
> `return <div>{sharedList}</div>;`
- [p] ★ {preknowledge: local variable lifecycle, memory allocation} {bridging: local variables exist only for the duration of the function call and cannot cause side effects} Mutating objects created inside the render pass does not violate purity because no outside code holds a reference to them. The mutation is localized and produces zero observable side effects. ◼ Educational objective: deconstruct Principle 4.
- [principle] Principle 5: Confine Side Effects to Event Handlers and Lifecycle Effects
> [!PRINCIPLE]
> **Principle 5: Confine Side Effects to Event Handlers and Lifecycle Effects**
> You must quarantine all side effects (such as network requests, DOM mutations, timers, and storage writes) inside **event handlers** or lifecycle effects, never in the render body.
> 
> >> side effect quarantine : isolating external mutations to dedicated response phases outside render
> >> event handler response : user-triggered actions that execute after rendering completes
> 
> *It is best practice to do this:*
> `function handleClick() {`
> `  // Side effect runs on click`
> `  updateDatabase(item.id);`
> `}`
> `return <button onClick={handleClick} />;`
> 
> *Instead of doing this:*
> `// Side effect runs during render`
> `updateDatabase(item.id);`
> `return <button />;`
- [p] ★ {preknowledge: render phase vs commit phase, browser events} {bridging: render calculations must remain pure, while effects execute in response to user actions or lifecycle events} The render pass is purely for calculating what the screen should look like. Any action that alters external systems belongs in event handlers (like button clicks) where user intent is explicit and render idempotence is preserved. ◼ Educational objective: deconstruct Principle 5.
