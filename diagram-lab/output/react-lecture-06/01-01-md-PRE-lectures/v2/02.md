### Lowercase Tags and Silent Disappearances

- [p] ◇ In standard HTML, browsers recognize dozens of built-in tags like `<article>`, `<header>`, and `<p>`. These tags are defined by web standards. When a browser sees a lowercase tag name, it creates a native DOM element in memory. If the tag name is unknown, the browser still creates an empty HTML element. It does not throw an error. It simply paints nothing on the screen. ◼ Educational objective: establish how browsers handle lowercase HTML tags and explain why unknown elements fail silently.
- [p] ★ {preknowledge: JavaScript functions, HTML elements, JSX tags} {bridging: developers assume that any function returning markup can be used as a JSX tag, but lowercase tags bypass the function completely} When Marcus writes a function named `articleCard` and places `<articleCard />` in his JSX, he expects React to run his code. Look at the naive lowercase attempt: ◼ Educational objective: demonstrate the silent failure caused by lowercase component naming.
- [code] Naive Lowercase Component:
```jsx title="Naive Lowercase Tag"
function articleCard() {
  return (<article><h2>Breaking News</h2></article>);
}

export default function App() {
  return (<articleCard />); // **WRONG:** compiles to native string, bypassing **FUNCTION**
}
```
◼ **The what-this-introduces list:** 1. `function articleCard`: lowercase function declaration. 2. `<articleCard />`: lowercase JSX element tag. 3. `App`: parent component mounting the tag. 4. Silent failure: no build error, but the function never runs.
- [p] ★ {preknowledge: JSX compilation, abstract syntax trees, function references} {bridging: the failure happens because the JSX compiler uses capitalization to decide between a string literal and a function identifier} The JSX compiler does not inspect your JavaScript scope to see if a function exists. Instead, it inspects the first letter of the tag name. If the tag begins with a lowercase letter, the compiler emits a string literal: `_jsx("articlecard")`. React receives this string and calls `document.createElement("articlecard")`. The browser creates an empty native DOM node. Your custom function `articleCard()` is completely ignored. ◼ Educational objective: deconstruct the AST compiler branch that routes lowercase tags to string literals.
- [figure] ```html-figure src="figures/02-00-ast-tag-routing.html" caption="The JSX compiler AST branch: lowercase tags compile to string literals, while capitalized tags compile to function references."```
- [grounding] [!WILD] **Why does a lowercase component fail silently?** The JSX compiler follows a strict syntactic rule. When the tag starts with a lowercase letter, the transpiler generates `_jsx("tagname")`. The browser treats this as an unknown custom element. It creates an empty HTML element without styling or content. The terminal reports a successful build because the syntax is valid JavaScript. The browser console stays empty because unknown HTML tags are permitted by the HTML specification. To tell the compiler that your tag represents a JavaScript function, you must capitalize the first letter: `<ArticleCard />`.
- [callout] > [!TIP]
> **To impress the interviewer:** When asked why React requires PascalCase for components, explain the compiler mechanism. JSX is transpiled into function calls like `_jsx()`. The transpiler uses the first letter to decide whether to pass a string literal (`"div"`) or a direct function identifier (`ArticleCard`). Lowercase tags always become strings, bypassing your component function entirely.

### Component Anatomy and Declarative Invocation

- [p] ◇ A React **component** is a pure JavaScript function that returns user interface markup. It is the fundamental unit of composition in React applications. Every component must satisfy two non-negotiable rules. First, its name must start with an uppercase letter using **PascalCase**. Second, it must return valid JSX markup or null. ◼ Educational objective: define the core anatomy and return contract of a React component.
- [p] ★ {preknowledge: function declarations, return statements, JSX elements} {bridging: developers often wonder whether they can invoke a component directly as a regular JavaScript function or if they must use JSX tags} When mounting a component inside another component, you face an architectural fork between two invocation patterns: ◼ Educational objective: introduce the pedagogical crossroads between imperative function calls and declarative JSX.
- [p] - **Option 1 (The foundational way)**: Call the component directly as a plain JavaScript function (`ArticleCard()`). ◼ Educational objective: declare Option 1 with concrete syntax tokens.
- [p] - **Option 2 (The modern idiomatic way)**: Declare the component as a JSX element tag (`<ArticleCard />`). ◼ Educational objective: declare Option 2 with concrete syntax tokens.
- [p] First, look at Option 1 calling the component imperatively as a function: ◼ Educational objective: transition to Option 1 code.
- [code] Option 1:
```jsx title="Option 1: The Foundational Way (ArticleCard())"
export default function App() {
  return (
    <main>
      {ArticleCard()} // Executes function directly via **PARENTHESES**
    </main>
  );
}
```
◼ **The what-this-introduces list:** 1. `ArticleCard()`: direct imperative function execution. 2. `{}`: expression evaluation window inside JSX. 3. Bypassed component boundary: React treats the returned elements as direct children of App.
- [p] ★ In Option 1, JavaScript executes `ArticleCard()` immediately during render. The function returns its JSX elements, and they appear on the screen. However, React does not see `ArticleCard` as a distinct component node. In the React DevTools tree, `ArticleCard` does not exist. React cannot manage its lifecycle independently, and future features like hooks will fail. ◼ Educational objective: explain the engine consequences and limitations of imperative component execution.
- [p] Next, look at Option 2 declaring the component as a JSX element: ◼ Educational objective: transition to Option 2 code.
- [code] Option 2:
```jsx title="Option 2: The Modern Idiomatic Way (<ArticleCard />)"
export default function App() {
  return (
    <main>
      <ArticleCard /> // Declares component boundary via **JSX TAG**
    </main>
  );
}
```
◼ **The what-this-introduces list:** 1. `<ArticleCard />`: declarative JSX element tag. 2. Self-closing syntax: clean termination for elements without children. 3. First-class component node: React registers the component in its render tree.
- [p] ★ In Option 2, the compiler transforms `<ArticleCard />` into `_jsx(ArticleCard, {})`. You do not execute the function yourself. You pass the function reference to React. React decides when to call `ArticleCard()`, mounts it as an independent node in the component tree, and displays it in React DevTools. This declarative invocation is the cornerstone of React's component model. ◼ Educational objective: analyze how declarative invocation enables React to manage component lifecycles.
- [callout] > [!KEY]
> Always name React components using PascalCase and invoke them declaratively with JSX tags (`<ArticleCard />`). Never call component functions directly with parentheses (`ArticleCard()`).

### Principles of React: The Core Laws of Component Anatomy and Invocation

- [principle] **Principle 1: Always Capitalize Component Names Using PascalCase**
You must name every React component using **PascalCase** (starting with an uppercase letter), so the compiler routes the tag to your custom JavaScript function rather than a native HTML element string.
*We should do this:*
`<ArticleCard />`
// Transpiles to _jsx(ArticleCard, {})
*We should not do this:*
`<articleCard />`
// Transpiles to _jsx('articlecard', {})
- [p] In senior technical interviews, explaining why React requires PascalCase requires dissecting the compiler's Abstract Syntax Tree (AST) tag name evaluation:
- [p] 1. **The Lowercase Tag Pathway (Native HTML String Literal):** If the tag begins with a lowercase character (`/^[a-z]/`), the JSX compiler assumes it represents a built-in browser host element. It emits a string literal: `_jsx("articlecard", {})`. At runtime, React passes this raw string to `document.createElement("articlecard")`. Because `"articlecard"` is not a standard HTML element, the browser instantiates an empty `HTMLUnknownElement`, ignoring your JavaScript function completely and painting a blank node.
- [p] 2. **The Uppercase Tag Pathway (Component Function Identifier):** If the tag begins with an uppercase character (`/^[A-Z]/`) or contains a dot (`Article.Card`), the JSX compiler treats it as an in-scope JavaScript variable. It emits the variable identifier directly: `_jsx(ArticleCard, {})`. At runtime, React receives a direct function reference, invokes `ArticleCard(props)` in memory, and mounts its rendered tree.
- [code] Principle 1:
```jsx title="Principle 1: PascalCase Identifier Routing"
// **WRONG:** Lowercase tag compiles to native HTML string
function articleCard() { return (<article>News</article>); }
const el = <articleCard />; // Blank HTMLUnknownElement

// **RIGHT:** Capitalized tag compiles to custom function
function ArticleCard() { return (<article>News</article>); }
const el = <ArticleCard />; // Executes component function
```

- [principle] **Principle 2: Invoke Components Declaratively with JSX Tags Rather Than Function Parentheses**
You must invoke components declaratively using **JSX tags** (`<ArticleCard />`), never calling the component function directly with parentheses (`ArticleCard()`).
*It is best practice to do this:*
`<ArticleCard />`
// Preserves component boundary and hooks
*Instead of doing this:*
`{ArticleCard()}`
// Bypasses React lifecycle and DevTools tree
- [p] To understand why calling a component with parentheses breaks your architecture in production, senior engineers analyze three runtime consequences:
- [p] 1. **Fiber Node Boundary and Lifecycle:** Writing `<ArticleCard />` instructs React to create a dedicated Fiber node in the virtual DOM tree. React controls when to mount, reconcile, re-render, or unmount this instance independently. Calling `ArticleCard()` directly bypasses Fiber creation: it immediately executes the function during the parent's render phase and splices the returned JSX into the parent's children.
- [p] 2. **React Hooks State Allocation:** React tracks hooks by associating an internal linked list of hook records with the currently rendering Fiber node. Calling `ArticleCard()` directly inside a parent component binds `ArticleCard`'s internal hooks to the parent's Fiber, risking hook order corruption and runtime crashes.
- [p] 3. **DevTools Hierarchy and Profiling:** React DevTools inspects the Fiber tree. A declarative tag `<ArticleCard />` appears as an inspectable component node displaying its own props, state, and render timings. Calling `{ArticleCard()}` erases the component from DevTools entirely, flattening its elements into the parent.
- [code] Principle 2:
```jsx title="Principle 2: Declarative Tag vs Function Call"
// **WRONG:** Direct function call flattens tree and breaks hooks
export default function App() {
  return (<main>{ArticleCard()}</main>);
}

// **RIGHT:** Declarative JSX tag creates independent boundary
export default function App() {
  return (<main><ArticleCard /></main>);
}
```

- [principle] **Principle 3: Always Return Valid JSX Markup or Null from Component Functions**
You must ensure every component return statement evaluates to **valid JSX markup or null**, never returning `undefined` (which halts React rendering).
*We should do this:*
`return (<div>Story</div>);`
// Valid JSX node rendered to UI
*We should not do this:*
`return;`
// Implicit undefined return throws runtime error
- [p] In technical interviews, this return contract is evaluated across three distinct evaluation results:
- [p] 1. **Valid React Nodes (Elements, Primitives, and Portals):** A component may return a JSX element (`<article />`), a React Fragment (`<>...</>`), a string (`"Breaking News"`), a number (`42`), or an array of elements. React reconciles each of these types into corresponding DOM nodes or text nodes.
- [p] 2. **The Intentional Zero-Node Render (`null`):** Returning `null` is the official, intentional mechanism for conditional rendering when a component should display nothing. React keeps the component cleanly mounted in the Fiber tree, retains its hook state, and renders zero DOM nodes.
- [p] 3. **The Unintentional Crash (`undefined`):** In JavaScript, a function without an explicit `return` statement or with a bare `return;` automatically evaluates to `undefined`. In React, returning `undefined` is treated as a developer bug (such as forgetting a return statement inside a conditional guard). React throws an immediate fatal error.
- [code] Principle 3:
```jsx title="Principle 3: Component Return Contract"
// **WRONG:** Falling through without return produces undefined
function EditorialBanner({ isVisible }) {
  if (!isVisible) return; // Undefined -> runtime crash!
  return (<aside>Breaking Dispatch</aside>);
}

// **RIGHT:** Return null to intentionally suppress rendering
function EditorialBanner({ isVisible }) {
  if (!isVisible) return null; // Clean zero-node render
  return (<aside>Breaking Dispatch</aside>);
}
```

- [principle] **Principle 4: Keep Component Rendering Pure with Zero Side Effects**
You must author component functions as **pure calculations**, never modifying external variables or querying DOM nodes during render.
>> pure calculations : code that produces the same output for identical inputs without mutating outside state
*We should do this:*
`return (<h2>Headline</h2>);`
// Pure calculation produces deterministic UI
*We should not do this:*
`window.articleCount++;`
`return (<h2>Headline</h2>);`
// Side effect in render causes rendering bugs
- [p] Senior React interviews evaluate purity through three mathematical and architectural guarantees:
- [p] 1. **Mathematical Projection (`UI = f(data)`):** A pure component function is an idempotent calculation. Given identical data, it must return the exact same JSX tree every single time it executes, without depending on external mutable state or time-sensitive calculations (such as `Date.now()` or `Math.random()`).
- [p] 2. **Zero Side Effects in the Render Phase:** A side effect is any operation that modifies state outside the current function execution: mutating a global variable, updating the DOM manually, writing to `localStorage`, or firing network requests. Executing side effects during render violates React's concurrency model, where renders can be aborted, restarted, or paused by the scheduler.
- [p] 3. **The StrictMode Double-Render Verification:** In development mode under `React.StrictMode`, React intentionally executes component functions twice for every render. If a component mutates an external counter (`globalCount++`) during render, the counter increments by two instead of one. This deliberate double-render acts as an automated audit that immediately exposes impure functions.
- [code] Principle 4:
```jsx title="Principle 4: Pure Component Execution Contract"
// **WRONG:** Modifying outside variables during render
let globalCount = 0;
function ArticleCounter() {
  globalCount++; // Mutates external state during render!
  return (<span>Count: {globalCount}</span>);
}

// **RIGHT:** Pure calculation without external mutation
function ArticleCounter() {
  return (<span>Articles Published</span>);
}
```

- [principle] **Principle 5: Declare Component Functions at Top-Level Module Scope, Never Nested Inside Other Components**
You must always define component functions at the **top-level scope** of a module, strictly avoiding nesting component declarations inside the body of another component.
*We should do this:*
`function Byline() {`
`  return (<span>Byline</span>);`
`}`
`function Card() {`
`  return (<Byline />);`
`}`
// Top-level definition preserves identity across renders
*We should not do this:*
`function Card() {`
`  function Byline() {`
`    return (<span>Byline</span>);`
`  }`
`  return (<Byline />);`
`}`
// Nested declaration recreates component type on every render
- [p] In software architecture, understanding why nesting component definitions is catastrophic requires analyzing how React tracks component identity:
- [p] 1. **Function Reference Identity and Remounting:** When a component is declared inside another component's body, JavaScript creates a brand-new function object on every render pass of the parent. Because React compares component types by function reference (`prevType === nextType`), React sees a completely different component type. It destroys the previous DOM subtree, runs unmount cleanup, and remounts from scratch.
- [p] 2. **State and Focus Destruction:** Remounting on every render wipes all local state held by the child, causes active input focus to vanish, cancels CSS transitions, and severely degrades rendering performance. Defining components at top-level module scope guarantees a stable function reference across all renders.
- [code] Principle 5:
```jsx title="Principle 5: Top-Level Definition vs Nested Component"
// **WRONG:** Inner function gets fresh identity every render
function ArticleCard() {
  function Byline() { return (<span>By Marcus</span>); }
  return (<article><Byline /></article>); // Remounts every render!
}

// **RIGHT:** Top-level declaration maintains stable identity
function Byline() { return (<span>By Marcus</span>); }
function ArticleCard() {
  return (<article><Byline /></article>); // Stable node identity
}
```

### Glossary

- [p] - **Component**: A pure JavaScript function that accepts inputs and returns a description of user interface markup as React elements.
- [p] - **PascalCase**: A naming convention where the first letter of each compound word is capitalized (for example, `ArticleCard`), required by React to differentiate custom components from native HTML elements.
- [p] - **Fiber Node**: An internal data structure created by React representing a unit of work and a component instance in the virtual DOM tree.
- [p] - **Declarative Invocation**: Rendering a component by writing its tag name in JSX (`<ArticleCard />`), leaving React to manage instantiation and lifecycle.
- [p] - **Component Identity**: The mechanism by which React determines whether two rendered elements represent the same component instance, based on function reference equality and tree position.

## Beyond the basics

- [p] - **AST tag name transpilation**: Modern JSX transforms compile uppercase tags into `jsx(Component, props)` while lowercase tags compile to `jsx("tag", props)`. This decision is made purely at parse time by inspecting character casing (see [react.dev/learn/your-first-component](https://react.dev/learn/your-first-component)).
- [p] - **Why calling components as functions breaks hooks**: Hooks rely on React's internal current Fiber dispatcher. Calling a component imperatively (`MyComponent()`) executes it within the caller's Fiber context, causing hook order mismatches when conditional branches change (see [react.dev/reference/rules/rules-of-hooks](https://react.dev/reference/rules/rules-of-hooks)).
- [p] - **Top-level declaration and remount prevention**: Declaring a component inside another component re-creates the function on every render pass. Because `prevType !== nextType`, React completely destroys and remounts the child subtree (see [react.dev/learn/preserving-and-resetting-state](https://react.dev/learn/preserving-and-resetting-state)).
