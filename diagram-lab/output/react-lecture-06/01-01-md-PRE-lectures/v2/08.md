### The Monolithic File and the Import Trap

- [p] ◇ In early project stages, developers often place multiple components in a single file for convenience. As an application grows, a monolithic `App.jsx` becomes an unmaintainable bottleneck. Multiple developers editing different widgets inside the same file generate endless merge conflicts. Furthermore, locating bugs in a 1,200-line script slows down the entire engineering team. To build scalable React applications, you must extract each component into its own dedicated ES module file. ◼ Educational objective: establish the friction of monolithic component files.
- [p] ★ {preknowledge: ES module exports, JSX tags} {bridging: developers confuse default and named import syntax, causing silent undefined bindings} When splitting components into separate files, mistyping import syntax causes fatal runtime crashes. Look at the naive attempt: ◼ Educational objective: demonstrate the import mismatch anti-pattern.
- [code] Naive Import Mismatch:
```jsx title="Naive Import Mismatch"
import { ArticleCard } from './ArticleCard.jsx'; // **WRONG:** curly braces search named property on **DEFAULT EXPORT**

export default function App() {
  return (<ArticleCard />); // **WRONG:** crashes with undefined element type **EXCEPTION**
}
```
◼ **The what-this-introduces list:** 1. `import { ArticleCard }`: erroneous named import on a default export. 2. `ArticleCard`: resolves silently to `undefined`. 3. `_jsx(undefined, {})`: fatal runtime error during rendering.
- [p] ★ {preknowledge: module namespace objects, JSX compilation} {bridging: default exports bind to .default, while named imports search named property keys} When a file exports a component using `export default`, the bundler places that function on the `.default` property of the module namespace object. If you write `import { ArticleCard } from './ArticleCard.jsx'`, the JavaScript engine looks for an export literally named `ArticleCard`. Because none exists, `ArticleCard` is assigned `undefined`. When React attempts to render `<ArticleCard />`, it invokes `_jsx(undefined, {})`. React throws a fatal runtime exception: `Error: Element type is invalid: expected a string or a class/function but got: undefined.` ◼ Educational objective: explain the runtime crash caused by mismatched default and named imports.
- [figure] ```html-figure src="figures/08-00-default-vs-named-exports.html" caption="The ES module namespace: default exports bind to .default, while named exports bind to exact identifier keys."```
- [grounding] [!WILD] **Why does an undefined component crash during rendering instead of import?** When developers mix up import syntax, they expect Vite or the browser to throw a syntax error immediately at the import statement. Why does the file load silently, only to explode when React renders? Because in JavaScript ES modules, importing a non-existent named export from a module is legally permitted at syntax level; it simply resolves to undefined. The failure only occurs when React's runtime attempts to evaluate `<ArticleCard />`. React inspects the first argument to `_jsx()` and finds `undefined` instead of a function or DOM string tag, halting with a fatal type error.
- [callout] > [!TIP]
> **To impress the interviewer:** When asked how default and named imports differ, explain that a default export binds to the module's internal `.default` property and is imported without curly braces, while named exports represent specific properties and must be imported with curly braces matching their exact exported names.

### Principles of React: The Core Laws of ES Module Imports

- [p] ◇ To prepare for senior technical interviews, we must separate monolithic scripting habits from React's modular file architecture and establish the five fundamental laws governing how components are split, exported, and imported across ES modules. In React, clean module boundaries enable team parallelization, tree-shaking, and predictable component loading. We formalize these rules into five standalone principles. ◼ Educational objective: establish the necessity of principled module architecture for senior interviews.
- [principle] Principle 1: Isolate Each Reusable Component in Its Own Dedicated Module File
> [!PRINCIPLE]
> **Principle 1: Isolate Each Reusable Component in Its Own Dedicated Module File**
> You must place each primary component in an **independent `.jsx` file**, strictly avoiding monolithic multi-component files.
> 
> >> independent .jsx file : a dedicated file containing a single component and its localized dependencies
> >> monolithic multi-component files : placing dozens of components in one massive script, creating merge conflicts
> 
> *It is best practice to do this:*
> `// src/components/ArticleCard.jsx`
> `export default function ArticleCard() {`
> `  return (`
> `    <article className="card" />`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `// All components inlined in App.jsx`
> `function Card() { return <article />; }`
> `function Feed() { return <Card />; }`
- [p] ★ {preknowledge: ES modules, file organization} {bridging: one-component-per-file architecture enables code reuse and team scalability} Placing multiple components in a single file creates tight coupling and merge bottlenecks. Isolating each component into its own file allows developers to edit, test, and style components independently. ◼ Educational objective: deconstruct Principle 1.
- [principle] Principle 2: Export Primary Components as Default Exports
> [!PRINCIPLE]
> **Principle 2: Export Primary Components as Default Exports**
> You must export the single primary component of a file using **`export default`**, importing it without curly braces under any convenient identifier name.
> 
> >> export default : ES module syntax declaring the main entity of a module
> >> without curly braces : importing the default export directly as an identifier (import Card from './Card.jsx')
> 
> *It is best practice to do this:*
> `export default function ArticleCard() {`
> `  return (`
> `    <article className="card" />`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function ArticleCard() {`
> `  return (`
> `    <article className="card" />`
> `  );`
> `}`
> `window.ArticleCard = ArticleCard;`
- [p] ★ {preknowledge: default export syntax, module binding} {bridging: default exports communicate the primary role of a component module} A component file typically has one primary visual responsibility. Using `export default` designates that component as the primary export, allowing consumers to import it cleanly without worrying about exact name matching. ◼ Educational objective: deconstruct Principle 2.
- [principle] Principle 3: Export Supporting Utilities as Named Exports
> [!PRINCIPLE]
> **Principle 3: Export Supporting Utilities as Named Exports**
> You must export auxiliary helpers, constants, or secondary widgets using **named exports** (`export function formatHeadline()`), importing them with exact curly braces (`{ formatHeadline }`).
> 
> >> named exports : exporting specific variables or functions using export const / export function
> >> exact curly braces : import { helper } requiring an exact name match with the exported identifier
> 
> *It is best practice to do this:*
> `export function formatRole(role) {`
> `  return role.toUpperCase();`
> `}`
> 
> *Instead of doing this:*
> `// Attaching helpers to default object`
> `export default {`
> `  formatRole: (r) => r.toUpperCase()`
> `};`
- [p] ★ {preknowledge: named exports, tree shaking} {bridging: named exports allow bundlers to tree-shake unused functions} Auxiliary functions and constants should be exported as named exports. Named exports enforce exact naming contracts and enable bundlers to drop unreferenced functions during tree-shaking. ◼ Educational objective: deconstruct Principle 3.
- [principle] Principle 4: Never Wrap Default Exports in Import Curly Braces
> [!PRINCIPLE]
> **Principle 4: Never Wrap Default Exports in Import Curly Braces**
> You must import default exports **without curly braces** (`import Card from './Card.jsx'`), because curly braces search for a named property and evaluate to `undefined` on default exports.
> 
> >> without curly braces : binding the default export directly to a local variable
> >> evaluate to undefined : JavaScript failing to find a matching named key on the module namespace
> 
> *We should do this:*
> `import ArticleCard from './Card.jsx';`
> 
> *We should not do this:*
> `// Evaluates to undefined at runtime!`
> `import { ArticleCard } from './Card.jsx';`
- [p] ★ {preknowledge: module namespace, object property lookup} {bridging: curly braces signal named export lookup, not object destructuring} In import statements, curly braces are not destructuring assignment; they are module syntax instructing the engine to look for specific named exports. Wrapping a default export in braces looks for a named export that does not exist, resolving silently to `undefined`. ◼ Educational objective: deconstruct Principle 4.
- [principle] Principle 5: Component Render Fails with TypeError When Importing Undefined
> [!PRINCIPLE]
> **Principle 5: Component Render Fails with TypeError When Importing Undefined**
> You must recognize that importing a mismatched export resolves silently to `undefined`, which crashes React during render with **Element type is invalid**.
> 
> >> resolves silently to undefined : JavaScript allowing missing named imports to evaluate to undefined without early error
> >> Element type is invalid : the fatal runtime error React throws when attempting to render undefined
> 
> *We should do this:*
> `import Card from './Card.jsx';`
> `return (<Card />);`
> 
> *We should not do this:*
> `import { Card } from './Card.jsx';`
> `// Crashes: Element type is invalid!`
> `return (<Card />);`
- [p] ★ {preknowledge: React element creation, _jsx call} {bridging: React requires a string or function as the first argument to createElement} When React encounters `<Component />`, it compiles it to `_jsx(Component, {})`. If `Component` is `undefined` due to an import mismatch, React halts execution with an unhandled exception during rendering, not at import time. ◼ Educational objective: deconstruct Principle 5.
- [callout] > [!KEY]
> Export the primary component as `default` (imported without braces). Export helper functions as `named` (imported with braces). Never wrap a default export in curly braces.

### Step 1: First, we construct the parent container <App.jsx>

- [p] We begin by constructing the top-level application shell in `src/App.jsx`. This component acts as the outer editorial container. It imports `ArticleCard` as a default import without curly braces and mounts it inside the page layout: ◼ Educational objective: construct top-level container with default import.
- [code] App.jsx:
```jsx title="src/App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // Imports default component without **CURLIES**

export default function App() {
  return (
    <div className="editorial-shell">
      <ArticleCard /> // Mounts modular article card at layout **ROOT**
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `import ArticleCard from ...`: default import without curly braces. 2. `<ArticleCard />`: mounting the imported child component. 3. Clean root layout delegated to child files.
- [p] Notice the import syntax: `import ArticleCard from './components/ArticleCard.jsx'`. Because `ArticleCard.jsx` exports its component as `default`, we do not use curly braces. Writing `{ ArticleCard }` here would assign `undefined` and crash the render pass. ◼ Educational objective: emphasize default import syntax without braces.

### Step 2: Next, we extract the primary card component <ArticleCard.jsx>

- [p] Now we create the component file `src/components/ArticleCard.jsx`. This file represents the primary article presentation card. We declare the component and export it as the default export of the module: ◼ Educational objective: declare primary component with default export.
- [code] ArticleCard.jsx:
```jsx title="src/components/ArticleCard.jsx" startLine="1" continues="bottom"
import AuthorBadge, { formatRole } from './AuthorBadge.jsx'; // Combined default and named **IMPORT**

export default function ArticleCard() { // Primary component default **EXPORT**
  const headline = 'Offshore Banking Secrets Exposed';
  const role = formatRole('investigative'); // Calls named utility **FUNCTION**
  return (
    <article className="article-card">
      <span className="desk-tag">{role}</span>
      <h2 className="headline">{headline}</h2>
```
◼ **The what-this-introduces list:** 1. Combined default and named import. 2. `export default function ArticleCard()`: default export. 3. Calling named helper `formatRole()`.
- [p] Notice line 1: `import AuthorBadge, { formatRole } from './AuthorBadge.jsx'`. In a single line, we import the default component `AuthorBadge` without braces, and the named utility `formatRole` with braces. This demonstrates how default and named imports coexist harmoniously. ◼ Educational objective: explain combined default and named import syntax.

### Step 3: Then, we declare the author badge and named helper <AuthorBadge.jsx>

- [p] Next, we create `src/components/AuthorBadge.jsx`. This file exports two entities: a named helper function `formatRole` that formats editorial desk tags, and a default component `AuthorBadge` that renders the reporter's credentials: ◼ Educational objective: declare companion module with both named and default exports.
- [code] AuthorBadge.jsx:
```jsx title="src/components/AuthorBadge.jsx"
export function formatRole(role) { // Named export for string **FORMATTER**
  return role.toUpperCase() + ' DESK';
}
export default function AuthorBadge() { // Default export for badge **COMPONENT**
  return (
    <div className="author-badge">
      <span className="author-name">Clara Foster</span> // Reporter **PROFILE**
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `export function formatRole()`: named function export. 2. `export default function AuthorBadge()`: default component export. 3. Multi-export module pattern.
- [p] Notice that `formatRole` carries `export`, while `AuthorBadge` carries `export default`. The keyword `default` flags `AuthorBadge` as the primary export of the file. Any other export in the file must be a named export. ◼ Educational objective: distinguish export from export default in the same file.

### Step 4: Finally, we mount the child badge inside <ArticleCard.jsx>

- [p] Finally, we complete `src/components/ArticleCard.jsx` by mounting the `<AuthorBadge />` component inside the article card layout and closing the JSX return statement: ◼ Educational objective: finalize component nesting and close JSX return.
- [code] ArticleCard.jsx:
```jsx title="src/components/ArticleCard.jsx" startLine="9" continues="top"
      <AuthorBadge /> // Mounts imported child component at card **BASE**
    </article>
  );
}
```
◼ **The what-this-introduces list:** 1. `<AuthorBadge />`: mounting imported default component. 2. Closed article tag. 3. `continues="top"`: completing component slice.
- [p] Notice how modular our application has become: `App.jsx` imports `ArticleCard.jsx`, which in turn imports `AuthorBadge.jsx` and its helper `formatRole`. Each file has a single clear responsibility, carries its own imports, and can be edited without conflicting with other components. ◼ Educational objective: summarize modular component architecture.

### Glossary

- [glossary] ES Module ◼ A standard JavaScript file format that uses import and export statements to share code across files.
- [glossary] Default Export ◼ An export declared with `export default` representing the primary entity of a module, imported without curly braces.
- [glossary] Named Export ◼ An export declared with `export const` or `export function`, imported with matching curly braces.
- [glossary] Module Namespace ◼ The internal JavaScript object containing all exports of a module, with default exports stored under the `.default` property.
- [glossary] Element Type Is Invalid ◼ The fatal runtime error React throws when a component identifier resolves to `undefined` during rendering.

## Beyond the basics

- **Default vs named export conventions**: Official React documentation recommends sticking to one export style within a codebase or using default exports for components and named exports for utilities (see [react.dev/learn/importing-and-exporting-components#default-vs-named-exports](https://react.dev/learn/importing-and-exporting-components#default-vs-named-exports)).
- **Renaming imports with the as keyword**: You can rename named imports to resolve naming collisions using `import { Button as PrimaryButton } from './Button.jsx'` (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).
- **Exporting multiple named components from an index file**: Barrel files (`index.js`) re-export multiple components via `export * from './Button.jsx'` for convenient package-style imports (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).
- **Dynamic imports with React.lazy**: Code-splitting components across separate network chunks is achieved via dynamic `import()` and `React.lazy()` (see [react.dev/reference/react/lazy](https://react.dev/reference/react/lazy)).
- **Tree-shaking mechanics in modern bundlers**: Bundlers like Rollup and Vite analyze static named exports to eliminate dead code from final production bundles (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Component Isolation & Default Exports

➔ ALWAYS place each primary reusable component in its own dedicated `.jsx` file.

➔ ALWAYS export the primary component using `export default` and import it without curly braces.

➔ NEVER place multiple complex layout components inside a single monolithic file.

❒ Named Exports & Import Correctness

➔ ALWAYS export auxiliary helpers, types, and secondary widgets as named exports (`export function ...`).

➔ ALWAYS import named exports using matching curly braces (`import { helper } from '...'`).

➔ NEVER wrap a default export in curly braces during import, because it evaluates to `undefined` and crashes React at runtime.

**DO THIS:** import default components without curly braces and named helpers with curly braces

```jsx right
import ArticleCard, { formatRole } from './ArticleCard.jsx';

export default function App() {
  return (<ArticleCard />);
}
```

**DO NOT DO THIS:** wrap default exports in curly braces or mix up export styles

```jsx wrong
import { ArticleCard } from './ArticleCard.jsx';

export default function App() {
  return (<ArticleCard />);
}
```

| | **DEFAULT EXPORT**<br>(primary component) | **NAMED EXPORT**<br>(utility / secondary) |
| ---: | :--- | :--- |
| **Export Syntax** | `export default function Card()` | `export function formatText()` |
| **Import Syntax** | `import Card from './Card.jsx'` | `import { formatText } from './Card.jsx'` |
| **Curly Braces** | Strictly forbidden | Mandatory |
| **Module Slot** | Attached to `.default` property | Attached to exact property name |
| **Count Per File** | Exactly one per module | Unlimited per module |
