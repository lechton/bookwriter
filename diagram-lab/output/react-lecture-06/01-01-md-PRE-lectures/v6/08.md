### The Friction of Monolithic Files and Copy-Paste Components

- [p] ★ {preknowledge: component declaration, JSX return contract, parent-child nesting} Think back to how you defined components: you wrote JavaScript functions that return JSX markup describing user interface elements. When building a small prototype, placing several components in a single starter file feels quick and convenient. You define a card component, a header, and a badge all in the same document. But as an application grows, different pages across the site demand access to those same visual building blocks. On The National Times, the front page, the archive section, and the search results all need to render article cards with status badges. ◼ Educational objective: recall component functions and identify the physical limitation of keeping multiple components in one starter file.
- [p] ★ {problem: monolithic files cause git merge conflicts and block clean code reuse} When a team keeps all components inside a single monolithic App.jsx file, the file quickly swells to over a thousand lines of code. Engineers working on different features must constantly edit the exact same document, causing frequent git merge conflicts. Furthermore, another page cannot reuse a single component without importing the entire application shell and all its unrelated layout logic. ◼ Educational objective: expose the operational pain of monolithic component files.
- [p] ★ {old solution: copying and pasting component functions across files} When developers cannot easily import a component from a giant monolithic file, they sometimes fall into the copy-paste trap. A developer may copy the entire card function into a new file, thinking this is faster than restructuring the codebase. ◼ Educational objective: introduce the naive copy-paste attempt and demonstrate why it leads to maintenance drift.

- [code] Naive Monolithic File with Duplicated Components:

```jsx title="Naive Monolithic Implementation"
function Badge({ text }) { // Trapped helper cannot be shared
  return <span className="badge">{text}</span>;
}
function ArticleCard() { // Monolithic component definition
  return (
    <article className="card">
      <Badge text="Latest News" />
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `Badge`: a secondary UI helper trapped inside the same file as `ArticleCard`. 2. `ArticleCard`: a reusable component trapped inside `App.jsx` with zero independent export. 3. `App`: the root shell forced to hold component definitions directly in its local scope.

- [p] ★ {mechanism: splitting components into dedicated ES modules with explicit exports} To solve this problem, modern JavaScript and React rely on ES modules to organize components into dedicated files. You create a new file named `ArticleCard.jsx` under `src/components/`, export the card component, and import it wherever it is needed. Each component lives in its own file with its own clear responsibilities. When a design update occurs, you edit the component in one place, and every page that imports it automatically reflects the change. ◼ Educational objective: explain how moving components into dedicated modules eliminates duplication and establishes clean boundaries.

### What Are ES Modules and How Does React Use Imports?

- [p] ◇ {conceptual grounding: JavaScript files as isolated modules} In modern web development, every JavaScript file is an isolated **module**. Variables, functions, and objects defined inside a module are private by default. Other files cannot access or modify them unless the file explicitly shares them using the `export` keyword. This isolation prevents global namespace collisions and keeps your codebase modular and predictable. ◼ Educational objective: establish that files are private modules by default.
- [p] ◇ {syntactic decoding: default exports versus named exports} JavaScript provides two primary ways to export values from a module: **default exports** and **named exports**. A default export represents the primary value or component that a file provides, declared with `export default`. A file can have at most one default export. In contrast, named exports allow a module to share multiple values or helper components, declared with `export function Name()`. When importing a named export, you place its exact name inside curly braces: `import { Badge } from './ArticleCard.jsx'`. ◼ Educational objective: contrast the single-item default export with multi-item named exports.
- [p] ◇ {syntactic clarification: named import curly braces versus object destructuring} In JavaScript, the curly braces in `import { Badge } from './ArticleCard.jsx'` look identical to object destructuring, but they are an ES module language construct. They tell the JavaScript engine to link directly to the specific named export binding declared in that module. Unlike runtime object destructuring, ES module import bindings are evaluated and linked statically before any component function executes. ◼ Educational objective: clarify that import braces are static module links rather than runtime object destructuring.
- [p] ★ {compiler transformation: build-time module resolution and bundling} Under the hood, modern build tools like Vite use the ES module dependency tree to resolve files and package code for the browser. When you write an import statement, the bundler checks that the target file exists on disk and verifies that the requested export name matches an exported binding. If you import a named export with default syntax, or misspell the exported name, the build tool halts immediately with an explicit error before invalid code reaches the browser. ◼ Educational objective: explain how bundlers use the module dependency tree to verify imports at build time.

### Principles of React: Splitting Components with Imports and Exports

- [p] ◇ When preparing for technical interviews, candidates must explain how components are organized across files, how default and named imports differ in mechanics and trade-offs, why exported functions must carry explicit names, and how the module dependency tree operates. To master these concepts, we formalize the six governing principles of component imports and exports: ◼ Educational objective: frame the upcoming principles from the perspective of an engineering candidate preparing for technical interviews.

> [!PRINCIPLE]
> **Principle 1: Give Each Shared Component Its Own Module**
> Move a component into its own file under `src/components/` when another file needs it or when its current file becomes hard to scan. Export the component from that file, and keep private helpers used by only one component unexported in that same file.
> 
> >> module boundary : an isolated file that encapsulates internal logic and exposes explicit exports
> 
> *It is best practice to do this:*
> `export default function ArticleCard() { // Dedicated module export`
> `  return <article className="card" />;`
> `}`
> 
> *Instead of doing this:*
> `function ArticleCard() { ... } // Monolithic file dumping all components`
> `function Badge() { ... }`
> `export default function App() { ... }`

- [p] ★ Principle 1 operational derivation: Moving a component into its own module takes three steps: (1) create a new file such as `src/components/ArticleCard.jsx`, (2) export the component function from that file, and (3) import it in every file that renders it. Top-level variables and helper functions defined in a module remain completely private unless you add the `export` keyword. If a helper function like `formatDate` is only used inside `ArticleCard`, keeping it unexported protects it from outside interference and keeps your module contract clean. If an outside file attempts to import an unexported helper, the build halts with an explicit missing export error. ◼ Educational objective: walk through the three steps of file splitting and prove that unexported helpers remain private.

> [!PRINCIPLE]
> **Principle 2: Import Each Component in the Form It Was Exported**
> Every file that renders a component must import it using the exact syntax matching its export. Use `import Component from 'module-path'` for a default export and `import { Component } from 'module-path'` for a named export. ES modules link imports to exports by kind and name before any component runs.
> 
> >> module linking : the process where the JavaScript engine connects import statements to corresponding export declarations
> 
> *We should do this:*
> `import ArticleCard from './ArticleCard.jsx'; // Default import: no curly braces`
> `import { Badge } from './ArticleCard.jsx'; // Named import: requires curly braces { }`
> 
> *We should not do this:*
> `import { ArticleCard } from './ArticleCard.jsx'; // Wrong: default export cannot use curly braces { }`
> `import Badge from './ArticleCard.jsx'; // Wrong: named export cannot omit curly braces { }`

- [p] ★ Principle 2 operational derivation: When you import a default export with curly braces (`import { ArticleCard }`), or import a named export without curly braces (`import Badge`), the syntax violates the module contract. In Vite's development server, a mismatched default import blanks the page and displays an error in the browser console: "The requested module does not provide an export named default". During a production build, `vite build` halts immediately with `[MISSING_EXPORT] "default" is not exported by "src/components/ArticleCard.jsx"`. If you forget to write an import statement entirely, the browser throws a runtime `ReferenceError: ArticleCard is not defined`. In legacy bundlers with CommonJS interop, this mistake resulted in the infamous React error: "Element type is invalid: expected a string or a class/function but got: undefined". In modern native ES modules, the build tool stops the mistake earlier during module linking. ◼ Educational objective: demonstrate both development and production error messages for mismatched imports and explain the historical React undefined element error.

> [!PRINCIPLE]
> **Principle 3: Choose the Export Style by What the File Provides**
> Use a default export when a file exists to provide one primary component, and use named exports when a file provides multiple components or utilities. A default import can take any local variable name, while a named import must match the exported name character for character.
> 
> >> name drift : an inconsistency where different files import the same default export under different local names
> 
> *It is best practice to do this:*
> `export default function ArticleCard() {} // Primary card export`
> `export function Badge({ text }) {} // Secondary utility export`
> 
> *Instead of doing this:*
> `import AuthorTag from './ArticleCard.jsx'; // Silently renames card to author tag!`

- [p] ★ Principle 3 operational derivation: The fundamental mechanical difference between default and named exports lies in name binding. Because a default export is the single anonymous fallback value of a module, the importing file can assign it any local variable name: `import CustomCard from './ArticleCard.jsx'` compiles and works perfectly. However, this flexibility can be dangerous: if an engineer accidentally writes `import AuthorTag from './ArticleCard.jsx'`, the code renders the entire article card under a misleading name without throwing any build error. In contrast, named exports strictly enforce that the import identifier inside curly braces matches the exported identifier. If you rename the named export `Badge` to `StatusBadge` in the source file, any file still importing `{ Badge }` immediately fails to build with an explicit missing export error. ◼ Educational objective: prove that default imports permit arbitrary local naming while named imports enforce strict identifier contracts.

> [!PRINCIPLE]
> **Principle 4: Name Every Exported Component Function**
> Always write exported components as named function declarations, such as `export default function ArticleCard() {}`. If you export an anonymous arrow function without a name, the JavaScript engine assigns it the fallback identifier `default`, and React prints `<default>` in its error callstacks and warnings.
> 
> >> anonymous component : a component function declared without a name identifier in its definition
> 
> *We should do this:*
> `export default function ArticleCard() { // Named function in error stacks`
> `  return <article>Latest News</article>;`
> `}`
> 
> *We should not do this:*
> `export default () => { // Anonymous export appears as <default>`
> `  return <article>Latest News</article>;`
> `};`

- [p] ★ Principle 4 operational derivation: Official React documentation strongly discourages anonymous default exports like `export default () => {}`. When a component function has no name, the JavaScript runtime assigns it the name of the export key, which is the literal string `"default"`. If an unhandled exception or rendering error occurs inside that component, React displays an error message: "An error occurred in the <default> component". In a production codebase containing dozens of default-exported components, an error naming `<default>` provides zero clue about which file or component actually failed. Writing a named function declaration ensures React callstacks, React DevTools, and browser performance profiles display `<ArticleCard>` clearly. ◼ Educational objective: demonstrate the `<default>` error stack symptom and show how naming components restores debugging clarity.

> [!PRINCIPLE]
> **Principle 5: Match Import Paths to Filenames Exactly, Including Case**
> Write every import path with the exact capitalization of the file on disk. The default macOS file system ignores letter casing and resolves `./components/articleCard.jsx` to `ArticleCard.jsx`, while Linux build servers enforce strict case sensitivity and fail the build.
> 
> >> case-sensitive file system : an operating system storage model where uppercase and lowercase letters represent distinct files
> 
> *We should do this:*
> `import ArticleCard from './components/ArticleCard.jsx'; // Exact casing matches disk`
> 
> *We should not do this:*
> `import ArticleCard from './components/articleCard.jsx'; // Lowercase path breaks on Linux CI`

- [p] ★ Principle 5 operational derivation: On macOS, the standard APFS file system is case-preserving but case-insensitive. If a file on disk is named `ArticleCard.jsx`, writing an import path with lowercase `articleCard.jsx` resolves and compiles with zero warnings on a developer's Mac laptop. However, when the code is pushed to a continuous integration (CI) server running Linux, the Linux file system treats uppercase and lowercase characters as completely different paths. The CI build immediately fails with `[UNRESOLVED_IMPORT] Could not resolve 'components/articleCard.jsx' in src/App.jsx`. Furthermore, because Git on macOS defaults to `core.ignorecase = true`, renaming a file's casing in the Mac Finder is not recorded by Git. Developers must use `git mv src/components/articleCard.jsx src/components/ArticleCard.jsx` to ensure Git registers the change. ◼ Educational objective: explain the classic "works on my Mac, breaks on Linux CI" case-sensitivity defect and demonstrate git mv.

> [!PRINCIPLE]
> **Principle 6: Separate What Runs on Import from What Runs on Render**
> Importing a module executes its top-level code once when the module loads, regardless of how many files import it. In contrast, code placed inside a component function runs only when React actively renders that component in the user interface.
> 
> >> module evaluation : the one-time execution of top-level code when a file is first imported
> >> render execution : the invocation of a component function by React to produce JSX markup

- [p] ★ Principle 6 operational derivation: In JavaScript, ES modules are singletons: when a file is imported for the first time, the JavaScript runtime evaluates all code written at the file's top level. If that same file is imported by five other components across your application, the top-level code does not execute again; the runtime returns the cached module export. A `console.log` placed at the top level of `ArticleCard.jsx` prints immediately when the application starts, even if no component on screen ever renders `<ArticleCard />`. In contrast, code placed inside the `ArticleCard` function body stays completely silent until React mounts the component into the render tree. Understanding this separation ensures developers do not place expensive calculations or unintended side effects at module scope. ◼ Educational objective: prove that module top-level code evaluates once on import while component functions execute only upon rendering.

### Step 1: First, we extract the primary card component <ArticleCard.jsx>

- [p] ★ {step motivation: extracting the card into a dedicated file under src/components/} We begin by creating a new file on disk: `src/components/ArticleCard.jsx`. - [p] ★ {step motivation: importing default and named exports cleanly in the root shell} Now that `src/components/ArticleCard.jsx` provides both a default card and a named badge, we open `src/App.jsx` and import them. We use default import syntax for `ArticleCard` and named import syntax with curly braces for `Badge`. We render two distinct cards: one with a "LATEST NEWS" badge and another with an "ARCHIVE" badge. Notice that both files now have clear, focused jobs: `ArticleCard.jsx` manages card structure and badge styling, while `App.jsx` orchestrates page layout. ◼ Meaningful pedagogical commentary: matching import syntax to export styles, composing modular components in parent shell.

### Where you will meet this

- [p] 1. **Design System Component Libraries**: UI libraries like buttons, modals, and cards export primary components as default exports or grouped named exports for consumption across enterprise applications.
- [p] 2. **Multi-Page Feature Routing**: File-based routing frameworks (like Next.js) require each route page to export a default React component, while co-located utility files provide named helper exports.
- [p] 3. **Icon and Utility Packages**: Icon libraries package hundreds of SVG icons as individual named exports (`import { SearchIcon, CloseIcon }`), enabling bundlers to include only the icons your application renders.

### Glossary

- [glossary] Default Export ◼ The primary value or component exported by a module, declared with export default and imported without curly braces under any local name.
- [glossary] Named Export ◼ A specific value or component exported by a module using its declared name, imported inside curly braces matching the export identifier.
- [glossary] Module Dependency Tree ◼ The hierarchical graph of file relationships formed by import and export statements, used by bundlers to package application code.
- [glossary] Render Tree ◼ The runtime hierarchy of React component elements mounted on screen, evaluated by React during application rendering.
- [glossary] Name Drift ◼ An inconsistency where different files import the same default export under different local names, making codebase searches difficult.

**Architectural Takeaways & Decision Matrix**

❒ Module Organization & Export Choice

➔ ALWAYS give each component that other files use its own module under `src/components/`, and keep single-use helpers unexported in that file.

➔ NEVER export anonymous component functions like `export default () => {}`, because React prints `<default>` in error stacks and DevTools.

❒ Import Matching & Casing Discipline

➔ ALWAYS match import syntax to the export style, using default imports without braces for default exports and curly braces for named exports.

➔ ALWAYS write import paths with the exact casing of the filename on disk to prevent build failures on case-sensitive Linux CI servers.

**DO THIS:** match import syntax to export style and name exported functions

```jsx right
export default function ArticleCard({ title }) {
  return <article className="card">{title}</article>;
}
export function Badge({ text }) {
  return <span className="badge">{text}</span>;
}
```

**DO NOT DO THIS:** mix up default and named syntax or use anonymous components

