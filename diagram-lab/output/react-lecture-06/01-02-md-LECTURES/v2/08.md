### The Monolithic File and the Import Trap

In early project stages, developers often place multiple components in a single file for convenience. As an application grows, a monolithic `App.jsx` becomes an unmaintainable bottleneck. Multiple developers editing different widgets inside the same file generate endless merge conflicts. Furthermore, locating bugs in a 1,200-line script slows down the entire engineering team. To build scalable React applications, you must extract each component into its own dedicated ES module file.

When splitting components into separate files, mistyping import syntax causes fatal runtime crashes.

Look at the naive attempt below:

```jsx title="Naive Import Mismatch"
import { ArticleCard } from './ArticleCard.jsx'; // **WRONG:** curly braces search named property on **DEFAULT EXPORT**

export default function App() {
  return (<ArticleCard />); // **WRONG:** crashes with undefined element type **EXCEPTION**
}
```

When a file exports a component using `export default`, the bundler places that function on the `.default` property of the module namespace object. If you write `import { ArticleCard } from './ArticleCard.jsx'`, the JavaScript engine looks for an export literally named `ArticleCard`. Because none exists, `ArticleCard` is assigned `undefined`. When React attempts to render `<ArticleCard />`, it invokes `_jsx(undefined, {})`. React throws a fatal runtime exception: `Error: Element type is invalid: expected a string or a class/function but got: undefined. You likely forgot to export your component or mixed up default and named imports.`

```html-figure src="figures/08-00-default-vs-named-exports.html" caption="The ES module namespace: default exports bind to .default, while named exports bind to exact identifier keys."
```

> [!WILD]
> **Why does an undefined component crash during rendering instead of import?** When developers mix up import syntax, they expect Vite or the browser to throw a syntax error immediately at the import statement. Why does the file load silently, only to explode when React renders? Because in JavaScript ES modules, importing a non-existent named export from a module is legally permitted at syntax level; it simply resolves to undefined. The failure only occurs when React's runtime attempts to evaluate `<ArticleCard />`. React inspects the first argument to `_jsx()` and finds `undefined` instead of a function or DOM string tag, halting with a fatal type error.

> [!TIP]
> **To impress the interviewer:** When asked how default and named imports differ, explain that a default export binds to the module's internal `.default` property and is imported without curly braces, while named exports represent specific properties and must be imported with curly braces matching their exact exported names.

### Principles of React: The Core Laws of ES Module Imports

To prepare for any technical interview, we must separate monolithic scripting habits from React's modular file architecture and establish the five fundamental laws governing how components are split, exported, and imported across ES modules. In React, clean module boundaries enable team parallelization, tree-shaking, and predictable component loading. We formalize these rules into five standalone principles.

> [!PRINCIPLE]
> **Principle 1: Isolate Each Reusable Component in Its Own Dedicated Module File**
> You must place each primary component in an **independent `.jsx` file**, strictly avoiding monolithic multi-component files.
> 
> >> independent .jsx file : a dedicated file containing a single component and its localized dependencies
> >> monolithic multi-component files : placing dozens of components in one massive script, creating merge conflicts
> 
> *It is best practice to do this:*
> `// src/components/ArticleCard.jsx`
> `export default function ArticleCard() {`
> `  return (`
> `    <article className="card" />`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `// All components inlined in App.jsx`
> `function Card() { return <article />; }`
> `function Feed() { return <Card />; }`

In senior engineering interviews, modular software architecture begins with single-responsibility module files:

1. **Monolithic Multi-Component Files (Anti-Pattern):** Declaring dozens of components inside `App.jsx` creates an unmaintainable codebase where multiple developers trigger merge conflicts on the same file. Finding bugs becomes a chore, and bundlers struggle to optimize tree branches.
2. **Dedicated Component Modules (Idiomatic):** Placing each component in its own file (`ArticleCard.jsx`, `AuthorBadge.jsx`) establishes clear boundaries. Each file owns its specific dependencies, styling, and tests, allowing team members to develop components concurrently without collision.

```jsx title="Principle 1: Component File Isolation"
// **RIGHT:** Dedicated component module with single responsibility
export default function ArticleCard() {
  return (
    <article className="article-card">
      <h2>Top Story</h2>
    </article>
  );
}
```

> [!PRINCIPLE]
> **Principle 2: Export Primary Components as Default Exports**
> You must export the single primary component of a file using **`export default`**, importing it without curly braces under any convenient identifier name.
> 
> >> export default : ES module syntax declaring the main entity of a module
> >> without curly braces : importing the default export directly as an identifier (import ArticleCard from './ArticleCard.jsx')
> 
> *It is best practice to do this:*
> `export default function ArticleCard() {`
> `  return (`
> `    <article className="card" />`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function ArticleCard() {`
> `  return (`
> `    <article className="card" />`
> `  );`
> `}`
> `window.ArticleCard = ArticleCard;`

Interviewers evaluate whether candidates understand the canonical export convention for React components:

1. **The Primary Entity Convention:** A component file typically has one main visual responsibility. Using `export default` signals to every developer and build tool that this function represents the primary export of the module file.
2. **Braceless Import Syntax:** When importing a default export, consumers write `import ArticleCard from './ArticleCard.jsx'`. Because it is the default export, it does not require curly braces and can be renamed at the import site if naming conflicts arise.

```jsx title="Principle 2: Default Component Export"
// **RIGHT:** Primary component exported as default
export default function AuthorBadge() {
  return (
    <div className="author-badge">
      <span>Clara Foster</span>
    </div>
  );
}
```

> [!PRINCIPLE]
> **Principle 3: Export Supporting Utilities as Named Exports**
> You must export auxiliary helpers, constants, or secondary widgets using **named exports** (`export function formatHeadline()`), importing them with exact curly braces (`{ formatHeadline }`).
> 
> >> named exports : exporting specific variables or functions using export const / export function
> >> exact curly braces : import { helper } requiring an exact name match with the exported identifier
> 
> *It is best practice to do this:*
> `export function formatRole(role) {`
> `  return role.toUpperCase();`
> `}`
> 
> *Instead of doing this:*
> `// Attaching helpers to default object`
> `export default {`
> `  formatRole: (r) => r.toUpperCase()`
> `};`

Understanding how named exports interact with tree-shaking is a vital senior engineering topic:

1. **Exact Identifier Binding:** Named exports (`export function formatRole(...)`) attach directly to named keys on the module namespace. When importing them, developers must use curly braces with the exact matching name: `import { formatRole } from './AuthorBadge.jsx'`.
2. **Bundler Tree-Shaking:** Modern bundlers like Vite and Rollup analyze named exports statically. If a module exports five utility functions but your application only imports one, the bundler eliminates the other four from the final production bundle. Bundling helpers into a default object defeats tree-shaking.

```jsx title="Principle 3: Named Helper Export"
// **RIGHT:** Named helper exported alongside default component
export function formatRole(role) {
  return role.toUpperCase() + ' DESK';
}
```

> [!PRINCIPLE]
> **Principle 4: Never Wrap Default Exports in Import Curly Braces**
> You must import default exports **without curly braces** (`import Card from './ArticleCard.jsx'`), because curly braces search for a named property and evaluate to `undefined` on default exports.
> 
> >> without curly braces : binding the default export directly to a local variable
> >> evaluate to undefined : JavaScript failing to find a matching named key on the module namespace
> 
> *We should do this:*
> `import ArticleCard from`
> `  './ArticleCard.jsx';`
> 
> *We should not do this:*
> `import { ArticleCard } from`
> `  './ArticleCard.jsx';`

Interviewers frequently test candidates on the most common import mistake in React:

1. **Curly Braces Search Named Keys:** In an `import` statement, curly braces do not perform object destructuring; they are ES module syntax specifying that JavaScript must look for a named export matching that exact identifier on the module namespace object.
2. **The Default Slot Mismatch:** When a component is exported via `export default`, it lives under the internal key `.default`. Writing `import { ArticleCard }` looks for a named export called `ArticleCard`, finds nothing, and assigns `undefined` without a compile-time syntax error.

```jsx title="Principle 4: Clean Braceless Import"
// **RIGHT:** Default export imported without curly braces
import ArticleCard from './ArticleCard.jsx';

export default function App() {
  return (<ArticleCard />);
}
```

> [!PRINCIPLE]
> **Principle 5: Component Render Fails with TypeError When Importing Undefined**
> You must recognize that importing a mismatched export resolves silently to `undefined`, which crashes React during render with **Element type is invalid**.
> 
> >> resolves silently to undefined : JavaScript allowing missing named imports to evaluate to undefined without early error
> >> Element type is invalid : the fatal runtime error React throws when attempting to render undefined
> 
> *We should do this:*
> `import ArticleCard from`
> `  './ArticleCard.jsx';`
> `return (<ArticleCard />);`
> 
> *We should not do this:*
> `import { ArticleCard } from`
> `  './ArticleCard.jsx';`
> `return (<ArticleCard />);`

Understanding where and why import mismatches explode during React's lifecycle separates juniors from seniors:

1. **Silent Import Resolution:** In standard ECMAScript modules, importing an undefined named export is syntactically valid: JavaScript sets the variable to `undefined` and continues execution. Neither the bundler nor the browser halts at the import line.
2. **Runtime Render Crash:** The crash occurs when React executes your JSX return statement: `<ArticleCard />` compiles to `_jsx(ArticleCard, {})`. React requires the first argument to be a valid component function or HTML tag string. Finding `undefined`, React halts with `Element type is invalid`.

```jsx title="Principle 5: Verified Component Invocation"
// **RIGHT:** Valid component reference guarantees successful render
import ArticleCard from './ArticleCard.jsx';

export default function App() {
  return (
    <main>
      <ArticleCard />
    </main>
  );
}
```

> [!KEY]
> Export the primary component as `default` (imported without braces). Export helper functions as `named` (imported with braces). Never wrap a default export in curly braces.

To master component file splitting and ES module imports, we will construct the editorial desk for The National Times. We will progress across four sequential steps: constructing the top-level container in `src/App.jsx`, extracting the primary card component into `src/components/ArticleCard.jsx`, declaring the author badge and named helper in `src/components/AuthorBadge.jsx`, and assembling default and named imports inside `ArticleCard.jsx`.

### Step 1: First, we construct the parent container <App.jsx>

We begin by constructing the top-level application shell in `src/App.jsx`. This component acts as the outer editorial container. It imports `ArticleCard` as a default import without curly braces and mounts it inside the page layout:

```jsx title="src/App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // Imports default component without **CURLIES**

export default function App() {
  return (
    <div className="editorial-shell">
      <ArticleCard /> // Mounts modular article card at layout **ROOT**
    </div>
  );
}
```

Notice the import syntax: `import ArticleCard from './components/ArticleCard.jsx'`. Because `ArticleCard.jsx` exports its component as `default`, we do not use curly braces. Writing `{ ArticleCard }` here would assign `undefined` and crash the render pass.

### Step 2: Next, we extract the primary card component <ArticleCard.jsx>

Now we create the component file `src/components/ArticleCard.jsx`. This file represents the primary article presentation card. We declare the component and export it as the default export of the module:

```jsx title="src/components/ArticleCard.jsx" startLine="1" continues="bottom"
import AuthorBadge, { formatRole } from './AuthorBadge.jsx'; // Combined default and named **IMPORT**

export default function ArticleCard() { // Primary component default **EXPORT**
  const headline = 'Offshore Banking Secrets Exposed';
  const role = formatRole('investigative'); // Calls named utility **FUNCTION**
  return (
    <article className="article-card">
      <span className="desk-tag">{role}</span>
      <h2 className="headline">{headline}</h2>
```

Notice line 1: `import AuthorBadge, { formatRole } from './AuthorBadge.jsx'`. In a single line, we import the default component `AuthorBadge` without braces, and the named utility `formatRole` with braces. This demonstrates how default and named imports coexist harmoniously.

### Step 3: Then, we declare the author badge and named helper <AuthorBadge.jsx>

Next, we create `src/components/AuthorBadge.jsx`. This file exports two entities: a named helper function `formatRole` that formats editorial desk tags, and a default component `AuthorBadge` that renders the reporter's credentials:

```jsx title="src/components/AuthorBadge.jsx"
export function formatRole(role) { // Named export for string **FORMATTER**
  return role.toUpperCase() + ' DESK';
}
export default function AuthorBadge() { // Default export for badge **COMPONENT**
  return (
    <div className="author-badge">
      <span className="author-name">Clara Foster</span> // Reporter **PROFILE**
    </div>
  );
}
```

Notice that `formatRole` carries `export`, while `AuthorBadge` carries `export default`. The keyword `default` flags `AuthorBadge` as the primary export of the file. Any other export in the file must be a named export.

### Step 4: Finally, we mount the child badge inside <ArticleCard.jsx>

Finally, we complete `src/components/ArticleCard.jsx` by mounting the `<AuthorBadge />` component inside the article card layout and closing the JSX return statement:

```jsx title="src/components/ArticleCard.jsx" startLine="9" continues="top"
      <AuthorBadge /> // Mounts imported child component at card **BASE**
    </article>
  );
}
```

Notice how modular our application has become: `App.jsx` imports `ArticleCard.jsx`, which in turn imports `AuthorBadge.jsx` and its helper `formatRole`. Each file has a single clear responsibility, carries its own imports, and can be edited without conflicting with other components.

### Where you will meet this

1. **Multi-Page Web Applications**: Extracting page layouts, navigation headers, and footers into dedicated module files.
2. **Design System Component Libraries**: Exporting primary UI widgets as defaults and design tokens or utility helpers as named exports.
3. **Data Fetching and API Services**: Exporting API client components alongside named data transformation functions.
4. **Third-Party Package Consumption**: Importing default components alongside named hooks from npm libraries (`import React, { useState } from 'react'`).

### Glossary

- **ES Module**: A standard JavaScript file format that uses import and export statements to share code across files.
- **Default Export**: An export declared with `export default` representing the primary entity of a module, imported without curly braces.
- **Named Export**: An export declared with `export const` or `export function`, imported with matching curly braces.
- **Module Namespace**: The internal JavaScript object containing all exports of a module, with default exports stored under the `.default` property.
- **Element Type Is Invalid**: The fatal runtime error React throws when a component identifier resolves to `undefined` during rendering.

## Beyond the basics

- **Default vs named export conventions**: Official React documentation recommends sticking to one export style within a codebase or using default exports for components and named exports for utilities (see [react.dev/learn/importing-and-exporting-components#default-vs-named-exports](https://react.dev/learn/importing-and-exporting-components#default-vs-named-exports)).
- **Renaming imports with the as keyword**: You can rename named imports to resolve naming collisions using `import { formatRole as getRoleBadge } from './AuthorBadge.jsx'` (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).
- **Exporting multiple named components from an index file**: Barrel files (`index.js`) re-export multiple components via `export * from './AuthorBadge.jsx'` for convenient package-style imports (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).
- **Dynamic imports with React.lazy**: Code-splitting components across separate network chunks is achieved via dynamic `import()` and `React.lazy()` (see [react.dev/reference/react/lazy](https://react.dev/reference/react/lazy)).
- **Tree-shaking mechanics in modern bundlers**: Bundlers like Rollup and Vite analyze static named exports to eliminate dead code from final production bundles (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Component Isolation & Default Exports

➔ ALWAYS place each primary reusable component in its own dedicated `.jsx` file.

➔ ALWAYS export the primary component using `export default` and import it without curly braces.

➔ NEVER place multiple complex layout components inside a single monolithic file.

❒ Named Exports & Import Correctness

➔ ALWAYS export auxiliary helpers, types, and secondary widgets as named exports (`export function ...`).

➔ ALWAYS import named exports using matching curly braces (`import { formatRole } from './AuthorBadge.jsx'`).

➔ NEVER wrap a default export in curly braces during import, because it evaluates to `undefined` and crashes React at runtime.

**DO THIS:** import default components without curly braces and named helpers with curly braces

```jsx right
import ArticleCard, { formatRole } from './ArticleCard.jsx';

export default function App() {
  return (<ArticleCard />);
}
```

**DO NOT DO THIS:** wrap default exports in curly braces or mix up export styles

```jsx wrong
import { ArticleCard } from './ArticleCard.jsx';

export default function App() {
  return (<ArticleCard />);
}
```
