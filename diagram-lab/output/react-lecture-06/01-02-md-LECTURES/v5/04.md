### The Literal Text Trap and Broken Image Paths

Think back to how you render data in traditional browser scripts. In plain JavaScript, you declare a variable holding an article headline: `const headline = "Transit Accord Reached"`. In classic templating languages, you might expect the template engine to look up that variable automatically. When developers transition to React, they often assume JSX reads variables the same way. You sit at your keyboard, type the variable name between HTML tags, and expect React to find it.

On The National Times, Clara Foster sits down to format a breaking transit dispatch card. Clara opens `DispatchCard.jsx` and declares local variables: the story headline and the author's avatar URL. Then, Clara writes the component markup:

`return (
  <article className="dispatch-card">
    <h2>headline</h2>
    <img src="avatarUrl" alt="Author photo" />
  </article>
);`

Clara saves the file and switches to the browser.

Instead of displaying the transit headline, the screen prints the literal word "headline". Beneath it, the author photo shows an empty broken-image icon. The browser network console reports an immediate failure:

`GET http://localhost:5173/avatarUrl 404 (Not Found)`

The browser treated `"avatarUrl"` as a literal URL string path rather than reading Clara's JavaScript variable from memory.

```jsx title="Naive Literal JSX"
function DispatchCard() {
  const headline = "Transit Union Approves Contract";
  const avatarUrl = "/photos/reporters/clara.jpg"; // Holds image file **PATH**
  return (
    <article className="dispatch-card">
      <h2>headline</h2> // **WRONG:** prints text instead of **VARIABLE**
      <img src="avatarUrl" /> // **WRONG:** requests path **AVATARURL**
    </article>
  );
}
```

Why did this happen? In JSX, text written between tags is treated as static character content. The JSX compiler does not scan text nodes for matching JavaScript identifiers. It simply passes the characters straight through to the browser DOM.

To fix an urgent news alert on the same card, Clara tries another common developer impulse. Clara writes a standard JavaScript `if` statement directly inside the markup:

```jsx title="Naive Statement in JSX"
function DispatchCard() {
  const isUrgent = true; // Tracks urgent story **STATUS**
  return (
    <span className="badge">
      {if (isUrgent) { "URGENT" }} // **WRONG:** statement crashes **PARSER**
    </span>
  );
}
```

The moment Clara saves the file, the local dev server halts compilation. The browser displays a red error overlay:

`SyntaxError: Unexpected token 'if'`

The compiler rejected the code instantly. Why does JSX permit variables inside curly braces but crash on an `if` statement?

> [!WILD]
> **Why does an attribute quote break variable lookup?**
>
> In HTML, quotes around attributes are standard syntax for strings. In JSX, however, double quotes strictly instruct the compiler to create a static string literal. When you write `src="avatarUrl"`, React tells the browser to fetch the relative path `/avatarUrl` from your web server. The server cannot find a file named `avatarUrl`, returning a 404 error. To read a variable from memory, you must remove the quotes and enclose the variable in curly braces: `src={avatarUrl}`.

### The Evaluation Window: Bridging Markup and JavaScript Execution

To understand dynamic data, we must recognize two alternating modes. JSX switches between markup mode and JavaScript mode. When the compiler parses a JSX element, it begins in markup mode. In markup mode, every character between tags is treated as literal text.

To step out of static markup and run live JavaScript, React provides an **evaluation window** marked by curly braces (`{}`). When the compiler encounters an opening curly brace `{`, it temporarily exits markup mode. It evaluates the JavaScript code sitting inside before returning to markup mode at the closing brace `}`.

The most critical rule of the JSX evaluation window is the divide between **expressions** and **statements**. In ECMAScript grammar, an **expression** is any unit of code that resolves to a single discrete value in memory. Numbers (`4 + 2`), variables (`headline`), template literals (`` `${readTime} min` ``), ternary conditions (`isUrgent ? "URGENT" : "STANDARD"`), and function calls (`formatDate()`) are all expressions.

A **statement**, by contrast, controls execution flow without producing a value. Statements like `if`, `for`, `while`, and `switch` perform actions, but they evaluate to nothing. JSX compiles directly into JavaScript function calls (`_jsx()`). Every item inside curly braces must produce a passing value. Placing an `if` statement inside curly braces fails. JavaScript function arguments cannot accept control-flow statements.

Once an expression evaluates, React consults its **primitive render matrix** to determine what appears on screen:

1. **Strings and Numbers**: Strings (`"Transit"`) and numbers (`42`) render directly into visible browser DOM text nodes.
2. **Booleans**: The values `true` and `false` are treated as invisible values and emit zero DOM nodes.
3. **Null and Undefined**: The primitives `null` and `undefined` are also treated as invisible and render nothing to the screen.

This behavior allows developers to write conditional expressions without printing unwanted words like "false" or "null" onto the screen.

### Principles of React: JavaScript Expressions and JSX Evaluation

In technical interviews, senior candidates must articulate the compiler grammar that separates JSX evaluation windows from plain template strings. To master this architecture, we formalize the six governing principles of JavaScript expressions in JSX:

> [!PRINCIPLE]
> **Principle 1: Step Out of Static Markup Using Curly Braces as an Evaluation Window**
> Wrapping identifiers in curly braces switches the JSX parser from static text into JavaScript expression evaluation. The runtime reads the live variable from memory and injects its value directly into the rendered tree.
> 
> >> evaluation window : curly braces that switch parser from static markup to JavaScript code
> 
> *We should do this:*
> `// Evaluating variable in curly braces`
> `<h2>{headline}</h2>`
> 
> *We should not do this:*
> `// Rendering variable as static text`
> `<h2>headline</h2>`
When building interfaces with HTML-first template engines like Vue, Django, or Jinja, you author a text document. The template engine scans raw HTML strings looking for special markers to replace with data. Because JSX looks visually identical to HTML, developer intuition naturally expects that same behavior. If you declare `const headline = "Transit Accord";` and write `<h2>headline</h2>`, you might expect the engine to inspect your local variables, see `headline`, and insert its value.

JSX is not a text template; it is a syntax bridge that compiles directly into standard JavaScript function calls. To guarantee predictable execution, the JSX compiler strictly defaults to "markup mode" whenever it reads characters between tags. It assumes every bare word you type is literal, static text intended for the screen.

When you write `<h2>headline</h2>`, the compiler emits:

```jsx title="Compiler Output"
_jsx("h2", { children: "headline" })
```

The browser receives the raw text string `"headline"` and paints those exact eight letters onto the page.

To break out of markup mode, you must explicitly declare an evaluation window using curly braces: `<h2>{headline}</h2>`. The curly braces act as a switch for the parser. They tell the compiler: "Stop treating characters as literal text. Step into JavaScript mode, evaluate the identifier inside this boundary, and hand its live value to the element." The compiler emits:

```jsx title="Compiler Output"
_jsx("h2", { children: headline })
```

Because `headline` is passed without quotes as a true JavaScript identifier, the runtime reads the live string value from memory and renders the actual headline text in the browser.



> [!PRINCIPLE]
> **Principle 2: Pass Only Value-Producing Expressions Inside Curly Braces**
> Curly braces accept exclusively JavaScript expressions that resolve to a discrete value. Imperative control-flow statements like `if`, `for`, and `while` do not produce values and are syntax errors inside JSX argument lists.
> 
> >> expression : code that calculates a result you can pass as a function argument
> 
> *We should do this:*
> `// Passing value-producing expression`
> `<span className="badge">`
> `  {isUrgent ? 'URGENT' : 'STANDARD'}`
> `</span>`
> 
> *We should not do this:*
> `// Passing control-flow statement`
> `<span className="badge">`
> `  {if (isUrgent) { 'URGENT' }}`
> `</span>`
Developers often wonder why they cannot write familiar control-flow statements like `if (isUrgent) { ... }` inside JSX curly braces. It feels frustrating because `if` statements are fundamental building blocks of JavaScript.

The reason is rooted in standard JavaScript grammar, not a limitation invented by React. Under the hood, every JSX tag compiles into a standard JavaScript function call. When you write `<span className="badge">{ ... }</span>`, the compiler turns it into `_jsx("span", { children: ... })`.

In JavaScript, function arguments and object properties must be **expressions**—units of code that evaluate to a single value. Look at what happens if the compiler allowed an `if` statement inside the curly braces:

```jsx title="Compiler Output"
// What the compiler would have to generate:
_jsx("span", {
  children: if (isUrgent) { "URGENT" } // Crash! JavaScript forbids statements here
});
```

Would you ever write `console.log(if (isUrgent) { "URGENT" })` in normal JavaScript? Of course not! Standard JavaScript throws `SyntaxError: Unexpected token 'if'` because statements produce no value and cannot be passed into functions.

To display conditional text, you must use an expression that evaluates to a value. A ternary operator (`isUrgent ? "URGENT" : "STANDARD"`) evaluates to a single concrete string, which JavaScript happily passes to the function:

```jsx title="Compiler Output"
_jsx("span", {
  children: isUrgent ? "URGENT" : "STANDARD" // Valid: passes a single value
});
```


> [!PRINCIPLE]
> **Principle 3: Drop String Quotes to Bind Dynamic Attributes**
> Dynamic attribute values are bound directly with curly braces without quotation marks. Quoting curly braces treats the variable name as a literal text string rather than evaluating the variable in memory.
> 
> >> dynamic binding : passing variable values to attributes without enclosing quotes
> 
> *We should do this:*
> `// Binding variable in naked curlies`
> `<img src={avatarUrl} alt="Reporter" />`
> 
> *We should not do this:*
> `// Quoting variable as string literal`
> `<img src="avatarUrl" alt="Reporter" />`
In standard HTML, every attribute value is wrapped in quotation marks (`<img src="/photo.jpg">`). When moving to JSX, developer muscle memory leads to two common mistakes: writing `src="avatarUrl"` or writing `src="{avatarUrl}"`.

Both mistakes cause the browser image loader to fail. In JSX attributes, double quotes and curly braces are two mutually exclusive parser switches.

When you use double quotes (`src="..."`), you lock the attribute into static string mode. The compiler refuses to inspect JavaScript variables. If you write `src="avatarUrl"`, the browser makes a network request for a file literally named `avatarUrl` and returns a `404 Not Found`. If you write `src="{avatarUrl}"`, the compiler treats the curly braces as literal characters in the URL string, requesting the broken path `"%7BavatarUrl%7D"`.

To pass a dynamic variable, you must drop the quotation marks completely and write `src={avatarUrl}`. Look at the compiled output:

```jsx title="Compiler Output"
// Raw quotes: fetches broken path "/avatarUrl"
_jsx("img", { src: "avatarUrl" })

// Curly braces: reads live variable from memory
_jsx("img", { src: avatarUrl })
```

By removing the quotes, you tell the parser to evaluate the identifier as live JavaScript code, allowing React to read the image path from memory and hand it directly to the browser.


> [!PRINCIPLE]
> **Principle 4: Booleans, Null, and Undefined Render Nothing to Enable Inline Conditionals**
> React treats booleans (`true`, `false`), `null`, and `undefined` as empty render slots that emit zero DOM nodes. This design makes inline conditional rendering clean and concise, whereas numbers and strings always render visible text.
> 
> >> empty render slot : primitive types that evaluate cleanly while emitting zero DOM nodes
> 
> *It is best practice to do this:*
> `// Clean conditional rendering via boolean`
> `{isUrgent && (`
> `  <span className="badge">LIVE</span>`
> `)}`
> 
> *Instead of doing this:*
> `// Unnecessary ternary returning null`
> `{isUrgent ? (`
> `  <span className="badge">LIVE</span>`
> `) : null}`
In standard JavaScript, converting primitive values into text preserves their literal characters:
- `String(false)` produces `"false"`.
- `String(null)` produces `"null"`.
- `String(undefined)` produces `"undefined"`.

Now look at what happens when you place a condition inside a container in JSX:

```jsx title="Component Source"
<div>
  {isUrgent && <Badge />}
</div>
```

When an article is not urgent, `isUrgent` holds the boolean value `false`. JavaScript’s `&&` operator evaluates the left side first. Because `isUrgent` is `false`, JavaScript stops immediately. It short-circuits, ignores `<Badge />`, and evaluates the whole expression to `false`. So what sits inside your `<div>` is literally the boolean value `false`:

```jsx title="Evaluated Expression"
<div>
  {false}
</div>
```

If React simply converted its children to text the way normal JavaScript string interpolation does—like `String(false)`—that boolean `false` would become the text string "false". The browser would create a text node and render:

```html title="Browser Render"
<div>false</div>
```

A user visiting your website would look at the article card, and right where the badge should be, they would read the literal word **"false"** printed on the page!

To prevent this problem, React has a built-in rule. When React builds the DOM for `<div>{false}</div>`, it checks the data type of the child. If the value is a boolean (`true` or `false`), `null`, or `undefined`, React **suppresses** it. It does not convert it into text. It creates zero DOM nodes. Instead of rendering `<div>false</div>`, the browser renders an empty container:

```html title="Browser Render"
<div></div>
```

Because of this built-in rule, the word "false" never appears on the screen. The space stays completely clean.

> [!PRINCIPLE]
> **Principle 5: Guard Numeric Conditionals with Explicit Booleans to Prevent Rogue Zero Output**
> React suppresses booleans and nullish values but always renders primitive numbers as living DOM text nodes. When evaluating numeric counters or array lengths with logical AND (`&&`), developers must convert the count to an explicit boolean to prevent rendering an orphaned `0` in the browser.
> 
> >> rogue zero : an unintended visible 0 rendered when a numeric 0 short-circuits in JSX
> >> explicit boolean guard : converting numeric expressions to true or false before evaluating &&
> 
> *We should do this:*
> `// Guarding count with comparison`
> `{unreadCount > 0 && (`
> `  <Badge count={unreadCount} />`
> `)}`
> 
> *We should not do this:*
> `// Passing raw numeric counter`
> `{unreadCount && (`
> `  <Badge count={unreadCount} />`
> `)}`
Developers often assume that React hides all falsy values. Look at what happens when you write a message counter using the `&&` operator:

```jsx title="Component Source"
const unreadCount = 0;

<div>
  {unreadCount && <Badge count={unreadCount} />}
</div>
```

When there are no new messages, `unreadCount` is `0`. Developer intuition says: *"Zero is falsy. Since React hides falsy values, nothing will show up inside the `<div>`."* That assumption is completely wrong.

Watch what JavaScript actually does:
1. JavaScript evaluates the left side of `&&`: `unreadCount`.
2. In JavaScript, `0` is a falsy value.
3. Because the left side is falsy, the `&&` operator stops immediately and returns that left-hand value: **the number `0`**.
4. The code inside the container becomes:

```jsx title="Evaluated Expression"
<div>
  {0}
</div>
```

Now React inspects what is inside the `<div>`:
- Is it `true` or `false`? **No.**
- Is it `null`? **No.**
- Is it `undefined`? **No.**
- It is a **number** (`0`).

React hides booleans, but it **never hides numbers**. In user interfaces, the number zero is important data—a bank balance of `$0`, a shopping cart with `0` items, or a game score of `0` must be visible to the user. Because `0` is a number, React creates a real browser text node and puts it inside the `<div>`:

```html title="Browser Render"
<div>0</div>
```

Instead of an empty container, the browser paints a literal **`0`** on the screen! This is the famous **Rogue Zero** bug. You will see it on live websites: a notification bell with a stray `0` floating next to it, or a table with an orphaned `0` where an empty state should be.

The bug happened because JavaScript gave React a **number** (`0`), not a **boolean** (`false`). To make the element disappear cleanly, you must make sure the left side of the `&&` evaluates to a real boolean. You have three production choices:

First, convert the count with a comparison operator (`> 0`):

```jsx title="Safe Boolean Comparison"
<div>
  {unreadCount > 0 && <Badge count={unreadCount} />}
</div>
```

Second, cast the number explicitly using `Boolean()`:

```jsx title="Explicit Boolean Cast"
<div>
  {Boolean(unreadCount) && <Badge count={unreadCount} />}
</div>
```

Third, use an explicit ternary operator that returns `null` for the empty state:

```jsx title="Ternary with Null"
<div>
  {unreadCount > 0 ? <Badge count={unreadCount} /> : null}
</div>
```

The moment JavaScript gives React `false` or `null` instead of the number `0`, React's rule kicks in, and the rogue zero disappears.


> [!PRINCIPLE]
> **Principle 6: Inline Styles Require a JavaScript Object, Not a CSS String**
> The `style` attribute in JSX accepts a JavaScript object literal rather than a CSS string. The outer braces open the JSX expression window, while the inner braces construct the object with camelCase properties.

> 
> >> style object : a JavaScript object with camelCase keys passed to the style prop
> 
> *We should do this:*
> `// Passing object literal in curlies`
> `<div style={{`
> `  padding: 16,`
> `  backgroundColor: '#f1f5f9'`
> `}} />`
> 
> *We should not do this:*
> `// Omitting inner object curlies`
> `<div style={`
> `  padding: 16,`
> `  backgroundColor: '#f1f5f9'`
> `} />`
Junior developers often find the double curly braces in `style={{ padding: 16 }}` confusing, assuming that React has invented a special "double-brace" syntax operator.

React has no special double-brace operator. What looks like a single syntax feature is actually two separate, ordinary JavaScript concepts sitting next to each other. The outer braces `{ ... }` are the JSX evaluation window that switches from markup mode to JavaScript mode. The inner braces `{ padding: 16 }` are a standard JavaScript object literal.

You can see this clearly by separating the object into a variable before passing it to JSX:

```jsx title="Style Object Extraction"
// Step 1: Create a normal JavaScript object
const cardStyle = { padding: 16, backgroundColor: '#f1f5f9' };

// Step 2: Pass the variable into the JSX evaluation window
<div style={cardStyle} />
```


When you write the object inline, the two pairs of braces simply touch each other: `style={{ padding: 16 }}`. If you mistakenly omit the inner braces and write `<div style={ padding: 16 } />`, JavaScript does not see an object. It sees `padding: 16` inside an expression block, interprets the colon as a statement label, and crashes with `SyntaxError: Unexpected token ':'`.

Furthermore, inline style properties in JSX use camelCase (`backgroundColor`) rather than hyphenated CSS strings (`background-color`). In JavaScript, the hyphen is the subtraction operator, so `background-color` would be parsed as `background minus color`. More importantly, React assigns this object directly to the browser element's native CSSOM object: `domNode.style.backgroundColor = '#f1f5f9'`. React simply mirrors the exact same camelCase property names that web browsers have used natively for decades.

| :--- | :--- | :--- | :--- |

To see how these principles operate under the hood, examine the transpiled JavaScript output emitted by the compiler. When build tools transform JSX, every expression inside curly braces becomes an argument in a standard `_jsx()` call:

```js title="Transpiled Expression Output"
import { jsx as _jsx, jsxs as _jsxs } from 'react/jsx-runtime'; // Imports runtime **FUNCTIONS**
const output = _jsxs("article", { // Evaluates root article **CONTAINER**
  className: "dispatch-card",
  children: [
    _jsx("h2", { children: headline }), // Passes variable as child **VALUE**
    _jsx("img", { src: avatarUrl }), // Assigns variable to src **PROPERTY**
    _jsxs("p", { children: [readTime, " min"] }) // Evaluates static and dynamic **CHILDREN**
  ]
});
```

> [!TIP]
> **To impress the interviewer:** Avoid saying "React doesn't support if statements." The authoritative answer is rooted in **ECMAScript argument grammar**. JSX compiles into JavaScript function calls (`_jsx()`). In JavaScript, function arguments must be expressions evaluating to a value. An `if` block is a control-flow statement producing no value. This makes it illegal as a function argument. Use value-producing expressions like ternary operators (`condition ? a : b`) instead.

### Step 1: First, we construct the news dispatch card with inline expressions <DispatchCard.jsx>

In Step 1, we build the presentation card component `DispatchCard.jsx`. On The National Times, breaking dispatches require live data. They display a headline, reporter photo, and reading time. In traditional templates, developers had to concatenate strings or perform manual DOM selections. In React, we declare local variables in the component body. We cleanly project them into markup using curly braces. Here we reach a foundational architectural crossroad when binding attributes:

When passing values to JSX attributes, developers choose between two syntax approaches:
- **Option 1 (The Foundational Way: Static String Attribute)**: Wrap the attribute value in double quotes (`src="avatarUrl"`), treating the value as a literal string.
- **Option 2 (The Modern Idiomatic Way: Dynamic Expression Window)**: Supply the attribute value in naked curly braces (`src={avatarUrl}`), evaluating the variable reference in memory.

First, examine Option 1 with a static string attribute:

```jsx title="Option 1: The Foundational Way (src='avatarUrl')"
export default function DispatchCard() {
  const avatarUrl = "/photos/clara.jpg"; // Local avatar **PATH**
  return (
    <article className="dispatch-card">
      <img src="avatarUrl" /> // **WRONG:** requests path **AVATARURL**
    </article>
  );
}
```

In Option 1, wrapping `"avatarUrl"` in double quotes tells the JSX compiler to emit a static string primitive. When the browser renders the `<img>` tag, its network engine requests the literal endpoint `http://localhost:5173/avatarUrl`. The file does not exist on disk, resulting in a 404 network failure and a broken image icon on the front page.

Next, examine Option 2 using the modern idiomatic dynamic expression window:

```jsx title="Option 2: The Modern Idiomatic Way (src={avatarUrl})"
export default function DispatchCard() {
  const avatarUrl = "/photos/clara.jpg"; // Local reporter photo **PATH**
  return (
    <article className="dispatch-card">
      <img src={avatarUrl} /> // Binds dynamic image source from **MEMORY**
    </article>
  );
}
```

In Option 2, writing `src={avatarUrl}` omits the quotation marks and opens an evaluation window. The compiler reads the identifier `avatarUrl` from local scope and assigns the string `"/photos/clara.jpg"` directly to the DOM node's `src` property. The browser fetches the reporter's photograph seamlessly.

Now, examine the first half of `DispatchCard.jsx`, establishing local variables and evaluating the headline and urgency badge:

```jsx title="DispatchCard.jsx" startLine="1" continues="bottom"
export default function DispatchCard() {
  const headline = "Transit Union Approves Contract"; // Story headline **STRING**
  const reporter = "Clara Foster"; // Reporter byline **NAME**
  const avatarUrl = "/photos/clara.jpg"; // Reporter photo endpoint **URL**
  const isUrgent = true; // Breaking dispatch urgency **FLAG**
  return (
    <article className="dispatch-card">
      <span className="badge">{isUrgent ? "URGENT" : "STANDARD"}</span> // Evaluates conditional ternary **BADGE**
      <h2 className="headline">{headline}</h2> // Projects headline variable into **HEADING**
```

Notice how `{isUrgent ? "URGENT" : "STANDARD"}` evaluates a ternary expression directly inside the badge. When `isUrgent` is `true`, it resolves to the string `"URGENT"`. Directly beneath, `{headline}` reads the article title from memory.

Next, examine the conclusion of `DispatchCard.jsx`, binding the dynamic image attribute and calculating reading duration:

```jsx title="DispatchCard.jsx" startLine="10" continues="top"
      <div className="meta">
        <img src={avatarUrl} alt={reporter} /> // Binds dynamic image and alt **PROPERTIES**
        <span>{reporter} • 4 min</span> // Interpolates reporter name and duration **TEXT**
      </div>
    </article>
  );
}
```

The component concludes by passing `avatarUrl` into `src` using naked curly braces. React passes the image URL directly into the DOM element property, rendering the portrait without network errors.

### Step 2: Finally, we mount the dispatch card into the page container <App.jsx>

In Step 2, we complete the practical example by mounting `DispatchCard` inside the top-level application container `App.jsx`. The root component establishes the newsroom page shell using `<main className="page-shell">` and an application masthead header `<h1>`. By mounting `<DispatchCard />` declaratively inside `App`, we keep the page container lean and focused on layout, while `DispatchCard` cleanly encapsulates its local variables and dynamic evaluation logic.

```jsx title="App.jsx"
import DispatchCard from './components/DispatchCard.jsx'; // Imports dispatch card **COMPONENT**
export default function App() {
  return (
    <main className="page-shell">
      <h1>The National Times</h1> // Renders newsroom layout **MASTHEAD**
      <DispatchCard /> // Mounts evaluated dispatch presentation **CARD**
    </main>
  );
}
```

By separating `DispatchCard` from `App`, we maintain a clean architectural boundary. `App` manages the top-level semantic structure of the document, while `DispatchCard` manages its internal dynamic expressions.

### Component Summary

```component-code title="Summary: The Logic of Nested Components"
App.jsx | none | parent | [role: The **root application component** establishes the top-level semantic document container. It renders the site header masthead and declares the layout shell. What is its structural role? It provides a stable page layout boundary while delegating card content entirely to the child component.]
  DispatchCard.jsx | none | child | [role: This is the **presentation component**. It declares local story variables and cleanly projects them into text, attributes, and ternary conditions using **curly braces (`{}`)**. What makes this essential? ```
```

In legacy web applications, populating dynamic headlines and author photos required manual DOM queries (`document.querySelector('.headline').textContent = ...`). That manual pipeline was fragile: renaming an element ID broke the script silently. In React, curly braces `{}` establish a declarative bridge. The component describes the target markup, and React evaluates the local JavaScript variables directly into the element tree. The browser receives clean, accurate DOM nodes with zero manual string manipulation.

### Where you will meet this

1. **Dynamic Content Cards and Editorial Feeds**: Online news portals like The National Times project headlines, reporter names, publication dates, and category tags directly into article cards using curly braces, eliminating manual string assembly.
2. **Media Players and Image Galleries**: Binding dynamic media URLs to `src`, `poster`, and `href` attributes requires naked curly braces (`src={videoUrl}`) to prevent the browser from requesting literal placeholder strings.
3. **Calculated Metrics and Live Analytics**: Dashboards evaluate mathematical expressions directly inside JSX (such as `{activeReaders * 100 / totalSubscribers}%`) to compute and display formatted metrics in real time without intermediate state variables.

### Glossary

- **Evaluation Window**: An inline JavaScript portal established by curly braces (`{}`) inside JSX that steps out of static markup to evaluate live expressions.
- **JavaScript Expression**: Any unit of code that evaluates to a single discrete value in memory (such as variables, math, ternary operations, and function calls).
- **Control-Flow Statement**: Imperative JavaScript language constructs (like `if`, `for`, or `while`) that execute actions without returning a value, strictly forbidden inside JSX curly braces.
- **Dynamic JSX Attribute**: An HTML-like element property bound to a live JavaScript expression using naked curly braces without quotes (`src={avatarUrl}`).
- **Primitive Render Matrix**: React's internal type-resolution rules that paint numbers and strings to the DOM while rendering booleans, `null`, and `undefined` as invisible empty output.
- **Double Curlicues**: The syntax pattern `{{ ... }}` used in JSX where an outer evaluation window encloses an inner JavaScript object literal.

### Summary

**JavaScript Expressions in JSX Decision Matrix**

❒ Text and Variable Interpolation

➔ ALWAYS enclose JavaScript variables in curly braces (`<h2>{headline}</h2>`) to project evaluated runtime values into the rendered DOM.

➔ NEVER write bare variable names inside tag children (`<h2>headline</h2>`), which causes the browser to display literal placeholder text.

❒ Dynamic Attribute Binding

➔ ALWAYS use naked curly braces without quotes (`src={avatarUrl}`) when binding dynamic variables to HTML attributes.

➔ NEVER enclose curly braces in quotation marks (`src="{avatarUrl}"`), which instructs the compiler to treat the expression as a literal string.

❒ Expressions vs Statements

➔ ALWAYS use value-producing expressions (such as ternary operators `{isUrgent ? 'A' : 'B'}`) inside curly braces.

➔ NEVER place control-flow statements (`if`, `for`, `while`) inside JSX curly braces, which triggers fatal compiler syntax crashes.

**DO THIS:** Evaluate expressions with curly braces and bind naked attributes

```jsx right
export default function DispatchCard() {
  const headline = "Transit Union Approves Contract";
  const avatarUrl = "/photos/clara.jpg";
  return (
    <article className="dispatch-card">
      <h2>{headline}</h2>
      <img src={avatarUrl} alt="Reporter" />
    </article>
  );
}
```

**DO NOT DO THIS:** Write literal variable names or quote dynamic attribute curlicues

```jsx wrong
export default function DispatchCard() {
  const headline = "Transit Union Approves Contract";
  const avatarUrl = "/photos/clara.jpg";
  return (
    <article className="dispatch-card">
      <h2>headline</h2>
      <img src="avatarUrl" alt="Reporter" />
    </article>
  );
}
```

| ---: | :--- | :--- |
| **Text Interpolation** | Writes literal characters:<br>`<h2>headline</h2>` | Evaluates identifier in memory:<br>`<h2>{headline}</h2>` |
| **Attribute Binding** | Raw string literal:<br>`src="avatarUrl"` | Living variable reference:<br>`src={avatarUrl}` |
| **Accepted Grammar** | Raw text tokens and XML tags | Any value-producing expression:<br>ternary, math, template literal |
| **Forbidden Grammar** | Unclosed XML tags | Control-flow statements:<br>`if`, `for`, `while`, `switch` |
| **Boolean Output** | Prints literal string:<br>`"true"` or `"false"` | Invisible visual value:<br>emits zero nodes to the DOM |
| **Under the Hood** | Emits static string argument:<br>`_jsx("h2",`<br>`{ children:`<br>`"headline" })` | Emits runtime variable argument:<br>`_jsx("h2",`<br>`{ children:`<br>`headline })` |
