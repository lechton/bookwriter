# Lecture 34: Catching Type and Lint Errors with svelte-check
> INTERVIEW QUESTION | ❱ CORE | How do you check your Svelte project for type and lint errors before shipping?

1. A web developer prepares to send tonight's new National Times edition to the production web servers.
2. The article card now requires a numeric identification number, because the database rejects text identifiers.
3. The developer updates the front page, but an untouched archive page still passes text identifiers to the card.
4. Why did it pass?
5. The local development server compiles without complaint, but the archive page crashes when readers click old stories.
6. Your code editor, the program, only verifies tabs open on your screen, leaving closed components completely uninspected.
7. Today your workflow gains one command that audits every component, script, and stylesheet across your entire project.

### The Trap of the Clean Screen

During local development, your application feels completely solid. When you run your local development server with Vite, Svelte transforms files on the fly as your browser navigates the site (see Lecture 2). Vite optimizes aggressively for speed, so it compiles only the components needed to render the exact page open in your browser window. If you spend the afternoon polishing the home page, an archive page located three directories away is never compiled, never evaluated, and never checked.

At the same time, your code editor, the program running on your computer such as Visual Studio Code, provides real-time diagnostics through the Svelte extension. As we saw when adding TypeScript to a component with the `lang="ts"` attribute (see Lecture 22), the editor highlights typos and mismatched types with immediate red squiggles. But code editors face strict memory limits. To keep your computer fast, language tools prioritize active tabs. They thoroughly inspect the files currently visible on your screen, but they do not continuously scan every unopened file across a project containing hundreds of components.

This creates a dangerous blind spot. Suppose you refactor the newsroom's article card component. You convert its properties to TypeScript, requiring every story to provide a numeric identification code for database queries. You update the home page to pass numbers, and your editor shows zero errors. But an old archive page, closed and untouched for months, still passes a string. The local development server does not crash because you never visited the archive route today. The editor does not complain because the archive tab is closed. If you bundle the code and deploy it to production servers, the archive page crashes the moment a reader opens it tonight.

Before inspecting the solution, examine the two components that create this conflict. `ArchiveGrid.svelte` serves as the container shell that renders historical news dispatches, while `ArticleCard.svelte` renders an individual story card on the screen.

```components title="national-times — Component Explorer"
ArchiveGrid.svelte | renders historical news dispatches | shell
  ArticleCard.svelte | displays single dispatch card | card | Story #**104**;; Harbor Strike
```

Here is `ArticleCard.svelte`. It defines a strict TypeScript interface for its incoming properties using `$props()`, Svelte's rune for receiving data from parent components (see Lecture 9 and Lecture 22). Notice also that its style block contains a leftover `.author-tag` rule from an earlier revision, an unused selector, meaning a CSS rule whose corresponding HTML class was removed from the markup (see Lecture 17).

```svelte title="ArticleCard.svelte"
<script lang="ts">
  interface Props {
    id: number; // **RIGHT:** Strictly typed **NUMERIC** identifier for database queries.
    title: string;
  }

  let { id, title }: Props = $props();
</script>

<article class="card">
  <h3>Story #{id}</h3>
  <p>{title}</p>
</article>

<style>
  .card {
    border: 1px solid #e2e8f0;
    padding: 1rem;
  }
  .author-tag { // **WRONG:** Leftover **UNUSED** selector; Svelte compiler flags this warning.
    color: #64748b;
  }
</style>
```

Next, look at `ArchiveGrid.svelte`. It imports `ArticleCard.svelte` to display past reporting. The first story passes a valid number, but the second story passes a string, directly violating the component contract.

```svelte title="ArchiveGrid.svelte"
<script lang="ts">
  import ArticleCard from './ArticleCard.svelte';
</script>

<section class="archive-grid">
  <h2>Historical Dispatches</h2>
  <ArticleCard id={104} title="Harbor Strike" />
  <ArticleCard id="old-88" title="City Hall Protest" /> <!-- **WRONG:** Passing text **VIOLATES** the numeric prop contract. -->
</section>
```

### Why the TypeScript Compiler Cannot Save You

When developers realize that closed tabs hide type errors, their first instinct is to reach for the standard TypeScript compiler by running `tsc --noEmit` on the command line. But running the standard TypeScript compiler on a Svelte codebase immediately hits a structural wall: TypeScript does not understand `.svelte` files. The standard compiler knows how to parse plain `.ts` and `.js` files, but it has no parser for Svelte's single-file components. If you point `tsc` at your project, it completely ignores the template markup, knows nothing about `$props()` or `$state()`, and cannot verify whether a parent component passed the correct properties to a child.

To bridge this divide, the Svelte core team created a dedicated command-line tool: `svelte-check`. This tool acts as a headless diagnostics engine, meaning a program that inspects code from the terminal without opening a graphical window, tailored specifically to Svelte architecture. Under the hood, `svelte-check` loads the Svelte compiler alongside TypeScript's language services. It converts every `.svelte` component into a virtual TypeScript representation, analyzing the script logic, the template markup expressions, the component properties, and even the CSS stylesheet rules in a single comprehensive pass across your entire repository.

You run `svelte-check` directly from your project root using the Node package executor.

```sh title="Terminal"
npx svelte-check --tsconfig ./tsconfig.json // **RIGHT:** Audits **ALL** components across the entire repository.
```

When you execute this command against our newsroom project, `svelte-check` scours every folder and prints precise diagnostics directly to the terminal console. It does not matter whether `ArchiveGrid.svelte` was open in your editor or whether you visited its route in your browser. The tool scans every file on disk and catches both flaws immediately:

```txt title="Terminal"
ArchiveGrid.svelte:8:16
Error: Type 'string' is not assignable to type 'number'. (ts)
<ArticleCard id="old-88" title="City Hall Protest" />

ArticleCard.svelte:17:3
Warning: Unused CSS selector ".author-tag" (svelte)
.author-tag {
```

Look at what `svelte-check` accomplished. First, it identified the type mismatch on line 8 of `ArchiveGrid.svelte`, catching the broken contract before any human user could trigger it in production. Second, it acted as a linter, a software tool that inspects code for stylistic flaws and dead rules, by catching the dead `.author-tag` rule in `ArticleCard.svelte`. Svelte's scoped CSS compiler flags unused selectors as warnings (see Lecture 17), and `svelte-check` surfaces those compiler warnings straight to your terminal output, preventing dead styling bloat from lingering in your shipped CSS bundles.

### Automating Verification with npm run check

Running a command manually is useful, but human memory is fallible. A developer rushing to meet an evening deadline might forget to run the check before pushing their Git commit. The professional standard is to embed project verification directly into your team's automated build and deployment pipelines.

When you scaffold a new Svelte or SvelteKit application using `sv create` (see Lecture 2), the project generator automatically configures a `check` script inside your `package.json` file.

```json title="package.json"
{
  "scripts": {
    "dev": "vite dev",
    "build": "vite build",
    "check": "svelte-kit sync && svelte-check --tsconfig ./tsconfig.json" // **RIGHT:** Prepares route types and **AUDITS** the codebase.
  }
}
```

Notice the prefix command: `svelte-kit sync`. In SvelteKit applications, routing and server load functions rely on generated TypeScript definitions, such as `PageData` and route parameter types. Running `svelte-kit sync` generates these auxiliary type files inside the `.svelte-kit` directory before `svelte-check` begins its inspection, ensuring that all route-level contracts are completely up to date. In a standalone Svelte project without SvelteKit, the command simply runs `svelte-check --tsconfig ./tsconfig.json`.

The true power of `svelte-check` lies in its operating system exit codes. An exit code is a numeric status returned by a terminal program when it completes, telling the operating system whether the command succeeded. When `svelte-check` finishes with zero errors, it exits with status code 0, signaling total success. But if it discovers even one type mismatch or syntax defect, it exits with a non-zero status code, typically code 1.

Continuous Integration, an automated server pipeline that builds and tests code on every Git push, monitors these exit codes. By adding `npm run check` as a mandatory gate before `npm run build` in your deployment workflow, any branch containing a broken component contract automatically fails the build. The deployment halts instantly, the team receives an alert, and broken code is physically blocked from reaching your production servers.

> [!TIP]
> **To impress the interviewer:** Explain that `tsc` cannot inspect Svelte components directly because it does not understand single-file component syntax or Svelte template expressions. Emphasize that `svelte-check` bridges this gap by leveraging the Svelte compiler and TypeScript language server to evaluate virtual representations of components, catching both type mismatches and compiler warnings like unused CSS selectors or accessibility violations. In SvelteKit environments, always highlight that running `svelte-kit sync` prior to `svelte-check` is essential to synchronize generated route types before running project-wide diagnostics.

> [!KEY]
> Code editors only verify the files currently open on your screen, but svelte-check audits every component contract, script, and stylesheet across your entire repository in a single automated pass.

### Tuning the Auditor: Strict Hygiene and Watch Mode

As your project grows, you can customize `svelte-check` with command-line flags to enforce stricter quality standards across your engineering team. By default, `svelte-check` reports warnings, such as unused CSS selectors or accessibility warnings like missing image alternative text, but does not cause the command to fail if only warnings are present. If you want zero tolerance for sloppy code, you pass the `--fail-on-warnings` flag.

```sh title="Terminal"
npx svelte-check --tsconfig ./tsconfig.json --fail-on-warnings // **RIGHT:** Treats compiler warnings as fatal **ERRORS**.
```

With `--fail-on-warnings` enabled, the leftover `.author-tag` rule in `ArticleCard.svelte` causes the command to exit with status code 1. This forces developers to clean up orphaned style rules and fix accessibility tags before their pull requests can merge, keeping the application clean and accessible for all users.

Another powerful option during active development is the `--watch` flag. Instead of running once and exiting, `svelte-check --watch` remains active in your terminal, continuously monitoring the file system. Whenever you save a file in any folder, it re-runs its diagnostic pass in seconds. Keeping a dedicated terminal pane open with watch mode gives you the global safety of whole-project checking alongside the blazing local speed of Vite.

### Where you will meet this

- The National Times deployment pipeline runs `npm run check` before bundling assets, preventing unvisited archive pages from crashing in front of evening readers.
- An e-commerce team refactors a product checkout callback prop, and `svelte-check` immediately flags four secondary promotional pages that still pass outdated arguments.

### Summary

`svelte-check` is the essential command-line diagnostic tool that brings project-wide type checking and compiler linting to Svelte applications. While local development tools and editor extensions prioritize active tabs for speed, `svelte-check` audits every `.svelte`, `.ts`, and `.js` file across your entire codebase in a single headless pass. By integrating `npm run check` into Continuous Integration pipelines, engineering teams catch broken component contracts, unused CSS selectors, and accessibility defects before code reaches production servers.

- Your code editor and development server only check active tabs and visited pages, leaving closed files unverified.
- The standard TypeScript compiler `tsc` cannot parse `.svelte` template syntax, single-file components, or Svelte runes.
- `svelte-check` analyzes all components, TypeScript files, and stylesheets across the entire repository from the command line.
- The tool reports both hard TypeScript type errors and Svelte compiler warnings, including unused CSS and accessibility issues.
- Adding `--fail-on-warnings` turns compiler warnings into fatal errors, enforcing strict quality standards in CI pipelines.
- Standard projects run `npm run check`, while SvelteKit projects use `svelte-kit sync && svelte-check` to synchronize route types first.
