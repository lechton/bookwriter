# Lecture 30: Raw HTML Injection
> INTERVIEW QUESTION | ❱ CORE | How do you render raw HTML from a string, and what's the danger?

1. You fetch a blog post from a headless CMS.
2. The response body is a giant string of paragraph and bold tags.
3. You bind this string inside your template.
4. Svelte prints the literal angle brackets onto the screen.
5. How do you force actual rendering?
6. Furthermore, what happens if that string contains a malicious script tag?
7. You must unlock the HTML parser without destroying the user's security.

### Unlocking the browser parser

When you place a variable into markup, Svelte treats it as raw text by default. This is a critical security feature. If a user enters `<script>stealCookies()</script>` as their profile name, Svelte converts the angle brackets into harmless text entities. The browser renders the text literally and ignores the script.

But sometimes you actually want the browser to parse the markup. When your data source is trusted, like your own database or a vetted markdown renderer, printing raw tags breaks the page. You need a way to bypass Svelte's text encoding and hand the string directly to the browser's HTML parser.

```components title="Raw HTML Injection — Component Explorer"
Article.svelte | | generic | **Hello**;; Welcome to my blog.
```

To tell Svelte that a string is safe to parse, you wrap the expression in a special tag.

```svelte title="Article.svelte"
<script>
  let content = "<h1>Hello</h1><p>Welcome to my blog.</p>";
</script>

<article>
  {content} // **WRONG:** Prints literal brackets to the screen.
  {@html content} // **RIGHT:** Renders a heading and a paragraph.
</article>
```

The syntax drops the string blindly into the DOM. Svelte does not sanitize the input, and it does not check for missing closing tags. If the string contains a script tag, the browser will execute it immediately.

### The cross-site scripting danger

Because the framework skips all safety checks, rendering unverified user input creates a severe vulnerability. This is called Cross-Site Scripting (XSS). An attacker can submit a comment containing a malicious script, and if you render it directly, that script runs in the browser of every person who reads the comment.

> [!TIP]
> **To impress the interviewer:** Mention that you should always sanitize untrusted HTML on the server before it reaches the client, using a robust library like DOMPurify. Never rely solely on client-side sanitization.

If you absolutely must render user-provided HTML, you have to clean it first.

```svelte title="Article.svelte"
<script>
  // Assume DOMPurify is imported and available
  import DOMPurify from 'isomorphic-dompurify';

  let untrustedInput = "<img src=x onerror=alert('hacked') />";
  let safeContent = DOMPurify.sanitize(untrustedInput);
</script>

<div>
  {@html untrustedInput} // **WRONG:** Executes the alert script.
  {@html safeContent} // **RIGHT:** Strips the dangerous attributes first.
</div>
```

### Summary

Svelte protects you by encoding text automatically, but sometimes you need to render actual tags. You can bypass this protection intentionally, but doing so shifts the security responsibility entirely onto you.

- Text bindings escape HTML characters to prevent accidental execution.
- A specific injection tag hands a string directly to the browser parser.
- Svelte performs zero sanitization on injected strings.
- Injecting user-supplied data without sanitization causes XSS vulnerabilities.
- Always scrub untrusted markup using a dedicated library before rendering it.

| ---: | :--- | :--- |
| **Syntax** | `{variable}` | `{@html variable}` |
| **Parsing** | Escaped as plain text | Parsed as DOM nodes |
| **Security** | Safe by default | Dangerous with untrusted data |
| **Use case** | User names and comments | Trusted CMS article bodies |
