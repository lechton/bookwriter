### The Meaning of HTTP Status Codes

Every HTTP response returned by a web server includes a three-digit numeric status code. This status code acts as the universal communication protocol between backends and clients, informing web browsers, mobile applications, reverse proxies, and monitoring dashboards how the server handled the request.

HTTP status codes follow strict semantic categories:
- **2xx (Success)**: indicates that the client request was successfully received, understood, and accepted.
- **4xx (Client Error)**: indicates that the request contains bad syntax, missing fields, or invalid authentication.
- **5xx (Server Error)**: indicates that the server encountered an unexpected error while processing a valid request.

In NestJS, standard response handling applies sensible default status codes out of the box. Any route decorated with `@Get()`, `@Put()`, `@Patch()`, or `@Delete()` returns an HTTP status of **200 OK** by default. Route handlers decorated with `@Post()` return an HTTP status of **201 Created** by default.

These framework defaults cover standard CRUD operations, but real-world architectures require finer precision. For example, queuing a long-running background export should return **202 Accepted**, permanently deleting an article should return **204 No Content**, and rejecting an invalid form requires returning **400 Bad Request**.

In traditional Express applications, developers manually set status codes by calling library-specific methods on the response stream:

```typescript title="Express Status Call"
import { Request, Response } from 'express';

export function submitTipHandler(req: Request, res: Response) {
  if (!req.body.content) {
    res.status(400).json({ error: 'Content required' }); // **WRONG:** imperatively calls library-specific status **METHOD**
    return;
  }
  res.status(202).json({ status: 'Queued' }); // **WRONG:** ties handler directly to platform **RESPONSE**
}
```

This manual style introduces drawbacks: injecting the raw response object disables NestJS interceptors, breaks portability across alternate engines like Fastify, and mixes low-level transport commands into high-level business logic.

### The HttpCode Decorator and HttpStatus Enum

To declare custom HTTP status codes cleanly without dropping into low-level response objects, NestJS provides the **`@HttpCode()` decorator** (a method decorator that overrides framework defaults and assigns a specific HTTP status code to successful responses).

Along with `@HttpCode()`, NestJS provides the **`HttpStatus` enum** (a standardized TypeScript enumeration exported from `@nestjs/common` that maps human-readable status names to their official HTTP numeric values).

Instead of hardcoding raw numeric constants like `@HttpCode(202)`, using `@HttpCode(HttpStatus.ACCEPTED)` makes your code self-documenting, readable, and resilient against typos.

To see this in action on The National Times, our investigative tip intake system coordinates three files. First, `submit-tip.dto.ts` defines the tip submission payload. Second, `tips.controller.ts` exposes `POST /tips` decorated with `@HttpCode(HttpStatus.ACCEPTED)` to signal that the tip was accepted and queued for editorial investigation. Third, `app.module.ts` registers the controller into the application module tree.

```components title="national-times-api — Component Explorer"

  tips.controller.ts | POST /tips | navigation
    submit-tip.dto.ts | whistleblower payload | form | {"content": "Budget discrepancy in City Council"};; Status: **202 Accepted**
```

The component explorer panel above displays this architecture. In the left file tree, `submit-tip.dto.ts` resides in `src/`, `tips.controller.ts` in `controllers/`, and `app.module.ts` in `modules/`. On the right canvas, `app.module.ts` mounts `tips.controller.ts`, which nests `submit-tip.dto.ts`. Here is `submit-tip.dto.ts` defining the payload shape:

```ts title="submit-tip.dto.ts"
export class SubmitTipDto {
  content: string; // **RIGHT:** declares tip message property on runtime **DTO**
}
```

Here is `tips.controller.ts` applying `@HttpCode()`:

```ts title="tips.controller.ts"
import { Controller, Post, Body, HttpCode, HttpStatus } from '@nestjs/common';
import { SubmitTipDto } from './submit-tip.dto';

@Controller('tips')
export class TipsController {
  @Post()
  @HttpCode(HttpStatus.ACCEPTED)
  submit(@Body() submitTipDto: SubmitTipDto) {
    return {
      status: 'Queued for editorial review',
      receivedAt: '2026-09-10T04:00:00Z',
    }; // **RIGHT:** returns 202 status indicating background **PROCESSING**
  }
}
```

And here is `app.module.ts` registering the controller:

```ts title="app.module.ts"
import { Module } from '@nestjs/common';
import { TipsController } from './tips.controller';

@Module({
  controllers: [TipsController], // **RIGHT:** mounts tips controller to expose custom **STATUS**
})
export class AppModule {}
```

### Success Status Overrides versus Exception Throwing

A critical distinction in NestJS architecture is knowing when to use `@HttpCode()` and when to throw an HTTP Exception.

The `@HttpCode()` decorator is designed specifically for successful execution paths. When your controller method completes its logic normally and returns a value, NestJS stamps the response with the status code declared in `@HttpCode()`.

However, if a submission is invalid, such as our opening scenario where a reader submits a blank form, you should not attempt to return a 400 status through `@HttpCode()`. Using `@HttpCode(400)` on a method means the method will return 400 even when valid data is submitted.

For error conditions, the idiomatic NestJS pattern is to throw an **`HttpException`** (a built-in framework error class that halts execution and instructs the exception layer to return a specific HTTP error status).

NestJS exports pre-built exceptions for common HTTP errors, including `BadRequestException` (400), `UnauthorizedException` (401), `ForbiddenException` (403), and `NotFoundException` (404):

```typescript title="Throwing Validation Exceptions"
import { BadRequestException } from '@nestjs/common';

if (!submitTipDto.content) {
  throw new BadRequestException('Tip content must not be blank'); // **RIGHT:** halts execution and produces 400 **JSON**
}
```

When you throw `BadRequestException`, NestJS halts handler execution immediately and delegates to the global exception layer. The server returns an HTTP 400 Bad Request status with a standardized JSON error envelope: `{"statusCode": 400, "message": "Tip content must not be blank", "error": "Bad Request"}`. This prevents the frontend from displaying an incorrect success message.

### Common Status Code Patterns in Production

When designing production APIs for The National Times, four status patterns appear constantly:

1. **`HttpStatus.OK` (200)**: The universal standard for successful data retrieval, updates, and non-creation mutations.
2. **`HttpStatus.CREATED` (201)**: The default for `@Post()` handlers. Signals that a new database record or resource was successfully minted.
3. **`HttpStatus.ACCEPTED` (202)**: Used when an operation has been accepted into a processing queue, but computation or validation will finish asynchronously in the background.
4. **`HttpStatus.NO_CONTENT` (204)**: Standard for successful deletion endpoints. When you apply `@HttpCode(HttpStatus.NO_CONTENT)`, HTTP protocol rules dictate that no response body can be transmitted. Any return value from the controller method is discarded.

> [!KEY]
> Use @HttpCode() with the HttpStatus enum to override default success status codes declaratively without sacrificing NestJS response lifecycle features.

> [!TIP]
> **To impress the interviewer:** Distinguish between when to use `@HttpCode()` and when to throw an `HttpException`. Use `@HttpCode()` (such as `@HttpCode(HttpStatus.NO_CONTENT)` or `HttpStatus.ACCEPTED`) when an operation completes successfully on its intended path. Use NestJS built-in exceptions (such as `throw new BadRequestException()` or `NotFoundException()`) for client and server error states, allowing global exception filters to format uniform error envelopes.

### Where you will meet this

- Background report generation: returning `202 Accepted` when queuing a long-running PDF export of reader archives.
- Editorial deletion endpoints: applying `204 No Content` to `DELETE /articles/:id` when a draft is permanently purged.
- Form validation failures: throwing `BadRequestException` (400) when a subscriber signup form omits mandatory fields.
- Third-party webhook acknowledgments: replying with `200 OK` to payment gateway webhooks after receiving subscription events.

### Summary

**Custom HTTP Status Codes and Semantic Outcomes**

In daily production, delivering semantically accurate HTTP status codes ensures that client applications, reverse proxies, and monitoring systems interpret backend outcomes correctly. While procedural code relies on low-level response methods, NestJS pairs the `@HttpCode()` decorator with the `HttpStatus` enum for declarative status management. Here is your streetwise review.

❒ Declarative Status Overrides with HttpCode

1. Avoid **manually injecting response objects solely to change success status codes**.<br>&nbsp;&nbsp;&nbsp;&nbsp;**DO NOT DO THIS:** Injecting `@Res()` to call `res.status()` couples your route handler directly to the underlying HTTP server.
```typescript wrong
@Post()
create(@Res() res: any) {
  res.status(202).json({ ok: true });
}
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Use the `@HttpCode()` decorator paired with the `HttpStatus` enum.
```typescript right
@Post()
@HttpCode(HttpStatus.ACCEPTED)
create() {
  return { ok: true };
}
```
2. Use **204 No Content for deletion endpoints** that return empty bodies.<br>&nbsp;&nbsp;&nbsp;&nbsp;**DO NOT DO THIS:** Returning empty objects with 200 OK status codes wastes bandwidth and ignores HTTP semantics.
```typescript wrong
@Delete(':id')
remove(@Param('id') id: string) {
  return {};
}
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Declare `@HttpCode(HttpStatus.NO_CONTENT)` to communicate successful deletion cleanly.
```typescript right
@Delete(':id')
@HttpCode(HttpStatus.NO_CONTENT)
remove(@Param('id') id: string) {
  return;
}
```

❒ Success Statuses versus Exception Handling

1. Distinguish between **successful completion overrides and error state exceptions**.<br>&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Throw built-in HTTP exceptions for validation errors rather than returning error objects manually.
```typescript right
if (!payload.text) {
  throw new BadRequestException('Text required');
}
```

➔ NEVER use `@HttpCode()` on a controller method to handle client error conditions.

➔ ALWAYS use the `HttpStatus` enum instead of raw numbers to enhance readability and prevent typos.

➔ IF an action runs asynchronously in the background THEN **return `HttpStatus.ACCEPTED` (202)**.
