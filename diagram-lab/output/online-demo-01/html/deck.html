Answer. In Svelte 3 and 4, reactivity is driven strictly by variable assignment (=). Reactive Statements

State (Legacy)

Question. What is the purpose and syntactic structure of the $: labeled statement in Svelte 3/4?

Answer. In Svelte 3 and 4, the $: prefix (which utilizes standard JavaScript label syntax) is used to construct reactive statements and reactive declarations. The compiler automatically analyzes the code following the label, infers the local variables acting as dependencies, and instruments the compiled output to re-execute that specific block of code whenever those dependencies change. A reactive declaration defines a new variable (e.g., $: x = y * 2), while a reactive statement runs arbitrary side-effects without variable declaration (e.g., $: console.log(y)).

Summary. The $: label marks code that should automatically re-run. Svelte handles the dependency tracking statically during compilation, meaning any referenced local reactive variables will automatically trigger the statement when updated.

Question. How does the Svelte compiler automatically infer dependencies for a legacy $: reactive statement?

Answer. In legacy Svelte (v3/v4), the compiler acts as a static analysis tool. When it encounters the $: label, it parses the trailing expression into an Abstract Syntax Tree (AST). Q33

Introduction to Runes

Svelte 5RunesArchitecture

Question. What are Svelte 5 Runes, and what specific architectural limitations of legacy reactivity do they address?

Answer. Svelte 5 Runes are explicitly declared, fine-grained reactive primitives (such as $state, $derived, and $effect). They replace the legacy component-level reactivity system to address three major architectural limitations: 1. Universal State: Legacy reactivity was strictly bound to .svelte files. Runes can be declared in raw .svelte.js or .ts files, making it effortless to share state across the entire application without using stores. 2. Explicit Deep Reactivity: Legacy Svelte relied on the assignment operator (=) to trigger updates, which caused confusion when mutating nested arrays or objects. Runes use an explicit Proxy-based signal system, so deep object mutations trigger updates automatically. 3. Fine-Grained DOM Updates: Legacy reactivity dirty-checked the entire component on every state change. Runes use a signal graph to pinpoint exact DOM nodes that depend on the state, bypassing component-level checks and vastly improving performance.

Summary. Runes untangle reactivity from the .svelte component boundary. They offer explicit, deeply reactive, and surgically fine-grained state management that scales gracefully into large codebases.

Q36

$state.frozen / $state.raw: Opting Out of Deep Reactivity

Svelte 5Runes$state.rawPerformance

Question. What is the $state.frozen rune, and in what scenarios should it be chosen over standard $state?

Answer. The rune that was prototyped as $state.frozen shipped in Svelte 5 as **$state.raw*. It declares reactive state that Svelte does not* wrap in a deep Proxy: assignment to the variable itself is reactive (config = newConfig triggers updates), but mutating a nested property (config.theme = 'dark') is silent — there is no proxy to detect it, so no update fires.

Use it whenever you hold read-mostly structured data that you replace wholesale instead of mutate in place: configuration objects, look-up tables, parsed fixtures, feature flags, immutable shapes received from a store. The payoff is concrete: Svelte skips the per-property proxy allocation on every access, so cold reads and initial mount of large objects are cheaper, and you stop paying for fine-grained tracking you never use.

The trap is symmetric: reaching for $state.raw to "optimize" a value you then mutate at depth is the same bug as legacy Svelte's user.age = 31 — the change lands in memory but the UI never hears about it. The rule is prescriptive, not stylistic: deep reactivity is the default because it is always correct; $state.raw is an opt-out you take only when you commit to the replace-don't-mutate discipline for that value.

Summary. $state.raw (the rune prototyped as $state.frozen) is the deliberate off-switch for deep proxying. Choose it for read-mostly structured data that you replace rather than mutate, and leave $state as the default everywhere else — because only the deep variant is correct when you need in-place edits to render.

Q38

$derived.by: The Block-Body Form

Svelte 5Runes$derived.byComputed Values

Question. How does the $derived.by rune differ from a standard $derived expression, and when is it necessary?

Answer. $derived and $derived.by are the same mechanism wearing two syntactic shapes. The plain form $derived(expr) takes a single expression; .by takes a zero-argument function whose body is a block of statements, and returns whatever the block returns. Under the hood they compile to the same memoized, lazily-recomputed, dependency-tracked signal — the dependency tracking, caching, and laziness rules are identical to Q37.

.by is necessary in exactly one situation: when the computation cannot be written as a single expression. The rule is prescriptive, not stylistic — use $derived(expr) whenever you can, and reach for $derived.by(() => { ... }) only when you genuinely need statements. The four common triggers are: a let for an intermediate variable, a for or for...of loop that accumulates a result, a try/catch around something that may throw, or several sequential calculations that read more clearly as steps than as one tangled ternary. If you find yourself writing $derived.by(() => { return expr; }) — a function whose body is just a single return — you have written the wrong form; collapse it back to $derived(expr).

Summary. $derived(expr) and $derived.by(() => { ... }) are the same memoized signal under the hood — .by exists only for computations that need statements (loops, intermediate lets, try/catch, multi-step logic). Reach for plain $derived first; switch to .by only when an expression genuinely cannot carry the work.

Q46

Microtask Batching

Svelte 5ReactivityMicrotaskPerformance

Question. What is the microtask batching mechanism in Svelte, and how does it protect against redundant UI renders?

Answer.

The mechanism — what happens on every write

  • Two-step write: every **$state assignment** (a line like count = 5) does two things in sequence — it stores the new value immediately, and it tells Svelte to schedule one flush later. A flush is Svelte's term for the moment it actually updates the screen.
  • Scheduled, not immediate: that flush is queued on the microtask queue — a built-in JavaScript list of tiny tasks that the browser runs after your current function finishes, but before it paints anything. So if you write to the same variable ten times in a row, all ten writes land before the flush ever runs.
  • What the flush does: Svelte looks at every **$derived value (a computed value that depends on others) whose inputs changed, recomputes only those, and then writes the final values** to the DOM. Intermediate steps are skipped entirely.

The protection — why renders are not redundant

  • One render per tick: a loop calling count += 1 ten times produces one DOM update at the end, not ten. The flush sees the final value of count and acts on that alone.
  • Multiple variables coalesce: if a handler updates several variables at once, each is flagged as changed (Svelte marks "this one's stale, re-check it"), but Svelte processes all of those flags in a single flush that runs once after the handler returns — never one flush per variable.
  • No wasted renders: Svelte never paints an intermediate value that the user would never see, because the screen only updates after the flush.

The rule — what you should and should not do

  • Do not debounce: never reach for **setTimeout or manual batching to combine reactive writes — the runtime already does it**, so adding your own delay just makes the UI feel laggy.
  • **Do await tick() when you need to read the DOM after it has settled** (see Q47). tick() is Svelte's function that returns a Promise resolving once the current flush finishes — the only legitimate reason to wait for a flush.

Summary. Svelte schedules exactly one flush per microtask. Multiple synchronous writes to one or more signals coalesce into a single render of the final state, so intermediate values the user would never see are never written to the DOM. The runtime already batches — do not add manual debouncing on top.

Q47

The tick() Function

Svelte 5ReactivitytickDOM

Question. How do you manually tap into the rendering cycle using Svelte's tick function, and what does it return?

Answer.

**What tick() is and what it returns**

  • Returns a Promise: tick() is a function imported from 'svelte' that returns a Promise — a built-in JavaScript object representing a value that will be available later. You await it inside an async function.
  • Resolves after the flush: the Promise resolves (becomes ready) once the current reactive flush finishes — the flush being Svelte's term for the moment it walks the dirty signals and writes the final values to the DOM (see Q46).
  • No value carried: tick() does not return a value when awaited. It is a synchronization primitive — its job is to give you a moment in time, not data.

Why you need it

  • DOM reads are stale mid-handler: when you write el.scrollTop = 0 right after a state change, the DOM has not updated yet because the flush is scheduled for after your handler returns. Reading el.scrollHeight at that instant returns the old value.
  • **await tick() unblocks the flush: by awaiting the Promise, you yield control back to JavaScript, the microtask queue runs, the flush executes and paints**, and execution resumes with the DOM in its new state.
  • The fix is one line: count += 1; await tick(); console.log(el.scrollHeight); — now the log shows the post-update measurement.

The rules for correct use

  • **Only inside async functions:** await is a JavaScript keyword that only works inside a function declared async. Using await tick() in a synchronous handler is a syntax error.
  • Use sparingly: reach for tick() only when you genuinely need to read or measure the DOM after a state change. Most reactive code never needs it — Svelte's template bindings already reflect new state automatically.
  • Never use it to order side effects: if you need code to run after state settles, prefer **$effect** (see Q20) over manual tick(). tick() answers measurement, $effect answers reaction.

Summary. tick() is imported from 'svelte' and returns a Promise that resolves after the current reactive flush finishes. await it inside an async function when you need to read or measure the DOM after a state change; for everything else, prefer $effect.

Q48

Practical tick() Scenario: Auto-Scrolling a Chat Log

Svelte 5tickDOMscrollPractical

Question. Provide a practical scenario where awaiting tick() is required to read accurate DOM states after a state change.

Answer.

The scenario — a chat log that must auto-scroll to the bottom

  • The feature: a chat component renders an array of messages with {#each}, and every time a new message arrives, the container must scroll to the bottom so the latest message is visible.
  • The measurement: to scroll to the bottom you read **el.scrollHeight (the full height of the content) and assign it to el.scrollTop (the scroll position). This is a DOM read followed by a DOM write** that depends on the read.
  • The trap: calling messages.push(newMsg) dirties state, but the new <li> is not in the DOM yet because the flush is scheduled for after the handler returns (see Q46). Reading scrollHeight at that instant returns the pre-push height — the new message is invisible, and the scroll lands one message short.

**The fix — await tick() between the write and the read**

  • Yield before measuring: insert **await tick()** between the state change and the DOM read. tick() returns a Promise that resolves once the current reactive flush finishes — the flush being Svelte's term for the moment the new <li> is actually written to the DOM.
  • Now the read is accurate: by the time execution resumes, the DOM reflects the new array, so **el.scrollHeight** includes the freshly pushed message, and el.scrollTop = el.scrollHeight lands exactly at the bottom.
  • **The handler must be async:** await only works inside a function declared **async**, so the click/send handler must be async function send() rather than a plain function.

**Why you cannot fake it with setTimeout**

  • **setTimeout(fn, 0) is wrong: it schedules the callback on the macrotask queue, which runs after** rendering — meaning the user sees one frame of the old scroll position before it jumps. tick() resolves on the microtask queue, before paint, so the scroll updates in the same frame as the new message.
  • No debounce either: wrapping the scroll in a timeout adds visible latency that feels broken. tick() adds none — it waits only for the flush that was already going to happen.

Summary. Auto-scrolling a chat log after messages.push(...) requires reading scrollHeight, but the new <li> is not in the DOM until the flush runs. await tick() between the push and the read guarantees the measurement reflects the new state — and unlike setTimeout, it resolves before paint, so there is no visible latency.

Q49

Syncing Local State with a Prop

Svelte 5Runes$state$derivedProps

Question. How do you initialize a reactive local variable that dynamically syncs with an incoming prop using Runes?

Answer.

The two patterns — pick by whether the local copy must be editable

  • **Editable local copy → $state(prop):** declare let local = $state(prop.value) to create a deeply reactive local variable (see Q34) whose initial value is copied from the prop. The user can then mutate local freely — typing into a bound input, toggling, etc.
  • **Read-only mirror → $derived(prop.value):** declare let mirror = $derived(prop.value) to create a memoized computed value (see Q37) that re-evaluates whenever the prop changes. You cannot assign to a $derived — it is a pure function of its inputs.

**Why $state(prop) alone does not sync**

  • One-shot initialization: writing let local = $state(prop.value) copies the prop's value once, at component setup. The $state(...) call runs a single time, so later changes to the prop do not flow into local.
  • The prop is a moving target: props in Svelte 5 are reactive — the parent can pass a new value at any time, and the child sees the update — but $state(initialValue) only reads initialValue at birth.
  • The fix when you need both: to get an editable local copy that also re-syncs when the prop changes, combine the two — declare let local = $state(prop.value) and add a $effect(() => { local = prop.value; }) that watches the prop and overwrites the local copy on change (with care; see Q21 about avoiding effect loops).

The prescriptive rule

  • **Default to $derived: if the local value is a pure transform of the prop (formatting, filtering, computing), reach for $derived** — it is always correct, never goes stale, and costs nothing when nobody reads it.
  • **Reach for $state(prop) only when the child must own its own edits** to the value (form inputs, draft text, in-progress edits). Accept that you then own the synchronization back to the prop.
  • **Avoid the legacy let x = prop:** it neither tracks the prop nor participates in reactivity — a silent source of stale-UI bugs.

Summary. Use $state(prop.value) for an editable local copy initialized once from a prop, and $derived(prop.value) for a read-only computed mirror that re-syncs automatically. $state(prop) alone does not track later prop changes — pair it with a $effect only when you need both editability and continuous sync.
