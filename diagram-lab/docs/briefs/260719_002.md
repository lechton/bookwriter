# Brief 002 — Instruction design for the diagram step: can a model be instructed into creativity?

**Date:** 2026-07-19 · **Scope:** the diagram that follows each code example · **Status:** proposal, with paste-ready instruction block; awaiting bake-off experiment
**Builds on:** `docs/briefs/260719_001.md` (diagnosis: the gap is the brief, not the model)

## 1. The question

Can we write instructions that aid Gemini, or any model, to innovate and be creative in adapting the neo-brutalist style into a different design for every card? And what is the best possible description of the design step?

## 2. Short answer

Yes, but not by asking for creativity. "Be creative" is an exhortation and it already failed: the README told local Gemini to "adapt a creative way to present the topic of each card in a unique diagram" and the result was one repeated skeleton. What works is structured divergence: force the model through a casting step with a menu to choose from, a mapping to verify, a name to commit to, and a default that is explicitly banned. Creativity in models is elicited by task structure, not by adjectives.

## 3. What the lab evidence says

- **Online Gemini innovated** because the brief was scene-shaped: build an app, design a language. It produced named metaphors (The Switch, The Blueprint, The Two-Way Street, The Terminal, The Lifecycle Flow, per `docs/Gemini_instructions.md`).
- **Local Gemini flattened** because the brief was production-shaped: fixed pattern library, deterministic, print constraints, plus one vague "be creative" paragraph. Contradictory instructions resolve toward safety (brief 001, section 5).
- **Exemplars alone cause transcription, not innovation.** Given `docs/demo_diagrams.md` to study, local runs copied its diagrams wholesale into `svelte-demo` 05–18. Imitation is the model's default move; instructions must force a *new* casting per topic, with exemplars as grammar reference only.
- **exp-001 showed the fix works:** naming the metaphor before writing markup ("Dead Wire vs Live Wire", "The Live Feed") produced visibly stronger diagrams on the first build, same constraints, same pipeline.

## 4. The design step, described

The design step is **casting a metaphor, not drawing a diagram.** Concretely: map the card's mechanism onto a scene the reader already knows from real life, verify the mapping is complete, then let the scene dictate the markup. The neo-brutalist grammar (borders, chips, hard shadows, dashed vs solid) stays fixed; the scene is the variable. Creativity here is semantic, not decorative: the goal is a layout whose structure mirrors the mental model of the code ("Semantic Layouts", `docs/Gemini_instructions.md`), never more ornament ("Function Dictates Form", same source).

The step in six moves:

1. **MECHANISM** — one plain sentence stating what the code does, no framework jargon. ("One source updates many subscribers.")
2. **CAST** — three candidate real-world scenes, each from a different family: flow (wires, pipes, roads), container (vault, zone, room), comparison (old vs new, before vs after), machine (factory, stamp, engine), social (courtroom, newsroom, checkpoint).
3. **MAP** — for the strongest candidate, write the isomorphism: every code element equals exactly one scene element. Leftover, unmapped parts mean the metaphor is wrong; recast.
4. **NAME** — commit to a two-to-five-word concept name. This becomes the diagram's label chip and its registry entry.
5. **RENDER** — build the scene with the print-safe vocabulary. Every arrow must represent a specific operation; every zone must carry a name; light backgrounds only.
6. **CHECK** — could a reader reconstruct the mechanism from the diagram alone? If not, return to CAST.

## 5. The paste-ready instruction block

Proposed addition to the authoring contract (README) or to any per-card prompt, placed immediately after the code example and before any diagram markup:

```text
## Diagram design step (mandatory, before any markup)
1. MECHANISM: state in one plain sentence what the code does. No framework jargon.
2. CAST: name three candidate real-world scenes whose structure matches the mechanism, each from a different family (flow, container, comparison, machine, social). One line each.
3. MAP: for the strongest candidate, write the mapping: each code element = one scene element. If anything is unmapped, cast again.
4. NAME: give the diagram its concept name (two to five words). It must not appear in the deck's Used Metaphors list.
5. RENDER: build the scene in print-safe HTML+CSS. Rules: every arrow is a labeled operation; every zone has a name; light backgrounds; no unlabeled box-arrow-box skeletons.
6. CHECK: could a reader reconstruct the mechanism from the diagram alone? If not, return to step 2.
Then emit the card line: **Diagram concept.** <Name> — followed by the markup.
```

Supporting machinery that makes the block bite:

- **Used Metaphors registry** — a running list per deck (like the typology list in `Gemini_instructions.md`) that the prompt includes and step 4 forbids reusing. Repetition is the main tell of lazy output; the registry makes freshness checkable.
- **Metaphor menu** — the family list in step 2 doubles as a catalog; choosing from a menu is easy for a model, inventing from nothing is hard. The menu is what turns "be creative" into a multiple-choice task.
- **The banned default** — step 5's "no unlabeled box-arrow-box" line names the failure mode explicitly. Models avoid named failures far better than unnamed ones.
- **Shot loop rubric** — after `node src/shot.mjs <demo> deck`, score the PNG: named scene? mapping complete? arrows are operations? zones named? print-safe? fresh versus the registry? Any "no" routes back to CAST.

## 6. Why this works on weaker models, and its limits

The structure compensates for exactly what weaker models lack: forced divergence (step 2 asks for three, because the first answer is always the modal answer), a menu to diverge within, an explicit verification (step 3) that catches wrong metaphors, and a banned default that removes the lazy attractor. Stronger models need less scaffolding but still benefit from the registry and the ban. Honest limits: instructions raise the floor and the median, not the ceiling — the online platform's best work may still come from open-ended sessions, so the division of labor from brief 001 (online invents, local transcribes) remains the fallback for flagship diagrams. Two real risks to police: forced metaphors can turn cheesy or misleading (the MAP step is the guard), and exemplars in context cause copying (keep exemplars in the style guide, not in the per-card prompt).

## 7. Proposed verification: exp-002 bake-off

Controlled test before adopting the block: pick one topic with no existing diagram (candidate: `$derived.by` vs `$derived`), then generate the same card twice with the same model — once under the current README instructions, once with the design-step block prepended. Same text, same code, diagram is the only variable. Compare `output/exp-002_derived-by/` shots side by side; if the block's card shows a named, mapped, fresh scene and the control shows box-arrow-box, adopt the block into the README contract and record the decision in brief 003. Variants follow the exp-001 convention: numbered files, one metaphor each.
